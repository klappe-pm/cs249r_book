# V3-12.04 The Trajectory Saga Pattern

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-sagas-architecture

When the repair worker dispatches its request to provision the temporary test environment, the remote service may allocate the virtual machine and start billing even if a network partition drops the return acknowledgment before it reaches the runtime. That lost reply breaks the binary assumption of a classical database saga, which coordinates a long-lived transaction across independent services by assuming that each local step either commits cleanly or aborts cleanly and reports which one happened. In an agent trajectory, the runtime can be left with an active cleanup obligation for a remote resource whose endpoint-assigned identifier has not yet arrived. A saga for agent tool calls therefore cannot merely log completed steps after they return; it must durably register each recovery obligation before dispatch and explicitly track what the runtime does not yet know.

**Definition 12.1: Trajectory saga**

***Trajectory saga*** is a recovery pattern that durably records constituent tool actions and coordinates compensating actions when established external effects must be remediated, while explicitly preserving unresolved outcomes and inter-action dependencies.

1.  **Significance**: Enables systematic recovery across independent external tools and services that share no common distributed transaction boundary.
2.  **Distinction**: Compensation represents new forward execution that produces its own observable outcome, rather than an atomic rollback or physical reversal of the environment.
3.  **Common pitfall**: Deferring cleanup registration until after receiving a successful forward response, creating a crash window where external resources leak without any durable record of their recovery obligation.

In its classical formulation, a saga consists of a sequence of separately committed forward steps ${F}_1, \dots, {F}_n$, each paired with a compensating step ${C}_i$ that the runtime executes if downstream failures require remediating earlier effects ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-garciamolina1987sagas|Garcia-Molina and Salem 1987]]). A forward action that produces no external side effect requires no compensation. When every forward step succeeds, the saga completes execution as ${F}_1, \dots, {F}_n$. If step ${F}_k$ fails, a linear saga unwinds by executing compensating actions in reverse order:

$$
{F}_1, \dots, {F}_{k-1}, {F_k^{\text{fail}}}, {C}_k, {C}_{k-1}, \dots, {C}_1, \tag{1}
$$

^eq-vol3-saga-unwind

where ${C}_k$ runs only when evidence confirms that the failed step actually produced an external effect. If the outcome of ${F}_k$ remains unknown, the runtime’s settlement rules keep the obligation for ${C}_k$ open rather than guessing. While [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^eq-vol3-saga-unwind|equation 1]] models an idealized sequential workflow, non-linear trajectories require a generalized directed cleanup graph. Each compensating step ${C}_i$ is itself an independent, separately committed operation with its own execution outcome; an unwind can stall partway through, leaving certain compensations settled while others remain pending or in flight.

### Obligation Registration

^sec-vol3-failure-recovery-obligation-registration

Registering a compensating step before dispatching the forward action creates an immediate addressing problem: when the worker sends a provisioning request, the cloud service has not yet created the environment or returned the handle needed to tear it down. Waiting until the reply arrives to log the cleanup would open a crash window in which a dropped connection orphans a live, billed environment with no local recovery record; the runtime instead durably registers a cleanup template *before* forward dispatch and binds the target identifier when evidence arrives. In our temporary test-infrastructure workflow, let `provision_test_env_r18` be the stable logical operation that provisions an isolated test environment, and let `release_test_env_r18` be its corresponding cleanup operation, a distinct logical identity that remains stable across retries and restarts. Neither identity should be confused with the endpoint-generated environment identifier. That system handle, denoted `env_r18_01` in a successful provisioning run, becomes known to the runtime only after correlated response evidence settles the forward operation.

The pre-dispatch cleanup template records the exact forward operation and payload, authorized capability scope, execution preconditions, dependencies, and an explicit rule for binding the returned environment identifier once it arrives. Appended directly to the write-ahead log alongside the forward admission record, this registration shares the forward attempt’s storage acknowledgment and resource reservation, avoiding the overhead and complexity of an independent state machine. Registering the cleanup before the effect it cleans up applies intent before effect (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-intent-before-effect|11]]) to the recovery obligation itself.

↩︎ The durable intent record written before dispatch is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-persistence-wal|Durable Intent Before Dispatch]]**.

The resulting template binds cleanup to the specific environment instantiated by this provisioning operation, rather than relying on transient metadata like display names. Durably registering this template establishes a binding commitment for future recovery rather than asserting that the resource already exists. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^tbl-vol3-compensation-registration|Table 1]] follows this distinction across each phase of the crash boundary.

| Boundary                                              | Durable obligation and available evidence                                                                                                               | Permitted interpretation                                                                                                  |
|:------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------|
| Before provisioning dispatch                          | `provision_test_env_r18`, exact request and scope, admission and reservation, and template for `release_test_env_r18` with an unbound environment field | Cleanup is planned; no generated resource identity or provisioning outcome is yet established                             |
| Provisioning intent survives, but its result does not | The same obligation and unresolved forward attempt                                                                                                      | The request may be delayed, running, or completed; missing evidence does not authorize another creation or settle cleanup |
| Adequate correlated provisioning evidence arrives     | The evidence binds `env_r18_01` to `provision_test_env_r18`; the binding is durably recorded                                                            | Cleanup can target that resource if its dependencies and preconditions hold and it passes the admission check             |
| Cleanup is dispatched                                 | A separate admitted intent for `release_test_env_r18`, with its own attempt identity, payload, reservation, and repeat contract                         | Cleanup is in progress or unresolved; sending the request does not establish release                                      |
| Adequate cleanup evidence arrives                     | Recorded evidence establishes the declared postcondition, or identifies remaining work and its owner                                                    | Close only the established part of the obligation; retain unsupported or partial outcomes explicitly                      |

Table 1: **Registration and deferred result binding**: The recovery obligation precedes the forward effect, while an endpoint-generated resource identifier is bound only when the evidence supports it.

^tbl-vol3-compensation-registration

When an acknowledgment is lost following dispatch, an idempotent result-recovery probe may retrieve the missing outcome. For a mutating tool without endpoint deduplication, this is the probe that the tool contract of **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^eq-vol3-legacy-tool-contract|equation 7.1]]** ships beside its actuate and compensate routines. The template registered here instantiates that contract’s compensate routine for one specific, bound resource. If probing is unsupported or inconclusive, settlement rules mandate that the operation remain open with an assigned recovery owner. A naive runtime might query the external service, observe that the environment is absent, and prematurely close the cleanup record on the assumption that creation failed. Doing so creates a race condition. If the original provisioning request was merely delayed in transit, the remote service may instantiate the environment seconds later, leaving an **orphaned resource** that accrues compute charges indefinitely without any controlling process. If the endpoint supports explicit request cancellation, the runtime can invoke that contract to terminate the pending creation, provided the endpoint guarantees that canceled requests will not take effect downstream.

↪ Result recovery, as distinct from repeated execution, is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Distributed State Foundations#^sec-vol3-appendix-systems-retries|Repetition and Result Recovery]]**.

### Semantic Compensation

^sec-vol3-failure-recovery-semantic-compensation

Once `env_r18_01` is bound and a failed integration run triggers `release_test_env_r18`, the runtime must verify that teardown succeeded even though the external world cannot be rewound to its state before provisioning. Rather than checking for an impossible physical reversal, the runtime checks whether the compensating action has re-established a declared set of postconditions while leaving outside side effects to their own lifecycles.

**Definition 12.2: Semantic compensation**

***Semantic compensation*** is an independent forward action designed to establish declared application postconditions following an earlier side effect, without claiming to erase execution history or restore every dimension of the external environment.

1.  **Significance**: Provides a verifiable, checkable objective for recovery when exact physical or historical reversal is impossible.
2.  **Distinction**: Releasing a temporary environment terminates its active allocation; it does not un-send network packets, erase system audit logs, or refund consumed compute charges.
3.  **Common pitfall**: Treating an endpoint’s asynchronous acceptance response as proof that declared postconditions have been achieved when only request receipt has occurred.

In our running example, the compensation contract stipulates that the task-owned environment must no longer be allocated and that no active integration test may still depend on it, requiring any diagnostic artifacts to be transferred to durable storage prior to deallocation. The contract also defines what evidence the endpoint must supply to demonstrate successful release. Because final billing charges often settle asynchronously hours after an environment is torn down, the runtime decouples the physical resource obligation from financial settlement.

Formally, let ${\sigma_0}$ represent the state of the environment prior to executing forward step ${F}$, and let ${\sigma_0'}$ denote the state after executing ${F}$ followed by its compensating action ${C}$. Because physical time cannot be reversed and side effects alter audit trails and financial balances, ${\sigma_0'}$ and ${\sigma_0}$ inevitably differ. Compensation guarantees equivalence only with respect to an explicitly declared set of postcondition predicates ${\Phi}$. The compensation succeeds if and only if both states agree on every predicate in ${\Phi}$:

$$
{\sigma_0'} \equiv_{{\Phi}} {\sigma_0} \iff \forall {\phi} \in {\Phi}:\ {\phi}({\sigma_0'}) = {\phi}({\sigma_0}). \tag{2}
$$

^eq-vol3-semantic-equivalence

Here, predicates such as “the environment is allocated” and “an admitted test depends on it” belong to ${\Phi}$, and both evaluate to false in ${\sigma_0}$ and ${\sigma_0'}$. In contrast, billing records and audit histories lie outside ${\Phi}$, which is why financial reconciliation requires an independent settlement lifecycle. A compensation contract claims to satisfy only the predicates explicitly declared in ${\Phi}$; unmodeled side effects remain unaddressed.

Compensation inevitably operates on an environment that has moved on. External services or human operators may have observed the intermediate state, consumed compute seconds cannot be un-billed, and concurrent processes can alter cleanup preconditions. For instance, if a peer workflow has attached to the temporary environment for joint debugging, the originating agent cannot unilaterally destroy the resource simply because its own plan stalled. The runtime’s admission control boundary must inspect live ownership and active dependency graphs at the moment of compensation, rather than blindly following stale planning text.

Local workspace restoration plays a complementary but narrower role. A compatible checkpoint restores only the local workspace projection managed directly by the runtime. Checkpoints cannot reset remote cloud environments, running external daemons, dispatched batch jobs, or accrued service charges. Those external side effects demand semantic compensation. When recovery requires both local rollback and remote compensation, the runtime orchestrates both mechanisms, verifying the independent outcome of each path before declaring the system recovered.

↩︎ Checkpoint restoration, which reinstates the record and workspace without re-executing external actions, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.05 Checkpoints#^sec-vol3-durable-execution-recovery-boundaries|Consistent recovery boundaries]]**.

### Cleanup Failures

^sec-vol3-failure-recovery-cleanup-failures

Because cleanup actions cross the same external tool boundaries as forward actions, they encounter the same failure modes: network drops, rate limits, and remote service outages. Consequently, every compensating operation must pass admission control, and its intent must be durably committed before dispatch. When retrying a failed cleanup call, the runtime assigns each transport attempt a unique attempt identifier, while `release_test_env_r18` continues to designate the persistent logical operation. Retries adhere to the endpoint’s repeat contract. The stable logical key ensures that duplicate deletion requests execute safely without targeting a different resource if the external system reuses names or identifiers.

↩︎ Stable operation identities, with a fresh attempt identity for each retry under the endpoint’s repeat contract, are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|Operation identity and endpoint contracts]]**.

The coordinator retires a compensation entry only upon receiving verifiable outcome evidence, rather than assuming success simply because a remote call returned without a transport error. If a release call times out, three states remain possible: the environment may be gone, it may still be undergoing deallocation, or it may remain allocated. The settlement rules keep all three possibilities open. Furthermore, cleanup actions consume quota and wall-clock execution budget; a timed-out call refunds nothing. If cleanup cannot progress further within its assigned budget, the obligation stays on record with its accumulated evidence and an assigned escalation owner. In this way, a failed agent trajectory can terminate safely without masking unresolved external leaks.

Preregistered cleanup templates execute under the supervision of the trusted runtime coordinator without invoking another model inference step. This separation enforces least-privilege control: even if the model’s forward execution authority is revoked following an anomaly or budget exhaustion, a narrowly scoped cleanup grant remains accessible to the coordinator to tear down provisioned resources. If remediation requires operations beyond this pre-authorized grant, the runtime does not guess; it halts and issues an explicitly owned handoff. Later authenticated evidence or manual operator actions can settle the obligation without restarting the obsolete agent trajectory.

### The Cleanup Graph

^sec-vol3-failure-recovery-cleanup-graph

Tearing down `env_r18_01` the moment a failure is detected would sever an integration test that is still running inside it and destroy diagnostic logs before they are copied to durable storage, whereas deleting an unrelated local scratch directory need not wait for either step. A simple last-in, first-out (LIFO) unwind stack is adequate only when an agent executes a strictly linear sequence and every cleanup precondition follows that reverse order. When an agent invokes tools concurrently, triggers asynchronous background tasks, or branches across speculative plans, recovery requires tracking explicit causal dependencies in a directed **cleanup graph** $({V},{E})$, where each vertex represents an admitted cleanup operation and a directed edge

$$
{C}_j \rightarrow {C}_k
$$

signifies that compensating operation ${C}_j$ must establish its declared settlement conditions before ${C}_k$ is permitted to dispatch. Declared cleanup dependencies must form a directed acyclic graph (DAG); cyclical dependencies represent contradictory recovery requirements that demand explicit operator intervention rather than an arbitrary stack ordering.

In our temporary environment scenario, confirming that the test process has stopped (or canceling it and verifying termination) and preserving diagnostic test artifacts outside the sandbox are both predecessors of `release_test_env_r18` in $({V},{E})$. Removing the unrelated local scratch directory forms an independent vertex with no edges to the environment release, provided no active test or pending evidence collection depends on it. The cleanup graph answers what must happen first, settlement rules determine what has been empirically verified, and admission control determines which operations may run next. The graph cannot be sequenced until provisioning evidence has bound its target, which is why [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^fig-vol3-saga-flow|figure 1]] draws the release ordering beneath the registration step it depends on.

![[90 Assets/Volume III/12 Failure Recovery/Vol3 Saga Flow e4d1d51db6.svg]]

Figure 1: **Registration Before Dispatch, Release After Evidence**: The forward lane records the cleanup obligation before `provision_test_env_r18` is sent, and binds `env_r18_01` only when correlated evidence arrives; a lost reply leaves the obligation open with an owner instead of guessing a target. The dashed link shows the binding supplying the target of the registered cleanup. In the cleanup lane, `release_test_env_r18` waits for its predecessors, and its own outcome either closes the obligation or remains owned, so no path ends in an assumed clean state.

^fig-vol3-saga-flow

Structuring cleanup as a DAG isolates failures and enables concurrent unwinding. An unresolved or failed cleanup node blocks only its transitive dependents in $({V},{E})$; independent recovery subgraphs can proceed immediately once their predecessors settle, their preconditions hold, and they clear admission control. Executing independent cleanup actions in parallel reduces overall recovery latency.

The cleanup graph enforces ordering without erasing historical accountability. Settled nodes retain their verification evidence, while failed or ambiguous nodes remain bound to their assigned owners. While an authorized administrator may deliberately accept residual risk to unblock downstream execution, the system never silently records an unconfirmed release as clean.

### Branch-Scoped Compensation

^sec-vol3-failure-recovery-branch-compensation

If an agent creates a cloud test sandbox during a common trajectory prefix before branching into three candidate test configurations, tearing down that sandbox when Candidate B fails would sabotage the active experiments in Candidates A and C. During tree search or multi-candidate exploration, branch ancestry tracks where model execution diverged, but it reveals nothing about which external resources each branch still claims.

The runtime therefore decouples resource ownership from logical branch history by tracking effects and cleanup obligations through reference-counted dependency graphs. When the runtime abandons a speculative branch, it reclaims only those resources owned exclusively by that branch, once its outstanding work has settled or stopped cleanly. Shared resources remain allocated until all surviving dependencies permit release. Furthermore, if an abandoned branch dispatched a provisioning request whose outcome remains unknown, that request stays recorded in the durable operation table; pruning a branch from the scheduler does not erase an unresolved external obligation.

Restoring a branch’s local workspace or context window does not rewind the external environment to the branch point, and evidence gathered from an abandoned candidate cannot be assumed valid for a sibling branch merely because they share an ancestor. During counterfactual execution, local workspaces can be rolled back to earlier checkpoints, but external networks, databases, and billing meters cannot. Enforcing this distinction ensures that speculative branch pruning never silently discards external recovery duties.

↩︎ Counterfactual branches, which replay a recorded prefix and then require fresh observations, are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.07 Recorded Trajectory Replay#^sec-vol3-durable-execution-counterfactual-branches|Counterfactual branches]]**.

**Checkpoint 12.1: Compensation obligations and dependency scope**

Compensation is registered before dispatch and settled by evidence afterward. Each prompt places an obligation on one side of that boundary.

**Registration**: Provisioning returns its resource identifier only after creation. What must be recorded before dispatch, and what can be bound only afterward?

**Unknown creation**: Why does an empty resource lookup not justify closing cleanup while a provisioning request may still be delayed?

**Cleanup outcome**: Release is accepted but completion is unconfirmed. Which resource and charge obligations remain, and what evidence could settle each?

**Cleanup graph**: Draw the graph for four nodes: end the test, preserve artifacts, release the environment, delete unrelated private scratch. Which nodes can run in parallel, and which one waits if ending the test stays unresolved?

**Branch scope**: Two branches share an environment. Why does abandoning one branch not authorize releasing it or discarding its unresolved operations?

While semantic compensation systematically remediates partial effects, unwinding external work is not always the right response to a fault. When earlier steps have already built healthy, reusable state and a subsequent step fails before touching it, tearing those resources down wastes time and budget that a bounded in-place fix could preserve. Deciding whether to unwind or repair in place requires comparing the expected cost of forward correction against the expense of backward unwinding and rebuilding.
