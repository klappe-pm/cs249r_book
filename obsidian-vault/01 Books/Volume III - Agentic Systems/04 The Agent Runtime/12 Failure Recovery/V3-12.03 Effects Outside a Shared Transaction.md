# V3-12.03 Effects Outside a Shared Transaction

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-sagas-acid-boundary

When the integration suite crashes inside the temporary test environment, rolling back the agent runtime’s local database cannot reach across the network to deallocate the remote virtual machine. Even if the cloud provider’s environment service executes internal database transactions with strict ACID guarantees, its database and the runtime’s execution log commit in separate administrative domains with no shared atomic boundary. Inside a single database or a tightly coupled cluster, a locking transaction holds exclusive locks until commit or abort, and two-phase commit coordinates an atomic decision across cooperating resource managers ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-gray1981transaction|Gray 1981]]). In two-phase commit, each participant first prepares by writing the recovery state needed to either commit or abort on command, and then holds its locked resources in that prepared state until the coordinator announces the global decision. Agent tool workflows break both requirements of that protocol. First, the external endpoints an agent invokes commit each request on receipt and rarely expose a prepare phase or accept the agent runtime as their transaction coordinator. Second, even where internal services do cooperate, a prepared participant must keep its resources locked while waiting for the coordinator, and a coordinator crash while participants are prepared prolongs that wait until recovery completes. Holding database locks or reserved capacity across model generation, long integration tests, or asynchronous human review would stall competing work for unacceptable periods. Across the independently administered services in this workflow, recovery therefore relies on tentative operations, explicit cancellations, and idempotent exchanges rather than assuming a shared transaction ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-helland2007life|Helland 2007]]).

When atomic rollback across independent boundaries is impossible, systems must rely on **compensation**:[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn2|²]] a forward-executing operation that establishes acceptable postconditions after a prior effect has already committed. Compensation does not erase history or restore the universe to its pristine pre-transaction state. For example, releasing a cloud-hosted development environment deallocates its virtual compute instances and stops active billing meters. The provisioning event, network ingress logs, and financial charges already accrued remain permanent, and the teardown request itself may fail on an unreachable network. To structure multi-step workflows without global isolation, Garcia-Molina and Salem introduced the **saga** pattern for long-lived transactions ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-garciamolina1987sagas|Garcia-Molina and Salem 1987]]). Rather than treating the entire trajectory as a single atomic unit, a saga partitions execution into a sequence of smaller, independently committed steps. It pairs each forward step with a compensating action designed to mitigate its side effects if a later step fails.

↪ Two-phase commit’s blocking behavior and the original saga abstraction are developed in **[[05 Reference/Volume III - Agentic Systems/V3 Distributed State Foundations#^sec-vol3-appendix-systems-transactions|Classical Transaction Background]]**.

Compensation is not the only recovery strategy. Apart from a plain retry of an operation whose repeat contract permits one, an agent runtime chooses among three families of response:

1.  *Compensation*: execute explicit counteracting operations to neutralize partial side effects.
2.  *Forward repair*: preserve valid intermediate artifacts, such as a successfully compiled binary or a provisioned database schema, and adjust subsequent steps rather than discarding completed progress.
3.  *Escalated handoff*: halt autonomous dispatch and transfer unresolved obligations, active resource handles, and diagnostic logs to an authorized human operator.

The runtime balances available evidence against projected forward costs to choose among these alternatives; capital and compute time already expended are sunk costs that must not distort future recovery decisions. Whichever path it selects, two rules that the harness already enforces govern the choice, and recovery is where both are tested hardest.

The settlement rule governs what the runtime may believe about an external effect. The harness stated it as a rule about the operation table: withdrawing an operation’s observation eligibility never settles the operation, and only authenticated, correlated evidence does. Recovery needs the rule in a sharper form, as three mutually exclusive evidence states for every dispatched operation: *established*, *established absent*, or *unknown*. An outcome begins as unknown, and only evidence correlated with that specific operation, interpreted through the target endpoint’s contract, can move it to established or established absent. A dropped TCP acknowledgment, an HTTP gateway timeout, an asynchronous accepted-but-pending status, or a status query that returns nothing while the original request may still be in transit all leave the outcome unknown. An unknown outcome keeps its liability reservation against the task budget, keeps a durable record with a named owner, and blocks any forward action that presupposes either success or failure. The runtime may repeat the dispatch only when the endpoint’s verified repeat contract makes re-execution safe, which is settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]).

↩︎ The settlement rule, which separates observation eligibility from settling the operation, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.04 The Trajectory Record#^sec-vol3-controlplane-acb|The Trajectory Record]]**.

The admission check governs what the runtime may do next. Every candidate operation passes the same predicates the harness applies to ordinary work, whether it is forward progress, a retry, an environment repair, a status probe, or a cleanup action. The predicates are valid authority and approval, satisfied dependencies, available capacity, and enough time before the deadline. They also require a reservation whose bounded liability fits beside actual consumption, outstanding liability from unsettled operations, and the protected finalization reserve. The check is re-evaluated at the dispatch boundary immediately before transmission, so a plan-time approval or an earlier durable intent cannot override a later administrative hold, a revoked token, or a depleted budget. Recovery operations receive no exemption. Organizational liability for remote infrastructure does, however, outlive the agent’s reasoning loop, so administrative cleanup backed by independent operational credentials can still pass admission and decommission orphaned resources long after model-directed continuation has ended.

↩︎ The admission check and the finalization reserve it protects are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-agent-harness-transition-guards|Transition guards and the admission check]]**.

A naive undo stack, such as a reversed list of tool invocations that maps server creation to server deletion, is too brittle to satisfy either the settlement rule or the admission check. In-flight operations fail asynchronously, remote endpoints drop responses, and partial writes leave external resources in states that cannot be resolved by replaying inverse functions with original arguments. Instead, the runtime must persist a structured recovery obligation *before* allowing any request to cross the network boundary. This obligation captures correlation identifiers, parent-child causal links, parameter snapshots, timeout thresholds, and settlement state, providing the durable bookkeeping needed to handle partial failure without leaking resources. The trajectory saga pattern formalizes this durable record of obligations.
