# V3-12.11 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-failure-recovery-fallacies

Recovery errors in agentic architectures arise when engineers treat evidence gathered at one system boundary as an absolute guarantee about the state across another. Each fallacy or pitfall below mistakes a local record, a timeout, or an intermediate guard for settled external reality.

**Fallacy**: *A local transaction or durable log makes a whole tool workflow atomic.*

A local database transaction or write-ahead log protects only the state that directly participates in it, such as an internal outcome record and its corresponding outbox entry. Side effects produced by external tools remain outside that boundary, no matter how meticulously the runtime logs each invocation ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.03 Effects Outside a Shared Transaction#^sec-vol3-sagas-acid-boundary|section 12.2]]). Reliable recovery architectures must clearly delineate the true atomic boundary, treat downstream outcomes as unknown whenever execution halts ambiguously, and preregister compensation actions for every side effect that can escape into external systems.

**Pitfall**: *Treating a timeout as permission to try a new operation.*

When an external tool call times out, the earlier request often continues executing to completion on the remote service. For example, issuing a fresh provisioning request immediately after an earlier call times out can leave two live cloud environments running concurrently, one of them unowned, unmonitored, and accumulating billing charges. Systems must settle the definitive state of the original operation before proceeding, repeating requests only within the strict idempotency guarantees of that endpoint’s contract ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.05 Forward Recovery#^sec-vol3-sagas-forward-vs-backward|section 12.4]]). Retrying an existing request, proposing a mutated alternative, and issuing a compensating transaction represent three distinct operations, each requiring its own explicit admission check.

**Fallacy**: *Crossing a pivot guarantees forward completion and retires cleanup.*

Crossing a pivot point commits the system to forward recovery and narrows remaining fallback options, but it provides no guarantee that subsequent operations will succeed. In the remediation scenario, even after canary checks approve a rollout to proceed, 71.4 percent of the remaining expected irreversible loss stems from erroneous modifications that slipped past the pivot undetected (notebook [12.2](https://mlsysbook.ai/vol3/12_failure_recovery/12_failure_recovery.html#nbk-12-pivot-expected-loss)). These failures demand bounded follow-up procedures and designated human ownership, while outstanding cleanup tasks must remain durably recorded until explicitly settled.

**Pitfall**: *Equating a repeated state or an open breaker with a resolved failure.*

Observing an identical state digest does not necessarily indicate an unproductive loop; intentional search and backtracking algorithms generate the exact same fingerprint. Similarly, an open circuit breaker merely blocks new admissions within its protection scope while allowing in-flight external calls to continue executing. Runtimes must record precisely why an intervention took place and track which side effects remain unresolved. Enforcing execution boundaries at the infrastructural admission gate ensures that system constraints hold even when a planning model disregards an advisory prompt.

**Fallacy**: *A cumulative budget ceiling is enough to catch a looping trajectory.*

While a cumulative financial ceiling caps catastrophic expenditure, an agent trapped in an append-only context loop typically exhausts nearly the entire allocation before the threshold trips. In notebook [12.3](https://mlsysbook.ai/vol3/12_failure_recovery/12_failure_recovery.html#nbk-12-loop-cost), running an errant trajectory until it hits the 50-turn ceiling costs \$4.42, roughly 88.7× the \$0.050 incurred when halting at turn 4, because quadratic context accumulation inflates token volume on every turn. A cumulative ceiling functions merely as an emergency backstop, whereas active progress detectors with low detection latency provide the operational control.

**Pitfall**: *Letting every layer retry on its own allowance.*

When a client library, an API gateway, and a trajectory-level recovery orchestrator each independently permit 3 attempts, retries multiply across the system stack. A single failing logical operation can barrage downstream services with 27 requests instead of the intended 3, amplifying load precisely when an already degraded dependency is least able to absorb it. System designers must assign the retry allowance for each logical operation to a single authoritative owner that coordinates attempts across all 3 layers ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.08 Tool Circuit Breakers#^sec-vol3-sagas-containment|section 12.7]]).
