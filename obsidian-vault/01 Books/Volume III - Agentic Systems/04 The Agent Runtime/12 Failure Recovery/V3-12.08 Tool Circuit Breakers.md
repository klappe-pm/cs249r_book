# V3-12.08 Tool Circuit Breakers

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-sagas-containment

When an external dependency such as an automated test harness or a code-execution sandbox slows down under load, multiple concurrent agent trajectories queue up behind it. A watchdog timer can suspend an individual stalled trajectory, but other trajectories continue submitting tests to the same saturated service, while underlying client libraries inject retries beneath the agent’s high-level proposals. System recovery therefore requires bounding aggregate load across the entire dependency pool rather than policing the execution limits of individual tasks.

A service slowdown does not, by itself, imply an increasing request rate. For a closed population of sequential clients, longer round-trip latencies depress the arrival rate of new requests because each client waits longer between turns. Work amplification emerges instead through feedback loops. Automated retries multiply outbound attempts. An abandoned timeout leaves orphaned work executing on the remote server while a replacement job begins. Uncoordinated middleware layers duplicate retries in nested stacks, and widespread simultaneous errors synchronize the subsequent wave of arrivals.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn8|⁸]] An agent runtime must identify which mechanism is driving downstream load, rather than treating every timeout as an invitation to fire off another attempt.

Containing these feedback loops requires pairing three complementary controls across the dependency boundary. When a dependency is actively failing, a *circuit breaker* intercepts and withholds new outbound calls based on recent infrastructure health signals. For calls that remain eligible to retry, a single retry owner applying *exponential backoff with jitter* spaces out and desynchronizes the attempts. While calls are in flight or queued, *bulkheads* cap the concurrency and queue slots that any one dependency can occupy on the host. None of these controls establishes whether an earlier in-flight operation, such as the unconfirmed `test_r18` execution, ever ran to completion on the remote host.

### Breaker Scope and Failure Classification

^sec-vol3-failure-recovery-breaker-scope

If a single circuit breaker covers an entire multi-tenant tool service and counts every client schema error as an outage, one malformed agent trajectory can trip the breaker and lock out every healthy tenant in the fleet. A **circuit breaker** avoids that collateral outage by enforcing a dynamic admission policy over a clearly delineated dependency boundary ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-nygard2007releaseit|Nygard 2007]]). This boundary, the breaker’s scope, may correspond to a specific remote API endpoint, an entire geographical region, an isolated compute cluster, or a single tenant’s quota partition. If a downstream service returns a quota exhaustion error for one tenant, a tenant-scoped breaker trips only for that tenant’s traffic rather than cutting off access for the entire fleet. The breaker’s configuration determines which failure modes count against its health budget, the sliding observation window and minimum sample size required before taking action, and the protocol for probing whether the dependency has recovered.

Separating infrastructure failures from client errors is what keeps that health budget accurate. An outcome should count against the dependency’s health only when it reflects an inability of the service to handle work, such as dropped TCP connections, transport timeouts, internal server errors, or explicit throttling directives targeted at that scope. Conversely, a client or domain rejection returned by the scoped endpoint can be neutral for this breaker’s infrastructure-failure metric even when the task fails. A returned schema error, permission denial, authentication failure, or ordinary “record not found” response establishes that the responding endpoint handled that request; it does not establish that every operation of the dependency is healthy. A rejection produced by local validation or authorization before dispatch supplies no observation of the dependency and must not enter its health window.

For the policy used here, the window includes dispatched calls with classified outcomes at this dependency scope, including endpoint-generated client/domain rejections as nonfailure observations. Locally withheld proposals are excluded. Other policies may exclude neutral endpoint responses as well, but must state that denominator explicitly. Formally, consider a rolling window ${W}$ of recent classified outcomes. Let ${e}_i = 1$ if call ${i}$ was a counted infrastructure failure and ${e}_i = 0$ otherwise. The breaker trips to the `OPEN` state when

$$
\lvert {W}\rvert \ge {n_{\min}} \quad\text{and}\quad {r} = \frac{1}{\lvert {W}\rvert}\sum_{i \in {W}} {e}_i \ge {r_{\text{trip}}}, \tag{7}
$$

^eq-vol3-breaker-trip

where ${n_{\min}}$ represents the minimum evidence threshold required to prevent early spurious trips during periods of low traffic, and ${r_{\text{trip}}}$ is the policy’s failure-fraction threshold.

[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.08 Tool Circuit Breakers#^tbl-vol3-circuit-breaker-states|Table 7]] adapts the classic three-state machine to tool-call admission. These gate-level states belong to one dependency scope and are distinct from the trajectory states that the control plane governs.

| Breaker state | Admission policy                                                                   | Evidence used to change it                                                             |
|:--------------|:-----------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------|
| `CLOSED`      | Permit consideration of calls; the admission check and repeat contract still apply | Current scoped outcomes meet the configured trip rule                                  |
| `OPEN`        | Withhold new ordinary calls to this scope                                          | Cooldown and current policy permit a limited trial                                     |
| `HALF_OPEN`   | Admit only the bounded probe allowance; hold or reject other calls                 | Current-generation probe evidence supports reopening or a controlled return to service |

Table 7: **Scoped Circuit-Breaker States**: Breaker admission gates govern subsequent outbound dispatches across a dependency boundary, while in-flight executions and capacity guarantees remain governed by settlement protocols.

^tbl-vol3-circuit-breaker-states

Tripping the breaker to `OPEN` governs subsequent call admissions only; it leaves requests that have already crossed the network boundary to resolve under their existing transport and settlement rules. The runtime records a withheld request as rejected at the gate, not as dispatched. The gateway returns a structured observation naming the blocked scope and the estimated cooldown, which lets the model revise its plan or choose another tool, but containment rests on enforcement at the gateway, not on the model heeding that message.

The `HALF_OPEN` state needs concurrency control. Under a single-probe policy, the gateway claims the probe permit atomically before dispatch; otherwise dozens of workers waking at the end of a cooldown would each act as the probe and re-saturate the recovering dependency. Each trial cycle also increments a monotonic `breaker_generation` counter, recorded with the probe’s identity at admission, and only a response carrying the active generation may change the breaker’s state. The counter is local fencing metadata, distinct from a trajectory’s `control_epoch` and from an authenticated storage `owner_epoch`.

↩︎ Fencing tokens and the `owner_epoch` that a replacement worker installs at enforcing boundaries are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-durable-execution-availability-ownership|Availability and ownership]]**.

If a dispatched probe times out or fails, the breaker immediately reopens to `OPEN` and increments `breaker_generation`. Robust policies also lengthen the subsequent cooldown interval via exponential backoff:

$$
{T_{\text{cool}}} \leftarrow \min(2\,{T_{\text{cool}}},\, {T_{\text{cool}}^{\max}}),
$$

ensuring that an uncooperative or persistently degraded dependency receives geometrically fewer probe attempts up to the ceiling ${T_{\text{cool}}^{\max}}$. If a delayed response from an earlier probe generation eventually succeeds, that late arrival can settle its own operation record and its charges, but the generation guard prevents it from closing the newly reopened breaker or usurping a newer trial’s slot.

A probe is a concrete network operation, not a cost-free diagnostic abstraction. It must pass normal admission checks and follow a safe operational contract. A supported read-only status query serves well as a probe; issuing a resource-creation request under the label of a health probe risks creating orphaned remote state. Moreover, because a successful probe proves only that the service handled a single isolated request, the gateway must restore regular traffic gradually under rate-limiting and concurrency constraints. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.08 Tool Circuit Breakers#^fig-vol3-circuit-breakers|Figure 4]] illustrates transitions across the three breaker states (`CLOSED`, `OPEN`, `HALF_OPEN`). Failure rates trip the breaker, atomic probe slots govern trial execution, generation counters fence out late responses, and consecutive probe failures double the cooldown interval (${T_{\text{cool}}}$) up to its maximum ceiling.

![[90 Assets/Volume III/12 Failure Recovery/Fig Vol3 Circuit Breakers 8c6cf05fc1.svg]]

Figure 4: **Scoped Breaker Transitions**: The breaker trips from `CLOSED` to `OPEN` only when the window holds at least ${n_{\min}}$ classified outcomes and their failure fraction reaches ${r_{\text{trip}}}$, as in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.08 Tool Circuit Breakers#^eq-vol3-breaker-trip|equation 7]]. After the cooldown, one probe slot is claimed atomically; only a result from the current generation may close the breaker, while a failed probe reopens it, advances `breaker_generation`, and lengthens the cooldown up to its cap. A late result from an older generation settles its own operation in the operation table and changes no breaker state. Thresholds and cooldowns are policy parameters.

### Retry Coordination and Jitter

^sec-vol3-failure-recovery-retry-coordination

![[90 Assets/Volume III/12 Failure Recovery/Vol3 Failure Recovery Margin Retry Layers c6dd43c033.svg]]

*A tree from one red square on the left branching into 3 violet dots, then 9 violet dots, then 27 small violet dots, with the counts 1, 3, 9, and 27 printed beneath the columns.*

*Three independent retry layers turn one failing call into 27 attempts.*

When a client library, an intermediate API gateway, and an agent planning loop each retry a failing call on independent allowances, their retries multiply downstream load just when the dependency is failing. If each of those 3 layers allows 3 attempts (one try plus two retries) on its own allowance, a single failing logical operation sends 27 requests downstream, one for every path through the 3 layers. A single owner holding the same allowance would send 3 ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-brooker2019timeouts|Brooker 2019]]). The multiplier grows exponentially with the number of layers; delegating retry authorization to a single designated component and accounting for attempts across all layers in one shared budget removes it.

Before scheduling any retry, the governing component must apply the settlement rules and idempotency contracts. The system preserves the original logical operation identifier while distinguishing individual network transport attempts. If the agent mutates the request payload, for example by adjusting a flag after an intermediate reflection step, the runtime treats the invocation as a brand-new logical operation rather than a retry attempt. Once scheduled, the retry must pass through all admission checks exactly like fresh traffic; waiting out a backoff window confers no privileged bypass of gateway admission policies.

When multiple requests fail simultaneously during a service disruption, retrying after identical, fixed delays preserves their synchronization, causing recurrent traffic spikes at each retry step. **Capped exponential backoff with full jitter**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn9|⁹]] breaks this synchronization by doubling the backoff ceiling exponentially up to a maximum cap and drawing the actual delay uniformly at random:

$$
{b}_j = \min({b_{\max}}, {b}_0 2^{j}), \qquad {d}_j \sim \operatorname{Uniform}(0,{b}_j). \tag{8}
$$

^eq-vol3-full-jitter

Here ${j}=0$ indexes the first retry, ${b}_0$ represents the base backoff duration, and ${b_{\max}}$ enforces an upper bound on the backoff ceiling. Brooker’s analysis of retry strategies demonstrates that full jitter minimizes client contention and total completion times compared to uniform or decorrelated alternatives ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-brooker2015backoff|Brooker 2015]]). The parameter ${b_{\max}}$ caps the span of individual delay intervals rather than the total number of attempts. Furthermore, if a downstream dependency returns explicit backoff metadata (such as an HTTP `Retry-After` header), that server-specified minimum overrides any shorter delay sampled locally.

While independent jitter alters the arrival distribution and suppresses average contention, it supplies no deterministic reduction in peak burst size because random draws can cluster and coincide with background traffic. Rate-limiting gates and concurrency bulkheads must therefore inspect every request following its delay, re-evaluating admission rules and `breaker_generation` before dispatch. When the breaker remains open, the gateway must reject the request cleanly, preventing the agent runtime from spinning in an unthrottled loop of failed retries and redundant model inferences.

### Bulkhead Isolation

^sec-vol3-failure-recovery-bulkhead-isolation

Without per-dependency concurrency limits, one unresponsive tool, such as an overloaded code-formatting service, can tie up every worker slot in the host runtime until the agent can neither run local commands nor commit checkpoint state. **Bulkhead isolation** prevents a single stalled dependency from starving the rest of the runtime by partitioning system resources into segregated compartments with explicit concurrency and queue limits per external dependency ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-nygard2007releaseit|Nygard 2007]]).

Systems architects must distinguish between the specific physical resources being constrained. Blocking worker threads, asynchronous event handles, open TCP sockets, retained payload buffers, and remote job reservations represent different resource pools. Switching an agent engine from synchronous threads to asynchronous coroutines frees operating system threads, but an unresolved asynchronous call still consumes file descriptors, socket buffers, and heap memory for in-flight context. Effective bulkheads define explicit limits for each bottleneck resource.

Little’s law (theorem [5.1](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#thrm-05-littles-law)) relates mean occupancy to admitted throughput and mean slot residence in a stable system. If each admitted call holds one worker until the same external timeout and there is no other worker residence in this calculation, their product gives mean blocked workers. Applying the offered request rate instead estimates the worker demand the dependency would create if every request were admitted. For sustained smooth traffic, negligible scheduling gaps, and work-conserving service, clipping that demand at the pool size gives a fluid occupancy estimate. Here ${\lambda_{\text{arr}}}$ denotes the offered request rate, ${T_{\text{out}}}$ the timeout, and ${N_{\text{pool}}}$ the pool size:

$$
{N_{\text{blocked}}} = \min({N_{\text{pool}}},\, {\lambda_{\text{arr}}} {T_{\text{out}}}). \tag{9}
$$

^eq-vol3-blocked-workers

When offered demand reaches or exceeds the pool size, this approximation predicts saturation if enough dependency work remains queued to keep every worker busy. It does not determine exact occupancy or time to exhaustion under arbitrary arrivals, admission rejection, or competing local work. Without a dependency cap, those blocked calls can deny local work a worker even when the local operation itself is fast.

Bulkheads bound queue capacity as well as active concurrency. When both are full, the gateway fails fast, rejecting further requests at admission and reporting that disposition to the task’s recovery manager. A deeper queue absorbs transient bursts at the cost of memory and wait time, and no queued request may be dispatched after the task’s deadline has passed.

Local concurrency bounds do not constrain remote work that outlives a client-side timeout. Closing a local socket leaves the test or compilation running on the remote cluster, so bounding downstream blast radius means bounding outstanding logical operations and their liability, through cooperative cancellation or by withholding further submissions. Partitioned thread pools likewise do nothing about shared-disk or network saturation caused by concurrent jobs. A bulkhead protects only the quantities it explicitly limits.

*Jitter lowers the expected retry rate, not the possible peak.*

**Napkin Math 12.4: What capacity and jitter actually bound**

**Problem**: Which worker-occupancy limits can bounded admission guarantee in the stated burst, and which retry-arrival quantities does jitter determine only in expectation?

**Occupancy**: Suppose 256 trajectories each submit one blocking external call to an otherwise idle pool of 300 workers. No call finishes during the admission burst, and there are no nested calls. Without a dependency cap, only 44 workers remain free for everything else. This is the transient burst before any timeout fires; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.08 Tool Circuit Breakers#^eq-vol3-blocked-workers|equation 9]] gives the separately stated smooth-load estimate, while the explicit dependency cap bounds worker occupancy in either case.

**Bounded admission**: Now cap that dependency at 64 occupied workers and 32 waiting requests. Queued requests do not occupy workers. The burst fills both limits and rejects 160 requests before dispatch. It cannot occupy 236 workers in the shared pool. The cap protects worker slots, not CPU time or storage access.

**Retry arrivals**: Separately, consider 128 eligible retries released at one time, with no subsequent retries or unrelated traffic. If they all arrive in a stipulated 2 ms interval, the average over that interval is 64,000 requests/s. If each independently chooses an arrival uniformly across 2 s, the expected offered rate inside that interval is 64 requests/s. A fixed 2 ms subinterval has expected count 0.128; its realized count can be larger.

**Systems insight**: A cap provides a deterministic bound on concurrency, while jitter shapes only the expected arrival rate over time. With the cap in place, the stalled dependency can hold at most 64 workers regardless of how long the stall persists, making the cap size the maximum fraction of the pool that the dependency can ever monopolize. Jitter lowers the mean offered rate 1,000-fold, from 64,000 requests/s to 64 requests/s. That factor is the ratio of the jitter span to the stipulated burst window. The lesson lies in the gap between the expected count and the realized one, which can include every retry in the cohort, so peak rate containment still requires an admission rate limiter. Both mechanisms bound local host resources rather than remote liability.

**Checkpoint 12.4: Contain load without erasing uncertainty**

Breakers, caps, and jitter each bound a different quantity. Name the quantity before trusting the bound.

**Stale probe**: A probe times out, the breaker reopens, and its success arrives during a newer trial. What may that evidence update, and why must it not close the current breaker?

**Safe repeat**: The breaker is closed and the retry delay has elapsed, but the earlier test outcome remains unknown. Which additional contract and admission checks are required?

**Protected quantity**: Why can an execution cap preserve worker slots without bounding remote jobs or guaranteeing fast local reads?

**Worker-occupancy estimate**: Under the smooth-load approximation, how does uncapped worker demand change when the timeout doubles, and which explicit worker cap keeps the rest of the pool available regardless of the timeout?

**Arrival claim**: Why is an expected offered rate below nominal capacity insufficient to establish that no queue will overflow?

Breakers, retry ownership, and bulkheads protect a shared dependency from the agents that use it. When the suspect component is a trajectory itself, the question changes from how much load to admit to what may proceed at all.
