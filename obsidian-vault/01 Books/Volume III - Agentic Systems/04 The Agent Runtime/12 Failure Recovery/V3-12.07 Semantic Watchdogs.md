# V3-12.07 Semantic Watchdogs

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-sagas-watchdogs

In the running connection-pool repair, after the targeted check on revision `r18` fails, the agent can oscillate between two complementary edits that each undo the other and reproduce the exact same test failure. Every API invocation succeeds, every tool execution exits cleanly, and the execution trace lengthens, yet the underlying defect remains untouched.

Classical liveness monitoring[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn7|⁷]] cannot catch this failure because a traditional heartbeat detects only the absence of activity: daemons that stop emitting keepalives, threads deadlocked on mutexes, or network connections stalled on unacknowledged packets. In those traditional failure modes, an external supervisor intervenes by restarting the stalled process. A looping agent trajectory fails in the opposite way, staying hyperactive and reporting green health status on every probe while compute tokens and API budgets burn. Hard cumulative caps eventually halt the runaway process, but only after the trajectory has consumed nearly its entire budget. Catching unproductive cycles early requires monitoring task-level semantic evidence rather than low-level process liveness.

A **semantic watchdog** is a runtime policy that monitors task-level observations, flags indicators of stagnation or oscillation, and executes a bounded intervention. Because semantic signals represent heuristic, fallible evidence about task health rather than formal proofs of futility, the runtime decouples detection from execution control. The detector provides the diagnostic signal, but the runtime enforcement mechanism imposes the admission hold, suspending subsequent tool execution even when the model proposes continuing. That hold is the harness’s `pending_control` hold, a flag on the trajectory record that withholds admission of new work. The watchdog, control, and incident holds of this chapter all use that one flag and differ only in whether the trajectory then steps from `READY` into `PAUSED`. The split applies trajectory-level encapsulation (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-trajectory-encapsulation|10]]) to progress. The runtime, not the trajectory, decides whether work continues, because the trajectory cannot be relied on to notice that it has stopped advancing.

Static limits, such as the repair cap on a single repair episode or cumulative token and financial budgets, bound worst-case resource exposure across the entire trajectory. The harness already ends a runaway retry loop once its next call no longer fits the budget, and it steers, restricts, and then finalizes as headroom shrinks. Those stages respond to consumption, and consumption says nothing about progress. A semantic watchdog supplies the missing evidence, providing earlier, dynamic termination based on empirical progress. Even if an agent still possesses 80 percent of its turn allowance, continuing a detected non-progress pattern wastes both time and money. Watchdog heuristics operate strictly within existing budget envelopes; a permissive or malfunctioning detector can never grant an agent more attempts than its hard budget ceilings permit.

↩︎ The runaway retry loop and the steer, restrict, and finalize stages that respond to consumed budget are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-harness-staged-escalation|Staged budget escalation and enforcement]]**.

### Progress Evidence

^sec-vol3-failure-recovery-progress-evidence

A watchdog that watches only raw tool return codes or uncanonicalized file timestamps either misses an agent toggling between two broken patches in `ws_r18` or raises a false alarm while the agent runs read-only log inspections. To evaluate trajectory health accurately, a semantic monitor requires three components: a concrete projection of task state, an authoritative observation stream, and a sliding comparison window. In our automated defect-repair scenario, meaningful evidence includes the source tree modifications, the specific regression suites executed against each candidate revision, and the resulting compiler or test diagnostic streams. Systems designers must maintain strict provenance for this evidence: a passing unit test validates only its scoped assertions, not complete task correctness. The runtime attaches the source revision, test scope, and verifier configuration to every evaluation record, ensuring that the watchdog compares identical verification criteria across successive turns.

Three complementary signals capture the primary failure patterns observed in practice. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^tbl-vol3-watchdog-invariants|Table 5]] summarizes what each signal detects alongside its operational failure modes.

| Signal                               | What it can flag                                                                       | False alarm and missed case                                                                                        |
|:-------------------------------------|:---------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------|
| Repeated captured state              | Candidate contents return to a previously recorded projection within a bounded history | Useful inspection or planned backtracking can repeat contents; irrelevant file changes can hide a loop             |
| Stagnant verification results        | Declared task metrics fail to improve over a chosen interval                           | Exploration can temporarily worsen a metric; a better score can hide a regression outside the check’s coverage     |
| Repeated proposed action and outcome | Similar requests recur under apparently unchanged conditions after the same failure    | Waiting on a valid job or retrying after conditions change can be right; paraphrased requests evade exact matching |

Table 5: **Watchdog Signals and Their Limits**: Each signal provides empirical evidence for runtime intervention, rather than mathematical proof that a trajectory is permanently stalled.

^tbl-vol3-watchdog-invariants

To detect state recurrence, the runtime extracts the candidate workspace state, canonicalizes its contents, and computes a cryptographic or stable non-cryptographic digest. Let ${h_{\text{state},t}}$ denote the digest of the canonicalized projection captured at observation step ${t}$, and let the runtime retain a bounded history window of the previous ${m}$ digests. The watchdog flags a recurrence of period ${\ell}$ whenever the current digest matches an earlier entry in the active window:

$$
\exists\, {\ell} \in \{1, \dots, {m}\}:\ {h_{\text{state},t}} = {h_{\text{state},t-k}}. \tag{6}
$$

^eq-vol3-state-recurrence

A period of ${\ell}=1$ indicates an uninformative stutter turn, where an admitted action produced no net change in the tracked workspace files. A period of ${\ell}=2$ captures an oscillation where the agent toggles back and forth between two candidate patches. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^lst-vol3-state-recurrence-detector|Listing 1]] implements [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^eq-vol3-state-recurrence|equation 6]] by scanning backward from the most recent observation.

``` python
def recurrence_period(window: list[str], current: str) -> int | None:
    # window holds the most recent digests, oldest first, at most m entries
    for lag, past in enumerate(reversed(window), start=1):
        if past == current:
            return lag
    return None
```

Listing 1: **Bounded state-recurrence check**: The scan returns the smallest period at which the current digest repeats within the retained window, or no period. A returned period is evidence for a progress review, not proof of a loop.

^lst-vol3-state-recurrence-detector

Digest equality confirms that the captured projection has matched an earlier state, but it does not tell the runtime why. In practice, false alarms stem from productive investigative actions that leave workspace files unaltered, such as diagnostic read-only commands or log inspection, far more often than from hash collisions. Conversely, an agent can defeat an uncalibrated detector by writing a transient timestamp or updating an ephemeral scratch file on every turn, producing novel hashes while trapped in a conceptual loop.

Effective canonicalization therefore requires a precise specification: the runtime must explicitly declare which file paths, metadata attributes, and environment variables belong to the task projection, and filter out non-deterministic noise. Because file serialization, path sorting, and hashing scale linearly with total workspace size, state capture often dominates the runtime overhead of the watchdog. Maintaining a bounded history window of size ${m}$ caps memory consumption and comparison latency to $\mathcal{O}({m})$, though it inevitably blinds the detector to long-period cycles exceeding ${m}$ turns.

Verification metrics demand similarly rigorous interpretation. System designers typically orient evaluation metrics so that higher values denote better performance, for example by tracking the negative count of compilation errors alongside the number of passing unit tests. A naive watchdog policy might treat any upward movement in a single metric as sufficient evidence of progress. A more robust criterion requires a **Pareto improvement**, where at least one metric advances and no tracked metric regresses. Both rules have blind spots under real development workloads. A productive refactoring might temporarily break compilation while an agent restructures an interface, whereas a superficial patch might fix a trivial test while masking a severe regression in unmeasured components. Runtime policies therefore combine metric thresholds with declared grace periods, permitting temporary regressions within a bounded number of turns.

Action comparison operates prior to tool dispatch, whereas outcome comparison evaluates the empirical results of admitted operations. Re-submitting an identical command immediately after it returns a deterministic execution error provides strong evidence of stagnation. However, identical tool invocations are entirely legitimate when external preconditions change, such as polling a long-running batch job or re-reading an updated file. Conversely, minor variations in prompt formatting or parameter nonces can easily evade exact-string matching. While semantic embedding models can identify paraphrased tool arguments, they introduce inference latency and classification errors of their own. Reliable watchdogs anchor their logic directly on observed tool signatures and structured execution returns, which the runtime controls authoritatively, rather than on the model’s internal reasoning tokens. In the running repair, for example, observing that workspace `ws_r18` remains byte-identical while background task `test_r18` executes does not indicate a repair loop. The runtime tracks the pending asynchronous job and respects its execution deadline rather than demanding source modifications on every poll.

### The Cost of an Undetected Loop

^sec-vol3-failure-recovery-loop-cost-section

![[90 Assets/Volume III/12 Failure Recovery/Vol3 Failure Recovery Margin Loop Cost 18c2093cca.svg]]

*A convex curve of cumulative input tokens against turns, rising slowly then steeply. A green dot near the origin is labeled Early stop and a red dot at the top right is labeled Turn ceiling; the area under the curve past the green dot is shaded pale red.*

*Re-sent input grows with the square of turns; late stops pay for it.*

Every extra turn a detector waits before flagging an execution loop costs more than the turn before it, because stateless foundation model APIs re-submit the accumulated conversation history, tool inputs, and environment responses on each call. If an agent loops without context pruning or prefix cache reuse, input tokens accumulate quadratically with the number of turns, the append-only resend of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 2.9]]** applied from the loop’s first turn. Notebook [12.3](https://mlsysbook.ai/vol3/12_failure_recovery/12_failure_recovery.html#nbk-12-loop-cost) prices this compounding overhead by contrasting a trajectory governed solely by a generous turn ceiling with one terminated promptly by a semantic watchdog.

↩︎ Prefix cache reuse across turns is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kvcache-radix-tree|Prefix Caching Across Turns]]**.

**Napkin Math 12.3: What an undetected loop costs**

**Problem**: Assume a loop continues to a 50-turn ceiling unless the runtime intervenes after completed turn 4. How much model spending and elapsed loop time does the intervention avoid? The intervention turn is stipulated, not a guaranteed first-detection time.

**Variables**: The first input has 1,000 tokens. Each turn appends 300 output tokens and an 800-token error observation, increasing the next input by 1,100 tokens. There is no compaction or prefix caching. The largest input plus output is 55,200 tokens, within the assumed 64,000-token combined capacity. Each serial turn takes 10 s despite the growing input, and hypothetical prices are \$3 and \$15 per million input and output tokens.

**Math**: **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 2.9]]** gives the total prompt tokens sent, ${S_{\text{sent}}} = {H}\,{S_{\text{base}}} + {\Delta S_{\text{turn}}}\,{H}({H}-1)/2$, with base prompt length ${S_{\text{base}}}$ and per-turn append ${\Delta S_{\text{turn}}}$; here ${H}$ counts completed turns from the loop’s start rather than the whole trajectory’s horizon. The ceiling case processes 50 $\times$ 1,000 + 1,100 $\times$ 50 $\times$ 49/2 = 1,397,500 input tokens, costs \$4.42 in model charges, and lasts 8.33 min. The early stop processes 4 $\times$ 1,000 + 1,100 $\times$ 4 $\times$ 3/2 = 10,600 input tokens, costs \$0.050, and lasts 40 s.

**Result**: The ceiling case costs about 88.7× as much, so earlier stopping avoids \$4.37 of gross model charges.

**Systems insight**: Append-only re-sending makes a loop’s input grow with the square of the turns it runs, so detection latency is the primary engineering control; a static budget ceiling serves merely as an ultimate backstop. Stopping this loop at turn 25 instead of 50 already cuts its input 3.9×. In an end-to-end deployment, every dollar spent on an undetected looping attempt is absorbed into $\mathbb{E}[{C_{\text{attempt}}}]$ in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**. Because that expected attempt cost is divided by task acceptance probability, uncontained loops aggressively inflate the effective cost per completed task across the entire fleet. The saving is gross; detector inference overhead, false alarms on useful work, and compensating cleanup actions must be debited against these savings, while prompt caching and context compaction mitigate the steepness of the quadratic curve.

### Watchdog Responses

^sec-vol3-failure-recovery-watchdog-responses

If a watchdog responds to a detected loop only by appending a warning to the prompt, the model can ignore the message and submit the same failing tool call again; if the watchdog instead aborts the trajectory on the first repeated digest, a false alarm kills a repair that was legitimately backtracking. To enforce intervention without turning every heuristic trigger into a task failure, the runtime constructs a structured diagnostic finding (recording the triggering observations, candidate workspace revisions, plan version, active detection rule, and sliding window indices) and asserts the `pending_control` hold on the trajectory record, which immediately blocks the admission gate from dispatching any further model-proposed tool calls. Unlike an operator pause or a security quarantine, however, the watchdog leaves the trajectory in `READY` rather than transitioning it into `PAUSED`, because two of the three available responses resume autonomous execution immediately after adjusting the trajectory’s context or workspace. While the admission hold is active, the runtime policy selects an intervention from the three escalation options detailed in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^tbl-vol3-watchdog-escalation-protocol|table 6]]. Two of these options parallel the budget-escalation stages in the agent harness, although they are triggered by lack of progress evidence rather than by consumed budget: bounded diagnostic continuation injects corrective feedback just as the harness’s steer stage does, and ending model-directed repair moves the trajectory into guarded finalization just as the harness’s finalize stage does. The remaining option, controlled backtrack, has no counterpart in budget escalation because exhausting a budget cannot be fixed by restoring an earlier workspace checkpoint. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^fig-vol3-semantic-watchdog|Figure 3]] models this detection and containment sequence. The top panel identifies a period-2 oscillation between alternating revisions (${h_{\text{state},t}} = {h_{\text{state},t-2}}$) that produce identical test failures. The bottom panel records a structured finding that clamps the trajectory into an admission hold, routing execution to diagnostic continuation, controlled backtracking, or finalization.

↩︎ Control plane state machine rules and admission holds are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-controlplane-statemachine|Trajectory States]]**.

| Response                        | What the runtime does                                                                                        | Condition that limits it                                                                                  |
|:--------------------------------|:-------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------------------|
| Bounded diagnostic continuation | Stage a truthful watchdog observation and admit a limited investigation or revised proposal                  | The new work must pass the admission check                                                                |
| Controlled backtrack            | Restore a compatible private candidate boundary and revise the continuation while retaining failure evidence | Restored files do not undo external effects; unresolved operations and dependencies must be accounted for |
| End model-directed repair       | Stop ordinary admission, enter guarded finalization, and resolve or transfer remaining duties                | Compensation and trusted cleanup still pass the admission check and settle only on evidence               |

Table 6: **Watchdog Escalation Protocol**: Runtime guards enforce the selected response; a prompt warning alone does not constrain subsequent behavior or settle outstanding effects.

^tbl-vol3-watchdog-escalation-protocol

![[90 Assets/Volume III/12 Failure Recovery/Semantic Watchdog Oscillation 025f597da6.svg]]

Figure 3: **From Recurrence to Guarded Response**: Four observations of the repair alternate between two versions of the same change with the same test failure, so ${h_{\text{state},t}} = {h_{\text{state},t-2}}$ and [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^eq-vol3-state-recurrence|equation 6]] reports period ${\ell} = 2$. Equal digests establish equality of the captured projection only, and a deliberate backtrack can produce the same pattern. The finding records the supporting observations, rule, and window; the runtime then withholds new work and its policy selects one of the three responses of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^tbl-vol3-watchdog-escalation-protocol|table 6]], in no fixed order.

^fig-vol3-semantic-watchdog

In a bounded diagnostic continuation, the runtime injects an explicit, factual watchdog observation into the agent’s context rather than terminating the session. A representative observation states: “The proposed test invocation was withheld. The candidate patch and test failure match an earlier attempt in the active observation window, and no changed preconditions were recorded. Formulate an alternative hypothesis before re-submitting.” This message reports concrete runtime evidence without speculating on model capability, entering a freshly assembled prompt rather than interrupting an in-flight token stream. The diagnostic prompt is not a suggestion; the admission gate enforces the boundary, rejecting repeated dispatches if the model ignores the feedback.

If intervention arrives during active work, the runtime records the same hold and withdraws eligibility from in-flight output before the continuation reaches a paused boundary. In distributed environments, initiating cancellation is an asynchronous request rather than proof that remote execution has terminated. Outstanding side effects, background test runs, and cloud infrastructure charges remain tracked under the settlement rules until remote services confirm termination, and any further investigation must pass the admission check.

When policy dictates a controlled backtrack, the engine applies checkpointing mechanisms to restore the workspace to a known-clean state. The runtime preserves the diagnostic history of the abandoned branch so the agent does not repeat the exact sequence, revalidates evidence for the restored candidate, and enforces command restrictions at the admission gate rather than relying on prompt steering. If the trajectory exhausts its retry or diagnostic budget, the runtime halts model execution entirely and transfers control to the guarded finalization protocol.

**Checkpoint 12.3: Progress evidence and intervention**

A watchdog turns fallible progress evidence into an enforced hold. Test both halves.

**Useful repetition**: `ws_r18` is unchanged while its admitted test runs. Why might a repeated-state alarm be premature, and what limits the wait?

**Metric direction**: A candidate passes more checks but introduces a new compiler error. Why is improvement in one metric not enough to establish a Pareto improvement or task acceptance?

**Policy vs. proof**: What can an attempt ceiling guarantee that a state-hash detector cannot? What can a bounded history miss?

**Detection-latency estimate**: Using the loop notebook’s quadratic term, estimate how the loop’s input tokens change if intervention moves from the notebook’s turn to twice that turn, before computing it exactly. Which omitted costs and detector errors could reverse the gross saving per accepted task?

**Outstanding work**: A watchdog holds new proposals after a test timeout. Which effect and charge obligations remain, and why does the hold not establish that the test stopped?

A progress monitor operates strictly within the scope of an individual trajectory. In production clusters, however, repeated execution failures often reflect an impaired upstream dependency (an overloaded database, a rate-limited package repository, a failing authentication service) shared across thousands of concurrent agents. Because individual attempt budgets do not limit aggregate cluster load, independent agents retrying in parallel can trigger a retry storm. Mitigating shared degradation requires shifting operational control from individual agent watchdogs to system-level circuit breakers and shared dependency boundaries.
