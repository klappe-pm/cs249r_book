# V3-12.06 Irreversible Commitments

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-sagas-pivot

When an agent abandons an in-flight repair task, releasing the temporary integration-test environment `env_r18_01` deallocates its virtual infrastructure while leaving behind only the accumulated compute charges. Publishing a software package to an external registry or rolling a configuration change across a live production fleet crosses a different boundary, because no recovery action within the agent’s authority can pull back downloaded artifacts or undo dropped customer requests. The property of **reversibility** is therefore always relative to a specified subsystem and an explicit boundary of control: a local filesystem snapshot restores the directories it tracks and nothing beyond them, and a cloud teardown stops future billing without erasing past logs.

### Recovery Contracts

^sec-vol3-failure-recovery-recovery-contracts

A runtime cannot infer how to undo an action from an endpoint’s name or its coarse authority tier alone: a configuration change that can be reverted by restoring a snapshot in a local workspace requires an explicit compensating call in a staging environment and becomes unrecallable once pushed to live client traffic. Before initiating any state modification, the execution runtime must therefore determine three properties for each proposed effect: the precise target state, the recovery action available under the task’s granted authority, and the concrete evidence needed to verify that the recovery postcondition holds. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.06 Irreversible Commitments#^tbl-vol3-action-invertibility|Table 3]] distinguishes three operational recovery contracts. These contracts represent intrinsic semantic properties of the underlying operation rather than superficial endpoint names or the coarse authority levels ${A}_0$ to ${A}_3$.

| Recovery contract                                      | Required boundary                                                                                         | Residual effects                                                            |
|:-------------------------------------------------------|:----------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------|
| Restore selected state                                 | Available prior state and control over the affected objects and conflicting writers                       | Charges, external observations, and other effects outside that state remain |
| Compensate a known effect                              | Authorized corrective action with explicit application postconditions and compatible current dependencies | History and other declared residue remain; compensation can itself fail     |
| Manage a commitment that cannot be undone within scope | Explicit acceptance of the nonrestorable effect and a plan for verification, follow-up, and escalation    | The committed effect remains even if later work fails                       |

Table 3: **Action recovery contracts**: Defining what state can be restored and what residual effects remain observable. Compensation is a distinct forward operation requiring explicit verification of success, rather than an assumed automatic inverse guaranteed by a tool label.

^tbl-vol3-action-invertibility

Tearing down a temporary test environment sits squarely in the second row. Releasing environment instance `env_r18_01` deallocates its underlying compute resources, but earlier execution history and billing charges remain permanently on record. When a workflow instead includes an action in the third row, one that no operation within the agent’s authority can undo, the runtime can no longer rely on post-hoc compensation and must organize the plan around the point of no return.

### The Commitment Region

^sec-vol3-failure-recovery-commitment-region

Suppose an authorized publishing agent deploys an artifact to an external package registry first and checks its cryptographic signature and dependency versions second. When the signature check fails, the defective package is already publicly visible across external mirrors, and no action within the agent’s authority can withdraw copies that downstream users have already downloaded. An irreversible action in the third row of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.06 Irreversible Commitments#^tbl-vol3-action-invertibility|table 3]] therefore requires explicit architectural structure, because the recovery planner must organize surrounding preparation and verification around it.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn6|⁶]]

**Definition 12.3: Pivot action**

A ***pivot action*** is the designated irreversible commitment within a bounded region of a plan, after which restoring the region’s precommitment state is no longer an available recovery strategy.

1.  **Significance**: The pivot splits a plan region into two distinct phases: a compensable preparation phase before it and an irreversible phase after it. Hoisting validation checks ahead of the pivot is the primary systems mechanism for preventing defective actions from becoming permanent damage.
2.  **Distinction**: Being a pivot is an architectural property of an action within a plan region under a specific authority grant, rather than an intrinsic attribute of an API endpoint name. The same API call may be compensable under an administrative role with rollback privileges, yet act as a pivot under a restricted operational grant.
3.  **Common pitfall**: Delaying checks until after the pivot when they could have run before it. Executing validation late converts failures that compensation could have cleanly resolved into committed production outages.

A **commitment region** encompasses the span of an execution plan structured around a single pivot: preparatory work that compensation can still unwind, the pivot action itself, and the follow-up obligations that remain afterward. Commitment regions carry intent before effect (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-intent-before-effect|11]]) across a step that compensation cannot reach. Everything the runtime must check and record is settled before the irreversible action.

Within each commitment region, the agent must perform every validation check that can legitimately precede commitment before releasing the irreversible action. The runtime must preserve all necessary artifacts, validate their versions and dependencies, and record the authorized intent, resource reservations, recovery metadata, and follow-up obligations to durable storage under the failure-domain contract of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-durable-execution-ack-failure-domain|Acknowledgment and the failure domain]]**. Only after crossing this durable boundary does the pivot action face its final admission check at dispatch time.

Limiting each region to a single pivot is an architectural discipline rather than a restriction that an entire task trajectory contain only one irreversible action. When a complex workload requires several independent state changes, the plan decomposes into a sequence of distinct commitment regions.

In that publishing workflow, suppose the agent must both release the approved artifact to the external registry and notify downstream recipients. A naive plan publishes the artifact first, validates signatures and dependency versions second, drafts release notes third, and sends notifications fourth, exposing the public registry to any defect that step 2 catches. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.06 Irreversible Commitments#^tbl-vol3-commitment-reordering|Table 4]] reorders the workflow so that every local check and compensable preparation step runs ahead of publication, isolating publication as the single commitment of its region and placing recipient notification in a second region that waits for publication evidence.

| Step | First plan                          | Reordered plan                                                   | Recovery if a later step fails                                         |
|:-----|:------------------------------------|:-----------------------------------------------------------------|:-----------------------------------------------------------------------|
| 1    | Publish the artifact (commitment)   | Validate signature and dependency versions locally               | Nothing external to undo                                               |
| 2    | Validate signature and dependencies | Stage release notes and the notification payload privately       | Discard staged drafts                                                  |
| 3    | Prepare release notes               | Confirm authority and approval; record intent and follow-up duty | Nothing external to undo                                               |
| 4    | Notify the recipient (commitment)   | Publish the artifact (commitment of this region)                 | Publication stands; notification remains an owned follow-up obligation |
| 5    |                                     | Deliver the staged notification after publication evidence       | A second commitment region with its own unknown-outcome handling       |

Table 4: **Reordering around a commitment**: Checks and compensable preparation move ahead of publication, so a failure before step 4 leaves nothing public. Notification depends on publication evidence and therefore cannot move ahead of it; it forms a second region.

^tbl-vol3-commitment-reordering

True data and control dependencies bound how aggressively the runtime can hoist operations. For example, a validation check that depends on the published artifact, such as confirming that a public package mirror resolves its new identifier, cannot run before release. That verification must remain after the commitment, tracked as an explicit operational risk assigned to a designated owner.

Executing a commitment does not terminate cleanup. When an agent allocates independent temporary resources that are no longer needed by subsequent duties, the runtime must still release them. The orchestrator keeps the list of pending compensations across the commitment boundary, withholding only those recovery actions whose preconditions no longer hold or whose execution would directly contradict the committed state.

The software repair agent encounters few pivots within its typical grant, because even submitting a pull request for review can be withdrawn or closed. In contrast, the on-call remediation agent encounters a pivot in nearly every incident it handles, because it operates at authority level ${A}_3$ against shared production infrastructure.

**Lighthouse 12.1: Remediation agent (pivot and compensation)**

**Workload**: The remediation agent responds to production alerts when a service’s error rate spikes following a configuration change. Its task contract permits querying telemetry systems, staging a candidate configuration on a canary slice (the small fraction of servers that receives traffic first), and rolling that configuration out fleet-wide after obtaining approval. Its operational horizon is tight, and any state modification directly affects live traffic across shared production infrastructure.

**Recovery contracts**: Querying telemetry metrics and reading logs produces no state changes to compensate. Staging a correction on the canary slice is fully compensable; reverting the canary restores the declared routing and configuration predicates, even though client requests already processed by the canary cannot be recalled. Scaling server replicas is compensable, leaving behind only the accumulated cloud charges. Rolling the configuration across the fleet alongside a rolling service restart constitutes the commitment region’s pivot action, because severed TCP connections, invalidated cache entries, and requests dropped during the restart lie beyond any recovery action permitted by the agent’s grant.

**Binding constraint**: While the software repair agent’s recovery budget is dominated by token re-reads during prompt reconstruction, the remediation agent’s recovery cost is dominated by expected irreversible loss. Every diagnostic check and synthetic test that can evaluate the canary belongs before the fleet rollout. Furthermore, the human-in-the-loop approval gate described in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^sec-vol3-controlplane-hitl|Approval Gates]]** must sit directly at this pivot boundary, maximizing the operational loss prevented per minute of engineer review.

The lighthouse’s ordering rule can be priced. The **expected irreversible loss** of an execution plan, ${L_A}$ (the subscript is part of the symbol’s name, not an authority level), sums a product over every proposed action ${a}$. The product combines the probability that the action is defective, its blast-radius consequence if committed, and the unrecoverable fraction $1-{\rho_{a}}$ that compensation cannot restore:

$$
{L_A} = \sum_{a} \Pr(\text{bad}\ {a})\cdot \text{consequence}({a})\cdot(1-{\rho_{a}}). \tag{5}
$$

Hoisting a diagnostic check ahead of the pivot transforms an unrecoverable failure mode (${\rho_{a}} = 0$) into a partially compensable canary rollback (${\rho_{a}} > 0$). Conversely, scheduling that same validation check after the pivot leaves ${\rho_{a}} = 0$, forfeiting any loss reduction. A real pre-pivot check recovers through two separate factors. It catches only a fraction ${v}$ of defective actions, and reverting a caught action avoids only a fraction ${\rho_{\text{revert}}}$ of its consequence, while a missed action recovers nothing. The action’s recoverable fraction in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.06 Irreversible Commitments#^eq-vol3-expected-irreversible-loss|equation 5]] is therefore the product ${\rho_{a}} = {v}\,{\rho_{\text{revert}}}$, and keeping the factors apart shows which one an engineering investment moves.

**Napkin Math 12.2: Expected irreversible loss around a pivot**

**Problem**: How much expected irreversible loss (${L_A}$) per task does hoisting canary verification ahead of the fleet rollout eliminate for the remediation agent, and how does a specified increase in the pre-pivot catch rate change the remaining loss?

**Variables**: A proposed fleet change is wrong with probability ${p_{\text{bad}}}$ = 4 percent. A wrong change that commits at the pivot inflicts $\text{consequence}({a})$ = \$12,000. Canary checks catch ${v}$ = 80 percent of wrong changes before the pivot, and reverting the canary avoids ${\rho_{\text{revert}}}$ = 90 percent of a caught change’s impact. The attempt itself costs \$20 across model inference calls, telemetry queries, post-change health checks, and on-call engineer review, with reviewer time accounting for the dominant share. All values represent scenario assumptions.

**Math**: Executing the fleet rollout first provides no recovery mechanism; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.06 Irreversible Commitments#^eq-vol3-expected-irreversible-loss|equation 5]] yields ${p_{\text{bad}}}\,\text{consequence}({a})$ = \$480. Staging on the canary first alters the risk: caught changes cost ${p_{\text{bad}}} {v}\,\text{consequence}({a})\,(1-{\rho_{\text{revert}}})$ = \$38.40, while missed changes cost ${p_{\text{bad}}}(1-{v})\,\text{consequence}({a})$ = \$96, totaling \$134.40. These two terms collapse algebraically to ${L_A} = {p_{\text{bad}}}\,\text{consequence}({a})\,(1 - {v}{\rho_{\text{revert}}})$, which is [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.06 Irreversible Commitments#^eq-vol3-expected-irreversible-loss|equation 5]] with ${\rho_{a}} = {v}{\rho_{\text{revert}}}$.

**Result**: Reordering operations cuts expected irreversible loss by 3.6×. Of the residual loss that remains, 71.4 percent stems from wrong changes that crossed the pivot undetected.

**Systems insight**: Because ${L_A} = {p_{\text{bad}}}\,\text{consequence}({a})\,(1-{v}{\rho_{\text{revert}}})$, each 10 percentage points of pre-pivot catch rate eliminate \$43.20 of expected loss per task, roughly 2× the attempt’s baseline execution cost. Even after reordering, the remaining loss is still 7× that attempt cost. For high-authority ${A}_3$ workloads, ${L_A}$ belongs directly in the expected cost calculation of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**. Charged to every attempt, accepted or not, the loss joins the numerator, ${C_{\text{eff}}} = (\mathbb{E}[{C_{\text{attempt}}}] + {L_A})/{p_{\text{acc}}}$, where it dominates model token expenses. The demonstrated catch-rate sensitivity makes better canary coverage a candidate engineering investment. Choosing it ahead of better revert fidelity, fewer defective proposals, or a smaller consequence requires comparing their feasible expected-loss reductions against implementation cost and added delay. Improving revert fidelity benefits only caught changes; cheaper model calls change attempt cost rather than this scenario’s irreversible-loss term.

### Local Staging and External Settlement

^sec-vol3-failure-recovery-staging-settlement

When a commitment region finishes its pivot action and must trigger a follow-up obligation on a second external service, crashing between the two calls can leave the first commitment complete while its required follow-up vanishes from memory. The runtime bridges that gap, without pretending the two external services share a transaction, by staging the follow-up obligation in the same local commit that records the pivot’s outcome.

**Example 12.1: What an outbox does not commit**

**Scenario**: Consider again the reordered publication workflow. Publishing the package and notifying external recipients represent two distinct commitments, where notification strictly depends on the verified outcome of publication.

**Diagnosis**: Once evidence of publication arrives, the runtime can atomically record that outcome while enqueuing the downstream notification into an **outbox**, a durable local log of outbound requests awaiting delivery. Because both state updates participate in a single local database transaction and write-ahead log, a system crash cannot persist the publication outcome while losing the notification obligation. Conversely, a crash immediately prior to that local transaction loses no state, because the durable publication intent and follow-up requirements survive, allowing recovery reconciliation to replay the update. This local database transaction cannot, however, span physical network boundaries, so it cannot atomically publish to the external registry and deliver a message to an external notification service.

If package publication succeeds but notification delivery fails, the orchestrator reports the partial outcome and retains the notification obligation for subsequent delivery. If the network drops the acknowledgment for the publication request itself, the settlement protocol applies directly to the publication operation. Under these conditions, the workflow engine can claim neither confirmed publication nor safe abandonment.

**Systems lesson**: The transactional outbox pattern renders pending external actions recoverable by persisting them as durable local obligations, while preserving the independent failure domain of each remote service.

^exmp-11-the-dual-commit-trap-and-pivot

An outbox entry that is recorded but not yet confirmed sent establishes only that an intent was committed to local durable storage, not that it was never transmitted across the network. A system crash or network timeout can occur immediately after an outbound request is sent but before the local database records the dispatch update. Consequently, the external settlement rule applies to a dispatched commitment just as it does to any other network operation. At a pivot boundary, while an operation’s outcome remains indeterminate, the runtime must suspend any subsequent action that relies on either verified commitment or verified noncommitment. Independent observation queries and safe local cleanup may proceed under their own admission checks, but the state machine must treat an unknown outcome as a distinct third branch, neither safely before the pivot nor definitively after it.

### The Finalization Contract

^sec-vol3-failure-recovery-finalization-contract

While idempotent interfaces ensure that retrying an operation is safe, extended downstream outages or network partitions can outlast an agent’s permitted execution window. To prevent open-ended execution loops, the runtime establishes a **finalization contract** before executing any irreversible commitment. The contract extends the harness’s finalization reserve, which funds finalization on every exit path. Written for one commitment region before its pivot, the contract names what that funding must buy there: the allowable remediation procedures, bound resource allocations, hard execution deadlines, and the designated escalation targets for any unresolved obligations.

When normal task execution ends, whether by completing its primary plan, hitting a deadline, or exhausting its operational authority, the harness’s guards move the trajectory into the `FINALIZING` state. The finalization phase operates under a dedicated, separately metered resource budget. While model-driven repair steps must still pass standard admission checks, pre-registered deterministic cleanup handlers execute under their own restricted, highly targeted cleanup grants.

↩︎ The `FINALIZING` state, through which every exit path passes under a dedicated reserve, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-agent-harness-finalization-duties|Finalization and remaining duties]]**.

When automated finalization fails to establish the required postconditions, the runtime writes a complete handoff record to durable storage. This record captures all verified state changes, indeterminate external operations, active resource leases, unreleased reservations, and the next responsible owner. The runtime then initiates a formal, acknowledged handoff. When an on-call engineer acknowledges the escalation page, that response transfers operational custody of the incident, leaving the underlying external operations to be reconciled manually.

Commitment regions and finalization contracts bound what a trajectory can damage. They do not bound what it can waste. A repair loop whose every call is admissible can consume its budget without moving the task toward completion, and no error ever announces it.
