# V3-12.16 Footnotes

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^footnotes

<sup>1</sup> **Lost acknowledgment**: Gray named this the generals paradox in his 1978 notes on database operating systems: over a channel that can lose messages, no finite exchange lets both parties know that the last message arrived ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-gray1978notes|Gray 1978]]). Fischer, Lynch, and Paterson later proved that in a fully asynchronous system no deterministic consensus protocol can guarantee termination while preserving agreement and validity if even one process may crash, since a crashed process cannot be told apart from a slow one ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-fischer1985impossibility|Fischer et al. 1985]]). A tool-call timeout inherits the same ambiguity, which is why the settlement rule keeps the outcome unknown rather than guessing.

^fn1

<sup>2</sup> **Compensating transaction**: Gray’s 1981 travel-agent example had this exact structure ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-gray1981transaction|Gray 1981]]). Because each flight or hotel reservation commits at an independent organization, canceling the itinerary requires executing a compensating transaction. Gray proposed that each nested step return the name and parameters of its compensator for the parent coordinator to log, falling back to human intervention as a last resort. However, Gray’s coordinator logs the compensator only after the forward step successfully returns. A trajectory saga must instead record the recovery obligation before dispatching the request over the network, because a dropped connection or lost acknowledgment would otherwise leave unmanaged side effects with no corresponding recovery record.

^fn2

<sup>3</sup> **Recovery vocabulary**: The same terminology carries conflicting meanings across the two architectural lineages this chapter draws on. Garcia-Molina and Salem defined running compensations as backward recovery for sagas, reserving forward recovery for executing missing steps from a save-point ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-garciamolina1987sagas|Garcia-Molina and Salem 1987]]). In the classical dependability taxonomy, however, compensation denotes masking an error through redundancy ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-avizienis2004basic|Avizienis et al. 2004]]); this chapter follows the saga usage, so compensation counts as backward recovery even though each compensating step is itself a forward operation.

^fn3

<sup>4</sup> **Measured self-repair**: When code-generation repair was evaluated against unconditioned resampling under matched sampling budgets, performance gains were often modest, varied substantially across problem subsets, and occasionally disappeared; high-quality feedback from a stronger verifier or a human supervisor yielded the only substantial improvements ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-olausson2024selfrepair|Olausson et al. 2024]]). In the absence of external ground-truth feedback, unguided self-correction on complex reasoning tasks can actually degrade accuracy ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-huang2024cannot|Huang et al. 2024]]). Because the diagnostic signal rather than the retry attempt provides the corrective value, engineers must estimate ${p}$ separately for each failure class and feedback mechanism.

^fn4

<sup>5</sup> **Recovery blocks**: Randell’s classic recovery block architecture structured fault tolerance around a primary routine, an acceptance test, and a fixed sequence of alternates, each executed from a restored checkpoint until one passed or the sequence was exhausted ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-randell1975system|Randell 1975]]). An agentic repair episode preserves the acceptance test and finite iteration, but its alternates are dynamically sampled from a language model rather than written in advance. Consequently, exhausting an episode signals an exhausted recovery budget rather than proof that no feasible solution exists.

^fn5

<sup>6</sup> **Pivot subtransaction**: The term comes from multidatabase transaction models, which classified each subtransaction as compensatable, retriable, or pivot (neither), allowed at most one pivot per global transaction, and required commits in the order compensatable, pivot, retriable ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-mehrotra1992transaction|Mehrotra et al. 1992]]). The commitment region keeps that order: compensable preparation first, one pivot, then follow-up duties that can only be retried or handed off.

^fn6

<sup>7</sup> **Liveness property**: In Alpern and Schneider’s formalization, a liveness property says that something good eventually happens, and every finite execution can still be extended to satisfy it ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-alpern1985defining|Alpern and Schneider 1985]]). No finite window of observations can therefore prove that a trajectory will never make progress. The runtime converts the question into a safety property, such as “no more than ${N}$ admitted attempts,” which a finite history can violate and a gate can enforce.

^fn7

<sup>8</sup> **Metastable failure**: Retry amplification can outlive its trigger. Bronson and colleagues describe systems in which a brief overload causes failures whose retries keep offered load above capacity after the original cause has gone, so the system stays degraded until load is shed or the retry policy changes ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-bronson2021metastable|Bronson et al. 2021]]). A shared tool dependency serving many trajectories is exposed to the same feedback loop.

^fn8

<sup>9</sup> **Binary exponential backoff**: The idea predates service retries. In the 1976 Ethernet design, a station whose transmission collided waited a random interval whose mean doubled after each successive collision ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-metcalfe1976ethernet|Metcalfe and Boggs 1976]]). Randomization desynchronized contending senders and doubling adapted to unknown load, the same two jobs jitter and the exponential cap do for retries against a shared tool.

^fn9

<sup>10</sup> **Fail-safe defaults**: Saltzer and Schroeder argued for basing access decisions on permission rather than exclusion because the two designs fail differently: a mistake in a permission-based mechanism refuses a legitimate request, which someone notices and reports, while a mistake in an exclusion-based one grants access silently ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-saltzer1975|Saltzer and Schroeder 1975]]). An incident hold inherits that asymmetry; a wrongly held trajectory costs time and surfaces in review, whereas a wrongly admitted action may be irreversible.

^fn10
