# V3-12.12 Summary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-sagas-summary

Recovering from failure in an agentic system requires making decisions under incomplete knowledge. An execution runtime cannot roll back the external world, nor can it always confirm whether an in-flight tool call actually took effect. Consequently, every recovery decision converges on two concrete questions evaluated at the admission boundary before the next operation runs: *What has the observed evidence conclusively established*, and *what do current authority, dependencies, and resource allowances permit?* Retries, forward repairs, backward compensations, pivot commitments, and external interventions are not disconnected subsystems. They are different answers to these two questions, which is why one operation table and one admission gate can govern them all.

Every quantitative comparison in the chapter set action on imperfect evidence against the cost of waiting for certainty. The pairs are an in-place repair attempt against a full rebuild and an early validation check before a pivot against irreversible loss committed after it. They also include a watchdog’s false interventions against runaway token burn and a rapid retry against the load it imposes on a struggling dependency. No analytical comparison relieves the runtime of maintaining explicit ownership over whatever state remains unsettled. **Key Takeaways: Recover from evidence and preserve residual duties**

- **A timeout settles nothing**: An execution outcome is verified complete, confirmed absent, or explicitly classified as unknown under the endpoint’s contract. Neither an expired timeout, a logged intent, nor a restored local workspace can determine whether an external side effect actually took place. Consequently, an unknown outcome must keep its resource reservations locked and retain a designated owner until external reality is verified.
- **Cleanup is owed before the effect exists**: The runtime must persist the compensation template (forward operation identity, blast-radius scope, dependencies, and identifier-binding rules) to durable storage before dispatching the forward action. Compensations are full operations with their own failure modes and outcomes, governed by an explicit cleanup dependency graph rather than an oversimplified reverse stack.
- **Repair pays only above its threshold**: At any given endpoint, attempting a bounded in-place repair outperforms unwinding and rebuilding from scratch only when the measured success probability exceeds ${C_{\text{repair}}}/{C_{\text{fallback}}}$, evaluated independently across latency and financial cost budgets. Expected statistical benefit must never bypass the admission gate, and every proposed repair action requires its own fresh evidence.
- **Irreversible loss is set before the pivot**: Because compensation cannot undo the commitment in this scenario, moving the same validation check before the pivot allows it to avert loss that detecting the defect afterward cannot undo. In the remediation scenario, deploying a canary check prior to the pivot cut expected loss 3.6×. Both forward cleanup and residual obligations survive past the pivot.
- **Detection latency sets a loop’s cost**: In an append-only agent conversation, prompt tokens grow quadratically with the turn count; allowing a cycling agent to reach turn 50 cost 88.7× as much as halting it at turn 4. Because intermediate progress signals are fallible evidence, the admission gate, not an advisory message to the model, must enforce the hold.
- **Retries need exactly one owner**: Uncoordinated retry loops across layered subsystems multiply traffic exponentially just when a downstream dependency is failing. Containing a fault requires a single designated retry owner, generation-scoped circuit breakers, bounded probe requests, and per-dependency concurrency bulkheads. Randomized jitter lowers the expected arrival rate and concurrency caps bound worker occupancy, but only an admission rate limiter bounds the peak request rate.
- **Stopping a trajectory is not recovering it**: Halting an execution trajectory does not eliminate active side effects, dangling external leases, or unsettled transactions. True containment maintains isolated, narrowly authorized cleanup routines, while robust fault injection tests evaluate residual duties and unverified outcomes rather than mistaking an idle process for a recovered system.

^callout-takeaways--12-2-366cf807

Intent before effect (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-intent-before-effect|11]]) reaches past the intent record in this chapter to the cleanup that record implies. The runtime registers corrective obligations before dispatch, verifies its commitments before the pivot, and tracks every unsettled duty until evidence resolves it. Complementing this, trajectory-level encapsulation (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-trajectory-encapsulation|10]]) empowers the runtime to intervene and halt execution when progress metrics degrade. Systems engineers must design for the reality that tool actions cannot always be undone and tasks cannot always be saved. When failures strike, a well-architected agent runtime preserves safety, limits collateral damage, and maintains an auditable chain of custody over the state it leaves behind.
