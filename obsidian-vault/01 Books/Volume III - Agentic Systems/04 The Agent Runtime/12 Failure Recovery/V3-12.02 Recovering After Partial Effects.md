# V3-12.02 Recovering After Partial Effects

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-failure-recovery-introduction

![[90 Assets/Volume III/12 Failure Recovery/Hsa Locator Ha c792579384.svg]]

*H·S·A locator triad with the Horizon and Authority axes highlighted.*

*Over a long horizon, authority becomes a recovery problem for the runtime.*

When a replacement worker takes over the repair agent’s failed connection-pool repair (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**), it reconstructs the execution log and restores the candidate workspace snapshot `ws_r18`. The surviving history records an intent to run `test_r18`, but contains no evidence confirming whether the test passed, failed, or ever ran. As **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-persistence-migration|Resuming a Trajectory]]** demonstrated, the worker cannot treat missing evidence as a clean slate; it must retain that uncertainty alongside the unresolved liability. State reconstruction recovers the factual foundation of the execution, but facts alone do not dictate the next step. The runtime’s recovery policy must decide whether to wait for delayed evidence, attempt a targeted repair of the candidate snapshot, or abort the task entirely.

Now expand the scope of the repair to include an external side effect. Besides the unresolved `test_r18`, which remains a separate operation whose outcome is still owed, the repair provisions an isolated, temporary integration-test environment and runs a new integration suite against `ws_r18` inside it. The agent’s authorization grant covers this ephemeral environment and nothing else. Production deployments, public network routing, payment processing, and the deletion of unrelated cloud resources remain strictly beyond its authority.

If a network timeout or process crash drops the provisioning reply, the worker faces an immediate impasse: it cannot know whether the remote environment was successfully allocated or never created.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn1|¹]] Suppose instead that telemetry confirms creation, but the integration suite subsequently crashes. Rolling back the local workspace to snapshot `ws_r18` resets internal state, yet the external environment remains active and billing charges continue to accumulate. Local rollback does not undo distributed side effects. Reclaiming those external resources requires an explicit compensating cleanup operation, followed by concrete evidence that the operation satisfied its declared postconditions.

Durable logs, checkpoints, and deterministic replay reconstruct what the runtime intended and what it observed. That historical reconstruction provides the evidence for recovery, but passive logs cannot alter the outside world. An execution log does not tear down an orphaned test cluster, resolve a lost network acknowledgment, or evaluate whether a subsequent attempt justifies its operational cost.

↩︎ Durable logs, checkpoints, and deterministic replay are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution#^sec-vol3-durable-execution|Durable Execution]]**.

Complicating matters further, agent failures frequently manifest without throwing runtime exceptions. An agent trajectory can issue structurally valid tool calls while drifting into destructive patterns: alternating indefinitely between two conflicting edits, bombarding a degraded testing service with aggressive retries, or attempting to transmit private credentials after parsing an untrusted document. Every network call returns a successful status, every worker health check reports green, yet the agent either makes zero forward progress or actively threatens system integrity.

The recovery architecture records every compensating cleanup obligation before dispatching the operation that produces an external side effect. When an operation is interrupted, the runtime evaluates the surviving evidence alongside projected forward costs and ignores sunk expenses. It then chooses whether to retry the operation, repair the proposal within a bound, run compensating actions that unwind external side effects, or hand control to an authorized human operator. Furthermore, the architecture bounds ongoing executions even when no component raises an explicit error. By intercepting actions at the admission gate where new tool calls are scheduled, the runtime halts unproductive loops, throttles retries against saturated dependencies, and quarantines suspicious behaviors. It does not rely on prompt warnings that an agent model might overlook or ignore.

[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.03 Effects Outside a Shared Transaction#^sec-vol3-sagas-acid-boundary|Section 12.2]] demonstrates why the environment service and runtime log in this workflow share no atomic commit boundary, carrying forward from the harness the two rules that govern every subsequent recovery decision. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^sec-vol3-sagas-architecture|Section 12.3]] translates these invariants into an executable saga pattern, tracking compensation obligations as explicit, dependency-ordered records. Where an execution encounters partial failure, [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.05 Forward Recovery#^sec-vol3-sagas-forward-vs-backward|section 12.4]] formalizes how to evaluate the marginal cost of forward repair against backward unwinding, while [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.06 Irreversible Commitments#^sec-vol3-sagas-pivot|section 12.5]] governs the critical transition across irreversible commitment points.

To address failures that emerge without explicit error signals, the runtime introduces three containment boundaries. Progress watchdogs identify trajectory stagnation and oscillatory loops ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^sec-vol3-sagas-watchdogs|section 12.6]]). Dependency controls insulate shared backend services from retry cascades ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.08 Tool Circuit Breakers#^sec-vol3-sagas-containment|section 12.7]]). Automated quarantine policies isolate suspected security incidents ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.09 Incident Containment#^sec-vol3-sagas-quarantine|section 12.8]]). Finally, [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.10 Fault-Tolerant System Synthesis#^sec-vol3-sagas-case-study|section 12.9]] unites these control loops in a recovery worksheet for a degraded connection-pool repair, detailing the fault-injection test harness required to verify recovery correctness under real-world failures.
