# V3-12.05 Forward Recovery

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery|V3-12 Failure Recovery]]

^sec-vol3-sagas-forward-vs-backward

Take the branch in which provisioning evidence did arrive. The separately authorized operation `provision_test_env_r18` has settled, binding the temporary integration-test environment `env_r18_01`. Before dispatching the integration test, the runtime validates the proposed test configuration and rejects it because a field requiring an integer contains a string. The candidate workspace remains `ws_r18`, and no integration test has started. Releasing the environment through `release_test_env_r18` would discard expensive, fully functional preparation. Conversely, a bounded correction of the configuration can restore readiness without rebuilding the environment from scratch.

This situation differs from the unresolved `test_r18` intent that the replacement worker recovered. When the runtime rejects a proposal before dispatch, it establishes definitive evidence that the executor never launched the action. A missing result under the settlement rule provides no such assurance; the operation might have succeeded, failed, or stalled midway through execution.

In dependable system design, **forward recovery** modifies the current state or repairs a proposed action to restore an admissible path toward completing the task. By contrast, **backward recovery** returns the system to an earlier saved state. The classical dependability taxonomy formalizes these strategies as rollforward and rollback, where rollback restores a previously captured checkpoint ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-avizienis2004basic|Avizienis et al. 2004]]).[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn3|³]] Forward repair, the response family named earlier, is the agent runtime’s form of forward recovery, which keeps valid intermediate artifacts and corrects the proposal that failed. In an agentic system, restoring a workspace checkpoint performs backward recovery for the local filesystem and memory state that the checkpoint covers. External systems, however, rarely support true rollback, and compensation sits across the divide. In intent it is backward recovery, because it moves the environment back toward the pre-effect predicates of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^eq-vol3-semantic-equivalence|equation 2]]. In execution it is forward, a new operation with its own outcome, which is why the trajectory saga definition calls it new forward execution. It achieves semantic equivalence rather than physical restoration.

### Recovery Actions and Evidence

^sec-vol3-failure-recovery-recovery-actions

Treating every failure as a blanket instruction to “try again” either re-sends a non-idempotent provisioning call after an ambiguous timeout or tears down a healthy test environment `env_r18_01` when only a local configuration field had the wrong type. Separating “try again” by the evidence each failure leaves behind yields five distinct choices, because forward repair splits into two forms while retry, compensation, and escalation each remain one. A transport retry repeats the same logical operation under an established repeat contract. Forward repair takes two forms: resampling requests an entirely fresh candidate proposal from the model, while feedback-based repair ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-madaan2023selfrefine|Madaan et al. 2023]]; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.15 Source References#^ref-shinn2023reflexion|Shinn et al. 2023]]) supplies targeted diagnostics to prompt a revised proposal. Compensation executes registered actions to establish fallback postconditions, and escalation transfers decision authority or unresolved obligations to an authorized supervisor. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.05 Forward Recovery#^tbl-vol3-recovery-comparison|Table 2]] separates these choices by the evidence they require and the obligations that remain on the runtime.

| Choice                      | Appropriate basis                                                                                      | Obligation that remains                                                      |
|:----------------------------|:-------------------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------|
| Retry an existing operation | Its repeat contract and current evidence permit another transport attempt                              | Preserve logical identity, possible prior effects, and charges               |
| Generate a new proposal     | The task still permits another candidate and the runtime can distinguish it from already admitted work | Validate the complete proposal; a new sample is not a recovered result       |
| Repair using feedback       | A scoped diagnostic suggests a permitted change to the action or its prerequisites                     | Pass the admission check again; verify the repaired outcome                  |
| Compensate                  | Registered recovery actions remain applicable to established effects                                   | Respect dependency order and verify postconditions or retain residual duties |
| Hold or escalate            | No admissible automatic path remains                                                                   | Name the decision or settlement owner; do not discard pending work           |

Table 2: **Recovery choices and their evidence**: The error label alone does not select a safe response. Recovery changes are new admissions unless they merely reconstruct recorded state.

^tbl-vol3-recovery-comparison

A network timeout raises an effect-status question before any model-repair question can be addressed, and the runtime relies on the settlement rule to resolve whether external state was altered. Similarly, an HTTP 429 rate-limit response proves only what the external service contract guarantees; it does not prove that an attempted state mutation was rejected before execution. Exponential backoff regulates the timing and throughput of a permitted retry, but no backoff schedule can transform an unsafe, non-idempotent repeat into a safe operation.

In contrast to an ambiguous timeout, a pre-dispatch configuration rejection provides a well-defined basis for repair. Because the schema validator rejected the payload locally, the runtime establishes that the proposed action never reached the executor or modified remote state. The runtime can therefore supply the original request, the target schema, the field-level diagnostic, and the task scope within a bounded repair prompt, validating the revised proposal before admitting any side effect. If the repair instead modifies source code rather than an ephemeral test configuration, the modified artifact constitutes a new candidate revision requiring fresh test evidence; previous test passes for `ws_r18` cannot certify altered code.

↩︎ Structured, bounded rejection diagnostics are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-rejection-diagnostics|Rejection diagnostics]]**.

Providing feedback modifies the model’s prompt conditioning without expanding its execution authority. While drawing independent resamples from a fixed prompt yields the same success probability on every attempt, repeated failures in operational agents are rarely independent. Instead, repeated failures typically expose an intrinsically difficult task, a persistent prompt misconception, or an unexpected environment state. The empirical repair success rate ${p}$ is therefore a measured property of a specific failure class and feedback policy, which systems engineers must estimate from recorded operational episodes.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn4|⁴]]

↩︎ The feedback axis established in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^sec-vol3-test-time-compute-feedback-axis|Revising from observations along the feedback axis]]** separates feedback that adds an external observation from asking the model to re-examine its own output.

Accumulating failed responses and diagnostic traces across successive attempts also inflates the prompt for subsequent calls. Runtimes must manage two distinct resource boundaries: the per-invocation context window capacity and the cumulative task token meter. Context assembly must fit relevant diagnostic evidence within a single invocation’s context limit, whereas the billing meter charges for all input and output tokens consumed across the full sequence of repair calls. While context compaction can summarize historical attempts to fit within the context window, compaction consumes additional model calls, adds latency, and discards fine-grained diagnostic detail. Notebook [12.3](https://mlsysbook.ai/vol3/12_failure_recovery/12_failure_recovery.html#nbk-12-loop-cost) in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^sec-vol3-failure-recovery-loop-cost-section|section 12.6.2]] prices what appending feedback turn after turn costs under a concrete workload.

### Admissibility and Expected Cost

^sec-vol3-failure-recovery-admissibility-cost

A repair call that is inexpensive on average can still overrun the task’s remaining dollar ceiling in the worst case or attempt to bypass an expired permission grant. Before evaluating the economic trade-offs of recovery, the runtime therefore eliminates any candidate action that fails admission control. For instance, an authentication failure never grants permission to synthesize an unauthorized bypass; instead, the runtime must either request an authorized credential refresh, locate a permitted fallback operation, or pause execution and escalate. Financial, latency, and context limits enforce hard ceilings: the runtime admits a candidate repair only if its maximum bounded liability fits within the remaining budget and deadline allowances and the assembled repair context fits within the target model’s context capacity.

↩︎ Bounded-liability admission, which admits an operation only when its maximum charge fits the remaining allowance, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-agent-harness-reservation-settlement|Reservation and settlement]]**.

Expected cost guides the recovery policy only among candidate actions that have cleared admission. Historical expenditures are sunk costs; recovery decisions must depend strictly on forward-looking costs and risks: the cost of retaining useful state, rebuilding that state from scratch, attempting repair, and managing secondary failure. While expensive earlier preparation often implies costly reconstruction, past spending alone never justifies continuing down a failing path. Ongoing resource holding fees, unsafe residual side effects, or task deadline expirations often dictate that discarding partially completed work is preferable to attempting a repair.

### Repair Vs. Rebuild

^sec-vol3-failure-recovery-repair-vs-rebuild

When `env_r18_01` is already running and only the test configuration failed local validation, tearing down and rebuilding the environment wastes every second spent provisioning it. Yet spending turns on a low-probability repair wastes tokens and still pays for the rebuild if the repair fails. To compare attempting a bounded repair against executing an immediate fallback that unwinds and rebuilds the required state, let ${C_{\text{fallback}}}$ denote the future cost of compensating existing side effects and rebuilding to a declared readiness endpoint. Let one bounded repair attempt cost ${C_{\text{repair}}}$, with probability ${p}$ of reaching that same endpoint. Assuming that an unsuccessful repair leaves the original fallback pathway available at unchanged cost, the expected total cost of attempting repair before falling back is

$$
\mathbb{E}[{C_{\text{repair\ first}}}] = {C_{\text{repair}}} + (1-{p}){C_{\text{fallback}}}. \tag{3}
$$

^eq-vol3-repair-first-cost

For any strictly positive fallback cost, attempting repair first yields a lower expected cost than an immediate fallback whenever

$$
{p} > {p}^* = \frac{{C_{\text{repair}}}}{{C_{\text{fallback}}}}. \tag{4}
$$

^eq-vol3-repair-breakeven

Engineers must evaluate this comparison independently for latency (in seconds) and monetary expense (in model dollars), as their respective break-even thresholds ${p}^*$ often diverge. If ${C_{\text{repair}}} \ge {C_{\text{fallback}}}$, no success probability below one can make repair cheaper on that resource axis. Furthermore, if a failed repair alters residual side effects, extends resource holding times, or increases fallback complexity, the term $(1-{p}){C_{\text{fallback}}}$ must be replaced by the corresponding conditional fallback cost. Expected cost is the last of three gates, not the first. Evidence class decides which candidates exist at all, admissibility removes those that authority, allowance, or the deadline forbids, and only then does [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.05 Forward Recovery#^eq-vol3-repair-breakeven|equation 4]] rank the survivors; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.05 Forward Recovery#^fig-vol3-recovery-decision-tree|figure 2]] lays out that order.

![[90 Assets/Volume III/12 Failure Recovery/Recovery Decision Tree dea109109c.svg]]

Figure 2: **Recovery Decision Order**: Evidence class comes first, because an unknown outcome admits only a retry of the same operation under its repeat contract (a result-recovery probe or a wait gathers evidence that moves the outcome out of this branch rather than acting on it), while a rejected proposal or an established effect opens new proposals, repair, and compensation. Admissibility then removes candidates that lack authority, allowance with the finalization reserve intact, or time; if none remain, the runtime holds or escalates. Expected cost at a matched endpoint chooses only among the admissible survivors, and applies separately to seconds and dollars.

^fig-vol3-recovery-decision-tree

**Napkin Math 12.1: Repair vs. unwind at matched readiness**

**Problem**: After the locally rejected integration-test configuration, at what repair success probability does one attempt become cheaper than immediate compensation and rebuilding, measured separately in time and model dollars? Both paths end at the same endpoint: a usable isolated environment and a validated configuration ready to submit the integration test against `ws_r18`, possibly in a different environment after rebuilding.

**Variables**: All inputs are hypothetical, and the earlier operations are settled, so no unknown provisioning request is being repeated. Immediate compensation takes 40.6 s; rebuilding, including obtaining and validating a usable configuration, takes 46 s. Rebuilding uses 38,500 input and 3,100 output tokens at \$3 and \$15 per million, respectively. Compensators use no model tokens.

The isolated repair call receives 2,390 tokens in its *entire* request, including instructions, scope, failed configuration, and diagnostic; no earlier conversation is silently appended. It produces 180 output tokens. Assume 0.09 s of pre-output processing for this short request, which excludes queueing and so is not a measured time to first token, then 50 tokens/s, followed by 0.4 s of local validation on either outcome. The local repair has no external effects; on failure its private candidate is discarded and the original fallback remains available at unchanged cost. Success means the stated readiness checks passed. Dollars cover model tokens only, and time excludes queueing and new outages.

**Math**: The fallback takes ${C_{\text{fallback}}}$ = 40.6 s + 46 s = 86.6 s and \$0.162 in model charges. One repair attempt takes ${C_{\text{repair}}}$ = 0.09 s + 180/50 s + 0.4 s = 4.09 s and costs \$0.00987. The break-even ${p}^* = {C_{\text{repair}}}/{C_{\text{fallback}}}$ is about 4.7 percent for elapsed time and 6.1 percent for model dollars. At an assumed 50 percent success probability, ${C_{\text{repair}}} + (1-{p}){C_{\text{fallback}}}$ gives an expected 47.39 s and \$0.09087.

**Result**: Repair first pays on both axes whenever at least one attempt in 16 succeeds, and at the assumed rate it cuts expected time to readiness by 45.3 percent.

**Systems insight**: The fallback cost ${C_{\text{fallback}}}$ sets the decision threshold. When compensation discards expensive, reusable preparation, the ratio ${C_{\text{repair}}}/{C_{\text{fallback}}}$ is small, making repair the preferred first attempt for any failure class whose measured success rate clears it. As ${C_{\text{fallback}}}$ decreases toward ${C_{\text{repair}}}$, however, the threshold approaches certainty and immediate unwind becomes the optimal choice. Expected cost ranks admissible actions; the admission check still decides which actions are permitted to run.

### The Repair Episode

^sec-vol3-failure-recovery-repair-episode

Even when a single repair attempt is cheap enough to try first, allowing an agent to retry a broken configuration without a cap, or to reset its attempt counter by renaming the step, turns a bounded fix into an open-ended loop. An agent runtime cannot know in advance whether a given failure is repairable, so it groups corrective attempts into a bounded **repair episode**.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.16 Footnotes#^fn5|⁵]] Each episode maintains a unique identity, records the task and candidate versions it governs, and tracks an attempt counter against an explicit allowance, the repair cap ${K_{\text{repair}}}$. Every corrective model invocation or tool dispatch must pass admission control and reserve its liability against that allowance. Because the counter increments upon admission rather than success, failed, timed-out, or aborted executions cannot evade the limit. Furthermore, transport retries and secondary proposals remain explicitly tied to their parent operations, ensuring that underlying retry mechanisms cannot silently consume a fresh allowance.

Because the attempt limit is an operational policy parameter, exhausting it provides no proof that the underlying problem is unsolvable. A task’s cumulative financial budget and outstanding obligations carry across any revised plan or renamed operation. Only an authorized policy modification can initiate a new repair episode, and that new episode inherits all previous telemetry and resource consumption.

Observing repeated errors or identical candidate states justifies early runtime inspection, but repetition alone does not constitute definitive proof of non-progress. An unchanged error diagnostic can follow valuable internal context pruning, and revisiting an earlier state may represent a deliberate search backtrack. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^sec-vol3-sagas-watchdogs|Section 12.6]] formalizes dedicated watchdog mechanisms to detect these stalls. Once the episode allowance is exhausted or an admission check fails, the runtime denies further repair attempts and selects among still-permitted compensation, a paused continuation awaiting operator inspection, or an explicit escalation.

**Checkpoint 12.2: Choose and bound a repair**

A disciplined recovery strategy evaluates evidence class first, verifies admission constraints second, and optimizes expected cost last.

**Unknown vs. rejected**: Why does a locally rejected configuration support a different recovery decision from a timed-out provisioning request?

**Matched endpoints**: What is missing from a comparison that prices successful repair but stops the rebuild path just before the failed step?

**Break-even estimate**: A repair attempt costs one twentieth of the unwind-and-rebuild fallback, and recorded episodes for this failure class succeed one time in ten. Should the runtime repair first, and how small would the fallback have to become to reverse the decision?

**Expected vs. bounded cost**: Why can a repair have a favorable expected dollar cost but still fail the admission test?

**Residual effects**: Which term must change if a failed repair leaves an extra resource to compensate or increases the fallback’s holding cost?

The break-even analysis in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.05 Forward Recovery#^sec-vol3-failure-recovery-repair-vs-rebuild|section 12.4.3]] assumed that compensation remains an available fallback pathway throughout repair. Certain external commitments, however, irreversibly alter outside state, permanently foreclosing compensation and demanding different safety guarantees.
