# V3-14.06 Staged Releases

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14 Operating Agents|V3-14 Operating Agents]]

^sec-vol3-evaluation-releases

Although the revised observation interface produced accepted repairs on the isolated fixture in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.05 Incident Postmortems#^sec-vol3-evaluation-postmortems|section 14.4]], promoting that revision straight to full production traffic would expose live repositories and external services to unmeasured failure modes. That fixture result supports only testing the change on a broader task set; production authority is a separate grant. A release decision connects the change to its evidence and to the consequences of being wrong, because when an agent regression triggers a rollback, stopping new traffic does not undo tool calls, state mutations, or cloud allocations that remain in flight.

Staging separates evidence available before live execution from evidence that requires it. Offline trials compare configurations on declared fixtures. **Shadow execution** tests a candidate against authorized copies of current inputs without assigning it the live task. After that, a **canary**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.13 Footnotes#^fn5|⁵]] assigns a bounded portion of eligible live tasks to the candidate under an explicit release policy. The canary is the ramped online controlled experiment of web services, applied to agent configurations ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-kohavi2008|Kohavi et al. 2009]]). Each stage answers its own question, and causal and statistical release evidence (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-release-evidence|12]]) supports a scoped decision at each step. Failure at any stage routes to the same enforced admission hold ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^fig-vol3-canary-deployment-pipeline|figure 3]]), which stops new candidate work while recovery settles the work already in flight. The subsections that follow develop the criterion each stage applies.

![[90 Assets/Volume III/14 Agent Operations/Vol3 Canary Deployment Pipeline 0d11cb2b47.svg]]

Figure 3: **Staged Release and Its Hold Path**: Each stage applies its own criterion: the lower bound of the paired acceptance interval against the declared margin offline, a divergence measure of tool-call drift in shadow execution, and a sequential likelihood-ratio monitor with hard tripwires in the canary. The symbols in the stage boxes are defined in the subsections that follow. A wider release requires every criterion of the declared release gate ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.07 The Release Decision#^eq-vol3-eval-release-gate|equation 5]]). An unmet or inconclusive offline result, a drift review that finds a problem, or a canary alarm leads to the same hold. The hold stops new candidate admission; outstanding candidate operations keep their identities and owners, and recovery, not rollback, settles their effects.

### Offline Comparison and Shadow Evidence

^sec-vol3-evaluation-releases-shadow

Replaying live user requests through a candidate in shadow mode before it clears its paired offline comparison, or mirroring inputs without isolating side effects and checking recipient permissions, can leak private data to new endpoints or mutate production records twice. The offline decision therefore comes first, using the paired comparison of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-paired|Paired outcome comparison]]** with the same criteria, sampling unit, budgets, and predeclared margin; comparing separate Wilson lower bounds does not answer it. In the worked case the lower difference bound misses the tolerance, so the candidate stays offline, and favorable traces leave the unmet gate unmet.

For a configuration that clears the offline gate, shadow execution copies each input into a separate execution with its own identity and allowance, while the baseline still serves the original task. Privacy and authorization checks must permit the copied input, its destinations, and the shadow tool operations, since discarding the output does not license sending private data to a new service. The shadow environment also bounds the answerable questions. An isolated stateful replica supports checks of the resulting artifact, a recorded-response fixture supports a narrower comparison under the matching-request rule, and a synthetic success reply to an unperformed mutation establishes nothing about production. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^tbl-vol3-dark-traffic-routing|Table 6]] distinguishes the live task from the additional experiment.

| Boundary             | Baseline execution                                     | Shadow execution                                                                        |
|:---------------------|:-------------------------------------------------------|:----------------------------------------------------------------------------------------|
| Task assignment      | Serves the original admitted live task                 | Receives an authorized copy as a separate experiment                                    |
| Effects              | Uses only the live task’s current grant                | Uses separately bounded isolated state or an explicitly supported observation path      |
| Data access          | Follows the task’s disclosure and access policy        | Copying inputs and forwarding tool arguments require their own permitted recipients     |
| Acceptance evidence  | Applies the live task criteria                         | Applies only criteria supported by the shadow fixture’s fidelity                        |
| Delivery and cleanup | Returns the task result through its authorized channel | Withholds candidate output from the live task and settles its own resources and charges |

Table 6: **Shadow execution boundaries**: Input mirroring adds an experiment. It neither divides the baseline’s original task assignment nor makes the copied data and tool traffic harmless.

^tbl-vol3-dark-traffic-routing

Read access still has effects. Queries can acquire locks, consume quotas, trigger logging, or disclose arguments, so the shadow design names the services it contacts, relying on sandbox isolation and tool mediation.

Tool selection, token use, and latency differences can expose a changed operating pattern before live task assignment. For tool selection, the Jensen–Shannon divergence ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-lin1991divergence|Lin 1991]]) between the baseline and candidate distributions of tool calls, ${p_{b}}$ and ${p_{c}}$, summarizes the change in one number. It is built from the Kullback–Leibler divergence ${\mathcal{D}_{\text{KL}}}({p_{b}}\,\|\,{p_{c}})=\sum_{y} {p_{b}}({y})\ln\bigl({p_{b}}({y})/{p_{c}}({y})\bigr)$, the expected log-ratio between two distributions over tool calls ${y}$, which is zero only when they match:

$$
{\mathcal{D}_{\text{JS}}}({p_{b}}\,\|\,{p_{c}})=\tfrac12 {\mathcal{D}_{\text{KL}}}({p_{b}}\,\|\,{\bar{P}})+\tfrac12 {\mathcal{D}_{\text{KL}}}({p_{c}}\,\|\,{\bar{P}}),\qquad {\bar{P}}=\tfrac12({p_{b}}+{p_{c}}). \tag{1}
$$

^eq-vol3-eval-tool-drift

Unlike ${\mathcal{D}_{\text{KL}}}({p_{b}}\,\|\,{p_{c}})$, which divides by zero whenever one configuration calls a tool the other never uses, ${\mathcal{D}_{\text{JS}}}$ compares each distribution against their average ${\bar{P}}$. Every tool used by either configuration has a mixture probability of at least half its single-configuration share, so the probability ratio against ${\bar{P}}({y})$ never exceeds $2$ and its natural logarithm never exceeds $\ln 2$. That bound makes ${\mathcal{D}_{\text{JS}}}$ symmetric and confines it to $0\le {\mathcal{D}_{\text{JS}}}\le\ln 2$, which gives a fixed scale for comparing releases. For a sense of that scale, suppose the baseline sends 70 percent of its tool calls to tests and the rest to lint, and the candidate splits them evenly. That plainly visible shift gives ${\mathcal{D}_{\text{JS}}}$ of about 0.021, roughly 3 percent of the 0.693 maximum that two configurations with no tool in common would reach. A useful alert threshold is therefore a small number, and it means something only against the divergence between two baseline samples of the same size, which shows how far the distribution moves by chance. The distributions must come from comparable inputs and one declared action-counting policy, and difference alone is not regression, since the intended repair may remove redundant calls. A shadow result can justify another test or a hold, whereas it cannot supply evidence for production effects that the shadow deliberately prevented.

### Canary Task Assignment

^sec-vol3-evaluation-releases-canary

Routing canary traffic per model call rather than per trajectory mixes `baseline_v1` and `candidate_v2` inside a single repair task, making any resulting failure or side effect impossible to attribute to either configuration. Because a canary is live execution with real effects, the release policy declares the eligible population, allocation rule, candidate configuration (model request, prompt, tools, harness, and verifier versions), comparison policy, resource limits, and stop conditions before any task is assigned. An allocation fraction ${\rho}$ limits the share of eligible tasks assigned under that rule; it is neither a per-task authority grant nor a worst-case bound on total effects.

The policy assigns the configuration at the task or trajectory boundary and preserves it through continuation. Retries, resumed work, and delayed labels keep the original cohort identity, and dependent tasks from one customer or repository may need that larger unit of randomization. This is **trajectory-level sticky routing**, a stable configuration assignment rather than a promise to retain one physical model instance; workers can change through the resume protocol, and cohort assignment alone does not guarantee warm serving state.

↩︎ The resume protocol, under which a replacement worker takes ownership of a trajectory, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-persistence-migration|Resuming a Trajectory]]**.

Outcome delay matters even when assignment is correct. Under the four-verdict rule of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^sec-vol3-evaluation-contract-verdicts|The four-verdict rule]]**, every admitted task stays counted in its cohort, because counting only completed fast tasks can make a slow failing candidate look favorable. The analysis specifies when labels are mature and how unresolved cases affect promotion, and a failed label-delivery path is an evidence failure, not a reason to drop those tasks.

### Sequential Monitoring

^sec-vol3-evaluation-releases-sequential

Repeatedly applying a fixed-sample test after each new canary outcome inflates its false-positive rate well above the nominal level ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-johari2017peeking|Johari et al. 2017]]). A sequential design instead declares in advance how accumulating evidence will be used. The **sequential probability ratio test** (SPRT)[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.13 Footnotes#^fn6|⁶]] ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-wald1945sequential|Wald 1945]]) is the compact example for two specified distributions, and it is a different procedure from the paired offline noninferiority test.

Let independent task labels ${X}_i$ be Bernoulli with a stationary acceptance probability, and let the simple hypotheses be ${p_{\text{acc}}}={p}_0$ and ${p_{\text{acc}}}={p}_1$, with $0<{p}_1<{p}_0<1$ and the lower value a particular degradation. Both values are design inputs, not estimates. With ${d}_n=\sum_{i=1}^{{n}} {X}_i$, the log-likelihood ratio favoring the degraded hypothesis is

$$
{\Lambda}_n = {d}_n \ln\left(\frac{{p}_1}{{p}_0}\right) + ({n}-{d}_n)\ln\left(\frac{1-{p}_1}{1-{p}_0}\right). \tag{2}
$$

^eq-vol3-release-sprt

Success moves the statistic in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^eq-vol3-release-sprt|equation 2]] downward; failure moves it upward. Let ${\alpha_{\text{sig}}}$ target the probability of choosing degradation under ${p}_0$, and ${\beta_{\text{stat}}}$ the probability of choosing ${p}_0$ under ${p}_1$. For $0<{\alpha_{\text{sig}}},{\beta_{\text{stat}}}<1$ and ${\alpha_{\text{sig}}}+{\beta_{\text{stat}}}<1$, Wald’s commonly used approximate log boundaries are

$$
{u} = \ln\left(\frac{1-{\beta_{\text{stat}}}}{{\alpha_{\text{sig}}}}\right), \qquad {b_{\text{low}}} = \ln\left(\frac{{\beta_{\text{stat}}}}{1-{\alpha_{\text{sig}}}}\right). \tag{3}
$$

^eq-vol3-release-sprt-boundaries

Discrete observations can overshoot these approximate thresholds because a single task label jumps across the boundary in a finite step rather than stopping on it exactly. Calibrating the realized error probabilities therefore requires evaluating the discrete walk under the actual model ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-fischer2026improving|Fischer and Ramdas 2026]]).

![[90 Assets/Volume III/14 Agent Operations/Vol3 Eval Margin Sprt Corridor 5bd990d0ee.svg]]

*A shaded corridor between a red upper line labeled hold and a green lower line labeled select p sub 0. From a common start on a dotted center line, a red dashed line rises to the upper boundary and a green dashed line falls to the lower one. The middle of the corridor is labeled keep sampling.*

*Evidence drifts toward hold under degradation and toward selecting ${p}_0$ otherwise; between the boundaries, keep sampling.*

**Systems Perspective 14.2: Reading a sequential decision**

At ${\Lambda}_n\ge {u}$, the test selects the specified degraded hypothesis and the release policy can stop new candidate admission. At ${\Lambda}_n\le {b_{\text{low}}}$, it selects ${p}_0$ against that particular alternative. Between the boundaries, evidence remains inconclusive. Selecting ${p}_0$ rejects one specified degradation; general noninferiority, broader traffic, and safety each need their own evidence. A deadline or sample cap that ends collection between the boundaries leaves the decision inconclusive.

A production stream can violate this model through changing task mix, shared outages, correlated tasks, or delayed labels. Processing results in completion order creates selection bias when duration depends on outcome, which a declared admission-order analysis avoids at the cost of waiting behind unresolved tasks. Testing several metrics or restarting after an unfavorable path needs error control beyond these two boundaries.

The same simplified model gives a planning approximation for the expected stopping sample count. Under ${p}_1$, each labeled task moves the log-likelihood ratio by an expected step of ${m}_1={p}_1\ln({p}_1/{p}_0)+(1-{p}_1)\ln((1-{p}_1)/(1-{p}_0))$. Neglecting boundary overshoot, the walk ends at the upper boundary ${u}$ with probability $1-{\beta_{\text{stat}}}$ and at the lower boundary ${b_{\text{low}}}$ with probability ${\beta_{\text{stat}}}$. Dividing that expected terminal position by the expected step per task gives the expected stopping sample count:

$$
\mathbb{E}_1[{N_{\text{stop}}}]\approx\frac{(1-{\beta_{\text{stat}}}){u}+{\beta_{\text{stat}}} {b_{\text{low}}}}{{m}_1}. \tag{4}
$$

^eq-vol3-release-sprt-samples

The numerator in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^eq-vol3-release-sprt-samples|equation 4]] averages both terminal decisions, as in the classical average-sample-number approximation ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-wald1945sequential|Wald 1945]]; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-hory2004sequential|Hory and Hero 2004]], eq. 24). **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-sprt|Wald's sequential probability ratio test (SPRT) decision boundaries]]** derives the approximate decision boundaries and stopping-sample expression while distinguishing target errors from realized errors.

**Napkin Math 14.3: Sequential evidence takes calendar time**

**Problem**: Consider a separate, hypothetical later configuration that has met its offline and shadow prerequisites. Its monitor compares ${p}_0$ equal to 0.90 with ${p}_1$ equal to 0.75, using design targets ${\alpha_{\text{sig}}}$ equal to 0.01 and ${\beta_{\text{stat}}}$ equal to 0.05. At 60 eligible tasks/hour and a 5 percent candidate allocation, what stopping-sample and calendar-time scale does the no-overshoot approximation predict under ${p}_1$?

**Assumptions**: Outcomes are independent with constant probability, admissions arrive at regular intervals, and each label arrives exactly 0.5 h after admission with none lost. The test is untruncated, with no operational tripwire.

**Math**: The approximate boundaries are 4.5539 and -2.9857. Under ${p}_1$, the expected increment is 0.09233. Neglecting overshoot and substituting the target decision probabilities gives expected terminal log-likelihood 4.1769. Dividing that quantity by the expected increment gives approximately 45.24 labeled tasks. The average includes both possible decisions, including mistaken selection of ${p}_0$; it is not the expected number until an alarm.

Candidate admissions occur at 3 tasks/hour. The corresponding admission-time scale is 15.08 h; adding the fixed label delay gives approximately 15.58 h until a decision. Tasks admitted while labels are pending can still be executing when the test stops.

**Systems insight**: The sample count is fixed by the hypotheses and error targets, so calendar time to a decision scales as $1/{\rho}$. Doubling the allocation to 10 percent cuts the time to about 8.0 h. Choose ${\rho}$ from the decision deadline and from the exposure the release can tolerate to harms the monitor does not measure, and keep independent admission and effect limits, because an expected sample count is not a maximum.

The sample count and the canary fraction control different harms. Under ${p}_1$, each candidate task fails about ${p}_0-{p}_1$ more often than it would under the baseline. With allocation fraction ${\rho}$ of eligible arrivals at rate ${\lambda_{\text{arr}}}$ and label delay ${t_{\text{label}}}$, the monitor decides after roughly $\mathbb{E}_1[{N_{\text{stop}}}]$ labeled tasks plus the ${\rho}{\lambda_{\text{arr}}} {t_{\text{label}}}$ tasks admitted while their labels are pending, so the measured regression costs about $(\mathbb{E}_1[{N_{\text{stop}}}]+{\rho}{\lambda_{\text{arr}}} {t_{\text{label}}})({p}_0-{p}_1)$ excess failures. In the notebook’s scenario that is about 7 at the canary fraction and about 11 at full allocation. The fraction enters only through the label delay; its main effect on a measured regression is the calendar time needed to collect the samples.

Harms the monitor does not measure behave differently. They accrue for every admitted candidate task until some other mechanism detects them, so their rate scales with ${\rho}$, and this canary exposes candidate tasks at 5 percent of the full-allocation rate. The test’s sample size fixes the harm from a measured regression; the canary’s size limits the harms the test does not measure. A production release of a foundation model shows what the second kind of harm looks like when it escapes.

**War Story 14.1: The GPT-4o sycophancy rollback (2025)**

**Context**: In late April 2025, OpenAI rolled out an update to the GPT-4o model behind ChatGPT, adjusting its default personality ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-openai2025sycophancy|OpenAI 2025b]]).

**Mechanism**: By OpenAI’s account, the update focused too much on short-term user feedback and did not account for how users’ interactions evolve over time. The model skewed toward responses that were overly supportive but disingenuous. OpenAI’s follow-up analysis reports that changes including an added reward signal from user thumbs-up and thumbs-down feedback weakened the influence of the primary reward that had held sycophancy in check. The same analysis reports that the offline evaluations and the A/B test of the update both looked good before launch ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-openai2025expanding|OpenAI 2025a]]).

**Impact**: The update reached ChatGPT users before the behavior was recognized, and OpenAI rolled it back, returning users to an earlier version with more balanced behavior.

**Fix**: OpenAI committed to refining training techniques and system prompts to steer the model away from sycophancy, adding guardrails for honesty and transparency, expanding predeployment testing with direct user feedback, and expanding its evaluations to catch behavioral issues beyond sycophancy.

**Systems lesson**: A release gate passes exactly the criteria it declares. A regression in a property that no criterion measures clears every term of the gate, and no sequential monitor can stop it because none is watching it. The durable responses are a new criterion for the next release and an admission hold on the regressed configuration.

The sycophancy regression is that unmeasured harm at full scale. Detection came from outside the declared criteria, and the effective response was an admission stop on the regressed configuration followed by settlement of what it had already done.

### Operational Tripwires

^sec-vol3-evaluation-releases-tripwires

Waiting for a sequential statistical monitor to accumulate dozens of labeled tasks after a candidate dispatches a forbidden tool call allows a deterministic policy breach to keep repeating until the sample threshold is met. A hard operational tripwire therefore does not wait for statistical evidence: a verified forbidden dispatch, an exhausted release allowance, or too much unresolved candidate work immediately stops further admission under the declared policy. A task-count cap bounds effects only when each task’s effects are also bounded at enforcing endpoints; a routing percentage alone supplies neither bound.

↩︎ The per-trajectory budget vector that caps each task’s turns, tokens, elapsed time, and cost is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-harness-multidim-budgets|Turn, token, time, and dollar budgets]]**.

Rollback changes which configuration may receive new work. It does not retract transmitted requests, restore changed objects, or make a baseline worker eligible to continue a candidate trajectory without the ownership and compatibility checks of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-persistence-migration|Resuming a Trajectory]]**. Outstanding candidate operations keep their original identities, and an explicit recovery policy governs their effects, cleanup, and residual owners. Detection, confirmed admission stop, and effect settlement are distinct intervals, and effects that cannot be undone or remain unknown at the cutoff stay out of any average that implies every case was restored.

↩︎ Settling residual effects through admitted compensation under an accountable owner, once model-directed work has stopped, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.09 Incident Containment#^sec-vol3-failure-recovery-residual-settlement|Residual settlement]]**.

### Release Measurements

^sec-vol3-evaluation-releases-measurements

Reporting only the pass rate of completed canary tasks, or comparing the throughput of an arrival-limited 5 percent canary directly against a fully loaded baseline, can make a slow, stalling candidate look both accurate and fast. Release reporting therefore keeps a fraction of tasks, a rate of completion, and the resources spent producing them distinct. The accepted task is the unit that trajectory goodput (principle [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/V3 Agents at Scale Principles#^pri-vol3-trajectory-goodput|15]]) charges all initiated work against. That principle is developed with the economics of agents at scale; the release record needs only its measured rate, defined below.

↪ Trajectory goodput as the throughput metric for sizing an agent platform is developed in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.07 Capacity for Trajectories#^sec-vol3-agent-economics-residence-service-quota|Residence, service, and quota]]**.

For a declared admitted cohort of size ${N}$, let ${N_{\text{acc}}}$ count tasks meeting the complete acceptance contract by the observation cutoff, so ${\alpha}={N_{\text{acc}}}/{N}$. Pending and unknown cases sit in ${N}$ as not accepted under the default of the four-verdict rule, and the report lists them separately from established failures.

For an observation interval $[{t_{a}},{t_{b}})$, let ${N_{\text{acc}}}[{t_{a}},{t_{b}})$ count acceptance events in that interval under the declared measurement policy. Over that interval, trajectory goodput is measured as

$$
{\mathcal{G}} = \frac{{N_{\text{acc}}}[{t_{a}},{t_{b}})}{{T_{\text{obs}}}}, \qquad {T_{\text{obs}}}={t_{b}}-{t_{a}}.
$$

The denominator is elapsed observation time, not the sum of overlapping task durations, and the report states startup and drain treatment, concurrency, and arrival policy. A small canary can be arrival-limited, so its measured goodput is not comparable with a fully loaded baseline’s capacity. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^tbl-vol3-sre-metrics|Table 7]] keeps companion measurements tied to their denominators.

| Measurement                | Denominator or boundary                                                                                                                                                                                 | Interpretation to preserve                                                                    |
|:---------------------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------|
| Observed accepted fraction | All tasks in the declared admitted cohort                                                                                                                                                               | Report failed, pending, and unknown cases separately                                          |
| Trajectory goodput         | Elapsed observation interval                                                                                                                                                                            | Match workload and capacity before comparing rates                                            |
| Cost per accepted task     | Accepted count, with all included cohort costs in the numerator                                                                                                                                         | Include failed work and report unsettled liability; undefined when none are accepted          |
| Intervention burden        | Events per task, or tasks with an intervention divided by all tasks                                                                                                                                     | Event counts can exceed one per task; routine required approval is not automatically a defect |
| Latency and settlement     | Named start/end events and observation cutoff                                                                                                                                                           | Report unresolved cases; an empirical percentile is not a hard per-task deadline              |
| Behavioral change          | Comparable input mix and declared action-counting policy; ${\mathcal{D}_{\text{JS}}}$ from [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^eq-vol3-eval-tool-drift\|equation 1]] | A different tool distribution may reflect improvement, regression, or changed demand          |

Table 7: **Release measurements and their scope**: Operational signals retain their units and populations. Zero observed violations does not establish zero future risk, and a denied proposal is distinct from an escaped effect.

^tbl-vol3-sre-metrics

The paired comparison, diagnostic experiment, and sequential monitor answer different questions and cannot substitute for one another. A coherent release record brings them together with their fixtures, limits, and residual obligations so that the resulting decision can be inspected.
