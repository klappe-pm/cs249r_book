# V3-14.05 Incident Postmortems

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14 Operating Agents|V3-14 Operating Agents]]

^sec-vol3-evaluation-postmortems

When verdict-aware retention preserves the failed connection-pool repair trial of `candidate_v2` ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.02 From Offline Verdict to Live Operation#^sec-vol3-operations-introduction|section 14.1]]), the retained trace shows the search response ending in the middle of a source excerpt with no truncation notice, even though the bounded-observation contract requires one, followed by a model response that proposes replacing a file outside the permitted repair scope. The runtime rejects that proposal before dispatch. While the execution trace pinpoints where the observation was cut short and where the runtime blocked the illegal operation, it cannot reveal whether a complete observation would have produced an accepted repair. An incident postmortem[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.13 Footnotes#^fn4|⁴]] connects such telemetry to a testable explanation and a scoped corrective change.

↩︎ The bounded-observation contract, under which an adapter that cuts a result must say so in a typed truncation notice, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.07 Observation Stream Truncation#^sec-vol3-tool-calling-truncation-notices|Truncation notices and inspection handles]]**.

Rigorous postmortems keep these initial findings strictly separated. Delivering an excerpt without truncation metadata demonstrates an interface defect. Emitting an out-of-scope file replacement reveals how the foundation model behaved when starved of context. Intercepting that illegal write confirms that the admission gate functioned as designed. Because failures in agentic systems typically stem from compounding interactions across subsystems, prematurely pinning the fault on a single component obscures the precise conditions that engineering fixes must resolve.

### Reconstruction and Replay

^sec-vol3-postmortem-replay

Rereading a static trace cannot show whether `candidate_v2` would have repaired the connection pool given an untruncated search result. Re-running a modified agent against recorded tool outputs without request matching can also pair new model calls with stale environment replies. The three uses of a recorded trajectory from durable execution become the postmortem’s three instruments, each answering a distinct diagnostic question:

- *Time-travel replay* folds recorded decisions from a compatible execution checkpoint to recover the exact system state visible to the agent at the moment of failure.
- *Harness regression replay* executes deterministic component code against captured inputs while disabling live external side effects.
- A *counterfactual branch* forks execution from a saved prefix, altering a specific variable or interface contract and collecting fresh observations along the divergent path.

↩︎ The three uses of a recorded trajectory, and the limits of what each one shows, are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.07 Recorded Trajectory Replay#^sec-vol3-persistence-replay|Recorded Trajectory Replay]]**.

Time-travel replay only inspects the past, and no replay mode can synthesize an unrecorded historical outcome. Demonstrating that a revised routine now passes its tests does not change what the original trial delivered, observed, or did. Furthermore, the fidelity of time-travel replay remains strictly bounded by the capture contract defined in perspective [14.1](https://mlsysbook.ai/vol3/14_agent_operations/14_agent_operations.html#psp-13-telemetry-duality). Examining the delivered context reveals the truncated excerpt presented to the model. Reviewing separately preserved raw stdout reveals what the adapter dropped. Inspecting redacted logs reveals only execution metadata and high-level status.

Harness regression replay is especially effective for isolating data transformations without incurring expensive model invocations. Supplying captured tool responses to legacy and revised observation adapters, with live effect paths disabled, deterministically verifies that the legacy adapter omitted a required partial-result marker while the revised adapter correctly supplies it. However, this offline harness test cannot predict how a model will respond to the revised observation envelope. Answering that question requires a live experiment. Any alteration to prompt text, sampling temperature, model configuration, or tool observation formats represents an intervention rather than a passive replay. Recorded downstream responses remain reusable only under the matching-request rule of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms|Hermetic Evaluation Gyms]]**; matching solely on tool names risks fabricating artificial successes by pairing new model actions with obsolete environment responses.

### Fault Attribution

^sec-vol3-postmortem-attribution

Blaming the model for proposing an out-of-scope file rewrite, or trusting the model’s own retrospective explanation of why it failed, confuses a downstream symptom with the upstream truncation defect that triggered it. In the connection-pool incident, comparing the search tool’s raw output against the delivered envelope confirms that the observation adapter silently truncated the text. That finding yields an engineering hypothesis, namely that omitting the completeness signal misled the model into generating inappropriate repair proposals. Validating this hypothesis demands empirical outcomes measured after an intervention rather than repeated scrutiny of historical telemetry. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.05 Incident Postmortems#^tbl-vol3-fault-attribution|Table 4]] distinguishes useful evidence from claims that telemetry cannot support alone; its rows represent overlapping investigation paths rather than mutually exclusive diagnoses.

| Suspected boundary    | Evidence or controlled comparison                                           | Limit of the finding                                                                 |
|:----------------------|:----------------------------------------------------------------------------|:-------------------------------------------------------------------------------------|
| Context assembly      | Compare retained source versions, delivered messages, and omission metadata | An omitted fact is not proof that restoring it will complete the task                |
| Tool observation      | Compare captured output with the adapter’s declared and delivered envelopes | A truncation defect does not make the model’s later inference correct                |
| Model response        | Repeat the specified invocation or continuation under controlled conditions | A different response does not identify temperature or sampling as the original cause |
| Runtime admission     | Exercise captured proposals and control inputs against the stated guards    | A rejected proposal differs from an unauthorized operation that was dispatched       |
| Execution environment | Compare endpoint evidence, configuration, and relevant fault records        | A timeout or process termination signal alone does not identify its underlying cause |

Table 4: **Evidence for diagnostic hypotheses**: Localization constrains an explanation without making the subsystem categories exclusive.

^tbl-vol3-fault-attribution

System diagnostics must account for this ambiguity at every layer, because neither low-level system signals nor high-level model outputs are self-explanatory. An operating-system signal that terminates a container cannot distinguish an out-of-memory eviction from an administrative kill. Likewise, a schema-valid model response can still rest on unverified assumptions, and an agent’s retrospective self-explanation remains a generative hypothesis rather than empirical evidence.

### Controlled Diagnostic Experiments

^sec-vol3-postmortem-ablation

If an engineer ships an omission marker and pagination together while external service latency drifts between runs, a higher pass rate cannot distinguish whether the marker, the pagination, or the quieter infrastructure fixed the failure. To move from suspicion to actionable diagnosis, a controlled ablation protocol defines five elements before execution: the baseline checkpoint boundary, the specific architectural intervention, all frozen system configurations, allowable sources of stochastic variation, and uniform acceptance criteria. Resetting repository files while allowing external service behaviors to drift introduces confounding variables; interleaving experimental trials across branches helps decouple the intervention effect from infrastructure drift. Disentangling bundled changes such as a partial-result marker and pagination reads requires factorial conditions that vary each mechanism independently. The NIST discussion of one-factor experiments demonstrates why varying a single factor at a time fails to expose cross-component interactions ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-guthrie2020nisthandbook|Guthrie 2020, sec. 5.2.1.2]]).

**Example 14.1: A controlled test of observation completeness**

**Problem**: A diagnostic fixture reproduces a silently truncated search result during the connection-pool repair. What do the following hypothetical outcomes support about a proposed interface change?

**Scenario**: The experiment restores a private copy of a compatible saved prefix of `pool_repair_01` for every continuation, under three branches: the original interface, an added warning, and a revised paginated interface. Each run maintains its own execution lineage and identity, meaning these continuation trials offer evidence about counterfactual behavior without altering the recorded history of the trials that produced `ws_r18` or `ws_r19`. All conditions share the model configuration, sampling settings, starting candidate, permitted operations, budget, and checks, and each receives 20 fresh stochastic continuations. Acceptance uses the repair’s criteria and rejects any run that proposes the out-of-scope rewrite, which the unchanged admission gate blocks before dispatch, and every run reaches a known assessment.

The original-interface condition deliberately retains the adapter defect, delivering the truncated excerpt without an omission notice, and yields 1 accepted repair alongside 19 rejected runs that propose the forbidden rewrite. By contrast, a warning-only condition adds an instruction that search results may be incomplete without providing a continuation mechanism, producing 8 accepted repairs and 12 budget-limited runs that never reach an accepted repair, though none proposes the forbidden rewrite. Finally, the revised-interface condition supplies typed partial-result metadata together with a supported way to retrieve remaining results, achieving 20 accepted repairs with zero nonaccepted runs and no forbidden rewrite proposals. Across all three conditions, the admission gate prevents any unauthorized write from dispatching.

**Diagnosis**: Suppressing an illegal write proposal is not the same as successfully repairing the connection pool. While adding a static warning discourages the model from proposing out-of-scope file modifications, several continuations exhaust their execution budgets without reaching an acceptable fix. Conversely, the paginated interface achieves a complete success rate across these trials, justifying broader evaluation of that interface package. However, this diagnostic outcome does not prove that the metadata marker alone drove the turnaround, nor does it imply that model behavior was blameless in the original incident.

These stochastic continuations characterize performance strictly conditional on this specific saved prefix and fixture environment. Even achieving 20 accepted runs out of 20 trials still leaves an upper bound of 16 percent on the failure rate under the Wilson score interval of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-wilson|Confidence intervals for acceptance]]**. Furthermore, these diagnostic ablation runs must remain segregated from benchmark task-set evaluations; pooling them into release metrics would artificially inflate sample size and distort generalization estimates.

**Systems insight**: The observation adapter has an explicit, reproducible defect, and the counterfactual trials demonstrate that repairing it substantially improves continuation outcomes. When designing diagnostic experiments, engineers should preserve admission controls across all conditions, distinguish between safety enforcement (blocking forbidden actions) and functional utility (completing the task), and validate patches against diverse held-out tasks before declaring release readiness.

^exmp-13-counterfactual-ablation-of-a-silent

Because the revised interface restores the bounded-observation contract that the original adapter violated, pagination mechanisms must maintain snapshot consistency against an immutable source revision. Exposing a continuation token for content that the server cannot subsequently serve would substitute one observation defect for another.

### Scoped Regression Tests

^sec-vol3-evaluation-postmortems-regression

Testing an observation-adapter fix only through full end-to-end agent runs wastes model tokens on a deterministic serialization rule, whereas running only the adapter unit test never verifies that the repaired agent actually completes the connection-pool fix. A corrective patch therefore requires verification at two distinct architectural levels: the localized boundary where the defect occurred and the end-to-end task pipeline whose reliability it aims to restore.

At the boundary level, unit tests must remain entirely deterministic and decoupled from stochastic model calls. Observation-adapter test suites should systematically inject complete, truncated, malformed, and empty payloads, verifying that serialized envelopes correctly populate status fields and omission metadata. In parallel, admission-gate suites must directly submit synthesized out-of-scope file modifications to confirm that the policy engine blocks illegal writes prior to dispatch. Neither verification step requires invoking an LLM.

At the system level, regression tests execute the modified agent within an isolated fixture and evaluate the resulting candidate against the full acceptance suite. Engineers should never treat a bare runtime status of `COMPLETED` as an indicator of correctness, nor should they mistake a single passing test run for a guarantee of operational stability. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.05 Incident Postmortems#^tbl-vol3-postmortem-template|Table 5]] organizes the essential artifacts of an investigation, separating confirmed defects from ongoing statistical uncertainty.

| Report element          | Evidence to preserve                                                                                                      |
|:------------------------|:--------------------------------------------------------------------------------------------------------------------------|
| Incident and coverage   | Task, trial, configuration, candidate, relevant operation identities, retained interval, and missing or redacted material |
| Established findings    | Delivered partial observation without required metadata; exact forbidden proposal and recorded pre-dispatch refusal       |
| Tested change           | Interface revision, compatible fixture and saved boundary, branch identities, unchanged guards, and allowed randomness    |
| Outcomes                | Common acceptance and proposal/effect criteria, every run’s verdict, budget stops, and unavailable assessments            |
| Corrective verification | Adapter and admission tests, repeated task-level checks, and the actual revision tested                                   |
| Remaining questions     | Untested fixtures and interactions, retention limits, residual-operation owners, and evidence needed for release          |

Table 5: **A bounded postmortem record**: A rigorous incident record documents the empirical evidence supporting a fix alongside unresolved engineering uncertainties, avoiding oversimplified single-cause attributions.

^tbl-vol3-postmortem-template

**Checkpoint 14.3: Diagnosis and regression scope**

Use the repair experiment to distinguish a localized defect from a release claim.

**Replay modes**: Which test can establish that an adapter omitted a required marker without making a fresh model call, and what can that test not establish?

**Changed requests**: Why must a branch requesting another page obtain a matching observation instead of consuming the next recorded tool result?

**Common outcomes**: Why do fewer forbidden proposals not necessarily imply more accepted repairs?

**Diagnostic sample size**: About how many consecutive accepted continuations would the revised interface need before the Wilson upper limit on its failure rate fell below 5 percent?

**Regression scope**: Which checks test the adapter, which test admission, and which test completion of the repaired task?

An incident postmortem fulfills its engineering objective when it documents an established interface defect, provides a reproducible regression fixture, and verifies a targeted fix. However, resolving a single localized failure does not guarantee general reliability across diverse production workloads. Staged release evaluation determines which additional tasks, edge cases, and runtime conditions the candidate system must navigate while teams gather the next tier of empirical evidence.
