# V3-14.08 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14 Operating Agents|V3-14 Operating Agents]]

^sec-vol3-operations-fallacies

Even an apparently thorough operational record can answer the wrong engineering question. The failure modes below break the link between operational evidence and deployment readiness, and each exacts a measurable cost in operational stability, exposure, or diagnostic visibility.

**Pitfall**: *Relying on uniform head sampling to keep examples of rare failures.*

Head sampling makes a retention decision at request ingestion, long before the agent’s final execution outcome is known ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.04 Trace Retention and Privacy#^sec-vol3-evaluation-budgets|section 14.3]]). Because severe regressions and edge-case agent failures are inherently rare, uniform head sampling discards the vast majority of critical failure traces. At a 10 percent sampling rate, an intermittent failure mode that occurs 5 times across an evaluation run leaves no detailed trace 59 percent of the time, blinding engineers during root-cause debugging. Systems should instead employ tail sampling keyed to task outcomes and anomalous step traces. Engineers should retain a small, fixed uniform control sample to validate aggregate rates, while computing production failure rates from complete, lightweight accounting telemetry rather than sampled execution traces.

**Fallacy**: *A small canary fraction limits the damage a regression can do.*

For regressions that automated monitors track, the total blast radius depends on the sample count required to achieve statistical confidence rather than the traffic split percentage ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^sec-vol3-evaluation-releases|section 14.5]]). In the reference monitor, a decision needs the same expected number of labeled tasks at any allocation (notebook [14.3](https://mlsysbook.ai/vol3/14_agent_operations/14_agent_operations.html#nbk-13-sizing-canary-traffic-and-circuit)), so the measured regression costs about 7 excess failures at a 5 percent allocation and about 11 at full allocation. A small fraction trims only the failures among tasks admitted while labels are pending, and it stretches the time to a decision to 15.58 h. A small traffic fraction limits damage only for unmonitored hazards or qualitative failures that human operators spot manually. Automated deployment systems must therefore enforce hard circuit-breaker limits and absolute failure thresholds that operate independently of the canary traffic fraction.

**Pitfall**: *Treating a clean diagnostic run or a rollback as closing the incident.*

A successful diagnostic run demonstrates stability only within the narrow confines of its specific test fixture ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.05 Incident Postmortems#^sec-vol3-postmortem-ablation|section 14.4.3]]). Statistically, observing 20 accepted runs out of 20 diagnostic executions still leaves the true failure rate as high as 16 percent at 95 percent confidence. Furthermore, rolling back candidate code or throttling traffic merely prevents new failures; it cannot retract state mutations, external tool invocations, or corrupted database records that the agent already generated. Teams must maintain regression monitoring, enforce bounded exposure limits, and retain designated recovery owners until all asynchronous downstream effects have fully settled.

**Pitfall**: *Reading a successful span or a zero exit code as a passed task.*

Span status records how one operation ended, not whether the task met its contract ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.03 Distributed Trajectory Tracing#^sec-vol3-evaluation-tracing-fields|section 14.2.2]]). A test process can exit cleanly while its output shows failed assertions, and a client span can end in a timeout while the candidate still produces a valid patch from cached context. A dashboard that counts green spans as accepted work therefore reports activity rather than acceptance, and the gap widens exactly when verdicts arrive late, after the execution spans have closed. Traces should carry a reference to the task verdict rather than a copy of it, and every acceptance figure should come from the accounting record, where pending and unknown verdicts stay in the denominator.

**Fallacy**: *A configuration that clears every term of the release gate is safe to release.*

A conjunctive gate enforces exactly the predicates written into it and nothing else ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.07 The Release Decision#^sec-vol3-evaluation-synthesis-math|section 14.6.3]]). A regression in a property no criterion measures clears every term, and no sequential monitor stops it, because none is watching that property. The sycophancy rollback of war story [14.1](https://mlsysbook.ai/vol3/14_agent_operations/14_agent_operations.html#ws-vol3-evaluation-gpt4o-sycophancy-2025) followed offline evaluations and an A/B test that both looked good. Zero observed violations in a cohort also bound the violation rate only as tightly as the cohort’s size allows. A passed gate supports the scoped claim its predicates state, and the canary’s allocation, the hard tripwires, and a recovery owner for every outstanding effect remain the protection against what the gate does not measure.
