# V3-14.03 Distributed Trajectory Tracing

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14 Operating Agents|V3-14 Operating Agents]]

^sec-vol3-evaluation-tracing

When a trial of `candidate_v2` on the connection-pool repair fails or stalls, aggregate summary metrics record only the wall-clock total and the final verdict, blending remote inference stalls, blocked test containers, and malformed or truncated tool outputs into one undifferentiated number. A trace separates those possibilities by binding every interaction back to the specific evaluation trial, candidate revision, and runtime operation, replacing disjointed service logs with an end-to-end causal record.

**Distributed tracing** tracks units of work across process and network boundaries, an operational model established at production scale by Dapper ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-sigelman2010dapper|Sigelman et al. 2010]]). At the core of this model, a **span** represents a single contiguous unit of execution defined by a unique identifier, explicit start and end timestamps, structured attributes, and optional timed events. Hierarchical parent-child relationships capture synchronous nesting, while trace links correlate decoupled asynchronous interactions that fall outside a single call tree, following the standard OpenTelemetry model ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-opentelemetry2026traces|OpenTelemetry Authors 2026]]). Within an agentic trajectory, a large language model (LLM) generation step, a mediated tool execution in a sandbox, and subsequent result validation each form distinct spans. Omitting instrumentation at any of these boundaries leaves unmonitored voids, obscuring whether an unexpected delay originated in model inference, queueing overhead, or environment setup.

### Diagnostic Capture and Recovery History

^sec-vol3-evaluation-tracing-capture

During the connection-pool repair, every model invocation and sandbox tool call emits both a durable log record and a diagnostic trace span, often carrying the same operation identifier. Treating those two streams as interchangeable is a dangerous operational shortcut. If an execution engine relies on its diagnostic tracing pipeline to reconstruct state after a worker crash, a single load-shedding event that drops spans or truncates large tool payloads will corrupt recovery. Separating the recovery path from the observability path ensures that telemetry backpressure never compromises execution durability.

**Systems Perspective 14.1: Recovery history and diagnostic traces**

The durable trajectory log preserves the authoritative, acknowledged state transitions and input artifacts required to reconstruct execution state after a failure. A diagnostic telemetry stream that happens to share identical span identifiers cannot replace this log. Diagnostic traces prioritize performance analysis, bottleneck detection, and interactive debugging; under high load or network partitions, tracing pipelines legitimately sample traces, truncate large payloads, or drop spans. The same runtime event can emit records to both pipelines, but their guarantees differ completely. An observability agent might discard an optional span to protect telemetry egress, while the durable recovery engine must guarantee that operation identifiers, resource reservations, and partial results persist to durable storage.

↩︎ The durable trajectory log, from which recovery reconstructs execution state, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.03 The Trajectory Log#^sec-vol3-durable-execution-log-evidence|The log as recorded evidence]]**.

Systems engineers must maintain this distinction when tracking asynchronous operations such as the test run on `ws_r18` that recovery left unresolved before evaluation began. When an HTTP client monitoring that sandbox times out and terminates its diagnostic span, the underlying test does not vanish. The workload continues running inside the container until the sandbox emits an authenticated callback with the test results, which the operation table records against the original operation while the trajectory stays paused. The distributed trace reflects that split execution without rerunning the test or resuming the model prematurely. It correlates the late-arriving callback with the original dispatch attempt through a trace link, which preserves both the client-side timeout and the true server-side execution lifetime.

Captured content demands an equally strict boundary. An evaluation harness must distinguish between what an agent proposed, what intermediate middleware modified, and what the model actually received. The delivered-input manifest records the exact byte sequence presented to the model context window, which frequently diverges from raw tool output due to prompt templating, token budget truncation, or context compression. Cryptographic hashes verify payload integrity against historical records, but a hash digest cannot reconstruct payload bytes that were omitted or pruned from storage. Exact deterministic replay and forensic debugging therefore require preserving delivered-input manifests and raw observations in content-addressed storage alongside the trace metadata.

### Trace Evidence Fields

^sec-vol3-evaluation-tracing-fields

Preserving input manifests and span records helps little if each service emits unstandardized telemetry tags that omit which trial, candidate revision, transport attempt, or truncation policy produced an observation. An evaluation harness instead requires a disciplined, minimal schema that links experimental parameters directly to runtime and network observations. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.03 Distributed Trajectory Tracing#^tbl-vol3-trace-evidence-fields|Table 1]] organizes the essential fields into five functional categories. The attribute names may follow a standard such as the OpenTelemetry semantic conventions; the five groups are the minimal information required to diagnose agent behavior.

| Record group          | Information to preserve                                                                                                                    | Question it answers                                                                 |
|:----------------------|:-------------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------|
| Evaluation identity   | Task identity, trial identity, fixture and criterion versions, system configuration, candidate artifact revision                           | Which experiment and candidate does this observation concern?                       |
| Observed work         | Trace and span identities, operation kind, producer, start/end boundary, clock domain, parent or dependency links                          | Which work was observed, where, and in relation to what other work?                 |
| Admission and attempt | Model invocation or logical operation identity, transport attempt, applicable decision and policy references                               | Was this proposal withheld or admitted, and which attempt produced the evidence?    |
| Outcome and usage     | Response status and source, evidence scope, observed token/tool usage, unresolved liability, task-verdict reference                        | What is known about the operation, its costs, and the separate acceptance decision? |
| Capture limits        | Delivered-input and observation references, omitted ranges or bytes, instrumentation version, known drops, retention/access classification | What can an investigator inspect, and what does this record leave unavailable?      |

Table 1: **Minimal trace evidence groups**: Keep identities, observed facts, runtime decisions, and capture limits distinguishable. A completed span is not a completed task.

^tbl-vol3-trace-evidence-fields

This schema carries the task, trial, configuration, and artifact distinctions of the acceptance record into each observed interaction, while constraining provider provenance to what the remote interface exposes. In evaluation tracing, span status must remain decoupled from the final task verdict. An operating system process running a test suite may exit with code 0, prompting the tracing layer to mark the span successful, even though the test output reveals that the candidate failed critical assertions. Conversely, a client span might terminate with a timeout error while fetching auxiliary documentation, yet the candidate agent may still synthesize a valid patch from cached context. The authoritative task acceptance decision relies on independent verification suites and often arrives long after the agent’s execution spans have closed.

Propagating context across architectural boundaries such as an API gateway, an asynchronous queue, or an isolated worker sandbox demands standardized metadata carriers. The W3C Trace Context specification ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.12 Source References#^ref-w3c2021tracecontext|W3C Distributed Tracing Working Group 2021]]) provides standard HTTP and messaging headers to propagate correlation identifiers across distributed components. Trace identifiers, however, establish correlation, not authorization. A worker sandbox receiving a trace identifier cannot treat it as an admission token, nor can an agent bypass security policies by injecting arbitrary parent headers. Admission control, credential validation, and payload sanitization remain the exclusive responsibility of the runtime host. Furthermore, trace headers must never carry sensitive prompt tokens, credentials, or proprietary task data across untrusted network boundaries. When black-box tools or legacy binaries cannot emit internal spans, the orchestrator must record host-observed boundaries, explicitly tagging the span as an external dispatch-to-response measurement rather than an internal execution trace.

### Span Overlap and Latency Attribution

^sec-vol3-evaluation-tracing-latency

Summing span durations to obtain total agent execution time is a common error in telemetry analysis. Because a parent span encloses the lifetimes of its children, adding parent and child durations double-counts work. Furthermore, when an agent orchestrator fires multiple tool calls concurrently, for example a static analysis linter alongside a targeted test suite, their child spans overlap on the timeline. Execution order stems strictly from completion dependencies, never from parent-child hierarchy alone. Comparing durations measured on a single monotonic clock is straightforward, but correlating timestamps across distributed worker hosts requires an explicit alignment model.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.13 Footnotes#^fn1|¹]] Without synchronized time sources or clock-offset modeling, apparent span overlap between distinct machines can reflect nothing more than physical clock skew. Instrumentation boundaries introduce similar attribution challenges. Client-observed model latency encompasses TCP connection handshakes, TLS negotiation, queueing delay at the inference gateway, and network transfer time, so time to first token is never an isolated measurement of model prefill compute.

To quantify where latency optimizations yield true wall-clock savings, systems engineers measure the critical path through the trajectory’s dependency graph, the longest chain of dependent operations recorded in the trace.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.13 Footnotes#^fn2|²]] Sequential operations add their durations directly, whereas concurrent branches that join at a common synchronization barrier contribute only the duration of the slowest branch. Shortening a branch off the critical path leaves elapsed time unchanged, and shortening one on it helps only until the next-longest branch takes its place (notebook [14.1](https://mlsysbook.ai/vol3/14_agent_operations/14_agent_operations.html#nbk-13-critical-path-latency-and-bottleneck)).

↪ An acceleration is priced by the time it removes from this critical path, a trade-off developed in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^sec-vol3-agent-economics-criticalpath|Critical-Path Latency]]**.

The hypothetical intervals used in notebook [14.1](https://mlsysbook.ai/vol3/14_agent_operations/14_agent_operations.html#nbk-13-critical-path-latency-and-bottleneck) share a single host clock. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.03 Distributed Trajectory Tracing#^fig-vol3-overlapping-trace-intervals|Figure 1]] places them on a common axis so that the parallel checks, their join, and the unaccounted interval remain visible together.

**Napkin Math 14.1: Observed time and the critical path**

**Problem**: How much elapsed time do the recorded spans explain, and how much would shortening one check reduce the segment if the other durations and dependencies stayed unchanged?

**Assumptions**: [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.03 Distributed Trajectory Tracing#^tbl-vol3-trace-hierarchy|Table 2]] gives observations from a separate hypothetical timing trial that inspects `ws_r19`. The model first proposes checks, the runtime admits two independent read-only checks, and synthesis waits for both. All intervals use one host clock, no hidden dependency delays either check’s start, and admission takes no separate time. The enclosing segment runs from retrieval dispatch through the final response.

| Observed span                      | Interval after segment start (s) | Required predecessor                         |
|:-----------------------------------|:---------------------------------|:---------------------------------------------|
| Retrieve supporting context        | \[0, 0.2\]                       | Segment start                                |
| Model call proposing checks        | \[0.2, 3.2\]                     | Retrieval response                           |
| Targeted tests                     | \[3.2, 9.2\]                     | Validated and admitted check proposal        |
| Static lint check                  | \[3.2, 5.2\]                     | Same proposal; independent of targeted tests |
| Model call synthesizing the report | \[9.7, 11.7\]                    | Both check responses                         |

Table 2: **Hypothetical observed span intervals**: The two checks overlap. The enclosing segment measures 11.7 s; its duration is not additional work to sum with these children.

^tbl-vol3-trace-hierarchy

**Math**: Adding all leaf durations yields 13.2 s, an overestimate that double-counts concurrent execution during the validation phase. Following the path through retrieval, planning, the longer check (targeted tests), and synthesis, which counts the overlapping checks once, explains 11.2 s. The remaining 0.5 s occurs between the completion of the slowest check and the dispatch of the final synthesis call. Because the trace lacks instrumentation for intermediate runtime bookkeeping, prompt serialization, or context collation, this duration remains unattributed. An unmeasured interval highlights a boundary where instrumentation must be refined rather than evidence of worker idle time.

**Intervention**: Suppose an optimization accelerates the targeted test suite from 6.0 s down to 1 s while all other components remain unchanged. Because the static lint check requires 2.0 s, lint replaces the test suite as the bottleneck on the parallel branch. Recomputing the critical path yields 7.7 s for the total segment, achieving an overall elapsed reduction of 4 s.

**Systems insight**: A performance optimization on a parallel execution branch yields wall-clock returns only up to the duration gap to the next-longest concurrent path. Accelerating the test suite by 5 s yields only 4 s of end-to-end savings because static linting immediately becomes the new critical-path limiter. Systems architects must recompute the critical path across the entire dependency graph before estimating the value of an optimization. Furthermore, theoretical speedups must always be verified empirically in controlled trials; real-world optimizations can shift resource contention, alter cache locality, change garbage collection pressure, or elicit different token generation lengths from the model.

**Checkpoint 14.1: Interpret the trace's evidence**

**Identity**: Why does sharing a trace ID neither authorize a tool call nor make a result applicable to a different candidate revision?

**Outcome**: A client span ends at timeout, and a later grader remains pending. Which operation and task conclusions are still unavailable?

**Overlap**: Why do parent-child links and concurrent checks prevent summing every span duration into task latency?

**Missing time**: What additional capture would be needed to explain the notebook’s gap, and why does its location not identify a unique cause?

**Changed path**: Using the notebook’s intervals, how much would the segment shrink if the lint check, rather than the tests, were cut to 1 s? What does the resulting duration imply about where to spend optimization effort?

Distributed trajectory tracing provides the causal fabric needed to diagnose why an agent succeeded, failed, or stalled. However, capturing detailed telemetry incurs concrete engineering costs in CPU overhead, network bandwidth, and persistent storage. In high-throughput evaluation harnesses, preserving every token, tool payload, and internal span across thousands of benchmark trials is rarely feasible. Defining what to measure is only the first half of the observability problem; the second half is establishing capture and retention policies that preserve critical failure evidence without overwhelming the telemetry infrastructure.
