# V3-13.02 The Evaluation Problem

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13 Agent Evaluation|V3-13 Agent Evaluation]]

^sec-vol3-evaluation-problem

For the repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**), the connection-pool repair has come through its turbulent hour. The replacement worker reconstructed candidate workspace `ws_r18`, kept the interrupted test operation unresolved rather than guessing its outcome, and accounted for the temporary integration-test environment. Suppose a fresh targeted check then passes on `ws_r18` and the environment is released, satisfying the cleanup postcondition. Recovery has done its job, but it leaves open the question the previous chapter ended on, whether the runtime completed the task and whether its recovery policy improved outcomes at an acceptable cost.

↩︎ The recovery of the connection-pool repair, which reconstructs `ws_r18` and keeps its test operation unresolved, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.10 Fault-Tolerant System Synthesis#^sec-vol3-synthesis-architecture|Mechanism composition]]**.

![[90 Assets/Volume III/13 Evaluation/Hsa Locator Hsa 18ba12f601.svg]]

*H·S·A locator with all three axes, Horizon, State, and Authority, highlighted.*

*Evaluation examines the state a result rests on, the resources spent across its horizon, and the authority it exercised.*

The runtime mechanisms developed so far govern execution integrity rather than task success. An authority check confirms that each action was permitted by policy, the durable event log records what operations took place, and the recovery protocol ensures that partial side effects were undone or safely handed off. None of these components evaluates whether the resulting code patch actually fixes the bug. Relying on the agent’s own assessment is equally insufficient, because self-reporting constitutes the weakest tier of closure evidence (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-invariant-closure|The invariant closure principle]]**). When an agent executes tests inside its own mutable workspace, those tests are fully within reach of its edits. A faulty patch can pass because the agent commented out an assertion, altered mock data, or deleted a failing test. Even when an agent leaves tests untouched, a single successful run represents only one sample drawn from a stochastic distribution. The same agent may resolve an incident on one attempt and loop without progress on the next under the identical starting state.

Engineering decisions are also comparative. A new configuration, `candidate_v2`, with an updated system prompt, refined tool schemas, a revised recovery policy, or a different base model, is ready for deployment. The engineering team must decide whether it reliably outperforms the incumbent `baseline_v1` across the full distribution of repair tasks the system will encounter. The base model is only one of those levers, and published results show the others moving acceptance just as far. A terminal-task benchmark reports the same models run inside many independently built agent scaffolds, the prompts, tool definitions, and control loop that surround the model ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-merrill2026terminal|Merrill et al. 2026]]). [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.02 The Evaluation Problem#^fig-vol3-scaffold-spread|Figure 1]] plots every model evaluated in at least five of them.

^fig-vol3-scaffold-spread

The widest row in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.02 The Evaluation Problem#^fig-vol3-scaffold-spread|figure 1]] is one model scored between 58 percent and 80 percent across 11 scaffolds. The median spread across the 16 models is 14 points, against a median reported standard error of about 3 points. The differences are therefore real, not sampling noise, and they come from exactly the components `candidate_v2` changes. An evaluation that attributes a score to the base model alone credits the wrong part of the system, which is why the configuration under test is declared in full before any trial runs.

Transforming noisy, individual agent trials into a defensible release decision requires an end-to-end evaluation pipeline. That pipeline begins with an acceptance contract, which specifies precisely what evidence credits a task, which invariants must hold, and how missing or malformed artifacts are penalized. To make trials interpretable and secure, the evaluation system isolates task fixtures behind a protected grading boundary that sits beyond the agent’s reach. Behind this boundary, the grading harness partitions criteria between deterministic mechanical checks (static analysis, invariant assertions, hidden unit tests) and calibrated judgments for open-ended properties.

Because agent behavior is stochastic, moving from single runs to configuration comparison demands statistical rigor. Evaluating `candidate_v2` against `baseline_v1` requires paired trials on the same sampled tasks and decision metrics that reflect operational reality, including acceptance, consistency over repeated runs, and the cost per accepted task introduced in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^sec-vol3-intro-horizon-arithmetic|Reliability and Cost over a Horizon]]**. Together, these mechanisms turn individual trials into an offline judgment about `candidate_v2`: whether it accepts tasks at least as reliably as `baseline_v1`, at what cost, and with what uncertainty. Explaining why an individual trial failed and exposing the candidate to live work require operational traces, controlled diagnosis, and staged release (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14 Operating Agents#^sec-vol3-operations|Operating Agents]]**), but every offline or online claim starts with the acceptance contract for a single trial.
