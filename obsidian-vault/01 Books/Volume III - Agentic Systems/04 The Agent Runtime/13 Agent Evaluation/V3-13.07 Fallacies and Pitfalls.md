# V3-13.07 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13 Agent Evaluation|V3-13 Agent Evaluation]]

^sec-vol3-evaluation-fallacies

Even an apparently thorough evaluation report can answer the wrong engineering question. The failure modes below break the link between the evidence an offline evaluation collects and the claim it is used to support, and each exacts a measurable cost in reliability, sample efficiency, or grading accuracy.

**Fallacy**: *An agent that succeeds on 90 percent of runs is a reliable agent.*

Single-run success rates evaluate an agent executing an isolated task once. Real agentic workloads, however, recur, and the probability of passing every recurrence falls geometrically with their number ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-pass-k|section 13.5.4]]). When an agent achieves a 90 percent single-run acceptance rate, a task that recurs 8 times succeeds on every recurrence only 43 percent of the time. Sustaining 90 percent end-to-end consistency across all 8 invocations demands an individual single-run acceptance rate of 98.7 percent. Evaluation harnesses should report pass$^{k}$ when the claim concerns repeated executions of the same task without human intervention, and reserve selected acceptance metrics for workflows where an automated checker can safely discard and retry intermediate failures.

**Pitfall**: *Comparing two systems by whether their separate confidence intervals overlap.*

Checking whether two marginal confidence intervals overlap is an overly conservative and statistically flawed criterion for comparing candidate releases. Separate Wilson score intervals quantify candidate and baseline success rates in isolation, but deployment decisions hinge on the distribution of their paired differences across identical task inputs ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-paired|section 13.5.3]]). Positive within-task covariance reduces the variance of the difference. In the benchmark comparison, exploiting that covariance retains only about 40 percent of the variance present in two independent arms. Evaluating the systems as unpaired cohorts forces teams to run roughly 2.5× as many tasks to achieve identical statistical power. Teams should preserve task-level pairing throughout the evaluation harness, specify the required noninferiority margin before running the benchmark, and decide releases based on the lower bound of the paired confidence interval.

**Fallacy**: *A grader that is isolated from the agent and agrees with a second judge is a correct grader.*

Isolating a grader from the agent and limiting submitted-code execution protect measurement integrity within those enforced boundaries, while inter-rater agreement confirms that two evaluators behave consistently. However, consistent agreement does not guarantee ground-truth correctness ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.05 Grading Trajectories#^sec-vol3-evaluation-grading|section 13.4]]). Two automated judges that each approve 90 percent of submissions without analyzing the execution trace will agree on 82 percent of evaluations purely by chance, yielding a Cohen’s ${\kappa}$ of 0. High rater consensus often conceals shared systematic biases or overly lenient acceptance thresholds. Evaluation pipelines must calibrate automated judges against a curated test suite of known, independently verified agent failures and explicitly track the grader’s false-acceptance rate.

**Pitfall**: *Tuning a configuration against the held-out suite that will judge it.*

Every prompt, tool definition, or architecture change chosen because it fixed a held-out failure moves information from the suite into the configuration ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-leakage|section 13.3.5]]). After enough such rounds the held-out score measures fit to that suite rather than performance on the task population it was sampled from, and no sandbox reset or similarity filter detects the drift, because nothing leaked through the environment ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-dwork2015reusable|Dwork et al. 2015]]). A paired interval computed on that suite then understates the uncertainty of the claim it supports, since its tasks were no longer chosen independently of the configuration. Teams should develop against a separate development suite, retire a held-out suite into development use once it has steered decisions, and reserve a fresh sample for the comparison that decides between configurations.

**Fallacy**: *The configuration with the higher accuracy is the better configuration.*

Accuracy alone ranks a policy that retries until something passes above one that answers once, even when the first spends far more per accepted task, which is why leaderboards that rank accuracy alone reward needlessly costly agent designs ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-kapoor2024agents|Kapoor et al. 2024]]). Two policies can even reach the same acceptance probability at different costs. At the same candidate cap, the full batch of notebook [13.3](https://mlsysbook.ai/vol3/13_evaluation/13_evaluation.html#nbk-13-metrics-and-selection) pays a 53 percent premium per accepted task over sequential stopping ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-matched-budgets|section 13.5.5]]). Comparisons should fix the task distribution, criteria, and resource envelope before any trial runs, charge every failed attempt to the accepted tasks, and report budgeted acceptance and cost per accepted task alongside accuracy.
