# V3-13.03 The Task Acceptance Contract

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13 Agent Evaluation|V3-13 Agent Evaluation]]

^sec-vol3-evaluation-contract

The recovered workspace `ws_r18` from the chapter opening belonged to an interrupted run, so crediting `candidate_v2` from a test result on `ws_r18`, or scoring a model checkpoint without pinning the prompt templates, tool schemas, and starting workspace around it, would rest a release claim on stale evidence or an undeclared scaffold change. To prevent both ambiguities on the connection-pool repair task (`pool_repair_01`), a fresh evaluation trial begins from an immutable initial environment snapshot (`pool_fixture_v1`), grades the run against an explicit criteria specification (`repair_accept_v1`), and produces a new candidate artifact, `ws_r19`. The system under test, `candidate_v2`, names the complete operational configuration (base model, prompt templates, tool definitions, and runtime harness) rather than an isolated source-code revision or model checkpoint, and every verification check in the remainder of this chapter must evaluate the exact bytes of `ws_r19` rather than borrowing results from `ws_r18`.

A **trial** is a single end-to-end execution conducted under a declared task, fixture, system configuration, and evaluation protocol. A second execution constitutes a distinct trial, even when all inputs, initial states, and configurations remain identical. Rerunning this single repair ten times yields ten trials of one task rather than ten distinct tasks, a distinction whose statistical cost [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-resampling|section 13.5.1]] quantifies. Before aggregating results across runs, however, the evaluation harness must apply an unambiguous acceptance rule to determine whether any individual trial succeeded.

### Evidence Dimensions

^sec-vol3-evaluation-contract-dimensions

When an evaluation harness collapses every check into a single pass/fail bit, a recoverable schema rejection early in the run looks identical to a broken patch, while a passing unit test can hide a prohibited credential read or an unclosed cloud environment. An evaluation contract avoids both errors by translating the high-level task specification (its expected outcomes, permitted operations, and resource constraints) into separate, checkable dimensions. It is the five-part task contract of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-five-part-contract|The five-part task contract]]** made checkable, with the goal and completion criteria turned into measured properties and the permitted actions turned into compliance checks. Specifically, the contract defines what properties are measured, which artifact versions are examined, which instruments perform the measurement, where the observation boundaries lie, and how the harness handles missing or ambiguous evidence. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^tbl-vol3-eval-contract-hierarchy|Table 1]] organizes verification across four parallel dimensions of evidence.

| Dimension             | Evidence to inspect                                                                                                                    | Consequence for the repair                                                                                     |
|:----------------------|:---------------------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------|
| Proposal validity     | Completed proposal, parsing and schema results, represented tool and arguments                                                         | An invalid configuration rejected before dispatch can be repaired; the rejection alone need not fail the trial |
| Execution behavior    | Admitted operations and attempts, endpoint outcomes, ordering, observed partial effects, and recovery history                          | An accepted request is not necessarily a finished test; a timeout can leave an operation unresolved            |
| Task outcome          | Exact candidate artifact, required defect and regression checks, final answer, and any declared qualitative rubric                     | A targeted pass supports only its coverage; a readable report cannot replace missing required checks           |
| Constraint compliance | Authority decisions and observed effects, protected-artifact checks, consumption and liability, elapsed intervals, and residual owners | Good final code does not erase a prohibited effect or satisfy an unmet cleanup or budget condition             |

Table 1: **Dimensions of Task Evaluation**: Each dimension contributes scoped evidence. The task’s declared criteria determine which findings reject a trial, which remain pending, and which serve only as diagnostics.

^tbl-vol3-eval-contract-hierarchy

These four dimensions organize where evidence comes from, and they map directly onto the criteria that define an accepted task below. Task outcome supplies the outcome criteria. Proposal validity and execution behavior supply the process criteria. Constraint compliance supplies the resource and residual-duty criteria, together with the authority side of process. That division also tracks the three operational exposures the agent carries. Checks of the resulting artifact and environment examine the state a result rests on, resource criteria measure what the horizon consumed, and compliance checks audit the authority the trial exercised.

Separating these dimensions prevents intermediate runtime recoverable errors from contaminating the assessment of the final artifact. For instance, if an agent generates a tool invocation with an invalid argument type, a local schema validator can reject the call. If the agent inspects the rejection, corrects the payload, and dispatches a valid request that successfully repairs the bug, an evaluation policy that permits self-correction will accept the trial. Conversely, if a security policy strictly prohibits even the attempt to access a sensitive credential store, that single malformed or unauthorized proposal constitutes an immediate, terminal violation.

Because of these differing rules, the evaluation record must distinguish whether every event was a raw proposal, an admitted request, or an observed state mutation. Maintaining parallel evidence streams also preserves diagnostic value when a trial fails. If an agent overwrites a protected configuration file, the trial is rejected; nevertheless, retaining the test execution logs, elapsed wall-clock time, and cleanup traces explains why the system failed, aiding post-mortem analysis without altering the failure verdict.

**Definition 13.1: Accepted task**

***Accepted task*** is a task completion credited to a particular trial because the available evidence satisfies its declared outcome, process, resource, and residual-duty criteria at the required evidence level.

1.  **Significance**: Acceptance defines the denominator for cost efficiency (${C_{\text{eff}}}$ in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**). The compute, token, and infrastructure costs of all rejected or unresolved runs are charged against the accepted trials. Artificially weakening the acceptance contract creates an illusion of efficiency, lowering nominal cost per accepted task without making the underlying system cheaper.
2.  **Distinction**: Passing a single test harness or verifier is substantially narrower than achieving task acceptance. A trial might pass a targeted regression test yet fail due to resource exhaustion, unauthorized side effects, or leaked background processes. Moreover, task identity refers to the underlying problem specification, whereas trial identity refers to an individual execution attempting that task.
3.  **Common pitfall**: Crediting a trial based solely on an agent’s self-generated claim of completion, a successful transport status code, or a passing test run executed against a different candidate workspace revision.

### Evaluation Instruments and Coverage

^sec-vol3-evaluation-contract-instruments

Verifying whether the trial that produced `ws_r19` satisfies all four dimensions of its acceptance contract requires inspecting live tool proposals during execution, testing the resulting workspace afterward, and reviewing the accompanying repair report, a span no single checker can cover. Three instruments therefore supply the evidence for these criteria, each bounded by specific operational limits. Runtime guards and external programmatic checks represent the two halves of invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]). Runtime guards enforce bounds at the operational boundaries they mediate, such as blocking an unauthorized dispatch or intercepting a disallowed network connection. External checks assess specified artifact properties independently after execution, verifying for example whether the submitted candidate passes a defect reproducer and the required regression suite. Finally, qualitative judgments, whether supplied by human experts or automated evaluator models, assess compliance with an explicit rubric, such as whether a generated technical report accurately explains its supporting evidence. Applying model-based rubrics requires the calibration developed in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.05 Grading Trajectories#^sec-vol3-evaluation-grading|section 13.4]].

All three instruments obey the **coverage rule**: an evaluation check establishes only those properties that its scope, input vectors, and underlying assumptions directly support. Isolating an automated grader from agent tampering protects the integrity of its measurements, but it cannot expand its coverage. A test suite can pass completely yet still miss a critical defect if the test cases fail to exercise that execution path.

↩︎ The principle that each verification check answers a narrow question rather than certifying task satisfaction is established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^sec-vol3-foundation-model-continuations|Checking Candidate Outputs]]**.

**Definition 13.2: State-delta verification**

***State-delta verification*** checks specified properties of an observed change between declared initial and resulting environment states, using measurements tied to the relevant versions and task criteria.

1.  **Significance**: It distinguishes a claimed repair from an observed artifact or service mutation that meets the selected checks, ensuring the agent produced genuine state changes.
2.  **Distinction**: Verification relies on scoped, structured comparisons of designated state components rather than naive differential subtraction of entire filesystems or databases. Furthermore, verifying that a state delta satisfies designated checks does not prove total correctness across unmonitored subsystems.
3.  **Common pitfall**: Treating any non-empty patch or successful tool response as evidence that the intended change occurred without unintended side effects.

The evaluation criterion dictates both the required observation and the appropriate instrument. A read-only analysis task succeeds when the agent produces an empirically supported answer while leaving the persistent environment untouched. Conversely, a software repair task alters persistent files, requiring the harness to inspect execution history alongside final disk states. If an agent executes an unauthorized file deletion and subsequently recreates the file before finishing, the action still violates a policy forbidding unauthorized deletion.

Resource accounting likewise demands precisely defined observation boundaries. The evaluation harness must meter the active execution phase and the finalization phase against distinct budget allowances. Token expenditures, financial costs, and occupied compute resources must remain separate accounting streams rather than being collapsed into a single scalar. Moreover, settled operational charges must be distinguished from outstanding reserved liabilities; halting an evaluation trial at a wall-clock cutoff does not automatically cancel background container instances or release cloud reservations.

↩︎ Bounded-liability admission, which keeps outstanding reservations separate from settled charges, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-agent-harness-reservation-settlement|Reservation and settlement]]**.

### The Four-Verdict Rule

^sec-vol3-evaluation-contract-verdicts

When a trial reaches its observation cutoff while a regression suite is still running or a resource charge remains unsettled, forcing every criterion into a binary pass or fail either credits unfinished work or records an incomplete check as a substantive violation. For every declared criterion in the contract, the harness must instead retain the observed result and resolve it to one of four discrete verdicts. A `pass` means the evidence definitively meets the requirement. A `fail` means the evidence establishes a violation. A `pending` verdict applies while a required assessment remains actively underway within the observation window. An `unknown` verdict applies when necessary evidence is missing or unavailable at the cutoff, and it is accompanied by a structured record explaining why. These four categories function strictly as evaluation verdicts rather than trajectory lifecycle states.

The aggregation logic short-circuits. An established failure of any mandatory criterion immediately resolves the overall trial verdict to `fail`, even if other criteria remain pending or unobserved. A trial is accepted if and only if all mandatory criteria achieve a `pass`. If any required check remains unfulfilled and none have failed, the trial remains pending or unknown. This convention is the **four-verdict rule**. Its main corollary governs every measurement in this chapter: incomplete, timed-out, or unresolvable trials must remain in the denominator under a declared rule, because dropping them changes the underlying population being evaluated. Unless a contract declares otherwise, this chapter applies one default. An unresolved trial stays in the count ${N}$ and is not accepted, so a point estimate of the accepted fraction, the acceptance estimator of **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-task-acceptance|equation 4.8]]**, treats it as a non-acceptance. The report lists unresolved trials separately from established failures and adds the two bounds obtained by resolving every one of them as accepted and every one as failed, which shows how far the open verdicts could still move the result.

**Example 13.1: A targeted pass is not a completed evaluation**

**Problem**: The trial submits candidate workspace `ws_r19` under `repair_accept_v1`. The contract requires six conditions: the defect reproducer and designated regression checks must pass, the report must state its supported scope, permitted actions and resource allowances must hold, and temporary resources must be released or transferred under its residual-duty policy. The first three are outcome criteria, and the last three are the process, resource, and residual-duty criteria of the accepted-task definition. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^tbl-vol3-repair-acceptance-record|Table 2]] logs what the harness has observed against each condition so far. At an interim observation checkpoint, can this trial be accepted?

| Required evidence               | Observation for this trial                                                                                                                  | Verdict at this observation                                        |
|:--------------------------------|:--------------------------------------------------------------------------------------------------------------------------------------------|:-------------------------------------------------------------------|
| Candidate-specific defect check | The designated reproducer passed on `ws_r19`                                                                                                | `pass` for this check only                                         |
| Required regression coverage    | The designated suite has not yet produced a complete result                                                                                 | `pending`                                                          |
| Report scope                    | The declared review found that the report identifies the candidate, completed check, and missing coverage                                   | `pass` under that rubric and review                                |
| Permitted process               | Retained mediation and protected-artifact checks satisfy the specified process criteria; a malformed proposal was corrected before dispatch | `pass` within the stated coverage                                  |
| Resource criteria               | Admissions remained within the configured bounds, but required final usage evidence for an outstanding operation is not yet available       | Admission-bound check `pass`; final-accounting criterion `pending` |
| Residual duties                 | The designated service acknowledged ownership of the remaining operation and charge reconciliation, as this contract permits                | Handoff criterion `pass`; the external outcome remains unresolved  |

Table 2: **An Interim Repair Evaluation Record**: Hypothetical findings for one identified trial. Each result retains its criterion and scope; successful handoff does not establish the result of the transferred operation.

^tbl-vol3-repair-acceptance-record

**Result**: No row of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^tbl-vol3-repair-acceptance-record|table 2]] records a failure, yet the trial cannot be accepted at this interim checkpoint. Its overall verdict remains `pending` because required regression coverage and final accounting reconciliation have not yet concluded. If the regression suite subsequently reports a failed assertion, the overall verdict immediately transitions to `fail`, while the unresolved charge remains recorded. If the observation window closes before those results arrive, the uncompleted criteria transition to `unknown`, a gap that neither the targeted pass nor the accepted handoff can fill.

**Systems insight**: The evaluation record distinguishes task completion, runtime enforcement, grader coverage, and owned residual work. A favorable result in one operational dimension cannot substitute for missing evidence in another.

^exmp-13-repair-acceptance-record

The acceptance contract formalizes the necessary conditions for crediting an individual trial. However, the validity of comparative benchmarks across multiple systems depends equally on the stability and isolation of the underlying evaluation harness. A silently updated package dependency, an unpinned base container image, or data leakage that exposes test suites to the model can move benchmark scores by more than the difference being measured without reflecting any genuine improvement in system architecture or agent capability.
