# V3-13.06 Statistical Evaluation Rigor

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13 Agent Evaluation|V3-13 Agent Evaluation]]

^sec-vol3-evaluation-rigor

When an updated agent configuration (`candidate_v2`) passes several more sampled benchmark tasks than a production baseline (`baseline_v1`) in an evaluation sweep, engineering teams are often tempted to declare immediate progress. However, that modest margin can easily reflect random sampling noise. Conversely, a seemingly smaller overall improvement can provide decisive evidence of system progress if the evaluation protocol preserves task-level pairings and demonstrates that the candidate resolves difficult failures without regressing on previously solved tasks. Distinguishing meaningful engineering progress from statistical fluctuation requires two foundations. The first is a defined target population of tasks that the benchmark is meant to represent. The second is a decomposition of variance across both problem instances and non-deterministic execution runs. Rigorous statistical evaluation attaches uncertainty directly to the comparative delta between configurations rather than treating each system as an isolated, independent score.

### Tasks and Repeated Runs

^sec-vol3-evaluation-resampling

Running the same 20 repair tasks ten times each produces 200 trials, yet treating those 200 trials as independent tasks understates the uncertainty of the benchmark whenever task difficulty varies across the workload. The acceptance contract separated a task from a trial, and statistical analysis sharpens that distinction. A *task* specifies the evaluation problem (a concrete problem description, an environment fixture such as a container filesystem and database snapshot, and an automated verification contract), while a *run* is one trial of a configuration on that task. The words run and trial name the same execution; run is used here because the statistics count repetitions of a task. Generating a second candidate patch for a connection-pool defect is another run of that same task, not a new problem instance. Because agentic execution relies on stochastic token sampling, network I/O, and asynchronous tool interactions, outcomes fluctuate across repeated runs of identical tasks even when running at temperature zero or with fixed random seeds, for the serving-path reasons traced in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.05 Autoregressive Generation#^sec-vol3-foundation-model-repetition-replay|Repetition and replay]]**.

Let ${p}_i$ be a fixed system’s probability of acceptance on task ${i}$ under the declared execution and grading protocol. Suppose tasks are independently sampled from a specified population, and ${R}$ runs are independent conditional on each task. Let ${\hat{p}}$ be the task-averaged estimate, the mean over the ${N}$ tasks of each task’s fraction of accepted runs. With the same number of runs per task,

$$
\operatorname{Var}({\hat{p}})=\frac{{\sigma_{\text{task}}}^2}{{N}}+\frac{{\sigma_{\text{run}}}^2}{{N} {R}},\qquad {\sigma_{\text{task}}}^2=\operatorname{Var}({p}_i),\quad {\sigma_{\text{run}}}^2=\mathbb E[{p}_i(1-{p}_i)]. \tag{1}
$$

^eq-variance-decomposition

The first term in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-variance-decomposition|equation 1]] reflects population diversity in task difficulty (${\sigma_{\text{task}}}^2$); the second reflects runtime execution variance across repeated attempts on the same task (${\sigma_{\text{run}}}^2$). This decomposition provides a concrete operational rule for budgeting evaluation compute. Adding more repeated runs (${R}$) reduces only the second term. In contrast, evaluating additional independently sampled tasks (${N}$) reduces both terms simultaneously. If new tasks cost nothing beyond their runs, a graded run spent on a new task therefore never buys less precision than one spent on a repeat, and the best design runs each task once. Repeats earn a place only because a new task usually costs more than a run, since it needs its own fixture, criteria, and validation. The variance ratio ${\sigma_{\text{run}}}^2/{\sigma_{\text{task}}}^2$ sets the scale of that trade. Once the number of repeats ${R}$ exceeds it, the run term is the smaller of the two, so further repeats shave only that term while the task term, which only fresh tasks reduce, dominates the uncertainty. How far past the ratio repeats remain worthwhile depends on how much a fresh task costs, the trade worked through in the first problem of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.10 Exercises#^sec-vol3-13-evaluation-exercises-5fd17744|section 13.9]].

Evaluating a fixed benchmark suite targets a narrower objective: estimating mean performance on that specific static collection of problems. Running repeated trials on that fixed suite pins down its sample mean with higher precision, but it does not make the suite any more representative of future, unseen workloads. Furthermore, evaluation suites frequently violate the assumption of independent tasks. Multiple test cases derived from the same source code repository, shared external service degradation during evaluation sweeps, or cross-trial state leakage inside shared sandbox environments all introduce correlated outcomes. Sound statistical analysis must group these evaluations into clusters rather than treating every individual trial as an independent random sample.

### Confidence Intervals for Acceptance

^sec-vol3-evaluation-wilson

When a safety or reliability check records zero violations across 50 sampled tasks, the textbook Wald confidence interval collapses to zero width and falsely claims that future violations are impossible. In general, when an evaluation protocol executes a single run across each of ${N}$ independently sampled tasks and observes ${X}$ acceptances, the empirical proportion ${\hat{p}}={X}/{N}$ (the ${R}=1$ case of the task-averaged estimate) estimates the true population acceptance probability. A confidence interval quantifies the uncertainty from that finite sample size. It does not account for grader error, unhandled task timeouts, test-set contamination, or shifts in the underlying task distribution, which demand independent operational controls.

The standard Wald interval, ${\hat{p}}\pm {z_{\alpha/2}}\sqrt{{\hat{p}}(1-{\hat{p}})/{N}}$, breaks down in the extreme-probability regimes characteristic of safety and reliability gating. Empirical variance vanishes when every observed run succeeds or fails. Near the boundaries, the formula can also produce impossible interval endpoints below zero or above one.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.12 Footnotes#^fn2|²]] The **Wilson score interval** ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-wilson1927probable|Wilson 1927]]) avoids both failures by using the hypothesized rate, not the observed one, in the variance:[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.12 Footnotes#^fn3|³]]

$$
{\tilde{p}}=\frac{{X}+{z_{\alpha/2}}^2/2}{{N}+{z_{\alpha/2}}^2},\qquad [{L},{U}]={\tilde{p}}\pm\frac{{z_{\alpha/2}}}{{N}+{z_{\alpha/2}}^2}\sqrt{\frac{{X}({N}-{X})}{{N}}+\frac{{z_{\alpha/2}}^2}{4}}. \tag{2}
$$

^eq-wilson-interval

Here ${z_{\alpha/2}}$ is the standard normal quantile for the selected two-sided confidence level. For zero acceptances in 50 independent tasks, [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-wilson-interval|equation 2]] gives a lower limit of zero and an upper limit of ${z_{\alpha/2}}^2/(50+{z_{\alpha/2}}^2)$, which panel B of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^fig-vol3-sample-size-confidence-intervals|figure 4]] marks. Read with the outcomes reversed, the same arithmetic prices a clean record: zero observed violations in 50 tasks remains consistent with a violation rate up to that limit.

These binary examples assume complete verdicts. If an evaluation sweep leaves trials unresolved due to timeouts, infrastructure failures, or grader crashes, the evaluation team must prespecify a handling protocol before examining the data, such as the default of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^sec-vol3-evaluation-contract-verdicts|section 13.2.3]] that counts them as not accepted and reports both-outcome bounds. Simply discarding uncompleted tasks introduces severe survivorship bias, skewing results toward trivial tasks that execute rapidly and pass without contention.

Published leaderboards show how quickly intervals of this kind swallow a ranking. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^fig-vol3-leaderboard-rank-ties|Figure 3]] plots one evaluator’s runs of 33 models on a repository-repair benchmark ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-jimenez2024swebench|Jimenez et al. 2024]]), all under the same scaffold, with the standard error reported for each run ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-epochai2026benchmarks|Epoch AI 2026]]).

### Paired Outcome Comparison

^sec-vol3-evaluation-paired

When `candidate_v2` and `baseline_v1` are evaluated as two independent cohorts, or judged by whether their separate confidence intervals overlap, between-task difficulty variance swamps the comparison and can hide a genuine gain or conceal regressions on previously solved tasks. Comparing system versions under causal and statistical release evidence (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-release-evidence|12]]) instead requires running the baseline and candidate on separate, comparably initialized executions of each sampled task, with matched criteria and allowances, and keeping each task’s pair of outcomes together. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^tbl-vol3-mcnemar-contingency|Table 4]] organizes a hypothetical complete comparison drawn from a prespecified cohort that never included the pending `ws_r19` trial.

| Baseline outcome | Candidate accepted | Candidate rejected |
|:-----------------|:-------------------|:-------------------|
| Accepted         | ${n}_{11}=70$      | ${b}=12$           |
| Rejected         | ${c}=18$           | ${n}_{00}=50$      |

Table 4: **Paired task outcomes**: One baseline run and one candidate run on each of 150 independently sampled tasks. Counts are illustrative, with no missing verdicts; execution order and fixtures follow the prespecified comparison protocol.

^tbl-vol3-mcnemar-contingency

The baseline’s accepted count is ${n}_{11}+{b}$ and the candidate’s is ${n}_{11}+{c}$. The observed difference is

$$
{\hat{\Delta}}={\hat{p}_{\text{cand}}}-{\hat{p}_{\text{base}}}=\frac{{c}-{b}}{{N}}.
$$

The discordant pairs determine the net gain, while the concordant pairs still count in ${N}$ and in the uncertainty. Marginal counts alone cannot reveal whether the candidate gained tasks without losing any or traded many wins for many losses.

**McNemar’s test**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.12 Footnotes#^fn4|⁴]] ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-mcnemar1947note|McNemar 1947]]) asks whether the paired marginal probabilities are equal. Under that null, and conditional on ${n_{\text{disc}}}={b}+{c}>0$ discordant pairs, candidate wins are $\operatorname{Binomial}({n_{\text{disc}}},1/2)$, and the exact two-sided test sums the symmetric tails:

$$
{p_{\text{val}}}=\min\!\left(1,\;2\sum_{j=0}^{\min({b},{c})}\binom{{n_{\text{disc}}}}{{j}}2^{-{n_{\text{disc}}}}\right).
$$

A release decision usually asks a magnitude question instead of an equality question. **Noninferiority** is the claim that the candidate loses no more than a declared tolerance ${\delta_{\text{tol}}}$, and it needs an interval $[{L_{\Delta}},{U_{\Delta}}]$ for ${\Delta}$ itself. The worksheet uses Newcombe’s paired-score method 10 ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-newcombe1998improved|Newcombe 1998]]), which combines the candidate and baseline Wilson intervals of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-wilson-interval|equation 2]] through a continuity-corrected estimate of their within-pair correlation. Positive within-pair dependence can therefore narrow the interval even when both marginal counts stay fixed. The result is nominal and approximate, valid for one prespecified look under independent paired sampling. **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-newcombe|Interval for a paired difference of proportions]]** states the interval in full, and the paired bootstrap ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-efron1979bootstrap|Efron 1979]]) serves statistics that lack such an analytic interval.

**Napkin Math 13.1: A paired gain and an inconclusive gate**

**Problem**: For the 150 task pairs in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^tbl-vol3-mcnemar-contingency|table 4]], does the candidate establish noninferiority under a prespecified tolerance of 2 percentage points, that is, ${L_{\Delta}}>-{\delta_{\text{tol}}}$ for the lower endpoint of a nominal 95 percent paired-score interval? If not, how many pairs would the gate need?

**Math**: The observed gain is ${\hat{\Delta}}=({c}-{b})/{N}=$ (18 $-$ 12)/150, or 4 points. Method 10 gives the interval from -3.21 to 11.12 points, so the lower half-width ${\hat{\Delta}}-{L_{\Delta}}$ is 7.21 points. Clearing the gate needs that half-width below ${\hat{\Delta}}+{\delta_{\text{tol}}}$, 6 points. Half-widths shrink as $1/\sqrt {N}$, so the required count is ${N'}\approx {N}\left[({\hat{\Delta}}-{L_{\Delta}})/({\hat{\Delta}}+{\delta_{\text{tol}}})\right]^2$.

**Result**: The lower endpoint lies below $-{\delta_{\text{tol}}}$, so the gate is not met, and the interval includes zero, so superiority is not established either. The exact two-sided McNemar value, 0.362, answers the separate equality question.

**Systems insight**: The candidate is held, and the knob that moves the decision is the planned number of pairs. A 4-point gain that holds needs about 217 pairs, a count that only centers the expected lower limit on the margin and so clears the gate with roughly even odds. A powered plan adds the power quantile to the confidence quantile while keeping the engineering tolerance fixed, using the paired variance developed in this section. A true gain of zero needs the half-width inside the 2-point tolerance itself, about 1,900 pairs. Plan that count before collecting data, because rerunning the same comparison until one look passes is a different, uncalibrated test.

These planning counts follow from standard scaling laws. For a single proportion, the confidence interval half-width scales as ${z_{\alpha/2}}\sqrt{{p_{\text{acc}}}(1-{p_{\text{acc}}})/{N}}$, reaching its maximum at ${p_{\text{acc}}}=0.5$. Because precision improves only as $1/\sqrt{{N}}$, halving the margin of error requires a fourfold increase in evaluation tasks. Detecting a difference between two configurations is considerably more demanding than estimating a single rate. For two independent arms with average acceptance probability ${\bar{p}}$, minimum detectable difference ${\delta_{\text{MDE}}}$, two-sided significance ${\alpha_{\text{sig}}}$, and power $1-{\beta_{\text{stat}}}$, a standard planning estimate of the tasks needed per arm is

$$
{N_{\text{arm}}}\approx\frac{2\,({z_{\alpha/2}}+{z_{\beta}})^2\,{\bar{p}}(1-{\bar{p}})}{{\delta_{\text{MDE}}}^2}. \tag{3}
$$

^eq-vol3-eval-planning-power

**[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-bootstrap|Statistical planning and bootstrap intervals]]** derives the fuller equal-arm form, which keeps the pooled variance under the null but uses each arm’s own variance under the alternative, and states its assumptions; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-vol3-eval-planning-power|equation 3]] replaces the alternative variance with the pooled one. Because the denominator scales with ${\delta_{\text{MDE}}}^2$, resolving a small improvement on uncorrelated arms requires thousands of tasks unless paired evaluation removes the shared task-to-task variance.

At ${p_{\text{acc}}}=0.5$ and 95 percent confidence, 100 independent tasks give a half-width of about 9.8 percentage points (the Wilson interval gives 9.6), and a half-width of 2 points needs 2,401 tasks. With a 5 percent two-sided significance target and 80 percent power at ${\bar{p}}=0.5$, [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-vol3-eval-planning-power|equation 3]] asks for about 2,450 tasks per arm to detect a 4-point difference and 9,800 per arm for a 2-point difference. The half-width curves in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^fig-vol3-sample-size-confidence-intervals|figure 4]] flatten long before they reach the 2-point half-width target, and near zero or full acceptance only the Wilson interval stays inside $[0,1]$ with a nonzero width.

![[90 Assets/Volume III/13 Evaluation/Sample Size Confidence Intervals 505c0257db.svg]]

^fig-vol3-sample-size-confidence-intervals

Pairing preserves within-task dependence, reducing the variance of the difference when candidate and baseline outcomes have positive covariance. Each task’s candidate-minus-baseline outcome takes the value $-1$, $0$, or $+1$, so with discordant fraction ${\psi}$ the paired estimate has variance $({\psi}-{\Delta}^2)/{N}$. The worked table has 20 percent discordant pairs, which puts the paired variance at about 40 percent of the variance two independent arms would have at the same acceptance rates. The same precision therefore needs well under half as many tasks. On the worked table this normal-approximation variance gives a symmetric half-width of about ±7.1 points, which can be computed by hand and sits close to the 7.21-point lower half-width of the asymmetric method-10 interval in notebook [13.1](https://mlsysbook.ai/vol3/13_evaluation/13_evaluation.html#nbk-vol3-evaluation-wilson-superiority). Estimation, detection, and noninferiority thus need different counts, and a paired plan also rests on an assumed discordance rate that the study must later report as observed.

![[90 Assets/Volume III/13 Evaluation/Vol3 Eval Margin Paired Variance 0905c28805.svg]]

*Two horizontal bars. A gray bar labeled independent arms is full length and labeled 100 percent. A purple bar labeled paired tasks is well under half as long, with its percentage printed inside and the word variance beside it.*

*Pairing the worked comparison leaves about 40 percent of the independent-arm variance.*

A powered noninferiority plan combines that paired variance with the distance from the anticipated gain to the negative tolerance. Before collecting the release sample, the evaluation team fixes the anticipated gain, discordant fraction, tolerance, and target power. Under a fixed-variance normal approximation, a single candidate-minus-baseline outcome has variance equal to the discordant fraction minus the squared anticipated gain. Multiplying this per-pair variance by the squared sum of the confidence and power quantiles and dividing by the squared sum of the anticipated gain and tolerance (which must be positive) yields the required number of task pairs. Both quantiles appear inside that squared sum because the sample must absorb two distinct margins between the true anticipated gain and the noninferiority boundary. For the two-sided 95 percent interval, the confidence quantile of 1.96 sets the half-width between the future observed difference and its lower confidence bound, while the power quantile sets how far the observed difference can fall below the true anticipated gain by chance and still keep its lower bound above the negative tolerance with the target probability. Because this approximation assumes independent pairs, complete verdicts, one planned look, and a variance held fixed at its planning value, it does not supply exact method-10 power. Rare outcomes, clustering, a changed discordance pattern, or direct calibration of the paired-score gate requires a design-specific power assessment. Furthermore, the comparison so far uses one run per configuration per task, and permitting multiple attempts changes both what success means and what it costs.

### Potential and Repeated-Run Consistency

^sec-vol3-evaluation-pass-k

Permitting multiple attempts means one thing when a repair agent can generate eight candidate patches offline and let a test suite pick a winner, and quite another when a support agent must answer the same compliance question across thousands of live customer sessions without a single wrong reply. Across those workloads, three engineering achievements remain distinct: producing a candidate pool that contains at least one correct patch, deploying an automated selector that reliably extracts that patch, and operating an agent that solves the problem consistently on every execution. **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.04 Selecting from a Candidate Pool#^sec-vol3-test-time-compute-pass-at-k|Candidate availability under pass@k]]** defined pass@${k}$ as candidate availability: the probability that a pool of ${k}$ independent runs contains at least one acceptable solution. For automated workloads that recur continuously in production without a checker between the agent and the user, availability alone is insufficient. Production deployment demands the opposite quantifier: repeated-run consistency, where all ${k}$ independent executions must pass. These two metrics anchor opposite ends of system reliability, and they diverge sharply as ${k}$ scales.

**Theorem 13.1: Availability and consistency over repeated runs**

*For a fixed task ${i}$, initial-state distribution, complete generation policy, and binary pass criterion, let runs be independent and identically distributed given the task, each passing with probability ${p}_i$.* Averaged over the declared task distribution, pass@${k}$ is the probability that at least one of ${k}$ runs passes, and **pass$^{k}$** or **repeated-run consistency** is the probability that all ${k}$ pass. From ${R}_i\ge {k}$ fully graded runs with ${s}_i$ passes, pass$^{k}$ has an unbiased subset estimator ${\widehat{r}}_{i,{k}}$ ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-yao2024taubench|Yao et al. 2024]]):

$$
\operatorname{pass@}{k}=\mathbb{E}_i\left[1-(1-{p}_i)^{k}\right], \tag{4}
$$

^eq-pass-at-k

$$
\operatorname{pass}^{{k}}=\mathbb{E}_i\left[{p}_i^{k}\right],\qquad {\widehat{r}}_{i,{k}}=\frac{\binom{{s}_i}{{k}}}{\binom{{R}_i}{{k}}}. \tag{5}
$$

^eq-pass-pow-k

- **Task pass probability** (${p}_i$): Single-run acceptance under the declared reset and grading protocol.
- **Claim size** (${k}$): Runs the claim covers, a pool for pass@${k}$ and recurrences for pass$^{k}$.
- **Graded runs** (${R}_i$, ${s}_i$): Runs generated for the estimate and the number that passed; the numerator of ${\widehat{r}}_{i,{k}}$ is zero when ${s}_i<{k}$. The subset estimator for pass@${k}$ is the one of **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.04 Selecting from a Candidate Pool#^sec-vol3-test-time-compute-pass-at-k|Candidate availability under pass@k]]**, applied per task and averaged.

Because pass@${k}$ rises with ${k}$ while pass$^{k}$ falls, the same system can look near perfect or unreliable depending on which quantifier the claim needs, as notebook [13.2](https://mlsysbook.ai/vol3/13_evaluation/13_evaluation.html#nbk-vol3-evaluation-pass-pow-k) shows numerically.

Each ${k}$-subset of the ${R}_i$ graded runs contributes one to ${\widehat{r}}_{i,{k}}$ when all its members pass, so the estimator’s expectation is ${p}_i^{k}$. It mirrors the pass@${k}$ estimator, which counts the subsets that contain at least one pass; **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-pass-at-k|Pass@k and repeated-run consistency]]** derives both by indicator averaging and gives product forms that avoid factorial overflow. Average task-level estimates with the declared task weights, never by repeat count. The pass@${k}$ metric measures candidate availability, while the deployed selector’s returned results are measured separately; pass$^{k}$ can describe complete system runs, selector included. The consistency metric entered agent benchmarking with ${\tau}$-bench, which reports it for tool-using agents in customer-service domains[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.12 Footnotes#^fn5|⁵]] ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-yao2024taubench|Yao et al. 2024]]).

**Napkin Math 13.2: Single-run success is not reliability**

**Problem**: A system accepts a recurring task on 90 percent of single runs. How often does it pass all 8 recurrences, and what single-run rate would hold 90 percent consistency?

**Math**: By [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-pass-pow-k|equation 5]] for one task, pass$^{k}={p}^{k}$. With ${p}$ equal to 0.9 and ${k}$ equal to 8, that is about 43 percent; at 80 percent it falls to about 17 percent. Availability over the same runs, $1-(1-{p})^{k}$, is effectively 100 percent. Holding 90 percent requires ${p}\ge {p_{\text{target}}}^{1/{k}}$, about 98.7 percent.

**Systems insight**: Recurrences compound exactly as turns do in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]**, so consistency is set by the single-run success probability raised to the number of recurrences. Halving the single-run failure rate to reach 95 percent lifts pass$^{k}$ only to 66 percent; holding 90 percent needs single-run failure of 1.3 percent, a 7.6× cut. Recurring work therefore buys reliability most cheaply with a check that catches a failed run before delivery, which turns a failed recurrence into a retry.

The divergence between near-certain availability and an eight-run consistency of just 43 percent defines the **verification gap**, the distance between what a pool makes available and what a single unchecked run delivers. A selector paired with a reliable automated checker closes it, converting availability into an accepted delivery at the computational cost priced in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-matched-budgets|section 13.5.5]]. The same holds for recurring work, where a check before delivery turns a failed recurrence into a retry and the claim becomes selected acceptance, as notebook [13.2](https://mlsysbook.ai/vol3/13_evaluation/13_evaluation.html#nbk-vol3-evaluation-pass-pow-k) concludes. Recurring work with no check between the run and its consumer, such as an answer a customer reads at once, gets only consistency. The gap is the practical face of the verification asymmetry (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-verification-asymmetry|3]]), because the check that closes it is only as trustworthy as its error rates.

![[90 Assets/Volume III/13 Evaluation/Vol3 Eval Margin Pass K Diverge 3355cbbebf.svg]]

*Two lines from k equals 1 to k equals 8 that start at the same point near the top. The blue pass at k line rises to 100 percent; the purple pass to the power k line falls steadily to a labeled dot about halfway down.*

*At 90 percent per run, availability nears certainty while 8-run consistency falls to 43 percent.*

A sequence of ${k}$ independently drawn *new tasks* has all-success probability $(\mathbb{E}_i[{p}_i])^{k}$. Because ${x}^{k}$ is convex for ${k}\ge 1$, Jensen’s inequality (the mean of a convex function is at least the function of the mean) places that value at or below $\mathbb{E}_i[{p}_i^{k}]$. The inequality is strict whenever task difficulty varies across the workload ($\operatorname{Var}({p}_i) > 0$) and ${k}\ge2$. Consequently, repeating one task overstates consistency across new tasks. Suppose two equally likely task types pass on 50 percent and 90 percent of runs. Repeating one randomly selected task 2 times passes every run 53 percent of the time, while 2 independently drawn tasks all pass only 49 percent of the time. The single-run average is the same, but the experiment is not. Shared outages, state carried between runs, or feedback-conditioned revisions also break these independence formulas, and [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^tbl-vol3-statistical-metrics|table 5]] names the experiment behind each quantity.

| Reported quantity   | Sampling unit and question                                                               | What it does not establish                          |
|:--------------------|:-----------------------------------------------------------------------------------------|:----------------------------------------------------|
| pass@${k}$          | One task’s pool: does at least one member pass the declared criterion?                   | That the deployed selector returns it within budget |
| Selected acceptance | One complete system trial: does the actual returned result meet the acceptance contract? | That every future run or task will pass             |
| pass$^{k}$          | One task repeated ${k}$ times: do all runs pass?                                         | Success across ${k}$ independently drawn new tasks  |
| Budgeted acceptance | One complete policy trial under stated resource limits                                   | The best score achievable by any policy             |

Table 5: **Metrics name different experiments**: The criterion, task distribution, reset and dependence assumptions, and treatment of unresolved verdicts accompany every score.

^tbl-vol3-statistical-metrics

Unresolved verdicts in a pool follow the default of the four-verdict rule, counted as not accepted and reported with the bounds from resolving them all either way. Which row of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^tbl-vol3-statistical-metrics|table 5]] a claim needs depends on how the work is used. The four recurring workloads use it differently, and [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^tbl-vol3-evaluation-evidence-by-archetype|table 6]] pairs each workload’s checker with the metric and evidence limit.

**Lighthouse 13.1: Evidence standard by archetype**

| Workload          | Checker the task admits                                              | Metric the claim needs                                                         | Binding evidence limit                                                   |
|:------------------|:---------------------------------------------------------------------|:-------------------------------------------------------------------------------|:-------------------------------------------------------------------------|
| Repair agent      | Sealed regression and defect tests on the exact submitted artifact   | Selected acceptance under budget; pass@${k}$ only with the checker in the loop | Test coverage, and grader isolation from submitted code                  |
| Research agent    | Rubric scored by a calibrated judge; citation checks against sources | Selected acceptance with the judge’s error rates reported                      | Judge false-acceptance rate on untrusted retrieved content               |
| Remediation agent | State-delta checks on an isolated replica; approval records          | pass$^{k}$ over recurring incident classes, with zero forbidden effects        | Irreversible writes that no shadow fixture can exercise                  |
| Support agent     | Policy-grounded rubric per answer                                    | pass$^{k}$ across sessions asking the same policy question                     | Consistency over many short sessions, measured only on live-like traffic |

Table 6: **Evidence standard by workload**: Each workload’s checker determines which metric its claims can support, and each carries a different limit on what its evaluation can establish.

^tbl-vol3-evaluation-evidence-by-archetype

**Systems insight**: Across the rows of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^tbl-vol3-evaluation-evidence-by-archetype|table 6]], the archetype decides the quantifier. The repair agent can buy acceptance with checked retries, so it reports selected acceptance priced through ${C_{\text{eff}}}$. The support agent cannot retry a wrong policy answer once a customer has read it, so its claim is pass$^{k}$ (notebook [13.2](https://mlsysbook.ai/vol3/13_evaluation/13_evaluation.html#nbk-vol3-evaluation-pass-pow-k)). The research agent’s number is only as good as its judge, and the remediation agent’s release rests on hard limits that statistics cannot supply.

### Matched-Budget Comparison

^sec-vol3-evaluation-matched-budgets

Leaderboards that rank configurations by pass rate alone reward a policy that generates and checks ten candidates per task over one that answers in a single pass, even when the multi-sample policy spends several times more per accepted task ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-kapoor2024agents|Kapoor et al. 2024]]). A sound comparison fixes the task distribution, criteria, and resource envelope before any trial runs. An experiment that isolates a prompt change holds the rest of the configuration fixed; one that compares complete policies lets each spend the same envelope differently among generation, checking, and repair, so equal budgets need not mean equal sample counts. Report allowances and actual use, with time and tokens separate from monetary charges.

↩︎ The controlled and system-level comparison designs are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.08 Evaluating Deliberation Policies#^sec-vol3-test-time-compute-comparison-design|Controlled and system-level comparisons]]**.

For a fixed complete policy $\pi$, let $\text{Acc}_\pi$ indicate accepted completion under the declared criteria, ${C_{\text{attempt}}}$ its total monetary charge, and ${C_{\max}}$ a monetary ceiling. Its budgeted acceptance is

$$
{q_{\pi}}({C_{\max}})=\Pr(\text{Acc}_\pi=1\ \land\ {C_{\text{attempt}}}\le {C_{\max}}).
$$

Token and elapsed-time ceilings add separate conditions in their own units. The charge covers generation, grading, failed attempts, discarded work, and required cleanup, with unknown charges counted as outstanding liabilities. Observed cost per accepted task divides the total charge for all initiated trials by their accepted count; its population counterpart is ${C_{\text{eff}}}$ from **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**, with $\mathbb{E}[{C_{\text{attempt}}}]$ as the attempt cost and $\Pr(\text{Acc}_\pi=1)$ as ${p_{\text{acc}}}$. Because failed trials are charged to accepted ones, the ratio never falls below the mean cost of the successful trials alone, and a cohort with no accepted tasks reports its spend and the zero count.

**[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.04 Selecting from a Candidate Pool#^sec-vol3-test-time-compute-pass-at-k|Candidate availability under pass@k]]** priced breadth in candidates under the most favorable assumptions: independent, isolated candidates with constant pass probability ${p}>0$ and a checker that decides the stipulated criterion exactly. A parallel pool of ${k}$ always spends ${k}$ candidates and reaches availability ${q}_k=1-(1-{p})^{k}$. Sequential generation that stops at the first pass reaches the same ${q}_k$ after an expected $\mathbb{E}[{M}_k]={q}_k/{p}$ candidates, and never more than ${k}$. Charging each candidate its generation cost ${g}$ and its checking cost ${v}$, in dollars, and charging every initiated trial against the accepted ones turns those counts into costs per accepted task:

$$
{C_{\text{eff,batch}}}=\frac{{k}({g}+{v})}{{q}_k},\qquad {C_{\text{eff,seq}}}=\frac{{g}+{v}}{{p}}. \tag{6}
$$

^eq-cost-per-accepted-task-iid

Pricing generation and checking separately exposes a third policy that candidate counts hide. Generating all candidates first and stopping only the *checking* early costs ${k} {g}+({q}_k/{p}){v}$ per trial in expectation, because generation already performed stays paid for even when checking stops. Choosing a generator under sequential stopping therefore reduces to comparing $({g}+{v})/{p}$ across generators rather than choosing ${k}$, and when checking dominates, raising ${p}$ upstream wins because every failed attempt pays for a check. The formulas in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-cost-per-accepted-task-iid|equation 6]] omit latency constraints, checker errors, task heterogeneity, and adaptive feedback.

↩︎ The trade-off between spending a fixed deliberation budget on generating candidates and on checking them is established in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.04 Selecting from a Candidate Pool#^sec-vol3-test-time-compute-selection-costs|Balancing pool size against checking cost]]**.

**Napkin Math 13.3: Pricing generation and checking separately**

**Problem**: At the same candidate cap, how much does stopping generation at the first pass save per accepted task once generation and checking carry separate dollar prices?

**Assumptions**: Use a fixed-task pass probability of 40 percent, at most 3 isolated candidates, generation cost \$0.03, and exact checking cost \$0.01 per candidate, with no other costs.

**Math**: Both policies return a passing candidate with probability 78.4 percent. Full batch generation and checking cost \$0.12 per initiated trial. Sequential generation and checking start 1.96 candidates on average and cost \$0.0784. Either policy’s all-fail path incurs the full batch cost. Charging failed trials to accepted ones gives approximately \$0.153 for the batch policy vs. \$0.10 for sequential early stopping.

**Systems insight**: Under sequential stopping, ${C_{\text{eff}}}=({g}+{v})/{p}$ whatever the cap, so raising the cap buys acceptance probability at no increase in cost per accepted task, while the full batch here pays a 53 percent premium for the same acceptance. Generating all candidates and stopping only the checks falls between the two, since it pays the batch’s full generation cost but only the sequential policy’s expected checking cost. With generation and checking prices held fixed, the one knob that lowers ${C_{\text{eff}}}$ is the single-candidate pass probability. Doubling ${p}$ halves it, to \$0.05. An imperfect selector, a deadline, or a shared environment changes these formulas and is measured as part of the policy.

**Checkpoint 13.3: Statistical evidence**

**Unit of replication**: An evaluation suite already runs each task more times than ${\sigma_{\text{run}}}^2/{\sigma_{\text{task}}}^2$. Which variance component does each option reduce, and how do fixture and run costs determine whether the next evaluation budget should buy repeats or new tasks?

**Comparison evidence**: How do estimation precision, planned detection power, and an observed paired difference answer different questions?

**Potential and selection**: A pool contains a passing patch but the selector returns another. Which metric records the available pass, and which records the delivered failure?

**Consistency estimate**: A support agent answers a refund-policy question correctly on 95 percent of single runs. Estimate pass$^{k}$ over 5 sessions, and the single-run rate that would hold 90 percent consistency over those sessions.

**Budget accounting**: Why must generating all candidates before checking be priced differently from generating only after the preceding candidate fails?

These metrics quantify outcomes under a declared experiment, and for the worked comparison they return an offline verdict and stop there. `candidate_v2` accepted more paired tasks than `baseline_v1`, yet its paired interval does not exclude a loss larger than the declared tolerance, so the offline evidence establishes neither noninferiority nor superiority. A powered next sample needs its gain, discordance, and tolerance fixed before any data arrive. What the metrics cannot report is why an individual trial failed. A lower acceptance rate could arise from the model, missing context, an observation boundary, or a slow dependency, and separating those causes takes execution evidence and controlled experiments rather than more aggregate counts.
