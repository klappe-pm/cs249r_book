# V3-13.04 Hermetic Evaluation Gyms

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13 Agent Evaluation|V3-13 Agent Evaluation]]

^sec-vol3-evaluation-gyms

If a trial of `candidate_v2` on `pool_repair_01` inherits mutated state from an earlier run or reaches live external endpoints that shift between attempts, the observed score difference against `baseline_v1` measures environmental contamination rather than an architectural improvement. Both systems must execute against the declared task under equivalent starting conditions, and the evaluator must verify every result directly against the artifact generated during that specific trial. An **evaluation gym** provides the task’s interactive environment, establishes controlled starting conditions, and exposes clean interfaces for capturing trial evidence. Its **hermetic boundary** explicitly specifies which dependencies are provisioned or simulated and which external network and filesystem interactions are blocked. This boundary serves as an experimental contract: it fixes the declared experimental conditions without requiring either identical model responses or absolute production fidelity. A stochastic environment qualifies as hermetic once every source of non-determinism is declared, bounded, and systematically recorded.

### Task Fixtures

^sec-vol3-evaluation-gyms-fixtures

When two trials of `pool_repair_01` pull floating package versions or start from slightly different service states, a third-party library update between runs can masquerade as a regression or gain in the agent itself. A **task fixture** prevents that drift by packaging the exact initial state, dependencies, and configuration required to instantiate an evaluation task. In an automated repair benchmark, `pool_fixture_v1` pins the baseline repository commit, the language toolchain and package versions, the simulated test-service behaviors, and the files the agent is permitted to read or edit. The fixture establishes the baseline conditions under which an agent attempts the task, whereas separate acceptance criteria evaluate the resulting artifact; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^tbl-vol3-evaluation-fixture-contract|table 3]] records the conditions that must accompany the trial.

| Fixture component       | What the repair evaluation declares                                                                                            | Why the comparison needs it                                          |
|:------------------------|:-------------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------|
| Initial task state      | Starting source revision, supplied defect description, permitted files, and initial service state                              | Neither system inherits another trial’s fix or an undeclared hint    |
| Executable dependencies | Toolchain, packages, tool interfaces, service fixtures, and relevant configuration versions                                    | A dependency change is not mistaken for a system improvement         |
| Interaction policy      | Available tools, permitted data and destinations, resource limits, and external behaviors represented                          | Both systems face the declared task and authority boundary           |
| Variation policy        | Fixed or sampled fault conditions, scheduling and random inputs where controlled, and recorded provenance where not controlled | The experiment distinguishes intended variation from missing control |
| Evidence boundary       | Exported candidate identity, protected grader configuration, criteria version, and allowed development feedback                | A result applies to the actual submitted artifact and check          |
| Trial lifecycle         | Reset readiness, output capture, observation cutoff, cleanup, and residual ownership                                           | Late work and retained state cannot silently enter the next trial    |

Table 3: **A fixture contract for comparable trials**: The fixture manifest defines what parameters are held constant, which factors may vary, and what evidence must be captured, ensuring apples-to-apples comparisons without requiring full reproduction of every production nuance.

^tbl-vol3-evaluation-fixture-contract

A rigorous benchmark must also document how tasks are sampled from the broader problem distribution, because repeatedly evaluating a single fixture characterizes only that specific repair workflow ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-rigor|section 13.5]]). Even when an evaluator fixes the pseudo-random seed of the language model, non-deterministic inference serving (dynamic batching, asynchronous token streaming, and accelerator kernel scheduling) introduces subtle timing variations. The evaluation run must therefore record all accessible execution provenance alongside explicit statements regarding unconstrained sources of entropy.

### Controlled Interactions

^sec-vol3-evaluation-gyms-interactions

Pinning a static starting snapshot is only the first step, because evaluating a repair agent on a single-turn prompt-and-patch benchmark never tests whether it can diagnose compiler errors, respect state-dependent APIs, or revise a broken attempt across turns. Interactive evaluation instead exercises the closed loop where an agent inspects its environment, parses diagnostic feedback, revises its working candidate, and runs intermediate checks. Because the fixture mirrors the task domain, its components vary accordingly. A document-analysis fixture locks down static reference documents and vector indices, whereas an interactive browser benchmark configures authentication credentials, pre-populated user sessions, and mutable web-application databases.

Providing authentic command-line and language tools within an isolated sandbox allows the evaluation harness to exercise compilation pipelines, filesystem operations, and sub-process execution directly. For external dependencies, stateful service emulators can track conversational state and state-dependent APIs where downstream responses depend on earlier writes. Prerecorded network traces support a much narrower replay boundary, since a recorded interaction remains valid only as long as the agent’s request method, endpoint, arguments, schema versions, and call order match the recorded sequence exactly. If the agent deviates by issuing an unexpected API call or reordering operations, the replay harness cannot simply deliver the next historical record. Under the matching-request rule, the evaluator must either provide a synthetically valid response for the novel path or fail fast by signaling an unsupported interaction.

↩︎ Request matching, which a replay adapter applies before returning any recorded response, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.07 Recorded Trajectory Replay#^sec-vol3-durable-execution-harness-regression-replay|Harness regression replay]]**.

In an environment testing automated cloud-resource repair, a mock service that invariably returns immediate HTTP 200 responses fails to evaluate whether the agent can handle dropped connections, timeout retries, or eventual consistency. A fault-injecting fixture instead exercises resilience by selectively dropping packets, introducing synthetic latency, or withholding acknowledgments, exposing real-world distributed systems failure modes. Engineering an evaluation gym therefore involves a continuous trade-off between fidelity and determinism. Simple deterministic mocks maximize reproducibility and run rapidly, but they routinely omit real-world concurrency, race conditions, partial failures, and subtle error codes. Conversely, deploying full-scale, live service instances yields high behavioral fidelity at the expense of heavy provisioning overhead, slow trial resets, and environmental flakiness. Systems architects must align simulation fidelity with the specific capabilities being claimed. Furthermore, any architectural behaviors intentionally omitted by the fixture must be documented alongside reported metrics, because a perfect success rate against a simplified mock shows competence only within that sanitized world. Finally, testing agents against live production or external third-party APIs requires dedicated authorization and hard resource bounds; prefixing an execution run with the label “benchmark” confers no legal or operational authority to touch production infrastructure.

### State Reset Between Trials

^sec-vol3-evaluation-gyms-reset

Once an interactive trial finishes, reverting a repository with `git checkout` is rarely enough to restore a clean starting state: orphan background processes, uncleared message queues, temporary files in `/tmp`, and mutated API mocks can all leak side effects into the next trial. Beyond the baseline sandbox reset contract, evaluation requires every trial to start from an environment identical to the declared task fixture. Resetting a trial means terminating all background worker processes, capturing the candidate artifact at a consistent filesystem checkpoint, revoking session-specific credentials, and scrubbing every mutable resource. If an asynchronous operation initiated during an earlier trial remains in flight, the hosting container or virtual machine cannot return to the warm pool until that background operation terminates or its target resource is destroyed. Discarding a workspace directory while background network writes are still pending leaves the host environment corrupted.

↩︎ The reset contract that must hold before a pooled sandbox serves a new lease is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|The reset contract]]**.

To maintain high throughput across thousands of evaluation runs, evaluation frameworks rely on copy-on-write (CoW) filesystem overlays and virtual machine snapshots rather than provisioning fresh environments from scratch. When reporting benchmark throughput, system designers should explicitly break down end-to-end latency into container warm-up, snapshot reset, agent execution, queueing delays, and grading, because reporting only sandbox lease acquisition times creates a misleading picture of cluster capacity. Controlled sharing of underlying resources remains compatible with sound experimental methodology as long as the shared state cannot leak across trials. Immutable compiler caches and base operating system images can be shared safely across sandboxes. Evaluating an agent against a pre-warmed cache is valid when warm-cache performance is the stated target of the experiment. Whenever concurrent trials compete for shared host resources such as CPU cycles, memory bandwidth, or host kernel threads, however, evaluators must measure resource contention directly or randomize trial ordering to prevent queuing artifacts from being mistaken for candidate improvements.

### Grader Isolation

^sec-vol3-evaluation-gyms-grader-isolation

Resetting the sandbox between runs protects the starting state, but a trial can still corrupt its own verdict if the agent or its submitted code can reach the tests that grade it. Visible unit tests are useful during iterative problem-solving to give the agent intermediate feedback, whereas held-out acceptance tests, which act as the sealed tests of the closure evidence levels, must judge the final submission without becoming an optimization target themselves. **Grader isolation** keeps reference solutions, secret test suites, grading scripts, and authoritative score registries outside the agent’s execution environment, and cryptographically binds the resulting score to the exact artifact digest (such as the SHA-256 hash of workspace snapshot `ws_r19`) captured at completion.

↩︎ Sealed tests outrank visible tests among the closure evidence levels established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-invariant-closure|The invariant closure principle]]**, because the agent never sees their definitions and cannot reach where they run.

Submitted code stays untrusted after the agent process stops. If an evaluation harness imports the candidate package directly into the Python interpreter running the grading assertions, the submitted code can monkey-patch core assertions, manipulate built-in object prototypes, or rewrite test runner hooks. Similarly, if secret test files are mounted into the filesystem where candidate code can inspect directory trees or read file contents, the tests are irrevocably compromised. Mounting files as read-only prevents direct overwrites, but it provides zero protection against exfiltration or inspection.

↩︎ Why code running inside the supervisor’s own interpreter can reach the supervisor’s state is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.04 Limits of In-Process Restriction#^sec-vol3-sandboxes-object-graph|The reachable object graph]]**.

A robust grading architecture must enforce two distinct security boundaries: the live agent’s access during task execution and the submitted artifact’s execution reach during evaluation. In [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^fig-vol3-eval-gym-architecture|figure 2]], an external trusted controller manages evaluation logic, holds the private test suites, and commits results to a secure database, while candidate code executes inside a strictly sandboxed runner. The controller orchestrates testing over a narrow, well-defined remote procedure call (RPC) interface and strictly enforces a patch-admission policy specifying which repository files the candidate was permitted to touch. It treats all candidate-generated stdout, stderr, and exit codes as untrusted observations.

![[90 Assets/Volume III/13 Evaluation/Ch13 Eval Gym Architecture 2c313d6c74.svg]]

Figure 2: **Trial Sandbox and Grading Boundary**: The agent under test edits and runs checks inside a single-use fixture whose base image is shared read-only and whose writes land in a per-trial copy-on-write layer; external egress is blocked, and service fixtures stand in for the dependencies the task declares. The captured candidate `ws_r19` crosses to a grading boundary, where a trusted controller keeps the held-out tests, criteria, and result store and sends selected tests to a separately limited execution of the candidate code. That execution remains the attack surface, because submitted code runs with the tests it receives, so its outputs are untrusted observations until the controller binds each criterion’s verdict to the exact artifact.

^fig-vol3-eval-gym-architecture

When repository unit tests require in-process execution alongside submitted code, the test harness itself becomes an explicit attack surface. In these configurations, rigorous evaluation harnesses run automated adversarial probes before grading, in which synthetic exploit patches attempt to read environment variables, inspect parent memory spaces, override assertion operators, and forge passing exit signals. Passing these containment checks demonstrates resistance against known circumvention techniques, though such verification covers only the specific security perimeters tested.

### Evaluation Leakage

^sec-vol3-evaluation-gyms-leakage

Even when a sandbox blocks external network access and isolates the grader, a benchmark score is still invalid if the answer crosses the trial boundary through the model’s weights, its retrieval index, or its persistent memory. Pre-trial leakage occurs through **contamination**, when benchmark solutions appear in pretraining corpora, or through retrieval, when external retrieval-augmented generation (RAG) vector indices index ground-truth patches. Runtime leakage occurs when multi-agent systems or persistent memory stores retain information across successive runs, inadvertently passing solutions from one trial to the next.

↩︎ Cross-session memory trials keep reference answers and fixtures outside both writable and retrievable stores, under the trial design established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.11 Evaluating Memory Policies#^sec-vol3-long-term-memory-policy-trials|Cross-session policy trials]]**.

Furthermore, an evaluation suite can leak methodologically even when the sandboxes remain completely sterile. Repeatedly refining prompts, tool definitions, or agent architectures based on error analyses of held-out test failures converts that held-out suite into an informal training set.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.12 Footnotes#^fn1|¹]] Hyperparameter adjustments and prompt changes guided by held-out feedback systematically overfit the evaluation suite, eroding its statistical validity as an unbiased assessment of generalization ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-dwork2015reusable|Dwork et al. 2015]]). Maintaining sound evaluation requires tracking end-to-end data provenance for task prompts, gold-standard solutions, unit tests, and trajectory logs. While n-gram filtering and embedding similarity checks help flag potential contamination, falling below an arbitrary similarity threshold never guarantees true task independence. **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.05 Split Design#^sec-vol3-flywheel-evaluation|Split Design]]** formalizes the dataset splitting protocols required to enforce this separation.

Public agent benchmarks trade off these gym controls (task fixtures, interactive dependencies, isolated graders, and coverage limits) in different ways. SWE-bench presents real-world repository issues and validates generated patches against task-specific test suites ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-jimenez2024swebench|Jimenez et al. 2024]]). Its evaluation harness checks both `FAIL_TO_PASS` assertions (verifying that the reported defect is resolved) and `PASS_TO_PASS` assertions (verifying that existing functionality has not regressed) ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-jimenez2024swebench|Jimenez et al. 2024]]), grounding correctness in concrete runtime behavior rather than static code similarity. GAIA poses complex, tool-assisted questions where each task specifies a concise, unambiguous ground truth, grading only the normalized final answer against an exact-match target ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-mialon2023gaia|Mialon et al. 2023]]). While computationally inexpensive and deterministic, this check treats the agent as a black box, observing nothing about the cost, safety, or validity of the intermediate steps taken to reach the output. WebArena deploys fully functional web applications within isolated environments, evaluating tasks by inspecting the resulting database and application state rather than parsing agent transcripts ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.11 Source References#^ref-zhou2024webarena|Zhou et al. 2024]]). However, targeted state assertions verify only the specific records they query. If an agent executes an e-commerce purchase successfully but inadvertently deletes unrelated order records along the way, a narrow state query still registers a pass. Comprehensive evaluation therefore requires explicit checks for unintended side effects, illustrating why the constraint-compliance dimension in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^tbl-vol3-eval-contract-hierarchy|table 1]] demands independent validation.

**Checkpoint 13.1: Comparable trials and protected evidence**

**Identity**: Why must a result for `ws_r18` not become the grade for newly submitted `ws_r19`, even on the same task fixture?

**Fidelity**: Which recovery claim cannot be tested by a provisioning mock that always returns immediate success?

**Grader boundary**: Hidden tests are absent during the agent’s run but share an interpreter with candidate code during grading. Which attack surface remains, and which change to the grader design closes it?

**Reset**: A previous trial left an unresolved remote job. Can its sandbox return to the pool, and what must be established first?

**Leakage**: Why can repeated tuning on held-out errors weaken the evaluation even when every sandbox resets correctly?

^callout-checkpoint-13-1-1e7a6481

Isolating the evaluation gym ensures that the captured candidate artifact and its execution trace reflect the trial itself rather than environmental drift or test leakage. Once the gym protects that evidence collection boundary, the next systems challenge centers on grading mechanics: identifying which criteria can be verified through deterministic execution checks and which demand calibrated judgment or human-in-the-loop review.
