# V3-10.07 Supervised Waiting

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-controlplane-yielding

When the agent dispatches the integration test for candidate `r18`, the model generates nothing for as long as the test runs, which is tens of seconds for the integration test priced in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^sec-vol3-kv-workload-dynamics|Residence time and service rate]]**, and minutes for a broader suite. If the worker thread that dispatched the job blocks until the result returns, it cannot service any other trajectory in the interim, and the runtime becomes unresponsive to operator pauses or high-priority interactive requests. The repair trajectory requires no token generation while the test executes. What it requires instead is an external supervisor: a control entity that tracks the in-flight job, holds the execution continuation, and buffers incoming evidence without tying up a worker thread in a synchronous wait.

Yielding execution through an asynchronous wait[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.16 Footnotes#^fn4|⁴]] releases the worker thread immediately, leaving the trajectory record as the explicit holder of pending state. Alternatively, a runtime with blocking workers can maintain controllability if an independent supervisor thread handles operator requests, heartbeats, and deadlines. The requirement holds for any event-loop implementation. Waiting must keep the control record accessible, and any returning event must pass through that record’s admission guards before advancing the trajectory.

### The Result Wakeup Pipeline

^sec-vol3-agent-harness-wakeup-pipeline

The asynchronous job interface decouples job acceptance from completion, so a result can arrive seconds or hours after dispatch, out of order, or more than once. The register-before-send rule makes that safe. For an external job, registration records the owning trajectory, the invocation and attempt identifiers, the external job handle when available, the expected workspace source revision, the observation eligibility policy, and the outstanding liability, so even an immediate callback finds the record it needs.

↩︎ The asynchronous tool invocation interface and completion polling contracts are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.09 Asynchronous Tool Dispatch#^sec-vol3-tool-calling-async|Asynchronous Tool Dispatch]]**.

Regardless of how the runtime structures concurrency, the supervisor must satisfy four distinct logical obligations when processing an incoming result. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.07 Supervised Waiting#^tbl-vol3-event-wakeup-pipeline|Table 7]] stages them in order and pairs each with the inference it does not license.

| Stage                        | Harness responsibility                                                                                                                                                  | Tempting but false inference                                                |
|:-----------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------|
| Receive an event             | Obtain a notification, status reply, timer event, or control request through the designated interface.                                                                  | A notification establishes a completed result.                              |
| Authenticate and correlate   | Check the source and match the event to its task, operation or attempt, and recorded execution context.                                                                 | A matching identifier authorizes a new action or makes the payload true.    |
| Update the record            | Preserve reported outcome, source revision, capture limits, usage, and any unresolved obligation; decide whether the evidence is eligible for the waiting continuation. | Evidence for an earlier attempt belongs directly in the current model turn. |
| Apply the continuation guard | Evaluate pending controls, the wait policy, dependencies, current grants, and budget before making continuation eligible.                                               | New evidence requires an immediate model call.                              |

Table 7: **Event handling before continuation**: Receiving evidence, recording its meaning, and admitting further work are separate supervisory decisions.

^tbl-vol3-event-wakeup-pipeline

The event handler generalizes the callback logic in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^lst-vol3-harness-on-result|listing 2]] across all event sources. Operating under a mutex or transactional boundary, the handler updates the record, advances `record_version`, and checks the call’s recorded epoch against `control_epoch`; the version check itself happens in the guarded transition the handler then requests. Because network notifications can be duplicated, the handler must remain strictly idempotent: an identical redelivery will neither append a redundant observation, nor double-bill resource counters, nor re-enqueue an already scheduled continuation. Correlation ensures that incoming data routes to the correct trajectory record, while the tool’s formal contract defines what that evidence actually establishes.

This discipline applies equally to streamed outputs. Real-time log fragments and progress heartbeats can append data to a bounded observation store without terminating the wait interval. Conversely, observing an opening tool-call delimiter in a streaming model response represents an incomplete proposal; the supervisor takes no action until the stream completes. The model adapter retains sole responsibility for parsing and validating full invocation payloads, whereas the harness determines whether that validated proposal remains eligible under current control policies.

### Job and Batch Waits

^sec-vol3-agent-harness-job-batch-waits

If a runtime woke the model on every status poll to ask whether to keep waiting, or treated a prompt in raw job stdout as a trigger to resume generation, a ten-minute test run would burn tokens on empty polling turns and let unverified log output drive control decisions. Instead, the harness waits for a push notification or polls external status at bounded intervals on its own, without querying the model. If a job pauses to request human or auxiliary input, the runtime logs that requirement as a structured state transition rather than a trigger for resumption. Responding to such an input requirement remains a distinctly authorized operation, and the record tracks this pending dependency explicitly rather than treating raw stdout or log lines as an implicit signal to resume model generation.

Parallel tool invocations demand an explicit continuation policy. Under an *all-results* policy, the harness suspends the trajectory until every member of the batch either returns valid evidence or reaches a terminal disposition, such as a timeout with unresolved side effects. Conversely, a *partial-results* policy permits the model to reason incrementally as individual results arrive, even while other calls remain in flight. Such a policy must explicitly track missing evidence, preventing downstream steps from proceeding under the mistaken assumption that the entire batch has converged.

For example, a completed lint result need not settle a concurrent test job. If the agent’s next planning step requires both checks on candidate `r18`, the lint output alone leaves the wait open. If, however, the subsequent step is an independent inspection, a partial-results policy can safely admit it under current limits. Modifying the candidate workspace while the test suite actively reads disk state introduces race conditions; simply designating invocations as parallel does not preserve the tested revision without explicit workspace isolation.

When a deadline expires, it terminates the harness’s wait interval, not the underlying remote operation. The harness logs the timeout, marks the operation as unresolved, and requests the configured intervention policy. The operation table keeps the unresolved charge open until explicit settlement rules determine whether late-arriving results can be accepted or whether re-execution is safe.

### Results During a Pause

^sec-vol3-agent-harness-results-during-pause

If suspending a trajectory also shut down its event listener, any tool callback arriving while the run sat in `PAUSED` or `FINALIZING` would be dropped at the socket, stranding the job’s budget reservation and losing its completion evidence. The harness event handler must therefore remain active even when continuation is suspended. When the `r18` test result arrives during a pause, it settles its entry in the operation table while the trajectory stays `PAUSED` along the path traced in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-agent-harness-pause-entry|section 10.4.3]], and only the resume guard can let it inform the next model call. The same holds during finalization, where late-arriving evidence can settle outstanding liabilities without reviving an already terminated trajectory.

### Resources Retained While Waiting

^sec-vol3-agent-harness-retained-resources

Releasing a worker thread does not dismantle the underlying execution environment: sandboxed processes, disk workspaces, network sockets, buffered logs, and retained inference states remain allocated. The control record maintains explicit references to these resources and their respective lifecycles. Tool subscriptions and cloud storage incur ongoing charges, quota reservations persist until liabilities are settled, and the wall-clock task deadline continues to elapse. Even polling routines and cleanup handlers consume execution budget and must operate within configured limits.

A workspace lease guarantees the availability of candidate source edits and test artifacts according to the lifetime contracts established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.07 The Agent Workspace#^sec-vol3-sandboxes-lease|Workspace leases]]**, persisting across multiple tool boundaries. Its term bounds what a waiting trajectory can lose. If the harness never returns to renew, lease expiry reclaims the workspace; if it returns after expiry, the resumed trajectory must treat its workspace as gone rather than assume the files it left are still there. In parallel, the model serving infrastructure decides whether to retain, evict, or page out key-value cache state across turns. Releasing the harness worker does not remove the residency tax of **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^sec-vol3-kv-workload-dynamics|Residence time and service rate]]**: attention state kept resident through the wait still divides the turn rate its memory can sustain by $1 + {T_{\text{tool}}}/{T_{\text{model}}}$. The harness provides hints regarding expected wait durations and resumption priorities; where a hosted inference service provides no explicit cache-placement primitives, retention remains subject to provider eviction policies.

↩︎ Keep, move, and drop policies for a paused trajectory’s KV-cache state are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kv-cache-keep-move-drop|Keep, move, and drop policies]]**.

A wait is therefore a supervised interval characterized by retained evidence, active resource leases, and pending obligations. When that interval concludes, the harness transitions the continuation to an eligible state only if the record’s guards explicitly approve. Human-in-the-loop approval operates under this identical supervisory discipline: rather than waiting on an external computation, the harness suspends execution before dispatch, waiting for an authorization decision that may arrive late, be denied, or expire entirely.
