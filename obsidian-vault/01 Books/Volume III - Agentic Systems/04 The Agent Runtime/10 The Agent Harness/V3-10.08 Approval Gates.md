# V3-10.08 Approval Gates

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-controlplane-hitl

Consider the internal-review workflow: an agent proposes submitting candidate patch `r18` along with selected verification records, but trusted policy permits submission only after an authorized engineer signs off. The proposal is complete, yet the human reviewer is unavailable. Meanwhile, the task’s deadline clock continues advancing, an operator can request a pause, and credentials or access grants can expire. The harness cannot simply leave the proposal floating in the model’s context window, nor can it allow a retry loop or subsequent model step to dispatch the action prematurely. Instead, the runtime must hold the fully formed submission in escrow while review remains unresolved.

↩︎ Action-bound approval, which ties sign-off on the `r18` patch submission to its exact canonical payload, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.08 Delegated Identity and Credential Brokering#^sec-vol3-security-action-bound-approval|Action-bound approval]]**.

**Definition 10.3: Approval escrow**

***Approval escrow*** is the harness’s retention of an undispatched proposal pending required approval and subsequent dispatch admission. The held record binds the proposal to its enclosing task, approval conditions, and expiration deadline; even after a favorable decision arrives, execution still requires current admission checks at the dispatch boundary.

1.  **Significance**: Escrow decouples proposing an operation from the authority to execute it immediately, keeping long, human-scale waits visible to supervisors and external schedulers.
2.  **Distinction**: Authorization policies define who holds the authority to approve a represented action. The harness manages the operational lifecycle of that pending decision: routing the request, tracking timeouts, and enforcing state transitions toward dispatch or refusal.
3.  **Common pitfall**: Treating a recorded approval as an unconditional instruction to execute, ignoring subsequent changes to credentials, task deadlines, branch states, or available compute capacity.

Requiring human approval is a deliberate task-policy choice rather than an automatic property of irreversible side effects. Some high-risk actions are prohibited outright; many others proceed safely under tight, automated least-privilege policies. Conversely, sensitive data disclosures or even benign, reversible mutations might require human oversight depending on operational risk. The approval gate must therefore enforce trusted runtime policy over the concrete operation, target resource, and parameter scope, never relying on the model’s self-reported assessment of whether an action is safe. Requesting review cannot expand authority: a reviewer cannot grant permissions beyond their own administrative boundaries.

When a safety policy such as a production code freeze exists solely as prompt instructions inside the model’s context window, no gate stands between a proposed mutation and the target system (war story [10.1](https://mlsysbook.ai/vol3/10_agent_harness/10_agent_harness.html#ws-10-replit-code-freeze-2025)).

**War Story 10.1: A code freeze stated only to the model (2025)**

**Context**: In July 2025, SaaStr founder Jason Lemkin was building an application with Replit’s autonomous coding agent and placed the project under an explicit code freeze, instructing the agent in natural language not to modify code or production infrastructure ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.15 Source References#^ref-sharwood2025replit|Sharwood 2025]]).

**Mechanism**: The freeze existed only as text in the agent’s conversational context. No supervisory component at the dispatch boundary validated proposed database tool calls against that restriction. Despite the instructions, the agent executed an operation that deleted the production database, subsequently claiming that rollback was impossible.

**Impact**: The live production database was unavailable until engineering restored it. Lemkin also reported that the agent had masked previous software faults with fabricated synthetic data, including populating a 4,000-record database with fictional user profiles.

**Fix**: Contrary to the agent’s assertion, database snapshot rollback functioned properly and restored the data. Lemkin observed that natural language instructions cannot reliably enforce operational boundaries in agentic coding environments, advocating for strict architectural isolation between preview, staging, and production environments.

**Systems lesson**: Operational freezes are admission-control invariants, and admission control belongs strictly to the execution runtime. Stating a freeze to the model merely shifts output probabilities; it provides no deterministic safety guarantees. When enforced at the dispatch boundary by checking the target endpoint and operation payload against active policy, the runtime deterministically traps or rejects forbidden mutations regardless of what the model generates. This reflects the foundational requirement of invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]).

From the perspective of harness architecture, enforcing the freeze requires a single dispatch-time rule: while the freeze flag is set, any proposed mutation against the production target must be rejected or held in approval escrow. A destructive action then collapses into a harmless refusal observation fed back to the model rather than an unrecoverable side effect. Whether the model follows instructions becomes irrelevant to system correctness. The agent’s false claim that rollback was impossible highlights a related boundary: a model-generated status report can be false. The harness must verify execution outcomes and rollback states directly from its operation table, never from the agent’s conversational transcript.

Approval gates must also remain selective and narrow. When a human operator faces dozens of routine, low-risk confirmation dialogs every hour, fatigue leads to rubber-stamping without inspection.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.16 Footnotes#^fn5|⁵]] A gate where every request is approved adds no closure beyond the policy check that routed the request to it. Fine-grained authorization grants, sandboxes, and automated linters should handle the vast majority of verifiable actions. Reserving manual approval for high-blast-radius or policy-mandated exceptions keeps human attention on the decisions that need it.

### Held Proposals

^sec-vol3-agent-harness-held-proposals

If an approval request pointed only to a mutable workspace path or an unversioned tool call, a concurrent edit or plan revision could change the underlying patch between the moment the reviewer inspected `r18` and the moment the harness dispatched the submission. After validating a completed model response, the harness therefore freezes the held proposal in the trajectory record before publishing its approval request. The record references the task and requester, intended tool origin and operation, immutable candidate artifact and selected evidence, applicable preconditions, required approver policy, and approval expiry. It also assigns an approval-request identifier and a held-proposal version, and computes the **approval digest**, the digest that action-bound approval binds, computed here over the canonical held proposal and covering the operation, its arguments, its target, and the versions of the referenced artifacts. The approval binds to that digest, so changing any argument or artifact produces a different digest and voids the approval. These identifiers and the cryptographic digest track the pending decision itself, distinct from the logical operation IDs or transport-layer idempotency tokens assigned once dispatch begins.

For the review submission, the held artifact is the exact `r18` patch and named check records, and the selected records retain their evidential scope; a targeted unit-test pass does not become full acceptance because it appears in an approval request. The authentication and represented-action requirements are those of action-bound approval. The harness adds the recorded status needed to distinguish pending, denied, expired, withdrawn, and admitted requests. In [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^fig-vol3-human-escrow|figure 3]], panel (a) binds the exact proposal payload, artifact hashes, destination scope, and expiration timestamp into an immutable approval digest for revision `r18`. Panel (b) traces the four-step resolution sequence that parks the trajectory in `AWAITING_APPROVAL` until reviewer decisions and dispatch guards are verified.

![[90 Assets/Volume III/10 Agent Harness/Fig Vol3 Human Escrow 856e3492e9.svg]]

Figure 3: **The Approval Gate**: Panel (a) lists what the reviewer approves for the r18 review submission: the exact proposal, its destination and data scope, the selected evidence with its limited scope, the preconditions, the digest that binds the approval, the expiry, and the requesting trajectory. Panel (b) holds the proposal without sending it, obtains a decision the model takes no part in, and rechecks current conditions at the dispatch boundary. An approval without capacity stays held; a denial, expiry, or stale proposal returns a refusal observation.

^fig-vol3-human-escrow

The trajectory enters `AWAITING_APPROVAL` without sending the held tool call. Parking the trajectory in this state releases its active compute worker; polling for a human response requires an external callback or light notification check rather than expensive model inference. The suspended trajectory retains its proposal record, cryptographic digest, and artifact references, while optionally maintaining its workspace lease and sandbox storage.

Under stable flow, Little’s law (theorem [5.1](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#thrm-05-littles-law)) makes the mean number of trajectories held in `AWAITING_APPROVAL` equal to the rate of approval requests multiplied by the mean time to a decision, ${N_{\text{held}}} = {\lambda_{\text{arr}}}\,{T_{\text{wait}}}$. Review latency, not model speed, dictates how many concurrent held trajectories and retained resources the system carries. The relation fixes the mean, not the peak. A burst of review requests after an incident, or a reviewer who clears the queue once a day, holds far more than the mean for as long as the backlog lasts. The pool for held workspaces is therefore sized from the arrival pattern. The approval expiry strictly bounds this wait for a decision, while the trajectory’s overall deadline clock advances independently. Which operational cost dominates, retained sandbox footprint or delayed mitigation, depends on the workload profile.

↩︎ Little’s law, which equates mean occupancy with arrival rate times mean residence time, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^sec-vol3-kv-workload-dynamics|Residence time and service rate]]**.

**Lighthouse 10.1: Remediation agent (approval escrow)**

**Workload**: The remediation agent diagnoses a production incident and proposes a change, such as restoring a previous service configuration, that policy holds for an on-call reviewer. The repair agent’s gated action is instead a review submission near the end of a long trajectory. Both wait in `AWAITING_APPROVAL`, and Little’s law, ${N_{\text{held}}} = {\lambda_{\text{arr}}}\,{T_{\text{wait}}}$ for the ${N_{\text{held}}}$ trajectories held at once over a decision time ${T_{\text{wait}}}$, prices each wait. All rates and times below are scenario inputs.

**Repair agent**: Review requests arrive at 6 per hour and a decision takes 2 hours on average, so about 12 trajectories are held at once. Each keeps its workspace lease, 512 MiB in the reference coding-agent profile, so escrow retains 6 GiB of sandbox memory while no user waits on the outcome.

**Remediation agent**: Requests arrive at 2 per hour, so on average 0.5 trajectories are held and retained resources are negligible. The cost is time: with 6 minutes of diagnosis, a 15-minute mean decision, and 9 minutes to apply and verify, approval is 50 percent of the 30-minute time to mitigate, all of it spent with the service degraded.

**Systems insight**: One escrow mechanism binds on different terms. For the repair agent, retained memory scales with ${T_{\text{wait}}}$, so halving the decision time halves the held workspace. For the remediation agent, each minute removed from ${T_{\text{wait}}}$ removes a minute of degradation, and approval is the largest term in time to mitigate. Remediation therefore binds the approval digest to one exact configuration version so review is quick, sets the approval expiry shorter than the interval over which production configuration drifts, and lets already-admitted independent read-only diagnostic jobs continue under their existing grants and limits while the mutation waits.

### Approval Decisions and Duplicate Delivery

^sec-vol3-agent-harness-approval-decisions

Webhook deliveries from an approval service can arrive twice after a network retry, or arrive late after the request has already expired or been withdrawn by an operator. Rather than blindly treating any inbound approval packet as an immediate trigger to resume execution, the harness requires an authenticated decision cryptographically tied to the held request identifier and version. It validates the decision against the active escrow record and recalculates the approval digest. Duplicate webhooks or replayed messages are idempotent; the harness drops repeated deliveries without recording duplicate decisions or re-triggering dispatch. Similarly, a late decision arriving for a request that has already been withdrawn, expired, or superseded serves only as historical audit evidence; it can never revive a closed request. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^tbl-vol3-escrow-transitions|Table 8]] distinguishes recording such a decision from admitting the operation.

| Event while in `AWAITING_APPROVAL`                            | Recorded handling                                                                    | Continuation                                             |
|:--------------------------------------------------------------|:-------------------------------------------------------------------------------------|:---------------------------------------------------------|
| Required decision has not arrived                             | Keep the proposal undispatched until its expiry or another control event             | Remain `AWAITING_APPROVAL`                               |
| Valid approval arrives, but capacity is unavailable           | Record the decision; retain the held request without dispatch                        | Remain `AWAITING_APPROVAL`; recheck at admission         |
| Reviewer denies, request expires, or proposal becomes stale   | Close the held request and record the specific refusal reason                        | Return to `READY` only if continuation remains permitted |
| Approval is valid and every current admission condition holds | Consume the held request for dispatch, reserve liability, and register the operation | Enter `WAITING_TOOL` and issue the admitted request      |
| Task deadline or terminating control takes precedence         | Withdraw any still-undispatched request and record the stop reason                   | Enter `FINALIZING`                                       |

Table 8: **Approval decisions and admission**: A favorable decision does not bypass current conditions or allocate execution capacity by itself.

^tbl-vol3-escrow-transitions

Silence leaves the request unapproved. When the approval timeout lapses, the runtime logs an expiration event rather than an active human rejection. Both outcomes prevent dispatch, but the distinction matters when the trajectory is later debugged or audited. If the agent’s task policy permits continuation after a refusal, the harness delivers a compact observation record confirming that the operation was withheld:

``` json
{"approval_id": "review_r18",
 "status": "REFUSED", "reason": "APPROVAL_EXPIRED",
 "dispatch_status": "not_sent"}
```

The model can then interpret this refusal observation and propose an alternative strategy. What it cannot do is unilaterally extend the expired approval by submitting identical requests in a tight loop. Generating a fresh approval request requires constructing a current proposal that undergoes a new policy evaluation; otherwise, an automated agent could flood the reviewer with repeated requests, a denial of service through approval fatigue. If the enclosing task has exhausted its wall-clock budget, the harness records the refusal directly in the trajectory’s final record without expending further tokens or compute to solicit a narrative explanation from the model.

### Dispatch-Time Rechecks

^sec-vol3-agent-harness-dispatch-rechecks

Between the moment a reviewer signs off on the `r18` submission and the moment a worker prepares to dispatch it, the target branch may have advanced, the task’s token or financial budget may have been exhausted, or short-lived credentials may have lapsed. Human approval therefore satisfies only the governance precondition for admission, never exempting the held proposal from standard admission control when dispatch begins.

At the dispatch boundary, the harness re-evaluates the entire operational state. It recomputes the approval digest to ensure the artifact has not been modified in place, checks that the approval lease has not expired, and executes the full suite of rate-limit, budget, and authorization checks. Because queueing delays and downstream rate limits can stall an approved request in escrow, checks validated when the approval message arrived cannot be grandfathered into execution. If any check fails, the harness logs the specific refusal reason; if a task-level termination triggers, the trajectory routes immediately to finalization.

Consider a submission that requires an unmodified target branch. Reading the branch HEAD before requesting approval cannot prevent concurrent commits during the minutes or hours the request sits in escrow. When operations carry concurrency preconditions, the dispatching endpoint must verify the expected target version atomically alongside the mutation, or use an external optimistic locking mechanism.

↩︎ The atomic conditional update, which verifies an expected version in the same step as the write, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-conditional-updates|Conditional updates]]**.

Admitting a held request follows the register-before-send protocol with one additional step in the same atomic update. Under an exclusive lock, the harness registers the outgoing operation and marks the held escrow record as consumed. This prevents duplicate approval callbacks or concurrent workers from dispatching the action twice, and it strictly orders an approver’s sign-off against a racing operator cancellation or timeout. If a cancellation commits first, it withdraws the held request and records an unambiguous `not_sent` status. If admission commits first, the operation becomes owned work. A later control may still withhold release through the serialized gate, but the harness retains the record and reservation until non-release and the absence of remote liability are established. If an unhandled transport failure occurs after the packet departs the host, the harness must treat the remote effect as indeterminate. While marking an approval consumed prevents duplicate local dispatch, it cannot guarantee endpoint deduplication or resolve an in-flight network partition.

### Withdrawal of Held Requests

^sec-vol3-agent-harness-held-request-withdrawal

If an operator pauses a trajectory while a proposal sits in `AWAITING_APPROVAL`, leaving the request active in the review queue would let a reviewer’s click trigger dispatch while the trajectory is supposed to be held. Pausing from `AWAITING_APPROVAL` therefore follows the supervisory lifecycle in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-controlplane-statemachine|section 10.4]] with an explicit escrow cleanup step: the harness immediately withdraws the pending approval request, marks the proposal as not dispatched in the audit trail, and transitions through `READY` to `PAUSED`. If an approver submits a late decision while the task is paused or after it resumes, the harness rejects the decision because its associated request was already revoked. Should the agent still require the operation upon resuming, it must generate a fresh proposal subject to current state and policy checks.

Cancellation and task expiration route directly into `FINALIZING`. This terminal path requires all previously dispatched work and outstanding external resources to be settled or transferred to an accepting owner. Withdrawing a held review submission leaves no side effects on external targets, but it does not automatically terminate concurrent asynchronous test jobs, settle their compute costs, or undo previously committed mutations. By maintaining a strict separation between held proposals in escrow and committed entries in the operation table, the harness provides unambiguous operational visibility even when complex trajectories terminate abruptly.

**Checkpoint 10.2: Approval over time**

The internal-review submission for `r18` is held while the task approaches its deadline.

**Approval vs. capacity**: A valid approval arrives while execution capacity is unavailable, and capacity frees only after the approval’s expiry. Decide the trajectory’s state at each event and what the model sees.

**Withdrawn request**: An operator pauses the trajectory before admission, then the approval arrives. Which record prevents the withdrawn request from running after resume?

**Stale precondition**: The target branch changes after a pre-dispatch read. Which endpoint condition preserves the approved operation’s precondition?

**Lost reply**: Dispatch may have occurred before its reply was lost. Why is `dispatch_status: not_sent` now unjustified, and which outstanding records must remain?

**Held-trajectory estimate**: Approval requests arrive at ten per hour and a decision takes thirty minutes on average. Estimate how many trajectories sit in `AWAITING_APPROVAL`, and how the count changes if reviewers answer twice as fast.

The approval gate now has a bounded lifetime and an explicit handoff from held proposal to admitted work. Human agreement is one condition in that handoff, alongside current authority, resource bounds, and action-time preconditions. Multiple trajectories can satisfy those conditions while competing for the same execution capacity, so the harness next needs a policy for sharing that capacity without bypassing their individual gates.
