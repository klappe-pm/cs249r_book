# V3-10.04 The Trajectory Record

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-controlplane-acb

When an operator issues a pause request, the conversation transcript cannot answer the questions the harness must resolve. The transcript records what the user and model said, but runtime decisions require knowing the state of the underlying system. Specifically, the harness must know which candidate revision is under test, whether a background validation job has finished, how much compute budget remains once outstanding asynchronous tasks are accounted for, and whether any external side effects are still in flight. Simultaneously, the cluster scheduler must distinguish a trajectory blocked on a container execution from one actively waiting for its next inference turn. None of these operational facts belong in the prompt. Resolving them requires runtime-owned control state that the harness can inspect, mutate, and enforce directly without relying on the foundation model to reconstruct its own execution history.

**Definition 10.2: Trajectory record**

***Trajectory record*** is the per-trajectory control state owned and maintained by the harness. It encapsulates identity and task scope, lifecycle state, resource limits and financial accounting, security grants and workspace leases, pending asynchronous operations, and references to prompt context, the live execution plan, container environments, and verified evidence.

1.  **Significance**: It provides the harness with an authoritative, centralized structure to inspect and govern the entire trajectory, tracking resource consumption, pending asynchronous operations, and security grants across inference calls.
2.  **Distinction**: While the conversation transcript records user-model message exchanges, the trajectory record tracks the operational state required to govern execution across multiple turns. A live in-memory record represents active control state, not a durable audit log or proof that external claims are verified.
3.  **Common pitfall**: Treating a model’s generated text or self-reported progress as an authoritative update to consumed budget, granted capabilities, tool execution results, or task completion.

[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.04 The Trajectory Record#^tbl-vol3-acb-schema|Table 2]] organizes these fields by the supervisory decisions they support. The table is a logical schema. A distributed runtime may partition these field groups across different storage backends, for example keeping ephemeral context references in memory while persisting cost accounts to an external store, provided each group retains a single authoritative writer and a well-defined update protocol.

| Field group                         | Contents                                                                                                       | Supervisory use                                                                       |
|:------------------------------------|:---------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------|
| Identity and task                   | Trajectory, requester, tenant, optional parent, task contract and version                                      | Bind requests and charges to the right task and authority                             |
| Control                             | `state`, `record_version`, `control_epoch`, `pending_control`, exit reason                                     | Decide whether a continuation or state change is current and permitted                |
| Continuation                        | Context reference and version, live-plan reference and revision, candidate workspace and evidence references   | Assemble the next call from the intended task state                                   |
| Limits and accounting               | Per-call limits, `actual_consumption`, `outstanding_reservations`, `finalization_reserve`, and `deadline`      | Check new liability against the remaining allowance and preserve funds for final work |
| Authority and resources             | Current grants, workspace leases, credential-broker references, resource owners                                | Check accessible operations and identify resources requiring release or transfer      |
| Current invocation and observations | `current_model_call`, `observation_eligible_calls`, attempt IDs, job handles, deadlines, and expected versions | Correlate events and decide which may inform the current continuation                 |
| Held approval                       | `held_approval`: exact proposal reference, applicable task and plan versions, approval status and expiry       | Keep a proposed action undispatched while its decision is pending                     |

Two questions about a running operation must be answered separately: whether its result may still inform the model, and whether the harness still owes anything for it. The first is **observation eligibility**, which defines whether the output of an operation is permitted to enter the prompt context for the next model invocation. The second is an outstanding obligation, and the two can come apart. A tool call can lose observation eligibility (when an invocation step times out, or the user cancels a subtask) even while the remote execution continues running in a backend container. To prevent orphaned side effects and resource leaks, the **operation table** tracks every logical operation across its entire lifecycle: transport retries, incoming execution evidence, and the specific subsystem responsible for final settlement.

The trajectory record manages this lifecycle through two versioning counters. While `record_version` increments on every serialized update to provide optimistic concurrency control, the **control epoch** (`control_epoch`) tracks the specific planning and invocation cycle against which proposals and observations are validated. The epoch does not advance on every turn; it advances when the harness withdraws a continuation’s claim on outstanding results, as when a wait deadline expires, an operator interrupts, or a plan revision supersedes pending work. Each call records the epoch current at its registration, so an ordinary result from this turn’s dispatch still matches. Incrementing the epoch invalidates in-flight observations registered under the earlier epoch without breaking the underlying operation’s idempotency contract. As a result, the harness continues tracking background tasks and their external side effects even after the agent has stopped waiting for their immediate output.

↩︎ The operation idempotency contract and retry semantics are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|Retrying Uncertain Actions]]**.

A parallel discipline governs resource accounting. The harness separates settled usage (`actual_consumption`) from provisional allocations (`outstanding_reservations`), which represent admitted operations whose compute or financial costs have not yet been finalized. The harness withholds a dedicated **finalization reserve** from general exploratory steps. This reserve guarantees that the runtime retains sufficient budget to execute mandated cleanup tasks, release sandboxes, and run deterministic verification suites before the trajectory terminates. Wall-clock deadlines operate independently of token limits, because waiting on remote containers or human reviewers consumes real time even when token generation is idle. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-controlplane-accounting|Section 10.9]] formalizes this admission test; the trajectory record provides the live metrics required to enforce it.

These lifecycle and accounting guarantees unite under one working rule, the *settlement rule*. It is the trajectory-level form of settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]). That principle says a timeout does not establish whether an effect occurred, so a blind retry is unsafe; the settlement rule adds that losing interest in a result does not release the effect’s charge or its owner either. Under this rule, withdrawing an operation’s observation eligibility, whether through a timeout, a plan revision, an operator pause, or trajectory cancellation, never removes the operation from the operation table or releases its budget reservation. Only authenticated, correlated evidence can settle an outcome, confirm completion, or release reserved budget. Until that proof arrives, the outstanding obligation retains a designated settlement owner responsible for reconciling its ultimate state.

### Update Authority and Referenced State

^sec-vol3-agent-harness-update-authority

If a model’s output could directly update its own budget balance, grant set, or step status, a single hallucinated or manipulative reply could reset the spending meter or mark an unrun test complete. Only the harness therefore holds write authority over the trajectory record. While the model can propose plan changes, tool calls, or completion assertions, the harness treats these outputs strictly as unverified proposals that must pass admission checks before the runtime commits them to the record. Provider billing APIs and tool execution metrics supply authoritative consumption figures, cryptographically signed or authenticated tool events supply operational evidence, and control APIs supply verified operator intent. Because this control state stays separate from prompt text, an agent may receive read-only notifications of its remaining budget without ever gaining the ability to change the meter.

To keep control operations lightweight and prevent multi-megabyte state copies during routine scheduler queries, the trajectory record stores references (content hashes, storage URIs, and job identifiers) rather than deep-copying full prompt contexts, workspace filesystems, or observation payloads. However, these references represent real underlying resource commitments. A paused or waiting trajectory continues to consume resources across distributed subsystems: KV-cache allocations in inference engines, isolated container environments and disk volumes, and open network sockets. The trajectory record holds the authoritative handles to these external assets and signals lifecycle transitions to their respective managers.

These in-memory references and handles hold only while the host process remains alive. Preserving this control state across process crashes and ensuring that record updates remain strictly serialized with respect to external side effects requires write-ahead logging and durable execution protocols. A dedicated durable-log offset in the control record binds the volatile runtime state to its persistent backing log.

↪ Committing each admitted operation and its reservation to durable storage before dispatch is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-persistence-wal|Durable Intent Before Dispatch]]**.

### The Live Plan

^sec-vol3-harness-live-plan

Once the repair agent generates candidate `r18` and dispatches a targeted unit test in a background container, a static candidate graph or a checklist in prompt text can no longer represent the state of the work. It cannot separate the edit that produced `r18`, the test currently in flight against that revision, and the broader integration suite still waiting on the test result. Runtime execution therefore demands a **live plan**, a dependency-ordered directed acyclic graph of execution steps that explicitly separates proposed actions from operations currently in flight and evidence already verified. Each step in the plan defines a unique identifier, explicit prerequisite steps or evidence dependencies, the target candidate artifact and operating conditions to which it applies, and its current execution status. When the harness admits a step, it binds that step directly to an entry in the operation table. When a step completes, the harness links it to the immutable evidence supporting that completion, never to an unverified checkbox emitted in model text.

⇄ **Contrast:** The revisable candidate plan established in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.06 Revising Candidate Plans#^sec-vol3-test-time-compute-planning-revision|Revising Candidate Plans]]** tracks only unexecuted candidate operations and their supporting evidence; the live plan also records operations in flight.

While the test runner executes in its background container, the live plan records the step as in flight rather than optimistically assuming success. When the runner completes, a passing status validates only that targeted test against candidate `r18` under those exact container flags; the remaining verification steps and final acceptance criteria remain unfulfilled. An operator’s pause request arriving mid-test acts as an independent supervisory event, interrupting further dispatch without corrupting the historical inputs or the validity of the ongoing test execution.

When incoming observations demonstrate that a strategy is failing, the model may propose a plan revision to alter downstream tasks. Before adopting any revised plan, the harness validates it against the overarching task contract, current evidence dependencies, remaining budget, and security grants. Adopting the revision advances the plan revision counter and invalidates pending, undispatched proposals and held approvals whose underlying assumptions have changed. Existing verified evidence remains valid under its original operating conditions. The harness synchronizes plan adoption with the tool dispatcher to prevent race conditions where a stale proposal might pass admission against a superseded plan.

Now consider what happens if a plan revision modifies the source code while the targeted test for candidate `r18` is still running in the background. The active container job is testing candidate `r18`, not the new revision. Relabeling the step in the plan cannot convert those eventual test results into evidence for the modified code. Deleting the step from the plan likewise does not abort the remote job, reverse its external side effects, or automatically refund its compute reservation. Instead, the harness keeps the active operation in the operation table under its original settlement owner, blocks downstream steps whose prerequisites are no longer satisfied, and evaluates the replacement work through a fresh admission check. Undoing an external effect requires compensation, a later action that offsets the earlier one (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^sec-vol3-failure-recovery-semantic-compensation|Semantic compensation]]**), not a retroactive edit to plan text.

By maintaining an explicit, dependency-tracked live plan, the trajectory record delineates what the agent has proposed, what the harness has admitted to the execution plane, and what obligations remain outstanding. The harness must therefore govern how this record evolves, so that it stays consistent across concurrent tool events, asynchronous worker callbacks, and operator interruptions. It does so by binding all lifecycle mutations to formal, guarded state transitions.
