# V3-10.03 The Loop and the Harness

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-controlplane-need

When the `r18` repair agent runs inside a bare execution loop, an operator pause during the test suite or an unconstrained retry cycle immediately exposes the lack of an external control plane. A control plane is a path, separate from the one that performs model calls and tool work, that decides whether that work may proceed. An unmanaged loop treats model completions as direct execution instructions; a harness treats them as untrusted proposals, evaluating every action against explicit admission policies, budget constraints, and external supervisory signals.

### The Anatomy of an Unmanaged Loop

^sec-vol3-harness-unmanaged-loop

The unmediated while-loop of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^lst-vol3-naive-agent-loop|An Unmediated Agent Loop]]** is the pattern most prototype agents still use, popularized by ReAct ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.15 Source References#^ref-yao2023react|Yao et al. 2023]]): invoke a foundation model, dispatch the tools requested in its completion, append the results to the message history, and repeat until the model emits a stopping condition. A single turn spans six phases, from context assembly to assessment against the task contract, and several of those phases must wait on external tools or human reviewers. What the prototype loop lacks for production operation is a place for those phases’ decisions to live, because it confines all operational state to the message list and the local call stack of the client process.

↩︎ The six-phase turn lifecycle, including the phases that pause a turn for tools and approvals, is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^sec-vol3-intro-execution-lifecycle|The six phases of a turn]]**.

Confining control state to the message list and call stack leaves three operational paths with nowhere to land. When an operator tries to pause a run during a long test suite, the runtime has no interface to receive the command. When cumulative token consumption exhausts the allocated budget, the loop cannot withhold the next model call without terminating abruptly and abandoning in-flight work. When the model proposes a tool invocation, the call executes immediately under ambient authority, without policy checks or human review. Although a supervised harness may also execute as a loop or coroutine, it wraps that loop in an explicit state machine whose guards govern every continuation path, filtering each proposal before any tool call is admitted ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.03 The Loop and the Harness#^fig-vol3-controlplane-arch|figure 1]]).

![[90 Assets/Volume III/10 Agent Harness/Fig Vol3 Controlplane Arch 5693eb8107.svg]]

Figure 1: **The Prototype Loop vs. the Agent Harness**: Panel (a) runs the model’s proposed call directly and keeps all state in the message list, so an outside request has nowhere to land, nothing bounds cumulative spend, and calls that policy would gate run at once. Panel (b) wraps the same loop in a harness whose trajectory record, guarded transitions, control and approval paths, and reserved budgets decide what is admitted. The model only proposes, and the tool layer settles the outcomes of admitted calls.

^fig-vol3-controlplane-arch

In an unmanaged system, execution context is scattered across disparate subsystems: host operating systems track local processes, remote clusters hold asynchronous job handles, storage systems manage workspace leases, and identity providers track credential expirations. Panel (b) consolidates these responsibilities into a single runtime-owned record for each trajectory. Operators, cluster schedulers, and dispatch paths all consult this authoritative record before initiating state changes. While a system may pass budget constraints to the model in the prompt and the model may cooperate with pause requests, actual enforcement remains strictly with the runtime. Relying on model cooperation violates invariant closure; the runtime itself must guarantee that system safety invariants hold under all execution paths (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]).

**Definition 10.1: Agent harness**

***Agent harness*** is the runtime component that owns the agent loop for one trajectory, assembling each model call, interpreting the reply, deciding whether and when each proposed tool call is dispatched, and keeping the record through which outside components inspect, pause, bound, or stop continuation.

1.  **Significance**: It keeps continuation decisions independent of model cooperation while preserving the grants, consumption, and outstanding work those decisions must respect.
2.  **Distinction**: The tool layer mediates calls and tracks their outcomes, and the sandbox bounds execution under its policy. The harness composes those mechanisms with control requests, waiting, scheduling, and lifetime budgets.
3.  **Common pitfall**: Keeping status and pending obligations only in prompt text or inaccessible execution-local state, so a separate control path cannot inspect them or prevent further dispatch.

### One Turn Under Supervision

^sec-vol3-harness-lifecycle-turn

In a single turn of the `r18` repair workflow, the harness mediates every step from the moment the trajectory becomes eligible for another model call, through the model’s proposal to run the regression test against candidate `r18`, to an operator’s pause and subsequent resume ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.03 The Loop and the Harness#^tbl-vol3-harness-control-trace|table 1]]). Across that turn, lifecycle states record whether the trajectory is eligible for continuation (`READY`), actively querying the model (`CALLING_MODEL`), awaiting tool completion (`WAITING_TOOL`), or suspended by an operator (`PAUSED`).

| Event                                             | Harness decision and recorded obligation                                                                                                                                                                                          |
|:--------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| The repair is eligible for another model call     | From `READY`, confirm that no operator request is pending, that shared model capacity is available, and that the budget covers the most this call could cost. Set that amount aside, then enter `CALLING_MODEL` and send the call |
| A complete reply proposes the test of `r18`       | Record what the call actually used. Check the proposed test against the task’s permissions and the remaining budget, set aside the test’s maximum cost, and record the test as running before sending it. Enter `WAITING_TOOL`    |
| The operator requests a pause while the test runs | Stop admitting new work. Keep tracking the running test and its cost, but no longer let its result restart the model; then step through `READY` to `PAUSED` with no moment at which new work could start                          |
| The test result arrives during the pause          | Confirm that the result is genuine and belongs to this test of `r18`. Record its outcome and cost, but leave the trajectory paused and the model’s context unchanged                                                              |
| The operator requests resume                      | Recheck task state, permissions, the recorded evidence, and the budget before returning to `READY`. The scheduler may then admit another call; the result supports only the test and revision it actually checked                 |

Table 1: **A repair trajectory under supervision**: An illustrative control trace. A paused trajectory admits no new work, yet its outstanding job and charges keep an owner.

^tbl-vol3-harness-control-trace

Three features of the trace recur through the rest of the chapter. First, every row that admits work reserves before it sends. Affordability cannot be judged from settled charges alone, because the running test job may still bill and the proposed call may generate up to its full output allowance. The harness therefore reserves each operation’s worst-case liability at admission and reconciles reported usage afterward. Notebook [10.2](https://mlsysbook.ai/vol3/10_agent_harness/10_agent_harness.html#nbk-10-bounded-liability-admission) later prices a call that a check of settled spend admits and this reservation test refuses. Second, the pause and the test result are independent events. The pause stops new admission without stopping the job, and the job’s result settles the job’s outstanding charge without resuming the turn. Third, the reply’s content never acts on its own. A truncated or canceled reply yields nothing to dispatch, a claim of completion triggers an independent check rather than ending the task, and an action that policy requires a human to review waits in a dedicated hold with its own expiry. Each of these needs runtime state that the message list does not have.

The trace also separates the decision to continue from the resources an agent holds. While the repair trajectory sits in `PAUSED` or `WAITING_TOOL`, it keeps its workspace, its cached repository state, and its running test job, but it does not hold a worker thread or a place in the queue for model calls. Because the harness, not the repair loop, decides when the trajectory next calls the model, an interactive trajectory can take the next model-call slot without waiting for the repair to give it up. Which resources a wait releases, and which it keeps, is the subject of supervised waiting ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.07 Supervised Waiting#^sec-vol3-controlplane-yielding|section 10.6]]); how model calls are divided among trajectories is the subject of scheduling ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.09 Scheduling Concurrent Trajectories#^sec-vol3-controlplane-scheduling|section 10.8]]). Before the harness can enforce any of these transitions, waits, or schedules, however, it needs an authoritative data structure where that operational state lives.
