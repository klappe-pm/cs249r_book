# V3-10.06 Control Actions

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-controlplane-signals

The test job for candidate `r18` is still executing when an operator requests a pause. The harness must halt the repair loop’s forward progress without losing the job’s tracking identity, its allocated budget reservation, or the diagnostic evidence it might return. Delaying the pause until the test finishes strips the operator of interactive control over potentially runaway execution. Conversely, declaring the job canceled merely because the trajectory state transitions to `PAUSED` fabricates an execution outcome the runtime has not yet observed.

External control decouples receiving a request from establishing the physical execution state that request demands. When an operator intervenes, the harness authenticates the caller, verifies authority over the target trajectory, and appends the requested directive to `pending_control` while holding the record lock. Because this update occurs under the lock, the admission-ordering invariants established in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-controlplane-statemachine|section 10.4]] fix exactly which operations fall under the request’s scope. The controller acknowledges the hold to the operator only after the update commits to the record (and, once durable execution is in place, to its log). The response delivered to the operator must also distinguish three distinct milestones: request received, new admission stopped, and subsequent confirmation that running work has terminated.

### Admission Boundaries and Active Generation

^sec-vol3-agent-harness-admission-boundaries

When an operator sends a pause or cancel signal while an agent is preparing a model call or stepping through a batch of proposed tool calls, the harness needs well-defined points where it can stop new work before a request leaves the host. Each such checkpoint is a **turn boundary**, evaluated immediately before dispatching an inference call to a foundation model and immediately before invoking any external tool, including each individually admitted call within a proposed parallel batch. The name marks where control takes effect, not a boundary between turns: one turn (one step of the trajectory, counted by ${H}$) contains a turn boundary before its model call and one before each tool call it admits. A pause that lands midway through a batch therefore leaves the calls already sent registered as owned work and withholds the rest. The admission check evaluates control flags under the trajectory record lock, and the release gate serializes its final decision with subsequent control updates. A flag check followed by an uncoordinated send would leave a race window and would not enforce this boundary. The guarantee is local. The boundary fixes which operations were admitted before the request took effect, rather than implying that all work stopped when the operator pressed stop, and it leaves every remaining obligation explicit and inspectable.

Local candidate processing does not have to wait for remote model generation to finish. The foundation-model contract already separates a `CANCELED` reply from a `REJECTED` one and withholds both from dispatch; the harness turns that cancellation into a control action. It can initiate **streaming cancellation**, commanding the serving engine to stop generating an in-progress reply, terminating the invocation’s eligibility to produce an actionable candidate, and retaining partial output solely for bounded diagnosis. A canceled or truncated payload never becomes a dispatchable call, even if a tolerant JSON parser closes its dangling brackets, a valid tool-call prefix appeared before the abort signal, or an apparently complete response arrives after eligibility was withdrawn. The quarantining rule (**[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-status-envelope|The normalized status envelope]]**), an application of invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) to the reply status, holds regardless of how the invocation ended. Late-arriving evidence remains useful only to reconcile accounting usage or explain what the serving engine executed.

↩︎ The distinction between rejected and canceled streamed replies, and the rule that a partial payload never reaches dispatch, are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-streaming-cancellation|Streaming and cancellation]]**.

Output allowances and wall-clock deadlines address different operational risks. An output token ceiling enforces a hard boundary on generated volume under the serving engine’s accounting contract; wall-clock latency, however, also depends on scheduling queues, network stalls, and autoregressive decode throughput. Even under ideal conditions, waiting for a full generation pass introduces substantial delay.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.16 Footnotes#^fn3|³]] At a fixed per-token decode time, a call admitted with output allowance ${K_{\max}}$, generating at ${t_{\text{decode}}}$, can postpone the next turn boundary by approximately

$$
{t_{\text{boundary}}} \approx {K_{\max}} \times {t_{\text{decode}}}
$$

Assuming an optimistic decode latency of 21.075 ms per generated token, the single-accelerator, single-request floor of the estimate in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-per-call-work-estimate|Estimating per-call hardware work]]**, with no queueing or memory-access stalls, a 4,096-token allowance postpones the boundary by roughly 86.3 s. Pause or cancellation logic that passively waits for generation to complete would therefore block for more than a minute, and real serving queues only lengthen the wait. A node that splits the weights across several accelerators lowers the per-token floor but leaves the generation estimate linear in ${K_{\max}}$. Halving the allowance therefore halves the full-allowance generation time at a fixed rate, whereas streaming cancellation removes the dependence on generation length entirely. The harness uses both: turn boundaries govern discrete operation admission, while streaming cancellation stops active generations in flight.

Stopping local execution differs from terminating remote execution. A host deadline determines when the supervisor ceases waiting and initiates intervention; confirming that remote inference has actually stopped requires positive evidence from the service. Under the settlement rule, unconfirmed resource usage remains an outstanding liability rather than an assumed refund.

### Pause and Resume Policy

^sec-vol3-agent-harness-pause-resume-policy

When an operator pauses the repair trajectory while the `r18` test container is already running, stepping the record from `READY` into `PAUSED` ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-controlplane-statemachine|section 10.4]]) stops new admissions but leaves a policy choice over the in-flight job itself. One pause policy permits the active `r18` test to finish under its existing budget limits while holding the repair loop’s continuation; another requests immediate cancellation and records whatever outcome the executor confirms. A pause policy that permits execution to proceed leaves the workspace live and mutable, and the operator interface must reflect this active state. Any administrative inspection that demands quiescence requires positive confirmation that all concurrent writers have stopped, or else an isolated snapshot taken at a declared boundary. When the operator resumes the trajectory, execution proceeds along the guarded transitions defined in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-controlplane-statemachine|section 10.4]]; the pause policy governs only what ran while held, without altering the invariants enforced after resumption. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.06 Control Actions#^tbl-vol3-signal-vocabulary|Table 6]] compares these requested changes to continuation.

| Request                         | Required control effect                                                            | Guarded outcome                                                              |
|:--------------------------------|:-----------------------------------------------------------------------------------|:-----------------------------------------------------------------------------|
| Cancel                          | Hold new admission; request cancellation and account for owned work                | `FINALIZING`, then a recorded cancellation outcome when finalization permits |
| Interrupt with new instructions | Hold affected proposals; validate the instruction and revise its task dependencies | `READY` only when the revised continuation is eligible                       |
| Pause                           | Hold continuation and preserve an owner for outstanding work                       | `READY` to `PAUSED` with no runnable gap                                     |
| Resume                          | Reconcile evidence and recheck current permission and limits                       | `PAUSED` to `READY`, or remain held if guards fail                           |
| Kill                            | Stop admission and invoke available enforcement against active work                | `FINALIZING`, with confirmed and unresolved outcomes recorded                |
| Budget or deadline stop         | Deny further ordinary admission; preserve funded finalization duties               | `FINALIZING`, with the stopping reason and remaining obligations             |

Table 6: **Control requests and their enforced scope**: A control action changes admission and continuation through the guarded lifecycle. Cancellation and termination of already admitted work require separate evidence.

^tbl-vol3-signal-vocabulary

Mid-trajectory user steering demands the same transactional discipline. If an operator injects a steering instruction, such as directing the agent to modify a different target file, the harness cannot append the prompt to the conversation context and assume existing operations adapt. Adding instructions does not retroactively invalidate an already admitted file edit or revoke an active tool approval. Instead, the harness records the instruction, determines which plan steps and proposed actions are superseded, and verifies whether outstanding operations conflict with the revised task.

### Termination and Remaining Obligations

^sec-vol3-agent-harness-termination-obligations

When a runaway child process or wedged tool handler ignores a cooperative cancellation request, waiting for polite shutdown leaves the trajectory holding local compute and credentials indefinitely. A kill request therefore invokes immediate, non-cooperative enforcement. Trajectory-level encapsulation (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-trajectory-encapsulation|10]]) is what makes this enforcement possible: because control requests are recorded independently of model output, the runtime can stop new admission and abort the local work it supervises without waiting on the model or on an external service’s response. When a kill signal arrives, the controller halts local execution, revokes mediated access tokens, and fences off obsolete workers across the execution paths under its control. The sandbox reset contract in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|The reset contract]]** determines which child processes, descendant namespaces, network channels, and allocated resources that enforcement covers. Asynchronous remote work, third-party transactions, and external handles lie beyond direct local process control and demand their own corroborating evidence.

Finalization therefore records confirmed termination separately from unresolved side effects and pending charges, which retain their designated owner under the settlement rule. The operation’s repeat contract determines whether another attempt is safe, and settlement must precede any retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]); an operation identifier alone cannot reveal what the interrupted execution actually modified.

Enforcing external control decouples trajectory continuation from model behavior and frees execution resources. Worker threads and compute slots never remain blocked while an external job or cancellation response is outstanding. By persisting these control directives and outstanding obligations within the trajectory record, the harness safely suspends execution and yields worker resources, admitting continuation only when verified events satisfy the state machine’s guards.
