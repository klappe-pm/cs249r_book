# V3-10.05 Trajectory States

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-controlplane-statemachine

Keeping the trajectory record consistent across asynchronous callbacks and timeouts becomes critical when a tool result arrives after the turn that requested it has already moved on. Suppose the wait deadline for candidate `r18`’s test suite elapses before a result arrives, so the harness records the outcome as unknown and proceeds; one minute later, the test service returns a success report. Both statements reflect reality: the outcome was indeed unknown when the deadline expired, and the tests ultimately passed. The failure occurs if the harness splices that late result into an obsolete turn as though the model had possessed the evidence when selecting its next action. This defect, known as **observation crossing**, conflates the asynchronous physical history of an operation with the causal evidence admitted to a particular continuation. Preventing it requires two mechanisms: guarded transitions that decide when a continuation may advance, and an epoch fence that decides which late results may still inform it ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-agent-harness-late-results|section 10.4.2]]).

A state machine with guarded transitions[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.16 Footnotes#^fn1|¹]] makes every such admission explicit. Beyond resolving observation races, guarded transitions prevent scheduling anomalies, such as mistaking a trajectory held for human approval as idle and erroneously dispatching another model call. The runtime control plane, rather than generated model output, governs all state transitions. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^tbl-vol3-lifecycle-states|Table 3]] defines this supervisory state machine, organized around five live states, a finalizing state through which every exit must pass, and three terminal absorbing outcomes.

| State                             | Meaning                                                                                  | Legal next states                                          |
|:----------------------------------|:-----------------------------------------------------------------------------------------|:-----------------------------------------------------------|
| `READY`                           | Eligible to be considered for the next model call; admission guards still apply.         | `CALLING_MODEL`, `PAUSED`, `FINALIZING`                    |
| `CALLING_MODEL`                   | A model invocation is registered for the current continuation.                           | `READY`, `WAITING_TOOL`, `AWAITING_APPROVAL`, `FINALIZING` |
| `WAITING_TOOL`                    | The continuation awaits a declared set or batch of tool observations.                    | `READY`, `FINALIZING`                                      |
| `AWAITING_APPROVAL`               | An exact proposed action is held; approval and dispatch eligibility remain unresolved.   | `WAITING_TOOL`, `READY`, `FINALIZING`                      |
| `PAUSED`                          | The continuation is held at a local boundary; no new model or tool work is admitted.     | `READY`, `FINALIZING`                                      |
| `FINALIZING`                      | The runtime is checking the exit outcome and resolving or transferring remaining duties. | `COMPLETED`, `FAILED`, `CANCELED`                          |
| `COMPLETED`, `FAILED`, `CANCELED` | The continuation has ended; retained evidence and assigned obligations may remain.       | None                                                       |

Table 3: **Guarded Trajectory States**: An edge permits consideration of a transition, not unconditional execution. Events can update accounting or evidence without changing state.

^tbl-vol3-lifecycle-states

The normal operational cycle follows `READY` → `CALLING_MODEL` → `WAITING_TOOL` → `READY`, tracing through the five live states and guarded transitions shown in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^fig-vol3-harness-trajectory-states|figure 2]]. Proposals requiring review divert into `AWAITING_APPROVAL`. Pause commands transition to `PAUSED` exclusively from `READY`. All termination triggers (completion requests, cancellations, or exhausted budgets) route through `FINALIZING` before reaching the absorbing terminal states (`COMPLETED`, `FAILED`, `CANCELED`). During execution, a model response may produce no admissible action, request task completion, or propose an action requiring operator approval. While the normalized invocation status defined in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^tbl-vol3-invocation-status|Normalized invocation status envelope]]** fixes how the runtime processes individual call outcomes, [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^tbl-vol3-harness-status-routing|table 4]] specifies how each outcome shifts the overall trajectory state. Two names appear in both vocabularies with different meanings: a reply status of `COMPLETED` or `CANCELED` describes one model call, while the terminal states of the same names describe the whole trajectory. A completed reply ends a call, not the task. Only a reply whose status is `COMPLETED` proceeds to tool candidate validation. The harness must never convert a malformed, truncated, or canceled partial stream into an actionable tool invocation only because a parser managed to salvage partial arguments from the payload.

| Reply status and content               | Next state          | Condition or residue                                                          |
|:---------------------------------------|:--------------------|:------------------------------------------------------------------------------|
| `COMPLETED`, validated tool proposal   | `WAITING_TOOL`      | Once its dispatch is admitted                                                 |
| `COMPLETED`, proposal requiring review | `AWAITING_APPROVAL` | When policy requires review of the exact action                               |
| `COMPLETED`, completion request        | `FINALIZING`        | The task’s completion check follows                                           |
| `COMPLETED`, no admissible action      | `READY`             | With an observation saying so                                                 |
| `TRUNCATED`, `REFUSED`, `REJECTED`     | `READY`             | With a bounded observation, unless the task’s refusal policy finalizes        |
| `CANCELED`                             | `READY`             | Under the control hold that caused the cancellation                           |
| `TRANSPORT_FAILURE`, `FAULTED`         | `READY`             | For bounded failure handling while the budget permits, `FINALIZING` otherwise |

Table 4: **Reply Status and Next State**: Every non-completed status returns to a state that admits no dispatch from the failed reply; reservations for failed or faulted calls stay outstanding until usage settles.

^tbl-vol3-harness-status-routing

Action approval introduces a controlled detour to this cycle. An approved action transitions from `AWAITING_APPROVAL` to `WAITING_TOOL` only when its active dispatch guards pass; recording operator approval does not automatically execute the tool. Conversely, a denial, expiration, or operator withdrawal emits a refusal observation back to `READY`.

![[90 Assets/Volume III/10 Agent Harness/Harness Trajectory States 2e6ae90035.svg]]

Figure 2: **Trajectory State Machine**: Five live states, a finalizing state, and three terminal outcomes. The ordinary cycle runs from READY through CALLING_MODEL and WAITING_TOOL back to READY; a proposal that policy requires reviewed is held in AWAITING_APPROVAL, and pause is entered only from READY. Every exit passes through FINALIZING, which stops admission and resolves or transfers remaining duties before an absorbing terminal state. Each arrow is a guarded edge, and events such as a late result or a usage report can update the record’s operation table without changing state.

### Transition Guards and the Admission Check

^sec-vol3-agent-harness-transition-guards

A trajectory sitting in `READY` can still be unsafe to advance if an operator pause arrived a millisecond earlier, a credential expired while the trajectory waited in the queue, or an unresolved prior operation still blocks a dependent mutation. Navigating a legal edge in the state machine is therefore only a necessary condition for progress, not an unconditional right to execute. Before the runtime admits new work, whether invoking a model or dispatching a tool, it evaluates a set of predicates known as the *admission check*: no pending control hold may be active, the context, credentials, and any required action approvals must remain valid, upstream data dependencies must be resolved, and both deadline slack and downstream service capacity must be confirmed. The runtime must also reserve the operation’s bounded financial liability from the task budget without encroaching on the dedicated finalization reserve ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-controlplane-accounting|section 10.9]]), and for tool calls it must verify that arguments are structurally complete. Because system state changes continuously, this evaluation holds only at the instant it executes; an approval granted seconds earlier or a scheduling decision made on a previous tick does not carry forward.

The admission check and its state updates execute as a single atomic transaction. Protected by the trajectory record lock,[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.16 Footnotes#^fn2|²]] the harness evaluates the guard predicates, reserves the required liability, registers the outgoing invocation or attempt ID, marks the expected observation as eligible, and commits the state transition. Releasing the record lock before network transmission, however, opens a brief window before the bytes leave the host in which an operator pause or cancellation can commit. To close that window without holding the record lock across slow network I/O, the runtime passes the admitted request to a release gate that serializes the final release-or-withhold decision with control updates. This gate rechecks current controls and the existing admission without reserving liability twice, withholding transmission if a stop arrived after the record lock was released. Together, these steps enforce the *register-before-send rule*. Registering state before dispatch ensures that even an immediate response never arrives before the local record exists to receive it. Conversely, transmitting requests strictly outside the critical section prevents slow network I/O, stalled inference endpoints, or lagging tool services from blocking concurrent control actions, scheduler ticks, or arriving results from other workers.

External control requests acquire this same monitor lock, so stops and admissions are strictly serialized under an *admission-order rule*. If a pause, cancellation, or kill command commits before an admission check runs, it immediately blocks new outbound work. If admission commits first, the operation becomes owned work with a registered identity and reservation, and a later control cannot erase or refund that reservation on intent alone. Although the release gate can still withhold a definitely unsent attempt, settling that attempt requires authoritative evidence that release did not occur and that no remote liability remains. A volatile withheld flag does not survive a host crash, and once a packet may have left the host, a cancellation request cannot establish `not_sent` without remote evidence. Tool-side idempotency and stale-lease fencing therefore still require the endpoint contracts detailed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|Operation identity and endpoint contracts]]**.

To coordinate concurrent state access without heavyweight distributed locks, the harness pairs optimistic concurrency validation with epoch fencing. The `record_version` field detects competing updates at the point of commit, implementing the validation step of optimistic concurrency control ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.15 Source References#^ref-kung1981optimistic|Kung and Robinson 1981]]). In parallel, increments to `control_epoch` fence out stale asynchronous responses, the same generation-number check that the tool layer applies to superseded workers at the endpoint. Here the fenced party is an observation: a response stamped with an old epoch cannot advance the current continuation, however well formed it is. These control plane identifiers operate alongside, rather than replace, logical operation identifiers and transport attempt counters. A network retry generates a new attempt ID under the same logical operation, whereas an operator interruption bumps the control epoch to invalidate pending replies without erasing the operation’s entry in the operation table. The record now carries several counters, and each advances on different events and rejects a different kind of stale input ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^tbl-vol3-harness-counters|table 5]]).

↩︎ Epoch fencing of superseded workers at the mutating resource is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|Operation identity and endpoint contracts]]**.

| Counter               | Advances when                                                                                                                                                                 | What a stale value rejects                                                 |
|:----------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------|
| `record_version`      | Any committed update to the trajectory record                                                                                                                                 | A decision made on a view of the record that has since changed             |
| `control_epoch`       | A wait deadline, an operator interruption, or a plan revision withdraws a continuation’s claim on outstanding results                                                         | A result registered under an earlier epoch, as input to the current turn   |
| Plan revision         | The harness adopts a revised live plan                                                                                                                                        | A proposal or held approval formed against the superseded plan             |
| Held-proposal version | The harness records a new or changed held proposal for approval ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^sec-vol3-controlplane-hitl\|section 10.7]]) | An approval decision for a different version of the proposal               |
| Attempt ID            | A transport retry of the same logical operation                                                                                                                               | Nothing by itself; it lets late evidence name the attempt that produced it |

Table 5: **Trajectory Record Counters**: Each counter advances on its own events and rejects its own kind of stale input, so none can stand in for another.

^tbl-vol3-harness-counters

[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^lst-vol3-guarded-transition|Listing 1]] expresses these rules as a single supervisory procedure. The legal edges match [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^tbl-vol3-lifecycle-states|table 3]], and any edge without a registered guard predicate is rejected by default. The caller provides the `record_version` it observed when formulating its transition request; a concurrent modification by another worker causes the version check to fail. Similarly, duplicate deliveries of an event fail either the version check or the edge guard, guaranteeing that no action is admitted twice.

``` python
LIVE = {"READY", "CALLING_MODEL", "WAITING_TOOL",
        "AWAITING_APPROVAL", "PAUSED"}
LEGAL = {("READY", "CALLING_MODEL"), ("READY", "PAUSED"),
         ("CALLING_MODEL", "READY"), ("CALLING_MODEL", "WAITING_TOOL"),
         ("CALLING_MODEL", "AWAITING_APPROVAL"), ("WAITING_TOOL", "READY"),
         ("AWAITING_APPROVAL", "WAITING_TOOL"),
         ("AWAITING_APPROVAL", "READY"), ("PAUSED", "READY")}
LEGAL |= {(s, "FINALIZING") for s in LIVE}
LEGAL |= {("FINALIZING", t) for t in ("COMPLETED", "FAILED", "CANCELED")}
# GUARDS maps each edge to a predicate over (record, decision).

def transition(rec, new_state, decision, admit=None):
    with rec.lock:                            # the local decision only
        edge = (rec.state, new_state)
        guard = GUARDS.get(edge)              # no guard, no permission
        if edge not in LEGAL or guard is None or not guard(rec, decision):
            raise IllegalTransition(edge, decision.id)
        if decision.seen_version != rec.record_version:
            raise StaleDecision(decision.id)  # a competing update won
        if admit is not None:
            admit(rec)                        # reserve, register, set eligibility
        rec.state = new_state
        rec.record_version += 1
        rec.history.append((edge, decision.id, rec.record_version))
    # The caller passes admitted work to the serialized release gate outside this lock.
```

Listing 1: **Guarded Transitions**: Every state change checks the legal edge, its explicit guard, and the record version under the record lock, then performs admission bookkeeping before the state changes; the admitted request is sent only after the lock is released.

^lst-vol3-guarded-transition

Here, the guard registered on the `READY` → `CALLING_MODEL` edge executes the complete admission check, while `admit` performs the liability reservations and bookkeeping required by the register-before-send rule. Because the monitor lock protects only in-memory lookups, state updates, and an array append, lock contention remains negligible compared to the hundreds of milliseconds consumed by remote inference or tool execution.

### Late Results and Observation Eligibility

^sec-vol3-agent-harness-late-results

When an asynchronous tool result arrives, the harness must reconcile financial and physical state without corrupting the prompt history of an active turn. Upon reception, the runtime authenticates the payload and correlates its task identifier, logical operation ID, and attempt number against the trajectory record. Mismatched or unauthenticated messages are logged for audit and dropped. Valid results immediately update the trajectory’s operation table: the runtime records raw execution evidence and converts reserved charges into settled resource usage.

However, updating the operation table does not imply that the result belongs in the model’s current prompt context. As [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^lst-vol3-harness-on-result|listing 2]] shows, the runtime splits incoming evidence into two separate paths: settlement in the operation table, which every authentic result receives, and epoch-fenced observation staging. Every authentic result records evidence and settles any confirmed usage. An observation, however, is staged for immediate prompt injection only if its call ID remains registered in `observation_eligible_calls` and the epoch recorded with the call at registration matches the active `control_epoch`. The remote service never sees the epoch; when the harness correlates the result, it looks up the epoch by call ID and attaches it to the local result envelope as `result.epoch`. This field comes from the registration record, not the remote payload. The two checks fail in different ways. The eligibility set is the per-call statement of which results the current wait expects, and removing an entry after staging is what stops a redelivery from being staged twice. The epoch is a bulk fence: a timeout or operator interruption advances it once and thereby invalidates every call registered under the old epoch, including any whose removal from the set was missed. If an operation timed out or an operator intervened, its recorded epoch is obsolete. The harness settles the financial balance but refuses to inject the result into the current turn, which eliminates observation crossing. Should that late evidence prove relevant to future turns, the runtime can re-evaluate and stage it during subsequent guarded context assembly. Staging a result does not by itself end the wait. A declared **wait policy** establishes the criteria required to return from `WAITING_TOOL` to `READY`, and the handler requests that transition only when the policy is satisfied.

``` python
def on_tool_result(rec, result):
    if not authenticate(result):
        return audit(rec, "unauthenticated_result", result)
    with rec.lock:
        op = rec.operation_table.get(result.operation_id)
        if op is None or result.attempt_id not in op.attempts:
            return audit(rec, "unknown_operation", result)
        if not op.record_evidence(result):  # already recorded: duplicate
            return
        settle(rec, op, result.usage)       # reserved -> actual; rest stays owed
        eligible = (result.call_id in rec.observation_eligible_calls
                    and result.epoch == rec.control_epoch)
        if eligible:
            rec.observation_eligible_calls.discard(result.call_id)
            stage_observation(rec, result)  # for the current wait only
        rec.record_version += 1
        seen = rec.record_version
    if eligible and wait_policy_satisfied(rec):  # the guard rechecks it
        transition(rec, "READY", Decision(result.id, seen))
```

Listing 2: **Routing a Tool Result**: Authenticated evidence always reaches the operation table and settles usage, while only a currently eligible result under the current control epoch is staged for the waiting continuation.

^lst-vol3-harness-on-result

Systems typically implement one of four wait policies: all required results arrive, an acceptable partial batch completes, a wait deadline expires, or an operator triggers an explicit withdrawal. The trajectory record distinguishes confirmed evidence from unreturned, unresolved calls. In the candidate `r18` repair scenario, a timeout records that the outcome was unknown at the deadline; it cannot justify inferring that the test suite failed. When the test service eventually reports that candidate `r18` passed, the operation table records that verified outcome with its exact scope. A timeout likewise never authorizes an uncoordinated re-execution of a non-idempotent operation. Dependent actions must still satisfy all guard preconditions and adhere to the tool’s mutation safety contract.

### Pause Entry and Outstanding Work

^sec-vol3-agent-harness-pause-entry

When a pause command arrives while a trajectory is in `CALLING_MODEL` or `WAITING_TOOL`, jumping straight into `PAUSED` would either orphan the in-flight model stream and remote tool job or leave their state transitions ambiguous. The state machine therefore permits entry into `PAUSED` exclusively from `READY`. If a pause command arrives mid-call or mid-wait, the runtime asserts a `pending_control` hold. The hold blocks the admission of any subsequent work, revokes observation eligibility for active model streams, invalidates any pending approval requests, and ends the active observation wait. For a trajectory in `WAITING_TOOL`, this is the explicit-withdrawal wait policy, and it is what permits the `WAITING_TOOL` → `READY` step. If policy dictates, the control plane issues cancellation requests to remote workers; under the settlement rule, these operations remain registered in the operation table until remote confirmation arrives. Any partial token stream received from a canceled model call is preserved solely for diagnostic logging, never stitched together to form a valid dispatch.

Once these local eligibility revocations are logged, the trajectory steps through `READY` directly into `PAUSED` under the existing admission hold. Because the lock prevents concurrent scheduling during this step-down, no runnable window opens between the transitions. Entering `PAUSED` halts continuation progress, ensuring that neither pending responses nor held proposals can advance the continuation. However, background tools already running in external systems may continue their physical execution. For example, the remote test execution for candidate `r18` can complete while the trajectory remains paused; its completion payload updates the operation table and settles the reserved charge without triggering a new inference cycle.

Resuming execution requires a guarded `PAUSED` → `READY` transition, followed by a brand-new admission check that reconciles all evidence recorded in the operation table during the pause. Resumption is not an automated rollback of pause-time revocations, so state withdrawn during a pause is never restored. Expired authorization tokens remain expired, withdrawn approvals require fresh operator authorization, and canceled partial responses stay abandoned. Any earlier operation that remains unconfirmed continues to block its dependent actions, even if unrelated steps become eligible. Meanwhile, physical resource retention operates under independent lifecycles: sandboxed workspace leases, buffer allocations, compute reservations, and model context caches persist or expire according to their respective lifetime policies rather than the trajectory’s instantaneous state.

### Finalization and Remaining Duties

^sec-vol3-agent-harness-finalization-duties

Ending a run the instant the model claims completion, an operator cancels, or the budget runs out would skip independent acceptance checks, leave delegated credentials active, and abandon unsettled background jobs. Every exit from the live states therefore passes through `FINALIZING` before reaching a terminal state ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^fig-vol3-harness-trajectory-states|figure 2]]). Upon entering this state, the runtime immediately suspends standard work admission, records the exit reason, revokes unused delegation authority where supported, and triggers the task completion check when completion is claimed. An end-of-turn token emitted by a model merely requests this validation; genuine task completion requires an independent completion check, such as the task contract’s acceptance tests, run outside the model. All finalization checks and mandatory cleanup routines draw from their dedicated, pre-funded reserve.

During finalization, the control plane may block to await pending results, report verification failures, or hand off outstanding cancellation, billing reconciliation, and resource reclamation tasks to an external supervisor. The transition guard into any terminal state requires that every outstanding obligation be either definitively settled or explicitly transferred to an accepting upstream owner. Clearing an unresolved task from a local tracking set violates the guard. To effect a legitimate transfer, the runtime must transmit complete metadata (operation IDs, recorded evidence, and budget reservations), allowing the recipient service to assume supervisory responsibility.

All terminal states (`COMPLETED`, `FAILED`, and `CANCELED`) are strictly absorbing. Once a trajectory enters a terminal state, its continuation terminates permanently. Late-arriving tool results or charge settlements can still update archived historical records through the designated supervisory owner, but no event can transition the continuation back to `READY`. Resuming an investigation or re-attempting a task requires instantiating a fresh trajectory with a new identifier linked back to the prior run. Within this architecture, `COMPLETED` denotes solely that the programmatic completion criteria configured for the harness were met. Whether those criteria demonstrate true task competence is an empirical systems question addressed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.02 The Evaluation Problem#^sec-vol3-evaluation-problem|The Evaluation Problem]]**.

**Checkpoint 10.1: Trajectory record and guarded states**

**Late test evidence**: The wait for `r18` times out, then a success result arrives during `PAUSED`. Decide which structure changes, `observation_eligible_calls` or the `operation_table`, and name the guarded step that must run before the next model call can use the result.

**Pause boundary**: Write the sequence of record updates that takes `WAITING_TOOL` through `READY` to `PAUSED`. At which point is new admission blocked, and which entries stay in the operation table?

**Admission race**: Two schedulers both read `record_version` 41 and try to admit a model call. Using [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^lst-vol3-guarded-transition|listing 1]], which check rejects the loser, and what has the loser reserved or sent by then?

**Terminal responsibility**: Cancellation of a paid job is unconfirmed when the continuation ends. List what the terminal guard requires before `CANCELED`, and who owns the job’s charge afterward.

Guarded transitions keep every update to the record causally consistent under network delays, tool timeouts, and concurrent interventions. They describe pause entry, however, only from the record’s side. An operator who presses pause needs more: an authenticated way to register the request, a bound on how long it takes effect while a model call is still generating, and a distinction between a pause, a cancellation, and a kill that leaves outstanding work owned in each case.
