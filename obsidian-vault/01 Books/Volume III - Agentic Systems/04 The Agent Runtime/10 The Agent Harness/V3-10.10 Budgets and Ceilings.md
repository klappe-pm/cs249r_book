# V3-10.10 Budgets and Ceilings

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-controlplane-accounting

A repair trajectory that receives its fair share of model service on every round can still loop across dozens of failing patch attempts without converging, or launch a new model generation when an unbilled test job in flight has already committed the rest of its allowance. Fair scheduling and provider quotas govern how a trajectory shares cluster capacity at a single step, not how much total work one trajectory may accumulate or how much uncommitted liability it carries while background jobs run. Bounding cumulative consumption therefore requires a multi-dimensional trajectory budget enforced at admission against worst-case in-flight liabilities and sized from empirical task outcomes.

### Turn, Token, Time, and Dollar Budgets

^sec-vol3-harness-multidim-budgets

When the repair agent generates a candidate code patch that fails its regression test, the model often responds by proposing a slight variant, followed by another permutation and eventually a broader diagnostic routine that also fails. Each failure appends an error trace to the conversational context while every individual tool call remains syntactically well formed and stays within per-invocation token and compute limits. The trajectory therefore yields cleanly at every tool boundary, receives its scheduled turn on the inference server, and satisfies every local admission check, yet dozens of turns later this **runaway retry loop** has burned through substantial cloud and inference budgets while making zero measurable progress toward resolving the defect. In [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^fig-vol3-epistemic-attractor-cycle|figure 4]], failing tests append repeated error observations to the context until turn-completion proposals vanish. The same figure shows the external budget that halts the cycle at the admission boundary and moves the trajectory into `FINALIZING` once the next call’s liability no longer fits the allowance.

Ending such a loop is the harness’s responsibility. As failure outputs accumulate in the prompt context, they dilute the original system instructions and task specifications. Under severe context dilution, model generations that terminate the trajectory become increasingly rare. Prompt-level guardrails, such as injecting notices about remaining funds or requesting that the model self-regulate under a cost ceiling, offer probabilistic nudges rather than deterministic bounds, and their effect weakens as the context fills with repeated stack traces. Because an errant model remains syntactically coherent and locally compliant while failing globally, trajectory bounds must reside within the external supervisory control plane (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-trajectory-encapsulation|10]]). Deciding whether an agent has stalled requires complex semantic heuristics, but an external budget deterministically stops further ordinary admission when the allowance is exhausted.

↩︎ Attention dilution as stale observations and superseded logs accumulate in the working context is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^sec-vol3-context-engineering-usable-context-test|Testing usable working context]]**.

![[90 Assets/Volume III/10 Agent Harness/Fig Vol3 Epistemic Attractor Cycle cffd204461.svg]]

Figure 4: **A Runaway Loop and the Budget That Ends It**: A failing targeted test appends error observations to the context, completion requests become rare, and each retry is well formed and within per-call limits, so the loop continues without progress. The harness budget, kept outside the context, applies the reservation test at every admission. When a call does not fit or the deadline has passed, admission is refused and the trajectory enters FINALIZING, which settles or transfers its outstanding work.

^fig-vol3-epistemic-attractor-cycle

To constrain total resource consumption, the harness establishes a multi-dimensional per-trajectory **budget**, the vector

$$
{\mathbf{B}} = \langle {H_{\max}},\ {N_{\max}},\ {T_{\max}},\ {C_{\max}} \rangle
$$

where the components establish formal allowances on execution turns (${H_{\max}}$), cumulative tokens (${N_{\max}}$), elapsed wall-clock time (${T_{\max}}$), and total financial cost (${C_{\max}}$). The harness configuration must unambiguously define what increments each meter: admitted model invocations increment the turn counter, effective input prompt tokens plus generated output tokens increment the token counter, and direct API charges, sandboxed execution fees, and paid third-party tool usage increment the dollar counter. Retried operations, network reconnects, and failed invocations consume real resources and must be billed against these totals. Production harnesses frequently extend this vector with additional domain-specific limits, such as sandbox disk allocations or maximum external API query counts.

Each dimension governs a distinct operational constraint. A trajectory with very few turns can rapidly exhaust financial limits through large-context reasoning models, while an inexpensive agent can tie up execution sandboxes across long asynchronous polling delays. Unlike consumable token or dollar allowances, elapsed time represents a monotonically advancing wall-clock deadline measured from task initiation. Network delays, sandboxed compilation phases, human approval holds, and backoff pauses all advance this deadline unless the task contract explicitly provides a paused clock. When the primary execution deadline expires, the harness halts the admission of new exploratory work while supervising in-flight background operations. Post-execution finalization requires its own separately allocated time allowance and reserved funding; an expired exploration deadline must never trigger an unconstrained cleanup phase that runs indefinitely.

The harness may safely expose current budget metrics to the model, enabling the agent to adjust its planning strategy toward cheaper alternatives. However, the model must never possess the authority to modify accounting records, release reservations, or exempt its own calls from admission gates. This separation allows cooperative optimization while guaranteeing that system bounds remain strictly invariant to model behavior.

### Reservation and Settlement

^sec-vol3-agent-harness-reservation-settlement

If the harness checks only settled invoices before admitting a new model call, a trajectory with an unbilled test job in flight and a 4,096-token generation ahead can pass admission and then exceed its dollar ceiling once both bills arrive. A budget serves as a hard ceiling only when the admission gate sets aside the worst-case cost of in-flight and proposed work before authorizing new liabilities.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.16 Footnotes#^fn7|⁷]] The amount set aside for an admitted operation is its **budget reservation**, the operation’s maximum additional charge, withheld from the allowance at admission and released only when evidence settles the operation. The chapter keeps the word escrow for held proposals awaiting approval, which hold an action rather than an amount. Test-time search reserved each candidate’s maximum completion before dispatch and kept unsettled reservations against its quota; the harness extends that discipline from one search to every operation of the trajectory, including tool jobs and the finalization reserve.

↩︎ Reserving a candidate’s maximum completion before dispatch, within a task-wide quota, is established in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.07 Bounded Search#^sec-vol3-test-time-compute-admission-limits|Reserving budget before admitting work]]**.

**Definition 10.4: Bounded-liability admission**

***Bounded-liability admission*** is the harness rule that admits a new operation only when, in every cumulative budget dimension, actual consumption plus outstanding reservations plus the operation’s maximum additional charge plus the protected finalization reserve fits within the allowance.

1.  **Significance**: It turns a budget that is merely reported into an enforceable upper bound on per-attempt expenditure (the numerator of cost per accepted task, **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**) while guaranteeing that essential post-task verification checks remain fully funded.
2.  **Distinction**: Whereas a simple spend check merely compares settled invoices against the allowance, bounded-liability admission reserves capacity for in-flight requests and charges the worst-case ceiling of the pending operation.
3.  **Common pitfall**: Prematurely releasing a reservation upon a network timeout or client-side cancellation before upstream providers settle actual usage. This error exposes uncommitted budget that concurrent operations can claim before delayed billing charges arrive.

For each cumulative resource dimension, the admission test is

$$
\text{actual consumption} + \text{outstanding reservations} + \text{proposed bounded liability} + \text{protected finalization reserve} \leq \text{allowance} \tag{1}
$$

^eq-vol3-bounded-liability-admission

The harness evaluates this inequality componentwise across all cumulative resource dimensions, while evaluating wall-clock deadlines through a separate timing guard. The term for outstanding reservations encompasses all admitted but unsettled operations, including concurrent inference requests and active paid tools. The protected finalization reserve isolates dedicated funding for validation runs, report generation, and environment teardown, preventing exploratory steps from exhausting the funds needed to verify final results. When the trajectory transitions into finalization, the harness reallocates the necessary portion of this protected reserve into active operation reservations, avoiding duplicate accounting. Because the inequality is the budget clause of the admission check, it runs under the record lock with the rest of that check, and the register-before-send rule keeps two concurrent subtasks from reading the same uncommitted headroom and spending it twice.

[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^lst-vol3-harness-turn|Listing 3]] assembles the pieces introduced so far into one turn: the guarded transition of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^lst-vol3-guarded-transition|listing 1]], the reservation that admission makes, the status routing of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^tbl-vol3-harness-status-routing|table 4]], the approval hold, and register-before-send for tool calls. The reservation is made inside the guarded transition into `CALLING_MODEL`, so an unaffordable call is refused before any request leaves the host. Usage settles the reservation after the reply, and the reply’s status decides the next state before any content can become a tool call. Admission never depends on a charge discovered after the call.

``` python
def run_turn(rec):
    call = new_invocation(rec)
    liability = bound_call(rec.limits)        # full input + output allowance
    transition(rec, "CALLING_MODEL", Decision(call.id, rec.record_version),
               admit=lambda r: reserve(r, call, liability))  # admission test
    reply = invoke_model(rec.context(), rec.limits, call.id)  # lock released
    settle(rec, call, reply.usage)            # missing usage stays reserved
    nxt = Decision(call.id, rec.record_version)
    if reply.status != "COMPLETED":           # truncated, canceled, refused, ...
        return transition(rec, route_status(rec, reply), nxt)  # never dispatched
    proposal = validate(rec, reply)           # schema, epoch, authority
    if proposal.kind == "complete":
        return transition(rec, "FINALIZING", nxt)   # completion check follows
    if proposal.kind == "none":
        return transition(rec, "READY", nxt)
    if needs_approval(rec, proposal):
        return transition(rec, "AWAITING_APPROVAL", nxt,
                          admit=lambda r: hold(r, proposal))
    transition(rec, "WAITING_TOOL", nxt,
               admit=lambda r: reserve_and_register(r, proposal.calls))
    dispatch(proposal.calls)                  # serialized release gate; already reserved
```

Listing 3: **One Admitted Turn**: The harness reserves the call’s bounded liability inside the guarded transition, settles from reported usage, routes every non-completed status away from dispatch, and reserves and registers tool calls before sending them.

^lst-vol3-harness-turn

The `reserve` step evaluates [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^eq-vol3-bounded-liability-admission|equation 1]] and aborts the state transition whenever the proposed invocation exceeds available headroom; `route_status` maps terminal inference conditions according to [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^tbl-vol3-harness-status-routing|table 4]]. For clarity, the listing abstracts batched invocation checks and multi-step approval lifecycles. Its `invoke_model` and `dispatch` helpers also include the serialized release gate: they recheck the admitted operation against current controls before release, retain ownership and liability if release is withheld, and exit through guarded refusal or control handling without returning a fabricated remote reply. These helpers perform no second reservation and keep slow network I/O outside the record lock. This listing describes live-host supervision; crash reconstruction requires the durable evidence developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution#^sec-vol3-durable-execution|Durable Execution]]**.

A control action can also commit while `run_turn` is blocked in `invoke_model`, because that call runs outside the lock. The control path then performs the pause entry itself: it withdraws the call’s eligibility, cancels the stream if policy says so, and steps the record through `READY` to `PAUSED`. When `invoke_model` returns, `settle` still records the call’s usage, but the next `transition` starts from `PAUSED`. Every edge it could request from there fails: the edges to `WAITING_TOOL` and `AWAITING_APPROVAL` are not legal from `PAUSED`, and the guards on the legal ones, to `READY` and `FINALIZING`, admit only the control path’s own resume or stop decisions. The transition raises `IllegalTransition`, and the reply is kept only as diagnostic evidence, as a `CANCELED` reply would be.

For a model call, the proposed bounded liability prices every input token at the undiscounted input rate ${c_{\text{in}}}$, cached or not, and the full output allowance ${K_{\max}}$ at the output rate ${c_{\text{out}}}$:

$$
\text{liability} = {c_{\text{in}}}\, {S} + {c_{\text{out}}}\, {K_{\max}} \tag{2}
$$

^eq-vol3-harness-liability

Here ${S}$ counts the whole prompt, unlike the uncached-only count used for settled charges in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-harness-metered-accounting|section 10.9.3]]. Pricing the prompt at full rate keeps the bound valid when an expected cache hit fails to materialize, and charging the whole allowance keeps it valid when the model generates up to its cap; settlement later replaces both worst cases with reported usage.

Even when the unreserved balance remains strictly positive, it may prove insufficient to cover the maximum liability of the next operation. A naive spend check admits such a call on the basis of past settled invoices, only to exceed the budget ceiling once the provider bills the resulting tokens. While shrinking the requested maximum output tokens can lower the call’s worst-case liability, this optimization succeeds only if prompt tokens and outstanding tool charges still fit within the margin. External paid tools that lack enforceable execution timeouts or bounded billing tiers cannot provide a finite liability ceiling either. Under a strict enforcement policy, the harness must either reject such open-ended tools outright, substitute bounded proxies, or explicitly declare an approximate threshold that tolerates financial overshoot. Enforcing a client-side network timeout does not provide an immutable cost ceiling because the remote provider may continue billing until its own worker processes finish.

**Napkin Math 10.2: A call the spend check admits**

**Problem**: A repair trajectory has a \$3.50 allowance, \$2.58 of settled spend, a \$0.50 reservation on its unsettled test job, and a \$0.30 finalization reserve. The next model call carries 50,000 input tokens and a 4,096-token output allowance, reserved at hypothetical prices of \$3 and \$15 per million input and output tokens. Should the harness admit it?

**Math**: The call’s bounded liability is \$0.15 of input plus \$0.06 of output, \$0.21 in all. A spend check sees \$3.50 − \$2.58 = \$0.92 of headroom. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^eq-vol3-bounded-liability-admission|Equation 1]] subtracts the reservation and the finalization reserve as well, leaving \$0.12.

**Result**: The spend check admits the call; bounded-liability admission refuses it. Admitted, the call would leave the final checks \$0.09 short once the test settles in full.

**Systems insight**: Input is 70.9 percent of this call’s liability, so trimming the output allowance barely helps. The call fits only if its input falls to about 19,500 tokens, through compaction, or if the test job settles and releases part of its reservation. Every \$0.10 of unsettled liability removes about 33,300 input tokens from what the next call may carry, which is why settling promptly from usage evidence is worth more than a smaller output cap.

![[90 Assets/Volume III/10 Agent Harness/Vol3 Harness Admission Margin 853ace6cfc.svg]]

A dashed vertical line marks the next call at 0.21 dollars, inside the upper bar and beyond the end of the lower bar.*

*The spend check sees room for the call; after reservations, it no longer fits.*

Settlement replaces the reservation with verified consumption once the harness receives an authenticated, correlated usage report from the provider. An incremental report moves confirmed charges into the settled meter while the remaining liability stays reserved, and only terminal billing evidence releases the residual; a dropped stream, missing telemetry, or client-side timeout shows nothing about what the provider billed. Cached input is reserved at the full rate unless the provider contractually guarantees the hit, and it is settled at the cached rate the usage report shows. Canceling a stream early can likewise lower the eventual output charge, but admission of later work cannot count on a cancellation that has not yet settled. The ceiling holds because every request passes the check (complete mediation ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.15 Source References#^ref-saltzer1975|Saltzer and Schroeder 1975]])), every reservation is a worst-case bound, and only verified execution records settle it.

### Metered Accounting and Prefix Cache Reuse

^sec-vol3-harness-metered-accounting

Once a model call or tool job finishes, the harness replaces its worst-case reservation with the actual bill, and that bill depends heavily on whether the serving engine reused cached prefix state or had to reprocess the prompt from scratch. Inference providers bill token usage in distinct categories: uncached input tokens (${n_{\text{in}}}$), cached prompt tokens (${n_{\text{cache}}}$), and generated output tokens (${K}$). For any completed turn ${t}$, the harness updates the accumulated cost according to:

$$
{C}^{({t})} = {C}^{({t}-1)} + {c_{\text{in}}}\, {n_{\text{in}}}^{({t})} + {c_{\text{cache}}}\, {n_{\text{cache}}}^{({t})} + {c_{\text{out}}}\, {K}^{({t})} + \sum_{j} {c_{\text{tool}}}({a}_{t,j})
$$

where input token categories are mutually disjoint, unit pricing matches token dimensions, and each tool execution charge ${c_{\text{tool}}}$ is counted exactly once. This equation defines how in-flight reservations turn into settled charges against the budget.

Metering the append-only context workload of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-trajectory-cost-accumulation|How multi-turn history drives up input cost]]** against a full budget vector shows how a cache miss shifts which allowance dimension leads (notebook [10.3](https://mlsysbook.ai/vol3/10_agent_harness/10_agent_harness.html#nbk-10-multi-dimensional-accounting-and-prefix-cache)). The calculation assumes that the serving engine reuses KV-cache state for the system prompt and prior turns and bills each newly appended observation and tool output as uncached input. That reuse is not guaranteed by append-only text alone; the matching cache state must still be resident on the worker that serves the next call.

**Napkin Math 10.3: Metering a trajectory against its budget**

**Problem**: The coding workload has completed 30 turns under hypothetical allowances of 40 turns, 2 million effective input-plus-output tokens, 900 s elapsed, and \$3.50. The clock reads 460 s. Assume all usage is settled, no paid-tool charges, and prices of \$3 per million uncached input tokens, \$0.30 per million cached input tokens, and \$15 per million output tokens. Which allowance has the largest current used fraction in the reuse and no-reuse cases?

**Math**: With a base prompt of 8,000 tokens, 1,500 tokens appended per turn, and 200 output tokens per turn, **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 2.9]]** gives 892,500 input tokens over the trajectory, 898,500 with output. Under prefix reuse, every turn’s earlier prefix is billed as cached input, 841,000 tokens, so the model charge is \$0.50. Billed entirely as uncached input, the same tokens cost \$2.77.

**Result**: With reuse, the trajectory has used 75 percent of its turns, 44.9 percent of its tokens, 51.1 percent of its time, and 14.2 percent of its dollars, so turns lead. Without reuse, dollars lead at 79.1 percent.

**Systems insight**: The leading dimension changes when caching fails. The token meter counts cached input in full and cannot see the change; the dollar meter rises 5.5 times for the same tokens. A harness that sizes ${C_{\max}}$ from the cached bill will therefore meet its dollar ceiling first on exactly the trajectories that miss the cache. Reserving at the undiscounted rate and sizing the dollar allowance from the no-reuse cost keeps a cache miss from turning into a budget stop; what reuse is worth across a workload is priced in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.04 Context Reuse and Retry Budgets#^sec-vol3-agent-economics-prefix-cache-value|Pricing prefix cache hits]]**.

### Staged Budget Escalation and Enforcement

^sec-vol3-harness-staged-escalation

If a trajectory runs at full scope until the admission gate abruptly refuses its next call, it often halts mid-investigation without compacting its findings, narrowing its tool use, or producing a useful diagnostic summary. A well-designed harness therefore introduces progressive interventions before the admission gate forcibly shuts down exploratory execution. Its primary warning signal is the maximum consumed fraction across all active budget dimensions, $\max({\rho_H}, {\rho_N}, {\rho_T}, {\rho_C})$, computed with unbilled reservations included rather than from settled invoices alone. The wall-clock timer yields the temporal fraction ${\rho_T}$. This multi-dimensional indicator steers adaptive interventions, even as the underlying gate continues to evaluate bounded liabilities independently across each axis.

[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^tbl-vol3-budget-triggers|Table 9]] delineates the progressive escalation stages that precede hard enforcement. A deployment policy triggers each stage from the admission terms themselves rather than from a fixed percentage of the allowance, because a fixed percentage ignores how large the next step is. Steering begins when the remaining headroom can fund only a few more calls at their current bounded liability, and finalization begins when the next call’s liability no longer fits beside the finalization reserve. The stages change how a trajectory approaches a hard ceiling, not which stopping rule prevails; a hard ceiling still takes precedence over satisficing and marginal stopping, the order established for search in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.07 Bounded Search#^sec-vol3-test-time-compute-admission-limits|Reserving budget before admitting work]]**.

| Stage        | Harness action                                                                            | Scope and limitation                                                                                 |
|:-------------|:------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------|
| **Steer**    | Supply the remaining allowance and ask for a smaller next step or final report            | Changes the model’s information, not the admission bound                                             |
| **Restrict** | Narrow specific grants or disable new delegation                                          | Blocks newly disallowed admissions; retained authority and outstanding work still require accounting |
| **Finalize** | Stop ordinary continuation and use protected resources for checks, reporting, and cleanup | Does not erase charges or effects already in flight; unresolved duties retain an owner               |

Table 9: **Budget Intervention Stages**: Adaptations can preserve useful work near an allowance, but every admitted operation still passes the bounded-liability test.

^tbl-vol3-budget-triggers

Each intervention during the steering and restriction stages carries its own accounting and caching trade-offs. Context compaction can reclaim token headroom when sufficient budget remains to execute it without destroying critical state, although invoking a summarization model consumes additional tokens of its own and discards detail. Narrowing authority is similarly partial. Downgrading an agent to read-only tools prevents irreversible state mutations while still allowing expensive retrieval queries or context leaks to external APIs. Revoking delegation privileges stops new child trajectories without canceling background subtasks that are already active or releasing their reserved liabilities. Even how the harness enforces a tool restriction matters for cost, because dynamically mutating the tool schema inside the prompt invalidates cached prefix state from the modification point onward, which trades prefix-cache reuse for reduced tool exposure unless the restriction is enforced at the harness admission gate instead.

↩︎ The prompt reduction and information loss of each compaction method are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^sec-vol3-context-engineering-compaction-method|Choosing a compaction method]]**.

When a trajectory enters the finalization stage due to budget exhaustion, the system must not compromise its validation standards. If an expensive regression test remains in-flight, its reservation must remain held until final usage telemetry settles the charge. The final diagnostic report must accurately report candidate `r18` and record which validation suites completed successfully, rather than treating an early unit test pass as substitute verification for incomplete end-to-end checks.

### Choosing a Ceiling from Task Evidence

^sec-vol3-agent-harness-choosing-ceiling

Set a trajectory ceiling too low and the harness cuts off repairs that would have succeeded in a few more turns; set it too high and failed runs burn through the extra allowance without recovering. Enforcement makes a ceiling binding, so choosing its value requires evidence from representative tasks. Engineers evaluate candidate budget vectors by testing the end-to-end control policy across a workload sample while holding models, tool suites, and acceptance tests constant. The acceptance fraction, accepted tasks divided by all attempted tasks, counts both outright failures and trajectories halted by budget exhaustion. System evaluations must report total dollar expenditure, wall-clock latency, unresolved background liabilities, and operator intervention frequency alongside raw task completion. Dividing the total cost of all attempts by the accepted count gives the cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**), which amortizes the expenses of failed and abandoned runs across successful completions. Budget limits appear artificially inexpensive whenever benchmark evaluations omit the costs of failed trajectories from total expenditure. Kapoor et al. ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.15 Source References#^ref-kapoor2024agents|2024]]) argue that evaluating agent accuracy in isolation from cost produces needlessly fragile and expensive architectures, so the two must be optimized jointly.

Baseline profiling under unconstrained budgets reveals the empirical completion time and token distributions of successful trajectories, highlighting candidate threshold targets. However, because early steering, throttling, and finalization alter downstream model reasoning, engineers must evaluate the complete policy empirically rather than assuming post-hoc truncation models reality. In practice, empirical cost-benefit curves rarely display a sharp knee. The operational decision rule selects the budget ceiling that minimizes cost per accepted task while keeping unresolved liabilities and manual interventions within acceptable operational bounds. When the difference between two policies falls within measurement uncertainty, the simpler policy is preferred.

Baseline profiling of public repair-agent runs shows what such distributions look like. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^fig-vol3-model-calls-resolved-vs-failed|Figure 5]] plots the distribution of model calls per trajectory for five published agent configurations on the same 500 repository-repair tasks ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.15 Source References#^ref-jimenez2024swebench|Jimenez et al. 2024]]), split by whether the patch was accepted.

Two lessons follow for ceiling choice. Failed runs take more calls than accepted ones in every configuration of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^fig-vol3-model-calls-resolved-vs-failed|figure 5]], so the tail of the call distribution is mostly spend on attempts that will not be accepted. A ceiling at the accepted runs’ 90th percentile halts at most 10 percent of eventual successes but 15 to 31 percent of eventual failures. The same figure also warns against reading a ceiling off another configuration, because the percentile ranges from 46 to 101 calls across the five and differs even between the two agents built on the same model (82 and 101). These percentiles come from post-hoc truncations of unconstrained runs rather than enforced policy trials: because a ceiling the agent can see changes how it spends the remaining calls, the estimate locates a candidate ceiling and the policy evaluation confirms it.

Re-running the same model under several enforced ceilings supplies the confirmation. **Checkpoint 10.3: A budget is an admission decision**

The repair trajectory is paused with an unresolved paid test job. A smaller model call would fit the currently unreserved allowance, but the task’s elapsed deadline has passed.

**Admission**: Why does a fitting dollar reservation not permit the call under the current task contract?

**Settlement**: Which evidence would release the test job’s unused reservation, and why is its timeout insufficient?

**Finalization**: How can the harness fund a final report while preserving responsibility for the unknown job charge?

**Admission estimate**: In notebook [10.2](https://mlsysbook.ai/vol3/10_agent_harness/10_agent_harness.html#nbk-10-bounded-liability-admission), the test job settles and releases half its reservation. Estimate the largest input the same call could then carry at its full output allowance.

**Ceiling choice**: Policy A accepts more tasks but incurs more total cost and more unresolved liabilities than policy B. Which quantity decides between them, and what trial evidence is required before trusting the difference?

Bounded-liability admission completes the harness’s supervisory control plane: the trajectory record tracks ownership and outstanding obligations, guarded transitions govern state changes and waits, the scheduler divides shared model service, and multi-dimensional budgets cap lifetime spend without relying on model self-restraint. Resource accounting, however, bounds aggregate consumption rather than semantic problem-solving progress; catching a stalled repair loop before it exhausts its allowance requires synthesizing progress evidence across repeated tool failures and state transitions. Even for resource and lifecycle bounds, these guarantees hold only when engineers enforce them at the runtime boundary rather than substituting cooperative coroutines, settled-spend checks, or prompt instructions.

↪ Progress evidence for detecting a trajectory that loops without advancing is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^sec-vol3-failure-recovery-progress-evidence|Progress evidence]]**.
