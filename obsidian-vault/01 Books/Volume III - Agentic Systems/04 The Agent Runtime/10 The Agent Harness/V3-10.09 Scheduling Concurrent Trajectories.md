# V3-10.09 Scheduling Concurrent Trajectories

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-controlplane-scheduling

When the test suite for candidate `r18` finishes and the repair trajectory returns to `READY`, it rarely has the serving cluster to itself: an interactive user session and a backlog of repository maintenance tasks may already be waiting to query the model. If the harness simply dispatches requests as soon as tasks generate them, aggressive retry loops will monopolize model capacity; if it unconditionally favors interactive requests, large maintenance jobs can wait indefinitely. Concurrency alone does not solve resource allocation, so the harness needs an explicit scheduling policy to arbitrate among eligible calls.

The unit of scheduling admission is a `READY` trajectory’s **next model call**, rather than its entire multi-step task or the downstream tool execution that the reply may propose. Completing an asynchronous wait does not grant immediate dispatch; it makes a trajectory eligible only through a guarded transition into the `READY` state, where it queues for the scheduler’s approval. Downstream, the inference serving engine manages batching, KV-cache allocation, and accelerator execution. That low-level engine scheduling remains strictly decoupled from the harness’s control plane, which decides which high-level trajectory may submit work in the first place.

### Fair Sharing and the Scheduling Charge

^sec-vol3-agent-harness-scheduling-charge

A single maintenance prompt containing extensive code diffs can consume 40,000 tokens while a concise interactive query requires only 2,000 tokens, so granting an equal number of model calls across classes does not deliver equal service. A scheduler must therefore define what resource its allocations apportion. The policy used here bills each admitted request a declared **scheduling charge** equal to its full input-token count plus its maximum allowed output-token reservation. This conservative metric measures admitted token commitments rather than actual generated output, monetary cost, accelerator occupancy, or task utility. Cached prompt tokens remain part of this upfront charge because serving-engine cache hits cannot be guaranteed before dispatch.

**Weighted deficit round-robin** provides an effective, low-overhead mechanism for apportioning this declared token charge across diverse service classes. For each class, the scheduler keeps a credit counter and a queue of the class’s `READY` trajectories, served in rotation from a pointer that persists between rounds. At the beginning of each scheduling round, the system increments each class’s credit counter by a quantum proportional to its assigned weight. The scheduler then steps through the classes, admitting calls as long as their token charges fit within the available credit and all downstream capacity gates pass. Each admission deducts the call’s charge from the class balance. Unspent credit carries over into subsequent rounds, allowing a class with large requests to gradually accumulate enough deficit credit to admit a multi-thousand-token prompt. When a class exhausts its active work, the scheduler resets its credit counter to zero so it cannot hoard unearned allocations during idle periods. This design adapts the deficit carryover mechanism[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.16 Footnotes#^fn6|⁶]] of deficit round-robin ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.15 Source References#^ref-shreedhar1995efficient|Shreedhar and Varghese 1995]]) from network packet scheduling to language model admission control.

Credit belongs to the service class rather than to individual trajectories, so a tenant cannot enlarge its share by spawning hundreds of concurrent tasks. Within a class, the rotation pointer persists across passes; a scan that restarted at the head of the queue on every pass would let trajectories near the front absorb fresh credit while those near the tail starved. Every class expected to make progress needs a positive weight, and any ceiling on accumulated credit must accommodate the largest single request the policy permits. A credit cap below that size leaves the largest calls stalled indefinitely despite repeated replenishment rounds.

**Napkin Math 10.1: Charge shares vs. call shares**

**Problem**: An interactive class has weight 3 and a maintenance class has weight 1, with a base quantum of 8,000 charge tokens per unit weight per round. An interactive call carries 2,000 input tokens and a 500-token output allowance; a maintenance call carries 40,000 input tokens and a 2,000-token output allowance. Assume both classes remain continuously backlogged at these fixed call sizes, no provider or local-capacity gate binds, and carried credit can cover the largest permitted call. Over many rounds, how many calls does each class admit?

**Math**: Each round credits 24,000 tokens to the interactive class and 8,000 tokens to maintenance. Because interactive calls incur a scheduling charge of 2,500 tokens each, the interactive class averages 24,000 / 2,500 = 9.6 calls per round. A maintenance call incurs a charge of 42,000 tokens, so its class must carry forward credit for 42,000 / 8,000 = 5.25 rounds per call.

**Result**: The interactive class receives 75 percent of the total token charge capacity, but it dispatches roughly 50 times as many admitted calls as the maintenance class.

**Systems insight**: Class weights determine the long-term division of token charges, while admitted call rates depend directly on request size. The maintenance class’s mean interval between admissions, measured in credit rounds, equals its request charge divided by its per-round quantum under the stated assumptions. Halving its input to 20,000 tokens reduces this aggregate interval to approximately 2.8 rounds per admission without changing class weights. An individual trajectory also waits behind its class peers; execution, tool waits, and approval time lie outside this quotient. Increasing a class weight shifts its aggregate token share; shrinking prompt sizes (through prompt compaction or targeted context retrieval) accelerates its call dispatch rate. Finally, the scheduler’s credit ceiling must accommodate at least one complete maintenance charge, or that class will never accumulate sufficient deficit credit to dispatch.

Configuring class weights fixes how the declared token charge is shared, not the proportion of admitted calls, and it divides capacity in proportion to weight rather than creating capacity. Under sustained overload, scheduling weights redistribute queueing delay without increasing provider throughput, so bounding latency under persistent saturation requires admission limits on incoming tasks or explicit rejection.

### Quota and Capacity Gates

^sec-vol3-agent-harness-quota-capacity-gates

A model call selected by the fairness scheduler can still fail at dispatch with an HTTP 429 rejection if the tenant’s provider quota is full, or stall downstream if local sandboxes are out of memory. Before dispatching a nominated call, the harness must therefore pass two capacity gates: external provider quotas and local execution capacity. Model providers enforce rate limits across distinct dimensions, specifically requests per minute (RPM), tokens per minute (TPM), and concurrent in-flight requests, and the provider’s accounting contract determines what must be reserved before transmission. For token limits, providers typically debit the full input count plus the declared maximum output allowance against the current time window until generation finishes. Pricing discounts do not relax rate limits; a provider that discounts cached prompt tokens on the invoice may still count those tokens at full weight against the tenant’s rolling TPM window. Satisfying a token quota likewise guarantees nothing about request concurrency, which is capped independently to protect serving infrastructure.

A local rate limiter lets the harness hold pending calls rather than discover provider saturation through HTTP 429 (Too Many Requests) rejections. It must account for all traffic that shares the provider allocation, including harness processes on other machines. When that traffic or the provider’s windowing algorithm is opaque, it keeps safety headroom and adjusts its refill rate from response headers that report remaining quota and suggested retry intervals.

Local execution resources impose a second set of gates. A tool call that compiles code or runs an integration test needs sandbox slots, CPU cores, memory, and storage bandwidth even when model token quotas are abundant. Each bottleneck must be tracked in its own physical unit: bytes of disk space, bytes per second of transfer, operations per second of storage I/O. Counting homogeneous sandbox slots suffices only when every job fits an identical envelope; with heterogeneous jobs, slot counts alone do not prevent out-of-memory failures. Tool dispatch therefore has its own admission queue, shared by policy in these physical units rather than in model tokens. A protected action whose approval arrives when no sandbox slot is free stays in `AWAITING_APPROVAL` alongside its recorded decision ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^tbl-vol3-escrow-transitions|table 8]]) instead of returning to `READY` and issuing another model call.

Selection by the scheduler is a nomination, not an execution grant. Between the scheduler picking a candidate and committing its dispatch, an operator can pause the trajectory, a grant can expire, or a concurrent step can consume the remaining budget. The nominated call therefore still passes the atomic admission check, which records every quota and capacity reservation before the request leaves the host. If two scheduler workers nominate the same candidate, the `record_version` check lets exactly one commit. A call blocked by insufficient credit, an exhausted rate limit, or a full sandbox pool stays in `READY`; that delay is backpressure, not task failure. Once a call is sent, its reservations follow the settlement rule. An HTTP timeout after transmission keeps them outstanding, because the provider may have processed and billed the request, and provider-quota refunds follow the provider’s own accounting contract.

Fair sharing decides which eligible trajectory is served next, and quota and capacity gates decide whether that work can run now. Neither limits the total work one trajectory requests across many turns; a repair agent can receive its fair share of tokens indefinitely without converging on a valid patch. That limit is the trajectory budget.
