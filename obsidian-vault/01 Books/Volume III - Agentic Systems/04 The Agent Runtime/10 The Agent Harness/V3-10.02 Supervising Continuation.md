# V3-10.02 Supervising Continuation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness|V3-10 The Agent Harness]]

^sec-vol3-harness-overview

![[90 Assets/Volume III/03 Test Time Compute/Hsa Locator H 8f8aca5627.svg]]

*H·S·A locator triad with the Horizon axis highlighted.*

*The horizon exposure, bounded by a harness that keeps control outside the model.*

Consider the connection-pool repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) at the moment it produces candidate patch `r18`. A test job is actively running against a fixed snapshot of that revision when an operator requests a pause for manual inspection. Simultaneously, an independent interactive task queues for model service, and the repair trajectory approaches its allocated budget. Even if the test job finishes cleanly and the next model reply is syntactically flawless, neither event answers whether the repair should proceed right now. That continuation decision depends on operational conditions outside the model: the operator’s pending signal, current task states, shared cluster capacity, and the allowance remaining once in-flight work is accounted for.

The runtime components examined so far each address part of this operational environment. The tool layer tracks job handles and operation repeat contracts, the sandbox isolates execution and bounds workspace lifetimes, and the security checks test each dispatch against its confidentiality and provenance labels and bind each approval to the exact action it covers. Each of these mechanisms, however, operates at the boundary of a single invocation, resource, or decision; none possesses the context or authority to decide whether the trajectory as a whole may take another step. That decision cannot be delegated to the model either. An agent instructed to self-regulate (to pause on request, or to halt before exceeding an allowance) evaluates that rule afresh on every turn. Because of horizon compounding (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]**), even a high per-turn compliance rate decays across an extended run, so a constraint the model honors on almost every turn is still violated in a predictable share of long trajectories. Operational control also requires state that cannot live in an ephemeral context window. An operator needs immediate status without reconstructing the conversation transcript; a scheduler must distinguish between work waiting on background jobs and work eligible to run; and the dispatch path must enforce security grants and token allowances before invoking downstream tools. All three operations demand a single, authoritative account of the trajectory that an unstructured message list cannot maintain.

The agent harness provides this missing supervisory layer by taking ownership of the execution loop for an individual trajectory. The agent proposes candidate actions; the harness determines whether each step runs immediately, yields to other work, or halts, and it enforces those decisions against an execution record that only the runtime can modify. This is trajectory-level encapsulation (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-trajectory-encapsulation|10]]). The runtime governs each model call as one step of a whole trajectory, and the trajectory advances only through transitions and admissions that the runtime’s guards permit. The reason is that the trajectory cannot be relied on to yield, to stop, or to notice that it has stopped making progress. Invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) says that bounds belong below the model; this principle names the unit those bounds must cover, the whole trajectory rather than the single call. In the harness, the principle takes the form of two working rules. First, every outbound model call or tool dispatch must pass an explicit admission check (active operator signals, capability grants, shared capacity, and remaining budget) at the instant it would execute. Second, in-flight work stays accountable: no pause signal, timeout, or cancellation proves that running work has stopped or that its cost is settled, so every outstanding operation keeps a named owner until evidence settles it.

The record described in this chapter lives in host memory, while making its guarantees survive host failure is the work of durable execution (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution#^sec-vol3-durable-execution|Durable Execution]]**). Within a live host, the harness develops in the order these supervisory decisions arise across a repair turn: separating the control path from the bare execution loop ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.03 The Loop and the Harness#^sec-vol3-controlplane-need|section 10.2]]), maintaining an authoritative account of the trajectory ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.04 The Trajectory Record#^sec-vol3-controlplane-acb|section 10.3]]), and enforcing guarded rules for how that account may change ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-controlplane-statemachine|section 10.4]]). Operators then need a way to stop or redirect active work ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.06 Control Actions#^sec-vol3-controlplane-signals|section 10.5]]), while long tool jobs and human reviews need waits that keep supervision intact ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.07 Supervised Waiting#^sec-vol3-controlplane-yielding|section 10.6]], [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^sec-vol3-controlplane-hitl|section 10.7]]). Across concurrent trajectories, shared model service must be divided fairly ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.09 Scheduling Concurrent Trajectories#^sec-vol3-controlplane-scheduling|section 10.8]]), and across many turns, cumulative consumption must be bounded ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-controlplane-accounting|section 10.9]]). Seeing why those guarantees require a dedicated runtime component starts with what breaks when the `r18` repair turn runs inside an unmediated loop.
