# V3-11.10 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-durable-execution-fallacies

Building durable agentic systems demands clarity about what persistent state actually guarantees. The most consequential engineering mistakes confuse a surviving record with evidence it cannot provide, or expend heavy recovery effort where structured logging has already eliminated the need.

**Fallacy**: *Saving the final context window is enough to audit or recover a trajectory.*

A model’s final context window represents only the transient view passed to the last inference call, filtered through compaction policies and bounded observation budgets. It omits the operational decision history: which candidate proposals were admitted, which intents became durable, and which raw tool observations arrived and were subsequently summarized away. For example, if a tool returns an exposed credential at turn 7 and a compaction pass replaces that observation with an abstract summary at turn 12, the final context retains no trace of the leak. Comprehensive auditing and reliable crash recovery require the append-only event sequence defined in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.03 The Trajectory Log#^tbl-vol3-durable-log-schema|table 1]]. From an authoritative log with the required retained payloads, the execution engine can deterministically rebuild each captured past context window, whereas a surviving context window lacks the operational history needed to reconstruct the log.

**Pitfall**: *Checkpointing after every turn to be safe.*

Naively snapshotting full agent state after every turn introduces severe latency overhead for minimal operational gain. When turn-by-turn events and workspace mutations are already appended to a durable log, taking a full checkpoint only reduces replay time during recovery, yet it forces execution to pause on every step. In the crash trace of notebook [11.1](https://mlsysbook.ai/vol3/11_durable_execution/11_durable_execution.html#nbk-11-checkpoint-cadence), checkpointing after each of the 100 turns spends 52 s in cumulative capture and recovery time, compared to 6 s for a 25-turn stride. Engineers should tune this cadence with the logged balance of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.05 Checkpoints#^eq-vol3-logged-stride|equation 5]], grounding the calculation in the per-turn log reconstruction cost rather than the much slower runtime of live re-execution.

**Fallacy**: *Rerunning the model at temperature zero reproduces a trajectory.*

Greedy decoding fixes only the argmax token-selection rule for a given logit distribution, and the serving path that computes those logits is not numerically deterministic (**[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.05 Autoregressive Generation#^sec-vol3-foundation-model-repetition-replay|Repetition and replay]]**). Because autoregressive generation conditions every token on all preceding tokens, a single flipped token early in execution steers the entire subsequent trajectory into a different subspace.

Across multi-step agent horizons, trajectory reproduction compounds multiplicatively (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]**). Even under the optimistic assumption that individual greedy calls reproduce their recorded outputs 99 percent of the time, a 30-turn trajectory matches its recording end to end only 74 percent of the time. That estimate ignores external non-determinism such as shifting system clocks, generated identifiers, and mutating external environments. Rerunning an agent prompt creates an entirely new execution trajectory that generates fresh side effects; reliable reproduction requires replaying the exact model completions and tool results recorded in the log.

**Pitfall**: *Using an incomplete replica to conclude that a call was never sent.*

In distributed systems, the absence of an event record in a replica does not prove that an action never took place. When recovery logic evaluates whether to re-dispatch an unconfirmed operation after a crash, inspecting an asynchronous read replica or diagnostic log can lead to duplicate side effects. If replication lag delays the arrival of an acknowledged intent, recovery logic reading that replica might incorrectly assume the request was never transmitted, even though the crashed worker had already dispatched the RPC to an external service. Re-dispatching on that false assumption duplicates external mutations. Recovery engines must verify prefix completeness directly against the authoritative, strongly consistent store before treating the absence of an intent as evidence of non-dispatch.

**Fallacy**: *A durable intent, or a newer ownership epoch, makes an unresolved operation safe to settle or repeat.*

Writing an intent record before dispatch guarantees that an operation is tracked, but it does not resolve the state of an in-flight network request. When an agent crashes with an operation marked in-flight, a missing response or recorded timeout leaves the physical outcome ambiguous. The crash might have occurred before the packet left the network interface, or after the remote service processed the mutation but before the acknowledgment arrived. Similarly, advancing an ownership epoch fences zombie workers from committing further updates to internal databases, but an epoch token cannot retroactively cancel a request already delivered to an external endpoint. Resolving an unconfirmed operation requires positive evidence obtained through the remote service’s inquiry API, and repeating it requires the endpoint’s idempotency contract. Settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]) applies after a crash exactly as it does after a timeout.

**Pitfall**: *Resuming a recovered trajectory on whichever server is free.*

Reconstructing an agent’s memory by folding an event log requires minimal CPU time and consumes no model tokens. Teams often make the mistake of budgeting recovery purely around log deserialization, scheduling the resumed agent on whichever inference node happens to report idle capacity. However, moving to a server without compatible cached state discards KV-cache locality. When the resumed agent issues its next model call, the target accelerator must recompute the attention state across the entire reconstructed context window. For a 32,768-token context on the reference model and accelerator, this cold prefill phase alone imposes a latency floor of roughly 2.3 s, even before accounting for network queueing delays. Prefix-aware dispatch compares the avoided prefill work against queueing, transfer delay, and capacity at eligible workers ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^eq-vol3-resume-time|equation 7]]), while preserving the exact prefix during prompt assembly.
