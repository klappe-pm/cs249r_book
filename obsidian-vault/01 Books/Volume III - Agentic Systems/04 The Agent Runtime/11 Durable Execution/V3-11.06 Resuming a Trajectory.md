# V3-11.06 Resuming a Trajectory

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-persistence-migration

The worksheet’s replacement worker now holds everything the previous sections promised: the checkpoint that binds `record_R_ckpt` to `ws_r18`, and a suffix that ends at the durable intent for `test_r18` under `attempt1` with no result. Holding that record is not yet permission to act on it. The workspace can be restored byte for byte, but the missing result supports no inference about the test, which may never have launched, may have finished as the host lost power, or may still be running remotely. Another worker may also believe it still owns the trajectory, and the budget and approvals recorded before the crash may no longer match current policy. The replacement therefore cannot simply re-run the command or assume failure; it must establish ownership, restore state, settle what it can of the outstanding obligations, and only then admit new work.

**Resume** establishes a usable continuation from surviving records under current ownership and cluster policy. It proceeds in five stages, which the subsections below follow in order. The worker validates that the authoritative log is available and acquires exclusive trajectory ownership. It then restores compatible in-memory records and workspace artifacts and reconciles outstanding external operations and resource budgets. Finally, it evaluates admission for new work, rebuilding serving state if that work begins with a model call. Reconstruction reproduces the agent’s causal history, while subsequent admission gates decide whether to grant or withhold execution authority. If required evidence, ownership fencing, or admission grants are unavailable, the runtime safely holds the trajectory in place rather than proceeding on speculative assumptions.

### Availability and Ownership

^sec-vol3-durable-execution-availability-ownership

If a replacement worker starts reconstructing state from a lagging storage replica or begins dispatching while a network-partitioned predecessor is still running, it can miss an already-sent `test_r18` intent or race against the old worker’s late writes. Before parsing records, the worker must therefore locate the authoritative committed log prefix and the required checkpoint artifacts. Under the log completeness rules of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-persistence-wal|section 11.3]], the absence of an entry is meaningful only after the worker proves that the log prefix is intact. If storage replicas disagree, network partitions obscure the tail, or an immutable artifact is missing from object storage, the worker must report that reconstruction is unavailable rather than treating the gap as an empty history.

Reading durable state does not confer the authority to act on it. Trajectory ownership requires an explicit grant from an ownership coordinator, a strongly consistent lease service whose own state is replicated so that it survives the failures the trajectory log survives. The coordinator authenticates the claimant and issues a new `owner_epoch`. This epoch bump assigns execution responsibility to the replacement worker while leaving `record_version`, `control_epoch`, and the identities of admitted operations unchanged.

The distinction between active ownership and historical inspection matters because the previous worker may have been partitioned rather than permanently destroyed. The tool layer met the same zombie worker, a stalled holder that outlives its lease and resumes writing, and the same remedy protects the whole trajectory. Ownership is held under a lease, so expiry bounds how long a lost worker can block recovery, but expiry alone is not exclusion. Exclusion requires a **fencing token**, a monotonically increasing ownership generation that stateful resources compare against the newest generation they have observed, rejecting requests stamped with stale epochs ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-kleppmann2017designing|Kleppmann 2016]]). For a trajectory the `owner_epoch` is that token. Fencing exclusion holds only at the boundaries that verify it: the write-ahead log, the dispatch gate, and each participating downstream resource. The replacement worker must install the new ownership generation at those boundaries before relying on mutual exclusion, and any boundary unable to verify current ownership must withhold protected operations.

↩︎ Leases and epoch fencing at the tool endpoint, with their lock-service origins, are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|Operation identity and endpoint contracts]]**.

↪ The handoff in which the old owner’s delayed write meets the newly installed fence is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Distributed State Foundations#^sec-vol3-appendix-systems-fencing|Leases and Fencing]]**.

Fencing operates over a narrower scope than effect settlement. A dispatch gateway can reject new dispatch attempts from the old worker while an operation that the old worker previously initiated remains in flight on an external runner. The replacement worker therefore preserves `operation_id=test_r18` along with the evidence recorded for that earlier attempt. Passing the ownership check authorizes the new worker to issue fresh dispatches, but it does not permit re-dispatching `test_r18`. A gateway’s local pending-or-complete tracking table cannot make its log record atomic with an independent service endpoint’s real-world side effects.

### State Restoration

^sec-vol3-durable-execution-state-restoration

Once ownership is secured, re-running past turns to rebuild memory would re-sample the model and risk repeating external side effects. Instead, the worker restores the control record and the workspace by the procedure of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.05 Checkpoints#^sec-vol3-durable-execution-recovery-boundaries|section 11.4.1]], folding the committed suffix over the base checkpoint without calling any model or tool. For the worksheet, the result is the state already traced there, with `ws_r18` untouched and the in-doubt intent and reservation for `test_r18` in the record. What restoration cannot supply is the executor’s job handle `job_tests_18`, which survives only if the failed worker flushed the executor’s acknowledgment to the log before crashing. Without it, reconciliation must find the job by its logged operation identity.

### Effect and Charge Reconciliation

^sec-vol3-durable-execution-effect-reconciliation

Restoring the log leaves `test_r18` in doubt, and the remote test runner may have finished and reported its result while no worker was alive to receive it. To keep such callbacks from vanishing with the crashed process, durable execution moves the harness’s result wakeup registrations out of worker memory into a durable result inbox that operates independently of any single host. The inbox retains authenticated completion records, indexed by trajectory identifier, logical operation, and attempt identity, and stamped with executor signatures and scope metadata for independent validation. The current trajectory owner ingests this evidence into the log and the `operation_table`. However, receiving an inbox message does not settle an operation. Pending statuses, gateway timeouts, and partial payloads leave the operation in doubt.

↩︎ The result wakeup pipeline and its register-before-send rule are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.07 Supervised Waiting#^sec-vol3-agent-harness-wakeup-pipeline|The result wakeup pipeline]]**.

When the inbox holds no settling record for `test_r18`, the worker queries the tool endpoint directly to recover the job and its execution output by reconciliation, a bounded status query by logical operation identity under the tool’s contract. If the endpoint returns a verified completion record, that result confirms the status of `ws_r18` for that specific test run, though it does not imply that the broader repair objective has been met. If the endpoint cannot be reached or returns an ambiguous status, the operation remains in doubt. In that situation, the endpoint retry contract, rather than the absence of a response or a matching identifier, governs whether launching another attempt is safe.

↩︎ Reconciliation, the bounded inspection of external state that settles an ambiguous operation, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-reconciliation|Reconciliation]]**.

The same rigorous accounting applies to financial and computational budgets. The worker reconstructs `actual_consumption`, `outstanding_reservations`, and the protected `finalization_reserve` by replaying all recorded `BudgetReserved` and `BudgetSettled` transitions. External model providers and compute clusters do not refund resources because an orchestrator crashed mid-flight. A partial usage report settles only the verified fraction of a call, while the unverified remainder stays locked in outstanding reservations. The replacement worker inherits the duty to retrieve final usage evidence. Until that evidence arrives, the unverified remainder stays reserved as liability, the harness’s rule that missing usage is never released as unspent budget.

Control transitions and human approvals remain authoritative across failures. A trajectory recovered in the `PAUSED` state remains suspended, and a trajectory that reached a terminal continuation remains terminal. A held action recovers into `AWAITING_APPROVAL`, the state in which approval and dispatch eligibility are both unresolved. A pending request keeps waiting for its reviewer. An approval granted before the crash still releases the action only when the dispatch-time rechecks pass under the new owner. An approval that has expired, become stale, or been explicitly revoked remains void across all workers. When authenticated results arrive after an operation has timed out or the trajectory has paused, they update the `operation_table` to keep an accurate audit trail, rather than retroactively mutating an obsolete conversation turn. The current owner must validate those newly settled facts before admitting them into subsequent model contexts.

### Continuation Admission

^sec-vol3-durable-execution-continuation-admission

During the minutes a trajectory spent down and recovering, its operating deadline may have expired, an operator may have paused the run, or an in-doubt `test_r18` may still hold budget and block dependent edits. Recovered history accounts for past decisions, but current conditions govern the next step. Before admitting new work, the harness evaluates task and plan dependencies, capability grants, approval statuses, cluster dispatch capacity, and remaining funds. To pass admission, the sum of `actual_consumption`, `outstanding_reservations`, the bounded liability of the proposed step, and the protected `finalization_reserve` must fit within the cumulative budget ceiling. Deadlines for normal operation are enforced independently: when an operating deadline expires, the agent cannot schedule new exploratory calls simply because monetary budget remains. Instead, the runtime transitions strictly to finalization routines using the declared time and resource reserve.

↩︎ Bounded-liability admission, the budget rule this check enforces, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-agent-harness-reservation-settlement|Reservation and settlement]]**.

Unsettled external effects block dependent operations rather than stalling the entire system. An independent observation or read-only query may proceed if its own authorization and admission checks pass, whereas any action that mutates or depends on an in-doubt operation remains withheld. Resuming execution from `PAUSED` requires passing the guarded state machine transitions. Similarly, recovered partial model streams are discarded rather than promoted to completed candidates. A logged proposal that was never admitted requires fresh admission; an already admitted but definitely unsent attempt retains its identity and reservation and must pass the dispatch-time recheck without reserving budget again.

↩︎ The control-plane state machine and its guarded transitions out of `PAUSED` are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-controlplane-statemachine|Trajectory States]]**.

Context assembly must distinguish historical reconstruction from forward continuation. When auditing earlier turns, the runtime inspects the immutable delivered-input manifest and recorded summaries that the model actually received. When constructing the prompt for the next turn (`ContextBuilt`), the prompt composer may incorporate newly settled test results or approved plan revisions. Systems must preserve historical input manifests verbatim rather than silently substituting fresh retrievals or recomputed summaries.

Infrastructure and prompt updates also demand explicit governance. During extended downtimes, operators may update model checkpoints, prompt templates, or tool schemas. The runtime can either pin execution to the recorded versions, validate a verified migration path to the updated schema, or halt continuation if semantic compatibility cannot be proven. An in-doubt intent preserves its original parameter semantics regardless of subsequent schema versions. Whenever configuration shifts occur, the runtime records the transition and its provenance boundaries so that future evaluations treat the executions as distinct configurations.

Dispatching a new model call requires compatible serving state, though not necessarily a cold start. Depending on cluster cache eviction policies and prefix tree management, the inference engine may retain the full KV prefix, retain reusable prefix segments, or require full context prefill. Inspecting an audit record or keeping a trajectory paused requires no prefill computation. A serial-stage estimate of resume latency sums the constituent stages:

$$
{T_{\text{resume}}} = {T_{\text{own}}} + {T_{\text{read}}} + {T_{\text{fold}}} + {T_{\text{ws}}} + {T_{\text{rec}}} + {T_{\text{prefill}}}, \tag{7}
$$

^eq-vol3-resume-time

which accounts for acquiring the ownership fence, fetching and verifying the checkpoint and suffix, folding the log suffix, restoring workspace files, reconciling outstanding external operations, and rebuilding serving state for the next invocation. When stages overlap, elapsed resume time follows their dependency critical path rather than this serial sum. The terms map onto the subsections in order. ${T_{\text{own}}}$ and ${T_{\text{read}}}$ belong to availability and ownership (the two can overlap, since reading the log needs no ownership), ${T_{\text{fold}}}$ and ${T_{\text{ws}}}$ to state restoration, ${T_{\text{rec}}}$ to reconciliation, and ${T_{\text{prefill}}}$ is the last step of continuation admission.

↩︎ Prefix tree management and KV-cache eviction policies are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kvcache-radix-tree|Prefix Caching Across Turns]]**.

The final term marks a divergence between agent recovery and classical database crash recovery. In database systems like ARIES ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-mohan1992aries|Mohan et al. 1992]]), recovery time is dominated by reading the write-ahead log and redoing logged updates to dirty data pages on disk. In agent systems, deterministic log folding is cheap, because it executes local harness logic and updates in-memory tables without calling foundation models. Rebuilding the serving state, however, forces the system to recompute attention keys and values across the entire context history whenever no compatible cache prefix survives. Applying the weight-only prefill floor derived in **[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^sec-vol3-appendix-inference-roofline|Cost Asymmetry Between Input Prefill and Output Generation]]** to the reference model and accelerator, the arithmetic compute floor alone for a 32,768-token context requires roughly 2.3 s of an accelerator’s peak 8-bit tensor throughput. This floor comes before accounting for memory bandwidth overhead, kernel launch delays, or queueing contention. Because attention state is strictly a function of the token prefix (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-prefix-coherence|5]]), losing that cache throws away reusable computation while the causal knowledge survives safely in the log. Routing to a worker with compatible cached state can avoid prefix recomputation if the next prompt preserves that prefix; placement must also account for queueing, transfer delays, and available capacity. Systems engineers should profile each component of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^eq-vol3-resume-time|equation 7]] before dedicating engineering effort to any single phase.

↩︎ Why prompt assembly must reproduce the delivered prefix token for token to keep cache reuse is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-exact-prefix|Preserving an exact prefix]]**.

Resume converts surviving durable records into an authorized continuation without misreading silence as failure. The same records support a second use that admits no new work at all, inspecting and testing what the trajectory already did.
