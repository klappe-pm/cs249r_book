# V3-11.07 Recorded Trajectory Replay

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-persistence-replay

When an agent execution stalls or fails during an automated repair, resuming the session admits fresh work under current system conditions. Post-mortem debugging asks a different question, namely what the runtime recorded at the moment of failure and how the harness code responded to the inputs available at that time. Rerunning a targeted test like `test_r18` under a new attempt cannot resolve that inquiry. Because external services drift, package versions change, and model sampling introduces variance, a new execution merely supplies fresh observations rather than reproducing the missing historical outcome.

**Replay** substitutes retained execution records for live, non-deterministic inputs. The guarantees provided by replay depend entirely on which portion of the system computation is repeated. Retained trajectories serve three distinct purposes ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.07 Recorded Trajectory Replay#^tbl-vol3-replay-comparison|table 5]]): reconstructing a recorded state projection, which debuggers call time-travel replay; validating harness logic through regression replay; and branching into counterfactual experiments.

| Mode                      | Inputs and computation                                                                                         | Supported conclusion                                        |
|:--------------------------|:---------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------|
| Time-travel replay        | Fold retained events with the specified reducer and compatible checkpoint                                      | What selected runtime state the recorded history represents |
| Harness regression replay | Run harness logic against captured inputs at a declared boundary, with live effects disabled                   | How that harness implementation responds to those inputs    |
| Counterfactual branch     | Restore compatible starting state, change a declared condition, and obtain valid observations for the new path | What happened in this new experiment                        |

Table 5: **Three uses of a recorded trajectory**: Reconstructing history, testing code, and exploring alternative execution paths answer distinct engineering questions. None establishes an unobserved external outcome.

^tbl-vol3-replay-comparison

The first two modes make the same change to live execution. Where a live turn samples the model, passes the authorization gate, and dispatches the tool, replay disconnects the model and the tools and streams recorded replies and observations from the log into the harness ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.07 Recorded Trajectory Replay#^fig-vol3-replay-mode|figure 4]]). They differ in what runs on those recorded inputs.

![[90 Assets/Volume III/11 Durable Execution/Fig Vol3 Replay Mode d3c41123a0.svg]]

Figure 4: **Live Execution vs. Replay**: In live execution (top), each turn samples the model, passes its proposal through the authorization gate, dispatches the tool, and appends every step to the log. In replay (bottom), the model client is stubbed and tool dispatch is disconnected, so recorded replies and results stream into the harness and any request the log does not account for stops the replay. Folding those events reconstructs the recorded projection, and running harness logic against them is regression replay. A counterfactual branch differs from both, because after restoring its starting state it obtains new observations from compatible fixtures or isolated execution.

### Projection Reconstruction

^sec-vol3-durable-execution-projection-reconstruction

When an engineer inspects a stalled trajectory to see what reservations were locked or what prompt bytes reached the model at turn 18, re-evaluating live policy rules or re-running prompt assembly would overwrite the historical state with today’s decisions. Projection reconstruction, the first replay mode, avoids that contamination by running only the reducer over the log as a deterministic event stream. Folding the log applies previously recorded decisions directly; today’s authorization policy never re-evaluates historical proposals. Starting from a known checkpoint `record_R_ckpt`, the compatible suffix reconstructs the selected record through its captured admission, reservation, intent, and outcome events. If the suffix ends abruptly after a `ToolIntent` record without an accompanying settling event, the resulting projection faithfully retains that in-doubt operation, exposing an interrupted execution.

Historical inspection can also retrieve the immutable input manifest captured for a specific `ContextBuilt` event. This manifest reveals the exact token sequence and bounded observations delivered to the model, rather than a prompt newly assembled from current, potentially mutated data sources. Reconstructing the corresponding workspace environment similarly requires mounting the compatible snapshot together with any incremental filesystem deltas logged up to that point.

**Definition 11.3: Time-travel replay**

***Time-travel replay*** reconstructs a selected recorded state at a historical log boundary from compatible checkpoints, events, and retained artifacts, without repeating the original model calls or external actions.

1.  **Significance**: It renders the runtime’s historical evidence, decisions, and unresolved obligations fully inspectable at any retained log boundary for the cost of storage reads and a state fold, requiring zero model inference and generating zero external side effects.
2.  **Distinction**: Time-travel replay reconstructs an internal projection of recorded state, rather than restoring the full external world or re-evaluating decisions under updated policy rules.
3.  **Common pitfall**: Promising arbitrary historical inspection across every past turn when retention policies have already pruned required event payloads, filesystem snapshots, or historical reducer definitions.

### Harness Regression Replay

^sec-vol3-durable-execution-harness-regression-replay

Folding recorded decisions shows what the old harness decided, but it cannot test whether a code change in the harness state machine or prompt builder introduces a bug when handling the same historical inputs. **Harness regression replay** executes the harness code itself against captured external inputs rather than folding precomputed decisions through a reducer. Instead of querying live model endpoints or invoking real tools, the harness consumes recorded model completions, external tool observations, and control events. For deterministic reproduction, the captured boundary must supply all nondeterministic inputs consumed by the harness logic: wall-clock timestamps, randomly generated identifiers, configuration parameters, policy rules, and event arrival schedules. While this capture boundary does not need to simulate the entire operating system, any unrecorded source of entropy weakens reproducibility. This principle directly mirrors deterministic replay in operating-system debuggers, which record asynchronous hardware interrupts and system call outputs to allow developers to step backward through complex race conditions ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-king2005debugging|King et al. 2005]]).

To serve captured inputs correctly, the replay adapter follows the **matching-request rule**, matching every outgoing request against the recorded trace before returning a response. A captured model response is valid only for its specific prompt invocation and delivered token payload. Similarly, a tool observation corresponds to a unique logical operation and attempt, parameterized by exact tool names and serialized arguments. Replay adapters enforce matching using canonicalized representations or explicitly declared normalization schemes, combined with logged arrival sequences or formal concurrency models.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.15 Footnotes#^fn8|⁸]] A naive FIFO queue that blindly yields the next recorded event risks routing the test outcome of `test_r18` to an entirely different operation or candidate patch. If an outgoing request deviates from the recorded trace, the replay engine must immediately fail the comparison; under no circumstances should it fall back silently to a live network call.

A reliable regression harness must seal all live side-effect pathways. Real tool dispatch, external callback handlers, asynchronous background reconciliation loops, and production database writes must be severed or redirected to in-memory mocks. While the test may mutate isolated, ephemeral test state, all interactions with external infrastructure are replaced by recorded observations. Enforcing these isolation boundaries is strictly the responsibility of the test runtime; the harness must never trust the model or agent code to refrain from issuing live operations.

Consider an edge case where an asynchronous tool returns an authenticated late result after an agent repair job has transitioned into the `PAUSED` state. According to the control-plane state machine, the correct harness behavior is to record the arriving observation in the operation table while keeping the agent paused, rather than automatically triggering a new model inference step. If a developer modifies the harness and inadvertently introduces a code path that fires an unauthorized model invocation upon receiving the late event, the regression replay immediately detects the discrepancy and fails the test. Successful execution against this historical trace proves only that the harness correctly handles that specific scenario; passing a replayed unit test for `test_r18` does not constitute evidence of general task competence or end-to-end patch correctness.

When engineers update harness orchestration logic or tighten safety policies, behavioral changes are often intentional. Regression suites must therefore specify which outputs require strict byte-for-byte equivalence and which represent expected divergence. A diff between replayed execution and the historical baseline can indicate an unintended regression, an intentional algorithmic improvement, or a defect in the input capture itself. While replaying against recorded inputs eliminates expensive model API charges and external tool latencies, it still consumes local compute cycles, disk I/O, and setup overhead, and it validates behavior solely within the narrow envelope of previously observed execution paths.

### Counterfactual Branches

^sec-vol3-durable-execution-counterfactual-branches

Regression replay must stop the moment a change alters the request the agent emits, so it cannot show what a trajectory would do next if an engineer modifies a prompt template, selects a different foundation model, updates an authorization policy, or changes an observation filter. To test such an intervention past the point where it changes the agent’s actions, the runtime forks execution by allocating a fresh branch identifier linked explicitly to the parent log sequence at a designated checkpoint boundary ${j_{\text{ckpt}}}$. It documents the intervention in metadata and reconstructs the historical execution environment to match that precise point in time. In the crash repair scenario, branching from checkpoint ${j_{\text{ckpt}}}$ requires mounting the exact workspace snapshot `ws_r18` alongside matching dependency fixtures. If an engineer restores only the historical source code while executing against current, upgraded third-party packages, the experiment conflates the intentional prompt or code change with uncontrolled environment drift.

With durable logs, the runtime reconstructs the unchanged prefix deterministically through projection folding, completely avoiding redundant model sampling or tool execution up to the fork point. Beyond that boundary, however, the newly diverged continuation requires genuine observations that correspond to its altered actions. A captured historical response remains valid only as long as the outgoing request and environmental assumptions match the historical trace exactly. The moment the modified agent proposes a different test command, alters tool arguments, or produces an alternative patch candidate, the recorded downstream events become obsolete. At this divergence point, the branch must either halt replay or transition into active execution, gathering fresh observations from an isolated sandbox or compatible test fixture. Because the branch represents an unverified trajectory, production side effects remain strictly disabled, and human approvals granted to the parent execution never carry over automatically to the branch.

A **counterfactual branch** is thus a distinct, newly identified execution thread that inherits a validated historical prefix while exploring an alternative downstream path. Inspecting an individual branch helps engineers diagnose why a specific bug occurred or test how a targeted prompt patch performs on a known failure mode. Establishing broader claims about agent reliability or task success rates, however, requires running statistically grounded benchmarks across distribution-scale test suites. Replay establishes the precise boundary where historical evidence ends and new computation begins, and the same retained evidence can pinpoint the exact step at which two executions diverge.
