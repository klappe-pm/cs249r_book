# V3-11.03 The Trajectory Log

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-persistence-event-sourcing

A replacement worker can rebuild the crashed trajectory only from what the failed worker wrote somewhere that outlived it, so the first design question is what outliving it means. If the worker host and its attached disk are destroyed together mid-turn, a replacement on an independent machine can resume only if the acknowledged history was already replicated to independent storage. Durability is therefore meaningful only relative to an explicit fault model that names which failures the stored history must survive. Systems engineers call this boundary a **failure domain**, the set of faults across which a persistence guarantee holds. Three tiers of increasing severity recur: a process crash that leaves host storage intact, replacement of the worker node while a shared network-attached volume survives, and permanent loss of that storage tier. Each tier demands stronger replication and wider physical fault isolation, and [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-durable-execution-ack-failure-domain|section 11.3.1]] prices the acknowledgment each one requires. The crash worksheet targets the strongest tier, in which the acknowledged event history and every artifact required for recovery survive the simultaneous destruction of the worker host and its attached disk. Every durability claim in this chapter is made relative to that contract.

### The Log as Recorded Evidence

^sec-vol3-durable-execution-log-evidence

Surviving the failure domain solves where the bytes live, but it leaves open what those bytes must record so the replacement worker never has to ask the model what happened before the crash. Re-prompting the model from its last visible message cannot reconstruct past control state, because stochastic sampling and a changed external environment steer the trajectory down a different path. Instead, the runtime decouples execution state from process lifetime by recording an append-only, chronological history of every decision and observation across the trajectory.

**Definition 11.1: Trajectory log**

***Trajectory log*** is the append-only, ordered sequence of typed events (including delivered model prompts, returned completions, resource authorizations, control transitions, and observed tool outcomes) from which a deterministic reducer reconstructs an agent trajectory’s control state.

1.  **Significance**: Recovery folds recorded decisions sequentially rather than re-executing completed turns. A crash late in a long trajectory therefore costs only deterministic replay time. It avoids fresh model invocations, which would re-expose the system to the compounding error rates of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]** and accumulate redundant token charges against the task attempt budget in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**.
2.  **Distinction**: The trajectory record (definition [10.2](https://mlsysbook.ai/vol3/10_agent_harness/10_agent_harness.html#dfn-trajectory-record)) is the live in-memory projection that governs the immediate next decision. The trajectory log is the immutable, append-only history from which that record is derived. The context window is the transient, curated token sequence supplied to the model.
3.  **Common pitfall**: Recording only tool results while omitting operation dispatches. If an admitted tool call crashes mid-execution or drops its network response, the absence of an intent record leaves the recovery worker unaware that an external side effect may already be in flight.

Formally, the log is a sequence

$$
{\mathbf{e}_{1:j}} = [{e}_1, {e}_2, \dots, {e}_j]
$$

When an agent refines an earlier hypothesis or encounters an unexpected tool error, it appends fresh evidence to the tail of the log rather than mutating historical records in place.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.15 Footnotes#^fn1|¹]] The active trajectory record represents an accumulated projection over this append-only stream. Starting from a base state ${R}_0$, a deterministic reducer applies each recorded event sequentially:

$$
{R}_j = \text{fold}({R}_0, {\mathbf{e}_{1:j}}) = \text{apply}(\dots\text{apply}(\text{apply}({R}_0, {e}_1), {e}_2)\dots, {e}_j)
$$

In this formulation, ${j}$ indexes the durable log sequence boundary rather than the interaction turn ${t}$. Given deterministic reducer semantics and complete event payloads, folding reconstructs the precise control state without invoking the foundation model or re-executing external tools. This architecture embodies the classic **event sourcing** pattern ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-kleppmann2017designing|Kleppmann 2016]]): historical decisions serve as deterministic inputs to state reconstruction, while unrecorded events remain explicitly unknown. If the latest durable log entry indicates that a test execution was authorized and dispatched, but contains no corresponding completion event, the reconstructed state marks that operation as unresolved ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.03 The Trajectory Log#^fig-vol3-event-sourcing|figure 1]]). For the worksheet crash, the fold keeps the held reservation and the dispatched `test_r18` intent, and it invents no outcome for the test.

![[90 Assets/Volume III/11 Durable Execution/Vol3 Event Sourcing c420781dfc.svg]]

Figure 1: **The Trajectory Record as a Projection of the Log**: The record in runtime memory (top) is lost on a crash; the durable, append-only log (bottom) is not. Folding the logged events through a deterministic reducer, starting from the initial record ${R}_0$, rebuilds the recorded projection ${R}_j$ at boundary ${j}$ without calling the model or any tool. Because the log ends at the test’s recorded intent with no recorded result, the reconstructed record keeps the admission and reservation and marks the test unresolved rather than inventing its outcome.

^fig-vol3-event-sourcing

Engineers must distinguish the trajectory log from the model’s active context window. Context assembly is selective and ephemeral: prompt compilation filters past interactions, and context compaction periodically replaces verbose command outputs with concise summaries. The trajectory log, by contrast, preserves the exact delivered inputs and operational decisions required by the system’s replay contract. For a truncated observation, the log retains the exact byte slice exposed to the model rather than the full, unpruned output stream emitted by the tool. State reconstruction reproduces only what was durably captured. A compacted summary replays as a summary, and a logged hash of a payload can verify those bytes only while the stored payload itself survives ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.09 Log Retention and State Compaction#^sec-vol3-durable-execution-payload-storage|section 11.8.2]] develops this separation of digests from bytes).

### The Log Event Schema

^sec-vol3-durable-execution-event-schema

If a log entry records only that a tool was called without capturing the worker lease, control epoch, or reservation bound, a replacement worker cannot tell whether a late callback belongs to an invalidated turn or how much budget remains locked. An event log supports reliable recovery only when its schema captures the operational metadata that succeeding workers need to answer those questions. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.03 The Trajectory Log#^tbl-vol3-durable-log-schema|Table 1]] groups these event families by their roles during reconstruction. These schemas define logical event boundaries rather than requiring isolated physical storage writes for every individual field. For example, a high-throughput runtime can coalesce authorization checks, budget reservations, and tool dispatch intents into a single batched write transaction, provided the deterministic reducer preserves their causal dependencies. The storage engine must also durably acknowledge the batch before dispatch (the ordering that [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-persistence-wal|section 11.3]] develops).

Every event envelope contains a trajectory identifier, a unique event identifier, a monotonically increasing `sequence_number`, schema type and version tags, and tenant or issuer provenance. In addition, the log records the active reducer version alongside the worker lease identity under which appends were accepted. Within this envelope, the `sequence_number` defines total event ordering, and `record_version` tracks state machine modifications. The `control_epoch` is the harness’s control fence, which advances whenever a pause, cancellation, or interruption invalidates in-flight continuations, so an observation stamped with an older epoch cannot advance the current one. A distinct `owner_epoch` counts grants of trajectory ownership, so that storage can reject appends from a worker whose ownership has passed to another (the fencing mechanism of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-durable-execution-availability-ownership|section 11.5.1]]). Neither ownership handoffs across workers nor control-epoch increments alter the unique logical identity of an in-flight operation.

↩︎ Epoch fencing, which keeps a stale asynchronous response from advancing the current continuation, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-agent-harness-transition-guards|Transition guards and the admission check]]**.

| Event family                                    | Required contents                                                                                                                                                                                                 | Reconstruction use                                                                                               |
|:------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------|
| `TaskStarted`                                   | Task and requester, initial grants and limits, ordinary and finalization deadlines, initial record and workspace references, configuration provenance                                                             | Establish the initial scope and accounting contract                                                              |
| `ContextBuilt`, `ModelReplied`                  | Model-call identity, immutable delivered-input manifest and bytes or available references, assembly and request configuration, reply status and payload, raw signals and available provider provenance            | Recover what was supplied and observed without resampling the historical invocation                              |
| `Authorized`, `BudgetReserved`, `BudgetSettled` | Decision and policy version, invocation or operation identity, reservation bound, actual usage evidence, remaining unresolved liability, protected finalization reserve                                           | Rebuild admission and accounting, not merely a remaining-balance scalar                                          |

The software repair worksheet illustrates how these identifiers link distributed lifecycle events. Alongside the workspace snapshot `ws_r18`, the identifier `operation_id=test_r18` designates the logical test suite invocation, while `attempt_id=attempt1` tracks the specific network transport attempt. If an asynchronous test executor returns an acknowledgment containing a cluster job identifier such as `job_tests_18`, that handle correlates future asynchronous callbacks with the original operation. However, a recovering worker can discover this link only if that acknowledgment was durably flushed to the log before the crash. A durable `ToolResult` may record an active execution state, a timeout, or a completed test report; the reducer interprets these payloads according to their authenticated provenance. If an asynchronous execution finishes after the supervisor has already timed out the enclosing step, the late-arriving `ToolResult` updates the operation table rather than corrupting an obsolete execution branch.

↩︎ The observation-eligibility protocol that routes late results to the operation table rather than the active turn is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-agent-harness-late-results|Late results and observation eligibility]]**.

Capturing model context requires equal diligence regarding immutability. The manifest in `ContextBuilt` must record the exact tokenized payload or byte stream delivered over the wire, rather than mutable file system paths or external URLs that could mutate before recovery occurs. The log must also capture available inference engine provenance (model checkpoints, serving system versions, and decoding configurations), recording any gaps because hosted model identifiers frequently hide upstream weight updates or inference engine modifications. When execution resumes, the replacement worker can assemble an updated prompt context from recent evidence while preserving the historical invocation records exactly as delivered.

Defining an event schema specifies what state reconstruction requires, but schema definitions alone cannot guarantee that writes reach disk before an agent issues network requests. If a runtime persists a model completion but crashes before flushing the subsequent tool intent, the recovering worker cannot determine whether an external tool call was dispatched, risking duplicate side effects. To resolve this vulnerability, the runtime must enforce strict write-ahead ordering between logging an operational intent and releasing its network dispatch.
