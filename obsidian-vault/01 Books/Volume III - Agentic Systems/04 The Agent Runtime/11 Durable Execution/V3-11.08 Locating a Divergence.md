# V3-11.08 Locating a Divergence

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-persistence-non-determinism

When an automated software-repair workflow undergoes regression replay, execution proceeds uneventfully until reaching the recorded targeted-test result for candidate patch `r18`. The stored test result itself remains identical, but a revised harness assembles a subtly different observation context for the subsequent model call. Waiting until the final repair verdict to compare the runs obscures this earlier discrepancy under layers of compounding tool calls and token generations. Effective debugging requires pinpointing the exact architectural boundary where two executions first cease to agree within the recorded evidence.

A **divergence point** is the first observable mismatch under a declared equivalence relation: between recorded and reconstructed state, between historical and revised harness logic on captured inputs, or between a golden trace and a live execution. Every comparison must explicitly define both its boundary and its equivalence criteria. In practice, two serialized JSON payloads might differ in a harmless trace identifier while representing the same permitted operation. Conversely, two tool invocations cannot be treated as equivalent simply because their shell commands match if they execute against different repository commits or working trees. A coarse turn counter obscures these distinctions when context assembly, model inference, authorization policy checks, and tool dispatch all unfold within a single turn.

### Boundary-By-Boundary Comparison

^sec-vol3-durable-execution-boundary-comparison

Separating those four intra-turn stages turns a coarse turn diff into a precise fault isolator: if the tool output at the end of one turn matches the recording, the first mismatch in the next turn must appear at assembled model input, model response, harness admission decision, or tool observation. A boundary-by-boundary comparison isolates that earliest mismatch by starting at a verified checkpoint or initial state and stepping forward through corresponding events in their recorded sequence. Stable invocation and operation identifiers align the traces across runs, preserving any concurrency ordering or partial-order dependencies required by the replay contract. At each boundary, the diagnostic runtime evaluates three elements: the inputs delivered to that stage, the transformation configured for it (such as a prompt template, parser, or security filter), and the resulting output. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.08 Locating a Divergence#^tbl-vol3-nondeterminism-mitigation|Table 6]] organizes this diagnostic evidence by the earliest architectural boundary where a mismatch surfaces, preventing engineers from confusing downstream symptoms with root causes.

| First observed difference              | Evidence to compare                                                                                                                          | What the difference establishes                                                                                         |
|:---------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------|
| Assembled model input                  | Delivered messages and tool descriptions, source and workspace versions, compaction output, assembly configuration                           | The compared calls did not receive the same recorded input; inspect the earliest changed dependency or assembly step    |
| Model response                         | Complete request, decoding parameters, requested and available served-model provenance, response status and payload                          | The responses differ under the visible conditions; unrecorded service internals may limit further diagnosis             |
| Harness decision or admitted operation | Recorded response, parser and policy versions, captured clock and control inputs, current grants and reservations, exact operation arguments | The supervisory decision differs; determine whether this is an intended policy change, a defect, or an uncaptured input |
| Tool observation                       | Logical operation and attempt identities, actual arguments, target snapshot, service configuration and returned evidence                     | The recorded outcomes or observations differ; determine whether the requests and relevant environments were comparable  |

Table 6: **Evidence for Localizing Divergence**: Compare inputs and configuration at the earliest observable mismatch before interpreting downstream differences. A missing record limits the diagnosis rather than proving a particular cause.

^tbl-vol3-nondeterminism-mitigation

In the `r18` regression replay from the section opening, suppose the original trace recorded that `r18` passed a targeted unit test, but noted that the broader regression suite was omitted. The original harness forwarded both statements to the model. During regression replay with an updated prompt builder, a modified context-compaction rule drops the scope limitation while preserving the word “passed.” Because the replay supplies the identical recorded test output and workspace snapshot, the first divergence occurs at the delivered context input, before the runtime invokes the model. This immediate mismatch isolates the defect to the context assembly change, which stripped the qualification evidence. Whether this omission subsequently misled the model into making a false completion claim remains a separate causal question for controlled experimentation; the divergence itself is already localized.

Localization granularity depends entirely on what artifacts survive in the persistent store. A surviving cryptographic digest confirms that bytes changed but hides the omitted text, while recording only the agent’s final answer conceals every intermediate boundary. An informative diagnostic report identifies both the last boundary that verified successfully and the specific missing record that halted further automated comparison, rather than attributing the failure to whichever component appears last in the execution trace.

### Localization and Explanation

^sec-vol3-durable-execution-localization-explanation

Even after a boundary comparison flags a mismatch at a specific step, a hash difference alone cannot show which lines of prompt text changed, and matching hashes cannot explain why two identical prompts yielded different model replies. A cryptographic context digest verifies the byte-level integrity of the payload it covers, but it proves nothing about execution state outside that hash. Matching digests guarantee identical prompt text, yet sampling temperatures, decoding penalties, external tool schemas excluded from the hashed payload, model snapshot revisions, and provider configurations may still differ. Even when a visible request matches across every byte and parameter, hosted inference endpoints can still vary on the server. Conversely, unequal digests prove that the input representation changed, but explaining *why* requires inspecting the payload diff alongside its provenance metadata. Engineers must examine both the retained content and its lineage before drawing conclusions from hash comparisons.

Live model invocations can diverge even on identical prompts due to hardware and algorithmic factors. Lowering the temperature to zero or pinning a random seed standardizes the sampling policy, but it cannot eliminate variations from cluster-level accelerator scheduling, non-deterministic floating-point summation in parallel kernels, or silent provider-side model updates. Because an early divergence in a model response alters all subsequent prompts and tool invocations, downstream differences often reflect these cascading input changes rather than fresh errors. Debugging must center on explaining this initial point of departure.

↩︎ Floating-point reduction order and other sources of serving-path non-determinism are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.05 Autoregressive Generation#^sec-vol3-foundation-model-repetition-replay|Repetition and replay]]**.

Regression replay controls this cascading variance by supplying captured outputs at a declared boundary, following the principles developed in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.07 Recorded Trajectory Replay#^sec-vol3-persistence-replay|section 11.6]]. However, this isolation holds only if the harness captures every external dependency. If an authorization decision or scheduling check consults an unrecorded host clock, an unversioned environment variable, or a dynamic feature flag, determinism across that boundary collapses. When such leaks occur, developers must either capture the missing environmental inputs into the event log or narrow the replay scope to subcomponents with fully hermetic boundaries. Targeted interface interception in the harness achieves this control without requiring heavy, whole-machine snapshot infrastructure.

Sound diagnostic localization therefore yields a bounded engineering claim rather than an unverified causal leap. It specifies the earliest observed mismatch, catalogs the configurations and input artifacts confirmed to be identical, highlights the explicit differences found, and flags any missing evidence. While counterfactual replays can test whether a specific change explains the failure, observing an altered outcome in one trace does not prove that a fix behaves reliably across diverse workloads. Distribution-scale evaluation establishes the causal and statistical methodology needed to evaluate those system-wide claims; durable execution supplies the auditable evidence required to begin that inquiry.

**Checkpoint 11.3: Replay and divergence**

**First mismatch**: The recorded `r18` test result is unchanged, but a replayed context omits its coverage limitation. What has been localized, and what has not been proved?

**Equal hashes**: Two calls share identical context digests yet produce different model responses. Which request parameters and provenance fields must be compared before attributing the difference to model non-determinism?

**Capture boundary**: A replay reads the current host clock while evaluating a recorded human approval. Is the resulting mismatch necessarily an agent defect, and what changes would restore a meaningful comparison?

**Changed behavior**: Why can a revised security policy’s refusal represent an intended regression-test success, while an alternative model response following that refusal constitutes a brand-new execution branch?

These boundary comparisons depend on which events, delivered inputs, and environmental artifacts remain accessible. An agent runtime’s retention policy therefore decides which recovery guarantees and diagnostic claims the engineering team can defend in production, which makes it more than a storage cost optimization.
