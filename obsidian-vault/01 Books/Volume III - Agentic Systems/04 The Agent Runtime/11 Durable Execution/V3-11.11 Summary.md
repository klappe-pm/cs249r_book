# V3-11.11 Summary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-durable-execution-summary

Durable execution enforces a strict separation between what an agent runtime can verify locally and what actually transpires across external network boundaries. A runtime knows its own decisions, the dispatches it initiated, and the observations it received, provided each event reached storage provisioned to survive the declared failure domain before any dependent action occurred. What the runtime cannot deduce from internal logs alone is whether a dispatched request that yielded no response took effect in the outside world. Every mechanism examined in this chapter maintains this boundary. Durability must always be stated relative to a specific, named failure domain. Event log reconstruction replaces expensive model re-execution across recorded history. Ambiguous external outcomes remain explicitly assigned to an owner rather than resolved through speculative retries or uncoordinated model invocations. Providing these guarantees incurs concrete, quantifiable systems costs: a write acknowledgment per external dispatch, a brief coordination pause during checkpointing, a prompt prefill during cold resume, and about 1.5 cents per trajectory for a year of retention. Each overhead can be measured, budgeted, and amortized rather than avoided, and [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.11 Summary#^tbl-vol3-durable-execution-key-equations|table 7]] summarizes the governing relations that enforce dispatch ordering and balance checkpoint frequency against resume latency.

**Key Takeaways: Preserve the evidence needed to continue**

- **The event log, rather than the LLM context window, serves as the authoritative recovery record**: A deterministic reducer folds recorded decisions, delivered inputs, and resource reservations back into the trajectory’s control state. In the event of a crash, recovery incurs the modest CPU cost of local log reconstruction rather than invoking redundant, nondeterministic model turns. The prompt context is merely a transient view assembled from this underlying history, and cannot reconstruct past state on its own.
- **Durability is meaningful only relative to a declared failure domain**: An acknowledgment guarantees persistence only against the specific faults its underlying storage tier is provisioned to survive. Because the runtime must hold external dispatch until the intent is acknowledged, the write latency of that storage layer establishes the performance floor for every dispatch. An absent intent record proves that no dispatch took place only when the surviving log history can be verified as complete.
- **Fine-grained event logging shifts the checkpoint optimum**: Classical checkpoint cadence balances capture overhead against lost execution time. Because replaying a deterministic event log is orders of magnitude cheaper than invoking new model calls, logging each turn lengthens the optimal checkpoint stride by the square root of the re-execution-to-reconstruction cost ratio. In the worked trace, the stride grows by a factor of 14.1×. Because the cost curve is broad and flat around this minimum, choosing a stride within a factor of 2 raises the cadence-dependent overhead by at most 25 percent.
- **Resuming an agent requires acquiring authorization rather than merely restoring memory**: Reconstructed state explains why past decisions occurred, but the ownership lease, the fencing epoch, remaining token allowances, and human approvals govern subsequent actions. Any in-doubt external side effects and financial liabilities transfer intact to the new worker. A worker retaining compatible KV state avoids prefix recomputation, but the placement decision also depends on queueing, transfer delay, and capacity.
- **Deterministic replay serves a different diagnostic purpose than a live rerun**: In regression replay, the test harness feeds recorded inputs back into the agent logic with live tool execution disabled, isolating the exact state boundary where behavior diverges. Conversely, re-running an agent against live models generates an entirely new trajectory; because model sampling and external environments drift, divergences during a rerun cannot isolate where the original execution went wrong.
- **Retention policies must reflect operational guarantees rather than raw storage costs**: Fast crash recovery, regression replay, and post-incident auditing require different artifacts over distinct operational lifetimes. Long-term object storage is inexpensive. In the worked estimate, retaining every recovery and replay input for a full year costs about 0.7 percent of a single attempt. Eagerly pruning intermediate artifacts saves negligible budget while permanently forfeiting the ability to verify or reconstruct past runs.

^callout-takeaways--11-2-f4e02963

The principle of intent before effect (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-intent-before-effect|11]]) mandates writing an immutable record to durable storage before any external dispatch leaves the host, with durability calibrated against the failure domain the system claims to tolerate. Checkpoints and retained execution artifacts make this internal state reconstructible, while leaving in-doubt external outcomes explicitly visible to recovery supervisors. This discipline preserves the precise evidence that an automated or human recovery decision requires, while leaving the choice of recovery action to a separate policy that reads it. That separation also delineates the mechanical boundary of invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]). The runtime can guarantee that no admitted effect escapes unrecorded and that no settled effect repeats without an explicit idempotency contract. However, local logs alone cannot determine whether an in-doubt external request succeeded across the network, nor can they judge whether a historically recorded action was semantically correct.
