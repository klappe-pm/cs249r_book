# V3-11.02 Worker Failure Mid-Trajectory

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-persistence-need

![[90 Assets/Volume III/11 Durable Execution/Hsa Locator Hs df73049857.svg]]

*H·S·A locator with the Horizon and State axes highlighted in purple and Authority in gray.*

*Horizon stretches state past one worker’s life, so continuation needs a durable record.*

Consider a software repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) that has admitted and dispatched an integration test against `ws_r18`, a fixed workspace snapshot of candidate patch `r18`. Before the test runner reports a result, the worker process crashes, or the host suffers a spot preemption (the sudden reclamation of an ephemeral cloud node). A replacement worker cannot simply re-invoke the model with the original prompt. Starting over discards context: the pending test invocation, the active capability tokens and resource reservations, any pause state acknowledged by an operator, and any evidence indicating whether the remote executor accepted, completed, or failed the job. Worse, the original test suite may still be executing on a remote cluster, incurring financial charges and modifying sandbox state, while a newly launched model redundantly dispatches a conflicting command. This crash, with its dispatched but unreported test, is the chapter’s running worksheet, and each section asks what the surviving record says about it.

The agent harness already tracks most of what the replacement worker requires. Its live trajectory record separates pending execution continuations from outstanding external obligations, while its admission checks govern which actions may cross the runtime boundary. In a naive implementation, however, both structures reside exclusively in volatile host memory and vanish the instant the worker fails. The model’s context window cannot substitute for this operational state. A large language model (LLM) context contains only an episodic transcript shaped by bounded observation windows and prompt compaction; it contains no record of in-flight network sockets, admitted capability tokens, or active cloud billing meters. As the execution horizon expands across dozens of turns and long-running external tasks, worker crashes, node preemptions, and rolling updates shift from rare anomalies to operational certainties.

↩︎ The trajectory record that holds pending continuations and outstanding obligations is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.04 The Trajectory Record#^sec-vol3-controlplane-acb|The Trajectory Record]]**.

Surviving mid-trajectory failures requires durable history: an append-only, ordered log of every decision, admitted action, and received observation. With this durable log, a replacement worker can deterministically reconstruct the agent’s state, reconcile side effects that already reached external systems, and safely resume execution under valid authority. That capability names the chapter’s subject. A trajectory has **durable execution** when a different worker, after any failure the runtime declares it tolerates, can reconstruct the trajectory’s control state and outstanding obligations from surviving records and continue it without losing an effect that already escaped or repeating one unsafely. One ordering rule makes that possible. Under write-ahead durability, the record of an intended action becomes durable before the action is dispatched over the network. The rule is the runtime’s mechanical answer to the horizon and state exposures, a bound placed below the model that no prompt can supply. It carries measurable costs in acknowledgment latency on every dispatch, capture pauses at checkpoints, and reconstruction time on recovery.

The chapter builds the durable runtime in the order a crash demands it. First, the trajectory log ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.03 The Trajectory Log#^sec-vol3-persistence-event-sourcing|section 11.2]]) defines the record from which a clean worker rebuilds control state, and durable intent before dispatch ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-persistence-wal|section 11.3]]) orders that record against external effects while pricing the acknowledgment each failure domain requires. Folding an unbounded log and reconstructing mutated files from scratch would grow too slow over long runs, so checkpoints ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.05 Checkpoints#^sec-vol3-persistence-checkpointing|section 11.4]]) bind the control record to workspace snapshots at regular strides. The resume protocol ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-persistence-migration|section 11.5]]) then turns that reconstructed state into an authorized continuation under a new owner. The same durable records then serve offline debugging. Replay ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.07 Recorded Trajectory Replay#^sec-vol3-persistence-replay|section 11.6]]) inspects or tests history without new model calls, divergence localization ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.08 Locating a Divergence#^sec-vol3-persistence-non-determinism|section 11.7]]) finds the earliest boundary where two executions disagree, and retention ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.09 Log Retention and State Compaction#^sec-vol3-persistence-compaction|section 11.8]]) decides which of these recovery and replay promises the stored bytes can still keep. Each mechanism answers the central question of the worksheet crash by establishing what the surviving record proves and what ambiguity remains unresolved.
