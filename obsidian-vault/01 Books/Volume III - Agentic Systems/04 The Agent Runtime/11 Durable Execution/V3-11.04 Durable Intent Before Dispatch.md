# V3-11.04 Durable Intent Before Dispatch

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-persistence-wal

In the crash worksheet, the repair worker’s next step is to submit `test_r18` against workspace `ws_r18`. If the harness dispatches that test request across the network and crashes before the `ToolIntent` record reaches durable storage, a replacement worker folding the surviving log recovers a plan that still says “run the test.” Meanwhile the original job is already executing on the remote cluster and accruing charges. Recording only the eventual result leaves that blind spot open on every call. To prevent duplicate runs and untracked financial liability, the runtime must commit the admitted request and its reservation to persistent storage before that request ever leaves its control.

Recording the admitted request durably before dispatching it is classical **write-ahead logging** applied to trajectory dispatch. A durable history ensures that recovery can identify every external operation that may have begun, even if network partitions or crashes prevent the worker from ever receiving the reply. Under the runtime’s declared failure model, an external mutation that occurs without a recoverable record of intent is a **phantom effect**. Eliminating phantom effects requires two guarantees, strict write-ahead ordering in the runtime execution pipeline and a storage substrate that reliably outlives the failures the system claims to tolerate. Together they are the Part IV principle of intent before effect (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-intent-before-effect|11]]), whose ordering this section derives ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^eq-vol3-wal-ordering|equation 1]]) and whose storage half it prices.

↪ The database form of write-ahead logging, and why a runtime borrows its ordering but not its control over remote state, is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Distributed State Foundations#^sec-vol3-appendix-systems-transactions|Classical Transaction Background]]**.

**Definition 11.2: Durable intent**

***Durable intent*** is the immutable record of an admitted operation, capturing its identity, input arguments, a reference to its authorization decision and capability grant, and its budget reservation, acknowledged by storage that survives the declared failure domain before the request is dispatched.

1.  **Significance**: It converts a crash between dispatch and reply from an untracked phantom effect into an unresolved operation with an explicit owner, at the price of placing one durable acknowledgment on the critical path of every dispatch ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^tbl-vol3-durable-ack-domains|table 2]]).
2.  **Distinction**: A durable intent records that work may have escaped into the external environment. It does not certify that the remote endpoint committed or executed the work, nor does it mandate that a recovered worker must re-execute it.
3.  **Common pitfall**: Taking an acknowledgment from storage that shares the failure boundary the design claims to survive, such as writing to a local scratch volume under a system contract that promises resilience against host or volume loss.

The intent references the grant rather than copying a secret into it. A log retained for months and read during replay is the wrong place for a credential, so the secret stays with the credential broker, and a recovered worker obtains a fresh use of it only by passing admission under current ownership.

↩︎ The credential broker, which holds a secret outside the guest and uses it on behalf of an authorized request, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^sec-vol3-sandboxes-credential-brokering|Credential brokering]]**.

### Acknowledgment and the Failure Domain

^sec-vol3-durable-execution-ack-failure-domain

Suppose the repair worker appends the `test_r18` intent with a standard POSIX `write()` call, observes a successful return, and promptly dispatches the test. The host then suffers an immediate power failure. A successful `write()` guarantees only that the kernel copied the payload into its page cache; those dirty pages evaporate when the power cuts before writeback to disk. When the replacement worker boots, it finds an empty log, completely unaware that a remote test is already active. A returned `write()` therefore covers only the first failure domain of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.03 The Trajectory Log#^sec-vol3-persistence-event-sourcing|section 11.2]], a process crash on an intact host, while offering zero protection against host power loss.

This reasoning extends upward through the failure hierarchy. If a worker fails, a replacement process can recover using reattachable block storage, provided that the replacement can mount the disk and read the acknowledged log and artifacts. If the failure domain includes the permanent destruction of the worker’s storage volume, as in cloud environments where spot instances or underlying hardware failures destroy ephemeral disks, the acknowledgment must originate from a storage service outside that volume. Remoteness alone does not satisfy this requirement. An asynchronous replica updated out of band can lag the primary log, leaving the replacement worker with an incomplete history during a failover.

Each step up the failure hierarchy demands a correspondingly stronger persistence barrier. Surviving host power loss requires `fsync()` or `fdatasync()`, which returns only after the underlying storage device reports that the data has reached stable media. The two system calls differ in how they handle metadata: `fsync()` flushes file attributes such as modification timestamps, whereas `fdatasync()` flushes only the metadata strictly required to read the payload back. For a trajectory log that preallocates its disk files, using `fdatasync()` eliminates an unneeded disk seek and metadata write per barrier. Even with these system calls, subtle failure modes remain.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.15 Footnotes#^fn2|²]] If a drive contains a volatile write cache, it must honor the disk flush command before an acknowledgment truly covers power loss. Alternatively, the write must specify Force Unit Access (a per-write flag that bypasses the drive cache entirely). Even a verified local barrier, however, cannot survive the catastrophic loss of the physical drive or volume. Surviving permanent volume loss requires a replicated storage engine that returns a success acknowledgment only after a quorum of replicas, distributed across distinct failure domains, have committed the record.[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.15 Footnotes#^fn3|³]] The worksheet requires two durable copies outside the worker volume before dispatch. This chosen placement policy is stronger than the single-volume-loss requirement alone; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^tbl-vol3-durable-ack-domains|table 2]] lists acknowledgments that satisfy the stated contracts.

| Failure the contract tolerates          | Acknowledgment that survives it                                                                                                                                   | Acknowledgment that does not                                      |
|:----------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------|
| Process crash; host and volume intact   | Returned `write()`, which places the bytes in the kernel page cache that outlives the process                                                                     | An event queued only in the runtime’s own memory                  |
| Power loss or host crash; volume intact | Returned `fdatasync()` or `fsync()`, with the device write cache flushed or bypassed                                                                              | Returned `write()` alone, whose dirty pages were volatile         |
| Permanent loss of the worker’s volume   | Acknowledgment from a replicated store after two replicas outside that volume’s failure domain made it durable, under the worksheet’s additional placement policy | Local barrier plus an asynchronous copy that may not have arrived |

Table 2: **Durable Acknowledgment by Failure Domain**: The first two rows name the local barriers for their failures; the final row uses the worksheet’s chosen two-off-volume-copy policy. Moving down the table adds a wait, first for the storage device and then for network round trips to the slowest required replica, so the declared failure domain and placement policy set the latency floor of every dispatch.

^tbl-vol3-durable-ack-domains

The implementation must define precisely which failure modes its persistence layer covers, how storage errors surface to the application, and how a replacement worker discovers the complete authoritative history. Underlying storage engines provide the mechanical primitives, but the systems architect must establish the durability contract. When an acknowledgment fails or times out with an ambiguous status, the runtime must hold dispatch and resolve the append according to the storage contract. Resolution means re-reading the authoritative log. If the intent is present, the attempt is admitted but still unsent, so a pause or a failed recheck can still withhold it. If a complete authoritative prefix lacks it, the worker appends it again under the same event identity, which storage deduplicates if the first append did land. Holding back a dispatch during a storage outage may temporarily stall progress, but dispatching before confirmation permanently destroys the evidence required to govern in-flight work after a crash.

↪ Why a durability claim must name both its acknowledgment and the failures it survives, and how durability differs from atomicity and isolation, is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Distributed State Foundations#^sec-vol3-appendix-systems-boundaries|Guarantee Boundaries]]**.

### Durable Admission Ordering

^sec-vol3-durable-execution-admission-ordering

If a worker validates a proposal and reserves budget in memory (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.05 Trajectory States#^sec-vol3-agent-harness-transition-guards|Transition guards and the admission check]]**) but dispatches the network call before the storage acknowledgment returns, a crash in that gap leaves an untracked phantom effect. Durable execution closes that window by inserting an acknowledged intent write between admission and network release. For an attempt that proceeds to dispatch and later produces an observation, the ordering is

$$
{e_{\text{prop}}} \prec {e_{\text{auth}}} \prec {e_{\text{flush}}} \prec {a_{\text{ext}}} \prec {e_{\text{obs}}}. \tag{1}
$$

^eq-vol3-wal-ordering

In [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^eq-vol3-wal-ordering|equation 1]], ${e_{\text{prop}}}$ is the validated complete proposal, ${e_{\text{auth}}}$ is the admitted authorization and reservation decision, and ${e_{\text{flush}}}$ acknowledges its recoverable `ToolIntent` and required preceding records under the declared failure domain. The action ${a_{\text{ext}}}$ is dispatch, not endpoint completion. The event ${e_{\text{obs}}}$ is the later durable recording of received evidence, whose status may still be pending, partial, or unknown. The ordering constrains the events that occur, though an attempt can stop before dispatch or never produce evidence. Its payoff is that the position of a crash in this sequence determines what recovery may conclude ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^fig-vol3-intent-before-dispatch|figure 2]]). A crash before the worker receives ${e_{\text{flush}}}$ means the attempt was never dispatched, though an intent may already be durable if its acknowledgment was lost in transit. Recovery must inspect the complete authoritative prefix to determine whether that intent survived. Once ${e_{\text{flush}}}$ is durable, a crash at any point before adequate outcome evidence ${e_{\text{obs}}}$ becomes durable leaves an **in-doubt action**, an admitted operation whose outcome the surviving evidence cannot settle. Because releasing the network request ${a_{\text{ext}}}$ does not write a separate log record, the surviving log looks identical whether the worker crashed just before sending the packet, while the request was in flight, or after recording a pending or timeout observation. That window is the tool layer’s uncertain outcome (definition [7.4](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-uncertain-outcome)) seen from the recovery side, and it is what the fold of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.03 The Trajectory Log#^sec-vol3-durable-execution-log-evidence|section 11.2.1]] marked unresolved. Only recorded, correlated evidence establishes an outcome.

![[90 Assets/Volume III/11 Durable Execution/Vol3 Intent Before Dispatch 6d88035a03.svg]]

Figure 2: **Intent Before Dispatch**: The runtime validates a proposal, admits it with a reservation, and waits for the intent’s acknowledgment under the declared failure domain before dispatch carries the request past the durability barrier. Where a crash falls determines the recovery state of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^tbl-vol3-durable-recovery-states|table 3]]. Before the worker receives the acknowledgment, dispatch is withheld, but the intent may already be durable if its acknowledgment was lost. An absent intent establishes non-dispatch only when the authoritative prefix is complete. Between the acknowledgment and adequate recorded evidence, including a crash before dispatch, the operation is in doubt; a pending or timeout observation leaves it there. After correlated outcome evidence is recorded, the outcome is established within the endpoint’s contract.

^fig-vol3-intent-before-dispatch

In the crash worksheet, the intent names `operation_id=test_r18`, `attempt_id=attempt1`, the immutable `ws_r18` input, the selected check, and the endpoint’s repeat contract. It references the applicable `Authorized` and `BudgetReserved` decisions, together with the requester and task bindings, `control_epoch`, and `owner_epoch` under which they were made. The recoverable prefix must reconstruct the admitted reservation itself, rather than merely a remaining balance.

Admission and control stay coordinated while the barrier is pending. An operator pause or an administrative change in authority can still intercept and withhold an admitted but unsent request, because logging a durable intent records permission to dispatch rather than an irrevocable obligation to execute. The harness’s dispatch-time recheck, the last gate before the request leaves, re-evaluates the admitted attempt against current control state without reserving a second batch of budget. If the release mechanism already dispatched the request across the network, subsequent control actions must treat the request as sent. Conversely, a withheld request keeps its entry in the operation table and its reserved budget until verified evidence confirms that no remote side effects or financial liabilities remain.

↩︎ Dispatch-time rechecks, which re-run budget, authority, and approval checks at the moment of release, are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^sec-vol3-agent-harness-dispatch-rechecks|Dispatch-time rechecks]]**.

Foundation model invocations require identical rigor regarding identity and liability. Token generation streams over network sockets, and an interrupted invocation can incur charges on the provider’s bill even if a worker crash prevents the client from ever logging the output. The same ordering therefore covers model calls. The `ContextBuilt` record and the invocation’s `BudgetReserved` decision become durable before the request leaves, so a crash mid-stream leaves a logged invocation with no `ModelReplied`. Recovery treats that invocation as in doubt only for its charge, which it settles from the provider’s usage evidence. The lost reply cannot be reconstructed by replaying the prompt, because stochastic sampling produces a different completion, so recovery discards any partial stream and never replays the call. Any retry is a separately admitted invocation, requiring a fresh invocation identity, validated request and context, current admission checks, and a durable budget reservation before dispatch.

### Recovery Evidence and the Completeness Rule

^sec-vol3-durable-execution-completeness-rule

The first of the three recovery states in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^fig-vol3-intent-before-dispatch|figure 2]] (not dispatched) carries a hidden precondition. Following a crash, a recovering worker can treat the absence of a logged intent as proof that dispatch never occurred only if it holds the complete authoritative history promised by the failure domain. This requirement is the **completeness rule**. An asynchronously updated read replica cannot satisfy this rule, because the replica cannot distinguish between an operation that was never dispatched and an intent whose log record has not yet arrived across the network. [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^tbl-vol3-durable-recovery-states|Table 3]] outlines the recovery states governed by this rule.

| Surviving evidence                                                                            | What it establishes                                                                  | Consequence for continuation                                                                                       |
|:----------------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------|
| No durable intent in a complete authoritative prefix, under enforced write-ahead dispatch     | This attempt was not dispatched through the mediated path                            | Reconsider the recorded proposal under current admission checks; do not dispatch automatically                     |
| Durable intent plus adequate, correlated outcome evidence                                     | The recorded outcome is established to the extent supported by the endpoint contract | Reuse that evidence within its candidate and check scope; settle charges separately where necessary                |
| Durable intent without adequate outcome evidence, including a timeout or pending `ToolResult` | The operation is in doubt                                                            | Retain its identity, liability, and settlement owner; withhold dependent work until its guards permit continuation |

Table 3: **Recovery States of a Logged Action**: These classifications require a complete surviving authoritative prefix. An incomplete replica cannot establish that an absent intent was never dispatched.

^tbl-vol3-durable-recovery-states

In the crash worksheet scenario, the dispatched test may have failed to reach the service, may still be executing on a remote runner, or may have finished just before the worker crashed. If the executor’s reply accepting the job was never logged, its job handle, `job_tests_18`, is lost with the worker as well. To resolve this ambiguity, the runtime performs a targeted lookup using the logged operation identity, authenticating and correlating any newly discovered evidence before updating the operation table. A verified test result establishes the check for `ws_r18`; whether to accept the overall repair remains a distinct policy decision.

The in-doubt status reflects runtime uncertainty rather than external failure, and resolving it is a question about the endpoint. **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|Operation identity and endpoint contracts]]** details the endpoint requirements needed to execute a safe repeat: strict identity scoping, immutable payload binding, retention of prior execution results, handling of concurrent in-flight requests, and coordination between state mutations and returned values. A client-provided idempotency key protects only those endpoints that implement these semantics. Probing an endpoint by resource name provides much weaker guarantees, as a matching name might belong to an unrelated operation, while an absent resource could indicate that a delayed initial request is still in transit. For an in-doubt action, durable execution therefore applies settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]) unchanged. The log supplies the operation identity and its evidence, and only the endpoint’s contract or positive outcome evidence licenses another attempt.

↪ The idempotence and deduplication contracts behind a safe repeat are developed in **[[05 Reference/Volume III - Agentic Systems/V3 Distributed State Foundations#^sec-vol3-appendix-systems-retries|Repetition and Result Recovery]]**.

**Systems Perspective 11.1: Write-ahead logging, from pages to endpoints**

Database write-ahead logging forces a modification’s log record to stable storage before the corresponding dirty page can be written to disk, ensuring that crash recovery can redo committed updates and undo uncommitted ones ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-gray1992|Gray and Reuter 1992]]; [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-mohan1992aries|Mohan et al. 1992]]). This dual guarantee works because the database engine exerts exclusive ownership over its buffer pool and disk pages. In contrast, an agent runtime logs intent for side effects that occur at remote endpoints outside its administrative control. The runtime log can reconstruct the internal state of the agent, but it holds no undo records for external systems, and external tool endpoints rarely expose a two-phase commit prepare phase to tentatively hold modifications ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-gray1978notes|Gray 1978]]). A durable intent is therefore a unilateral record that work may have escaped, with no prepared state at the endpoint that recovery could commit or roll back. Distributed systems architects reached an identical conclusion when scaling web architectures, replacing heavyweight distributed transactions with idempotent messaging across independent administrative domains ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-helland2007life|Helland 2007]]). The logging protocol applies directly; what changes is the recovery model, which must explicitly handle in-doubt operations whenever endpoint evidence is missing.

When surviving evidence proves insufficient to resolve an action, the operation table keeps an owner assigned for reconciliation or explicit operator intervention across timeouts, pauses, and terminal execution paths. Independent branches of execution can proceed under their own guards while dependent operations await resolution. Remediating an effect that is established but unwanted calls for a compensating action, a follow-up operation that undoes or offsets it, which **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^sec-vol3-sagas-architecture|The Trajectory Saga Pattern]]** develops.

### Group Commit

^sec-vol3-durable-execution-group-commit

Intent before effect puts one durable acknowledgment on the critical path of every dispatch. For a single trajectory the price is small, because a millisecond-scale acknowledgment sits beside a turn that spends seconds on model and tool work. The price that matters is throughput. An agent runtime managing dozens of concurrent trajectories pays that barrier separately for each dispatch, and every dispatch in the fleet queues for the same storage service. Under the worksheet’s replicated quorum contract, each barrier is a network round trip to remote storage nodes. **Group commit**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.15 Footnotes#^fn4|⁴]] mitigates this overhead by coalescing multiple ready log records into a single shared storage acknowledgment ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-dewitt1984|DeWitt et al. 1984]]). A batch coordinator aggregates pending intent records, issues one consolidated write to the replicated store, and unblocks individual dispatches only after receiving a successful quorum acknowledgment. Even within a batch, every individual trajectory strictly maintains write-ahead intent ordering before transmission.

![[90 Assets/Volume III/11 Durable Execution/Vol3 Durable Margin 001 5d70990738.svg]]

*Timeline with five arrival dots at staggered times, each followed by a horizontal line ending at a dashed vertical line labeled ack. Below the lines, a gray box labeled gather is followed by a purple box labeled flush that ends at the ack line. Text below reads first waits gather plus flush and last still waits the flush.*

*Every batch member waits the whole shared flush; only storage work divides.*

For a successful batch, let ${t_{\text{arr}, i}}$ be the time event ${i}$ enters the batching queue, ${t_{\text{start}}}$ the start of the batch’s storage operation, and ${t_{\text{ack}}}$ the time its durable acknowledgment becomes available. If notification delay is excluded, event ${i}$ waits

$$
{L_{\text{lat}, i}} = ({t_{\text{start}}}-{t_{\text{arr}, i}}) + ({t_{\text{ack}}}-{t_{\text{start}}}) = {t_{\text{ack}}}-{t_{\text{arr}, i}}. \tag{2}
$$

^eq-vol3-group-commit-latency

The first term in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^eq-vol3-group-commit-latency|equation 2]] captures queueing and batch aggregation delay, while the second term represents the shared physical storage latency. If a batch contains ${N_{\text{batch}}}$ records, dividing the storage duration equally yields an amortized storage cost of $({t_{\text{ack}}}-{t_{\text{start}}})/{N_{\text{batch}}}$ per event. Amortization, however, does not compress elapsed time. Every member in the batch must wait through the full storage round trip, plus internal scheduling overhead, before its request can be dispatched.

Increasing the batch size reduces storage overhead per record but increases the queueing delay experienced by early arrivals. Under light traffic, aggregation delay dominates, making a batch flush timer essential to bound tail latency. Under heavy load, throughput amortization keeps queue depths manageable, though very large payloads can eventually inflate the storage operation itself. With a 2 ms timer and a 4 ms quorum acknowledgment, a batch of 16 intents incurs only 0.25 ms of amortized storage work per intent. Yet the first arrival waits 6 ms, and even the final arrival still waits the full 4 ms storage round trip. A sound design therefore sizes the batch timer within the allowable dispatch latency budget, instruments queueing delay separately from storage service time, and never weakens the declared durability domain to shave milliseconds off dispatch latency.

**Checkpoint 11.1: Intent, evidence, and the durability domain**

**Failure domain**: The worker acknowledges an intent locally, dispatches the test, then permanently loses its disk before asynchronous replication. Does the remote replica’s missing intent license a fresh dispatch, and which acknowledgment in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^tbl-vol3-durable-ack-domains|table 2]] would have made that inference sound?

**Crash boundary**: `test_r18` has a durable intent and reservation but no durable result. List the possibilities that remain and the one piece of evidence that would narrow them fastest.

**Event meaning**: A durable `ToolResult` reports a timeout. Decide whether to release the test’s reservation, and justify the decision.

**Current control**: A pause is accepted after the intent becomes durable but before the dispatch-time recheck releases the request. Which check stops the request, and what happens to its reservation?

**Batch cost**: If the batch timer doubles while the batch size and storage duration stay fixed, which term of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^eq-vol3-group-commit-latency|equation 2]] grows, and what happens to the amortized storage work per intent?

Write-ahead logging protects the identity and liabilities of actions that escape the runtime, but an event history alone cannot reconstruct the state of mutated files, code repositories, or training environments. Each log boundary must therefore be coupled to a verified snapshot of the surrounding workspace, so that a recovering worker restores the precise execution context in which those actions were taken.
