# V3-11.09 Log Retention and State Compaction

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^sec-vol3-persistence-compaction

An agent can reconstruct its execution trajectory from a checkpoint at sequence ${j_{\text{ckpt}}}$ and its subsequent suffix only as long as both the event records and their referenced artifacts remain intact. An event that points to a deleted workspace snapshot `ws_r18` restores nothing. Conversely, retaining megabytes of raw compiler output is useless if the durable intent record for `test_r18` was prematurely discarded. Retention policies must therefore stem directly from the platform’s recovery contract (the exact state and replay capabilities the system guarantees to support) rather than from storage format convenience.

### Retention Lifetimes

^sec-vol3-durable-execution-retention-lifetimes

That recovery contract changes as a trajectory ages: an active run needs its latest checkpoint and in-flight operation table only until the task settles, whereas a regression test or compliance audit months later still needs the delivered prompts and tool outcomes, and raw profiler traces may be useful for only a few days of debugging. Expiring every artifact on a single timer either breaks long-window audit replay or forces the cluster to keep terabytes of raw telemetry for months. A production runtime must therefore separate three retention lifetimes: current recovery, historical replay, and optional diagnostics.

1.  **Current recovery** demands the minimum set of assets needed to resume a crashed agent immediately: the latest published checkpoint, the complete committed event suffix required to reconstruct the active state record and workspace, and every external artifact referenced by those records. It also requires the operation table that tracks in-flight operations, including attempt counts, mutual-exclusion reservations, and settlement owners. These operational obligations frequently outlive the worker process executing the task.
2.  **Historical replay** serves auditing, regression testing, and offline evaluation. Replay often requires earlier checkpoints, exact prompt templates, delivered model inputs, recorded completions, and environmental snapshots that online recovery has long since superseded.
3.  **Diagnostics and telemetry** capture ancillary metadata, such as raw network packet dumps, fine-grained profiler traces, or unparsed stdout streams that were filtered before reaching the model’s context.

Although these data classes overlap, each requires an independent retention schedule. A sound retention policy explicitly specifies the supported recovery boundary or replay window, the required artifact classes, the expiration triggers, and the subsystem responsible for settling unresolved work. A recovery guarantee holds only for data copies maintained within the declared failure domain. Pruning a required artifact prematurely breaks the recovery contract; retaining its cryptographic digest in a manifest does not preserve the missing bytes.

In the running crash scenario, `record_R_ckpt`, the workspace snapshot `ws_r18`, and the committed suffix through the `ToolIntent` for operation `test_r18` (attempt `attempt1`) constitute mandatory recovery inputs. The missing tool result remains unknown until reconciliation completes. The runtime can safely prune an unrelated diagnostic log without compromising reconstruction under a contract that never uses it. In contrast, deleting `ws_r18` destroys recovery entirely, because prompting the model to generate the patch again initiates a new, non-deterministic execution rather than restoring the candidate under test.

### Content-Addressed Payload Storage

^sec-vol3-durable-execution-payload-storage

Storing multi-megabyte payloads directly within sequential log envelopes quickly degrades storage engine performance and inflates write amplification. **Content-addressed payload storage**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.15 Footnotes#^fn9|⁹]] solves this by decoupling event metadata from bulk data: large payloads reside in dedicated blob storage, identified and verified by cryptographic content digests. Under this scheme, an event envelope remains compact, recording only the payload’s content digest, byte length, schema format, and storage location, alongside the bounded observation delivered to the agent model and its omission metadata. If that delivered observation is also offloaded to separate blob storage, it becomes a required recovery dependency as well.

For bounded observations, the tool contract governs what the runtime captured, what it omitted, and what remains accessible through subsequent reads. While an unparsed raw tail might be optional for a particular replay target, a file delta, model input, or result body consumed by a state reducer cannot be treated as optional simply because it is large.

↩︎ The truncation notices and inspection handles that record what a bounded observation omitted, and what stays retrievable, are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.07 Observation Stream Truncation#^sec-vol3-tool-calling-truncation-notices|Truncation notices and inspection handles]]**.

Write ordering between payloads and log envelopes matters for durability. A required payload must receive durable write acknowledgment from the storage system before any committed event envelope or checkpoint publishes a reference to it. Committing the reference first opens a crash window: if the worker fails while the payload write is still in flight, the log survives but records a dangling reference to missing bytes.

Upon retrieval, the runtime validates cryptographic integrity and checks tenant access permissions, because a content digest identifies stored bytes without granting permission to read them. Content addressing naturally deduplicates identical payloads across trajectories, allowing multiple runs on the same repository to share an immutable base workspace. However, task-specific provenance, confidentiality, and retention policies must remain strictly decoupled from storage deduplication. A shared payload can be reclaimed only when no active retention contract across any trajectory requires it, so expiring one task’s logs never deletes another task’s required dependency. Separating envelopes, per-turn payloads, and workspace snapshots in this way also makes the retention bill straightforward to price, revealing which storage classes actually drive operational costs.

**Napkin Math 11.2: The price of keeping every recovery input**

**Problem**: A repair trajectory runs 30 turns. Each turn appends 4 KB of event envelopes and 128 KB of delivered inputs and result bodies, and the trajectory pins one 50 MB immutable workspace snapshot. A representative standard object-storage tier costs \$23 per TB-month. What does retaining every recovery and replay input for 12 months cost, relative to a hypothetical \$2.10 attempt?

**Math**: The log holds 30 $\times$ (4 + 128) KB = 3.96 MB, and the workspace brings the total to about 54 MB. Retention costs 0.054 GB $\times$ \$0.023 per GB-month $\times$ 12 months $\approx$ 1.5 cents.

**Result**: About 0.7 percent of the attempt’s cost, of which the log alone is 0.05 percent.

**Systems insight**: A year of full recovery and replay retention adds under 1 percent to ${C_{\text{attempt}}}$ in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**, and the workspace snapshot, not the log, is 93 percent of the bytes. The bill grows linearly with retention months and bytes per turn, so the effective lever is sharing workspace bases by content address across trajectories of the same repository; truncating the log saves almost nothing. Set retention by the recovery and replay promise, because pruning a required artifact forfeits a reconstruction claim to save 0.05 percent of an attempt.

### Log Compaction

^sec-vol3-durable-execution-log-compaction

Keeping every event from the start of a trajectory grows the log without bound, even after a published checkpoint at sequence ${j_{\text{ckpt}}}$ has already captured `record_R_ckpt` and workspace `ws_r18`. Yet deleting that earlier prefix while the checkpoint is still staging, or while an audit replay still depends on it, breaks the runtime’s promises. **Log compaction** reclaims storage capacity safely by retiring the older prefix once a newer published checkpoint preserves the active state and all unresolved operations required by the current recovery contract. The retained suffix of subsequent events must connect seamlessly to the checkpoint’s exact committed sequence boundary. Before pruning any log records or referenced artifacts, the storage layer must verify both conditions: the replacement checkpoint and its dependencies are durable across the declared failure domain, and no active historical replay, auditing, or compliance obligation still depends on the older prefix.

Compaction preserves current recovery while deliberately shortening the historical replay horizon. Downstream systems cannot substitute a later agent context for an earlier one once the original inputs have expired. Similarly, squashing incremental workspace deltas into a single snapshot preserves the latest workspace tree while shedding intermediate revisions. A compaction policy must therefore explicitly define the surviving replay interval. An uncompacted event history grows monotonically with every turn, regardless of how tightly the agent manages its prompt token budget.

Systems engineers must not confuse log compaction with context compaction. Context compaction operates on prompt token budgets: when conversational history approaches model context limits, the runtime condenses prior turns and commits a `Compacted` event to the log. This event records the exact summary text delivered to subsequent model calls, preserving deterministic replay for future turns. The underlying historical events and payloads that generated the summary remain governed by their own retention policies rather than vanishing when the context window shrinks. Diagnostic telemetry can follow aggressive downsampling or retention rules; in contrast, recovery-critical events and payloads must remain bit-for-bit complete throughout their promised operational lifetime.

↪ Sampling and retention policies for diagnostic traces are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.04 Trace Retention and Privacy#^sec-vol3-evaluation-budgets|Trace Retention and Privacy]]**.

### The Storage Engine Contract

^sec-vol3-persistence-engine-design

A storage layer can quietly undermine durable execution if its ingestion mechanics treat every duplicate event key as a harmless network retry. When a worker retries a log append after a lost storage acknowledgment, the retried record carries the exact same envelope and payload bytes as the first attempt. If a bug or an unfenced zombie worker instead submits a timeout `ToolResult` for `test_r18` under an event identity or sequence number that the store already holds with verified success evidence, the two writes share a key while disagreeing on what happened. A plain key-uniqueness constraint (such as an `ON CONFLICT DO NOTHING` clause) cannot tell those two cases apart, so it keeps the stored record and silently hides the conflicting write. Ingestion must instead perform semantic deduplication, comparing the immutable envelope and payload against the stored record under a declared canonical encoding. An identical retry returns an acknowledgment for the existing record. A conflicting payload under the same identity signals an integrity violation or a split-brain failure (two workers both acting as owner), not an idempotent duplicate, so the store must raise an error or record a distinct conflict event that the operation table evaluates. Deduplicating an event insertion, moreover, never deduplicates an external side effect that has already occurred.

The same discipline governs how the engine manages capacity and replication. When disk saturation or transient faults block new commits, the runtime must apply backpressure and stall the trajectory rather than proceed speculatively. A bounded circular buffer may overwrite an older entry only after every recovery and replay contract has released it. Moving older logs to a cheaper cold tier obeys the same completeness rule: the local copy can be retired only after every referenced payload body, not merely its index entry, has arrived and been verified at the destination. Replication across nodes must preserve both prefix completeness and ownership provenance. A follower that receives records out of order may stage them in memory, but it can advertise a recoverable prefix only up to its first sequence gap. Fresh appends must validate the active lease and fencing token to block zombie writes, whereas replicated historical events keep their original worker provenance and timestamps rather than taking on the credentials of the replicating node.

At the physical layer, an append-only event model can sit on any storage engine that guarantees deterministic ordering. Key-value stores built on log-structured merge trees (LSM trees) ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-oneil1996log|O’Neil et al. 1996]]), for example, index immutable events under composite trajectory and sequence keys. In an LSM tree, storage-level compaction periodically merges the tree’s sorted on-disk files (sorted string tables) to reclaim space and speed reads. Despite the shared name, it is purely physical. It reorganizes bytes without changing the logical sequence of events, so unlike log compaction it never retires evidence. Overwriting an existing event with a newer state representation, by contrast, is a destructive application-level mutation, permissible only when a retention contract authorizes discarding the older evidence, because the order of observations and decisions is the agent’s causal chain.

Each cost derived earlier in the chapter therefore becomes a concrete requirement when selecting or configuring the storage engine. On the write path, the durable-acknowledgment boundary (local disk, quorum `fsync`, or multi-region replication) sets both the dispatch latency floor of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^tbl-vol3-durable-ack-domains|table 2]] and the batch wait of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^eq-vol3-group-commit-latency|equation 2]]. The engine’s internal write amplification multiplies the snapshot bytes that [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.05 Checkpoints#^eq-vol3-snapshot-bytes|equation 3]] already counts. Its blob-store integration determines whether the payload-before-reference ordering of [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.09 Log Retention and State Compaction#^sec-vol3-durable-execution-payload-storage|section 11.8.2]] can be enforced in one place. On the recovery path, sequential read throughput governs the suffix read time ${T_{\text{read}}}$ in [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^eq-vol3-resume-time|equation 7]], while atomic compare-and-set support on the `owner_epoch` determines whether the log itself can reject a stale owner’s appends without an external lock hop.

A single relational or key-value store suffices for modest deployments. At higher throughput, architectures often split into an online recovery store for low-latency point lookups by trajectory and an offline analytical store for columnar scans over historical replays. The analytical copy may lag the primary only while a durable, synchronized copy already satisfies the recovery contract within the declared failure domain, and every additional copy needs its own prefix synchronization, completeness verification, and retention policy.

**Checkpoint 11.4: Retention is a recovery promise**

**Missing dependency**: The checkpoint manifest and suffix survive, but `ws_r18` is gone. Which reconstruction claim is no longer supported, and why does its digest not repair the loss?

**Pruning boundary**: A new checkpoint supports current recovery. What else must be checked before deleting the older prefix, and which historical replay promises might be lost?

**Replication window**: A local intent is acknowledged and its tool request dispatched before the remote copy arrives. Which declared failure domain would make that ordering insufficient?

**Conflicting retry**: An incoming event has an existing sequence number but different result content. Why must ingestion reject the conflict rather than silently accept the duplicate key?

Retention completes the reconstruction contract by guaranteeing that committed evidence and required artifacts remain accessible after a failure. A storage engine faithfully preserves recorded uncertainties, but determining whether an external operation actually succeeded or produced correct side effects requires active reconciliation. Resolving in-flight ambiguities and reconciling orphan operations belong to effect-recovery policy, not to the storage engine.
