# V3-11.15 Footnotes

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution|V3-11 Durable Execution]]

^footnotes

<sup>1</sup> **Append-Only Log as Primary Record**: Rosenblum and Ousterhout’s log-structured file system treated the sequential log as the primary on-disk data structure, boosting write throughput and simplifying crash recovery ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-rosenblum1992lfs|Rosenblum and Ousterhout 1992]]). A trajectory log inherits these exact advantages: append operations never overwrite historical evidence required by future recovery passes, so a recovering worker can reconstruct state by streaming an ordered log rather than untangling conflicting in-place updates.

^fn1

<sup>2</sup> **Crash Consistency in Practice**: A study of eleven widely used applications, including databases, key-value stores, and version-control systems, found 60 crash vulnerabilities, because each application’s update protocol depended on subtle file-system persistence behavior that its authors had assumed rather than tested ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-pillai2014crash|Pillai et al. 2014]]). A trajectory log inherits the same exposure, so its durability claim should be checked by injecting crashes between every write and barrier, not inferred from the calls it makes.

^fn2

<sup>3</sup> **Quorum Acknowledgment**: Consensus protocols such as Paxos ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-lamport1998parttime|Lamport 1998]]) and Raft ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-ongaro2014search|Ongaro and Ousterhout 2014]]) commit a log entry once a majority of replicas store it; because any two majorities share a replica, an acknowledged entry survives the loss of any minority. The guarantee covers only failures the replicas do not share, so a quorum placed on one host or one power domain gives the latency of replication without the durability the worksheet’s contract requires.

^fn3

<sup>4</sup> **Group Commit Origin**: DeWitt and colleagues introduced group commit for main-memory database systems, where memory transactions executed so quickly that the physical log write at each commit became the primary throughput bottleneck ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-dewitt1984|DeWitt et al. 1984]]). Agent dispatch enters the same regime whenever durable intent logging requires a network round trip to a storage quorum, allowing classical database batching techniques to apply directly to trajectory logging.

^fn4

<sup>5</sup> **Consistent Snapshot**: Chandy and Lamport defined a consistent global state of a distributed system as one in which every recorded message receipt has a recorded send, and gave a protocol that captures such a state without stopping the system ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-chandy1985distributed|Chandy and Lamport 1985]]). A trajectory checkpoint obeys the same test on a smaller scale: the record must not refer to workspace bytes that the paired snapshot lacks, or restoration produces a state that never existed.

^fn5

<sup>6</sup> **Checkpoint Interval Lineage**: Young posed the problem for long batch jobs that saved restart information periodically so that a random failure need not restart the job from the beginning ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-young1974|Young 1974]]). The derivation assumes that lost work must be computed again; a trajectory whose turns are logged violates that assumption, which is why the interval lengthens once the log absorbs the lost-work term.

^fn6

<sup>7</sup> **Determinants**: Log-based recovery protocols record each nondeterministic event as a determinant, the information needed to reproduce its outcome during recovery, and are classified by when determinants reach stable storage ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-elnozahy2002survey|Elnozahy et al. 2002]]). In an agent trajectory the model reply is the dominant determinant: a sampled reply cannot be regenerated, so logging it is what lets the fold replace re-execution.

^fn7

<sup>8</sup> **Happened-Before**: Lamport showed that events in a distributed system are only partially ordered: one event precedes another when a chain of process steps and messages links them, and otherwise the two are concurrent ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-lamport1978time|Lamport 1978]]). Parallel tool calls in one turn are concurrent in this sense, so a replay must either record the order the harness actually observed or declare that any order is equivalent.

^fn8

<sup>9</sup> **Content Addressing**: Venti used a hash of each block’s contents as its identifier, which made stored blocks write-once and let duplicate copies coalesce into one ([[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.14 Source References#^ref-quinlan2002venti|Quinlan and Dorward 2002]]). Coalescing is what lets many trajectories over the same repository share a workspace base, and it is also why deletion must track references across tasks rather than per task.

^fn9
