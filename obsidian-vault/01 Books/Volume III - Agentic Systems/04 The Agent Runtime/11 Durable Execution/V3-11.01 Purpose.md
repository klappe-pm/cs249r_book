*Why must an agent write down what it is about to do before it does it?*

Real agent tasks, such as migrating an enterprise database or debugging a distributed codebase, run for minutes, hours, or days, long enough that process restarts, node preemptions, and rolling updates stop being rare events and become part of the workload. The harness that supervises such a task keeps its control record in the memory of a single worker, and the model’s context holds only a curated transcript, so one crash erases the admitted operations, held reservations, and pending approvals that tell a successor what may happen next. Restarting from the original prompt is worse than slow, because it resamples a stochastic model and may repeat an external effect, such as a deployment or a payment, that has already escaped. Durable execution answers with an ordering discipline inherited from transaction processing. The runtime appends every decision and observation to a log that outlives the worker, makes each intended action durable before dispatching it, and rebuilds control state by folding that history rather than by asking the model again. The log still cannot report what happened to a request whose reply never arrived, and keeping that ambiguity visible instead of guessing it away is what lets state survive a long horizon without corrupting the world the agent acts on.

**Learning Objectives**

- Construct a trajectory log whose fold rebuilds control state without treating recorded claims as world truth
- Apply intent-before-dispatch ordering under a declared failure domain, price its acknowledgment, and classify what each crash position lets recovery conclude
- Select a checkpoint representation and cadence from write volume, capture pause, and reconstruction cost
- Design a resume policy that reconciles outstanding obligations under current ownership within a stage-by-stage latency budget
- Distinguish time-travel replay of a recorded projection, harness regression replay, and counterfactual branches by the conclusion each supports
- Diagnose the first divergence between two executions from captured inputs, stating what the evidence cannot establish
- Design retention policies that keep the bytes each declared recovery, replay, and diagnostic promise requires
