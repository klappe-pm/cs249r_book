# V3-20.02 Answers to the Three Questions

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20 Conclusion|V3-20 Conclusion]]

^sec-vol3-conclusion-questions

Every mechanism in the book now carries a price in one unit, the cost per accepted task of each lighthouse (**[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.10 Cost per Accepted Task by Archetype#^sec-vol3-agent-economics-synthesis|Cost per Accepted Task by Archetype]]**). With that unit, the three architectural questions posed in the introduction, each answered in part by every later chapter, can be answered concisely. Each answer is a design claim that one live workload can test.

↩︎ The three foundational architectural questions governing agentic design are established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.09 Book Organization#^sec-vol3-intro-questions|The book's three questions]]**.

The first question asked when an adaptive, model-directed loop earns its cost over a deterministic workflow. The answer is settled not once for an entire application but at each decision point, by measuring the cost per accepted task under a fixed contract. A model should direct the next action only where interpreting dynamic, unstructured evidence improves the task acceptance rate by a larger factor than the added inference calls increase the cost of an attempt. Deterministic software should govern everywhere else. By this measure, a model-directed loop can earn its cost in phases such as root-cause diagnosis, where the next diagnostic step cannot be listed in advance, while deterministic control handles the predictable orchestration around it. On a production remediation attempt priced in [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.05 The Contract Behind the Incident#^sec-vol3-envelope-four-questions|section 20.4.2]], for example, model calls are a small fraction of the attempt’s cost; whether additional diagnostic calls earn that cost depends on the relative acceptance improvement measured against a matched baseline under the same contract and latency constraints.

The second question asked what operational machinery must surround the model. The answer scales with the task’s exposure to state, authority, and horizon. Carrying state across turns requires selectively retrieved context, explicitly budgeted serving state, and durable audit records that preserve source authority, whereas exercising authority over external services adds typed, mediated action interfaces, definitive effect settlement before any retry loop runs, and process containment enforced beneath the model. When those actions span a multi-turn horizon, the runtime must also wrap the trajectory in a supervisory harness, record a write-ahead log of intent before committing each external side effect, and register compensating workflows for actions that cannot be reversed cleanly. A read-only lookup needs little of this protective scaffolding, whereas an autonomous remediation agent operating on live production systems needs all of it.

The third question asked how operators verify that a task has actually succeeded. The answer requires objective evidence collected from an authoritative endpoint that directly monitors the target system, evaluated against an explicit contract adopted by system owners before execution began. This verification must satisfy a pre-declared closure evidence level, with any residual uncertainty explicitly quantified and assigned to an accountable owner. A model’s self-generated report never serves as evidence, however coherent or persuasive, because a component executing within the loop cannot certify its own output. Stated as an operational acceptance rule, this is the discipline of invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]).

Each answer is easy to state for a single component. Agent systems fail most often where the answers must hold across the boundaries between components, because services that pass their own tests can still drop an in-flight task when state, authority, and verification move from one to the next. Keeping those boundaries closed across a complete trajectory rests on the fifteen invariants developed across the book.
