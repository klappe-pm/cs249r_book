# V3-20.09 Safety Cases Built on Evidence

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20 Conclusion|V3-20 Conclusion]]

^sec-vol3-conclusion-safety

An incident record links an approved configuration change to an observed service outcome, but the link does not imply general correctness. The engineer must still establish which claims the record supports, which enforcement mechanisms make those claims trustworthy, and which failure modes remain unaddressed. That work takes the form of an empirical *safety case*: an inspectable, structured argument that specific claims hold within a defined operating envelope, not a certificate that the agent behaves correctly under all reachable conditions.[[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.15 Footnotes#^fn1|¹]]

Each case connects three elements: a *claim* states a specific operational property such as authorization validity or idempotency, an *argument* explains how the architecture and runtime mechanisms enforce that property, and *evidence* backs the argument with audit logs, telemetry windows, regression suites, and operator review traces. As assurance-case methodology emphasizes ([[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.14 Source References#^ref-lipson2013assurance|Lipson 2013]]), citing a governance tool or testing practice is not enough; the case must show enforcement, coverage, and relevance to the artifact actually deployed, and it records assumptions and counterexamples so that reviewers can see where the argument stops.

### The Incident Safety Case

^sec-vol3-conclusion-incident-safety-case

Showing that the rollback restored latency on the database during the health window does not prove that the remediation agent is safe to run on arbitrary database incidents. [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.09 Safety Cases Built on Evidence#^tbl-vol3-safety-case|Table 7]] scopes the safety case for this incident to the mediated database change and its observed outcome, combining runtime records with the validation suites a production case requires so that each row states what the case must verify rather than asserting that every offline test ran during the live incident.

|:---------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| The mediated change to `db_primary_01` requires approval for the exact request and current preconditions | The action gate checks `approval_42` against `change_request_42`, its target, desired settings, expected `config_v7`, and validity conditions before dispatch | The approval and admission records, together with tests of missing, expired, mismatched, and stale approvals                                                  | The argument depends on controlled access paths and endpoint enforcement; an unrelated privileged operator or bypass is outside this particular gate’s claim                                          |
| The lost response does not justify issuing a fresh duplicate change                                      | The settlement process preserves `op_42` for `operations_owner_42` and reconciles through the endpoint’s operation-status and deduplication contract          | Durable intent and obligation registration recorded before dispatch; the lost-response status; the later source confirmation that `op_42` applied `config_v8` | The endpoint must honor the stated identity, atomic version check, and retention contract, including delayed requests; unavailable status leaves the operation unresolved rather than proving failure |

^tbl-vol3-safety-case

An agent’s diagnostic report can point engineers to anomalous telemetry or inconsistent logs, but it cannot prove its own successful execution. A recorded operator sign-off counts as evidence only where the contract requires it, and human review has its own failure modes and blind spots, so it needs the same provenance and scope checks as an automated assertion.

### Release Evidence and Staged Exposure

^sec-vol3-conclusion-release-evidence

The three claims of [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.09 Safety Cases Built on Evidence#^tbl-vol3-safety-case|table 7]] concern one execution. Releasing the configuration that handled it is a population question, answered by the staged offline, shadow, and canary evidence of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^sec-vol3-evaluation-releases|Staged Releases]]** under causal and statistical release evidence (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-release-evidence|12]]). In that comparison this incident counts as a single trial, and halving the detectable difference between two configurations quadruples the tasks per arm (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-vol3-eval-planning-power|equation 13.3]]**), so one incident cannot settle a release. Had the rollback stayed unknown at the observation cutoff, that trial would count as unresolved even if latency later recovered, because healthy telemetry on one service does not settle an outstanding effect.

Staged exposure carries the limit the incident showed. Stopping a canary, revoking its tokens, or draining its traffic halts only future dispatches; a request the endpoint has already applied, as it applied the rollback before the reply was lost, persists with its settlement owner. A release safety case therefore documents how partially executed work is contained and settled rather than assuming that rolling back a container image restores world state.

↩︎ Tripwires that stop admission, and rollback that leaves transmitted requests and changed objects in place, are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.06 Staged Releases#^sec-vol3-evaluation-releases-tripwires|Operational tripwires]]**.

### Keeping Release Evidence Valid After a Change

^sec-vol3-feedback-stability

An incident trace does not automatically belong in a learning pipeline. If an engineer proposes extracting a segment as a training record, the training admission predicates decide whether its context, targets, permissions, and provenance qualify. An unresolved or aborted trace is not a negative example because a lost reply or an expired deadline can halt a trajectory after the model proposed the right repair, and penalizing that action trains the policy against valid proposals. Validation suites must also stay out of the training loop, because repeatedly selecting policies against the same evaluation set erodes its statistical validity ([[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.14 Source References#^ref-dwork2015reusable|Dwork et al. 2015]]). Here the verification asymmetry (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-verification-asymmetry|3]]) meets release evidence (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-release-evidence|12]]). Once a verification metric becomes a training loss or reward, it loses its standing as an independent assessment. This is Goodhart’s law in the form **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^sec-vol3-test-time-compute-selection-pressure|How search exploits imperfect checks]]** met it under search and **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.04 Verifiable Rewards#^sec-vol3-rlvr-score-intended-outcome|The score and the intended outcome]]** met it under training. Optimization concentrates on the verifier’s blind spots, so release evidence must come from checks the optimization never observed.

↩︎ The admission predicates for a training record, covering record fidelity, permitted use, process and outcome conditions, and target suitability, are established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.06 Staged Verifier Cascades#^sec-vol3-verifier-funnel|Admission predicates]]**.

Updating model weights or prompts produces a new configuration that needs fresh release evidence, not an endorsement inherited from past incidents. A weight update also invalidates serving state, since KV tensors computed under the old weights are not valid for the new model even when the prefix text is identical. The safety case therefore binds to the exact configuration scheduled for deployment, and the resolution of this incident remains an audit of one execution, not a clearance for later versions.

**Checkpoint 20.3: Defend the incident's acceptance**

Each prompt tests whether a piece of evidence supports the claim it is attached to.

**Claim scope**: Which records establish that the approved change applied, and why is acceptable latency alone insufficient?

**Missing evidence**: If operation status remains unavailable, what must stay unresolved and who retains responsibility?

**Evidence quality**: How can a model report or human review contribute without becoming independent proof of every claimed property?

**Evidence volume**: A team can afford only twice as many release tasks per arm. By **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-vol3-eval-planning-power|equation 13.3]]**, by what factor does the smallest difference it can detect shrink, and is that enough to rank two configurations that differ by a few points?

**Changed configuration**: Why do stopping candidate admissions and preserving the same prompt establish neither reversal of earlier effects nor compatibility of old KV state with new weights?

An inspectable safety case makes the acceptance decision transparent and lists its residual risks, including states outside the measurement window, shifting workloads, and unverified edge cases, as explicit design constraints. A case that names its limits is the only kind a reviewer can check.
