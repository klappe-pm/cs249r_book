# V3-20.08 Choosing a Remedy from the Evidence

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20 Conclusion|V3-20 Conclusion]]

^sec-vol3-conclusion-adaptation

An execution trace supports a more precise question than whether the agent needs a larger model. If the context manifest still presents the old configuration as current after settlement confirms the new one, the defect lies in state selection. If the runtime blindly retries the rollback after a timeout, the defect lies in outcome handling and the endpoint’s recovery contract. Further training might change how often the model reaches these paths, but new weights cannot supply a missing state transition or make a non-idempotent retry safe.

Intervention selection pairs an attributed failure with a targeted remedy, and the intervention ladder orders the candidates by cost and reversibility. Context and retrieval, tool interfaces, and runtime control come before changes to model weights, which are reserved for residual failures that evidence traces to the model’s behavior rather than to a missing record or check. The ordering is a default justified by cost, not a sequence every failure must climb; an authorization bypass points directly to a runtime enforcement repair.

↩︎ The intervention ladder ordering candidate remedies by operational cost and reversibility is established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.03 Capability Gap Diagnosis#^sec-vol3-flywheel-intervention-order|The intervention ladder]]**.

### Attribution and Remedy Selection

^sec-vol3-conclusion-remedy-selection

Placing a failure on that ladder requires more than reading the execution log, because a trace records only the path the run took. To isolate which layer caused a failed run of this incident, the engineer reconstructs the saved input, tool contract, runtime state, and outcome. The engineer then varies one suspected factor at a time in a counterfactual replay. Supplying the new configuration in the staged context tests whether stale state misled the model, and replacing a generic timeout with an explicit pending status tests whether the tool interface hid an in-flight operation. Once a single change repairs the failure on replay, the candidate fix is evaluated across the affected task suite alongside regression checks on unrelated workloads. [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.08 Choosing a Remedy from the Evidence#^tbl-vol3-intervention-ladder-tradeoffs|Table 6]] pairs each kind of intervention with the evidence that justifies it: three reversible structural fixes, two training changes, and delegation, which is a separate architectural decision.

| Intervention           | Evidence motivating the change                                                                              | Obligation the change leaves in place                                                         |
|:-----------------------|:------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------|
| Context and retrieval  | Needed facts are absent, stale, or obscured in the actual model input                                       | Validate source versions and preserve current task constraints                                |
| Tool interface         | Arguments or outcome states are ambiguous to the caller                                                     | Enforce authorization and distinguish a rejected request from an unresolved effect            |
| Runtime control        | Budgets, action preconditions, or settlement rules are not enforced at the responsible boundary             | Test enforcement and recovery under the declared failure model                                |
| Supervised fine-tuning | Admitted demonstrations represent a recurring behavior the current policy handles poorly                    | Supply current contracts and evaluate generalization and regressions                          |
| Reward-driven learning | New attempts can be assessed under a useful scoped reward without a demonstrated response at every decision | Protect assessment, inspect reward gaps, and evaluate held-out behavior                       |
| Delegated trajectories | Separate ownership and focused contexts may improve a declared task objective                               | Bound authority and spending, reconcile results, and compare with a capable single controller |

Table 6: **Evidence for an Intervention**: A causal diagnosis directs the remedy; no row guarantees improvement or removes the obligations enforced elsewhere in the system.

^tbl-vol3-intervention-ladder-tradeoffs

Adapting model weights reshapes which actions the model proposes; it never relieves the runtime of enforcing contracts, budgets, or security boundaries. Supervised fine-tuning imitates demonstrated recovery paths, and reinforcement learning from verifiable rewards optimizes behavior through exploration. Both must show their gains on the deployment distribution, and a sandboxed reward evaluator can still be gamed or miss edge cases of the task.

↩︎ Reward hacking, which exploits the gap between a verifiable reward and the intended task, is established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.04 Verifiable Rewards#^sec-vol3-rlvr-score-intended-outcome|The score and the intended outcome]]**.

Delegation lies outside the ladder. Partitioning a task across agents changes topology, ownership boundaries, and communication overhead rather than repairing a failed component, and a workload with cleanly decoupled subtasks may warrant it without any training. The baseline is a capable single controller with selective retrieval and parallel tool calls, and the comparison must charge the redundant contexts, serialization across dependencies, and reconciliation that make up the coordination tax (principle [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/V3 Agents at Scale Principles#^pri-vol3-coordination-tax|14]]). Diagnostic sub-agents reading logs in parallel could shorten triage for this incident, with no worker permitted to apply production changes, but only if the serial share and integration overhead pass the screen of **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^eq-vol3-multiagent-speedup|equation 18.1]]**. Diagnosis accounts for only 20 percent of this incident’s time to mitigate, while operator approval takes 50 percent and applying and verifying the change takes the rest. Because parallel sub-agents can compress only that 20 percent diagnostic window while approval and verification remain in the serial fraction of **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^eq-vol3-multiagent-speedup|equation 18.1]]**, the screen is hard to pass, which is why this incident closed without delegation.

↩︎ Benchmarking a multi-agent design against a single controller with matched tools, budgets, and concurrency limits is established in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^sec-vol3-multiagent-matched-conditions|Matched comparison conditions]]**.

An intervention that improves reliability must also pay for itself. A one-time investment in data, training, and evaluation is recovered only after enough tasks have run for the per-task saving to repay it (**[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.09 Pricing the Choice of Architecture#^eq-vol3-breakeven-volume|equation 19.8]]**), and the comparison holds only while both configurations accept the same share of tasks. Choosing an intervention therefore combines attribution, matched comparison, and end-to-end cost accounting, while authority and acceptance stay outside the configuration being changed. Once a remedy is chosen, the remaining question is what evidence supports releasing the changed configuration within its declared envelope.

↩︎ The break-even task volume of an adaptation investment is established in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.09 Pricing the Choice of Architecture#^sec-vol3-selection-adaptation-payback|Payback of an adaptation investment]]**.
