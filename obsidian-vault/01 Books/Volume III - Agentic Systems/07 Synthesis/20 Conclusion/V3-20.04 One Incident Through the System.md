# V3-20.04 One Incident Through the System

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20 Conclusion|V3-20 Conclusion]]

^sec-vol3-conclusion-capstone

A database service triggers a query-latency alert shortly after a configuration change. An automated remediation agent inspects telemetry, correlates logs, and proposes reverting to the previous known-good settings. The human operator approves the rollback, but the configuration endpoint drops the network connection before returning an acknowledgment. Whether the mutation took effect is now unknown, the classic dilemma of a lost acknowledgment in a distributed system, and no fluent explanation from a language model can resolve it. If the runtime treats the timeout as a failure and retries under a fresh operation identifier, it risks executing the mutation twice. If it assumes success, it risks closing an incident while degraded queries continue to affect production. If it simply halts, it leaves a live production change unverified, with no one accountable for reconciling it. Each failure mode arises by default when every component satisfies its local contract and no component owns the boundary between them. The end-to-end argument that grounded the closure evidence levels (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-invariant-closure|The invariant closure principle]]**) applies to this single incident. An intermediate success report from a tool or a model call cannot establish acceptance, and only the principal holding the task contract can verify completion against direct evidence from the service.

![[90 Assets/Volume III/13 Evaluation/Hsa Locator Hsa 18ba12f601.svg]]

*H·S·A locator with all three axes, Horizon, State, and Authority, highlighted in purple.*

*Horizon, state, and authority return together, and the runtime closes each on one trajectory.*

This incident, `incident_42` on database service `db_primary_01`, is a workload of the remediation agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**), the book’s irreversible actor, which operates over a bounded horizon, mutates shared production state, and exercises real authority over a live service. Its single trajectory, from diagnostic telemetry through operator approval, dispatch, and acceptance, anchors the rest of the chapter. At every transition the criterion is the same. The system must durably and verifiably record what it proposed, what permissions were granted, what effects occurred, what evidence validates the outcome, and which principal bears ongoing responsibility. In this architecture, the managed database service owns its active configuration, the runtime orchestrator owns execution and control decisions, and the accepting authority verifies whether post-remediation evidence satisfies the delegated operational contract. One named human principal, `operations_owner_42`, is accountable both for any operation the runtime cannot settle and for the service once the incident is accepted. The runtime’s settlement process, a runtime component rather than a person, reconciles uncertain operations on that owner’s behalf.

### Trajectory Ownership

^sec-vol3-conclusion-trajectory-owners

The incident lifecycle begins under `incident_contract_v1`, which grants bounded diagnostic read access and sets gates for proposing, approving, and validating configuration mutations. Because initial privileges are observational only, the runtime provisions `read_scope_42` to query authorized service endpoints so that telemetry gathering cannot inadvertently trigger state changes or be coerced into production writes. Throughout this trace, identifiers such as `read_scope_42` denote durable local record keys rather than opaque cryptographic hashes.

Next, the context manager gathers the initial latency alert, recent time-series metrics, active configuration parameters, and relevant runbook sections into an auditable manifest, `context_manifest_42`. Every observation in this manifest records its originating source, a version tag when available, and a precise ingestion timestamp. The retrieved runbook suggests a memory-pool misconfiguration, but it might describe a previous software deployment. By diffing the runbook recommendations against the active production configuration (`config_v7`) and current telemetry, the agent formulates a diagnostic hypothesis. Additional diagnostic queries, constrained by the task’s remaining call budget, must corroborate this hypothesis against alternative explanations such as downstream network congestion or disk saturation.

When the diagnostic evidence converges on a known regression, the model emits `change_request_42`, which specifies the target configuration keys, the desired values, and the expected baseline version `config_v7`. Under the incident change policy, an authorized human operator reviews the proposed diff and issues `approval_42`. This record binds the operator’s identity to the request identifier, the target host, the exact payload parameters, the prerequisite baseline `config_v7`, and an expiration window. The approval records permission for that exact payload and nothing broader; it does not perform the mutation. The model drafts the operational rationale, but it cannot grant itself execution authority. An approval granted minutes before execution is an earlier check, and complete mediation (definition [7.1](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-complete-mediation)) requires a fresh one at the moment of use. Before network dispatch, the runtime action gate therefore rechecks the operator’s authorization, compares the payload with the approval’s digest, checks the expiration deadline and resource quotas, and evaluates the runtime preconditions. If an operator revokes the ticket or the model generates an altered proposal, the original approval no longer matches and cannot silently apply to a mutated repair payload.

↩︎ Rechecking an approved request’s digest, expiry, budget, and authorization at the dispatch boundary is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^sec-vol3-agent-harness-dispatch-rechecks|Dispatch-time rechecks]]**.

Even a thorough pre-dispatch check leaves a time-of-check to time-of-use (TOCTOU) race if a peer operator changes the settings between the gate check and the write. The endpoint closes this window with the conditional update of **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-conditional-updates|Conditional updates]]**, an atomic expected-version check. It applies the change only if the live version still matches `config_v7` and otherwise rejects it, returning the task for re-diagnosis. The endpoint also makes the write idempotent in the sense of definition [7.5](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-idempotent-action). It deduplicates requests by an operation identity bound to the caller, target, and payload, and it keeps that identity for longer than the maximum client retry horizon, so a replayed request inside the window is recognized rather than reapplied. A read-only operation-status lookup completes the endpoint contract. These guarantees must live in the endpoint itself, since a client tool schema can declare an invariant but only the server can enforce it.

Before transmitting the RPC, the runtime appends an intent record for `op_42` to a write-ahead journal at the durability boundary chosen for the deployment, together with its *obligation registration*, which names the corrective-action template, the preconditions it must satisfy, and the accountable owner, `operations_owner_42`. Once both are persistent on disk, the runtime dispatches the request with operation identity `op_42` and expected version `config_v7`.

↩︎ Deduplication by an operation identity bound to caller, target, and payload is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|Operation identity and endpoint contracts]]**.

The endpoint’s response is then lost in transit, and the runtime sees a socket timeout. This is the lost-acknowledgment problem that opened **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.02 Recovering After Partial Effects#^sec-vol3-failure-recovery-introduction|Recovering After Partial Effects]]**, and the timeout yields no information about execution state. The network may have dropped the outbound packet, the endpoint may still be executing the transaction, or the endpoint may have committed the write and lost the acknowledgment on the way back. Instead of retrying blindly or declaring failure, the runtime logs the status of `op_42` as unknown and hands it to the settlement process, which issues an authorized status query against the endpoint’s operation registry rather than a second mutating RPC.

In the successful branch of this scenario, the lookup confirms that `op_42` committed the requested payload, transitioning the database configuration to `config_v8`. The immutable operation identity binds this remote confirmation to the local dispatch record, resolving the ambiguity even if the original RPC was delayed in transit. If the lookup instead returns an empty record or meets a transient outage, the settlement process cannot conclude that the mutation failed, because the original request might still be queued in the network. In that branch the status stays unknown, kept in its obligation registration as an open obligation of `operations_owner_42` rather than lost when the process terminates.

↩︎ Registering the recovery obligation alongside the forward intent, before dispatch, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^sec-vol3-failure-recovery-obligation-registration|Obligation registration]]**.

Confirming that `config_v8` committed settles the mutation but not the incident. The context manager retires the stale `config_v7` snapshot and assembles fresh telemetry under live load. Assume that latency percentiles and error budgets over an observation window, `health_window_42`, meet the thresholds in `incident_contract_v1` and that the policy checks pass. An authorized principal or automated gatekeeper then signs `acceptance_42`, which binds together the original incident contract, the operator approval, the settled operation identifier, the new active configuration version (`config_v8`), and the validated metric window. Only then is the incident formally closed under contract for the evaluated duration. Monitoring the service after the window passes to `operations_owner_42`, the same owner who would have held `op_42` had its status stayed unknown.

Seen from above, this one incident has crossed nearly every part of the book ([[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.04 One Incident Through the System#^fig-vol3-trajectory-lifecycle|figure 1]]). The adopted contract came first; the loop that diagnosed the regression was assembled from the model call, context, tools, and sandbox of Parts I to III; the harness of Part IV wrapped every step; and acceptance rested on external evidence rather than the agent’s report. Learning and delegation never entered, because neither was needed to close this task.

### Untrusted Text in the Same Task

^sec-vol3-conclusion-adversarial-evidence

The diagnostic reads assembled in the context manifest also expose the trajectory to untrusted text, because production telemetry is rarely sterile. A log entry or issue tracker comment fetched under the read grant can carry an indirect prompt injection, instructions written to exfiltrate database credentials to an external server. The payload enters the agent’s context through an authorized diagnostic read, yet the untrusted text inherits none of the operator’s administrative authority. An agent that acted on it would be the confused deputy of definition [7.3](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-confused-deputy), spending the operator’s grant on the attacker’s intent. Structured provenance tags and XML delimiters help the model separate ingested data from instructions, but model comprehension is not a security boundary. Isolation outside the model runtime must govern what a schema-valid tool call can execute with legitimate system privileges.

↩︎ Indirect prompt injection, delivered through an observation the agent reads rather than by the interacting user, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.03 The Adversarial Threat Model#^sec-vol3-security-injection-entry-points|Prompt injection entry points]]**.

In this scenario, an attempted exfiltration meets several independent barriers. If the manipulated model emits a tool call directed to an unauthorized external IP address, the runtime action gate blocks dispatch, because the read grant permits queries only against the named diagnostic endpoints and an arbitrary address is not among them. Independently of that grant, the sandbox’s egress policy drops unsanctioned outbound sockets at the network layer regardless of what code or parameters the agent generates. The read grant says which services the task may ask; the egress policy says which hosts any process may reach. Allowing unrestricted outbound connections would create an exfiltration channel even with local filesystems mounted read-only.

↩︎ Network egress enforcement placed outside the guest’s control boundary is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^sec-vol3-sandboxes-egress-enforcement|Enforcement outside the guest]]**.

The harder case uses only permitted operations. A diagnostic query to an endpoint inside the read grant can carry a database connection string in one of its arguments, and both the tool and the destination are allowed. The dispatch release check of **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-dispatch|equation 9.3]]** catches it. The credential carries a confidentiality label whose recipient set excludes the telemetry service, the label propagates into the query string built from it, and the reference monitor rejects dispatch because the recipient is not in that set. Layered constraints thus bound the blast radius of a successful injection, at the gate, at the network layer, and on the data itself.

When the action gate intercepts an unauthorized or malformed action, it appends the rejection to the audit journal as an undispatched intent. An operation that has already crossed into production is a different matter, because terminating the sandbox does not undo an external state change; the operations owner must determine from the audit log which side effects materialized and select the compensating action. If an adversarial prompt leads the model to assert that latency has normalized, the runtime ignores the assertion, since model output never substitutes for telemetry verified across the health window. The same ownership boundaries that handle component outages handle adversarial attacks.

The remediation trajectory terminates with a single model and a single runtime controller. Mining the trace for post-training or delegating sub-problems to sub-agents are later, optional decisions ([[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.06 State and Evidence Across Boundaries#^sec-vol3-conclusion-seams|section 20.5.2]], [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.08 Choosing a Remedy from the Evidence#^sec-vol3-conclusion-adaptation|section 20.7]]); neither optimization alters the authorization invariants required to dispatch the rollback or the empirical evidence demanded to seal the acceptance record. What governed every gate along the trace, before any diagnostic query or rollback ran, is the incident’s task contract.
