# V3-20.07 Execution, Settlement, and Recovery

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20 Conclusion|V3-20 Conclusion]]

^sec-vol3-conclusion-execution

The incident trace resolved its lost reply with a single status query, and it could do so only because every piece of state that query needed was persisted before the network dropped the reply. Three properties made each step admissible: durability that covers the declared failure domain, evidence states the runtime keeps apart, and obligations that outlive the process that created them.

### Durable Intent Before Dispatch

^sec-vol3-execution-pipeline-stages

The trace wrote the intent for the rollback and its obligation registration before the request left (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-intent-before-effect|11]]), binding the operation to its request, approval, endpoint contract, reservation, and accountable owner. Registering the obligation only after a response would have left exactly the gap the lost reply exposed, an active remote mutation with no durable record of who must reconcile it. The ordering is a database write-ahead log applied to an external effect, with one difference that shapes everything after it. A database’s recovery manager can redo or undo a logged update itself. The runtime can neither redo nor undo the endpoint’s mutation: the log tells it which operation to ask about, and only the endpoint can answer. The acknowledgment must also cover the declared failure domain, since a local `fsync` does not survive the loss of the storage device, and the execution gate withholds dispatch when that acknowledgment is missing or ambiguous. Recording intent commits the system to track the operation, not to execute it, so a pause or a revoked authority can still withhold the unsent request.

↩︎ Durable intent, the admitted operation acknowledged by storage that survives the declared failure domain before dispatch, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-persistence-wal|Durable Intent Before Dispatch]]**.

### Lost Responses and Unresolved Operations

^sec-vol3-execution-sagas

Neither the expired timer nor the surviving intent log can say which of the trace’s three outcomes occurred. Because the agent’s local log and the external configuration service cannot share one atomic transaction, recovery from a lost reply depends on guarantees at the endpoint, and issuing an idempotent status query rather than a fresh mutation is settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]). Once correlated evidence confirms that the endpoint applied the new configuration, dependent tasks may consume the result, and any later replay of the same operation must conform to the endpoint’s repeat contract and pass admission checks again. [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.07 Execution, Settlement, and Recovery#^tbl-vol3-execution-pipeline-stages|Table 5]] separates boundary states that simple agent designs treat as interchangeable tool errors.

| Evidence at the boundary                                          | What the runtime may conclude                                               | Continuation and owner                                                                                           |
|:------------------------------------------------------------------|:----------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------|
| Current admission fails before this attempt is released           | This attempt was withheld through the gate; earlier attempts are unaffected | Record rejection and its reason; reconsider only under current authority                                         |
| `op_42` intent survives, but its response is lost                 | The external outcome remains unknown                                        | Withhold dependent mutation; `operations_owner_42` retains reconciliation and outstanding liability              |
| Correlated status evidence establishes application as `config_v8` | This operation’s effect is established under the endpoint contract          | Record settlement evidence; obtain the service-health evidence required for acceptance                           |
| Status remains unavailable within the follow-up allowance         | Automated reconciliation has not established the outcome                    | End this continuation as unresolved; retain the operation, evidence, reservation, and acknowledged handoff owner |

Table 5: **Execution Evidence and Continuation**: Local rejection, uncertain delivery, and established application support different decisions. Closing a continuation does not close an unresolved external obligation.

^tbl-vol3-execution-pipeline-stages

Settling the operation does not complete acceptance, which still needs service-health evidence. The operation’s budget reservation also stays open until settlement, because a charge for remote work can arrive after its reply, as the canceled child with a late bill showed in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.08 Spending Governance#^sec-vol3-agent-economics-governance|Spending Governance]]**.

### Recovery and Stopping Obligations

^sec-vol3-execution-watchdog

In this incident, the database configuration is restorable selected state, because the endpoint keeps the old version and a further versioned write can return to it. The queries the service answered while a wrong configuration was live are a different matter, a commitment that cannot be undone. That is why the health window, not a later rollback, limits the damage of a wrong change. To separate those cases before any mutation leaves the harness, a recovery contract asks three things of every effect before dispatch: its target state, the recovery action available under the task’s authority, and the evidence that would show recovery worked.

Even a write that restores the old configuration is a compensating step in the sense of the trajectory saga (definition [12.1](https://mlsysbook.ai/vol3/12_failure_recovery/12_failure_recovery.html#dfn-trajectory-saga)). It is a new forward action that observers may see half-applied, not an erasure of the first. It needs current credentials, approval, and preconditions checked against the live service, the same admission the typed action contract (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-strict-action-abi|7]]) applies to any forward action. Because the operation was itself a rollback, restoring the old configuration would reinstate the one the incident was opened against, so the useful correction after a wrong rollback is usually a newly diagnosed change. Compensations can themselves stall or fail partially. Rolling back a local workspace cannot reverse an external configuration change, just as a network cancellation request cannot guarantee that the remote endpoint stopped executing. Until an authorized successor acknowledges the handoff, every residual obligation stays with the operations owner.

↩︎ Restoring selected state, compensating a known effect, and managing a commitment that cannot be undone are established as recovery contracts in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.06 Irreversible Commitments#^sec-vol3-failure-recovery-recovery-contracts|Recovery contracts]]**.

Stopping a run must preserve admitted work in the same way. A semantic watchdog that halts a stalled loop can mistake legitimate polling of a pending status for a livelock, so the harness backs it with a hard dispatch ceiling. A hold then suspends new speculative dispatches, preserves every admitted operation, and lets only separately authorized settlement and recovery work proceed.

↩︎ Semantic watchdogs that detect activity without progress are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.07 Semantic Watchdogs#^sec-vol3-sagas-watchdogs|Semantic Watchdogs]]**.

**Checkpoint 20.2: Auditing the incident's action boundary**

Each prompt names a failure at the action boundary; decide which record or check must catch it.

**Changed precondition**: `approval_42` names `config_v7`, but another operator changes the configuration before application. Which check must prevent the stale proposal from applying, and who may authorize a revised change?

**Retry exposure**: The log contains the intent for `op_42`, but no response. If some fraction of lost replies hide an applied change, what fraction of fresh-identity retries duplicate the change, and which endpoint guarantee brings that fraction to zero?

**Missing obligation**: A design registers the recovery obligation only after receiving success. Identify the failure interval this leaves uncovered and the record and owner that must survive it.

**Unresolved exit**: The follow-up allowance expires while status remains unknown. Which operation, financial liability, and handoff records must remain even though this continuation ends?

Because every failure in this trace is anchored to a defined boundary and an accountable owner, the record also shows where the next safeguard belongs. Choosing that safeguard is itself a decision that needs evidence.
