# V3-20.11 Essential Complexity and the Specification Boundary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20 Conclusion|V3-20 Conclusion]]

^sec-vol3-conclusion-brooks

Suppose an incident model proposes shortening the observation window so that the database service can be declared recovered sooner. The model can state the trade-offs, draft the revised acceptance predicate, and identify supporting metrics, yet none of that alters the incident contract. Until the authorized contract owner adopts a revision through the change-management policy, the runtime evaluates the incident against the existing criteria. Helping to formulate a decision is different from holding the authority to make it binding.

Brooks separated the essential difficulty of conceptualizing complex software entities from the accidental difficulty of expressing them in a particular programming language or machine environment ([[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.14 Source References#^ref-brooks1987no|Brooks 1987]]). In incident management, producing a configuration change is the accidental part; deciding which service behaviors count as recovery, and which risks the change introduces, is the essential work. An agent can generate a valid configuration payload while the recovery criteria remain poorly specified, and faster payload generation does nothing to resolve that ambiguity.

The boundary does not confine language models to syntax. An agent can propose requirements, weigh design trade-offs, expose inconsistent assumptions across services, or draft fault-injection tests, all of which is conceptual work, and its value depends on the verifiable evidence and arguments it produces. If a fraction of specification and review remains unaided by models, that work acts as the serial fraction in the Amdahl bound of **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^eq-vol3-multiagent-speedup|equation 18.1]]**, here with one human and one model rather than many workers. A task whose specification and review require half of the original effort cannot finish more than twice as fast, however quickly the model produces everything else, so end-to-end turnaround stays dominated by deliberate human specification and review.

The specification boundary applies the task contract of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-five-part-contract|The five-part task contract]]** to revisions of that contract, separating candidate proposal from authoritative adoption. The organization responsible for a service decides who may approve changes to its goals, permissions, and acceptance conditions, and the runtime enforces those policies. An agent gains no governance authority by authoring a new contract, and it cannot enlarge its own permissions or relax its evaluation when a task becomes difficult. This is invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) applied to the contract itself; the model can no more alter its own acceptance criteria than certify its own execution trace.

Approval bindings and acceptance records enforce the boundary in practice, because the agent cannot create either by declaring it. An agent that finds a real flaw in the criteria can trigger an authorized review, and the review records which contract governed the attempted execution and which evidence supports any revised claim, so that an unmet condition is never silently replaced by a more lenient one. Even a valuable contract revision proposed by an agent governs production only after it passes that formal adoption process.

The same boundary governs tests. An agent-written test suite has real value even when the model also drafted the implementation, but both can encode the same mistaken requirement. Candidates are therefore judged against the adopted contract, protected regression suites, live observations, and qualified human review, and agreement between a generated candidate and its co-generated tests never counts as independent verification. Across code, tests, and contracts alike, agents can support accountable decisions about bounded tasks, while deciding what those tasks mean remains the responsibility of the system’s owners.
