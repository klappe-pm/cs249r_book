# V3-05.13 Exercises

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management|V3-05 KV Cache Management]]

^sec-vol3-kv-cache-exercises

Unless a problem states otherwise, use the hypothetical reference deployment in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.13 Exercises#^tbl-vol3-kv-cache-exercise-givens|table 8]]. Its values are problem inputs chosen for round arithmetic, not measurements of any system. Take GB as $10^9$ bytes, count $2{P}$ weight operations per processed token, and model one engine iteration over ${n}$ token positions with the chapter’s weight-only estimate, ${t}({n}) = \max\left(5\;\text{ms},\; 2 {P} {n} / {R_{\text{attain}}}\right)$.

| **Quantity**                                  | **Symbol**                                      | **Given**                       |
|:----------------------------------------------|:------------------------------------------------|:--------------------------------|
| Model parameters                              | ${P}$                                           | $50 \times 10^{9}$              |
| Layers, key-value heads, head dimension       | ${N_L}$, ${H_{\text{KV}}}$, ${d_{\text{head}}}$ | 48, 8, 128                      |
| Bytes per stored KV element                   | ${s_{\text{elem}}}$                             | 2                               |
| KV pool after weights and runtime reserve     | ${M_{\text{pool}}}$                             | 400 GB                          |
| Sustained prefill rate                        | ${R_{\text{attain}}}$                           | $2 \times 10^{15}$ operations/s |
| Weight-read floor of one iteration            |                                                 | 5 ms                            |
| Aggregate host-link bandwidth, each direction | ${\text{BW}_{\text{link}}}$                     | 400 GB/s                        |

Table 8: **Reference deployment for the exercises**: Hypothetical givens shared by the problems below.

^tbl-vol3-kv-cache-exercise-givens

**1. Sizing retained state for a session target (Basic).** An operator must hold 200 unshared sessions resident at once, each retaining 16,384 tokens.

1.  Compute ${m_{\text{token}}}$ from [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^eq-mem-token|equation 1]], the payload ${M_{\text{KV}}}$ of one session, and the resident-fit bound in the pool.
2.  A multi-head variant of the same model stores 64 key-value heads per layer instead of 8. Compute its fit, and explain why no allocator policy can recover the difference.
3.  Two proposals would meet the target: storing KV at one byte per element, or having the harness cap retained context. Find the longest retained length that meets the target at two bytes per element. Then argue which proposal to try first and what evidence each must produce before it ships.

**2. When paging pays (Basic).** Static reservation sizes every request for a cap of 8,192 tokens. The request population’s mean final length is 3,072 tokens.

1.  What fraction of a reservation holds state at completion, and how many reservations fit in the pool?
2.  Paged allocation uses 32-token blocks, and final lengths have uniformly distributed remainders modulo the block size. Estimate the mean tail waste per sequence, its share of allocated KV memory, and the final-length snapshot count estimated by dividing the pool by the mean allocation. Repeat for 256-token blocks. Does this estimate alone determine live admission capacity?
3.  If the mean final length rose to 7,000 tokens under the same cap, how much of paging’s capacity advantage over static reservation would remain? Name one benefit of block allocation that does not depend on the length distribution.

**3. Moving one field (Basic).** A session sends four requests of 6,000 prompt tokens each. The first 4,500 tokens are invariant instructions and tool schemas, except for a request timestamp serialized after the first 300 tokens. The service reuses only complete 256-token blocks; the first request finds nothing cached, and each later request finds the earlier state resident, compatible, and permitted.

1.  Compute ${\rho_{\text{prefix}}}$ from [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^eq-hprefix|equation 2]] over the four requests.
2.  Recompute it after the harness moves the timestamp to follow the invariant prefix.
3.  For layout (b), how much weight-only prefill does each hit avoid, and how much more would a service that also reuses partial tail blocks avoid? Which change should the team make first?

**4. Choosing a chunk budget (Intermediate).** Forty-eight requests are decoding when an 8,000-token uncached prompt arrives.

1.  If the engine runs the prompt as one unit, what gap between tokens do the ongoing decodes see?
2.  The ongoing streams must see at most 25 ms between tokens. Using [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.07 Chunked Prefill Scheduling#^eq-kv-token-budget|equation 3]] with one position per decode, find the largest budget ${N_{\text{budget}}}$ and chunk size that meet the target, the number of iterations the prompt needs, and the time until its prefill completes.
3.  Ignoring the smaller final chunk, show that prefill completion is approximately $\left(2 {P} {S_{\text{new}}}/{R_{\text{attain}}}\right) \cdot {T} / \left({T} - 2 {P} \lvert{\mathcal{D}}\rvert / {R_{\text{attain}}}\right)$ for an inter-token target ${T}$ above the weight-read floor, where ${S_{\text{new}}}$ is the uncached prompt length. Find the tightest ${T}$ that still completes the prompt within 500 ms.
4.  Explain why a target approaching $2 {P} \lvert{\mathcal{D}}\rvert / {R_{\text{attain}}}$ is unworkable, and propose a design change for a service whose streams need 8 ms between tokens while new prompts need their prefill within 500 ms.

**5. Reload, recompute, and a return burst (Intermediate).**

1.  Evaluate [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^eq-kv-reload-ratio|equation 4]] for the reference deployment. How much faster is reload than recomputation, and why does the answer not depend on retained length?
2.  Below what sustained link bandwidth would recomputation become the faster way back?
3.  Forty paused sessions of 32,768 tokens each return at the same instant. Compute each session’s state, its isolated reload time, the reload completion time of the last session when reloads share the full aggregate link rate, and the time to recompute all forty sequentially from weight work alone.
4.  Each returning session must be restored within 250 ms. How many of the forty meet that target if reloads share the link fairly, and how many if they are served one at a time in arrival order at the full link rate? Propose two design changes that would serve the rest.

**6. Shared prefix and residence time (Intermediate).** Requests carry 24,576 prompt tokens and an output allowance ${K_{\max}} = 1{,}024$. A block-aligned common prefix of 16,384 tokens is compatible and shareable across all of them. Blocks hold ${S_{\text{blk}}} = 16$ tokens, and the planner withholds headroom ${f_{\text{head}}} = 0.10$. Each turn generates for 4 s and then waits 36 s for a tool.

1.  Using [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^eq-kv-demand-shared|equation 6]], compute the usable blocks and the resident-fit bound without and with sharing. Compare the gain with $1/(1-{f})$.
2.  The operator wants memory to sustain 10 turns/s. Using the shared fit and [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^eq-vol3-littles-law|equation 7]], what rate does keeping state through the wait sustain, and how many resident slots would the target require under that policy?
3.  Instead, each paused turn moves its private blocks to host memory and reloads them when the tool returns, while the common prefix stays resident for the other requests. Compute the memory-bound rate, the host-link traffic at 10 turns/s, and the restoration delay per turn. Is the link the binding resource?

**7. Fan-out over a shared source bundle (Advanced).** The research agent retrieves a 60,000-token bundle of source documents and fans the question out to 12 workers. Each worker’s input is the bundle followed by a 2,000-token private instruction, and each may generate up to 3,000 tokens. A synthesis call then reads the bundle followed by all 12 worker outputs. Ignore block rounding and headroom.

1.  A contiguous allocator deep-copies the bundle’s state into every worker. How much KV state does it copy? Compute the KV footprint of one question with and without block sharing, and how many questions each policy keeps resident in the pool.
2.  A developer serializes each worker’s private instruction before the bundle so that the model reads its task first. What happens to the shared footprint in (a), and what layout serves both goals?
3.  For the synthesis call, how much weight-only prefill does a hit on the bundle avoid, and how much new prefill remains? Contrast the constraint that binds this workload with the one that binds the repair agent in this chapter.
4.  A platform team proposes reusing the bundle’s KV state across different users’ questions that retrieve the same documents. State the conditions under which that reuse is compatible, available, and permitted, and explain why a hit says nothing about whether the documents are current or trustworthy.

**8. Paused state through a human approval (Advanced).** The remediation agent proposes a production change and waits for human approval. During a major incident, 60 trajectories await approval at once. Each retains 20,000 tokens: an 8,000-token invariant prefix, identical and shareable across trajectories, followed by 12,000 tokens of incident-specific diagnostics. Each turn generates for 6 s, approval takes 10 minutes, and the host can hold 1 TB of parked state.

1.  Under the keep policy, what share of the pool do the 60 trajectories hold without sharing and with the prefix shared, and what residency tax does the approval wait impose?
2.  Suppose the private blocks move to host memory and the shared prefix stays resident. Compute the host footprint, and compare the time to restore 20 trajectories whose approvals arrive together by reload with the time to recompute their private regions sequentially.
3.  Before acting on an approval, the harness must re-observe production state (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-source-authority|6]]), and the refreshed observations replace the diagnostics from token 8,000 onward. How much of the parked state remains usable? Recommend a paused-state policy, and say how the recommendation changes if refreshed observations were only appended after the existing diagnostics.
4.  Compared with the repair agent, what binds this workload, and how large is its restoration cost relative to the wait?

**What’s Next: From reusable computation to durable information**

Dropping the r18 request’s attention state forfeits no evidence, because the serving engine can rebuild it from the token log. The repair’s next session still needs that evidence once this serving session ends: the candidate at r18, the r17 failure, the passing reproducer, and the integration checks that remain unresolved. KV state can itself be moved or serialized, so storage location alone does not separate a cache from a memory. The unresolved problem is which information should persist, how it is identified and updated as its sources change, and how a later session retrieves evidence appropriate to its task. **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory#^sec-vol3-long-term-memory|Long-Term Memory]]** develops that durable-information contract.
