# V3-05.08 Paused-State Policies

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management|V3-05 KV Cache Management]]

^sec-vol3-kvcache-swapping

While the r18 repair request waits 45 seconds for its integration test suite (or whenever an agent blocks on an external tool or remote database), the model generates no tokens, yet retaining its KV cache in accelerator memory ties up scarce HBM. To prevent idle requests from starving active generation, the serving engine must execute a **paused-state policy**: retain the state in device memory, offload it to host memory or secondary storage, or drop it entirely and reconstruct it when the tool output arrives. Systems research on tool-augmented generation evaluated these same three mechanisms (preserve, swap, and discard), selecting dynamically among them per request to minimize wasted accelerator memory ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-abhyankar2024infercept|Abhyankar et al. 2024]]). This choice balances device memory capacity against host storage, interconnect transfer time, and recomputation latency.

Because the KV pool is a mechanical bound, invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) places this lifecycle decision below the model. The model cannot observe pool occupancy, its proposals cannot enforce a memory release, and the correctness of the next turn never depends on where the state was stored during the wait. The serving engine therefore executes the policy and chooses whether to keep, move, or drop the blocks, while the agent runtime may supply hints through the serving interface, such as the expected wait duration or the likelihood that the trajectory will resume.

↪ Harness supervision of resources retained during external tool waits is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.07 Supervised Waiting#^sec-vol3-agent-harness-retained-resources|Resources retained while waiting]]**.

### Reclaimable State

^sec-vol3-kv-cache-reclaimable-state

Evicting or offloading a paused trajectory frees far less memory than its logical token count suggests whenever its prefix blocks are still shared with active requests or pinned by in-flight transfers. Prefix blocks shared with concurrent trajectories, such as common system prompts or branching execution paths, must remain allocated on the accelerator as long as another request holds a valid reference. Similarly, blocks currently committed to in-flight asynchronous direct memory access (DMA) copies or active kernel operations cannot be freed until those transfers complete. The uniquely reclaimable footprint consists solely of unshared blocks with no pending operations, and every pause calculation must use this private footprint as its baseline.

Offloading state requires available capacity at the target tier and a coordinated handoff protocol. To maintain memory safety, the engine must preserve source blocks in accelerator memory until the outbound DMA transfer to host memory verifies successfully. During the transfer window, the state consumes both device HBM and host DRAM concurrently. The host-memory budget must therefore accommodate these transient transfer buffers alongside already parked trajectories. Upon resumption, the sequence reverses: the scheduler must allocate accelerator blocks, initiate an inward transfer, and update page tables before attention kernels can resume execution.

Discarding the KV cache relinquishes the computed state while preserving the underlying information, provided the raw input sequence and environment observations remain recorded in durable logs. Because attention state is derived from the token prefix (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-prefix-coherence|5]]), state lost this way can be derived again. If the request resumes, the engine reconstructs the missing attention state by re-running prefill across the historical prompt. This reconstruction requires exact provenance: the precise token sequence, active LoRA adapters, position encodings, attention masks, and multimodal embeddings. A compressed conversation summary cannot substitute for the raw token history. Reconstruction typically reuses any compatible prefix blocks that remain in memory and prefills only the missing suffix. In managed inference platforms, callers can exploit these trade-offs only to the degree that the hosting service exposes explicit prefix caching or session controls.

### Keep, Move, and Drop Policies

^sec-vol3-kv-cache-keep-move-drop

For those uniquely reclaimable blocks, the serving engine has three choices while the tool runs: keep them on the accelerator at the cost of HBM capacity, move them to host memory at the cost of interconnect bandwidth, or drop them and rebuild the suffix through prefill when the tool returns. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^tbl-vol3-reclamation-policies|Table 4]] compares how the three policies trade accelerator memory against restoration work.

| **Policy** | **Accelerator capacity released**                 | **Work needed on return**                      | **Principal constraint**                          |
|:-----------|:--------------------------------------------------|:-----------------------------------------------|:--------------------------------------------------|
| Keep       | None from the retained blocks                     | No restoration of those blocks                 | Retention competes with other allocations         |
| Move       | Reclaimable source blocks after a successful copy | Allocate and reload compatible state           | Destination capacity and contested transfer paths |
| Drop       | Reclaimable blocks after safe release             | Reconstruct missing state from retained inputs | Input availability and prefill capacity           |

Table 4: **Paused-state choices**: Restoration work is separate from queueing and processing the new observation, which can occur under every policy.

^tbl-vol3-reclamation-policies

Each policy targets a distinct operational regime. Retaining state on the accelerator is optimal when the memory pool has ample headroom and the agent anticipates an immediate return. Holding the blocks incurs zero marginal cost if no competing work requires memory, and it guarantees zero restoration latency when generation resumes. Under memory pressure, moving state to host DRAM releases accelerator capacity without discarding the completed prefill computation. Dropping state becomes the preferred choice when the probability of resumption is low, host DRAM is exhausted, or the context is short enough that recomputing prefill is faster than transferring the data across the bus. Whichever policy runs, the engine must enforce memory isolation boundaries so that retained, offloaded, or evicted blocks remain protected from unauthorized access by other tenants.

When pause durations extend across minutes or hours, as for workflows waiting for human approval, the engine can migrate state beyond host DRAM to non-volatile storage. Hierarchical serving systems organize storage across host memory and NVMe drives, prefetching cached layers sequentially so that retrieval from disk overlaps with execution of earlier layers ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-gao2024cachedattention|Gao et al. 2024]]). At data center scale, distributed architectures pool the host memory and solid-state storage of thousands of nodes into a shared cluster-wide KV cache ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-qin2024mooncake|Qin et al. 2024]]). Across all storage tiers, cached attention tensors represent derived, transient state; the durable history of user inputs, tool actions, and execution evidence resides in the runtime’s authoritative event log.

### Comparing Reload and Recompute During the Test Wait

^sec-vol3-kv-cache-test-wait-comparison

When the repair agent pauses at r18 for its 45 s integration test on the eight-accelerator node, its 32,768-token context puts concrete numbers on all three policies. With all historical KV entries materialized, every 16-token block completely filled, and no blocks shared or committed to in-flight transfers, the uniquely reclaimable cache footprint is 10.74 GB (excluding auxiliary page tables and transfer buffers, which the runtime budgets separately).

The transfer and recompute durations derive directly from hardware specifications. Because tensor parallelism partitions key-value heads evenly across the eight accelerators, each device holds one-eighth of the total state and transfers data over its own 64 GB/s PCIe link. When all eight links operate concurrently, the node moves state at an aggregate bandwidth of ${\text{BW}_{\text{link}}} =$ 512 GB/s. Offloading the complete 10.74 GB payload across this interface requires 21 ms, and restoring it upon resumption takes an identical 21 ms.

Reconstruction instead repeats the prefill pass. For a model with ${P}$ parameters and a sequence of ${S}$ tokens, evaluating the feed-forward and projection weights requires $2{P} {S}$ floating-point operations. At the sustained prefill rate assumed for the reference system, recomputing this context demands 1.3 s. Including the quadratic attention term of **[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^eq-appdx-prefill-long|equation 4]]** would lengthen it further. (Because every policy must eventually process the incoming test observation once the wait concludes, that downstream prefill is common to all policies and omitted from this comparison.)

In this weight-only comparison, both transfer duration and recompute duration scale linearly with sequence length ${S}$, so their ratio is independent of context size:

$$
\frac{{T_{\text{reload}}}}{{T_{\text{recompute}}}} = \frac{{S} \, {m_{\text{token}}} / {\text{BW}_{\text{link}}}}{2 {P} {S} / {R_{\text{attain}}}} = \frac{{m_{\text{token}}} \, {R_{\text{attain}}}}{2 {P} \, {\text{BW}_{\text{link}}}} \tag{4}
$$

^eq-kv-reload-ratio

![[90 Assets/Volume III/05 KV Cache/KV Reload Vs Recompute Margin 9ee637bd00.svg]]

*Two bars on a log scale from 1 millisecond to 10 seconds: a blue bar of 21 ms for reload over host links and an orange bar of 1.3 s for recomputing the prefill, with a bracket between their ends labeled about 62 times.*

*Reloading paused state beats rebuilding it by about 62× in the linear reference comparison.*

Here ${R_{\text{attain}}}$ represents the sustained prefill throughput, and ${m_{\text{token}}}$ is the cache footprint per token. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^eq-kv-reload-ratio|Equation 4]] applies the reload-versus-reconstruction comparison of **[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^sec-vol3-appendix-inference-queueing|Queueing for Trajectories]]** to this reference architecture. Reloading retained state is approximately 62× faster than recomputing from raw tokens. Even when heavy bus contention degrades link bandwidth to a quarter of its rated capacity, reloading remains 15× faster than prefill. Under this linear reference comparison, recomputation becomes advantageous when host DRAM capacity or PCIe bandwidth is sufficiently constrained by competing workloads, leaving accelerator compute as the less congested resource.

Retaining the cache on-chip throughout the 45 s wait ties up 10.74 GB $\times$ 45 s $\approx$ 483.18 GB·s of memory-time capacity (calculated using the unrounded payload). This cumulative occupancy translates into lost serving capacity whenever concurrent requests queue for device memory. Counted in request slots rather than bytes, that occupancy is a residence. Little’s law is the queueing identity that equates mean occupancy with arrival rate times mean residence. It converts this residence into a lost turn rate in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^sec-vol3-kv-workload-dynamics|section 5.8.2]], where the same wait divides the memory-bound rate by the ratio of the whole turn cycle to its generation time.

Moving the state to host memory immediately upon entering the pause releases those accelerator blocks as soon as the 21 ms outbound copy completes. The freed blocks can serve other queries for 45 s $-$ 21 ms $=$ 44.98 s before the test returns. The policy incurs 42 ms of total transfer work across the bus, but only the inbound reload sits on the critical path of the resuming query, adding 21 ms of restoration delay. Dropping the state avoids bus transfer entirely, but forces 1.3 s of prefill work onto the critical path before generation can restart.

If the engine can predict the tool completion timestamp accurately, typically from a hint the agent runtime supplies, asynchronous prefetching can schedule the inward transfer to complete precisely as the test finishes. Reserving the destination device blocks at the start of that inbound copy yields an accelerator release window of 45 s $-$ 21 ms $-$ 21 ms $=$ 44.96 s. Prefetching hides restoration latency completely while maintaining both transfer stages, though it requires reliable advance knowledge of return times.

The same reasoning extends to every context length and wait. The round-trip transfer time, which scales linearly with context length and equals 42 ms in this configuration, sets a necessary condition. A pause shorter than the round trip ends before offloading can move the state out and back without delaying resumption. Keeping it avoids restoration work when memory permits; under pressure, moving or dropping it may still be necessary. Above the round trip, offloading becomes possible, and whether it pays depends on whether other requests are queued for the freed memory and how much reload delay the resuming turn tolerates. For long pauses under memory pressure, offloading reclaims device memory for almost the entire wait at the cost of a sub-second reload. The worked 32,768-token, 45 s test sits far beyond that round trip. It also sits short of the much longer waits at which parked state accumulates enough to fill host memory, a boundary set by host capacity and by how fast paused trajectories arrive rather than by a fixed duration. The example therefore falls squarely in the offload regime ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^fig-vol3-swapping-tradeoff|figure 6]]). When pauses stretch into minutes or hours, as for operations awaiting human review, parked state accumulates in host memory, and the decision turns on host capacity, secondary storage bandwidth, or eventual recomputation.

### Uncertain Returns and Competing Transfers

^sec-vol3-kv-cache-uncertain-returns

External tool runs vary widely in duration: a test suite may fail immediately on a syntax error, finish early, or stall on an environmental hang, and this variance complicates offload and prefetch decisions. If a tool completes earlier than forecasted while offloading is still in flight, the engine must either wait for the outbound transfer to finalize before reloading or cancel the transfer mid-stream, exposing unbuffered restoration latency. Conversely, premature prefetching followed by a delayed return re-occupies accelerator memory while the model remains idle, negating the capacity reclaimed during the pause. If a paused trajectory is canceled or times out, an anticipatory inward reload wastes interconnect bandwidth outright. A robust pause policy must therefore evaluate the full probability distribution of return times alongside client latency service-level objectives (SLOs), rather than relying on mean wait times and uncontended transfer estimates.

Furthermore, transfers rarely occur in isolation. Multiple paused trajectories frequently finish their external tasks in close temporal proximity, triggering a surge of concurrent reloads across shared host-memory buses, PCIe switches, and storage links. Summing nominal per-accelerator link rates is valid only if interconnect topologies and memory controllers maintain non-blocking throughput under concurrent load.

Suppose 32 paused repairs on a node finish their external tasks simultaneously. Their combined attention state totals 344 GB, which requires at least 0.67 s to reload even when the eight host links sustain their maximum aggregate throughput. The final reload in the queue therefore experiences a restoration delay roughly 32× longer than the isolated 21 ms reload latency, and any congestion on shared bus root complexes lengthens the tail further. System engineers must provision transfer queues, admission controls, and accelerator headroom specifically to absorb these burst-induced restoration delays.

Pipelining can overlap data transfers with computation, but strict causal dependencies dictate which operations can run concurrently. In standard full-attention models, generating or processing new observation tokens requires access to all historical key and value tensors. An engine cannot compute attention for layer ${\ell}$ until the historical KV blocks for layer ${\ell}$ reside in accelerator memory. Transfer latency can therefore be hidden only if the engine streams state in layer by layer (reloading layer ${\ell}+1$ while executing attention on layer ${\ell}$) or if the node schedules unrelated generation requests while the paused state reloads in the background. Both techniques require careful engine coordination: layer-wise streaming requires fine-grained synchronization across DMA engines, while concurrent execution requires reserve accelerator memory to host the in-flight requests alongside incoming reload buffers.

### Reclamation Vs. Approximation

^sec-vol3-kvcache-intrasequence

Dropping individual tokens from an active KV cache or quantizing its keys and values shrinks memory occupancy without waiting for a tool pause. Unlike keeping, offloading, or recomputing, however, these lossy approximations alter the model’s forward pass and can silently break a multi-turn repair when an evicted token turns out to matter ten turns later. Because selective token eviction, local sliding windows, and low-precision KV quantization change the underlying model computation, their efficacy cannot be judged by memory savings alone; they require empirical validation against task accuracy. In agentic workflows, an eviction policy cannot assume that low attention weight during past decoding steps implies irrelevance in future turns.

The mechanics of **attention sinks** demonstrate why naive eviction schemes break down. Because softmax normalizes attention weights to sum to one across the sequence, transformer layers deposit residual attention mass on the initial sequence positions whenever a query has no strong semantic match among current tokens. A sliding-window policy that evicts those initial tokens removes this stabilizing mass, causing generation perplexity to degrade sharply once context length exceeds the window size. Retaining a small set of initial sink tokens alongside the sliding window restores numerical stability across long sequence streams ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-xiao2024streamingllm|Xiao et al. 2024]]). More sophisticated pruning strategies retain tokens that accumulate high cumulative attention mass ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-zhang2023h2o|Zhang et al. 2023]]) or that receive significant attention within a recent temporal window ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-liu2023scissorhands|Liu et al. 2023]]).

While past attention predicts future utility reasonably well in conventional conversation, agent trajectories routinely violate this assumption in three distinct ways:

1.  *Dormant constraints*: Instructions defined early in an execution trace (such as environment constraints, security policies, or API rules) often receive negligible attention across dozens of intermediate tool turns. When the agent produces its final edit or synthesis, violating those dormant instructions causes silent task failure.
2.  *Exact identifiers*: Unique entities like commit hashes, process IDs, file paths, and cryptographic nonces may appear once during environment exploration and remain unreferenced for many turns. If an eviction heuristic prunes these tokens because intermediate turns ignored them, the agent cannot quote them accurately in subsequent shell or API calls.
3.  *Tool-schema syntax*: Schema definitions and JSON delimiters in the system prompt govern the grammar of every tool call. Individual decoding steps frequently assign weak attention mass to structural delimiters like brackets and colons. Pruning them produces malformed syntax that crashes downstream parsers rather than a graceful degradation in output quality.

Cache approximation in agentic systems must therefore be evaluated against hard semantic dependencies rather than aggregate perplexity. The lossless policies (keep, move, and drop) cost interconnect bandwidth and tiered memory capacity, but they preserve the full-attention computation for the same recorded inputs and compatible configuration, subject to numerical differences across implementations. They decide where one paused trajectory’s state lives. They leave open how many trajectories a node can carry when each one holds memory for its whole residence, waits included, and answering that requires putting time into the capacity accounting.
