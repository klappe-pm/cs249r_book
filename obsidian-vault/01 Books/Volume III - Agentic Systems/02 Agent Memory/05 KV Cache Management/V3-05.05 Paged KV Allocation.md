# V3-05.05 Paged KV Allocation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management|V3-05 KV Cache Management]]

^sec-vol3-kvcache-pagedattention

When an integration-test log extends an agent’s repair context, the serving engine need not relocate the existing KV tensor to find a larger contiguous buffer. Instead, it allocates additional fixed-size physical blocks and appends their identifiers to the request’s block table. The attention kernel dereferences that table when reading earlier token positions. PagedAttention demonstrated this combination of dynamic block allocation and noncontiguous attention over KV storage ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-kwon2023vllm|Kwon et al. 2023]]). Its lineage traces directly to paged virtual memory. The Manchester Atlas one-level store introduced paging in 1962 to decouple a program’s contiguous virtual address space from scattered physical page frames ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-kilburn1962onelevel|Kilburn et al. 1962]]). The block table applies this same indirection to token positions, allowing sequences to grow dynamically without requiring contiguous physical allocations.

**Definition 5.2: Paged KV block table**

***Paged KV block table*** is a per-sequence software mapping from logical token blocks to the physical KV blocks that store their initialized key and value entries.

1.  **Significance**: A sequence can grow by acquiring another block without relocating its existing blocks.
2.  **Distinction**: The table maps token positions for the attention kernel; it is not the accelerator’s hardware page table.
3.  **Common pitfall**: A mapped block has allocated capacity, but only its initialized token entries may be read as valid KV state.

### Token-To-Block Mapping

^sec-vol3-kv-cache-token-block-mapping

Once physical blocks sit scattered across accelerator memory, the attention kernel can no longer locate a token’s keys and values by adding a fixed stride to a single base pointer. It must resolve each token position through the sequence’s block table. Consider an illustrative block size of four tokens, chosen to make the mapping concrete rather than to recommend a production configuration. A ten-token prefix occupies logical blocks 0, 1, and 2. Its block table contains `[3, 7, 9]`: token positions 0–3 reside in physical block 3, positions 4–7 in block 7, and positions 8–9 in the first two slots of block 9. Physical block IDs are pool indices managed by the allocator, not raw memory addresses or token sequence numbers.

For any token position, the attention kernel determines its logical block index via integer division by the block size, consults the block table to locate the physical block, and calculates the token’s offset within that block using the modulo remainder. For token position 9 with a four-token block size, the kernel calculates logical block $\lfloor 9 / 4 \rfloor = 2$, looks up physical block 9, and determines offset $9 \bmod 4 = 1$ (the second slot). Computing the final byte offset in device memory incorporates the model layer, KV head index, and tensor stride conventions. This software lookup preserves logical sequence ordering even when physical blocks are scattered across high-bandwidth memory among other requests’ blocks, as panel (a) of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.05 Paged KV Allocation#^fig-vol3-pagedattention-mapping|figure 3]] traces for position 9.

Figure 3: **Block Table Indirection and Tail Copy-on-Write**: Panel (a) follows each logical block through its table entry to a physical block scattered among other requests’ blocks; position 9 resolves to logical block 2, then to physical block 9, slot 1. Panel (b) shows two candidates that share the full blocks 3 and 7, while candidate B’s private append first copies the two initialized entries of the shared tail into block 14.

^fig-vol3-pagedattention-mapping

Because every block in the allocator’s pool is interchangeable and of identical size, any free block satisfies an allocation request. Paging thereby eliminates external memory fragmentation at block granularity. The remaining memory overhead consists of block-table metadata, temporary scratchpad buffers, and unallocated slots in each sequence’s final block.

### Block Size and Tail Waste

^sec-vol3-kv-cache-block-size-tail

In the ten-token prefix traced in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.05 Paged KV Allocation#^fig-vol3-pagedattention-mapping|figure 3]], physical block 9 holds positions 8 and 9 in its first two slots while its remaining two slots sit empty. Because sequence lengths rarely align with block boundaries, the final block of a sequence typically contains such uninitialized slots. This internal fragmentation constitutes the **tail waste** ${\Delta_{\text{tail}}}$. For a block holding ${S_{\text{blk}}}$ tokens, tail waste is bounded by $0 \leq {\Delta_{\text{tail}}} \leq {S_{\text{blk}}}-1$, with an expected value of $({S_{\text{blk}}}-1)/2$ when sequence lengths yield uniformly distributed remainders modulo ${S_{\text{blk}}}$. A sequence whose length is an exact multiple of ${S_{\text{blk}}}$ incurs zero tail waste.

Block size trades allocation granularity against indexing overhead. Smaller blocks (for example, 16 tokens) reduce worst-case tail waste and permit fine-grained prefix sharing and copy-on-write duplication, though they inflate block-table metadata and increase indexing overhead for the attention kernel. Larger blocks (for example, 64 tokens) amortize bookkeeping costs and align more effectively with memory bus transactions and tensor core tile dimensions on modern accelerators, at the cost of greater tail waste and copy overhead during branch forks. Selecting an appropriate block size therefore requires balancing sequence length distributions, tree-search branching patterns, and hardware memory access characteristics.

**Napkin Math 5.2: Converting block size into KV storage**

**Problem**: Given the Llama 3 70B geometry and a 16-bit KV representation, what physical storage granularity and maximum tail slack result from two candidate block sizes?

**Math**: Each token requires 327680 bytes across all model layers and attention heads. Multiplying that unit footprint by 16 tokens yields 5.24 MB per block. Multiplying by 64 tokens yields 20.97 MB. These values are node-wide footprints summed across all model shards, not the local allocation on a single accelerator.

The maximum unused tail contains one fewer slot than a full block. A 16-token block can therefore leave at most 15 slots (4.92 MB) unused, while a 64-token block can leave at most 63 slots (20.64 MB) unused.

For a 32,768-token agent context, even the larger block’s worst-case tail waste represents only 0.2 percent of the sequence’s total memory footprint.

**Systems insight**: Because tail slack is bounded by at most one block per unshared sequence, its relative overhead diminishes as sequence length increases. At multi-thousand-token agent context lengths, tail waste ceases to be the governing constraint. Engineers should select block sizes primarily to optimize attention kernel throughput and sharing granularity, revisiting tail waste only when serving workloads dominated by short sequences.

*The final-length snapshot estimate is about 16× the full-cap reservation count.*

Translating these worst-case bounds into expected memory overhead requires evaluating the workload’s sequence length distribution. Consider final sequence lengths modeled as a capped exponential distribution with a mean of 2,048 tokens, bounded by the 32,768-token ceiling established for static reservation. Under this distribution, 16-token blocks leave 0.4 percent of allocated KV memory unused, whereas 64-token blocks leave 1.5 percent.

Dividing the same pool, which accommodated only 48 static worst-case reservations, by the expected paged footprint gives a planning estimate of approximately 780 final-length request snapshots, a 16× increase over full-cap reservation. This capacity multiplier represents the core payoff of paging: memory allocation expands incrementally as tokens are generated, rather than reserving buffer space for an upper bound that most requests never reach. Because the gain is close to the ratio of the cap to the mean final length (32,768 to 2,048), it measures how far the population falls short of the cap. This snapshot estimate describes a hypothetical population sampled at completion; the requests resident in a running service have a length distribution that also depends on growth and residence time, and actual admission must account for current unique blocks and promised generation growth. Moreover, a request like r18 that actually grows to the cap gains no final-length capacity from paging. What paging still buys it is growth without relocation, memory claimed only as tokens arrive rather than at admission, and block-level sharing with forked candidates.

### Copy-On-Write Prefix Sharing

^sec-vol3-kv-cache-cow-prefix-sharing

When a repair agent samples parallel candidate patches from the same prompt and tool-execution prefix to verify them empirically (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-verification-asymmetry|3]]), giving each branch its own contiguous KV buffer duplicates gigabytes of identical prefix state across every candidate. The breadth allocation of **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^sec-vol3-test-time-compute-breadth-axis|Parallel sampling along the breadth axis]]** already priced this difference: with the prompt stored once, peak KV demand grows as the shared prefix plus each candidate’s private tokens, whereas without sharing every candidate carries its own copy of the prompt. Paged allocation delivers the shared form by pointing every candidate’s block table to the same physical blocks across the common prefix whenever the model architecture and runtime configuration allow block sharing.

The difference is large at agent context scales. Under contiguous allocation, giving each of four candidate branches its own copy of an 8,192-token prefix requires writing 10.7 GB of KV state for the Llama 3 70B geometry, counting the four new copies and not the parent’s original. That is the footprint of one full 32,768-token context, since four copies of 8,192 tokens hold that many token positions. Under paged allocation, duplicating the block tables avoids copying any tensor payload. The engine updates software metadata and increments reference counters; cloning a block table requires work proportional to the number of block entries rather than the roughly ten gigabytes of underlying KV data.

A shared sequence tail requires special handling when branches diverge. If the final block of a shared prefix is only partially filled, two concurrent candidates cannot independently append new tokens into its remaining empty slots without overwriting each other. In the ten-token example, both candidates initially share the block table `[3, 7, 9]`. Physical block 9 contains only two valid tokens (positions 8 and 9 in slots 0 and 1). Before candidate B writes token position 10, the engine allocates a fresh physical block 14, copies the two initialized entries from block 9 into block 14, and updates candidate B’s final block-table entry to point to block 14. Candidate B then writes token 10 into slot 2 of its private block 14. This **copy-on-write**[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.15 Footnotes#^fn5|⁵]] operation leaves candidate A’s state unchanged, as panel (b) of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.05 Paged KV Allocation#^fig-vol3-pagedattention-mapping|figure 3]] draws. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.05 Paged KV Allocation#^tbl-vol3-kv-cow-trace|Table 3]] records the ownership transition, assuming these two candidates are the sole owners of the prefix.

| **State**                     | **Candidate A table** | **Candidate B table** | **Physical ownership**                                   |
|:------------------------------|:----------------------|:----------------------|:---------------------------------------------------------|
| Before append                 | `[3, 7, 9]`           | `[3, 7, 9]`           | Blocks 3, 7, and 9 each have two owners                  |
| After B’s private-tail append | `[3, 7, 9]`           | `[3, 7, 14]`          | Blocks 3 and 7 retain two owners; 9 and 14 each have one |

Table 3: **Partial-tail copy-on-write**: Full prefix blocks remain shared while the initialized portion of the tail is copied before a private append. The block IDs label allocations; they do not imply contiguous addresses.

^tbl-vol3-kv-cow-trace

Copy-on-write is necessary only when mutating a shared, partially filled block. When a candidate branches at an exact block boundary (for instance, after a twelve-token prefix using four-token blocks), token position 12 initiates a new logical block ($\lfloor 12 / 4 \rfloor = 3$). The generating candidate allocates an unshared block from the free pool and appends its ID to its block table, requiring no data copying. Similarly, if a partial tail block is already privately owned (reference count of 1), the candidate appends subsequent tokens directly into the remaining slots without allocation or copying. The engine selects the appropriate operation based on two state variables: the occupancy of the target block and its current reference count.

When an agent discards an unpromising candidate trajectory, the engine decrements the reference counts of its constituent physical blocks. A block returns to the free pool when its reference count reaches zero and all outstanding device operations (tracked via asynchronous completion events) have finished. A dormant prefix-cache entry ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kvcache-radix-tree|section 5.5]]) may also retain physical blocks even after an active request completes, preserving them across subsequent agent turns. Total physical memory consumption is therefore governed by the number of unique physical blocks resident on the accelerator, not the aggregate logical token count across all active candidates.

**Checkpoint 5.1: Reasoning about KV allocation**

The allocation policy must preserve each sequence’s state while managing capacity shared by many requests.

**Reservation estimate**: If the hypothetical mean final length doubled to 4,096 tokens under the same 32,768-token cap, what fraction of each static reservation would be populated at completion, and would static reservation admit any more sequences?

**External fragmentation**: Identify why the three free extents in the example cannot satisfy its contiguous request, and why a fixed-size block pool changes that condition.

**Tail ownership**: Trace a private append to a shared partial tail and distinguish it from an append at a full-block boundary.

**Reclamation**: Explain why ending an active request does not always make its blocks immediately reusable.

Paged allocation decouples logical sequence expansion from physical memory layout, eliminating external fragmentation while enabling zero-copy prefix sharing across concurrent trajectories. Sharing state across independent requests or across subsequent turns of an agent session requires a complementary mechanism, prefix caching, in which the serving engine identifies matching historical prefixes across disparate requests and manages cache retention under memory pressure.
