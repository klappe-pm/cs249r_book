# V3-05.04 Memory Fragmentation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management|V3-05 KV Cache Management]]

^sec-vol3-kvcache-fragmentation

When the repair agent runs an integration test and receives a compiler traceback or test log, its next generation step needs KV cache space for both its accumulated history and the newly ingested output. Yet neither the harness nor the serving engine knows in advance how many tokens the model will generate or how many tool turns will follow. A static footprint calculation sizes the tokens processed so far. The memory allocator governs what happens as sequences grow: how much spare buffer to reserve at admission, whether an expanding sequence must be copied to a larger region in memory, and how quickly freed capacity returns to the shared pool.

### Reservation and Growth

^sec-vol3-kv-cache-reservation-growth

Provisioning a contiguous memory buffer for the full configured token cap (${S_{\max}}$) the moment a request arrives guarantees that a growing sequence never stalls for reallocation or runs out of memory mid-generation. Yet it locks every unpopulated slot for the entire life of the request, so no concurrent sequence can use that capacity. This upfront policy is **static reservation**: because the maximum buffer is secured at admission, the sequence expands in place within its pre-allocated envelope. The reservation covers only KV cache state; activation tensors and temporary runtime scratchpads draw from separate memory pools.

In the 526.0 GB KV pool modeled above, an admission cap of 32,768 tokens requires 10.74 GB for each reservation. Dividing the pool by this single-request footprint bounds concurrency to at most 48 resident reservations, assuming balanced tensor-parallel sharding across accelerators and no auxiliary overhead beyond the baseline runtime reserve. The count matches the 32,768-token row of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^tbl-vol3-kv-payload-fit|table 1]] because a full-cap reservation is exactly that context’s footprint, whether or not the tokens ever arrive.

Now consider the resulting capacity utilization for a mixed request population, mostly short turns with occasional long trajectories like r18, all admitted under the same cap. If those requests finish at a mean length of 2,048 tokens, each reservation is only 6.25 percent populated even upon completion, holding 2,048 valid token states out of 32,768 allocated slots. During earlier decoding steps, utilization is lower still. Empirical evaluations confirm that this structural waste dominates naive serving systems: when Kwon et al. ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-kwon2023vllm|2023]]) profiled early systems, actual token state accounted for only 20.4 to 38.2 percent of allocated KV memory, with the remainder lost to reservation slack and fragmentation.

A second strategy grows a contiguous allocation incrementally as tokens arrive. When adjacent capacity is unavailable in the allocator’s address space, the memory manager cannot simply extend the buffer in place. Instead, it must allocate a larger buffer elsewhere, copy all existing key and value entries from the old buffer to the new buffer, and then release the original space. This approach incurs two severe penalties: the allocator must hold both buffers simultaneously during the transfer, causing transient memory spikes, and the synchronous copy consumes substantial memory bandwidth. Contiguity here refers to an unbroken span in the framework allocator’s virtual address space, even though the accelerator already translates virtual addresses to physical memory in hardware. The restriction comes from how standard attention kernels index memory rather than from the memory hardware itself. Because a conventional attention kernel locates each token’s keys and values by adding a fixed stride to a single base pointer, the allocator must keep a sequence’s entire KV tensor in one unbroken buffer and copy it whenever growth runs into an adjacent allocation. Hardware page tables alone do not remove that bottleneck for the serving engine, because the policies that govern KV reuse operate on token blocks in user space: how many tokens a unit of allocation holds, how many candidate sequences reference each unit, and when a shared unit must be copied before a write. Putting that indirection in a software block table that the attention kernel reads directly eliminates contiguous-buffer reallocation while keeping block sizing and sharing under the serving engine’s control ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.05 Paged KV Allocation#^sec-vol3-kvcache-pagedattention|section 5.4]]).

### Two Kinds of Unused Capacity

^sec-vol3-kv-cache-unused-capacity

Static reservation and incremental contiguous growth each strand capacity in a different place. Static reservation locks thousands of unpopulated slots inside active allocations, whereas variable-size contiguous buffers leave free capacity split across disconnected gaps too small to satisfy a new contiguous request even when aggregate free memory is ample. Unused slots locked inside an active reservation constitute **internal fragmentation**; free capacity split across disconnected extents too small to satisfy a contiguous request constitutes **external fragmentation**. This classic distinction originates in early storage allocation research for multiprogrammed systems[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.15 Footnotes#^fn4|⁴]] ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-randell1969fragmentation|Randell 1969]]). [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.04 Memory Fragmentation#^tbl-vol3-kv-fragmentation-taxonomies|Table 2]] separates them because each condition demands a distinct systems remedy: eliminating reservation slack cures the first, whereas changing the allocation granularity cures the second.

| **Condition**          | **Where capacity is unavailable**                           | **Consequence**                                                               |
|:-----------------------|:------------------------------------------------------------|:------------------------------------------------------------------------------|
| Internal fragmentation | Inside an allocation, beyond its initialized entries        | Other requests cannot use the reserved slots                                  |
| External fragmentation | In separate free extents of a variable-size allocation pool | A contiguous request can fail even when aggregate free capacity is sufficient |

Table 2: **Unused KV capacity**: Reservation slack belongs to an allocation; external fragmentation concerns free space that cannot satisfy a particular contiguous request.

^tbl-vol3-kv-fragmentation-taxonomies

Suppose an allocator has three free extents of 256 token slots each, separated by live allocations, when a new sequence arrives requesting 512 contiguous slots. Even though the allocator holds 768 free slots in aggregate (more than enough capacity to satisfy the request), the allocation fails because no single extent can hold 512 contiguous slots. The failure stems entirely from the contiguity requirement rather than an absolute shortage of memory.

In an agentic repair workload, this memory pressure becomes acute because a paused trajectory retains its allocation under naive retention policies while waiting for tool execution, even as concurrent requests demand memory to grow. A robust serving system therefore requires two complementary architectural mechanisms: first, a space-efficient allocation unit, which fixed-size blocks provide, and second, an explicit lifecycle and eviction policy, which [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kvcache-swapping|section 5.7]] develops.
