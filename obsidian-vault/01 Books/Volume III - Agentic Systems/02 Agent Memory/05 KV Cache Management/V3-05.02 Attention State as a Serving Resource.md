# V3-05.02 Attention State as a Serving Resource

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management|V3-05 KV Cache Management]]

^sec-vol3-kvcache-introduction

The connection-pool repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) has reached a candidate revision, r18. Its targeted reproducer passes, prompting the harness to submit a fully serialized request of 32,768 tokens and launch an integration test suite that runs for 45 seconds. If the serving engine holds the request’s attention state in accelerator memory throughout that entire wait, the device does no work for that workflow. The model generates zero tokens during the test suite, yet its retained state pins memory that another concurrent request could put to work. This is the tool-wait problem named in the turn lifecycle of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^sec-vol3-intro-execution-lifecycle|The six phases of a turn]]**. Preserving that state is a deliberate systems policy, and running an agentic service requires pricing that policy against its alternatives; although this 32,768-token request is shorter than the staged request of the context-engineering examples, every per-request footprint and transfer time below scales linearly with context length.

![[90 Assets/Volume III/04 Context Engineering/Hsa Locator S a07206df7c.svg]]

*H·S·A locator with the State axis highlighted.*

*State becomes a physical resource claim inside the serving system.*

Earlier abstractions stop short of that physical commitment. **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering#^sec-vol3-context-engineering|Context Engineering]]** established how the harness selects and refreshes prompt context for each call, and its prefix-layout calculation priced a cached prefix as a discounted line on the bill. Neither abstraction captures the physical footprint of the underlying computation. They do not say how many gigabytes of memory that retained attention state consumes, how many concurrent trajectories an accelerator can hold at once, or what the serving engine should do with that state when an agent pauses to await tool execution. Those mechanical questions decide whether an inference node that comfortably supports a single repair workflow can scale to sustain dozens.

↩︎ Pricing a reused prompt prefix at a discounted cached-input rate is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-exact-prefix|Preserving an exact prefix]]**.

Managing retained attention state is not solely an internal serving problem; it spans an operational boundary between two parties. The application caller controls its submitted context, tool execution timing, and any cache-management hints the serving API exposes. The serving operator controls physical device allocation, memory placement, compute scheduling, and retention policies. When the two belong to separate organizations, as with hosted commercial model APIs, the caller cannot manage physical accelerator memory directly. Instead, the application influences retention only through the interfaces and pricing tiers the service exposes. Distinguishing where these responsibilities divide clarifies which performance levers belong to the agent harness and runtime that run the loop around the model, and which belong to the serving engine, the inference software that executes model calls and manages accelerator memory.

The chapter follows the r18 request’s attention state through its life in the serving engine, and each stage raises the question the next one answers. Sizing the state from model geometry shows how few 32,768-token contexts fit in the memory left after the weights ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^sec-vol3-kvcache-geometry|section 5.2]]). Allocating that state naively strands much of the pool ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.04 Memory Fragmentation#^sec-vol3-kvcache-fragmentation|section 5.3]]), which fixed-size blocks recover while letting forked candidates share a prefix ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.05 Paged KV Allocation#^sec-vol3-kvcache-pagedattention|section 5.4]]). Sharing within one request invites reuse across turns, which needs an index over retained prefixes and a rule for what to evict ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kvcache-radix-tree|section 5.5]]). Whatever the cache misses must be prefilled without stalling other requests’ generation ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.07 Chunked Prefill Scheduling#^sec-vol3-kvcache-chunked-prefill|section 5.6]]). The test wait itself forces a choice among keeping, moving, and dropping the paused state ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kvcache-swapping|section 5.7]]). Finally, residence time turns a count of resident contexts into a sustainable turn rate ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^sec-vol3-kvcache-capacity-planning|section 5.8]]).
