# V3-05.09 Capacity for Agent Workloads

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management|V3-05 KV Cache Management]]

^sec-vol3-kvcache-capacity-planning

A paused repair task can hold key-value state in accelerator memory for minutes without executing a single forward pass, while an incoming request demands both memory capacity and execution time immediately. How an engine handles paused state dictates how many concurrent agent trajectories can fit in memory. Converting that static concurrency into a sustainable throughput, however, requires modeling how long each session holds its memory. Capacity planning therefore first establishes physical occupancy bounds and then couples those bounds to residence time.

Tracking memory demand in agentic serving differs from tracking standard batch inference, where every active sequence holds a private cache. In an agent workload, logical contexts overlap through shared system prompts and tool descriptions while continuations allocate private blocks and dormant prefixes wait to be reused or paged out. Summing the logical key-value footprints of all active trajectories therefore double-counts shared prefix blocks, whereas counting only the requests currently decoding tokens ignores the dormant KV state that still occupies HBM. Capacity planning must instead count unique physical blocks across the pool.

### A Resident-Fit Bound

^sec-vol3-kv-capacity-formulations

Sizing a node by dividing raw HBM by a prompt’s token footprint overestimates how many requests can safely run at once. This happens because each admitted request also needs room for its generated output, rounds its allocation to whole blocks, and shares part of the pool with runtime headroom. To build a capacity model that accounts for these bounds, consider a set of equal-length requests with input prompt length ${S}$ and a maximum generation allowance of ${K_{\max}}$ tokens. Because paged allocation hands out fixed-size blocks of ${S_{\text{blk}}}$ tokens, each private allocation rounds up to the nearest whole block. Without prefix sharing, every resident request must independently provision memory for its full prompt and output allowance. When requests share an identical, compatible prefix, however, the memory pool allocates those prefix blocks once and pays only for each request’s private remainder. For this simple decomposition, assume that the common prefix aligns cleanly with a block boundary; any trailing partial block follows the copy-on-write accounting described earlier.

The memory available for key-value caching is whatever high-bandwidth memory remains after allocating model weights and reserving memory for execution runtimes:

$$
{M_{\text{pool}}} = {M_{\text{HBM}}} - {M_{\text{weights}}} - {M_{\text{runtime}}} \tag{5}
$$

^eq-mkv-pool

Production deployments typically withhold an additional headroom fraction ${f_{\text{head}}}$ of this pool to absorb bursty intermediate activations and memory fragmentation. Given block size ${S_{\text{blk}}}$, a block-aligned common prefix of ${S_{\text{prefix}}}$ tokens, and a cache footprint of ${m_{\text{token}}}$ bytes per token across all layers, the total physical block demand across ${B}$ resident requests (every request whose state is resident, whether decoding or paused) must satisfy

$$
\left\lceil \frac{{S_{\text{prefix}}}}{{S_{\text{blk}}}} \right\rceil + {B} \left\lceil \frac{{S} + {K_{\max}} - {S_{\text{prefix}}}}{{S_{\text{blk}}}} \right\rceil \le \left\lfloor \frac{(1-{f_{\text{head}}})\, {M_{\text{pool}}}}{{S_{\text{blk}}} \, {m_{\text{token}}}} \right\rfloor \tag{6}
$$

^eq-kv-demand-shared

The resident-fit bound of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^sec-vol3-kvcache-geometry|section 5.2]], refined for blocks, headroom, and sharing, is the maximum integer ${B}$ that satisfies [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^eq-kv-demand-shared|equation 6]]. Setting ${S_{\text{prefix}}} = 0$ yields the unshared baseline. Let ${f}$ denote the fraction of a full request’s blocks that belong to the shared prefix, so each additional request allocates only the private fraction $1 - {f}$ of an unshared request’s blocks. When the usable pool is large compared with the single copy of the shared prefix, paying for that prefix once leaves almost the entire pool for private blocks, and dividing by $1 - {f}$ per request raises the resident fit by nearly $1/(1 - {f})$. Sharing therefore delivers its largest gains when common instructions and workspace state represent a dominant fraction of the total context and private working memory (the unique turn history and generation allowance) remains small. Notebook [5.3](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#nbk-05-sizing-hbm-for-multi-turn-agent) grounds these formulations on the same eight-accelerator DGX H100 node serving Llama 3 70B. Rather than optimistically assuming an average generation length, the sizing calculation reserves the full ${K_{\max}}$ token allowance, which guarantees that resident requests cannot trigger out-of-memory aborts during decoding. It treats the headroom fraction as a deliberate provisioning reserve.

**Napkin Math 5.3: From logical contexts to physical fit**

**Problem**: How many complete request snapshots fit when a common prefix is stored once rather than copied for every request?

**Variables**: The Llama 3 70B model uses 16-bit weights and KV state on the DGX H100 node. After weights and the stipulated 20 GB runtime reserve, its KV pool ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^eq-mkv-pool|equation 5]]) is 526.0 GB. Withhold an additional 10 percent. Each request has 32,768 input tokens and an allowance of 2,048 output tokens. The requests come from a fleet of repair workers on one repository snapshot, so their first 24,576 input tokens (instructions, tool schemas, and the shared workspace state) are identical and form the common prefix. Blocks hold 16 tokens, or 5.243 MB of KV state across the node.

**Math**: Divide the remaining pool by bytes per block and round down, giving 90,292 usable blocks. An unshared request occupies 2,176 blocks (11.41 GB). Dividing the usable block count by that request count and rounding down gives 41 resident requests. That count is down from the 48 of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^tbl-vol3-kv-payload-fit|table 1]] because each request also reserves its output allowance, the headroom is withheld, and allocation rounds to whole blocks. With sharing, subtract the common prefix’s 1,536 blocks (8.05 GB) once, then divide by 640 private blocks per request (3.36 GB). Rounding down gives 138 resident requests.

**Systems insight**: The common prefix covers 70.6 percent of each request’s blocks, and sharing it raises the fit 3.4×, close to the large-pool limit $1/(1-{f}) \approx$ 3.4× for a shared fraction ${f}$. In that limit, the gain depends on ${f}$ alone, making prompt layout and the scope of sharing the primary architectural levers. A prefix shared only across one deployment’s instructions covers far less of each request than one that also spans a common workspace, as the archetype comparison below shows. Within a given scope, keeping invariant tokens at the front of the serialized input, strictly ahead of any volatile turn history, maximizes ${f}$. Although sharing does not reduce the decoding work per token or change any request’s logical context, it multiplies concurrent capacity. These values are physical fit bounds for the designated memory partition, not runtime admission limits.

![[90 Assets/Volume III/05 KV Cache/KV Sharing Gain Margin ae5b39e34a.svg]]

*A green curve rising from 1 times at zero shared fraction and steepening to 10 times at a shared fraction of 90 percent, with a blue dot at a shared fraction of 70.6 percent labeled 3.4 times.*

*The sharing gain $1/(1-{f})$ steepens as the shared fraction of each request grows.*

In production environments, requests arrive with varied lengths and different degrees of prefix overlap. An admission controller must therefore balance committed blocks, anticipated generation growth, and temporary staging buffers required during KV transfers or eviction copies. Furthermore, an aggregate node-wide memory bound is necessary but not sufficient: multi-GPU deployments distribute KV cache blocks across tensor-parallel shards, meaning a free physical block on one accelerator cannot alleviate memory exhaustion on another. Admission decisions must satisfy physical capacity constraints across every individual device.

### Residence Time and Service Rate

^sec-vol3-kv-workload-dynamics

A node that fits 41 unshared agent contexts in memory at once can still sustain fewer than one turn per second if every slot stays occupied across a 45 s integration test. A static fit bound counts only how many slots can exist in memory simultaneously. Translating that capacity into sustainable throughput requires dividing by how long each request holds its slot, and classical queueing theory supplies the identity that links capacity, residence, and throughput.

**Theorem 5.1: Occupancy equals rate times residence (Little's law)**

*In any stable system where items arrive, reside for a while, and leave, the long-run averages obey one identity, whatever the arrival pattern, service order, or residence distribution.* **Little’s law** ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-little1961|Little 1961]]) states

$$
{\bar{N}_{\text{slot}}} = {\lambda_{\text{arr}}} {\bar{T}_{\text{hold}}} \tag{7}
$$

^eq-vol3-littles-law

- **Mean occupancy** (${\bar{N}_{\text{slot}}}$): average number of items resident, here KV slots held.
- **Throughput** (${\lambda_{\text{arr}}}$): long-run arrival rate, equal to the completion rate when unfinished work does not accumulate.
- **Mean residence** (${\bar{T}_{\text{hold}}}$): average time an item holds its slot, counting every phase in which the slot stays allocated.

A slot held in accelerator memory while an agent waits for external tool execution remains resident throughout that wait; omitting idle waiting time from ${\bar{T}_{\text{hold}}}$ artificially deflates the denominator and overstates sustainable system throughput.

The law’s generality has a price. Its proof assumes nothing about how items arrive or how long they stay, only that the long-run averages exist, and for that reason it fixes the mean occupancy and says nothing about the peak. A burst of arrivals, or residences that end together, can hold far more slots than ${\bar{N}_{\text{slot}}}$ for as long as the backlog lasts, so capacity is sized from the arrival and residence patterns, not from the mean identity alone.

Rearranging the relation as ${\lambda_{\text{arr}}} = {\bar{N}_{\text{slot}}}/{\bar{T}_{\text{hold}}}$ expresses the achievable service rate as a function of allocated capacity and residence duration. Here each resident item is one turn’s generation-and-tool-wait cycle, not a complete multi-turn trajectory. Let ${T_{\text{model}}}$ be the time a turn spends generating and ${T_{\text{tool}}}$ the time it then waits on its tool. A slot kept through the wait resides for ${T_{\text{model}}} + {T_{\text{tool}}}$, while a slot released for the wait resides for ${T_{\text{model}}}$ alone. For the same number of slots, the two policies’ turn rates therefore differ by the factor $1 + {T_{\text{tool}}}/{T_{\text{model}}}$. That factor is the **residency tax** of a synchronous tool wait, and notebook [5.4](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#nbk-05-residency-tax) prices it for the repair turn.

↪ Little’s law applied to whole multi-turn trajectories with tool waits is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^sec-vol3-appendix-inference-queueing|Queueing for Trajectories]]**.

**Napkin Math 5.4: The residency tax of a tool wait**

**Problem**: The node holds 41 unshared request slots. Each repair turn resides 5 s while generating and, under the keep policy, another 45 s while its integration test runs. What turn rate can memory sustain with the wait held resident, and with the slot released for the wait?

**Math**: By [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^eq-vol3-littles-law|equation 7]], ${\lambda_{\text{arr}}} = {\bar{N}_{\text{slot}}}/{\bar{T}_{\text{hold}}}$. Keeping state through the wait gives ${\bar{T}_{\text{hold}}} =$ 50 s and ${\lambda_{\text{arr}}} =$ 0.82 turns/s. Releasing the slot for the wait gives ${\bar{T}_{\text{hold}}} =$ 5 s and ${\lambda_{\text{arr}}} =$ 8.2 turns/s. The ratio is $1 + {T_{\text{tool}}}/{T_{\text{model}}}$, or 10×.

**Systems insight**: Holding paused state through an idle tool wait penalizes the memory-bound turn rate by a factor of $1 + {T_{\text{tool}}}/{T_{\text{model}}}$. The economic viability of keeping state in accelerator memory depends on the ratio of wait duration to generation time, not the wait duration alone. Once the wait dominates, moving the state out to host memory, at a restoration latency of about 21 ms, becomes the better default whenever memory is contested. This same factor scales the memory term of every attempt’s cost, expanding $\mathbb{E}[{C_{\text{attempt}}}]$ in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]** across the entire unevicted residence.

*A bracket labeled slot held 50 s spans one bar made of a short blue segment labeled generate 5 s and a long gray segment labeled tool wait 45 s, above the note rate divided by 10.*

*A kept slot is paid for across the whole cycle, rather than only while it generates.*

The turn rate calculated from releasing slots is an ideal upper bound imposed strictly by memory capacity. In practice, prefill computation, state restoration bandwidth, PCIe bus contention, and scheduling queues introduce additional bottlenecks; compute throughput or interconnect bandwidth often saturates before memory is fully exhausted. Furthermore, if multiple trajectories share prefix blocks, those blocks remain pinned in memory even if one trajectory enters an idle wait.

Because Little’s law fixes only the mean, the residency calculation also hides the peaks that agent workloads produce. Tool executions frequently complete together, as in the correlated return burst of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kv-cache-uncertain-returns|section 5.7.4]], and tree-search agents fan out into many candidate paths at once, so instantaneous memory demand rises well above the average for as long as the burst lasts. Robust capacity planning must therefore stress-test the empirical distributions of prompt length, dynamic output expansion, search branching, and tool latencies against both device-level physical boundaries and strict service-level latency objectives.

These dynamics manifest differently across agent architectures. The software repair agent operates in a batch-like regime characterized by deep context windows and prolonged tool waits during test suite runs. By contrast, the customer support agent services numerous concurrent, short sessions where users wait interactively for low-latency responses. These contrasting profiles place divergent demands on the key-value pool and require distinct sharing and retention strategies.

**Lighthouse 5.1: Attention-state residency by archetype**

[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^tbl-vol3-kv-residency-archetype|Table 5]] puts the repair agent beside a support agent on the same node and pool. Both deployments share a 6,144-token prefix of system prompt and tool schemas across all their sessions. That prefix carries no customer or repository data, so isolation permits sharing it across sessions. The scope is narrower than in notebook [5.3](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#nbk-05-sizing-hbm-for-multi-turn-agent), where repair workers on one repository snapshot also share their workspace state. The support agent’s inputs are scenario values, not measurements.

| **Quantity**                        | **Repair agent**                | **Support agent**               |
|:------------------------------------|:--------------------------------|:--------------------------------|
| Retained tokens per session         | 32,768                          | 8,192                           |
| Shared fraction of each session     | 18.8%                           | 75%                             |
| Resident sessions, unshared         | 48                              | 195                             |
| Resident sessions, prefix shared    | 60                              | 780                             |
| Generation, then idle wait per turn | 5 s, then 45 s test             | 2 s, then 20 s reply            |

| Resume by reload vs. recompute      | 21 ms vs. 1.3 s                 | 5 ms vs. 0.32 s                 |

Table 5: **Residency by archetype**: Payload fits use the unrounded KV pool of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^tbl-vol3-kv-payload-fit|table 1]] without headroom or output allowance, so they exceed the block-rounded bounds computed earlier; resume times use the node’s host links and sustained prefill rate from the paused-state comparison.

^tbl-vol3-kv-residency-archetype

**Systems insight**: Prefix sharing yields asymmetric benefits across these two archetypes. Sharing the common prompt prefix expands the support agent’s resident session capacity 4×, yet yields only a 1.25× expansion for the repair agent, because the shared prefix constitutes a far larger fraction of each support session’s total context. Repair sessions recover a large sharing gain only when the scope widens to a common workspace, which raised the fit 3.4× in the capacity notebook. While both workloads pay a similar residency tax, the optimal pause policy diverges based on who waits for the resume. The repair agent should migrate its state to host memory during tests, as the regime analysis of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^fig-vol3-swapping-tradeoff|figure 6]] recommends. It can fall back to dropping the state when host memory is tight, since recomputation adds only 2.6 percent to a 50 s turn cycle where an automated test harness waits. In contrast, the support agent should keep or move its state and avoid dropping it, because recomputation lands directly in front of an interactive user as added delay to the first token. For support workloads, the decision that matters most is therefore what happens to each session’s private history beyond the shared prefix. Rebuilding that history is what the customer waits for, so keeping or moving it, not enlarging the shared prefix, protects the first token.

### KV Pool Telemetry

^sec-vol3-kv-telemetry-metrics

A single aggregate metric such as occupied pool fraction cannot distinguish healthy, amortized caching from an impending allocation failure. A memory pool at high utilization composed mostly of discardable dormant prefixes can easily admit a new request through cheap reclamation. Conversely, that same utilization level with all blocks pinned by active decoding leaves no headroom for context expansion. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^tbl-vol3-kv-pool-states|Table 6]] establishes the physical categories required to interpret these operational states.

| **Pool state**            | **Accounting and consequence**                                                                                                                                              |
|:--------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Active or pinned          | Count each physical block once, even when several requests reference it. It cannot be reclaimed while any required owner or operation still uses it.                        |
| Reserved or in flight     | Count additional blocks unavailable for admission because they are reserved or being populated, copied, or transferred. Exclude blocks already counted as active or pinned. |
| Reclaimable dormant cache | Count retained blocks that have no required active or in-flight use and can be discarded under the service’s policy. Reclaiming them can remove a future reuse opportunity. |
| Genuinely free            | Count blocks immediately available to allocate, with no live owner, unfinished operation, or reservation.                                                                   |

Table 6: **Physical pool accounting**: Apply the rows in order so each block belongs to exactly one category at a given instant. Logical references are tracked separately from physical storage.

^tbl-vol3-kv-pool-states

Evaluating blocks in this strict order ensures that every physical block belongs to exactly one state at any given instant. For instance, while a paused trajectory’s private blocks are being copied out to host memory, each source block stays in the first row, pinned by the transfer that still reads it, and becomes reclaimable only when the copy completes. On the return trip, the device blocks allocated to receive the reload sit in the second row until the transfer lands. Similarly, a dormant prefix is reclaimable only when all dependent references and asynchronous operations have cleared. This taxonomy exposes true admission capacity without double-counting shared blocks or assuming that eviction requests free memory instantaneously.

Physical pool accounting provides only the static half of the operational picture; it must be coupled with continuous telemetry on throughput, work volume, and latency. A production telemetry pipeline should record offered request rates, prompt and completion token volumes, the token-weighted prefix hit rate of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^eq-hprefix|equation 2]], eviction and restoration bandwidth, recomputed tokens, and the distribution of tool wait and resumption intervals. Operators must evaluate these metrics alongside concrete latency targets: admission delay in the scheduling queue, time to first token, inter-token latency, and state resumption delay. Hit rates in isolation can mislead. A high reuse fraction can coexist with long scheduling queues, while high eviction counts may be entirely benign if the discarded prefixes represent cold sessions that will never be queried again.

The definitive signature of memory thrashing is **cache churn**: the rapid cycle of evicting blocks only to reload or recompute them shortly thereafter.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.15 Footnotes#^fn8|⁸]] When cache churn coincides with degrading tail latency or falling completed work under sustained offered load, it signals that the aggregate working set of active trajectories has overrun physical memory capacity. Resolving this collapse requires adjusting admission policies, offload thresholds, or scheduling priorities. Because the memory occupancy threshold at which churn begins varies across allocators and workload compositions, operators must correlate physical pool states with queue dynamics rather than relying on a static utilization ceiling. Furthermore, this diagnostic boundary matters across system layers: client applications consuming remote API endpoints observe only black-box latency and error codes, whereas infrastructure operators have access to the physical block states, page tables, and transfer telemetry required to perform root-cause remediation. Coupling resident-fit bounds with telemetry across those block states lets operators see which KV blocks must stay pinned, which can be reclaimed or offloaded, and what restoration delay each choice adds to end-to-end execution.

**Checkpoint 5.2: Fit, pressure, and completed work**

Two runs report the same occupied fraction, but one holds mostly dormant prefixes and the other holds mostly active state.

**Physical ownership**: Explain why their immediate admission options differ and how a shared block should be counted.

**Sharing estimate**: If the common prefix in the notebook shrank to 12,288 tokens, estimate the shared fraction ${f}$ and the sharing gain from $1/(1-{f})$. Would sharing still more than double the resident-fit bound?

**Residency tax**: If the hypothetical wait doubles while generation residence stays fixed, by what factor does the retained-slot rate constraint fall, and does the case for moving state get stronger or weaker?

**Policy evidence**: Which workload, restoration, and latency measurements would distinguish useful eviction from repeated churn?
