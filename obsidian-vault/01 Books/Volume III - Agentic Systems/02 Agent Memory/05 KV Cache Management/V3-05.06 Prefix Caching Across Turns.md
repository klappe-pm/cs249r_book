# V3-05.06 Prefix Caching Across Turns

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management|V3-05 KV Cache Management]]

^sec-vol3-kvcache-radix-tree

In the connection-pool repair scenario, the agent invocation that processes an integration-test result often begins with the identical system prompt, tool definitions, and historical observations present in the preceding turn. If the serving engine retained the corresponding key-value (KV) activations from that earlier call, it can attach those existing tensors directly to the new request, prefilling only the newly arrived tokens. On the bill, this saving appears as a discounted cached-input rate; in system implementation, it translates into a concrete serving architecture governed by an index, an explicit ownership contract, and an eviction policy.

**Definition 5.3: Prefix cache**

***Prefix cache*** is the serving system’s index of retained KV state, keyed by exact token prefix and computation configuration, allowing subsequent requests sharing that initial sequence to attach existing state instead of recomputing it during prefill.

1.  **Significance**: It converts repeated prefill work into an index lookup across request boundaries. The computational savings grow with the length of the matched prefix and recur on every turn that preserves that prefix, making stable prompt layouts essential across long trajectories.
2.  **Distinction**: Block sharing reuses state among candidates that the engine forks from one request and therefore knows to be related. A prefix cache must find reusable state, by content, for requests that arrive independently over time, and it can offer only what memory pressure and eviction have left resident.
3.  **Common pitfall**: Assuming a cache hit guarantees semantic freshness. Matching cached tokens verifies identical historical inputs and execution settings, but it does not check whether the real-world state described by those tokens has changed.

### Prefix Compatibility

^sec-vol3-kv-cache-prefix-compatibility

Attaching cached KV blocks from an earlier turn corrupts generation if a single upstream token, adapter weight, or positional encoding differs between the two calls. The reason is that, under causal full attention, every token’s keys and values depend on the exact token prefix and execution configuration that produced them (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-prefix-coherence|5]]). Matching token identifiers from the first position of the sequence is only the first prerequisite. The cached KV tensors remain mathematically valid only when generated under identical execution parameters: the same base model weights, active low-rank adaptation (LoRA) adapters (lightweight fine-tuned weight adjustments), positional encodings, and attention masks. For multimodal requests containing images, audio, or structured embeddings, matching the synthetic placeholder tokens in the text prompt is insufficient; the underlying tensor inputs and projection parameters must match exactly. A production serving engine must encode these operational dependencies directly into its cache keys or validate them before binding cached blocks to a request.

Even when a cached prefix is mathematically compatible, the engine still has to verify that its blocks are physically resident and permitted to the caller. Computationally compatible tensors may have already been evicted from accelerator high-bandwidth memory (HBM), or they may reside in host memory or on solid-state drives, requiring an explicit page-in transfer before the model can consume them. Conversely, tensors residing directly in local accelerator memory may belong to a different tenant or security domain, making them ineligible for sharing under isolation rules. The reusable prefix length is the longest contiguous token sequence that simultaneously satisfies compatibility, physical residency, and access permissions. That sequence is frequently shorter than the longest match found in the prefix tree. Furthermore, newly generated tokens qualify for subsequent prefix matching only after their corresponding KV blocks have been fully materialized in memory and committed to the index.

These structural requirements operate independently of semantic validity. Updating a target repository from commit `r17` to `r18` does not alter or invalidate the KV activations previously computed for an older prompt describing `r17`. Those tensors remain numerically identical and computationally compatible with the stale prompt, even though the context no longer reflects the current state of the code. The harness’s context-selection policies govern which evidence to provide to the model. When the agent harness updates or replaces outdated logs in the serialized prompt, the prefix matcher detects the divergence, immediately terminates the match at the first altered token, and triggers a fresh prefill for the updated text. The prompt layout, rather than the cache layer, enforces freshness.

↩︎ How the harness withdraws a stale observation, such as the `r17` test failure, while keeping it as history is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-context-rot|Context Invalidation]]**.

### Radix Prefix Lookup

^sec-vol3-kv-cache-radix-lookup

Matching a new request against thousands of retained multi-thousand-token agent prompts token by token would build a deep, pointer-heavy index. A **radix prefix cache** avoids this by compressing chains of single-child token transitions into variable-length sequence edges in a radix tree ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-zheng2024sglang|Zheng et al. 2024]]).[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.15 Footnotes#^fn6|⁶]] To resolve a cache match, the scheduler walks the tree from the root, matching prompt tokens along successive edges until reaching a divergence point. This traversal simultaneously identifies the longest common prefix and the physical KV blocks storing its activations. Once a match is identified, the engine must acquire explicit ownership of those memory blocks before the background eviction thread can reclaim them. Lookup overhead scales with the prefix length examined, remaining on the order of microseconds on host CPUs. Alternatively, systems can implement an equivalent reuse contract using chained hash tables, where each fixed-size block is keyed by a cryptographic hash of its token content concatenated with the hash of its parent prefix.

The tree’s shape follows from the causal dependence that context staging already turned into a layout rule. Every position’s keys and values depend on the full history before it, so a node’s KV state is valid only beneath its exact ancestors. An identical passage that follows a modified token therefore lives on a different branch with no reusable state. The layout rule is the harness’s half of the same constraint. Staging volatile components (dynamic counters, tool outputs, scratchpad notes) toward the end of the prompt keeps the long invariant prefix on one path from the root, and compaction that rewrites only trailing turns leaves that path intact.

↩︎ Stable-prefix layout rules for prompt staging are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-staging|Staging the Next Invocation]]**.

Physical memory allocation introduces a practical policy choice at block boundaries without altering the underlying definition of compatibility. Suppose a later request matches the ten-token prefix whose blocks `[3, 7, 9]` were traced earlier, with block `9` holding two initialized entries. A serving engine that supports partial-tail reuse preserves all ten tokens and resolves the new turn’s divergent append with the same copy-on-write step recorded in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.05 Paged KV Allocation#^tbl-vol3-kv-cow-trace|table 3]]. An engine that caches only complete blocks reuses eight tokens and prefills the remaining two. Both designs are valid. The partial-tail strategy minimizes redundant prefill at the expense of copy-on-write buffer management, while the full-block strategy simplifies allocation by trading a modest amount of recomputation for uniform block lifecycles.

### Retention and Eviction Under Pressure

^sec-vol3-kv-cache-retention-eviction

Keeping finished requests’ KV blocks around as dormant cache entries allows subsequent turns to reuse them. Those dormant blocks, however, eventually fill the KV pool and force the allocator to evict old entries without racing active kernels or breaking shared tree paths. When an inference request finishes, the serving engine releases the request’s execution handles while the cache manager retains its own structural references to the blocks. The system’s retention policy then determines whether the next turn finds that KV state still resident in accelerator memory, pages it back from host RAM, or recomputes it from tokens.

Reusing and reclaiming memory blocks requires strict ownership tracking across concurrent threads and hardware streams. When a request matches a cached prefix, the memory manager increments reference counts on the corresponding blocks before dispatching execution kernels. Conversely, before reclaiming a physical block under memory pressure, the allocator must sever the cache’s indexing reference, confirm that active execution references have dropped to zero, and synchronize with outstanding device streams that might still be reading or writing those memory addresses. The allocator must also synchronize index modifications and reference changes so that a concurrent lookup cannot bind to a block while background eviction is tearing it down.

In tree-structured prefix caches, **leaf-first eviction** maintains structural consistency by preserving contiguous paths from the root and evicting unused leaf nodes first. Because internal nodes store common prefix state shared across multiple conversation branches, evicting an ancestor would invalidate all of its downstream descendants. An internal node becomes eligible for reclamation only after all of its descendant children have been evicted. Within the set of eligible leaves, systems frequently adopt a least-recently-used (LRU) policy ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-zheng2024sglang|Zheng et al. 2024]]), operating on the premise that recent access predicts near-term reuse ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-belady1966study|Belady 1966]]).[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.15 Footnotes#^fn7|⁷]] Reclamation therefore cascades upward. An inactive parent cannot be reclaimed while its child remains cached, but once the child leaf is evicted, the parent itself becomes an eligible leaf and can be freed if memory pressure persists ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^fig-vol3-radix-tree-cache|figure 4]]).

![[90 Assets/Volume III/05 KV Cache/Radix Prefix Tree Architecture 4a30a23f5a.svg]]

Figure 4: **Leaf-First Eviction in a Radix Prefix Cache**: Each node stands for a run of tokens and the KV blocks that hold them, so a request’s cached state is the path from the root to its node. Nodes on a running request’s path stay active. Only dormant leaves are eligible, which is why the dormant Other-task node in panel (a) survives until its Final-turn child is evicted in panel (b). A least-recently-used policy would choose among the eligible leaves; it never removes an ancestor before its retained descendants.

^fig-vol3-radix-tree-cache

Leaf-first eviction keeps residency prefix-closed, meaning that every resident node’s ancestors are also resident, and in full-attention models that property is an operational necessity. While freeing an upstream prefix block leaves the numeric values of a retained downstream suffix physically untouched, causal attention requires the entire preceding context to evaluate subsequent tokens. An orphaned suffix block is useless on the accelerator until its missing ancestral prefix is either reloaded from auxiliary storage or recomputed through a new prefill pass.

Retention policies therefore balance occupied accelerator capacity against the computational cost a future hit would eliminate. Recency alone provides an imperfect signal: an agent may generate a speculative branch that is never visited again, whereas a system prompt shared by hundreds of concurrent agent workers remains valuable despite sporadic gaps between calls. More resilient eviction schemes score cached nodes by balancing their expected reuse probability and recomputation cost against their physical memory footprint, adapting the retention weights to match dynamic workload demands.

### Prefix Hit Rate and the Reuse Contract

^sec-vol3-kv-cache-hit-rate-contract

Counting raw matching tokens in a prompt overstates real-world system benefits whenever matching blocks have been evicted, tenant isolation policies prohibit sharing, or memory allocators round matches down to physical block boundaries. Systems engineers evaluate caching efficacy by measuring the tokens actually served from reusable KV state without recomputation. Across a specified workload window, the **token-weighted prefix hit rate** is defined as

$$
{\rho_{\text{prefix}}} = \frac{\sum_{i} {S_{\text{match}}}^{({i})}}{\sum_{i} {S_{\text{prompt}}}^{({i})}} \tag{2}
$$

^eq-hprefix

where ${S_{\text{prompt}}}^{({i})}$ represents the prompt token count of request ${i}$, and ${S_{\text{match}}}^{({i})}$ counts the prompt tokens whose compatible KV activations were attached without recomputation after enforcing availability, security permissions, and block-alignment constraints. In the earlier four-token block example, a request matching ten tokens under a full-block-only caching policy yields ${S_{\text{match}}} = 8$, leaving two tokens to be prefilled. A production telemetry pipeline should also distinguish warm hits (state already resident in accelerator HBM) from cold hits (state that must be restored across PCIe from host memory).

A 4,096-token prefix of invariant system instructions and tool definitions, smaller than the shared zone of the r18 context, already shows the scale of the prefill work a hit avoids. Retaining this sequence in memory occupies 1.34 GB of KV activations distributed across the server node. Reconstructing that state from scratch requires roughly 578 trillion operations for linear projection layers, plus approximately 22 trillion operations for causal self-attention (**[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^eq-appdx-prefill-long|equation 4]]**). If the node sustains 45 percent of its peak 16-bit floating-point throughput (about 3,560 trillion operations per second), rebuilding that prefix incurs 169 ms of prefill latency on every cache miss. In contrast, a turn that scores a cache hit and appends only a 32-token suffix bypasses the prefix prefill entirely, requiring only a single memory-bandwidth-bound pass over the model weights. Because a 32-token suffix provides too little parallel arithmetic to saturate the accelerator’s matrix units, execution time is bounded by the weight-read floor of roughly 5 ms. In general, a weight-only forward pass over ${n}$ token positions takes ${t}({n}) = \max\left({T_{\text{read}}},\; 2{P} {n}/{R_{\text{attain}}}\right)$, the larger of the time ${T_{\text{read}}}$ to read the weights once from accelerator memory and the time to perform $2{P} {n}$ weight operations at the sustained rate ${R_{\text{attain}}}$. These are the two per-token floors of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-fm-token-floors|equation 2.7]]** applied to a whole pass (**[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^eq-appdx-batched-step|equation 5]]** derives the bound and its assumptions, while the full prefix rebuild adds the quadratic attention term). The hit thus replaces 169 ms of prefix prefill with a pass of about 5 ms, and a trajectory that keeps its invariant prefix stable collects that saving on every turn, in both latency and aggregate prefill work.

Although [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^eq-hprefix|equation 2]] measures the computational work avoided during prefill, end-to-end request latency also includes novel suffix prefill, autoregressive token generation, batch scheduling delays, and memory transfers. Once a hit eliminates prefix compute, any of these can dominate total response time. When monitoring production clusters, a declining prefix hit rate warrants investigating both sides of the client-service interface. On the client side, minor modifications in prompt serialization (such as altered whitespace, injected timestamps, or reordered JSON schema keys) prematurely truncate prefix matches. On the server side, heightened memory pressure, poor cross-node routing, or mismatched runtime configurations can render compatible state unavailable or physically inaccessible.

When using hosted model APIs, application developers require an explicit reuse contract rather than relying on unverified assumptions about the provider’s internal memory allocator. This contract must clearly define eligible token inputs, compatible execution configurations, tenant isolation boundaries, and supported retention lifetimes. In agentic workflows, cache expiration tightly couples this reuse contract to tool execution latency. If an external tool call blocks longer than the provider’s idle eviction threshold, the subsequent turn discovers that its cached prefix has been purged and incurs a full prefill penalty. This is the remote equivalent of the drop-and-recompute policy described in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kvcache-swapping|section 5.7]]. An agent harness aware of these eviction horizons can anticipate cache misses during long tool waits rather than absorbing unexpected latency spikes. The cached-token metric returned in API usage records is the client’s primary telemetry signal, though interpreting it requires understanding its precise operational scope.

**Systems Perspective 5.1: Reading a cached-token count**

A usage record that reports cached input tokens indicates how many prompt tokens the provider served from reusable KV state, which is the numerator of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^eq-hprefix|equation 2]] for that specific request. However, this metric remains silent on where those tensors resided (accelerator HBM vs. host DRAM), how the provider indexed them, or how long they will remain unevicted before the next invocation.

Its diagnostic value emerges when tracked across successive turns of an agent trajectory. Dividing the cached-token count by the total prompt tokens yields the caller’s observed prefix hit rate. A count that abruptly plunges to zero following an extended tool execution is consistent with cache expiration under idle eviction, but memory pressure, routing changes, and incompatible execution settings can produce the same observation. A count that stabilizes below the expected value may indicate an early prompt serialization divergence. Comparing submitted token prefixes and checking request routing and execution settings helps distinguish that client-side cause from unavailable or ineligible cached state. A confirmed layout divergence is an issue the client application can resolve directly in its prompt assembly pipeline.

An agent application must maintain functional correctness regardless of whether a request hits or misses the cache; the serialized context, not the cache, dictates the model’s true prompt input. A cache hit eliminates redundant arithmetic. When an agent turn introduces a voluminous test log or extensive retrieval chunk, it inevitably injects new prefill compute into the execution engine. Scheduling that compute-heavy prefill alongside ongoing, memory-bandwidth-bound token generation for existing requests is the next serving problem.
