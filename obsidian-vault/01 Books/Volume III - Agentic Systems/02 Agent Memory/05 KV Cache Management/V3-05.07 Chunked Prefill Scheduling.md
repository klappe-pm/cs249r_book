# V3-05.07 Chunked Prefill Scheduling

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management|V3-05 KV Cache Management]]

^sec-vol3-kvcache-chunked-prefill

Prefix reuse eliminates redundant computation on shared prompt prefixes, but new observations inevitably introduce fresh work. When the repair agent submits selected integration-test output, the serving engine must process the uncached suffix of the serialized request before generating the next response token. Other requests may already be generating tokens on the same accelerators. If the engine schedules the entire new prefill as one uninterrupted monolithic batch, those ongoing decode streams must wait for that pass to finish before executing their next decode step. In interactive agent workflows, that stall translates directly into noticeable inter-token latency spikes.

Trimming the observation reduces the raw number of tokens to process, but once the request reaches the server, scheduling determines how execution time is shared among active streams. The engine does not need to execute a long prefill as an all-or-nothing unit. Continuous batching already re-forms the batch at every forward step, admitting and retiring requests between token-generation steps ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-yu2022orca|Yu et al. 2022]]). That per-iteration boundary is exactly where a slice of one request’s prefill can be combined with other requests’ decodes. By splitting long prefills into smaller token chunks that co-run alongside ongoing decodes, the scheduler bounds how long any single iteration can stall active generation streams ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-agrawal2023sarathi|Agrawal et al. 2023]], [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-agrawal2024sarathi|2024]]).

↩︎ Prefill, decode, time to first token, and continuous batching are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-call-latency-decomposition|Where a call spends its time]]**.

**Definition 5.4: Chunked prefill**

***Chunked prefill*** is a scheduling policy that splits a request’s uncached prompt into token spans processed over several engine iterations, each iteration also advancing ongoing decodes, while preserving causal order.

1.  **Significance**: It bounds the gap between consecutive output tokens for ongoing requests to the duration of a single chunked iteration rather than a full monolithic prefill, at the expense of a modest delay in time to first token for the new request.
2.  **Distinction**: A chunk represents an execution quantum for the scheduler rather than a physical storage layout. The memory allocator maps the resulting KV activations into memory blocks whose page sizes operate independently of chunk boundaries.
3.  **Common pitfall**: Treating the per-iteration token budget as an exact wall-clock time limit. Iteration latency depends on attended context length, memory bandwidth, and batch composition, so operators must calibrate the budget against measured gaps between output tokens under realistic workloads.

### Causal Correctness Across Chunks

^sec-vol3-kv-cache-causal-chunks

Splitting a prompt across several iterations would change the model’s outputs if a later chunk attended only to tokens inside its own slice or used reset position indices. To preserve exact causal attention across chunks, each query token in the active chunk must attend to the compatible per-layer KV state produced by all earlier prefixes. It must also attend to the prior and concurrent tokens within its own chunk, as the causal mask enforces, while remaining blind to subsequent tokens. The engine preserves continuous positional encodings and mask logic as it extends the stored KV state, loading previously computed keys and values from memory rather than recomputing their projections from raw token embeddings. Chunking therefore alters the temporal execution schedule while preserving exact causal semantics, modulo minor floating-point non-associativity across kernel tiling and batching configurations. This scheduling flexibility incurs two physical costs: subsequent chunks must repeatedly stream earlier KV activations from high-bandwidth memory, increasing aggregate memory traffic, and smaller prefill slices introduce additional kernel-launch and scheduling overheads.

### The Per-Iteration Token Budget

^sec-vol3-kv-cache-token-budget

Admitting too many prefill tokens into one iteration stalls active decode streams, while admitting too few stretches a new prompt across dozens of small, overhead-heavy steps. To bound the work of each forward pass, a scheduler establishes an iteration-level **token budget** ${N_{\text{budget}}}$. In standard autoregressive decoding, each scheduled decode request contributes one token position, whereas each scheduled prefill contributes the token count of its next chunk. An engine iteration admitting prefill chunks of size ${C}_i$ alongside a set ${\mathcal{D}}$ of active decode requests must satisfy

$$
\sum_{i} {C}_i + \lvert{\mathcal{D}}\rvert \le {N_{\text{budget}}} \tag{3}
$$

^eq-kv-token-budget

while ensuring that the admitted combination fits within available accelerator memory. A request whose prompt spans multiple chunks retains its partially computed prefix KV state in memory across iterations while waiting for its subsequent slices to run.

A common scheduling policy prioritizes ongoing decoding requests by reserving $\lvert{\mathcal{D}}\rvert$ slots first, dedicating the remaining capacity ${N_{\text{budget}}} - \lvert{\mathcal{D}}\rvert$ to prefill chunks. This decoding-first priority ensures steady token generation for active streams without requiring them to wait for an entire multi-thousand-token prompt. However, the arriving request may require several iterations to complete its prefill, particularly if heavy decode traffic restricts the available chunk size. Conversely, allocating too much budget to prefill chunks can starve decode streams and trigger latency spikes. A robust scheduler must balance decode responsiveness against prefill completion progress to avoid both stream stalls and prompt starvation.

The weight-only step-time model ${t}({n})$ of the prefix-hit estimate gives the scale of this trade-off, with ${n}$ the token positions that [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.07 Chunked Prefill Scheduling#^eq-kv-token-budget|equation 3]] admits in one iteration. With 32 ongoing decodes and nothing else, each step sits at the weight-read floor of about 5 ms. Admitting a 4,096-token prefill as one separate unit inserts about 162 ms of arithmetic before the next decode step runs (weight work only, so slightly below the 169 ms prefix rebuild, which includes attention). Waiting through that prefill pass and the 5 ms decode pass stretches the gap between output tokens to about 168 ms.

Dividing that prompt into 512-token chunks reshapes execution by batching one prefill chunk and the 32 decode tokens into the same forward pass. Each of the eight iterations now carries 544 positions, sits in the arithmetic-bound regime, and takes about 22 ms. Because the decodes advance on every iteration, their worst gap between tokens is one 22 ms step, about 8× smaller than under the monolithic schedule. The new prompt completes after eight such mixed iterations, or about 173 ms instead of 162 ms, because each pass also performs the weight arithmetic for the 32 co-scheduled decode tokens. Chunking thus buys existing streams a much shorter gap for a modest delay in the new request’s first token. On one time axis, the monolithic schedule leaves a single long gap between two output tokens, while the chunked schedule places a token at every iteration boundary and finishes the prompt only slightly later ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.07 Chunked Prefill Scheduling#^fig-vol3-chunked-timeline|figure 5]]). Both schedules omit attention traffic, which grows with each chunk’s context, and per-iteration overhead, so measured iterations run longer and the budget must come from measurement.

Characterizing these trade-offs requires replaying representative arrival traces across candidate token budgets while tracking key systems metrics: time to first token for newly admitted requests, inter-token latency for active decode streams, aggregate token throughput, and accelerator memory occupancy. High-percentile latency measurements, such as the p99 inter-token gap, expose transient scheduling hiccups far better than arithmetic averages, which easily conceal the disruptive stalls of occasional large prefills. Operators must also distinguish server iteration step times from client-perceived streaming intervals; downstream buffering, transport serialization, and network round-trip times introduce variances that server-side metrics do not capture.

Selecting the token budget ${N_{\text{budget}}}$ ultimately balances hardware execution efficiency against service responsiveness. Smaller chunks provide frequent scheduling checkpoints that protect inter-token deadlines, yet they extend total prompt completion times and add kernel-launch overhead. Larger chunks maximize tensor-core utilization by providing wider matrix dimensions during attention and feed-forward operations, but they penalize concurrent decode streams with longer stalls. In practice, operators configure the token budget to the largest chunk size whose corresponding iteration duration comfortably satisfies the target inter-token latency objective for active streams. On the reference node, the weight-only estimate gives the starting point. An inter-token target comfortably above 22 ms admits the 512-token chunk alongside 32 decodes. A tighter target forces smaller chunks and a later first token for the new request, while running the prompt unchunked exposes the decodes to the full 168 ms gap. Measured attention traffic and per-iteration overhead then shrink the admissible chunk from that estimate.

**Prefill-decode disaggregation**, introduced with the call-latency decomposition of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-call-latency-decomposition|Where a call spends its time]]**, takes the structural alternative to chunking and places the two phases on separate worker pools ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-patel2024|Patel et al. 2024]]; [[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.14 Source References#^ref-zhong2024distserve|Zhong et al. 2024]]). It replaces compute contention on one worker with a transfer of each prompt’s KV state from the prefill pool to a decode worker before generation starts. When the interconnect saturates or queues build at either pool, that transfer can cost more than phase isolation saves. For an agent calling a hosted endpoint, that topology stays behind the serving API and appears only as request latency, streaming variance, and concurrency limits.

Chunking and disaggregation govern how active requests share compute resources during model execution. Once generation completes and an agent suspends execution to invoke an external tool or inspect an environment, the operational challenge changes from scheduling compute to managing idle memory. Deciding whether that trajectory’s KV state remains resident in accelerator memory, spills to host memory, or evicts entirely becomes the governing concern.
