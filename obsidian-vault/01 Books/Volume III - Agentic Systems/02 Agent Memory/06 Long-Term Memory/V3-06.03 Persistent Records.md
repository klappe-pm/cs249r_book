# V3-06.03 Persistent Records

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-persistent-need

When a multi-session repair agent stores repository source files, test execution logs, and its own progress notes in a single undifferentiated memory pool, a later session can easily treat an unverified hypothesis or an old `r17` test log as current ground truth about the code. Those artifacts play different roles in the repair. The repository source defines what the code looks like at a given commit. An execution log records how a test behaved under specific runtime parameters against that commit. A progress note records only where the previous session planned to resume work. Retrieval strategies, cache validation, and deletion policies all depend on keeping these operational roles distinct.

### Record Roles

^sec-vol3-long-term-memory-record-roles

Separating those roles begins with where each artifact originates. Version-controlled repositories, production databases, system configurations, and user profiles exist outside the agent’s execution loop, whereas raw environment observations, tool output traces, progress summaries, and speculative heuristics are produced during execution on top of those external sources, and search indexes are derived from both. Grouping all of them under the single label “agent memory” obscures the boundary between a verifiable source and a derived claim. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.03 Persistent Records#^tbl-vol3-memory-tiers|Table 1]] categorizes these records by their architectural role in the evidence chain.

| **Record role**          | **Example**                                                                                    | **What a later use must preserve**                                                        |
|:-------------------------|:-----------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------|
| Source record            | `src/pool.py` at a specified revision; the user’s stated scheduling preference                 | The designated source, applicable version or scope, and access conditions                 |
| Observation or event log | The outcome of `test_waiter_notified_on_return` under recorded source, test, and configuration | What was observed, when, and under which conditions; gaps in the retained history         |
| Agent-written memory     | A progress note, session summary, or proposed repair lesson                                    | Supporting records, uncertainty, intended scope, and the policy for correction or removal |
| Derived retrieval index  | Search entries over source files, logs, or notes                                               | Which source generation produced the entry and how changes affect its use                 |

Table 1: **Roles of persistent records**: These are roles in an evidence chain, not a hierarchy of storage devices or universal levels of trust. One record can serve more than one role.

^tbl-vol3-memory-tiers

A **source of record** is the designated authoritative origin for a specific claim. For example, the Git tree serves as the source of record for a file’s contents at a particular commit hash, while an authenticated user message serves as the source of record for that user’s operational constraints. Establishing a source of record defines where any downstream assertion must be validated. It confers evidential provenance rather than correctness. A repository commit may harbor a regression, and an inline code comment may contain unauthorized instructions. Under the principle that authority stays with the source (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-source-authority|6]]), authority describes an evidentiary relationship between a claim and its origin, never an unconstrained permission grant. When an agent’s generated output drifts from its source of record, the output still binds whoever deployed the agent, as one tribunal made explicit in the case that follows. For a memory system, the further question is what happens when such an answer is kept and read again.

**War Story 6.1: A support chatbot contradicts its policy page (2024)**

**Context**: In November 2022, following the death of his grandmother, passenger Jake Moffatt consulted the customer-support chatbot on Air Canada’s website regarding bereavement fares ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-moffatt2024aircanada|Civil Resolution Tribunal of British Columbia 2024]]). Air Canada’s formal bereavement policy, published on a separate page of the website, explicitly prohibited retroactive bereavement fare adjustments once travel was completed.

**Mechanism**: The chatbot erroneously informed Moffatt that he could purchase regular-fare tickets immediately and submit a bereavement refund claim within 90 days of ticket issuance, directly contradicting the airline’s published policy. When Moffatt submitted his claim, Air Canada denied it based on the static policy page. Before the British Columbia Civil Resolution Tribunal, Air Canada argued that the chatbot was an independent legal entity responsible for its own actions.

**Impact**: The tribunal rejected Air Canada’s argument, finding that the chatbot was an integral component of Air Canada’s website and that the airline remained liable for all information published through it. Finding Air Canada liable for negligent misrepresentation, the tribunal ordered the airline to pay CA\$650.88 in damages (representing the difference between the full fare and the bereavement rate), alongside interest and statutory tribunal fees.

**Fix**: The tribunal dismissed the assertion that customers must independently reconcile conflicting guidance across different website pages, holding that the airline was responsible for all information on its website, whether a static page or a chatbot supplied it.

**Systems lesson**: A generated response is a derived artifact, yet users and legal frameworks treat it as an authoritative corporate commitment. The engineering remedy is to stage the versioned source of record into the model call and constrain the answer to claims that text supports, which is the job of the retrieval contract developed below. Model fluency provides neither evidentiary validity nor legal protection.

Through the taxonomy of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.03 Persistent Records#^tbl-vol3-memory-tiers|table 1]], the published policy page functioned as the source of record, while the chatbot’s generated response was a derived artifact that diverged from ground truth. If a customer-support system logs its previous dialogue turns to inform future responses, those conversational turns become agent-written memory. They document past interactions, but they never constitute organizational policy. A store that kept the chatbot’s wrong answer and retrieved it for the next bereavement question would repeat the error with the apparent weight of precedent, unless the record carried its role as a derived answer and a link to the policy version it claimed to reflect.

Observation logs capture empirical execution history. When an agent tests a connection pool, an execution log showing a failure at revision `r17` remains valid diagnostic history even after revision `r18` resolves the bug. The subsequent passing run confirms that the specific reproducer succeeded under that exact environment configuration. An execution log provides primary evidence of what the system observed during a run, rather than proving the universal validity of any underlying program assertion. Retaining this historical record across machine restarts or worker failures requires durable persistence guarantees.

↪ Durable, replicated logs that survive worker and machine failures are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.03 The Trajectory Log#^sec-vol3-persistence-event-sourcing|The Trajectory Log]]**.

Agent-written memory synthesizes raw observations into structured artifacts for future execution steps, taking the form of scratchpad notes, session summaries, or learned heuristics. Condensing raw traces prevents repetitive computation and conserves context window capacity. However, summarization introduces its own failure modes, because compression can strip vital boundary conditions or fabricate causal explanations. For instance, the observation that the targeted reproducer passed at `r18` is strictly justified by the execution log. In contrast, the generalized claim that connection-pool timeouts always stem from missed thread notifications asserts a universal rule that a single test execution cannot substantiate. Storing an unsupported generalization in a persistent database creates compounding errors in subsequent planning steps.

This divergence mirrors the foundational distinction from cognitive psychology ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-tulving1972episodic|Tulving 1972]]) that agent architectures have adopted. **Episodic memory** captures discrete, time-stamped events anchored to specific execution contexts. **Semantic memory** stores generalized knowledge, rules, and abstractions extracted across multiple episodes. **Procedural memory** complements both by preserving executable workflows, tool scripts, and operational runbooks. In the terms of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.03 Persistent Records#^tbl-vol3-memory-tiers|table 1]], observation logs and episode summaries are episodic records, generated lessons and reference facts are semantic records, and reusable repair workflows represent procedural records. In an engineered system, semantic and procedural records are therefore derived artifacts whose epistemic validity depends entirely on the fidelity and scope of the underlying episodic records.

A retrieval index serves as an auxiliary acceleration structure for locating information across storage tiers. Whether an index stores term postings, learned vector embeddings, or graph edges over source files, logs, and agent notes (structures this chapter develops in turn), an index only locates candidate records. When a search query matches an index entry, a high similarity score demonstrates lexical or semantic affinity to the query string, but provides no assurance of operational applicability to the current task. Operational applicability depends on whether the referenced record matches the current system state, schema revision, and environment constraints.

### Read and Write Lifecycle

^sec-vol3-long-term-memory-read-write-lifecycle

Consider the state of a code-repair agent immediately after it writes revision `r18`. If its vector or keyword index was generated from revision `r17`, a retrieval query for `src/pool.py` will return the unpatched file. While that record remains an accurate historical reflection of `r17`, serving it as current context leads the model to believe the bug persists, prompting redundant or conflicting edits. The staleness that context invalidation guards against thus extends beyond the active prompt into the persistent storage tiers that feed subsequent inference calls.

↩︎ Context invalidation, which withdraws a staged observation’s authority over current state once its source changes, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-context-rot|Context Invalidation]]**.

Precomputing search indexes eliminates the need to scan large repositories or execution histories during inference. However, this optimization incurs an ongoing synchronization cost. Every update to a source file requires indexing new content and invalidating or evicting obsolete embeddings. Executing these updates synchronously blocks read or write operations, while background asynchronous indexing opens a lag window in which the index still answers from `r17` although the file is already at `r18`. A query that arrives inside that window needs an explicit rule for what it may return, which [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^sec-vol3-long-term-memory-index-coordination|section 6.9.2]] supplies.

Conversational agents meet the same consistency problem in user state. A user who said “Schedule no meetings before 10:00 AM” later says “before 11:00 AM.” The two directives are nearly identical as text, yet their intent is mutually exclusive. A store that treats the second as a duplicate keeps the stale behavior, and one that appends it without retiring the first leaves a contradiction in every later prompt. Telling a complementary fact from a superseding one requires explicit lifecycle metadata, which the write path ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^sec-vol3-long-term-memory-write-path|section 6.8]]) supplies and carries to every derived index, alongside validation, time-to-live (TTL) expiration, and cascade deletion.

The read side comes first, because lifecycle metadata protects the agent only if every read reports it. A retrieval interface must therefore return candidate text alongside the provenance, version, and completeness information on which safe execution depends.
