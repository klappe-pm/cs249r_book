# V3-06.08 Multi-Hop Retrieval

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-persistent-graphrag

In the connection-pool repair, no single ranked passage delivers all the evidence the fix requires, because the core implementation in `src/pool.py`, the waiter-notification test, and the recorded test execution logs answer distinct questions. Examining the pool implementation in isolation cannot reveal which execution paths the test actually exercised, and inspecting a passing test log leaves unanswered whether the change preserved wider public interface guarantees. **Multi-hop retrieval** addresses this gap by traversing explicit relationships between evidence items, assembling an explanatory chain that no individual passage’s retrieval score could justify alone.

Implementing multi-hop retrieval does not necessarily demand a dedicated graph database. An agent can inspect a retrieved passage, extract an unresolved reference, and issue a targeted tool call to fetch the next source artifact. Alternatively, an execution runtime can resolve known references ahead of time before invoking the model. Precomputing and maintaining explicit entity relationships pays off only when downstream queries reuse those links frequently enough to amortize the parsing and indexing overhead.

### Evidence Paths

^sec-vol3-long-term-memory-evidence-paths

Handing the model separate snippets from `r17` test logs, `tests/test_pool.py`, and `src/pool.py` without recording how they connect leaves the agent to guess which test exercised which method and under which revision. An explicit evidence path instead chains those records together. It starts at the recorded failure of `test_waiter_notified_on_return` under revision `r17` (scoped by its test revision and runtime environment). From there, the traversal traces from the test assertion in `tests/test_pool.py` directly into the pool operations exercised by the waiter-return scenario in `src/pool.py`. It then compares those source regions against the candidate patch in revision `r18` and its corresponding reproducer execution. Public interface contracts and unrelated callers remain isolated for subsequent targeted queries.

The edges along this path carry distinct semantics. A link from a test run to a commit hash binds an outcome to an exact observed artifact. A static symbol reference in test code points only to an implementation entity awaiting inspection. A diff between revisions isolates textual modifications between snapshots. A robust retrieval payload preserves these labeled edge semantics alongside precise source locations and commit hashes. The runtime must also expose unresolved or broken links, such as a missing test log, an ambiguous dynamic dispatch target, or a traversal halted by a token budget. A static evidence path highlights plausible candidate root causes, but it cannot prove that those specific statements executed during the failing run, nor does it guarantee that all contributing dependencies were discovered.

### Maintained Code Graphs

^sec-vol3-long-term-memory-code-graphs

Following every file that merely imports `src/pool.py` floods a multi-hop search with dozens of irrelevant modules, whereas a flat symbol table cannot trace how a value mutated in one method reaches a waiter queue in another. To support selective reasoning over software repositories, a **code property graph** unifies abstract syntax trees, control-flow graphs, and program-dependence graphs into a single directed graph of program entities connected by typed edges ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-yamaguchi2014modeling|Yamaguchi et al. 2014]]). The edge types most relevant to software agents include syntactic containment and declaration, call edges connecting call sites to function targets, data-dependence edges tracking value definitions to their uses, type inheritance, and module-level imports.

Edge typing is what makes multi-hop graph traversal selective rather than combinatorial. Restricting the walk to call and data-dependence edges traces directly from `test_waiter_notified_on_return` through the pool’s resource-return method to the state it mutates, ignoring module-import edges that fan out into unrelated files. The entry point for such a traversal, the seed node, can be resolved via an exact symbol lookup, an initial ranked passage retrieval, or an explicit file and line coordinate from an execution trace.

However, an edge is only as reliable as its underlying extraction mechanism. Lexical parsing reliably identifies declared syntax. Resolving cross-file call targets requires complete type information and build configuration. Dynamic execution traces observe only the concrete paths taken during a specific invocation. Code graphs must therefore track provenance on every edge, ensuring the runtime never presents a statically inferred call as an observed runtime event. Furthermore, maintaining these graphs introduces ongoing invalidation overhead as the codebase evolves. A local edit to a method signature might invalidate caller graphs and dependent summaries across multiple repositories, whereas modifying an internal comment leaves structural edges unchanged. When source artifacts shift, any relationship whose underlying evidence has changed must be pruned or marked stale according to the update contracts established in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^sec-vol3-persistent-invalidation|section 6.9]].

### Bounded Expansion

^sec-vol3-long-term-memory-bounded-expansion

Even on a typed code graph, an unconstrained walk out from `test_waiter_notified_on_return` can loop indefinitely around mutually recursive helpers or fan out through a shared logging utility into dozens of callers, exhausting the downstream context window. Traversal routines therefore require strict operational guards: filtering permitted edge types, restricting traversal direction, capping maximum search depth, and bounding the total number of visited nodes. Tracking visited entity identifiers is essential to prevent cyclic loops from triggering infinite expansion. Even with structural bounds, context packing limits remain binding because a small handful of large code or documentation nodes can easily overrun the prompt budget.

Within these operational boundaries, the runtime can prioritize candidate nodes using semantic relevance, edge type affinities, or graph-centrality algorithms like Personalized PageRank ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-page1999pagerank|Page et al. 1999]]), which concentrates random-walk probability around the initial seed nodes. However, applying a naive score threshold across candidate nodes risks fragmenting the evidence chain. Preserving a coherent explanation often requires retaining an intermediate node with a lower individual query score to maintain topological connectivity between the seed and high-value leaf evidence, while compensating by pruning non-essential nodes elsewhere.

↪ The personalized PageRank update and its unique fixed point are developed in **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-pagerank|PageRank symbol graphing for repository maps]]**.

*One more level of depth turns a comfortable fit into an overflow.*

Depth, more than node size, decides whether a neighborhood fits the context budget, because every hop multiplies the expansion frontier by the branching factor. Notebook [6.3](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-graph-neighborhood-expansion-vs-context) counts an exact tree to show how quickly one extra level turns a comfortable payload into an overflow.

**Napkin Math 6.3: Graph expansion and the evidence budget**

**Problem**: Can the complete neighborhood around one seed fit the chapter’s 6,144-token retrieval allowance?

**Variables**: Suppose the neighborhood is a tree with exactly 3 children per internal node, explored through depth 3, with the seed at depth zero and no repeated nodes. Each complete node record occupies 180 serialized tokens, including its local provenance. Reserve 100 tokens total for edge descriptions and the result envelope. All counts are hypothetical fixed serialization sizes.

**Math**: Counting the seed and all levels gives the geometric sum $1 + 3 + 9 + 27 = (3^{4}-1)/(3-1) =$ 40 nodes, in general $(\text{children}^{\text{depth}+1}-1)/(\text{children}-1)$. Staging them requires 40 $\times$ 180 $+$ 100 $=$ 7,300 tokens, exceeding the allowance. With the same envelope reservation, the maximum number of complete equal-sized nodes is $\lfloor(6{,}144 - 100)/180\rfloor =$ 33.

Stopping one level earlier, at depth 2, stages all 13 nodes in 2,440 tokens.

**Systems insight**: Depth dominates traversal cost because every additional hop multiplies the expansion frontier by the graph’s branching factor. A single extra level separates an evidence payload that comfortably fits the context window from one that overflows the allocation. Traversal engines must bound depth and filter edge types before ranking nodes. Within those limits, scoring should prioritize nodes that preserve path connectivity rather than greedily selecting disconnected high-scoring fragments.

Production code graphs contain clustered communities, cycles, and heavily skewed degree distributions. Consequently, calculating reachable nodes by raising an average branching factor to a traversal depth typically overestimates distinct reachable entities while underestimating the local search work required to evaluate candidate edges. When an evidence path exceeds the staging budget, the runtime must either narrow the query scope, return a truncated subgraph accompanied by an explicit continuation cursor, or defer downstream expansion to subsequent interactive agent turns. Under the absence rule, any traversal halted by an engineering limit must be explicitly reported as partial rather than exhausted.

### Community Summaries as Derived Memory

^sec-vol3-graphrag-hierarchical

Not every agent question resolves to a single evidence path. High-level architectural queries often span entire subsystems, for example how connection pooling, HTTP request dispatching, and transaction lifecycles interact across a service framework. Graph-based retrieval-augmented generation (GraphRAG) addresses these broader questions by constructing an entity knowledge graph and precomputing hierarchical summaries over densely connected subgraphs, or communities ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-edge2024graphrag|Edge et al. 2024]]). Unsupervised community detection[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn7|⁷]] clusters related nodes based on network topology. However, whether a detected topological cluster corresponds to a true architectural boundary, and whether its generated natural-language summary remains technically accurate, are separate verification concerns.

A derived summary amortizes token costs by synthesizing scattered facts into a concise artifact, but it remains a lossy, secondary representation. Every generated summary must retain bidirectional links to its source evidence and record the precise artifact revisions and operating parameters it describes. It must also inherit the most restrictive access label among its underlying inputs, so that a summary built partly from records restricted to one tenant is itself restricted to that tenant. Detailed execution plans should inspect the authoritative underlying records; the summary serves primarily as an indexed navigational map.

↪ How labels propagate through summaries and other transformations under an information-flow policy is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^sec-vol3-security-label-propagation|Label propagation through transformations]]**.

For instance, an automated repair summary might record that revision `r18` passed `test_waiter_notified_on_return` under a specific thread-concurrency configuration. Because an observation is scoped to its tested configuration, this fact cannot be generalized into an assertion that “the connection pool is thread-safe.” Moreover, precomputed summaries incur ongoing invalidation debt. Persisting an explicit dependency manifest between source files, detected communities, and generated summaries turns invalidation into a traversal of recorded dependencies rather than a guess. Any code modification flags all dependent summaries (and any higher-level rollups derived from them) as dirty. The runtime can continue to serve a dirty summary as a labeled historical snapshot until an offline job or on-demand trigger recompiles or invalidates it.

**Checkpoint 6.2: Choosing and bounding related evidence**

Apply these retrieval strategies to the running connection-pool repair.

**Method choice**: A debugging query begins with an exact test identifier, but the subsequent inquiry requires identifying all upstream callers of the modified pool method. Which indexes or direct reads best support each step, and under what workload conditions does maintaining a persistent code property graph justify its synchronization overhead?

**Evidence path**: Why does a static dependency path from a failing test to a pool implementation fail to prove the runtime root cause or guarantee the general correctness of patch `r18`?

**Expansion estimate**: In the tree expansion model from notebook [6.3](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-graph-neighborhood-expansion-vs-context), if each node record shrank by half, how many levels could traversal proceed before exceeding the retrieval budget, and what computational search overhead would that additional level incur that serialization bounds fail to capture?

**Derived summaries**: What provenance links and execution constraints must accompany a synthetic summary of a passing reproducer run to prevent a subsequent agent session from drawing invalid conclusions?

Deciding whether to retain a detailed path explanation or a high-level subsystem summary is a write-policy decision rather than a search mechanic. That policy dictates the fidelity, staleness, and cost of the evidence that every subsequent agent session can retrieve.
