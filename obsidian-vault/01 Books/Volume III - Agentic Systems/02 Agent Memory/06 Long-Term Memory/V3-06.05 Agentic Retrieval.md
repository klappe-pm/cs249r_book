# V3-06.05 Agentic Retrieval

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-long-term-memory-agentic-retrieval

Predicting every file the repair agent will need before invoking the model either stuffs the prompt with irrelevant code or misses a helper dependency that becomes visible only after reading the first stack frame. Forcing the model to search interactively for files the task already named, however, wastes an entire inference turn on a predictable lookup. Two retrieval architectures divide this work differently. In a pre-staged architecture, the runtime predicts which artifacts will be necessary (such as `src/pool.py`, `tests/test_pool.py`, and a stack trace from a prior run) and injects them directly into the prompt before model execution begins. In an agentic architecture, the runtime equips the model with bounded text search, file reading, and symbol-navigation tools, allowing the agent to locate notification logic, inspect the test harness, and follow cross-file references as intermediate discoveries dictate. Both architectures operate over the same underlying storage systems and share identical security boundaries. They differ in when the information need is resolved and which component formulates the retrieval queries.

Pre-staging implements standard **retrieval-augmented generation** (RAG), where the host system selects external documents and packages them alongside the prompt before inference begins ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-lewis2020retrieval|Lewis et al. 2020]]). By contrast, **agentic retrieval** delegates query formulation to the model during the execution loop, interleaving environment observations with subsequent reasoning and action steps ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-yao2023react|Yao et al. 2023]]). Autonomous systems designed for repository-scale software engineering ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-jimenez2024swebench|Jimenez et al. 2024]]) rely on this interactive loop, because search and navigation commands shaped for code inspection prove far more adaptable than a single, static set of top-${k}$ retrieved passages staged up front ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-yang2024sweagent|Yang et al. 2024]]). Rather than mutually exclusive alternatives, these two patterns represent complementary policies operating over the same underlying data stores.

That trade-off sets the operating envelope of each policy. When the required files are known from the task description or project layout, pre-staging them into the initial prompt avoids spending a full model turn on discovery. When a failing assertion in `tests/test_pool.py` names an internal helper whose definition resides in another module, model-directed search lets that intermediate observation shape the next query instead of guessing the transitive dependency graph up front. Interactive exploration, however, introduces its own failure modes: an agent can chase unpromising leads, issue redundant searches across familiar directories, or stop probing before gathering enough evidence to verify a fix.

Before introducing an auxiliary index, such as an inverted text index or a vector store, an engineer should benchmark against a live-source baseline. Bounded substring searches and direct file reads inspect the target workspace directly on disk, introducing no external index that can lag behind ongoing edits. When a problem description already specifies exact filenames or literal error strings, these live-source primitives often supply all the retrieval capability the agent requires. Direct filesystem access, however, presents distinct systems trade-offs. Live reads observe whichever version of a file exists at the exact moment of execution. If concurrent processes modify the workspace, separate reads executed across successive turns can straddle modifications and observe inconsistent snapshots. Furthermore, raw literal searches locate character matches without semantic awareness, failing to distinguish an active symbol definition from an obsolete comment or an unrelated log message. An auxiliary index justifies its memory footprint, construction time, and synchronization overhead only when it earns them back. It measurably amortizes repetitive scanning costs across long trajectories, resolves vocabulary mismatches through semantic embeddings, or accelerates traversal over structural relationships such as call graphs derived from abstract syntax trees (ASTs). An evaluation must charge the cost of building and refreshing the index directly against its query-time savings. The chapter prices that charge at its end, once lexical, dense, and graph indexes are in hand (notebook [6.5](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-storage-amplification)).

When an agent probes its environment, the runtime can optimize query execution through parallelism. A single model turn can emit several independent tool calls that the runtime batches or executes concurrently across threads. Only queries that strictly depend on earlier observations must block for sequential resolution. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.05 Agentic Retrieval#^tbl-vol3-long-term-memory-staged-vs-agentic|Table 3]] summarizes the core trade-offs between runtime pre-staging and model-directed probing.

| Property               | Runtime pre-staging                                            | Model-directed probing                                         |
|:-----------------------|:---------------------------------------------------------------|:---------------------------------------------------------------|
| Query selection        | Runtime policy selects evidence before model invocation        | Model formulates queries dynamically from prior observations   |
| Optimal scenario       | Likely evidence needs are predictable in advance               | Intermediate results dictate which question to ask next        |
| Computational overhead | Retrieval latency and staging cost prior to the call           | Search latency and extra inference rounds for query refinement |
| Characteristic failure | Missing transitively imported dependencies or bloating context | Chasing unproductive paths or terminating search prematurely   |
| Freshness guarantee    | Governed by source version and read contract at staging        | Governed by the same read contract at tool execution time      |
| Resource governance    | Bounded by staging timeouts and context-window capacity        | Bounded by per-call limits and trajectory-wide step budgets    |

Table 3: **Pre-staging and model-directed retrieval**: Query timing and ownership change between the two policies, while source applicability and runtime-enforced limits remain shared.

^tbl-vol3-long-term-memory-staged-vs-agentic

Under both policies, the execution runtime retains authority over security boundaries and resource consumption. The model acts strictly as an untrusted query generator. It may propose a narrower search path, supply query strings, or request specific filters, but it can never expand the authorized workspace, assume a different principal identity, or increase its own resource ceilings. The runtime enforces these boundaries at the tool interface. Tool calling schemas define and constrain the supported request parameters, while tool execution results transmit truncation warnings, resource limits, and continuation tokens back to the agent.

↪ Tool interface schemas that bound which request parameters a model may supply are developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-schemas|Tool Interface Schemas]]**.

In production systems, these two strategies often merge into a tiered hybrid policy. The runtime pre-stages a compact workspace outline, an architectural summary, or persistent user preferences directly into the initial context window, giving the model immediate structural grounding. The agent then issues targeted tool calls to inspect specific function implementations or test traces only when those details become necessary. Evaluating such a hybrid design requires balancing the upfront token overhead of pre-staging against the inference latency and token expenditure of avoided tool turns.

The choice among a direct read, pre-staging, and directed probing follows from how much of the information need the task itself names. When the task names its targets, such as `src/pool.py` or a pinned note, a direct read stages exactly those records and spends no ranking or exploratory turn. When the needed evidence is predictable but unnamed, such as the tests that usually accompany a module, pre-staging captures it in one step at the price of some irrelevant tokens. When each needed item can be found only from the one before, as when a failing assertion names a helper whose definition names a lock, no pre-staged set can anticipate the chain, and model-directed probing pays one model round per dependent hop. A hybrid seeds the first hop by pre-staging or direct read and leaves the remaining hops to probing. Whichever component formulates the query, what comes back depends on the matching mechanism behind the read, whether lexical matching, learned similarity, or structural traversal, and each mechanism answers a different kind of information need.
