# V3-06.11 Evaluating Memory Policies

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-persistent-governance-eval

Excluding a stale failure trace from an earlier run keeps an outdated representation out of the agent’s next request, but it does not ensure that the agent finds the fresh evidence needed to effect a repair. Conversely, a stored reflection might reproduce a recent passing test run accurately while overstating what the pass proves. Rigorous evaluation cannot treat memory as a static lookup table. It must follow information across its full lifecycle: from initial admission into persistent storage, through indexing, retrieval, and prompt staging, to the subsequent updates, supersessions, and deletions that maintain consistency as the environment evolves.

The appropriate unit of comparison is the *memory policy*. A memory policy encompasses what an agent writes, how it indexes and retrieves records, how it stages evidence in the prompt, and how it maintains that evidence across sessions. The retrieval index is merely one component of that policy. Component-level microbenchmarks help locate failures in search precision or index latency, but task-level outcomes ultimately decide whether the assembled policy satisfies operational acceptance criteria.

### Cross-Session Policy Trials

^sec-vol3-long-term-memory-policy-trials

If an evaluation harness shares a single writable vector store across candidate memory policies, a reflection or reference answer written during Policy A’s run leaks into Policy B’s trial and makes Policy B appear to learn from tasks it never solved. A controlled cross-session trial begins with a fixed source snapshot and an isolated initial memory store for each policy, running identical task sequences under identical constraints on model inference, tool execution, and compute budgets. Records generated during one trial session may influence subsequent sessions within that same trial, since that cross-session behavior is what the trial measures, but they must never contaminate a parallel trial. Ground-truth reference answers, test fixtures, and evaluator annotations must remain strictly outside both writable and retrievable stores.

↪ Evaluation leakage, including solutions that persistent memory carries from one run into the next, is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-leakage|Evaluation leakage]]**.

The comparison in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.11 Evaluating Memory Policies#^tbl-vol3-memory-policy-comparison|table 10]] isolates the baseline benefit of raw persistence from the operational benefit of governing what persists. Across all experimental conditions, the system enforces identical access controls and action permissions. The “unchecked” condition isolates content admission alone, while all conditions experience external source modifications and user updates on the same synchronized fixture schedule.

| **Policy condition**                        | **Question the comparison tests**                                                                                             |
|:--------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------|
| New memory writes disabled                  | Can the task be completed from the allowed sources without accumulating additional cross-session memory?                      |
| Unchecked memory writes                     | Does retaining proposed notes help later sessions, or propagate unsupported claims and duplicates?                            |
| Checked admission, no lifecycle maintenance | Do admission checks help initially but leave records misleading after later changes?                                          |
| Checked admission and lifecycle maintenance | Do correction, supersession, revalidation, expiry, and deletion preserve useful evidence under change, at an acceptable cost? |

Table 10: **Memory policy comparison**: Begin each condition from the same store and evaluate the same sequence of sessions. The conditions isolate responsibilities; none is an assumed empirical winner.

^tbl-vol3-memory-policy-comparison

The scheduling preference supplies a concrete lifecycle fixture: an initial preference recorded at 10:00, an explicit supersession at 11:00, and a user deletion request in a subsequent session. The evaluation tests whether the agent applies the active preference before deletion and complies with post-deletion invariants afterward. This requires inspecting every storage tier: primary vector and keyword indices, consolidated summaries, and staged prompt templates. An agent that suppresses the primary record from raw search results but still retrieves an unpruned summary containing the old preference violates its withdrawal contract. System backups or audit logs retained for regulatory compliance must also fall under an explicit data-retention policy rather than being counted as active working memory.

Similarly, an iterative software-repair fixture retains the failing run at `r17`, records the subsequent passing run at `r18`, and then challenges a future agent session to distinguish historical debugging context from the current state of the implementation without inappropriately broadening the reproducer’s scope. When source files change, the fixture tests two behaviors: a relevant source edit should trigger revalidation of dependent records, while an unrelated source edit tests whether the policy mistakenly discards valid, useful evidence.

Deterministic fixed-record probes isolate specific defects in admission filtering, retrieval ranking, or cache invalidation. Full task trials then allow policies to accumulate their own records across multi-turn interactions, causing their execution trajectories to diverge naturally over time. Evaluators must hold initial conditions and scoring rubrics constant across runs. When stochastic generation or environment variations introduce noise, evaluations must report the number of independent trials alongside the full distribution of outcomes rather than relying solely on mean performance.

### Retrieval Relevance Judgments

^sec-vol3-long-term-memory-relevance-judgments

Scoring a retriever by whether it returns the `r17` failure log for a query about `src/pool.py` rewards the right record when the task asks for bug history and rewards a stale defect when the task asks whether `r18` passes. For each test query, the benchmark must define the eligible source snapshot, the authorized access scope, and the specific records relevant to the agent’s immediate task. Evaluation fixtures must explicitly label temporal validity rather than expecting an embedding model’s similarity score to distinguish historical context from current state.

Let ${\mathcal{R}}_k$ be the set of distinct records returned up to cutoff ${k}$, and let ${\mathcal{D}^*}$ be the set of labeled relevant records in the eligible snapshot. Precision at cutoff ${k}$ is defined as

$$
\text{P}@{k} = \frac{\lvert{\mathcal{R}}_k \cap {\mathcal{D}^*}\rvert}{{k}}, \qquad {k} > 0. \tag{5}
$$

^eq-vol3-precision-at-k

The denominator is the target cutoff ${k}$, not the number of records the retriever actually returned. Unfilled result positions receive zero credit. Under this formulation, an empty result set scores zero, ensuring that a policy that underfills its staged context cannot artificially outscore a policy that retrieves a broader set of useful evidence. In contrast, calculating precision strictly over the returned records (with $\lvert{\mathcal{R}}_k\rvert$ in the denominator) can invert these rankings. Evaluators must explicitly declare their denominator convention and report the raw count of returned records alongside precision scores.

Recall measures the fraction of relevant evidence retrieved from the eligible store:

$$
\text{Recall}@{k} = \frac{\lvert{\mathcal{R}}_k \cap {\mathcal{D}^*}\rvert}{\lvert{\mathcal{D}^*}\rvert}. \tag{6}
$$

^eq-vol3-recall-at-k

When the relevant set ${\mathcal{D}^*}$ is empty, recall is mathematically undefined ($0/0$). Evaluators should isolate unanswerable queries into a dedicated reporting cohort, assessing whether the agent correctly recognizes the absence of supporting evidence or fabricates an unsupported claim. Keeping the completion status of every evaluation query visible ensures that such boundary conditions are not swept into an aggregate average.

When surfacing an immediate answer is the priority, Mean Reciprocal Rank (MRR) evaluates how quickly the system finds its first hit. MRR computes the arithmetic mean of the reciprocal rank of the first relevant record across all evaluated queries, scoring zero whenever no relevant item appears within cutoff ${k}$. However, MRR is insensitive to whether the complete evidence required for a multi-hop reasoning chain was assembled. Multi-hop evaluation fixtures must separately verify that all required entity relationships and source versions are present.

Temporal applicability demands a separate metric. The **stale-return rate** is the fraction of current-state queries that return at least one record invalidated by subsequent source modifications. It measures the store one layer below the stale-support rate of context engineering (**[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-stale-support|equation 4.7]]**). Stale-return counts what retrieval hands back. Stale-support counts decisions that rest on superseded evidence once it is in context. A stale record that the runtime labels or excludes at staging therefore raises the first without raising the second. Historical retrospective queries must be evaluated and reported separately. Because a retriever that returns nothing returns no stale records, a degenerate policy that returns zero results achieves a perfect stale-return rate of zero while completely failing the task. Consequently, stale-return rates must always be reported alongside recall and evidence coverage.

### Lifecycle Outcomes and Full Costs

^sec-vol3-long-term-memory-lifecycle-costs

A memory policy that deletes a user preference from its primary table in 2 ms while leaving the preference inside a cached episode summary and a background embedding queue appears fast and compliant only until the next session stages the summary. In supersession and deletion trials, evaluators track whether an updated or deleted record, along with all its downstream representations (index postings, graph edges, and cached summaries), reached the declared target state within an established deadline. The benchmark logs update latency, queue backlogs, and unresolved timeouts. In this analysis, expiring a record from active retrieval and physically purging it from persistent storage are distinct operations that require distinct accounting. Describing a record loosely as “forgotten” obscures whether data was merely hidden from the read path or permanently deleted from the database.

End-to-end task acceptance remains the ultimate arbiter of system quality. The acceptance rate must be calculated across all admitted task trials, explicitly including timeouts, uncaught exceptions, and partial completions in the denominator. Satisfying an obsolete constraint is an operational failure, even if the retriever achieved high precision against a stale label set.

System resource accounting must respect the same strict evaluation boundaries. Cost accounting aggregates the end-to-end compute footprint: query generation, keyword search, dense similarity computation, cross-encoder reranking, model token usage, memory writes, offline consolidation, and background index compaction. This tally must include asynchronous background operations that do not directly block foreground user requests, as well as deferred maintenance tasks lingering at the end of the evaluation window. Dividing the total expenditure by the number of successfully completed tasks yields the cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**). If a system completes zero tasks, evaluators must report total expenditure and zero successes rather than computing an undefined or misleading ratio.

Storage measurements require equally clear accounting boundaries. Benchmarks should report raw source bytes separately from auxiliary structures, including inverted index postings, dense vector tables, graph adjacency lists, version metadata, and durability replicas. A benchmark report must explicitly define whether its reported storage amplification represents auxiliary bytes divided by raw source bytes, or total stored bytes (source plus auxiliary) divided by raw source bytes. Similarly, update-latency benchmarks must compare equivalent operations: a full index rebuild against a full index rebuild, rather than comparing a complete re-indexing pass against an asynchronous tombstone lookup. Notebook [6.5](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-storage-amplification) compares both metrics across two representative store architectures.

*Dense vectors multiply a store’s auxiliary bytes by an order of magnitude.*

**Napkin Math 6.5: Why two memory stores differ by an order of magnitude**

**Problem**: A hypothetical repository holds 50,000 files of 200 tokens each, 40 MB of source. Store A adds a BM25 index and a structural graph with 4 edges per file. Store B adds the same BM25 index plus 100-token chunks embedded as 768-dimensional vectors under an HNSW graph shaped like the one in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^tbl-vol3-ann-tradeoffs|table 5]]. The vectors are kept at full FP32 width, twice the FP16 width of the exact-scan corpus, and the encoder is stipulated to be slower than the local batch of notebook [6.4](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-index-maintenance-cost). How do their auxiliary bytes and re-index times compare?

**Math**: Store A’s auxiliary structures occupy 14.4 MB, an auxiliary ratio of 0.36× over the raw source (total ratio 1.36×). Store B’s occupy 340.8 MB, of which the vectors alone are 307.2 MB, an auxiliary ratio of 8.52× (total 9.52×). After an edit to 15 files, at stipulated throughputs for postings updates and parsing, Store A re-indexes in 34.1 ms. Store B must re-embed 30 chunks. At 50 chunks per second it needs 612 ms.

Store B carries ~24× the auxiliary bytes of Store A and takes ~18× as long to re-index.

**Systems insight**: Dense vectors dominate both the bytes and the maintenance time, because each chunk becomes hundreds of floating-point components produced by a model pass. Compressing the vectors attacks the byte term, and storing them at FP16 would halve the vector bytes. Only a faster encoder or fewer re-embedded chunks attacks the time term, which sets the stale window after every edit. The time ratio therefore depends on the stipulated encoder throughput and shrinks with a faster encoder, while the byte ratio does not depend on it. A dense index is worth its order of magnitude only when it raises task acceptance enough to repay that maintenance in the cost per accepted task. The live-source baseline of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.05 Agentic Retrieval#^sec-vol3-long-term-memory-agentic-retrieval|section 6.4]] pays neither term, which is why it is the comparison every added index must beat.

Staging depth warrants independent empirical measurement because task success does not increase monotonically with the retrieval cutoff ${k}$. Recall@${k}$ ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.11 Evaluating Memory Policies#^eq-vol3-recall-at-k|equation 6]]) cannot decrease as ${k}$ increases, but every added record changes the prompt the model must use. Two effects that limit usable working context act together here. Each superficially similar but irrelevant passage adds to the softmax normalizer and so dilutes the attention the critical evidence receives (attention dilution). A larger staged set also pushes some of that evidence toward the middle of the prompt, where models use it least reliably (lost in the middle) ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-liu2024lost|Liu et al. 2024]]). Too few records starve the decision of evidence; too many bury it. The optimal operating range depends heavily on the model’s attention architecture, task complexity, and reranker quality. This mirrors the working-set view of context (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-attention-working-set|4]]). In practice, a retrieval pipeline should configure candidate generation to maximize recall, use a precise reranker to stage only a compact working set into the prompt, and systematically sweep staging depth across evaluation trials rather than assuming a single static cutoff.

↩︎ Usable working context, with attention dilution and the lost-in-the-middle effect that bound it, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^sec-vol3-context-engineering-physics|Usable Working Context]]**.

Benign workload trials therefore map a multidimensional trade-off space rather than a single scalar benchmark score. A more expansive memory store retains helpful edge-case experiences, but it also accumulates obsolete or contradictory records. Conversely, a strict admission gate shields the agent from spurious lessons at the expense of rejecting valuable domain context. Varying read and write policies under identical operational budgets separates whether accepted task outcomes change because of evidence coverage, temporal applicability, lifecycle maintenance, or compute and storage costs, before testing how those same policies hold up when retrieved content is actively hostile.

### Adversarial Boundary Tests

^sec-vol3-long-term-memory-adversarial-tests

An indirect prompt injection embedded inside a fetched documentation page can trick a background reflection worker into storing an unauthorized directive as a permanent project lesson, where it survives long after the untrusted page is evicted from the context window ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-greshake2023not|Greshake et al. 2023]]). In an isolated evaluation sandbox, test harnesses inject synthetic credentials, probe unauthorized namespace boundaries, and retrieve documents embedded with indirect prompt injections. The test suite evaluates two enforcement layers: whether the runtime intercepts and suppresses unauthorized reads and writes, and whether an adversarial payload survives in downstream consolidated summaries after the primary source document has been withdrawn.

Evaluators must capture both the model’s proposed actions and the runtime’s actual execution disposition. Logging both stages ensures that the evaluation distinguishes an attempted security breach from an executed vulnerability. The memory policy is accountable for the records it admits, indexes, and stages; the tool and runtime authorization subsystems are accountable for governing what the agent is permitted to execute against the external environment.

↪ The general adversarial-evaluation method developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.10 Adversarial Robustness and Red-Teaming#^sec-vol3-security-evaluation|Adversarial Robustness and Red-Teaming]]** specifies the trial and the attacker’s capabilities and measures attack success beside useful completion.

**Checkpoint 6.4: Evidence across sessions**

A proposed memory policy raises retrieval scores on a static snapshot. Its authors have not tested updates, deletion, or later task outcomes.

**Trial isolation**: How can an evaluation harness prevent one policy’s stored reflections or reference answers from contaminating another policy’s trial?

**Update semantics**: Which later-session probes would distinguish successful preference supersession from keeping both conflicting preferences?

**Withdrawal scope**: What must be inspected beyond the original record after a deletion request, and what retention limits must the result disclose?

**Metric boundary**: Why can a zero stale-return rate coexist with failed retrieval, and which task and cost measurements would reveal the failure?

**Cost per accepted task**: Policy B raises acceptance from 50 percent to 60 percent but adds background maintenance equal to a tenth of Policy A’s attempt cost. Estimate whether its cost per accepted task rises or falls, and find the acceptance rate at which the two policies break even.
