# V3-06.15 Exercises

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-long-term-memory-exercises

Every quantity below is a hypothetical given chosen for round arithmetic, not a measurement of any system. Each problem ends in a decision; state the decision and the number that justifies it.

**1. Serializing a smaller call (Basic).** A call permits 16,384 tokens. The runtime reserves 1,024 for output, and all other serialized input occupies 11,264. The result envelope costs 96 tokens, and each retrieved record carries a 300-token body and 60 tokens of source, version, and provenance metadata.

1.  How many complete records fit, and how many tokens remain?
2.  A retrieval limit that counts only bodies would admit how many records, and by how much would their serialization overshoot the allowance?
3.  The task owner wants 13 records staged. Metadata cannot be dropped, because the version labels are what let the model tell `r17` from `r18`. What is the largest body excerpt per record that meets the request?
4.  Two more tool results adding 512 tokens of other input arrive before the call. How many complete records fit now, and which reservation should the runtime recompute before dispatch?

**2. Where the exact scan stops paying (Basic).** A tenant’s store holds ${N} = 2{,}000{,}000$ vectors of dimension ${d} = 1{,}024$ in FP16 (${s_{\text{elem}}} = 2$ bytes). The host sustains 100 GB/s of memory bandwidth and 2 TFLOP/s of peak arithmetic, and each search has a 5 ms latency budget.

1.  Compute the bytes, FLOPs, and arithmetic intensity of one exact scan, and compare the intensity with the host’s ridge point.
2.  What is the bandwidth floor for one full scan, and what optimistic eligible-vector ceiling does that floor set under the budget?
3.  A scope filter restricts most queries to one project of 150,000 vectors. Does the bandwidth floor rule out an exact scan, and what measurement would decide whether it meets the search budget?
4.  Would storing the full corpus as INT8 bring the bandwidth floor of an unfiltered exact scan within budget?

**3. How much agreement buys (Basic).** Lexical search returns P, Q, R, S in that order, and dense search returns S, T, P, U. Every candidate is fully scoped to the same `r18` snapshot, ties break by candidate identifier, and the runtime stages three records.

1.  With ${k_{\text{rrf}}} = 60$, compute every fused score with [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^eq-vol3-reciprocal-rank-fusion|equation 3]] and the staged set.
2.  Find the largest rank ${r}$ at which a candidate appearing at rank ${r}$ in both lists still outscores a candidate at rank 1 in only one list, for ${k_{\text{rrf}}} = 60$ and for ${k_{\text{rrf}}} = 1$.
3.  Candidate Q is the reproducer test the agent must read. Is there any positive ${k_{\text{rrf}}}$ at which Q outranks P? How does Q reach the staged set at ${k_{\text{rrf}}} = 60$, and what should the runtime do instead of relying on that?

**4. How much the task names (Intermediate).** Transfer the choice of retrieval policy ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.05 Agentic Retrieval#^sec-vol3-long-term-memory-agentic-retrieval|section 6.4]]) to the research agent, whose store holds notes distilled from fetched pages. Every model round takes 4 s, and retrieval operations are fast enough to ignore. Each note serializes to 600 tokens with its metadata, the retrieval allowance is 6,144 tokens, and everything retrieved stays in context until the answer. Three policies are available. A *direct read* stages exactly the records the task names, with no extra round. *Pre-staging* stages the top 8 ranked notes before the first call; when that set lacks needed evidence, the model falls back to probing for what is missing. A *model-directed probe* costs one model round and returns 2 notes. Every policy ends with one answer round. Three tasks arrive:

- R1: “Reconcile pinned notes `n-4412` and `n-4413`.” The evidence is those two notes. Pre-staging captures both with probability 0.9, and a miss costs one probe round. Directed search needs one probe round.
- R2: “What has earlier work in this project established about battery fade under fast charging?” The evidence is three unnamed notes. Pre-staging captures all three with probability 0.8, and a miss costs one probe round. Directed search needs two probe rounds.
- R3: “Trace where the 40 percent figure in `n-4412` came from.” The evidence is `n-4412` and three further notes, each found only from a citation in the one before. Pre-staging includes `n-4412` but captures the whole chain with probability 0.1, and a miss costs three dependent probe rounds. Directed search needs four dependent probe rounds.

1.  For R1, compute the expected latency and staged tokens of each policy. Which policy wins, and what does pre-staging add that the research agent’s binding constraint makes costly?
2.  For R2, compare pre-staging with directed search in expected latency, expected staged tokens, and worst-case staged tokens against the allowance. Which should the runtime choose?
3.  For R3, compute the same quantities for pre-staging and for directed search. Why is pre-staging’s lower expected latency not a reason to choose it?
4.  Design a policy for R3 that combines two of the three, and compute its latency and staged tokens. State the selection rule the three tasks illustrate, and name the property of a returned record that stays the same whichever policy retrieves it.

**5. Fitting an index in memory (Intermediate).** A research store holds ${N} = 50{,}000{,}000$ passage vectors of dimension ${d} = 768$ in FP16 on a host with 64 GB of memory available for the index. The candidate designs are an exact scan of the raw vectors, HNSW with 32 eight-byte links per vector, and IVF-PQ with ${m} = 96$ one-byte subcodes, ${C} = 10{,}000$ FP16 coarse centroids, and an 8-byte record identifier per stored code.

1.  Which designs fit the memory budget? Compute the resident bytes of each.
2.  For IVF-PQ, give the subvector dimension, the per-query lookup-table size with FP32 entries, and the compression ratio over the FP16 vectors.
3.  With ${n_{\text{probe}}} = 16$ and evenly filled cells, how many bytes of codes does one query scan, and how does that compare with the bytes read to compare the query against every coarse centroid? What does the comparison suggest about the next optimization?
4.  Full-precision re-scoring of a 100-candidate shortlist reads vectors from secondary storage. How many bytes does that fetch, what distance accuracy does it recover, and which upstream misses can it not repair?

**6. Synchronous re-indexing in a repair session (Intermediate).** Each edit in a repair session changes 5 files and 15 indexed chunks. Stipulated costs are 4 ms to parse a file, 2 ms to update one chunk’s postings, 40 ms per local embedding batch of up to 8 chunks, 150 ms per batch on a remote service, 50 ns for a local in-memory exclusion update per file, and 30 ns for a local lookup on one of 40 candidates per query. All strategies share a durable source-commit and coordination boundary whose costs are excluded, along with fallback retrieval costs. Background rebuilding starts immediately after that commit and executes the stipulated stages serially without queueing. A session performs 60 edits, and the model’s next dependent query arrives 2 s after each source commit.

1.  What write-path time does synchronous re-indexing add per edit with the local service, with the remote service, and over the whole session?
2.  What local metadata work does exclusion add per write and per query, and which costs are absent from this comparison?
3.  Under background re-indexing with exclusion, is any dependent query served while replacement entries are missing?
4.  A new runtime issues an automatic verification search 50 ms after every source commit. Which queries now fall inside the rebuild interval, what does the retrieval layer return for them, and does that change justify synchronous re-indexing?

**7. Deletion deadlines in a support store (Intermediate).** Transfer the invalidation analysis to the support agent. Its store holds 80,000,000 memory vectors under an HNSW graph, kept at constant size because inserts balance removals. Each day 2,000 customers request full deletion of their 40 records apiece, and 20,000 customers supersede one preference, tombstoning its old vector. Compaction is triggered at ${\rho_{\text{dead}}} = 0.10$, rebuilds the live graph at a stipulated 20,000 vectors per second, and each tombstone occupies 16 bytes of an in-memory exclusion set. Retention policy requires deleted content to be physically removed within 30 days.

1.  How many days until the ${\rho_{\text{dead}}}$ trigger fires, and what is ${\rho_{\text{dead}}}$ when the retention deadline arrives? Which constraint sets the compaction schedule?
2.  How long does one compaction take, and how large is the exclusion set just before it?
3.  Each superseded preference also appears in two session summaries of about 1,000 tokens each. How many summary tokens per day would regeneration cost, and what cheaper treatment does the write lifecycle allow for a summary that is only historical?
4.  The repair agent’s binding hazard is its own edits making indexed copies stale. Name the support agent’s binding hazard and the mechanism in this chapter that answers it.

**8. Typed edges as a budget control (Intermediate).** A structural graph around a seed function has, on average, 4 outgoing call edges and 10 import edges per node. The retrieval allowance is 8,192 tokens, each node record serializes to 200 tokens, and edges plus the envelope take 150 tokens. Treat the neighborhood as an exact tree with no repeated nodes.

1.  Through what depth does a traversal restricted to call edges fit, and through what depth does one that also follows imports fit?
2.  What is the largest number of complete nodes the allowance holds?
3.  Could trimming node records to 120 tokens let a depth-3 call-only traversal fit? What is the largest node record that would?
4.  Why would the exact-tree count overstate the staged size of a real repository graph, and why is that no reason to drop the depth bound?

**9. Does a dense index pay for itself? (Advanced).** Two memory policies serve the same repair workload with one attempt per task. Policy L, lexical plus structural retrieval, accepts 55 percent of tasks at \$0.80 per attempt. Policy D adds dense retrieval, accepts 62 percent, and stages more evidence, raising the attempt cost to \$0.84. It also re-embeds 20 chunks for each of 6 edits per task at \$0.0005 per chunk and carries \$0.01 per task of amortized vector storage. Its encoder processes 50 chunks per second.

1.  Compute ${C_{\text{eff}}}$ for both policies with **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**. Which is cheaper per accepted task?
2.  What acceptance rate must Policy D reach to break even with Policy L?
3.  How long does each edit leave the dense index without current entries, and what must the retrieval layer do for queries in that window?
4.  The vendor of Policy D’s encoder reports that Recall@10 rose from 0.60 to 0.80 on a static snapshot. Critique the claim as evidence for adopting Policy D, and design the trial that would settle the decision.

**10. Redesigning a freshness scheme (Advanced).** A team proposes to keep a repair index current with a per-file dirty flag that is set when an edit commits and cleared when a rebuild finishes, plus a five-minute age limit measured from the worker’s source capture. At expiry, an entry becomes ineligible immediately and is scheduled for re-indexing; until a replacement appears, the gateway returns an incomplete result. Every replica applies each primary update exactly 2 s after it commits there, and a publication replaces the file’s current entries. Consider one timeline. At ${t} = -0.1$ s worker W1 captures `src/pool.py` at `r17` and begins indexing it. At ${t} = 0$ the agent commits `r18` and the flag is set. At ${t} = 0.5$ s worker W2 publishes `r18` entries and clears the flag. At ${t} = 0.7$ s W1 finishes and publishes its `r17` entries. No other publication occurs before W1’s entries expire. The agent queries the file every 3 s from ${t} = 3$ s onward.

1.  Ignoring replicas, under the proposal, for how long are `r17` entries served as current, and how many of the agent’s queries can receive them?
2.  Assign generation intervals to the `r17` and `r18` entries and apply [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^eq-vol3-index-validity|equation 4]] with ${g_q}$ = `r18`. Which entries are admitted, and what must W1’s publication check do?
3.  A query issued at ${t} = 1$ s reaches a replica, carrying the log sequence number of the `r18` commit. Using the read-your-writes rule, compare a 0.5 s wait bound with a 1.5 s bound in added latency and in the evidence returned.
4.  Write the redesigned protocol as at most five rules, and state which part of the proposal, if any, survives.

**What’s Next: From memory policy to tool execution**

The memory policies in this chapter already assume controlled operations that read sources, search indexes, update records, and return bounded observations. A retrieved record names the version it observed, but whether the source still holds that version when an edit commits, and whether an update that timed out took effect at all, are questions no stored record can answer. Settling them requires an interface that separates a generated request from its authorization, execution, and reported outcome, the boundary Part III, Tool Use, develops. **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling#^sec-vol3-tool-calling|Tool Calling]]** begins with the tool-call contract through which the repair’s proposed reads and writes become permitted operations, so that retrieved information is never mistaken for permission to act.
