# V3-06.17 Footnotes

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^footnotes

<sup>1</sup> **BM25 (Best Match 25)**: The name records one weighting in the “Best Match” series of the Okapi retrieval system, built on the simple approximations to a two-Poisson model of term occurrence that Robertson and Walker ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-robertson1994simple|1994]]) derived. The formula survived decades of learned rankers because it needs no training data, only corpus statistics an index already keeps, which is why it remains the baseline a repository agent can deploy on the day its workspace is created.

^fn1

<sup>2</sup> **Inverse Document Frequency (IDF)**: Spärck Jones ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-sparckjones1972statistical|1972]]) proposed weighting a term by how few documents contain it, on the argument that a term shared by most documents cannot tell them apart. In a repository that argument favors exactly the tokens an agent searches for, such as a unique test name or error string, and discounts keywords every file shares, which is why a rare identifier ranks sharply under BM25 while a vague symptom description does not.

^fn2

<sup>3</sup> **Cost-Based Access Path Selection**: The System R optimizer chose among index scans, sequential scans, and join orders by estimating each predicate’s selectivity and the pages each plan would touch ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-selinger1979access|Selinger et al. 1979]]). A retrieval gateway faces the same estimate with a scope filter as the predicate and a postings list or vector index as the access path, and a wrong estimate costs either a scan of the whole corpus or an empty result that looks like absence.

^fn3

<sup>4</sup> **Vector Space Model**: Ranking documents by the angle between a query vector and each document vector predates learned encoders; Salton et al. ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-salton1975vector|1975]]) represented every document as a vector of term weights and scored it by cosine similarity. Dense retrieval keeps the geometry and replaces sparse, interpretable term weights with learned components, which is what lets it bridge vocabulary and also why no single component explains a match.

^fn4

<sup>5</sup> **Approximate Nearest Neighbors**: Exact nearest-neighbor structures that work well in two or three dimensions degrade toward a full scan as dimension grows, the curse of dimensionality. Indyk and Motwani ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-indyk1998approximate|1998]]) relaxed the problem to returning a point within a factor of the true nearest distance and showed, through locality-sensitive hashing, that the relaxation admits sublinear query time. Every ANN index an agent uses makes the same bargain, so its misses are part of the contract, measured as recall, never a defect to be tuned away.

^fn5

<sup>6</sup> **RRF score monotonicity**: With fixed ${k_{\text{rrf}}} > 0$, moving an item from rank ${r}$ to ${r'} < {r}$ in one input list increases its contribution by $1/({k_{\text{rrf}}}+{r'})-1/({k_{\text{rrf}}}+{r})>0$ ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-cormack2009reciprocal|Cormack et al. 2009]]). If its contributions from other lists do not decrease, its total score increases. This is a property of the item’s score, not a guarantee of improved final rank when other candidates also change, or of relevant evidence.

^fn6

<sup>7</sup> **Community Detection**: GraphRAG partitions its entity graph using the Leiden algorithm, which refines modularity-based clustering to ensure that every detected community is well-separated and internally connected ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-traag2019leiden|Traag et al. 2019]]). Modularity optimization rewards groups with higher internal edge density than an equivalent random network. A detected community reflects entity co-occurrence density within the extracted corpora; whether that topological cluster corresponds to a logical module boundary recognized by system maintainers must be verified against actual source architecture.

^fn7

<sup>8</sup> **Death Certificates**: Distributed replicated databases encountered this challenge decades ago. If a replica silently deletes an entry, a delayed update arriving from a partitioned peer appears to be fresh data and resurrects the deleted record. Demers et al. ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-demers1987epidemic|1987]]) resolved this in epidemic replication by writing an explicit “death certificate” that propagates through the cluster and supersedes older versions. In an agent memory architecture, lagging asynchronous indexers, pipeline queues, and restored snapshots function just like stale replicas, making durable tombstone markers necessary prior to physical deletion.

^fn8

<sup>9</sup> **Session Guarantees**: The Bayou project established four foundational client-centric guarantees for weakly consistent distributed storage: read your writes, monotonic reads, writes follow reads, and monotonic writes ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-terry1994session|Terry et al. 1994]]). An agentic system requires more than simple read-your-writes behavior. For example, if an agent reads `r18` from an up-to-date replica and subsequently retrieves `r17` from a lagging node on the next step, the system violates monotonic reads, and the agent’s view of workspace history moves backward.

^fn9
