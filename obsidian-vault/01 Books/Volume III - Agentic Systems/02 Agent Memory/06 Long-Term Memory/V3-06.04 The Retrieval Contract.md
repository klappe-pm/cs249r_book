# V3-06.04 The Retrieval Contract

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-persistent-governance

Diagnosing the connection pool’s stalled waiter requires both the current implementation in `src/pool.py` and the test telemetry associated with `test_waiter_notified_on_return`. A search across repository history can easily return both an r17 test failure and an r18 reproducer pass. While both records are genuine, they answer distinct questions: one documents the defect that triggered the investigation, whereas the other evaluates a candidate patch. Before choosing an index structure or a similarity metric, a system must specify what the agent’s next decision demands and what guarantees a returned record actually establishes.

**Definition 6.1: Retrieval contract**

A ***retrieval contract*** specifies the information requested, the permitted scope and resource limits of the read, and the provenance, applicability, and completion information returned with its results.

1.  **Significance**: It ensures a bounded search result remains interpretable before that result enters the next model invocation. A misread or misattributed result exacts a double penalty in the cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**): its tokens consume prompt budget and inference cost during the attempt, while the mistaken decision it induces drives down the acceptance probability.
2.  **Distinction**: Ranking algorithms merely score and order candidate items under a specific relevance heuristic. The retrieval contract establishes authorization boundaries, version constraints, serialization budgets, and explicit completion semantics.
3.  **Common pitfall**: Mistaking an empty result or a truncated scan for definitive proof that the requested data does not exist.

This contract applies uniformly whether the agent executes an index search, a relational database query, or a direct filesystem read; it mandates no single storage layout or similarity threshold. It divides the work among three parties ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.04 The Retrieval Contract#^fig-vol3-retrieval-contract|figure 1]]). The runtime sets the request’s bounds, the retrieval service checks access and searches within them, and the result envelope reports status, provenance, and limitations before the runtime stages any evidence for the next model call.

![[90 Assets/Volume III/06 Long Term Memory/Episodic Memory Stack 721bbea748.svg]]

Figure 1: **The Retrieval Contract**: The runtime sets the request’s scope, version requirement, and limits; the model may propose search terms but cannot widen those bounds. The retrieval service checks access, searches, and excludes inapplicable versions, and the envelope reports what was searched and whether the operation completed, returned a partial result, or was unavailable. Only then does the runtime stage selected evidence, with its source and version labels, within the payload budget.

### The Bounded Request

^sec-vol3-persistent-query-tuple

A raw information need such as “find the notification logic” underspecifies the retrieval operation. It leaves undefined whether the caller requires the active workspace, an earlier Git revision, or a diff between them. It says nothing about which repositories the principal may access. It also ignores how many tokens the caller’s remaining context window can accommodate. As summarized in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.04 The Retrieval Contract#^tbl-vol3-query-tuple|table 2]], framing retrieval as a bounded request separates these operational constraints from the underlying index mechanics.

| Request field                    | Meaning in the repair task                                                                 | Boundary it establishes                                                               |
|:---------------------------------|:-------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------|
| Query or information need        | Locate the waiter-notification implementation or the recorded reproducer result            | The requested match or observation, not a promise that it exists                      |
| Authorized scope and principal   | The designated repair workspace and the identity under which it is read                    | The runtime checks permitted paths and records; a scope string alone grants no access |
| Version or freshness requirement | Read r18, compare r17 with r18, or read the current source under stated snapshot semantics | Which state can answer the question                                                   |
| Result-count and payload limits  | Bound returned items and their serialized representation                                   | Count and content size are separate limits                                            |
| Execution limits                 | Deadline and supported bounds on scans, expansions, or other search work                   | When to stop waiting or searching and report incomplete work                          |
| Optional filters                 | Restrict file type, symbol kind, or other relevant metadata                                | Narrow the information need without replacing authorization                           |

Table 2: **A bounded retrieval request**: The runtime can supply task-wide defaults, while each query specializes the information need within those limits.

^tbl-vol3-query-tuple

A version requirement differs from a wall-clock freshness heuristic. An index entry for revision r17 remains invalid as current r18 source code even if an indexing worker refreshed it seconds ago. Wall-clock TTLs merely trigger periodic reindexing, whereas explicit version tokens establish whether a cached representation strictly matches its underlying source snapshot. When the retrieval service cannot fulfill the requested version from its precomputed index, it must either fall back to an authorized direct read of the primary store or return an explicit incomplete status. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^sec-vol3-persistent-invalidation|Section 6.9]] develops this trade-off once the index itself can lag its source.

Similarly, result-count, payload-size, and compute limits constrain different dimensions of system resource consumption. Ten complete source files consume far more serialized tokens than ten function docstrings, yet returning a single item might still require scanning millions of candidate records. The payload limit protects the caller’s downstream context window, search-work budgets (such as graph traversal caps or posting-list scan limits) constrain retrieval service compute, and execution deadlines prevent the agent runtime from blocking indefinitely. Client timeouts must also propagate cancellation signals to the underlying storage engines. Uncancelled background queries continue to consume backend resources and inflate total execution cost.

### The Result Envelope

^sec-vol3-persistent-result-envelope

Returning bare text snippets from a search leaves the caller unable to tell whether the matches came from `r17` or `r18`, or whether zero hits meant the symbol was absent from the repository or the query timed out halfway through the index. To keep search outcomes interpretable, a production retrieval service wraps matching records in a result envelope that specifies the repository scope and snapshot revision actually searched, the terminal execution status, and any operational constraints that qualify the results:

- `complete` confirms that the declared search algorithm ran to conclusion under its stated semantics. It is a mechanical guarantee about the search performed, not a claim to have found every relevant fact.
- `partial` indicates that the operation halted before exhaustive evaluation, explicitly recording the abort reason (such as an expired deadline, an unavailable index partition, or an output payload cap).
- `unavailable` signals that the retrieval subsystem failed to return usable data, whether due to network partitions, authorization failures, or service crashes.

When an operation yields partial results or truncates output to respect payload limits, the envelope provides an opaque continuation cursor so subsequent bounded requests can resume paging without re-executing the entire query. Together with the terminal status, that cursor and envelope decide what the runtime may infer when a query returns zero hits, a rule this chapter calls the *absence rule*. An empty result proves nonexistence if and only if a fully completed exhaustive scan produced it, and even then only within the scanned scope and revision snapshot. A completed literal string search across the repository showing that a symbol does not occur in revision r18 meets this standard. A truncated or partial scan that returns zero matches proves nothing, because the target may reside in an unvisited partition. An approximate index ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^sec-vol3-long-term-memory-vector-search|section 6.6.2]]) offers no absence guarantee even when it completes, because it deliberately skips most of the candidate space to save work. A result set that lacks the relevant record may reflect that skipped region rather than the record’s absence from the corpus.

At the item level, every returned record carries structured metadata alongside its raw content: a persistent URI or path, byte or line ranges, the exact source commit or snapshot identifier, and a content hash of the returned bytes. When an item represents an empirical observation, such as a test execution log, the record must document the runtime configuration, environment variables, test revision, and terminal outcome. If an item stores a derived lesson or summary synthesized by an agent in an earlier session, its envelope must link to the primary records supporting that inference and flag its status as a derived model output. If the retrieval engine attaches a relevance score, it must name the algorithm that produced it (a lexical ranking function, a vector similarity, or a learned reranker, each developed later in this chapter). Ranking scores exist on their algorithm’s internal scale; systems must not treat them as calibrated probabilities.

``` yaml
status: complete
scope: {workspace: repair, principal: repair-agent, source_snapshot: r18}
items:
  - role: source_record
    path: src/pool.py
    lines: [a, b]
    revision: r18
    content_hash: h18
    score: {method: lexical_rank, value: s}
    content: <slice of the return path>
  - role: observation
    test: test_waiter_notified_on_return
    revision: r17
    configuration: c17
    outcome: failed
    content: <recorded failure trace>
```

Listing 1: **A serialized result envelope**: The response-level fields report what was searched and how the search ended; each item carries its role, location, version, and hash beside its content. Symbolic values stand for settings and contents chosen by the runtime; the field names do not prescribe a storage API.

^lst-vol3-result-envelope

In the connection-pool repair task, the staged payload might pair a slice of `src/pool.py` from revision `r18` with an error trace recorded under revision `r17`, as in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.04 The Retrieval Contract#^lst-vol3-result-envelope|listing 1]]. The fields outside the two `content` bodies count against the payload budget just as the bodies do. The r17 trace explains why the repair was initiated, but it provides zero evidence regarding the behavior of the r18 candidate. By packaging each record in an explicit envelope, the retrieval subsystem preserves these applicability distinctions across the boundary between persistent storage and the working context. Envelope labels, however, record provenance without certifying veracity. A cryptographic content hash verifies only that the byte sequence matches a specific snapshot. It does not validate the factual correctness of the text. Similarly, categorizing a record as user input or agent-written memory confers no administrative authority on any instructions embedded within that content.

↩︎ The scope rule and the untrusted span are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-source-scope|Preserving source and scope]]**.

### Evidence Staging

^sec-vol3-persistent-quarantine

Piping top-ranked retrieval hits straight from the search backend into the prompt lets uncalibrated similarity scores, stripped version labels, and uncounted metadata wrappers overrun the context budget or slip stale `r17` excerpts into an `r18` decision. The agent runtime, never the retrieval backend or a raw ranking score, therefore decides which records enter the downstream prompt: it selects evidence for the immediate decision, keeps the source and version tags needed to interpret each item, and accounts for the full serialized token footprint. Staging is where invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) reaches the durable read boundary. The bound below the model is mechanical, because a runtime rule rather than the model or the ranker decides what is admitted. The version labels the runtime preserves are the evidence a later acceptance check needs to tell an `r17` observation from an `r18` one. Even after those checks, retrieved records remain untrusted spans when fetched from a local repository, because serialization that separates them from system instructions cannot stop the model from following text embedded in a record body, the hazard known as prompt injection.

↪ Indirect prompt injection, delivered through retrieved documents and other observations an agent reads, is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.03 The Adversarial Threat Model#^sec-vol3-security-injection-entry-points|Prompt injection entry points]]**.

Accurate payload accounting must measure the entire serialized envelope, including wrapper tags, source paths, version identifiers, and status headers, alongside the raw text bodies. Underestimating this structural overhead leads directly to context exhaustion. The token count in notebook [6.1](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-retrieval-payload-budget) shows how metadata overhead changes the number of complete records an agent can stage within a fixed prompt allocation.

**Napkin Math 6.1: Making room for retrieved evidence**

**Problem**: A hypothetical model call permits 32,768 tokens in total. Reserving 2,048 tokens for generation leaves the remainder for input. If baseline system prompts, tool schemas, and conversation history occupy 24,576 tokens, how many complete retrieval records can the prompt accommodate?

**Math**: The retrieval allowance is $32,768 - 2,048 - 24,576 = 6,144$ tokens. Assume a 128-token response envelope and records that each contain 512 body tokens plus 64 metadata tokens, giving 576 tokens per record.

The maximum number of complete records that fit is 10. Staging these records alongside their envelope consumes $128 + 10 \times 576 = 5,888$ tokens, leaving a remainder of 256 tokens, too few to hold another complete record.

A naive sizing policy that accounts only for raw document bodies would admit 12 records. When serialized with metadata and envelopes, however, those records require 7,040 tokens, overshooting the allocated retrieval budget by 896 tokens.

**Systems insight**: Metadata and envelope framing consume context capacity just as surely as document bodies. In this configuration, each record dedicates 64 of its 576 tokens to provenance, causing a body-only heuristic to overcommit the prompt by 2 records. The runtime must reserve capacity for output tokens and the global envelope first, then admit $\lfloor(\text{allowance} - \text{envelope})/(\text{body} + \text{metadata})\rfloor$ records, remembering that every token assigned to system instructions or tool definitions shrinks the retrieval allowance one for one.

Because subword tokenizers (such as Byte-Pair Encoding) merge tokens across string boundaries, tokenizing text fragments in isolation and summing their counts yields an inaccurate total. Runtimes must measure token lengths on the final, fully serialized prompt structure using the target model’s tokenizer. When a critical record exceeds the remaining budget, the runtime must not silently truncate the text. Instead, it should stage a syntactically coherent excerpt with explicit truncation markers, defer the item to a subsequent retrieval pass, or return an opaque handle that the model can resolve on demand.

Every staged token also incurs concrete inference engine overhead beyond occupying space in the context window. Retrieved context must be processed through the model’s compute-intensive prefill phase and then pinned in accelerator memory as key-value (KV) cache tensors for the duration of the generation cycle or prefix cache retention window. Staging more records increases the token volume that the serving engine must process and retain, although the resulting prefill latency depends on the model, prefix reuse, and serving configuration. Every retained token counts against the resident-fit bound of the serving node’s KV pool, so a generous staging policy reduces how many trajectories the node can serve concurrently.

↩︎ The per-sequence footprint of key-value cache state, and how it limits the number of sequences a node can serve concurrently, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^sec-vol3-kvcache-geometry|The Footprint of Retained Attention State]]**.

**Checkpoint 6.1: Interpreting a bounded result**

Each question presents a retrieval outcome; decide what operational conclusions it licenses.

**Stale excerpt**: A query for current source returns an r17 excerpt after the workspace reaches r18. Which historical diagnostic inferences remain valid, and what must happen before the excerpt informs an r18 edit?

**Deadline vs. completion**: A search reaches its deadline with no matches. Which status does it return, and which conclusion that a completed literal scan of the same snapshot would support is unavailable here?

**Payload estimate**: If per-record metadata doubled from the value in notebook [6.1](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-retrieval-payload-budget), how many complete records would fit the same allowance, and what must the runtime measure before dispatching the call?

The retrieval contract establishes the operational bounds, provenance requirements, and payload limits for each read, but it leaves open an architectural question, namely which component formulates the query. A runtime can predict needed evidence and pre-stage it before invoking the model, or it can equip the agent with search tools to probe the store interactively as discoveries unfold.
