# V3-06.12 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-long-term-memory-fallacies

Persistent memory systems fail when they grant a stored representation more operational authority than its underlying provenance supports, or when they treat write-time admission as a permanent guarantee of validity. Each fallacy or pitfall that follows is a design shortcut that produces silent state corruption, latency spikes, or decisions made on stale evidence, and most carry a cost that one of the chapter’s notebooks quantifies.

**Fallacy**: *A near-duplicate memory carries no new information.*

The 10:00-to-11:00 revision at the admission gate ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^sec-vol3-memory-admission-gate|section 6.8.2]]) is one instance of a wider class. A flipped flag (“notify me of failures” becoming “do not notify me of failures”) and a scoped exception (“no meetings before 11:00 on Fridays”) also land beside the record they modify in embedding space. Yet the first reverses it and the second must coexist with it. A similarity threshold fails differently on each, dropping the reversal as a repeat and collapsing the exception into the general rule, so the agent either keeps the prohibited behavior or loses the narrower constraint. High geometric proximity does not imply semantic equivalence. An admission pipeline must first establish entity identity, scope, record kind, and explicit update semantics. Geometric similarity should deduplicate storage only after verifying that the new record asserts no state change and no change of scope.

**Pitfall**: *Treating a high-ranked record as current.*

Vector similarity scores indicate semantic or topical affinity with a query, but they convey nothing about temporal freshness, transactional validity, or operational authority. In the trace that opens [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^sec-vol3-persistent-invalidation|section 6.9]], the outdated `r17` excerpt of `src/pool.py` ranks first for the notification query. At turn 13 the agent consumed it without a version label and concluded that its own completed edit had been lost. It spent the following turns re-issuing that edit and then making speculative changes that pushed the repository further from a reviewed state. Coordinated generation checks prevent this particular cascade. Filtering 50 candidates adds 1.5 μs of local metadata lookup work under the stipulated scenario, excluding the durable coordination and fallback costs (notebook [6.4](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-index-maintenance-cost)). While index rank identifies candidate relevance, the runtime must rely on provenance, version tags, visibility scope, and completion status to govern how a retrieved record is applied.

**Fallacy**: *Staging more retrieved records gives the model more evidence.*

Recall@${k}$ cannot decrease as ${k}$ grows, but task success does not follow it ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-liu2024lost|Liu et al. 2024]]). In notebook [6.1](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-retrieval-payload-budget), a staging policy that counts only raw document bodies admits 12 records that serialize to 7,040 tokens, overrunning a 6,144-token allowance before any of it reaches the model. Even within the allowance, the dilution and position effects that make staging depth a measured quantity rather than a maximum still apply. Staging depth must be calibrated against downstream task completion and execution budgets rather than optimizing recall in isolation ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.11 Evaluating Memory Policies#^sec-vol3-persistent-governance-eval|section 6.10]]).

**Pitfall**: *Re-indexing synchronously on every write to keep the index current.*

Recomputing dense embeddings and rebuilding index graphs synchronously on every mutation introduces severe write latency and throughput bottlenecks. Under the stipulated costs of notebook [6.4](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-index-maintenance-cost), synchronous re-indexing adds between 88 ms and 1.26 s of blocking latency to every edit. Decoupling exclusion from rebuilding moves that work off the write path. The local exclusion updates take 0.4 μs, and each later query adds 1.5 μs of metadata lookups, excluding the common durable commit and coordination costs and any fallback retrieval. Replacement entries are built in the background. Blocking for fresh indexed representations can still be useful when dependent queries arrive inside the rebuild window and direct fallback cannot answer them within budget.

**Fallacy**: *Every dense store needs an approximate index, because an exact scan is too slow.*

Flat, exact vector scans scale linearly with the number of candidate vectors, but memory bandwidth alone carries substantial collections within tight latency budgets. In notebook [6.2](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-memory-bandwidth-and-latency-floor), an unindexed scan across 10,000,000 vectors has a streaming floor of 307.2 ms. Applying a tenant or workspace filter beforehand reduces the candidate set to 10,000 vectors, dropping the streaming floor to 0.31 ms. A 10 ms query budget gives an optimistic ceiling of ~326,000 vectors before query encoding, top-${k}$ selection, and record fetches are charged. Exact scans deliver perfect recall under the metric with zero graph construction overhead, no index fragmentation, and immediate write availability. The bandwidth floor rules out infeasible scans. Measured full-request latency determines whether an exact scan meets the budget and whether an approximate index merits its maintenance overhead.

**Pitfall**: *Evaluating memory on a static snapshot.*

Benchmarking a memory subsystem against a static snapshot conceals the operational costs and failure modes that emerge under continuous mutation. Snapshot benchmarks ignore index drift, synchronization lag, compaction overhead, and stale-read anomalies. In notebook [6.5](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-storage-amplification), modifying 15 files leaves a dense vector store without current entries for 612 ms, compared to 34.1 ms for a lexical and structural store. Every query in that window must fall back to a direct read or a partial result. Static tests also miss race conditions such as a delayed worker republishing superseded state or an explicitly deleted user preference persisting inside a rolled-up summary. Evaluate memory architectures using dynamic lifecycle fixtures ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.11 Evaluating Memory Policies#^sec-vol3-persistent-governance-eval|section 6.10]]), measuring end-to-end task completion, synchronization latency, and storage amplification across realistic write-read-delete workloads.
