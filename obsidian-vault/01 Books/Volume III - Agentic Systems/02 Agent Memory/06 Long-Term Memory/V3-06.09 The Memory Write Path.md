# V3-06.09 The Memory Write Path

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-long-term-memory-write-path

Retrieval can return only what the system has retained. An assistant that carries the directive “no meetings before 10:00” strictly within its current context window loses that constraint the moment the session terminates. Persisting the preference into long-term storage solves immediate conversational volatility, but it introduces the consistency challenge previewed in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.03 Persistent Records#^sec-vol3-persistent-need|section 6.2]]. When the user later moves the boundary to 11:00, the runtime must ensure the earlier record stops governing new scheduling decisions without corrupting the historical audit trail.

The distinction between authoritative sources and derived records governs writes just as it governed reads (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-source-authority|6]]). A user’s explicit directive provides direct evidence of an intent within a specific operational scope. An agent’s internal paraphrase constitutes a lossy derived representation. An automated rationale explaining why the user dislikes morning meetings is an ungrounded secondary inference. Storing all three artifacts as interchangeable assertions flattens evidentiary weight, depriving downstream retrieval pipelines of the ability to distinguish verified user intent from speculative model summaries.

**Definition 6.2: Memory write policy**

A ***memory write policy*** is the runtime rule governing which proposed records enter durable storage, what claims and operational scopes they carry, and how the system subsequently corrects, supersedes, revalidates, expires, or deletes those records and their downstream derivations.

1.  **Significance**: Every admitted record becomes a candidate for retrieval in subsequent agent sessions. An unverified lesson admitted into storage can degrade the execution accuracy of every future task that retrieves it. The write path provides the most economical barrier against memory pollution because admission checks execute once per write rather than amortizing filtering costs across thousands of subsequent retrieval queries.
2.  **Distinction**: Storage retention preserves raw bytes in a database or index. The memory write policy governs the operational authority of those bytes, defining what claims an entry can justify and when it must stop influencing execution decisions.
3.  **Common pitfall**: Deduplicating writes based purely on embedding similarity, which erroneously discards near-identical updates (such as a revised meeting time or flipped boolean flag) as redundant duplicates.

### Record Scope and Evidence

^sec-vol3-long-term-memory-record-scope

A user says “no meetings before 10:00” while looking at their team calendar in New York, and the agent stores the bare rule `"no meetings before 10:00"`. Next month, the agent rejects a 9:30 London client call on the user’s travel calendar because the stored record never captured which calendar, which time zone, or which consent boundary authorized the write. Every candidate memory record requires a concrete provenance tuple: an identifiable owner, an intended operational role, a bounded applicability scope, and verifiable backing evidence. In addition, the runtime must enforce explicit consent boundaries: permission to inspect user messages during active reasoning does not grant permission to commit those details into durable storage.

Software repair trajectories generate a different class of evidence. For example, test execution records showing a failure at revision `r17` and a pass at revision `r18` represent immutable historical observations, but neither result justifies an unconditioned assertion about the codebase. A synthesized rule such as “inspect the return path when a waiter remains blocked” represents a heuristic hypothesis derived from that sequence, not a proven invariant. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^tbl-vol3-long-term-memory-write-policy|Table 7]] formalizes these distinctions by categorizing how different memory records bind later execution.

| Record kind                          | Evidence retained                                                                  | Limit on later use                                                                    |
|:-------------------------------------|:-----------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------|
| Explicit preference                  | User statement, identity, scope, and statement version                             | Applies within that scope until revised or withdrawn                                  |
| Scoped observation                   | Tool result, checked revision, command, and relevant execution conditions          | Reports the observed case, not all later states                                       |
| Generated lesson or hypothesis       | Supporting observations, derivation, unresolved assumptions, and contrary evidence | Suggests an investigation; does not establish a new fact or grant authority           |
| Episode summary or continuation note | Task identifier and links to retained events and artifacts                         | Carries selected history or unfinished work; does not replace the underlying evidence |

Table 7: **Claims in agent-written memory**: Record kinds differ in what supports them and what a later task may infer from them.

^tbl-vol3-long-term-memory-write-policy

These record kinds impose distinct demands across different operational archetypes. The research agent and support agent stress the memory write pipeline in different ways than the repair agent does.

**Lighthouse 6.1: Persistent memory by archetype**

[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^tbl-vol3-memory-by-archetype|Table 8]] sets the three workloads side by side, from the record each one keeps to the policy it leans on.

| **Lighthouse**     | **Dominant durable record**                             | **Source of record**                                   | **Binding hazard**                                              | **Write-policy emphasis**                                                     |
|:-------------------|:--------------------------------------------------------|:-------------------------------------------------------|:----------------------------------------------------------------|:------------------------------------------------------------------------------|
| **Repair agent**   | Test observations and progress notes tied to revisions  | The repository at a source generation                  | Its own edits make indexed copies stale                         | Tag every observation with its revision; invalidate on the agent’s own writes |
| **Research agent** | Notes and summaries distilled from fetched pages        | Each external page as fetched, with its time           | Untrusted text becomes a confident lesson through summarization | Admit distilled claims as hypotheses with links to the fetched pages          |
| **Support agent**  | Customer history, preferences, and answers about policy | The customer record and the published policy documents | A superseded preference or ungrounded policy answer is reused   | Supersede by explicit replacement; propagate deletion to every derived copy   |

Table 8: **Persistent memory by archetype**: The binding hazard, not the storage technology, decides which part of the write policy each workload stresses.

^tbl-vol3-memory-by-archetype

**Systems insight**: The repair agent’s memory hazard comes from its own writes, the research agent’s from other people’s text, and the support agent’s from time. One retrieval contract serves all three, and the write policy is where they diverge.

### Admission Before Deduplication

^sec-vol3-memory-admission-gate

When a model can commit notes directly to durable storage without a runtime check, or when the write pipeline deduplicates candidates by cosine similarity before inspecting their claims, a speculative guess enters the store as fact while a preference revision from “no meetings before 10:00” to “no meetings before 11:00” is discarded as a near-duplicate. Even when an architecture allows the language model to manage its active context by paging memory entries explicitly ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-packer2023memgpt|Packer et al. 2023]]), context paging controls only working set occupancy; durable admission remains the exclusive responsibility of the storage runtime. The **admission gate** validates write permissions, confirms that the target store allows persistent retention for the active session, classifies the record type, and verifies that attached evidence satisfies the schema before any deduplication check runs. Structural schema validation checks required fields such as timestamps and provenance identifiers.

Semantic fidelity, the requirement that the proposed record asserts nothing absent from the raw transcript, needs a check of its own, and that check is a verifier with error rates like any other. A deterministic check can validate a constrained structured input against the proposed record’s owner, relation, value, and scope. Finding “11:00” in free-form text establishes only its occurrence; “11:00 applies only on Fridays” does not support an unrestricted scheduling preference. For free-text summaries, a calibrated model-based judge is one fallible fidelity check, and its false acceptance rate (**[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^sec-vol3-test-time-compute-check-precision|How base rates limit check precision]]**) measures how often unsupported claims pass that check into durable storage, where every later session can retrieve them. Generating a summary and establishing that it is faithful are different events, which is the verification asymmetry (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-verification-asymmetry|3]]) applied to memory admission. Sensitive data (such as credentials and private identifiers) demands strict classification and scrubbing policies. Regular expression filters miss unstructured disclosures that match no standard secret pattern. When an agent proposes an interpretive conclusion lacking direct observational backing, the admission gate must either reject the candidate or downgrade it to an explicitly tagged hypothesis, preventing it from masquerading as a validated preference or concrete observation.

Only after passing admission validation does the runtime evaluate whether the candidate record inserts a new entry, updates an existing record, or duplicates existing knowledge. Vector similarity in an embedding space is useful for candidate retrieval, but it cannot resolve write semantics. Because distance thresholds would treat the 10:00-to-11:00 revision as an uninformative repeat, deduplication and update routing must match on entity identity, scope, and record kind first.

When an admitted record targets an existing entity under an identical scope, the runtime executes **supersession**. The runtime creates a newly versioned record and marks the prior entry as superseded. This terminates the prior record’s eligibility for active decision-making while preserving it in historical logs for auditing and provenance tracing. When scopes differ (for example, if the 11:00 restriction applies only to Fridays), both records remain valid within their respective domains. When scopes overlap ambiguously, the runtime must flag an unresolved conflict or prompt the user for clarification. Heuristically synthesizing conflicting records into a fuzzy compromise produces brittle, ungrounded behavior. Systems must also distinguish an in-place correction from a true state transition. Fixing a transcription error that corrupted “10:00” repairs the fidelity of an existing record, whereas accepting an 11:00 update documents an authentic change in preference.

Concurrent updates demand explicit coordination primitives at the storage layer. A proposed supersession must carry the base version identifier against which it was generated. The store then evaluates and applies the update atomically through a compare-and-swap or conditional write. This is the same optimistic validation that context engineering applied to tool preconditions, and it closes the race inherent in separate read and write phases. Optimistic validation suits memory writes particularly well. Two sessions seldom revise the same preference concurrently, so conflicts are rare, and a model call lasting several seconds makes a pessimistic lock impractical to hold across the invocation that proposes the write. When a collision does occur, the runtime must abort the write, reload the latest state, and re-evaluate the update against an explicit conflict resolution policy. Handing the conflict back to the model to blend the two states without transactional guarantees invites silent corruption.

↩︎ Optimistic validation, which checks at commit that the state a decision read is unchanged and aborts otherwise, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-change-detection|Detecting change and bounding uncertainty]]**.

### Recorded Observations and Derived Lessons

^sec-vol3-memory-dual-write-path

If an agent waits for a reflective summary and vector embedding to finish before recording a tool’s raw output, a timeout or crash in the summarization model loses the hard evidence of what the tool actually did. When an agent executes an action, the runtime immediately writes the raw observation (the execution context, task ID, source revision, tool parameters, and raw output status) to durable storage. Only after this initial write does the runtime schedule background pipelines for summarization, embedding generation, and heuristic reflection, keeping costly model calls off the synchronous tool path. Generating reflective summaries has demonstrated substantial empirical gains in autonomous error recovery ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-shinn2023reflexion|Shinn et al. 2023]]). The resulting verbal reflections must nonetheless enter the store strictly as generated hypotheses ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^tbl-vol3-long-term-memory-write-policy|table 7]]), with explicit foreign-key links to the raw observations from which they were induced.

Write acknowledgments must explicitly report the durability boundary achieved. Systems must distinguish among three distinct guarantees: *buffered in memory* (queued in an ephemeral local ring buffer), *committed to durable storage* (flushed to non-volatile disk or replicated across storage nodes under the durability contract), and *indexed for search* (visible to vector and keyword retrieval engines). Merely enqueuing an event into an in-memory worker queue provides zero crash durability. If a task requires strict persistence guarantees before taking non-reversible external actions, the runtime must block on storage confirmation rather than proceeding optimistically. In addition, background indexing and reflection pipelines consume significant accelerator cycles and storage I/O. System schedulers must explicitly account for these background workloads to prevent asynchronous memory indexing from starving user-facing interactive inference.

### Revalidation, Expiration, and Deletion

^sec-vol3-memory-recency-decay

Once a record is committed, its status changes as its supporting evidence and operational context evolve. The superseded 10:00 preference and the `r17` test failure both remain accurate historical records after they lose eligibility for current decisions, while an unconfirmed scheduling rule retrieved across 30 runs without complaint is thirty times reused, not thirty times verified. Retaining historical snapshots is a deliberate architectural policy choice, and keeping active records trustworthy over time requires explicit rules for revalidation, expiration, and deletion.

**Revalidation** refreshes the empirical support for an existing record. Asking the user to confirm that the 11:00 scheduling boundary remains active provides authoritative fresh evidence, whereas repeated retrieval across dozens of runs indicates only frequent usage and adds no new support. Consequently, storage schemas must maintain distinct timestamps for record creation, last access, and last authoritative confirmation. Similarly, revalidating an automated diagnosis or heuristic rule derived from revision `r18` requires evaluating it against the current source code tree and active test environment, rather than treating age-based decay as a proxy for correctness.

**Expiration** revokes a record’s eligibility for decision-making once an expiration timestamp passes or a defined system condition is triggered. An expired temporary directive, such as an out-of-office scheduling window, must not govern subsequent actions without explicit reconfirmation. Some memory systems rank records by similarity multiplied by a recency factor that shrinks with age. Penalizing an expired record this way is inadequate, because if a query has few close semantic matches, an expired record with a penalized score can still surface in the top-${k}$ retrieval set and contaminate the prompt. Robust write paths enforce hard filtering, partitioning or tagging expired records so that operational retrieval filters exclude them unconditionally while retaining the payload for compliance auditing.

Records built from a user’s own data carry an obligation that records about source code do not, because the person they describe has a say in whether and how long they persist. Permission to read a message during reasoning does not grant permission to retain it ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^sec-vol3-long-term-memory-record-scope|section 6.8.1]]). Each admitted user record should therefore carry the consent under which it was admitted and a retention period after which it must be deleted rather than merely excluded from retrieval. A store can honor a withdrawal of consent only if it can list every record that describes the user, derived summaries included, together with the consent recorded for each. Withdrawal of consent, an elapsed retention period, and an explicit deletion request all start the same deletion procedure.

Deletion addresses the physical and logical lifecycle of the stored data. When a user revokes consent or asks to delete a preference, purging the primary database row is only the initial step. Stale representations frequently linger in secondary indexes, dense vector stores, consolidated episodic summaries, key-value caches, and pre-staged prompt templates managed by the runtime. The key-value case is easy to miss, because a cached prefix that contains the deleted preference still matches any request that repeats those tokens, and a prefix match certifies identical tokens, not current facts. The runtime must therefore evict that prefix or change the prompt so it no longer matches. A comprehensive deletion procedure must identify every downstream derivative, revoke its retrieval eligibility immediately, and schedule background reclamation or re-indexing under the governing data retention policy. To bridge the latency between request receipt and asynchronous garbage collection, systems write the storage counterpart of the marker that context invalidation places in a prompt. This **tombstone**[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn8|⁸]] is a durable exclusion record that filters the entity out of all active query paths before physical purging completes.

↩︎ Why a prefix-cache hit verifies identical tokens rather than fresh evidence is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kv-cache-prefix-compatibility|Prefix compatibility]]**.

↩︎ Tombstones as masking records that log-structured storage engines keep until compaction, and their contrast with an advisory notice in a prompt, are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-invalidation-choice|Removing, replacing, or appending]]**.

A deletion receipt must specify the exact boundary of guarantees achieved. Immutable cold backups, out-of-band external audit logs, and in-flight API payloads dispatched to third-party model providers lie outside the synchronous deletion perimeter. Deleting a record from runtime memory cannot retract a prompt token that an external foundation model has already processed, nor can it un-schedule a calendar invite already sent across an enterprise network. What the runtime can and must guarantee is that every internal index, cache, and prompt assembly buffer within its trust domain immediately ceases to use the deleted entity in future reasoning cycles.

### Consolidation

^sec-vol3-memory-consolidation

After a dozen debugging sessions on an asynchronous runtime, retrieving forty separate stack traces and raw test logs overflows the retrieval budget before the model sees the pattern connecting them. **Consolidation** compresses clusters of related, fine-grained records into structured, high-level representations optimized for future retrieval, such as an architectural summary documenting which notification paths were evaluated, which revisions broke invariants, and which hypotheses remain open. Autonomous agent architectures frequently employ background workers to synthesize episodic observations into higher-level reflections ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-park2023generative|Park et al. 2023]]). From a systems perspective, every consolidated reflection is a generated lesson ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^tbl-vol3-long-term-memory-write-policy|table 7]]). Clustering records by embedding proximity helps identify candidate groups for consolidation, but vector similarity alone cannot establish causal relationships. Verifying that two failures share an underlying defect requires structural evidence that semantic proximity cannot supply.

When generating consolidated records, the write pipeline must preserve provenance graphs, explicitly recording references to the constituent raw records, boundary conditions, and any observed counterexamples. Synthesizing multiple successful execution traces into an unconditioned, global procedure risks overgeneralizing domain-specific behavior. Retaining the underlying source observations alongside the consolidated abstraction also remains a deliberate architectural decision. Consolidated summaries minimize prompt tokens during inference, but stripping the raw logs removes the granular execution traces necessary for deep auditing and subsequent re-indexing.

### Self-Reinforcing Errors

^sec-vol3-memory-self-poisoning

A faulty diagnostic guess that is copied into an episode summary, absorbed into a weekly milestone report, and ultimately consolidated into a cross-project heuristic still rests entirely on the original faulty inference. Under formal evidentiary rules, repeated retrieval and re-summarization provide zero independent validation, yet each consolidation cycle risks treating the stored conjecture as an established premise and amplifying it across successive generations of context. **Memory poisoning** is the persistence of an unverified or withdrawn claim through the records derived from it. To prevent it, the storage engine must maintain rigorous dependency provenance across all derived artifacts. When an operator or verification pass invalidates a poisoned record, the invalidation must cascade through the entire dependency graph, retracting or marking as suspect every downstream summary and derived lesson. Merely down-ranking or tombstoning the root record is insufficient if derivative summaries continue circulating through retrieval indexes. Finally, even a fully validated, un-poisoned lesson functions merely as a candidate action suggestion. The execution engine must still enforce strict runtime authorization policies and environmental preconditions whenever an agent attempts to act on retrieved memories.

**Checkpoint 6.3: Following a preference through its lifecycle**

A user changes “no meetings before 10:00” to “no meetings before 11:00” for the same calendar and later requests deletion of the preference. An index and a session summary still contain the original value.

**Admission and revision**: Explain why semantic embedding similarity must not discard the 11:00 update, and identify the record that enters the superseded state.

**Evidence and time**: The 11:00 preference was retrieved in 30 scheduling tasks across six months without explicit user revalidation. Should the runtime apply it to the next task without prompt confirmation, and which specific timestamp field determines this policy decision?

**Withdrawal**: Enumerate all storage and cache representations that must stop influencing downstream prompts, and specify what guarantees the deletion acknowledgment can truthfully report if an immutable backup retains the raw record for 90 days.

**Claim scope**: Contrast the evidentiary threshold required for an explicit user constraint against that required for an inductively generated scheduling heuristic.

The memory write path establishes what a stored record claims, what evidence supports it, and when its operational validity ends. Those decisions reach the agent, however, only through derived indexes and caches that are rebuilt after the store changes, and until a lagging index catches up it can still answer with the record the write path just retired.
