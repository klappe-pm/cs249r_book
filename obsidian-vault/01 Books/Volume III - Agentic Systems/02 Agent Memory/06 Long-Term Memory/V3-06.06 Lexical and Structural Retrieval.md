# V3-06.06 Lexical and Structural Retrieval

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-persistent-bm25

When the repair agent investigates its stalled waiter, it faces distinct information needs: locating `tests/test_pool.py`, finding references to `test_waiter_notified_on_return`, and isolating the function enclosing a suspect synchronization statement. A well-designed retrieval contract does not force these varied tasks through a single mechanism. A known file path requires only a direct file read. A specific identifier calls for literal text search or symbol lookup. A broad symptom description requires ranking multiple candidate passages before the agent can decide which source files merit inspection.

### Exact Lookup and Lexical Ranking

^sec-vol3-long-term-memory-exact-lexical

When the repair agent already knows a path such as `tests/test_pool.py`, an exact path lookup retrieves that object directly from the authorized repository snapshot, whereas a literal text search for a token like `notify` or `waiter` scans for exact character sequences under declared case and boundary rules. Once a literal search across a repository returns dozens of matches spanning definitions, comments, import lines, and archived failure logs, however, neither exact lookup nor unranked substring matching can tell the caller which file matters most or order the candidate set.

To support repeated lexical queries across large corpora without scanning every byte on disk, retrieval systems rely on an **inverted index** ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-zobel2006inverted|Zobel and Moffat 2006]]). The index maps each distinct term to a postings list containing every document where the term appears. Beyond the document identifier, each posting typically stores the term’s in-document frequency and position offsets. How source text maps into postings depends entirely on the index’s analyzer. The analyzer determines token boundaries: whether it preserves full identifier tokens, splits `snake_case` and `camelCase` identifiers, normalizes letter case, or strips inflectional affixes through stemming. Consequently, a ranked match on an analyzed identifier behaves differently from an exact match on the raw string. When an agent requires an exact literal hit, it must either query an unanalyzed exact-match field or verify the returned source snippet directly.

When a query matches dozens or hundreds of candidates, ranking determines which documents enter the agent’s bounded context window. The **BM25**[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn1|¹]] scoring function balances three factors: term rarity across the corpus,[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn2|²]] sub-linear term frequency saturation within each candidate, and document-length normalization ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-robertson2009bm25|Robertson and Zaragoza 2009]]):

$$
\operatorname{score}({x},{Q})=\sum_{{q}\in {Q}}\operatorname{IDF}({q}) \frac{{f}({q},{x})({k_1}+1)}{{f}({q},{x})+{k_1}(1-{b}+{b}\lvert {x}\rvert/{\overline{|x|}})}, \qquad \operatorname{IDF}({q})=\ln\left(1+\frac{{N}-{n}({q})+0.5}{{n}({q})+0.5}\right). \tag{1}
$$

^eq-vol3-bm25

Here ${Q}$ contains the query terms, ${x}$ is an indexed document, ${f}({q},{x})$ is the term frequency of ${q}$ in ${x}$, $\lvert {x}\rvert$ is the document length in analyzer terms, and ${\overline{|x|}}$ is the collection’s mean document length. The corpus contains ${N}$ documents in total, of which ${n}({q})$ contain query term ${q}$. These lengths are analyzer counts, not the foundation model’s token counts. These symbols are local to lexical ranking. In particular, ${x}$ and ${b}$ do not carry the meanings earlier chapters gave those letters. The tuning parameter ${k_1}>0$ controls term-frequency saturation. At a fixed document length, the frequency factor rises toward ${k_1}+1$ as ${f}({q},{x})$ grows, so each additional occurrence adds less to the score than the one before. The parameter ${b}\in[0,1]$ modulates document-length normalization, with ${b}=1$ fully penalizing documents proportional to their relative length and ${b}=0$ disabling length normalization entirely. Because ranking depends on these mechanics, document chunk boundaries, analyzer choices, and parameter settings alter candidate scores even when the underlying source text remains unchanged.

**Example 6.1: A higher lexical score is a ranking decision**

**Scenario**: Consider a hypothetical index of 100,000 documents with a mean length of 400 analyzer terms. A single query term appears in 5 documents. With ${k_1}=$ 1.2 and ${b}=$ 0.75, its inverse document frequency is 9.808.

**Analysis**: A short candidate contains 80 terms and 1 occurrence of the query term. A long candidate contains 4,000 terms and 6 occurrences. The length term ${k_1}(1-{b}+{b}\lvert {x}\rvert/{\overline{|x|}})$ in the denominator of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.06 Lexical and Structural Retrieval#^eq-vol3-bm25|equation 1]] is 0.48 for the short candidate but 9.3 for the long one, so the long candidate’s extra occurrences are divided by a far larger denominator. Substituting these counts into the scoring rule gives 14.58 for the short candidate and 8.46 for the long candidate. Repetition alone does not determine their order: saturation and length normalization outweigh the long candidate’s additional occurrences.

**Systems lesson**: Rank orders candidates for inspection. If the short candidate is a comment while the long one holds the implementation, the agent still needs source inspection or structural information, and choosing whole files rather than functions as documents would change both scores.

### Structural Evidence

^sec-vol3-long-term-memory-structural-evidence

A lexical match on `notify` finds the token inside `src/pool.py` and inside an archived `r17` failure log alike, but it cannot return the complete enclosing function or trace which test calls the method that invokes `notify()`. **Structural retrieval** recovers that program organization: the enclosing function, type declarations, lexical scopes, and identifiers in call expressions. A parser translates source text into abstract syntax trees with explicit spans, while symbol resolution and semantic analysis establish directed relationships between definitions and call sites. While parsing a call expression identifies the call site syntactically, resolving which concrete implementation executes at runtime requires interprocedural analysis.

How much of that caller-callee chain a structural index recovers depends on language semantics, dependencies, and build configuration. Dynamic dispatch, reflection, generated code, and cross-process calls frequently escape static resolution. In a structural index, a missing edge therefore indicates a gap in static coverage rather than an unreachable path, while a static call edge records a potential invocation rather than an executed one. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.06 Lexical and Structural Retrieval#^fig-vol3-lexical-vs-ast|Figure 2]] contrasts the two representations on the connection-pool repair: whereas the lexical index maps `notify` to flat term frequencies in `src/pool.py` and `r17.log` alike, the structural index links `test_waiter_notified_on_return` to the pool’s return method and onward to `_available.notify()` while flagging dynamic calls whose targets remain unresolved.

Lexical indexes can carry path and symbol metadata, but text matching alone establishes no semantic relationship.

| **Information need**                              | **Suitable starting method**                      | **What the result establishes**                                                    |
|:--------------------------------------------------|:--------------------------------------------------|:-----------------------------------------------------------------------------------|
| Read a known path or locate a literal identifier  | Direct source read or declared exact-match search | The requested content or occurrences within the searched scope and version         |
| Find likely relevant documents from query terms   | Lexical ranking such as BM25                      | Candidate order under the analyzer, document boundaries, and scoring rule          |

### Search Scope

^sec-vol3-long-term-memory-search-scope

When a search service selects its top-ranked candidates globally across the repository and only afterward discards results outside `src/pool.py` and `tests/test_pool.py` (post-filtering), it can easily return an empty set while eligible matches sit farther down the global ranking. Restricting an initial probe to `src/pool.py` and `tests/test_pool.py` focuses the evidence and limits noise only when filtering and ranking are coordinated and the retrieval interface explicitly reports that bounded scope. A subsequent probe can then widen the scope to investigate callers across the repository. Restricting candidates before final scoring (pre-filtering) avoids the post-filtering drop, as does continuing postings traversal until the requested quota of filtered documents is filled. When query budgets or latency limits terminate the search early, the result remains partial.

Choosing the evaluation order is a cost-based optimization decision analogous to access path selection in relational database optimizers ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-selinger1979access|Selinger et al. 1979]]).[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn3|³]] The decision balances the filter’s selectivity against the rarity of the query terms. A selective filter, such as one that isolates two files in a repository of thousands, favors pre-filtering candidate documents and evaluating BM25 scores only on the survivors. Conversely, a broad filter paired with a rare identifier favors scoring first, because the rare term’s postings list is already short, provided the search engine continues scanning until enough eligible results remain. This trade-off reemerges with even sharper operational hazards when searching vector proximity graphs ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^sec-vol3-persistent-dense-retrieval|section 6.6]]).

### Vocabulary Mismatch

^sec-vol3-long-term-memory-vocabulary-mismatch

Early in an investigation, the agent may know only an observed symptom such as “a connection is returned, but another caller keeps waiting,” phrased in words the source code never uses, so exact and structural lookups return nothing. This failure is the **vocabulary mismatch** problem, where code authors and users describe identical concepts using distinct vocabularies ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-furnas1987vocabulary|Furnas et al. 1987]]). Heuristic techniques like identifier splitting, synonym expansion, or query reformulation can recover some lexical matches. Once an exploratory search identifies a concrete test name, literal lookup is far more direct than further conceptual search. When lexical heuristics still leave the candidate set inadequate, the agent needs a representation that maps descriptive prose to differently worded source implementations, along with hybrid rankers that combine dense semantic similarity with exact lexical precision without mistaking similarity for verification.
