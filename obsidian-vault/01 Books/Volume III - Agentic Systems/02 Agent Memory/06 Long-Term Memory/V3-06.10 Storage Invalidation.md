# V3-06.10 Storage Invalidation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-persistent-invalidation

The connection-pool repair has reached revision `r18`, yet a subsequent search can still return an excerpt of `src/pool.py` indexed at `r17`. Consider how a single stale read unravels an otherwise systematic debugging trajectory:

1.  At turn 12, the agent edits the return path in `src/pool.py`, and the workspace edit tool confirms the updated file at `r18`.
2.  At turn 13, a search for the notification logic retrieves the `r17` chunk, which still contains the buggy line replaced in the previous turn, without a version label.
3.  At turn 14, the model infers that its earlier modification was lost and reissues the edit. The edit tool rejects the request because the target snippet no longer exists in the current file.
4.  At turn 15, the model confronts conflicting signals: a confirmed write, an excerpt contradicting that write, and a failed re-edit. It concludes that the workspace filesystem is corrupted and begins issuing speculative, wide-ranging edits. Each action burns context tokens and tool budget while driving the repository further from a reviewed state.

The unlabeled stale read initiates this failure by presenting an accurate historical excerpt as current state. The conflicting evidence does not establish filesystem corruption. A direct read of the current source could expose the mismatch. Model reasoning cannot reliably compensate for a retrieval layer that conceals which version its evidence describes, and each turn the trace wasted lengthens the horizon over which per-turn errors compound (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]**). Maintaining a persistent index therefore forces a clean separation between two operations that an ephemeral staged prompt naturally couples: withholding obsolete records and generating their replacements.

**Definition 6.3: Storage invalidation**

***Storage invalidation*** is the exclusion of a derived record (an index entry, vector, summary, or cached result) from current-state retrieval once a relevant change to its source makes it inapplicable, independent of when a replacement is built.

1.  **Significance**: Coordinating exclusion with the source commit prevents known-obsolete entries from remaining eligible while their replacements are built. Notebook [6.4](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-index-maintenance-cost) compares the additional metadata and indexing work, separately from the common durable commit and coordination costs. In the turn-by-turn `r17`-to-`r18` trace from turns 12 through 15, one unlabeled stale read cost three turns of the repair’s budget.
2.  **Distinction**: Rebuilding synthesizes a replacement representation, whereas invalidation merely suppresses the obsolete one. This ensures that any query arriving during the rebuild window receives either an authoritative direct read or an explicit incomplete result rather than stale data.
3.  **Common pitfall**: Tracking staleness with an ephemeral dirty flag that clears automatically when a background job finishes. If an uncoordinated indexing worker completes late or a retrieval gateway restarts without durable tombstone state, obsolete entries can be erroneously readmitted.

### Source Generations

^sec-vol3-long-term-memory-source-generations

Relying on filesystem modification timestamps (`mtime`) to detect stale index entries fails when clock skew, branch switches, or sub-millisecond edits leave two revisions with indistinguishable timestamps. To guarantee freshness, an index entry must explicitly record the **source generation** from which it was derived: a monotonic version identity defined by the storage system’s write contract. In the connection-pool repair, `r17` and `r18` denote successive repository states. Once the runtime establishes `r18` as the active generation, any query seeking current code must systematically discard entries tagged with `r17`.

Deciding which derived records an edit affects is the dependency tracking that context invalidation applied to staged observations, now applied to records that persist in the store and its indexes. What is new at this layer is that generations make the tracking durable across sessions, and that some derived records cannot be patched in place. Data dependencies often span beyond individual files. A raw code excerpt depends solely on its source file revision. A call-graph edge depends on multiple source files alongside the static-analysis configuration. An episodic summary depends on the tool outputs and diagnostic logs it consolidates. When an underlying artifact changes, the runtime must invalidate all affected downstream records while keeping unrelated entries intact. If the dependency graph is coarse or incomplete, the runtime must conservatively widen the invalidation boundary or explicitly report retrieval uncertainty. A missing dependency link must never be treated as proof of validity.

↩︎ Tracking which claims depend on which observations, and propagating invalidation through that record, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-claim-dependencies|Tracking claim dependencies]]**.

From a systems standpoint, every retrieval index is a materialized view over base data, a problem relational database management systems have addressed for decades. Classical incremental view maintenance computes updates to a view algebraically from delta changes in base relations, bypassing the need to re-evaluate the full query ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-blakeley1986efficiently|Blakeley et al. 1986]]; [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-gupta1995maintenance|Gupta and Mumick 1995]]). Unstructured retrieval indexes, however, resist algebraic delta maintenance. Under fixed-size chunking schemes, inserting even two lines near the beginning of a source file shifts the token boundaries of every subsequent chunk. Because deep neural embedding models are non-linear, an updated vector cannot be synthesized from a vector subtraction and a text diff. Consequently, changed text requires discarding existing entries and running end-to-end forward passes to re-embed the new chunks. Practical retrieval architectures therefore decouple invalidation, a metadata exclusion coordinated with the source commit, from index rebuilding, which consumes substantial compute and network latency.

Beyond source generations, an embedding record must also encode the model identifier, tokenization pipeline, and preprocessing hyperparameters that generated it. A valid source generation confirms only that the underlying text is up to date. It does not indicate whether the vector remains compatible with the active retrieval model and query encoder.

### Source and Index Coordination

^sec-vol3-long-term-memory-index-coordination

If the workspace commits `r18` and publishes an asynchronous invalidation event on a message queue, a retrieval query arriving two milliseconds later can reach the index gateway before the queue message does and receive `r17` as current state. Avoiding that race requires a coordinated protocol among the storage coordinator, the indexing pipeline, and the retrieval gateway. This protocol assumes that the agent runtime governs workspace modifications. It also assumes that the retrieval gateway can query an authoritative source generation along with its content. Finally, it assumes that writes, index publications, and query admission share a coordination boundary, such as an atomic database transaction, a conditional write to a strongly consistent store whose replicas agree on a single commit order, or a local mutex. During an in-flight write, the gateway either holds queries within a tight latency deadline or marks the affected file scope as temporarily unavailable. A message queue or publish-subscribe broker alone cannot enforce these properties, because delivering a message is a separate event from committing the write it announces. The coordination sequence orchestrates a source modification while a straggling index worker remains active:

1.  The source coordinator commits the patch as generation `r18` and atomically updates the active generation watermark for admission checks. Here a watermark is a position marker, the highest generation the gateway treats as current, not one of the compaction thresholds of context engineering. This prevents a visibility split where newly committed code is readable from disk while an out-of-band index registry continues to treat `r17` as current.
2.  A subsequent query for `src/pool.py` retrieves candidate vectors derived from `r17` from the background index. The retrieval gateway checks their embedded generation tag against the active watermark (`r18`) and suppresses them. This exclusion signals index lag rather than a missing file or a failed edit.
3.  An indexing job started prior to the commit finishes late. During index publication, the worker checks its captured generation within the coordination boundary. Recognizing that generation `r18` has superseded its input, the coordinator discards the stale output or redirects it to an archival store.
4.  A fresh worker generates replacement vectors from an `r18` snapshot. It publishes them conditionally, committing the batch only if the workspace generation and index configuration remain unchanged throughout the indexing window.
5.  Inbound queries continuously evaluate candidate generations against the active watermark. Publishing `r18` records never reactivates older `r17` entries, and background garbage collectors reclaim retired vectors on an independent schedule.

Publication validation and index installation must occur as a single atomic operation, because checking generation validity first and writing later introduces a time-of-check to time-of-use (TOCTOU) race condition that allows concurrent edits to invalidate the payload. In-memory and durable tombstones record excluded generations while background workers rebuild representations. Because query admission enforces generation checks on every lookup, old candidates remain excluded even if temporary dirty flags clear prematurely. Similarly, deleting a source file installs a versioned tombstone, preventing delayed workers from accidentally resurrecting an obsolete record from an earlier snapshot.

Because most commits modify only a few files, replacing the entire index on every commit would waste work. Entries for files untouched by `r18` remain accurate even though they were indexed at `r17` or earlier, whereas entries for `src/pool.py` become obsolete at `r18`. Source generations capture this per-entry validity in a compact, interval-based form. Each derived entry ${c}$ carries a valid lifetime $[{g_{\text{birth}}}({c}), {g_{\text{death}}}({c}))$, where ${g_{\text{death}}}({c})$ remains open ($\infty$) as long as the underlying source scope is untouched and is set to the superseding generation (such as `r18` for `src/pool.py`’s `r17` records) when an edit modifies or deletes that scope. A query evaluating workspace generation ${g_q}$ admits candidate entry ${c}$ if and only if

$$
\text{IsValid}({c}, {g_q}) = \big({g_{\text{birth}}}({c}) \le {g_q} < {g_{\text{death}}}({c})\big). \tag{4}
$$

^eq-vol3-index-validity

For current-state execution, the runtime sets ${g_q}$ to the active workspace generation. For historical diagnostics, such as an agent reviewing why an execution failed at revision `r17`, the query sets ${g_q}$ to that historical revision. Subject to retention policies, [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^eq-vol3-index-validity|equation 4]] serves both use cases uniformly, admitting `src/pool.py`’s `[r17, r18)` entries for an `r17` replay while excluding them for `r18`.

Exclusion solves freshness, but it introduces an efficiency trade-off that compounds over time. Suppressed records continue to occupy memory. In an HNSW graph, tombstoned nodes remain embedded in their neighbors’ adjacency lists. Because greedy graph traversal continues to visit and evaluate these dead nodes before filtering them out at the admission boundary, a search with a fixed beam width explores fewer live items, degrading overall recall. To bound that loss, a background compaction process tracks the ratio of tombstoned records, ${\rho_{\text{dead}}} = \lvert {V_{\text{tomb}}}\rvert/\lvert {V}\rvert$. When this ratio crosses a tuned threshold, the system builds a compacted graph: it purges unreferenced records, recomputes neighbor connections among surviving nodes, rebuilds navigation entry points, and atomically swaps the compacted index into memory. This workflow adopts the compaction design of log-structured merge-trees ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-oneil1996log|O’Neil et al. 1996]]), balancing query latency and retrieval recall against the compute cost of background rebuilds. This is compaction in the storage-engine sense, rewriting a structure without its dead entries, not the summarization that context compaction performs on a prompt.

This coordination contract must remain robust against system restarts and uncoordinated writers. When a retrieval gateway restarts, it must reconstruct its authoritative generation state from durable storage before accepting queries. An empty in-memory tombstone table must never be treated as evidence that the index is fresh. If external tools or developers modify files without routing through the runtime coordinator, filesystem watcher events may arrive out of order or be dropped. In response, the gateway must fall back to direct, version-validated reads against the filesystem. If it cannot verify whether an indexed chunk matches disk before its query deadline expires, it must flag the result envelope as unverified rather than returning potentially stale data.

Replicated retrieval topologies require explicit **read-your-writes**[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn9|⁹]] guarantees, ensuring that an agent always observes the outcomes of its own preceding actions ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-terry1994session|Terry et al. 1994]]). When an agent issues a search following an edit, the query carries the log sequence number (LSN) corresponding to that write. A replica whose replay position (the last log entry it has applied) lags that LSN must pause execution within a bounded wait window. If the replica does not catch up before the deadline elapses, the gateway either routes the request to an authoritative primary or returns an explicit partial-status response.

### Retrieval During Index Refresh

^sec-vol3-long-term-memory-refresh-retrieval

Suppressing the stale `r17` vector for `src/pool.py` stops the agent from reading obsolete code, but while the `r18` embedding is still building in the background, a query for the pool implementation still needs an answer. When invalidation suppresses a record during an index refresh, the gateway must return an honest assessment of available evidence. As outlined in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^tbl-vol3-invalidation-tradeoffs|table 9]], a production retrieval layer can respond with one of three outcomes.

| Retrieval outcome             | Evidence supplied                                                                        | Remaining limitation                                                                                             |
|:------------------------------|:-----------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------|
| Current indexed result        | Payload whose source generation and index configuration satisfy the request              | Ranking and bounded search can still omit relevant records; completion status must reflect the search performed. |
| Authorized direct source read | A bounded source excerpt with its observed version and provenance                        | Direct access can be expensive, unavailable, or too narrow to answer the whole query.                            |
| Explicit incomplete result    | Admissible partial evidence, or no payload, with an explanation of the unavailable scope | The caller lacks the requested evidence and must not infer that the source contains no match.                    |

Table 9: **Retrieval choices during index refresh**: Exclusion protects against known version mismatch; replacement retrieval and search completeness remain separate obligations.

^tbl-vol3-invalidation-tradeoffs

The appropriate fallback depends on query structure. For an explicit target path like `src/pool.py`, the gateway can execute an authorized direct source read, returning the live `r18` text while background embedding jobs run. Conversely, a broad semantic query, such as a search for all modules affected by a modified locking interface, cannot be answered by reading a single file. Answering it accurately requires either a refreshed semantic index or comprehensive static analysis across many files. If bounded direct reads cannot resolve the query within the execution budget, the gateway must return an explicit incomplete result. Artificially inflating candidate limits (such as expanding ${k}$ during top-${k}$ nearest-neighbor retrieval) does not solve this problem, because an unindexed record is absent from the vector index and no search depth can retrieve it.

Where to place this maintenance overhead is an explicit design choice. Synchronous re-indexing moves parsing, chunking, and embedding directly onto the write path, guaranteeing that fresh representations exist before any subsequent tool executes. Background re-indexing acknowledges writes after the required durable source commit and coordinated exclusion, allowing tools to return before rebuilding finishes while relying on the gateway to manage queries during the refresh window. This architectural trade-off depends on workspace edit frequency and whether bounded direct reads can satisfy immediate downstream queries. As notebook [6.4](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-index-maintenance-cost) quantifies, their additional indexing and local metadata work can differ by several orders of magnitude, and they also differ in what a query during the rebuild sees ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^fig-vol3-index-invalidation|figure 7]]). Synchronous re-indexing never exposes that interval but stalls the write, unchecked background indexing serves `r17` entries as current, and background indexing with exclusion suppresses `r17` and answers the query with a direct read or a partial result.

**Napkin Math 6.4: Who pays for keeping the index current**

**Problem**: The repair’s next edit modifies 8 files across 16 indexed chunks. All strategies share the same durable source-commit and coordination boundary. The exclusion costs count only incremental in-memory metadata updates and lookups, excluding durable commit and replication, coordination contention, restart reconstruction, and fallback retrieval. The stipulated per-stage costs are 3.5 ms to parse a file and 2 ms to update one chunk’s lexical postings. A local embedding batch of up to 16 chunks costs 28 ms, and a remote embedding RPC costs 150 ms. Recording an exclusion entry costs 50 ns, and checking an entry costs 30 ns. Given these costs, how much additional indexing or local metadata work does each strategy add, and which path bears it?

**Math**: Synchronous re-indexing halts write completion until parsing, postings updates, and vector embeddings are fully finished. Backed by a local embedding model, this pipeline adds 88 ms directly to the write path. A single batched remote embedding call increases write overhead to 210 ms, while serial remote requests per file inflate it to 1.26 s. In contrast, updating 8 local exclusion entries adds 0.4 μs of in-memory metadata work. Subsequent retrieval passes check 50 candidates against this metadata, adding 1.5 μs of local lookup work. The local re-indexing stages consume 220,000× as much time as these metadata updates. This ratio does not compare complete durable write latencies.

**Systems insight**: Under the coordinated generation protocol, exclusion suppresses known-obsolete entries before subsequent admission, though it does not produce fresh representations immediately. The small local metadata costs do not price the complete durable enforcement path. The computational cost of re-indexing is not eliminated; it is deferred to background workers, requiring the query gateway to manage the staleness gap using the strategies in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^tbl-vol3-invalidation-tradeoffs|table 9]]. Coordinate exclusion with the source commit. Consider synchronous re-indexing when dependent queries arrive before background pipelines can finish and bounded fallback cannot supply the required evidence.

Background re-indexing without a generation check returns after the source commit but admits r17 entries as current until the rebuild finishes. Background re-indexing with coordinated exclusion returns before rebuilding finishes; a query in the interval sees r17 excluded and receives a direct read or a partial result, and the worker publishes only if its generation is still current. The cost labels compare incremental indexing and local metadata work, excluding the common durable commit and coordination costs and any fallback retrieval. The time axis is schematic.

^fig-vol3-index-invalidation

Retrieved evidence represents the source state observed at the moment of the read. In an agentic system, a concurrent write can land before the model finishes deliberating and invokes its chosen action. Any tool call whose correctness depends on an unmodified workspace must therefore enforce an execution-time precondition, such as an optimistic version check, at the tool boundary. The storage subsystem’s core duty is to preserve and surface the exact generation metadata that this precondition requires.

↪ The atomic conditional update that enforces this version precondition at the tool boundary is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-conditional-updates|Conditional updates]]**.

Source-generation checks suppress obsolete records, atomic publication prevents straggling workers from reinstating stale representations, and explicit fallback contracts clarify whether fresh evidence is available. Together, these mechanisms enforce internal storage consistency rather than task success. In accordance with the end-to-end argument ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-saltzer1984endtoend|Saltzer et al. 1984]]), whether the `r18` patch truly resolves the stalled waiter can be established only at the system boundary through integration tests executed against the real runtime environment. What the storage layer guarantees to that boundary is an uncompromised, auditable record of the exact source generation reflected in every retrieved fact.
