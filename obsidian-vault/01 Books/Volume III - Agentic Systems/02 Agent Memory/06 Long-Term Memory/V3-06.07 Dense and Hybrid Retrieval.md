# V3-06.07 Dense and Hybrid Retrieval

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-persistent-dense-retrieval

When an agent investigates a bug report describing a caller that hangs indefinitely, lexical search across the repository can easily rank the critical return path in `src/pool.py` low or miss it entirely. The line that matters executes `notify()`, but the report describes a caller that keeps waiting. Dense retrieval supplies a complementary candidate-generation mechanism, using learned representations to match a query against records that share underlying meaning rather than literal tokens. Because dense and lexical methods fail in different places, production systems usually run both and combine their rankings ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^sec-vol3-long-term-memory-rank-fusion|section 6.6.3]]).

### Dense Retrieval

^sec-vol3-long-term-memory-dense-retrieval

Running a neural model over every repository file on each search would make retrieval the slowest step in the agent loop. **Dense retrieval** avoids per-query corpus scoring by encoding a query and each searchable record as vectors in a shared geometric space and ranking records by vector similarity.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn4|⁴]] In a bi-encoder architecture, records are embedded offline before a request arrives, leaving only the query to be encoded online at request time ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-karpukhin2020dense|Karpukhin et al. 2020]]). This separation removes heavy embedding inference from the critical query path. Offline encoding, however, creates an ongoing maintenance obligation. Newly inserted or modified records require fresh vector generation, and upgrading or fine-tuning the underlying encoder invalidates the entire index, which demands a complete corpus re-embedding.

The distance metric is defined by the interaction between the encoder and index configurations. For example, inner product search is mathematically identical to cosine similarity when vectors are unit-normalized ($\ell_2 = 1.0$), which shifts the computational cost of vector normalization to indexing time rather than paying for vector division on the query path. Neither metric, however, produces a calibrated probability that a candidate record answers the agent’s question. They represent uncalibrated geometric affinities.

In the software repair task, that geometric affinity bridges the vocabulary gap between the bug report and the return-and-notify code, yielding a candidate for inspection rather than proof of a defect, but the same semantic abstraction blurs fine syntactic distinctions on which execution depends. In `src/pool.py`, the return path invokes `self._available.notify()`, the shutdown routine invokes `self._available.notify_all()`, and acquisition invokes `self._available.wait(timeout)`. All three statements share the same condition variable, module context, and conceptual vocabulary of thread synchronization. Consequently, an encoder often maps all three to neighboring points in vector space when queried about thread unblocking. Their operational semantics are nonetheless entirely distinct: one wakes a single waiter, another wakes every waiter, and the third blocks. An exact lexical search for `notify(` isolates the call site immediately, and BM25 assigns the rare identifier a high inverse document frequency (IDF). The systems challenge is therefore determining which retrieval mechanism surfaces the precise evidence the workload requires.

### Exact and Approximate Vector Search

^sec-vol3-long-term-memory-vector-search

Scoring a query vector against every vector in an unfiltered multi-million-record store streams gigabytes of embeddings from memory on every search. Building an approximate index, by contrast, is unnecessary complexity when a tenant or file filter already narrows the eligible set to a few thousand vectors. An **exact vector scan** scores every vector in the eligible search set under the chosen distance metric. It serves as the baseline ground truth for measuring what an approximate search misses, and it remains a practical serving method whenever the eligible candidate set is small enough to stream within the latency budget.

The resource requirements of an exact scan follow directly from dimensional arithmetic, independent of any specific hardware architecture. Let ${N}$ be the number of eligible vectors, ${d}$ their dimension, and ${s_{\text{elem}}}$ the storage width in bytes per component. Like the ranking symbols before them, these letters are local to vector search. Traversing the stored vectors requires streaming ${N} {d}{s_{\text{elem}}}$ bytes from memory, so on a memory system that sustains bandwidth ${\text{BW}}$ one scan takes at least ${N} {d}{s_{\text{elem}}}/{\text{BW}}$. Counting two floating-point operations per multiply-accumulate operation, dot-product scoring requires approximately $2{N} {d}$ FLOPs. These totals account only for the vector inner products. They exclude the latency of query embedding, top-${k}$ heap maintenance, and fetching the full record payloads from persistent storage.

↪ The roofline model and the ridge point that separates bandwidth-bound from compute-bound work are developed in **[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^sec-vol3-appendix-inference-roofline|Cost Asymmetry Between Input Prefill and Output Generation]]**.

**Napkin Math 6.2: Why an exact vector scan is bandwidth-bound**

**Problem**: Consider a hypothetical searchable set of 10,000,000 vectors, each with 768 components stored in FP16 at 2 bytes per component, held in the main memory of a reference server CPU. Which resource limits one exact dot-product scan, and what floor does it set?

**Math**: Multiply the vector count by the dimension and component width:

$$
{N} {d}{s_{\text{elem}}} = 10^7 \times 768 \times 2\ \text{bytes}.
$$

The raw vectors occupy 15.36 GB. Counting two FLOPs per multiply-add gives $2{N} {d}$, or 15.36 GFLOP per scan. Arithmetic intensity, the FLOPs performed per byte moved from memory, is therefore $2{N} {d}/({N} {d}{s_{\text{elem}}}) = 2/{s_{\text{elem}}}$, which is 1 FLOP/byte at FP16 whatever the corpus size or dimension. The reference host delivers 1 TFLOP/s and 50 GB/s, a ridge point of 20 FLOP/byte, the intensity below which memory bandwidth rather than arithmetic limits the rate. The scan sits far below the ridge, so bandwidth sets its floor. Streaming the vectors takes at least 307.2 ms, while the arithmetic alone would take 15.36 ms. A trajectory that issues 20 such searches spends at least 6.1 s moving vectors. Because the floor is linear in the eligible count, a scope filter that leaves 10,000 vectors has a streaming floor of 0.31 ms. A 10 ms search budget sets an optimistic maximum of ~326,000 vectors on this host before accounting for the rest of the request.

**Systems insight**: The intensity of an exact scan is fixed by the component width, so added arithmetic never speeds it up, and an accelerator’s higher ridge leaves it bandwidth-bound there too. The levers are fewer bytes per vector (compression) and fewer vectors touched (a narrower eligible set or an approximate index). The bandwidth floor screens out exact scans that cannot meet the search budget. When that floor fits, benchmark the complete request, including query encoding, top-${k}$ selection, and record fetches. Choose an exact scan when its measured request latency meets the budget. An approximate index must justify its maintenance cost and recall loss against that baseline.

The memory-bandwidth limit behind output-bound latency (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-memory-bandwidth-decoding|2]]) therefore reappears in retrieval, because an exact scan, like a decode step, performs only a few operations for each byte it streams. The same arithmetic shows where an exact scan remains the right choice. When selective metadata filters restrict the search space to thousands of eligible vectors, an exact scan streams megabytes rather than gigabytes, reducing the streaming floor to sub-millisecond times without the operational overhead of graph maintenance or quantization codebooks.

*The exact-scan streaming floor grows with eligible vectors; the search budget sets an optimistic candidate ceiling.*

When candidate sets grow into millions of vectors and queries must return within tight latency budgets, scanning the entire corpus becomes prohibitive. **Approximate nearest-neighbor (ANN) search**[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn5|⁵]] trades mathematical exactness for orders-of-magnitude reductions in latency and memory traffic, pruning the search space at the cost of occasionally missing true nearest neighbors. Systems cut memory traffic in one of two ways: by traversing a proximity graph to evaluate only a tiny fraction of the vector population, or by partitioning the space and compressing vector representations with quantization codes.

A **hierarchical navigable small-world (HNSW)** index organizes high-dimensional vectors into a multi-layer proximity graph ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-malkov2018efficient|Malkov and Yashunin 2018]]). Layer 0 contains every vector in the dataset. Each inserted vector is also assigned a maximum layer $\ell = \lfloor -\ln {U} \cdot {m_\ell} \rfloor$. Here ${U}$ is drawn uniformly from $(0, 1]$, and ${m_\ell} = 1 / \ln {M}$, where ${M}$ is the maximum number of bidirectional connections per node per layer. The assignment gives each vector probability ${M}^{-{L}}$ of reaching layer ${L}$ or above, so each layer holds roughly $1/{M}$ as many nodes as the one beneath it. This exponentially thinning hierarchy mirrors the express transit lanes of a skip list ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-pugh1990skip|Pugh 1990]]). Traversal begins at an entry point in the sparsest top layer, greedily hopping to whichever neighbor minimizes distance to the query vector ${\mathbf{q}}$. When no neighbor yields further progress, the search drops down to that node’s counterpart in the next layer and resumes the greedy walk. Upon reaching layer 0, the traversal switches from greedy routing to a beam search that maintains a priority queue of the ${ef_{\text{search}}}$ closest candidates discovered so far. The search terminates when the closest unexplored neighbor cannot improve the current candidate set, returning the top ${k}$ vectors. The beam width ${ef_{\text{search}}}$ is the primary query-time recall knob. A vector the beam never visits cannot be returned ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^fig-vol3-hnsw-routing|figure 3]]), so widening the beam evaluates more distances and recovers more true neighbors at the cost of higher query latency.

Constructing an HNSW graph requires executing this layered search for every incoming vector and establishing bidirectional links to its nearest neighbors in each layer. This graph topology incurs substantial memory overhead beyond the raw vectors. Deletions are harder still, because severing a node without reconstructing edge paths among its neighbors risks partitioning the graph and stranding downstream vectors. Production systems therefore mark a deleted node with a tombstone, an exclusion marker that hides it from results while its links stay in place, and [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^sec-vol3-persistent-invalidation|section 6.9]] examines how the cost of that compromise compounds.

![[90 Assets/Volume III/06 Long Term Memory/Hnsw Hierarchical Routing 66c5257b5d.svg]]

Figure 3: **Searching an HNSW Graph**: Each upper layer holds a geometrically smaller subset of the vectors. The query enters at the top, hops greedily toward ${\mathbf{q}}$ until no neighbor is closer, and drops a layer from that node. In layer 0 the walk widens into a beam of width ${ef_{\text{search}}}$ that visits more nodes than it returns and yields the best ${k}$. A vector the beam never visits cannot be returned, which is where approximate search misses come from.

^fig-vol3-hnsw-routing

Rather than navigating a graph over full-precision vectors, an inverted file index combined with **product quantization** (IVF-PQ) reduces memory traffic by partitioning the vector space and lossily compressing the stored representations ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-jegou2011product|Jégou et al. 2011]]). It has an offline build pipeline and an online query pipeline ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^fig-vol3-ivf-pq|figure 4]]). During index construction, coarse ${k}$-means clusters the corpus into ${C}$ Voronoi cells (each cell is the region of vectors nearer its centroid than any other centroid), each backed by an inverted list of vector identifiers. At query time, the system computes the distance from the uncompressed query vector to all ${C}$ coarse centroids and evaluates only the vectors residing in the ${n_{\text{probe}}}$ closest cells.

Product quantization then compresses every stored vector. It splits the ${d}$ dimensions into ${m}$ distinct subvectors of dimension ${d}/{m}$. For each subspace, ${k}$-means trains a codebook of 256 centroids, allowing any subvector to be represented by a single one-byte index ${c^{\text{pq}}}_j \in [0, 255]$ indicating its nearest centroid. Storing a compressed vector therefore requires only ${m}$ bytes. At query time, the uncompressed query vector ${\mathbf{q}}$ is segmented into the same ${m}$ subspaces. Because squared Euclidean distance in ${d}$ dimensions decomposes into the sum of squared distances across the ${m}$ orthogonal subspaces, the runtime precomputes an asymmetric distance lookup table $\text{LUT}[{j}, {c^{\text{pq}}}]$ storing the squared Euclidean distance between the query’s ${j}$-th subvector and each of the 256 centroids ${c^{\text{pq}}}$ in subspace ${j}$. Approximating each stored subvector by its assigned centroid ${c^{\text{pq}}}_j$ reduces the total distance between the query ${\mathbf{q}}$ and a stored quantized vector ${\mathbf{x}}$ with codes ${c^{\text{pq}}}_1, \dots, {c^{\text{pq}}}_{{m}}$ to summing one table lookup per subspace:

$$
{\tilde{d}}({\mathbf{q}}, {\mathbf{x}}) = \sum_{j=1}^{{m}} \text{LUT}[{j}, {c^{\text{pq}}}_j]. \tag{2}
$$

^eq-vol3-pq-adc

[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^eq-vol3-pq-adc|Equation 2]] transforms a bandwidth-bound ${d}$-component dot product into ${m}$ single-byte reads and table lookups. Because the lookup table is small enough to stay in processor cache, each scored vector costs ${m}$ bytes of memory traffic instead of ${d}{s_{\text{elem}}}$, a reduction by the factor ${d}{s_{\text{elem}}}/{m}$ in exactly the term that bounded the exact scan. The parameter ${n_{\text{probe}}}$ balances recall against the number of cells scanned, while the subvector count ${m}$ trades distance fidelity against bytes per code. Systems commonly recover distance accuracy by re-scoring a short candidate list against full-precision vectors stored on secondary media or remote memory. The same design scales to billions of vectors on accelerators ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-johnson2019billion|Johnson et al. 2019]]). The quantization codebooks and coarse centroids, however, are calibrated on the vector distribution present during index construction. As the corpus drifts or the embedding model changes, quantization error grows until the index is retrained.

![[90 Assets/Volume III/06 Long Term Memory/Episodic Ivf Pq c63cf191d5.svg]]

Figure 4: **IVF-PQ Build and Query**: At build time each stored vector is split into ${m} = 64$ subvectors, each replaced by the one-byte index of its nearest centroid in that subspace’s codebook, and the code is appended to the inverted list of its nearest coarse cell. At query time the full-precision query selects the ${n_{\text{probe}}}$ nearest cells, fills a table of distances to every subspace centroid, and scores each stored code with ${m}$ table lookups. Sizes follow the exact-scan notebook’s corpus.

^fig-vol3-ivf-pq

Sizing both designs for the 10-million-vector corpus of the exact-scan notebook shows what each one costs in memory. With 32 eight-byte links per node, an HNSW graph adds 2.56 GB of edge topology to 15.36 GB of vectors. Because greedy routing traverses arbitrary graph links, memory access patterns are dominated by dependent random reads, requiring both the graph and the vectors to remain memory-resident. Product quantization with 64 subvectors of 12 dimensions stores 0.64 GB of codes, 24× smaller than the FP16 vectors, and its per-query lookup table occupies only 65.5 KB. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^tbl-vol3-ann-tradeoffs|Table 5]] sets the three designs side by side.

| **Property**                  | **Exact scan**                        | **IVF-PQ**                                                     | **HNSW**                                                                 |
|:------------------------------|:--------------------------------------|:---------------------------------------------------------------|:-------------------------------------------------------------------------|
| **Work per query**            | Every eligible vector                 | ${C}$ centroids plus the codes in ${n_{\text{probe}}}$ cells   | Distances along a greedy path and a beam of width ${ef_{\text{search}}}$ |
| **Resident bytes (notebook)** | 15.36 GB                              | 0.64 GB of codes, plus centroids and codebooks                 | 17.92 GB of vectors and links                                            |
| **Distance fidelity**         | Exact under the metric                | Approximate; re-scoring a short list recovers it               | Exact for each visited vector; misses come from unvisited ones           |
| **Recall knob**               | None needed                           | ${n_{\text{probe}}}$, ${m}$                                    | ${ef_{\text{search}}}$, ${M}$                                            |
| **Insert and delete**         | Append; delete by exclusion           | Cheap append; centroids and codebooks age as the corpus drifts | Insert runs a search and relinks neighbors; delete leaves a marked node  |
| **Memory access**             | Sequential streaming, bandwidth-bound | Short sequential scans of small codes                          | Dependent random reads, one per hop                                      |

Table 5: **Exact and approximate vector search**: Each design trades the bytes a query touches against recall and update cost. Footprints use the exact-scan notebook’s hypothetical corpus and the stipulated index shapes above; measured latency and recall depend on the data, queries, and settings.

^tbl-vol3-ann-tradeoffs

Selecting among these index structures requires evaluating them against the specific record volumes, query distributions, and latency budgets the agent encounters. Two evaluation metrics answer different questions here. Recall against an exact scan measures algorithmic fidelity to the mathematical distance metric, whereas end-to-end task success measures whether the retrieved records contain the requisite causal evidence to resolve the agent’s objective.

The filtering hazard from lexical search ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.06 Lexical and Structural Retrieval#^sec-vol3-long-term-memory-search-scope|section 6.5.3]]) returns here in sharper form, because scope filters present greater friction on a graph index than on inverted postings lists. In lexical retrieval, intersecting a postings list with an eligibility bitset prunes unauthorized documents without altering how the remaining documents are traversed. In an HNSW graph, restricting search during traversal (pre-filtering) forces the beam to step exclusively onto eligible nodes. If a tenant boundary or file path mask isolates regions of the graph, the greedy walk stalls at a local minimum when all outgoing links lead to masked nodes. The search terminates prematurely and returns incomplete results, even when highly relevant eligible nodes exist just beyond the masked barrier. Conversely, filtering after an unconstrained search (post-filtering) risks returning an empty set whenever the top-${k}$ candidates fall outside the authorized scope. Systems escape the dilemma in one of three ways ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^fig-vol3-access-prefilter|figure 5]]). They partition the index into scope-isolated subgraphs, seed extra entry points inside the authorized region, or fall back to an exact scan when the filter is selective enough that the measured full request meets the budget. The floor in notebook [6.2](https://mlsysbook.ai/vol3/06_long_term_memory/06_long_term_memory.html#nbk-06-memory-bandwidth-and-latency-floor) serves as an initial feasibility screen for that fallback.

![[90 Assets/Volume III/06 Long Term Memory/Retrieval Access Control Prefilter 63539d52b3.svg]]

Figure 5: **Filtering Inside a Graph Walk**: A scope mask applied during traversal (A) removes the only links between the entry region and the eligible vectors nearest ${\mathbf{q}}$, so the greedy walk stops at a local minimum and returns too few results even though eligible neighbors exist. The three responses (B) partition the index along scope boundaries, restart the walk from an entry point inside the eligible region, or, when the filter is selective, score every eligible vector exactly.

### Rank Fusion and Reranking

^sec-vol3-long-term-memory-rank-fusion

Running both lexical search and dense retrieval covers each method’s blind spots, but combining their outputs naively fails in two ways. Adding unbounded BM25 scores directly to cosine similarities in $[-1, 1]$ skews the combined order toward whichever scale is larger. Deduplicating hits by file path alone merges a stale `r17` span with its patched `r18` counterpart or treats identical code in another tenant as authorized local evidence. Production systems that combine multiple candidate-generation mechanisms through **hybrid retrieval** must therefore resolve candidate identity by tenant scope, source path, commit or version identifier, and span coordinates before merging lists.

Because lexical scores and dense similarity scores reside on non-comparable scales, directly normalizing or adding raw scores introduces calibration instability. **Reciprocal rank fusion (RRF)** bypasses score calibration by combining ranked lists based solely on candidate ordinal positions ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-cormack2009reciprocal|Cormack et al. 2009]]). Let ${\mathcal{L}}_i$ denote the list returned by method ${i}$, and let ${r}_i({x_{\text{cand}}})$ represent the 1-based rank of candidate ${x_{\text{cand}}}$ within that list. For a positive smoothing parameter ${k_{\text{rrf}}}$, the truncated RRF score is defined as:

$$
\operatorname{RRF}({x_{\text{cand}}}) = \sum_{i:\,{x_{\text{cand}}}\in {\mathcal{L}}_i} \frac{1}{{k_{\text{rrf}}} + {r}_i({x_{\text{cand}}})}. \tag{3}
$$

^eq-vol3-reciprocal-rank-fusion

A candidate absent from a given list contributes zero from that source. Increasing ${k_{\text{rrf}}}$ compresses the score differential between adjacent ranks without making the method entirely parameter-free.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.17 Footnotes#^fn6|⁶]] The runtime must also define an explicit tie-breaking convention and configure candidate cutoff depths for each retrieval path.

To see how RRF rewards consensus across divergent retrieval mechanisms, consider an illustrative repair query evaluated on the authorized `r18` snapshot. Let A be the return-and-notify implementation span, B the reproducer test, and C, D, and E three additional candidate records. Suppose lexical search produces the ranking B, A, D, while dense retrieval produces C, A, E. With the standard choice ${k_{\text{rrf}}} =$ 60, [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^eq-vol3-reciprocal-rank-fusion|equation 3]] assigns candidate A two second-place contributions, $1/(60+2) + 1/(60+2)$, whereas candidate B receives only a single first-place contribution of $1/(60+1)$. Summing every candidate’s contributions in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^tbl-vol3-rrf-scoring|table 6]] puts candidate A at the top fused rank on consensus across both retrieval paths, even though neither individual retriever ranked it first.

| Candidate | Lexical rank | Dense rank | RRF score | Fused position |
|:----------|-------------:|-----------:|----------:|---------------:|
| A         |            2 |          2 |   0.03226 |              1 |
| B         |            1 |          — |   0.01639 |              2 |
| C         |            — |          1 |   0.01639 |              3 |
| D         |            3 |          — |   0.01587 |              4 |
| E         |            — |          3 |   0.01587 |              5 |

Table 6: **Fusion of hypothetical candidate rankings**: A benefits from appearing in both lists. A dash means absence from that truncated list and contributes zero. Equal scores are ordered by candidate ID, not by inferred relevance.

^tbl-vol3-rrf-scoring

Dual consensus elevates candidate A for closer inspection, but agreement across two candidate generators remains an incomplete guarantee of relevance when both retrievers share systematic blind spots. To establish higher precision before staging evidence into the agent’s context window, systems employ a **cross-encoder reranker** ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.16 Source References#^ref-nogueira2019passage|Nogueira and Cho 2019]]). Rather than scoring query and document independently, a cross-encoder runs the query and the candidate through the model together as one input, so every query token can attend to every candidate token. Because each score depends on a specific query and candidate pair, nothing can be computed before the query arrives, and this joint pass captures fine-grained token interactions at substantial query-time cost. A reranker can only reorder candidates already surfaced by upstream generators. It cannot retrieve missing records, and its score reflects structural and semantic resemblance rather than verified task applicability.

The substantial computational demand of this joint pass is why rerankers operate exclusively on short candidate pools. In a bi-encoder design, candidate vectors are computed offline, reducing query-time evaluation to a lightweight vector dot product. In a cross-encoder, query and candidate tokens must be processed jointly through the transformer layers, preventing offline precomputation. Computational cost scales with both candidate pool depth and token sequence length. For example, reranking a pool of 50 candidates of 300 tokens each against a 100-token query requires processing 20,000 tokens, a prefill load comparable to a substantial model call, spent entirely on ordering. Systems manage this latency budget by constraining candidate pool sizes, invoking rerankers conditionally based on query ambiguity, or executing reranking asynchronously off the interactive path. The complete hybrid pipeline therefore narrows as it proceeds ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^fig-vol3-hnsw-rrf|figure 6]]). Two candidate generators feed a fusion step that needs only ranks, the costly reranker sees only the short fused pool, and the runtime stages a small labeled set within the payload budget.

![[90 Assets/Volume III/06 Long Term Memory/Vol3 Ch06 Hnsw Rrf c2a545501c.svg]]

Figure 6: **From Candidate Lists to Staged Evidence**: Lexical and dense retrieval each rank candidates for the repair symptom. Candidates are joined on their full identity, so an r17 span never merges with its r18 counterpart, and reciprocal rank fusion combines ranks rather than raw scores, with the smoothing parameter ${k_{\text{rrf}}}$ still a design choice. A cross-encoder reorders only a short pool, because its work grows with both pool size and pair length, and the runtime stages a small labeled set within the payload budget.

^fig-vol3-hnsw-rrf

Once reranked, top-ranked candidates pass into the staging pipeline ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.04 The Retrieval Contract#^sec-vol3-persistent-quarantine|section 6.3.3]]), where their provenance and authority are verified before injection into the agent’s context payload. Even an optimally ranked evidence set, however, provides bounded guarantees. Retrieving the `r18` implementation and a passing reproducer confirms local syntax and isolated test execution, but it cannot prove that all concurrent caller paths remain race-free. Validating broader system properties requires corroborating records, such as runtime execution traces and multi-threaded test outcomes, that no single ranked list assembles on its own.
