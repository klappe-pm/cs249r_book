# V3-06.02 Memory Beyond One Session

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory|V3-06 Long-Term Memory]]

^sec-vol3-long-term-memory-introduction

Consider the repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) working on its connection-pool defect across several sessions. When the initial session terminates, the subsequent run must reconstruct the operational state: the candidate source tree at revision `r18`, the diagnostic failure observed at `r17`, the passing run of `test_waiter_notified_on_return`, the integration checks that remain unresolved, and an operational note indicating where to resume execution. None of this state survives inside a transient context window once the process exits. Persisting only the final summary message discards critical supporting evidence. Conversely, retaining raw message transcripts without explicit scope creates confusion. An agent reading an unannotated log can easily mistake an earlier failure under `r17` for an error in the new candidate patch.

*H·S·A locator with the State axis highlighted.*

*Durable State, closed by checking each retrieved record against its source.*

Standard runtime mechanisms do not bridge this gap. Context engineering selects among information already staged for a single model call, while the inference serving system maintains key-value (KV) attention cache state purely to accelerate that computation. Although a prefix cache can outlive an individual request, it remains a derived acceleration structure for a compatible prompt prefix (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-prefix-coherence|5]]), regardless of the storage medium holding it. Long-term memory addresses a different systems problem, preserving information that must govern decisions across distinct invocations. A durable memory system must explicitly resolve what records to retain, how to index and retrieve them efficiently, and how to update or invalidate them when external sources change. In the formal framing of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-hsa|The H·S·A Exposure Space]]**, these records constitute durable State (${S}_3$), persisting across session boundaries.

Architecting persistent memory for an agent requires solving three interconnected systems problems. First, the data model must establish explicit record roles that keep external sources, tool observations, and agent-authored notes strictly differentiated, ensuring that subsequent sessions recognize what evidence each record supports. Second, the system requires a retrieval contract. Regardless of the candidate generation mechanism, every read must report its query scope, the snapshot versions it admitted, and whether the search terminated cleanly or degraded under resource budgets. Third, the storage engine needs a write lifecycle that admits, updates, supersedes, expires, and deletes records while propagating those mutations to downstream indexes and summaries.

The chapter takes these problems in the order a read depends on them. Record roles come first ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.03 Persistent Records#^sec-vol3-persistent-need|section 6.2]]), because every later indexing, retrieval, and invalidation policy depends on knowing what authority a stored record carries. The retrieval contract ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.04 The Retrieval Contract#^sec-vol3-persistent-governance|section 6.3]]) then fixes what any read must specify and report, whatever index sits behind it, and the choice between pre-staged and model-directed retrieval ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.05 Agentic Retrieval#^sec-vol3-long-term-memory-agentic-retrieval|section 6.4]]) decides which component formulates the query. Three method sections match index structures to information needs, moving from names and syntax ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.06 Lexical and Structural Retrieval#^sec-vol3-persistent-bm25|section 6.5]]) through learned representations and fused rankings ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.07 Dense and Hybrid Retrieval#^sec-vol3-persistent-dense-retrieval|section 6.6]]) to chains of related evidence ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.08 Multi-Hop Retrieval#^sec-vol3-persistent-graphrag|section 6.7]]). The write path ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^sec-vol3-long-term-memory-write-path|section 6.8]]) and storage invalidation ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.10 Storage Invalidation#^sec-vol3-persistent-invalidation|section 6.9]]) keep the store and its derived indexes truthful as sources change, and the final section ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.11 Evaluating Memory Policies#^sec-vol3-persistent-governance-eval|section 6.10]]) judges a complete memory policy by the tasks it helps finish across sessions.
