# V3-04.09 Evaluating Context Policies

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-evaluation

At the end of the repair’s timeline, the reproducer has passed on `r18`, the history has been compacted, and the next request must carry the task constraints, the `r17` failure of `test_waiter_notified_on_return`, and the `r18` pass, each with its scope. At this point, the context policy succeeds only if the next prompt gives the model enough evidence to distinguish the active candidate patch from the earlier failure while showing which verification checks remain open. Token reduction alone is never evidence of success. When compaction erases version boundaries, an agent can mistake an obsolete diagnostic failure for current reality, or mistake a partial reproducer pass for complete task success, which example [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^exmp-04-context-evidence-probe|4.1]] dissects.

**Example 4.1: A passing test without its version**

**Scenario**: The repair stands where this chapter left it. `test_waiter_notified_on_return` failed at `r17` and passes at `r18` under the recorded configuration, and broader behavior is unverified. Before the next call, a naive compaction policy replaces these entries with one summary: “The waiter test passed; the repair is complete.” The API constraint and the deployment prohibition survive verbatim.

**Diagnosis**: A schema validator checking for a string-valued `test_status` accepts the summary without error, and a rule-based constraint check confirms that both negative constraints remain present. Neither check, however, detects that a single-case observation was turned into a claim of complete task success. An evidence probe closes this gap by freezing the history and inspecting both the assembled prompt and the model’s next decision, checking candidate and test identities, reproducer scope, and open acceptance checks. In a controlled variant, the evaluator edits a relevant test or source file after the passing run. A sound policy leads the agent to see that the earlier pass no longer covers the modified code, and to run fresh checks before declaring the repair done. An edit to an unrelated file serves as a negative control to confirm that the policy does not invalidate context indiscriminately.

**Systems lesson**: A context policy must preserve causal relationships and version bindings, not merely isolated field names. A test result has meaning only relative to the exact artifact and execution conditions under which it was produced, and subsequent decisions must respect those boundaries. Targeted evidence probes pinpoint semantic information loss, while repeated dynamic trials verify whether the agent acts on those preserved distinctions during execution.

^exmp-04-context-evidence-probe

Every mechanism in this chapter meets at failures of this kind: selection decides what enters the prompt, staging sets representation and zone order, compaction and progress records govern what survives across trunk rewrites, and invalidation decides when stale support must be refreshed. Judging a policy by summary length alone misses the failures that happen at those joins, so evaluation must test the complete context policy (external reads, schema checks, and fallback paths included) under the target workload’s rules and budgets.

### Comparing Complete Policies

^sec-vol3-context-engineering-policy-comparison

Testing the complete policy means accounting for every read, summary call, and retry it triggers outside the main prompt, because comparing main prompt lengths alone can credit a “compact” policy that quietly shifts token spend into extra tool reads or helper calls. A fair comparison starts every repair trial from the same source snapshot, task contract, and initial observations, and charges every auxiliary read or model call to the policy that issued it. The harness holds the model, sampling settings, tool definitions, and acceptance suite fixed while varying only the context policy under shared ceilings such as the 128,000-token window and 30-turn step budget.

A complete policy specification must also state the operating rules that would otherwise hide costs or failure paths. A sliding-window policy must state how it pins system instructions and task constraints. A summarizing policy must state its trigger and target watermarks, protected-field inventory, and fallback path when a summary fails the audit. Any policy that moves raw payloads behind handles must state what happens when a handle read fails. Labels like “sliding window,” “summarizer,” or “structured record” leave out these rules, even though fallback behavior often decides whether an agent recovers or fails when context is missing.

Repeated runs across task cohorts remain necessary even under greedy decoding with fixed seeds, because distributed serving engines, kernel nondeterminism, and asynchronous tool scheduling all introduce run-to-run variation. Evaluation logs must record model versions, serving-engine builds, sampling settings, sandbox images, and KV-cache policies so that infrastructure changes are not mistaken for context-policy gains. A single passing run shows only that a trajectory can succeed once, not how reliably the policy performs.

↩︎ Why greedy decoding with a fixed seed still varies across served calls, and the difference between replaying a trajectory and re-querying the model, are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.05 Autoregressive Generation#^sec-vol3-foundation-model-repetition-replay|Repetition and replay]]**.

↪ How many tasks and repeated runs an estimate needs, and the confidence intervals on acceptance rates, are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-rigor|Statistical Evaluation Rigor]]**.

### Measuring Retention, Behavior, and Cost

^sec-vol3-context-engineering-retention-behavior-cost

A failed trial may come from a compaction pass that dropped a required constraint, or from a model that ignored a constraint still in the prompt. To tell them apart, the evaluation harness defines a required-information inventory against the task fixture before inspecting any runs. For the connection-pool repair, that inventory lists the public API rules, the approved workspace path, the no-deploy rule, the source and test revisions, and the scope of each test run.

**Required-field retention** is the fraction of required items whose value, scope, and provenance match the ground-truth fixture; merely keeping a field named `test_status` does not count. Exact identifiers and compiler messages can be checked by string equality, whereas paraphrased claims need semantic checks that account for grading uncertainty. Recording omitted, altered, and unsupported fields separately tells engineers whether the failure came from aggressive pruning or from hallucinated rewriting.

Retention across repeated compaction passes is much stricter than retention across a single pass, because an item can drop out during an intermediate rewrite and only reappear later through an expensive re-read. The benchmark must therefore state whether it checks retention at every compaction boundary, uninterrupted survival across the whole run, or presence just before a decision step. In [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-constraint-retention|equation 6]], ${\mathcal{C}}$ is the set of critical constraints from the task contract (the negative scope of the goal and the limits on permitted actions) rather than the five-part contract tuple itself. The quantity $|{\mathcal{C}}|$ is their count, and ${k}$ counts compaction boundaries rather than turns or retries. Multiplying the binary indicator across all ${k}$ boundaries means that a single drop at any intermediate boundary sets that constraint’s product to zero for the rest of the run, even if a later read restores the text. For uninterrupted retention across ${k}$ compaction boundaries, the retention fraction is

$$
{\eta_{\mathcal{C}}}({k}) = \frac{1}{|{\mathcal{C}}|} \sum_{{c} \in {\mathcal{C}}} \prod_{i=1}^{{k}} {\mathbb{I}}\left[{c} \text{ correctly retained at boundary } {i}\right]. \tag{6}
$$

^eq-vol3-constraint-retention

![[90 Assets/Volume III/04 Context Engineering/Ch04 Constraint Survival b2f9a55638.svg]]

*A red curve of single-constraint survival probability falls from 100 percent at zero rounds toward zero. A green dot at 10 rounds is labeled 59.9 percent and a red dot at 40 rounds is labeled 12.9 percent.*

*A small per-round loss compounds geometrically over repeated compactions.*

The product in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-constraint-retention|equation 6]] shows why summarizing an earlier summary is so hazardous. When a required constraint survives each compaction round independently with probability $1-{\rho}$, its survival probability across ${k}$ rounds compounds to $(1-{\rho})^{k}$, following the same compounding law as **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]** with compaction passes in place of decision steps. Under a seemingly small per-round loss rate of 5 percent, a constraint survives 10 compaction rounds with probability 59.9 percent, but survives 40 rounds with probability only 12.9 percent. That rapid decay is why production runtimes check protected fields in host code at every compaction boundary rather than trusting an unconstrained model summary. Extending the calculation to the full working set requires joint survival estimates because real compaction losses often correlate across fields within the same pass.

Behavioral metrics likewise need explicit denominators. A constraint-violation rate counts violating actions against the decision points where that constraint applied, logging blocked proposals separately from executed violations so generation errors are not confused with missing host gates. In the same way, the **stale-support rate**

$$
{\epsilon_{\text{stale}}} = \frac{\text{decisions that treat superseded support as current}}{\text{decisions that require current evidence}} \tag{7}
$$

^eq-vol3-stale-support

restricts its denominator to decisions where evidence freshness affects validity. Under the scope rule, citing the `r17` failure as history after moving to `r18` is valid, whereas citing it as proof of how `r18` behaves is a stale-support error.

End-to-end task acceptance estimates the acceptance probability ${p_{\text{acc}}}$ in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**:

$$
{\hat{p}} = \frac{{N_{\text{acc}}}}{{N}}, \tag{8}
$$

^eq-vol3-task-acceptance

where ${N_{\text{acc}}}$ counts the trials that pass the full verification standard within their resource budgets and ${N}$ counts all assigned trials. Passing the single-case reproducer is only an intermediate milestone, and timed-out runs, tool crashes, or context overflows must stay in the denominator ${N}$ rather than being dropped. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^tbl-vol3-context-evaluation|Table 10]] brings these representation, behavioral, and outcome metrics together under one measurement contract.

↪ The task acceptance contract that decides which trials count as accepted is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^sec-vol3-evaluation-contract|The Task Acceptance Contract]]**.

| Measurement              | What the evaluator records                                                                     | What the result cannot establish                           |
|:-------------------------|:-----------------------------------------------------------------------------------------------|:-----------------------------------------------------------|
| Required-field retention | Correct values and evidence scope at each specified compaction boundary                        | That the inventory includes every fact needed later        |
| Constraint compliance    | Violating proposals among applicable proposals, separately from executed violations            | That prompt text enforces an action boundary               |
| Current-evidence use     | Decisions using superseded support as current, among eligible decisions                        | That every old observation is irrelevant                   |
| Task acceptance          | Trials meeting the common evidence standard, including every assigned trial in the denominator | Correctness beyond that standard’s coverage                |
| Request footprint        | Fully serialized input length, output reservation, and rejected oversized requests             | Lower total task cost or adequate information              |
| Resource use             | All calls, source reads, compaction, checks, and elapsed time charged to the cohort            | A benefit unless accepted outcomes justify the expenditure |

Table 10: **Context-policy measurement contract**: Representation checks, behavioral observations, and task outcomes answer different questions. Their denominators and coverage must remain explicit when comparing policies.

^tbl-vol3-context-evaluation

Compression measures representation size rather than decision quality. To compute compression at a decision step, serialize both an uncompacted reference prompt containing the full raw history and the candidate prompt produced by the context policy with the same tokenizer, including system instructions, tool declarations, schemas, and framing delimiters in both. The **request compression ratio** is

$$
{\gamma_{\text{req}}} = \frac{{S_{\text{ref}}}}{{S_{\pi}}}, \tag{9}
$$

^eq-vol3-request-compression

where ${S_{\text{ref}}}$ and ${S_{\pi}}$ are the token counts of the uncompacted reference request and the policy-generated request. Because ${S_{\text{ref}}}$ is an analytical baseline, it can exceed the serving engine’s context window without needing to be run. Values of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-request-compression|equation 9]] above $1.0$ indicate token savings, provided both numerator and denominator count complete serialized requests rather than comparing raw observations against a framed prompt.

Compression ratios also depend on how a run unfolds. On fixed-trace probes where every policy processes the same recorded transcript, request lengths compare directly. In live closed-loop trials, however, a high compression ratio can mean only that a weak policy wandered through extra exploratory turns that then had to be compacted. Reports should therefore pair compression ratios with total token counts and full system spend (including summarization calls, search queries, and handle reads) so a policy cannot look cheap merely by moving tokens out of the main prompt into helper calls.

Checking that an agent actually uses what the prompt retains requires causal interventions rather than static inspection, because token presence, attention weights, or copied identifiers show only correlation. By removing or altering a key variable in a controlled fixture (such as the branch tag or test status) while holding the rest of the prompt fixed, an evaluator can see whether the model’s next tool call changes accordingly. If the call stays the same, the model is ignoring that field under the current layout. Those static interventions still need to be paired with live task runs, where an agent can recover from an omitted prompt field by reading the workspace through a tool call. Counterfactual probes test omitted payloads in the same way. If a compaction policy replaces raw test logs with an external handle, temporarily disabling the handle store shows whether the agent falls back cleanly or guesses when retrieval fails. Field-presence checks never see this failure mode.

Choosing a production context policy means weighing all of these measurements together across task acceptance, failure modes, latency, and total dollar cost under shared limits. A structured-record policy that keeps every schema field yet still leads the model to declare victory on an incomplete check fails its purpose. The right production policy is the one that minimizes the effective cost per accepted task, ${C_{\text{eff}}}$, across the evaluation cohort: shrinking the prompt lowers per-call spend, but if aggressive pruning lowers ${p_{\text{acc}}}$, the cost per accepted task rises sharply.

**Checkpoint 4.3: Testing what survives compaction**

A candidate policy preserves the manifest’s field names but drops specific values and version relationships. Its resulting request is measurably shorter than the uncompacted reference prompt.

**Retention**: How does an automated validation check distinguish mere field key presence from the semantic retention of the `r18` reproducer test outcome?

**Evidence scope**: How does an intervention probe distinguish a valid historical reference to the `r17` failure from an unsupported assertion about the `r18` workspace?

**Cost boundary**: If the runtime fetches an evicted diagnostic log on every subsequent turn via tool calls, which metrics reveal whether compaction achieved a net resource reduction?

**Retention estimate**: Using the hypothetical per-round loss rate from [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-constraint-retention|equation 6]], after how many compaction rounds does a single constraint’s survival probability fall below even odds (50 percent), and what does this imply for where protected-field validation must execute?

**Controlled comparison**: Why can a fixed-trace probe isolate representation defects without predicting dynamic end-to-end task completion rates?

Every evaluation result is only as strong as its test fixtures, evidence rules, and cost accounting. The most common evaluation mistakes come from treating a single intermediate metric as proof of overall quality, such as mistaking a shorter prompt for better context or mistaking safety instructions in the prompt for an enforced execution gate.
