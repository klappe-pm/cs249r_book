# V3-04.07 Structured Progress Records

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-summarization

By the time the candidate patch is tested, the repair has moved through three linked events: at `r17`, the controlled test failed; the agent’s patch then wrote `r18`; and the reproducer passed on `r18`. All three events must survive the next compaction with their relationships intact. A naive summary that says only “fixed the notification bug” drops the distinctions the agent needs to choose its next step. The `r17` test saw a returned connection leave a waiting thread blocked. The `r18` run showed only that the waiter wakes under that single test schedule, which proves nothing yet about the broader regression suite or public API compatibility. Once raw diagnostic turns are evicted from the window, the next call still needs to tell verified observations apart from working hypotheses and an incomplete repair.

A **structured progress record** carries this state across compactions in named fields, holding active task constraints, verified observations, working hypotheses, artifact versions, and open obligations instead of replaying raw dialogue. A fixed schema lets host code flag missing fields and internal contradictions automatically, though checking whether the recorded claims match what actually happened still requires an audit against host logs. This record is a continuation manifest for the next prompt rather than an execution checkpoint: snapshotting processes, tracking dirty files on disk, and recovering in-flight tool calls belong to execution persistence.

↪ Execution checkpoints, which bind workspace snapshots and in-flight operations to a committed log position, are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.05 Checkpoints#^sec-vol3-persistence-checkpointing|Checkpoints]]**.

### Recording Facts and Open Questions

^sec-vol3-context-engineering-facts-open-questions

Keeping a continuation record trustworthy starts with separating facts the host runtime can verify from hypotheses proposed by the model, so a compaction pass cannot turn an instruction like “test this repair” into a claim that “this repair passed.” Active task constraints come from the task contract rather than from a model’s summary. Artifact versions and tool outcomes come from host execution logs rather than free-form prose. A diagnosis stays marked as a hypothesis even when it explains the symptoms seen so far. In the connection-pool repair, the agent cannot loosen public API rules, widen its allowed workspace, or lift deployment blocks merely by rewriting its progress record. When an operator updates the task contract, the runtime writes the new terms directly into the prompt rather than keeping old instructions to save a prefix hit. Each progress record names the contract version it was built against, so the runtime can check its fields against current rules ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.07 Structured Progress Records#^tbl-vol3-checkpoint-schema|table 7]]).

↩︎ The five-part task specification contract, the source of a task’s binding constraints, is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-five-part-contract|The five-part task contract]]**.

| Record field           | Repair information to retain                                                                                                   | Basis for checking it                                                              |
|:-----------------------|:-------------------------------------------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------|
| Task and constraints   | Repair waiter notification; preserve the public API; approved workspace only; no production deployment                         | Current task contract and explicit authorized updates                              |
| Artifact identities    | `src/pool.py` at `r18`, candidate patch identity, and the version of `tests/test_pool.py` and configuration used by each check | Recorded reads, applied diff, and check inputs                                     |
| Supported observations | Waiter remained blocked at `r17`; `test_waiter_notified_on_return` passed on `r18` under the recorded conditions               | Corresponding tool results, not the model’s account of them                        |
| Hypotheses             | Timeout explanation lacks support from the controlled trace; missed notification is the working explanation                    | Relevant observations and a retained distinction between diagnosis and observation |
| Unresolved obligations | Broader behavior and public API compatibility are not yet established by the reproducer                                        | Required acceptance evidence compared with checks already performed                |
| Next bounded step      | Inspect the patch and relevant tests to choose the next permitted regression check                                             | Remaining task needs, permissions, and resource allowance                          |
| Raw-payload handles    | References to the original trace, patch, and test output when later inspection may require more detail                         | Retained payload identity, access permissions, and retrieval availability          |

Table 7: **A progress record for continuation**: Named fields preserve the difference between historical evidence, the current candidate, and work still needed. Field presence alone does not establish semantic fidelity.

^tbl-vol3-checkpoint-schema

Every observation entry in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.07 Structured Progress Records#^tbl-vol3-checkpoint-schema|table 7]] follows the scope rule, so the `r17` failure and the `r18` pass each speak only for their own revision. Milestones record the exact check run and its result (“reproducer passed on `r18`”) rather than a blanket claim (“the race condition is gone”). The handle row applies the handle rule, so the agent can pull back an exact assertion diff or full trace on demand without keeping raw logs in every prompt.

### Auditing Before Replacing Active History

^sec-vol3-context-engineering-record-audit

Because a model-written progress record is an untrusted candidate to replace active history, it can satisfy every schema type check (supplying a valid status string, artifact tag, and event ID) while still reporting a test run that never happened. Before swapping the record into the prompt, the runtime must therefore check both its structure and its factual claims against host logs, applying the same split between schema validity and factual correctness that governs tool calls.

↩︎ The gap between a schema-valid payload and a correct one is established for tool calls in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.08 Grammar-Guided Decoding#^sec-vol3-foundation-model-structural-guarantee-scope|What a grammar mask guarantees]]**.

To avoid circular validation, the audit checks candidate records against a required-field inventory owned by the host runtime. If the runtime trusted a checklist generated by the summarizer itself, a hallucinating model could drop the no-deploy rule from both the summary and the checklist while passing self-consistency checks. Instead, the runtime reads active constraints straight from the task contract and checks artifact hashes and test outcomes against its own execution log. While that check guarantees that known contract terms and logged events are accurately reported, deciding which code excerpts the next step will need remains a selection decision that no schema check can settle automatically.

For every claimed milestone, the runtime looks up the referenced event in the execution log and compares the recorded command, exit code, artifact version, and test scope. An unlogged tool result stays marked unknown, a failed check stays failed regardless of how the summary phrases it, and a nonzero exit code records failure without proving why it failed. Open questions stay marked as hypotheses until a logged check settles them. If a candidate record claims that the full regression suite passed on `r18` when the event log shows only `test_waiter_notified_on_return`, the audit catches the mismatch and rejects the replacement. Broader questions (whether that one test covers enough behavior, whether edge cases remain in other modules, or whether the next action is permitted) belong to test execution and policy gates rather than the summary audit.

Version checks are how the audit enforces the scope rule: a historical milestone may cite `r17`, whereas any claim about the current pool must point to evidence recorded at `r18`. Separating a missing log entry, a valid historical observation, and an unsupported claim about current code lets the runtime keep useful `r17` history without mistaking it for proof that `r18` works. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.07 Structured Progress Records#^lst-vol3-progress-audit|Listing 2]] puts these three checks into one host-side function, where every compared value comes from state the summarizer did not write: the runtime’s required-field inventory, the logged tool events, and the current workspace versions.

``` python
def audit_record(record, inventory, events, workspace):
    findings = []

    # 1. Required fields: contract constraints plus promoted discoveries,
    #    such as the controlled waiter-before-return schedule.
    for field in inventory.required_fields():
        if record.value_of(field.name) != field.value:
            findings.append(("missing_or_altered", field.name))

    # 2. Historical and current claims must match recorded evidence.
    for claim in (*record.milestones, *record.current_state_claims):
        event = events.get(claim.event_id)
        if event is None:
            findings.append(("no_evidence", claim))
        elif (claim.operation, claim.result, claim.artifact,
              claim.artifact_version, claim.scope) != \
             (event.operation, event.result, event.artifact,
              event.artifact_version, event.scope):
            findings.append(("contradicts_event", claim))

    # 3. Scope: history may name r17; a current-state claim needs support
    #    recorded at the version the workspace holds now.
    for claim in record.current_state_claims:
        if claim.artifact_version != workspace.version_of(claim.artifact):
            findings.append(("needs_current_evidence", claim))

    return findings
```

Listing 2: **Auditing a candidate progress record**: Every comparison uses evidence the summarizer did not produce. An empty result permits replacement; any finding rejects the candidate.

^lst-vol3-progress-audit

On our candidate record, Check 2 rejects the claim that the full regression suite passed on `r18` because the event log records only the single reproducer test. Check 1 catches any dropped no-deployment rule or test-schedule flag, and Check 3 keeps the `r17` failure as history while blocking any claim that it describes the `r18` workspace. Because the audit can reject a candidate, the runtime keeps raw tool logs and source diffs in storage until the candidate record is accepted or rejected; evicting turns from the prompt never means deleting raw payloads from backing storage. When the audit finds a mismatch, the runtime can either feed the specific findings back to the model for a bounded correction pass or build a minimal record directly from its own event log. Because correction calls spend both tokens and wall-clock time, the runtime caps repair attempts, handle reads, and elapsed time rather than looping until a candidate happens to pass. If the cap is reached without a verified record, the runtime keeps a larger slice of raw history (if space permits), pulls needed files on demand, or stops with an explicit handoff error. Running out of retries never makes an unverified summary safe to admit.

### Continuing from the Record

^sec-vol3-context-engineering-record-continuation

Once the `r18` progress record passes the audit, it anchors the next call without dragging along pages of refuted timeout speculation. The runtime assembles the request from the active contract, the verified record, and the fresh observations or code excerpts needed for the next step. It places them in root, trunk, and leaf order, so the audited record sits in the reusable trunk until a constraint change or new trunk refresh replaces it. The assembled request, including framing and any payloads pulled back through handles, must still fit inside ${S_{\max}} - {K_{\max}}$.

In the connection-pool repair, the next call sees the `r18` patch alongside the passing reproducer and the still-open API compatibility checks. Whenever a later step needs details that compaction omitted, the runtime reads the original artifacts through their handles or reports the missing evidence explicitly. Compaction acts like a reversible cache rather than a one-way loss only when two conditions hold: the raw payloads remain in storage, and each new compaction pass is built from those raw records rather than by summarizing the previous summary. Summarizing an earlier summary carries forward every earlier omission, compounding small per-round losses across the run ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^sec-vol3-context-engineering-retention-behavior-cost|section 4.8.2]]).

Writing a structured record to disk lets summary state survive a process restart, yet a saved context record alone does not make an interrupted run resumable. Restoring workspace files, syncing git worktrees, and reconciling in-flight tool calls with unknown outcomes belong to execution recovery. Context continuation has a narrower job, ensuring that the next model call receives a checked record of task constraints and observations under their stated conditions.

↪ Restoring workspace state and reconciling in-flight tool calls on resumption are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-persistence-migration|Resuming a Trajectory]]**.

**Checkpoint 4.2: Continuing after compaction**

A candidate progress record says the repair is complete, while the retained evidence contains only a passing reproducer on `r18`.

**Evidence scope**: Which claim should the audit reject, and which historical result should it retain?

**Constraint preservation**: How can the runtime check for a missing no-deployment requirement without relying on the summary’s own checklist?

**Missing detail**: What conditions must hold before a raw-payload handle can supply an omitted assertion to the next call?

**Correction budget**: If each rejected record costs one more call as large as the compaction pass and the policy caps corrections at two, what is the worst-case multiple on ${C_{\text{comp}}}$ in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^eq-vol3-hysteretic-compaction-cost|equation 4]], and which outcomes remain permissible once the cap is reached?

A structured progress record preserves the distinctions an agent needs after old dialogue turns are evicted, yet those recorded observations support current decisions only while the workspace still matches what they read. Whenever an edit changes a source file, updates a configuration, or modifies a test fixture, the runtime must decide which findings still apply to the present state without erasing what was observed earlier.
