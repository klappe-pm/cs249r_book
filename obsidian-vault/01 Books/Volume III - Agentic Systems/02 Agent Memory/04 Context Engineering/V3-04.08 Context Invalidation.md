# V3-04.08 Context Invalidation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-context-rot

At the moment the repair agent’s candidate patch writes `src/pool.py` from `r17` to `r18`, before the reproducer runs again, the working context still holds the `r17` source excerpt, the `r17` test failure, and the missed-notification hypothesis built on both. While that failure still describes how the unpatched code behaved under the earlier source, test harness, and schedule, it says nothing about whether the `r18` patch fixes the bug.

The same boundary separates historical source excerpts from current code. An excerpt of `src/pool.py` read at `r17` explains why the agent formed its missed-notification hypothesis, whereas planning another edit against `r18` requires reading `src/pool.py` at `r18`. When building the next request, the runtime must choose whether to keep the `r17` excerpt as labeled history, replace it with the `r18` code, or drop it because the next step no longer needs it.

**Definition 4.3: Context invalidation**

***Context invalidation*** withdraws a staged observation’s authority to support claims about current state whenever an underlying artifact or operational precondition changes, while preserving that observation as historical evidence of the state it originally recorded.

1.  **Significance**: When a superseded observation leaks into a decision prompt, it introduces an unchecked step error that compounds across multi-step execution horizons (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]**). Invalidation intercepts this drift by converting stale state into an explicit refresh operation scheduled before the model acts.
2.  **Distinction**: Invalidation alters an observation’s applicability to the present, not its historical truth. It also differs from context deletion, which merely removes tokens from the request payload. The test failure at `r17` remains an immutable, accurate record of revision `r17`.
3.  **Common pitfall**: Treating a fresh timestamp or an unexpired polling interval as a guarantee that an in-context observation matches the current artifact on disk.

When a runtime neglects context invalidation, stale observations mislead decisions in three ways. First, in *offset drift*, the model plans an edit against line numbers or byte offsets read at `r17`, so after `r18` shifts the file, the patch tool either rejects the hunk ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^lst-vol3-stale-offset-edit|listing 3]]) or fuzzy-matches it into the wrong function. Second, in *ghost-symptom chasing*, the `r17` failure trace stays unmarked in the prompt, leading the model to keep diagnosing a bug that the candidate patch already fixed. Third, in *regression from old negative evidence*, a long early failure log outweighs a short passing notice from a later run, prompting the model to revert or complicate a working edit. Each failure confuses historical observation with current state, a confusion that dependency tracking turns into an explicit refresh step.

``` text
--- a/src/pool.py   (hunk planned from the r17 excerpt)
+++ b/src/pool.py
@@ -87,3 +87,4 @@
     def release(self, conn):
         self._idle.append(conn)
+        self._wake_one_waiter()
         return None
error: hunk 1 does not apply at line 87 of src/pool.py (r18)
error: expected context 'def release(self, conn):', found a different function
```

Listing 3: **An edit planned from a superseded read**: The hunk’s line numbers and context come from the r17 excerpt, and the patch tool rejects it against r18. Illustrative output, not a recorded trace.

### Tracking Claim Dependencies

^sec-vol3-context-engineering-claim-dependencies

Turning those failure modes into explicit refresh steps requires recording what each entry in the prompt depends on. Test-time deliberation solved the planning version of this problem by binding each observation to what it read and propagating lost support through a candidate plan’s dependency graph (**[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.06 Revising Candidate Plans#^sec-vol3-test-time-compute-precondition-invalidation|Invalidating stale and refuted evidence]]**). Context invalidation applies the same graph machinery to the working context, with two changes. The graph now covers the observations staged in the request rather than uncommitted plan nodes, and its usual trigger is a write the agent itself ran against the workspace. Observations reached by that write are marked historical rather than retracted. In the working context, a source excerpt records its file path, repository revision, and line span or abstract syntax tree (AST) symbol, while a test run records the source commit, test-suite revision, selected test case, runtime environment, and exit status. Derived conclusions inherit dependencies from their supporting observations, so once `r18` replaces `r17`, the behavior of the patched pool is an open question that needs fresh test runs ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^tbl-vol3-context-tracking-schemas|table 8]]).

| Manifest entry                       | Relevant dependencies                                                      | Treatment after the candidate patch                                       |
|:-------------------------------------|:---------------------------------------------------------------------------|:--------------------------------------------------------------------------|
| Source excerpt used to plan the edit | `src/pool.py` at the recorded revision                                     | Re-read the needed region at `r18` before planning another edit.          |
| Controlled waiter/return failure     | Source, test, and configuration used at `r17`                              | Retain as historical evidence; do not report it as a test of `r18`.       |
| Missed-notification hypothesis       | The `r17` source and observed failure                                      | Keep its status as a hypothesis; reassess using the patch and new checks. |
| Subsequent passing reproducer        | `r18`, the executed `tests/test_pool.py`, selected test, and configuration | Record this bounded result; broader behavior remains unresolved.          |

Table 8: **Dependencies and current applicability**: Each entry has a different reason to remain in, leave, or be refreshed within the repair’s next request.

^tbl-vol3-context-tracking-schemas

The runtime maintains this dependency graph in host code rather than leaving bookkeeping to model attention. Every staged observation ${o}_{t}$ binds to its target artifact through an **observation binding**:

$$
{\lambda}({o}_{t}) = \langle \text{artifact}, \text{kind}, \text{revision}, \text{range}, \text{content id} \rangle, \tag{5}
$$

^eq-vol3-observation-binding

where ${\lambda}({o}_{t})$ records the artifact identifier, its kind (source file, test run, daemon process, or build output), the revision observed, the byte range or symbol read, and a cryptographic hash of the content. Derived entries (working hypotheses and test summaries) hold directed edges to each supporting observation, forming the in-memory dependency graph.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn9|⁹]] Propagation follows the plan-graph traversal with one difference made possible by the binding: a tool write marks its directly bound observations historical rather than unsupported, and only the conclusions downstream of them are flagged for reassessment. Running this propagation when the patch writes `r18` produces the right-hand column of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^tbl-vol3-context-tracking-schemas|table 8]], while an excerpt of `docs/pool.md` and the API usage note built from it keep their status because nothing they depend on changed ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^fig-vol3-invalidation-graph|figure 4]]).

![[90 Assets/Volume III/04 Context Engineering/Ch04 Invalidation Graph c74d637c43.svg]]

Figure 4: **Invalidation Follows Recorded Dependencies**: Each staged observation carries the binding ${\lambda}({o}_{t})$ of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^eq-vol3-observation-binding|equation 5]], and each derived entry holds an edge to the observations it depends on. When the patch writes src/pool.py from r17 to r18, propagation marks the source excerpt and the controlled test run historical and flags the missed-notification hypothesis for reassessment. The documentation excerpt and the note derived from it keep their status because nothing they depend on changed. A historical observation remains evidence about r17; the marking removes only its support for claims about r18.

^fig-vol3-invalidation-graph

Selective invalidation is only as accurate as its recorded edges. Editing a test assertion, changing a timeout setting, or modifying a core struct immediately invalidates dependent test claims. Whenever dependency edges are coarse or incomplete, safety favors over-invalidation. Marking a wider set of entries for refresh avoids acting on silent regressions, because a missing edge never proves freshness.

Cryptographic content hashes verify whether input files stay identical across steps.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn10|¹⁰]] When checking a derived result, the runtime compares the current content hashes of its direct dependencies against the hashes recorded when the tool ran. Even when all input hashes match, nondeterministic behavior (thread scheduling or network timing) means that a single passing run is still only one sample, so the manifest tracks artifact versions, execution scope, and sampling uncertainty separately.

### Detecting Change and Bounding Uncertainty

^sec-vol3-context-engineering-change-detection

The clearest signal that an artifact has changed is a write completed through a runtime tool. When a file-editing tool writes `r18`, the runtime marks all `r17` source excerpts historical and records open test obligations for the modified file. Because a tool call that fails or times out can still leave partial edits on disk, the runtime checks the affected files alongside exit codes and return payloads, marking dependent observations for refresh until the on-disk state is known. All of this tracking belongs in the runtime’s dependency graph rather than in prompt reminders asking the model to remember what changed.

External processes can also change workspace files outside the agent’s tool calls. Cheap filesystem metadata (file size and modification time) offers a quick hint to re-check a file, while content hashes or git commit IDs confirm whether the bytes actually changed. Kernel filesystem watchers such as Linux’s `inotify` cut detection delay, yet queue overflows, unmonitored mounts, and dropped events can leave a cached view stale ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-linuxManpages2026inotify|Linux man-pages project 2026]]). Runtimes therefore treat watcher notifications as hints to re-verify hashes rather than as a complete log of changes.

To bound staleness on external resources that emit no change events, runtimes often set a **time-to-live** (TTL) that forces a fresh read once an observation passes a chosen age. A TTL is a practical rule of thumb tuned to how fast the environment changes and what a stale decision costs, not a guarantee of consistency.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn11|¹¹]] An observation can go stale microseconds after it is read, and an expired entry may still match an unchanged resource. Before any high-consequence action, the runtime bypasses TTL caches and reads the current state directly.

Even when the runtime refreshes context right before building a prompt, the external system can still change between prompt assembly and tool execution. Context engineering cannot close that race window inside the prompt; closing it requires action-time preconditions at the tool boundary, such as atomic compare-and-swap writes or revision checks.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn12|¹²]] Context assembly contributes by recording the exact revision ID on which the model planned its action so the tool runner can check that revision before applying the write.

↪ Execution-time preconditions enforced as atomic conditional updates at the tool boundary are developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-conditional-updates|Conditional updates]]**.

### Removing, Replacing, or Appending

^sec-vol3-context-engineering-invalidation-choice

Once dependency tracking or a version check marks an in-context observation outdated, the runtime must decide how to reflect that change in the next request ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^tbl-vol3-invalidation-policies|table 9]]). It can remove the outdated payload outright, replace it in place with a short marker or fresh read, or append a superseding notice at the end of the prompt. Each choice trades KV-cache prefix reuse against the risk of leaving stale tokens visible to attention.

| Policy                      | What the next request contains                                                               | Limitation                                                                                              |
|:----------------------------|:---------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------|
| Remove the old payload      | Other selected material, without the outdated excerpt                                        | The request no longer supplies that historical detail; provenance must be retained elsewhere if needed. |
| Replace the old payload     | Current evidence, or a short marker that identifies the superseded entry and pending refresh | A marker is not fresh evidence; changing earlier tokens also changes the reusable prefix boundary.      |
| Append a superseding notice | The unchanged old payload plus a notice describing its status                                | The outdated material remains visible and occupies capacity; the notice does not enforce correct use.   |

Table 9: **Invalidation representation choices**: Removing a payload, replacing it in place, and appending a notice are different operations, even when each is described informally as tombstoning, the practice of leaving a marker where deleted content stood.

^tbl-vol3-invalidation-policies

In the connection-pool repair, an in-place marker can state directly that the earlier excerpt came from `r17` and that the agent must read `r18` before planning another edit. It can also keep a short note on the `r17` failure if that history still informs the diagnosis. That replacement keeps the investigation coherent without presenting old code as current state, and a handle to the full `r17` excerpt preserves auditability without spending working-set tokens.

Appending a notice at the end of the prompt preserves the KV-cache prefix across the turn, yet it leaves the model to weigh the earlier excerpt against the trailing correction.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn13|¹³]] Placing the notice at the end of the request or phrasing it strongly does not guarantee that attention will favor the correction over the detailed code or error trace above it. Conversely, removing the payload drops the stale tokens from the prompt, though it can leave downstream hypotheses dangling unless the runtime also propagates the change through the dependency graph. Both removal and in-place replacement end KV-cache reuse at the first modified token, forcing the serving engine to prefill the entire suffix that follows.

**Napkin Math 4.4: Token accounting for invalidation**

**Problem**: How do payload removal, in-place replacement, and appended notices change resident token counts and the uncached suffix that the serving engine must prefill?

**Variables**: The baseline prompt is the 47,000-token request under the selecting policy of notebook [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-evidence-budget). An outdated 850-token source excerpt from `r17` sits at the start of the trunk, leaving the 15,000-token root (system instructions and tool declarations) as the unchanged prefix. An in-place tombstone marker takes 24 tokens, and an appended notice, including role and message framing, takes 128 tokens. These counts are serialized token lengths assuming no cross-boundary BPE re-tokenization. To isolate the invalidation edit itself, the leaf is held fixed from the previous call and the notice is appended at the end of the request after the leaf. Both removal and in-place replacement diverge from the previous request at the end of the root prefix, ending KV-cache reuse there.

**Math**: Removing the excerpt leaves 47,000 − 850 = 46,150 resident tokens, and subtracting the reusable root leaves 46,150 − 15,000 = 31,150 tokens in the uncached suffix.

Replacing the excerpt with a tombstone leaves 46,150 + 24 = 46,174 resident tokens and an uncached suffix of 46,174 − 15,000 = 31,174 tokens. Appending a notice leaves all earlier tokens untouched, giving 47,000 + 128 = 47,128 resident tokens with only the new 128-token tail beyond the cached prefix.

**Systems insight**: For the invalidation edit alone, appending preserves the cached prefix and prefills only 128 tokens against 31,174 under in-place replacement, roughly 244× fewer. On a real next call that also replaces the 8,000-token leaf, both choices prefill that new leaf as well, narrowing the per-call difference to the trunk that replacement recomputes. Moreover, the cache saving from appending recurs as a cost on every later call because all 850 superseded tokens remain in the prompt, diluting attention on current evidence ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^eq-vol3-softmax-dilution|equation 2]]) and inviting ghost-symptom chasing. Runtimes therefore use the dependency graph to combine both approaches. They append a notice for historical observations that the agent cites only as background. They replace or tombstone code regions that upcoming edits target, or batch that replacement into the next scheduled trunk rewrite when the trunk prefix will be recomputed anyway (notebook [4.2](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-quantitative-impact-of-prefix-layout)). Because none of the three options loads the new code, the read of `r18` and the output reserve must be budgeted separately.

Context invalidation keeps historical observations separate from claims about present state by combining dependency tracking, bounded freshness checks, and deliberate replacement rules. Whether the complete context policy actually supplies enough evidence for valid actions while lowering token spend and prefill latency is an empirical question that only end-to-end evaluation on realistic tasks can answer.
