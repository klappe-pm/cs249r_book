# V3-04.13 Exercises

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-exercises

Unless a problem states otherwise, use the reference repair harness and the hypothetical prices in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.13 Exercises#^tbl-vol3-context-engineering-exercise-givens|table 12]]. Token counts are for complete serialized requests, prices are problem inputs rather than any provider’s schedule, and a reused prefix is assumed to have compatible cached state available.

| **Quantity**                         | **Symbol**   | **Given**                                   |
|:-------------------------------------|:-------------|:--------------------------------------------|
| Context window of the repair harness | ${S_{\max}}$ | 128,000 tokens                              |
| Step budget of the repair harness    | ${H}$        | 30 turns                                    |
| Uncached input price                 |              | \$3 per million tokens                      |
| Reused-prefix input price            |              | \$0.30 per million tokens (10% of uncached) |
| Output price                         |              | \$15 per million tokens                     |

Table 12: **Givens for the exercises**: The window and step budget come from the registry’s repair-harness profile; every price is hypothetical.

^tbl-vol3-context-engineering-exercise-givens

**1. Tool catalogs and the output reserve (Basic).** The repair harness gains a larger tool catalog and longer patch outputs. Its tool declarations grow to 30,000 tokens, and the runtime raises ${K_{\max}}$ to 16,000 tokens. Application instructions stay at 3,000 tokens and task state at 24,000, and every tool result is appended at 4,000 tokens.

1.  Using [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^eq-vol3-context-budget-partition|equation 1]], compute the input limit, the observation budget, the number of appended turns that fit, and the largest per-turn digest that carries the full step budget ${H}$.
2.  A proposal loads tool declarations on demand, the on-demand staging that **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.10 Designing the Active Toolkit#^sec-vol3-tool-calling-tool-staging|Static and on-demand staging]]** weighs against static staging, and keeps only 6,000 tokens of core declarations resident. Repeat (a).
3.  Show that no tool-declaration policy lets unmodified 4,000-token results be appended for all ${H}$ turns under the 16,000-token reserve. Which term must the design change instead? Compare the per-turn digest each declaration policy allows, and state what the on-demand policy adds to a request whenever a turn needs a non-core tool.

**2. When appending stops being cheaper (Basic).** Every request carries a fixed 39,000 tokens of instructions, declarations, and task state. The appending policy adds ${\Delta S_{\text{turn}}} = 4{,}000$ tokens of tool results per turn and keeps them all; the selecting policy keeps ${S_{\text{obs}}} = 8{,}000$ tokens of observations on every call. Assume no prefix reuse and a window large enough to admit every request.

1.  Write the cumulative input tokens of each policy over ${H}$ turns. At which call does the appending policy’s single request first exceed the selecting policy’s, and at which horizon does its cumulative bill first exceed?
2.  A longer task runs a 60-turn step budget. Compute both cumulative bills in tokens and at the uncached input price, and their ratio.
3.  Show that the ratio of the two bills is exactly linear in ${H}$ and find its slope. At what horizon does appending cost three times as much as selecting? Use the result to critique a plan to “add selection later, once tasks get long.”

**3. Look-alike evidence versus bulk (Basic).** In the toy head of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^eq-vol3-softmax-dilution|equation 2]], the target key has logit ${z_{\text{target}}} = 6$. The request holds 40,000 unrelated keys at logit $-2$ and a superseded 850-token `r17` excerpt whose keys share identifiers with the evidence, giving each a logit of 2. All logits stay fixed as keys are added or removed.

1.  Compute ${\alpha_{\text{target}}}$ without the excerpt and with it.
2.  How many unrelated keys contribute as much to the normalizer as the 850 excerpt keys?
3.  The runtime can either drop half of the unrelated keys or drop the excerpt. Compute ${\alpha_{\text{target}}}$ for each choice, and for dropping every unrelated key while keeping the excerpt. Which removal should the runtime make first, and which measurement from [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^sec-vol3-context-engineering-evaluation|section 4.8]] would confirm the choice on a trained model?

**4. Choosing a watermark gap (Intermediate).** A noisier test suite raises arrivals to ${\Delta S_{\text{turn}}} = 6{,}000$ tokens. Compaction returns the request to ${S_{\text{low}}} = 47{,}000$ tokens: a 15,000-token root, a 24,000-token trunk, and an 8,000-token leaf. The output reserve is ${K_{\max}} = 8{,}000$. Two triggers are proposed, ${S_{\text{high}}} = 92{,}000$ and ${S_{\text{high}}} = 68{,}000$. Model each cycle as ${n_{\text{cycle}}}$ ordinary calls at request lengths ${S_{\text{low}}} + {i} \, {\Delta S_{\text{turn}}}$ for ${i} = 1, \ldots, {n_{\text{cycle}}}$, the last of which triggers a compaction pass over the same request. The first ordinary call after a pass reuses only the root, because the pass rewrote the trunk; every later call reuses the whole previous request. Each ordinary call generates 1,000 output tokens. The compaction pass processes its entire input uncached and generates a 6,000-token record.

1.  For each trigger, compute ${n_{\text{cycle}}}$ from [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^eq-vol3-hysteretic-compaction-cadence|equation 3]], the trigger length and overshoot, whether the trigger request plus ${K_{\max}}$ fits the window, and the number of passes within ${H}$.
2.  Compute ${C_{\text{comp}}}$, the mean ordinary-call cost, and ${\bar{C}_{\text{turn}}}$ from [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^eq-vol3-hysteretic-compaction-cost|equation 4]] for each trigger.
3.  Each pass independently loses each of 10 unprotected constraints with probability 0.02. Compute the probability that all 10 survive every pass of the step budget under each trigger.
4.  Choose a trigger and explain why the narrow gap loses on both cost and retention even though each of its passes is cheaper. What measured property of the workload would justify the narrow gap anyway?

**5. Replace now, or ride the next rewrite? (Intermediate).** Start from the request of notebook [4.4](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-invalidation-tokens): 47,000 tokens behind a 15,000-token root, with an 850-token `r17` excerpt opening the trunk, a 24-token replacement marker, and a 128-token appended notice. Twenty calls remain, and each later call reuses the whole previous request; the new leaf content is the same under both policies and can be ignored.

1.  Compute the input cost of the next call under replacement and under an appended notice.
2.  How many more tokens does the appended policy keep resident on every later call, what do they cost per call at the reused-prefix price, and after how many calls would the two policies break even on price alone?
3.  A compaction pass is scheduled six calls from now and will rewrite the trunk regardless. Propose an invalidation policy that uses this fact, and state the condition under which it must replace the excerpt immediately anyway. Using [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-stale-support|equation 7]], identify which of the next six decisions belong in the denominator and how the policy keeps the numerator at zero.

**6. Paying for a protected-field check (Intermediate).** A model-written progress record loses each of 12 required constraints independently with probability ${\rho} = 0.03$ per compaction round, and the trajectory runs 3 rounds. A lost constraint makes the task unacceptable; with every constraint intact, ${p_{\text{acc}}} = 0.6$. An attempt costs \$2. A protected-field check in the style of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.07 Structured Progress Records#^lst-vol3-progress-audit|listing 2]] detects 90 percent of losses and repairs each detected loss; budget it as one \$0.05 correction call per round.

1.  Without the check, compute the probability that all 12 constraints survive, the resulting ${p_{\text{acc}}}$, and ${C_{\text{eff}}}$.
2.  Repeat with the check, treating undetected losses as the new per-round loss.
3.  What per-round loss would an unchecked summarizer need to keep all-constraint survival at or above 95 percent over 3 rounds?
4.  With the check in place, after how many rounds does all-constraint survival first fall below 50 percent? The runtime in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.07 Structured Progress Records#^sec-vol3-context-engineering-summarization|section 4.6]] copies contract constraints directly from the task contract. What does that change, and which protected fields remain exposed to ${\rho}$?

**7. A stable root for short sessions (Advanced).** The support agent serves 50,000 sessions a day. Each request carries a 20,000-token root of policy instructions and tool declarations and a 2,000-token customer record. A session makes 6 calls; before call ${t}$ the request has grown by 1,500 tokens per turn to $22{,}000 + 1{,}500\,{t}$ tokens, and each call generates 300 output tokens. Sessions arrive often enough that compatible root state is always resident. Layout A places the customer record and a session timestamp ahead of the root; Layout B places the root first. Within a session, every call after the first reuses the whole previous request under either layout.

1.  Compute the input and output cost per session, the daily bill, and the token-weighted prefix hit rate under each layout.
2.  Show that the entire difference arises on the first call of each session. Which term of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^eq-vol3-context-budget-partition|equation 1]] binds here, and how does that differ from what binds the repair agent over its step budget?
3.  A developer templates the customer’s name into the first line of the policy instructions to personalize the tone. Which layout does that recreate, and what does it cost per day?
4.  A cost review proposes cutting the root to 10,000 tokens by removing policy text. Under Layout B, compute the saving per session. With a 90 percent resolution rate at the full root, and each unresolved session escalating to a human at \$4, how many percentage points of resolution can the cut lose before it costs more than it saves? What evidence should the proposal present before it ships?

**8. Freshness through a human approval (Advanced).** The remediation agent decides on a production change from 5 observations of shared state. Other actors change each observed resource independently, as a Poisson process with mean rate ${r_{\text{chg}}}$ of one change per 20 minutes. The runtime refreshes an observation only when it is older than a 10-minute time-to-live, so at decision time each observation’s age is uniformly distributed between 0 and 10 minutes.

1.  Compute the probability that one observation still describes its resource at decision time and the probability that all 5 do. If every decision requires current evidence for all 5, estimate ${\epsilon_{\text{stale}}}$ from [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-stale-support|equation 7]].
2.  A teammate proposes refreshing all 5 observations immediately before each model call. The call takes 30 seconds, and the action executes after a human approval that takes 10 minutes. Compute the probability that at least one of the 5 resources changes between refresh and execution, first ignoring the approval and then including it. What does the result show about the limit of any context-refresh policy for this workload?
3.  Only one observation, the configuration version the change edits, determines whether the action is safe; the other four were diagnostic. Redesign the policy around the binding ${\lambda}({o}_{t})$ of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^eq-vol3-observation-binding|equation 5]] and an action-time precondition at the tool boundary that re-observes and re-requests approval when the precondition fails. Compute the probability that the precondition holds at execution and the expected number of approval rounds, and compare with a precondition on all 5 observations. Contrast the change signal available here with the one the repair agent uses after its own patch.

**What’s Next: From selected tokens to physical attention state**

The runtime has chosen the token sequence for the next call, and the prefix-layout calculation priced its reused prefix as a discounted line on the bill. Behind that discount sits physical state. The serving system must decide whether to retain the attention state computed from earlier compatible prefixes, and holding it occupies accelerator memory even while the agent generates nothing and waits on a tool, memory that competing requests could use. **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management#^sec-vol3-kv-cache|KV Cache Management]]** sizes that state and develops the storage, sharing, and retention decisions for it. Those decisions can change execution cost without changing which observations belong in the logical working context.
