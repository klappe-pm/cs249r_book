# V3-04.10 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-fallacies

A prompt can be compressed until it drops a required constraint, or left as an uncurated transcript where superseded tool outputs sit beside current state. Both failures happen when engineers ask the prompt payload to do the work of state tracking, durable storage, and execution enforcement all at once.

**Fallacy**: *If every token fits, every needed fact is usable.*

Admitting a prompt within the interface’s context window does not ensure that the model can attend to and extract every critical fact ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^sec-vol3-context-engineering-physics|section 4.3]]). Token capacity sets only an upper bound on input size, whereas evidence retrieval depends on how attention weight is distributed. For example, under fixed logits, the toy attention head in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^eq-vol3-softmax-dilution|equation 2]] assigns 96.8 percent of its attention weight to the target token across a sequence of 100 keys. This share declines to 2.9 percent when distributed across 100,000 keys, even though all 100,000 keys fit within the context limit. Validating a context layout therefore requires varying information density and placement alongside sequence length, measuring actual task completion on realistic workloads rather than relying on raw token budgets.

**Pitfall**: *Treating deterministic extraction as lossless task understanding.*

Deterministic filters and parsers guarantee reproducibility, but reproducibility is not task understanding. A heuristic parser consistently extracts the same error lines while silently dropping the warning that preceded them. For example, filtering exclusively for `FAILED` status lines in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^lst-vol3-compaction-observation|listing 1]] isolates the failing assertion while discarding the event sequence that makes the failure actionable. Deterministic pipelines make transformations inspectable and debuggable, yet they remain vulnerable to silent data loss. Reliable runtimes guard against this by marking protected fields that summarization passes cannot discard, noting omitted spans, and retaining content-addressed handles to raw payloads so that an agent can re-read original data when needed.

**Fallacy**: *A valid progress-record schema guarantees continued compliance.*

A structured schema verifies syntactic presence, but it cannot guarantee that task constraints survive repeated compaction cycles. Under the hypothetical 5 percent per-round loss rate modeled in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^eq-vol3-constraint-retention|equation 6]], an operational policy constraint survives 40 iterative compaction steps with only 12.9 percent probability, even though every intermediate serialized record validates cleanly against the schema. Systems engineers must treat prompt context as an advisory channel rather than an enforcement layer. Runtimes must validate protected fields against ground-truth sources at every compaction boundary ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.07 Structured Progress Records#^sec-vol3-context-engineering-summarization|section 4.6]]), check subsequent agent actions against security policies, and enforce hard execution boundaries in host code rather than relying on in-context reminders.

**Pitfall**: *Keeping obsolete support solely to preserve a prefix hit.*

Appending corrections to the end of a transcript preserves prefix-cache hits for the next call. In notebook [4.4](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-invalidation-tokens), the invalidation edit alone makes in-place replacement reprocess roughly 244× as many tokens beyond the prefix, a gap that narrows to the size of the trunk once the next call’s new leaf is counted. However, prioritizing short-term cache hits retains 850 superseded tokens across all subsequent requests, forcing the model to repeatedly reconcile stale text with appended errata. The dependency graph decides which rule applies. Evidence in any region that a later edit or current-state decision targets should be replaced, and appended notices reserved for inert history that the agent cites only as rationale ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-context-rot|section 4.7]]).

**Fallacy**: *A larger context window removes the need to select and compact.*

Expanding context windows raises physical token limits, but it does not eliminate the compounding latency, cost, and attention dilution of unmanaged histories. As demonstrated in notebook [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-evidence-budget), an append-only transcript policy running across a 30-turn horizon requires 167,000 tokens by its final request. While an expanded window accommodates this trajectory, it bills 3,030,000 input tokens compared to 1,410,000 tokens for a selective policy that maintains a compact working set of 8,000 observation tokens, a factor of 2.1× in token volume. The extra tokens also dilute attention over the evidence required for subsequent tool calls. Structured selection and compaction remain necessary, reducing both the effective trial cost ${C_{\text{eff}}}$ and the distraction within the request regardless of window capacity.

**Pitfall**: *Placing unnecessary volatile fields before reusable content.*

Prefix-caching engines match sequence tokens strictly from left to right. Inserting dynamic values (timestamps, request identifiers, ephemeral counters) near the start of a prompt breaks cache reuse across turns, even when the system prompt, schemas, and task instructions that follow are completely unchanged. In notebook [4.2](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-quantitative-impact-of-prefix-layout), this volatile layout increases the input bill so that it is 3.2× that of the stable layout under explicit reuse and pricing assumptions. Exact-prefix matching halts at the very first differing token, regardless of message roles or field meaning. System architects should structure prompts hierarchically, pinning invariant instructions and tools at the root prefix and deferring volatile, per-call parameters to the leaves.

These pitfalls share one root cause: treating the prompt window as a single store for evidence, task state, and execution enforcement. Sound context engineering divides those jobs across the runtime, using the working context to stage task-relevant evidence for the next decision, external stores to hold verified history, and host gates to enforce action boundaries.
