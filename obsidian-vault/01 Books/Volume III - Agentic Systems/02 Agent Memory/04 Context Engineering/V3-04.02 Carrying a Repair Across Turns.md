# V3-04.02 Carrying a Repair Across Turns

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-overview

The repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) has spent several turns investigating a connection-pool defect. It has inspected the pool implementation, executed a reproduction test, and revised its initial diagnosis. Deliberation has left behind candidate versions, a refuted timeout hypothesis, test observations, and the dependency records that tie them together (**[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.06 Revising Candidate Plans#^sec-vol3-test-time-compute-planning-revision|Revising Candidate Plans]]**). None of that progress lives inside the model. Because foundation models are stateless functions across turns, every call begins and ends with the payload assembled by the host runtime. The agent can use the test trace, honor public API constraints, and avoid revisiting a rejected hypothesis only if the runtime includes them in the upcoming request. The runtime must also structure that request so that the status and role of each artifact remain unambiguous.

![[90 Assets/Volume III/04 Context Engineering/Hsa Locator S a07206df7c.svg]]

*H·S·A locator with only the State axis lit in purple.*

*Working context governs the within-session state exposure by selecting, representing, and refreshing what each call carries.*

The token accounting of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.04 Tokenizing the Request#^sec-vol3-foundation-model-tokenization|Tokenizing the Request]]** settles two questions for an individual request: whether the payload satisfies the admission bound, and what its tokens cost (**[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-cost|The Cost of a Model Call]]**). Those bounds, however, do not determine whether the prompt helps the model make a sound decision. A prompt can fit well within token limits and still fail to guide the agent toward a valid repair. The simplest agent architectures evade this problem by treating context as an append-only log, concatenating every observation, tool execution, and partial response into an expanding transcript. That policy breaks down almost immediately. Even while the transcript fits within physical limits, the runtime pays repeatedly for obsolete tokens that the next decision no longer requires. Stale code snippets sit alongside their replacements, and refuted hypotheses linger alongside the test results that disproved them, diluting the model’s attention. When an extended trajectory inevitably exhausts the context window, an unmanaged runtime must truncate blindly, evicting instructions or early constraints without any principled criterion for what to preserve.

↩︎ The quadratic input cost of resending an append-only history on every call is established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-trajectory-cost-accumulation|How multi-turn history drives up input cost]]**.

The agent’s *working context* is the runtime subsystem that decides what each model call receives. Rather than treating context as a passive transcript, this subsystem constructs a bounded working set tailored to a single decision. It establishes token budgets for each distinct role in the prompt and arranges data layouts so unchanged prefixes can be reused across turns. It compacts historical evidence without distorting the facts, maintains structured progress records that resist summarization drift, and enforces invalidation rules whenever external actions alter environment state. The host runtime owns assembly, token budgets, records, and execution gates. Selection and compaction can use heuristics or model-generated candidates, which the runtime must check against the task’s requirements and retained evidence before admission.

The chapter follows the repair agent through its next decision, and each section answers the question the previous one leaves open. The runtime first decides which evidence the next step needs and how the input allowance divides among competing roles ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^sec-vol3-context-engineering-decision|section 4.2]]). Admitting that evidence does not mean the model can use it, so [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^sec-vol3-context-engineering-physics|section 4.3]] separates the window an interface accepts from the context a model reliably acts on. The selected items then need a layout that keeps their sources distinct and their stable prefix reusable across turns ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-staging|section 4.4]]). When history outgrows the budget, compaction ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^sec-vol3-context-engineering-compaction|section 4.5]]) and audited progress records ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.07 Structured Progress Records#^sec-vol3-context-engineering-summarization|section 4.6]]) shorten it without erasing causal evidence or refuted hypotheses. When the agent’s own edits change the workspace, invalidation ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-context-rot|section 4.7]]) withdraws the observations that no longer describe it. Evaluation ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^sec-vol3-context-engineering-evaluation|section 4.8]]) then asks how to show that a complete policy lowers the cost per accepted task.
