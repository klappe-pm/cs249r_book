# V3-04.03 The Working-Set Decision

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-decision

As our connection-pool investigation unfolds, the runtime accumulates far more information than was present at initialization. A controlled test has shown that a connection returned to the pool while a waiting client remained blocked, so the initial timeout hypothesis has lost support and missed notification is now the leading candidate explanation. The next model call must build on these findings. If the runtime replays the entire conversational history without distinguishing raw observations from superseded hypotheses, it forces the model to weigh discounted failure modes alongside the evidence that disproved them.

Consider the codebase at version `r17`, where the relevant files are `src/pool.py` and `tests/test_pool.py`, and the failure is captured by the reproducer `test_waiter_notified_on_return`. Before prompting the model for a candidate patch, the runtime must decide which source excerpts, test results, interface constraints, and open questions belong in the upcoming prompt. This choice is the **working-set decision**, the runtime’s selection of the bounded subset of task information needed to run the next concrete step. Making that choice is the first obligation of treating context as a selected working set (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-attention-working-set|4]]).

The term draws on Denning’s classic working-set model of program behavior ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-denning1968|Denning 1968]]). Over any time window, a running program references only a fraction of its total address space, so an operating system avoids thrashing by keeping those active pages in physical memory while leaving dormant pages on backing storage. An agent runtime faces a similar residency problem when it stages tokens in context to support the next step without exhausting its prompt budget, yet one structural difference separates context engineering from virtual memory. Denning’s working set is measured from page references the program has already issued, whereas an agent runtime must assemble the context working set *before* calling the model, predicting what the upcoming decision will need.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn1|¹]] Moreover, standard foundation model interfaces report only generated tokens and emit no hardware-style reference bits to show which staged context tokens the model actually relied on during inference.

In context management, relevance to the next step must govern selection rather than chronological recency. Core user constraints set at the start of a session remain binding after dozens of intermediate tool calls, whereas a lengthy test log produced moments ago may contribute only a single exit code. Candidate information also comes from well beyond the dialogue history: system instructions, tool declarations, newly read source files, and retrieved reference documents ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-lewis2020retrieval|Lewis et al. 2020]]) all compete for space in the assembled request. The runtime must build a working representation from these sources without letting any staged copy outrank its origin, because authority stays with the source (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-source-authority|6]]). The environment remains the only authority on system state, and runtime policy, not the model, decides which actions are permitted.

To organize this selection, the runtime builds a **context manifest**, a structured inventory that lists each item chosen for the upcoming request and why the next step needs it. The manifest for the connection-pool repair’s next request ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^tbl-vol3-context-manifest|table 1]]) reads like a specification rather than a raw byte stream, naming each entry and the exact content it supplies. Code snippets and test logs keep their source and version labels, and their contents enter the prompt only where the next decision requires them.

| Selected entry          | Content needed for the next step                                                                                                                                            |
|:------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Goal and constraints    | Repair waiter notification; preserve the public API; remain within the approved workspace; do not deploy to production.                                                     |
| Current artifacts       | Relevant source and test excerpts from `src/pool.py` and `tests/test_pool.py` at `r17`, together with the configuration used by the controlled test.                        |
| Observed result         | On `r17`, the controlled waiter/return test recorded an available connection while a waiter remained blocked. Keep the test identity and conditions attached to the result. |
| Hypothesis status       | The timeout explanation has lost support. Missed notification remains a hypothesis, not an established cause.                                                               |
| Repair and check status | No candidate patch has yet been checked. Behavior outside the controlled reproducer remains unresolved.                                                                     |
| Next bounded step       | Propose a candidate change to the notification path using the current excerpts; do not report the defect as repaired.                                                       |

Table 1: **Selecting the next request**: Each entry supplies a distinct part of the illustrative connection-pool decision. Version labels identify the example’s artifacts, not measured repository revisions.

^tbl-vol3-context-manifest

Building this manifest requires careful filtering. Keeping a failure log without tying it to its source commit (`r17`) can mislead later turns into reading an old error trace as evidence against a newly patched file. Likewise, recording a short label like “notification bug” without noting its uncertainty turns a working hypothesis into a settled root cause. Conversely, keeping the full dialogue of rejected theories wastes space once the runtime records which test refuted the timeout hypothesis. While a foundation model can help summarize earlier turns to draft this manifest, the runtime must check those candidate summaries against recorded environment observations before admitting them into the prompt.

The active working context must also stay separate from durable records in external storage. Rather than inlining a long test log into the prompt, the runtime can supply a **raw-payload handle**, a short reference to an external record that an authorized tool can read on demand under access and retention rules. This design enforces the **handle rule**: once a payload moves behind a handle, it re-enters the working context only through an explicit, checked read. If a later step needs a specific stack-trace line or configuration value omitted from the initial prompt, the model calls a retrieval tool to bring that slice into context.

Every working-set candidate must fit within the endpoint’s context admission bounds. When an endpoint shares one context window across inputs and outputs, the serialized prompt length ${S}$ must satisfy ${S} \le {S_{\max}} - {K_{\max}}$, where ${K_{\max}}$ is the token budget reserved for generation. When providers enforce separate input and output limits, ${S} \le {S_{\max}}$ applies directly. The runtime must count tokens on the fully formatted wire request (system envelopes, chat delimiters, and JSON tool schemas included) rather than summing isolated strings, because tokenizer merges and framing overhead can easily erase the savings of a shorter evidence block.

↩︎ The admission bound and the output headroom ${K_{\max}}$ it reserves are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.04 Tokenizing the Request#^sec-vol3-foundation-model-output-headroom|Output headroom]]**.

While this inequality sets the overall ceiling, the runtime must divide the available input space across the four roles in the manifest:

$$
{S_{\text{system}}} + {S_{\text{tools}}} + {S_{\text{state}}} + {S_{\text{obs}}} \le {S_{\max}} - {K_{\max}}. \tag{1}
$$

^eq-vol3-context-budget-partition

Here ${S_{\text{system}}}$ counts the static system instructions, ${S_{\text{tools}}}$ counts API schemas and tool declarations, ${S_{\text{state}}}$ counts active constraints, progress records, and staged source or test excerpts, and ${S_{\text{obs}}}$ counts recent tool outputs and user steering. Because all four terms share a fixed ceiling, growth in any one term squeezes the others. A runtime that appends every raw tool output[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn2|²]] lets ${S_{\text{obs}}}$ grow on every turn until command-line logs crowd out ${S_{\text{state}}}$, the constraints and code excerpts the next decision needs. Whereas appending lets observations expand until they displace task state, selection holds each role’s share steady by moving older results into external records that a handle can still reach ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^fig-vol3-working-set-selection|figure 1]]).

[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^eq-vol3-context-budget-partition|Equation 1]] is a planning budget rather than an exact identity, because sub-word tokenization across joined strings does not equal the sum of separately tokenized parts. The runtime must therefore check the assembled wire request against the provider’s limit, and when the request runs over, the budget partition tells the runtime which share (usually the observation buffer or older history) to trim or compact first. Prompt staging ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-staging|section 4.4]]) then orders these same four components by how often they change so the serving engine can reuse their cached prefix.

**Napkin Math 4.1: How much of the window is evidence**

**Problem**: In our reference repository-repair harness, an agent runs inside a 128,000-token context window under a 30-turn step budget. The runtime reserves 8,000 tokens for generation (${K_{\max}}$) and assigns 3,000 tokens to system instructions (${S_{\text{system}}}$) and 12,000 tokens to tool declarations (${S_{\text{tools}}}$). Dynamic task state (constraints, progress records, and active code excerpts) takes 24,000 tokens (${S_{\text{state}}}$). If every raw tool result is appended directly at 4,000 tokens per turn, how many turns fit within the window, and what maximum per-turn observation size lets the agent finish the full step budget?

**Variables**: The context window and step horizon come from the registry’s repository-repair harness profile, while component sizes and per-turn observation counts are scenario values for fully serialized wire requests.

**Math**: By [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^eq-vol3-context-budget-partition|equation 1]], the usable input allowance is 128,000 − 8,000 = 120,000 tokens. Subtracting system instructions and tool declarations leaves 105,000 tokens (82.0 percent of the context window) for state and observations, and deducting the 24,000 tokens of state leaves an observation budget of 81,000 tokens. Under naive appending, this budget holds 81,000 / 4,000 = 20 turns. Lasting all 30 turns requires keeping the per-turn observation payload to at most 81,000 / 30 = 2,700 tokens.

**Result**: The appending policy overflows the context window at turn 21, well short of the 30-turn budget.

**Systems insight**: Because the number of feasible turns equals the observation budget divided by the per-turn observation size, observation volume is the primary design lever. Compacting each result into an informative 2,000-token digest extends the run to 40 turns and clears the step budget. Fitting inside the window, however, is only the first cost. Because an appending policy re-reads every accumulated token on each call, its cumulative input bill grows quadratically in ${H}$. This follows the re-send pattern of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 2.9]]** with a per-turn append ${\Delta S_{\text{turn}}}$ of 4,000 tokens, where the first request already holds one tool result, so the appended sum runs to ${H}({H}+1)/2$. Selection keeps the bill linear. Across this step budget, and even granting the appending policy a window large enough to admit its final request, appending bills 3,030,000 input tokens against 1,410,000 for selection, 2.1× as many. That extra spend enters the numerator of ${C_{\text{eff}}}$ (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**) on every attempt.

The notebooks throughout this chapter reuse this baseline scenario, adopting the 128,000-token window, the 30-turn step budget, and the component token allocations defined above. Whereas the repair agent binds on the growth of ${S_{\text{obs}}}$ against ${S_{\text{state}}}$, the other three lighthouses stress different terms of the same partition.

**Lighthouse 4.1: Context by archetype**

Each recurring workload places pressure on a distinct component of the context budget in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^eq-vol3-context-budget-partition|equation 1]], calling for a different runtime mechanism ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^tbl-vol3-context-by-archetype|table 2]]).

|:----------------------|:------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Repair agent**      | Source excerpts, test logs, and a progress record from its own workspace, accumulating over a 30-turn step budget | Growth of ${S_{\text{obs}}}$ displacing ${S_{\text{state}}}$                  | Compaction and progress records ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^sec-vol3-context-engineering-compaction\|section 4.5]])                                                                                                                                                                                    |
| **Research agent**    | Retrieved pages and search results written by third parties                                                       | Third-party text that dominates ${S_{\text{obs}}}$ and may carry instructions | Staging that keeps each span’s source attached ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-source-scope\|section 4.4.2]]); enforcement in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.06 Quarantined Readers and Ingestion Isolation#^sec-vol3-security-quarantined-readers\|Quarantined Readers and Ingestion Isolation]]** |

Table 2: **Context by archetype**: The four recurring workloads bind on different terms of the same input budget.

^tbl-vol3-context-by-archetype

**Systems insight**: The same budget equation binds on different constraints across workloads: token growth for the repair agent, source tracking for the research agent, freshness for the remediation agent, and prefix reuse across short sessions for the support agent. As a result, a policy tuned for one workload rarely transfers directly to another. Compaction rules that keep a repair agent within its token budget do not solve the main risk of a research agent, where untrusted external text matters far more than transcript length.

Every one of these budgets governs *admission*, ensuring that a serialized payload fits inside the provider’s context limit, yet admission alone does not mean the prompt supports the next decision. A prompt can obey the budget while omitting the return path needed to write a patch, or it can include every relevant code excerpt while burying version boundaries under old error logs. Sizing a context budget is therefore only the first step; the runtime must also ask how well the model can find and use the tokens admitted into that window.
