*Why can an agent lose the thread of a task even when its entire history still fits?*

An agent’s context window is a finite and expensive resource, not an unbounded repository for raw text. Naively accumulating tool outputs, conversational turns, and retrieved snippets exhausts token capacity, inflates prefill latency, and spreads attention across material the next decision does not need. Fitting is not the same as being usable. A request that fits can still place a refuted hypothesis beside the test that refuted it, or present a result from an earlier revision as a fact about the current one. Effective context engineering treats each request as a deliberately selected working set, in which relevant state is compacted without losing its provenance, superseded observations are withdrawn, and bulky artifacts stay in durable storage behind handles. Stale or truncated evidence that does reach the model produces errors that compound across later turns. The systems challenge is to carry an accurate, minimal projection of the environment within the token budget, so that the state an agent carries bounds its uncertainty rather than compounding it.

**Learning Objectives**

- Distinguish nominal request capacity from usable working context and explain why admitted tokens dilute needed evidence
- Allocate the next request’s input budget while preserving output headroom and task-relevant evidence
- Design a context layout that orders entries by change rate for prefix reuse and binds each observation to its evidential scope
- Compare compaction policies by information loss, recovery requirements, and the cost of repeated transformations
- Audit a progress record against runtime-owned sources and quantify how unchecked per-round constraint loss compounds across compaction cycles
- Apply dependency-aware invalidation without treating historical observations as proof of current state
- Evaluate context policies by decision quality, accepted outcomes, and total resource use under common limits
