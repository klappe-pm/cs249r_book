# V3-04.05 Staging the Next Invocation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-staging

In our connection-pool repair task, the selected manifest holds several distinct kinds of material: public API constraints, source excerpts from `src/pool.py` at revision `r17`, test results from `test_waiter_notified_on_return`, and the missed-notification working hypothesis alongside an abandoned timeout explanation. Concatenating these items into a flat, unlabeled string would blur the distinctions that guide the model’s next decision. Once a selection policy chooses the working set for an upcoming call, staging turns those entries into a structured request payload. That assembly step records the source, authority, and revision of every item so the model can tell policy instructions apart from test observations and working hypotheses, while ordering the content to minimize token churn across consecutive calls.

### Ordering by Change Rate

^sec-vol3-context-engineering-change-rate-ordering

Minimizing token churn across calls means ordering the prompt by how often each piece of context changes, placing stable material ahead of volatile updates. This layout partitions the serialized prompt into three regions: the **root**, the **trunk**, and the **leaf**, which group content strictly by its update cadence during a trajectory rather than by message role or authority ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^tbl-vol3-context-zone-stratification|table 4]]). In the repair scenario from notebook [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-evidence-budget), the root holds 3,000 tokens of system instructions and 12,000 tokens of tool declarations. The trunk holds 24,000 tokens of evolving task state, and the leaf receives 8,000 tokens of newly staged observations.

| Zone  | Contents in the repair request                                                                                           | When it changes                                                                       |
|:------|:-------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------|
| Root  | Application instructions and available tool definitions                                                                  | The application contract or tool interface changes                                    |
| Trunk | Task constraints, the current progress record, and selected source and test content at `r17`                             | A task constraint changes, an artifact is edited, or the progress record is refreshed |
| Leaf  | The latest scoped test observation and the next bounded step, here proposing a candidate change to the notification path | New evidence or a new next-step decision arrives                                      |

Table 4: **Context ordered by change rate**: The zones help preserve a stable request prefix. Message roles and source metadata remain separate from these placement choices.

^tbl-vol3-context-zone-stratification

Prefix stability must never override correctness. The root stays fixed only while its declarations remain accurate; if a tool definition changes during a session, the runtime updates the root on the next call and accepts the cache miss. Likewise, when a candidate patch advances the repository from `r17` to `r18`, the runtime cannot keep `r17` source code in the trunk just to keep the prefix warm. The earlier test failure remains valid historical evidence about `r17`, but checking whether it persists on the patched workspace requires a fresh run ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-context-rot|section 4.7]]).

Information can also move between zones as a trajectory advances. An observation first staged in the leaf can fold into the trunk’s progress record during a scheduled refresh so long as its source, version, and scope stay attached. Conversely, a per-step instruction injected into the leaf keeps its full authority despite sitting at the end of the prompt. Zone placement sets the physical order of tokens to match their change rate, whereas schemas and message roles carry provenance and meaning.

### Preserving Source and Scope

^sec-vol3-context-engineering-source-scope

As observations move from the leaf into the trunk or across compaction passes, each entry must keep the revision and execution conditions that produced it so the model does not read a local result as a universal fact about the codebase. For our failing test case, the host runtime attaches the test name, the workspace revision (`r17`), the test configuration, and a run identifier directly to the observation payload. This discipline enforces the **scope rule**:[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn5|⁵]] an observation supports claims only for the artifact versions and execution conditions under which it was gathered, and every later context transformation (summarization, compaction, and invalidation alike) must preserve those bounds.

The runtime builds this framing on the outside rather than reading it from text inside the observation. A serializer places raw tool output strictly as a literal data value inside a structured envelope so that mismatched quotes, markdown delimiters, or control characters cannot corrupt the surrounding schema. Even with that framing, the payload itself remains an **untrusted span**: arbitrary text whose arrival the runtime can record, but whose claims it cannot vouch for. In a traditional parser, escaping quotes keeps a string literal out of the executable syntax tree. A language model, by contrast, processes the framing tags and the escaped data string inside them as one sequence of tokens in the same attention pass. Careful encoding therefore stops format injection at the host serializer, yet it cannot stop the model from attending to and following adversarial instructions hidden inside the text ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-greshake2023not|Greshake et al. 2023]]).

Provenance labels therefore guide interpretation rather than enforcing security. Marking a tool output as untrusted data helps the model weigh its source, but if an observation tells the agent to drop a database or overwrite production credentials, the model may still propose that call. Security boundaries (filesystem sandboxes, read-only mounts, and deployment blocks) must run in host code outside the model’s prompt interpretation: staging keeps instructions and observations distinct in the request, while host gates enforce what may run.

↪ The host-side information-flow policy that limits what untrusted context may influence and where private data may flow is enforced in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^sec-vol3-security-taint-tracking|Information-Flow Policy]]**.

How much weight this distinction carries depends on the workload. The repair agent’s observations come mostly from its own workspace, whose files change only when the agent or its tests change them. The research agent fills its requests with third-party text, so its ${S_{\text{obs}}}$ consists mostly of untrusted spans (lighthouse [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#lhs-04-context-by-archetype)). For that workload the untrusted-span boundary, not token growth, is the binding concern. Once each entry’s source and scope are framed, the serializer must emit the root and trunk in a repeatable token sequence so the serving engine can reuse their cached attention state.

### Preserving an Exact Prefix

^sec-vol3-context-engineering-exact-prefix

Because causal self-attention computes each token’s keys and values from all preceding tokens, a single changed token near the beginning of a request invalidates the cached key-value (KV) attention state for every later position, even when thousands of trailing tokens are identical. Serving engines equipped with prefix caching[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn6|⁶]] skip redundant prefill computation only across an identical leading token sequence, because attention state is derived from the token prefix (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-prefix-coherence|5]]). Ordering the zones by change rate is what turns this rule into savings. A call that changes only the leaf reuses the root and trunk, whereas a compaction that rewrites the trunk ends reuse at the root boundary and forces recomputation of every later token ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^fig-vol3-context-zones|figure 3]]).

![[90 Assets/Volume III/04 Context Engineering/Context Staging Layout f2575e641d.svg]]

Figure 3: **Reuse Ends at the First Changed Token**: Three consecutive requests follow the root, trunk, and leaf order of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^tbl-vol3-context-zone-stratification|table 4]], with the output reserve ${K_{\max}}$ beyond the input limit ${S_{\max}}-{K_{\max}}$. A new observation changes only the leaf, so the root and trunk remain a reusable prefix. Refreshing the trunk to r18 moves the first changed token to the end of the root, and every later token is processed again. The figure assumes compatible cached state on the serving side; an identical prefix alone does not guarantee reuse.

^fig-vol3-context-zones

Cache equality depends on the final serialized token sequence rather than on high-level application state. Small serialization changes (JSON key order, whitespace padding, prompt template edits, or token merges across boundaries) can quietly alter the token stream. For example, byte-pair encodings (BPE) often merge trailing whitespace with the leading characters of the next string, producing different token IDs at zone joins. Prefix stability must therefore be checked on the assembled, tokenized wire request.

An identical token prefix is necessary for cache reuse, but it is not sufficient on its own. The serving engine must also still hold compatible cache blocks in accelerator memory under the same model weights, positional encoding offsets, and attention configuration. Memory pressure, LRU eviction, or cluster autoscaling can drop cached blocks between turns even when the request prefix is byte-for-byte identical. While the serving engine manages and evicts those internal tensors, the agent runtime is responsible for keeping static material in a repeatable prefix and refreshing whatever state the next decision requires.

↪ Prefix compatibility and the retention and eviction of cached KV blocks in the serving engine are developed in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kvcache-radix-tree|Prefix Caching Across Turns]]**.

Placing fast-changing metadata near the start of a request forfeits prefix reuse for no benefit, whereas moving per-call fields (request IDs, wall-clock timestamps, step counters) into the leaf preserves reuse across the root and trunk. Whenever an early field changes, cache sharing stops at the first differing token. Consider the extreme case where the first token changes on every call, which bounds the extra cost of putting volatile fields at the front of a request.

**Napkin Math 4.2: Pricing a context layout across one trajectory**

**Problem**: The repair agent of notebook [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-evidence-budget) runs its full 30-turn step budget under the selecting policy, making one call per turn. Each request carries a 15,000-token root of instructions and tool declarations, a 24,000-token trunk of task state, and an 8,000-token leaf of selected observations, measured after serialization. The leaf is replaced on each call rather than appended, and the trunk is rewritten on 2 calls after the first, one for each compaction pass that notebook [4.3](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-compaction-cadence) finds this step budget triggers. Input tokens cost a hypothetical \$3 per million tokens, with cached reads billed at 10 percent of that price. What input bill follows from each layout?

**Variables**: Both layouts send 47,000 tokens per request and 1,410,000 input tokens across the trajectory, matching the selecting policy budget from notebook [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-evidence-budget). In the unstable layout, the first token changes on every call and no prefix is reused. In the stable layout, the first call is cold, the 2 trunk rewrites first differ right after the root, and the remaining 27 calls first differ right after the trunk, with compatible cached state kept for every matching prefix. This calculation isolates input token pricing, omitting generation charges and cache storage fees.

**Math**: The unstable layout processes all input without reuse, billing \$4.23. In the stable layout, the initial cold call processes the whole request, each trunk rewrite prefills the trunk and leaf, and every warm call processes only the leaf, for a total uncached volume of $47{,}000 + 2 \times 32{,}000 + 27 \times 8{,}000 = 327{,}000$ tokens. The remaining 1,083,000 tokens hit the prefix cache (76.8 percent of all input tokens). Billing uncached tokens at full price and reused tokens at the discounted rate gives \$1.31 for the trajectory.

**Result**: Average input cost drops from \$0.141 per call in the unstable layout to \$0.044 in the stable layout. An unstable layout bills 3.2× the stable layout and requires 4.3× more uncached prefill tokens. These figures are billing and token-volume ratios, not end-to-end execution speedups.

**Systems insight**: With a stable prefix, the size of the volatile leaf sets the marginal input cost of each warm call, whereas rewriting the trunk prefills 32,000 tokens, the cost of 4 leaf-only calls. Engineers should keep per-call dynamic fields in the leaf and rewrite the trunk only when workspace files or active task constraints change. That discipline lowers the input share of attempt cost in ${C_{\text{eff}}}$ by the ratio above, while keeping task accuracy (${p_{\text{acc}}}$) intact because the staged context still reflects current environment state. A high cache hit rate never justifies keeping stale context.

**Checkpoint 4.1: Checking the staged request**

A candidate patch has just moved the workspace from `r17` to `r18`, and the runtime is staging the next request.

**Provenance after promotion**: If a test result moves from the leaf into a refreshed progress record, what source, version, and scope must remain attached to it?

**Volatile fields**: Why does a changing field near the start shorten prefix reuse without necessarily eliminating it, and where should a per-call request identifier go?

**Trunk refresh estimate**: With the layout notebook’s zone sizes, how many uncached input tokens does the trajectory pay if the trunk is rewritten on every fourth call after the first instead of twice? Compare the result with the unstable layout’s count.

**Stale trunk**: After the source changes from `r17` to `r18`, why is keeping the old source in the trunk an incorrect optimization even when it raises the hit rate?

Staging puts the selected evidence into a clear schema and an order built for prefix reuse, yet ordering alone does not shrink long tool outputs: an oversized test log or large source file still takes its full share of the budget. When the needed working set outgrows the available budget, the runtime must shorten the representation itself while keeping the evidence later decisions need.
