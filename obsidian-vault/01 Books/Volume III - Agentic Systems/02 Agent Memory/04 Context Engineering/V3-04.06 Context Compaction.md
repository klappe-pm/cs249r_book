# V3-04.06 Context Compaction

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-compaction

As the connection-pool repair runs across turns, it accumulates repeated source listings, boilerplate test-setup output, and long execution traces. Keeping every line in every prompt uses space that later turns need for patch inspection and regression checks. Yet collapsing that trace into a bare note like “the test failed” drops the clues that matter: which revision failed, which thread schedule ran, and which assertion tripped. Compaction must shorten the working context without erasing the causal links future decisions rely on.

**Definition 4.2: Context compaction**

***Context compaction*** replaces material in a working context with a shorter representation chosen for the task’s next decisions.

1.  **Significance**: It creates room for new observations inside the fixed input allowance ${S_{\max}}-{K_{\max}}$, allowing an agent trajectory to run past the turn at which appending would overflow while retaining critical evidence, constraints, and unresolved obligations.
2.  **Distinction**: A compressed representation is inherently lossy or access-deferred. Keeping a handle to omitted material makes recovery conditional on an explicit retrieval step.
3.  **Common pitfall**: Assuming that a deterministic extractor, or a summary mentioning all required field names, guarantees that no decision-critical information was lost.

### Choosing a Compaction Method

^sec-vol3-context-engineering-compaction-method

A regular-expression filter trims log lines deterministically, but it can drop the one line that explains an intermittent fault. A source-code outline keeps API signatures while stripping the locking logic needed to spot a missed wakeup, and an LLM-written summary can preserve high-level diagnostic intent while inventing details or misstating whether a check passed.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn7|⁷]] Different compaction methods thus trade token savings against validation work and the risk of silent information loss in different ways, and no single method fits all runtime data.

The right representation depends on the next step: checking an interface takes only an outline, whereas debugging a race condition requires full function bodies and thread-interleaving logs. Each option in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^tbl-vol3-compaction-spectrum|table 5]] is therefore defined by what it keeps in the request and what the runtime must check, rather than by a fixed reduction ratio.

| Representation                    | What remains in the request                                             | What must be checked                                                                           |
|:----------------------------------|:------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------|
| Normalized or deduplicated text   | Selected text with repeated output or formatting removed                | Whether repetition, ordering, timing, or formatting carries task evidence                      |
| Tool-result digest and raw handle | Status, selected evidence, source identity, and a retrieval reference   | Whether the digest supports the next decision and the omitted payload remains accessible       |
| Deterministic extraction          | Matched log records, selected fields, source excerpts, or code outlines | Whether the extraction rule omitted relevant context, relationships, or implementation details |
| Model-written summary             | A generated account of observations, hypotheses, and progress           | Whether each retained claim is supported and required details and uncertainty remain explicit  |

Table 5: **Compaction representation choices**: Trade-offs between prompt reduction, residual prompt contents, and the downstream validation required to prevent silent information loss.

^tbl-vol3-compaction-spectrum

The first three classes in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^tbl-vol3-compaction-spectrum|table 5]] use deterministic rules that run in host code without calling a language model. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^tbl-vol3-compaction-techniques|Table 6]] breaks those three rows into the concrete techniques a runtime builds and asks what specific evidence each one can drop without raising an error. Deterministic filtering guarantees repeatable output, but it cannot guarantee that the remaining lines suffice for the task; a filter is safe only when later decisions do not depend on what it cut.

| Technique                              | What it keeps                                                        | What it can silently drop                                            |
|:---------------------------------------|:---------------------------------------------------------------------|:---------------------------------------------------------------------|
| Repeated-poll deduplication            | One copy of an unchanged status output and a repetition count        | A brief change between polls, or the timing of repetitions           |
| Terminal-control stripping             | Plain text without escape codes, progress redraws, or spinners       | Timing or ordering signals carried only by the redraws               |
| Diff hunk folding                      | Changed lines, their location, and a marker for unchanged context    | Surrounding code needed to judge whether the change is correct       |
| Superseded-read replacement            | A pointer from an old file read to the edit that replaced its source | Old text a later decision needs to explain what changed              |
| Head, tail, and failure-marker slicing | Setup lines, final lines, and lines matching failure patterns        | An intermediate warning or event ordering that matches no pattern    |
| Source outline                         | Signatures, types, and docstrings, with bodies folded                | The implementation a repair must read, such as the notification path |
| Tool-result digest                     | Status, exit code, payload size, and a handle to the retained output | Every detail of the payload until the handle is retrieved            |

Table 6: **Deterministic compaction techniques**: Specific evidence dropped by programmatic pruning methods. The trace in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^lst-vol3-compaction-observation|listing 1]] demonstrates how naive failure-marker slicing discards the causal ordering behind a test failure.

^tbl-vol3-compaction-techniques

Lossless byte compression offers no shortcut for fitting a large payload into the prompt. Decompressing the bytes before inference still spends the full uncompressed token count against the window, whereas passing compressed bytes or encoded text directly to the tokenizer splits high-entropy byte streams into fine-grained tokens that the model cannot interpret as source code or logs. The alternative that loses nothing is the handle rule from the working-set decision, which pairs a digest in the request with a handle to the retained payload. The raw payload stays in an external artifact store, and the cost of that choice falls on the later step that needs the payload, which pays a read’s latency and the tokens of whatever it brings back. In our connection-pool repair task, running the controlled regression test at revision `r17` produces the log excerpt in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^lst-vol3-compaction-observation|listing 1]] (with repeated polling lines already stripped).

``` text
source=src/pool.py@r17 test=tests/test_pool.py@r17
test_name=test_waiter_notified_on_return
configuration=controlled waiter-before-return schedule
... repeated worker progress messages ...
waiter_registered_before_return=true
connection_available_after_return=true
waiter_resumed_at_notification_check=false
FAILED: assert waiter_resumed_at_notification_check
```

Listing 1: **Observation before compaction**: The event ordering and failed assertion together identify what the controlled test observed at r17.

^lst-vol3-compaction-observation

A simple filter that keeps only lines matching `FAILED` captures the final assertion failure while dropping the event sequence that explains it. Without seeing that `waiter_registered_before_return` and `connection_available_after_return` both evaluated to true, the model cannot tell whether the failure came from a registration race, an exhausted pool, or a missed notification. A compact, structured digest keeps that causal chain intact: “At `r17`, `test_waiter_notified_on_return` registered the waiter before returning a connection. The connection became available, but `assert waiter_resumed_at_notification_check` failed at the notification check.” Alongside this digest, the context keeps the revision tags (`src/pool.py@r17`, `tests/test_pool.py@r17`), the test schedule, and a handle to the full trace for on-demand inspection.

This short record supports the missed-notification hypothesis under the tested conditions while keeping measured facts separate from diagnostic guesses. When a candidate patch produces revision `r18`, the runtime records the new test outcome against `r18` rather than overwriting or merging it with the `r17` failure. Collapsing both runs into an unqualified note such as “the bug is fixed” would erase the provenance needed to check what the patch actually changed.

### Protecting Task-Scoped Fields

^sec-vol3-context-engineering-protected-fields

Keeping that provenance intact across compaction passes requires naming which fields a pass is never allowed to drop. In the connection-pool trace, losing the source revision (`pool.py@r17`), the test name (`test_waiter_notified_on_return`), or the concurrency schedule leaves the next turn without the conditions needed to reproduce the fault. The runtime therefore defines a set of **protected fields** that must survive every compaction transform, and checks before committing an updated working context that those fields remain present and unchanged. Alongside test identity, revision, scheduling flags, failed assertion, and exit status, global task constraints stay pinned as well: preserving the public API, keeping edits inside the approved repository directory, and blocking production deploys. Specific function bodies or configuration lines omitted from the digest can then be paged back in through handles when a later step needs them.

Which fields need protection depends on the current phase of the task. Pinning every historical line number, diff hunk, and identifier defeats compaction by filling the budget, whereas a rigid boilerplate schema can drop the exact relationship a task hinges on, such as an assertion message detached from its commit hash or concurrency schedule. At the same time, runtime filters must scrub credentials, tokens, and private keys so that secret strings are never kept merely because they matched a literal-retention rule.

Protected fields are not limited to static parameters known at the start of a run, because agents often uncover new conditions during execution. Suppose our concurrency reproducer fails reliably under the controlled `waiter-before-return` schedule but passes most of the time under the default operating-system thread scheduler. That dependency does not appear in the initial task prompt; it emerges only in tool output. A summarizer that records “the waiter test failed” while dropping the schedule flag lets a later turn rerun the test under the default scheduler, see a chance pass on broken code, and declare the repair done. Whenever tool output shows that an outcome depends on a run parameter, the runtime promotes that parameter into the protected-field set alongside the observation it qualifies, subjecting it to the same checks as the original contract constraints.

Automated checks catch missing test names, altered literals, or results attached to the wrong revision, though schema checks alone cannot prove that the inventory covers every needed fact or that the model will use what survives ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^sec-vol3-context-engineering-evaluation|section 4.8]]). Before evicting any raw payload, the runtime records what happened to the omitted material: either it is no longer needed, it stays reachable behind a handle, or it has been permanently dropped and leaves an explicit gap in the context. If a later step needs an evicted detail and retrieval fails, the agent must rerun the tool or report the gap rather than making up plausible history.

### Scheduling Compaction Within the Request Budget

^sec-vol3-context-engineering-compaction-scheduling

Because each compaction pass folds new leaf observations into the trunk’s progress record, compacting after every small tool output would rewrite the trunk on every turn and forfeit prefix reuse across the trajectory. To avoid paying that trunk-rewrite cost on every step, runtimes separate the trigger threshold from the post-compaction target length. This two-threshold rule, **hysteresis**,[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn8|⁸]] lets observations build up in the leaf over several turns before the runtime rewrites the trunk. A narrow gap between the two watermarks causes frequent, costly rewrites, whereas a wider gap lets the agent run longer between passes at the cost of deeper compression when a pass finally triggers. Sizing the gap balances token headroom against information loss: compressing too far risks stripping needed detail, while compressing too little causes thrashing.

Let ${S_{\text{high}}}$ and ${S_{\text{low}}}$ denote the upper trigger threshold and the post-compaction target, measured in total serialized input tokens. Because the runtime must keep room for generation, these watermarks obey ${S_{\text{low}}} < {S_{\text{high}}} \le {S_{\max}} - {K_{\max}}$, where ${S_{\max}}$ is the context window limit and ${K_{\max}}$ is the reserved output allowance. Both thresholds are runtime policy choices rather than physical model limits.

In an idealized cycle where each compaction pass resets the request to ${S_{\text{low}}}$ and each turn adds ${\Delta S_{\text{turn}}} > 0$ net input tokens, the runtime checks the request length after each addition before calling the model. The integer number of turns between compaction passes is

$$
{n_{\text{cycle}}} = \left\lceil \frac{{S_{\text{high}}} - {S_{\text{low}}}}{{\Delta S_{\text{turn}}}} \right\rceil. \tag{3}
$$

^eq-vol3-hysteretic-compaction-cadence

![[90 Assets/Volume III/04 Context Engineering/Ch04 Compaction Sawtooth 0941e1e189.svg]]

*A blue sawtooth of request length over turns 1 to 30 climbs from a dashed low line to a dashed high line, where a red dot marks each compaction and the line drops back to low. A solid red limit line sits above the high line.*

*Hysteresis turns compaction into a sawtooth whose gap sets the cadence.*

Because context length is checked at turn boundaries, the serialized length just before compaction is ${S_{\text{low}}} + {n_{\text{cycle}}}{\Delta S_{\text{turn}}}$, which can overshoot ${S_{\text{high}}}$ by up to ${\Delta S_{\text{turn}}} - 1$ tokens. That possible overshoot makes ${S_{\text{high}}}$ a soft threshold: when tool outputs vary widely in size, the runtime must either trim oversized observations or stage them behind handles so a single large output cannot cross the hard ceiling ${S_{\max}} - {K_{\max}}$. If the runtime calls a model to write the summary, that compaction call also needs its own input and output budgets.

Compaction directly affects prompt-cache spend. A pass that rewrites the trunk invalidates cached KV blocks from the end of the root onward, incurring the trunk-prefill cost shown in Call ${n}+2$ of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^fig-vol3-context-zones|figure 3]]. Over a cycle of ${n_{\text{cycle}}}$ task turns and one compaction pass, let ${{C_{\text{call}}}}_{{i}}$ be the total cost of task turn ${i}$ (cached and uncached input tokens plus generated output tokens). Let ${C_{\text{comp}}}$ be the full cost of the compaction pass under the same billing rules. The amortized cost per task turn is

$$
{\bar{C}_{\text{turn}}} = \frac{\sum_{i=1}^{{n_{\text{cycle}}}} {{C_{\text{call}}}}_{i} + {C_{\text{comp}}}}{{n_{\text{cycle}}}}. \tag{4}
$$

^eq-vol3-hysteretic-compaction-cost

Any cache misses caused by rewriting the trunk already appear in the uncached token charges of the following ${{C_{\text{call}}}}_{{i}}$ terms, so adding a separate cache-invalidation penalty would double-count them. Beyond prompt tokens, a full cost comparison must also count external storage, handle-retrieval latency, repeated checks, and runs that fail because needed context was dropped too early. A schedule that minimizes per-turn token spend ${\bar{C}_{\text{turn}}}$ can still raise the effective cost per accepted task (${C_{\text{eff}}}$) if heavy compression sends the agent down dead ends. The watermark gap $({S_{\text{high}}} - {S_{\text{low}}})$ sets ${n_{\text{cycle}}}$ and therefore how many turns share ${C_{\text{comp}}}$.

**Napkin Math 4.3: Spacing compaction passes**

**Problem**: The repair agent from notebook [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-evidence-budget) appends each 4,000-token tool result and compacts instead of overflowing. Its 128,000-token context window, minus the 8,000-token output reserve, leaves 120,000 tokens for serialized input. Each compaction pass resets the prompt back to 47,000 tokens (matching the baseline selecting policy’s request size), and the next pass triggers at 92,000 tokens. How often does compaction run, and how many passes does the agent execute across its 30-turn step budget?

**Variables**: Every compaction pass resets the prompt to the target ${S_{\text{low}}}$, and per-turn additions ${\Delta S_{\text{turn}}}$ stay constant at 4,000 tokens. The runtime checks request length after each tool addition before calling the model. The watermarks are runtime policy settings rather than hardware limits.

**Math**: Applying [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^eq-vol3-hysteretic-compaction-cadence|equation 3]] gives ${n_{\text{cycle}}} = \lceil (92{,}000 - 47{,}000) / 4{,}000 \rceil = 12$ additions between compaction passes. The request reaches the trigger at 95,000 input tokens, overshooting ${S_{\text{high}}}$ by 3,000 tokens, and adding the output reserve brings the total to 103,000 tokens, still inside the window before compaction runs. Across the 30-turn step budget, the runtime runs 2 compaction passes, each rewriting the trunk. Those are the two trunk rewrites priced in notebook [4.2](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-quantitative-impact-of-prefix-layout), where the leaf was replaced on every call rather than growing between passes. Raising the post-compaction target to 81,000 tokens under the same arrival rate shrinks the interval to 3 additions.

**Systems insight**: Compaction frequency grows with the token arrival rate divided by the watermark gap, so narrowing the gap from 12 arrivals to 3 triggers compaction 4× as often and raises the per-turn compaction overhead in [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^eq-vol3-hysteretic-compaction-cost|equation 4]] by the same factor. Setting a gap smaller than a single turn’s arrival causes thrashing by compacting on every step. Designers should size the gap to span several arrivals and compress toward ${S_{\text{low}}}$ only as far as protected-field rules allow, testing on real tasks where the line between needed context and removable detail lies.

A shortened observation captures only one piece of the repair’s state; finishing the task also requires carrying forward the current candidate patch, the checks already run on it, the remaining test obligations, and the next bounded step. Because free-form prose summaries easily blur those links during compaction, the runtime keeps them in a structured progress record.
