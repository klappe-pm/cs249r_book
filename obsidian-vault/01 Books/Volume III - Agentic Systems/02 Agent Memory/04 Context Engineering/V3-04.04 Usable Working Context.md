# V3-04.04 Usable Working Context

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering|V3-04 Context Engineering]]

^sec-vol3-context-engineering-physics

In notebook [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-evidence-budget), the 128,000-token window admits the investigation’s full transcript for its first 20 turns, yet fitting an entire history inside the window does not mean the runtime should send all of it. What matters is what each item contributes to the pending decision: an omitted synchronization contract can ruin a proposed repair, whereas ten pages of repeated timeout speculation only add noise. Raw request length cannot separate essential evidence from distraction.

The **nominal context capacity** is the maximum sequence length that the configured model interface accepts under its input and generation limits. How well the model reasons over a chosen set of instructions and evidence is a separate question, answered only by testing concrete tasks against explicit quality criteria (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-attention-working-set|4]]).

**Definition 4.1: Usable working context**

***Usable working context*** is the context content, organization, and length with which a specified model and invocation configuration meet a chosen quality criterion on a stated workload.

1.  **Significance**: Usable working context, rather than the nominal window, determines how much of the input allowance ${S_{\max}}-{K_{\max}}$ effectively supports decisions. It dictates how many turns an execution trajectory can sustain before selection or compaction must intervene, directly setting the input token cost per accepted task in ${C_{\text{eff}}}$.
2.  **Distinction**: Nominal capacity is an architectural boundary of the serving interface that admits a request; usable working context is an empirical property of a task, model, and representation that only evaluation can establish.
3.  **Common pitfall**: Treating a fixed fraction of the nominal window, or success on an isolated synthetic retrieval probe, as a universal guarantee of usable context for a production workload.

For a software repair workload, that criterion might require candidate patches to pass designated regression tests while staying within a permitted edit scope, whereas an information extraction workload requires high precision and recall against a target schema. Because failure modes differ across workloads, usable working context must be measured on each workload rather than read off the model card.

### Testing Usable Working Context

^sec-vol3-context-engineering-usable-context-test

Testing whether a context length is usable starts with what the task asks the model to do with the staged text. A model that scores nearly perfectly on an isolated retrieval probe[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn3|³]] by finding a single planted fact in a long input can still fail a repair decision at the same length. The repair requires relating observed symptoms to source files, honoring API invariants, and separating a measured failure from an unverified hypothesis ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^tbl-vol3-capacity-comparison|table 3]]). Synthetic retrieval probes quickly flag gross blind spots, but validating a context policy requires testing actual task decisions under realistic conditions.

| Test obligation           | Isolated key-retrieval probe                        | Connection-pool repair decision                                                                               |
|:--------------------------|:----------------------------------------------------|:--------------------------------------------------------------------------------------------------------------|
| Identify relevant content | Return the requested planted value.                 | Find the source, test conditions, and observation relevant to the notification path.                          |
| Interpret relationships   | Match the queried key to its value.                 | Tie the failure to `r17` and distinguish the missed-notification hypothesis from the observed blocked waiter. |
| Respect task constraints  | Meet the probe’s answer requirements.               | Propose a scoped change while preserving the public API and leaving untested behavior unresolved.             |
| Establish success         | Compare the returned value with the probe’s target. | Apply the chosen candidate checks and scope criteria; report only what they establish.                        |

Table 3: **Retrieval and decision scope**: A simple retrieval probe and the running repair example test different capabilities.

^tbl-vol3-capacity-comparison

Context organization directly affects task success even when all required facts are present in the prompt. Evaluating multi-document question answering and key-value retrieval, Liu et al. ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-liu2024lost|2024]]) reported marked sensitivity to the position of relevant information across model architectures, with accuracy dropping substantially when key facts appeared in the middle of the input. This position sensitivity, known as **lost in the middle**, means systems engineers cannot treat context as an unordered bag of tokens. Placement policies must be tested on the target workload, because how accuracy varies with position depends on the model family and prompt layout.

Length degrades comprehension even when every required fact remains in the input. One long-context benchmark isolates that effect by rewriting each of its stories at lengths from a few hundred tokens to the full text while preserving the details its questions depend on. A change in score across lengths therefore reflects the surrounding material rather than missing evidence ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-fictionlive2025bench|Fiction.live 2025]]). Answering requires following the order of events and drawing inferences from implicitly stated information, a task closer to a repair decision than to returning a planted value. [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^fig-vol3-context-length-comprehension|Figure 2]] plots the scores against the length of story in context, as aggregated by Epoch AI ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-epochai2026benchmarks|2026]]).

Two features of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^fig-vol3-context-length-comprehension|figure 2]] bear directly on the working budget: the decline starts early and runs deep, and models differ widely at any fixed length. Across the 53 fully scored models, the median falls from 100 percent on the shortest version to 58 percent at 8K tokens and 56 percent at 60K, with only 3 models staying at or above 90 percent at 60K. At 60K tokens, scores also span from 22 to 100 percent. This spread is the empirical content of the definition above. Usable working context belongs to a specified model, configuration, and workload, so the budget must be found by evaluation rather than read from the window.

A first-order mechanism explains why appending distractor tokens cannot be treated as free. Within an individual attention head, a query assigns weight to each visible key through a softmax operation ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-vaswani2017|Vaswani et al. 2017]]). For a target key with scaled logit ${z_{\text{target}}}$ alongside ${n}$ other keys with logits ${z}_j = {\mathbf{q}}\cdot{\mathbf{k}}_j/\sqrt{{d_{\text{head}}}}$ for head dimension ${d_{\text{head}}}$, the target’s weight is

$$
{\alpha_{\text{target}}} = \frac{e^{{z_{\text{target}}}}}{e^{{z_{\text{target}}}} + \sum_{j=1}^{{n}} e^{{z}_j}}. \tag{2}
$$

^eq-vol3-softmax-dilution

![[90 Assets/Volume III/04 Context Engineering/Vol3 Working Sets Margin 002 01bb8f1acf.svg]]

*Line chart of target attention weight from 0 to 100 percent against the number of keys, from few to many on a log scale. The curve starts near 100 percent at a green dot and falls to near zero at a red dot.*

*Fixed-logit distractors shrink the target’s share of one normalizer.*

All weights share a single normalizer. Because each additional key contributes a strictly positive term $e^{{z}_j}$ to the denominator of [[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.04 Usable Working Context#^eq-vol3-softmax-dilution|equation 2]], expanding the sequence length while holding logits constant depresses the target key’s share of attention. This structural decay is **attention dilution**. In a toy head with a target logit of 6 and every background logit at -2, the target commands 96.8 percent of the weight among 100 keys. When the context expands to 100,000 keys, that same target’s share falls to 2.9 percent, even though no single background key is individually competitive.

In agent execution, this effect is often worse than unrelated filler would produce.[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.15 Footnotes#^fn4|⁴]] Stale tool outputs, superseded logs, and earlier source reads share identifiers such as `waiter`, `connection`, and `timeout` with the evidence that matters, so they produce large inner products with query vectors and keep elevated logits. This dynamic is a sufficient condition for dilution under fixed logits, not a deterministic forecast of failure. Production models sharpen logits, route evidence across multiple attention heads and layers, and learn position-dependent retrieval behaviors, which is why Liu et al. ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-liu2024lost|2024]]) measured degradation empirically rather than deriving it analytically. Trained models also show a second consequence of the shared normalizer. Because the weights must sum to one, a query with no strong match deposits its leftover weight on the first few positions, which act as attention sinks regardless of their content ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.14 Source References#^ref-xiao2024streamingllm|Xiao et al. 2024]]). Sinks change where leftover weight goes, not the dilution argument, and every staged token still adds a term to the normalizer that the evidence for the next decision must compete against.

↪ Why cache eviction policies must retain attention-sink tokens is developed in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kvcache-intrasequence|Reclamation vs. approximation]]**.

### Choosing a Working Budget

^sec-vol3-context-engineering-working-budget

Sizing a working budget from the window’s admission bound alone can still leave a request too long for the model to use reliably. Choosing a working budget therefore takes two steps, and only the first can be computed from the window. In notebook [4.1](https://mlsysbook.ai/vol3/04_context_engineering/04_context_engineering.html#nbk-04-evidence-budget), the admission bound leaves 81,000 tokens for observations in any one request. An appending policy must hold each result to 2,700 tokens to last all 30 turns, whereas a selecting policy can spend up to that whole share on every request because it does not accumulate. The ceiling says what fits, not what the next decision can use, so the second step searches beneath it empirically.

To find that working point, engineers test complete context policies on representative task suites ([[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^sec-vol3-context-engineering-evaluation|section 4.8]]) and choose the budget that meets the workload’s quality criterion at the lowest effective cost. Because a context policy sets a token limit alongside what material is retrieved, how structured data is formatted, and where each piece sits in the prompt, decision quality must be weighed alongside input size, latency, and token spend. Additional context can supply needed grounding, add harmless noise, or degrade reasoning through dilution, which means the quality curve is rarely monotonic and seldom has a single sharp peak. A documented operating envelope must therefore name the workload, model configuration, quality threshold, and test conditions.

These choices carry direct resource consequences under model-call cost accounting. Uncached tokens add prefill latency and compute charges, whereas aligned prefix caching spreads prompt costs across repeated turns. High cache hit rates or discounted per-token prices mean little if stale context hurts decisions, yet pruning context too sharply to save prefill cost can strip away required constraints. The engineering goal is to meet the task quality bar at the lowest effective cost per accepted task, ${C_{\text{eff}}}$ (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**). Trimming unneeded tokens lowers the attempt cost in the numerator, whereas dropping a needed fact lowers the acceptance probability ${p_{\text{acc}}}$ in the denominator and drives up total spend across failed runs.

In the connection-pool repair example, keeping the full transcript of early exploratory turns wastes space once distilled test observations, code snippets, interface invariants, and active hypotheses are ready to guide the next patch. Stripping away a required interface contract or error log merely to fit an arbitrary sub-budget, however, is just as harmful. When no candidate policy meets both the task criterion and the available budget, the runtime must fetch the missing information, narrow the scope of the next permitted action, or report the limit. Passing a request-admission check never certifies that the staged context is adequate. Once the runtime selects that working set and bounds its token budget, it must arrange those items into a concrete prompt layout that keeps sources and evidence relationships distinct while separating stable prefix content from turn-by-turn updates.
