# V3-09.11 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09 Agent Security|V3-09 Agent Security]]

^sec-vol3-security-fallacies

Each of these design mistakes conflates evidence established at one operational boundary with authorization or trust at another. They persist because they readily pass superficial tests: a model successfully rejects a known exploit string, or an audit log records fewer observed disclosures. In each case, however, the runtime system’s true enforcement mechanisms, its evidence and release checks, remain unexamined.

**Fallacy**: *A guardrail classifier in front of the agent eliminates prompt injection.*

An input screening classifier is itself a learned function over text. Attackers can therefore evade it through paraphrasing, character encodings, or by splitting malicious payloads across multiple external documents and conversational turns ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-zou2023|Zou et al. 2023]]). An adaptive adversary optimizes prompts against the guardrail model just as systematically as against the agent itself. For example, EchoLeak passed a production classifier by formatting its malicious instructions as commentary addressed to the human reader (war story [9.1](https://mlsysbook.ai/vol3/09_security/09_security.html#ws-09-echoleak-2025)). Furthermore, multi-document agent workflows compound even negligible false-negative rates. A classifier that misses only 5 percent of individual malicious payloads still leaves 4.9 percent of research tasks exposed to at least one payload when the agent consumes 100 documents per task (notebook [9.1](https://mlsysbook.ai/vol3/09_security/09_security.html#nbk-09-injection-exposure)). Targeted attacker adaptation pushes this miss rate higher. Input screening filters low-effort noise and reduces the load on downstream controls, but architectural security depends on rigorous runtime release and evidence checks.

**Pitfall**: *Exempting read and search tools from disclosure checks.*

Systems engineers often assume that read and search operations are inherently safe because retrieving data leaves the remote index unmodified. However, every read request transmits query parameters, HTTP headers, or lookup keys across a trust boundary, making read-oriented tools effective channels for data exfiltration. In the hypothetical comparison of [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.10 Adversarial Robustness and Red-Teaming#^sec-vol3-security-evaluation|section 9.9]], which illustrates the method rather than measuring any system, an authorization policy that validated only the tool name and destination endpoint disclosed sensitive fixtures in 20 percent of attacked episodes. In contrast, enforcing an explicit release check on the data payload embedded within each query reduced the disclosure rate to 5 percent. Every outbound tool call is a potential communication channel; runtime policies must inspect the data entering each request and verify that its release to the specified destination is authorized.

**Fallacy**: *Safety post-training makes the model immune to injection.*

Safety alignment trains models to recognize and refuse overtly malicious requests, such as generating exploit code or hate speech. Indirect prompt injection, however, masks its malicious intent as an ordinary, benign step within an authorized task, such as formatting a database query or running a local diagnostic. An attacker directly exploits the model’s core instruction-following capability, deliberately pitting its helpfulness against its safety guardrails. Wei and colleagues identified these competing objectives as a primary cause of safety-training failures ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-wei2023jailbroken|Wei et al. 2023]]). While post-training can reduce attack success under standard benchmark protocols, fine-tuned weights cannot enforce a hard security boundary that the model itself cannot cross. Systems engineers must enforce authority delegation and data release checks within the execution runtime beneath the model.

**Pitfall**: *Cleaning retained state by deleting the raw injection.*

Deleting an offending input document or message from disk does not purge its influence from the agent. In multi-turn systems, intermediate inferences quickly propagate into summaries, distilled execution lessons, and queued tool proposals that preserve the attacker’s intent long after the raw injection is removed ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.09 Multi-Turn Attacks and State Persistence#^sec-vol3-security-multiturn|section 9.8]]). Remediating corrupted state demands rigorous provenance tracking: developers must withdraw the tainted source, trace its causal dependencies across every derived record, and treat the broader retained memory as suspect whenever those dependencies cannot be cleanly isolated.

**Fallacy**: *A valid scalar extracted by a separate reader is trusted evidence.*

Parsing unstructured model output into a typed scalar, such as the extracted boolean `claimed_tests_passed: true`, verifies syntactic structure rather than operational authenticity. Constraining data to a schema does not elevate an untrusted source into an authoritative one. Under the formal dispatch model of [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-dispatch|equation 3]], an assertion whose provenance traces to unverified external text lies outside the set of authorized influences. The runtime must reject such claims during evidence checking, no matter how cleanly structured the parser’s output appears. Authoritative evidence must originate directly from a designated execution runner and remain strictly scoped to the automated checks that runner independently conducted.

**Pitfall**: *Treating a lower attack-success rate as a complete security result.*

An empirical attack-success rate provides an incomplete measure of security on its own. The observed rate depends heavily on the adversary’s search budget, the target threat model, and the specific test harness configuration, all while omitting the operational costs imposed by the defense. In the hypothetical comparison of [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.10 Adversarial Robustness and Red-Teaming#^sec-vol3-security-evaluation|section 9.9]], an apparent 75 percent reduction in observed disclosures falls to 40 percent in the scenario where unresolved evaluation runs in both arms are disclosures. The least favorable comparative reduction instead uses the defended arm’s upper rate and the baseline’s confirmed lower rate. Furthermore, achieving that protection came with a 12.5 percent increase in cost per accepted benign repair. Observing zero successful attacks in a finite test suite does not close the question either: recording zero breaches across 100 trials still leaves an upper confidence bound as high as 3.0 percent. Robust evaluations must report statistical confidence bounds, account explicitly for unresolved outcomes, and measure benign task utility alongside attack mitigation.
