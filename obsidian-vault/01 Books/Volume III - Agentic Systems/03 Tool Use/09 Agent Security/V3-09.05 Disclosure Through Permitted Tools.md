# V3-09.05 Disclosure Through Permitted Tools

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09 Agent Security|V3-09 Agent Security]]

^sec-vol3-security-exfiltration

Because a network-enabled tool adapter transmits its request parameters before receiving any response, confidential test fixtures embedded in a `package_search` query leak beyond the repair boundary even if the remote lookup returns no match. Traditional access control models evaluate tool invocations by the operational actions they perform or the remote state they mutate, treating read and search calls as benign because they leave the remote service unchanged. Enforcing task confidentiality, however, requires tracing information flow through the tool request itself. The runtime must verify that `package_search` is an authorized operation and also that its outbound arguments carry only data permitted to reach the external recipient.

### Data Provenance and Recipients

^sec-vol3-security-data-recipients

At the schema level, a benign documentation lookup such as `package_search(query="connection pool timeout documentation")` and an injected proposal such as `package_search(query="dependency diagnosis PRIVATE_CASE_EXAMPLE")`, where `PRIVATE_CASE_EXAMPLE` comes from the confidential test fixture, look identical. Structurally, both arguments are well-formed strings that satisfy the tool parameter schema. The distinction lies in the provenance of the tokens within the second string and whether the destination service is authorized to receive that payload.

To catch this discrepancy before dispatch, the runtime must maintain explicit provenance metadata for data objects and outbound destinations. In this scenario, it records the fixture source identity, version hash, private confidentiality classification, and the specific subtask authorized to inspect it. The origin of an untrusted README file is an orthogonal tracking concern: it records the source of untrusted instructions entering the context, whereas the fixture classification records data confidentiality. An agent runtime must manage both dimensions simultaneously, recognizing that untrusted instructions from a public repository can steer how trusted, private data is used.

When the agent first reads the local fixture to diagnose a test failure, the runtime logs the operation in its policy record, capturing the file’s source identity, version, and private classification. That grant permits local inspection only. When the language model subsequently plans a `package_search` containing tokens derived from that fixture, the outbound query inherits the fixture’s confidentiality restriction under the runtime’s dependency policy. Before dispatching the HTTP request to the external search adapter, the runtime checks whether the destination holds an explicit release grant for that classified data. Because no such grant exists, the security monitor intercepts the call, records `rejected_before_dispatch`, and returns a bounded policy diagnostic that identifies the violated rule without echoing the sensitive content. The agent can then recover by issuing a documentation query built outside the fixture’s influence or by falling back to local analysis, preserving task progress without exposing private data.

Enforcing this boundary requires deterministic runtime tracking rather than relying on the language model to classify or redact its own outputs. A compromised model can easily disguise confidential data through paraphrasing, base64 encoding, or chunking values across multiple parameter fields. Simple string matching against known secret values fails against these transformations. Instead, the runtime must conservatively treat any output generated after ingesting confidential tokens as dependent on that private input; [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^sec-vol3-security-taint-tracking|section 9.6]] formalizes these propagation rules and their utility cost. As a defensive baseline, the runtime treats any value with missing or ambiguous provenance as restricted by default.

### The Lethal Trifecta

^sec-vol3-security-lethal-trifecta

The same failure path emerged in a major production assistant in 2025, where the attack payload arrived via email and the exfiltration endpoint hid behind a trusted domain. Rather than breaking out of a sandbox or stealing a token, the attack steered the model into assembling private context into an outbound request that every perimeter check allowed.

**War Story 9.1: EchoLeak: Zero-click disclosure through an allowed domain (2025)**

**Context**: Microsoft 365 Copilot answers a user’s questions by retrieving from that user’s mail, files, and chats into the model’s context. In 2025, Aim Labs disclosed EchoLeak, a chain that let an outside attacker extract data from that context with no action by the victim beyond ordinary use of the assistant ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-aimlabs2025echoleak|Aim Labs 2025]]). Microsoft tracked it as CVE-2025-32711 ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-msrc2025echoleak|Microsoft Security Response Center 2025]]).

**Mechanism**: The attacker sends the victim an email phrased as benign human correspondence, bypassing the service’s prompt-injection filters. When the victim later asks a related question, the retrieval pipeline pulls the malicious email into context alongside private documents and emails. The injected instructions then direct the model to render that private data within a Markdown link or image tag pointing to an attacker-controlled server. Reference-style Markdown, which defines a link’s URL on a separate line from the link text, bypassed the service’s external link redaction, while the image tag caused the client application to fetch the URL automatically. The client’s Content Security Policy, a browser allowlist of the domains a page may load from, would have stopped a fetch to the attacker’s server, so the attacker tunneled the exfiltration through an open redirect on a permitted Microsoft-hosted domain. An open redirect forwards a request to whatever URL a parameter names, so the allowed domain relayed the data onward. Aim Labs designated this vulnerability pattern a *large language model (LLM) scope violation*: untrusted external input manipulating an agent into exposing data that the untrusted author could never access directly.

**Impact**: Microsoft rated the vulnerability critical, describing it as AI command injection that allowed an unauthorized attacker to disclose information over a network ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-msrc2025echoleak|Microsoft Security Response Center 2025]]). Anything the assistant could retrieve for a question was within reach of one inbound email.

**Fix**: Microsoft mitigated the issue in the service; customers had no action to take ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-msrc2025echoleak|Microsoft Security Response Center 2025]]).

**Systems lesson**: Every bypassed defense targeted either superficial syntax or static channels: heuristic classifiers evaluated message text, a sanitization filter stripped standard URL syntax, and a network allowlist checked host domains. None of these mechanisms tracked data provenance. Halting this attack requires evaluating the flow of data to its recipient. Content derived from confidential context must never be emitted to an outbound endpoint selected or influenced by untrusted instructions.

EchoLeak and the package-search vulnerability share one topology, the **lethal trifecta** that the sandbox threat model named ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-willison2025lethal|Willison 2025]]): private data in reach, attacker-controlled content in context, and an outbound channel. Severing any one leg closes the exfiltration path. The GitHub MCP leak of **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.05 Interoperable Tool Discovery#^sec-vol3-tool-calling-discovery-authority|Discovery and authority]]** had the same shape with a public mutation tool in place of the outbound channel and ambient authority as the enabling condition. Containment severs legs by withholding reach. Executing tests inside an isolated runner lets the agent evaluate code against confidential fixtures without loading fixture bytes into the model’s context, and an egress boundary can strip network access from subtasks that need no external documentation. Containment cannot handle a workflow that genuinely needs all three legs at once. There, a dependency-and-recipient check before dispatch must arbitrate each outbound request, distinguishing legitimate local processing from release ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.05 Disclosure Through Permitted Tools#^fig-vol3-exfiltration-conjunction|figure 2]]).

![[90 Assets/Volume III/09 Security/Exfiltration Conjunction 99b1f58e66.svg]]

Figure 2: **Three Connections on One Disclosure Path**: The fixture disclosure needs private data in reach, attacker-controlled content, and an outbound recipient. Each dashed box weakens or removes one connection at some cost to useful work; when the task needs all three, the dependency and recipient check before dispatch decides whether the query may leave. The three connections describe this injection-driven path, not every possible leak or harm.

^fig-vol3-exfiltration-conjunction

Severing connections wholesale often incurs steep utility penalties. Withholding fixture contents prevents the model from diagnosing complex failure modes, while disabling search leaves the agent unable to resolve unfamiliar library interfaces. The private-data leg can be weakened without withholding the data, by letting tools name stored content that the planner never reads ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.06 Quarantined Readers and Ingestion Isolation#^sec-vol3-security-retained-content-handles|section 9.5.4]]), but a named fixture still carries its release restrictions. Implementing a dynamic release check at the dispatch boundary preserves the greatest degree of operational capability, provided the runtime reliably enforces data dependencies and recipient policies. These three conditions characterize injection-driven data exfiltration specifically. Destructive actions within a writable workspace, such as overwriting repository files, need no outbound recipient and must be contained by workspace sandboxing and filesystem permissions instead.

### Detectors and Canary Values

^sec-vol3-security-detectors-canaries

Before building a full provenance tracker, teams often try to guard the dispatch boundary by scanning outbound tool arguments with signature-based pattern matchers (such as regular expressions for API keys) or statistical entropy detectors. While these detectors help catch accidental credential leakage, they cannot substitute for authorization decisions. Sensitive application data frequently consists of standard natural language tokens rather than high-entropy strings, while valid cryptographic hashes or package digests routinely trigger false positives. More fundamentally, an attacker or a compromised model can evade heuristic filters through base64 encoding, synonym substitution, or splitting secrets across multiple benign-looking queries. Because syntactic appearance does not correlate reliably with semantic disclosure, the absence of an alert from a pattern detector cannot be treated as authorization to transmit data.

A complementary diagnostic tool is the **canary value**, a unique synthetic secret planted where an evaluation framework can observe whether it escapes. When a network egress monitor or external logging endpoint detects a canary token in an outbound request, it confirms that a specific execution path leaks information. However, canaries operate as reactive audit signals rather than proactive defenses; an alert firing after network transmission notifies operators of a breach that has already succeeded. Canary tokens are valuable for automated security evaluation and red-teaming benchmarks, but runtime prevention still requires intercepting requests and validating data recipients prior to dispatch.

Exfiltration policies must account for every possible egress channel, not merely primary tool adapters. Side channels such as DNS lookups, proxy redirections, and inter-process communication with host services can bypass application-layer tool filters entirely. The execution environment must confine all system processes within an enforced network sandbox. Network-level destination filters also prevent server-side request forgery (SSRF), blocking an agent directed to fetch external URLs from probing internal cluster endpoints or cloud instance metadata services (such as `169.254.169.254`). Network-level destination filters and application-level release checks are complementary controls. The network sandbox enforces structural limits on where packets can physically travel, while the release check governs whether sensitive data may be transmitted to an otherwise approved external service.

↩︎ Network sandbox confinement and egress boundaries are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^sec-vol3-sandboxes-network|Egress Control]]**.

Authorizing a tool invocation therefore requires evaluating the data its payload carries alongside the operation itself, with provenance metadata kept by the runtime outside the model’s context window. Detectors, canaries, and egress filters all act at the outbound leg of the trifecta, after the injected instruction has already entered the planner’s context and shaped its proposal. Detection only lowers the rate at which payloads get through, and each payload it misses still steers a planner that holds the task’s authority. Weakening the untrusted-content leg earlier in the trajectory requires keeping raw external text out of the privileged planner in the first place.
