# V3-09.06 Quarantined Readers and Ingestion Isolation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09 Agent Security|V3-09 Agent Security]]

^sec-vol3-security-quarantined-readers

When the repair task inspects a third-party README, the planner needs to know which test flags or version constraints the package documents, not the raw prose in which an attacker hid the fixture-exfiltration note. Allowing that raw prose into the planner’s context window exposes the reasoning loop that holds the task’s tool grants, even if an egress policy later blocks the resulting search request. Ingestion isolation narrows that exposure before planning begins: an isolated extraction stage reads the untrusted source and returns only the specific, task-relevant fields through a narrow schema, keeping free-form instructions away from the planner without converting untrusted assertions into verified facts.

A **quarantined reader** is a model invocation configured with an isolated input context and a strictly enforced result contract. The reader receives the source excerpt alongside an extraction request, but operates with zero execution authority: it holds no environmental credentials, possesses no tool definitions, and cannot dispatch actions. The primary planner receives only the validated extraction payload rather than the original raw document. Meanwhile, the runtime environment governs both interfaces, validating output schemas and enforcing reference-monitor policies on every action proposed by either model. This pattern generalizes the dual-model architecture proposed by Willison, in which a privileged model with tool access never reads untrusted inputs, while an unprivileged quarantined model reads untrusted text but cannot invoke tools ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-willison2023dual|Willison 2023]]). The CaMeL architecture extended this approach by attaching provenance and permitted-use metadata to every extracted value, validating that metadata against system policy before each subsequent tool call ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-debenedetti2025camel|Debenedetti et al. 2025]]). CaMeL calls this metadata capabilities, but it plays the role of the labels developed later in this chapter, not of a grant of authority to the agent. In both designs the planner reasons over structured claims whose metadata the runtime, not the reader, supplies, and every action it proposes still passes the reference monitor ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.06 Quarantined Readers and Ingestion Isolation#^fig-vol3-quarantined-reader|figure 3]]).

↩︎ Complete mediation of tool dispatch by a reference monitor is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.03 Tool Subsystem Architecture#^sec-vol3-tool-calling-complete-mediation|Complete mediation]]**.

### Context and Permission Separation

^sec-vol3-security-context-separation

When querying an external package document about test behavior, the runtime never passes private test fixtures, prior conversation history, or execution tokens to the reader. Restricting the prompt enforces data minimization: the reader receives only the isolated source text and the precise question to be answered. Furthermore, dispatching text to an inference endpoint constitutes an external data disclosure governed by the task’s egress policy. The runtime must verify that transferring the excerpt complies with confidentiality rules before initiating inference, even though the reader has no tool privileges.

The host runtime accepts only completed payloads conforming to the declared schema, discarding any emitted tool calls, shell commands, or extra JSON fields. Omitting tool declarations from the reader’s prompt informs the model of its role. The enclosing runtime adapter and access controls do the actual enforcement, because they provide no execution path from the reader’s output buffer to an operating system shell, local filesystem, or external network socket. Hard quotas on input tokens, generated tokens, and retry attempts also prevent pathological or adversarial documents from exhausting serving capacity.

Engineers sometimes assume that hosting the reader on physically isolated accelerators or separate clusters mitigates prompt injection. Physical hardware isolation, however, offers no defense against semantic injection attacks, because the danger lies in untrusted data manipulating the planner’s reasoning, not in memory corruption across tenant boundaries. As long as the runtime enforces distinct prompt contexts, isolated key-value caches, and strict privilege revocation, the reader and planner can safely share the same underlying model weights and serving infrastructure. What matters is the integrity of the data and the authority granted across the interface, not compute collocation.

### Extraction Field Semantics

^sec-vol3-security-extraction-semantics

Isolating the reader’s context still leaves the design of its output schema. If the system asks whether an untrusted README claims that tests pass, a boolean field named `tests_passed` conflates what the document asserted with what the test runner actually executed. Instead, an extraction schema must represent source assertions rather than establish ground truth, exposing an explicit field such as `claimed_tests_passed` with three states: `true`, `false`, or `null`. These values indicate that the reader detected an explicit passing assertion, detected a failing assertion, or found insufficient evidence in the excerpt to support either conclusion. Providing an explicit `null` state allows the model to signal ambiguity or missing information, though the model may still occasionally hallucinate certainty when it should report uncertainty.

When the reader returns a response, the host runtime applies the status-first rule of the invocation contract, admitting only a call whose normalized status reports a completed generation, and then validates the payload against its declared schema. Syntactically valid fragments harvested from truncated generations are discarded immediately. Missing required fields, unexpected object properties, or oversized string values trigger explicit validation errors and bounded retries. While constrained decoding eliminates low-level syntax errors during token generation, the host runtime remains the final authority for structural validation.

↩︎ The normalized call status and the rule that quarantines any payload from an incomplete generation are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-contract|The Invocation Contract]]**.

The host attaches provenance and governance metadata from its own tracking state rather than trusting labels emitted by the reader. [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.06 Quarantined Readers and Ingestion Isolation#^lst-vol3-reader-record|Listing 1]] illustrates an admitted ingestion record for an extraction that involves non-confidential source text. Here, `doc_v3` identifies a specific immutable document snapshot, distinguishing it from the repair workspace’s target revision `r18`. By recording the exact excerpt provided to the reader, the host creates an auditable record of the evidence supplied during the ingestion step.

``` json
{
  "host_metadata": {
    "task_id": "repair_42",
    "source_id": "readme_7",
    "source_version": "doc_v3",
    "reader_input": "selected_excerpt",
    "integrity_provenance": "untrusted_external",
    "confidentiality": "public",
    "record_kind": "document_claim"
  },
  "reader_output": {
    "claimed_tests_passed": true
  }
}
```

Listing 1: **An extracted claim with retained provenance**: The reader supplies a candidate value. The host supplies task, source, coverage, and policy metadata; structural validation does not certify the claim.

^lst-vol3-reader-record

The `public` label reflects the source classification of the external documentation; if an extraction operates on proprietary code, the admitted record inherits that higher confidentiality tier for all downstream routing. Tracking source identifiers allows the runtime to trace every claim back to its origin, which is essential because even an authentic README can contain inaccurate statements. Because the host controls metadata synthesis, the reader model cannot elevate its own trust tier or bypass classification rules by injecting forged labels.

### Redirection Through Valid Fields

^sec-vol3-security-valid-field-redirection

Even with host-supplied metadata and an explicit `claimed_tests_passed` field ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.06 Quarantined Readers and Ingestion Isolation#^lst-vol3-reader-record|listing 1]]), an untrusted document can still steer the planner through a valid schema value. When the README states that all tests passed and the quarantined reader faithfully emits `claimed_tests_passed: true`, the raw injection string never enters the planner’s context window. The system still fails if the planner treats that boolean claim as empirical proof that the test suite succeeded.

Preserving the integrity of system operations requires the runtime to track the epistemic status of extracted claims throughout verification. The adapter admits a completed, schema-valid payload as a `document_claim`, documenting its source and excerpt coverage. This record validates the syntactic form of the claim, but provides zero guarantee that any test suite actually executed. The planner can use this claim as a hypothesis to guide further investigation, such as proposing a test run. If the planner instead proposes approving the repair based solely on this extracted assertion, the reference monitor intervenes. The monitor verifies preconditions against protected execution logs and refuses to substitute a document claim for genuine runtime evidence. This is authority staying with the source (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-source-authority|6]]) applied to a hostile document. The extracted field faithfully represents what the README says, but the designated source for whether a test passed is the runner, and no excerpt of another document supersedes it. Authoritative verification requires an authorized runner executing inside a sandboxed environment against the target candidate revision. A cryptographically logged pass for `test_waiter_notified_on_return` on commit `r18` provides authentic evidence for that individual test, while final repair acceptance continues to require satisfying the broader task specification.

This semantic redirection vulnerability applies to any structured field, including issue numbers or component names. An attacker does not need to craft natural-language injection directives if they can bias the reader into selecting a valid but harmful object identifier, for example one that directs a patch tool toward a critical system configuration file. Constrained schemas substantially restrict the attack surface compared to free-form text, but downstream components must still verify truth, relevance, and authorization before taking action. Conversely, allowing bounded free-text summaries provides richer descriptive power to the planner, but reintroduces the risk that adversarial instructions will pass through the summary. Both structured fields and short summaries remain tied to their untrusted source, though their failure modes and verification requirements differ.

### Opaque Handles for Retained Content

^sec-vol3-security-retained-content-handles

Structured fields and short summaries work when the planner needs only a claim from a document, but applying a software patch or analyzing a binary dump requires passing substantial raw data into a candidate workspace without reducing it to a scalar schema. Ingesting these raw bytes directly into the planner’s context window inflates token costs and exposes the model to injection payloads. The runtime instead captures the bytes in an isolated store and issues a **typed opaque handle**, a runtime-issued reference to stored bytes that a declared tool argument can name without the bytes entering model context. The handle extends the inspection handles of the tool boundary, which spared the context a long log, to content the planner should not read at all. It cuts context overhead and keeps untrusted tokens out of the planner, without endorsing the safety of the underlying data.

↩︎ Inspection handles that name retained tool output without staging it into context are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.07 Observation Stream Truncation#^sec-vol3-tool-calling-truncation-notices|Truncation notices and inspection handles]]**.

The planner passes the handle as an argument to declared tools rather than concatenating raw text into command strings. When an authorized tool resolves the handle, the runtime applies the object’s original provenance and confidentiality labels to the operation, treating the tool invocation as an interaction with untrusted data. Furthermore, tool-level access controls (sandboxed container boundaries, workspace preconditions, and restricted mutation scopes) constrain the damage a malicious patch can inflict during evaluation.

If the planner genuinely requires visibility into the raw payload to make an engineering decision, the runtime must offer a restricted inspection interface. Providing a bounded excerpt reveals part of the untrusted text to the planner, and the runtime must update the planner’s context state with the appropriate untrusted provenance. The system must never implement an unconstrained fallback that dumps the entire raw file into the planner’s context upon an extraction failure, as doing so would dismantle the architectural boundary under conditions an adversary can deliberately trigger.

### Extraction Loss and Overhead

^sec-vol3-security-extraction-loss

When a narrow extraction schema strips an unexpected stack trace, subtle dependency declaration, or version constraint from a repository README, the planner is left blind to the root cause of the failure. Ingestion quarantine is not free, and its information loss and latency costs must be counted alongside the protection it buys. If the reader misinterprets or drops an excerpt, the planner may issue redundant queries, formulate incorrect repair strategies, or propose unauthorized actions. To counter this, the runtime must record the exact byte ranges evaluated and explicitly flag partial extractions, ensuring that the absence of an extracted field is never misinterpreted as evidence that the condition does not exist.

Quarantined readers also introduce computational, memory, and latency overheads. If an untrusted document exceeds the reader’s context window after reserving space for instructions and schema constraints, the host must chunk the input or reject the request. Merging extractions across multiple chunks requires reconciling overlapping spans and preserving provenance chains. Context-pruning and serving-state optimizations apply directly to both reader and planner instances. Consequently, while shielding the planner reduces its active context size, the aggregate system often incurs higher memory utilization, longer end-to-end latency, and increased inference costs across both stages.

↩︎ The accelerator-memory footprint of retained attention state, which the reader and the planner each incur, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^sec-vol3-kvcache-geometry|The Footprint of Retained Attention State]]**.

Evaluating these architectural choices requires testing on identical task benchmarks under both benign and adversarial conditions. Practitioners should measure extraction error rates, end-to-end task completion rates, security containment effectiveness (preventing unauthorized disclosures or state mutations), false-positive rejection rates, and total resource consumption. When assessing performance gains, teams must isolate the contributions of reader model scale, schema design, and reference-monitor policies. Ingestion isolation justifies its operational overhead only when it measurably satisfies both security requirements and task utility. [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.10 Adversarial Robustness and Red-Teaming#^sec-vol3-security-attack-success-utility|Section 9.9.2]] prices both on one scale, with reader calls counted in the cost per accepted task.

Restricting input ingestion secures the initial entry point, but extracted fields, natural-language summaries, and opaque object handles still circulate through the agent’s reasoning loop. The next architectural challenge is tracking these data dependencies across multi-turn trajectories and enforcing rigorous information-flow policies at every subsequent tool invocation.
