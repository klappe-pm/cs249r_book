# V3-09.04 The Confused Deputy and Task-Scoped Authority

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09 Agent Security|V3-09 Agent Security]]

^sec-vol3-security-confused-deputy

When the README names the private fixture as a search argument and the interface check confirms only that the runtime is permitted to search, the fixture leak repeats the shape of Hardy’s compiler case ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-hardy1988confused|Hardy 1988]]) with a query string in place of an output file. Because the runtime holds broader functional capability than any single request should exercise, prompt injection turns the confused deputy (definition [7.3](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-confused-deputy)) from an occasional configuration mistake into the central failure mode of an agent.

↩︎ The confused deputy, as an authorized program misdirected by a party that cannot exercise the authority itself, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.05 Interoperable Tool Discovery#^sec-vol3-tool-calling-discovery-authority|Discovery and authority]]**.

The execution runtime is that deputy and its identity is legitimate, so authorization has to ask whether a specific proposed invocation falls within the bounded authority delegated for the active repair task. While scoped capabilities constrain an agent’s execution sandbox, the runtime must also isolate the user’s task objectives from untrusted instructions discovered while processing external data. An external document can supply factual evidence to guide a bug fix, but it carries no authorization to direct execution or modify permissions, because its author holds no administrative authority over the user’s environment.

### Request-Level Authorization

^sec-vol3-security-request-authorization

The fixture-search proposal composes two individually permitted activities, reading a local test fixture and querying public package documentation, into an unauthorized data release. The typed action contract (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-strict-action-abi|7]]) guarantees that the proposal is validated against its declared interface and the session’s grants before it reaches the environment, and both checks pass here. A tool-permission check on the function name confirms only that the search tool is registered, and an endpoint allowlist confirms only that the destination hostname is permitted. Neither check verifies whether the private fixture data is allowed to leave the execution boundary. Consequently, task-level data restrictions must remain bound to the fixture data whenever the runtime evaluates an outbound request.

To prevent this exfiltration, the runtime validates every proposed action against an authoritative authorization record under its own control. For this repair task, the record associates the authenticated user with the active task scope, catalogs the private fixture and its version, and defines the permitted egress policies for the documentation search service. The model merely generates a candidate invocation; it cannot redefine or override these authoritative bindings. The runtime resolves target resources and payload references independently before dispatching any call, rather than relying on model-provided resource labels or rationales. Maintaining this enforcement requires the runtime to track data provenance across prompt extraction and variable transformations, ensuring that confidential inputs cannot be laundered through intermediate tool calls.

This request-level mediation produces a deterministic, enforceable decision. An outbound query containing an approved public package identifier proceeds normally, assuming all other task invariants hold. In contrast, a query embedding content from the private fixture is rejected immediately because the task policy grants no release authorization for confidential fixtures to external services. When rejecting the request, the runtime halts dispatch, logs the policy violation, and injects a synthetic refusal observation back into the agent loop. Because a tool’s function signature carries neither data provenance nor release policy, the runtime enforcement layer must evaluate both properties directly. To avoid secondary data leakage, the runtime’s audit record identifies the restricted source while omitting the sensitive payload from log storage.

### Task-Bound Authority

^sec-vol3-security-task-bound-authority

Checking each request against the task’s authorization record only holds if the credential behind that request is scoped to the same task. If an agent runtime instead executes a single-repository bug fix using the developer’s full personal token or a shared automation service account, a prompt injection inside that repository’s README can reach every other repository and production service those credentials unlock. The runtime must therefore enforce zero ambient authority, granting only the task-bound authority delegated for the specific job rather than the superset of ambient credentials held by the user or the platform. If completing a repair genuinely requires broader access, that elevation must happen through an out-of-band, trusted authorization workflow; neither an untrusted README instruction nor the model’s reasoning can widen the grant on its own. [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.08 Delegated Identity and Credential Brokering#^sec-vol3-security-credentials|Section 9.7]] develops how identity brokering and credential minting enforce these boundaries across remote services.

Restricting authority limits the blast radius of a redirected model. Capability bounds, however, limit reach rather than correctness: within permitted boundaries, a misdirected agent can still waste API rate limits on unhelpful queries, introduce subtle regressions into source files, or select erroneous evidence. Even for reach, the task-bound grant must be the only authority the worker can exercise. Narrowing a grant does not revoke the broader one it was derived from, so the runtime must account for any parent credential the worker still holds.

↩︎ Attenuation of delegated authority, which leaves a retained parent grant usable until the runtime withdraws it, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^sec-vol3-sandboxes-attenuation|Narrowing delegated authority]]**.

The repair agent operates with relatively modest authority: it modifies files inside a disposable workspace and submits patches for human review. In contrast, research agents, customer support agents, and infrastructure remediation agents differ in how much untrusted content they read and in which authority level (${A}_0$ to ${A}_3$) an injection can borrow. Those two quantities dictate which authorization checks must bind when an untrusted payload arrives.

**Lighthouse 9.1: Authority by archetype**

The four recurring workloads read different untrusted content and hold different authority, as [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.04 The Confused Deputy and Task-Scoped Authority#^tbl-vol3-authority-by-archetype|table 2]] lays out. |:----------------------|:-------------------------------------------|:-------------------------------------------------------------------------|---------------:|------------------:|:----------------------------------------------------------------------------|
| **Repair agent**      | Dependency READMEs, issues, search results | Workspace edits, package searches, patch submission (${A}_1$ to ${A}_2$) |             20 |             18.2% | Evidence check on acceptance; release check on searches                     |

^tbl-vol3-authority-by-archetype

**Systems insight**: Exposure frequency and borrowable authority run in opposite directions across these archetypes. A research agent encounters an untrusted payload approximately 11 times as often as a support agent, but its principal exposure is data disclosure, making outbound release filtering its main binding check. Conversely, while a customer support agent encounters relatively few untrusted inputs per task, a successful injection can directly manipulate financial records or issue refunds, the confused deputy problem in its starkest form. Because expected loss depends on attack exposure, the probability that an exposed task produces an unauthorized effect, and the consequence of that effect, allocating defensive engineering effort based on exposure frequency alone leaves high-consequence workloads exposed.

Task-scoped grants and endpoint allowlists bound which tools the deputy may invoke and which services it may contact, but they still evaluate the call by its interface rather than its payload. Even when the runtime narrows credentials to the single repair task and permits only the approved package-search endpoint, any argument bytes placed into an outbound request cross that service boundary the moment the call is dispatched.
