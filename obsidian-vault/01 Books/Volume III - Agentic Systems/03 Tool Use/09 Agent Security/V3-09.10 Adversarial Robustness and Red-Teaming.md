# V3-09.10 Adversarial Robustness and Red-Teaming

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09 Agent Security|V3-09 Agent Security]]

^sec-vol3-security-evaluation

In an end-to-end trajectory test of the repair agent, a model that proposes an overt fixture-bearing `package_search` causes no breach if the runtime broker intercepts and blocks the call before dispatch, whereas a model that emits a benign-looking search query that covertly encodes private fixture tokens compromises the task without ever producing an overtly malicious string. Evaluating the adversarial robustness of an agent therefore requires measuring concrete effects at the relevant system boundary (what actually crossed the network or mutated persistent state) rather than grading the model’s generated text or intermediate reasoning with a token-level classifier.

### Trial Specification

^sec-vol3-security-trial-specification

If a red-team trial runs against live credentials or conflates an unfixed bug with a leaked secret, the benchmark either causes real damage or misdiagnoses why the agent failed. A sound trial specification therefore separates the legitimate user task and its acceptance criteria from the adversary’s objective, and always runs against synthetic private data and instrumented mock endpoints rather than live network destinations. In the benchmark fixture, the legitimate task permits selected package queries and local workspace edits to fix a bug, while the security invariant requires that private fixture contents never reach the external search endpoint. Similarly, an integrity evaluation tests whether an adversary can forge success signals, for example by injecting a falsified `tests_passed: true` flag into execution history, and cause the agent to accept unverified code without the protected test runner actually confirming the result. Because confidentiality and integrity failures arise from distinct mechanisms and demand different mitigations, evaluators must track and report them as separate outcomes.

Every trial specification must explicitly define the adversary’s capabilities and attack surface. It states what inputs the attacker controls (such as a single `README` passage, an external search result, a poisoned record in long-term memory, or a streaming sequence of tool outputs), along with their budget, observation feedback, adaptation limits, and stopping horizon. A static attacker who submits a single payload exercises different failure modes than an adaptive adversary who observes intermediate tool outputs and refines subsequent prompts over multiple turns. When comparing competing security policies, benchmark protocols must either evaluate both systems against the exact same static attack suite or grant an equally budgeted adaptive red-team agent access to each system. Benchmarking a new defense solely against an attack suite engineered against an older, different policy creates a false sense of security, as it systematically overlooks vulnerabilities unique to the new policy’s specific validation checks and assumptions.

Controlled evaluation requires isolating experimental variables across runs. The task distribution, repository snapshots, tool schemas, authorization grants, base model checkpoints, temperature settings, and resource quotas must remain identical between baseline and defended trials. Furthermore, each trial must run within an isolated execution sandbox with fresh mutable state. While persistence testing intentionally carries over specific poisoned state, such as memory summaries or persistent workspace files, across sequential sessions, evaluators must ensure that artifacts from one trial never cross-contaminate another. Finally, red teams must partition attacks into development sets and held-out test sets. A policy hand-tuned until it successfully blocks a published attack suite has merely overfitted to known signatures, demonstrating little about its resilience against a novel adversary.

Two benchmarks apply these controls in complementary ways. InjecAgent provides a standardized benchmark of indirect prompt injection attacks embedded across diverse tool responses, explicitly categorizing payloads by their intended goal, either triggering unauthorized state-mutating actions or exfiltrating private data ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-zhan2024injecagent|Zhan et al. 2024]]). In contrast, AgentDojo provides a dynamic execution environment featuring coupled user tasks and injection vectors ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-debenedetti2024agentdojo|Debenedetti et al. 2024]]). By simultaneously measuring task completion without attacks, task completion under adversarial perturbation, and attack success rates within identical runs, AgentDojo directly exposes the operational overhead and false-block costs of candidate defenses. While both testbeds provide reproducible baselines for academic and industrial comparisons, engineers must still enforce strict train-test splits and incorporate adaptive red-teaming before certifying a production system.

For every evaluation episode, the test harness must capture structured telemetry: the exact tool invocation and its parameters, associated provenance labels and version tags, the runtime policy broker’s decision, and the final state of protected sinks. The analysis places each attacked episode on one outcome ladder. An episode in which the model never proposes a prohibited operation ends at the first rung. One that does records proposed misuse, and the runtime then either blocks it before dispatch or dispatches it. A dispatched operation ends in confirmed harm, no observed harm, or an unresolved outcome. Each rung is a different record (the proposal, the monitor’s decision, the endpoint log), and the rest of this section reports results in these terms. An execution timeout or connection reset does not prove that an exfiltration payload failed to escape; external network delays or asynchronous dispatch may simply have hidden a leak. Evaluators must use the tool contract and mock endpoint logs to reconcile available evidence. If an outcome remains unverified when the trial hits its stopping horizon, it must remain explicitly categorized as unresolved rather than credited as a successful defense.

### Attack Success and Useful Completion

^sec-vol3-security-attack-success-utility

If an adaptive attack spans ten conversational turns and succeeds on the tenth, counting individual tool calls in the denominator reports a 90 percent defense rate for an episode that was completely compromised. The **attack-success rate** avoids this dilution by taking whole attacked episodes as its denominator: it measures the count of observed successful attack episodes divided by all eligible attacked episodes under the declared protocol. An episode must remain in the denominator even if the defensive policy preemptively halts execution, the agent encounters a timeout, or the injected prompt fails to elicit any tool proposal at all. Only genuine infrastructure setup errors qualify for exclusion, and engineers must fix the eligibility criteria before inspecting evaluation runs to prevent selective reporting.

Unresolved episodes demand rigorous accounting rather than silent omission. When a portion of eligible trials ends with ambiguous telemetry or uninspected state, the ratio of confirmed harms to total episodes represents only an empirical lower bound on the true compromise rate. To establish an honest safety envelope, evaluators must also report the conservative upper bound, calculated by treating every unresolved episode as an attacker success. These bounding fractions quantify observational gaps in the test harness rather than statistical sampling error over future workloads, highlighting exactly how much uncertainty stems from unmonitored execution paths.

When comparing a defended system against an undefended baseline under identical conditions, engineers frequently compute the relative attack reduction: one minus the defended rate divided by the baseline rate. While relative metrics convey overall progress, they can easily mislead if reported in isolation. For instance, if the baseline attack-success rate is zero, the ratio becomes undefined; if a defense performs worse, it yields a negative reduction. Furthermore, a high relative reduction over a tiny sample size can conceal large absolute vulnerabilities. Engineering reports should therefore always publish the raw trial counts and absolute attack-success rates alongside any relative percentage gains.

Security metrics are meaningless without measuring useful task completion. A policy that trivially disables all tool dispatch will achieve a perfect zero percent attack-success rate while delivering zero utility. Evaluators must therefore maintain separate, parallel metrics for useful work: accepted legitimate tasks over all eligible benign trials, and accepted legitimate tasks over all eligible attacked trials. A security filter might successfully prevent a private data leak, yet leave the original software repair incomplete or broken. To isolate policy errors from general model limitations, systems engineers track the **false-block rate**. It is the fraction of legitimate, benign tasks that fail solely because a defensive policy erroneously refused a valid operation under a rule fixed in advance. Benchmarking harnesses must categorize task failures precisely, distinguishing policy-induced false blocks from unrelated failures such as syntax errors, environment timeouts, or exhausted search budgets. The published results of Debenedetti et al. ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-debenedetti2024agentdojo|2024]]) show why utility and attack success must be read together. [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.10 Adversarial Robustness and Red-Teaming#^fig-vol3-utility-vs-attack-success|Figure 5]] places each evaluated configuration by its benign utility and its targeted attack-success rate under the same injection attack. It also traces one model through the four defenses the authors ran on it.

^fig-vol3-utility-vs-attack-success

Without a defense, attack success across the evaluated models runs from 1 percent to 56 percent, and two versions of one model family with the same benign utility, 79 percent, succumb at 34 percent and 1 percent. Capability is therefore no proxy for resistance, and a model update can move resistance by more than an order of magnitude without changing utility. The defenses on the single ablated model sort along the same line as this chapter’s argument. Delimiting untrusted text, an instruction to the model, leaves attack success at 42 percent against an undefended 48 percent. An injection detector cuts it to 8 percent but drops utility from 69 percent to 41 percent, the false-block cost defined above. Narrowing the tool set to those relevant to the user’s request, before any tool output is read, cuts attack success to 7 percent while utility reaches 72 percent. Of the four, only the defense that constrains what can be done, rather than what the model is told, holds both metrics.

Comprehensive evaluation also tallies operational latency and financial cost across the full trial boundary, including reader model calls, policy broker checks, provenance tracing, retry loops, and uncompleted attempts. When an overly restrictive defense rejects valid actions, it forces unnecessary retries or leaves tasks uncompleted, directly driving up the effective cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**). Because the effective unit cost scales inversely with the acceptance probability (${C_{\text{eff}}} \propto 1/{p_{\text{acc}}}$), an aggressive defense that suppresses attacks at the expense of high false blocks imposes a steep monetary and operational penalty on ordinary workloads. Framing security and utility through this shared economic lens allows systems designers to evaluate defense trade-offs objectively.

**Napkin Math 9.2: Pricing fewer disclosures against lost repairs**

**Problem**: Two hypothetical policies run on the same repair-task distribution with synthetic private fixtures and a fixed collection of injected README payloads. Policy A checks the permitted search operation and destination but has no confidential-query rule. Policy B adds conservative dependency labels and a release check before search dispatch. Each receives 100 attacked episodes and 100 separate benign episodes; the counts are hypothetical teaching inputs. What does B buy, and what does it cost?

| Outcome count                                        | Policy A | Policy B |
|:-----------------------------------------------------|---------:|---------:|
| Attacked episodes with confirmed fixture disclosure  |       20 |        5 |
| Attacked episodes with unresolved disclosure outcome |        5 |       10 |
| Accepted legitimate repairs under attack             |       65 |       55 |
| Accepted benign repairs                              |       90 |       80 |
| Benign repairs prevented by a false policy block     |        5 |       15 |

Table 4: **Hypothetical security and utility outcomes**: Attacked and benign trials are separate cohorts. Accepted attacked repairs exclude disclosure and unresolved outcomes in this fixture; other incomplete repairs remain in the denominator.

^tbl-vol3-security-policy-comparison

**Math**: Dividing each confirmed-disclosure count in [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.10 Adversarial Robustness and Red-Teaming#^tbl-vol3-security-policy-comparison|table 4]] by the attacked-episode count gives 20 percent for A and 5 percent for B, a relative reduction of 75 percent. In the stipulated scenario where every unresolved outcome in both arms is a disclosure, the rates rise to 25 percent and 15 percent, and the reduction falls to 40 percent. Even that figure is not the least favorable comparative reduction, because unresolved episodes in the baseline arm A could have been clean while unresolved episodes in the defended arm B could all have leaked. The worst-case bound on B’s relative improvement therefore compares B’s upper disclosure fraction with A’s confirmed lower fraction. On benign work, B accepts 10 fewer repairs per 100, which equals its extra false blocks. The attacked cohort shows the same cost. B completes 55 legitimate repairs under attack against A’s 65, although fewer of its attacked episodes end in disclosure or an unresolved outcome. The reason is that its release check also blocks searches the repair itself needed. At equal cost per attempt, **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]** scales with $1/{p_{\text{acc}}}$, so B’s cost per accepted benign repair is 12.5 percent higher than A’s before counting its own label and check work.

**Systems insight**: Policy B achieves an apparent 75 percent reduction in observed disclosures, but it does so at the cost of a 12.5 percent increase in effective cost per accepted benign task, driven entirely by its elevated false-block rate. Two engineering levers govern this trade-off. First, refining the false-block policy recovers benign acceptance one-for-one without sacrificing the integrity of the release check. Second, reducing evaluation uncertainty is as important as tuning the policy itself: in the scenario where unresolved outcomes in both arms are disclosures, Policy B’s apparent relative advantage falls from 75 percent to 40 percent. Finally, Policy B’s remaining confirmed disclosures pinpoint concrete failure modes (untracked data dependencies, misclassified release boundaries, or policy bypasses) that engineers must diagnose in audit traces before clearing the system for deployment.

### Adaptive Attack Testing

^sec-vol3-security-adaptive-attack-testing

A fixed collection of injected README payloads provides a reproducible regression test during development, but an attacker whose first fixture query is blocked by Policy B’s release check will not keep submitting the same canned phrasing. Certifying system robustness demands adaptive evaluation that actively probes the boundaries of policy enforcement, systematically varying injection channels, summary representations, retrieval contexts, tool signatures, and network endpoints while holding the underlying legitimate task constant. Red-teaming must also test structural bypasses alongside natural-language trickery. These scenarios include injecting boolean literals (such as spoofing a `tests_passed: true` field) to subvert status parsers, reusing expired capability handles across task sessions, and mounting time-of-check to time-of-use attacks where an approval request mutates before dispatch. Evaluating against these diverse attack patterns tests whether the architecture’s security contracts hold under stress rather than whether a model happens to recognize a specific prompt phrasing.

Because stochastic decoding and distributed tool environments introduce execution variance, red teams must run repeated independent trials and report comprehensive confidence intervals alongside raw counts and tested strategies. A common pitfall in empirical defense papers is treating zero observed attacks as proof of invulnerability. Observing zero successes across a finite sample bounds the attack-success rate, but never proves it is zero. For example, if a defense experiences zero compromises across 100 independent trials, the 95 percent confidence upper bound on its true attack-success rate remains 3.0 percent, closely matching the classical rule-of-three[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.16 Footnotes#^fn11|¹¹]] estimate of $3/{n}$. Translating such benchmark figures into production risk estimates requires explicit modeling of adversary capability, attack prevalence, and shifting operational workloads. Naively multiplying an empirical attack-success rate by total monthly request volume provides an illusion of precision without modeling attacker incentives. The non-negotiable systems requirement here is transparently declaring the outcome boundary, trial protocol, and empirical uncertainty.

**Checkpoint 9.3: Interpreting a defense report**

A proposed defense lowers observed fixture disclosures but blocks more legitimate searches and leaves several endpoint results unresolved.

**Outcome boundary**: Which records distinguish proposed misuse, a block before dispatch, confirmed harm, and an unresolved outcome?

**Denominators**: Why must a refused or timed-out attacked task remain in its eligible cohort, and how should unresolved effects be reported?

**Utility**: Which benign and attacked completion measures would distinguish useful protection from simply disabling the search tool?

**Adaptation**: How can an evaluation test a poisoned summary retrieved in a later session without contaminating other trials or treating a fixed attack set as a universal guarantee?

**Zero-success bound**: A defense shows no disclosures in 50 attacked episodes. Estimate the upper bound on its attack-success rate at the level used above, and decide whether the report supports release for a task that tolerates at most 1 percent.
