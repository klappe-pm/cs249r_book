# V3-09.07 Information-Flow Policy

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09 Agent Security|V3-09 Agent Security]]

^sec-vol3-security-taint-tracking

The reader can still return a schema-valid `claimed_tests_passed: true`, and the planner, which has seen the private fixture, can still propose a well-formed search query that carries it. Restricting the reader’s output format settles neither the evidence question nor the release question that the threat model posed, so the runtime must retain, for every value, the information a use policy needs at dispatch. Information-flow control[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.16 Footnotes#^fn5|⁵]] is the classical discipline for governing how data may influence other data and operations, and an agent runtime applies it as an information-flow policy.

**Definition 9.2: Information-flow policy**

***Information-flow policy*** is a runtime-enforced rule set that attaches integrity provenance and confidentiality labels to every record, propagates them through each transformation, and admits an operation only if its data may reach the operation’s recipient and its influences are acceptable for the operation’s use.

1.  **Significance**: It turns “do not leak the fixture” and “do not trust the README” into two baseline set checks the reference monitor evaluates before dispatch ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-dispatch|equation 3]]), at the cost of a label lookup per argument rather than a judgment per proposal.
2.  **Distinction**: Access control decides whether a principal may touch an object. Information-flow policy decides where data may go, and what it may justify, after it has been touched. The fixture read is permitted access; the fixture-bearing search is a prohibited flow.
3.  **Common pitfall**: Tracking a single trusted or tainted bit. One bit cannot express that trusted test evidence is private while public documentation is non-authoritative, so it either blocks useful work or releases private data.

**Taint tracking**[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.16 Footnotes#^fn6|⁶]] is one implementation technique: the system marks inputs with relevant properties and propagates those properties through covered transformations. Integrity provenance and confidentiality impose different obligations, and both must survive extraction and later use.

### Integrity and Confidentiality

^sec-vol3-security-integrity-confidentiality

In the repair task, a private test fixture is trustworthy input for a local test run that must never leave the workspace, whereas a public `README.md` is safe to quote to an external search service but untrusted as evidence that tests passed. A single “tainted” bit cannot distinguish between what may be trusted and what may be disclosed, so each of the threat model’s two questions ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.03 The Adversarial Threat Model#^sec-vol3-security-influence-permission-evidence|section 9.2.2]]) becomes an independent property that the runtime stores and checks. Integrity records which sources and transformations influenced a value, so a protected decision can ask whether those influences are acceptable for it. An assertion extracted from a public README remains a claim by that source, even if the value is a boolean. The document can suggest a check to run, but the acceptance procedure must obtain the relevant result from the protected runner. This is the proposal/evidence distinction that governs the tool boundary.

↩︎ The separation of what the model proposed from the evidence the runtime holds about an operation’s effect is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.02 The Tool Boundary#^sec-vol3-tool-calling-boundary|The Tool Boundary]]**.

Confidentiality records who may receive a value. A private fixture can be an appropriate input to an authorized local test and an inappropriate one for an external search request; a reliable record of exactly which fixture bytes the runtime read grants no permission to disclose them. [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^tbl-vol3-flow-policy-dimensions|Table 3]] keeps these questions separate.

| Runtime property     | Question at use time                                              | Repair-task example                                              |
|:---------------------|:------------------------------------------------------------------|:-----------------------------------------------------------------|
| Integrity provenance | Does the evidence meet the requirements of this decision?         | A README assertion does not establish a protected test outcome.  |
| Confidentiality      | May this information reach this recipient through this operation? | A permitted search endpoint may not receive the private fixture. |

Table 3: **Independent information-flow obligations**: Accurate provenance is not permission to disclose, and permission to disclose is not evidence that a claim is true.

^tbl-vol3-flow-policy-dimensions

The host attaches these properties to each record using the source adapter, the authenticated task context, and the applicable data policy. Each record names the task, source and version, extracted value or handle, integrity provenance, confidentiality restrictions, and derivation history. Fields inside an untrusted payload that claim `trusted: true` or `classification: public` therefore cannot overwrite the host’s metadata. Even so, protecting the record from tampering only preserves what the runtime recorded; it does not prove the payload true or the classification process complete.

### Label Propagation Through Transformations

^sec-vol3-security-label-propagation

A deterministic adapter can propagate labels directly along its known dependencies: concatenating a public package name with private fixture contents yields a value subject to the fixture’s release restrictions, whereas parsing an integer from an external issue retains that issue’s provenance. Although a validator may confirm that the integer names an issue in the permitted repository, parsing alone does not establish that the task should modify that issue.

Model-generated transformations require a coarser policy, because neither the generated explanation nor attention weights yield a trustworthy semantic dependency graph. A conservative policy treats a model output as potentially dependent on all the selected inputs available to that invocation and carries their integrity provenance and confidentiality restrictions into the derived record and subsequent proposal. It is a declared over-approximation: it assumes every input may have influenced every output token, and it proves no noninterference[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.16 Footnotes#^fn7|⁷]] property for the whole system.

Stated over sets, the rule becomes something a runtime can implement and a reader can check. The host attaches two properties to every record ${x}$: its integrity provenance ${\iota}({x})$, the set of sources whose content may have influenced it, and its confidentiality ${\kappa}({x})$, the set of recipients permitted to receive it. Representing confidentiality as a set of permitted readers follows the decentralized label model ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-myers1998complete|Myers and Liskov 1998]]). A public record has no recipient restriction, so its ${\kappa}$ contains every recipient; an implementation represents that with a marker that intersection treats as its identity, since no finite set can list every recipient. When a transformation derives ${y}$ from inputs ${x}_1, \dots, {x}_k$, the derived record carries

$$
{\iota}({y}) = \bigcup_{i=1}^{{k}} {\iota}({x}_i), \qquad {\kappa}({y}) = \bigcap_{i=1}^{{k}} {\kappa}({x}_i) \tag{2}
$$

^eq-vol3-flow-join

Provenance accumulates and the permitted recipients shrink. For a deterministic adapter, the inputs are the arguments it actually reads. For a model invocation, they are all the selected inputs in its context, which is where the conservative approximation enters. A query generated by a planner that saw both `readme_7` and the private fixture has both sources in ${\iota}$ and a ${\kappa}$ no wider than the fixture’s, whatever words the query contains.

↪ The security lattice behind these labels, with its ordering, join, and meet, is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-lattice|Information flow security lattice]]**.

The cost is overrestriction. A planner that sees a private fixture may produce an ordinary public package name, yet its query remains potentially fixture-dependent under this policy. A more selective design can construct the query from separately approved public fields through a trusted adapter, or run a restricted decision step without the private inputs. That separation must include derived summaries and other state that could carry the dependency; asking the same model to omit secrets establishes none of it.

Dependencies include control choices as well as copied substrings. Selecting one of several public package names according to a private fixture value can disclose information even when no fixture text appears in the query. Tracking only string matches would miss that path. The conservative invocation rule covers such possible dependence within the inputs it tracks, at the cost of also restricting benign choices.

Labels survive compaction and persistence. A summary of the README remains derived from the README, and a retained diagnosis based on private data keeps that dependency when retrieved later. Removing the original document from active context leaves the summary, an outstanding proposal, and a stored lesson labeled as before. Memory provenance supplies the record relationships; the flow policy adds the restrictions required for their next use.

↩︎ Dependency provenance that links summaries and consolidated lessons back to their source records is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.09 The Memory Write Path#^sec-vol3-memory-self-poisoning|Self-reinforcing errors]]**.

### Operation and Destination Mediation

^sec-vol3-security-operation-mediation

A tool named `read` or `search` is not exempt from mediation: a local read can pull protected data into model context, and an external search transmits its query string to a remote server even if it mutates no remote record. The reference monitor therefore applies integrity and confidentiality checks before every dispatch, alongside the structure, permission, and state checks from **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-boundary-checks|Structure, permission, and state checks]]**, identifying the actual operation, resolved resources, recipients, and data that the call will expose.

The policy admits externally derived values wherever the operation tolerates them. It can let an untrusted candidate patch enter a bounded local test while forbidding that candidate from modifying protected acceptance machinery. The test observation then supplies new evidence about the candidate, while the original document stays non-authoritative. Permitted influence is a property of the specific operation and its enforcement, not a universal clean/tainted division.

Without an authorized, use-scoped exception, both obligations reduce to one admission test. Let a proposed operation ${o}$ send argument values to the host-resolved recipient ${r}$, and let ${x}$ be the record obtained by applying [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-join|equation 2]] to those arguments and to the invocation that proposed them. The monitor admits dispatch only if

$$
{r} \in {\kappa}({x}) \qquad \text{and} \qquad {\iota}({x}) \subseteq {\text{Inf}}({o}) \tag{3}
$$

^eq-vol3-flow-dispatch

where ${\text{Inf}}({o})$ is the set of sources the task policy accepts as influences on ${o}$. The first condition is the release check and the second is the evidence check; they fail independently. A local test run can accept candidate code from any source, so its ${\text{Inf}}({o})$ is unrestricted, while recording a test pass for acceptance admits only the protected runner. This admission test is the information-flow half of containment beneath the model (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-zero-trust-sandboxing|9]]). **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^sec-vol3-sandboxes-least-privilege|Capabilities and Credentials]]** applied it to what executing code can reach. The same principle requires that an operation sending data onward be dispatched only when the applicable policy admits its recipient and use, either on the joined labels or on a separately authenticated, use-scoped decision.

For the repair variant, the runtime checks the task’s search grant and the query’s data dependencies separately. The grant allows selected package searches, and sending the private fixture is outside it. A fixture-dependent query therefore fails the release policy before network dispatch, because the search endpoint is not in the fixture’s recipient set. Independently, `claimed_tests_passed: true` from `readme_7` at `doc_v3` fails the evidence requirement for recording a test pass, because that source lies outside the runner-only ${\text{Inf}}({o})$. The runtime retains that assertion as document content, never as a runner result ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^fig-vol3-taint-tracking-pipeline|figure 4]]).

![[90 Assets/Volume III/09 Security/Taint Tracking Pipeline 1428116961.svg]]

Figure 4: **Two Labels, Two Independent Checks**: A planner invocation that saw both the README and the private fixture yields a query whose integrity provenance ${\iota}$ is the union of its inputs’ and whose confidentiality ${\kappa}$ is their intersection. The search endpoint lies outside ${\kappa}({x})$, so the release check rejects the query before dispatch. Separately, the README-derived test claim lies outside the runner-only ${\text{Inf}}({o})$, so the evidence check refuses to record it as a pass.

^fig-vol3-taint-tracking-pipeline

These checks must cover every route through which the protected operation can occur. A general command runner that bypasses the labeled adapter would invalidate the claimed boundary. Sandbox and egress enforcement constrain that route; the flow policy determines which data may traverse a permitted route. An unregistered tool, missing required provenance, or an unresolved recipient defaults to rejection, or to a hold for an authorized decision under an explicit policy.

The returned observation records the policy disposition and withholds the content that was blocked: it states that the query depends on data not releasable to the external endpoint and omits the private query itself. A decision record distinguishes rejection before dispatch from an operation already sent whose outcome is unknown. These controls cover the adapters, dependency records, and channels they model; timing channels outside that model need their own boundary ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.09 Multi-Turn Attacks and State Persistence#^sec-vol3-security-multiturn|section 9.8]]).

### Typed Handle Resolution

^sec-vol3-security-handle-resolution

If a planner could bypass the release check by passing a fixture’s opaque handle `h` to `package_search` instead of raw bytes, or by interpolating a handle-looking substring into a shell command, handles would launder secrets rather than protect them. Instead, handles keep raw bytes away from the planner while leaving the underlying data under policy: a typed argument identifies a blob reference, and a trusted adapter obtains the content only after checking the proposed use. This explicit argument boundary is safer than expanding handle-looking substrings inside arbitrary shell commands, where quoting, nested fields, or interpolation can obscure what the operation will consume.

At dereference, the runtime authenticates the caller, checks the handle’s task ownership, designated object and version, lifetime, permitted operation, and destination, and retrieves the object’s integrity and confidentiality metadata from the host record rather than from model-supplied fields. The runtime then applies the same use policy to the underlying content and proposal dependencies. A permitted local test may consume the fixture, while an external search is blocked under this task’s grant. Replacing fixture bytes with an identifier therefore cannot change the dispatch decision when an adapter later expands the handle.

In the notation of [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-join|equation 2]], a handle argument ${h}$ designating the host object $\text{obj}({h})$ is checked with the effective labels

$$
{\iota_{\text{eff}}}({h}) = {\iota}({h}) \cup {\iota}(\text{obj}({h})), \qquad {\kappa_{\text{eff}}}({h}) = {\kappa}({h}) \cap {\kappa}(\text{obj}({h})) \tag{4}
$$

^eq-vol3-flow-deref

together with the condition that ${o}$ is among the operations the handle’s host record permits. The handle’s own labels record what influenced its selection; the object’s labels record what its bytes carry. Both enter [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-dispatch|equation 3]], so a fixture handle inherits the fixture’s recipient set and fails the release check at the search endpoint exactly as the bytes would.

An identifier or content hash is not authority. Identical bytes can belong to different tasks with different release restrictions, so content-addressed storage must not collapse their authorization records. The adapter must also bind the approved object version to the exact bytes it consumes, rather than checking one version and resolving another. Moreover, because selecting a handle under private influence can itself convey a choice, hiding the blob contents does not remove the need to track the planner’s dependencies.

Handles narrow exposure and keep enforcement at the point where bytes cross a boundary. Whether an untrusted patch is safe to apply or run remains a question for content and effect checks, task grants, and execution containment, even when the planner never reads the patch text.

[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^lst-vol3-reference-monitor|Listing 2]] assembles the propagation rule ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-join|equation 2]]), handle resolution ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-deref|equation 4]]), and admission test ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-dispatch|equation 3]]) into one dispatch check. Although the planner emits the entire tool call, the tool schema distinguishes parameters that accept fresh model-composed text (`proposal.model_wrote(name)`) from parameters that must reference an existing host-tracked record or handle. A fresh value the planner composed, such as a search query string, has no prior host record of its own and inherits the proposing invocation’s label, which is how a generated query acquires the fixture’s restrictions. By contrast, a parameter expected to name an existing host object must match a stored entry in `records`, so a fabricated or unknown identifier fails with `missing_provenance`. Every other unknown, including an unregistered tool or an unresolved recipient, likewise ends in rejection rather than permission. Rejection by default is the fail-safe default that Saltzer and Schroeder set among their design principles ([[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.15 Source References#^ref-saltzer1975|Saltzer and Schroeder 1975]]). The diagnostic names the rule that failed and never the blocked content, so the refusal itself does not become a disclosure path. The abbreviated listing covers dispatch without endorsement or declassification, while the host decision records below supply the additional checks for an authorized exception.

``` python
from dataclasses import dataclass
from functools import reduce

PUBLIC = None  # readers marker: no recipient restriction

@dataclass(frozen=True)
class Label:
    sources: frozenset  # integrity provenance: possible influences
    readers: frozenset | None  # confidentiality: permitted recipients

def meet(a, b):  # intersection, with PUBLIC as its identity
    return b if a is PUBLIC else a if b is PUBLIC else a & b

def join(labels):  # conservative derivation rule
    return Label(frozenset().union(*(l.sources for l in labels)),
                 reduce(meet, (l.readers for l in labels)))

def reject(rule):  # names the rule, never the blocked content
    return {"status": "rejected_before_dispatch", "rule": rule}

def check_dispatch(proposal, registry, records, task):
    tool = registry.get(proposal.tool)
    if tool is None:
        return reject("unregistered_tool")
    recipient = tool.resolve_recipient(proposal.args)  # host-resolved
    if recipient is None:
        return reject("unresolved_recipient")
    if not task.grant.permits(tool.name, recipient):
        return reject("outside_task_grant")
    labels = [proposal.invocation_label]  # all selected model inputs
    for name, value in proposal.args.items():
        label = records.label_of(task.id, value)  # host metadata only
        if label is None and proposal.model_wrote(name):
            label = proposal.invocation_label  # inherits all its inputs
        if label is None:
            return reject("missing_provenance")
        if tool.is_handle(name):
            obj = records.resolve_handle(task.id, value)
            if obj is None or tool.name not in obj.permitted_ops:
                return reject("handle_not_usable_here")
            label = join([label, obj.label])  # dereference-time labels
        labels.append(label)
    x = join(labels)
    if x.readers is not PUBLIC and recipient not in x.readers:
        return reject("release: recipient not permitted")
    if not tool.accepts_influence(task, x.sources):
        return reject("evidence: source not accepted for this use")
    return {"status": "admitted", "recipient": recipient, "label": x}
```

Listing 2: **Dispatch check at the reference monitor**: The host resolves the recipient, joins labels over arguments, dereferenced handles, and the proposing invocation, then applies the release and evidence checks separately. Unknown tools, recipients, and records default to rejection.

### Endorsement and Declassification

^sec-vol3-security-endorsement-declassification

An issue identifier extracted from an untrusted bug report cannot select a target repository until a trusted lookup confirms that the issue belongs to the task’s permitted scope. A diagnostic summary computed in a private workspace likewise cannot leave that workspace until an authorized rule approves its release. Some useful workflows need such an explicit decision to relax a restriction. **Endorsement** permits a value to serve a specified integrity-sensitive use under trusted policy. When the trusted repository lookup establishes that an extracted issue identifier denotes a resource within the task’s allowed scope, that endorsement supports the resource-selection check without endorsing every statement in the issue.

The monitor first applies the baseline checks of [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-dispatch|equation 3]]. When a check fails, it may admit the named use only if the task policy permits an exception and an authenticated, host-maintained decision matches the exact record and version, operation, recipient where applicable, authorizing principal, and current conditions. For an issue identifier, the host record can bind `issue_id_12` at `doc_v3` to resource selection in `repair_42`. It can also name the repository lookup that checked its scope and record the authorized principal and validity conditions. This binding authorizes no different identifier, version, use, or test-pass claim. An endorsement discharges only the stated integrity obligation, and a declassification discharges only the stated release obligation. Any other failed condition still rejects dispatch, and the stored ${\iota}({x})$ is never rewritten. Every subsequent use therefore continues to see the issue as an influence: an extracted test-pass claim still requires an actual runner observation tied to the relevant candidate and check, and the targeted result at `r18` retains its limited evidential scope.

**Declassification**[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.16 Footnotes#^fn8|⁸]] permits an authorized release of information otherwise restricted by confidentiality policy. A task might allow a reviewed, bounded diagnostic to leave the private workspace without authorizing the underlying fixture. The release decision must identify the content or approved transformation, recipient, purpose, and applicable task conditions, authorizing that named recipient for the exact approved content and use without rewriting the source labels. The approval must cover the fully joined proposal dependencies, including control choices, along with the exact bytes or trusted transformation the adapter will send. A reviewed diagnostic therefore never authorizes the underlying fixture, a later diagnostic, or a changed destination. Likewise, a redactor or schema validator acquires no release authority merely by changing how a value is represented.

Both decisions preserve provenance and their own scope in the runtime record rather than erasing all labels. A human can authorize an exact represented action when the applicable policy permits that approval, but clicking “approve” does not make a README claim true, waive an organizational restriction the approver cannot change, or authorize all later calls. A changed payload or destination needs the applicable checks again.

**Checkpoint 9.1: A valid value is not a permitted use**

The repair task allows selected external package searches and local tests, but not release of its private fixture. The reader extracts `claimed_tests_passed: true` from an external README. The planner has also seen the private fixture. For this search, the task policy accepts all sources in the joined query label as influences and permits no release exception.

**Evidence source**: May the runtime record the extracted boolean as a successful test? Name the source and version information it would need instead.

**Release vs. evidence check**: The planner proposes a schema-valid search query copied from the fixture. Which condition of [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-dispatch|equation 3]] fails, and which one holds?

**Control dependence**: The planner chooses one of two public package names according to a private fixture value. Compute ${\iota}$ and ${\kappa}$ of the resulting query with [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-join|equation 2]], and decide whether the search endpoint may receive it.

**Handle resolution**: The planner submits a typed fixture handle instead of bytes. Using [[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^eq-vol3-flow-deref|equation 4]], show why the search is rejected exactly as the bytes would be.

Information-flow policy connects source records to enforceable decisions about their use. It retains uncertainty about what untrusted content establishes and restricts where confidential dependencies may travel. Delegated identity supplies the other side of those decisions: which requester, task, and service policies authorize the operation or the release.
