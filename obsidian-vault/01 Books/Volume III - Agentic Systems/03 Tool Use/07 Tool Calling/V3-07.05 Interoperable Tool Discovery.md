# V3-07.05 Interoperable Tool Discovery

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-mcp

In practice, a tool implementation such as `conditional_replace_file` can live in several environments: an in-process adapter compiled into the application, a standalone background daemon, or a remote microservice managed by another team. Before the model can propose a valid call, the host runtime must determine which operations that endpoint exposes and how to encode their arguments. This discovery phase supplies that interface metadata. Under the grant rule, however, learning that an operation exists confers no authority to execute it. Discovery defines interface syntax, whereas authorization governs execution rights.

### The Model Context Protocol

^sec-vol3-tool-calling-mcp-protocol

When building a self-contained agent with a small, static set of tools, registering local functions directly in-process is simple and fast. However, when multiple host applications must connect to independently maintained tool services, custom point-to-point integration quickly becomes impractical. The underlying challenge is combinatorial. Without a shared interface, ${N_{\text{host}}}$ host runtimes integrating ${N_{\text{tool}}}$ tool services require up to ${N_{\text{host}}} \times {N_{\text{tool}}}$ bespoke adapters. Standardizing on a common protocol reduces this burden to ${N_{\text{host}}} + {N_{\text{tool}}}$ implementations, allowing each side to build to the specification once.

![[90 Assets/Volume III/07 Tool Calling/Tool Calling Margin Adapter Count 7584b486af.svg]]

*Two small graphs. Left: three host boxes each wired to four tool-service boxes, twelve crossing adapter lines, labeled N host times N tool. Right: the same hosts and services each wired once to a central protocol box, labeled N host plus N tool.*

*A shared protocol turns pairwise adapters into one implementation per side.*

Decoupling tools across a protocol boundary also provides fault isolation. When a tool runs in a separate process, a memory leak, segmentation fault, or unhandled blocking call crashes only the tool server rather than tearing down the primary agent orchestration loop. Even so, protocol standardization does not eliminate engineering responsibilities. Integrators must still define tool semantics, audit version compatibility, and enforce security policies. Local in-process plugins and out-of-process tool servers represent deliberate deployment trade-offs rather than mutually exclusive or evolutionary stages.

The **Model Context Protocol (MCP)** exemplifies this architecture. MCP structures integrations across three distinct entities: a host application (such as an interactive environment or agent runtime), clients that manage connections, and servers that expose capabilities. The host runs one client per connected server, and each client speaks the protocol on the host’s behalf. Servers can run as local child processes or as remote network services. This architectural division clarifies integration responsibilities rather than prescribing a specific execution sandbox ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-mcp2025specification|Model Context Protocol 2025]]).

Each deployment model matches different operational demands. A local child process keeps filesystem operations adjacent to the working copy and simplifies process lifecycle management. Conversely, a remote service can centralize credential storage, connection pooling, and backend access without replicating sensitive configurations across every host machine. Both options, however, introduce distinct failure modes and resource boundaries. An unconfined local process still reaches whatever local filesystem it is granted, while a severed network link can leave an in-flight operation executing invisibly on a remote server. The choice between them follows where resource governance and policy enforcement belong, weighing transport latency against tool execution duration rather than presuming any transport topology is universally superior.

### Tool Listing and Invocation

^sec-vol3-tool-calling-listing-invocation

Connecting a host client to multiple servers raises an immediate routing hazard: if two connected servers both advertise an `apply_patch` operation and the host dispatches calls by bare function name, an untrusted server can silently shadow the repository’s patch tool. Even though MCP separates discovery from execution through two primary wire operations (`tools/list` to discover available tool definitions and `tools/call` for execution[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn3|³]]), the host must bind each discovered definition to its specific server instance and local policy before exposing it. On the wire, each definition advertises a unique name, a natural-language description, and a JSON Schema governing accepted arguments; an invocation names the target tool and supplies a matching argument dictionary. These messages establish the mechanics of interface exchange rather than a task’s execution rights. The MCP tools specification ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-mcp2025specification|Model Context Protocol 2025]]) defines these message formats and mandates server-side input validation and access controls.

To trace where policy boundaries sit during execution, consider a repository server advertising two illustrative operations: `read_source` and `apply_patch`. A concrete integration sequence proceeds through several verification checkpoints:

1.  The host’s client queries `tools/list`, and the host admits each returned schema only if its own policy allows it (for example, because the server and its version are on an allowlist), binding each admitted schema explicitly to that server instance and its locally governed tool policy so no other server can shadow it.
2.  The host determines which admitted definitions to expose in the model context for the connection-pool repair task.
3.  When the model proposes an operation, the host runtime validates the arguments against the schema and verifies task-level authorization before transmitting the request.
4.  Upon receiving `tools/call`, the endpoint independently verifies the request against the underlying operating system permissions and data access controls it manages.

For the connection-pool repair, discovering that `apply_patch` exists leaves the permitted edit paths and the expected-version preconditions unchanged. The guarantee of atomic, conditional updates derives entirely from the server implementation, never from an encouraging function name. If an endpoint fails to provide conditional-update guarantees, the runtime must reject it as incompatible with the task’s safety contract.

### Discovery and Authority

^sec-vol3-tool-calling-discovery-authority

Just as an encouraging function name proves nothing about atomicity, a discovered `apply_patch` description that states “approved for all workspaces” or embeds instructions to steer the model is an untrusted external input, not an authorization grant. A description returned during discovery might accurately summarize an operation, omit critical failure modes, or attempt to redirect model behavior, and even an authenticated server can supply a misleading description because verifying a server’s identity does not imply endorsing every claim it emits.

Filtering which tools appear in the model prompt narrows the attack surface, but catalog filtering alone cannot replace per-call enforcement. Task grants evolve dynamically, and call arguments select specific resources at runtime. Authorizing an agent to inspect `src/pool.py` does not permit it to read unrelated credentials or transmit private source code to an external service. Defense in depth also requires the server or backing service to enforce its own perimeter rather than assuming every client performs flawless checks. Host authorization and endpoint authorization protect different assets and operational domains; neither supersedes the other. On the return path, protocol framing cleanly differentiates a tool result payload from a system message, but it does not disarm adversarial text within the payload. When ambient credential reach serves as the sole barrier between discovery and side effects, adversarial text in a tool result can steer the agent across repository boundaries (war story [7.1](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#ws-07-github-mcp-2025)).

↪ Prompt injection delivered through tool responses and other observations is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.03 The Adversarial Threat Model#^sec-vol3-security-injection-entry-points|Prompt injection entry points]]**.

**War Story 7.1: GitHub MCP private-repository leak (2025)**

**Context**: In May 2025, Invariant Labs demonstrated an attack on an agent connected to GitHub through its MCP integration ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-milanta2025github|Milanta and Beurer-Kellner 2025]]). The user owned both a public and a private repository and directed the agent, running in a desktop client, to inspect open issues in the public repository. The agent’s GitHub access token held permissions that spanned both repositories.

**Mechanism**: An attacker filed an issue in the public repository containing prompt instructions designed to redirect the model. After reading the issue as an ordinary tool result, the agent executed the server’s schema-valid tools to inspect the user’s private repositories and then opened a pull request in the public repository containing the exfiltrated contents. Every tool call remained within the personal access token’s broad credential scope, and no runtime check verified whether the target repository matched the task’s intended scope. Although the client prompted users to confirm tool calls by default, developers frequently enable an “Always Allow” setting to avoid operational friction.

**Impact**: The public pull request disclosed sensitive information, including the private repository name, relocation plans, and salary details. Invariant Labs characterized the breakdown as an architectural failure in agent runtime mediation rather than a software defect in GitHub’s server implementation.

**Fix**: The researchers recommended enforcing context-aware access control at runtime, such as restricting an agent session to the repository the user named, alongside continuous monitoring of agent-server traffic. They also observed that model alignment training alone failed to stop the attack.

**Systems lesson**: Discovery, schema validity, and credential authentication all succeeded. The failure was an absence of complete mediation (definition [7.1](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-complete-mediation)) against the task’s explicit grants, which should have refused the first private-repository read, a read-only ${A}_0$ action, well before any write occurred.

This exploit succeeded because three distinct conditions coincided:

1.  The agent ingested untrusted external text that mounted an indirect prompt injection, attacker instructions planted in data the agent reads as input ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-greshake2023not|Greshake et al. 2023]]).
2.  The agent held ambient authority broader than its active task required.
3.  The runtime provided tools capable of public mutations.

Eliminating any single condition breaks the attack chain. The second condition is the classic *confused deputy* problem ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-hardy1988confused|Hardy 1988]]), which the introduction glossed as the hazard of authority that comes from where a program runs rather than from the request it serves. The tool boundary is the first place the runtime must defeat it mechanically.

↩︎ The confused deputy, glossed alongside zero ambient authority, is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-fail-plausible|The fail-plausible fault]]**.

**Definition 7.3: Confused deputy**

A ***confused deputy*** is a program holding legitimate authority for one purpose that is manipulated into exercising that authority on behalf of a party with no right to direct it, because the system does not tie the authority exercised to the party directing the action.

1.  **Significance**: In an agent system the runtime is the deputy. It holds task credentials and dispatches tool calls, so every prompt injection is an attempt to borrow those privileges, and the authority level assigned to the task, from read-only inspection (${A}_0$) to irreversible external mutation (${A}_3$), caps what a successful injection can cost.
2.  **Distinction**: The attacker acquires no new credentials; it borrows authority the deputy already holds. Checking the deputy’s identity reveals nothing, because the deputy is legitimate. Authorization must instead check whether this request, within the active task, justifies exercising the deputy’s authority.
3.  **Common pitfall**: Approving an action because its model-generated rationale looks plausible. A justification such as “required for debugging” is part of the unverified request, not independent evidence that the operation is authorized.

In the GitHub incident, the agent exercised the user’s repository credentials on behalf of the remote attacker who wrote the issue text. Prompt injection and exfiltration channels need defenses of their own, but the tool boundary directly governs the second condition. The runtime defeats the confused deputy by evaluating every call against the task’s explicit grants rather than against the reach of the credential it happens to hold.

**Checkpoint 7.1: Discovery is not permission**

A repository server advertises a schema-valid `apply_patch` tool whose description says “use any path needed to complete the repair.” The current task permits edits only to its designated working copy. Later, a read result includes a request to upload repository contents to an external endpoint.

**Discovery vs. permission**: Which information does discovery supply, and which claimed permissions must the host refuse to derive from the description?

**Per-call checks**: Why must an allowed tool still be checked against the proposed arguments and current grants at dispatch? What must the endpoint enforce independently?

**Read authority**: Why does the read operation require authorization even though it does not edit a file?

**Returned text**: What do protocol framing and the provenance labels of context engineering establish about the returned text, and what do they leave open about its influence on the model?

**Placing the check**: In war story [7.1](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#ws-07-github-mcp-2025), at which call would a per-call check against the task’s grants have refused, and which of the three enabling conditions would that remove?

Discovery establishes how to address an operation, and authorization determines whether a given task may attempt it. Neither mechanism, however, resolves whether an in-flight mutation actually took effect when a network connection drops or a response times out. Because permission to initiate an action does not confer permission to blindly repeat it when the outcome is uncertain, robust execution requires explicit operation identity and idempotency guarantees.
