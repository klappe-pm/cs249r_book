# V3-07.10 Designing the Active Toolkit

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-toolkit-design

Across the `src/pool.py` repair, the agent has needed to inspect source files, apply candidate patches, run test suites, and read diagnostics, and how the runtime packages those capabilities into a toolkit can fail at either extreme. If each tool exposes too little functionality per invocation, the model must coordinate low-level state across dozens of turns. If the runtime instead exposes an unconstrained catalog, the context window fills with irrelevant tool schemas that consume input capacity and bloat prefill latency on every turn, and each extra descriptor is one more candidate the model must rule out. Whether those candidates lower selection accuracy for a given model and catalog is an empirical question that catalog evaluation ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.10 Designing the Active Toolkit#^sec-vol3-tool-calling-catalog-evaluation|section 7.9.3]]) measures rather than assumes. The goal of toolkit design is to expose operations so that the model can choose an appropriate next step without carrying unnecessary definitions or managing avoidable intermediate state.

Two design dimensions govern this trade-off. Granularity determines how much work an individual tool performs, while catalog selection determines which subset of tool definitions the model sees on any given turn, known as the **active toolkit**. A small catalog can contain either narrowly bounded primitives or a broadly expressive command runner, whereas an enterprise environment registering hundreds of specialized tools must stage them selectively rather than presenting the entire catalog on every turn.

### Static and On-Demand Staging

^sec-vol3-tool-calling-tool-staging

Serializing all 50 registered tool descriptors into every model call burns 15,000 tokens of context capacity on every turn even when a step needs only six tools, whereas selecting a narrow subset on demand risks omitting the one tool the repair needs next. In **static staging**, the runtime serializes a fixed set of tool descriptors into every request, keeping available interfaces predictable and eliminating separate discovery steps at the cost of carrying unused schemas on every turn. In **on-demand staging**, the runtime dynamically selects descriptors as the trajectory unfolds, shrinking the prompt footprint and prefill latency at the risk that an omitted tool forces the agent to spend extra turns locating it.

Selection mechanisms vary widely in implementation complexity. A runtime can employ deterministic task-to-tool mappings, hierarchical namespace menus, keyword matching, dense vector retrieval, or a combination of these approaches. Dense retrieval represents one possible search technique rather than a universal requirement for large catalogs. Any match returned by a retriever is merely a candidate descriptor. A robust systems design provides a bounded fallback path, such as a dedicated tool-search operation or an explicit discovery-failure signal, so that an omitted descriptor does not cause the model to conclude erroneously that the operation cannot be performed.

Staging a descriptor makes its syntactic and semantic contract visible to the model; under the grant rule, staging confers no execution privileges. The runtime must still resolve and authenticate every proposed invocation against registered tool identities and permissions before execution. If a dynamic discovery step returns a modified or re-versioned descriptor, the runtime must reconcile that version before executing it, preventing the model from dispatching against an interface different from the one it was provided.

Tool definitions consume prompt capacity alongside system instructions, source excerpts, previous observations, and generation headroom. Systems engineers must measure the final serialized request, including formatting delimiters, wrapper schemas, and selection metadata, rather than tallying independently tokenized description fragments under the false assumption that token boundaries are free. The following notebook counts the catalog-related input for a single model request.

*Selection frees most of the catalog’s input, on every call.*

**Napkin Math 7.4: The input budget of an active catalog**

**Problem**: How much next-call input capacity does a selected catalog release after counting its additional framing and selection information?

**Variables**: Suppose a registered catalog has 50 tools. Each complete descriptor contributes 300 tokens, including its share of catalog framing. The alternative stages 6 of the same descriptors plus 400 additional tokens for the selection interface and metadata. These are stipulated contributions within the final serialization, with other request content unchanged. In this scenario the runtime selects the subset without another model call.

**Math**: Full staging uses $50 \times 300 = 15{,}000$ tokens. The selected descriptors plus selection overhead use $6 \times 300 + 400 = 2{,}200$ tokens. The released capacity is therefore $15{,}000 - 2{,}200 = 12{,}800$ tokens.

**Systems insight**: Selection pays whenever its overhead is smaller than the unused descriptors it removes, $({n_{\text{reg}}} - {n_{\text{sel}}})\,{S_{\text{desc}}} > {S_{\text{sel}}}$ for ${n_{\text{sel}}}$ of ${n_{\text{reg}}}$ descriptors of ${S_{\text{desc}}}$ tokens each and ${S_{\text{sel}}}$ tokens of selection overhead. Here that is 400 against 13,200 tokens. Break-even sits at about 1.3 unused descriptors, so the saving grows linearly with catalog size. The released capacity recurs on every call that would have carried the full catalog, so over a trajectory it multiplies by the number of turns, like the carried observation in notebook [7.2](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#nbk-07-observation-budget). The comparison flips when selection needs its own model call or a missed tool forces rediscovery; those calls belong in the same token count.

Static and selected catalogs also interact differently with prefix caching in serving runtimes. When an inference engine uses radix-tree or hash-based KV cache reuse, maintaining an identical serialized prefix across turns allows the engine to bypass prefill computation for earlier prompt segments. Static staging preserves a stable prompt prefix across calls, maximizing cache reuse as long as earlier conversation state remains intact. Conversely, modifying descriptors or reordering them across turns moves the point of prompt divergence earlier, invalidating downstream cached KV blocks and forcing redundant prefill computation. Caching also changes what selection buys. If the full catalog sits in a cached root billed at 10 percent of the uncached price, as assumed in notebook [7.2](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#nbk-07-observation-budget), the dollar value of the tokens that selection releases in notebook [7.4](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#nbk-07-memory-footprint-and-prefill-latency) shrinks by the same factor of 10. The released context capacity is unchanged. Once caching applies, selection pays mainly in capacity for task evidence rather than in money. A hybrid strategy applies the change-rate ordering of **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-staging|Staging the Next Invocation]]** to the catalog: an immutable core of common descriptors sits in the stable root of the prompt, and task-specific additions are appended later. Even so, systems designers must not retain obsolete or revoked definitions merely to retain a cache hit, as doing so exposes outdated interfaces to the model. Removing an earlier temporary tool definition also alters the prompt prefix for subsequent turns, invalidating the cached state of the assistant responses and observations that followed it.

↩︎ Radix-tree prefix caching and KV block reuse across prompt turns are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kvcache-radix-tree|Prefix Caching Across Turns]]**.

### Tool Granularity

^sec-vol3-tool-calling-granularity

Whereas staging decides which tools appear on a turn, granularity decides how much operational work each call encapsulates. A file-editing interface built from separate `open_file`, `seek_cursor`, `write_bytes`, and `close_file` tools forces the model to spend four turns and manage raw file descriptors, cursor offsets, and cleanup across the trajectory only to apply a one-line patch. Classic systems modularity principles apply directly here. Parnas established that effective module boundaries hide design decisions that are subject to change ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-parnas1972criteria|Parnas 1972]]). Ousterhout formalized this criterion through deep vs. shallow interfaces, measuring how much implementation complexity an abstraction hides relative to the surface area it exposes ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-ousterhout2018philosophy|Ousterhout 2018]]). The same principles hold in agent systems, where tool interfaces designed around an agent’s editing, navigation, and testing patterns raised task success rates on software engineering benchmarks ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-yang2024sweagent|Yang et al. 2024]]). A **deep interface** encapsulates substantial functionality behind a concise contract, whereas a shallow interface exposes almost as much complexity as it implements. Decomposing a file edit into `open_file`, `seek_cursor`, `write_bytes`, and `close_file` is warranted only when intermediate inspection is an explicit requirement.

A task-level patch operation moves mechanical file manipulation behind the tool implementation, returning a unified diff, a resulting version hash, or an explicit conflict. The conditional-edit contract in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-schemas|section 7.3]] illustrates this boundary. However, interface naming alone does not guarantee transactional safety. If an operation advertises all-or-nothing execution, the underlying implementation must enforce that atomicity across its mutation scope and failure modes. When operations span multiple files or distributed endpoints, partial side effects can occur, and the runtime must report those partial outcomes explicitly in the tool observation. Bundling multi-step work into a single tool call reallocates responsibility from model planning to runtime execution, but the underlying systems obligations remain intact. For the same edit, the shallow composition spends four model calls where the task-level operation spends one ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.10 Designing the Active Toolkit#^fig-vol3-deep-vs-shallow-interface|figure 4]]).

![[90 Assets/Volume III/07 Tool Calling/Deep Vs Shallow Tool Interface fb05bf810c.svg]]

Figure 4: **Shallow and deep interfaces for one edit**: The low-level composition (a) spends four model calls and places a handle, a cursor, and cleanup in the trajectory between them. The task-level operation (b) spends one call and moves the version check and the change behind the interface, returning either a diff with its new version or a version conflict. The deeper interface is all-or-nothing only if its implementation provides that property; either way, the obligations move rather than disappear.

^fig-vol3-deep-vs-shallow-interface

Careful toolkit design does not require eliminating all overlapping capabilities. A system can effectively combine a structured search tool that returns abstract syntax tree (AST) matches with an authorized shell runner that supports complex log analysis beyond the search tool’s schema. To prevent model confusion, their descriptors must articulate clear functional boundaries, target inputs, and operational limits. Providing duplicate tools with near-identical names and indistinguishable schemas adds selection noise without expanding capability; in contrast, providing complementary interfaces with distinct observation formats, coverage scopes, or authorization grants offers substantial utility. [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.10 Designing the Active Toolkit#^tbl-vol3-toolkit-granularity|Table 4]] summarizes how these interface styles partition responsibility between the model and runtime.

| Interface style                   | Work assigned to the model                                   | Work assigned to the implementation                                                           |
|:----------------------------------|:-------------------------------------------------------------|:----------------------------------------------------------------------------------------------|
| Low-level composition             | Select intermediate operations and manage their dependencies | Validate each operation and expose handle, status, and cleanup semantics.                     |
| Task-level operation              | Specify a bounded intent, such as a patch or a test target   | Implement preconditions, mutation boundaries, and interpretable results for that task.        |
| General command or program runner | Construct a program that expresses the intended work         | Enforce execution grants and resource limits, supervise the job, and return bounded evidence. |

Table 4: **Toolkit granularity and responsibility**: Broader composition and task-specific interfaces place different obligations on the model and implementation; neither column substitutes for authorization or containment.

^tbl-vol3-toolkit-granularity

An argument schema constrains the syntactic format of a request, but it cannot constrain the underlying code execution. A specialized symbol-renaming tool may parse external ASTs, inspect secondary source trees, or execute defective third-party libraries. A narrow signature provides safety only when the implementation and its surrounding execution sandbox enforce that advertised boundary. Conversely, a shell runner’s blast radius is defined by its working directory, operating-system privileges, credential access, and network egress rules. Because the side effects of an expressive shell command cannot be reliably determined by inspecting its arguments, the runtime must rely on containment to enforce isolation.

↪ The isolation envelope that enforces a command’s reach regardless of its arguments is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^sec-vol3-sandboxes-microvms|Choosing an Isolation Envelope]]**.

Tool implementations should also adopt defensive defaults that fail visibly. When an agent provides an ambiguous file path or target identifier, rejecting the call with an informative diagnostic is far safer than guessing or silently appending data, as appending is a stateful mutation that can silently duplicate configuration entries. A dry-run mode allows the model to inspect a proposed diff against the current workspace state before committing changes; the runtime must still enforce approval gates and verify preconditions at execution time. These defensive defaults make operational failures interpretable, but engineers should remember that rollback capabilities and high-fidelity simulation are properties of the underlying tool implementation, not inherent guarantees of the interface.

### Catalog Evaluation

^sec-vol3-tool-calling-catalog-evaluation

Choosing between those granularity and staging options requires measuring end-to-end trajectories rather than single-step accuracy. Comparing a 12-tool structured catalog against a single `run_shell` tool by tool-selection accuracy alone makes the shell runner look superior, because the model cannot pick the wrong tool name out of a catalog of one. That comparison hides the unconfined mutations and recovery turns the shell introduces. Evaluating toolkit designs therefore requires holding all other experimental factors constant (the benchmark task distribution, initial workspace snapshots, model checkpoints, generation parameters, token budgets, and verification suites). The trials must also exercise realistic failure modes across the connection-pool repair workload. These include locating relevant source files across deep directory hierarchies, applying patches against concurrently modified buffers, interpreting noisy test failure logs, and recovering when a needed descriptor is omitted from the initial active toolkit. Those trials separate catalog coverage gaps from model selection errors, and separate selection accuracy from execution-time runtime failures.

Because a recovered selection error costs extra inference turns and latency whereas an unrecovered error aborts the task, evaluation logs must record selection errors, malformed arguments, rejected preconditions, extra discovery calls, recovery turns, and uncontained side effects alongside binary task completion. Cost accounting sums serialized descriptor tokens, retrieval latency, sandbox compute time, observation overhead, and tokens spent on failed attempts. Toolkits can then be ranked by total cost per accepted task (${C_{\text{eff}}}$) rather than by the probability of avoiding a single selection error. Any comparison between designs with different security postures, such as an unconstrained command runner vs. a scoped AST manipulation tool, must report those privilege differences explicitly rather than attributing the gap to catalog size alone.

The ultimate objective of toolkit engineering is an active catalog whose contracts align with workload demands while keeping execution costs and failure modes transparent. Static staging, on-demand selection, task-level abstractions, and expressive command runners represent trade-offs to evaluate against these cost and reliability metrics. The same engineering principles apply when an agent interacts with a graphical user interface instead of a programmatic API: mouse clicks, keyboard events, and visual screen parsers impose their own granularity challenges, prefill budgets, and containment boundaries.
