# V3-07.11 Visual Actuation and Computer Use

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-visual-actuation

Consider the staging-container restart scenario when an administrative web dashboard provides no programmatic API. A **computer-use tool** bridges this interface gap by rendering visual screenshots to the model and translating model-generated targets into synthetic mouse clicks, keystrokes, or scrolling gestures, the low-level input space pioneered in early web-agent research ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-shi2017world|Shi et al. 2017]]). Operating on raw pixels does not relax system invariants. While the model proposes an interaction based on an observed frame, the execution runtime retains responsibility for validating arguments, enforcing authorization, dispatching OS events, and interpreting observations. A coordinate within display boundaries merely confirms that an event can reach the window manager, offering no assurance about the state mutation that the event will trigger.

### An Action Against a Changing Surface

^sec-vol3-tool-calling-changing-surface

In that web dashboard, suppose the agent observes a confirmation modal for restarting the staging container `srv-stage-04` and proposes clicking the Restart button at screen coordinates $(640, 420)$. Milliseconds before the click is dispatched, however, an alert pops a production container dialog into the foreground at those exact coordinates. Controlling a graphical surface requires the same interface contract used for structured tool calls, adapted for spatial and temporal change where a coordinate pair does not identify the underlying resource. When the runtime captures an observation, it records the application and window identifier, a unique capture identifier, an observation timestamp, and the exact geometric frame presented to the model. If the runtime downsamples, pads, or crops the image before model ingestion, it must retain the crop offsets and scaling factors needed to project a proposed coordinate back into the native display coordinate space. Raw screenshot pixels, application-relative window coordinates, and virtual desktop coordinates represent distinct spatial reference frames. The runtime adapter must validate all proposed points against the active viewport. Silently clamping out-of-bounds coordinates to the nearest edge risks turning an invalid model hallucination into a destructive click on an unintended adjacent control.

Before dispatching the proposed click on the Restart button, the adapter must recheck the current application focus, active window state, and target dialog parameters using platform accessibility or windowing APIs. If a background network event or concurrent operator action has brought a production container dialog into the foreground at those screen coordinates, valid spatial coordinates no longer justify executing the model’s proposal. The runtime must detect the stale precondition, abort the pending dispatch, and request a fresh visual observation. While benign updates such as a ticking taskbar clock do not invalidate a target, any modification to a resource identifier, modal overlay, or button layout alters the operational effect.

Once the staging dialog is re-verified, the policy engine must evaluate the session grant against the intended container restart rather than checking a generic permission to emit mouse clicks. If the interface cannot establish which backend operation the click will execute with the confidence required by the security policy, the runtime must block dispatch and escalate the decision to an authorized operator. Otherwise, the adapter dispatches the bounded input event and records its immediate outcome. Structured endpoints enforce resource identity and action preconditions directly at the server interface, providing a robust execution boundary. By contrast, visual actuation cannot achieve atomic execution. Capturing a fresh screenshot reduces staleness, but it cannot prevent a concurrent state change from slipping between the observation capture and the event dispatch.

After dispatching the input event, the subsequent observation must verify operational progress rather than mere input delivery. A disappearing confirmation modal might indicate that the server accepted the restart command, but it might also mean that a network timeout dismissed the dialog without action. The runtime must gather corroborating evidence of the restart, either by inspecting a refreshed dashboard status indicator or by issuing an authorized read-only status query. If the click produces no visible change and the dashboard continues displaying the previous state, the requested operation might still be processing asynchronously. Under these conditions, the execution yields an uncertain outcome (definition [7.4](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-uncertain-outcome)), which the runtime must resolve through the idempotency and reconciliation protocols detailed in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|section 7.5]] rather than by repeatedly firing redundant clicks.

### Visual Observation Budgets

^sec-vol3-tool-calling-visual-budgets

Verifying each visual step with a fresh screenshot carries a steep context cost: retaining one high-resolution desktop screenshot per turn converts each frame into thousands of visual tokens and multiplies that payload across every subsequent turn of a computer-use trajectory. Vision encoders partition input images into fixed-size grid patches, and because visual token consumption directly inflates inference latency and per-turn billing, systems engineers must monitor both the raw byte representation submitted to the model and its resulting token allocation. A screenshot is priced like any other staged observation: its token count plays the role of ${S_{\text{shaped}}}$ in notebook [7.2](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#nbk-07-observation-budget), and every later call that retains it multiplies that count by ${H_{\text{rem}}}$. This is why the techniques below shrink the per-frame count and why retention policy matters as much as resolution.

↩︎ How a vision front-end turns an image into reserved context positions, and how one image can overflow a request’s headroom, is established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.04 Tokenizing the Request#^sec-vol3-foundation-model-multimodal-accounting|Counting multimodal inputs]]**.

Naively compressing visual inputs introduces sharp engineering trade-offs. Downscaling an entire screen capture reduces token consumption, but blurs fine visual details such as container names, port numbers, or warning banners until they become unreadable. Conversely, tightly cropping the image preserves full pixel resolution around a candidate button, but strips away peripheral context, concealing modal warning banners or active window titles that are essential for correct interpretation.

A resilient architecture balances these demands through hierarchical visual sampling: capturing a low-resolution full-screen overview to establish window layout and focus, paired with an on-demand, high-resolution crop around the target interaction zone. Each visual artifact must retain its parent observation identifier and affine coordinate mapping so the runtime can translate local crop coordinates back to native display space. Similarly, transmitting visual diffs of modified screen regions reduces payload size during iterative tasks, provided the diff retains sufficient surrounding landmark geometry for the vision model to orient itself. Because large language model inference engines rely on exact prefix matching for KV-cache reuse, altering a visual frame across turns invalidates cached prefixes for all subsequent tokens. A well-designed observation budget delivers the minimal visual evidence necessary to authorize and execute the next operational decision while keeping token consumption bounded.

**Checkpoint 7.4: A click is still a tool call**

A dashboard changes after the model observes a staging restart dialog. The adapter can capture the display and send a click, but cannot atomically bind that click to the displayed resource.

**Target identity**: Which changes require rejecting the old proposal, and why is a coordinate-range check insufficient?

**Observation geometry**: What information must accompany a resized crop so a proposed point can be mapped to the intended surface?

**Authority and freshness**: What does a new screenshot establish, and which action-time uncertainty remains before dispatch?

**Effect evidence**: If the click times out and the old status remains visible, why is another click not automatically justified? What evidence would support the intended restart without claiming the whole task is complete?
