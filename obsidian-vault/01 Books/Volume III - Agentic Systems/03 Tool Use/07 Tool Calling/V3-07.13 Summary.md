# V3-07.13 Summary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-summary

Every runtime mechanism in this chapter enforces one discipline. An agent may base its next decision only on what returning evidence directly confirms. A schema validates the syntactic shape of a request, an authorization grant restricts its permissible targets, an endpoint check enforces execution preconditions and timing, and an observation reports what the tool actually measured. None of these mechanisms assumes that a proposed operation successfully altered external state, nor does a completed execution guarantee that the broader task has succeeded. When evidence is missing, as it was after the timed-out staging restart, the runtime must record the evidentiary gap explicitly rather than interpolating an assumed outcome. **Key Takeaways: A tool call includes its returning evidence**

- **A call ends at its observation, not its dispatch**: The runtime matches each returning result to its corresponding invocation, recording whether the proposal was rejected, dispatched, completed, or left in an indeterminate state. Subsequent planning must reason strictly from this confirmed disposition rather than assuming an action succeeded because the host dispatched it.
- **Schemas shape requests; enforcement governs effects**: Type signatures and parameter descriptions guide the model to structure valid calls, but authorization grants, resource quotas, and precondition checks govern actual execution. Any mutation that depends on an unchanged target resource must verify preconditions atomically alongside the write, rather than relying on stale observations from an earlier read.
- **Discovery does not confer permission**: Exposing a tool interface in the context window reveals structural syntax, but connectivity and schema compliance never imply authorization. The host runtime must validate every invocation against task-scoped grants, including read-only queries, while the remote endpoint enforces its own perimeter independently.
- **An unknown effect forbids blind repetition**: Because a timed-out attempt may have committed before network acknowledgment was lost, duplicate side effects track reply loss rather than request loss. The runtime may retry an unacknowledged invocation only under provably idempotent semantics, an endpoint deduplication contract, or explicit probe reconciliation. Otherwise, it must preserve the operation as an unresolved effect.
- **Truncation must disclose what it dropped**: Buffer limits and model context windows constrain distinct physical resources, yet both force data omission. An observation payload that incorporates execution status, provenance metadata, and a measured omission counter preserves diagnostic integrity, whereas silent head truncation often discards the terminal error or stack trace needed to diagnose a fault.
- **Acknowledgment is not completion**: Long-running jobs require durable handles, scoped inspection, authorized input channels, and unambiguous cancellation outcomes. Event-driven runtime detection re-awakens the model only when a state change can alter the next action, preventing empty polling loops that burn inference budgets on uninformative checks.
- **No toolkit size is universally optimal**: Catalog staging and API granularity navigate a trade-off among context overhead, selection accuracy, expressiveness, and security boundaries, while visual interfaces introduce freshness and target-geometry constraints. System designers must evaluate a toolkit by its total cost per accepted task and the precision of the authority it leaves bounded.

The typed action contract (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-strict-action-abi|7]]) separates an interpretable proposal emitted by the model from the authorization required to execute it. When network drops or timeouts leave an outcome ambiguous, settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]) extends that discipline to prevent silent state corruption. The runtime must either establish that repeating the call is safe or record an unresolved effect. A tool’s completion report, however, confirms only that an operation finished, not that the overall task succeeded. Final acceptance always demands invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]), verifying that the system’s operational requirements hold in reality before declaring success.
