# V3-07.06 Retrying Uncertain Actions

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-idempotency

Permission to initiate the staging restart `POST /containers/srv-stage-04/restart` does not settle what happened when its socket times out. At that timeout, the client cannot tell whether the request was dropped in transit, delayed in a network queue, still running inside the daemon, halted after partially reconfiguring the service, or completed with only its acknowledgment lost. A client-side timeout[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn4|⁴]] records only that the caller stopped waiting for a response; it conveys no information about endpoint execution state ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-cristian1991understanding|Cristian 1991]]). Deciding what to do next requires two orthogonal pieces of knowledge, the operation’s repeat behavior and evidence about the earlier attempt, and prompting the model to retry supplies neither. Settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]) permits repeating an uncertain mutation only after its repetition has been shown safe; otherwise the runtime records the mutation as unresolved.

**Definition 7.4: Uncertain outcome**

***Uncertain outcome*** is the recorded status of a dispatched operation whose effect the runtime can neither confirm nor exclude, because its reply was lost, late, or never produced. The operation stays unsettled until an endpoint deduplication contract, a reconciliation query, or an authorized decision establishes what happened.

1.  **Significance**: An unsettled mutation blocks any retry that could duplicate it. Under blind retry, the duplicate rate tracks the reply-loss rate almost one for one (notebook [7.1](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#nbk-07-settlement-budget)).
2.  **Distinction**: A definite failure provides actionable knowledge, whereas an uncertain outcome represents missing information. A network timeout leaves the execution unknown; it does not make it a failure.
3.  **Common pitfall**: Recording a timed-out restart as a definitive failure, which improperly authorizes the very retry that duplicates the mutation.

### Delayed Attempts

^sec-vol3-tool-calling-delayed-attempts

Suppose the runtime dispatches restart attempt A, the network buffers the packet in transit, and when the client timeout fires, a status probe reports that the container has not restarted. If the runtime treats that unchanged state as proof that attempt A was dropped and dispatches attempt B, attempt B restarts the container first and the delayed attempt A arrives moments later to restart it a second time. A probe that reads an unchanged service state reports the present accurately, yet it cannot guarantee that a delayed request will not execute in the near future.

![[90 Assets/Volume III/07 Tool Calling/Tool Calling Margin Delayed Attempt f848ffc50e.svg]]

*Timeline with a runtime lane and a service lane. Attempt A leaves the runtime as a long dashed arrow. The runtime times out, probes the service, and hears unchanged. Attempt B then arrives and causes restart 1; the delayed attempt A lands afterward and causes restart 2, labeled second restart.*

*An unchanged probe cannot rule out an attempt still in flight.*

The probe returned accurate telemetry, but the runtime drew a flawed inference, mistaking “not yet observed” for “cannot still happen.” An attempt already executing inside the service produces an identical hazard. Sending an asynchronous cancellation request settles this ambiguity only if the endpoint explicitly confirms what halted and whether any side effects committed or could still commit. Safe repetition therefore demands much more than a client timeout followed by an optimistic read.

### Idempotent Actions

^sec-vol3-tool-calling-idempotent-actions

Setting a configuration field to `"timeout_ms": 5000` twice leaves the field at `5000`, whereas incrementing a counter, appending a log entry, or restarting a container produces a second event on the second call. Deciding whether to retry an unacknowledged tool call therefore depends on the physical consequence of running the operation a second time, which is captured by whether the operation is idempotent.[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn5|⁵]]

**Definition 7.5: Idempotent action**

***Idempotent action*** is an operation whose repeated application has the same effect on a specified state as one application, ${f}({f}({s})) = {f}({s})$, under the operation’s stated conditions.

1.  **Significance**: Idempotence is the cheapest settlement. A timed-out idempotent call can be retried without reconciliation, which removes the duplicate-effect path priced in notebook [7.1](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#nbk-07-settlement-budget).
2.  **Distinction**: The property belongs strictly to the implemented operation and its target state; it does not guarantee identical network responses, zero resource consumption, or isolation from concurrent writes by other processes.
3.  **Common pitfall**: Assuming idempotence from an HTTP verb or tool name alone. Operations such as restarting a service or appending a log entry introduce new state transitions on every invocation, regardless of the API naming convention.

Whether an operation is idempotent depends on the endpoint’s implementation rather than its name or HTTP verb. [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^tbl-vol3-tool-idempotency|Table 2]] sorts the three repeat semantics at the tool boundary by what a second execution means and what the runtime must still check before allowing one.

| Operation semantics               | What repetition means                                    | What the runtime must still consider                                                           |
|:----------------------------------|:---------------------------------------------------------|:-----------------------------------------------------------------------------------------------|
| Read without an intended mutation | Obtain another observation, possibly of a changed source | Access and disclosure permission, resource cost, and the version the result describes          |
| Set a desired state               | Reapply a value that may already hold                    | Intervening writes, conditional-update rules, and any additional effects the endpoint performs |
| Produce another event             | Append, charge, restart, or otherwise add an effect      | A deduplication contract or sufficient evidence that another execution is safe                 |

Table 2: **Repeat behavior at the tool boundary**: Safety follows the implemented operation and its conditions, not a universal classification of tool names.

^tbl-vol3-tool-idempotency

The repair’s conditional update, a set-a-desired-state operation in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^tbl-vol3-tool-idempotency|table 2]], shows why the classification alone does not settle a timeout. Suppose a repair tool predicates its patch on source version `r17`. Once it installs `r18`, repeating the conditional request cannot accidentally overwrite subsequent edits, provided the endpoint checks the version and applies the write atomically. The repeated request returns an optimistic concurrency conflict rather than a success status. While this atomic check protects the repository from corruption, it leaves open the question of whether the earlier attempt or a competing process committed `r18`. Resolving that attribution requires tracking operation identity across attempts. The endpoint must retain each operation’s result and return it to a repeated request, which is the deduplication contract of [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|section 7.5.3]].

Repeat behavior operates along an orthogonal axis from the authority levels ${A}_0$ through ${A}_3$ defined in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-hsa|The H·S·A Exposure Space]]**. An authority level governs whether an agent may execute an action autonomously; repeat behavior dictates whether the runtime can safely re-execute that action after an ambiguous failure. These concerns intersect directly at level ${A}_2$, which is reserved for external operations backed by well-defined compensating actions and a separate retry policy preventing duplicate effects. An external tool call qualifies for ${A}_2$ autonomy only if an executable compensation handler is in place and the runtime settles every transport timeout prior to retrying, relying on verified idempotent semantics, an endpoint deduplication contract, or bounded reconciliation. The staging restart that opened this chapter is such a call. It is an external mutation that adds an event on every execution, so the remediation agent may run it at ${A}_2$ only if that compensation contract is in place and its timeout can be settled by one of those three means.

**Napkin Math 7.1: Which retry path duplicates an effect?**

**Problem**: Suppose inbound requests and outbound replies are lost independently, with request-loss probability ${q_{\text{req}}}$ and reply-loss probability ${q_{\text{rep}}}$, each 2 percent. Every delivered request executes successfully, and every caller timeout triggers exactly one blind retry of a non-idempotent operation without deduplication. Dropped packets are assumed to be permanently lost rather than delayed. What is the probability that a single dispatched action executes more than once, and how many duplicate mutations will an agent fleet induce each day?

**Math**: The initial attempt times out whenever the outbound request or the returning reply is lost, with probability $\Pr(\text{timeout}) = 1-(1-{q_{\text{req}}})(1-{q_{\text{rep}}})$, here $1-(1-0.02)(1-0.02)$, or 3.96 percent. Producing an unintended duplicate mutation requires a specific sequence. The original request must reach the endpoint, its confirmation reply must be lost in transit, and the subsequent retry request must successfully reach the endpoint, so $\Pr(\text{dup}) = (1-{q_{\text{req}}})\,{q_{\text{rep}}}\,(1-{q_{\text{req}}})$. With the assumed rates:

$\Pr(\text{duplicate effect}) = (1-0.02)\times 0.02\times(1-0.02)$

This evaluates to 1.9208 percent. Whether the retry’s own confirmation reaches the caller has no bearing on whether the endpoint mutated twice. In a fleet of 50 workers where each worker executes 4,000 mutating calls per day, the system processes 200,000 daily calls. Under this naive retry policy, the fleet triggers approximately 3,842 duplicate mutations every day.

**Systems insight**: The duplicate execution rate tracks the reply-loss rate almost one-to-one because creating a duplicate requires losing a reply between two successfully delivered requests. Losing an initial request produces only an unexecuted, harmless timeout. While halving reply loss reduces duplicate mutations by half, implementing an endpoint deduplication contract eliminates this failure mode entirely. At production scale, protocol-level deduplication contracts, not network hardening, serve as the primary reliability control. This simplified model ignores delayed packets, which introduce additional duplicate execution paths.

### Operation Identity and Endpoint Contracts

^sec-vol3-tool-calling-operation-ids

If a runtime derives deduplication keys by hashing the tool name and arguments, a deliberate second restart of `srv-stage-04` an hour later collides with the first and is silently skipped. If it generates a fresh key on every timeout, every retry executes as a brand-new restart. A **logical operation ID**, commonly called an idempotency key in transactional storage and payment systems, identifies a single intended effect across multiple transport attempts. As Pat Helland observed, any distributed messaging substrate that survives network partitions and process crashes must occasionally retransmit packets. Consequently, the receiving endpoint, rather than the transport network, must assume responsibility for rendering duplicate messages harmless ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-helland2012idempotence|Helland 2012]]). An **attempt ID**, in contrast, tracks an individual request-response exchange over the wire. When the agent runtime retries an unacknowledged restart, it preserves the original operation ID while generating a fresh attempt ID for transport tracing. When the agent later issues a distinct request to restart the same container, the runtime allocates a new operation ID even though the arguments are identical.

An operation identifier provides safety only when governed by an explicit endpoint contract. This contract binds the operation ID to the caller’s identity, the target resource scope, and the serialized payload. If a client reuses an active operation ID with mismatched arguments, the endpoint must reject the request with a client error (such as an HTTP 409 Conflict) rather than silently dispatching a mutated operation. The endpoint must also enforce access control independently on each attempt, because possessing a valid operation token does not substitute for authorized credentials when dispatching actions or retrieving retained execution results.

The contract must also govern concurrent and interleaved requests. If a duplicate request arrives while the original attempt is actively executing, the endpoint should return an in-progress or pending status instead of spawning a parallel worker. If a duplicate arrives after execution finishes, the endpoint returns the previously computed and retained result. To uphold this guarantee under crash failures, the endpoint’s persistence mechanism must atomically link the side effect with its stored completion record. If a worker applies the mutation and crashes before persisting the result, a simple log of request receipt cannot prove that re-execution is safe. Where the underlying resource supports it, enclosing both the mutation and the result record within a single database transaction guarantees atomic state transitions. When acting against external services lacking transactional boundaries, the endpoint must coordinate with the downstream system’s native deduplication mechanisms. Every request therefore ends in one of four outcomes of the endpoint’s lookup, and only an unseen operation ID executes ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^fig-vol3-idempotency-flow|figure 2]]).

![[90 Assets/Volume III/07 Tool Calling/Idempotency Nonce Execution Flow c373014969.svg]]

Figure 2: **One operation, many attempts**: The runtime creates the operation ID once and gives each attempt a fresh attempt ID, so a timeout leads either to another attempt of the same intent or, once attempts run out, to an unresolved outcome. The endpoint’s lookup, scoped to caller and resource within its retention window, decides whether a request returns a retained result, a pending status, or an ID conflict, or executes. Only the last branch applies the effect. Recording the result inside the same transaction boundary, where the effect permits one, keeps a crash from leaving an applied effect without the record that deduplicates its retries.

^fig-vol3-idempotency-flow

[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^lst-vol3-dispatch-operation-id|Listing 3]] illustrates the client runtime’s implementation of this protocol. The runtime assigns the operation ID once upon admitting the intended mutation, then generates a fresh attempt ID for every network transmission. If repeated retries exhaust the attempt budget, the function returns an explicit unresolved outcome rather than propagating an uncaught exception. This design ensures that transport uncertainty surfaces directly to downstream reconciliation logic rather than disappearing into an unhandled error path. Because this retry loop is safe only when the remote endpoint guarantees deduplication, the runtime invokes this path exclusively for tools whose descriptors formally declare compliance with the operation ID contract.

↪ Recording each admitted operation and its identity durably before dispatch, so that recovery can find every effect that may have begun, is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-persistence-wal|Durable Intent Before Dispatch]]**.

``` python
def dispatch_mutation(transport, tool, args, op_id, max_attempts=3):
    # op_id was created once, when the runtime admitted this intent.
    for attempt in range(max_attempts):
        try:
            reply = transport.post(tool, args,
                                   operation_id=op_id,
                                   attempt_id=new_attempt_id(),
                                   timeout_s=transport.timeout_s)
        except (TimeoutError, ConnectionError):
            backoff(attempt)
            continue                     # same op_id; endpoint deduplicates
        if reply.status == "id_conflict":  # op_id reused with other args
            return {"op_id": op_id, "outcome": "rejected"}
        return {"op_id": op_id, "outcome": reply.status,  # completed or
                "result": reply.result}                   # pending
    return {"op_id": op_id, "outcome": "unresolved"}    # reconcile next
```

Listing 3: **Retrying one intended effect**: The operation ID stays fixed across attempts, and exhausting the attempts yields an unresolved outcome. The loop is safe only against an endpoint that deduplicates by operation ID within its retention window.

^lst-vol3-dispatch-operation-id

Operation IDs deduplicate retries of one intent by one caller. A different hazard arises when two copies of the caller both believe they own the work, as happens when the runtime restarts or hands a trajectory to a replacement worker while the original is only stalled. Distributed schedulers commonly coordinate such assignments through leases, time-bounded claims on granted authority. If a worker encounters an unobserved execution stall (such as a lengthy garbage collection pause or network blip), its lease may expire. The orchestrator reassigns the task to a second worker while the first worker remains active, creating a split-brain scenario where both workers execute mutations concurrently. Sizing lease durations well above the p99 of observed execution latency reduces the frequency of overlapping executions, but statistical padding cannot eliminate the failure mode entirely. True mutual exclusion requires fencing at the destination resource, such as associating every task reassignment with a monotonically increasing epoch number that the destination endpoint verifies on every write before committing state changes.[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn6|⁶]] Operation IDs and fencing are complementary: the first makes a repeated request harmless, and the second refuses a request from a caller that no longer owns the work.

↪ Leases, fencing tokens, and the handoff where a stale owner’s delayed write meets the new fence are collected for reference in **[[05 Reference/Volume III - Agentic Systems/V3 Distributed State Foundations#^sec-vol3-appendix-systems-fencing|Leases and Fencing]]**.

A deduplication contract is incomplete without an explicit retention window. Endpoints must publish how long they retain operation IDs and cached results, as well as how they handle delayed requests that arrive after that retention boundary has elapsed. Once the retention window expires, resubmitting an old operation ID risks being treated as a brand-new request, reintroducing duplicate-execution risks. An idempotency token prevents duplicate execution only when paired with active endpoint deduplication, durable coupling between side effects and result records, and an unambiguous retention schedule. The tool runtime must never assume stronger guarantees than the underlying interface explicitly provides.

### Reconciliation

^sec-vol3-tool-calling-reconciliation

When an endpoint lacks native deduplication and a mutating call times out, merely observing that the target system now matches the desired state does not prove that the timed-out call produced it. A concurrent agent or human operator might have made the change, or an earlier mutation might already have been overwritten. To settle ambiguous operations against such endpoints, the runtime relies on **reconciliation**, an authorized, bounded inspection of external system state. Obtaining an operation-specific receipt (such as an execution log entry or transaction identifier bearing the caller’s unique metadata) yields stronger evidence than a bare state check. Runtime diagnostics must keep that epistemic distinction intact rather than synthesizing a false success receipt for an unverified call.

Reconciliation works reliably only when designed prior to dispatch. A mutating tool operating over an endpoint without deduplication can be formalized as a three-part interface:

$$
{\mathbb{T}_{a}} = \langle \text{actuate}({a}),\ \text{probe}({a}, {s}_0),\ \text{compensate}({a}) \rangle \tag{1}
$$

^eq-vol3-legacy-tool-contract

In [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^eq-vol3-legacy-tool-contract|equation 1]], $\text{actuate}({a})$ performs the desired mutation ${a}$. The verification probe $\text{probe}({a}, {s}_0)$ is an authorized read operation, authored alongside the tool, that evaluates whether the intended postcondition holds relative to an initial baseline state ${s}_0$ captured immediately before dispatch. The optional compensation routine $\text{compensate}({a})$ provides an authorized procedure for mitigating partial or unintended side effects if execution falters.[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn7|⁷]] The probe must be implemented ahead of time as part of the tool contract, because allowing an agent model to improvise verification queries on the fly after a timeout replaces transport uncertainty with unverified heuristic guesswork. Capturing the baseline state ${s}_0$ before dispatch provides the reference point. For example, before appending a configuration block to a remote file, the adapter records the file’s initial length and cryptographic hash. After a timeout, the probe can distinguish whether the current bytes match the baseline, match the expected appended content, or match neither. These observations do not establish which actor produced the current state or whether the original attempt can still execute; those questions require an operation-specific receipt or endpoint guarantee.

Observing an “unchanged” probe result justifies an immediate retry only when backed by definitive structural guarantees. The runtime must either verify that the original attempt can no longer execute (for example, because the attempt has expired under a published request-expiry rule), or rely on inherently idempotent semantics where repeat execution is harmless. Without those assurances, the delayed-attempt hazard illustrated in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-delayed-attempts|section 7.5.1]] remains fully active. Reconciliation probes are also distributed network calls that can time out, fail, or exceed their allotted latency budgets, leaving the state unresolved.

Under these conditions, the only sound engineering decision is to classify the action as an unsettled outcome. The runtime preserves the operation identity alongside all gathered telemetry, suppresses automated retries, and escalates the ambiguity to an administrative reconciliation pipeline or human operator. A partially applied mutation frequently requires specialized remediation; many real-world actions lack mathematical inverses, and compensation remains an independent mutation with its own potential failure modes. Downstream tasks that depend strictly on the uncertain operation must block until settlement completes, whereas independent parallel subtasks can safely continue executing.

**Checkpoint 7.2: Settling an uncertain effect**

**Delayed attempt**: A restart times out, and a later probe sees the old state. The first attempt may still commit. What additional guarantee or evidence is needed before repeating the restart?

**Duplicate rate**: In notebook [7.1](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#nbk-07-settlement-budget), reply loss doubles while request loss stays fixed. Roughly how does the daily duplicate count change, and which single change removes that path instead of shrinking it?

**Operation identity**: The agent deliberately restarts the same container a second time an hour later. Why must that request carry a new operation ID even though its arguments are identical, and what goes wrong if the runtime derives operation IDs from an argument hash?

**Matching state**: A probe written before dispatch finds that the intended configuration block is present after a timeout. Why does a matching current state not prove that this attempt produced it, and what baseline should the probe have captured?

Whether an operation ends completed, pending, or permanently ambiguous, that disposition must reach the next model call as a concise, accurate observation, so the agent plans from what is known rather than from an invented outcome. Getting any result back into the model, even the unremarkable output of a test run that did finish, raises a resource problem of its own.
