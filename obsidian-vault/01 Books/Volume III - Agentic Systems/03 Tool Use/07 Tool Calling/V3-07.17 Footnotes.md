# V3-07.17 Footnotes

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^footnotes

<sup>1</sup> **Time-of-Check to Time-of-Use**: Bishop and Dilger analyzed the UNIX file-access race in which the binding of a name to an object changes between a program’s check and its later use, so a privileged program can be steered onto a file it never checked ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-bishop1996checking|Bishop and Dilger 1996]]). A tool adapter that validates `src/pool.py` and then reopens the path by name inherits the same window: a symbolic link swapped in between turns a permitted edit into an edit elsewhere. Resolving the path once and operating on the resolved object, rather than re-resolving the string, is what closes it.

^fn1

<sup>2</sup> **Optimistic Validation Under Contention**: The expected-version check is commit-time validation from optimistic concurrency control, applied to one file. What is new at the tool boundary is the price of a conflict: each failed validation costs the agent a fresh read and a new proposal, paid in model turns rather than in microseconds.

^fn2

<sup>3</sup> **JSON-RPC Request Identifiers**: MCP frames these messages as JSON-RPC 2.0 requests, each carrying an `id` that its response echoes ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-mcp2025specification|Model Context Protocol 2025]]). That identifier does the work of this chapter’s call identifier, matching a reply to its request on one connection. It says nothing about whether a second `tools/call` with the same arguments is the same intended effect, which is why retry safety needs the separate operation identity developed in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|section 7.5]].

^fn3

<sup>4</sup> **Once or Not at All**: The remote-procedure-call guarantee that a failed call executed either once or not at all, met for model calls in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-request-specification|What a request specifies]]**, applies unchanged to a timed-out tool call. What changes is the price of the uncertainty: a timed-out generation at worst wastes a bill, whereas a timed-out mutation may already have changed the world. An agent runtime must therefore preserve “once or not at all” as an explicit, unsettled status rather than collapsing it into a conventional failure that invites an immediate retry.

^fn4

<sup>5</sup> **Idempotent** (Latin *idem*, “the same,” and *potent*, “power”): Benjamin Peirce introduced the term in his 1870 survey of linear associative algebras to describe an element that remains unchanged when raised to any positive integer power, ${x}^{n} = {x}$ ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-peirce1881linear|Peirce 1881]]). Systems engineering applies the term to system state, where executing an idempotent mutation multiple times leaves the system in the same state as executing it once. Algebraic idempotence, however, guarantees nothing about identical return payloads, execution costs, or hidden side effects introduced along the execution path.

^fn5

<sup>6</sup> **Epoch Checks at the Resource**: Distributed lock services encountered this exact failure mode when stale lock holders continued mutating storage after their leases lapsed. The Chubby lock service addressed this with a sequencer: an opaque token containing the lock name, mode, and generation number, which clients transmit alongside mutating requests and target servers validate before committing writes ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-burrows2006chubby|Burrows 2006]]). The check sits at the resource because a stale worker cannot detect its own staleness, so only the mutating resource can reject an out-of-date epoch number.

^fn6

<sup>7</sup> **Compensating Actions**: A compensation, the saga mechanism the introduction glossed for ${A}_2$ grants, is a new forward action that semantically neutralizes an earlier step rather than rolling it back in place. Processing a payment refund, for instance, leaves both the original charge and the subsequent credit in the account’s transaction history. For this reason, tool architectures must treat compensation as a separate authorized operation requiring its own execution budget and outcome settlement, rather than pretending the initial mutation never occurred.

^fn7

<sup>8</sup> **Circular Wait**: Coffman, Elphick, and Shoshani identified four conditions that must all hold for a deadlock: mutual exclusion, hold and wait, no preemption, and a circular chain of processes each waiting on the next ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-coffman1971|Coffman et al. 1971]]). Two full pipes satisfy all four, since each side holds its own buffer, cannot take the other’s, and waits on it. A readiness loop removes the circular wait, because the host never blocks on one channel while the other has bytes to move.

^fn8

<sup>9</sup> **Terminal Control Functions**: The escape sequences that color and reposition terminal text were standardized in ECMA-48, first published in 1976 and adopted internationally as ISO/IEC 6429 ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-ecma1991control|Ecma International 1991]]). Its control functions act on a presentation position on a display rather than on a stream of lines, which is why recovering what an operator saw requires emulating that display rather than filtering bytes.

^fn9

<sup>10</sup> **Eight-Bit Exit Status**: Under POSIX semantics, a parent process inspects child termination through status macros like `WIFEXITED` and `WEXITSTATUS`, which yield only the low-order eight bits (values 0–255) of the argument passed to `exit`. A program that terminates with exit code 256 wraps modulo 256 and appears to the parent as exit status 0. Standard shells also synthesize return codes above 128 when a process is killed by a signal (for example, 137 for `SIGKILL` 9 or 139 for `SIGSEGV` 11), collapsing fatal OS signals into ambiguous numerical exit statuses. An adapter that records explicit disposition variants, such as `exited(code)` vs. `signaled(sig)`, avoids truncating or conflating these conditions.

^fn10

<sup>11</sup> **Names vs. Capabilities**: Dennis and Van Horn’s foundational capability model granted authority through possession of an unforgeable ticket or reference ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-dennis1966|Dennis and Van Horn 1966]]). Agent runtime architectures intentionally stop short of treating context-visible observation handles as capabilities. Because text in a model’s context window can be logged, leaked, copied by prompt injections, or replayed across user boundaries, the runtime treats an inspection handle merely as an identifier (a name). The runtime verifies caller authorization and execution scope on each access, ensuring that possessing a handle string grants no ambient authority.

^fn11
