# V3-07.09 Asynchronous Tool Dispatch

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-async

When an automated repair agent launches an extensive regression test suite, it rarely has any useful decision to make until the results arrive. A prompt return from that tool invocation is only an acknowledgment of receipt; the actual computation has only just begun. During the intervening minutes or hours, the agent runtime must supervise background execution, enforce resource budgets, and maintain system safety without freezing its control plane or burning inference tokens on idle waiting.

### Synchronous and Asynchronous Interfaces

^sec-vol3-tool-calling-async-mismatch

Choosing between blocking on a call and returning a background handle trades control-plane responsiveness against workspace isolation: blocking a supervisor thread on a five-minute integration build leaves the host unable to answer cancellation signals, whereas returning a handle immediately lets the agent edit `src/pool.py` midway through the test run and corrupt the workspace snapshot under test. A synchronous tool interface, which blocks the caller until execution finishes and returns the final result directly, fits sub-second database lookups or local checks where the agent cannot proceed without the answer, though worker threads must still monitor process heartbeats, stream partial output, and enforce timeouts without freezing the control plane. An asynchronous interface instead decouples job submission from job completion by returning a handle representing the pending task alongside methods to inspect its status, stream intermediate observations, or await termination. This separation allows the agent trajectory to suspend cleanly without burning model inference cycles, or to continue executing independent tasks concurrently, provided the runtime isolates the background job within a fixed snapshot or copy-on-write workspace so concurrent edits cannot contaminate the run.

Decoupling task execution from model inference also resolves the serving side of the tool-wait problem named in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^sec-vol3-intro-execution-lifecycle|The six phases of a turn]]**. While a background job runs, the model generates no tokens, so the serving engine can keep, move, or discard and later recompute the trajectory’s KV cache state under the paused-state policies of **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kvcache-swapping|Paused-State Policies]]**, independently of the tool’s lifecycle. Keeping an open HTTP connection or a blocked synchronous socket throughout a long build provides no caching guarantee and only ties up host network resources. When the background job completes and the trajectory resumes, the runtime constructs the next prompt, and the serving engine either recomputes attention state over the prompt prefix or restores it from a prefix cache, depending on what it has evicted.

### Job Handles

^sec-vol3-tool-calling-async-escrow

Once job submission is decoupled from completion, the handle returned at dispatch must keep a queued job distinct from a finished one. If an asynchronous test runner returns `"status": "ok"` as soon as a job enters the work queue, the model treats a queued test suite as a passing one. If a later status poll times out and the adapter reports `"status": "failed"`, the model rolls back a patch while the test job is still running in the background. The runtime admits a proposed asynchronous call using the same validation, authorization, and resource checks required for synchronous invocation. If the executor accepts the work, the runtime records the job’s identity, owner, requested operation, applicable source revision, execution limits, and observation location. A model-visible **job handle** identifies that record without exposing the executor’s internal process-management interface. Under the principle of least privilege, which gives each component only the authority its current task needs, status reads, output inspection, interactive input, and cancellation each require their own explicit authorization checks. A provider-neutral dispatch acknowledgment records only the pending handle:

``` json
{
  "call_id": "call_tests_1",
  "status": "accepted_pending",
  "job_id": "job_tests_18",
  "source_revision": "r18",
  "result_available": false
}
```

Here `call_id` correlates the dispatch exchange, while `job_id` identifies the accepted work for later interactions. If a mutating operation also requires a logical operation ID for retry handling, that identity retains the idempotency semantics established in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|section 7.5]]; a job ID alone supplies no deduplication guarantee. Dropping the dispatch reply across an unreliable network leaves the runtime uncertain whether the executor accepted the task, mirroring the ambiguity of a timeout during a synchronous call.

This initial acknowledgment confirms only that the executor accepted the request into its work queue; it makes no claims about whether the process has started running or whether tests have passed. Subsequent status queries can report active execution, an explicit request for user input, completion with a structured result, or failure with diagnostic details. If network partitions or host restarts make the executor temporarily unreachable, returning “last observed running” alongside “current status unavailable” preserves operational context instead of triggering a mistaken rollback.

When the result becomes available, the runtime delivers the bounded observation contract, specifying the tested revision, the checks actually executed, the process exit disposition, and any output truncation. For example, a completed test job at revision `r18` can report that `test_waiter_notified_on_return` passed. Because a child process can exit cleanly while an output buffer truncates under heavy logging, process termination and output completeness remain distinct fields in the observation contract.

### Resumption Mechanisms

^sec-vol3-tool-calling-async-resumption

Even when a job handle reports pending state accurately, letting the model poll a five-minute background job every five seconds spends 59 full model calls reading the same 32,768-token context only to receive `"still running"`. Systems track asynchronous job state through three primary mechanisms, distinguished by whether state detection requires model inference ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.09 Asynchronous Tool Dispatch#^tbl-vol3-resumption-mechanisms|table 3]]).

| Mechanism                           | Who checks or reports status?                         | When model inference is useful                                      |
|:------------------------------------|:------------------------------------------------------|:--------------------------------------------------------------------|
| Model-directed inspection           | The model proposes a bounded status or output request | A new observation may change the diagnosis or next action           |
| Runtime polling                     | The runtime checks on a bounded schedule              | A reported change requires a decision or the final result is ready  |
| Completion or progress notification | The executor signals a relevant event to the runtime  | The runtime has obtained evidence sufficient to resume deliberation |

Table 3: **Resumption choices**: Waiting and status detection can occur outside model inference; deliberate inspection remains useful when it informs a decision.

^tbl-vol3-resumption-mechanisms

By delegating health checks to the runtime, systems avoid redundant inference calls while retaining simple polling semantics. Event-driven notifications (such as webhooks or message queues) further eliminate polling traffic between the runtime and the executor, though they introduce operational complexity. The runtime must authenticate callbacks, correlate incoming events with job identifiers, and handle dropped, delayed, or duplicated deliveries. In practice, receiving a completion notification often acts as a trigger for the runtime to execute a validated status read, rather than treating the notification payload itself as authoritative proof of completion. Both polling and notification architectures require dedicated supervisory resources to manage pending jobs across runtime host failures.

↪ The durable return path that lets a replacement worker recover a pending job’s result after the runtime host fails is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-durable-execution-effect-reconciliation|Effect and charge reconciliation]]**.

**Napkin Math 7.3: The extra cost of asking whether a job finished**

**Problem**: A background test job completes in 300 s. Under a model-directed polling strategy, the agent queries status every 5 s, starting one interval after dispatch and ending strictly before completion. Assume each status check finishes before the next scheduled query and does not alter overall execution time. Each model invocation consumes a 32,768-token prompt (including preceding status history) and generates a 40-token query, with no additional model acknowledgment required. What incremental inference overhead does this polling loop impose compared to event-driven runtime detection?

**Math**: Both architectures make the initial dispatch call and the final completion call, so those shared calls are excluded. The polling schedule produces 59 intermediate model invocations, consuming 1,933,312 input tokens and 2,360 generated tokens. The selected context length remains fixed across queries rather than accumulating unbounded history.

Assume 95 percent of input tokens qualify for prompt caching discounts, priced at \$0.30 per million tokens vs. \$3 per million uncached tokens, with generation billed at \$15 per million tokens. Multiplying token counts by their respective rates yields \$0.8410 in input charges and \$0.0354 in output charges, producing \$0.8764 of direct inference overhead per background job.

**Systems insight**: The overhead is ${N_{\text{poll}}} = \lceil {T_{\text{job}}}/{\Delta} {t} \rceil - 1$ status calls for a job of duration ${T_{\text{job}}}$ polled every ${\Delta} {t}$, each reading ${S}$ input tokens and generating ${K}$. It therefore costs ${N_{\text{poll}}}({S}\,{c_{\text{in}}} + {K}\,{c_{\text{out}}})$ at per-token input price ${c_{\text{in}}}$ (here the cache-blended price) and output price ${c_{\text{out}}}$. It grows linearly with job duration and inversely with the poll interval. Halving the interval roughly doubles the expenditure, and the interval also sets detection delay: a completion is noticed at most ${\Delta} {t}$ after it happens. Under model-directed polling, cost and worst-case delay therefore trade directly, since halving the cost by doubling ${\Delta} {t}$ doubles the worst-case delay, whereas runtime polling decouples the two because its checks cost no inference. The \$0.8764 per pending job is more than twice the \$0.36 that carrying the shaped observation of notebook [7.2](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#nbk-07-observation-budget) through 30 uncached calls cost. It inflates the attempt cost in the numerator of effective cost ${C_{\text{eff}}}$, paying for status information that the host runtime can monitor at near-zero cost. Systems should delegate routine state tracking to the runtime harness, waking the model only when an incoming observation can change the next decision.

### Job Supervision and Cancellation

^sec-vol3-tool-calling-async-governance

Delegating status checks to the runtime also leaves the runtime responsible for supervising the background job while the model trajectory is paused. Throughout the job’s lifetime, the runtime enforces its execution deadline, resource ceilings, output budgets, and permitted external side effects, returning the latest status and a timestamped, truncation-marked output slice whenever a bounded inspection request arrives. If a job’s output stream goes silent, the runtime cannot assume deadlock from silence alone; an explicit status signal or diagnostic probe is needed to tell slow computation apart from blocked I/O awaiting user input or a wedged worker process.

When a tool genuinely awaits interactive input, the runtime should avoid guessing from operating-system process sleep states. Wherever possible, adapters invoke tools in non-interactive modes with complete parameters supplied up front; when interaction cannot be avoided, an explicit adapter event or structured message must declare what prompt the job expects. Before forwarding any input from the agent, the runtime re-checks the job’s state, the input’s meaning, and the session’s grants, because answering `"yes"` to an interactive migration prompt can trigger schema mutations that exceed a read-only inspection grant.

When a job must be stopped, whether by an explicit cancellation request or an expired deadline, the runtime treats cancellation as an asynchronous control operation with its own intermediate states rather than an instantaneous rollback. After acknowledging the cancellation request, the runtime records what the executor actually reports: the job may stop cleanly, finish before the signal arrives, reject cancellation, or become unreachable with termination unconfirmed. Reclaiming every descendant process is where naive cancellation fails. When a background job runs `bash -c "make && pytest"` and times out, sending `SIGTERM` only to the top-level shell kills the shell. It leaves `make`, compiler workers, and `pytest` running as orphaned children reparented to `PID 1`, and they still hold filesystem locks and burn CPU cycles. On a POSIX host, the containment unit for local signaling is instead a **process group**, which groups all processes reached by a single signal. The execution adapter makes each job the leader of its own process group at spawn time by calling `setpgid(0, 0)` in the child before `exec`. It then signals the entire group with `SIGTERM` first, which gives processes a bounded grace period to flush buffers and release locks, and follows with an uncatchable `SIGKILL`. [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.09 Asynchronous Tool Dispatch#^lst-vol3-process-group-teardown|Listing 6]] implements this escalation pattern and reports one of four verified outcomes. The outcome is `exited` when the group was gone before any signal, `terminated` when it stopped during the `SIGTERM` grace period, `killed` when it stopped only after `SIGKILL`, and `unconfirmed` when members remain after both. If an untrusted process deliberately creates a new session or process group to escape group signaling, the runtime must rely on kernel-level isolation boundaries.

↪ Tearing down processes that detach from the task’s process group, as part of a sandbox’s reset contract, is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|The reset contract]]**.

``` python
import os, signal, subprocess, time

def spawn_job(argv):
    proc = subprocess.Popen(argv, process_group=0)  # setpgid(0, 0)
    return proc.pid                  # the leader's PID is the group ID

def group_alive(pgid):
    try:                             # reap exited children of ours,
        while os.waitpid(-pgid, os.WNOHANG)[0] > 0:  # or zombies
            pass                                     # still count
    except ChildProcessError:        # no children of ours remain
        pass
    try:
        os.killpg(pgid, 0)           # signal 0 probes, delivers nothing
        return True
    except ProcessLookupError:
        return False

def terminate_group(pgid, grace_s=3.0):
    for sig, wait_s in ((signal.SIGTERM, grace_s), (signal.SIGKILL, 1.0)):
        try:
            os.killpg(pgid, sig)
        except ProcessLookupError:   # group already gone
            return "exited" if sig == signal.SIGTERM else "terminated"
        deadline = time.monotonic() + wait_s
        while time.monotonic() < deadline:
            if not group_alive(pgid):
                return "terminated" if sig == signal.SIGTERM else "killed"
            time.sleep(0.05)
    return "unconfirmed"             # report it; do not claim a stop
```

Listing 6: **Process-group teardown with escalation**: The job leads its own group, so one signal reaches every descendant still in it. Liveness is probed with signal 0 after reaping exited children, and a group that survives `SIGKILL` is reported as unconfirmed rather than assumed stopped.

^lst-vol3-process-group-teardown

Two subtle POSIX semantics explain why `group_alive` pairs `os.waitpid(-pgid, os.WNOHANG)` with `os.killpg(pgid, 0)`. First, an exited direct child remains in the kernel process table as a zombie until its parent reaps it, so probing the process group before reaping would report an exited child as still alive. The `while` loop drains every direct child in `pgid` that has already exited, stopping as soon as `waitpid` returns `0` (meaning direct children still exist in the group and none is currently ready to reap) or raises `ChildProcessError` (meaning no direct children remain). Second, `waitpid` can see only the runtime’s direct children. If the group leader exits while its grandchildren (`make` and `pytest`) are still running, the kernel reparents those grandchildren to `init` (`PID 1`), making them invisible to `waitpid` even though they remain in process group `pgid`. Sending signal 0 via `os.killpg(pgid, 0)` delivers no signal, yet asks the kernel whether any live process still belongs to `pgid` regardless of parent. Reaping zombies first and probing `pgid` with signal 0 afterward therefore confirms whether the entire process tree has exited.

Even when process termination is confirmed, stopping an execution does not roll back side effects that occurred before the signal arrived. A canceled deployment script may already have mutated external cloud resources, and a canceled test run may leave temporary database tables behind. The final observation emitted by the runtime must record all known side effects, pending cleanup obligations, and ambiguous states. In the system’s execution log, a status of “canceled” confirms that execution halted; it does not signify that the system returned to its original state.

↪ Remediating the partial effects and cleanup obligations an interrupted job leaves behind is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^sec-vol3-sagas-architecture|The Trajectory Saga Pattern]]**.

An asynchronous interface thus carries the tool contract across time. It acknowledges queued work without stalling the trajectory, keeps resource limits and supervision in force while the model waits, returns bounded observations, and never reports a requested state as a confirmed one. Every mechanism so far has treated one tool at a time and taken that tool’s presence for granted. The remaining decisions concern the whole set: which tools the model sees on a given turn, and how much work each one performs.
