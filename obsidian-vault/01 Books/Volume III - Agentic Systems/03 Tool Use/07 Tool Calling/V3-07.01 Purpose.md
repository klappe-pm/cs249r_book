*Why does a tool call that parses cleanly still need a runtime between it and the world?*

A tool call is the first point at which a model’s output can change something outside the conversation. A proposal that parses cleanly can still name a target the task was never granted, act on a file that has changed since the model read it, or repeat an operation whose first attempt already took effect. Generating the call therefore cannot be what authorizes it. The runtime must stand between proposal and effect, validating each call against its schema, checking it against the grants the task holds, dispatching it, and recording what is actually known about the result. That record is often incomplete. A request that times out may have been lost, may still be running, or may have succeeded without a delivered reply, and a blind retry can restart healthy workers or apply the same change twice. The outcome has to stay explicitly unknown until the runtime settles it, rather than be filled in by the model’s account or the runtime’s optimism. What returns to the model is itself a design decision. A log far longer than the next call can hold must be cut down without hiding the line that matters, and a job that outlives one turn must report back without being mistaken for a finished one. Tool calling keeps the model a proposer and leaves authority with the runtime, which exercises it only on evidence it can check.

**Learning Objectives**

- Trace a proposed tool call through validation, authorization, dispatch, and a correlated observation into the next model call
- Design a tool descriptor that separates structural validation from action-time preconditions enforced with the effect
- Distinguish tool discovery and connectivity from the grants required to invoke an operation
- Select blind retry, endpoint deduplication, or reconciliation for an uncertain effect from operation semantics and loss rates
- Design bounded observations that preserve execution status, omission information, and the scope of available evidence
- Compare waiting and resumption strategies for long-running tools by detection delay, inference cost, and retained supervision
- Evaluate toolkit granularity by context cost, cost per accepted task, and enforced reach across structured, general-purpose, and computer-use interfaces
