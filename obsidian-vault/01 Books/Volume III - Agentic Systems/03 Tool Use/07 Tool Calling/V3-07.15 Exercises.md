# V3-07.15 Exercises

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-exercises

All quantities below are hypothetical problem givens, chosen to be round, and describe no particular provider, protocol version, or deployment. Assume message losses are independent unless a problem says otherwise.

**1. Blind retry at fleet volume (Basic).** A tool fleet issues 120,000 mutating calls a day to an endpoint with no deduplication. Each request is lost with probability 1 percent and each reply with probability 3 percent; lost messages never arrive later, and every timeout triggers exactly one retry.

1.  Compute the per-call timeout probability, the per-call duplicate-effect probability, and the expected duplicates per day.
2.  A network team offers two upgrades: halve reply loss, or halve request loss. Compute the daily duplicates under each and explain why one of them slightly *increases* duplicates.
3.  Name the change that removes the duplicate path rather than shrinking it, and state what the endpoint must bind the identifier to for that change to hold.

**2. Sizing the tail (Basic).** An adapter stages test logs with a head-and-tail policy under ${M_{\text{obs},\max}} = 16{,}384$ bytes, with ${M_{\text{notice}}} = 256$ bytes and ${M_{\text{head}}} = 4{,}096$ bytes. A failing run writes 9,000,000 bytes in total. Its only diagnostic is a 2,400-byte panic block, followed by 11,000 bytes of teardown output and a 600-byte final summary.

1.  Compute ${M_{\text{tail}}}$ and determine whether the whole panic block reaches the model.
2.  Keeping ${M_{\text{obs},\max}}$ and ${M_{\text{notice}}}$ fixed, find the largest ${M_{\text{head}}}$ that keeps the entire panic block in the tail. How many bytes does the omission notice report in either configuration?
3.  The same runner sometimes prints the panic before 200,000 bytes of teardown output. Explain why no split of this ${M_{\text{obs},\max}}$ fixes that case, and name the mechanism from [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.07 Observation Stream Truncation#^sec-vol3-tool-calling-streaming|section 7.6]] that does.

**3. When catalog selection pays (Basic).** A repair harness registers 80 tools, each contributing 420 tokens to the final serialized request. On-demand staging exposes 8 of them plus 900 tokens of selection interface and metadata, and the runtime selects without an extra model call. A trajectory makes 40 model calls, and uncached input costs \$3 per million tokens.

1.  Compute the catalog input of one call under each layout, the capacity released per call, and the break-even number of unused descriptors.
2.  Compute the tokens and uncached dollars released over the trajectory.
3.  In one trajectory out of five, a needed tool was not staged and the agent spends one extra model call of 30,000 input tokens rediscovering it. Does selection still pay? State the condition under which the comparison would flip.
4.  The 80 descriptors come from three interoperable tool servers discovered at session start. One of them advertises `delete_branch` with a description stating that it is approved for all repositories, and the task’s grants do not include branch deletion. Does staging or omitting that descriptor change what the agent may do? Name the check that governs the call if the model proposes it anyway, where each part of that check runs, and what the returned observation should report.

**4. The price of asking whether a job finished (Intermediate).** A repair agent’s test suite completes after 1,500 s. Under model-directed polling, the model checks every 30 s, starting one interval after dispatch, with each status call reading a 48,000-token selected input and generating 60 tokens. The cache covers 90 percent of that input. Hypothetical prices per million tokens are \$3 uncached input, \$0.30 cached input, and \$15 output. The fleet runs 2,000 such jobs a day.

1.  Compute the pending-status calls per job, the incremental cost per job, and the daily fleet cost of polling.
2.  Product management caps model-directed polling at \$0.10 per job. Find the minimum poll interval that meets the cap, and the worst-case delay between completion and detection at that interval for a job whose completion time is not known in advance.
3.  Runtime polling every 10 s costs no inference. Compare its worst-case detection delay and token cost with the answer to (b), then choose a design to ship and state what model-directed inspection remains useful for.

**5. Retrying a refund (Intermediate; second lighthouse).** The support agent issues refunds through a payment endpoint that offers no deduplication contract. It sends 40,000 refund calls a day, each averaging \$60. Requests are lost with probability 0.5 percent and replies with probability 1.5 percent. The alternative to blind retry is an authorized reconciliation probe written before dispatch ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^eq-vol3-legacy-tool-contract|equation 1]]), which adds 4 s to the customer’s wait on every timed-out call. For parts (a) and (b), assume lost messages never arrive later and every delivered refund request executes successfully.

1.  Under one blind retry per timeout, compute the expected duplicate refunds per day and their dollar exposure.
2.  Under the probe policy, compute the fraction of sessions that incur the extra wait and the total added customer wait per day.
3.  Compare the duplicate-refund exposure with the added customer wait. State what operation-specific evidence or endpoint guarantee would make the probe sufficient to settle the original refund or permit a retry, including how it rules out an attempt that could still execute before authorizing another execution. If the probe is inconclusive or the allowed wait expires, specify the recorded outcome and escalation. What response-latency limit would be needed to decide whether this policy meets the service target? Explain why a refund’s operation ID must not be a hash of the customer and amount.

**6. Carry, drop, or re-read (Intermediate).** A repair agent stages a 6,000-token test observation that stays in context for its remaining 45 model calls. Uncached input costs \$3 per million tokens. An alternative policy keeps the observation for the 5 calls in which it informs a decision, then replaces it with a 300-token summary carrying an inspection handle for the rest of the trajectory. Each later re-read through the handle costs one extra model call with 40,000 input tokens and returns a 2,000-token slice that stays in context for 5 calls.

1.  Compute the carried input tokens and uncached cost of keeping the observation, and the same for dropping it with no re-reads.
2.  Find the number of re-reads at which dropping stops being cheaper.
3.  Tokens are not the only cost of a re-read. Identify one latency cost and one evidence risk the token count in (a) omits, and state which of them would change the policy for a log whose failure sits in the omitted middle.

**7. Scheduling a batch by footprint (Intermediate).** A response proposes five calls for the connection-pool repair, listed with durations and declared footprints. `read_source(pool.py)` takes 2 s and reads `pool.py`. `read_source(config.py)` takes 2 s and reads `config.py`. `apply_patch(pool.py)` takes 1 s, reads and writes `pool.py`, and uses the version returned by the first read. `run_tests` takes 30 s, reads `pool.py`, `config.py`, and `tests/`, and writes `.cache`. `lint(pool.py)` takes 5 s, reads `pool.py`, and writes `.cache`. The workflow requires tests and lint to see the patched file.

1.  Apply the noninterference condition to find which pairs may overlap, then give the shortest schedule and its makespan. Compare with fully serial dispatch.
2.  Changing the linter to write `.lintcache` instead is a one-line configuration change. Compute the new makespan.
3.  The model proposes replacing `lint` and `run_tests` with one `bash -c "make check"` call that runs both in sequence for 35 s and whose footprint is undeclared. What must the runtime do with it, and what does that cost in makespan relative to (b)?
4.  Between the read of `pool.py` and `apply_patch`, a teammate commits a change to the same file. The patch arguments still pass schema validation. State which descriptor field and which endpoint operation reject the stale patch, why a separate version check before the write is insufficient, and what the rejection returned to the model should contain.

**8. Retention windows and delayed attempts (Advanced).** A runtime retries a mutating call against an endpoint that deduplicates by operation ID. Each attempt waits a 10 s timeout, then backs off 1, 2, 4, and 8 s before attempts two through five. The network can delay a request by up to 120 s before delivery. The endpoint retains operation IDs for 60 s after first receipt.

1.  Compute the send time of each attempt and the retention window needed so that no delivered attempt of this operation can execute a second time.
2.  The endpoint’s retention is fixed at 60 s. Show that no schedule containing even one retry closes the gap, then redesign the contract so every attempt carries the original logical operation’s admission timestamp and the endpoint rejects the operation more than 45 s after that timestamp. Assuming clocks agree within 2 s, which attempts may the runtime still send while preserving that expiry bound?
3.  Critique the redesign. What new failure mode does request expiry introduce, what outcome must the runtime record when every permitted attempt times out, and which settlement mechanism from [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|section 7.5]] takes over?

**9. One shell or twelve tools (Advanced; second lighthouse).** A team proposes giving the remediation agent a single `run_shell` tool with a 500-token descriptor in place of 12 structured tools of 350 tokens each, citing fewer selection errors. A trajectory makes 30 model calls at \$3 per million uncached input tokens. With structured tools, an attempt costs \$1.20, is accepted with probability 0.80, and causes an unconfined production change with probability 0.001. With the shell, those figures are an attempt cost reduced by the descriptor savings, acceptance probability 0.78, and unconfined-change probability 0.004. Each unconfined change costs \$2,000 to detect and repair.

1.  Compute the per-trajectory descriptor savings and ${C_{\text{eff}}} = \mathbb{E}[{C_{\text{attempt}}}]/{p_{\text{acc}}}$ for each design, first from token costs alone and then including expected change losses in the attempt cost.
2.  Find the unconfined-change probability the shell design would need to match the structured design’s ${C_{\text{eff}}}$.
3.  Critique the team’s evaluation metric, and propose a toolkit that keeps most of the descriptor savings without the loss. Say which mechanism bounds the shell’s reach and which staging policy recovers context capacity.

**What’s Next: From tool interfaces to execution isolation**

A well-specified, authorized tool can still execute faulty or untrusted code. The boundary checks a call’s arguments against the task’s grants. A general-purpose command runner such as `run_shell`, however, accepts commands whose effects no argument check can bound, and even a narrow tool’s implementation can reach whatever its host process can. A descriptor does not limit which files the running code reads, which external services it contacts, or how many resources it consumes. **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes#^sec-vol3-sandboxes|Agent Sandboxes]]** develops the execution envelope that enforces those limits beneath the running code, extending the tool contract from permitted requests to contained execution.
