# V3-07.07 Observation Stream Truncation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-streaming

An automated repair agent running a test suite may encounter a process that terminates with a definitive exit code while generating a log far too vast to fit within the subsequent model request. Conversely, a remote network operation may time out with an uncertain execution state while its local connection layer still captures valuable diagnostic telemetry. Determining the concrete execution outcome of a tool invocation and deciding what subset of telemetry to stage into the prompt are distinct systems responsibilities. An agent runtime must maintain this architectural separation rather than collapsing nuanced execution states into an opaque success or failure string.

Tool execution telemetry encounters two distinct resource boundaries on its return path. **Capture** governs the physical resources (kernel memory, disk storage, CPU cycles, and wall-clock time) spent receiving output from an external process or service. Context staging governs the logical volume of tokens admitted into the model’s prompt after filtering, normalization, and serialization. A brief shell command such as `grep -rn` or an unconstrained compiler build can emit hundreds of megabytes in seconds. Without rigorous capture limits, the runtime risks buffer overruns, pipe deadlocks, or host memory exhaustion long before prompt construction begins.

↩︎ The context budget that bounds the observation tokens admitted to each request is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^sec-vol3-context-engineering-decision|The Working-Set Decision]]**.

### Bounded Output Capture

^sec-vol3-tool-calling-bounded-capture

Waiting for a child process to exit before reading its standard output stalls the child indefinitely as soon as its output exceeds the operating system pipe buffer (64 KB on modern Linux kernels). Buffering all output into host memory instead lets a runaway producer exhaust RAM in seconds. An execution adapter must continuously drain its communication channels while enforcing capture limits through bounded in-memory buffers and quota-managed disk storage.

The canonical failure mode in tool execution is a **pipe deadlock**, which establishes a circular wait[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn8|⁸]] across two bounded pipes. An adapter communicating with a child process over standard input and standard output manages two unidirectional kernel pipes. Suppose the host writes a large payload to the child’s input pipe and defers reading standard output until writing completes. If the child process emits verbose startup diagnostics before consuming its input, the output pipe fills, causing the child’s write call to block. Concurrently, the host fills the input pipe buffer, causing its own write call to block. Both processes sleep interruptibly while waiting for the other to read, halting forward progress until an external watchdog timer terminates the task. Resolving the deadlock requires structural decoupling. The adapter must set all file descriptors to non-blocking mode and multiplex reads and writes across an asynchronous event loop, or dedicate concurrent worker threads to drain standard output and standard error independently. Draining output streams must never block on transmitting input.

An operational capture policy must also define explicit behavior when limits are reached. When incoming data exceeds a retention threshold, the runtime can either drop subsequent bytes while continuing to drain the pipe to prevent process stalls, or actively terminate the executing process. The runtime must persist telemetry recording which policy was triggered and whether byte loss occurred. Because continuously reading and discarding gigabytes of runaway output still burns CPU cycles and context-switch overhead, an output-volume limit complements execution timeouts and kernel resource controls (such as POSIX process quotas or cgroup limits) rather than replacing them. Process termination is itself an asynchronous state transition with its own failure semantics, addressed alongside cancellation mechanisms in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.09 Asynchronous Tool Dispatch#^sec-vol3-tool-calling-async-governance|section 7.8.4]].

Within these capture boundaries, the runtime extracts the most informative evidence for model evaluation. For software engineering and compilation workloads, preserving an initial prefix and a trailing suffix captures the critical context. Build systems print environment configuration, command invocations, and compilation flags at the start, while emitting panic stack traces, assertion failures, and summary verdicts at the very end. However, intermediate warnings or early test failures can easily be lost in the omitted middle. A production capture policy must therefore disclose the exact magnitude of its omissions, while specialized diagnostic filters can selectively extract recognized error patterns from the middle stream. [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.07 Observation Stream Truncation#^lst-vol3-head-truncation|Listing 4]] illustrates why naive head-only truncation fails in automated workflows: in this representative test log, the panic trace and assertion failure appear only after tens of thousands of passing test cases.

``` text
$ cargo test --all
   Compiling core v0.1.0 (/workspace/core)
running 48219 tests
test engine::scheduler::test_fifo ... ok
[... 48,217 further passing tests ...]
test memory::paging::test_allocator ... FAILED
---- memory::paging::test_allocator stdout ----
thread 'test_allocator' panicked at src/memory.rs:142:9:
assertion `left == right` failed
test result: FAILED. 48218 passed; 1 failed; 0 ignored
```

Listing 4: **Where head-only truncation cuts**: The invocation context sits at the top of the log and the failure sits at the bottom. A policy that keeps only the first bytes returns the banner and passing tests and discards the panic.

^lst-vol3-head-truncation

Under a head-only policy, the model receives a nonzero exit status with zero explanatory context, forcing it to guess at root causes rather than making informed repairs. A **head-and-tail policy** resolves this by partitioning the observation byte budget ${M_{\text{obs},\max}}$ across three components:

$$
{M_{\text{obs},\max}} = {M_{\text{head}}} + {M_{\text{notice}}} + {M_{\text{tail}}} \tag{2}
$$

^eq-vol3-observation-byte-budget

In [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.07 Observation Stream Truncation#^eq-vol3-observation-byte-budget|equation 2]], ${M_{\text{head}}}$ reserves space for the initial execution prefix, ${M_{\text{notice}}}$ allocates bytes for an explicit truncation disclaimer, and ${M_{\text{tail}}}$ preserves the most recent output suffix. The adapter implements this with fixed memory overhead: ${M_{\text{head}}}$ bytes are captured into a linear buffer until full, after which incoming bytes feed a ring buffer of size ${M_{\text{tail}}}$. The omission counter increases only when a byte is evicted from that ring, so bytes still retained in the tail are not counted as dropped. When the child process exits, the adapter serializes the head buffer, an omission notice detailing the exact count of dropped bytes, and the ring buffer in chronological order. Capture memory stays fixed however long the process writes ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.07 Observation Stream Truncation#^fig-vol3-stream-ingestion|figure 3]]).

![[90 Assets/Volume III/07 Tool Calling/Vol3 Stream Ingestion 16a4d1d66b.svg]]

Figure 3: **Bounded capture before staging**: The adapter drains each bounded pipe from one readiness loop, so neither channel stalls the child, and enforces a byte limit and a deadline on capture. The head fills once, the tail ring overwrites its oldest bytes, and the middle is counted but not kept, so capture memory stays fixed however long the process writes. The staged observation carries status, head, a notice of the measured omission, and tail within the byte budget ${M_{\text{obs},\max}}$; a retained record, when authorized, lets later calls read omitted ranges by handle.

^fig-vol3-stream-ingestion

Line counts are convenient for display, but they offer no memory safety because a single line can span gigabytes. The runtime therefore enforces byte limits across all capture and parser buffers, and the ingestion layer truncates on valid Unicode code-point boundaries so that multi-byte characters are never split before token lengths are measured. Because the model context is billed and bounded in tokens rather than bytes, an assumed bytes-per-token ratio serves only to size ${M_{\text{obs},\max}}$ in advance. Once the observation is staged, the runtime measures it with the model’s own tokenizer against the observation share ${S_{\text{obs}}}$ of the context budget. That token count includes schema framing, invocation provenance, exit status fields, and the truncation notice itself, leaving headroom for task history, system instructions, and generation so that tool output cannot crowd out the rest of the window.

**Napkin Math 7.2: The cost of carrying one observation through a trajectory**

**Problem**: A hypothetical test log contains 24 MB of text. Assume, only for this estimate, 3 bytes per token. The model’s context window is 128,000 tokens. The adapter instead produces a 4,000-token serialized observation, including its metadata, and the context policy selects that same payload for 30 later model calls. Assume input costs \$3 per million uncached tokens and cached input costs 10 percent of that price. What are the size and later input-cost consequences?

**Math**: Dividing the raw bytes by the assumed bytes per token gives $24 \times 10^{6} / 3 = 8{,}000{,}000$ tokens, or 62.5× the entire window. The raw log cannot be admitted to this request. Actual tokenization depends on the specific vocabulary and input encoding; a coarse byte ratio serves for capacity planning rather than admission validation.

The shaped result occupies 3.1 percent of the whole window, before accounting for other context and output reserve. Its later input contribution is $4{,}000 \times 30 = 120{,}000$ tokens. At the assumed prices, these later reads cost \$0.36 if all are uncached, or \$0.036 if all qualify for cached-input billing. These figures exclude the initial inclusion, output generation, and all other request content.

**Systems insight**: Every staged observation incurs repeated token fees across subsequent turns that retain it in context. Its carried input is ${S_{\text{shaped}}} \cdot {H_{\text{rem}}}$ tokens. This is the serialized size ${S_{\text{shaped}}}$ of this one observation (one contributor to the observation share ${S_{\text{obs}}}$ of each request) times the number ${H_{\text{rem}}}$ of later calls that retain it, and systems engineers control both factors. Halving the staged payload or pruning the observation once the agent acts on its diagnostic cuts token expenditure proportionally, while cached-input billing cuts the carried cost by a factor of 10 under the assumed prices. Aggressive observation shaping directly lowers the amortized inference cost per accepted task, ${C_{\text{eff}}}$, provided the retained evidence remains sufficient for subsequent reasoning.

↩︎ The cost per accepted task, ${C_{\text{eff}}}$, is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^sec-vol3-intro-horizon-arithmetic|Reliability and Cost over a Horizon]]**.

### Truncation Notices and Inspection Handles

^sec-vol3-tool-calling-truncation-notices

Once a head-and-tail policy drops the middle of a log to fit ${M_{\text{obs},\max}}$, the model needs to know whether those omitted bytes still sit in storage or were discarded at the pipe boundary. Otherwise it cannot tell whether to request the missing slice or re-run the test suite with a narrower filter. A truncated observation must therefore state what was selected, what was omitted, and whether the missing data remains retrievable, distinguishing a complete capture that was staged as an excerpt from an unrecoverable drop at the pipe. Omission figures must also reflect what the adapter actually measured: if a stream dropped packets or ended early under buffer overruns, the runtime reports that uncertainty rather than fabricating an exact byte count.

When storage policy permits retention, the runtime can spool the full raw output to an external artifact store and supply the model with an **inspection handle**, the raw-payload handle of **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.03 The Working-Set Decision#^sec-vol3-context-engineering-decision|The Working-Set Decision]]** as it appears at the tool boundary, subject to the same handle rule. Instead of re-executing an expensive build or test run to view omitted output, the agent can issue secondary queries such as `read_observation_slice(handle, offset_bytes, max_bytes)` to examine targeted slices. It can also invoke a server-side regular-expression search over the retained log that returns only matching lines and their byte offsets. Retaining raw logs outside the context window shifts the engineering burden to storage governance. Because retained logs consume disk space and often contain environment variables, authorization tokens, or internal paths, the artifact store must enforce capacity quotas and eviction horizons alongside the same disclosure policies that govern the primary tool call. It must return an explicit error when a handle has expired or been evicted. Content hashes can verify that a stored log has not changed, whereas read authorization and retention lifetime remain separate runtime checks.

Structured tools can avoid post-hoc log slicing altogether by partitioning query results into pages bounded in both record count and serialized byte size, so that a single oversized record cannot overflow the response. Each page reports whether more records remain, whether a scan limit or deadline cut the search short, and which cursor resumes the query. Because authorization and snapshot isolation are independent of pagination, the contract must also state whether later pages read from a frozen snapshot or see concurrent writes.

↩︎ The result envelope’s completion status and continuation cursor are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.04 The Retrieval Contract#^sec-vol3-persistent-result-envelope|The result envelope]]**.

The placement of continuation state highlights a key systems trade-off amplified by agentic workloads: stateful server-side cursors vs. stateless client tokens. A stateful cursor maintains an open database cursor, transaction snapshot, or cache entry on the server until the client finishes iterating. However, autonomous agents abandon search trajectories routinely. An informative diagnostic on the first page often redirects the agent’s entire plan, causing abandoned server sessions to accumulate until garbage collection or time-to-live timeouts reclaim them. A **stateless cursor** avoids server-side state by encoding the continuation position directly within the token passed to the client. Because that token travels through the model’s context, where generated or injected text could alter it to reach rows outside the original query, the backend authenticates it. It serializes a query descriptor, the last evaluated sort key, and an issuance timestamp into a payload ${d}$ and returns the token ${d} \parallel \text{MAC}_{\text{key}}({d})$ signed with a secret server key. When the client returns the token, the backend verifies the message authentication code and expiration time, ensuring resistance against client-side tampering without consuming server memory. The trade-offs for stateless cursors are relaxed consistency and increased prompt overhead. Resumption queries typically evaluate against live data rather than an isolated snapshot, and serialized cryptographic tokens consume prompt tokens on every turn that carries them.

Bounded capture and disciplined staging keep tool output within its memory and context budgets without deadlocking the child. Fitting the bytes into a budget, however, says nothing about whether they faithfully represent what the program displayed or what the process actually did. A terminal log can be garbled by its own redraws, and a clean-looking log can come from a run that checked nothing.
