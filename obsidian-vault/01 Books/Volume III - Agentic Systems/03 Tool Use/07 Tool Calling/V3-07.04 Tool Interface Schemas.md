# V3-07.04 Tool Interface Schemas

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-schemas

When the repair agent finishes inspecting revision `r17` of `src/pool.py` and proposes a patch to produce `r18`, that boundary between static validation and dispatch-time checks becomes concrete. Before applying the modification to the workspace, the host runtime must resolve four questions: which tool operation the model selected, what its arguments denote, whether the current task possesses the authority required to execute the mutation, and whether `src/pool.py` still matches the revision `r17` state on which the model based its proposal. A well-formed JSON payload satisfies syntactic structure, but syntax alone cannot answer these operational questions.

A **tool descriptor** defines an operation’s functional purpose, input parameters, expected return values, and execution side effects. Within that descriptor, the **argument schema** codifies machine-checkable constraints: required fields, primitive types, permitted enumerations, and supported size bounds. These specifications serve two distinct audiences: natural-language descriptions guide the language model in selecting and parameterizing tools, while the surrounding runtime and downstream service endpoints validate and enforce the interface contract.

### Descriptor Semantics

^sec-vol3-tool-calling-descriptor-semantics

Even when every field passes JSON type checking, unstated edge cases in a descriptor can destroy workspace state: if a file-replacement tool leaves unspecified whether an empty `replacement` string is a no-op or a zero-byte write, a model attempting to leave `src/pool.py` unchanged will wipe the file. A tool such as `conditional_replace_file`, which replaces a single file in the task’s designated workspace and commits the change only if that file still matches the expected source version, must therefore state exact semantic invariants alongside its types. The `path` field resolves strictly relative to the designated workspace rather than an arbitrary host location, `expected_version` identifies the baseline source revision the model inspected, and `replacement` supplies the complete replacement content encoded in the endpoint’s documented format, with an empty string explicitly defined to truncate the file to zero bytes.

Full file replacement keeps this precondition example transparent, though production runtimes often prefer line-anchored patches or structured diffs to minimize token generation overhead. The interface comparison in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.10 Comparing Output Interfaces#^sec-vol3-foundation-model-interface-design|Comparing Output Interfaces]]** shows that localized edits reduce generated output while still demanding the same coordination between precondition verification and atomic mutation. [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^lst-vol3-tool-schema|Listing 2]] illustrates the machine-checkable argument structure for that contract. The request payload contains neither a credential token nor a privilege flag through which the model might expand its access rights, and the host runtime independently binds the invocation to the task’s authorized execution context.

``` json
{
  "type": "object",
  "required": ["path", "expected_version", "replacement"],
  "additionalProperties": false,
  "properties": {
    "path": {
      "type": "string",
      "minLength": 1,
      "description": "File path relative to the designated workspace."
    },
    "expected_version": {
      "type": "string",
      "minLength": 1,
      "description": "Source version returned with the inspected file."
    },
    "replacement": {
      "type": "string",
      "description": "Complete replacement text, written as UTF-8."
    }
  }
}
```

Listing 2: **Conditional file replacement arguments**: The schema describes the request’s structure. Its descriptions do not implement path confinement, authorization, or atomic version checking.

^lst-vol3-tool-schema

The descriptor’s result contract requires equal precision. A completed replacement reports the affected path and its newly assigned revision token. A version conflict explicitly reports that the target diverged and the replacement was not applied. The runtime must also distinguish deterministic client errors (malformed arguments or insufficient authority) from indeterminate transport failures where the endpoint’s state remains unknown after a dropped connection. A comprehensive descriptor models all four outcomes, including network timeouts where no acknowledgment arrives.

Precise field names and descriptions eliminate avoidable ambiguity during generation. For example, a file-reading tool should state whether its offset argument counts bytes, characters, or lines. Similarly, a timeout parameter must state its measurement units and specify whether it bounds connection establishment, remote execution, or end-to-end response delivery. While clear documentation guides the model toward valid parameters, the execution runtime must programmatically enforce all defaults, enumeration sets, and numerical bounds. Explicit tool documentation measurably improves the reliability of generation. Patil et al. ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-patil2023gorilla|2023]]) demonstrated that models trained to condition tool invocations on retrieved API documentation invent nonexistent operations and hallucinate invalid arguments far less frequently than models relying solely on unconditioned prompting.

### Structure, Permission, and State Checks

^sec-vol3-tool-calling-boundary-checks

If generation halts at the output token limit or a client disconnection in the middle of a `replacement` string and a permissive parser closes the JSON object or accepts a partial payload, executing that call writes a half-finished `src/pool.py` to disk. Before parsing any arguments, the runtime therefore verifies that the model produced a completed candidate under the invocation contract defined in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-contract|The Invocation Contract]]** and aborts immediately on a truncated response. Once execution status confirms a complete output, the runtime parses the candidate and validates its arguments against the tool’s registered JSON schema before performing any domain checks.

In this replacement example, omitting `expected_version` or supplying a numeric `path` fails structural validation immediately. Setting `"additionalProperties": false` in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^lst-vol3-tool-schema|listing 2]] likewise causes the parser to reject hallucinated arguments such as `force` or `recursive`. However, structural conformance resolves only syntax. Verifying whether the path resides within the task’s assigned sandbox, and determining whether the target still contains the inspected source revision, require distinct evaluation steps. As summarized in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^tbl-vol3-schema-contract|table 1]], the runtime enforces these guarantees across layered boundaries.

| Check                | Question for the proposed edit                                                                   | What passing does not establish                                                        |
|:---------------------|:-------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------|
| Argument structure   | Are the required fields present with the declared types and supported constraints?               | The path is permitted, the version is current, or the replacement is a correct repair. |
| Authority            | Do the task’s current grants permit this operation on the resolved target?                       | The arguments fit resource limits or the operation will succeed.                       |
| Resource limits      | Does the request fit enforced payload, execution, and result limits?                             | The target still satisfies the operation’s preconditions when the effect happens.      |
| Domain preconditions | Does the target support this operation, and does its version match when the update takes effect? | The returned evidence will establish task acceptance.                                  |

Table 1: **Checks at the tool boundary**: Each check establishes a different part of the action contract. Rows follow the round trip; domain preconditions come last because the endpoint enforces them together with the effect, so source-dependent checks remain valid through the operation they protect.

^tbl-vol3-schema-contract

A string formatted as a file path does not constitute a confined resource reference.[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn1|¹]] The tool implementation must canonicalize and resolve the target inside the authorized workspace, accounting for symlinks, directory traversal escapes, and path alias changes that could redirect the operation. Similarly, declaring `replacement` as a string does not bound its encoded memory footprint. Production adapters enforce explicit byte-size limits on incoming payloads, bound the volume of captured diagnostic output, and apply strict execution timeouts. Static schema validation handles input syntax, whereas dynamic state verification, path confinement, and resource throttling remain runtime obligations. **[[05 Reference/Volume III - Agentic Systems/V3 Typed Tool Interfaces#^sec-vol3-app-b-json-schema|Schema Rules for Tool Definitions]]** supplies a bounded edit descriptor along with schema rules for required fields, size limits, explicit units, and variant semantics.

Grammar-guided decoding does not change this division of labor. A token-level mask removes syntax errors before the candidate exists, but it cannot resolve a filesystem reference, evaluate an access policy, or compare a version tag with the file’s current revision. The host runtime validates the materialized request, and the endpoint verifies dynamic preconditions at the moment the effect happens. This separation instantiates the typed action contract (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-strict-action-abi|7]]). The contract admits a call to the environment only after validation, precondition, and authorization checks, with the version precondition enforced together with the mutation rather than during an earlier read.

↩︎ The structural guarantee of grammar-guided decoding, and the reference and permission checks it leaves open, are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.08 Grammar-Guided Decoding#^sec-vol3-foundation-model-structural-guarantee-scope|What a grammar mask guarantees]]**.

### Conditional Updates

^sec-vol3-tool-calling-conditional-updates

An earlier read confirmed only that `src/pool.py` matched revision `r17` at the instant of observation. If another agent or background process modifies `src/pool.py` while the model is generating its patch, applying an unconditioned write silently overwrites those intervening changes. The `expected_version` parameter binds the retrieval contract of **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06.04 The Retrieval Contract#^sec-vol3-persistent-governance|The Retrieval Contract]]** directly to the mutation contract enforced here so that this lost-update race cannot succeed. To prevent the lost update, the storage service must verify the expected version and commit the replacement as a single atomic **conditional update**, the storage equivalent of a hardware compare-and-swap (CAS) primitive.[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn2|²]] In this example, the workspace source service executes the entire sequence inside a single coordination boundary: it resolves the target file, verifies that its current revision matches `expected_version`, writes the new content, and publishes the resulting revision token. Decomposing this sequence into non-atomic operations (reading the revision, verifying it in user space, then issuing a write) reopens a race window where concurrent writers can intervene. The atomic conditional update closes this time-of-check to time-of-use gap.

↩︎ Why context engineering cannot close the refresh-to-execute race, and leaves the revision check to the tool boundary, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-change-detection|Detecting change and bounding uncertainty]]**.

This execution branch yields two distinct operational outcomes:

1.  If the current source revision remains `r17`, the update commits the replacement and returns `r18`, identifying the new revision produced by the edit.
2.  If another writer modified the source first, the version check fails. The service rejects the replacement, leaves the storage state unaltered, and returns an explicit version-conflict status.

Following a conflict, the runtime directs the agent to perform an authorized read of the updated source file and synthesize a fresh proposal, rather than blindly overwriting the intervening modifications. This concurrency guarantee holds only as long as all mutations route through the shared coordination boundary. If external processes or unmanaged scripts modify files directly on disk, bypassing the version service, version tokens offer no protection and the endpoint cannot ensure integrity. Dry-run previews follow the identical principle. A dry run confirms that a proposed patch applies cleanly against revision `r17` at the moment of evaluation, but it establishes no lock on that revision. The runtime must re-verify all preconditions, permissions, and version tokens when executing the live write.

Receiving a successful `r18` confirmation verifies that the file modification committed to disk, but it does not establish that the underlying connection-pool bug has been resolved. Demonstrating functional correctness requires empirical validation. A subsequent passing run of `test_waiter_notified_on_return` is evidence that the patch fixes the exercised case of the race, while broader task acceptance continues to follow the project’s verification suite. At the network layer, a dropped reply leaves the caller uncertain whether the server committed the edit or failed before processing the payload. The retry and idempotency contracts analyzed in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|section 7.5]] resolve this operational uncertainty.

### Rejection Diagnostics

^sec-vol3-tool-calling-rejection-diagnostics

If a rejected tool call returns only `"Error: operation failed"`, the model guesses blindly on its next turn. If a permission denial dumps the host directory tree and environment variables to explain why a path was refused, the error message itself leaks unauthorized state. When an operation fails, the runtime must return a structured, bounded diagnostic that isolates the failure condition without leaking information beyond the task’s authorized grants. A structural rejection should identify the missing `expected_version` property. A concurrency conflict should state that revision `r17` has been superseded. Permission rejections, by contrast, must refuse access cleanly without exposing directory structures or path hints that an agent might probe. The runtime logs whether a rejection originated locally during client-side schema validation or remotely at the service endpoint, allowing downstream decision logic to distinguish between an unattempted proposal and a failed remote mutation. Clear, bounded diagnostics give the model the exact evidence needed to synthesize a valid revision, which must then traverse the same validation pipeline.

The descriptor, its layered checks, and its diagnostics together define one tool’s contract, and every check so far has assumed that the runtime already holds that contract and knows which endpoint implements it. In a real deployment the contract arrives from elsewhere: a repository server, another team’s service, a vendor’s integration. How the runtime learns which operations exist, and why learning that an operation exists confers nothing, is the next problem. How many of the discovered descriptors to stage on each turn is a separate budget question that [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.10 Designing the Active Toolkit#^sec-vol3-tool-calling-toolkit-design|section 7.9]] takes up.
