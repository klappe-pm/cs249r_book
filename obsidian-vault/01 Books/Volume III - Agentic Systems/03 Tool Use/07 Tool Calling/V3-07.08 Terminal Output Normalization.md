# V3-07.08 Terminal Output Normalization

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-observation-parsing

When a command-line tool executes interactively, it redraws progress indicators with carriage returns and styles diagnostics with terminal escape sequences. Captured directly at the byte level, standard output does not represent the clean visual layout a human engineer sees on a terminal screen. Wherever possible, tool adapters should invoke command-line utilities in noninteractive or batch modes (for example, `--batch` or `--no-color`), or ideally request structured machine-readable outputs such as JSON or JUnit XML. Structured reports provide discrete test identifiers, execution timings, and explicit assertions, eliminating the brittle heuristics required to parse colored progress logs. Even so, structured formatting is a transport convention; receiving a syntactically valid JSON payload does not guarantee that the tool performed all required checks or that its outputs can be trusted without schema validation and memory bounds.

When terminal output is unavoidable, the adapter must enforce a declared normalization policy backed by a stateful virtual terminal emulator or bounded screen buffer. Removing ANSI color sequences (`\x1b[31m`) is straightforward, but naively stripping control bytes like carriage returns (`\r`) or cursor positioning sequences silently corrupts output semantics.[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn9|⁹]] Because a carriage return moves the cursor to the beginning of the line without advancing to the next, a terminal progress indicator updates by repeatedly overwriting existing text. Stripping `\r` without simulating terminal geometry causes overwritten states to concatenate. For the bytes `Running... \rFailed!`, the screen shows `Failed!` written over the start of the line (`Failed!...`), whereas naive stripping yields `Running... Failed!`, a line that never appeared. Over a long run the same error accumulates megabytes of repeated progress fragments. The adapter’s parser must therefore maintain cursor coordinates across chunked streaming reads while bounding its internal buffer allocations. When an adapter supports only a subset of control sequences, it must explicitly mark unsupported or incomplete escape sequences rather than discarding them silently. Because collapsing interactive updates into a final snapshot loses intermediate state transitions, the runtime should retain the raw byte stream in secondary storage as an authoritative audit log while delivering only the normalized, bounded representation to the model context. Normalization also shifts byte positions, so the adapter records a mapping from normalized offsets back to raw offsets to keep range queries through an inspection handle aligned with the original text.

Tool adapters must preserve the provenance of standard output (`stdout`) and standard error (`stderr`) while treating stream assignments as advisory conventions. In Unix environments, programs frequently emit progress updates, debugging traces, or configuration warnings across either descriptor, and capturing the two streams through separate pipes forfeits their relative temporal interleaving. When chronological event ordering is essential for root-cause diagnosis, adapters should multiplex streams using pseudo-terminal (pty) pairs or timestamped chunk logging. In extracting diagnostics, the adapter should rely on known output formats such as compiler error lines and language tracebacks, retaining source file paths and line offsets while reporting parsing failures explicitly rather than guessing a root cause from an incomplete fragment. Normalizing terminal output cleans up presentation, but the resulting text carries no intrinsic authority. Safe serialization practices, including escaping control characters and enforcing UTF-8 boundaries, protect the agent’s structural messaging format from delimiter injection, while the evidence-scope rule continues to dictate what the text actually proves.

### Process Status and Evidential Scope

^sec-vol3-tool-calling-process-status

Even a cleanly normalized log cannot by itself prove that a check ran. A test runner pointed at an unmatched directory filter discovers zero tests and exits cleanly with status 0. A shell pipeline run without `set -o pipefail` suffers a fatal crash in its first command while still returning status 0, because its final formatting stage succeeded. The adapter must therefore read process disposition directly from operating-system primitives, such as `waitpid` status macros or container runtime lifecycle events, rather than parsing success messages from output logs. It must still treat exit status 0 as an application convention rather than proof that every required check ran. Querying the process supervisor lets the adapter report an unambiguous exit code,[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn10|¹⁰]] an unhandled terminating signal, or a timeout without textual speculation. Equally, observing end-of-file on standard streams does not prove that a process has finished its work, because a daemon or worker process can close its inherited descriptors while continuing to run in the background. Conversely, a broken socket or interrupted channel leaves the state of any requested side effects uncertain.

An API client can likewise catch an internal runtime exception, print the error payload to standard output, and terminate with code 0 because the transport exchange itself finished without an unhandled crash. Under the evidence-scope rule, the adapter treats the operating-system process status as one evidentiary signal alongside structured output payloads and the task’s acceptance criteria. In a connection-pool repair, for instance, confirming that a targeted reproduction test passes on workspace revision `r18` proves only that the reproducer succeeded; it does not substantiate broader system stability or justify full patch acceptance. [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.08 Terminal Output Normalization#^lst-vol3-observation-sanitization|Listing 5]] illustrates how an adapter packages these signals together. The adapter runs a targeted test against workspace snapshot `r18`, parses its assertions, and captures the full output stream within its retention budget, while staging only a bounded summary into the prompt context.

``` json
{
  "call_id": "call_test_42",
  "scope": {"repository": "repair-workspace", "revision": "r18"},
  "process": {"state": "exited", "exit_code": 0},
  "check": {
    "target": "tests/test_pool.py::test_waiter_notified_on_return",
    "outcome": "passed",
    "broader_regression_checks": "not_run"
  },
  "observation": {
    "capture": "complete",
    "staged_view": "excerpt",
    "selection": "invocation header and final test summary",
    "text": "Target: tests/test_pool.py::test_waiter_notified_on_return\n[intermediate output omitted]\nResult: passed",
    "omission_notice": "Intermediate output omitted from this view.",
    "inspection_handle": "obs_42",
    "retention": "until this task ends"
  }
}
```

Listing 5: **A bounded result with scoped evidence**: Process disposition, tested source, check outcome, and observation completeness answer different questions.

^lst-vol3-observation-sanitization

Each block in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.08 Terminal Output Normalization#^lst-vol3-observation-sanitization|listing 5]] answers a separate question so the model cannot mistake a clean exit or a short excerpt for full verification. The `call_id` field ties the result to the turn that requested it. The `scope` field pins the evidence to workspace revision `r18`, so a pass on one commit cannot be credited to a later edit. The `check` field records that the single reproducer passed while broader regression suites were not run. Because the full log was captured but only the header and summary verdict were staged into the prompt, the `observation` block marks `capture` as complete and `staged_view` as an excerpt, and it exposes `obs_42` as an inspection handle for paginated follow-up reads. Had resource limits truncated collection at the pipe, `capture` itself would be marked incomplete with the surviving byte ranges noted. Under the grant rule, the runtime mediates every read on `obs_42`, so knowing the handle string confers no ambient authority across sessions.[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.17 Footnotes#^fn11|¹¹]]

**Checkpoint 7.3: Interpreting bounded observations**

**Omitted evidence**: A known failed test run has a complete retained log but only a head-and-tail excerpt in context. What can the agent infer from the absent stack trace, and what bounded inspection should it request?

**Scoped status**: The result above reports exit code zero and one targeted pass on `r18`. Which claims does that support, and which acceptance questions remain open?

**Instruction-like output**: A normalized log contains an instruction to upload the repository elsewhere. Which presentation checks have occurred, and why do they grant no authority for that proposed upload?

Synchronous tool execution assumes the adapter can resolve process status, normalize terminal streams, and package evidence within the span of a single model turn. When operations run longer than conversational deadlines allow, asynchronous dispatch extends this same return-path contract to running jobs, tracking process lifecycles and staging bounded observations without mistaking dispatch for completion.
