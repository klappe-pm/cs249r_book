# V3-07.02 The Tool Boundary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-boundary

An agent asked to restart a container on a staging server, the kind of infrastructure change the remediation agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) makes, emits a short tool call. The host runtime checks the call against the tool’s schema, confirms that this session may restart that container, and sends `POST /containers/srv-stage-04/restart`. Two seconds later the socket times out. The request may be lost, delayed, still executing, or completed without a delivered reply. A retry could restart healthy workers, and the first attempt can still take effect after the timeout.

![[90 Assets/Volume III/07 Tool Calling/Hsa Locator A 066dc9f6a5.svg]]

*H·S·A locator with only the Authority axis lit in purple; Horizon and State axes gray.*

*The Authority axis, closed at the tool boundary by mediating every proposed call.*

Nothing about this failure is exotic. The repair agent meets the same questions on every turn of the connection-pool repair. It reads `src/pool.py`, replaces text derived from the version it read, runs the test suite, and receives a log far longer than the next model call can hold. Each step is a tool call, and each can be rejected, left running, completed without a reply, or answered with more output than the model should see.

The pieces built so far do not settle these questions. **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^sec-vol3-foundation-model-messages-tool-definitions|Messages and tool definitions]]** gave the model a structured way to propose a call. The memory chapters already relied on tools to read sources, search indexes, and update records without examining what happens between a proposal and its result. A retrieval result identifies the version it observed, but whether the file still has that version when a later edit commits is an action-time precondition that something must enforce. A proposal names an operation and its arguments. It does not decide whether this task may run the operation, whether an earlier attempt already ran it, or what the next model call should receive.

The runtime’s tool boundary is the path between a proposed call and the environment it would change. The boundary validates each proposal, checks it against the task’s grants, dispatches it, tracks what is known about its effect, and returns a bounded observation matched to the call. Throughout, it keeps apart the three things the timeout blurs: what the model proposed, what effect the operation had, and what evidence the runtime holds about either. The chapter follows one call from proposal to observation, then widens to effects whose outcome stays uncertain, to output too large to return whole, to jobs that outlive a model turn, and finally to the catalog of tools the model sees.

↩︎ The separation of proposal, effect, and observation is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^sec-vol3-intro-trajectory-systems-boundary|Why the runtime manages the trajectory, not the single call]]**.
