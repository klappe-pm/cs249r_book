# V3-07.03 Tool Subsystem Architecture

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling|V3-07 Tool Calling]]

^sec-vol3-tool-calling-unix-analogy

When the socket times out on `restart_container`, a runtime that drops the failed call from history or reports it as a clean failure invites the next model turn to issue a duplicate restart. [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.03 Tool Subsystem Architecture#^lst-vol3-tool-call-turn|Listing 1]] shows the staging restart as one turn of the loop, in a provider-neutral form. The runtime reports what it knows about this attempt, and the next model call receives that result together with the earlier request and proposal.

``` json
[
  {"role": "user",
   "content": "Stage-04 is serving a stale config. Restart it."},
  {"role": "assistant",
   "content": [
     {"type": "tool_call", "id": "call_1", "name": "restart_container",
      "arguments": {"container_id": "srv-stage-04"}}]},
  {"role": "tool",
   "content": [
     {"type": "tool_result", "call_id": "call_1",
      "content": {"transport_status": "timeout", "effect_status": "unknown"}}]}
]
```

Listing 1: **One turn of the tool-call loop**: A call identifier correlates the proposed call with its result. The next model call receives the timeout as an unknown effect, not as evidence that the restart did not happen.

^lst-vol3-tool-call-turn

The runtime correlates each result with its corresponding call using an explicit identifier rather than message order alone. That identifier establishes message lineage across asynchronous turns, but correlation alone does not resolve whether the target service completed the requested mutation. Preventing duplicate restarts requires an operational contract for idempotency, developed in [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|section 7.5]]. Even if the subsequent model turn assumes that the service recovered, the runtime preserves the underlying uncertainty. It authorizes a retry only when idempotent semantics, an endpoint deduplication contract, or reconciliation evidence that also rules out a still-delayed attempt supports it. Fresh evidence that the container looks unchanged is not enough on its own ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-delayed-attempts|section 7.5.1]]).

### One Mediated Round Trip

^sec-vol3-tool-calling-round-trip

Between the `tool_call` and `tool_result` messages of [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.03 Tool Subsystem Architecture#^lst-vol3-tool-call-turn|listing 1]] lies the runtime’s mediation path. If the runtime piped a model’s proposed call straight to an execution backend and piped the raw output straight back into the prompt, an unauthorized call would mutate the host and an unbounded log would overflow the next context window. Instead, once the inference engine emits a structured invocation block at the model-side call surface, execution passes entirely to the runtime, which mediates the round trip between the proposed call and the next turn’s observation across the four coordinated stages of [[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.03 Tool Subsystem Architecture#^fig-vol3-tool-call-loop|figure 1]]: argument validation, policy authorization, dispatch with outcome tracking, and observation shaping.

↩︎ The six-phase turn lifecycle, whose validation, execution, and observation phases these four stages refine, is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^sec-vol3-intro-execution-lifecycle|The six phases of a turn]]**.

Request validation parses proposed arguments against the tool’s declared schema, verifying required fields, data types, value ranges, and relational invariants among parameters. Dynamic constraints that depend on volatile environment state cannot be settled at this boundary. The system must evaluate them at the execution boundary rather than inferring them from historical context. Next, operation authorization verifies the active session’s security grants and access policies against the targeted resource, for read operations as well as state mutations, and admits the call against its concurrency budgets and rate limits.

Following authorization, dispatch submits the permitted operation to the underlying execution provider while outcome tracking maintains execution identity and status. This tracking distinguishes among pre-dispatch rejections, active background tasks, successfully reported results, and unconfirmed execution states. A transport timeout indicates only that the runtime exceeded its waiting deadline, leaving the remote execution state unconfirmed. Finally, observation shaping maps the raw return value back to the originating call identifier, truncating payloads to fit context budgets, sanitizing terminal escape sequences, and tagging the output with accurate status metadata. If log output must be truncated, the payload explicitly discloses the omission; if a system returns an asynchronous job ticket, observation shaping reports it as an acknowledgment rather than a completed effect.

Certain validation checks must execute at the remote endpoint because safety requires atomicity with the state change itself. For example, an edit conditioned on a source version requires the version check to occur in lockstep with the update. Consequently, the host runtime and the remote endpoint each enforce their respective boundaries. The endpoint checks access independently, even for requests that the host runtime already cleared. This division is the end-to-end argument applied to system protection. An authorization check that depends on private endpoint state can be finalized only at that endpoint, which makes preliminary host-level checks useful optimizations rather than authoritative substitutes ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-saltzer1984endtoend|Saltzer et al. 1984]]).

![[90 Assets/Volume III/07 Tool Calling/Tool Call Loop 6aca7c387a.svg]]

Figure 1: **The tool-call loop**: Validation and authorization can reject a proposed call before dispatch. For a dispatched call, the runtime tracks the available outcome and shapes the return into a bounded observation matched to its call identifier. An unknown effect remains unknown in that observation.

^fig-vol3-tool-call-loop

When the serving interface returns native structured call blocks, the runtime extracts the proposed operation and arguments directly. When a model emits proposals within unstructured free text, the runtime must first detect and parse those fragments before validation can proceed. Constrained decoding eliminates syntactic parsing failures by enforcing grammar rules directly during token generation. However, syntax alone never establishes operational safety. Whether the target resource exists, whether the observed version remains current, and whether the current session holds execution privileges remain runtime checks that no decoding grammar can verify.

### Complete Mediation

^sec-vol3-tool-calling-complete-mediation

Just as a decoding grammar cannot verify execution privileges, a system-prompt instruction to touch only staging containers or read only inside `/workspace` places no barrier between a hallucinated or prompt-injected tool call and the host operating system. Securing the tool interface rests on complete mediation ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-saltzer1975|Saltzer and Schroeder 1975]]), the protection principle that already required the tool handler of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^sec-vol3-foundation-model-likelihood-checked-properties|Why token likelihood cannot replace checks]]** to check a validated path again when the read executes. At the tool boundary, mediation must govern both reads and mutations. Emitting a tool name does not grant the model ambient runtime authority, nor does receiving an observation make external data trusted.

**Definition 7.1: Complete mediation**

***Complete mediation*** requires every proposed access to pass through an enforced authorization boundary before it reaches the protected resource. In an agent runtime, the return path is also mediated so that observations enter context under explicit access, payload, and status contracts.

1.  **Significance**: A valid-looking call cannot bypass the checks governing what the session may read, change, or disclose.
2.  **Distinction**: Schema validation establishes structural admissibility, not permission. Observation normalization establishes a usable representation, not the truth of its contents or immunity to prompt injection, attacker-controlled content that attempts to redirect the model.
3.  **Common pitfall**: Treating a prompt instruction such as “never delete production data” as an access barrier. The runtime must enforce the restriction even when the model proposes the prohibited action.

Stating complete mediation as a policy does not by itself guarantee that every tool route honors it. Anderson formalized the architectural mechanism required to make that guarantee hold across every access path: the reference monitor ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-anderson1972computer|Anderson 1972]]).

**Definition 7.2: Reference monitor**

***Reference monitor*** is the enforcement component through which every access to a protected resource passes. It must be tamper-proof, always invoked, and small enough to verify. In an agent runtime, the host’s validation and authorization path is the reference monitor for proposed tool calls, and each endpoint’s access check is a second monitor for the resources that endpoint owns.

1.  **Significance**: The three requirements turn complete mediation from an intention into a checkable property of the runtime’s structure.
2.  **Distinction**: The policy specifies permitted accesses, whereas the reference monitor provides the non-bypassable mechanism that evaluates and enforces those rules on every attempt.
3.  **Common pitfall**: Adding a tool route that does not pass through the monitor, such as an unrestricted shell with network access beside a checked file adapter, which makes the adapter’s checks advisory.

These three requirements dictate concrete architectural choices at the tool boundary. *Tamper-proofing* ensures that neither generated model tokens nor untrusted data ingested from external systems can alter the authorization rules enforced by the runtime. *Always-invoked* mandates that every operational path pass through the monitor without exception. Exposing an unrestricted shell runner alongside a sandboxed file tool, for example, undermines the protection boundary, because the agent can bypass file restrictions by issuing shell commands. Finally, *verifiability* requires policy decisions to be deterministic, auditable software checks. Although an auxiliary classifier or guardrail model can score operational risk, probabilistic inference cannot be verified in the strict systems sense; the monitor itself must enforce deterministic access boundaries.

Two operational rules follow directly from complete mediation. The *grant rule* establishes that execution authority derives solely from the session’s active security grants, re-evaluated on every invocation. Read operations demand the same rigorous mediation as state mutations, because returning private records discloses sensitive data even when environment state remains unchanged. Nothing the model sees or emits enlarges those grants, whether a schema-valid call or a tool description claiming broad permission; later sections apply the rule to each new artifact they introduce. The *evidence-scope rule* establishes that an observation confirms only the specific metric or condition measured by the tool during that invocation. Reporting that an operating system process exited with code zero confirms only process termination; it does not prove overall task completion, which remains a distinct judgment governed by invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]). Raw output text also remains untrusted data even after the runtime strips terminal formatting and normalizes metadata; observations supply empirical evidence of state, but they carry no ambient authority to dictate subsequent actions.

### Batches and Forced Calls

^sec-vol3-tool-calling-batches-forced-calls

When a single model response proposes reading `src/pool.py` and patching `src/pool.py` in the same batch, dispatching both calls in parallel yields non-deterministic results depending on which thread reaches the file first. When batched operations are strictly read-only and independent, such as reading three distinct source files, the runtime can dispatch them concurrently and correlate each returned observation with its respective call identifier. A failure in one read does not invalidate concurrent reads that succeeded. Every call in the batch must still pass validation and authorization individually and draw from a shared resource and rate-limit budget.

When tools declare a trustworthy **resource footprint**, the explicit read set ${R}_i$ and write set ${W}_i$ of each call ${i}$, the runtime can check whether batched mutations and reads interfere. Calls ${i}$ and ${j}$ may run concurrently when neither writes state the other reads or writes, ${W}_i \cap ({R}_j \cup {W}_j) = \emptyset$ and ${W}_j \cap {R}_i = \emptyset$, which are Bernstein’s conditions for noninterference ([[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.16 Source References#^ref-bernstein1966|Bernstein 1966]]). Reads of two different files pass both conditions; a read and an edit of `src/pool.py` fail the first, because the edit writes the file the read reads. This guarantee, however, relies entirely on the completeness of footprint declarations; any hidden side effect or undeclared shared dependency invalidates the concurrency guarantee.

Operations with opaque side effects, such as arbitrary shell commands, have unknown footprints. In such cases, the runtime must either isolate the execution environment, serialize calls conservatively, or reject batched execution in favor of fine-grained tools. When operations have causal dependencies, those ordering constraints must come from the workflow policy or an explicit dependency graph. The sequential order of tokens generated by the model is not reliable evidence of intended execution order. Batching also does not imply atomicity; a batch forms a transaction only when the underlying tool substrate explicitly provides transactional all-or-nothing rollback semantics.

The runtime can also govern whether the model proposes an action. Using serving-level **tool-choice control**, the runtime can configure tool calling as optional, mandate that the model invoke at least one tool, restrict selection to a specific named operation, or forbid tool execution altogether. Orchestration engines use these constraints to guide execution phases, for instance forcing a diagnostic read before permitting an edit, or disallowing tool calls to force a final textual summary. Tool-choice controls, however, only shape model generation; under the grant rule, forcing a tool choice confers no operational authorization. Executing each stage of this mediated round trip requires an unambiguous request representation, establishing a strict operational boundary between static schema validation and dynamic preconditions verified at dispatch time.
