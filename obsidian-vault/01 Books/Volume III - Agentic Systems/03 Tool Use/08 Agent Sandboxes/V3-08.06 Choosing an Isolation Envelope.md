# V3-08.06 Choosing an Isolation Envelope

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-microvms

A lightweight log parser, a multi-turn software repair task compiling code and executing test suites, and an untrusted customer-uploaded binary demand different operating interfaces. Selecting an appropriate execution envelope begins with these workload requirements and the host resources that must remain protected, rather than defaulting to a convenient packaging format.

**Definition 8.3: Isolation envelope**

An ***isolation envelope*** is the enforced boundary around executing code, specified by the resources it exposes, the components it shares with the host or other workloads, and the mechanisms that restrict access and consumption.

1.  **Significance**: It makes the permitted reach of an operation a property of its execution environment rather than a request to the model or program.
2.  **Distinction**: A grant specifies permitted authority, whereas the envelope enforces that boundary against executing code. Enforcing confinement guarantees that code cannot exceed its assigned reach, but it does not validate whether every permitted operation aligns with the agent’s intended task.
3.  **Common pitfall**: Treating the high-level label of a container, virtual machine, or language runtime as a complete isolation policy without auditing its concrete configuration, host mounts, and exposed system interfaces.

Choosing a different envelope changes both the composition of the trusted computing base defined in the threat model and the interface untrusted code can reach. Narrowing that interface simplifies security review, but counting system calls or source lines cannot produce a quantitative probability of sandbox escape. A systems comparison instead asks which failure modes each envelope contains, which components remain trusted, and which operating interfaces the workload requires. The four envelopes in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^fig-vol3-isolation-spectrum|figure 4]] differ first in where a system call lands: in the host kernel after a filter, in an emulating user-space kernel, in a separate guest kernel, or nowhere at all, because restricted bytecode has no system-call instruction.

![[90 Assets/Volume III/08 Sandboxes/Isolation Spectrum V2 f66ad5dad7.svg]]

Figure 4: **Where a System Call Lands**: Amber boxes run untrusted code, purple boxes are trusted mediators, and the host kernel closes every column. A shared-kernel container sends every call to the host kernel through a filter. A user-space kernel traps and emulates each call and makes a reduced set of host calls. A microVM’s guest kernel handles ordinary calls natively, and only device I/O exits to the monitor. Restricted bytecode has no system-call instruction and reaches the host only through imported functions. The columns differ in which interface untrusted code can reach, not in a ranked probability of escape.

### Shared and Interposed Kernels

^sec-vol3-sandboxes-gvisor-vs-microvm

The first two columns of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^fig-vol3-isolation-spectrum|figure 4]] start from a standard POSIX process and differ in whether its system calls reach the host kernel directly. When untrusted code issues a permitted system call inside an ordinary container, the host kernel services that call itself, so a single exploitable bug in the shared kernel compromises the entire host. A **shared-kernel container** confines host processes using native operating-system primitives. Linux namespaces restrict views of global resources such as process trees, network interfaces, and mount tables. Access controls and seccomp filters restrict permissible operations. Control groups bound resource consumption. Container isolation is therefore only as strong as the host kernel and the configuration around it; packaging an application into an image provides no security boundary on its own.

To avoid exposing the host kernel directly, a **user-space kernel** places an intermediary kernel implementation between the application and the host operating system. For example, gVisor’s Sentry reimplements the Linux kernel API as a memory-safe user-space process written in Go ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-google2019gvisor|Google 2019]]). The Sentry intercepts application system calls, services them internally without passing the raw call through to the host kernel, and requests host resources through a restricted seccomp filter. An envelope must still be audited by its concrete configuration rather than its name, because the trusted path can change under an unchanged label. The original gVisor design routed every filesystem operation through a separate proxy process so that the Sentry held no host file descriptors, whereas a later revision lets the Sentry open paths itself relative to descriptors handed to it at startup ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-gvisor2023directfs|Ranjan 2023]]). Because compilers and build tools depend on specific POSIX behaviors, an engineering team must also verify that the user-space kernel supports the system calls its toolchain needs, and pair the emulator with independent storage and compute quotas.

### Separate Guest Kernels

^sec-vol3-sandboxes-guest-kernels

When a build or repair task needs full Linux system-call compatibility without exposing the host kernel to guest exploits, user-space emulation can fall short on either coverage or speed. A **microVM** instead runs a real guest kernel and its workload behind a hardware-virtualization boundary managed by a virtual machine monitor (VMM). Application system calls execute natively inside the guest kernel, and only interactions with the host cross explicitly configured virtualization and device interfaces. Compromising the guest kernel therefore does not hand control of the host to the attacker; security rests on the monitor, the hypervisor, the CPU virtualization extensions, and the virtual devices exposed to the guest.

Hardware-assisted virtualization roots this isolation directly in processor architectural state ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-uhlig2005intel|Uhlig et al. 2005]]). The CPU runs the hypervisor in VMX root operation and executes the guest, kernel and applications alike, in VMX non-root operation. Ordinary instructions in non-root operation execute natively, including the guest’s own system-call instructions (`syscall` or `sysenter`), which trap into the guest kernel without hypervisor intervention. Sensitive operations,[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn4|⁴]] such as modifying control registers, reprogramming interrupt controllers, or accessing unmapped physical device registers, trigger a VM exit. During a VM exit, the CPU hardware automatically saves guest register state into the hypervisor-managed Virtual Machine Control Structure (VMCS) and transfers execution control to the hypervisor. Memory translation proceeds through two distinct stages: the guest page tables translate guest virtual addresses to guest physical addresses, and hypervisor-controlled Extended Page Tables (EPT) or Nested Page Tables (NPT)[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn5|⁵]] translate guest physical addresses to host physical memory:

$$
\text{guest virtual} \xrightarrow{\text{guest page tables}} \text{guest physical} \xrightarrow{\text{hypervisor page tables}} \text{host physical}
$$

Even if an untrusted agent exploits a kernel vulnerability inside the guest and gains root privileges, it can rewrite only the first mapping. Because the guest kernel cannot modify the hypervisor’s second-stage page tables, it remains physically incapable of addressing host memory frames that the hypervisor has not explicitly mapped into its address space. This hardware boundary is what separates a guest kernel compromise from a host compromise.

Firecracker exemplifies this minimalist approach, building on the Linux Kernel-based Virtual Machine (KVM) subsystem ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-kivity2007kvm|Kivity et al. 2007]]). To minimize both cold-start latency and reachable attack surface, Firecracker originally stripped away legacy PC hardware. It omits a BIOS, dispenses with PCI bus emulation, provides minimal virtio-net and virtio-block devices alongside a basic serial console and minimal keyboard controller, and boots an uncompressed guest kernel directly ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-agache2020firecracker|Agache et al. 2020]]). Subsequent releases introduced ACPI support and an optional virtio-pci transport ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-firecracker2025changelog|Firecracker Project 2025]]), reiterating that the exposed attack surface depends entirely on the specific version and runtime flags deployed. Furthermore, Firecracker establishes a clean architectural separation: while the VMM exposes virtual network interfaces to the guest, host-side networking infrastructure (such as iptables, nftables, or eBPF programs) enforces outbound egress filtering. The agent’s external network policy is thus governed by the host orchestration plane rather than entrusted to the guest ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-firecracker2024design|Firecracker Project 2024]]).

### Restricted Bytecode and Host Imports

^sec-vol3-sandboxes-wasm

Not every tool call needs a guest kernel or a POSIX process: a structured log parser that runs for a few milliseconds per call cannot afford even a fast virtual-machine restore on every invocation. A **bytecode sandbox**[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn6|⁶]] instead executes code compiled to an intermediate representation whose runtime governs memory accesses and control flow directly. WebAssembly, for example, confines guest code to a contiguous, linear memory space that the runtime isolates using software bounds checks or hardware page-table protections with unmapped guard pages ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-haas2017bringing|Haas et al. 2017]]). WebAssembly defines no native system-call instruction; guest modules interact with the outside world only by calling host functions explicitly imported at instantiation. Those memory boundaries protect the host from the module rather than separating data structures inside the module from one another, and any imported host function runs with host privileges to perform whatever action its implementation allows.

The WebAssembly System Interface (WASI) maps directly to the capability-based security model introduced in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^sec-vol3-sandboxes-least-privilege|section 8.4]]. During module initialization, the host pre-opens specific directory file descriptors and binds them to the sandbox environment. Every subsequent guest path lookup must resolve relative to one of these pre-opened descriptors;[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn7|⁷]] any directory traversal attempting to escape the assigned root (such as `../../etc/passwd`) immediately fails with a capability-violation error before reaching host filesystem primitives.

Bytecode sandboxing fits workloads that compile to WebAssembly and need only narrow host interactions, such as a log parser that reads an input buffer and returns a sanitized record without touching the filesystem or network sockets. Supplying broad host imports, however, re-opens the attack surface, because the runtime, its ahead-of-time or just-in-time compiler, and every imported host function belong to the trusted computing base. Execution time and linear memory growth must also be capped so a module cannot stall or exhaust the host.

### The System-Call Tax

^sec-vol3-sandboxes-syscall-tax

A dependency install, Git checkout, compilation, or test run issues tens of thousands to millions of system calls to read timers, open files, map memory, and spawn subprocesses, so even a few microseconds of mediation overhead per call can add seconds to a build. Because the four envelopes handle operating-system requests at different boundaries, each pays a different combination of up to three per-call costs, which together make up the envelope’s **system-call tax**:

$$
{T_{\text{syscall}}} = {T_{\text{trap}}} + {T_{\text{filter}}} + {T_{\text{switch}}} \tag{3}
$$

^eq-vol3-syscall-tax

Here ${T_{\text{trap}}}$ is the hardware cost of crossing a privilege boundary, ${T_{\text{filter}}}$ is the software cost of validating or emulating the requested operation, and ${T_{\text{switch}}}$ is the context-switch cost of transferring execution control to another thread or process. [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^tbl-vol3-isolation-transitions|Table 4]] shows which cost terms each envelope pays.

| Envelope                | Where a system call goes                                    | Terms paid, and on which calls                                                              | Host interface exposed                             |
|:------------------------|:------------------------------------------------------------|:--------------------------------------------------------------------------------------------|:---------------------------------------------------|
| Shared-kernel container | Host kernel, after an in-kernel filter                      | Trap and filter on every call; no switch                                                    | The host kernel’s system-call interface, filtered  |
| User-space kernel       | Intercepted and emulated by the user-space kernel           | Trap, emulation, and a switch or exit on every call                                         | A reduced set of host calls made by the emulator   |
| MicroVM                 | Guest kernel, natively in non-root operation                | A native trap for ordinary calls; a VM exit and a switch to the monitor only for device I/O | The monitor’s devices and the hypervisor interface |
| Restricted bytecode     | No system-call instruction; host imports are function calls | A function call plus argument checks, only on imported operations                           | Only the functions the host imports                |

Table 4: **Where each envelope handles a system call**: The envelope determines which calls cross to the host, which cost terms of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^eq-vol3-syscall-tax|equation 3]] they pay, and which host interface untrusted code can reach.

^tbl-vol3-isolation-transitions

For coding workflows, the sharpest performance split is between user-space kernel emulation and microVM virtualization. A user-space kernel intercepts and emulates every system call, switching context between application and emulator threads, whereas a microVM handles ordinary system calls natively inside its guest kernel and exits to the host monitor only on physical or virtual device I/O. Measurements of user-space kernels confirm that frequent system calls, especially filesystem operations routed through external proxy daemons, pay heavy latency penalties compared to native Linux execution ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-young2019true|Young et al. 2019]]). Illustrative per-call costs show the scale of the gap. Assume a 0.1 μs trap, 0.05 μs of in-kernel filtering, 1.5 μs of emulation, and a 2 μs switch to the emulator. Every 1,000,000 ordinary calls then add about 0.15 s in a container, 0.1 s in a microVM, and 3.6 s in a user-space kernel, 36× the microVM’s cost, before counting the microVM’s device exits. At those rates the tax barely registers when a task issues tens of thousands of calls, but adds seconds to a build that issues millions. Workloads dominated by dense system calls therefore favor microVMs or shared-kernel containers over user-space kernels, whereas pure in-memory computation in a bytecode sandbox avoids operating-system calls altogether. Because exact timings vary with CPU microarchitecture, host kernel settings, and runtime implementation, the per-call terms show where latency comes from rather than fixing universal constants.

### Envelope Selection

^sec-vol3-sandboxes-envelope-choice

No single envelope fits every agent action. Starting a fresh microVM for a few milliseconds of log parsing wastes more time on setup than on work, while running an unreviewed native build inside a shared-kernel container exposes the host kernel to whatever exploit the build triggers. [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^tbl-vol3-isolation-taxonomy|Table 5]] compares the four envelopes by trusted components, order-of-magnitude start cost, and typical workload fit, subject to the threat model and the three selection criteria below.

| Envelope                | Boundary and trusted components                                                 | Start cost (order)                            | Fits                                                                    |
|:------------------------|:--------------------------------------------------------------------------------|:----------------------------------------------|:------------------------------------------------------------------------|
| Shared-kernel container | Configured host-kernel isolation; workload and host share that kernel           | Milliseconds to sub-second                    | Trusted or reviewed code; work with no secrets or shared state in reach |
| User-space kernel       | An interposed application-kernel implementation plus its restricted host access | Milliseconds to sub-second                    | Untrusted code with modest system-call volume and supported interfaces  |
| MicroVM                 | Guest kernel separated by the VMM/hypervisor and configured hardware boundary   | Milliseconds from a snapshot; sub-second cold | Untrusted native code, package installs, multi-turn coding              |
| Restricted bytecode     | Runtime-enforced execution semantics and explicitly provided host interfaces    | Microseconds to milliseconds                  | Pure computation, parsers, per-call tools                               |

Table 5: **Execution-envelope choices**: Each envelope trusts different components and pays a different start cost; the example fits depend on the declared threat model, the code an action runs, the authority it holds, and how long it holds the envelope.

^tbl-vol3-isolation-taxonomy

Selecting an envelope depends on three characteristics of the agent’s action: the code it runs, the authority it holds, and how long it holds the envelope. Weighing those three dimensions together determines which isolation boundary in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^tbl-vol3-isolation-taxonomy|table 5]] fits the call and whether its startup cost should be paid per call or amortized across the trajectory:

1.  **Workload profile**: Pure computation over deterministic inputs maps directly to restricted bytecode. Arbitrary POSIX binaries, package managers, and shell scripts require the broader interface of a user-space kernel or a dedicated microVM. A shared-kernel container remains eligible when its configured boundary and trusted host kernel satisfy the declared threat model; it does not contain compromise of that shared kernel.
2.  **Authority level**: At ${A}_1$, where mutation is confined to a discardable sandbox, tool admission checks only the request, so once code runs the envelope must enforce the boundary against the assumed attacker. The repair scenario assumes arbitrary native code, including a compromised guest kernel, must not control host enforcement; this warrants the separate guest kernel of a microVM under that threat model. At ${A}_2$ and ${A}_3$, where actions reach external infrastructure, the envelope must be coupled with credential brokers and approval gates, because local containment cannot stop an authorized external call from altering remote state.
3.  **Execution horizon**: The time over which an envelope is retained decides how its setup is amortized. A setup of 15 ms is prohibitive for a 3 ms parser invoked hundreds of times, but negligible across a multi-turn repair trajectory that runs for minutes (Notebook [8.1](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#nbk-08-envelope-amortization)).

Applying these criteria to the three workloads that opened the section gives three different envelopes:

- The structured log parser executes in a lightweight bytecode sandbox created on demand per invocation.
- The connection-pool repair agent retains a dedicated microVM throughout its entire multi-turn trajectory. A user-space kernel is an alternative under a narrower threat model that keeps the emulator trusted, provided its interfaces and performance support the toolchain.
- The customer-uploaded binary runs in an ephemeral microVM stripped of all credentials with outbound egress unconditionally denied. A binary that needs more than this profile allows is refused rather than granted relaxed host privileges.

In every case, the security guarantee is defined by the concrete mounts, virtual devices, packet filters, and resource ceilings applied to that envelope. Performance evaluations must measure the complete lifecycle: admission latency, time to first useful work, steady-state throughput, and final teardown overhead under realistic concurrency. A runtime that advertises instant container creation often defers storage setup or package initialization to the first execution turn. Furthermore, startup costs interact directly with envelope lifecycle policies: allocating a fresh envelope for every atomic step trades initialization latency for clean-slate isolation, whereas retaining an envelope across turns amortizes startup at the cost of managing accumulated state.

**Napkin Math 8.1: Paying setup once or repeatedly**

**Problem**: A hypothetical trajectory performs 100 sequential parser calls, each requiring 3 ms of useful execution, and preparing the envelope through readiness for useful work costs 15 ms in the chapter’s illustrative sandbox profile. How much elapsed time does a fresh envelope per call add over one envelope retained for the trajectory, and at what per-call work does the fresh envelope become affordable?

**Math**: For ${N}$ calls, setup time ${T_{\text{setup}}}$, and useful work ${W}$ per call, fresh-per-call execution takes ${N}({T_{\text{setup}}}+{W})$ and trajectory reuse takes ${T_{\text{setup}}}+{N} {W}$. Both perform 300 ms of useful work. Fresh-per-call execution adds 1500 ms of setup, totaling 1800 ms; reuse adds one 15 ms setup, totaling 315 ms, a 5.7× difference. Setup is ${T_{\text{setup}}}/({T_{\text{setup}}}+{W})$ = 83.3 percent of every fresh call. Holding setup to at most 10 percent of a fresh call requires ${W} \ge {T_{\text{setup}}}(1-{\phi})/{\phi}$ for a cap ${\phi}$, here 135 ms of work per call.

**Systems insight**: The ratio ${W}/{T_{\text{setup}}}$ determines the setup-cost trade-off. Calls with at least 135 ms of useful work can afford a fresh envelope each. Below that, retaining one envelope for the trajectory reduces overhead, at the price of a within-task trust policy, since state from earlier calls reaches later ones. Reuse never crosses tenants: ready capacity for the next task comes from pooling and verified reset ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling|section 8.8]]). The comparison counts setup and useful work only, excluding model calls, queueing, and teardown.

### Resource Limits

^sec-vol3-sandboxes-resource-limits

Choosing an envelope and its lifetime settles what code can reach, not how much host capacity it may consume. An untrusted test script that enters an infinite loop, allocates gigabytes of heap, forks child processes in a tight loop, or streams gigabytes of logs to standard output can stall the host without ever breaching a file or network boundary. The host must therefore enforce resource quotas across the entire workload, including host-side helper threads and emulator processes, measured from the host kernel rather than from guest-reported counters. Even when hard quotas cap total usage, noisy-neighbor contention across shared CPU caches, memory channels, and storage buses requires separate monitoring, and validation suites should test runaway memory allocation and output floods alongside access-control denials.

On Linux systems, cgroups v2 provides a single control hierarchy to govern these execution trees across both container processes and microVM monitor and vCPU threads ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-linux2024cgroupv2|The Linux Kernel Documentation Project 2024a]]). Within that hierarchy, `cpu.max` throttles the group once it exhausts its scheduling-period CPU quota, and `pids.max` caps process creation before a fork bomb can exhaust the host process table. Memory limits use two thresholds so the supervisor does not lose diagnostic state to an abrupt kill. Crossing `memory.high` throttles allocating threads and triggers synchronous page reclaim, whereas the out-of-memory (OOM) killer steps in only if usage reaches `memory.max` after reclaim fails. Because an unannounced OOM kill wipes out transient traces and in-memory state before the supervisor can read them, that graduated buffer gives the runtime room to record why the task stalled. Supervisors pair it with Pressure Stall Information (PSI) ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-linux2024psi|The Linux Kernel Documentation Project 2024d]]), which tracks the share of elapsed time threads spend stalled on CPU runqueues, memory page allocation, or blocking disk I/O. By registering stall thresholds with `epoll`, the supervisor receives early warning when a sandbox enters severe contention and can trigger memory compaction, capture diagnostic state, or terminate the failing agent with an explicit reason code instead of losing the process silently.

### Accelerator and Device Access

^sec-vol3-sandboxes-gpu

Suppose the repository under repair contains compiled tensor kernels, so its test suite needs an accelerator to run. The candidate code the agent wrote now drives a physical device that another tenant will use next, and that device joins the isolation boundary. The envelope must then account for the host driver and the ioctl surface it exposes to the sandbox, and for the partitioning of compute and device memory. It must also account for faults that could crash a device shared with adjacent tenants, and for the device memory a tenant leaves behind, which the reset contract of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|section 8.8.1]] must scrub. Offloading accelerator work to a remote service replaces direct hardware passthrough with a structured RPC interface, shifting the isolation burden to the service’s multi-tenancy and admission controls.

Direct hardware assignment exposes the host to device direct memory access (DMA), enabling peripheral devices to read and write arbitrary host physical addresses independently of CPU page tables. Standard CPU address-space isolation provides no protection against rogue DMA transactions. As detailed in the Linux VFIO framework ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-linux2024vfio|The Linux Kernel Documentation Project 2024e]]), secure device assignment requires an I/O Memory Management Unit (IOMMU) to translate and restrict device DMA requests through dedicated I/O page tables. Because the IOMMU sits upstream near the host root complex, it can police only transactions that travel all the way up the PCIe tree. If a downstream PCIe switch routes peer-to-peer traffic directly between two slots without access control services forcing that traffic up through the IOMMU, one device can read or overwrite its neighbor’s memory without translation. Devices that can reach each other along such paths share one IOMMU isolation group, so the true physical boundary often encompasses several slots rather than a single card. For a passed-through accelerator, the unit of isolation is therefore that group rather than the microVM. Every device in the group must be assigned to the same tenant, which means the group, not the guest, sets how finely a host can divide its accelerators among tenants. Hardware partitioning features that split a single physical accelerator into isolated instances narrow that sharing, yet they do not remove the surrounding obligations. The fault domain, the driver’s exposure, and the device memory left behind must still be validated, because CPU-level virtualization guarantees end at the PCIe bus.

The selected envelope establishes a rigorous execution boundary, resource policy, and lifecycle for compute. Multi-turn workflows, however, impose a parallel requirement for state continuity, because iterative test cycles require access to code modifications and intermediate artifacts generated across preceding turns. Decoupling this persistent filesystem state from the transient lifecycle of worker processes and sandboxes requires a dedicated task-local workspace architecture governed by explicit retention and export policies.
