# V3-08.11 Summary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-summary

A sandbox is an enforceable contract defining the boundaries of execution. It specifies precisely which hardware and operating system resources untrusted code can touch, which platform components form the trusted computing base, and how long both the execution environment and its delegated privileges endure. Because these limits are enforced beneath the executing process, the boundary never depends on model compliance. However, strong isolation introduces concrete operational costs: every admitted trajectory incurs startup latency, memory footprint, and environment reset overhead. In the chapter’s README attack scenario, containment succeeds through architectural enforcement rather than prompt adherence. The injected command cannot read the host’s credentials or open a route to an unapproved destination, although the same instructions can still misuse a channel the task was permitted, as the `submit_report` request showed.

In the connection-pool repair scenario, this architecture preserves candidate patches and test artifacts while denying the agent access to the host account or the mutable state of concurrent tasks. The evaluation harness keeps validation suites outside the writable workspace, giving the test runner bounded scratch storage. This separation protects the integrity of gathered evidence, even though accepting the repair requires end-to-end evaluation beyond the targeted regression checks run against candidate `r18`. **Key Takeaways: Containment includes reach and lifetime**

- **Execution environments define blast radius**: Tool declarations specify intended interfaces, but the execution environment determines the files, sockets, and memory addresses a process can actually touch. The blast radius of an agent action spans everything its running code can read, mutate, exfiltrate, or consume. Consequently, robust isolation must be enforced by the operating system or hypervisor beneath the process.
- **In-process filtering cannot guarantee isolation**: Code executing inside the supervisor’s runtime can reach the supervisor’s objects through attribute traversal and subclass walks, and native libraries share its address space and identity. The shown escape follows from shared object reach. A process or virtual machine boundary can govern that reach, while a purpose-built language can instead bound its operands, operations, and cost by construction.
- **Capabilities bound reach to what the task was handed**: A capability binds authority to an unforgeable reference with an enforced lifetime instead of to ambient user identity. Attenuation can narrow a grant but never widen it, and deriving a child leaves the parent usable until the runtime withdraws it. Brokers let code request credentialed operations without holding the secret.
- **Envelope selection balances isolation against performance**: Containers, user-space kernels, microVMs, and bytecode runtimes place trust boundaries at different system layers and pay the system-call tax on different calls. A call-heavy build favors a guest kernel over an emulating one. Retaining an envelope for the trajectory amortizes setup when the within-task trust policy permits reuse. A policy that requires fresh state between calls can justify per-call setup even when it dominates useful work.
- **Permitted egress channels create exfiltration risks**: Network policies restrict unapproved endpoints, but permitted traffic, including API requests, artifact uploads, and DNS queries, can still carry sensitive task state outward. Once transport-level isolation is in place, safeguarding sensitive data becomes an information-flow tracking challenge.
- **Trajectory duration dictates pool capacity**: By Little’s law, active sandbox leases scale with arrival rate and total trajectory length rather than individual tool execution time. Copy-on-write memory sharing can reduce the resident footprint of concurrent agent workloads. Strict reset contracts must scrub compute, storage, and network state before an instance returns to the standby pool.

^callout-takeaways--8-2-83cdbd80

Enforcing containment beneath the model (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-zero-trust-sandboxing|9]]) ensures that execution boundaries remain intact regardless of model instructions or prompt injection attempts. This boundary complements the typed action contract (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-strict-action-abi|7]]), separating the admission of a tool request from the confinement of the code that fulfills it. Under invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]), these guarantees must reside below the model, in the supervisor and the envelope it configures, rather than in prompting guidelines. Ultimately, any isolation boundary protects only the specific resources its enforcement mechanisms monitor and reset across successive tool invocations.
