# V3-08.09 Sandbox Pools and Reset

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-pooling

The workspace lease keeps the repair’s edits, build artifacts, and helper processes alive across turns, and the egress controls bound what they can send. When the trajectory ends, a platform serving many tasks must provision the next tenant’s environment without delay. The next tenant must inherit none of the modified files, background daemons, open sockets, or credentials the repair left behind, yet it should not wait for a cold boot either. Sandbox pooling reconciles these requirements. The pool keeps a standby reserve of clean, pre-warmed instances to absorb arrivals, and an instance whose lease has ended rejoins the ready fleet only after a complete, verified reset, regardless of what status code its final tool returned.

Two naive extremes bracket this design space. At one end, a fresh envelope for every tool call carries no state between calls, but every call pays the full setup (Notebook [8.1](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#nbk-08-envelope-amortization) found setup to be 83.3 percent of each short parser call). The control plane must also pass the whole workspace across the boundary on every turn. At the other end, one long-lived environment reused across tasks pays no setup between trajectories, but mutable state accumulates in the guest, from stray files and corrupted configurations to backdoors planted by a prompt injection. A sandbox pool takes the middle path. It initializes instances in advance, holds them in a standby reserve, leases each instance to a single trajectory for that trajectory’s entire lifespan ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.07 The Agent Workspace#^sec-vol3-sandboxes-lease|section 8.6.3]]), and flags the instance as tainted the moment the lease expires. The tainted instance remains strictly unavailable until external hypervisor or operating system mechanisms either restore it to a verified baseline or destroy it entirely.

### The Reset Contract

^sec-vol3-sandboxes-pooling-reset

Wiping the workspace directory on disk does not make a used sandbox safe to hand to another tenant. A command run during the previous lease can double-fork a daemon that detaches from the task’s process group, or bind an abstract Unix domain socket with no filesystem path. It can plant a token in the kernel keyring, or schedule a cron job that fires minutes later. It can also shadow a binary earlier on the search path, or leave asynchronous work queued in a host broker. A **reset contract** specifies the exact conditions under which an execution environment is cleared for a new lease, enumerating every state domain that teardown or restoration must reset.

To stop cross-tenant leakage, the supervisor fences an expiring lease before cleanup begins, halting new tool calls under that lease and revoking its communication channels, credentials, and network authority. Next, the supervisor quiesces and terminates all owned execution, including child processes, background workers, and pending host-side tasks bound to the environment. A wall-clock timeout, error, or cancellation signal starts this sequence, but teardown requires positive confirmation from the enforcement layer rather than an elapsed timer. If the virtualization layer cannot confirm that all execution has stopped and that shared hardware resources have been severed cleanly, the supervisor destroys the instance instead of returning it to the pool.

Once all writers inside the sandbox are confirmed quiescent, the supervisor extracts and saves only the outputs permitted by the task’s export policy, such as the unified `git diff` of candidate edits and bounded test logs tied to the target commit. If artifacts are exported while the guest is still running, the supervisor enforces an explicit snapshot boundary so that concurrent writes cannot alter or corrupt the exported files. With permitted artifacts saved, the supervisor discards private mutable state or restores the environment from a trusted baseline, verifying readiness before assigning the sandbox to a new tenant. In the pool’s lifecycle ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^fig-vol3-sandbox-pool-lifecycle|figure 7]]), the only path back to standby runs through that verification, and every other exit from reclaiming ends in destruction. [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^tbl-vol3-reset-architectures|Table 7]] separates the required disposition across four state domains so a generic “reset complete” status cannot hide unhandled residue.

| State domain                       | Required disposition before reuse                                                                                                                     |
|:-----------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------|
| Guest execution and memory         | Stop owned work; destroy and recreate the execution instance or restore the defined memory, processor, and device state.                              |
| Workspace and storage              | Preserve eligible outputs, release old handles and mounts, and discard or restore the private state without modifying the trusted base.               |
| Network and broker authority       | Retire old sessions and lease identities; prevent delayed work from using the next tenant’s resources or grants.                                      |
| Host services and attached devices | Account for queued work, buffers, and device state that guest-memory rollback does not cover; complete their separate reset or keep them unavailable. |

Table 7: **Reset spans the owned state**: An implementation must specify which objects its teardown or rollback covers and how it handles the remainder. Guest reset does not reverse effects already issued to external systems.

^tbl-vol3-reset-architectures

![[90 Assets/Volume III/08 Sandboxes/Sandbox Pool Lifecycle fd4a9b5433.svg]]

Figure 7: **A Pooled Instance from Baseline to Reuse**: Instances are restored from a trusted baseline into standby, leased to one trajectory, and marked tainted when the lease ends. Reclaiming then follows the reset contract in order: fence the lease’s authority, quiesce owned work, export permitted outputs, discard or restore the covered state, and verify that contract. Passing checks return the instance to standby, and a failed check or an incomplete teardown removes it from service. The checks test a defined contract; a clean scan for known residue does not by itself show that every mutable object was covered.

^fig-vol3-sandbox-pool-lifecycle

Destroying a used execution instance and building a replacement from a trusted baseline avoids brittle denylists of files, process names, or sockets. Restoring an existing instance in place can also satisfy the reset contract, provided the restore resets every mutable layer and severs external dependencies. The condition is needed because rolling back guest memory pages and CPU registers neither purges pending messages from a host broker queue nor reverses an external database write. Any external side effect emitted before the reset remains unsettled afterward.

The accelerator obligation deferred from [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^sec-vol3-sandboxes-gpu|section 8.5.7]], scrubbing device state between tenants, lands here as the device row of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^tbl-vol3-reset-architectures|table 7]]. Terminating guest processes leaves their allocations intact in accelerator memory, where a later tenant can read leftover activations or model weights through unzeroed allocations or through inter-process memory handles that outlive the process. Before the accelerator rejoins standby, the supervisor must therefore run a device-level reset it can confirm, such as a PCIe function-level reset or a driver-mediated memory scrub, that zeroes device memory, invalidates the device’s page tables, and severs shared handles. A device whose reset cannot be confirmed stays out of service, exactly like a guest whose teardown cannot be verified.

An asymmetry governs reset verification: finding a single leftover process or file proves that reset failed, whereas scanning for known residue and finding nothing cannot prove that every mutable object was cleared. Readiness checks must therefore verify that the restoration mechanism itself ran to completion, rather than inspecting the interior of the guest against a checklist after the fact. Any failed check or incomplete teardown sends the instance straight to quarantine and destruction.

### Provisioning from a Trusted Baseline

^sec-vol3-sandboxes-pooling-snapshots

Cold-booting a fresh sandbox on every task arrival forces the incoming task to wait several seconds while the monitor starts, the guest kernel boots, language runtimes initialize, and heavy libraries load into memory. Snapshotting removes that cold-boot wait from the admission path. The runtime builds a golden environment with the required operating-system packages, interpreters, compilers, and project dependencies, initializes it once, and captures the virtual machine’s memory, processor registers, and virtual device states into a trusted baseline snapshot. Arriving tasks then restore clean instances directly from that snapshot in milliseconds. The golden baseline must never include a prior tenant’s private files, active credentials, or task residue, and it must be rebuilt regularly as security patches, compiler updates, and library revisions age out older images.

What a snapshot covers depends on the virtualization mechanism. Ephemeral storage, virtual device queues, network sockets, message broker state, system clocks, and hardware entropy pools need separate initialization outside memory restore. When cloning a running guest image, the supervisor must never duplicate a live tenant identity or reuse restored pseudorandom number generator (PRNG) state across instances, which would cause two guests to generate identical cryptographic keys or nonces. Before handing a lease to an incoming agent and letting untrusted code run its first instruction, the supervisor binds a fresh tenant identity, reseeds entropy, mounts the private workspace, configures an isolated network namespace, and installs resource limits.

Mapping the snapshot’s memory file into each new virtual machine as private copy-on-write pages (`mmap` with `MAP_PRIVATE`) lets the entire pool share one physical copy of unwritten pages such as guest kernel text, shared libraries, and precompiled bytecode. Only when an instance writes to a page does the CPU take a write fault and allocate a private page in host RAM.[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn9|⁹]] Even so, a pool’s memory budget must count both shared and private allocations. Hypervisor control blocks, extended page tables, writable workspace pages, and virtual device state all consume private host RAM, so the snapshot file size on disk does not measure the active pool’s resident memory footprint.

Lazy restoration defers reading snapshot pages into RAM until the guest touches them.[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn10|¹⁰]] While lazy paging makes sandbox creation look instantaneous in admission logs, it pushes a storm of disk or network page faults into the agent’s first tool call, especially when a burst of newly admitted instances fault in their working sets at the same time. An operator must therefore measure both the time to return a lease handle and the time until the first tool command finishes useful work.

### Sizing the Standby Pool for Bursts

^sec-vol3-sandboxes-pooling-queueing

Even a fast snapshot restore takes tens of milliseconds, so a burst of tasks arriving together will queue behind restoration workers unless clean instances are already waiting in memory. To absorb arrivals without restore delays, a pool maintains a **standby reserve** of clean, unassigned instances. Admitting a trajectory consumes one standby instance and binds it to the task. The provisioning engine starts a replacement restore, and expired leases stay quarantined until they complete their reset contract. Because reserve math depends on how the pool schedules work under load, the pool’s policy must specify upfront whether waiting tasks take precedence over rebuilding standby. It must also specify how many parallel restores the host can run without saturating memory bandwidth, and how admission behaves when host memory or CPU is full.

Sizing the pool spans two timescales: long-run active leases and short-run burst replenishment. Little’s law (theorem [5.1](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#thrm-05-littles-law)) governs the long-run active count. Under a steady flow with admitted arrival rate ${\lambda_{\text{arr}}}$ and mean lease holding duration ${T_{\text{hold}}}$, the average number of active sandbox leases is

$$
{N_{\text{active}}} = {\lambda_{\text{arr}}} \, {T_{\text{hold}}} \tag{4}
$$

^eq-vol3-pool-active

↩︎ Little’s law, and the residency tax a tool wait imposes on retained attention state, are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^sec-vol3-kv-workload-dynamics|Residence time and service rate]]**.

Because an agent holds its sandbox lease across the entire multi-turn trajectory rather than a single tool call, the agent’s deliberative horizon sets ${T_{\text{hold}}}$: the sandbox stays allocated while the model samples tokens, waits in inference queues, and runs tests. This is the mirror image of the residency tax that retained attention state pays during a tool wait. There the attention state sits idle while a test runs, and here the sandbox sits idle while the model deliberates, so the same long horizon inflates both resident footprints. Little’s law gives the mean active count, but it neither bounds peak concurrency nor guarantees that a newly arrived task will find a warm instance ready. Variable trajectory lengths, sudden arrival bursts, and reset delays still require hard admission caps paired with queueing or backpressure.

The standby reserve covers the short timescale: the replenishment window ${T_{\text{init}}}$ needed to prepare one clean instance. A cold boot pays monitor startup, guest kernel boot, and user-space setup in sequence (${T_{\text{cold}}} = {T_{\text{vmm}}} + {T_{\text{kernel}}} + {T_{\text{user}}}$), where starting language runtimes, importing libraries, and warming caches (${T_{\text{user}}}$) takes seconds. Restoring from a snapshot replaces kernel boot and user-space setup with restoring memory mappings, registers, and device state, cutting ${T_{\text{init}}}$ to milliseconds (15 ms in the chapter’s illustrative profile). Snapshotting also reshapes memory-bus traffic during a burst. Let ${M_{\text{guest}}}$ be the full memory image of one guest and ${M_{\text{dirty}}}$ the private pages one instance actually writes. Cold-booting ${N_{\text{burst}}}$ instances populates ${N_{\text{burst}}} {M_{\text{guest}}}$ bytes within ${T_{\text{cold}}}$, whereas ${N_{\text{burst}}}$ restored instances allocate only their ${N_{\text{burst}}} {M_{\text{dirty}}}$ private pages and spread those writes across the trajectory.

The reserve estimate here uses an idealized replenishment policy. Offered requests form a stationary Poisson stream. Every offered request, including one that must wait, immediately orders one clean replacement that becomes ready after the same ${T_{\text{init}}}$. Restore concurrency is unlimited, and active leases and memory have no admission limit. No request is lost, and completed replacements serve waiting requests in arrival order before rebuilding standby, so admitted throughput equals offered throughput and the same ${\lambda_{\text{arr}}}$ serves the active-lease estimate. Ended leases supply no ready instances until their reset completes and are not counted again as replenishment.

Under this policy, every arrival reduces net ready inventory (ready standby instances minus waiting requests) by one and starts one replacement that finishes after ${T_{\text{init}}}$. The sum of net ready inventory and in-flight replacements therefore stays fixed at ${N_{\text{reserve}}}$. Just before a new request arrives, the replacements still in flight are the orders placed by earlier arrivals during the preceding ${T_{\text{init}}}$ window. When that in-flight count is at least ${N_{\text{reserve}}}$, no ready instance remains in standby and the arriving request must wait. With one standby instance, for example, a second request that arrives before the first replacement finishes already waits. Because requests arrive as a Poisson stream at rate ${\lambda_{\text{arr}}}$, the number of arrivals during any window of duration ${T_{\text{init}}}$ follows a Poisson distribution with mean ${\lambda_{\text{arr}}} {T_{\text{init}}}$ and variance ${\lambda_{\text{arr}}} {T_{\text{init}}}$. Because Poisson arrivals see the stationary state, the request-level miss probability is the Poisson tail at or above ${N_{\text{reserve}}}$. Lost requests, replenishment only for admitted requests, finite restore workers, variable lead times, and resource admission limits each require a different calculation. To screen a reserve against a miss target ${\epsilon}$ (chosen by the operator, unrelated to the per-turn error rate of horizon compounding), approximating that Poisson count by a normal distribution with mean ${\lambda_{\text{arr}}} {T_{\text{init}}}$ and standard deviation $\sqrt{{\lambda_{\text{arr}}} {T_{\text{init}}}}$ yields

$$
{N_{\text{reserve}}} \ge {\lambda_{\text{arr}}} {T_{\text{init}}} + {z_{1-\epsilon}}\sqrt{{\lambda_{\text{arr}}} {T_{\text{init}}}} \tag{5}
$$

^eq-vol3-pool-reserve

where ${z_{1-\epsilon}}$ denotes the standard normal quantile.[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn11|¹¹]] Round this screening estimate upward, then check the discrete Poisson tail at or above the chosen reserve, since the quantile expression is not an exact guarantee. At small means the normal approximation is unsuitable. A guest-page memory budget follows from copy-on-write page sharing across one golden template, private dirty pages accumulated by active leases, and base overheads for standby instances:

$$
{M_{\text{pool}}} = {M_{\text{template}}} + {N_{\text{active}}} \, {M_{\text{dirty}}} + {N_{\text{reserve}}} \, {M_{\text{standby}}} \tag{6}
$$

^eq-vol3-pool-memory

The equation combines mean active guest pages with the configured standby allowance; it is not an instantaneous bound. It excludes waiting demand, transient restores, quarantine, and host monitor, page-table, and control state. A real budget also sets aside headroom; Notebook [8.4](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#nbk-08-sizing-a-pre-warmed-microvm-pool) charges both explicitly. Notebook [8.3](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#nbk-08-reserve-from-arrival-rate) applies these sizing relationships to a steady arrival stream.

**Napkin Math 8.3: Sizing a pool from its arrival rate**

**Problem**: A platform receives 2 offered coding trajectories per second under the no-loss, constant-lead-time policy, and each holds its lease for 300 s. In the chapter’s illustrative sandbox profile, restoring one clean instance from its snapshot takes 15 ms and a full guest image is 512 MB. Each active lease writes about 64 MB of private pages, and each standby keeps 8 MB. Does one standby meet the request-level miss target of 0.1 percent, what is the smallest supported reserve, and what guest-page allowance covers mean active leases and that reserve?

**Math**: By [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^eq-vol3-pool-active|equation 4]], active leases average ${\lambda_{\text{arr}}} {T_{\text{hold}}}$ = 2 per second × 300 s = 600. Arrivals during one restore average ${\lambda_{\text{arr}}} {T_{\text{init}}}$ = 0.03, far too small a mean for the normal approximation in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^eq-vol3-pool-reserve|equation 5]], so the Poisson tail is read directly. One standby misses when at least one prior replacement remains outstanding, with probability 2.96 percent, above the target. The smallest supported reserve is 2; its miss event requires at least two prior outstanding replacements, with probability $1 - e^{-{\lambda_{\text{arr}}} {T_{\text{init}}}}(1 + {\lambda_{\text{arr}}} {T_{\text{init}}}) \approx$ 0.044 percent, below the target. Private guest images for every active lease would occupy about 322.1 GB. With copy-on-write, [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^eq-vol3-pool-memory|equation 6]] gives about 39.0 GB, 8.3× less.

**Systems insight**: The agent’s trajectory horizon, rather than the latency of individual tool calls, dictates overall fleet cost. Active leases and their resident memory grow linearly in ${T_{\text{hold}}}$, so doubling trajectory length doubles the memory term, while copy-on-write sharing keeps a fleet of per-trajectory microVMs affordable. The reserve is governed instead by ${\lambda_{\text{arr}}} {T_{\text{init}}}$ and is sharply sensitive to it. The selected reserve of 2 meets the target only while restore stays below about 22 ms, and a 10× slower cold boot (${\lambda_{\text{arr}}} {T_{\text{init}}}$ = 0.3) needs a reserve of 4. Because every attempt holds its sandbox for ${T_{\text{hold}}}$, sandbox residency is part of $\mathbb{E}[{C_{\text{attempt}}}]$ in the cost per accepted task ${C_{\text{eff}}}$ (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**), and a rejected attempt pays it again. The estimate assumes the declared no-loss replenishment policy with constant lead time and unlimited restore concurrency; the next notebook treats a finite-worker burst.

While steady Poisson arrivals provide a baseline for continuous operations, agent workloads frequently experience sudden synchronized surges, such as a continuous-integration suite launching parallel repair tasks. A burst also breaks an assumption behind [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^eq-vol3-pool-reserve|equation 5]], because a host can run only a fixed number of restores at once, so replenishments queue instead of all finishing within ${T_{\text{init}}}$. Notebook [8.4](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#nbk-08-sizing-a-pre-warmed-microvm-pool) analyzes a deterministic burst under that limit to trace standby consumption, queue draining, and memory budgeting when arrival volume temporarily outstrips replenishment capacity.

**Napkin Math 8.4: Consuming and replenishing a ready reserve**

**Problem**: How long does a specified burst wait for clean environments, and what resident-memory allowance supports the resulting active leases and rebuilt reserve?

**Variables**: A hypothetical pool starts with 4 clean standby instances and no active leases. At the initial instant, 12 tasks arrive together. The supervisor admits as many as standby permits, then prioritizes queued tasks over rebuilding the reserve. It can restore 2 instances concurrently, each taking exactly 15 ms to become ready under that concurrency. Assume sufficient execution slots for all tasks, no other arrivals, no lease returns during the calculation, and no restore failures. Handoff and dispatch time are negligible in this model; the restore interval includes the required readiness work.

**Math**: Initial admission consumes the reserve, leaving 12 − 4 = 8 tasks waiting. The workers serve those tasks in 4 rounds of 15 ms, so the last admission occurs at 60 ms. Rebuilding the original reserve takes another 2 rounds. The pool has its full reserve again at 90 ms, while all 12 admitted leases remain active. Admitting the burst finishes allocating the environments, but the trajectories themselves continue executing.

For an illustrative memory allowance at that final state, suppose immutable resident pages consume 1,000 MB shared across the pool. Each active instance has 64 MB of additional private resident state, and each standby has 8 MB. The resulting 16 instances each require 8 MB for monitor, page-table, and control state. Reserve another 256 MB of headroom. The budget is in decimal megabytes and sums the exact byte quantities.

1,000 MB shared + 768 MB active-private + 32 MB standby-private + 128 MB control + 256 MB headroom = 2,184 MB.

The private-state terms include resident writable workspace pages, so the workspace is charged once. Host and broker services, storage caches, disk, and accelerator memory sit outside this pool-residency allowance. Transient restore buffers must fit within the stated headroom, and enforcement uses exact byte counts.

**Systems insight**: The standby reserve governs instantaneous admission capacity, while restoration concurrency dictates queue drainage rate. The last admission waits $\lceil ({N_{\text{burst}}} - {N_{\text{reserve}}})/{w} \rceil \, {T_{\text{init}}}$ for a burst of ${N_{\text{burst}}}$ tasks, a reserve of ${N_{\text{reserve}}}$, and ${w}$ restore workers. Using 4 workers instead of 2 therefore cuts the wait from 60 ms to 30 ms, provided restores do not slow under the added concurrency. Each added standby admits one more task immediately and costs 8 MB of idle private memory. The trace is deterministic; a different arrival pattern needs its own calculation.

An exhausted reserve must trigger explicit queueing, deferral, or rejection signals; it must never license the supervisor to lease an unreset or unverified sandbox to bypass admission bottlenecks. Admission control must also track physical resource headroom across active execution and background restoration. Instances awaiting teardown or memory scrubbing continue to occupy host memory and hypervisor tracking tables without providing usable standby capacity. Delays in resetting expired leases therefore represent hidden capacity drains that operators must measure alongside restore latency and trajectory duration.

**Checkpoint 8.2: Sizing and reclaiming a pool**

The pool equations and the reset contract answer each of these.

**Active-lease estimate**: Arrivals double while trajectories become half as long. Estimate the change in mean active leases, and name which term of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^eq-vol3-pool-memory|equation 6]] moves.

**Reserve sensitivity**: A cold boot replaces snapshot restore and takes an order of magnitude longer. Estimate ${\lambda_{\text{arr}}} {T_{\text{init}}}$ from the inputs of Notebook [8.3](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#nbk-08-reserve-from-arrival-rate) and compare the minimum reserves that meet the request-level miss target at the baseline and tenfold lead times.

### Sandboxes for Evaluation and Training Rollouts

^sec-vol3-sandboxes-substrate

↪ Repeated runs, confidence intervals, and paired comparisons for agents evaluated on this substrate are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-rigor|Statistical Evaluation Rigor]]**.

When an evaluation harness or a reinforcement-learning rollout loop runs thousands of candidate patches against a repository’s native test suite, any leftover file from a prior attempt or any writable test script lets a candidate pass by corrupting the grader rather than fixing the bug. Benchmarks such as SWE-bench ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-jimenez2024swebench|Jimenez et al. 2024]]) and training rollout pools therefore rely on the same pooled sandbox lifecycle as production traffic. A pinned baseline snapshot and a verified reset prevent cross-attempt contamination, while read-only mounts keep the test harness outside the agent’s writable scope and leave the runner only bounded scratch storage and controlled logging channels. Even so, an evaluation team must separate execution containment from test quality. A clean sandbox guarantees that the test suite started from a known baseline. It does not guarantee that the tests cover the bug, or that external dependencies, non-deterministic timers, and floating-point drift will produce identical scores across runs. Whether the pool serves production, evaluation, or training, its guarantee has the same shape. It provides a contained execution with task-local continuity starting from a verified baseline. What happens inside that boundary, including which permitted channels the code uses and what it sends through them, lies outside that guarantee. A sandbox that passes every reset check can therefore still host a task that discloses what it was allowed to read.
