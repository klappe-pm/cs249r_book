# V3-08.07 The Agent Workspace

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-cow

In the connection-pool repair task, the agent generates an edit in one turn to create candidate patch `r18`, runs a shell command in the next turn to compile the code, and then invokes the test suite to produce an evaluation report. Spawning a fresh process for every command protects the host from runaway memory allocations or lingering background jobs, but those separate processes must still view and modify a shared, continuous filesystem state. Conversely, keeping a single process alive does not establish boundaries around which files the agent may alter. An agent execution environment therefore requires an explicit workspace policy independent of its execution envelope.

That workspace policy delineates four boundaries: the immutable source baseline, the task’s private modifications, temporary scratch space, and the artifacts eligible for final export. Generated commands execute strictly within a designated task workspace, isolated entirely from the host’s primary working tree or operational directories. For a code repair run, candidate edits and intermediate build artifacts reside inside this task workspace. At the same time, authoritative acceptance test suites, benchmark harnesses, and reporting mechanisms remain strictly outside the agent’s writable scope, even when the agent is permitted to write temporary test output into a monitored scratch directory.

### Copy-On-Write Provisioning

^sec-vol3-sandboxes-cow-provisioning

A full private copy offers a straightforward way to provision an agent workspace, but creating duplicate copies of large source repositories, compilers, language runtimes, and dependencies introduces severe storage and I/O bottlenecks. Copy-on-write solves this by decoupling the immutable base environment from the modifications generated by individual tasks. The runtime pins a read-only base image and exposes a private, writable view for each trajectory. Read requests transparently access the shared base contents, while write operations allocate private storage on demand according to the underlying filesystem’s copying rules. Workspaces sharing the same underlying base remain completely isolated from each other’s mutations.

![[90 Assets/Volume III/08 Sandboxes/Vol3 Sandboxes Margin Copy Payload 6f61b155b9.svg]]

*Two horizontal bars on a log scale: full copy at 76.8 GB and copy-on-write at 1.28 GB of provisioning payload for 32 workspaces.*

*Copy-on-write provisioning moves what tasks write, not what they can see.*

A **layered filesystem** provides a standard implementation of this pattern at the file level. A read-only lower directory tree supplies the baseline repository, while a private, writable upper directory tree stores newly created, modified, or overwritten files. A union mount combines these two layers into a single merged namespace visible to the executing agent. When an agent deletes a file that exists in the read-only lower layer, the filesystem cannot remove the shared file; instead, it writes a special deletion marker into the upper layer to hide the lower entry. In Linux OverlayFS, this marker is known as a *whiteout* ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-linux2024overlayfs|The Linux Kernel Documentation Project 2024c]]). Because copy-up operations, directory merges, and whiteouts involve kernel metadata and filesystem-specific structures, the upper tree does not represent a clean, ready-to-commit source tree or patch.

The merged views in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.07 The Agent Workspace#^fig-vol3-workspace-overlay-visibility|figure 5]] distinguish shared bytes from task-visible files. The panels follow one overlay-filesystem backend while task A first edits a file and then deletes another; task B continues to read the baseline.

![[90 Assets/Volume III/08 Sandboxes/Workspace Overlay Visibility 1605b0fe77.svg]]

Figure 5: **Private Views over a Shared Baseline**: Both tasks initially read the same lower files through separate merged views. The first edit copies the code file into task A’s upper layer; deleting the lower data file then adds a whiteout in that upper layer. Neither operation changes the shared lower tree or task B’s view. These are file-level overlay semantics, not block-snapshot operations.

^fig-vol3-workspace-overlay-visibility

The private upper layer records differences from the baseline, including absence. Exporting the visible result therefore requires interpreting those differences; copying the upper directory alone would preserve internal deletion markers instead of a clean task artifact.

Furthermore, copy-on-write is a storage optimization, not an execution isolation boundary. Preventing concurrently executing tasks from modifying the shared base or reading each other’s private layers remains the duty of the sandbox execution envelope. That envelope also determines how the workspace is mounted and cached in memory. Containers sharing the host kernel can mount a file-level overlay directly, allowing every sandbox to read unmodified files from a single host page cache. A microVM, by contrast, typically attaches its workspace as a copy-on-write virtual block device managed by its own guest kernel. Unless the hypervisor maps shared host pages directly into the guest, each virtual machine caches the blocks it reads inside its own guest page cache, duplicating popular toolchain and library pages across active sandboxes.

### Cost of the First Modification

^sec-vol3-sandboxes-first-modification

How much data copy-on-write actually copies on the first write depends on whether the storage layer tracks whole files or fixed-size blocks. Under a file-level overlay such as OverlayFS, modifying a single byte in a 1.2 GB test fixture forces the filesystem to copy the entire 1.2 GB file into the private upper layer before applying the write. Because copy-on-write defers copying from workspace creation until an agent first mutates a file, the granularity of that copy operation sets both first-write latency and storage overhead. A block-level storage volume or an extent-sharing filesystem instead allocates private storage only for the modified blocks or extents, leaving shared pointers in place for the rest of the file. Even block-level sharing cannot make a one-byte edit cost one physical byte of I/O, however, because metadata allocation, journaling, and page-cache updates still operate on whole blocks.

**Napkin Math 8.2: Provisioning by copy, and the granularity of a first modification**

**Problem**: An evaluation host starts 32 workspaces for the same task. The pinned base (repository, toolchain, and dependencies) is 2.4 GB, and each task writes about 40 MB of edits and build outputs. The workspaces share one local drive with a sequential rate of 7 GB/s. How much payload does a full private copy move compared with a copy-on-write view, and what does a later one-byte change to a shared file cost?

**Provisioning**: A full copy moves 32 × 2.4 GB = 76.8 GB before any agent runs, at least 11.0 s of drive time even at the sequential rate. A copy-on-write view starts as a mount, and only written data acquires private storage, 1.28 GB across all tasks, at least 0.18 s. The copy moves 60× as many bytes, and the ratio is the base size over the bytes each task writes. Copy-on-write makes provisioning cost track what the agent changes, not what it can see.

**First modification**: Each of 32 independent workspaces initially shares an unchanged 1.2 GB binary fixture. Each task overwrites 1 byte within that fixture. Compare two hypothetical implementations: the first copies the entire file’s payload into private storage before modifying it; the second copies only the one 64 KB block containing the update. Assume that block was shared before the update and that no other block needs copying. Neither implementation uses a copy offload or compression in this accounting.

**Math**: File-granularity copying moves 32 × 1.2 GB = 38.4 GB of payload. Under the stipulated block-copy rule, the corresponding total is 32 × 64 KB = 2,048 KB. Both support the same 32 bytes of requested logical changes, and the file-granularity payload is about 19,000× larger.

**Systems insight**: Two ratios set the storage bill. Provisioning cost scales with the base size over the bytes each task writes (60× here), so copy-on-write wins whenever tasks change a small fraction of what they can see and loses its advantage as that fraction approaches one. First-write cost scales with the fixture size over the copying unit (about 19,000× here), independent of the edit’s size, so large mutable fixtures belong on block-granular storage and large immutable ones stay read-only. The totals count payload only; metadata, journaling, and caching add traffic, so the drive-time figures are lower bounds.

These two ratios point to three storage rules:

- *Mount immutable fixtures read-only*: Large test fixtures, model weights, and compiler binaries should remain strictly read-only whenever tasks do not require in-place mutation. Read-only mounts prevent inadvertent copy-up operations while allowing multiple concurrent sandboxes to share host page-cache entries.
- *Redirect volatile outputs to scratch volumes*: Build outputs, compiler intermediate files, and execution logs should write directly to dedicated, bounded scratch storage rather than triggering copy-up chains within the primary workspace overlay.
- *Align storage granularity with access patterns*: If tasks must perform localized edits on very large files or databases, systems should deploy block-level snapshotting or extent-sharing filesystems. Copy-on-write saves most I/O when an agent mutates a minor fraction of the workspace, but its performance advantage diminishes rapidly as modifications approach the size of the base image.

Even with copy-on-write efficiency, private task storage still needs hard bounds because runaway build logs, recursive file generation, or bloated cache directories can fill a host drive in seconds. The runtime therefore enforces quotas on both storage bytes and inode counts alongside I/O rate limits, surfacing any quota breach as an explicit resource-exhaustion error rather than letting a tool call fail with partial writes or corrupted state. Those per-workspace caps must also feed into host-level admission control, since dozens of sandboxes that each stay within a 10 GB quota can still exhaust a shared physical drive unless aggregate allocation is bounded.

### Workspace Leases

^sec-vol3-sandboxes-lease

Across a multi-turn repair trajectory, intermediate build caches, compiler outputs, and source edits must survive from one tool call to the next without ever becoming visible to a concurrent or subsequent tenant. A **workspace lease** enforces this continuity by binding a provisioned workspace to a single task, owner, execution envelope, and lifetime. When the agent dispatches a command during its turn, the runtime attaches the worker process to the leased workspace; when a new task arrives, it receives a separate, freshly provisioned view.

↪ Checkpoints that bind the lease’s workspace files to a committed log position, so private state survives a worker crash as well as a turn boundary, are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.05 Checkpoints#^sec-vol3-persistence-checkpointing|Checkpoints]]**.

The lease is an ownership and lifetime contract, not a concurrency lock. It differs from the scheduler’s lease of **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|Operation identity and endpoint contracts]]**, where a stale worker may still be running somewhere else and the destination must fence its writes with an epoch. A workspace is attached to one envelope, so a stale holder is fenced by the supervisor itself, which revokes the envelope’s access when the lease ends ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|section 8.8.1]]). Holding an active lease establishes which tenant owns a storage volume, but it does not guarantee that an earlier asynchronous command has finished writing or that orphaned background processes have closed their file handles. Before ending a tool turn or exporting workspace state, the runtime must stop lingering background jobs and flush pending I/O so that all writers are quiescent.

↩︎ Supervision and cancellation of background jobs that outlive a tool turn are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.09 Asynchronous Tool Dispatch#^sec-vol3-tool-calling-async-governance|Job supervision and cancellation]]**.

When a task finishes, the runtime extracts only the outputs allowed by the task’s export policy before tearing down private state. For a code repair agent, those outputs typically include a unified patch against the pinned baseline, a cryptographic hash or manifest of the resulting source tree, and structured logs from the test suite. The export pipeline must read from a stable snapshot or wait until all writer processes have stopped, so that the exported patch matches the exact files the test suite ran against. It must also canonicalize and check every file path inside the workspace boundary; otherwise, a symbolic link planted by an untrusted agent could trick the exporter into reading and leaking a host file.

A runtime must never archive the raw upper directory of an overlay filesystem as the task deliverable, because that upper layer contains kernel whiteout markers, internal metadata, compiler caches, temporary build artifacts, and any secrets spilled into the workspace. Export pipelines instead parse and filter outputs into clean diffs and vetted test reports. Downstream release pipelines verify independently that a candidate patch applies cleanly to trunk and passes continuous integration under trusted credentials before merging. The runtime then discards the remaining private state under the pooling and reset rules of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling|section 8.8]]. Controlling what the export pipeline extracts closes the file-based route out of the workspace. Running code inside the sandbox can, however, also open network sockets to send proprietary source code, test fixtures, or discovered vulnerabilities straight to an outside server, so the sandbox must govern outbound network traffic independently of storage.
