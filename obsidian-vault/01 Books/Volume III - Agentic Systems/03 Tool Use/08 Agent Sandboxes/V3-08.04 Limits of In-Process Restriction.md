# V3-08.04 Limits of In-Process Restriction

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-in-process-failure

The repair agent’s compiles and test runs need a process of their own; the temptation to skip one is strongest for small analysis steps. Consider the research agent summarizing a CSV file it retrieved. When the agent generates a Python script to compute summary statistics, an engineer might be tempted to execute that code directly inside the supervisor’s own Python runtime. In-process execution is appealing because it avoids the latency of spawning a child process and the cost of inter-process serialization, and it reuses heavy numerical libraries already resident in memory. However, this convenience co-locates untrusted, model-generated code with the supervisor’s private state, database connections, and operational credentials. Attempting to sanitize this environment by stripping dangerous functions from the script’s global namespace confuses an interface filter with an execution boundary. Although schema and argument checks verify that the agent requested an analysis operation, the arbitrary code carried within that payload executes with the full operational reach of the host process.

### The Reachable Object Graph

^sec-vol3-sandboxes-object-graph

Suppose a runtime developer attempts to isolate execution by passing an empty `__builtins__` dictionary and a single helper function, such as `total`, to Python’s `eval()` or `exec()`. The intended interface allows the script to sum numbers while withholding access to system calls. In ordinary Python, however, user-defined functions retain a live reference to the global namespace of the module where they were defined (`func.__globals__`). As demonstrated in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.04 Limits of In-Process Restriction#^lst-vol3-sandbox-escape|listing 1]], generated code can traverse this reference directly from the permitted helper function, recovering the supervisor’s module scope without ever invoking `import` or calling `globals()`.

``` python
# Defined in the supervisor module:
def total(values):
    return sum(values)

# Intended interface for generated code:
restricted = {"__builtins__": {}, "total": total}

# An expression submitted to eval(expression, restricted):
expression = "total.__globals__"
# Its result is the helper's defining module namespace,
# not merely the restricted dictionary above.
```

Listing 1: **Restricted names, reachable state**: A Python helper defined in the supervisor module retains access to that module’s globals. Passing the helper into another globals dictionary does not relocate or isolate it. This is a failure example, not a sandbox implementation.

^lst-vol3-sandbox-escape

This escape assumes only a standard Python function and unrestricted attribute access. The exposed module namespace often contains imported packages, configuration values, active network clients, and raw system primitives that the supervisor never intended to expose. Once code gains access to these objects, its reach expands to match the full operating system permissions of the supervisor process. The failure occurs long before the program reads a protected file or opens a network socket, because the interface boundary fails at the level of the language runtime itself.

Patching this vulnerability by blocking access to `.__globals__` merely invites alternate traversal paths. A denylist that filters specific attribute names must account for every object passed into the execution scope and every reference reachable through their class hierarchies. In dynamic languages, string-based filters fail because attribute names can be assembled at run time using dynamic lookups, such as `getattr(obj, "__" + "globals" + "__")`. Any literal value also provides a path to the universal base class `object`, from which an attacker can enumerate all subclasses loaded into memory, including classes that manipulate files and spawn processes.[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn1|¹]]

The shown escape follows from an accessible object reference inside the shared interpreter, not from undecidability. Rice’s theorem ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-rice1953classes|Rice 1953]]) addresses a broader limit: no classifier can decide every non-trivial semantic property of unrestricted Turing-complete programs. A classifier that admits all programs that never invoke a process-launching object and rejects every program that eventually does cannot be both sound and complete. A conservative filter may instead reject legitimate programs, and a restricted language may make its permitted behavior decidable. Effective confinement of arbitrary code must govern what execution can reach through its environment, rather than rely on a perfect classification of its source text.

Restricted languages and domain-specific evaluators remain useful in systems design. A purpose-built arithmetic evaluator can safely process formulas over supplied variables, and an isolated bytecode engine can enforce strict constraints on memory allocation and host imports. Such designs succeed because they enforce explicit capability models with formal resource guarantees, and the conditions are specific enough to check. In-process evaluation is safe only when all of the following hold. The language’s operands must be the values the supervisor supplied, so no reference leads back to the supervisor’s objects. The language must have no attribute access, calls, imports, or unbounded loops, so the reachable set cannot grow during evaluation. Its worst-case cost must be bounded by the size of the input, so a hostile expression cannot stall the supervisor that must stay responsive to every other task. A guard such as `p99_ms < 400 and error_rate < 0.01`, which the remediation agent attaches to a proposed configuration change and the supervisor evaluates over supplied metrics, meets all three. A single regular-expression operator with a backtracking matcher breaks the third, because its running time can grow exponentially in the input length. Designs that meet the conditions must not be conflated with running arbitrary Python code inside an interpreter whose globals have merely been pruned.

### Native Libraries and the Failure Domain

^sec-vol3-sandboxes-native-libraries

Even if an interpreter blocked every Python-level reference escape, data analysis scripts routinely invoke native extensions in C, C++, or Fortran to manipulate multidimensional arrays, parse structured files, and run numerical kernels. When those extensions execute in-process, their memory accesses take place directly in the supervisor’s address space, bypassing interpreter-level restrictions entirely. An out-of-bounds write or use-after-free in a C or C++ parser running inside the supervisor process can overwrite the supervisor’s heap, expose its in-memory API keys, or execute arbitrary machine instructions with the supervisor’s privileges.

A native-code compromise collapses the boundary at the operating system level. System calls issued from a compromised thread pass the kernel’s access checks because the kernel identifies the thread as the supervisor process. The compromised thread can then expose the supervisor’s credentials, terminate concurrent tasks, and halt enforcement of the broader tool contract. The underlying design question is which components belong to the trusted computing base. In-process evaluation places the language interpreter, user-defined helpers, third-party native libraries, and the supervisor’s orchestration logic into a single failure domain. Stripping symbol names from a script leaves all of these shared components exposed to memory corruption.

### Shared Authority and Shared Resources

^sec-vol3-sandboxes-shared-authority

Spawning a separate child process isolates virtual memory, but a child process launched under the developer’s OS user account still inherits open file descriptors, active database sockets, environment-variable tokens, and full read-write access to the developer’s home directory. Isolating address spaces does not automatically restrict **ambient authority**, the reach a process holds by virtue of the identity it runs as rather than because the task handed it anything. Zero ambient authority, which the introduction requires of the model, must therefore also hold for the processes its tool calls start. Inherited file handles maintain access even when the worker possesses no code to open those files by path, so sandboxing requires explicit control over which identities, descriptors, sockets, and filesystem mounts a worker process receives.

↩︎ Zero ambient authority, the requirement that every side effect pass through an explicit grant, is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-fail-plausible|The fail-plausible fault]]**.

System availability likewise demands an enforced boundary. A script can consume CPU cycles indefinitely, exhaust memory allocations, or flood the local disk with temporary files without ever reading a secret or transmitting a network packet. Permitted operations such as file creation or child process spawning can exhaust system-wide file descriptor tables or process table capacity. Namespace filtering cannot budget or bound these resources. If execution occurs within the supervisor process, halting a runaway loop or reclaiming leaked memory requires terminating the supervisor itself.

An execution boundary must therefore budget and enforce task-scoped limits from outside the worker: CPU cores, wall-clock time, hard memory ceilings, process counts, storage footprint, and standard output volume. When execution stalls or exceeds its quota, the supervisor steps in to throttle the group, reject further requests, or terminate the worker process, stopping further compute even though termination cannot undo external side effects that have already committed. [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^sec-vol3-sandboxes-microvms|Section 8.5]] compares the isolation envelopes that modern operating systems and hypervisors provide to enforce these limits. The runtime must first decide, however, which authorities may cross the boundary at all, because a child process that inherits the supervisor’s credentials has its own address space and is still unconfined.
