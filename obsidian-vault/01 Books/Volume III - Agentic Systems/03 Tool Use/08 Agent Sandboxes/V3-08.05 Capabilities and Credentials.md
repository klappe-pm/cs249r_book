# V3-08.05 Capabilities and Credentials

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-least-privilege

In the README attack, the task needs repository access, not the developer’s credentials, and the runtime must carry that distinction into the resources the executing code can reach. A `run_shell` worker launched with the developer’s identity is the confused deputy of definition [7.3](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-confused-deputy) moved one layer down. The GitHub MCP leak showed a tool adapter spending the user’s repository authority on an attacker’s behalf, and here a subprocess spends the developer’s file and network authority on behalf of README text. Identity-based access control can express narrow permissions through an access control list;[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn2|²]] the failure is letting the request exercise the service’s broader authority instead of the authority delegated for this task. That failure comes naturally under ambient authority, since an ordinary process exercises whatever its identity can reach. Capabilities, introduced by Dennis and Van Horn ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-dennis1966|1966]]) for multiprogrammed systems, make the delegation explicit instead ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-saltzer1975|Saltzer and Schroeder 1975]]; [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-miller2006robust|Miller 2006]]).

↩︎ The confused deputy, and the GitHub MCP leak that illustrates it, are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.05 Interoperable Tool Discovery#^sec-vol3-tool-calling-discovery-authority|Discovery and authority]]**.

**Definition 8.2: Capability**

A ***capability*** is an unforgeable reference that both designates a resource and authorizes specific operations on it, so that holding the reference is the permission to use it.

1.  **Significance**: It lets the runtime hand executing code exactly the objects and operations of the task grant, bounding the code’s blast radius by what it was given rather than by what its identity can reach.
2.  **Distinction**: Under ambient authority a process can reach everything its identity may touch, named globally; under capabilities the default reach is empty, and every access goes through a reference the holder received.
3.  **Common pitfall**: Treating a plain identifier, or a token the model can read and rewrite, as a capability. Without a protected binding the holder can forge or substitute a broader reference.

The goal both models serve is **least privilege**, the rule that each process holds only the authority its current task needs, so that a fault or an injected instruction can misuse no more than that task’s grant. Ambient authority grants more than the task needs by default, and capabilities make the rule enforceable. The two models differ in where authority comes from, how resources are named, and how authority is passed on and revoked ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^tbl-vol3-ambient-vs-capability|table 2]]). For the README attack the decisive row is default reach. Under ambient authority the injected command starts with everything the developer’s identity can touch, including `~/.aws/credentials`. Under capabilities it starts with nothing and holds only the references the task grant handed it.

↩︎ Least privilege applied to the separate operations on a job handle is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.09 Asynchronous Tool Dispatch#^sec-vol3-tool-calling-async-escrow|Job handles]]**.

| Dimension               | Ambient authority (identity and access control lists)         | Capability-based authority                                   |
|:------------------------|:--------------------------------------------------------------|:-------------------------------------------------------------|
| **Source of authority** | The identity the process runs as                              | Possession of an unforgeable reference                       |
| **Naming of resources** | Global names such as paths and network addresses              | Handles or tokens that designate the resource                |
| **Default reach**       | Everything the identity may touch                             | Nothing without a reference                                  |
| **Delegation**          | Typically the identity’s rights, or a separately managed role | Any subset, down to one object and one operation             |
| **Confused deputy**     | Common when a request exercises the service’s own authority   | Excluded when every access uses a designating reference      |
| **Revocation**          | A policy change for the identity                              | Expiry, a checked status on the reference, or handle closure |

Table 2: **Ambient and capability-based authority**: The two models differ in where authority comes from and how it is passed on, which decides whether a tool process can be steered into using authority the task never received.

^tbl-vol3-ambient-vs-capability

### Scoped Grants

^sec-vol3-sandboxes-scoped-grants

Turning capability-based authority into an enforceable runtime check requires an unforgeable representation. If a runtime represents a task grant as a plain file path or an unsigned string that the worker process can inspect and edit, the worker can substitute `~/.aws/credentials` or rewrite `"read"` to `"write"` to widen its own reach. A capability must instead be a protected handle checked by a runtime or kernel, or a cryptographic token verified by a service; it need not be a string visible to the model at all. Either way, the enforcement layer prevents the holder from fabricating broader rights or substituting another task’s reference.

Use ${\Gamma} = ({\mathcal{R}_{\Gamma}}, \mathcal{O}_{\Gamma}, {\phi_{\Gamma}}, {t_{\text{exp}}})$ as an abstract description of a grant: rights ${\mathcal{R}_{\Gamma}}$, objects $\mathcal{O}_{\Gamma}$, condition predicate ${\phi_{\Gamma}}$, and expiry time ${t_{\text{exp}}}$. The tuple describes authority independent of any token encoding. Its conditions can pair different operations with different objects and bind use to a task or recipient, so read and write listed among the rights need not both apply to every listed object.

The tuple becomes operational as a check. A proposed access ${r}$ names an operation, a target, and its arguments. The enforcement point admits it at time ${t}$ only if every condition in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^eq-vol3-capability-verdict|equation 1]] holds:

$$
\text{admit}({r}, {\Gamma}, {t}) \iff \text{authentic}({\Gamma}) \land {r}.\text{op} \in {\mathcal{R}_{\Gamma}} \land {r}.\text{target} \sqsubseteq \mathcal{O}_{\Gamma} \land {\phi_{\Gamma}}({r}) \land {t} < {t_{\text{exp}}} \tag{1}
$$

^eq-vol3-capability-verdict

Here $\text{authentic}({\Gamma})$ means the reference is protected and bound to this holder, whether by a kernel handle table or by a message authentication code the issuer can verify. The relation ${r}.\text{target} \sqsubseteq \mathcal{O}_{\Gamma}$ means the resolved target lies within the designated objects for that operation. A rejected access changes nothing and returns a structured observation the model can act on. The check is also cheap relative to what it guards. Verifying a handle or a message authentication code is a local computation, orders of magnitude shorter than the model call that produced the proposal, so mediating every access costs nothing a user would notice. The expensive part of capability enforcement is making sure no path bypasses the check.

For the repair, [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^tbl-vol3-scoped-repair-grant|table 3]] separates the resources an execution grant could cover. Paths are names relative to the task’s designated workspace, not arbitrary host paths.

| Resource                                  | Permitted use                                                        | Excluded use                                                  |
|:------------------------------------------|:---------------------------------------------------------------------|:--------------------------------------------------------------|
| Candidate source, including `src/pool.py` | Read and edit the permitted source files                             | Modify another task’s checkout or the protected baseline      |
| Task-local scratch and test outputs       | Create, read, and update within storage limits                       | Consume unbounded storage or inherit another tenant’s files   |
| Protected acceptance checks and fixtures  | Read permitted fixtures and invoke the designated checking interface | Replace the checks or alter their reported result             |
| Private repository service                | Request authorized fetches through the broker                        | Obtain the service credential or push to an unapproved target |

Table 3: **A scoped repair grant**: Different resources require different rights; authority over one row does not authorize the excluded use in another.

^tbl-vol3-scoped-repair-grant

The grant also has a lifetime and enforced limits on execution and output. It permits the repair to make progress while separating writable candidate artifacts from the machinery used to assess them. Tests keep their writable temporary files; protecting the acceptance checks means protecting their implementation and reported results.

Binding that grant to execution requires resolving the target inside the task’s scope and checking the required right and conditions before any effect takes place, using resource names that cannot be redirected to a different object by symlinks or concurrent renames. Because authority to edit `src/pool.py` says nothing about whether the file’s current contents match the model’s assumptions, the version precondition of **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-conditional-updates|Conditional updates]]** remains a separate check at the moment of the write. The executing code must then be unable to bypass the policy by opening another path, using an inherited handle, or contacting an unrestricted service directly, which can require restricted mounts, process identities, mediated interfaces, or other controls supplied by the envelope. Once the enforcement layer has bound the guest’s accessible resources to the grant, the guest need not attach a token to every system call; what matters is the resulting reach.

On Linux, the supervisor can act as a policy compiler. It verifies the grant, then translates the permitted paths and operations into kernel-enforced rules before it starts the worker. Landlock ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-linux2024landlock|The Linux Kernel Documentation Project 2024b]]), a Linux security module, lets an unprivileged process irreversibly restrict the filesystem hierarchies and network ports it and its descendants can access. A `seccomp-bpf` filter restricts which system calls the process may make and with which scalar arguments. The supervisor installs both, together with restricted mounts and an unprivileged identity, and then calls `execve` on the tool. The worker runs under limits the kernel enforces on every open and connect, without knowing the grant’s format and without being able to remove the rules it inherited. Filtering on system-call numbers cannot inspect the contents of pointer arguments safely,[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn3|³]] which is why path restrictions belong to a mechanism that resolves paths inside the kernel rather than to the system-call filter.

### Narrowing Delegated Authority

^sec-vol3-sandboxes-attenuation

When a repair trajectory delegates a subtask to a helper process or transitions from editing `src/pool.py` to running the test suite, handing over the full parent grant lets the helper modify files outside its subtask. Minting an unchecked child grant, by contrast, risks accidentally adding `execute` or `write` rights the parent never held. **Attenuation** prevents privilege escalation during delegation by deriving a child grant that permits no more than its parent. Writing ${\mathcal{A}}({\Gamma})$ for the accesses allowed by a grant, the relation requires

$$
{\Gamma_{\text{child}}}\sqsubseteq {\Gamma_{\text{parent}}} \quad\Longrightarrow\quad {\mathcal{A}}({\Gamma_{\text{child}}})\subseteq{\mathcal{A}}({\Gamma_{\text{parent}}}).
$$

Narrower object scope, fewer rights, stronger conditions, and an earlier expiry can establish that relation. Consider the repair’s edit grant, issued at time ${T}_0$, and two proposed children. All three carry the same condition ${\phi_{\Gamma}}$, which binds use to this task, so the tuples below list only the components that differ:

$$
\begin{aligned} {\Gamma_{\text{edit}}} &= \big({\mathcal{R}_{\Gamma}}=\{\text{read}, \text{write}\},\ \mathcal{O}_{\Gamma}=\texttt{repo/},\ {t_{\text{exp}}}={T}_0 + 300\,\text{s}\big) \\ {\Gamma_{\text{test}}} &= \big({\mathcal{R}_{\Gamma}}=\{\text{read}, \text{execute}\},\ \mathcal{O}_{\Gamma}=\texttt{repo/},\ {t_{\text{exp}}}={T}_0 + 120\,\text{s}\big) && \text{rejected: execute} \notin {\mathcal{R}_{\Gamma_{\text{edit}}}} \\ {\Gamma_{\text{scan}}} &= \big({\mathcal{R}_{\Gamma}}=\{\text{read}\},\ \mathcal{O}_{\Gamma}=\texttt{repo/src/pool.py},\ {t_{\text{exp}}}={T}_0 + 120\,\text{s}\big) && \text{valid: } {\Gamma_{\text{scan}}} \sqsubseteq {\Gamma_{\text{edit}}} \end{aligned}
$$

The test grant fails even though its lifetime is shorter, because it asks for a right the parent never held. Execution needs an appropriate parent grant or a separately authorized grant from the controller. A runtime that intends to support a test phase therefore includes execute in the grant it issues at the start, or issues a new grant for that phase. It then actively withdraws write authority over the source tree when testing begins, which freezes the candidate being graded. Task-local scratch is a separate object in the grant and stays writable, so the tests keep their temporary files. The read-only mount of the acceptance checks is a second layer beneath the grant. Even a grant such as ${\Gamma_{\text{edit}}}$ that names all of `repo/` cannot write through that mount. Together the two layers keep a candidate from modifying the fixtures and checks that grade it, the property sealed evaluation depends on.

↪ Sealed evaluation criteria held outside the agent’s reach are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-grader-isolation|Grader isolation]]**.

Attenuation can also happen without contacting the issuer. Chained-caveat tokens such as macaroons ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-birgisson2014macaroons|Birgisson et al. 2014]]) let any holder append a restriction and pass on the narrower token. The issuer mints a root token with a message authentication code ${\sigma}_0$ computed under a secret key only it holds. A holder adds caveat ${c}_i$ (a path prefix, a rights subset, a turn limit, an earlier expiry) and replaces the code with a keyed hash (HMAC) of the previous code and the caveat,

$$
{\sigma}_i = \text{HMAC}({\sigma}_{i-1},\, {c}_i). \tag{2}
$$

^eq-vol3-macaroon-chain

The verifier recomputes the chain of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^eq-vol3-macaroon-chain|equation 2]] from its root key and admits a request only if every caveat is satisfied. A holder of the child cannot remove a caveat without the prior code ${\sigma}_{i-1}$, which the chain does not reveal, so a subagent or tool worker can narrow authority offline but cannot widen the token it received.

This relation constrains derived authority; a trajectory can still move from inspection to an authorized edit or test phase under explicit policy. Deriving a read-only child also leaves a broader parent that the same holder retained fully usable. If a phase transition is meant to remove write authority, the runtime withdraws or disables the earlier grant and deals with access already opened under it. Delegation must also preserve aggregate budgets: several children together receive at most the parent’s resource allowance. Both forms of attenuation share this limit ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^fig-vol3-capability-attenuation|figure 3]]). A checked derivation narrows what a child may do but leaves the parent usable, and a chained-caveat token narrows what its next holder may do but cannot reach back to restrict a copy of the token someone already holds.

![[90 Assets/Volume III/08 Sandboxes/Capability Attenuation 465e0d5220.svg]]

Figure 3: **Attenuation and What It Leaves Behind**: Panel A derives two children from the edit grant. The test grant is rejected because it requests execute, which the parent never held, even though its expiry is earlier. The scan grant is valid because every component is narrower. Deriving it does not remove the edit grant, so a worker that retains the parent can still write until the runtime withdraws it. Panel B shows the chained-caveat alternative, in which each holder narrows a token offline by folding a caveat into the next code, and only a verifier holding the issuer’s key can check the whole chain.

^fig-vol3-capability-attenuation

The operative test is therefore which grants and resource handles the worker can still exercise, rather than merely whether the child grant is narrower. This test applies equally to a helper process inside one trajectory and to a subagent that receives a delegated grant, since passing a grant to another agent leaves the meaning of authority unchanged.

### Expiry and Revocation

^sec-vol3-sandboxes-expiry-revocation

Suppose the repair task’s 300-second edit phase expires while a worker process still holds an open writable file descriptor to `src/pool.py`. Rejecting new `open()` calls after ${t_{\text{exp}}}$ stops fresh handles from being created, but the already-open descriptor continues to permit writes unless the runtime closes the handle or stops the worker. An expiry timestamp states when a grant stops authorizing new use; revoking active access requires an enforcement mechanism that checks status on each operation, closes live handles, and terminates or constrains ongoing processes. When the edit phase ends, the transition must therefore stop or constrain the worker, revoke the usable reference where supported, or move subsequent work into a restricted execution context. The runtime must also record what it has actually confirmed rather than equating a changed policy record with completed revocation.

External effects have their own boundary. A broker can stop accepting new requests after expiry, but a previously admitted remote operation may still complete. A lease or cancellation request does not settle that effect or justify a retry. Environment teardown and readiness for reuse receive their full treatment in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|section 8.8.1]]; here the requirement is that authority have an enforced lifetime rather than an advisory timestamp.

↩︎ Why an unsettled remote outcome does not justify a blind retry is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|Retrying Uncertain Actions]]**.

**Checkpoint 8.1: Scope, attenuation, and lifetime**

A repair worker holds read and write access to the candidate source. It derives a read-only grant for `src/pool.py`, retains the original grant, and opens a writable handle before the edit phase expires.

**Derived vs. retained grants**: List every reference through which the worker can still write after deriving the child. Which of them must the runtime withdraw to end write authority?

**Attenuation test**: A proposed child adds test execution and shortens the expiry. Apply the component-wise check of ${\Gamma_{\text{child}}} \sqsubseteq {\Gamma_{\text{parent}}}$ and decide whether it is an attenuation of the edit grant.

**Expiry**: When the edit grant expires, the writable handle and one brokered fetch are still open. Decide what the runtime must do with each before it may record revocation as complete.

**Test-phase grant**: Write the tuple $({\mathcal{R}_{\Gamma}}, \mathcal{O}_{\Gamma}, {\phi_{\Gamma}}, {t_{\text{exp}}})$ for a test phase that keeps writable scratch while the acceptance machinery stays outside the worker’s writable scope.

### Credential Brokering

^sec-vol3-sandboxes-credential-brokering

Scoped file and process grants still leave a placement decision for external service secrets. Placing a private repository token inside the guest’s environment variables or `.netrc` file so the repair worker can run `git fetch` exposes that raw secret to any injected shell command or environment dump that reads process memory or disk. A **credential broker** instead holds the secret outside the guest and uses it on behalf of an authorized request. For example, when the repair worker requests a fetch from its approved private repository through a host-owned source-service adapter, the broker checks the bound task identity, repository, operation, destination, and current grant, then performs the credentialed request without returning the credential. Permission to fetch does not permit a push or access to another repository, so the worker can cause a narrowly authorized use of the credential without possessing the credential itself.

Brokering requires a supported mediation arrangement. An application adapter can make the upstream request directly; a proxy can attach credentials only where it can legitimately inspect and modify the relevant protocol exchange. A signing service likewise needs to authorize what it signs, not merely conceal its key. [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^sec-vol3-sandboxes-egress-enforcement|Section 8.7.1]] develops how the runtime constrains routes that might bypass these interfaces. If a tool genuinely requires a credential inside the guest, a narrowly scoped, short-lived credential shrinks the scope and window of exposure, while the guest still possesses it for that window.

↪ Tracking whether an allowed request’s data may flow to its recipient is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.07 Information-Flow Policy#^sec-vol3-security-taint-tracking|Information-Flow Policy]]**.

Keeping selected credentials outside the guest removes the most valuable target from the README attack, and from the environment dump in the Gemini CLI incident. The environment and repository content remain sensitive, and a brokered operation can still be misused within its permitted scope. Secret placement, access permission, and whether an allowed request’s data may flow to its recipient are three distinct concerns. A sandbox governs the first two, where authority resides and how execution is confined to it. The third is an information-flow problem that a sandbox alone cannot settle. Capabilities and brokering specify the resources the runtime intends to expose, and enforcing those limits in practice requires an execution envelope evaluated by what it shares with the host and which components uphold its boundary.
