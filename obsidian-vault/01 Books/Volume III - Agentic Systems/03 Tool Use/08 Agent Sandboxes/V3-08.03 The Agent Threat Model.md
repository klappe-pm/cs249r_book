# V3-08.03 The Agent Threat Model

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-threat-model

In the repair scenario, a single line planted in `README.md` turns a routine dependency check into an attempt to steal host credentials, while production vulnerabilities in shipped coding assistants demonstrate that sandbox escapes and command-injection failures are active operational risks rather than theoretical curiosities. A rigorous threat model for the repair task must therefore specify which inputs may be hostile, which failure modes the execution boundary must contain, and what resources the task legitimately requires from its environment.

The threat model must also fix how capable the hostile code is, and measured capability has moved quickly. Zhang et al. ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-zhang2024cybench|2024]]) assemble 40 professional-level capture-the-flag tasks, each initialized in an environment where an agent runs commands and observes their output, and score whether the agent identifies the vulnerability and executes the exploit without intermediate hints. [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.03 The Agent Threat Model#^fig-vol3-offensive-capability-trend|Figure 1]] plots the unguided solve rate of each evaluated model against its release date.

![[90 Assets/Volume III/08 Sandboxes/Cell 3 Output 1 264bf06b7f.png]]

Figure 1: **The Code Inside the Boundary Is Getting Better at Exploits**: Fraction of 40 professional capture-the-flag tasks an agent solves without hints, for each evaluated model at its release date. Filled points come from the benchmark’s leaderboard and open points from the developing lab’s own model or system card, so the most recent gains rest on self-reported runs under each lab’s agent configuration. ^fig-vol3-offensive-capability-trend

The best unguided result among models released in 2024 was 17.5 percent; the latest reported result is 93 percent. That trend removes a comfortable assumption from the threat model. Admitted code cannot be treated as merely buggy, because the model proposing it is measured finding and exploiting weaknesses in exactly the kind of environment a sandbox provides. Every interface the guest can reach, from the filesystem and process table to the network stack and the host kernel, is therefore attack surface. Containment must hold against code written by a capable exploit author, even when that code arrives as an ordinary step of the repair.

### Untrusted Input and Execution Reach

^sec-vol3-sandboxes-cohabitation

The planted README payload is an instance of indirect prompt injection, in which attacker-controlled material encountered as task data attempts to redirect model execution ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-greshake2023not|Greshake et al. 2023]]). Language models cannot reliably separate control instructions from untrusted data in their input context, and adversarial evaluation can bound the resulting attack success rate but never certify it as zero. While interface-level mechanisms such as message roles and provenance labels help structure conversational context, they do not enforce operating system protections. The sandbox runtime must maintain strict isolation boundaries even when the model faithfully obeys a hostile instruction. Unsafe proposals also arise routinely without an active adversary; an unintended command-line flag, a misspelled path, or a mistaken target directory produces identical operational damage. A production vulnerability in a commercial coding agent illustrates how quickly text-based admission checks collapse when decoupled from low-level isolation.

↪ Why a language model cannot separate control instructions from untrusted data in its input is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.03 The Adversarial Threat Model#^sec-vol3-security-injection-entry-points|Prompt injection entry points]]**.

↪ Why adversarial testing bounds but cannot zero the attack success rate is developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.10 Adversarial Robustness and Red-Teaming#^sec-vol3-security-adaptive-attack-testing|Adaptive attack testing]]**.

**War Story 8.1: Gemini CLI allow-list bypass (2025)**

**Context**: Google released the Gemini CLI coding agent on June 25, 2025, and on June 27 Tracebit reported that a repository could make it run commands the user never saw ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-cox2025gemini|Cox 2025]]). The CLI asked the user before running a shell command and let the user approve a command such as `grep` for later reuse.

**Mechanism**: The injected instructions sat inside the full text of the GNU General Public License in a repository’s `README.md`, where the model parsed them while a human reviewer was unlikely to notice them. They steered the agent to run an innocuous `grep`, which the user approved, followed by a chained command that began with `grep` and appended `env | curl` targeting a remote server. Because the allow-list check extracted only the root binary name with cursory validation, the chained command matched the approved `grep` rule. A long sequence of whitespace inside the command string pushed the appended payload off-screen in the interactive confirmation prompt.

**Impact**: The proof of concept silently exfiltrated the process’s environment variables, exposing sensitive credentials to the attacker’s server under the full authority of the user’s shell session. Google initially triaged the report at low priority and low severity (P2/S4) and raised both (to P1/S1) on July 23.

**Fix**: Version 0.1.14, released July 25, 2025, displays the complete command string and requires explicit approval for each additional binary invoked. Tracebit also recommended running agentic tools in dedicated sandboxing modes wherever possible.

**Systems lesson**: Textual validation of a command string functions merely as an admission filter at the prompt interface. Once admitted, an executing process is constrained only by the operating system environment hosting it. Because the agent executed directly within the developer’s interactive shell, a single approved command inherited all the authority of the user’s shell session. It could therefore read local environment variables, credentials, and configuration files and open network sockets over the host interface.

Both the Gemini CLI incident and the repository repair scenario combine untrusted content that steers the proposal, sensitive local state the executing code can read, and a channel that can carry that state out. Willison named this conjunction the *lethal trifecta* for agents ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-willison2025lethal|Willison 2025]]), and **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.05 Disclosure Through Permitted Tools#^sec-vol3-security-lethal-trifecta|The lethal trifecta]]** develops it. A sandbox cannot remove the untrusted content, because reading a vendored README is often the task itself, but it can shrink what the code can read and block the routes out. Exfiltration, however, is not the only failure mode. Local source code may itself be proprietary, and destructive workspace corruption or runaway compute loops require no network connectivity at all.

Sandbox design therefore begins by cataloging protected assets alongside legitimate execution requirements. For the code repair task, the runtime must provide a task-local source tree, necessary toolchains, and writable scratch space to execute test suites. It must exclude the developer’s home directory, SSH keys, unrelated repositories, and neighboring tenant files. Permitted external communication, such as package downloads or artifact publishing, requires explicit, scoped endpoints rather than open internet access. These constraints belong in enforced system configuration, not in natural language instructions asking the model to remain within bounds.

**Definition 8.1: Blast radius**

***Blast radius*** is the set of resources and effects reachable by faulty or adversarial execution under a stated threat model and enforcement boundary, including what it can read, change, disclose, or consume.

1.  **Significance**: It connects the task’s intended scope to the concrete filesystem, process, compute, and communication limits the runtime must enforce.
2.  **Distinction**: An authorization grant defines what a task is permitted to do. Blast radius measures the cumulative resources and state running code could compromise or mutate under failure or attack, including misuse within granted permissions.
3.  **Common pitfall**: Estimating execution reach from the high-level tools declared to the model, rather than from the operating system privileges available to the code executing behind them.

A threat model must also delineate which classes of failure it covers. In agent systems, these fall into three tiers. The first is ordinary application errors (such as a faulty test suite exhausting memory). The second is hostile code executing inside the guest environment (such as an injected shell script scanning local network interfaces). The last is compromise of the isolation mechanism itself (such as a kernel privilege escalation or container breakout). An envelope engineered to contain accidental test failures may collapse when confronted with an active kernel exploit. The third tier is why every sandbox design must name its **trusted computing base**: the hardware and software components whose correct operation the isolation depends on, which untrusted code must therefore be unable to modify or subvert. A kernel shared with the guest belongs to it; so does a hypervisor, a policy-enforcing proxy, or the supervisor process that installs the limits. Selecting an execution envelope therefore requires cataloging that base and every physical and operating system resource shared between guest and host.

### Blast Radius by Authority Level

^sec-vol3-sandboxes-blast-radius

How wide a blast radius the sandbox must bound depends on the task’s H·S·A authority level. A read-only (${A}_0$) summarization task needs no file writes to exfiltrate credentials over an open socket. Resetting a local container after a compensable (${A}_2$) or irreversible (${A}_3$) tool call, by contrast, cannot undo a payment already transmitted to an external API. [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.03 The Agent Threat Model#^tbl-vol3-sandboxes-authority-radius|Table 1]] maps each authority level to the exposures the runtime governs and the containment obligations they create.

↩︎ The H·S·A authority levels ${A}_0$ through ${A}_3$ are established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-hsa|The H·S·A Exposure Space]]**.

| Authority level                                                 | Exposure within the granted scope                                                            | Containment and control obligations                                                                                              |
|:----------------------------------------------------------------|:---------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------|
| **${A}_0$ (read access)**                                       | Confidential information can leave through returned observations or another permitted output | Restrict readable resources and destinations; govern what information the return path discloses.                                 |
| **${A}_1$ (mutation confined to a discardable sandbox)**        | Candidate files and task-local artifacts can be damaged; execution also consumes resources   | Confine changes to the designated workspace, enforce resource limits, and prevent mutable state from passing to another tenant.  |
| **${A}_2$ (external action that is retry-safe or compensable)** | Effects reach a system outside the disposable workspace                                      | Scope access to the external operation and enforce its retry or compensation contract; resetting the workspace does not undo it. |
| **${A}_3$ (irreversible external action)**                      | An external consequence may have no adequate reversal                                        | Enforce the required authorization or approval at the effect boundary, without a bypass through sandboxed code.                  |

Table 1: **Authority and execution exposure**: Task authority identifies consequences to govern, not a universal choice of isolation technology. Resource limits and mediated access remain necessary across the levels.

^tbl-vol3-sandboxes-authority-radius

Write protections keep a file intact at ${A}_0$, but only read isolation and network egress policies prevent confidential data from leaving the host. Conversely, at ${A}_2$ and ${A}_3$, actions such as processing a financial payment or updating a remote database land outside the disposable local workspace. Confining the local shell process does nothing to reverse an unintended external transaction once transmitted. Preventing external harms requires gating side effects behind mediation proxies and explicit authorization checks; validating that a command conforms to policy remains distinct from verifying that it aligns with the user’s actual goal.

Containment beneath the model (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-zero-trust-sandboxing|9]]) requires the execution boundary to be enforced outside the code being constrained. An isolation mechanism must be implemented by a layer below the code it controls ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.14 Source References#^ref-saltzer2009|Saltzer and Kaashoek 2009]]). The tool layer required its reference monitor to be tamper-proof, always invoked, and small enough to verify. The sandbox must meet the same three requirements for the code those calls start, and the third is why the trusted computing base named in the threat model should stay small. This is invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) at the execution boundary. Model-side measures lower the probability of an unsafe proposal, but only a mechanism the running code cannot modify bounds what that code can reach.

↩︎ The reference monitor and its three requirements (tamper-proof, always invoked, small enough to verify) are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.03 Tool Subsystem Architecture#^sec-vol3-tool-calling-complete-mediation|Complete mediation]]**.

In the repository scenario, the README text steers two requests through the same boundaries ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.03 The Agent Threat Model#^fig-vol3-threat-model|figure 2]]). The first is the injected `run_shell` command. The second uses a channel the task legitimately holds, because the same README asks the agent to attach source files to the diagnostic report it is permitted to send through a `submit_report` tool. The `run_shell` request is well typed, so tool admission passes it; the filesystem policy then stops it at the read of `~/.aws/credentials`. The destination policy would also refuse its upload, but the two checks guard different things. The read check protects the credential file, and the egress check protects the route out of the host. Neither duplicates the other, so had the credential been readable by some other route, the egress check alone would decide the outcome. The `submit_report` request, carrying private source, passes every gate because each of its steps is allowed, and its disclosure reaches the approved service without any boundary being escaped. Layering boundaries therefore narrows what an attack can do without bounding what a permitted channel can carry, a gap [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^sec-vol3-sandboxes-permitted-disclosure|section 8.7.4]] returns to. Each boundary must also log its decisions, since the absence of an error report is never evidence of safety.

![[90 Assets/Volume III/08 Sandboxes/Defense In Depth Rings 99c736fa6c.svg]]

Figure 2: **Where Each Boundary Acts**: Two requests steered by the same README text cross mediation, the execution envelope, and egress. The injected `run_shell` request is admitted because it is well typed, then stopped where it tries to read the credential. The dashed segment marks that the destination policy would also refuse its upload, a check on a different part of the path rather than an independent backup. The second request passes every check because each of its steps is permitted, so its disclosure reaches the approved service without any boundary being escaped.

Execution boundaries are defined by lifetime as well as resource scope. During a multi-turn repair task, edits to `src/pool.py` and intermediate test artifacts must persist across turns to support iterative debugging, yet that state must never leak into the initial environment of a later tenant or task. Within a turn, test runners need a writable scratch directory while the acceptance test suite itself stays mounted read-only outside the agent’s reach, so the model cannot pass a suite by deleting its assertions. When the task ends, the runtime must stop background child processes, reclaim virtual memory and scratch storage, and reset every state domain covered by the reset contract of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|section 8.8.1]]. A cooperative cancellation request neither forces runaway code to yield nor undoes an external network write that has already committed. Execution reach, the trusted computing base, and boundary lifetime therefore form the three core obligations an agent sandbox must discharge, beginning with where untrusted code runs relative to the software enforcing its limits.
