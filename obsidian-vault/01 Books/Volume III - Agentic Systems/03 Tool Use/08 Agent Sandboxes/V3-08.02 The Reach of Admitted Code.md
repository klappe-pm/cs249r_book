# V3-08.02 The Reach of Admitted Code

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-admitted-reach

Consider an adversarial variant of the connection-pool repair executed by the repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**). While inspecting a vendored dependency to verify how the library is configured, the coding agent reads its `README.md` file. Hidden near the bottom, inside an HTML comment stripped from rendered documentation but visible in raw source, lies a prompt injection addressed to automated assistants. It instructs the agent to upload host environment variables and cloud credentials to an external diagnostics endpoint before running any unit tests. Following these instructions, the model generates a `run_shell` command that reads `~/.aws/credentials` and attempts to transmit the contents over an HTTP socket. The proposed invocation complies with the tool’s parameter schema. A naive agent runtime that checks only whether `run_shell` is an authorized tool admits the call immediately, despite the task granting neither read access to host credentials nor permission to disclose them.

![[90 Assets/Volume III/07 Tool Calling/Hsa Locator A 066dc9f6a5.svg]]

*H·S·A locator with the Authority axis highlighted in purple; Horizon and State axes unlit.*

*Authority bounded beneath the model, limiting what code can change, read, and send.*

The typed action contracts established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-boundary-checks|Structure, permission, and state checks]]** check each proposed invocation’s structure, authority, and state preconditions before dispatch. Static contract validation, however, cannot solve the broader problem for a general-purpose command runner. Once an admitted subprocess begins execution, it can access every file descriptor, network socket, and system resource that the host process environment permits, regardless of what the tool description or prompt claimed. Securing an agent therefore requires sandboxing: projecting the task’s formal boundaries directly into the operating system environment where the admitted code runs.

Designing this execution environment demands balancing strict containment against the operational needs of real software tasks. For the connection-pool repair, the sandbox must provide a mutable workspace for source edits while mounting acceptance test suites as read-only volumes so the agent cannot tamper with evaluation criteria. Because a runaway test loop or fork bomb can exhaust host capacity without touching a forbidden file, the operating system must also cap CPU time, memory allocations, ephemeral storage, and process fork counts. The sandbox must also keep repository credentials off the guest filesystem by routing authenticated requests through external brokers. It must restrict outbound traffic to approved package registries and diagnostic services. Across a multi-turn trajectory, that environment must persist long enough for intermediate edits and compiler artifacts to survive from one step to the next, yet reset deterministically before another task arrives. Every boundary must hold even if the untrusted code gains administrative privileges inside its own environment, the worst case the design assumes. Every isolation mechanism also imposes startup latency and memory overhead that high-throughput agent platforms must provision.

Each of these requirements answers a question the README attack raises. Which inputs are hostile, and which components must stay correct for any limit to hold, is the threat model ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.03 The Agent Threat Model#^sec-vol3-sandboxes-threat-model|section 8.2]]). Why the limit cannot live inside the supervisor’s own interpreter, where pruned names leave reachable objects, native libraries, and inherited authority in place, comes next ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.04 Limits of In-Process Restriction#^sec-vol3-sandboxes-in-process-failure|section 8.3]]). What the code should hold instead is a capability scoped to the task, with credentials kept outside the guest (the code running inside the boundary, together with the environment it sees) by a broker ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^sec-vol3-sandboxes-least-privilege|section 8.4]]). An execution envelope, the enforced boundary around running code, imposes that scope. Which envelope fits among shared-kernel containers, user-space kernels, microVMs, and bytecode runtimes depends on the workload’s system calls, authority, and horizon ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^sec-vol3-sandboxes-microvms|section 8.5]]). The remaining sections give the envelope a workspace that persists across turns without leaking between tenants ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.07 The Agent Workspace#^sec-vol3-sandboxes-cow|section 8.6]]) and close the outbound channels a confined process can still use ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^sec-vol3-sandboxes-network|section 8.7]]). They then price the whole arrangement as a pool of environments that must be reset before reuse and sized for bursts of arrivals ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling|section 8.8]]).
