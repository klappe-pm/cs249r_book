# V3-08.10 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-fallacies

Robust containment requires both a sound enforcement boundary and sufficient host capacity to sustain that boundary under load. When deploying agent sandboxes, engineering teams often confuse practical filtering heuristics with architectural guarantees, or mistake microbenchmark startup latencies for the true operational cost of isolation.

**Fallacy**: *Removing dangerous names removes the process’s authority.*

Stripping dangerous symbols from an execution namespace hides convenient entry points, but it leaves the underlying runtime authority intact ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.04 Limits of In-Process Restriction#^sec-vol3-sandboxes-in-process-failure|section 8.3]]). Reachable object graphs, open file descriptors, and native extensions remain within the interpreter’s shared address space. For example, a caller can traverse an ordinary reference like `total.__globals__` to retrieve the supervisor’s unredacted module namespace from an allowed helper function. Rice’s theorem rules out a sound and complete semantic classifier for unrestricted programs; it does not cause this reachable-reference escape or prohibit conservative safe subsets. While a specialized, deliberately restricted language can enforce safety invariants through its own formal semantics, executing untrusted code inside the supervisor’s process forces both into a single failure domain. True containment and resource limits must be enforced by the host operating system outside that interpreter process.

**Pitfall**: *Choosing an envelope from a platform label alone.*

Architectural labels like “container” or “microVM” specify virtualization mechanisms, not actual security boundaries ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^sec-vol3-sandboxes-microvms|section 8.5]]). While a container shares the host kernel and a microVM interposes a guest kernel beneath a hypervisor monitor, the true blast radius depends on how the runtime environment is configured: filesystem mounts, virtualized devices, egress network routes, control groups, and trusted helper daemons. The same user-space kernel changed its trusted file-access path between releases without changing its name ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.06 Choosing an Isolation Envelope#^sec-vol3-sandboxes-gvisor-vs-microvm|section 8.5.1]]), and a microVM given a writable host mount or an unfiltered network route exposes exactly what its label suggests it hides. Systems engineers must evaluate the complete execution configuration against specific threat models and operational workloads. Lower startup latency indicates a lighter initialization path, not stronger isolation.

**Fallacy**: *The cost of strong isolation is its startup latency.*

Snapshot restoration reduces guest startup overhead to milliseconds, 15 ms in the chapter’s illustrative profile. However, boot latency is rarely the dominant infrastructure expense. The primary cost of sandboxing stems from cumulative memory residency across the lease horizon. At an arrival rate of 2 trajectories per second and lease durations of 300 s, the pool averages 600 active leases. Even with copy-on-write page sharing, mean active guest pages plus the configured reserve occupy roughly 39.0 GB, compared to the 322.1 GB required by isolated private images (Notebook [8.3](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#nbk-08-reserve-from-arrival-rate)). Sandbox provisioning must be budgeted by memory-seconds per trajectory, a quantity that scales directly with the lease hold time ${T_{\text{hold}}}$, rather than evaluated solely by boot time.

**Pitfall**: *Treating an allowed destination as approval of everything sent there.*

A network egress rule restricts traffic to approved remote endpoints, but it cannot verify whether the payload in a request body is safe ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^tbl-vol3-egress-filtering|table 6]]). Credential brokering keeps long-lived tokens and secret keys outside the guest environment while still allowing sandboxed code to request operations against authorized services. Under this design, an agent can use an approved outbound channel to exfiltrate private task data or modify remote state without ever extracting a credential or escaping the sandbox envelope. Preventing this residual abuse is an information-flow and semantic authorization challenge, rather than a perimeter-bypass flaw in the network sandbox.

**Fallacy**: *An empty workspace proves that a used envelope is ready for another tenant.*

Files represent only one of the four state domains cataloged in [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^tbl-vol3-reset-architectures|table 7]]. Even if a cleanup script successfully wipes every file, lingering processes from double-forked daemons, abstract Unix domain sockets, kernel keyring credentials, or modified environment search paths continue persisting. Any leftover artifact across these state domains compromises the next tenant. Multi-tenant recycling demands an explicit reset contract that accounts for every state domain an incoming lease could inspect, destroys or reinitializes that state to a known golden baseline, and validates isolation before reassignment. Moreover, no local cleanup protocol can undo external side effects already committed to remote APIs during the lease.

**Pitfall**: *Sizing the standby reserve from a restore time measured on an idle host.*

Determining standby pool capacity from initialization benchmarks gathered on an unloaded system severely underestimates provisioning requirements. Reserve sizing is governed by the traffic intensity parameter ${\lambda_{\text{arr}}} {T_{\text{init}}}$, where the request-level miss probability under the stated replenishment policy follows a steep Poisson tail. In the chapter’s illustrative profile, the selected reserve of 2 instances satisfies a 0.1 percent request-level miss objective only as long as snapshot restore completes in under 22 ms. If initialization degrades by a factor of 10×, as an unoptimized cold boot can, the required reserve jumps to 4 instances. Under burst traffic, concurrent VM restoration, host cache contention, and lazy demand paging across copy-on-write regions degrade ${T_{\text{init}}}$ precisely when capacity is most critical. Sizing calculations must measure initialization latency under the target concurrency of the anticipated burst rather than in quiescent conditions (Notebook [8.4](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#nbk-08-sizing-a-pre-warmed-microvm-pool)).
