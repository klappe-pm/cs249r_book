# V3-08.08 Egress Control

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes|V3-08 Agent Sandboxes]]

^sec-vol3-sandboxes-network

Consider the threat model where credential brokering is in place. An untrusted script triggered by an injected README cannot read the host’s authentication token from guest memory, yet it still holds legitimate read access to the local source files it was asked to repair. If that script opens an outbound socket and sends the repository contents to an unapproved server, proprietary source code leaks without the attacker ever breaking the hypervisor boundary or stealing a cryptographic key. **Egress control** governs the communication channels leading outward from the sandbox, enforcing outbound limits on the host’s physical and virtual network path rather than trusting guest processes or client settings to cooperate.

### Enforcement Outside the Guest

^sec-vol3-sandboxes-egress-enforcement

Setting `HTTP_PROXY` or `HTTPS_PROXY` inside the guest environment does nothing to stop an injected script that ignores environment variables, opens a raw socket to an external IP address, or tunnels data out over UDP. When a task evaluates self-contained code, runs local unit tests, or analyzes a static dataset, the cleanest defense is to give the sandbox no outbound network interface at all, leaving only a loopback device inside an isolated network namespace. Tasks that must pull packages, fetch remote Git commits, or report telemetry instead need a tightly scoped path through a host-owned service adapter or egress gateway. Host virtualization primitives such as Linux network namespaces, virtual Ethernet pairs, and `nftables` or eBPF cgroup filters block every other route outside the guest’s control boundary.

A complete network boundary covers direct IPv4 and IPv6 sockets, recursive DNS lookups, and host services reachable across local virtual bridges by combining two enforcement layers outside the guest. At the transport and network layer, a packet filter checks IP addresses and port numbers, admitting traffic only toward the designated mediator and dropping direct connections to raw IP literals or outside resolvers. At the application layer, the mediator inspects the protocol, service path, and operation. Testing this setup requires verifying that attempted bypasses, such as direct socket connections and unbrokered DNS queries, are dropped, not merely that cooperative HTTP clients work. Each layer covers the other’s blind spot ([[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^fig-vol3-network-egress|figure 6]]): the packet filter cannot distinguish a repository fetch from a push to the same IP address, while the application mediator never sees a raw socket connection that the packet filter has already dropped.

![[90 Assets/Volume III/08 Sandboxes/Network Egress Defense In Depth e42214369a.svg]]

Figure 6: **Two Enforcement Points Outside the Guest**: The packet filter sees only addresses and ports, so it admits connections to the mediator and drops a direct socket or a lookup sent toward an outside resolver, whatever name the program had in mind. The mediator interprets the request. It resolves its own fixed destinations, admits the repository fetch, and adds the brokered credential, while a push or a request for another repository fails the operation grant at the same hostname. A mediator can inspect or change methods, paths, and bodies only if it makes the upstream request itself or terminates TLS; a proxy that merely forwards encrypted traffic cannot.

^fig-vol3-network-egress

### Destination, Operation, and Data Scopes

^sec-vol3-sandboxes-egress-scopes

Allowing an agent to reach a hostname is far coarser than allowing only the operation the task needs. A single code-hosting endpoint serves read-only repository clones, branch pushes, pull-request comments, and public release uploads under the same HTTPS address. Permitting the hostname `github.com` or an internal Git server without inspecting the request therefore lets an agent push commits or post private source files to a public issue thread. As [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^tbl-vol3-egress-filtering|table 6]] shows, an egress policy must separate three questions: which destination endpoint the task may contact, which operation and resource it may touch there, and which data may travel in the request.

| Policy scope           | Question                                                              | What the restriction does not establish                     |
|:-----------------------|:----------------------------------------------------------------------|:------------------------------------------------------------|
| Destination            | Which service and network endpoint may this task reach?               | Every operation offered by that service is permitted.       |
| Operation and resource | Which action may it perform on which repository, object, or endpoint? | Every submitted field or body is appropriate to disclose.   |
| Submitted data         | Which information may leave through the allowed operation?            | A scanner can recognize every sensitive encoding or misuse. |

Table 6: **Three scopes of egress policy**: Destination restrictions, operation grants, and disclosure decisions constrain different aspects of an outbound request.

^tbl-vol3-egress-filtering

A host-owned service adapter enforces the first two scopes by mediating the API directly. When an agent asks to fetch a repository, the adapter checks the task’s identity, verifies that the target repository matches the task grant, and confirms that the requested operation is read-only before attaching the upstream credential on the host. The guest receives the fetched objects without ever seeing the token, while a request to push commits or read another repository on the same hostname is rejected at the adapter. The adapter must also validate query parameters and request fields so that a script cannot smuggle sensitive data out inside the URL parameters of a permitted `GET` request.

A standard HTTP forward proxy sees much less. When a proxy handles HTTPS traffic through an HTTP `CONNECT` tunnel, it relays an encrypted byte stream between the guest and the remote server. It sees only the initial target host and the Server Name Indication (SNI) header and remains blind to HTTP methods, URL paths, headers, and bodies. Enforcing operation- or payload-level rules through a proxy therefore requires terminating TLS at the gateway, decrypting and checking the request, and opening a separate upstream TLS connection. Because TLS interception requires installing a private root certificate authority inside the guest, which tools with pinned certificates or custom trust stores will reject, host-owned service adapters are more reliable when an operation grant must inspect the request.

### Name Resolution and Local Destinations

^sec-vol3-sandboxes-name-resolution

Inspecting the request at the gateway still fails if name resolution or routing can redirect an approved hostname to an internal target. If an egress gateway checks a hostname by resolving it once and then lets the guest open its own connection, an attacker-controlled DNS server can return an approved public IP address for the policy check. It can then switch the answer to `127.0.0.1` or an internal service address when the guest connects. To close this DNS rebinding window, the mediator must bind its approval to the exact IP address used for the connection and check every enabled address family including IPv6. It must also re-evaluate every HTTP redirect (`301` or `302`) before following it, so a public URL cannot redirect the request onto an internal host.

Host-local interfaces, private subnets (such as RFC 1918 ranges), and link-local addresses are the first targets of such redirects and direct probes. On cloud hosts, instances query the link-local metadata address `169.254.169.254` to fetch short-lived IAM credentials, hypervisor configuration, and bootstrap tokens without prior authentication. If packet filters block only public internet ranges and leave link-local or bridge addresses reachable, code inside the sandbox can read the host’s cloud role credentials in a single HTTP request. A network sandbox must therefore drop traffic to loopback, private, and link-local ranges by default and open only explicit host adapter endpoints.

Even when all direct TCP and UDP connections to the internet are blocked, an unrestricted recursive DNS resolver gives the guest an outbound data channel.[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.15 Footnotes#^fn8|⁸]] A script inside the sandbox can hex- or base32-encode a secret into subdomain labels such as `deadbeef.attacker.example` and ask the recursive resolver to look the name up. The resolver then forwards that query to the attacker’s authoritative nameserver, delivering the secret across the perimeter. Rather than exposing a general recursive resolver to the guest, the runtime should resolve names inside the host adapter against a fixed allowlist of exact hostnames, never broad wildcard domains, which leave subdomain labels open for signaling. It should also pair any dynamic lookup path with rate limits and query logging.

### Disclosure Through Permitted Channels

^sec-vol3-sandboxes-permitted-disclosure

Even when packet filters, service adapters, destination allowlists, and operation grants all work as designed, sensitive data can still leave through a payload the task is allowed to send. The `submit_report` request of [[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.03 The Agent Threat Model#^fig-vol3-threat-model|figure 2]] contacts only the approved endpoint and calls only the permitted operation. Yet the injected instruction has tucked proprietary source code into the report body, so every sandbox boundary holds while the payload leaks data beyond the task’s scope. At the mediator, the runtime can narrow that channel by enforcing strict schemas that replace free-form text fields with typed key-value pairs and by capping request body sizes to stop bulk dumps. It can also scan outbound buffers for high-entropy strings, keys, and known token formats before forwarding the request. Pattern and entropy scanners remain heuristic, however, because paraphrased source code, compressed snippets, or custom encodings pass signature checks cleanly. Deciding whether data derived from a private file may flow into a permitted outbound call at all is an information-flow question, which **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.05 Disclosure Through Permitted Tools#^sec-vol3-security-exfiltration|Disclosure Through Permitted Tools]]** develops for permitted tools.

Outbound network state also ends with the task lease. When a lease expires, the runtime must revoke its network identity and broker tokens at once, close active TCP connections, tear down virtual network interfaces, drop keep-alive sockets, and cancel in-flight brokered requests. Because a packet that has already left the host cannot be recalled by rolling back local disk state, preparing an execution environment for another tenant requires tearing down network and broker sessions alongside resetting compute and storage.
