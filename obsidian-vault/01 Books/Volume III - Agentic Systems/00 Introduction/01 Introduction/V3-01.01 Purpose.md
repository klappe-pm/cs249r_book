*Agentic Machine Learning Systems Stack*

*Agent stack focus for this chapter.*

*Why can a model that generates a fluent, correct action still fail to complete an autonomous task?*

The difference between answering a prompt and completing a delegated task marks the boundary of agentic machine learning systems. A foundation model can propose the exact line of code needed to fix a race condition, yet the repository remains broken until software inspects the source tree, applies the patch, runs regression tests, and verifies the outcome. Delegating autonomous work therefore requires building an engineered machine around the model, not merely selecting capable weights. That machine resembles a complete computer, with components that compute, remember, act on the external world, supervise execution, recover from faults, and learn from experience. However, its central processing element differs fundamentally from any classical processor: it is an autoregressive model whose outputs are stochastic proposals rather than deterministic execution. A fluent proposal can be subtly wrong, and the model cannot vouch for its own correctness. The surrounding system exists to contain that reality. The runtime determines what data the model perceives, bounds the actions it may execute, persists critical state across interruptions, and verifies whether the task actually succeeded. Every decision consumes computational time and monetary budget that only accepted outcomes justify. Building an agentic system is thus an exercise in systems engineering: sizing the runtime machinery to the horizon, state, and authority that the task demands.

**Learning Objectives**

- Trace the architectural evolution from predictive and generative machine learning to autonomous agentic systems
- Explain why a model’s stochastic proposals require an external runtime to close the interaction loop, and trace one turn through the runtime’s six phases
- Analyze which isolated-request assumptions a multi-turn trajectory breaks, and why the runtime accounts for cost, state, and authority per trajectory
- Classify a delegated task by horizon, state, and authority to identify its systems engineering obligations
- Distinguish mechanically enforced sandbox bounds from the external evidence that catches plausible but wrong results before task acceptance
- Calculate unchecked task reliability and cost per accepted task across multi-turn horizons, and use them to decide between a fixed workflow and a model-directed loop
- Specify a five-part task contract that separates goal, environment, permitted actions, observations, and completion criteria
