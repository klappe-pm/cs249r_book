# V3-01.09 Book Organization

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01 Introduction|V3-01 Introduction]]

^sec-vol3-intro-book-organization

Improving a model’s proposals does not grant it permission to run a shell command, and sandboxing a tool call does not stop a fifty-turn trajectory from drifting off course or losing its state on a crash. Because none of the layers of the stochastic computer map ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.04 The Stochastic Computer#^fig-vol3-stochastic-computer-map|figure 3]]) can do another layer’s job, the parts of this book follow those layers in dependency order. Each part builds on the guarantees beneath it and closes one exposure before the pieces assemble into a complete runtime.

### The Causal Order of the Parts

^sec-vol3-intro-causal-spine

That dependency order starts with a single model call, because every later guarantee depends on what one invocation reads, returns, and costs. Once the runtime chains calls across turns, it must first bound the growing state in context and memory, then contain the authority of tool calls, and finally supervise the multi-turn horizon across crashes, retries, and evaluation. Only after the runtime produces verified records of what happened can an engineering team train on those trajectories or scale across multiple agents. [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.09 Book Organization#^tbl-causal-spine|Table 4]] maps this dependency chain onto the seven parts of the book.

| Part                                   | Governing Problem                                                                      | New Capability                                                                                | Exposure Addressed                        |
|:---------------------------------------|:---------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------|:------------------------------------------|
| **Part I: The Model**                  | A fallible model proposal consumes time and resources.                                 | Interpret the call contract and decide when additional inference is worthwhile.               | Origin, then horizon within one decision  |
| **Part II: Agent Memory**              | Growing histories compete for limited context and can contain stale information.       | Manage the next call’s context, its serving state, and information retained across tasks.     | State                                     |
| **Part III: Tool Use**                 | Proposed actions need permission, containment, and protection against untrusted input. | Define tool interactions, bound execution, and constrain misuse of legitimate access.         | Authority                                 |
| **Part IV: The Agent Runtime**         | A sequence of permitted actions can still stall, lose state, or fail its task.         | Supervise execution, survive interruption, recover from failures, evaluate, and release.      | Horizon                                   |
| **Part V: Learning from Trajectories** | Execution records do not automatically constitute suitable learning data.              | Curate trajectories, teach demonstrated behavior, and improve policies using outcome rewards. | None; changes the model, not the exposure |
| **Part VI: Agents at Scale**           | Delegation and concurrency introduce coordination costs and shared resource limits.    | Compare multi-agent designs and provision resources per accepted task.                        | All three, multiplied                     |
| **Part VII: Synthesis**                | Component-level guarantees leave obligations at their interfaces.                      | Follow an incident-remediation task through the system and justify its acceptance.            | All three, together                       |

Table 4: **Causal Dependency Spine**: Each part develops capabilities that the later parts use to govern, evaluate, improve, and scale complete trajectories. The last column names the H·S·A exposure each part addresses.

^tbl-causal-spine

Within the parts, the chapters follow the same causal order. In Part I, **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model#^sec-vol3-foundation-model|The Foundation Model]]** fixes the contract around a single model call (what a request supplies, how a response reports completion, and what its input and output cost). **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03 Test-Time Compute#^sec-vol3-test-time-compute|Test-Time Compute]]** decides when another token, candidate, check, or call is worth its price. Part II addresses state. **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering#^sec-vol3-context-engineering|Context Engineering]]** selects the working set each call receives. **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management#^sec-vol3-kv-cache|KV Cache Management]]** prices the attention state that context leaves in accelerator memory and decides whether to keep, move, or drop it while an agent waits on a tool. **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/06 Long-Term Memory/V3-06 Long-Term Memory#^sec-vol3-long-term-memory|Long-Term Memory]]** keeps knowledge across sessions as claims that carry their provenance. Part III addresses authority. **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling#^sec-vol3-tool-calling|Tool Calling]]** places the runtime between a proposed call and its effect; **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes#^sec-vol3-sandboxes|Agent Sandboxes]]** enforces the task’s limits beneath the executing code; and **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09 Agent Security#^sec-vol3-security|Agent Security]]** defends against inputs that turn legitimate permissions toward an attacker’s ends.

Part IV builds the runtime that governs the horizon. **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness#^sec-vol3-agent-harness|The Agent Harness]]** keeps the decision to continue outside the model, driving the loop under budgets and approval gates. **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution#^sec-vol3-durable-execution|Durable Execution]]** records each intended action before dispatching it, so that a successor can resume after a crash without repeating an effect unsafely. Because restoring a snapshot does not undo an effect on an external system, **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12 Failure Recovery#^sec-vol3-failure-recovery|Failure Recovery]]** decides among retry, repair, compensation, and escalation by the cost still ahead, and halts trajectories that make no progress. **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13 Agent Evaluation#^sec-vol3-evaluation|Agent Evaluation]]** establishes what evidence supports a claim about a configuration, and **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14 Operating Agents#^sec-vol3-operations|Operating Agents]]** carries that evidence into live work through traces, postmortems, and staged releases.

Part V changes the model without expanding its exposure. **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15 Trajectory Curation#^sec-vol3-trajectory-curation|Trajectory Curation]]** decides whether a failure belongs in the weights at all and which records serve which learner. **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16 Trajectory Fine-Tuning#^sec-vol3-fine-tuning|Trajectory Fine-Tuning]]** trains on the responses curation selects and releases an update only when closed-loop acceptance improves. **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17 Reinforcement Learning from Verifiable Rewards#^sec-vol3-rlvr|Reinforcement Learning from Verifiable Rewards]]** replaces demonstrations with a programmatic check and defends that check against an optimizer that searches it for gaps. Part VI examines how scale multiplies all three exposures. **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination#^sec-vol3-multi-agent|Multi-Agent Coordination]]** asks when splitting a task across workers beats a single controller with the same tools and budget, and **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19 Agent Economics#^sec-vol3-agent-economics|Agent Economics]]** measures cost per accepted task over a cohort and prices each lever the runtime controls against it. Finally, **[[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20 Conclusion#^sec-vol3-conclusion|Conclusion]]** follows one incident remediation, a configuration rollback whose acknowledgment never arrives, across every boundary the book builds.

Each part opens with the systems principles it develops. Each principle is stated formally where it first appears and cited wherever later components depend on its guarantees, beginning with the invariant closure principle ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]).

↪ The full table of foundational systems principles, with each principle’s core statement and what it predicts, is developed in **[[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.03 The Principles of the Book#^sec-vol3-conclusion-principle-table|The Principles of the Book]]**.

The same ordering of parts also gives a practical order for fixing production failures, because the parts run from changes in what the model reads to changes in the model’s weights. Changing what a model sees in its context is cheap, fast, and easy to roll back. Retraining or fine-tuning model weights is the most expensive and least reversible fix, and it risks hurting performance on tasks the failure never touched. Fixes to schema constraints, tool interfaces, and runtime checks sit between those two ends, ordered by cost and reversibility. That sequence is a sensible default rather than a rigid ladder that every incident must climb step by step.

↪ The intervention ladder, which orders remedies from context assembly through tool schemas and runtime controls to fine-tuning and reinforcement learning by cost and reversibility, is developed in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.03 Capability Gap Diagnosis#^sec-vol3-flywheel-intervention-order|The intervention ladder]]**.

This dependency order is also why evaluation comes before offline learning in this book. A trace can record an action that was allowed and ran cleanly yet failed to advance the task; conversely, an accepted run often contains an earlier failed attempt that showed the agent how to recover. Offline learning methods need those distinctions so they train on genuine recovery rather than brittle luck. For the same reason, multi-agent coordination comes only after a complete single-agent runtime is in place: teams should compare the coordination cost, latency, and variance of multiple agents against a well-engineered single-agent baseline rather than a fragile while-loop.

This sequence is a teaching order rather than a mandate to deploy every mechanism on every workload. A production system needs only the safeguards its exposures demand, and a bounded, read-only query needs far less machinery than an agent authorized to modify live database clusters. The conclusion applies the full framework to the remediation agent (lighthouse [1.3](https://mlsysbook.ai/vol3/01_introduction/01_introduction.html#lhs-vol3-remediation-agent)), from an automated latency alert through an operator-approved configuration rollback to verified recovery.

### Reading Paths by Role

^sec-vol3-intro-pedagogical-paths

An infrastructure engineer sizing KV-cache pools, a platform engineer writing tool schemas, and a post-training researcher curating trajectories all touch different parts of an agent stack, yet a failure in one layer routinely shows up as a symptom in another. To keep those cross-layer dependencies clear without forcing every reader to know accelerator microarchitecture in advance, the main sequence assumes familiarity with foundation-model prompting, autoregressive token generation, systems programming, processes, virtual memory, file systems, networking, remote procedure calls, and basic probability. Beyond those basics, the book is self-contained: agent-specific concepts are defined where they first appear, and the appendices hold the serving-cost and mathematical derivations.

↪ Serving cost derivations for model invocations are developed in **[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^sec-vol3-appendix-inference|Inference Cost Foundations]]**.

Readers with a specific role can weight their focus while keeping this dependency order intact. Infrastructure engineers will lean on model serving contracts, KV-cache memory management, sandboxed execution, durability guarantees, and fleet economics. Platform and application engineers will focus on context engineering, tool interfaces, security containment, the agent harness, failure recovery, and evaluation benchmarks. Post-training researchers will concentrate on test-time compute, trajectory curation, fine-tuning, and reinforcement learning from verifiable rewards. Every path starts with the task model in this chapter and finishes with the end-to-end trajectory in the conclusion.

### The Book’s Three Questions

^sec-vol3-intro-questions

Without a shared cost metric, teams add autonomous loops where a fixed script would win. Without an exposure model, they overbuild sandboxes for read-only tasks or under-protect production databases. Without independent checks, they mistake a fluent completion message for a finished job. Every chapter that follows therefore answers three questions:

1.  **When does a model-directed loop justify its cost over a fixed workflow?** *Cost per accepted task* decides this trade-off. Each chapter develops mechanisms that either raise the probability of acceptance or cut the spend on failed attempts.
2.  **What runtime machinery must surround the model?** The H·S·A exposure space sizes it. Parts II through IV build the mechanisms that manage context across memory tiers, bound delegated authority against untrusted input, and supervise long horizons.
3.  **How do operators know that an autonomous task actually succeeded?** *Invariant closure* governs the answer. A model’s fluent self-report cannot replace external checks; acceptance rests on evidence gathered independently from the environment and judged against a contract adopted before the work begins.

↪ Answers to the three questions, tested with the complete architecture assembled, are developed in **[[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.02 Answers to the Three Questions#^sec-vol3-conclusion-questions|Answers to the Three Questions]]**.
