# V3-01.06 Invariant Closure

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01 Introduction|V3-01 Introduction]]

^sec-vol3-intro-governance

Each axis of the H·S·A space names a way an autonomous run can fail: an agent with write authority can touch the wrong resource, carried state can accumulate silent corruption, and a multi-turn trajectory can end with a fluent claim that the job is done while the defect remains live. Because the model cannot vouch for the safety or correctness of its own outputs, the surrounding runtime must close those exposures from outside the model. Doing so requires understanding the fault pattern characteristic of generative models, enforcing mechanical bounds and empirical checks on either side of the model, and writing both into an explicit task contract before execution begins.

### The Fail-Plausible Fault

^sec-vol3-intro-fail-plausible

In an autonomous repository repair loop, an agent can finish its run with a confident, well-reasoned summary declaring that a race condition is fixed, even though the underlying defect remains. The generated patch may be syntactically clean yet remove thread safety by deleting a synchronization lock, or the test suite may exit with return code zero only because the model commented out the failing assertions. Both failures are instances of the **fail-plausible fault**, in which the output looks well formed and credible while the required property remains unsatisfied.[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn6|⁶]]

Classical fault models show why this failure pattern needs its own category. In distributed systems, a *fail-stop* component halts when it faults, so a supervisor can detect the failure through missing heartbeats or nonzero exit codes ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.14 Source References#^ref-schlichting1983failstop|Schlichting and Schneider 1983]]). A *Byzantine* component may behave arbitrarily or deceptively, but Byzantine fault-tolerant agreement uses redundancy under a stated bound on the number of faulty replicas ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.14 Source References#^ref-lamport1982byzantine|Lamport et al. 1982]]).[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn7|⁷]] A plausible wrong answer evades both crash monitoring and agreement among model samples. Because the model process neither crashes nor halts, fail-stop monitors record a normal return. Sampling repeatedly from the same foundation model sets no bound on how many samples are wrong, because shared blind spots can make the samples agree on an incorrect answer. The fail-plausible fault is therefore an unsignaled semantic failure that looks like success on the surface.

![[90 Assets/Volume III/01 Introduction/Fault Models Margin 7baa81d456.svg]]

*Three stacked cards. Fail-stop: halts, so it is detected. Byzantine: bounded, so it is outvoted. Fail-plausible, highlighted in red: looks like success.*

*Crash detection and agreement leave plausible wrong answers needing an outside check.*

To keep fail-plausible faults from corrupting system state, the execution environment enforces **zero ambient authority**: the model holds no standing privileges of its own, and every external side effect must pass through an explicit grant checked by the runtime.[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn8|⁸]] Generated tokens cannot authorize commands, alter the runtime’s execution records, or declare acceptance. Instead, the runtime gathers environmental evidence strictly through designated tools and deterministic checks. For repository repair, this means separating the raw patch text the model proposed from the diff the runtime actually applied on disk (the two differ whenever a patch fails to apply cleanly). It also means keeping model-written summaries of test runs separate from actual process exit codes.

Every external check establishes a bounded claim that is narrower than the overall task goal. A clean compile shows only that the program obeys grammar and type rules under one build configuration. A passing regression test records only that the code ran cleanly for the inputs and thread schedules tested. As Dijkstra observed, testing can show the presence of defects, but never prove their absence ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.14 Source References#^ref-dijkstra1970structured|Dijkstra 1970]]).

### The Invariant Closure Principle

^sec-vol3-intro-invariant-closure

Containing fail-plausible faults therefore joins two distinct guarantees that the working-copy comparison in example [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^exmp-01-hsa-incident|1.1]] already separated: zero ambient authority prevents unauthorized actions, while external checks test whether an allowed action met the engineering goal. A filesystem boundary mechanically blocks writes outside the assigned workspace, whereas checking whether a patch inside that workspace repairs a race condition requires empirical evidence of how the program behaves. **Invariant closure** assigns both jobs to explicit mechanisms around the model rather than trusting the model’s own assurances. Limits are enforced mechanically below the model, and acceptance rests on evidence gathered above it. The principle below measures both against the task contract, the explicit specification of what may execute and what counts as done, which [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-five-part-contract|section 1.5.3]] defines. It also states the cost of leaving steps unchecked in terms of a per-step error rate ${\epsilon}$, a result that [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^sec-vol3-intro-horizon-arithmetic|section 1.6]] derives.

**Principle 1: Invariant closure**

**Invariant**: Constraints never rest on the model; bounds close mechanically below it, acceptance on evidence above it. Each enforced bound names the property and assumptions under which it holds, and each acceptance decision names the evidence standard it applies. Without either, a trajectory of ${H}$ independent steps, each correct with probability $1-{\epsilon}$, succeeds only with probability

$$
\Pr(\text{success}) = (1-{\epsilon})^{{H}}
$$

 while an enforced bound rejects the violations it blocks, and a check rejects those it detects.

**Implication**: Under the independent-step model without recovery, unchecked reliability decays exponentially with horizon; raising step accuracy does not remove the need for runtime bounds and checks. The runtime mediates permitted effects and resource use independently of the model’s compliance. It accepts completion only when evidence meets the task contract, preserving the distinction between a passing check and a guarantee beyond that check’s coverage. The contract itself is adopted by authorized people: the model can draft it but cannot adopt, relax, or certify against it. Greater operational exposure requires stronger justification for both the boundaries and the evidence.

^pri-invariant-closure

Mechanical enforcement sets concrete execution boundaries. A filesystem restriction blocks writes to protected paths as long as all file operations pass through the enforcement layer and its isolation assumptions hold. That boundary controls where edits land, while leaving the correctness of those edits as a separate question. Likewise, schema validation checks that a tool request is syntactically well formed, while authorization remains a separate check. The design rule is to keep each enforced property narrower than the full task claim and state explicitly what guarantee it provides.

Acceptance decisions rely on evidence organized across distinct **closure evidence levels**. The classical end-to-end argument explains why the levels differ ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.14 Source References#^ref-saltzer1984endtoend|Saltzer et al. 1984]]). An end-to-end task property can be checked only by an endpoint that knows the full task requirements, so correct behavior at a lower layer, such as generating well-typed code, cannot establish end-to-end correctness. Ordered from the weakest default grounding to the strongest, the five levels are:

1.  **Self-report**: The agent’s own account is an unverified claim rather than an observation of the environment.
2.  **Static analysis**: Analysis checks structural and type invariants without running the code.
3.  **Visible tests**: Tests run cases that the agent can inspect directly. They help during iterative diagnosis, but they expose test cases that candidate solutions can overfit.
4.  **Sealed tests**: Tests withhold their definitions from the agent and run inside tamper-proof sandboxes, protecting the evaluation from modification.
5.  **Formal verification**: A proof establishes that an implementation satisfies an explicit mathematical model, though confirming that the specification captures what the user actually wanted remains a human judgment.

The ordering is a default rather than an absolute ranking, because a level’s strength also depends on how complete its tests or its specification are. A thorough sealed test suite gives more practical confidence than a mathematical proof built on an incomplete specification.

In the race-condition repair, passing a sequential unit test gives evidence only for single-threaded execution. Sealing that test protects its assertions from modification, but does not widen its coverage. Showing that the concurrency bug is fixed requires running multi-threaded stress workloads that force thread interleavings across varied schedules. Human code review then checks operational assumptions that the test harness cannot probe. Because an automated verdict can be completely repeatable yet miss whole classes of inputs, acceptance claims must stay within what the test suite actually measured.

Some completion criteria cannot be reduced to executable boolean checks and require qualitative evaluation. An automated or human evaluator scores these outcomes against an explicit rubric, recording who owns the decision and what uncertainty remains while mechanical permission bounds stay in force. When the evidence falls short of the task contract, the runtime reports an unresolved outcome or escalates to human operators rather than treating a plausible narrative as verified completion.

Even executable verifiers differ in how often they accept an outcome that is in fact wrong, a false-acceptance rate that must be measured rather than assumed. Placed inside the loop, intermediate checks can shorten the unchecked horizon, but only for the error classes they actually cover and only when a failed check triggers repair or state restoration. Catching a bad edit without rolling back the workspace leaves the corrupted state in place for the next turn to build on, while errors outside the check’s coverage pass straight through into the compounding analyzed in [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^sec-vol3-intro-horizon-arithmetic|section 1.6]].

↪ Measuring a grader’s false-acceptance rate against independent reference assessment is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.05 Grading Trajectories#^sec-vol3-evaluation-grading-errors|Grader error rates]]**.

### The Five-Part Task Contract

^sec-vol3-intro-five-part-contract

Even with invariant closure in place, the runtime cannot enforce bounds or check completion against a bare instruction such as “repair the race condition.” Left to that five-word prompt, a proposed patch can delete the lock altogether, passing a sequential regression check while worsening concurrency failures under production load. A cleanup step can likewise wipe out uncommitted source files in a shared repository alongside scratch build artifacts. Before an execution engine dispatches any action, it needs an explicit specification of what resources may be modified and what evidence is required to accept the result.[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn9|⁹]]

A task specification turns an informal request into an enforceable contract. The contract is a five-part tuple, ${\mathcal{C}} = \langle {G}, {\mathcal{E}_{\text{env}}}, {\mathcal{A}_{\text{perm}}}, {\mathcal{O}_{\text{avail}}}, {\mathcal{K}_{\text{comp}}} \rangle$, which separates the goal from the execution environment, permitted actions, available observations, and completion criteria. That separation matters because natural-language instructions state intent without giving the runtime the rules it needs to authorize actions or check completion.[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn10|¹⁰]]

**Definition 1.4: Task contract**

***Task contract*** is the explicit specification of a delegated task that separates its goal, environment, permitted actions, available observations, and completion criteria, so that the runtime, not the model, decides what may execute and when the task is done.

1.  **Significance**: The completion criteria define what counts as accepted, which fixes the denominator of cost per accepted task. Two systems, or two versions of one system, can be compared only under the same contract.
2.  **Distinction**: A prompt communicates intent to the model; a contract is enforced by the runtime and the tool environment. The same sentence can appear in both, but only the contract constrains what executes.
3.  **Common pitfall**: Writing the permitted actions into the prompt alone. The model reads the limit, and the host process still allows everything its credentials allow.

In the repository repair task ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^tbl-contract-template|table 2]]), the goal ${G}$ includes an explicit **negative scope**, the set of existing behaviors and invariants that must stay untouched outside the reported defect. The environment ${\mathcal{E}_{\text{env}}}$ names the source baseline, runtime dependencies, and working copy where edits happen. Permitted actions ${\mathcal{A}_{\text{perm}}}$ allow bounded file edits, directory listing, and test runs, while blocking network egress and writes to parent directories. Available observations ${\mathcal{O}_{\text{avail}}}$ limit returned payloads to source excerpts, bounded test logs, and Git diffs. Finally, completion criteria ${\mathcal{K}_{\text{comp}}}$ name the sealed test suites that must pass alongside human review gates for behaviors the tests do not cover.

| Contract Component         |         Formal Symbol          | Systems Role                                        | Concrete Engineering Artifact                    |
|:---------------------------|:------------------------------:|:----------------------------------------------------|:-------------------------------------------------|
| **Goal**                   |             ${G}$              | Desired end state and explicit negative scope       | Repair request that preserves unrelated behavior |
| **Environment**            |  ${\mathcal{E}_{\text{env}}}$  | Target state and execution conditions               | Source baseline and designated working copy      |
| **Permitted Actions**      | ${\mathcal{A}_{\text{perm}}}$  | Operations and resources within delegated authority | Allowed edit paths and test commands             |
| **Available Observations** | ${\mathcal{O}_{\text{avail}}}$ | Information the task may obtain and return          | Source excerpts, bounded test output, and diff   |
| **Completion Criteria**    | ${\mathcal{K}_{\text{comp}}}$  | Evidence and decision rule for accepting the result | Required regression checks and review decision   |

Table 2: **Five-Part Task Specification Contract**: Each component answers a distinct systems question for the repair task, cleanly decoupling intent, execution context, authority, visibility, and verification.

^tbl-contract-template

Each part of the contract blocks a specific failure mode. Leaving negative scope out of the goal invites degenerate fixes, such as silencing a concurrency bug by deleting the failing assertion or removing multi-threaded access paths altogether. Similarly, if the environment is not isolated, agent edits and ad hoc package installs pollute shared host state and break reproducibility. At the tool boundary, omitting explicit action limits lets tool calls run with whatever ambient privileges the host process holds, while unbounded observations let large search outputs flood the context window, crowding out instructions and raising token costs. Finally, without formal completion criteria, the runtime has nothing to stop on except the model’s own claim that it is done.

Environments that keep changing on their own require the contract to separate what the agent changed from what the world changed. During live incident triage by the remediation agent (lighthouse [1.3](https://mlsysbook.ai/vol3/01_introduction/01_introduction.html#lhs-vol3-remediation-agent)), traffic and error rates keep shifting while the agent works. Unless the contract records which observations follow from the agent’s own configuration change and which reflect outside load, a coincidental drop in traffic reads as a successful fix. Observation rules must also distinguish an empty query result from a truncated response. When the runtime truncates a long test log to fit the token budget, it must mark the truncation in the prompt; otherwise, the model may treat the missing error message as proof that no error occurred.

Resource limits and stopping rules accompany the contract. Every delegated task needs turn limits, wall-clock deadlines, dollar ceilings, and clear rules for what happens when a budget runs out. Stopping on an exhausted budget yields an unresolved outcome, meaning the evidence gathered so far neither accepts nor rejects the work. That differs from a failure, where evidence shows the attempt missed the contract, and from a silent crash, which leaves no record at all. The runtime saves the intermediate diff, logs the incomplete checks, and escalates to a human engineer.

Writing a contract also reveals what cannot be safely delegated. Vague goals such as “improve maintainability” cannot be checked by automated tests alone. In those cases, the engineer must define measurable proxy checks, assign a human reviewer, or keep the subjective judgment out of the autonomous loop. The task contract makes these boundaries explicit so the runtime can enforce them mechanically.

Later chapters build each part of the contract. **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07 Tool Calling#^sec-vol3-tool-calling|Tool Calling]]** defines permitted actions and structured observation schemas, **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08 Agent Sandboxes#^sec-vol3-sandboxes|Agent Sandboxes]]** builds the isolated containers and virtual machines that contain untrusted code, and **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness#^sec-vol3-agent-harness|The Agent Harness]]** builds the harness that enforces goals, budgets, and stopping rules. **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13 Agent Evaluation#^sec-vol3-evaluation|Agent Evaluation]]** establishes the statistical and empirical evidence that completion criteria require, and **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14 Operating Agents#^sec-vol3-operations|Operating Agents]]** carries that evidence into live operation.

The invariant closure principle and the five-part task contract establish the governance boundaries for autonomous execution. Enforcing isolation below the model protects shared infrastructure, and checking empirical evidence above the model grounds acceptance in the task contract. Those checks and boundaries, however, are not free: running sealed regression suites, provisioning ephemeral sandboxes, and checking intermediate invariants all spend latency and compute budgets. Weighing those costs requires pricing how errors compound across turns and how retries and checks change the cost per accepted task.
