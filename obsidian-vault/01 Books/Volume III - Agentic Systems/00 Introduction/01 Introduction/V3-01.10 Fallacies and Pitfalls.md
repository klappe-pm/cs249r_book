# V3-01.10 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01 Introduction|V3-01 Introduction]]

^sec-vol3-intro-fallacies

These three questions frame every mechanism in the book, and they also expose the common traps that appear when teams build or measure agents without them. A patch can compile cleanly without resolving the underlying defect, just as an agent can consume its turn budget without producing fresh evidence. Autonomous execution fails when system designers mistake churn inside the loop for genuine task completion.

**Fallacy**: *A larger context window removes the need to manage task state.*

Expanding a context window increases how many tokens a single call can read, but it does not settle which state is current. In an append-only trajectory, stale observations and obsolete file edits pile up alongside current versions. Consider the software repair harness under a 30-turn budget. Starting from an initial prompt of 8,000 tokens and appending 1,500 tokens per turn, the final model call reads 51,500 tokens. This uses only 40 percent of a 128,000-token window, so buffer capacity never forces eviction. Yet without active state pruning, superseded revisions of edited files sit right beside their latest patches. Repeatedly resending earlier turns forces the system to read 892,500 cumulative input tokens, 17.3× the final context size. Even when an entire history fits in memory, raw capacity guarantees neither relevance nor freshness. The runtime must assemble the working context explicitly and mark which state is authoritative rather than leaving the model to untangle conflicting snapshots.

↪ The quadratic input-token cost of resending an append-only history is developed in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-trajectory-cost-accumulation|How multi-turn history drives up input cost]]**.

**Pitfall**: *Appending every failure and retrying until the model reports progress.*

Independent retries can improve acceptance, whereas retries that repeat the same failure provide no gain. With a per-attempt acceptance rate of 40 percent, a budget of ${k}$ = 5 independent attempts succeeds with probability $1-(1-{p_{\text{acc}}})^{{k}}$, here 92 percent. When an agent appends every failure trace into its prompt, however, the model tends to fixate on its earlier bad assumptions. If every retry repeats the same mistake, 5 attempts succeed no more often than the first attempt while spending 5 times the budget. A well-structured runtime keeps the full diagnostic history in an audit log and feeds the model only the distilled evidence needed for the next decision, under hard retry limits. Recovering from repeated failure requires a new hypothesis, a state change, or fresh evidence from the environment before another repair turn. Alternatively, a declared resampling policy can achieve genuinely independent retries by drawing fresh candidates from the clean starting prompt under a finite budget and independent acceptance checks, though another sample on its own is not evidence of progress. When resetting the prompt for a fresh attempt, the runtime must also roll back the workspace, because truncating or rewriting the working context changes only what the model reads while external effects that have already run persist on disk.

**Fallacy**: *A coherent model report establishes that the task is complete.*

A model’s natural-language claim that it has fixed an issue is an unverified hypothesis, not proof of completion. On the closure evidence levels of [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-invariant-closure|section 1.5.2]] it sits at the bottom, below even a compiler check, because a fail-plausible run produces the same confident report as a correct one. The horizon notebook ([1.1](https://mlsysbook.ai/vol3/01_introduction/01_introduction.html#nbk-01-horizon-compounding)) shows the size of the error. Under its assumptions, an unchecked 100-turn repair is correct in only 36.6 percent of runs. If every run ends with a confident completion message, a runtime that trusts that message accepts all of them, and most of its acceptances are wrong. The runtime must instead check the workspace against an explicit evidence standard (sealed tests, static analysis, and the stress runs a concurrency fix requires) and record both the verification artifacts and any remaining gaps.

**Pitfall**: *Expressing an authority limit only as an instruction to the model.*

Telling an agent in its prompt to modify files only within a project directory expresses intent, but it provides no protection against model mistakes or prompt injections hidden in untrusted source files. If the host environment exposes raw execution primitives, an agent can be steered into leaking secrets or modifying infrastructure. Read-only file access is not safe on its own either: an agent that reads an API secret from an environment variable and sends it in an outbound network request leaks data without touching a single local file. The execution boundary, not the prompt, must enforce permissions. Runtimes isolate agent processes with operating-system primitives (containers, isolated network namespaces, short-lived credentials, and scoped tool interfaces) that block unauthorized actions regardless of what the model asks to run.

**Fallacy**: *Environmental variation always requires a model-directed loop.*

Calling a foundation model to choose the next step after a predictable unit-test failure wastes time and tokens when the fix is a known fallback or a fixed retry sequence. Traditional software workflows handle most routine variation with deterministic control flow: branches, parameterized retries, state machines, and exponential backoffs. Model-directed decisions earn their keep only when choosing the next action requires interpreting open-ended evidence that fixed rules cannot parse, such as combining compiler and test diagnostics to edit several files. Engineers should benchmark agent loops against deterministic workflows under the same acceptance criteria; a loop is worth its latency, token spend, and variance only when it lowers the cost per accepted task.

**Pitfall**: *Charging only the successful final trajectory to the accepted result.*

Autonomous task completion frequently requires multiple attempts before a candidate patch satisfies the acceptance checks. Every abandoned branch, failed test run, and discarded attempt consumes compute and wall-clock time, even if its code never merges into the final repository. With a per-attempt acceptance rate of 40 percent, accounting only for the winning trajectory yields an apparent cost of \$2.10 per repair, whereas the true expected cost is \$5.25, a 2.5× understatement. Complete system accounting must also capture sandbox provisioning, tool execution overhead, and the cost of human triaging. Measured over a cohort, the numerator charges every initiated task, accepted or not, while the denominator counts only tasks accepted under the stated evidence standard. That cohort form, the measured counterpart to [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 2]], is developed in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.03 Cost per Accepted Task#^sec-vol3-agent-economics-accounting|Cost per Accepted Task]]**.

Each of these traps comes from mistaking a property of a single model call for a guarantee across the task. A working runtime keeps state current, enforces permissions in the execution layer rather than the prompt, and gates acceptance on independent evidence, judging the system by the cost of its verified outcomes rather than the fluency of its turns.
