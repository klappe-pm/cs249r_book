# V3-01.03 From a Useful Proposal to an Accepted Task

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01 Introduction|V3-01 Introduction]]

^sec-vol3-intro-existence-moment

That gap between a model response and a finished job is concrete when an engineering team delegates a repository repair: diagnosing and fixing an intermittent race condition in a distributed key-value store.[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn1|¹]] A foundation model[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn2|²]] can inspect the issue description and propose an edit to the connection-pool locking logic. Emitting that patch text, however, leaves the repository untouched. Resolving the defect requires an agent to locate the relevant source files, draft an edit, execute compilers and test runners inside an isolated environment, interpret diagnostic logs when a build fails, and verify that the resulting code satisfies the repository’s regression test suite.

An agentic system comes into existence when software closes this interaction loop. Rather than relying on an engineer to copy prompts and error traces back and forth, the surrounding software feeds the foundation model an objective alongside fresh environmental observations and captures the model’s proposed action. It then dispatches that action and returns structured execution feedback to guide the next decision.

The surrounding software, the **runtime**, enforces the boundary between what the model proposes and what the environment executes. All execution authority resides with the runtime. Because a model outputs only text or token streams, generating an operation’s name confers no permission to run it. The runtime parses the proposed action, checks that it complies with current access policies, and dispatches the call through a designated tool. A **tool** provides a structured interface to an environmental action, such as reading file contents, editing source code, running a shell command, or running a test suite. The part of the runtime that drives this loop is often called the agent harness, and **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10 The Agent Harness#^sec-vol3-agent-harness|The Agent Harness]]** develops it as a component of the runtime rather than a separate system. In the conversational arrangement of [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.03 From a Useful Proposal to an Accepted Task#^fig-vol3-open-vs-closed-loop-control|figure 2]] (panel A), a developer carries every command and every error by hand; in the agentic arrangement (panel B), the runtime dispatches only the actions it grants and routes verifier evidence back to itself rather than trusting the model’s account of what happened.

![[90 Assets/Volume III/01 Introduction/Open Vs Closed Loop Control 4841a71adc.svg]]

Figure 2: **A Person or a Runtime Closes the Loop**: In the conversational arrangement (A), the model answers and the developer runs every tool and carries each error back by hand. In the agentic arrangement (B), the runtime assembles context, receives the model’s proposal, and dispatches only actions it grants; the model holds no authority, and verifier evidence returns to the runtime rather than to the model’s own report.

^fig-vol3-open-vs-closed-loop-control

Panel B is the arrangement this book engineers. A capable model served by an optimized inference engine supplies proposals, but it cannot manage its own execution authority, maintain state across tool failures, or verify its actions against external reality. Those responsibilities fall on the surrounding software, so engineering an agent is the discipline of designing, securing, and operating the closed-loop system around the model. Analyzing and building that system requires four foundational instruments:

1.  **The Stochastic Computer**: An architectural map that relates the parts of an agentic system to the parts of a classical computer and marks where the comparison fails ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.04 The Stochastic Computer#^sec-vol3-intro-stochastic-computer|section 1.3]]).
2.  **The H·S·A Exposure Space**: An analytical coordinate system that measures how far a delegated task departs from stateless model inference along three operational dimensions: execution horizon (${H}$), persistent state (${S}_0$ to ${S}_3$), and external authority (${A}_0$ to ${A}_3$) ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-hsa|section 1.4]]).
3.  **The Invariant Closure Principle**: A governance rule stipulating that safety and security invariants must be mechanically enforced by the runtime below the model, while task acceptance must be verified against independent evidence above the model ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-governance|section 1.5]]). *Below* the model means between its proposal and the environment, where the runtime decides what may execute; *above* it means between the finished result and whoever accepts it, where the runtime decides what counts as done.
4.  **Horizon Reliability and Cost Arithmetic**: Mathematical relations that quantify how single-step error rates compound across multi-turn trajectories, showing how retry budgets and recovery mechanisms set the true compute cost per accepted task ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^sec-vol3-intro-horizon-arithmetic|section 1.6]]).

[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-hsa|Section 1.4]] also places four recurring reference workloads, which the book calls lighthouses, in the exposure space; the repair task is one of them. Once all four instruments are in hand, [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^sec-vol3-intro-running-example|section 1.7]] follows the repair task turn by turn to show where each one acts, and [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.09 Book Organization#^sec-vol3-intro-book-organization|section 1.8]] maps the instruments onto the structure of the book.
