# V3-01.05 The H·S·A Exposure Space

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01 Introduction|V3-01 Introduction]]

^sec-vol3-intro-hsa

![[90 Assets/Volume III/01 Introduction/Hsa Locator Origin 574b033854.svg]]

*H·S·A locator with no axis lit and the origin dot highlighted, marking a single model call.*

*Agents depart from a single model call along horizon, state, and authority.*

A single model call reads a static prompt, returns one completion, and leaves the outside world untouched. When a runtime instead stretches execution across dozens of turns, carries files and memory forward, and invokes tools that modify external systems, a single mistaken proposal can compound across steps, corrupt shared state, or trigger an irreversible outage. Sizing the runtime’s defenses to a task therefore starts from the book’s central runtime artifact, the **trajectory**, which records the complete sequence of steps the runtime must govern.

**Definition 1.2: Trajectory**

***Trajectory*** is the ordered sequence of recorded states, proposed actions, runtime decisions, and observations through which one delegated task proceeds, from its initial context to its ultimate acceptance, termination, or escalation.

1.  **Significance**: The trajectory length defines the operational horizon ${H}$, which governs how compounding errors degrade system reliability. Its complete span (encompassing rejected actions, retries, and failed branches) establishes the true accounting boundary when computing cost and latency per accepted task.
2.  **Distinction**: While a conversational transcript captures the tokens exchanged between a model and a user, a trajectory preserves the full causal history of execution. It records which action proposals the runtime approved, modified, or rejected, alongside the raw observations returned by external tools, linking every decision to the exact evidence available at that step.
3.  **Common pitfall**: Preserving only the final deliverable. Storing just the accepted patch or completed document hides the computational cost of discarded attempts, masks transient faults, and discards the intermediate verification evidence that justified accepting the work.

In compact notation, the trajectory is

$$
{\tau} = ({s}_0, {a}_0, {o}_1, {s}_1, {a}_1, {o}_2, \dots, {s}_{{H}})
$$

where ${s}_{t}$ is the recorded state available at decision step ${t}$, ${a}_{t}$ is the action the model proposes, and ${o}_{t+1}$ is the observation returned by the execution environment. Each transition from ${s}_{t}$ to ${s}_{t+1}$ is one **turn**: one model call paired with the runtime’s mediation of the resulting proposal. The notation establishes a total ordering across interactions, where each ${s}_{t}$ reflects the runtime’s partially observed view of the broader environment. The repair trajectory that [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^sec-vol3-intro-trajectory-systems-boundary|section 1.7.1]] follows turn by turn shows why the runtime must manage cost, state, and authority over this whole sequence rather than per call.

Each trajectory ${\tau}$ departs from an isolated model call along three operational dimensions: how many turns ${H}$ execution continues, what state ${s}_{t}$ persists across steps, and what external side effects the actions ${a}_{t}$ can trigger. This book models these dimensions as the Horizon, State, and Authority (H·S·A) exposure space.

**Definition 1.3: H·S·A exposure space**

***H·S·A exposure space*** is the three-dimensional coordinate system quantifying how far a delegated task departs from an isolated model call: its horizon ${H}$ measured in sequential turns, the state ${S}_0$ through ${S}_3$ carried between invocations, and the authority ${A}_0$ through ${A}_3$ exercised over external systems.

1.  **Significance**: Each axis identifies a concrete operational exposure that the runtime must bound. Horizon determines how rapidly unverified errors compound, state dictates the working memory and durable artifacts carried forward, and authority establishes the maximum blast radius of an errant action. Later divisions of this book systematically address how to close these exposures: Part II governs state, Part III controls authority, and Part IV bounds horizon.
2.  **Distinction**: A coordinate in this space describes the exposure a task carries, which is a property of the task and its environment. The runtime’s validation gates, sandboxes, and compensating operations are its response to that exposure, which [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-governance|section 1.5]] develops as closure. Closure is what the runtime builds; the coordinate is where the task sits.
3.  **Common pitfall**: Inferring authority from syntax or command names alone. Authority reflects the operational consequence of an action within its specific environment; an identical file deletion is discardable inside an ephemeral sandbox, but irreversible when executed directly against an unversioned production datastore.

Horizon ${H}$ tracks the length of execution in sequential turns. Every additional turn gives the agent another chance to invoke a tool with bad arguments, act on stale observations, or drift from the goal. [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^sec-vol3-intro-horizon-arithmetic|Section 1.6]] shows mathematically how unchecked step-level error rates compound into severe task-level failure rates across long sequences. Turn count and wall-clock latency are distinct budgets that require separate limits. A three-turn workflow that triggers a large remote build cluster can run for hours, whereas a hundred-turn in-memory code refactoring completes in seconds. Production runtimes must meter both, bounding turns to restrict error compounding and bounding wall-clock time to release compute and network resources.

State (${S}_0$ to ${S}_3$) describes the data, memory, and workspace artifacts that persist across turns. At ${S}_0$, the system is stateless, carrying no task context past a single call; stepping to ${S}_1$ adds conversational working state, including the tokenized context window and inference-tier serving state such as cached key-value (KV) attention pairs. Once the agent modifies task-local working artifacts within an isolated workspace (such as a private source tree, an ephemeral container, or an in-memory scratchpad), it reaches ${S}_2$. ${S}_3$ covers execution that reads or writes durable shared state outliving the task session, such as an authoritative database, a shared object store, or a central code repository. Because realistic workloads routinely span several tiers at once, this classification establishes what data the runtime must checkpoint or isolate, sets cache invalidation boundaries, and decides which storage system remains authoritative when local scratchpad views diverge.

Authority (${A}_0$ to ${A}_3$) defines the blast radius of actions delegated to the task. At ${A}_0$, access is strictly read-only, although exfiltration remains a risk if retrieved secrets leak into output text. Stepping up to ${A}_1$ permits mutations, but confines them entirely to a disposable workspace where unintended modifications carry zero external impact. At ${A}_2$, actions affect external systems, yet every mutating operation pairs with an explicit compensating transaction[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn4|⁴]] executed under verified preconditions and a separate retry policy that prevents duplicate effects. Finally, ${A}_3$ covers non-compensable actions (such as modifying unversioned production records, issuing financial transactions, or publishing public communications) for which no automated reversal exists. Authority reflects the operational consequence within the specific execution environment rather than command syntax. Because a trusted runtime mediates every action against an explicit per-task capability grant, restricting this grant provides the first and most cost-effective line of defense before deploying complex validation machinery.[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn5|⁵]]

The coordinate space in [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^fig-vol3-hsa-taxonomy|figure 4]] maps agentic workloads across three operational exposure axes: horizon (${H}$, turns along the horizontal), authority (${A}_0$ to ${A}_3$ on the vertical), and carried state (${S}_0$ to ${S}_3$ on the depth axis). This space serves as an analytical lens rather than a rigid taxonomy: two workloads occupying the same cell may still demand different runtime controls if their data sensitivity, tool reliability, or failure thresholds differ. Changing the execution environment can shift a task into a completely different cell even when its foundation model and turn horizon remain identical, as shown in example [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^exmp-01-hsa-incident|1.1]]. The four workloads plotted in the space are the book’s lighthouse workloads, described in [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|section 1.4.1]].

**Example 1.1: A working copy and the only copy**

**Scenario**: A coding assistant must repair a software defect while preserving adjacent, uncommitted edits authored by a developer. Consider two execution environments: an isolated, ephemeral sandbox containing a working copy of the project vs. direct access to the developer’s sole authoritative workspace. The foundation model, repair objective, and expected turn horizon remain identical in both configurations. In each case, the assistant issues a command to delete files while cleaning up intermediate build artifacts.

**Diagnosis**: Inside the ephemeral sandbox, the source files are ${S}_2$ working state and the mutation authority is bounded at ${A}_1$. Tearing down the sandbox discards any bad modifications without corrupting the developer’s original files. In the authoritative workspace, however, that identical command targets ${S}_3$ state. Although one person uses it, the workspace is durable state the task shares with its developer, it outlives the task, and it holds the only copy of the developer’s edits. If the deleted files contain unique, unstaged edits missing from version control history, the operation escalates to ${A}_3$ irreversible data loss. Version control alone does not prevent this loss, because uncommitted working-tree changes have no snapshots. A sound systems contract grants the agent access strictly to an isolated clone, excludes unrelated edits from the agent’s context, and reserves the integration of reviewed patches for a separate gate. The runtime must enforce that isolation boundary through tool authorization rather than relying on prompt instructions asking the model to be careful.

**Systems lesson**: The failure boundary shifted even though the model, prompt, and turn horizon remained unchanged. Automated test suites check functional behavior, and diff reviews check patch cleanliness, but neither prevents an unauthorized deletion command from wiping out working state. Sound systems engineering enforces safety at the infrastructure boundary, preventing destructive operations from reaching authoritative state, rather than relying on post-hoc checks to detect irreversible side effects.

### Four Lighthouse Workloads

^sec-vol3-intro-lighthouses

A mechanism that halves latency or cost for a short interactive query can be dead weight for a hundred-turn code repair or a dangerous shortcut for a live production rollback. To test mechanisms against concrete bottlenecks rather than in the abstract, the four workloads plotted across the H·S·A exposure space of [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^fig-vol3-hsa-taxonomy|figure 4]] serve as this book’s **lighthouses**: the support agent, remediation agent, repository repair agent, and research agent. Like a lighthouse, each is a fixed reference point that the reader can steer by as the mechanisms change from chapter to chapter. Each is bounded by a different systems bottleneck. Automated repository repair serves as the primary running example, while the other three appear whenever a chapter examines failure modes or constraints that repository repair does not trigger.

**Lighthouse 1.1: Repair agent (long-horizon worker)**

**Workload**: A repository coding agent diagnoses and fixes a defect in an isolated working copy, submitting a verified patch for review. The connection-pool race condition in this chapter serves as the concrete running example; its reference harness budgets 30 steps inside a 128,000-token context window.

**Exposure**: Long horizon (tens to hundreds of turns), a task-local working copy (${S}_2$), and filesystem edits confined strictly to that disposable sandbox (${A}_1$) until a human-reviewed patch is exported.

**Binding constraint**: Compounding errors across the trajectory, and repeated input whose cumulative token count grows quadratically with the number of turns. Each turn adds only one step of output and tool observations to the prompt, but resending that growing history on every turn means the model re-reads every earlier turn at each step. Without compatible prefix reuse (serving a repeated history from state already computed for it), this repeated input can dominate aggregate inference work and cost, while acceptance depends strictly on immutable test suites that the agent cannot modify.

**Lighthouse 1.2: Research agent (untrusted reader)**

**Workload**: A deep-research agent answers an open-ended question by querying, retrieving, and synthesizing external web sources, frequently delegating sub-queries to parallel worker agents.

**Exposure**: Horizons from tens of turns for one question to thousands for a standing crawl, an expanding knowledge store of ingested documents (${S}_3$), and read-only authority (${A}_0$).

**Binding constraint**: Ingested content is untrusted data. Through indirect prompt injection, in which a retrieved page carries text the model may follow as an instruction, it can redirect the trajectory or exfiltrate private context ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.14 Source References#^ref-greshake2023not|Greshake et al. 2023]]), so read-only access is still a serious security exposure. Aggregate token consumption from retrieved documents and worker fan-out dominates total execution cost.

**Lighthouse 1.3: Remediation agent (irreversible actor)**

**Workload**: An automated site-reliability agent diagnoses a live production incident and applies configuration or infrastructure changes to restore service. **[[01 Books/Volume III - Agentic Systems/07 Synthesis/20 Conclusion/V3-20.04 One Incident Through the System#^sec-vol3-conclusion-capstone|One Incident Through the System]]** analyzes one such remediation end to end.

**Exposure**: A moderate horizon (tens of turns), mutable shared production infrastructure (${S}_3$), and non-compensable or irreversible operations (${A}_3$).

**Binding constraint**: A single erroneous action can incur outages costing orders of magnitude more than all trajectory compute combined. Human-in-the-loop approval latency and the blast radius of incorrect decisions dominate systems design, requiring strict approval gates, compensating actions, and explicit points of no return before execution begins.

**Lighthouse 1.4: Support agent (interactive responder)**

**Workload**: A customer-operations agent resolves billing and booking inquiries while the user waits synchronously.

**Exposure**: Short sessions of a few turns each across thousands of concurrent users, with session context combined with sensitive enterprise database records (${S}_1$ with ${S}_3$). Authority escalates from read-only queries (${A}_0$) to compensable updates such as a seat hold that can be released (${A}_2$), and on to actions with no automated reversal such as a refund paid out to an external account (${A}_3$).

**Binding constraint**: Strict tail latency under high concurrency, combined with verifiable adherence to enterprise policy. Serving throughput and the aggregate memory overhead of retaining active session state across thousands of simultaneous connections dominate systems cost.

Comparing these four lighthouses shows why systems mechanisms cannot be evaluated in the abstract. Proactive context summarization is necessary for a multi-turn repository repair agent, but superfluous for a three-turn support session. An on-call remediation agent can read diagnostic telemetry under a prior grant while requiring explicit approval for production changes. A read-only researcher can likewise run under a bounded grant, though disclosing sensitive context may still require approval. The task boundary, rather than the workload label, decides where those gates belong. Each later chapter ties its mechanisms directly to the lighthouse whose binding constraints they resolve. Placing a workload in the space shows where it is exposed; how the runtime closes each exposure without trusting the model to do so is the subject of invariant closure.
