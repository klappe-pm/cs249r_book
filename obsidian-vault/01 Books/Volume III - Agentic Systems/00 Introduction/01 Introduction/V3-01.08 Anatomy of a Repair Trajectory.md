# V3-01.08 Anatomy of a Repair Trajectory

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01 Introduction|V3-01 Introduction]]

^sec-vol3-intro-running-example

Up to this point, the stochastic computer map, the H·S·A exposure space, invariant closure, and horizon arithmetic have appeared one instrument at a time. During an actual run of the race-condition repair ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.03 From a Useful Proposal to an Accepted Task#^sec-vol3-intro-existence-moment|section 1.2]]), all four act on the same sequence of steps at once: every proposed edit tests the workspace boundary, draws down the turn and dollar budget, and produces compiler or test output that shapes the next decision. Governing that loop requires the runtime to work at two scales: across the trajectory as a whole, where state, permissions, and cost accumulate from turn to turn, and inside each individual turn, where a proposal is checked, executed, and recorded before the next call begins.

### Why the Runtime Manages the Trajectory, Not the Single Call

^sec-vol3-intro-trajectory-systems-boundary

Execution begins when the runtime provisions an isolated working copy of the repository and supplies the initial task description. The model proposes running the failing test. After validating that this command is authorized, the runtime invokes the test runner and records its output. When the runner reports a deadlock, the runtime supplies the diagnostic output to the next model call. The model then proposes inspecting the connection-pool implementation, and the returned source code reveals the locking logic that requires repair.

Guided by this inspection, the model proposes a patch. As [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.04 The Stochastic Computer#^sec-vol3-intro-stochastic-computer|section 1.3]] established, that patch is a candidate rather than a certified computation. Before modifying the working copy, the runtime checks that the edit targets permitted files. That path check is a mechanical bound below the model, and it keeps this ${A}_1$ edit inside the ${S}_2$ working copy. The step also separates three things that a single-call view conflates: the model’s generated diff is a proposal, the modified file is an effect, and the tool’s execution report is an observation. When the next build reports an unclosed bracket, that observation steers the following turn. The model proposes a corrected patch, which the runtime applies before rerunning the build. The compiler has acted as an intermediate check in the sense of the horizon notebook ([1.1](https://mlsysbook.ai/vol3/01_introduction/01_introduction.html#nbk-01-horizon-compounding)), catching the syntax error one turn after it happened; the corrected patch and clean rebuild keep that error from carrying into the remaining turns. Once compilation succeeds and visible unit tests pass, the runtime collects regression evidence from the contract’s sealed suite, which the editing tools cannot touch, raising the closure evidence above the model from visible tests to sealed tests. It then records the resulting deliverable alongside these verification records. If the results satisfy the contract’s completion criteria, the runtime submits the repair; otherwise, it can continue iterating, abort, or escalate to a human engineer.

What the tools return shapes the next turn: a thread deadlock calls for a different fix than a syntax error, and a clean build never proves that a race condition is gone. Even a broad regression suite can miss a thread schedule that triggers the bug under load. An agent runtime therefore needs both a way to fold new evidence into the next call and a clear rule for when that evidence is enough to stop. The loop itself is old, since feedback control[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.15 Footnotes#^fn12|¹²]] and reinforcement learning have long organized action around observations of an environment ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.14 Source References#^ref-wiener1948cybernetics|Wiener 1948]]; [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.14 Source References#^ref-sutton2018reinforcement|Sutton and Barto 2018]]), and ReAct showed foundation models interleaving reasoning, actions, and observations in the same way ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.14 Source References#^ref-yao2023react|Yao et al. 2023]]). What the runtime adds is accountability for that loop, which is why fault isolation, access control, and recovery remain necessary when a generated proposal can be wrong or destructive.

Because dependencies cross turn boundaries, the runtime must manage the whole trajectory rather than isolated calls. The corrected patch depends on compiler errors produced several turns earlier, each edit draws down the task’s cumulative token and dollar budget, and every action must be checked against the task’s permissions. A single model request ends as soon as its response stream finishes, whereas the delegated task, along with any background tool runs, finishes only when the runtime settles it. Even the prompt itself compounds from turn to turn: in a recorded repository repair from the benchmark in [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.03 From a Useful Proposal to an Accepted Task#^sec-vol3-intro-existence-moment|section 1.2]], each turn appends the model’s command and the shell’s output to the conversation history before invoking the model again ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^fig-vol3-repair-trajectory-context-growth|figure 6]]).

Across the 22 model calls of that trajectory, the first call reads 5,499 characters of task prompt and system instructions, whereas by call 22 the context read on a single turn has grown to 29,594 characters (5.4× the initial call). Because every call resends the accumulated transcript of earlier turns, the trajectory transmits 396,997 characters of input across its 22 calls even though only 29,594 distinct characters enter the transcript (13.4× retransmission). That quadratic growth in cumulative input explains why multi-turn tool use dominates gateway token volume ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.02 The Evolution of Machine Learning Systems#^fig-vol3-agentic-token-growth|figure 1]]) and why context compaction (**[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04 Context Engineering#^sec-vol3-context-engineering|Context Engineering]]**) and key-value cache reuse across turns (**[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management#^sec-vol3-kv-cache|KV Cache Management]]**) are foundational runtime responsibilities.

Context accumulation is only one of the assumptions that break when a service built for isolated requests hosts a multi-turn trajectory ([[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^tbl-vol3-request-vs-trajectory|table 3]]). Stateful services may already provide some of these mechanisms; the comparison names engineering responsibilities that later chapters develop rather than limits built into web services.

A naive implementation might write this multi-turn interaction as a bare while-loop. As shown in [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^lst-vol3-naive-agent-loop|listing 1]], dispatching parsed commands directly and stopping whenever the model prints a completion token leaves every one of those responsibilities unaddressed.

``` python
prompt = task_description
while True:
    response = generate(prompt)
    command = parse_command(response)
    output = run_with_host_permissions(command)
    prompt += format_observation(command, output)
    if "TASK_COMPLETE" in response:
        break
```

Listing 1: **An Unmediated Agent Loop**: Direct command dispatch and model-declared completion leave authority, task evidence, resource limits, and recovery unspecified.

^lst-vol3-naive-agent-loop

Consider what happens when the first test fails and the model searches the host filesystem for the target function name. Because the loop has no authorization boundary, the search command runs with the full privileges of the host process rather than inside the repository copy. Whatever output the search produces is appended straight to the prompt without pagination, truncation, or filtering. If the command dumps thousands of lines of output, the context window overflows or drives up token costs on every later turn. Those failures come not from using a loop, but from leaving out authorization checks and context management.

The same loop also lets the model decide when the task is done. If the model falls into a cycle, proposing small variations of a broken patch turn after turn, the loop runs forever and burns budget without fixing the bug. Worse, if the host process crashes after writing a file edit to disk but before recording the test result, the in-memory transcript is lost while the modified file stays on disk. A restart from the original prompt then runs against a dirty, inconsistent working tree. Handling durability, rollbacks, and recovery requires knowing whether a workspace is disposable and whether actions have outside effects; an unmediated loop tracks neither.

These problems are familiar systems responsibilities (access control, durability, and resource accounting) operating across an entire task. A short, throwaway script can get by with simple retries, whereas an agent modifying shared production infrastructure needs durable checkpoints and compensating actions. In both cases, the runtime needs explicit components to check permissions, persist state, enforce budgets, and verify completion. Keeping those jobs outside the model’s unverified output closes the loop under the five-part task contract of [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-five-part-contract|section 1.5.3]], and it dictates how the runtime mediates each individual turn from context assembly to contract assessment.

### The Six Phases of a Turn

^sec-vol3-intro-execution-lifecycle

Consider the turn in which the repository repair agent proposes changing mutex acquisition in the connection pool. If the runtime ran that output straight against the shell, a truncated response or an out-of-scope file path would hit the workspace unchecked. Instead, each turn passes through six phases across the runtime, model, and tools:

1.  **Context assembly**: The runtime builds the next context from the task contract, current workspace state, and relevant observations. It checks that remaining token and dollar budgets allow another model call, pruning or summarizing older turns to stay within the window while keeping the history of workspace edits clear.
2.  **Model invocation**: The model reads that context and returns an action proposal along with call metadata. The runtime treats cut-off generations, network drops, or malformed outputs as failed calls rather than commands to execute, keeping serving and network errors out of the tool layer.
3.  **Validate and authorize**: The runtime checks the proposed operation against the tool’s schema and the task’s capability grant. For a code patch, it checks that the target files sit inside the allowed repository paths and that the patch format is valid. The runtime rejects unauthorized operations before dispatch or pauses the turn if human approval is required.
4.  **Tool execution**: The tool runs the authorized operation inside an isolated environment under strict timeouts and resource limits. Applying a patch, for example, modifies files in the sandboxed workspace before the repair passes verification. The runtime tracks running tools asynchronously rather than treating dispatch as completion.
5.  **Observation and evidence**: The runtime captures the tool’s raw output and formats it as evidence for later turns. A compiler failure produces error logs; passing tests produce exit codes and test results. The runtime’s audit log records what happened to every proposal. A rejected proposal leaves external state untouched, whereas a network call whose reply is lost leaves its outcome unknown, because the remote service may have applied the change before the connection dropped. The runtime therefore marks timed-out or truncated runs as unresolved rather than treating silence as success.
6.  **Assess against contract**: The runtime checks the updated task state against the contract’s completion criteria. Depending on the result, it can start another turn, wait on background jobs, ask the user for clarification, stop the trajectory as unresolved, or accept the deliverable. That decision rests on external evidence and remaining budgets rather than the model’s own report.

These six phases mark boundaries of responsibility rather than a rigid synchronous schedule. In production, authorized tools may run asynchronously against remote services, and a model call may propose a final answer instead of a tool call. Implementations can overlap independent work, but causality fixes the order of decisions: a runtime cannot authorize an action from observations that arrive after dispatch, and it cannot tell whether an external effect succeeded from the proposal alone. [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^fig-vol3-ch01-execution-lifecycle|Figure 7]] draws the phases as a U in which only an authorized request drops from validation to the tool. Its dashed paths carry the exceptions. A rejected request returns to the observation history as error feedback without touching any tool, approvals and background jobs pause the turn, and assessment at the end of the turn either starts the next turn, accepts the deliverable, or stops without acceptance.

![[90 Assets/Volume III/01 Introduction/Ch01 Execution Lifecycle b8657ccb51.svg]]

Figure 7: **The Six-Phase Turn Lifecycle**: Each phase marks a change in which component is responsible, not a mandated scheduler. The runtime assembles context, authorizes requests, records outcomes, and assesses progress; the model only proposes, and only an authorized request reaches a tool. A timed-out tool leaves its outcome unknown, and acceptance requires evidence independent of the model’s own report, so exhausted limits end in an unresolved outcome or escalation rather than success.

^fig-vol3-ch01-execution-lifecycle

The lifecycle also gives each piece of evidence its own record, which keeps the bounded claims of [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-fail-plausible|section 1.5.1]] from merging into one. Phase 4 records that a patch modified a file. Phase 5 records that compilation succeeded or that a named test passed on the schedules it exercised. Only phase 6 asks whether those records together meet the contract’s completion criteria. A runtime that logged one undifferentiated stream could not tell intermediate execution from verified resolution.

Whether these components run inside one local process or across services in a cluster, the core rule stays the same: authority is separate from generation. Permissions come from the runtime’s grant, completion criteria come from the task contract, and execution records come from tool observations, never from model text, unverified tool replies, or the agent’s own completion tokens.

In practice, running a test suite often takes much longer than generating the patch that triggered it. During that wait, the task stays active even though model inference is idle. The runtime must keep enough context to process the test results when they return. Holding serving state in high-bandwidth accelerator memory throughout a long tool wait, however, wastes scarce capacity, while evicting the key-value cache too early forces expensive recomputation on the next turn. Separating the lifetime of a task from the lifetime of its serving memory is therefore a central systems problem. Holding accelerator memory idle during slow external operations is the **tool-wait problem**; **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kvcache-swapping|Paused-State Policies]]** prices the trade-offs of keeping, offloading, or evicting that state.

The same distinction applies to context history. Keeping full diagnostic logs in durable storage for later audits does not mean resending every compiler warning in every prompt. Inference latency, accelerator memory, tool duration, and dollar cost pull in different directions when the runtime decides what to keep, recompute, or summarize. Giving every data record a clear owner and lifetime lets the runtime manage caches and context deliberately, and the same division of responsibilities organizes the rest of the book.
