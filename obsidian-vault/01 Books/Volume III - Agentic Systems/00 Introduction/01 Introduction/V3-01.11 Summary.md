# V3-01.11 Summary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01 Introduction|V3-01 Introduction]]

^sec-vol3-intro-summary

A foundation model generates candidate reasoning traces and actions, yet it cannot verify its own output or safely modify external systems. Four instruments govern the design of the runtime that surrounds it. The *stochastic computer* map compares an agent to a classical computer and locates where the analogy breaks: because the model only proposes, a deterministic runtime must manage persistent state, enforce permissions, and close the loop. The *H·S·A exposure space* sizes that runtime along three dimensions: execution horizon (${H}$), accumulated state (${S}_0$ to ${S}_3$), and delegated authority (${A}_0$ to ${A}_3$). *Invariant closure* then pairs hard execution boundaries below the model with independent, artifact-based acceptance checks above it.

Two economic relations price those choices. Under the independent-step model without recovery, unchecked multi-turn runs compound step errors exponentially, so catching and repairing errors early shortens the effective horizon over which mistakes accumulate. Measuring performance by *cost per accepted task* charges every wasted model call, sandbox run, and human review across failed attempts to the verified deliverables that pass. As the repository repair walkthrough and the four lighthouse systems show, runtime machinery should scale with exposure: an agent needs only the safeguards that its horizon, state, and authority demand.

**Key Takeaways: Agency is a property of the system, not the model**

- **Stochastic proposals need a closing runtime**: An agent resembles a classical computer, but its foundation model only proposes. It generates candidate tokens and actions, leaving the validation of correctness and actual execution to external software. The surrounding runtime must enforce permissions, preserve state across steps, and govern the full trajectory through failures and retries.
- **Task exposure dictates architectural obligations**: The H·S·A dimensions (horizon length, accumulated state, and delegated authority) pinpoint where an autonomous workflow requires protective sandboxes, durable checkpoints, human intervention, and verifiable evidence. System mechanisms should scale with this exposure profile; tasks with short horizons and constrained authority do not require the heavyweight control loops of high-exposure systems.
- **Runtime enforcement and empirical evidence serve distinct roles**: Structural boundaries enforce hard constraints on permitted actions, preventing catastrophic side effects regardless of model behavior. By contrast, verification checks produce empirical evidence only for the specific properties they measure. Task acceptance requires evaluating this evidence against a defined contract. Passing tests support claims only within their measured coverage; an eloquent report alone supplies no independent evidence.
- **Two numbers price every mechanism, autonomy included**: Under the independent-step model without recovery, unchecked task success decays exponentially with horizon length, so detecting and repairing errors before later turns depend on them can improve reliability without changing the model. Meanwhile, the cost per accepted task amortizes all wasted inference, compute infrastructure, and human oversight across verified deliverables. An autonomous loop justifies its operational complexity only when it reduces this net cost under the task contract.
