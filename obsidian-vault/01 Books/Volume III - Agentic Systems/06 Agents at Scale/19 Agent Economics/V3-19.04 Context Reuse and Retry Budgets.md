# V3-19.04 Context Reuse and Retry Budgets

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19 Agent Economics|V3-19 Agent Economics]]

^sec-vol3-agent-economics-caching

Across the turns of a repair, the same prompt prefix recurs call after call. Context engineering arranges the request so that the stable part comes first, and the serving system keeps the key-value (KV) attention state of that prefix so the next call need not recompute it. Reuse lowers cost, but it is not free, and it competes with two other purchases the runtime can make: compacting the context, which shortens the prompt but discards reusable state, and buying more attempts, which raises coverage but multiplies the bill. Each must be priced under the same acceptance contract before the runtime can tell which one lowers the cost per accepted task.

↩︎ The exact-prefix, execution-parameter, residency, and tenant conditions under which retained attention state may be reused are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kv-cache-prefix-compatibility|Prefix compatibility]]**.

### Pricing Prefix Cache Hits

^sec-vol3-agent-economics-prefix-cache-value

When an agent client retransmits the full conversation transcript on every turn while the provider’s serving cluster retains compatible KV state in memory across calls, the tokens sent on the wire diverge from the tokens recomputed on the server.[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.16 Footnotes#^fn1|¹]] Pricing multi-turn reuse therefore requires distinguishing between logical input, physical computation, and billed tokens. Over an execution trajectory of ${H}$ turns, one call each, let ${S}^{({t})}$ represent the logical input length on call ${t}$, ${S_{\text{hit}}}^{({t})}$ its eligible cached prefix length, and ${K}^{({t})}$ its billed output length. Under a published tariff with per-token rates ${c_{\text{in}}}$ for fresh input, ${c_{\text{cache}}}$ for cached input, and ${c_{\text{out}}}$ for generated output, the total token charge is

$$
{C_{\text{session}}}=\sum_{t=1}^{{H}}\left[{c_{\text{in}}}({S}^{({t})}-{S_{\text{hit}}}^{({t})})+{c_{\text{cache}}}{}{S_{\text{hit}}}^{({t})}+{c_{\text{out}}}{}{K}^{({t})}\right]. \tag{1}
$$

^eq-vol3-agent-economics-session-bill

Commercial pricing models often incorporate additional dimensions, including cache-write surcharges, hourly retention fees, and minimum eligible prefix thresholds. In an append-only agent transcript, each turn re-sends the cumulative history alongside newly observed tool outputs and model generations. With an initial prompt of ${S_{\text{base}}}$ tokens and ${\Delta S_{\text{turn}}}$ tokens appended per turn, the logical input over the whole trajectory is the quadratic re-send total ${S_{\text{sent}}}$ of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 2.9]]**. Ideal prefix reuse charges only ${S_{\text{fresh}}}={S_{\text{base}}}+({H}-1){\Delta S_{\text{turn}}}$ of that total at the fresh-input rate, once each for the initial prompt and every appended increment. Priced under the tariff, the total input bill is ${c_{\text{in}}}{}{S_{\text{fresh}}}+{c_{\text{cache}}}({S_{\text{sent}}}-{S_{\text{fresh}}})$. Because both ${c_{\text{cache}}}$ and ${\Delta S_{\text{turn}}}$ remain positive, the quadratic growth term does not disappear; caching merely scales down its cost coefficient from ${c_{\text{in}}}$ to ${c_{\text{cache}}}$. These formulations account for billed input tokens, not the physical accelerator memory required to hold this reusable state across requests.

↩︎ The accelerator memory that retained attention state occupies is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.03 The Footprint of Retained Attention State#^sec-vol3-kvcache-geometry|The Footprint of Retained Attention State]]**.

Prefix hits require strict alignment between the incoming token sequence and the cached execution context, including weights and adapters, token positions, attention masks, and applicable multimodal inputs, together with residency and tenant access conditions (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-prefix-coherence|5]]). Reusability breaks at the first altered token. Output sampling settings alone need not change already computed prefix tensors; any additional provider cache-key restrictions belong to the service contract. In production deployments, distributed request routing, memory pressure and cache eviction, and protracted tool execution times degrade realized hit rates. Economic models must therefore price observed, eligible hits under the actual service contract rather than assuming theoretical upper bounds.

**Napkin Math 19.2: Pricing an append-only trajectory**

**Problem**: An agent trajectory runs 30 turns, starting with an initial prompt of 8,000 input tokens and appending 1,500 tokens on each subsequent turn. Each invocation generates 200 output tokens. The provider tariff charges \$3 per million fresh input tokens, \$15 per million output tokens, and 10 percent of the fresh-input price for cached reads, with no separate write or retention fees. How much does ideal prefix reuse reduce the token bill for this trajectory?

**Math**: Cumulative logical input across all turns reaches 892,500 tokens. Under ideal prefix reuse, only 51,500 tokens are billed at the fresh-input rate. Input processing therefore costs \$2.678 without reuse vs. \$0.407 with prefix caching. Combining this with the constant \$0.090 output charge yields total bills of \$2.768 and \$0.497, representing a 5.6× cost reduction.

**Systems insight**: Cache hit rate governs financial efficiency. Because historical context constitutes almost all of this trajectory’s input, even small reductions in hit rate produce large absolute billing increases. If 10 percent of the eligible prefix misses (for example, because a volatile timestamp or session identifier sits near the prompt header), the session cost increases by \$0.227, raising the cached bill by 45.7 percent. Prefix caching modifies only the model inference term in effective cost (${C_{\text{eff}}}$): it lowers the cost of carrying context across turns while leaving delivered inputs, outputs, and task acceptance unchanged.

### The Price of Compaction

^sec-vol3-agent-economics-compaction-price

Unlike prefix caching, context compaction actively alters the input transcript. Replacing prior conversation turns with an aggregated summary shortens the active prompt, though it risks invalidating cached attention state. If summarization preserves a stable system prefix, subsequent requests can still reuse those initial blocks. To price the cache-invalidation penalty explicitly, consider the case of a complete cache miss: the first compacted invocation shares no reusable prefix with prior turns, but subsequent calls resume append-only prefix reuse from the compacted prompt. The baseline comparison retains the full uncompacted context over the same remaining turns, holding future token additions and ordinary output lengths constant. This analysis isolates the pure token price of compaction; whether a given summary preserves downstream task acceptance is evaluated separately using the context-policy evaluation of **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.09 Evaluating Context Policies#^sec-vol3-context-engineering-evaluation|Evaluating Context Policies]]**.

Let ${S}$ be the input length at the moment of compaction, ${S_{\text{comp}}} < {S}$ the compacted length, and ${N_{\text{rem}}} \ge 1$ the remaining ordinary invocations, **including the first compacted call**. Set the two call sequences side by side. Keeping the context makes ${N_{\text{rem}}}$ ordinary calls, the first of which reads the cached history plus one fresh increment. Compacting makes one summarization call followed by ${N_{\text{rem}}}$ ordinary calls on the compacted prompt. Assume the summarization call reads exactly what the keep path’s first call would have read, at the same cached and fresh prices. Its input charge then equals that call’s input charge, and the two cancel when the paths are differenced. Ordinary outputs are equal call for call. What remains on the compaction side with no counterpart on the keep side is the summary’s generated tokens, ${c_{\text{out}}}{}{K_{\text{sum}}}$, and the first compacted call, which must send all ${S_{\text{comp}}}$ tokens as fresh input to rebuild server KV cache state. Relative to keeping the original context, the upfront investment ${U}$ is therefore

$$
{U}={c_{\text{out}}}{}{K_{\text{sum}}}+{c_{\text{in}}}{}{S_{\text{comp}}},
$$

which combines the output generation fee of the summary with the fresh-input cost of repopulating the cache. Each subsequent call saves ${s}={c_{\text{cache}}}({S}-{S_{\text{comp}}})$ under the assumption of equal incremental growth. The cumulative cost difference across ${N_{\text{rem}}}$ remaining calls is therefore:

$$
{C_{\text{compact}}}({N_{\text{rem}}})-{C_{\text{keep}}}({N_{\text{rem}}})={U}-({N_{\text{rem}}}-1){s}, \qquad {N_{\min}}=1+\left\lceil\frac{{U}}{{s}}\right\rceil \quad({U}>0,\ {s}>0).
$$

Here ${N_{\min}}$ represents the **payback horizon**: the minimum number of remaining invocations required for per-turn cache savings to offset the initial compaction surcharge. When ${U} \le 0$, compaction pays for itself on the very first call; when ${s} = 0$ and ${U} > 0$, compaction never recovers its cost on token pricing alone. Accounting for the first compacted call separately from later turns prevents off-by-one errors when estimating the remaining trajectory budget.

**Napkin Math 19.3: Count the first compacted call**

**Problem**: In the preceding scenario, suppose the agent triggers compaction at turn 16, compressing 30,500 tokens down to 12,000. The summarization call emits 1,500 tokens under standard cached-history pricing. If 15 ordinary calls remain (including the first compacted turn), what is the minimum remaining horizon required for compaction to cost no more than retaining the full context?

**Math**: Retaining the uncompressed context incurs \$0.24525 in remaining input costs. Compaction incurs \$0.19035 across remaining ordinary calls plus \$0.03570 for the summarizer, totaling \$0.22605. The upfront differential is \$0.05850, against which each subsequent turn saves \$0.00555. With 11 calls remaining, compaction still costs \$0.00300 more than baseline. Reaching 12 remaining calls yields a net saving of \$0.00255.

**Systems insight**: Compaction lowers total expenditure only when the remaining trajectory length meets or exceeds the payback horizon ${N_{\min}}$. ${N_{\min}}$ scales inversely with the cached read rate, because the upfront cost ${U}$ depends on ${c_{\text{in}}}$ and ${c_{\text{out}}}$, whereas the per-call savings ${s}$ are proportional to ${c_{\text{cache}}}$. If the cached read tariff drops from 10 percent to 5 percent of the fresh-input price, the break-even horizon extends to 23 calls. Because only 15 calls remain, compaction under this discounted rate loses money. As KV caching becomes cheaper, compaction must occur earlier in an execution trajectory to justify its cache-invalidation penalty. Late-stage compaction must be justified by context window limits or attention fidelity rather than token savings. An aggressive summary that drops a key constraint and lowers acceptance erases any marginal token economy.

### Reasoning and Retry Budgets

^sec-vol3-agent-economics-reasoning-retry-budgets

Caching and compaction lower the token bill of a single trajectory; purchasing deeper internal reasoning within a call or funding multiple execution attempts instead spends extra compute to raise task acceptance. Because a configured reasoning token limit acts as an upper ceiling rather than a fixed spend, financial accounting must track actual billed token consumption and its empirical effect on acceptance under an identical evaluation contract, while weighing serial deliberation tokens against added turn latency. Deeper reasoning raises the all-in attempt cost ${c}$ by the billed price of the extra tokens and pays for itself only if it raises the per-attempt acceptance probability ${p}$ by a larger proportion, so that ${c}/{p}$ falls.

↩︎ The distinction between internal deliberation budgets and external orchestration is established in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^sec-vol3-test-time-compute-latent-vs-scaffold|Internal budgets and external orchestration]]**.

Consider a baseline model of **sequential retry** with early stopping, in which every attempt on a task has an identical acceptance probability ${p} > 0$. Conditioning on a fixed task prompt and external environment, attempts represent independent draws from the same agent configuration, each incurring an all-inclusive cost ${c}$ covering model inference, sandbox runtime, and output verification. Sequential retry terminates immediately upon the first accepted result or halts after exhausting a budget of ${k}$ attempts. The overall task acceptance probability (or coverage) is ${Q}_k = 1 - (1 - {p})^{k}$, and the expected number of executed attempts is $\sum_{j=0}^{{k}-1}(1-{p})^{j} = {Q}_k / {p}$. Dividing the expected total spend by the expected accepted tasks yields $({c} {Q}_k / {p}) / {Q}_k = {c} / {p}$. Under early stopping with independent trials, the expected cost per accepted task therefore does not depend on the attempt cap ${k}$. Raising ${k}$ expands overall task coverage, while early termination holds the average cost per successful outcome at exactly ${c} / {p}$. This is the per-attempt form of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]** with ${c}$ as the attempt cost.

In contrast, launching all ${k}$ attempts concurrently in a parallel batch costs ${k} {c} / {Q}_k$ per expected accepted task, provided the evaluation harness can identify and return an accepted candidate from the pool. These are the sequential and batch costs of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^eq-cost-per-accepted-task-iid|equation 13.6]]**, with the generation and checking charges folded into one attempt cost ${c}$. What this chapter adds is the comparison between buying more attempts from a cheap configuration and buying one attempt from a stronger one.

**Napkin Math 19.4: What a retry cap buys**

**Problem**: A lightweight agent configuration achieves an acceptance probability of 0.30 at an all-in cost of \$0.10 per attempt. A stronger configuration achieves 0.70 acceptance but costs \$0.40 per attempt. Allowing up to 5 lightweight attempts under the independent-trials model, which policy achieves the lowest cost per expected accepted task: sequential retry with early stopping, an unconditional parallel batch of 5 attempts, or a single attempt from the stronger model?

**Math**: Sequential retry achieves an expected coverage of 83.2 percent while consuming 2.773 attempts per task. This produces an expected spend of \$0.277 per submitted task and \$0.333 per accepted task. Running all 5 attempts in parallel yields identical coverage but requires \$0.500 per submitted task, increasing the cost per accepted task to \$0.601. A single invocation of the stronger model costs \$0.571 per accepted task.

**Systems insight**: Under early stopping, sequentially retrying a cheaper model outperforms a single call to a stronger model whenever ${c_{\text{small}}}/{p_{\text{small}}} < {c_{\text{big}}}/{p_{\text{big}}}$. In this scenario, sequential retry also delivers superior aggregate coverage (83.2 percent vs. 70 percent). Executing the batch concurrently secures that same coverage at a 1.8× multiplier in cost per accepted task, the ratio of ${k}$ to the expected sequential attempt count. A parallel burst is justified only when strict wall-clock deadlines assign significant value to lower latency, offsetting the substantial financial premium.

Production workloads rarely have a single, uniform success probability ${p}$. Easy tasks often pass on the first try and stop early, whereas difficult tasks maintain persistently low acceptance rates across repeated attempts. Because early stopping removes the easy tasks after one or two tries, later retry rounds are spent almost entirely on the harder tasks that remain. Substituting a single population-average success rate into $1-(1-{p})^{k}$ ignores this filtering effect and systematically overstates aggregate coverage. Because each additional retry round draws from a harder surviving pool with a lower acceptance yield, raising the retry cap also causes the realized cost per accepted task to drift above the single-attempt ratio ${c}/{p}$. Repeated-sampling studies show this effect. On benchmarks with automated verification, task coverage (the fraction of tasks solved by at least one sample) continues to climb across multiple orders of magnitude of generated samples, scaling roughly log-linearly rather than saturating as a single-parameter model would predict ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.15 Source References#^ref-brown2024monkeys|Brown et al. 2024]]). Environmental feedback, service outages, and shared mutable state further complicate fixed-probability assumptions. Engineers must therefore evaluate retry policies using outcome distributions measured per task over repeated runs.

↩︎ Per-task acceptance probabilities, and the distinction between a task and a repeated run of it, are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-resampling|Tasks and repeated runs]]**.

Generating extra candidate solutions also introduces verification risk. As analyzed in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.04 Selecting from a Candidate Pool#^sec-vol3-test-time-compute-selection-costs|Balancing pool size against checking cost]]**, repeated sampling raises the chance of a false acceptance, where a flawed candidate satisfies test assertions without truly solving the underlying task. Passing an automated check provides domain-specific verification evidence rather than an absolute guarantee of correctness. Ultimately, prefix caching, context compaction, and retry policies govern what compute resources an agent runtime purchases; determining how those purchased operations dictate end-to-end latency requires analyzing the critical execution path.
