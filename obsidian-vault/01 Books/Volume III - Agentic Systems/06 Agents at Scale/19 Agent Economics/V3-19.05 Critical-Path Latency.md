# V3-19.05 Critical-Path Latency

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19 Agent Economics|V3-19 Agent Economics]]

^sec-vol3-agent-economics-criticalpath

Accelerating a model call rarely yields a proportional reduction in end-to-end task time. In realistic agent workflows, container provisioning, repository setup, test suite execution, tool I/O, and consensus validation often dominate total elapsed time. Evaluating an acceleration technique therefore requires an end-to-end view. It must measure how much wall-clock time the proposed change strips from the critical path to a declared endpoint, what compute and memory resources it consumes, and whether the accelerated execution preserves the required acceptance evidence. Tracing exposes where time actually goes, while economic accounting determines whether accelerating that specific span is worth the operational cost.

### Dependency Graphs and Elapsed Time

^sec-vol3-agent-economics-dependency-graphs

Reading elapsed time from a distributed trace is easy to get wrong: summing an enclosing parent span’s duration with the durations of its nested children double-counts time, summing concurrent sibling spans inflates apparent latency, and omitting queueing delays, network transit, or uninstrumented runtime pauses undercounts it. When profiling an agent runtime, uninstrumented intervals must remain explicitly accounted for as unexplained gaps rather than arbitrarily attributed to neighboring components.

↩︎ The trace analysis of span nesting and the critical path is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.03 Distributed Trajectory Tracing#^sec-vol3-evaluation-tracing-latency|Span overlap and latency attribution]]**.

A span’s parent in a call tree denotes syntactic containment, which does not necessarily reflect an execution dependency. An agent runtime might spawn background log flushes or asynchronous cache warmers that outlive the caller without blocking the next step. Determining end-to-end latency requires constructing a directed acyclic execution graph based on true dispatch and join conditions. In this graph, a directed edge indicates that the successor task cannot begin until its predecessor completes. Along any path, the critical path counts only disjoint, non-overlapping intervals rather than inclusive parent spans alongside their children. Over such a graph, with vertex durations ${d}({v})$ and source-to-sink paths ${\Pi}$, the critical path is the longest path, the quantity every acceleration below is priced against:[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.16 Footnotes#^fn2|²]]

$$
{T_{\text{crit}}} = \max_{\pi \in {\Pi}} \sum_{{v} \in \pi} {d}({v}). \tag{2}
$$

^eq-vol3-critical-path

When the graph contains only mandatory computation, [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^eq-vol3-critical-path|equation 2]] establishes an idealized lower bound on completion time. The critical path matches the actual observed wall-clock interval only when the dependency graph incorporates real-world scheduling artifacts: thread scheduling delays, resource contention waits, queueing latencies, and sandbox initialization. Furthermore, the boundary of the graph depends on the system contract. Emitting an initial streamed token, evaluating a candidate patch against unit tests, and fully committing a validated pull request represent different completion endpoints, each with its own dependency sink.

A non-critical branch can shrink without moving elapsed time, and a critical one pays off only until a parallel branch becomes the longest. For pricing, the first case is not worthless, because a faster off-path branch may still free cluster capacity or reduce hosting costs. The second case means that every proposed optimization is priced against a recomputed critical path, not by subtracting isolated component savings from total elapsed time.

### The Payoff of Faster Inference

^sec-vol3-agent-economics-inference-payoff

When sandbox setup and test execution take minutes while model calls take seconds, paying a premium for faster inference barely moves completion time. Bounding the maximum possible wall-clock gain from model acceleration before buying faster serving hardware prevents teams from optimizing a tiny fraction of the critical path.

**Napkin Math 19.5: How much does faster inference buy?**

**Problem**: In a short hypothetical repair episode, far shorter than the 30-turn trajectory priced in notebook [19.2](https://mlsysbook.ai/vol3/19_agent_economics/19_agent_economics.html#nbk-18-prefix-cache-dollars), how much elapsed time does a 4× acceleration of every model call save?

**Variables**: All intervals execute sequentially, from runtime initialization through final sandbox snapshot export, without queueing, overlapping execution, or uninstrumented gaps. The durations listed in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^tbl-vol3-trace-critical-path|table 2]] represent disjoint, non-overlapping sums rather than nested spans. The proposed acceleration modifies only inference latency, leaving model outputs, tool operations, test evidence, scheduling decisions, and finalization unchanged.

| Disjoint category                            | Elapsed time |
|:---------------------------------------------|-------------:|
| All model calls in the episode               |      29.25 s |
| Required test execution                      |     245.60 s |
| Sandbox creation and snapshot export         |      37.35 s |
| Runtime initialization and repository status |       0.20 s |
| **Whole declared interval**                  | **312.40 s** |

Table 2: **One serial repair episode**: Categories partition elapsed time under the stated assumptions; the total is not an additional interval.

^tbl-vol3-trace-critical-path

**Math**: If model execution occupies fraction ${f}$ of baseline duration ${T}$ and accelerates by factor ${G_{\text{accel}}} \geq 1$, Amdahl’s law (**[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^sec-vol3-multiagent-coordination-tax|The coordination tax]]**) bounds the new duration: ${T'} = {T}[(1-{f})+{f}/{G_{\text{accel}}}]$. This is the delegation bound of **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^eq-vol3-multiagent-speedup|equation 18.1]]** with the overhead term set to zero and the worker count replaced by the acceleration factor; here the accelerated part is the model rather than the parallel work. In this episode, model work accounts for 9.4 percent of elapsed time. A 4× model acceleration reduces the episode to 290.46 s, saving 21.94 s for an overall speedup of 1.08×. Even instantaneous inference (${G_{\text{accel}}} \to \infty$) yields a whole-episode speedup of only 1.10× under these assumptions.

**Systems insight**: The theoretical speedup ceiling $1/(1-{f})$ dictates whether paying for faster model inference can ever satisfy an operational deadline. Because this ceiling depends only on baseline profile measurements, engineers can evaluate its viability before investing in model optimization or specialized serving infrastructure. In this repair episode, halving test execution duration while maintaining identical coverage saves 122.8 s, far more than the 21.94 s gained from a 4× model acceleration, and it also lowers the sandbox leasing charges in ${C_{\text{eff}}}$. When an engineering latency target exceeds what $1/(1-{f})$ can theoretically deliver, engineering effort belongs on test execution and environment lifecycle optimizations. In non-linear, branching trajectories, this principle applies directly to the recomputed critical path of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^eq-vol3-critical-path|equation 2]].

### Span Types and Their Levers

^sec-vol3-agent-economics-span-levers

Once distributed traces identify the critical path, engineers must match each bottleneck span to the physical factors governing its duration and the levers that can compress it ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^tbl-vol3-span-taxonomy|table 3]]). Buying faster token decoding when container cold starts or serial tool calls dominate the critical path spends engineering budget without moving completion time.

| Span                 | What sets its duration                         | What shortens it                                                         |
|:---------------------|:-----------------------------------------------|:-------------------------------------------------------------------------|
| Model, reading input | Context length, prefix-cache misses, queueing  | Cache-stable layout, smaller context, less queueing                      |
| Model, generating    | Output and reasoning tokens                    | Shorter outputs, smaller reasoning budget, speculative decoding          |
| Sandbox and tools    | Build size, test-suite size, cold starts       | Warm pools, snapshots, build caches, test selection, parallel tool calls |
| Network and services | Round trips, payload size, provider throttling | Response caching, prefetching, rate-limit headroom                       |
| Runtime              | Parsing, validation, logging, snapshotting     | Streaming parsers, incremental snapshots                                 |

Table 3: **Trajectory Span Types**: What bounds each kind of span on an agent’s critical path and which techniques shorten it. Each lever is admissible only if the accepted result still meets the same acceptance contract and coverage.

^tbl-vol3-span-taxonomy

When tool operations are independent, the runtime can dispatch them concurrently provided security policies, authorization boundaries, and resource reservations permit parallel execution. If three tool calls dispatch simultaneously without I/O contention and all three must complete before the agent continues, the synchronization join waits only for the longest operation rather than the sum of all three. However, concurrency gains diminish when tools contend for local resources, when dispatch is staggered, or when a downstream tool requires the output of an earlier call. In the sandbox domain, warm container pools, pre-baked filesystem snapshots, and persistent build caches shorten environment initialization spans, subject to strict isolation and teardown guarantees before each reuse.

↩︎ The reset contract that a pooled or snapshot-restored sandbox must satisfy before serving a new lease is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|The reset contract]]**.

Environment preparation can overlap model generation if the runtime executes speculative setup within a sandboxed, isolated scope that commits no external side effects before the full model response is validated and authorized. Streaming tokens from a large language model (LLM) does not constitute an authorized execution intent. Even a speculative read operation might violate an access boundary or leak uncommitted state. If the model output subsequently alters the required tool call or aborts, the runtime must discard speculative work, release allocated resources, and record any incurred compute charges in the task account.

Early stopping alters the evidentiary value of an execution as well as its duration. In a validation pipeline, a single failing assertion in a mandatory test immediately proves that a candidate solution is unacceptable, allowing the runtime to short-circuit the remaining suite. Conversely, an early pass confirms only a single check and provides zero evidence regarding the remainder of the test suite. Test prioritization and streaming failure detection thus accelerate defect rejection during intermediate iterations. However, final task acceptance still demands full test coverage across the declared verification contract. Furthermore, canceling a running check does not instantly free resources. Active worker processes must unwind cleanly, and any intermediate compute costs remain charged until the underlying jobs settle.

↩︎ Cancellation as an asynchronous control action, whose job may finish or keep running after the request and leave cleanup obligations unsettled, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.09 Asynchronous Tool Dispatch#^sec-vol3-tool-calling-async-governance|Job supervision and cancellation]]**.

### When Speculative Decoding Pays Off

^sec-vol3-agent-economics-speculative

When a draft model’s token proposals are frequently rejected by the target model, speculative decoding spends extra compute on drafting and verification while slowing generation below baseline. As the serving lever of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^tbl-vol3-span-taxonomy|table 3]] that shortens the generating span itself, speculative decoding must clear two boundaries: one inside the model call and one on the critical path. Inside the call, single-stream decoding is memory-bandwidth bound under the serving assumptions of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-per-call-work-estimate|Estimating per-call hardware work]]**, which leaves room to check several proposed tokens for roughly the price of generating one.

In speculative decoding, a lightweight draft model[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.16 Footnotes#^fn3|³]] proposes ${\gamma}$ candidate tokens per speculation round, and the larger target model verifies them in a single forward pass, accepting the longest matching prefix and generating one continuation token of its own ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.15 Source References#^ref-leviathan2023fast|Leviathan et al. 2023]]; [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.15 Source References#^ref-chen2023accelerating|C. Chen et al. 2023]]). Let the computational cost of generating one draft token equal a fraction ${\beta}$ of a standard target decoding step, and let ${\bar{m}}$ denote the mean number of draft tokens accepted per round. If evaluating ${\gamma}$ proposed tokens in parallel costs approximately one target step, each round yields ${\bar{m}} + 1$ verified tokens in the time equivalent to ${\gamma}{\beta} + 1$ target decoding steps. The resulting decoding speedup for an isolated stream is

$$
{S_{\text{spec}}}=\frac{{\bar{m}}+1}{{\gamma}{\beta}+1}. \tag{3}
$$

^eq-vol3-spec-speedup

Speculative execution accelerates the generation stream if and only if ${\bar{m}} > {\gamma}{\beta}$, that is, when the average number of accepted draft tokens exceeds the amortized drafting cost. When acceptance falls below this break-even threshold, drafting overhead accumulates faster than verification saves time, actively degrading generation latency. Furthermore, the assumption that parallel verification takes no longer than a single decoding step holds only when single-stream generation is memory-bandwidth bound (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-memory-bandwidth-decoding|2]]). As concurrent serving loads increase and large batch sizes shift accelerator utilization toward compute saturation, evaluating ${\gamma}$ tokens concurrently incurs substantial arithmetic overhead, eroding the latency advantage.

This break-even condition describes arithmetic steps within an isolated model call. Under production load, several costs erode the predicted gain. The runtime must synchronize the draft and target models and manage their KV caches. It also discards drafts when early stopping cancels generation mid-trajectory, holds the draft model in accelerator memory that could otherwise serve concurrent requests, and schedules variable-length verification batches. The condition therefore has to be confirmed under representative traffic by complete-call latency percentiles, accelerator utilization, queueing delays, and end-to-end task completion rates measured against the baseline configuration. A high token acceptance rate ${\bar{m}} / {\gamma}$ is an intermediate serving metric; it does not by itself establish a gain at the trajectory level.

On the critical path, speculative decoding shortens only the decode portion of each model call; prefill, queueing, and other call overhead join the non-model spans in the fixed part of the trajectory. Its trajectory-level effect follows from substituting the decode-stream speedup ${S_{\text{spec}}}$ for the acceleration factor ${G_{\text{accel}}}$ in the Amdahl bound of notebook [19.5](https://mlsysbook.ai/vol3/19_agent_economics/19_agent_economics.html#nbk-18-critical-path-investment). Here ${f}$ is the decode share of baseline elapsed time, so the trajectory-level speedup stays below $1/(1-{f})$. The estimate below treats the model intervals of the serial episode as pure decode, which makes it an optimistic bound.

Consider a concrete deployment scenario where the draft model proposes 5 tokens per round at a relative cost of 0.08 per token. The break-even threshold requires the mean accepted draft count to exceed 0.4 draft tokens per round. If the draft model aligns well with the agent’s prompt distribution and achieves 3.6 accepted tokens per round, [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^eq-vol3-spec-speedup|equation 3]] yields a decode-stream speedup of 3.29×. Applying this factor to the decode subtotal under the zero-nondecode approximation within the serial episode of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^tbl-vol3-trace-critical-path|table 2]] reduces total elapsed time from 312.40 s to 292.1 s, a modest 1.07× speedup for the overall episode. Conversely, if a complex reasoning task drops acceptance to 0.3 tokens per round, the system drops below break-even. Decode-stream performance then degrades to 0.93× of baseline speed, expanding total episode duration to 314.6 s. Drawn to scale, required tests and sandbox lifecycle operations form a non-model floor that no model acceleration crosses, so even instantaneous inference shortens this episode by less than a tenth ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.05 Critical-Path Latency#^fig-vol3-critical-path-waterfall|figure 2]]).

^fig-vol3-critical-path-waterfall

Accelerating a component on the critical path directly expands deadline headroom, whereas accelerating an off-critical operation primarily frees hardware capacity or lowers hosting costs. An optimization can justify higher operational expense if shaving critical-path latency satisfies a stringent user-facing service-level agreement (SLA). Conversely, an optimization that boosts raw token generation rate should be rejected if interconnect contention or server overhead erases those savings at the workflow level. Deploying speculative decoding in an agent system therefore depends on two boundaries. The serving engine must satisfy the micro-level condition ${\bar{m}} > {\gamma}{\beta}$ under realistic production concurrency. The overall agent workflow must also have a decode fraction ${f}$ large enough to make the macro-level ceiling $1/(1-{f})$ worth pursuing.

**Checkpoint 19.1: Cost and time per accepted task**

Before routing calls across models, check the account and the clock.

**Failed attempts**: A policy accepts 25 of 100 tickets. How many rejected attempts does each accepted repair pay for, and which of their charges stay in the numerator if one is canceled before its bill settles?

**Cache layout**: Which term of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.04 Context Reuse and Retry Budgets#^eq-vol3-agent-economics-session-bill|equation 1]] grows when a timestamp moves from the end of the system prompt to its front, and how does that term’s growth with the horizon change?

**Compaction payback**: With 11 calls left in notebook [19.3](https://mlsysbook.ai/vol3/19_agent_economics/19_agent_economics.html#nbk-vol3-compaction-crossing), should the runtime compact for price alone? What else could justify compacting anyway?

**Critical-path estimate**: Model calls take 9.4 percent of the serial episode. Before reading the table again, estimate the largest whole-episode speedup any model acceleration can buy, and decide whether halving the test interval would beat it.
