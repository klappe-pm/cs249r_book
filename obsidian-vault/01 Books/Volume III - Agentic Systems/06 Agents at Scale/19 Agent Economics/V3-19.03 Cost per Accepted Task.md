# V3-19.03 Cost per Accepted Task

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19 Agent Economics|V3-19 Agent Economics]]

^sec-vol3-agent-economics-accounting

Before the team can say which model repairs tickets more cheaply, it must fix what a repair is. A configuration scored against visible tests cannot be compared with one scored against a sealed suite, however carefully the invoices are tallied, because the two denominators count different things. Acceptance is defined only under an explicitly declared contract, checker, and execution environment. Isolating the effect of one policy choice (model selection, prompt construction, or tool scaffolding) therefore takes a matched comparison that holds the task contract, evaluation harness, and resource ceilings fixed while only the policy varies. The cost accounting also needs an explicit task cohort, the declared set of initiated tasks whose charges and outcomes it covers, and a cutoff timestamp. Together they decide which initiated tasks are under review, which outcomes count as accepted before the cutoff, and which operations, assessments, or invoices are still pending.

### Whole-Trajectory Cost and the Task Account

^sec-vol3-agent-economics-attempt-task-accounts

Within that boundary, an invoice that tracks only model tokens misses the container lease, test suite, cleanup job, and engineer triage that an attempt of ${H}$ turns incurs alongside inference long after the final token leaves the model server. This chapter numbers turns from one, ${t}=1,\dots,{H}$, so that the index matches the turn counts in its worked examples. The whole-trajectory cost of an attempt decomposes as

$$
{C_{\text{attempt}}} = \sum_{t=1}^{H} \left({C_{\text{in}}}^{({t})}+{C_{\text{out}}}^{({t})}+{C_{\text{tools}}}^{({t})}+{C_{\text{sandbox}}}^{({t})}\right)+{C_{\text{verify}}}+{C_{\text{cleanup}}}+{C_{\text{human}}}+{C_{\text{runtime}}}.
$$

Inside the turn loop, the input (${C_{\text{in}}}^{({t})}$) and output (${C_{\text{out}}}^{({t})}$) terms capture inference pricing under the provider’s rate card, including tiered rates and prompt-caching discounts. Tool invocation fees (${C_{\text{tools}}}^{({t})}$) cover billable external API requests and data lookups. The sandbox charge (${C_{\text{sandbox}}}^{({t})}$) prices the wall-clock lifetime of virtual machines or containers, including idle waits while external tools run. Outside the turn loop, verification (${C_{\text{verify}}}$) covers post-execution checks and test suites not already billed as sandbox time, and cleanup (${C_{\text{cleanup}}}$) pays for state reset, storage teardown, or compensating transactions. Whenever rejected attempts or policy escalations trigger human review, ${C_{\text{human}}}$ tallies manual engineering time within the declared system boundary. Runtime cost (${C_{\text{runtime}}}$) apportions orchestrator overhead, scheduler queues, and shared network telemetry. Every cost item must map to exactly one category so that an end-of-turn integration test billed as active sandbox compute time is never double-counted under verification.

**Definition 19.1: Whole-trajectory cost**

***Whole-trajectory cost*** is the total expense attributed to a single execution attempt across its model calls, environment runtime, validation assessment, and required finalization within a declared accounting boundary.

1.  **Significance**: It forms the numerator of cost per accepted task (${C_{\text{eff}}}$), capturing every cost driver that standard per-token pricing hides: container provisioning, external API calls, test-suite grading, state teardown, and human escalation. Failed attempts accumulate these charges just as successful ones do.
2.  **Distinction**: Whole-trajectory cost measures the expense of an individual attempt, whereas cost per accepted task amortizes all attempted and discarded work across the surviving accepted tasks in the cohort.
3.  **Common pitfall**: Closing the accounts the instant the agent process emits its final token, ignoring trailing cloud resources, pending cleanup jobs, or downstream engineer triage.

A single initiated task may involve multiple sequential retries or parallel delegated branches. Its **task account**, denoted ${C_{\text{task}}}$, aggregates every attempt, failed branch, and abandoned speculative execution, along with the task’s assigned share of capacity and orchestration overhead. When a sub-agent branch crashes or is canceled, its incurred costs do not vanish; they remain permanently logged against the task.

In production environments, operations are rarely settled instantly. The harness’s reservations hold part of the allowance against work that has been admitted but not yet billed. Because these funds remain committed until all external side effects resolve, any snapshot taken at an intermediate cutoff must distinguish settled expenditures from **outstanding liability**, the reserved balance backing active, unbilled operations. The settled total serves merely as a lower bound on the final task cost until all pending obligations clear.

### Cohort Cost per Accepted Task

^sec-vol3-agent-economics-cohort-ratio

Once those task accounts settle across a cohort, averaging the cost of successful tasks alone would still hide every rejected, timed-out, or canceled trajectory whose bills the surviving repairs must carry. For a finite cohort of ${N}$ initiated tasks with fully resolved accounting, let ${N_{\text{acc}}}$ represent the number of distinct tasks accepted under the declared contract. If an agent executes three successful retries on a single ticket, the system delivers exactly one accepted task; retries never inflate the denominator. For ${N_{\text{acc}}}>0$, the cohort cost per accepted task is

$$
{C_{\text{eff}}}=\frac{\sum_{i=1}^{{N}}{{C_{\text{task}}}}_i}{{N_{\text{acc}}}}.
$$

The numerator aggregates every dollar expended across all ${N}$ initiated tasks, whether they succeeded, crashed, timed out, or were rejected by validation. Keeping failed and canceled work in the numerator and pending verdicts explicit is exactly what trajectory goodput and the accepted task (principle [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/V3 Agents at Scale Principles#^pri-vol3-trajectory-goodput|15]]) demand of any account in this book. Only accepted tasks count as delivered work, and every charge incurred on the way to them stays on the bill. (This chapter defines trajectory goodput formally, as accepted tasks per unit time, when it sizes capacity in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.07 Capacity for Trajectories#^sec-vol3-agent-economics-residence-service-quota|section 19.6.1]].) If zero tasks are accepted (${N_{\text{acc}}} = 0$), the ratio is undefined. A transparent system report must then present the total expenditure and the zero count directly rather than masking the failure behind an artificial floor. Whenever tasks or invoices remain in flight at the accounting cutoff, the report must flag the cutoff timestamp and qualify the calculation as provisional. An unexecuted test suite represents a pending task, not an immediate failure, just as an asynchronous cloud billing adjustment can shift ${C_{\text{eff}}}$ hours after the code artifact is finalized.

**Definition 19.2: Cohort cost per accepted task**

***Cohort cost per accepted task*** is the total cost of every initiated task in a cohort (failed, canceled, and still-pending work included) within a declared accounting boundary, divided by the number of distinct tasks accepted under one declared contract, checker, and environment by a stated cutoff.

1.  **Significance**: It provides the empirical, measurable form of this book’s central economic metric ${C_{\text{eff}}}$. Because the count of accepted tasks divides every item in the numerator, a drop in task acceptance inflates the entire system bill, whereas a token price cut discounts only the inference fraction.
2.  **Distinction**: Whole-trajectory cost measures the expense of an isolated attempt; cohort cost per accepted task loads all failed, canceled, and abandoned attempts onto the small fraction of work that actually passes inspection.
3.  **Common pitfall**: Computing the average cost of successful trajectories alone. This survivor bias ignores the discarded attempts whose compute and environment bills must be paid by the surviving accepted tasks.

When all tasks in a cohort have reached a terminal state, the cohort acceptance rate is ${\alpha} = {N_{\text{acc}}} / {N}$. Let ${C_{\text{succ}}}$ denote the mean cost of an accepted task, and let ${C_{\text{fail}}}$ denote the mean cost of an unaccepted task (encompassing outright failures, policy cancellations, and timed-out executions). When both subsets are non-empty, partitioning the numerator yields

$$
{C_{\text{eff}}}={C_{\text{succ}}}+\frac{1-{\alpha}}{{\alpha}}{C_{\text{fail}}}.
$$

The cohort fraction ${\alpha}$ counts tasks, whereas the per-attempt acceptance probability ${p_{\text{acc}}}$ of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]** counts attempts. When every task gets exactly one attempt, the two coincide, and ${\alpha}$ estimates ${p_{\text{acc}}}$. When a task may retry, ${\alpha}$ estimates task-level coverage, the probability that some attempt on the task is accepted, while the per-attempt planning form stays $\mathbb{E}[{C_{\text{attempt}}}]/{p_{\text{acc}}}$. [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.04 Context Reuse and Retry Budgets#^sec-vol3-agent-economics-reasoning-retry-budgets|Section 19.3.3]] connects the two for sequential retry.

![[90 Assets/Volume III/19 Agent Economics/Vol3 Economics Rejected Per Accepted Margin 30f1837082.svg]]

*Curve of rejected tasks per accepted task falling steeply as acceptance rises. A red dot at low acceptance is labeled 3 and a green dot at high acceptance is labeled 0.33.*

*Each accepted task carries the rejected ones, and that load explodes as acceptance falls.*

The factor $(1-{\alpha})/{\alpha}$ represents the rejection multiplier, the number of failed tasks that each accepted task must pay for. This expression is an exact accounting identity for the cohort, not an asymptotic model or an assumption that retries will eventually converge. As the acceptance rate ${\alpha}$ falls toward zero, the multiplier grows without bound. Whether a steep discount on model tokens yields lower overall operating costs depends on both groups’ costs, which is why no universal threshold decides model selection in isolation. The concrete bug-repair scenario below prices this trade-off directly.

**Napkin Math 19.1: The token-price fallacy in automated bug repair**

**Problem:** Two hypothetical configurations each process the same 100 tickets, with one bounded attempt per ticket and the same acceptance contract. Every attempt, rejected or not, uses the fixed per-attempt usage that [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.03 Cost per Accepted Task#^tbl-vol3-token-price-fallacy|table 1]] assumes for its configuration, and all outcomes and charges are settled at the cutoff. The environment charge covers tool use, sandbox holding, and cleanup; the assessment charge covers checking not billed as sandbox time, together with allocated runtime overhead. Which configuration costs less per accepted repair?

| Parameter                             | Frontier configuration | Low-token-price configuration |
|:--------------------------------------|:-----------------------|:------------------------------|
| Input/output price per million tokens | \$3 / \$15             | \$0.30 / \$1.20               |
| Turns per attempt                     | 4                      | 7                             |
| Input/output tokens per turn          | 16,000 / 800           | 28,000 / 1,200                |
| Accepted tickets                      | 75                     | 25                            |
| Environment cost per turn             | \$0.03                 | \$0.03                        |
| Additional assessment per attempt     | \$0.05                 | \$0.05                        |

Table 1: **Illustrative Bug-Repair Cohort**: Assumed prices, usage, and accepted counts for two configurations; these are arithmetic inputs, not observed measurements.

^tbl-vol3-token-price-fallacy

**Math:** Applying the rates and usage in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.03 Cost per Accepted Task#^tbl-vol3-token-price-fallacy|table 1]] gives model charges per attempt of \$0.240 and \$0.069. Adding the other charges gives \$0.410 and \$0.329, respectively. The complete cohorts therefore cost \$41 and \$32.888. Dividing each total by its accepted count gives \$0.55 and \$1.32 per accepted repair. The lower-token-price configuration costs less per attempt but 2.4× as much per accepted task.

Now expand both accounting boundaries to include \$10 of engineer triage for each rejected attempt. The frontier configuration has 25 rejected tickets and the other has 75. Total costs become \$291 and \$782.888; costs per accepted task become \$3.88 and \$31.32, a ratio of 8.1×. Triage adds no accepted repairs; if engineers also completed tickets, that combined service would need its own named account.

**Systems insight:** With one attempt per ticket, a cheaper configuration wins only if its attempt cost falls by more than its acceptance does. Here acceptance falls by 66.7 percent, so the low-price configuration needed attempts at least that much cheaper. Its token charges fall by 71.3 percent, but its all-in attempt cost falls by only 19.8 percent, because its extra turns each pay the environment charge. Each of its accepted repairs also carries 3 rejected attempts, against 0.33 for the frontier configuration, so every charge that scales with rejections, such as triage, widens the gap.

**Systems Perspective 19.1: Reading a cost-per-accepted-task number**

The cost per accepted task is a cohort-level ratio of aggregate expenditures to accepted deliverables, evaluated at an explicit cutoff timestamp. Engineers must not confuse this ratio with the arithmetic mean of individual task expenses. In small cohorts, sample variability also prevents the ratio from serving as an unbiased estimator of the theoretical planning ratio $\mathbb{E}[{C_{\text{attempt}}}]/{p_{\text{acc}}}$. To be actionable, any reported ${C_{\text{eff}}}$ figure must be accompanied by its full context: total cohort expenditure, accepted task count with statistical confidence bounds, end-to-end latency distributions, pending execution statuses, and outstanding liabilities. An isolated efficiency number shorn of these context markers cannot support valid comparisons between competing system policies.

A rigorous matched comparison holds the acceptance contract and maximum resource allowances fixed across configurations, rather than enforcing identical expenditures. A more aggressive search policy might intentionally spend more compute per ticket to meet stringent latency deadlines or maximize task coverage, provided the underlying system objective values those gains. Inverting this metric yields **goodput per dollar** (accepted tasks delivered per unit of currency, the per-dollar counterpart of the trajectory goodput defined in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.07 Capacity for Trajectories#^sec-vol3-agent-economics-residence-service-quota|section 19.6.1]]), which keeps the same accounting boundary but reads it as throughput. In both formulations, acceptance confirms only that an artifact satisfied the automated contract within the designated test suite; it does not guarantee the complete absence of latent defects.

↩︎ Matched-budget comparison, which fixes the acceptance contract and resource envelope while each policy spends it differently, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-matched-budgets|Matched-budget comparison]]**.

Decomposing the account this way shows where a lever can act before anyone pays for it. The dominant term varies across workloads, and [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.10 Cost per Accepted Task by Archetype#^sec-vol3-agent-economics-synthesis|section 19.9]] prices all four lighthouses to show which term binds each. The levers the runtime controls most directly act on the inference term and on the number of attempts. In automated bug repair, re-sent prompt context makes up most of the inference charge, so prefix caching and context compaction act on that charge, while reasoning limits and retry budgets set how many model invocations an accepted task buys. Whether the inference term is the one worth attacking for a given workload is a separate question, and for the repair agent the answer turns out to be no.
