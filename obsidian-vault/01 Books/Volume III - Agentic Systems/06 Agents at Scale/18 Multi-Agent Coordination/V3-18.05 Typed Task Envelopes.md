# V3-18.05 Typed Task Envelopes

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination|V3-18 Multi-Agent Coordination]]

^sec-vol3-multiagent-contracts

A message asking `worker_caller_01` to “update the callers” leaves critical engineering boundaries unspecified: the target interface version, the files permitted to change, the resource budget, and the acceptance criteria for completion. If the worker fills those gaps from its own interpretation of the prompt, that interpretation becomes the de facto contract. While a workflow dependency edge dictates when a child task may begin, the task envelope defines what that child is permitted to read, modify, spend, and return. Delegation therefore requires a typed action contract (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-strict-action-abi|7]]) that extends across the agent boundary. It works much like a typed interface in a classic remote procedure call, which establishes formal argument types, return values, and failure semantics before execution begins ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-birrell1984rpc|Birrell and Nelson 1984]]).

**Definition 18.2: Typed task envelope**

A ***typed task envelope*** is a versioned assignment record binding a child task to identified inputs, a scoped authority grant, resource and lifecycle limits, completion requirements, and a bounded return format.

1.  **Significance**: The runtime validates task boundaries before admitting work and verifies returned artifacts against required evidence. In addition, capping the return payload prevents runaway worker outputs from flooding the coordinator’s context window on subsequent execution turns.
2.  **Distinction**: The envelope defines an operational, enforceable contract for execution and resources; the natural-language prompt merely describes the objective within those constraints.
3.  **Common pitfall**: Mistaking a syntactically valid envelope for proof of authorization or successful execution. Both authorization and task completion require verification against authoritative state records maintained outside the worker’s control.

### Task Assignments

^sec-vol3-multiagent-task-assignments

If a parent passes a subtask in free-form prose or embeds mutable budget numbers directly inside the child’s prompt, the child can misread its scope or rewrite its own limits. When delegating a subtask, the parent agent proposes the work, but the execution runtime authenticates the parent-child relationship, resolves the authority grant, and locks the resource reservation. In the task envelope shown in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.05 Typed Task Envelopes#^lst-vol3-task-envelope|listing 1]], field identifiers point to immutable registry records rather than embedding raw, unverified data. The referenced acceptance contract specifies expected caller behavior, exact test suite versions, the execution environment, and any required human reviews prior to final acceptance.

``` json
{
  "task_id": "worker_caller_01",
  "parent_task_id": "migration_task_01",
  "envelope_version": "caller_assignment_v1",
  "dispatch_id": "caller_dispatch_01",
  "assignment": "Update the designated authentication callers.",
  "inputs": {"base_ref": "repo_base_01"},
  "authority": {"grant_ref": "caller_private_patch_grant_01"},
  "budget": {"reservation_ref": "caller_reservation_01"},
  "completion": {
    "contract_ref": "migration_accept_v1",
    "required_evidence": [
      "candidate_ref", "write_set_ref", "dependencies_ref",
      "check_report_ref", "usage_ref", "settlement_ref"
    ]
  },
  "return_limits": {
    "receipt_bytes": 8192,
    "optional_summary_tokens": 256,
    "artifact_references": 8
  }
}
```

Listing 1: **Bounded Child Assignment**: The envelope identifies inputs, authority, resource ownership, acceptance requirements, and limits on the return.

^lst-vol3-task-envelope

In [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.05 Typed Task Envelopes#^lst-vol3-task-envelope|listing 1]], the task and dispatch identifiers tie the assignment to its durable write-ahead log intent, so that recovery can reconcile unresolved work before any permitted retry. The field `base_ref` pins the immutable repository snapshot exposed to the worker (any reads beyond that snapshot, such as queries to external package registries, require their own versioned references). Within that snapshot, `grant_ref` restricts the worker to editing designated caller files in an isolated scratch workspace, reading approved paths, and running local verification commands. The capability gate enforces parameter-level constraints on each tool invocation and explicitly withholds publication rights to shared branches. Alongside that authority grant, `reservation_ref` establishes hard limits on consumable resources, including input and output tokens as well as tool execution counts. Because the runtime resolves all three references against authoritative registry state before dispatch, a worker cannot expand its privileges or budget by modifying envelope fields in its own context.

↩︎ Durable intent, the admitted request recorded before dispatch so recovery retains its identity and can resolve an uncertain outcome, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.04 Durable Intent Before Dispatch#^sec-vol3-persistence-wal|Durable Intent Before Dispatch]]**.

The remaining two blocks in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.05 Typed Task Envelopes#^lst-vol3-task-envelope|listing 1]] govern how the child returns its work. Completion requirements name the evidence records the runtime must collect, such as candidate diffs, dependency manifests, check reports, and usage and settlement records, before the task can count as complete. Return limits cap the receipt size, optional summary tokens, and artifact references so bulky build outputs stay in external storage rather than flooding the coordinator’s context window. The receipt described next records how the child met those rules.

### Task Receipts

^sec-vol3-multiagent-task-receipts

When the child finishes or halts within those limits, the runtime packages the result into a receipt that mirrors the assignment envelope. The return payload in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.05 Typed Task Envelopes#^lst-vol3-task-receipt|listing 2]] describes a candidate change ready for integration review, one step short of an accepted modification. It strictly separates verified operational metadata from unverified model commentary. Runtime services directly populate and authenticate every field under `runtime`, whereas assertions generated by the worker model remain isolated under `worker_claims`.

``` json
{
  "task_id": "worker_caller_01",
  "envelope_version": "caller_assignment_v1",
  "dispatch_id": "caller_dispatch_01",
  "return_status": "complete",
  "runtime": {
    "status": "candidate_ready",
    "base_ref": "repo_base_01",
    "candidate_ref": "caller_candidate_01",
    "write_set_ref": "caller_writes_01",
    "dependencies_ref": "caller_dependencies_01",
    "check_report_ref": "caller_checks_01",
    "usage_ref": "caller_usage_01",
    "settlement_ref": "caller_settlement_01"
  },
  "worker_claims": {
    "summary": "Updated the designated callers for the migration."
  }
}
```

Listing 2: **Bounded Child Receipt**: Runtime records and a worker-authored explanation remain distinct; candidate readiness does not authorize publication.

^lst-vol3-task-receipt

The write-set record reflects the diff actually produced in the isolated workspace rather than the worker’s conversational recollection of what it modified. Similarly, the dependency record captures observed file reads, loaded package versions, configuration files, and external environment flags, bounded by explicit tracing coverage. The checker report records the exact candidate hash, the test command, the container environment, and the exit status. This record carries the evidence-scope rule of the tool boundary across the delegation boundary. A single call’s observation confirmed only what that call measured. A check result here establishes an outcome for one identified candidate hash, checker, and environment, and authorizes nothing beyond it. If the runtime cannot produce or verify every piece of mandatory evidence, the return status transitions to `evidence_unavailable` rather than `complete`.

↩︎ The evidence-scope rule, under which an observation confirms only what its tool measured during that invocation, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.03 Tool Subsystem Architecture#^sec-vol3-tool-calling-complete-mediation|Complete mediation]]**.

The usage record accounts for charged and reserved work across tokens, wall-clock time, and tool invocations. The settlement record distinguishes a stop acknowledgment, confirmed resource release, and unresolved background operations with retained owners. A `complete` return and the final settlement of every operation are therefore distinct statuses. This separation matters when the parent cancels an execution branch ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.08 Bounding In-Flight Work#^sec-vol3-multiagent-backpressure|section 18.7]]), ensuring that task termination does not leave orphaned background processes or dangling locks. Optional prose explanations may be shortened or omitted when space is constrained, with the omission explicitly recorded, while required identities, statuses, and evidence references pass intact. If the mandatory structural fields alone exceed `receipt_bytes`, the runtime generates an explicit payload-size failure rather than returning a truncated record.

### Reference Passing and Selective Reads

^sec-vol3-multiagent-reference-passing

Instead of inlining an entire repository tree into a child task’s context prompt, the parent passes an immutable repository reference (`base_ref`). The worker then issues targeted read queries to fetch only the source files relevant to its assignment. However, this pass-by-reference pattern yields net token savings only when the child inspects a small fraction of the code base. If the worker iteratively fetches broad directory trees, the combined cost of reference overhead, tool invocation tokens, and repeated context re-reads across turns can quickly outstrip the cost of an upfront payload. Passing a shared base reference also amortizes KV-cache prefill across parallel workers, but only when their prompt prefixes align.

↩︎ Prompt prefix alignment and KV-cache prefill amortization are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.05 Staging the Next Invocation#^sec-vol3-context-engineering-exact-prefix|Preserving an exact prefix]]**.

**Napkin Math 18.3: Price the reads after the handoff**

**Problem**: Each of 6 children receives either a 48,000-token repository slice or a 350-token reference envelope followed by 3,600 tokens of retrieved content. With all other inputs equal, no cache discount, and a hypothetical \$3 per million input tokens, how much repository-delivery input does the reference save?

**Math**: Pasting costs 6 $\times$ 48,000 $=$ 288,000 tokens, or \$0.864. The reference costs 6 $\times$ (350 $+$ 3,600) $=$ 23,700 tokens, or \$0.071, a 12.2× reduction. If every child instead reads the full slice, the reference design consumes 290,100 tokens and loses its saving.

**Systems insight**: The efficiency of reference passing depends entirely on read selectivity rather than the pointer mechanism alone. In this configuration, each child inspects only 7.5 percent of the slice, keeping reference passing economical until reads exceed 47,650 tokens. Effective multi-agent system design therefore pairs pointer handoffs with precise task scoping and indexing.

Once execution concludes, the receipt hands the parent coordinator an isolated candidate, its base version, and runtime-recorded evidence. Those records, not the absence of overlapping files, decide whether candidates can merge safely, because two patches that touch disjoint files can still break each other when integrated.
