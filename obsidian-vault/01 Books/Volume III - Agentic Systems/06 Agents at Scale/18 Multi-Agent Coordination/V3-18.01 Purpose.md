*Why can splitting a task across several agents cost more and deliver less than giving one agent the same resources?*

Splitting a task across several agents looks like the natural answer when the work is wide, since each worker can hold a smaller context and pursue its piece in parallel. The split replaces nothing the single agent already had. A capable single controller already runs searches and tests concurrently, keeps its context lean through retrieval and compaction, and holds scoped grants, so delegation must be judged against that baseline rather than against a fragile loop. What delegation adds is a set of boundaries between separately managed trajectories, and each boundary must carry explicitly what one trajectory carried implicitly. A worker can build against an interface that changes before its edit lands, two patches can merge cleanly and still break each other, reviewers that share a model can agree on the same mistake, and a canceled child can leave a container running and a budget half spent. Coordination overhead grows with every worker added, while the serial part of the task caps any speedup the parallel part can buy. Whether to split is therefore a measured decision. A multi-agent design earns its place only when it delivers more accepted tasks per unit of cost, or finishes them sooner in a way the objective values, than a single controller given the same tools and budget. Every handoff multiplies horizon, state, and authority, and the runtime must keep each delegated obligation owned until it settles.

**Learning Objectives**

- Estimate the speedup and useful worker count of a work partition from its serial fraction and coordination overhead
- Calculate makespan bounds from a task’s dependency graph to decide whether added slots or shorter tasks pay
- Design bounded receipts and credit windows that cap returned context and payload occupancy, and size mean residence under an explicit freshness policy
- Apply shared-write collision estimates to justify private workspaces and dependency revalidation before publication
- Calculate majority false approval under correlated reviewer errors to choose between more reviewers and a different check
- Evaluate fan-out completion rules and hedging under deadline, capacity, and duplicate-effect constraints
- Apply spawn limits, restart policies, attenuated grants, and atomic reservations to bound a delegation tree’s fan-out, authority, and spending
- Evaluate delegation against a capable single-controller baseline using a declared objective and matched resource ceilings
