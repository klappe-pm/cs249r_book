# V3-18.09 Capability Delegation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination|V3-18 Multi-Agent Coordination]]

^sec-vol3-multiagent-authority

Suppose `worker_caller_01`, an agent authorized only to update selected caller functions, spawns a new child task to inspect upstream source code and designates the root orchestrator as that child’s parent. If the runtime naively resolves authority from the client-supplied parent identifier, the inspection child inherits the root’s global authority, including publication credentials intended exclusively for the release integration service. The delegation tree (the supervision tree’s parent-child edges, along which grants now flow) has itself manufactured a confused deputy (definition [7.3](https://mlsysbook.ai/vol3/07_tool_calling/07_tool_calling.html#dfn-confused-deputy)). The runtime resolved authority from a name the requester supplied, the parent identifier that the child chose for itself. Similarly, two sibling workers dispatched concurrently might both observe the parent’s uncommitted budget before either issues an external call, overdrawing the task’s shared financial or token allowance. Task cancellation exposes a matching temporal hazard: a descendant grant that was perfectly valid when minted must admit no further work once the runtime revokes an ancestor in its lineage.

Scoped grants and credential brokering establish where authority resides within isolated execution environments. Multi-agent architectures extend this foundation through **attenuated delegation**: every hop down the task hierarchy passes authority no broader than the delegator’s existing authority. This model enforces the principle of least privilege ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-saltzer1975|Saltzer and Schroeder 1975]]) with capabilities (definition [8.2](https://mlsysbook.ai/vol3/08_sandboxes/08_sandboxes.html#dfn-capability)). The authority therefore travels in the reference a child holds rather than being looked up from the identity it claims, and confinement survives concurrent spending and ancestor state transitions. While a model may propose spawning a child task and suggest its scope, the runtime supervisor alone assigns the child’s identity, issues its attenuated grant, commits its resource reservation, and binds its lifecycle.

### Attenuated Grants and Split Allowances

^sec-vol3-multiagent-attenuated-grants

Passing a parent’s full credential or unreserved budget balance to a child lets a single compromised subtask modify unrelated files or spend the entire task allowance. To keep each hop narrower than the one above it, a delegation tree applies the containment relation ${\mathcal{A}}({\Gamma_{\text{child}}})\subseteq{\mathcal{A}}({\Gamma_{\text{parent}}})$ established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.05 Capabilities and Credentials#^sec-vol3-sandboxes-attenuation|Narrowing delegated authority]]** at every hop. In a multi-agent tree the relation governs concrete operations executed on underlying system resources, rather than superficial labels such as tool names or directory prefixes that an agent might attempt to manipulate. For example, an inspection child task may hold permission to inspect a specific interface file, but it must possess no rights to modify caller source files, exfiltrate repository data, or access the parent broker’s credentials for external repositories. The execution boundary enforces these perimeter restrictions directly; the child environment starts without inheriting broader host credentials or open file handles.

Runtimes can implement these bindings using either protected internal kernel handles or cryptographically verifiable bearer tokens. Chained-caveat tokens let a holder attenuate its grant locally without contacting an issuer, because each added restriction extends a keyed hash chain that the holder cannot unwind ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-birgisson2014macaroons|Birgisson et al. 2014]]). Because the runtime supervisor, never the generative model, binds the resulting capability to the specific task execution context, a compromised or malfunctioning worker cannot forge a parent lineage or substitute a token belonging to another task.

Permissions and consumable budgets require different delegation rules. Permissions are not depleted by use, so they can be shared: a parent that delegates read access retains its own ability to read. Consumable budgets, by contrast, are depletable resources that must be partitioned rather than duplicated, ensuring that each unit of currency or token quota is spent at most once. The admission control gate must therefore ensure that no unit of budget is created from nothing or spent twice anywhere in the delegation hierarchy. Before dispatching a child task, the runtime atomically reserves the child’s admitted liability against the shared allowance, accounting for all concurrent siblings and the parent’s own outstanding work. This atomic reservation prevents two sibling workers from racing to commit the same remaining balance. It is the shared-allowance rule of trajectory-level encapsulation (principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-trajectory-encapsulation|10]]) applied across a tree, under which concurrent holders reserve against one allowance and a derived allowance only narrows. If a child subsequently subdivides its allowance among its descendants, it creates a nested sub-budget that can never exceed its own allocation, not an independent pool that can be charged separately.

↪ The settlement rules developed in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.08 Spending Governance#^sec-vol3-agent-economics-budget-conservation|Budget conservation across descendants]]** decide when a delegated allocation’s unspent backing returns to the parent and count a late bill once.

### Revocation and Lineage Checks

^sec-vol3-multiagent-revocation-lineage

In a distributed multi-agent system, revocation cannot depend on promptly delivering push notifications to every running child. A robust architectural pattern assigns each task node in the runtime a monotonic generation counter and an operational state (such as active, canceled, or completed). When a grant is issued, the runtime binds it cryptographically to the complete root-to-holder lineage path, recording the exact generation counter of each ancestor at the moment of delegation. Revoking an ancestor marks that node ineligible or advances its generation counter. Node restarts must monotonically advance or preserve generation counters rather than resetting to zero, which would inadvertently revive expired or revoked grants.

When an agent submits an operation to the API gateway, the admission check verifies the grant’s cryptographic integrity, scope, and expiration while querying the current lifecycle status and generation of every ancestor in the bound lineage path. If any ancestor has been canceled or its generation has advanced, the gateway rejects the descendant’s request immediately, even if the leaf worker has not yet received a cancellation signal and still considers itself active. Traversing a lineage path of depth $\ell$ requires $\mathcal{O}(\ell)$ ancestor lookups at admission time, whereas advancing an ancestor’s generation number invalidates the entire subtree of descendant grants in $\mathcal{O}(1)$ time without rewriting individual token payloads. Gateway caches or indexed summaries can shorten those admission lookups at the cost of cache-invalidation rules, and [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.09 Capability Delegation#^tbl-vol3-gateway-epoch-table|table 8]] traces how the check behaves across `migration_task_01` without assuming that cancellation messages arrive everywhere at once.

| Situation                                                   | What the admission authority knows                               | Consequence                                                                                                                         |
|:------------------------------------------------------------|:-----------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------|
| A worker proposes an operation before cancellation          | Bound lineage generations match and ancestor tasks remain active | Continue checking operation scope, resource conditions, expiry, and budget; lineage validity alone does not authorize the operation |
| The root cancellation is committed before a later admission | The root is ineligible or its generation differs from the grant  | Reject the descendant request even if the worker has not received its cancellation message                                          |
| A remote gateway cannot establish current ancestor state    | A cached record may predate cancellation                         | Withhold admission under the strict freshness policy; do not claim current authorization from the old record                        |
| An external operation was admitted before cancellation      | Its outcome is still unresolved                                  | Retain operation identity and settlement ownership; rejecting later requests does not undo the earlier effect                       |

Table 8: **Lineage checks across cancellation**: The authority decision depends on current ancestor state and the order of admission, not on whether a child has acknowledged a message.

^tbl-vol3-gateway-epoch-table

Enforcing cancellation semantics requires an unambiguous, linearizable ordering point. Under a strict freshness policy, revocation updates and admission checks share an authoritative global order: once a revocation is committed, no subsequent admission check within that scope may evaluate against stale policy state. Because local signature verification and expiry checks establish only that a grant was valid when issued, a replicated gateway that cannot verify current ancestor state must fail closed, withholding admission from new operations.

Alternatively, systems that prioritize availability over strict consistency may permit distributed gateways to evaluate requests against cached ancestor state for a declared interval. This engineering trade-off introduces a **stale-policy window**, the bounded interval in which an already-revoked grant may still be accepted by an out-of-date gateway. The system designer must explicitly bound this window to account for cache invalidation propagation, token refresh intervals, clock skew assumptions, and network partition timeouts. Furthermore, revocation must actively sever all mediation pathways, including revoking open writable file handles held by running processes. Any operations already admitted to external systems prior to revocation remain governed by transactional settlement rules.

### Approval Requests and Operation Binding

^sec-vol3-multiagent-approval-binding

During execution, a worker may discover that completing its objective requires an operation that exceeds its delegated authority. Rather than terminating or attempting privilege escalation, the worker submits an authorization request. An approval binds to the exact operation it authorizes, never to a model’s explanation of it (**[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.08 Delegated Identity and Credential Brokering#^sec-vol3-security-action-bound-approval|Action-bound approval]]**), and the runtime recomputes that binding and rechecks its preconditions at dispatch (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.08 Approval Gates#^sec-vol3-agent-harness-dispatch-rechecks|Dispatch-time rechecks]]**). For a delegated publication, the bound operation names the originating task (`migration_task_01`), the content hash of the candidate artifact, the destination reference, and its base-version preconditions, so a candidate altered by a single byte after approval needs a fresh decision.

Delegation changes where the request goes and what the recheck must cover. The worker cannot widen its own grant, and attenuation forbids its parent from granting more than the parent holds. The runtime therefore collects such requests in a bounded approval queue, deduplicates repeated submissions from siblings, and routes each to the task owner rather than to an intermediate parent whose own grant could not cover the operation. Any rationale a root or worker model attaches remains unverified commentary. At dispatch, the recheck extends from the operation to its lineage: current grants, every ancestor’s lineage generation, and the remaining budget must still permit the action, so an ancestor cancellation committed after approval blocks it as surely as a changed candidate does. Passing validation tests in `migration_accept_v1`, obtaining operator approval, and executing the privileged publication remain three distinct, non-fungible events.

**Checkpoint 18.3: Bounding work, authority, and spending after a split**

**Cancellation scope**: The supervisor cancels `migration_task_01` after the gateway admitted `worker_interface_01`’s test operation but before its reply arrives. Which statements can the runtime make truthfully now, and which must wait for further evidence?

**Barrier vs. quorum**: At a per-worker on-time probability of 90 percent, why can a 6-of-8 stopping rule rescue a read-only analysis but not the two-part migration?

**Hedging a mutation**: Why is a hedged copy of a mutating tool call a retry before settlement, and what must both attempts share before the runtime may issue it?

**Credit window**: The reviewer drains 0.08 items per second. What window keeps the modeled mean residence under one minute, and which messages must travel outside the data credits?

**Joint allowances and revocation**: Two siblings each receive less than the parent’s remaining allowance. What must the runtime do so they cannot jointly overdraw it, and what happens at a remote gateway that cannot confirm an ancestor’s current generation?

Delegation controls conserve authority and spending, distinguish cancellation from completed cleanup, and separate administrative approval from verified success. These safeguards make task decomposition governable. Whether splitting a task across multiple agents is actually useful, however, remains a separate empirical question, answerable only by measurement against a strong single-agent baseline.
