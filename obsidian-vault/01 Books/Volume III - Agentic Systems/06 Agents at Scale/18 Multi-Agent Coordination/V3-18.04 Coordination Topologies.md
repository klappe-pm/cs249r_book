# V3-18.04 Coordination Topologies

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination|V3-18 Multi-Agent Coordination]]

^sec-vol3-multiagent-topologies

In the authentication migration (`migration_task_01`), the interface worker and the caller worker can inspect the baseline snapshot (`repo_base_01`) in parallel, yet the caller’s patch still depends on the interface definitions that its peer is actively modifying. Routing both workers through a single supervisor does not eliminate that underlying causal dependency. A runtime architecture that naively treats the supervisor’s message-routing graph as the true dependency graph will prematurely accept and publish a caller patch built on stale interface assumptions.

To build reliable multi-agent systems, engineers must distinguish three separate structural graphs that govern execution:

1.  The **dependency graph** defines causal precedence by recording which artifacts, decisions, or validation checks must complete before downstream work can safely proceed.
2.  The **communication topology** defines the network paths, protocols, and message envelopes through which agents exchange information.
3.  The **supervision tree** defines operational ownership over agent lifecycles, governing fault isolation, resource reservations, and cancellation cascades.

Because a supervisor frequently manages children whose outputs depend causally on one another, runtime engines must maintain these three structures independently. Conflating message delivery with causal dependency or lifecycle ownership leads directly to race conditions, orphaned processes, and corrupted state.

### Coordination Arrangements

^sec-vol3-multiagent-arrangements

When `migration_task_01` splits work across agents, the runtime must decide whether subtasks and candidate artifacts pass through a central coordinator, stream along staged queues, land in a shared store, or route directly between peer workers ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^tbl-vol3-topologies-comparison|table 2]]). The most prevalent pattern is the **supervisor-worker** topology (frequently termed orchestrator-worker). In this model, a centralized coordinator decomposes an incoming task, dispatches subtasks to subordinate workers, and synthesizes their returned receipts. This design directly mirrors the contract net protocol[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.16 Footnotes#^fn2|²]] originally developed for distributed problem solving ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-smith1980contract|Smith 1980]]). In production systems, these foundational topologies frequently compose. For example, a supervisor might dispatch parallel analytical investigations, stream their candidate patches through a staged validation pipeline, and persist intermediate progress within a shared task store.

| Arrangement       | How work crosses a boundary                                                           | Useful when                                                              | Obligation that remains                                              |
|:------------------|:--------------------------------------------------------------------------------------|:-------------------------------------------------------------------------|:---------------------------------------------------------------------|
| Supervisor–worker | A coordinator assigns subtasks and collects bounded receipts                          | A task has separable investigations and an explicit integration decision | Bound dispatch, returned context, and the coordinator’s own work     |
| Pipeline          | Each stage receives the artifacts and evidence its predecessor is required to provide | Later work depends on a sequence of transformations or checks            | Preserve stage preconditions and bound queues between stages         |
| Shared blackboard | Workers claim tasks and publish versioned artifacts through a shared store            | Different workers can contribute as dependencies become available        | Enforce claim ownership, publication rules, and dependency validity  |
| Actor messaging   | Workers hold local state and exchange addressed messages                              | Responsibilities require ongoing asynchronous interactions               | Define delivery, duplicate handling, ordering, and bounded mailboxes |

Table 2: **Coordination arrangements and runtime obligations**: While routing patterns structure message handoffs, the execution runtime must enforce result validity, resource boundaries, and state consistency across agent boundaries.

^tbl-vol3-topologies-comparison

Each coordination topology makes different trade-offs regarding where state accumulates and where synchronization occurs. A supervisor concentrates integration logic and validation evidence at a single coordinator, requiring compact, structured receipts to prevent prompt context exhaustion. A pipeline structures execution as a sequence of discrete transformations, keeping each stage’s working context tightly focused while streaming items concurrently across stages. By contrast, a shared blackboard[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.16 Footnotes#^fn3|³]] decouples agents entirely by externalizing coordination into a centralized artifact and task store ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-erman1980hearsay|Erman et al. 1980]]). In an actor architecture, originally formulated by Hewitt, Bishop, and Steiger, agents maintain completely isolated private state and communicate exclusively via asynchronous message passing to explicit addresses ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-hewitt1973actor|Hewitt et al. 1973]]). Both blackboards and actor meshes shift the coordination burden toward explicit conflict resolution, distributed ordering, and bounded mailbox management.

Message counts scale with the communication graph and its interaction protocol. If each of ${N_{\text{workers}}}$ participants transmits an update to every other participant during an execution round, the network must handle ${N_{\text{workers}}}({N_{\text{workers}}}-1)$ directed deliveries. With an average payload size of ${L}$ tokens per delivery, that single round consumes ${N_{\text{workers}}}({N_{\text{workers}}}-1){L}$ tokens across the system. In contrast, a supervisor managing ${N_{\text{workers}}}$ workers requires only $2{N_{\text{workers}}}$ deliveries per round (one dispatch envelope and one receipt per worker), consuming $2{N_{\text{workers}}}{}{L}$ tokens. The full mesh thus scales quadratically, transmitting $({N_{\text{workers}}}-1)/2$ times more messages per round than the centralized coordinator.

Raw transmission volume measures network traffic, not what the receiving models must ingest. In a fully connected mesh where each agent appends every incoming peer message to its prompt history, ingested tokens per round grow as $\mathcal{O}({N_{\text{workers}}}^2)$. The append-only re-send of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 2.9]]** compounds that growth across rounds, because each later prompt carries every earlier delivery. Even in a centralized topology, verbose receipts, iterative deliberation rounds, or frequent status polling against a blackboard store can exhaust context windows and inflate inference budgets. Across the four arrangements of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^fig-vol3-multi-agent-topologies|figure 1]], the supervisor’s round costs $2{N_{\text{workers}}}$ deliveries and the actor mesh up to ${N_{\text{workers}}}({N_{\text{workers}}}-1)$, while the pipeline and blackboard replace direct deliveries with bounded queues and versioned claims that the runtime must police. An arrangement therefore keeps context windows bounded only when each handoff carries the specific inputs and checks a subtask requires, and deciding when those handoffs may fire belongs to the dependency graph.

![[90 Assets/Volume III/18 Multi Agent/Coordination Topologies 66e5680e36.svg]]

Figure 1: **Four Coordination Arrangements**: Each panel shows where work crosses a boundary. A supervisor sends envelopes down and collects receipts, a pipeline passes artifacts through bounded queues, a blackboard mediates claims and versioned publications through a shared store, and actors exchange addressed messages through mailboxes. One supervisor round costs $2{N_{\text{workers}}}$ deliveries and a full mesh round ${N_{\text{workers}}}({N_{\text{workers}}}-1)$. Each topology imposes specific runtime obligations for bounding queues, isolating concurrent state, and verifying result correctness.

### Dependency Graphs and Concurrency

^sec-vol3-multiagent-dependency-graphs

Dispatching subtasks before their prerequisites are verified wastes tokens on stale assumptions or stalls worker slots behind unfinished upstream steps. To schedule concurrent work safely, the runtime models task precedence as a directed acyclic graph (DAG), $({V},{E})$. Each vertex ${v} \in {V}$ represents a bounded unit of execution, either an autonomous agent trajectory or a deterministic runtime validation check. A directed edge $({u},{v}) \in {E}$ indicates that vertex ${v}$ requires a declared precondition satisfied by vertex ${u}$, such as an emitted code artifact, a validated test report, or an explicit authorization token. A status message signaling task completion satisfies an incoming edge only when accompanied by verifiable output receipts.

A vertex becomes **dependency-ready** once every prerequisite predecessor condition has been verified. Dependency readiness alone does not trigger execution, however. The runtime dispatcher must additionally verify execution authority, allocate an active worker slot, and secure a bounded token and financial budget reservation. If a predecessor fails or emits invalid artifacts, the control plane either halts downstream successors or transitions execution to an explicit recovery branch. Loops and iterative refinement cycles enter the graph as unrolled, bounded attempts. Because graph acyclicity guarantees only the absence of logical dependency loops, the underlying runtime remains responsible for detecting dynamic deadlocks arising from shared resource locks, exhausted thread pools, or saturated queues.

To estimate the theoretical limits of parallel scheduling, assume each vertex ${v}$ occupies one interchangeable worker slot for a fixed duration ${d}({v})$, encompassing both model inference latency and external tool execution. Let ${N_{\text{workers}}}$ represent the pool of available parallel worker slots. Under these assumptions, aggregate slot-work ${W}$ totals every vertex’s duration, and critical-path duration ${T_{\text{crit}}}$ is the length of the longest dependency chain, the same critical path that trace analysis measures from recorded spans, here computed from assumed durations:

$$
{W}=\sum_{{v}\in {V}}{d}({v}),\qquad {T_{\text{crit}}}=\max_{\pi\in\operatorname{Paths}({V},{E})}\sum_{{v}\in\pi}{d}({v}). \tag{2}
$$

^eq-vol3-multiagent-dag-work

Any valid schedule’s total makespan ${T_{\text{finish}}}$ must satisfy the dual lower bounds

$$
{T_{\text{finish}}}\ge\max\left(\frac{{W}}{{N_{\text{workers}}}},{T_{\text{crit}}}\right). \tag{3}
$$

^eq-vol3-multiagent-dag-bound

The aggregate work bound ${W}/{N_{\text{workers}}}$ reflects the capacity constraint, since ${N_{\text{workers}}}$ parallel worker slots cannot complete ${W}$ total units of execution time in less than ${W}/{N_{\text{workers}}}$, regardless of schedule structure. The critical-path bound ${T_{\text{crit}}}$ reflects the causal precedence constraint, since sequential dependencies cannot be parallelized, and it establishes a lower bound on latency even with infinite worker slots.[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.16 Footnotes#^fn4|⁴]] In production environments, resource contention, queuing overhead, payload serialization, and trajectory retries expand the overall makespan well beyond these theoretical minimums unless explicitly incorporated into vertex durations ${d}({v})$ and graph edges.

↩︎ Trace-based measurement of the critical path is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.03 Distributed Trajectory Tracing#^sec-vol3-evaluation-tracing-latency|Span overlap and latency attribution]]**.

**Napkin Math 18.2: DAG scheduling in multi-agent execution**

**Problem**: Consider an illustrative repository upgrade with 4 worker slots. [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^tbl-vol3-multiagent-dag-schedule|Table 3]] gives assumed durations for a single successful execution of each node. Each node occupies one slot; there are no additional dispatch delays, resource conflicts, retries, or transfer costs. How much can overlap?

| Work                                                  | Required predecessors | Slot duration | Earliest start | Earliest finish |
|:------------------------------------------------------|:----------------------|:--------------|:---------------|:----------------|
| ${v}_1$: prepare shared specification                 | None                  | 20.5 s        | 0 s            | 20.5 s          |
| ${v}_2,{v}_3,{v}_4$: refactor separate modules        | ${v}_1$, for each     | 42 s each     | 20.5 s         | 62.5 s          |
| ${v}_5$: assess the joint changes from two modules    | ${v}_2,{v}_3$         | 43 s          | 62.5 s         | 105.5 s         |
| ${v}_6$: prepare bindings for the remaining module    | ${v}_4$               | 16.5 s        | 62.5 s         | 79 s            |
| ${v}_7$: integrate and run required regression checks | ${v}_5,{v}_6$         | 69 s          | 105.5 s        | 174.5 s         |

Table 3: **An idealized dependency schedule**: Starts are the latest finish among required predecessors. The schedule assumes that each predecessor supplies the result required by its successor.

^tbl-vol3-multiagent-dag-schedule

**Math**: Summing the node durations as in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^eq-vol3-multiagent-dag-work|equation 2]] gives 275 s of aggregate slot-work. Dividing by the slot count gives the work term in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^eq-vol3-multiagent-dag-bound|equation 3]], 68.75 s. The paths ${v}_1\to {v}_2\to {v}_5\to {v}_7$ and ${v}_1\to {v}_3\to {v}_5\to {v}_7$ tie for the critical path. The table’s schedule uses at most 3 slots, so it is feasible under the stated capacity and attains the path bound.

**Result**: Completion takes 174.5 s, a 1.58× speedup over executing these same nodes serially, and more slots cannot shorten the remaining chain.

**Systems insight**: Once a schedule attains the critical-path bound, as this one does, allocating worker slots beyond peak concurrency yields zero latency improvement. The off-critical branch through ${v}_4$ and ${v}_6$ finishes 26.5 s before ${v}_7$ can start, meaning optimizations on that branch do not affect overall makespan. In contrast, shortening ${v}_5$ or ${v}_7$ yields a direct second-for-second reduction in total makespan up to the available slack. Shortening ${v}_2$ in isolation provides no benefit because ${v}_3$ ties it on the critical path. Analyzing production agent traces requires distinguishing a dependency-limited schedule like this one from a capacity-limited schedule, where additional slots or reduced contention can still shorten makespan.

### Static Plans and Dynamic Spawning

^sec-vol3-multiagent-static-dynamic

When a coordinator fixes every subtask before execution begins, workers cannot branch when they uncover an undocumented dependency. Conversely, letting a model spawn children at will can turn a simple query into dozens of redundant trajectories. A **static plan** resolves this trade-off toward predictability by specifying its stages, conditional branches, validation checkpoints, and retry bounds ahead of execution. Because all artifact dependencies and message routes are declared upfront, operators can inspect handoffs statically and verify safety invariants before dispatch. With enforced per-node work limits, bounded attempts, and stated service or deadline assumptions, the declared graph supports worst-case resource and execution bounds. A termination deadline does not guarantee accepted completion or immediate settlement of external work.

In contrast, **dynamic spawning** provisions child agents at runtime in response to intermediate observations. For example, during a repository migration, a worker analyzing call sites might uncover an undocumented dependency and request an isolated sub-investigation. While the model proposes this subtask dynamically, the runtime control plane must evaluate and admit it under the prevailing task contract. Dynamic spawning allows systems to adapt flexibly to open-ended workloads, but it introduces non-deterministic execution graphs. When an unconstrained model decides how many child agents to spawn and when to spawn them, combinatorial fan-out can quickly overwhelm system capacity and inflate execution costs.

**War Story 18.1: Unbounded fan-out in a multi-agent research system (2025)**

**Context**: Anthropic’s engineering team described building an autonomous research system where a lead orchestrator plans an investigation, spawns parallel subagents to search for evidence, and synthesizes their findings ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-anthropic2025multiagent|Hadfield et al. 2025]]).

**Mechanism**: The lead agent possessed unconstrained authority to determine subagent fan-out. In early prototype versions, the model routinely spawned 50 subagents even for simple queries, searched endlessly for nonexistent sources, and allowed subagents to degrade coordination by flooding one another with excessive updates.

**Impact**: The engineering team reports that autonomous agents typically consume about 4× more tokens than standard conversational interactions, while multi-agent systems consume roughly 15× more. Although the multi-agent configuration outperformed a single agent by 90.2 percent on the team’s internal research evaluation, the unconstrained fan-out incurred disproportionate resource expenditure on straightforward tasks.

**Fix**: The team embedded explicit scaling heuristics into the orchestrator’s prompt, instructing the model to calibrate subagent allocation to query complexity, allocating a single agent for direct fact retrieval and scaling upward only for open-ended synthesis. Furthermore, the orchestrator was structured to wait synchronously for each dispatched subagent batch to conclude before initiating subsequent steps, simplifying state synchronization at the cost of pipeline parallelism.

**Systems lesson**: Dynamic fan-out is an architectural resource-allocation problem that cannot rely on model self-restraint alone. While prompt-based heuristics guide model proposals, the runtime control plane must enforce hard admission limits on tree breadth, recursion depth, and aggregate budget reservations. These limits directly bound the token consumption in the effective cost metric ${C_{\text{eff}}}$.

Uncontrolled fan-out illustrates the necessity of formal admission control in multi-agent architectures. Prompt instructions alone cannot curb subtask generation, because an unconstrained model can still propose redundant branches or trigger cascading worker requests. Allocating each child a budget fraction smaller than the parent’s remaining funds also fails to protect the system, as a burst of concurrent siblings can issue overlapping claims that collectively exceed available capacity. The runtime admission controller must atomically reserve each child’s maximum potential liability against the shared task budget before dispatching execution, an invariant that [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.09 Capability Delegation#^sec-vol3-multiagent-authority|section 18.8]] formalizes across hierarchical delegation trees. Production runtimes must independently enforce four distinct bounds: fan-out breadth (maximum children per parent), concurrent active slots (maximum parallel executions), recursion depth (maximum delegation layers), and absolute deadlines. A shallow tree can still exhaust resources through excessive breadth, while a strict concurrency cap can still permit an unbounded sequence of sequential worker allocations.

↩︎ Bounded-liability admission, which reserves an operation’s maximum charge before admitting it, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.10 Budgets and Ceilings#^sec-vol3-agent-harness-reservation-settlement|Reservation and settlement]]**.

### Supervision Trees

^sec-vol3-multiagent-supervision-trees

Beyond resource management, dispatching a child agent establishes lifecycle ownership. A child’s running trajectory, pending tool invocations, and uncommitted side effects typically outlive the ephemeral model call that spawned it. The supervision tree defines how the runtime isolates faults and manages recovery when a child encounters an unrecoverable failure. Following the supervision trees of Erlang/OTP (Open Telecom Platform),[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.16 Footnotes#^fn5|⁵]] systems formalize recovery through explicit, per-supervisor restart strategies ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-armstrong2003making|Armstrong 2003]], [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-armstrong2007erlang|2007]]):

- Under a `one_for_one` policy, the supervisor restarts only the failed child agent while allowing sibling workers to continue uninterrupted. This strategy is ideal for embarrassingly parallel or loosely coupled subtasks, such as searching disjoint documentation sources, where workers share no mutable intermediate state.
- Under a `one_for_all` policy, the failure of any single child triggers the supervisor to terminate and restart all sibling workers within that supervision group. This approach is needed for tightly coupled collaborative tasks where partial artifacts become invalid upon peer failure. For example, if an interface worker crashes and restarts with an altered API contract, any partial implementation generated by a concurrent caller worker is invalidated.

The two policies differ in blast radius ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^fig-vol3-supervisor-tree-isolation|figure 2]]): one failure under `one_for_one` costs a single fresh attempt and its reservation, whereas under `one_for_all` it discards the progress of every coupled sibling and restarts the whole group from recorded inputs. To prevent degenerate retry storms under either policy, supervision trees enforce a **restart intensity** bound, the maximum number of restarts permitted within a sliding time window. When a child agent repeatedly fails and breaches this threshold, the supervisor ceases local restarts, aborts its remaining subordinates, and escalates the failure upward to its own parent supervisor. In an agentic system, a restart must never continue from the failed worker’s corrupted or circular context window. Instead, the runtime treats each restart as a freshly admitted attempt. It provisions a clean context initialized from recorded input artifacts and acquires a fresh budget reservation. Whenever it aborts sibling processes under `one_for_all` or escalation, it also invokes the structured cancellation and cleanup protocols of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.08 Bounding In-Flight Work#^sec-vol3-multiagent-backpressure|section 18.7]].

![[90 Assets/Volume III/18 Multi Agent/Supervisor Tree Isolation f705b865b5.svg]]

Figure 2: **Restart Policies in a Supervision Tree**: Under the one-for-one policy (a), only the failed worker restarts, as a newly admitted attempt with its own reservation, while its siblings continue. Under the one-for-all policy (b), the supervisor stops the coupled siblings through the cancellation protocol and restarts the whole group from recorded inputs, because the caller’s partial work has lost its meaning. Either supervisor that exceeds its declared restart intensity stops restarting and escalates the failure to its parent.

**Checkpoint 18.1: Evaluating multi-agent coordination topologies**

**Dependency vs. routing**: The interface and caller workers communicate only through their supervisor. Why can they still produce interdependent patches, and which of the three structures records that?

**Critical-path estimate**: Using the durations in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^tbl-vol3-multiagent-dag-schedule|table 3]], estimate how much completion changes if ${v}_6$ is removed entirely, and how much if ${v}_5$ takes 20 s less. Which node should an engineering team speed up?

**Worker-count screen**: With ${f_{\text{parallel}}}=0.9$ and the notebook’s overhead ${\gamma}=$ 0.02 per extra worker, estimate the best worker count from $\sqrt{{f_{\text{parallel}}}/{\gamma}}$ and the speedup ceiling $1/(1-{f_{\text{parallel}}})$. Is it worth halving ${\gamma}$ or halving $1-{f_{\text{parallel}}}$?

**Aggregate admission**: Why can granting every child less than its parent’s remaining budget still oversubscribe the task? What must happen atomically?

A coordination topology fixes how work, messages, and lifecycle ownership cross agent boundaries, but routing and supervision alone do not specify what a child is allowed to do once it starts. Without an explicit contract on each handoff, a worker can still read stale inputs, touch files outside its scope, or return a long narrative in place of verifiable evidence. Every boundary crossing therefore requires a formal task envelope that states what artifacts the worker receives, what tools and tokens it may consume, and what typed receipt it must return.
