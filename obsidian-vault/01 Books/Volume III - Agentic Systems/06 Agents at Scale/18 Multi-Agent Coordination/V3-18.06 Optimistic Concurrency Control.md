# V3-18.06 Optimistic Concurrency Control

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination|V3-18 Multi-Agent Coordination]]

^sec-vol3-multiagent-concurrency

In `migration_task_01`, both `worker_interface_01` and `worker_caller_01` branch from the same baseline commit, `repo_base_01`, to edit their respective files. When the interface worker finishes first, the integration service accepts its patch as `repo_head_02`. Because the caller worker modifies a different file, a standard three-way textual merge succeeds cleanly without merge conflicts. The caller’s patch, however, still targets the obsolete interface. Modifying separate files prevented a textual collision, but it left the semantic dependency behind the caller’s code unchecked.

**Optimistic concurrency control (OCC)** resolves this tension by letting each agent work privately against a snapshot and validating every publication prerequisite before the shared branch changes ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-kung1981optimistic|Kung and Robinson 1981]]). A transaction runs a read phase against private copies, a validation phase that checks whether concurrent commits invalidated anything it read, and a write phase that commits only after validation succeeds. The expected-version check at the tool boundary is that validation applied to a single file. The scheme pays when conflicts are rare, because it trades lock waiting for occasional discarded work. A worker’s read phase, however, spans minutes of model generation and tool execution rather than the brief life of a database transaction, so a failed validation discards real inference spend. Its prerequisites include dependency freshness and acceptance evidence as well as unchanged files. Instead of holding a repository lock while an agent deliberates, the runtime decouples private execution from integration, which exposes parallelism and converts conflicts into the coordination tax of candidate revalidation and occasional discarded work.

↩︎ Conditional updates that commit only while the target still matches its expected version are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.04 Tool Interface Schemas#^sec-vol3-tool-calling-conditional-updates|Conditional updates]]**.

### Shared Workspace Hazards

^sec-vol3-multiagent-workspace-hazards

Operating multiple agents within a single shared working directory introduces three immediate failure modes. A **lost update** occurs when two workers inspect the same file, deliberate over multiple inference turns, and serialize their writes back to disk. The later write silently replaces the earlier contribution, and the operating system reports no error because both writes were valid. A **torn dependency read** emerges when an agent executes tests while a peer is actively modifying related files, for example by evaluating code after a new interface has landed but before the caller has been updated. The test runner executes against an incoherent intermediate state that no agent ever intended to propose. Finally, *tool-lock contention* strikes when concurrent build tools or version-control commands collide on local metadata locks, such as Git’s `.git/index.lock`. One worker crashes on a locked index even when the underlying edits target entirely disjoint directories.

![[90 Assets/Volume III/18 Multi Agent/Vol3 Multi Agent Write Collision 818b2eeed6.svg]]

*A rising S-shaped curve of shared-write probability against fleet size from 1 to 16 workers, crossing a dashed even-odds line, with a red dot labeled 5 workers.*

*Shared writes pass even odds at five workers, long before a fleet feels large.*

These collisions manifest surprisingly early as agent concurrency grows. Suppose a repository contains ${n}$ files and each of ${N_{\text{workers}}}$ workers modifies ${w}$ distinct files, chosen uniformly and independently at random. Worker ${k}+1$ avoids overlapping with all preceding workers only if it selects its ${w}$ files exclusively from the ${n}-{k} {w}$ files that earlier workers left untouched. The probability that all ${N_{\text{workers}}}$ write sets remain pairwise disjoint is therefore

$$
\Pr(\text{no shared write})=\prod_{k=1}^{{N_{\text{workers}}}-1}\frac{\binom{{n}-{k} {w}}{{w}}}{\binom{{n}}{{w}}}\approx\exp\left(-\frac{{N_{\text{workers}}}({N_{\text{workers}}}-1){w}^2}{2{n}}\right). \tag{4}
$$

^eq-vol3-multiagent-write-collision

[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.06 Optimistic Concurrency Control#^eq-vol3-multiagent-write-collision|Equation 4]] is the birthday bound[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.16 Footnotes#^fn6|⁶]] generalized to multi-file write sets. When ${w}$ is small relative to ${n}$, each of the ${N_{\text{workers}}}({N_{\text{workers}}}-1)/2$ worker pairs compares ${w}^2$ file choices against the ${n}$ repository files, so the exponent grows quadratically with both the worker count ${N_{\text{workers}}}$ and the write-set size ${w}$. Because the exponent scales with the number of worker pairs rather than linearly with the worker count, collision odds mount rapidly. In a hypothetical repository of 1,000 files where each worker touches 10 files, even 2 concurrent workers collide with probability 9.6 percent. At 5 workers, a write collision becomes more likely than not, and scaling to 8 workers drives the collision probability to 94.4 percent. In practice, uniform random access is an illustrative baseline that can understate risk when writes cluster. Actual agent modifications heavily cluster around package manifests, central routing tables, and shared configuration files. Rigorous workspace isolation is therefore an architectural prerequisite for multi-agent coordination, rather than a performance tuning knob reserved for large worker pools.

Providing each worker with an isolated workspace establishes a stable snapshot baseline and an unshared scratchpad for local modifications. When a worker finishes, the runtime therefore receives an immutable candidate artifact (identified by a cryptographic commit hash) rather than a reference to a mutable filesystem directory. Runtimes implement this isolation through two main mechanisms. Linked Git worktrees allocate a dedicated working tree, index, and `HEAD` pointer for each agent while sharing underlying object storage in `.git/objects`. Copy-on-write filesystems provide block-level cloning and zero-copy snapshots governed by runtime pooling lifecycles and reset contracts.

↩︎ Copy-on-write provisioning, which copies only what a task writes over a read-only base, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.07 The Agent Workspace#^sec-vol3-sandboxes-cow-provisioning|Copy-on-write provisioning]]**.

Neither filesystem mechanism provides security on its own. If an agent executes arbitrary shell commands with unrestricted filesystem permissions, it can traverse parent directories, access peer worktrees, or corrupt the shared Git directory. A robust architecture therefore pairs workspace isolation with an external sandbox and a mediated tool gateway. The gateway confines filesystem writes to the assigned worktree, strips integration credentials, and allocates ephemeral ports and temporary directories for test suites. Furthermore, discarding a worktree cleanly recycles local ephemeral state, but it cannot revoke side effects that an external service has already accepted.

### Dependency Validation at Integration

^sec-vol3-multiagent-dependency-validation

When a worker signals completion, the centralized integration service evaluates the returned execution receipt. The service resolves `runtime.base_ref` and `runtime.candidate_ref`, verifies cryptographic commit lineage, and independently derives the modified file paths rather than trusting a worker-reported write set. Beyond commit hashes, the service inspects `runtime.dependencies_ref`, which records the exact source versions, environmental flags, and file reads underpinning the candidate. Reliable dependency tracking requires runtime instrumentation of mediated filesystem calls, lockfiles, and configuration manifests; subjective, model-generated self-reports cannot be trusted for correctness. Furthermore, negative dependencies require careful tracking: an agent’s code generation may depend on the *absence* of a conflicting file, meaning that recording only positive file reads yields incomplete dependency graphs. Whenever dependency tracking is partial or ambiguous, the integration service treats an empty dependency manifest as unknown rather than disjoint, triggering a fresh revalidation of the candidate against the current branch head.

Let the commit content hashes ${h_{\text{base}}}$, ${h_{\text{worker}}}$, and ${h_{\text{head}}}$ identify the worker’s base, its returned candidate, and the integration head captured for this attempt. The protocol has four steps, which [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.06 Optimistic Concurrency Control#^lst-vol3-occ-commit|listing 3]] condenses into the control flow of an integration service.

1.  **Revalidate dependencies**: Compare dependency versions between ${h_{\text{base}}}$ and ${h_{\text{head}}}$. Pairwise disjoint file sets demonstrate only textual independence. If a referenced interface or schema changed on the main branch, the runtime must revise or regenerate the candidate before attempting integration.
2.  **Build the candidate**: Construct an immutable integration candidate ${h_{\text{candidate}}}$. If ${h_{\text{head}}}$ still matches ${h_{\text{base}}}$, the candidate is the worker’s own commit ${h_{\text{worker}}}$ (the fast-forward path). If the head advanced, the service stages a private merge commit combining ${h_{\text{head}}}$ and ${h_{\text{worker}}}$. Should textual or structural conflicts arise, the service may dispatch a bounded reconciliation task to an agent. The resulting merge artifact is treated as a fresh candidate proposal, subject to the full validation pipeline.
3.  **Check the exact candidate**: Every integration candidate must pass the scope and quality checks mandated by `migration_accept_v1` within the protected assessment sandbox of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-grader-isolation|Grader isolation]]**. Under the evidence-scope rule, verification tests executed on the worker’s private branch do not validate the newly synthesized merge candidate. Acceptance criteria must be evaluated directly on the exact commit hash ${h_{\text{candidate}}}$.
4.  **Publish with an expected-head update**: Advance the target ref if and only if the current branch pointer still equals the captured ${h_{\text{head}}}$ and all publication guards remain satisfied. These guards verify active grant authorization, unrevoked task status, comprehensive dependency tracking, and fresh acceptance test evidence. In Git, the low-level `update-ref` command with an expected old object hash guarantees an atomic compare-and-swap. The runtime sequences authorization guards with this atomic ref update to eliminate race conditions between token revocation and publication, while external dependencies are anchored by their action-time version contracts.

If a concurrent writer advances the branch head before the atomic ref update executes, the integration attempt aborts. Rather than blindly retrying the update against the new head, the service loops back to step 1, revalidating all dependencies against the updated state. If the publication command returns an ambiguous network outcome or timeout, the service must query the authoritative repository log before attempting a retry, preventing duplicate commits. [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.06 Optimistic Concurrency Control#^fig-vol3-occ-worktrees|Figure 3]] assembles three ingredients: private worktrees over shared repository storage, a staged merge that is textually clean even though the caller relies on the interface as of ${h_{\text{base}}}$, and the four-step gate whose moved-head exit returns to revalidation. [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.06 Optimistic Concurrency Control#^tbl-vol3-occ-dependency-trace|Table 4]] then follows the caller worker’s patch across each decision boundary.

``` python
def integrate(repo, task, receipt, contract, max_attempts):
    for attempt in range(max_attempts):
        head = repo.read_ref(TARGET)                          # h_head for this attempt
        stale = changed_dependencies(receipt.dependencies_ref, receipt.base_ref, head)
        if stale:
            return request_revision(task, stale, head)        # regenerate, then return
        if head == receipt.base_ref:
            candidate = receipt.candidate_ref                 # fast-forward case
        else:
            candidate = stage_merge(head, receipt.candidate_ref)
            if candidate is None:
                return request_reconciliation(task, head)     # another proposal
        evidence = run_protected_checks(contract, candidate)  # binds this exact candidate
        if not evidence.accepted:
            return reject(task, candidate, evidence)
        with publication_guard(task) as guard:                # cancellation, grants, lineage
            if not guard.eligible:
                return withdrawn(task)
            outcome = repo.update_ref(TARGET, candidate, expected=head)
        if outcome.uncertain:
            return reconcile_publication(task, candidate)     # never blind-retry the effect
        if outcome.applied:
            return published(task, candidate, evidence)
        # head moved: loop back to dependency validation for the new head
    return unresolved(task, reason="integration_attempts_exhausted")
```

Listing 3: **Guarded Integration of a Worker Candidate**: The service revalidates dependencies against the captured head, checks the exact candidate, and publishes with an expected-head update under the task’s publication guard.

Repeated invalidations quickly erode the efficiency gains of parallel delegation. If several agents continuously update overlapping dependencies, workers spend more compute discarding stale rollouts and reconciling candidates than generating productive code. Runtimes mitigate this through bounded retries, exponential backoff, and serialized commit queues, transitioning exhausted attempts into explicitly unresolved task states. However, when invalidation rates remain persistently high, the architectural remedy lies in work decomposition rather than concurrency tuning. Structuring the task graph to sequence interface migrations ahead of dependent caller tasks eliminates the cross-worker hazard entirely, achieving higher net throughput with fewer wasted agent turns.

### Leases for External Resources

^sec-vol3-multiagent-external-leases

Repository staging isolates and buffers only local repository state. A failed Git integration rolls back local commits, but it cannot undo mutations already executed on shared relational databases, physical test rigs, or external payment gateways. External resources operate under their own conditional-update and ownership semantics.

When managing unmergeable stateful resources (a live database migration lock, a dedicated test bench, or an embedded hardware debugger), the runtime must decide precisely when to enforce mutual exclusion. A **pessimistic lease** acquires an exclusive, time-bounded grant before an agent begins work, and the coordinator reclaims an expired grant so that a stalled holder cannot keep the resource indefinitely. Conflicting workers block until the lease holder releases the lock or times out, avoiding conflict-driven discarded work while the lease remains valid, but agent concurrency collapses into serialized execution. Conversely, *optimistic control* maximizes parallel execution by deferring conflict checks until publication. If validation fails, however, the runtime discards the entire execution trajectory, while any external side effects already dispatched to outside systems remain irreversible. This irreversibility governs the architectural division: optimistic concurrency control excels for private, discardable working trees, whereas the non-mergeable exclusive resources considered here require exclusion established at the target resource before issuing commands. [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.06 Optimistic Concurrency Control#^tbl-vol3-concurrency-controls|Table 5]] compares these operational strategies.

↩︎ Leases, the split-brain they permit when a stalled worker outlives its grant, and epoch fencing at the destination resource are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-operation-ids|Operation identity and endpoint contracts]]**.

| Pessimistic lease with fencing            | Before acting, at the resource                   | Waiting; avoids conflict-driven discard  | Serialized per resource                  | Non-mergeable resources and external effects | Stalled holders; expiry needs a resource-side fence                   |

Checking lease validity inside the runtime before dispatching a command is not enough on its own, because an agent stalled by rate limits or slow inference can outlive its lease while a previously dispatched write is still in transit. Each leased resource therefore needs the resource-side fencing token of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.06 Resuming a Trajectory#^sec-vol3-durable-execution-availability-ownership|Availability and ownership]]**, which stamps every lease transfer with a monotonically increasing generation number and rejects any write carrying an older generation. While the generation number fences out stale holders after a lease changes hands, a duplicate of the same operation sent by the current holder remains a separate hazard that the runtime settles through its operation identity under settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]). Delegation links these mechanisms whenever a supervisor restarts a failed or stalled worker under the policies of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^sec-vol3-multiagent-supervision-trees|section 18.3.4]], because the old attempt and the replacement attempt are siblings targeting the same external resource. Before the supervisor releases the replacement worker to issue commands, the runtime must advance the lease generation at the resource itself so that any late write from the superseded sibling is rejected at the destination.

↪ A delayed writer, traced before and after its replacement’s fencing token is installed, is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Distributed State Foundations#^sec-vol3-appendix-systems-fencing|Leases and Fencing]]**.

Guarded publication provides a robust concurrency framework for serializing concurrent state transitions. Its scope, however, is limited to structural and dependency consistency; OCC does not establish semantic correctness. If multiple workers inherit the same flawed assumptions from a shared planner, each worker can satisfy every step of the guarded publication protocol and cleanly commit a flawed patch to the repository.
