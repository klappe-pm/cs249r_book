# V3-18.08 Bounding In-Flight Work

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination|V3-18 Multi-Agent Coordination]]

^sec-vol3-multiagent-backpressure

Suppose the supervisor cancels `migration_task_01` while `worker_interface_01` awaits an external test job and `worker_caller_01` finishes generating a candidate patch. Even if the caller’s patch passes its local validation checks after the supervisor initiates cancellation, the runtime must ensure that the patch remains strictly unpublishable. Meanwhile, an external testing service may have already accepted the interface worker’s test request, incurring resource and billing charges that remain unsettled long after the worker process halts. In single-agent execution, a cancellation signal interrupts a local loop or an outstanding remote inference call. In a multi-agent system, that control boundary must span an entire hierarchy of distributed descendants.

↩︎ Pause and cancellation of a single trajectory, applied at turn boundaries and by streaming cancellation, are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/10 The Agent Harness/V3-10.06 Control Actions#^sec-vol3-controlplane-signals|Control Actions]]**.

To enforce cancellation across a fleet of workers, the runtime records the affected subtree, its current control generation, and the rationale for stopping. Authoritative dispatch and publication gates consult this record along the serialized path that admits new work. In distributed agent systems, closing admission, terminating execution, and releasing resources are three distinct milestones, each demanding its own independent evidence. Everything admitted before the cancellation stays under the settlement rule of failure recovery, now applied across the entire subtree. An operation admitted before the stop preserves its identity, execution status, and assigned owner until its outcome and associated financial charges settle. No cancellation signal, authorization revocation, timeout, or queue purge can retroactively erase that obligation.

↩︎ The settlement rule, which keeps an operation’s reservation and record until evidence establishes its outcome, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.03 Effects Outside a Shared Transaction#^sec-vol3-sagas-acid-boundary|Effects Outside a Shared Transaction]]**.

### Cancellation Context Trees

^sec-vol3-multiagent-cancellation-trees

When a parent task is canceled, a grandchild worker that has not yet received the stop signal can keep calling tools and publishing results under the parent’s delegated authority. The cancellation context tree prevents that leak without introducing a fourth graph structure. It is the supervision tree of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^sec-vol3-multiagent-supervision-trees|section 18.3.4]] seen from the control plane, with the same parent-child ownership edges, each annotated with the control generation of the ancestor that governs the child. A child’s *delegation lineage* is its path from that tree’s root. Cancellation proceeds in two steps across the runtime’s graphs. First, the runtime traces delegation lineage rather than data-dependency edges to determine which active workers must lose their authority and budget. Because execution mandates and resource allowances flow down the supervision tree, revoking an ancestor immediately strips every descendant in that subtree of eligibility to run tools or publish results. Second, once that subtree is marked ineligible, the runtime inspects the data-dependency graph to see which tasks outside the canceled subtree were waiting on its outputs. Any downstream continuation that required an artifact from the canceled subtree can no longer satisfy its preconditions and is invalidated, whereas sibling or downstream tasks that treated the canceled child as an optional speculative branch continue undisturbed.

**Definition 18.3: Hierarchical cancellation context tree**

***Hierarchical cancellation context tree*** is a runtime-owned delegation structure that links each child to the ancestor control decisions governing its continued execution and result publication.

1.  **Significance**: It identifies which descendants must lose eligibility when an ancestor stops and which outstanding operations still need an owner.
2.  **Distinction**: Propagating a stop request changes control policy; confirming remote termination, resource release, and effect settlement requires separate evidence.
3.  **Common pitfall**: Treating a canceled parent record as proof that every child, external job, and charge has ended.

The ordering of events at each admission and publication gate dictates the precise boundary of cancellation. Suppose an admission gateway accepts `worker_interface_01`’s test operation, logs its unique operation identity along with its resource reservation, and begins transmitting the request. If the parent task cancels before a reply arrives, that test operation remains admitted and must proceed through the settlement protocol. However, any subsequent request from either child that arrives at that gateway after the cancellation decision is serialized will be rejected immediately. Result publication follows the exact same linear order. The integration path must re-verify task eligibility at the atomic publication boundary: if the cancellation commits first, it blocks publication of any patch, regardless of whether that patch passed every local check. If publication commits before the cancellation is serialized at the boundary, the resulting state change stands as a durable modification that the recovery contract must handle.

Under this architecture, a supervisor can authoritatively report that its gateways deny new work and reject publications without falsely claiming that a disconnected or remote worker process has already halted. A remote enforcement gateway that loses connectivity to the central control plane must fail closed. If a gateway instead relies on cached authorization tokens, it operates under an explicit stale-authorization window and cannot guarantee immediate, subtree-wide revocation ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.09 Capability Delegation#^sec-vol3-multiagent-authority|section 18.8]]).

### Evidence Preservation During Cleanup

^sec-vol3-multiagent-cleanup-evidence

Closing a local client stream does not confirm that a remote model provider has ceased generation, and killing a local worker process leaves requests accepted by external services in flight. Because local termination and remote completion are asymmetric across distributed boundaries, the runtime must dispatch explicit stop requests to each reachable execution service, with each acknowledgment certifying only its specific operational scope ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.08 Bounding In-Flight Work#^tbl-vol3-cancellation-layers|table 7]]). An executor’s process-level or infrastructure confirmation always outranks an agent’s self-reported claim that it has halted.

| Evidence                                 | What it establishes                                                                   | What remains separate                                              |
|:-----------------------------------------|:--------------------------------------------------------------------------------------|:-------------------------------------------------------------------|
| Authoritative admission hold             | Later model/tool admissions and candidate publication are denied at the covered gates | Previously admitted work and disconnected enforcement points       |
| Executor confirms worker termination     | The identified execution scope has stopped under that executor’s contract             | Remote jobs, external effects, and final usage                     |
| Provider confirms an operation’s outcome | The identified operation has the reported effect status                               | Other attempts, cleanup operations, and unresolved charges         |
| Resource owner confirms release          | The identified slot, sandbox, or allocation is available again                        | Retention of required evidence and settlement of other obligations |

Table 7: **Evidence at cancellation boundaries**: Each acknowledgment supports a scoped claim rather than certifying that the whole subtree has disappeared.

^tbl-vol3-cancellation-layers

For an outstanding test request, the runtime retains the operation identity, execution attempt history, resource reservation, and external job handle while actively reconciling status. If the external test service eventually delivers a late result, that response can settle the operation’s outcome and finalize its billing without reactivating the canceled task trajectory. If the external outcome remains indeterminate, the runtime transfers the operation to a designated settlement owner. The execution receipt preserves these audit records through `runtime.settlement_ref`, ensuring they survive any context-window summarization or lineage compaction.

Cleanup operations cannot execute under the revoked worker’s authority; the runtime must provision a separately scoped administrative credential and a protected resource allowance. Furthermore, tearing down an allocated environment is itself an asynchronous operation with an uncertain outcome. Scratch workspace or container deletion must block until all relevant filesystem writers have terminated and required diagnostic artifacts have been safely archived. An asynchronous background sweeper reconciles registered physical allocations against these pending evidentiary obligations before unlinking directories or recycling sandbox containers.

↩︎ The cleanup graph that orders this teardown is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^sec-vol3-failure-recovery-cleanup-graph|The cleanup graph]]**.

### Hedged Requests and Speculative Work

^sec-vol3-multiagent-hedged-requests

![[90 Assets/Volume III/18 Multi Agent/Vol3 Multi Agent Barrier Odds a9f2c4d42f.svg]]

*A falling curve of the probability that every worker finishes by the deadline against fleet size from 1 to 16, crossing a dashed even-odds line at a red dot labeled 7 workers.*

*Waiting for every worker drops on-time odds below half by seven workers.*

Beyond handling failures and user aborts, cancellation is a primitive for speculative execution and latency management. When an agent workflow fans out across multiple subtasks, waiting for every parallel worker exposes the entire system to stragglers, the tail-at-scale problem ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-dean2013tail|Dean and Barroso 2013]]). Consider ${N_{\text{workers}}}$ parallel workers with independent and identically distributed completion times ${T}_i$ required to produce an admissible result. If ${F}({t})=\Pr({T}_i\le {t})$ represents the cumulative probability of a single worker finishing within time ${t}$, an **all-results barrier**, which requires every worker to complete, achieves a deadline completion probability of

$$
\Pr\bigl(\max_i {T}_i\le {t}\bigr)={F}({t})^{{N_{\text{workers}}}}.
$$

Because the barrier needs every worker’s admissible result, each added worker multiplies the deadline probability by another factor ${F}({t})<1$, so it decays geometrically as the fan-out ${N_{\text{workers}}}$ grows. This is the same geometric decay that horizon compounding (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]**) applies across turns, now applied across workers. In production systems, correlated queueing delays, shared rate limits, and unequal prompt lengths break the idealized independent model, so deadline probabilities must be measured under the shared serving conditions. However, if the task contract permits any ${k}$ interchangeable admissible results out of ${N_{\text{workers}}}$ replicas, the probability of meeting the deadline becomes

$$
\Pr({T}_{(k)}\le {t})=\sum_{j=k}^{{N_{\text{workers}}}}\binom{{N_{\text{workers}}}}{{j}} {F}({t})^{j}[1-{F}({t})]^{{N_{\text{workers}}}-{j}},
$$

where ${T}_{(k)}$ denotes the arrival time of the ${k}$th admissible result. This ${k}$-of-${N_{\text{workers}}}$ stopping rule applies strictly to interchangeable outputs, such as parallel candidate retrieval or redundant reasoning paths. In the migration scenario, by contrast, the system requires both the interface update and the caller refactor; no majority of completed caller patches can stand in for a missing interface patch.

**Napkin Math 18.5: A completion contract changes the barrier**

**Problem**: A hypothetical read-only analysis task permits any 6 interchangeable admissible results from 8 workers. Each worker independently has a 90 percent probability of returning such a result within 10 s of dispatch, including its checks. What is the probability of having sufficient results by that deadline, compared with waiting for every worker?

**Math**: Requiring every result gives ${F}({t})^{{N_{\text{workers}}}}$, or 43.05 percent. Summing the binomial probabilities for 6 through 8 completions gives 96.19 percent.

**Systems insight**: An all-results barrier multiplies the deadline probability by ${F}({t})$ for every worker added; at this per-worker rate it drops below even odds at 7 workers. Where the contract permits interchangeable results, a ${k}$-of-${N_{\text{workers}}}$ stopping rule recovers most of the lost probability. Where it does not, the fan-out itself must shrink or the per-worker tail must be cut. The workers still running after the rule fires consume resources until cancellation takes effect, and that work belongs in the cost account.

**Hedging**[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.16 Footnotes#^fn9|⁹]] mitigates tail latency by dispatching a redundant replacement attempt after a specified delay while the original worker continues running, subsequently accepting whichever admissible result completes first ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-dean2013tail|Dean and Barroso 2013]]). Hedging functions smoothly for read-only analyses and sandboxed candidate patches where a single runtime publication gate arbitrates the winner and cancels redundant runners. However, speculative hedging introduces acute hazards if an agent executes external mutating actions. Unless the destination service implements a strict duplicate-effect or idempotency contract, a trailing or canceled worker can execute irreversible side effects before its cancellation signal is processed. A hedge of a mutating action is a retry issued before the first attempt has settled, which settlement before retry (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-exactly-once-settlement|8]]) forbids unless both attempts carry one operation identity that the endpoint deduplicates. Furthermore, speculative attempts consume real token allowances and concurrency slots; dispatching hedges into a congested inference cluster amplifies queue depth and prolongs the very tail latencies the mechanism was intended to truncate.

↩︎ Uncertain outcomes and the endpoint deduplication contracts that make a repeated mutation safe are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|Retrying Uncertain Actions]]**.

### Credit-Based Flow Control

^sec-vol3-multiagent-credit-flow-control

Even when every child agent stays within its own token budget, a rate mismatch between stages of a pipeline can still destabilize the workflow. A fast producer that emits candidate changes faster than a downstream reviewer or test runner can drain them fills the queue between the two stages. As that backlog grows, candidates wait longer before inspection, so the repository state they were built against moves underneath them while they sit in line.

Consider an upstream agent that lists files and emits candidate diffs at ${\lambda_{\text{arr}}} =$ 5 items per second. A downstream reviewer model generates a 500-token critique for each item at a decode speed of 40 tokens per second, yielding an effective service rate of only ${\mu} =$ 0.08 items per second. In an unconstrained queue, the backlog expands at the net rate ${\lambda_{\text{arr}}} - {\mu}$. After 10 minutes, the queue accumulates 2,952 unreviewed items, and a newly submitted diff faces an estimated queue wait of 10.2 hours. Long before process memory is exhausted, the queued items become obsolete, because the repository state they reference has diverged, reproducing between agents the stale-observation failure that context invalidation guards against inside one trajectory. Per-agent token budgets fail to prevent this collapse because each individual candidate item is inexpensive to generate.

↩︎ Context invalidation, which withdraws observations that a later change has made stale, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.08 Context Invalidation#^sec-vol3-context-engineering-context-rot|Context Invalidation]]**.

A finite **credit window** prevents this divergence by bounding the number of admitted, in-flight items, much as an aggregate budget caps token expenditure. It is the same mechanism that bounds staged records in trajectory collection. A producer transmits only while it holds a credit the consumer issued for free capacity, so congestion delays the producer but never overflows a buffer. Let ${N_{\text{win}}}$ denote the fixed credit capacity of the channel, ${N_{\text{free}}}$ the unallocated credits held by the producer, and ${N_{\text{out}}}$ the outstanding admitted items currently circulating in the pipeline. The runtime enforces the structural invariant:

$$
{N_{\text{free}}}+{N_{\text{out}}}={N_{\text{win}}},\qquad {N_{\text{free}}}\ge0,\quad {N_{\text{out}}}\ge0.
$$

↩︎ Collection credits, which bound staged trajectories between generation and verification, are established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.09 Collection Pipeline Architecture#^sec-vol3-trajectory-curation-collection-credits|Collection credits and staging reserves]]**.

Under this discipline, admitting a new work item requires the producer to acquire and attach an available credit. That credit remains tied to the item while it traverses the network, waits in downstream queues, undergoes evaluation, or reserves output buffer space. The runtime returns the credit to the producer’s pool only when the item reaches a designated capacity-release boundary. Credit returns are processed atomically and with at-most-once semantics. A lost return silently shrinks the window, and a duplicated one inflates it, so network disconnections trigger a recount of outstanding credits against the authoritative runtime state rather than granting producers a fresh batch of credits.

Beyond protecting buffer memory, credit windows provide a sizing model for mean residence at a sustained service rate. Little’s law (theorem [5.1](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#thrm-05-littles-law), **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^eq-vol3-littles-law|equation 5.7]]**) states that the mean number of items held equals their admitted rate times their mean residence. Applying it to a saturated window takes one mapping. The items held are the outstanding ones, ${N_{\text{out}}}={N_{\text{win}}}$. The window admits a new item only when the consumer drains one, so the admitted rate is the drain rate ${\mu}$, not the producer’s offered rate ${\lambda_{\text{arr}}}$. Dividing the items held by the admitted rate gives a mean residence of ${N_{\text{win}}}/{\mu}$. With a window of ${N_{\text{win}}} =$ 8 credits in the pipeline above, a diff that would have waited 10.2 hours behind the unbounded backlog instead resides in the window for 100 seconds on average. A hard freshness requirement additionally needs admission timestamps, deadline checks before service, and bounded service times if timely service must be guaranteed. When credits are exhausted, the producer yields execution instead of flooding the pipeline with artifacts destined to be obsolete upon inspection. Furthermore, if each in-flight payload is constrained to at most ${D_{\text{vol}}}$ bytes, total memory occupancy cannot exceed ${N_{\text{win}}}{D_{\text{vol}}}$. This demonstrates why payload return bounds ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.05 Typed Task Envelopes#^sec-vol3-multiagent-contracts|section 18.4]]) serve as admission-control parameters rather than mere prompt formatting conventions.

Exhausting data credits, however, must never starve control-plane traffic. Signals such as cancellation commands, credit reconciliation messages, execution status receipts, and financial settlement records travel over reserved out-of-band control channels. The runtime must reject new task admissions whenever doing so would risk exhausting the execution slots reserved for downstream consumers and cleanup handlers. Otherwise, upstream producers waiting for credits will block the very consumers needed to release them, deadlocking the system. Finally, releasing a channel credit must not be conflated with releasing an external resource or refunding a financial commitment. Credit reclamation restores pipeline capacity, whereas financial settlement accounts for external cost.

Together, cancellation trees and credit windows bound the volume and financial exposure of in-flight work while keeping control paths responsive, and the credit window sets mean residence under the stated service rate. Neither control, however, decides which operations a child is allowed to propose while it runs. Enforcing those limits across a delegation tree depends on the authority model at each node: what capabilities each descendant holds, how its allowance is reserved, and how fresh its lineage must be when checked at a remote gateway ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.09 Capability Delegation#^sec-vol3-multiagent-authority|section 18.8]]).
