# V3-18.03 The Delegation Trade-Off

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination|V3-18 Multi-Agent Coordination]]

^sec-vol3-multiagent-need

Handing the interface update and the caller update to dedicated workers differs from issuing concurrent model queries, and that difference defines the unit of delegation. A **delegated worker** owns a bounded child trajectory with its own context window, model-and-tool loop, task contract, and independent lifecycle. Several candidate samples dispatched by one controller, such as the self-consistency votes of test-time compute, are instead parallel calls inside one trajectory. They are the cheapest ensemble an agent can run and also the most correlated, because every sample shares the model, the prompt, and the input’s difficulty, a dependence that [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.07 Correlated Ensemble Failures#^sec-vol3-multiagent-consensus|section 18.6]] quantifies. The architectural shift lies in establishing explicit boundaries between separately managed trajectories, regardless of whether those workers execute on a single host or across a distributed cluster.

↩︎ Self-consistency, which samples several reasoning paths and returns the plurality answer, is established in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.04 Selecting from a Candidate Pool#^sec-vol3-test-time-compute-selection-policies|Choosing a selection rule]]**.

The point of comparison throughout this chapter is the *capable baseline*: the single-agent runtime developed in earlier chapters, which already manages its context window, reserves system resources, verifies proposed tool effects externally, and executes candidate searches and isolated tools concurrently. Delegation retains every one of those operational requirements while introducing new coordination boundaries. The systems question is whether dividing control and context improves a declared task objective enough to justify the overhead of managing them.

### Motivations for Delegation

^sec-vol3-multiagent-motivations

When a single agent runs a wide repository migration inside one shared context and one broad authority grant, compiler diagnostics from one module crowd out the prompt needed for the next while every tool call carries permissions for the whole codebase. **Context partitioning** addresses the prompt growth directly: each worker retains only the material strictly necessary for its subtask. In the migration scenario, the interface worker maintains the target API contract and local unit tests without ingesting the intermediate compiler diagnostics of the caller worker, allowing each subsequent model invocation to process substantially fewer prompt tokens. However, the net token savings depend entirely on the structure of the decomposition. If both workers repeatedly require the full repository commit history, separate contexts duplicate prompt state rather than isolating it, a redundancy the single-agent baseline already avoids through retrieval and compaction.

Delegation also provides *separate task ownership*. Workers can pursue multi-turn exploratory investigations through iterative tool feedback and local reasoning loops while a central coordinator tracks inter-task dependencies and orchestrates final integration. Assigning task ownership, however, does not eliminate underlying data dependencies. A caller worker that generates code against an outdated interface must still reconcile its implementation once the interface worker finalizes the new contract. True operational independence derives from the causal graph of the task itself, never from cosmetic role descriptions in prompt templates.

Finally, decomposing work across workers enforces *task-scoped authority*, binding tools, execution capabilities, and resource budgets directly to individual subtasks. For example, a test-runner worker can be granted execution privileges in an isolated container without granting it credentials to publish pull requests or write to production databases. Even so, process isolation does not eliminate trust boundaries. A child worker’s textual output can still inject unvalidated claims or prompt injections into the parent coordinator’s context, and any external mutations it produces must still be verified and settled by the runtime. [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^tbl-vol3-delegation-matrix|Table 1]] separates these opportunities from capabilities already present in the baseline.

| Dimension               | One controller already provides                    | Delegation adds                                                     |
|:------------------------|:---------------------------------------------------|:--------------------------------------------------------------------|
| Parallel work           | Concurrent candidate calls and tools               | Independently managed, multi-turn subtask trajectories              |
| Context                 | Retrieval, compaction, and selective observations  | Separate working contexts and explicit return boundaries            |
| Authority and isolation | Scoped grants and sandboxed execution              | Descendant grants and lifecycle relationships to enforce            |
| State and evidence      | Versioned artifacts and checks on proposed changes | Cross-worker dependency validation and integrated-result assessment |
| Resource control        | Admission, reservations, deadlines, and settlement | Aggregate obligations across descendants and their communication    |

Table 1: **What Delegation Adds**: The comparison preserves the capable single-controller runtime and identifies the extra boundaries a coordinated design must justify.

### The Coordination Tax

^sec-vol3-multiagent-coordination-tax

Splitting the authentication migration across separate interface and caller workers adds work that a single controller never performs: the coordinator spends turns packaging task assignments and reconciling returned diffs, both workers ingest shared repository context, and final integration waits at the join barrier for the slower child to finish. Every delegation boundary incurs this coordination tax (principle [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/V3 Agents at Scale Principles#^pri-vol3-coordination-tax|14]]).

**Definition 18.1: Coordination tax**

***Coordination tax*** is the work and elapsed time a delegated design spends on handoffs rather than on the task: preparing and validating envelopes, delivering context, scheduling children, collecting receipts, and reconciling and integrating their results.

1.  **Significance**: The tax enters both terms of the cost per accepted task, ${C_{\text{eff}}}$ (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**): its tokens and tool time raise $\mathbb{E}[{C_{\text{attempt}}}]$, and the part on the critical path lengthens every attempt against its deadline.
2.  **Distinction**: While task decomposition aims to reduce makespan by distributing work concurrently, the coordination tax represents the unavoidable friction introduced by that distribution. This tax scales with worker count, communication frequency, and inter-task dependencies.
3.  **Common pitfall**: Accounting only for the tokens and execution time of successful worker turns. Context re-ingestion, supervisor arbitration turns, failed retries, and abandoned speculative branches all consume model quota and execution budgets.

Coordination tax impacts systems along two distinct dimensions: aggregate resource consumption and end-to-end latency. Duplicated input prompt tokens, redundant tool invocations, and serialize-deserialize cycles increase the total operational cost. Meanwhile, user-perceived delay is governed by **makespan**, the wall-clock time elapsed from the arrival of a task to the completion and verification of its final artifact. Makespan depends strictly on the operations situated on the critical path. A straggling child worker delays synchronization at the join barrier, while subsequent arbitration and reconciliation turns further inflate the critical path before results can be accepted.

Amdahl’s fixed-work argument[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.16 Footnotes#^fn1|¹]] gives the first screening model ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-amdahl1967|Amdahl 1967]]). Let ${T_{\text{serial}}}$ be the time for a fixed set of operations executed serially, with fraction ${f_{\text{parallel}}}$ perfectly divisible among ${N_{\text{workers}}}$ equally fast workers and fraction $1-{f_{\text{parallel}}}$ remaining serial. Assume enough resources for that division and let ${h}({N_{\text{workers}}})$ be the additional elapsed overhead, normalized by ${T_{\text{serial}}}$. Then

$$
\text{Speedup}({N_{\text{workers}}})=\frac{{T_{\text{serial}}}}{{T}({N_{\text{workers}}})}=\frac{1}{(1-{f_{\text{parallel}}})+{f_{\text{parallel}}}/{N_{\text{workers}}}+{h}({N_{\text{workers}}})}. \tag{1}
$$

^eq-vol3-multiagent-speedup

With no coordination overhead, ${h}({N_{\text{workers}}})=0$, [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^eq-vol3-multiagent-speedup|equation 1]] reduces to Amdahl’s law, and the serial term alone caps speedup at $1/(1-{f_{\text{parallel}}})$ for any number of workers. The equation provides a preliminary screening model for a specified work partition. The baseline ${T_{\text{serial}}}$ reflects that partition executed sequentially on a single thread of execution, rather than the capable baseline runtime (which already pipelines tool executions and concurrent candidate samplings). In production, an empirical benchmark of the capable baseline must replace ${T_{\text{serial}}}$ before finalizing any worker allocation. Within this theoretical formulation, achieving any net speedup over the serial reference requires that:

$$
{h}({N_{\text{workers}}})<{f_{\text{parallel}}}\left(1-\frac{1}{{N_{\text{workers}}}}\right).
$$

The right-hand side represents the theoretical wall-clock time saved by distributing the parallelizable portion across ${N_{\text{workers}}}$ workers. Whenever coordination overhead ${h}({N_{\text{workers}}})$ exceeds this threshold, the split task takes longer than serial execution. Furthermore, this inequality constrains execution time alone. Task acceptance rates, token expenditures, and monetary costs enter the trade-off in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^sec-vol3-multiagent-evaluation|section 18.9]], which gives serializing work and pairwise reconciliation separate coefficients because their remedies differ ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^sec-vol3-multiagent-scaling-models|section 18.9.3]]).

**Napkin Math 18.1: Screening a proposed work partition**

**Problem**: A hypothetical fixed workload has ${f_{\text{parallel}}}=$ 0.80 and assumed normalized overhead ${h}({N_{\text{workers}}})={\gamma}({N_{\text{workers}}}-1)$ with ${\gamma}=$ 0.02. The resource ceiling permits at most 16 workers. Which integer count minimizes modeled elapsed time?

**Math**: Evaluating the denominator of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^eq-vol3-multiagent-speedup|equation 1]] for each permitted count, four workers require 0.460 of the serial reference time. The minimum occurs at 6 workers, requiring 0.433, a 2.3× speedup. Eight workers increase the ratio to 0.440, because the shrinking parallel term ${f_{\text{parallel}}}/{N_{\text{workers}}}$ no longer pays for the added overhead. Halving the overhead coefficient to 0.01 moves the optimum to 9 workers and the speedup to 2.7×.

**Systems insight**: The serial fraction sets the ceiling and the overhead sets the useful fleet size. No worker count beats $1/(1-{f_{\text{parallel}}})=$ 5× here, and the best count sits near $\sqrt{{f_{\text{parallel}}}/{\gamma}}$, so halving the per-worker overhead ${\gamma}$ adds 3 workers but only 0.4 of speedup. Shrinking the serial planning and integration work is the larger lever.

A reduction in modeled makespan does not automatically justify a multi-agent architecture. Production systems optimize under varied constraints: one automated migration service may seek to maximize accepted pull requests prior to a nightly release window subject to a strict token budget, whereas another prioritizes minimizing the total cost per accepted migration. Trading latency for computational overhead is justified only against an explicit, pre-declared optimization objective, and the decision framework of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^sec-vol3-multiagent-evaluation|section 18.9]] charges that objective for retries and failed executions as well. Before sizing a worker pool, an engineer must map the causal dependency graph of the workload to see which subtasks can run concurrently and what evidence each downstream join requires. Those dependencies govern the coordination topology.
