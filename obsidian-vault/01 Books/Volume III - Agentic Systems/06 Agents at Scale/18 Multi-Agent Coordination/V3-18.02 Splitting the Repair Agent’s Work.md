# V3-18.02 Splitting the Repair Agent’s Work

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination|V3-18 Multi-Agent Coordination]]

^sec-vol3-multiagent-intro

The repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) has so far fixed a connection-pool race, a change confined to one module that a single controller holds comfortably in one context. Its next assignment is wider: migrate an authentication module across a repository, a change that reaches every caller of the module’s interface and is exactly the kind of repair task that tempts a split. The task naturally splits into two coupled changes: revising an internal interface and updating its downstream callers. A single coordinator could retain the entire task, dispatching parallel searches and test runs to collect evidence before synthesizing a unified patch. Alternatively, it could partition the problem, assigning the interface update and caller modifications to separate workers. Each worker operates within a focused context window, editing candidate files and reacting to compiler diagnostics independently. This division introduces an immediate distributed consistency challenge: the caller modifications must remain compatible with the interface that ultimately lands, not merely the snapshot the caller worker read at dispatch.

*H·S·A locator with all three axes, Horizon, State, and Authority, highlighted.*

*A fleet multiplies horizon, state, and authority, so every handoff must preserve closure.*

The runtime mechanisms established in earlier chapters govern a single execution trajectory at a time. Within that boundary, the harness checks each model and tool invocation against an assigned grant and token budget. Durable execution logs one trajectory’s event history, and failure recovery settles, repairs, or compensates the effects of that one trajectory. Evaluation compares trials of one configuration against another, and curation and post-training improve the policy that drives it. Partitioning the migration preserves these local controls inside each individual worker, but it leaves the coordination space between them unmanaged. A single-agent runtime provides no mechanism to resolve which interface revision the caller worker targets, whether a clean textual merge of two patches preserves semantic correctness, or what consensus among five reviewer agents actually guarantees. Nor does it define who claims an orphaned test container after a coordinator cancels a subtask, or how a parent bounds the authority and compute budget delegated to a child. Without explicit systems controls, every such gap threatens to make the split cost far more than it buys.

Making delegation governable requires runtime controls, and deciding whether it pays requires an empirical framework. The required controls are state records and verification gates owned directly by the runtime rather than left to prompt instructions. They include enforceable task assignments and receipts that separate an agent’s self-reported claims from verified tool evidence. They also include a publication barrier that revalidates cross-module dependencies before any candidate patch merges, clean cancellation paths that account for in-flight work, and authority grants that narrow monotonically at every delegation hop. These mechanisms pair with a measurement discipline that compares each multi-agent design against a single agent holding equivalent parallel tools and resource budgets, and that prices every token consumed by failed, retried, or canceled subtasks.

The migration carries the argument from the decision to split through the final accounting, and each control answers a hazard that the previous one exposes. A screen of serial work against coordination overhead first decides whether a partition can pay at all ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^sec-vol3-multiagent-need|section 18.2]]). Dependency, communication, and supervision structures then fix what may run concurrently and who owns each child ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^sec-vol3-multiagent-topologies|section 18.3]]), and typed envelopes and receipts fix what crosses each handoff ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.05 Typed Task Envelopes#^sec-vol3-multiagent-contracts|section 18.4]]). Once workers run in parallel, guarded publication keeps their edits consistent ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.06 Optimistic Concurrency Control#^sec-vol3-multiagent-concurrency|section 18.5]]), and a joint error model shows what agreement among reviewers can and cannot certify ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.07 Correlated Ensemble Failures#^sec-vol3-multiagent-consensus|section 18.6]]). Cancellation, hedging, and credit windows bound the work still in flight ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.08 Bounding In-Flight Work#^sec-vol3-multiagent-backpressure|section 18.7]]), and attenuated grants and atomic reservations bound authority and spending at every hop ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.09 Capability Delegation#^sec-vol3-multiagent-authority|section 18.8]]). A matched comparison against a capable single controller decides whether the whole design earns its tax ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^sec-vol3-multiagent-evaluation|section 18.9]]).
