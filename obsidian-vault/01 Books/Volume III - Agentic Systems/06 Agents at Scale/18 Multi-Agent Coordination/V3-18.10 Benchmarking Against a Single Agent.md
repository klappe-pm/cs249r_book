# V3-18.10 Benchmarking Against a Single Agent

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18 Multi-Agent Coordination|V3-18 Multi-Agent Coordination]]

^sec-vol3-multiagent-evaluation

When benchmarking the authentication migration (`migration_task_01`), granting parallel tool execution to the multi-agent supervisor while artificially restricting the single controller to serial execution measures a baseline handicap rather than the true benefit of delegation. A rigorous evaluation compares the supervisor against a single controller that already dispatches parallel searches and tests, beginning with an objective declared in advance, such as minimizing cost per accepted task subject to a deadline, or maximizing completed tasks within a fixed operating budget. The coordination tax (principle [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/V3 Agents at Scale Principles#^pri-vol3-coordination-tax|14]]) then appears in three measurements read together: accepted-task rate, elapsed wall-clock time, and cost per accepted task. While a Pareto improvement across all three dimensions is ideal, it is rarely achieved. In practice, delegating work across agents represents an explicit trade of computational cost for lower latency. This trade-off is justified only when the engineering objective values latency reduction and the solution satisfies all quality and budget constraints.

### Matched Comparison Conditions

^sec-vol3-multiagent-matched-conditions

Comparing a multi-agent fleet against a single-turn prompt or a controller with lower tool concurrency credits delegation for resources the single agent was never allowed to use. A fair evaluation applies the matched-budget comparison established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-matched-budgets|Matched-budget comparison]]**, which fixes the task distribution, criteria, and resource envelope before policies are compared. It also uses an equally capable baseline, an iterative single controller with parallel tool execution, rather than an isolated, single-turn model call. For delegation, the matched envelope must also fix starting fixtures, evidence access, and identical concurrency limits on both model calls and tool executions. Because either policy may terminate early, unconsumed budget represents an operational outcome rather than an experimental discrepancy. If a delegated design also alters underlying model selections or prompt formulations, the trial evaluates a compound bundle of variables, so isolating the architectural impact of delegation requires a controlled ablation. Finally, acceptance must be scored on the integrated end-to-end task rather than on worker subtasks, because an interface update that passes its local unit tests still fails the migration if the accompanying caller patch introduces breaking signature incompatibilities.

### Outcome, Latency, and Cost Metrics

^sec-vol3-multiagent-outcome-latency-cost

Every attempted task must remain in the evaluation denominator; tasks that encounter timeouts, unhandled errors, or indeterminate verdicts cannot be discarded from the benchmark. When the operational contract treats late delivery as an outage, on-time acceptance must be recorded as a distinct metric alongside gross completion. End-to-end latency spans the full execution envelope, measured continuously from task arrival through task decomposition, sub-agent dispatch, intermediate reconciliation, final integration, and automated assessment. Calculating median latency solely over accepted tasks introduces severe survival bias by filtering out prolonged failures. Systems evaluation therefore tracks latency across all arrivals. A task still running at the observation cutoff is *right-censored*: its latency is known only to exceed the cutoff, so it enters the latency distribution as a lower bound rather than being dropped. This is the same refusal to discard unresolved outcomes that keeps pending and unknown verdicts in the evaluation denominator (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^sec-vol3-evaluation-contract-verdicts|The four-verdict rule]]**).

Cost accounting must encompass the complete system boundary: supervisor orchestration, retrieval queries, verification suites, merge conflict reconciliation, failed exploratory attempts, canceled speculative branches, and environment cleanup. Token expenditures must distinguish input and output tokens at their respective market prices, while concurrent tool invocations must be billed by aggregate worker execution time, which frequently exceeds the wall-clock span of the critical path. The effective cost per accepted task divides this full cohort spend by the accepted count under the same matched-budget accounting, so an architecture with no accepted solutions still reports its spend and the zero count. The token inflation documented in war story [18.1](https://mlsysbook.ai/vol3/18_multi_agent/18_multi_agent.html#ws-vol3-multiagent-research-fanout-2025) illustrates why rigorous cost accounting is needed before committing to a multi-agent deployment.

**Napkin Math 18.6: How much acceptance a token multiple must buy**

**Problem**: A delegated multi-agent architecture consumes tokens at the ratios reported for the research system: 15× the token volume of a standard chat interaction, compared to 4× for an autonomous single agent. Assuming a constant price per token, how much must task acceptance improve for delegation to break even on cost per accepted task, and over which baseline success rates is break-even mathematically achievable?

**Math**: Let ${r}$ be the token multiple, delegated tokens per attempt over single-agent tokens per attempt. Following **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**, with cost proportional to tokens, the delegated cost per accepted task divided by the single-agent cost per accepted task is ${r}\,{p_{\text{single}}}/{p_{\text{multi}}}$. With ${r}=$ 15× $/$ 4× $=$ 3.75×, economic break-even requires that ${p_{\text{multi}}} =$ 3.75× $\cdot\, {p_{\text{single}}}$. Because probability is bounded (${p_{\text{multi}}} \le 1$), break-even is possible only when the single-agent baseline achieves ${p_{\text{single}}} \le$ 26.7 percent. Even if the reported evaluation score gain of 90.2 percent translated directly into an acceptance rate multiplier of 1.90×, the effective cost per accepted task would remain 2.0× that of the single-agent baseline.

**Systems insight**: When delegation multiplies token consumption by a factor of ${r}$, it reduces effective cost ${C_{\text{eff}}}$ if and only if it scales task acceptance by more than ${r}$. At an expansion ratio of 3.75×, this economic efficiency can materialize only on difficult tasks where the single agent succeeds less than 26.7 percent of the time. On workloads where a single agent already succeeds reliably, delegation cannot be justified by cost efficiency. It must be justified as a purchase of reduced wall-clock latency or broader search coverage, valued explicitly by the system’s operational requirements.

### Scaling Models for Worker Count

^sec-vol3-multiagent-scaling-models

![[90 Assets/Volume III/18 Multi Agent/Vol3 Multi Agent Usl Retrograde 403c490b3e.svg]]

*A capacity curve against worker count that rises steeply to a peak labeled peak at 6, then declines and crosses a baseline of 1 at a red dot, with the region beyond shaded and labeled slower than one worker from 41.*

*Coherency cost turns added workers into lost capacity past the peak.*

A matched trial is expensive, so before running one a team must decide which worker counts deserve a trial at all. The fixed-work scaling model of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^eq-vol3-multiagent-speedup|equation 1]] does not replace that benchmarking; its role is to guide the search by identifying promising worker counts. Varying the worker count alters resource contention, sub-task dispatch boundaries, and inter-agent reconciliation costs simultaneously. Consequently, any empirical overhead curve holds strictly within the evaluated range and serves as a hypothesis beyond it. To reason about scaling limits systematically, classical systems engineering separates everything that keeps a fleet from ideal division into work that serializes (undivided planning, and any overhead that queues at a single resource) and pairwise reconciliation. These two mechanisms require different architectural remedies.

**Theorem 18.1: Universal scalability law**

*For a fixed amount of work divided among ${N_{\text{workers}}}$ equally capable workers,* Gunther’s **universal scalability law** (USL) ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-gunther2008general|Gunther 2008]]) gives the relative capacity, the speedup over one worker, as [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^eq-vol3-multiagent-usl|equation 5]], with its peak at [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^eq-vol3-multiagent-usl-peak|equation 6]].

$$
\text{Speedup}({N_{\text{workers}}})=\frac{{N_{\text{workers}}}}{1+{\sigma_{\text{cont}}}({N_{\text{workers}}}-1)+{\kappa_{\text{coh}}} {N_{\text{workers}}}({N_{\text{workers}}}-1)} \tag{5}
$$

^eq-vol3-multiagent-usl

$$
{N_{\text{workers}}}^*=\sqrt{\frac{1-{\sigma_{\text{cont}}}}{{\kappa_{\text{coh}}}}} \tag{6}
$$

^eq-vol3-multiagent-usl-peak

- **Contention** (${\sigma_{\text{cont}}}$): The share of work that serializes, including undivided planning, final assessment, and queueing at single resources such as the supervisor or the integration queue.
- **Coherency** (${\kappa_{\text{coh}}}$): The cost of pairwise reconciliation. Each of the ${N_{\text{workers}}}({N_{\text{workers}}}-1)$ ordered worker pairs may exchange state, re-read a peer’s output, or resolve a conflicting change, the same count as the mesh round in [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.04 Coordination Topologies#^sec-vol3-multiagent-topologies|section 18.3]].
- **Amdahl’s law** (${\kappa_{\text{coh}}}=0$): Capacity saturates at $1/{\sigma_{\text{cont}}}$ and never declines.
- **Retrograde region** (${N_{\text{workers}}}>(1-{\sigma_{\text{cont}}})/{\kappa_{\text{coh}}}$): A positive ${\kappa_{\text{coh}}}$ makes added workers harmful, not merely useless. Capacity peaks at ${N_{\text{workers}}}^*$ and falls below one, slower than a single worker, past this count. With the screening notebook’s ${\sigma_{\text{cont}}}=$ 0.20 and ${\kappa_{\text{coh}}}=$ 0.02, every count from 41 workers up finishes later than the serial reference.

Dividing both the numerator and denominator of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^eq-vol3-multiagent-usl|equation 5]] by ${N_{\text{workers}}}$ yields $1/[{\sigma_{\text{cont}}}+(1-{\sigma_{\text{cont}}})/{N_{\text{workers}}}+{\kappa_{\text{coh}}}({N_{\text{workers}}}-1)]$. This expression matches [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^eq-vol3-multiagent-speedup|equation 1]] directly when setting the parallel fraction ${f_{\text{parallel}}}=1-{\sigma_{\text{cont}}}$ and the overhead function ${h}({N_{\text{workers}}})={\kappa_{\text{coh}}}({N_{\text{workers}}}-1)$. In elapsed-time terms, ${\sigma_{\text{cont}}}$ captures fixed serial work whose duration does not change as workers are added, whereas the screen’s linear penalty ${\gamma}$ plays the role of ${\kappa_{\text{coh}}}$ by capturing any elapsed delay that grows in proportion to ${N_{\text{workers}}}-1$. Multiplying top and bottom by ${N_{\text{workers}}}$ turns that linear elapsed-time penalty into the quadratic term ${\kappa_{\text{coh}}}{N_{\text{workers}}}({N_{\text{workers}}}-1)$ in the denominator of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^eq-vol3-multiagent-usl|equation 5]]. Two very different physical mechanisms can produce that same algebraic term. True pairwise state reconciliation generates ${N_{\text{workers}}}({N_{\text{workers}}}-1)$ interactions across the fleet, and when that quadratic aggregate work is shared evenly across the ${N_{\text{workers}}}$ concurrent workers, each worker experiences an elapsed delay proportional to ${N_{\text{workers}}}-1$. However, a central supervisor that sequentially processes one extra dispatch or receipt for each additional worker also adds an elapsed delay proportional to ${N_{\text{workers}}}-1$, without any peer-to-peer communication at all. A fitted value of ${\kappa_{\text{coh}}}$ therefore flags an elapsed overhead that scales with worker count, and engineers must still inspect traces to see whether the culprit is pairwise worker reconciliation or per-worker queuing at the coordinator. Applying the notebook’s assumed parameters, [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^eq-vol3-multiagent-usl-peak|equation 6]] places the continuous theoretical optimum at 6.3 workers, which evaluates to the discrete optimum of 6 workers identified in the screening notebook.

↪ The stationary-root analysis that locates the peak of a fixed partition’s speedup curve is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-amdahl|Optimal worker count under Amdahl's Law with coordination overhead]]**.

The architectural remedy depends on the measured source of overhead. Supervisor queue time, dependency invalidations, and reconciliation work help distinguish serial processing from cross-worker dependency work, and a matched trial that changes one mechanism can test the diagnosis. A verified serial bottleneck may benefit from pipelining supervisory prompts, sharding shared integration queues, or asynchronous event loops. When dependency reconciliation dominates, a partition that reduces cross-agent synchronization may instead pay. Interface refactoring coupled to caller implementations provides one such dependency hazard; a research query with independent search paths provides a contrasting partition.

**Lighthouse 18.1: Research agent (orchestrator-worker fan-out)**

**Workload**: The research agent addresses open-ended, breadth-first queries. A lead orchestrator decomposes the inquiry into independent search paths, dispatches read-only subagents to retrieve and analyze external sources, and synthesizes their condensed findings. The builders of one production research system report that this breadth-first regime is where delegation helps most, in contrast to coding tasks whose tight interdependencies leave less work to run in parallel ([[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.15 Source References#^ref-anthropic2025multiagent|Hadfield et al. 2025]]).

**Scenario coefficients**: Suppose lead-agent planning and final synthesis serialize ${\sigma_{\text{cont}}}=$ 0.10 of total execution, while subagents operate almost entirely without cross-communication (${\kappa_{\text{coh}}}=$ 0.002). Evaluating the scalability model yields an optimal fan-out of 21 subagents achieving 5.5× relative capacity. In contrast, the code repair agent’s high coherency limits its configuration to 6 workers at 2.3× capacity. Under these assumptions, the research partition permits a 3.5× wider effective worker fan-out. (These stylized coefficients illustrate the scaling regime rather than measured telemetry.)

**Local constraint**: Low coherency overhead permits wider fan-out under the supplied model, but token expenditure and context trust can still constrain deployment. At fixed per-worker work, token consumption scales linearly with fan-out, so the economic break-even threshold analyzed in notebook [18.6](https://mlsysbook.ai/vol3/18_multi_agent/18_multi_agent.html#nbk-17-token-multiplier-break-even) may cap deployment before the modeled capacity peak ${N_{\text{workers}}}^*$. Furthermore, because worker receipts incorporate uncurated text from external web APIs, the bounded receipt protocol of [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.05 Typed Task Envelopes#^sec-vol3-multiagent-contracts|section 18.4]] limits returned context and keeps worker claims separate from runtime evidence. Source-derived fields and summaries remain untrusted inputs whose proposed uses require the security checks established for the tool boundary.

**Systems insight**: Under the supplied coefficients, the research partition supports wider fan-out than the repair partition. Dependency traces can establish whether interface isolation addresses the repair workload’s overhead; matched outcome and cost measurements determine whether wider research fan-out earns its additional spend. Admission controls bound that spend independently of the modeled capacity gain.

In production systems, empirical engineering inverts this analytical workflow. Rather than postulating coefficients, engineers conduct targeted benchmarking trials across a small set of practical worker counts (for example, ${N_{\text{workers}}} \in \{1, 2, 4\}$) to estimate ${\sigma_{\text{cont}}}$ and ${\kappa_{\text{coh}}}$. The resulting model fit projects the empirical capacity peak ${N_{\text{workers}}}^*$, identifying the next candidate configuration to benchmark. A large fitted coherency parameter ${\kappa_{\text{coh}}}$ warrants inspecting traces and testing targeted interventions. Redesigning the task decomposition is justified when that evidence confirms that dependency reconciliation dominates; the coefficient alone does not establish the remedy.

### A Complete Delegation Decision

^sec-vol3-multiagent-delegation-decision

Once the scalability fit has nominated a configuration, the matched trial decides whether it earns its tax. Consider the evaluation results for a representative cohort of software migration tasks patterned after `migration_task_01`, evaluated under identical automated test suites (`migration_accept_v1`). Both configurations operate under identical constraints: matching tool and model concurrency limits, identical sandbox permissions, and equivalent token and financial ceilings. The experiment isolates the delegation architecture itself (how work is decomposed, dispatched, and integrated) rather than what the runtime allows.

**Napkin Math 18.7: Buying deadline coverage with delegation**

**Problem**: A prespecified screening protocol requires at least 80 accepted tasks before a final observation cutoff of 600 s, including at least 75 accepted before a strict deadline of 300 s, evaluated across 100 initiated tasks. Each architecture operates under a total cohort budget ceiling of \$20. Which configuration satisfies this engineering screen?

**Assumptions**: Every trial reaches a terminal verdict with settled charges. Tasks may continue executing past the deadline up to the final cutoff and budget ceiling, but late completions do not count toward on-time acceptance. Illustrative pricing is \$3 per million input tokens, \$10 per million output tokens, and \$0.01 per worker-second of metered sandbox, evaluation, and cleanup services, with no human intervention charges.

[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^tbl-vol3-multiagent-decision-costs|Table 9]] sets the outcome counts beside the resources that produce their cost.

| Cohort measurement                                | Single controller | Delegated configuration |
|:--------------------------------------------------|------------------:|------------------------:|
| Accepted by final cutoff                          |          80 (80%) |                80 (80%) |
| Accepted by deadline                              |                70 |                      78 |
| Median time, accepted tasks only (biased)         |             240 s |                   180 s |
| Total input tokens                                |         2,000,000 |               3,000,000 |
| Total output tokens                               |           400,000 |                 600,000 |
| Aggregate metered service time                    |             200 s |                   300 s |
| Total priced spend                                |              \$12 |                    \$18 |
| Included failed-attempt and canceled-branch spend |               \$3 |                     \$6 |
| Cost per accepted task                            |           \$0.150 |                 \$0.225 |

Table 9: **Costs and Outcomes of a Hypothetical Delegation**: Every model call and metered service contributes to total spend, including reconciliation and work not retained in the final artifact. The discarded-work row is a tagged subset, not an extra charge.

^tbl-vol3-multiagent-decision-costs

**Math**: Total spend sums input and output tokens multiplied by their respective rates, plus aggregate worker service time multiplied by its compute rate. Dividing this sum by total accepted tasks yields the effective cost per accepted task. Both architectures meet the gross acceptance target and stay within the budget ceiling, but only the delegated system satisfies the on-time completion threshold. Delegation incurs an incremental spend of \$6 to secure 8 additional on-time completions, a marginal cost of \$0.75 per additional on-time task, while inflating the overall cost per accepted task by 1.5×.

**Systems insight**: The screen advances the delegated configuration because the operational contract explicitly prioritizes deadline compliance over raw cost efficiency. Delegation does not Pareto-dominate the single-agent baseline; it trades dollar spend for wall-clock timeliness. The rational decision rule hinges on marginal value: delegate when an incremental on-time completion is worth at least \$0.75, but retain the single controller when the objective is minimizing cost per completed task. Because speculative failures and canceled branches account for 33.3 percent of the multi-agent spend, this discarded work is a substantial cost component to investigate when reducing the coordination tax. The median row is the survivors-only statistic that [[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.10 Benchmarking Against a Single Agent#^sec-vol3-multiagent-outcome-latency-cost|section 18.9.2]] warns against. It drops every task that was not accepted, so it flatters both configurations, and the decision deliberately rests on the on-time count instead. A production release decision further requires evaluating task diversity, paired statistical tests, and formal uncertainty bounds as detailed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-rigor|Statistical Evaluation Rigor]]**.

Whichever configuration the matched trial favors, a single capable controller or a delegated topology, the deployment must preserve end-to-end acceptance verification, fine-grained sandbox authority, and accounting for canceled speculative work. The scalability fit chooses which worker counts deserve a trial, and the matched trial prices those candidates against the declared objective. Skipping either step, or relaxing the runtime controls that keep handoffs, merges, reviews, and cancellations sound, exposes the deployment to predictable multi-agent failures.

↪ Choosing between a single controller and a delegated topology by pricing both against the same acceptance contract and objective is developed in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.09 Pricing the Choice of Architecture#^sec-vol3-selection-economics|When a bounded loop beats a single call]]**.
