# V3-15.10 Trajectory Provenance Tracking

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15 Trajectory Curation|V3-15 Trajectory Curation]]

^sec-vol3-flywheel-provenance

When an automated scrubbing pass strips sensitive network addresses from raw collection record `trace_r19_01` (from collection run `collection_run_r19_01` and candidate workspace `ws_r20`) to create `trace_r19_01_redacted_v1`, the transformed artifact cannot silently overwrite the source record and inherit its admission labels. Months after an execution trace enters a training corpus, curators must still be able to answer which collection run produced the sequence, which validation criteria were checked against which environment fixtures, whether the organization retains legal permission to train on the incorporated source code or API payloads, and whether sanitization invalidated the runtime state that justified the agent’s next action. A preserved execution trace and its evaluation scores cannot answer these questions on their own. In a production curation pipeline, **provenance** provides the immutable, versioned record that answers them across every derivation of a trace, giving `trace_r19_01_redacted_v1` an independent identity and its own admission decision.

### The Lineage Envelope

^sec-vol3-trajectory-curation-lineage-envelope

When a source repository revokes training permission or a grader bug invalidates a week of checks, an unindexed store of raw JSON traces cannot identify which corpus members must be pulled. A **lineage envelope**[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.17 Footnotes#^fn12|¹²]] prevents that blind spot by recording the origin, dependencies, transformations, and admission decisions of each individual record version. [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.10 Trajectory Provenance Tracking#^tbl-vol3-provenance-schema|Table 13]] outlines its six dimensions. Rather than embedding inline copies of sensitive or high-volume execution state, envelope fields point to content-addressed, access-controlled artifacts.

| Record dimension         | Information to bind                                                                                                                          | Question it answers                                                  |
|:-------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------|
| Collection identity      | Run, task, fixture, candidate, and source-record versions; sampling or selection policy                                                      | Which attempt and inputs does this record represent?                 |
| Generation configuration | Available model and adapter identity, tokenizer, delivered-context references, tool interfaces, harness configuration, and sampling settings | What generated and mediated the represented proposals?               |
| Environment and capture  | Relevant initial-state and dependency versions, operation/result references, retained boundaries, omissions, and unresolved effects          | Which interactions and evidence are available, and what is missing?  |
| Assessment               | Criterion and grader versions, per-criterion verdicts, evidence references, assessment time, and intended learning use                       | What was checked, on which artifact, for which admission decision?   |
| Transformation           | Parent-record identity, transformation implementation/configuration, changed fields, derived identity, and revalidation results              | How does the emitted view differ from the source?                    |
| Use and partition        | Permission decision and scope, retention restrictions, split/group assignment, and corpus membership                                         | Where may this version go, and which evaluation boundary follows it? |

Table 13: **Trajectory lineage envelope**: Versioned references connect a record to its origin and subsequent decisions. Their presence does not certify correctness, complete capture, or permission for every use.

^tbl-vol3-provenance-schema

The envelope must record only what the runtime interfaces actually reveal. When an agent executes against locally controlled model weights, the envelope binds the loaded base model and adapter checkpoint digests. Hosted inference endpoints, however, typically expose only a reported version string and request configuration; in those cases, the envelope documents those exact parameters rather than fabricating an unverifiable weight hash. Similarly, a prompt-template identifier fails to capture dynamic context injected at runtime, and a container base-image digest omits mutable mounted volumes or external network state. Systems engineers must document omissions explicitly rather than relying on identifiers of ambiguous scope.

Evaluation assessments bind directly to the exact byte representation tested. If a trajectory earns a passing score on a targeted capability test, that verdict applies only to that evaluated representation; any pending criterion remains pending when the record enters cold storage. The downstream evaluation cascade alone determines whether the available evidence authorizes a specific learning use, and cryptographic integrity checks then verify that the assessed byte representation is the exact one a downstream trainer reads.

### Integrity and Authentication

^sec-vol3-trajectory-curation-integrity-authentication

A trainer decides what to train on by reading the corpus manifest, so it must be able to confirm two things before the first gradient. The first is that the manifest is the one curation issued. The second is that no record was altered or swapped after admission, whether by a broken pipeline script or by anyone with write access to the store. Integrity mechanisms answer those two questions. They establish unmodified bytes, not correct content or permitted use. A cryptographic digest identifies a specified byte representation under standard collision-resistance assumptions. For that digest to remain meaningful across system components, the lineage envelope must fix both the canonical serialization scheme and the schema version over which the hash was calculated. Comparing an artifact against an expected digest detects bit corruption and unauthorized edits. Storing an unauthenticated digest directly beside mutable content in an object store, however, provides no protection, because an adversary or a broken pipeline script can overwrite the data and the digest together.

To guarantee authenticity, an authenticated manifest cryptographically binds expected artifact digests and associated metadata to a trusted issuing authority. Systems commonly use a message authentication code (MAC), such as HMAC as specified in RFC 2104 ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.16 Source References#^ref-krawczyk1997hmac|Krawczyk et al. 1997]]), computed with a secret key held outside the dataset in a key management service. Because any party holding a shared symmetric key can forge a valid MAC, production architectures often prefer asymmetric digital signatures (such as Ed25519) when datasets are distributed across multiple worker nodes. The manifest must record the cryptographic algorithm, key version, and authorized issuing scope, and key rotation policies must match the operational lifetime of the corpus. Verification confirms only that the authenticated byte representation has not changed since issuance; it covers nothing outside that boundary.

Cryptographic integrity must not be confused with semantic correctness. A faithfully authenticated trajectory trace can still hold hallucinated model outputs, an erroneous grader verdict, or private data that downstream consumers are prohibited from seeing. Similarly, computing a Merkle root[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.17 Footnotes#^fn13|¹³]] over captured execution events proves that a given event belongs to the recorded tree, but it proves nothing about execution events that the logging harness dropped or failed to observe. Claims about trajectory reproducibility must therefore stay within the reconstruction and re-execution boundaries established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.07 Recorded Trajectory Replay#^sec-vol3-persistence-replay|Recorded Trajectory Replay]]**.

### Derived Records

^sec-vol3-trajectory-curation-derived-records

Because an authenticated source record is immutable, scrubbing a private file path or API token from a recorded trace in place would break its digest and erase the only copy of what actually ran, often severing the causal link that justified the agent’s next command. At the same time, the data minimization and disclosure boundaries established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.04 Trace Retention and Privacy#^sec-vol3-evaluation-budgets-disclosure|Disclosure minimization]]** must be enforced before trajectory content enters an ingestion queue, a model-assisted curation worker, or a training store. To resolve that tension, a **derived record** is always created as a new version rather than an in-place modification. The derived record binds a reference to its parent trace, the versioned redaction policy and implementation, the explicit set of altered or excised fields, and any intentionally withheld content. Lineage references do not grant read authorization to restricted raw data, and systems must store original raw bytes only where retention policies explicitly permit them. When source records reach their retention expiration limit and are purged, the lineage envelope documents that boundary directly; retaining a cryptographic hash is not the same as retaining the source data. The source also keeps a reverse reference to each derived version, so that a later correction or withdrawal at the source reaches every artifact derived from it ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.10 Trajectory Provenance Tracking#^fig-vol3-provenance-envelope|figure 5]]).

Heuristic pattern matching and named-entity recognition models act as screening mechanisms rather than complete sanitization guarantees. Engineers must validate these detectors across the full output pipeline using realistic end-to-end test cases, including deeply nested payloads and generated metadata. Synthetic canaries provide an empirical measure of detector recall. The curation audit log must record how many canaries were injected, how many escaped detection, which semantic classes and text transformations were tested, and where the inspection boundary was applied. Observing zero canary escapes bounds the leak probability only for the evaluated canary distribution. False positives carry their own cost, because over-aggressive scrubbing strips necessary context and distorts the training signal.

↩︎ Canary values, planted synthetic secrets whose escape reveals a leaking path, are established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/09 Agent Security/V3-09.05 Disclosure Through Permitted Tools#^sec-vol3-security-detectors-canaries|Detectors and canary values]]**.

When scrubbing identifiers across multi-step interactions, curators use consistent pseudonyms to preserve relational dependencies across turns while preventing identity linkage beyond the access scope that the trace’s disclosure boundary permits. Tokenization effects require careful handling: replacing an identifier with a fixed-width placeholder often alters the sequence’s token count and attention boundaries because a placeholder string rarely splits into the same number of subword tokens as the original identifier, shifting every subsequent token index and misaligning any token-level loss masks that were indexed against the unredacted transcript. Similarly, reserializing a structured payload can preserve outer JSON or YAML formatting while silently breaking nested shell escaping, regular expression matches, or tool invocation syntax. Consequently, checking that an artifact parses successfully is distinct from verifying that it still supports the intended learning target.

↪ Re-verifying selected response spans against token offsets after templating or redaction shifts token boundaries is developed in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.04 Serializing Trajectories#^sec-vol3-fine-tuning-template-rendering|Rendering with versioned templates]]**.

Revalidation must systematically test every property that the transformation could have influenced. This includes validating record structure, ensuring action-observation consistency, verifying that the sanitized context still justifies the target action, and re-evaluating any criteria whose supporting evidence was altered. If a transformation modifies executable code or environment-dependent identifiers, the pipeline must execute the code against an isolated, authorized test fixture to obtain fresh runtime evidence, while archiving prior execution logs as historical artifacts.

**Example 15.1: A transformed record needs a new decision**

**Scenario**: During a collection run, an agent’s observation records a private system path that a subsequent diagnostic command references, and the source trace captures the successful output of that command. The curation pipeline replaces the path with a sanitized placeholder throughout `trace_r19_01_redacted_v1`.

**Diagnosis**: The recorded execution output remains valid evidence only for the original run bound to `trace_r19_01`; the agent never executed the sanitized placeholder path. The curator must determine whether the sanitized observation and the subsequent command still constitute a coherent learning example. A consistent placeholder can teach an agent how to parse and inspect arbitrary paths without exposing production directory structures. However, replaying the trajectory against an active execution harness requires an authorized, compatible mock fixture; otherwise, the substituted path fails to resolve. If the substitution obscures the causal distinction that prompted the agent’s action, the pipeline must reject the target for supervised training or withhold the record. The derived record inherits the source’s task grouping and train/test split assignment, while all pending evaluation verdicts remain pending until formal revalidation completes.

**Systems lesson**: Cryptographic integrity establishes which source artifact was transformed, whereas revalidation establishes what the transformed trajectory teaches. Neither operation can alter what physically occurred during the original execution run.

### Use Permission and Withdrawal

^sec-vol3-trajectory-curation-permission-withdrawal

Permission to execute an agent against a task fixture or inspect an internal repository does not convey permission to retain its artifacts, fine-tune models on its data, or publish the resulting corpus. The lineage envelope must record the explicit licensing constraints, the evidentiary basis for data retention, and the designated policy authority or human reviewer who approved data usage. This accounting must cover both the primary task assets and all third-party software dependencies pulled into the environment during execution. Automated license detectors and embedding-based similarity screens help identify suspect components, but they serve as screening tools rather than autonomous legal adjudicators.

When provenance evidence is ambiguous or incomplete, the curation pipeline must withhold the record from downstream consumers while logging the specific withholding rationale. This quarantine is use-specific: an asset held from public pretraining might remain eligible for internal safety evaluations. Furthermore, use-permission holds operate independently of task failure labels, confidentiality tiers, and fault-containment quarantine. Resolving a safety fault or task defect does not automatically grant data-usage clearance.

⇄ **Contrast:** Incident containment, which holds the work a suspect trajectory might touch rather than withholding a record from one use, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.09 Incident Containment#^sec-vol3-sagas-quarantine|Incident Containment]]**.

Approved data permissions operate under strict temporal and organizational scopes. To enforce policy changes, reverse references must connect each source record to its derived views, tokenized dataset partitions, and published corpus manifests. When an upstream data provider revokes permission, or when an organization updates its privacy policies, the system must propagate the restriction or withdrawal to every downstream artifact. The ingestion pipeline immediately halts new admissions under the revoked policy, while the catalog traces all distributed artifacts. Deleting a record from an active storage bucket leaves distributed offline copies and completed model parameter updates intact; managing those downstream exposures requires explicit operational ownership, retraining schedules, and audited unlearning procedures.

**Checkpoint 15.2: Defend a derived record's use**

Each bullet asks for a decision a curator makes before a derived record ships.

**Integrity vs. truth**: A manifest’s MAC verifies. Decide which of these it establishes: the bytes are unmodified, the grader verdict is correct, the record is permitted for training.

**Transformation**: A replacement preserves JSON parsing but changes a path used by a later action. Which historical evidence remains valid, and which learning-use checks must be repeated before admission?

**Screening**: A detector test inserts canaries of three classes and observes zero escapes. What claim can the report make, and which record classes remain untested?

**Lineage**: A redacted record’s source task is in the final-test group. Decide whether the redacted version may enter training, and name what must happen when an admitted source is later withdrawn.

A well-architected trajectory record has a verifiable origin, an explicit transformation history, a legally scoped permission envelope, and preserved evaluation boundaries. Connecting an execution trace through this provenance graph into a corpus manifest gives membership a precise meaning: verified fitness for a declared learning consumer. Carrying one record through every stage shows how these decisions fit together.
