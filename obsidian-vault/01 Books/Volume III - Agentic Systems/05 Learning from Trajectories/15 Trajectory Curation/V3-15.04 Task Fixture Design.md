# V3-15.04 Task Fixture Design

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15 Trajectory Curation|V3-15 Trajectory Curation]]

^sec-vol3-flywheel-fixtures

When an agent collection worker attempts a complex task such as connection-pool repair repeatedly, it can generate a distinct candidate solution on every run. If an attempt inherits residual state from an earlier repair attempt, however, it no longer demonstrates solving the problem from the declared initial state. Conversely, if a collection pipeline records only the final passing patch, it discards the sequence of tool invocations, intermediate terminal outputs, and error-recovery decisions that explain how that patch was derived. A **collection fixture** prevents both failures by preserving reproducible task conditions while recording the comprehensive execution evidence demanded by downstream learning algorithms.

The task fixture of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-fixtures|Task fixtures]]** already fixes the execution baseline (initial state, dependencies, permitted interfaces, variation policy, evidence boundary, and reset). Trajectory curation layers a collection contract on top of that fixture. The collection contract specifies why the task belongs in the corpus, which interaction records the ingestion pipeline may retain, and what intermediate evidence downstream admission filters will require.

### The Collection Manifest

^sec-vol3-trajectory-curation-collection-manifest

If a new collection run on `pool_repair_01` reuses the trial identity of `ws_r19`, overwrites the unresolved record of `test_r18`, or lets engineers adjust admission rules after inspecting the sampled outputs, the pipeline corrupts its own audit trail. Separating the versioned identities of the task specification (`pool_repair_01`), execution fixture (`pool_fixture_v1`), and evaluation criteria (`repair_accept_v1`) prevents that collision. Each new collection attempt receives its own run identity and produces an independent candidate artifact, while the historical evaluation candidate `ws_r19` stays permanently bound to its original trial, and a newly passing test run never alters an earlier unresolved record such as `test_r18`.

The **collection manifest** references the underlying evaluation fixture and records the operational decisions summarized in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.04 Task Fixture Design#^tbl-vol3-curation-fixture-use|table 2]]. Defining these fields before sampling begins ensures that data engineers fix the intended training role and capture requirements in advance, rather than biasing the sample or fitting admission rules retroactively to observed outputs.

| Collection field         | Decision recorded                                                                                                                | Consequence for the repair                                                                                     |
|:-------------------------|:---------------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------|
| Learning use             | Proposed behavior to improve and intended artifact consumer                                                                      | Collect evidence for interpreting failed checks and choosing a justified next action, not merely final patches |
| Source and permitted use | Task origin, access conditions, retention scope, and applicable restrictions on derived data                                     | Permission to inspect a repository does not by itself authorize exporting its contents into a corpus           |
| Task relationships       | Stable task identity, source lineage, and links to variants or shared solutions                                                  | Repeated attempts and derived variants remain identifiable when splits are assigned                            |
| Collection configuration | Sampling system, prompt and tool versions, allowed variation, and attempt-selection policy                                       | Distinguish a policy change from a changed task or collector                                                   |
| Required capture         | Delivered context, proposals, matched observations, candidate identity, and criterion-level evidence needed for the proposed use | Preserve what supported each decision, including incomplete observations and rejected proposals                |
| Admission policy         | Versioned conditions for accepting a record into each proposed artifact, with unresolved cases handled explicitly                | A targeted pass does not become whole-task acceptance or automatic demonstration eligibility                   |

Table 2: **Collection Decisions Attached to a Fixture**: The collection manifest extends the experimental contract with intended use, relationships, and evidence requirements. Actual admission follows inspection of the resulting record.

^tbl-vol3-curation-fixture-use

What the manifest must capture depends on the consumer that will train on the artifact. A demonstration selected for supervised error recovery must preserve the diagnostic context, error messages, and intermediate inspection steps that explain why a corrective action was taken. An offline preference comparison needs matched decision conditions and environment state across paired rollouts so that the comparison isolates policy differences. A fixture built for online reinforcement learning rollouts must instead expose live, resettable environment instances and versioned reward harnesses rather than static text logs. Because the target loss function decides how admitted trajectory data is tokenized and masked, a trace that lacks certain tool outputs may fail admission for imitation yet remain useful for failure diagnosis. Curation pipelines therefore tailor their logging schemas to the declared learning objective rather than relying on a single untyped event log, and verify that the grading harness itself is trustworthy before collection begins.

### Adequate and Inadequate Controls

^sec-vol3-trajectory-curation-controls

An automated grader that accepts an invalid solution pollutes a training corpus with false-positive demonstrations, while a grader that rejects valid work starves the collection pipeline. Before launching data collection at fleet scale, engineers calibrate grading harnesses against independently verified **adequate and inadequate controls**, candidate implementations whose expected verdicts are known in advance.

↩︎ Measuring a grader’s false-acceptance rate against independently assessed calibration cases is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.05 Grading Trajectories#^sec-vol3-evaluation-grading-errors|Grader error rates]]**.

For the connection-pool repair task, an inadequate control is a candidate that deliberately keeps the target defect, such as leaving worker threads blocked after a connection returns to the pool (the missed-wakeup bug). This buggy candidate must reliably trigger a failure in the reproducer suite. Conversely, an adequate control is an independently reviewed reference patch that resolves the issue cleanly; it must consistently pass the test harness. If the reproducer accepts the buggy control or rejects the reference repair, the failure points to a flaw in the test harness, flaky environment state, or broken process exit bindings that must be fixed before collection proceeds. Each control isolates and tests a specific grading criterion. A run that produces the reference repair must satisfy the full suite of regression, execution, resource, and residual-duty checks defined in `repair_accept_v1`. Separate controls check that the agent does not alter protected configuration files or emit premature completion signals.

The harness that grades collection runs executes outside the agent’s authority boundary, satisfying invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]). It keeps the grader isolation of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-grader-isolation|Grader isolation]]**, so candidate code cannot rewrite tests, forge exit codes, or read hidden assets, and [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.06 Staged Verifier Cascades#^sec-vol3-verifier-gaming|section 15.5.2]] develops what admission adds to that boundary. Whenever engineers modify a fixture, update a grading rubric, or shift the target task distribution, they validate the changes against fresh control suites rather than inheriting prior trust.

Controls matter equally for tasks that change no persistent state. Consider a read-only evaluation fixture, `report_comparison_v1`, containing two immutable experiment reports. Report A documents that an optimization method was evaluated on Linux; Report B documents that an alternative method was evaluated on Windows. Neither report contains comparative throughput or latency measurements. The agent’s prompt asks for the documented platform coverage and asks whether the reports show which method achieves higher throughput. The task’s grading criteria demand accurate, source-specific attribution, an explicit statement that the throughput comparison is unsupported by the evidence, and strict compliance with read-only access limits.

Here, an adequate control is an independently validated response that maps each platform to its source and declines to declare a throughput winner. Inadequate controls include responses that swap the platform attributions, invent throughput claims, or return an empty answer that omits the documented facts. Because the filesystem stays bit-for-bit identical across all runs, diff-based checks cannot evaluate success; the grading harness must instead run structured field assertions and rubric checks to verify factual attribution and confirm that the agent stated the limits of the evidence. Automated curation can therefore harvest examples of grounded abstention without granting write permissions or requiring workspace patches, across whatever trajectory sources feed the collector.

### Trajectory Sources

^sec-vol3-trajectory-curation-sources

Relying on a single source of trajectories leaves systematic blind spots in a training corpus: production logs overrepresent routine queries and abandoned user sessions, human demonstrations are too slow to cover wide fault matrices, and synthetic rollouts repeat whatever strategy the current policy already favors. Trajectory harvesting therefore draws from all three origins (human demonstrations, production telemetry, and synthetic model rollouts), balancing what each contributes against the collection risk it carries ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.04 Task Fixture Design#^tbl-vol3-data-source-comparison|table 3]]).

| Source               | Useful contribution                                                     | Collection limitation to address                                                                                      |
|:---------------------|:------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------|
| Human demonstrations | Deliberately chosen strategies and explanations for difficult decisions | Expertise does not guarantee correct actions, faithful capture, or representative task selection                      |
| Production records   | Tasks and failures encountered under actual operating conditions        | Retention and user selection can bias the sample; missing evidence and use restrictions can limit reuse               |
| Model-generated runs | Repeated attempts and controlled variations on specified fixtures       | The sampler and grader influence which behaviors appear and survive; repeated success can concentrate on one strategy |

Table 3: **Trajectory Source Trade-offs**: Sources contribute different evidence and coverage. Each still requires an appropriate capture, assessment, and permitted-use contract.

^tbl-vol3-data-source-comparison

These three sources complement one another across the lifecycle of a training pipeline. A production failure reveals a real-world edge case that warrants reproduction in a benchmark. A human demonstration provides an expert recovery strategy to seed the model. Synthetic rollouts explore fault matrices through automated variation. When generating those synthetic rollouts, the environment must compute state transitions dynamically. If an agent emits an action that diverges from a historical trace, the platform cannot replay the next observation from a recorded log; doing so breaks environment causality and feeds contradictory context into the trajectory. Synthetic collection requires a live, interactive environment that generates valid observations for whatever action sequence the policy proposes.

The choice of data source shapes the distribution of harvested behaviors. A collection policy that filters strictly for short, successful runs discards trajectories that show backtracking and fault recovery under partial observability, whereas relying uncritically on production traces overrepresents abandoned sessions and unresolved timeouts. Recording the collection policy, sampling parameters, and task-family metadata in the manifest lets downstream curation stages distinguish genuinely rare engineering events from artificial gaps created by collection filters, and sets up the question of how broadly the task fixtures themselves span the domain.

### Task Population Coverage

^sec-vol3-trajectory-curation-task-coverage

A repair corpus collected only on shallow, single-file bugs with clear stack traces produces a policy that stalls as soon as production code hides a race condition behind deep dependencies or ambiguous test output. To match operational conditions, task distributions must vary systematically across the dimensions that make tasks hard in practice. In software repair, fixtures should vary across dependency tree depth, the clarity of error feedback before an edit, and the concurrency conditions encountered during testing. In document synthesis, fixtures should deliberately include contradictory sources, missing numerical metrics, and schema drift across versions.

The H·S·A exposures (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-hsa|The H·S·A Exposure Space]]**) characterize each variant: the horizon ${H}$ in turns required to solve the task, the state level (${S}_0$ to ${S}_3$) the task retains or mutates across steps, and the authority level (${A}_0$ to ${A}_3$) its tool set grants. Varying a task along these exposures provides a concrete basis for task variation that avoids arbitrary context-length thresholds or the false assumption that all meaningful tasks must mutate a filesystem.

System privileges and tool access grants remain explicit and enforced across all task variants. As a model improves, it may learn to query fewer tools, avoid redundant exploratory commands, or complete tasks in fewer turns. That progress changes the agent’s realized exposure to the environment, but the underlying permissions and runtime sandboxing boundaries stay fixed. Similarly, the environment reset contract governs every reuse of a fixture. If a failed run leaves background processes running, uncommitted file locks, or open network sockets, teardown must clear this residual state before the next collection worker starts, whether the previous trajectory was admitted into the corpus or discarded.

↩︎ The reset contract, which catalogs every piece of state that teardown must clear before an environment serves a new lease, is established in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.09 Sandbox Pools and Reset#^sec-vol3-sandboxes-pooling-reset|The reset contract]]**.

A well-designed collection fixture unifies the task specification and grading criteria with an explicit learning objective, a capture contract, and a structured distribution of variants. Before collection workers run across this task matrix, however, the held-out evaluation tasks must be partitioned and quarantined, so that no collected record can reach the evidence that will later judge the trained model. Reserving those tasks is the focus of [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.05 Split Design#^sec-vol3-flywheel-evaluation|section 15.4]].
