# V3-15.05 Split Design

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15 Trajectory Curation|V3-15 Trajectory Curation]]

^sec-vol3-flywheel-evaluation

Consider an automated collection pipeline that harvests multiple repair trajectories for the same connection-pool defect. If an engineer naively partitions the resulting execution traces at random, one successful repair trajectory lands in the training set while another attempt at the exact same defect lands in the final test set. Varying the random seed, prompt wording, or tool sequence creates superficial operational diversity, but it does not make the underlying engineering problem new. When the fine-tuned policy subsequently encounters this task during evaluation, it does not demonstrate generalization; it merely recalls an environment, bug mechanism, and solution it has already observed during training. This failure mode is **split leakage**: information about an evaluation target reaching the training pipeline through a related or derived record ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.16 Source References#^ref-kaufman2012leakage|Kaufman et al. 2012]]).

In agent trajectory curation, split leakage is the default outcome rather than a rare edge case.[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.17 Footnotes#^fn1|¹]] Suppose an agent executes 8 rollouts per task and an engineer partitions the individual traces at random using a 80 percent/20 percent ratio. A task remains cleanly isolated on one side of the split only if every one of its attempts independently falls into that same partition. For a training fraction ${f_{\text{train}}}$ and ${k}$ independent attempts per task, that non-leakage probability is ${f_{\text{train}}}^{k} + (1-{f_{\text{train}}})^{k}$. Consequently, 83.2 percent of all tasks straddle the train–test boundary, contaminating the evaluation protocol. Partitioning schemes must therefore follow structural task relationships rather than arbitrary trace run identifiers.

![[90 Assets/Volume III/15 Trajectory Curation/Vol3 Trajectory Curation Margin 001 84995c8423.svg]]

*Line chart of the share of tasks that straddle a random 80/20 trace split against attempts per task from one to eight. The curve starts at zero for one attempt and rises steeply, reaching 83 percent at eight attempts, marked with a red dot.*

*With eight attempts per task, a random 80/20 trace split leaves 83 percent of tasks on both sides.*

While the fixture contract defines what an individual execution trial represents, split design governs what subsequent evaluations can validly claim about agent learning. To preserve that validity, engineers isolate and lock down protected evaluation tasks before data collection, model-assisted filtering, or hyperparameter tuning begins. If developers inspect final test failures and then harvest demonstrations targeting those specific failure modes, they turn the test suite into training feedback, and the benchmark ceases to be an independent evaluation even when no raw test trajectory enters the training manifest.

### Evaluation Claims and Task Groups

^sec-vol3-trajectory-curation-claims-groups

A split that holds out individual bug tickets within a single repository cannot test whether a fine-tuned agent transfers to an unseen codebase. A split that holds out entire repository families, by contrast, is unnecessarily restrictive when the agent will only ever serve one internal monorepo. Every evaluation split must therefore begin with an explicit claim about the capability under test. An in-distribution deployment check asks whether an adapted agent can resolve new maintenance tickets within the repositories and runtime environments it already serves. An out-of-distribution transfer check asks whether that agent succeeds across unseen repository families, software architectures, or tool environments. Familiarity with a shared build tool, compiler flags, or API schema reflects legitimate deployment conditions and is not leakage. Evaluating an agent on a defect whose solution appeared during fine-tuning, however, invalidates the measurement under either claim.

To enforce these boundaries systematically, the curation pipeline organizes tasks into groups. A **task group** collects all repeated attempts, paraphrased prompts, derived test fixtures, and solution-equivalent variations of a single underlying problem. If a benchmark contains an issue fixture `pool_repair_01`, any rollout generated from an alternate random seed, a renamed variable, or an identical upstream bug copied into a downstream fork belongs to that same task group. The split manifest records the structural reason for each grouping because simple heuristics fail in opposite directions. Grouping solely by repository name misses cross-repository forks and vendored copies. Grouping by shared dependencies merges unrelated software defects into giant clusters.

Formally, let the group map ${g}({f})$ send an environment fixture ${f}$ to its designated task group, and let the split map ${s}({g})$ assign that group to a partition: training, development, or final test. Every harvested trajectory, synthesized record, or distilled learning example inherits the partition assignment of its originating fixture. Partition integrity requires that:

$$
{g}({f}_i)={g}({f}_j) \implies {s}({g}({f}_i))={s}({g}({f}_j)).
$$

This partitioning invariant guarantees that every known form of a problem stays on one side of the split. Because the guarantee is only as strong as the pipeline’s record of how tasks relate, production split manifests log the active grouping policy, git commit lineages, schema versions, and quarantined matches awaiting human triage. When allocating splits, randomization operates over task groups rather than individual rollouts, stratifying by task complexity or repository size where needed. Evaluation dashboards report group counts alongside raw trajectory counts, because dozens of rollouts on one fixture still test only one problem.

[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.05 Split Design#^tbl-vol3-partitioning-discipline|Table 4]] maps common evaluation claims to their required isolation boundaries. Every valid protocol enforces task-group isolation at a minimum.

| Evaluation claim                                | Additional held-out boundary                                                       | Interpretation                                                                                       |
|:------------------------------------------------|:-----------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------|
| New tasks in the intended operating environment | Underlying task and solution-equivalent variants                                   | Shared repositories and interfaces may match deployment; task answers remain protected               |
| Transfer to new repository families             | Declared related repositories, including relevant forks or copied problem families | Measures transfer beyond those families, rather than universal generalization across all codebases   |
| Adaptation to changed tool interfaces           | Specified schema families or transformations                                       | Tests adaptation to the declared interface shift while holding baseline environment conditions fixed |
| Transfer to new problem domains                 | Named task-domain categories                                                       | Evaluates domain shift specifically, complementing broader operational benchmarks                    |
| Robustness to runtime changes                   | Specified dependency or runtime configurations                                     | Measures resilience to configuration and library drift under controlled operating conditions         |

Table 4: **Partition boundaries follow evaluation claims**: Shared infrastructure and leaked answers represent fundamentally different conditions. Changing multiple axes simultaneously measures a combined shift and obscures attribution.

^tbl-vol3-partitioning-discipline

Engineering teams must also keep development and final-test partitions separate across iterations. Development tasks guide day-to-day tuning of prompts, trajectory filters, and fine-tuning mixtures, while final-test tasks provide a single measurement of the finished system under the declared protocol. Evaluating candidate checkpoints repeatedly against the final test suite and adjusting data mixtures from those scores leaks test signal into the training loop. Whenever a team inspects a final-test failure to diagnose a model flaw or build a training demonstration, it must reclassify that task group as development data and draw an unseen task group to replace it in the final test. Keeping that boundary intact requires controlling every path through which held-out evidence could reach upstream components.

### Held-Out Evidence Protection

^sec-vol3-trajectory-curation-heldout-protection

If a synthetic problem generator reads a held-out test specification, it weaves the target logic into nominally new training fixtures. If an automated trajectory ranker scores candidates by their performance on the final test suite, it tunes the training corpus to that test set without copying a single token. A partition boundary is therefore an architectural firewall across information paths, not merely a directory tag on a storage volume. Reference patches, ground-truth task specifications, hidden unit tests, and final evaluation outcomes must stay isolated from every upstream component: trajectory harvesting prompts, vector retrieval indexes, shared cross-session agent memories, synthetic generators, and model-based selection filters. During a trial itself, the agent likewise receives only the feedback the test protocol permits, such as local development tests, while the hidden acceptance suite stays behind the grader isolation of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-grader-isolation|Grader isolation]]**. Protecting held-out evidence means auditing every one of these access paths across both upstream curation pipelines and the trial runtime.

Whenever new candidate fixtures enter the curation pipeline, ingestion checks compare them against reserved task groups using task identifiers, git commit histories, patch hashes, and abstract syntax trees. Any fixture with ambiguous lineage goes to a quarantine queue for manual review rather than receiving a fresh identifier. Redaction, variable renaming, and schema changes do not break provenance; derived records always inherit their parent fixture’s group assignment. If a later audit finds that training data leaked information about a final-test task, deleting the offending record from the data lake is not enough. Because the leaked signal is already in the weights, the team must retire the checkpoint, re-evaluate any affected claims, and retrain from a clean corpus snapshot.

Even when local split boundaries are airtight, pipelines remain exposed to contamination: the appearance of evaluation tasks or solutions inside the base model’s pretraining web crawl.[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.17 Footnotes#^fn2|²]] Public benchmarks drawn from competitive programming sites or popular open-source repositories often sit inside pretraining corpora, which undermines zero-shot or few-shot generalization claims. Defensible evaluation therefore relies on private fixtures authored behind internal firewalls, commit timestamps audited against model training cutoffs, and documented data provenance, backed by similarity screening to catch unrecorded duplicates before splits are frozen.

↩︎ Contamination is one form of the pre-trial leakage established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-leakage|Evaluation leakage]]**.

### Similarity Screening

^sec-vol3-trajectory-dedup-minhash

Metadata group assignments catch only the relationships the pipeline already knows; a vendored library or a bug copied across unrelated repositories without a shared git commit slips right past them. Similarity screening searches for those unrecorded relatives so they can join their task group before splits are assigned, and the same screen limits redundancy inside the training corpus. In language-model pretraining, removing near-duplicate documents cuts verbatim memorization and improves generalization ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.16 Source References#^ref-lee2022|Lee et al. 2022]]). In agent trajectory curation, however, similarity depends on how a record is represented. Purely textual overlap misleads in both directions. Two repairs can fix the same race condition with almost no shared lines in their patch diffs. Two traces that run the same shell commands and test invocations can diverge completely in how they read the terminal output and recover from errors.

To capture meaningful similarity in agent trajectories, feature extraction combines text shingles, parsed code structure, and tool-call sequences. A **shingle** is a local feature extracted from a document or trace, such as an n-gram of command tokens or a subtree from an abstract syntax tree (AST). While parsing code into an AST strips away formatting differences, aggressive canonicalization (discarding variable names, literal constants, or statement order) can erase the difference between a working patch and a broken one. Curation pipelines therefore version their normalization rules and treat high similarity scores as prompts for inspection rather than triggers for automatic deletion. To compare feature sets across hundreds of thousands of trajectories, pipelines use MinHash ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.16 Source References#^ref-broder1997resemblance|Broder 1997]]),[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.17 Footnotes#^fn3|³]] which compresses large feature sets into short signatures by taking the minimum hash value under each of several random permutations. Workloads where feature counts matter use weighted or bag-based variants instead.

For nonempty finite feature sets ${X}_1$ and ${X}_2$, the Jaccard similarity ${J}({X}_1,{X}_2)$ and the theoretical MinHash collision probability satisfy:

$$
{J}({X}_1,{X}_2)=\frac{|{X}_1\cap {X}_2|}{|{X}_1\cup {X}_2|}, \qquad \Pr\!\left(\min_{{x}\in {X}_1}{\sigma}({x})=\min_{{x}\in {X}_2}{\sigma}({x})\right)={J}({X}_1,{X}_2).
$$

Here, ${\sigma}$ is a uniformly random permutation of the feature vocabulary. Under ${\sigma}$, every element of the union ${X}_1\cup {X}_2$ is equally likely to receive the smallest rank. When that smallest element lies in the intersection ${X}_1\cap {X}_2$, it belongs to both sets and becomes the minimum of each, whereas an element belonging to only one set leaves the other set with a strictly larger minimum. Each permutation therefore acts as a binary trial that produces a match with probability $|{X}_1\cap {X}_2|/|{X}_1\cup {X}_2|$. Across ${n_{\sigma}}$ independent random permutations, the fraction of matching signature components averages those independent binary indicators, forming an unbiased estimator of ${J}({X}_1,{X}_2)$ with variance ${J}(1-{J})/{n_{\sigma}}$ ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.16 Source References#^ref-li2022cminhash|Li and Li 2022]]). Production systems approximate true permutations with universal hash families and define explicit fallback rules for empty feature sets.

Comparing every pair of MinHash signatures directly still scales quadratically with corpus size, so pipelines index signatures with Locality-Sensitive Hashing (LSH).[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.17 Footnotes#^fn4|⁴]] An LSH index splits an ${n_{\sigma}}$-component signature into ${b}$ bands of ${r}$ rows each (${n_{\sigma}} = {b} {r}$). Two trajectories become candidate near-duplicates if their signatures match across all ${r}$ rows in at least one band. With independent hash components, a pair with Jaccard similarity ${J}$ matches all rows of a given band with probability ${J}^{{r}}$, and collides in at least one of the ${b}$ bands with probability:

$$
{p_{\text{candidate}}}=1-(1-{J}^{{r}})^{b}.
$$

This function forms an S-shaped selection curve whose steep region sits near $(1/{b})^{1/{r}}$. With the signature length ${n_{\sigma}} = {b} {r}$ held fixed, the two parameters trade off directly. Moving components from rows into bands (fewer rows per band, more bands) shifts the curve toward lower similarities, which catches more potential duplicates at the cost of larger collision buckets and heavier downstream review. Adding bands without reducing rows shifts the curve the same way while lengthening every signature.

![[90 Assets/Volume III/15 Trajectory Curation/Vol3 Trajectory Curation Margin 002 62fb0de471.svg]]

*S-shaped curve of candidate probability against Jaccard similarity from zero to one for 32 bands of 4 rows. The curve stays near zero below 0.2, rises steeply between 0.3 and 0.6, and reaches nearly one by 0.8. Dots mark 87 percent at 0.5 and nearly 100 percent at 0.8.*

*Banding transforms candidate retrieval into an S-shaped probability curve governed by the number of bands and rows.*

With ${n_{\sigma}} =$ 128 independent ideal components, the variance ${J}(1-{J})/{n_{\sigma}}$ peaks at ${J} = 0.5$, so the standard error is at most $0.5/\sqrt{{n_{\sigma}}}$, or 0.0442 on the Jaccard scale. Storing each component in 4 bytes requires 512 bytes per signature and 51.2 MB for 100,000 records. While this raw matrix excludes the feature inverted index, metadata storage, and candidate staging buffers, it shows that signature storage is small even for large corpora.

The index configuration of 32 bands with 4 rows retrieves a pair with similarity ${J} =$ 0.5 with candidate probability 87.3 percent, and candidate retrieval becomes virtually certain at ${J} =$ 0.8. Downstream review capacity, whether automated AST diff verification or human inspection, is the binding constraint. Because this configuration routes most moderately similar pairs to review, engineers tune the band geometry to their review budget rather than to an abstract similarity target.

Engineers must inspect candidate pairs in context before merging task groups or discarding trajectories from the corpus. Trajectory deduplication differs from document deduplication: a short, three-step execution trace is not automatically better than a longer trace that shows error recovery, and two agents that produce identical code patches may have taken distinct decision paths that are both worth keeping. Once every known and screened relative is locked into its group’s partition, the admission cascade can evaluate each candidate record on its own evidence.
