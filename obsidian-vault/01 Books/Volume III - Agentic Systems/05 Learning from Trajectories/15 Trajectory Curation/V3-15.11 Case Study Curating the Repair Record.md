# V3-15.11 Case Study Curating the Repair Record

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15 Trajectory Curation|V3-15 Trajectory Curation]]

^sec-vol3-flywheel-synthesis

The recovery run `collection_run_r19_01`, whose targets [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.07 Recovery Demonstration Curation#^sec-vol3-trajectory-curation-conditioning-evidence|section 15.6.2]] selected, exercises each stage of that admission and provenance chain. Its refused edit, schema inspection, and corrected edit produced `ws_r20`, which satisfied `repair_accept_v1`. The raw trace `trace_r19_01` records that sequence without altering any earlier record, neither the pending trial verdict on `ws_r19` nor the unresolved earlier test operation `test_r18`. The curation question is which parts of this record may enter a learning artifact, for which consumer, and on what evidence.

The training objective is recovery from harness refusals, the residual behavior that the campaign’s probes left with the model. The target policy `recovery_targets_v1` already fixed which tokens contribute direct supervised loss: the schema query `e3`, the corrected edit `e4`, and the final summary `e6`. The refused proposal `e2`, the test summary `e5`, the task prompt, and the intermediate tool responses stay as conditioning context. Target selection is only the first stage of admission. The record that actually enters a corpus is a transformed view of `trace_r19_01`, so the remaining stages must verify that view, bind its provenance, and publish it to a manifest.

### Admission of the Derived View

^sec-vol3-trajectory-curation-derived-view-admission

Replacing sensitive fixture paths in `trace_r19_01` with synthetic placeholders produces `trace_r19_01_redacted_v1`, but if that redaction strips the file names the agent needed to deduce the schema, training on the redacted trace teaches the model to guess rather than inspect. While the underlying execution stems directly from the original run, admission filtering must verify whether this sanitized view preserves the causal chain of the recovery lesson rather than assuming the raw run’s pass carries over. The admission pipeline does not demand byte-for-byte fidelity with historical environment state; it requires that the transformed trace still support supervised imitation of the selected targets. [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.11 Case Study Curating the Repair Record#^tbl-vol3-synthesis-trajectory-roles|Table 14]] evaluates this derived view against the curation cascade’s admission predicates, where each passing verdict in a production manifest links directly to an underlying verification log.

| Admission predicate                                   | Evidence and decision for this record                                                                                                                           | Remaining boundary                                                                                                                                                                  |
|:------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Record adequacy, $\text{chk}_{\text{record}}$         | The retained source and transformation records preserve the relevant delivered context, event associations, refusal, correction, and candidate-specific results | Retaining the malformed proposal provides necessary conditioning context without selecting it as a supervised training target                                                       |
| Permitted use, $\text{chk}_{\text{use}}$              | The approved-use decision covers this derived view and imitation use; its source task group was assigned to training before collection                          | Path redaction maintains the original task group and split assignment without granting broader permissions or creating an independent evaluation task                               |
| Process conditions, $\text{chk}_{\text{proc,demo}}$   | The declared assessment permits correction of this malformed proposal and supports the required authority, resource, and residual-duty conditions               | Because the harness rejected the malformed proposal prior to dispatch, no unauthorized disk modifications occurred; other prohibited operations require distinct safety evaluations |
| Outcome criteria, $\text{chk}_{\text{out,demo}}$      | The collection’s source assessment satisfies `repair_accept_v1` for `ws_r20`; the derived record preserves the scope of that finding                            | Passing test suites in the original workspace verifies the code repair, but does not certify executable replay against the redacted paths                                           |
| Target suitability, $\text{chk}_{\text{target,demo}}$ | A use-specific review finds that the transformed context supports the selected schema inspection, corrected edit, and bounded report                            | Admitting these specific target tokens for supervised imitation does not validate other model turns or authorize arbitrary downstream tasks                                         |

Table 14: **An Admission Decision for a Derived Recovery Record**: The predicates apply to identified evidence and a specified consumer. A missing required assessment leaves the decision pending or unknown rather than inheriting an unconditional pass.

^tbl-vol3-synthesis-trajectory-roles

Because each predicate evaluates to true, the pipeline admits the transformed example as a verified decision demonstration. Had path substitution stripped the file names essential for the agent to deduce the correct schema, target suitability ($\text{chk}_{\text{target,demo}}$) would have failed. Furthermore, while this redacted trace is valid for token-level imitation learning, it cannot serve a downstream consumer that requires executable replay, because executing the synthetic paths would require spinning up a fresh environment with matching mock fixtures. A single execution lineage can therefore support fine-tuning while being disqualified from offline replay benchmarks. Neither a valid cryptographic digest nor an overall task pass provides blanket approval across different training regimens.

### Corpus Manifest Publication

^sec-vol3-trajectory-curation-manifest-publication

Admitting `trace_r19_01_redacted_v1` into a storage bucket without binding its target mask, split group, and grader versions leaves a downstream trainer free to supervise the refused edit `e2` by mistake or leak the task into evaluation. Publishing the curated trajectory to the corpus release `repair_demonstrations_v1` prevents that drift by recording every link in the artifact’s provenance chain inside the corpus manifest. For this member, the manifest binds the record to its originating run (`collection_run_r19_01`), task identifier, fixture snapshot, candidate code patch, and evaluation grader versions. It references both the transformed trace (`trace_r19_01_redacted_v1`) and the target selection policy (`recovery_targets_v1`), while logging the specific data governance approvals, task group assignments, and split partition versions. Any missing metadata or inactive model dependencies are explicitly tagged as unavailable rather than omitted.

At the corpus level, the manifest catalogs the source data pools, sampling weights, token accounting budgets, domain coverage metrics, and the formal evaluation protocol. Maintaining clear distinctions among raw interaction counts, stored trace tokens, and selected supervised target tokens prevents deceptive accounting. During training, serialization formats and loss masks enforce these target boundaries, ensuring that future trajectory steps never leak into earlier conditioning windows.

This curated trajectory yields a single demonstration artifact. It cannot be repurposed as a preference pair, because the rejected proposal `e2` and the later edit `e4` follow different prefixes (`e4` comes after the refusal and the schema lookup), so they are not alternative continuations of one context. A preference artifact would need competing completions sampled from one saved branch point. Similarly, publishing an environment for reinforcement learning rollouts requires exporting the task fixture, harness configurations, and dynamic graders, rather than static token sequences.

Publishing an immutable corpus manifest establishes a versioned training baseline, which remains separate from deployment governance for any resulting model. Tracking lineage guarantees that if an upstream fixture defect or data privacy request emerges later, pipeline operators can cleanly trace and purge all derived artifacts across downstream model versions. At the infrastructure layer, ephemeral execution sandboxes are destroyed and billed compute charges are settled independently of whether a trace reaches the corpus manifest.

### Cost per Emitted Artifact

^sec-vol3-trajectory-curation-cost-per-artifact

Because every initiated run incurs compute and verification charges whether or not it reaches the manifest, raw trial volume is a deceptive metric for collection economics. A pipeline may execute thousands of autonomous interactions yet emit only a small handful of usable training samples, as trajectories fail safety filters, duplicate existing task solutions, crash during tool dispatch, or remain stalled in asynchronous evaluation queues. Consequently, systems engineers must evaluate collection economics using the cost per emitted artifact, amortizing all spent compute and infrastructure overhead across the accepted dataset.

For a given collection cohort and accounting cutoff, let ${C_{\text{cohort}}}$ represent the total monetary expenditure incurred across environment provisioning, inference generation, tool sandbox execution, automated verification, human review, redaction transformations, and storage. Let ${N_{\text{emit}}}$ denote the number of valid artifacts emitted for a designated consumer by that cutoff. The cost per emitted artifact is defined as

$$
{C_{\text{emit}}}=\frac{{C_{\text{cohort}}}}{{N_{\text{emit}}}},\qquad {N_{\text{emit}}}>0. \tag{5}
$$

^eq-cost-usable

The numerator ${C_{\text{cohort}}}$ captures all unproductive runs, rejected proposals, and pipeline failures; if a cohort yields zero usable artifacts (${N_{\text{emit}}} = 0$), the pipeline registers the incurred financial loss without dividing by zero. Structurally, [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.11 Case Study Curating the Repair Record#^eq-cost-usable|equation 5]] mirrors the cost per accepted task formulation (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**): the unit cost equals the average cost per attempt divided by the end-to-end emission yield. This metric isolates data acquisition efficiency, distinguishing curation costs from both runtime inference serving and subsequent model fine-tuning.

**Napkin Math 15.7: Cost follows the emitted artifact**

**Problem**: A collection cohort initiates 500 collection attempts, incurring \$300 in fully accounted costs across environment provisioning, generation, tool calls, automated verification, curation transforms, storage, and human review. The demonstration selector emits at most one artifact per task. What does each emitted artifact cost, and which operational lever most effectively reduces that price?

| Disposition at the cutoff           | Attempts | Meaning for this demonstration artifact                                                                          |
|:------------------------------------|---------:|:-----------------------------------------------------------------------------------------------------------------|
| Selected and emitted                |       15 | All required admission conditions and selection decisions are complete                                           |
| Otherwise assessed but not selected |      470 | Record and use conditions pass; a recorded process, outcome, target, or redundancy decision excludes the attempt |
| Ineligible for this use             |       10 | A specified split or transformation-use condition fails; no other row counts these attempts                      |
| Pending assessment                  |        3 | A required decision is still expected within its observation window                                              |
| Unknown at the cutoff               |        2 | Required evidence is unavailable or insufficient, with the reason retained                                       |
| Total accounted                     |      500 | Every initiated attempt appears once                                                                             |

Table 15: **Cohort Dispositions for One Consumer**: These hypothetical counts belong to this acquisition worksheet, not the earlier token-pool or cascade-planning examples. The detailed registry retains each nonselection reason.

^tbl-vol3-curation-cohort-dispositions

**Math**: The selected-and-emitted row of [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.11 Case Study Curating the Repair Record#^tbl-vol3-curation-cohort-dispositions|table 15]] yields an emission rate of 15 / 500 = 3 percent. The average cost per attempt is \$300 / 500 = \$0.60. Applying [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.11 Case Study Curating the Repair Record#^eq-cost-usable|equation 5]] yields \$0.60 / 3 percent = \$20 per emitted artifact. This emission yield differs from a task-completion rate, because the curator caps repeated solutions for the same task and several nonselected runs successfully resolved their repair targets. It is also far below the route yield of notebook [15.2](https://mlsysbook.ai/vol3/15_trajectory_curation/15_trajectory_curation.html#nbk-14-verification-cascade-economics-and-throughput), which counts the records that pass one route’s predicates. Emission yield charges every initiated attempt with the per-task cap, redundancy decisions, ineligibility, and whatever is still pending at the cutoff.

**Systems insight**: Because unit cost equals attempt cost divided by emission yield, curation yield serves as the primary economic lever. For example, raising yield to 6 percent cuts the unit price in half to \$10. With 97 percent of attempts failing to emit a usable artifact, engineering effort should focus on diagnosing nonselection causes before purchasing additional generation compute. High redundancy indicates that the system should launch fewer attempts per task; ineligibility points to split or permission defects caught too late; and backlogged pending evaluations point to verification bottlenecks.

A published manifest documents what was emitted, verifies eligibility across all admission gates, isolates supervision targets, and tallies total acquisition cost. Operational efficiency and curation hygiene, however, are prerequisites rather than guarantees of model improvement. The test of a curated corpus is offline evaluation against held-out task groups under controlled benchmark protocols, where neither a low cost per artifact nor a high emission yield can substitute for task performance.
