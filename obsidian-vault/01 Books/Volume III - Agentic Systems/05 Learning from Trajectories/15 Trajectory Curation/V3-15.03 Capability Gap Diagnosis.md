# V3-15.03 Capability Gap Diagnosis

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15 Trajectory Curation|V3-15 Trajectory Curation]]

^sec-vol3-flywheel-gap

In **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13 Agent Evaluation#^sec-vol3-evaluation|Agent Evaluation]]**, the repair agent’s trial on `pool_repair_01` submitted workspace `ws_r19` with its targeted reproducer passing, while regression and resource-accounting checks remained pending. The run was therefore neither an accepted repair nor a valid demonstration. A separate trial of the same task failed outright after the observation interface silently truncated a search result. The postmortem’s controlled ablation traced most of that failure to the interface: once pagination was added, every continuation from the saved prefix reached an accepted repair, even though the ablation did not prove the model blameless. A team that had collected those truncated-observation runs for training would have taught the model to work around an interface defect that a single adapter change removed. An execution failure belongs in the trajectory curation pipeline only after diagnosis confirms that model weights are the right target for repair. Modifying weights is justified only when confronting a genuine **capability gap**: an operational failure that persists even when the model receives complete context, interacts through a well-formed interface, and runs in a healthy runtime with adequate resources. Every other failure stems from an external system defect that calls for a cheaper, far more reversible engineering fix.

↩︎ The controlled ablation that traced the truncated-observation failure to the interface is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.05 Incident Postmortems#^sec-vol3-postmortem-ablation|Controlled diagnostic experiments]]**.

### Diagnosis and the Learning Objective

^sec-vol3-trajectory-curation-diagnosis-objective

Separating a capability gap from an external system defect starts with decomposing the failing trace, because the final failure verdict on `pool_repair_01` alone revealed nothing about which subsystem broke. The postmortem analysis in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.05 Incident Postmortems#^sec-vol3-evaluation-postmortems|Incident Postmortems]]** separated three distinct events within that truncated-observation incident: an interface defect (the search excerpt arrived without truncation metadata), a forbidden action proposal (the next response proposed replacing a file outside the repair scope), and a successful runtime refusal (the admission gate rejected that proposal before dispatch). Such findings often coexist within a single execution trace. Adding missing truncation metadata repairs the interface contract. Retaining the admission guard enforces system boundaries against out-of-scope dispatches. Training the policy to seek additional evidence addresses model behavior. Each diagnostic finding demands its own engineering remedy.

[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.03 Capability Gap Diagnosis#^tbl-vol3-failure-taxonomy|Table 1]] connects diagnostic findings to candidate system interventions and their corresponding learning objectives. Because multiple failure modes frequently overlap in production traces, engineers must evaluate each candidate intervention under realistic operating conditions. The sequence in which teams investigate and apply these remedies follows directly from their computational cost and operational reversibility.

↩︎ Failure attribution, and the limit of what each finding shows, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.05 Incident Postmortems#^sec-vol3-postmortem-attribution|Fault attribution]]**.

| Diagnostic finding                                                    | Direct system intervention to investigate                                | Possible learning use and its limit                                                                                                                 |
|:----------------------------------------------------------------------|:-------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------|
| A required fact was absent from the delivered context                 | Repair retrieval or assembly and preserve source and omission status     | Teach the model to recognize insufficient evidence and request it; weights cannot supply a reliable current fact that was never observed            |
| A tool description or response violated its interface contract        | Correct the schema, documentation, or observation adapter                | Teach interpretation of valid status and recovery information; learned habits do not repair the interface itself                                    |
| An operation encountered an execution failure or unresolved outcome   | Investigate endpoint behavior, resource bounds, and recovery ownership   | Teach bounded recovery or escalation under represented uncertainty; a retry proposal cannot establish that the earlier effect failed                |
| The model repeatedly chose an unsupported or ineffective continuation | Compare prompts, examples, and targeted policy updates on declared tasks | Collect justified alternative actions or recovery targets; repeated failure alone does not identify a unique cause or prove that training will help |

Table 1: **Diagnostic Findings and Learning Uses**: A direct system repair and a behavioral learning objective can both be justified by the same incident. Each proposal needs its own evidence and scope.

### The Intervention Ladder

^sec-vol3-flywheel-intervention-order

Fine-tuning a model to compensate for an omitted context fact or an ambiguous tool schema is **premature fine-tuning**, an expensive waste of compute and curation effort on a defect that a prompt or schema fix cures in minutes. To prevent that misallocation, the **intervention ladder** orders failure remedies by ascending engineering cost and descending reversibility. Its rungs are context retrieval and assembly, tool definitions and schemas, runtime execution controls, supervised fine-tuning (updating weights to imitate selected demonstrations), and reinforcement learning (updating weights to raise a verified reward on fresh rollouts). Engineers test the inexpensive, reversible rungs first by default, advancing to a weight update only when diagnostic evidence establishes a genuine capability gap and confirms that training improves the behavior rather than masking an interface or runtime defect.

This ordering reflects how cost, reversibility, and enforcement guarantees change across the stack. Engineering and compute costs rise sharply at each rung. Editing a prompt assembly pipeline, schema definition, or runtime timeout modifies version-controlled configuration that an engineer can test against integration fixtures in minutes. Retraining weights, by contrast, requires curating a trajectory corpus, running accelerator jobs, and re-evaluating every capability the model serves rather than only the failing task.

Those cost differences are compounded by reversibility and blast radius. A defect repaired at a lower rung reverts cleanly as a configuration change whose impact is limited to the callers of the changed tool or prompt. Updating model weights, by contrast, alters behavior across the entire input space, and rolling back a checkpoint discards every concurrent improvement alongside the targeted fix. Reinforcement learning sits at the top of the ladder for the same reason: beyond the dataset and validation demands of supervised fine-tuning, it requires distributed rollout fleets, isolated reward verification harnesses, and optimization controls that keep the policy from exploiting loopholes in the reward check.

Even when a weight update succeeds, statistical weights cannot replace runtime enforcement. A fine-tuned policy may propose out-of-scope tool calls far less often, but lower observed failure rates do not guarantee compliance on every permitted input. Invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) requires that execution runtimes never assume policy compliance; resource budgets, authorization checks, and process sandboxes remain hard boundaries regardless of how thoroughly the model has been trained.

The end-to-end argument ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.16 Source References#^ref-saltzer1984endtoend|Saltzer et al. 1984]]) yields the same conclusion for tool interfaces: a function belongs where it can be implemented completely and correctly. A typed action contract (principle [[01 Books/Volume III - Agentic Systems/03 Tool Use/V3 Tool Use Principles#^pri-vol3-strict-action-abi|7]]) provides enforceable guarantees across any model version placed behind it. By contrast, fine-tuning a model to guess fields omitted by an API schema teaches brittle habits that break as soon as the interface changes. An integration test on an observation adapter can verify directly that truncated outputs return explicit pagination markers, resolving the ambiguity at the interface layer without asking downstream models to guess what was cut.

Empirical evidence, rather than administrative habit, decides when a failure climbs the ladder. Engineers test each lower rung with a **counterfactual probe**, a controlled re-execution of the recorded failure trace with that rung’s suspected defect removed. A context probe begins by injecting the missing fact directly into the prompt. An interface probe resumes matched saved prefixes with corrected tool descriptions or schemas and samples fresh continuations under the controlled conditions of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-rigor|Statistical Evaluation Rigor]]** (since replaying a fixed proposal would test only the validation or adapter boundary, not whether the model chooses a different action). If both checks leave the failure intact, a runtime probe runs the identical tool payload inside an isolated sandbox with relaxed resource limits. Whenever a failure disappears under one of these probes, the result supports a repair at that rung under the probed conditions without ruling out other contributing causes. Probing in ladder order routes each resolved defect to an immediate, reversible repair, so only the failures that survive all three probes reach the weights ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.03 Capability Gap Diagnosis#^fig-vol3-failure-diagnostic-tree|figure 1]]). Even then, checkpoints trained on this residual must pass the evaluation protocol of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-rigor|Statistical Evaluation Rigor]]** rather than ship merely because model weights were the last hypothesis left.

A failure that disappears under a probe routes to an immediate systems repair, modifying versioned artifacts that revert cleanly as configuration. The intervention ladder is a diagnostic discipline rather than a rigid queue. When counterfactual probes immediately expose a capability gap in an agent that fails despite complete context, a clear schema, and a healthy runtime, engineers can skip lower-rung changes and proceed directly to targeted training, provided the empirical evidence of the gap is recorded first. Moreover, production environments routinely return partial outputs, transient network timeouts, and service-unavailable errors; training an agent to handle those degraded conditions is a valid behavioral objective, not an excuse to leave broken interfaces unfixed. Notebook [15.1](https://mlsysbook.ai/vol3/15_trajectory_curation/15_trajectory_curation.html#nbk-14-intervention-order-tradeoff) prices the compute and reliability trade-offs across this hierarchy for a representative failure workload.

**Napkin Math 15.1: Pricing the ladder for one failure mix**

**Problem**: A hypothetical maintenance agent executes 50,000 trajectories per month, with 6 percent failing (3,000 total failures). Counterfactual probes attribute 70 percent of the failures to a tool schema that omits a required field and 20 percent to sandbox startup timeouts; only the remaining failures survive every probe. One engineering team repairs the tool schema and scales the sandbox pool before considering training. A second team bypasses system repairs and fine-tunes the base model on all failing trajectories using corrected demonstration targets, training on 4,096-token sequences across 3 epochs. What failure modes does each path eliminate, and what is the direct compute cost of the training run?

**Variables**: The underlying model contains 70.6 billion parameters. Standard transformer training requires approximately 6 floating-point operations (FLOPs) per parameter per token ($6{P} {D}$). A dedicated cluster node of 8 accelerators provides a dense 16-bit compute peak of 989 TFLOP/s per device while sustaining 30 percent model FLOPs utilization (MFU). Accelerator rental costs \$4 per hour. Both paths assume that diagnostic attribution is correct and exclude data curation, annotation, and software engineering labor.

**Math**: System-level repairs eliminate the 2,700 failures attributed to interface and runtime defects (90 percent of all failures), deploying and reverting cleanly as versioned configuration updates. In contrast, fine-tuning indiscriminately across all 3,000 failures trains on 3,000 $\times$ 4,096 $\times$ 3 = 36,864,000 tokens. Evaluating $6 \times \text{parameters} \times \text{tokens}$ yields 1.56 × 10¹⁹ FLOPs of total training compute. At sustained cluster throughput, this workload requires 1.8 h of wall-clock time (14.6 accelerator-hours), resulting in an accelerator invoice of \$58. Fine-tuning exclusively on the 300 residual failures that survived diagnostic probing costs only \$6.

**Result**: The direct accelerator invoice of \$58 is modest, so raw compute expenditure does not govern intervention ordering. The decisive factor is the architectural debt and reliability profile left in production. Under premature fine-tuning, the tool schema still omits the required field and the sandbox pool still times out under load; consequently, those operational failures return whenever the model guesses incorrectly or cluster load spikes. Furthermore, teaching the model to work around missing fields creates fragile behavioral compensations that collapse as soon as the interface changes. Its training corpus also squanders curation and review effort on incidents whose proper remedy was never behavioral. Under the systems repair path, engineers resolve 90 percent of all failures permanently for every model checkpoint, leaving a residual of 300 failures whose curated corpus is focused entirely on genuine policy gaps.

**Systems insight**: The primary risk of premature fine-tuning is rarely compute expenditure; it is architectural misattribution. While an invoice of \$58 appears manageable, training cannot fix the 90 percent of failures rooted below the weights. Only a systems repair resolves those defects permanently across all current and future model generations. The governing engineering principle is to attribute failures with counterfactual probes first, remediate what lies below the weights in software, and train exclusively on the residual capability gap that survives.

Once diagnostic probing isolates a genuine residual failure, engineers must specify the exact behavior to train before gathering examples. For the repair agent, the paginated interface now supplies completeness metadata, but a policy can still ignore it. Runs on the repaired interface that receive that metadata and still draw a conclusion from a partial result form the residual that a learning objective can target. An effective objective does not aim vaguely to “fix failed trajectories.” Instead, it trains the policy to inspect the completeness metadata of a search result, issue a permitted follow-up query when pagination indicates more records exist, and state remaining data boundaries when limits are reached. Evaluating the fine-tuned model requires checking both the final task outcome and the efficiency of the path, including redundant reads, context token use, and unsupported intermediate claims. A policy can easily learn a circuitous investigation habit that raises task acceptance at the cost of high latency and token spend, or an overly aggressive shortcut that skips required checks; neither flaw shows up in cross-entropy training loss alone.

### Learning Artifacts

^sec-vol3-trajectory-curation-learning-artifacts

Targeting that residual behavior does not mean keeping only clean, end-to-end successes, because a pipeline that discards every flawed run throws away most of its training signal. A trace that stumbled on a malformed tool call before recovering still demonstrates how to repair the mistake, and a run that failed outright on a subtle race condition still captures a valuable test environment. Depending on what evidence a trace preserves, a single recorded interaction can feed three distinct learning artifacts, each governed by its own admission criteria.

**Imitation material** consists of complete demonstrations or extracted trajectory segments whose decision steps represent exemplary behavior under the supplied context. When curating an error-recovery sequence, the ingestion pipeline can retain an initial malformed tool proposal and its runtime rejection within the conversational history, while selecting only the subsequent corrected action as the supervised target. Faithfully preserving an error in conversational context provides realism, but supervising a model to imitate an unnecessary retry loop degrades runtime efficiency. Curation explicitly designates the target tokens to be reinforced.

A **preference comparison** pairs alternative trajectories generated from a shared initial context, attaching an explicit, justified preference ordering. Two runs of a task form a valid comparison pair only when their initial state, environment configuration, and accessible action spaces are identical. Furthermore, a failing or degraded run belongs in the rejected slot only when an evaluator records explicit diagnostic criteria explaining why its trajectory was inferior. These supporting assessments, tie-breaking criteria, and conditioning contexts allow offline preference optimization methods to construct statistically sound loss objectives.

↪ The trajectory preference loss, which scores the preferred and dispreferred records against a frozen reference policy, is developed in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.09 Trajectory Preference Optimization#^sec-vol3-fine-tuning-preference-loss|The trajectory preference loss]]**.

A **rollout fixture** bundles a reproducible task environment, versioned configuration fixtures, and an automated grading specification to support online exploration during reward-based reinforcement learning. An unsuccessful execution attempt often reveals a valuable environmental corner case even when none of its recorded actions warrant imitation. In this setting, the trace does not provide demonstration data; rather, it seeds a versioned simulation fixture that recreates the problematic state so the policy can explore alternative trajectories and optimize against the reward specification.

↪ Optimizing a policy against verifiable checks on the rollouts it executes in such an environment is developed in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.03 Foundations of Verifiable Rewards#^sec-vol3-rlvr-need|Foundations of Verifiable Rewards]]**.

These three downstream roles explain why a curation pipeline preserves execution failures rather than discarding them. A single flawed trajectory can support diagnostic root-cause analysis, provide multi-turn context for an error-recovery demonstration, serve as a negative example within a preference comparison, or seed a simulation fixture for online reinforcement learning. The intended downstream artifact dictates the admission evidence required to validate the record. Symmetrically, successful trajectories that produce no state mutations (an agent correctly refusing an out-of-scope request or answering a read-only query) constitute valid imitation demonstrations whenever the task specification requires restraint. Producing a nonempty workspace modification is never an inherent admission requirement.

Every proposed trajectory collection campaign must formally document four elements: the specific behavioral capability to be trained, the target artifact format, the empirical evidence required for admission, and the held-out evaluation claim that will assess the trained model. When trajectory evaluations rely on automated model judges or human annotators, those evaluations must operate under explicit rubrics with evaluator coverage and scoring variance fully exposed.

Curation produces defensible artifacts for declared uses, while held-out evaluation decides whether the resulting model update actually improves the system. That separation is the decision boundary of verified trajectory post-training (principle [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/V3 Trajectory Learning Principles#^pri-vol3-trajectory-post-training|13]]), which holds that a recorded outcome does not by itself determine how a trajectory may be used for learning. Two obligations follow before any record is collected. Fixtures must translate the desired behavior into collectible tasks, and the evaluation split must be reserved first, so that data selection never consumes the evidence later used to judge it.
