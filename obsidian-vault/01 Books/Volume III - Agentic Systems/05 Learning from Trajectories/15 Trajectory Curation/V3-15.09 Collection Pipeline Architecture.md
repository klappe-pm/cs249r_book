# V3-15.09 Collection Pipeline Architecture

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15 Trajectory Curation|V3-15 Trajectory Curation]]

^sec-vol3-flywheel-pipeline

During a collection campaign, a fleet of rollout workers can finish hundreds of candidate traces while downstream test sandboxes are saturated. A multi-predicate check can also stall waiting on a single lagging reviewer after earlier checks have already passed. Because generation, verification, and dataset publication run at different speeds, structuring collection as an asynchronous pipeline decouples the stages within explicit capacity limits. When downstream verifiers or review queues fill up, backpressure throttles or pauses new rollouts before in-flight outputs exhaust staging storage.

### Pipeline Responsibilities

^sec-vol3-trajectory-curation-pipeline-responsibilities

If a rollout worker tears down its execution sandbox before persisting the candidate workspace bytes, or if a network retry submits a duplicate trace without a stable run identity, the collector either loses the evidence for an accepted run or double-counts examples in the published corpus. To give every artifact and buffer reservation an explicit owner across handoffs, the pipeline divides into four responsibilities ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.09 Collection Pipeline Architecture#^tbl-vol3-pipeline-stages|table 12]]). These stages may share a single host or run as distributed services across a cluster; the division fixes ownership of work, state, and evidence rather than hardware layout.

| Responsibility         | Input and owned work                                                                                                    | Handoff condition                                                                                                     |
|:-----------------------|:------------------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------|
| Collection admission   | Versioned task fixture, generator configuration, permitted interactions, preassigned split group, and collection budget | Reserve capacity for admitted work and its bounded output before starting the rollout                                 |
| Rollout and capture    | Execute through the trusted harness; record the available interaction history, candidate artifact, and capture gaps     | Persist the required candidate bytes and manifest at a consistent boundary before releasing their only execution copy |
| Staging and assessment | Hold a bounded record or protected artifact references; run the selected cascade and any separately admitted review     | Record criterion-level results and the proposed learning use, including unresolved assessments                        |
| Dataset publication    | Apply the declared use, transformation, permission, and split policies to assessed records                              | Publish an identified derived version with its eligibility decision and provenance, or record another disposition     |

Table 12: **Collection responsibilities and handoffs**: Each boundary transfers identified work under a capacity and evidence contract. Completing a rollout does not guarantee task acceptance or publication as a training example.

^tbl-vol3-pipeline-stages

At each handoff, the pipeline checks an explicit contract. In a software repair collection run, for instance, the handoff from capture to assessment binds the persisted workspace bytes (`ws_r20`) to the acceptance policy (`repair_accept_v1`) and records which execution artifacts are available for the declared learning use within the trace capture limits. The verification cascade then runs the predicates of [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.06 Staged Verifier Cascades#^sec-vol3-flywheel-verification|section 15.5]], separating whether a rollout solved the task from whether it qualifies as a demonstration, a preference pair, or a rollout fixture. If a predicate cannot be completed immediately, the pipeline records its state as `pending` or `unknown` rather than treating it as a failure. Slow stages such as human review or formal verification pull cases from a dedicated, bounded queue; transferring a record to that queue requires an acknowledgment that buffer space is reserved, so stalled reviews cannot pile up and exhaust staging storage.

↩︎ Trace capture limits and retention boundaries are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.04 Trace Retention and Privacy#^sec-vol3-evaluation-budgets|Trace Retention and Privacy]]**.

Because distributed workers and network links fail, message delivery is retried. Every submission is therefore bound to its collection run identifier, artifact version, and assessment policy. When a retry arrives with an identical payload under the same identifier, the stage returns the existing decision. If the payload differs from the earlier submission under that identifier, the pipeline routes the conflict to an operator queue. A retry never publishes duplicate training examples or frees a staging reservation twice, which sets up the quantitative sizing of those staging reservations.

↩︎ Semantic deduplication of retried writes, which acknowledges an identical retry and rejects a conflicting payload under the same identity, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11.09 Log Retention and State Compaction#^sec-vol3-persistence-engine-design|The storage engine contract]]**.

### Collection Credits and Staging Reserves

^sec-vol3-trajectory-curation-collection-credits

Sizing those staging reservations around average verifier throughput fails as soon as a defective test fixture or unresponsive dependency forces every verifier slot to run until its hard timeout. In steady state, when completed rollouts arrive at verification at an average rate ${\lambda_{\text{arr}}}$ and ${N_{\text{workers}}}$ equivalent verifier slots each require a mean service time ${\bar{T}_{\text{svc}}}$ per record, the pool provides an aggregate service capacity of ${N_{\text{workers}}}/{\bar{T}_{\text{svc}}}$ records per second at nominal utilization ${\rho_{\text{serv}}}={\lambda_{\text{arr}}} {\bar{T}_{\text{svc}}}/{N_{\text{workers}}}$. Little’s law (theorem [5.1](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#thrm-05-littles-law)) gives the mean number of records in service as ${\lambda_{\text{arr}}} {\bar{T}_{\text{svc}}} = {\rho_{\text{serv}}} {N_{\text{workers}}}$, so the nominal utilization is also the fraction of slots occupied on average.

↩︎ Little’s law, which ties mean occupancy to arrival rate and residence time, is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.09 Capacity for Agent Workloads#^sec-vol3-kv-workload-dynamics|Residence time and service rate]]**.

That steady-state baseline breaks when a stall forces every verifier execution to block until hitting its hard timeout ${T_{\text{out}}}$, collapsing aggregate checking capacity from ${N_{\text{workers}}}/{\bar{T}_{\text{svc}}}$ to ${N_{\text{workers}}}/{T_{\text{out}}}$. If rollouts continue arriving at rate ${\lambda_{\text{arr}}}$, unassessed records accumulate in staging at a net rate of ${\lambda_{\text{arr}}} - {N_{\text{workers}}}/{T_{\text{out}}}$ records per second. If each record reserves buffer space up to a maximum per-record ceiling ${s_{\max}}$, a staging storage pool of total capacity ${M_{\text{stage}}}$ that is empty when the burst begins is exhausted after

$$
{T_{\text{exhaust}}}=\frac{{M_{\text{stage}}}}{\left({\lambda_{\text{arr}}}-{N_{\text{workers}}}/{T_{\text{out}}}\right){s_{\max}}}.
$$

A store that already holds records at onset is exhausted sooner, in proportion to the space they occupy. Crossing an alert threshold does not halt staging growth immediately, because two sequential waves of records still arrive before the buffer stabilizes. First, while the controller takes ${T_{\text{react}}}$ to detect the stall and close dispatch, the dispatcher continues launching replacement rollouts, so staging keeps accumulating net reservations at rate $({\lambda_{\text{arr}}}-{N_{\text{workers}}}/{T_{\text{out}}}){s_{\max}}$ throughout that delay. Second, at the moment dispatch finally closes, the rollouts still executing in the fleet hold up to ${M_{\text{inflight}}}$ in reservations that can all complete before stalled verifiers drain them. Subtracting both waves from total capacity ${M_{\text{stage}}}$ bounds the high watermark (the fraction of the store at which the alert must trigger):

$$
\text{watermark} \le 1-\frac{{M_{\text{inflight}}} + {T_{\text{react}}}\left({\lambda_{\text{arr}}}-{N_{\text{workers}}}/{T_{\text{out}}}\right){s_{\max}}}{{M_{\text{stage}}}}.
$$

Notebook [15.4](https://mlsysbook.ai/vol3/15_trajectory_curation/15_trajectory_curation.html#nbk-14-verifier-burst-exhaustion) evaluates how fast staging fills on a representative verification fleet and where dispatch must stop.

**Napkin Math 15.4: How long a staging store survives a timeout burst**

**Problem**: A hypothetical collector runs 1,024 concurrent rollouts that each take 45 s. 512 verifier slots take 16.875 s per record on average. Each record reserves a ceiling of 8 MB in a 32 GB staging store. Treat completions as a steady flow and all slots as interchangeable. A defective fixture then makes every test run to its 120 s timeout. How long until the store is fully reserved, and where must dispatch stop if the controller needs 30 s to act?

**Math**: Rollouts complete at 22.8 records per second against a nominal capacity of 30.3, giving a utilization of 0.75; by Little’s law, that is also the average fraction of the 512 slots in use. During the burst, capacity falls to 4.3 records per second, so staging grows by 18.5 records, or 147.9 MB/s of reservations, every second. Starting from an empty store, it is fully reserved after 216.3 s, about 3.6 min. When dispatch stops, the rollouts already running still hold up to 8.2 GB of reservations, and growth over the 30 s reaction delay adds 4.4 GB. Subtracting both from the 32 GB store places the high watermark at or below 60 percent of the store.

**Systems insight**: Size staging buffers for service-time collapses rather than nominal steady-state utilization. Even at a modest nominal utilization of 0.75, a verifier stall fills available storage in only 3.6 min. The exhaustion time ${T_{\text{exhaust}}}$ shrinks proportionally as the record ceiling ${s_{\max}}$ increases and scales linearly with total store size ${M_{\text{stage}}}$. Watermarks must account for work already in flight and controller reaction latency, backed by hard credit caps when feedback loops lag.

The in-flight term in that headroom shows why admission control must count unfinished work rather than queue depth. Queue length reflects past arrivals, while rollouts admitted before a verifier stall complete and emit records long after the dispatcher stops issuing new work. Admission controllers therefore limit both the count of active records and their aggregate reserved bytes, and they charge each reservation at the per-record ceiling ${s_{\max}}$ rather than the mean size, because mean sizes set steady-state storage while the ceiling bounds a worst-case burst.

A **collection credit**[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.17 Footnotes#^fn11|¹¹]] enforces both constraints through a single accounting token: every admitted rollout acquires one credit from a shared pool, reserving storage for its maximum possible payload throughout rollout execution, intermediate staging, and downstream assessment. The credit returns to the pool only when the record reaches a durable terminal disposition or completes an acknowledged handoff to another capacity-controlled queue. Consequently, every unit of pending work is explicitly accounted for across the entire cluster. When a trajectory exceeds its expected allocation, the capture harness enforces an explicit truncation policy rather than silently clipping required state. For example, it records the partial execution trace with marked omissions and flags the artifact as ineligible for training regimes that require full fidelity. Because one credit spans all four responsibilities, the pool also bounds work that has left the collector but not yet reached a disposition ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.09 Collection Pipeline Architecture#^fig-vol3-collection-pipeline|figure 4]]).

↪ Credit windows between cooperating agents, and the throughput a window of fixed size allows, are developed in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.08 Bounding In-Flight Work#^sec-vol3-multiagent-credit-flow-control|Credit-based flow control]]**.

![[90 Assets/Volume III/15 Trajectory Curation/Vol3 Collection Pipeline 3d603f5816.svg]]

Figure 4: **Collection Credits Across Four Responsibilities**: Each admitted run holds one credit through rollout, capture, staging, and assessment. The credit returns to the pool only when the record reaches a durable disposition or an acknowledged transfer to another bounded owner, such as the review queue. A watermark derived from in-flight work slows dispatch before the pool is exhausted, and a hard limit stops admission when that feedback arrives late.

^fig-vol3-collection-pipeline

The credit pool directly bounds the count and aggregate record volume of all outstanding runs. This mechanism governs staging buffers, not auxiliary execution resources. Accelerator memory for model inference, sandbox container filesystems, verifier scratch disks, and external object stores each require separate capacity pools with independent accounting. Storing a lightweight URI reference in a message queue does not bound the multi-gigabyte container image or execution trace to which it points. Robust admission controllers verify reservations across all requisite resource pools up front. This pre-allocation invariant ensures that a pipeline stage never acquires one scarce resource, such as an accelerator slot, only to block indefinitely waiting for an unreserved downstream buffer. That credit bound holds even when a completion burst arrives while verification is paused, as notebook [15.5](https://mlsysbook.ai/vol3/15_trajectory_curation/15_trajectory_curation.html#nbk-14-sizing-intermediate-staging-buffers-and) works out for a hypothetical collector.

**Napkin Math 15.5: Reserve capacity before the completion burst**

**Problem**: A hypothetical collector provisions 12 end-to-end credits, each reserving a per-record ceiling of about 2.10 MB. Currently, 4 records sit staged in storage and 8 rollouts are actively executing, each holding an allocated credit while verification is temporarily paused. May the dispatcher admit an additional rollout? Furthermore, once all active rollouts finish and verification resumes, how long will this accumulated cohort take to drain?

**Variables**: 2 verifiers each assess one record at a time in exactly 10 s, including durable disposition; no new rollout is admitted during the drain, and transfer and publication add no delay.

**Math**: The 12 outstanding runs hold every credit: staged records reserve 8.39 MB and running rollouts 16.78 MB, for 25.17 MB (exactly 25165824 bytes) with 0 credits free, so the dispatcher admits nothing. Draining the queue takes ⌈12 / 2⌉ = 6 waves of 10 s, or 60 s.

**Systems insight**: Total byte consumption is strictly bounded by credits multiplied by the ceiling (${s_{\max}}$), independent of arrival timing, while drain latency scales as ⌈credits / verifiers⌉ times service time. Adding verifiers accelerates queue drainage without increasing the byte bound; expanding credits raises both. Engineers should dimension credit pools against physical staging limits and scale verifiers to meet drain deadlines, treating a slower assessment as a longer drain with the reservation still actively held.

The two models bound different quantities. Arrival and service rates govern how rapidly an outage consumes available headroom, while credit limits cap total buffer consumption regardless of timing. Production telemetry must continuously track queue depths, allocated vs. physically consumed bytes, the age of the oldest pending assessment, verification pass rates, and downstream sink throughput. Retries, escalated evaluations, and diagnostic reviews must all consume allocations from this same credit pool. When external dependencies fail, failure containment mechanisms prevent repeated re-verification attempts from amplifying an isolated service outage into cluster-wide failure, leaving steady-state capacity planning to determine which stage limits throughput when the pipeline is healthy.

↩︎ Circuit breakers, coordinated retries, and bulkheads that keep retry amplification from spreading a dependency outage are established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.08 Tool Circuit Breakers#^sec-vol3-sagas-containment|Tool Circuit Breakers]]**.

### The Collection Bottleneck

^sec-vol3-flywheel-bottleneck

Under-provisioning cheap CPU verifier slots can throttle an entire accelerator fleet, leaving expensive generation hardware sitting idle while trajectories wait to be checked. While credit controls prevent staging buffers from overflowing during an outage, steady-state capacity planning compares generation, verification, and storage to find where throughput actually binds. With ${N_{\text{GPU}}}$ accelerators each spending ${T_{\text{gen}}}$ accelerator-seconds per attempt, generation has a service ceiling of ${N_{\text{GPU}}} / {T_{\text{gen}}}$ attempts per second. With ${N_{\text{workers}}}$ verifier slots and expected slot service time ${T_{\text{check}}}$ per attempt from [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.06 Staged Verifier Cascades#^eq-verifier-cost-cascade|equation 1]], assessment has a service ceiling of ${N_{\text{workers}}} / {T_{\text{check}}}$. Charging every write at its per-record ceiling ${s_{\max}}$ gives a conservative provisioned storage rate of ${\text{BW}_{\text{store}}} / {s_{\max}}$ for sustained write bandwidth ${\text{BW}_{\text{store}}}$. With enough credits, work, and scheduling capacity to saturate the stages, the idealized planning rate ${R_{\text{attempt}}}$ is:

$$
{R_{\text{attempt}}}=\min\left(\frac{{N_{\text{GPU}}}}{{T_{\text{gen}}}},\ \frac{{N_{\text{workers}}}}{{T_{\text{check}}}},\ \frac{{\text{BW}_{\text{store}}}}{{s_{\max}}}\right). \tag{4}
$$

^eq-vol3-trajectory-curation-throughput-bound

[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.09 Collection Pipeline Architecture#^eq-vol3-trajectory-curation-throughput-bound|Equation 4]] identifies the binding stage in this stipulated model. Its planned admitted-record rate is ${R_{\text{attempt}}} \cdot {Y}$, where ${Y}$ is the route yield. Actual throughput can be lower because of credits, scheduling, or another shared service. Smaller writes can exceed the conservative storage term, so that term alone does not diagnose an observed storage bottleneck.

The bound separates the stage that limits throughput from the stage that drives cost. In the illustrated low-priced deterministic route, verifiers occupy CPU slots that cost pennies per hour compared with accelerator instances, yet starving that pool stalls the whole collector. Under the notebook’s active-resource accounting, unused capacity is redeployed or unbilled, and generation compute and task yield dominate the charge per admitted record. A dedicated fleet billed during idle wall time has a different cost boundary. Deterministic verification is not inexpensive for every workload. A model judge or a human reviewer can change that split, and Exercise 5 in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.15 Exercises#^sec-vol3-14-trajectory-curation-exercises-d5aa1f5a|section 15.14]] prices a route in which human review dominates. Notebook [15.6](https://mlsysbook.ai/vol3/15_trajectory_curation/15_trajectory_curation.html#nbk-14-collection-bottleneck) evaluates this economic trade-off on a representative deployment.

**Napkin Math 15.6: The cheapest stage can set the rate**

**Problem**: A hypothetical collector uses 64 accelerators, each spending 60 s of accelerator time per attempt at \$2.50 per hour. It checks attempts with the admission route of notebook [15.2](https://mlsysbook.ai/vol3/15_trajectory_curation/15_trajectory_curation.html#nbk-14-verification-cascade-economics-and-throughput), whose cheaper order occupies 6.24 s of slot time per attempt and admits 20.52 percent of attempts, on 4 verifier slots priced at \$0.04 per slot-hour. Records of at most 8 MB go to a store that sustains 200 MB/s. Assume sufficient end-to-end credits and no further shared service bottleneck, charge each write at its record ceiling, and bill only active accelerator and occupied verifier time, with unused capacity redeployed or unbilled. Which stage binds this planning model, and what is the active-resource charge per admitted record?

**Math**: By [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.09 Collection Pipeline Architecture#^eq-vol3-trajectory-curation-throughput-bound|equation 4]], generation supports 64 / 60 s = 1.07 attempts per second, assessment 4 / 6.24 s = 0.64, and conservative provisioned storage supports 200 MB/s / 8 MB = 25. Assessment binds in this model, and matching generation needs 1.07 × 6.24 s, rounded up to 7 slots. Generation costs \$0.042 per attempt; adding checking and dividing by the yield gives \$0.20 per admitted record, of which checking is 0.2 percent.

**Systems insight**: Throughput bottlenecks and cost drivers are often decoupled. In this scenario, running only 4 inexpensive verifier slots leaves 39.9 percent of generation capacity unused. Despite this bottleneck, the financial cost of an admitted record is dominated by generation expense divided by yield, following the cost per accepted task formulation (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**). Adding verifier slots raises the idealized rate until generation saturates while leaving the active-resource charge per record unchanged. With a dedicated fleet billed during idle wall time, greater utilization can instead lower the bill per emitted record. Holding active work per attempt and resource rates fixed, halving the yield to 10.26 percent doubles the unrounded cost per admitted record, displayed to the nearest cent as \$0.41. Fixture design and sampling policy control that yield; their measured cost and coverage consequences determine whether a change is worthwhile.

### Artifact Capture and Resource Release

^sec-vol3-trajectory-curation-artifact-capture

Tearing down a rollout container before its logs and workspace diffs reach durable storage destroys the only copy of the attempt, while reassigning a pooled container before background writers exit lets a stale rollout pollute the next task. Collection pipelines therefore inherit the runtime’s sandbox lifecycle and reset contracts. Rollout workers must persist all candidate artifacts, interaction traces, and evaluation evidence to durable storage before tearing down the execution sandbox. A pooled environment cannot be reassigned until background writer processes terminate, stale network credentials and access tokens are revoked, and filesystem reset postconditions pass. If a downstream verification stage needs interactive access to unpersisted sandbox state, it must hold that environment under an explicit time-bounded lease and operational budget; otherwise, the checker logs the assessment as unavailable and releases the host.

When a worker’s dispatch lease expires, expiration does not instantly terminate the executing process or roll back its external side effects. A replacement worker must therefore establish explicit ownership and verify fresh admission checks, while late-arriving outputs from the orphaned worker remain strictly quarantined to their original run. Similarly, if container cleanup fails or an external side effect leaves an indeterminate state, the owning process retains responsibility under the trajectory saga, even if the associated trajectory is discarded from training. Releasing a collection credit frees buffer staging, but it does not absolve the runtime of its teardown and cleanup obligations. Once physical movement from execution to durable disposition is bounded and accounted for, data governance determines artifact admissibility. It asks which upstream source versions justify inclusion, what lossy or privacy-preserving transformations were applied, and which dataset split partitions and license restrictions govern the resulting weights.

↩︎ The trajectory saga, which keeps a compensation obligation open while an external effect remains unresolved, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^sec-vol3-sagas-architecture|The Trajectory Saga Pattern]]**.
