# V3-16.08 Schema Robustness

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16 Trajectory Fine-Tuning|V3-16 Trajectory Fine-Tuning]]

^sec-vol3-fine-tuning-schemas

Suppose a deployment updates its `read_file` tool so the active interface requires a string argument named `target_uri`, forbids extraneous keys, and resolves paths relative to an authorized fixture directory. Even when training trajectories such as `trace_r19_01_redacted_v1` taught the repair agent to inspect a tool schema after a refusal, a corpus that showed only one static `read_file` signature across thousands of examples lets the policy memorize legacy parameter keys in its weights instead of reading the contract supplied in the prompt context:

``` json
{
  "proposed_call": {
    "name": "read_file",
    "arguments": {"file_path": "src/pool.py"}
  },
  "current_argument_schema": {
    "type": "object",
    "properties": {"target_uri": {"type": "string"}},
    "required": ["target_uri"],
    "additionalProperties": false
  }
}
```

This proposal violates the presented schema because it omits the required `target_uri` property and supplies the disallowed `file_path` key. Because the agent runtime validates invocations before dispatch, the schema validator rejects the call immediately; the compatible payload is `{"target_uri": "src/pool.py"}`, and whether that path exists and whether the agent holds authorization to access it remain independent downstream runtime checks. Consulting a schema in a recorded trace and adhering to an altered interface contract at serving time are therefore two distinct capabilities, and testing whether a model genuinely conditions on the presented schema requires perturbing the interface definition while holding the underlying task fixed.

Emitting stale parameter keys is a clear failure mode of interface memorization, but attributing it to trajectory fine-tuning requires controlled comparison, because base foundation models also make schema errors when prompted zero-shot. Isolating the effect of fine-tuning demands evaluating both the base and fine-tuned policies under identical prompts, sampling parameters, and tool schemas; [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.12 Evaluating a Fine-Tuned Agent#^sec-vol3-fine-tuning-benchmarking|section 16.11]] formalizes the metrics and comparison protocol that establish this attribution.

### Schema Augmentation

^sec-vol3-fine-tuning-schema-augmentation

To keep the policy from memorizing `file_path`, **schema augmentation** constructs training trajectories with declared interface mutations so the model must read the argument names from the prompt context rather than from its weights. That transformation requires more than a string find-and-replace on tool-call arguments: renaming `file_path` to `target_uri` in the call while leaving `file_path` in the prompt schema or in an earlier error message trains the policy on a contradictory transcript. Every part of the decision context (schema definitions, selected calls, mock observations, and error messages) must change together, and the resulting derived trajectories are tracked under the lineage rules of **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.10 Trajectory Provenance Tracking#^sec-vol3-trajectory-curation-derived-records|Derived records]]**. Conditioning policies directly on delivered interface contracts is well established: incorporating retrieved API documentation into training prompts lets fine-tuned models adapt when documentation changes after deployment ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-patil2023gorilla|Patil et al. 2023]]). [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.08 Schema Robustness#^tbl-vol3-schema-perturbation-operators|Table 9]] pairs each schema transformation with the consistency check that keeps the resulting trajectory coherent.

↩︎ The rule that a transformed trajectory becomes a new derived version bound to its parent trace is established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.10 Trajectory Provenance Tracking#^sec-vol3-trajectory-curation-derived-records|Derived records]]**.

| Transformation                        | Intended coverage                                                | Required consistency check                                                                                                           |
|:--------------------------------------|:-----------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------|
| Reorder declarations or object fields | Dependence on one textual order where order has no semantic role | Preserve represented values and dependencies; do not shuffle dependent tool operations                                               |
| Rename tool or argument identifiers   | Binding the call to the presented interface                      | Update schema, selected calls, documentation, and relevant embedded references; provide compatible adapter behavior                  |
| Add unused tool declarations          | Tool selection amid additional choices                           | Keep distractors coherent with available capabilities and authority; account for longer or ambiguous context                         |
| Remove an optional argument           | Behavior when a previously available option is absent            | Establish the replacement default or behavior, then recheck observations and target adequacy; deletion need not preserve the outcome |

Table 9: **Coherent Schema Transformations**: Each augmentation changes a decision context and therefore requires more than surface substitution.

^tbl-vol3-schema-perturbation-operators

In the read-tool example, a meaning-preserving rename needs an adapter that maps `target_uri` to the underlying file operation. Every prior tool output, system prompt, or turn that mentions `file_path` must be updated across the context, so the derived record shows a coherent interaction without claiming those bytes appeared in the original historical run. Whenever a transformation changes return values, ordering, defaults, or side effects, the pipeline generates fresh execution evidence, either by replaying the trajectory in an instrumented sandbox or by synthesizing verified responses, rather than splicing stale historical observations onto modified calls.

These transformations carry direct storage and compute costs: renaming identifiers shifts subword boundaries and token counts, adding distractor tools lengthens the prompt at every turn (raising training FLOPs and inference KV-cache footprints), and every synthetic variant expands the corpus that verification pipelines must check. Teams therefore version each transformation pipeline, track token expansion ratios, and test whether the schema transfer gains pay for the added training and review cost.

### Transfer Evaluation

^sec-vol3-fine-tuning-transfer-evaluation

Measuring whether schema augmentation actually prevented memorization requires separating three evaluation regimes: new tasks on familiar tool schemas, familiar tasks on renamed or restructured interfaces, and new tasks on unfamiliar tool families. Mixing these regimes in one score hides where a policy breaks. Evaluation splits must hold out task answers and their synthetic variants, whereas reusing familiar tool schemas across train and test splits is not contamination when the benchmark is testing task transfer under a known interface.

↩︎ The isolation of held-out task answers, and the rule that transformed records inherit their parent’s split group, are established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.05 Split Design#^sec-vol3-trajectory-curation-heldout-protection|Held-out evidence protection]]**.

Within each regime, the evaluation harness separates structural schema conformance, tool selection, and task completion, because a call can pass the JSON Schema validator while invoking the wrong tool, targeting an unauthorized path, or supplying arguments that do not fix the bug. Comparing augmented and unaugmented checkpoints under an equal token budget across both familiar and renamed schemas shows whether the model gained interface robustness without losing task performance, while the runtime continues to validate every call before execution. Supervised imitation and schema augmentation together teach an agent to emit valid calls that match demonstrated behavior; when several valid calls all pass the schema and solve the task at different costs or risks, the objective must move from imitation to preference comparison.
