# V3-16.12 Evaluating a Fine-Tuned Agent

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16 Trajectory Fine-Tuning|V3-16 Trajectory Fine-Tuning]]

^sec-vol3-fine-tuning-benchmarking

A fine-tuned checkpoint can reach a low loss on a repair corpus yet fail to resolve actual connection-pool leaks in production. Training configurations and data manifests record how an artifact was produced, but only closed-loop trials reveal how the policy navigates multi-step execution when its own actions dictate future observations. The task acceptance contract defined in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^sec-vol3-evaluation-contract|The Task Acceptance Contract]]** governs these trials, addressing the specific failure modes and behavioral shifts that weight updates introduce.

### Comparable Loss and Closed-Loop Performance

^sec-vol3-fine-tuning-eval-decoupling

Held-out token loss measures prediction accuracy under teacher forcing, where recorded prefixes are supplied at every step, whereas closed-loop task completion runs the policy on the context history its own actions create under a fixed time and token budget. Even as an offline check for optimization bugs, token losses from two training runs are comparable only when computed under an identical measurement contract: if one run uses an all-token loss and another masks observations, their dashboard losses average over different token sets. In notebook [16.1](https://mlsysbook.ai/vol3/16_fine_tuning/16_fine_tuning.html#nbk-15-gradient-budget-and-compute-allocation), an unmasked causal loss averages across 16,383 prediction terms (of which read-only observations make up 77.1 percent of the stored input), whereas the masked objective averages over the 800 selected response tokens. Comparing raw training losses across those two runs rewards the unmasked checkpoint for predicting repetitive compiler boilerplate rather than choosing better actions. Valid offline comparison requires recomputing held-out loss on a common validation split under the exact same prompt contexts, tokenizer, serialization template, target mask, and normalization rule, logging both the active-target count and the split version. If two checkpoints use different tokenizers, their per-token losses do not even share a common unit.

**Example 16.1: A lower loss is not yet a release decision**

**Scenario**: In an evaluation bake-off, two candidate checkpoints are trained on the same curated trajectories: one with an all-token loss and the other with a selected-target response mask. The run trained on all tokens displays a substantially lower dashboard loss.

**Diagnosis**: The two training metrics calculate averages over incompatible target sets. The all-token run lowers its average by predicting the repetitive parts of environment observations (echoed schemas, boilerplate, repeated paths), whereas the masked run evaluates only policy tokens. Evaluating both checkpoints on an identical held-out validation set using matched response masks makes their loss values comparable. Even a checkpoint with superior held-out loss, however, is evaluated solely on teacher-forced prefixes; during autonomous rollouts, compounding errors can still cause it to invoke invalid tools, misinterpret unexpected exceptions, or blow past its step budget.

**Systems lesson**: Rank candidate checkpoints offline using an identical held-out evaluation loss, but base promotion and release decisions exclusively on closed-loop task acceptance. A checkpoint boasting lower loss remains unpromotable if it fails the recovery criteria specified in the release contract. When modifying training data and loss masks simultaneously, run controlled ablation trials to isolate the source of any observed performance shift.

### Task and Behavior Measurements

^sec-vol3-fine-tuning-eval-scorecard

Because neither held-out loss nor a single syntax check can show whether a weight update improved repair behavior without breaking other tasks, the release harness evaluates a candidate against the full policy stack it would replace across five complementary measurements: budgeted task acceptance, call validity, schema robustness, resource use, and capability retention. Budgeted task acceptance is the primary release outcome, measured under the declared criteria, runtime feedback rules, pinned fixtures, and resource envelopes of the task acceptance contract. Every initiated trial is counted, so runs that stall or time out at the observation cutoff are recorded as failures or unresolved verdicts rather than dropped. When the production deployment wraps the model in a multi-candidate selection or repair loop, the harness evaluates that composite loop alongside diagnostic views such as single-attempt pass rate (pass@1) and repeated-run consistency (pass$^{k}$, **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-pass-k|Potential and repeated-run consistency]]**).

When a trial fails that acceptance check, an end-to-end pass rate does not show whether the policy chose a flawed repair plan or failed to form a legal tool call in the first place. Measuring call validity separates those causes by checking whether generated tool calls satisfy the active interface contract in the production parser and schema validator. Rather than collapsing every bad call into a single failure rate, the harness separates unparsable outputs, missing required fields, type mismatches, and truncated proposals from downstream tool execution errors ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.12 Evaluating a Fine-Tuned Agent#^tbl-vol3-tool-validity-failures|table 11]]).

| Observed category       | Evidence to inspect                                                               | Competing explanations to test                                                                 |
|:------------------------|:----------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------|
| Malformed serialization | Delivered template, raw output, parser contract, and selected training targets    | Defective examples, template mismatch, generation behavior, or capture failure                 |
| Schema violation        | Schema actually delivered for this invocation and the complete proposed arguments | Stale context, inadequate schema coverage, a serialization mismatch, or an incorrect validator |
| Undeclared tool         | Tool inventory delivered to the model and any intervening configuration change    | Learned tool-name preference, missing interface context, or inconsistent serving configuration |
| Truncated proposal      | Output limit, stop status, transport evidence, and target termination policy      | Resource exhaustion, interruption, decoding configuration, or unsuitable targets               |

Table 11: **Call Failures Guide Investigations**: A category identifies an observable problem. Controlled comparisons and retained evidence are needed to distinguish its possible causes.

^tbl-vol3-tool-validity-failures

Passing the validator on familiar tool definitions still does not show whether the fine-tuned policy is reading the delivered contract or recalling argument names from its weights. Evaluating schema robustness tests whether the policy generalizes to modified tool interfaces, scoring familiar schemas separately from renamed schemas and unseen tool families ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-qin2024toolllm|Qin et al. 2024]]) with mock tools and call-site checks updated in lockstep ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.08 Schema Robustness#^sec-vol3-fine-tuning-schemas|section 16.7]]). Over ${N}$ proposed calls ${a}_i$, each checked against its active schema set ${\mathcal{S}}_i$, **schema-following accuracy** is the fraction of calls that name a declared tool and satisfy its type schema:

$$
\text{SFA}=\frac{1}{{N}}\sum_{i=1}^{{N}}{\mathbf{1}}\{\operatorname{tool}({a}_i)\in{\mathcal{S}}_i\ \wedge\ {a}_i\models{\mathcal{S}}_i\}.
$$

On the same evaluated calls, **parametric recall error** is the fraction of calls that emit parameter names from the training key set ${\mathcal{K}_{\text{train}}}$ that do not appear in the delivered schema ${\mathcal{S}}_i$:

$$
\text{PRE}=\frac{1}{{N}}\sum_{i=1}^{{N}}{\mathbf{1}}\{\exists {p}\in\operatorname{keys}({a}_i):{p}\in{\mathcal{K}_{\text{train}}}\wedge {p}\notin\operatorname{params}({\mathcal{S}}_i)\}.
$$

When an adapted policy’s SFA rises on familiar schemas while its PRE climbs on renamed schemas, the weights are recalling training-set argument keys rather than reading the prompt. Before blaming the weights, however, the release audit checks the serving prompt to confirm that the old key was not accidentally left in the template.

A candidate that passes both task and schema checks can still spend too many turns or tokens per repair to be viable in production. Accounting for resource use prices what the policy spends to achieve that acceptance rate, tracking wall-clock latency, turn counts, generated tokens, and API charges through the effective cost per accepted task ${C_{\text{eff}}}$ (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**), which divides the total spend across all initiated attempts (including rejected calls, retries, verifier runs, and sandbox cleanup) by the number of accepted solutions. Because ${C_{\text{eff}}}$ divides by the acceptance rate, a fine-tuned candidate that takes an extra diagnostic turn per attempt can still lower ${C_{\text{eff}}}$ if those turns prevent failed runs. If a candidate completes zero tasks in a trial set, the report lists total spend beside the zero-acceptance count rather than an undefined ratio.

↩︎ Comparing policies under one fixed resource envelope, with time and tokens reported separately from monetary charges, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-matched-budgets|Matched-budget comparison]]**.

Even a repair update that improves acceptance at lower ${C_{\text{eff}}}$ can degrade the other tasks the deployment serves if weight updates overwrite broader skills. Testing capability retention checks that specializing the weights on repair traces has not degraded those non-repair tasks, using a regression suite drawn from the agent’s full operational scope rather than generic language benchmarks alone. When performance drops on non-repair tasks, engineers check both the serving template and the training mixture before attributing the drop to catastrophic forgetting[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.19 Footnotes#^fn11|¹¹]] ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-mccloskey1989catastrophic|McCloskey and Cohen 1989]]), and re-evaluate any mitigation, such as mixing in general trajectories, lowering the learning rate, or switching to a LoRA adapter, on the same five-part scorecard.

### Controlled Comparison and Conditional Release

^sec-vol3-fine-tuning-eval-protocol

To attribute changes on those five measurements to the weight update rather than to a coincidental prompt or schema edit, the release protocol varies one factor at a time under the fixture contract of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-fixtures|Task fixtures]]**. Each comparison pins task fixtures, acceptance criteria, resource budgets, and random seeds across repeated trials, binding every score to an artifact manifest that records the checkpoint or adapter hash, base model hash, tokenizer version, serialization template, decoding parameters, and harness commit.

The leakage controls of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-leakage|Evaluation leakage]]** govern contamination here as well. Re-prompted attempts, redacted traces, and paraphrased variants inherit their source task’s split. Checkpoints and tuning mixtures are selected on validation splits alone. A test suite whose failures were fed back into training or prompt tuning has become development data and must be replaced by a fresh split. Benchmarking on familiar repositories or APIs reflects legitimate deployment requirements, but a claim that the fine-tuned policy generalizes demands held-out schema and environment families.

Controlled ablations compare the fine-tuned checkpoint against the incumbent policy, as well as against the prompt-engineering, schema-refactoring, and runtime-guardrail alternatives prioritized by the intervention ladder. Because the candidate and the incumbent can run on the same tasks, the comparison is a paired one, and the paired-outcome discipline (an interval on the difference, never two overlapping single-arm intervals) applies unchanged. Reading several ablations at once adds one correction beyond a single pair. If each comparison is tested at the same significance level, the chance that at least one of them shows a false win grows with their number, so the per-comparison level must be tightened. Dividing it by the number of comparisons is the simplest such rule. A release claim resting on one seed or one favorable run is a sample of one.

↩︎ Paired comparison of two configurations on the same tasks, with intervals on the difference and the rule for splitting trials between new tasks and repeats, is established in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-rigor|Statistical Evaluation Rigor]]**.

While a lower common validation loss confirms that training optimized the intended objective, only closed-loop task acceptance, recovery resilience, and load-tested serving configurations provide defensible release evidence. A fine-tuned candidate enters the same declared release gate as any other change (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/14 Operating Agents/V3-14.07 The Release Decision#^sec-vol3-evaluation-synthesis-math|The declared decision rule]]**), approved for an exact artifact hash and operating envelope under principle [[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/V3 Agent Runtime Principles#^pri-vol3-release-evidence|12]]. Even after a fine-tuned model passes release qualification, external safety boundaries remain non-negotiable: runtime schema validators, permission sandboxes, token budgets, and supervisory recovery monitors must remain active in production. Assembling the scope, serialization, masking, batching, coverage, and release decisions into one auditable training manifest turns an admitted recovery record into a deployable policy candidate.
