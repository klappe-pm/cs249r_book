# V3-16.11 Parameter-Efficient Fine-Tuning

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16 Trajectory Fine-Tuning|V3-16 Trajectory Fine-Tuning]]

^sec-vol3-fine-tuning-peft

Full fine-tuning of an agent policy updates and stores a complete replica of every base parameter, requiring the training system to allocate memory for base weights, gradients, and optimizer state across the entire model. For an adaptive-moment optimizer under mixed precision, that state is a higher-precision master copy of each weight plus two running moments, so each trained parameter carries several times the bytes of its weight. Training a second specialized agent role, such as a diagnostic planner or an execution monitor, duplicates that resource footprint in full. **Parameter-efficient fine-tuning** avoids this multiplicative overhead by freezing the base model and training only a compact set of auxiliary parameters known as an **adapter**[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.19 Footnotes#^fn9|⁹]] ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-houlsby2019parameter|Houlsby et al. 2019]]), which is distributed alongside the immutable base checkpoint. For systems operating multiple specialized agent roles, lightweight adapters streamline storage and version management. Adapters give modularity, not isolation. An adapter is only a set of weight matrices; like the rest of the weights, it shapes proposals and holds no permissions of its own, and roles served from one process share that process’s failure domain ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.11 Parameter-Efficient Fine-Tuning#^sec-vol3-fine-tuning-adapter-release|section 16.10.2]]).

Rather than inserting extra sequential layers into the network, **low-rank adaptation (LoRA)** expresses the weight update to a selected projection matrix through two low-rank factor matrices ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-hu2021lora|Hu et al. 2021]]). Let ${\mathbf{W}}_0\in\mathbb{R}^{{d_{\text{out}}}\times {d_{\text{in}}}}$ denote a frozen base weight matrix acting on column-vector inputs. LoRA models the adapted matrix as

$$
{\mathbf{W}}={\mathbf{W}}_0+\frac{{\gamma}}{{r}}{\mathbf{B}}{\mathbf{A}},\qquad {\mathbf{B}}\in\mathbb{R}^{{d_{\text{out}}}\times {r}},\quad {\mathbf{A}}\in\mathbb{R}^{{r}\times {d_{\text{in}}}}.
$$

Here, the rank hyperparameter ${r} \ll \min({d_{\text{in}}}, {d_{\text{out}}})$ bounds the rank of the update, and the scaling factor ${\gamma}/{r}$ stabilizes optimization across different choices of ${r}$. The two factor matrices contain ${r}({d_{\text{in}}}+{d_{\text{out}}})$ trainable parameters. When sizing a run, engineers must sum this parameter count over all targeted matrices; attention projections and multi-layer perceptron projections frequently differ in dimensionality and need not be square. Target matrix selection and rank operate as primary capacity knobs, tuned directly against empirical validation performance.[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.19 Footnotes#^fn10|¹⁰]]

Initializing ${\mathbf{A}}$ from a Gaussian distribution and setting ${\mathbf{B}}=0$ ensures that ${\Delta}{\mathbf{W}} = \frac{{\gamma}}{{r}}{\mathbf{B}}{\mathbf{A}}$ is initially zero, allowing training to begin from the exact forward mapping of the pretrained base model. This asymmetric initialization is necessary to break symmetry without disturbing the initial forward pass. On the first backward step, the nonzero random entries in ${\mathbf{A}}$ project the layer input into a nonzero gradient for ${\mathbf{B}}$, whereas the gradient with respect to ${\mathbf{A}}$ evaluates to zero because it is scaled by ${\mathbf{B}}=0$. Once the first optimizer step updates ${\mathbf{B}}$ to nonzero values, subsequent backward passes propagate nonzero gradients into ${\mathbf{A}}$ as well, whereas initializing both matrices to zero would leave both gradients at zero permanently. Freezing ${\mathbf{W}}_0$ eliminates the memory required for base gradients and optimizer state, yet the backward pass still evaluates matrix-vector products through ${\mathbf{W}}_0^T$ to propagate activation gradients down to earlier transformer layers. The resulting gradient with respect to the layer input combines contributions from both the frozen base path and the adapter bypass, as given in **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-lora|LoRA matrix decomposition]]**.

### Parameter-State Inventory

^sec-vol3-fine-tuning-state-inventory

![[90 Assets/Volume III/16 Fine Tuning/Vol3 Sft Margin Adapter 4c8e93fc98.svg]]

*Two horizontal bars. The upper bar, labeled full fine-tuning 128 GB, is about eight times longer than the lower bar, labeled LoRA run 16.1 GB, almost all of it frozen base weights.*

*Training 0.10 percent of the parameters still keeps 12.6 percent of the state.*

Because ${\mathbf{W}}_0$ participates in every forward and backward pass, freezing the base model does not shrink GPU memory in proportion to the trainable parameter count: training 0.1 percent of the parameters still keeps 100 percent of the frozen base weights in device memory. Engineers size training hardware by counting the bytes of each resident array (frozen base weights, adapter weights, gradients, master weights, and optimizer moments), as notebook [16.5](https://mlsysbook.ai/vol3/16_fine_tuning/16_fine_tuning.html#nbk-15-adapter-state-inventory) does for a full fine-tuning run versus a LoRA run under mixed precision. Dynamic activations and temporary kernel workspaces are budgeted separately, because their size scales with sequence length, batch layout, and attention implementation rather than parameter count.

**Napkin Math 16.5: What adapter training removes from the inventory**

**Problem**: A hypothetical model contains 8,000,000,000 base parameters. The run attaches rank-16 adapters to 2 matrices in each of 32 layers. Each selected matrix maps an input width of 4,096 to an output width of 4,096. No other parameters are trained in the adapter case. What parameter-state memory does this save compared with training every base parameter?

For each trainable parameter, assume a weight using 2 bytes, a gradient using 2 bytes, a separate higher-precision master weight that the optimizer updates, using 4 bytes, and two optimizer moments (running averages of the gradient and its square) each using 4 bytes. Frozen parameters retain only their 2 bytes weight copy. This is the mixed-precision accounting of adaptive-moment optimization ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-kingma2014adam|Kingma and Ba 2015]]; [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-micikevicius2017mixed|Micikevicius et al. 2018]]), totaling 16 bytes per trainable parameter as modeled by Rajbhandari et al. ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-rajbhandari2020|2020]]); it is one declared implementation convention, not a requirement of every optimizer or framework. Count one unsharded resident copy of each array; display capacities in decimal MB and GB.

**Math**: Each adapted matrix adds ${r}({d_{\text{in}}}+{d_{\text{out}}})$ parameters, so the adapters contain 32 $\times$ 2 $\times$ 16 $\times$ (4,096 $+$ 4,096) $=$ 8,388,608 parameters, 0.10 percent of the base. The convention assigns 16 bytes of state to each trainable parameter and 2 bytes to each frozen one. [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.11 Parameter-Efficient Fine-Tuning#^tbl-vol3-sft-memory-breakdown|Table 10]] inventories the resulting arrays.

| Resident component            | Adapter-training inventory |
|:------------------------------|:---------------------------|
| Frozen base weights           | 16 GB                      |
| Trainable adapter weights     | 16.78 MB                   |
| Adapter gradients             | 16.78 MB                   |
| Adapter master weights        | 33.55 MB                   |
| Two adapter optimizer moments | 67.11 MB                   |

Table 10: **A declared parameter-state inventory**: The count includes only the listed resident arrays, not the full peak memory of a training step.

^tbl-vol3-sft-memory-breakdown

**Result**: The adapter arrays total 134.22 MB. Including the frozen base gives approximately 16.13 GB, compared with 128 GB for full-parameter training under the same convention, a reduction of approximately 111.87 GB, or 7.9×. The saving comes from dropping gradients, master weights, and optimizer moments for the frozen base.

**Systems insight**: Even though adapter training updates only 0.10 percent of the parameters, the system must still allocate 12.6 percent of the full-parameter memory state. The frozen base weights remain resident throughout execution and constitute 99.2 percent of what remains. Consequently, total parameter-state savings are bounded by the ratio of trainable to frozen bytes per parameter (here 16 bytes against 2 bytes, so no choice of rank can push the reduction past that ratio). Rank adjustments exert virtually no influence on this footprint; doubling the rank increases memory by only 134.22 MB. The primary engineering lever for shrinking adapter memory state is therefore the numerical precision of the frozen base itself. Dynamic activations and execution workspaces, required under both training paradigms, must be provisioned on top of this subtotal.

Beyond persistent parameter state, a complete memory plan must budget for forward activations (whether retained in high-bandwidth memory or selectively recomputed), temporary kernel scratchpads, collective communication buffers, allocator fragmentation, and operating headroom. Sharding and offloading distribute these resident arrays across cluster nodes or host memory tiers, trading network or PCIe interconnect bandwidth for device memory headroom. When on-device capacity is severely constrained, quantizing the frozen base weights directly targets the dominant state component, as demonstrated by QLoRA (quantized LoRA) ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-dettmers2023qlora|Dettmers et al. 2023]]), trading runtime dequantization arithmetic and metadata storage for lower memory occupancy. Because dynamic activation footprints and kernel workspaces scale with context length, batch structure, and attention kernels, engineers should profile these dynamic terms directly on the target hardware cluster before finalizing resource sizing.

### Adapter Release and Compatibility

^sec-vol3-fine-tuning-adapter-release

Once training finishes, the same split between the frozen base ${\mathbf{W}}_0$ and the low-rank factors ${\mathbf{B}}$ and ${\mathbf{A}}$ governs how the artifact is shipped and served. Because those factors express weight deltas relative to a specific base matrix ${\mathbf{W}}_0$, mounting a trained adapter onto a silently updated base checkpoint corrupts model outputs without raising a tensor-shape error. Releasing an adapter for a specialized agent role therefore requires shipping a configuration manifest alongside the low-rank weights that pins the parent base model version, target projection names, rank ${r}$, scaling factor ${\gamma}$, tokenizer revision, prompt templates, numerical precision, and links to the training corpus and evaluation audit. At serving time, the runtime must also enforce KV-cache prefix compatibility: cached prefix states computed under one adapter cannot be reused by another adapter that modifies the layers that produced them.

↩︎ The rule that cached key-value prefix state is reusable only under the same base weights and active adapters is established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kv-cache-prefix-compatibility|Prefix compatibility]]**.

Keeping adapters decoupled from the base weights lets a serving engine host several agent roles over one shared base model in accelerator memory, batching concurrent requests across distinct adapters while running the shared base projections in common matrix multiplications ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-lin2023slora|Sheng et al. 2024]]; [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.18 Source References#^ref-chen2023punica|Chen et al. 2024]]). While this layout amortizes base-weight memory across roles, each role still pays for its own factor matrices and dynamic activations. Sharing one serving process across roles also provides no fault or authority isolation between them. A bad adapter or anomalous input shares the process’s resource limits, and distinct roles still need distinct runtime capability grants. When a deployment serves only a single role, folding the adapter directly into the base weights (${\mathbf{W}} = {\mathbf{W}}_0 + \frac{{\gamma}}{{r}}{\mathbf{B}}{\mathbf{A}}$) removes per-token adapter kernel overhead and yields a single dense checkpoint.

If a newly deployed adapter regresses in production, rolling back the routing configuration sends new task admissions back to the prior verified release. Model rollback, however, cannot undo tool side effects already committed to external systems (database writes, network calls, or file edits) or settle in-flight trajectories on its own. The release policy must therefore declare whether active runs finish under their starting adapter or hand over to the fallback policy under the runtime’s recovery rules. Whether an update is packaged as an adapter or a dense checkpoint, deciding if it is safe to promote requires closed-loop evaluation.
