# V3-16.03 Scope of Supervised Fine-Tuning

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16 Trajectory Fine-Tuning|V3-16 Trajectory Fine-Tuning]]

^sec-vol3-fine-tuning-scope

Before turning an admitted record such as `trace_r19_01_redacted_v1` into a weight update, engineers must decide whether the failure it repaired belongs in the model’s parameters at all. Fine-tuning a model to work around a missing prompt instruction or a broken tool schema bakes a temporary workaround into billions of weights, only for the behavior to break again the next time the interface changes. Modifying model weights is an expensive, high-blast-radius change reserved for behavioral failures that survive cheaper fixes. The intervention ladder orders changes by cost and reversibility, so engineers test prompt, schema, and runtime fixes before spending compute on parameter updates, while diagnostic evidence can justify a direct weight update when the policy itself is at fault. Verified trajectory post-training (principle [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/V3 Trajectory Learning Principles#^pri-vol3-trajectory-post-training|13]]) requires curation to tie recorded evidence to a declared learning use and separate admissible targets from contextual or rejected actions. While this ordering is the default because of cost and blast radius, fine-tuning also pays when moving stable procedural guidance into the weights costs less than resending a long instructional prefix on every turn ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.10 Policy Distillation#^sec-vol3-fine-tuning-distillation|section 16.9]]).

↩︎ The intervention ladder, which orders context, schema, runtime, and parameter interventions by cost and reversibility, is established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.03 Capability Gap Diagnosis#^sec-vol3-flywheel-intervention-order|The intervention ladder]]**.

Once diagnostic evidence justifies a parameter update, **supervised fine-tuning (SFT)** adjusts trainable model parameters to maximize the conditional likelihood of selected target tokens given their causal prefix context. When processing `trace_r19_01_redacted_v1`, the training loop must follow the recovery sequence defined in `recovery_targets_v1` rather than computing loss over every recorded token. The model must see the historical context and tool outputs that justify a chosen action, yet the data pipeline must exclude later steps that would reveal future observations or solutions ahead of time. Trajectory fine-tuning therefore inherits two data contracts: a *target-selection contract* that designates which tokens contribute to the loss gradient, and a *conditioning contract* that governs what causal history the model sees when generating those tokens.

The two contracts separate learning improved behavior from overfitting an idiosyncratic run. In an error-recovery trajectory, the behavioral goal is teaching the model to inspect an updated schema after a refusal, issue a properly formed corrective call, and interpret what the runtime verification check establishes. Memorizing the file paths of a specific test fixture or predicting hard-coded test outputs lowers training loss without teaching generalizable recovery skills. Whether the updated policy transfers these habits to unfamiliar environments and new tasks is what [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.12 Evaluating a Fine-Tuned Agent#^sec-vol3-fine-tuning-benchmarking|section 16.11]] measures, and keeping the update generalizable starts with deciding which parts of agent behavior live in weights versus the prompt and runtime.

### Procedure, Contracts, and Enforcement

^sec-vol3-fine-tuning-behavior-homes

If a fine-tuned repair agent memorizes an API signature in its parameters instead of reading the prompt, a routine tool-interface change, such as adding a required parameter or revoking a permission, immediately breaks the deployed policy. Every response the agent generates combines the model’s static weights with the dynamic context window assembled for that call, and fine-tuning updates only the weights. Engineers therefore divide agent behavior across three architectural homes, summarized in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.03 Scope of Supervised Fine-Tuning#^tbl-vol3-fine-tuning-scope|table 1]]:

- *Procedure* is behavior that stays stable across tasks and changes slowly, such as inspecting diagnostic output before modifying source code or checking unresolved issues before reporting completion. Procedure is what model weights can reliably absorb.
- *Contracts* are the dynamic operational facts that vary across deployments, user sessions, and individual turns, such as API tool definitions, schema requirements, environment parameters, and granted permissions. Contracts belong in the prompt context; a model that memorized an earlier schema will keep emitting obsolete arguments when an interface changes.
- *Enforcement* covers the invariants that must hold even when the model proposes an invalid or adversarial action, such as schema validation, authorization checks, sandbox containment, and execution timeouts. Enforcement stays in the deterministic runtime harness under invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]).

| Home    | Intended responsibility                                                                    | Consequence for fine-tuning                                                                                                      |
|:--------|:-------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------|
| Weights | Learned procedures and response tendencies, including tool selection and recovery behavior | Update the proposal distribution, then measure whether the changed behavior helps under the declared task conditions             |
| Context | Current task facts, tool schemas, observations, and represented scope                      | Supply the information the policy needs now; do not rely on memorized versions as the authority for current facts or permissions |
| Runtime | Validation, authorization, containment, resource controls, and evidence collection         | Preserve enforcement independently of the learned policy; a model’s predicted result is not an observed external effect          |

Table 1: **Responsibilities of Weights, Context, and Runtime**: Weights hold procedure, context holds the current contract, and the runtime enforces that contract whatever the model proposes.

^tbl-vol3-fine-tuning-scope

Relying on parameters to store interface contracts makes a deployment brittle, because a revoked permission stays revoked regardless of how often the action appeared in past training demonstrations. Fine-tuning cannot replace dynamic contracts; what it can teach is the habit of reading and following whichever contract the context window supplies.

This boundary disproves the view that fine-tuning only moves the prompt into the weights. Only the procedural parts of a prompt (structured reasoning guidelines, diagnostic checklists, or few-shot error-recovery examples) belong in the parameters, where they save token overhead on every turn ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.10 Policy Distillation#^sec-vol3-fine-tuning-distillation|section 16.9]]). The contractual parts must stay in the prompt context, because omitting them forces the model to guess the current execution environment. The deterministic checks that enforce authorization and boundary invariants cannot live in either prompts or weights, because a probability distribution over tokens cannot guarantee an invariant.

Fine-tuning changes the policy’s proposal distribution: which tools it requests, how thoroughly it inspects diagnostic evidence, and which execution paths it tries. Those shifts change task success rates, end-to-end latency, and token use, yet every proposed action still runs inside the horizons, state transitions, and authority boundaries enforced by the runtime harness. This separation is the proposal boundary of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^sec-vol3-foundation-model-role|The Model Call Boundary]]**. Training reshapes what the policy proposes, while the runtime decides which actions may execute, and that boundary governs every adaptation choice that follows.

### Objective, Behavior Source, and Artifact

^sec-vol3-fine-tuning-adaptation-choices

Deciding that a recovery habit belongs in the weights still leaves a team to choose whether to imitate single corrections or rank competing repairs, whether to train on recorded logs or collect fresh trajectories, and whether to ship a full checkpoint copy or a lightweight adapter. Treating “fine-tuning” as a single knob obscures which decision is responsible when an update overfits or exceeds its memory budget, so the pipeline separates adaptation along three independent axes:

- **Training Objective**: The loss function that defines the learning signal. Supervised imitation maximizes the likelihood of curated target demonstrations, whereas preference methods such as direct preference optimization ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.09 Trajectory Preference Optimization#^sec-vol3-fine-tuning-dpo|section 16.8]]) adjust weights by contrasting preferred trajectories against dispreferred alternatives under an explicit ranking rule.
- **Behavior Source**: Where the demonstrations and conditioning inputs come from. Traces may be collected from instrumented production runs and filtered by offline verification, generated by a teacher configuration with privileged context or a larger search budget ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.10 Policy Distillation#^sec-vol3-fine-tuning-distillation|section 16.9]]), labeled on the states the learner itself reaches, or constructed by injecting faults the recordings never contained ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.07 Exposure Bias#^sec-vol3-fine-tuning-dagger|section 16.6.2]]).
- **Parameter Artifact**: Which weights the run updates and stores. Teams can update all model parameters directly or train compact adapter matrices, such as low-rank adaptation (LoRA) modules, that attach to a frozen base checkpoint ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.11 Parameter-Efficient Fine-Tuning#^sec-vol3-fine-tuning-peft|section 16.10]]).

Because these three choices are independent, they combine freely; a deployment can, for example, train a low-rank adapter with a preference objective on synthetic teacher demonstrations. Whichever combination a team chooses, the run still trains on trajectory records converted into model inputs, so the first pipeline step is reconstructing the input prefix and conditioning window for each selected response.
