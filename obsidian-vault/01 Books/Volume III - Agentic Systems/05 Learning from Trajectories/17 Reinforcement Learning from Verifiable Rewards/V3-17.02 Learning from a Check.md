# V3-17.02 Learning from a Check

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17 Reinforcement Learning from Verifiable Rewards|V3-17 Reinforcement Learning from Verifiable Rewards]]

^sec-vol3-rlvr-introduction-228c

The previous chapter left the repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) with `trained_policy_v1`, a supervised checkpoint fitted to the one malformed-argument recovery that curation admitted. Its release gate already had to send trials into a state the corpus never covered, the version conflict for which no demonstration exists (**[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.13 Case Study Training the Repair Policy#^sec-vol3-fine-tuning-synthesis|Case Study: Training the Repair Policy]]**). More imitation needs someone to record that recovery, and a preference pair needs two admissible records of it. The agent’s versioned test fixtures and acceptance checks need neither. They can score entirely novel attempts whose intermediate actions have no labeled target. An autonomous policy might inspect an unexpected source file, attempt an alternative refactoring strategy, or halt when it encounters an unfamiliar error. While the automated test suite verifies whether the final patch succeeds, it provides no token-by-token guidance during intermediate decision steps.

![[90 Assets/Volume III/01 Introduction/Hsa Locator Origin 574b033854.svg]]

*H·S·A locator with no axis highlighted and the origin dot marked, indicating that training moves no exposure.*

*Training changes the policy and leaves every exposure where the runtime closes it.*

Test-time selection already uses those acceptance outcomes to filter multiple generated rollouts and extract a passing candidate, yet it pays that inference latency on every incoming task while leaving the base policy unchanged. Neither imitation of scarce human-verified repairs nor test-time filtering increases the policy’s intrinsic probability of solving an unseen fault from verification signals alone. Reinforcement learning bridges this gap by converting acceptance verdicts directly into gradient updates. In doing so, it alters the role of the verification suite. Once a check enters the optimization objective, any flaw in the test fixture is compiled into the network weights rather than miscounted on a single run. The acceptance check that once decided a release (**[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^sec-vol3-evaluation-contract|The Task Acceptance Contract]]**) becomes the signal that decides every update.

Turning automated test outcomes into policy updates requires four coupled mechanisms. The reward design must evaluate functional correctness without introducing shortcuts that optimization can exploit. The policy update rule must then solve multi-turn credit assignment, translating a single terminal pass or fail into per-token update coefficients across an interactive trajectory. For that update to match what the agent actually did, the rollout recorder must log the exact context prefixes the policy saw and the exact tokens it generated. Finally, the compute fleet (sandboxed environments, verification workers, and gradient engines) must be sized so that training updates receive complete, synchronized candidate groups without stalling the pipeline.

The chapter takes these mechanisms in the order a student would need to build them. It first fixes what an outcome-driven update can and cannot learn ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.03 Foundations of Verifiable Rewards#^sec-vol3-rlvr-need|section 17.2]]), then prices the reward that drives it, including the false accepts a verifier admits ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.04 Verifiable Rewards#^sec-vol3-rlvr-rewards|section 17.3]]). Credit assignment follows, first through return and value estimates ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.05 Credit Across Turns#^sec-vol3-rlvr-credit|section 17.4]]) and then through group-relative policy optimization ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.06 Group Relative Policy Optimization#^sec-vol3-rlvr-grpo|section 17.5]]), the worked optimizer. The remaining sections keep that optimizer honest in practice: faithful records of multi-turn rollouts ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.07 Multi-Turn Agentic RL#^sec-vol3-rlvr-multi-turn|section 17.6]]), a verifier the candidate cannot reach ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.08 Verifier Isolation#^sec-vol3-rlvr-sandboxing|section 17.7]]), diagnostics for the pathologies that rising reward can hide ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.09 Training Pathologies#^sec-vol3-rlvr-pathologies|section 17.8]]), and the rollout, verifier, and staleness arithmetic that sizes the training fleet ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.10 Environments and Rollouts#^sec-vol3-rlvr-infrastructure|section 17.9]]). A case study then follows one repair group through the whole loop ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.11 Case Study Reinforcing the Repair Policy#^sec-vol3-rlvr-synthesis|section 17.10]]).
