# V3-17.08 Verifier Isolation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17 Reinforcement Learning from Verifiable Rewards|V3-17 Reinforcement Learning from Verifiable Rewards]]

^sec-vol3-rlvr-sandboxing

Consider the representative trial `rl_trial_01`, in which an agent submits a candidate patch after running local unit tests against an edited connection pool. The reinforcement learning loop requires an authoritative verdict under the evaluation specification `repair_accept_v1`, not an unverified self-report from the environment that generated the patch. As the METR evaluations in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.04 Verifiable Rewards#^sec-vol3-rlvr-rewards|section 17.3]] illustrate, an agent capable of modifying its evaluation environment can bypass the intended task and rewrite its own scoring logic, and where the scorer is within reach it often does.

To prevent this failure mode, the learning loop puts the grader isolation of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-grader-isolation|Grader isolation]]** on the reward path, with held-out tests kept by a trusted controller outside the candidate’s sandbox. We call this architectural guarantee **verifier isolation**: the assessment harness and its verdict are protected from both the executing agent policy and the candidate code it submits.[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.17 Footnotes#^fn8|⁸]] Whereas test coverage determines whether a test suite exercises the required behavioral contract, verifier isolation guarantees that the emitted verdict reflects the actual execution of those tests rather than unauthorized tampering.

### Separate Assessment Workspaces

^sec-vol3-rlvr-assessment-workspaces

Grading a patch inside the same container where the agent explored leaves the test runner, module imports, and exit codes exposed to the candidate’s modifications. To close that path, the controller separates the exploration workspace from the assessment workspace ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.08 Verifier Isolation#^tbl-vol3-dual-sandbox-boundaries|table 7]]). When an episode finishes, the controller captures the candidate artifact, binds it to the rollout identifier and base source revision, and admits it only if its diff modifies files the task permits, such as application source rather than tests, grading scripts, or container configuration. The controller then applies that admitted diff to a fresh copy of the declared fixture in a separate assessment workspace. Because the test suite must import or execute the patched application to evaluate it, the candidate remains untrusted even after it crosses into the assessment container. Application code that runs inside the same language interpreter process as the grader can still monkeypatch assertion objects or reporting hooks in memory, and hidden test files mounted read-only inside the candidate’s filesystem namespace can still be opened and read by the application at runtime. The assessment harness must therefore keep the authoritative verdict store and protected test definitions outside the process and filesystem scope reachable by the code under test, treating candidate stdout, stderr, and exit codes strictly as telemetry rather than verdicts.

| Responsibility       | Exploration side                                         | Assessment side                                                                 |
|:---------------------|:---------------------------------------------------------|:--------------------------------------------------------------------------------|
| Mutable task state   | Task-scoped working copy and permitted local diagnostics | Candidate applied to an identified fixture under its own execution limits       |
| Assessment authority | Public feedback, not control of the deciding check       | Protected criteria, checker configuration, and authoritative result storage     |
| Handoff              | Consistently captured candidate and bounded provenance   | Verdict and declared evidence bound to candidate, fixture, and checker versions |

Table 7: **Dual-workspace boundaries**: Exploration and assessment have separate state and authority. The candidate crosses as untrusted material; separation does not certify its behavior.

^tbl-vol3-dual-sandbox-boundaries

Reinforcement learning adds a failure mode that offline evaluation seldom meets, the exploitation of exception handling in the verification harness. A candidate patch that hangs, triggers an unhandled memory fault, or crashes the test runner can convert an inevitable test failure into a missing verdict. If the training pipeline silently drops rollouts with missing verdicts from batch normalization, or assigns them a default score higher than a failure, the policy learns to generate crash-inducing code rather than viable solutions. The resource caps declared for the candidate’s own execution decide whether a crash or timeout counts against the candidate. A breach of those limits, such as an infinite loop that exhausts a 60 s execution budget, is candidate-induced. Any such resource exhaustion or process crash maps to a failure (${R} = 0$) and never outscores an orderly test failure. A failure of the host or grader while the candidate stayed within its limits, such as an out-of-memory crash caused by host oversubscription, is infrastructure and leaves the outcome unresolved under the rules of [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.07 Multi-Turn Agentic RL#^sec-vol3-rlvr-stopping-censored|section 17.6.3]]. In neither case may the system emit a default pass, and training telemetry must report the two outcomes separately.

Isolating the workspace does not stop information from leaving through permitted outputs, the confinement problem that agent sandboxes face on their egress channels (**[[01 Books/Volume III - Agentic Systems/03 Tool Use/08 Agent Sandboxes/V3-08.08 Egress Control#^sec-vol3-sandboxes-name-resolution|Name resolution and local destinations]]**). Even binary pass/fail responses leak information across successive submissions. In multi-turn rollouts, intermediate feedback must never expose hidden test names, assertion details, or internal stack traces, which would let the policy reconstruct the hidden suite turn by turn. The training loop must therefore declare what feedback reaches the agent and keep it to the minimum the task needs. Tests queried repeatedly to generate training rewards also become de facto training data, so an unbiased release assessment requires evaluation suites that the training loop never executes.

### Repeated Checks and Noisy Rewards

^sec-vol3-rlvr-repeated-checks

Verifier isolation eliminates deliberate tampering, but it cannot prevent non-deterministic evaluation outcomes. Flaky checks, caused by thread scheduling races, network jitter, or asynchronous event loops, can spuriously accept an incorrect patch or fail a valid one, even when the test definitions are completely protected. Repeating the check reduces the rate of accidental acceptance. If a test suite is under-specified, however, an incorrect patch that satisfies those partial requirements will pass every repetition.

Let ${p_{\text{trial}}}$ represent the probability that a fixed candidate patch passes a single verification trial under a specified protocol. Assuming ${n_{\text{trial}}}$ independent trials share the same pass probability, the **all-pass rule**, which requires unanimous success across all ${n_{\text{trial}}}$ trials, accepts the candidate with probability

$$
\Pr(\text{accept candidate})={p_{\text{trial}}}^{{n_{\text{trial}}}}.
$$

In this notation, ${n_{\text{trial}}}$ denotes the total number of trials conducted, including the first. An initial pass followed by ${n_{\text{trial}}}$ additional confirmation reruns would instead yield an acceptance probability of ${p_{\text{trial}}}^{{n_{\text{trial}}}+1}$. When trials are statistically dependent, the all-pass probability becomes the product of conditional probabilities $\prod_{j=1}^{{n_{\text{trial}}}} \Pr(\text{pass}_j\mid\text{all earlier passes})$, which can diverge sharply from ${p_{\text{trial}}}^{{n_{\text{trial}}}}$. Launching fresh container instances with randomized execution seeds promotes independence, whereas a persistent checker bug or shared host-level bottleneck introduces positive correlation across runs.

Group normalization makes a flaky pass as damaging as a tampered one. On a hard task, a lone false pass receives the same near-$\sqrt{{G}-1}$ coefficient ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.06 Group Relative Policy Optimization#^eq-vol3-grpo-lone-pass|equation 3]]) as an authentic solution, so the optimizer spends its largest updates on scheduling luck. The all-pass trade-off between accidental-reward risk, false rejections, and extra verification work is priced in notebook [17.5](https://mlsysbook.ai/vol3/17_rlvr/17_rlvr.html#nbk-vol3-rlvr-repeated-checks).

**Napkin Math 17.5: The cost of an all-pass rule**

**Problem**: How does requiring repeated passes change accidental reward, false rejection, and verification work?

**Variables**: In a hypothetical fixture, a fixed incorrect patch has trial pass probability ${p_{b}}$ of 0.20, while a fixed correct patch has trial pass probability ${p_{g}}$ of 0.98. Trials are independent under an unchanged protocol. Acceptance requires ${n_{\text{trial}}}$ total passes, with ${n_{\text{trial}}}$ set to 3; verification stops at the first rejection. A separate illustration considers a group of 16 independently assessed incorrect candidates with the same ${p_{b}}$.

**Math**: A single trial for each incorrect candidate gives group probability $1-(1-{p_{b}})^{G}$ of at least one false pass, or 97.2 percent. In the special case of exactly one pass, its standardized coefficient approaches $\sqrt{{G}-1}$, approximately 3.87, as ${\epsilon_{\text{stab}}}$ approaches zero. The all-pass rule lowers each incorrect candidate’s acceptance probability to ${p_{b}}^{{n_{\text{trial}}}}$, or 0.8 percent, but rejects the correct candidate with probability $1-{p_{g}}^{{n_{\text{trial}}}}$, or 5.88 percent.

Trial ${j}+1$ is needed only if the preceding ${j}$ trials passed. Consequently,

$$
\mathbb E[{N_{\text{trial}}}\mid {p_{\text{trial}}}]=\sum_{j=0}^{{n_{\text{trial}}}-1}{p_{\text{trial}}}^{j}.
$$

For the incorrect patch, $1+{p_{b}}+{p_{b}}^2$ gives 1.24 trials; for the correct patch, $1+{p_{g}}+{p_{g}}^2$ gives 2.9404. Running every trial regardless of earlier outcomes instead consumes ${n_{\text{trial}}}$ trials per candidate.

**Systems insight**: Each added trial multiplies an incorrect patch’s acceptance by ${p_{b}}$ and a correct patch’s by ${p_{g}}$, so the rule pays when ${p_{b}}$ is far below ${p_{g}}$. Here 3 trials cut an incorrect patch’s acceptance from a per-trial 0.20 to 0.8 percent, at a false-rejection cost of 5.88 percent for the correct one. Stopping at the first rejection makes the cost fall mostly on correct candidates, which run nearly all ${n_{\text{trial}}}$ trials, so size the verifier pool for the passing fraction of the population, not for one trial per candidate.

A real candidate population mixes pass probabilities. Because the expected trial workload $\sum_{j=0}^{{n_{\text{trial}}}-1} {p_{\text{trial}}}^{j}$ is convex in ${p_{\text{trial}}}$, substituting the population’s mean pass probability directly into the formula underestimates total compute demand by Jensen’s inequality. High-quality candidates progress deeper into repeated trials than low-quality ones, concentrating the verification workload on the most promising rollouts. Sizing verification capacity, measured in completed candidate evaluations per second, therefore requires weighting the trial demand by the empirical distribution of candidate quality rather than using a single average pass rate.

When successive runs disagree, repetition alone is insufficient, because the divergence indicates an unstable test harness that requires its own repair. Verification harnesses should deliberately vary test execution order and process scheduling, running regular sanity checks against known-valid and known-invalid reference artifacts to detect fixture drift before emitting training rewards. If a specific test case stays flaky across runs, operators must quarantine it from the active reward loop. Because quarantining alters the task’s reward function, all test suite revisions must be versioned, preserving the historical trial records and audit trail. Verifier isolation and repeated assessment address the named tampering and flakiness paths; policy quality remains bounded by the properties the protected checks cover and requires independent release evidence.

**Checkpoint 17.2: Optimizing agent trajectories**

The recorded interaction, group statistic, and protected assessment must describe the same training event.

**Group coefficients**: How does GRPO form its baseline, and which objective term loses its signal when every observed reward agrees?

**False accepts in the gradient**: Why is the fraction of false accepts among accepted trajectories not their fraction of the gradient?

**Group-size budget**: A task family passes 20 percent of attempts in groups of 8. Estimate the rollouts spent per group that carries any reward contrast, then identify what additional evidence is needed to choose between doubling ${G}$ and retargeting task difficulty.

**Action records**: Why are sampled token IDs and actual delivered prefixes needed when observations are excluded from action scoring?

**Candidate execution**: A patch passes path checks and enters a fresh grader. Which boundary is still missing if its code shares the grader’s interpreter and result store?

**Repeated assessment**: Why do three total independent trials differ from an initial pass plus three reruns, and what false-rejection cost accompanies an all-pass rule?

**Protected evidence**: Why are hidden checks repeatedly used for training rewards not an untouched release evaluation set?
