# V3-17.10 Environments and Rollouts

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17 Reinforcement Learning from Verifiable Rewards|V3-17 Reinforcement Learning from Verifiable Rewards]]

^sec-vol3-rlvr-infrastructure

Before a single repair rollout can contribute to a parameter update, it passes through pipeline stages whose latencies span two orders of magnitude: a model inference step samples tokens in tens of milliseconds, stateful tool commands and test suites inside `pool_fixture_v1` run for seconds, and cold sandbox provisioning can take longer still. Coordinating model inference, isolated sandboxes, automated assessment suites, and trace storage across those disparate timescales is the central systems challenge of verifiable reinforcement learning. The pipeline must keep every stage saturated while preserving the statistical contract of the learning algorithm, maximizing rollout throughput without silently altering, truncating, or biasing the distribution of trajectories delivered to the optimizer.

### Task Fixtures and Reset Conditions

^sec-vol3-rlvr-task-fixtures

A recorded trajectory from a previous failure cannot be replayed as a reinforcement learning task on its own. Without a reproducible container image, pinned dependencies, and a verified grading suite, candidate rollouts fail on missing packages or residual files left by earlier runs. Every rollout therefore begins with a concrete task environment governed by a fixture contract that defines the initial filesystem state, available tool APIs, network permissions, and reward evaluation criteria.

↩︎ Collection fixtures, which layer a collection contract on the evaluation gym’s execution baseline, are established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.04 Task Fixture Design#^sec-vol3-flywheel-fixtures|Task Fixture Design]]**.

Data splitting requires the same discipline before any task is sampled or filtered into a curriculum, keeping related problem variants, mutations, and solution-equivalent tasks on the same side of the split. Training on familiar repositories teaches local code conventions, whereas holding out entire repository families tests whether the policy transfers to unfamiliar codebases. Within each split, ground-truth reference solutions and known defective candidates calibrate the verifier so that flaky dependencies and harness faults show up as operational errors rather than false rejections. Because filtering tasks by difficulty to sharpen reward contrast also shifts the task mixture, the pipeline must log the active curriculum rather than reading a higher training reward as a gain across the uncurated population.

↩︎ Task groups, which keep every variant of a problem on one side of the split, are established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.05 Split Design#^sec-vol3-trajectory-curation-claims-groups|Evaluation claims and task groups]]**.

Between successive episodes, an environment slot executes a **rollout reset** to restore the fixture to its declared initial state. Its obligations are those of the trial reset in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-reset|State reset between trials]]**, which terminates lingering processes, scrubs writes and credentials, and settles outstanding operations before the slot is reused. Snapshots restore local disk state in milliseconds but leave external side effects to teardown handlers. Controlled stochasticity, such as randomized problem seeds or initial state permutations, must be codified directly in the fixture specification. While offline benchmarks incur reset overhead only intermittently, reinforcement learning loops execute resets across millions of rollout cycles, making reset efficiency a direct driver of aggregate throughput.

### Environment-Cycle Time and Throughput

^sec-vol3-rlvr-environment-cycle

A cold container reset takes several seconds, whereas a snapshot restore finishes in milliseconds, so the reset mechanism can easily take as long as the model inference and tool calls of the episode itself. To price how much capacity a faster reset actually recovers, consider an environment slot executing agent trajectories serially. Let ${H}$ be the horizon (the number of interaction turns), ${T_{\text{model}}}$ the model inference time per turn, ${T_{\text{tool}}}$ the tool execution time per turn, ${T_{v}}$ the final assessment duration, and ${T_{r}}$ the environment reset time. Assuming constant durations, no intra-slot concurrency, and zero queueing delay, the total slot cycle time is

$$
{T_{\text{cycle}}}={H}({T_{\text{model}}}+{T_{\text{tool}}})+{T_{v}}+{T_{r}}. \tag{6}
$$

^eq-vol3-rlvr-environment-cycle

Accelerating the reset routine directly shortens this cycle, but by a bounded amount. Amdahl’s law sets that bound. Speeding up one stage of a fixed workload shortens the whole by at most the time that stage occupied, so the overall speedup is limited by that stage’s share of the total. Multiplying the reciprocal of ${T_{\text{cycle}}}$ by the total number of environment slots gives the theoretical capacity ceiling of the rollout fleet. However, that projection assumes model inference servers, tool executors, verification sandboxes, and storage pipelines can sustain this aggregate rate without contention. We compute this baseline capacity in notebook [17.6](https://mlsysbook.ai/vol3/17_rlvr/17_rlvr.html#nbk-16-exploration-reset-goodput) before examining where downstream shared bottlenecks arise.

**Napkin Math 17.6: Reset cost and slot capacity**

**Problem**: A hypothetical pool contains 256 environment slots. Each episode has 20 decisions, each using 120 ms of model service and 80 ms of tool execution, followed by 0.5 s of assessment. Cold reset takes 3.5 s; snapshot reset takes 15 ms. What capacity change follows under the serial-slot assumptions?

**Math**: Under the serial-cycle model in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.10 Environments and Rollouts#^eq-vol3-rlvr-environment-cycle|equation 6]], non-reset work takes 4.5 s per cycle. Cold reset gives a cycle of 8 s, of which 56.25 percent is non-reset work. Snapshot reset gives a cycle of 4.515 s and a non-reset fraction of 99.67 percent. For either case, idealized pool capacity is the number of slots divided by cycle time.

**Result**: The corresponding capacities are approximately 115,200 and 204,120 episodes per hour, a 1.77× local capacity ratio. The non-reset fraction includes tool and assessment time, rather than representing accelerator utilization alone.

**Systems insight**: Reducing cold reset from 3.5 s to the stated snapshot latency yields a 1.77× slot-capacity gain; eliminating reset entirely would leave the 4.5 s of active work as the cycle-time floor. This is Amdahl’s law applied to the slot. The capacity ratio is ${T_{\text{cycle,cold}}} / {T_{\text{cycle,snap}}}$, and because the active work term remains fixed, optimizing reset latency yields diminishing returns once reset overhead is a small fraction of the cycle. Furthermore, these recovered slot-hours translate into training updates only if downstream inference serving, verification workers, storage pipelines, and the training loop possess sufficient headroom to process 1.77× as many episodes. In a balanced pipeline, the stage with the least headroom dictates the realized throughput gain.

↪ Amdahl’s law bounds the speedup that a fixed serial fraction allows, as developed in **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/18 Multi-Agent Coordination/V3-18.03 The Delegation Trade-Off#^sec-vol3-multiagent-coordination-tax|The coordination tax]]**.

### Complete-Group Scheduling

^sec-vol3-rlvr-group-scheduling

The serial-slot model prices each environment slot in isolation, but group-relative training dispatches ${G}$ rollouts for the same task as a cohort and consumes their completed trajectories in minibatches. At dispatch, that shared task prompt is an advantage: because all ${G}$ rollouts start from an identical prompt token sequence under matching model weights and compatible cache allocation policies, a radix-tree prefix cache computes the prompt’s key-value states once across the cohort (principle [[01 Books/Volume III - Agentic Systems/02 Agent Memory/V3 Agent Memory Principles#^pri-vol3-prefix-coherence|5]]), whereas promoting a new policy checkpoint invalidates those cached entries and forces a cold start even on identical prompts. Once the ${G}$ rollouts begin executing, however, each one interleaves bursty model inference with blocking tool waits while training workers wait for completed groups. Allocating distinct resource pools for inference and training decouples those workloads, whereas colocated or alternating execution schedules reduce model weight broadcast and network synchronization costs depending on the relative runtimes of rollout generation and gradient computation.

↩︎ The weight, exact-prefix, and residency conditions for prefix-cache reuse are established in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kv-cache-prefix-compatibility|Prefix compatibility]]**.

When the training loop synchronizes across rollout groups before updating parameters, the trainer enforces a **group barrier**. The step duration is dictated by the slowest member of the cohort:

$$
{T_{\text{step}}}=\max_i {T_{\text{traj}}}({\tau}_i)+{T_{\text{train}}}, \tag{7}
$$

^eq-vol3-rlvr-step-time

Every worker slot that finishes earlier sits idle until the tail completes. Because variable tool execution times, multi-turn reasoning loops, and compiler or test runs give agent trajectories heavy latency tails, that tail wait can leave a large share of the pool idle.

For a hypothetical group of 4 whose members complete between 0.2 s and 16.8 s, [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.10 Environments and Rollouts#^eq-vol3-rlvr-step-time|equation 7]] holds all four slots until the 16.8 s member finishes, stranding 65 percent of reserved slot capacity in an idle state. This barrier penalty, charted in panel (a) of [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.10 Environments and Rollouts#^fig-vol3-asynchronous-freshness-pipeline|figure 2]], motivates releasing slots early and gathering rollouts asynchronously.

Under group-relative objectives, asynchronous rollout completion does not remove the mathematical requirement for an aggregated group baseline. The scheduler assigns the group identifier, fixture configuration, planned cohort membership, and generating checkpoint version prior to dispatch. Each completed member record and its verification status buffer in memory until the group closure policy determines eligibility. If the objective requires verified rewards across all group members, group closure must hold the record until all members report. If an environment terminates due to turn caps or time limits, the orchestrator applies the declared protocol penalty. Infrastructure failures such as sandbox crashes or network timeouts stay unresolved under the rules of [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.07 Multi-Turn Agentic RL#^sec-vol3-rlvr-stopping-censored|section 17.6.3]], and the closure policy must say whether the group waits for them or closes without them.

As soon as a rollout finishes, its environment slot frees its inference concurrency and sandbox resources for subsequent work, retaining only its compact trajectory record in an aggregation buffer while evicting key-value cache states from accelerator memory. Because rollouts complete out of order, group buffers, verification queues, and training ingestion queues require bounded capacities in both record count and total bytes. Admission controllers must track in-flight slot allocations alongside buffered records, applying backpressure upstream to prevent intermediate queues from overflowing host memory during bursty completions.

Prematurely closing a group with only its fastest-finishing members distorts the baseline sample. Slower trajectories often represent harder subtasks, alternative multi-step tool interactions, or transient infrastructure contention. Recomputing relative advantages across only the early completions fails to recover the true underlying distribution; early truncation imposes a survival bias that favors fast, simplistic solutions. Training pipelines must explicitly log all exclusions and their causal categories, monitor completion latency distributions, and track task coverage shifts over time. Similarly, filtering out zero-variance groups (where all members receive identical rewards) reduces gradient variance in advantage-based policy surrogates, but it also eliminates training signals intended for auxiliary objectives, such as reference-policy divergence constraints.

### Policy Staleness

^sec-vol3-rlvr-freshness

Decoupling rollout collection from training updates means trajectories can arrive after the optimizer has already advanced the policy weights. The version disparity between the policy that sampled an action and the policy undergoing optimization is **policy staleness**. Asynchronous actor-learner frameworks such as IMPALA address this discrepancy by pairing asynchronous scheduling with off-policy corrections,[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.17 Footnotes#^fn9|⁹]] reweighting trajectory tokens by the probability ratio between the learner and actor checkpoints ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.16 Source References#^ref-espeholt2018impala|Espeholt et al. 2018]]). For an episode pinned to a single behavior checkpoint, let ${\text{ver}_b}$ denote its generating version and $\text{ver}_t$ the trainer’s active version. When the training loop steps at a steady pace, the update-count lag is

$$
{\Delta}\text{ver}=\text{ver}_t-{\text{ver}_b}\approx\left\lfloor\frac{{\Delta T_{\text{rollout}}}}{{T_{\text{step}}}}\right\rfloor, \tag{8}
$$

^eq-vol3-rlvr-staleness

where ${\Delta T_{\text{rollout}}}$ is the wall-clock time elapsed from sampling the first prompt token to admission into the training batch, and ${T_{\text{step}}}$ is the training step latency. This relationship enables system designers to calibrate staleness bounds directly from rollout duration. Long agent rollouts are precisely the trajectories most prone to severe staleness. Bounded staleness has a long lineage in distributed training architectures, where worker parameter reads are constrained to a fixed step horizon ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.16 Source References#^ref-ho2013more|Ho et al. 2013]]), and asynchronous actor-learner algorithms tolerate bounded lag in exchange for high actor utilization ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.16 Source References#^ref-mnih2016asynchronous|Mnih et al. 2016]]). Applied at admission ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.10 Environments and Rollouts#^fig-vol3-asynchronous-freshness-pipeline|figure 2]], panels b and c), the check admits the two short rollouts and excludes the long one, recording why it was dropped. These are record-level lag decisions, not a complete group-admission rule. Under an objective that requires the planned cohort, every member must also have a resolved reward and satisfy that bound before the group enters an update.

![[90 Assets/Volume III/17 Rlvr/Asynchronous Freshness Pipeline 5d74f23543.svg]]

Figure 2: **Group Barriers and Version-Checked Admission**: (a) In the hypothetical group of four, the barrier holds every slot until the 16.8 s member finishes, leaving 65 percent of reserved slot time idle. (b) Asynchronous collection releases slots early, so the trainer’s version advances while rollouts run. Each record carries the version that sampled it, and its lag ${\Delta}\text{ver}$ at admission grows with its duration; the long rollout exceeds the illustrative bound and is excluded with its reason recorded. (c) A record leaves verification with a pass, a fail, or an unavailable verdict, waits in a bounded group buffer, and reaches the trainer only if its lag is within the bound. While this admission check enforces a strict bound on version lag, it cannot prevent distribution drift when individual gradient updates make large steps in parameter space.

^fig-vol3-asynchronous-freshness-pipeline

While the version counter provides an operational threshold for admission control, distribution divergence requires separate monitoring: a single large optimizer step can shift output probabilities far more dramatically than several incremental updates. Production diagnostics must break down elapsed age into generation time, tool wait states, verification latency, group buffer residence, and ingestion queue delay, while tracking empirical probability-ratio distributions (${\pi_\theta} / \pi_{\text{old}}$) to detect distribution drift directly. Logging per-invocation metadata as described in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.07 Multi-Turn Agentic RL#^sec-vol3-rlvr-multi-turn|section 17.6]] accurately captures that behavior distribution even when policy checkpoints update mid-episode. Training on such composite trajectories requires optimization formulations that support turn-by-turn behavior probabilities, because retroactively relabeling an entire trajectory under the newest policy checkpoint distorts importance weights and introduces optimization instability.

Freshness limits balance off-policy variance against selection bias. Discarding trajectories that exceed a staleness threshold bounds policy lag, but because complex tasks demand more reasoning steps and tool calls, strict staleness cutoffs systematically eliminate hard problems from the training distribution. As indicated by [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.10 Environments and Rollouts#^eq-vol3-rlvr-staleness|equation 8]], systems engineers can preserve task diversity by reducing the numerator rather than loosening the bound. Reducing generation, tool-wait, verification, group-buffer, and ingestion delays can shorten ${\Delta T_{\text{rollout}}}$ while preserving the long-horizon tasks the learner needs. Synchronous collection eliminates staleness entirely at the expense of straggler idle time, whereas multiple optimization epochs over a single collected batch reintroduce policy lag. While the clipped surrogate objective in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.06 Group Relative Policy Optimization#^sec-vol3-rlvr-grpo-clipped-objective|section 17.5.2]] limits policy updates driven by stale probability ratios, it neither bounds importance sampling variance nor corrects for the shift in visited state distributions ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.16 Source References#^ref-schulman2017proximal|Schulman et al. 2017]]). Because discarded trajectories consume inference and sandbox capacity without producing gradient updates, monitoring systems must track discard rates, compute overhead, and shifts in task coverage.

### Verification Capacity

^sec-vol3-rlvr-verification-capacity

Even when inference and sandbox slots keep up with rollout generation, an undersized verifier pool backs up completed trajectories in the assessment queue, lengthening ${\Delta T_{\text{rollout}}}$ until valid rollouts miss the staleness cutoff. Verifier sizing reuses the pool model of **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/15 Trajectory Curation/V3-15.09 Collection Pipeline Architecture#^sec-vol3-trajectory-curation-collection-credits|Collection credits and staging reserves]]**, changed only in that a reinforcement-learning trajectory may need several trials rather than one. Let ${\lambda_{\text{traj}}}$ denote completed trajectories arriving per second, ${N_{\text{workers}}}$ the number of independent verification worker slots, and ${T_{\text{trial}}}$ the mean execution duration for one verification trial, including environment provisioning, execution, and cleanup. When each trajectory requires ${n_{\text{trial}}}$ total trials to evaluate determinism or flaky tests, each trajectory demands an average of ${n_{\text{trial}}} {T_{\text{trial}}}$ worker-seconds. By Little’s law (theorem [5.1](https://mlsysbook.ai/vol3/05_kv_cache/05_kv_cache.html#thrm-05-littles-law)), mean busy workers equal the arrival rate times that demand. The ideal service capacity ${\mu_{\text{verify}}}$ and resulting offered utilization ${\rho_{\text{serv}}}$ are

$$
{\mu_{\text{verify}}}=\frac{{N_{\text{workers}}}}{{n_{\text{trial}}} {T_{\text{trial}}}},\qquad {\rho_{\text{serv}}}=\frac{{\lambda_{\text{traj}}} {n_{\text{trial}}} {T_{\text{trial}}}}{{N_{\text{workers}}}}. \tag{9}
$$

^eq-vol3-verification-throughput-roofline

Both ${\lambda_{\text{traj}}}$ and ${\mu_{\text{verify}}}$ measure completed trajectories per second. As in that pool model, a pool run at ${\lambda_{\text{traj}}}={\mu_{\text{verify}}}$ has no margin for bursts or slow trials, so designers choose a target utilization $0<{\rho_{\text{target}}}<1$ and provision at least $\lceil{\lambda_{\text{traj}}} {n_{\text{trial}}} {T_{\text{trial}}}/{\rho_{\text{target}}}\rceil$ worker slots. Queue capacity limits and upstream admission control remain necessary. While executing a candidate’s ${n_{\text{trial}}}$ trials concurrently across multiple slots reduces wall-clock verification latency, the aggregate worker-second demand remains identical.

For a hypothetical arrival of 512 trajectories every 16 s, ${\lambda_{\text{traj}}}$ is 32 trajectories per second. With each trial lasting 8 s, a single trial per trajectory consumes 256 worker equivalents at that arrival rate. Executing all 3 trials elevates demand to 768 worker equivalents. Applying the utilization relationship in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.10 Environments and Rollouts#^eq-vol3-verification-throughput-roofline|equation 9]] with an illustrative 80 percent target requires provisioning 960 worker slots. Verification demand scales linearly with ${n_{\text{trial}}}$, and the target utilization establishes the necessary headroom against queueing delays.

Early-exit evaluation policies alter these capacity requirements. Under the stop-on-first-rejection policy of notebook [17.5](https://mlsysbook.ai/vol3/17_rlvr/17_rlvr.html#nbk-vol3-rlvr-repeated-checks), verification terminates upon the first failing trial. Capacity models therefore substitute that notebook’s expected executed trial count in place of ${n_{\text{trial}}}$ when computing total worker demand, averaged over the empirical mixture of pass rates for the convexity reason given in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.08 Verifier Isolation#^sec-vol3-rlvr-repeated-checks|section 17.7.2]]. Sizing calculations must also incorporate unequal trial durations, sandbox initialization overhead, and retry cascades. In-memory queues absorb brief arrival spikes, but sustained overload requires adding worker slots or adopting more aggressive early-exit evaluation rules.

### Policy Version Gating

^sec-vol3-rlvr-release-gating

Once the verifier pool has scored a batch and the trainer has produced a new checkpoint, that checkpoint faces two distinct promotion gates: entering the rollout fleet to collect the next batch, and shipping to production users. For internal collection gating, automated checks verify prompt-template compatibility, tool-calling syntax, entropy bounds against policy collapse, and memory utilization before promoting the candidate weights to the rollout fleet. The orchestrator records the promoted artifact digest and generating version for every dispatched episode. If a promoted version still falls into degenerate loops or crashes sandboxes, the controller halts further admission under that version, and any side effects produced by faulty rollouts remain subject to their designated cleanup handlers.

Production deployment release requires a formal evaluation framework verifying regression resistance, safety constraints, latency budgets, and out-of-distribution transfer. Internal training diagnostics provide rapid feedback during optimization, but they must remain strictly quarantined from release benchmarks to prevent benchmark leakage. Production evaluation suites must enforce an isolated assessment boundary, logging benchmark exposure whenever validation metrics inform architectural or hyperparameter revisions.

↩︎ Controlled comparison and conditional release of a trained checkpoint are established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.12 Evaluating a Fine-Tuned Agent#^sec-vol3-fine-tuning-eval-protocol|Controlled comparison and conditional release]]**.

System evaluations must carefully distinguish between operational consistency and genuine capability expansion. In the competitive reasoning benchmark study of Yue et al. ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.16 Source References#^ref-yue2025does|2025]]), RLVR-trained models improve pass@1 while base models match or exceed them when sampled across broad cohorts (${k} \gg 1$). This pattern is consistent with concentrating probability mass onto successful solution modes that the base model could already generate; it does not establish a universal limit on acquiring new behavior. Reporting pass@1, pass@${k}$ at large ${k}$, and the repeated-trial pass$^{k}$ defined in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-pass-k|Potential and repeated-run consistency]]** separates a policy that has become more reliable from one that has expanded its underlying capabilities. A candidate checkpoint must remain unreleased until it satisfies recovery, transfer, and unresolved-outcome criteria across comprehensive production testbeds. Balancing rollout generation, straggler barriers, staleness bounds, verifier capacity, and release gating provides the infrastructure that keeps this learning loop saturated. Tracing how these mechanisms operate together requires following a complete update cycle on a concrete repair workload.
