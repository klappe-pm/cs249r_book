# V3-17.03 Foundations of Verifiable Rewards

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17 Reinforcement Learning from Verifiable Rewards|V3-17 Reinforcement Learning from Verifiable Rewards]]

^sec-vol3-rlvr-need

Starting from `trained_policy_v1` (**[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.13 Case Study Training the Repair Policy#^sec-vol3-fine-tuning-synthesis|Case Study: Training the Repair Policy]]**), the repair agent can already propose tool calls and edits when dispatched on a version-conflict bug for which no curated recovery exists. Whereas behavioral cloning (supervised imitation of recorded actions) stalls the moment a trajectory leaves the demonstrated corpus, reinforcement learning executes candidate rollouts in the live container environment and scores the resulting trajectories against programmatic checks. The supervised checkpoint serves only to bootstrap sampling; once exploration begins, optimization depends entirely on the agent’s ability to act, observe, and receive an evaluative score. Before any gradient update can convert those raw outcomes into policy improvements, however, the system must define how multi-turn rollouts are represented, how baselines separate signal from variance, and how execution boundaries protect verification harnesses during exploration.

### Policies, Rollouts, and Rewards

^sec-vol3-rlvr-policies-rollouts-rewards

An agent repairing a repository cannot inspect the container’s underlying disk or process table directly; it sees only the transcript of prompts, tool calls, and truncated command outputs delivered into its context window. A **policy** ${\pi_\theta}({a}_k\mid {h}_k)$, parameterized by weights ${\theta}$, defines a probability distribution over responses ${a}_k$ conditioned on that delivered interaction history ${h}_k$ through turn ${k}$. We consider a finite decision horizon ${H}$ with turn indices ${k}=0,\ldots,{H}-1$. (We reserve ${k}$ for agent-environment turns because ${t}$ later indexes individual autoregressive tokens within a rollout.) The history ${h}_k$ plays the role of the recorded state ${s}_k$ in the trajectory notation of **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-hsa|The H·S·A Exposure Space]]**, the runtime’s delivered view at turn ${k}$ rather than the environment itself. A response ${a}_k$ represents either a proposed tool call, such as a shell command or structured API query, or a terminal answer. The runtime validates and executes any requested operation, returning standard output, standard error, or structured payloads as observations for subsequent turns. Because modern context windows cannot always ingest unbounded execution logs, the policy consumes a constructed prompt that may truncate or summarize older history, never inspecting the underlying state ${s}_{k}$ directly. An edited configuration file or sandbox directory affects policy decisions only after tool invocations reflect its contents back into ${h}_k$.

↪ The partially observable Markov decision process behind this observation constraint is developed in **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-pomdp|POMDP formalization of trajectories]]**.

A **rollout**, or sampled trajectory ${\tau}$, records one complete execution trace under specified task definitions, policy weights, environment states, and harness constraints. In our illustrative repair scenario, a trial `rl_trial_01` on task `pool_repair_01` starts container sandbox `pool_fixture_v1` and tests candidate patches against test harness `repair_accept_v1`. Each rollout generates its own telemetry, intermediate command outputs, and terminal verification artifacts; past demonstration records provide no credit to this live attempt.

A **reward** is a scalar score computed under an explicit verification rule. In the simplest formulation, intermediate turns emit zero reward, leaving a single terminal score ${R}({\tau})$ evaluated at horizon completion without temporal discounting (a discount factor ${\gamma}=1$, so a reward counts the same whichever turn it arrives on). The trajectory **return** collapses to this terminal score, giving the expected return objective:

$$
{J}({\theta})=\mathbb{E}_{{\tau}\sim{\pi_\theta}}\left[{R}({\tau})\right].
$$

The expectation averages over policy randomness, task sampling distributions, and environment variations (such as nondeterministic test execution times or network latencies). Maximizing ${J}({\theta})$ drives the policy to increase the expected *measured* reward under these conditions. Whether that measured score reflects true task utility depends on the fidelity of the reward harness itself, an engineering challenge analyzed in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.04 Verifiable Rewards#^sec-vol3-rlvr-rewards|section 17.3]]. When the reward comes from an automated, deterministic check (such as unit test execution, syntax validation, type checking, or a formal proof assistant) rather than from an imperfect learned preference model or manual human grading, this approach is called reinforcement learning with verifiable rewards (RLVR)[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.17 Footnotes#^fn1|¹]] ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.16 Source References#^ref-lambert2024tulu|Lambert et al. 2024]]).

**Definition 17.1: Reinforcement learning with verifiable rewards**

***Reinforcement learning with verifiable rewards (RLVR)*** is policy optimization using reward signals computed by automated checks of specified properties of the policy’s outputs or interactions, such as tests or proof checkers, rather than relying solely on learned preference scores or human ratings.

1.  **Significance**: An automated verification harness provides an objective training signal without requiring step-by-step demonstrations. Directly rewarding task success increases the acceptance rate ${p_{\text{acc}}}$ in the cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**) even when human demonstrations do not exist. However, the verifier’s false-accept rate bounds only the per-rollout chance that a sampled failure is rewarded. When true passes are rare, false accepts can make up a far larger share of the rewarded rollouts ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.04 Verifiable Rewards#^sec-vol3-rlvr-false-accepts|section 17.3.2]]).
2.  **Distinction**: Whereas behavioral cloning trains the policy to reproduce specific recorded responses, RLVR evaluates only whether the completed trajectory satisfies programmatic criteria. The resulting policy gradient is strictly bounded by the coverage, sensitivity, and sandboxed security of the underlying verifier.
3.  **Common pitfall**: Mistaking higher reward scores on a fixed verification suite for broad task competence, or treating automated verification as a reason to relax runtime isolation and execution guardrails.

### Baselines and Credit Assignment

^sec-vol3-rlvr-baselines-credit

When a binary check such as `repair_accept_v1` emits $1$ for a pass and $0$ for a failure, multiplying action log-probabilities directly by the raw score multiplies every failed rollout by zero, leaving the update with no signal to penalize the actions that failed. Policy-gradient algorithms adjust model parameters by estimating a gradient direction that increases or decreases the log-probabilities of sampled actions relative to an offset reference level. Standard estimators subtract a **baseline** from the raw outcome: the centered advantage is ${R}({\tau})-{b}({h}_0)$, where ${b}({h}_0)$ depends on the initial task prompt and context ${h}_0$ but remains independent of the sampled action sequence ${\tau}$. That baseline can be a fixed scalar, an empirical rolling mean across task batches, or a parametric value estimate, and it does not necessarily require training a separate critic network ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.16 Source References#^ref-williams1992simple|Williams 1992]]).

Consider a binary verification check where success yields $1.0$ and failure yields $0.0$. With a fixed baseline of 0.25, a passing rollout receives a centered score of 0.75, whereas a failing rollout yields -0.25. These opposing signs drive gradient updates in opposite directions: positive centered returns reinforce the probabilities of every token and tool call sampled along the passing trajectory, whereas negative centered returns suppress them. In contrast, setting the baseline to zero leaves failed rollouts with a centered score of $0.0$, discarding the negative gradient signal that penalizes counterproductive trajectories.

This uniform attribution illustrates the classic **credit-assignment problem**:[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.17 Footnotes#^fn2|²]] a terminal verifier evaluates overall trajectory success, but it cannot differentiate the decisive tool call from irrelevant or mildly detrimental exploratory steps. While subtracting an appropriate baseline reduces the variance of the policy gradient estimator without introducing bias ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.16 Source References#^ref-greensmith2004variance|Greensmith et al. 2004]]), it applies a uniform scalar adjustment across the entire trajectory rather than isolating action-specific causal effects. [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.05 Credit Across Turns#^sec-vol3-rlvr-credit|Section 17.4]] formalizes these estimators and their bias-variance trade-offs, and [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.06 Group Relative Policy Optimization#^sec-vol3-rlvr-grpo|section 17.5]] introduces group-relative scoring to compute data-dependent baselines across parallel rollouts without training an auxiliary value network.

### Exploration and Protected Assessment

^sec-vol3-rlvr-exploration-assessment

If every sampled rollout on an unfamiliar bug fails `repair_accept_v1`, the batch returns exclusively zero rewards, and subtracting a baseline still gives the optimizer no clue which actions came closer to a fix. Because a policy-gradient update can optimize only over trajectories that the sampling harness actually produces, **exploration**, the sampling of action sequences the policy has rarely tried at points where it still spreads probability across several plausible actions, determines what reinforcement learning can discover. On a binary verification check (pass vs. fail), a task instance that the policy never solves leaves a zero baseline, or one that tracks the observed outcomes such as the mean of a group of attempts ([[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.06 Group Relative Policy Optimization#^sec-vol3-rlvr-grpo-zero-variance|section 17.5.4]]), with every centered score at zero. A fixed positive baseline does produce a gradient, but it pushes down every sampled action alike and gives the update nothing to prefer. Either way, without variation in the outcome signal the update carries no contrast, regardless of how many rollouts the collector generates. If a policy solves a task instance with base probability ${p}$, sampling a group of ${G}$ independent rollouts yields at least one successful trajectory with probability $1-(1-{p})^{G}$. That condition is the one that binds when ${p}$ is small; the group optimizer of [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.06 Group Relative Policy Optimization#^sec-vol3-rlvr-grpo|section 17.5]] also needs at least one failure in the same group, a stricter condition derived there. When ${p}=0$, scaling the group size ${G}$ yields no contrast at all. System builders overcome this cold-start bottleneck by seeding the policy through supervised fine-tuning on demonstrations, curating curricula with progressive difficulty, or structuring reward functions with informative intermediate milestones.

Because exploration systematically exposes edge cases in both the target environment and the evaluation harness, the execution runtime must enforce rigid capability and resource boundaries. As an agent generates thousands of candidate interactions, optimization will exploit any loose permission, such as reading hidden test fixtures, patching Python test runners, or modifying exit codes in the evaluation container, to manufacture high rewards without solving the underlying problem. Preventing such gaming requires a protected assessment boundary. The agent’s actions execute within an isolated sandbox, while the verifier runs with separate privileges, shielded storage, and read-only access to private test suites. [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.08 Verifier Isolation#^sec-vol3-rlvr-sandboxing|Section 17.7]] places that boundary on the reward path once the reward and the update it drives are in place. Even with complete isolation, held-out evaluation on disjoint test distributions remains necessary to determine whether the policy acquired robust problem-solving behavior or merely fit the idiosyncrasies of the training verifiers. Before any of that machinery can be designed, however, the reward itself must be pinned down: what the check measures, how often it is wrong, and how other terms may be added to it without overturning the pass-over-failure order.
