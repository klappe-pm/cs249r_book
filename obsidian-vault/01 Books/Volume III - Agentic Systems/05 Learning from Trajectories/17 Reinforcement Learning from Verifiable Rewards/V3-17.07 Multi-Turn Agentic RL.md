# V3-17.07 Multi-Turn Agentic RL

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17 Reinforcement Learning from Verifiable Rewards|V3-17 Reinforcement Learning from Verifiable Rewards]]

^sec-vol3-rlvr-multi-turn

In a single-turn response, the policy generates one contiguous block of tokens from one static prompt, so the final text holds the entire training example. In a multi-turn repair trial, however, the agent alternates between proposing actions (code edits, shell commands, or structured tool invocations) and reading observations returned by compilers, test runners, and the container runtime, while the harness compacts or truncates older turns to fit the context window.

That interactive loop breaks single-turn training assumptions in three places: earlier conditioning prefixes are overwritten as the context window compacts, environment observations sit interleaved with sampled policy tokens, and infrastructure timeouts or node preemptions can cut an episode off mid-flight. Preserving a valid gradient update across those turns, whether under GRPO or any other multi-turn policy-gradient optimizer, requires capturing each model invocation before compaction alters its prefix, masking non-policy tokens out of the loss denominator, and separating task-budget failures from censored runs.

### Invocation Records

^sec-vol3-rlvr-invocation-records

Consider a concrete execution: trial `rl_trial_01` running against `pool_fixture_v1`. In turn 1, the model invokes a test suite. The harness runs the suite and delivers a truncated failure log. In turn 2, the model conditions on that log and proposes a targeted source patch. By turn 4, context window pressure forces the harness to compress the earlier diagnostic logs into a concise two-line summary. If the training pipeline subsequently attempts to reconstruct the rollout from the final episode transcript, it confronts a corrupted causal graph: turn 2 would appear conditioned on the two-line summary rather than the full failure log that actually prompted the patch. Action probabilities computed against that retrofitted context score the policy’s decisions against information states the agent never encountered during sampling.

To guarantee replay fidelity, the rollout recorder must capture each invocation’s delivered input token prefix alongside the exact token IDs emitted by the generator, linking both to a durable interaction record. Storing full token arrays for every step across millions of rollouts would quickly exhaust cluster storage, so systems deduplicate shared prefixes with immutable content-addressed blobs or prefix-tree references. Along with those prefix references, the record registers the tokenizer version, chat template, attention masks, rotary position offsets, and compaction decisions that shaped the prompt. Storing raw UTF-8 text and re-tokenizing it during training cannot substitute for the recorded token IDs. Small differences in BPE merge rules, whitespace handling, or tool-schema formatting shift token boundaries and sequence lengths, so only the captured IDs preserve the trajectory that was actually sampled. [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.07 Multi-Turn Agentic RL#^tbl-vol3-rlvr-rollout-record|Table 6]] extends the input-fidelity principles established in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.04 Serializing Trajectories#^sec-vol3-fine-tuning-serialization|Serializing Trajectories]]** to the sampling evidence required by multi-turn reinforcement learning.

### Policy Actions and Conditioning Context

^sec-vol3-rlvr-policy-actions-conditioning

Even with every invocation’s input prefix and output tokens preserved in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.07 Multi-Turn Agentic RL#^tbl-vol3-rlvr-rollout-record|table 6]], only a fraction of the tokens in a multi-turn rollout were chosen by the policy; the rest were supplied by the user prompt, the tool harness, or the container environment. To connect those recorded invocations to the mathematical objectives developed earlier, we map the episode into the flattened policy-token index ${t}=1,\ldots,{N}_i$ from [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.06 Group Relative Policy Optimization#^sec-vol3-rlvr-grpo-clipped-objective|section 17.5.2]] for rollout ${i}$, while retaining the structural mapping to invocation ${k}$ and the local generation offset. Each conditioning prefix ${x}_{i,t}$ consists of the exact input context delivered to invocation ${k}$ concatenated with the preceding policy tokens generated within that invocation.

When computing action-scoring losses, the distinction between conditioning and generation is absolute. Prompts, environment feedback, tool payloads, and harness scaffolding act exclusively as conditioning context. They propagate activations through the model to shape downstream attention and predictions, but they are not sampled policy actions; their token log probabilities must never appear in the loss objective. Consequently, loss normalization denominators must count only the scored policy tokens, while the runtime cost accounting tallies prefill processing and decode generation as separate operational line items.

This action-scoring mask serves a different purpose from the imitation masks used in supervised fine-tuning. In the supervised recovery example, the malformed proposal `e2` and its refusal stay in the prefix as context but carry a zero loss mask, so they are never imitation targets, because the objective is imitation of curated behavior (**[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16.05 Observation Loss Masking#^sec-vol3-fine-tuning-loss-masking|Observation Loss Masking]]**). In reinforcement learning, however, the mask identifies the support of the exploration distribution, and verified trajectory post-training (principle [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/V3 Trajectory Learning Principles#^pri-vol3-trajectory-post-training|13]]) admits every sampled action, weighted by its verified outcome. If the policy samples an invalid JSON schema or an unparsable shell command during exploration, that sequence is an authentic policy action, even if the execution harness subsequently refuses to dispatch it. Masking those tokens out because a curator would not present them as demonstrations corrupts the estimator. The malformed tokens escape the negative update, and the failing rollout’s whole negative coefficient lands on its remaining well-formed tokens, so the update pushes down valid syntax in place of the mistake. Similarly, when the model generates an end-of-turn delimiter or stop token, that token is an action that consumed probability mass. By contrast, an abrupt terminator injected by a dataloader when cutting off an execution is harness intervention, not policy choice, and must be excluded. Any partial-action scoring strategy requires an explicit mathematical objective and denominator rather than an ad hoc mask inherited from a supervised training pipeline.

The denominator of the importance-sampling probability ratio must represent the true behavior distribution that generated the token. Inference engines often apply sampling transforms that renormalize the distribution over a restricted subset of the vocabulary, such as temperature scaling, top-${k}$ truncation, nucleus (top-${p}$) filtering, or grammar-constrained finite-state decoding. The rollout record must therefore store the normalized chosen-token log probability under the active generation configuration, along with the sampling parameters required to reconstruct the sampling state. When computing policy updates, the trainer evaluates the numerator under the target policy ${\pi_\theta}$ using the identical prefix recorded during generation. Substituting unconstrained model logits into the denominator treats the behavior policy as an unconstrained softmax. Some systems adopt this simplification to avoid caching rollout probabilities, but it introduces estimator bias that must be tracked explicitly as an approximation.

Freezing the policy checkpoint across each episode substantially simplifies this accounting. In high-throughput asynchronous architectures where weight updates occur concurrently with rollout generation, an agent might execute invocation 1 on checkpoint ${v}_1$ and invocation 2 on checkpoint ${v}_2$. If an infrastructure design permits cross-invocation updates within a single trial, the record must associate behavior checkpoints and generation probabilities per invocation. Tagging the entire rollout with a single model version misattributes the provenance of later tokens.

Once token log probabilities and behavior distributions are properly recorded, the system links the trajectory-level advantage coefficient ${\hat{A}}_i$ to each sampled policy token. If the system assigns advantages at the turn level rather than across the entire trajectory, it must adhere to the estimator and continuation rules detailed in [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.05 Credit Across Turns#^sec-vol3-rlvr-credit|section 17.4]]. Two parallel rollouts that happen to reach turn 3 may possess radically different interaction histories, execution latencies, and tool states; comparing intermediate outcomes purely by matching turn indices provides an invalid foundation for relative reward scoring.

### Stopping and Censored Rollouts

^sec-vol3-rlvr-stopping-censored

Attaching a terminal reward to those scored tokens assumes the episode reached a valid stopping point, yet a repair rollout that halts at 5 minutes because it exhausted its 10-turn task budget and one that halts at 3 minutes because the cluster scheduler reclaimed its host node look identical if the harness logs only that execution stopped. How the learning algorithm interprets an enforced stop depends entirely on the task specification and what triggered the halt. If a task contract defines success as accepted code completion within a declared budget of 10 turns and 5 minutes, exhausting that budget without reaching a solution constitutes an authentic task failure. The policy legitimately receives a zero or negative reward. The rollout record must log the exact termination reason and resource metrics, noting whether the boundary interrupted active model generation or an external tool execution.

Other interruptions stem from external operational limits rather than policy choices. For example, a single tool invocation exceeding a 30 s sandbox deadline produces an error observation from which the agent can still recover. Alternatively, an assessment microservice may crash, leaving the verifier unable to score an otherwise complete pull request. If an orchestration worker aborts an active rollout because the cluster scheduler reclaims the node or the batch queue deadline expires before task budget exhaustion, the collector produces a **censored rollout**. The rollout record must treat budget exhaustion, observation recovery, verifier unavailability, and infrastructure preemption as mutually exclusive execution states. They map onto the four-verdict rule of **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.03 The Task Acceptance Contract#^sec-vol3-evaluation-contract-verdicts|The four-verdict rule]]**. Budget exhaustion is a `fail`. A recovered tool error is an ordinary observation inside the trajectory. Verifier unavailability and preemption leave the outcome `pending` while a retry is still possible and `unknown` once it is not. Throughout this chapter, a censored or unresolved rollout means one in the last two states, whose reward is missing because of the infrastructure rather than the policy.

Mishandling censored rollouts biases the training data in one of two opposite directions. Silently discarding incomplete rollouts introduces classic survivorship bias, purging complex, multi-turn trajectories from the training set and skewing policy optimization toward trivial, fast tasks. Conversely, assigning a default reward of zero to rollouts interrupted by infrastructure outages penalizes the agent for distributed system failures, teaching the policy to avoid long multi-step trajectories. The training pipeline must declare an explicit policy for censored episodes: waiting for asynchronous verifier recovery, scheduling idempotently bounded retries, or applying statistical imputation methods that account for missing outcomes without biasing advantage estimates.

Finally, terminating policy sampling does not automatically stop pending asynchronous operations. Dispatched bash subshells, spawned containers, and cloud API calls remain active until explicitly cancelled. The harness must track resource ownership across the full operational lifecycle, ensuring that abandoned or censored rollouts clean up orphaned processes and container volumes regardless of whether the resulting trajectory is admitted into an optimization batch.

### Collection and Deployment Contracts

^sec-vol3-rlvr-collection-deployment-contracts

Those turn caps, context compaction policies, observation truncation limits, and tool refusal responses are not passive safety rails; they define the Markov decision process that the policy explores. If the training environment diverges from the intended deployment contract, the agent learns behavioral adaptations that fail in production: a policy trained with a generous 50-turn allowance can learn meandering trial-and-error debugging strategies that collapse when placed under a strict 10-turn production limit. When teams intentionally expand training budgets as an exploratory curriculum to bootstrap discovery in sparse-reward environments, the transfer penalty under tighter deployment constraints must be tracked as an explicit empirical metric.

Decoupling model invocation from episode lifetime is equally important for cluster efficiency. Tool-heavy agent rollouts can spend most of their lifetime waiting for external work: a policy might generate a tool request in 200 ms, followed by a 45 s wait while an external container compiles code and runs a test suite. An accelerator held for that rollout during the wait would compute for under 1 percent of the episode, and the loss compounds across every rollout in the training cluster. High-throughput collection engines decouple inference serving from episode execution, scheduling active invocations from other ready rollouts onto the accelerator while blocked rollouts wait for external tool observations. This interleaving maximizes hardware utilization without changing the causal observation stream consumed by any individual trajectory. [[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.10 Environments and Rollouts#^sec-vol3-rlvr-infrastructure|Section 17.9]] develops the bounded queues, group completion barriers, and version-tracking protocols required to coordinate that asynchronous schedule at scale. A rollout record can give a faithful account of what the policy observed, what tokens it generated, and how the environment responded. That recorded trajectory can still guide policy updates safely only if an uncompromised boundary separates the artifacts the policy is permitted to modify from the independent harness that evaluates them.
