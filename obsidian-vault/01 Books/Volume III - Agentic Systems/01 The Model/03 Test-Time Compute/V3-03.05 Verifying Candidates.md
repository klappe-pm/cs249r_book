# V3-03.05 Verifying Candidates

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03 Test-Time Compute|V3-03 Test-Time Compute]]

^sec-vol3-test-time-compute-verification

In a connection-pool repair, clean compilation confirms only syntax and types, and even a targeted concurrency test exercises only a handful of thread schedules and can miss a race condition. Every verification check answers a bounded question, never the whole question of whether a candidate is safe to ship. Engineers therefore have to decide which checks to run, whether to attach them to finished candidates or to intermediate steps, and how much trust to place in a passing verdict when valid candidates are rare.

### Checking Whole Outputs Vs. Intermediate Steps

^sec-vol3-test-time-compute-outcome-step-evidence

Waiting until a candidate patch is completely written before running any check wastes every token spent elaborating a diagnosis that went wrong in step one, whereas scoring every intermediate step from scratch rescans the growing prefix again and again. An **outcome check** tests a completed candidate against an external rule, such as whether a patched service passes an end-to-end regression suite. An **outcome reward model**, by contrast, predicts a scalar quality score for the finished candidate, like the learned verifiers trained to rank candidate solutions in mathematical reasoning ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-cobbe2021training|Cobbe et al. 2021]]). The outcome check runs the artifact and reports what happened; the reward model only predicts how good the artifact looks.

Step-level checks evaluate intermediate claims or partial states before the candidate is complete. In the connection-pool repair, a step check can test whether a waiting worker receives a wake-up signal before the agent drafts a full timeout patch. If the trace refutes the timeout explanation, the runtime drops that branch immediately and saves the remaining generation tokens. Learned process scorers similarly score or prune partial reasoning traces, using low step scores as early warnings of downstream failure. **Process supervision**[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.14 Footnotes#^fn2|²]] attaches feedback to discrete intermediate steps rather than waiting for the final answer ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-uesato2022solving|Uesato et al. 2022]]; [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-lightman2023let|Lightman et al. 2024]]). What separates outcome feedback from process feedback is where the signal attaches, not what the scorer reads, since a learned outcome scorer can also read the full reasoning trace before grading the final output.

**Definition 3.3: Process reward model (PRM)**

A ***process reward model*** (PRM) is a learned scorer that assigns a value to each intermediate step of a candidate trajectory, conditioned on the task context and the preceding steps.

1.  **Significance**: Step scores allow search algorithms to prune unpromising branches early, keeping beam search and tree search, the search procedures that extend only the best-scoring partial candidates ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.07 Bounded Search#^sec-vol3-test-time-compute-search-structures|section 3.6.1]]), within finite computational budgets.
2.  **Distinction**: An outcome reward model evaluates only terminal states; a process reward model assigns credit across intermediate steps. This early steering capability requires dense step-level supervision, which costs substantially more to gather than automated test outcomes.
3.  **Common pitfall**: Mistaking a high step score for verified correctness. A process reward model provides heuristic guidance for ranking and pruning, but it offers no formal guarantees and satisfies no closure evidence level.

Each granularity catches failures the other misses. An outcome check tests the assembled artifact end to end, catching integration bugs that look harmless inside any single step. A process check catches errors early and stops broken branches from burning more generation tokens, but checking too often adds scorer overhead and risks pruning good branches when step scores are noisy. Choosing how often to check balances saved generation tokens against scorer cost and false rejections.

Step-scoring cost also depends on whether the serving engine reuses prefix state across steps. Suppose a scorer reads a task prompt of ${S}$ tokens plus the candidate’s growing prefix after each of its ${J}$ steps, where each step adds ${\Delta} {S_{\text{step}}}$ tokens. Scoring each cumulative prefix from scratch, without reusing key-value cache state from earlier steps, processes

$$
\sum_{j=1}^{{J}}\left({S} + {j}\,{\Delta} {S_{\text{step}}}\right) = {J} {S} + \frac{{J}({J}+1)}{2}\,{\Delta} {S_{\text{step}}} \tag{2}
$$

^eq-vol3-prm-rescoring

scorer input tokens, which grows quadratically with the number of steps ${J}$. The beam-search calculation later in this chapter (notebook [3.6](https://mlsysbook.ai/vol3/03_test_time_compute/03_test_time_compute.html#nbk-03-compute-allocation-and-latency-trade-offs)) charges the ${j}\,{\Delta} {S_{\text{step}}}$ term of [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^eq-vol3-prm-rescoring|equation 2]], with the task prompt ${S}$ excluded, for every extension scored at step ${j}$. When the serving engine caches prefixes across steps, incremental scoring reads only the new ${\Delta} {S_{\text{step}}}$ tokens at each step and removes the quadratic growth; scorers that must re-read the whole candidate without prefix caching pay the full sum.

[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^tbl-vol3-verifier-classes|Table 4]] compares four common kinds of check by what they inspect, where they can be fooled, whether they are deterministic, and which closure evidence level (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-invariant-closure|The invariant closure principle]]**) they reach. Compilers and sealed test suites establish bounded, reproducible facts within their scope, whereas learned scorers only rank or prune candidates.

### How Base Rates Limit Check Precision

^sec-vol3-test-time-compute-check-precision

When only 5 percent of generated patches actually fix a bug, even a test suite that falsely passes just 2 percent of broken patches leaves nearly a third of all passing candidates defective. The reliability question for any check is what share of the candidates that pass it are genuinely valid. Call meeting the full task specification $\text{Valid}$ and receiving a positive check verdict $\text{PASS}$. Let ${p_{\text{valid}}} = \Pr(\text{Valid})$ be the base rate of valid candidates in the generator’s output distribution, ${\epsilon_{\text{FA}}} = \Pr(\text{PASS}\mid\neg\text{Valid})$ the **false acceptance rate**, and ${\epsilon_{\text{FR}}} = \Pr(\neg\text{PASS}\mid\text{Valid})$ the **false rejection rate**. Here “acceptance” means passing the internal verifier, not authorization to ship to production. The valid-candidate rate ${p_{\text{valid}}}$ is not the test-pass probability ${p}$ used in pass@${k}$: ${p_{\text{valid}}}$ is the chance of meeting the full task specification, whereas ${p}$ is the chance of passing the stated tests. A perfect check makes the two coincide; an imperfect check separates them, and the precision formula below measures the gap.

The total probability that a random candidate passes the verifier is ${q}={p_{\text{valid}}}(1-{\epsilon_{\text{FR}}})+(1-{p_{\text{valid}}})\,{\epsilon_{\text{FA}}}$. Applying the same Bayes’ rule that gave the defect share among one checker’s passing patches (**[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^eq-vol3-fm-checker-posterior|equation 2.4]]**) gives the precision of positive verdicts:

$$
{\Pi_{V}} \equiv \Pr(\text{Valid}\mid\text{PASS}) =\frac{{p_{\text{valid}}}(1-{\epsilon_{\text{FR}}})}{{p_{\text{valid}}}(1-{\epsilon_{\text{FR}}})+(1-{p_{\text{valid}}})\,{\epsilon_{\text{FA}}}}. \tag{3}
$$

^eq-vol3-verifier-precision

![[90 Assets/Volume III/03 Test Time Compute/Vol3 Ttc Margin Precision Base Rate 519a3437f7.svg]]

*A dark curve of the valid share among passing candidates plotted against the valid-candidate rate. It rises steeply at low rates and flattens near the top. The low-rate region is shaded red, and a red dot is labeled 5 percent valid, 70 percent of passes.*

*At a low valid rate, even a strict check passes many invalid candidates.*

When valid candidates are rare, even a check with a small false acceptance rate produces a passing pool where broken candidates make up a large share, the same base-rate trap that **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^sec-vol3-foundation-model-self-review-evidence|Self-review and external evidence]]** showed for a single checked patch. Applied across a candidate pool, this is the verification asymmetry (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-verification-asymmetry|3]]) in quantitative form. Generating a passing candidate and knowing that a passing candidate is valid are different events, and the base rate and checker error rates, not the pool size, bound how far a pass can be trusted. Both error rates therefore have to be measured on real tasks for each model family and test harness.

While [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^eq-vol3-verifier-precision|equation 3]] describes the pool of passing candidates as a whole, the reliability of the single candidate the runtime *returns* depends on the selection rule. Suppose candidate-check pairs are drawn independently and identically for a fixed task under constant error rates. Suppose also that the runtime checks the pool in a fixed order unrelated to quality, returns the first candidate that passes, and abstains if none passes. Under that first-passing rule, the probability that a returned candidate is valid equals ${\Pi_{V}}$: learning that earlier candidates in the list failed does not change the conditional validity of the first one that passes. Picking the candidate with the highest continuous reward score behaves differently, because maximizing a noisy score actively concentrates positive scoring errors, as the next subsection shows.

**Napkin Math 3.4: Yield and risk under asymmetric verifier error**

**Problem**: A repair policy generates all 64 candidates before selection. It uses the first-passing rule above and abstains when no candidate passes. What does additional breadth buy, and what risk remains?

**Variables**: All rates are hypothetical. Each candidate contains 1,024 tokens, billed at \$15 per million output tokens. The valid-candidate rate is 5 percent, false rejection is 10 percent, and false acceptance is 2 percent. Suppose a separately authorized deployment policy deploys the selected candidate without further checking. A defective deployment incurs \$500 in incident loss. For this calculation alone, valid deployments and abstentions incur zero incident loss, and missed repairs and delay are left unpriced.

**Math**: The expected passing counts are 2.88 valid candidates and 1.216 invalid candidates, totaling 4.096. [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^eq-vol3-verifier-precision|Equation 3]] yields 70.31 percent precision. Conditional on making a selection, the probability of a defective selection is therefore 29.69 percent, with expected incident loss \$148.44 per selected deployment.

The probability of any selection is $1-(1-{q})^{N}$, or 98.55 percent; the policy abstains on 1.45 percent of batches. Multiplying selection coverage by conditional defect probability gives 29.26 percent defective selections per task attempt and \$146.28 expected incident loss per attempt, including abstentions. Generating the entire batch costs \$0.98 in output charges. Input charges, checking, and other operational costs are omitted. A sequential policy that stops generation at the first pass would have a different generation bill.

**Systems insight**: Expected incident loss per attempt is about 149 times the output bill, so the acceptance policy, not the token price, sets the cost of this task. Precision responds to two knobs of similar strength: halving the false acceptance rate raises it from 70.31 percent to 82.6 percent, and doubling the valid-candidate rate raises it to 83.3 percent. More candidates move neither. At a low base rate, spend on whichever of a better generator or a stricter check is cheaper, and price false rejections too when a missed valid repair is costly.

With ${p_{\text{valid}}}$, ${\epsilon_{\text{FA}}}$, and ${\epsilon_{\text{FR}}}$ held fixed, growing the pool size ${N}$ does not change precision ${\Pi_{V}}$. A wider pool raises the chance of finding at least one passing candidate, but it also raises the chance that the batch holds at least one false pass: $1-[1-(1-{p_{\text{valid}}})\,{\epsilon_{\text{FA}}}]^{N}$. In the calculation above, that false-pass exposure reaches 70.70 percent, while the probability of actually returning a defective candidate is 29.26 percent. The gap arises because under a first-passing rule a false pass later in the batch does no harm if an earlier valid candidate passes first. Pool availability, passing-set precision, and deployed defect risk are three distinct numbers.

### How Search Exploits Imperfect Checks

^sec-vol3-test-time-compute-selection-pressure

The more candidates a search generates and ranks against an imperfect scorer or test suite, the more likely the winning candidate is one that exploited a scorer blind spot or deleted a failing assertion rather than fixing the bug. Fixed error rates describe passive sampling from a fixed distribution, but adaptive search changes the candidates themselves. When a search policy steers generation or picks the maximum of a noisy score, it pushes candidates into regions where the evaluator is poorly calibrated, so the baseline rates ${p_{\text{valid}}}$, ${\epsilon_{\text{FA}}}$, and ${\epsilon_{\text{FR}}}$ no longer hold for the candidates that reach the end of the search. Optimizing against an imperfect proxy breaks down in three distinct ways ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-manheim2018categorizing|Manheim and Garrabrant 2018]]). Manheim and Garrabrant classify them as forms of Goodhart’s law.[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.14 Footnotes#^fn3|³]] In *regressional* Goodhart, picking the highest score selects for positive measurement noise. In *extremal* Goodhart, correlations that hold on typical candidates break down in the tail reached by search. In *adversarial* Goodhart, candidate code tampers with or bypasses the test harness.

The regressional effect can be written out directly. Suppose a learned scorer reports an estimated utility ${\hat{U}}_i = {U}_i + {\epsilon}_i$ for candidate ${i}$, where ${U}_i$ is true task utility and ${\epsilon}_i$ is an independent scoring error with mean zero and standard deviation ${\sigma}$ (scoring noise, distinct from the per-turn error rate in horizon compounding). Picking $\arg\max_i {\hat{U}}_i$ maximizes the sum of utility and noise, so the winning candidate is disproportionately one that drew a large positive error. For independent Gaussian errors, the expected maximum error across ${N}$ candidates scales for large ${N}$ as

$$
\mathbb{E}\Bigl[\max_{i \le {N}} {\epsilon}_i\Bigr] \approx {\sigma}\sqrt{2\ln {N}}. \tag{4}
$$

^eq-vol3-argmax-noise

In units of ${\sigma}$, the exact expectation is 1.0 at 4 candidates and 2.3 at 64 candidates, where the asymptotic formula gives 2.9.[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.14 Footnotes#^fn4|⁴]] That expected maximum is an upper bound on the winner’s expected scoring error, reached when all candidates have the same true utility. When true utilities vary, selection responds to both utility and noise (Exercise 8 derives the winner’s error for a Gaussian utility model). An acceptance threshold calibrated on single, unselected completions therefore cannot be reused unmodified on argmax-selected winners.

A rising scoring error on the winner does not by itself mean that true utility is falling. In Exercise 8(b), independent Gaussian utility and noise make both the winner’s expected utility and its expected scoring error rise with pool size. Empirical studies of best-of-${N}$ sampling under learned reward models show a sharper divergence: the proxy score keeps climbing while a held-out reference score rises, flattens, and then drops ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-gao2023scaling|Gao et al. 2023]]). That downturn comes from tail miscalibration or exploitable gaps in the proxy, not from [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^eq-vol3-argmax-noise|equation 4]] alone. [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^fig-vol3-goodhart-divergence|Figure 4]] sketches the pattern, with the winner’s proxy score rising (dashed blue curve) while the held-out reference score peaks and turns down (solid green curve).

![[90 Assets/Volume III/03 Test Time Compute/Goodhart Divergence d760149639.svg]]

Figure 4: **Proxy and Reference Scores under Selection**: A qualitative sketch of the measured best-of-${N}$ pattern. The proxy score of the selected candidate keeps rising as ${N}$ grows, while a held-out reference score rises and then declines. The widening gap illustrates proxy optimism under selection; the declining reference score is an empirical pattern, not a necessary consequence of growing scoring error. The axes carry no values, and the point where the reference score turns down depends on the task.

^fig-vol3-goodhart-divergence

Checker blind spots compound across large pools by the same binomial arithmetic as pass@${k}$. If an unmodeled edge case or loophole appears in a fraction ${p_{\text{exp}}}$ of single draws, a pool of ${N}$ candidates contains at least one loophole-exploiting candidate with probability $1-(1-{p_{\text{exp}}})^{N}$. A loophole that shows up in only 0.5 percent of individual samples, rare enough to miss during single-call testing, appears in a batch of 64 candidates with probability 27.4 percent. Once a broken candidate slips through that loophole and receives a passing mark, competitive selection promotes it. Checker accuracy measured on unselected outputs therefore overstates accuracy under search, and the gap widens as the pool grows.

In the connection-pool repair, a patch can pass the test suite either by fixing the missing wake-up notification or by deleting the unit-test assertion that checks for blocked worker threads. Both edits raise the test score, and only the first fixes the bug. The candidate under test must therefore be isolated from the verifier so that generated code cannot edit test files or forge pass signals.

↪ Grader isolation enforces this separation down to the candidate’s process and interpreter, as developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.04 Hermetic Evaluation Gyms#^sec-vol3-evaluation-gyms-grader-isolation|Grader isolation]]**.

Isolating the grader stops tampering, but it does not widen what the test suite covers: a sealed regression suite still misses untested thread schedules, and a learned judge can still prefer confident, broken code. Evaluation must therefore test the outputs that the complete search policy produces at its deployed budget, counting false acceptances and abstentions explicitly. Adding confidence requires an independent check that covers a different failure mode rather than a second correlated scorer.

Verification also produces concrete intermediate facts that later turns can reuse, including refuted diagnoses, verified invariants, and passing test subsets. When a check refutes one assumption inside a multi-part candidate plan, the runtime does not need to throw away components that never depended on that assumption, provided it records which parts of the plan rest on which premises.
