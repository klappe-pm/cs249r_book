# V3-03.10 Summary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03 Test-Time Compute|V3-03 Test-Time Compute]]

^sec-vol3-ch3-summary

Test-time compute turns the cost of a decision into an explicit runtime trade-off. While model weights fix what a single forward pass can do, the runtime chooses how much extra work to spend, whether to spend it on depth, breadth, or feedback, and what evidence justifies stopping. Extra deliberation lowers cost per accepted task only when three links all hold. Generation surfaces a valid candidate that a single call missed, the selector picks that candidate out of the pool, and the verifier checks the property the task actually requires. If any link fails, attempt cost rises while the acceptance rate ${p_{\text{acc}}}$ stalls, driving up ${C_{\text{eff}}}$. A deliberation policy should therefore be judged like any other systems component: by the accepted tasks it delivers per dollar and per second within the service deadline. **Key Takeaways: More work needs a bounded policy**

- **Observe when the question is empirical**: Generating more tokens re-examines what is already in the prompt, whereas running an external check brings in new runtime facts. In the connection-pool repair, generating one explanatory trace took 539.5× as long as the targeted probe that separated the two hypotheses.
- **A pool is only as good as its selector**: Pass@${k}$ caps what an unchanged-member selector can return, not what it actually returns. Averaging pass rates across a mixed workload naively predicts 94.2 percent success across 8 candidates when the true pool delivers only 50.0 percent, because extra samples cannot solve tasks where the model has zero chance of success.
- **A pass inherits the base rate**: When valid candidates make up 5 percent of the generator’s output, a verifier with a 2 percent false acceptance rate leaves only 70.31 percent of passing candidates valid. Under the fixed IID first-passing rule, returned candidates have that same precision regardless of pool size. With equal true utilities and independent Gaussian noise, picking the top score among 64 candidates inflates the winner’s score by about 2.3 standard deviations of noise.
- **Revise along recorded dependencies**: When an observation refutes an assumption, regenerate only the artifacts that depend on it rather than rebuilding the whole candidate plan. Missing dependency edges let stale conclusions survive silently, and plan revision never undoes side effects already committed to external systems.
- **Budgets end searches, not uncertainty**: Every pruned branch, verifier call, and failed attempt belongs in the cost per accepted task ${C_{\text{eff}}}$, and service deadlines bound how many sequential rounds can run. When a budget or deadline runs out without an accepted candidate, the runtime must abstain or escalate rather than returning the top-scoring unverified candidate.

^callout-takeaways--3-2-ec6e1013

The verification asymmetry (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-verification-asymmetry|3]]) gives a practical order for diagnosing any deliberation policy whose cost per accepted task is too high. First check pool availability per task via pass@${N}$. If passing candidates rarely enter the pool, switch to a stronger model or escalate rather than sampling wider. If the pass rate for a task is zero under the current prompt and model, more samples will not help. Where availability is healthy, check ${\Pi_{V}}$ at the measured base rate, because a low precision means a better generator or a stricter check buys more than a larger pool. Only when both availability and precision are sound does the question become how many rounds of search to buy, which the marginal stopping rule answers in conditional acceptance gain per dollar. At every step, the runtime, not the model, decides whether to continue, abstain, or escalate.
