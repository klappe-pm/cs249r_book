# V3-03.03 Three Axes of Test-Time Compute

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03 Test-Time Compute|V3-03 Test-Time Compute]]

^sec-vol3-test-time-compute-computation-allocation

Giving a repair agent a four-thousand-token allowance does not determine its latency, memory footprint, or diagnostic reach, because the runtime can spend those same four thousand tokens on one long derivation, four parallel candidate patches, or three edit–test–revise rounds. Although all three options can consume the same number of output tokens, they stress the serving system in different ways. A long derivation generates tokens one after another along a single causal chain. Independent candidate patches can run concurrently across accelerator hardware. An edit–test–revise loop must pause model generation while each diagnostic test runs. Those dependencies determine which operations sit on the critical latency path and how much state the serving engine must hold in memory.

**Depth** extends sequential computation within a single candidate, **breadth** explores multiple candidate paths concurrently, and **feedback** folds environment observations into subsequent revisions. A **test-time deliberation rollout** is one bounded candidate-generation path, potentially interleaving verification checks and observation-driven revisions; the term comes from game search, where a rollout plays one line of moves forward to its end. Depth lengthens a rollout, breadth runs several in parallel, and feedback inserts checks between a rollout’s turns. An allocation policy can combine all three: it might generate several candidate patches in parallel, run regression tests against each, and spend deeper step-by-step reasoning only on the most promising survivor. Throughout, model weights remain frozen, and every axis draws from the same test-time budget.

**Definition 3.1: Test-time compute budget**

***Test-time compute budget*** is the per-decision allowance of processed prompt tokens, generated tokens, model invocations, verification checks, and elapsed wall-clock time that a runtime may expend, with model weights fixed, before it must select a candidate, abstain, or escalate to a human operator.

1.  **Significance**: The budget sets the attempt cost in the effective cost per accepted task, ${C_{\text{eff}}} = \mathbb{E}[{C_{\text{attempt}}}]/{p_{\text{acc}}}$ (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**). Additional deliberation reduces cost per accepted task when it increases the acceptance rate ${p_{\text{acc}}}$ proportionally faster than it increases the expected attempt cost. A higher cost per accepted task can still be justified when it buys the required acceptance rate within the deadline ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.08 Evaluating Deliberation Policies#^sec-vol3-test-time-compute-operating-point|section 3.7.3]]).
2.  **Distinction**: Training compute amortizes weight optimization once across all future tasks. Test-time compute recurs on every decision, where an internal reasoning allowance is merely one control surface alongside external tool invocations and verification checks.
3.  **Common pitfall**: Treating the maximum allocation ceiling as the expected spend, or treating an exhausted budget as evidence that the best remaining candidate is acceptable.

What separates the three axes is their dependency structure ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^fig-vol3-allocation-axes|figure 2]]). Depth extends a single candidate through multi-step reasoning, breadth fans out to sampled candidates that converge on a selector, and feedback routes a candidate through a sandboxed check whose observation conditions the revision.

Figure 2: **Three compute allocation topologies**: Depth extends one candidate; breadth exposes separate sampled candidate paths followed by selection; feedback makes a later candidate depend on an observed check result. The arrows show dependencies, not guaranteed latency, cost, or correctness.

### Extending Reasoning Along the Depth Axis

^sec-vol3-test-time-compute-depth-axis

Asking a model to jump straight from a bug report to a patch often misses multi-step lock interactions, yet letting it reason for thousands of tokens puts every step onto the critical latency path and can exhaust the output limit before any code is emitted. Extending a call along the depth axis lets an autoregressive model unroll intermediate reasoning tokens before emitting its final decision or artifact, generalizing early scratchpad techniques and chain-of-thought prompting ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-nye2021show|Nye et al. 2021]]; [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-wei2022cot|Wei et al. 2022]]). In the connection-pool scenario, these intermediate tokens might trace thread interleavings step by step: acquiring the pool mutex, checking for leaked socket descriptors, and signaling waiter condition variables. Because autoregressive generation conditions on all prior tokens, later decoding steps can inspect earlier derivations, catch flawed assumptions, and change course before emitting code. That gain comes entirely from running extra forward passes over the growing context rather than changing the network weights.

On the hardware, however, extending a single generation path serializes the work. Because transformer decoding at small batch sizes is memory-bandwidth bound, step latency is set by the time needed to stream all model parameters from high-bandwidth memory into processor caches (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-memory-bandwidth-decoding|2]]). Wall-clock generation time therefore scales roughly linearly with the number of generated tokens under a fixed serving setup. A long reasoning trace shows only that the accelerator performed more work, not that the resulting code compiles or runs correctly. The runtime must also leave enough output budget for the final patch: a derivation that hits the token limit mid-thought returns a truncated response, which the invocation contract quarantines like any other incomplete call rather than admitting as a candidate.

### Parallel Sampling Along the Breadth Axis

^sec-vol3-test-time-compute-breadth-axis

Drawing a single completion commits the repair to whatever hypothesis the model’s first tokens favored, and if that initial framing is wrong, extra depth only elaborates a flawed premise. Sampling along the breadth axis hedges against that commitment by requesting multiple candidate patches from the same source excerpt and task specification using stochastic decoding controls. Conditional on a fixed prompt and independent random seeds, these samples are statistically independent draws from the model’s output distribution. Even so, they remain bounded by what the model knows: if the model assigns negligible probability mass to a valid thread-notification pattern, every independent sample can repeat the same missing broadcast. Independent draws can still fail in identical ways.

↩︎ Temperature, top-${k}$, and nucleus sampling controls are established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.05 Autoregressive Generation#^sec-vol3-foundation-model-sampling-controls|Sampling controls]]**.

Because parallel candidates do not depend on one another, breadth exposes fine-grained concurrency at modest latency cost. Under memory-bandwidth-bound decoding (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-memory-bandwidth-decoding|2]]), a batch of ${N}$ concurrent candidate streams reads the model weights once per step for all ${N}$ tokens. Spending an allowance of ${N} \times {K}$ tokens sequentially along the depth axis multiplies generation latency by roughly ${N}$. Generating ${N}$ candidates of length ${K}$ in parallel, by contrast, keeps total generation time close to the duration of the longest candidate, $\max_n {T_{\text{decode}}}({K}_n)$, provided the batch stays memory-bandwidth bound and fits in accelerator memory.

Accelerator memory is where breadth extracts its price. Each active generation stream must maintain its own key-value (KV) cache for the tokens it generates. When the serving system shares prefixes across streams, the ${S}$-token prompt is stored once in memory, and peak KV cache demand scales as

$$
{M_{\text{KV}}^{\text{breadth}}} \propto {S} + \sum_{n=1}^{{N}} {K}_n
$$

Without shared prefix caching, the serving engine stores ${N}$ copies of the prompt’s KV tensors, and memory demand scales as ${N} {S} + \sum_n {K}_n$. When total KV cache demand exceeds hardware capacity, the serving engine must split candidates into sequential waves. Once forced into waves, breadth latency degrades from the duration of the single longest candidate toward the sum across waves, while memory thrashing and queueing delays stretch individual token latencies. Whether identical prompt prefixes share physical memory or receive provider billing discounts depends on the serving engine.

↪ Block sharing, which stores a common prompt’s KV state once for every candidate that branches from it, is developed in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.05 Paged KV Allocation#^sec-vol3-kv-cache-cow-prefix-sharing|Copy-on-write prefix sharing]]**.

Breadth also shifts the burden downstream, because generating a wide pool of candidates pays off only if the runtime can tell which candidate is best. A pool that holds a working patch is useless if the selector cannot identify it. In a study of repeated sampling, Brown et al. ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-brown2024monkeys|2024]]) showed that the probability that at least one candidate is correct (pass@${k}$) kept rising across four orders of magnitude of samples. In contrast, practical selectors such as majority voting and learned reward models (scorers trained to predict whether a candidate is correct, examined in [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^sec-vol3-test-time-compute-outcome-step-evidence|section 3.4.1]]) plateaued after a few hundred samples. Candidate selection is therefore a major consumer of compute and verification budget, not an incidental final step.

### Revising from Observations Along the Feedback Axis

^sec-vol3-test-time-compute-feedback-axis

Neither a longer chain of thought nor a wider pool of samples tells the model whether a waiting thread actually receives a condition-variable signal at runtime. The feedback axis supplies that missing evidence by executing a check on a candidate and feeding the resulting observation into the next model request. Instead of relying on frozen weights and a static prompt alone, the repair agent proposes a candidate patch, the runtime runs a bounded test suite, and the next model call receives concrete diagnostics such as a stack trace from a deadlocked worker thread. Those runtime observations narrow the next candidate far more sharply than asking the model to reread the original prompt on its own ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-shinn2023reflexion|Shinn et al. 2023]]).

Verification checks return structured outcomes: failure, pass, or inconclusive execution (such as a test timeout). A failure trace points to broken assertions or regressions; a passing test confirms that the code satisfies the exercised assertions under the tested conditions; and final acceptance remains a separate policy gate. Running diagnostics is itself an external action that consumes CPU and memory, runs inside a sandbox, and adds wall-clock latency even when used only inside deliberation.

Each feedback round is also one more turn of the horizon ${H}$, which ties this axis to horizon compounding (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-horizon-compounding|equation 1.1]]**). Unchecked turns compound error as $(1-{\epsilon})^{{H}}$, and the introduction showed (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^sec-vol3-intro-horizon-arithmetic|Reliability and Cost over a Horizon]]**) that a check which rejects a bad step and retries it resets that compounding. Feedback is the one axis that places such a check inside every turn, so it can lengthen a deliberation without the unchecked compounding its extra turns would otherwise carry, to the extent that its checks deserve trust ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^sec-vol3-test-time-compute-verification|section 3.4]]).

Feedback forces strict serialization because the next revision cannot start until the current check finishes and returns its observation. Context policies that append every prior candidate and diagnostic report also make the input prompt grow from turn to turn. For an initial prompt length ${S_{\text{base}}}$, candidate lengths ${K}_j$, and observation lengths $\lvert {o}_j\rvert$, an append-only policy yields an input length at turn ${t}$ of

$$
{S}^{({t})} = {S_{\text{base}}} + \sum_{j=1}^{{t}-1}({K}_j + \lvert {o}_j\rvert)
$$

This is the append-only growth that **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 2.9]]** priced across a whole trajectory, now confined to one decision, and it drives up prompt prefill latency, accelerator memory usage, and token billing on every round. Context-compaction methods can summarize earlier attempts or drop stale diagnostic traces, but the allocation policy must budget for the full token volume actually sent to the model API.

↪ Context-compaction methods and their scheduling within the request budget are developed in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/04 Context Engineering/V3-04.06 Context Compaction#^sec-vol3-context-engineering-compaction|Context Compaction]]**.

### The Three Axes Under One Output Ceiling

^sec-vol3-test-time-compute-common-output-ceiling

Capping generated tokens at a single number does not cap wall-clock latency, accelerator memory, or input-token billing, because depth, breadth, and feedback turn the same output ceiling into different resource loads. Runtimes therefore track four quantities across the three axes: input and output token counts, critical-path wall-clock latency, peak retained accelerator state, and external information gained. Let ${T_{\text{prefill}}}({S})$ be the time required to ingest an ${S}$-token prompt, ${t_{\text{decode}}}$ the per-token decoding step time, and ${T_{\text{decode}}}({K})$ the total generation time for ${K}$ tokens. Let ${t_{\text{check}}}$ be the duration of the external check in feedback round ${t}$, which is also the turn index of the trajectory. With ${K_{\text{ext}}}$ tokens of extended depth, ${N}$ breadth candidates executed concurrently, and ${H}$ feedback turns, the latency dimension decomposes into three critical paths:

$$
\begin{aligned} {T^{\text{depth}}} &\approx {T_{\text{prefill}}}({S}) + {K_{\text{ext}}}\,{t_{\text{decode}}},\\ {T^{\text{breadth}}} &\approx {T_{\text{prefill}}}({S}) + \max_{n} {T_{\text{decode}}}({K}_n),\\ {T^{\text{feedback}}} &\approx \sum_{t=1}^{{H}}\bigl({T_{\text{prefill}}}({S}^{({t})}) + {T_{\text{decode}}}({K}_t) + {{t_{\text{check}}}}_{{t}}\bigr). \end{aligned} \tag{1}
$$

^eq-vol3-allocation-critical-path

The critical path for breadth assumes the serving cluster has enough memory and compute capacity to decode all ${N}$ streams concurrently at an unchanged step time. When capacity saturates, decoding falls back into serialized waves and shifts the critical path toward the sum across candidate streams. The feedback expression, by contrast, grows from two sources: sequential check durations ${t_{\text{check}}}$ and lengthening prompt prefill times ${T_{\text{prefill}}}({S}^{({t})})$ as context accumulates. [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^eq-vol3-allocation-critical-path|Equation 1]] covers only latency; [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^tbl-vol3-allocation-model|table 1]] sets those critical paths beside the tokens processed, the peak model state retained, and the external information acquired.

| **Axis** | **Tokens processed**                                        | **Critical path**                  | **Peak retained model state**                          | **New information**                      |
|:---------|:------------------------------------------------------------|:-----------------------------------|:-------------------------------------------------------|:-----------------------------------------|
| Depth    | ${S} + {K_{\text{ext}}}$                                    | One dependent sequence             | One context of ${S} + {K_{\text{ext}}}$ tokens         | None beyond the request and weights      |
| Breadth  | ${S} + \sum_n {K}_n$ (prompt shared)                        | Longest candidate, given capacity  | ${N}$ contexts, ${S} + \sum_n {K}_n$ tokens if shared  | Sampling variation over the same request |
| Feedback | $\sum_{t}({S}^{({t})} + {K}_t)$, with ${S}^{({t})}$ growing | Sum of turns, including each check | One active context of ${S}^{({H})} + {K}_{{H}}$ tokens | Observations from executed checks        |

Table 1: **Resource model of the three allocation axes**: Symbolic accounting of processed tokens, critical path, retained model state, and information source. Concurrency and prefix sharing are capacity and implementation assumptions, not properties of the axis.

^tbl-vol3-allocation-model

Of the three axes, only feedback brings in external information absent from the model weights and prompt. The calculation below evaluates these expressions for the connection-pool repair under a fixed output ceiling of 4,096 tokens, showing how equal output ceilings produce different latencies and token bills.

**Napkin Math 3.2: One decision, three allocations**

**Problem**: A repair request starts with 4,096 input tokens and a common ceiling of 4,096 generated tokens. How do depth, breadth, and feedback spend that allowance?

**Variables**: Reuse the illustrative per-token generation time from the preceding example. Breadth has capacity for 4 concurrent streams at that same rate. Each short candidate uses 1,024 generated tokens. Feedback uses 3 turns, each followed by a 1.5 s check returning 340 tokens. Later feedback requests append earlier candidates and reports. Hypothetical prices are \$3 per million input tokens and \$15 per million output tokens, without cache discounts, so each breadth stream is billed for its own copy of the prompt (unlike the shared-prefix row of [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^tbl-vol3-allocation-model|table 1]]). Generation times omit prefill, queueing, and transport; the feedback time additionally includes its checks. The bill counts model tokens only, and [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^tbl-vol3-allocation-tradeoffs|table 2]] tallies each allocation’s tokens, time, and bill side by side.

| Allocation | Input tokens | Output tokens | Generation and included checks | Model-token bill |
|:-----------|-------------:|--------------:|-------------------------------:|-----------------:|
| Depth      |        4,096 |         4,096 |                        86.32 s |        \$0.07373 |
| Breadth    |       16,384 |         4,096 |                        21.58 s |        \$0.11059 |
| Feedback   |       16,380 |         3,072 |                        69.24 s |        \$0.09522 |

Table 2: **Allocation accounting under a common output ceiling**: Equal ceilings produce unequal spend. Allowances omit prefill, queueing, selection, and tool charges.

^tbl-vol3-allocation-tradeoffs

**Math**: In [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^tbl-vol3-allocation-tradeoffs|table 2]], depth generates all 4,096 tokens along a single path. Breadth generates 1,024 tokens on each of 4 concurrent paths, shortening the critical path by 4×. However, reading the prompt 4 times across unshared streams adds 12,288 input tokens, multiplying its billing cost to 1.5× that of depth. Feedback accumulates input context over ${H}$ turns according to ${H}\,{S_{\text{base}}} + ({K} + \lvert {o}\rvert)\,{H}({H}-1)/2$, reaching 16,380 tokens at ${H} =$ 3 because each successive round re-reads all prior candidates and observation reports.

**Systems insight**: Breadth trades money for lower wall-clock latency, and its entire billing premium comes from the $({N}-1){S}$ re-read prompt tokens. The governing ratio is prompt length relative to generated output: a large repository context makes breadth’s input bill grow steeply with both ${N}$ and ${S}$, whereas a short prompt or a shared prefix cache removes most of that surcharge. Feedback lands between depth and breadth in both latency and billing while remaining the only axis that acquires new runtime observations. Because this accounting leaves out pass rates, it prices the work rather than the quality of the result.

### Internal Budgets and External Orchestration

^sec-vol3-test-time-compute-latent-vs-scaffold

When a model service hides its intermediate reasoning tokens behind an API, a runtime that gauges effort from the length of the visible reply understates both token spend and latency. Production systems therefore separate two control surfaces: internal model deliberation and external workflow orchestration. A model service may expose an internal budget that caps how many intermediate tokens a single call may spend, while the runtime independently controls how many calls to dispatch, which tool checks to run, and what context to pass into subsequent requests. Internal budgets adjust depth inside one call; external orchestration governs breadth across branches, schedules sandboxed checks, and assembles revised prompts. Because the service may redact intermediate tokens from the returned text, the runtime must read explicit token-usage headers and termination status codes rather than character counts to enforce quotas and track spend.

### How Reasoning Models Spend Output Allowances

^sec-vol3-test-time-compute-reasoning-models

That internal budget governs **reasoning models**, which can otherwise burn an entire output allowance on intermediate steps and return an empty or truncated final answer. Trained with reinforcement learning on tasks with objective, verifiable outcomes, such as formal mathematics, logic puzzles, and unit-tested codebases, these models learn to generate extended intermediate scratchpads that propose solutions, check steps, and backtrack within a single call ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-openai2024o1|OpenAI 2024]]; [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-deepseekai2025deepseekr1|DeepSeek-AI et al. 2025]]). At the serving layer, those intermediate reasoning tokens are ordinary autoregressive output tokens that consume accelerator compute, fill the KV cache, and incur full output-token charges. Because that scratchpad draws from the call’s output allowance, services expose a reasoning-budget parameter that turns sequential depth from a fixed model habit into a per-request runtime knob. The orchestrator can set that knob by task, yet internal reasoning still operates strictly over the supplied prompt and static weights. An extended scratchpad can check arithmetic or trace logic across the prompt, but it cannot observe runtime behavior or tell whether a proposed patch fixes a connection leak without running a test suite.

↪ Reinforcement learning on tasks with verifiable outcomes, the training that produces reasoning models, is developed in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17 Reinforcement Learning from Verifiable Rewards#^sec-vol3-rlvr|Reinforcement Learning from Verifiable Rewards]]**.

Because models trained with verifiable rewards spend output allowances differently than instruction-tuned models (models adapted to follow example instructions and responses), token ceilings must be calibrated per model family, and call telemetry guides orchestration policy without guaranteeing that a completed candidate is correct. Treating depth as a per-call knob alongside external breadth and feedback still lets the runtime vary spend across tasks, raising the practical question of which allocation axis pays off at each level of task difficulty.

**Example 3.1: Compute-optimal test-time allocation**

**Scenario**: Snell et al. ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-snell2024scaling|2024]]) evaluated strategies for spending a fixed test-time compute budget across reasoning benchmarks, comparing sequential revision of a single candidate against parallel breadth sampling and search guided by learned process verifiers ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^sec-vol3-test-time-compute-verification|section 3.4]]). The study grouped benchmark problems into difficulty tiers by the base model’s single-shot success rate.

**Diagnosis**: On easier problems, sequential revision used the budget most effectively, fixing minor mistakes without the overhead of parallel sampling. On moderately difficult problems, hybrid strategies combining parallel exploration with verifier-guided search reached higher accuracy. On the hardest problems, scaling test-time compute hit diminishing returns across all axes. At matched total FLOPs, a well-chosen test-time allocation let a smaller model beat a model 14 times larger whenever the smaller model had a nonzero base success rate. When base success sat near zero, spending FLOPs on a larger base model beat exhausting tokens on parallel rollouts.

**Systems lesson**: With the supplied prompt held fixed, extra reasoning and sampling can surface capabilities the model already has, but they cannot supply missing runtime facts. Feedback can bring new observations into the next call, though their value still depends on the check’s coverage and the model’s ability to use them. Runtimes should route budgets by estimated difficulty: spend a small budget or a single call on straightforward tasks, use parallel search and feedback on moderately hard tasks, and escalate near-zero-yield requests to a stronger model or a human operator instead of burning tokens on unguided sampling.

^exmp-03-compute-optimal-allocation

Because a runtime does not know a task’s true difficulty in advance, it estimates difficulty with cheap, fast signals before committing a large deliberation budget. Common signals include agreement among two or three short pilot samples, fast static linters, and historical failure rates on similar requests. When pilot samples agree and pass static checks, the runtime keeps the budget small and finishes in one call. When pilot samples disagree or linters flag errors, the scheduler escalates to broader sampling or an edit–test–revise loop, and if the budget ceiling is reached without a verified candidate, it stops and escalates to a human operator. Each routing signal acts as a classifier whose precision and recall should be measured on held-out tasks.

In practice, internal depth and external breadth work together. Each rollout may use enough depth to draft a coherent code patch while the runtime samples several such patches in parallel and filters them through a test harness. Even so, the mix has to fit the system’s bottlenecks: slow tests stretch the feedback critical path, and weak tests dull the value of each observation. Those same checks also matter during training, because reinforcement learning with verifiable rewards uses them as a training reward. Any blind spot or false pass that causes a bad selection at test time therefore becomes a loophole that training actively optimizes for on every weight update.

↪ How an acceptance check becomes a training reward, and how its gaps are exploited during training, is developed in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/17 Reinforcement Learning from Verifiable Rewards/V3-17.04 Verifiable Rewards#^sec-vol3-rlvr-rewards|Verifiable Rewards]]**.

**Checkpoint 3.1: Choosing an allocation**

**Information**: For the connection-pool repair, which axis can separate a short timeout from a missed notification, and why can the other two not?

**Concurrency**: If the service admits only one candidate at a time, how long does the notebook’s breadth allocation take to generate, and which allocation then has the shortest path?

**Breadth premium**: How many extra input tokens does 4-way breadth read compared with depth for a 4,096-token prompt, and what happens to that premium when the repository context grows eightfold?

**Evidence**: If a revised patch passes a targeted test, what additional information determines whether the task may stop?

Choosing how to spend compute across depth, breadth, and feedback determines what candidates enter the pool, but generating a good candidate does not help if the selector picks a plausible broken one instead. The next step is choosing among candidates without spending more on selection than the pool is worth.
