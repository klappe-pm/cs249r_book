# V3-03.02 Limits of a Single Response

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03 Test-Time Compute|V3-03 Test-Time Compute]]

^sec-vol3-test-time-compute-insufficient-response

The repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) inspects the connection-pool implementation and receives a completed candidate patch. The invocation contract admits it as a candidate, yet the patch rests on an incomplete diagnosis. Client requests intermittently stall even after idle connections become available. Two distinct failure modes can produce this symptom: an aggressive timeout that aborts too early, or a lost notification when a worker thread returns a connection to the pool. When prompted, the language model proposes extending the timeout. That change offers a plausible workaround, but it provides no evidence that the timeout caused the stalls. Deploying such a patch immediately risks masking the latency tail while leaving the concurrency defect intact.

![[90 Assets/Volume III/03 Test Time Compute/Hsa Locator H 8f8aca5627.svg]]

*H·S·A locator with the Horizon axis highlighted.*

*Deliberation extends the horizon with extra model turns and checks inside one decision, and hard ceilings bound that spend.*

Before committing to an edit, the agent runtime can spend extra work in three distinct ways. It can give the model a longer output allowance to trace how threads acquire and release the lock step by step. It can sample several candidate patches that modify different parts of the pooling logic. It can also run a targeted test harness to record whether a waiting thread actually receives the condition-variable notification. Each option buys a different kind of evidence. Extended reasoning can expose logical flaws in the source text. Sampling across temperature or prompt variations can surface fixes that a greedy single pass misses. An instrumented test, by contrast, observes runtime state directly and reveals dynamic thread interactions that token generation alone cannot establish.

This division marks the boundary between model computation and runtime observation. Extra model computation re-evaluates information already present in the prompt. Within a single generation, a model can backtrack and revise an earlier analytical misstep even as the previous tokens remain frozen in its prefix. Pure computation, however, cannot create new empirical facts. Only an executed test reports how the running process behaves, and its conclusions hold only for the conditions and thread schedules that the test harness exercised.

Suppose the targeted test forces an interleaving where one worker thread waits while another returns a connection. The trace shows that the connection enters the pool, yet the waiting worker stays blocked past the notification point. That observation rules out the timeout hypothesis immediately and points the agent toward the signaling path. The agent can then write a patch that repairs the notification logic and test it against the failing reproducer. Passing a targeted reproducer still does not establish full task acceptance, because narrow tests can miss edge cases, and neither an unchecked hypothesis nor an isolated micro-test is enough to ship code to production. Even so, the two paths part ways before any file changes ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.02 Limits of a Single Response#^fig-vol3-diagnostic-tree|figure 1]]). Acting on the first guess hides the symptom and keeps the defect, whereas checking first spends one short test to learn which hypothesis survives.

![[90 Assets/Volume III/03 Test Time Compute/Diagnostic Tree 3040ee564d.svg]]

Figure 1: **Committing to a Hypothesis vs. Checking It**: Both paths start from the same connection-pool failure. On the left, generation builds on the timeout explanation without any observation that separates it from a missed notification, so the patch can hide the symptom while the defect remains. On the right, a targeted test orders a waiting worker and a returning connection, and its observation contradicts the timeout explanation before any edit. The revised candidate passes the reproducer, which still falls short of task acceptance.

^fig-vol3-diagnostic-tree

**Napkin Math 3.1: A probe vs. a longer answer**

**Problem**: A prepared diagnostic test takes 40 ms. A proposed explanation contains 1,024 output tokens. How long does the explanation take to generate relative to the test?

**Variables**: The illustrative per-token generation time from **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-per-call-work-estimate|Estimating per-call hardware work]]** is 21.07 ms, derived from memory-bandwidth limits rather than a measured production service rate. The hypothetical output pricing is \$15 per million tokens. Prompt processing, queueing, transport, test preparation, and the downstream model call that reads the test observation are excluded.

**Math**: Generating 1,024 tokens at 21.07 ms per token requires 21.58 s and incurs \$0.01536 in token charges. Dividing this generation latency by the 40 ms test run yields a factor of 539.5×.

**Systems insight**: When the unresolved question concerns dynamic program behavior, the probe settles it 539.5× faster than the model can generate a speculative explanation of it, and only the probe’s answer is an observation. Running a test is preferable whenever its preparation and execution time remain below the explanation’s 21.58 s and its outcome cleanly separates the competing failure modes. Conversely, an inconclusive test that does not separate the hypotheses provides no diagnostic gain regardless of its speed. Failure to reproduce can still supply negative evidence when the test’s sensitivity to the suspected fault is known. A sound runtime spends work on whichever operation most cheaply removes the main source of uncertainty.

The probe, and the decision to revise the patch on its evidence, both happened outside any single model call. The invocation contract of the previous chapter ends at one prompt and one candidate, accompanied only by metadata indicating whether generation reached a stop token or an output limit. That interface cannot decide whether the next second of latency or fraction of a cent is better spent on longer reasoning, extra candidate samples, or a runtime probe. An API response marked complete confirms only that generation finished, not that the proposed patch fixes the bug. **Test-time compute** is all the system work the runtime orchestrates around the model call, with model weights held fixed, to generate, test, and select candidates before committing to an action. Governing that spend requires a runtime policy that sets hard ceilings on latency and cost, routes work across reasoning and checks, and stops cleanly without mistaking an exhausted budget for a verified solution.

↩︎ The bounded single-invocation model contract is established in **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-contract|The Invocation Contract]]**.

Each part of that policy raises the next question. The runtime first chooses how to spend extra work across reasoning depth, candidate breadth, and empirical feedback ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^sec-vol3-test-time-compute-computation-allocation|section 3.2]]). Breadth produces a pool, so the runtime must then pick from it without being fooled by a plausible failure ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.04 Selecting from a Candidate Pool#^sec-vol3-test-time-compute-candidate-diversity|section 3.3]]), and picking well depends on how far a passing check can be trusted ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^sec-vol3-test-time-compute-verification|section 3.4]]). When a check refutes a premise partway through a plan, the runtime should regenerate only what depended on it ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.06 Revising Candidate Plans#^sec-vol3-test-time-compute-planning-revision|section 3.5]]). Candidates and revisions together form a search whose spending must be tracked, reserved, and stopped ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.07 Bounded Search#^sec-vol3-test-time-compute-bounded-search|section 3.6]]), and the complete policy is finally judged against its alternatives under one budget and one deadline ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.08 Evaluating Deliberation Policies#^sec-vol3-test-time-compute-strategy-design|section 3.7]]).
