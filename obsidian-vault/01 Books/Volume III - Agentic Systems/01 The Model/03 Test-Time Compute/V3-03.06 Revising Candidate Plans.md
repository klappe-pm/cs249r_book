# V3-03.06 Revising Candidate Plans

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03 Test-Time Compute|V3-03 Test-Time Compute]]

^sec-vol3-test-time-compute-planning-revision

When a targeted test refutes the initial diagnosis inside a multi-part repair plan, throwing away the entire plan wastes valid work such as API compatibility checks, whereas keeping the plan unchanged leaves the patch and test selection resting on a disproven premise. Suppose the repair agent forms a diagnosis, drafts a patch, checks public API constraints, and picks a test plan for a connection-pool leak, and a targeted test then refutes the diagnosis. To avoid both waste and stale conclusions, the runtime needs to identify which parts of the candidate depend on the refuted premise before deciding what the next model call should regenerate.

A **revisable candidate plan** records those dependencies explicitly. Instead of logging past actions, it tracks unexecuted candidate artifacts together with the evidence or upstream artifacts each one relies on. When new evidence refutes a premise, the runtime invalidates and regenerates only the affected subgraph while keeping supported artifacts intact, and the replacement artifacts then go through their own checks. This design comes directly from truth maintenance systems, which record explicit justifications for each conclusion so that retracting a premise automatically invalidates every step built on it ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-doyle1979truth|Doyle 1979]]).

### Tracking Dependencies Inside a Candidate

^sec-vol3-test-time-compute-plan-graph

Suppose the first repair candidate blames the connection-pool failure on an overly short client timeout. To know which parts of that candidate survive when a test refutes the timeout hypothesis, the runtime represents the candidate as a directed acyclic graph with a directed edge from each prerequisite to the artifact that depends on it ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.06 Revising Candidate Plans#^tbl-vol3-candidate-plan-dependencies|table 5]]). Here the source excerpt, initial failure log, API declaration, and test inventory are supplied inputs, whereas the diagnosis, patch candidate, check selection, and API compatibility notes are generated artifacts. The graph records which components depend on which, whether or not the model generated them in that order.

| Artifact                | Direct prerequisites                        | What the artifact contributes                                     |
|:------------------------|:--------------------------------------------|:------------------------------------------------------------------|
| Source excerpt          | Repository revision and file identity       | The implementation being considered                               |
| Diagnosis               | Source excerpt and failure observation      | A proposed explanation of the failure                             |
| Patch candidate         | Source excerpt and diagnosis                | A proposed change to that implementation                          |
| Test inventory          | Repository revision (a supplied input)      | The tests available for selection                                 |
| Check selection         | Patch candidate and test inventory          | Checks intended to distinguish this repair from an inadequate one |
| API compatibility notes | Task constraints and public API declaration | Restrictions that every acceptable repair must preserve           |

Table 5: **Dependencies within a repair candidate**: Each row names the inputs needed to interpret its artifact. A separate compatibility branch can be retained only while its own inputs remain applicable.

^tbl-vol3-candidate-plan-dependencies

Now suppose the waiter-and-return test shows that an idle connection entered the pool while a waiting worker stayed blocked past the notification point. That observation refutes the timeout diagnosis and points to a missed wake-up notification instead. Because both the timeout patch and its check selection depend on the refuted diagnosis, the runtime marks them invalid and schedules them for replacement. The source excerpt stays valid because the repository file has not changed, and the API compatibility notes stay valid because the public interface constraints have not changed. The runtime builds the next prompt from the still-valid inputs plus the new test observation, asks for a new diagnosis, patch, and check selection, and runs checks on the new artifacts.

That selective reuse is only as sound as the recorded edges. A graph with a missing edge keeps stale conclusions just as an unmanaged prompt buffer does: if the compatibility notes silently depended on helper signatures that the new patch changes, leaving out that edge keeps broken compatibility claims in place. Dependency tracking pays off when maintaining the graph and walking its edges costs less in time and tokens than regenerating the unaffected branches from scratch.

### Invalidating Stale and Refuted Evidence

^sec-vol3-test-time-compute-precondition-invalidation

Walking the dependency graph requires distinguishing an actively refuted claim from an observation whose preconditions no longer match the current candidate. A failing test directly refutes the claim that a patch fixes the bug, whereas a passing test from an earlier candidate remains a true record of what that earlier patch did while saying nothing about the edited patch now on the table. Reusing the earlier pass after the code changes would let an unverified edit slip through on stale evidence, whereas treating an expired observation as a direct contradiction would falsely rule out a working hypothesis.

To keep reuse sound, every recorded observation must carry its full provenance: the exact source revision or patch digest, test suite version, compiler flags, and runtime environment. Likewise, an observation from reading a file must bind to the cryptographic hash of the file contents when read, not to a file path whose contents a later step might overwrite.

When an input changes or a premise fails, the runtime marks that node unsupported and walks the directed edges to find every downstream artifact that needs review. If node ${v}$ loses support, the invalidated set is its reachable descendants in the graph: $\text{Desc}({v}) = \{{u} \mid {v} \rightsquigarrow {u}\}$, where ${v} \rightsquigarrow {u}$ means a directed path runs from ${v}$ to ${u}$. Breadth-first search finds $\text{Desc}({v})$ in time linear in the vertices and edges.[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.14 Footnotes#^fn5|⁵]] Every node outside $\text{Desc}({v})$ keeps its support, including separate subgraphs such as the API compatibility notes. Walking a candidate graph of dozens or hundreds of nodes, like the one in [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.06 Revising Candidate Plans#^tbl-vol3-candidate-plan-dependencies|table 5]], takes a negligible fraction of the illustrative 21.07 ms needed to decode a single token. The real engineering work is therefore recording the dependency edges accurately rather than traversing them. In the connection-pool repair, the waiter-and-return test contradicts the timeout diagnosis, and graph traversal marks its descendants (the patch and check selection) for review. The next call regenerates only the diagnosis and that branch from the retained inputs ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.06 Revising Candidate Plans#^fig-vol3-plan-revision|figure 5]]).

![[90 Assets/Volume III/03 Test Time Compute/Fig Vol3 Plan Revision ec9456866a.svg]]

Figure 5: **Invalidation and Scoped Regeneration**: In (A), the waiter-and-return test contradicts the timeout diagnosis. Following the recorded dependency edges marks the patch and check selection for review, while the recorded inputs and the separately derived API notes keep their support. In (B), a new request supplies that supported frontier and regenerates only the diagnosis, patch, and check selection. The graph records candidate artifacts, not executed operations, and each replacement must still pass its own checks. The test inventory that also feeds check selection is omitted.

^fig-vol3-plan-revision

Content hashes and environment digests make invalidation deterministic only when the recorded boundary captures every input that matters. An integration test that calls a live network service can change its outcome even when local files stay bit-identical, whereas editing an unrelated README file should not invalidate unit-test results whose code and inputs did not change. Sound reuse therefore depends on checking the full execution context (sandbox isolation, mocks, and declared inputs) rather than file timestamps or paths alone.

Candidate plans must also be kept separate from live environment state. The dependency graph tracks uncommitted candidate artifacts and their justifications; reading files, writing to disk, or running binaries in a sandbox changes real system state. Dropping an invalidated node from the plan graph does not roll back a modified file or free a running container, so the runtime must handle rollback and cleanup through separate recovery routines.

↪ Compensation and cleanup of external effects that outlive an abandoned candidate branch are developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.04 The Trajectory Saga Pattern#^sec-vol3-failure-recovery-branch-compensation|Branch-scoped compensation]]**.

### Choosing How Much of a Plan to Regenerate

^sec-vol3-test-time-compute-revision-mechanics

Once graph traversal marks the invalidated nodes, the runtime must decide whether to replace a single node, rebuild its entire downstream subgraph, or stop deliberating altogether. Replacing a single step in isolation fails when the new artifact changes an interface that downstream steps rely on, whereas regenerating the whole plan from scratch wastes tokens and risks breaking parts that already worked. To scope a revision cleanly, the runtime builds a prompt with the task constraints, the still-valid upstream frontier, the observation that refuted the old step, and the exact nodes marked for replacement. In the connection-pool repair, the prompt asks for a new diagnosis, patch, and check selection while keeping the unchanged source excerpt and API notes. When the model returns replacement artifacts, the runtime checks both that they fit the retained artifacts and that their own prerequisites are met, because a locally valid replacement can still clash with preserved downstream nodes.

Depending on how much support the new observation removes, the runtime chooses among three responses. [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.06 Revising Candidate Plans#^fig-vol3-hierarchical-revision|Figure 6]] orders these three responses around two questions, whether the dependents of the affected artifact still have their needs met and whether the task’s own premises still hold:

1.  A **local repair** replaces a single node while keeping its interface and contracts unchanged so that its dependents stay valid, such as fixing a malformed shell flag in a test command without changing what the test checks.
2.  A **subgraph resynthesis** replaces a node and all of its descendants, feeding the model the intact upstream frontier and asking it to rebuild the path to the goal. In the connection-pool repair, this replaces the diagnosis, patch, and test selection while keeping the source excerpt and API compatibility notes.
3.  **Stopping deliberation** applies when new evidence refutes a premise of the task itself, such as a missing host library or credentials without write access. No plan revision can fix a broken task premise, so the runtime stops deliberating and escalates or reports the task unresolved instead of spending more tokens.

![[90 Assets/Volume III/03 Test Time Compute/Hierarchical Revision Mechanics c8772d1459.svg]]

Figure 6: **Choosing the Revision Scope**: Two questions about the new evidence select among three responses. If the artifact’s dependents still have what they need, a local repair replaces it alone. If they do not but the task’s premises hold, subgraph resynthesis replaces the artifact and its descendants. If a premise has failed, deliberation stops and the task is reported unresolved or escalated. The tiers classify responses by how much support the evidence removes rather than establishing an unconditional preference for minimal edits.

^fig-vol3-hierarchical-revision

Smallest is not always best. When new evidence overturns an early framing assumption or the dependency graph has grown tangled, regenerating the whole candidate from scratch often produces a cleaner, more consistent result than patching a large subgraph, at the cost of re-emitting settled material and risking regressions in parts that already worked. Choosing between scoped revision and full regeneration weighs the share of the graph that was invalidated against the tokens, time, and checks needed to rebuild and verify the candidate.

**Napkin Math 3.5: Output cost of a local plan revision**

**Problem**: Suppose a candidate contains 12 nodes, each requiring 150 generated tokens. New evidence leaves 3 nodes needing replacement. How much output does scoped regeneration avoid if either approach produces a candidate adequate for the same subsequent checks?

**Math**: Multiplying the complete node count by the output per node gives 1,800 tokens for full regeneration. Multiplying the replacement count by the same output allowance gives 450 tokens for scoped regeneration. The scoped request generates 25 percent of the full request’s output, avoiding 75 percent of that output under the equal-node-size assumption.

**Systems insight**: Scoped regeneration saves the exact fraction of the plan that keeps its support. That saving shrinks linearly as the refuted premise reaches more descendants and disappears when every node depends on it, so once most of the plan rests on the rejected premise, full regeneration costs little more and is simpler to check. This count covers generated plan tokens only; both options still pay for prompt input, integration, and verification checks.

These output savings have to be weighed against the work of maintaining dependencies, building scoped prompts, and checking hybrid plans. Once a candidate plan passes verification and crosses into execution, it stops being an uncommitted candidate graph and becomes live workflow state that the harness executes and durable execution checkpoints across machine failures.

↪ Persisting committed plan state across worker and infrastructure faults is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/11 Durable Execution/V3-11 Durable Execution#^sec-vol3-durable-execution|Durable Execution]]**.

### Preventing Revision Thrashing

^sec-vol3-test-time-compute-replanning-thrashing

Even when each scoped revision saves tokens compared with full regeneration, a revision loop without stopping rules can still oscillate between two diagnoses, produce cosmetically different patches with the same bug, or regenerate plans in response to harmless compiler warnings. The runtime therefore checks whether a proposed revision responds to new evidence that actually refutes a premise, rather than treating every warning or score fluctuation as a reason to replan.

To prevent thrashing, the runtime enforces hard ceilings on model calls, total tokens, check runs, and wall-clock time. Every revision attempt, including a failed local repair, draws from that allowance, and the same ceilings bound the search as a whole ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.07 Bounded Search#^sec-vol3-test-time-compute-early-exit|section 3.6.6]]). When the budget runs out, the loop stops and reports the task unresolved or escalates to a human operator without merging the unverified patch. Seeing the same or structurally equivalent candidate under unchanged observations also triggers an immediate stop; revisiting an earlier idea is justified only when a new test observation has changed the evidence.

Dependency graphs let the runtime revise a single candidate without throwing away its valid parts, but an agent often holds several partial candidates at once. Deciding which partial candidate to extend next, how to keep concurrent branches from corrupting one another’s workspaces, and when to stop searching altogether turns revision into bounded search.
