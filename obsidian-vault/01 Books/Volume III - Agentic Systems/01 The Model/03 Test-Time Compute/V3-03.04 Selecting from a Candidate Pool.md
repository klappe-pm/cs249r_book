# V3-03.04 Selecting from a Candidate Pool

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03 Test-Time Compute|V3-03 Test-Time Compute]]

^sec-vol3-test-time-compute-candidate-diversity

Sampling eight candidate patches for the connection pool helps nothing if seven of them repeat the same broken timeout workaround and the selector picks one of the seven over the single patch that fixes the notification bug. In a typical pool, one candidate might lengthen an acquisition timeout, another might add exponential retries, and a third might change how the connection-return path wakes waiting threads. The runtime has to decide which proposal, if any, has enough supporting evidence to return, and gathering that evidence consumes time and tokens from the same deliberation budget that produced the pool.

Two questions separate generation from selection: whether the pool holds at least one candidate that solves the task, and whether the selector can pick that candidate without accepting a broken one. A generator can flood the pool with proposals without making selection any easier; conversely, a sharper selector can raise end-to-end reliability without sampling a single extra candidate.

### Useful Variation Among Candidates

^sec-vol3-test-time-compute-candidate-variation

Renaming local variables, reformatting comments, or rewriting a loop can produce eight distinct token sequences that all leave the synchronization bug untouched. Surface variation in token sequences does not guarantee diverse repair hypotheses. In the connection-pool repair, candidates add value only when they test different explanations that downstream checks can tell apart. Changing the thread-notification path vs. lengthening the timeout tests two distinct hypotheses. Generating half a dozen slightly reworded versions of the same timeout bump only wastes verification runs.

This problem is separate from statistical dependence. When the task, prompt, base model, and sampling controls stay fixed, separate draws with independent random seeds are genuinely independent and identically distributed (IID). Even so, if the model puts almost all of its probability mass on timeout edits, independent draws will still fill the pool with variations on that one mistake.

Across a mixed production workload, shared model blind spots matter even more. A model often solves familiar patterns reliably while failing every time on an unfamiliar edge case, so repeated samples on a hard task fail together far more often than the average pass rate across all tasks would suggest. While samples on a single fixed task may be conditionally independent, treating attempts across a mixed workload as draws with one shared pass probability hides that clustering. Feedback-driven revision changes the distribution again: once the runtime feeds test errors into later prompts, each new candidate depends directly on what earlier checks found.

A runtime can encourage broader exploration by raising sampling temperature or prompting the model to try distinct diagnostic angles under the same task constraints. Pushing diversity too hard, however, often produces syntax errors, broken invariants, or nonsensical edits. A diversification method earns its keep only if it raises the task pass rate within a fixed compute and latency budget.

To avoid wasting test runs on near-duplicates, the runtime can prune redundant candidates early by deduplicating on structure and behavior. Abstract syntax tree (AST) normalization strips away surface changes such as variable names and whitespace, and behavioral clustering runs candidates on cheap inputs to group those with identical outputs. Using both steps let a competitive code-generation system narrow tens of thousands of raw model samples down to a handful of distinct submissions ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-li2022alphacode|Li et al. 2022]]). Each method groups candidates by a bounded equivalence relation, whether normalized syntax or matching outputs on a probe set, and deduplication is sound whenever that relation preserves the property the downstream check tests.

### Choosing a Selection Rule

^sec-vol3-test-time-compute-selection-policies

Picking the most common patch by majority vote fails whenever the model’s favored mistake outnumbers the one candidate that fixes the bug, whereas running the full test suite on every raw sample wastes sandbox time on patches that do not even parse. Runtimes therefore combine three kinds of selection signal, ordered by cost and by the strength of the claim each supports: direct execution checks, answer agreement (consensus voting), and learned ranking.

Direct checks, such as a parser, a type checker, or a test harness, test a candidate deterministically against explicit rules. Each establishes only the property it checks, as the scoped check pipeline of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^sec-vol3-foundation-model-scoped-check-pipeline|Staging checks by cost and scope]]** showed, so clean compilation says nothing about whether a race condition is gone. Running candidate code is also an external action that requires sandbox isolation, hard timeouts, and tight permission boundaries.

Answer agreement combines independent reasoning paths by vote. In **self-consistency**, the runtime samples several reasoning chains, normalizes their final answers, and takes the plurality vote ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-wang2022self|Wang et al. 2023]]). That works well for arithmetic, symbolic logic, or short factual answers, but majority vote still reflects only what the generator produces most often. When a model shares a systematic bias or takes a flawed shortcut, independent samples regularly converge on the same wrong answer. For code repair, voting over raw patches is a poor selector: behavioral agreement inherits the coverage limits of the probe inputs, and a minority patch that actually passes the reproducer should beat a popular patch that fails it.

When deterministic checks cannot cover every requirement, learned rankers and model-based judges supply a heuristic ordering. A learned reward model or a secondary large language model (LLM) judge (a model prompted to grade another model’s output) can score explanation clarity, check style guidelines, or rank patches before the runtime spends time on heavy integration tests. Even so, ranking and acceptance answer different questions. Ranking orders candidates from best to worst under a score; acceptance decides whether a candidate meets the task contract. If every candidate in the pool is broken, picking the highest-ranked candidate returns the best-looking failure. Returning a candidate instead of abstaining requires a verifier that produces an objective pass or fail result.

**Definition 3.2: Verifier-guided selection**

***Verifier-guided selection*** is a selection policy that returns a candidate only when a **verifier**, a check whose criteria and observations the candidate cannot modify, passes it, and abstains when no candidate passes.

1.  **Significance**: Its success rate is capped by pass@${k}$, the chance the pool holds a passing candidate ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.04 Selecting from a Candidate Pool#^sec-vol3-test-time-compute-pass-at-k|section 3.3.3]]), while the share of its selections that are correct depends on both the verifier’s passing-set precision and the selection policy ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^sec-vol3-test-time-compute-check-precision|section 3.4.2]]). The fixed IID first-passing policy developed there preserves passing-set precision; ranking among passing candidates need not. Selection coverage and selected correctness together determine the probability of returning a valid result.
2.  **Distinction**: Voting selects what the generator produces most often and learned ranking selects what a scorer prefers; only a verifier’s verdict can justify returning a candidate instead of abstaining.
3.  **Common pitfall**: Treating the verifier’s pass as task acceptance; the verdict covers the checked property, and its false acceptance rate grows in importance as the pool’s valid-candidate rate falls.

A production runtime stages these checks cheapest first, following the cost-ordered cascade of **[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^tbl-verification-layers|Scoped candidate checks]]**, so that parsing and AST checks drop malformed candidates before they reach sandboxed tests or an LLM judge. Inside a search, the stage order should come from measured run time and rejection rate rather than guesswork. Running a compiled binary in a warm container might take 5 ms, whereas calling a large LLM judge to grade code quality is a full model call that can take 800 ms and eat into the token budget. Comparing several candidates in a single prompt also scales differently with context length than scoring each candidate on its own. Because checking competes directly with generation for time and tokens, selection has to be budgeted as part of test-time compute.

### Candidate Availability Under Pass@${k}$

^sec-vol3-test-time-compute-pass-at-k

When a runtime fails to return a working patch from a pool of ${k}$ samples, the engineer needs to know whether the generator never produced a passing patch or the selector threw a passing patch away. **pass@${k}$** separates those two failures by measuring the probability that at least one of ${k}$ sampled candidates passes the specified tests ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-chen2021evaluating|Chen et al. 2021]]).[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.14 Footnotes#^fn1|¹]]

For a fixed task and fixed generation policy, suppose independent samples each pass the tests with probability ${p}$. The probability that all ${k}$ samples fail is $(1-{p})^{k}$, so

$$
\operatorname{pass@}{k} = 1-(1-{p})^{k}.
$$

This expression is conditional on that task and sampling policy. To summarize a workload with different task-level pass probabilities, average the task-level quantities; substituting the workload’s average ${p}$ generally gives a different result. For an adaptive policy that revises its prompt after feedback, evaluate the policy’s resulting pools rather than assuming they follow this fixed-distribution formula.

In a benchmark, generate ${n} \ge {k}$ candidates for a task and let ${c}$ pass the fixed test criterion. Of the $\binom{{n}}{{k}}$ subsets of size ${k}$, exactly $\binom{{n}-{c}}{{k}}$ contain only failures. The subset estimator is therefore

$$
{\widehat{\operatorname{pass@}k}} = 1-\frac{\binom{{n}-{c}}{{k}}}{\binom{{n}}{{k}}},
$$

with the numerator taken as zero when ${n}-{c}<{k}$. Under independent, identically distributed sampling for the fixed task, this estimates the probability that a fresh pool of ${k}$ candidates contains a test-passing member without bias; **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-pass-at-k|Pass@k and repeated-run consistency]]** derives this expectation and details evaluation without factorials. Benchmark results average these estimates over tasks ([[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.13 Source References#^ref-chen2021evaluating|Chen et al. 2021]]).

The relationship to deployed selection follows from the event being measured. If the selector must return an unchanged member of the same pool, it cannot return a test-passing candidate when the pool contains none. Its probability of returning a test-passing candidate is therefore at most pass@${k}$, counting abstention as no returned pass. A selector that always finds a passing member whenever one exists reaches this ceiling; whether the deployed selector does, within the deployment’s checking budget, is a separate measurement.

The predicate in pass@${k}$ is passing these tests, which is narrower than satisfying the complete task requirements. The ceiling also covers only selectors that return an unchanged pool member rather than repairing candidates or synthesizing a new artifact. Benchmarks therefore report candidate availability alongside selected-output performance under the relevant criterion, because the gap between the two can be large. At 10,000 samples, the smaller model’s pools hold a correct answer for 98 percent of the problems, yet majority voting returns one for 43 percent, and 59 percent for the larger model. Beyond 256 samples the vote gains less than a point while coverage gains another 10. The repair agent’s coverage rises from 16 percent with one sample to 56 percent at 250, but that growth is usable only because tests can identify which candidate passes. Spending on breadth is therefore justified by the selector, not by the pool. Without a check that recognizes the correct candidate, the added samples raise the pass@${k}$ ceiling without raising what the runtime returns.

Breadth has a price that pass@${k}$ makes easy to compute. In **best-of-${N}$ sampling**, the runtime generates ${N}$ candidates for one decision and returns one that its selector admits. The pool is the same object pass@${k}$ describes, so its availability is pass@${k}$ with ${k} = {N}$, written pass@${N}$ from here on. The notebook below prices that pool against the simplest alternative, generating one candidate at a time and stopping at the first pass, under the most favorable selection assumption, in which the verifier is the acceptance check itself.

**Napkin Math 3.3: The price of a larger pool**

**Problem**: Each candidate repair passes the task’s verifier with probability ${p}$, independently for this task, and the verifier is the acceptance check. How many candidates per accepted repair does a parallel pool of ${N}$ spend, compared with sequential retry that stops at the first pass and gives up after ${N}$ attempts?

**Variables**: ${p}$ = 30 percent (hypothetical); pools of 1, 2, 4, and 8 candidates; a selector that returns a passing member whenever one exists.

**Math**: The formula pass@${N} = 1-(1-{p})^{N}$ gives 30, 51, 76, and 94.2 percent for those pools. The last of 8 candidates adds ${p}(1-{p})^{{N}-1}$, only 2.5 percentage points. The parallel pool always spends 8 candidates, or 8.5 per accepted repair. Sequential retry fails only when all 8 attempts fail, so it reaches the same 94.2 percent. Because each subsequent attempt runs only when all earlier attempts failed (with probabilities $1, 1-{p}, \dots, (1-{p})^{{N}-1}$), its expected spend is the finite geometric sum $[1-(1-{p})^{N}]/{p}$ = 3.14 candidates. Dividing that expected spend by the pass probability $1-(1-{p})^{N}$ cancels the numerator and leaves $1/{p}$ = 3.3 candidates per accepted repair.

**Systems insight**: At equal success, the parallel pool costs 2.5× as much per accepted repair; what it buys is one round instead of an expected 3.14 sequential generate-and-check rounds. Breadth buys latency, not cost. In ${C_{\text{eff}}} = \mathbb{E}[{C_{\text{attempt}}}]/{p_{\text{acc}}}$ it raises ${p_{\text{acc}}}$ per round but raises the attempt cost faster. Size ${N}$ as the smallest pool whose pass@${N}$ meets the target within the rounds the deadline allows, and stop growing it once the next candidate’s gain is worth less than its cost.

### Balancing Pool Size Against Checking Cost

^sec-vol3-test-time-compute-selection-costs

Growing the candidate pool raises the chance that a valid repair enters the pool, but it also multiplies the checking load. Under a fixed deliberation budget, spending nearly everything on generation starves verification and forces the selector onto cheap, shallow heuristics. A smaller pool paired with a thorough check often beats a large pool paired with a weak selector; only when candidate generation itself is the bottleneck does a wider pool pay off right away. Comparing the two regimes therefore requires pricing generation and selection together rather than tuning either stage on its own.

Checker errors also compound as the pool grows, because each extra invalid candidate gives an imperfect verifier another chance to register a false pass. If a verifier has a 5 percent false acceptance rate (it passes 5 percent of invalid candidates, defined formally in [[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.05 Verifying Candidates#^sec-vol3-test-time-compute-check-precision|section 3.4.2]]), testing twenty invalid candidates with independent check outcomes makes at least one false pass more likely than not ($1 - (1 - 0.05)^{20} \approx 64\%$). Whether the selector actually returns that false pass depends on what else sits in the pool and on the tie-breaking rule, a distinction the next section makes exact. The defect rate of the returned candidate depends on the generator’s base rate of valid candidates, the check’s false-acceptance and false-rejection rates, and how the selector chooses among passing candidates. When an adaptive search steers generation using verifier scores, it shifts all three quantities at once and can push candidates straight into the verifier’s blind spots.

Selection rules and pass@${N}$ price the candidate pool under a stated check, but they treat the check itself as a black box. In practice, checks differ in whether they inspect finished artifacts or intermediate steps, how the generator’s base rate bounds the precision of a passing verdict, and how quickly search pressure exploits their blind spots. Designing a selector that deserves trust therefore requires looking inside the verification checks themselves.
