# V3-02.05 Autoregressive Generation

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-autoregressive

Even when a request fixes the conversation history and the list of available tool schemas, the model’s reply remains open-ended and stochastic. On the same repair prompt, one call might propose `read_file` on a configuration path, a second might inspect a different directory, and a third might return prose instead of a tool call. Understanding how the serving engine generates tokens one step at a time explains how to set token budgets and sampling parameters, why repeating a live API call can produce a different trajectory, and why only replaying a recorded response reproduces downstream execution exactly.

### Token-By-Token Generation

^sec-vol3-foundation-model-conditional-token-selection

When a model emits a file path inside a `read_file` argument, it chooses each token from learned statistical patterns without checking the filesystem, and that early choice conditions every closing delimiter and reasoning token that follows. Autoregressive language models generate text by factoring the joint probability of a sequence into a product of conditional next-token distributions ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-bengio2003neural|Bengio et al. 2003]]). Let ${x_{1:S}}$ denote the input tokens and ${y_{1:K}}$ an output sequence. Its conditional probability factors as

$$
\Pr({y_{1:K}} \mid {x_{1:S}}) = \prod_{t=1}^{{K}} \Pr({y}_t \mid {x_{1:S}}, {y_{<t}}) \tag{2}
$$

^eq-autoregressive-factorization

At output position ${t}$, the model with parameters ${\theta}$ produces one score, or **logit**, for each token in vocabulary ${\mathcal{V}}$:

$$
{\mathbf{z}}_t = {\mathbf{f}_\theta}({x_{1:S}}, {y_{<t}}) \in \mathbb{R}^{|{\mathcal{V}}|}
$$

A decoding rule selects a token from these scores and appends it to the prefix for position ${t}+1$, so early token choices cascade through the rest of the sequence. In an inference serving engine, the decode loop reads the prompt, computes next-token logits, picks an output token, appends it to the prefix, and repeats until a stop condition fires. Generation ends normally when the model emits an end-of-sequence token or matches a caller-supplied stop sequence. It can also stop early at the output token ceiling, or abort on a timeout or network drop. Serving interfaces must report which stop condition fired: an incomplete JSON object cut off at the token limit needs different handling than a finished tool call, and even a clean stop sequence says only that generation ended, not that the task succeeded.

Production Transformer implementations ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-vaswani2017|Vaswani et al. 2017]]) avoid recomputing earlier tokens at every decode step by keeping a *key-value (KV) cache*:[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn3|³]] memory buffers holding the attention keys and values already computed for earlier positions. For a given full-attention architecture and precision, keeping more tokens in flight takes more cache memory. That cache is transient serving state, not an audit log of which tools ran or what they changed. **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05 KV Cache Management#^sec-vol3-kv-cache|KV Cache Management]]** covers cache layout and sizing; for a single call, the key point is that both prompt tokens and generated tokens occupy memory during the call.

Because each generated token extends a dependent sequence, output length is a major cost variable of a call, and the serving implementation sets its realized latency. Although the conditional dependence in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.05 Autoregressive Generation#^eq-autoregressive-factorization|equation 2]] fixes the mathematical order of token choices, it does not mandate that hardware evaluate each token in an isolated forward pass. Techniques such as speculative decoding,[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn4|⁴]] for example, draft candidate token blocks with a small auxiliary model and score them in parallel with the target model, provably preserving the target output distribution ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-leviathan2023fast|Leviathan et al. 2023]]; [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-chen2023accelerating|Chen et al. 2023]]). The per-token decode floor derived in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-cost|section 2.8]] is therefore a property of plain one-token-per-pass decoding, not a law of the factorization.

### Sampling Controls

^sec-vol3-foundation-model-sampling-controls

Lowering sampling randomness can make a model repeat its top-scoring token choice, yet the highest-scoring token is often a plausible guess rather than a valid file path or a working patch. For positive **temperature**[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn5|⁵]] ${\tau_{\text{temp}}}$ (subscripted to keep it distinct from the trajectory ${\tau}$), softmax converts the logits into next-token probabilities:

$$
\Pr({y}_t = {v} \mid {x_{1:S}}, {y_{<t}}) = \frac{\exp\left({z}_{t, {v}} / {\tau_{\text{temp}}}\right)}{\sum_{{w} \in {\mathcal{V}}} \exp\left({z}_{t, {w}} / {\tau_{\text{temp}}}\right)} \tag{3}
$$

^eq-temperature-softmax

Unit temperature (${\tau_{\text{temp}}} = 1.0$) leaves the logits unscaled. Lowering a positive temperature amplifies logit differences and concentrates probability mass on the highest-scoring tokens; raising it flattens the distribution, which approaches uniformity across a finite vocabulary as temperature grows without bound. Temperature therefore controls output entropy, not model confidence: because next-token cross-entropy training minimizes sequence prediction error rather than calibrating scores to task success, high token probability does not mean a completed response is correct.

**Greedy decoding** instead picks a highest-scoring token, $\operatorname{argmax}_{{v} \in {\mathcal{V}}} {z}_{t, {v}}$, with a tie-breaking rule. Given fixed logits and a fixed tie rule, that choice is deterministic. Serving APIs often expose greedy decoding as ${\tau_{\text{temp}}} = 0$, which the engine implements by taking the argmax directly rather than dividing by zero in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.05 Autoregressive Generation#^eq-temperature-softmax|equation 3]]. As positive temperature approaches zero, softmax puts all probability mass on the maximum, though if several tokens tie for the top logit, the limit alone does not pick among them.

Sampling can also restrict which tokens remain eligible. **Top-${k}$ sampling** ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-fan2018hierarchical|Fan et al. 2018]]) keeps the ${k}$ highest-scoring tokens under a tie rule and renormalizes their probabilities. **Top-${p}$ sampling**, or nucleus sampling, sorts tokens by descending probability, keeps the shortest prefix whose cumulative mass reaches ${p}$ ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-holtzman2020curious|Holtzman et al. 2020]]), and renormalizes that set. Because top-${k}$ fixes the candidate count regardless of shape, it can keep unlikely tail tokens when the distribution is sharp and cut plausible options when the distribution is flat. Top-${p}$ instead lets the active pool expand or shrink with the distribution’s spread. When temperature scaling and nucleus truncation are used together, the order in which they run changes the active pool: scaling logits by ${\tau_{\text{temp}}}$ before computing probabilities alters how much mass the leading tokens carry and therefore changes how many tokens are needed to reach the cumulative threshold ${p}$. That ordering and the engine’s numerical conventions are therefore part of the decoding configuration.

Neither filter tells valid file paths, true claims, or safe commands from wrong ones. A rare token may be the exact identifier a patch needs, while a high-probability continuation may name a file that does not exist. Truncation filters change which candidates reach the runtime; only checks against the environment and task contract tell whether that change helps.

**Napkin Math 2.1: Temperature and truncation on the same logits**

**Problem**: A hypothetical vocabulary ${\mathcal{V}} = \{{v}_1, {v}_2, {v}_3, {v}_4, {v}_5\}$ has logits ${\mathbf{z}}_t = [12, 10.5, 9, 6, 3]$, held fixed so that differences arise strictly from the decoding configuration. How much probability mass concentrates onto the top token when halving the temperature, and which tokens survive nucleus truncation?

**Math**: At temperature ${\tau_{\text{temp}}} =$ 1, the exponentiated logits sum to 207596.9. Normalizing each exponential by this partition sum yields the baseline distribution:

${\mathbf{p}_{\tau_{\text{temp}}=1}} \approx [0.7840, 0.1749, 0.0390, 0.0019, 0.0001]$.

Halving the temperature to ${\tau_{\text{temp}}} =$ 0.5 doubles the exponent of each term. Following normalization, the probability of the mode ${v}_1$ rises to 0.9503, capturing 95.0 percent of the total distribution. All lower-ranked tokens retain positive probability under untruncated softmax.

Returning to unit temperature and applying nucleus truncation with ${p} =$ 0.90 evaluates cumulative probability mass. The lead token ${v}_1$ provides 0.7840, which falls short of the threshold. Incorporating ${v}_2$ (0.1749) brings cumulative coverage to 0.9589, which satisfies the threshold and defines the active nucleus as $\{{v}_1, {v}_2\}$. Renormalizing across this active set assigns probability 0.8176 to ${v}_1$ and 0.1824 to ${v}_2$, while strictly zeroing the remaining tail tokens $\{{v}_3, {v}_4, {v}_5\}$.

**Systems insight**: Temperature governs candidate diversity. Halving temperature compresses the non-top probability tail from 21.6 percent to 5.0 percent, achieving a 4.3× reduction, whereas nucleus truncation eliminates the tail entirely. Repeated calls produce diverse outputs only when probability mass occupies this tail, which is the stochastic resource that parallel candidate sampling draws on in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^sec-vol3-test-time-compute-breadth-axis|Parallel sampling along the breadth axis]]**. Because neither transformation ensures that the highest-scoring candidate is correct, engineering teams configure decoding parameters based on empirical task pass rates rather than raw model likelihood.

### Repetition and Replay

^sec-vol3-foundation-model-repetition-replay

Greedy decoding removes sampling variance from a fixed logit vector, but it does not make served API calls reproducible end to end. In a production cluster, two identical requests can land on different server nodes, accelerator revisions, or kernel builds. Small differences in floating-point reduction order[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn6|⁶]] can shift nearly tied logits in their least significant bits, and flipping an argmax choice at position ${t}=1$ changes the prefix for every token after it. Fixing a pseudorandom seed controls the sampler’s random number generator, but it cannot prevent numerical differences across backend kernels or dynamic batch sizes. Reproducing a call from scratch requires pinning the serving environment and kernels as well as setting ${\tau_{\text{temp}}} = 0$. A 2025 production incident shows how serving-fleet bugs alone can change model outputs while caller requests stay identical.

**War Story 2.1: Three serving bugs behind unchanged requests (2025)**

**Context**: Between August and early September 2025, three separate infrastructure bugs intermittently degraded the responses of Anthropic’s Claude models ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-anthropic2025postmortem|Anthropic 2025]]). These defects stemmed entirely from the serving infrastructure rather than caller requests or model weights.

**Mechanism**: A front-end routing defect directed standard traffic to server clusters configured for extended context windows, while session stickiness (routing a client’s follow-up requests to the server that handled its earlier ones) kept those follow-up requests on the misconfigured nodes. Concurrently, an improperly deployed kernel optimization on a specialized accelerator cluster occasionally assigned outsized probability to improbable tokens. Finally, an optimization in the token-selection pipeline triggered a compiler bug: an approximate top-${k}$ routine with mixed-precision subroutines emitted incorrect tokens under specific dynamic batch sizes.

**Impact**: During peak impact, the routing failure corrupted 16 percent of requests to one production model, and approximately 30 percent of active coding agent users encountered at least one misrouted interaction. Generated responses contained foreign-language script insertions within English prose and syntax anomalies in generated source code. Automated regression suites initially missed these failures because a response often recovered from an isolated corrupted token later in generation, and intermittent runtime conditions meant an identical prompt could succeed on one invocation and fail on the next.

**Fix**: Engineers rolled back the offending kernel deployments, corrected cluster routing rules, and replaced the approximate top-${k}$ kernel with an exact selection routine running in 32-bit floating-point precision, trading a minor throughput penalty for numerical stability. Anthropic subsequently deployed continuous canary evaluations across production fleets to catch subtle generational drift.

**Systems lesson**: Output distributions reflect the concrete serving pipeline just as heavily as the model weights or input context. Corrupted tokens arrived packaged in well-formed HTTP payloads and cleanly closed generation blocks, a direct instance of the fail-plausible fault (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-fail-plausible|The fail-plausible fault]]**). Agent runtimes must log full call-level metadata (runtime versions, routing tags, and sampling parameters) while subjecting every proposed action to external environment validation regardless of nominal generation success.

Incidents like this one set the logging baseline for an agent runtime. The runtime log should record the serialized prompt, model and tokenizer identifiers, sampling settings, token limits, and any routing or seed metadata, alongside the raw response payload, stop reason, and token usage. Those records also separate two kinds of debugging: replaying a recorded response tests the runtime’s downstream logic without model variance, whereas re-sending the live request tests how the agent handles variation across calls. Benchmarks should measure and report that call-to-call variance rather than judging a configuration from a single run.

An agent runtime therefore receives candidate tokens produced under a specific decoding configuration and ended by a specific stop condition. That stop condition is the first thing the runtime must read. A generation that ran into its output ceiling, was refused, or was cut off in transit can still deliver bytes that look like a finished proposal, and no check on the payload alone tells the difference. Before asking whether a `read_file` proposal names an existing, permitted path, the runtime needs a record of whether a complete candidate arrived at all.
