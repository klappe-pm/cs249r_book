# V3-02.07 Checking Candidate Outputs

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-continuations

Passing the status gate admits a completed proposal to the candidate path, whether that proposal is the initial `read_file("src/pool.py")` request or the connection-pool patch the repair agent emits on the next turn. Neither high token probability nor schema conformance determines whether the runtime can safely act on either candidate: a well-formed `read_file` request can still target a missing or unauthorized path ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^sec-vol3-foundation-model-proposals-observations|section 2.2.2]]), and a candidate patch can parse cleanly, compile against existing headers, and pass a sequential unit test while leaving the underlying race condition untouched. Because each verification check answers a narrow question rather than certifying overall task satisfaction, the runtime must track what each gate actually proves and what it leaves open.

### Why Token Likelihood Cannot Replace Checks

^sec-vol3-foundation-model-likelihood-checked-properties

A model often assigns high probability to an obsolete or nonexistent file path because that path matches common directory naming patterns in its training corpus. Autoregressive generation scores tokens by how well they fit training data and prompt context, not by whether a path exists on disk, whether the caller has permission to read it, or whether an edited function preserves a lock invariant.

Checking a candidate therefore means pairing each required property with the tool or gate that actually tests it. For a `read_file` proposal, a schema validator checks that the payload has only allowed keys and a string-valued `path`. Passing that check proves schema conformance, provided the validator implements the schema dialect faithfully and inspects the exact object passed to execution. Proving that the target file exists requires checking the filesystem, and proving permission requires checking the task’s capability grant against the host policy.

Static checks and dynamic tests likewise establish different claims. A compiler checks types and syntax under fixed flags, while a linter flags suspect patterns with static rules. Dynamic tests run concrete code paths and check runtime assertions, so a passing single-threaded checkout test says nothing about how the connection pool behaves under concurrent contention.

↩︎ The closure evidence levels, from self-report and static checks through visible and sealed tests to formal proof, are established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-invariant-closure|The invariant closure principle]]**.

Because each check covers only its own scope, the runtime must treat model output as untrusted data rather than executable control flow. A candidate tool call stays passive data until an authorized tool handler validates and dispatches it, checking permissions at the moment of access[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn8|⁸]] regardless of what the model claims about its own rights. Running an untrusted code patch likewise executes arbitrary machine instructions and belongs inside an isolated sandbox even during early test runs.

### Self-Review and External Evidence

^sec-vol3-foundation-model-self-review-evidence

Asking a model to review or refine its own patch can catch surface syntax mistakes or missing edge cases, yet self-review is just another generation step drawn from the same weights and conditioned on the same incomplete context. When the model starts from a mistaken assumption about an API or lock protocol, prompting it to critique its own answer usually repeats that assumption rather than catching it. Re-prompting does not create an independent check: across reasoning benchmarks, models asked to grade and revise their own answers without new external evidence rarely improve accuracy and often turn right answers into wrong ones ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-huang2024cannot|Huang et al. 2024]]).

Refining a candidate and certifying a property must therefore stay separate. A model’s critique can guide the next search step, but external tools (compilers, linters, sandboxed test runners, and kernel permission checks) must supply the evidence for the properties they test. No model critique, whether from the generator itself or from a separate **learned judge** (a second model prompted or trained to score the first model’s output), carries authority to clear a security boundary or approve a release. When a pipeline uses a learned judge to rank or filter candidates, the runtime should treat its verdicts as noisy scores with measurable false-accept rates and known biases, such as favoring longer answers or particular list positions ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-zheng2023judging|Zheng et al. 2023]]). Even when a check returns a passing verdict, a conditional-probability calculation shows how much defect risk remains when the checker itself can pass a defective patch.

**Systems Perspective 2.1: What a passing verdict leaves unresolved**

Let ${\epsilon}$ denote the defect rate, the share of generated patches that violate a specified behavioral property (a local symbol here, distinct from the per-turn error rate of horizon compounding), and let ${\epsilon_{\text{FA}}}$ denote the checker’s false-accept rate, the probability that it passes a defective patch. Suppose ${\epsilon} =$ 18 percent, ${\epsilon_{\text{FA}}} =$ 0.65, and the checker passes valid patches with probability 0.85. Bayes’ rule gives the fraction of defective patches among the passing results:

$$
\Pr(\text{Defective} \mid \text{PASS}) = \frac{{\epsilon_{\text{FA}}} \cdot {\epsilon}}{{\epsilon_{\text{FA}}} \cdot {\epsilon} + \Pr(\text{PASS} \mid \text{Valid}) \cdot (1 - {\epsilon})} \tag{4}
$$

^eq-vol3-fm-checker-posterior

Substituting the assumed rates gives $\frac{0.65 \times 0.18}{(0.65 \times 0.18) + (0.85 \times (1 - 0.18))}\approx 14.37\%$. The defect share among passing patches falls only from 18 percent to 14.37 percent, because the checker rejects 35 percent of defective patches while also rejecting 15 percent of valid ones. The lever is ${\epsilon_{\text{FA}}}$: a checker with half the false-accept rate, 0.325, lowers the residual to 7.7 percent. Repeating the same check buys no such guarantee, because its behavior on the surviving candidates is correlated with the first pass. Every defective patch that passes also inflates the apparent acceptance probability ${p_{\text{acc}}}$ in the cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**).

A sound checker for the exact property drives ${\epsilon_{\text{FA}}}$ to zero under its assumptions. Determinism alone does not supply soundness, and soundness for schema membership does not extend to patch behavior. The residual in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^eq-vol3-fm-checker-posterior|equation 4]] is one minus the precision ${\Pi_{V}}$ of a passing verdict in the verification asymmetry (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-verification-asymmetry|3]]), written there with valid-candidate rate ${p_{\text{valid}}} = 1 - {\epsilon}$ and false-reject rate ${\epsilon_{\text{FR}}} = 1 - \Pr(\text{PASS} \mid \text{Valid})$. That principle holds that producing a candidate, selecting it, and establishing that it satisfies the task are different events, and it yields a design rule. Select each validation gate for the specific property it establishes and its false-accept rate, and let the task contract determine what residual defect rate the system can tolerate.

### Staging Checks by Cost and Scope

^sec-vol3-foundation-model-scoped-check-pipeline

Running full end-to-end integration tests or sandboxed reproduction scripts on every model output is orders of magnitude more expensive than parsing JSON or running a static linter. The runtime therefore stages candidate checks from cheapest to most expensive, rejecting malformed or unauthorized requests early before spending compute on behavioral tests. Ordering checks by cost improves throughput, yet each gate tests a different property rather than a tighter approximation of overall correctness. [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^tbl-verification-layers|Table 3]] lists these four layers along with what each costs and what its passing result leaves open.

| Verification layer        | Gate mechanism                                   | Property or evidence                                             | Cost to account for                            | Limit of the claim                                                |
|:--------------------------|:-------------------------------------------------|:-----------------------------------------------------------------|:-----------------------------------------------|:------------------------------------------------------------------|
| **Syntax and schema**     | Parser and schema validator                      | Required fields, supported types, and declared value constraints | Parsing and validation                         | Does not establish permission or correct values beyond the schema |
| **Authorization**         | Task permission check and enforcing tool handler | Requested operation and target fall within the current grant     | Policy lookup and mediation                    | Permission does not establish that the operation serves the goal  |
| **Static analysis**       | Compiler, type checker, or linter                | Properties covered by the selected analysis and configuration    | Analysis of the candidate and its dependencies | Coverage depends on the checker and language assumptions          |
| **Behavioral evaluation** | Controlled execution and designated tests        | Observed outcomes for the exercised inputs and conditions        | Environment preparation and execution          | Passing cases do not establish untested behavior                  |

Table 3: **Scoped candidate checks**: A passing result supports a named claim, not every property needed for task acceptance. The runtime preserves these distinctions when composing the checks.

^tbl-verification-layers

Consider how this pipeline handles an inspection request versus a patch. Behind the status gate of [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-contract|section 2.5]], a `read_file` proposal needs only the first two rows of [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^tbl-verification-layers|table 3]] before dispatch, because reading the file supplies an observation for the next turn rather than finishing the repair. When evaluating a proposed patch, by contrast, the pipeline checks patch syntax and target paths, applies the diff in an isolated scratch workspace, and runs the required unit and stress tests. Final acceptance follows the task contract’s evidence standard, escalating to human review when automated checks cannot settle safety or correctness.

Every layer in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^tbl-verification-layers|table 3]] inspects tokens the model has already emitted. Even when a streaming monitor aborts a broken response early, the offending token has already been chosen, and recovering still requires another call. For the first layer of that cascade, syntax and schema conformance, the runtime knows the legal structure before decoding begins and can enforce it inside the sampler itself.
