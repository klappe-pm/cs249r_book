# V3-02.03 The Model Call Boundary

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-role

If a runtime treats a model’s output string `read_file("src/pool.py")` as an already-authorized file read, a single hallucinated path can read outside the workspace before any check runs. Keeping a proposed action separate from an executed one requires splitting each call across three components: the foundation model, the inference service, and the agent runtime. The foundation model[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn1|¹]] computes conditional probability distributions over token sequences given a prompt context. The **inference service** hosts the model weights, runs forward passes on accelerators, applies sampling parameters, and packages the output tokens into a response record. The agent runtime drives the task: it builds the prompt, tracks budgets, checks candidate outputs, and decides whether an action is allowed to run in the host environment. Even when all three run in the same process on one machine, their interfaces keep generated text separate from the decision to act on it.

**Definition 2.1: Proposal**

A ***proposal*** is model output that specifies a candidate action or answer for the runtime to evaluate, carrying zero ambient authority and producing no external side effects until the runtime explicitly validates, authorizes, and executes it.

1.  **Significance**: Every external effect of an agent depends on an explicit runtime decision. Because the model call possesses zero ambient authority, a rejected proposal costs one inference invocation rather than an unintended modification to the environment. That invocation still consumes resources and counts toward ${C_{\text{attempt}}}$ in the cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**).
2.  **Distinction**: A proposal must not be confused with an *effect* (a state change executed by the runtime after authorization) or an *observation* (the runtime’s factual record of what an operation returned). Emitting `read_file("src/pool.py")` is merely a proposal; the file contents subsequently retrieved from disk and supplied to the next call constitute an observation.
3.  **Common pitfall**: Logging a tool request as an executed action, or accepting a model’s textual claim that “the file has been read” as an empirical observation, allows fluent prose to stand in for operational evidence.

### Messages and Tool Definitions

^sec-vol3-foundation-model-messages-tool-definitions

A model cannot tell an operator’s instruction, a user’s prompt, and a file excerpt returned by a tool apart unless the runtime labels each piece of the request, yet those labels alone do not make the content trustworthy. The runtime organizes the prompt as an ordered sequence of role-tagged messages: a `system` message sets task instructions and constraints, a `user` message supplies the task prompt, an `assistant` message records earlier model outputs, and a `tool` message carries the raw observation returned when an action runs. Role tags organize the token stream for the model’s attention mechanism, while the runtime remains responsible for checking whether the content is authentic and follows the task contract.

↩︎ The task contract, which fixes the goal, environment, permitted actions, available observations, and completion criteria, is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-five-part-contract|The five-part task contract]]**.

Alongside the message history, the request advertises the tools available to the model and gives their argument schemas. In [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^lst-vol3-model-request|listing 1]], the runtime declares a file-reading tool with one required string parameter. The JSON-schema definition tells the model what syntax a valid proposal needs, while the runtime enforces workspace sandboxing and filesystem permissions independently.

``` yaml
model_config: repair-model/config-a
messages:
  - role: system
    content: Propose the next inspection for the assigned repair.
  - role: user
    content: Inspect the connection-pool locking logic in src/pool.py.
tools:
  - name: read_file
    arguments_schema:
      type: object
      properties: {path: {type: string}}
      required: [path]
      additionalProperties: false
limits:
  max_output_tokens: K_max
  deadline: T_deadline
sampling: selected_sampling_settings
```

Listing 1: **A bounded inspection request**: This provider-neutral record separates model-visible messages and tool definitions from the configuration and limits governing the call. Symbolic values stand for settings chosen by the runtime; the field names do not prescribe a vendor API.

^lst-vol3-model-request

The `model_config` field binds the request to a specific model version, weights checkpoint, and serving profile, while `sampling` controls how the service draws output tokens from the model’s predicted distribution. Two resource bounds protect the call from running away: `max_output_tokens` (${K_{\max}}$) caps how many tokens the call can generate, and `deadline` (${T_{\text{deadline}}}$) sets a timeout against queue delays and serving stalls. Writing those bounds into the request works only when the inference service or client runtime enforces them during generation.

When generation finishes, the inference service returns free-form text, a tool proposal, or a service error, and a runtime adapter normalizes that provider-specific reply into a single envelope ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^lst-vol3-model-response|listing 2]]). Here, the service reports a completed generation pass that produced a tool request to read `src/pool.py`, one diagnostic step before any repair is checked.

``` yaml
kind: tool_request
payload:
  name: read_file
  arguments: {path: src/pool.py}
stop_reason: tool_request
status: COMPLETED
usage: {input_tokens: S, output_tokens: K}
```

Listing 2: **A returned tool proposal**: Response kind identifies what the payload represents, while status and stop reason describe the invocation. Usage counts describe consumed generation resources, not progress on the repair.

^lst-vol3-model-response

Here, `kind` tells the runtime parser how to read the payload. The normalized `status` confirms that transport and generation finished under the adapter’s contract, while `stop_reason` records the **stop reason** reported by the serving engine: whether the model emitted a tool-call marker, hit an end-of-sequence token, or stopped at the token limit. The `usage` block counts ${S}$ input tokens read and ${K}$ output tokens generated. Bare ${S}$ is sequence length throughout this book, here the prompt a call reads; the State levels ${S}_0$ to ${S}_3$ always carry their subscript. Tracking usage across calls prevents context-window overflow and feeds cost accounting; if a provider omits token counts, the runtime records usage as missing rather than zero.

Every path out of the response ends in the runtime, and the stop reason chooses the path ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^fig-vol3-model-call-surface|figure 1]]). A tool call goes to validation and authorization before anything runs, a finished answer goes to verification, and output cut off at its limit goes to quarantine, where it is kept for diagnosis and never executed ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-status-envelope|section 2.5.2]] states the rule).

![[90 Assets/Volume III/02 Foundation Model/Model Call Surface 113d6d60f1.svg]]

Figure 1: **The Model Call Surface**: The request carries messages, tool definitions, and limits into a model with frozen weights, which returns a proposal with a stop reason and usage counts. Every arrow out of the response lands in the agent runtime. The runtime validates and authorizes a tool call before anything runs, returns the result as a new message for the next call, sends a finished answer to verification, and quarantines output cut off at its limit.

### Proposals and Observations

^sec-vol3-foundation-model-proposals-observations

Following the tool-call branch of [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^fig-vol3-model-call-surface|figure 1]] turns that returned `read_file` proposal into an observation without trusting its text. Because the payload could still carry a traversal string like `../../etc/passwd` or a malformed argument, the runtime first checks structural conformance, confirming that the proposed arguments match the declared schema (for example, that `path` is a string rather than a shell command). Next, it checks the arguments against the task’s permission grant: advertising `read_file` lets the model propose file reads, but grants no right to read arbitrary paths. The runtime verifies that `src/pool.py` resolves inside the allowed workspace rather than escaping to host files through directory traversal. Once authorized, the tool runs outside the model call, inside an isolated sandbox or container with its own timeout.

After the tool finishes, the runtime records what happened and builds the next prompt. It appends the model’s `assistant` proposal paired with a `tool` message carrying the observation (here, the bounded file excerpt). That observation reports the actual outcome, including a missing file or a permission denial, and notes when the output was truncated; **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.03 Tool Subsystem Architecture#^sec-vol3-tool-calling-round-trip|One mediated round trip]]** develops how the runtime matches each result to the call it answers, records errors, and marks truncation.

The model on the next turn sees the tool output only because the runtime rebuilds and sends the updated context window. Foundation models are stateless token predictors with no internal memory of earlier requests or tool runs. Session identifiers or server-side prefix caching (reusing attention state the service already computed for a prompt prefix that repeats across turns, priced in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-trajectory-cost-accumulation|section 2.8.3]]) can cut latency, but the runtime alone decides which messages enter the prompt. That separation also means an observation can go stale: a file excerpt in the prompt shows the file only as it stood when read, so if a later command edits the file on disk, the excerpt in context is out of date.

The gap between a proposal and an observation is where the fail-plausible fault enters. A model can emit a well-formed proposal targeting the wrong source module, or a convincing analysis grounded in an obsolete observation, and the tokens look the same either way. Agent engineering therefore requires treating status, schema structure, security authorization, and empirical evidence as distinct, non-fungible properties of the interaction. [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^tbl-vol3-foundation-model-responsibilities|Table 1]] summarizes what the runtime owns around every call, whether the model runs in the local process or behind a remote API.

↩︎ The fail-plausible fault, output that looks well formed and credible while the intended property fails, is established in **[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^sec-vol3-intro-fail-plausible|The fail-plausible fault]]**.

| Model term                  | Runtime responsibility                                                       | Failure if the runtime ignores it                                     |
|:----------------------------|:-----------------------------------------------------------------------------|:----------------------------------------------------------------------|
| **Context window**          | Count the complete input representation and reserve output headroom          | Rejected request or insufficient room for a complete response         |
| **Sampling settings**       | Choose supported settings and retain them with the request and output        | Unexplained variation or an unjustified assumption of reproducibility |
| **Tool call**               | Check the proposal, authorize access, and return the actual tool observation | A proposed operation mistaken for an executed or permitted one        |
| **Stop reason**             | Interpret it with normalized status before treating the payload as complete  | An interrupted or refused response treated as a finished candidate    |
| **Fluent but wrong output** | Evaluate the relevant claim using checks and observations with stated limits | Credibility mistaken for evidence of the intended property            |
| **Successful response**     | Distinguish delivery and generation completion from task acceptance          | A completed call recorded as a successful repair                      |

Table 1: **What the runtime owns around a model call**: Each feature of the call creates an obligation outside the model’s generated content. Satisfying one obligation does not discharge the others.

^tbl-vol3-foundation-model-responsibilities

The request and response records fix the boundary around a model call: messages supply context, tool definitions specify what the model may propose, and the runtime mediates every effect on external state. Before the service can run the call, however, the whole request must fit inside the model’s context window with room left for the response, and checking that fit requires counting tokens rather than characters, messages, or files.
