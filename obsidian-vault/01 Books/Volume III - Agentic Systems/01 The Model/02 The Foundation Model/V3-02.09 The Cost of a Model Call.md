# V3-02.09 The Cost of a Model Call

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-cost

On the repair agent’s first turn, reading a long prompt of repository context and tool schemas takes less accelerator time than generating a short reply, yet across a multi-turn repair loop, resending that growing prompt history balloons into hundreds of thousands of input tokens. Counting a call as a single black-box unit, or summing input and output tokens into one unweighted total, hides which phase actually drives latency and cluster work. An invocation contract therefore budgets prompt reading and output generation separately, pricing both a single call’s latency and a multi-turn trajectory’s cumulative input load.

Input length and output length stress distinct subsystems in the inference serving stack. Prompt ingestion exposes many known token positions to parallel matrix computation across the accelerator’s execution units. Conversely, autoregressive token generation executes as a strictly sequential loop, where each new token depends on the hidden state of all preceding positions. Because hardware handles these two phases under different physical constraints, output length is the primary software lever for controlling generation latency. A long prompt, a short reply, or a congested service queue can, however, shift the latency bottleneck elsewhere.

### Where a Call Spends Its Time

^sec-vol3-foundation-model-call-latency-decomposition

A runtime that records only the total wall-clock time of a slow call cannot tell whether the delay came from a bloated prompt, a backed-up serving queue, or a long reply, yet each cause requires a different fix. To separate them, the runtime measures five non-overlapping phases. They run from the moment it prepares the outbound request to the moment the normalized response is ready for validation. The phases are preparation (context assembly, serialization, and network send), queueing (waiting in the service’s admission queue), **prefill** (reading the prompt tokens in a parallel forward pass), **decode** (generating output tokens step by step), and postprocessing (response transfer, deserialization, and schema checks):

$$
{T_{\text{call}}} = {T_{\text{prep}}} + {T_{\text{queue}}} + {T_{\text{prefill}}} + {T_{\text{decode}}} + {T_{\text{post}}} \tag{6}
$$

^eq-vol3-call-latency

Each term in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-call-latency|equation 6]] is an elapsed time in seconds, measured with timestamps rather than estimated backward from token counts; when network transfer or local preparation overlaps server execution, the spans track non-overlapping intervals so nothing is counted twice. The first generated token needs careful accounting so it is not charged to both prefill and decode. In a standard Transformer, the prefill pass reads the whole prompt and produces the logits from which the first output token is drawn. On the client side, the time from sending the request to receiving that first token is the **time to first token** (TTFT), and the average spacing between later tokens is the **time per output token** (TPOT). Serving systems track TTFT and TPOT as separate objectives because prefill and decode contend for the same accelerator compute and memory bandwidth; disaggregated serving systems go further and run prefill and decode on separate accelerator pools so neither stalls the other ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-zhong2024distserve|Zhong et al. 2024]]).

When TTFT includes sampling and delivering the first token, the remaining decode interval covers only the next ${K}-1$ tokens in a completion of length ${K}$. For a streamed reply, adding client-measured TTFT, the ${K}-1$ inter-token intervals, and final deserialization gives the full call latency without double-counting the first token. Client-measured TTFT is larger than server prefill time because it also includes network transit and queueing, and because servers and networks often batch several streamed tokens into one network chunk, chunk arrival times on the client do not always match per-token step times on the accelerator.

The first-token boundary separates these two measurements in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^fig-vol3-first-token-accounting|figure 5]]. The service produces the initial logits during prefill, but the client must still wait for sampling and delivery before its TTFT interval ends.

![[90 Assets/Volume III/02 Foundation Model/First Token Accounting cd26640ab6.svg]]

Figure 5: **First-Token Accounting**: A schematic timeline separates server prefill from client time to first token. Here K is the total number of output tokens. Prefill supplies the initial logits; only the remaining output tokens require subsequent generation passes. The later tokens arrive together in an illustrative buffered chunk, so client arrivals do not identify individual service steps. Distances are not measured durations.

^fig-vol3-first-token-accounting

A client trace can therefore identify a long wait for the first token without establishing how much of that wait the accelerator spent on prefill. Diagnosing the delay requires queueing and execution boundaries from the service, rather than a finer sampling of chunk arrivals.

Capping `max_output_tokens` bounds how many tokens the model can emit, not how fast the call returns; a congested queue can burn the entire deadline before prefill even starts. Latency benchmarks must therefore record the model, prompt and output lengths, prefix-cache hit rate, and cluster load. Even when a single agent runs one turn at a time, the serving cluster rarely runs that call alone: continuous batching schedules requests at each decode step ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-yu2022orca|Yu et al. 2022]]), interleaving the agent’s tokens with dozens of other requests.

### Estimating Per-Call Hardware Work

^sec-vol3-foundation-model-per-call-work-estimate

Counting input and output tokens together hides why a two-hundred-token reply can take longer on the accelerator than an eight-thousand-token prompt. Input processing and output generation hit different hardware bottlenecks, so a baseline work model gives them separate per-token time floors. A dense Transformer with ${P}$ parameters executes approximately $2{P}$ floating-point operations for each token it processes, in prefill and decode alike. What differs is how often the weights must be read. Prefill reads each weight tensor from accelerator memory once per call and reuses it across all ${S}$ prompt positions, so a long prompt spreads one weight read over thousands of tokens of arithmetic, and each prompt token costs about $2{P}$ operations at the peak arithmetic rate ${R_{\text{peak}}}$. Single-stream decode produces one token per step, so it reads every weight once per generated token. Each output token therefore moves the full weight payload of ${P}\,{s_{\text{elem}}}$ bytes (with ${s_{\text{elem}}}$ bytes per parameter) across a memory interface of bandwidth ${\text{BW}}$, and its arithmetic finishes long before those bytes arrive.

These two regimes are the two limbs of the roofline model ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-williams2009|Williams et al. 2009]]), which bounds attainable throughput by the lesser of the peak arithmetic rate and the memory bandwidth multiplied by the work done per byte moved. Prefill does much work per byte and sits under the arithmetic limb; low-batch decode does little and sits under the bandwidth limb, a split that empirical evaluations of Transformer inference confirm ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-pope2023efficiently|Pope et al. 2023]]). The two floors are

$$
{t_{\text{prefill}}} \approx \frac{2{P}}{{R_{\text{peak}}}}, \qquad {t_{\text{decode}}} \ge \frac{{P}\,{s_{\text{elem}}}}{{\text{BW}}} \tag{7}
$$

^eq-vol3-fm-token-floors

The lowercase symbols are per-token floors. The analytical budget uses the allowances ${T_{\text{prefill}}} \approx {S}\,{t_{\text{prefill}}}$ and ${T_{\text{decode}}} \approx {K}\,{t_{\text{decode}}}$. Dividing the two floors cancels the parameter count ${P}$:

$$
\frac{{t_{\text{decode}}}}{{t_{\text{prefill}}}} \approx \frac{{R_{\text{peak}}} \, {s_{\text{elem}}}}{2 \, {\text{BW}}} \tag{8}
$$

^eq-vol3-fm-floor-ratio

Consider a concrete reference deployment: a dense model with 70.6B parameters stored in 8-bit precision (${s_{\text{elem}}} = 1$ byte) on a single accelerator with an 8-bit peak rate of 1,979 TFLOP/s and a memory bandwidth of 3.35 TB/s. Each token costs 141.2 GFLOP of arithmetic, and dividing by the peak rate gives a prefill floor of 71.35 μs per prompt token. Each decode step reads 70.6 GB of weights, and dividing by the bandwidth gives a decode floor of 21.075 ms per generated token. Under [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-fm-floor-ratio|equation 8]], decoding a single output token therefore takes the same hardware time as ingesting roughly 295 prompt tokens. This asymmetry is the content of output-bound latency (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-memory-bandwidth-decoding|2]]), under which each plain, unbatched decode step incurs a full weight read in this model, so output volume can dominate call latency. The ratio reflects weight-dominated, unbatched decode against peak-throughput prefill, not a measured cloud service rate or a commercial billing tier.

↪ Both execution floors and their operating boundaries are developed in **[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^sec-vol3-appendix-inference-roofline|Cost Asymmetry Between Input Prefill and Output Generation]]**.

This analytical budget charges each prompt token once at the prefill floor and reserves one decode floor step for each generated token. The first output token receives that allowance even though prefill supplies its initial logits. The budget therefore includes an extra decode-floor step relative to the measured post-TTFT interval, which contains only subsequent generation steps.

The budget is an idealized hardware baseline rather than a substitute for wall-clock measurement: it omits network transit, queueing delay, attention quadratics, and runtime software overhead. It also assumes standard autoregressive generation without speculative decoding. In production, a serving system that batches concurrent client requests, distributes model weights across tensor-parallel accelerators (sharding individual weight matrices across multiple devices), or reuses cached attention state substantially alters the relationship between token count and elapsed time. The analytical estimate is therefore suited to comparing interface formats and output volumes, but certifying a production deadline requires measuring latency directly under realistic serving load.

Applying this baseline to the first repair turn shows how output tokens dominate. A prompt of 8,000 tokens contributes 0.571 s of prefill work, while generating a reply of 200 tokens is charged 4.215 s of decode work. The total call estimate is 4.786 s. Although output constitutes only 2.4 percent of the call’s total tokens, it accounts for 88.1 percent of the modeled hardware time. Pruning redundant output tokens therefore reduces overall latency far more effectively than removing an identical number of prompt tokens. At the same time, an agent benefits from a cheaper invocation only if the model still receives sufficient diagnostic context to generate a correct candidate; engineers must prune verbosity from the output format, not critical evidence from the prompt.

### How Multi-Turn History Drives Up Input Cost

^sec-vol3-foundation-model-trajectory-cost-accumulation

Even when individual turns produce concise outputs, a multi-turn trajectory can still generate a large prompt-ingestion workload. Consider an agent runtime that maintains an append-only execution log and re-transmits the full cumulative history on every invocation. If the initial turn contains ${S_{\text{base}}}$ prompt tokens and each subsequent turn appends ${\Delta S_{\text{turn}}}$ tokens of combined model output and tool observations, a trajectory spanning a horizon of ${H}$ turns submits:

$$
{S_{\text{sent}}} = \sum_{j=0}^{{H}-1} \left({S_{\text{base}}} + {j}\,{\Delta S_{\text{turn}}}\right) = {H} {S_{\text{base}}} + {\Delta S_{\text{turn}}} \frac{{H}({H}-1)}{2} \tag{9}
$$

^eq-vol3-trajectory-resend

prompt tokens in total. The quadratic growth in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 9]] comes from resending the growing history on every turn rather than from an inherent need of multi-turn reasoning. Sliding-window context buffers, trimmed tool outputs, or turn summaries can reduce the tokens sent, and a stateful serving endpoint can hold the conversation on the server to avoid resending the bytes over the network even when attention still spans the full history.

![[90 Assets/Volume III/02 Foundation Model/Resend Vs Prefix Reuse Margin 0e798004ea.svg]]

*Two curves of cumulative input tokens from turn 1 to turn 30. A red curve labeled re-sent bends upward to 892.5k. A green line labeled fresh prefill rises slowly to 51.5k.*

*Re-sent input grows with the square of the horizon; prefix reuse keeps fresh prefill linear.*

Repeated prompt input need not mean repeated computation. **Prefix caching** enables the inference engine to retain and reuse previously computed Key-Value (KV) activations for prompt prefixes that remain identical across consecutive requests ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-zheng2024sglang|Zheng et al. 2024]]). Reuse holds only for an exact token prefix computed under the same model and serving configuration, so altering an early system instruction or a tool schema forces fresh prefill from that point onward. The full compatibility conditions are developed in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.06 Prefix Caching Across Turns#^sec-vol3-kv-cache-prefix-compatibility|Prefix compatibility]]**.

To see how much work prefix reuse saves, suppose the inference service caches earlier prompt prefixes and runs fresh prefill only on the newly appended turn suffix (the model’s previous reply plus the new tool observation). Across all ${H}$ turns, the prompt tokens needing fresh prefill drop to ${S_{\text{base}}} + ({H}-1)\,{\Delta S_{\text{turn}}}$. That baseline conservatively assumes the server does not keep the KV state produced during decode; engines that retain decoded KV state as well avoid fresh prefill on the earlier model replies too.

**Napkin Math 2.2: The price of an append-only trajectory**

**Problem**: A coding agent runs 30 turns. Its first prompt has 8,000 tokens, each turn appends 1,500 tokens, and each call emits 200 output tokens. Assume that every prompt fits the service’s context limit and that compatible earlier prompt state remains available for reuse. How much input does the trajectory supply, and how does prompt-prefix reuse change its estimated processing work?

**Math**: Applying the arithmetic series in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-trajectory-resend|equation 9]] gives $30\times 8,000+1,500\times\frac{30\times 29}{2}=892,500$ prompt tokens. Total output is $30\times 200=6,000$ tokens. Without reuse, input therefore accounts for 99.3 percent of the combined input and output token count, although it does not account for that share of processing time.

With prompt-prefix reuse, fresh prefill covers $8,000+29\times 1,500=51,500$ tokens. Dividing the original input count by this fresh-prefill count gives a 17.3× reduction. At the reference prefill floor, the prefill-work estimate falls from 63.68 s to 3.67 s. Decode work stays at 126.45 s; caching earlier input does not remove the task’s new responses.

**Systems insight**: Append-only context makes input work grow with the square of the horizon. Doubling the trajectory to 60 turns multiplies re-sent input by 3.5× but fresh prefill under prefix reuse by only 1.9×, because reuse converts quadratic growth into a linear trajectory. Prefix reuse therefore serves as the primary lever for minimizing the input component of ${C_{\text{attempt}}}$ in the cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**), with its value compounding as horizons lengthen. While caching preserves the full decision context without loss of information, cache eviction and cross-worker request routing can dilute these theoretical savings in production.

Even across the multi-turn trajectory above, decode time at the unbatched floor exceeds uncached prefill time, yet on a shared serving cluster uncached prefill can dominate the aggregate hardware work of that same trajectory. The two statements price different accounts. Wall-clock latency governs the responsiveness of a single trajectory. Because each turn depends on the outcome of prior tool executions, an agent cannot parallelize its own dependent turns, and every output token remains a sequential step on the critical path even when the server batches that step with other requests. Computational work, by contrast, sets cluster throughput, hardware provisioning, and aggregate operating cost. When a serving cluster batches dozens of concurrent streams, the weight reads at each decode step are amortized across all active requests in the batch. The amortized service time per decoded token then drops from the memory-bandwidth floor toward the compute-bound arithmetic limit $2{P}/{R_{\text{peak}}}$ of [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^eq-vol3-fm-token-floors|equation 7]], the same per-token efficiency as prompt prefill (**[[05 Reference/Volume III - Agentic Systems/V3 Inference Cost Foundations#^sec-vol3-appendix-inference-roofline|Cost Asymmetry Between Input Prefill and Output Generation]]** derives the batched-step bound). Once input and output tokens require comparable hardware work per token, total cluster work scales with aggregate token volume, which for an append-only agent is dominated by re-sent prompt history, provided the cluster sustains high batching and has memory for the attention state. Prefix reuse acts directly on that input component, while its effect on end-to-end latency depends on how much the input contributes to the call a consumer waits on.

Which term an engineer should attack therefore depends on who waits for the output, and the repair agent alone cannot show the contrast. Its consumer is a compilation and test pipeline that must wait for a syntactically complete response. The support agent instead streams output tokens to a person reading as they arrive. The consumer requirements determine which latency terms these two illustrated workloads prioritize.

**Lighthouse 2.1: Call latency for two lighthouses**

**Support agent**: A customer-operations turn submits an 8,192-token prompt (consisting of policy documentation, customer account history, and recent dialogue) and streams an 150-token response to a human user in a live chat interface. At the chapter’s reference hardware floors, prefill takes 0.58 s and generating the full reply requires 3.2 s. However, token streaming displays the initial words immediately following queueing and prefill; the remaining tokens arrive at approximately 47 tokens per second, faster than a person reads. Under these lengths and streaming rates, TTFT governs how soon the user can begin reading. When 6,144 prompt tokens represent a common prefix of system instructions, organizational policies, and tool definitions shared across all concurrent sessions, prefix caching leaves only 2,048 tokens of fresh prefill, which takes just 0.15 s. In a loaded cluster, admission queueing becomes the dominant contributor to first-token latency.

**Repair agent**: The initial repair turn commits 88.1 percent of its estimated hardware work to generating a 200-token response. The agent runtime can parse, validate, and execute the generated patch only after receiving the entire payload. Decode duration dominates this repair estimate, making the compactness of the requested code representation its primary optimization lever.

**Systems insight**: The illustrated support turn prioritizes TTFT because the user can read while the remaining tokens arrive, whereas output volume dominates the illustrated repair call, whose consumer waits for a complete patch. Shortening the support reply does not directly remove queueing or prefill from first-token latency. Caching the repair prompt reduces its input work and input cost, but that saving contributes little to this output-dominated estimate. Different prompt lengths, streaming rates, or serving load can change the binding term; measured phase durations and queueing determine which intervention improves the latency the consumer waits on.

Prefix reuse is not free. A cached prefix occupies accelerator memory that concurrent requests cannot use, and holding it through a long tool wait pins memory that no generation is using. Eviction discards only derived attention state, never the context itself, so the runtime can rebuild the prompt from its own logs at the cost of fresh prefill. Which evidence the model sees and whether its attention state is worth keeping are therefore separate decisions.

↪ The choice to keep, move, or drop attention state held through a tool wait is developed in **[[01 Books/Volume III - Agentic Systems/02 Agent Memory/05 KV Cache Management/V3-05.08 Paused-State Policies#^sec-vol3-kvcache-swapping|Paused-State Policies]]**.

Billed dollars form a third account, separate from latency and hardware work. Providers bill uncached input, cached input, and output tokens at different rates, and on-premise hardware amortizes fixed costs across utilization, so token-count ratios do not translate directly into dollars; **[[01 Books/Volume III - Agentic Systems/06 Agents at Scale/19 Agent Economics/V3-19.04 Context Reuse and Retry Budgets#^sec-vol3-agent-economics-prefix-cache-value|Pricing prefix cache hits]]** prices a whole trajectory under such tariffs. The per-call estimate is one building block of a task budget that also carries failed tool executions, retries, validation runs, and idle reservations during tool waits.

**Checkpoint 2.3: Pricing calls and trajectories**

A call’s token count and its elapsed execution time quantify distinct facets of the overall system budget.

**Measurement boundary**: If the time to first token already accounts for sampling and delivering the initial token, how many subsequent token-generation intervals remain in a completed completion of length ${K}$?

**Horizon estimate**: If an agent trajectory triples to 90 turns under fixed ${S_{\text{base}}}$ and ${\Delta S_{\text{turn}}}$, estimate the growth factor for uncached re-sent input vs. fresh prefill under prefix caching. Which term dictates whether scaling to longer trajectories remains computationally viable?

**Reuse assumptions**: How does the analytical work estimate change if the inference server evicts the cached prefix from accelerator memory during a blocking tool execution?

**Cost denominator**: Why does an overwhelming majority of input tokens fail to produce an equivalent majority of financial cost when providers bill cached input and generated output at starkly different rates?

**Interface estimate**: A full-file replacement requires 1,850 output tokens, whereas a localized diff requires only 80. At the reference decode floor, which interface alternative can realistically operate within a 15 s latency deadline? Why is this analytical roofline model insufficient on its own to guarantee real-world service-level agreement (SLA) compliance?

Breaking down a call’s cost shows two main sources of waste: generating unchanged output tokens that the tool interface does not need, and recomputing prompt prefixes that the server could reuse. Cutting that waste helps only when the resulting output still solves the task, because a short diff that fails to apply or a cached prompt that produces a broken edit wastes the entire call. Choosing an output interface therefore requires comparing candidate accuracy, failure modes, and total resource spend under the same task budget.
