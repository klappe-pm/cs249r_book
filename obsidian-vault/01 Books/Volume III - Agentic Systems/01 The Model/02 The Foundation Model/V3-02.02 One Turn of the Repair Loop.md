# V3-02.02 One Turn of the Repair Loop

^sec-vol3-foundation-model-introduction

![[90 Assets/Volume III/01 Introduction/Hsa Locator Origin 574b033854.svg]]

*H·S·A locator with all three axes gray and only the origin dot highlighted in purple.*

*A single call runs one turn, carries no state, and holds zero ambient authority.*

The repair agent (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.05 The H·S·A Exposure Space#^sec-vol3-intro-lighthouses|Four lighthouse workloads]]**) needs to inspect the connection-pool implementation before proposing a change. A model call that emits `read_file("src/pool.py")` produces only an unexecuted text string. Of the six phases of a turn (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.08 Anatomy of a Repair Trajectory#^sec-vol3-intro-execution-lifecycle|The six phases of a turn]]**), only the call itself belongs to the model; checking the path, authorizing the read, running it, and returning the observation all belong to the runtime. This loop of model-generated proposals and runtime observations is the interaction pattern formalized by ReAct ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-yao2023react|Yao et al. 2023]]), and every runtime phase depends on knowing what the single model phase delivers.

In a chat window, a human reader spots a response cut off mid-sentence, judges whether a shell command is safe to run, and waits out variable generation delays. An autonomous agent removes that human reader. The runtime receives the response as data and must check in code what a person would judge by eye: whether the prompt fit inside the context window, whether generation finished normally or hit the output token limit, whether a well-formed tool request targets a path inside the allowed workspace, and how much time and budget the call spent. Raw reply text cannot answer those questions; a runtime that guesses call state by scraping output strings will eventually apply a truncated patch or run a command outside its workspace.

Preventing those failures requires an explicit call contract between the agent runtime and the inference service. That contract covers both directions of the call: the outbound request (message history, advertised tool definitions, and token and time limits) and the inbound response record (payload kind, stop reason, normalized status, and token usage). It also fixes the checks the runtime runs before dispatching any proposed action, along with the latency and input-recomputation costs of each call. Rather than assuming the model is reliable, the contract treats the inference service as an untrusted, probabilistic generator and keeps every control-flow decision in the runtime.

The chapter follows the repair agent’s single inspection call from request to bill, adding one runtime obligation at each step. Before the call is sent, the runtime must know who owns which decision ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.03 The Model Call Boundary#^sec-vol3-foundation-model-role|section 2.2]]) and whether the serialized request fits with room left for an answer ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.04 Tokenizing the Request#^sec-vol3-foundation-model-tokenization|section 2.3]]). How the service then produces a candidate ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.05 Autoregressive Generation#^sec-vol3-foundation-model-autoregressive|section 2.4]]) explains why repeated calls differ and why generation can stop before the candidate is whole. That possibility fixes the order of the checks on the way back. The runtime first reads the call’s normalized status to learn whether a complete candidate arrived at all ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-contract|section 2.5]]), then asks which property each check on a completed candidate actually establishes ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^sec-vol3-foundation-model-continuations|section 2.6]]), and finally whether syntax errors can be prevented during generation instead of rejected after it ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.08 Grammar-Guided Decoding#^sec-vol3-foundation-model-grammar-constrained|section 2.7]]). The last two sections price the call. Output length and re-sent history set its latency and work ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-cost|section 2.8]]), and those costs decide how competing output representations should be compared, on accepted repairs under a matched budget ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.10 Comparing Output Interfaces#^sec-vol3-foundation-model-interface-design|section 2.9]]).
