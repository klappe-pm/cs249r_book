# V3-02.08 Grammar-Guided Decoding

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-grammar-constrained

If the repair agent’s `read_file("src/pool.py")` call omits the closing quotation mark before emitting an end-of-turn token, the schema validator in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^tbl-verification-layers|table 3]] catches the malformed JSON and blocks dispatch, but recovering still costs another full round of queueing, prefill, and decoding. Because the request already declares the tool schema ahead of time, the inference engine does not need to wait for an illegal token to arrive at the parser; it can mask out every vocabulary token that would violate the required syntax at each decode step, so a syntax error cannot be sampled in the first place.

**Definition 2.3: Grammar-constrained decoding**

***Grammar-constrained decoding*** restricts next-token selection during autoregressive generation to tokens whose decoded text preserves a viable prefix of a target formal grammar.

1.  **Significance**: Dynamic token masking guarantees that any completed generation sequence strictly satisfies the structural grammar, eliminating syntax errors at the model boundary when the constraint parser covers the target schema.
2.  **Distinction**: Post-generation validation inspects an already emitted sequence and discards invalid payloads after full generation. Constrained decoding actively shapes the vocabulary distribution at every generation step. Even so, neither approach verifies whether a syntactically correct payload contains sensible parameter values or possesses valid execution permissions.
3.  **Common pitfall**: Mistaking a viable prefix for a completed data structure. If token limits, request timeouts, or connection failures truncate generation early, the emitted sequence remains an unfinished prefix that cannot be safely dispatched.

### Legal Prefixes and Completed Structures

^sec-vol3-foundation-model-legal-prefixes

If a model emits an unquoted identifier or a stray comma after `{"path":`, the entire JSON payload breaks and no later token can repair it. To block illegal tokens before they are sampled, the constraint engine keeps a running parse state synchronized with the sequence generated so far. For a schema expecting a string-valued `path` parameter, once `{"path":` appears in the buffer, the grammar allows optional whitespace followed by an opening quotation mark, and forbids unquoted booleans, numbers, or bare identifiers. When the generator emits `{"path":"src/`, the text is a viable prefix:[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn9|⁹]] although incomplete as a JSON document, it can still be completed into a valid object by later string and delimiter tokens. Constrained decoding admits a candidate token only if it can extend the current prefix toward an accepting grammar state.

At generation step ${t}$, let ${q}_t$ represent the parser’s internal state, including nested scope tracking for recursive structures. Let ${\mathcal{V}_{\text{valid}}}({q}_t)$ denote the set of vocabulary tokens whose decoded strings maintain a viable prefix under the target grammar. Because modern language models operate on subword tokens rather than individual characters, a single token can span multiple characters, punctuation marks, or whitespace segments (for example, a single token `.py"}` that finishes the extension, closes the string, and closes the object). The engine must therefore simulate the parser across the token’s full decoded byte sequence to confirm that every character transition is valid.

For each token index ${i}$ in vocabulary ${\mathcal{V}}$, the constraint engine constructs an additive logit mask:

$$
{M}_i({q}_t) = \begin{cases} 0 & \text{if } {i} \in {\mathcal{V}_{\text{valid}}}({q}_t) \\ -\infty & \text{if } {i} \notin {\mathcal{V}_{\text{valid}}}({q}_t) \end{cases}
$$

Adding this mask to the unnormalized logit vector ${\mathbf{z}}_t$ produces the filtered logit vector ${\mathbf{z}'}_t = {\mathbf{z}}_t + {\mathbf{M}}({q}_t)$. At unit temperature, the resulting softmax distribution becomes

$$
{p}_{t, i} = \frac{\exp({z'}_{t, i})}{\sum_{j \in {\mathcal{V}}} \exp({z'}_{t, j})} = \begin{cases} \frac{\exp({z}_{t, i})}{\sum_{k \in {\mathcal{V}_{\text{valid}}}({q}_t)} \exp({z}_{t, k})} & \text{if } {i} \in {\mathcal{V}_{\text{valid}}}({q}_t) \\ 0 & \text{if } {i} \notin {\mathcal{V}_{\text{valid}}}({q}_t) \end{cases} \tag{5}
$$

^eq-vol3-fm-masked-softmax

Setting the logits of invalid tokens to $-\infty$ forces their sampling probabilities to zero, renormalizing the distribution entirely across viable continuations. Once the sampler draws a token from this restricted set, the engine consumes that token’s characters and advances the parser to state ${q}_{t+1}$. This formulation assumes that ${\mathcal{V}_{\text{valid}}}({q}_t)$ remains nonempty and that the sampling configuration respects the mask. The engine applies the mask before top-${k}$ or nucleus truncation so that these filters select among legal continuations. If an implementation instead truncates first and no retained token belongs to ${\mathcal{V}_{\text{valid}}}({q}_t)$, the serving runtime must raise an explicit constraint-satisfaction error rather than silently disabling the mask. Positive finite temperature rescales the remaining probabilities without removing their support.

Recomputing ${\mathcal{V}_{\text{valid}}}({q}_t)$ from scratch at every step would cost a scan of the whole vocabulary per token. For a regular grammar or a flat tool schema with a finite state space, engines compile the schema once into a finite-state automaton whose states each carry a precomputed mask ${\mathbf{M}}({q}_t)$, so that each step is a table lookup followed by a state transition ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-willard2023outlines|Willard and Louf 2023]]). When a grammar allows recursive nesting, such as nested JSON objects or parenthesized expressions, a pushdown stack tracks the open scopes at runtime while precomputed masks still accelerate the lexical transitions at each state. Incremental parsing of this kind yields syntactically valid output even for a language as structured as SQL ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-scholak2021picard|Scholak et al. 2021]]). The automaton in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.08 Grammar-Guided Decoding#^fig-vol3-grammar-constrained-fsm|figure 4]] is compiled for a query tool with two fields, `query` and `limit`, rather than for `read_file`, and the masking mechanism is identical.

![[90 Assets/Volume III/02 Foundation Model/Grammar Constrained Decoding Fsm 84ae5b674a.svg]]

Figure 4: **Grammar-Constrained Decoding**: A tool schema compiles once into an automaton whose states each carry a token mask. At every step the mask sets illegal tokens to $-\infty$ before normalization, so only a legal continuation can be drawn, and the drawn token advances the automaton. The logit values are illustrative: a fluent but illegal continuation can outscore the legal one and still receive zero probability. A precomputed per-state mask suits a finite-state constraint; nested structures need additional parser state. The strip along the bottom lists what the mask leaves unchecked.

^fig-vol3-grammar-constrained-fsm

The resulting guarantee is conditional. The mask keeps every prefix viable, and the engine disallows the end-of-sequence (`<eos>`) token while required fields or closing delimiters remain unwritten, so an output that ends normally belongs to the enforced language. Nothing in the mask makes generation end normally within its token budget.

↪ The automaton behind the token mask, and the induction showing that a constrained output ending in a permitted end token belongs to the grammar, are developed in **[[05 Reference/Volume III - Agentic Systems/V3 Mathematical Foundations#^sec-vol3-appendix-math-dfa|Finite-state constrained decoding]]**.

Consider what happens when an inference request hits its maximum output token limit while emitting arguments, leaving the decoding buffer at `{"path":"src/po`. The string is a viable prefix under the schema, yet the envelope reports `status: TRUNCATED`, and the quarantining rule of [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-status-envelope|section 2.5.2]] applies. A heuristic repair parser that appends the closing quote and brace would fabricate the call `read_file("src/po")`, which the model never finished and which names a file nobody asked for. The mask governs which tokens can appear; it never promotes an interrupted generation to a completed one.

### What a Grammar Mask Guarantees

^sec-vol3-foundation-model-structural-guarantee-scope

Grammar masking moves the first row of [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^tbl-verification-layers|table 3]] into generation and leaves every other row where it was. A masked `{"path":"src/pool.py"}` still names a file that may not exist or may lie outside the grant, because the mask operates strictly on the textual representation and never queries repository state or security policy. Property by property, the mask’s own reach is narrow ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.08 Grammar-Guided Decoding#^tbl-vol3-verification-dimensions|table 4]]).

| Verification dimension    | What the grammar mask establishes                                   | Evidence still required                                       |
|:--------------------------|:--------------------------------------------------------------------|:--------------------------------------------------------------|
| **Syntactic conformance** | All of it for the enforced grammar, once generation accepts         | A `COMPLETED` status, since a legal prefix may be unfinished  |
| **Schema completeness**   | Only the constraints its compiler supports, at accepting completion | A final validation pass against the authoritative schema      |
| **Referential integrity** | Nothing                                                             | Observation of the named resource in the relevant environment |
| **Semantic invariants**   | Nothing                                                             | Checks or judgments covering the task property                |
| **Authorization bounds**  | Nothing; generated text grants no authority                         | A runtime permission decision for the proposed operation      |

Table 4: **Reach of the grammar mask**: A completed constrained output establishes membership in the enforced output language. Every other property keeps the check it needed without the mask.

^tbl-vol3-verification-dimensions

How much a grammar mask guarantees depends on the grammar it compiles. Enforcing a general JSON grammar guarantees only RFC 8259 syntax (balanced braces, legal numbers, and escaped strings) without restricting keys or value types. Compiling a specific JSON Schema into the constraint engine goes further, enforcing required fields, distinguishing integers from floats, and restricting strings to declared regular expressions or enumerations.

Even a schema-aware mask has limits when a schema uses features that cannot be compiled into a finite-state or pushdown automaton. Keywords that enforce cross-field conditionals (`if`/`then`/`else`), unique array elements, or arbitrary lookahead often exceed what precomputed token masks support. Whenever an engine drops unsupported schema keywords, has a bug in its grammar compiler, or parses types differently from the downstream consumer, the guarantee stops holding. The runtime should therefore document which schema features its mask enforces and still run a final check against the authoritative schema before dispatch. Under invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]), logit masking is a mechanical bound below the model: it enforces syntax without the model’s cooperation while leaving authorization and semantic checks above the model.

A strict schema can also force a model to guess when context is missing. If a schema requires a `path` string with no alternative branch, every completed output must supply a path even when the prompt gives no clue which file to inspect. Stripping out every token outside that single object shape leaves the model no way to report that information is missing, so it must invent a plausible path to reach an accepting parser state.

Adding an explicit `unknown` variant or a structured `error` branch to the schema avoids that forced guessing and lets the model report missing context cleanly. Those branches are semantic choices inside the payload, distinct from transport statuses and tool errors. They make an honest report possible without forcing one, since the model can still guess a path when `unknown` is available, or pick `unknown` when the answer is already in the prompt. The runtime therefore handles each branch under the task contract, gathering another observation or asking the user when the model reports uncertainty.

### Learned Formatting and Runtime Constraints

^sec-vol3-foundation-model-learned-formatting-constraints

Fine-tuning a model on tool examples makes well-formed arguments likely but still permits rare syntax slips on long contexts, whereas a grammar mask alone forces valid syntax even when the model has no idea which tool or argument fits the task. The two mechanisms work at different layers and complement each other. Supervised fine-tuning (further training on curated example responses, developed in **[[01 Books/Volume III - Agentic Systems/05 Learning from Trajectories/16 Trajectory Fine-Tuning/V3-16 Trajectory Fine-Tuning#^sec-vol3-fine-tuning|Trajectory Fine-Tuning]]**) and instruction tuning teach models to map prompts onto tool definitions and put high probability on appropriate arguments ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-schick2023toolformer|Schick et al. 2023]]). Runtime logit masking fixes the support of the distribution at each step by setting illegal tokens to zero probability. A model tuned for tool use puts high logits on sensible tokens, and the runtime mask guarantees that sampling noise or long-context drift cannot emit broken syntax. Neither replaces the other: training alone gives no hard guarantee against syntax errors, and a grammar mask supplies no domain knowledge about which file path is right.

Grammar constraints also carry their own costs. Compiling complex regular expressions or nested JSON schemas into deterministic automata consumes CPU time and memory. In dynamic environments where agents construct ad hoc schemas per request, compilation latency can offset the latency saved by avoiding syntax retries. Similarly, tracking parse states and computing masks across large vocabularies ($|{\mathcal{V}}| \ge 128{,}000$ tokens) adds per-token decoding overhead unless supported by precomputed lookup indices or bitmasks applied on the accelerator. Eliminating syntax retries lowers total cost only when compilation, mask memory, and per-token mask work together cost less than the retries they replace.

**Checkpoint 2.2: Evaluating schema-constrained decoding**

A repair agent uses constrained decoding for file-reading proposals. Its runtime records response kind and invocation status separately.

**Completion**: If an output ceiling interrupts a legal JSON prefix, can you explain why grammar masking does not permit dispatch of the fragment?

**Constraint scope**: If a completed request satisfies the schema but names a nonexistent file, can you identify which property was enforced and which observation is still needed?

**Response variants**: A completed, schema-valid response selects the `unknown` variant. Decide what the runtime does next, and name the observation it should obtain before calling the model again.

**Combined mechanisms**: Can you explain why a model trained for tool use can still benefit from runtime masks without either mechanism granting execution authority?

Constrained decoding removes one class of syntax failure before dispatch, but a structurally valid invocation still needs enough budget to finish and external evidence to justify execution. Whether a mask pays for itself, and what any call costs at all, depends on how prompt processing and token generation consume time on the serving hardware.
