# V3-02.04 Tokenizing the Request

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-tokenization

Once the repair agent appends the `src/pool.py` excerpt and a compiler diagnostic to its message history, every piece of the request (role delimiters, tool schemas, system instructions, file paths, and source lines) serializes into a single sequence of discrete tokens before entering the model. Whether the next call fits the context window depends on the token count of that fully assembled sequence, plus the output room reserved for the reply, measured strictly against the target model’s tokenizer and wire format.

### Tokens in the Serialized Request

^sec-vol3-foundation-model-serialized-request-tokens

Leading indentation or an unusual identifier in `src/pool.py` can change the prompt’s token count even when a character counter or source-code lexer sees the same program structure, because a model’s **tokenizer** slices text into vocabulary identifiers whose boundaries rarely match words, identifiers, or JSON fields. Subword methods represent common fragments compactly while splitting unfamiliar words and identifiers into smaller pieces ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-sennrich2016subword|Sennrich et al. 2016]]). **Byte-pair encoding** (BPE)[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn2|²]] learns repeated combinations of smaller units; other tokenizers use different segmentation rules, and some learn them directly from raw text without assuming word boundaries ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-kudo2018sentencepiece|Kudo and Richardson 2018]]). Because a single token may represent a word, part of a word, whitespace, punctuation, or a combination of these, small formatting changes alter the token sequence.

Indentation alone alters the resulting sequence. Under one widely used byte-pair vocabulary, `cl100k_base`, for example, the unindented line `def get_user_id():` encodes as five tokens beginning with `def` (identifier 755). Indenting that exact line by four spaces yields six tokens: three leading spaces (262), followed by `def` with the fourth space fused to the keyword (711), and finally the remaining four tokens. A compiler lexer records indentation as block structure and emits the same keyword token at both levels; the model instead receives a different opening sequence of integer identifiers, with only the four tokens after the keyword shared ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.04 Tokenizing the Request#^fig-vol3-token-ast-mismatch|figure 2]]).

![[90 Assets/Volume III/02 Foundation Model/Token Ast Mismatch e5bd4fc6a1.svg]]

Figure 2: **One Keyword, Two Token Sequences**: The same Python line, unindented and indented by four spaces, drawn on one character grid, with a compiler lexer’s tokens above the characters and a byte-pair tokenizer’s tokens below. ^fig-vol3-token-ast-mismatch

In an inspection request, the string `src/pool.py` is a single path argument at the tool interface, yet it splits into several subword tokens at the model interface. Changing a file path, adding indentation, or escaping source code inside JSON shifts token boundaries in ways a fixed character-to-token ratio cannot predict. Neither JSON framing nor punctuation adds a constant fraction of tokens over plain prose, so the runtime must tokenize the exact byte sequence it plans to send.

Wire framing adds further tokens beyond the visible text. Model APIs wrap messages in control tokens that mark roles, turn boundaries, and tool schemas. Counting only the user prompt or tool output misses that wrapper. When the runtime formats the wire payload locally, it must run the model’s own tokenizer over the complete formatted sequence; when a remote service applies its own chat template or hidden system wrapper, the runtime must use the provider’s token-counting endpoint and admission rules. Because vocabularies and merge tables differ across model families, a token count from one model does not carry over to another.

The same count applies to generated output. A compact tool call uses fewer output tokens than a long prose explanation wrapping the same call, though the exact count depends on how the call is serialized. Shorter schemas cut latency and token spend only when they keep the fields the runtime needs; dropping required arguments, file paths, or error variants to save a few tokens makes downstream execution brittle.

### Output Headroom

^sec-vol3-foundation-model-output-headroom

A prompt that fits inside the context window can still leave too little room for the model to finish its reply, cutting off a tool call mid-argument. To prevent a long prompt from starving the response, the admission check must reserve **output headroom** before sending the call. Let ${S}$ denote the length of the fully serialized input prompt, ${S_{\max}}$ the total **context window** (the maximum sequence capacity spanning input and output tokens within a single invocation), and ${K_{\max}}$ the reserved generation allowance. Where input tokens and generated tokens share a unified context budget, an admission check must enforce:

$$
{S} \le {S_{\max}} - {K_{\max}} \tag{1}
$$

^eq-vol3-fm-admission

This inequality guarantees that an incoming prompt cannot fill the context buffer and leave the model no room to answer. Many services also cap input and output lengths separately alongside the shared window, so the runtime must satisfy both the individual caps and the combined bound. Reasoning models add another wrinkle: they emit intermediate reasoning tokens before the visible answer, and those hidden tokens count against ${K_{\max}}$ even when the caller never sees them. A three-line visible reply can exhaust a generous output allowance if the model spent hundreds of hidden reasoning tokens first.

↪ How reasoning models spend generated tokens on intermediate work, and how the runtime budgets them, is developed in **[[01 Books/Volume III - Agentic Systems/01 The Model/03 Test-Time Compute/V3-03.03 Three Axes of Test-Time Compute#^sec-vol3-test-time-compute-reasoning-models|How reasoning models spend output allowances]]**.

Suppose the repair interface has a combined window of 8,192 tokens, and the runtime reserves 1,024 tokens for generation. Its input ceiling is ${S_{\max}} - {K_{\max}} = 8,192 - 1,024 = 7,168$ tokens. If the fully serialized request occupies 6,000 tokens, $7,168 - 6,000 = 1,168$ tokens of room remain for additional input while preserving the response allowance. The limits are scenario values, not a named model’s specification.

If an incoming tool observation exceeds this remaining headroom, the admission check fails. The runtime can then compress prompt history, extract a narrower file slice, or route the call to an execution profile with a larger context window. Shrinking the output allowance ${K_{\max}}$ to force admission is risky, as it leaves the model insufficient room to complete complex tool invocations or structured plans. Similarly, silently truncating tool outputs to squeeze them into the remaining margin can strip away the critical stack trace or diagnostic error that the agent needs to resolve the bug.

Even when a request satisfies admission checks, generation can still hit the output token ceiling mid-stream. The runtime must never confuse a syntactically well-formed prefix with a successfully terminated generation. A truncated JSON object may happen to pass a lenient parser if closed artificially, yet it remains an incomplete execution plan. While a partial payload provides valuable diagnostic telemetry, executing it as an intact tool call can cause downstream corruption. The invocation contract in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-contract|section 2.5]] turns this boundary into an explicit rule that reads the call’s status before its payload.

### Counting Multimodal Inputs

^sec-vol3-foundation-model-multimodal-accounting

Attaching a screenshot of a failing dashboard or user-interface (UI) render to a repair request can push a prompt that fit in text well past the context limit. A vision front-end maps each image into a sequence of context positions, and although vision transformers slice images into uniform patches ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-dosovitskiy2021image|Dosovitskiy et al. 2021]]), preprocessing steps such as dynamic tiling, resolution scaling, and spatial pooling mean the billed token count rarely equals a simple patch count.

Consider the earlier budget when adding this visual artifact. If the service reports that the image and its framing tokens require an additional 2,048 context positions, the total request demand expands to $6,000 + 2,048 + 1,024 = 9,072$ tokens. This total exceeds the 8,192-token context window by 880 tokens, triggering an immediate admission failure before dispatch. The runtime must step in before calling the model. Downscaling the image cuts its token count under some vision backends, but heavy compression can blur single-character error codes or fine trace lines. Budgeting multimodal inputs therefore trades visual detail against the context ceiling.

**Checkpoint 2.1: Admitting the next repair request**

The repair agent is about to add a source excerpt and a diagnostic image to its next call. Its output allowance must remain available for a complete proposal.

**Input budget**: Can you identify which message and tool-definition framing must be counted beyond the visible source excerpt?

**Output headroom**: With the window fixed at 8,192 tokens and the image added, would halving the output reservation make the request fit? Compute the remaining excess, and state what the smaller reservation risks.

**Generation status**: If a returned fragment parses successfully after the output limit is reached, can you explain why it is still not a completed candidate?

Token accounting checks upfront that the full request fits with room reserved for the reply. Admission, however, covers only starting capacity. Once decoding begins, token-by-token autoregressive generation determines how that reserved headroom is spent and whether the call finishes cleanly or stops mid-stream.
