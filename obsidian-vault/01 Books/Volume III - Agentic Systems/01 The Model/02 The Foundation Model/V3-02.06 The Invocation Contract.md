# V3-02.06 The Invocation Contract

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-contract

When a repair call hits its output token limit after emitting `read_file("src/pool")` instead of `read_file("src/pool.py")`, or when a local deadline expires while the remote server keeps decoding and billing tokens, raw reply text cannot tell the runtime what happened. Both strings parse as valid arguments, and an empty socket says nothing about remote execution. To keep how a call ended attached to what it returned, the host runtime pairs each outbound request specification with a normalized inbound response envelope so that every remote generation is governed by a single contract.

**Definition 2.2: Model invocation contract**

***Model invocation contract*** is the pair of records that bounds one model call: a request fixing the input, model configuration, sampling settings, and enforced output and time limits, and a normalized envelope reporting the call’s status, payload, and resource use.

1.  **Significance**: The contract establishes each model call as a distinct, countable unit within an agent trajectory. Its usage record prices the call’s share of ${C_{\text{attempt}}}$, and its status flag isolates completed generations from partial or failed calls. Consequently, the cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**) can be computed from recorded telemetry rather than heuristically reconstructed from conversation transcripts.
2.  **Distinction**: The invocation contract describes the model call rather than the overarching task. A generated tool request can fully conform to decoding limits without ever being dispatched, and a fully generated response can fail downstream validation. Dispatch authorization, tool execution, and task-level acceptance remain separate runtime decisions backed by their own evidence.
3.  **Common pitfall**: Recording only the payload text. Without explicit status flags and usage accounting, a truncated fragment is indistinguishable from an intentional short response, and unrecorded token consumption silently distorts operational cost accounting as zero-cost execution.

### What a Request Specifies

^sec-vol3-foundation-model-request-specification

Leaving any part of a model request implicit, such as an unpinned model alias that silently updates, an unenforced token cap, or an unrecorded sampling setting, makes it impossible to price the call or explain why its behavior changed. At the generation interface, the bounded request fixes six fields:

$$
{\mathcal{R}} = \langle {\mathbf{x}}, \text{ModelID}, {K_{\max}}, {T_{\text{deadline}}}, {\mathcal{S}_{\text{stop}}}, {\boldsymbol{\Theta}_{\text{sample}}} \rangle
$$

The first field, ${\mathbf{x}} = ({x}_1, {x}_2, \dots, {x}_{{S}})$, encodes the serialized messages, role markers, advertised tool schemas, and formatting delimiters visible to the model, which the runtime builds from structured `messages` and `tools` inputs before serialization. Once the input sequence is fixed, `ModelID` and ${\boldsymbol{\Theta}_{\text{sample}}}$ specify how the serving stack evaluates it. `ModelID` names the model weights and serving deployment selected through `model_config`, where engineers distinguish mutable provider aliases (such as `model-latest`) from pinned, immutable revisions (such as dated or content-addressed snapshots). The sampling parameters ${\boldsymbol{\Theta}_{\text{sample}}}$, including temperature and top-${p}$, then fix the selection rule used during decoding. Together with the serialized input and returned output, those fields document the call; exact regeneration also depends on the serving path, as war story [2.1](https://mlsysbook.ai/vol3/02_foundation_model/02_foundation_model.html#ws-02-anthropic-serving-bugs-2025) showed.

To bound how long that generation may run, the request pairs an output allowance ${K_{\max}}$ with a local waiting deadline ${T_{\text{deadline}}}$. Because a system cannot rely on the model to stop on time, invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) places both limits below the model, where the host runtime and serving system enforce them mechanically. Before sending the call, the runtime checks that the prompt and output allowance fit inside the context window, and the adapter notes whether the provider bills hidden reasoning tokens against ${K_{\max}}$, since counting only visible text would understate what the call spent.

Generation can also end before reaching ${K_{\max}}$ when the output matches one of the stop sequences in ${\mathcal{S}_{\text{stop}}}$, which halt decoding as soon as the serving engine encounters them. Because the engine matches raw byte or character sequences without parsing structure, a stop sequence that appears inside an argument or quoted string can cut off generation before the closing quotes or braces are emitted. The runtime must therefore record the provider’s stop reason and validate syntax separately.

Resource limits are enforced in two places: on the client host and on the remote serving cluster. Locally, the host runtime caps incoming response bytes and stops waiting when the deadline ${T_{\text{deadline}}}$ expires. A local timeout ends the caller’s wait and marks the call failed, but it does not prove that the remote server stopped decoding or freed accelerator memory.[[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.16 Footnotes#^fn7|⁷]] Server-side token caps and cancellation protocols handle the remote side, so every limit should state which component enforces it and which resource it bounds.

### The Normalized Status Envelope

^sec-vol3-foundation-model-status-envelope

If a runtime inspects only the returned text or tool arguments, a partial string cut off by a token ceiling looks just like a finished proposal. To keep how a call ended attached to what it returned, the runtime wraps every response in a **normalized status envelope**:

$$
{\mathcal{N}} = \langle \text{status}, {\mathbf{y}}, {\mathbf{m}} \rangle
$$

Here, ${\mathbf{y}}$ is the returned payload, which may be complete, partial, or empty, and ${\mathbf{m}}$ holds the call’s telemetry: the response `kind`, the raw provider `stop_reason`, reported token `usage`, request identifiers, latency timestamps, and serving settings. Keeping ${\mathbf{y}}$ paired with ${\mathbf{m}}$ prevents downstream code from reading the payload without its status, and records unreported usage as unknown rather than zero.

Because different model APIs report stop reasons, error codes, and transport failures in incompatible ways, the runtime adapter maps provider-specific signals onto the seven normalized statuses in [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^tbl-vol3-invocation-status|table 2]]. Two of them, `REJECTED` and `CANCELED`, occur only while a response is streaming ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^sec-vol3-foundation-model-streaming-cancellation|section 2.5.3]]). Each status records what the host runtime verified locally; if two events race, such as a local cancellation crossing an incoming completion frame, the adapter resolves the status deterministically while keeping the raw provider signals in ${\mathbf{m}}$.

| Status flag         | Terminal condition                                                               | Payload integrity                                                              | Admissible host action                                               |
|:--------------------|:---------------------------------------------------------------------------------|:-------------------------------------------------------------------------------|:---------------------------------------------------------------------|
| `COMPLETED`         | Confirmed normal generation termination within the call’s limits                 | Fully generated according to the protocol; syntax and meaning remain unchecked | Admit to candidate validation, not directly to dispatch              |
| `TRUNCATED`         | Generation reaches a token or context ceiling before confirmed normal completion | Incomplete candidate that may nevertheless parse                               | Withhold from action; record the limit and diagnose                  |
| `REFUSED`           | The model or service explicitly declines the request or response                 | Refusal notice, partial content, or no payload                                 | Handle under the task’s refusal policy; do not treat as an action    |
| `TRANSPORT_FAILURE` | Delivery fails or the local deadline expires without accepted completion         | Missing or partial content; remote outcome may be unknown                      | Record uncertainty and apply bounded failure handling                |
| `REJECTED`          | A runtime monitor rejects the response during reception                          | Content observed before rejection                                              | Withhold from action; record the rejection and request cancellation  |
| `CANCELED`          | Discretionary runtime or operator cancellation before accepted completion        | Partial, missing, or otherwise unusable as a completed candidate               | Stop local candidate processing; track remote termination separately |
| `FAULTED`           | The service reports an execution failure                                         | Missing, partial, or diagnostic content                                        | Record the reported fault and route to failure handling              |

Table 2: **Normalized invocation status envelope**: Status controls admission to the candidate path. Completion is a generation outcome, while authorization, tool execution, and task acceptance remain separate decisions.

^tbl-vol3-invocation-status

For a `read_file` request, `kind="tool_request"` tells the runtime which schema to check, while `status="COMPLETED"` confirms that generation finished normally. Neither field says that the tool ran or that the file read succeeded; completion describes generation, whereas tool execution and task acceptance are separate runtime decisions.

Applying invariant closure (principle [[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.06 Invariant Closure#^pri-invariant-closure|1]]) to the status field gives a hard gate: the **quarantining rule**. Under this rule, no payload whose status is anything other than `COMPLETED` may enter the candidate validation or tool-dispatch path. The runtime checks `status` before parsing or dispatching the payload. It can log an interrupted or malformed fragment for diagnosis, but that log entry cannot trigger a tool call or be promoted to a finished proposal. When later chapters sample several candidates for one task, any candidate cut off by a token limit obeys the same rule: a truncated payload is a diagnosable failure, never a partial action.

A destructive shell command shows why parsing alone cannot replace this status check. Suppose the complete intended command is

``` bash
rm -rf /tmp/scratch/cache_dir
```

If an exhausted token quota cuts off generation mid-path, the prefix is

``` bash
rm -rf /tmp/scratch
```

That truncated prefix is valid shell syntax, yet it deletes the entire parent directory. Because the envelope marks the call `TRUNCATED`, the quarantining rule blocks the command before it reaches the shell. Conversely, `status="COMPLETED"` grants no permission to run; it establishes only that the model finished emitting its proposal. [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^lst-vol3-completed-candidate-gate|Listing 3]] implements this admission check, passing only completed generations to the candidate path while leaving syntax, permissions, and task verification to later stages.

``` python
def completed_candidate(envelope):
    if envelope["status"] != "COMPLETED":
        raise ValueError("Response is not a completed candidate")
    # Syntax, permission, and task evidence remain unchecked.
    return envelope["payload"]
```

Listing 3: **Completed-candidate admission**: The status check admits only completed generations to the candidate path. Returning the payload grants no execution authority.

^lst-vol3-completed-candidate-gate

Incomplete payloads go to a diagnostic log with its own storage and access limits, keeping the partial byte stream and `stop_reason` for debugging. “Repairing” a truncated fragment by appending guessed arguments or closing braces invents a new candidate that the model never completed, and such patched fragments must never be marked `COMPLETED`.

### Streaming and Cancellation

^sec-vol3-foundation-model-streaming-cancellation

Waiting for a four-thousand-token response to finish before checking its structure wastes seconds of accelerator time when the first key violates the tool schema. **Streaming** delivers response fragments over the connection as generation proceeds, letting the runtime inspect prefixes early, provided its parser follows the provider’s framing protocol rather than assuming each network chunk holds one token. When an arriving prefix violates the required format, the stream monitor stops waiting immediately instead of buffering the rest of an unusable reply. Because generation is still in flight, the monitor checks whether the prefix can still be completed into a valid structure, not whether it is already complete.

Rejection and cancellation are distinct events. When the stream monitor spots a structural violation, the runtime sets the status to `REJECTED` and sends a cancel request to the service. When an operator or runtime policy aborts a compliant stream before completion, the runtime marks the status `CANCELED`. A local deadline that expires before completion maps instead to `TRANSPORT_FAILURE` ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^tbl-vol3-invocation-status|table 2]]), after which the runtime may also send a cancel request. Keeping the partial payload out of tool dispatch is a local guarantee the host enforces in all three cases. Stopping the remote decode loop and freeing accelerator memory, however, depends on the serving engine honoring the cancel signal; merely closing a client socket does not prove that remote decoding stopped.

Consider a call with an output allowance of 4,096 tokens whose stream validator detects a schema violation at step ${t_{\text{cut}}} =$ 96. The runtime’s part of the response finishes at once. It records the rejection, discards the partial proposal, and sends a cancel request. The service’s part depends on whether that request is honored ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.06 The Invocation Contract#^fig-vol3-streaming-cancellation|figure 3]]).

![[90 Assets/Volume III/02 Foundation Model/Streaming Token Cancellation 9601cbe94b.svg]]

Figure 3: **Reject, Then Cancel**: The runtime’s stream validator advances a parser state as each prefix arrives and holds the output rather than acting on it. At step 96 the proposal introduces a key outside the schema, so the runtime records a rejection, discards the partial proposal, and sends a cancel request. The runtime outcomes on the left hold regardless of the service; the service outcomes on the right hold only if the service receives and honors the cancel request.

^fig-vol3-streaming-cancellation

The skipped-step count shown is an upper bound that requires provider cooperation. If the serving engine processes the cancellation promptly, it skips up to ${K_{\max}} - {t_{\text{cut}}} =$ 4,000 autoregressive decode steps. In the reference unbatched deployment, each plain autoregressive decode step reads the model weights from accelerator memory, so the step takes at least the weight bytes divided by the memory bandwidth; for the reference deployment of [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-cost|section 2.8]], that floor is 21.075 ms per generated token. At that reference floor, skipping all these steps avoids 84.3 s of estimated decode work. An honored cancellation also frees the request’s slot among the requests the serving engine decodes together and releases the call’s KV-cache allocations. If the remote service fails to honor the cancellation, the host runtime still quarantines the rejected payload locally, but the remote service may continue generating up to its token allowance.

Nonstreaming calls apply the same status gate once the whole response arrives. Streaming moves the check earlier in the call so the runtime can reject bad prefixes and reclaim resources sooner, without relaxing the rule that incomplete prefixes never run. Either way, the status gate settles only whether a complete candidate arrived. A `COMPLETED` `read_file` proposal can still name a missing file or a path outside the workspace, so the next question is what each subsequent check on that candidate actually proves.
