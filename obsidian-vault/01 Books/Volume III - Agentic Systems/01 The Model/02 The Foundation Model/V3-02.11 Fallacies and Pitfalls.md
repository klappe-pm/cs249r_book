# V3-02.11 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-fallacies

A code repair request can return promptly yet name the wrong file, or return the right patch long after its latency budget has expired. In autonomous execution loops, engineers frequently conflate distinct operational boundaries, confusing inference execution with total round-trip latency, syntactic validity with semantic correctness, and transport success with task completion. These failures expose several persistent mistaken assumptions about the model call.

**Fallacy**: *One model response has a fixed cost.*

Output length drives most of the execution time in the unbatched interface comparison. At its reference hardware floors, decoding a single output token takes far longer than reading a prompt token in parallel. Regenerating a whole file takes 39.6 s, whereas emitting a localized patch for the same bug takes 2.3 s, a 17.5× speedup that comes almost entirely from generating fewer tokens ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-cost|section 2.8]]). Engineers must therefore budget input and output tokens separately rather than treating a model call as a fixed unit of work. Wall-clock budgets must also cover queueing and network transit; setting `max_output_tokens` caps how many tokens the model generates, not when the reply arrives.

**Pitfall**: *Treating a completed invocation as a completed task.*

A status of `COMPLETED` says only that the serving engine finished generating tokens within the call’s limits; it does not mean the output is right or even usable. In the interface comparison, every localized edit finished on time, yet only 57 percent of those trials produced patches that passed the repair checks. Conversely, a call cut off at the token ceiling can still leave a syntactically valid file path, which is why the runtime must check completion status before acting on the payload. Every call record needs two separate facts: whether a complete candidate arrived from the service, and whether independent checks confirm that it satisfies the task contract.

**Fallacy**: *Valid JSON means a safe and correct tool call.*

A JSON object passes schema validation whenever its fields match the declared types, whether the payload is safe, authorized, or sensible. A tool call with a string `path` passes schema checks whether that path names the intended file, a stale file, or a sensitive directory outside the workspace. As [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.07 Checking Candidate Outputs#^tbl-verification-layers|table 3]] shows, schema validation checks structure, while permission gates and task checks govern safety and correctness. The same gap holds for behavioral checks: a test runner with a false-accept rate of 0.65 on defective patches still leaves 14.37 percent of its passing candidates defective under the assumed rates. Even under grammar-constrained decoding, a call cut off at the token limit remains an unfinished fragment even though every token emitted before truncation was legal.

**Pitfall**: *Collapsing every unsuccessful outcome into the same retry.*

Retrying a failed call with the exact same request repeats the cause of the failure when the fault is not transient. If a whole-file request misses a 15 s deadline, resending the identical prompt spends another 39.6 s of estimated work only to time out again, while the first call may still be running and billed on the server, since a local timeout leaves the remote outcome unknown. Likewise, a call that hits `max_output_tokens` will truncate at the same limit on retry, and a safety refusal will refuse again. Instead of treating every failure like a dropped packet, the runtime should route on the normalized status: bounded backoff for transient service faults, a larger output allowance or more compact output format for truncation, and a fresh file read when an edit anchor fails to match. **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/12 Failure Recovery/V3-12.05 Forward Recovery#^sec-vol3-failure-recovery-recovery-actions|Recovery actions and evidence]]** develops which recovery action fits each failure class.

↪ The idempotency rules that decide when a timed-out call may be repeated are developed in **[[01 Books/Volume III - Agentic Systems/03 Tool Use/07 Tool Calling/V3-07.06 Retrying Uncertain Actions#^sec-vol3-tool-calling-idempotency|Retrying Uncertain Actions]]**.

**Fallacy**: *Greedy decoding makes a served call reproducible.*

Greedy selection fixes the token choice for a given logit vector, but the serving infrastructure computes that vector, and two distinct causes can change it. The first operates even on a healthy serving path, where batch-dependent floating-point reduction order shifts closely contested logits in their least significant bits, enough to flip an argmax and redirect every later token. The second is a change to the serving path itself. In war story [2.1](https://mlsysbook.ai/vol3/02_foundation_model/02_foundation_model.html#ws-02-anthropic-serving-bugs-2025), misrouting and a miscompiled top-${k}$ operation changed model outputs for identical requests, affecting 16 percent of one model’s requests at peak impact, so an identical prompt succeeded on one attempt and failed on the next. Pinning the temperature addresses neither cause. Systems engineers should record the model revision and serving configuration with every invocation, and replay recorded responses whenever the goal is to reproduce downstream runtime behavior deterministically.

Each of these traps blurs two separate runtime records: token usage measures spend, completion status tracks whether generation finished, schema validation checks form, and acceptance tests check the result. Keeping those records separate lets higher-level loops compose single model calls without mistaking a clean response envelope for a working repair.
