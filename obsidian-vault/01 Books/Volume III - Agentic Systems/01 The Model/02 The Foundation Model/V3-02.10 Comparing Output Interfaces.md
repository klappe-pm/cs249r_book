# V3-02.10 Comparing Output Interfaces

[[Home|Home]] · [[01 Books/Volume III - Agentic Systems/Volume 3 Overview|Volume Overview]] · [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02 The Foundation Model|V3-02 The Foundation Model]]

^sec-vol3-foundation-model-interface-design

When the repair agent proposes a fix to the connection-pool locking logic in `src/pool.py`, its output payload does not need to repeat the entire source file. The model could emit a fully rewritten file, or it could target a specific code block and emit only the replacement text. Emitting a localized edit consumes far fewer generation tokens by omitting unchanged code, but it creates an operational dependency: the execution runtime must locate the exact target coordinates in the target file. The interface therefore determines both the computational cost of generating a candidate and the operational preconditions required for the runtime to apply it.

High schema parse rates alone cannot validate an interface design. A whole-file replacement might parse into valid JSON yet arrive long after the service deadline because the model spent tens of seconds generating unchanged lines. Conversely, a compact diff might arrive in about 2.3 s yet fail to match its target anchors against current repository state. Neither outcome delivers an accepted repair. A rigorous empirical comparison must track the model call’s completion status, account for all compute resources consumed across retries, and validate the resulting artifact against uniform acceptance criteria.

### Three Choices in an Output Interface

^sec-vol3-foundation-model-interface-design-dimensions

When a patch interface fails in production by timing out on long files, missing its target lines, or breaking JSON syntax, teams often swap the entire prompt format at once and cannot tell whether edit granularity, wire framing, or decoding constraints caused the failure. Because those three choices are independent, diagnosing a failure or comparing designs requires varying one dimension at a time.

The first choice, *edit granularity*, sets how much text the model must emit to describe a change. At one end, a whole-file format returns the entire file, regenerating hundreds of untouched lines alongside the edit. At the other end, a localized edit supplies only a target locator and the replacement lines. An anchored search-and-replace block, for instance, gives an exact snippet of source text to find and the new text to substitute; if that anchor snippet is missing from the file or appears more than once, the runtime cannot apply the edit uniquely. Rewriting the whole file avoids anchor mismatches, but forces the runtime to check that the model did not accidentally delete unrelated functions or overwrite concurrent edits.

Regardless of which granularity the interface chooses, *serialization framing* remains an independent decision. Either edit size can be wrapped in JSON (one schema carrying a path and full file body, another carrying a path, search snippet, and replacement block) or framed with Markdown code fences or unified diff headers. Token overhead comes from the tokenizer’s vocabulary and the wrapper markers, not from whether the outer wrapper is JSON or diff syntax; emitting thousands of tokens for an unchanged file is the price of whole-file granularity, not of JSON.

How the runtime enforces that framing, the *constraint mechanism*, is independent of both granularity and wire syntax. An engineer can get structured outputs through fine-tuning, few-shot examples in the prompt, or grammar masking during decoding, and can combine them by running a fine-tuned model under a grammar mask. As [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.08 Grammar-Guided Decoding#^sec-vol3-foundation-model-grammar-constrained|section 2.7]] showed, a grammar mask guarantees grammatical form, not valid targets or working code: it cannot ensure that an anchor snippet exists in the file or that the edit fixes the race condition. Changing serialization and decoding constraints at the same time tests a bundle of choices rather than isolating which change helped.

### Matched-Budget Comparison

^sec-vol3-foundation-model-matched-budget-comparison

Giving a brittle diff format free retries whenever its output fails to parse, or dropping timed-out whole-file calls from the denominator, makes a weak interface look more accurate than it is. A fair comparison holds every condition fixed except the interface itself. In the connection-pool repair benchmark, every trial starts from the same repository snapshot and defect description, under the same model weights, sampling parameters, tools, acceptance tests, resource ceilings, and retry policy. Matched budgets do not require equal token consumption, because prompt overhead and response length are properties of the interface under test; they require identical operating limits and accounting rules.

↪ Matched-budget comparison of complete agent policies, charging every initiated trial to the cost per accepted task, is developed in **[[01 Books/Volume III - Agentic Systems/04 The Agent Runtime/13 Agent Evaluation/V3-13.06 Statistical Evaluation Rigor#^sec-vol3-evaluation-matched-budgets|Matched-budget comparison]]**.

Two deadlines bound the comparison. The invocation deadline ends when the runtime receives and normalizes the model’s response. The task deadline also covers parsing, patching, compilation, and tests, and every retry, unparsable output, and failing run draws against it. A benchmark that grants free retries after malformed responses therefore subsidizes the brittle interface.

The harness also records each intermediate stage separately from final acceptance ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.10 Comparing Output Interfaces#^tbl-vol3-interface-evaluation|table 5]]). Every initiated trial stays in the denominator of the top-level success rate, because discarding unparsable responses or timed-out calls inflates reported accuracy. Conditional rates, such as the share of applied edits that pass tests, remain useful diagnostics when they state their filter explicitly.

| Measurement         | What the trial records                                                                       | What it does not establish                                 |
|:--------------------|:---------------------------------------------------------------------------------------------|:-----------------------------------------------------------|
| Invocation outcome  | Completion status, elapsed time, and token usage                                             | That a delivered candidate is valid                        |
| Structural validity | Whether a completed payload parses and satisfies the required schema                         | That its values describe the current environment           |
| Applicability       | Whether the authorized edit identifies its target and can be applied to the expected version | That the resulting program repairs the defect              |
| Acceptance evidence | Results of the same required checks on the resulting artifact                                | Correctness beyond the checks’ coverage                    |
| Resource use        | All calls and checks charged to the trial, including failed attempts                         | A benefit unless accepted outcomes justify the expenditure |

Table 5: **Interface evaluation measurements**: Distinct observations prevent a formatting improvement from being mistaken for a task-level improvement. The same task fixtures, acceptance standard, and resource ceilings govern each design.

^tbl-vol3-interface-evaluation

Latency measurements also need their serving conditions. Cache hits, batching contention, and queueing change observed wall-clock time at fixed prompt and completion lengths, so a few favorable measurements during quiet periods do not establish deadline reliability; tail latency decides deadline violations in shared clusters ([[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.15 Source References#^ref-dean2013tail|Dean and Barroso 2013]]). The engineering question is whether a representation leaves enough headroom under the tail of the latency distribution to generate and validate a candidate fix.

### Choosing an Edit Format Under a Deadline

^sec-vol3-foundation-model-deadline-representation-choice

When a repair call must finish inside a fifteen-second deadline, asking the model to rewrite an entire source file spends almost the whole budget copying unchanged lines before a single test can run. The per-token floors of [[01 Books/Volume III - Agentic Systems/01 The Model/02 The Foundation Model/V3-02.09 The Cost of a Model Call#^sec-vol3-foundation-model-per-call-work-estimate|section 2.8.2]] put a concrete price on that unchanged text, and that price falls on edit granularity rather than on the outer wrapper format.

![[90 Assets/Volume III/02 Foundation Model/Representation Deadline Margin b4f2119427.svg]]

*Two horizontal bars against a dashed red 15 s deadline line with a pale red zone beyond it. Whole file: a thin light-blue prompt segment and a long dark-blue output segment totaling 39.6 s. Local edit: short segments totaling 2.3 s, with a leader labeling its light segment as prompt.*

*Generating unchanged code, not reading the prompt, pushes the whole file past the deadline.*

**Napkin Math 2.3: A repair representation under an invocation deadline**

**Problem**: A repair invocation begins with 8,000 baseline context tokens and operates under an invocation deadline of 15 s. Emitting a whole-file replacement requires 350 additional instruction tokens and 1,850 output tokens. Emitting a localized edit requires 120 additional instruction tokens and 80 output tokens. These token counts represent scenario parameters. Using the prefill and autoregressive decoding rates established earlier, which interface representation fits within the simplified service-work budget?

**Math**: The service-work model charges prompt prefill at 71.35 μs per token and autoregressive decoding at 21.075 ms per token. To isolate inference execution, this baseline calculation omits request serialization, network transit, server-side queueing, and subsequent validation runs. Multiplying each interface’s token profile by these unit costs yields:

$(8,000+350)\times 0.00007135\,\text{s}+1,850\times 0.021075\,\text{s}\approx 39.58\,\text{s}$

$(8,000+120)\times 0.00007135\,\text{s}+80\times 0.021075\,\text{s}\approx 2.27\,\text{s}$

The whole-file estimate exceeds the deadline by a wide margin, whereas the localized edit finishes well within the allocated budget. The localized representation provides a 17.5× reduction in estimated service work, with token decoding accounting for 98.5 percent of the whole-file latency. In production, normalized invocation outcomes and observed wall-clock times determine whether the candidate arrived before deadline expiration.

To evaluate downstream yield, consider a second hypothetical scenario where localized edits complete on time with valid syntax, but only 95 percent resolve to an applicable edit on the codebase. Among those applicable edits, assume 60 percent pass the required test suite. The fraction of all initiated trials that yield an accepted repair is:

$0.95\times 0.60=0.57$

This 57 percent yield is the product of the applicability rate and the conditional test-pass rate, requiring no independence assumption between stages. Invocations that miss deadlines or emit invalid syntax reduce this end-to-end yield even further.

**Systems insight**: When output generation threatens an invocation deadline, shrinking representation granularity is the primary engineering lever. Because autoregressive decoding is memory-bandwidth bound, each generated token costs roughly 295 prompt prefill tokens at hardware reference floors (principle [[01 Books/Volume III - Agentic Systems/01 The Model/V3 Model Principles#^pri-vol3-memory-bandwidth-decoding|2]]). Whole-file generation squanders almost all of its 39.6 s runtime emitting unchanged code, while the localized edit meets the deadline with a 6.6× safety margin. However, compact representations trade decoding latency for applicability risk: localized edits require exact anchor matching, which restricts the passing yield to 57 percent in this scenario. That hypothetical yield forms the acceptance probability ${p_{\text{acc}}}$ that governs the amortized cost per accepted task (**[[01 Books/Volume III - Agentic Systems/00 Introduction/01 Introduction/V3-01.07 Reliability and Cost Over a Horizon#^eq-vol3-cost-per-accepted-task|equation 1.2]]**).

The call deadline acts as a hard filter: under these timing numbers, a whole-file response misses the cutoff before any test can run, so its code quality never comes into play. If the deadline is relaxed past the whole-file duration, the trade-off flips toward applicability and patch accuracy. With a generous time budget, a localized edit format that frequently misses stale anchors or ambiguous line ranges can lose to a whole-file format that applies cleanly every time.

**Checkpoint 2.4: Reconsidering the interface when conditions change**

The repair interface must be reassessed whenever the workspace state or resource budget shifts.

**Applicability**: If the source file changes after the prompt is assembled, which measurement in the benchmark pipeline changes, and what preconditions must the runtime verify before applying either representation?

**Deadline**: If the invocation deadline doubles while token lengths and accounting rates stay fixed, which representations fit the budget, and how do you distinguish that analytical estimate from an empirical completion guarantee?

**Serialization**: If the localized edit is encoded as a JSON object rather than plain text delimiters, which latency benefits survive and which token counts must be re-profiled?

**Admission**: How do you distinguish a `COMPLETED` but malformed request from a syntactically valid but `TRUNCATED` request? Which specific check prevents each from triggering downstream tool execution?

**Acceptance evidence**: If an edit applies cleanly and passes a sequential test suite, what additional runtime evidence does a race-condition task still require before acceptance?

Interface benchmarking joins the call contract to the cost of the call. The request specifies the context and output allowances; the normalized response confirms whether the model delivered a completed payload before the deadline; and tiered evaluation metrics determine whether the proposed mutation reliably solves the task within resource constraints. Assuming that a valid schema implies an applicable patch, or that a fast diff implies defect-free code, collapses these stages into one and hides which of them failed.
