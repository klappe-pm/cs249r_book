# V2-03.12 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03 Network Fabrics|V2-03 Network Fabrics]]

^sec-network-fabrics-fallacies

Designing and operating high-performance fabrics for ML requires unlearning assumptions from traditional data-center networking. The following fallacies and pitfalls capture the most common errors that stall training and degrade cluster productivity.

**Fallacy**: *More bandwidth always means faster training.*

Engineers assume upgrading from HDR (200 Gb/s) to NDR (400 Gb/s) will yield proportional gains, but the ${\alpha}$-${\beta}$ model ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-performance-model|section 3.4.4]]) reveals this is only true in the bandwidth-dominated regime. For small models or the small-message phases of pipeline parallelism, the startup term ${\alpha}$ (1.5 μs in this chapter’s NDR scenario, including NIC processing, switch hops, and FEC) dictates performance. If a workload is latency-bound, a 2$\times$ bandwidth increase may deliver only a small fraction of the line-rate gain while adding substantial power and transceiver cost.

Consider a 10 KB message (typical for control synchronization). On 200 Gb/s InfiniBand, it takes 1.90 μs. Upgrading to 400 Gb/s reduces this to 1.70 μs, a 10.5 percent improvement despite doubling the link rate.

**Fallacy**: *Lossless Ethernet is as reliable as InfiniBand.*

RoCE over Ethernet can achieve throughput comparable to InfiniBand for large transfers, but lossless operation depends on the configuration and interaction of PFC, ECN, routing, buffers, and NIC behavior ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing#^sec-network-fabrics-pfc|section 3.6.1]]). A slow drainer or firmware defect can trigger a PFC storm, where PAUSE frames spread beyond the original queue, and a forwarding loop or cyclic buffer dependency can freeze the lossless class outright. InfiniBand’s per-hop credit mechanism avoids this specific reactive PAUSE-frame cascade, but the fabric still requires deadlock-free routing, sound virtual-lane configuration, and congestion management ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-infiniband2000spec|InfiniBand Trade Association 2000]]). Both fabrics require validation and telemetry; RoCE adds particular sensitivity to the configuration of Ethernet losslessness. Procurement should therefore compare complete transport stacks rather than link rates, because the stack determines where flow-control state and operational risk reside even when nominal rates match.

**Pitfall**: *Accepting data-center oversubscription ratios for synchronous training.*

Oversubscription relies on the traffic crossing a shared boundary fitting its available capacity. Bulk-synchronous training can violate that assumption with coordinated bursts. In the cut-saturating scenario of [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.06 Level 3 Switch and Topology#^sec-network-fabrics-fat-tree|section 3.5.2]], 4:1 oversubscription increases the modeled communication bound by 4×. Applied to a \$300M cluster with the assumed 30 percent communication fraction, the resulting idle-capacity estimate exceeds \$142.1M. This is an equivalent-capacity comparison under the stated schedule, not an equipment loss or a universal penalty for every collective.

**Fallacy**: *TCP bandwidth tests are sufficient for ML fabric validation.*

Standard benchmarks like `iperf` measure kernel-based TCP/IP performance. TCP throughput depends on host processing, offloads, and tuning as well as wire speed; it has no fixed throughput ceiling independent of that configuration. An RDMA training job exercises a different data path, so a low TCP result does not establish that the RDMA path is slow, and a high TCP result does not validate collective performance. Validation protocols must use RDMA-specific tools from the `perftest` suite to match the workload’s data path.

**Pitfall**: *Relying on adaptive routing instead of topology-aware placement.*

Adaptive routing can distribute traffic across available paths, but it cannot increase their total capacity. For a 1,024-GPU job spanning two oversubscribed spine groups, the group-to-group links become limiting when the collective sends more crossing traffic than those links can carry within its time budget. Placement can reduce that traffic, and routing can reduce path imbalance. Both must be evaluated against the actual collective schedule.

↪ Topology-aware gang placement that keeps collective traffic off contended cross-rack paths is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.07 Topology-Aware Scheduling#^sec-fleet-orchestration-placement-algorithms|Placement algorithms]]**.

**Fallacy**: *Network fabric problems always appear as hard failures.*

Network performance issues in ML clusters often show up as subtle training slowdowns rather than errors, because jobs continue to run while gradients arrive late. The silent-waste estimate in [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.10 Monitoring and Debugging#^sec-network-fabrics-monitoring|section 3.9]] shows how a small bandwidth loss accumulates into wasted GPU-hours over a long run without raising a single alarm. Detection therefore depends on comparing delivered throughput with a baseline, not on waiting for an error.

**Pitfall**: *Treating PFC and ECN counters as optional production details.*

Without discard counters and PFC pause durations, queue pressure and recovery activity can stay hidden behind a slow collective, so both belong in production telemetry, correlated with collective completion time and the affected paths. Rising values do not by themselves establish a failing transceiver or predict an inevitable job failure. Physical error counters, traffic load, routing, and configured watchdog actions help distinguish the causes and select a response.

**Self-Check: Question**

1.  Why is using standard TCP benchmark tools like `iperf` to validate an ML cluster network fabric considered a major operational fallacy?

    1.  `iperf` measures the TCP path, whose throughput depends on host processing, offloads, and tuning; it does not validate the RDMA path exercised by distributed training
    2.  `iperf` only operates over wireless IEEE 802.11 interfaces and cannot bind to physical QSFP56 ports
    3.  `iperf` automatically enables InfiniBand credit-based flow control on standard Ethernet switches
    4.  `iperf` encrypts all network packets with 4096-bit RSA keys, causing false GPU thermal throttling

2.  An infrastructure team claims: ‘Adaptive routing completely eliminates the need for topology-aware job placement in our GPU cluster.’ Why is this assertion a critical pitfall?

    1.  Adaptive routing only functions when all GPU servers are manufactured by the same vendor
    2.  Adaptive routing disables link-layer CRC error checking on optical switches
    3.  Adaptive routing forces all AllReduce operations to execute sequentially across a single ring
    4.  Adaptive routing balances traffic across existing paths, but it cannot synthesize bisection bandwidth that does not exist if a job is split across an oversubscribed or constrained network boundary

3.  Explain why upgrading an InfiniBand fabric from HDR ($200\text{ Gb/s}$) to NDR ($400\text{ Gb/s}$) yields less than a $15\%$ reduction in transfer time for a $10\text{ KB}$ control message, and state the condition under which bandwidth upgrades deliver linear performance gains.

4.  True or False: Lossless RoCEv2 Ethernet fabrics provide the exact same operational simplicity and fault immunity as InfiniBand fabrics because both support zero-packet-loss guarantees.
