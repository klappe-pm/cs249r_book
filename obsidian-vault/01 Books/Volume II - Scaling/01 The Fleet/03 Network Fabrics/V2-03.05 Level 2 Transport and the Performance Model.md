# V2-03.05 Level 2 Transport and the Performance Model

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03 Network Fabrics|V2-03 Network Fabrics]]

^sec-network-fabrics-transport

Closing the physical link budget delivers raw bits between adjacent ports, but a single AllReduce across 1,024 GPUs still stalls if host software sits in the path of every transfer or if a dropped packet triggers a multi-millisecond recovery pause. Turning raw wire rate into predictable step time requires a transport layer that offloads memory-to-memory delivery and bounds loss recovery (a contract met either through a physically lossless fabric or through loss-tolerant endpoint recovery), together with a performance model that separates fixed per-message startup latency from sustained link bandwidth.

### RDMA and GPUDirect

^sec-network-fabrics-rdma

A conventional kernel TCP path charges the host for every byte it moves. Interrupt processing, protocol work, and payload copies consume CPU cycles and memory bandwidth that the training process also needs for data loading and preprocessing, and the charge grows with aggregate I/O as many streams or NICs drive a host at 400 Gb/s link rates. Modern TCP stacks reduce the charge with segmentation offload, receive-side scaling, zero-copy interfaces, and careful non-uniform memory access (NUMA) placement, so a single stream need not exhaust a server’s memory bandwidth. They do not remove it, and the contention becomes harder to provision predictably as nodes add NICs.

**Definition 3.3: Remote direct memory access (RDMA)**

***Remote direct memory access (RDMA)*** is a networking technology that offloads transport processing to network interface hardware, allowing access to registered remote memory without per-transfer kernel processing of the payload.

1.  **Significance**: RDMA can reduce end-to-end message latency from tens of microseconds for a kernel TCP path to low-single-digit microseconds on a tuned fabric, shrinking the fixed startup cost that every message adds to the Fleet Law’s communication term ${T_{\text{comm}}}({N})$.
2.  **Distinction**: Unlike a conventional kernel TCP path, RDMA offloads transport processing to NIC hardware and permits user-space access to registered memory. The resulting CPU-core and memory-bandwidth savings depend on the host, NIC, I/O path, message size, and software configuration rather than on link rate alone.
3.  **Common pitfall**: RDMA is an access and offload model, not one loss-recovery algorithm. Reliable InfiniBand and RoCE transports detect loss and retransmit ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-infiniband2000spec|InfiniBand Trade Association 2000]]). Some RNIC generations use the Go-Back-N-style recovery noted with the loss inversion, which makes a drop expensive ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-losslessness|section 3.4.3]] quantifies the cost), while other designs support stronger selective recovery or tolerate lossy Ethernet without the link-layer pause mechanism (priority flow control) that many RoCE deployments rely on ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-mittal2018irn|Mittal et al. 2018]]). The requirement is reliable completion with a recovery tail that the synchronized workload can tolerate, not a physically lossless Ethernet fabric in every implementation.

RDMA bypasses the kernel data path. Before any transfer, software registers a memory buffer, which pins its pages in physical memory and gives the NIC the addresses and access rights it needs. The sending NIC can then name a registered buffer on the remote machine, and the remote NIC places the data there directly, with no remote CPU copying the payload. Offloading transport logic to the NIC in this way allows applications to read and write registered remote memory without per-message kernel intervention. Each message skips the interrupts, software protocol work, and payload copies of the kernel path, which is how RDMA shrinks the fixed startup cost.

For ML, GPUDirect RDMA,[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.16 Footnotes#^fn3|³]] the path that dense nodes pair with one NIC per GPU (**[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-dense-nodes|Dense node designs]]**), extends this principle to accelerator memory ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-nvidia2026gpudirectRdma|NVIDIA 2026b]]). Within a sending node ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^fig-gpudirect-data-path|figure 5]]), GPUDirect RDMA routes an ${n}$-byte payload (what one participant sends, not the model-wide gradient state) along the solid green peer-to-peer path through the PCIe switch straight to the RDMA NIC, bypassing host memory entirely. Without this direct memory access (DMA) bypass, the dashed gray staging path must first copy ${n}$ bytes from GPU memory into a registered host-memory buffer and subsequently read ${n}$ bytes out to the NIC, generating roughly $2{n}$ bytes of redundant host-memory bus traffic. The network still transfers the payload, and the PCIe path may comprise multiple DMA transactions; the optimization removes staging copies rather than collapsing the transfer into one transaction.

![[90 Assets/Volume II/03 Network Fabrics/Gpudirect Data Path de2968c9e0.svg]]

Figure 5: **GPUDirect RDMA Data Path**: Without GPUDirect (dashed), a sending node first writes the ${n}$-byte payload from GPU memory into a registered host-memory buffer and the NIC then reads it back out, about $2{n}$ bytes of host-memory traffic per payload. With GPUDirect RDMA (solid), the NIC reads GPU memory directly over the PCIe peer-to-peer path, so the host-memory bounce disappears.

### InfiniBand and RoCE

^sec-network-fabrics-ib-roce

GPU clusters commonly choose between two RDMA transport stacks, and the decision is a reliability-versus-operations trade-off. In their usual deployments, both stacks keep switch buffers from overflowing under synchronized bursts, and they do so in different places. InfiniBand uses **credit-based flow control**. Each receiver advertises its free buffer space to the sender at the other end of the link in units called credits, and the sender transmits only into space that has been advertised. A buffer therefore cannot overflow; congestion appears as senders waiting for credits rather than as dropped packets. Ethernet was designed to drop packets when buffers fill, so RoCE deployments that want the same behavior add two mechanisms. Priority flow control (PFC) lets a filling switch port send a PAUSE frame that stops its upstream neighbor for one traffic class, and explicit congestion notification (ECN) marks packets that pass through a filling queue so that their senders slow down before a pause is needed. InfiniBand thus builds losslessness into the link layer, while RoCE assembles it from switch configuration and end-to-end congestion control ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^tbl-network-fabrics-rdma-stacks|table 4]]); [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing#^sec-network-fabrics-pfc|section 3.6.1]] develops PFC’s failure modes.

The InfiniBand[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.16 Footnotes#^fn4|⁴]] row reflects a protocol heritage that favors hardware-managed losslessness over Ethernet compatibility. Both RDMA stacks nonetheless share the same user-space bypass across the user-space, kernel, and hardware boundary ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^fig-ib-roce-stack|figure 6]]). The conventional copied TCP/IP path on the left uses two software copies across kernel buffer boundaries and runs the protocol in software. The RDMA stack on the right traces a single amber bypass arrow from the collective communication library (such as the NVIDIA Collective Communications Library, or NCCL) and the user-space **verbs API** straight to the RDMA NIC, which keeps the operating system off the active data path. The verbs API is the programming interface through which software posts RDMA work requests to the NIC.

### Reliable Delivery and Loss Recovery

^sec-network-fabrics-losslessness

By routing the user-space verbs API directly to hardware ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^fig-ib-roce-stack|figure 6]]), the architecture decouples collective library calls from the operating system, leaving the transport hardware and fabric to arbitrate reliable delivery and packet loss. Reliable connected transports in both InfiniBand and RoCE detect loss and retransmit ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-infiniband2000spec|InfiniBand Trade Association 2000]]); credits and PFC exist to make that retransmission rare ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-guo2016rdma|Guo et al. 2016]]; [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-gangidi2024rdma|Gangidi et al. 2024]]). Losslessness is therefore a deployment contract rather than a property of RDMA as a family. Designs that operate over lossy Ethernet without PFC shift more responsibility to endpoint congestion control, packet reordering, and selective recovery ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-mittal2018irn|Mittal et al. 2018]]).

Recovery granularity therefore matters. On an RNIC with **Go-Back-N**-style recovery and no out-of-order retention, a lost packet invalidates every packet that arrives after it, and the sender must retransmit from the missing sequence point. The penalty is everything the sender transmitted between the lost packet and the moment it learned of the loss. That span is the resent window, and it is at most link rate times detection delay. If the receiver’s negative acknowledgment (its message reporting the gap) reaches the sender after one 5 μs round trip, a sender at 50 GB/s has meanwhile sent 250 KB, all of which it must send again; a drop 900 MB into a 1 GB transfer wastes that window, not the 900 MB already delivered. The transfer stalls until the resent window arrives. When detection instead waits for the sender’s own retransmission timeout, the stall grows with that timeout, although the resent window stops growing once the sender reaches its cap on data sent but not yet acknowledged. Resending at line rate takes at most one more detection delay, because the window is at most link rate times that delay. Below that cap, a faster link therefore resends more bytes per drop without shortening the stall.

An RNIC with selective recovery retransmits only the missing packets, so the same physical loss produces a shorter tail ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-mittal2018irn|Mittal et al. 2018]]). Either way the stall spans many packet wire times, and a synchronous collective exposes the slowest recovery to every waiting worker.

Fabric designers can reduce that tail by suppressing drops with PFC, by using a loss-tolerant transport with bounded endpoint recovery, or by combining congestion control and admission policy so queues rarely overflow. Each choice moves state and failure modes between switches and endpoints.

### The ${\alpha}$-${\beta}$ Performance Model

^sec-network-fabrics-performance-model

Even on a lossless RDMA path with zero packet drops, doubling the link rate barely speeds up a few-kilobyte pipeline control handoff while cutting a multi-hundred-megabyte gradient transfer nearly in half. Separating those two behaviors requires a cost model that distinguishes fixed per-message overhead from per-byte transmission rate. The ${\alpha}$-${\beta}$ model (principle [[01 Books/Volume II - Scaling/01 The Fleet/V2 Fleet Principles#^pri-alpha-beta-model|5]]) decomposes message transfer time as ${T}({n}) = {\alpha}+ {n}/{\beta}$, where ${n}$ is the message size in bytes, ${\alpha}$ is the fixed startup latency, and ${\beta}$ is the sustained bandwidth in bytes per unit time ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-hockney1994|Hockney 1994]]). The physical topology influences both parameters through path length and available capacity. A collective built from many sequential rounds of messages pays ${\alpha}$ once per round, so its startup cost can grow with the number of participants even when the underlying fabric provides short physical paths.

↪ The same decomposition, summed over each schedule’s rounds, is developed for collective algorithms in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.06 Pricing Collectives by Rounds and Chunks#^sec-communication-collective-operations-collective-operations-network-performance-modeling-0d8e|Pricing Collectives by Rounds and Chunks]]**.

The model reveals two regimes that call for different engineering responses. When ${n}< {\alpha}{\beta}$, the startup cost ${\alpha}$ exceeds the transmission cost, placing small control messages deep in the latency-bound region, whereas when ${n}> {\alpha}{\beta}$, the ${n}/{\beta}$ term dominates and large gradient transfers sit deep in the bandwidth-bound region. Near the crossover both terms matter, and where a collective lands also depends on how its algorithm divides the payload into messages and schedules them across rounds.

↪ The crossover message size that separates the latency-dominated and bandwidth-dominated regimes, with a worked InfiniBand NDR example, is developed in **[[05 Reference/Volume II - Scaling/V2 Communication Foundations#^sec-appdx-comm-foundations-regimes|Latency-dominated vs. bandwidth-dominated regimes]]**.

For the modeled NDR InfiniBand path with ${\alpha}=$ 1.5 μs and ${\beta}=$ 50 GB/s, the crossover point ${n^*} = {\alpha}\cdot {\beta}\approx$ 75 KB. Measured startup latency and delivered bandwidth vary with the NIC, switch path, software stack, and contention, so these parameters describe a scenario rather than a protocol constant. Far below the crossover, more bandwidth removes only a small part of transfer time; far above it, lower startup latency removes only a small part. Shorter paths can lower ${\alpha}$, while additional delivered path bandwidth raises ${\beta}$; their value depends on the message sizes the workload actually exchanges.

**Napkin Math 3.1: The alpha-beta crossover**

**Problem**: A fabric designer is comparing a modeled InfiniBand NDR path (1.5 μs, 50 GB/s) against a modeled RoCE path over slower Ethernet (5 μs, 12.5 GB/s). The comparison deliberately bundles a higher-latency stack with a slower link, so a third path, RoCE on a 400 Gb/s link, separates the two effects. For a 4 KB control message and a 350 MB gradient shard, which part of ${T}({n})={\alpha}+{n}/{\beta}$ dominates, and why does the first path help for different reasons in each regime?

**Math**: Apply ${T}({n}) = {\alpha}+ {n}/{\beta}$ for a 4 KB control message and a 350 MB gradient shard.

1.  **Small message** (4 KB):
    - InfiniBand: $1.5\,{\text{µ}}\text{s} + 4\,\text{KB}/50\,\text{GB/s} = 1.5 + 0.08 = \mathbf{1.58}\,{\text{µ}}\text{s}$
    - RoCE (100G): $5.0\,{\text{µ}}\text{s} + 4\,\text{KB}/12.5\,\text{GB/s} = 5.0 + 0.32 = \mathbf{5.32}\,{\text{µ}}\text{s}$
    - **Result**: Under these assumed path parameters, the NDR path is 3.4× faster because its modeled ${\alpha}$ is lower.
2.  **Large message** (350 MB):
    - InfiniBand: ${T}= {\alpha}+ {n}/{\beta}=$ 7.0 ms
    - RoCE (100G): ${T}= {\alpha}+ {n}/{\beta}=$ 28.01 ms
    - **Result**: Under these assumed path parameters, the NDR path is 4× faster because its modeled ${\beta}$ is higher. That factor is the ratio of the two line rates, so it measures the faster link rather than the transport.
3.  **Same line rate** (RoCE at 400 Gb/s, RoCE ${\alpha}$):
    - Small message: 5.08 μs, still 3.2× the NDR time, because the assumed ${\alpha}$ is all that separates these two paths.
    - Large message: 7.0 ms, essentially the NDR time, because at equal ${\beta}$ nothing but a few microseconds of ${\alpha}$ separates them.

**Systems insight**: This scenario places the crossover $({n^*} = {\alpha}{\beta})$ near 75 KB. Because gradients are megabytes to gigabytes, their transfers are usually bandwidth dominated, whereas pipeline coordination can remain latency dominated. A higher line rate produces little benefit for a message whose startup term dominates; transport processing, topology, and hop count then govern the improvement. At equal line rate the two stacks in this scenario differ on the control message and barely at all on the gradient shard, so a recommendation between them weighs how much step time small messages consume against the operational burden of each stack ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^tbl-network-fabrics-rdma-stacks|table 4]]).

The two message sizes in notebook [3.1](https://mlsysbook.ai/vol2/03_network_fabrics/03_network_fabrics.html#nbk-network-fabrics-alpha-beta-crossover) map directly onto the 175B training job. For the 4 KB control message that notifies a pipeline stage its next microbatch is ready (${T}({n}) \approx$ 1.58 μs on NDR), the transmission term contributes only 5.1 percent of the total, so faster links offer little benefit. For the rounded 350 MB shard that stands for one share of the 350 GB gradient across the 1,024 GPUs (${T}({n}) \approx$ 7.0 ms for that one message), transmission dominates, and doubling bandwidth to 100 GB/s approximately halves the transfer time.

Across the full range of message sizes, each path traces a flat latency-dominated plateau that bends into a linear bandwidth-dominated regime ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^fig-alpha-beta-crossover|figure 7]]). On the modeled NDR path, the knee at 75 KB marks where transmission time overtakes the 1.5 μs startup latency; the 100 Gb/s RoCE path sits on a higher floor of 5 μs and bends near 62.5 KB. The exact positions reflect the assumed ${\alpha}$ and ${\beta}$ scenario parameters rather than invariant protocol constants. On both paths, startup latency governs sub-kilobyte control handoffs, whereas multi-megabyte gradient shards sit well inside the bandwidth-bound regime.

Figure 7: **The ${\alpha}$-${\beta}$ Crossover**: Modeled transfer time as a function of message size for an NDR InfiniBand path and a 100 Gb/s RoCE baseline using the scenario parameters in the text. Small messages are latency dominated (flat region), while large messages are bandwidth dominated (linear region); on the InfiniBand path the dotted asymptotes show the knee sitting where the two terms are equal. Beyond classifying individual transfers, the same model identifies when a collective overtakes computation. A ring AllReduce, one common schedule, passes chunks around a logical cycle of participants, in a ReduceScatter phase that leaves each participant one chunk of the combined result and then an AllGather phase, with no requirement that the physical switches form a ring. The scaling laws that push training toward more parameters (**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.04 AI Scaling Laws#^sec-vol2-intro-ai-scaling-laws-a043|AI Scaling Laws]]**) enlarge, in direct proportion, the gradient that every data-parallel step must reduce. Summed over the ring’s rounds, the ${\alpha}$-${\beta}$ cost of each transfer then decides when that collective outlasts the step’s computation. At that point the network becomes the pacing constraint for the entire job.

↪ The ring AllReduce derivation, and the schedules that compete with it, are developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-collective-operations-collective-operations-ring-allreduce-ffce|Ring AllReduce]]**.

A measured collective shows both regimes and where the two-parameter model needs care. NVIDIA publishes the full output of the standard NCCL AllReduce benchmark on one node of eight H100 GPUs connected by NVLink, sweeping message sizes from 8 bytes to 16 GB ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-nvidia2026exemplarnccl|NVIDIA 2026a]]). The run crosses no external network, so it tests the two-parameter form itself, free of external switch paths and fabric congestion. The two-parameter model can be built from two summary values of that sweep, the median time of the small messages as ${\alpha}$ and the delivered rate of the largest message as ${\beta}$, and set beside the measured time ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^fig-nccl-allreduce-measured|figure 8]]). The small messages sit on a floor of about 17 µs regardless of size, and the largest messages approach 274 GB/s of algorithm bandwidth, defined as the tensor size divided by completion time.

The benchmark multiplies that algorithm bandwidth by $2(8-1)/8 = 1.75$, the bytes a ring AllReduce sends across each GPU’s links per tensor byte reduced, to report 480 GB/s of bus bandwidth. The benchmark applies this factor whichever schedule ran, so the figure is a normalization rather than a link measurement, and it can exceed NVLink’s 450 GB/s per direction.

↪ In-network reduction, in which switches rather than GPUs combine contributions and which NVLink SHARP brings to the node’s NVLink switches, is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^sec-communication-sharp|In-network reduction with SHARP]]**.

Between the two extremes, the model places this fitted collective’s knee near 5 MB, far above the 75 KB crossover of a single NDR path, but the measured time runs up to 1.7× the model’s prediction for messages between roughly 1 MB and 1 GB. Across that middle range, chunks are not yet large enough to fill every parallel NVLink channel and amortize per-round protocol overhead, so delivered bandwidth is still ramping toward its peak. The model is therefore close at the two ends and optimistic in the middle, and that middle range is where the gradient buckets (the groups of gradient tensors reduced in one call) of data-parallel training often fall.

**Checkpoint 3.1: Protocol selection**

Consider the 175B job on the 1,024-GPU reference cluster. Its gradient exchanges move messages of hundreds of megabytes, while its pipeline stages coordinate through frequent control messages of a few kilobytes.

**Protocol fit**: use the ${\alpha}$-${\beta}$ crossover to recommend a transport stack, and justify the choice for both the large gradient messages and the small control messages.

**RoCE requirements**: compare the infrastructure required by PFC-based and PFC-free RoCE designs with InfiniBand’s credit-based fabric.

**Line rate vs. startup cost**: explain why moving the control messages from a 100 Gb/s path to a 400 Gb/s path with the same ${\alpha}$ would barely change their transfer time.

The ${\alpha}$-${\beta}$ model quantifies the speed of a single link, but the 175B-parameter model requires 1,024 GPUs to work in concert. Scaling these transport primitives from a pair of nodes to a warehouse-scale supercomputer demands a **network topology**: a specific pattern of connections that maximizes ${\text{BW}_{\text{bisect}}}$ while minimizing the hop count and cabling cost for global collective operations.
