# V2-03.16 Footnotes

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03 Network Fabrics|V2-03 Network Fabrics]]

^footnotes

<sup>1</sup> **BSP (bulk synchronous parallel)**: Proposed by Valiant ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-valiant1990|1990]]) as a bridging model between parallel hardware and software. Synchronous data-parallel training follows the same barrier structure ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-goyal2017accurate|Goyal et al. 2017]]; [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-li2020pytorch|Li et al. 2020]]).

^fn1

<sup>2</sup> **Elephant and mice flows**: The model-wide gradient size is not the size of one network flow. A collective can split each worker’s local gradient shard across channels and transport connections; the resulting long-lived flows can still collide under ECMP when their static hashes select the same path.

^fn2

<sup>3</sup> **GPUDirect RDMA**: Introduced by NVIDIA for Kepler-class GPUs and CUDA 5.0, GPUDirect RDMA enables a direct PCIe path between GPU memory and third-party peer devices such as network interfaces ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-nvidia2026gpudirectRdma|NVIDIA 2026b]]). Before GPUDirect, every gradient transfer had to stage through host memory, consuming CPU memory bandwidth that competes with data loading. Eliminating this bounce path is one reason overlapping communication with backward-pass computation is feasible at scale.

^fn3

<sup>4</sup> **InfiniBand**: Formed in 1999 from the merger of two competing server I/O standards (Future I/O and NGIO), InfiniBand was originally designed to replace PCI as a general-purpose system interconnect. Its pivot to HPC networking preserved the credit-based, hardware-managed flow control that server I/O demanded, and that heritage is why InfiniBand provides native losslessness without the PFC fragility of Ethernet-based RDMA fabrics.

^fn4

<sup>5</sup> **Switch radix**: High-end switches such as NVIDIA Quantum-2 offer a radix of 64 ports, each at 400 Gb/s. As model scale pushes toward 100,000 GPUs, higher radix (128 or 256 ports), larger local accelerator domains, or accepted topology constraints are the main ways to avoid adding switch tiers, each of which adds switch latency and cost.

^fn5

<sup>6</sup> **Fat-tree (Clos network)**: The underlying multi-stage switching theory was invented by Clos ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-clos1953|1953]]) at Bell Labs to minimize the number of electromechanical crosspoints in telephone exchanges. Leiserson ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-leiserson1985|1985]]) at MIT generalized the concept as the “fat-tree,” where the tree is “fat” because link bandwidth increases toward the root, proving it could emulate any network of equal hardware volume. The same cost-minimization logic that drove 1950s telephony now drives ML cluster design: minimize switch count while guaranteeing non-blocking connectivity for global AllReduce.

^fn6

<sup>7</sup> **Dragonfly topology**: Introduced by Kim et al. ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-kim2008|2008]]) at ISCA 2008, the dragonfly uses high-radix routers grouped into fully connected “super-nodes.” For systems with at least 16,000 terminals, the architecture achieves a 52 percent network-cost reduction relative to a folded Clos (the fat-tree of [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.06 Level 3 Switch and Topology#^sec-network-fabrics-fat-tree|section 3.5.2]]) of equivalent bandwidth, though global optical link oversubscription can create AllToAll bottlenecks during MoE token routing.

^fn7

<sup>8</sup> **DCQCN (data center quantized congestion notification)**: Introduced by Zhu et al. ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-zhu2015|2015]]) (Microsoft and Mellanox) at SIGCOMM 2015 for large-scale RDMA fabrics, its binary ECN/CNP feedback loop is simpler to deploy than telemetry-rich schemes. However, it creates a delicate tuning surface for training collectives: Meta’s 2024 RoCE deployment showed that aggressive ECN marking reduces PFC pauses but degrades collective completion time ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-gangidi2024rdma|Gangidi et al. 2024]]).

^fn8

<sup>9</sup> **HPCC (high precision congestion control)**: Introduced by Li et al. ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-li2019|2019]]) (Alibaba) at SIGCOMM 2019, HPCC requires programmable switch ASICs that append INT metadata to packets at line rate, a hardware dependency that limits the fabrics able to deploy it.

^fn9

<sup>10</sup> **ECMP (equal-cost multi-path)**: ECMP selects a path by hashing on the 5-tuple (source/destination IP, source/destination port, protocol), which means the same flow always takes the same path. This determinism is a feature for packet ordering but a liability for ML. Because a single AllReduce ring produces a small number of persistent flows, hash collisions are not transient statistical events but hot spots that last as long as those flows do.

^fn10

<sup>11</sup> **Packet spraying**: Unlike standard Ethernet (which hashes flows to single paths to avoid reordering), packet spraying sends individual packets of a single flow across multiple paths. This can improve use of the available ${\text{BW}_{\text{bisect}}}$ by AllReduce elephant flows when the transport can tolerate or repair reordering. The Ultra Ethernet Consortium (UEC) specification design explicitly includes multi-path packet spraying and flexible ordering to reduce the ECMP collision problem for AI/HPC traffic ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-ultraEthernet2025specification|Ultra Ethernet Consortium 2025]]).

^fn11
