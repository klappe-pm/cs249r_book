# V2-03.11 Network Technologies That Move the Ceiling

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03 Network Fabrics|V2-03 Network Fabrics]]

^sec-network-fabrics-emerging

Monitoring keeps deployed fabrics honest, but it cannot push past the physical ceilings it measures, such as the reach and power limits that copper approaches at high signaling rates. New fabric technologies earn attention only when they move one of those bounds. As clusters scale toward 100,000 GPUs, the durable design variables are power per bit, reach, and the ratio of compute to memory to network capacity, not the product names attached to a particular roadmap.

### Protocol Convergence and Link Density

^sec-network-fabrics-protocol-convergence

Standard RoCEv2 leaves operators with fragile PFC pause thresholds and with ECMP hashing that was never designed for synchronized elephant flows, while InfiniBand locks the fabric into a single-vendor stack. The Ultra Ethernet Consortium (UEC) addresses these reliability and load-balancing limits for AI/HPC traffic over Ethernet. Its Ultra Ethernet Transport design combines packet spraying across multiple paths, flexible ordering, multiple transport delivery services, congestion-control changes, and telemetry ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-ultraEthernet2025specification|Ultra Ethernet Consortium 2025]]). The architectural question is how the selected service delivers the required completion and ordering semantics under congestion or loss. Packet trimming (cutting an overflowing packet down to its header instead of dropping it, so the receiver learns of the loss at once), retry, and endpoint recovery should therefore be judged by their effect on completion-time tails and resource cost. Whether the design reproduces a lossless-fabric mechanism is not the test.

Higher switch capacity attacks hop count as well as raw bandwidth. XDR InfiniBand pushes 800 Gb/s per port, and Ethernet roadmaps include 800GbE and 1.6TbE link speeds ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-nvidia2026quantumX800|NVIDIA 2026c]]; [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-ethernetAlliance2025roadmap|Ethernet Alliance 2025]]). Ethernet switch silicon with 1.6 Tb/s ports pushes aggregate capacity to 102.4 Tb/s in current Tomahawk 6-class designs ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-broadcom2025tomahawk6|Broadcom Inc. 2025]]). A single 1.6 Tb/s port delivers 4 times the bandwidth of a 400G port, so the same ASIC can instead expose 4 times as many 400G ports. Spending that capacity on radix rather than port rate is what flattens the topology, because fat-tree host count grows as ${k}^2/2$ at two tiers and ${k}^3/4$ at three. A cluster that previously required three tiers of switches may then be served by two when radix, port rate, and placement constraints line up, potentially reducing the number of optical links and switching stages. The transceiver savings require explicit port and cable accounting; removing one tier does not automatically halve the module count, and the latency benefit depends on the resulting paths and traffic.

### Optical Interconnects

^sec-network-fabrics-optical

![[90 Assets/Volume II/03 Network Fabrics/Network Fabrics Physical Reach Ladder 93ba0cd396.svg]]

*Vertical reach ladder with four marked levels: package at millimeters, DAC at 1 to 3 meters, AOC at 3 to 30 meters, and optics beyond 30 meters.*

*Each extra meter pushes the fabric from copper toward optics.*

Pushing ports from 400 Gb/s to the 800 Gb/s and 1.6 Tb/s rates of [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.11 Network Technologies That Move the Ceiling#^sec-network-fabrics-protocol-convergence|section 3.10.1]] takes more lanes, faster lanes, or both. Eight lanes in the 100 Gb/s class of current NDR links reach 800 Gb/s, but an 800 Gb/s port on four lanes or a 1.6 Tb/s port on eight lanes doubles the per-lane rate to the 200 Gb/s class, which sharply increases the insertion loss per meter of passive copper. As that usable reach shrinks, in line with the link-budget example in [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.04 Level 1 Wire and Link#^sec-network-fabrics-serdes|section 3.3.3]], the SerDes must spend more energy per bit on equalization to recover the signal. Active electrical cables, which add retimer chips to regenerate the signal mid-cable, extend that reach but add latency and power of their own, leaving optical interconnects as the primary lever on power per bit and reach.

Co-packaged optics (CPO) places optical engines close to the switch or accelerator on a shared package substrate. Moving the optical engine from the switch faceplate to the package shortens the SerDes-to-optics electrical path from centimeters of board trace to millimeters, which reduces the signal-conditioning burden before transmission over fiber. The receiving optical engine converts the signal back to electrical form. Fiber still introduces propagation delay and has a loss budget; packaging the optics closer to the processor does not remove those constraints.

Co-packaged optics therefore changes the electrical portion of the link budget while retaining the reach advantages of optical transmission. Usable reach still depends on the fiber, connectors, optical power, and receiver design. The relevant comparison holds payload capacity and error targets fixed, then measures the power saved by the shorter electrical path against the packaging and maintenance costs of integration. The power side of that comparison can be estimated port by port for a single switch.

**Napkin Math 3.5: The optical dividend**

**Problem**: How much optics power does a 51.2 Tb/s switch save by moving from pluggable transceivers to co-packaged optics?

**Math**:

1.  **Pluggable architecture**: 128 ports $\times$ 20 W = 2.56 kW for optics alone.
2.  **CPO architecture**: 128 engines $\times$ 10 W = 1.28 kW.
3.  **Savings**: The savings reach 1.28 kW of power per switch.

**Systems insight**: Across 1,000 switches, the assumed pluggable modules consume 2.56 MW. The modeled CPO configuration saves 1.28 MW, equivalent to the reference power budget of roughly 1,800 H100 GPUs. That equivalence measures the scale of the saving; using it for additional accelerators also requires compute capacity, power delivery, and cooling in the right locations. Optics power constrains both operating cost and the equipment a facility can support.

The spine example for 10,000 GPUs assigns 400 kW to pluggable optics. That subtotal counts only the selected spine-side endpoints. Applying the same fractional saving to those endpoints would require a CPO implementation with the assumed per-port power and capacity; opposite-end optics remain outside the comparison. Integration also changes serviceability: replacing a failed optical component may involve a larger assembly than swapping a pluggable module. The energy benefit must be evaluated alongside packaging, repair, and spare-capacity costs.

For ML infrastructure, CPO could flatten the bandwidth hierarchy by narrowing the gap between intra-node and inter-node bandwidth. If inter-node links achieve bandwidth comparable to NVLink-class local fabrics (hundreds of GB/s per GPU), the bandwidth penalty for extending tensor parallelism beyond a single node would shrink. Cross-node tensor parallelism would then become economical for more workloads, provided that startup latency and collective frequency also fit the step-time budget.

However, CPO introduces new challenges. Optical components are sensitive to temperature (laser wavelength shifts with temperature, requiring active thermal management), and integrating photonics on the same package as a 1,000 W GPU creates a hostile thermal environment for the optical components. The manufacturing processes for silicon photonics and CMOS transistors are similar but not identical, requiring separate fabrication steps that increase package cost and complexity. Hybrid integration, which places the photonics chiplet on a cooler region of the package substrate and thermally isolates it from the GPU die, is one way to manage that environment, at the cost of a longer electrical path than full co-location.

### Disaggregated and Composable Architectures

^sec-network-fabrics-disaggregated

As the gap between package-level and rack-level interconnects narrows, architects can reconsider the fixed compute-to-memory ratio of the server node, which leaves compute or memory underused when workloads need different resource ratios. Compute Express Link (CXL) memory pooling allows supported hosts to access assigned memory capacity through a CXL path, while disaggregated designs make some resource allocations independent of the chassis boundary. This changes which links lie on the workload’s critical path. It does not merge CXL memory access, NVLink communication, and InfiniBand transport into one interchangeable service; each path retains its own supported operations, bandwidth, and latency.

↩︎ CXL memory pooling, which makes node memory capacity less rigid but remains a capacity tier rather than a high-bandwidth memory (HBM) replacement, is established in **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.10 Infrastructure Technologies That Move the Walls#^sec-compute-cxl|Compute express link (CXL)]]**.

A composed node therefore needs a new traffic budget. The ${\alpha}$-${\beta}$ distinction between startup and transfer cost remains useful, but each path requires its own parameters and access model. Remote memory traffic can compete with other transfers, and fine-grained dependent accesses can expose latency that a bulk-bandwidth estimate hides. Disaggregation improves resource flexibility only when these added costs fit the workload’s execution budget. Composition relocates the synchronization backbone onto new paths rather than eliminating it.
