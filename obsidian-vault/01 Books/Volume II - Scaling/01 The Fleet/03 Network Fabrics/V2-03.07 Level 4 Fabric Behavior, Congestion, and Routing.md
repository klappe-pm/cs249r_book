# V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03 Network Fabrics|V2-03 Network Fabrics]]

^sec-network-fabrics-behavior

A collective can finish late even when the topology provides full ${\text{BW}_{\text{bisect}}}$. Levels 1 through 3 determine how long a transfer takes on an unloaded path; fabric behavior determines how much longer it takes once the job’s own synchronized traffic loads that path. Competing flows can concentrate on one output path, and the BSP barrier introduced in [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.03 How ML Networking Inverts Data-Center Assumptions#^sec-network-workload-inversion|section 3.2]] exposes any delay that extends the last required transfer. The relevant paths are those used by the participating workers; a congested link elsewhere in the fleet need not affect the job. In the Fleet Law (**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^eq-fleet-law|equation 1.3]]**), measured transfer durations contribute to ${T_{\text{comm}}}({N})$, while residual waiting at synchronization contributes to ${T_{\text{sync}}}({N})$, the point where the communication axis of C³ hands its cost to the coordination axis. A timeline must assign each interval consistently so the same congestion delay is not counted twice.

The p99 tail latency introduced with the BSP barrier helps expose delays that an average hides, but a particular barrier waits for its last required participant, not for a percentile. Evaluating a fabric therefore requires both transfer-time distributions and the collective completion times they produce under load.

### Priority Flow Control (PFC)

^sec-network-fabrics-pfc

The BSP weakest-link property means that even a single dropped packet can trigger a retransmission timeout that stalls the global barrier for milliseconds, a delay that can rival the entire communication phase of a training step. PFC-based RoCEv2 fabrics prevent the drop in the first place by running PFC, the pause mechanism introduced with the RDMA stacks ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-ib-roce|section 3.4.2]]), in lossless mode, so that upstream senders stop before any buffer saturates ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-guo2016rdma|Guo et al. 2016]]; [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-gangidi2024rdma|Gangidi et al. 2024]]).

**Definition 3.8: Priority flow control**

***Priority flow control (PFC)*** is a link-layer mechanism used by RoCEv2 ML cluster fabrics to prevent switch buffer overflow. When a port’s queue depth crosses a configured threshold, the switch sends PAUSE frames to an upstream sender, which throttles injection on a per-priority basis without dropping packets.

1.  **Significance**: In PFC-based RoCEv2 deployments, PFC is the foundation for a lossless Ethernet service. A PFC PAUSE frame must reach the upstream sender before the buffer overflows, so each pause threshold must leave headroom for the data still in flight during roughly one link round trip.
2.  **Distinction**: Unlike standard IEEE 802.3 flow control, which pauses all traffic classes on a link, PFC operates per priority class, allowing latency-sensitive control messages to continue flowing while only pausing the congested gradient data queue.
3.  **Common pitfall**: A frequent misconception is that PFC solves congestion. It transforms packet loss into congestion spreading. PFC itself places no bound on how far PAUSE frames propagate, so a single faulty transceiver can pause traffic far from its own link unless a watchdog intervenes.

The danger of PFC lies in its cascading nature. When a switch port’s buffer fills, it sends a PAUSE frame upstream, which can move congestion into the upstream switch and trigger another PAUSE frame. A slow receiver, routing hot spot, or true fan-in burst (many senders converging on one port) can therefore pause links unrelated to the original queue. This behavior, known as **congestion spreading**, is the primary operational risk of PFC-based lossless Ethernet, and the flows it stalls without ever touching the congested queue are called **victim flows**. Fan-in is one trigger, but it is not intrinsic to every collective. A bandwidth-optimal ring exchanges data point to point, although multiple ring flows can still collide at a shared egress or an oversubscribed cut and create a hot spot without a single aggregation receiver ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing#^sec-network-fabrics-incast|section 3.6.5]]).

### Lossless Fabric Hazards and Watchdog Recovery

^sec-network-pfc-hazards

While priority flow control provides the illusion of a lossless physical layer, relying on link-layer backpressure introduces structural failure modes that do not exist in loss-tolerant packet-switched networks. When switch queues cannot drop packets to relieve congestion, pressure propagates backward through the network graph, creating two distinct hyperscale failure modes: buffer-dependency deadlocks and PFC storms.

**Definition 3.9: Cyclic buffer dependency deadlock**

***Cyclic buffer dependency deadlock*** is a permanent distributed lockup in a lossless network, whether its backpressure uses PFC PAUSE frames or InfiniBand credits. A set of switch port queues forms a closed dependency cycle, and each queue holds packets destined for the next queue while backpressure from that same queue pauses it.

1.  **Significance**: A single such deadlock permanently halts traffic across all participating ports and upstream links, requiring manual intervention or watchdog timeouts that discard packets to recover. InfiniBand fabrics prevent it through deadlock-free routing and virtual-lane assignment, and PFC-based Ethernet fabrics need the same discipline in their routing and priority configuration.
2.  **Distinction**: Unlike a PFC storm (which is a transient cascade of backpressure triggered by a slow-draining endpoint), a buffer-dependency deadlock is a static, self-sustaining topological cycle that cannot resolve itself even after traffic injection stops.
3.  **Common pitfall**: Assuming multi-stage Clos (fat-tree) fabrics are inherently immune to deadlocks. Dynamic multipath routing, link failures, and address resolution flooding can introduce cyclic forwarding dependencies across switch tiers.

#### The Graph Mechanics of Buffer-Dependency Deadlocks

^sec-network-deadlock-graph

In a lossless network, a switch cannot forward a packet to downstream buffer ${b}_j$ if ${b}_j$ is full; instead, it holds the packet in upstream buffer ${b}_i$ and awaits credit or pause clearance. A directed buffer dependency graph ${G}= ({V}, {E})$ formalizes this relationship. Each vertex ${b}_k \in {V}$ represents a packet buffer or virtual lane queue at a switch port. A directed edge $({b}_i, {b}_j) \in {E}$ indicates that a packet currently occupying buffer ${b}_i$ requires buffer ${b}_j$ along its routing path to make forward progress.

A directed cycle in the buffer dependency graph is a necessary condition for a cyclic buffer dependency deadlock (definition [3.9](https://mlsysbook.ai/vol2/03_network_fabrics/03_network_fabrics.html#dfn-network-fabrics-pfc-deadlock)), but a cycle alone does not establish that progress has stopped. The cyclic dependency in [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing#^eq-network-buffer-dependency-cycle|equation 1]] becomes a deadlock when the occupied buffers cannot drain and every participant waits for its successor:

$$
{b}_1 \to {b}_2 \to \dots \to {b}_k \to {b}_1 \tag{1}
$$

^eq-network-buffer-dependency-cycle

When each buffer in the cycle fills beyond its configured pause threshold, each port asserts a PFC PAUSE frame to its predecessor. Because no buffer can advance a packet into a paused successor, no buffer can drain, and no port can de-assert its PAUSE signal. The entire cycle freezes permanently. A four-switch ring whose queues (${b}_1$ through ${b}_4$) are completely full shows this mutual protocol interlock ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing#^fig-pfc-credit-deadlock|figure 12]]). Solid gray arrows trace packet forwarding dependencies advancing clockwise (${b}_1 \to {b}_2 \to {b}_3 \to {b}_4 \to {b}_1$), while dashed red PAUSE frames propagate counterclockwise. Each full queue pauses its upstream predecessor while waiting for its downstream successor to drain, permanently freezing all four queues until an external watchdog intervenes to drop frames.

![[90 Assets/Volume II/03 Network Fabrics/Pfc Credit Deadlock be7f9cc9b8.svg]]

Figure 12: **A PFC Deadlock from a Cyclic Buffer Dependency**: Four switch queues form the cycle of [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing#^eq-network-buffer-dependency-cycle|equation 1]]. Follow the solid arrows clockwise: each full buffer holds packets that need space in the next. The dashed PAUSE frames run counterclockwise, so each full queue pauses its upstream predecessor while awaiting space in its downstream successor, and no queue can drain until a watchdog drops packets.

^fig-pfc-credit-deadlock

Routing changes and flooding can create the dependencies needed for deadlock. During link failure or route convergence, inconsistent forwarding tables can create transient loops. A lossy IP network eventually discards a looping packet when its time-to-live expires; a lossless class has no such release, so looping traffic can fill the buffers along the loop and hold them. If traffic occupies a cycle of mutually blocked queues, backpressure can prevent progress until recovery breaks the dependency. Multicast or broadcast replication can also fill queues whose dependencies intersect, while cross-connects and asymmetric failover paths can introduce cycles absent from the intended hierarchical route. None of these conditions alone proves a deadlock; the occupied buffers and pause states must form the closed waiting cycle described by the model. Microsoft’s production RoCE deployment encountered the flooding trigger directly (war story [3.1](https://mlsysbook.ai/vol2/03_network_fabrics/03_network_fabrics.html#ws-network-fabrics-microsoft-pfc-deadlock)).

**War Story 3.1: Microsoft's PFC deadlock (2016)**

**Context**: A team led by Chuanxiong Guo at Microsoft Research deployed RoCEv2 across Microsoft’s data centers, a fleet operating at the scale of tens of thousands of servers, to support latency-sensitive services. Their design provided a lossless fabric with PFC, and the team developed a Differentiated Services Code Point (DSCP)-based PFC mechanism to extend the deployment beyond virtual local area network (VLAN) boundaries ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-guo2016rdma|Guo et al. 2016]]).

**Mechanism**: PFC interacted with Ethernet flooding to create a cyclic buffer dependency. A dead server with an incomplete mapping between an IP address and a media-access-control address caused upstream switches to flood lossless packets to every port; PFC PAUSE frames then propagated upstream in response to the flooded traffic, forming a closed loop of paused buffers.

**Impact**: Lossless traffic through the switches in the cycle stopped entirely and stayed stopped, because no buffer in the dependency loop could drain without outside intervention.

**Fix**: Microsoft blocked broadcast and multicast traffic from entering lossless traffic classes, and dropped lossless packets when the corresponding Address Resolution Protocol (ARP) entry was incomplete rather than falling back to flooding.

**Systems lesson**: PFC backpressure is a structural vulnerability of lossless Ethernet at hyperscale. RoCE fabrics require packet-class discipline, PFC pause telemetry, and hardware-level safeguards because a mechanism designed to avoid packet loss can itself become the failure mode. ML training fabrics built on RoCE inherit this risk directly. A single incomplete ARP entry can freeze the lossless class that carries a multi-thousand-GPU training run’s gradients, with the cluster appearing healthy while no gradient flows between workers.

#### PFC Storms and Victim Flows

^sec-network-pfc-storms

In contrast to a static topological cycle, a **PFC storm** is a dynamic, runaway amplification phenomenon triggered when a single “slow drainer” (an accelerator stalled by memory bus saturation, operating system preemption, or a degraded transceiver with elevated bit error rates) fails to consume packets at wire speed. The attached ToR switch queue fills and sends a PAUSE frame to the sender. Because multi-port switches aggregate traffic from many sources across shared packet buffers, the paused queue blocks buffer allocation for unrelated packets. Packets of one priority class also leave the paused queue in order, so a packet bound for an uncongested port waits behind the blocked packets ahead of it (head-of-line blocking). The spine switches feeding that ToR then fill their buffers and pause the other leaf switches that send through them, and each additional tier widens the set of paused links until traffic between node pairs that never communicated with the stalled worker also stops. These victim flows turn one slow endpoint into a job-wide barrier delay, because every data-parallel worker whose path crosses a paused spine port now arrives late at the barrier.

Congestion spreading is the mechanism behind both a storm and a deadlock. A storm is the form that a slow drainer sustains, so it can end when the drainer recovers, unlike the closed cycle of a deadlock.

A degraded transceiver is one such slow drainer, so a component-exposure calculation shows how often a cluster should expect at least one, even though exposure alone does not estimate the probability of a PFC storm.

**Napkin Math 3.4: Probability of at least one transceiver degradation**

**Problem**: A 4096-GPU RoCE cluster, larger than the reference cluster, is in operation. If the probability that a given transceiver begins degrading on a given day is 0.001 percent, what is the chance that at least one transceiver degrades on a given day?

**Math**: Assume independent transceiver-degradation events with the same per-device probability.

1.  **Total exposure**: 4096 $\times$ 3 link tiers = 12,288 links, or 24,576 transceivers.
2.  **Probability of zero transceiver degradations**: $\Pr(\text{no degradation}) = (1 - 0.00001)^{24,576} \approx 0.782$.
3.  **Probability of at least one degradation**: $\Pr(\text{at least one degradation}) = 1 - 0.782 = \mathbf{0.218}$ (about 21.8 percent).

**Systems insight**: Under these assumptions, a large RoCE cluster has a 21.8 percent daily chance of at least one degraded transceiver. This result motivates hardware telemetry and automated remediation, but estimating fabric-wide freeze risk additionally requires the conditional probability that a degradation triggers and propagates a PFC storm.

#### Watchdog Recovery and the Lossy Alternative

^sec-network-pfc-watchdogs-and-lossy

Switches can use **PFC watchdog timers** to detect prolonged pause states and trigger recovery without a full reboot. The configured threshold ${T_{\text{watchdog}}}$ must fit the deployment’s pause and recovery budgets; a range such as $50\text{--}200\text{ ms}$ is a configuration example, not a universal requirement. Exceeding it indicates stalled progress, not proof of a cyclic deadlock. Depending on the implementation, mitigation can disable pause handling or discard affected traffic so blocked queues can drain. The transport must then recover any lost data, with the completion penalty determined by retransmission behavior, outstanding traffic, and the collective’s dependencies. On an RNIC with Go-Back-N-style recovery ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-losslessness|section 3.4.3]]), each discarded packet also costs the in-flight window behind it, so breaking a pause converts a stalled queue into a retransmission tail that the waiting collective absorbs.

This systemic brittleness is driving hyperscale operators toward next-generation architectures such as the Ultra Ethernet Consortium (UEC) ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-ultraEthernet2025specification|Ultra Ethernet Consortium 2025]]), detailed in [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.11 Network Technologies That Move the Ceiling#^sec-network-fabrics-protocol-convergence|section 3.10.1]], and loss-tolerant RDMA designs ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-mittal2018irn|Mittal et al. 2018]]). Designs that combine packet spraying (sending one flow’s packets over many paths) with congestion control and selective retransmission can operate without link-layer PFC. Removing PFC removes its pause-based deadlocks and storms, but endpoint recovery must still bound the completion-time penalty of congestion and loss.

### End-To-End Congestion Control with DCQCN and HPCC

^sec-network-fabrics-congestion-control

Because link-layer PFC fires only when a switch buffer is already near exhaustion, relying on pauses alone invites the cascades and watchdog drops of [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing#^sec-network-pfc-hazards|section 3.6.2]]. Keeping queues below those thresholds requires end-to-end congestion control, which throttles sender injection rates before buffers fill. For a BSP workload with a completion-time target, this rate control is a *latency requirement* rather than an *optional throughput optimization*: delaying a required transfer extends the synchronization boundary, so the controller must balance delivered throughput against queueing and recovery tails.

The first widely deployed solution, **DCQCN**,[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.16 Footnotes#^fn8|⁸]] operates as a reactive feedback loop using ECN ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-zhu2015|Zhu et al. 2015]]). When a switch’s queue depth exceeds a configured threshold, it marks the ECN bit in the packet header. The receiver echoes this mark back to the sender via a congestion notification packet (CNP), prompting the sender to reduce its injection rate using a multiplicative-decrease algorithm. DCQCN is widely supported, but production AI collectives expose a tuning problem because the feedback loop takes a full network round trip to take effect. Setting the ECN threshold high leaves too little buffer headroom for synchronized bursts to slow down before hitting the PFC pause threshold, whereas setting it low causes senders to throttle aggressively on brief queue spikes and underutilize the link. Consequently, ECN thresholds and NIC firmware behavior trade off PFC avoidance, throughput, visibility, and tail latency rather than offering one stable optimum ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-gangidi2024rdma|Gangidi et al. 2024]]).

**HPCC**[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.16 Footnotes#^fn9|⁹]] uses in-network telemetry (INT) to give the sender more information about path load ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.15 Source References#^ref-li2019|Li et al. 2019]]). Switch measurements of queue occupancy and transmitted traffic let the controller estimate an appropriate injection rate rather than react only to a binary congestion mark. That information still arrives after a feedback delay, so the controller must account for changing load and avoid overreaction. The evaluated design reduces queue buildup and tail latency, but requires switch telemetry support and compatible endpoint processing. DCQCN needs less detailed switch feedback, trading that simpler deployment requirement against a different tuning problem.

### Adaptive Routing

^sec-network-fabrics-adaptive-routing

Throttling senders with DCQCN or HPCC relieves a filling queue only by slowing the flows that cross it, even when parallel spine links sit idle. That imbalance is the ECMP hash-collision problem from [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.03 How ML Networking Inverts Data-Center Assumptions#^sec-network-workload-inversion|section 3.2]]: because static flow hashing,[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.16 Footnotes#^fn10|¹⁰]] which works well for millions of small flows, pins each persistent elephant flow to a fixed path, an 8-flow AllReduce across 4 equal-cost paths can place 4 flows on one link while another carries none. In a synchronized training step, that overloaded link then determines completion time and can halve useful bandwidth.

Adaptive routing mitigates this problem by allowing switches to select among eligible output paths using congestion information rather than only a static hash. That choice moves traffic onto paths with room and adds no capacity, so it repairs a collision but cannot relieve a fabric whose paths are all full. The implementation is protocol- and device-dependent. Packet-level spraying[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.16 Footnotes#^fn11|¹¹]] can send packets of one connection over different paths, so the receiver may observe reordering. Compatible endpoint support must accept out-of-order placement or restore the transport’s required ordering; the presence of InfiniBand alone does not guarantee arbitrary spraying across every path. Ethernet fabrics can also employ **flowlet switching**, which changes a flow’s path between bursts separated by a gap large enough to preserve packet order across the candidate paths, so its usefulness depends on how often the workload leaves such gaps relative to path delay differences.

MoE expert exchanges illustrate why path diversity matters: a dense exchange among 64 expert-parallel ranks contains at most $64(64-1)=4{,}032$ directed remote rank pairs after excluding self-transfers, with active traffic governed by expert placement and token-routing sparsity. Where static-hash collisions concentrate that traffic onto a few links, adaptive routing spreads it across the provisioned ${\text{BW}_{\text{bisect}}}$. Archetype B (DLRM at Scale) creates similar exchanges when batches of embedding requests and results move among table shards, although batch and shard placement determine the traffic matrix rather than every individual lookup requiring a global exchange.

### The Incast Problem in ML

^sec-network-fabrics-incast

Congestion control and adaptive routing manage flows that traverse the interior of the fabric. A different failure mode occurs at the edge, where the traffic pattern itself overwhelms a single port regardless of how much capacity the fabric interior provides.

**Definition 3.10: Incast**

***Incast*** is a many-to-one ML cluster traffic pattern in which a large number of senders simultaneously transmit data to a single receiver port. It concentrates line-rate traffic from multiple sources into a single switch queue, and it can overflow the buffer if the burst outlasts the available buffering and control response, even when the rest of the fabric is uncongested.

1.  **Significance**: Flat aggregation, synchronized storage reads, or other fan-in phases can direct many senders toward one receiver. The deliberately worst-case scenario here assumes a RoCE fabric whose ports all run at 400 Gb/s. In it, 256 senders each transmit at 50 GB/s toward one switch egress, producing 12.8 TB/s of offered load against a 400 Gb/s port. A 32 MB buffer then overflows in about 2.5 μs under the stated assumptions, after which the switch either drops packets or, in a PFC deployment, pauses its upstream neighbors. The example is a stress bound, not the traffic matrix of a ring AllReduce.
2.  **Distinction**: Unlike general congestion (which occurs on shared internal links when aggregate traffic exceeds link capacity), incast is an endpoint bottleneck. It occurs even if every internal spine and leaf link is completely uncongested, because the bottleneck is the single destination port, not the fabric interior.
3.  **Common pitfall**: Incast is not necessarily rare or unpredictable. Training jobs create it on a schedule, whenever many GPUs read dataset shards from or write checkpoints to the same storage node, and in the aggregation step of a tree or hierarchical reduction, where several ranks send partial sums to one parent. A gradient ring is different; its point-to-point flows can still collide at a shared egress, but that is a hot spot rather than many-to-one incast. The severity depends on the collective algorithm, topology, routing, and oversubscription, so it must be measured and mitigated rather than treated as an edge case.

In a worst-case incast, 12.8 TB/s of offered traffic from 256 senders converges on a single 400 Gb/s (50 GB/s) egress ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.07 Level 4 Fabric Behavior, Congestion, and Routing#^fig-congestion-cascade|figure 13]]). Each sender injects at 50 GB/s. The buffer fills over a finite interval; control feedback can reduce arrivals, drops can discard excess traffic, or backpressure can move the queueing upstream. Whether that pressure spreads depends on shared queues and the paths carrying the traffic. Let the aggregate arrival rate to one egress be ${\lambda_{\text{arr}}}$, the egress service rate be ${\mu}$, and the instantaneous queue occupancy be ${Q}({t})$. While a burst persists and ${\lambda_{\text{arr}}} > {\mu}$, the queue grows at the net rate

$$
{Q}({t}) = \min\!\left({Q_{\text{max}}},\; {Q}(0) + ({\lambda_{\text{arr}}}-{\mu}){t}\right),
$$

where ${Q_{\text{max}}}$ is the finite buffer capacity. The ratio ${\rho_{\text{egress}}}={\lambda_{\text{arr}}}/{\mu}$ distinguishes a drainable workload from sustained overload: for ${\rho_{\text{egress}}}<1$, idle intervals can drain the queue; as long-run ${\rho_{\text{egress}}}$ approaches one, less slack remains to absorb bursts; and for ${\rho_{\text{egress}}}>1$, occupancy must reach a control threshold or the buffer limit if the overload persists. This is a packet queue, distinct from the request queues of an inference server. Serialization and propagation set the unloaded path latency, whereas queued bytes add approximately ${Q}/{\mu}$ of waiting time.

⇄ **Contrast:** Request queues, whose arrival and service rates set serving latency rather than switch buffer occupancy, are developed in **[[05 Reference/Volume II - Scaling/V2 Inference Foundations#^sec-appdx-inference-scale-queuing-theory-batched-inference-bbf0|Queuing theory for batched inference]]**.

In the deliberately worst-case incast above, ${\rho_{\text{egress}}}$ is 256×, so the 32 MB buffer fills in about 2.5 μs. Once full, that buffer represents 640 μs of egress waiting time. By contrast, the bandwidth-delay product (link rate times round-trip time) for the 400 Gb/s egress and an illustrative 5 μs feedback round trip is only 250 KB; it measures data in flight on the path, not the buffering needed to absorb an arbitrary fan-in burst. ECN must mark early enough for feedback to arrive before exhaustion, and in this worst case the buffer fills before a 5 μs round trip completes, so even a mark on the first queued byte returns too late. PFC can prevent a drop, but its backpressure can spread congestion. A larger buffer extends the reaction window at the cost of a larger tail-latency bound.

The 12.8 TB/s offered load oversubscribes the destination egress by 256×. Flat aggregation or synchronized reads can create this pattern; bandwidth-optimal ring AllReduce does not, because each rank exchanges point-to-point chunks.

^fig-congestion-cascade

Synchronized ML traffic is susceptible to both true fan-in and shared-egress hot spots. When a layer finishes backward computation, many ranks can inject traffic at once, and flat or hierarchical aggregation phases can create true fan-in. Production clusters mitigate both cases along three complementary dimensions:

1.  **Time.** Layer-staggering triggers each gradient bucket’s AllReduce as soon as backpropagation produces it. Final-layer gradients reduce while earlier layers are still computing, so communication is spread across the backward pass instead of released as one synchronized burst. The same staggering is communication-computation overlap, so it also hides transfer time behind the backward computation that remains.
2.  **Space.** Collective algorithm selection bounds fan-in at individual switch ports. Hierarchical and rail-local reductions aggregate gradients in stages so that no single port must absorb all senders at once, and topology-aware placement keeps concurrent ring flows off oversubscribed ports.
3.  **Priority.** Quality of service (QoS) classification tags gradient traffic with the highest service class to reduce interference from background storage or management traffic; shared links, buffers, and arbitration still constrain isolation.

These mitigations spread the burst in time, space, and priority, but they do not eliminate congestion or tail latency. A production cluster must therefore deliver predictable step times with that residual congestion in place.

    2.  Packet spraying encrypts packets with unique keys across paths, which InfiniBand decrypts in hardware while Ethernet lacks AES accelerators
    3.  Packet spraying routes packets over wireless backup links, which Ethernet switches do not support
    4.  Packet spraying reduces packet header size from 40 bytes to 4 bytes, doubling Ethernet wire efficiency

5.  Place the following events in order to illustrate how an incast burst escalates into a cluster-wide PFC congestion storm in a RoCEv2 fabric:

<!-- -->

1.  The downstream switch buffer reaches its high-water mark and emits PFC PAUSE frames upstream
2.  Upstream switches pause their transmission queues, causing their own ingress buffers to fill with traffic destined for other ports
3.  Multiple GPU senders simultaneously initiate flat-aggregation transfers targeting a common aggregation node
4.  Second-tier upstream switches emit PAUSE frames to unrelated sender nodes, freezing victim flows across the fabric
5.  The common destination switch egress queue is oversubscribed by the combined line-rate traffic
