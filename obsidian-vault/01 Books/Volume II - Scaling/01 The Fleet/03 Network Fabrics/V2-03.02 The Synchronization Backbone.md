# V2-03.02 The Synchronization Backbone

^sec-network-fabrics-introduction

![[90 Assets/Volume II/03 Network Fabrics/Network Fabrics GPU Fanout 254ef5b1aa.svg]]

*A schematic fan: one red source node on the left connects by six gray arrows to six blue nodes on the right, showing one node reaching many peers.*

*One slow link stalls every peer that waits on it.*

At the node boundary, each GPU’s NVLink bandwidth narrows to a single external network port, the bottom of the bandwidth hierarchy traced in **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02 Compute Infrastructure#^sec-compute-infrastructure|Compute Infrastructure]]**. How much that narrowing costs depends on what the training job must push through the port, and how often. Consider the running instance of Archetype A (GPT-4/Llama-3), a 175B-parameter GPT-3-class dense transformer partitioned across the 1,024 GPUs of the reference cluster. Each training step must combine gradient contributions so that corresponding model replicas apply the same update. This operation, called AllReduce, returns the combined result to every participating worker.

The model has 350 GB of gradient data at two bytes per parameter, the 16-bit gradients of mixed-precision training that this chapter assumes throughout (FP32 gradients would double the figure). That model-wide figure is not what any one GPU sends. When a reduction partitions the gradient across all 1,024 ranks (the numbered workers of the job), each rank owns a 1/1,024 share, a few hundred megabytes, which the transport examples below round to one assumed gradient-shard size; the job’s tensor, pipeline, and data-parallel split (**[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training#^sec-distributed-training-systems|Distributed Training]]**) sets each GPU’s actual payload. Worked examples that switch to another model, precision, or payload state their parameters explicitly.

A delayed transfer on the step’s critical path can leave the other 1023 GPUs waiting at a job-wide synchronization boundary. The fabric’s contribution to training time therefore depends on which transfers the next computation needs and how much of their cost remains exposed. In that role the fabric is not auxiliary infrastructure; it is the synchronization backbone that decides whether the cluster trains as one machine.

Within the multi-tier fleet hierarchy framed by **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^fig-fleet-stack|The Fleet Stack]]**, the fabric turns isolated accelerator nodes into a coherent training system. Accelerators, power delivery, cooling, racks, and pods define what each node can compute in isolation; the fabric determines whether the nodes can act together before communication cost overwhelms computation. That design space organizes into a **five-level model** of co-dependent tiers, developed in [[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.03 How ML Networking Inverts Data-Center Assumptions#^sec-network-fabrics-five-level-model|section 3.2.1]].

At scale, communication cost can dominate computation cost. The fleet-law decomposition in **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^sec-vol2-introduction-fleet-law|The Fleet Law]]** makes this explicit: the nonoverlapped communication term ${T_{\text{comm}}}({N}) - {T_{\text{overlap}}}$ determines how much of each training step is exposed to the network fabric. The fabric influences the layers above it by determining whether communication can run while independent computation continues, which collective algorithms are viable, and how network partitions interact with node failures. That concurrency, communication-computation overlap, is what the ${T_{\text{overlap}}}$ term credits, because transfer time that proceeds behind useful arithmetic does not lengthen the step.

↪ How layer-by-layer scheduling achieves that overlap, and how much communication it still leaves exposed, is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.11 Communication-Computation Overlap#^sec-communication-overlap|Communication-Computation Overlap]]**.

A collective is a communication operation performed by a group of workers. Its name specifies the result each worker receives, while an algorithm determines the messages that produce that result. The physical network fabric carries three recurring collective communication patterns:

- **AllReduce**: Combines corresponding values from all participants and returns the same result to each; synchronous training uses a sum, followed by normalization, to average gradient contributions across workers.
- **AllGather**: Collects a distinct portion from each participant and returns the concatenated collection to every participant, as required when reconstructing a sharded parameter tensor.
- **AllToAll**: Lets each participant send a distinct portion to every other participant, an exchange central to expert parallelism when workers host different expert subnetworks and must route tokens to their assigned destinations.

Collective communication algorithms orchestrate these patterns, while the fabric layer supplies the physical wires and switches that carry them. The distinction matters because the fabric’s physical properties (bandwidth, latency, and topology) determine which patterns are efficient and which become bottlenecks.

↪ The full set of collective primitives, with the output contract each one guarantees, is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.05 Collective Operation Primitives#^sec-collective-communication-six-core-primitives-8a66|The six core primitives]]**.

**Systems Perspective 3.1: The network as a gradient bus**

In a single machine, the memory bus moves data between the processor and memory. In a distributed training cluster, the network fabric serves an analogous role as the gradient bus that carries contributions between workers. When those exchanges limit progress, the job encounters the network wall mapped across the pod tier in **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.02 The Infrastructure Walls#^fig-three-walls-grid|The Four Infrastructure Walls]]**. Protocols, topologies, congestion control, and collective schedules determine how effectively the job uses the available paths. This bus has a narrow segment. In the reported product chronology, the external-port budgets remain below the aggregate NVLink budget from its first plotted generation onward ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.02 The Synchronization Backbone#^fig-network-bandwidth-scaling|figure 1]]). Product years mix confirmed shipments with announcements and planned availability; they do not establish an exact first-shipment chronology. How much of that gap a job actually feels depends on its message sizes, port provisioning, routing, and contention, so the link ratio bounds the problem rather than predicting a transfer time.

↩︎ Communication dominance at scale, the network wall, is established in **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^sec-introduction-communication-becomes-dominant-e1b6|Communication dominance and the network wall]]**.

^fig-network-bandwidth-scaling

The reference hardware gives the gradient bus analogy a concrete scale. A single H100 has a precision-specific FP16 peak of 989 TFLOP/s and memory bandwidth of 3.35 TB/s. Each GPU’s NVLink ports together provide 900 GB/s of bidirectional bandwidth to its peers within the node. The comparison that matters is per GPU and per direction. In the reference node each GPU has its own network interface card (NIC) with one NDR InfiniBand port, so a tensor leaving the node through that GPU drops from 450 GB/s of NVLink bandwidth to 50 GB/s at the port. This 9× gap is the node boundary’s cliff that the bandwidth hierarchy of **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-bandwidth-hierarchy|Bandwidth hierarchy]]** already identified. The model-wide 350 GB gradient state does not all pass through every 50 GB/s port; partitioning and the collective schedule determine each port’s traffic. Converting that gap into a step-time estimate requires the workload’s local payloads and communication dependencies.

↪ The network hierarchy ratio between intra-node and inter-node bandwidth, with the reference NVLink and InfiniBand values behind it, is developed in **[[05 Reference/Volume II - Scaling/V2 Fleet Foundations#^sec-appdx-fleet-foundations-numbers-to-know|Numbers Every Fleet Engineer Should Know]]**.

Which traffic must cross that gap depends on how the job is partitioned. The same hierarchy keeps tensor parallelism, with its per-layer exchanges, inside the NVLink domain and lets pipeline stages and data-parallel replicas span nodes, the combination called 3D parallelism whose schedules are developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.07 Hybrid Parallelism#^sec-distributed-training-systems-systems-hybrid-parallelism-3d-loop|The 3D training loop]]**. The job has one further lever over that traffic. Each data-parallel replica can sum gradients over several microbatches, the small slices of a batch, before an exchange (gradient accumulation), reducing how often it must cross the node boundary at the cost of changing the batch and update schedule.

Exposed communication leaves gaps between dependent compute phases. Two assumed training schedules on a common 230 ms axis, each containing 100 ms forward and backward compute phases, make that cost visible ([[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.02 The Synchronization Backbone#^fig-bandwidth-cliff-gantt|figure 2]]). The 8-GPU intra-node case assumes a 1 ms AllReduce and spends 99.5 percent of the step in those compute phases; the 64-GPU inter-node case assumes a 30 ms AllReduce and spends 87 percent in computation. The two AllReduce durations are illustrative inputs chosen to show the effect, not values derived from the link rates above, and the percentages are shares of the schedule rather than measured arithmetic utilization.

![[90 Assets/Volume II/03 Network Fabrics/Bandwidth Cliff Gantt 70861b083e.svg]]

Figure 2: **The Bandwidth Cliff in a Training Step**: Illustrative timelines on a common millisecond axis for the same compute phases: an 8-GPU intra-node job (top) with an assumed 1 ms AllReduce, and a 64-GPU inter-node job (bottom) with an assumed 30 ms AllReduce. These durations illustrate an exposed communication cost rather than predict a particular fabric. The AllReduce phase (red) grows from a thin sliver to a larger share of the step. Without overlap, model computation waits during AllReduce. The compute phases occupy 99.5 percent and 87 percent of these illustrative schedules, a gap of 12.5 percentage points; these shares are not arithmetic utilization measurements.

^fig-bandwidth-cliff-gantt

In Fleet Law terms, the widened red block is the part of ${T_{\text{comm}}}({N})$ that no ${T_{\text{overlap}}}$ has hidden. In the inter-node schedule it is 30 ms of every 230 ms step, about 13 percent, and that share applies to every accelerator-hour the cluster spends for the life of the run. Network fabric design therefore belongs at the center of distributed-training design rather than at its edge, and keeping that exposed window small requires rethinking the traffic assumptions that govern conventional data-center fabrics.
