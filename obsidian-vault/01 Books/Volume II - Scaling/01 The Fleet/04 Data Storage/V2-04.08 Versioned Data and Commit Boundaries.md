# V2-04.08 Versioned Data and Commit Boundaries

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-data-versioning-orchestration

If a multi-week training run suffers a sudden loss spike or a deployed model regresses, an engineering team that did not record which shard versions, preprocessing code, and shuffle seeds fed each step cannot tell a model bug from a silent change in the input data. A checkpoint manifest provides one commit boundary per save. The data pipeline that built the training corpus has many, one at every stage that turns raw inputs into processed shards. The storage system must record both the exact bytes read and the preprocessing code, shuffle seed, schema, and integrity checks that produced them before the run began.

**Lighthouse 4.1: Archetype B (DLRM at Scale): Feature store latency**

While Archetype A (GPT-4/Llama-3) trains on static, versioned shards, Archetype B (DLRM at Scale) trains on live feature streams that change every second as users click and interact. Replaying an exact batch then becomes a point-in-time problem, which a feature store answers by keeping a retained, versioned feature log.

↪ Point-in-time correctness, the leakage it prevents, and the storage cost of retained feature history are developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.05 Feature Store Operations#^sec-ml-operations-scale-pointintime-correctness-41f4|Point-in-time correctness]]**.

Even when the underlying shard files are immutable, a distributed loader produces a stream of consumed samples whose versions and order can shift across epochs during a 30-day run. Dataset versioning provides a “Git for data” record by snapshotting the cryptographic hashes[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn13|¹³]] of every data shard, the exact preprocessing code used for tokenization, and the random seeds governing the global shuffle. With that snapshot in place, engineers investigating a mid-run divergence can replay the exact batch that triggered the loss spike and test whether the culprit was a corrupted sample or numerical instability in the optimizer.

At petabyte scale, the data pipeline has to make every transformation reproducible. Raw documents are cleaned, tokenized, packed into training examples, and sharded across storage tiers. Each stage writes an immutable artifact, and each artifact records the input version, code version, schema, and statistical checks it satisfied. Once those dependencies are explicit, the pipeline forms a directed acyclic graph: later artifacts depend on earlier artifacts, and no stage is allowed to rewrite its own history. When a training job starts, the cluster manager verifies that each worker’s local NVMe shards match the data snapshot declared for the run. Treating the data pipeline as a graph of versioned artifacts rather than a simple file transfer makes silent data drift detectable and attributable to a specific stage, code version, or input snapshot. Immutability also pays a storage dividend. Because an artifact never changes once written, a manifest can name it by content identifier, a hash of its bytes, and many experiments can reference the same unchanged shards without copying entire datasets.

### Replay and Commit Boundaries in Data Pipelines

^sec-storage-distributed-transformation-semantics

When a tokenization worker crashes halfway through building a shard of the running example’s corpus, its replacement must decide which raw documents to process again without silently dropping records or writing duplicates. Versioned artifacts identify *what* a pipeline produced, while commit and replay rules determine whether mid-stage failures can alter that result. The storage system’s part in that decision is the commit boundary, the point at which a stage’s output becomes durable and visible downstream, the same contract that [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|section 4.6]] applied to checkpoint generations. That shared contract is why a storage chapter owns these semantics, because whether a replay loses or duplicates data is decided by what the store has committed. The restarted worker compares its input position with the last committed output and replays everything after it, so the work at risk is whatever accumulated past the last commit.

Two service-rate effects govern how much uncommitted work accumulates. Records are assigned to workers by a partition key, such as a document’s source or a user identifier, and partition skew arises when one key owns disproportionate work and holds its stage open while the rest of the fleet idles. Backpressure propagates a slow downstream stage’s limit upstream by slowing admission or bounding in-flight data, a control response to overload rather than another name for slow processing.

Failures near the commit boundary raise a correctness question, and three guarantees answer it differently. At-most-once processing never replays uncertain work, so a document that was read but whose output was never confirmed is lost. At-least-once processing replays everything after the last confirmed commit, so a document whose output was written but not yet confirmed is written twice. An effectively exactly-once outcome combines replayable inputs with idempotent writes, writes that leave the same result however many times they repeat, or with transactional output keyed by a stable event or transaction identifier ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-akidau2015|Akidau et al. 2015]]). Reliably delivering each record from one worker to the next cannot provide this guarantee on its own, because the duplicate arises from the worker’s own replay. The streaming feature pipelines of Archetype B (DLRM at Scale) face this question on every event.

**Example 4.2: The acknowledgment gap**

**Failure trace**: A feature-pipeline worker writes the output row for click event `e42`, then crashes before it records that the write succeeded. Its replacement cannot tell whether `e42` was committed. Skipping the event risks losing it. Replaying it with an append writes the feature row a second time, so that click counts twice in every training set built from the table. Writing the row under the stable key `(feature_version, e42)` turns the replay into an overwrite of the same row, so the uncertain event can be reprocessed safely.

**Systems lesson**: Exactly-once belongs at the output commit boundary, whose record must bind the input position, transformation version, stable identifier, and commit state.

^exmp-storage-acknowledgment-gap

The two replays differ only in how the output is addressed. An append gives every attempt its own row, while a write under a stable key sends every attempt to the same row, so reprocessing uncertain work leaves the stored result unchanged ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.08 Versioned Data and Commit Boundaries#^fig-storage-commit-boundary|figure 9]]).

![[90 Assets/Volume II/04 Data Storage/Data Storage Commit Boundary df9e61cc04.svg]]

Figure 9: **The Acknowledgment Gap at a Commit Boundary**: A worker stores the output row for event e42 and crashes before it records the commit, so its replacement cannot tell whether the row exists and must replay the event. (a) Appending the replayed row duplicates it, and the click counts twice in every training set built from the table. (b) Writing under the stable key (feature_version, e42) makes the replay an overwrite of the same row, so at-least-once replay produces an effectively exactly-once result.

^fig-storage-commit-boundary

Streaming adds a time boundary to the contract. Event time records when an event occurred; processing time records when a worker handled it. A pipeline that aggregates clicks per hour must decide when an hour is finished, even though events can arrive late. A watermark is its running estimate that every event up to some event time has arrived, which lets it close that window and emit the result; a late-data policy determines whether later arrivals update, retract, quarantine, or drop the result ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-akidau2015|Akidau et al. 2015]]). Watermarks therefore trade freshness against completeness rather than prove that no older event remains.

Each of these mechanisms buys one property at the cost of another. Buffering absorbs finite bursts or temporary slowdowns but increases recovery state and freshness lag; sustained overload still requires backpressure or more service capacity. Aggressive watermarks reduce delay but exclude more late data, while replays help only when writes are safe to repeat. These choices change the stored result, because a feature table closed under an aggressive watermark holds different rows from one closed under a lenient watermark. A reproducible training snapshot must therefore record source and code versions alongside partitioning, replay policy, stable identifiers, watermark state, and late-data decisions. That record is what lets a later feature backfill, a replay of history under new code, rejoin features at the correct points in time without mixing old and new histories.

↪ Feature backfills that replay history under this snapshot contract are developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.05 Feature Store Operations#^sec-ml-operations-scale-backfill-procedures-eb66|Backfill procedures]]**.

### The Synthetic Fuel Line

^sec-storage-synthetic-fuel

The versioned-artifact contract applies to generated training samples as well as collected ones. When a fleet generates candidate samples, filters them, and verifies the survivors, each stage adds storage traffic and records that must remain linked to the accepted payload. The pressure to generate comes from the compute-optimal allocation of **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.04 AI Scaling Laws#^sec-vol2-intro-ai-scaling-laws-a043|AI Scaling Laws]]**, which grows the token budget with the parameter count. As high-quality human-generated text becomes harder to expand, the fleet encounters the **data wall**: the point where additional training samples must increasingly come from synthesis, simulation, curation, or expensive human collection ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-villalobos2024will|Villalobos et al. 2024]]).

This shift from simple collection to managed data generation sends more than payload bytes through the hierarchy. A “synthetic fuel line” must also store the **provenance chain** of every sample: which model generated it, which filters accepted or rejected it, which verifier models scored it, and which downstream run consumed it. That lineage makes repeated reuse of generated material traceable, and the data wall invites that reuse, because a fleet short of new human-generated text can end up training on its own earlier outputs. The lineage record therefore supports investigation of **model collapse**, where recursive training on generated data can degrade the learned distribution ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-shumailov2024|Shumailov et al. 2024]]); retaining provenance alone does not prevent the degradation. The storage design must separately budget retained artifacts and the repeated scans used to assess them.

**Napkin Math 4.8: The storage cost of synthetic data**

**Problem**: A 1 TB synthetic dataset retains provenance metadata and undergoes three independent verification scans. How much persistent capacity and pipeline traffic does it require if verifier outputs are not retained as full dataset copies?

1.  **Raw Payload**: 1 TB.
2.  **Provenance Overhead**: 40 percent extra for lineage hashes, generation logs, and verifier scores.
3.  **Verification Traffic**: 3 verifier passes each read the payload, producing 3 TB of read traffic. Their scores reside in the provenance metadata rather than in three retained payload copies.
4.  **Capacity Result**: Persistent capacity is 1 TB $\times$ 1.4 = 1.4 TB, a 1.4× capacity factor.
5.  **Traffic Result**: Writing the payload and metadata once and reading the payload three times moves 4.4 TB, a 4.4× traffic factor before generation and verifier compute are counted.

**Systems insight**: Verification primarily draws on service rate and compute, while retained provenance consumes capacity. The two costs coincide only when the pipeline materializes each verifier output as another full dataset. Synthetic storage must therefore budget bytes at rest separately from bytes moved and record which generator, filters, verifiers, and downstream runs produced each accepted sample.

Generated data therefore makes lineage part of the payload, so the store must budget retained provenance and verification traffic alongside the samples themselves.

**Self-Check: Question**

1.  A feature-pipeline worker writes the output row for click event `e42`, then crashes before it records that the write succeeded. Its replacement cannot tell whether the row was committed. Which design lets the replacement reprocess `e42` without losing the event or counting it twice?

    1.  Write each output row under a stable key such as `(feature_version, e42)`, so a replay overwrites the same row instead of appending a second one.
    2.  Switch the stage to at-most-once processing, so uncertain events are never replayed.
    3.  Deliver messages between workers over a reliable transport, so every message arrives exactly once.
    4.  Lengthen the watermark delay, so late events have more time to arrive before the window closes.

2.  A team generates a $1\text{ TB}$ synthetic text dataset. Retained provenance adds $40\%$ metadata overhead, and 3 verifier models each read the payload once without materializing another full copy. What persistent capacity and total pipeline traffic are required?

    1.  $1.4\text{ TB}$ of persistent capacity and $4.4\text{ TB}$ of traffic: $1\text{ TB}$ payload write, $0.4\text{ TB}$ metadata write, and $3\text{ TB}$ of verifier reads.
    2.  Exactly $1.0\text{ TB}$, because verifier models run entirely in GPU registers without generating persistent storage artifacts.
    3.  Roughly $0.4\text{ TB}$, because synthetic data compresses more efficiently than natural language text.
    4.  Roughly $14\text{ TB}$, because every verifier model stores a full $350\text{ GB}$ copy of its internal neural activations for every sample.
