# V2-04.03 How ML Workloads Invert Storage Assumptions

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-workload-inversion

A database administrator moving to an ML infrastructure team would find many familiar storage design principles inverted by the multi-terabyte sequential scans and checkpoint bursts of the 175B running example. Transactional databases emphasize small random accesses and strong consistency, issuing thousands of 4 KB reads per second to serve user queries. Storage designs for that regime combine caching algorithms that assume recently accessed records will soon be requested again, write-ahead logs that save each change before applying it, which supports point-in-time recovery, and redundant array of independent disks (RAID),[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn1|¹]] which trades capacity and performance for fault tolerance. Full-corpus pretraining breaks the locality and access-size assumptions behind that stack while retaining the need to protect durable state; fine-tuning, curriculum learning, hard-example mining, recommendation features, and retrieval introduce their own skewed working sets, so each inversion below is a property of the workload rather than of ML as a whole.

Full-corpus pretraining inverts these assumptions when samples are packaged into sequential shards (large files that each hold many samples), allowing the pipeline to stream through datasets that span hundreds of terabytes. Individual accesses are large (megabytes rather than kilobytes) because models consume batches of images or text sequences, while immutable, versioned training shards avoid read-write conflicts during a run even though checkpoint publication and live feature updates still require explicit consistency guarantees. Image and video workloads can demand hundreds of gigabytes per second for days or weeks, whereas compact tokenized text can require much less input bandwidth even when checkpoint writes dominate total traffic. The mismatch between what storage was optimized for and what ML actually needs creates the **I/O wall** (principle [[01 Books/Volume II - Scaling/01 The Fleet/V2 Fleet Principles#^pri-io-wall|7]]): when storage throughput cannot deliver training data as fast as accelerators consume it, GPUs idle regardless of their computational power. For bandwidth-heavy image and video inputs, that wall arrives when accelerator count grows faster than provisioned storage throughput, making the *data pipeline*, not the *model*, the limiting factor whenever a fixed input service time cannot keep pace with faster compute.

↪ How storage stalls surface as communication or coordination bottlenecks in the C$^3$ taxonomy is developed in **[[05 Reference/Volume II - Scaling/V2 The C³ Taxonomy#^sec-appdx-c3-taxonomy-storage-substrate|Storage as the persistent substrate]]**.

**Systems Perspective 4.1: The moving I/O bottleneck**

Hold the batch representation and storage path fixed while improving compute throughput. The batch now finishes sooner, leaving less time to deliver the next one. Prefetching can overlap delivery with execution, but it cannot overcome a sustained service-rate deficit. This compute-to-storage imbalance does not imply that every larger model is input bound. A model that performs more computation on the same batch can instead give storage more time. The design must follow workload service times, not advertised peak-throughput trends.

A normalized example isolates the effect. Suppose input delivery takes one quarter of the original compute time and overlaps perfectly with computation, so each batch takes the longer of the two service times. Doubling compute speed halves batch time, and quadrupling it halves batch time again, at which point compute and delivery take equal time. Beyond that point the pipeline is delivery bound. A sixteenfold faster accelerator still raises batch throughput only fourfold, and the remaining compute sits idle behind the input path. That plateau is an I/O wall for this workload and allocation. Faster storage, a more compact representation, or additional independent input paths can move it; deeper prefetching alone cannot.

The first inversion is access pattern. Where database workloads issue *random access patterns* that benefit from seek-time optimization, full-corpus pretraining performs large *sequential scans*. An epoch in the running example reads each selected sample once, in the order produced by shard and buffer shuffling, so the pattern resembles video streaming more than database queries. Storage systems optimized for random IOPS[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn2|²]] waste capabilities on this workload, whereas systems optimized for sequential throughput excel. The penalty for the wrong pattern is large. A Gen4/Gen5 NVMe drive delivers roughly 7–14 GB/s for sequential reads, while small 4 KB random reads can fall near 0.5 GB/s, an order-of-magnitude to 30$\times$ drop. Hard drives pay an even steeper 100$\times$ throughput reduction because mechanical seek times dominate random access.

The shuffling that ML training requires adds a complication rooted in the requirements of stochastic gradient descent. Stochastic gradient descent requires that each mini-batch be drawn approximately uniformly from the training distribution; presenting samples in a correlated order (all samples from the same document, all images from the same class) biases the gradient estimates and slows or destabilizes convergence. True global shuffling would satisfy this requirement perfectly, but it requires random access across the entire dataset, destroying the sequential access pattern that storage hardware demands. Even for a multi-terabyte corpus, random per-sample seeks are I/O-prohibitive. A round illustrative dataset of 1 trillion 4-byte tokens (about 4 TB) stored as individual elements on NVMe and accessed at random would take hundreds to thousands of hours to read at the drive’s random-read IOPS rate, rather than about ten minutes of sequential streaming. The practical solution is therefore a compromise that shuffles the order of large data shards and then shuffles samples within each shard’s local buffer. This preserves sequential I/O, but adequate mixing depends on shard composition and buffer size, a dependence [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^sec-storage-multi-worker|section 4.4.2]] turns into a validation step for the loader.

The second inversion is working set size. Traditional applications rely on temporal locality. A web server repeatedly accesses popular pages, and a cache holding the top 10 percent of content serves 90 percent of requests. In the chapter’s full-corpus pretraining scenario, the 6 TB serialized corpus has no “popular” token range; each selected token is consumed once per epoch. A cache of any practical size holds only a small fraction of the corpus, and most samples are effectively “cold” when accessed. This access pattern makes traditional recency caching much less effective. A least recently used (LRU)[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn3|³]] cache can approach a 0 percent hit rate for a cyclic scan larger than the cache, because each sample is evicted before its next access. With independently reshuffled epochs, cross-epoch hits are low but nonzero and depend on the cache fraction and sample order.

Other training policies create different locality. Multi-task or curriculum learning, hard-example mining, and filtered sampling access some subsets more frequently during particular phases. This temporary working set lets the NVMe tier exploit locality. Large-scale pretraining jobs that repeatedly scan a fixed corpus remain the scenario for the hierarchy derived here; systems serving another sampling policy should measure its reuse distribution before adopting the same cache design.

The third inversion is write pattern. Transactional systems generate continuous streams of small writes, each immediately durable. ML systems generate occasional large writes when saving checkpoints. A 175B parameter model checkpoint, including optimizer state, occupies roughly 2,450 GB. Saving it every 10 minutes generates concentrated bursts that saturate bandwidth for seconds, followed by long idle periods. These synchronized bursts, called checkpoint storms and defined formally in definition [4.5](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#dfn-data-storage-checkpoint-storm), must be absorbed by the shared file system without disrupting ongoing training reads. The bursty write pattern is particularly challenging because all nodes in the cluster write their checkpoint shards simultaneously. If 256 nodes each write 10 GB, the parallel file system receives 2.4 TB of writes in a single burst, which blocks training if the job writes synchronously to that tier. Local staging and asynchronous replication can shorten this pause, as [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|section 4.6]] develops. When checkpoint and gradient traffic share one fabric, traffic isolation also keeps the burst from delaying the job’s collectives.

↩︎ Traffic isolation and quality-of-service mechanisms are established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.09 Network Virtualization#^sec-network-fabrics-qos|Traffic isolation and quality of service]]**.

The fourth inversion is subtler. The read/write ratio shifts by lifecycle phase. During the intervals between checkpoints, the input pipeline reads continuously. Across a complete run, however, the read/write ratio depends on input size, epoch count, checkpoint size, and save frequency. The running language-model example produces far more checkpoint bytes than training-input bytes despite spending most of its time between saves. During data preprocessing, both reads and writes are heavy, and the access pattern more closely resembles a MapReduce job than a training loop. Tokenization, deduplication, and shuffling scan the raw corpus once (large sequential reads) and write intermediate artifacts (large sequential writes). The next stage then scans those artifacts again. A 3 TB compressed text corpus typically expands to 6 TB of tokenized shards before the first training epoch begins, loading each storage tier differently from the read-only training phase that follows. No single storage configuration optimizes for all phases, which is why ML systems require a multi-tier hierarchy rather than a single storage technology.

A fifth inversion emerges when comparing training and inference workloads. *Training* reads datasets sequentially and writes checkpoints in bursts. Weight-resident *inference*, by contrast, performs one large model read at startup and then serves requests from HBM. Its storage challenge is cold-start latency: the time required to load a model when scaling up or recovering from failure. The limiting constraint flips from sustained dataset throughput to a bulk read whose duration depends on which tier supplies the weights. Retrieval, KV-cache offload (moving a request’s saved attention state out of HBM), and models larger than aggregate HBM create additional serving-time I/O, so this weight-resident case is a baseline rather than a universal inference pattern. [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.10 Storage for Serving#^sec-storage-inference|Section 4.9]] derives the load times and connects that baseline to the retrieval workload that follows.

Serving at fleet scale also creates a fan-out read burst. A serving cluster with 100 replicas of the 175B running model holds 35 TB of FP16 weights, and a model rollout must deliver a new version to every replica within minutes while the old version keeps serving. The burst is the checkpoint storm in reverse. Instead of many nodes *writing* to shared storage at once, many nodes *read* the same data at once.

| **Workload pattern**       |          **Traditional assumption**          |                            **ML reality**                             |
|:---------------------------|:--------------------------------------------:|:---------------------------------------------------------------------:|
| **Access pattern**         |                Random access                 |                         Sequential streaming                          |
| **Working set**            | Fits in cache, with strong temporal locality |      Exceeds all cache levels; low locality in full-corpus scans      |
| **Write pattern**          |           Continuous small writes            |                          Bursty large writes                          |
| **Read/write ratio**       |                   Balanced                   |            Phase-dependent (read-only to write-dominated)             |
| **Training vs. inference** |      One access pattern for all phases       | Corpus streaming in training; bulk model loads and fan-out in serving |

Table 1: **ML Workloads Invert Traditional Storage Assumptions**: The five inversions of full-corpus training and serving. Where databases optimize for random IOPS with cacheable working sets, ML training streams sequentially through datasets that exceed all cache levels and writes state in bursts, its read/write balance shifts by lifecycle phase, and serving replaces dataset streaming with bulk model loads.

^tbl-storage-assumptions

Together, the five inversions collected in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.03 How ML Workloads Invert Storage Assumptions#^tbl-storage-assumptions|table 1]] reduce to one procurement rule, which is to optimize for streaming reads and bursty writes rather than database-style random IOPS. An organization provisioning storage for ML based on database-era heuristics will over-invest in random IOPS for sequential training shards, under-invest in the sustained bandwidth those shards require, and fail to account for the bursty write patterns that checkpointing creates.

**Checkpoint 4.1: Storage workload analysis**

Consider the storage subsystem for a new ML training cluster with 512 GPUs. The primary workload will train large language models on a 10 TB text dataset.

**Database heuristics**: use the five storage workload inversions to name at least three database optimization strategies that would be counterproductive for this workload.

**Epoch reads**: calculate the total data volume read when each training epoch reads the full 10 TB dataset once and the cluster trains for 100 epochs, then compare it to a typical database workload.

**Checkpoint bandwidth**: calculate the minimum write bandwidth required when the model saves a 500 GB checkpoint every 15 minutes and each save must complete within 30 seconds.

**Write duty cycle**: calculate the percentage of time the storage system spends in “write mode” vs. “read mode” under bursty checkpoints every 15 minutes.

Translating these five inversions into a concrete architecture requires separating how a dataset is packaged from how fast each storage tier must serve it. The required delivery rate depends on workload demand rather than parameter count alone. It equals the aggregate input bytes consumed during a delivery window divided by that window, a rate that representation, batch size, parallelism, and compute time jointly set ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^sec-storage-pipeline-equation|section 4.4]]) and that prefetching alone cannot sustain when demand exceeds a tier’s allocated share. In the running example, the 1.5 trillion tokens of training data produce roughly 6 TB of sequential token-ID reads per epoch from a 3 TB compressed source corpus. Stored as one file per sample, that corpus would spend its storage budget on file opens rather than payload bytes, the metadata bottleneck that [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier3-pfs|section 4.3.6]] develops as the small file problem. Preprocessing the corpus into large sequential shards ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-aizman2019|Aizman et al. 2019]]) amortizes open, seek, and close costs across many tokens without changing the payload byte rate ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-data-formats|section 4.3.5]]). Where those shards should live, and how close to the accelerator, is the question the storage hierarchy answers.

**Self-Check: Question**

1.  A storage procurement team is sizing storage hardware for a cluster dedicated to pretraining foundation models on a $200\text{ TB}$ immutable text corpus. Which purchasing decision represents the most severe misallocation of budget based on ML workload characteristics?

    1.  Paying a premium for enterprise SSDs optimized for high $4\text{ KB}$ random-read IOPS while under-provisioning sustained sequential read bandwidth (GB/s).
    2.  Aggregating raw text samples into $256\text{ MB}$ to $4\text{ GB}$ contiguous binary shards prior to training to amortize file-system metadata operations.
    3.  Provisioning local NVMe drives on compute nodes to serve as a warm read cache for multi-epoch training passes.
    4.  Sizing the parallel file system write tier to absorb synchronized multi-terabyte checkpoint write bursts from hundreds of nodes.

2.  True or False: An in-memory LRU cache sized to $300\text{ GB}$ placed in front of a $3\text{ TB}$ uniformly shuffled pretraining dataset will achieve roughly a $90\%$ hit rate after the first epoch warms the cache because all samples are reused across epochs.

3.  Explain why ML data loaders implement shard-level shuffling combined with within-shard buffer mixing rather than true global per-sample random shuffling across petabyte-scale training corpora.

4.  When an inference platform deploys a new version of a 175B-parameter model ($350\text{ GB}$ FP16 weights) across 100 serving replicas, how does the storage access profile contrast with a training checkpoint save?

    1.  It generates continuous small random writes to update parameter journals on each replica node.
    2.  It streams an incremental delta of only modified parameters over hours to minimize bandwidth utilization.
    3.  It creates a synchronized fan-out read burst of roughly $35\text{ TB}$ ($100 \times 350\text{ GB}$) that must complete within the deployment latency budget while serving traffic continues.
    4.  It requires sustained multi-gigabyte-per-second sequential write bandwidth to central durable object storage.

5.  A team plans one storage configuration for the whole life of a language-model project: tokenizing and deduplicating a $3\text{ TB}$ compressed corpus into $6\text{ TB}$ of shards, then training on those shards with periodic checkpoints. Why does the chapter conclude that no single configuration optimizes every phase?

    1.  Preprocessing reads and writes large sequential artifacts in MapReduce-like passes, while training reads immutable shards between bursty checkpoint writes, so the read/write balance and access pattern change by phase.
    2.  Training reads are dominated by small random lookups that only a database-style random-IOPS tier can serve, while preprocessing is purely sequential.
    3.  The tokenized corpus is smaller than the compressed source, so preprocessing frees capacity that the training phase cannot use.
    4.  Checkpoint writes are continuous and small, so they require a different write-ahead log configuration than preprocessing.
