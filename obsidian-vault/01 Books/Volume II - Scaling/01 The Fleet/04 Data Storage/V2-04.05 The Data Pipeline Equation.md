# V2-04.05 The Data Pipeline Equation

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-pipeline-equation

Whether a training job streams from object storage or reads from local NVMe, each worker’s next batch must reach HBM before the current compute step finishes; falling short starves the fleet’s accelerators, while provisioning far above demand strands capital in idle storage bandwidth. Sizing the hierarchy therefore begins by turning the accelerator consumption rate into a required byte rate. The data pipeline throughput equation in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^eq-pipeline-throughput|equation 2]] quantifies the bandwidth the pipeline must sustain for a target training rate:

$$
{\text{BW}_{\text{required}}} = {N_{\text{GPU}}} \times {\eta_{\text{target}}}\times \frac{{D_{\text{vol}}^{(\text{batch})}}}{{T_{\text{compute}}}} \tag{2}
$$

^eq-pipeline-throughput

where ${N_{\text{GPU}}}$ counts accelerators consuming distinct local input batches, ${\eta_{\text{target}}}$ is the target fraction of wall-clock time spent computing (typically 0.8 to 0.95), ${D_{\text{vol}}^{(\text{batch})}}$ is one local batch in bytes, and ${T_{\text{compute}}}$ is its uninterrupted compute time. Devices that cooperate on one batch do not each require an independent storage read, so their shared input must be counted once at the tier being sized.

The target fraction decides which rate the pipeline must meet. Eliminating sustained input stalls requires sizing the pipeline to full demand, which supplies batches at the full compute rate. A target fraction below one sizes it for a slower training rate that the team has chosen to accept. This target is an active-time fraction, not model FLOPs utilization. If iteration time already includes stalls, multiplying by the target fraction again would count the slowdown twice. The text-versus-image comparison of notebook [4.1](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#nbk-data-storage-text-vs-image-bandwidth) already applied this equation with ${\eta_{\text{target}}}= 1$; the equation makes the target fraction explicit, and the service chain below adds the requirement that every stage, rather than the accelerator-facing endpoint alone, meet the resulting rate.

The demand equation sizes the accelerator-facing endpoint, but bytes must traverse the complete service chain. Let ${r}_{{j}}$ denote the measured service rate of stage ${j}$, including object-store reads, network transfer, decoding and augmentation, host-memory copies, and host-to-device transfer. Express all rates in the same output-equivalent bytes per second, using each stage’s expansion or compression ratio; raw compressed-read bandwidth cannot be compared directly with decoded-tensor bandwidth. With bounded buffers and no sustained backlog, the pipeline can deliver at most

$$
{r_{\text{pipeline}}}= \min_{{j}} {r}_{{j}}, \qquad {r_{\text{pipeline}}}\geq {\text{BW}_{\text{required}}}. \tag{3}
$$

^eq-storage-service-chain

Capacity at one tier cannot compensate for a slower downstream stage. Compression may raise the storage-read rate while lowering the decode rate; additional loader workers may raise decoding throughput while saturating the host-memory or PCIe stage. GPUDirect Storage ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass#^sec-storage-gds|section 4.5]]) can drop the host-copy stage from the chain, which raises the minimum when that copy is the limiting stage or takes cores from the stage that is. The end-to-end inequality in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^eq-storage-service-chain|equation 3]] therefore turns the chapter’s hierarchy into a testable contract. Measure every stage under representative concurrency, then provision or overlap the stage whose service rate is the minimum.

The throughput equation in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^eq-pipeline-throughput|equation 2]] exposes four levers on storage demand, and none of them is free. Reducing the accelerator count (${N_{\text{GPU}}}$) lowers aggregate input demand by reducing the number of distinct consumers, but it lowers training throughput with it, whereas lowering target utilization (${\eta_{\text{target}}}$) relaxes the delivery rate only by accepting idle accelerators. Decreasing the per-batch data volume (${D_{\text{vol}}^{(\text{batch})}}$) through a more compact representation of the same samples helps only while decoding keeps pace, and shrinking the batch itself changes the training configuration and its statistical efficiency. Increasing compute time (${T_{\text{compute}}}$) gives storage longer to deliver each batch, at the cost of proportionally longer iterations. This is also why a faster accelerator can expose an input bottleneck that a slower one hid. The equation therefore sizes the pipeline for a chosen training configuration; deliberately slowing useful computation does not improve delivery.

The consequences of falling short are captured by the **data stall ratio**, defined in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^eq-data-stall|equation 4]] as the fraction of each training step where the accelerator waits for data:

$$
\text{Data Stall \%} = \frac{{T_{\text{step}}}- {T_{\text{compute}}}}{{T_{\text{step}}}} \times 100 \tag{4}
$$

^eq-data-stall

The data stall ratio covers one worker’s input path with communication excluded, so its ${T_{\text{step}}}$ is compute plus exposed input wait. The Fleet Law of **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^sec-vol2-introduction-fleet-law|The Fleet Law]]** carries no input-wait term, so it implicitly treats the next batch as already resident. Whatever input wait the loader fails to hide adds to the distributed step on top of ${T_{\text{comm}}}({N})$ and ${T_{\text{sync}}}({N})$, as compute (${C}_1$) capacity that sits idle while storage catches up. In a real distributed job, the gap ${T_{\text{step}}}- {T_{\text{compute}}}$ also contains exposed communication and synchronization, so the ratio implicates storage only when that gap is measured as time spent waiting on the input queue, separately from collectives and barriers. Without overlap, step time adds compute and I/O time. Pipelining reduces step time to the longer of the two durations and stall time to the positive difference between I/O and compute.

**Napkin Math 4.5: The data stall ratio**

**Problem**: A GPU processes a batch in 200 ms, but storage takes 250 ms to deliver the next batch. What fraction of each training step is the accelerator idle, and how much does pipelining I/O with compute reduce that stall?

*Without pipelining* (sequential I/O then compute):

$$
T_{\text{step}} = T_{\text{IO}} + T_{\text{compute}} = 250 + 200 = 450 \text{ ms}
$$

$$
\text{Stall \%} = \frac{250}{450} = 55.6\%
$$

*With pipelining* (I/O overlapped with compute):

$$
T_{\text{step}} = \max(200, 250) = 250 \text{ ms}
$$

$$
\text{Stall \%} = \frac{250 - 200}{250} = {20\%}
$$

**Systems insight**: Even with pipelining, the accelerator is idle 20 percent of the time. To eliminate the stall entirely, the next batch must arrive within the 200 ms compute window, either by increasing effective storage bandwidth or by adding parallel I/O streams. Deeper prefetch buffers cannot help here, because the delivery time exceeds the compute window on every step rather than merely in the tail.

The data stall ratio measures time lost waiting for inputs relative to the chosen iteration window. Acceptable stall time depends on the fleet’s cost and throughput objectives; a threshold is a policy choice, not a universal storage-health boundary. Instrument batch-ready times and accelerator execution in the same trace to distinguish input starvation from synchronization, CPU preprocessing, and other idle intervals. General profiling tools can expose these events, but an idle accelerator alone does not identify storage as the cause.

↪ An I/O-wait efficiency target for the fleet Data axis is developed in **[[05 Reference/Volume II - Scaling/V2 The C³ Taxonomy#^sec-appdx-c3-dam-scorecard|Fleet diagnostic scorecard]]**.

A storage pipeline that met its budget at launch can drift out of it as datasets grow, jobs contend, and drives age, so it requires continuous monitoring to keep silent bottlenecks from eroding training efficiency. Key metrics to track in real time include per-tier bandwidth utilization (NVMe, network, object storage), prefetch buffer depth (how many batches are queued and ready), the data stall ratio per GPU, the parallel file system’s metadata operation rate, and NVMe drive health indicators (wear level, temperature, error counts). Alert thresholds should trigger before stalls become visible in training loss curves. An undetected 5 percent increase in data stall ratio across the 1,024-GPU reference cluster (half the running cluster) for just one week wastes about \$17,203 in idle compute (1,024 GPUs $\times$ \$2/GPU-hour $\times$ 168 hours $\times$ 5 percent). Comprehensive storage monitoring is therefore a first-order economic concern rather than an operational nicety.

Diagnose a storage stall at three levels. The application timeline identifies when the accelerator waits; per-worker rates and queue depth identify the pipeline stage that falls behind; device and shared-server counters show which resource limits that stage. Correlating those observations distinguishes a byte-bandwidth shortage from metadata contention or insufficient decoding capacity. Because a small development dataset may hide the contention and accumulated state of a production run, a pipeline stress test should use representative data volume and concurrency and run long enough to expose queue depletion, resource leaks, and memory pressure before the loader is coupled to an expensive training job.

The terms in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^eq-pipeline-throughput|equation 2]] explain why the chapter’s workloads place such different demands on the same cluster. In the bandwidth comparison of notebook [4.1](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#nbk-data-storage-text-vs-image-bandwidth), image classification with ResNet-50 on ImageNet combines large compressed samples (116 KB per image on average) with short iteration times (100 to 200 ms), pushing ${D_{\text{vol}}^{(\text{batch})}} / {T_{\text{compute}}}$ high, whereas language-model pretraining packs 4,096 4-byte token IDs into 16 KB per sequence even though total volume over the run still reaches trillions of tokens. Recommendation model training, the Archetype B (DLRM at Scale) workload, combines both access modes. Embedding lookups require high-IOPS random access to the embedding table while the dense layers stream sequential training batches. Which storage tier limits delivery therefore follows the workload’s access profile rather than cluster size alone. Archetype C (Federated MobileNet) falls outside this shared-storage analysis, because its raw training data stays on the devices that produce it; there is no central corpus to stage, and its storage constraints become per-device capacity and upload limits.

Each submission emulates a set of accelerators that consume samples with a fixed per-sample compute time, so the storage system, not a real GPU, sets the pace. Each submission reports the read throughput the system sustained while keeping the emulated accelerators at least 90 percent busy (70 percent for CosmoFlow, which trains on 3D cosmology simulation data) ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-mlcommons2024storage|MLCommons 2024]]; [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-devarajan2021dlio|Devarajan et al. 2021]]). Across the 124 passing results of the closed division in the 2024 round, sustained throughput grows in proportion to the number of emulated accelerators, as the ${N_{\text{GPU}}}$ term of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^eq-pipeline-throughput|equation 2]] predicts ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^fig-mlperf-storage-demand|figure 3]], panel a).

Per accelerator, the median demand differs about 15× across workloads. ResNet-50 is demanding by image-classification standards, yet it is the lightest of the three because its samples are small 2D images while 3D U-Net reads whole medical volumes. An emulated H100 needs about 2.8 GB/s for 3D U-Net on medical volumes, 0.55 GB/s for CosmoFlow, and 0.18 GB/s for ResNet-50 ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^fig-mlperf-storage-demand|figure 3]], panel b). Emulating H100s instead of A100s raises every workload’s demand by 1.6–2×, because the faster accelerator shortens ${T_{\text{compute}}}$ while the bytes per batch stay the same. A storage tier sized for one accelerator generation is therefore undersized for the next, even when the dataset and the model do not change.

Because ${\text{BW}_{\text{required}}}$ grows linearly with ${N_{\text{GPU}}}$, adding compute nodes against a fixed shared file system moves any workload leftward along [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^fig-data-stall-frontier|figure 4]] until supply equals demand; past that saturation knee, additional GPUs add cost without raising training throughput, and [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^eq-pipeline-throughput|equation 2]] locates that limit from the storage tier’s measured bandwidth. Even to the right of the knee, however, the frontier in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^fig-data-stall-frontier|figure 4]] assumes that storage reads and CPU preparation overlap computation completely and that latency spikes never empty the input queue. Achieving that overlap in practice requires pipelining the loader stages and sizing a prefetch buffer deep enough to absorb tail delays.

### Pipelining and Prefetching

^sec-storage-pipelining

When a data loader waits until the GPU finishes batch ${k}$ before reading and decoding batch ${k}+1$, the accelerator sits idle across the entire storage read and CPU preparation window on every step, as panel (a) of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^fig-data-pipeline-vol2|figure 5]] shows. Pipelining removes that synchronous stall by staging and preparing batch ${k}+1$ on host resources while the GPU trains on batch ${k}$, turning the sum of input and compute time into their maximum (**[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-dam-coordination-sum-max|D·A·M coordination from sum to max]]**). When delivery keeps pace and enough prepared work sits in host memory to absorb latency variation, four batches finish in about the time sequential loading needs for two (panel (b)); at fleet scale, the open question is how deep that buffer of prepared work must be.

![[90 Assets/Volume II/04 Data Storage/Data Pipelining e34a3dd242.svg]]

Figure 5: **Pipelined Data Loading**: Both panels share one time scale, with illustrative stage durations. Sequential loading (a) leaves the GPU idle while each batch is read and prepared. Pipelined loading (b) reads and prepares batch ${k}+1$ while the GPU trains on batch ${k}$, so four batches finish in about the time sequential loading needs for two (dashed line). The shaded column marks one instant with three batches in flight. The overlap hides storage latency only while delivery keeps pace with compute and the prefetch buffer is deep enough to absorb variance.

^fig-data-pipeline-vol2

Pipelining converts a sequential bottleneck into overlapped execution ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^fig-data-pipeline-vol2|figure 5]]), but continuous saturation requires a prefetch buffer deep enough to absorb variance in I/O latency. Stage durations need not be deterministic if ready batches cover the delays. Storage systems experience I/O jitter: variation in read latency caused by contention and background work. NVMe drives suffer occasional latency spikes during internal garbage collection (when the controller reorganizes NAND flash blocks) or wear-leveling operations. Parallel file systems incur spikes when multiple training jobs contend for the same OSS nodes, when the MDS processes a burst of metadata operations, or when background scrubbing detects and repairs bit errors. Object storage likewise exposes delays from shared-service contention and maintenance.

A single slow I/O creates a “bubble” when it exhausts the pipeline’s ready work. If the CPU is preparing batch ${k}+1$ with no additional batches ready, a delayed read can leave batch ${k}+1$ unavailable when the GPU finishes batch ${k}$. The GPU then idles until the batch is ready. A longer queue tolerates a longer interruption, and delivery faster than consumption can refill it afterward. Rather than preparing just one batch ahead, the CPU maintains a queue of ${N_{\text{prefetch}}}$ preloaded batches.

A buffer sized to the measured p99 I/O delay needs enough ready batches to cover that delay without draining:

$$
{Q_{\text{prefetch,min}}}= \left\lceil \frac{{T_{\text{IO,p99}}}}{{T_{\text{compute}}}} \right\rceil \tag{5}
$$

^eq-prefetch-depth

The prefetch depth equation in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^eq-prefetch-depth|equation 5]] estimates how many ready batches cover the selected latency window. Outstanding reads contribute to replenishing that buffer but do not count as ready batches until they complete. The equation assumes that the long-run data supply rate is at least as high as the accelerator’s consumption rate; prefetching absorbs latency variance, not a sustained bandwidth deficit. When average throughput is sufficient but p99 latency exceeds compute time, deeper prefetching absorbs delays within the provisioned window; rarer or correlated delays can still cause stalls. When sustained delivery is lower than demand, identify the limiting stage before choosing more storage bandwidth, additional decoding capacity, a different representation, or local staging. The equation uses the p99 delay rather than the mean because a buffer sized for the mean drains whenever a slow read arrives, and the tail-latency arithmetic of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier3-pfs|section 4.3.6]] shows that when a step depends on many servers, some read is slow on most steps. Even the p99 window leaves rarer events and correlated interruptions to test.

If object-storage reads take 500 ms at the 99th percentile and compute takes 200 ms, then ${Q_{\text{prefetch,min}}} = 3$ batches; provisioning five ready batches adds a margin. A data loader’s configured work-ahead count (for example, a per-worker prefetch factor) is not a count of ready batches, because some of that work may still be loading or preprocessing. The quantity that protects the accelerator is completed-queue occupancy and its refill rate, measured against the delay window on whichever tier serves the reads.

![[90 Assets/Volume II/04 Data Storage/Vol2 Data Storage Margin 002 d7016d6b2c.svg]]

*Sequence strip showing a 500 ms p99 I/O delay spanning two and a half 200 ms compute windows, which rounds up to a prefetch depth of three batches.*

*A 500 ms p99 read spans 2.5 steps of 200 ms, so three ready batches must cover it.*

The image job of notebook [4.1](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#nbk-data-storage-text-vs-image-bandwidth) shows how prefetch buffer depth follows the serving tier. Each GPU processes its batch in roughly 200 ms, and once its 256 images are decoded into $224{\times}224{\times}3$-byte tensors, the collated batch occupies about 40 MB per GPU. Reading from local NVMe, the p99 I/O latency for that batch is approximately 50 ms. Under the p99-window model, the minimum ready-buffer depth is $\lceil 50/200 \rceil = 1$ batch, and this example provisions a depth of 2. Reading from a parallel file system, the p99 I/O latency rises to roughly 200 ms due to network jitter and contention, requiring a minimum depth of $\lceil 200/200 \rceil = 1$, with an illustrative provisioned depth of 3. Reading from object storage, the p99 latency can exceed 500 ms, requiring a depth of at least 3, with an illustrative provisioned depth of 5 or more.

These ready-batch depths translate directly into host DRAM consumption. At 40 MB per batch, a depth-5 prefetch buffer per GPU consumes 200 MB, and 8 GPUs per node consume 1.6 GB. At 40 MB per batch with a depth of 1, the same node needs only 320 MB. Measured delivery delays, batch size, and the chosen protection window determine this memory budget. Queue occupancy and refill rate must still be tested under correlated delays.

The representation decides whether that depth is cheap. Text barely registers, because a per-GPU batch of a few packed 4,096-token sequences occupies tens of kilobytes, so even a deep text queue is negligible. Decoded images are where depth costs memory. The 256-image batch above is roughly 39 MB before rounding, and a buffer of 8 such batches consumes about 308 MB per GPU, modest against a node’s 512 GB of DRAM even after multiplying by the GPUs on the node. Higher-resolution images and video raise the per-batch size by an order of magnitude or more, at which point the prefetch buffer competes with embedding tables and other DRAM consumers.

Prefetching and the storage hierarchy together form a layered defense against stalls. The prefetch buffer in host DRAM absorbs I/O variance from NVMe reads. The local NVMe cache absorbs network variance from shared storage (whether a parallel file system or an object store). The parallel file system read-ahead cache absorbs variance from disk seeks across the OSS cluster. Because each layer adds latency tolerance at the cost of memory or storage capacity, the system designer must check each active path against the interruption window it is intended to absorb and verify that sustained delivery replenishes the consumed batches.

The image job shows what staging buys when steps are short. Its 500 ms object-store p99 against a 200 ms step calls for 3 ready batches, while a local NVMe hit at 50 ms needs only 1. The 175B running example sits at the other end of the scale. Against its modeled 4.64-second step, even the object-store p99 is about 11 percent of one step, so $\lceil 500/4{,}639 \rceil = 1$ ready batch covers the p99 on every tier, and staging its shards on local NVMe does not reduce its prefetch depth. The running example stages for other reasons, which [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.09 Storage Economics#^sec-storage-economics|section 4.8]] weighs. The copy happens once before training starts, and local reads remove the rarer and correlated object-store delays that a buffer sized to the p99 does not cover.

### Multi-Worker Data Loading

^sec-storage-multi-worker

A single CPU core cannot keep a high-throughput accelerator fed, even when the storage hardware is fast enough, because of the CPU work required between the storage read and the GPU transfer. For image training, decoding a 116 KB JPEG image into a $224{\times}224{\times}3$ raw tensor costs several milliseconds of CPU time. One measurement decoded full-resolution ImageNet images at about 530 per second across the four virtual CPUs of a cloud inference instance ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-kang2020jointly|Kang et al. 2020]]), and each augmentation, such as a random crop, flip, or color jitter, adds further work per image. The image job of notebook [4.1](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#nbk-data-storage-text-vs-image-bandwidth) feeds each GPU 256 images every 200 ms step, more than 1,000 images per second. At 1,000 images per second per GPU and 8 GPUs per node, a single core would need to decode and augment 8,000 images per second, tens of times what a single core can sustain.

The solution is multi-worker data loading, where ${W}$ worker processes each read from storage, decode, augment, and enqueue batches independently. The effective I/O throughput scales approximately linearly with ${W}$ until one of three bottlenecks is reached: the storage device’s bandwidth saturates, the PCIe bus between host and device saturates, or the workers exhaust host CPU cycles.

The worker count ${W}$ is tuned as on a single node, by profiling the data stall ratio, since too few workers starve the GPU and too many waste CPU on contention. At fleet scale, every core given to loading is a core the training runtime, communication threads, and operating system cannot use, so dividing host CPU between data loading and training orchestration is itself a capacity planning exercise. How those workers exploit concurrency then depends on which tier serves their reads. On local NVMe, workers issue concurrent reads to the same RAID array and rely on NVMe’s deep command queues to expose device parallelism until shared drive or controller capacity saturates. On a parallel file system, they distribute reads across different OSS nodes to aggregate server bandwidth. On object storage, they issue concurrent HTTP GET requests to distinct shards.

Multi-worker loading must also preserve shuffle quality without giving up I/O efficiency. Under the shard-level and within-shard shuffling of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.03 How ML Workloads Invert Storage Assumptions#^sec-storage-workload-inversion|section 4.2]], the loader assigns contiguous groups of the shuffled shard list to each worker, and the adequacy of that mixing depends on how the shards were built. A corpus whose shards are internally homogeneous, such as one source or one class per shard, needs finer shards or a larger shuffle buffer, so the layout should be validated against the loss curve of a fully shuffled baseline on a subset before the run commits to it.

The shuffle buffer size creates a memory-randomness trade-off. A larger buffer provides better randomness (because samples are drawn from a larger pool) but consumes more host DRAM. For the running example with text data, a shuffle buffer of 10,000 sequences at 2,048 tokens each, with each token represented as a 4-byte integer, consumes roughly 82 MB. This is negligible relative to the 512 GB of host DRAM. For image data, where each decoded image occupies 151 KB, a shuffle buffer of 10,000 images consumes 1.5 GB, still manageable but a nontrivial fraction of the prefetch budget. The data loader designer must balance shuffle buffer size against prefetch depth, since both compete for the same host DRAM capacity.

The data loading pipeline, from storage read through decode, augmentation, and transfer to accelerator, is the complete fuel delivery system for the training engine, and when any stage becomes the bottleneck the accelerator starves. Local reads can reduce network and shared-storage wait, which makes shard placement across nodes the next decision when that path limits delivery.

### Data Locality and Placement

^sec-storage-data-locality

Even when a node has enough CPU workers to decode batches at full speed, fetching every shard across a shared storage network exposes the training loop to fabric congestion and remote service queues. Placing shards on node-local NVMe avoids that shared-network contention, whereas keeping them in a remote parallel file system or object store preserves a single shared pool that any node can read without copying data ahead of time. Because local NVMe’s advantage depends on both the node’s drive stripe and the per-client bandwidth the remote tier can sustain, placement decisions must compare measured client rates rather than assume a fixed local-to-remote ratio.

The staging decision determines where the job pays for data movement, whether before training starts, during the first epoch, or on every epoch. The simplest strategy is static placement, or *prestaging*. At the beginning of a training job, the orchestrator assigns a fixed subset of data shards to each node, and the node copies its shards from shared storage (the object store in the running example, a parallel file system in many on-premises clusters) to local NVMe drives before the first iteration. Reads remain local while the assigned shards fit and the sampling policy uses that assignment, which gives the highest steady-state throughput at the cost of the longest startup delay. Staging a 10 TB dataset across 256 nodes at 500 MB/s per node takes roughly 80 seconds under ideal conditions, and contention on shared bandwidth can extend that stall to several minutes. A changed dataset or assignment requires restaging, so the placement policy must preserve the intended sample distribution as well as local throughput.

The alternative is dynamic placement, or *on-demand staging*, where nodes fetch shards from shared storage when the data loader first accesses them and retain them locally for reuse. This removes the upfront delay and supports datasets larger than aggregate local NVMe capacity and sampling policies that change the active subset over time, but the first epoch pays the full network-read cost. Cache misses consume shared-storage bandwidth and expose remote latency unless prefetching hides it; cache hits retain the benefit of local reads, so the pattern pays off when later epochs reread the cached shards.

The cache view of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^eq-storage-cache-service-time|equation 1]] puts a number on that trade. Take the multi-modal job of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier2-nvme|section 4.3.4]], whose 35 TB corpus overflows a node’s 30.7 TB of local NVMe. If the job samples uniformly and the cache holds that fraction of the corpus, about 88 percent of reads hit the 28 GB/s local stripe and the remaining 12 percent fall through to the node’s 4 GB/s share of the parallel file system. The delivered rate of a serial loader is then a harmonic mean, about 16 GB/s, only 58 percent of the all-local rate. The service time here is the time to deliver one byte, so the loader averages the time per byte across hits and misses rather than averaging the two bandwidths directly. A miss rate near one in eight costs about two-fifths of the bandwidth because each missed byte takes 7× as long as a hit, and that mean is the optimistic case; misses that cluster in time drain the prefetch buffer faster than the average suggests.

*Streaming* keeps data off local storage entirely, reading records from the parallel file system or object store on every epoch. It has no startup delay and needs no local NVMe capacity, but every epoch absorbs the network-read cost again. On transfer cost alone, streaming suits single-epoch pretraining, which reads each byte once, and datasets that exceed the cluster’s aggregate local capacity. The single-epoch running example stages anyway, for reasons of latency tails rather than transfer fees, as [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.09 Storage Economics#^sec-storage-economics|section 4.8]] shows.

A more advanced approach is locality-aware scheduling. The scheduler keeps track of which data shards are cached on which nodes’ local NVMe drives. When it starts a new job or replaces a failed node, it prefers a node that already has the required data cached, rather than treating all nodes as interchangeable. This uses the principle of data gravity,[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn11|¹¹]] co-locating compute with data to minimize transfer times. Scheduling avoids a staging copy only when an available node holds the required, validated shard versions. The next requirement is therefore to identify the cached contents precisely enough to reuse them safely.

For the 6 TB serialized dataset distributed across 256 nodes, each node is responsible for approximately 23.4 GB of data. If a node fails, its replacement must restage that shard subset from shared storage. Drawn at the uncontended 4 GB/s per-node share of the chapter’s parallel file system, the copy takes about 5.9 seconds. At an effective 400 MB/s per-node rate, which recovery contention can impose and which is also the order of the per-node share of the 50–100 GB/s object-store streaming path described in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier4-object|section 4.3.7]], the same copy stretches to about 58.6 seconds. If the orchestrator can instead schedule the replacement workload on an idle node that already has the data cached from a previous run, staging time is zero and training resumes as soon as the replacement joins. The saving is modest per event but recurs. At a per-GPU mean time between failures of 50,000 hours, GPU faults alone give the 256-node cluster about 1 node failure per day, and each contended restage idles the whole synchronous job for the copy time above. Larger fleets fail proportionally more often, although each node’s share of the corpus shrinks as the node count grows.

The pipeline equation, the prefetch queue, the loader workers, and shard placement together determine which bytes reach host memory and when. On the conventional buffered path, however, those bytes are also copied by the CPU through host DRAM before the accelerator’s DMA can start, and at high request rates that copy competes with decoding for the same cores. Orchestration does not remove that copy; a more direct data path between storage and accelerator can.
