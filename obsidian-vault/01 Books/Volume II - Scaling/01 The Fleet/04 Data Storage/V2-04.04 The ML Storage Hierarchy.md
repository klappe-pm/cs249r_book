# V2-04.04 The ML Storage Hierarchy

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-hierarchy

No single storage device can hold a petabyte-scale training corpus, absorb multi-terabyte checkpoints, and still feed an accelerator at terabytes per second. HBM supplies high local bandwidth at limited capacity, whereas object storage pools durable capacity behind a much slower service and client path. A multi-tier hierarchy combines these resources rather than requiring one technology to meet every demand. Each tier offers a different balance of bandwidth, latency, capacity, and cost. The hierarchy extends the familiar processor memory hierarchy across nodes. The new fleet-level decision is how local staging reduces demand on shared storage while preserving a durable, consistently versioned source. Comparing the tiers fairly requires stating each resource at its own scope, per accelerator, per node, or as an aggregate shared service ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^tbl-storage-hierarchy-merged|table 2]]).

| **Storage tier**         | **Typical capacity** |   **Bandwidth**    |   **Latency**    |     **Illustrative cost basis**      |
|:-------------------------|:--------------------:|:------------------:|:----------------:|:------------------------------------:|
| **GPU HBM**              |        80 GB         |     3.35 TB/s      |     ~273 ns      |      ~\$15/GB acquisition cost       |
| **Host DRAM**            |     512 GB–2 TB      |      200 GB/s      |     ~100 ns      |       ~\$3/GB acquisition cost       |
| **Local NVMe SSD**       |       4–30 TB        |     7–25 GB/s      |     ~100 μs      |     ~\$0.10/GB/month provisioned     |
| **Parallel File System** |       100+ PB        | 1+ TB/s aggregate  |      ~1 ms       | ~\$0.03/GB/month provisioned/service |
| **Object Storage**       |   Very large pool    | 100 GB/s aggregate |      ~50 ms      |       ~\$0.02/GB/month service       |
| **Archive/Cold Storage** |   Very large pool    |       1 GB/s       | Minutes to hours |      ~\$0.004/GB/month service       |

Table 2: **Extended Memory Hierarchy for ML Systems**: HBM bandwidth is per accelerator, host DRAM and local NVMe are per node, and parallel-file-system and object-storage figures are aggregate service rates. These different scopes are not directly comparable tier ratios; divide shared bandwidth among active clients and account for each client path before sizing prefetching and caching. Memory costs are acquisition dollars per GB, while storage costs are recurring dollars per GB-month; comparing them requires an explicit amortization period and utilization assumption.

^tbl-storage-hierarchy-merged

HBM’s advantage over host DRAM in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^tbl-storage-hierarchy-merged|table 2]] is *bandwidth*, not *latency*, because its lead comes from wide stacked interfaces rather than faster cells (**[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^sec-compute-hbm|HBM and the memory wall]]**). The latency cliff between adjacent tiers opens only at NVMe and below, where each access adds media time and storage-protocol processing and, beyond the node, network hops and queueing. The storage hierarchy model (principle [[01 Books/Volume II - Scaling/01 The Fleet/V2 Fleet Principles#^pri-storage-hierarchy|8]]) therefore governs storage tiering and pipeline design. The local tiers exchange bandwidth for capacity, while shared tiers aggregate many devices and expose a different client path. Because per-client bandwidth depends on allocation and contention rather than a fixed factor between tiers, data format choices, caching strategies, prefetch buffer sizing, and tiering policies all exist to manage the movement of data upward through the hierarchy so that the accelerator never starves.

The rest of the chapter numbers the six tiers by distance from the accelerator, from Tier 0 (HBM) through Tier 1 (host DRAM), Tier 2 (local NVMe), Tier 3 (parallel file system), and Tier 4 (object storage) to Tier 5 (archive). Distance alone hides an important distinction, because each tier’s bandwidth figure describes a different scope: per accelerator, per node, or a shared service divided among its clients ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^fig-storage-pyramid|figure 1]]).

^fig-storage-pyramid

The physical tiers of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^fig-storage-pyramid|figure 1]] govern the trade-off among access distance, capacity, and cost. Shared services can aggregate more bandwidth than an individual local device, so the ordering is not a monotonic ranking of aggregate throughput. This trade-off is not arbitrary; it reflects the physics of data proximity. HBM sits on the same silicon interposer as the accelerator, connected by thousands of parallel traces measured in millimeters, whereas host DRAM connects to the CPU memory controller and reaches the accelerator across the host-device interconnect, and local NVMe reaches across the circuit board over PCIe lanes. Beyond the node, the parallel file system traverses meters of cable and network switches, while object storage may span kilometers of fiber between data centers. Distance, protocol overhead, and contention can increase access latency, while media technology and provisioning determine capacity cost. Distance is therefore a guide rather than a measurement; only the complete client path establishes all three properties for a given consumer.

The engineering challenge is to deliver each batch to HBM before the accelerator needs it. In the running example, the durable corpus lives in object storage (Tier 4) as a 3 TB compressed source copy plus 6 TB of tokenized training shards, but the accelerator needs each batch in HBM (Tier 0) before the current step ends. The chapter’s reference design fixes one path between them. At job start, each node copies its share of the tokenized shards from object storage to its local NVMe (Tier 2). The single training epoch then reads from that local copy, prepares batches in host DRAM, and transfers them to HBM. Local reads keep slow object-store responses out of each training step, the reason [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.09 Storage Economics#^sec-storage-economics|section 4.8]] gives for staging a corpus this job reads only once. The parallel file system (Tier 3) holds checkpoints rather than training inputs. Streaming the shards directly from object storage, or serving them from a parallel file system, are the alternatives the chapter weighs against this design, and the hierarchy describes placement choices, not a requirement that every byte visit every level.

### Bandwidth Cliffs Between Tiers

^sec-storage-bandwidth-cliffs

Stepping down one level from a single accelerator’s HBM (3.35 TB/s) to the whole host’s DRAM (~200 GB/s) drops bandwidth by roughly 16.8×, and that comparison still understates the cliff on an eight-GPU node because all eight accelerators share the same host-memory bandwidth. Comparing adjacent tiers requires making the scope of each rate explicit (per accelerator, per node, or across a shared service), as bracketed in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^fig-storage-pyramid|figure 1]]. Between host DRAM and NVMe, the ratio is roughly 7.1× (200 GB/s vs. ~28 GB/s from a 4-drive RAID-0). Between NVMe and a parallel file system, the ratio depends on the per-node allocation. If a 1 TB/s aggregate parallel file system (PFS) serves 256 nodes, each node receives roughly 4 GB/s, a 7× reduction from the local RAID-0 stripe. Object-storage throughput likewise depends on the client path and allocation; there is no fixed ratio to a parallel file system.

![[90 Assets/Volume II/04 Data Storage/Data Storage Bandwidth Cliff 6de78d844f.svg]]

*Four horizontal violet bars on a log scale, longest at top: HBM 3.35 TB/s, host DRAM 200 GB/s, four-drive NVMe 28 GB/s, and a per-node parallel-file-system share of about 4 GB/s.*

*Per-client bandwidth falls roughly 7 to 17$\times$ at each step from HBM to a node’s share of the parallel file system.*

As [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.02 The Fuel Line#^sec-storage-fuel-line|section 4.1]] established, a cliff is not a feed requirement; the feed rate remains input-batch bytes divided by iteration time, summed over distinct consumers. What the cliffs decide is where buffering must sit. Along the chosen path, host DRAM can buffer prepared batches and NVMe can cache shards from shared storage. Each buffer must cover the delay of the tier below it while that tier sustains the consumption rate; durable repositories need not act as intermediate buffers.

The same hierarchy can be analyzed as a cache rather than as six isolated devices. If a request hits the hot tier with probability ${h}$, taking ${T_{\text{hot}}}$, and otherwise falls through to a colder tier, taking total end-to-end miss-path time ${T_{\text{cold}}}$ (including the failed hot-tier lookup), its mean service time is

$$
\mathbb{E}[{T}] = {h} {T_{\text{hot}}}+ (1-{h}){T_{\text{cold}}}. \tag{1}
$$

^eq-storage-cache-service-time

For fixed-size records served serially, the corresponding effective bandwidth is the record size divided by $\mathbb{E}[{T}]$. The arithmetic makes small miss rates consequential. With a 95 percent hit rate and a cold-tier access 100× slower than a hot-tier access, $\mathbb{E}[{T}]=5.95{T_{\text{hot}}}$, so the effective request rate is only about one-sixth of the all-hot rate. Concurrent requests and prefetching can overlap service, so this mean is a sizing baseline rather than a fleet-throughput or latency guarantee. Correlated misses or a heavy-tailed cold tier can drain the prefetch buffer even when the average satisfies the pipeline budget, so production designs must check a tail percentile and miss bursts as well as $\mathbb{E}[{T}]$.

The batch-volume arithmetic also explains why increasing cluster size creates storage pressure. Aggregate demand is each consumer’s batch bytes divided by its compute window, summed over consumers, so at a fixed per-node rate it grows linearly with node count. The per-node rate itself spans orders of magnitude across data modalities, as text and image training on the running cluster show.

![[90 Assets/Volume II/04 Data Storage/Vol2 Data Storage Margin 001 758ff16e20.svg]]

*Two-bar log-scale ladder: a long violet bar for image training at 303 GB/s above a short bar for text training at 168 MB/s.*

*Image training demands 1,800× the storage bandwidth of text.*

**Napkin Math 4.1: Text vs. image bandwidth**

**Problem**: How much aggregate storage bandwidth does a 2,048-GPU cluster require for text training vs. image training?

**Setup**: Compare two declared batch representations at the same compute window and number of independent input consumers. The result depends on batch volume and rate, not modality alone. Both jobs are generic ones sized to the running cluster, not the 175B running job. Each GPU consumes one per-GPU batch every step, a pace that fits a model far smaller than 175B parameters.

For text training, the demand is low. With a per-GPU batch of one packed sequence of 4,096 tokens and a 200 ms step time, the aggregate bandwidth is:

$$
2{,}048 \text{ GPUs} \times 4{,}096 \text{ tokens/GPU} \times 4 \text{ bytes/token} \div 0.2\text{s} \approx {167.8 MB/s}
$$

This is easily served by a single network-attached storage node, one file server that clients reach over the network.

Image training demands far more. Using a common batch size of 256 per GPU (ImageNet at $224{\times}224$, roughly 116 KB/image), the aggregate bandwidth is:

$$
2{,}048 \text{ GPUs} \times 256 \text{ images/GPU} \times 115.7 \text{ KB/image} \div 0.2\text{s} \approx {303.2 GB/s}
$$

**Systems insight**: Under the stated batch representations and compute times, image training requires 1,800× higher input bandwidth than text training. The text example is *volume-heavy* but *bandwidth-light*. One network-attached storage server can carry its input feed, so its storage design is shaped by total corpus volume and, as later sections show, by checkpoint traffic. The image example is *bandwidth-heavy*, with a feed that exceeds any single storage server and calls for the aggregate bandwidth of many servers or of local caches. Whether either demand becomes an actual bottleneck still depends on the measured delivery rate of the path that serves it.

The 175B running job sits lower still. Its 6 TB epoch spread over the modeled 25.6-day run averages about 2.7 MB/s for the whole cluster, corpus bytes divided by run length, roughly 60× below the notebook’s generic text job. Each token of a 175B model carries so much computation that the corpus trickles in, which is why the running example’s storage design is shaped by checkpoint traffic rather than by its input feed.

The image result is a floor for visual data rather than a ceiling. At about 303.2 GB/s across 256 nodes, the image job already consumes nearly a third of a 1 TB/s parallel file system built from 100 data-serving nodes (the architecture [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier3-pfs|section 4.3.6]] develops). Higher-resolution images and video clips, at megabytes per sample rather than the roughly 116 KB of a compressed ImageNet image, raise the per-node demand by an order of magnitude or more, and a fleet several times larger multiplies it again. Demand at that scale exceeds what a shared file system of this size can serve, so the architecture must rely on local NVMe caching to take repeated reads off shared storage.

The bandwidth cliff between tiers also has implications for the data format at each level. Computation consumes float16 tensors, packed token IDs, or other supported representations, while NVMe and object storage can retain compressed records. Compression reduces bytes stored and transferred but adds decoding work. The chosen format must let CPU or GPU decoding keep pace with consumption; maximum compression can reduce end-to-end throughput when decoding becomes the limiting stage. A host-decoded path stages the resulting tensors in DRAM, while a GPU-decoded path moves the transformation and its resource demand to the accelerator.

The format challenge intensifies for multi-modal training, which combines text, images, audio, and video in a single model. Serialized sizes span orders of magnitude, from 4 bytes per text token to roughly 116 KB per compressed image to megabytes per short video clip, depending on representation, compression, resolution, and duration, and each modality requires its own decoding and augmentation work. A multi-modal training job must manage these parallel streams and provision for their combined service demand. For a corpus containing 3 TB of text, 50 TB of images, and 200 TB of video, video dominates retained capacity. Its bandwidth contribution also depends on how frequently training samples it and how many bytes each sampled batch reads. Corpus size alone determines neither the delivery rate nor the modality’s contribution to model quality.

Tracing how each tier meets these bandwidth and format constraints begins at the top of the pyramid and steps outward from the accelerator to the archive. That descent starts where computation actually consumes bytes: HBM, the tier fast enough to keep accelerator arithmetic fed but far too scarce to hold the full training corpus.

### Tier 0 GPU HBM

^sec-storage-tier0-hbm

The scarcest resource in the system sits closest to the arithmetic. On the H100 used here, HBM holds the active weights and activations served to the accelerator, while caches and on-chip buffers reuse portions of that state. Its stacked packaging supplies 3.35 TB/s of aggregate bandwidth, the top of the cliffs just measured. That bandwidth is what makes large-scale deep learning feasible, because a matrix multiplication involving billions of parameters reads those parameters from memory on every forward and backward pass. What HBM lacks is room.

↩︎ High-bandwidth memory packaging, the 3D stacking and through-silicon vias behind this bandwidth, is established in **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^sec-compute-hbm|HBM and the memory wall]]**.

For placing the unpartitioned running model, the immediate constraint is *capacity*. Once state fits, HBM bandwidth can still limit execution. The node-memory budget of **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-node-memory|Node memory partitioning]]** already shows how far one 80 GB device falls short of the 175B running example. The FP16 weights alone, 350 GB, need at least five H100 accelerators. The mixed-precision contract this chapter checkpoints also retains 700 GB of FP32 master weights, so weights, gradients, master weights, and Adam moments occupy 2.80 TB before activations and communication buffers. State that does not fit in one HBM pool must be split across accelerators or kept outside HBM and fetched when needed. Splitting it across the cluster makes the run possible, but every shard becomes a separate piece of state that lower tiers must stage, save, and restore in step with the others. HBM scarcity is what forces the rest of the hierarchy to exist, and HBM is the destination that every lower tier exists to serve.

Because HBM capacity is so limited relative to both model size and dataset size, the accelerator processes data in batches. Each batch occupies a fraction of HBM for the duration of one forward-backward pass, then is discarded to make room for the next. The rate at which batches must be supplied sets the bandwidth requirement for all lower tiers.

The razor-thin margin is a defining feature of large model training, visible in the HBM budget that each 80 GB H100 carries while the fleet trains the 175B parameter model ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^tbl-hbm-memory-budget|table 3]]). The table treats partitioning as a storage layout, and the chapter keeps this one layout throughout. Tensor parallelism splits each layer eight ways across the GPUs of one node, and pipeline parallelism places successive groups of layers on eight nodes, so one complete replica of the model and its training state spans sixty-four GPUs, each holding a 1/64 slice. Data parallelism repeats that replica thirty-two times across the running cluster, and every replica holds an identical copy of the state. Sharding the replicated optimizer and gradient state across data-parallel replicas is the second stage of the Zero Redundancy Optimizer (ZeRO), a training technique in its own right; its third stage also partitions the weights. This layout needs neither, because the unsharded slices already fit. Here only the resulting per-GPU slices matter, because they set the storage pressure HBM sees.

↪ Sharded data parallelism (ZeRO and FSDP), which partitions optimizer, gradient, and weight state across workers, is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-memoryefficient-data-parallelism-zero-fsdp-0e69|Memory-efficient data parallelism with ZeRO and FSDP]]**.

| **Component**                             | **Size per GPU** |
|:------------------------------------------|:----------------:|
| Model Weights (FP16, replica slice)       |      5.5 GB      |
| Optimizer State (replica slice)           |     21.9 GB      |
| FP32 Master Weights (replica slice)       |     10.9 GB      |
| Activations (variable by sequence length) |     10–20 GB     |
| Gradient Buffers (FP16, replica slice)    |      5.5 GB      |
| Communication Buffers (NCCL)              |      2–4 GB      |
| **Total Occupied**                        | **55.8–67.8 GB** |

Table 3: **HBM Memory Budget for 175B-Parameter Training**: Per-GPU allocation when one replica of a 175B model and its unsharded mixed-precision Adam state is split across sixty-four GPUs, eight ways inside each node and across a pipeline of eight nodes. The weight, optimizer, master-weight, and gradient rows are each GPU’s 1/64 slice. The resulting budget occupies most of an 80 GB HBM device, leaving limited buffer for the incoming data pipeline. Any delay in fetching the next batch from host memory risks starving the accelerator.

^tbl-hbm-memory-budget

Even with aggressive partitioning, the total memory footprint reaches 55.8–67.8 GB in decimal gigabytes, about 64.9–78.9 percent of the HBM pool (the device’s nominal 80 GB is a binary capacity, slightly larger than 80 decimal gigabytes). The remaining headroom shrinks further once fragmentation and framework workspaces are included, and that headroom is all the incoming data pipeline has to work with. An input batch and its activations occupy HBM for one training step, while model weights and optimizer state persist across steps. Prefetching the next batch therefore competes with the live training footprint for scarce capacity; a deeper input queue is useful only if the memory budget can accommodate it.

From the data pipeline’s perspective, Tier 0 is not a storage tier to be managed but a constraint to be satisfied. The pipeline’s purpose is to ensure that the batch the accelerator needs *next* is already resident in HBM before the *current* batch’s computation completes. If it arrives late, the accelerator stalls. If it arrives early, it consumes HBM that could hold activations. The tension between “just in time” and “just too late” defines the pipeline’s buffer management strategy, quantified in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^sec-storage-pipeline-equation|section 4.4]].

### Tier 1 Host DRAM

^sec-storage-tier1-dram

One level below HBM, host DRAM serves as the staging area for the data pipeline. Every byte of training data that reaches the accelerator passes through host DRAM first (unless GPUDirect Storage bypasses it, as described in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass#^sec-storage-gds|section 4.5]]). A typical training node contains 512 GB to 2 TB of system memory shared across the host CPU and its peripherals. The bandwidth between host DRAM and the accelerator is limited to what PCIe Gen 5 (about 64 GB/s per direction, 128 GB/s bidirectional) can provide. A faster path requires a CPU-accelerator superchip, a module that joins the two processors over a coherent NVLink-class host link, which approaches the 900 GB/s that NVLink provides between accelerators. Host DRAM plays three roles in the ML storage hierarchy. It is the prefetch buffer, a home for embedding tables too large for HBM, and the augmentation workspace. The data loader occupies two of these roles at once, because its augmentation stage and the prefetch buffer it fills both live in host DRAM.

The data loader pipeline that runs in host DRAM works as it does on a single node. Reader threads fetch compressed samples, workers decode and augment them, and a collation stage assembles batches in pinned, or page-locked, memory for the host-to-accelerator direct memory access (DMA) transfer. At fleet scale, these stages compete with the node’s other demands for the same host DRAM.

↪ The single-node overlap techniques behind this loader (prefetching, pinned host buffers, and double buffering) are collected for reference in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-dam-coordination-sum-max|D·A·M coordination from sum to max]]**.

Host DRAM’s most critical function is serving as a prefetch buffer. When the accelerator finishes processing batch ${k}$, batch ${k}+1$ should already be assembled in host memory, ready for transfer to HBM. The depth of this prefetch buffer determines how much I/O variance the pipeline can absorb without stalling.

Recommendation workloads, the regime of Archetype B (DLRM at Scale), place a different demand on host DRAM: hosting embedding tables that can exceed 100 GB, far too large for HBM. These tables reside in host DRAM and are accessed through lookups that fetch only the rows needed for the current batch. The bandwidth between host DRAM and HBM becomes the critical bottleneck for these workloads, and some systems go further, pooling embedding tables in the DRAM of dedicated CPU servers and returning only the requested rows over remote direct memory access (RDMA).

↪ Sharding embedding tables across servers, and the sparse row exchanges that result, is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-parameter-servers-embedding-sharding-8821|Sparse embedding sharding]]**.

Host DRAM also provides the augmentation workspace that the CPU pipeline requires. Data augmentation operations (resizing images, applying noise) execute on the CPU and require temporary memory for intermediate results. A training pipeline that applies five augmentations to a 256-image batch at 116 KB per image needs tens of megabytes of working space for each augmentation stage. Although modest per-batch, this memory accumulates when multiple data loader workers run in parallel. GPU-side decoding with libraries such as the NVIDIA Data Loading Library (DALI) moves decode and augmentation onto the accelerator, so smaller compressed bytes cross the host link and host DRAM bandwidth demand falls. The work then consumes HBM capacity and compute cycles instead, which helps an input-bound job and hurts a compute-bound one.

The three roles interact in subtle ways. The prefetch buffer and the augmentation workspace compete for the same physical DRAM, and embedding tables consume capacity that could otherwise serve as deeper prefetch queues. A node with 512 GB of DRAM hosting a 200 GB embedding table has only 312 GB remaining for prefetching and augmentation. If the data loader uses 8 workers, each maintaining a decode buffer of 1 GB, the effective prefetch capacity drops further. System architects must balance these competing demands by profiling the actual memory consumption of each pipeline stage and provisioning DRAM accordingly.

The physical layout of DRAM also matters. On a dual-socket node, each socket’s DRAM forms a non-uniform memory access (NUMA) domain local to the GPUs on that socket’s PCIe root complex, and reaching the other socket’s DRAM crosses the inter-socket link, with a penalty that depends on the processor, topology, and concurrent traffic (**[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-infrastructure-pcie-hierarchy-within-node-c56f|The PCIe hierarchy within a node]]**). NUMA-aware allocation keeps each data loader worker and its prefetch buffer in the same NUMA domain as the GPUs it serves; the gain should be measured on the target node rather than assumed.

Host DRAM sits below the first cliff of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-bandwidth-cliffs|section 4.3.1]], and the host-to-GPU interconnect adds a separate cliff, with effective transfer bandwidth depending on whether the node uses PCIe or NVLink. In the conventional path that stages payloads through host memory, a depleted DRAM prefetch buffer leaves the accelerator waiting for lower tiers. The direct path of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass#^sec-storage-gds|section 4.5]] removes that staging copy when the data layout and devices support it. In the running example, the 256-node cluster requires each node’s host DRAM to sustain a continuous flow of packed token batches ready for PCIe transfer. If the NVMe-to-DRAM read pipeline falls behind by more time than the prefetch buffer covers, the buffer drains and the accelerator idles until the next batch arrives.

### Tier 2 Local NVMe

^sec-storage-tier2-nvme

When the working set exceeds host DRAM, the system falls to Tier 2: the local NVMe drives attached directly to the compute node. NVMe[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn4|⁴]] provides a high-performance protocol designed specifically for solid-state drives, achieving 7 GB/s of sequential throughput per drive. NVMe’s deep queues and PCIe lanes, rather than faster flash, explain why it delivers 10$\times$ to 50$\times$ the throughput of SATA SSDs (capped near 550 MB/s by the link) with identical NAND flash, provided the loader keeps many asynchronous reads outstanding. With four drives in a RAID-0 configuration, a single node can sustain roughly 28 GB/s of sequential reads before overhead, sufficient to stream the 6 TB serialized dataset from local disk in about 3.6 minutes under ideal sequential conditions.

In ML training, local NVMe acts as a cache, storing data shards fetched from distributed storage. Workers can reread resident shards across epochs without fetching them over the network again. The savings depend on reuse, cache capacity, and whether remote reads cross a charged transfer boundary ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.09 Storage Economics#^sec-storage-economics|section 4.8]]). Staging pays an initial transfer cost and provisions local capacity in exchange for avoiding later remote reads; it does not eliminate storage cost or read latency.

The local cache pattern requires careful capacity planning. A training node with four 7.68 TB NVMe drives provides approximately 30.7 TB of local storage. For the running example, the 6 TB serialized dataset fits comfortably on a single node’s local storage with room for checkpoint staging and temporary augmentation buffers, and each node holds only its assigned share. A multi-modal training job in which any node may read any sample combines 20 TB of images, 10 TB of text, and 5 TB of audio for a total of 35 TB, exceeding one node’s local capacity by about 4.3 TB and forcing the pipeline to stream from the parallel file system for at least part of the dataset. The design trade-off is between provisioning more local NVMe (which increases node cost) and accepting network-dependent reads (which risks latency spikes).

The I/O wall takes a deceptive form at this tier. The HBM-to-NVMe ratio of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-bandwidth-cliffs|section 4.3.1]] does not set demand, so the question here is whether the stripe meets the input-batch rate, not whether it approaches HBM. Pipelining overlaps that delivery with compute ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.05 The Data Pipeline Equation#^sec-storage-pipeline-equation|section 4.4]]), while GPUDirect Storage ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass#^sec-storage-gds|section 4.5]]) can remove host payload copies when those copies limit throughput. The wall is easy to miss because NVMe performance is excellent by historical standards. A storage engineer accustomed to HDD-era throughput of 150 MB/s might view 28 GB/s from a local RAID-0 stripe as more than enough. Whether 28 GB/s suffices depends on the batch representation and consumption rate. Compact text may fit within this budget, while image or video inputs may require more bandwidth; overlap hides transfer time only when sustained supply keeps pace with demand.

Local NVMe also supports local checkpoint staging. Writing a consistent snapshot locally and replicating it to shared storage in the background can shorten ${T_{\text{write}}}$, the time training pauses to save a checkpoint, when the shared write would otherwise be slower. Resuming after a local save accepts a period during which a node failure can destroy the new shard. The storage design must therefore specify both the exposed pause and the later durability boundary, while retaining a previous recoverable generation, one complete saved version of the checkpoint. [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|Section 4.6]] develops this trade-off and its timing model.

The same local NVMe tier also pays for itself by recovering utilization lost to remote-read latency. When congestion on a shared file system drains the host prefetch buffer and exposes I/O wait on every step, staging shards onto node-local flash converts that exposed remote wait into reclaimed accelerator compute time.

**Napkin Math 4.2: Return on investment of local NVMe caching**

**Problem**: A vision-model training pipeline, a separate workload from the 175B language model, runs each step in 800 ms on the 1,024-GPU reference cluster. It reads from a shared parallel file system, and even with prefetching, congestion bursts on that shared service drain the loader’s buffer and leave an average of 150 ms of exposed I/O wait per step. Assume that serving the same shards from local NVMe leaves only 10 ms of exposed wait per step, the residue of local tail latency that the prefetch queue does not cover. How much does adding local NVMe SSDs to each node improve GPU utilization?

**Math**: GPU utilization here means the fraction of step time spent in computation, an active-time fraction rather than model FLOPs utilization.

1.  **Remote Only**: 800 ms / (800 ms + 150 ms) $\approx$ 84.2 percent.
2.  **Local Cache**: Prefetching from local NVMe removes the congestion bursts of the shared service, leaving the assumed local residue.
    - New Util: 800 ms / (800 ms + 10 ms) $\approx$ 98.8 percent.

**Systems insight**: Local storage can act as a *GPU utilization multiplier*. In this scenario, adding a \$500 NVMe drive to a node whose accelerators each cost \$30,000 recovers 14.6 percent of the GPU’s capacity that was previously wasted on I/O wait. Across the 1,024-GPU cluster, that utilization gain is equivalent to adding 149 GPUs worth of useful work without buying that many more accelerators. The gain is exactly the exposed remote wait that local reads remove, so it is large only when shared-storage congestion leaves a wait of this size; where it does, local NVMe is not auxiliary but the physical buffer that decouples expensive compute from unpredictable shared storage.

A practical concern at this tier is SSD endurance. NAND flash memory can sustain a limited number of write-erase cycles before the cells degrade. Enterprise NVMe drives are rated for 1 to 3 drive writes per day (DWPD) over a 5-year lifespan. For a 7.68 TB drive at 1 DWPD, this means the drive can absorb 7.68 TB of writes per day, or roughly 14 PB total over its lifetime.

ML training workloads are predominantly read-heavy (the dataset is written once and read many times), which is favorable for SSD endurance. However, checkpoint writes can be intensive. If each node saves its roughly 10 GB share of the running example’s checkpoint every 10 minutes, that is about 1.4 TB per day of checkpoint writes spread across the node’s drives, well within a four-drive node’s 1 DWPD budget. The risk emerges when local NVMe is used as a staging buffer for both checkpoint writes and dataset caching. The combined write volume from initial dataset staging plus repeated checkpoint saves must remain within the drive’s endurance rating. Within that rating, read-heavy training fleets rarely wear out their drives, so a storage refresh cycle is usually driven by density rather than wear, and its timing belongs to the lifecycle cost analysis of **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.10 Fleet Economics and Utilization#^sec-ml-operations-scale-depreciation|Depreciation and lifecycle]]**.

### Data Formats for Training

^sec-storage-data-formats

Local NVMe can stream 28 GB/s per node, but packaging determines how much of that bandwidth reaches the loader. The same multi-terabyte dataset stored in different formats can yield I/O throughput that differs by over 100$\times$ on identical hardware, because each format charges a different access cost: per-file metadata, unnecessary feature reads, or sequential shard traversal. A directory containing one JPEG per sample pays a separate file open and metadata lookup for every image. At roughly 10 to 50 microseconds per open in the kernel’s file-system layer, a node reading 8,000 images per second spends 80 to 400 ms of CPU time per second on opens alone, before it decodes a single byte. On a shared file system the same operations also queue at a metadata service, the fleet-scale form of this cost that [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier3-pfs|section 4.3.6]] develops as the small file problem. A standard ImageNet training pipeline makes the cost of the wrong format visible.

**Napkin Math 4.3: The ImageNet bottleneck analysis**

**Problem**: A ResNet-50 training job on ImageNet (1.28M, ~116 KB average) targets 1000 images/s. Can individual JPEG files on an HDD sustain that rate, or does the job need NVMe?

**Math**:

1.  **Raw Bandwidth**: 1000 images/s $\times$ 116 KB = 116 MB/s.
2.  **HDD reality**: A 7200 RPM hard disk drive (HDD) delivers 100 IOPS at random reads. Sustaining 1000 images/s requires 10× more IOPS than the disk provides.
3.  **Result**: When every image is a separate random read, shuffling individual files on an HDD will starve the GPU, capping utilization at about 10 percent before decode, seek, and file-system overheads.

**Systems insight**: Two fixes work, and they remove different limits. NVMe answers a random read in roughly 100 μs rather than the milliseconds of a mechanical seek, so even one outstanding request covers the 1000 images/s that the HDD’s 100 IOPS cannot. Alternatively, converting the dataset to a sequential format (TFRecord/WebDataset) removes the random reads altogether and turns the HDD problem into a bandwidth one, in which the job needs 116 MB/s, within the roughly 150 MB/s that one HDD streams sequentially.

The first format choice is the record layout. Row-oriented formats, such as CSV or JSON lines, store successive records together and are easy to inspect and debug. They can stream many records from one file, although parsing text and reading unused fields consume CPU cycles and bandwidth.

A second choice solves a different storage problem. Columnar formats like Apache Parquet and Apache Arrow avoid unnecessary reads when tabular features can be selected before transfer. They organize data by column rather than by row, which allows for excellent compression as data within a column is typically of the same type and has lower entropy. Column pruning lets the reader fetch only required features. Predicate pushdown applies filters at the storage reader and can skip groups of records using their metadata, further reducing unnecessary I/O. These formats are well-suited for tabular ML tasks and feature engineering, such as the feature tables of Archetype B (DLRM at Scale), but are less natural for unstructured data like images or audio, which are treated as atomic blobs.

A third choice addresses the training access pattern directly. Sequential streaming formats reduce per-sample metadata to the cost of opening a shard. TFRecord, Mosaic’s StreamingDataset format ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-mosaicStreamingMainConcepts|Databricks 2026]]), and WebDataset[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn5|⁵]] group many samples into large, contiguous binary files called shards. WebDataset uses standard `tar` archives, in which each sample keeps its image, label, and metadata entries while the loader streams the archive in order. A data loader opens a single shard and streams its contents sequentially, amortizing the open over thousands of samples. The `tar`-based formats have the added advantage of being valid targets for HTTP byte-range requests, making them ideal for streaming data directly from object storage without downloading the entire file first.

A key trade-off within streaming formats is the presence of an index. TFRecord readers often rely on a separate index file that records each sample’s byte offset within a shard, while the scientific array format HDF5 embeds its index in the file itself. This enables efficient random access within a shard but introduces a metadata dependency, because the index must be read and held in memory. WebDataset is indexless, because each record in the `tar` archive contains its own header specifying its size, allowing for purely sequential streaming without any external metadata. The trade-off is that indexless formats cannot efficiently seek to an arbitrary sample within a shard, a capability that matters for curriculum learning or active learning workloads that require nonsequential data access.

Compression integration also varies across formats, and it trades storage bytes against CPU decoding work. Parquet integrates compression at the column level, exploiting type homogeneity for high ratios. WebDataset and TFRecord typically leave compression to the individual sample. A WebDataset of images stores already-compressed JPEG files, while a text dataset might apply zstd compression per shard, and the host CPU pays for that decompression.

Consider two illustrative codecs on the same corpus: a lighter codec compresses 3:1 and produces 1.5 GB/s of decoded output per CPU core, while a denser codec compresses 4:1 and produces 0.5 GB/s per core. These are scenario assumptions, not fixed properties of named codec levels. At the 28 GB/s local NVMe rate, multiplying that read rate by each compression ratio yields potential decoded output rates of 84 GB/s and 112 GB/s, respectively, provided CPU decoding keeps pace. Dividing each uncompressed output rate by its per-core decoding speed gives 56 cores for the lighter codec and 224 for the denser one. The denser codec needs 4× as many cores, because it produces one-third more uncompressed bytes from the same storage read while decoding each byte at one-third the per-core speed.

Running each codec at the drives’ full output is the worst case, an upper bound on decode work; a node needs only enough cores to decode its own share of demand. The generic text job of notebook [4.1](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#nbk-data-storage-text-vs-image-bandwidth) asks the entire cluster for about 167.8 MB/s, which a single core of either codec covers, so these core counts become the limit only for image and video feeds whose decoded demand per node approaches the drives’ rate. With fewer cores than that demand requires, decoding limits delivery before storage saturates, so compression is chosen from the measured corpus, decoder, and available CPU budget rather than from the compression ratio alone.

For the running example, the 1.5 trillion token dataset is stored as roughly 2,000 shards of 3 GB each in a custom binary format. Each shard contains a small header (token count, vocabulary size, byte order) followed by a contiguous array of 4-byte token IDs. The number of `open()` calls per epoch is therefore the number of shards, not the number of tokens (trillions), an approximately 750,000,000× reduction in metadata operations that makes streaming from both local NVMe and remote storage feasible at training scale. When staged on storage with the standard Unix (POSIX) file interface, such as local NVMe or a parallel file system, the data loader memory-maps the shard, treating the file as a region of virtual memory, and indexes directly into the token array by position, achieving near-peak read bandwidth with zero per-sample metadata overhead. When the same shards are read directly from object storage, the loader uses HTTP ranged GET streaming and an explicit local buffer rather than memory mapping. The formats differ chiefly in the access cost each one imposes per sample on the storage path ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^tbl-data-formats|table 4]]).

| **Format**          |             **Overhead/sample**             | **Random access** | **Streaming** | **Compression** |
|:--------------------|:-------------------------------------------:|:-----------------:|:-------------:|:---------------:|
| Individual files    | $\approx 50\ {\text{µ}}$s (open/stat/close) |        Yes        |     Poor      |    Per-file     |
| Parquet             |  $\approx 1\ {\text{µ}}$s (row group seek)  |  Yes (row group)  |     Good      |  Column-level   |

Packaging removes the per-file cost within one node, but no node-local format gives every node the same view of the data. That requirement belongs to the next tier.

### Tier 3 Parallel File Systems

^sec-storage-tier3-pfs

Local NVMe drives cannot give 256 training nodes a single namespace for shared datasets or a globally visible home for checkpoints that survive a node crash. A parallel file system provides that shared tier across the cluster.

**Definition 4.1: Parallel file system**

***Parallel file system (PFS)*** is a distributed storage architecture for ML training clusters that stripes data across many storage servers to provide aggregate throughput exceeding the capacity of any single device.

1.  **Significance**: A PFS aggregates storage I/O bandwidth $({\text{BW}_{\text{storage}}})$ across object storage servers (OSS). Twenty OSS nodes delivering 10 GB/s each offer 200 GB/s aggregate. When the client and network sustain that full rate, a 10 GB striped shard loads in about 50 ms rather than the 1 second a single 10 GB/s server would need. The rate that enters the data-movement term ${D_{\text{vol}}}/{\text{BW}}$ of the single-machine iron law recalled in **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^sec-vol2-introduction-fleet-law|The Fleet Law]]** is the bandwidth that reaches the actual consumer, not the aggregate rating.
2.  **Distinction**: Unlike network-attached storage, where every I/O request routes through a single server, a Lustre-style PFS client receives stripe location metadata from a dedicated metadata server (MDS) and then reads data directly from multiple OSS nodes in parallel. The MDS and OSS paths are architecturally separated, so data bandwidth scales with OSS count while metadata operations scale with MDS count.
3.  **Common pitfall**: A frequent misconception is that a PFS has unlimited throughput if enough OSS nodes are added. In reality, every open, stat, and create on a Lustre-style PFS passes through the MDS, whose service rate is finite and does not grow with the number of OSS nodes; a one-time burst of 10,000 opens does not by itself establish sustained saturation. The MDS becomes a throughput bottleneck when the aggregate metadata-operation arrival rate exceeds its service rate, regardless of spare bandwidth at the OSS nodes.

A Lustre-style parallel file system decouples metadata lookups from bulk data movement ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^fig-storage-pfs-architecture|figure 2]]), separating two concerns that traditional file systems handle together ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-schwan2003lustre|Schwan 2003]]). Metadata servers (MDS) manage the namespace (persisting file layouts and attributes on metadata targets, or MDTs): file creation, directory listings, permission checks, and lock management. Object storage servers (OSS)[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn6|⁶]] manage the actual data blocks (stored on object storage targets, or OSTs), each serving a stripe of every large file. When a client opens a 10 GB training shard, the MDS tells the client which OSS nodes hold which stripes, and the client reads from all of them in parallel. A Lustre[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn7|⁷]] deployment with 100 OSS nodes, each providing 10 GB/s, delivers an aggregate 1 TB/s.

![[90 Assets/Volume II/04 Data Storage/Pfs Architecture ec4f185b34.svg]]

Figure 2: **Parallel File System Architecture**: A client makes one metadata request (MDS $\to$ MDT) to learn a file’s stripe map, then reads the stripes directly from the object storage servers (OSS $\to$ OST) in parallel. Each OST holds every Nth stripe of the file in round-robin order, so consecutive stripes (dark) sit on different servers and one client reads them at once. The shared data path lets every client draw on every OSS, so aggregate bandwidth grows with the number of servers while metadata traffic stays on a separate path.

^fig-storage-pfs-architecture

This abstract architecture has concrete implications for performance tuning. When a training job creates a new dataset directory on Lustre, the administrator configures the stripe count (the number of OSTs a file is spread across) and stripe size (the chunk size written to each OST) for that directory ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-lustreSetstripe|Lustre Wiki 2017]]). For large sequential-read training shards, administrators may choose wider striping and multi-megabyte stripe sizes so a single file can draw bandwidth from multiple OSS nodes. Lustre’s striping guide treats wide striping as useful for very large files or files accessed by many clients, while smaller files often use fewer stripes to reduce overhead ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-lustreFileStripingGuide|Lustre Wiki 2019]]).

A 4 GB data shard striped across 100 OSTs with 4 MB stripes places roughly 10 stripes on each OST. When a data loader reads large contiguous ranges, the Lustre client can issue parallel read requests to the OSS nodes holding those stripes, aggregating their bandwidth. The client also maintains its own read-ahead buffer, prefetching the next several stripes while the application processes the current ones. This file-system-level read-ahead is distinct from the data loader’s application-level prefetch buffer; the two layers of prefetching compound and can hide much of the delay to the OSS nodes from the training process, provided delivery keeps pace.

The separation between metadata and data paths is how a Lustre-style system reaches the aggregate bandwidth that ML workloads demand. GPFS[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn8|⁸]] (IBM Spectrum Scale) is a shared-disk alternative that stripes data and metadata across its disks and coordinates concurrent access through token-based distributed locking ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-schmuck2002gpfs|Schmuck and Haskin 2002]]). Its lock protocol preserves consistency across clients without a simple MDS/OSS split, at the price of more complex lock management that must scale to thousands of nodes.

The data path scales with the number of object storage servers, but every file still begins with a request to the metadata service, and that service has a finite operation rate. That finite rate is the source of the small file problem. The per-open cost that [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-data-formats|section 4.3.5]] charged to one node’s CPU now lands on a metadata service shared by the whole fleet. Each `open()` system call requires a metadata lookup, lock acquisition, and attribute fetch. Suppose a dataset of millions of 10 KB images is stored as individual files, and each of 10,000 workers, a fleet several times the running cluster, opens a new file every few samples. The aggregate open rate then exceeds the few hundred thousand operations per second an MDS typically serves. The MDS becomes the serialization point, and delivery collapses to its operation rate long before the data links saturate.

**Definition 4.2: Small file problem**

***Small file problem*** is an ML data-loading pathology in which per-file operations overwhelm a storage system’s metadata service.

1.  **Significance**: `open`, `stat`, and `close` requests from 10,000 workers can serialize at the metadata service, idle the cluster, and reduce effective I/O bandwidth $({\text{BW}_{\text{storage}}})$.
2.  **Distinction**: This is a metadata request-rate and latency $({L_{\text{lat}}})$ problem, not a bulk bit-rate problem.
3.  **Common pitfall**: Faster SSDs do not fix this format problem. Packing samples into sequential containers such as TFRecord or Parquet amortizes metadata operations across many samples.

At production scale, the metadata bottleneck can collapse an otherwise high-bandwidth file system. When a cluster migrates from aggregated containers back to individual sample files, metadata request queues saturate long before the underlying storage servers or network links reach their byte-rate limits.

**Example 4.1: The metadata meltdown**

**Scenario**: A large-scale training cluster migrates from a preprocessed sequential dataset to 200 million raw image files stored individually on a parallel file system provisioned for 500 GB/s aggregate bandwidth.

**Diagnosis**: The file system delivers less than 1 percent of rated throughput. Millions of per-second `stat()` and `open()` calls overwhelm the metadata servers, choking data loaders despite abundant network and storage bandwidth.

**Systems lesson**: Metadata contention limits delivery when operation demand exceeds metadata service capacity. Bundling 200 million raw images into 50,000 large tar shards (for example, WebDataset) reduces the file count by 4,000× and amortizes per-file operations across samples. Packaging alone does not prevent startup contention if loaders still enumerate files with per-file `stat()` calls; distributing a precomputed dataset manifest removes those repeated lookups from the hot path. Measure metadata operation rate alongside byte bandwidth to determine which service limits delivery.

^exmp-data-storage-metadata-meltdown

Striping and aggregation solve different problems. Striping distributes large files across data servers, whereas aggregation, the shard packaging of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-data-formats|section 4.3.5]], reduces the number of files the MDS must track. Realized bandwidth then depends on the reader. A read contained within one stripe uses a single server, while enough concurrent reads spanning stripes can draw from several servers at once. Wider striping therefore helps only when read sizes and concurrency exploit those paths, and small files usually need fewer stripes.

Parallel file systems provide a shared namespace and lock management that support coordinated checkpoints ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-schmuck2002gpfs|Schmuck and Haskin 2002]]), but the two ML write patterns need different guarantees from them. Immutable training shards remove conflicts with concurrent writers once the dataset version has been published, so readers need only agree on which completed version belongs to the run. A checkpoint needs more. File-system locks coordinate individual writes, and a completed write to one file does not establish that the other shards are complete, so a multi-file generation needs an application-level publication protocol, which declares it restorable only after every shard has persisted. [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|Section 4.6]] states that protocol.

The performance of a parallel file system depends on the *balance* of load across OSS nodes as well as their *number*. If a shard uses 10 of 100 equally provisioned OSS nodes, those servers offer at most 10 percent of the system’s aggregate server bandwidth. Realized delivery can be lower because of client limits, request size, or insufficient concurrency. Conversely, when many concurrent readers draw on shards striped across all 100 servers, demand spreads over every server and realized bandwidth can approach the system’s rating, provided the clients and network keep pace. Placement and access scheduling therefore matter alongside the number of storage servers, and a simple shard-assignment calculation shows how readers can bunch on one shard even when aggregate storage capacity looks ample.

**Napkin Math 4.4: The thundering herd: Shard contention**

**Problem**: A dataset is split into 1,000 shards on a shared file system. If 32 workers each pick a shard at random to start their next epoch, what is the probability that at least two GPUs “collide” on the same shard, creating a potential read hotspot? A shard collision does not imply a server collision unless the placement maps each shard to a distinct server.

**Math**: This is a variant of the “Birthday Problem” in probability.

1.  **Probability of No Collision**: $\approx e^{-{n_{\text{workers}}}^2/(2{K_{\text{shards}}})} = e^{-32^2/2{,}000} \approx 0.60$.
2.  **Probability of Contention**: $1 - 0.60 = 40\%$.

**Systems insight**: With 32 workers and 1,000 shards, the 40.1 percent collision probability identifies a potential storage-shard hotspot. Whether that collision delays workers depends on shard placement, caching, and available service capacity. Coordinating shard assignments can reduce this source of tail latency when assignments spread demand across independently serving devices while preserving the intended sampling policy.

At the scale of thousands of nodes, tail latency ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-dean2013|Dean and Barroso 2013a]]) can dominate exposed input wait. If a training step requires data from 100 storage servers and each independently has a 1 percent chance of being slow, the probability that all 100 respond quickly is $0.99^{100} = 0.366$, meaning over 63 percent of these request sets contain at least one slow response. Shared congestion can correlate delays, changing that probability. A slow response delays the step only when prefetching fails to hide it and the required input lies on the step’s critical path. When it does, the delay is not confined to one worker, because synchronous data-parallel training waits for every worker at the next collective, so one late fetch stretches the whole fleet’s step.

Systems can mitigate tail latency through hedged requests: after a chosen delay, the client issues a redundant read to another replica and uses the first valid response. The trigger delay trades faster tail completion against extra work ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-dean2013tail|Dean and Barroso 2013b]]). An independence model can multiply the probabilities of two slow replicas, but shared congestion and the later start of the hedge invalidate a simple squared-probability latency guarantee. Issuing a hedge at the median response time would duplicate roughly half of requests before accounting for cancellation; that load can worsen the congestion the scheme aims to avoid. A hedge therefore pays off only when its trigger sits in the measured tail and the duplicate traffic it adds stays within the spare service capacity.

↪ Tail latency as a serving constraint, where routing and load balancing decide which requests miss the p99 target, is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^sec-inference-scale-load-balancing-request-routing-4997|Load Balancing and Request Routing]]**.

The effectiveness of hedged requests depends on the replicated data layout. If both replicas reside on OSS nodes that share the same network switch, a switch failure makes both copies simultaneously unavailable. Effective hedging requires failure-domain-aware placement: replicas should reside in different racks, connected through different top-of-rack switches, so that the failure of any single component affects at most one replica.

In production clusters, the parallel file system is a shared utility, simultaneously servicing many concurrent training jobs with different I/O patterns. At any given moment, a large language model job might be streaming sequentially through text shards, a computer vision job might be reading random image shards, and a checkpoint storm from a third job could be saturating write bandwidth. This concurrency gives rise to the noisy neighbor problem, where one job’s I/O pattern severely degrades performance for all other jobs. A checkpoint save that consumes a disproportionate share of the PFS’s internal network bandwidth causes read latency for other jobs to spike, potentially stalling their training pipelines. The impact of sharing is easy to quantify. A PFS with 1 TB/s aggregate bandwidth, shared across 10 concurrent training jobs, provides only 100 GB/s per job on average. If one job’s checkpoint storm consumes 400 GB/s for 10 seconds, the remaining nine jobs share 600 GB/s, a 33 percent reduction that can trigger data stalls in their accelerator pipelines. PFS administrators mitigate this through I/O scheduling policies (quality-of-service tiers, bandwidth quotas per job), but these policies add administrative complexity and can reduce peak single-job throughput.

A related challenge is namespace isolation, which gives each team its own directory tree with its own striping settings. Different teams and workloads require different storage configurations. A team training on millions of 100 KB images first needs to aggregate samples to reduce metadata operations; increasing stripe count does not remove per-file metadata work. A team working with large video shards can use wider striping when read sizes and concurrency exploit the additional data paths. Misconfigured striping for one team’s workload can create hotspots that degrade performance for the entire shared file system.

**Checkpoint 4.2: Parallel file system design**

Consider a training cluster with 512 nodes, each running 8 GPUs. The training job requires 400 GB/s of aggregate read bandwidth.

**OSS count**: calculate the number of OSS nodes required when each Lustre OSS delivers 10 GB/s.

**Metadata cost**: calculate the time required to open 200 million 116 KB image files sequentially when each `open()` call takes 50 ${\text{µ}}$s on the MDS, then state the practical implication.

**Shard count**: calculate the number of metadata operations needed to read the full dataset when images are bundled into 4 GB tar files.

Parallel file systems solve the shared-namespace problem for active training clusters, but their cost per byte is too high for the organization’s complete data holdings. The petabytes of raw training data, historical checkpoints, and preprocessed datasets that an ML organization accumulates over years require a tier optimized for capacity and durability rather than bandwidth.

### Tier 4 Object Storage

^sec-storage-tier4-object

Keeping petabytes of raw corpora, preprocessed shards, and historical checkpoints on a parallel file system would pay high-bandwidth server rates for data that sits mostly at rest. At petabyte scale, object storage provides the durable, lower-cost foundation of the hierarchy. Services like Amazon S3 and Google Cloud Storage organize data in object namespaces where objects are retrieved by keys rather than by POSIX directory paths ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-awsS3ObjectKeys|Amazon Web Services 2026c]]; [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-googleCloudStorageObjects|Google Cloud 2026]]). Unlike file systems, which organize data in hierarchical directories with metadata-rich operations (rename, link, permission inheritance), object storage treats each object as an opaque blob identified by a unique key. The simpler interface changes the namespace operations exposed to clients; the service still manages metadata for placement, versions, access control, and integrity as capacity grows.

Services such as Amazon S3 publish an “eleven nines”[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn9|⁹]] annual durability target (99.999999999 percent). Erasure coding,[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn10|¹⁰]] replication, placement, and repair contribute to storage protection, but a coding scheme alone does not establish a service’s durability target. Selecting a source-of-truth tier for training data and checkpoint archives requires checking the chosen service’s failure model alongside versioning, lifecycle policy, access control, and recovery testing.

Three different guarantees govern whether that source of truth is usable. Durability asks whether acknowledged data survives failures; availability asks whether the storage service responds when a client needs it; and consistency asks which version a read is allowed to observe when writes overlap or replicas disagree. Replication can improve durability and availability without by itself guaranteeing that a reader sees the newest committed checkpoint. A recovery design must therefore state all three properties instead of treating a durability percentage as a complete reliability contract.

**Definition 4.3: Erasure coding**

***Erasure coding*** protects stored data by adding redundant fragments, with the Reed-Solomon scheme considered here encoding ${d}$ data and ${m}$ parity blocks so that any ${d}$ remaining fragments recover the original.

1.  **Significance**: Coding can protect against fragment loss with less capacity overhead than full replication. A 4+2 Reed-Solomon code stores four data fragments and two parity fragments, tolerating two unavailable fragments at 1.5$\times$ storage overhead instead of the 3$\times$ overhead of triple replication. Actual durability also depends on failure correlation, placement, detection, and repair.
2.  **Distinction**: Unlike replication (which stores complete copies), erasure coding uses mathematical encoding (for example, Reed-Solomon) to distribute redundant information across different failure domains (disks, racks, or sites).
3.  **Common pitfall**: A frequent misconception is that erasure coding is “free durability.” In reality, it is a latency-compute trade-off: reconstructing data after a failure requires additional CPU cycles and increases the p99 latency of the storage read.

Erasure coding lets the service recover data without requiring the training application to manage fragments. In the form considered here, the service retains the original ${d}$ data fragments alongside parity, so healthy reads can use the data fragments directly. When a required fragment is unavailable, reconstruction uses surviving data and parity fragments. The object interface hides that recovery procedure, but additional I/O, network traffic, and decoding can remain visible as longer read latency. Protection against data loss does not imply unchanged service time during a failure.

Object storage also costs less per byte. At a representative \$0.02/GB/month, its recurring capacity rate is 5× lower than the local-NVMe rate of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^tbl-storage-hierarchy-merged|table 2]], and [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.09 Storage Economics#^sec-storage-economics|section 4.8]] converts that ratio into annual costs for a 100 TB dataset. Comparing it with HBM acquisition cost additionally requires a hardware lifetime and utilization assumption. This cost advantage makes object storage a common home for the organization’s training data lake, where raw data, preprocessed datasets, and archived model artifacts can reside durably.

Request latency also matters. Design estimates use 50 to 100 ms for an object GET as a representative planning range rather than a universal service guarantee. Much of that delay is the price of the indirection that provides durability. The service looks up the object’s location in a distributed metadata index, determines which fragments to read, fetches them from potentially different storage nodes, and reconstructs data when a fragment is unavailable, all on top of the client network path and queueing. Large transfers amortize per-request overhead across more bytes, while small transfers can spend most of their elapsed time on that overhead. Request size and concurrency therefore enter the delivery budget alongside aggregate bandwidth.

The remedy is the shard packaging of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-data-formats|section 4.3.5]], applied here to request latency rather than metadata operations. Formats like WebDataset ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-aizman2019|Aizman et al. 2019]]) or Mosaic Streaming ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-mosaicStreamingMainConcepts|Databricks 2026]]) bundle samples into multi-gigabyte shards that transform high-latency random access into high-bandwidth sequential streaming. Rather than issuing billions of small GET requests, the data loader issues hundreds of large reads in parallel, each fetching an entire shard that contains thousands of samples. With sufficient parallelism and colocated network capacity, object storage can sustain high aggregate throughput, enough to feed large training clusters for some workloads. The streaming pattern works by assigning each data loader worker a subset of shards and having it read them sequentially. Within each shard, samples are stored contiguously, so the worker decodes them in order and shuffles them in a local buffer. This approach achieves pseudo-random access across the dataset while maintaining sequential I/O at the storage level.

The architecture of a streaming data loader for object storage differs from a local-storage loader in important ways. A local-storage loader can use memory-mapped I/O to treat the dataset as a virtual memory region, relying on the operating system’s page fault mechanism to load data on demand. This approach is elegant but incompatible with object storage, which answers HTTP requests rather than offering the POSIX file system interface that memory mapping requires. Instead, an object-storage loader must explicitly manage HTTP connections, issue ranged GET requests for specific byte ranges within shards, handle retries on transient failures, and manage a local buffer pool for decoded samples. Libraries like WebDataset and Mosaic Streaming encapsulate this complexity, presenting a simple iterator interface to the training loop while managing the HTTP transport and buffering internally.

Applying this streaming architecture to the running example makes the design concrete as an alternative to the staged path the chapter adopts. Instead of copying shards to local NVMe at job start, the cluster would read them from the object store throughout the run. The tokenized training set is stored in an S3-like object store as roughly 2,000 shards of 3 GB each. The streaming architecture assigns each of the 256 compute nodes a unique subset of roughly 8 shards. Within each node, 8 data loader worker processes issue concurrent HTTP `Range` requests to fetch 256 MB chunks from their assigned shards. Across the cluster, this results in 2,048 concurrent requests, allowing aggregate throughput in the 50–100 GB/s range when the object store and network path are provisioned for it, far exceeding the roughly 167.8 MB/s required by the generic text job in the text-versus-image comparison. The running example’s average input demand is lower still. The network between the compute cluster’s virtual private cloud (VPC, its isolated network inside the provider) and the object-storage endpoint can cap streaming throughput, but at these provisioned service rates the cap still exceeds what the running job needs. Organizations that co-locate compute and storage in the same cloud availability zone (one isolated data-center site of a provider) can reduce cross-network latency, which lowers the required prefetch buffer depth for jobs with short steps and improves overall pipeline efficiency.

That request parallelism is what object storage rewards. Each of the 2,048 GET requests is independent and can be served by a different storage node within the cloud provider’s infrastructure, and the count grows with the fleet. With each request fetching a 256 MB chunk of a shard, the aggregate throughput depends on the cloud provider’s network capacity, internal bandwidth, and request-rate quotas. The practical limit is often the network bandwidth between the compute cluster and the object storage service, not the storage service’s internal media bandwidth.

Many object storage services provide strong read-after-write consistency, which means that a subsequent read of an acknowledged object sees the completed write. Amazon S3 announced strong read-after-write consistency for object writes and overwrites, together with strongly consistent listing, in December 2020 ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-aws2020s3|Amazon Web Services 2020]]). The relevant contract is the documented behavior of the chosen backend, not a blanket assumption about object storage. Per-object consistency still does not make a checkpoint spanning many objects atomic, so the publication protocol of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|section 4.6]] applies here as it does on a file system.

The scale of ML datasets makes them vulnerable to silent data corruption: subtle bit flips in the storage medium or during network transfer that can introduce training artifacts nearly impossible to diagnose. Object storage services provide per-object checksums that verify integrity on upload, copy, or download; Amazon S3, for example, documents checksum options including CRC-family and cryptographic hashes ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-awsS3ObjectIntegrity|Amazon Web Services 2026a]]). Parallel file systems often rely on underlying RAID or erasure coding for physical integrity but may not provide end-to-end checksums visible to the application. A well-engineered large-scale ML pipeline computes and stores a checksum for each data shard during preprocessing and verifies it when the shard is first loaded by a training worker. The verification overhead is negligible compared to the cost of training on corrupted data, and checkpoints need the same check, because a flipped bit in restored state can make training diverge silently after recovery.

↪ Detecting and verifying silent data corruption across the fleet, including in restored checkpoints, is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.06 Check-And-Verify Defenses Against Silent Data Corruption#^sec-ft-sdc-verification|Check-and-Verify Defenses Against Silent Data Corruption]]**.

Training datasets can contain sensitive information, including personal data, proprietary text, and licensed images. Storage design must carry the organization’s access and retention policies through every copy. Object services expose identity policies and encryption options; parallel file systems provide POSIX permissions and access-control lists. Audit coverage and enforcement depend on the configured platform, not the tier’s name. Versioned manifests should identify derived shards and retained copies so that access reviews, retention decisions, and deletion workflows can locate the relevant artifacts; a deletion request, for example, must reach every immutable preprocessed shard derived from the deleted record. Storage controls protect stored bytes; evaluating what a trained model retains requires additional model-level analysis.

The transition from Tier 4 to Tier 5 is driven primarily by economics. Data that is accessed rarely should move to archive storage when retrieval latency and governance requirements allow it, because archive capacity is cheaper still.

### Tier 5 Archive and Cold Storage

^sec-storage-tier5-archive

Archive services such as S3 Glacier preserve rarely accessed lineage (superseded checkpoints, raw source corpora, and training logs) over multi-year horizons so that a deployed model can still be reproduced or audited years after its run ends. At a representative \$0.004/GB/month, archive storage is 5× cheaper than the \$0.02/GB/month object-storage assumption used in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier4-object|section 4.3.7]], trading that lower capacity rate for retrieval latency measured in minutes to hours and making this tier unsuitable for operational access. The record at stake is training data provenance: the link from a deployed model to the exact data versions, hyperparameters, and preprocessing that produced it. The organization’s governance policy determines which records to retain and for how long, and the storage design must keep them identifiable and retrievable for that period; archive serves when its retrieval delay meets the requirement, while records needed during frequent investigations may justify a warmer tier.

Automated lifecycle policies govern the transition of data between tiers based on access recency. As one illustration of how such automation is expressed, a time-based rule for ML infrastructure might move checkpoints as follows. The most recent three checkpoints remain on the parallel file system for fast recovery. Checkpoints older than 72 hours are transitioned to object storage, and checkpoints older than 90 days are transitioned to archive storage. Checkpoints older than two years are deleted unless flagged for regulatory retention. S3 Lifecycle rules provide the same general transition/archive/delete mechanism for object lifetimes ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-awsS3LifecycleManagement|Amazon Web Services 2026b]]). The running example’s checkpoint retention in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|section 4.6]] adopts a count-based variant of the same idea, where the transition rule keys on checkpoint count rather than age. Without automation, teams either hoard data on expensive tiers (wasting budget) or delete data too aggressively (losing reproducibility). The lifecycle policy encodes the organization’s cost-recovery trade-off in a declarative rule that requires no manual intervention.

For the 175B model training run, the archive tier holds the complete training lineage: the raw 3 TB compressed source corpus, the 6 TB serialized shard set, all preprocessing scripts, the final checkpoint, and a sampled subset of intermediate checkpoints. Capacity must include every retained full checkpoint as well as both corpus representations; [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^tbl-data-storage-175b-footprint|table 5]] computes that total for the declared retention policy. The asymmetry between archive cost and compute cost makes retention inexpensive relative to the run it documents; failures to archive usually reflect missing lifecycle ownership, unclear retention policy, or retrieval-process neglect rather than raw capacity cost.

Archive storage services offer multiple retrieval speed tiers, each with different pricing. In an S3 Glacier-style service, standard retrieval may complete within hours at moderate cost, expedited retrieval may complete within minutes at a higher cost, and bulk retrieval may trade still more latency for the lowest retrieval price ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-awsS3GlacierRetrieval|Amazon Web Services 2026d]]). The choice of retrieval tier depends on the urgency of the use case. Forensic analysis of a production incident warrants faster retrieval; annual compliance audits can use slower bulk retrieval. Designing the lifecycle policy requires understanding the storage cost, the expected retrieval frequency, and the urgency for each class of data.

The six tiers now have their roles, capacities, and prices, but a role does not say how fast bytes must climb the hierarchy. That rate is set by the accelerators consuming them, and it is the next quantity to derive.

2.  Host DRAM (Tier 1) executes a four-stage data loader pipeline: Read, Decode, Augment, and Collate. Why place the final collated batch in page-locked (‘pinned’) host memory for direct asynchronous DMA to GPU HBM without an intermediate staging copy?

    1.  Pinned memory automatically compresses tensors using host CPU vector units before PCIe transmission.
    2.  Pinned memory locks physical pages in host RAM so the PCIe DMA controller can copy data directly to GPU memory without an intermediate pinned staging copy.
    3.  Pinned memory replicates the batch across all NUMA nodes to ensure uniform memory access for parallel data loader threads.
    4.  Pinned memory guarantees transactional ACID durability on host storage in case the worker process crashes during transfer.

3.  A vision training cluster migrating to a high-performance parallel file system (PFS) with $500\text{ GB/s}$ rated aggregate bandwidth reports that throughput during ImageNet training is capped at under $5\text{ GB/s}$, with storage data disks showing negligible I/O activity. The dataset consists of millions of individual JPEG files. A worker trace shows repeated waits for file opens, and the MDS reports a sustained operation queue with rising lookup latency while its service rate is saturated. What bottleneck do these additional measurements establish, and which fix addresses it?

    1.  The network fabric is dropping packets due to congestion; enable flow control on top-of-rack switches.
    2.  The parallel file system is bottlenecked on drive endurance wear-leveling; replace SSDs with high-DWPD enterprise drives.
    3.  The dataset is stored as millions of individual image files, saturating the Metadata Server (MDS) with per-file POSIX lookups; repackage images into large sequential shards (such as WebDataset tar archives).
    4.  The GPUs are compute-bound and cannot consume data faster; decrease the batch size to increase I/O request frequency.

What can be concluded about this sizing decision from the supplied information?

    3.  The model will fail to converge because object storage cannot maintain ACID consistency when serving multiple modalities simultaneously.
