# V2-04.02 The Fuel Line

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-fuel-line

The dense accelerator nodes of **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02 Compute Infrastructure#^sec-compute-infrastructure|Compute Infrastructure]]** pack eight GPUs delivering petaFLOP/s of aggregate compute, and the InfiniBand fabrics of **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03 Network Fabrics#^sec-network-fabrics|Network Fabrics]]** connect thousands of such nodes at hundreds of gigabits per second. Within the multi-tier fleet stack of **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^fig-fleet-stack|The Fleet Stack]]**, data storage completes that physical foundation, staging training data, model weights, optimizer state, and intermediate checkpoints at the right distance from the accelerator. An engine without fuel is expensive sculpture. The engineering question is how to deliver that fuel fast enough that the accelerators of a training cluster never starve.

The running cluster for that question is 256 eight-GPU nodes, 2,048 accelerators in all, deliberately twice the 1,024-GPU (128-node) reference cluster used elsewhere in this book, because the larger fleet makes the pressure on shared storage easier to see. Every worked number for the 175B job uses this running cluster; a side scenario with a different workload or fleet size names its own scale where it appears.

*Storage is the physical substrate spanning Compute (${C}_1$), Communication (${C}_2$), and Coordination (${C}_3$).*

Consider the running example for the storage analysis, an instance of Archetype A (GPT-4/Llama-3). A 175-billion parameter language model trains on 1.5 trillion tokens of text: roughly 3 TB in compressed source form, or 6 TB once represented as 4-byte token IDs. That token budget is set upstream of storage. Under the compute-optimal scaling results of **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.04 AI Scaling Laws#^sec-vol2-intro-ai-scaling-laws-a043|AI Scaling Laws]]**, the training-token count grows in proportion to parameter count, so each step up the model-size curve enlarges both the corpus the fleet must hold and the bytes each epoch must read. This corpus already sits below the compute-optimal allocation for a 175B-parameter model, so a compute-optimal run would raise both figures further. The run makes a single pass (one epoch) over this corpus, reading every selected token once in an order determined by the shuffle seed. No small “hot” subset dominates access. Meanwhile, each training step consumes one global batch of 1,536 sequences (3,145,728 tokens), then waits for the next. On the running cluster the modeled step takes about 4.64 seconds, an estimate from the book’s performance model rather than a measurement, so the single epoch lasts about 25.6 days. If storage cannot deliver that batch before the current step ends, the accelerators sit idle, and the organization pays for silicon that produces heat instead of gradients.

The problem is deceptive because storage technology has improved substantially. Non-Volatile Memory Express (NVMe) drives achieve 7 GB/s of sequential throughput, a figure that would have seemed out of reach a decade ago. An H100 moves data internally through high-bandwidth memory (HBM) at 3.35 TB/s, roughly 479× the sequential bandwidth of a single NVMe drive. This ratio contrasts two tiers; it is not the rate at which storage must supply training inputs, because HBM bandwidth also carries repeated weight, activation, and tensor traffic during computation. The storage feed requirement is instead determined by the input-batch bytes each accelerator needs per iteration. Dividing those bytes by the compute window gives one worker’s required delivery rate; summing across workers gives the fleet demand. That rate must be evaluated at each tier using the representation stored there, since compressed inputs and decoded tensors occupy different numbers of bytes. A hierarchy becomes useful when the durable source cannot meet that rate or its latency varies enough to interrupt computation. Faster tiers stage upcoming batches while the durable tier supplies capacity and preserves the source data.

The storage problem joins physics with economics. Physics favors the memory closest to the accelerator, which offers the highest bandwidth in the smallest capacity; economics favors shared storage, which pools far more capacity at lower cost per byte behind additional interfaces and service queues. Device technology, interconnects, and contention then determine the rate a particular consumer actually receives. The engineering task is to place and move data so that the accelerator receives each batch before it is needed. The resulting design problem is quantitative. It asks how fast each tier must be, how deep the pipeline must run, and which bytes are worth keeping close to the accelerator. Improving arithmetic throughput alone does not improve input delivery or checkpoint persistence. Those paths require their own bandwidth and latency budgets.

*Over the run, checkpoint writes exceed one epoch of training-data reads by more than 1,000 times.*

The canonical training-data footprint for this example is roughly 9 TB across the hierarchy, combining the example’s compressed corpus and tokenized shards. Additional shuffled or packed variants can raise the staging footprint, but the per-epoch training read over 4-byte token IDs is 6 TB. This chapter adopts one resumable mixed-precision Adaptive Moment Estimation (Adam) checkpoint contract: FP16 model weights at 2 bytes per parameter, FP32 master weights at 4, and two FP32 Adam moments at 4 each, for 14 bytes per parameter. This is the 16-byte training state of **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-node-memory|Node memory partitioning]]** without its 2-byte FP16 gradients, which are recomputed after restore, while scheduler, random-number-generator, and data-loader metadata are negligible at this scale. The resulting checkpoint is 2,450 GB every 10 minutes. The storage plan budgets a 30-day training window, which the modeled 25.6-day epoch fits inside. Over that window on the 256-node cluster, the storage system must deliver 6 TB of tokenized training data in the run’s single epoch, absorb 10.6 PB of checkpoint writes, and stage model weights for evaluation runs. The sections that follow use this same contract for every checkpoint size, duration, retention total, and lifetime-write calculation.

Those numbers force the storage path. ML access patterns first invert the assumptions behind conventional storage systems. That inversion forces a hierarchy from HBM to cold archive. The hierarchy then requires a pipeline equation that sizes delivery and direct data paths that remove host copies. It also requires a checkpoint protocol for the dominant write traffic, commit boundaries that keep every versioned artifact reproducible (generated training data included), and economics that decide which bytes belong at each tier. Serving-time model loading and retrieval indexes are variations on the same fuel-line problem, and devices that move the boundaries between tiers close the chapter. In each workload, the storage system must place the right representation at the right distance before the accelerator asks for it.

**Self-Check: Question**

1.  An H100 accelerator consumes data from its HBM at roughly $3.35\text{ TB/s}$, while a single local NVMe drive delivers sequential reads at roughly $7\text{ GB/s}$. A team is designing the storage infrastructure for a 1,000-accelerator training fleet. Which conclusion follows directly from this bandwidth ratio?

    1.  The gap is easily bridged by standard NVMe RAID arrays because sequential read throughput scales without bound across drives.
    2.  The roughly $479\times$ device-bandwidth gap motivates tiered staging, but required input bandwidth must be calculated from batch bytes and compute time rather than equated with HBM traffic.
    3.  The bandwidth gap is negligible because large-scale training is entirely compute-bound and rarely exercises HBM bandwidth.
    4.  The bandwidth gap disappears when high-speed InfiniBand fabrics deliver data directly into HBM from remote storage endpoints without local staging.

2.  A 175B-parameter model trains for 30 days on 256 nodes, writing resumable mixed-precision Adam checkpoints of roughly $2.45\text{ TB}$ ($350\text{ GB}$ FP16 weights, $700\text{ GB}$ FP32 master weights, and $1.4\text{ TB}$ of Adam moments) every 10 minutes. Explain why ML storage design is fundamentally a joint physics-and-economics optimization problem.

3.  True or False: A cluster benchmark demonstrating that compute hardware achieves advertised peak TFLOP/s and network fabric achieves advertised bisection bandwidth is sufficient evidence that end-to-end training throughput will scale linearly with accelerator count.

4.  An accelerator upgrade reduces compute time per batch while the input representation and storage delivery time remain fixed. What is the primary systems consequence for training cluster design?

    1.  Training pipelines automatically increase data compression ratios to prevent accelerator starvation without requiring architectural adjustments.
    2.  Storage hierarchies can eliminate intermediate DRAM and NVMe caching tiers because modern network fabrics directly absorb the difference.
    3.  Checkpoint intervals must be decreased proportionally to the compute growth to keep local NVMe buffers from overflowing.
    4.  The compute window available to deliver each batch shrinks, so input I/O can become the bottleneck unless the measured delivery path keeps pace.
