# V2-04.16 Footnotes

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^footnotes

<sup>1</sup> **RAID (redundant array of independent disks)**: A Berkeley taxonomy of drive-combining strategies that trade redundancy, capacity, and I/O performance ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-patterson1988raid|Patterson et al. 1988]]). RAID 0 stripes data without redundancy and can suit a disposable cache backed by a durable source. A drive failure then requires restaging; redundancy may still be worthwhile when that recovery cost or the required availability justifies it. Unreplicated checkpoints and sole dataset copies require a different durability contract.

^fn1

<sup>2</sup> **IOPS (input/output operations per second)**: The metric that dominated storage procurement for decades because database workloads issue millions of small random reads. ML training inverts this priority: a pipeline streaming 256 MB shards sequentially needs sustained GB/s throughput, not per-operation speed. Provisioning storage by IOPS rating for an ML workload over-spends on random-access capability the pipeline never exercises.

^fn2

<sup>3</sup> **LRU (least recently used)**: An eviction policy that discards the entry unused for the longest time, effective when recently accessed data is likely to be accessed again soon. Under independent reshuffling, some samples retained from the end of one epoch may be reused early in the next, so teams should measure that reuse before allocating DRAM that could otherwise serve as prefetch buffers.

^fn3

<sup>4</sup> **NVMe (Non-Volatile Memory Express)**: A storage protocol designed for SSDs, connecting directly to the CPU via PCIe lanes. Its many deep command queues, replacing the single 32-command queue of the older SATA interface, are what allow a multi-worker ML data loader to keep enough requests outstanding to saturate the drive’s bandwidth.

^fn4

<sup>5</sup> **WebDataset**: A data format that repurposes standard POSIX tar archives for ML training. The design insight is that tar’s sequential header-then-data layout, invented in 1979 for tape backup, maps perfectly onto the streaming access pattern that ML data loaders need.

^fn5

<sup>6</sup> **OSS (object storage server)**: In parallel file system terminology, “object” means a chunk of striped file data managed by an object storage target, a usage that predates cloud object storage (S3, GCS) by over a decade. Confusing the two is a common source of miscommunication: when a Lustre administrator says “add more OSS nodes,” they mean adding data-serving capacity to the parallel file system, not provisioning cloud buckets.

^fn6

<sup>7</sup> **Lustre**: A portmanteau of “Linux” and “cluster,” developed at Carnegie Mellon University and first deployed in production in 2003. Lustre is common in HPC and ML infrastructure because its architecture scales aggregate bandwidth linearly with the number of OSS nodes, the same property that makes it a natural choice for training clusters where a single job may demand hundreds of GB/s of sustained read throughput.

^fn7

<sup>8</sup> **GPFS (General Parallel File System)**: Developed by IBM Research starting in 1998, now marketed as IBM Spectrum Scale. For ML checkpoint writes, its token-based distributed coordination can reduce reliance on a single dedicated metadata path, but it also makes lock behavior part of the performance envelope.

^fn8

<sup>9</sup> **Eleven nines (99.999999999 percent durability)**: A design target of 11 nines annual durability corresponds to an expected loss probability of about $10^{-11}$ per object-year; for one million objects, that is about one expected object loss per 100,000 years.

^fn9

<sup>10</sup> **Erasure coding**: Built on Reed-Solomon codes ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-reed1960|Reed and Solomon 1960]]), which use maximum-distance-separable coding to recover the original data from any sufficient subset of encoded fragments. In storage systems, Reed-Solomon-style codes and later local-reconstruction variants trade storage overhead against repair bandwidth and degraded-read cost ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-plank1997|Plank 1997]]; [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-huang2012erasure|Huang et al. 2012]]). Local-reconstruction codes, for example, read fewer surviving fragments to rebuild a lost one, cutting repair traffic at the price of a little extra capacity.

^fn10

<sup>11</sup> **Data gravity**: A metaphor treating large datasets as massive objects that attract compute. The gravitational analogy is apt: moving a 100 TB dataset out of one cloud provider to another costs roughly \$9,000 in egress fees and takes hours, while launching compute next to the data is near-instantaneous. In ML fleet design, data gravity means the storage location of the training dataset often dictates the physical placement of the entire training cluster.

^fn11

<sup>12</sup> **GDS (GPUDirect Storage)**: Part of NVIDIA’s GPUDirect family, which also includes GPUDirect RDMA (network adapters writing directly to GPU memory) and GPUDirect Peer-to-Peer (inter-GPU memory access); GDS extends this data-copy-bypass approach to NVMe storage. With RDMA and GDS, payload data can traverse the path remote storage $\to$ network $\to$ GPU memory without a CPU-mediated bounce copy, while the CPU still issues and coordinates the operations.

^fn12

<sup>13</sup> **Hash cost (SHA-256)**: Verifying the integrity of a 100 TB dataset using SHA-256 consumes approximately 55.6 CPU-core hours at a per-core hashing rate of 500 MB/s. The work parallelizes across shards, but it still competes with decoding for host cores and must read every byte, so the validation step is best pipelined with ingestion rather than run as a separate pass before the fleet starts.

^fn13
