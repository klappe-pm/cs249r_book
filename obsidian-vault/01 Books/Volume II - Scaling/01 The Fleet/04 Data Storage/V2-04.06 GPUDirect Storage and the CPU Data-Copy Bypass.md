# V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-gds

Even when the storage tier has enough raw bandwidth, the traditional data path for loading training data routes every shard read from storage $\to$ host DRAM $\to$ GPU HBM in three hops, one of them a CPU copy inside host DRAM. Data is first read from NVMe into a kernel buffer in host DRAM by a DMA transfer, then copied by the CPU into the data loader’s user-space buffer, and finally transferred over PCIe to GPU memory by the GPU’s DMA engine. Each hop adds latency and consumes host resources because the CPU must orchestrate every transfer, manage buffer allocation, and handle interrupts from both the storage device and the GPU. For a single transfer, this overhead is negligible, but when eight GPUs on a node each demand thousands of small transfers per second, the aggregate CPU load for payload movement alone can saturate multiple cores and starve the data augmentation stage. GPUDirect Storage (GDS),[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.16 Footnotes#^fn12|¹²]] which removes that host-memory bounce copy for local or RDMA-attached NVMe while the CPU still submits and coordinates I/O through the software stack, pays off whenever that host copy limits throughput.

**Definition 4.4: GPUDirect Storage**

***GPUDirect storage (GDS)*** is a technology that enables a direct DMA path between NVMe storage devices and GPU memory, bypassing the system-DRAM bounce buffer and CPU payload copies while retaining CPU submission and control.

1.  **Significance**: It eliminates the “bounce buffer” through system memory. In the small-transfer model detailed in notebook [4.6](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#nbk-data-storage-cpu-bypass-dividend), the assumed active CPU service per request falls by 75 percent. That model estimates CPU capacity savings, not an end-to-end latency guarantee. Whether the storage link saturates depends on the remaining bottlenecks.
2.  **Distinction**: Unlike traditional I/O, where payload data is staged through host buffers and copied between them, GDS provides direct memory access between the storage controller and the accelerator. CPU-issued I/O calls and kernel storage drivers remain in the control path.
3.  **Common pitfall**: A frequent misconception is that GDS makes all storage “faster.” The direct path depends on supported storage and interconnect configurations; it does not eliminate media latency, network latency, or queueing.

The software layers in the traditional I/O path contribute control overhead as well as payload-copy work. Direct I/O and pinned buffers can avoid some copies even without GDS. The correct baseline is therefore the actual data path rather than a fixed number of copies for every read. The direct path changes the payload route without eliminating the software control path. The application registers a GPU memory region for direct DMA (through the cuFile API in NVIDIA’s implementation), and later reads move payload from NVMe into GPU memory without an intermediate system-memory buffer. The file system and kernel storage drivers still handle submission and completion.

The benefit from GDS matters when host payload movement is a limiting stage after other pipeline work is accounted for. In [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass#^fig-gds-path|figure 6]], the conventional path takes two DMA hops through intermediate host-DRAM bounce buffers, while GDS takes a single direct DMA transfer. The direct path eliminates the CPU payload-copy stage, but the dashed control link shows that the host CPU still orchestrates transfer submission and completion.

![[90 Assets/Volume II/04 Data Storage/Gds Path 8a12212ca6.svg]]

Figure 6: **Traditional vs. GPUDirect Storage Path**: Both panels draw the same node: CPU and host DRAM above a PCIe switch, NVMe and GPU below it. Green routes are DMA transfers of payload bytes. In the buffered path (a), payload climbs into host DRAM and comes back down, and the CPU copies every payload from the kernel buffer to a pinned buffer before the accelerator’s DMA can start. In the GDS path (b), NVMe transfers directly into GPU memory, and the dashed CPU link shows the submission and completion work that remains.

^fig-gds-path

GDS benefits depend on the bottleneck, request sizes, alignment, concurrency, and storage topology. Removing host bounce buffers can improve throughput when those copies limit the path; it does not imply that the smallest transfers benefit most. Small I/O may remain submission- or latency-limited and require concurrency to approach the available bandwidth. Benchmarks of the direct path therefore measure I/O size and per-device behavior as well as throughput. The benefit appears only in an end-to-end comparison of the pipeline with and without the direct path, and the clearest case is the one where host CPU time per request is the limiting stage.

**Napkin Math 4.6: The CPU bypass dividend**

**Problem**: A training node with 8 GPUs loads 116 KB images at 8,000 images/s per GPU (64,000 images/s total). That rate is deliberately aggressive, several times the per-GPU image rate of notebook [4.1](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#nbk-data-storage-text-vs-image-bandwidth), to isolate the case in which per-request CPU work is the limiting stage. Assume active CPU service of 120 μs per request on the buffered path and 30 μs on the direct path. These illustrative service times exclude time blocked on I/O; compare the implied CPU load rather than treating elapsed transfer latency as CPU time.

**Traditional path**: In the assumed buffered implementation, each image requires a DMA from NVMe to DRAM, a host copy from kernel to user space, and a PCIe transfer to GPU. At 64,000 images/s with 120 μs of CPU time per image, the CPU spends 7.68 seconds of CPU time per wall-clock second, consuming roughly 8 cores worth of processing just for data movement.

**GDS path**: Each image is transferred directly via DMA from NVMe to GPU. At 30 μs of CPU time per image (for initiating the DMA), the CPU spends 1.92 seconds of CPU time per wall-clock second, freeing roughly 6 cores for data augmentation.

**Systems insight**: Under the assumed CPU-service costs, bypassing payload copies releases processing capacity for preprocessing. The calculation does not predict end-to-end transfer latency, nor prove that preprocessing or storage throughput can sustain this request rate.

GDS has practical limitations. Not all NVMe controllers support peer-to-peer PCIe transfers, and the data must already be in a format that the GPU can consume directly (raw pixel values, token IDs, or formats handled by GPU decoders, rather than arbitrary compressed JPEG or gzip streams). In practice, many pipelines use a hybrid approach: CPU-side decoding for compressed formats followed by a normal pinned-memory GPU transfer, while GDS is reserved for direct reads of GPU-consumable data from supported local or remote storage.

The architectural evolution from CPU-mediated copies to direct storage access reflects a broader trend of removing CPU payload copies from the critical data path wherever possible. RDMA allows network payloads to move without CPU copying, while GDS provides the same bypass for storage payloads. Together, RDMA and GDS let data flow from remote storage (such as NVMe over Fabrics, or NVMe-oF), through the network fabric, and into GPU memory without a host-memory bounce copy. The CPU still submits and coordinates the operation, while more of its capacity remains available for data augmentation, pipeline orchestration, and error handling.

↩︎ RDMA and kernel-bypass network paths are established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-rdma|RDMA and GPUDirect]]**.

The GDS design principle also extends to checkpoint writes. Whereas a host-staged path transfers checkpoint bytes from GPU HBM through host DRAM to NVMe, a supported direct path can bypass that host staging for a 2,450 GB checkpoint. Removing the copy reduces ${T_{\text{write}}}$ only when that movement contributes to the exposed pause; snapshot consistency, serialization, storage service, and durable publication remain separate requirements.

### The Complete Data Path

^sec-storage-complete-path

Combining GDS with the multi-tier hierarchy, the complete data path connects the tiers for the running example. At the beginning of the training job, the 6 TB serialized shard set, derived from the 3 TB compressed source corpus, is staged from object storage into the cluster’s local NVMe caches, with each node receiving its assigned shard subset during setup. The data loader workers read tokenized shards from NVMe, assemble packed sequences in pinned host DRAM, and transfer those batches to the accelerator. With GDS enabled, token IDs that are already in a GPU-consumable layout can be loaded directly into GPU memory without CPU payload copying; compressed formats still require CPU or GPU decompression before use.

During steady-state training on the host-staged path, CPU data loader workers read from local NVMe and fill a prefetch queue in host DRAM. The GPU receives batches from this queue via PCIe DMA; the supported GDS alternative bypasses that host payload staging. The compute phase (forward pass, backward pass, optimizer step) consumes the batch and updates model state in HBM. Every 10 minutes, the training framework captures a consistent checkpoint, writes it to local NVMe through the chosen path, and copies it to the parallel file system in the background. The checkpoint protocol must still establish when all required shards are safe to publish for recovery.

At the end of the training job, the final model checkpoint is promoted from the parallel file system to object storage for long-term retention. The local NVMe copies are deleted during job cleanup. If the model is deployed for inference, it is loaded from object storage into the serving cluster’s HBM, completing the lifecycle of data movement through the hierarchy.

Training samples and checkpoints are each copied several times in this lifecycle. Each training sample traverses one chain of copies: object storage $\to$ NVMe (staging), NVMe $\to$ host DRAM (read), host DRAM $\to$ GPU HBM (transfer). Each checkpoint traverses another: GPU HBM $\to$ NVMe (local save), NVMe $\to$ parallel file system (async copy), parallel file system $\to$ object storage (long-term retention). Every copy consumes bandwidth and contributes latency. The engineering goal is to minimize copies on the critical path (the training loop) and tolerate additional copies on noncritical paths (staging and archival). Both lifecycles cross the same tiers in opposite directions, with synchronous critical-path copies drawn solid and asynchronous background transfers drawn dashed in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass#^fig-storage-complete-data-path|figure 7]]. For training inputs moving rightward, the active loop waits only on local promotion into HBM (or the optional GDS bypass); for checkpoints flowing leftward, the exposed pause is confined to the local NVMe save while parallel-file-system replication and archival retention proceed off the critical path.

![[90 Assets/Volume II/04 Data Storage/Complete Data Path 147ae9e03f.svg]]

Figure 7: **The Complete Data Path**: Columns are storage tiers, ordered from the durable object store (left) to accelerator memory (right). Training data moves right and bypasses the parallel file system in this running example; checkpoints return left through it. Solid arrows mark copies the training loop waits on; dashed arrows mark copies that run once per job or in the background. The dashed outline is one GPU node: every copy the training loop waits on stays inside it.

^fig-storage-complete-data-path

Every copy that leaves the node also needs a network, and the choice of network decides whom a storage burst can disturb. Many training nodes carry a small number of storage-facing network adapters on a separate front-end network, in addition to one compute-fabric adapter per accelerator. Routing staging reads and checkpoint copies over that front-end network isolates them from gradient collectives, but it caps each node’s storage bandwidth at a few front-end ports. Routing storage over the compute fabric offers far more bandwidth, and remote GDS reads use exactly that RDMA path, but then a checkpoint burst shares switch buffers and spine links with the job’s collectives and must be separated by traffic classes.

For the running example, each node’s fair share of a 1 TB/s file system shared by 256 nodes is roughly 4 GB/s, and copying its roughly 10 GB checkpoint shard within the 10-minute interval needs far less, so a front-end network can carry it. Image workloads that stream hundreds of GB/s across the cluster push designs toward the compute fabric. Through the C$^3$ lens, storage traffic becomes communication (${C}_2$) load the moment it leaves the node, and the network chosen to carry it decides which collectives a storage burst can delay.

Over the 30-day window, checkpointing writes roughly 10.6 PB of state against a single read of the 6 TB serialized dataset, so checkpoints, not training inputs, are the storage workload to design next. That design must take a multi-terabyte save off the training critical path without ever exposing a checkpoint that cannot be restored.
