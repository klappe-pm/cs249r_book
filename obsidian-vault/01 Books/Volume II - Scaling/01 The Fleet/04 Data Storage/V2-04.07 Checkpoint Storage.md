# V2-04.07 Checkpoint Storage

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-checkpointing

After the 2,048 accelerators of the running cluster have been training for six hours, a power supply failure turns checkpoint storage into the difference between resuming within minutes and repeating hours or days of lost computation. Whether the job recovers cleanly depends on three storage questions: how quickly the most recent checkpoint was saved, where its shards reside, and whether they can be read back intact. Because checkpoints are also the heaviest write workload in the hierarchy, the storage architecture must minimize ${T_{\text{write}}}$, the time the training pipeline pauses to save a snapshot, while stating when that snapshot becomes durable and visible for restore. The save interval is an input to this storage analysis; selecting it from failure rates and recovery costs is a separate reliability decision derived in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-young-daly|The Young-Daly checkpoint interval]]**.

Under the resumable mixed-precision Adam contract of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.02 The Fuel Line#^sec-storage-fuel-line|section 4.1]], the 175B parameter model’s 2,450 GB checkpoint comprises 350 GB of FP16 model weights, 700 GB of FP32 master weights, and 1,400 GB for the two FP32 Adam moments, while learning-rate-scheduler state, random-number-generator state, and the data-loader cursor add negligible bytes and gradients are recomputed after restore. When a save triggers, every participating worker process, called a rank, writes its assigned shard at once, producing the checkpoint storm introduced in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.03 How ML Workloads Invert Storage Assumptions#^sec-storage-workload-inversion|section 4.2]].

Keeping that burst tractable requires the write-once rule, under which a coordinated save writes each unique byte once, whatever the parallel layout. In the running layout of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^tbl-hbm-memory-budget|table 3]], each node holds the 1/8 of a replica’s state that belongs to its pipeline stage, and all thirty-two replicas hold identical copies of it. A coordinated save therefore assigns each replica a disjoint 1/32 of every stage slice, so each of the 256 nodes writes about 1/256 of the checkpoint. The third ZeRO stage (ZeRO-3), which partitions the weights as well, makes that even split the natural one, because every rank already owns a distinct slice.

Breaking the write-once rule is a real risk even in the running layout, where a save in which every replica writes the full state it holds would multiply the checkpoint bytes by the replica count. Its cost is clearest in a deliberately extreme thought experiment, a smaller model whose complete resumable state is written once per GPU of the book’s reference cluster.

**Definition 4.5: Checkpoint storm**

***Checkpoint storm*** is a burst of synchronized network and storage traffic that occurs when all nodes in an ML training fleet save model state simultaneously.

1.  **Significance**: When each replica writes its own full copy, the naive storm takes ${T_{\text{write}}} = {N_{\text{DP}}} \times \text{per-replica state} / {\text{BW}_{\text{ingest}}}$, where ${N_{\text{DP}}}$ is the number of replicas writing at once and ${\text{BW}_{\text{ingest}}}$ is the aggregate rate at which the target storage tier absorbs writes. A coordinated save that writes each unique byte once takes $\text{unique state} / {\text{BW}_{\text{ingest}}}$. Under the chapter’s checkpoint contract, a 70B-parameter model, smaller than the 175B running example, stores 140 GB of FP16 weights, 280 GB of FP32 master weights, and 560 GB of Adam moments. With vanilla data parallelism across 1,024 replicas (one per GPU of the book’s reference cluster, rather than the chapter’s 256-node fleet), naively writing that complete state from every replica generates 1003.5 TB of simultaneous traffic. No 80 GB device can hold a 0.98 TB replica, so the case is a bound on write volume rather than a deployable layout. At 100 GB/s of aggregate storage ingest bandwidth, the write takes roughly 10,035.2 seconds, or over 167.3 minutes of training stall. A coordinated checkpoint protocol writes one logical copy. Replicated data parallelism can select one writer; ZeRO-3 instead spreads that copy across the ranks, each writing the slice it owns. In the sharded example the total is roughly 0.98 TB, bringing ${T_{\text{write}}}$ down to roughly 9.8 seconds. Gradients do not appear in either total because recovery recomputes them.
2.  **Distinction**: Unlike general I/O contention (which is stochastic and unpredictable), a checkpoint storm is synchronous and periodic: every node writes at the same moment because the training orchestrator triggers checkpoint after a fixed step count. Its predictability makes it both more damaging (all nodes compete simultaneously) and more tractable (it can be prevented by design through staggered scheduling or asynchronous serialization).
3.  **Common pitfall**: A frequent misconception is that checkpointing every 100 steps is “low overhead” whatever the save protocol. Under the naive protocol at 70B scale, if each training step takes 10 seconds and a checkpoint storm takes 10,035.2 seconds, checkpointing every 100 steps means spending most of the run on checkpoint I/O rather than useful training.

The severity of a checkpoint storm depends on two factors: the per-node shard size, determined by the model size and the sharding strategy, and the throughput of the first write tier, typically local NVMe. A concrete 175B example shows why the local-write phase, rather than the durable copy to the parallel file system, governs the exposed training pause.

**Napkin Math 4.7: Tiered checkpoint staging**

**Problem**: Assume sustained bandwidth, local drives that write as fast as their rated sequential read speed, no snapshot-copy, serialization, or coordination overhead, and no interference from background copies. The resulting times are bandwidth lower bounds. A 256-node cluster saves a 175B-parameter checkpoint every 10 minutes. Each checkpoint totals 2,450 GB. Writing each unique byte once and spreading the bytes evenly across nodes, each node saves roughly 9.6 GB.

1.  **Per-node write to local NVMe** (4 drives at 7 GB/s each = 28 GB/s): 9.6 GB $\div$ 28 GB/s $\approx$ 0.34 seconds.
2.  **Async copy to PFS**: 256 $\times$ 9.6 GB $\approx$ 2.4 TB total. If the PFS provides 1 TB/s aggregate, the storm completes in roughly 2.4 seconds.
3.  **Per-node PFS bandwidth**: If all 256 write simultaneously, each gets 1000 GB/s $\div$ 256 = 3.9 GB/s.
4.  **Training pause**: At least 0.34 seconds for the local NVMe write under this model. The PFS copy overlaps with the next training iteration.
5.  **Overhead lower bound**: 0.34 seconds pause every 600 seconds $\approx$ 0.06 percent training time lost to checkpointing.

**Systems insight**: Under these 1 TB/s aggregate-PFS assumptions, tiered staging reduces checkpoint overhead from about a 2.4 seconds PFS-direct write to a sub-second local write. The training pause can end at the local snapshot boundary before durable publication, but actual pause includes snapshot creation, serialization, and coordination in addition to this byte-transfer lower bound.

A PFS-direct save of a few seconds every 10 minutes costs well under 1 percent of the run, which can make tiered staging look unnecessary for the running example. The checkpoint-dominance argument of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass#^sec-storage-complete-path|section 4.5.1]] concerns bytes moved, not this pause, and the notebook’s few-second save holds only while its assumptions do. The job has the whole 1 TB/s file system to itself; shared among the ten concurrent jobs of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier3-pfs|section 4.3.6]], it receives a tenth of the bandwidth, the same save takes ten times as long, and its burst slows the other jobs’ reads. Realized ingest also falls below the rated aggregate once serialization, metadata operations, and stragglers enter. The save interval shrinks as the fleet grows, because a larger fleet fails more often and the reliability analysis of **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-young-daly|The Young-Daly checkpoint interval]]** then calls for more frequent saves, and a larger model scales every save with it.

Tiered staging insulates the training loop from that shared-tier contention by splitting the save into two phases. In the first phase, as calculated in notebook [4.7](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#nbk-data-storage-checkpoint-storm), each of the 256 nodes writes its 9.6 GB share of the 2,450 GB checkpoint across 4 local NVMe drives at 28 GB/s, establishing a byte-transfer lower bound on ${T_{\text{write}}}$ of roughly 0.34 seconds before snapshot-copy, serialization, and coordination overhead. Once every required local shard has completed and the captured state is no longer being modified, the training pipeline can resume.

In the second phase, a background process asynchronously copies the local checkpoint to the parallel file system for durability. The copy can overlap training, but it still competes for memory, network, and storage service and must drain before repeated saves create an unbounded backlog. The two phases therefore land differently in the Fleet Law (**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^eq-fleet-law|equation 1.3]]**). The local write is a pause that every rank takes at the same step boundary, and training resumes only when the slowest writer has finished its shard. That is the shape of a barrier rather than of a transfer between workers, a coordination (${C}_3$) cost, so the pause adds to the synchronization term ${T_{\text{sync}}}({N})$ of each saving step, the term that already carries barrier and straggler waiting. The background copy belongs to no step’s critical path. While it stays hidden and drains before the next save, it adds nothing to the step time; it reappears only as interference, in ${T_{\text{comm}}}({N})$ when it shares links with collectives or in exposed input wait when it slows shared-storage reads. Rate-limiting the copy, or staggering its start across nodes, spreads the burst over time and keeps that interference low, at the price of a later durability boundary.

If a node fails before its copy completes, the new generation may lose a required shard. Replication to peer nodes’ NVMe drives can protect against a single-node loss, provided replicas occupy independent failure domains. Waiting for that replication extends the pause beyond the local-only calculation. A design that resumes earlier must retain the previous committed generation until the new one reaches its declared durability boundary.

Durability alone does not make a distributed checkpoint restorable. Each rank writes its checksummed shard under an immutable generation identifier. Only after every shard has persisted does a coordinator publish a manifest naming the complete shard set. That commit uses an atomic primitive of the target tier, an operation that takes effect completely or not at all. A file system offers a create or rename. An object store offers a conditional create, which succeeds only if the name is still unused, or a versioned pointer, a small record that names the current generation. A crash can then leave garbage to collect but never an incomplete generation that appears valid.

↪ The commit rule behind this ordering, a two-phase commit over the shard set, and the consistency of the cut that a manifest names are developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-reliability-checkpoint-coordination-patterns-f670|Checkpoint coordination patterns]]**.

The exposed pause and the durability boundary therefore fall at different moments, as the four concurrent lanes of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^fig-storage-checkpoint-staging|figure 8]] align them. Training pauses only during the local NVMe shard write (${t}_0$ to ${t}_1$), resuming on live state while the parallel file system absorbs the asynchronous copy (${t}_1$ to ${t}_2$) and the coordinator validates checksums before publishing the manifest last (${t}_3$).

### Synchronous and Asynchronous Checkpoint Writes

^sec-storage-distributed-checkpoint

In the two-phase timeline of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^fig-storage-checkpoint-staging|figure 8]], the first phase is still synchronous with respect to local flash. Across 256 nodes, every node must write and acknowledge its shard of the same completed training step before the completion barrier releases the next iteration, with the commit rules that make that cut consistent developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-reliability-checkpoint-coordination-patterns-f670|Checkpoint coordination patterns]]**. The slowest local writer therefore sets the exposed pause from ${t}_0$ to ${t}_1$.

Asynchronous checkpointing shrinks even that local-flash pause by staging the snapshot in host DRAM first. Nodes coordinate the training step to capture, copy each accelerator-resident shard into a dedicated pinned host-memory buffer, and resume training immediately while a background thread writes the buffer to local NVMe. The snapshot buffer must remain immutable until the background write finishes; separate live-state buffers allow training to advance without changing the captured generation. If a node fails during the asynchronous write, its local shard may be incomplete. The job must wait for the required writes or peer replication before declaring this generation durable, even if training has already resumed.

The choice between synchronous and asynchronous checkpointing depends on the pause budget and save frequency. A 1-second pause costs the running example about 22 percent of one modeled 4.64-second step, or 0.17 percent of the 10-minute save interval. At that cadence a synchronous save is cheap; the overhead grows with pause length times save frequency, so the case for asynchronous checkpointing strengthens as saves come more often or pauses grow longer. Asynchronous checkpointing reduces exposed write time when snapshot buffers and background bandwidth are available, but its buffer capacity, contention, and durability delay also enter the decision.

Checkpoint formats implement the write-once rule of the checkpoint storm as rank-sharded saves, as in DeepSpeed’s zero-redundancy checkpointing and PyTorch’s Distributed Checkpoint ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-pytorchDistributedCheckpointDocs|PyTorch Contributors 2026]]). The sharding is what keeps the pause short. Had one node saved the full 2,450 GB itself, its 28 GB/s local stripe would need more than a minute rather than the 0.34 seconds of an even shard. Making each individual save fast, however, creates a cumulative capacity problem once thousands of snapshots accumulate over a multi-week run.

### Checkpoint Retention and Restore

^sec-storage-checkpoint-retention

Checkpointing a 175B-parameter model every 10 minutes over a 30-day training window generates roughly 4,320 snapshots of 2,450 GB each, totaling approximately 10.6 PB, a volume that would crowd a shared parallel file system if retained in full. The retention policy this run adopts keeps the three most recent checkpoints on the parallel file system for fast recovery, copies every 100th checkpoint and the final checkpoint to object storage for long-term auditability, and deletes the rest. This policy reduces the parallel file system checkpoint footprint from 10.6 PB to roughly 7.35 TB (three live full checkpoints) while preserving 43 periodic historical snapshots in object storage, plus the final checkpoint when it does not coincide with that schedule, for posttraining analysis.

Incremental checkpointing offers a further optimization for reducing ${T_{\text{write}}}$. Rather than saving the entire training state every time, an incremental checkpoint records changed state relative to a declared base or preceding generation. The delta must include changed optimizer and continuation state as well as parameters. For models where a large fraction of parameters are frozen (such as fine-tuning scenarios where only the last few layers are updated), incremental checkpoints can be orders of magnitude smaller than full checkpoints. Restoring a generation requires its base and every intervening delta, so smaller saves add recovery work and dependencies. Periodic full checkpoints bound that chain, and the retention policy must preserve each dependency until no retained generation requires it. A shorter pause matters only if the checkpoint can be read back; the costlier failure is a checkpoint that was written but never verified as restorable.

**War Story 4.1: The backup that had not been restored (2017)**

**Context**: On January 31, 2017, a GitLab.com site reliability engineer working a database replication incident accidentally wiped the primary PostgreSQL data directory ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-gitlab2017postmortem|GitLab 2017]]).

**Mechanism**: All five layered backup paths failed simultaneously: S3 dumps were silently empty due to a version mismatch, Azure disk snapshots were disabled, replication was broken, LVM snapshots were six hours stale, and WAL archiving was unimplemented.

**Impact**: Six hours of production database writes, user comments, and repository metadata were permanently lost, requiring an 18-hour emergency restoration from a staging snapshot.

**Fix**: GitLab instituted automated daily backup restoration testing, unified PostgreSQL versioning across environments, and implemented automated WAL archiving to S3.

**Systems lesson**: Storage reliability is a restore property, not a backup property. A checkpoint, replica, or dump only counts if the team regularly proves that it can be located, validated, and restored under incident conditions. ML systems face the same vulnerability. A model checkpoint written to object storage or a snapshot of a feature store (the system that stores model input features) is useless if silent version mismatches or missing restore tests prevent resuming a multi-day training run after node preemption.

For the running job, a restore test reads a retained generation’s shards back, checks them against its manifest, and resumes training from them.

↪ The restore drill, which tests this recovery path before an incident relies on it, is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.07 Software Faults#^sec-ft-software-fault-detection-prevention|Software fault detection and prevention]]**.

The total data moved through the hierarchy is approximately 10.6 PB of checkpoint data plus 6 TB per 1 epoch of training data reads. For a single-epoch language model training run, checkpoint I/O dominates data loading I/O by a factor of over 1,764.

Checkpoints therefore set the run’s write budget, while the far smaller training corpus carries a different obligation. Because training quality depends on the exact samples delivered at every step, each byte of that corpus must remain traceable to the source version and transformation code that produced it.
