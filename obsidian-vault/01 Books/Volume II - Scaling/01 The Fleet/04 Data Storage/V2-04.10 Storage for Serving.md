# V2-04.10 Storage for Serving

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-inference

Where full-corpus training streams datasets for weeks and writes checkpoints in bursts, the weight-resident serving baseline of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.03 How ML Workloads Invert Storage Assumptions#^sec-storage-workload-inversion|section 4.2]] reads the model weights once when a replica starts or recovers and then answers requests out of HBM, before KV-cache offload and retrieval indexes add serving-time I/O of their own.

That startup read makes model loading latency, often called cold-start time, the primary storage metric for weight-resident inference: the duration required to load a model from storage into the accelerator’s HBM. For the 175B parameter language model, the weights alone occupy 350 GB in FP16 format; loading that footprint sequentially from a single high-performance NVMe drive at 14 GB/s takes 25 seconds, an unacceptable delay for a user-facing application. Loading from a shared PFS at a per-node rate of 4 GB/s takes 87.5 seconds. Reading from object storage at 1 GB/s stretches the delay to 5.8 minutes.

To reduce cold-start time, the model is sharded and loaded in parallel. If the 350 GB model is striped across 8 NVMe drives, each loading a 43.75 GB shard at 7 GB/s, the total load time drops to roughly 6.2 seconds. When using tensor parallelism across 8 GPUs, each GPU loads only its 43.75 GB shard. If the weights already sit in host DRAM, each GPU’s own PCIe link could move its shard in about 0.7 seconds, but the 8 transfers share the node’s 200 GB/s of host-memory bandwidth, so the full load takes about 1.8 seconds. For the most latency-sensitive applications, organizations maintain warm replicas: one or more copies of the model weights kept preloaded in host DRAM, ready for that host-memory-bound transfer. This trades DRAM capacity for a load of about 1.8 seconds instead of the 6.2 seconds striped NVMe read.

↪ How cold-start time limits autoscaling, and how warm pools trade idle capacity for scaling response, is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.14 Autoscaling and Capacity Control#^sec-inference-scale-autoscaling-capacity-control|Autoscaling and Capacity Control]]**.

These load times describe one replica. The model rollout previewed in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.03 How ML Workloads Invert Storage Assumptions#^sec-storage-workload-inversion|section 4.2]] asks all 100 replicas to load a new version at once, 35 TB of weights in one burst. If every replica reads from object storage at the 1 GB/s single-client rate, the fleet asks the store for 100 GB/s. A store whose aggregate service matches that figure, the 100 GB/s of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^tbl-storage-hierarchy-merged|table 2]], finishes the rollout in about 5.8 minutes, no slower than one replica’s cold start; any smaller aggregate share stretches the rollout in proportion. Reading from the 1 TB/s parallel file system instead would take about 35 seconds, but only by claiming the whole file system and starving every training job that shares it, the read-side mirror of a checkpoint storm. Serving fleets therefore stage the new version on local NVMe at a paced rate ahead of the traffic switch, roll the update across groups of replicas so that the old version keeps serving, or let replicas that have finished loading supply the rest.

During autoregressive generation, the server keeps a per-request record of the attention keys and values produced by earlier tokens so it can generate the next token without recomputing the entire prefix. This record, called the key-value cache (KV cache), grows with sequence length and can consume significant HBM. For long sequences (128K tokens or more), KV cache offloading to host DRAM or NVMe extends the effective context window at the cost of increased latency per generated token, because cache blocks must be moved back into HBM before attention can use them. The storage lesson is that inference maintains an active working set rather than presenting solely a model-loading demand. When serving must also retrieve external context to ground that generation, the storage pipeline faces an entirely different access pattern: low-latency random queries into high-dimensional vector indexes.

↪ KV-cache growth and the HBM capacity wall it creates for serving are developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-kv-cache-wall|The KV cache wall and memory capacity]]**.

### Retrieval Indexes

^sec-data-storage-retrieval-infrastructure

An inference request that needs supporting documents cannot wait for a sequential scan of the training corpus. A retrieval system first converts documents into vectors that represent semantic meaning, then finds nearby vectors and returns their source documents as context. The same storage analysis still applies, but the unit of demand becomes a query and its index accesses, and the deadline becomes the serving latency budget. With a graph-based approximate nearest-neighbor (ANN) index, which links each vector to a few of its neighbors, the storage system traverses a high-dimensional vector graph instead of streaming sequential blobs via formats such as TFRecord or Parquet. Other index families shift the storage demand elsewhere. Exact flat search scans every stored vector and is bound by scan bandwidth. Inverted-file (IVF) partitioning groups vectors into clusters and probes only the few nearest the query, so each query reads a small part of the index. Product quantization (PQ) compresses each vector into short codes so that more of the index fits in memory, at some cost in accuracy.

**Systems Perspective 4.4: The IOPS bottleneck in high-dimensional search**

For graph-based ANN, this architectural pattern shifts the primary storage bottleneck from sequential read bandwidth to random-access IOPS. The search traverses a high-dimensional graph to find approximate nearest neighbors across billions of embeddings. Its performance is governed by the trade-off among recall, latency, and capacity, where recall is the fraction of the true nearest neighbors that the approximate search returns. Raising recall requires traversing a larger portion of the index, driving up IOPS and latency. The arithmetic of a disk-resident traversal shows why IOPS, not bytes, sets the limit. Each hop that misses DRAM costs one dependent SSD read of roughly 100 μs ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^tbl-storage-hierarchy-merged|table 2]]), and the next hop cannot start until that read returns, so ten such hops already spend a millisecond of the serving budget in storage alone. Throughput is bounded separately. A drive whose 4 KB random reads run near 0.5 GB/s ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.03 How ML Workloads Invert Storage Assumptions#^sec-storage-workload-inversion|section 4.2]]) completes on the order of $10^5$ such reads per second, and every concurrent query draws on that same budget, while each read moves only a few kilobytes.

How often a hop misses DRAM depends on how much of the index fits there. A 1,536-dimension embedding in FP32 (4 bytes per value) consumes approximately 6.1 KB, so a billion-document corpus requires roughly 6.1 TB before graph adjacency lists. At 50 to 100 bytes per node, those lists add 50 GB to 100 GB, for about 6.2 TB at the high end. Production indexes can be larger once identifiers, graph levels, allocator overhead, deleted-entry slack, and replication are included. In-memory hierarchical navigable small world graph indexes make graph navigation fast when the index fits in DRAM ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-malkov2020hnsw|Malkov and Yashunin 2020]]). Disk-backed graph indexes such as DiskANN trade DRAM footprint against SSD traversal while targeting high recall and low query latency ([[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.15 Source References#^ref-subramanya2019diskann|Subramanya et al. 2019]]).

Graph-based retrieval therefore spends storage budget on index levels that keep random traversal inside the serving latency service-level objective. A disk-backed graph is economical only if the extra SSD accesses do not erase the quality gain from searching a larger corpus. The same hierarchy now supports bulk model loading, request-scoped KV state, and retrieval, each with a distinct service-rate contract. Every design so far also assumes today’s six tiers, and the boundaries between those tiers are themselves moving.

    3.  The node’s $4\text{ GB/s}$ share of the parallel file system, for about 87.5 seconds.
    4.  A single object-storage client at $1\text{ GB/s}$, for about 5.8 minutes.

    3.  The object store finishes in about 35 seconds because each replica reads only its own share of the weights.
    4.  Rollout time is independent of the source tier because each replica’s load is limited by its own PCIe link.
