# V2-04.09 Storage Economics

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04 Data Storage|V2-04 Data Storage]]

^sec-storage-economics

Checkpoints, training shards, and the lineage that binds them now each have a place in the hierarchy, and every placement carries a price set by the tier that holds the bytes and by how often they cross a billing boundary. ML storage economics is therefore not simply about choosing the cheapest capacity tier; the design objective is to minimize total cost of data delivery, which combines recurring storage charges, cross-boundary transfer fees, request and retrieval fees, and the opportunity cost of idle accelerators.

Applied to one 100 TB training dataset, the per-gigabyte rates quoted earlier for each tier diverge by orders of magnitude: object storage (S3 Standard) costs \$24,000 per year, provisioned local NVMe costs \$120,000 per year, and archival storage (such as Glacier) drops to \$4,800 per year. By contrast, hypothetically provisioning the same capacity as GPU memory at \$15/GB would require \$1,500,000 in upfront acquisition cost alone, before factoring in amortization, power, or server housing.

The 5× cost difference between local NVMe and object storage motivates placing data on the least expensive tier that meets its delivery and recovery requirements. Device technology contributes to the cost gradient. HBM uses 3D-stacked silicon with through-silicon vias, and accelerator-adjacent capacity is constrained by packaging and node design. Shared storage pools capacity across clients but introduces network and service dependencies. The cost comparison must include those dependencies rather than infer the cheapest usable path from capacity price alone.

![[90 Assets/Volume II/04 Data Storage/Vol2 Data Storage Margin 003 0b9e0ccfcf.svg]]

*One cost bar: a short gray one-year storage segment labeled 24K dollars beside a long violet ten-epoch egress segment labeled 90K dollars.*

*Repeated cross-boundary egress, not storage, dominates cloud cost.*

Storage cost, however, is only part of the equation. Data transfer costs can dominate, especially in cloud environments. When compute runs in a different region (a provider’s separate group of data centers) or cloud from the bucket, as assumed here, reading the 100 TB dataset from object storage to compute instances incurs a transfer charge of \$9,000, called an egress fee because it bills bytes leaving the region or cloud. For multi-epoch training that reads the dataset 10 times, the egress cost alone reaches \$90,000, more than the annual storage cost. This inversion, where *reading* data costs more than *storing* it, drives the architecture decision to cache data on local NVMe rather than streaming from object storage each epoch.

The economic analysis changes further when accounting for the opportunity cost of accelerator idle time. The book’s reference cluster of 1,024 GPUs, half the chapter’s running cluster, at \$2/GPU-hour costs \$49,152 per day. If input stalls reduce its compute-active fraction from 90 percent to 70 percent, the lost compute time is valued at \$9,830 per day. Over a 30 days training run, this amounts to \$294,912. That value sets a budget for evaluating a storage upgrade, but the recoverable benefit depends on how much exposed wait the upgrade removes. Capacity that does not relieve the limiting stage yields no corresponding compute-time saving.

**Systems Perspective 4.3: The storage cost iceberg**

The visible cost of storage (\$/GB/month) is the tip of the iceberg. Below the surface lie costs that often exceed the storage cost itself:

- **Egress fees**: The ten-epoch egress charge of \$90,000 computed above already exceeds a year of storage.
- **Request fees**: Object storage charges per-request fees. S3 Standard GET requests cost about \$0.0004 per 1,000 requests, so a dataset of 100M individual files, read once, costs about \$40 in GET request fees before data transfer or retrieval charges, even though the storage cost is \$2,000/month.
- **Idle accelerator cost**: The \$9,830 per day of lost compute computed above dwarfs any storage saving.
- **Retrieval fees**: Archive storage charges retrieval fees (\$0.02/GB for Glacier) in addition to egress. Restoring a 100 TB dataset from Glacier costs \$2,000 in retrieval fees plus \$9,000 in egress.

The economically rational strategy often invests more in storage (local NVMe caching, parallel file system capacity) to reduce transfer costs and prevent accelerator stalls.

The cost iceberg reveals that raw storage capacity can account for less than half of the total expenditure; replication, metadata operations, API calls, and cross-region transfers can collectively dominate the bill at scale. Among those hidden line items, egress is the one that often flips the architecture decision. Unlike capacity charges, which scale with the volume of data stored, egress charges scale with the volume of data read, and ML training reads the full dataset on every epoch.

**Napkin Math 4.9: The cost of egress**

**Problem**: A team trains a vision model on a 50 TB image dataset stored in S3. Training runs for 20 epochs. The decision is whether to stream from S3 each epoch or stage to local NVMe.

**Option A**: Stream from S3

- Storage: 50 TB $\times$ \$0.02/GB/month $\times$ 12 months = \$12,000/year
- Egress: 50 TB $\times$ 20 epochs $\times$ \$0.09/GB = \$90,000 per training run
- Total for 4 training runs/year: \$12,000 + \$360,000 = \$372,000/year

**Option B**: Stage to local NVMe

- Storage (S3 source of truth): \$12,000/year
- NVMe capacity (50 TB across cluster): 50 TB $\times$ \$0.10/GB/month $\times$ 12 = \$60,000/year
- Egress (stage once per training run): 50 TB $\times$ 4 runs $\times$ \$0.09/GB = \$18,000/year
- Total: \$12,000 + \$60,000 + \$18,000 = \$90,000/year

**Systems insight**: Local NVMe caching saves \$282,000/year at 20 epochs per run, enough to fund 9 additional H100 GPUs at list price. Including the \$60,000/year provisioned NVMe cost and the once-per-run staging egress, the break-even point is just over 4 epochs per run; by the fifth epoch, local caching is cheaper than streaming from S3 every epoch.

The notebook turns the iceberg into a decision rule: the cheapest storage tier is not always the cheapest delivery path. Object storage can remain the source of truth, but repeated reads make egress, request overhead, and idle-accelerator cost part of the storage design. Multi-epoch vision training may justify staging on local NVMe by the fifth epoch, while single-epoch language-model pretraining may leave the corpus in object storage and optimize the streaming path instead. The running example stages anyway, although it reads its corpus only once, because egress is not what decides it. Each node’s share of the shards fits easily on local NVMe, the staging copy happens once before the clock starts, and local reads keep object-store latency tails out of every training step. When compute and bucket share a region, transfer fees largely disappear and the same comparison turns on request charges, latency, and idle accelerators instead. The architecture is therefore chosen from access pattern, read count, and latency sensitivity rather than from \$/GB/month alone.

The cost analysis extends to the parallel file system tier, which occupies a middle ground between NVMe and object storage in both performance and price. A parallel file system capable of delivering 1 TB/s aggregate bandwidth requires roughly 100 OSS nodes, each with multiple NVMe drives and high-bandwidth network connections. Because the throughput target, not the stored capacity, sets that server count, a bandwidth-sized system costs far more than its stored bytes alone would suggest. This expense is justified only if the alternative, streaming from object storage and paying egress fees, is even more expensive, or if the latency requirements of checkpoint writes cannot be met by object storage alone. The break-even analysis depends on the organization’s workload mix. A team running a single long training job may find that staging data on local NVMe and bypassing the parallel file system entirely is the cheapest option, while a team running many concurrent short jobs benefits from the shared namespace that a parallel file system provides.

The decision to build vs. buy storage infrastructure hinges on the trade-off between the high capital expenditure of an on-premises parallel file system and the recurring operational expenditure of cloud object storage. A 1-petabyte Lustre deployment, sized for capacity rather than for the 1 TB/s target above, costs roughly \$3–5 million in hardware, plus an additional \$500,000 per year in operational overhead for power, cooling, and engineering support. Storing 1 PB in a cloud object store at \$0.02/GB/month costs \$240,000 per year for storage alone. Egress fees for accessing the data, however, dominate the total cost. Reading that petabyte at 10 reads/year adds \$900,000 in data transfer fees.

Under these assumptions, annual cloud delivery costs \$1,140,000; after subtracting \$500,000 of on-premises operations, the net savings are \$640,000 per year. The resulting hardware break-even is roughly 4.7–7.8 years, and a payback within two years would require a hotter workload with many more full-dataset reads per year, lower capital expense, or non-egress drivers such as checkpoint latency and shared-namespace requirements. For the running example, the 6 TB serialized corpus is much smaller than 1 PB, so the local-storage case is driven more by latency, repeated experiments, and checkpoint staging than by one-year egress savings alone.

### Tiering Strategies

^sec-storage-tiering

The cost structure laid out above turns tiering into a placement policy: keep data only as close to the accelerator as its access frequency and latency requirement justify. A tiering strategy encodes that policy across the hierarchy. Its hot, warm, cold, and archive labels name placement roles for a dataset rather than devices, and they follow the scope brackets of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^fig-storage-pyramid|figure 1]]. HBM stays outside these labels, because it holds the live batch and model state rather than a stored dataset.

The hot tier is the node-local pair of local NVMe and host DRAM, which holds the data the running job consumes. Earlier sections called local NVMe a warm cache because it sits in front of shared storage; in this placement vocabulary the same drives belong to the hot tier. This tier is provisioned per node, so data that multiple jobs or teams need simultaneously cannot live here alone. That shared-access requirement justifies the warm tier, the parallel file system, whose shared namespace and strong consistency serve datasets used by multiple jobs or teams, shared checkpoints for fault recovery, and model artifacts under active development. The cold tier is object storage, the canonical repository where datasets are authored and versioned and the durable backup for checkpoints staged through the parallel file system. Data that must be retained for compliance or reproducibility but is not expected to be accessed during normal operations drops to the archive tier (Glacier or equivalent).

Lifecycle policies of the kind shown for the archive tier in [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier5-archive|section 4.3.8]] automate both directions of movement. They promote data from cold to warm when a job requests it, demote it when no job has read it for a configured period, and transition cold data to archive after 90 to 365 days since last access.

In the running example, the 3 TB source corpus and 6 TB serialized shards live permanently in object storage (cold tier), and the staging and cleanup lifecycle of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.06 GPUDirect Storage and the CPU Data-Copy Bypass#^sec-storage-complete-path|section 4.5.1]] moves each node’s shards through local NVMe (hot tier) for the life of the job. The parallel file system holds only the job’s recent checkpoints, which the retention policy of [[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpoint-retention|section 4.6.2]] governs.

The economic benefit of automated tiering compounds over time. An organization retaining 50 training datasets of 10 TB each would need 500 TB of parallel file system capacity if all data were left in place. If ten datasets are active concurrently and the other forty can be demoted after their jobs finish, automated tiering reduces the dataset capacity required on the parallel file system to 100 TB, saving \$144,000 per year at the parallel file system’s per-TB rate. These savings are invisible in any single experiment but substantial when accumulated across the fleet. Tiering and staging thus settle where training data and checkpoints live and what each placement costs; serving reuses the same hierarchy for a different objective, governed by the time to bring a model into HBM and the latency of serving-time state rather than epoch throughput.

What does the economic analysis reveal about streaming vs. staging?

    1.  Streaming directly from object storage every epoch is cheaper because local NVMe drives add unnecessary provisioned storage overhead.
    2.  Egress fees are negligible compared to monthly storage costs, making tier selection purely a matter of operational convenience.
    3.  Staging data once to local NVMe per run saves roughly $\$282,000$ per year compared to streaming from object storage every epoch, breaking even after just 5 epochs per run.
    4.  The team should migrate the dataset to cold tape archive to eliminate both egress fees and provisioned storage costs.

In a 1,000-GPU cluster where compute time is billed at $\$2.00$ per GPU-hour, an undersized storage system introduces an additional 20 percentage points of input stalls (reducing the active compute fraction from $90\%$ to $70\%$). An enterprise evaluates building an on-premises 1 PB parallel file system ($\$3\text{M to } \$5\text{M}$ capex plus $\$500\text{k/year}$ opex) versus storing the 1 PB corpus in cloud object storage ($\$240\text{k/year}$ storage) and paying $\$0.09/\text{GB}$ egress fees for 10 full-dataset reads per year ($\$900\text{k/year}$ egress). What is the realistic financial payback horizon for building the on-premises system under these parameters?

    3.  Exactly 20 years, because on-premises operational overhead exceeds all cloud storage and egress fees combined.
    4.  There is no payback horizon because cloud object storage is perpetually free for research and training workloads.
