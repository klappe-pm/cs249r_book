# V2-02.05 Sustained Compute and Precision

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02 Compute Infrastructure|V2-02 Compute Infrastructure]]

^sec-compute-tensor-cores

A fleet sized from advertised matrix throughput can miss its training deadline when operations cannot use the advertised precision or keep the matrix units of [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.03 The Accelerator#^sec-compute-matrix-units|section 2.2.5]] busy. Sizing a fleet therefore requires knowing both which matrix operations are eligible for the advertised rate and how much throughput those operations sustain across the complete workload.

Tensor Core precision support widened with each generation traced in [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.03 The Accelerator#^sec-compute-infrastructure-evolution-gpu-architectures-566b|section 2.2.3]], from FP16 on Volta to FP8 on Hopper, because neural network training and inference tolerate lower numerical precision than was once assumed. Transformer Engine recipes and FP8 autocast decide which supported operations run in FP8, recording tensor ranges and applying scale factors so values fit the format, but they do not establish that a layer is numerically safe at that precision. Precision policy therefore remains a software configuration and validation decision, which **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-fp8|FP8 for distributed training]]** develops for training.

The relationship between numerical precision and hardware throughput matters for infrastructure planning because it directly affects how much useful work each accelerator can perform per second. Lower precision representations use fewer bits per number, which has two compounding benefits: more numbers fit in the same HBM capacity (reducing memory pressure), and the arithmetic units can process more operations per cycle (increasing throughput). Within a format’s bits, the exponent sets the range of values it can represent and the mantissa sets how finely it resolves them. Each format an H100-class accelerator supports unlocks a different dense peak rate and plays a usual role in training or inference ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.05 Sustained Compute and Precision#^tbl-precision-throughput|table 8]]).

| **Format**     | **Bits** | **Exponent** | **Mantissa** | **H100 dense peak** |         **Typical use**          |
|:---------------|:--------:|:------------:|:------------:|:-------------------:|:--------------------------------:|
| **FP32**       |    32    |      8       |      23      |     ~67 TFLOP/s     | Master weights, loss computation |
| **TF32**       |    19    |      8       |      10      |    494.5 TFLOP/s    |    Training (NVIDIA default)     |
| **BF16**       |    16    |      8       |      7       |     989 TFLOP/s     |      Training, fine-tuning       |
| **FP16**       |    16    |      5       |      10      |     989 TFLOP/s     |    Training with loss scaling    |
| **FP8 (E4M3)** |    8     |      4       |      3       |    1,979 TFLOP/s    |      Forward pass, weights       |
| **FP8 (E5M2)** |    8     |      5       |      2       |    1,979 TFLOP/s    |     Backward pass, gradients     |
| **INT8**       |    8     |     N/A      |     N/A      |     1,979 TOPS      |    Post-training quantization    |

Table 8: **Precision Formats and Hardware Throughput on H100**: The table uses dense peak throughput where Tensor Core support exists; structured sparsity can roughly double several of these advertised peaks. The choice of precision affects both the training dynamics (convergence, numerical stability) and the infrastructure requirements (memory capacity, bandwidth utilization). TF32 preserves the FP32 exponent width but reduces mantissa precision so Tensor Cores can accelerate common FP32 training workloads.

^tbl-precision-throughput

For training, many workloads use the standard mixed-precision recipe, which decouples storage from arithmetic precision by keeping FP32 master weights while the forward and backward passes run in BF16 or FP16 at full Tensor Core throughput. FP16 training relies on loss scaling, which multiplies the loss so that small gradients stay within FP16’s narrow range. The node memory examples in [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-node-memory|section 2.5.3]] assume retained FP16 gradients; implementations that retain a full FP32 accumulation buffer must add that buffer to their peak budget. The FP8 recipes described earlier extend the same decoupling one step further, running eligible matrix operations in eight bits while the master weights stay in FP32.

↪ The byte widths of each format and the per-parameter memory of mixed-precision training are collected for reference in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-training-memory|Numeric Precision and Training Memory]]**.

The practical implication for fleet design is that peak TFLOP/s specifications are precision-dependent. The H100 delivers 989 TFLOP/s in FP16 but twice that (1,979 TFLOP/s) in FP8. FP8 therefore doubles the advertised arithmetic ceiling for supported operations on the same hardware. The complete training run gains less when communication, memory traffic, or higher-precision operations remain on the critical path. Precision engineering is therefore a primary optimization lever for infrastructure planners, alongside its effect on model accuracy.

Approaching peak throughput requires pipeline balance. Operand staging and reuse must supply the arithmetic units at the rate the operation requires. Kernel fusion and tiled attention such as FlashAttention improve that balance by keeping intermediate values on chip instead of making separate HBM round-trips, mechanisms that **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-kernel-levers|Kernel-Level Levers]]** collects for reference. For our 175B model, the fleet-level gain depends on how much step time the affected kernels consume. A faster attention kernel shortens the step only in proportion to attention’s share of it, the same Amdahl accounting that bounds every partial speedup.

### Peak Vs. Sustained Throughput

^sec-compute-infrastructure-peak-vs-sustained-throughput-625a

A training run budgeted for 1,000 GPU-hours from datasheet TFLOP/s will consume 2,500 GPU-hours in practice when the workload sustains only 40 percent of peak throughput. Infrastructure planning therefore separates *peak* throughput (the maximum rate for the vendor-specified operation and precision) from *sustained* throughput (what the complete workload delivers). Peak TFLOP/s assumes that eligible arithmetic units remain fed under the stated sparsity, precision, and clock conditions; it does not include memory stalls, ineligible operations, communication, or software overhead. Sustained fractions therefore vary with model shape, batch size, precision, implementation, and scale. The gap arises from several sources, each representing a different physical or software limitation.

Memory stalls occur when the Tensor Cores complete their current tile multiplication before the next tile has been loaded from HBM. Even with the H100’s 3.35 TB/s HBM bandwidth, the Tensor Cores can consume data faster than HBM can deliver it for certain matrix dimensions, creating idle cycles while the arithmetic units wait for data.

Dependency stalls arise when one operation must complete before the next can begin, leaving some processing elements idle. In a Transformer layer, the attention computation must complete before the feed-forward network can begin, and the feed-forward computation must complete before the next layer’s attention can start. These sequential dependencies create brief periods where some hardware resources are unused, even within one accelerator. When the model is split into sequential stages on different accelerators (pipeline parallelism), the same dependencies become pipeline bubbles, idle slots in which a whole stage waits for its predecessor. Splitting each batch into microbatches reduces the waste by feeding later microbatches into stages that would otherwise wait. The term pipeline bubble refers only to this cross-device case, whose scheduling **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training#^sec-distributed-training-systems|Distributed Training]]** develops. At the infrastructure level, the lesson is that peak throughput assumes every unit stays busy, while real training includes dependency gaps that lower sustained utilization.

AllReduce operations used in tensor parallelism and gradient synchronization used in data parallelism can likewise delay computations that depend on their results; even when communication overlaps computation on separate streams, operations that depend on the collective output cannot proceed until the transfer completes. Kernel submission, memory allocation, and framework control also consume time, and when each kernel completes in microseconds, launch overhead of a similar size becomes a comparable share of the step that only a host-and-device execution trace can separate from slow arithmetic or memory access. Achieving high sustained utilization is therefore largely a matter of minimizing the time Tensor Cores spend idle between operations, which is why kernel fusion and specialized kernel libraries such as FlashAttention and the Transformer Engine exist.

The last source of the gap is the device itself, and no kernel change removes it. Device variation, sometimes called the silicon lottery, means that nominally identical accelerators sustain different clocks. Clock behavior also depends on the configured power limit, temperature, and workload, so a slow participant should not be diagnosed from its product label or frequency alone. In synchronous training, a participant that finishes dependent work late delays its whole process group, the set of processes that run a collective together. One device sustaining a clock about 2.5 percent below its peers can slow every synchronous step it joins by up to that fraction, because the other participants wait for it at each collective. Fleet management systems therefore track per-device sustained throughput and can move persistent underperformers to pools, such as inference serving, where they do not gate a synchronized group. Profiling must determine whether local arithmetic, memory, communication, or a power limit caused that delay before changing placement or replacing hardware.

Capacity planning must use a measured or conservatively modeled sustained rate, not the peak specification. A run estimated at 1,000 GPU-hours from peak FLOP/s requires $1/{\eta_{\text{hw}}}$ times that estimate when its measured utilization fraction is ${\eta_{\text{hw}}}$. Infrastructure teams track model FLOPs utilization (MFU), the useful model computation per second divided by the selected hardware peak, as the standard measure of ${\eta_{\text{hw}}}$, but comparisons remain meaningful only when model-FLOP conventions, precision, hardware peak, and system scale match.

↪ MFU as the measure of program goodput, one factor of fleet-level ML goodput, is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.03 ML Goodput#^sec-performance-engineering-fleet-efficiency-metric-dff4|Program goodput and its measure]]**.

The accelerator’s physics establish a concrete problem. Our 175B model requires 350 GB of memory for its weights alone in FP16, and Adam-style training state raises the requirement to multiple terabytes once optimizer moments, gradients, and activations are included. A single H100 provides 80 GB of HBM. No single accelerator can hold this model, an instance of the memory capacity gap (principle [[01 Books/Volume II - Scaling/01 The Fleet/V2 Fleet Principles#^pri-memory-capacity-gap|2]]), in which frontier memory requirements outgrow single-accelerator HBM. The system must expand to the next physical level: the node.

**Self-Check: Question**

1.  An H100 advertises twice the dense arithmetic rate in FP8 that it advertises in FP16. A team sizes a training run’s GPU-hours by assuming the full FP8 rate. Which statement best describes the planning error?

    1.  FP8 halves the bytes per weight, so memory-bound phases also run exactly twice as fast and the plan is correct.
    2.  The FP8 rating is a ceiling for eligible matrix operations; ineligible operations, memory stalls, communication, and the need to validate the precision policy keep the sustained rate below it, so the plan must use a measured sustained rate.
    3.  FP8 Tensor Core rates apply only to inference, so a training plan must use the FP32 rate instead.
    4.  FP8 runs slower than FP16 on Tensor Cores because of scaling overhead, so the plan overestimates the time.

2.  A training run is estimated at 1,000 GPU-hours from peak FLOP/s. Profiling a representative window shows a model FLOPs utilization (MFU) of 0.4. How many GPU-hours should the plan budget, and what must match before this MFU can be compared with another team’s figure?

3.  True or False: In synchronous training, an accelerator that sustains a clock about 2.5 percent below its peers costs the job at most 2.5 percent of that one device’s throughput.

4.  The standard mixed-precision recipe runs the forward and backward passes in BF16 or FP16 but keeps a full-precision FP32 copy of the parameters, called the \_\_\_\_ weights, so that updates much smaller than a weight are not lost to FP16 rounding.
