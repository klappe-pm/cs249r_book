# V2-02.04 The Memory Wall

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02 Compute Infrastructure|V2-02 Compute Infrastructure]]

^sec-compute-memory-wall

Single-request inference on our 175B running model has a latency floor set by memory delivery. Its weights occupy 350 GB in FP16. In dense autoregressive decode at batch size 1, each generated token uses all of those weights, whose footprint far exceeds on-chip storage, so every token must stream them in from memory. Suppose, hypothetically, that one H100 could hold them. Streaming the whole 350 GB through that device’s HBM at about 3.35 TB/s takes over 100 ms per token, long enough to be a perceptible pause between generated words. No real H100 holds the model, so the figure is a floor on bandwidth demand rather than a prediction of deployed latency, but it shows that the memory wall is a delay a user can notice, not an abstract architectural ratio.

That floor reflects a structural divergence. Transistor scaling has multiplied logic throughput far faster than off-chip interconnects can supply operands. In phases with little data reuse, where each fetched byte feeds few operations, specialized matrix units therefore routinely spend more time waiting for bytes than executing math. This divergence is the memory wall ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-wulf1995|Wulf and McKee 1995]]). In those phases the weight and activation streams of large neural networks make memory bandwidth rather than peak compute the governing constraint.

↪ The diagnostic table that maps memory-bound, compute-bound, and latency-bound symptoms to the optimizations that help is developed in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-bottleneck-diagnostic|Bottleneck diagnostic]]**.

Three levers ease that constraint. Sharding spreads the weights across more memory paths, so each path streams fewer bytes. Quantization shrinks the bytes themselves. Reuse lets each fetched byte feed more arithmetic, which batching and on-chip tiling make possible. The Roofline Model, recapped for one machine in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-roofline|The roofline bound]]**, tests whether the resulting data supply can feed the arithmetic units. Its ridge point, peak arithmetic divided by memory bandwidth, is the number of operations a kernel must perform per byte fetched before arithmetic rather than memory becomes the limit. The ridge point recurs throughout the analysis below, and [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^sec-compute-roofline|section 2.3.2]] evaluates it for the H100. Where each architecture places its bytes sets how much bandwidth those levers can draw on ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^fig-accelerator-memory-tier-map|figure 6]]), because moving the active working set closer to arithmetic increases available bandwidth while reducing the capacity that can reside there.

The dotted arrow marks the design trade-off: moving data closer to compute raises bandwidth but reduces capacity.

^fig-accelerator-memory-tier-map

Accelerators do not line up along a single performance axis; they fall into structural clusters according to where each architecture places its bytes ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^fig-accelerator-memory-tier-map|figure 6]]). Edge devices in the lower band keep memory cheap and compact, but their bandwidth remains constrained, and the devices of Archetype C (Federated MobileNet) sit in that corner. The binding limit on each such device, however, is not its place on this memory map but the power envelope that bounds compute. A phone-class device sustains only 2 W to 3 W, while one H100’s thermal envelope is about 233× larger. A federated fleet therefore grows by adding devices rather than by moving up the memory tiers, and at fleet scale, as **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.07 The Fleet Stack and the Lighthouse Archetypes#^sec-vol2-introduction-archetypes|Three systems archetypes]]** noted, communication and which devices participate in each round limit progress as well.

↪ The power, thermal, and memory limits of phone-class edge devices are developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^sec-edge-intelligence-design-constraints-c776|Design Constraints]]**.

Within the data center tiers, HBM moves memory onto the accelerator package, buying enough capacity and enough bandwidth for active model state. Local-SRAM designs push the working set still closer to arithmetic, buying extraordinary bandwidth at the cost of much smaller resident capacity. Of the two, HBM is the next engineering response, because it is the highest-bandwidth tier that can hold tens to hundreds of gigabytes next to the compute die, although it is not the fastest memory in the system.

### HBM and the Memory Wall

^sec-compute-hbm

An H100 can execute 1,979 TFLOP/s of low-precision matrix arithmetic, but the batch-1 weight-streaming example for our 175B model supplies too little reuse to approach that peak. In a bandwidth-floor model its arithmetic units would use well under 1 percent of the matrix peak while the weights stream in. The limiting resource is the speed of *delivery* relative to *multiplication*. Once weights fit through sharding or compression, the serving path must still deliver the active shards at the required rate. Additional arithmetic capacity alone does not raise a binding bandwidth ceiling. HBM increases that data supply within the package.[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.15 Footnotes#^fn2|²]]

HBM is the bottom on-package tier of the accelerator memory hierarchy, beneath the register file, the L1 and shared memory (SRAM),[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.15 Footnotes#^fn3|³]] and the L2 cache. Aggregate bandwidth falls from hundreds of TB/s at the registers to the 3.35 TB/s of the H100’s 80 GB of HBM3, while capacity grows in the opposite direction.

↪ The single-accelerator memory hierarchy, from registers and shared memory through HBM to host memory, is collected for reference in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-memory-hierarchy|Accelerator Memory Hierarchy]]**.

The bandwidth gap between registers and HBM is approximately 100$\times$, but that ratio alone does not specify stalled time. Utilization depends on **arithmetic intensity**, the floating-point operations performed per byte moved from memory (FLOP/byte), which tiling raises by staging matrix blocks on chip so that each fetched operand feeds many multiply-accumulate operations. **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-kernel-levers|Kernel-Level Levers]]** collects tiling with the other kernel-level levers for reference.

↪ Arithmetic intensity and the boundary it draws between memory-bound and compute-bound work are collected for reference in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-arithmetic-intensity-boundary|Arithmetic Intensity Boundary]]**.

**Definition 2.2: HBM**

***HBM*** is a 3D-stacked DRAM architecture used by ML accelerators, with through-silicon vias (TSVs) connecting memory dies vertically within each stack and a wide interface across the package interposer connecting the stack to the processor.

1.  **Significance**: HBM3 in the H100 delivers approximately 3.35 TB/s of memory bandwidth (roughly 17× DDR5’s ~200 GB/s) at roughly 4 pJ/bit for an HBM2-class stack ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-oconnor2017fine|O’Connor et al. 2017]]) vs. roughly 20 pJ/bit for off-package DRAM ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-horowitz2014|Horowitz 2014]]). This bandwidth sets the ${\text{BW}}$ term of the single-machine iron law given in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-iron-law-mapping|Iron Law Mapping]]**. The H100’s FP16 ridge point is approximately $989\,\text{TFLOP/s} / 3.35\,\text{TB/s} \approx 295$ FLOP/byte, so any operator with arithmetic intensity below 295 FLOP/byte (for example, single-request decode, which performs two FLOPs for every two-byte FP16 weight it reads) remains memory-bound even with HBM.
2.  **Distinction**: Unlike socketed DDR memory, which communicates across centimeters of printed circuit board (PCB) trace, an HBM stack sits beside the processor on the package. Its micrometer-scale vertical connections can be 1,000$\times$ shorter than board traces, but the complete processor-to-memory path also crosses the interposer. The wide, short on-package interface raises bandwidth without relying on a proportionate increase in per-pin signaling rate.
3.  **Common pitfall**: A frequent misconception is that HBM solves the memory wall. HBM moves the wall rather than eliminating it. From the V100 (900 GB/s with 125 TFLOP/s FP16) to the H100 (3.35 TB/s with 989 TFLOP/s FP16), peak arithmetic $({R_{\text{peak}}})$ grew faster than HBM bandwidth.

Traditional DDR memory connects to the processor through pins on the edge of a printed circuit board. Each DIMM communicates over a 64-bit bus, and even with multiple channels (8 channels is typical for a high-end server CPU), a modern server tops out at roughly 200 GB/s of aggregate memory bandwidth.

The physical distance from the DIMM slot to the processor die is measured in centimeters, and every centimeter of copper trace introduces capacitance, signal attenuation, and energy loss. At DDR5 data rates (4,800–6,400 MT/s per pin), the signal conditioning circuits must compensate for that degradation, consuming substantial power per bit transferred. Increasing the data rate on these long traces requires progressively more power for signal conditioning, creating a diminishing-returns curve that DDR5 is already approaching.

HBM sidesteps that board-level degradation through 2.5D integration ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^fig-hbm-architecture|figure 7]]). Instead of driving signals horizontally across centimeters of motherboard trace over a narrow 64-bit bus, it stacks DRAM dies vertically and places the stack beside the processor on a silicon interposer.

![[90 Assets/Volume II/02 Compute Infrastructure/Hbm Architecture c3bd7fc73d.svg]]

Figure 7: **HBM 3D-Stacked Architecture**: Left: high-bandwidth memory stacks DRAM dies on a base logic die, links them vertically with through-silicon vias (TSVs), and places the stack on a silicon interposer beside the GPU die, so each stack reaches the GPU over a 1,024-bit interface only millimeters long. Right: DDR5 instead sits on a DIMM across the motherboard, reached over a 64-bit channel through centimeters of board trace. The wider, shorter path raises bandwidth and lowers energy per bit, but HBM bandwidth and capacity remain finite, so the memory wall moves rather than disappears.

^fig-hbm-architecture

The vertical stacking changes how bandwidth scales. Rather than pushing signals faster through long copper traces (the DDR approach, which has diminishing returns), HBM multiplies the number of parallel signal paths. A single HBM stack bonds 8–12 DRAM dies, threading thousands of through-silicon vias (TSVs),[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.15 Footnotes#^fn4|⁴]] copper pillars etched through each die, to form a 1024-bit-wide interface per stack, compared to 64 bits for a DDR5 channel. This 16$\times$ wider interface is the main source of HBM’s bandwidth advantage; HBM need not exceed DDR’s per-pin signaling rate. The processor and HBM stacks share a package and communicate across the silicon interposer, shortening the electrical path relative to socketed DIMMs. This packaging primarily improves bandwidth and energy per transferred bit; it does not by itself imply that complete HBM load latency is only a few nanoseconds.

The shorter path also lowers transfer energy per bit by roughly 5$\times$, from approximately 20 pJ/bit for off-package DRAM ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-horowitz2014|Horowitz 2014]]) to about 4 pJ/bit for HBM2 ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-oconnor2017fine|O’Connor et al. 2017]]), because the short interconnects present less capacitance and need less driving current. The same reduced loading lets the 1024-bit interface run at moderate per-pin rates instead of the high-power signaling that long board traces require. Propagation delay shrinks by only a fraction of a nanosecond, small next to the DRAM array and controller delays that dominate access latency, so HBM’s advantage lies in bandwidth and energy per bit rather than in latency. Modern accelerators therefore widen the memory interface across an interposer rather than driving off-package pins faster; set side by side in [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^tbl-hbm-comparison|table 5]], the bandwidth, interface-width, and energy differences all trace to placement and width rather than to faster signaling.

^tbl-hbm-comparison

This bandwidth advantage comes at a price. HBM costs approximately \$10–\$15 per GB, compared to roughly \$3 per GB for DDR5 server memory. For an H100 with 80 GB of HBM3, the memory alone represents approximately \$800–\$1,200 of the accelerator’s manufacturing cost. For a B200 with 180 GB of HBM3e, the memory cost rises to \$1,800–\$2,700 per accelerator, making HBM one of the most expensive components in the system.

Packaging adds manufacturing stages beyond fabricating the memory dies. The stacking process includes thinning, alignment, bonding, and vertical interconnection, so usable stack yield depends on both the dies and their assembly. Those yields compound, because a 12-high HBM3e stack is usable only if every die and every bonding step succeeds, so even small per-step losses multiply into a complete-stack yield below that of a single DRAM die. The silicon interposer must also accommodate the processor and multiple HBM stacks. With each stack occupying roughly 100 mm², an illustrative large package that pairs a reticle-sized processor with several stacks needs an interposer exceeding 1,000 mm². Testing, repair provisions, and assembly yield all affect cost; die count alone does not determine how many complete stacks remain usable. Supply is a constraint as well as cost. HBM production is concentrated among a few manufacturers whose stacking steps need specialized equipment, so memory availability can pace accelerator delivery, a lead-time risk that **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.10 Fleet Economics and Utilization#^sec-ml-operations-scale-procurement|Capacity lead time as operational risk]]** plans for.

For our 175B model, this cost-capacity trade-off explains why accelerators typically offer 80 GB to 192 GB of HBM while the host server provides 512 GB to 2 TB of DDR. The *fast* memory holds state touched every step (weight shards, activations, gradients, and usually the sharded optimizer state), while the *cheap* memory holds staging buffers, data loading queues, and colder state that capacity pressure forces out, such as offloaded optimizer shards.

The boundary between what resides in HBM and what resides in DDR is a design parameter for training frameworks, and managing it is one of the jobs of ZeRO (Zero Redundancy Optimizer) sharding and offloading strategies. Sharding divides optimizer, gradient, and parameter state across workers; offloading places colder state in host DRAM or Non-Volatile Memory Express (NVMe) when HBM capacity is the binding limit. Getting this boundary wrong in either direction is costly. Placing too much data in HBM wastes expensive capacity, while placing too much in DDR creates bandwidth stalls that idle the arithmetic units.

**Lighthouse 2.1: Archetype B (DLRM at Scale): The capacity wall**

Archetype A (GPT-4/Llama-3) has so far exposed the bandwidth side of the memory wall. Archetype B (DLRM at Scale) exposes the capacity side, the boundary between fast and cheap memory just examined. An embedding table of 10 TB or more cannot fit into the 80 GB HBM of a single H100, nor can it fit into the aggregate HBM of a single 8-GPU node (640 GB nameplate, about 687 GB in decimal bytes). Capacity alone requires at least 15 such nodes before accounting for replication, hot-table headroom, and bandwidth balance. Sharding makes lookup routing and result exchange part of the request path. An AllToAll exchange sends distinct portions to different participants; its traffic depends on the batch and placement. Clearing the capacity limit therefore creates a second question about bandwidth and latency.

#### Energy Cost of Data Movement

^sec-compute-infrastructure-energy-cost-data-movement-3cd1

Data movement also dominates energy. At 3.97 pJ per bit, the HBM2 access energy that O’Connor et al. estimate ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-oconnor2017fine|2017]]), reading one 16-bit operand costs about 64 pJ. One FP16 multiply-accumulate costs roughly 1.5 pJ at the 45 nm node ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-horowitz2014|Horowitz 2014]]). The raw fetch therefore costs about 42× the arithmetic it feeds, until tiling and reuse spread it across many operations. From off-package DRAM at about 20 pJ per bit, the same fetch costs roughly 5× more again. That ratio is why accelerators devote so much silicon to reuse, and why the levers that cut bytes, such as quantization and fusion, improve power efficiency as well as speed. **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.03 The Physics of Data Movement#^sec-communication-collective-operations-physics-data-movement|The Physics of Data Movement]]** extends the per-boundary accounting to collective communication, and **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/15 Sustainable AI/V2-15.05 Energy Measurement and Modeling#^sec-sustainable-ai-arithmetic-intensity-energy-roofline-6d13-roofline-6d13|Arithmetic intensity and energy roofline]]** turns these per-byte costs into an energy roofline.

#### HBM Generations and the Scaling Boundary

^sec-compute-infrastructure-hbm-generations-scaling-frontier-5827

HBM has grown alongside model sizes, but far more slowly than parameter counts, which is why capacity pressure keeps pushing models across devices. Each generation increases the number of stacked dies, the signaling rate per pin, and the total capacity per stack. The projected HBM4 generation in [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^tbl-hbm-evolution|table 6]] marks the scaling boundary, doubling the interface width from 1024 to 2048 bits for the first time since HBM’s introduction, because pin-rate increases alone no longer sustain the required bandwidth growth. The wider bus also needs more interposer area for routing, one reason accelerator packages have grown as bandwidth targets rise.

The generations in [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^tbl-hbm-evolution|table 6]] move both capacity and bandwidth for our running example, and the step to HBM3e matters most. Using decimal bytes consistently, an A100 with 85.9 GB of HBM2e holds 24.5 percent of our 175B model’s FP16 weights. An H100 with 85.9 GB of HBM3 holds the same fraction while delivering the data 64 percent faster. A B200 with 193.3 GB of HBM3e raises the resident share to 55.2 percent at about 8 TB/s. Because even HBM3e leaves nearly half the model outside a single package, multiple accelerators are still needed in a node ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-node|section 2.5]]).

Quantization changes the capacity story for inference. Storing weights in INT8 or INT4 halves or quarters the footprint, and [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.09 Accelerator Selection for Fleet Workloads#^sec-compute-infrastructure-precision-throughput-tradeoffs-49a5|section 2.8.1]] works through how many accelerators the running model then needs. The capacity constraints that drive multi-accelerator nodes for training, where FP16 or BF16 precision is typically required, are substantially relaxed for inference, where INT8 or INT4 quantization is often acceptable, which is one reason training and inference infrastructure have different optimal configurations.

Aggregate package bandwidth scales with the number of HBM stacks that can sit beside the processor die on the silicon interposer. The H100 has 5 HBM3 stacks, each providing approximately 670 GB/s, for a total of 3.35 TB/s aggregate bandwidth. A B200-class Blackwell GPU package uses 8 HBM3e stacks for an aggregate of about 8 TB/s. The number of stacks is constrained by the interposer area available for HBM placement. Each HBM stack occupies approximately 100 mm² of interposer area, and the total interposer must accommodate both the processor die(s) and all HBM stacks. Larger interposers allow more HBM stacks (and therefore higher bandwidth and capacity) but are more expensive and harder to manufacture.

The interposer area constraint creates a concrete design tension. Making the processor die larger (more Tensor Cores, more SMs) leaves less interposer area for HBM stacks, potentially reducing bandwidth. Making the processor die smaller (fewer Tensor Cores) frees interposer area for more HBM but reduces peak compute throughput. The optimal balance depends on the target workload’s position relative to the ridge point. Compute-bound workloads, whose arithmetic intensity sits above it, benefit from a larger processor die (more Tensor Cores). Bandwidth-bound workloads below it benefit from more HBM stacks, so a workload’s arithmetic intensity predicts which side of the balance it falls on before any silicon is committed.

#### Memory Bandwidth and Token Latency

^sec-compute-infrastructure-memory-bandwidth-token-latency-1b38

Adding or upgrading HBM stacks raises both memory *capacity* (how many gigabytes the package can store) and memory *bandwidth* (how many terabytes per second it can deliver), which answer two separate procurement questions. Capacity determines whether a model’s weights *fit*, with headroom for the remaining live state; bandwidth limits how fast the model can *run* when data movement sets the critical path. Dense autoregressive decode at batch size 1 isolates the second question because each weight serves only one token before the next weight load. The next three calculations step down from the running model to Llama-3 70B. Its FP16 weights span two H100s rather than the running model’s five, and the H200 comparison that follows needs a model whose serving behavior a real memory upgrade can change; the arithmetic carries over to the 175B model by scaling the bytes.

**Napkin Math 2.1: The physics of token latency**

**Problem**: A weight-only model of batch-1 decode for Llama-3 70B uses 141.2 GB of FP16 weights. To isolate the two resource demands, assume hypothetical capacity sufficient to hold them while retaining one H100-equivalent compute rate and HBM path. Which term gives the larger time estimate: arithmetic or weight transfer?

1.  **Compute time**: Each token requires $2 \times 70.6 \times 10^9 = 1.41 \times 10^{11}$ floating-point operations. At 989 TFLOP/s of FP16/BF16 Tensor Core peak throughput, the arithmetic takes ${T_{\text{compute}}} \approx \text{\textbf{0.14}}\text{ ms}$.
2.  **Memory time**: Loading 141.2 GB of weights from HBM at 3.35 TB/s takes ${T_{\text{memory}}} \approx \text{\textbf{42.1}}\text{ ms}$.

**Systems insight**: The memory term accounts for 99.7 percent of the sum of these two idealized times. That ratio identifies a bandwidth-dominated estimate; it is not a measurement of cycles spent idle. Raising compute throughput alone barely changes this estimate. A faster memory path reduces the weight-transfer floor, while actual token latency also includes the other memory traffic, communication, and execution costs omitted here.

Holding that weight load fixed and changing only the memory system shows how directly each HBM generation moves the floor. For the same 70.6B FP16 model, with 141 GB of weights, the single-path streaming floor is roughly 141 GB/2.04 TB/s = 69.2 ms at A100-class bandwidth. At H100-class bandwidth (the notebook’s memory term) it is 141 GB/3.35 TB/s = 42.1 ms, and at B200-class bandwidth it is 141 GB/8 TB/s = 17.7 ms. The floor falls nearly in proportion to each bandwidth gain. As in the notebook, each case isolates one accelerator-equivalent HBM path even though the full FP16 model does not fit on one A100 or H100. These bounds screen memory bandwidth against a latency target; whether token latency improves by the same ratio depends on the other work on the request’s critical path.

The same floor at trillion-parameter scale shows the limit of bandwidth gains alone, even at the projected 12–16 TB/s of an HBM4-class package. A dense 1T-parameter model requires roughly 2 TB of FP16 weight storage. Streaming those weights through one B200-class path at about 8 TB/s gives 2000 GB/8 TB/s = 250 ms for one batch-1 weight load. At the assumed 16 TB/s, that floor becomes roughly 125 ms. Neither path has been shown to hold the full model, and even the faster floor limits a single path to about eight tokens per second for one request. A responsive trillion-parameter service must therefore split its weights across many memory paths, shrink them with reduced precision, or both; which combination depends on the latency target and the quality the reduced precision preserves. The cleanest test of how far a memory upgrade moves real latency compares two accelerators that differ only in their memory system.

**Napkin Math 2.2: The memory wall: H100 vs. H200**

Comparing the NVIDIA H100 against the H200 isolates a memory-system upgrade for large language models (LLMs). While both chips share the same compute cores (same peak TFLOP/s), the H200 provides 1.4× higher memory bandwidth and 1.8× more HBM capacity.

This comparison uses a Llama 3 model with 70.6B parameters, sequence length 2,048, and batch size 1. Both cases retain FP16 weights and the hypothetical capacity convention of notebook [2.1](https://mlsysbook.ai/vol2/02_compute_infrastructure/02_compute_infrastructure.html#nbk-token-latency): each streams the complete payload through one accelerator-equivalent HBM path, even though it cannot fit on one H100. The comparison isolates path latency rather than establishing two feasible single-device deployments.

The reported speedup comes from a serving-latency model whose inter-token latency adds two terms to the weight-streaming time, reads of the key-value cache that holds attention state for the request’s earlier tokens and a fixed per-layer overhead for launching kernels, so it is not a raw bandwidth ratio alone. The weight-only estimate provides a comparison. Its memory term accounts for 99.7 percent of the summed compute and transfer times, so reducing that term suggests a gain near the HBM bandwidth ratio, 4.8 TB/s $\div$ 3.35 TB/s $\approx$ 1.4×.

**Systems insight**: For the modeled configuration, the latency model predicts an H200 speedup of 1.4× over the H100 despite equal peak arithmetic throughput. Its agreement with the bandwidth ratio follows from the dominant memory term of that model, so a measured pair of systems would be the test. Changing batch size, context length, or partitioning requires evaluating the new configuration; the estimate does not establish one bottleneck for all autoregressive models.

The modeled memory-time share, 99.7 percent in this example, indicates the memory-boundedness of this workload under the stated assumptions. A workload this memory-bound gains almost nothing from more TFLOP/s and nearly proportionally from more TB/s, which is what the H200 comparison predicts, so bandwidth per dollar rather than peak arithmetic is the useful procurement metric for this regime. A measured execution timeline is still needed to determine how much transfer overlaps computation and which delays remain exposed, which keeps a hardware-screening calculation separate from a performance forecast. For training workloads, reusing weights across more tokens can instead shift the constraint toward arithmetic throughput; the Roofline Model tests the compute and bandwidth ceilings for the actual operation and batch shape before either specification becomes a procurement metric.

### Roofline Model

^sec-compute-roofline

The token latency calculation in notebook [2.1](https://mlsysbook.ai/vol2/02_compute_infrastructure/02_compute_infrastructure.html#nbk-token-latency) makes memory bandwidth the relevant procurement metric for the batch-1 workload. The Roofline Model of Williams, Waterman, and Patterson ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-williams2009|Williams et al. 2009]]) tests whether that diagnosis survives a change in batch shape, precision, or accelerator by relating the workload’s arithmetic intensity to the candidate accelerator’s compute and bandwidth ceilings.

For an H100 (989 TFLOP/s FP16, 3.35 TB/s HBM), the ridge point is about 295 FLOP/byte. Most LLM inference operators fall well below this threshold, which is why the roofline remains the first diagnostic tool for identifying whether more compute or more bandwidth will improve performance. The quantity that places a workload on the plot is the arithmetic intensity introduced with tiling above, written ${I}$ in FLOP/byte.

↪ Placing measured kernels on the roofline by arithmetic intensity is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.07 Program Goodput#^sec-performance-engineering-roofline|Drilling into the step]]**.

![[90 Assets/Volume II/02 Compute Infrastructure/Compute Infrastructure Decode Roofline 91af58cda5.svg]]

*A roofline: a blue memory-bound slope rising to an orange compute-bound ceiling at the ridge point. A workload dot sits low on the blue slope, far left of the ridge, marking LLM decode as deeply memory bound.*

*Decode sits deep in the memory-bound regime, far below the ridge.*

As the single-machine recap in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-roofline|The roofline bound]]** derives, the Roofline Model expresses the maximum achievable performance of a workload as the lesser of two ceilings:

$$
\text{Achievable FLOP/s} = \min\left({R_{\text{peak}}},\ {\text{BW}} \times {I}\right) \tag{1}
$$

^eq-compute-roofline

In [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^eq-compute-roofline|equation 1]], below the ridge point the sloped bandwidth ceiling, which grows with ${I}$, is the lower one; above it the flat compute roof binds, and a measured kernel can sit below either.

**Definition 2.3: Ridge point**

***Ridge point*** is the ML accelerator arithmetic intensity where the memory bandwidth ceiling meets the compute ceiling $({I_{\text{ridge}}} = \frac{{R_{\text{peak}}}}{{\text{BW}}})$.

1.  **Significance**: It is the accelerator’s efficiency threshold. Below the ridge point, bandwidth supplies the lower modeled ceiling $({\text{BW}})$; above it, arithmetic supplies the lower ceiling $({R_{\text{peak}}})$.
2.  **Distinction**: Unlike peak FLOP/s, which describes only the horizontal ceiling, the ridge point describes the balance between arithmetic and memory delivery in the architecture. A rising ridge point over hardware generations indicates that compute is growing faster than bandwidth, making utilization harder.
3.  **Common pitfall**: A frequent misconception is that an accelerator has a single ridge point. In reality, it varies by precision. Because ${R_{\text{peak}}}$ is higher for INT8 than FP32 while ${\text{BW}}$ is constant, the ridge point for INT8 is much higher, requiring more data reuse to saturate the hardware.

Machine learning workloads land in different regions of the roofline plot depending on the operation and the batch configuration, not on the model family. Single-request autoregressive decode streams the full weight tensor (two bytes per parameter in FP16) from HBM to perform two floating-point operations per parameter, an arithmetic intensity of about 1 FLOP/byte, far below the H100’s ridge point of 295 FLOP/byte. The token-latency calculation in notebook [2.1](https://mlsysbook.ai/vol2/02_compute_infrastructure/02_compute_infrastructure.html#nbk-token-latency) showed that the arithmetic finishes in microseconds while the weight movement takes milliseconds. Every other regime in [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^tbl-roofline-workloads|table 7]], including prefill, the phase that processes a request’s prompt before decode begins, comes from reusing each byte fetched from HBM across more operations. Decode also reads the key-value (KV) cache, the stored attention keys and values of earlier tokens, and because each request has its own cache, batching does not amortize that traffic.

| **Workload phase**                   | **Source of reuse**                                   |           **Idealized intensity**            | **What moves it**                                   |
|:-------------------------------------|:------------------------------------------------------|:--------------------------------------------:|:----------------------------------------------------|
| **Decode, batch 1**                  | None; each weight serves one token                    |                 1 FLOP/byte                  | Batching requests, lower-precision weights          |
| **Decode, batch 32**                 | Each weight read serves every request in the batch    |                 32 FLOP/byte                 | Batch size, until key-value cache traffic dominates |
| **Prefill, 512-token prompt**        | Each weight read serves every prompt token            |                512 FLOP/byte                 | Prompt length and batch size                        |
| **Convolution training** (ResNet-50) | Filters reused across spatial positions and the batch |                200 FLOP/byte                 | Channel depth, tensor layout, operator fusion       |
| **LLM training, 2048 local tokens**  | Each weight read serves every token on the device     |               2,048 FLOP/byte                | Local microbatch size and sequence length           |
| **Attention**                        | Keys and values reused across queries                 | Shape-dependent, on either side of the ridge | Sequence length, head dimension, SRAM tiling        |

Table 7: **Roofline Placement by Workload Phase**: Language-model intensities count only weight traffic at the HBM level, the same idealization used for [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^fig-roofline-landscape|figure 8]], against an H100 FP16 ridge point of 295 FLOP/byte; the convolution value is a representative scenario figure rather than a derived count. Attention is not plotted in the figure because its placement depends on shape. Measured placement must also count activation, key-value cache, and optimizer traffic.

^tbl-roofline-workloads

The table’s intensities are idealized reuse counts that classify an execution phase and batch shape, not a model family, and tensor layout, fusion, precision, and cache residency move the measured point. Which kernel-level change then helps, more reuse and fewer bytes below the ridge or a cheaper operation above it, is a diagnosis that **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.07 Program Goodput#^sec-performance-engineering-roofline|Drilling into the step]]** develops.

A measured workload point below its roofline ceiling needs further diagnosis. Dependencies, insufficient parallel work, irregular accesses, synchronization, and power limits can all prevent a kernel from approaching that ceiling. The gap identifies a question for profiling; it does not establish that software optimization can recover the entire difference.

Whole phases spread even wider than individual operators. The idealized intensities of decode and training differ by 2,048×, which is why the same hardware shows widely different utilization across them. Batch-1 decode sits near 1 FLOP/byte, far left of the ridge and deeply bound by memory bandwidth, while large-batch training near 2,048 FLOP/byte crosses the ridge and reaches the compute roof ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^fig-roofline-landscape|figure 8]]). The training point assumes that 2048 tokens on one accelerator share each weight read, the local reuse that a large global batch alone does not guarantee, so it counts tokens rather than sequences and local rather than global batch. It is a contrast case, not a universal intensity for training. Actual placement requires counting bytes at the memory level being modeled and accounting for tensor shapes, fusion, and reuse.

![[90 Assets/Volume II/02 Compute Infrastructure/Cell 48 Output 1 84eb0c79dd.png]]

Figure 8: **The H100 Roofline Landscape**: Attainable FP16 throughput is the lower of two ceilings, the memory-bandwidth slope (blue) and the compute roof (orange), which meet at the dashed ridge point. Each dot places a representative workload by its arithmetic intensity; workloads left of the ridge stay capped by bandwidth however much compute the chip offers, and only those to its right can approach peak throughput.

^fig-roofline-landscape

The table’s batching rows can be turned into a utilization bound. For inference serving, batching multiple requests together moves the workload point rightward on the plot, because each weight read is multiplied against more activations. Under the weight-traffic-only bound, batch-1 decode on an H100 can use at most 0.34 percent of the FP16 peak. At batch size 64, each weight read from HBM serves every request in the batch, the intensity rises to 64 FLOP/byte, and the bound climbs to about 22 percent of peak, a 64× gain that still leaves the workload below the ridge. The linear growth holds only in this approximation; key-value cache traffic, which batching does not amortize, activation traffic, and capacity limits lower both figures in practice. The gain has a cost. Waiting to assemble a batch can introduce queuing latency, although a serving policy can instead dispatch a smaller batch when a latency deadline approaches. Serving systems must carefully balance this trade-off between throughput (larger batches, higher utilization) and latency (smaller batches, faster response per request).

For fleet procurement, the roofline is a screening test rather than a throughput forecast. It rules out upgrades that raise a nonbinding ceiling, while the gap below the relevant ceiling identifies work still needed in software or communication. For the running model, the two ends of the landscape give opposite hardware answers. Memory capacity and bandwidth screen out infeasible accelerator choices, while for the candidates that remain, fleet sizing also needs a sustained compute rate at a precision the workload can use, within the node’s memory budget, the interconnect, and the facility power envelope.

**Example 2.2: Roofline analysis: Training vs. inference**

**Scenario**: An engineering team evaluates hardware choices for serving (decode batch size 1) vs. training (batch size 2048) a 175B parameter model on an H100 GPU (ridge point 295.2 FLOP/byte).

**Diagnosis**: The weight-traffic model gives single-token decode arithmetic intensity ${I}=$ 1 FLOP/byte $\ll$ 295.2 FLOP/byte, bounding throughput to 0.34 percent of the selected peak FLOP/s. The assumed training reuse raises intensity to ${I}=$ 2,048 FLOP/byte $\gg$ 295.2 FLOP/byte, making arithmetic the lower roofline ceiling. This placement identifies the relevant bound without establishing achieved throughput.

**Systems lesson**: Hardware selection starts with the phase’s arithmetic intensity and memory footprint. The modeled training phase benefits from arithmetic capacity, while batch-1 decode benefits from bandwidth. Sustained throughput at the required quality and latency determines whether either advantage justifies its cost.
