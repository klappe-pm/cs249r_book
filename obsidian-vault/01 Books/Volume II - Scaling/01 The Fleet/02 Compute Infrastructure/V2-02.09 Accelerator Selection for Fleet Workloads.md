# V2-02.09 Accelerator Selection for Fleet Workloads

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02 Compute Infrastructure|V2-02 Compute Infrastructure]]

^sec-compute-accelerator-selection

The same H100 that sustains 30–50 percent of peak throughput during well-tuned large-batch training may achieve less than 5 percent utilization during single-request inference, because the binding constraint shifts from arithmetic to memory bandwidth. An accelerator’s compute throughput, memory bandwidth, memory capacity, and power consumption are meaningful only in relation to the workload running on it. Selecting the right accelerator therefore requires mapping each workload archetype to its position on the roofline plot and identifying which physical resource dominates its performance.

For the 175B running example, large local matrix operations can place substantial training work above the roofline ridge point. Arithmetic throughput then matters alongside the capacity needed for sharded state and the interconnect needed by the partition. H100, B200, and TPU v5p configurations are candidates to evaluate under the same workload and quality target. The selected software stack must express the required operations efficiently enough for the hardware advantage to appear in sustained execution.

Serving the same language model changes the answer, for the reason the token-latency notebook [2.1](https://mlsysbook.ai/vol2/02_compute_infrastructure/02_compute_infrastructure.html#nbk-token-latency) established. At batch size 1, the H100’s 3.35 TB/s bandwidth determines decode throughput while much of the arithmetic silicon waits, so the key metric becomes memory bandwidth per dollar rather than peak TFLOP/s. Batching helps for the reason [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^sec-compute-roofline|section 2.3.2]] quantified, reusing each weight read across more requests, which is why serving systems work so hard to batch without violating tail-latency service-level objectives (SLOs). The workload did not change names, but the binding term of the single-machine iron law moved from arithmetic to data movement, and the accelerator choice changes with it.

Recommendation models split the decision across sparse lookup and dense computation, the memory-placement case that the recommendation pod of [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.08 The Pod#^sec-compute-fleet|section 2.7.1]] already resolved. Vision workloads and diffusion models, which generate an image by removing noise from it over repeated passes of a denoising network, move back toward arithmetic throughput because convolutions ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^tbl-roofline-workloads|table 7]]), attention blocks, and denoising networks reuse data heavily. Diffusion inference makes this especially clear. A standard Stable Diffusion v1.5 configuration runs 50 denoising steps, so the service pays for a sequence of full model evaluations rather than one decode step per token. For these workloads, TFLOP/s per dollar often dominates bandwidth per dollar once model state fits in memory.

Mixture of experts (MoE) activates only part of a much larger parameter set for each token ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-shazeer2017outrageously|Shazeer et al. 2017]]); Mixtral-8x7B ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-jiang2024mixtral|Jiang et al. 2024]]) has 46.7B total parameters but only 12.9B active per token because its router chooses 2 experts of 8 experts experts. The router sends tokens to those experts across devices through the AllToAll collective, so the selection consequence is a fabric with enough bisection bandwidth, together with load balancing, for the theoretical saving to appear in the training trace ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-fedus2022switch|Fedus et al. 2022]]; [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.14 Source References#^ref-lepikhin2021gshard|Lepikhin et al. 2021]]). Multi-modal models similarly combine phases with different arithmetic intensity and batching behavior, such as vision encoding and text decode. Their relative cost and placement determine whether flexible scheduling, additional memory, or communication capacity changes the critical path; modality count alone does not select an accelerator architecture, so the planner must follow the data exchanged between the actual phases.

↪ MoE AllToAll routing and expert load imbalance are developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.09 AllToAll Exchanges at Scale#^sec-collective-communication-moe-dynamic-routing|Dynamic routing and expert imbalance in MoE AllToAll]]**.

**Systems Perspective 2.2: Matching hardware to workload**

Workload diversity can justify a heterogeneous fleet, with each pool provisioned for its binding resource. The gain comes from matching hardware to the work assigned to it, while keeping each tightly synchronized training group balanced. The fleet-wide decision must account for that matching benefit together with the cost of supporting multiple platforms.

### Precision and Throughput Trade-Offs

^sec-compute-infrastructure-precision-throughput-tradeoffs-49a5

Booking a twofold training speedup from FP8 on a capacity spreadsheet, or sizing a serving pool for FP16 weights when INT4 would pass quality validation, can misstate fleet device counts by a factor of two or more. The number formats and peak rates of [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.05 Sustained Compute and Precision#^sec-compute-tensor-cores|section 2.4]] become fleet decisions as soon as they set how many accelerators a job requires. FP8 doubles the H100’s advertised arithmetic ceiling for supported operations, from 989 TFLOP/s to 1,979 TFLOP/s per GPU, but that doubling is a peak-capacity comparison, not a training speedup that can be booked before workload validation. Infrastructure sizing must use the sustained rate of a validated precision policy.

For inference, quantization changes both weight storage and the possible hardware topology. Our 175B model at FP16 requires 350 GB, so the parameters alone span at least five 80 GB H100 GPUs. Quantizing to INT8 halves the weight payload to 175 GB, which fits on three GPUs, and INT4 shrinks it further to 87.5 GB, which fits on two GPUs. These are weight-only capacity bounds; quantization metadata, attention state, and workspace also need memory. Reading 4-bit rather than 16-bit weights quarters the raw payload, but it does not change physical bandwidth or guarantee a fourfold token-latency reduction. Kernel support, conversion work, other traffic, and any change in device count determine the realized gain, subject to validation of model quality.

### Benchmarking Accelerator Performance

^sec-compute-infrastructure-benchmarking-accelerator-performance-6920

A procurement team comparing accelerators needs a published number that predicts the performance the organization will actually achieve. Peak TFLOP/s, memory bandwidth, and TDP describe *potential*, not *achieved* performance, so the decision turns on whose measured results to trust and under what rules they were produced. The industry-standard reference is MLPerf, maintained by MLCommons. MLPerf Training reports the time to train reference models to a target accuracy, and MLPerf Inference reports serving throughput and latency under realistic batching and streaming conditions. Both capture complete system performance, including software stack efficiency, communication overhead, and memory management, rather than raw silicon speed alone.

Closed-division results fix the workload and quality target so implementations can be compared, and open-division results allow broader changes, rules that **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.04 Measuring Goodput#^sec-performance-engineering-measurement-contract|The measurement contract]]** reads as one instance of a measurement contract. Neither division predicts a deployment automatically. A team must compare the submission’s workload, software, precision, hardware count, and quality target with the intended system before using its result for procurement.

For our 175B model, training, fine-tuning, and serving need separate measurements. Batch shape, trainable state, sequence length, and partitioning can change both capacity demand and the critical path. Fine-tuning does not occupy a fixed point between training and decode merely because it updates an existing model. The team must evaluate the intended phases on candidate hardware with the actual model and data pipeline, using published MLPerf results as comparative evidence rather than deployment forecasts. MFU reports the share of the chosen peak that useful model computation averages over a measurement window. Time to train a reference model to a target metric also captures the I/O stalls, checkpointing, and restart delays that a steady-state MFU window can omit, although neither establishes the model quality reached.

### Inference-Specific Infrastructure Considerations

^sec-compute-infrastructure-inferencespecific-infrastructure-considerations-10c9

Training and serving place opposite demands on the same cluster because they optimize over different timescales. A large training run is one long job that occupies its allocation for days or weeks and is judged by sustained *throughput* and time to a target quality. Its steps repeat the same exchanges, so communication demand is easier to characterize than an arrival stream, and an individual operation can take milliseconds to seconds without harm, although failures, I/O, and changes in execution shape still affect the schedule. Serving trained models must instead turn the same hardware into responses for many independent, short-lived requests arriving at irregular intervals, each under a latency target that for interactive use is measured in tens of milliseconds.

Serving infrastructure must meet *latency* targets at an acceptable *cost per query* under a variable request load. Independent requests can be assigned to separate replicas, but a replica that shards a model across devices still communicates within each request. Prompt processing, successive decode steps, and complete responses also have different latency budgets. Capacity planning must therefore specify the request mix, model placement, and service targets before concluding that serving needs less network capacity than training; training and serving part ways on utilization, model placement, network traffic, and the cost metric that judges them ([[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.09 Accelerator Selection for Fleet Workloads#^tbl-training-serving-infrastructure|table 16]]).

| **Dimension**       | **Training infrastructure**                                                                                       | **Serving infrastructure**                                                                                                                   |
|:--------------------|:------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------|
| **GPU utilization** | Large local batches push dense layers into the compute-bound regime; well-tuned runs commonly sustain 30–50% MFU. | Batch-1 decode is deeply memory bound and can fall below 5% MFU; batching raises utilization at the cost of latency, within memory capacity. |
| **Model placement** | Tensor and pipeline parallelism distribute a single model across many GPUs.                                       | Replicas of the model, or large shards of it, handle independent requests, so memory demand scales with concurrent serving capacity.         |
| **Network traffic** | The partition determines gradient, activation, and parameter exchanges between workers.                           | Independent replicas can serve separate requests, but sharded replicas still require inter-device exchanges within each request.             |
| **Cost metric**     | Cost per completed run at a target quality includes the measured schedule and recovery overhead.                  | Cost per request or per 1,000 tokens depends on request shape, latency targets, utilization, and provisioned capacity.                       |

Table 16: **Training vs. Serving Infrastructure**: Training and serving optimize different hardware behaviors, so capacity planning must compare utilization, model placement, network traffic, and cost in the mode the fleet will actually run.

^tbl-training-serving-infrastructure

Serving therefore cannot be planned as training with smaller batches, because the optimization target changes from synchronized throughput to latency-bounded, continuously billed requests. The implication is that effective serving infrastructure often uses different hardware, different software, and different facility designs than the training infrastructure. Some organizations use previous-generation GPUs (A100s) for serving because the memory bandwidth per dollar can be competitive with newer GPUs, and the lower TDP (400 W vs. 700 W) allows higher rack density and lower cooling costs.

The inference workload itself splits into two distinct phases with opposing bottlenecks. The prefill phase processes prompt tokens in parallel, increasing weight reuse and potentially approaching the compute ceiling when the prompt and batch shapes supply enough work. The decode phase generates tokens sequentially for each request and is deeply memory-bandwidth-bound at small batch sizes. Serving systems raise utilization by admitting and retiring requests at iteration boundaries, called continuous batching, and by limiting how much prompt work delays the next decode iteration, mechanisms that **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale#^sec-inference-scale|Serving at Scale]]** develops.

A napkin estimate shows how quickly serving capacity reaches training scale. One tensor-parallel replica of the running model on an eight-GPU node streams its FP16 weights once per decode step, which takes at least 13.1 ms at H100 HBM bandwidth. Batching 32 concurrent requests yields about 2,450 tokens/s per replica. A service handling 1,000 requests/s at 250 output tokens each must generate 250,000 tokens/s, which requires at least 103 replicas, or 824 GPUs, most of the 1,024-GPU training reference cluster. The estimate is a lower bound because it ignores key-value cache traffic, prefill work, and headroom for bursts and failures; **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^sec-inference-scale-batching-strategies-scale-6733|Batching Strategies at Scale]]** replaces it with batching models that account for key-value cache capacity, variable request lengths, and latency targets. Reliability objectives differ as well. A training job can absorb an occasional failure because checkpointing recovers the lost progress, whereas a stalled serving replica delays every request routed to it until traffic fails over.

### The Accelerator Decision Matrix

^sec-compute-infrastructure-accelerator-decision-matrix-8bba

Combining workload regime, precision policy, and serving latency targets yields the procurement screen in [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.09 Accelerator Selection for Fleet Workloads#^tbl-accelerator-decision|table 17]]. Its candidate configurations rest on representative assumptions rather than fixed assignments of model families to bottlenecks or vendors. The rule is to diagnose the binding constraint first, then compare sustained useful work within the capacity, quality, latency, and facility budgets. The table’s constraint column is the per-device one, what a single accelerator must supply. The archetype roster of **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.07 The Fleet Stack and the Lighthouse Archetypes#^sec-vol2-introduction-archetypes|Three systems archetypes]]** answers a different question, which constraint binds the fleet as a whole, so a workload can be compute-bound on each device and still communication-bound across the cluster, as Archetype A is.

| **Workload**                      |         **Binding constraint**         |                           **Key metric**                            |               **Recommended class**               |
|:----------------------------------|:--------------------------------------:|:-------------------------------------------------------------------:|:-------------------------------------------------:|
| **LLM training ($>100\text{B}$)** |       Compute (high batch size)        | Sustained useful throughput at validated precision, interconnect BW |                H100/B200, TPU v5p                 |
| **LLM inference (batch=1)**       |            Memory bandwidth            |                           GB/s per dollar                           |             A100, H100 (bandwidth/\$)             |
| **LLM inference (batched)**       |          Compute + bandwidth           |    Sustained token throughput within latency and capacity limits    |                    H100, B200                     |
| **Vision model training**         |      Compute (large spatial dims)      |         Sustained useful throughput at validated precision          |       H100/B200 configurations to evaluate        |
| **Recommendation (embeddings)**   |            Memory capacity             |                            GB per dollar                            |               CPU DRAM + GPU hybrid               |
| **Fine-tuning ($<13\text{B}$)**   | Memory capacity (state near HBM limit) |                            HBM capacity                             |           A100-class capacity candidate           |
| **Research/prototyping**          |              Flexibility               |                         Software ecosystem                          | GPU or accelerator with required operator support |

Table 17: **The Accelerator Decision Matrix**: The optimal accelerator depends not on peak specifications but on which physical resource (compute, bandwidth, or capacity) is the binding constraint for the target workload. The Roofline Model screens the compute and bandwidth ceilings at the intended precision and shape. Among candidates that clear capacity and facility constraints, measured sustained useful work at the required quality and latency determines value.

^tbl-accelerator-decision

For our 175B running example, [[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.09 Accelerator Selection for Fleet Workloads#^tbl-accelerator-decision|table 17]] separates the training purchase from the serving purchase. The workload constraint comes first; software support, deployment lifetime, and measured sustained throughput are compared only among candidates that clear it. A cheaper accelerator-hour is useful only if it supplies the required throughput within the capacity, latency, and facility budgets.

**Checkpoint 2.4: Accelerator selection**

An engineering team needs to deploy a 70B-parameter model for both training and inference. Training will use batch size 2048 across 256 GPUs for 3 months. Inference will serve 10,000 requests per second at batch size 1 for 2 years.

**Training intensity**: identify the local microbatch, sequence length, and partitioning information needed to estimate training intensity; compare it with batch-1 decode under the chapter’s weight-traffic approximation.

**Hardware split**: identify which measurements are needed to determine whether training and inference should use the same hardware or different hardware.

**Two-year cost**: formulate the 2-year inference-cost comparison between H100s rented at a cloud rate of \$4/GPU-hour and A100s already in the fleet, charged at its reference in-service rate of \$2/GPU-hour, and identify the prompt and output lengths, replica placement, sustained throughput, and capacity assumptions required to evaluate it.

Each of these selections assumes the memory, communication, and power boundaries stay fixed at today’s package and rack limits. Hardware technologies now entering deployment do not remove those walls, but they relocate where each constraint binds across a facility’s lifetime.

    1.  Peak FP8 TFLOP/s per dollar, because decode performs two floating-point operations per parameter.
    2.  Memory bandwidth per dollar, confirmed by measured throughput at the required latency, because batch-1 decode streams the weights with little reuse.
    3.  Host DRAM capacity per dollar, because the weights should be served from host memory.
    4.  Bisection bandwidth of the cluster fabric, because every request crosses the network.
