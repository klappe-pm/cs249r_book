# V2-07.14 Distributed Debugging and Observability

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-fault-tolerance-reliability-reliability-distributed-debugging-observability-1a7f

At 2:00 AM, latency on the flagship generative API spikes from 200 ms to 5 seconds, but CPU, memory, and network metrics all look normal. The latency breach can justify immediate mitigation under a predefined policy; choosing a targeted repair requires locating the stalled work across hundreds of microservices. Distributed debugging and observability provide the diagnostic capability required to locate these invisible bottlenecks.

### Diagnostic Challenges in Distributed ML Systems

^sec-fault-tolerance-reliability-reliability-distributed-ml-systems-hard-debug-8d8a

When a latency spike or stalled collective appears on one run and vanishes on the next, the evidence needed for recovery is split across timing, state, scale, and model behavior. Nondeterminism enters from multiple directions: network timing variations change execution order, thread scheduling differences alter race conditions, GPU kernel execution order varies across runs, and floating-point operation ordering changes numerical results. Consequently, a bug that manifests on one execution may not reproduce on subsequent runs, creating “Heisenbugs”[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn20|²⁰]] that appear to vanish when observed.

Partial failures turn that nondeterminism into a recovery problem. A single machine can also suffer partial failures, but distribution adds independently progressing workers and communication paths. One component can stop while others continue, leaving peers uncertain whether it has failed or become unreachable. Scale then removes manual inspection as a viable debugging method. With thousands of components, automated tools must filter large telemetry streams and identify the few signals that explain the incident. ML systems add model behavior to the same diagnostic problem: silent accuracy degradation produces wrong results without errors, numerical issues like NaN and infinity propagate through computation, data-dependent bugs manifest only for specific inputs, and learning causes expected behavior changes that can resemble bugs. Isolating a fault across all four sources requires structured telemetry that links cluster-wide symptoms to individual requests and events.

### Observability Pillars

^sec-fault-tolerance-reliability-reliability-observability-pillars-0e45

Observability supports both immediate mitigation and investigation of the cause. Suppose a recommendation service suddenly violates its latency SLO while the model replicas still report healthy GPU utilization. Metrics establish the timing and scope of the symptom, traces show which service span consumes the request budget, and logs record events inside that service. [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.14 Distributed Debugging and Observability#^fig-observability-three-pillars|Figure 18]] connects these streams to operational decisions. A single signal can justify an action, such as shedding load when a queue exceeds its budget. Joining request and trace context with model versions, deployment tags, and time windows strengthens the diagnosis when several causes could explain the same symptom. Correlated evidence narrows those possibilities; it does not by itself prove the physical or software cause.

↪ How metrics, logs, and traces become a fleet-wide observability architecture that routes evidence across many models and owners is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.07 Monitoring at Scale#^sec-ml-operations-scale-observability-architecture-ba87|Observability architecture]]**.

![[90 Assets/Volume II/07 Fault Tolerance/Observability Three Pillars 732ff5647b.svg]]

Figure 18: **The Three Pillars of Observability**: Diagnosis of fleet failures can combine three signal types. Metrics reveal *when* and *where* a problem occurs (for example, GPU utilization drops). Logs provide the *what* through event context (for example, an out-of-memory exception). Traces expose the *request path* by linking events across the distributed lifecycle (for example, identifying the request that triggered the memory spike). A single signal can justify immediate mitigation; joining signals on shared identifiers strengthens diagnosis without proving the cause.

^fig-observability-three-pillars

Metrics are the first evidence because they compress fleet behavior into time series that can trigger action. A metric stream becomes fault-tolerance infrastructure only when an alert maps to a recovery decision. High p99 latency may trigger load shedding, a falling cache hit rate may trigger fallback features, and a sudden prediction-distribution shift may block a rollout before it corrupts user-facing decisions.

Logs provide the event context that a metric intentionally discards. Structured logging uses formats such as JavaScript Object Notation (JSON) with consistent fields, so incident tooling can search by service, request, model version, GPU, feature store, or trace identifier. A GPU memory allocation failure logged this way records both the local failure context and the trace identifiers needed to connect the event to distributed metrics and spans ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.14 Distributed Debugging and Observability#^lst-structured-log-entry|listing 2]]).

``` json
{
  "timestamp": "2024-01-15T10:23:45.123Z",
  "level": "ERROR",
  "service": "inference-server",
  "trace_id": "abc123",
  "span_id": "def456",
  "message": "GPU memory allocation failed",
  "gpu_id": 3,
  "requested_bytes": 4294967296,
  "available_bytes": 2147483648
}
```

Listing 2: **Structured JSON Log Entry**: A structured log entry for a GPU memory allocation failure, including trace and span identifiers for correlation with distributed traces and resource metrics for diagnosis.

^lst-structured-log-entry

For fault tolerance, the important logging property is consistent correlation rather than the particular backend. Log levels should map incidents to escalation consistently across components, but the recovery system depends more on whether operators can query events by the same request, trace, model version, feature version, and deployment identifiers that appear in metrics and spans. Log aggregation is therefore useful because it preserves the join between local failure context and fleet-wide symptoms.

Traces show where latency or failure propagated across distributed components. A trace is the end-to-end journey of a request, a span is one operation within that journey, and context propagation carries the trace identity across service boundaries. A trace through an ML inference pipeline illustrates how these spans compose:

``` text
Trace: user-request-12345
|-- Span: api-gateway (5 ms)
|   `-- Span: auth-service (2 ms)
|-- Span: feature-service (15 ms)
|   |-- Span: user-feature-lookup (8 ms)
|   `-- Span: item-feature-lookup (12 ms)
|-- Span: inference-service (45 ms)
|   |-- Span: preprocessing (3 ms)
|   |-- Span: model-inference (40 ms)
|   `-- Span: postprocessing (2 ms)
`-- Span: response-formatting (1 ms)
Total: 66 ms
```

Standard distributed tracing APIs such as OpenTelemetry carry this context across services, and a tracing backend stores and visualizes the traces. The durable requirement is not the particular backend but enough preserved context to answer whether the fault lives in request routing, feature retrieval, model execution, postprocessing, or a dependency outside the model service.

A single training job uses the same three pillars with the job, step, and rank as its shared identifiers. Its metrics are per-rank series such as step time, gradient norm, and loss, so a rank that lags or diverges stands out against its peers. Its logs are each rank’s records of errors, restarts, and collective timeouts. Its trace of a training step records when each rank entered and left each collective, which shows the rank the others waited on; Meta used such communication traces to locate stalled collectives and slow workers during Llama 3 pretraining (war story [7.2](https://mlsysbook.ai/vol2/07_fault_tolerance/07_fault_tolerance.html#ws-fault-tolerance-llama3-failure-cadence)). Joined on those identifiers, the three streams let operators match a symptom to its first recovery action in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^tbl-training-failure-response-map|table 7]].

### ML-Specific Debugging

^sec-fault-tolerance-reliability-reliability-mlspecific-debugging-27d5

Operational signals alone are not enough when a process stays healthy while its tensors, inputs, or per-rank execution times drift outside the model’s contract. ML systems therefore add specialized debugging across three surfaces: numerical health inside the computation, semantic validity across the data pipeline, and straggler attribution across distributed stages.

#### Numerical Debugging

^sec-fault-tolerance-reliability-reliability-numerical-debugging-ee2a

Numerical debugging targets failures where tensors remain valid objects but contain invalid values. NaN detection[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn21|²¹]] exposes values that can propagate through later arithmetic without a process crash. A minimal diagnostic check only flags the invalid output ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.14 Distributed Debugging and Observability#^lst-nan-detection|listing 3]]), so the caller must act on the result and block its publication.

``` python
# Check tensor for NaN values
# (propagate from any corrupted computation)
if torch.isnan(output).any():
    log.error("NaN detected in output", request_id=request_id)
    # Caller must retain a replayable input reference and block or replace this output
```

Listing 3: **NaN Detection**: This check flags NaN output for diagnosis. The caller must block publication or choose a fallback; a logged request identifier refers to an input retained by the application for replay.

^lst-nan-detection

During training, per-step gradient statistics expose numerical faults before they corrupt the entire run. Tracking the global gradient norm catches sudden explosion or vanishing, histogramming the gradient distribution flags outlier spikes, and logging layer-wise gradient norms isolates which block in the network first destabilized. Mixed-precision training[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn22|²²]] can introduce related numerical issues when narrow dynamic range interacts with unstable updates. A dynamic loss scaler reduces its scale after detecting nonfinite gradients, indicating overflow or another invalid operation rather than proving underflow. Gradient magnitudes, skipped updates, and comparison with a higher-precision replay help distinguish range problems from other causes; ordinary FP16 rounding differences are not themselves faults.

#### Data Debugging and Validation

^sec-fault-tolerance-data-debugging-validation

Data bugs surface as valid-looking but wrong inputs, so debugging must verify semantic correctness at each pipeline boundary in addition to numerical validity. Validation checks expected format, shape, value ranges, required fields, and encoding before data reaches the model, catching malformed examples while the failure is still local to the input path. Once the input passes those static checks, the system needs evidence about behavior over time. Distribution monitors track feature drift, null-rate changes, and outliers as they emerge, while transformation instrumentation logs intermediate shapes and statistics so teams can compare each stage against known-good data. Together, these signals separate a corrupted input path from a numerical failure inside the model.

↪ The validation gates and response policies that run these data checks continuously across a production fleet are developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.05 Feature Store Operations#^sec-ml-operations-scale-data-quality-operations-e77b|Data quality operations]]**.

#### Straggler Detection and Analysis

^sec-fault-tolerance-reliability-reliability-straggler-detection-analysis-6925

Perspective [7.6](https://mlsysbook.ai/vol2/07_fault_tolerance/07_fault_tolerance.html#psp-fault-tolerance-straggler-or-failure) treated a straggler as a slow training rank that holds up a synchronous step. The same idea extends to serving once “peer” means any component on a request’s path, so straggler diagnosis there asks which replica or service stage is slow enough to become a failure-equivalent bottleneck. A slow serving replica delays requests routed to it and can trigger retries under load; its effect on the service’s tail percentile depends on its traffic share and the routing policy. A request that waits for several required parallel branches is instead bounded by the last required completion. Operation-level timing instrumentation measures time for each operation, enabling latency attribution across pipeline stages. Wrapping each operation in a context manager that emits per-span timing metrics makes performance directly comparable across replicas ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.14 Distributed Debugging and Observability#^lst-timing-instrumentation|listing 4]]).

``` python
# Wrap operations in timing context managers for latency attribution
with timer("feature_lookup"):
    features = feature_store.lookup(
        ids
    )  # Often the latency bottleneck
with timer("model_inference"):
    predictions = model(features)  # Host submission time for asynchronous GPU work
```

Listing 4: **Operation-Level Timing**: Context manager instrumentation attributes latency to individual pipeline stages, enabling straggler detection by comparing the same span across replicas.

^lst-timing-instrumentation

For asynchronous GPU execution, the host span around `model(features)` in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.14 Distributed Debugging and Observability#^lst-timing-instrumentation|listing 4]] measures only the CPU time required to enqueue kernels onto the GPU stream, not completed device work. Because kernel launches return to the host before the GPU finishes executing them, a naive host timer can report a fast inference span even on a thermally throttled GPU and misattribute the delay to whichever later stage first synchronizes the stream or copies predictions back to host memory. Measuring actual GPU execution time requires recording hardware events on the stream before and after the forward pass and reading their elapsed time after the stream completes. Like-for-like component timing is then compared across replicas with percentile analysis. The p50 latency shows typical performance, while p99 shows tail latency, and comparing p99 across replicas identifies workers whose slow path has become a fleet-wide bottleneck. The diagnosis must then separate the causes that share this slow-worker symptom, which include the gray-failure causes of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-distinguishing-stragglers-failures-285d|section 7.9.5]] and data skew, in which some inputs are slower to process.

### Serving Failure Patterns

^sec-fault-tolerance-reliability-reliability-common-failure-patterns-3306

Serving failures require a symptom-to-action mapping under much tighter latency constraints than the training-loss signatures of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-failure-detection-mechanisms-efed|section 7.9.1]]. Common serving symptoms differ both in what each one reveals and in what the serving system must do first ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.14 Distributed Debugging and Observability#^tbl-serving-failure-response-map|table 18]]). Cascade failures are hardest to diagnose because the root cause is obscured by the secondary timeouts and retries it generates, as example [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.14 Distributed Debugging and Observability#^exmp-fault-tolerance-diagnosing-cascade-failure|7.1]] traces across metrics, logs, and spans.

| **Symptom**                | **Likely interpretation**                                                               | **Immediate response**                                                                         |
|:---------------------------|:----------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------|
| Latency spikes             | Resource contention, garbage collection, cold caches, or model reloads                  | Check placement and capacity; repeated spikes usually mean the problem is no longer transient. |
| Rising error rates         | Dependency failure, data-format change, or model bug                                    | Investigate immediately because errors compound across dependent services.                     |
| Silent quality degradation | Model drift, feature degradation, or data-pipeline fault                                | Use quality monitoring beyond standard operational metrics.                                    |
| Cascade failure            | Timeout exhaustion, resource depletion, or error propagation from one failing component | Trip circuit breakers and preserve isolation boundaries before the failure spreads.            |

Table 18: **Serving Failure Response Map**: Serving incidents must be classified quickly because every diagnosis competes with a user-facing latency budget. The table ties each symptom to the first operational response rather than treating all serving failures as generic errors.

^tbl-serving-failure-response-map

**Example 7.1: Diagnosing a cascade failure**

**Scenario**: A recommendation system experiences sudden latency spikes.

**Diagnosis**: The three observability pillars narrow the failure path. Metrics reveal the symptom: p99 latency jumped from 45 ms to 800 ms at 14:32, with error rate increasing from 0.1 percent to 15 percent. Traces locate the delay in the feature-service span, which consumes 700 ms instead of the normal 12 ms, while model inference remains at 40 ms. Logs show repeated connection timeouts to the user embedding cache at 14:31, followed by requests bypassing the cache and reaching the embedding database directly. That evidence identifies cache unavailability and increased downstream demand; it does not yet distinguish a failed cache process from a network or resource problem.

**Systems lesson**: Cache unavailability can transfer enough demand to overwhelm the embedding database. A circuit breaker and a validated default-embedding path can limit that cascade while diagnosis continues. The fallback must also respect the quality budget and avoid sending the rejected demand to another saturated dependency.

^exmp-fault-tolerance-diagnosing-cascade-failure

Observability and diagnostic maps help operators isolate a failure once it strikes, but verifying that detectors, circuit breakers, and recovery paths actually hold under fire requires triggering those failures deliberately before production traffic meets them.
