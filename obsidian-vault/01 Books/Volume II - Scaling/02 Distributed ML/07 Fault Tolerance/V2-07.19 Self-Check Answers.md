1.  **A production cluster operates 10,000 GPUs, where each individual GPU exhibits an independent MTTF of 50,000 hours and an availability of 99.99%. What is the resulting GPU-only cluster MTBF, and what is the probability that all 10,000 GPUs are simultaneously operational at any random instant?**

    1.  Cluster MTBF is 50 hours; simultaneous cluster availability is approximately 90.5%.
    2.  Cluster MTBF is 500 hours; simultaneous cluster availability is approximately 99.0%.
    3.  Cluster MTBF is 5.0 hours; simultaneous cluster availability is approximately 36.8%.
    4.  Cluster MTBF is 0.5 hours; simultaneous cluster availability is approximately 1.0%.

    *Answer*: The correct answer is C. The cluster MTBF scales inversely with component count: $\text{MTBF}_{\text{cluster}} = \text{MTBF}_{\text{component}} / N = 50{,}000 / 10{,}000 = 5.0$ hours. The simultaneous availability follows the product of individual reliabilities: $R_{\text{cluster}} = (0.9999)^{10{,}000} \approx e^{-1} \approx 0.368$ (36.8%). The 50-hour option incorrectly divides 50,000 by 1,000 instead of 10,000 and overestimates availability. The 500-hour and 0.5-hour options miscalculate the linear $1/N$ scaling by one or two orders of magnitude.

    *Learning Objective*: Calculate the system-level MTBF and availability scaling for large accelerator clusters.

2.  **Using an illustrative unprotected-memory soft-error rate of 250 FIT/Mbit and 80 GiB of HBM per device, explain why a 1,024-GPU training cluster needs ECC protection.**

    *Answer*: Using the chapter’s 80 GiB device capacity gives about $7.04\times10^8$ Mbit across 1,024 GPUs. Multiplying by 250 FIT/Mbit yields about $1.76\times10^{11}$ FIT. Since 1 FIT is one event per billion hours, this is about 176 raw memory errors per hour, approximately one every 20 seconds. ECC corrects covered error patterns before they become application-visible; the residual job-interrupting and silent-corruption rates depend on the protection scheme, not the raw rate alone.

    *Learning Objective*: Analyze why high-density memory subsystems dominate the soft-error failure budget in distributed ML clusters.

2.  **During a distributed AllReduce operation, a single GPU rank experiences a silent bit flip in an exponent calculation. The rank does not crash, passes network timeouts, and contributes an anomalously large gradient to the collective average. How is this failure categorized, and what is its primary danger to the training run?**

    1.  Byzantine failure; it silently poisons model weights and gradients while bypassing standard process-liveness and timeout detection.
    2.  Fail-stop failure; it immediately halts the AllReduce collective and triggers an automated container restart.
    3.  Transient network failure; it is automatically corrected by underlying InfiniBand packet retransmission protocols.
    4.  Benign gray failure; it is absorbed by stochastic gradient descent with zero impact on final convergence.

    *Answer*: The correct answer is A. This is a Byzantine failure because the defective component continues participating in collective communication while transmitting mathematically corrupted data, silently poisoning global model parameters without triggering fail-stop crash handlers. Categorizing this as a fail-stop failure is incorrect because fail-stop components cease operation and are caught by timeout mechanisms. Categorizing this as a transient packet loss error confuses network transport retries with silent arithmetic corruption. Categorizing this as a benign gray failure that self-corrects through stochastic gradient descent is incorrect because exponent bit flips can scale gradients by orders of magnitude, causing divergence or NaN collapse.

    *Learning Objective*: Compare Byzantine failures and silent data corruption against fail-stop failures in synchronous distributed training.

1.  **A cluster node passes cold-boot diagnostics and memory tests during morning maintenance, but repeatedly produces incorrect matrix multiplication results under sustained thermal load during large-batch backward passes. What type of fault does this represent, and what is the appropriate operational response?**

    1.  Transient fault; retry the exact batch on the same node since the fault will disappear automatically.
    2.  Intermittent fault; collect runtime telemetry under load, quarantine the node, and replace or repair it rather than returning it directly to production.
    3.  Permanent stuck-at-0 fault; immediately discard all training checkpoints because the device cannot execute any instructions.
    4.  Software race condition; upgrade the host OS kernel and increase the AllReduce heartbeat timeout threshold.

    *Answer*: The correct answer is B. The recurring load-dependent signature is consistent with an intermittent fault and warrants quarantine and tests under the conditions that exposed it. Passing a cold-boot test does not clear that risk. Thermal correlation alone does not exclude software or runtime defects; replay and telemetry must corroborate hardware attribution before repair or replacement. Retrying without validation risks recurring corruption.

    *Learning Objective*: Classify hardware faults by their temporal signature and determine appropriate mitigation strategies.

2.  **Compare the impact of a single-bit flip in the sign bit versus a single-bit flip in the exponent bits of an IEEE 754 floating-point weight or gradient tensor during neural network training.**

    *Answer*: A sign-bit flip reverses the value, potentially changing the direction of an update. An exponent-bit flip can change its scale by orders of magnitude or create a nonfinite value, so it can be more damaging than a low mantissa-bit error. The effect depends on the original bit pattern, operation, and error masking; not every exponent error immediately causes divergence.

    *Learning Objective*: Analyze the vulnerability of floating-point numerical representations to single-bit hardware upsets.

3.  **A node that stays alive and keeps answering heartbeats but runs slowly or erratically, so that timeouts never fire, is said to suffer a \_\_\_\_ failure.**

    *Answer*: The correct answer is gray (a gray failure). Because the node never stops responding, fail-stop detection through heartbeats and timeouts cannot catch it; the fleet must detect it through straggler analysis and performance evidence instead.

    *Learning Objective*: Identify failure modes that evade timeout-based detection and require performance-based evidence.

4.  **How does a permanent stuck-at fault in a specialized accelerator’s Tensor Core multiply-accumulate unit manifest differently during training compared to a traditional processor crash?**

    1.  It causes an immediate kernel execution timeout that terminates the local process group within milliseconds.
    2.  It corrupts operating system page tables, forcing an immediate kernel panic and node reboot.
    3.  It triggers a PCIe bus reset that automatically redirects subsequent GEMM operations to host CPU memory.
    4.  It can produce repeatable incorrect values in computations using the defective datapath while the process remains alive.

    *Answer*: The correct answer is D. A stuck-at datapath defect can repeatedly corrupt affected computations without raising a process exception. The visible effect depends on which instructions, values and lanes use the faulty circuit, and whether later operations mask the error. It need not affect every matrix multiplication or always cause divergence. The other choices incorrectly require a crash, bus reset or automatic CPU fallback.

    *Learning Objective*: Compare the manifestation of permanent datapath faults in specialized accelerator matrix units against scalar processor faults.

5.  **Because electronic components exhibit a constant failure rate during their useful life phase under the exponential reliability model, cluster operators should assign newly delivered accelerator nodes directly to multi-week foundation model pretraining runs without prior burn-in testing.**

    *Answer*: False. Newly manufactured hardware can exhibit elevated early-life failure rates from manufacturing defects, marginal packaging, and assembly flaws. Operators screen new or repaired nodes under qualified stress procedures before assigning expensive long jobs. Temperature, voltage, duration, and acceptance criteria depend on the component and procedure; a generic burn-in duration is not an operating specification or a guarantee of later reliability.

    *Learning Objective*: Evaluate the operational risks of bypassing burn-in screening for newly deployed accelerator hardware.

1.  **In a 100,000-GPU training cluster where each device has an illustrative SDC probability of $10^{-6}$ per GPU-hour, what is the expected SDC exposure and failure cadence during continuous AllReduce training with 2-second step times?**

    1.  The cluster experiences roughly 55.6 GPU-hours of exposure per 2-second step, resulting in an expected SDC event approximately every 18,000 steps (every ~10 hours).
    2.  The cluster experiences an SDC event on every single step because 100,000 GPUs exceed the reliability threshold.
    3.  The cluster experiences an SDC event once every 1,000 days because $10^{-6}$ is negligible for 2-second steps.
    4.  The cluster experiences an SDC event exactly every 50,000 hours regardless of cluster size.

    *Answer*: The correct answer is A. For a 2-second step ($2/3600 = 1/1800$ hours), 100,000 GPUs accumulate $100{,}000 / 1800 \approx 55.56$ GPU-hours of exposure per step. With an individual rate of $10^{-6}$ per GPU-hour, the probability of at least one SDC per step is $1 - (1 - 10^{-6})^{55.56} \approx 5.56 \times 10^{-5}$. The expected number of steps between SDC events is $1 / (5.56 \times 10^{-5}) \approx 18{,}000$ steps, which equals $18{,}000 \times 2 / 3600 = 10$ hours. The single-step claim exaggerates probability by orders of magnitude. The 1,000-day and 50,000-hour options ignore the $100{,}000\times$ fleet accumulation factor.

    *Learning Objective*: Calculate how silent data corruption risk compounds across fleet-scale collective communication operations.

2.  **Explain what gradient checksums and redundant computation can each detect during AllReduce, and why checksums alone cannot establish the arithmetic correctness of every worker contribution.**

    *Answer*: Checksums can detect changed bytes in transport or storage, and digests of supposedly identical reduced buffers can expose disagreement. A worker can compute an incorrect gradient and then checksum those incorrect bytes successfully. Detecting that arithmetic fault requires independent recomputation, replay, invariants, or statistical evidence. Those checks can block suspect updates within their coverage; they are not a universal guarantee against arbitrary faulty workers.

    *Learning Objective*: Design check-and-verify mechanisms to detect silent data corruption during distributed collective reductions.

3.  **Safety-critical embedded systems use dual or triple modular redundancy to detect or mask hardware faults. Explain why the same approach does not transfer to a 10,000-GPU training fleet, and describe how fleets spend redundancy instead.**

    *Answer*: Dual and triple modular redundancy run every computation two or three times, paying 100 or 200 percent hardware overhead so that a single wrong output is caught or outvoted within one control deadline. That price is reasonable for a small vehicle computer where one wrong output is dangerous. For fleet training it would double or triple the cost of the most expensive computation the organization runs, to guard against corruption events that arrive far less often than once per step and that rollback to a clean checkpoint can repair. Fleets therefore spend redundancy selectively: screening removes defective devices, cheap statistical checks run continuously, hot spares absorb drained nodes, and full recomputation is reserved for suspected corruption.

    *Learning Objective*: Evaluate why full modular redundancy is uneconomic for fleet training and how selective redundancy replaces it.

4.  **A component that remains active but sends arbitrary, corrupted, or conflicting data requires \_\_\_\_ fault tolerance reasoning rather than only fail-stop detection.**

    *Answer*: Byzantine. Such faults require explicit assumptions about faulty participants and independent validation; ordinary byte-integrity checks alone cannot prove that a local gradient was computed correctly.

    *Learning Objective*: Apply Byzantine fault tolerance principles to protect parameter updates against silent data corruption.

1.  **Why are GPU memory leaks in 70B+ parameter distributed training pipelines particularly destructive and difficult to diagnose compared to standard CPU memory leaks?**

    1.  GPU memory is dynamically swapped to NVMe disk automatically, causing unpredictable I/O thrashing rather than out-of-memory errors.
    2.  GPU allocators immediately throw segmentation faults upon the first unreleased tensor, preventing any batch execution.
    3.  Accelerator memory is scarce (40–80 GB per device) and shared across weights, optimizer state, and activations; a small leak per batch gradually builds over hundreds of steps until triggering an un-checkpointed OOM crash mid-run.
    4.  GPU memory leaks only occur when using mixed-precision BF16 formats and disappear entirely when switching to FP32 weights.

    *Answer*: The correct answer is C. Model, gradient, optimizer, and activation state can leave little accelerator-memory headroom. Retaining a graph or tensor every step gradually consumes that headroom until allocation fails, potentially far from the leak’s origin. Changing precision affects capacity but does not fix the leak; ordinary device allocations do not automatically spill to disk.

    *Learning Objective*: Analyze the accumulation mechanics and failure risks of accelerator memory leaks in distributed training.

2.  **Contrast a pipeline deadlock with a data race condition in distributed parallel training in terms of their system symptoms and impact on model convergence.**

    *Answer*: A deadlock prevents progress because stages wait on cyclic dependencies; utilization may be low or misleadingly high if communication kernels spin. A data race allows unsynchronized accesses to mutable state, producing timing-dependent results or corrupted updates while execution continues. Neither fault has a universal utilization percentage, so diagnosis requires progress counters, dependency traces, and correctness checks.

    *Learning Objective*: Compare synchronization failure modes across distributed parallel training paradigms.

3.  **Justify why a silent data preprocessing defect (such as unintended prompt truncation or incorrect token masking) presents a much higher compute and financial risk than a syntax error that crashes on the first batch.**

    *Answer*: A syntax error usually stops execution early and gives direct feedback, limiting wasted work. A silent preprocessing defect can preserve valid shapes while changing the objective, allowing expensive training to continue before evaluation exposes the problem. The loss depends on when the defect is detected, which state or data it affected, and whether valid checkpoints permit recovery; it need not invalidate the entire run.

    *Learning Objective*: Justify why silent software transformations in data pipelines present higher business and compute risk than fail-stop software errors.

4.  \*\*A preprocessing change silently truncates prompts and discards the system prompt. Sequence the reliability gates in the order that should catch the defect, from earliest and cheapest to the final proof that recovery works:

<!-- -->

1.  A fault-injection test showing that the resulting alert blocks publication or rolls back to a known-good state
2.  A boundary unit test asserting that tokenizer limits, system prompts, and masks survive preprocessing
3.  An integration replay that follows one recorded batch through loading, sharding, collation, and model input construction\*\*

*Answer*: The correct sequence is (2) -\> (3) -\> (1). - (2) The boundary unit test catches the tokenizer defect before any distributed execution. - (3) Integration replay confirms that batch shapes and metadata survive the full input path. - (1) Fault injection demonstrates that, if corruption does slip through, the detector fires and recovery satisfies its objectives before corrupted state commits.

*Learning Objective*: Design a layered software validation pipeline in which each gate exercises a specific invariant and authorizes a specific decision.

1.  **The expected cost of a training run is modeled as base compute, plus expected failures times the cost per failure, plus the cost of fault-tolerance mechanisms. Under this model, when does one more unit of fault-tolerance investment lower the total expected cost?**

    1.  Whenever it reduces the expected number of failures, regardless of what it costs.
    2.  Whenever the cluster is large enough to fail several times per day.
    3.  While the reduction in expected failure cost it buys exceeds its own marginal cost.
    4.  Whenever total fault-tolerance spending stays below the base compute cost of the run.

    *Answer*: The correct answer is C. The investment criterion compares the marginal cost of protection with the marginal reduction in expected failure cost; additional protection pays while the second exceeds the first. Reducing failures at any price ignores that protection itself adds cost, and a large, frequently failing cluster usually satisfies the criterion but does not define it. Comparing protection with base compute is not the test, because base compute is held fixed.

    *Learning Objective*: Apply the marginal investment criterion to decide whether an added fault-tolerance mechanism lowers expected run cost.

2.  **A 175B-parameter language model trains on 10,000 GPUs at about \$2 per GPU-hour, and a ViT-Large model trains for two days on a much smaller allocation. Both checkpoint once a day. Why can one failure cost the language model run roughly \$0.5M of compute but the vision run only tens of thousands of dollars?**

    1.  Each GPU in the language model run fails more often, so every failure destroys more work.
    2.  Lost progress is priced by what the allocation costs per hour and how much state must be recovered, so up to a day of rework on a 10,000-GPU allocation costs about \$0.5M while a smaller allocation loses far less per day.
    3.  Vision checkpoints are larger than language model checkpoints, which shortens vision recovery.
    4.  Vision runs carry no state beyond their weights, so they can resume from any data position at no cost.

    *Answer*: The correct answer is B. At 10,000 GPUs and about \$2 per GPU-hour, a day of lost progress costs about \$0.5M before schedule delay, while a smaller vision allocation burns far less per hour. The per-device failure rate is the same physics in both runs, so the gap comes from what each hour of the allocation costs. The checkpoint-size claim is reversed, since the 175B checkpoint is terabytes against a single-digit-gigabyte vision checkpoint, and vision runs still carry augmentation and data-order state.

    *Learning Objective*: Explain why the cost of a single failure varies by orders of magnitude across workloads.

3.  **On the 10,000-GPU cluster, about 6.2 failures per day each stall every GPU during recovery, at about \$2 per GPU-hour. An idle eight-GPU hot-spare node costs about \$384 per day. Estimate how much recovery time the spare must save per failure to pay for itself, and state the condition attached to that estimate.**

    *Answer*: Shaving one minute from each recovery is worth about 6.2 failures times 10,000 GPUs times \$2 per hour divided by 60, or roughly \$2,100 per day, so each second saved per failure is worth about \$34 per day and the spare breaks even near 11 seconds saved per failure. The estimate holds only if the spare is refilled before the next failure arrives, about 3.9 hours later, and if the time saved is real recovery time while the fleet waits. At fleet scale, idle capacity that shortens recovery is cheap relative to the GPU-time it protects.

    *Learning Objective*: Calculate the break-even recovery-time saving for a hot-spare node and identify the assumption it depends on.

4.  **True or False: A hot-spare node that pays for itself beside a 10,000-GPU training cluster is also a sound investment beside an eight-GPU job, because the node and its daily cost are identical.**

    *Answer*: False. The spare’s benefit scales with how often failures occur and how many GPUs wait during each recovery. An eight-GPU job fails rarely and idles few GPUs per recovery, so the spare would sit idle far longer than it could save. Scale reverses the verdict on the same hardware.

    *Learning Objective*: Evaluate how cluster scale changes the return on the same fault-tolerance investment.

1.  **A team checkpoints every 30 minutes with asynchronous flushing. It promises a recovery point objective (RPO) of 15 minutes and a recovery time objective (RTO) of 10 minutes, and reloading the checkpoint alone takes 12 minutes. Which assessment is correct?**

    1.  Both promises hold, because the Young-Daly interval already minimizes expected waste.
    2.  The RPO holds because asynchronous flushing removes the write from the critical path, but the RTO fails.
    3.  The RTO holds because detection and warmup overlap with checkpoint reload, but the RPO fails.
    4.  Both promises fail, because a 30-minute interval cannot bound lost progress below 30 minutes without a more frequent durable log or replica, and a 12-minute reload alone exceeds the 10-minute RTO before detection, replacement, and warmup are counted.

    *Answer*: The correct answer is D. Lost progress can reach a full interval, and asynchronous flushing can leave the last durable generation older still, so a 15-minute RPO needs a more frequent durable log or replica. Recovery time covers detection, replacement, restore, and warmup, so a 12-minute reload alone breaks a 10-minute RTO. The Young-Daly interval minimizes expected waste but does not certify these service constraints, and asynchronous flushing shortens the training pause without making the newest checkpoint durable sooner.

    *Learning Objective*: Evaluate whether a checkpoint policy satisfies stated recovery point and recovery time objectives.

2.  **A training cluster quadruples in size from 1,000 GPUs to 4,000 GPUs, reducing its system MTBF by a factor of 4. Assuming checkpoint write time $T_{\text{write}}$ remains constant, calculate by what factor the Young-Daly optimal checkpoint interval $\tau_{\text{opt}}$ changes.**

    *Answer*: Under the Young-Daly formula $\tau_{\text{opt}} = \sqrt{2 \cdot T_{\text{write}} \cdot \text{MTBF}_{\text{system}}}$, the optimal interval scales with the square root of MTBF. When MTBF decreases by a factor of 4 ($\text{MTBF}' = \text{MTBF}/4$), the new optimal interval becomes $\tau_{\text{opt}}' = \sqrt{2 \cdot T_{\text{write}} \cdot (\text{MTBF}/4)} = \frac{1}{2}\tau_{\text{opt}}$. The optimal interval halves (becomes $2\times$ more frequent), not $4\times$, due to the square-root relationship.

    *Learning Objective*: Calculate the mathematical scaling of the Young-Daly optimal checkpoint interval as cluster size increases.

3.  **How does sharded checkpointing (such as in ZeRO-3 or PyTorch FSDP) differ from centralized checkpointing in terms of I/O parallelism and recovery requirements?**

    1.  Sharded checkpointing requires every worker to broadcast its state to all peers before writing, doubling network communication overhead.
    2.  Sharded checkpointing writes a single monolithic file from Rank 0, minimizing storage metadata operations.
    3.  Each worker writes only its locally partitioned parameter and optimizer shard directly to storage in parallel, aggregating storage fabric bandwidth but requiring all shards to be present and consistent during recovery.
    4.  Sharded checkpointing stores only model weights, discarding optimizer state to achieve sub-second write times.

    *Answer*: The correct answer is C. Under ZeRO-3/FSDP sharded checkpointing, each worker saves only its local partition of weights and optimizer states (e.g., $\approx 10$ GB per worker instead of 10 TB total), parallelizing write bandwidth across the cluster. The trade-off is recovery complexity: all worker shards must be present, and changing the worker count upon restart requires remapping and resharding state. Broadcasting state to all peers describes redundant replication. Writing a monolithic file from Rank 0 describes centralized checkpointing. Discarding optimizer state would prevent deterministic optimizer resumption.

    *Learning Objective*: Compare sharded checkpointing with centralized checkpointing in terms of I/O parallelism and recovery complexity.

4.  **Explain the memory composition breakdown of checkpoint files for large language models trained with mixed-precision AdamW, detailing why optimizer states dominate storage requirements.**

    *Answer*: In the chapter’s reference mixed-precision AdamW format, BF16/FP16 weights occupy 2 bytes per parameter, separate FP32 master weights occupy 4 bytes, and the two FP32 moment tensors occupy 8 bytes. Optimizer-side state therefore accounts for 12 of 14 bytes per parameter, about 86 percent, or 840 GB of a 980 GB checkpoint for a 70B model before metadata. Implementations with different state formats require their own payload calculation.

    *Learning Objective*: Analyze the composition of checkpoint storage payloads across model weights and optimizer states.

5.  \*\*Sequence the 6 steps of a standard distributed sharded checkpoint coordination protocol in chronological order:

1.  Coordinator confirms all writes and commits checkpoint metadata
2.  Each worker writes its local state shard directly to persistent storage
3.  Coordinator broadcasts checkpoint completion signal, allowing next barrier clearance
4.  Coordinator broadcasts checkpoint initiation request with a unique checkpoint ID
5.  Each worker reaches a consistent execution state via barrier synchronization
6.  Each worker reports shard write completion back to the coordinator\*\*

*Answer*: The correct sequence is (4) -\> (5) -\> (2) -\> (6) -\> (1) -\> (3). - (4) Coordinator broadcasts checkpoint initiation request with checkpoint ID. - (5) Workers reach consistent step boundary via barrier synchronization. - (2) Workers write their respective state shards in parallel. - (6) Workers report write completion to the coordinator. - (1) Coordinator commits metadata once all shards are verified. - (3) Coordinator broadcasts completion signal so normal training resumes.

6.  **What is the primary advantage of adopting a bounded asynchronous checkpoint consistency model over a strict synchronous checkpoint model in a 10,000-GPU cluster?**

    1.  It can reduce barrier waiting by letting workers progress within a bounded step window while retaining compatible shard versions or replay information to construct a consistent recovery cut.
    2.  It guarantees that all workers write their state at the exact same nanosecond without requiring any communication with a coordinator.
    3.  It eliminates the need for persistent storage by maintaining checkpoints entirely in L2 cache memory.
    4.  It ensures that lost computation after a hardware crash is always zero steps.

    *Answer*: The correct answer is A. A bounded-asynchronous protocol can reduce barrier waiting, but bounded step skew alone does not make saved shards mutually consistent. The manager must retain compatible versions or sufficient replay information to reconstruct a valid cut before publishing a recoverable generation. This differs from asynchronous flushing of one synchronized snapshot, which overlaps I/O without relaxing recovery consistency. The other choices do not provide a valid persistent recovery protocol.

    *Learning Objective*: Evaluate consistency models and two-phase commit protocols for distributed checkpointing.

1.  **A 10,000-GPU training job experiences a GPU failure. The cluster implements cold restart, where $T_{\text{detect}} = 30\text{ s}$, $T_{\text{restart}} = 3\text{ min}$, $T_{\text{load}} = 36\text{ s}$, and $T_{\text{warmup}} = 2\text{ min}$. If the cluster MTBF is 5 hours, what is the daily compute loss incurred solely from recovery time?**

    1.  Approximately 0.5 minutes daily, wasting 5 GPU-hours per day.
    2.  Approximately 6.6 minutes daily, wasting 100 GPU-hours per day.
    3.  Approximately 15 minutes daily, wasting 500 GPU-hours per day.
    4.  Approximately 29.3 minutes daily, wasting roughly 4,880 GPU-hours per day across the fleet.

Across 10,000 GPUs this is $10{,}000\times29.28/60=4{,}880$ GPU-hours, about 2.03 percent of daily capacity. The other choices fail to combine failure frequency, recovery duration, and fleet size.

2.  **Compare a warm restart with a cold restart for a single-GPU failure in a 1,000-GPU cluster in terms of recovery latency, memory state guarantees, and software complexity.**

    *Answer*: A cold restart stops the worker group and restores a valid checkpoint, trading a full reload and warmup for simpler state handling. A warm restart keeps surviving processes, but a replacement must reconstruct state at the survivors’ committed step or the group must roll back to a common recovery point; combining an older shard with advanced survivor state is unsafe. The chapter’s 4–10-minute cold and 30–90-second warm ranges are planning examples, not guarantees. Warm recovery additionally requires runtime support for membership changes and communicator reconstruction, with cold restart as a safety net.

    *Learning Objective*: Compare warm and cold restart mechanisms for distributed training failure recovery.

3.  **In a compute-dominated 1,000-GPU synchronous job, one GPU remains at half speed, reducing useful cluster throughput by approximately half. What comparison determines whether replacing it is worth the interruption?**

    1.  Throughput drops by only 0.1% (1/1000th); the straggler should always be tolerated to avoid restart overhead.
    2.  Compare the useful work lost during replacement, restart, and replay with the work recovered by removing the slowdown over its expected remaining duration.
    3.  Cluster throughput remains 100% because asynchronous gradient buffering absorbs all rank jitter.
    4.  Throughput drops by 100% because any slow rank immediately triggers an NCCL assertion crash.

    *Answer*: The correct answer is B. If the slowdown is expected to persist for $K$ useful updates, replacement pays off when $K(t_{\mathrm{slow}}-t_{\mathrm{healthy}})>T_{\mathrm{restart}}+T_{\mathrm{replay}}$. The restart budget includes waiting for replacement capacity and restoring state. A transient may clear before this threshold; cluster MTBF does not determine the remaining slowdown horizon.

    *Learning Objective*: Evaluate the economic and throughput break-even criteria for proactively replacing stragglers.

Checksums test byte integrity or agreement, while replay, independent computation, invariants and statistical checks provide different evidence about computed results. Coverage must match the declared fault model; no single check establishes end-to-end correctness.

    *Learning Objective*: Evaluate the limitations of hardware ECC and justify the necessity of end-to-end software verification against silent data corruption.
