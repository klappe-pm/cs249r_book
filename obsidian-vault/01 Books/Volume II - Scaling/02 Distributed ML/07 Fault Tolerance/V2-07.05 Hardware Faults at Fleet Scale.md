# V2-07.05 Hardware Faults at Fleet Scale

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-fault-tolerance-hardware-fault-taxonomy

A cosmic ray that flips one bit in a GPU’s high-bandwidth memory and a solder joint that cracks under thermal cycling are physical events, but the recovery system never observes them directly. It observes symptoms: a gradient spike with no process crash, a rank that disappears from the collective, or a node that fails only after it heats under sustained load. The failure taxonomy of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.04 Failure Taxonomy#^sec-fault-tolerance-reliability-reliability-failure-taxonomy-e78c|section 7.3]] already classifies such events by persistence, manifestation, and scope. For hardware, persistence carries most of the operational weight because it decides whether the fleet should retry, quarantine, or replace a component, while manifestation decides whether the fleet notices the fault at all.

ML workloads raise the stakes of each fault. A training step performs trillions of arithmetic operations on state that persists into later steps, so a wrong value can survive beyond the computation that produced it. The damage depends on the affected value and its later use. Under the IEEE 754 format,[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn6|⁶]] a sign-bit flip inverts a weight, while an exponent-bit flip can move a small gradient by many orders of magnitude. Fault-injection studies show that network resilience varies with model, layer, and bit position, so a few faults in vulnerable locations can cost disproportionate accuracy ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-reagen2018|Reagen et al. 2018]]). A valid-looking corrupted value can enter learned state without triggering the process failure that would otherwise initiate recovery.

↪ How an FP16 exponent-bit flip rescales a value by $2^{16}$ and can saturate an attention softmax is developed in **[[05 Reference/Volume II - Scaling/V2 Reliability Foundations#^sec-appdx-reliability-sdc-perturbation|Silent Data Corruption in Attention]]**.

Fleet scale turns these rare device events into routine operating conditions. Smaller geometries and lower operating voltages can reduce the charge needed to disturb a stored value ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-baumann2005|Baumann 2005]]). Fleet studies at Google and Meta found that a small but persistent population of processors, on the order of a few per several thousand machines, computes wrong results without raising any error ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-hochschild2021|Hochschild et al. 2021]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-dixit2021silent|Dixit et al. 2021]]). Studies of accelerator training fleets likewise conclude that rare hardware faults appear often enough that software-level detection and recovery become part of the training system design ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-he2023|He et al. 2023]]). ML system architects must therefore treat hardware as an unreliable substrate and budget for end-to-end integrity checks, replayed computation on high-value paths, and periodic consistency checks as system requirements rather than high-performance computing specialties.

### Fault Persistence and the Fleet Response

^sec-ft-fault-persistence-response

Each persistence class from the taxonomy maps to a different fleet action, from retry for a fault that leaves nothing to repair, through quarantine for one that returns under load, to replacement for one that repeats on every attempt ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.05 Hardware Faults at Fleet Scale#^fig-fault-tolerance-failure-spectrum|figure 5]]). A transient fault, as [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.04 Failure Taxonomy#^sec-fault-tolerance-reliability-reliability-transient-failures-57b4|section 7.3.1]] established, leaves no lasting defect from that event, so the fleet’s question is only whether its effect escaped. A single-event upset, a voltage droop on an unstable power path ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-reddi2013|Reddi and Gupta 2013]]), a timing violation, or a soft error in combinational logic ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-mukherjee2005|Mukherjee et al. 2005]]) can corrupt a tensor, packet, or instruction. Detection and correction can prevent propagation; affected state may otherwise require rollback. During training, an undetected error in weights or gradients can compromise convergence and contaminate subsequent checkpoints ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-he2023|He et al. 2023]]). During stateless inference, an activation error can remain confined to one request ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-mahmoud2020|Mahmoud et al. 2020]]). If that activation enters retained state such as a KV cache, later outputs can also depend on it.

![[90 Assets/Volume II/07 Fault Tolerance/Failure Spectrum 2d19fffb35.svg]]

Figure 5: **The ML Failure Spectrum**: Hardware faults ordered by how long they persist. A transient fault leaves nothing to repair, an intermittent fault returns under the load that exposed it, and a permanent fault repeats on every retry. Persistence decides the fleet response, from retry through quarantine to replacement, and fault tolerance engineering must handle all three to keep a fleet making progress.

^fig-fault-tolerance-failure-spectrum

A permanent fault announces itself through repeatability. The same accelerator, memory cell, or link fails again after retry, often at the same address or in the same workload phase. Manufacturing defects and wear-out mechanisms such as electromigration[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn7|⁷]] and oxide breakdown produce this signature, and the stuck-at fault, in which a signal remains fixed at 0 or 1 regardless of input, is its standard abstract model ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-seong2010|Seong et al. 2010]]). Repeatability helps locate the defect but does not make the result trustworthy. A permanent datapath fault keeps producing wrong gradients until the device is drained from the cluster ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-he2023|He et al. 2023]]), and rerunning the computation on the same device reproduces the error instead of exposing it. The fleet must stop trusting the component, quarantine it, and restore from a checkpoint that predates its first bad write.

Intermittent faults create the most operational ambiguity because they produce evidence and then disappear. A node may pass a reboot test, rejoin the fleet, and fail again only when the next job drives the package into the same thermal, voltage, or communication regime. Cracked solder joints, aging packages, and contamination between contacts create these load-dependent conditions ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-constantinescu2008|Constantinescu 2008]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-rashid2015|Rashid et al. 2015]]), and reduced voltage margins cause timing errors that are hard to reproduce ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-zhang2018thundervolt|Zhang et al. 2018]]). Sporadic errors of this kind can accumulate across iterations and degrade convergence without any explicit failure ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-rashid2015|Rashid et al. 2015]]). An intermittent node should therefore remain suspect until evidence clears it. The fleet drains it from long jobs, correlates its error logs, and readmits it only after it passes stress tests under the load that exposed the fault. Otherwise one marginal component can make validation and recovery untrustworthy for every job that lands on it. Across the three persistence classes, the evidence that exposes a fault also determines the fleet’s response ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.05 Hardware Faults at Fleet Scale#^tbl-fault-types-4bac2d27|table 3]]).

| **Persistence**  | **Fleet signature**                                       | **Detection evidence**                                         | **Fleet response**                                                |
|:-----------------|:----------------------------------------------------------|:---------------------------------------------------------------|:------------------------------------------------------------------|
| **Transient**    | One-time wrong value or lost message; retry succeeds      | Corrected-error counters, checksum mismatches, gradient spikes | Correct or retry; roll back if durable state was contaminated     |
| **Intermittent** | Recurring errors under specific load, heat, or voltage    | Correlated error logs and repeated anomalies on one node       | Drain and quarantine; readmit only after screening under load     |
| **Permanent**    | Reproducible failure at the same device, address, or link | Failed self-test or replay mismatch on the same device         | Replace the component; restore from a checkpoint before the fault |

Table 3: **Hardware Fault Persistence and Fleet Response**: The persistence class of a hardware fault determines the evidence that exposes it and the action the fleet takes. Manifestation is a separate axis: any of the three classes can surface as a crash or as silent corruption ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-constantinescu2008|Constantinescu 2008]]).

### Hardware Lifecycle and the Hazard Rate

^sec-fault-tolerance-reliability-reliability-bathtub-curve-hardware-lifecycle-7d8a

A newly unboxed accelerator rack is far more likely to fail in its first week of service than in its sixth month, and a multi-year-old rack that has endured thousands of thermal cycles becomes fragile again as packages and solder joints fatigue. While persistence classifies a fault after it strikes, the hazard function ${h}({t})$, the failure rate at a given age among components that have survived to that age, describes *when* over a component’s operating lifespan faults are most likely to occur, partitioning hardware longevity into three reliability regimes ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.05 Hardware Faults at Fleet Scale#^fig-bathtub-curve|figure 6]]). The first phase, infant mortality, brings elevated failure rates from manufacturing defects, improper installation, and early-life failure of marginal components. For electronic components it typically lasts days to weeks, which is why burn-in testing[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn8|⁸]] stresses hardware before deployment to precipitate those early failures prior to production use.

After surviving infant mortality, components enter the useful-life phase, where failure rates remain relatively constant under the standard reliability-engineering model ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-birolini2017|Birolini 2017]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-klutke2003|Klutke et al. 2003]]). This phase spans the longest portion of a component’s lifetime and is the regime where the exponential reliability model in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.03 The Mathematics of Inevitable Failure#^eq-single-component-reliability|equation 1]] applies most accurately. For data center GPUs, the useful-life window is an operational planning concept shaped by refresh cycles, cooling, utilization, and observed fleet health rather than a fixed physical duration.

As components age, they enter the wear-out phase, where failure rates increase due to accumulated wear. For GPUs, wear mechanisms include electromigration in circuits, thermal cycling stress on solder joints, and degradation of thermal interface materials. The onset of wear-out depends heavily on operating conditions; components operated at high temperatures or with frequent thermal cycling enter wear-out earlier.

The practical implication for ML systems is that fleet-wide failure rates can depend on age distribution. Under the bathtub model, a new cohort passes through elevated early-life risk, a relatively stable period, and eventual wear-out. Screening, operating conditions, and replacement policy determine how much of that pattern appears in field data. Mixed-age fleets combine cohorts at different stages, so their aggregate hazard need not follow the curve of a single cohort.

![[90 Assets/Volume II/07 Fault Tolerance/Cell 14 Output 1 ea0eff4207.png]]

Figure 6: **The Bathtub Curve**: Hardware failure rates ${h}({t})$ vary over time. (1) Infant mortality: high failure rate initially due to manufacturing defects. (2) Useful life: constant, low failure rate where random failures dominate. (3) Wear-out: increasing failure rate as components age. Burn-in testing aims to filter out infant mortality failures before deployment.

^fig-bathtub-curve

These three hazard regimes in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.05 Hardware Faults at Fleet Scale#^fig-bathtub-curve|figure 6]] translate directly into admission control and maintenance policies. Before assigning new or repaired nodes to a long training run, operators use matrix-multiply, memory, and communication stress tests to expose marginal components. During service, temperature trends, error counts, and performance degradation help identify devices for scheduled replacement. Screening moves failures out of expensive production runs. An infant-mortality failure caught during a few hours of stress testing costs only idle time, while the same failure weeks into a pretraining run forces a checkpoint rollback. For that reason operators often route fresh or repaired nodes to short jobs first. Monitoring then checks whether the constant-rate model remains appropriate as the fleet ages.

### Fleet-Scale Detection and Mitigation

^sec-ft-hardware-fault-detection-mitigation-8f7f

Burn-in screening and lifecycle replacement keep the most failure-prone hardware out of long training runs, but even healthy mid-life devices still suffer random faults that compound across a fleet just as the interruption rates of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.03 The Mathematics of Inevitable Failure#^sec-fault-tolerance-reliability-reliability-mathematics-inevitable-failure-93ef|section 7.2]] do. Field studies of DRAM in large data centers found memory errors frequent enough that error-correcting memory, background scrubbing (periodically rereading memory to correct errors before they accumulate), and error-rate monitoring are standard fleet practice rather than optional hardening ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-schroeder2009|Schroeder et al. 2009]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-sridharan2015|Sridharan et al. 2015]]). Protection consumes some capacity and bandwidth for check bits and scrubbing, but that cost is small compared with a corrupted multi-week run.

Detection works in layers with different coverage and cost. At the hardware layer, error-correcting codes[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn9|⁹]] ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-hamming1950|Hamming 1950]]) correct and detect the memory-error patterns covered by the implemented code, and link-level CRCs[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn10|¹⁰]] check corruption in transit. These protections operate within their enabled storage and transport boundaries; they do not validate an incorrect arithmetic result merely because its bytes arrive intact. Before deployment, built-in self-test and the burn-in screening of the hardware lifecycle expose manufacturing defects and permanent faults ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-bushnell2002|Bushnell and Agrawal 2002]]). During service, operators periodically pull nodes from production and run known-answer stress tests on arithmetic, memory, and interconnect, because defective processors often fail only on particular instruction mixes, data patterns, or operating points ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-hochschild2021|Hochschild et al. 2021]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-dixit2021silent|Dixit et al. 2021]]).

The software layer draws its cheapest evidence from metrics the training loop already emits. Statistical checks on loss, gradient norms, and activations flag silent drift ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-chandola2009|Chandola et al. 2009]]), missed heartbeats identify suspected failures ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-kawazoe-aguilera1997-3f27fe66|Kawazoe Aguilera et al. 1997]]), and watchdog timers catch tasks that stall without crashing ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-pont2002using|Pont and Ong 2002]]). A node that stays alive but runs slowly or erratically, the gray failure of the failure taxonomy, can degrade progress while still meeting a liveness timeout, so [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-distinguishing-stragglers-failures-285d|section 7.9.5]] treats it through straggler detection. Redundant computation adds stronger evidence on selected paths, either periodically or in response to an anomaly, by replaying a step on another device or comparing independently computed results. Its frequency depends on the residual corruption risk, the value of the protected state, and the cost of detecting an error late.

**Checkpoint 7.2: Classifying a hardware fault**

Verify your understanding of the transient, permanent, and intermittent fault categories and the fault, error, failure progression:

**Transient fault**: classify a GPU that produces a wrong result once after a cosmic-ray strike and then computes correctly for the rest of the run, and justify why detection and rollback to a known-good checkpoint, not node replacement, match that fault.

**Intermittent vs. permanent**: distinguish an intermittent fault from a permanent one when both can produce a stuck-at value, including the diagnostic signal that separates them.

**Fault-error-failure chain**: trace a single bit flip through the fault, error, failure chain, identifying where error correction codes and checkpoint-restart each intervene.

**Silent corruption**: explain why silent corruption sits apart from the other fault manifestations even when its underlying fault is an ordinary transient bit flip.

**Self-Check: Question**

1.  A cluster node passes cold-boot diagnostics and memory tests during morning maintenance, but repeatedly produces incorrect matrix multiplication results under sustained thermal load during large-batch backward passes. What type of fault does this represent, and what is the appropriate operational response?

    1.  Transient fault; retry the exact batch on the same node since the fault will disappear automatically.
    2.  Intermittent fault; collect runtime telemetry under load, quarantine the node, and replace or repair it rather than returning it directly to production.
    3.  Permanent stuck-at-0 fault; immediately discard all training checkpoints because the device cannot execute any instructions.
    4.  Software race condition; upgrade the host OS kernel and increase the AllReduce heartbeat timeout threshold.

2.  Compare the impact of a single-bit flip in the sign bit versus a single-bit flip in the exponent bits of an IEEE 754 floating-point weight or gradient tensor during neural network training.

3.  A node that stays alive and keeps answering heartbeats but runs slowly or erratically, so that timeouts never fire, is said to suffer a \_\_\_\_ failure.

4.  How does a permanent stuck-at fault in a specialized accelerator’s Tensor Core multiply-accumulate unit manifest differently during training compared to a traditional processor crash?

    1.  It causes an immediate kernel execution timeout that terminates the local process group within milliseconds.
    2.  It corrupts operating system page tables, forcing an immediate kernel panic and node reboot.
    3.  It triggers a PCIe bus reset that automatically redirects subsequent GEMM operations to host CPU memory.
    4.  It can produce repeatable incorrect values in computations using the defective datapath while the process remains alive.

5.  Because electronic components exhibit a constant failure rate during their useful life phase under the exponential reliability model, cluster operators should assign newly delivered accelerator nodes directly to multi-week foundation model pretraining runs without prior burn-in testing.
