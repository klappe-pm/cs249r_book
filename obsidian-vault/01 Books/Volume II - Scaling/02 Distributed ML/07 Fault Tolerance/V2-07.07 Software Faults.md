# V2-07.07 Software Faults

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-ft-software-faults

A team spends three months testing a large language model (LLM) against complex prompt-level failure cases, only to realize that its preprocessing script kept only the last 512 tokens of each input, silently discarding the system prompt on long requests. The example exposes an ordinary source of ML failure that algorithmic testing can miss. A logic error in a data loader or prompt assembler can preserve valid tensor shapes while changing the computation’s meaning, allowing the pipeline to continue without a crash.

Software faults require a different recovery lens from hardware failures. Hardware faults enter from silicon, electrons, and physical wear; software faults enter through design choices, dependency versions, and pipeline glue. The fault-tolerance problem shifts from replacing a failed component to identifying which valid-looking transformation corrupted data, gradients, or predictions. Every boundary between framework, library, runtime, and distributed system is a place where such a transformation can hide.

### Software Fault Properties and Propagation

^sec-ft-software-fault-properties

A single tensor reference leaked on every training iteration lets a correctly sized job drift toward the device memory limit over hundreds of steps and then crash with an out-of-memory error far from the code that leaked it. Across ML frameworks, software faults of this kind span logic errors, resource leaks, concurrency bugs, and integration mismatches that propagate across system boundaries. Race conditions in asynchronous updates can lose or overwrite parameter updates, and deadlocks[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn11|¹¹]] leave workers waiting on messages that never arrive. Because many of these faults surface only under high load, on particular hardware, or with a specific pairing of a high-level framework and a low-level numerical library such as cuDNN, root-cause analysis must treat the model code, the runtime, and its dependencies as one versioned artifact.

### Software Fault Detection and Prevention

^sec-ft-software-fault-detection-prevention

The prompt-truncation bug from the opening example and the memory or synchronization bugs above should never survive unchallenged into a multi-week run. Because many software faults leave the pipeline running while corrupting inputs or gradients, each verification gate must establish which invariant holds and which recovery action is safe when it fails. A unit test catches the tokenizer boundary before launch, an integration replay verifies that a recorded batch reproduces the expected shapes and state on known-good hardware, and a fault-injection test verifies that a corrupted buffer or lost worker triggers rollback before tainting committed state.

Several of these gates also test the recovery machinery itself before an incident relies on it. A restore drill verifies a checkpoint manifest, the record that names every saved shard and the training step they share ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-reliability-reliability-distributed-checkpointing-5dcc|section 7.8.5.2]]). A membership fault-injection test kills or partitions a worker and checks that, once replaced, the stale process can no longer write state the job will trust. The epoch, lease, and fencing rules of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-recovery-procedures-002d|section 7.9.2]] enforce that guarantee by stamping every write with the current membership counter, so storage rejects any write that carries an older one. Every recovery drill is judged against two bounds formalized in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-reliability-reliability-checkpoint-restart-fundamentals-0ac2|section 7.8]]: how much completed work a failure may lose and how long recovery may take before useful execution resumes. Across all six gates, each test earns its place through the operational decision it authorizes ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.07 Software Faults#^tbl-software-faults-summary-ft|table 4]]).

| **Reliability evidence**       | **Invariant exercised**                                                            | **Decision enabled**                                      |
|:-------------------------------|:-----------------------------------------------------------------------------------|:----------------------------------------------------------|
| **Boundary unit test**         | Tokenizer limits, tensor shapes, masks, and step metadata remain valid             | Reject the change before distributed execution            |
| **Deterministic replay**       | A recorded batch produces equivalent state on known-good hardware                  | Separate input or software defects from suspect hardware  |
| **Checkpoint restore drill**   | A committed manifest restores every shard and resumes at its named step            | Accept the generation as satisfying the recovery contract |
| **Membership fault injection** | A killed or partitioned worker loses ownership and cannot write after replacement  | Validate ownership handoff and communicator rebuild       |
| **Corruption injection**       | A changed shard, reduced buffer, or checkpoint fails the intended verifier         | Block the optimizer step or roll back before propagation  |
| **Dependency rollback test**   | A versioned runtime and artifact set can return to the last known-good combination | Authorize automated rollback instead of manual repair     |

Table 4: **Reliability Evidence and Recovery Decisions**: Tests earn operational value when each one establishes an invariant and authorizes a specific rejection, rollback, isolation, or restore decision.

^tbl-software-faults-summary-ft

These safeguards matter only when each gate targets a concrete corruption path. A test that checks only whether the tokenizer runs is too weak; it must assert that system prompts, labels, masks, and sequence-length metadata survive preprocessing with the intended semantics. Integration replay then follows one recorded batch through loading, sharding, collation, and model input construction. Fault injection tests whether the detector fires before the protected commit and whether recovery stays within the named bounds on lost work and recovery time for the injected fault. Restore drills, stale-writer rejection, and corrupted-shard rejection therefore provide evidence that generic build success cannot supply, and [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.15 Fault Injection Tools and Frameworks#^sec-ft-fault-injection-tools-frameworks|section 7.14]] exercises those claims directly once the recovery paths themselves have been built. Before building those paths, however, a fleet must decide how much protection each workload is worth.

**Self-Check: Question**

1.  Why are GPU memory leaks in 70B+ parameter distributed training pipelines particularly destructive and difficult to diagnose compared to standard CPU memory leaks?

    1.  GPU memory is dynamically swapped to NVMe disk automatically, causing unpredictable I/O thrashing rather than out-of-memory errors.
    2.  GPU allocators immediately throw segmentation faults upon the first unreleased tensor, preventing any batch execution.
    3.  Accelerator memory is scarce (40–80 GB per device) and shared across weights, optimizer state, and activations; a small leak per batch gradually builds over hundreds of steps until triggering an un-checkpointed OOM crash mid-run.
    4.  GPU memory leaks only occur when using mixed-precision BF16 formats and disappear entirely when switching to FP32 weights.

2.  Contrast a pipeline deadlock with a data race condition in distributed parallel training in terms of their system symptoms and impact on model convergence.

3.  Justify why a silent data preprocessing defect (such as unintended prompt truncation or incorrect token masking) presents a much higher compute and financial risk than a syntax error that crashes on the first batch.

4.  A preprocessing change silently truncates prompts and discards the system prompt. Sequence the reliability gates in the order that should catch the defect, from earliest and cheapest to the final proof that recovery works:

<!-- -->

1.  A fault-injection test showing that the resulting alert blocks publication or rolls back to a known-good state
2.  A boundary unit test asserting that tokenizer limits, system prompts, and masks survive preprocessing
3.  An integration replay that follows one recorded batch through loading, sharding, collation, and model input construction
