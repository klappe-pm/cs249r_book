# V2-07.15 Fault Injection Tools and Frameworks

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-ft-fault-injection-tools-frameworks

An injected failure is useful evidence only when it resembles the production failure the system must survive. A multi-node training cluster that claims to tolerate network partitions should have that connection severed in a staging environment so engineers can observe what the orchestration layer does. Fault injection is the engineering discipline of deliberately perturbing a system to empirically verify that robustness mechanisms work before production traffic discovers the gap. Fault-injection tools for tensors and accelerators cover bit flips, corrupted tensor values, and accelerator-oriented failures ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-chen2020tensorfi|Chen et al. 2020]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-tsai2021|Tsai et al. 2021]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-grafe2023|Gräfe et al. 2023]]), while network partitions, latency injection, dependency termination, and API-response faults belong to chaos and distributed-systems testing practice ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-basiri2016|Basiri et al. 2016]]).

An injection experiment is evidence only at the level where it injects. Its fault model names the originating disturbance, such as a transient single-bit upset or a permanent multi-bit defect, and its error model names the corrupted state that results. Results for transient single-bit faults therefore do not establish resilience to permanent multi-bit defects ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-sangchoolie2017|Sangchoolie et al. 2017]]). The injection level also decides which masking the experiment includes. Hardware absorbs many physical disturbances before software sees them, in unused units, overwritten values, and dead instructions ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-mohanram2003|Mohanram and Touba 2003]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-ko2021|Ko 2021]]). Hardware-based injection through field-programmable gate array (FPGA) emulation or particle-beam exposure ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-velazco2010|Velazco et al. 2010]]) passes through that masking, while software tools such as PyTorchFI ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-mahmoud2020|Mahmoud et al. 2020]]) perturb weights, activations, and gradients directly. They cover many model states quickly, but by skipping the masking they can overstate how often a physical fault corrupts the model. Frameworks such as Fidelity ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-he2020fidelity|He et al. 2020]]) narrow that abstraction gap by mapping hardware faults to the software-visible errors they produce. A tensor mutation still tests how the software responds to a corrupted value; on its own, it does not estimate production vulnerability.

For fleet recovery, the most valuable experiments inject faults at the level where recovery decisions are made. Killing a rank in the middle of a collective or delaying its heartbeat past the timeout exercises the detection layers of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-failure-detection-mechanisms-efed|section 7.9.1]]. Partitioning a node from the rendezvous service exercises the membership and fencing rules of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-recovery-procedures-002d|section 7.9.2]]. Corrupting one checkpoint shard exercises the manifest check of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-reliability-reliability-distributed-checkpointing-5dcc|section 7.8.5.2]]. Each of these experiments tests one row of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.07 Software Faults#^tbl-software-faults-summary-ft|table 4]]. Running these experiments continuously in staging, and in controlled form in production, keeps rarely executed recovery code from decaying between real incidents ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-basiri2016|Basiri et al. 2016]]). A recovery path is trustworthy only for the fault model it has been exercised against, which is why the case studies that follow report both the failures production fleets met and the machinery that absorbed them.

**Self-Check: Question**

1.  Why might a software-based fault injection framework (such as PyTorchFI) overestimate a neural network’s vulnerability to radiation-induced soft errors when compared against physical beam testing on real silicon?

    1.  Software-based tools only inject faults into 8-bit integer quantized models, whereas physical radiation only affects 64-bit floating point registers.
    2.  Physical radiation only damages power delivery networks and never alters logic gate states in operational GPUs.
    3.  Software injection tools can only simulate permanent stuck-at faults and cannot model transient bit flips.
    4.  Software injection mutates high-level tensor variables directly, completely bypassing microarchitectural and circuit-level masking (such as ECC correction, speculative instruction discarding, and dead registers) that absorb soft errors in hardware.

2.  Explain why killing a rank mid-collective, partitioning a node from the rendezvous service, and corrupting one checkpoint shard are more valuable fleet-recovery experiments than tensor bit flips alone.

3.  Software-based fault injection frameworks are universally preferred over FPGA-based injection for production resilience certification because software tools capture register-level gate timing violations and physical alpha-particle strikes with higher fidelity.

4.  Explain how fault-injection frameworks such as Fidelity bridge the abstraction gap between low-level hardware faults and high-level software models.
