# V2-07.18 Summary

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-fault-tolerance-reliability-reliability-summary-48b0

Fault tolerance turns the statistical expectation of hardware failure into a manageable operational routine. Individual component reliability compounds across thousands of devices, driving system-level MTBF from years down to hours. At fleet scale, systems must bound lost work and recovery delay through recovery that is automatic, fast, and minimally disruptive to training or serving.

In training, progress is only as safe as the last state the fleet can prove it can restore. Checkpointing bounds lost work, and the Young-Daly interval ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-ft-young-daly-interval|equation 7]]) prices that bound against write cost, shrinking only with the square root of a falling MTBF. Even at that optimum, under independent failures and a fixed write time, the share of compute lost to saves and rework grows with the square root of cluster size. RPO and RTO turn the expected-value optimum into a service contract. A manifest published last defines which generation exists, and fencing at the resource boundary decides who may still write to it. The retries that recovery triggers stay safe only when each operation is idempotent, inherits its caller’s deadline, and draws on one shared retry budget, so the response cannot amplify the incident. Elastic recovery then trades capacity for continuity, valid only while the data, batch-size, and optimizer invariants survive the resize.

Serving inverts the budget. Training can spend minutes restoring state that satisfies its optimization contract; an interactive request has milliseconds, so serving buys availability with ready replicas and decides in advance which state it will rebuild, replicate, or abandon. The KV cache is the clearest case, derived state that can be reconstructed from retained history only when the latency budget allows. When neither redundancy nor reconstruction fits that budget, graceful degradation keeps the service useful by sacrificing a named property that was validated before the incident.

Recovery depends on evidence about both the failure and the state being restored. A loss spike can originate in hardware, data, numerical behavior, or synchronization. Suspect state can justify a pause or rollback while investigation continues; attributing the cause to a device requires corroborating telemetry, replay, or integrity evidence. Restore drills and fault injection then test whether the selected response actually preserves valid state and meets its recovery budget. Passing those tests establishes evidence for the exercised fault model, rather than a guarantee against every failure.

**Key Takeaways: Failure is normal operation**

- **Scale makes failure routine**: A 10,000-GPU cluster encounters hardware failures every few hours under the chapter’s component-rate assumptions; software must treat failure as a normal state.
- **Liveness is not correctness**: A gray failure keeps answering heartbeats while every peer waits on it, and silent data corruption passes ECC while feeding wrong gradients into a correct AllReduce, so detection needs progress measurements and check-and-verify evidence beside liveness checks.
- **Recovery is a contract**: RPO bounds lost progress, RTO bounds recovery delay, MTTR combines with MTBF to determine steady-state availability, a manifest identifies committed state, and fencing prevents an expired worker epoch from writing after replacement.
- **Checkpoint cadence balances two costs**: Under the first-order assumptions, ${T^\ast_{\text{ckpt}}} = \sqrt{2 \cdot {T_{\text{write}}} \cdot {\text{MTBF}_{\text{system}}}}$ balances checkpoint write overhead against expected rework; for the 175B running example on a 10,000-GPU cluster it lands near 13.8 min. The selected interval must also meet limits on lost progress; recovery delay needs its own budget.
- **Elasticity enables persistence**: Designing training jobs to be “elastic” (rebuilding communication groups and rebalancing data shards as traced in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.11 Elastic Recovery#^fig-elastic-flow|figure 16]]) can reduce waiting for replacement capacity. The runtime must preserve valid state and data coverage, and either preserve batch size or validate the changed optimization policy. Checkpoint cadence still determines how much work must be replayed.
- **Serving recovery follows the state budget**: Preserve authoritative history, then choose reconstruction, checkpointing, or replication for derived state according to the latency contract ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^tbl-stateful-failover|table 13]]). A ready replacement provides useful service only when it can also recover the context the request needs.
- **Degradation is a designed mode**: When recovery cannot finish inside the latency budget, a fallback validated in advance (a smaller model, cached results, default features, or shed low-priority load) keeps the service useful, provided monitoring exposes how much quality was traded away.

^callout-takeaways--7-17-044f06eb

Fault tolerance makes the cost of coordination a deliberate part of the execution budget. **[[05 Reference/Volume II - Scaling/V2 The C³ Taxonomy#^sec-appdx-c3-taxonomy-case-3|Case 3 on coordination overhead]]** works a complete coordination-bound diagnosis, attributing a large run’s lost wall time to checkpoints, failures, pipeline bubbles, and scheduling. In the Fleet Law (**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^eq-fleet-law|equation 1.3]]**), checkpoint pauses, detection timeouts, and restarts all land in the synchronization term ${T_{\text{sync}}}({N})$, and in goodput accounting they are runtime losses. The chapter’s mechanisms spend Coordination (${C}_3$) so that a failure does not erase completed Compute, and asynchronous checkpointing and warm restart earn their complexity by moving part of that synchronization cost into ${T_{\text{overlap}}}$ or shrinking it outright. The useful comparison is between time spent preserving and validating state during normal operation and time lost reconstructing trustworthy execution after a failure. A cheaper recovery mechanism is valuable only when it still meets the workload’s limits on lost progress, response delay, and degraded quality.

**What’s Next: From resilience to resource management**

Keeping the fleet running despite inevitable hardware failures requires three layers: checkpointing preserves progress, elasticity absorbs node losses, and redundancy protects stateful serving sessions. Each layer also assumed capacity the job cannot grant itself, whether replacement nodes held in reserve, a hot spare kept idle, spot capacity that may vanish, or replicas placed across independent failure domains. Providing that capacity takes allocation decisions, made while many jobs compete for the same fleet, from month-long training runs to hour-long experiments. A fault-tolerant cluster therefore still needs orchestration to decide which jobs run where, when to preempt, and how to share capacity fairly among them.
