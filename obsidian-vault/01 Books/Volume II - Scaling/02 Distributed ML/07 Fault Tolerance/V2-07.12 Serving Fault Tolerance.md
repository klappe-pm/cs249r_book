# V2-07.12 Serving Fault Tolerance

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-fault-tolerance-reliability-reliability-serving-fault-tolerance-5375

When users ask a voice assistant to turn off the lights, they will not tolerate a five-minute pause while the inference server reloads from a checkpoint. Serving presents a different challenge, because users expect millisecond-level responsiveness even when backend GPUs crash. The C³ budget for fault tolerance shifts accordingly. Training pays for coordination in synchronization time so that a failure does not erase completed compute, while serving pays in standing redundant compute and in routing coordination so that a failure does not break a latency contract.

A serving replica is a runnable copy of the model that can accept requests; the routing layer chooses a replica, and a readiness check determines whether that replica can serve successfully. Replicas may share external state stores or keep request state in accelerator memory, so replacing compute does not necessarily replace the state a request needs. Serving fault tolerance asks how those mechanisms behave when replicas, GPUs, or state stores fail under live latency budgets.

### Stateless Vs. Stateful Serving

^sec-fault-tolerance-reliability-reliability-stateless-vs-stateful-serving-0a60

The first serving decision is where request state lives, because that choice determines whether failover is a retry or a state-reconstruction problem. A stateless model worker retains no required per-session state between requests. It obtains the necessary context from the request or an external state store, so another ready worker can process the same request. Because the external store carries the session history, a stateful application can still use stateless model workers, although that store remains a reliability dependency.

The stateless pattern appears when the input itself carries all context: an image classifier processes one image, an object detector processes one frame, a single-turn text classifier processes one snippet, and an embedding service maps one input to one vector. Fault tolerance can then focus on replica health and request routing. Redundant replicas serve requests in parallel, load balancing sends traffic only to healthy replicas, health checks remove failed replicas from rotation, and automatic replacement starts a new replica when capacity falls. When a replica fails, in-flight requests to that replica can be retried elsewhere, because no quality-bearing session state has been lost.

Stateless serving offers the simpler architecture when the application permits it. However, many ML applications inherently require state across requests. Consider a chatbot. A single-turn question-answering system can operate statelessly, processing each question independently. A conversational assistant must preserve its history somewhere, but the model worker can still be stateless if each request carries the complete history or reads it from a durable external store. Worker-local state creates a stronger dependency when later requests rely on information available only at the selected replica.

Stateful serving appears when later work depends on retained session state. For a transformer, the key-value (KV) cache stores attention keys and values computed for earlier tokens so the worker can reuse them while generating subsequent tokens. This cache is derived state. If the authoritative token history and compatible model version remain available, a replacement can recompute it by processing that history again. Losing the history itself is a different failure because cache reconstruction no longer has its required input. Streaming speech recognition similarly maintains context from previous audio, recommendation sessions accumulate user context, and interactive editing maintains document state across edits.

The fault-tolerance consequence is that failure loses quality-bearing state rather than serving capacity alone. KV cache loss requires reprocessing previous turns, session context loss forces users to repeat previous interactions, and accumulated user state loss degrades quality when context is unavailable. The mitigation choice follows the size, update rate, and quality value of that state. Session affinity routes a session to the same replica, state checkpointing periodically saves session state, state replication maintains a standby copy, and graceful degradation keeps the service available at reduced quality if state cannot be recovered. [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^tbl-stateless-stateful-comparison|Table 12]] contrasts how that state boundary reshapes routing, failure impact, and recovery complexity. Whether the architecture is stateless or stateful, maintaining availability under live latency constraints requires deploying redundant capacity.

↪ How the KV cache grows with sequence length and concurrency until it fills accelerator memory is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-kv-cache-wall|The KV cache wall and memory capacity]]**.

| **Aspect**               |      **Stateless serving**       |            **Stateful serving**             |
|:-------------------------|:--------------------------------:|:-------------------------------------------:|
| **Request routing**      |           Any replica            |           Session-affine replica            |
| **Failure impact**       |     Retry on another replica     |            Potential state loss             |
| **Recovery complexity**  |     Restart and load weights     |     Reload state + reconstruct context      |
| **Redundancy approach**  |      Active-active replicas      |         Replicated state + standby          |
| **Work after detection** | Route or retry to a ready worker | Recover required state, then route or retry |

### Redundancy and Replication

^sec-fault-tolerance-reliability-reliability-redundancy-replication-2239

Redundancy buys availability only when replica placement and spare capacity match the failure domain being defended against. Turning multiple model copies into uninterrupted service requires sizing the replica count to the availability target, choosing how live traffic is split across healthy and standby workers, and placing those replicas across independent failure domains.

#### Availability Calculations

^sec-fault-tolerance-reliability-reliability-availability-calculations-ef0a

Serving redundancy is the parallel composition of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.03 The Mathematics of Inevitable Failure#^sec-fault-tolerance-reliability-quantitative-analysis|section 7.2.1]] applied to interchangeable replicas, with availability in place of survival probability. For a single replica with availability ${A_{\text{single}}}$ (probability of being operational at any given time), [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^eq-availability-redundancy|equation 12]] quantifies how multiple independent replicas achieve higher system availability:

$$
{A_{\text{system}}}= 1 - (1 - {A_{\text{single}}})^{k} \tag{12}
$$

^eq-availability-redundancy

where ${k}$ is the number of replicas. For a service whose single replica is available 99 percent of the time, redundancy compounds as follows.

For a single replica, availability of 99 percent corresponds to 3.65 days of downtime per year. Adding independent replicas changes the tail of the failure distribution quickly. Two replicas give 99.99 percent, or 52.6 minutes of downtime per year, and three replicas give 99.9999 percent, or 31.5 seconds. The arithmetic assumes independent failures and enough capacity on any surviving replica to meet the service target; shared power, shared networking, and shared software bugs reduce actual availability below these theoretical values.

#### Replication Strategies

^sec-fault-tolerance-reliability-reliability-replication-strategies-aaa2

The availability equation says how much redundancy can help; the replication topology determines how that redundancy behaves under normal execution and sudden hardware loss. Two fundamental designs make opposite bets ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^fig-serving-redundancy|figure 17]]). Active-active replication splits ingress traffic evenly across live replicas, one-third each for three, which keeps every device busy but requires spare headroom so the survivors can absorb a failed replica’s share. Active-passive replication sends all traffic to a designated primary and keeps a pre-warmed standby whose weights remain loaded in accelerator memory, which makes failover fast at the expense of a device that serves nothing while the primary is healthy.

![[90 Assets/Volume II/07 Fault Tolerance/Serving Redundancy 8a8ffc4ff8.svg]]

Figure 17: **Serving Redundancy Strategies**: Active-active (left) splits traffic across three replicas, each carrying about one-third, which uses every device but requires enough headroom for the survivors to absorb a failed replica’s share. Active-passive (right) sends all traffic to one primary and keeps a warm standby with weights already loaded, which simplifies failover at the cost of capacity that serves nothing while the primary is healthy.

^fig-serving-redundancy

Geographic replication extends the same choice across regions. It protects against data-center or regional network failures, but requests routed to distant regions pay additional latency, and the active-active headroom problem reappears at regional scale. When a region fails, the surviving regions must absorb its traffic and, for stateful services, rebuild its sessions, so each region either carries spare capacity sized for the largest region it may absorb or accepts degraded latency during the failover. Traffic returns to a recovered region gradually, because its caches and warm replicas start empty and an abrupt shift back would overload it and trigger the same failover again. Multi-tier designs combine several replication policies at once: edge caches replicate for latency, regional serving clusters replicate for availability, and a global primary or coordination layer preserves consistency and freshness.

#### Replica Placement and Failure Domains

^sec-fault-tolerance-reliability-reliability-replica-placement-failure-domains-73a7

Effective redundancy requires placing replicas in independent failure domains. Different machines tolerate individual machine failures; different racks tolerate rack-level failures from power or top-of-rack switch issues; different availability zones, the separately powered and networked sections of one region, tolerate data-center-section failures; and different regions tolerate entire data-center failures. The independence level should match the availability requirement and cost constraint. Regional replication is expensive because it duplicates compute and network capacity, but it is necessary when regional failure must not become user-visible downtime. Placement alone, however, only creates the possibility of recovery; the serving system still needs a control loop that notices the failure, removes the affected replica from traffic, and preserves enough state that the user-visible service continues with bounded degradation.

### Failover Mechanisms

^sec-fault-tolerance-reliability-reliability-failover-mechanisms-5ddd

When a replica fails, traffic must be redirected to healthy replicas, and the speed and reliability of that redirection determine how much of the failure users see. The mechanism decomposes into two questions: how the system decides that a replica can no longer serve, and what happens to stateful sessions already attached to it.

#### Health Checking

^sec-fault-tolerance-reliability-reliability-health-checking-a604

Health checks decide when traffic should move. The liveness and readiness probes of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-failure-detection-mechanisms-efed|section 7.9.1]] apply to a serving replica, where readiness means that its weights are loaded, its accelerator is initialized, warmup has completed, and dependencies such as feature stores (the services that supply precomputed model input features) are reachable. Serving adds an inference check, which runs a known input through the model and compares the output with the expected result, catching the silent failure in which the process is healthy but its answers are wrong. The load balancer acts on these signals.

↪ What each probe must test on an accelerator replica, from process liveness to a fixed-prompt inference check, is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^sec-inference-scale-health-checking-failover-070e|Health checking and failover]]**.

The probe parameters set the failover budget. With a 5 s check interval, a 2 s timeout, and a failure threshold of 3 missed probes, a crashed replica leaves rotation 12–17 s after it fails, depending on where the crash falls between probes. Every request routed to it in that window fails or waits for a client retry. Replica-level failover on this time scale therefore protects subsequent traffic, not the requests that hit the crash; a request with a millisecond budget can still meet it only through a retry on another ready replica within its remaining deadline. Shortening the interval or lowering the threshold speeds failover but raises the false-positive rate, marking healthy replicas unhealthy during transient stalls and removing capacity exactly when load is high. A success threshold of 2 clean probes applies the same caution in reverse, holding a recovered replica out of rotation until it has proved stable.

#### Session Affinity and Stateful Failover

^sec-fault-tolerance-reliability-reliability-session-affinity-stateful-failover-27b2

For stateful serving, session affinity routes all requests within a session to the same replica. Load balancers maintain session-to-replica mapping through sticky sessions implemented with cookies, headers, or IP hashing. Affinity preserves locality but supplies no replacement copy when that replica fails. Checkpointing saves session state periodically, replication copies it to a standby, and external systems such as Redis or Memcached move it outside the model worker. The external store still needs its own availability and durability contract. Accepting state loss is valid only when the service can reconstruct derived state from retained history or explicitly begin a reduced-context session. Which option fits a workload depends on state size, update frequency, and the quality impact of state loss, as [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^tbl-stateful-failover|table 13]] summarizes across the four common approaches.

| **Approach**                | **Recovery latency** |              **State guarantee**               | **Operational complexity** |
|:----------------------------|:--------------------:|:----------------------------------------------:|:--------------------------:|
| **State loss**              |         Fast         |                      None                      |            Low             |
| **Checkpointing**           |        Medium        | Consistent snapshot; later updates may be lost |           Medium           |
| **Synchronous replication** |         Fast         |                     Strong                     |            High            |
| **Distributed state**       |         Fast         |                  Configurable                  |           Medium           |

Table 13: **Stateful Failover Approaches**: Recovery latency, state guarantees, and operational complexity distinguish four approaches to session-state failover. Checkpoint recovery may lose updates after the saved snapshot. Distributed storage can provide different consistency contracts, and synchronous replication provides its promised guarantee only under the specified acknowledgment and fault model.

^tbl-stateful-failover

### Model-Specific Serving Fault Tolerance

^sec-fault-tolerance-reliability-reliability-modelspecific-serving-fault-tolerance-3245

Retrying a failed image classification request on another replica loses no session state, whereas losing the replica that holds a multi-turn LLM conversation drops gigabytes of live attention state and losing a recommendation feature store leaves the ranker with stale user signals. Model-specific serving policies therefore start from a state-loss budget: which state can be rebuilt within the latency deadline, which state must be replicated in advance, and which state may be degraded temporarily without violating the product contract. Each of the three common serving regimes answers that budget differently, setting both its fault-tolerance policy and its degradation path ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^tbl-serving-recovery-state-invariants|table 14]]).

| **Serving workload** | **State expensive to lose**                    | **Fault-tolerance policy**                                                                                  | **Degradation path**                                                   |
|:---------------------|:-----------------------------------------------|:------------------------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------|
| LLM conversation     | KV cache, conversation context, prefix state   | Replicate or checkpoint high-value session state; regenerate only when the latency budget allows.           | Rebuild from transcript, reuse cached prefixes, or ask for retry.      |
| Recommendation       | Fresh user features, item features, embeddings | Replicate feature stores, cache hot features, and monitor freshness as a reliability signal.                | Serve stale or default features with measured quality loss.            |
| Vision service       | Preprocessing state, device health, edge input | Retry stateless requests on healthy replicas and fail closed on preprocessing or accelerator-health faults. | Use a smaller local model, defer prediction, or return low confidence. |

Table 14: **Serving Recovery State Invariants**: Serving fault tolerance starts from the state whose loss changes user-visible quality. LLMs protect live context, recommendation systems protect feature freshness, and vision services protect preprocessing and device correctness.

^tbl-serving-recovery-state-invariants

The KV cache[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn19|¹⁹]] can be substantial (gigabytes for long contexts across attention layers). Losing it requires recomputing attention state from the retained token history, which can take seconds to minutes; previously delivered text need not be generated again. During an in-flight response, recovery must also know which output tokens the client has already received so a retry does not silently duplicate or replace part of the response.

![[90 Assets/Volume II/07 Fault Tolerance/Fault Tolerance KV Live State Ladder a355cb981d.svg]]

*Two rows. An image retry shows only a thin baseline mark labeled no state lost. An LLM conversation shows a full-width blue bar labeled 43 GB.*

*A retried image loses nothing; a lost conversation loses 43 GB of KV cache.*

LLM serving choices trade KV-cache recovery latency against memory and storage overhead. The simplest strategy is to accept regeneration cost by rebuilding KV cache from conversation history after failure, but this can turn a long conversation into a multi-second or multi-minute restart. KV-cache checkpointing saves live state periodically and bounds the amount of regeneration, while KV-cache replication keeps a standby copy for fast failover at the cost of extra memory. Prefix caching, also offered as prompt caching, reuses state for common system prompts and shared context. A compatible cached prefix can reduce reconstruction work if it survives the failure and remains accessible to the replacement worker. Cache reuse alone does not establish a failover guarantee or preserve the session-specific history.

Recommendation serving protects freshness rather than conversational continuity. Recommendations depend on user and item features from feature stores, so feature-store unavailability can either degrade ranking quality or block recommendations entirely. The serving decision is the staleness budget. Replicated feature stores keep recent features available across zones, local caches cover hot features, fallback to stale features accepts measured quality loss, and default features let the service return a lower-quality result when lookup fails. Real-time features such as recent user actions make freshness monitoring part of fault tolerance, because a pipeline that keeps serving old features is available operationally but wrong semantically. Large embedding tables may also sit behind dedicated embedding services, which need their own replication and failover plan.

Vision serving is usually closer to the stateless end of the spectrum because each image or frame can be retried on another replica. That simplicity changes where the checks belong. Thermal throttling threatens latency, while uncorrected memory errors threaten numerical validity; health policy must distinguish those consequences. Preprocessing checks must also prevent invalid resize, crop, color conversion, or normalization from producing apparently valid predictions. When a preprocessing or accelerator-health check fails, the service fails closed, withholding the prediction rather than returning one it cannot trust. At the edge, disconnection can require a validated smaller local model, delayed nonurgent work, or abstention when the available computation cannot meet the prediction contract.

When redundancy cannot preserve full service, the remaining choice depends on the application contract. A validated reduced-capability response can preserve useful availability; if no such response is acceptable, the system must reject or defer the work. Graceful degradation makes the permitted reduction explicit before failure occurs.
