# V2-07.09 Checkpointing and Progress Preservation

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-fault-tolerance-reliability-reliability-checkpoint-restart-fundamentals-0ac2

When a top-of-rack switch dies two weeks into the training run of a 175-billion-parameter model, the cluster loses 64 GPUs instantly. Because a large cluster experiences such interruptions routinely ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.02 Failure Analysis at Scale#^sec-fault-tolerance-reliability-reliability-failure-analysis-scale-6b4b|section 7.1]]), it cannot restart multi-week jobs from scratch; training fault tolerance must preserve state, detect and classify the failure, and resume or resize the worker group. Checkpointing supplies the first of those three obligations, and every detection, restart, and elastic-resizing path later in the chapter depends on the durable snapshot it produces. The first design question is what that snapshot must contain to make a restart valid.

**Definition 7.1: Checkpointing**

***Checkpointing*** is the periodic serialization of the complete training state (parameters, optimizer state, data loader position, and random state) to persistent storage at a recorded training step.

1.  **Significance**: It minimizes lost work after a system failure by trading checkpoint I/O against rework. Writing too often wastes accelerator time on storage traffic; writing too rarely risks replaying many completed steps after a failure. The Young-Daly interval developed in this section chooses the cadence that balances write cost against expected lost work.
2.  **Distinction**: A resumable checkpoint captures a consistent execution state, including optimizer state, random-number generator state, data position, and learning rate schedules. It can use full or incremental storage; bitwise replay additionally requires compatible deterministic execution.
3.  **Common pitfall**: A frequent misconception is that checkpointing is “just writing to disk.” For large models it is a storage-system stress test, because the simultaneous write from thousands of GPUs can trigger a checkpoint storm (definition [4.5](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#dfn-data-storage-checkpoint-storm)) that saturates the shared network and storage bandwidth $({\text{BW}})$.

A checkpoint is useful only if it resumes the recorded step consistently. In distributed training, every shard must belong to the same recoverable state; a collection of files from different steps does not preserve progress. For the interval model, assume that writing a checkpoint completes durably before it becomes available for recovery and that a failure discards the work performed since the last completed checkpoint.

Two recovery objectives turn the requirements of a valid restart into a contract. The recovery point objective (RPO) bounds acceptable lost progress, so checkpoint age and replication lag must fit within it. The recovery time objective (RTO) bounds the delay until useful work resumes, which covers detection, resource replacement, restore, and warmup. A 20-minute checkpoint interval cannot promise an RPO below 20 minutes without a more frequent durable log or replica, and asynchronous flushing can leave the last durable generation older still. A five-minute RTO is impossible if checkpoint reload alone takes eight minutes. These objectives apply to a stated fault model. Corruption discovered after several saves can require rollback beyond the newest durable checkpoint. The Young-Daly interval derived next minimizes expected waste; RPO and RTO impose service constraints that the expected-value optimum must still satisfy ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-beyer2016sre|Beyer et al. 2016]]).

### The Young-Daly Checkpoint Interval

^sec-fault-tolerance-young-daly

When failures are expected during a job, the key engineering decision is how often to write that state, because every save costs I/O time and every unsaved step is work a failure can erase. The Young-Daly formula[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn12|¹²]] (principle [[01 Books/Volume II - Scaling/02 Distributed ML/V2 Distributed ML Principles#^pri-young-daly|13]]) gives a first-order estimate of that balance through a square-root rule:

$$
{T^\ast_{\text{ckpt}}} = \sqrt{2 \cdot {T_{\text{write}}} \cdot {\text{MTBF}_{\text{system}}}} \tag{7}
$$

^eq-ft-young-daly-interval

${T_{\text{write}}}$ in distributed ML training is not the time to flush a small process state; it includes transferring model weights and optimizer state to durable storage. The reference format here stores BF16 weights, separate FP32 master weights, and two FP32 moment tensors per parameter for Adam. A single resumable checkpoint for a 70B-parameter model therefore approaches a terabyte at 14 bytes per parameter; for the later 175B-parameter running example, it exceeds two terabytes. Of those 14 bytes per parameter, the optimizer state[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn13|¹³]] dominates the payload, exactly as in the storage sizing of the same resumable checkpoint in **[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|Checkpoint Storage]]**, so the optimizer state rather than the model weights sets most of ${T_{\text{write}}}$. Reducing ${T_{\text{write}}}$ requires a smaller payload or higher sustained write bandwidth, and ${T_{\text{write}}}$ is the central constraint that determines how tightly the checkpoint interval can be set before I/O overhead displaces productive training compute.

![[90 Assets/Volume II/07 Fault Tolerance/Vol2 Fault Tolerance Margin 002 f67bbbb2c1.svg]]

*Stacked checkpoint payload bar where BF16 weights occupy 14 percent and optimizer state, the FP32 master weights plus Adam moments, occupies 86 percent.*

*Optimizer state, not weights, dominates checkpoint size.*

To see the balance, consider an interval between saves. Doubling that interval approximately halves the checkpoint writes per unit of training, but a failure then loses twice as much work on average. Under the constant-rate, rare-failure approximation, failure occurs approximately uniformly within an interval, so the average lost work is half the interval. When write time is small relative to the interval, the wasted fraction from saving and replaying work is approximately the sum below. Detection, allocation, and restoration time require a separate recovery budget.

$$
{W}({T_{\text{ckpt}}}) \approx \frac{{T_{\text{write}}}}{{T_{\text{ckpt}}}} + \frac{{T_{\text{ckpt}}}}{2 \cdot {\text{MTBF}_{\text{system}}}} \tag{8}
$$

^eq-ft-checkpoint-waste

Setting the first derivative to zero ($\frac{d{W}}{d{T_{\text{ckpt}}}} = -\frac{{T_{\text{write}}}}{{T_{\text{ckpt}}}^2} + \frac{1}{2 \cdot {\text{MTBF}_{\text{system}}}} = 0$) directly yields the square-root minimum of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-ft-young-daly-interval|equation 7]]. As clusters grow, system MTBF drops, so the optimal interval shrinks, demanding higher-bandwidth storage to keep ${T_{\text{write}}}$ small before checkpoint overhead consumes the cluster’s compute capacity. Because the relationship is a square root, halving MTBF tightens the interval by only $\sqrt{2}\approx 1.4\times$, so doubling cluster size does not demand doubling checkpoint I/O bandwidth when checkpoint size and the other assumptions stay fixed. Substituting the optimum back into [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-ft-checkpoint-waste|equation 8]] gives a minimum waste of $\sqrt{2{T_{\text{write}}}/{\text{MTBF}_{\text{system}}}}$. Because ${\text{MTBF}_{\text{system}}}$ falls as $1/{N}$ under independent failures, that optimized overhead grows as $\sqrt{{N}}$, and doubling the cluster raises it by a factor of $\sqrt{2}$ even though the interval itself adapts.

↩︎ The per-tier storage bandwidths that bound how quickly a checkpoint can be written are established in **[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-hierarchy|The ML Storage Hierarchy]]**.

### Checkpoint Interval from Failure Analysis

^sec-fault-tolerance-reliability-reliability-checkpoint-interval-failure-analysis-c28d

The Young-Daly interval of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-ft-young-daly-interval|equation 7]] needs two inputs, the system MTBF and the write time ${T_{\text{write}}}$, and the chapter’s 10,000-GPU cluster supplies both as computed values. The worked cascade ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.03 The Mathematics of Inevitable Failure#^sec-fault-tolerance-reliability-reliability-worked-example-cluster-mtbf-calculation-9255|section 7.2.2]]) put full-system MTBF, including PCIe and network failures (the redundant power supplies add no term), at 3.87 hours. For the write time, the 175B running example’s 2.45 TB resumable checkpoint drains to shared storage at the sustained aggregate write bandwidth this chapter assumes for the cluster, 100 GB/s, which takes 24.5 s. Substituting these into the Young-Daly formula gives a candidate interval for this cluster, which must still satisfy its RPO and RTO.

**Napkin Math 7.2: The Young-Daly optimal interval**

**Problem**: A 10,000-GPU cluster has an MTBF of 3.87 hours. A full model checkpoint takes 24.5 s to write. What is the optimal checkpoint frequency?

**Math**: Apply the Young-Daly interval of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-ft-young-daly-interval|equation 7]] (principle [[01 Books/Volume II - Scaling/02 Distributed ML/V2 Distributed ML Principles#^pri-young-daly|13]]).

1.  **Convert to common units**: ${\text{MTBF}_{\text{system}}} =$ 3.87 hours $\times$ 3600 s/hour = 13932 s.
2.  **Substitute and solve**: With ${T_{\text{write}}} =$ 24.5 s and ${\text{MTBF}_{\text{system}}} =$ 13932 s, the formula gives ${T^\ast_{\text{ckpt}}} \approx$ 826.2 s, or about 13.8 min.

**Systems insight**: At this interval, the checkpoint overhead (time spent saving plus time spent recomputing) is minimized to approximately 5.9 percent. Checkpointing every hour instead would lengthen the expected rework after each failure, wasting about 13.6 percent of the cluster’s capacity.

The result connects measured or estimated interruption rates to checkpoint policy. At this interval, saving and expected replay together consume approximately 5.9 percent of training time in the first-order model, half from writes and half from replay, because at the square-root optimum the two terms of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-ft-checkpoint-waste|equation 8]] are equal. Plotting those two terms for this cluster shows how forgiving the optimum is ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^fig-checkpoint-tradeoff|figure 11]]). Write overhead falls hyperbolically and expected rework climbs linearly, so their sum has a shallow floor around 14 min. An interval slightly off the optimum costs little, while one several times too short or too long costs far more, which is why a rough MTBF estimate still yields a usable schedule. How far the estimate itself can be trusted depends on the simplifying assumptions behind it.

**Systems Perspective 7.3: Young-Daly formula assumptions**

The first-order Young-Daly formula provides valuable intuition but rests on assumptions that may not hold when write times are non-negligible relative to MTBF; the renewal model derived in **[[05 Reference/Volume II - Scaling/V2 Reliability Foundations#^sec-appdx-reliability-daly-2nd-order|Checkpoint Intervals Beyond the First-Order Approximation]]** shows how finite checkpoint time changes the optimum. The assumptions are:

- Exponentially distributed failures: Assumes a constant failure rate. Real hardware follows the bathtub curve, with higher rates during burn-in and wear-out phases.
- Deterministic checkpoint time: Assumes ${T_{\text{write}}}$ is constant. In practice, checkpoint time varies from save to save with storage contention, network congestion, and memory pressure.
- Recovery cost is independent of the chosen interval: A fixed per-failure recovery cost does not change the first-order minimizing interval. Recovery can take longer than checkpoint writing because it also includes job scheduling delays, topology reconstruction, and warmup; it still belongs in the total-waste budget.
- Aggregate interruption process: Independent constant-rate failure sources can contribute to one job-interruption rate. Shared power, cooling, or switch failures require a model of incident frequency and recovery cost; adding per-device rates alone misses those common causes.
- Infinite timeline: Optimizes for long training runs. Short runs, where total time is comparable to MTBF, require different analysis.

When these assumptions are violated, the optimal interval may shift significantly. Restart time adds a per-failure term to total expected waste rather than a cost paid at every checkpoint; it does not replace ${T_{\text{write}}}$ inside [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-ft-young-daly-interval|equation 7]] unless a recovery-aware Daly-style model is explicitly derived and calibrated.

Along an execution timeline, a training run alternates productive compute intervals (${T_{\text{ckpt}}}$) with synchronous save barriers (${T_{\text{write}}}$), and a failure charges two distinct penalties ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^fig-checkpoint-recovery-timeline|figure 12]]). Uncheckpointed progress is discarded as lost rework, and the restart latency (${T_{\text{recovery}}}$) of job scheduling, checkpoint loading, and pipeline warmup follows before useful work resumes. Restart adds scheduling and warmup to reading the saved state back, so total restart time can exceed the checkpoint write time. Recovery latency belongs in the total-waste and service-level objective (SLO) budgets as a per-failure term (perspective [7.3](https://mlsysbook.ai/vol2/07_fault_tolerance/07_fault_tolerance.html#psp-fault-tolerance-young-daly-formula-assumptions)) rather than inside the per-checkpoint write term.

![[90 Assets/Volume II/07 Fault Tolerance/Checkpoint Recovery Timeline 70c8ff51ae.svg]]

Figure 12: **Checkpoint-Recovery Timeline**: A training run alternates productive compute (blue) with durable checkpoint writes (green). When a failure strikes, all compute since the last completed checkpoint is lost (red hatching), and the job must then read the checkpoint and restart (red) before productive compute resumes. A failure therefore costs the rework since the last save plus the recovery latency; the Young-Daly interval trades the first of these against the write time paid at every checkpoint.

### Checkpoint Overhead Analysis

^sec-fault-tolerance-reliability-reliability-checkpoint-overhead-analysis-f5df

The interval calculation chooses *when* the system preserves state; the write path decides what each save costs while training waits. [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-checkpoint-overhead|Equation 9]] generalizes the save-side term of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^eq-ft-checkpoint-waste|equation 8]] to include any pause beyond the write itself:

$$
{f_{\text{ckpt}}}= \frac{{T_{\text{write}}}}{{T_{\text{ckpt}}}} + \frac{{T_{\text{pause}}}}{{T_{\text{ckpt}}}} \tag{9}
$$

^eq-checkpoint-overhead

Here, ${f_{\text{ckpt}}}$ is the dimensionless fraction of time lost to checkpointing, ${T_{\text{write}}}$ is checkpoint write time, ${T_{\text{ckpt}}}$ is the checkpoint interval, and ${T_{\text{pause}}}$ is any training pause beyond the checkpoint write itself. This includes memory allocation, coordination, and serialization. Total first-order waste is then ${W}({T_{\text{ckpt}}}) \approx {f_{\text{ckpt}}}+ {T_{\text{ckpt}}}/(2 \cdot {\text{MTBF}_{\text{system}}})$, so checkpoint overhead in this section means the save side alone, with expected rework counted separately. How large ${f_{\text{ckpt}}}$ becomes depends first on whether training waits for durable storage.

#### Synchronous Vs. Asynchronous Checkpointing

^sec-fault-tolerance-reliability-reliability-synchronous-vs-asynchronous-checkpointing-ecc1

Synchronous checkpointing resumes training only after every worker’s portion reaches durable storage. Asynchronous checkpointing instead pauses the accelerators only long enough to copy the weights and optimizer tensors from GPU memory into host memory or local staging, then flushes that staged copy to remote storage in the background while training continues. The brief device-to-host copy is necessary because the next optimizer step updates the live GPU tensors in place, which would otherwise overwrite state that is still being serialized. **[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-distributed-checkpoint|Synchronous and asynchronous checkpoint writes]]** develops the write path behind both approaches. For recovery, blocking alone does not establish consistency, so the protocol must ensure that every shard belongs to the same recoverable training state. Recovery can use an asynchronous generation only after all required shards reach the storage tier that survives the modeled failure and the coordinator publishes completion. If a failure strikes while the background flush is still in flight, recovery must fall back to the previous committed generation.

A synchronous save pauses every accelerator in the job for the full remote write, and **[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|Checkpoint Storage]]** prices that exposed pause on a slow shared tier. Asynchronous capture shrinks the exposed pause to the local staging copy and moves the remote flush off the critical path, which is why production systems stage checkpoints rather than block on shared storage. The Young-Daly interval computed earlier from a blocking write is therefore the conservative case; a staged save that exposes a shorter pause shifts the optimum toward shorter intervals and lower save overhead, provided each background flush completes within the interval. Write time also varies widely across model types ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^tbl-checkpoint-overhead-by-model|table 6]]). Larger models require longer writes but also earn longer optimal intervals, so save overhead grows only with the square root of write time.

The Archetype A row in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^tbl-checkpoint-overhead-by-model|table 6]] uses the same 14-byte-per-parameter resumable checkpoint (2.45 TB) as the rest of the chapter. Its interval calculation uses the GPU-only cluster MTBF rather than the shorter full-system MTBF of the worked cascade, so the square-root rule gives a longer interval than the Young-Daly notebook. The table keeps the GPU-only basis because its purpose is comparison across model types. Switching every row to the full-system MTBF would shorten each interval, and raise each overhead, by the same square-root factor, leaving the ranking across rows unchanged.

The ResNet-50 and BERT-Large rows count only FP32 weights, so their write times and resulting intervals are lower bounds for a resumable checkpoint. Their intervals of seconds describe the balance for that smaller payload; selecting a recovery cadence requires including optimizer, schedule, and input-stream state. Small-state jobs rarely run on a cluster this large, and their actual storage bandwidth and complete recovery state determine whether saves every few minutes or every epoch have negligible overhead. The large-state rows show why interval selection becomes consequential when each save moves hundreds of gigabytes or terabytes.

These per-model overheads assume the write path is uncontended. When thousands of workers save at the same step, their combined burst becomes the checkpoint storm that **[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|Checkpoint Storage]]** defines and sizes; for recovery, the burst matters because a stalled write delays the generation that a failure would fall back on. Staging hides the write from training, yet a snapshot held only on local staging does not survive loss of its node.

### Checkpoint Storage and Recovery

^sec-fault-tolerance-reliability-reliability-checkpoint-storage-recovery-6634

Writing a checkpoint to node-local NVMe makes the save fast, but if the node itself fails, that local snapshot vanishes along with the hardware it was meant to recover. Writing only to a durable remote filesystem or object store survives the node failure, but pulling multi-terabyte state back across shared storage links slows every recovery. Recovery mechanisms therefore pair tiers from the storage hierarchy. Local NVMe provides fast staging and survivor reads, distributed filesystems provide durability across node failures, and object storage provides long-term retention. Together, the tiers let the saved state both outlast the fault and reload within the recovery budget.

↩︎ Tiered checkpoint storage designs and asynchronous write pipelines are established in **[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.07 Checkpoint Storage#^sec-storage-checkpointing|Checkpoint Storage]]**.

For fault tolerance, checkpoint placement determines which failures the saved state survives, while the restore path determines how quickly that surviving state becomes useful. On the 128-node Archetype A reference cluster, each node holds about 19.1 GB of the 2.45 TB checkpoint for the 175B running example. Reading that share from local NVMe at 5 GB/s takes about 3.8 s, with every node reading in parallel, while pulling the full checkpoint back through shared storage at 100 GB/s aggregate takes about 24.5 s. The local path is faster because it multiplies drive bandwidth by node count, but a sole copy on a lost node cannot restore that node’s shard. The replacement node must read its share from a copy outside the failed domain, such as a distributed filesystem or object store, whose recovery time is set by sustained aggregate reads, network capacity, and deserialization. A sound placement therefore keeps a fast local copy for the survivors and a durable remote copy for whatever the failure took away, and these rates must still be measured under the job’s own load.

### Checkpoint Coordination Patterns

^sec-fault-tolerance-reliability-checkpoint-coordination-patterns-f670

If workers in a sharded training job save their local shards at different steps without coordinating, rolling one failed worker back to its last save invalidates every peer that already consumed gradients or activations from its later steps. Rollbacks then cascade backward through the run in the classic domino effect ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-elnozahy2002survey|Elnozahy et al. 2002]]). Avoiding that cascade requires choosing how workers coordinate across two orthogonal dimensions. Workers can vary in whether they synchronize to capture a consistent cut, a set of per-worker states that could all have existed at the same moment (**coordinated** versus **uncoordinated checkpointing**). They can also vary in whether they funnel state through one writer or persist shards in parallel (centralized versus distributed checkpointing). Because distributed ML workers exchange state at every step, production training relies on **coordinated checkpointing**. In this scheme, workers synchronize at step boundaries or through an explicit two-phase commit protocol, so that all saved shards belong to a single globally consistent recovery line, the consistent cut that every worker rolls back to together. Once coordination guarantees consistency, the remaining architectural decision is how those shards reach persistent storage: whether workers funnel their state through a single coordinator or write their partitions directly in parallel.

#### Centralized Checkpointing

^sec-fault-tolerance-reliability-reliability-centralized-checkpointing-83a7

In centralized checkpointing, workers send their state to a coordinator process that assembles and writes the complete checkpoint. This approach simplifies checkpoint management and can produce self-contained checkpoint files, but all state crosses the coordinator’s network links, and coordinator failure interrupts the save. A streaming writer can avoid buffering the entire checkpoint, although it cannot remove the ingress bottleneck. That bottleneck is structural. The coordinator receives through one node’s network links, so its write time grows with total state volume, whereas independent writers each move only their own share of the state through their own links. The gap between the two patterns therefore widens in proportion to the number of writers. For the 175B running example, the 128 nodes of the reference cluster would funnel 2.45 TB through one node’s links instead of 19.1 GB through each. The pattern is viable while that one path meets the checkpoint budget; state volume and sustained bandwidth determine the limit more directly than a fixed worker count. Centralized checkpointing is therefore attractive when operational simplicity matters more than aggregate bandwidth, whereas distributed and sharded approaches become necessary once the checkpoint itself is a fleet-scale object.

#### Distributed Checkpointing

^sec-fault-tolerance-reliability-reliability-distributed-checkpointing-5dcc

Distributed checkpointing eliminates this coordinator funnel by having each worker persist its own shard directly. [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^fig-distributed-checkpoint-architecture|Figure 13]] contrasts the dataflow topologies. The centralized pattern concentrates traffic at the coordinator’s ingress, while the distributed pattern writes in parallel to local NVMe and drains the shards to remote object storage in the background. With fixed per-worker shard sizes and sufficient independent staging bandwidth, adding workers need not lengthen the local write pause. Shared drain capacity and completion coordination can still limit scaling. A coordinator signals when to checkpoint and confirms completion, but state flows directly from workers to storage without aggregation.

![[90 Assets/Volume II/07 Fault Tolerance/Distributed Checkpoint Architecture 9d5fd51f69.svg]]

Figure 13: **Distributed Checkpoint Architecture**: Centralized vs. sharded checkpoint writes. In the centralized pattern (left), every worker funnels its shard through one coordinator, whose ingress bandwidth and buffering constrain the write path and whose failure halts the save. In the distributed pattern (right), each worker writes its own shard to local NVMe in parallel and a background process drains the shards to remote object storage, so the local blocking write time can remain roughly constant with fixed shard sizes and sufficient staging bandwidth; shared drain capacity still limits completion.

^fig-distributed-checkpoint-architecture

A synchronous version of the coordination protocol proceeds in six steps:

1.  Coordinator broadcasts checkpoint request with checkpoint ID
2.  Each worker reaches a consistent state (barrier synchronization)
3.  Each worker writes an immutable shard to a generation-specific staging prefix and records its byte length and cryptographic digest
4.  Each worker confirms durable write completion to the coordinator
5.  The coordinator writes an immutable manifest after all confirmations; the manifest names the training step, topology, model and optimizer formats, data-loader position, random state, and the length and digest of every shard, then publishes a commit marker or atomic pointer to that manifest
6.  Coordinator broadcasts checkpoint complete, training resumes

The idealized protocol assumes step 2 completes quickly. The barrier, however, waits for the slowest of thousands of arrivals, so a single slow worker can make it dominate the checkpoint pause even when the storage path has ample bandwidth. Measuring arrival skew separately from copying and writing reveals whether coordination or data movement limits the save.

The manifest, not the presence of a directory or a plausible set of shard names, defines a committed checkpoint generation. Restore accepts only a published manifest whose shards all match their recorded lengths and digests; staged shards without that final publication remain unreachable and can be garbage collected. This rule prevents a partially overwritten `latest` directory from masquerading as recoverable state and makes generation rollback explicit. PyTorch Distributed Checkpoint follows this ordering, with storage writers persisting each rank’s data before the coordinator’s `finish()` operation writes the metadata and marks the checkpoint successful, while the storage backend supplies the publication semantics ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-pytorchDistributedCheckpointDocs|PyTorch Contributors 2026a]]).

Steps 3 through 5 are two-phase commit,[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn14|¹⁴]] the classic distributed-systems protocol for making one decision atomic across many participants ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-gray1978|Gray 1978]]), applied to a checkpoint. Steps 3 and 4 form its prepare phase, in which each worker stages its shard and reports success, and step 5 is its commit phase, in which the coordinator durably records the decision by publishing the manifest. The manifest publication rule inherits the protocol’s guarantee and its known weakness. If the coordinator crashes after workers prepare but before it records a decision, the system must not expose those shards as a valid checkpoint, and the prepared participants remain blocked until the original or a replacement coordinator recovers the durable decision. Uncommitted staged shards can be garbage collected only after recovery establishes that no commit decision exists.

Atomic publication also does not by itself make the published shards consistent. Synchronous gradient updates naturally create step boundaries where all workers have applied the same updates, whereas asynchronous training and pipeline parallelism require explicit coordination to define a consistent cut. The set of per-worker states a manifest names is a cut, and the cut is consistent when all of those states could have existed together at one moment of a valid execution. In a consistent cut, no shard reflects an update another shard has not yet seen. If rank 0 saves its shard after step 1000 and rank 1 saves its shard after step 1001, rank 1’s shard carries an update that rank 0’s shard has not applied, so the pair describes a model the job never held and cannot be restored together.

The coordination protocol decides which cuts a manifest can name, and the consistency model the system claims (strict, bounded-asynchronous, or eventual) states whether that consistent cut is fixed at save time or reconstructed at recovery from retained versions. Synchronous training takes the strict model at its natural step boundaries; the weaker models apply when workers advance asynchronously and share no common step at which to save.

**Systems Perspective 7.4: Checkpoint consistency models**

Strict synchronous: All workers checkpoint at exactly the same training step. Provides strongest consistency but highest overhead from barrier synchronization.

Bounded asynchronous: Workers may progress at different rates while the checkpoint manager tracks which snapshots can form a consistent recovery cut. Bounding step skew alone is insufficient, because the system must retain compatible shard versions or enough replay information to reconstruct that cut. Asynchronous flushing can also preserve a single synchronized snapshot while its writes complete in the background, avoiding training stalls without relaxing recovery consistency.

Eventual consistency: Workers save independently and recovery attempts to reconcile their versions. A usable design must retain enough compatible versions or replay information to reconstruct a valid state; arbitrary recent shards do not necessarily form a recoverable generation. Reduced coordination at save time therefore transfers work and storage requirements to recovery.

#### Sharded Checkpointing

^sec-fault-tolerance-reliability-reliability-sharded-checkpointing-58d0

Modern distributed training frameworks partition model state across workers using techniques like ZeRO and FSDP, which shard parameters, gradients, and optimizer state instead of replicating them on every data-parallel worker. In these configurations, no single worker holds complete model state. Each worker holds only its assigned parameter shard plus corresponding optimizer state.

↩︎ How ZeRO and FSDP partition training state across data-parallel workers is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-memoryefficient-data-parallelism-zero-fsdp-0e69|Memory-efficient data parallelism with ZeRO and FSDP]]**.

Sharded checkpointing[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn15|¹⁵]] ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-rajbhandari2020|Rajbhandari et al. 2020]]) uses this distribution. Each worker writes only its shard, which divides the per-worker write volume by the number of shards. Recovery loads shards and redistributes state to workers based on the recovery configuration.

Dividing state across the fleet keeps per-worker saves small even for multi-terabyte models. A 175B parameter model with a 2.45 TB checkpoint distributed across 1,024 workers requires each worker to write only 2.4 GB, achievable in seconds with local NVMe storage. When elastic scaling or hardware replacement changes the worker count between save and restore, shard redistribution must remap the saved partitions to the new worker configuration, which is why frameworks need flexible resharding support to recover across topology changes. Yet possessing a valid checkpoint is only half the recovery path. Sharding distributes the write work and staging controls the shared I/O burst, but the system must still detect the failure, trigger restoration, and coordinate the distributed shards before training can resume. The speed of detection and recovery therefore governs the cost of the interruption.
