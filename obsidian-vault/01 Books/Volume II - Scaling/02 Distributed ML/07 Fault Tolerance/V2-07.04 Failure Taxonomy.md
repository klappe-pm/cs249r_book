# V2-07.04 Failure Taxonomy

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-fault-tolerance-reliability-reliability-failure-taxonomy-e78c

A network partition that clears in seconds and a permanent GPU failure both interrupt a training step, yet retrying the first succeeds while retrying the second wastes cluster time on dead silicon. Silent memory corruption that produces wrong gradients demands a different defense again from a node crash that stops responding altogether. While the MTBF calculations quantify *how often* interruptions arrive, which sets checkpoint intervals and spare-pool sizes, choosing the right recovery action requires distinguishing *what kind* of failure has occurred. In standard reliability terms, a fault is the underlying defect or disturbance, an error is the corrupted internal state it produces, and a failure is the externally visible misbehavior that the training or serving system must handle ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-avizienis2004basic|Avizienis et al. 2004]]).

No single label captures all of these differences. Reliability decisions require three orthogonal axes ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-constantinescu2008|Constantinescu 2008]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-lamport1982byzantine|Lamport et al. 1982]]): persistence (transient, intermittent, or permanent), manifestation (fail-stop, degraded, or value-corrupting), and failure scope (one device, one node, a rack or power domain, or the whole job). Two manifestations need names because liveness checks cannot see them. A **gray failure** is a component that stays alive but runs slowly or erratically, so it keeps answering the liveness checks that would flag a crash while every peer that waits on it slows down. **Silent data corruption (SDC)** goes further, producing wrong values with no error at all.

Because the three axes are independent, a single fault sits on all three at once. A transient disturbance can manifest as either a detected crash or silent corruption, while a permanent switch failure can remain confined to one rack or partition an entire job. Each axis governs a different operational choice. Persistence determines whether a fault clears on its own or requires hardware quarantine and replacement ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.05 Hardware Faults at Fleet Scale#^sec-ft-fault-persistence-response|section 7.4.1]]). Manifestation separates crashed ranks from slow stragglers ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-distinguishing-stragglers-failures-285d|section 7.9.5]]) and from Byzantine value corruption, while scope determines when a single shared hazard can defeat naive redundancy. The subsections that follow take one case from each axis: transient failures for persistence, fail-stop and Byzantine failures for manifestation, and correlated failures for scope.

Production logs show which of these failures a large run actually meets. During a 54-day period of Llama 3 405B pretraining on 16,384 H100 GPUs, Meta attributed each of 419 unexpected interruptions to a root-cause component ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-dubey2024llama|Dubey et al. 2024]]). Grouped by cause in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.04 Failure Taxonomy#^fig-llama3-interruptions|figure 2]], GPU components account for 268 of them, about 64 percent, led by 148 faulty GPUs and 72 HBM memory failures. Software caused 56, of which 54 were bugs and 2 were failed dependencies. Network switches and cables caused 35, unplanned host maintenance 32, and the remaining host hardware, from NICs to power supplies, 21. The last 7 were NCCL watchdog timeouts whose underlying cause was never found. Only 6 interruptions were attributed to silent data corruption, and that count includes only corruption that was caught. Most fault-tolerance effort therefore goes to frequent, detectable accelerator failures, while the rare silent ones demand a different kind of defense.

### Transient Failures

^sec-fault-tolerance-reliability-reliability-transient-failures-57b4

A transient fault clears without physical repair, but the state it corrupts can persist after the disturbance ends, forcing recovery to retry or validate affected work before relying on that state. In large-scale training systems, temporary disruptions range from network packet loss, where dropped packets are recovered by transport retransmission, to memory bit flips triggered by cosmic-ray-induced single-event upsets.[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn4|⁴]] Timing disturbances can be equally disruptive without corrupting bits directly. Under temperature spikes, thermal throttling reduces compute throughput without halting execution. Software timeouts fire when transient contention delays a collective beyond its allotted window.

Transient faults are particularly difficult to diagnose in ML training when they leave no explicit error signal. If hardware protection and the computation itself do not mask a memory bit flip during gradient computation, the corrupted value propagates into later updates while training continues. Large-scale SDC studies document such escaped corruption in production processors, and DRAM field studies confirm that memory errors occur frequently enough to require fleet-level monitoring ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-dixit2021silent|Dixit et al. 2021]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-sridharan2015|Sridharan et al. 2015]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-schroeder2009|Schroeder et al. 2009]]). In ML training, that undetected corruption surfaces as degraded gradients, anomalous loss curves, or rollback-worthy checkpoints rather than an explicit crash.

How the system responds to a transient failure therefore depends on whether the fault announces itself. Errors that raise explicit exceptions can be handled through bounded retry logic, whereas silent corruption requires end-to-end validation. Checksums catch altered bytes in storage or transport, cross-rank digests, which compare a short hash of each rank’s copy, expose disagreement across a supposedly identical reduced buffer, and statistical or replay checks test whether the computation itself remains plausible. Because a rank that computes the wrong local gradient and then checksums those wrong bytes will pass an ordinary transport check, only independent recomputation, invariants, or model-level evidence can expose the error.

### Fail-Stop Failures

^sec-fault-tolerance-reliability-reliability-failstop-failures-5cdd

In synchronous distributed training, a single participant that goes silent stalls the entire group’s next update. A conventional AllReduce cannot complete until every rank supplies its input, so one dead GPU in a 10,000-GPU job can leave the other 9,999 accelerators waiting at the barrier until recovery begins. Smaller communication groups limit the immediate dependency, although pipeline or data-parallel stages soon propagate the stall across the rest of the job. Such **fail-stop failures** occur when a component ceases operation outright and stops responding to requests. A GPU hardware failure renders an individual accelerator unresponsive, and a host node crash terminates all training processes on the machine. A network partition severs communication between a healthy node and the cluster, and a storage failure blocks workers from reading or writing checkpoint shards.

A stopped component gives a clearer symptom than one that keeps returning plausible but incorrect values. Yet a stopped rank announces itself only through silence, so detection rests on timeouts that must separate an outright crash from a slow or isolated host, such as a GPU still writing a large checkpoint while the collective waits. Once a timeout flags the missing participant, the recovery system replaces or restarts it and restores the most recent valid checkpoint; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-failure-detection-mechanisms-efed|section 7.9.1]] sets that timeout threshold once the full recovery-time budget is in view.

### Byzantine Failures

^sec-fault-tolerance-reliability-reliability-byzantine-failures-8a24

Where a fail-stop component ceases to participate, a value-corrupting component can keep running while returning incorrect results. A GPU may return wrong gradients without raising an error, a link may deliver a corrupted packet whose error pattern its cyclic redundancy check (CRC) happens not to cover, or a worker may compute different results for identical inputs and state. Byzantine failures allow arbitrary behavior, including inconsistent messages to different participants ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-lamport1982byzantine|Lamport et al. 1982]]). ML systems can encounter this broader failure model through silent data corruption or adversarial corruption. Numerical instability and determinism violations also require validation when they break the execution contract, but ordinary rounding differences or intentionally stochastic outputs are not themselves evidence of a faulty worker. The recovery concern is a participant whose accepted contribution can corrupt shared state without a visible crash.

The two models leave different evidence ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.04 Failure Taxonomy#^fig-failure-types|figure 3]]). A fail-stop worker such as W2 falls silent, and its missing heartbeats, the periodic liveness messages each worker sends, make it suspect. A Byzantine worker such as W6 keeps sending messages on schedule, so it passes every liveness check while the values it sends are wrong.

![[90 Assets/Volume II/07 Fault Tolerance/Failure Types f3b7d556c2.svg]]

Figure 3: **Fail-Stop vs. Byzantine Failures**: In the fail-stop model (left), a failed worker simply ceases to send messages, which a timeout flags as suspect without distinguishing a crash from delay or isolation. In the Byzantine model (right), a failed worker continues to participate but sends incorrect data (for example, corrupted gradients reported as valid), which can poison the global model state if not detected by redundant validation.

^fig-failure-types

In an ML fleet, the most common source of value corruption is not an adversary but hardware that changes a value without raising an error, the silent data corruption already met among transient failures. Its physical causes, the training signals that expose it, and the verification and hot-spare defenses that contain it are developed together in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.06 Check-And-Verify Defenses Against Silent Data Corruption#^sec-ft-sdc-verification|section 7.5]], after the hardware faults that produce it. Whatever its source, a Byzantine contribution violates a contract that liveness checks never test. Ordinary data-parallel workers process different batches and need not produce identical local gradients; the required contract is that each contribution correctly represents its assigned computation. A single Byzantine worker can violate that contract and corrupt the averaged gradient, potentially causing training to diverge or converge to a poor solution. **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.07 Fleet-Internal Trust Boundaries#^sec-security-privacy-gradient-sync-integrity|Gradient synchronization integrity]]** examines the same weakness when the corrupting worker is a deliberate attacker.

Redundant computation supplies one form of evidence against Byzantine failures. Workers repeating a computation from matching inputs, state, and random-number streams can compare results under a stated numerical tolerance. Statistical outlier detection and invariants provide additional evidence without fully repeating the computation. Each method has a coverage limit. Agreement can miss shared faults, while a statistical anomaly can arise from legitimate data variation. Detection overhead must therefore be evaluated together with the faults the method can expose.

Byzantine-resilient distributed training algorithms exist but impose significant overhead. Krum ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-blanchard2017machine|Blanchard et al. 2017]]) keeps the single worker gradient whose nearest neighbors lie closest to it and discards the rest, while coordinate-wise trimmed mean ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-yin2018byzantine|Yin et al. 2018]]) drops the largest and smallest values in each coordinate before averaging what remains. Both compute aggregates that stay robust to a bounded number of Byzantine workers, but they require more communication and computation than simple averaging. Without such protection, corrupted gradients can push the optimizer toward an unreliable model state while the training job appears healthy. Reliability must therefore protect semantic correctness rather than process liveness alone.[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn5|⁵]]

### Correlated Failures

^sec-fault-tolerance-reliability-reliability-correlated-failures-95e8

The reliability calculations in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.03 The Mathematics of Inevitable Failure#^sec-fault-tolerance-reliability-reliability-mathematics-inevitable-failure-93ef|section 7.2]] assume independent failures, yet real systems depart sharply from this assumption when common physical or operational dependencies take down multiple components at once. Within a single node, a power fault that exhausts the chassis’s redundant supplies, such as the loss of its feed circuits, removes every GPU in the chassis. Across a cluster, a top-of-rack network switch failure isolates all attached nodes, while a cooling system failure can trigger thermal shutdowns down an entire row of racks. Shared software and operational dependencies widen the blast radius further. A software bug in an updated CUDA driver can crash processes across nodes whenever they exercise the affected code path, and operator error during cluster reconfiguration can render an entire fleet unreachable.

Correlated failures violate the independence assumption underlying [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.03 The Mathematics of Inevitable Failure#^eq-system-reliability-n-components|equation 3]]. A model that counts only independent device failures omits shared hazards and their potentially larger blast radius; incident frequency and the number of affected devices must be modeled separately. Correlated failures can also defeat redundancy strategies. Three replicas of a model provide no protection against a shared power failure if all three run on the same power domain.

Defending against correlated failures requires classifying each failure by its scope, the failure domain it takes down, and ensuring that redundancy spans independent domains. Common failure domains in ML infrastructure range from a single GPU to an entire data center region, and each calls for its own mitigation ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.04 Failure Taxonomy#^tbl-failure-domains|table 2]]). These domains nest, so a physical disruption scales upward from one eight-GPU node to a rack and then to a multi-rack power and network envelope ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.04 Failure Taxonomy#^fig-failure-domains|figure 4]]). The software-version domain in the table cuts across that physical nesting, because every node running the same version shares its bugs wherever it sits. Its mitigation is a staged rollout, which first deploys a new version to a small canary slice of the fleet and widens the deployment only while that slice stays healthy.

Placing replicas within the same domain provides zero protection against that domain’s failure mode. The highlighted rack in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.04 Failure Taxonomy#^fig-failure-domains|figure 4]] contains nodes that share a top-of-rack (ToR) switch, so that switch’s loss can disconnect every attached node from the job. A neighboring rack with a separate switch can remain reachable during that event even if both racks share a power domain, yet that same placement does not protect against loss of their shared power source. Redundancy must therefore cross the relevant failure boundary, not merely occupy different devices.

**Power-domain correlation**: explain why placing all 3 model replicas in the same power domain fails to provide protection against a power outage confined to that domain.

**War Story 7.1: The supercomputer that swapped in spare cubes (2024)**

**Context**: Google’s Tensor Processing Unit (TPU) v4 machine-learning supercomputer used 4,096 TPU chips connected by a custom 3D torus inter-chip interconnect (ICI) fabric, and Google engineers published their operating experience with automatic fault resiliency and hardware recovery ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-zu2024tpuv4|Zu et al. 2024]]).

**Mechanism**: At 4,096-chip scale, machine and link failures could remove participants or paths required by a job’s configured communication topology.

**Impact**: Losing a required participant can interrupt the synchronous job across the slice. Losing a link instead raises a routing question: whether the remaining fabric can still provide the required communication paths.

**Fix**: Google used optical circuit switches (OCS) to assemble replacement slices from spare healthy TPU cubes, the pod’s building blocks of chips wired as a $4{\times}4{\times}4$ mesh, for machine outages, together with fault-tolerant routing for supported OCS outage patterns. The response depended on which resource failed.

**Systems lesson**: Fault tolerance is a topology-management problem. In tightly coupled accelerator fleets, recovery must preserve the communication graph, not merely replace an individual component; otherwise one local hardware fault can become a cluster-wide training interruption.
