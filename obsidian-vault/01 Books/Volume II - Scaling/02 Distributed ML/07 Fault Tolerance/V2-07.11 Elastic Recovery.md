# V2-07.11 Elastic Recovery

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance|V2-07 Fault Tolerance]]

^sec-fault-tolerance-reliability-reliability-elastic-training-4f87

Suppose a 1,024-GPU training job loses an 8-GPU node to a hardware fault, but the cluster has no spare nodes available. A fixed-size recovery policy leaves the remaining 1,016 GPUs waiting until replacement capacity becomes available or the allocation is released. Elastic recovery allows the job to resize and continue with less compute, provided its state and parallel decomposition fit the smaller allocation.

**Definition 7.2: Elastic training**

***Elastic training*** is the capability of a distributed training job to adjust its worker count across membership changes, potentially through a coordinated worker-group restart.

1.  **Significance**: It converts a permanent capacity loss into a temporary interruption followed by reduced throughput. A pure data-parallel 1,024-GPU job that loses 8 GPUs retains 99.2 percent of its device count and may resume if the remaining devices can hold the state. Tensor- and pipeline-parallel jobs additionally need a feasible partition and compatible group sizes; retained device count does not guarantee the same fraction of throughput. The recovery policy must either preserve the effective batch size through additional accumulation or validate the optimization changes caused by a smaller batch.
2.  **Distinction**: Unlike fixed-size checkpoint-restart recovery, which waits for replacement hardware to restore the original allocation, elastic recovery can restart or resume with a different worker count. The optimization loop may pause while membership, ranks, and state are re-established.
3.  **Common pitfall**: A frequent misconception is that elasticity is “automatic.” In reality, recovery requires coordinated adaptation: the training framework, the data loader, and the orchestrator must all synchronize their state to ensure that no data samples are lost or double-counted during the resize.

A small example shows the lifecycle in three phases ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.11 Elastic Recovery#^fig-elastic-flow|figure 16]]). Execution begins with a balanced four-node AllReduce ring at full throughput. When Node 3 drops out, the survivors pause at a rendezvous barrier and reload the last consistent checkpoint. The group then contracts into a three-node ring in which each worker takes a one-third larger data shard, resuming productive training at 75 percent throughput if the per-worker rate remains unchanged.

![[90 Assets/Volume II/07 Fault Tolerance/Elastic Flow 1ffbf56e03.svg]]

Figure 16: **Elastic Training Recovery**: Read the three phases top to bottom. Rather than restoring the original worker count before resuming, elastic training pauses when a node fails, reloads the last consistent checkpoint, re-forms the ring over the ${N}-1$ survivors, and redistributes the failed node’s data shards among them. The job resumes at reduced throughput (75 percent here, assuming an unchanged per-worker rate), turning a hard failure into a temporary slowdown.

### Recovery Adaptation Mechanisms

^sec-fault-tolerance-reliability-reliability-elastic-training-mechanisms-49b1

Shedding a lost node narrows the active ring instead of idling the whole allocation until replacement hardware arrives, so elastic recovery converts a job termination into a bounded capacity adjustment. When a failure reduces the worker count, the recovery path must adapt several training components before productive work resumes. Each adaptation addresses a specific consistency requirement that, if violated, would corrupt the model or waste computation.

Batch size adjustment comes first. With fewer surviving workers, either each worker must process more samples to preserve the global batch size, or the global batch size must shrink, which in turn may require recalibrating the learning rate to preserve convergence. Changing the global batch size changes the optimization regime as well as the amount of work per step. The linear and square-root learning-rate rules of **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-systems-systems-learning-rate-scaling-rules-fa26|Learning rate scaling rules]]** are candidate policies for a resized job, with the worker-count ratio standing in for the batch ratio when per-worker microbatch size and accumulation count stay fixed ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-goyal2017accurate|Goyal et al. 2017]]). For a shrink, the square-root rule reduces the learning rate less than linear scaling does; that arithmetic does not establish which policy is more stable, and either policy requires validation for the optimizer, schedule, and workload. Preserving the global batch instead can avoid introducing this change in optimization regime.

Gradient accumulation offers that alternative. Each surviving worker processes additional micro-batches before synchronization to maintain the original effective batch size. If worker count drops by half, doubling the accumulation steps preserves the number of examples per update and can retain the existing learning-rate schedule. Each worker then performs twice as much micro-batch computation per update, although communication and overlap determine the wall-time increase. Equal batch size does not imply bitwise-identical updates or identical behavior from operations that depend on micro-batch statistics.

Data loader redistribution must agree with the recovered training step and new membership. When workers are lost, the loader reassigns the remaining logical input stream so that the resize itself neither omits samples nor counts them twice in an update. Replaying work discarded by checkpoint rollback is expected; duplicating contributions within the resumed stream is a different error. The saved data position and sampling state distinguish those cases.

State resharding adds further complexity when using sharded model parallelism (ZeRO/FSDP). When parameters and optimizer states are sharded once across the entire job without replication, losing a worker removes the only live in-memory copy of its shard, so the job must reload a complete durable checkpoint generation before repartitioning the state across the smaller worker set. When the job instead uses hybrid sharding that replicates each shard across two or more data-parallel groups, a surviving replica group still holds a live copy in GPU memory and can supply the missing shard over the network without reading from storage. Only after the missing values are recovered from a peer replica or a durable checkpoint can the runtime redistribute shard ownership across the surviving workers. Changing shard ownership alone cannot recover missing values.

#### Spot Instance Preemption as a Failure Class

^sec-fault-tolerance-reliability-reliability-spot-instance-arbitrage-68ad

Hardware faults are not the only event that removes workers from a running job. Cloud providers often price preemptible (“spot”) instances below on-demand capacity, with the caveat that they can be reclaimed with little warning. Once workers vanish, recovery faces the same missing-state and membership problems as a hardware failure. An advance notice, when available, can allow a coordinated save or drain before departure and therefore changes the recovery opportunity.

Both fixed-size and elastic jobs can recover from preemption using checkpoints, but a fixed-size job must regain its required allocation before restarting. An elastic job can instead resume at reduced scale if enough capacity remains and the training invariants survive the resize. Recovery still pays for detection, state restoration, and group reconstruction; repeated reclamations can erase the apparent price advantage. At the reference fleet prices of \$0.70/GPU-hour for spot capacity against \$2/GPU-hour for on-demand capacity, the savings can outweigh the lost work and resizing delays; **[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.09 Cost Optimization#^sec-fleet-orchestration-spot-instances|Spot instances and preemptible VMs]]** develops the full spot-versus-on-demand cost model.

**Lighthouse 7.2: Archetype C (Federated MobileNet): Dropout as the normal case**

Archetype C (Federated MobileNet) makes worker departure an expected part of training. Training proceeds in rounds, in each of which a coordinator sends the current model to a set of clients and combines the updates they return. The phone-class clients train while charging, idle, and connected, so a client that disappears mid-round is an ordinary event rather than a fault to repair. The coordinator therefore selects more clients than a round needs and closes the round at a deadline. The round tolerates departures as long as enough compatible updates arrive; otherwise the coordinator abandons it ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-mcmahan2017communication|McMahan et al. 2017]]; [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-bonawitz2019towards|Bonawitz et al. 2019]]). Model-version checks prevent updates computed against a replaced model from entering the current aggregate, the federated counterpart of fencing a stale epoch, while aggregation weights account for the examples contributed under the chosen learning algorithm. Version checks and weighting do not remove participation bias. Recovery must preserve the coordinator state needed to continue that algorithm, including the model, round position, and any persistent optimizer or sampling state, rather than assuming weights alone suffice. **[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.08 Federated Learning Systems at Scale#^sec-edge-intelligence-client-scheduling-f675|Client scheduling]]** develops the round design, including deadlines, participation requirements, and the bias that arises when some kinds of devices report less often than others.

#### Framework Support for Elastic Recovery

^sec-fault-tolerance-reliability-reliability-framework-support-elastic-training-8b75

Whether worker loss comes from a hardware fault or a spot preemption, training frameworks differ in how many of the resize invariants (group membership, shard ownership, data loader redistribution, and batch-size or learning-rate adjustment) they enforce automatically after a failure. PyTorch Elastic (TorchElastic) uses agents to monitor workers and a rendezvous mechanism to establish group membership ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-pytorchElasticDocs|PyTorch Contributors 2026c]], [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-pytorchRendezvousDocs|2026b]]). On a failure or membership change, it stops all surviving workers, forms a new worker group, and starts its workers with new `RANK` and `WORLD_SIZE` assignments. It handles rank reassignment and communication-group reconstruction while leaving batch size, learning rate, and checkpoint semantics to user code. DeepSpeed ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-rasley2020|Rasley et al. 2020]]) provides ZeRO-based distributed training and checkpointing building blocks for large models ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-deepspeedCheckpointingDocs|DeepSpeed Developers 2026a]]). Recovery reloads from the last durable checkpoint, and Universal Checkpointing addresses portability across some changes in parallelism and topology ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-deepspeedUniversalCheckpointingDocs|DeepSpeed Developers 2026b]]), though elastic behavior still depends on the surrounding launcher and resource manager.

Ray Train, built on Ray’s actor model, provides a checkpoint-oriented recovery path that restarts a worker group after a failure or preemption and resumes from the latest available checkpoint. The training function remains responsible for saving and loading sufficient state ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-rayTrainFaultToleranceDocs|Ray Project 2026]]). Horovod Elastic similarly builds on Horovod’s data-parallel training system ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-sergeev2018horovod|Sergeev and Balso 2018]]) with an elastic state API for worker additions and removals ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.20 Source References#^ref-horovodElasticDocs|Horovod Developers 2026]]). The API resets ranks and reconstructs communication while leaving convergence-sensitive choices such as learning-rate or batch-size policy to the training script. Across these four frameworks, restarting the worker group is largely automated, while state resharding remains manual, deployment-dependent, or tied to a checkpoint reload ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.11 Elastic Recovery#^tbl-elastic-training-comparison|table 10]]).

| **Framework**       | **Failure detection** | **Automatic recovery** | **State resharding** | **Cluster integration** |
|:--------------------|:---------------------:|:----------------------:|:--------------------:|:-----------------------:|
| **PyTorch Elastic** |  Rendezvous timeout   |          Yes           |        Manual        |       Kubernetes        |
| **DeepSpeed**       |       External        |    Checkpoint-based    | Deployment-dependent |   External schedulers   |
| **Ray Train**       |   Actor supervision   | Checkpoint retry path  |  Checkpoint reload   |       Ray Cluster       |
| **Horovod Elastic** |   Driver heartbeat    |          Yes           |        Manual        |    Slurm, Kubernetes    |

Table 10: **Elastic Recovery Framework Comparison**: Frameworks differ in how they detect worker failures and how much of the recovery sequence (group reconstruction, state redistribution, batch size adjustment) they automate.

### Model-Specific Training Fault Tolerance

^sec-fault-tolerance-reliability-reliability-modelspecific-training-fault-tolerance-4b70

Restoring model weights alone does not guarantee a valid restart. An LLM that reloads its weights but loses its curriculum cursor, the record of where training stands in its planned document order, trains twice on the same documents, and a continuous recommender that rolls back its embedding tables serves stale user preferences. The checkpoint and recovery mechanisms of [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-reliability-reliability-checkpoint-restart-fundamentals-0ac2|section 7.8]] and [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-failure-detection-recovery-0f54|section 7.9]] must therefore adapt to the workload costs priced in [[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.08 The Cost of Failure#^sec-fault-tolerance-reliability-reliability-modeltype-diversity-failure-impact-8ec0|section 7.7.1]]. The design question is not simply how often to checkpoint, but which state variable would make a restart mathematically or economically wrong. For recommendation workloads, incremental checkpointing, tiered checkpointing, and embedding versioning can reduce the cost of preserving fresh state. Incremental storage can still reconstruct an exact generation from a base and its required deltas; accepting stale or approximate state is a separate choice. For each workload, the state at risk determines what its checkpoint must contain ([[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.11 Elastic Recovery#^tbl-training-recovery-state-invariants|table 11]]).

| **Workload**   | **State at risk**                                                                                  | **Checkpoint implication**                                                                                                                                                                                                 |
|:---------------|:---------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| LLM training   | Optimizer state, curriculum position, document position, long-context schedule                     | Preserve the FP32 optimizer state where precision matters, shard writes with ZeRO/FSDP, move serialization off the critical path, and include the data-schedule position so the optimization trajectory resumes correctly. |
| Recommendation | Embedding freshness, feature-store version                                                         | Preserve fresh state with incremental checkpointing, tiered checkpointing, and embedding versioning; accepting stale or approximate state requires a separate recovery contract.                                           |
| Vision         | Augmentation seeds, shuffling order, batch-normalization statistics, progressive-resizing schedule | Capture the stochastic and normalization state that controls the input stream; weights alone are not enough to reproduce the training trajectory.                                                                          |
| Scientific ML  | Simulator state, search frontier, explored configurations, validation seeds                        | Treat the model, simulator, search process, and random state as one consistency unit so recovery does not duplicate exploration or invalidate comparisons.                                                                 |

Table 11: **Training Recovery State Invariants**: Workloads require different checkpoint contents because they make different state variables quality-bearing. The correct recovery policy starts from the state that would make a restart wrong, then chooses sharding, incrementality, or domain-state capture accordingly.

^tbl-training-recovery-state-invariants

The common pattern is that recovery correctness is broader than weight restoration. LLMs can reload weights but resume with the wrong curriculum position. Recommendation models that train continuously can reload dense parameters but serve stale embeddings, so a failure that loses recent updates carries a freshness cost as well as a replay cost. The recovery budget must reflect the workload’s measured sensitivity to stale state.[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.21 Footnotes#^fn18|¹⁸]] Vision models have smaller checkpoints, about 1.2 GB for the ViT-Large example, which permit more frequent saves on the same storage path. Yet reproducing their input stream requires the augmentation configuration, random-number generator state, and data position rather than only the initial shuffling seed. A progressive-resizing schedule, which raises image resolution as training proceeds, must also resume at the same stage. Scientific models can reload a neural network while losing the simulator state that made the data meaningful, and an iterative search must also retain which configurations it has evaluated when those results choose its next candidates. In every case the checkpoint boundary must include whatever prior decisions affect future work, wherever that state resides. Once the trained model is deployed to users, however, the operational calculus shifts from protecting *weeks of batch computation* to protecting *milliseconds of real-time latency*.

**Self-Check: Question**

1.  When an 8-GPU node fails during a 1,024-GPU training run and no spare nodes are available, how does an elastic training framework enable the job to continue without idling the remaining 1,016 GPUs?

    1.  It automatically pauses the run and waits indefinitely until physical hardware repair replaces the defective node.
    2.  It shifts the missing 8 ranks of computation entirely to host CPU threads without changing the communication topology.
    3.  It can rebuild the worker group and restore valid state on the survivors when memory and parallelism permit, preserving data and batch invariants; 99.2% retained device count does not guarantee the same fraction of throughput.
    4.  It ignores the lost node and allows the remaining workers to continue training without synchronizing gradients.

2.  When an elastic training job resizes from $N_{\text{base}}$ to $N_{\text{new}}$ workers, compare using gradient accumulation adjustment versus learning rate recalibration to preserve optimization dynamics.

3.  How does elastic recovery transform the economics of training large foundation models on preemptible cloud ‘spot’ instances?

    1.  It can resume at reduced scale after preemption when state and parallelism fit the survivors, reducing waiting for replacement capacity; net savings still depend on lost work, recovery cost, and preemption frequency.
    2.  It forces cloud providers to guarantee $100\%$ uptime for spot instances by running redundant dummy processes.
    3.  It eliminates all network communication requirements, allowing spot instances to train completely independently without synchronizing weights.
    4.  It converts spot instances into dedicated on-demand instances at zero additional billing charge.

4.  For large recommendation systems with multi-terabyte embedding tables, checkpoint and recovery strategies must always prioritize strict full-state reproducibility over embedding freshness to avoid business revenue loss.
