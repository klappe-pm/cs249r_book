# V2-05.08 Hierarchical Communication

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05 Collective Communication|V2-05 Collective Communication]]

^sec-communication-collective-operations-collective-operations-mapping-collectives-topology-3214

The AllReduce cost models in [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-collective-operations-collective-operations-allreduce-algorithms-7545|section 5.6]] assume a flat network with uniform endpoint bandwidth, whereas real clusters expose the tiered bandwidth hierarchy of **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-bandwidth-hierarchy|Bandwidth hierarchy]]**. Because intra-node links are abundant and fast while inter-node links are scarce and expensive, hierarchical communication shrinks payloads locally before they cross the scarce tier, decomposing AllReduce into a local ReduceScatter, a cross-node reduction, and a local AllGather. It also aligns traffic with the physical fabric, whether switches aggregate packets in the network, rail-optimized trees separate GPU lanes, or direct-connect pods wire accelerators into multidimensional tori.

### Hierarchical AllReduce

^sec-communication-collective-operations-collective-operations-hierarchical-allreduce-1338

On a DGX H100 node, each GPU’s local NVLink capacity is 450 GB/s per direction (the 900 GB/s datasheet figure is the bidirectional total), while its one inter-node port provides 50 GB/s over InfiniBand. These are endpoint capacity budgets, not a promise of uniform achieved rate to every peer. Intra-node connectivity and simultaneous traffic still matter. That hierarchical network motivates a schedule that assigns work to each tier according to its usable capacity.

A flat ring advances at the rate of its slowest edge, and every ordering of a multi-node ring crosses node boundaries, so it can leave local NVLink capacity unused while loading scarce inter-node links. Hierarchical AllReduce explicitly partitions the global operation into three phases that align communication volume with the fabric tiers ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^fig-hierarchical-allreduce|figure 7]]).

![[90 Assets/Volume II/05 Collective Communication/Hierarchical Allreduce 9a5688172f.svg]]

Figure 7: **Hierarchical AllReduce**: Three-phase decomposition that exploits the intra-node/inter-node bandwidth gap. Phase 1 performs intra-node aggregation over NVLink (an NVLink ring acting as a ReduceScatter that leaves each GPU holding a node-shard partial sum), leaving a payload of ${M}/{G_{\text{node}}}$ on each of the ${G_{\text{node}}}$ GPUs per node. Phase 2 runs an AllReduce across corresponding GPUs using InfiniBand. Phase 3 completes intra-node distribution over NVLink (the AllGather that returns each GPU to the full result). The schematic shows two representative ranks per node; the same decomposition applies to ${G_{\text{node}}}$ ranks.

^fig-hierarchical-allreduce

With ${G_{\text{node}}}$ GPUs in each of ${N_{\text{nodes}}}$ nodes, the three phases form a single causal pipeline. First, an intra-node ReduceScatter over NVLink performs a local reduction among the ${G_{\text{node}}}$ GPUs in each node, leaving each GPU with a $1/{G_{\text{node}}}$ shard of partially reduced data while consuming only abundant intra-node bandwidth. Next, each corresponding-rank group applies an inter-node AllReduce over InfiniBand to its ${M}/{G_{\text{node}}}$-byte input shard, where the chosen collective algorithm dictates the bytes transmitted across the network fabric. Finally, an intra-node AllGather over NVLink redistributes the globally reduced shards within each node, completing the collective without consuming additional inter-node bandwidth.

Only Phase 2 (Shard AllReduce) loads the slower inter-node InfiniBand links ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^fig-hierarchical-allreduce|figure 7]]). In this middle phase, each corresponding-rank group reduces an ${M}/{G_{\text{node}}}$-byte shard across ${N_{\text{nodes}}}$ nodes. A ring in that group sends $2({N_{\text{nodes}}}-1){M}/({N_{\text{nodes}}}{G_{\text{node}}})$ bytes per participating GPU and receives the same amount. Summing across the node’s ${G_{\text{node}}}$ GPUs gives $2({N_{\text{nodes}}}-1){M}/{N_{\text{nodes}}}$ bytes sent per node. Smaller per-port payloads improve elapsed time when the node has independent ports and sufficient fabric capacity; sharding does not create bandwidth on a shared uplink. An 8-node budget quantifies the bandwidth multiplier this decomposition provides when those ports operate in parallel.

**Napkin Math 5.4: The hierarchical bandwidth multiplier**

**Problem**: A cluster has 8 nodes, each with 8 GPUs (64 total). The system must AllReduce the chapter’s 1 GB reference buffer. Assume each GPU has its own full-rate inter-node port, one rail per GPU as on a DGX H100 (rails are the subject of [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^sec-collective-communication-railoptimized-routing-nvidia-dgx-7081|section 5.7.4.1]]), with no oversubscription. The flat baseline is a single ring over all 64 ranks. How much faster is Hierarchical AllReduce than that flat ring?

**Flat ring AllReduce (ignoring hierarchy)**:

- Each GPU sends ~2 GB total (the bandwidth-optimal Ring AllReduce formula).
- Every edge of a ring carries the same traffic in every step, so the whole ring advances at the rate of its slowest edge. Every ordering puts at least one fabric-crossing edge on each node, even the node-contiguous ordering that crosses the fabric only once per node.
- **Effective Bandwidth**: Limited by the slowest link = 50 GB/s (InfiniBand).
- **Time**: $\approx$ $2 \times 1\ \text{GB} / 50\ \text{GB/s}$ = 40 ms (bandwidth term dominates).

**Hierarchical AllReduce (3-phase decomposition)**:

1.  **Intra-node ReduceScatter**: Each GPU sends 875 MB at 450 GB/s per direction → ~1.94 ms

2.  **Inter-Node AllReduce**: Each GPU AllReduces a $1\ \text{GB}/8$ = 125 MB shard over InfiniBand; Ring moves roughly $2({N_{\text{nodes}}}-1)/{N_{\text{nodes}}}$ times that payload, and after adding the small latency term the phase takes ~4.40 ms at 50 GB/s

    (The eight shard groups run concurrently, each on its own GPU’s port, so the node’s eight ports together carry the full payload in parallel.)

3.  **Intra-node AllGather**: Each GPU receives 875 MB at 450 GB/s per direction → ~1.94 ms

4.  **Total time**: $\approx$ 1.94 ms + 4.40 ms + 1.94 ms = 8.3 ms

**Systems insight**: Hierarchical AllReduce achieves a 4.8× speedup by reducing the inter-node payload from 1 GB to 125 MB per GPU before the Ring traffic multiplier. The flat ring used one port’s worth of fabric bandwidth because a single ring runs at its slowest edge; the hierarchical schedule uses all eight ports at once. That is also its precondition, since a node whose GPUs shared one uplink would carry the eight shard streams one after another and lose most of the speedup. This is why NVIDIA’s NCCL and similar libraries often select hierarchical algorithms on multi-node clusters when the topology supports them.

This book’s running instance makes the same comparison on the cluster it was defined for. Archetype A’s 175B-parameter model produces a 350 GB BF16 gradient, and the reference cluster holds 1,024 GPUs as 128 nodes of 8. A single flat ring over every GPU would spend about 14.0 s per full-gradient reduction. The hierarchical schedule sends one-eighth of the gradient through each GPU’s port in a shard ring that spans every node and completes in about 3.1 s, a 4.5× improvement. The cross-node phase still accounts for about 1.7 s of that time. Seconds per step remain a large exposed cost even after hierarchy. That is why the production layout for this instance shards the model so that each data-parallel group reduces a fraction of this payload. It is also why the overlap and compression techniques later in the chapter still matter at this scale.

These three phases also generalize to additional fabric tiers. For example, 4 racks of 4 nodes with 8 GPUs per node contain 128 GPUs. A rack-local ReduceScatter over 32 GPUs can leave each GPU with $1/32$ of the original payload for the cross-rack phase. The total elapsed time still includes both local phases, the cross-rack collective’s traffic factor, startup, and contention. A cross-rack oversubscription ratio alone cannot determine a speedup over a flat ring.

### Multidimensional Reduction on a Torus

^sec-collective-communication-torus-topology-tpu-pods-68b2

Hierarchy fits a fabric whose tiers differ in speed. A torus, the direct-connect topology of Google’s Tensor Processing Unit (TPU) pods, has uniform links instead, and its collectives reduce along one dimension at a time. TPU v4 pods support a 3D torus topology, unlike the 2D torus used by TPU v2 and v3. In the regular 3D torus model, each chip links directly to six neighbors $(\pm {X}, \pm {Y}, \pm {Z})$ with equal per-link bandwidth. For collectives, the torus invites dimension-ordered reduction, which decomposes the AllReduce into sequential Ring AllReduces along axis-aligned torus rings. For a pod with ${X}{\times}{Y}{\times}{Z}$ chips, ranks first execute independent X-dimension rings for each fixed $({Y},{Z})$ coordinate, producing partial sums along each X line. A second phase runs Y-dimension rings to combine those partials across the ${X} \times {Y}$ plane. A third phase executes Z-dimension rings across fixed $({X},{Y})$ coordinates to complete the global reduction.

↩︎ The torus topology and its bisection and path-length trade-offs against the fat-tree are established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.06 Level 3 Switch and Topology#^sec-network-fabrics-dragonfly|Dragonfly and torus alternatives]]**.

On a $4{\times}4$ 2D torus grid of 16 ranks, the dimension-ordered schedule runs in two phases ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^fig-torus-reduction|figure 8]]). In Phase 1 (orange solid paths), each row executes an independent 4-rank Ring AllReduce across the horizontal X dimension using dashed wrap-around boundary links to close the ring ($2({X}-1) = 6$ steps). Once row partial sums are established, Phase 2 (slate solid paths) executes orthogonal 4-rank vertical Ring AllReduces down the Y dimension ($2({Y}-1) = 6$ steps). These phases use direct nearest-neighbor links without multi-hop routing within a logical ring edge. They reduce the startup count from $2({N}-1) = 30$ rounds on a flat 16-rank ring to $2({X}-1) + 2({Y}-1) = 12$ rounds, a 2.5× reduction in the modeled startup term. In this simple form each axis still processes the full message, so the round-count saving comes at a byte cost that the partitioned dimension-wise schedule removes.

![[90 Assets/Volume II/05 Collective Communication/Torus Reduction a997b9e2e5.svg]]

Figure 8: **Dimension-Ordered Reduction on a Torus Topology**: In a 2D torus mesh ($4 \times 4$ node grid representing a simplified TPU pod slice), AllReduce proceeds sequentially along orthogonal dimensions. Phase 1 (orange) executes four parallel horizontal rings across the X dimension ($2({X}-1) = 6$ steps). Phase 2 (slate) then executes four parallel vertical rings across the Y dimension ($2({Y}-1) = 6$ steps) on the row-aggregated partial sums. Dashed stubs mark the torus wrap-around links, each leaving one edge of the grid and re-entering at the opposite edge. This dimension-ordered decomposition needs 12 startup rounds against 30 for a 16-rank 1D global ring, a $2.5\times$ reduction, but each axis processes the full message, so its bandwidth time is $3{M}/{\beta}$ for this grid.

^fig-torus-reduction

The byte term does not shrink with the rings. Because every axis processes the full ${M}$-byte tensor, the bandwidth time is $2{M}[({X}-1)/{X}+ ({Y}-1)/{Y}+ ({Z}-1)/{Z}]/{\beta}$ for equal per-axis bandwidth ${\beta}$. The startup term is $2[({X}-1)+({Y}-1)+({Z}-1)]{\alpha}$. Shorter rings reduce startup cost, but these sequential full-message AllReduces do not retain the bandwidth cost of one global ring.

A bandwidth-efficient multidimensional implementation instead partitions the work with dimension-wise ReduceScatter followed by reverse-order AllGather. The X-dimension ReduceScatter sends ${M}({X}-1)/{X}$ bytes per rank and leaves each rank at a given X coordinate holding the row-reduced sum for the same ${M}/{X}$ shard. Because all ranks in a Y-column share that X coordinate, they hold matching shards and can run a Y-dimension ReduceScatter on that ${M}/{X}$ slice alone, sending $({M}/{X})({Y}-1)/{Y}$ bytes per rank and subdividing the slice to ${M}/({X}{Y})$. On the $4{\times}4$ grid, the X-dimension ReduceScatter leaves each rank one of 4 shards of the tensor, and the Y-dimension ReduceScatter leaves it one of 16, where the two axes finish the subdivision. On a three-axis torus, the Z-dimension ReduceScatter repeats the subdivision across ranks that share both X and Y coordinates, leaving each of the ${N}= {X} {Y} {Z}$ chips with a distinct ${M}/{N}$ shard of the global sum after sending ${M}({N}-1)/{N}$ bytes in total. The mirrored AllGather along Z, Y, and X doubles that volume to $2({N}-1){M}/{N}$, the ring’s optimal byte term, while keeping the short rings’ startup count. The torus thus teaches the same lesson as hierarchy, which is to shrink the payload before each successive stage rather than send the full tensor through every one.

Dimension-ordered reduction follows direct neighbor links and separates axis traffic in time; it does not change the network diameter or eliminate contention with other workloads. The torus topology also provides natural fault tolerance through alternate routing paths. If one link in the X-dimension fails, traffic can detour through the Y or Z dimensions (at the cost of increased latency). The compiler and collective runtime must choose a schedule for the actual topology, message size, and available links.

### In-Network Reduction with SHARP

^sec-communication-sharp

Hierarchical and dimension-ordered schedules redistribute work across links, but their software reduction stages still require endpoint GPUs to receive and combine contributions. NVIDIA’s Scalable Hierarchical Aggregation and Reduction Protocol (SHARP)[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.17 Footnotes#^fn6|⁶]] moves that intermediate aggregation into the network. Instead of routing each partial sum through a GPU for arithmetic, an aggregation-capable InfiniBand switch combines contributions as packets pass through it.

A centralized endpoint reduction and in-switch aggregation send different data up the switch tree ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^fig-sharp-innetwork|figure 9]]). In the endpoint tree of panel (a), intermediate switches merely forward raw packets, forcing all four full gradient tensors (${\mathbf{g}}_0$ through ${\mathbf{g}}_3$) across the upper links into a single Reducer GPU that executes every addition. In panel (b), SHARP offloads arithmetic to aggregation-capable switch application-specific integrated circuits (ASICs): each intermediate switch computes partial sums (${\mathbf{g}}_0+{\mathbf{g}}_1$ and ${\mathbf{g}}_2+{\mathbf{g}}_3$) in-flight, leaving only the combined shards for the root switch to finalize. In this four-GPU tree, moving reduction into the network fabric halves the upper link traffic and relieves accelerator endpoints from coordinating arithmetic steps.

![[90 Assets/Volume II/05 Collective Communication/Sharp Innetwork cd2eed9a81.svg]]

Figure 9: **Endpoint and In-Network Reduction**: The upstream half of a reduction over four GPUs. (a) Switches only forward packets, so every full gradient tensor crosses the upper links and converges on one reducer GPU, which does all the arithmetic. (b) Aggregation-capable switches add their inputs, so each upper link carries one partial sum and the root switch finishes the reduction; the result then travels back down the same tree. A software reduction tree also aggregates along its path, but performs arithmetic at endpoints rather than switches. The diagram compares where arithmetic happens, not measured speedup.

^fig-sharp-innetwork

SHARP changes both terms of the cost model. On the startup side, it shortens the dependency chain. In a software-based tree reduction, each level waits for an intermediate GPU to receive, reduce, and forward its inputs. With SHARP, the switch performs that step in the packet path, so no GPU execution stage or extra endpoint round trip sits between levels. On the byte side, each upper-tier link carries one partial sum rather than every contribution beneath it ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^fig-sharp-innetwork|figure 9]]). In the idealized aggregation tree, each GPU sends its contribution up once and receives the result once, whereas a ring rank sends nearly $2{M}$. Endpoint memory traffic falls for the same reason. Switch processing and contention for aggregation resources add costs of their own, so moving arithmetic into the network changes the ${\alpha}$-${\beta}$ terms rather than eliminating them.

Which benefit matters follows the regimes of [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.06 Pricing Collectives by Rounds and Chunks#^sec-communication-collective-operations-collective-operations-network-performance-modeling-0d8e|section 5.5]]. For small and medium messages, where startup rounds dominate, the shorter dependency chain is the main gain, although for very small messages fixed switch-processing overhead can limit it. For large messages the startup saving becomes proportionally small, and what remains is the byte saving at the endpoints and on the upper tier, which shortens the collective only when those links are the limiting resource. Graham et al. ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-graham2020|2020]]) report multi-fold reduction-bandwidth improvements and smaller application-level gains for PyTorch workloads when SHARP Streaming-Aggregation, its mode for large messages, is enabled on HDR/Quantum InfiniBand switches.

A faster collective reaches step time only through the exposed part of its transfer, and strong scaling campaigns (training a fixed model across more accelerators without proportionally growing batch size) enlarge that part. As the per-accelerator batch shrinks, each gradient tensor stays large (proportional to model size) but the backward pass per accelerator shortens, exposing more of the communication budget. The limiting term can still be bandwidth; strong scaling alone does not establish that startup latency dominates. In-switch aggregation helps when its reduction in endpoint work or fabric traffic shortens the exposed critical path.

In-switch reduction also brings hardware and capacity constraints of its own. The switch ASIC must support the exact reduction operator and numerical format the job uses, such as FP16 or BF16 gradients, which vary across switch generations. Its finite internal memory limits how many aggregation trees can remain active at once. A large cluster running many concurrent jobs or process groups can therefore exhaust switch-tree capacity and fall back to host-based reductions. Moreover, the HDR and Quantum SHARP implementations examined here depend on InfiniBand switch support, so their gains do not carry over to Ethernet fabrics unless an equivalent in-network aggregation path is present.

### Topology-Aware Routing

^sec-communication-collective-operations-collective-operations-topology-detection-selection-2dc7

Two runs of the same 64-GPU Ring AllReduce on identical hardware can differ by a multiple in throughput depending on whether consecutive logical ranks sit on the same NVLink domain or across shared inter-node uplinks. Hierarchy and in-network aggregation change where bytes move and where sums are computed, but their benefit still depends on mapping the logical communication pattern onto physical links.

Communication libraries like NCCL perform topology detection at initialization and use graph search to choose paths through the hardware topology available to them ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-nvidiaNcclUserGuide|NVIDIA 2026]]). For each pair of ranks, the library must determine whether the peer sits behind a local NVLink switch or 100 meters away across an InfiniBand fabric, because that mapping decides which physical links each logical hop occupies. Local GPU, NVLink, PCIe, and NIC connectivity informs those choices, but local discovery does not reveal every remote switch, route, or competing flow. Fabric configuration and placement information must complement the library’s view when diagnosing cross-node contention.

The topology detection process begins with hardware enumeration. NCCL queries the PCIe bus to discover GPU placement, NVLink connectivity between GPUs, and NIC-to-PCIe-switch affinity. From this information, it constructs an internal graph where nodes represent GPUs and edges represent physical links with annotated bandwidth and latency. A graph search algorithm then finds communication paths that maximize aggregate bandwidth while minimizing the number of cross-domain hops (transitions between NVLink, PCIe, and InfiniBand domains). This topology-aware path selection is what allows NCCL to approach theoretical peak bandwidth on well-configured systems, while topology-unaware implementations can leave a large fraction of bandwidth unused.

#### Rail-Optimized Routing (NVIDIA DGX)

^sec-collective-communication-railoptimized-routing-nvidia-dgx-7081

In the eight-GPU DGX layout considered here, each GPU has a dedicated inter-node NIC, and the fabric connects matching NIC positions to rail switches. Rail-optimized routing fits the corresponding-shard phase of hierarchical AllReduce. GPU 0 on Node A exchanges its shard with GPU 0 on Nodes B and C, GPU 1 exchanges with peer GPU 1s, and so on. The eight rails can carry these groups concurrently ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^tbl-rail-optimized|table 8]]), subject to their physical capacity and competing traffic. Other collectives may require cross-rail paths.

↩︎ Rail-optimized cabling, which connects each GPU slot position to its own rail switch, is established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.06 Level 3 Switch and Topology#^sec-network-fabrics-rail-optimized|Rail-optimized topology]]**.

| **Rail**   | **Participants**                                                                         | **Traffic**  |
|:-----------|:-----------------------------------------------------------------------------------------|:------------:|
| **Rail 0** | Node0-GPU0 $\leftrightarrow$ Node1-GPU0 $\leftrightarrow$ Node2-GPU0 $\leftrightarrow$ … | ${M}/8$ each |
| **Rail 1** | Node0-GPU1 $\leftrightarrow$ Node1-GPU1 $\leftrightarrow$ Node2-GPU1 $\leftrightarrow$ … | ${M}/8$ each |
| **…**      | …                                                                                        |      …       |
| **Rail 7** | Node0-GPU7 $\leftrightarrow$ Node1-GPU7 $\leftrightarrow$ Node2-GPU7 $\leftrightarrow$ … | ${M}/8$ each |

Table 8: **Rail-Optimized Traffic Distribution**: Each rail carries 1/8 of the total traffic independently.

^tbl-rail-optimized

If all eight shard streams converge on one remote NIC, that endpoint faces 8$\times$ the balanced receive demand. In the equal-shard layout, matching each shard group to its intended rail distributes one-eighth of the payload to each NIC. This removes that particular concentration; achieving the predicted rate still requires sufficient switch, uplink, and bisection capacity for concurrent traffic.

NVIDIA designed the DGX node and rail layout together so that Phase 2 of hierarchical AllReduce ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^sec-communication-collective-operations-collective-operations-hierarchical-allreduce-1338|section 5.7.1]]) maps each corresponding-rank shard group onto its own rail. NCCL exploits that structure whenever its topology detection finds aligned ranks. When the job scheduler assigns process ranks without topology awareness, however, logical shards and physical rails drift apart. Cross-node traffic is then routed through the wrong NICs or across spine switches, cutting a node’s usable injection bandwidth to as little as one-eighth of the rail-aligned value when all eight shard exchanges converge on one NIC. Large deployments therefore enforce topology-aware rank assignment through device ordering (`CUDA_VISIBLE_DEVICES`), NIC binding, and scheduler placement policies so that logical rank ${i}$ on every node stays bound to rail ${i}$.

↪ How the scheduler places a job’s gangs on the topology hierarchy so that its collectives stay on fast links is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.07 Topology-Aware Scheduling#^sec-fleet-orchestration-topology-aware|Topology-Aware Scheduling]]**.

Hierarchical execution and topology-aware routing connect the cost model to a physical placement. The ${\alpha}$-${\beta}$ terms estimate the service required by each scheduled exchange; hierarchy redistributes work across fabric tiers, and rail alignment can balance corresponding-shard traffic across independent ports. None removes shared-capacity limits. Measured collective duration must confirm that the intended placement shortens the dependency path before the design is accepted.

    1.  Hierarchical AllReduce converts the floating-point values to 8-bit integers during the intra-node phase to save inter-node bandwidth.
    2.  Flat Ring AllReduce requires every GPU to establish an optical fiber connection directly to all 63 other GPUs in the cluster.
    3.  Local ReduceScatter creates one 125 MB shard per GPU from a 1 GB tensor; corresponding-rank AllReduces can distribute these shards across the eight ports, followed by local AllGather.
    4.  Hierarchical AllReduce executes without any inter-node network synchronization barriers.

2.  How does dimension-ordered reduction on a 3D torus network (such as Google TPU pods) optimize communication latency and link utilization compared to running a single global logical ring?

    2.  It executes axis-aligned rings in sequence, reducing startup rounds to $2[(X-1)+(Y-1)+(Z-1)]$ while trading extra full-message transfers for shorter rings.
    3.  It broadcasts full gradient tensors directly to all pod nodes simultaneously over optical circuit switches.
    4.  It routes all collective packets through a single central root TPU in the pod to minimize total wire length.
