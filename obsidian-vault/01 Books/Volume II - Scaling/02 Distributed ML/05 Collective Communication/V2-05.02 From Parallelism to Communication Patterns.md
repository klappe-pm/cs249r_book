# V2-05.02 From Parallelism to Communication Patterns

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05 Collective Communication|V2-05 Collective Communication]]

^sec-communication-collective-operations-collective-operations-communication-fundamentals-44eb

When 10,000 GPUs cooperate on one training update, the splits created by data, tensor, pipeline, and expert parallelism determine which results must cross device boundaries. Workers execute collective operations within participating groups and point-to-point transfers between pipeline stages. In the multi-tier fleet stack of **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^fig-fleet-stack|The Fleet Stack]]**, these exchanges occupy the Distributed Execution row of the Distribution band, where logical parallelism becomes physical traffic.

Every such split assumes that replicas, shards, stages, and experts can exchange gradients, activations, parameters, and tokens quickly enough for the optimizer to see one coherent training run. In data parallelism, each worker holds a full copy of the model and processes its own slice of the batch, so the copies must agree on one combined gradient before every update. Tensor, pipeline, and expert parallelism divide the model itself, so partial results must cross device boundaries within each step. Each of these exchanges is charged to the Fleet Law’s communication term ${T_{\text{comm}}}({N})$, and the part of it not hidden behind computation counts against program goodput, the ratio of a step’s ideal execution time to its actual time (**[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.07 Program Goodput#^sec-performance-engineering-iron-law|The iron law and the Fleet Law terms]]**). Every way of splitting the model relocates work onto the network, and this chapter turns those exchanges into schedules whose latency, bandwidth, and topology costs can be computed.

↪ The partitioning strategies themselves, and the 3D parallelism cube that composes data, pipeline, and tensor parallelism into one configuration space, are developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.03 The Parallelism Design Space#^sec-distributed-training-systems-systems-singlemachine-distributed-transition-1ee4|The Parallelism Design Space]]**.

The gap between that assumption and the wire reveals an asymmetry in how computation and communication scale. Computation is local because each GPU works on its own data, so aggregate compute grows with the number of GPUs. Communication is global because keeping the fleet synchronized requires information to cross physical links with finite latency, bandwidth, interconnect topology, and energy. Gradient synchronization is the central case, because every synchronous data-parallel step repeats it on the full gradient. Scaling laws (principle [[01 Books/Volume II - Scaling/02 Distributed ML/V2 Distributed ML Principles#^pri-universal-scaling|9]]) make that case harder over time, because the capability they reward comes from more parameters trained on more accelerators, so the gradient to be reduced and the group that must agree on it grow together.

Managing that global traffic begins by separating an operation’s result from the schedule that produces it. **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.02 The Synchronization Backbone#^sec-network-fabrics-introduction|The Synchronization Backbone]]** named AllReduce, AllGather, and AllToAll as the traffic the fabric must carry; here they become contracts on results. AllReduce[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.17 Footnotes#^fn1|¹]] combines corresponding tensor elements across participating workers, called ranks after their index in the group, and returns the reduced tensor to every worker. AllGather instead concatenates their shards, ReduceScatter combines contributions but leaves each worker with only a shard of the result, and AllToAll sends different data to different destinations. The parallel decomposition determines which contract each exchange needs; ring, tree, and hierarchical algorithms are alternative schedules for carrying that contract out.

For the initial gradient budget, consider a ring schedule: each worker passes tensor chunks to a neighbor, first accumulating their sums and then circulating the completed chunks. Each phase moves nearly one tensor’s worth of data per worker, so the bandwidth budget is approximately twice the gradient size divided by link bandwidth. [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-collective-operations-collective-operations-ring-allreduce-ffce|Section 5.6.3]] derives the detailed round count once the transfer model is established.

**Definition 5.1: Gradient synchronization**

***Gradient synchronization*** is the collective communication step in synchronous data-parallel training in which every worker contributes its locally computed gradient tensor to an aggregate reduction, then receives the same reduced result so all model replicas apply an identical update.

1.  **Significance**: Communicating all gradients of a 70B-parameter model in BF16 gives a 140 GB logical payload per replica per step. As a communication-only baseline, suppose every rank reduces that complete buffer. A ring across 1,000 GPUs at 50 GB/s per link has a bandwidth budget of approximately $2 \times 140/50$ $\approx$ 5.6 s of transfer per step. Model partitioning shrinks each rank’s share of that buffer, and only the portion of ${T_{\text{comm}}}({N})$ left exposed after overlap adds to step time in the Fleet Law (**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^eq-fleet-law|equation 1.3]]**).
2.  **Distinction**: Unlike a parameter server, which concentrates every worker’s gradient at a central aggregator, ring AllReduce spreads the exchange so that each worker sends $2 \times ({N}-1)/{N}\times {M}$ bytes per step, approaching $2{M}$ however large the cluster grows ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-collective-operations-naive-vs-optimal|section 5.6.1]] develops the comparison).
3.  **Common pitfall**: A frequent misconception is that ring AllReduce makes every worker exchange data with every other worker. In ring AllReduce, each worker communicates with neighbors according to a schedule, and the per-node communication volume is approximately constant as the cluster grows. The scaling pressure comes from latency steps, topology, and the gradient volume per step, not from every worker opening a distinct stream to every other worker.

For standard synchronous data-parallel stochastic gradient descent (SGD), gradient synchronization supplies the shared gradient needed for one optimization trajectory. Replicas that apply different local gradients can diverge. To reproduce the intended global-batch update, they must also start from matching parameters and optimizer state, weight local contributions correctly, and apply the same update rule. The AllReduce primitive provides the reduction; convergence follows from the optimization assumptions, not from communication alone. Floating-point reduction order can still change low-order bits.

In general, a model with ${P}$ parameters contributes $2{P}$ bytes per data-parallel replica when all gradients are communicated in BF16 (2 bytes per parameter); stored weight precision alone does not determine that choice. For the 70-billion-parameter model in the definition above, that complete logical gradient is 140 GB, and a ring moves nearly twice its input buffer size per rank.[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.17 Footnotes#^fn2|²]] If a replica spans multiple ranks through model parallelism, each corresponding-shard group reduces its own portion rather than this full buffer.

Because every bandwidth term in this chapter scales linearly with payload size, the worked derivations use this compact 70B gradient (or the chapter’s reference gradient buffer first priced in the energy estimate of [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.03 The Physics of Data Movement#^sec-communication-collective-operations-physics-data-movement|section 5.2]]) and vary rank count to isolate how each schedule scales. [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^sec-communication-collective-operations-collective-operations-hierarchical-allreduce-1338|Section 5.7.1]] then prices the full 175B-parameter running instance of Archetype A (GPT-4/Llama-3) on this book’s reference cluster.

At large scale (hundreds of billions of parameters across thousands of GPUs), gradient synchronization can dominate training step time unless collective communication is systematically optimized. Understanding how to manage that overhead requires modeling data movement as physics rather than as an abstract API call.

**Self-Check: Question**

1.  A dense-model training run triples its GPU count from 64 to 192 while holding the global work per update fixed. Step time drops by only 30%, and per-GPU compute utilization falls. Which scaling mechanism should the team investigate, without treating these aggregates as proof of the cause?

    1.  Backpropagation stops functioning correctly across multiple nodes because gradients cannot be computed concurrently across independent data batches.
    2.  Floating-point accumulation during gradient reduction becomes numerically unstable when more than 64 GPUs participate in the collective.
    3.  Host CPU memory bandwidth saturates because all optimizer states must be shuffled through host DRAM on every multi-node step.
    4.  Local compute can shrink while global synchronization and shared-link transfers remain exposed; rank-aligned traces are needed to determine whether communication actually limits the step.

2.  A logical Ring AllReduce cost model uses a 140 GB input per rank, corresponding to the model-wide BF16 gradient size of a 70B-parameter model. Holding that input fixed, a team expects per-rank sent volume to grow over 100 times when the group grows from 8 to 1,000 ranks. Explain why the expectation is false and why time can still increase. Treat this as transfer arithmetic, not a claim that a full replicated training state fits on one GPU.

3.  True or False: In synchronous data-parallel distributed training, using Ring AllReduce causes each GPU network bandwidth requirement to scale quadratically with the number of GPUs $N$ because every worker must open a direct communication socket to every other worker in the cluster.
