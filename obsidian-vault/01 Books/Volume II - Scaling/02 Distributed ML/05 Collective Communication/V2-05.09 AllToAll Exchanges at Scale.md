# V2-05.09 AllToAll Exchanges at Scale

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05 Collective Communication|V2-05 Collective Communication]]

^sec-communication-alltoall

Hierarchy, in-network reduction, and rail alignment were all developed for AllReduce, whose uniform payload lets every rank follow the same schedule. In a mixture-of-experts model with 64 experts distributed across 8 GPUs (8 experts per GPU), or in the sharded embedding tables of [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.04 Parallelism Strategies and Their Traffic#^tbl-parallelism-communication-mapping|table 1]], a gating network or lookup table assigns each input to a specific destination rank. Tokens assigned to remote GPUs must physically cross the fabric before expert computation can proceed and return afterward, breaking AllReduce’s symmetry so the exchange finishes only when its slowest path completes.

**Systems Perspective 5.1: AllToAll vs. AllReduce: Why scale differs**

Ring AllReduce can pipeline a uniform payload through neighbor exchanges. AllToAll presents a different scaling problem because every rank has destination-specific traffic, but the logical peer count alone does not determine its cost.

An AllToAll over ${N}$ ranks creates ${N}({N}-1)$ logical source-destination transfers, yet each rank’s aggregate payload can remain fixed under weak scaling (per-rank work held fixed as ranks are added). Its lower bound is governed by the largest of four terms: source injection time (how long a rank’s port takes to send its bytes), destination reception time (how long a port takes to receive them), traffic crossing the fabric bisection, and per-message startup or scheduling overhead. Oversubscription and routing determine how much physical capacity those flows share. Message granularity determines how often they pay ${\alpha}$. In the ${\alpha}$-${\beta}$ model, that startup term acts as a bound only when messages are serialized, because concurrent sends can share one startup, although the rate at which an endpoint can issue messages still limits those sends. Routing skew determines whether one destination or link becomes the critical path. A full-bisection network carrying balanced, coarse-grained traffic can therefore scale well despite the quadratic logical connection count, whereas an oversubscribed fabric or skewed expert assignment can stall at much smaller ${N}$.

Expert parallelism and large-scale recommendation systems can reach a communication wall earlier than standard data parallelism when their traffic exhausts injection, reception, or bisection capacity, or when routing and destination skew create hotspots. The primitive determines the traffic matrix; the physical fabric and routing distribution determine the scaling ceiling.

**Napkin Math 5.5: AllToAll for MoE token routing**

**Problem**: An MoE model processes a batch of 4096 tokens across 8 GPUs (512 tokens per GPU). Each token is a 2048-dimensional hidden state in BF16 (4.096 KB per token). The gating network assigns each token to exactly 1 of 64 experts (8 experts per GPU). Assuming uniform routing (each expert receives 64 tokens), how much data does each GPU send and receive?

**Math**:

Each GPU holds 512 tokens that need to reach 64 different experts across 8 GPUs. With uniform routing, each GPU sends 64 tokens to each of the other 7 GPUs (keeping 64 tokens local).

- Data per GPU-to-GPU transfer: 64 tokens $\times$ 4.096 KB/token = 262.144 KB
- Total data sent per GPU: 7 $\times$ 262.144 KB = 1.84 MB
- Total data received per GPU: 1.84 MB (symmetric)

**Latency Analysis** (InfiniBand NDR, ${\alpha}=$ 1.5 μs, ${\beta}=$ 50 GB/s):

Each of the 7 transfers is a 262.144 KB message. From the ${\alpha}$-${\beta}$ model: ${T_{\text{transfer}}}$ = 1.5 μs + 5 μs = 6.5 μs per transfer.

If serialized: 7 $\times$ 6.5 μs = 45.5 μs. If all 7 transfers are issued concurrently, they still share the GPU’s 50 GB/s injection port. The aggregate injection lower bound is therefore ${\alpha}+ \text{total bytes sent}/{\beta}=$ 38.2 μs, before contention and additional collective overhead. Full duplex permits simultaneous sending and receiving; it does not provide one full-bandwidth outgoing port per peer.

**Systems insight**: The injection result is only a lower bound. If the topology’s usable bisection bandwidth is ${\text{BW}_{\text{bisect}}}$ and ${V_{\text{cut}}}$ bytes must cross its minimum cut, the exchange also obeys ${T}\geq {V_{\text{cut}}}/{\text{BW}_{\text{bisect}}}$. Oversubscription reduces ${\text{BW}_{\text{bisect}}}$, fine-grained peer messages add startup cost, and expert skew raises the maximum receive volume above the uniform estimate. The forward pass runs the AllToAll twice per layer, once for token dispatch and once for result collection; training also communicates gradients during backward.

### Dynamic Routing and Expert Imbalance in MoE AllToAll

^sec-collective-communication-moe-dynamic-routing

The worked trace in notebook [5.5](https://mlsysbook.ai/vol2/05_collective_communication/05_collective_communication.html#nbk-collective-communication-alltoall-moe-token-routing) assumes uniform token routing, in which every expert receives an identical share of tokens. In production MoE models, routing decisions are dynamic and data-dependent. The exchange keeps its two-phase shape, but its buffer sizes, its slowest receiver, and its load on the fabric all become functions of the routing distribution. The hierarchy just developed for AllReduce reappears as one of the schedules that can contain them.

Each MoE layer performs two exchanges. In an MoE transformer layer with ${N_{\text{experts}}}$ experts distributed across ${N}$ ranks (${N_{\text{experts}}}/{N}$ experts per rank), each rank holds a local batch of ${B_{\text{tok}}}$ tokens. A gating router computes top-${k_{\text{experts}}}$ routing probabilities over all ${N_{\text{experts}}}$ experts for each token, inducing two collective communication phases separated by expert computation. During token dispatch, each rank partitions its ${B_{\text{tok}}}$ local token activation vectors (${\mathbf{x}}\in \mathbb{R}^{d}$, where ${d}$ is the model’s hidden dimension) according to the destination ranks hosting the selected experts. The rank then executes an AllToAll collective (or variable-size `AllToAllv`) to route tokens across the fabric according to the routing matrix. After each rank computes forward passes through its assigned local expert feed-forward networks (FFNs), the token combine phase executes a second AllToAll collective to route output vectors back to their originating ranks. Each rank then computes the weighted combination of expert outputs:

$$
{\mathbf{y}}_i = \sum_{j \in \text{top-}{k_{\text{experts}}}} {{p_{\text{gate}}}}_{i,j} \cdot \text{Expert}_j({\mathbf{x}}_i)
$$

Because routing is data-dependent, so are the required buffer sizes, even when the input tensor shape is fixed. One simplified model treats assignments of different tokens independently: the count for expert ${e}$ is then ${B_e}\sim \text{Binomial}({N} {B_{\text{tok}}}, {p_e})$, where ${p_e}$ is the fixed probability that a token selects expert ${e}$. Correlated tokens or changing router probabilities require a different count model. To avoid reallocating buffers for every routing decision, a capacity-limited implementation can reserve space using an expert capacity factor ${C_{\text{cap}}}\ge 1.0$, a multiplier on each expert’s average share of token assignments ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-lepikhin2021gshard|Lepikhin et al. 2021]]; [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-fedus2022switch|Fedus et al. 2022]]):

$$
\text{Capacity}_{e}= \left\lceil \frac{{N}\times {B_{\text{tok}}}\times {k_{\text{experts}}}}{{N_{\text{experts}}}} \times {C_{\text{cap}}}\right\rceil
$$

The capacity factor exposes a trade-off between reserved space and retained expert assignments. At uniform expected capacity (${C_{\text{cap}}}= 1.0$), some experts can still overflow while others have unused slots. A dropping implementation bypasses excess assignments through the residual connection, changing the computation and potentially harming training quality. Increasing headroom (${C_{\text{cap}}}> 1.0$, for example $1.25$–$1.5$) can reduce overflow. If the implementation transmits every reserved slot, its padded payload grows by approximately a factor of ${C_{\text{cap}}}$ relative to the uniform capacity-one budget; kernels that skip unused slots need not perform the corresponding dummy computation. A dropless implementation retains every assignment and can use variable-size `AllToAllv` to avoid sending unused slots. It still needs enough memory for the realized counts and remains exposed to routing skew.

Because token routing is determined by input semantics, some experts inevitably receive disproportionate token volumes. An expert that receives several times the average load raises its host GPU’s receive traffic by the same excess. The host’s total receive volume depends on the combined load of all experts assigned to it, which is the rank-level quantity in the bound that follows.

Routing skew can create stragglers in both communication and expert computation. An inbound reception bottleneck bounds dispatch completion by the most heavily loaded receiver. Other ranks may finish their transfers earlier, but work that needs the delayed expert outputs must wait. The receive budget gives a lower bound before expert computation and the return exchange are counted:

$$
{T_{\text{dispatch}}}\ge \frac{{B_{\text{max}}}\times {d}\times {s_{\text{elem}}}}{{\text{BW}_{\text{rx}}}}
$$

 where ${B_{\text{max}}}= \max_{i} \sum_{{e}\in \text{rank } {i}} {B_e}$ counts the largest remotely received token batch at any rank ${i}$, restricting ${B_e}$ in this sum to assignments arriving from other ranks. Here ${s_{\text{elem}}}$ is the bytes per activation element, and ${\text{BW}_{\text{rx}}}$ is that rank’s receive bandwidth.

Bisection capacity provides a separate limit. Ring AllReduce exchanges data with logical ring neighbors, whereas AllToAll permits every rank on one side of the bisection to send to every rank on the other. Under uniform destination assignment, a fraction $({N}-1)/{N}\approx 1$ of tokens leaves its source rank; the fraction crossing nodes or a particular fabric cut depends on placement. In the simplified symmetric fabric model, each rank has injection bandwidth ${\text{BW}_{\text{inject}}}$, the rate its port can send into the fabric, and an oversubscription ratio ${R}:1$ gives a switch tier ${R}$ times more downlink than uplink capacity. Usable bisection bandwidth ${\text{BW}_{\text{bisect}}} = ({N}\cdot {\text{BW}_{\text{inject}}}) / (2{R})$ then bounds the time needed to carry traffic across that cut:

$$
{T_{\text{dispatch}}}\ge \frac{{V_{\text{cut}}}}{{\text{BW}_{\text{bisect}}}}
$$

↩︎ Bisection bandwidth and the cost of oversubscription are established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.06 Level 3 Switch and Topology#^sec-network-fabrics-topology|Level 3 Switch and Topology]]**.

**Napkin Math 5.6: The cost of a hot expert rank**

**Problem**: Return to the uniform routing of notebook [5.5](https://mlsysbook.ai/vol2/05_collective_communication/05_collective_communication.html#nbk-collective-communication-alltoall-moe-token-routing): 8 GPUs, 64 experts, 4.096 KB per token, and one 50 GB/s port per GPU. Suppose skew sends one rank’s experts 1.5 times the average remote load. This is an assumed realized routing skew; the per-expert capacity factor reserves total-assignment headroom and does not determine remote arrivals. How does the receive bound on dispatch change?

**Math**:

1.  **Uniform receiver**: Each GPU receives 448 remote tokens, or 1.84 MB, so ${T_{\text{dispatch}}}\ge$ 1.84 MB / 50 GB/s $\approx$ 36.7 μs.
2.  **Hot receiver**: ${B_{\text{max}}}$ rises to 672 remote tokens, or 2.75 MB, so ${T_{\text{dispatch}}}\ge$ 2.75 MB / 50 GB/s $\approx$ 55.1 μs.

**Systems insight**: The exchange cannot finish before its hottest receiver, so a 1.5× load on one rank raises the dispatch bound for the whole layer by the same factor. Transmitting unused capacity slots can add padding bytes; the amount depends on the packing layout rather than on this receive-skew factor alone. A variable-size exchange removes unused-slot traffic but not the receive bound. Expert computation processes local as well as remote assignments, so its work grows by the same factor only if the hot rank’s total local-plus-remote assignment count also grows by that factor, with unchanged work per assignment.

Scale compounds both problems. To amortize small-message overhead across thousands of GPUs, hierarchical MoE runtimes decompose the flat AllToAll into a two-level collective ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-hwang2023tutel|Hwang et al. 2023]]). Intra-node NVLink first coalesces tokens destined for experts on the same remote server node. Participating nodes then exchange aggregated payloads over InfiniBand or RoCE, and receiving GPUs use NVLink to distribute tokens to the GPUs hosting the targeted experts. At the logical level, this replaces ${N}({N}-1)$ directed rank pairs with ${N_{\text{nodes}}}({N_{\text{nodes}}}-1)$ directed node pairs; actual transport connections depend on the implementation. Coalescing can improve link utilization and reduce startup overhead, but the token bytes still have to cross the required fabric cuts, and skew can still overload a destination.

### AllToAll Schedule Selection

^sec-collective-communication-alltoall-schedule-selection

A flat, fixed-size AllToAll schedule that works well for balanced, megabyte-scale peer transfers on eight GPUs can stall across thousands of GPUs when per-peer chunks shrink to a few kilobytes or when expert skew forces every rank to pad its buffers to the hottest receiver’s count. Because `AllToAll` names only the destination-specific contract, the runtime must match its schedule to the traffic matrix and physical hierarchy rather than treating every exchange as one flat pattern. Three schedules cover the common regimes ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.09 AllToAll Exchanges at Scale#^tbl-alltoall-schedule-selection|table 9]]). Direct pairwise exchange suits balanced, coarse per-peer chunks. Hierarchical exchange coalesces many small remote chunks before they cross scarce inter-node links. Variable-size exchange avoids padding when token or embedding counts differ by destination. Hierarchical designs such as Tutel’s two-dimensional exchange demonstrate why the best schedule changes with message size, scale, and topology ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-hwang2023tutel|Hwang et al. 2023]]).

| **Schedule**                        | **When it fits**                                                                                                              | **Cost exposed**                                                                                                                                                  |
|:------------------------------------|:------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Direct pairwise exchange**        | Balanced, coarse per-peer chunks on a small or full-bisection process group                                                   | Each rank injects directly to its peers; fine granularity repeats startup and scheduling cost, while oversubscription can bind the bisection                      |
| **Hierarchical/coalesced exchange** | Many small remote chunks across multi-GPU nodes or rails; pack by remote node, exchange aggregates, then redistribute locally | Coalescing amortizes inter-node startups and respects fast local links, but adds packing, local copies, synchronization, and temporary buffers                    |
| **Variable-size exchange**          | Token or embedding counts differ by destination and padding to the maximum count would waste substantial bandwidth            | Explicit counts and displacements avoid padding, but count exchange and irregular transfers add control overhead; the hottest receiver still sets completion time |

Table 9: **AllToAll Schedule Selection**: The right schedule minimizes the active bound rather than the logical peer count. Direct exchange preserves simplicity, hierarchy coalesces traffic before scarce links, and variable-size exchange removes padding without removing skew.

^tbl-alltoall-schedule-selection

The selection test follows the four terms from perspective [5.1](https://mlsysbook.ai/vol2/05_collective_communication/05_collective_communication.html#psp-collective-communication-alltoall-vs-allreduce-why-scale-differs) and [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.09 AllToAll Exchanges at Scale#^sec-collective-communication-moe-dynamic-routing|section 5.8.1]]. When per-peer chunks are already coarse and source injection or fabric bisection dominates, coalescing cannot shrink the byte term and only adds local copies. When each remote destination receives a small chunk so that the serialized startup cost ${N}{\alpha}$ dominates instead, a hierarchical schedule replaces those many inter-node startups with a single aggregated exchange per remote node. Under routing skew, a variable-size interface keeps padding from inflating ${V_{\text{cut}}}$, though the runtime must still provision memory and time for the hottest receiver’s load. Because these bounds depend on live routing behavior, a runtime must benchmark candidate schedules under the observed token-count distribution, rank placement, and fabric topology rather than relying on a balanced, fixed-size microbenchmark. Even the best schedule, however, must still transmit the full activation or gradient payload unless the system reduces the bytes themselves.

**Self-Check: Question**

1.  Why can MoE token routing with AllToAll encounter contention and tail-latency limits even when its per-worker payload is smaller than that of a dense AllReduce?

    1.  AllToAll transfers more total bytes per GPU than AllReduce, requiring each GPU to send $2(N-1)M$ bytes instead of $2 \frac{N-1}{N} M$ bytes.
    2.  AllToAll exchanges distinct payloads among many peers; routing skew and concurrent cross-fabric transfers can concentrate traffic on shared links and destinations.
    3.  AllToAll cannot execute over InfiniBand fabrics and must fall back to host CPU TCP/IP socket emulation.
    4.  AllToAll mandates single-precision FP32 representation, preventing BF16 or FP16 tensor transfers across remote experts.

2.  True or False: In a mixture-of-experts (MoE) model where tokens are routed across 8 GPUs using full-duplex InfiniBand NDR (50 GB/s per port), issuing 7 concurrent peer transfers allows the GPU to achieve an aggregate outgoing transmission rate of $7 \times 50\text{ GB/s} = 350\text{ GB/s}$.
