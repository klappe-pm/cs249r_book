# V2-05.07 AllReduce Algorithms and Topologies

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05 Collective Communication|V2-05 Collective Communication]]

^sec-communication-collective-operations-collective-operations-allreduce-algorithms-7545

A correct AllReduce must give each of 1,000 GPUs the reduced sum of all 1,000 gradient contributions, subject to the floating-point reduction contract, and the algorithm that delivers it sets the cluster’s scaling ceiling. The naive answer, in which every GPU sends to one central server whose single network link must carry every worker’s gradient, fails first, which makes it the right place to start.

### Naive Approaches Vs. the Bandwidth Bottleneck

^sec-communication-collective-operations-naive-vs-optimal

Consider a naive implementation using a parameter server (a star topology), with a dedicated server in addition to the workers. All ${N}$ workers send their gradients to that server; it sums them and sends the result back. The server must receive ${N}\times {M}$ bytes and send ${N}\times {M}$ bytes, so its bandwidth budget grows as ${T_{\text{comm}}} \propto {N}\times {M}/ {\beta}$. At 1,000 GPUs, concentrating those transfers at one server creates a scaling bottleneck even if the arithmetic is fast.

This naive approach captures the pressure that early distributed ML frameworks had to manage. Parameter-server systems receive, aggregate, and redistribute model updates through a server tier, and practical implementations shard the parameter space to spread that load ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-dean2012large|Dean et al. 2012]]; [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-li2014|Li et al. 2014]]). Sharding reduces the per-server traffic from ${N}\times {M}$ to ${N}\times {M}/{K_{\text{srv}}}$ (where ${K_{\text{srv}}}$ is the number of servers). The server tier still grows as workers and model state grow, and it introduces additional complexity in parameter partitioning and consistency management.

The bottleneck comes from concentration, not from total traffic. Every AllReduce algorithm moves more total data as workers are added, because every worker’s contribution must be combined and every worker must receive the result. A star, however, routes all of that traffic through one endpoint, so the server’s time grows as ${N}\times {M}/{\beta}$. A ring spreads the same work so that each rank sends about $2{M}$ and its time stays near $2{M}/{\beta}$ however large ${N}$ becomes. The ratio of the two is about ${N}/2$, so at 1,024 workers the server’s byte time is roughly 500× the ring’s, before startup, arithmetic, or contention are counted. Bandwidth optimality makes that comparison precise by measuring an algorithm’s required byte movement against a lower bound under a stated communication model, which the next derivation supplies for AllReduce.

**War Story 5.1: When the parameter server became the bottleneck (2017)**

**Context**: In 2017, Alexander Sergeev and Mike Del Balso’s team at Uber open-sourced Horovod as part of Uber’s Michelangelo ML platform, where TensorFlow training jobs needed to scale across many GPUs without forcing every model author to rewrite large portions of training code ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-sergeev2018horovod|Sergeev and Balso 2018]]).

**Mechanism**: TensorFlow’s stock distributed training relied on a parameter-server pattern that concentrated gradient traffic through a central tier. As worker count ${N}$ grew, the central server link saturated, degrading scaling efficiency.

**Impact**: Scaling training beyond a single node resulted in severe throughput bottlenecks and required complex, model-specific parameter partitioning.

**Fix**: Uber adopted Baidu’s ring AllReduce algorithm ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-gibiansky2017baidu|Gibiansky 2017]]), wrapping bandwidth-optimal collective reduction behind a lightweight API that replaced parameter servers with ring communication.

**Systems lesson**: A collective algorithm is also a developer interface. Scaling improves when the communication primitive is both bandwidth efficient and easy enough that teams actually use it correctly.

### The Bandwidth-Optimal Lower Bound

^sec-communication-bandwidth-lower-bound

Before choosing a schedule to replace the parameter server, we need to know the minimum byte volume any point-to-point AllReduce must move when ${N}$ ranks each start with an ${M}$-byte gradient and neither compression nor in-network switch reduction is used. Reducing one independent data item across ${N}$ ranks and distributing its result requires at least $2({N}-1)$ item transfers in aggregate ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-patarasuk2009|Patarasuk and Yuan 2009]]). The count has two halves. Combining ${N}$ contributions that start on ${N}$ different ranks takes at least ${N}-1$ transfers, because each transfer combines at most two partial sums and so reduces the number of separate partial sums by at most one. Delivering the finished value to the other ${N}-1$ ranks then takes at least one transfer each. For an ${M}$-byte tensor, the minimum aggregate sent volume is therefore $2({N}-1){M}$ bytes. At least one rank must send the average share, $2({N}-1){M}/{N}$ bytes; a balanced algorithm assigns that share to every rank.

Take ${\beta}$ as each rank’s available send bandwidth, with equal receive bandwidth that can operate simultaneously. Dividing the required sent volume by ${\beta}$ gives the full-duplex bandwidth lower bound:

$$
{T_{\text{bandwidth}}^{\text{min}}}= \frac{2({N}-1)}{{N}} \cdot \frac{{M}}{{\beta}}
$$

As ${N}$ grows large, the bandwidth lower bound approaches $2{M}/{\beta}$, independent of ${N}$ (principle [[01 Books/Volume II - Scaling/02 Distributed ML/V2 Distributed ML Principles#^pri-allreduce-bandwidth-bound|11]]). Ring AllReduce matches the required byte volume under this model; startup and local reduction still add time ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-patarasuk2009|Patarasuk and Yuan 2009]]; [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-thakur2005|Thakur et al. 2005]]). On a 64-GPU cluster synchronizing the chapter’s 1 GB reference buffer over 50 GB/s links, the ring’s byte term is about 39.4 ms, establishing the physical floor against which every concrete AllReduce schedule that follows must be judged.

### Ring AllReduce

^sec-communication-collective-operations-collective-operations-ring-allreduce-ffce

To hit that $2({N}-1){M}/{N}$ byte floor without funneling traffic through a central server, Ring AllReduce arranges nodes in a logical loop ($0 \to 1 \to \dots \to {N}-1 \to 0$) where each node sends to its successor while receiving from its predecessor at the same time. Splitting the tensor into equal chunks spreads the required byte volume across every rank and reaches the bandwidth lower bound in the ideal endpoint model ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-patarasuk2009|Patarasuk and Yuan 2009]]).

The algorithm splits the vector of size ${M}$ into ${N}$ chunks and then alternates communication and local reduction in two phases, a ReduceScatter phase (often called scatter-reduce) followed by an AllGather phase. [Algorithm 1](https://mlsysbook.ai/vol2/05_collective_communication/05_collective_communication.html#algo-ring-allreduce) states the mechanics before the figure and trace make the same dataflow concrete.

$N$

Across the $2({N}-1)$ send/receive rounds each rank moves ${M}/{N}$ bytes per round, for $2({N}-1){M}/{N}$ bytes sent and the same received. The bandwidth term therefore reaches the information-theoretic lower bound, while the latency term grows as $2({N}-1){\alpha}$. On a four-GPU ring with wrap-around links, the state progresses in two phases ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^fig-ring-allreduce|figure 3]]). In row (a), ${N}-1 = 3$ ReduceScatter steps circulate gradient chunks A through D until each GPU holds exactly one fully reduced partition (green ${\Sigma} {A}$ through ${\Sigma} {D}$). In row (b), ${N}-1 = 3$ subsequent AllGather steps forward those finished shards around the ring until every device holds the complete sum.

![[90 Assets/Volume II/05 Collective Communication/Ring Allreduce cb2830f899.svg]]

Figure 3: **Ring AllReduce Data Flow**: Four GPUs in a logical ring, each gradient split into chunks A to D; the wrap-around link closes the ring from GPU 3 back to GPU 0. (a) After the ${N}-1$ ReduceScatter steps, in which every GPU sends one chunk to its neighbor and adds the chunk it receives, each GPU holds one fully reduced chunk. (b) After ${N}-1$ AllGather steps that forward those finished chunks around the same ring, every GPU holds the full sum. Every link carries data in every step, so each GPU sends $2\frac{{N}-1}{{N}}{M}$ bytes in total, while the $2({N}-1)$ steps each pay one startup latency ${\alpha}$.

^fig-ring-allreduce

Logical ring edges may share physical links, and startup, local reduction, or contention can leave transfer capacity unused, so byte optimality does not guarantee peak physical-link utilization. To see how the logical schedule itself reaches that byte lower bound, consider 4 GPUs reducing a vector of 4 elements by summation. Each GPU ${i}$ starts with a local gradient vector ${\mathbf{g}}_i = [{a}_i, {b}_i, {c}_i, {d}_i]$ split into 4 chunks (one per GPU), and the algorithm proceeds through two phases.

**Example 5.1: Ring AllReduce: Two-phase example (4 GPUs)**

**Scenario**: Four GPUs ($0 \to 1 \to 2 \to 3 \to 0$) perform a Ring AllReduce on local vectors $[1, 5, 3, 7]$, $[2, 6, 4, 8]$, $[3, 7, 5, 9]$, and $[4, 8, 6, 10]$ to compute the element-wise sum $[10, 26, 18, 34]$.

**Diagnosis**: The trace has to show three properties of the schedule, namely that it takes $2({N}-1) = 6$ steps, that every GPU sends and receives in every step, and that each step moves only one chunk. Ring AllReduce splits each vector into ${N}=4$ chunks ${a}$, ${b}$, ${c}$, ${d}$. In ReduceScatter step ${s}$ (${s}= 1, 2, 3$), GPU ${i}$ sends its running copy of chunk $({i}-{s}+1) \bmod 4$ to GPU $({i}+1) \bmod 4$, which adds it to its own copy. After the third step, each GPU owns one fully reduced chunk. In AllGather step ${s}$, GPU ${i}$ forwards the finished chunk it completed or received most recently to GPU $({i}+1) \bmod 4$, which stores it without arithmetic. In each of the six steps, every GPU receives one chunk and updates the value it holds ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^tbl-ring-allreduce-trace|table 5]]).

| **Step**            | **GPU 0** | **GPU 1** | **GPU 2** | **GPU 3** |
|:--------------------|:---------:|:---------:|:---------:|:---------:|
| **ReduceScatter 1** |   d: 17   |   a: 3    |   b: 13   |   c: 11   |
| **ReduceScatter 2** |   c: 14   |   d: 25   |   a: 6    |   b: 21   |
| **ReduceScatter 3** |   b: 26   |   c: 18   |   d: 34   |   a: 10   |
| **AllGather 1**     |   a: 10   |   b: 26   |   c: 18   |   d: 34   |
| **AllGather 2**     |   d: 34   |   a: 10   |   b: 26   |   c: 18   |

Table 5: **Ring AllReduce Trace**: The chunk each of four GPUs receives in each of the six steps. In the three ReduceScatter steps the GPU adds the incoming chunk to its running partial sum; in the three AllGather steps it stores an already finished sum.

^tbl-ring-allreduce-trace

Every cell in every row is filled, so every GPU receives (and, symmetrically, sends) one chunk in every step, and after the sixth step every GPU holds \[10, 26, 18, 34\]. The steps are also chained, because the chunk a GPU sends next is the one it has just received. A GPU with a slow link therefore holds up every step, and in bandwidth-bound steps the whole collective slows by about the same factor as that link.

**Systems lesson**: Ring AllReduce achieves the optimal byte volume under the stated model: each GPU sends $2\frac{{N}-1}{{N}}{M}$ total bytes, approaching $2{M}$ as ${N}$ grows, while the startup-round count continues to grow. Physical-link utilization also depends on placement and runtime overhead.

**Checkpoint 5.2: Ring AllReduce mechanics**

Verify your understanding of bandwidth-optimal reduction:

**Step count**: calculate the number of sequential steps required for a ring of ${N}$ GPUs to complete the full AllReduce.

**Bandwidth optimality**: explain why Ring AllReduce is bandwidth-optimal, including how many times each byte of the total message ${M}$ traverses the network per GPU.

**Straggler impact**: determine the impact on total collective completion time when one GPU in the ring is 50 percent slower than the others.

**Send/receive duality**: assess the True or False claim that every GPU is both a sender and a receiver in every step of Ring AllReduce.

Generalizing the six-step trace of example [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^exmp-collective-communication-ring-allreduce-step-by-step-trace-4-gpus|5.1]] to ${N}$ ranks yields the closed-form cost model for those checkpoint questions. Each node sends and receives $\frac{{M}}{{N}}$ bytes in each of the $2({N}-1)$ steps.

$$
{T_{\text{ring}}} = \underbrace{2({N}-1){\alpha}}_{\text{Latency Term}} + \underbrace{2\frac{{N}-1}{{N}} \frac{{M}}{{\beta}}}_{\text{Bandwidth Term}}
$$

The bandwidth term approaches $2{M}/{\beta}$ as ${N}\to \infty$, reaching the full-duplex lower bound. Each rank sends nearly $2{M}$ bytes across the two phases and receives the same amount concurrently. In contrast, the latency term scales linearly with ${N}$. Across 10,000 nodes, 19,998 sequential startup rounds accumulate substantial latency, which explains why Ring AllReduce becomes uncompetitive for small payloads. For a multi-gigabyte gradient buffer at moderate rank count, however, the bandwidth term dominates completely, as the 70B calculation in notebook [5.2](https://mlsysbook.ai/vol2/05_collective_communication/05_collective_communication.html#nbk-collective-communication-allreduce-cost-70b-model) confirms.

**Napkin Math 5.2: AllReduce cost for a 70B model**

**Problem**: Consider a communication-only baseline for a 70B parameter model across 64 GPUs connected by InfiniBand NDR (50 GB/s per port). The bandwidth term barely depends on rank count, so this smaller group reproduces the bandwidth-only estimate from the opening definition while keeping the latency term visible. Each rank contributes a complete logical gradient buffer communicated in BF16 (2 bytes per parameter). This calculation isolates collective cost without establishing that the training state fits on each GPU. How long does one AllReduce take?

**Step 1**: Size the gradient payload. Each rank in this baseline contributes the complete logical gradient tensor of $7 \times 10^{10} \times 2\ \text{bytes}$ $=$ 140 GB. A hybrid layout that partitions the model would instead reduce corresponding gradient shards within smaller groups and requires its own calculation.

**Step 2**: Apply the Ring AllReduce bandwidth formula.

$$
{T_{\text{bandwidth}}}= 2 \cdot \frac{{N}-1}{{N}} \cdot \frac{{M}}{{\beta}}
$$

Substituting: ${T_{\text{bandwidth}}}$ = 1.96875 $\times$ 140 GB / 50 GB/s $\approx$ 5,512.5 ms.

**Step 3**: Add the latency term.

$$
{T_{\text{latency}}}= 2({N}-1) \cdot {\alpha}
$$

Substituting: ${T_{\text{latency}}}=$ 126 $\times$ 1.5 μs = 0.2 ms.

**Step 4**: Total communication time. Total: ${T_{\text{ring}}} \approx$ 5,512.5 ms + 0.2 ms $\approx$ 5,512.7 ms.

**Systems insight**: The modeled full-buffer AllReduce takes over five seconds under the stated link and rank assumptions, and almost all of it is the bandwidth term. Its effect on step time depends on how much remains exposed relative to useful computation. When it is fully exposed, halving it saves about 2.8 s per step; across a 100,000-step campaign on these 64 GPUs, that is roughly 4,900 GPU-hours of reserved accelerator time. Large-scale training systems can launch reductions for output-side gradients while input-side layers are still computing. Partitioned training also changes each rank’s payload and participating group, so this complete-gradient budget must be recomputed for the actual layout.

### Tree AllReduce

^sec-communication-collective-operations-tree-allreduce

Ring AllReduce’s byte efficiency comes with many startup rounds. As the group grows, the $2({N}-1){\alpha}$ term can exceed the byte-transfer term for a fixed payload; the crossover depends on the measured path parameters. Tree AllReduce reduces the number of dependent rounds. In the simple reduce phase, pairs combine contributions and forward partial sums toward a root, taking $\log_2 {N}$ steps for a balanced power-of-two group. The broadcast phase distributes the result in another $\log_2 {N}$ steps. This shorter dependency chain motivates the comparison before bandwidth costs are counted.

![[90 Assets/Volume II/05 Collective Communication/Collective Communication Ring Tree Divergence 9791d7ad1b.svg]]

*Latency rounds against rank count N on linear axes. An amber straight line labeled ring, 2 times N minus 1, climbs steadily; a blue curve labeled tree, 2 log base 2 of N, bends over and stays near the bottom.*

*Ring latency grows with N; tree stays logarithmic.*

The simple full-message tree loses parallel activity as contributions converge. A ring activates all ${N}$ logical edges in each round. In a pairwise tree reduction, the first round has ${N}/2$ senders and ${N}/2$ receivers, so every rank is still active. The next round has ${N}/4$ senders and ${N}/4$ receivers, and the final reduction exchange involves two ranks while the remaining $({N}-2)$ have completed their upstream contribution. Sending the full message through successive levels adds byte-transfer time along the dependency path. This is a limitation of the simple schedule, not every tree-based implementation or every physical link mapping.

The resulting time complexity depends on the specific tree variant. A simple reduce-then-broadcast tree has logarithmic latency but nonuniform traffic and root/interior bottlenecks. Recursive doubling, in which partners at doubling distances exchange the entire tensor in each of $\log_2 {N}$ rounds, also has a logarithmic round count and incurs $\mathcal{O}(\log {N})$ full-message bandwidth per rank. The following simplified model, which uses the simple tree’s counts, captures the latency advantage and the potential bandwidth penalty of tree-like collectives:

$$
{T_{\text{tree-like}}}\approx \underbrace{2\log_2 {N}\cdot {\alpha}}_{\text{Latency}} + \underbrace{2 \log_2 {N}\frac{{M}}{{\beta}}}_{\text{Bandwidth penalty in full-message exchange variants}}
$$

The latency term is logarithmic ($\mathcal{O}(\log {N})$). For 1,024 nodes, Ring needs 2,046 steps while Tree needs only 20. That roughly 100× reduction in steps makes Tree attractive for small, frequent collectives across large process groups, such as scalar reductions, control messages, or small-batch activation reductions. The bandwidth term carries the penalty, because tree-like algorithms can underutilize links or concentrate traffic on interior links, and recursive-doubling-style full-message exchanges add a $\log_2 {N}$ bandwidth factor. These penalties make naive tree variants a poor choice for data parallelism’s large gradient AllReduce, where bandwidth efficiency determines whether the network is saturated or partially idle.

For large-scale data parallelism, this bandwidth penalty decides the comparison whenever the implementation repeatedly exchanges full messages or creates root/interior bottlenecks. On the 64-GPU cluster of [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-bandwidth-lower-bound|section 5.6.2]], the simple tree forwards the whole tensor once per level on the way up and once per level on the way down, $2\log_2 64 = 12$ full-message transfers. Its byte time is about 240 ms against the ring’s 39.4 ms, or 6.1× the ring’s byte time. The difference of roughly 200 ms per step would accumulate to about 5.6 hours over a 100,000-step run if fully exposed, although actual wall-clock savings also depend on startup, placement, and overlap. For a 70B-parameter model’s 140 GB gradient AllReduce across 1,000 GPUs, a bandwidth-inefficient tree-like variant can erase the latency advantage that motivated it. Optimized double-tree algorithms exist precisely to keep logarithmic latency without imposing that naive bandwidth penalty.

Small activation reductions provide a useful case for fewer startup rounds. For an eight-GPU group communicating a 1 MB tensor, the simple model reduces Ring’s $2(8-1){\alpha}= 14{\alpha}$ to Tree’s $2\log_2(8){\alpha}= 6{\alpha}$, but Tree’s byte term remains about 3.4× Ring’s. Whether the saved startups outweigh those extra byte transfers depends on the measured latency and bandwidth. Tensor-parallel collectives also have a scheduling constraint independent of this comparison: a layer that needs the reduced activation must wait for it. A critical-path dependency does not by itself imply a latency-dominated transfer or select a tree algorithm.

### Recursive Halving-Doubling (Butterfly)

^sec-communication-butterfly

The simple full-message Tree reduces startup rounds but repeats more byte-transfer work than Ring. Recursive halving-doubling, sometimes called the Butterfly algorithm, combines logarithmic rounds with the optimal byte volume under the flat-network model. It pairs ranks exactly as recursive doubling does, but where recursive doubling exchanges the whole tensor in every round, halving-doubling halves the exchanged region in each ReduceScatter round and doubles it in each AllGather round. That difference removes the $\log_2 {N}$ byte penalty. For a power-of-two group, it uses $2\log_2 {N}$ rounds: $\log_2 {N}$ ReduceScatter rounds followed by $\log_2 {N}$ AllGather rounds. A partner-bit index ${k}$ selects the XOR pairing with mask $2^{k}$. The ReduceScatter trace below visits those bits in increasing order as messages shrink; the matching AllGather reverses that order as the assembled result grows.

In the ReduceScatter phase (first $\log_2 {N}$ rounds), GPU ${i}$ partners with GPU ${i}\oplus 2^{k}$ (XOR of indices). Because the two partners made identical retention choices in all earlier rounds, both enter round ${k}$ holding partial sums for the exact same ${M}/2^{k}$-byte region of the tensor. They split that active region in half, retain complementary halves of size ${M}/2^{{k}+1}$, and send the other half to each other to add into the half each retained. Across the $\log_2 {N}$ rounds, the bytes each GPU sends form a geometric series ${M}/2 + {M}/4 + \dots + {M}/{N} = \frac{{N}-1}{{N}}{M}$, leaving each GPU with a distinct ${M}/{N}$-byte slice of the fully reduced result. AllGather traverses the partner bits in reverse, exchanging completed regions of doubling size ${M}/{N}, 2{M}/{N}, \dots, {M}/2$ until every rank holds the full result.

Summing the $2\log_2 {N}$ startups and the two symmetric geometric byte series gives the recursive halving-doubling cost:

$$
{T_{\text{butterfly}}}= 2\log_2 {N}\cdot {\alpha}+ 2\frac{{N}-1}{{N}} \cdot \frac{{M}}{{\beta}}
$$

The schedule combines logarithmic latency ($\mathcal{O}(\log {N})$, like Tree) with bandwidth-optimal data movement ($2({N}-1)/{N}\cdot {M}/{\beta}$, like Ring). The catch is that it requires nonneighbor communication (GPU ${i}$ must communicate with GPU ${i}\oplus 2^{k}$, which may be physically distant), and it requires ${N}$ to be a power of two. For clusters where ${N}$ is not a power of two, additional complexity is needed to handle the irregular cases.

Recursive halving-doubling is used in MPI-style collective implementations and is useful as a theoretical point in the latency-bandwidth trade-off ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-thakur2005|Thakur et al. 2005]]). NVIDIA’s GPU collective backend, the NVIDIA Collective Communications Library (NCCL), offers implementation families that include ring, tree-derived, hierarchical, NVLink/NVSwitch-aware, and pattern-aware choices, with exact names and availability changing by version and topology ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-jeaugey2017nccl|Jeaugey 2017]]; [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-nvidiaNcclUserGuide|NVIDIA 2026]]). Whatever a particular release calls them, practical communication libraries select algorithms through a topology-aware cost model because nonlocal communication patterns can create contention on shared network links that erodes theoretical advantages.

The partner distance is where topology enters. Consider the ReduceScatter phase for 8 GPUs placed four per node on two nodes, GPUs 0–3 on the first and GPUs 4–7 on the second, which proceeds in $\log_2(8) = 3$ rounds. In round ${k}=0$, each GPU ${i}$ partners with GPU ${i}\oplus 1$, pairing neighbors: (0,1), (2,3), (4,5), (6,7). They exchange half their data and reduce, and the lower-numbered GPU of each pair keeps the first half of the tensor while its partner keeps the second half. In round ${k}=1$, the distance doubles: GPU ${i}$ partners with GPU ${i}\oplus 2$, creating pairs (0,2), (1,3), (4,6), (5,7). GPUs 0 and 2 both hold the first half, so they split it between them, and GPUs 1 and 3 likewise split the second half. In round ${k}=2$, the distance doubles again: GPU ${i}$ partners with GPU ${i}\oplus 4$, creating pairs (0,4), (1,5), (2,6), (3,7).

Physical placement determines the cost of these logical pairings ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^fig-butterfly-rounds|figure 4]]). Rounds ${k}=0$ and ${k}=1$ pair GPUs within a node, but in round ${k}=2$ every GPU on the first node exchanges with one on the second, so that round crosses the node boundary. On eight-GPU nodes the same crossing would appear one round later, at ${k}=3$ in a 16-rank group. Keeping consecutive ranks on one node confines the large exchanges to fast local links and leaves only the smallest ones on the slower fabric. In a separate 1,024-rank example, the final ReduceScatter round pairs GPU ${i}$ with GPU ${i}\oplus 512$. If the two rank halves occupy different racks, those exchanges share the inter-rack fabric. The algorithm’s logarithmic rounds and optimal byte volume therefore do not establish its runtime advantage; placement, shared paths, and the changing chunk size in each round must enter the comparison.

![[90 Assets/Volume II/05 Collective Communication/Collective Communication Butterfly Rounds d084d290cb.svg]]

Figure 4: **Halving-Doubling Partners across a Node Boundary**: The ReduceScatter phase of recursive halving-doubling on 8 GPUs placed four per node. In round ${k}$, GPU ${i}$ exchanges with GPU ${i} \oplus 2^{{k}}$ and sends half of the region it still holds, so the exchanged volume halves each round. (a) and (b) The first two rounds pair GPUs inside a node and use NVLink. (c) The last round pairs every GPU with one on the other node, so the round with the smallest message is the only one that crosses the slower fabric. ### Double Binary Tree

^sec-communication-double-tree

Where recursive halving-doubling requires power-of-two groups and long-distance XOR pairings across fabric cuts, a tree schedule can follow physical topology more flexibly, provided it overcomes the single-tree bandwidth bottleneck. In a single binary tree, half the ranks sit at the leaves and only send (during reduction) or only receive (during broadcast), leaving half of each leaf’s bidirectional link capacity idle while interior nodes do double duty. NCCL resolves this imbalance with a double binary tree ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-jeaugey2017nccl|Jeaugey 2017]]; [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-nvidiaNcclUserGuide|NVIDIA 2026]]), constructing two independent binary trees with complementary interior-node roles and running both simultaneously so each carries half the payload.

The complementary-tree construction balances endpoint work by making ranks that act as interior nodes in one tree act as leaves in the other. With eight ranks, build the first tree by labeling the nodes of a binary tree in the order of an in-order traversal (left subtree, then node, then right subtree). In a balanced seven-node tree labeled from 0, in-order traversal puts the leaves at the even ranks 0, 2, 4, and 6 and the interior nodes at 1, 3, and 5. In one simple construction, the eighth rank, 7, becomes the root, with rank 3, the root of the seven-node tree, as its only child. A single child is enough, because rank 7 joins the interior only so that every rank is interior in exactly one of the two trees. The odd ranks 1, 3, 5, and 7 thus form the first tree’s interior and the even ranks are its leaves. The second tree shifts every rank by one position, so the even ranks become its interior and the odd ranks its leaves ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^fig-double-binary-tree|figure 5]]). Each tree carries half the tensor, ${M}/2$, and the two halves never meet.

![[90 Assets/Volume II/05 Collective Communication/Collective Communication Double Binary Tree 1a70c9e701.svg]]

Figure 5: **Complementary Roles in a Double Binary Tree**: Two reduction trees over eight ranks, each carrying half of the tensor toward its root. (a) The first tree places the odd ranks at its interior and the even ranks at its leaves. (b) The second tree shifts every rank by one, which swaps the roles. The strip below shows the result: every rank is an interior node in exactly one tree and a leaf in the other, so it forwards one combined half and sends one half of its own, about ${M}$ in the reduce phase. The broadcast phase runs the same trees in the opposite direction.

^fig-double-binary-tree

Two further steps bring the byte term down from the simple tree’s $2\log_2 {N}\cdot {M}/{\beta}$ to about $2{M}/{\beta}$. First, each tree pipelines its half in small chunks, so while one chunk moves up from the leaves, the next is already leaving them and every level works at once. Tree depth then adds startup rounds and a short pipeline fill, not repeated full-message transfers. Second, count what one rank sends during the reduce phase. As an interior node of one tree it combines the inputs of its (at most two) children and forwards one ${M}/2$ stream to its parent. As a leaf of the other tree it sends its own ${M}/2$ contribution. It therefore sends about ${M}$ in total. The broadcast phase mirrors that traffic, for about $2{M}$ per rank across both phases, the same per-rank volume as the ring. This logical balance does not guarantee that every physical link stays busy or that both trees avoid shared fabric bottlenecks; rank placement and routing still matter.

The combined performance is approximately:

$$
{T_{\text{double-tree}}}\approx 2\log_2 {N}\cdot {\alpha}+ \frac{2{M}}{{\beta}}
$$

The ideal bandwidth term approaches $2{M}/{\beta}$ while the startup-round count remains logarithmic. This combination makes the double binary tree a useful candidate across message sizes that penalize either the ring’s many rounds or the simple tree’s repeated full-message transfers. Complementary endpoint roles do not ensure disjoint physical paths, so topology-aware tree construction seeks a good placement, and measurements must establish the achieved rate under contention.

### The Algorithm Crossover Point

^sec-communication-collective-operations-algorithm-crossover

Plotting the three cost models for a 256-GPU group on a 200 Gbps fabric, over message sizes from 1 KB to 10 GB, shows the simple Tree and Ring curves intersecting near 1 MB ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^fig-allreduce-crossover|figure 6]]). At small sizes, fewer startup rounds favor the tree schedules; at large sizes, the simple full-message Tree pays more byte-transfer time. The Double Binary Tree curve includes illustrative overhead factors, so it approaches a comparable bandwidth-dominated regime without representing a measured library result. The candidate schedules differ in their latency and bandwidth terms, in whether they reach the bandwidth lower bound, and in the constraint each one places on the group ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^tbl-allreduce-comparison|table 6]]).

| **Algorithm**   |           **Latency**           |               **Bandwidth**                | **Bandwidth optimal?** |         **Constraint**          |
|:----------------|:-------------------------------:|:------------------------------------------:|:----------------------:|:-------------------------------:|
| **Ring**        |   $\mathcal{O}({N}){\alpha}$    |  $2\frac{{N}-1}{{N}}\frac{{M}}{{\beta}}$   |          Yes           |              None               |
| **Simple Tree** | $\mathcal{O}(\log {N}){\alpha}$ | $\mathcal{O}(\log {N})\frac{{M}}{{\beta}}$ |           No           |              None               |
| **Butterfly**   | $\mathcal{O}(\log {N}){\alpha}$ |  $2\frac{{N}-1}{{N}}\frac{{M}}{{\beta}}$   |          Yes           |          ${N}= 2^{m}$           |
| **Double Tree** | $\mathcal{O}(\log {N}){\alpha}$ |       $\approx\frac{2{M}}{{\beta}}$        |      Near-optimal      | Complementary tree construction |

Table 6: **AllReduce Algorithm Comparison**: Each algorithm occupies a different point in the latency-bandwidth trade-off space. Ring and Butterfly achieve bandwidth optimality with different latency characteristics, while Double Binary Tree combines logarithmic depth with a near-optimal byte term. The Tree row refers to the simple full-message model, not every tree implementation.

^tbl-allreduce-comparison

![[90 Assets/Volume II/05 Collective Communication/Cell 14 Output 1 406b5592af.png]]

Figure 6: **Algorithm Crossover in Collective Communication**: Below about 1 MB the simple tree’s fewer startup rounds make it faster than the ring; above that size the ring’s smaller byte volume wins, and the double binary tree tracks the faster of the two across most sizes. The curves are modeled AllReduce times for a 256-GPU group on a 200 Gbps interconnect with ${\alpha} = 1\ {\text{µ}}\text{s}$, over messages from 1 KB to 10 GB. The double binary tree curve applies modest latency and bandwidth overhead factors (1.2$\times$ and 1.05$\times$) to its ideal cost, so it illustrates the model rather than a measured library result.

^fig-allreduce-crossover

The intersection near 1 MB in [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^fig-allreduce-crossover|figure 6]] marks where the modeled Ring and simple Tree have equal total cost. It is an algorithm crossover, distinct from the startup-versus-transfer crossover for one message. Setting ${T_{\text{ring}}} = {T_{\text{tree}}}$ and solving for payload ${M}$ identifies the point where Ring’s lower byte cost compensates for its additional startup rounds:

$$
{T_{\text{ring}}} = 2({N}-1){\alpha}+ 2\frac{{N}-1}{{N}}\frac{{M}}{{\beta}}
$$

$$
{T_{\text{tree}}} = 2\log_2 {N}\cdot {\alpha}+ 2\log_2 {N}\cdot \frac{{M}}{{\beta}}
$$

For large ${N}$, $({N}-1) \approx {N}$ and $\frac{{N}-1}{{N}} \approx 1$, so the ring pays a latency term proportional to ${N}$ while moving each byte close to the bandwidth limit:

$$
{T_{\text{ring}}} \approx 2{N}{\alpha}+ \frac{2{M}}{{\beta}}, \quad {T_{\text{tree}}} \approx 2\log_2 {N}\cdot {\alpha}+ \frac{2\log_2 {N}\cdot {M}}{{\beta}}
$$

The tree has the opposite shape: logarithmic startup cost, but each message byte moves through more stages. Setting the estimates equal isolates the message size where the cheaper latency path stops compensating for the extra bandwidth work:

$$
2{N}{\alpha}+ \frac{2{M}}{{\beta}} = 2\log_2 {N}\cdot {\alpha}+ \frac{2\log_2 {N}\cdot {M}}{{\beta}}
$$

$$
\frac{2{M}}{{\beta}} - \frac{2\log_2 {N}\cdot {M}}{{\beta}} = 2\log_2 {N}\cdot {\alpha}- 2{N}{\alpha}
$$

$$
\frac{2{M}}{{\beta}}(1 - \log_2 {N}) = 2{\alpha}(\log_2 {N}- {N})
$$

Since ${N}\gg \log_2 {N}$ for large clusters, $(\log_2 {N}- {N}) \approx -{N}$ and $(1 - \log_2 {N}) \approx -\log_2 {N}$, yielding:

$$
\frac{2{M}}{{\beta}}(-\log_2 {N}) \approx 2{\alpha}(-{N})
$$

$$
\boxed{{M_{\text{crossover}}} \approx \frac{{N}\cdot {\alpha}\cdot {\beta}}{\log_2 {N}}}
$$

The log-aware crossover formula is the large-${N}$ approximation to the exact crossover ${M_{\text{crossover}}}({N})$ derived in **[[05 Reference/Volume II - Scaling/V2 Communication Foundations#^sec-appdx-comm-foundations-ring-vs-tree|Ring vs. tree vs. recursive halving-doubling]]**. Within this two-algorithm model, Ring wins above the crossover because its byte savings exceed its extra startup cost; the simple Tree wins below it because the startup saving is larger. The crossover rises with ${N}$ because each added rank adds Ring startup rounds faster than it adds Tree byte transfers. It rises with ${\alpha}$ because each of those rounds costs more, and with ${\beta}$ because each byte saved is worth less time. A bucket that favors Ring on a small group can therefore favor Tree on a larger one. Optimized trees and topology-dependent rates require separate comparisons.

On the reference cluster, with the chapter’s effective NDR ${\alpha}=$ 1.5 μs and ${\beta}=$ 50 GB/s across all 1,024 GPUs, the estimate gives ${M_{\text{crossover}}} \approx$ $\frac{1{,}024 \times 1.5\ {\text{µ}}\text{s} \times 50\ \text{GB/s}}{\log_2 1{,}024} = \frac{1{,}024 \times 1.5\ {\text{µ}}\text{s} \times 50\ \text{GB/s}}{10}$ $\approx$ 7.7 MB. A gradient bucket of tens of megabytes or the full model gradient therefore sits on the ring side of the crossover, while a reduction of a few hundred kilobytes sits on the tree side. The section’s two other configurations change the group and the fabric, which moves the crossover. A smaller 256-GPU group on a slower 200 Gbps fabric with ${\alpha}= 1\ {\text{µ}}\text{s}$ moves the curves’ intersection down to about 1 MB ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^fig-allreduce-crossover|figure 6]]). A 64-GPU group on a still slower, higher-latency fabric places a 1 MB buffer almost exactly on the crossover (notebook [5.3](https://mlsysbook.ai/vol2/05_collective_communication/05_collective_communication.html#nbk-collective-communication-ring-vs-tree-crossover)).

This crossover separates only Ring from the simple Tree. Butterfly pays Ring’s byte term with logarithmic startup rounds ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^tbl-allreduce-comparison|table 6]]), so for a power-of-two group on a flat network the model gives Ring no win over Butterfly. Ring’s case rests on what that model leaves out. Ring runs on any group size, and its exchanges stay between neighbors, whereas Butterfly’s long-distance pairings can contend on shared links ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-butterfly|section 5.6.5]]).

NCCL’s algorithm selection is more nuanced than a two-way split. The double binary tree offers logarithmic latency with near-optimal bandwidth, so it competes with both Ring and Tree across a broad range of message sizes. The library also weighs the number of channels (parallel communication streams), the network topology, and whether a hop is inter-node or intra-node. The effective selection logic resembles a multi-way decision indexed by message size, GPU count, and topology type rather than a single crossover point. The crossover formula nevertheless explains the shape of those choices, because every candidate trades startup rounds against bytes moved. The model therefore names a candidate worth benchmarking rather than proving the library wrong, and an override is retained only after measured collective duration and exposed training-step time confirm it.

Training frameworks decide which payloads reach that analysis. PyTorch DistributedDataParallel (DDP) groups gradient tensors into buckets ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.11 Communication-Computation Overlap#^sec-communication-bucket-fusion|section 5.10.3]]), while FSDP groups parameter gathers and gradient reductions according to its sharding units. A bucket size alone does not locate a crossover, because rank count, effective startup cost, and available bandwidth also enter the comparison. NCCL’s algorithm selection must therefore be evaluated for the actual invocation and topology rather than inferred from a nominal bucket-size range, so the worked comparison that follows states its group size, payload, and fabric.

**Napkin Math 5.3: The ring vs. tree crossover**

**Problem**: A cluster synchronizes a 1 MB buffer across 64 GPUs. The network has latency ${\alpha}=$ 10 μs and bandwidth ${\beta}=$ 10 GB/s. Which algorithm performs better: Ring or Tree?

**Math**:

**Latency**:

1.  **Ring Latency**: $2({N}-1){\alpha}=$ $2 \times 63 \times 10\ {\text{µ}}\text{s}$ = 1260 μs.
2.  **Tree Latency**: $2(\log_2 {N}){\alpha}=$ $2 \times 6 \times 10\ {\text{µ}}\text{s}$ = 120 μs.

**Bandwidth** (note the difference):

3.  **Ring Bandwidth**: $2\frac{{N}-1}{{N}}\frac{{M}}{{\beta}} \approx$ $2 \times \frac{1\text{ MB}}{10\text{ GB/s}}$ = 196.9 μs (optimal: each rank sends about $2{M}$ in total, the lower bound).
4.  **Tree Bandwidth**: $2\log_2 {N}\cdot \frac{{M}}{{\beta}} =$ $12 \times \frac{1\text{ MB}}{10\text{ GB/s}}$ = 1200 μs (each level sends full message).

Summing the latency and bandwidth terms gives each algorithm’s total time ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^tbl-collective-communication-ring-vs-tree-1mb-64gpu|table 7]]).

| **Algorithm** | **Latency** | **Bandwidth** | **Total** |
|:--------------|:-----------:|:-------------:|:---------:|
| **Ring**      |   1260 μs   |   196.9 μs    | 1456.9 μs |
| **Tree**      |   120 μs    |    1200 μs    |  1320 μs  |

Table 7: **Ring vs. Tree AllReduce Timing for a 1 MB Buffer on 64 GPUs**: Latency, bandwidth, and total-time terms with ${\alpha}=$ 10 μs and ${\beta}=$ 10 GB/s.

^tbl-collective-communication-ring-vs-tree-1mb-64gpu

Tree wins, but only by 9 percent. For this 1 MB message, the payload is near the crossover point.

**Systems insight**: Ring’s latency term (10.5× Tree’s) nearly balances Tree’s bandwidth term (6.1× Ring’s). The log-aware crossover estimate predicts ${M_{\text{crossover}}} \approx {N}{\alpha}{\beta}/ \log_2 {N}=$ $64 \times 10\ {\text{µ}}\text{s} \times 10\ \text{GB/s} / 6$ $\approx$ 1.1 MB. At 1 MB, the payload is just below crossover, so Tree wins. At 10 MB, Ring would dominate.

The crossover point sits inside the range that gradient reductions can traverse as bucket sizes change. In this example, the 1 MB AllReduce lies near crossover, whereas a 10 MB DDP bucket is already above it. A fused bucket of 50–300 MB or the full 140 GB BF16 gradient of a 70B parameters model favors Ring over the simple Tree model even more strongly. These conclusions apply to the stated AllReduce configuration. An MoE token-routing payload of the same size still requires an AllToAll schedule, and optimized tree or hierarchical implementations require their own cost comparison.
