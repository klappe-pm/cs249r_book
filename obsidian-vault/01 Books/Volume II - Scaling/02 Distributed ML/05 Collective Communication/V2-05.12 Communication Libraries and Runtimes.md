# V2-05.12 Communication Libraries and Runtimes

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05 Collective Communication|V2-05 Collective Communication]]

^sec-communication-collective-operations-collective-operations-communication-libraries-nccl-5307

Production libraries implement the ring, tree, and hierarchical schedules, so the engineering decision is which library preserves the chapter’s cost, topology, and overlap assumptions on the target hardware.

### Backend Selection

^sec-communication-backend-selection

A collective runtime that bounces GPU tensors through host DRAM over PCIe or ignores NVLink and rail topology can cut effective reduction bandwidth by an order of magnitude even when it implements the right ring or tree schedule. Four properties therefore separate communication backends in practice: the device memory path, topology awareness, portability, and observability. NCCL leads on the first two for NVIDIA GPUs because it executes the collective algorithms of [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-collective-operations-collective-operations-allreduce-algorithms-7545|section 5.6]] and [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^sec-communication-collective-operations-collective-operations-mapping-collectives-topology-3214|section 5.7]] directly on GPU-resident buffers ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-jeaugey2017nccl|Jeaugey 2017]]; [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-nvidiaNcclUserGuide|NVIDIA 2026]]). Its kernel fusion combines reduction arithmetic with data movement so intermediate results do not bounce back to HBM. GPUDirect RDMA lets the network card read and write GPU memory directly over PCIe without staging payloads through host DRAM. To keep multiple links busy at once, channel pipelining splits each collective across parallel communication channels, though realized throughput still depends on NIC placement, routing, and contention because extra channels cannot create port capacity. Documented environment variables then expose these choices for observability, with `NCCL_ALGO` and `NCCL_PROTO` inspecting or overriding the selected algorithm and protocol and `NCCL_DEBUG` reporting the active topology, channels, and schedule ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-nvidiaNcclUserGuide|NVIDIA 2026]]).

MPI matters when portability, CPU-side coordination, or HPC integration decides the choice ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-mpiforum2015mpi31|Message Passing Interface Forum 2015]]), and two of its features bear directly on overlap. Non-blocking collectives such as `MPI_Iallreduce` return a request handle that the application tests or waits on, a completion model different from NCCL’s ordering on CUDA streams, the in-order queues of kernels and copies that a GPU executes. Persistent collectives, introduced in MPI 4.0, initialize an operation once and activate it at every step, amortizing setup for a training loop that repeats the same AllReduce shape. Either feature hides a transfer only when independent work exists and the runtime makes progress. MPI’s one-sided communication (`MPI_Put`, `MPI_Get`, `MPI_Accumulate`) maps onto RDMA hardware and suits asynchronous designs in which one process writes another’s memory without its participation. CUDA-aware MPI implementations accept GPU pointers, but the selected transport decides whether data still passes through host memory, so that path must be benchmarked against NCCL.

Portability is the strength of Gloo, a PyTorch backend for CPU tensors, development, and testing whose TCP transport exercises collective semantics on one machine before a job reaches an accelerator cluster. Whether a faster shared-memory transport is active must be measured rather than assumed. Other accelerators have their own backends, AMD’s RCCL for the ROCm stack and Intel’s oneCCL, because the same algorithm has different effective ${\alpha}$, ${\beta}$, and topology constraints on each platform. PyTorch’s `torch.distributed` routes each call to the backend its process group names, so teams often mix them, with NCCL reducing gradients in a GPU group while a CPU group uses Gloo for barriers, scalar broadcasts, or sampler state. Applied to common scenarios, the four properties select a library, or a pairing of libraries, for each ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.12 Communication Libraries and Runtimes#^tbl-library-selection|table 13]]).

| **Scenario**                      |              **Recommended library**              | **Rationale**                                |
|:----------------------------------|:-------------------------------------------------:|:---------------------------------------------|
| **Multi-GPU training (NVIDIA)**   |                       NCCL                        | GPUDirect, kernel fusion, NVLink-aware       |
| **CPU-only distributed training** |                    Gloo or MPI                    | Mature CPU optimizations                     |
| **Development/debugging**         |                       Gloo                        | Cross-platform, no CUDA dependency           |
| **Mixed vendor GPUs**             | Vendor-specific groups; validate cross-group path | NCCL, RCCL, and oneCCL are vendor-specific   |
| **HPC integration**               |                    MPI + NCCL                     | MPI for job launch, NCCL for GPU collectives |

Table 13: **Communication Library Selection**: Choose based on hardware and workload requirements. Many NVIDIA GPU training deployments use NCCL; Gloo serves as a portable fallback.

^tbl-library-selection

The table follows from the chapter’s cost model. A backend’s memory path and topology choices determine how it uses the fabric, and its diagnostic signals help identify whether ${\alpha}$, ${\beta}$, or processor overhead limits the job. The resulting performance must still be measured with the workload’s collective and placement.

### Calibrating Collective Communication Models

^sec-communication-nccl-reality

When an engineer runs the `nccl-tests` benchmark suite on a new cluster and compares the reported `AllReduce` time against the naive point-to-point expression ${\alpha}+{M}/{\beta}$, the achieved bandwidth appears to be roughly half of the link specification even on a healthy fabric. The naive expression omits the collective’s traffic factor, about 2 for a ring. Bus bandwidth, defined in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-performance-model|The α-β performance model]]**, multiplies the measured rate of tensor size over completion time by the ring’s factor whichever schedule ran, so it is a normalization that matches the traffic only for a ring. The bandwidth-latency trade-off (principle [[01 Books/Volume II - Scaling/01 The Fleet/V2 Fleet Principles#^pri-alpha-beta-model|5]]) provides accurate first-order predictions only when it models the same collective that the benchmark executes. For a ring AllReduce over ${N}$ ranks and an ${M}$-byte tensor, the first-order cost is $2({N}-1){\alpha}+ 2({N}-1){M}/({N}{\beta})$, whereas a tree, a hierarchical schedule, and a switch-assisted reduction each carry their own step counts and traffic factors. NCCL also selects protocols, channels, and algorithms according to message size and detected topology, making those runtime choices part of the experimental condition ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-jeaugey2017nccl|Jeaugey 2017]]; [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-nvidiaNcclUserGuide|NVIDIA 2026]]).

A calibrated collective model therefore records the operation, reduction datatype, rank count, tensor size, algorithm and protocol, topology, rank placement, and achieved bus bandwidth. It then fits effective ${\alpha}$ and ${\beta}$ to measurements from that same configuration, as **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-performance-model|The α-β performance model]]** does for one measured NCCL AllReduce. Comparing predicted and observed time under this contract reveals software overhead or topology loss without mistaking a collective’s algorithmic traffic factor for library inefficiency. The resulting parameters apply only to the measured regime; changing the collective, process group, topology, or library version requires recalibration. A calibrated model selects a collective schedule and sizes its overlap window. Attributing an observed training-step regression to kernels, memory, communication, or contention is a broader measurement task, which the program goodput analysis of **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.07 Program Goodput#^sec-performance-engineering-profiling|Program Goodput]]** develops.

Communication diagnosis begins by comparing the workload against a matched bare-collective baseline and recording the selected algorithm, protocol, rank placement, and achieved bandwidth. A healthy baseline with a slow training step points to invocation granularity, contention, stragglers, or insufficient overlap rather than the fabric alone. Profiler traces and the attribution workflow separate those causes.

The backend must satisfy both the collective contract and the measured execution budget. A fast isolated collective is insufficient when its placement, invocation order, or progress behavior leaves the training step waiting.
