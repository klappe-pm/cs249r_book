# V2-05.04 Parallelism Strategies and Their Traffic

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05 Collective Communication|V2-05 Collective Communication]]

^sec-communication-parallelism-patterns

Once a training job splits its batch, layers, or parameters across devices, no rank holds all the state needed to finish a step on its own. A synchronous data-parallel worker computes gradients from its local batch slice, but its optimizer cannot update the weights until every replica’s gradients have been combined. Some of those reductions can start as backward layers finish, while earlier layers are still computing. Tensor ownership determines where each tensor must go, and gradient or activation readiness determines when each transfer can start.

How the model is partitioned dictates which tensors cross device boundaries and which ranks must exchange them. For Archetype A (GPT-4/Llama-3), dense gradient contributions are combined within each data-parallel group; in a hybrid layout, that group contains the matching parameter shard from each replica. AllReduce serves the replicated-gradient baseline. For Archetype B (DLRM at Scale),[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.17 Footnotes#^fn5|⁵]] lookup requests travel to embedding-shard owners and the resulting vectors return to the workers that need them. Mixture-of-experts (MoE) routing similarly sends activations to the ranks hosting selected experts and returns their outputs. These destination-specific exchanges motivate AllToAll.

↩︎ The three lighthouse archetypes and the C³ regimes each one stresses are established in **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.07 The Fleet Stack and the Lighthouse Archetypes#^sec-vol2-introduction-archetypes|Three systems archetypes]]**.

At large scale, these parallelism strategies can be combined. A 3D parallelism layout combines data parallelism, tensor parallelism, and pipeline parallelism, creating distinct communication groups whose exchanges may overlap in time. In a node-local tensor-parallel example, layer reductions use NVLink, pipeline stages exchange activations and their gradients point-to-point across nodes for each microbatch (a slice of the batch), and data-parallel groups reduce matching parameter shards over InfiniBand. Other placements change those physical paths while retaining the logical communication requirements.

Each primitive operates on a different process group, a subset of the total GPU population that participates in that particular collective. Classical Message Passing Interface (MPI) uses a communicator as the object that names such a participating set; its communicator size is the number of ranks in that set. MPI libraries already selected collective algorithms based on communicator size and message size ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.16 Source References#^ref-thakur2005|Thakur et al. 2005]]). GPU communication libraries inherit that algorithm-selection problem and add the further challenge of coordinating overlapping process groups without creating contention between concurrent collectives.

Each parallelism strategy fixes the data it must move, the collective primitive that moves it, and the term most likely to limit it ([[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.04 Parallelism Strategies and Their Traffic#^tbl-parallelism-communication-mapping|table 1]]), and with them which participants must exchange data. The collective primitives that follow make each exchange’s contract precise, the pricing model then charges it per round, and the collective algorithms provide its execution schedule.

| **Parallelism strategy**      | **What must move**                         |   **Primary primitive**    |            **Primary constraint**            |
|:------------------------------|:-------------------------------------------|:--------------------------:|:--------------------------------------------:|
| **Data Parallelism**          | Full gradient, averaged across replicas    |         AllReduce          |          Bandwidth (large payloads)          |
| **FSDP/ZeRO-3**               | Parameter shards in, gradient shards out   | AllGather + ReduceScatter  |          Bandwidth, high frequency           |
| **Tensor Parallelism**        | Partial layer activations within the node  |    AllReduce, AllGather    | Critical path (NVLink bandwidth and latency) |
| **Sequence Parallelism**      | Activations sharded along the sequence     | AllGather + ReduceScatter  |       Bandwidth (activation exchange)        |
| **Pipeline Parallelism**      | Activations to the next stage              | Point-to-Point (Send/Recv) |      Latency (microbatch dependencies)       |
| **Expert Parallelism (MoE)**  | Tokens to the ranks hosting their experts  |          AllToAll          |    Startup, injection/bisection, or skew     |
| **Embedding Sharding (DLRM)** | Embedding lookups to and from shard owners |          AllToAll          |    Granularity, fabric capacity, or skew     |

Table 1: **Parallelism-to-Collective Mapping**: How each parallelism strategy becomes a traffic pattern. Pipeline parallelism alone relies on point-to-point transfers rather than a collective.

^tbl-parallelism-communication-mapping

In this table, expert parallelism refers to the mixture-of-experts architecture pattern, in which each token activates only a few experts. Data parallelism and fully sharded data parallel (FSDP), which divides each replica’s parameters, gradients, and optimizer state across the data-parallel ranks, generate large reductions and gathers that reward byte-efficient rings and hierarchical schedules. Tensor parallelism, by contrast, generates smaller, more frequent messages directly on the critical path, so low software overhead and fast node-local links dominate its cost. Pipeline parallelism also sits on the critical path, because each stage waits for the previous stage’s microbatch, but its stages often exchange activations across nodes, so the size of those activations sets its transfer regime. Expert parallelism and sharded embedding tables produce destination-specific traffic whose bottleneck shifts among message granularity, endpoint injection and reception, fabric bisection, oversubscription, routing, and skew.

The table’s rows describe data center parallelism, so they leave out the federated Archetype C. Across all three lighthouse archetypes, the dominant exchange and its bottleneck differ.

**Lighthouse 5.1: Communication archetype patterns**

A gradient’s communication pattern depends on the system’s objective function and constraint regime. Each lighthouse archetype faces a distinct communication challenge, and the techniques developed in this chapter map to those challenges differently, as [[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.04 Parallelism Strategies and Their Traffic#^tbl-archetype-collective-mapping|table 2]] summarizes.

| **Archetype**                         |             **Primary collective**             |         **Candidate limiter**         | **Optimization strategy**                                   |
|:--------------------------------------|:----------------------------------------------:|:-------------------------------------:|:------------------------------------------------------------|
| **Archetype A (GPT-4/Llama-3)**       |                   AllReduce                    |         Bandwidth (${\beta}$)         | Hierarchical AllReduce; rail-optimized placement            |
| **Archetype B (DLRM at Scale)**       |                    AllToAll                    | Granularity, fabric capacity, or skew | Message coalescing; topology-aware routing; shard balancing |
| **Archetype C (Federated MobileNet)** | Client uploads to an aggregator (asynchronous) |   Uplink bandwidth and availability   | Aggressive quantization; error feedback                     |

Table 2: **Archetype-to-Collective Mapping**: Each lighthouse archetype produces a characteristic traffic pattern, but the limiting term depends on message shape, placement, and the physical fabric.

^tbl-archetype-collective-mapping

The table separates traffic pattern from limiting resource. A dense reduction, a destination-specific exchange, and an intermittent device update require different interventions even though all three serve a training workload. Hierarchical AllReduce, AllToAll schedule selection, and compression with error feedback each receive their own treatment later in the chapter.

A traffic map names which pattern a workload generates, but it does not specify what each rank must hold when the call completes. Before any of those interventions can be priced, each exchange needs a precise contract.
