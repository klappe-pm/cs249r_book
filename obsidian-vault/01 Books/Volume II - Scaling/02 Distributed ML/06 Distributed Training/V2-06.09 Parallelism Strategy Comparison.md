# V2-06.09 Parallelism Strategy Comparison

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training|V2-06 Distributed Training]]

^sec-distributed-training-systems-systems-parallelism-strategy-comparison-d92a

A parallelism strategy is useful only if it moves the limiting constraint without creating a larger one. Assembling data, tensor, pipeline, and hybrid partitioning into a coherent decision procedure requires evaluating where each strategy relocates overhead across the cluster’s memory and interconnect hierarchy. For a new model, the decisive questions are which memory state fits, how often communication occurs, where the pipeline bubble appears, and which abstraction cost the engineering team can tolerate. Sequence, context, and expert parallelism sit beside the 3D core in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.09 Parallelism Strategy Comparison#^tbl-parallelism-compare|table 9]], and they remain subject to the same batch, memory, and topology constraints.

| **Strategy**                     | **Binding constraint**                                 | **Primary movement**                        | **Placement decision**                                     | **Validation signal**                                |
|:---------------------------------|:-------------------------------------------------------|:--------------------------------------------|:-----------------------------------------------------------|:-----------------------------------------------------|
| **DDP**                          | Model state fits on one accelerator                    | AllReduce gradients every step              | Replicate full model across data-parallel workers          | Step time dominated by compute, not synchronization  |
| **FSDP/ZeRO**                    | Model state exceeds one accelerator                    | Gather parameters; ReduceScatter gradients  | Size prefetch and reshard windows within peak memory       | State plus activations and workspaces fit            |
| **Tensor parallelism**           | One layer exceeds local capacity or runs too slowly    | Reduce or gather partial layer results      | Keep tightly coupled partitions on fast local links        | Exposed collective time fits the layer-time budget   |
| **Pipeline parallelism**         | Layer stack fits only when split by stage              | Activations and gradients between stages    | Balance stages and live microbatch activations             | Bubble and peak activation memory meet budget        |
| **Sequence/context parallelism** | Activations or attention context exceed local capacity | Exchange sequence shards or attention state | Partition long sequences across a low-latency group        | Longer context fits without communication dominating |
| **Expert parallelism**           | Sparse expert capacity exceeds local memory            | Route token activations with AllToAll       | Balance expert load across a high-bisection group          | Expert imbalance and dropped-token rate stay bounded |
| **Hybrid parallelism**           | More than one constraint binds at once                 | Multiple collectives on coupled axes        | Satisfy divisibility, batch, topology, and failure domains | MFU improves within memory and network budgets       |

Table 9: **Parallel Training Strategies**: Data, tensor, and pipeline parallelism form the canonical 3D core. Sequence/context parallelism extends the partition along token positions, while expert parallelism extends it across sparse model capacity. Strategy selection remains an engineering feasibility test: identify the binding constraint, the communication primitive it creates, the placement decision it forces, and the measurement that proves the strategy is helping.

^tbl-parallelism-compare

A decision path condenses the table, starting from memory fit and then asking which structure breaks the budget ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.09 Parallelism Strategy Comparison#^fig-parallelism-flowchart|figure 22]]). The 175B reference model takes the layer branch on step time rather than capacity. An average layer holds about 29.2 GB of training state, which fits one GPU. Without tensor parallelism, however, the rule that sets configuration D’s depth, the shallowest power-of-two pipeline at which unsharded state fits, gives 64 single-GPU stages instead of 8. At the same 96 microbatches per replica, that pipeline’s bubble idles 39.6 percent of each step rather than 6.8 percent, and the modeled step grows from 8.71 seconds to 12.04 seconds. Tensor parallelism inside the NVLink node is what keeps the pipeline shallow, and because its 350 GB shards still exceed one GPU, the path ends at combining axes. Before accepting any branch, check peak memory, global batch, communication service time, and load balance together; bandwidth is a feasibility constraint throughout the decision, not an afterthought.

![[90 Assets/Volume II/06 Distributed Training/Parallelism Flowchart 3f7052a8c3.svg]]

Figure 22: **Parallelism Strategy Decision Framework**: A selection guide that begins with memory fit. For a model that fits on one device, evaluate data parallelism against the throughput target and input-delivery budget; the complete dataset need not fit in accelerator memory. A model that does not fit first asks whether a single layer is too large or too slow for one device. If so, tensor parallelism splits each layer inside one node, and a model whose tensor-parallel shards still exceed device memory, such as the 175B reference model, combines tensor, pipeline, and data parallelism. A model whose layers fit is routed by depth, with a deep stack leading to pipeline parallelism and otherwise sharded data parallelism (FSDP/ZeRO). Any outcome can add data parallelism for throughput, and peak memory, global batch, bandwidth, and workload imbalance constrain every candidate.

^fig-parallelism-flowchart

Identifying the limiting constraint comes before choosing an implementation stack, which is why both the strategy comparison and the decision path stay deliberately coarse. Dense large-model training and recommendation-style workloads motivated each of these partitioning strategies. The same constraint logic also reaches the federated edge case ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.09 Parallelism Strategy Comparison#^tbl-partitioning-archetypes|table 10]]), where the bottleneck shifts from accelerator memory and fabric bandwidth to unreliable devices, privacy, and intermittent connectivity. A configuration chosen across these regimes still has to be expressed in software, and the way a framework expresses it decides which of the chapter’s budgets the engineer controls directly.

Partitioning and coordination choices differ with the system’s primary bottleneck:

| **Archetype**                         | **Primary partitioning strategy** | **The logic**                                                                                                                                                                                                                                                                                             |
|:--------------------------------------|:---------------------------------:|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Archetype A (GPT-4/Llama-3)**       |       Hybrid 3D parallelism       | Combine tensor (width), pipeline (depth), and data (throughput) parallelism to fit roughly 3.5 TB of weights under third-party estimates (OpenAI has not disclosed the parameter count).                                                                                                                  |
| **Archetype B (DLRM at Scale)**       |        Embedding sharding         | Partition massive 10 TB+ tables across parameter servers or accelerator shards; use sparse AllToAll updates.                                                                                                                                                                                              |
| **Archetype C (Federated MobileNet)** |        Federated learning         | The same logic extends to coordinating on-device MobileNet updates across unreliable, privacy-constrained edge devices; **[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.08 Federated Learning Systems at Scale#^sec-edge-intelligence-federated-systems\|Federated Learning Systems at Scale]]** develops this regime. |
