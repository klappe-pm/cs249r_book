# V2-06.03 The Parallelism Design Space

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training|V2-06 Distributed Training]]

^sec-distributed-training-systems-systems-singlemachine-distributed-transition-1ee4

Once a model or its training time outgrows a single GPU, the training loop offers three nested axes to split across devices: the examples in a batch, the layers of the model, and the matrix operations inside each layer. Data parallelism assigns different examples to model replicas; pipeline parallelism assigns successive layer groups to different devices; tensor parallelism splits the operations inside a layer. Because every split adds inter-device communication and synchronization overhead on top of single-machine compute and memory limits (**[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy|The D·A·M Taxonomy]]**), profiling and design must treat these three strategies as *loop transformations*.

In compiler terms, data parallelism acts like a parallel for-loop that assigns different batch indices to devices running the same model. Tensor parallelism resembles vectorization, or single instruction, multiple data (SIMD), by partitioning the work inside matrix operations. This is an analogy for the work split rather than for a shared instruction stream or register file, since the devices still exchange tensor shards over an interconnect. Pipeline parallelism instead resembles instruction pipelining, assigning successive layer groups to stages so that overlapping microbatches, the slices of a batch that flow through the stages one after another, keep those stages active, subject to dependency delays and load balance.

However the loop is split, distributed training[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.15 Footnotes#^fn1|¹]] spreads the workload across machines that must coordinate to train a single model. Coordination here means keeping every model shard or replica on a compatible training step. Basic barriers can keep a small research run ordered, but long-running training jobs also need timeout, checkpoint, and recovery mechanisms so one failed worker does not waste days of compute.

↪ Checkpointing and recovery for long-running training jobs are developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07 Fault Tolerance#^sec-fault-tolerance-reliability|Fault Tolerance]]**.

Mapping those three loop transformations onto hardware follows the cluster’s interconnect hierarchy. Within a single node, multiple GPUs coordinate across separate device memories over high-bandwidth NVLink or PCIe links,[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.15 Footnotes#^fn2|²]] with collective libraries such as NCCL scheduling the transfers.

Crossing node boundaries adds slower inter-node network links, fault-tolerance exposure, and cluster orchestration. Single-GPU kernel and memory efficiency must be tuned before crossing them, because any waste on one device is multiplied across the fleet. Matching the three loop splits to these intra-node and inter-node tiers decomposes the design space onto a three-dimensional grid, ${N}= {N_{\text{DP}}} \times {N_{\text{PP}}} \times {N_{\text{TP}}}$, that partitions cluster execution across tensor parallelism (${N_{\text{TP}}}$, intra-layer sharding), pipeline parallelism (${N_{\text{PP}}}$, sequential stage partitioning), and data parallelism (${N_{\text{DP}}}$, batch replication). Each cell of the grid is one accelerator coordinate ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.03 The Parallelism Design Space#^fig-3d-parallelism-cube|figure 2]]).

![[90 Assets/Volume II/06 Distributed Training/3d Parallelism Cube 6a29a6d051.svg]]

Figure 2: **The 3D Parallelism Cube**: The configuration space decomposes cluster training across three orthogonal axes: tensor parallelism (${N_{\text{TP}}}$, intra-layer sharding), pipeline parallelism (${N_{\text{PP}}}$, sequential stage partitioning), and data parallelism (${N_{\text{DP}}}$, batch replication). Each cell is one accelerator, identified by its $({N_{\text{DP}}}, {N_{\text{PP}}}, {N_{\text{TP}}})$ coordinate, so the cube holds ${N} = {N_{\text{DP}}} \times {N_{\text{PP}}} \times {N_{\text{TP}}}$ devices. A feasible point must jointly satisfy model divisibility, per-device memory limits, and the network hierarchy that carries each axis’s traffic.

^fig-3d-parallelism-cube

Under the three-dimensional partitioning of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.03 The Parallelism Design Space#^fig-3d-parallelism-cube|figure 2]], called **3D parallelism**, the total accelerator allocation scales as the product ${N}= {N_{\text{DP}}} \times {N_{\text{PP}}} \times {N_{\text{TP}}}$. The axes represent distinct mathematical partitions, but they are not independent configuration knobs. Tensor and pipeline degrees must divide the model structure, the data-parallel degree and microbatch schedule must produce a viable global batch, every partition must fit memory, and each communication group must map onto an adequate topology and acceptable failure domain. Training systems therefore select a jointly feasible coordinate rather than tuning ${N_{\text{DP}}}$, ${N_{\text{PP}}}$, and ${N_{\text{TP}}}$ in isolation.

### Parallelism Strategy Selection and Engineering Trade-Offs

^sec-distributed-training-systems-systems-engineering-tradeoffs-selecting-parallelism-strategy-b344

A parallelism strategy that places frequent, high-volume exchanges on a slow link fails before it leaves the whiteboard, because communication stalls the accelerators it was meant to feed. Choosing a strategy is therefore a constraint satisfaction problem governed by parameter count $({P})$, batch size $({B})$, and interconnect bandwidth. A first feasibility screen compares the traffic each strategy creates against the hardware topology ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.03 The Parallelism Design Space#^tbl-parallelism-tradeoffs|table 1]]). In that screen, ${N_L}$ denotes layer count, ${S}$ sequence length, and ${d}$ hidden width. The table identifies traffic sources rather than complete byte budgets; datatype width, partition degree, and communication frequency enter the worked mechanisms below.

| **Strategy**               | **Communication pattern** |                           **Comm. volume**                            | **Hardware constraint**              |
|:---------------------------|:-------------------------:|:---------------------------------------------------------------------:|:-------------------------------------|
| **Data Parallel (DP)**     |    AllReduce Gradients    |             $\propto {M_{\text{grad}}}$ (gradient bytes)              | Requires high bisection BW           |
| **Tensor Parallel (TP)**   |   AllReduce Activations   | $\propto {B}\times {S}\times {d}\times {N_L}$ (per-layer activations) | Fast domain matched to layer traffic |
| **Pipeline Parallel (PP)** |   Point-to-Point (P2P)    |            $\propto {B}\times {S}\times {d}$ (Activations)            | Link must sustain stage activations  |

Table 1: **Parallelism Communication Costs**: Tensor parallelism exchanges partial layer results frequently and favors a fast communication domain, which can span servers. Pipeline parallelism transfers boundary activations; its bandwidth need depends on tensor shape and microbatch schedule. Data parallelism synchronizes gradient bytes, whose exposed cost depends on overlap and topology. Memory sharding addresses capacity but does not automatically reduce communication.

^tbl-parallelism-tradeoffs

Those bandwidth requirements impose a hard constraint on hardware placement: each parallelism axis must map onto an interconnect tier that can sustain its traffic within the compute budget. A quick back-of-envelope bandwidth feasibility check catches a mismatch before any code is written.

↩︎ The communication domains and bandwidth hierarchy used to evaluate placement are established in **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.06 The Node#^sec-compute-bandwidth-hierarchy|Bandwidth hierarchy]]**.

**Systems Perspective 6.1: Bandwidth feasibility check**

Tensor parallelism leaves each device with part of a layer’s output, and an AllReduce sums those partial outputs twice per transformer block in the forward pass, once after attention and once after the feed-forward network ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-tensor-parallelism-d76e|section 6.5.3]]). These frequent tensor-parallel collectives must fit the layer-time budget. The test compares the time one layer’s local share of computation takes with the time its collectives take on each candidate link. For the forward pass of one GPT-3 layer split 8 ways, processing one 2,048-token sequence at half of an H100’s dense FP16 peak:

- Local compute per layer: about 1.9 ms
- Tensor-parallel transfer per layer over NVLink: about 0.4 ms
- The same transfer over one NDR InfiniBand port: about 3.5 ms

On NVLink the exchange is a fraction of the layer’s compute; across InfiniBand it would take longer than the compute it serves. The amount hidden depends on independent work available in the execution schedule. NVLink is one suitable fast domain, but the test uses message bytes, exposed latency, and sustained link rate rather than an interconnect brand or chassis boundary. Cross-rack placement may favor pipeline or data parallelism when the available fabric cannot meet the tensor-parallel budget; their activation and gradient traffic must also be checked.

The communication costs in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.03 The Parallelism Design Space#^tbl-parallelism-tradeoffs|table 1]] already narrow the choice before any mechanism has been developed, because a strategy is viable only when its traffic fits the tier that must carry it. What each formula implies in practice depends on the mechanics of data, tensor, and pipeline parallelism developed over the rest of the chapter, and [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.09 Parallelism Strategy Comparison#^sec-distributed-training-systems-systems-parallelism-strategy-comparison-d92a|section 6.8]] turns the same constraints into a decision procedure once those mechanics are in place.

**Self-Check: Question**

1.  Framing distributed parallelism strategies as compiler loop transformations across the training loop’s iterators (batches, layers, and operations), which distributed strategy corresponds to vectorization (SIMD) of inner matrix multiplications?

    1.  Tensor parallelism, which partitions inner matrix-multiplication operations across devices and exchanges partial results over the interconnect
    2.  Data parallelism, which unrolls the outer batch loop across devices so each rank processes independent data indices
    3.  Pipeline parallelism, which stages sequential layer operations across devices analogous to CPU instruction pipelining
    4.  Model replication, which duplicates the entire forward and backward execution redundantly across machines

2.  In the 3D parallelism cube, where the device count equals the product of the data-, pipeline-, and tensor-parallel degrees, how do the three scaling axes interact to allocate cluster accelerators for large models?

    1.  The three axes are mutually exclusive; choosing data parallelism precludes using tensor or pipeline parallelism in the same cluster
    2.  Tensor and pipeline parallelism can combine within a node, but data parallelism can only be used if model parallelism is disabled
    3.  The total accelerator count is the sum of the three degrees, with each parallelism type requiring a disjoint node pool
    4.  The axes compose multiplicatively, so one layout can split layers (TP), stage the layer stack (PP), and replicate the pipeline across data shards (DP), and its device count is the product of the three degrees

3.  True or False: If a neural network’s parameters exceed a single GPU’s memory capacity, tensor parallelism can be scaled across standard commodity Ethernet switches between server racks, provided the global batch size is made large enough.

4.  For one GPT-3 layer split eight ways, the chapter’s bandwidth feasibility check finds about 1.9 ms of local compute, about 0.4 ms of tensor-parallel transfer over NVLink, and about 3.5 ms for the same transfer over one NDR InfiniBand port.
