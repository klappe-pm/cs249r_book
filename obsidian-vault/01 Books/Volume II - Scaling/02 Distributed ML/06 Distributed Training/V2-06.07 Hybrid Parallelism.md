# V2-06.07 Hybrid Parallelism

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training|V2-06 Distributed Training]]

^sec-distributed-training-systems-systems-hybrid-parallelism-12a0

The 175B-parameter running example has now exhausted each parallelism family on its own. Data parallelism with ZeRO-3 makes the state fit, but the per-step parameter regather priced in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-model-parallelism-7437|section 6.5]] would take about 3× as long as the computation it serves, while tensor parallelism confined to one 8-GPU node still leaves several hundred gigabytes of training state per device. Because replication and state sharding ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-data-parallelism-6132|section 6.3]]) distribute examples and storage whereas tensor and pipeline partitioning ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-model-parallelism-7437|section 6.5]]) distribute layer computation, **hybrid parallelism** composes both families orthogonally. Model parallelism splits the architecture so each replica fits available HBM and stays on fast links, while data parallelism scales throughput across multiple model replicas to process 300 billion tokens within calendar limits. This orthogonal composition defines Archetype A training at frontier scale.

**Lighthouse 6.2: Archetype A (GPT-4/Llama-3): Physics of 3D parallelism**

Archetype A (GPT-4/Llama-3) illustrates the motivation for hybrid parallelism. Parameter count $({P})$ must first be converted to a complete memory budget before comparison with device capacity $({M_{\text{device}}})$, while dataset size $({D})$ and the deadline determine the throughput target. Tensor parallelism partitions layer computations within a suitable communication domain; pipeline parallelism assigns consecutive layers to stages; and data parallelism distributes examples from ${D}$ across replicas. A design combines the dimensions that address its constraints; efficient execution does not require all three in every case.

To see why the combination matters, consider four parallelism configurations for training the 175B model on a 1,024-GPU cluster organized as 128 nodes of 8 GPUs each. The progression from pure data parallelism through tensor and pipeline parallelism shows which axis makes the job fit and what each axis adds to the step time.

All four configurations run the same modeled training step, the one this book uses whenever it quotes a step time for this model on this cluster, the reference job. One step is one optimizer update over a global batch of 1,536 sequences of 2,048 tokens in 16-bit mixed precision, and each replica feeds its share of the batch through the model one sequence per microbatch. Each GPU computes at 45 percent of its peak before communication, and up to 85 percent of the data-parallel gradient reduction hides behind backward computation. Because the model, batch, and cluster are fixed, the average computation per GPU is the same 7.25 seconds per step in every configuration. In B, C, and D every replica receives the same whole number of sequences, so every GPU carries exactly that load. A is the exception, because its 1,536 sequences do not divide evenly over 1,024 replicas (1.5 each). Some GPUs would process two sequences while others process one, so the walk quotes no step time or efficiency for A. The configurations differ only in the training state each GPU must hold and in the time each adds to that computation for tensor-parallel exchanges, exposed data-parallel transfer, and the pipeline bubble.

In Configuration A, pure data parallelism (DP-1024) serves as a counterfactual rather than a feasible placement for this model. Every GPU would hold the full 2,800 GB of training state against 80 GB of HBM. The FP16 weights alone occupy 350 GB, so an A100 or H100 cannot replicate them; sharding only optimizer states does not change that fact. Communication is not what rules the layout out. If replication were possible, all 1,024 ranks would AllReduce the 350 GB gradient once per step. A hierarchical reduction first reduces inside each node over NVLink, so each GPU’s InfiniBand port carries 1/8 of the gradient, and the exchange takes about 3.1 seconds, of which about 0.46 seconds stays exposed beside the average 7.25 seconds of computation. The scaling-efficiency notebook in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-systems-systems-distributed-training-efficiency-metrics-9488|section 6.4]] reached only 15 percent for this placement because it priced the exchange as a flat ring on each GPU’s port behind a shorter FP8 compute window, which hides far less of the transfer.

Configuration B introduces intra-node tensor parallelism alongside data parallelism (TP-8, DP-128). Within each of 128 model replicas, 8 GPUs use tensor parallelism over NVLink. The corresponding tensor shard from every replica forms one 128-rank data-parallel group, so the layout contains 8 such groups. Each rank AllReduces its 1/8 gradient shard, 43.75 GB rather than 350 GB, in about 1.74 seconds. Tensor parallelism is not free, however. Its forward and backward activation AllReduces add about 0.90 seconds per step on NVLink, so the modeled step grows to 8.42 seconds, a scaling efficiency of 86 percent. The layout still does not fit. At 16 bytes per parameter each GPU would hold about 350 GB of training state, so tensor parallelism confined to one node is not enough by itself, and the layout would also need gradient and optimizer sharding across its data-parallel group before it fits.

Configuration C adds pipeline stages across nodes (TP-8, PP-4, DP-32) so that each of 32 model replicas uses 8-way tensor parallelism within a stage and 4 pipeline stages across nodes. For each of the 8 $\times$ 4 tensor-and-pipeline shard positions, the corresponding ranks from all replicas form one 32-rank data-parallel group. Each rank therefore AllReduces a $350/(8\times4)\approx10.94$ GB gradient shard, in about 0.42 seconds. Pipeline communication forwards activations between stages and has lower volume than a full-model AllReduce. The trade-off is the pipeline bubble. At the beginning and end of each training step, some pipeline stages are idle while waiting for activations from earlier stages or gradients from later stages. The bubble fraction is approximately $({N_{\text{PP}}}-1)/({m}+{N_{\text{PP}}}-1)$, so with 4 pipeline stages and the 48 microbatches each replica receives per step, the bubble idles $3/51 \approx 5.9\%$ of the pipelined step, about 0.45 seconds. The pipeline cuts the data-parallel traffic by another factor of 4, but the bubble costs more time than the smaller transfer saves, so the modeled step lengthens to 8.67 seconds and efficiency falls to 84 percent.

Configuration C does not fit memory by itself either. Its training state is about 87.5 GB per GPU, above the 80 GB of an H100. Adding ZeRO-1 across its 32-rank data-parallel group closes that gap. Each GPU then keeps its tensor-and-pipeline slice of weights and gradients but only a 1/32 share of that slice’s optimizer state, about 24 GB in all. ZeRO-1 matches plain DDP’s ideal data-parallel byte volume at matching communication widths ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^tbl-zero-stages|table 3]]), so the model prices the same step for it, but equal bytes do not preserve the overlap schedule. Gradient reduction to owners must precede their optimizer updates, and the updated-parameter AllGather follows those updates. Configuration C with ZeRO-1 passes this simplified persistent-state memory budget, and its predicted step holds only if that reduction, update, and parameter-gather sequence achieves the modeled exposed communication time.

Configuration D deepens the pipeline instead of sharding the optimizer (TP-8, PP-8, DP-16). It is the layout of the reference job, in which tensor parallelism spans one node and the pipeline is the shallowest power of two at which unsharded mixed-precision Adam state fits. Each GPU holds about 43.8 GB of training state, which leaves about 36 GB of the 80 GB budget for activations, workspaces, and communication buffers. Each of the 16 replicas runs its 96 sequences as 96 one-sequence microbatches, so the bubble idles $7/103 \approx 6.8\%$ of the pipelined step, about 0.53 seconds, and the 16-rank data-parallel groups reduce their smaller shards in about 0.21 seconds. With tensor-parallel, data-parallel, and bubble time all charged, the modeled step takes 8.71 seconds, a scaling efficiency of 83 percent. Against configuration C with ZeRO-1, the deeper pipeline costs about 0.04 seconds per step, its larger bubble less its smaller transfer. Its optimizer still waits for the reduced gradients, but each GPU holds the optimizer state for its whole tensor-and-pipeline slice and updates that slice in place, so the post-update parameter AllGather that ZeRO-1 adds never enters the step.

Within this step model, communication does not separate the layouts. B, C, and D finish within 3 percentage points of one another, and each added axis lengthens the modeled step slightly because it brings its own exchange or idle time. Memory decides the design. Tensor parallelism inside the NVLink domain divides the training state by the node size at the price of frequent exchanges on the fastest link, pipeline stages divide it again at the price of a bubble, and data parallelism leaves only small gradient shards for InfiniBand. Peak memory, kernel shape, and scheduling still need verification before that prediction becomes a runnable design. The infrastructure hierarchy therefore dictates the parallelism hierarchy. Here, hierarchy-aware parallelism means matching exchange requirements to measured communication domains rather than choosing each degree independently.

**Definition 6.12: Hierarchy-aware parallelism**

***Hierarchy-aware parallelism*** is the strategy of mapping different parallel execution modes to the physical bandwidth tiers of the cluster.

1.  **Significance**: It places high-frequency synchronization (for example, tensor parallelism) on fast links such as NVLink, while assigning lower-frequency exchanges (for example, data parallelism) to slower tiers when their transfers fit the schedule. This alignment can improve scaling efficiency $({\eta_{\text{scaling}}})$ by reducing exposed communication time $({T_{\text{comm}}})$ and latency $({L_{\text{lat}}})$; the gain depends on readiness, contention, and available overlap.
2.  **Distinction**: Unlike uniform parallelism, which treats all node-to-node links as equal, hierarchy-aware strategies respect the bandwidth cliffs between die, node, and rack boundaries.
3.  **Common pitfall**: A frequent misconception is that any model can be sharded across any number of nodes. In reality, if the hierarchy mapping is wrong (for example, sharding a large tensor across a slow inter-rack link), the communication time will dwarf the compute time, making the scale-out useless.

The dependence runs both ways, because a parallelism configuration also determines which traffic the fabric must carry. In the reference job’s TP-8, PP-8, DP-16 layout, tensor reductions stay within each fast local domain, pipeline traffic crosses neighboring stages, and data-parallel groups synchronize corresponding shards across replicas. Rail-optimized and hierarchical fabrics can exploit that structure, but a workload mix that adds expert AllToAll traffic changes the global bandwidth requirement. Infrastructure planning must therefore evaluate the anticipated communication groups together rather than optimizing the fabric for a single layout.

↩︎ Rail-optimized fabrics, which cable each GPU slot position to its own rail switch, are established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.06 Level 3 Switch and Topology#^sec-network-fabrics-rail-optimized|Rail-optimized topology]]**.

### The 3D Training Loop

^sec-distributed-training-systems-systems-hybrid-parallelism-3d-loop

A 175B-parameter model trained with 3D parallelism ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.03 The Parallelism Design Space#^fig-3d-parallelism-cube|figure 2]]) can be traced on a fleet configured with tensor parallelism (TP) of 8 GPUs, pipeline parallelism (PP) of 16, and data parallelism (DP) of 128. This configuration uses 16,384 GPUs (8 GPUs $\times$ 16 $\times$ 128) organized into a hierarchy of bandwidth domains. That is 16× the 1,024-GPU reference cluster, so every level of the hierarchy is exercised even though parameter count alone would not require all three dimensions. [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.07 Hybrid Parallelism#^sec-distributed-training-systems-systems-hybrid-parallelism-configuration-design|Section 6.6.2]] justifies its pipeline depth.

The training step begins at the data-parallel level. Each of the 128 model replicas receives a distinct slice of the global batch. Within each replica, the model is split across 16 pipeline stages (nodes), with microbatches flowing sequentially from the embedding layer on Node 0 to the loss calculation on Node 15. At the finest granularity, within each node, the 8 GPUs fuse into a single “super-accelerator” via TP. The transformer matrix multiplications are split across these devices; column- and row-parallel pairs retain local intermediate shards and exchange partial results at the reduction points already derived. For a 175B-scale hidden dimension, the activation payload is roughly 201.3 MB. The resulting tensor-parallel traffic is about 4.2 GB per pipeline stage per microbatch in the forward pass, or 8.5 GB including the backward pass. Across the full 96-layer replica, the forward tensor-parallel traffic is about 67.6 GB. This traffic is the highest-intensity in the system, but its exposed latency can remain small relative to compute because the chips communicate over 300 GB/s–450 GB/s of local bandwidth per direction.

The backward pass exposes dependencies between parallelism dimensions. Nodes exchange activation gradients point-to-point, roughly 201.3 MB per microbatch per stage boundary in this example. A smaller payload still stalls a stage if it arrives after the stage needs it. Data-parallel synchronization creates another dependency. Although full-model gradients occupy about 350 GB, each data-parallel group exchanges only the corresponding tensor- and pipeline-parallel parameter shard. Gradient bucketing groups ready gradients as backward computation proceeds. Which exchange limits the step depends on its readiness, service time, and overlap; data parallelism is not necessarily the final bottleneck.

↩︎ Bucket fusion, which groups gradients that become ready together into larger reductions so communication can begin during backpropagation, is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.11 Communication-Computation Overlap#^sec-communication-bucket-fusion|Bucket fusion]]**.

The architectural imperative is *bandwidth matching*, in which each exchange’s startup and transfer time must fit its available compute or overlap interval. In this mapping, frequent TP exchanges use the NVLink domain (300 GB/s per direction or higher), while PP transfers cross nodes and DP reductions overlap backward computation. Accumulation can enlarge the compute interval between DP synchronizations, subject to the global-batch constraint. An infeasible mapping leaves part or all of the 16,384 GPUs fleet waiting. Comparing service time with the schedule completes the feasibility check introduced in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.03 The Parallelism Design Space#^sec-distributed-training-systems-systems-engineering-tradeoffs-selecting-parallelism-strategy-b344|section 6.2.1]].

### Hybrid-Parallelism Worked Example

^sec-distributed-training-systems-systems-hybrid-parallelism-configuration-design

Applied to physical infrastructure, bandwidth matching turns cluster design into a placement problem, and memory capacity per device (80 GB) bounds every placement. For the 3D training loop’s layout on 16,384 GPUs, built from 8-GPU NVLink nodes, this reasoning leads to a concrete placement. Fix tensor parallelism at ${N_{\text{TP}}}=8$ so the bandwidth-heavy matrix-multiplication collectives stay within one 8-GPU node. Map pipeline parallelism across nodes in the same high-bandwidth rack or island, here ${N_{\text{PP}}}=16$, with ${N_{\text{PP}}}=8$ as the alternative when the per-device memory budget allows. Use data parallelism for the remaining scale-out dimension across pods. The result is not a generic rule but a consequence of matching each traffic pattern to the cheapest fabric tier that can carry it. With the placement fixed, the next question is whether the static model state fits inside each accelerator’s HBM budget.

The memory budget for a 175B model must include every persistent training component. Under the mixed-precision Adam convention used here, each parameter has FP16 weights and gradients, an FP32 master weight, and two FP32 optimizer moments, totaling 16 bytes before activations and workspaces. With tensor parallelism degree 8 alone, these components occupy 350 GB per device, exceeding H100-class capacity. Adding 16 pipeline stages spreads that state across the product of the two degrees, yielding 21.9 GB per device under even partitioning. A budget that counts only weights and optimizer moments, about 13.7 GB per device here, understates this total. Activation peaks, layer imbalance, and communication workspaces must fit in the remaining memory before this configuration is feasible. Activation checkpointing can bring those peaks within budget, but the plan then pays in useful throughput, because recomputation costs about one extra forward pass per step when full and a few percent when selective ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-compute-phase-forward-backward|section 6.3.1.2]]), work that HFU counts and MFU does not.

Once the configuration fits in memory, its traffic still follows the same tiers, and each data-parallel group reduces only its tensor-and-pipeline shard of the 350 GB gradient buffer once per update. Gradient bucketing overlaps that reduction with backward computation, so its exposed cost depends on the computation remaining before the optimizer needs the reduced shard.

The last cost is scheduling rather than bandwidth, because a pipelined model is only efficient when enough microbatches are in flight to keep all stages busy. This remaining cost is the pipeline bubble developed in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-pipeline-parallelism-8748|section 6.5.2]]. Applying its bubble fraction $\frac{{N_{\text{PP}}}-1}{{m}+ {N_{\text{PP}}} - 1}$ to this hybrid layout, ${N_{\text{PP}}}=$ 16 stages with ${m}=$ 32 microbatches waste $\frac{15}{47} \approx 31.9\%$ of theoretical compute capacity, nearly one-third. Configuration C’s 4 stages at the same microbatch count would waste roughly 9 percent.

The deeper pipeline is chosen at this scale for two reasons. Its 16 stages spread the full training state to about 21.9 GB per device without optimizer sharding. Filling 16,384 GPUs with configuration C’s 32-GPU replicas would instead need 4× as many data-parallel replicas, which multiplies the global batch ${N_{\text{DP}}} \times {m}\times {B_{\text{micro}}}$ by the same factor at the same per-replica schedule. The shallow pipeline spends global batch; the deep one spends bubble. The 1F1B scheduling that reclaims activation memory, and the larger microbatch counts it makes practical, drive the bubble fraction down asymptotically. Every added microbatch also enlarges the global batch, so the bubble target must be reconciled with the critical-batch constraint from [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-systems-systems-critical-batch-size-parallelism-hurt-4961|section 6.4.6]].

Blackwell, the accelerator generation after the H100, shows how a wider fast communication domain changes 3D parallelism choices. NVLink 5 provides 1.8 TB/s of bidirectional bandwidth per GPU, twice the H100’s capacity, which shortens the transfer term for a fixed payload but does not reduce message startup latency. Larger tensor-parallel (${N_{\text{TP}}}$) groups, such as ${N_{\text{TP}}}=$ 16 or ${N_{\text{TP}}}=$ 32 across nodes, remain subject to topology and local-kernel efficiency. The 10 TB/s internal link joins Blackwell’s two dies behind one logical GPU, so those dies are not separate tensor-parallel ranks.

For a larger 1 trillion-parameter model on this hardware, one candidate uses ${N_{\text{TP}}}=$ 16 across two 8-GPU nodes joined by NVLink Switch and ${N_{\text{PP}}}=$ 8. Relative to the H100 layout’s ${N_{\text{TP}}}=$ 8 and ${N_{\text{PP}}}=$ 16, this preserves the model-partition product while halving stage count, and the bubble must be recomputed from the new stage and microbatch counts rather than assumed to halve. Improving local bandwidth shifts pressure outward. Once intra-node exchanges limit the step less, the inter-node fabric that carries pipeline and data-parallel traffic, together with any expert AllToAll service, becomes the term to check against the next tier. The same placement constraints define a search over the TP, PP, and DP factorizations of a fleet.

**Example 6.1: Automated design space search**

**Scenario**: An engineering team schedules a 175B-parameter model across 8,192 H100 GPUs (80 GB HBM each), 8× the 1,024-GPU reference cluster so that the pipeline and data-parallel degrees both have room to vary. The team navigates the multi-dimensional 3D-parallelism search space (TP $\times$ PP $\times$ DP).

**Diagnosis**: Candidate configurations must fit within 80 GB HBM and satisfy the modeled communication budget. The search evaluates TP $\times$ PP $\times$ DP factorizations and selects TP=8 GPUs, PP=8, and DP=128 as the best predicted MFU among configurations feasible under its assumptions. That result is a candidate for measurement, not proof of the best attainable runtime.

**Systems lesson**: This search favors TP=8 GPUs within the reference topology’s fast domain and PP=8, with 36.4 percent projected MFU. The result balances memory, local computation, transfers, and pipeline idle time within the search’s cost model. A different topology, microbatch schedule, or kernel efficiency can change the preferred factorization.

^exmp-distributed-training-automated-design-space-search-tier-3-optimizer

Adjusting any one dimension shifts the pressure onto the other two, making the factorization TP $\times$ PP $\times$ DP a tightly coupled system rather than three independent knobs. A projected MFU such as this search’s still needs comparison with measured execution, and published runs report MFU well below peak that can fall as the same model moves to more GPUs (**[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.03 ML Goodput#^fig-mfu-progression|figure]]** in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.03 ML Goodput#^sec-performance-engineering-fleet-efficiency-metric-dff4|Program goodput and its measure]]**).

**Checkpoint 6.4: Hybrid 3D parallelism**

Verify your understanding of how parallelism strategies combine:

**Dimension roles**: identify which dimension in a TP=8, PP=16, DP=128 configuration partitions operations within each layer inside one node.

**Bubble vs. depth**: determine how moving from PP=16 to PP=8 changes the pipeline bubble fraction.

**DP vs. PP**: explain the trade-off, with the budget fixed at that layout’s 16,384 GPUs, between increasing DP (data parallelism) and increasing PP (pipeline parallelism).

**Latency sensitivity**: identify which dimension, TP, PP, or DP, is most sensitive to inter-node latency.

The four configurations and the worked layout tell one story. Pure data parallelism would replicate 2,800 GB of training state on every GPU, which no fabric can repair. Keeping tensor parallelism inside the NVLink domain cuts each rank’s state and gradient shard by the tensor-parallel degree at the price of tensor-parallel exchanges, and pipeline stages cut them again at the price of a bubble. Communication alone does not make a layout feasible, however. Each layout must also hold the full training state, which is why configuration B would need gradient and optimizer sharding across its data-parallel group, why configuration C needs ZeRO-1, and why the reference job’s TP-8, PP-8, DP-16 layout deepens the pipeline until unsharded state fits, at a modeled 83 percent scaling efficiency. The worked layout at 16× that scale goes deeper still, until the persistent state falls to about 21.9 GB per device. Hybrid parallelism is therefore the joint solution of a memory constraint, a bandwidth hierarchy, and a batch-size limit, and every axis added to satisfy one of them tightens another. Alignment training tests that joint solution hardest, because it asks one fleet to host several models with different memory and compute profiles at the same time.
