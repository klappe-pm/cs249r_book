# V2-06.06 Model Parallelism

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training|V2-06 Distributed Training]]

^sec-distributed-training-systems-systems-model-parallelism-7437

Sharded data parallelism distributes stored state but still asks each worker to execute every layer on its local examples. If one layer’s gathered parameters and working memory exceed device capacity, or its execution is too slow for the target schedule, splitting that computation becomes a candidate. Model parallelism addresses this form of the memory capacity gap (principle [[01 Books/Volume II - Scaling/01 The Fleet/V2 Fleet Principles#^pri-memory-capacity-gap|2]]) by assigning different computations to different devices. Its value must be compared with offload, recomputation, and smaller local batches under the same throughput and quality requirements.

**Definition 6.7: Model parallelism**

***Model parallelism*** is a distributed training strategy that partitions a single neural network’s parameters or operations across multiple devices so each device computes a distinct portion of the model.

1.  **Significance**: If a model with parameter state ${M_{\text{weights}}}$ is split across ${N_{\text{TP}}} {N_{\text{PP}}}$ model-parallel devices, the ideal per-device parameter footprint falls toward ${M_{\text{weights}}}/({N_{\text{TP}}} {N_{\text{PP}}})$, enabling training of models that exceed single-device memory. The cost is extra communication for activations and gradients plus idle time from sequential dependencies, so the memory gain must exceed the transfer and pipeline-bubble overhead introduced by the partition.
2.  **Distinction**: Unlike data parallelism, which replicates the full model on every worker and shards the minibatch, model parallelism shards the model itself. Pipeline parallelism and tensor parallelism are implementation forms of model parallelism: one partitions layers into stages, while the other partitions individual tensor operations.
3.  **Common pitfall**: A frequent misconception is that model parallelism automatically speeds up training. Its possible gains are capacity, less traffic on the slow tier, and shorter layer time, and whichever gain a plan relies on must justify the added transfer and idle cost. Without careful scheduling and overlap, downstream devices wait for upstream activations and utilization can fall below a single-device baseline.

![[90 Assets/Volume II/06 Distributed Training/Distributed Training Memory Budget 0c17c39c33.svg]]

*Ladder of three blue memory rungs for a 175B-parameter mixed-precision Adam training state: optimizer 2,100 GB (longest), gradients 350 GB, and weights 350 GB.*

*Weights are only a small slice of the full Adam training state.*

Memory fit alone does not settle whether a model needs this kind of partition. For a 175B-parameter model, weights alone occupy 350 GB, or about 5.5 GB per GPU across a 64-GPU group, 1/16 of the 1,024-GPU reference cluster. Full mixed-precision Adam training state is much larger, 2,800 GB globally, yet ZeRO-3 across the same 64 GPUs reduces it to roughly 43.8 GB per GPU before activations, which fits an 80 GB accelerator. ZeRO-3 can therefore make the static state fit, as the notebook below confirms. It pays for that fit in traffic, because every step regathers every layer’s parameters across the data-parallel fabric, roughly three times the model’s parameter bytes per worker ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-memoryefficient-data-parallelism-zero-fsdp-0e69|section 6.3.3]]). It also cannot split an individual layer’s computation or activations across devices.

Activations add a separate memory requirement. Under the earlier unchecked-storage assumptions, a 2048-token sequence through 175B parameters produces roughly 1.1 TB at a local batch of 4 sequences; optimizer sharding does not reduce that storage. Recomputation trades memory for extra FLOPs, partitioning distributes activations, and offload moves them to another memory tier. Kernel and batch-size choices also change the budget. Full activation checkpointing brings the same modeled case down to ~19.3 GB. The following notebook, which uses a single-sequence local batch, checks whether ZeRO-3 plus checkpointing fits the model without partitioning its computation.

**Napkin Math 6.7: The memory wall of scale**

**Problem**: Training a 175B-parameter model (like GPT-3) on a 64-GPU group of NVIDIA A100s (80 GB), smaller than the 1,024-GPU reference cluster. The A100 carries the same 80 GB of HBM as the reference H100, so the capacity verdict carries over, and a small group is the harder test of whether sharding alone suffices. Can data parallelism with ZeRO-3 handle this?

**Math**:

1.  **Parameter storage**: 175B params $\times$ 2 bytes (FP16) = 350 GB.
2.  **Gradients and optimizer state**: Gradients add 175B params $\times$ 2 bytes = 350 GB, while Adam FP32 master weights, momentum, and variance add 175B params $\times$ 12 bytes = 2,100 GB.
3.  **Total static memory**: 2,800 GB.
4.  **ZeRO-3 sharding**: With 64 GPUs, per-GPU static memory = 2,800 GB/64 GPUs $\approx$ 43.8 GB.
5.  **Activation memory**: For sequence length 2048 and batch size 1, the canonical full-checkpointing strategy stores $\approx$ 4.8 GB of activations per GPU.

**Systems insight**: 43.8 GB (static) + 4.8 GB (dynamic) = 48.6 GB. Under this simplified accounting, ZeRO-3 plus full activation checkpointing fits within the 80 GB A100 capacity, leaving material headroom for framework buffers and transient layer gathers. If those additional allocations exceed the remaining HBM, the design can reduce the local batch, offload state, increase the sharding degree, or add tensor or pipeline parallelism; tensor parallelism is not the only recourse.

In this example, sharding and checkpointing make the modeled state fit, leaving two distinct reasons to partition the model itself. One is regather traffic. On the 1,024-GPU reference cluster, ZeRO-3 moves about 1.1 TB per worker per step for this model, which on one NDR InfiniBand port takes about 3× as each GPU’s computation for one training step, and longer still when gradient accumulation regathers the parameters for every microbatch. The other is layer execution, since full sharding gathers parameters on demand without ever splitting a single layer’s computation or activations across devices.

Model parallelism instead cuts the computation graph directly, either between sequential layer groups (such as layers 1–4 and layers 5–8) or inside a layer across channels and attention heads. Layer cuts introduce pipeline dependencies that leave downstream devices idle while an upstream stage computes, creating the pipeline bubble that governs utilization for this partition ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-pipeline-parallelism-8748|section 6.5.2]]). Channel and head cuts, the tensor parallelism of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-tensor-parallelism-d76e|section 6.5.3]], address both regather traffic and layer execution by partitioning individual weight matrices across devices. They expose concurrent work within a layer at the price of intra-layer exchanges, which the column-then-row pairing of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-tensor-parallel-split|figure 16]] confines to block boundaries.

These cuts enable the large-scale cases that exceed a single device for different reasons. GPT-3, with 175B parameters, was trained with model parallelism within each matrix multiplication and across layers ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-brown2020language|Brown et al. 2020]]). That partition avoids the full-parameter regather that ZeRO-3 pays on every step. Vision transformers processing high-resolution $16{k}{\times}16{k}$ pixel images use model parallelism to bound activation memory. Mixture-of-experts (MoE) architectures, whose sparsely activated feed-forward blocks are developed in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-expert-parallelism-mixture-experts-bc45|section 6.5.5]], distribute their conditional computation paths across hardware ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-shazeer2017outrageously|Shazeer et al. 2017]]; [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-lepikhin2021gshard|Lepikhin et al. 2021]]; [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-fedus2022switch|Fedus et al. 2022]]).

Each partitioning strategy trades single-device memory overflow for a different systems cost: layer-wise partitioning pays in idle time, pipeline parallelism pays in scheduling complexity to hide that idle time, and tensor parallelism pays in NVLink bandwidth to split individual layers. Sequence and context parallelism, expert parallelism, and sparse embedding sharding then extend the same trade-off to long-context activations, sparsely activated experts, and sparsely touched embedding tables.

### Layer-Wise Partitioning

^sec-distributed-training-systems-systems-layerwise-partitioning-cf6a

Where ZeRO-3 met the capacity limit by sharding storage while every worker still executed every layer, layer-wise model parallelism gives each device a *unique* contiguous block of layers to compute. It is the least invasive model cut: with 8-way partitioning, the 175B-parameter model’s 350 GB of FP16 weights fall to approximately 44 GB per GPU, though activations, gradients, and optimizer state still need sharding, offload, or pipeline scheduling ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.07 Hybrid Parallelism#^sec-distributed-training-systems-systems-hybrid-parallelism-12a0|section 6.6]]).

Because consecutive layer blocks remain sequentially dependent, however, a single batch passing through those stages in order leaves every other GPU waiting for its turn. In a 16-layer transformer placed four consecutive layers per GPU ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-dist-layers-blocks|figure 13]]), panel (a) shows each device holding one-quarter of the weights and exchanging only boundary activations and gradients, while panel (b) reveals the utilization penalty: without microbatch pipelining, each GPU computes in only two of the eight schematic time slots and sits idle for the other six.

![[90 Assets/Volume II/06 Distributed Training/Layer Wise Partitioning c6338f4489.svg]]

Figure 13: **Layer-Wise Model Parallelism**: (a) A 16-layer transformer placed four consecutive layers per GPU, cutting each GPU’s weight footprint to one-quarter of the model. Forward activations cross each stage boundary left to right; gradients return right to left. (b) Without microbatching, one batch visits the stages in turn, forward (F) and then backward (B) in reverse, in equal schematic time slots, so each GPU works in only 2 of 8 slots. The microbatched schedule in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-pipeline-parallelism|figure 14]] fills much of that idle time.

^fig-dist-layers-blocks

Partitioning layers changes where an optimizer update runs without necessarily changing the update rule. Each GPU can apply Adam ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-kingma2014adam|Kingma and Ba 2015]]), AdaFactor, or another optimizer to its parameter slice once the required gradients are complete. A device holding transformer layers 1–12 updates those layers. Tied parameters, which share one weight matrix across stages, can still require coordination, as can global gradient clipping, whose norm spans every stage, and a combined data-parallel group. Preserving synchronous optimization also requires the schedule to use consistent parameter versions. Sequential dependencies introduce pipeline bubbles, and unequal stage service times add waiting. The engineering problem is to overlap microbatches and balance stage work while preserving that update contract ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-rasley2020|Rasley et al. 2020]]).

### Pipeline Parallelism

^sec-distributed-training-systems-systems-pipeline-parallelism-8748

Without pipelining, a four-stage layer partition leaves three of the four GPUs idle at any moment because downstream stages cannot start until upstream stages finish the entire batch ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-dist-layers-blocks|figure 13]]). Pipeline parallelism breaks that stall by splitting the batch into smaller microbatches and streaming them through the stages like a relay race. As soon as GPU 1 finishes the initial transformer blocks on microbatch 1, it hands the resulting activation tensor to GPU 2 and immediately starts microbatch 2. For the 175B model with hidden dimension 12,288 and a microbatch of 4 sequences at 2,048 tokens each, that forward handoff carries approximately 201 MB per stage boundary per microbatch. GPU 2 needs that payload before processing the same microbatch, creating a dependency chain through the stages, while other microbatches occupy the remaining stages concurrently. Backward propagates activation gradients in reverse as each stage computes gradients for its own parameters.

**Definition 6.8: Pipeline parallelism**

***Pipeline parallelism*** is a model parallelism technique that partitions a neural network’s layers into sequential stages assigned to different devices, passing activations forward and gradients backward between stages while overlapping computation across stages using microbatches to maintain throughput.

1.  **Significance**: Each boundary transfers forward activations and backward activation gradients. A forward tensor contains ${B_{\text{micro}}} \times {S}\times {d}\times 2$ bytes at BF16, where ${B_{\text{micro}}}$ is the microbatch size. For a hidden dimension of 8,192 with microbatch size 1 and a 2,048-token sequence, the forward payload is approximately 8,192 $\times$ 2,048 $\times$ 2 $\approx$ 34 MB per microbatch per boundary. Backward traffic and all microbatches must be counted before comparing this with a per-update gradient AllReduce or sizing a 50 GB/s InfiniBand link. In a balanced noninterleaved schedule with ideal transfers, the idle fraction is approximately $({N_{\text{PP}}}-1)/({m}+{N_{\text{PP}}}-1)$, where ${N_{\text{PP}}}$ is the stage count and ${m}$ the microbatch count.
2.  **Distinction**: Tensor parallelism partitions operations within a layer and introduces communication among their participants. Pipeline parallelism instead transfers activations and their gradients between sequential stages. This coarser exchange can suit slower links when the transfer fits within the stage schedule; the interconnect name alone does not establish feasibility.
3.  **Common pitfall**: A frequent misconception is that adding pipeline stages always improves throughput. Each additional stage increases the pipeline bubble fraction $({N_{\text{PP}}}-1)/({m}+{N_{\text{PP}}}-1)$ unless the number of microbatches ${m}$ scales proportionally, causing hardware to idle and erasing the benefit of deeper partitioning.

In the GPipe schedule of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-pipeline-parallelism|figure 14]], a four-stage pipeline processes four microbatches (${N_{\text{PP}}}=4, {m}=4$). Dividing the global batch into discrete microbatches allows forward passes to overlap diagonally across stages before backward passes unfold in reverse order. While microbatching raises hardware utilization above naive sequential placement, pipeline fill (${t}_1$–${t}_3$) and drain (${t}_{12}$–${t}_{14}$) bubbles still leave each device idle for 6 of 14 time slots.

![[90 Assets/Volume II/06 Distributed Training/Pipeline Parallelism e1c2df00d6.svg]]

Figure 14: **Pipeline Parallelism Schedule**: A 4-stage pipeline processes 4 microbatches with all forward passes (F) before any backward pass (B), as in GPipe. Rows are pipeline stages and columns are equal time slots. Each backward pass enters a stage only after the next stage has produced that microbatch’s gradient, so every stage idles ${N_{\text{PP}}}-1$ slots in the forward phase and ${N_{\text{PP}}}-1$ in the backward phase, 6 of 14 slots in all.

^fig-pipeline-parallelism

Tracing the schedule grid in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-pipeline-parallelism|figure 14]] column by column reveals how the fill and drain bubbles arise. In the first slot only stage 0 has work, the forward pass of microbatch 1. In the second, stage 0 starts microbatch 2 while stage 1 receives microbatch 1’s activations, and by the fourth slot every stage holds a different microbatch. The last stage then turns microbatch 4 around into its backward pass, and gradients travel upstream in reverse microbatch order, so stage 0 waits until the eleventh slot for its first gradient. Each stage therefore idles 3 slots in the forward phase and 3 more in the backward phase, 6 of the 14 slots in the step. Those idle slots may fall at the start of its row, the middle, or the end. That share, about 43 percent, is the bubble fraction $({N_{\text{PP}}}-1)/({m}+{N_{\text{PP}}}-1)$ at ${N_{\text{PP}}}={m}=$ 4. Adding microbatches lengthens the busy diagonal without lengthening fill and drain in this balanced schedule. Increasing ${m}$ is therefore one way to reduce the idle fraction; later schedules also change which work can occupy the gaps.

**Napkin Math 6.8: The cost of the pipeline bubble**

**Problem**: A large-model training run uses pipeline parallelism across 8 stages. To hide the sequential delay, the batch is split into 32 microbatches. What fraction of GPU cycles does the pipeline bubble leave idle?

**Math**: For balanced, noninterleaved synchronous stages under the one-forward-one-backward (1F1B) schedule developed below, with ideal transfers, the bubble fraction follows from the stage and microbatch counts. The time units below each combine one forward and one backward service interval; they are not individual optimizer steps.

1.  **Wait time**: At the start and end of each batch, GPUs sit idle for ${N_{\text{PP}}}-1$ steps.
2.  **Productive time**: GPUs compute for ${m}$ steps.
3.  **Bubble fraction**: $({N_{\text{PP}}}-1) / ({N_{\text{PP}}}-1+{m}) =$ 7 $/$ (7 $+$ 32) $\approx$ 17.9 percent.

**Systems insight**: Pipeline parallelism is a *utilization-memory trade-off*. With this stage count and schedule fixed, reducing the bubble from 18 percent to 5 percent requires more microbatches $({m})$. In general, holding the bubble under 10 percent requires ${m}> 9({N_{\text{PP}}}-1)$, because $({N_{\text{PP}}}-1)/({m}+{N_{\text{PP}}}-1) < 0.1$ rearranges to that bound. The activation memory those microbatches need depends on the schedule. GPipe retains activations across the microbatches, whereas the 1F1B schedule developed next releases them during the steady state. The modeled 17.9 percent idle fraction also motivates interleaved pipelining, which divides each device’s work into smaller stages. Interleaving can reduce the original 18 percent bubble, but additional transfers and memory requirements determine the net gain.

GPipe[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.15 Footnotes#^fn4|⁴]] ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-huang2019gpipe|Huang et al. 2019]]) introduced synchronous pipeline parallelism with microbatch accumulation, while PipeDream ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-narayanan2019|Narayanan et al. 2019]]) developed asynchronous approaches with weight stashing, which keeps one parameter version per in-flight minibatch so that its forward and backward passes use the same weights. Modern systems use 1F1B (one-forward-one-backward)[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.15 Footnotes#^fn5|⁵]] scheduling to reclaim activation memory earlier. That lower memory pressure makes larger microbatch counts practical, and the larger ${m}$ is what shrinks the bubble term.

At the schedule level, 1F1B is a warmup, steady-state, and drain loop. In [algorithm 1](https://mlsysbook.ai/vol2/06_distributed_training/06_distributed_training.html#algo-one-forward-one-backward-pipeline), each stage alternates forward work for newer microbatches with backward work for older microbatches once gradients arrive, so activations can be released before the whole batch has completed.

${N_{\text{PP}}}$

Run on four stages with eight microbatches, the schedule gives each stage a short warm-up of forward passes, a steady state that alternates one backward with one forward, and a drain of the remaining backward passes ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-pipeline-1f1b|figure 15]]). The warm-up and drain phases still leave a bubble of roughly $({N_{\text{PP}}}-1)/({m}+{N_{\text{PP}}}-1)$, 6 of 22 slots here. Interleaving backward work in the steady state, however, frees each activation as soon as its backward consumes it. Stage 0 never holds more than four microbatches’ activations where an all-forwards-first schedule would hold all eight, so peak activation memory grows with the stage count rather than the microbatch count. That is the gain over GPipe-style all-forward-then-all-backward scheduling, and it lets the system raise ${m}$ until activation memory, recomputation, or the global-batch constraint becomes the next limit.

![[90 Assets/Volume II/06 Distributed Training/Pipeline 1f1b Schedule ab3e16f86a.svg]]

Figure 15: **One-Forward-One-Backward (1F1B) Pipeline Schedule**: Four stages process eight microbatches in equal schematic slots. After a warm-up of forward passes, each stage alternates one backward pass with one forward pass, then drains its remaining backward passes. Fill and drain still idle every stage for 6 of 22 slots, the bubble fraction $({N_{\text{PP}}}-1)/({m}+{N_{\text{PP}}}-1)$, but each stage releases a microbatch’s activations as soon as that microbatch’s backward pass runs. The bars at the right count the most microbatches whose activations a stage holds at once, four at stage 0 and one at the last stage, against the eight an all-forwards-first schedule would hold (dashed).

^fig-pipeline-1f1b

The activation handoff has shape ${B_{\text{micro}}} \times {S}\times {d}$; its completion still constrains the next stage. The 1F1B schedule in [algorithm 1](https://mlsysbook.ai/vol2/06_distributed_training/06_distributed_training.html#algo-one-forward-one-backward-pipeline) reduces activation residency, but fill, drain, communication, and load imbalance leave idle time.

Zero-bubble pipeline schedules further reduce idle time by decoupling the two matrix multiplications inside each layer’s backward pass. In a standard backward pass, the GPU computes both $\partial {\mathcal{L}}/ \partial {\mathbf{X}}$ (the activation gradient propagated backward to the preceding stage) and $\partial {\mathcal{L}}/ \partial {\mathbf{W}}$ (the weight gradient accumulated locally for the optimizer step) back-to-back as a single backward unit. Zero-bubble scheduling splits them into separate kernels. A B kernel multiplies the incoming upstream gradient by the stage’s persistent weights ${\mathbf{W}}^T$ to compute only the activation gradient $\partial {\mathcal{L}}/ \partial {\mathbf{X}}$ and immediately sends it to the previous stage. A W kernel multiplies the saved forward activation ${\mathbf{X}}^T$ by the upstream gradient to compute the weight gradient $\partial {\mathcal{L}}/ \partial {\mathbf{W}}$ locally. Because upstream stages cannot begin their own backward work until they receive $\partial {\mathcal{L}}/ \partial {\mathbf{X}}$, the B kernel sits on the critical path and must execute promptly, whereas the W kernel has no cross-stage dependency and can be scheduled opportunistically to fill local pipeline bubbles.

The B/W split creates scheduling freedom, although all deferred W kernels must still finish before the corresponding optimizer update. In the balanced four-stage, eight-microbatch schedule of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-pipeline-1f1b|figure 15]], noninterleaved 1F1B still leaves $3/11 \approx 27$ percent of each stage’s time idle, by the bubble fraction derived above. Reordering forward, activation-gradient, and weight-gradient work allows deferred W kernels to soak up those idle slots. Approaching zero bubble time in practice also depends on kernel durations, memory headroom, and optimizer synchronization, so splitting the backward pass alone does not guarantee it.

The trade-off is memory. Because the B kernel needs only the incoming gradient and the persistent weights ${\mathbf{W}}$, whereas the W kernel requires the saved forward activation ${\mathbf{X}}$, a stage cannot free a microbatch’s forward activation when B finishes. Deferring W to fill a later bubble forces the stage to keep both ${\mathbf{X}}$ and the incoming gradient resident in device memory until W finally executes, increasing peak memory usage. Some implementations address this by combining zero-bubble scheduling with activation checkpointing, selectively recomputing certain activations before W rather than storing them across the delay. The interaction between these techniques creates a three-way trade-off among pipeline bubble size, memory consumption, and recomputation overhead, an example of the displacement of overhead (principle [[01 Books/Volume II - Scaling/02 Distributed ML/V2 Distributed ML Principles#^pri-conservation-overhead|14]]).

### Tensor Parallelism

^sec-distributed-training-systems-systems-tensor-parallelism-d76e

Every pipeline schedule so far keeps whole layers on each device, which is why its traffic is confined to stage boundaries and tolerates moderate interconnect bandwidth. The same property sets its limit. A pipeline cannot help when a single layer’s weights or activations exceed one device, and it cannot shorten the time one layer takes, because that layer still runs on one accelerator.

Tensor parallelism splits the weight matrices within each layer instead of assigning complete layers to devices. This operator-level parallelism (also called intra-layer parallelism) enables finer-grained distribution but requires high-bandwidth interconnects for the frequent intra-layer communication it introduces.

**Definition 6.9: Tensor parallelism**

***Tensor parallelism*** partitions individual tensor operations across devices, commonly through column-parallel or row-parallel weight splits. Communication combines or redistributes the resulting tensor shards as required by the next operation. The Megatron-style forward-pass example below illustrates one such arrangement.

1.  **Significance**: The Megatron-LM arrangement developed below uses two AllReduce operations per transformer block in the forward pass, one after attention and one after the MLP. Each reduces a 2-byte activation tensor of ${B}\times {S}\times {d}$ elements, where ${B}$ counts the sequences in flight through the layer. A ring AllReduce moves roughly $2({N_{\text{TP}}}-1)/{N_{\text{TP}}}$ times that payload per GPU, and the exchange recurs in every one of the 96 blocks of the GPT-3 shape, with backward adding corresponding exchanges. Whether that traffic hides behind computation depends on the link that carries it, which the arithmetic after the mechanism quantifies.
2.  **Distinction**: Unlike pipeline parallelism, which communicates only at layer boundaries and transfers small activation slices, tensor parallelism synchronizes within every layer via AllReduce. It is therefore sensitive to the per-operation latency of the interconnect and favors a fast communication domain such as NVLink, which can extend beyond one node.
3.  **Common pitfall**: Extending tensor parallelism across nodes without checking the transfer budget can erase the compute saving. The reference NVLink specification is approximately 900 GB/s bidirectional, or 450 GB/s per direction; InfiniBand NDR provides 50 GB/s per port, a 9× per-direction gap. These specifications identify a placement risk. Whether the split helps depends on sustained bandwidth, operation size, compute saved, and overlap.

Frequent intra-layer exchanges favor placing tensor-parallel groups within the fastest available communication domain. Pipeline stages communicate at coarser boundaries and can often span slower domains when their transfers fit the schedule. This difference motivates a hybrid that maps each exchange to a suitable fabric tier; it does not impose a universal node boundary for either strategy.

*Two violet bars: NVLink at 450 GB/s per direction and InfiniBand NDR at 50 GB/s, with a 9× arrow between their ends.*

*Tensor-parallel exchanges belong on the fast tier, about 9$\times$ an NDR port.*

Megatron-style tensor parallelism[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.15 Footnotes#^fn6|⁶]] ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-shoeybi2019megatron|Shoeybi et al. 2019]]) partitions matrix multiplications by alternating column and row splits. In the two-GPU dataflow of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-tensor-parallel-split|figure 16]], column-parallel splitting partitions the first weight matrix ${\mathbf{A}}= [{\mathbf{A}}_1 \mid {\mathbf{A}}_2]$ to produce local activation slices ${\mathbf{Y}}_1, {\mathbf{Y}}_2$ from replicated input ${\mathbf{X}}$. Row-parallel splitting then partitions the second weight matrix ${\mathbf{B}}= [{\mathbf{B}}_1 ; {\mathbf{B}}_2]$ so that each GPU computes partial products ${\mathbf{Z}}_1, {\mathbf{Z}}_2$ locally. This defers cross-device communication to a single AllReduce that reconstructs output ${\mathbf{Z}}$.

Column-parallel linear layers split weights along columns. For input ${\mathbf{X}}$ and weight matrix ${\mathbf{W}}= [{\mathbf{W}}_1 \mid {\mathbf{W}}_2]$ split across 2 GPUs:

$$
{\mathbf{Y}}= {\mathbf{X}}{\mathbf{W}}= {\mathbf{X}}[{\mathbf{W}}_1 \mid {\mathbf{W}}_2] = [{\mathbf{X}}{\mathbf{W}}_1 \mid {\mathbf{X}}{\mathbf{W}}_2]
$$

 Each GPU computes its partition independently. The concatenation in the equation is logical, because when the next operation is row-parallel, each output shard remains on its producing device and feeds the matching weight shard without an AllGather. The row-parallel half of the pattern splits weights along rows, ${\mathbf{W}}= \begin{bmatrix} {\mathbf{W}}_1 \\ {\mathbf{W}}_2 \end{bmatrix}$, and the layer’s input arrives split along its columns to match, each GPU holding the shard it kept from a preceding column-parallel layer:

$$
{\mathbf{Y}}= {\mathbf{X}}{\mathbf{W}}= {\mathbf{X}}_1 {\mathbf{W}}_1 + {\mathbf{X}}_2 {\mathbf{W}}_2
$$

 Each GPU computes a partial sum, and the system pays one AllReduce to combine the partial outputs.

![[90 Assets/Volume II/06 Distributed Training/Tensor Parallel Split c1bba21f43.svg]]

Figure 16: **Matrix Partitioning under Tensor Parallelism**: A Megatron-LM layer pair on two GPUs, read left to right. The first layer (for example, QKV or the first feed-forward layer) is split by columns, ${\mathbf{A}} = [{\mathbf{A}}_1 \mid {\mathbf{A}}_2]$, so each GPU computes its own slice ${\mathbf{Y}}_i$ of the replicated input’s output. The second layer is split by rows, ${\mathbf{B}} = [{\mathbf{B}}_1 ; {\mathbf{B}}_2]$, so each slice feeds its matching shard on the same GPU without communication. The only collective is the amber AllReduce that sums the partial outputs ${\mathbf{Z}}_1 + {\mathbf{Z}}_2$, leaving the full result on both GPUs.

^fig-tensor-parallel-split

The column-then-row sequence of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-tensor-parallel-split|figure 16]] embodies the governing architectural invariant. Pairing a column-parallel layer directly with a row-parallel layer allows intermediate activations (${\mathbf{Y}}_1, {\mathbf{Y}}_2$) to remain strictly local on each GPU, confining inter-device synchronization to a single collective at the end of the block. This locality holds because the intermediate operation between the two projections acts independently on each GPU’s column slice without cross-rank data.

Megatron applies that pattern twice in each transformer block. In multi-head attention, the QKV projection is column-parallel along the head dimension so that each GPU receives the complete query, key, and value vectors for a disjoint subset of ${N_{\text{heads}}}/{N_{\text{TP}}}$ attention heads, computes attention locally for those heads, and feeds the resulting head outputs into the row-parallel attention output projection. In the feed-forward network, the first linear layer is column-parallel, the element-wise nonlinearity applies independently to each coordinate of the local slice, and the second linear layer is row-parallel. The forward pass therefore places one AllReduce after attention and one after the feed-forward network, for two forward AllReduce operations per transformer layer. In the backward pass, the dataflow reverses so that gradients enter each row-parallel output layer without communication, while at the input of each column-parallel layer every GPU computes a partial input gradient from its local weight slice and runs an AllReduce to sum those contributions before the preceding residual connection, adding two symmetric backward AllReduces per layer.

Communication volume per transformer layer depends on sequence length ${S}$, hidden dimension ${d}$, tensor-parallel degree ${N_{\text{TP}}}$, and batch size ${B}$. The batch size is the number of sequences in flight through the layer (the local batch, or the microbatch ${B_{\text{micro}}}$ when the layer also sits in a pipeline). The activation payload is:

$$
{M_{\text{act}}}= {B}\times {S}\times {d}\times {s_{\text{elem}}}
$$

A ring AllReduce transfers approximately $2({N_{\text{TP}}}-1)/{N_{\text{TP}}} \times {M_{\text{act}}}$ bytes per GPU, which is close to $2{M_{\text{act}}}$ for large ${N_{\text{TP}}}$. For the GPT-3 shape (${S}=$ 2048, ${d}=$ 12,288, 96 layers) with ${B}=$ 4 and FP16, the activation payload is 4 $\times$ 2048 $\times$ 12,288 $\times$ 2 $\approx$ 201 MB.

At ${N_{\text{TP}}}=$ 8 the ring factor is 1.75, giving roughly 352 MB per AllReduce. With two AllReduces in each of the 96 layers, this totals approximately 67.6 GB per forward microbatch. The symmetric backward exchanges bring the total to roughly 135 GB per forward/backward microbatch, before any recomputation. Set against the computation it serves, that volume is modest on the right link and prohibitive on the wrong one. At the per-layer compute rate of the earlier feasibility check, one such microbatch takes about 2.2 s of forward and backward computation per GPU. Its tensor-parallel traffic takes about 0.3 s on NVLink but about 2.7 s on one InfiniBand port, longer than the computation. The gap matters because this traffic sits on the critical path of every layer. The next operation consumes each reduced result and cannot start on that data until the reduction completes, whereas a data-parallel gradient reduction can overlap the backward computation that remains. The number of microbatches per update and the available overlap then determine the required fabric service rate. Computing MFU requires the complete compute and exposed-communication time, not the bandwidth ratio alone.

Tensor parallelism eventually reaches a workload-dependent limit because smaller operation shards leave less computation to cover communication. Per-GPU ring AllReduce bytes approach 2$\times$ the activation tensor size, while local matrix shapes and collective startup costs change with group size. The useful degree therefore depends on layer shape, microbatch size, and the fast communication domain. Llama 3 405B’s TP=8 arrangement within NVLink-connected H100 nodes ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-dubey2024llama|Dubey et al. 2024]]) and node-local groups in other large training systems ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-jiang2024megascale|Z. Jiang et al. 2024]]) illustrate a placement choice, not a universal eight-device limit. Tensor parallelism also costs more to adopt than data parallelism. It replaces standard linear layers with column-parallel and row-parallel variants inside the model definition, whereas data parallelism wraps the model externally without modifying its internals.

### Sequence and Context Parallelism

^sec-distributed-training-systems-sequence-context-parallelism

While tensor parallelism partitions weight matrices within linear layers, the memory footprint of large-scale transformer training is increasingly dominated by activations. As models scale their context length from thousands to hundreds of thousands or millions of tokens (${S}\ge 32\text{k}\dots 1\text{M}+$), the activation footprint scales proportionally:

$$
{M_{\text{activations}}} = \mathcal{O}({B}\times {S}\times {d}\times {N_L})
$$

 for linear, normalization, and residual layers, and $\mathcal{O}({B}\times {N_{\text{heads}}} \times {S}^2 \times {N_L})$ for un-tiled attention (or $\mathcal{O}({B}\times {S}\times {d}\times {N_L})$ with tiled FlashAttention, which computes attention block by block without storing the full score matrix). At long contexts, activation memory dwarfs parameter storage, exposing the memory capacity gap (principle [[01 Books/Volume II - Scaling/01 The Fleet/V2 Fleet Principles#^pri-memory-capacity-gap|2]]). Two complementary methods address this constraint by sharding along the sequence axis: sequence parallelism (SP) within the tensor-parallel domain, and context parallelism (CP) across dedicated long-sequence communication groups.

**Definition 6.10: Sequence and context parallelism**

***Sequence and context parallelism*** partition the token sequence dimension to reduce per-device activation storage. Sequence parallelism (SP) retains sequence shards during operations such as LayerNorm and Dropout within a tensor-parallel group. Context parallelism (CP) partitions the sequence across a dedicated group and exchanges the information needed for attention, through mechanisms developed below that either pass key/value blocks around a ring or transpose between sequence and head partitions.

1.  **Significance**: Long contexts can exhaust activation memory even when sharded model state fits. The relevant limit depends on batch size, layer shapes, attention kernels, and checkpointing. Sequence parallelism divides the targeted activation storage by ${N_{\text{TP}}}$ while preserving the ideal collective payload volume in the decomposition below. Context parallelism distributes sequence-dependent storage; linear context growth (${c}\times {S_{\text{single}}}$, with ${c}$ denoting the context-parallel degree) is an ideal capacity estimate that still requires communication buffers and computation to fit the budget.
2.  **Distinction**: Tensor parallelism partitions weight matrices along hidden dimensions ${d}$, whereas context parallelism partitions the sequence axis ${S}$. Ring Attention exchanges key/value chunks between devices, while Ulysses uses an AllToAll to transpose between sequence and head dimensions. Both require placement that can service their exchanges within the attention schedule.
3.  **Common pitfall**: Assuming context parallelism eliminates the quadratic attention compute complexity. CP distributes the attention computation across devices, reducing *per-device* memory and FLOPs by $1/{c}$, but the *aggregate* cluster FLOPs for dense self-attention still scale quadratically as $\mathcal{O}({S}^2)$.

#### Megatron Sequence Parallelism

^sec-distributed-training-megatron-sequence-parallelism-7a2e

In the Megatron-style arrangement just derived, the column-then-row pairing in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-tensor-parallel-split|figure 16]] splits the QKV projection and first MLP layer column-wise, and the attention output projection and second MLP layer row-wise. The surrounding LayerNorm, Dropout, and residual operations retain replicated activations across all ${N_{\text{TP}}}$ devices. LayerNorm operates across a token’s hidden features, while Dropout and residual addition operate element-wise; none requires another token’s features. This token independence permits partitioning the otherwise replicated ${B}\times {S}\times {d}$ activation tensor along its sequence dimension.

Megatron Sequence Parallelism ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-korthikanti2023activation|Korthikanti et al. 2023]]) eliminates this redundancy by sharding the sequence dimension across the ${N_{\text{TP}}}$ ranks for all non-tensor-parallel operations. Instead of replicating activations, each GPU holds only a ${B}\times ({S}/{N_{\text{TP}}}) \times {d}$ slice during LayerNorm and Dropout.

This sharding incurs zero additional communication volume. In standard tensor parallelism, the row-parallel matrix multiplication is followed by an AllReduce to sum partial products across ranks. An AllReduce decomposes into a ReduceScatter followed by an AllGather, the identity established among the collective primitives in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.05 Collective Operation Primitives#^sec-collective-communication-six-core-primitives-8a66|The six core primitives]]**:

$$
\text{AllReduce}({x}) \equiv \text{AllGather}(\text{ReduceScatter}({x}))
$$

 Megatron-SP decouples this collective pair across the transformer block. Following the row-parallel linear layer, a ReduceScatter reduces partial sums while scattering the resulting activations along the sequence dimension, leaving each GPU with an ${S}/{N_{\text{TP}}}$ token slice. LayerNorm, residual additions, and Dropout then execute on these local slices with zero cross-device communication. Immediately before the next column-parallel linear layer, an AllGather across the sequence dimension reassembles the complete ${S}$ tokens required for the weight-partitioned matrix multiplication.

In this ideal payload accounting, standard TP executes two AllReduces per transformer block ($2 \times 2({N_{\text{TP}}}-1)/{N_{\text{TP}}} \times {M_{\text{act}}}$ bytes), while Megatron-SP executes two ReduceScatter and AllGather pairs ($2 \times [({N_{\text{TP}}}-1)/{N_{\text{TP}}} + ({N_{\text{TP}}}-1)/{N_{\text{TP}}}] \times {M_{\text{act}}}= 2 \times 2({N_{\text{TP}}}-1)/{N_{\text{TP}}} \times {M_{\text{act}}}$ bytes). The volumes match while the targeted activation storage falls by a factor of ${N_{\text{TP}}}$. Equal bytes do not imply equal elapsed time, because separating the collectives changes readiness, startup costs, and overlap opportunities.

#### Context Parallelism with Ring Attention Versus Ulysses

^sec-distributed-training-context-parallelism-ring-ulysses-8b1f

Megatron-SP shards the ${S}$ dimension across the ${N_{\text{TP}}}$ devices only outside the attention and MLP blocks; inside self-attention, each tensor-parallel rank still processes the full sequence length ${S}$ for its local heads, so long-context runs can still exhaust HBM even after sequence parallelism and activation checkpointing. Context parallelism of degree ${c}$ breaks that ceiling by partitioning the sequence itself across ${c}$ accelerators throughout the entire block, including attention. Because every query token must still attend to keys and values from other sequence partitions, context parallelism requires cross-partition exchanges, supplied either by ring-based point-to-point transfers, by AllToAll head-sequence transpositions, or by a hierarchical combination of both.

Ring Attention ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-liu2023ringAttention|Liu et al. 2023]]) organizes devices in a logical ring where each GPU holds a query chunk ${\mathbf{Q}}_i$ of length ${S}/{c}$ and an initial key/value chunk $({\mathbf{K}}_i, {\mathbf{V}}_i)$. Computation proceeds in ${c}$ rounds along the ring. In each round, GPU ${i}$ computes block attention between its stationary ${\mathbf{Q}}_i$ and resident $({\mathbf{K}}_j, {\mathbf{V}}_j)$ tiles using an online softmax accumulator. At the same time, it asynchronously transmits $({\mathbf{K}}_j, {\mathbf{V}}_j)$ to ring neighbor $({i}+1) \bmod {c}$ and receives $({\mathbf{K}}_{j-1}, {\mathbf{V}}_{j-1})$ from $({i}-1) \bmod {c}$. After ${c}$ rounds every query chunk has attended to every key/value tile, yet no device ever stores the full key/value sequence ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-ring-attention-rounds|figure 17]]). Normalizing a query’s attention scores requires all of them, but they arrive one tile at a time. The online softmax therefore maintains a running maximum and running sum of attention scores as tiles arrive and rescales earlier partial sums whenever the maximum changes. Each round’s partial result merges into that running state, which likewise spares each device the full attention matrix.

![[90 Assets/Volume II/06 Distributed Training/Ring Attention Rounds 927825266d.svg]]

Figure 17: **Ring Attention Rounds**: Context parallelism of degree four on four GPUs. Each GPU keeps its query chunk and, in each round, attends to the key/value tile it currently holds while sending that tile to the next GPU in the ring; dashed arrows close the ring from GPU 3 back to GPU 0. After four rounds every query chunk has seen every tile, so each GPU’s attention output for its own queries is complete. The transfer hides behind the block computation only when chunks are long enough, the overlap condition derived next.

^fig-ring-attention-rounds

For one sequence with standard multi-head attention, let ${n}={S}/{c}$ be the tokens per chunk, ${d}$ the total head width, ${s_{\text{elem}}}$ the bytes per stored element, ${R_{\text{peak}}}{\eta_{\text{hw}}}$ the sustained attention FLOP/s, and ${\text{BW}_{\text{link}}}$ the one-way transfer rate. Computing both ${\mathbf{Q}}{\mathbf{K}}^T$ and the weighted-value product costs approximately $4{n}^2 {d}$ FLOPs, while sending ${\mathbf{K}}$ and ${\mathbf{V}}$ costs $2 {n} {d}\, {s_{\text{elem}}}$ bytes. Ignoring startup, softmax, and overlap interference gives the necessary tile-size estimate:

$$
\frac{4{n}^2 {d}}{{R_{\text{peak}}}{\eta_{\text{hw}}}} \ge \frac{2 {n} {d}\, {s_{\text{elem}}}}{{\text{BW}_{\text{link}}}} \iff {n}\ge \frac{{s_{\text{elem}}} {R_{\text{peak}}}{\eta_{\text{hw}}}}{2{\text{BW}_{\text{link}}}}
$$

 This compares computation time with transfer time; HBM bandwidth cannot substitute for ${R_{\text{peak}}}{\eta_{\text{hw}}}$. It is an idealized overlap condition, not a guarantee.

For an H100 sustaining half its dense FP16 peak with 2-byte elements, the condition requires chunks of at least about 1,100 tokens per device when KV tiles travel over NVLink, and about 9,900 tokens when they cross one NDR InfiniBand port. A million-token context split across a few dozen devices clears both bounds, whereas splitting a 32K context across many nodes can leave each chunk too short to hide its transfers. Grouped-query attention, in which several query heads share one key-value head, changes the transferred KV width, and causal masking changes the tile work. Both require recomputing the two costs.

In causal autoregressive attention, a query token can attend only to earlier or current positions, so whenever a rank holding query chunk ${i}$ receives a key and value chunk from a later sequence position ${j}> {i}$, the entire upper-triangular tile is masked out. Under naive contiguous partitioning, rank ${i} = 0$ holds the earliest tokens and performs useful work only on its own chunk (${j} = 0$), sitting idle during the remaining ${c} - 1$ ring rounds while rank ${c} - 1$ (holding the final tokens) computes on every round. Because the ring steps synchronously at the pace of the busiest rank, this load imbalance leaves half the cluster’s compute cycles idle. Production implementations eliminate this skew with zigzag or striped token partitioning, which splits the sequence into $2{c}$ sub-chunks and gives each device one early sub-chunk and one complementary late sub-chunk (for example, one chunk from the start of the sequence and one from the end). Every device then holds the same share of unmasked causal tiles in every round of the ring.

DeepSpeed Ulysses ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-jacobs2023deepspeed|Jacobs et al. 2023]]) exploits the independence of attention heads rather than circulating tiles along a ring. Each head attends over the whole sequence without reading any other head’s scores, so the attention work can be split by heads instead of by tokens. Outside the attention core, activations are sharded along the sequence dimension (${S}/{c}$ tokens, all ${N_{\text{heads}}}$ attention heads). Before computing self-attention, an AllToAll collective transposes the tensor from sequence-partitioned `[S/c, h, d_head]` to head-partitioned `[S, h/c, d_head]`. Each GPU now holds the full sequence length ${S}$, but only a subset ${N_{\text{heads}}}/{c}$ of attention heads. Each device computes standard local FlashAttention across the full sequence for its heads; each rank owns complete heads, while the kernel handles causal masking locally. A second AllToAll collective transposes the attention output back to `[S/c, h, d_head]`. Ulysses is conceptually clean and reuses single-GPU attention kernels, but requires that the head count be divisible by the context degree and therefore no smaller than it (${N_{\text{heads}}} \ge {c}$). Under grouped-query attention, where the key-value head count ${H_{\text{KV}}}$ is smaller, a direct head-sharding implementation requires compatible divisibility and ${c}\le {H_{\text{KV}}}$. Replicating KV heads changes that limit and its communication budget.

The ownership map in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-ulysses-ownership-transpose|figure 18]] makes this transpose explicit. Unlike the stationary query chunks in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-ring-attention-rounds|figure 17]], a Ulysses rank receives every token for its assigned heads.

![[90 Assets/Volume II/06 Distributed Training/Ulysses Ownership Transpose 30e76cee25.svg]]

Figure 18: **Ulysses Ownership Transpose**: A schematic with four ranks, four tokens, and four attention heads labels each token–head tile by its owning rank. The first AllToAll changes ownership from token rows to head columns. Each rank computes attention across the full sequence for its head, then the inverse AllToAll restores token ownership for subsequent layers. The head dimension is omitted. This example assumes ordinary multihead attention with compatible divisibility; it does not depict KV-head replication under grouped-query attention.

^fig-ulysses-ownership-transpose

The exchanged tiles change where attention executes rather than removing its interactions. Head count and KV-head layout constrain this partition even when the activation bytes fit in memory.

A hierarchical configuration can combine head-sequence transposes within a fast domain and ring exchanges between domains. For an eight-device intra-node domain, a Ulysses group satisfies (${c_{\text{intra}}}\le 8$), while a second degree (${c_{\text{inter}}}$) determines the ring’s inter-node partition. In this example, Ulysses partitions heads locally and Ring Attention circulates KV blocks across nodes. The arrangement is feasible only if head divisibility, peak memory, link service time, and the overlap condition all hold; hierarchy alone does not prevent fabric saturation.

### Expert Parallelism (Mixture of Experts)

^sec-distributed-training-systems-systems-expert-parallelism-mixture-experts-bc45

Tensor, pipeline, sequence, and context parallelism all partition dense layers that every token traverses, so scaling a dense model’s parameter count increases its per-token compute cost in lockstep. MoE architectures ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-shazeer2017outrageously|Shazeer et al. 2017]]) break that lockstep through conditional computation, and expert parallelism distributes the resulting capacity across devices. In an MoE layer, the feed-forward block contains ${N_{\text{experts}}}$ independent feed-forward networks (“experts”), and a gating network selects only a small subset, often top-1 or top-2, for each token. Adding more experts while holding each expert’s shape and the selected count fixed expands stored parameters without increasing expert FLOPs per token, trading dense matrix work for routing and all-to-all communication.

In a distributed setting, experts are partitioned across workers, with each rank hosting a disjoint subset of expert networks. One routing cycle across four ranks shows the sequence ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-moe-all-to-all-routing|figure 19]]). After top-${k_{\text{experts}}}$ gating selects destination experts, an AllToAll dispatch shuffles tokens across the fabric to the hosting ranks. Expert FFNs then compute locally, and a second AllToAll return routes the processed activations back to the originating ranks to form the gate-weighted sum. The backward pass repeats both exchanges in reverse order, sending output gradients to the ranks hosting the experts and returning input gradients to the ranks that own the tokens. The primary advantage is decoupling model size from per-token compute, which lets parameter count grow within feasible hardware budgets. The primary constraint is the AllToAll communication, which is bandwidth-intensive and sensitive to load imbalance.

![[90 Assets/Volume II/06 Distributed Training/Moe All To All Routing 9d9d59e5e5.svg]]

Figure 19: **Mixture-of-Experts (MoE) AllToAll Routing**: Expert parallelism on four ranks, one expert per rank, read left to right and drawn for top-1 routing with one token traced. Each rank’s gate picks the top-${k_{\text{experts}}}$ experts for its tokens; the first AllToAll dispatches every token to the rank that hosts its expert, the experts compute, and a second AllToAll returns the results so each rank can form the gate-weighted sum for its own tokens. In both exchanges every rank may send to every other rank, which is why the pattern stresses the fabric’s bisection bandwidth.

^fig-moe-all-to-all-routing

**Definition 6.11: Expert parallelism**

***Expert parallelism*** is the distribution strategy for mixture-of-experts models that places different experts on different devices and routes each token’s activations to the devices hosting its selected experts through AllToAll collectives, scaling total parameter count across the cluster without scaling the compute each token consumes.

1.  **Significance**: It decouples model capacity from compute budget. For illustration, a trillion-parameter MoE model may activate on the order of 10B parameters per token, so per-token FLOPs remain near those of a 10B dense model while capacity grows roughly 100$\times$. The price is communication structure: every MoE layer requires two AllToAll shuffles per pass (dispatch and combine) whose volume scales with tokens moved times hidden dimension, stressing the cluster’s bisection bandwidth rather than any single link.
2.  **Distinction**: Unlike tensor parallelism, which splits dense operations so that every device computes a fraction of every token, expert parallelism is conditional computation. Each device computes only the tokens routed to its experts, which makes both the communication pattern and the load distribution data-dependent rather than fixed by the architecture.
3.  **Common pitfall**: A frequent misconception is that experts share work evenly. A hot expert receiving, for example, 3–5$\times$ its uniform share can overflow its device’s activation buffer while sibling devices idle. Capacity limits and routing penalties are possible responses; a design that retains every assignment must instead accommodate the resulting memory and scheduling demand.

↩︎ The terms that set an AllToAll’s completion time, from traffic across the fabric bisection to hotspots created by skewed expert loads, are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.09 AllToAll Exchanges at Scale#^sec-communication-alltoall|AllToAll Exchanges at Scale]]**.

AllToAll dispatch routes token activations to their assigned experts. Consider ${N_{\text{experts}}}=$ 64 experts across 64 GPUs, processing a routing-group batch of ${B}=$ 4 sequences of length ${S}=$ 2048 and hidden dimension ${d}=$ 4096. Under top-1 routing, ${B}\times {S}$ tokens each contribute one activation vector. At FP16, the logical dispatch payload is ${B}\cdot {S}\cdot {d}\cdot 2$ bytes, approximately 67 MB; returning expert outputs doubles the forward payload to about 134 MB per block. Local destinations reduce bytes crossing the network, multiple selected experts increase routes, and backward adds gradient transfers. The resulting service time depends on placement and load balance, including in Switch Transformer ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-fedus2022switch|Fedus et al. 2022]]) (up to 2,048 experts) and GShard ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-lepikhin2021gshard|Lepikhin et al. 2021]]).

Uniform routing is a useful capacity baseline, not a guarantee. An expert receiving several times its uniform share, the hot expert of the definition above, needs correspondingly more token processing and activation storage. The actual skew depends on the learned router and batch. A hot expert can exhaust its buffer or delay the step while other experts remain underused, coupling memory feasibility to load balance.

One response bounds expert workload with a capacity factor ${C_{\text{cap}}}$. For top-1 routing, a capacity of roughly ${C_{\text{cap}}}\cdot ({B}\times {S})/{N_{\text{experts}}}$ token assignments per expert provides headroom above uniform load. A dropping implementation sends excess tokens past that expert through the residual connection; implementations that retain every assignment instead need memory and scheduling to accommodate the imbalance. An auxiliary load balancing loss can encourage less concentrated routing. Models using more than one expert per token, such as Mixtral 8x7B with top-2 routing ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-jiang2024mixtral|A. Q. Jiang et al. 2024]]), require a capacity budget that counts all selected assignments rather than reusing the top-1 denominator unchanged.

Sparse routing gives MoE layers the same coordination problem that the embedding tables of Archetype B (DLRM at Scale) pose. In both, which device a token’s data must reach depends on the data itself, so load balance cannot be fixed in advance. MoE language models nonetheless remain Archetype A (GPT-4/Llama-3) workloads, because their dense layers still carry the tensor, pipeline, and data-parallel traffic developed above.

### Sparse Embedding Sharding

^sec-distributed-training-systems-systems-parameter-servers-embedding-sharding-8821

Expert parallelism places parameters that only some tokens touch. Recommendation models push that sparsity much further. Their parameters are dominated by embedding tables (often 10 TB+) that no single GPU can hold, and their updates are sparse, because a batch of users interacts with only a tiny fraction of the items. Sharding those tables is model parallelism over stored state rather than over computation. The parameter server (PS) architecture, formalized by Li et al. ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-li2014|2014]]), remains a common way to do it. A parameter server architecture separates workers, which compute gradients, from servers, which store parameters and apply updates.

For dense models such as ResNet or BERT, that separation concentrates traffic, as [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-gradient-synchronization-614b|section 6.3.1.3]] noted. With ${N}$ workers, a server’s inbound links must absorb ${N}$ gradient streams at once. This incast problem is why dense training moved to ring AllReduce, in which every worker sends and receives at its own link rate and the aggregate load spreads across all nodes.

Sparse embedding tables reverse that balance. In a sparse parameter-server design, the tables are sharded across servers, and workers request only rows indexed by their local minibatches. A sparse pull returns those embedding vectors; a sparse push sends updates for the touched rows. This pattern avoids exchanging the complete table, but hot rows, lookup rates, and network contention can still limit throughput. Embedding-sharding frameworks such as TorchRec also support accelerator-based layouts, so sparse partitioning should not be equated with a CPU-only server architecture. Recommendation training at this scale is the volume’s Archetype B (DLRM at Scale) regime, and it differs from the dense running example in which resource runs out first.

Whether the shards live on servers or in accelerator memory, each table must be split along some axis. Row-wise sharding partitions embedding tables by row, placing the whole embedding vector of the entity with identifier id on the shard that [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^eq-distributed-training-embedding-row-shard|equation 3]] selects:

$$
{s} = \text{hash}(\text{id}) \bmod {N_{\text{shards}}} \tag{3}
$$

^eq-distributed-training-embedding-row-shard

Each shard ${s}$ contains approximately ${N_{\text{entities}}}/{N_{\text{shards}}}$ embeddings, where ${N_{\text{entities}}}$ is the total number of entities and ${N_{\text{shards}}}$ is the shard count. Column-wise sharding instead partitions each embedding vector ${\mathbf{e}}$ across devices, as [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^eq-distributed-training-embedding-column-shard|equation 4]] writes it:

$$
{\mathbf{e}} = [{\mathbf{e}}^{(0)}, {\mathbf{e}}^{(1)}, \ldots, {\mathbf{e}}^{({N_{\text{shards}}}-1)}] \tag{4}
$$

^eq-distributed-training-embedding-column-shard

Each device stores a slice of every embedding. Hybrid sharding combines both approaches, and the choice among the three depends on lookup patterns and communication overhead ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^tbl-embedding-sharding|table 6]]).

| **Sharding strategy** |    **Lookup pattern**    | **Communication** |      **Best for**       |
|:----------------------|:------------------------:|:-----------------:|:-----------------------:|
| **Row-wise**          | Single device per lookup |  AllToAll gather  | Uniform access patterns |
| **Column-wise**       |  All devices per lookup  |     AllGather     |     Hot embeddings      |
| **Hybrid**            |   Varies by embedding    |       Mixed       |    Production RecSys    |

Table 6: **Embedding Sharding Strategies**: Comparison of row-wise, column-wise, and hybrid embedding placement strategies, balancing lookup locality against network communication collectives and memory load balancing.

^tbl-embedding-sharding

The trade-off is locality against load balance. Row-wise sharding keeps each embedding vector whole on one device, while column-wise sharding spreads its dimensions across devices. Both require returning the pieces each consuming computation needs, but placement alone does not prescribe a collective; the runtime can use remote procedure calls to the shards or collectives according to where inputs and outputs reside. A row-wise layout commonly realizes its lookups as an AllToAll of whole vectors, and a column-wise layout as an AllGather of slices of each vector ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^fig-embedding-sharding|figure 20]]). Hybrid placement can replicate or column-partition hot embeddings while row-sharding the cold tail, trading additional storage and communication against concentrated lookup load.

![[90 Assets/Volume II/06 Distributed Training/Embedding Sharding c71b9a7477.svg]]

Figure 20: **Embedding Sharding Strategies**: Row-wise sharding places complete embedding vectors on specific servers based on entity ID, requiring a network gather for lookup. Column-wise sharding splits each vector across all servers, allowing parallel local lookups followed by an AllGather, which is efficient for popular “hot” embeddings. Hybrid sharding combines these approaches, using replication or column sharding for hot items and row sharding for the “cold” long tail to balance load and memory.

^fig-embedding-sharding

On accelerators, a row-wise layout turns each training step’s lookups into an AllToAll exchange. Every worker sends the indices its minibatch touches to the shards that own them and receives the embedding vectors back, and the backward pass returns gradients for the touched rows along the same routes. The exchange obeys the AllToAll bound of **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.09 AllToAll Exchanges at Scale#^sec-communication-alltoall|AllToAll Exchanges at Scale]]**, and like MoE dispatch its volume and balance depend on which rows the data touches, so hot rows overload their owners unless the layout replicates or splits them.

**Lighthouse 6.1: Archetype B (DLRM at Scale): DLRM vs. LLM scaling**

Each workload scales through a distinct mechanism and is limited by a different resource. Dense LLMs scale through data, tensor, and pipeline parallelism, constrained by compute throughput and by the bandwidth that dense gradient and activation collectives need over fabrics such as NVLink and InfiniBand. Sparse recommendation models such as DLRM scale by sharding embedding tables of 10 TB or more across parameter servers or accelerator memory, where aggregate memory capacity, lookup rate, and the latency of many small random accesses dominate. The distinction shapes cluster design, favoring accelerator pods built around high-bandwidth dense fabrics for LLMs and memory-capacity-rich layouts for recommendation systems. This holds whether the embedding shards live in CPU-hosted servers, in accelerator HBM, or in a tiered hybrid that keeps hot rows on accelerators and cold rows in host memory.
