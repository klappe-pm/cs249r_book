# V2-06.08 Multi-Model Training for Alignment and RLHF

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training|V2-06 Distributed Training]]

^sec-distributed-training-rlhf

A cluster partitioned to train a single model cannot run post-training alignment in place, because reinforcement learning from human feedback (RLHF) coordinates up to four distinct models inside a single training step. In proximal policy optimization (PPO), an active policy generates responses token by token, a preference-trained reward model scores them, a frozen reference copy constrains policy drift, and a learned value model estimates expected returns to guide the gradient update. Those roles carry sharply different memory footprints and alternate between memory-bandwidth-bound autoregressive generation and compute-bound backward passes. Direct preference optimization (DPO) sidesteps online generation and drops the separate reward and value models, trading live exploration for a simpler two-model loop. Designing an alignment cluster therefore starts by tallying which models, states, and execution phases must coexist on the fleet.

### The Multi-Model Coordination Problem

^sec-distributed-training-rlhf-coordination

Holding four models in accelerator memory at once multiplies the static state budget before a single prompt is even decoded, and only two of those models ever run a backward pass. In PPO ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-schulman2017proximal|Schulman et al. 2017]]), as used in InstructGPT-style systems ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-ouyang2022instructgpt|Ouyang et al. 2022]]), the four roles differ sharply in execution mode and memory burden ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.08 Multi-Model Training for Alignment and RLHF#^tbl-rlhf-model-coordination-roles|table 7]]). In [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.08 Multi-Model Training for Alignment and RLHF#^fig-rlhf-ppo-step|figure 21]], the policy ${\pi_\theta}$ generates responses for scoring by the frozen reference and reward models and evaluation by the value model ${M_{\text{value}}}$. The penalized reward (${r}- {\beta_{\text{KL}}}\,\text{KL}$) subtracts a Kullback–Leibler divergence penalty, weighted by a coefficient ${\beta_{\text{KL}}}$ unrelated to link bandwidth ${\beta}$, to discourage drift from the reference. Generalized advantage estimation (GAE) combines rewards and value estimates to judge how much better a response was than expected. Those estimates guide policy updates; the value model learns to predict returns, the cumulative discounted reward that follows each generated token. Reference and reward models remain forward-only in this loop, and shared-backbone implementations can combine roles without changing their distinct responsibilities.

That asymmetry drives placement.

The aggregate memory demand of the four-model PPO system dwarfs standard pretraining. A naive co-location of a 70B policy, 70B reference, 13B reward, and 13B value model requires approximately 1,494 GB of accelerator memory, before accounting for the KV caches and intermediate activations generated during sequence generation. A key-value (KV) cache stores attention keys and values for previously processed tokens so the policy can generate the next token without recomputing that state. It grows with the number and length of active sequences, creating a temporary memory budget distinct from weights and optimizer state. On H100 GPUs with 80 GB of HBM each, this system requires a minimum of 19 GPUs as an aggregate static-state capacity lower bound, including optimizer state and gradients. This division does not establish a feasible placement, because each phase must also fit its KV or activation peak, workspaces, and uneven shards. Replicated policy groups increase the total state further.

### Infrastructure Asymmetry Between Training and Inference Models

^sec-distributed-training-rlhf-asymmetry

The defining infrastructure challenge of RLHF is not the *total memory footprint* but the *asymmetry* between the models’ compute profiles. The policy and value models require full backward passes with gradient computation, activation checkpointing, and optimizer updates, compute-intensive operations that benefit from tensor parallelism and high arithmetic intensity. The reference and reward models, by contrast, perform only forward passes over generated sequences. Their scoring passes do not require optimizer state, and they need not decode token by token. The policy’s rollout phase creates the autoregressive generation workload and its KV-cache budget. Separating scoring from generation matters because forward-only execution does not imply a single memory or compute profile.

The asymmetry creates a placement dilemma. Co-location permits devices to serve different phases, but inactive model state can occupy memory needed for the active phase. Dedicated pools allow each role to use a suitable execution configuration, but pools may idle while waiting for another role’s output. Separation also adds transfers of generated sequences, scores, and updated policy weights. The design must compare phase utilization and data movement rather than assume that either placement eliminates waste.

The PPO rollout phase introduces autoregressive dependencies absent from the teacher-forced pretraining baseline, in which each input token comes from the training data rather than from the model’s previous output. The policy generates responses before sequence-level rewards guide its updates. At small active batches, decoding is often memory bandwidth bound because each new token requires another model pass. Each token in the KV cache holds a key vector and a value vector per KV head in every layer. For a Llama-2-70B-style grouped-query attention policy generating 1,024 tokens for each of 256 active sequences, those per-token bytes, written out in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^eq-kv-bytes-per-token|equation 10.5]]**, put the generated-token portion at 85.9 GB. That portion alone already exceeds the 80 GB of HBM on one H100, and prompt tokens add KV state as well. This temporary cache must fit alongside the state live during rollout; its lifetime differs from training activations and optimizer state.

↪ The capacity wall this cache imposes on serving systems is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-kv-cache-wall|The KV cache wall and memory capacity]]**.

RLHF systems address this asymmetry through temporal multiplexing. During the generation phase, the cluster behaves like an inference system: the policy model generates sequences while the reference model computes log-probabilities, and batching active sequences alongside their KV state determines how much useful work shares each weight read. During the training phase, the same fleet switches back to training mode and computes gradients through the policy and value models using the 3D parallelism configuration of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.07 Hybrid Parallelism#^sec-distributed-training-systems-systems-hybrid-parallelism-12a0|section 6.6]], where activation residency and gradient synchronization again govern the schedule. Because PPO alternates between inference-shaped rollout work across four model roles and training-shaped updates, reformulating the alignment objective itself can eliminate part of that infrastructure overhead.

### Resource Requirements for PPO Versus DPO

^sec-distributed-training-rlhf-quantitative

Standard offline DPO ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-rafailov2023dpo|Rafailov et al. 2023]]) takes that route by removing the separate reward and value models, along with the online rollout phase, from the update loop, reformulating alignment as a supervised loss over offline preference pairs. The policy learns directly from preferred and dispreferred responses using their log-probabilities relative to a frozen reference; because those responses are already in the training data, the update requires neither autoregressive generation nor advantage estimation.

A DPO implementation that retains a resident reference has two model roles, the trainable policy and the frozen reference. For fixed preference pairs and a fixed reference, reference log-probabilities can instead be precomputed, removing that model from the repeated update loop. Offline DPO needs no autoregressive rollout during those updates. Variable lengths still require padding, packing, or length-aware batching, and policy training can use the same partitioning, accumulation, and overlap mechanisms as pretraining.

The infrastructure difference follows from how each method obtains feedback. Offline DPO learns from a fixed preference dataset, so the policy never receives feedback on new responses. PPO-style training scores responses from the evolving policy and can expose behavior the dataset lacks, provided the reward signal is reliable. The generation phase, the reward and value models, and the memory they occupy are the price of that online loop, so the choice is settled by achieved quality per unit of total resource cost.

To make the infrastructure trade-off concrete, consider aligning a 70B policy model using a policy/reference pool of 256 H100 GPUs (80 GB HBM each). PPO’s separate reward and value pools sit outside that allocation. The policy is a 70B-class model rather than the 175B reference, a size at which each role’s memory budget stays readable while the four PPO roles together still need at least 19 GPUs, more than one node.

**Napkin Math 6.9: RLHF infrastructure budget: PPO vs. DPO**

**Problem**: This alignment setup co-locates a 70B policy model with a 70B reference model and, for PPO, uses pools outside the 256-GPU policy/reference allocation for a 13B reward model and a 13B value model. Under 3D parallelism (TP=8 GPUs, PP=4, DP=8), how much memory resides on each policy GPU, and which separate model pools and generation-phase memory requirements does DPO remove?

**PPO memory budget** (per-GPU, with TP=8 GPUs, PP=4, DP=8 for policy)

The policy model under 3D parallelism with TP=8 GPUs and PP=4 distributes one replica’s 1,120 GB training state across 32 GPUs, yielding 35 GB per GPU. The reference model, requiring only 140 GB for inference, is co-located with the policy GPUs at an additional 4.4 GB per GPU (140 GB / 32 GPUs). It could instead be sharded across an additional 8 GPUs pool outside the policy allocation at 17.5 GB each. The 13B reward model adds 26 GB shared across its pool. The 13B value model in training mode adds approximately 208 GB (13B $\times$ 16 bytes/param) across its pool.

Total static memory (one co-located policy + reference replica on 32 GPUs): 35 GB + 4.4 GB $\approx$ 39.4 GB per GPU, leaving $\sim$ 40.6 GB for activations and KV cache. With generation-phase KV caches for a rollout batch containing 256 sequences and 1,024 tokens inside one ${T} {P}{\times}{P} {P}$ policy replica, each policy GPU must reserve an additional 85.9 GB/32 GPUs $\approx$ 2.7 GB for its KV cache shard. The remaining $\sim$ 37.9 GB is generation-phase headroom. Once rollout KV state is released, the update phase recovers the 40.6 GB headroom before allocating training activations and other runtime buffers. The phase peaks must be evaluated separately.

**DPO memory budget (same parallelism configuration)**

The policy model uses the same 35 GB per GPU. The reference model adds 4.4 GB per GPU (co-located). No reward model, no value model, no KV cache for generation.

On the policy GPUs, total static memory is 35 GB + 4.4 GB = 39.4 GB per GPU, identical to PPO’s co-located policy/reference footprint. Both have 40.6 GB available before update-phase activations and runtime buffers when PPO releases its rollout KV cache. DPO removes the separate generation peak and the reward/value model pools; the absence of rollout KV state alone does not establish larger update microbatches.

**Throughput comparison**

PPO alternates generation and parameter updates. If generation consumes 60 percent of an iteration in this illustrative schedule, updates occupy the remaining 40 percent. That time fraction is a share of the schedule rather than an MFU, so update-phase MFU must be multiplied by it to report update computation over the whole iteration, using the same allocated hardware denominator. DPO eliminates online generation, but its measured throughput still depends on sequence lengths, reference scoring, parallelism, and memory use. The static-state comparison in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.08 Multi-Model Training for Alignment and RLHF#^tbl-ppo-vs-dpo|table 8]] is therefore kept separate from these schedule-dependent effects.

**Systems insight**: In this 13B reward/value-model scenario, DPO reduces the one-copy static-state budget by 15.7 percent by eliminating the reward and value models. It also removes online generation, but the throughput benefit requires a measured schedule. Infrastructure constraints therefore weigh on the choice between PPO and DPO as much as modeling preferences do. An organization with a limited GPU budget may prefer DPO because it restores the workload to a fixed-data training loop. If the PPO value model is policy-sized rather than 13B, the reduction is larger still, from 2,406 GB to 1,260 GB.

### Sequence Length Variance and Batching Challenges

^sec-distributed-training-rlhf-batching

The throughput comparison in notebook [6.9](https://mlsysbook.ai/vol2/06_distributed_training/06_distributed_training.html#nbk-distributed-training-rlhf-infrastructure-budget-ppo-vs-dpo) noted that even after DPO removes online generation, realized step time still depends on sequence-length variance. Pretraining often packs documents into fixed-length blocks, such as 2,048 or 4,096 tokens, whereas alignment batches combine prompts and responses whose lengths can span a 10–50$\times$ range within a single minibatch. Those variable lengths directly govern activation residency, padding waste, and load balance across workers.

Length variance creates two interacting problems. Padding every sequence to the longest in a batch can leave most token positions unused. A batch of one 2,048-token sequence and fifteen 128-token sequences, padded to 2,048 tokens, fills only 3,968 of its 32,768 positions. Kernels that execute padded positions therefore spend about 88 percent of their work on padding, while kernels that skip them recover most of that waste. Dynamic batching groups similar lengths to reduce padding, but assignments across workers still need balancing. A worker processing longer sequences can have a larger activation peak and finish later, leaving other workers waiting for the required gradient contributions.

Sequence packing combines short sequences within a fixed-length input, with attention masking that keeps their contexts separate, and adaptive microbatching sizes each microbatch by token count or predicted memory. Packing must also respect the weighting rule of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-dataset-splitting-1edf|section 6.3.1.1]]. The reduction must keep the objective’s own denominator, valid-token counts for a token-mean PPO loss and pair counts for standard DPO ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-rafailov2023dpo|Rafailov et al. 2023]]), so packing changes layout but not weighting. Balancing token work across workers then remains a performance goal rather than a correctness requirement.

RLHF shows why no single parallelism strategy is sufficient by itself. The policy model may need tensor and pipeline parallelism, the reference and reward models behave like inference services, the value model may require training state, and the rollout data pipeline changes shape from step to step. The procedure that handles this case is the general one, which identifies the limiting constraint first and then chooses the parallelism pattern that moves the least data while fitting the required state.
