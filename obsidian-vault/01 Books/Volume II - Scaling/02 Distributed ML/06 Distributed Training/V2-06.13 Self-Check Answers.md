1.  **A research team is training a 3B-parameter transformer that fits comfortably in one H100 GPU’s 80 GB of memory, but projected single-GPU training would take 18 months to reach target loss. The dataset is 3 TB and fits on local NVMe storage. Which signal makes distributed training necessary in this scenario?**

    1.  Dataset exceeding GPU HBM capacity, which automatically mandates tensor parallelism regardless of execution time
    2.  The presence of NVLink inside the node, which makes multi-machine scaling mandatory by default
    3.  Unacceptable wall-clock training duration, even though single-device memory capacity and local storage are sufficient
    4.  Fault tolerance limitations, because single-GPU training cannot survive hardware restarts

    *Answer*: The correct answer is C. The deadline is the binding constraint even though the complete model fits and local storage is sufficient. Memory exhaustion can motivate sharding, offload, or other capacity remedies; dataset capacity and delivery rate can motivate distributed data services without forcing model computation across devices. NVLink enables exchanges when needed but does not mandate distribution. Single-device jobs can checkpoint and recover from interruption.

    *Learning Objective*: Analyze which physical trigger necessitates distributed training when model memory and dataset storage are not binding constraints

2.  **A team doubles a data-parallel cluster from 64 to 128 GPUs and observes that total step time drops by only 12 percent even though per-worker compute time halves. Using the distributed step-time equation $T_{\text{step}}(N) = T_{\text{compute}}/N + T_{\text{comm}}(N) + T_{\text{sync}}(N) - T_{\text{overlap}}$, explain what the observation establishes and what measurement would distinguish possible causes.**

    *Answer*: The observation establishes that halving per-worker compute did not halve the complete step. Exposed communication, synchronization, reduced overlap, or another critical-path delay can explain the residual; the step-time ratio alone does not identify which one binds. Compare aligned rank timelines for gradient readiness, collective transfer, barrier waiting, input delivery, and kernel execution. Collective waiting may reflect a late participant rather than limited fabric capacity, so link utilization during the critical interval is needed to support a network diagnosis.

    *Learning Objective*: Analyze how the communication-computation ratio limits scaling when per-worker compute shrinks faster than communication cost

3.  **True or False: A cluster of 1,024 GPUs, each with a 50,000-hour mean time to failure, should expect a GPU failure roughly every two days if failures are independent, even though any single GPU fails only about once every five to six years.**

    *Answer*: True. Independent constant-rate failures add, so the cluster failure rate is about 1,024/50,000 per hour and the cluster mean time between failures is about 49 hours. Whether each failure interrupts training depends on recovery and redundancy, which is why distribution makes fault tolerance a first-order budget rather than an afterthought.

    *Learning Objective*: Estimate how cluster size converts a rare per-device failure into a frequent cluster-level event

4.  **The dimensionless ratio $\rho = T_{\text{comm}}(N) / (T_{\text{compute}}/N)$, which screens communication demand relative to per-worker compute time, is defined as the \_\_\_\_.**

    *Answer*: Communication-Computation Ratio. The ratio compares communication time with per-worker compute time. A large ratio warns that communication may limit scaling, but actual step time depends on overlap, readiness, and other exposed work. A small ratio alone does not guarantee near-linear scaling.

    *Learning Objective*: Define the metric governing the transition between compute-bound and communication-bound cluster operation

1.  **Framing distributed parallelism strategies as compiler loop transformations across the training loop’s iterators (batches, layers, and operations), which distributed strategy corresponds to vectorization (SIMD) of inner matrix multiplications?**

    1.  Tensor parallelism, which partitions inner matrix-multiplication operations across devices and exchanges partial results over the interconnect
    2.  Data parallelism, which unrolls the outer batch loop across devices so each rank processes independent data indices
    3.  Pipeline parallelism, which stages sequential layer operations across devices analogous to CPU instruction pipelining
    4.  Model replication, which duplicates the entire forward and backward execution redundantly across machines

    *Answer*: The correct answer is A. Tensor parallelism partitions inner matrix operations, analogous to vectorizing the inner loop. The analogy describes the computational cut; NVLink still exchanges messages between devices with separate memory and does not provide a shared vector register file. Unrolling the outer batch loop describes data parallelism, while staging layer groups describes pipeline parallelism. Replication does not partition an operation.

    *Learning Objective*: Classify distributed parallelism strategies according to compiler loop transformations

2.  **In the 3D parallelism cube, where the device count equals the product of the data-, pipeline-, and tensor-parallel degrees, how do the three scaling axes interact to allocate cluster accelerators for large models?**

    1.  The three axes are mutually exclusive; choosing data parallelism precludes using tensor or pipeline parallelism in the same cluster
    2.  Tensor and pipeline parallelism can combine within a node, but data parallelism can only be used if model parallelism is disabled
    3.  The total accelerator count is the sum of the three degrees, with each parallelism type requiring a disjoint node pool
    4.  The axes compose multiplicatively, so one layout can split layers (TP), stage the layer stack (PP), and replicate the pipeline across data shards (DP), and its device count is the product of the three degrees

    *Answer*: The correct answer is D. Data, pipeline, and tensor parallelism partition different workload dimensions, and the product of their degrees gives the accelerator count. The degrees are not independent knobs: tensor and pipeline degrees must divide the model, the data-parallel degree and microbatch schedule must give a viable global batch, every partition must fit memory, and each axis’s traffic must map onto a tier that can carry it. Large-model configurations routinely compose all three, for example TP=8 inside an NVLink node, PP=16 across nodes, and DP=128 across the cluster. Mutual exclusivity, a ban on combining data and model parallelism, and an additive count all contradict that multiplicative composition.

    *Learning Objective*: Calculate total cluster resource allocation using the multiplicative axes of the 3D parallelism cube

3.  **True or False: If a neural network’s parameters exceed a single GPU’s memory capacity, tensor parallelism can be scaled across standard commodity Ethernet switches between server racks, provided the global batch size is made large enough.**

    *Answer*: False. Increasing global batch size does not guarantee that frequent tensor-parallel exchanges fit within the compute window. Slow inter-rack links can dominate every layer. Tensor parallelism should use the fastest available domain; pipeline or data parallelism usually better matches slower links, subject to measured workload and topology constraints.

    *Learning Objective*: Evaluate the physical feasibility of tensor parallelism across commodity network fabrics

4.  **For one GPT-3 layer split eight ways, the chapter’s bandwidth feasibility check finds about 1.9 ms of local compute, about 0.4 ms of tensor-parallel transfer over NVLink, and about 3.5 ms for the same transfer over one NDR InfiniBand port. Explain what these numbers imply for where the tensor-parallel group should be placed and what a planner must still check before accepting that placement.**

    *Answer*: Over NVLink the per-layer exchange is a fraction of the layer’s compute, so it can fit inside the layer-time budget; over one InfiniBand port it takes longer than the compute it serves, so every layer would wait on the network. The tensor-parallel group therefore belongs in the fast communication domain. The planner must still check how much of the transfer the schedule can actually hide, the message startup latency, and whether the pipeline and data-parallel traffic placed on the slower tiers fits their own budgets.

    *Learning Objective*: Apply a per-layer bandwidth feasibility test to place tensor parallelism on a fabric tier

1.  **A 7B-parameter transformer in mixed precision requires 112 GB of static memory for standard replicated DDP (14 GB for FP16 weights, 14 GB for FP16 gradients, and 84 GB for FP32 Adam master weights, momentum, and variance). Under ZeRO Stage 3 (or FSDP Full Shard) across 64 GPUs, what is the resulting static training memory per GPU?**

    1.  $112\text{ GB}$, because ZeRO-3 only reduces dynamic activation memory rather than model state
    2.  $28\text{ GB}$, because only optimizer states are sharded while parameters and gradients remain fully replicated
    3.  $1.75\text{ GB}$, because weights, gradients, and optimizer states are each partitioned equally across all 64 workers
    4.  $0.25\text{ GB}$, because INT4 quantization eliminates floating-point representation entirely

    *Answer*: The correct answer is C. ZeRO-3 / FSDP partitions all three components of static training state, namely FP16 model weights (2 bytes/param), FP16 gradients (2 bytes/param), and FP32 Adam states (12 bytes/param), across the $N=64$ ranks ($16\text{ bytes/param} / 64 = 0.25\text{ bytes/param}$ per device). For a 7B model ($7 \times 10^9 \times 0.25\text{ bytes} = 1.75\text{ GB}$ per GPU), this leaves substantial HBM headroom for dynamic activations. Asserting that state remains 112 GB ignores parameter and optimizer sharding. ZeRO-1 retains 28 GB of weights and gradients plus its optimizer shard, so its total is greater than 28 GB. Claiming INT4 compression confuses precision quantization with state sharding.

    *Learning Objective*: Calculate per-GPU static memory reduction under ZeRO-3 parameter, gradient, and optimizer state sharding

2.  **An 8-GPU node can use four-step gradient accumulation to match the effective batch of 32 GPUs connected by 10 Gb/s Ethernet. Explain why the smaller allocation can cost less even when the larger allocation completes the fixed-sample workload sooner.**

    *Answer*: Four accumulation microsteps synchronize once per optimizer update, keeping collective traffic inside the fast local interconnect while matching the effective global batch. The 32-GPU allocation adds arithmetic capacity but pays inter-node communication overhead and rents four nodes. Compare node-hours at the same sample budget and target quality: lower hourly capacity cost can outweigh longer elapsed time, so better cost efficiency does not imply higher throughput.

    *Learning Objective*: Compare gradient accumulation on high-speed intra-node fabrics against naive scale-out across bandwidth-constrained networks

3.  \*\*Order the memory sharding stages of data parallelism from least sharded (highest memory footprint) to deepest sharded (lowest memory footprint):

<!-- -->

1.  ZeRO-2 (shards optimizer states and gradients using ReduceScatter)
2.  Standard DDP (full replication of parameters, gradients, and optimizer states)
3.  ZeRO-3 / FSDP (shards optimizer states, gradients, and model parameters with layer-wise AllGather/ReduceScatter)
4.  ZeRO-1 (shards optimizer states only, keeping parameters and gradients replicated)\*\*

*Answer*: (2) -\> (4) -\> (1) -\> (3). First, (2) Standard DDP replicates all 16 bytes/param on every GPU. Next, (4) ZeRO-1 shards optimizer states (~4$\times$ static reduction). Then, (1) ZeRO-2 additionally shards gradients (~8$\times$ static reduction). Finally, (3) ZeRO-3 / FSDP shards the parameters themselves, achieving linear $1/N$ memory reduction.

*Learning Objective*: Classify the memory sharding stages of ZeRO and FSDP by depth of partitioned state

4.  **If a model’s parameters, gradients, optimizer state, activations, and working buffers already fit comfortably within single-GPU memory with high compute utilization under standard DDP, what is the expected throughput impact of enabling ZeRO-3 / FSDP Full Sharding?**

    1.  Throughput will increase linearly by $N\times$ because sharding reduces per-GPU gradient memory
    2.  Throughput can decrease because FSDP introduces additional AllGather collectives before forward and backward passes and ReduceScatter on the critical path
    3.  Throughput will remain exactly identical because NCCL automatically hides all collective communication overhead
    4.  Throughput will double because parameter sharding eliminates the backward pass entirely

    *Answer*: The correct answer is B. With full resharding, FSDP adds parameter AllGathers before forward and backward computation and uses ReduceScatter for gradients. When memory savings do not enable a better execution configuration, exposed extra communication can reduce throughput. The penalty depends on overlap and topology; neither linear speedup nor perfect hiding follows from sharding alone.

    *Learning Objective*: Evaluate the communication throughput overhead of FSDP when device memory is not the binding constraint

5.  **Why did modern distributed training frameworks replace centralized parameter servers with decentralized AllReduce collective topologies for dense synchronous training?**

    1.  Parameter servers cannot execute stochastic gradient descent updates with mathematical validity
    2.  Parameter servers are restricted to CPU hosts and cannot interface with GPU accelerators
    3.  AllReduce eliminates all network traffic by updating weights locally without exchanging data
    4.  Centralized parameter servers create an $\mathcal{O}(N)$ network bottleneck at the server’s network interface, whereas AllReduce distributes communication symmetrically across all workers

    *Answer*: The correct answer is D. A centralized server must service the dense gradient and parameter streams of all workers, concentrating traffic at its interfaces. AllReduce distributes that exchange among participants. For an ideal ring, each worker transfers $2(N-1)/N \times M_{\text{grad}}$ bytes; tree schedules have their own transfer and startup accounting. Whether either design meets the step budget depends on sustained bandwidth, topology, readiness, and overlap. Parameter servers can implement valid SGD on CPU or GPU hosts, and AllReduce still requires communication.

    *Learning Objective*: Compare centralized and decentralized synchronization topologies in terms of bandwidth bottlenecks for dense gradient traffic

6.  **In standard PyTorch DistributedDataParallel, each worker uses a \_\_\_\_ to partition dataset indices deterministically and assign rank-specific shards based on process rank and epoch seed.**

    *Answer*: DistributedSampler. It assigns rank-specific dataset indices using the rank and epoch seed. When the dataset size is not divisible by the worker count, padding can repeat samples unless the remainder is dropped; the sampler and loss accounting must handle that boundary explicitly.

    *Learning Objective*: Identify deterministic rank-specific dataset partitioning and account for repeated or dropped remainder samples

1.  **A team scales a data-parallel training run from 8 to 64 workers, increasing the effective global batch size from 512 to 4,096 samples. If the model operates comfortably below its critical batch size, which learning-rate adjustment follows the linear scaling heuristic?**

    1.  Keep the learning rate unchanged, because large-batch variance reduction automatically stabilizes optimization
    2.  Multiply the learning rate by 64 to match the total worker count rather than the batch expansion ratio
    3.  Multiply the learning rate by $\sqrt{8}$ from step zero without a warmup schedule
    4.  Multiply the learning rate by $8\times$ (matching the batch expansion ratio) and include a gradual linear warmup schedule

    *Answer*: The correct answer is D. The batch expansion is $4096/512=8$, so the linear scaling heuristic multiplies the learning rate by eight, with warmup to limit early instability. It is a starting configuration to validate, not a universal optimizer rule. Scaling by the total worker count uses the wrong ratio; square-root scaling is a different heuristic.

    *Learning Objective*: Apply linear learning rate scaling with warmup for large-batch data-parallel training

2.  **Explain the distinction between hardware efficiency and statistical efficiency in distributed training, and describe a concrete scenario where a cluster configuration achieves high hardware efficiency but poor statistical efficiency.**

    *Answer*: Hardware efficiency measures how effectively compute capacity produces step throughput after exposed execution overhead. Statistical efficiency measures how effectively processed samples advance learning toward the target quality. A global batch far beyond the critical-batch crossover can keep MFU high while added examples yield diminishing reductions in update count. This can increase the examples and allocated GPU-hours needed to reach the target. Whether wall-clock time also increases depends on achieved throughput and the measured steps to the same target; high throughput alone does not establish either a faster or slower complete run.

    *Learning Objective*: Compare hardware throughput efficiency with statistical sample efficiency in distributed optimization

3.  **Why must the learning-rate schedule be revalidated when moving from Bulk-Synchronous Parallel (BSP) to Stale-Synchronous Parallel (SSP) at the same global batch size?**

    1.  Gradients computed against stale parameters can alter update stability, with effects that depend on delay, objective, and optimizer schedule
    2.  SSP workers compute exact full-batch gradients instead of stochastic minibatches
    3.  SSP eliminates all inter-GPU network communication, which alters the loss landscape
    4.  SSP is mathematically restricted to second-order quasi-Newton optimizers that require small step sizes

    *Answer*: The correct answer is A. SSP permits gradients from parameter snapshots that lag behind the current state. Their effect on stability depends on the delay bound, objective, and optimizer schedule; there is no universal staleness penalty or mandatory learning-rate reduction. A smaller learning rate is one candidate to validate by comparing complete runs to the same target quality. SSP still communicates, uses stochastic minibatches, and is not restricted to second-order optimizers.

    *Learning Objective*: Explain the impact of bounded gradient staleness on optimizer stability and learning rate selection

4.  **The threshold batch size $B^* \approx \frac{\text{tr}(\Sigma)}{\|\nabla \mathcal{L}(\theta)\|^2}$, representing the point where gradient variance equals true gradient magnitude and past which larger batches yield diminishing returns in sample efficiency, is known as the \_\_\_\_.**

    *Answer*: critical batch size. The gradient-noise-scale proxy estimates the crossover where larger batches give diminishing reductions in optimization steps per added sample. Below that crossover, steps can fall approximately inversely with batch size; the relationship depends on optimizer, training phase, and target quality.

    *Learning Objective*: Define critical batch size in terms of gradient covariance trace and gradient norm

5.  **Why does the FP8 recipe described in this chapter pair the E4M3 format for forward-pass activations and weights with the E5M2 format for backward-pass gradients?**

    1.  E4M3 has a wider numerical range than E5M2, which prevents gradient underflow during backpropagation
    2.  E4M3 spends more bits on the mantissa, giving finer precision for bounded weights and activations, while E5M2 spends more bits on the exponent, giving the wider dynamic range that small and widely varying gradients need
    3.  E4M3 is an integer format while E5M2 is a floating-point format supported exclusively on CPU hosts
    4.  E5M2 requires half the memory bandwidth of E4M3, accelerating the backward pass AllReduce

    *Answer*: The correct answer is B. E4M3 provides finer precision, while E5M2 provides a wider representable range. The cited recipe uses these properties for scaled weights/activations and gradients respectively. Tensor distributions and scaling determine suitability; neither format guarantees that all values avoid underflow or overflow. Both are one-byte floating-point formats, so choosing E5M2 rather than E4M3 does not halve wire traffic.

    *Learning Objective*: Compare E4M3 and E5M2 FP8 formats based on numerical range, precision, and training tensor roles

6.  **Explain why per-tensor dynamic scaling is necessary in FP8 distributed training and describe how the scaling factor is computed during execution.**

    *Answer*: FP8 scaling maps each tensor into the limited representable range. A simple current-maximum rule uses $S=\mathrm{FP8}_{\max}/\max(|X|)$ before casting, with an appropriate zero-tensor guard. For a product of independently scaled operands, the output must be divided by the product of their scales. Practical policies may use history or smaller scaling blocks; the objective is to balance rounding, underflow, and overflow.

    *Learning Objective*: Explain how scaling balances rounding, underflow, and overflow in FP8 tensors

1.  **In Megatron-LM style tensor parallelism for a transformer layer, how are the linear projections in the multi-head attention block arranged to minimize cross-device collective communication?**

    1.  Both QKV and Output projections are column-parallel, requiring an AllGather after each projection
    2.  Both QKV and Output projections are row-parallel, requiring an AllReduce before each projection
    3.  The QKV projection is column-parallel and the Output projection is row-parallel, requiring only a single AllReduce at the end of the attention block
    4.  The QKV projection is partitioned across pipeline stages while the Output projection is replicated across data-parallel ranks

    *Answer*: The correct answer is C. In Megatron-LM, the first linear layer (QKV projection) is column-parallel ($W = [W_1 | W_2]$), producing partitioned intermediate activations without communication. The second linear layer (Output projection) is row-parallel ($W = [W_1 ; W_2]$), taking those partitioned activations directly as inputs and generating partial sums. Only a single AllReduce at the end of the row-parallel projection is required to sum the partial outputs. Using column-parallel for both layers would require an intermediate AllGather. Using row-parallel for both layers would require an AllReduce before the second layer. Splitting QKV and Output across pipeline stages confuses intra-layer tensor parallelism with inter-layer pipelining.

    *Learning Objective*: Analyze the column-then-row linear layer pairing in Megatron-LM tensor parallelism

2.  **In a synchronous 1F1B pipeline-parallel training schedule with $p=8$ stages and $m=32$ microbatches, calculate the theoretical pipeline bubble fraction and explain how increasing the microbatch count $m$ affects bubble overhead and activation memory.**

    *Answer*: The bubble fraction is $F_{\text{bubble}} = \frac{p-1}{m+p-1} = \frac{8-1}{32+8-1} = \frac{7}{39} \approx 17.9\%$. Increasing the microbatch count $m$ relative to stage count $p$ drives the bubble fraction down toward zero ($F_{\text{bubble}} \to 0$). Under 1F1B scheduling, with equal activation sizes per microbatch, peak activation memory per stage is bounded at $\mathcal{O}(p)$ rather than GPipe’s $\mathcal{O}(m)$, making larger microbatch counts practical.

    *Learning Objective*: Calculate pipeline bubble overhead and explain the role of microbatch count in pipeline utilization

3.  \*\*Order the four sequential phases of token routing and execution in Expert Parallelism (Mixture of Experts) across distributed workers:

<!-- -->

1.  AllToAll Combine: Processed token embeddings are routed back to their original source devices for residual connections
2.  Computation: Sharded expert feed-forward networks process their assigned token batches
3.  Gating: A router network evaluates tokens and selects top-k destination experts
4.  AllToAll Dispatch: Tokens are shuffled across the network fabric to the devices hosting their selected experts\*\*

*Answer*: (3) -\> (4) -\> (2) -\> (1). First, (3) Gating evaluates token representations to select destination experts. Next, (4) AllToAll Dispatch routes tokens across the interconnect to the GPUs hosting the chosen experts. Then, (2) Computation executes the local expert feed-forward layers on the received tokens. Finally, (1) AllToAll Combine routes the processed representations back to their originating devices.

4.  **In a capacity-limited Mixture of Experts (MoE) system using top-1 routing and token dropping, what occurs when a hot expert receives more tokens than its allocated buffer capacity determined by the Capacity Factor $C$?**

    1.  Excess tokens are dropped and pass through the MoE layer unprocessed via the residual connection
    2.  The expert GPU dynamically allocates host CPU memory over PCIe, halting computation on other ranks
    3.  The AllToAll collective automatically pauses until all sibling experts process matching token counts
    4.  The extra tokens are rerouted to a random cold expert regardless of gating network weights

    *Answer*: The correct answer is A. To prevent memory overflow and load-imbalance stalls on devices hosting popular experts, the stated top-1 dropping implementation enforces a capacity limit $C \cdot (B \times S)/E$. When an expert’s assigned token count exceeds this buffer, the excess tokens are dropped and bypass the feed-forward computation, flowing directly through the residual connection. Dynamically allocating host CPU memory would stall GPU execution. Collective communication does not pause dynamically for uneven token counts. Rerouting to random unselected experts would violate gating semantics.

    *Learning Objective*: Explain the function of the capacity factor and token dropping in distributed MoE routing

5.  **Contrast the communication patterns and hardware interconnect requirements of dense LLM training (Megatron-style Tensor Parallelism) with large-scale Recommendation Systems (DLRM embedding sharding).**

    *Answer*: Dense LLM tensor parallelism places frequent activation reductions on the layer critical path, favoring high-bandwidth, low-latency local fabrics. DLRM instead shards large embedding tables and exchanges the rows selected by each batch. Its memory-capacity and random-access constraints differ from dense arithmetic, but sparse lookup and redistribution traffic can still saturate network links under fan-out or skew.

    *Learning Objective*: Compare dense model tensor parallelism against sparse embedding sharding communication patterns

6.  **True or False: Ring Attention scales context length beyond single-GPU memory capacity by circulating key/value blocks in an accelerator ring across $N-1$ communication rounds while overlapping transfer with block-level attention computation.**

    *Answer*: True. Ring Attention partitions the query, key, and value sequences across $N$ GPUs so each device holds only $S/N$ tokens of key/value state. Each GPU evaluates its query block against all $N$ key/value blocks, including its local block, using $N-1$ transfers. Transfer can overlap block computation when the interconnect and compute budget permit; the distributed state capacity grows with worker count.

    *Learning Objective*: Evaluate the memory and communication mechanism of Ring Attention for long-context sequence parallelism

2.  Tensor-parallel reductions

4.  **In a 16,384-GPU cluster configured with $\text{TP}=8$, $\text{PP}=16$, and $\text{DP}=128$, how many GPUs participate in each individual data-parallel AllReduce communicator group?**

    1.  $16{,}384\text{ GPUs}$, because all accelerators in the cluster must synchronize in a single global collective
    2.  $128\text{ GPUs}$, because each rank communicates only with its corresponding tensor-and-pipeline shard position across the 128 model replicas
    3.  $8\text{ GPUs}$, matching the tensor-parallel degree within each local node
    4.  $16\text{ GPUs}$, matching the pipeline stage depth across the cluster spine

Neither topology is always more cost-effective.

1.  **Why does Proximal Policy Optimization (PPO) in multi-model RLHF create an infrastructure asymmetry challenge that does not exist in standard pretraining?**

    1.  It combines policy and value-model training with policy-generated autoregressive rollouts and forward-only scoring by frozen reference and reward models.
    2.  All four models in PPO must be trained with identical optimizer hyperparameters on the same GPU
    3.  PPO requires all models to be converted to INT4 precision to enable cross-node gradient synchronization
    4.  PPO eliminates backward passes entirely, turning distributed training into a stateless inference service

    *Answer*: The correct answer is A. The policy generates autoregressive rollouts, requiring a generation-time KV cache; policy and value updates require backward passes and optimizer state. Frozen reference and reward models score generated sequences without generating those sequences themselves. These phases have different memory and compute demands. Freezing scoring models does not eliminate the policy and value-model training work.

    *Learning Objective*: Analyze the infrastructure asymmetry between training and inference models in multi-model RLHF

2.  **Explain how Direct Preference Optimization (DPO) simplifies cluster infrastructure compared to PPO, detailing which models and computational phases are eliminated.**

    *Answer*: Standard offline DPO removes separate reward and value models and online autoregressive rollouts from the update loop. It trains on fixed preference pairs using a policy and a frozen reference, whose scores may be precomputed. Static-state savings depend on the PPO model sizes and placement. Removing rollout KV state eliminates a generation peak; it does not by itself enlarge update microbatches because both methods still need policy activations and other live buffers.

    *Learning Objective*: Compare the memory and execution pipeline requirements of PPO and DPO alignment architectures

3.  **During the autoregressive generation phase of PPO alignment for a 70B-parameter model, which growing runtime state can limit generation concurrency in accelerator memory?**

    1.  FP32 Adam momentum and variance buffers stored on CPU hosts
    2.  Key-Value (KV) cache memory in GPU HBM, bounded by memory bandwidth during token-by-token generation
    3.  AllReduce gradient communication buffers across InfiniBand switches
    4.  Host filesystem NVMe write bandwidth for checkpoint dumping

    *Answer*: The correct answer is B. The KV cache grows with concurrent sequence count, context length, layer count, and KV-head width. It can limit how many rollouts fit beside model weights and other resident state. Small-batch decoding is often memory-bandwidth bound, but cache capacity and compute limits must be evaluated separately. Optimizer buffers and checkpoint I/O do not explain this per-sequence growth.

    *Learning Objective*: Identify the binding resource bottleneck during the generation phase of online RLHF

4.  **The scheduling approach in RLHF distributed systems where the accelerator fleet alternates between an autoregressive rollout phase dominated by KV cache memory and a backward training phase dominated by matrix GEMM compute is known as \_\_\_\_.**

    *Answer*: temporal multiplexing. Temporal multiplexing reconfigures hardware resources dynamically between inference-shaped sequence generation and training-shaped gradient backpropagation.

    *Learning Objective*: Define temporal multiplexing as the scheduling strategy for alternating execution phases in RLHF

5.  **True or False: Because Direct Preference Optimization (DPO) eliminates reward and value models and avoids online sequence generation, it is strictly superior to PPO for all model alignment and exploration tasks.**

    *Answer*: False. DPO is restricted to optimizing against a static offline dataset of preference pairs, preventing the policy from generating novel outputs and exploring beyond the provided data. For tasks requiring iterative self-improvement and exploration (such as multi-step mathematical reasoning), PPO’s online rollout and reward feedback loop can discover superior trajectories, justifying its higher infrastructure overhead.

    *Learning Objective*: Evaluate the functional trade-offs between static DPO optimization and dynamic PPO exploration

**Self-Check: Answer**

1.  **According to the chapter’s parallelism decision framework, which condition indicates that standard DistributedDataParallel (DDP) is a sensible baseline to evaluate over FSDP, TP, or PP?**

    1.  The model’s single layer weight matrices exceed the HBM capacity of an individual GPU
    2.  The cluster is connected by slow 10 Gb/s commodity Ethernet across 1,024 nodes
    3.  The entire model state (parameters, gradients, and optimizer state) fits comfortably within single-device memory with sufficient headroom for activations
    4.  The model architecture contains sparse Mixture-of-Experts routing layers

    *Answer*: The correct answer is C. Comfortable full-state and activation fit makes DDP a sensible baseline because it avoids sharded parameter reconstruction and pipeline bubbles. Memory fit alone does not prove maximum throughput; exposed communication and useful batch size still need evaluation. An oversized layer makes tensor parallelism a candidate, while offload or recomputation may enable other layouts. Slow Ethernet requires a workload-specific communication budget; accumulation or a faster fabric may help. Sparse MoE routing motivates evaluating expert placement and its AllToAll demand.

    *Learning Objective*: Identify the binding constraint criteria that validate using standard Data Parallelism

2.  **An engineering team observes that an 8-GPU training job using pure pipeline parallelism achieves only 35 percent Model Flops Utilization (MFU), while interconnect links are largely idle. Using the bubble formula $F_{\text{bubble}} = \frac{p-1}{m+p-1}$, explain how to assess the pipeline-bubble hypothesis and propose two adjustments if the trace confirms it.**

    *Answer*: Low MFU and idle interconnect links make pipeline bubbles a candidate, but they do not prove the cause. Measure stage timelines and the microbatch count, and compare observed fill/drain idle slots with the bubble formula. Stage imbalance, input stalls, or inefficient local kernels can also lower MFU. If bubbles bind, increasing microbatch count can reduce their fraction, subject to activation memory and useful global batch size. Reducing stage count can also help when the revised memory budget fits; replacing some intra-node stages with tensor parallelism additionally requires a suitable communication budget.

    *Learning Objective*: Analyze pipeline bubble underutilization and propose architectural remedies

3.  \*\*Order the following parallelism strategies by their structural granularity from coarsest (whole model / batch level) to finest (intra-operator level):

<!-- -->

1.  Tensor Parallelism (Megatron column/row splits)
2.  Standard Data Parallelism (batch dimension splitting)
3.  Pipeline Parallelism (inter-layer stage splitting)\*\*

*Answer*: (2) -\> (3) -\> (1). First, (2) Standard Data Parallelism operates at the coarsest granularity, replicating the entire model and partitioning only the outer batch loop. Next, (3) Pipeline Parallelism partitions at the inter-layer boundary (assigning sequential layer groups to stages). Finally, (1) Tensor Parallelism operates at the finest intra-operator granularity, partitioning individual weight matrices within each layer.

*Learning Objective*: Rank distributed parallelism strategies by their structural decomposition granularity

**Self-Check: Answer**

1.  **In distributed training framework runtimes (such as PyTorch DDP), what mechanism combines multiple small layer gradient tensors into contiguous memory buffers before launching collective communication?**

    1.  Activation checkpointing
    2.  ZeRO Stage 3 parameter gathering
    3.  Temporal multiplexing
    4.  Gradient bucketing

    *Answer*: The correct answer is D. Gradient bucketing groups individual layer gradient tensors into larger contiguous memory buffers (typically 25–50 MB buckets) during the backward pass. Launching an AllReduce on a single aggregated bucket amortizes collective invocation latency and saturates network link bandwidth far more effectively than issuing hundreds of tiny per-tensor transfers. Activation checkpointing recomputes activations to save memory. ZeRO-3 parameter gathering reconstructs sharded weights on demand. Temporal multiplexing alternates execution modes in multi-model RLHF.

    *Learning Objective*: Explain the role of gradient bucketing in amortizing collective communication latency

2.  **Contrast the collective communication primitive invocation frequency of standard DDP against full-shard FSDP with resharding for a model with $N_L$ layers during a single training step.**

    *Answer*: DDP launches one AllReduce per ready gradient bucket, often overlapping those calls with backward computation. Full-shard FSDP with layer-level wrapping and resharding after forward typically adds an AllGather before forward, another before backward, and a ReduceScatter after backward: approximately $3N_L$ calls. Actual counts depend on wrapping, bucketing, prefetch, and resharding policy.

    *Learning Objective*: Compare collective communication primitive invocations between standard DDP and full-shard FSDP

3.  **Explain why framework optimizations such as CUDA graphs and asynchronous communication streams cannot eliminate the physical scaling penalty of distributed training as the cluster size $N$ becomes very large.**

    *Answer*: Framework optimizations can reduce launch overhead and change readiness, overlap, and effective communication service time. They cannot make a required payload cross a finite-bandwidth link instantaneously. At fixed global work, adding ranks reduces local compute while required transfers and coordination can remain exposed. A scaling prediction therefore needs the actual workload, collective schedule, and critical path; a fixed-residual Amdahl ceiling applies only under that model’s assumptions.

    *Learning Objective*: Evaluate the physical limits of framework-level communication optimizations

1.  **A team achieves 50 percent Model Flops Utilization (MFU) on a single node, scales to 1,024 GPUs, and measures a scaling efficiency $(\eta_{\text{scaling}})$ of 50 percent on their communication-heavy workload. What is the cluster’s realized model-FLOP rate during distributed execution as a fraction of peak hardware compute?**

    1.  25 percent of peak compute (delivering 256 GPU-equivalents of model computation)
    2.  50 percent of peak compute (delivering 512 GPU-equivalents of useful work)
    3.  100 percent of peak compute (delivering 1,024 GPU-equivalents of useful work)
    4.  12.5 percent of peak compute (delivering 128 GPU-equivalents of useful work)

    *Answer*: The correct answer is A. Starting from the single-node MFU baseline, the distributed model-FLOP rate is $0.50\times0.50=0.25$ of fleet peak, or 256 peak-GPU equivalents. The scaling factor accounts for losses relative to that baseline. A measured distributed MFU would already include those losses and must not be multiplied by scaling efficiency again. Retained-progress goodput additionally requires accounting for replay and recovery outside this measurement.

    *Learning Objective*: Calculate distributed model-FLOP rate from a local MFU baseline and scaling efficiency without double-counting losses

2.  **A procurement team plans capacity for a graph neural network workload using a vendor benchmark that reports 85 percent scaling efficiency at 1,024 GPUs for large-language-model training. Explain why this figure cannot be treated as a property of the cluster and what the team should measure instead.**

    *Answer*: Scaling efficiency is a joint property of the workload’s communication-to-computation ratio, the parallelism strategy, the network topology, and the software stack (collective library version, kernel fusion, overlap quality). The benchmark fixes all four for a language model; a graph neural network with irregular communication changes the first and likely the second, so the same hardware can deliver much lower efficiency. The team should measure scaling on the target workload, at the intended device count and parallelism layout, and plan capacity from that measured curve rather than from a hero benchmark.

    *Learning Objective*: Explain why scaling efficiency must be measured on the target workload rather than inherited from vendor benchmarks.

3.  **Why is gradient accumulation NOT a cost-free substitute for true physical scale-out even though it reduces gradient AllReduce communication frequency by a factor of $k$?**

    1.  It is mathematically incompatible with the Adam optimizer
    2.  It keeps a live gradient buffer resident, spaces optimizer updates by $k$ microsteps, and requires appropriate accumulation precision and normalization
    3.  It requires dedicated InfiniBand links between CPU and GPU for each microstep
    4.  It forces batch normalization layers to synchronize across all nodes on every forward pass

    *Answer*: The correct answer is B. One optimizer update follows $k$ forward/backward microsteps, but this does not imply $k$ times the wall-clock update latency: saved synchronization and the comparison schedule affect elapsed time. A live gradient buffer remains resident during the window. Unscaled FP16 accumulation can overflow; accumulation precision and loss normalization must preserve the intended update. Changes in effective batch size must be evaluated at matched target quality. Accumulation is compatible with Adam and requires neither special CPU-GPU links nor mandatory cross-node batch normalization.

    *Learning Objective*: Analyze the memory, latency, and numerical stability trade-offs of gradient accumulation

4.  **The largest global batch size beyond which adding more samples per step yields diminishing reductions in the number of steps needed to reach target quality is called the \_\_\_\_.**

    *Answer*: critical batch size. Beyond this workload-dependent point, larger global batches can raise hardware throughput without proportionally reducing the steps to target quality, so hardware scaling and statistical scaling must be evaluated separately.

    *Learning Objective*: Identify the critical batch size as the statistical limit on useful data-parallel scale-out.

5.  **True or False: If a 7B-parameter model fits comfortably in single-GPU memory with high compute utilization under standard DDP, universally enabling ZeRO-3 / FSDP full sharding will always increase training throughput by reducing per-GPU memory consumption.**

    *Answer*: False. FSDP trades memory capacity for parameter-gather and gradient-reduction traffic. If its memory savings do not enable a more efficient batch or layout, the exposed communication can lower throughput. The outcome depends on wrapping, resharding, overlap, and network capacity, so neither a universal gain nor a fixed percentage penalty follows from sharding.

    *Learning Objective*: Evaluate the performance pitfall of applying FSDP when memory capacity is not binding
