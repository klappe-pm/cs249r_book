# V2-06.10 Frameworks and Runtime Contracts

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training|V2-06 Distributed Training]]

^sec-distributed-training-systems-systems-framework-integration-cf71

A TP-8, PP-16, DP-128 layout that passes every feasibility check on paper can still hang at its first collective if two ranks disagree on the membership of their communication group, or run slowly if gradient buckets become ready in an order the collective runtime cannot overlap. Choosing DDP, FSDP/ZeRO-style sharding, tensor parallelism, or pipeline parallelism is therefore also a decision about which constraints the runtime owns and which constraints the engineer must manage directly. Sparse workloads add another contract, the parameter-server push/pull interface ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-li2014|Li et al. 2014]]) developed for Archetype B in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-parameter-servers-embedding-sharding-8821|section 6.5.6]].

The training framework defines process groups (its records of which ranks form each tensor-parallel, pipeline, or data-parallel group), gradient buckets, and the point in backpropagation when each reduction becomes ready; the collective runtime maps those reductions onto ring, tree, or hierarchical algorithms. The engineer must choose compatible group membership and bucket order and verify which communication remains exposed on the step’s critical path.

Production frameworks expose these same strategies under different names, which makes a translation aid useful when reading their documentation or configuration files. Four widely used stacks name the chapter’s strategies differently ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.10 Frameworks and Runtime Contracts#^tbl-framework-strategy-map|table 11]]); the names change between releases, but the partition each one implements does not.

| **Strategy**              | **PyTorch**                        | **DeepSpeed**                  | **Megatron-LM**                        | **JAX**                                                         |
|:--------------------------|:-----------------------------------|:-------------------------------|:---------------------------------------|:----------------------------------------------------------------|
| **Data parallel**         | DistributedDataParallel (DDP)      | DeepSpeed engine, ZeRO stage 0 | Data-parallel process groups           | Batch axis sharded over a device mesh                           |
| **Sharded data parallel** | Fully Sharded Data Parallel (FSDP) | ZeRO stages 1–3                | Distributed optimizer                  | Parameter and optimizer state sharded over a mesh axis          |
| **Tensor parallel**       | DTensor tensor-parallel APIs       | AutoTP or Megatron integration | Column- and row-parallel linear layers | Sharding annotations on model axes, partitioned by the compiler |
| **Pipeline parallel**     | `torch.distributed.pipelining`     | Pipeline engine                | Pipeline schedules (1F1B, interleaved) | User-written stage schedules                                    |

Table 11: **Framework Names for the Parallelism Strategies**: A translation aid, not a ranking. Each entry names the mechanism a framework uses for the partition developed in this chapter; exact class and option names vary across releases.

^tbl-framework-strategy-map

The training design therefore determines message size, readiness order, and frequency, while collective algorithms determine how those messages move. No framework abstraction changes those physical costs, so distributed-training efficiency ultimately depends on interconnect bandwidth, memory capacity, synchronization latency, and the useful overlap admitted by the computation graph. Confusing the simplicity of a framework API with exemption from those physical costs produces the recurring engineering mistakes below.

↩︎ Overlap of gradient exchange with backpropagation, the lever that takes communication off a step’s critical path, is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.11 Communication-Computation Overlap#^sec-communication-overlap|Communication-Computation Overlap]]**.
