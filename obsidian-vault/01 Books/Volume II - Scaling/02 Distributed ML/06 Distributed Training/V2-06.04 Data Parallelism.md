# V2-06.04 Data Parallelism

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training|V2-06 Distributed Training]]

^sec-distributed-training-systems-systems-data-parallelism-6132

When a model fits on one accelerator but training takes weeks, replicating its computation lets several workers process examples concurrently. The initial data-parallel baseline gives each worker the same model state and a local portion of one global minibatch. Combining those local contributions before the optimizer update preserves the intended global-batch estimator; the sampling and weighting conditions below explain when that equivalence holds.

**Definition 6.2: Data parallelism**

***Data parallelism*** distributes training examples across workers that execute the model and combine their contributions to its optimization updates.

1.  **Significance**: With ${N}$ workers each processing a local batch of ${B_{\text{local}}}$ examples once per update, the global batch size is ${N}\times {B_{\text{local}}}$. At fixed local work, 1,024 workers offer an ideal 1,024$\times$ throughput increase before exposed overhead. A 1B-parameter model with BF16 gradients contributes a 2 GB gradient payload; ring AllReduce moves $2({N}-1)/{N}$ times that payload per worker. Realized speedup depends on local compute, collective service, overlap, and load balance.
2.  **Distinction**: The replicated synchronous baseline keeps a full model copy on each worker and aggregates gradients before each optimizer update. Model parallelism instead partitions the model’s computation. Sharded data parallelism, developed below, retains data-parallel computation while distributing training-state storage.
3.  **Common pitfall**: Data parallelism does not scale indefinitely with worker count. Holding the local batch ${B_{\text{local}}}$ fixed while adding workers grows the global batch. Beyond the workload-dependent critical batch size, additional examples yield diminishing reductions in the steps needed to reach target quality ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-Shallue2019measuring|Shallue et al. 2019]]). The crossover developed in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-systems-systems-critical-batch-size-parallelism-hurt-4961|section 6.4.6]] therefore limits the statistical benefit even when gradient variance continues to decrease.

Data parallelism applies when examples can be processed independently, as in training a ResNet model ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-he2016|He et al. 2016]]) on ImageNet. Each replica computes its local loss gradient, and the workers combine those contributions to reproduce the intended global-batch gradient. The averaging rule makes the sampling and weighting assumptions explicit.

Consider a model with parameters ${\theta}$ training on a dataset ${D}$. The loss function for a single data point ${x}_i$ is ${\mathcal{L}}({\theta}, {x}_i)$. In standard stochastic gradient descent (SGD) with batch size ${B}$, the gradient update for a minibatch is:

$$
{\mathbf{g}}= \frac{1}{{B}} \sum_{i=1}^{B}\nabla_{{\theta}} {\mathcal{L}}({\theta}, {x}_i)
$$

In data parallelism with ${N}$ devices, each device ${k}$ computes gradients on its own minibatch ${\mathcal{B}}_k$:

$$
{\mathbf{g}}_k = \frac{1}{|{\mathcal{B}}_k|} \sum_{{x}_i \in {\mathcal{B}}_k} \nabla_{{\theta}} {\mathcal{L}}({\theta}, {x}_i)
$$

When all workers use the same local batch size, the global update averages these local gradients:

$$
{\mathbf{g}_{\text{global}}}= \frac{1}{{N}} \sum_{k=1}^{N}{\mathbf{g}}_k
$$

Under that equal-batch assumption, the averaging is mathematically equivalent to computing the gradient on the combined batch ${B_{\text{total}}}= \bigcup_{k=1}^{N} {\mathcal{B}}_k$:

$$
{\mathbf{g}_{\text{global}}}= \frac{1}{|{B_{\text{total}}}|} \sum_{{x}_i \in {B_{\text{total}}}} \nabla_{{\theta}} {\mathcal{L}}({\theta}, {x}_i)
$$

For unequal local batch sizes, the combined-batch gradient is the weighted average ${\mathbf{g}_{\text{global}}}= (1/|{B_{\text{total}}}|)\sum_k |{\mathcal{B}}_k|{\mathbf{g}}_k$. Data parallelism therefore maintains the statistical properties of SGD training, because sampling the intended global batch across devices, computing local gradient sums independently, and normalizing by the aggregate denominator reproduces its estimator. The reduction step uses an AllReduce over local gradient sums and valid-item counts, the numbers of examples or tokens that contribute to the loss.

Three batch quantities recur from here on, and the chapter keeps them apart. A worker’s local batch ${B_{\text{local}}}$ is the set of examples it processes for one update, playing the role of ${\mathcal{B}}_k$ above. The global batch ${B_{\text{global}}}= {N}\times {B_{\text{local}}}$ is the set the update averages over. Pipeline parallelism later splits a batch into ${m}$ microbatches of size ${B_{\text{micro}}}$ that flow through stages one after another; the word microbatch is reserved for those pipeline slices.

↪ The ring and tree AllReduce cost models that set the price of this synchronization are developed in **[[05 Reference/Volume II - Scaling/V2 Communication Foundations#^sec-appdx-comm-foundations-allreduce|AllReduce]]**.

**Checkpoint 6.1: Data parallelism mechanics**

Verify your understanding of how data parallelism distributes work:

**State placement**: determine whether data parallelism shards or replicates the model state (weights) across GPUs.

**Global batch size**: calculate the effective global batch size for 8 GPUs with a per-GPU batch size of 32.

**Single-device equivalence**: explain why data parallelism is mathematically equivalent to single-device training with a larger batch size.

**Limiting constraint**: identify the primary hardware resource that constrains data parallelism as more nodes are added: GPU TFLOP/s or network bandwidth.

The method parallels gradient accumulation, where a device accumulates contributions from multiple forward and backward passes before one optimizer update. Both techniques use gradient addition and the intended loss denominator to process a larger effective batch. Distribution adds communication, partial failures, and coordination to that arithmetic.

### Data Parallelism Implementation

^sec-distributed-training-systems-systems-data-parallelism-implementation-fa03

The SGD equivalence holds only when each phase preserves the intended aggregate sampling and weighting, complete local gradient contributions, and a single synchronized update. The five-stage execution pipeline in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^fig-dist-train-data-parallelism|figure 3]] follows the dataflow across four GPU swimlanes, from assigning local batches to synchronizing the computed gradients. Identical model replicas ingest disjoint batch shards and compute local gradients (${\mathbf{g}}_0$–${\mathbf{g}}_3$). They then synchronize through a ring AllReduce collective before applying uniform parameter updates.

![[90 Assets/Volume II/06 Distributed Training/Data Parallel Flow d989c6a234.svg]]

Figure 3: **Data Parallelism Implementation Pipeline**: The five-stage workflow for data-parallel training: (1) partition the global batch, (2) assign sharded mini-batches to individual GPUs, (3) compute independent forward and backward passes to produce local gradients ${\mathbf{g}}_i$, (4) execute an AllReduce collective across the cluster to obtain the average gradient ${\mathbf{g}_{\text{global}}}$, and (5) update parameters identically across all devices. This strategy preserves the mathematical semantics of single-device SGD while distributing the compute burden.

^fig-dist-train-data-parallelism

The gradient synchronization stage of [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^fig-dist-train-data-parallelism|figure 3]] (stage 4) creates a dependency, because each rank must receive the completed reduction before applying its optimizer update. The exposed wait can reflect bandwidth, collective startup, or a late contribution. Measuring that wait determines whether synchronization limits scaling; the dependency alone does not identify the limiting resource.

#### Dataset Splitting

^sec-distributed-training-systems-systems-dataset-splitting-1edf

Data splitting is the first place where the SGD equivalence can fail. The aggregate examples or tokens, their sampling probabilities, and their gradient weights must reproduce the intended global-batch estimator. Unique, equal-sized shards satisfy that invariant, but they are sufficient rather than required. Uniform sampling without replacement can assign disjoint shards. Sampling with replacement can legitimately repeat examples. Variable-length batches can assign unequal token counts if the reduction weights each worker by its valid-example or valid-token denominator, which excludes the padding tokens that fill out shorter sequences. An unweighted mean of unequal local means instead overweights workers with smaller denominators.

The sampler is therefore an integral component of the distributed training system rather than merely an input-loader convenience. A distributed sampler coordinates workers by rank and can deterministically partition or draw indices from a seeded sampling stream. The 1.28 million training images of ImageNet-1k do not divide evenly across 32 GPUs. A sampler that pads by repeating whole examples, unlike the token padding of variable-length batches, gives each GPU 40,037 examples per epoch and adds 17 repeats across the job. The loss normalization or sample weights must account for those repeats when exact epoch-level weighting matters. A recorded seed and deterministic index stream make sample assignment repeatable. Bitwise run reproducibility additionally depends on kernel determinism, collective reduction order, numerical precision, and checkpointed random-number-generator state.

#### Compute-Phase Forward and Backward Passes

^sec-distributed-training-systems-systems-compute-phase-forward-backward

For a replicated model whose local forward and backward operations require no cross-worker state, the computation phase is *embarrassingly parallel*. Each GPU executes the model on its local batch; synchronized normalization or additional model partitioning can introduce communication within that phase. To isolate the activation term, consider an unpartitioned 175B reference model at a local batch of 4 sequences and sequence length 2048. This is a hypothetical memory budget, not a feasible one-GPU training configuration, because weights and optimizer state must fit as well. Without optimization, storing these activations for backpropagation would consume roughly 1.1 TB of HBM, an order of magnitude beyond the capacity of even an H100 GPU. Activation checkpointing recomputes selected activations during the backward pass rather than retaining them, reducing this example’s footprint to ~19.3 GB at the cost of extra computation.

The capacity test must include activations rather than stopping at bytes per parameter. **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-training-memory|Numeric Precision and Training Memory]]** tabulates the 16-byte-per-parameter training state from which this test starts. At the point of peak residency,

$$
{M_{\text{total}}} = {M_{\text{weights}}} + {M_{\text{gradients}}} + {M_{\text{optimizer}}} + {M_{\text{activations}}},
$$

 with communication buffers and temporary workspaces consuming additional headroom. Sharding ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-memoryefficient-data-parallelism-zero-fsdp-0e69|section 6.3.3]]) reduces the first three terms according to its stage, whereas sequence length, local batch size, and pipeline scheduling govern ${M_{\text{activations}}}$. Activation checkpointing reduces that last term by retaining only selected boundaries and recomputing the omitted forward operators during backpropagation ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-narayanan2021|Narayanan et al. 2021]]). Full recomputation re-executes about one extra forward pass per step. Because a backward pass costs roughly two forward passes, a step that needed three forward-pass equivalents of arithmetic now needs four, about a third more ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-chen2016training|Chen et al. 2016]]). Selective recomputation re-executes only operators whose activations are large but cheap to produce, such as the attention softmax and dropout, and keeps most of the memory saving for a few percent of extra arithmetic ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-korthikanti2023activation|Korthikanti et al. 2023]]). Recomputed operations raise hardware FLOPs utilization (HFU) but not model FLOPs utilization (MFU), which credits only the model’s own forward and backward work. A plan that buys feasibility with full recomputation therefore pays for it in useful throughput. The memory saved is purchased with additional FLOPs and a longer critical path. A feasible parallelism plan must budget both effects.

As the backward pass traverses the computation graph in reverse, it produces gradients for the parameters held by each replica or shard. Under pure data parallelism, a full 175B FP16 replica would imply a 350 GB gradient tensor per worker, which exceeds single-accelerator memory budgets. Large runs therefore combine data parallelism with sharding, tensor parallelism, or pipeline parallelism. Each local gradient contributes to the intended global-batch estimator. Aggregation can begin as gradient tensors become ready, overlapping later backward computation, but the optimizer must wait for the completed contributions it consumes. This readiness schedule connects local computation to collective communication.

#### Gradient Synchronization

^sec-distributed-training-systems-systems-gradient-synchronization-614b

Gradient synchronization combines local contributions into the synchronous update. Each replica must receive the aggregate before applying that update. In a centralized parameter-server design, where servers hold the parameters and workers send them gradients, fixed per-worker payload and update frequency give the server $\mathcal{O}({N})$ incoming traffic. That concentration becomes a bottleneck when demand exceeds the server tier’s service capacity; sharding the server state or changing the communication pattern can relieve it.

The replicated synchronous baseline distributes aggregation through collective communication. AllReduce lets each worker contribute its local gradient tensor and receive the same reduced result, which the training loop normalizes to obtain the global average. In sharded variants such as ZeRO and FSDP, ReduceScatter and AllGather change which result each worker retains, leaving each worker only its own shard of the reduced gradient and reconstructing full parameters on demand. Small messages emphasize startup latency; large messages emphasize sustained bandwidth. Centralized aggregation remains another design choice, particularly for the sparse workloads developed later.

↩︎ The result contracts of AllReduce, ReduceScatter, and AllGather, and the decomposition of AllReduce into a ReduceScatter followed by an AllGather, are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.05 Collective Operation Primitives#^sec-collective-communication-six-core-primitives-8a66|The six core primitives]]**.

At the Distributed Execution row of the fleet stack, the loop specifies an AllReduce contract while its implementation determines the cost. For a large worker group, ring AllReduce transfers approximately $2{M_{\text{grad}}}$ bytes per worker for an ${M_{\text{grad}}}$-byte gradient payload. **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05 Collective Communication#^sec-collective-communication|Collective Communication]]** derived this approximate $2{M_{\text{grad}}}$ volume and compared algorithms whose startup costs, topology, and contention differ. That chapter also examined how libraries such as NCCL schedule exchanges within and across communication domains.

Because those algorithms predict different times on the same hardware, diagnosing a measured collective starts by comparing its trace against each prediction. A typical comparison sets a flat ring against a hierarchical AllReduce, which reduces within each NVLink node before crossing the inter-node fabric. Consider a hypothetical A100 cluster with HDR InfiniBand running an AllReduce of a 3 GB gradient tensor across 128 nodes (1,024 GPUs). The flat-ring estimate is 239.8 ms, the idealized hierarchical estimate is 48.5 ms, and the trace measures 100 ms. The observation rules out the flat schedule, and the residual above the hierarchical ideal must come from lower achieved rates, startup, or a late participant. Switch counters showing inter-node links at 60 percent utilization do not settle the question, because an aggregate can hide one saturated port during the exposed interval. Per-port and per-channel traces must locate the bottleneck before any topology change.

↩︎ Hierarchical AllReduce and its cost relative to a flat ring are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.08 Hierarchical Communication#^sec-communication-collective-operations-collective-operations-hierarchical-allreduce-1338|Hierarchical AllReduce]]**.

Across the wider design space, [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^fig-coll-comm|figure 4]] compares three synchronization topologies. The bandwidth-optimal ring AllReduce circulates chunks along neighbor links ($2({N}-1)/{N}$ volume). The centralized parameter server is constrained by network interface card (NIC) saturation at the server node. The dense mesh of logical AllToAll peer traffic requires ${N}({N}-1)$ messages. In dense synchronous data-parallel settings, ring AllReduce avoids a single reducer bottleneck by distributing traffic evenly across participating links, as Baidu’s implementation illustrates ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-gibiansky2017baidu|Gibiansky 2017]]).

#### Parameter Updating

^sec-distributed-training-systems-systems-parameter-updating-bb64

Parameter updating closes the replicated synchronous contract. After the gradient AllReduce ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-patarasuk2009|Patarasuk and Yuan 2009]]), every worker holds the same global gradient and applies it to its own replica with SGD, momentum, or Adam, so the update stays decentralized without losing equivalence to single-device training. Identical gradients alone are insufficient, because optimizer moments, learning rates, and step counts must also match across replicas. Frameworks automate the cycle of splitting data, computing gradients, synchronizing, and updating, but they cannot remove the ordering constraint that keeps the replicas coherent. Every worker must finish aggregating the current step’s gradient before any replica computes from the updated weights.

#### Synchronization Models

^sec-distributed-training-systems-systems-synchronization-models-396f

Whether every worker must wait at a barrier on every step defines the job’s synchronization model. The baseline is bulk synchronous parallel (BSP), the superstep-and-barrier model, in which workers compute from one parameter version, combine their gradient contributions, and complete the update before computing from the next version. This is a dependency order, not a requirement that every device update at the same wall-clock instant.

↩︎ Bulk synchronous parallel execution and its barrier cost are established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.03 How ML Networking Inverts Data-Center Assumptions#^sec-network-workload-inversion|How ML Networking Inverts Data-Center Assumptions]]**.

With the same global batch and reduction, BSP matches the corresponding synchronous single-device update mathematically. It does not by itself guarantee bitwise reproducibility. Floating-point reduction order, nondeterministic kernels, data-order state, and failure recovery can still change the result. The synchronization cost is that the slowest worker determines iteration time. A worker that keeps producing correct results but runs markedly slower than its peers is a **straggler**, and under BSP every straggler delays the entire step. Relaxing the barrier changes the optimization process as well as the waiting time.

Stale synchronous parallel (SSP) relaxes this constraint by allowing workers to proceed up to ${s}$ iterations ahead of the slowest worker before blocking. This bounds staleness while reducing synchronization delays. SSP requires careful learning rate tuning since workers compute gradients on slightly different parameter versions. The bounded staleness guarantee provides a middle ground between BSP’s strong consistency and fully asynchronous approaches ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-ho2013more|Ho et al. 2013]]).

Asynchronous parallel (ASP) execution removes the global update barrier, allowing a worker’s contribution to be applied while others continue computing; asynchronous SGD is the optimizer run under that protocol. Less barrier waiting can improve update throughput, but communication and shared-state contention remain. Gradients computed from older parameter versions introduce staleness that can affect convergence. [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-systems-systems-staleness-impact-bsp-vs-ssp-vs-asp-e153|Section 6.4.4]] develops the objective and delay assumptions needed to evaluate that trade-off. The three models lie on one spectrum, from the strong consistency of BSP to the barrier-free updates of ASP ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^tbl-sync-models|table 2]]).

| **Model** |  **Consistency**  |       **Throughput**        | **Convergence**                    | **Use case**                   |
|:----------|:-----------------:|:---------------------------:|:-----------------------------------|:-------------------------------|
| **BSP**   |      Strong       |  Bounded by slowest worker  | Same synchronous update semantics  | Controlled final training runs |
| **SSP**   | Bounded staleness | Less global-barrier waiting | Depends on delay and tuning        | Hyperparameter search          |
| **ASP**   |       Weak        |  No global update barrier   | Depends on staleness and objective | Large heterogeneous clusters   |

Table 2: **Synchronization Model Trade-Offs**: BSP, SSP, and ASP trade consistency for throughput along a spectrum. BSP preserves synchronous update boundaries but pays for the slowest worker; SSP permits bounded progress ahead of slower workers; ASP removes the global update barrier without a finite protocol-wide staleness bound. Throughput and time to target quality depend on the workload and implementation. Reproducibility requires a separate deterministic-execution contract.

#### Barrier Semantics and Failure Modes

^sec-distributed-training-systems-systems-barrier-semantics-failure-modes-5c94

An optimizer update that consumes an AllReduce result must wait for every required contribution. Workers can execute independent computation while a collective is in flight, but they must issue compatible collectives in the same group order and wait for completion before consuming the result. This coupling creates failure modes absent from single-device training.

A worker failure can leave peers waiting for a contribution that will never arrive. The runtime may report a communication error, or the operation may remain blocked until a timeout detects the failure. Watchdogs bound that wait so the job can enter recovery rather than retain an unusable allocation indefinitely.

![[90 Assets/Volume II/06 Distributed Training/Vol2 Distributed Training Margin 002 d65398f4b5.svg]]

*Five worker dots in a column. Four blue workers have gray lanes that stop just short of a red vertical barrier, each ending in a pause mark; the middle worker is a dashed red hollow circle labeled missing with no lane, so the barrier never releases.*

*One missing worker stalls the entire AllReduce barrier.*

Collective mismatches occur when workers issue incompatible operations, tensor shapes, or ordering within a communication group. Conditional computation can create such a mismatch if some workers omit an expected reduction. Variable sequence lengths or different expert routes do not inherently violate the protocol; the runtime must construct a compatible communication schedule for those varying local computations.

Stragglers extend an iteration when their late work lies on its critical path. Thermal throttling, network congestion, or OS jitter can delay a required contribution even when other workers are ready. At 1,000 GPUs with a 1 percent straggler probability per GPU per step, the expected count is 10 stragglers per step, but the number that matters under BSP is the chance of a step with none at all. That chance is the per-GPU on-time probability raised to the GPU count, about 0.004 percent. Almost every step therefore waits for at least one slow worker, which is why the slowest worker, not the typical one, sets step time. The resulting exposed wait depends on how late that contribution arrives and what independent work remains. Deployed systems bound these waits with timeouts and heartbeat monitoring, and elastic training lets a job continue with a resized worker group after a failure.

↪ Heartbeat and collective-timeout failure detection, and the trade-off between restarting healthy workers and leaving peers blocked, are developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.10 Failure Detection and Recovery#^sec-fault-tolerance-reliability-reliability-failure-detection-mechanisms-efed|Failure detection mechanisms]]**.

### Data Parallelism Trade-Offs

^sec-distributed-training-systems-systems-data-parallelism-tradeoffs

Data parallelism is the simplest way to add accelerators because it leaves each replica’s model computation intact, but adding workers eventually hits either a communication wall or a statistical wall ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-ben-nun2019|Ben-Nun and Hoefler 2019]]). Near-linear throughput scaling requires local compute efficiency, balanced input delivery, and small exposed synchronization costs. Which wall arrives first depends on whether the global batch stays fixed or grows as workers are added. Holding the global batch fixed while adding workers is **strong scaling**: each worker’s local batch shrinks, so communication must hide behind less computation. Holding the local batch fixed so that the global batch grows with ${N}$ is **weak scaling**: per-worker computation stays constant, but each update averages more examples, which eventually stops reducing the number of updates needed. The rest of the chapter refers to the two regimes by these names.

Weak scaling pays off when the larger global batch still reaches the target accuracy. Goyal et al. ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-goyal2017accurate|2017]]) trained ResNet-50 on ImageNet in about one hour on 256 GPUs at a global batch of 8,192 images; the learning-rate rules that let that batch reach the target accuracy are developed in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-systems-systems-learning-rate-scaling-rules-fa26|section 6.4.5]].

Replicated data parallelism retains the model’s local operators, and frameworks can trigger gradient reductions as backward computation produces them. Each replica executes a complete forward and backward pass, avoiding the bubbles of pipeline parallelism, the idle slots while layer stages fill with work and drain. Input stalls, imbalance, and exposed reductions can still leave devices idle.

These advantages hold only until replication runs into memory capacity, communication bandwidth, or statistical diminishing returns. The memory wall arrives first on large models because a replicated worker holds every parameter, gradient, and optimizer state, demanding more than 1 TB per replica for the 175B-parameter example before activations. Even when the state fits, communication limits useful scaling once its exposed cost grows relative to local work. As ${N}$ increases, the ideal ring bandwidth term $\frac{2({N}-1)}{{N}} \frac{{M_{\text{grad}}}}{{\beta}}$ approaches a constant for a fixed gradient payload ${M_{\text{grad}}}$ and link bandwidth ${\beta}$, while startup latency, topology, and shrinking local computation worsen the balance. Statistical efficiency then sets the ceiling under weak scaling, because growing ${B_{\text{global}}}= {N}\times {B_{\text{local}}}$ with ${N}$ eventually yields diminishing reductions in update count. Strong scaling avoids that batch-size ceiling only by shrinking each worker’s local batch, which exposes the communication trade-off sooner.

**Napkin Math 6.1: GPT-2 data parallel scaling: Single node**

A GPT-2 scaling scenario makes the efficiency loss concrete by holding the model fixed and changing only the communication domain. GPT-2 stands in for the 175B reference here because it fits on one GPU, so pure replicated data parallelism applies and communication is the only variable. This notebook and the next report parallel efficiency, the achieved speedup divided by the GPU count, which [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-scaling-math|section 6.4.1]] develops as scaling efficiency. The first case keeps all eight GPUs inside a single NVLink node.

**Single-GPU baseline**

- Batch size: 16 (with activation checkpointing, fits in 32 GB)
- Time per step: 1.8 s
- Baseline time for 50K single-GPU steps: 25 hours

The following durations hold the total sample budget fixed, so larger global batches require fewer optimizer updates. They assume those samples attain the same quality; the calculation establishes throughput scaling, not convergence equivalence.

**8 GPUs: single node with NVLink**

- Per-GPU batch: 16, global batch: 128
- Gradient synchronization: 5.2 GB @ 450 GB/s (NVLink, per direction) $\approx$ 11.7 ms

Performance results:

- Compute: 1800 ms per step
- Communication: 11.7 ms per step
- Total: 1811.7 ms per step
- Speedup (throughput): 8×
- Parallel efficiency: 99.4 percent

Training time: 25 hours ÷ 8 = 3.1 hours

Inside the node, NVLink keeps gradient exchange small relative to compute, so efficiency stays near 99.4 percent. The picture inverts once the same model must synchronize across nodes over a commodity network.

**Napkin Math 6.2: GPT-2 data parallel scaling: Commodity scale-out**

The second case scales the same GPT-2 run across multiple nodes, replacing the intra-node NVLink hop with inter-node Ethernet for the bulk of the AllReduce. The 10 Gb Ethernet link models a commodity cloud tier without a dedicated training fabric, far slower than the InfiniBand of the reference cluster, which makes the cost of leaving the node easy to see.

**Commodity network configuration**: 32 GPUs across 4 nodes

- Per-GPU batch: 16, global batch: 512
- Intra-node communication: 11.7 ms (NVLink)
- Inter-node communication: 5.8 GB @ 1.25 GB/s (10GbE) $\approx$ 4650 ms

Performance results:

- Compute: 1800 ms (27.9 percent of time)
- Communication: 4661.7 ms (72.1 percent of time), so communication dominates and becomes the bottleneck.
- Total: 6461.7 ms per step
- Speedup (throughput): 8.9× faster → 2.8 hours
- Parallel efficiency: 27.9 percent

The scale-out run bought its larger global batch with four nodes on a slow network. A single node can reach the same global batch another way, by running several local microsteps and accumulating their gradients before one AllReduce. The comparison below is therefore between two placements, one node with accumulation against four nodes without it. Accumulation’s job is to keep the global batch equal, while the saving comes from never leaving the NVLink domain.

**Napkin Math 6.3: Gradient accumulation speedup**

**Problem**: A GPT-2 run on a commodity 10G network is communication-bound at 32 GPUs across 4 nodes, costing \$359 for a fixed number of samples. Can a single 8-GPU node that uses gradient accumulation to match that global batch process the same samples for less?

**Math**:

1.  **Effective batch size**: 8 GPUs $\times$ batch 16 $\times$ 4 accumulation steps = 512.
2.  **Communication overhead**: With 4-step accumulation, the job AllReduces once every 4 steps (overhead = 11.7 ms / (4 $\times$ 1800 ms) $\approx$ $0.162\%$).
3.  **Training duration**: Total time is 3.1 hours.
4.  **Scale-out baseline cost**: 4 nodes $\times$ 2.8 hours $\times$ \$32/hr = \$359.
5.  **Accumulation cost**: 3.1 hours $\times$ \$32/hr = \$100.

**Systems insight**: The one-node plan saves \$259 (72.1 percent). Almost all of that saving comes from placement, because the four-node run spent most of each step on the slow inter-node link and the single node never uses it. Gradient accumulation is what makes the single node a fair substitute, because it reproduces the four-node global batch. Its own contribution to speed is small, since the same node already ran at 99.4 percent parallel efficiency without accumulation. Accumulation on a multi-node job still requires inter-node synchronization once per window.

In this GPT-2 scenario, changing the communication domain drops efficiency from 99.4 percent to 27.9 percent. Accumulation can preserve the effective batch while avoiding the slow scale-out link, at the cost of additional local computation between updates. It leaves each worker’s replicated model state unchanged, however; reducing that memory burden requires sharding.

### Memory-Efficient Data Parallelism with ZeRO and FSDP

^sec-distributed-training-systems-systems-memoryefficient-data-parallelism-zero-fsdp-0e69

Replicated data parallelism stores an identical copy of weights, gradients, and optimizer state on every GPU, so a 7B-parameter model demands 112 GB on each device and overflows an 80 GB accelerator before a single activation is allocated. The Zero Redundancy Optimizer (ZeRO) ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-rajbhandari2020|Rajbhandari et al. 2020]]) and PyTorch’s Fully Sharded Data Parallel (FSDP) ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.14 Source References#^ref-zhao2023|Zhao et al. 2023]]) remove that duplication by sharding training state across workers while keeping each worker’s full forward and backward computation.[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.15 Footnotes#^fn3|³]] Sharding can make a model fit in memory without splitting its layer computations across devices.

**Definition 6.3: Sharded data parallelism**

***Sharded data parallelism*** partitions optimizer state, gradients, and at the deepest stage the parameters themselves across data-parallel workers. Each worker processes its own minibatch shard and uses collectives to obtain the parameters and reduced gradients it needs. Full sharding reduces each worker’s persistent state toward $1/{N}$ of the replicated training state; activations and temporary buffers still contribute to peak memory.

1.  **Significance**: Under the mixed-precision Adam convention used here, 16 bytes of state per parameter gives a 7B-parameter model 112 GB of training state, exceeding a 80 GB accelerator before activations. ZeRO Stage 3 across 64 workers reduces persistent state per device to 1.75 GB (0.25 bytes per parameter). The resulting AllGather and ReduceScatter traffic trades memory capacity for communication whose exposed cost depends on the interconnect and available overlap.
2.  **Distinction**: Unlike vanilla data parallelism, which replicates training state, sharded data parallelism partitions its storage. Unlike model parallelism, it retains each worker’s full forward and backward computation. Fully sharded execution gathers parameters for the current computation; the resharding schedule determines when it releases them.
3.  **Common pitfall**: A frequent misconception is that sharding is free memory. The on-demand AllGathers place parameter traffic on the critical path of every layer in every step. On slower interconnects or at small per-worker batch sizes, the exposed communication erodes throughput faster than the memory savings help. Capacity is purchased with bandwidth.

The scale of the savings is clearest on a model whose replicated training state only modestly overflows one accelerator, so that the effect of each sharding stage stays visible. The 175B reference returns in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-model-parallelism-7437|section 6.5]], when the question becomes whether sharding alone is enough.

**Napkin Math 6.4: ZeRO memory savings**

**Problem**: Training a 7B parameter Llama-2 model in mixed precision requires 16 bytes per parameter for weights, gradients, and optimizer state. Does the full training state fit on a single A100-80 GB, and how does ZeRO Stage 3 with 64 GPUs change the per-device memory requirement?

**Baseline: Standard DDP (replicated state)** Per-Parameter Memory Cost:

- **Weights (FP16)**: 2 bytes
- **Gradients (FP16)**: 2 bytes
- **Optimizer state (FP32)**: 12 bytes (4 master weight + 4 momentum + 4 variance)
- **Total**: 16 bytes/parameter

Total Memory for 7B Model:

$$
C_{\text{state,total}} = 7 \times 10^9 \times 16 \text{ bytes} \approx 112 \text{ GB}
$$

**Baseline outcome**: Out-of-memory (OOM) on A100-80 GB.

**Optimization: ZeRO-3 (fully sharded)** With ${N}=$ 64 GPUs, state is partitioned:

- **Weights**: 2$/{N}$ bytes
- **Gradients**: 2$/{N}$ bytes
- **Optimizer**: 12$/{N}$ bytes
- **Total**: 16$/{N}=$ 0.25 bytes/parameter effective storage

Per-GPU Memory:

$$
C_{\text{state,ZeRO3}} = \frac{112 \text{ GB}}{64} \approx 1.75 \text{ GB}
$$

**Result**: The persistent state fits, leaving ~78 GB for activations, gathered parameters, temporary buffers, and runtime allocations. Their simultaneous peak determines whether the chosen batch size fits.

ZeRO reaches that result in stages, and the intermediate stages matter because each one buys memory with a different communication pattern. Optimizer sharding alone (ZeRO-1) already brings the replicated footprint of the same model under the accelerator ceiling, because optimizer state is three-quarters of it. Gradient sharding (ZeRO-2) and parameter sharding (ZeRO-3/FSDP) continue toward the fully sharded figure ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^fig-zero-memory|figure 6]]). Each stage also changes which collectives the update uses ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^tbl-zero-stages|table 3]]).

![[90 Assets/Volume II/06 Distributed Training/Cell 19 Output 1 46f00bf1f8.png]]

Figure 6: **ZeRO Memory Reduction**: Standard data parallelism (DDP) replicates all model states across every GPU. ZeRO progressively partitions these states: ZeRO-1 shards optimizer states, ZeRO-2 adds gradient sharding, and ZeRO-3 shards the parameters themselves; each dashed outline marks the replicated stack a stage no longer holds. ZeRO-3 achieves linear memory scaling, enabling models with 100B+ parameters to fit on accelerators that could not hold the replicated state.

^fig-zero-memory

| **Stage**       |  **What is sharded**  |    **Memory reduction**    |              **Communication overhead**              |
|:----------------|:---------------------:|:--------------------------:|:----------------------------------------------------:|
| **ZeRO-1**      | Optimizer states only |         ~4$\times$         |  Reduce to owner + AllGather ($1\times$ DDP volume)  |
| **ZeRO-2**      |     \+ Gradients      |         ~8$\times$         |   ReduceScatter + AllGather ($1\times$ DDP volume)   |
| **ZeRO-3/FSDP** |     \+ Parameters     | ~${N}$ (linear in workers) | AllGather before each layer ($1.5\times$ DDP volume) |

Table 3: **ZeRO Sharding Stages**: Each stage shards a different layer of training state and trades a different communication primitive. ZeRO-1 and ZeRO-2 both replace the gradient AllReduce with a reduction to each shard’s owner and a parameter AllGather, matching DDP volume, and differ only in whether each worker keeps a full-size gradient buffer; ZeRO-3 (FSDP) adds per-layer AllGathers during forward and backward passes, unlocking near-linear memory scaling at $1.5\times$ communication.

^tbl-zero-stages

The first step, ZeRO-1, shards optimizer states across GPUs so each GPU stores only $1/{N}$ of the Adam optimizer-related state. During backpropagation, each worker still materializes the full 2 bytes/param gradient buffer locally, which is why gradient memory remains unsharded in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^tbl-zero-stages|table 3]]. Once gradients are ready, however, they need only be reduced to the worker responsible for each parameter shard via a ReduceScatter, and after each worker updates its owned shard, an AllGather broadcasts the updated parameters to restore the full replicas. This two-phase schedule (one gradient ReduceScatter plus one parameter AllGather) matches the table’s $1\times$ baseline communication volume, whereas running a full gradient AllReduce followed by a parameter AllGather would add 50 percent more traffic. Under the 12-byte convention that counts FP32 master weights, momentum, and variance, sharding the optimizer state reduces cluster-wide storage from $12{N}$ bytes/param to $12$ bytes/param in total, split evenly across the GPUs.

Building on that owner-update contract, ZeRO-2 eliminates persistent full-model gradient buffers by streaming the ReduceScatter during the backward pass. As each layer or communication bucket finishes its backward computation, workers immediately ReduceScatter that bucket’s gradients and free the slices owned by other ranks, leaving each GPU with only its $1/{N}$ persistent shard of reduced gradients. Each worker then updates its $1/{N}$ parameter partition using the corresponding optimizer state, and an AllGather restores the updated parameter replicas. In the ideal ring accounting, the gradient ReduceScatter and the parameter AllGather each transfer ${P}({N}-1)/{N}$ elements per worker, for $2{P}({N}-1)/{N}$ across both phases, matching DDP’s byte volume ($1\times$) when gradient and parameter communication widths match. Replicated parameters avoid forward parameter gathers, although model operations may still communicate. Under the FP16-gradient convention, persistent gradient storage falls from $2{N}$ bytes per parameter across ${N}$ workers to $2$ bytes per parameter in total, or $2/{N}$ per GPU, apart from transient bucket buffers.

The reductions in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^tbl-zero-stages|table 3]] count memory per GPU rather than across the cluster. They are large-worker limits, in which the replicated FP16 weights and gradients remain on each GPU under ZeRO-1 and only the FP16 weights remain under ZeRO-2.

At the deepest stage, ZeRO-3 and FSDP partition the parameters as well, leaving each GPU with a $1/{N}$ persistent slice of all three training states. Because workers no longer hold full parameter replicas between steps, the post-update parameter AllGather disappears and is replaced by two on-demand parameter AllGathers during computation. Each sharded unit gathers its parameters before the forward pass and immediately releases the non-local slices, then gathers them a second time before the backward pass and releases them again once local gradients are computed, and finally runs a ReduceScatter to deliver the completed gradients to each shard’s owner for the local optimizer update. Across four ranks ([[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^fig-zero-partitioning|figure 7]]) and under matching communication widths, ZeRO-1 (${M_{\text{optimizer}}}/4$) and ZeRO-2 (${M_{\text{optimizer}}}/4, {M_{\text{gradients}}}/4$) each execute two collective phases per step and retain the baseline $1\times$ communication volume. ZeRO-3 (${M_{\text{weights}}}/4, {M_{\text{gradients}}}/4, {M_{\text{optimizer}}}/4$) executes three collective phases of one parameter-equivalent payload each (forward AllGather, backward AllGather, and gradient ReduceScatter), which yields $3/2 = 1.5\times$ the baseline two-phase volume in this accounting.

![[90 Assets/Volume II/06 Distributed Training/Zero Partitioning 518e46e2df.svg]]

Figure 7: **ZeRO State Partitioning across GPU Ranks**: Which copy of each training state every GPU holds, for 4 workers. A filled full-width tile is a replicated copy; a quarter-width segment inside a dashed outline is that GPU’s shard, stepping one quarter per rank. ZeRO-1 shards optimizer state (${M_{\text{optimizer}}}/4$), ZeRO-2 adds gradients (${M_{\text{gradients}}}/4$), and ZeRO-3 shards parameters too (${M_{\text{weights}}}/4$). The footers give per-worker communication volume relative to DDP: only ZeRO-3 pays more, for the parameter AllGathers.

^fig-zero-partitioning

Full sharding adds parameter-readiness dependencies that replicated DDP avoids. With one sharding unit per layer, the forward pass needs an AllGather to reconstruct parameters (${M_{\text{layer}}}$ bytes). Resharding after forward requires another gather before backward (${M_{\text{layer}}}$ bytes), followed by a ReduceScatter for gradients (${M_{\text{layer}}}$ bytes under equal communication precision). For a model with ${N_L}$ layers, this schedule performs about $3{N_L}$ collective operations per step. DDP instead AllReduces gradient buckets as they become ready. At large worker counts, the ideal per-worker transfer volumes approach $3{M_{\text{param}}}$ bytes versus $2{M_{\text{param}}}$ for DDP. Here ${M_{\text{param}}}$ is the model’s parameter bytes at the communication precision, not full training state, and it equals ${M_{\text{grad}}}$ when parameters and gradients travel at the same width. These volumes do not determine elapsed time alone. While layer ${\ell}$ computes, layer ${\ell}+1$ can prefetch parameters, subject to memory headroom and fabric contention.

The allocation lifetimes in [[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^fig-fsdp-parameter-lifetime|figure 8]] separate persistent ownership from the temporary buffers needed to execute one sharding unit.

![[90 Assets/Volume II/06 Distributed Training/Fsdp Parameter Lifetime 48670dd741.svg]]

Figure 8: **FSDP Parameter Lifetimes**: One rank executes a sharding unit under a policy that reshards parameters after forward computation. Gathered parameters disappear between forward and backward, while saved activations remain until backward consumes them. Dashed cells show optional prefetch of another unit; these allocations can coexist with the current unit. The cells describe logical lifetimes, not byte totals or operation durations. Implementations may alias shard storage or reuse buffers.

^fig-fsdp-parameter-lifetime

A model fits only when all simultaneously live allocations fit. The persistent shards therefore establish a floor, while gathered units, saved activations, and prefetch determine how far the execution peak rises above it.

The choice between FSDP and DDP begins with peak memory. If replicated state, activations, and working buffers fit, DDP avoids repeated parameter gathers. When optimizer and gradient storage are the obstacle, ZeRO-2 offers savings while leaving parameters replicated. If parameters themselves do not fit, ZeRO-3/FSDP, offload, or partitioned computation must address that remaining constraint. For a 70B+ model on 80 GB devices, the need for tensor parallelism depends on the gathered layer size, activation budget, and throughput target; parameter count alone does not decide it.

Memory-efficient data parallelism requires careful tuning of sharding strategy (by layer, by transformer block, or flat) and mixed precision settings. Finer sharding reduces per-GPU memory but increases communication frequency, because more AllGather and ReduceScatter operations must execute per training step. Replicated or sharded, a data-parallel design earns its added workers only when they turn into faster progress toward target quality, and scaling efficiency measures that conversion.
