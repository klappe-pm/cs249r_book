# V2-08.18 Footnotes

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08 Fleet Orchestration|V2-08 Fleet Orchestration]]

^footnotes

<sup>1</sup> **Gang scheduling**: Formalized by Ousterhout ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.17 Source References#^ref-ousterhout1982scheduling|1982]]) for parallel systems, where the “Ousterhout matrix” co-schedules related threads across processors in synchronized time slices. In a rigid ML training group, incomplete allocation prevents collective completion, so held resources can remain idle until the missing ranks launch.

^fn1

<sup>2</sup> **Placement group**: A cloud-native abstraction that requests instances be placed within a high-bandwidth, low-latency network domain. For the ML Fleet, placement groups reduce placement scatter and may expose higher network limits than unconstrained placement. They do not guarantee workload-level bisection bandwidth: topology oversubscription, concurrent traffic, routing, and the collective pattern still determine delivered AllReduce bandwidth.

^fn2

<sup>3</sup> **Bin packing**: First-fit decreasing has a classical asymptotic $11/9$ approximation ratio for one-dimensional bin packing, with an additive constant in the finite-instance bound. That result does not guarantee the same ratio for ML placement with several resource dimensions, topology constraints, and indivisible gangs. A scheduler must evaluate its heuristic against feasible placements and the stranded capacity it leaves.

^fn3

<sup>4</sup> **Hold-and-wait**: One of the four Coffman conditions (mutual exclusion, hold-and-wait, no preemption, and circular wait), all of which must hold for deadlock to occur ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.17 Source References#^ref-coffman1971|Coffman et al. 1971]]). Gang scheduling removes hold-and-wait through atomic allocation, which is why it prevents this deadlock by construction; the price is reduced packing flexibility.

^fn4

<sup>5</sup> **Slurm Workload Manager**: Originally “SLURM,” an acronym for Simple Linux Utility for Resource Management, the project dropped the acronym capitalization in 2012. Developed at Lawrence Livermore National Laboratory beginning in 2002, Slurm’s centralized controller (`slurmctld`) maintains a single authoritative view of resource allocations. At very large scale, operators may partition fleets or federate schedulers to keep scheduling latency, policy isolation, and failure domains manageable.

^fn5

<sup>6</sup> **Controller pattern (reconciliation loop)**: A “level-triggered” design reconciles the current desired and observed states rather than depending on every intermediate event. A restarted controller can resume from durable state if its actions tolerate retries and its observations expose unfinished work. Multiple controllers still need distinct responsibilities so that one controller’s correction does not repeatedly undo another’s.

^fn6

<sup>7</sup> **Volcano**: Volcano provides a scheduler with batch and gang-scheduling mechanisms. Pods select it through their scheduler name, so it can coexist with Kubernetes’ default scheduler. The operational contract must account for interactions between schedulers sharing the same nodes; installing Volcano does not automatically transfer every workload’s scheduling to it.

^fn7

<sup>8</sup> **Kueue**: Kueue separates workload admission from pod placement. Its all-or-nothing mechanisms include waiting for admitted pods to become ready and requeuing workloads that exceed the configured timeout. Aggregate quota admission alone does not prove that a gang fits the physical topology; the guarantee depends on the configured readiness, topology, and placement mechanisms.

^fn8

<sup>9</sup> **Taints and tolerations**: Node taints can block scheduling of pods without matching tolerations. A toleration permits consideration of a node but neither requires placement there nor reserves it exclusively for training. Dedicated GPU pools also need controlled toleration assignment and placement constraints; removing existing workloads requires an eviction or drain policy appropriate to the taint’s effect.

^fn9

<sup>10</sup> **Spot instances**: The scenario’s 60 to 90 percent discount purchases reclaimable capacity, not a guaranteed interval for saving state. AWS’s best-effort stop or termination notice targets 2 minutes, while GCP preemptible shutdown allows up to 30 seconds; AWS hibernation begins immediately. If a job’s measured checkpoint time exceeds the reference 30-second window, a notice-triggered save cannot be its only recovery path.

^fn10

<sup>11</sup> **Attained service scheduling**: A discipline that uses consumed service to set priority when remaining work is unknown. Unlike shortest remaining processing time (SRPT), it cannot distinguish a newly arrived long job from a short one before either receives service. Its benefit depends on the workload distribution; protection against starvation remains necessary when new jobs repeatedly displace older ones.

^fn11

<sup>12</sup> **Noisy neighbor**: In GPU clusters, interference arises when one job’s bursty network traffic or memory bus utilization slows down a co-located job on the same node. In synchronous training, a delayed flow can extend collective completion when it lies on the communication critical path, propagating one tenant’s interference across a worker group.

^fn12

<sup>13</sup> **Multi-Instance GPU (MIG)**: Introduced with the A100 (2020), MIG partitions a single GPU into up to 7 hardware-isolated instances with dedicated memory controllers, L2 cache slices, and compute units ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.17 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020]]). The isolation is enforced at the hardware level, not by time-slicing, reducing noisy-neighbor interference relative to software-only sharing. Changing the partition layout requires stopping affected GPU workloads; the scheduler must include that disruption when adapting profiles to a changing workload mix.

^fn13

<sup>14</sup> **CUDA MPS (Multi-Process Service)**: The shared-resource mode used in this example does not reserve an independent hardware slice for each client, and a deployment must also account for the GPU fault domain its clients share ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.17 Source References#^ref-nvidiaCudaMps|NVIDIA 2026]]).

^fn14
