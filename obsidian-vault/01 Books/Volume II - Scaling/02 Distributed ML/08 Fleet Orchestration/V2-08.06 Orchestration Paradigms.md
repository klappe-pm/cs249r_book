# V2-08.06 Orchestration Paradigms

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08 Fleet Orchestration|V2-08 Fleet Orchestration]]

^sec-fleet-orchestration-paradigms

A pending gang and a queue of small backfill jobs need both a policy for sharing capacity and a control plane that can enforce it. The policies just developed apply across platforms; the orchestration paradigm determines how the platform represents allocations and recovers when observed state diverges from them. Slurm, shaped by HPC batch systems, favors explicit resource requests and predictable allocation. Kubernetes, shaped by cloud-native service management, favors declared desired state and continuous reconciliation. The choice is therefore not Slurm vs. Kubernetes as products; it is which control model best matches the workload mix, failure behavior, and operational culture of the fleet.

The two platforms embody two control models ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.06 Orchestration Paradigms#^fig-fleet-orchestration-slurm-vs-k8s|figure 6]]). Slurm follows an imperative batch model, in which the user states the resources a job needs and the central slurmctld dispatches that allocation through per-node slurmd daemons. Kubernetes follows a declarative model, in which the user states what should be running and controllers reconcile observed state toward that declaration through the API server and node agents. Both platforms accept explicit resource requirements and track execution state, so the useful distinction is which lifecycle the platform manages directly: an allocated batch job or a collection of workloads maintained by controllers. That distinction shapes how ML workloads are admitted, monitored, and recovered from failure, and distributed training still needs framework-level coordination under either model.

![[90 Assets/Volume II/08 Fleet Orchestration/Slurm Vs Kubernetes 88c843ed44.svg]]

Figure 6: **Architectural Paradigms: Slurm vs. Kubernetes**: Slurm (left) uses an imperative batch model where users submit explicit resource requests to a centralized controller (`slurmctld`) providing deterministic atomic allocation. Kubernetes (right) uses a declarative service model where controllers continuously reconcile observed cluster state in `etcd` against desired state specifications.

### Slurm and HPC Scheduling Heritage

^sec-fleet-orchestration-slurm

When a multi-node job needs an exclusive, non-overlapping block of accelerators for days at a time without partial-allocation deadlocks or conflicting node ownership, a centralized batch allocator is the most direct control plane. The Slurm Workload Manager[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.18 Footnotes#^fn5|⁵]] originated at Lawrence Livermore National Laboratory to solve that problem for Linux supercomputers ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.17 Source References#^ref-yoo2003|Yoo et al. 2003]]): long-running jobs, expensive shared hardware, and users who can specify resource needs in advance. In ML infrastructure, the same batch model maps to GPU training through partitions for heterogeneous accelerator pools and predictable atomic allocations for long-running distributed jobs.

Slurm’s batch submission model makes resource requirements explicit. Users submit job scripts, and the scheduler allocates resources within eligible partitions according to policy and availability. A submission of `sbatch --gres=gpu:8 --nodes=4` requests 8 GPUs on each of 4 nodes, a 32-GPU allocation. The request supplies a capacity contract, but useful execution still depends on the selected hardware and the application’s launch configuration. Overstating requirements strands resources; understating them can cause memory failures or poor performance.

Slurm’s architecture consists of a central controller daemon (`slurmctld`) that maintains the global view of cluster state and makes scheduling decisions, and per-node daemons (`slurmd`) that manage local resources and execute jobs. This centralized architecture provides the authoritative allocation model discussed in [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.03 Distributed Scheduling Complexity#^sec-fleet-orchestration-distributed-scheduling|section 8.2]]: the controller is the source of truth for resource assignments, reducing the risk of conflicting allocations. The cost is a potential single point of failure (addressed through active-passive failover) and a scheduling-throughput limit. As fleets grow, organizations may partition the cluster or federate schedulers to bound scheduling latency and failure impact; within a cluster, a typical ML configuration defines Slurm partitions by accelerator type and interconnect ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.06 Orchestration Paradigms#^tbl-fleet-orchestration-slurm-partitions|table 2]]).

| **Partition** | **GPUs/node**  | **Interconnect** |  **Typical use**   |
|:--------------|:--------------:|:----------------:|:------------------:|
| **dgx-a100**  | 8$\times$ A100 | NVLink + IB NDR  | Large LLM training |
| **a100-pcie** | 4$\times$ A100 |  PCIe + IB HDR   |  Medium training   |
| **inference** | 2$\times$ A10G |     Ethernet     |   Model serving    |
| **debug**     | 1$\times$ V100 |     Ethernet     |    Development     |

Table 2: **Slurm Partition Configuration**: Partitions organize heterogeneous accelerators into logical pools matched to workload characteristics. NVLink-connected partitions support tensor parallelism, while PCIe partitions serve workloads that rely primarily on data parallelism. Separating inference and debug partitions prevents experimental workloads from impacting production serving.

^tbl-fleet-orchestration-slurm-partitions

Within a partition, a request specifies both the number of GPUs a job needs and the **allocation shape**: how those GPUs are distributed across nodes. In Slurm, `--gres=gpu:N` or `--gpus-per-node=N` requests a per-node count, while `--gpus=N` requests a job-wide total. Whether the scheduler may split a node between jobs is a separate consumable-resource policy (Slurm’s `select/cons_tres` plugin), and a node-exclusive policy strands the unused devices in the six-on-eight example of [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.05 Core Allocation Constraints#^sec-fleet-orchestration-bin-packing|section 8.4.2]]. Shape decides communication. In an eight-GPU-per-node pool, a 16-GPU request that also fixes eight GPUs per node (`--gpus-per-node=8`) yields two fully populated nodes, whose NVLink domains follow from the node hardware rather than the count. A request for 16 GPUs with no per-node constraint gives the scheduler more freedom, so it can start sooner on partially occupied nodes, but it may spread the group across several of them. Whether that flexibility is useful depends on the parallelism configuration and its communication budget. Tensor-parallel groups with frequent exchanges may justify compact placement, while data-parallel groups with well-overlapped communication may tolerate a wider allocation.

The **fair-share scheduling** mechanism uses past consumption to influence future priority under contention. An illustrative heuristic combines base priority, the user’s target fair share (${F_{\text{target}}}$), recent actual consumption (${F_{\text{actual}}}$), and a small stabilizing constant (${\epsilon_{\text{stab}}}$); it illustrates the feedback without reproducing Slurm’s multifactor priority calculation:

$$
\text{Priority}_{\text{effective}} = \text{Priority}_{\text{base}} \times \frac{{F_{\text{target}}}}{{F_{\text{actual}}}+ {\epsilon_{\text{stab}}}} \tag{1}
$$

^eq-fleet-orchestration-fair-share

With base priority and target share fixed, [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.06 Orchestration Paradigms#^eq-fleet-orchestration-fair-share|equation 1]] lowers priority as recent consumption increases. Doubling consumption approximately halves this illustrative priority when the stabilizing constant is negligible. Actual admission also depends on other priority factors and feasible resources; low recent usage does not guarantee an immediate start.

The time decay of usage history determines how quickly the system “forgives” past heavy usage. A half-life of one week means that a researcher’s heavy usage from two weeks ago contributes only 25 percent to their current usage calculation. Short half-lives make the policy more responsive to recent changes but can encourage alternating bursts of usage. Long half-lives retain the effect of a completed large project when its researchers return with smaller jobs. The useful decay window depends on the fleet’s job durations and the period over which the organization intends to balance access. Usage itself need not count every device alike. **Trackable resources (TRES)** let accounting charge different accelerator classes different billing weights in fair-share usage, an administrative valuation that tracks economic cost only as far as the chosen weights do.

Preemption policies enable high-priority jobs to reclaim resources from running workloads, and for ML training the reclaim must leave time to save state. Slurm expresses that time as a grace period. It signals the selected job (`SIGTERM`), waits the configured `GraceTime`, and only then kills it (`SIGKILL`); under `PreemptMode=REQUEUE` it can also requeue an eligible job to run again later. Neither the signal nor the requeue saves model state. The application must handle the signal, publish a valid checkpoint within the grace period, and restore it on restart. If termination precedes completion of that save, recovery uses the last valid checkpoint and replays subsequent work. Preemption therefore buys access for high-priority work with the victim’s replay and restart time, a price that [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.09 Cost Optimization#^sec-fleet-orchestration-preemption-cascades|section 8.8.1]] develops.

↩︎ Checkpointing for progress preservation, including the checkpoint interval and coordination patterns, is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-reliability-reliability-checkpoint-restart-fundamentals-0ac2|Checkpointing and Progress Preservation]]**.

Several Slurm features expose ML structure to the batch system. A hyperparameter sweep is the opposite of a gang. Job arrays submit many trials as one record (for example, `--array=0-99`), and each trial reads its index from the `SLURM_ARRAY_TASK_ID` environment variable to select its configuration. Slurm schedules the elements independently, so individual trials become ideal backfill candidates that fill small gaps in capacity, while the array keeps submission and management overhead low without making the trials one indivisible gang.

Heterogeneous jobs carry the heterogeneous gang of [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.05 Core Allocation Constraints#^sec-fleet-orchestration-heterogeneous-gang|section 8.4.5]] into a batch allocation. One job can contain components with distinct resource requests, admitted together. The 64-GPU fine-tuning run of the 175B model, for example, could request 8 GPU nodes for training and 2 CPU-only nodes for on-the-fly tokenization as a single allocation. It could then launch training on the GPU component and data workers on the CPU component (`srun --het-group=0` and `--het-group=1`). This separation helps only if the data workers and transfer path sustain the training stage’s consumption rate; a heterogeneous allocation exposes that choice but does not itself balance the pipeline.

At the boundaries of each allocation, prolog and epilog scripts turn job transitions into health checks. A prolog tests reported topology, ECC counters, and link status on each allocated node and drains a failing node before launch. An epilog removes the job’s orphan processes and shared-memory segments. Draining a failing node this way applies the quarantine practice of [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.07 Topology-Aware Scheduling#^sec-fleet-orchestration-topology-discovery|section 8.6.4]] at job boundaries, keeping sensitive work off a node whose health evidence shows degradation. Passing the prolog reduces exposure to known faults but does not establish the bandwidth the job will receive.

Slurm’s strengths for ML training include explicit batch allocations, configurable fair-share policies, and integration with MPI-based distributed training frameworks. A mixed training-serving fleet also needs a service lifecycle that maintains ready replicas as demand and failures change. Inside a batch scheduler, adding or removing an inference replica means submitting or canceling a job, a far heavier operation than a controller adjusting a replica count, and a failed replica stays down until something resubmits it. Operators must integrate replica health, replacement, and demand-driven scaling with the batch scheduler, or assign those responsibilities to a service orchestration platform.

### Kubernetes Declarative Container Orchestration

^sec-fleet-orchestration-kubernetes

When a cluster runs always-on inference services alongside training jobs, managing serving replicas as batch scripts forces operators to rebuild health checks, rolling updates, and replica replacement by hand. Kubernetes addresses this mixed workload by managing both services and batch jobs through a **declarative model** that expresses a workload’s desired state and uses control loops to reconcile observations with that state ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.17 Source References#^ref-burns2016|Burns et al. 2016]]; [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.17 Source References#^ref-kubernetes-orchestration-fec67438|Cloud Native Computing Foundation 2024]]). The unit it places is the **pod**, one or more containers that share a node and a network identity, and its default scheduler places pods one at a time. The name collides with the hardware pod of **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.08 The Pod#^sec-compute-pod|The Pod]]**, the many racks joined under one fabric. A Kubernetes pod is a software unit that never spans more than one node, so a 64-pod training job is 64 container groups placed onto nodes, all of which can sit inside one hardware pod. Controllers above the scheduler give groups of pods a purpose: a Deployment keeps a set number of identical replica pods running, while a Job runs pods until they complete, retrying failures under a stated policy. The workload controller therefore determines what completion, replacement, or continued availability means.

Failure handling reveals the importance of the workload contract. Slurm can detect node failures and requeue eligible jobs when configured to do so. Kubernetes controllers maintain workload-specific goals, such as a Deployment’s replica count or a Job’s completion and retry policy. A replacement pod still has to be placed, become ready, and rejoin the distributed training run before progress resumes. Training operators can coordinate worker creation, while the framework remains responsible for valid state and group recovery. Both platforms therefore require an explicit agreement between allocation, process lifecycle, and application recovery.

Kubernetes’ control loop architecture uses the controller pattern:[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.18 Footnotes#^fn6|⁶]] controllers observe and update API objects through the API server, which persists cluster state in etcd, a replicated key-value store. Those objects contain desired state and reported observations, not instantaneous physical truth. The pattern repeats at every level: the Deployment controller reconciles the number of pod replicas, the scheduler binds pending pods to nodes, the kubelet (the agent on each node) keeps its assigned containers running, and the node controller marks nodes that stop reporting. Each component acts independently and communicates only through API objects, which makes the system resilient to the failure of any single controller. The price of that independence is that their interactions require clear ownership and retry behavior, particularly when a failed node’s last reported state no longer describes its execution.

Kubernetes needs an explicit resource representation before it can place GPU workloads. In the device-plugin model, **device plugins** expose accelerators as schedulable extended resources. The NVIDIA device plugin registers GPUs with the kubelet, enabling pod specifications that request GPU resources declaratively through the standard Kubernetes resource model. A pod then asks for whole GPUs by naming the `nvidia.com/gpu` resource in its limits ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.06 Orchestration Paradigms#^lst-fleet-orchestration-k8s-gpu|listing 1]]).

``` yaml
# Kubernetes pod resource specification for GPU allocation
resources:
  limits:
    nvidia.com/gpu: 4  # Request exactly 4 GPUs for this pod
  requests:
    cpu: "32"
    memory: "256Gi"
```

Listing 1: **Kubernetes GPU Allocation**: Pod resource specification requesting GPUs through the NVIDIA device plugin. The `nvidia.com/gpu` resource name follows Kubernetes extended resource conventions, where the domain prefix identifies the device plugin vendor. This declarative syntax enables portable GPU workload definitions across any Kubernetes cluster with the NVIDIA device plugin installed.

^lst-fleet-orchestration-k8s-gpu

When the device plugin exposes exclusive whole GPUs, a small model serving occasional requests can reserve a device while using only a fraction of its compute and memory capacity. Whole-device allocation suits workloads that need the capacity or isolation, but can strand resources for smaller workloads. The resource unit exposed by the plugin therefore matters, because sharing or partitioning changes what the scheduler can allocate and what isolation each allocation receives. Device plugins can also expose hardware partitions, such as MIG instances, as schedulable units, a choice that [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.11 Serving Capacity in the Shared Fleet#^sec-fleet-orchestration-resource-isolation|section 8.10.1]] develops with the serving workloads it suits.

Kubernetes’ default scheduler places pods independently, so it does not supply the group admission that [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.05 Core Allocation Constraints#^sec-fleet-orchestration-gang-scheduling|section 8.4.3]] requires. Under that default, a 64-pod training job receives 64 separate placement decisions, with no guarantee that all will succeed. If the cluster has resources for 60 pods but not 64, those 60 can occupy capacity while the remaining 4 wait. The platform must therefore configure a group-level admission and placement contract for a rigid job.

The mechanism that closes this gap is group admission. A **PodGroup** declares a group’s minimum runnable membership. The scheduler tentatively reserves a placement for each member as it finds one but binds none of them to nodes until the minimum membership is placed, and it releases every reservation if the attempt fails or times out. Admission and placement thereby become two decisions, with the group admitted only when placement has succeeded for enough of it. The Volcano[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.18 Footnotes#^fn7|⁷]] batch scheduler and the Coscheduling scheduler plugin both implement this pattern. Group admission does not make physical launches simultaneous; nodes can still fail or start at different times, so the framework must establish the communication group before training proceeds.

**War Story 8.1: OpenAI's gang-scheduling example (2021)**

**Context**: OpenAI scaled Kubernetes clusters to 7,500 nodes for workloads including GPT-3, CLIP, and DALL-E. Its account explains that MPI-coordinated optimizer groups needed all members scheduled before training could progress ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.17 Source References#^ref-sigler2021openai-kubernetes-c906164d|Sigler 2021]]).

**Mechanism**: The account illustrates the risk with two experiments each requesting the entire cluster. Incremental pod placement could allocate half the capacity to each, leaving neither with a complete group.

**Impact**: In that example, both jobs hold capacity without making progress. It demonstrates the deadlock mechanism rather than documenting a particular pair of stalled production runs.

**Fix**: OpenAI reports adopting the coscheduling plugin to add group-aware admission to the Kubernetes scheduler.

**Systems lesson**: Distributed ML scheduling must encode the job’s execution semantics. For MPI-style training, “some pods scheduled” is not partial progress; it is wasted allocation. Production schedulers need gang scheduling, quota controls, and workload-aware policies rather than generic pod placement alone.

Priority classes control scheduling precedence and preemption eligibility. A fleet might give inference higher priority than training to help protect serving service-level objectives (SLOs), but priority cannot replace ready capacity during a demand spike. With `preemptionPolicy: PreemptLowerPriority`, a pending pod can displace lower-priority pods when their removal makes placement feasible. With `preemptionPolicy: Never`, it retains queue precedence without initiating preemption and remains subject to higher-priority preemption. Termination, cleanup, and replacement startup take time. Training applications also need a checkpoint-aware shutdown path that fits the allowed grace period; assigning priorities does not create that path. The policy must balance serving readiness against repeated interruption of training.

Kueue[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.18 Footnotes#^fn8|⁸]] makes admission a separate control decision. It manages when workloads may consume quota, while a compatible scheduler binds their pods to nodes. The admission policy and placement policy must agree on resource types, group requirements, and topology. Separating these responsibilities lets each layer run its own policy, at the price of keeping the two consistent. Kueue represents each team or project as a queue with a configured quota (a ClusterQueue) and groups queues into cohorts whose members may lend one another unused quota, under the borrowing and reclaim contract of [[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.12 Multi-Tenancy and Quotas#^sec-fleet-orchestration-burst-capacity|section 8.11.2]].

### Kubernetes Ecosystem for ML Training

^sec-fleet-orchestration-k8s-ecosystem

Group admission handles one constraint that microservice orchestration can leave implicit but distributed training cannot. Four other such constraints remain. Workers must launch knowing their peers, collective traffic must avoid network layers built for request traffic, checkpoint writes need bandwidth rather than only storage capacity, and progress must be observable below the container. Operators and plugins add each constraint to the platform; the mechanism matters more than the product that happens to implement it.

Peer discovery is the job of the **training operator ecosystem**, which extends Kubernetes with job-specific resource types (custom resource definitions). In the Kubeflow Training Operator, a `PyTorchJob` declares the number of workers, the container image, and resource requirements. The operator creates the pods and injects the rendezvous address (`MASTER_ADDR` and `MASTER_PORT`), the group size, and each worker’s rank (`WORLD_SIZE` and `RANK`), which the framework uses to form its communication group. If a worker pod fails, the operator can detect the deviation and create a replacement pod to restore the desired replica count, but training-state recovery still depends on the framework’s checkpoint and rendezvous logic.

Collective traffic is the second constraint. The pod overlay network that the Container Network Interface (CNI) configures, designed for microservice requests, routes packets through software switching on the host CPU, which adds latency and caps bandwidth when it sits on the critical gradient-synchronization path. For bandwidth-sensitive training, **host networking** (`hostNetwork: true`) places pods in the host’s network namespace, bypassing the ordinary pod overlay path. It does not itself allocate remote direct memory access (RDMA) devices or grant permission to use them; device exposure, resource requests, drivers, and access controls require separate configuration. Operators such as NVIDIA’s Network Operator automate that exposure through RDMA device plugins and GPUDirect RDMA configuration, letting containerized workloads approach bare-metal interconnect performance once the rest of the stack is configured.

Checkpoint bandwidth is the third constraint, because storage integration must account for the checkpoint storm of definition [4.5](https://mlsysbook.ai/vol2/04_data_storage/04_data_storage.html#dfn-data-storage-checkpoint-storm), in which many workers write large amounts of state together. Kubernetes PersistentVolumeClaims (PVCs) request capacity on a configured storage system but do not reserve checkpoint throughput. A 1,024-GPU training job writing the 2.45 TB resumable checkpoint of the 175B model needs a measured write budget shared with other workloads. Backend bandwidth controls, client throttling, or staggered writes can limit interference; the platform must verify which controls the storage implementation enforces.

Visibility into progress is the fourth. The **observability stack** for training clusters combines general-purpose cluster monitoring (commonly Prometheus and Grafana) with accelerator telemetry such as the Data Center GPU Manager (DCGM) exporter, which reports utilization, memory bandwidth, temperature, and ECC errors. These observations locate symptoms. Correlating them with step progress, input waits, and communication traces is what distinguishes useful computation from stalls and identifies which dependency limits a training job.

↪ Fleet telemetry across device, network, and facility levels, and the correlation that narrows a failure domain, is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.07 Monitoring at Scale#^sec-ops-scale-fleet-telemetry|Fleet telemetry and hardware observability]]**.

The 1,024-GPU pretraining run for our 175B model illustrates how these responsibilities fit together. One possible deployment defines a `PyTorchJob` with 128 worker pods, each requesting 8 GPUs. Host networking removes the pod overlay from the gradient path, and the Network Operator exposes each node’s InfiniBand adapters to the workers through RDMA device plugins. A PVC backed by Lustre, a parallel file system, provides access to the 6 TB tokenized training corpus and a checkpoint path whose sustained bandwidth must be validated. DCGM metrics stream to Prometheus, supporting alerts on uncorrectable ECC errors and deviations from workload-specific communication baselines.

### Paradigm Trade-Offs and Selection Criteria

^sec-fleet-orchestration-paradigm-choice

Selecting a control plane requires matching its allocation and recovery contract to the workload mix. Rigid training groups need reliable atomic placement and checkpoint-aware interruption; serving replicas need readiness checks and continuous recovery. Existing operational expertise and the cost of running a second control plane also shape the choice. A fleet dedicated to long, homogeneous training runs that use bare-metal collectives, operated by a team fluent in batch scheduling, gains most from Slurm’s authoritative allocation and mature fair-share. A fleet that mixes training with always-on serving, and already runs cloud-native deployment and observability tooling, gains more from Kubernetes with a gang-admission layer added for its rigid jobs. The Slurm vs. Kubernetes trade-off organizes around the dimensions most relevant to ML workloads ([[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.06 Orchestration Paradigms#^tbl-fleet-orchestration-paradigm-comparison|table 3]]).

| **Dimension**                    | **Slurm**                                                                                                   | **Kubernetes**                                                                                                                  |
|:---------------------------------|:------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------|
| **Scheduling model**             | Imperative: user specifies exact resources and scheduler allocates them                                     | Declarative: user specifies desired state, system reconciles continuously                                                       |
| **Failure handling**             | Configuration-dependent requeue and checkpoint workflows                                                    | Self-healing through control loops                                                                                              |
| **Gang/atomic multi-node start** | Atomic job allocation plus backfill; Slurm “gang scheduling” specifically refers to time-slicing/preemption | Production clusters commonly use PodGroup-based support such as Volcano, Coscheduling, Kueue, or upstream alpha gang scheduling |
| **Fair-share**                   | Mature multi-factor priority with configurable decay                                                        | Kueue provides basic fair-share with ClusterQueue borrowing                                                                     |
| **Container overhead**           | None from a container runtime when jobs run directly on nodes                                               | Configuration-dependent networking overhead and container startup time                                                          |
| **Service management**           | No native support for long-running services                                                                 | Native Deployment, rolling updates, health checks                                                                               |
| **Ecosystem**                    | MPI, OpenMP, scientific computing libraries                                                                 | Cloud-native, microservices mesh, observability stack                                                                           |

Table 3: **Slurm vs. Kubernetes for ML Workloads**: The two paradigms reflect different design philosophies optimized for different workload characteristics. Most production ML platforms use elements of both, with Slurm managing dedicated training clusters and Kubernetes managing inference serving and pipeline orchestration.

^tbl-fleet-orchestration-paradigm-comparison

The gang-scheduling row of the table compresses a naming collision that is easy to miss. This chapter uses gang scheduling for atomic allocation of a whole execution group, which is the requirement distributed training imposes. Slurm reserves the name for the older, Ousterhout-style meaning of the term, in which co-scheduled jobs share nodes by time-slicing in synchronized rounds. Slurm provides atomic multi-node allocation under its ordinary job model, so the requirement is met even though Slurm’s “gang scheduling” option means something else.

The choice of scheduling paradigm also reflects organizational trajectory. Teams starting with HPC-focused training infrastructure may begin with Slurm and add Kubernetes for serving. Teams starting from cloud-native application infrastructure may begin with Kubernetes and add HPC-oriented extensions (Volcano, Kueue) for training. Slurm has meanwhile added a REST interface and container support, so the two platforms now overlap in capability. Either path can reach a functional hybrid architecture, but the starting point determines which capabilities are strongest and which require the most investment to develop.

### Hybrid Architectures in Practice

^sec-fleet-orchestration-hybrid-architectures

While the choice between Slurm and Kubernetes often appears binary, engineering organizations can deploy **hybrid architectures** that use the strengths of both systems. The relevant boundary again follows workload semantics rather than labels. Rigid, topology-sensitive jobs fit a batch scheduler’s atomic allocation contract, while malleable services fit a reconciliation loop that adjusts replica count continuously. Some training jobs are elastic, and some serving replicas are rigid multi-accelerator gangs, so neither “training” nor “serving” selects a control plane by itself.

The **Kubernetes-over-Slurm** pattern wraps the HPC scheduler within a cloud-native control plane. Kubernetes manages the lifecycle of training jobs through custom operators while delegating batch admission and placement to Slurm. The central engineering problem is ownership: exactly one control plane must authorize each placement, while the outer controller reconciles lifecycle state without issuing a conflicting allocation. The arrangement combines a declarative management surface with Slurm’s batch and topology policies, but it also creates a cross-control-plane failure boundary that operators must fence explicitly.

The **Slurm-alongside-Kubernetes** pattern takes a coarser-grained approach, maintaining separate clusters for training and serving that draw from a shared pool of physical nodes. A meta-scheduler or capacity broker acts as an arbitrator, dynamically reassigning nodes between the Slurm partition and the Kubernetes cluster based on demand signals. During intensive training campaigns, nodes are drained from Kubernetes and joined to Slurm; during product launches or traffic spikes, the flow reverses. The primary challenge is the mode-switching cost: draining a node, changing its ownership and configuration, and admitting it to the other control plane takes much longer than an ordinary placement decision. This latency limits sharing to planned capacity shifts rather than second-by-second inference bursts.

A shared application runtime such as Ray runs both training and serving through two abstractions, tasks (stateless function calls executed on remote workers) and actors (long-lived processes that keep state between calls). Ray’s placement groups, unlike the cloud network-locality abstraction of the same name, reserve bundles of logical resources for work that must run together, and serving replicas can also require multi-device groups. Inside a shared runtime the workloads keep their different state, latency, and recovery requirements, so the platform must still coordinate Ray’s logical allocations with the underlying resource manager and validate the isolation and recovery behavior needed by each workload.

Threading these patterns together, consider the lifecycle of our 175B parameter model. A hybrid platform can allocate the training gang through Slurm and later place serving replicas through Kubernetes. The orchestration boundary concerns resource ownership: the training job releases its allocation, and the serving control plane admits replicas against its own capacity and readiness requirements. Deciding whether the trained artifact is ready for production requires validation and release policy beyond the scheduler; **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ml-operations-scale-cicd-ml-scale-730a|CI/CD for ML at Scale]]** develops those validation checks and rollout policies.

A hybrid platform is useful when its separate allocation contracts justify the additional ownership and recovery boundary. The cost to measure is the coordination between control planes, including node draining and reassignment, rather than a presumed performance advantage from either product name. Because Slurm and Kubernetes now overlap in capability, the paradigm choice is a workload-specific design decision, and teams must establish the allocation and recovery guarantees they need before layering physical placement constraints on top of them.

**Checkpoint 8.1: Scheduling paradigm trade-offs**

Before the chapter turns to topology-aware placement, review the core trade-offs:

**Gang scheduling**: explain why a rigid synchronous execution group needs atomic allocation, and why the scheduler must still reserve capacity for a waiting gang that holds no GPUs itself.

**Slurm vs. Kubernetes**: compare authoritative allocation with desired-state reconciliation, and explain why either design must prevent duplicate ownership during a network partition.

**Group admission**: explain why a default scheduler that places pods one at a time can strand capacity for a 64-pod training job, and how a PodGroup’s minimum membership prevents it.

**Resource units**: explain how the resource unit a device plugin exposes changes what the scheduler can pack, and why a small model on an exclusively assigned GPU strands capacity.

**Backfill incentives**: explain why backfill scheduling depends on accurate job runtime estimates and why users have game-theoretic incentives to provide inaccurate estimates.

A control plane can now represent, admit, and reconcile an allocation, yet it still counts accelerators as if any group of the requested size were interchangeable. Two allocations of the same size can meet very different communication budgets depending on where the devices sit in the cluster fabric. The next layer of the scheduler must therefore weigh physical location alongside resource count.
