# V2-09.15 Footnotes

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09 Fleet Efficiency|V2-09 Fleet Efficiency]]

^footnotes

<sup>1</sup> **ML productivity goodput origin**: Google introduced the three-factor decomposition to measure its Tensor Processing Unit (TPU) fleet, calling it an iron law of performance for ML fleets by analogy with the processor iron law that splits execution time into instructions, cycles per instruction, and time per cycle ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-emer1984characterization|Emer and Clark 1984]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-wongpanich2025fleet|Wongpanich et al. 2025]]). The paper reports the factors across the whole fleet and segmented by job size and by workload phase, with real-time serving and bulk inference alongside training. The boundaries themselves name no accelerator, so this chapter applies them to any accelerator fleet, for serving replicas as well as training jobs.

^fn1

<sup>2</sup> **Effective training time**: Meta’s report defines it as the time spent on useful training over the elapsed time and states only that it exceeded 90 percent over a 54-day snapshot ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-dubey2024llama|Dubey et al. 2024]]). It is a per-job figure, so it says nothing about capacity the job never held, and the report does not say whether input waits count as useful. Its MFU comes from the scaling-configuration table rather than from that snapshot, which is why the measurement contract ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.04 Measuring Goodput#^sec-performance-engineering-measurement-contract|section 9.3.1]]) requires every factor to name its window.

^fn2

<sup>3</sup> **MFU and HFU**: The PaLM report proposed MFU in place of hardware FLOPs utilization (HFU), which counts every executed operation, because the executed count depends on implementation and compiler choices, most visibly rematerialization, which recomputes activations to save memory ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-chowdhery2022palm|Chowdhery et al. 2022]]). MFU’s reference rate depends only on the model architecture and the published peak rate, so runs of one model on different software stacks compare directly. For goodput accounting, the choice means that recomputation which lets a layout fit in memory is charged to program goodput as lost time rather than credited as work.

^fn3

<sup>4</sup> **MegaScale stragglers**: The heat map of per-rank forward and backward latency showed about 0.5 percent of machines running substantially slower than the rest, and excluding them made peak MFU consistent across runs ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-jiang2024megascale|Jiang et al. 2024]]). Separately, a few hosts took about 10 percent longer on the same forward computation, and removing them raised MFU by about 0.7 percent. A fraction of a percent of machines thus set the step time of every rank that synchronized with them, a program loss that only per-rank timing on every step could locate.

^fn4

<sup>5</sup> **Effective training time ratio (ETTR)**: Kokolis et al. ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-kokolis2025|2025]]) define a job’s ETTR as productive runtime over wallclock time, including time spent queued, and derive its expected value from the failure rate, checkpoint interval, checkpoint write cost, restart overhead, and queue time; they use it to estimate how much large jobs on Meta’s research clusters lose to failures. It is the closest published counterpart to this composition for the failure-driven terms. Because its denominator includes queueing, ETTR also spans part of scheduling goodput, so an ETTR and a runtime goodput for the same job are not directly comparable.

^fn5

<sup>6</sup> **MLPerf Training timing**: The rules as first published start the clock when the system first touches training or validation data, leave system initialization untimed, and exclude up to 20 minutes of model creation as well as one-time data reformatting ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-mattson2020mlperf|Mattson et al. 2020]]). Startup, compilation, and data preparation therefore never enter a benchmark’s time to train, although every production launch pays them in the startup term.

^fn6

<sup>7</sup> **MFU across Llama 3 configurations**: The report’s scaling table gives 43 percent BF16 MFU on 8,192 GPUs and 41 percent on 16,384 GPUs, with the same tensor and pipeline layout and twice the data parallelism ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-dubey2024llama|Dubey et al. 2024]]). The report attributes the drop to the smaller batch per data-parallel group needed to hold the global batch constant, so doubling the devices cost program goodput with no change to the model or its kernels.

^fn7

<sup>8</sup> **Relative gains and boundary order**: Raising one factor multiplies MPG by the ratio of its new value to its old one, whatever the other two factors are, so the ranking of levers at their ceilings does not depend on the order in which the boundaries are drawn. The loss shares of [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.03 ML Goodput#^eq-perf-goodput-loss-shares|equation 2]] do depend on that order, because each later factor’s loss is measured on what the earlier factors passed. A ranking by loss share can therefore differ from a ranking by relative gain, and only the second gives what a lever is worth.

^fn8

<sup>9</sup> **Persistent compilation caches**: JAX writes compiled executables to a persistent cache directory and keys each entry by the unoptimized program, the jaxlib version, the relevant compiler flags, and the device count and topology. PyTorch’s compiler keeps on-disk graph and kernel caches that later processes reuse, and it accepts an entry only for the same PyTorch and Triton versions and the same GPU. TensorRT serializes a built engine so that it can be reloaded, and by default the engine runs only on the GPU model and TensorRT version that built it. In all three frameworks the key is the tuple the text names, so an upgrade to the compiler or the accelerator turns every cached build into a new one.

^fn9
