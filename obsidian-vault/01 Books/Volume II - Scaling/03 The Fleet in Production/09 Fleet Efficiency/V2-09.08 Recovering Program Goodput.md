# V2-09.08 Recovering Program Goodput

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09 Fleet Efficiency|V2-09 Fleet Efficiency]]

^sec-performance-engineering-program-goodput

Tuning a single-device kernel when a step is bound by cross-node gradient reductions, or overlapping collectives when the step is bound by host kernel launches, leaves the critical path untouched. Recovering program goodput requires changing how a retained step executes, and an optimization helps only to the extent that it shortens an exposed term of the step. Three families of levers target distinct Fleet Law terms:

1.  **Compiler-derived partitioning** determines which collectives a step executes and across which physical links they travel (${T_{\text{comm}}}({N})$).
2.  **Communication overlap** hides a portion of those collectives behind independent computation, enlarging the overlap credit (${T_{\text{overlap}}}$).
3.  **Kernel-level optimizations** (fusion, tiling, graph replay, and compilation) compress single-device execution (${T_{\text{compute}}}/{N}$).

Because the speedup from any one lever depends on what the others leave exposed on the critical path, engineers apply these levers one at a time and re-measure the step after each change.

### Compiler-Derived Partitioning

^sec-performance-engineering-gspmd

A model whose tensor-parallel modules place AllReduce calls directly inside the forward and backward methods of each layer (**[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training#^sec-distributed-training-systems|Distributed Training]]**) cannot change how those layers are split, or move to a node topology that calls for a different split, without modifying the model code itself. A data-parallel wrapper adapts to a new device count on its own, but hand-partitioned layers do not. Because how a large training job is partitioned across devices determines most of the communication its step performs, tying that layout to hand-written layer code makes every layout change a code change. Compiler-derived partitioning, pioneered in the Accelerated Linear Algebra (XLA) compiler’s GSPMD partitioner ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-xu2021|Xu et al. 2021]]), shifts the derivation of tensor layouts and the insertion of collective operations from the model author to the compiler.

**Definition 9.5: Compiler-derived partitioning**

***Compiler-derived partitioning*** is the division of one program across a mesh of devices in which the programmer annotates how a few tensors are split along named mesh axes and the compiler derives the layout of every other tensor and inserts the collectives those layouts require.

1.  **Significance**: The inserted collectives are the step’s communication term, so the annotations and the mapping of mesh axes onto the fleet decide how much of each retained step a job spends communicating. Because the layout is stated apart from the model code, a different layout is a different set of annotations rather than a rewritten program.
2.  **Distinction**: Unlike programmer-specified parallelism, in which the engineer writes or selects each collective through a data-parallel wrapper or a hand-partitioned layer, compiler-derived partitioning leaves the engineer only the key annotations and derives the rest. The partitioning strategies themselves, data, tensor, and pipeline parallelism, are unchanged; what changes is who writes their communication.
3.  **Common pitfall**: A frequent mistake is to read the step’s communication from the annotations. Where derived layouts disagree, the compiler inserts resharding collectives that no line of the program names, so the step trace, not the source, is the record of what the step communicates.

Under this model, the engineer specifies only two inputs. The first is a logical device mesh whose axes carry symbolic names. For our running example, which uses tensor parallelism within each node and data parallelism across the 16 nodes, the mesh has a `model` axis of 8 devices and a `data` axis spanning the sixteen nodes. The second input is a small set of sharding annotations on key tensors, declaring which tensor dimension is partitioned along which mesh axis. The input batch dimension is split along the `data` axis. Within each feed-forward block, the gate and up projection weights (the two input matrices of the gated feed-forward layer, whose outputs the gated activation combines) are split column-wise along the `model` axis while the output projection weight is split row-wise. The attention projections are split by head along the `model` axis. Every other intermediate tensor in the program remains unannotated.

From those few seeds, the compiler derives the rest of the parallel program through sharding propagation, walking the computation graph to infer the output layout of each operator from the layouts of its inputs. Multiplying an input activation by a column-split weight matrix yields an activation split along its feature dimension; the subsequent element-wise gated activation preserves that layout without communication. Next, multiplying that feature-split activation by a row-split output weight produces a partial sum on each device, prompting the compiler to insert an AllReduce along the `model` axis to complete the projection. The backward pass mirrors this derivation. Each device’s weight gradients cover only its local shard along the `model` axis but represent partial sums across the `data` axis, so the compiler automatically inserts a cross-node gradient reduction along the `data` axis (or a ReduceScatter paired with a forward AllGather when optimizer state is sharded). The resulting communication schedule matches the hand-partitioned Megatron-style layer of **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-tensor-parallelism-d76e|Tensor parallelism]]**, yet it is synthesized automatically from single-device model code that contains no explicit collective calls ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.08 Recovering Program Goodput#^fig-performance-engineering-device-mesh|figure 8]]). Wherever two incompatible tensor layouts meet in the graph, propagation resolves the mismatch by inserting an AllGather, ReduceScatter, AllToAll, or point-to-point permutation.

^fig-performance-engineering-device-mesh

↩︎ Which strategies a training job combines, and the feasibility of each combination, are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.07 Hybrid Parallelism#^sec-distributed-training-systems-systems-hybrid-parallelism-12a0|Hybrid Parallelism]]**.

Every accelerator executes the same compiled binary, using its own mesh coordinates at runtime to index its local weight shard and select its collective peers—the single program, multiple data (SPMD) execution model from which GSPMD takes its name ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-xu2021|Xu et al. 2021]]). Because a single compilation serves all ranks, compilation time scales with the size of the model graph rather than the number of devices in the fleet. The collectives that propagation inserted are part of that compiled binary, so a stored artifact carries its communication schedule to every later job or replica that runs the same model, mesh, and annotations. Changing the mesh dimensions or sharding annotations still triggers a fresh compilation, whose runtime goodput cost is weighed against its program goodput gain in [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.10 Trading Between Factors#^sec-performance-engineering-compilation-overhead|section 9.9.3]].

Because the device mesh is a logical abstraction, the cluster scheduler’s physical placement determines which hardware links carry each mesh axis. When an eight-device `model` axis maps onto a single node, its per-layer AllReduce collectives traverse high-bandwidth NVLink; if that same axis is scattered across nodes, those identical collectives traverse the inter-node fabric at a fraction of the bandwidth. Three distinct mechanisms therefore govern a step’s communication cost: sharding annotations determine *which* collectives are synthesized, physical mesh placement determines *how fast* each collective runs, and stream scheduling determines *how much* of that duration remains exposed. In Fleet Law terms, compiler-derived partitioning sets ${T_{\text{comm}}}({N})$ and shapes the opportunity for ${T_{\text{overlap}}}$, while leaving single-device execution (${T_{\text{compute}}}/{N}$) to the kernel levers of [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.08 Recovering Program Goodput#^sec-performance-engineering-kernel-levers|section 9.7.3]].

Consequently, modifying a sharding annotation alters the step’s communication pattern without changing a single line of mathematical model code, and its effect must be verified under the measurement contract of [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.04 Measuring Goodput#^sec-performance-engineering-measurement-contract|section 9.3.1]]. The step trace provides the necessary audit: counting the collectives in one step by operation type and mesh axis, and checking that count against the intended layout, confirms whether propagation behaved as expected. An unexpected AllGather appearing in every layer is the classic symptom of an annotation conflict—typically caused by an intermediate reshape or a single misannotated tensor that forces the compiler to reshard back and forth. Because a compiler’s internal cost model can also pick a suboptimal propagation path, any compiler-derived layout should be treated as a hypothesis about ${T_{\text{comm}}}({N})$ until confirmed by the step trace.

At the fleet level, decoupling layout from model code allows the partitioning to adapt seamlessly to the allocation. When the fleet orchestrator resizes an elastic job (**[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.08 Elastic Scheduling#^sec-fleet-orchestration-elastic-policies|Elastic scaling policies]]**) onto a different node topology, the `model` axis can change along with the `data` axis, and the compiler regenerates the executable from the existing annotations. Exploring layout trade-offs—such as sharding optimizer states or shifting communication onto intra-node links—likewise reduces to editing annotations rather than rewriting layers. At the same time, our running example illustrates the boundary of what partitioning alone can achieve. Its mesh already confines every `model`-axis collective within a single node, so the extra time its 128-GPU step spends beyond the single-node baseline comes from traffic along the cross-node `data` axis. Whether that traffic can be hidden depends on how its transfer time compares with the backward compute window, and for the largest exchange, the gradient reduction, the answer decides when the reduction runs at all.

### Tensor-Parallel Collectives Under Contention

^sec-performance-engineering-overlap

Once the partitioning layout fixes which collectives a step must execute, the exposed communication time is whatever fraction of those collectives the schedule fails to hide behind independent computation. Our running example executes two classes of collectives that differ in their data dependencies. Cross-node gradient reductions along the `data` axis have loose dependencies. As soon as the backward pass finishes computing the gradients for one bucket of layers, that bucket can be reduced across nodes while backward computation continues on earlier layers. This is the standard bucketed overlap implemented by `DistributedDataParallel`. The analytical limits on hiding such loosely coupled exchanges are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.11 Communication-Computation Overlap#^sec-communication-overlap-limits|Overlap limits and exposed communication]]**, and for our 128-GPU job the full gradient reduction lies far outside them.

Each GPU holds the 16-bit gradients of its eighth of the 70B parameters, 17.5 GB, and a ring reduction across the 16 nodes sends 1.875 times that shard through the GPU’s own network interface. Even at the full 50 GB/s of an NDR port, the transfer takes at least 656 ms, 2.7× the entire 245 ms microbatch step, so no bucket schedule can hide it inside one step. Sharding the optimizer state does not rescue a single step, because the ReduceScatter that must overlap with backpropagation still needs about 328 ms, longer than the whole step.

The job therefore accumulates gradients over many microbatch steps and reduces them once per optimizer step. Holding a fully exposed reduction to 5 percent of the optimizer step requires accumulated computation 19 times as long as the reduction, about 12.5 s, which takes 51 microbatch steps of 245 ms, or about 1.8 million tokens per update. The archetype’s 175B reference job makes the same trade at larger scale, accumulating 96 microbatches per replica and spending about 2 percent of its optimizer step on the data-parallel reduction. At 51 microbatches, the reduction adds about 13 ms per microbatch on average, time that lies outside the microbatch step behind the chapter’s MFU figures and lowers program goodput over a whole optimizer step from 0.48 to about 0.456. The gradient reduction therefore cannot be what fills the 65 ms that each illustrative microbatch step spends beyond the node baseline. The constructed example assumes that this time is per-microbatch synchronization across the 16 nodes and the collective waits it causes, which recur on every microbatch and cannot hide; the example does not size them as a particular operation.

By contrast, intra-node collectives along the `model` axis have strict serial dependencies: each AllReduce completes an activation tensor that the very next operator in the same transformer layer consumes immediately, preventing subsequent operations in that layer from starting until the collective finishes. Because these `model`-axis exchanges never leave the node, their duration is already embedded inside the single-node baseline.

A bandwidth-floor estimate (excluding launch latency and activation recomputation) bounds how much of the single-node step those intra-node collectives can occupy. Each exchange point reduces roughly 36 MB of activations across the 8 GPUs of the node, and the 320 exchange points in a full forward-and-backward step require about 45 ms of NVLink transfer time. Even if none of that transfer were hidden, it would represent about 25 percent of the 180 ms single-node step—well within the 35 percent gap between the node’s 65 percent MFU and the arithmetic ideal. Consequently, `model`-axis collectives represent a local, node-level program loss that does not grow with fleet size so long as the `model` axis remains confined to a single node. The cross-node `data`-axis traffic carries the scaling penalty, and a single-rank trace easily separates the two because they execute on distinct process groups.

Hiding a collective whose output is needed by the next operation requires finding independent computation to execute concurrently. One approach interleaves work from a second microbatch that has no dependency on the collective in flight. The alternative is fine-grained compute-communication decomposition. It splits both the matrix multiplication and the collective that consumes its output into smaller tiles, so that one tile’s collective transfer runs concurrently with the next tile’s matrix multiplication. A partitioning compiler can synthesize this transformation automatically ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-wang2023overlap|Wang et al. 2022]]). Neither strategy shortens the communication time ${T_{\text{comm}}}({N})$ itself; both work purely by enlarging the overlap credit ${T_{\text{overlap}}}$.

However, overlapping communication and computation on the same accelerator is never contention-free. On NVIDIA GPUs, concurrent execution is orchestrated through CUDA streams—ordered queues of kernels, memory copies, and collectives that execute sequentially within a stream but may run concurrently across distinct streams. A distributed training step typically assigns matrix multiplications and element-wise ops to a compute stream while dispatching NCCL collectives to a separate communication stream ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.08 Recovering Program Goodput#^lst-performance-engineering-streams|listing 1]]).

``` python
compute_stream = torch.cuda.Stream()
comm_stream = torch.cuda.Stream()
producer_stream = torch.cuda.current_stream()
# Inputs are ready on producer_stream; gradients do not alias A or B.
compute_stream.wait_stream(producer_stream)
comm_stream.wait_stream(producer_stream)
A.record_stream(compute_stream)
B.record_stream(compute_stream)
gradients.record_stream(comm_stream)

with torch.cuda.stream(compute_stream):
    output = torch.matmul(A, B)  # Non-blocking compute

with torch.cuda.stream(comm_stream):
    work = dist.all_reduce(gradients, async_op=True)
    work.wait()  # Establish completion on the communication stream

torch.cuda.synchronize()  # Wait for both to complete
```

Listing 1: **Computation and a Collective on Separate Streams**: Both streams first wait for the stream that produced their inputs, and each tensor is recorded on the stream that uses it so that its storage is not reused while that stream still needs it. The matrix multiplication and the AllReduce may then run concurrently. Concurrency on the timeline does not by itself establish a shorter step.

^lst-performance-engineering-streams

Placing work on separate streams enables concurrency, but it does not partition the underlying hardware resources. Because collective libraries such as NCCL launch their own GPU kernels to copy, pack, and reduce buffers across NVLink and network interfaces, an overlapped collective competes directly with concurrent matrix multiplications for streaming multiprocessors (SMs), L2 cache, and HBM bandwidth ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-pati2024t3|Pati et al. 2024]]). In a kernel timeline, successful stream overlap shifts the collective bar underneath the compute kernels, but resource contention stretches the duration of those compute kernels, causing the step to finish later than an idealized contention-free model would predict ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.08 Recovering Program Goodput#^fig-performance-engineering-overlap-contention|figure 9]]). Overlapping a collective improves program goodput only if the communication time removed from the critical path exceeds the contention delay added to the concurrent computation—a net balance that only an end-to-end step measurement can verify.

![[90 Assets/Volume II/09 Performance Engineering/Performance Engineering Overlap Contention eeea6dbf51.svg]]

Figure 9: **Overlap on a Shared Device**: One step of three kernels and one collective on a compute stream and a communication stream. Serialized, the collective runs after the kernels and is exposed. Overlapped on a device with resources to spare, it hides completely behind the kernels. Overlapped on a real device, the collective’s own kernels take streaming multiprocessors and memory bandwidth from the kernel beside it, which runs longer, so the step ends between the two. Only a measured step shows where between them it ends. Durations are schematic, not measured.

^fig-performance-engineering-overlap-contention

When a program manages multi-stream overlap manually rather than relying on a tested wrapper, it must also enforce two correctness invariants. Data readiness uses `wait_stream` so that no consumer stream reads a tensor before its producer stream has finished writing it. Storage lifetime uses `record_stream` so that the caching allocator does not recycle a tensor’s memory buffer while a side stream is still reading it. Because host kernel launches are asynchronous, a tensor’s Python reference can go out of scope on the CPU before the side stream finishes using the buffer on the GPU, and the allocator tracks buffer liveness only on the allocating stream unless `record_stream` registers the side stream as well. Both invariants must be verified before crediting a shorter step time to communication overlap rather than to a data race that silently corrupted or skipped work.

Our 8-GPU serving replica, partitioned purely along the `model` axis within a single node, illustrates the opposite regime. At batch size one, each per-layer AllReduce transfers only about 32.8 KB across the 8 GPUs—orders of magnitude below the message size required to exit the latency-bound regime of **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.06 Pricing Collectives by Rounds and Chunks#^sec-communication-collective-operations-collective-operations-network-performance-modeling-0d8e|Pricing Collectives by Rounds and Chunks]]**. At this scale, fixed collective launch and protocol overhead (roughly 70× the wire transfer time itself) dominates the exchange, so a faster link would shorten only the small transfer portion. Stream overlap cannot hide the exchange either, because the immediately following layer operator awaits the reduced activation. Shortening this term requires either reducing the number of exchanges through the partitioning layout or cutting per-launch overhead via CUDA Graph replay. How larger decode batches alter this balance is analyzed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.11 Model Sharding for Inference#^sec-inference-scale-tensor-parallelism-b29f|Tensor parallelism]]**.

### Kernel-Level Levers

^sec-performance-engineering-kernel-levers

Even when inter-device communication is well hidden, an accelerator can waste much of its local execution time writing short-lived intermediate tensors out to HBM and reading them immediately back, materializing quadratic attention score matrices, or sitting idle between thousands of small host-dispatched kernels. Four single-device optimization techniques—operator fusion, tiling, graph replay, and graph compilation—recover these local losses without altering the model’s mathematical semantics. In the Fleet Law, all four techniques compress only the local execution term ${T_{\text{compute}}}/{N}$; because none of them directly reduces ${T_{\text{comm}}}({N})$ or ${T_{\text{sync}}}({N})$, their end-to-end fleet impact diminishes whenever exposed communication or barrier waits dominate the step.

↪ Fusion, tiling, graph replay, and compilation are collected for reference in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-kernel-levers|Kernel-Level Levers]]**.

Operator fusion merges a chain of consecutive operations into a single GPU kernel so that intermediate activations remain in registers or shared memory (SRAM) instead of round-tripping through HBM, while replacing multiple host kernel launches with one. It therefore reduces both the memory traffic volume ${D_{\text{vol}}}$ and the host-dispatch portion of ${L_{\text{lat}}}$. For a linear layer followed by an activation and normalization at the hidden dimension of Llama 2 70B and a batch of 2,048 tokens, eliminating the HBM write-and-read of the two intermediates cuts total modeled HBM traffic by a factor of about 1.7×. The hardware limit on fusion is register and SRAM pressure: keeping too many live intermediates per thread reduces SM occupancy and can eventually slow the kernel down. In a profile, successful fusion manifests as fewer kernel launches, fewer measured HBM bytes transferred, and a shorter step duration (**[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-kernel-levers-fusion|Fusion]]**).

The boundary comparison in [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.08 Recovering Program Goodput#^fig-fusion-before-after|figure 10]] shows which intermediate transfers fusion can remove.

![[90 Assets/Volume II/09 Performance Engineering/Fusion Hbm Boundary 72a423abe9.svg]]

Figure 10: **Fusion Across the HBM Boundary**: Separate kernels write each intermediate tensor to HBM and read it back for the next operation. A profile must confirm that the intermediate transfers disappear. Fewer launches alone establish a dispatch change, not a reduction in HBM traffic.

Tiling partitions a computation into blocks sized to fit in on-chip SRAM so that each operand fetched from HBM is reused across many arithmetic operations before eviction. Applied to self-attention (as in FlashAttention ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.14 Source References#^ref-dao2022|Dao et al. 2022]])), tiling evaluates attention block by block using online softmax rescaling, avoiding ever materializing the quadratic sequence-by-sequence score matrix in HBM. For a single attention head of our 70B model at a sequence length of 8,192 tokens, an idealized traffic bound shows that eliminating the score and probability matrix round-trips reduces HBM traffic by roughly 65×. Beyond cutting ${D_{\text{vol}}}$, tiling frees substantial HBM capacity, which training jobs reinvest in longer context lengths or larger microbatches and serving replicas reinvest in larger key-value caches. The trade-off is extra arithmetic for online rescaling and, during backpropagation, recomputing attention scores on the fly rather than storing them. Success is verified by the disappearance of quadratic score-matrix allocations and HBM traffic in the memory trace (**[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-kernel-levers-tiling|Tiling and IO-aware attention]]**).

The working set in [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.08 Recovering Program Goodput#^fig-performance-engineering-flashattention-tiling|figure 11]] stays local while attention consumes successive key/value tiles.

![[90 Assets/Volume II/09 Performance Engineering/Flashattention Working Set 9adc9a86fd.svg]]

Figure 11: **Tiled Attention and Online State**: For one query tile, the kernel reads relevant key/value tiles from HBM and updates on-chip state after each block. This state contains running row maxima, normalization sums, and output accumulators; the feedback path carries it into the next block. After the last required block, the kernel normalizes and writes the output tile. Score tiles remain temporary on-chip values rather than a sequence-by-sequence HBM allocation. Another query tile can require reading the same key/value tiles again; the diagram does not imply one global read.

^fig-performance-engineering-flashattention-tiling

The memory saving comes from the allocation that never crosses the HBM boundary, not from omitting attention pairs. Tile size must leave room for the retained state as well as the operands.

Graph replay captures a fixed sequence of GPU kernel launches once and replays the entire subgraph with a single host API call, compressing the host-dispatch portion of ${L_{\text{lat}}}$ while leaving kernel execution itself unchanged. In eager execution, dispatching the kernels of a single forward pass of our 70B model consumes roughly 12–24 ms of host CPU overhead—several times longer than the 5.2 ms weight-streaming floor of the serving replica’s decode step ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.07 Program Goodput#^sec-performance-engineering-roofline|section 9.6.3]]). Eager small-batch decode therefore becomes host-dispatch bound long before it saturates HBM bandwidth. Distributed training encounters the same regime under strong scaling: when a job expands across more accelerators at a fixed global batch size, per-device kernel durations shrink while the number of kernel launches per step stays constant. The constraint of graph replay is static structure: tensor shapes, memory addresses, and control flow must remain fixed across replays, requiring serving engines with dynamic batch sizes to capture and cache a separate graph for each padded shape bucket. Success is verified when inter-kernel launch gaps vanish from the kernel timeline (**[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-kernel-levers-replay|Graph replay]]**).

Graph compilation traces a region of the model into an intermediate computation graph, rewrites the graph, fuses compatible operators, plans static buffer reuse, and generates or autotunes specialized kernels for each fused subgraph—automating fusion, memory planning, and kernel selection in a single pass. Compilation reduces ${D_{\text{vol}}}$ and host dispatch ${L_{\text{lat}}}$, and when autotuning selects superior tile shapes it increases hardware compute efficiency ${\eta_{\text{hw}}}$ as well. Because compilation runs before the first retained step (and, without a persistent compilation cache, again after each restart, preemption, or elastic resize to a new mesh), its build duration is a runtime goodput cost that must be amortized across subsequent execution, a cross-factor trade-off quantified in [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.10 Trading Between Factors#^sec-performance-engineering-compilation-overhead|section 9.9.3]]. A recompilation triggered by new input shapes during steady-state execution instead slows retained steps and lowers program goodput. Success is verified by fewer, larger kernels in the timeline and a shorter steady-state step measured after compilation completes (**[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-kernel-levers-compilation|Compilation]]**).

Numeric precision also acts on local execution, although unlike the four techniques above it changes the model’s arithmetic. This book divides its mechanics between two domain chapters: reduced-precision training (such as FP8), which raises the compute ceiling ${R_{\text{peak}}}$ and halves activation and weight traffic under the numerical stability contract of **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-fp8|FP8 for distributed training]]**, and post-training weight quantization for inference, which reduces weight-streaming bytes ${D_{\text{vol}}}$ in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.10 Weight Quantization for Serving#^sec-inference-scale-weight-quantization-serving-097b|Weight Quantization for Serving]]**.

These single-device levers pay off very differently across our two running workloads. In the 128-GPU training job, large matrix multiplications already run near the H100 compute ceiling, so kernel-level levers can compress only the non-GEMM kernels on the bandwidth slope while leaving the job’s primary program loss, exposed cross-node communication, untouched. In the 8-GPU serving replica, by contrast, the program loss is overwhelmingly local (weight-streaming traffic and host kernel dispatch), allowing operator fusion, weight quantization, and CUDA Graph replay to close part of the gap to the bandwidth floor, as the replica case study in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.16 Case Studies#^sec-inference-scale-replica-decode-budget|One replica against its token-latency target]]** shows.

### Composing Program Fixes

^sec-performance-engineering-playbook

Applying several kernel and communication optimizations simultaneously—or adding their isolated microbenchmark speedups on a spreadsheet—almost always overpredicts the fleet gain, because speeding up backward compute kernels shrinks the execution window that previously hid gradient communication. Effective performance engineering therefore follows a disciplined, sequential loop that starts from the whole job rather than an individual kernel:

1.  Measure the program goodput of retained steps under the measurement contract ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.04 Measuring Goodput#^sec-performance-engineering-measurement-contract|section 9.3.1]]), and use factor localization ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.04 Measuring Goodput#^sec-performance-engineering-localize-factor|section 9.3.2]]) to confirm that the bottleneck lies in program goodput rather than scheduling or runtime goodput.
2.  Descend the profiling hierarchy ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.07 Program Goodput#^sec-performance-engineering-roofline|section 9.6.3]]) to identify which Fleet Law term holds the exposed time on the critical path, and select the lowest-cost candidate lever targeting that term ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.07 Program Goodput#^tbl-performance-engineering-bottleneck-patterns|table 7]]).
3.  Apply a single lever, re-measure the end-to-end step under the exact same contract, and restart the drill-down from the new trace—because compressing one exposed term routinely exposes another.

For our 128-GPU training example, the constructed drill-down identified exposed cross-node synchronization and collective waits along the `data` axis as the primary bottleneck. Where an exchange’s transfer time fits within the backward compute window, the first experiment targets communication overlap, either by tuning gradient bucket sizes and launch order or by sharding the optimizer state so that ReduceScatter overlaps with backpropagation and AllGather prefetches parameters ahead of the forward pass. The full gradient reduction does not fit. Even with the optimizer state sharded, its ReduceScatter alone needs about 328 ms, longer than the whole 245 ms microbatch step, so overlap cannot hide it within a step. The lever for that reduction is gradient accumulation. Running it once per optimizer step, after about 51 microbatches ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.08 Recovering Program Goodput#^sec-performance-engineering-overlap|section 9.7.2]]), holds even a fully exposed reduction to 5 percent of the update, and accumulating more microbatches shrinks that share further at the cost of a larger global batch. Sharding then reduces what must overlap with the final backward pass rather than making the reduction fit. Only after re-profiling that change does the second experiment target the remaining node-level losses (intra-node `model`-axis collectives and memory-bound non-GEMM kernels) via fine-grained compute-communication decomposition and operator fusion.

Isolated speedups fail to add linearly because every optimization alters the step’s critical path. A lever shortens a single Fleet Law term, and end-to-end step time decreases only by the portion of that term that was exposed. Once the first lever takes effect, every term’s share of the step shifts, invalidating isolated speedup estimates for subsequent levers. In practice, pairs of optimizations interact in three ways:

- **Reinforcing combinations.** Operator fusion and tiled attention free HBM activation memory; reinvesting that freed memory in a larger microbatch lengthens the compute window per step, which in turn hides a larger fraction of collective communication.
- **Redundant combinations.** Enabling a graph compiler that automatically fuses element-wise operator chains leaves nothing for a hand-written fused kernel on the same chain to recover.
- **Conflicting combinations.** Overlapping NCCL communication kernels steals SMs and HBM bandwidth from concurrent matrix multiplications, lengthening local compute. Conversely, speeding up backward compute kernels via FP8 or fusion shrinks the compute window that hid cross-node gradient reductions, exposing communication that was previously hidden for free.

Because of these interactions, an optimization validated on a single-node baseline must always be re-evaluated on the full fleet configuration. Only an end-to-end measurement under [[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.04 Measuring Goodput#^tbl-performance-engineering-measurement-contract|table 2]] can establish whether a combination of levers is reinforcing, redundant, or conflicting—and whether a rise in program goodput came at the expense of scheduling or runtime goodput ([[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.10 Trading Between Factors#^sec-performance-engineering-frontier-objective|section 9.9]]).
