# V2-11.14 Summary

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11 Edge Intelligence|V2-11 Edge Intelligence]]

^sec-edge-intelligence-summary-0af9

Edge intelligence extends the fleet to devices whose memory, power, and availability the operator cannot standardize. Sensors, microcontrollers, and smartphones contribute under different resource budgets, so a locally feasible learning policy also determines which parts of the population can participate. Archetype C (Federated MobileNet) makes this concrete. Local adaptation spends the compute axis of C³ inside each phone’s power and memory envelope. Adapters and update compression shrink the wide-area transfer in the Fleet Law’s communication term. Over-selection with round deadlines caps the Fleet Law’s synchronization term at the price of which devices are represented.

Three levers make learning possible under those constraints, and each acts on a different part of the same budget. Model adaptation shrinks trainable state and, when placed well, the saved activations that dominate peak memory. Data efficiency raises the signal extracted from each scarce example and protects earlier behavior with bounded replay. Federated coordination lets compatible updates from many devices improve one shared model without centralizing raw data. None of the three moves the device’s thermal, energy, or bandwidth limits; each decides how much useful learning fits inside them.

At runtime, those realities become an admission decision rather than a general preference to run “when idle.” Background adaptation may execute only when its predicted energy and sustained power fit the current device slack and profiled worst-case interference preserves the foreground deadline. Because charging status does not eliminate heat or contention, every admitted window remains revocable as the device state changes.

Local execution can meet latency, data-locality, and offline requirements, but those requirements alone do not justify local training. Adaptation must improve a validated outcome within its resource budget; federation must then preserve update compatibility, control disclosure, and evaluate the population actually represented by completed updates.

**Key Takeaways: Physics sets the budget**

- **The edge reverses the fleet**: Data centers fight to keep many accelerators busy; edge devices fight to learn under batteries, kilobytes, thermal throttling (the device-scale counterpart of principle [[01 Books/Volume II - Scaling/01 The Fleet/V2 Fleet Principles#^pri-power-density-wall|3]]), and intermittent links. The same Compute, Communication, Coordination constraints must account for device eligibility as well as aggregate throughput.
- **Bandwidth beats advertised TOPS**: One update step of the chapter’s 10M-parameter example moves about 800 MB, 20× the weight bytes read by an inference, across a phone memory interface roughly 44–65× narrower than data-center HBM. That is the same ceiling that bounds memory-bound decode (principle [[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-autoregressive-bottleneck|18]]). Quantization and locality help, but measured update speed depends on bytes moved and sustained bandwidth.
- **Learning multiplies the footprint**: Full-model backpropagation can require 4–12× the memory occupied by inference weights alone in the chapter’s configurations, depending on optimizer state, activations, and precision. Reducing trainable state helps only when the frozen model and remaining execution state also fit.
- **Background learning is conditional work**: Admit an adaptation window only when [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-background-admission|equation 2]] preserves energy, thermal, and foreground-latency budgets under worst-case measured interference. Charging alone is not sufficient.
- **Admission selects the population**: Passing the admission test correlates with hardware, charging habits, and connectivity, so the shared model learns from the admitted devices rather than the deployed fleet (principle [[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-participation-selects-population|20]]). Per-cohort participation and quality must be measured and corrected; loosening admission spends the budgets it exists to protect.
- **Each technique spends a different budget**: Bias-only updates, LoRA, sparse layers, few-shot data reuse, and experience replay each spend different memory, energy, and privacy budgets. Federated coordination adds population learning only when cumulative uploads stay below the data they replace, enough clients survive to clear secure aggregation’s participation floor so individual updates stay hidden, and shared state stays version-compatible.
- **Heterogeneity is normal operation**: Edge fleets span microcontrollers, phones, gateways, and NPUs with uneven availability, performance, and non-IID data. Stragglers, client drift, participation bias, and privacy-preserving observability are protocol design constraints, not deployment cleanup. Once models learn after release, the release artifact is the adaptation policy, versioned against a base model that rollback can restore.

^callout-takeaways--11-13-3e372d66

An edge learning policy determines both the work a device may perform and the population the fleet learns from. Tightening a resource budget can protect a user’s foreground experience while excluding that user’s data from shared improvement. The useful design target is therefore validated adaptation across the intended population, with local feasibility and fleet representation evaluated together.

**What’s Next: From devices to operations**

Once a model continues learning after release, what the fleet ships is no longer a fixed set of weights but an adaptation rule versioned against a base model, admitted device by device, validated through distributed outcome evidence when central labels are unavailable, and judged by which cohorts its completed updates represent. Production organizations run hundreds of models at once, many sharing features, data pipelines, and release machinery, so a change made for one can silently break another. Keeping that portfolio versioned, observable, and recoverable is a coordination problem in its own right.
