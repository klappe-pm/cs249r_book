# V2-11.07 Federated Learning Algorithms

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11 Edge Intelligence|V2-11 Edge Intelligence]]

^sec-edge-intelligence-federated-learning-6e7e

The voice assistant of the chapter’s opening, now deployed to millions of homes whose intermittently available devices contribute updates when local conditions permit, shows what local adaptation alone cannot do. One household pronounces “data” as “DAY-tuh” and another as “DA-tuh”; a third, a technical household, says “machine learning” every day, while a fourth never has. Local adaptation can specialize each model to its own household, but nothing it learns travels. If the fourth household starts using the phrase, its model must learn it from scratch, even though millions of other devices already handle it. Federation offers that transfer when the observations support a common objective. The system must decide which changes improve shared representations and which should remain personal, then evaluate whether aggregation helps the intended users.

Federated learning (definition [11.2](https://mlsysbook.ai/vol2/11_edge_intelligence/11_edge_intelligence.html#dfn-edge-intelligence-federated-learning)) supplies that transfer while each device keeps its raw examples local. The approach turns data locality into one privacy control, not a complete privacy guarantee. A system must still treat gradients, model deltas, participation timing, device identifiers, and aggregate statistics as sensitive outputs because these signals can reveal information about local users ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-kairouz2021|Kairouz and McMahan 2021]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-zhu2019deep|Zhu et al. 2019]]). Of the three architectures in [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.03 Why Learn on the Device#^fig-centralized-vs-decentralized|figure 2]], only federated learning pools experience across users without moving raw examples, and it buys that position with a protocol.

### Cross-Device and Cross-Silo Federations

^sec-edge-intelligence-privacypreserving-collaborative-learning-ecf9

Before choosing a federated optimization or privacy protocol, an architect must specify who the participants are, because a mobile cohort-sampling protocol applied to ten collaborating hospitals breaks scheduling, weighting, and fault recovery, and a consortium protocol that expects stable round membership fails on millions of intermittently connected phones. The voice assistant is cross-device, with millions of unreliable phones, whereas a group of hospitals that want to train a complication-prediction model without centralizing patient records is cross-silo, with a few reliable institutions that each hold a large dataset. That distinction changes the failure model, scheduling policy, and privacy unit before any optimizer is selected ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.07 Federated Learning Algorithms#^tbl-edge-cross-device-silo|table 6]]) ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-kairouz2021|Kairouz and McMahan 2021]]).

| **Design dimension**  | **Cross-device federation**                                     | **Cross-silo federation**                                                      |
|:----------------------|:----------------------------------------------------------------|:-------------------------------------------------------------------------------|
| **Participants**      | Large population of intermittently available personal devices   | Small set of known organizations or sites                                      |
| **Round semantics**   | Sample an eligible cohort; expect stragglers and dropouts       | Coordinate a stable membership; investigate missing sites                      |
| **Trust boundary**    | Treat client software and local data as potentially compromised | Authenticate institutions, but still isolate each data custodian               |
| **Weighting default** | Decide whether the objective represents examples or users       | Weighting follows the agreed institutional objective, not site size by default |
| **Privacy unit**      | Usually a user or device across its participation history       | Usually a person or record within a site’s data, sometimes the site itself     |

Table 6: **Cross-Device and Cross-Silo Federated Learning**: The participant population determines scheduling, trust, weighting, and privacy semantics. A protocol designed for millions of unreliable phones is not automatically appropriate for a consortium of hospitals.

^tbl-edge-cross-device-silo

### Learning Protocols

^sec-edge-intelligence-learning-protocols-139a

Once the participant population is defined, a federated round must coordinate devices that hold different data distributions, connect over constrained links, and drop out unpredictably. If devices trained on unaligned starting versions and uploaded raw weight tensors whenever they came online, the coordinator would sum incompatible parameter spaces and stall on offline stragglers. Practical distributed coordination protocols must therefore solve three engineering challenges simultaneously. Local training must produce compatible updates despite non-IID data distributions. Aggregation must combine those updates efficiently despite bandwidth constraints. Timing must be coordinated across devices with heterogeneous availability patterns.

#### Local Training

^sec-edge-intelligence-local-training-e73d

Local training turns the device’s adaptation policy into a contribution to a shared model. Every contribution needs a known starting version, a compatible parameter schema, and a declared local update rule. Otherwise, arrays with the same shape may describe changes to different models. A synchronous protocol therefore starts every participating client from the same shared version, trains on local examples under that rule, and returns the difference from the starting parameters, while personal parameters stay outside the aggregate.

The process repeats with a new shared version for each accepted round. Update frequency depends on device availability, local work, and communication cost. A secure transmission channel protects the transfer, but the receiving server can still inspect the update unless the aggregation protocol separately hides individual contributions. Model compatibility and update confidentiality are therefore distinct protocol obligations.

#### Federated Aggregation Protocols

^sec-edge-intelligence-federated-aggregation-protocols-5d37

The most widely used rule for combining client updates is federated averaging (FedAvg), which has become a canonical algorithm for federated learning ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-mcmahan2017communication|McMahan et al. 2017]]). In FedAvg, each device trains its local copy of the model using SGD on its private data. The algorithm is local SGD, which synchronizes only after several local steps to save communication, run with two changes that the data center version never faces. Only a sampled subset of clients participates in each round, and each client’s data is a non-IID shard of the population. The local steps that save communication therefore also pull each client toward its own optimum.

↩︎ Local SGD and the trade-off between synchronization frequency and convergence that it exposes are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.05 Scaling Efficiency and Convergence#^sec-distributed-training-systems-systems-distributed-training-efficiency-metrics-9488|Scaling Efficiency and Convergence]]**.

Formally, let ${\mathcal{D}}_k$ denote the local dataset on client ${k}$, and let ${\theta}_k^{t}$ be the parameters of the model on client ${k}$ at round ${t}$. Each client performs ${E}$ epochs of SGD on its local data, yielding an update ${\theta}_k^{{t}+1}$. The central server then aggregates these updates as:

$$
{\theta}^{{t}+1} = \sum_{k=1}^{{N_{\text{clients}}}} \frac{{n}_k}{{n_{\text{round}}}} {\theta}_k^{{t}+1} \tag{3}
$$

 where ${n}_k = |{\mathcal{D}}_k|$ is the number of samples on device ${k}$, ${n_{\text{round}}}= \sum_k {n}_k$ is the total number of samples across participating clients, and ${N_{\text{clients}}}$ is the number of active devices in the current round. Because every client starts from the same shared model and the weights sum to one, averaging the returned models is equivalent to adding the weighted average of the returned differences to the starting model, which is the form the local-training protocol transmits. Bare ${E}$ counts local epochs; the energy quantities of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-background-admission|equation 2]] always carry a subscript.

^eq-fedavg-weighted-aggregation

This formula optimizes an *example-weighted* objective, in which a client with ten times as many local examples receives ten times the influence. That choice is appropriate when every example should contribute equally, but it can let prolific users or large institutions dominate the model. A *user-weighted* objective instead assigns each participating client weight $1/{N_{\text{clients}}}$, optionally capping or normalizing each client’s local contribution before aggregation. Neither choice is universally fair. The system must declare whether its unit of interest is an example, a user, an organization, or a deployment cohort, then evaluate that population rather than inherit ${n}_k/{n_{\text{round}}}$ as an implementation default.

A deployed round wraps the averaging rule in policy that the equation leaves unstated ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.07 Federated Learning Algorithms#^fig-federated-averaging-cycle|figure 10]]). [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.07 Federated Learning Algorithms#^eq-fedavg-weighted-aggregation|Equation 3]] fixes how completed models combine, but not which clients are invited, how long the coordinator waits, or how few completions force a round to be abandoned. Those protocol choices decide which contributions enter the sum. A client that misses the deadline contributes nothing, and its examples are absent from ${n_{\text{round}}}$ for that round. Over-selection and its population-coverage trade-off are developed in [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.08 Federated Learning Systems at Scale#^sec-edge-intelligence-client-scheduling-f675|section 11.7.1]].

![[90 Assets/Volume II/11 Edge Intelligence/Federated Averaging Cycle a5b677b569.svg]]

Figure 10: **Federated Averaging Protocol**: One FedAvg round in four steps. (1) The coordinator selects a cohort, over-selecting to absorb dropouts, and broadcasts the global model ${\theta}^{{t}}$. (2) Each client runs ${E}$ local epochs on its private data. (3) Clients that finish before the round deadline upload ${\theta}_k^{{t}+1}$; a straggler that misses the deadline is dropped. (4) The coordinator forms the example-weighted average of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.07 Federated Learning Algorithms#^eq-fedavg-weighted-aggregation|equation 3]], which becomes the next global model.

^fig-federated-averaging-cycle

This basic structure introduces a number of design choices and trade-offs. The number of local epochs ${E}$ sets the balance between computation and communication. A larger ${E}$ reduces communication frequency but risks divergence if local data distributions vary too much. The selection of participating clients affects convergence stability and fairness. In real-world deployments, not all devices are available at all times, and hardware capabilities may differ substantially, requiring robust participation scheduling and failure tolerance.

⇄ **Contrast:** Federated rounds over intermittent wide-area clients contrast with the synchronous AllReduce collectives on low-latency cluster fabrics established in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-collective-operations-collective-operations-allreduce-algorithms-7545|AllReduce Algorithms and Topologies]]**.

#### Time to Target Under Client Drift

^sec-edge-intelligence-federated-learning-convergence-analysis-c1fc

A federated deployment must reach a quality target within its time, energy, and participation budgets. More local training can reduce how often clients communicate, but it also changes their updates and the time each selected cohort takes to finish. The engineering comparison is therefore time to an agreed quality target, not communication rounds alone.

##### What the FedAvg Controls Count

^sec-edge-intelligence-convergence-rate-fundamentals-bfef

FedAvg exposes the number of participating clients ${N_{\text{clients}}}$, local epochs ${E}$, and communication rounds ${R}$ as controls ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-mcmahan2017communication|McMahan et al. 2017]]). Their product ${N_{\text{clients}}} {E} {R}$ counts client-epochs when participation is fixed, which makes it a tally of the work a run performs rather than a measure of its progress. Clients can have different dataset sizes, and equal client-epoch counts can process different examples or produce conflicting updates, so two runs with the same ${N_{\text{clients}}} {E} {R}$ can end at very different quality. A convergence result is useful only when its assumptions match the optimizer, client sampling, and data distributions.

##### Non-IID Data Impact

^sec-edge-intelligence-noniid-data-impact-d8b9

Non-IID data is where federated averaging departs from the data center version of local SGD. Each local step moves a client toward the optimum of its own shard. After many local steps the client models sit near different optima, and their weighted average lands at a point that need not minimize the population objective. This client drift grows with the number of local steps and with how far the client distributions differ, and it degrades federated averaging relative to i.i.d. baselines ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-li2020|Li et al. 2020]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-zhao2018federated|Zhao et al. 2018]]). It therefore eats into the benefit of fewer communications exactly where communication is most expensive. How strongly depends on the partition, update rule, participation policy, and local step size. No universal heterogeneity score predicts a round count across applications, which is why [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.07 Federated Learning Algorithms#^sec-edge-intelligence-quantifying-heterogeneity-practice-eece|section 11.6.2.3.3]] measures the trade-off rather than computing it.

When statistical heterogeneity causes FedAvg to diverge or stall, two foundational algorithmic extensions address the root cause of client drift:

1.  **FedProx** ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-li2020|Li et al. 2020]]) adds a proximal penalty proportional to $\|{\theta} - {\theta_{\text{global}}}^{{t}}\|^2$ to each client’s local loss function. This penalty constrains local updates to remain in the neighborhood of the current global model ${\theta_{\text{global}}}^{{t}}$, stabilizing convergence under statistical heterogeneity and permitting devices to execute variable numbers of local epochs without destabilizing the server aggregate.
2.  **SCAFFOLD** ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-kairouz2021|Kairouz and McMahan 2021]]) corrects the local update direction directly using control variates. By maintaining a server control variate and per-client control variates that estimate the difference between client-local and global gradient directions, SCAFFOLD applies an additive correction to each local SGD step. Each step subtracts the client’s own control variate and adds the server’s, so the client moves along the estimated global direction rather than the direction its local data favors. This correction counters client drift under heterogeneous local data, although it roughly doubles the communication volume per round by transmitting control variates alongside model parameters. Each client’s control variate is useful only when that client returns, so the method suits cross-silo federations better than cross-device rounds that rarely sample the same device twice.

##### Measuring the Local-Work Trade-Off

^sec-edge-intelligence-quantifying-heterogeneity-practice-eece

Compare candidate local-epoch settings under the same initialization, data partition, participation policy, and held-out quality target. For each setting ${E}$, record the first validated round ${R}({E})$ that reaches the target and the elapsed duration ${t_r}({E})$ of each completed round, including client selection, local work, transfer, aggregation, and any waiting. The observed time to target is

$$
{T_{\text{target}}}({E}) = \sum_{{r}=1}^{{R}({E})} {t_r}({E}).
$$

Each ${t_r}({E})$ is one instance of the round budget sketched at the opening of the chapter. Read through the Fleet Law, it is the local training on the slowest client the round still awaits, plus the upload, plus the wait for enough reports, less whatever overlaps. The communication piece is easy to estimate. Over a constrained mobile uplink of 1–10 Mb/s, the chapter’s reference adapter update of 50 MB takes about 7 minutes to upload at the low end and about 42 seconds at the high end. That cost recurs in every one of the ${R}({E})$ rounds. A setting of ${E}$ that halves ${R}({E})$ therefore removes half of the cumulative upload time. It pays off only if the extra local training it adds to each round, on the slowest awaited client, costs less than the uploads it removes. Client drift keeps that comparison from being settled on paper, because more local steps can also raise ${R}({E})$, and only measured runs can rank the settings.

A useful experiment log records local epochs, completed clients, rounds to target, elapsed time, transmitted bytes, and device energy. If a run never reaches the quality target within the budget, report that outcome rather than extrapolating an invented convergence curve. Repeated runs and cohort-level validation distinguish a stable improvement from a fortunate sample of participating devices.

##### Communication-Computation Trade-Off

^sec-edge-intelligence-communicationcomputation-tradeoff-6e31

[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.07 Federated Learning Algorithms#^fig-comm-compute-tradeoff|Figure 11]] draws the two opposing paths of local work ${E}$ as a timeline of rounds. Each round’s width is its duration ${t_r}({E})$, each row’s round count is ${R}({E})$, and each row ends at its time to target ${T_{\text{target}}}({E})$. Drift adds a round to the large-${E}$ row, and the moderate row finishes first. The large-${E}$ row needs half the rounds of the small-${E}$ row yet finishes last, so a setting that requires fewer rounds can still prolong total wall-clock duration. A setting remains admissible only if its total consumption also fits within client energy and fleet-coverage budgets.

![[90 Assets/Volume II/11 Edge Intelligence/Federated Round Timeline 329a614bf1.svg]]

Figure 11: **Measuring the Local-Work Trade-Off**: The local-work setting ${E}$ acts through two opposing paths. More local epochs lengthen each round, ${t_r}({E})$, while reducing how often clients synchronize, which can lower the rounds to target, ${R}({E})$, unless client drift raises it. Only their combination, the measured time to target ${T_{\text{target}}}({E})$, ranks candidate settings, and a setting is admissible only if it also fits the client energy and population-coverage budgets.

^fig-comm-compute-tradeoff

The operating point depends on the deployment. Larger local updates can amortize transfer overhead, but they also change drift, completion time, and which clients finish. The network alone can move the optimum, as a cost model in relative units shows ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.07 Federated Learning Algorithms#^fig-fl-communication-computation|figure 12]]). Its minimum ${E}^*$ shifts from ${E}=10$ on the fast-network curve to ${E}=40$ on the slow-network curve because amortizing expensive transfers justifies more local work. These curves are not measured convergence results. A deployment must establish whether additional local work actually reduces time to target after drift and client completion are counted, and adaptive epoch policies need the same outcome and coverage checks as fixed settings.

![[90 Assets/Volume II/11 Edge Intelligence/Cell 23 Output 1 24ad330239.png]]

Figure 12: **Communication-Computation Trade-Off in Federated Learning**: As network bandwidth decreases from fast to slow, the time-minimizing number of local epochs shifts rightward because additional local computation amortizes more communication. The curves come from an illustrative cost model in relative units, not measurements; its growing local-work term stands in for the longer rounds and added drift that make excessive local work counterproductive.

^fig-fl-communication-computation

##### Diagnosing a Missed Target

^sec-edge-intelligence-federated-learning-work-93a2

Federated convergence results depend on the update rule, objective, sampling policy, and assumptions about client data ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-kairouz2021|Kairouz and McMahan 2021]]). Heterogeneity, participation, and local sample counts are therefore inputs to a feasibility assessment, not universal pass/fail thresholds. A deployment must demonstrate that its chosen configuration reaches the declared quality target within time and device budgets, with evaluation that represents the intended population.

When a configuration misses that target, the measured failure guides the next experiment. Conflicting local updates motivate testing less local work, adding proximal regularization (FedProx), incorporating control variates (SCAFFOLD), or switching to personalization. Long waits motivate scheduling or asynchronous alternatives, subject to privacy-protocol compatibility. Sparse local evidence motivates bounded adaptation and stronger validation. None of these changes replaces observations from absent cohorts; each must be reevaluated for quality, resource cost, and population coverage.

The aggregation rule specifies how compatible local models produce a shared model. The measured time to target establishes whether a configuration reaches its objective within budget. A controlled lab can hold participant availability and network conditions steady. A phone fleet cannot, so the implementation must define how selection, deadlines, and failures change the set of updates that actually enters each aggregate. These protocol decisions connect learning behavior to fleet orchestration.
