# V2-11.11 Production Integration

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11 Edge Intelligence|V2-11 Edge Intelligence]]

^sec-edge-intelligence-production-integration-beb5

A prototype can fine-tune an adapter on one Raspberry Pi under controlled conditions, where the engineer controls the input stream, inspects every loss curve, and reflashes weights by hand if an update diverges. Deploying that same adaptation policy across 50 million devices turns local learning into a production operations problem across devices whose runtimes, resource budgets, and update histories differ. The release contract must therefore govern not just a static set of initial weights, but what each device may learn in the field, how unlabeled local changes are gated, and how a trusted baseline is restored when adaptation fails.

### MLOps Integration Challenges

^sec-edge-intelligence-mlops-integration-challenges-bb4e

In a traditional cloud pipeline, the release artifact is a single immutable model binary; once millions of devices begin updating adapters offline on different schedules, the initially released weights no longer describe the behavior running in the field. Integrating on-device learning into machine learning operations (MLOps), the practices that version, deploy, monitor, and roll back production models, expands the scope of release engineering because backbones, adapters, update policies, and local histories evolve independently across heterogeneous hardware. Existing integration tests, version registries, and monitoring remain necessary, but they must now track and bound the permitted adaptation process alongside the initial model.

An edge learning lifecycle splits five stages between the cloud and the device ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.11 Production Integration#^fig-edge-mlops-pipeline|figure 19]]). Centralized base-model pretraining (Stage 1), per-tier hardware compression (Stage 2), and staged over-the-air rollouts (Stage 3) originate in the cloud, while local adaptation executes on-device under the released update policy (Stage 4). Aggregate telemetry (Stage 5) supplies evidence for deciding whether cloud retraining is warranted. The telemetry needs its own privacy controls; aggregation alone does not establish a privacy guarantee, and a detected change must be distinguished from a quality regression before triggering a new training cycle.

#### Deployment Pipeline Transformations

^sec-edge-intelligence-deployment-pipeline-transformations-431d

A release that enables local learning includes an adaptation policy alongside model artifacts. For example, the voice-assistant policy of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.10 Integrating the Edge Intelligence Pillars#^sec-edge-intelligence-pillar-integration-7e21|section 11.9]] assigns bias-only updates to budget devices and different LoRA ranks to mid-tier and flagship phones. These are conditional assignments: model footprint, runtime support, and live admission tests determine whether a device may execute them. CI/CD must therefore validate the selection logic and permitted update behavior across device configurations in addition to the initial weights.

Versioning must preserve relationships among those artifacts. A local adapter belongs to a particular base model, training policy, and representation schema; a replay buffer may also depend on the encoder that produced its features. Federated round identifiers record which shared version produced a returned contribution. Updating the base therefore requires a decision to retain, migrate, retrain, or discard dependent local state. A newer version number alone does not establish compatibility, and rollback must restore a compatible set of artifacts rather than independently selecting older files.

#### Continuous Training Orchestration

^sec-edge-intelligence-continuous-training-orchestration-8974

Continuous training on devices combines fleet-level round or release schedules with local admission decisions. A coordinator can request work, but a device trains only when its resource and availability tests pass. The orchestrator must therefore track eligible work and compatible state without assuming simultaneous execution across clients. Because devices run different base versions at once and may reconnect after days or weeks offline, a returned update must identify its base version. The coordinator can then reject the update, apply a stated staleness policy, or request new training from the current base ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.08 Federated Learning Systems at Scale#^sec-edge-intelligence-asynchronous-device-synchronization-348e|section 11.7.5.1]]). Per-device adapters and replay buffers carry their own version tags and need not be merged into the shared model.

Resource-aware scheduling applies [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-background-admission|equation 2]] at fleet scale, where federated rounds usually add idle, charging, and unmetered-network requirements on top of the local admission test. A daily energy cap bounds cumulative learning cost across many admitted windows. Admission also has a runtime half. Bias updates in early layers require backward computation through later operations; head-only adaptation confines that computation to the head. Either path competes with inference for compute, memory bandwidth, and thermal headroom on a shared SoC. Users judge the device by its quality of service (QoS), so the runtime gives inference priority and throttles or revokes a training window as foreground latency approaches its deadline. At the microcontroller extreme, measured update energy and available reserves determine how much learning a duty-cycled or harvested-power budget can support.[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.17 Footnotes#^fn20|²⁰]]

When a representative central validation set is unavailable, federated evaluation can aggregate metrics computed on local held-out data. Update magnitudes provide an optimization diagnostic, but small changes can reflect stalled learning rather than acceptable quality. Participation audits must accompany outcome measurements so that apparent progress is not confined to an overrepresented cohort.

#### Monitoring System Evolution

^sec-edge-intelligence-monitoring-system-evolution-94c9

Traditional monitoring aggregates metrics from centralized inference servers that see every request, whereas an adaptive fleet’s monitor sees only what devices report about models that may differ on every device. Fleet telemetry for edge devices, including federated analytics that report aggregate or differentially private summaries, is one of the fleet release controls in [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.11 Production Integration#^sec-edge-intelligence-fleet-release-controls-5e1a|section 11.10.1.5]]. Adaptation adds local model states that the operator may not observe centrally. Monitoring must distinguish a change in behavior from a change in quality. Unlabeled signals can identify divergence, while deciding whether the adapted model is better requires validated outcome evidence.

Drift detection presents additional challenges without access to ground truth labels. While traditional monitoring compares model predictions against labeled validation sets maintained on centralized infrastructure, on-device systems must detect drift using only the indirect local signals available during deployment. Confidence calibration compares output probabilities with eventual outcomes whenever labels exist; without verified outcomes, confidence shifts merely flag an altered score distribution. In parallel, input distribution monitoring applies statistical tests to detect when runtime feature distributions diverge from pretraining data without requiring labels. Task performance proxies use implicit feedback such as user corrections or session abandonment, though only after validating the causal link to task quality and accounting for how model suggestions alter subsequent user behavior. Finally, shadow baseline comparisons run a frozen base model alongside the adapted one; [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.11 Production Integration#^sec-edge-intelligence-validation-strategy-adaptation-ab3d|section 11.10.1.4]] develops why that comparison measures divergence rather than quality.

↪ Covariate shift, label shift, and concept drift, and why input monitors can stay silent under pure concept drift, are developed in **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.05 Environmental Shifts#^sec-robust-ai-distribution-shift-concept-drift-55e2|Distribution shift and concept drift]]**.

Cohort evaluation must separate contribution from benefit. A device that never trains can still download an improved shared model, but its users’ data may be poorly represented among the completed updates. Participation metrics reveal that coverage gap; per-cohort quality measurements establish whether it harms those users. A favorable global average cannot substitute for either measurement.

#### Validation Strategy Adaptation

^sec-edge-intelligence-validation-strategy-adaptation-ab3d

Traditional validation measures model quality directly against a held-out test set with known ground truth, whereas on-device learning has to validate adapted models where their inputs live, within privacy and resource limits, and usually without labels. Shadow model evaluation maintains multiple model variants on each device and compares their behavior. Devices can run a frozen, last-known-good model beside a locally adapted version and measure prediction divergence, confidence shifts, latency, and resource use on the same input stream. Without labels or a validated outcome proxy, these comparisons detect change, not performance degradation: agreement can hide a shared error, and disagreement does not reveal which model is correct. A shadow comparison can therefore suspend an update for further evaluation, but automatic rollback requires labeled outcomes, a validated behavioral invariant, or a proxy whose relationship to task quality has been established for the deployment.

The comparator can therefore act only as a gate, never as a judge ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.11 Production Integration#^fig-shadow-validation|figure 20]]). The live input stream is mirrored to the frozen baseline and the adapted candidate, and the comparator tracks their disagreement, confidence shift, and resource deltas. When disagreement exceeds a tolerance ${\tau}$, the gate holds the candidate out of service; validated outcome evidence then either clears it or confirms the regression that justifies rollback.

![[90 Assets/Volume II/11 Edge Intelligence/Shadow Validation 838c7ff331.svg]]

Figure 20: **On-Device Shadow Validation**: A frozen baseline runs beside the active model. Their disagreement, confidence, latency, and resource deltas can flag a change without labels; a rollback decision still requires a validated outcome signal or safety invariant.

^fig-shadow-validation

Confidence-based gates provide another change signal when labels are unavailable. Even a calibrated model’s confidence is interpretable only relative to the population and task on which calibration was measured. A drop can reflect distribution shift, ambiguity, or a changed score scale; stable confidence can coexist with overconfident errors. Systems may use confidence to trigger investigation or halt adaptation conservatively, but they should not call the adapted model worse without delayed labels, randomized evaluation, trusted user corrections, or another validated outcome signal.

Federated A/B testing randomly assigns devices to treatment and control adaptation policies, balanced across device tiers, and compares privacy-preserving aggregates of adaptation success rate, time to improvement, and final quality. A strategy that wins is then released through the staged rollout process that fleet operations owns. Because aggregated validation signals are themselves releases, they need data minimization, secure aggregation where appropriate, a declared privacy unit, and privacy accounting across repeated rounds. Even then, a population summary can miss a failure confined to a few users. Local gates and population summaries therefore provide different evidence, and evaluating an adaptive fleet requires measuring adaptation benefit, resource cost, and cohort coverage together.

↪ Staged rollout, which widens a release’s exposure only after each stage performs acceptably, is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ml-operations-scale-staged-rollout-strategies-2d1f|Staged rollout strategies]]**.

#### Fleet Release Controls

^sec-edge-intelligence-fleet-release-controls-5e1a

The preceding controls act on one adapted device or one federated round. Operating the whole population as one fleet adds three interacting constraints beyond those of any single device, so they form one operational design problem. Each constraint calls for its own platform control ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.11 Production Integration#^tbl-ops-scale-edge-fleet-controls|table 9]]), including hardware-in-the-loop validation and federated analytics.

| **Edge fleet constraint** | **Why it appears**                                                                                                                                                                                                         | **Platform control**                                                                                                                                                                    |
|:--------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Extreme version skew      | Rollouts can take weeks or months because devices are offline, on low battery, or on restricted networks. At any time, 50 model versions may remain active.                                                                | Maintain backward-compatible data pipelines and serving contracts for models deployed months earlier.                                                                                   |
| Device-aware validation   | Accuracy gates do not reveal whether a model exceeds a phone’s memory budget or triggers thermal throttling on its system-on-chip (SoC); microcontroller-class targets below Archetype C tighten the budget to about 1 MB. | Add hardware-in-the-loop validation on physical or emulated target devices before promotion.                                                                                            |
| Privacy-limited telemetry | Raw predictions cannot stream back continuously because privacy rules and bandwidth costs constrain observability.                                                                                                         | Use federated analytics: devices compute local statistics such as error rates or drift, then transmit permitted aggregate health signals under explicit privacy and retention controls. |

Table 9: **Edge Fleet Controls**: Edge operations couple rollout latency, device heterogeneity, and privacy-limited observability. The operations platform must reconstruct global fleet health from partial signals while preserving compatibility with many active model versions.

^tbl-ops-scale-edge-fleet-controls

Version skew and device-aware validation follow from the state an adapted fleet carries. A device that reconnects after weeks offline may still run a release several versions old, together with adapters and replay buffers tied to that base, so data pipelines and serving contracts must stay compatible across every active version rather than only the newest. A cloud accuracy gate says nothing about the tests of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-adaptation-peak-memory|equation 1]] and [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-background-admission|equation 2]], whose outcomes depend on each target’s runtime, operator placement, and thermal behavior. Hardware-in-the-loop validation therefore runs the candidate release, including its update path, on physical or emulated devices from each tier, and promotion waits until those tests pass there.

Federated health signals inherit the participation bias that [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.08 Federated Learning Systems at Scale#^sec-edge-intelligence-client-scheduling-f675|section 11.7.1]] identified for federated training. A device reports its local error rate or drift statistic only when its admission policy allows the work and its connectivity allows the upload, so the devices that report most are the well-charged, well-connected, newer ones. The fleet’s health dashboard then describes the admitted population rather than the deployed one, the same skew the participation selection principle ([[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-participation-selects-population|20]]) names for training. A staged edge rollout can look healthy because the devices most likely to fail, older hardware and thermally constrained phones, are also the least likely to report. The platform therefore tracks reporting coverage per device class and cohort alongside the health signals themselves, and holds promotion when a cohort’s coverage falls too low for its signal to count as evidence.

#### Performance Evaluation in Dynamic Environments

^sec-edge-intelligence-performance-evaluation-dynamic-environments-82a9

Static inference benchmarks characterize latency, throughput, energy efficiency, and accuracy for a fixed model, whereas on-device learning requires additional measurements of adaptation quality and training efficiency across successive updates to explain whether local learning is worth its resource cost. Sample efficiency measures the examples needed to reach a declared quality improvement under a fixed evaluation protocol. Gaining two percentage points from 100 local samples rather than 500 is an advantage when collecting useful samples is the binding constraint. Fewer samples need not mean faster or cheaper adaptation, because the more sample-efficient method may perform more work per example or retain more state; elapsed time, peak memory, and energy complete the comparison.

Because a sample-efficient update can still exceed hardware limits, device-envelope fit tests whether the improvement stays inside resource budgets. Memory-constrained convergence evaluates validation loss under a fixed RAM budget, such as “convergence within 256 KB training footprint,” while energy-per-update measures millijoules consumed per gradient step. An illustrative background envelope of 500–1000 mW corresponds to 1.8–3.6 kJ/hour while active. Battery impact depends on duty cycle, usable battery capacity, foreground demand, and charging state. Time-to-adaptation extends the same idea to scheduling by measuring wall-clock time from new data to measurable improvement, including waiting for idleness, charging status, and thermal headroom rather than only raw accelerator throughput.

Even an update that fits the device envelope must still prove its value to the user, so personalization quality evaluates whether adaptation improves the intended behavior while retaining earlier capabilities. Per-user performance delta compares the adapted model with the global baseline on user-specific holdout data; acceptance requires a declared improvement threshold and reported uncertainty. Privacy must be assessed under the specified disclosure policy and guarantee, rather than treated as an unspecified unit of exposure. Catastrophic forgetting measures degradation on the original task after adaptation. Its acceptable magnitude is application-specific, and accuracy changes must distinguish percentage points from relative percent.

When devices coordinate through the federated protocols examined in [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.07 Federated Learning Algorithms#^sec-edge-intelligence-federated-learning-6e7e|section 11.6]], evaluation expands from the device to the population. Communication efficiency relates quality improvement to total transmitted bytes; compression gains depend on the model, optimizer, data heterogeneity, and encoding ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-konevcny2016federated|Konečný et al. 2016]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-kairouz2021|Kairouz and McMahan 2021]]). Comparisons should also report bytes and elapsed time to the same quality target. Straggler policies change both waiting time and the cohort that contributes. Participation count, cohort coverage, and outcome uncertainty must therefore be evaluated together, without assuming that one participation threshold determines stability across all policies.

A system that infers quickly but adapts slowly, or adapts efficiently but ends at poor accuracy, still fails its deployment, so these training metrics and operational controls extend inference benchmarks and established MLOps practice to distributed, heterogeneous learning. Together they detect, hold, and reverse an adaptation that misbehaves, though they do not remove the underlying conditions that make adaptive fleets misbehave, from heterogeneous hardware and non-IID data to slow drift and adversarial clients.

    2.  The artifact is replaced by an uncompiled Python script executed directly on bare-metal microcontroller sensors.
    3.  The deployment pipeline requires manual per-device flashing over USB cables for every smartphone in the world.
    4.  The deployment artifact eliminates model weights entirely, transmitting only random seeds to client operating systems.

2.  What can a frozen shadow model establish when compared with a locally adapted model without labeled outcomes or a validated task-quality proxy?

    1.  The Shadow Model connects to cloud labeling services via satellite to annotate live user keystrokes in real time.
    2.  Prediction and confidence differences reveal behavioral change and can suspend an update for evaluation, but do not by themselves establish which model is more accurate.
    3.  The Shadow Model inverts user biometric features into cryptographic tokens to bypass operating system security firewalls.
    4.  The Shadow Model permanently deletes the active model whenever the device battery drops below 90%.
