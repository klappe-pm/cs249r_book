# V2-11.04 Design Constraints

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11 Edge Intelligence|V2-11 Edge Intelligence]]

^sec-edge-intelligence-design-constraints-c776

Fine-tuning a neural network on a smartphone is constrained by power and heat: a GPU training cluster may consume megawatts in a controlled facility, whereas a smartphone sustains only a few watts before throttling. Across the edge spectrum, memory ranges from a few gigabytes on phones down to hundreds of kilobytes on microcontrollers, sustained power ranges from a few watts down to milliwatts, and network connectivity may be intermittent or entirely absent. On-device learning must therefore use compute, memory, and data sparingly, and when a local model operates in a safety-critical loop, these resource limits become life-safety engineering problems.

**Lighthouse 11.1: Archetype C (Federated MobileNet): The edge power wall**

These constraints run through Archetype C (Federated MobileNet), where learning happens on phone-class devices whose power budget spans roughly 2–10 W, a few watts sustained with brief bursts toward 10 W, and which must share that budget with the user’s foreground work. Privacy and policy constraints often forbid moving raw examples off the device, and even where transfer is permitted, a mobile uplink and battery rarely afford shipping raw data to the cloud. Data locality is therefore both a policy requirement and a bandwidth and energy constraint. Quantized training, sparse updates, and federated coordination are the strategies that let Archetype C learn within that envelope. Held at that burst ceiling, an idealized 15 Wh battery would be exhausted in about 1.5 hours, and thermal throttling would end the workload sooner. Microcontroller-class sensors with hundreds of kilobytes of memory and milliwatt budgets sit at an extreme below Archetype C, and this chapter treats them as such.

The constraints on parameters, operations, and data interact. A larger batch can improve hardware utilization while exceeding memory capacity; a smaller trainable state can fit memory while extracting too little signal from local data. Compression provides one way to reach a feasible starting point. Quantization shrinks bytes per weight, pruning removes selected parameters, and knowledge distillation transfers behavior into a smaller architecture. Once the base model fits, local learning must also accommodate the state and work needed to adapt it.

On-device learning adds training state and work to the inference workload. A full-model update requires forward propagation, gradient computation through backpropagation, and weight updates. Memory grows because the update must hold gradients, optimizer state, and the activations saved for the backward pass. Arithmetic grows because the backward pass computes gradients with respect to both activations and weights, up to roughly twice the work of the forward pass. The size of each increase depends on the model, batch, precision, and execution schedule. Compression and selective adaptation address different parts of that pressure, so feasibility requires accounting for the resulting working set rather than applying a universal multiplier.

The relevant budget is the capacity available to the learning task. Centralized training can reserve resources and assemble datasets under a common management policy. A device must fit an update around the operating system, foreground applications, and locally available examples. Total installed memory or peak accelerator throughput therefore overstates what background learning can use.

These constraints define eligibility for a federated round. Model footprint and trainable state determine which device tiers can participate. Sparse, nonuniform data determines how much signal each local update can extract. Limited compute determines when training can run at all. A policy that exceeds the budget on weaker devices changes the population represented in the aggregate, even if it improves throughput on stronger devices.

### Quantifying Training Overhead on Edge Devices

^sec-edge-intelligence-quantifying-training-overhead-edge-devices-3e4c

A compact 10M-parameter model whose 40 MB of FP32 weights fit comfortably inside a smartphone’s background-memory allowance can balloon to 360 MB as soon as backpropagation adds gradients, optimizer state, and saved activations. That total exceeds the background memory ceiling and crashes the process on its first backward pass. Training changes memory footprint, memory bandwidth, and hardware utilization through additional live state and backward operations. The illustrative increases in [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^tbl-training-amplification|table 2]] count different things from row to row, so each multiplier carries its own denominator. The 4–12× memory range compares a training working set with the inference weights alone, leaving inference activations and workspace out of the denominator. The 2–3$\times$ compute range compares one update (forward plus a backward pass of one to two times the forward work) with one inference. The 10–50$\times$ energy range compares a converged adaptation, which takes many gradient steps, with a single inference, so it is not a per-sample multiplier.

| **Constraint dimension**  | **Inference**                               | **Training amplification**                                    | **Impact on design**                                                                     |
|:--------------------------|:--------------------------------------------|:--------------------------------------------------------------|:-----------------------------------------------------------------------------------------|
| **Memory Footprint**      | Model weights + single activation map       | Weights + full activation cache + gradients + optimizer state | 4–12$\times$ the inference weights alone; forces aggressive compression                  |
| **Compute Operations**    | Forward pass only                           | Forward + backward + weight update                            | 2–3$\times$ one inference, per update step; limits model complexity                      |
| **Memory Bandwidth**      | Sequential weight reads                     | Bidirectional data flow for gradients                         | Additional traffic depends on update scope and activation schedule                       |
| **Energy per Adaptation** | Single inference operation                  | Multiple gradient steps with convergence                      | 10–50$\times$ one inference, per converged adaptation; requires opportunistic scheduling |
| **Data Requirements**     | Current inputs; no training labels required | Local update examples, often sparse or noisy                  | Necessitates sample-efficient methods                                                    |
| **Hardware Utilization**  | Optimized for forward passes                | Different access patterns for backprop                        | Inference accelerators may not help training                                             |

This table quantifies how each constraint dimension intensifies when transitioning from running pretrained models to adapting them locally. The factors are illustrative: memory and compute compare an update with inference, while the energy row includes repeated optimization steps toward convergence. These different counting units must not be treated as one universal per-sample multiplier.

#### Peak Memory Usage

^sec-edge-intelligence-peak-memory-usage-a2ae

![[90 Assets/Volume II/11 Edge Intelligence/Vol2 Edge Intelligence Margin 001 bd2d8f5a04.svg]]

*Memory budget bar for a 300 MB background allowance, with a 75 MB gradient update filling one quarter and the rest left empty.*

*One gradient update claims a quarter of the background-memory allowance.*

Consider a smartphone keyboard that uses local gradient updates to adapt to a user’s vocabulary and typing patterns. In the illustrative device profile, an update requires 50 MB–100 MB for activations and optimizer state, against a background-memory allowance of 200 MB–300 MB. The actual allowance depends on the operating system, device, and foreground workload. At the selected operating point, the update consumes 25 percent of that allowance before other application state is counted. The design decision is how much learning can fit in the remaining budget while preserving responsive typing; the device’s total installed RAM does not answer it.

Whether an update stays inside that allowance depends on peak live residency over the step, because tensors are allocated and released dynamically as execution proceeds. The peak occurs when weights, saved activations, gradients, optimizer state, and temporary workspace coexist, which need not happen at the same operation in every implementation. For the 10M-parameter model of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^fig-training-memory-amplifier|figure 3]], 40 MB of FP32 weights belong to a 360 MB training working set, of which 200 MB is saved activations. Set against a smartphone’s 8 GB of installed RAM, that 360 MB working set looks modest, yet it exceeds even the top of the 200 MB–300 MB allowance that the operating system grants a background task after itself and the foreground applications. Activation checkpointing (also called gradient checkpointing) discards selected intermediate activations and recomputes them during the backward pass ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-chen2016training|Chen et al. 2016]]), the same trade that cuts activation memory in data-center training. It trades extra computation for lower activation storage, so its value depends on both the peak it removes and the additional time and energy the device can afford.

↩︎ Activation checkpointing, which recomputes selected activations in the backward pass to cut activation memory at the cost of extra FLOPs, is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-compute-phase-forward-backward|Compute-phase forward and backward passes]]**.

That allowance, not installed RAM, is the ceiling for a working-memory budget that every adaptation strategy in this chapter must meet ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^fig-tinytl-memory|figure 4]]). The runtime stages frozen weights from nonvolatile flash into volatile working memory and reserves headroom below the physical device ceiling ${M_{\text{device}}}$ for runtime and application state. Within the working-memory envelope ${M_{\text{peak}}}$, four quantities contribute: let ${M_{\text{weights,resident}}}$ be the backbone weights that must reside in working memory, ${M_{\text{train}}}$ the trainable parameters plus their gradients and optimizer state, ${M_{\text{activations}}}({t})$ the saved activation state, and ${M_{\text{workspace}}}({t})$ operator workspace. With all terms counted in bytes and disjoint, the required working memory is

$$
{M_{\text{peak}}}= {M_{\text{weights,resident}}}+ {M_{\text{train}}}+ \max_t\left[{M_{\text{activations}}}({t}) + {M_{\text{workspace}}}({t})\right]. \tag{1}
$$

^eq-edge-adaptation-peak-memory

Admission then requires ${M_{\text{peak}}}+ {M_{\text{reserve}}}\le {M_{\text{device}}}$, where ${M_{\text{reserve}}}$ holds the runtime, the operating system, and the foreground application; for a background task, ${M_{\text{device}}}- {M_{\text{reserve}}}$ is the allowance just described. Weights stored in nonvolatile memory still consume deployment storage, and any staging buffers belong in ${M_{\text{workspace}}}({t})$. The maximum must follow the actual execution schedule because activation and workspace peaks need not coincide. Each term is a separate lever, and the adaptation strategies of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.05 Model Adaptation#^sec-edge-intelligence-model-adaptation-6a82|section 11.4]] differ in which term they shrink. Freezing weights removes their gradients and optimizer state from ${M_{\text{train}}}$, but it does not make the frozen base or every backward dependency disappear.

![[90 Assets/Volume II/11 Edge Intelligence/Tinytl Memory Budget 49e4c5607f.svg]]

Figure 4: **Adaptation Memory Budget**: Working memory must hold the resident weights ${M_{\text{weights,resident}}}$, the trainable state ${M_{\text{train}}}$, and the peak of live activations plus workspace; together these form ${M_{\text{peak}}}$, which must fit under the device limit once the runtime and foreground application are reserved. Frozen weights kept in nonvolatile flash count toward storage, not working memory, until they are staged, and staging buffers belong to the workspace term. An inference optimization therefore needs a second feasibility check before it is used for adaptation. Reducing stored weights may leave activations or optimizer state as the dominant cost. Selecting which parameters to train changes that accounting, linking the memory analysis to the adaptation choices that follow.

### Model Constraints

^sec-edge-intelligence-model-constraints-9232

A model that fits comfortably on a smartphone can fail before a single backward pass on a smaller edge tier. MobileNetV2 requires approximately 14 MB of storage in its standard configuration. That fits easily in smartphone RAM yet far exceeds the 256 KB of SRAM and 1 MB of flash storage on microcontrollers such as the Arduino Nano 33 BLE Sense.[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.17 Footnotes#^fn5|⁵]] On such severely constrained platforms, even a single convolutional layer may exceed available RAM during training due to intermediate feature maps and gradient storage. Cloud-deployed models can span billions of parameters across multi-gigabyte memory budgets. Models intended for on-device learning must conform to tight limits on memory, storage, and compute, each tightened further by the factors of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^tbl-training-amplification|table 2]].

Training adds state whose size cannot be inferred from layer count alone. Backpropagation retains or recomputes intermediate activations, with storage determined by tensor shapes, precision, batch size, and the update schedule. The arithmetic grows quickly. A 10-layer convolutional model processing $64{\times}64$ images saves feature maps of $64{\times}64$ values per channel when its layers keep the input resolution. At FP32, every channel of every retained map then costs 16,384 bytes, about 16 KB. Ten layers of even a few channels each therefore outgrow the 256 KB of microcontroller SRAM before a single gradient or optimizer value is stored. The relevant comparison is that peak against the memory available to learning after runtime and application reserves, which is why the techniques later in this chapter attack saved activations as well as trainable parameters.

Model complexity also affects runtime energy consumption and thermal limits. In smartwatches or battery-powered wearables, sustained training can deplete the energy allowance or trigger thermal throttling even when its tensors fit in memory. Arithmetic precision alone does not determine feasibility; the update duration and measured power determine its energy cost. Benchmarks such as MLPerf Tiny provide small quantized inference targets for constrained devices ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-banbury2021mlperftiny|Banbury et al. 2021]]). On-device adaptation techniques address the additional training cost by freezing most parameters, reducing activation storage, or selecting sparse update sets ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-cai2020tinytl|Cai et al. 2020]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-kwon2024tinytrain|Kwon et al. 2024]]).

Battery and thermal constraints also determine when learning can run. The illustrative smartphone profile uses a sustained processing envelope of 2–3 W and brief bursts of 5–10 W. An update that fits during an idle interval may exceed the available headroom when foreground work starts. Charging supplies energy, but the runtime must still monitor heat and contention, reducing the update duty cycle or suspending learning when limits are approached. An overnight idle-and-charging policy provides one candidate window; measured device conditions determine whether that window remains usable.

These constraints make adaptation feasibility part of architecture selection. When the base model exceeds device capacity, partitioning, quantization, offloading, or a smaller architecture can change the deployment footprint, each with its own execution cost. INT8 or INT4 weights often decide whether the base model fits at all, and 1-bit weights cut weight bytes 16$\times$ relative to FP16 (32$\times$ relative to FP32) before scale metadata and activations are counted. Fitting the forward path is the starting point; quantization support and selective-update costs must then be established for the training path.

### Data Constraints

^sec-edge-intelligence-data-constraints-303e

Fitting the model and its update state into memory solves only the capacity side of the problem, because the available local data still sets how much a fitted update can actually learn. A fitness tracker that records thousands of accelerometer readings across a workout may receive only a single user-supplied activity label, or it may record from a sensor whose calibration has drifted. Unlike the curated datasets used in cloud training, edge data is locally collected, temporally sparse, and often unlabeled. Because sampling frequency, windowing, and temporal correlation can collapse an entire session of correlated sensor readings into a single independent observation, the learning policy must budget for usable supervision rather than raw stored bytes.

On-device data is also frequently non-i.i.d. ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-zhao2018federated|Zhao et al. 2018]]). A voice assistant deployed across households encounters variation in accents, languages, speaking styles, and command patterns. Smartphone keyboards observe individual typing patterns, autocorrect preferences, and multilingual usage. Centralized systems also encounter such variation, but a federated coordinator cannot freely shuffle raw examples across clients. Local updates therefore reflect different data distributions, complicating the balance between shared generalization and personalization.

Label scarcity compounds the distribution problem. Most edge-collected data is unlabeled by default, requiring systems to learn from weak or implicit supervision signals. A smartphone camera may capture thousands of images throughout the day, but only a few are associated with meaningful user actions (tagging, favoriting, or sharing) that could serve as implicit labels. In many applications, including anomaly detection in sensor data and gesture recognition adaptation, explicit labels may be entirely unavailable, making traditional supervised learning infeasible without alternative methods for weak supervision or unsupervised adaptation.

Data quality introduces further challenges. Environmental sensors or automotive ECUs can experience calibration changes, interference, or mechanical wear that corrupt or shift input signals. An adaptation loop may learn from those changes as if they represented useful new behavior. Local input checks and validated outcome signals must distinguish sensor faults from changes the model should learn, especially when raw observations are unavailable for central inspection.

Privacy and security requirements can further restrict which examples may be retained or shared. Keeping health data, personal communications, or behavioral traces on the device narrows raw-data exposure, but local storage and transmitted updates remain sensitive. The learning design must specify access, retention, and permitted disclosures alongside the data needed for adaptation and validation.

### Compute Constraints

^sec-edge-intelligence-compute-constraints-4d6d

Even when a compact model and validated local examples are in place, the processor that runs inference may not be able to train them: a mobile neural processing unit (NPU) advertised at tens of TOPS for INT8 inference can lack backward-pass or optimizer kernels entirely. An on-device update must then fall back to the CPU and can run far slower and hotter than the chip’s inference rating suggests. Across the edge hardware spectrum, from microcontrollers like the STM32F4 and ESP32, through mobile processors with dedicated AI accelerators (Apple Neural Engine, Qualcomm Hexagon, Google Tensor), to high-capability edge modules, inference ratings measure forward-pass throughput on fixed weights. Training workloads add backward and optimizer operations with very different execution paths.

Because an inference rating does not measure this backward path, feasibility depends on tracing where each update operator actually executes. Backpropagation reads saved or recomputed activations, produces gradients, and updates parameters and optimizer state. These operations add memory traffic, with the amount determined by the trainable subset and execution schedule. A specialized accelerator can expand the inference budget without executing any backward operator. The feasibility test is therefore the actual update path. It identifies which processor runs each backward and optimizer operator, including any fallback to the CPU or GPU, and measures time, memory, and energy for that path under foreground load. Each device class that follows gets this update-path test, applied to its own memory, operators, and power, rather than a verdict read from its inference rating.

At the most constrained end, devices such as the STM32F4[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.17 Footnotes#^fn6|⁶]] or ESP32-S3 microcontrollers offer only a few hundred kilobytes of SRAM and limited compute and power budgets ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-warden2020tinyml|Warden and Situnayake 2020]]). Although these families include single-precision floating-point support, practical ML deployments commonly rely on quantized or fixed-point kernels for efficiency. Libraries like CMSIS-NN ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-lai2018cmsis|Lai et al. 2018]]) provide optimized neural network kernels for Arm Cortex-M processors, achieving 4.6$\times$ runtime improvement through fixed-point arithmetic and single instruction, multiple data optimizations. These severe limitations preclude conventional deep learning libraries and require models designed for quantized arithmetic and minimal runtime memory allocation. Quantization-aware training[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.17 Footnotes#^fn7|⁷]] can prepare models for efficient quantized inference. Executing local updates requires a separately supported training path, potentially with selective updates, quantized gradients, or a compact floating-point working set.

Microcontroller memory rules out training configurations whose live tensors exceed SRAM, rather than every convolutional model. Feasibility depends on tensor shapes, update scope, numerical representation, and the compiled execution schedule. Plain stochastic gradient descent (SGD) reduces optimizer state compared with methods that retain additional moment arrays.[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.17 Footnotes#^fn8|⁸]] Non-neural adaptation, such as ${k}$-means clustering, offers a different way to update local centroids for sensor analysis. The method and its arithmetic must still fit the available memory and produce a validated improvement; neither a simple optimizer nor integer execution establishes that result alone.

Moving up the computational hierarchy, mobile-class hardware represents improvement but still operates under severe constraints. Platforms including the Qualcomm Snapdragon, Apple Neural Engine,[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.17 Footnotes#^fn9|⁹]] and the Google Tensor system-on-chip (SoC) provide significantly more compute power than microcontrollers, often featuring dedicated AI accelerators and optimized support for 8-bit or mixed-precision matrix operations. These accelerators offer dedicated matrix multiplication units, on-chip memory hierarchies, and power management features specifically designed for neural network inference, with varying support for local training workloads. While these platforms can support more sophisticated training routines, including full backpropagation over compact models, they still fall far short of the computational throughput and memory bandwidth available in centralized data centers. Training a lightweight transformer on a smartphone, for instance, is technically feasible but must be tightly bounded in both time and energy to avoid degrading the user experience.

Hardware capability contributes to on-device adaptation feasibility alongside the algorithm and runtime. The mobile accelerator scaling tracked in [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^fig-edge-npu-tops|figure 5]] shows Apple’s stated rating climbing from under 1 TOPS on the A11 Bionic to nearly 35 TOPS on the A17 Pro, a step in 2023 that may partly reflect a change in rating precision rather than in the hardware alone. These peak ratings concern forward inference. A training budget must also account for backward operators and the runtime that dispatches them.

**Systems Perspective 11.1: The silicon dividend of a dedicated NPU**

The gap between running a model on a generic mobile CPU and on a dedicated NPU is best understood as a “silicon dividend” rather than a marginal speedup. Published NPU profiles vary by silicon generation and workload, so this callout uses explicit scenario assumptions rather than a benchmark: a 20× latency improvement and a 60× energy-efficiency improvement relative to the modeled MobileNetV2 baseline (1.883 ms per inference on the CPU).

The dividend belongs to the operators the NPU actually executes. An update adds backward and optimizer work that costs roughly one to two more forward passes, because the backward pass computes gradients with respect to both activations and weights. If the runtime cannot place those operators on the NPU, they fall back to the CPU. The forward pass may still collect its 20× dividend, but CPU backward work and transfers between processors can dominate the complete update. The resulting speed and energy depend on that mixed execution path. An inference-dominated product and an adaptation-dominated one can therefore see very different returns from the same silicon, and only the traced update path says which case a deployment is in.

Published Syntiant Core 2 and STM32N6 results illustrate the cost of inference on dedicated neural processors in [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^fig-edge-inference-landscape|figure 6]]. The plotted observations span approximately 14× in reported energy, from Syntiant keyword spotting to STM32N6 visual wake word detection. The workloads and measurement boundaries differ: the STM32N6 results include pre-inference and post-inference work, while Syntiant reports MLPerf Tiny benchmark results. The span therefore does not establish a matched-task hardware-efficiency ranking. Energy per inference does not determine battery lifetime on its own, because inference frequency, sleep power, sensing, radio use, and usable battery capacity also enter that budget.

For a learning device the figure sets the scale against which an update must be judged. The plotted evaluations cost tens to hundreds of microjoules, while each second of training inside the 2–3 W sustained envelope spends joules, more than a thousand keyword-spotting evaluations at the plotted 30 to 160 ${\mu}$J. An update can therefore be a substantial energy cost, but its share of the device budget depends on how often training and inference run. Both paths need measurement over the same operating period.

These computational limitations become especially acute in real-time or battery-operated systems. There, the foreground latency budgets of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.03 Why Learn on the Device#^sec-edge-intelligence-alternative-approaches-decision-criteria-bd36|section 11.2.1]] bound how much interference local training may cause, although training itself need not finish within an inference deadline. Training also has different memory access patterns from inference. Gradient computation, activation storage, and optimizer updates add memory traffic whose magnitude depends on which parameters train and which intermediate states are retained. These transfers can create bottlenecks that pure computational metrics do not capture. Hardware designs can address these challenges with specialized support, but a particular device must expose that support through its training runtime. Mixed-precision datapaths may execute different formats in forward and backward kernels when those kernels exist. Sparse-update savings require an execution path that can actually skip the selected work; zero gradients alone do not establish reduced hardware cost ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.05 Model Adaptation#^sec-edge-intelligence-sparse-updates-879b|section 11.4.4]]). Near-memory compute architectures[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.17 Footnotes#^fn10|¹⁰]] reduce data movement costs by performing gradient updates directly adjacent to weight storage, addressing the memory bandwidth bottleneck. Most edge accelerators, however, remain optimized for inference, which leaves the backward and optimizer operators of local adaptation as an open hardware-software co-design problem.

#### The Mobile Memory Wall

^sec-edge-intelligence-mobile-memory-wall-5ffe

Rising NPU ratings tempt designers to read device capability from TOPS, but every byte a local update moves crosses the same memory interface as inference traffic, and an update moves far more bytes than an inference. Counting them for the 10M-parameter model of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^fig-training-memory-amplifier|figure 3]], under the simplest assumption that each tensor crosses DRAM once per use with no cache reuse, shows how far. The forward pass reads the weights and writes the saved activations, and the backward pass rereads the activations and weights and writes the gradients. An Adam step then reads the weights, gradients, and both moments and writes the weights and moments back. One update step moves about 800 MB, 20× the weight bytes a single inference reads. At the 51 GB/s peak bandwidth of an A17 Pro, that traffic alone needs about 16 ms per step before any arithmetic is counted.

Mobile language-model decode, the case already met as the autoregressive bottleneck (principle [[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-autoregressive-bottleneck|18]]), shows the same ceiling at its starkest, since decode pressure falls on memory and interconnect rather than peak arithmetic throughput ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-ma2026challenges|Ma and Patterson 2026]]). The interface itself is narrow by data-center standards. Data-center HBM3 on an H100 provides 3,350 GB/s of peak unidirectional DRAM memory bandwidth. Flagship mobile systems sit near 51 GB/s (A17 Pro, LPDDR5) to 77 GB/s (Snapdragon 8 Gen 3, LPDDR5X), a gap of roughly 44–65×.

↩︎ The memory wall, the widening gap between arithmetic throughput and the memory bandwidth that feeds it, is established in **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.04 The Memory Wall#^sec-compute-memory-wall|The Memory Wall]]**.

![[90 Assets/Volume II/11 Edge Intelligence/Edge Intelligence Bandwidth Ladder b2faa314c5.svg]]

*Two-rung violet bandwidth ladder on a log scale. Top rung, data-center HBM3 at 3,350 GB/s. Bottom rung, mobile memory at 77 GB/s.*

*Data-center high-bandwidth memory (HBM) outruns flagship mobile memory bandwidth by about 44 times.*

The ratio of bandwidth-bound times equals this bandwidth ratio only when both devices move the same bytes and sustain the same fraction of their peak bandwidth. Precision, batching, cache reuse, and runtime overhead all move the measured ratio. Low-precision weights attack that ceiling when weight traffic is what binds. Storing FP32 weights at 4 bits, for example, reduces weight bytes by 8$\times$ and reduces that component of traffic by the same factor if the runtime consumes the compressed representation efficiently. It does not increase physical bandwidth or remove cache-state traffic and decoding overhead, and the precision choice must satisfy both quality and measured latency requirements. For an on-device update the relief is smaller still. In the count above, the three weight reads (forward, backward, and optimizer) are only about 15 percent of the step’s traffic, and a quantized base leaves the saved activations, gradients, and optimizer state that make up the rest untouched.

**Systems Perspective 11.2: Why bandwidth, not TOPS, is the binding constraint**

Small-batch decode is the familiar memory-bound case. Each token rereads weights too large to stay in cache, so the data term $({D_{\text{vol}}} / {\text{BW}})$ of the single-machine iron law sets its time, and sustained bandwidth and bytes per token predict it better than peak TOPS. The roofline recap in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-roofline|The roofline bound]]** works that decode example. Local adaptation needs the same comparison applied to its own forward, backward, and optimizer traffic, counted per update step rather than per token, where the count above puts it at about 800 MB.

#### Memory Hierarchy Optimization

^sec-edge-intelligence-memory-hierarchy-optimization-8396

![[90 Assets/Volume II/11 Edge Intelligence/Edge Intelligence Device Memory Ladder 6da88a094a.svg]]

*Vertical ladder of three blue bars on a log scale showing device-class memory: phone 16 GB, IoT device up to 1 GB, microcontroller 256 KB.*

*Device memory spans more than four orders of magnitude, phone to microcontroller.*

Capacity is the question [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-adaptation-peak-memory|equation 1]] already answers. Quantization, pruning, and distillation can each shrink the resident and trainable terms of that working set ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-jacob2018|Jacob et al. 2018]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-han2015deep|Han et al. 2015]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-hinton2015distilling|Hinton et al. 2015]]), but their gains are workload-specific and do not combine automatically, so they must be validated together against the same budget. Once the working set fits, capacity says nothing about the second question, which is how much traffic the update drives through the hierarchy and how much of that traffic the caches can absorb. Operator tiling and memory layout aim to reuse active tensor blocks before eviction, while batch size controls activation storage and available parallelism. Gradient accumulation can limit the microbatch working set, but it also retains accumulation state and adds accesses, so its effect on traffic must be measured.

Training adds gradient and optimizer traffic to the tensor reads and writes already required by inference. When these transfers saturate memory bandwidth, additional arithmetic capacity cannot shorten the update. The activation checkpointing introduced with peak memory usage shows why capacity and traffic must be counted separately. Recomputing activations lowers the peak footprint while adding forward work and its memory reads, so capacity can improve as traffic and energy rise. Mixed-precision training changes bytes per stored tensor, but numerical stability and supported backward kernels determine whether the smaller representation is useful. Capacity, traffic, and update time therefore need separate measurements.

#### Mobile AI Accelerator Optimization

^sec-edge-intelligence-mobile-ai-accelerator-optimization-67fe

Accelerator choice depends on the training primitives that the device’s software stack exposes. Apple Neural Engine, Qualcomm Hexagon DSP, and Google Tensor devices have different compiler and runtime contracts, so the same update can follow different paths on each. A useful execution plan identifies where feature extraction, head or adapter training, and optimizer updates run. A dedicated engine may accelerate the frozen forward path while another processor handles learning, but transfers and duplicate representations then enter the cost. The supported operators and data movement must be established for the actual device and runtime version.

A local update may therefore execute on a CPU or GPU even when inference uses the dedicated neural accelerator. On a real device, the update-path test that opened the discussion of compute constraints becomes a short procedure.

1.  List the update’s operators in execution order: the forward pass, each backward operator that the trainable subset requires, and the optimizer step.
2.  For each operator, record the processor the runtime actually places it on, noting every fallback from the neural engine to the CPU or GPU.
3.  At each change of processor, add the transfer and any duplicate tensor representation to the update’s memory and traffic accounting.
4.  Measure time, peak memory, and energy for the complete traced path while a representative foreground workload runs.
5.  Feed those measurements into the peak-memory budget of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-adaptation-peak-memory|equation 1]] and the admission test of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-background-admission|equation 2]] that follows, which together decide whether the update may run.

Mixed-precision datapaths, sparse-update support, and near-memory compute can reduce those costs, but none of them is a prerequisite for training. What matters is whether the available runtime can execute the required operators within the device envelope.

### Energy, Heat, and Background Admission

^sec-edge-intelligence-energy-thermal-constraint-analysis-3133

An update path that fits in memory and runs on supported kernels still fails if 30 minutes of background backpropagation noticeably drains the battery, warms the handset in the user’s pocket, or delays foreground touch responses. Because energy draw, thermal dissipation, and shared-processor contention reach the user directly, a mobile power budget constrains both the model complexity a device can train and the schedule on which background learning is admitted.

**Napkin Math 11.1: Battery drain: The cost of edge learning**

**Problem**: A team is designing a background fine-tuning job for a personalized voice assistant on a smartphone. Run unconstrained, the training job draws 4.5 W, above the 2–3 W sustained envelope given earlier, and takes 30 minutes to complete. If the phone has a 15 Wh battery, how much of the user’s battery will this “invisible” update consume?

**Math**:

1.  Total energy: 4.5 W $\times$ 0.5 h = 2.25 Wh.
2.  **Battery impact**: 2.25 Wh/15 Wh = 15 percent.

**Systems insight**: Consuming 15 percent of a user’s battery for one background task makes update frequency a deployment decision. That energy cannot be translated into a fixed amount of screen-on time without specifying the foreground workload. A policy of **opportunistic scheduling** admits learning when device conditions permit it; a federated policy might require charging, Wi-Fi, and thermal headroom. Charging supplies energy but does not remove heat or foreground contention, so those constraints still need separate checks.

This battery calculation is the local edge-learning version of a broader energy constraint. Training must satisfy the user’s energy budget in addition to the model’s accuracy target. A production design therefore has to account for energy at scheduling time, compare local computation against communication cost, and defer learning when the user’s device cannot absorb the update.

That decision can be expressed as a background-work admission condition. Let ${E_{\text{update}}}$ be the predicted energy for one adaptation window, ${E_{\text{slack}}}$ the energy the policy permits before the next charging opportunity, ${P_{\text{device}}}$ the current sustained power, ${P_{\text{update}}}$ the adaptation increment, and ${P_{\text{thermal}}}$ the thermally sustainable limit. Let ${L_{\text{lat,fg}}}$ be measured foreground latency, ${\Delta L_{\text{lat,fg}}^{\text{wc}}}$ the worst-case latency increase under concurrent adaptation, and ${T_{\text{deadline}}}$ the foreground deadline. The runtime admits an update only if

$$
{E_{\text{update}}}\le {E_{\text{slack}}}\quad \land \quad {P_{\text{device}}}+ {P_{\text{update}}}\le {P_{\text{thermal}}}\quad \land \quad {L_{\text{lat,fg}}}+ {\Delta L_{\text{lat,fg}}^{\text{wc}}}\le {T_{\text{deadline}}}. \tag{2}
$$

^eq-edge-background-admission

Charging can enlarge the energy allowance, but it does not waive the thermal or foreground-latency tests. The quantities must come from device- and workload-specific profiling, and the runtime must revoke admission when the measured envelope changes. Shorter update windows, a lower duty cycle, or a smaller trainable parameter set can make a rejected update feasible; allowing background learning to consume the foreground deadline cannot.

The same test also decides who teaches a shared model. Passing it correlates with hardware class, charging habits, and connectivity, so devices that are old, rarely charged, or thermally tight contribute few updates. As a result, the population a federated model learns from is the admitted population rather than the deployed one (principle [[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-participation-selects-population|20]]). The admission policy that protects each device is therefore also a sampling policy, and [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.08 Federated Learning Systems at Scale#^sec-edge-intelligence-client-scheduling-f675|section 11.7.1]] measures the skew it creates.

**Example 11.1: On-device keyboard learning**

**Scenario**: Consider a mobile keyboard that trains its next-word predictor locally and contributes updates to a shared model through federated averaging ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.16 Source References#^ref-mcmahan2017communication|McMahan et al. 2017]]).

**Diagnosis**: In the keyboard profile of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^sec-edge-intelligence-peak-memory-usage-a2ae|section 11.3.1.1]], one local update needs 50 MB–100 MB of working memory against a background allowance of 200 MB–300 MB. At the selected operating point, the update alone therefore claims 25 percent of the allowance before the keyboard’s own state is counted, and the resident weights in ${M_{\text{peak}}}$ claim more. Exceeding the allowance risks process eviction mid-update. Energy is the second constraint. An unconstrained job like the one in notebook [11.1](https://mlsysbook.ai/vol2/11_edge_intelligence/11_edge_intelligence.html#nbk-edge-intelligence-battery-drain-cost-edge-learning) would take 15 percent of the battery, more than a policy that protects the user’s charge is likely to grant as ${E_{\text{slack}}}$ in [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-background-admission|equation 2]] while the phone runs on battery. The pipeline therefore admits training only when the device is idle, charging, and on Wi-Fi, and it quantizes update vectors to shrink the transmitted payload ${D_{\text{vol}}}$.

**Systems lesson**: A federated keyboard must satisfy all three terms of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-background-admission|equation 2]] (energy ${E_{\text{update}}}\le {E_{\text{slack}}}$, sustained power under ${P_{\text{thermal}}}$, and typing latency under its deadline), fit ${M_{\text{peak}}}$ within its memory allowance, respect uplink bandwidth ${\text{BW}}$, and meet its declared privacy guarantees together. Differential privacy adds a specific release guarantee and its associated costs; it is not implied by keeping raw text local.

### Matching Edge Constraints to Adaptation Pillars

^sec-edge-intelligence-holistic-resource-management-strategies-9e4b

Memory, data, compute, and admission constraints act on the same update window at once. Shrinking trainable parameters so an update fits in RAM still fails if local supervision is too sparse to guide the step or if intermittent connectivity drops the device from every federated round. The constraint analysis therefore yields three linked design decisions. The training amplification of [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^tbl-training-amplification|table 2]] motivates measuring the update footprint against [[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^eq-edge-background-admission|equation 2]] and choosing which parameters to adapt. Information scarcity, including limited local datasets, non-IID distributions, restrictions on data sharing, and minimal supervision, motivates data efficiency methods that reuse available evidence. When shared learning is useful, device heterogeneity and intermittent availability motivate federated coordination with explicit validation and privacy controls. Each pillar answers a different constraint within the same deployment budget and brings its own techniques to that answer ([[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.04 Design Constraints#^tbl-constraint-solution-mapping|table 3]]).
