# V2-12.04 Governance of State and Change

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12 ML Operations at Scale|V2-12 ML Operations at Scale]]

^sec-ml-operations-scale-multimodel-management-d8ac

Collisions through shared state rarely announce themselves at the model that changed. Imagine an e-commerce platform where the search ranking model uses outputs from a user embedding model: an unannounced dimensionality change can break the consumer’s input interface, while a shift in scale or meaning can pass shape checks yet degrade ranking quality. Because shared features, chained predictions, and common infrastructure make model behaviors interdependent across team boundaries, governing a portfolio requires both an artifact record and a data contract. Registries, dependency tracking, and ensemble-aware lifecycle controls identify the model versions and consumers involved, while feature operations preserve the meaning and timing of the inputs those consumers expect so release gates can evaluate a complete dependency state rather than an isolated model binary.

### Model Registries at Scale

^sec-ml-operations-scale-model-registries-scale-ccba

Storing model weights in ad-hoc cloud buckets or team-local folders leaves operators unable to tell which commit or dataset produced a deployed checkpoint, or which downstream rankers will break when an upstream embedding model is updated. Turning checkpoints into governed interfaces requires a model registry that serves as the central catalog for all machine learning artifacts in an organization, and at enterprise scale it also exposes the dependency graph that determines which downstream systems an update can break.

#### Core Registry Requirements

^sec-ml-operations-scale-core-registry-requirements-1a58

The registry can enforce dependency control only if four ordinary catalog capabilities are reliable ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^tbl-core-registry-requirements|table 6]]). Version identifiers let downstream consumers pin the exact artifact they validated; metadata exposes the training and deployment context needed for review; artifact storage turns registry entries into durable deployable assets; and access control keeps ownership boundaries explicit.

| **Requirement**    | **What it stores or enforces**                                                                                     | **Why it matters at scale**                                                               |
|:-------------------|:-------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------|
| Version management | Unique artifact identifiers plus lineage for training data, hyperparameters, code commits, and evaluation metrics. | Downstream consumers can pin the exact artifact they validated.                           |
| Metadata storage   | Training configuration, evaluation results, hardware requirements, serving configuration, and ownership.           | Deployment and review decisions can be made without reverse-engineering the artifact.     |
| Artifact storage   | Durable model binaries with efficient retrieval and caching near serving locations.                                | Large models such as LLMs can exceed 100 GB and cannot rely on ad-hoc file distribution.  |
| Access control     | Read-write, administrative, and read-only permissions at team and dependency boundaries.                           | Model developers, platform operators, and dependent teams interact through governed APIs. |

Table 6: **Core Registry Requirements**: Enterprise model registries need versioning, metadata, artifact storage, and access control before dependency-aware validation can be reliable. These catalog capabilities make model artifacts behave like governed production interfaces rather than files on shared storage.

^tbl-core-registry-requirements

#### Dependency Tracking

^sec-ml-operations-scale-dependency-tracking-1d7e

Beyond these core requirements, the distinguishing feature of enterprise registries is explicit dependency tracking. When Model A consumes features computed by Model B, that relationship must be recorded and enforced, because the recorded edges are what bound the work an upstream change creates. A version bump on embedding model ${E}$ propagates along those edges to an impact set of candidate retrieval, parallel rankers, and an ensemble, all of which must be re-evaluated before release ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^fig-model-registry|figure 3]]).

![[90 Assets/Volume II/12 Ops Scale/Model Dependency Graph 21f1d30770.svg]]

Figure 3: **Dependency-Aware Model Registry**: A version bump on embedding model ${E}$ starts a traversal of the registry’s recorded downstream edges: retrieval ${R}$, rankers ${K}_1$ to ${K}_3$, and ensemble ${M}$ form the impact set (dashed region) that must be re-evaluated before ${E}$ v3.2 ships. A model with no recorded edge from ${E}$, such as fraud model ${F}$, is not flagged, which is why an unrecorded dependency is a silent risk. The rankers also consume features derived from ${E}$ directly; only the retrieval path is drawn.

^fig-model-registry

The impact boundary in [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^fig-model-registry|figure 3]] identifies consumers that require evaluation after an upstream change. Fraud model ${F}$ has no recorded dependency, so the traversal does not flag it; an omitted edge would leave that conclusion incomplete. Within the recorded graph, upstream embedding model ${E}$ produces representations consumed by retrieval model ${R}$, three parallel rankers (${K}_1$, ${K}_2$, ${K}_3$) score those candidates using features derived from ${E}$, and ensemble model ${M}$ combines the scores into a final ranking. Recording these relationships tells the release controller where to test, and the tests on those consumers decide whether the new representations remain compatible.

Update approval begins with graph traversal and then requires behavioral and interface evidence. When embedding model ${E}$ is updated, the registry and release controller coordinate four steps:

1.  Traverse downstream edges to identify every dependent model (${R}$, ${K}_1$, ${K}_2$, ${K}_3$, and ${M}$).
2.  Re-evaluate each dependent model against the proposed embeddings.
3.  Block deployment of ${E}$ until every consumer passes.
4.  Roll out the approved version set through compatible intermediate states, retaining a validated rollback target. Topological ordering, which updates every producer before its consumers, is insufficient on its own if an existing consumer cannot accept the new producer’s outputs.

Without explicit dependency tracking, organizations discover architectural coupling through production outages when an upstream change silently corrupts downstream assumptions. A single YAML entry captures artifact location, training provenance, evaluation results, and declared dependencies ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^lst-registry-schema|listing 1]]). The downstream entries seed impact analysis; following their registry records reveals transitive consumers. Release approval additionally requires confirming that the update preserves the input-output contract expected by those consumers, or scheduling a coordinated rollout while retaining a validated rollback target.

``` yaml
model:
  name: user_embedding_v3
  version: "3.2.1"
  type: embedding_model
  domain: recommendation

artifact:
  path: gs://models/user_embedding_v3/3.2.1/
  format: tensorflow_savedmodel
  size_bytes: 4294967296

training:
  data_version: user_interaction_2024_01
  code_commit: abc123def
  started_at: 2024-01-15T10:00:00Z
  duration_hours: 48
  hardware: 8xA100-80 GB

evaluation:
  metrics:
    recall_at_100: 0.342
    embedding_quality: 0.891
  evaluation_set: eval_2024_01

dependencies:
  upstream:
    - feature_store/user_features_v2
    - feature_store/interaction_features_v1
  downstream:
    - models/candidate_retrieval_v4
    - models/ranking_ensemble_v2

serving:
  min_replicas: 10
  max_replicas: 100
  latency_p99_target_ms: 5
  memory_gb: 16

ownership:
  team: recommendation-core
  oncall: recsys-oncall-team
```

Listing 1: **Model Registry Schema**: A YAML entry capturing model metadata, artifact location, training provenance, and evaluation results for dependency tracking and reproducibility.

### Ensemble Management

^sec-ml-operations-scale-ensemble-management-67f5

The downstream entries in [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^lst-registry-schema|listing 1]], candidate retrieval and a ranking ensemble, point to a composition problem that registry edges alone cannot solve. When a recommendation pipeline chains retrieval, ranking, and filtering models owned by different teams, an upstream retrieval change that improves local recall can shift the candidate distribution enough to degrade final ranking. Recommendation systems exemplify this multi-model management challenge by chaining stages in sequence and combining predictions from several models within a stage. The platform must validate the complete recommendation interface even when different teams own its components.

#### Architectural Rationale for Recommendation Ensembles

^sec-ml-operations-scale-ensembles-dominate-recommendation-d94b

Recommendation architectures separate work when evaluating every candidate with the richest model would exceed the latency or compute budget. Retrieval produces a manageable candidate set, ranking scores that set with richer features, and later re-ranking or business-rule stages produce the final ordering ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-covington2016|Covington et al. 2016]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-liu2022|Liu et al. 2022]]). Within this path, specialized models can address competing objectives such as engagement, diversity, and freshness, while ensemble stages combine their outputs. The decomposition trades a smaller amount of expensive scoring for additional interfaces whose behavior the platform must validate.

The same decomposition improves experimentation velocity because teams can update individual components without retraining the entire recommendation stack, but that independence creates version-compatibility obligations for the platform. It also changes risk management. Other ensemble components can sometimes compensate when one model fails or produces poor results, yet the platform must detect when compensation hides a regression rather than resolving it.

#### Ensemble Deployment Patterns

^sec-ml-operations-scale-ensemble-deployment-patterns-c4eb

Deploying an ensemble update requires evaluating its effect on the composed system. Consider updating the fine ranking model within a recommendation ensemble. An illustrative staged ensemble deployment moves the update through four phases ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^tbl-ops-scale-ensemble-deploy|table 7]]): shadow deployment (24–48 hours logging without serving), canary (1 percent traffic for 4–8 hours), staged rollout (5 percent to 100 percent over 24–72 hours), and soak (7–14 days monitoring for delayed effects). These durations are planning assumptions; promotion requires enough eligible observations, mature outcomes, and acceptable guardrail metrics for the release decision.

| **Deployment stage** | **Actions**                                                          | **Duration** | **Rollback trigger**                   |
|:---------------------|:---------------------------------------------------------------------|:------------:|:---------------------------------------|
| **Shadow**           | New model scores alongside production, results logged but not served | 24–48 hours  | Quality metrics below threshold        |
| **Canary**           | 1% traffic receives new model results                                |  4–8 hours   | Statistical significance of regression |
| **Staged Rollout**   | 5% → 25% → 50% → 100%                                                | 24–72 hours  | Business metric degradation            |
| **Soak**             | Full traffic, extended monitoring                                    |  7–14 days   | Delayed effects emerge                 |

Table 7: **Staged Ensemble Deployment Pattern**: Four-phase rollout for updating recommendation ensemble components. Shadow deployment (24–48 hours) compares behavior without serving candidate outputs; resource isolation and outcome evidence bound what it establishes. Canary (1 percent traffic, 4–8 hours) enables statistical regression detection, staged rollout progressively increases exposure, and soak period (7–14 days) catches delayed interaction effects.

^tbl-ops-scale-ensemble-deploy

The extended timeline reflects the difficulty of detecting regressions in ensemble systems. A component change that improves its local metrics might degrade system-level performance through subtle interactions with other components.

#### Interaction Effects

^sec-ml-operations-scale-interaction-effects-9ae7

Ensemble components interact in ways that make local validation insufficient. If an upstream retrieval bug weakens the semantic similarity score passed to the ranking stage, a ranking model retrained during that period learns to down-weight the noisy retrieval score and rely more heavily on auxiliary popularity or recency signals. When engineers later fix the retrieval bug and restore sharp candidate sets, the adapted ranker still underweights semantic relevance, so an upstream improvement can paradoxically degrade end-to-end ranking quality. Even without retraining, a fixed ranker can respond poorly when an upstream update alters the feature distributions or candidate mix it was calibrated to score. Over longer horizons, ranking decisions also change which items users encounter, shaping the click and conversion feedback collected for future training. Logging intermediate candidate sets and stage scores helps isolate where these shifts enter the pipeline, while stable holdouts (fixed user groups kept on the previous system for comparison) and extended observation windows evaluate the complete system. Joint retraining is a targeted intervention when diagnostics confirm that downstream weights have adapted to an outdated upstream distribution, rather than a routine periodic reset.

### Model Lifecycle Management

^sec-ml-operations-scale-model-lifecycle-management-f112

Governing those dependencies over time requires controls at both ends of a model’s life. Promoting experimental notebooks straight to live traffic without staging gates causes avoidable outages. Retiring a model without migrating its consumers leaves behind “zombie models”[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.17 Footnotes#^fn2|²]] that silently drain GPU capacity and block platform upgrades. Lifecycle management keeps model dependencies from becoming permanent obligations: every promotion widens a model’s blast radius, and every retirement must migrate its consumers before the platform can reclaim resources. The lifecycle stages trace that progression from development to archive, each defined by the gates it imposes rather than by a status label.

``` text
Development → Staging → Canary → Production → Deprecation → Archive
```

In development, models exist as experimental artifacts. Operations requirements are intentionally light, but they are not optional: successful experiments must preserve results, version history, and enough reproducibility metadata to be challenged later. The operational concern is therefore transition readiness. A promising model should not move to staging until it has clear production-readiness criteria, automated evaluation against production-equivalent data, and documentation sufficient for review.

Staging tests the candidate as a deployable service before it serves user-visible outputs. Production-equivalent data, feature interfaces, and hardware make latency, throughput, and behavioral checks relevant to deployment. Shadow traffic can add evidence about live request patterns when its coverage justifies its cost. The promotion gate combines the checks required by the release contract with human review where model behavior or risk demands judgment.

Production widens the blast radius from validation traffic to live traffic, first through a small canary slice ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ml-operations-scale-canary-deployment-3d8b|section 12.5.5.2]]) and then at full exposure, so the model now requires continuous monitoring with alerting, capacity for traffic fluctuations, rollback procedures, and on-call support. Production is not a terminal state. Distribution shifts prompt investigation and evaluation; retraining is warranted when the resulting evidence supports an update. Feature and infrastructure changes likewise require compatibility checks, and periodic comparison with newer baselines tests whether the deployed model still earns its place.

The lifecycle closes only when a model can be retired without breaking its consumers. Deprecation identifies dependent systems, provides migration paths and timelines, maintains the old model until migration completes, and archives artifacts for reproducibility and audit. Organizations often underinvest in this final stage, allowing obsolete models to linger in production long after their replacements ship. Platform-level lifecycle enforcement closes that gap.

### Deployment Patterns by Model Count

^sec-ml-operations-scale-deployment-patterns-model-count-e071

How a model moves through those lifecycle stages depends on how many other models move with it. Rolling out a single isolated vision classifier once a month requires only a local canary, whereas pushing daily updates across a 50-model recommendation ensemble or hundreds of platform models without cross-model rate limits can trigger cascading regressions. The appropriate deployment pattern depends on the interdependence of the versions being updated, because a compatibility change can widen the rollback unit. Across the example deployment patterns in [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^tbl-ops-scale-deploy-patterns|table 8]], single model deployments update monthly for isolated vision classifiers, pipeline deployments weekly for 3–5 sequential NLP models, ensemble deployments daily for 10–50 recommendation components, and platform deployments continuously across hundreds of enterprise models. The cadences describe example operating contexts; model count does not determine release frequency or the evidence required for promotion.

| **Pattern**      | **Model count** | **Update frequency** |       **Example**       |
|:-----------------|:---------------:|:--------------------:|:-----------------------:|
| **Single Model** |        1        |       Monthly        |    Vision classifier    |
| **Pipeline**     |       3-5       |        Weekly        | NLP processing pipeline |
| **Ensemble**     |      10-50      |        Daily         |  Recommendation system  |
| **Platform**     |      100s       |      Continuous      | Enterprise ML platform  |

Table 8: **Deployment Patterns by Scale**: Four patterns addressing different model counts and update frequencies. Single model deployments (1 model, monthly updates) use standard canary rollouts, while platform deployments (100+ models, continuous updates) require automated policy enforcement, cross-model impact analysis, and global rate limiting to prevent simultaneous high-risk deployments.

^tbl-ops-scale-deploy-patterns

For a model without downstream model consumers, the rollback unit can be smaller. Canary deployments, blue-green switches,[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.17 Footnotes#^fn3|³]] and gradual rollouts still require a validated previous version together with compatible preprocessing, features, and serving configuration. Restoring the model artifact alone is sufficient only when those surrounding interfaces remain compatible.

Pipelines introduce ordering constraints because models execute in sequence and each model’s output feeds the next. Compatibility must hold at every intermediate deployment state. An upstream-first update is safe only if existing consumers accept its new outputs; otherwise the platform must prepare compatible consumers or stage both versions before switching traffic. The release record names the compatible version set and the rollback unit, which may span the entire pipeline.

Ensembles widen the coordination problem because multiple models may execute in parallel or in a graph. Different teams can update components on different schedules, partial updates may change only part of the ensemble, and the system behavior emerges from component interactions. Testing in isolation is therefore insufficient; integration testing becomes the deployment gate.

At platform scale, continuous deployment means some model is always being updated somewhere, so the platform must prevent individually safe changes from combining into an unsafe fleet state. Platform deployment requires automated rollout policies based on model risk classification, cross-model impact analysis before deployment approval, global rate limiting to prevent simultaneous high-risk deployments, and automated correlation of incidents with recent deployments.

### E-Commerce Model Ecosystem

^sec-ml-operations-scale-example-ecommerce-model-ecosystem-e47f

The registry, ensemble, lifecycle, and deployment-tier controls developed across this section converge in the e-commerce dependency graph that opened it, where updating a single user-embedding model alters the inputs to candidate retrieval, price sensitivity, ranking, and business rules simultaneously and turns a local model upgrade into a five-tier integration test. An e-commerce platform typically starts the graph with embedding models. A user embedding model generates user representations from behavior history, while a product embedding model represents products from attributes and interactions. Those embeddings are not final predictions; they are shared interfaces consumed by downstream services.

The next layer turns shared representations into candidate sets and business signals. A candidate retrieval model uses the embeddings to find relevant products, and a price sensitivity model estimates how strongly a user will respond to price changes. A ranking model then scores the candidate products using both embedding features and auxiliary signals, while a business rules model applies promotional and inventory constraints before results reach the user.

The resulting graph has five tiers, and its shape decides what a change costs. User and product representations travel over a shared bus into candidate retrieval and price sensitivity, which converge in ranking before business rules apply ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^fig-ecommerce-graph|figure 4]]).

![[90 Assets/Volume II/12 Ops Scale/Ecommerce Dependency Graph 2bf6eb20f5.svg]]

Figure 4: **E-Commerce Model Ecosystem**: Data sources feed a user embedding and a product embedding. A shared bus carries both embeddings into both mid-tier models, candidate retrieval and price sensitivity, whose outputs merge in the ranking model before business rules apply inventory and promotion constraints. Because every embedding reaches every downstream model, a change to the user embedding requires coordinated evaluation of all four consumers.

^fig-ecommerce-graph

Because the embedding bus in [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^fig-ecommerce-graph|figure 4]] branches directly to both mid-tier consumers, a change can affect candidate retrieval and price sensitivity before propagating through ranking and business rules. The platform therefore evaluates both direct embedding compatibility and downstream recommendation quality. If old consumers cannot accept the new embeddings, the release can retain both versions and route each consumer to the version it validated while migration proceeds. The rollback plan must preserve that compatible state as well. Because these models share features in addition to embeddings, the release must also pin versioned feature definitions and carry their guarantees of point-in-time correctness and freshness, the contracts that complete the state a release pipeline must validate.
