# V2-12.06 CI CD for ML at Scale

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12 ML Operations at Scale|V2-12 ML Operations at Scale]]

^sec-ml-operations-scale-cicd-ml-scale-730a

Versioned model dependencies and feature contracts define a candidate release, but they do not establish that it is safe to expose. Each model update must navigate the dependency web. In the e-commerce graph of [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^fig-ecommerce-graph|figure 4]], an embedding model update might require re-evaluation of four transitive downstream components, including the business rules layer, before any component can safely reach production. This coordination challenge transforms continuous integration and continuous deployment from a per-model concern into a platform orchestration problem. Whereas traditional software CI/CD focuses on code correctness and deployment reliability across interacting components, ML CI/CD adds learned behavior and changing data to that contract, requiring automated pipelines that validate data, verify statistical model performance, and confirm that upstream changes preserve downstream quality across every intermediate deployment state.

### Training Pipeline Automation

^sec-ml-operations-scale-training-pipeline-automation-9da3

When a training run is kicked off from an engineer’s laptop with unrecorded data paths and ad-hoc hyperparameters, no reviewer can reproduce the resulting checkpoint or verify what changed when it fails in staging. CI/CD for machine learning begins by making each training run an accountable producer of deployable artifacts. The pipeline records versioned inputs and execution conditions, defines recovery behavior, and preserves the results needed for deployment validation. Automation makes those obligations repeatable; reproducibility still depends on the recorded data, code, environment, and sources of nondeterminism.

#### Pipeline Stages

^sec-ml-operations-scale-pipeline-stages-06f5

[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^fig-ml-cicd|Figure 7]] stages the delivery lifecycle across continuous integration, training, and deployment, with an evaluation gate that blocks or registers a candidate. Monitoring returns drift signals to data validation. A confirmed population change may justify retraining, while a corrupted feature pipeline requires repair before it supplies another training run. The sequence matters because each stage establishes evidence for the next rather than treating every alert as permission to train and deploy.

![[90 Assets/Volume II/12 Ops Scale/ML Cicd 4ebe16ef8a.svg]]

Figure 7: **ML CI/CD Pipeline**: Read the top row left to right and the bottom row right to left. Continuous integration checks each commit; continuous training validates data, trains, and evaluates against a metrics gate that either blocks the candidate and raises an alert or registers it. Continuous deployment then moves the registered version through staging, a canary slice of traffic, and full production. Monitoring closes the loop: detected drift returns to data validation and investigation before a decision to retrain.

^fig-ml-cicd

1.  Data validation pins the data version and rejects schema, freshness, or distribution failures before they consume training capacity.
2.  Feature engineering preserves the feature contract between training and serving, so preprocessing changes do not become silent production regressions.
3.  Training records code, data, hyperparameters, hardware envelope, and random seeds so a promising artifact can be reproduced or challenged later.
4.  Evaluation compares the candidate with baselines, slice metrics (quality measured separately on subsets such as a region or user cohort), latency budgets, and task-specific gates before any user traffic is exposed.
5.  Artifact generation packages the model with its serving configuration, dependency versions, and rollback target.
6.  Registration records the artifact in the model registry with lineage, approvals, and deployment eligibility.

Each stage needs a defined retry boundary and durable outputs. If evaluation fails, the pipeline can reuse completed data-validation and feature-engineering results when their data, code, configuration, and relevant execution environment remain unchanged. Missing outputs or a changed dependency invalidate that reuse. Idempotent publication prevents a retry from registering duplicate artifacts or repeating external side effects.

#### Pipeline Orchestration

^sec-ml-operations-scale-pipeline-orchestration-705a

Training pipelines require orchestration systems that make dependency order, resource allocation, and failure recovery explicit. The orchestrator represents the workflow as a directed acyclic graph (DAG) and tracks dependencies between stages. It retries transient failures without rerunning unaffected work, schedules scarce resources such as GPUs and memory, caches intermediate results when inputs are unchanged, and records logs and artifacts for later debugging.

Common orchestration choices include Kubeflow Pipelines[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.17 Footnotes#^fn6|⁶]] ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-bisong2019|Bisong 2019]]), Airflow with ML extensions, and cloud-native solutions like Vertex AI Pipelines or SageMaker Pipelines. The choice depends on which dependency and resource contracts the platform must enforce, as well as existing infrastructure, team expertise, and scale requirements. Orchestration fixes the execution contract; parameterization fixes the variation contract, so the same graph can run against different data, models, and hardware envelopes without becoming a new program each time.

#### Pipeline Parameterization

^sec-ml-operations-scale-pipeline-parameterization-a5e4

Effective pipelines separate configuration from code ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^lst-pipeline-params|listing 3]]). The listing’s evaluation block names two standard ranking metrics: normalized discounted cumulative gain at rank 10 (NDCG@10), which rewards placing relevant items near the top of a list, and mean reciprocal rank (MRR), which averages the inverse position of the first relevant item.

``` yaml
training_pipeline:
  model_type: transformer_ranking
  data:
    train_path: gs://data/train/2024-01-*
    eval_path: gs://data/eval/2024-01-15
    schema_version: v3.2
  features:
    user_features: [embedding, history, demographics]
    item_features: [embedding, attributes, popularity]
  training:
    epochs: 10
    batch_size: 4096
    learning_rate: 0.001
    optimizer: adam
    hardware: 4xA100
  evaluation:
    metrics: [ndcg_10, mrr, coverage]
    baseline_model: ranking_v2.1.0
```

Listing 3: **Pipeline Parameterization**: A YAML configuration separating data paths, feature sets, training hyperparameters, and evaluation criteria from pipeline code.

^lst-pipeline-params

The separation enables configuration-driven training because the platform can vary data versions, hyperparameters, and resource requests without rewriting pipeline code. A parameter file is also an audit input, but a path or version label alone does not prove which bytes a run consumed. The execution record must resolve those references to immutable data and artifacts and retain the actual environment, feature definitions, and evaluation policy. That record lets a release reviewer reconstruct the conditions behind the candidate’s evidence.

### Validation Gates

^sec-ml-operations-scale-validation-gates-89a2

An immutable execution record tells a reviewer what a training run produced. Validation gates decide whether that candidate may advance toward production, because promoting a model solely for a 1 percent aggregate NDCG gain can still double p99 tail latency, degrade a protected subgroup, or rely on a corrupted upstream feature. A release gate consumes a versioned evidence bundle tying the candidate and its dependencies to metrics, thresholds, and accountable owners. Model performance, latency, policy and fairness constraints, data quality, and operational readiness each answer a different failure mode. Together they form an evaluation contract, a single versioned record of release evidence that remains attached to the release as it moves from offline validation to production experiments ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ops-scale-end-to-end-evaluation-contract|section 12.5.8]]).

#### Performance Gates

^sec-ml-operations-scale-performance-gates-18e5

Performance validation combines minimum acceptable performance with comparisons against the production baseline and historical results. The release policy names the primary improvement sought and the regression bounds permitted on secondary metrics, rather than requiring every metric to improve simultaneously. A performance gate therefore checks three conditions: absolute thresholds, relative improvement over the production model, and regression bounds on secondary metrics ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^lst-performance-gates|listing 4]]).

``` python
def evaluate_performance_gate(
    candidate_metrics, production_metrics, thresholds
):
    """
    Evaluate whether candidate model passes performance gates.

    Returns tuple of (passed: bool, reasons: list)
    """
    import math

    required_metrics = ("ndcg_10", "mrr", "coverage")
    required_thresholds = ("min_ndcg", "min_improvement", "max_regression")
    try:
        values = [candidate_metrics[k] for k in required_metrics]
        values += [production_metrics[k] for k in required_metrics]
        values += [thresholds[k] for k in required_thresholds]
        valid = all(math.isfinite(v) for v in values)
        valid = valid and production_metrics["ndcg_10"] > 0
        valid = valid and 0 <= thresholds["max_regression"] <= 1
    except (KeyError, TypeError, ValueError):
        valid = False
    if not valid:
        return False, ["Missing, nonfinite, or invalid gate inputs"]

    reasons = []

    # Absolute threshold check
    if candidate_metrics["ndcg_10"] < thresholds["min_ndcg"]:
        reasons.append(
            f"NDCG_10 {candidate_metrics['ndcg_10']:.4f} below minimum {thresholds['min_ndcg']}"
        )

    # Relative improvement check
    relative_improvement = (
        candidate_metrics["ndcg_10"] - production_metrics["ndcg_10"]
    ) / production_metrics["ndcg_10"]
    if relative_improvement < thresholds["min_improvement"]:
        reasons.append(
            f"Improvement {relative_improvement:.2%} below minimum {thresholds['min_improvement']:.2%}"
        )

    # Regression check on secondary metrics
    for metric in ["mrr", "coverage"]:
        if candidate_metrics[metric] < production_metrics[metric] * (
            1 - thresholds["max_regression"]
        ):
            reasons.append(
                f"{metric} regression exceeds {thresholds['max_regression']:.2%} tolerance"
            )

    return (len(reasons) == 0, reasons)
```

Listing 4: **Performance Gate Evaluation**: A validation function that checks absolute thresholds, relative improvement over the production model, and regression bounds on secondary metrics.

#### Latency Gates

^sec-ml-operations-scale-latency-gates-bf9e

Production models must meet workload-specific latency requirements. Validation measures representative request shapes at expected load, batching, and hardware. Illustrative thresholds span two orders of magnitude, from a 5 ms median for fraud detection to a 500 ms median time to first token (TTFT) for an LLM, and they are policy choices rather than universal model-type requirements ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^tbl-ops-scale-latency-gates|table 12]]). The LLM row measures TTFT, reflecting the prefill phase of **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.09 Prefill and Decode#^sec-inference-scale-prefill-decode|Prefill and Decode]]**; completion latency requires a separate output-length contract for decode. The other rows measure request-to-response latency.

| **Model type**      | **p50 target** | **p99 target** | **Gate action if exceeded**            |
|:--------------------|:--------------:|:--------------:|:---------------------------------------|
| **LLM (TTFT)**      |     500 ms     |    2000 ms     | Block deployment, require optimization |
| **Recommendation**  |     10 ms      |     50 ms      | Block deployment                       |
| **Fraud Detection** |      5 ms      |     20 ms      | Block deployment, high priority        |
| **Vision**          |     50 ms      |     200 ms     | Warning, conditional approval          |

Table 12: **Illustrative Latency Gates**: Assumed p50 and p99 service targets under a declared request distribution and load. LLM targets refer to TTFT; other targets cover the complete response. Product risk and the service contract determine thresholds and exception authority.

^tbl-ops-scale-latency-gates

Latency gates catch overt performance violations, but some regressions pass every gate and still degrade the product. The most dangerous failures are semantically silent: valid outputs built on corrupted inputs.

**Example 12.2: Silent model regression**

**Scenario**: A high-throughput product ranking model ($25{,}000\text{ QPS}$) passes offline validation and serving latency gates (per-request latency ${L_{\text{lat,SLO}}} < 12\text{ ms}$), but causes a 3.2 percent conversion rate drop post-deployment.

**Diagnosis**: An upstream schema change caused a key user-affinity feature to return `null` for 8 percent of queries. The serving layer silently imputed `null` as `0.0`, a valid float value, so HTTP error rates and latency remained normal while prediction quality degraded unalerted for 48 hours.

**Systems lesson**: Syntactically valid feature imputations cause semantically silent production failures. Automated release pipelines and monitoring systems must evaluate feature distribution shifts and null rates alongside system uptime and latency SLOs.

#### Fairness Gates

^sec-ml-operations-scale-fairness-gates-145c

Fairness concepts become operational at release time when policy choices are encoded as thresholds. For models affecting users, fairness validation turns a policy commitment into a release gate. A gate cannot test whether “the model is fair” in the abstract, because different contexts encode fairness differently and some definitions cannot hold at once. Each chosen definition becomes an executable bound on a measured gap between protected groups. A demographic-parity gate bounds the difference between groups in the rate of positive predictions; an equalized-odds gate bounds the difference in prediction rates between groups that share the same true outcome ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-hardt2016equality|Hardt et al. 2016]]). The operational point is not that every gate should enforce every definition. The gate must record which definition the organization chose, compare the measured value against historical baselines as well as absolute thresholds, and route borderline cases to human review because a near-threshold fairness result is also a governance decision.

↪ The fairness criteria behind these gates, and why they cannot all hold at once, are developed in **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/16 Responsible AI/V2-16.06 Fairness and Bias Mitigation#^sec-responsible-ai-fairness-machine-learning-2ba4|Fairness in machine learning]]**.

#### Data Quality Gates

^sec-ml-operations-scale-data-quality-gates-4c04

Before training or deployment, data quality validation reapplies the schema, distribution, freshness, and completeness checks of [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.05 Feature Store Operations#^sec-ml-operations-scale-data-quality-operations-e77b|section 12.4.7]] as a release gate ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-caveness2020|Caveness et al. 2020]]). Passing them establishes evidence for the properties tested; it does not rule out an untested semantic error.

These gates complete the offline evidence bundle. The next evidence must come from production traffic, gathered first without exposing users and then at a bounded share of live requests.

### Production Experimentation as a Release Gate

^sec-ml-operations-scale-production-experiment-validation

Offline validation on static holdouts cannot catch a candidate model that doubles tail latency under live concurrency or reduces user clicks when its predictions interact with real traffic. Once the offline gates pass, production experiments evaluate the candidate under a controlled exposure policy, starting from shadow traffic, which exposes no user to its outputs. Shadow traffic tests behavior without returning candidate outputs, interleaving compares rankers within a combined presentation, and A/B tests compare assigned variants. Network-effect checks determine whether interactions between experimental units undermine that comparison. These methods answer different questions; every release need not use all of them. Each supplies evidence for the online-experiment plane of the evaluation contract assembled in [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ops-scale-end-to-end-evaluation-contract|section 12.5.8]], so the statistics that follow are tools for filling one row of the release record, not a separate discipline.

Before exposure begins, the release record must name the invariant metrics, decision threshold, maximum user and infrastructure blast radius, stopping rule, rollback owner, and evidence required for promotion. A candidate that improves its primary metric but exhausts latency, reliability, fairness, or cost headroom fails the gate.

#### Shadow Deployment and Traffic Replay

^sec-ml-operations-scale-shadow-deployment-traffic-replay-ee4f

Shadow deployment runs the new model alongside production, receiving copied inputs and logging outputs without returning them to users. [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^fig-shadow-deployment|Figure 8]] contrasts mirroring to an isolated candidate (Panel A) with canary deployment (Panel B), which exposes a controlled share of traffic to candidate responses. Shadow execution can reveal defects absent from offline tests, but its resource consumption and external side effects still require containment. It also cannot reveal how users would react to outputs they never receive.

![[90 Assets/Volume II/12 Ops Scale/Shadow Deployment 1e393cccc0.svg]]

Figure 8: **Shadow and Canary Deployment**: In shadow deployment (A), the proxy mirrors all production traffic to the candidate; users receive only the production response, and both outputs are compared offline. No user sees the candidate’s output, but mirroring every request doubles inference load, so the shadow path needs its own capacity and must be isolated so it cannot slow production. In canary deployment (B), the splitter sends a small weighted slice of live traffic to the candidate (here the 5 percent stage) and widens it through the 1, 5, 25, 50, and 100 percent stages as evidence accumulates, rolling back if SLO or error metrics drift.

^fig-shadow-deployment

Shadow deployment earns its duplicate infrastructure cost when it answers validation questions offline tests cannot. A full-load shadow run measures errors, memory growth, and latency against the release SLOs, exposing leaks and resource contention that small offline datasets miss. Comparison under real traffic reveals output shifts such as changed confidence scores in a classifier or changed diversity in a recommender. That evidence holds only for the observed workload, duration, dependencies, and contention, and rare inputs may never arrive, so the shadow load profile and run length belong in the release record beside the result. Output differences require interpretation; they do not by themselves establish improvement or regression.

Shadow deployment requires capturing and replaying production traffic, and the replay choice determines the trade-off among fidelity, cost, and freshness. Three architectural patterns address different operational requirements.

Live mirroring duplicates every production request to the shadow model in real time. The production model serves the response while the shadow model processes the same input in parallel, providing immediate validation at full production scale but requiring shadow infrastructure capable of handling 100 percent traffic load. To keep this validation path from becoming a production dependency, the serving system must invoke shadow requests asynchronously, enforce timeouts, shed shadow load when it falls behind, and isolate resources so shadow work cannot affect production responses.

Sampled replay mirrors a configurable percentage of production traffic to shadow models. This reduces infrastructure costs, but the sampling rate and observation window must still supply enough eligible examples for the targeted failures. Uniform random sampling estimates the sampled traffic population, while stratification can ensure coverage of important segments. Adaptive sampling concentrates investigation on patterns where candidate and production outputs diverge. Such targeted samples need recorded inclusion probabilities, the chance that each request entered the sample, and an estimator that corrects for them before their error rates can be interpreted as fleet-wide rates.

Batch replay captures production traffic logs and replays them asynchronously against shadow models. This decouples validation from the live request path and supports regression tests during available capacity windows. Fidelity depends on what the logs preserve. Replaying request contents without their historical feature state can change the task, while replaying them faster changes queueing and load. A load test must reproduce the relevant arrival pattern and serving conditions; historical replay still cannot observe user responses to candidate outputs.

Effective shadow deployment requires quantitative comparisons tied to the intended change. Output divergence locates differences from production: classification systems track disagreement rates, probability shifts, and class-specific concentration, while regression systems can compare prediction errors or differences between outputs. A changed prediction is not inherently a regression; outcome evidence or a validation oracle, an independent check that determines the correct output, must establish its quality. Performance metrics assess latency, throughput, and resource consumption against the operating contract. A candidate with equivalent accuracy but 50 percent higher p99 latency needs review against that contract, even if both versions remain below the SLO.

The metric set must also separate operational failures from genuine model changes. Error-mode metrics count timeouts, exceptions, malformed outputs, and null predictions. A shadow model that times out on 0.1 percent of requests encounters 1,000 failures per day at 1M requests/day scale, and the request patterns that trigger those failures guide remediation. Statistical validation then determines whether observed differences represent genuine model changes or random variation. Because production and shadow models process the same requests, their outcomes are paired. Define a binary failure against a labeled outcome or validation oracle, let ${n_{\text{prod}}}$ count requests on which production fails and shadow succeeds, and let ${n_{\text{shadow}}}$ count requests on which shadow fails and production succeeds. McNemar’s large-sample test uses the discordant pairs:

$$
{\chi^2}= \frac{({n_{\text{prod}}}-{n_{\text{shadow}}})^2}{{n_{\text{prod}}}+{n_{\text{shadow}}}}
$$

The test starts from a null hypothesis, the assumption that production and shadow fail with equal probability. Under that hypothesis, the statistic approximately follows a chi-square distribution with one degree of freedom. The significance level ${\alpha_{\text{sig}}}$ is the probability of rejecting the null hypothesis when it is true, and the critical value is the threshold that the statistic exceeds with that probability when the null hypothesis holds.

Equivalently, the p-value is the probability of a statistic at least as large as the one observed if the null hypothesis holds, and the test rejects when the p-value falls below ${\alpha_{\text{sig}}}$. For a one-degree-of-freedom test at ${\alpha_{\text{sig}}} = 0.05$, the critical value is 3.84, so reject equal failure probabilities when ${\chi^2}> 3.84$. A rejection indicates that the failure probabilities differ, and the larger discordant count shows which model fails more often. Marginal failure rates, such as 1 percent for production and 1.5 percent for shadow, do not determine this statistic by themselves; the paired discordant counts ${n_{\text{prod}}}$ and ${n_{\text{shadow}}}$ must be retained.

#### Shadow Deployment Workflow

^sec-ml-operations-scale-worked-example-shadow-deployment-workflow-216d

Consider an illustrative fraud detection service processing 5 million transactions daily. A sampled shadow phase mirrors 10 percent of traffic for three days. Assume the eligible labeled subset yields recall of 94.2 percent for the shadow model versus 94.5 percent in production, and precision of 87.1 percent versus 82.3 percent. These point estimates alone establish neither improvement nor noninferiority, the finding that the shadow model is worse by no more than an agreed tolerance. The gate also needs labeled counts, paired outcomes, label maturity (enough elapsed time for each transaction’s true outcome to be known), uncertainty intervals, and a prespecified recall tolerance. Assume shadow p99 latency is 45 ms versus 38 ms in production, both below this service’s 50 ms SLO, a looser contract than the illustrative 20 ms fraud-detection gate in [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^tbl-ops-scale-latency-gates|table 12]]. The team proceeds to full shadow only after the statistical gate passes.

The full-shadow phase mirrors 100 percent of traffic for five days. In this scenario, the same labeled-data analysis supports the precision gain at full scale, but the run also exposes an edge case. The shadow model flags 0.02 percent of transactions as errors due to an unexpected feature distribution, which is 1,000 transactions per day. The root cause is heightened sensitivity to outliers in transaction amount. Adjusting feature clipping thresholds reduces the error rate to 0.001 percent in a new shadow run. Because clipping also changes model inputs, the revised candidate must pass the precision, recall, latency, and slice gates again before canary deployment.

Post-deployment validation then compares actual production metrics with the shadow predictions. Precision materializes at 87.3 percent in production vs. 87.1 percent in shadow, a nearby point estimate. Confirming agreement still requires uncertainty bounds and checks for label or traffic shifts; similarity between two percentages is insufficient.

#### Criteria for Shadow Deployment

^sec-ml-operations-scale-shadow-deployment-essential-8087

Shadow deployment earns its cost when the additional evidence reduces expected deployment harm enough to justify duplicate execution, comparison logging, and analysis. That cost includes infrastructure that bounds the shadow path’s effect on production. The mirroring layer enforces sampling, timeouts, and load shedding. Separate compute pools, network allocation, and database capacity keep shadow work from stealing production capacity, because shared queues or dependencies can still transmit failures that asynchronous invocation alone does not prevent.

New architectures, consequential predictions, live feature dependencies, and tight latency budgets can make the evidence worth that cost, but only for failures shadow traffic can reveal; user responses to candidate outputs remain unobserved, and rare events may remain absent. A smaller shadow phase, or a direct move from offline validation to a bounded canary, can be appropriate when existing evidence covers the relevant failure modes and residual exposure is acceptable. Routine retraining does not establish low risk by itself, because changed data or parameters can alter behavior without an architecture change. The platform should compare the additional evidence shadow execution can provide with its resource cost, the harm a canary could cause before containment, and the time needed to observe that harm.

#### Interleaving Experiments

^sec-ml-operations-scale-interleaving-experiments-519c

Interleaving experiments[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.17 Footnotes#^fn7|⁷]] were developed for ranking and search evaluation ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-chapelle2012|Chapelle et al. 2012]]) and are also used in recommender personalization experiments ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-netflix2017interleaving|Netflix Technology Blog 2017]]). Rather than splitting users between variants, interleaving presents items from both variants to each user, then measures which items users engage with.

The advantage of interleaving is statistical efficiency. An interleaving experiment can require far fewer samples than A/B testing, and Netflix reports more than 100$\times$ fewer users for some ranking experiments ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-netflix2017interleaving|Netflix Technology Blog 2017]]), because each user provides direct comparison signals rather than contributing only to aggregate statistics.

In an interleaving workflow, the variants produce ranked lists that a method such as team draft or probabilistic interleaving combines into one presentation. The mixing and credit-assignment rules must control position effects and identify which ranker contributed each item. Engagement with those items supplies a relative preference signal. [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^fig-interleaving-vs-ab|Figure 9]] contrasts the between-cohort comparison of A/B testing (Panel A) with this within-user comparison (Panel B). The latter can screen candidates efficiently, but preference within a blended list does not directly measure the effect of deploying either complete ranking policy on long-term outcomes such as retention. Those outcomes still require an experiment designed to measure them.

![[90 Assets/Volume II/12 Ops Scale/Interleaving Vs Ab 1529cfcc21.svg]]

Figure 9: **Interleaving vs. A/B Testing**: (A) A/B testing splits users into cohorts, and each cohort sees only one ranker’s list, so the comparison is between cohort means and must overcome the variation between users. (B) Interleaving has both rankers rank the same query for each user and merges the results into one list (here by team draft); each click is credited to the ranker that contributed the item, so every user supplies a paired, within-user comparison. That pairing can make ranker-preference screening more sample-efficient; it does not measure the full deployment outcome assessed by an A/B test ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-netflix2017interleaving|Netflix Technology Blog 2017]]).

#### A/B Test Sizing and Significance

^sec-ml-operations-scale-ab-testing-statistical-foundations-b9bd

At platform scale, experiment design determines how long a release occupies capacity and exposes users. A/B testing provides frameworks for comparing model variants ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-kohavi2008|Kohavi et al. 2009]], [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-kohavi2020trustworthy|2020]]), but its release decision depends on statistical power,[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.17 Footnotes#^fn8|⁸]] significance thresholds, and multiple testing correction. The formulas below supply inputs to the operational contract: the number of eligible observations, the promotion rule, and the permitted stopping schedule. They do not establish that behavior remains reliable outside the evaluated population.

For an equally allocated comparison of two proportions, the standard normal-approximation sample plan uses four parameters: significance level $({\alpha_{\text{sig}}})$, statistical power $(1-{\beta_{\text{stat}}})$, baseline conversion rate $({p_0})$, and minimum detectable effect $({\delta_{\text{MDE}}})$. [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^eq-ops-scale-ab-sample-size|Equation 4]] estimates observations per variant, assuming independent eligible outcomes and a small absolute difference near the baseline rate. Holding the other inputs fixed, the requirement scales inversely with the square of that difference:

![[90 Assets/Volume II/12 Ops Scale/Vol2 Ops Scale Margin 002 2e37a00fdb.svg]]

*Black inverse-square curve labeled n proportional to 1 over delta MDE squared, with a red dot labeled small effect high on the steep part and a gray dot labeled large effect at the flat end.*

*Detecting smaller effects explodes the required sample size.*

$$
{n} = \frac{({z_{\alpha/2}} + {z_{\beta}})^2 \times 2{p_0}(1-{p_0})}{{\delta_{\text{MDE}}}^2} \tag{4}
$$

^eq-ops-scale-ab-sample-size

where ${z_{\alpha/2}}$ is the two-sided critical value for significance level ${\alpha_{\text{sig}}}$ (typically 1.96 for ${\alpha_{\text{sig}}} = 0.05$), ${z_{\beta}}$ is the critical value for power (typically 0.84 for 80 percent power), ${p_0}$ is the baseline rate, and ${\delta_{\text{MDE}}}$ is the minimum detectable effect as an absolute difference. Both critical values use the positive upper-tail convention: the upper-tail areas are ${\alpha_{\text{sig}}}/2$ and ${\beta_{\text{stat}}}$, respectively.

Once data is collected, a two-proportion z-test determines if the observed difference is statistically significant. [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^eq-ab-ztest|Equation 5]] computes the test statistic as the difference in observed rates normalized by the pooled standard error:

$$
{z}= \frac{{\hat{p}_B}- {\hat{p}_A}}{\sqrt{{\hat{p}}(1-{\hat{p}})(\frac{1}{{m_A}} + \frac{1}{{m_B}})}} \tag{5}
$$

^eq-ab-ztest

where ${\hat{p}_A}$ and ${\hat{p}_B}$ are the observed conversion rates for control and treatment, ${m_A}$ and ${m_B}$ are sample sizes, and ${\hat{p}}= \frac{{m_A}{\hat{p}_A}+ {m_B}{\hat{p}_B}}{{m_A}+ {m_B}}$ is the pooled proportion. For the two-sided test, if $|{z}| > {z_{\alpha/2}}$, reject the null hypothesis and conclude the variants differ significantly.

#### Sample Size for Recommendation Models

^sec-ml-operations-scale-worked-example-sample-size-recommendation-model-5d42

A recommendation system has baseline CTR of 5 percent. The team wants to detect a 10 percent relative improvement (0.5 percentage points absolute) with 95 percent confidence and 80 percent power.

Parameters:

- ${z_{\alpha/2}} = 1.96$ (95 percent confidence, two-tailed)
- ${z_{\beta}} = 0.84$ (80 percent power)
- ${p_0}= 0.05$ (baseline CTR)
- ${\delta_{\text{MDE}}} = 0.005$ (0.5 percentage point improvement)

Calculation:

$$
{n} = \frac{(1.96 + 0.84)^2 \times 2 \times 0.05 \times 0.95}{0.005^2}
$$

$$
{n} = \frac{7.84 \times 0.095}{0.000025} = \frac{0.7448}{0.000025} = 29{,}792
$$

Each variant requires approximately 30,000 samples, totaling 60,000 observations. If requests supply independent eligible observations with immediately available outcomes, 1 million requests per day split evenly between variants collects that sample in less than 2 hours. However, for a model with 1 percent baseline CTR detecting a 5 percent relative improvement (0.05 percentage points), the calculation yields:

$$
{n} = \frac{7.84 \times 2 \times 0.01 \times 0.99}{0.0005^2} = \frac{0.155232}{0.00000025} = 620{,}928
$$

Now each variant needs approximately 621K samples. Under the same independence and outcome-availability assumptions, 1M total requests/day split evenly between the two variants collects that sample in about 30 hours. Required observation windows can extend either experiment beyond its collection time. Here, the lower baseline and smaller relative improvement also imply a much smaller absolute effect. At a fixed relative improvement, rarer outcomes require more observations; a fixed absolute effect would give a different comparison.

#### Multiple Testing Correction

^sec-ml-operations-scale-multiple-testing-correction-023f

Running multiple A/B tests simultaneously or sequentially without correction inflates the familywise error rate, the probability that at least one test in the family reports a false positive. With 20 independent tests whose null hypotheses are all true, at ${\alpha_{\text{sig}}} = 0.05$, that probability is:

$$
\Pr(\text{at least one false positive}) = 1 - (1-{\alpha_{\text{sig}}})^{k}= 1 - 0.95^{20} = 0.642
$$

The result is a 64 percent chance of at least one false rejection; a two-sided rejection can point in either direction. Two families of correction address this problem.

Bonferroni correction adjusts the significance threshold to ${\alpha_{\text{sig}}'} = \frac{{\alpha_{\text{sig}}}}{{k}}$ for ${k}$ tests. This is conservative but simple. For 20 tests with ${\alpha_{\text{sig}}} = 0.05$, use ${\alpha_{\text{sig}}'} = 0.0025$ for each test. This controls the familywise error rate but reduces statistical power; the Šidák variant, which sets the per-test level so that independent tests reach the familywise target exactly, is only slightly more lenient (0.00256 per test for 20 tests).

False discovery rate (FDR) control using the Benjamini-Hochberg procedure bounds the expected proportion of false discoveries among rejected hypotheses under independence or suitable positive dependence. It is not a hard cap on the probability of making at least one false discovery in a batch, which makes it appropriate when screening many candidate changes where a small fraction of false positives is acceptable. Order the ${k}$ observed p-values from smallest to largest, ${{p_{\text{val}}}}_{(1)} \leq {{p_{\text{val}}}}_{(2)} \leq \ldots \leq {{p_{\text{val}}}}_{({k})}$, and find the largest rank ${r}$ whose p-value satisfies:

$$
{{p_{\text{val}}}}_{(i)} \leq \frac{{r}}{{k}} \times {\alpha_{\text{sig}}}
$$

Reject all hypotheses ${H}_{(1)}, \ldots, {H}_{({r})}$ up to that cutoff rank. Only the most extreme p-value ${{p_{\text{val}}}}_{(1)}$ faces the strict Bonferroni threshold $\frac{1}{{k}}{\alpha_{\text{sig}}}$; each subsequent rank ${r}$ is compared against a linearly growing allowance $\frac{{r}}{{k}}{\alpha_{\text{sig}}}$. This step-up procedure therefore yields substantially higher statistical power than Bonferroni when evaluating large experiment portfolios.

#### Multiple Testing Scenario

^sec-ml-operations-scale-worked-example-multiple-testing-scenario-ce6c

A platform team runs 30 A/B tests per quarter comparing candidate models. Suppose every null hypothesis is true and each test has a calibrated false-positive probability of ${\alpha_{\text{sig}}} = 0.05$. Without correction, the expected count is $30 \times 0.05 = 1.5$ false rejections per quarter, or approximately 6 models over a year. These are false claims of a difference, not necessarily improvements: a two-sided rejection can point toward either benefit or harm.

Applying Bonferroni correction: ${\alpha_{\text{sig}}'} = \frac{0.05}{30} = 0.00167$ per test. This requires larger sample sizes. For the recommendation model example in [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ml-operations-scale-worked-example-sample-size-recommendation-model-5d42|section 12.5.3.6]] (5 percent baseline, 0.5-percentage-point effect), the original requirement was 30K samples per variant. With a two-sided Bonferroni threshold, the critical value rises to about 3.14, increasing the requirement to roughly 60K samples per variant.

Using FDR control at ${q}= 0.05$, the Benjamini-Hochberg procedure bounds the expected false-discovery proportion across repeated experiment families under its dependence assumptions, counting the proportion as zero when there are no rejections. Observing 10 significant results out of 30 tests does not establish how many of those 10 are false or give a conditional guarantee for that quarter. The procedure accepts a different error criterion from familywise control and can gain power in exchange.

The choice begins with the error the decision must control. When even one false promotion among the planned comparisons has serious consequences, familywise control is appropriate; Bonferroni is one simple option. Exploratory screening may instead use FDR control when a bounded expected proportion of false discoveries is acceptable and later validation will assess candidates individually. The experiment family and error criterion belong in the release plan before results are inspected.

**Checkpoint 12.3: Family-wise error rate under multiple testing**

The correction methods are Bonferroni and Benjamini-Hochberg. Apply the family-wise reasoning to a smaller platform.

**Family-wise error**: for 20 simultaneous A/B tests per quarter at ${\alpha_{\text{sig}}} = 0.05$ with no correction, calculate the expected number of false positives and the family-wise error rate under independence.

**Bonferroni correction**: apply Bonferroni correction, calculate the per-test threshold ${\alpha_{\text{sig}}'}$, compute the family-wise error rate after correction, and compare it to the uncorrected rate.

**Bonferroni vs. FDR**: for 20 tests where the team expects most candidates to genuinely improve the metric, choose Bonferroni or Benjamini-Hochberg FDR control and justify the statistical-power trade-off.

#### Sequential Testing and Early Stopping

^sec-ml-operations-scale-sequential-testing-early-stopping-5b04

Traditional A/B tests fix sample size in advance and evaluate once. Release teams rarely wait that long without looking, and looking is where the error rate leaks. A fixed-sample test checked after every batch of observations and stopped at the first $|{z}| > 1.96$ gets many chances to cross the threshold by chance, so its realized false-positive rate climbs well above the nominal 5 percent. Sequential testing budgets for those looks in advance, allowing monitoring during data collection with principled early stopping rules. Stopping can occur earlier when the evidence is strong, but the gain depends on the hypotheses, effect size, and stopping design.

The sequential probability ratio test, the classic design, updates a likelihood ratio after every observation and stops when the ratio crosses either of two thresholds set from the target error rates. Because it assumes two fully specified hypotheses, release experiments more often use group sequential designs. Group sequential methods divide the experiment into planned analysis stages. At each stage, the test statistic is compared with adjusted thresholds that maintain the overall ${\alpha_{\text{sig}}}$. The boundary family decides how that error budget is spent across the looks. An O’Brien-Fleming boundary spends almost none of it early, demanding overwhelming evidence to stop at the first looks and keeping the final threshold close to the fixed-sample value. A Pocock boundary spends it evenly, applying the same stricter threshold at every look. For a canary whose guardrail metric is checked every hour, the evaluation contract must prespecify a valid sequential stopping rule, such as one of these boundaries. Comparing each hourly look against the single-look 1.96 reintroduces the inflation the design exists to prevent.

A valid stopping rule still rests on the independence and stationarity assumptions behind these formulas, and production tests can violate both. Carryover occurs when treatment changes behavior after exposure ends, so a design that reassigns users must account for that persistence. Novelty can make early responses differ from later behavior, and no fixed number of weeks guarantees that the effect has settled, so observation windows must cover the relevant behavioral cycles and outcome delays. Surrogate metrics such as clicks can also move in a different direction from long-term objectives such as retention and revenue, which is why a release gate pairs the short-term surrogate with guardrail metrics that may require longer observation. Interference between users is the most consequential violation for social and marketplace products, because it biases the estimated effect itself rather than only its variance.

### SUTVA Violations and Network Effects

^sec-ml-operations-scale-sutva-violations-network-effects-2252

When User A on a social platform receives better content recommendations from a treatment model and shares those posts with friends in the control group, User B’s engagement rises even though User B never received the new algorithm. The control condition becomes contaminated through the natural mechanics of a networked product, violating the assumption behind every sample-size and significance calculation above that one user’s treatment assignment does not change another user’s outcome.

The stable unit treatment value assumption (SUTVA) requires well-defined treatment versions and no interference between units ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-rubin1980randomization|Rubin 1980]]). Its no-interference component says that user ${i}$’s outcome ${Y^{\text{pot}}}_{{i}}({w})$ depends on their own assignment ${w}$, not on other users’ assignments. Versioned releases address the treatment-definition requirement; network interactions challenge the second requirement. Ignoring those interactions can bias the effect estimate used for a deployment decision ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-hudgens2008toward|Hudgens and Halloran 2008]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.16 Source References#^ref-eckles2017design|Eckles et al. 2017]]).

Interference can travel through direct connections, shared markets, or geographic and temporal spillovers. A treated user may share recommended content with control users, changing their outcomes even though they never receive the new ranker. A ridesharing incentive may change driver supply and wait times for both groups. Local merchant recommendations may redirect traffic from neighboring areas assigned to control. In these examples, independent user assignment remains possible, but each user’s assignment no longer describes all the treatment exposure affecting that user’s outcome. The direction and size of the resulting bias depend on the interaction and the effect being estimated.

#### Quantifying SUTVA Violations

^sec-ml-operations-scale-quantifying-sutva-violations-e04e

Grouping connected users into randomized clusters changes the precision calculation as well as the exposure pattern. For clusters of equal or similar size with a common within-cluster outcome correlation, [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^eq-sutva-vif|equation 6]] gives a planning approximation for variance inflation relative to independent observations:

$$
\text{DEFF} \approx 1 + ({m}- 1){\rho_{\text{ICC}}} \tag{6}
$$

^eq-sutva-vif

where ${m}$ is the average cluster size and ${\rho_{\text{ICC}}}$ is the intra-cluster correlation of outcomes (how similar outcomes are within connected user groups). Multiplying an independent-observation sample plan by this factor approximates the additional observations needed under those assumptions. Unequal cluster sizes and the chosen estimator require a more specific precision analysis. This variance adjustment does not identify or remove bias from interference across clusters.

#### Network Effect Bias in Social Recommendation

^sec-ml-operations-scale-worked-example-network-effect-bias-social-recommendation-3de0

An illustrative social platform tests a new feed ranking algorithm. Individual user randomization assigns 50 percent of users to treatment.

Experimental setup:

- 10 million users, average 150 connections each
- Outcome: daily engagement minutes

With independent 50 percent assignment, a typical control user’s 150 connections split roughly evenly between arms, so almost every control user is exposed to treatment through dozens of treated neighbors.

Naive analysis results:

- Treatment group: 45.2 minutes average
- Control group: 43.8 minutes average
- Measured effect: +1.4 minutes (+3.2 percent)

Network analysis confirms that control users have on average about half of their connections in treatment. Those treated connections share algorithmically boosted content that control users see, inflating control group engagement. The observed data cannot say by how much, because almost no control user is unexposed. The sensitivity analysis therefore supplies the missing quantity as an explicit assumption, an unexposed control mean of 42.3 minutes:

- Adjusted control baseline: 42.3 minutes (what control would show without spillover)
- Contrast against the assumed baseline: +2.9 minutes (+6.9 percent)
- Under this assumption, spillover inflated control by 1.5 minutes, halving the measured effect

The assumed counterfactual is not identified by the observed group means or the connection count. Estimating an exposure-specific effect requires an explicit exposure mapping, assignment probabilities, sufficient probability of each exposure, and an estimator matched to those choices. The arithmetic shows how a plausible spillover assumption can change the interpretation of an experiment. It does not recover a known true effect, and a design effect for cluster randomization is a separate variance calculation that cannot correct interference bias.

#### Detection Strategies

^sec-ml-operations-scale-detection-strategies-dc16

Network-exposure diagnostics test for evidence of interference. Ego-network analysis summarizes each control user’s treated neighbors as ${e}_{{i}} = |\{{j}\in {\mathcal{N}}_{{i}} : {w}_{{j}} = 1\}| / |{\mathcal{N}}_{{i}}|$, where ${\mathcal{N}}_{{i}}$ is the recorded connection set for control user ${i}$ and ${w}_{{j}}$ is peer ${j}$’s treatment assignment. Correlation between control outcomes and ${e}_{{i}}$ motivates investigation, but graph structure and user differences can also explain it. Comparisons between high- and low-exposure control cohorts therefore require an assignment design and analysis that address those differences. Temporal analysis adds evidence about when effects appear, without by itself distinguishing contagion from a shared external trend. These diagnostics make the interference assumption testable within the observed graph and exposure definition; a null result does not prove that all spillover is absent.

#### Mitigation Approaches

^sec-ml-operations-scale-mitigation-approaches-dc04

When SUTVA violations are detected, four experimental designs modify assignment to address distinct interference paths, each demanding an exposure model tailored to its randomization unit. In graph cluster randomization, treatment is assigned at the community level rather than to individual users. Graph partitioning algorithms like Louvain or spectral clustering seek groups with dense internal connections and sparse cross-cluster edges. Whether that grouping sufficiently limits cross-arm interaction must be measured on the resulting partition. Assignment now operates over ${K}$ clusters, so precision depends on the number of independent assignment units, cluster sizes, within-cluster correlation, and remaining spillovers.

Ego-exclusion designs instead filter the analyzed cohort by discarding users whose network exposure crosses a safety threshold. Restricting evaluation to control users with minimal treatment connections (such as ${e}_{{i}} < 0.05$) reduces measured interference, but it cannot guarantee an uncontaminated baseline. Under uniform random assignment, a highly active user with hundreds of connections has a treated-neighbor fraction tightly concentrated around the global treatment share and almost never falls below 0.05, whereas an isolated user with only one or two connections frequently has zero treated peers. Conditioning on low network exposure therefore strips high-degree, high-activity users out of the control cohort and introduces severe selection bias unless the analysis reweights or matches across node degree.

For marketplace dynamics where network connections cannot be partitioned cleanly, switchback experiments alternate treatment and control over time blocks within the selected market or population. This reduces simultaneous cross-arm interaction within that unit, but outcomes can carry over between blocks; the analysis must account for persistence and time trends. Geo-based experiments instead randomize spatial units such as cities, while monitoring cross-boundary travel and shared supply. Choosing the unit trades interference control against the number of independent comparisons and the observation time needed for adequate precision.

The chosen design determines the infrastructure needed to support its claims. Graph-based assignment needs maintained topology and cluster records; a switchback needs an auditable schedule and outcome timing; an exposure-specific estimator needs the peer-assignment information its exposure model uses. Analysis must respect the randomization unit, and monitoring must track the spillovers that could invalidate the comparison. The sensitivity example shows why this work can matter: under its stated assumption, spillover halves the observed lift. The platform must estimate the relevant effect before treating that observed contrast as evidence for or against promotion.

### Staged Rollout Strategies

^sec-ml-operations-scale-staged-rollout-strategies-2d1f

Cutting 100 percent of live traffic over to a new ranking model all at once exposes every user to a latent bug until operators can roll back, whereas starting at a 5 percent canary cuts that initial blast radius twentyfold. Experiment design fixes how much evidence a release needs; staged rollout fixes how much live traffic may carry the candidate while that evidence accumulates, turning deployment risk into a controllable exposure budget. Traffic increases only after the model earns each larger blast radius through continued acceptable performance.

**Napkin Math 12.5: The safety of staged rollouts**

**Problem**: A team is deploying a new ranking model. A blue-green switch that moves all traffic at once (100 percent cutover) exposes all users to any potential bugs. A “Canary” deployment starts at 5 percent traffic. How much does the canary approach reduce the deployment’s “Risk Exposure”?

**Math**: Assume the same request rate, per-request harm, and time to effective rollback in both deployments. Under those assumptions, exposure is proportional to the affected traffic share; comparing shares alone would be insufficient if the smaller canary took longer to reveal the failure.

1.  **All-at-Once Blue-Green Exposure**: 100 percent of users affected until rollback.
2.  **Canary Exposure**: 5 percent of users affected until rollback.
3.  **Risk Mitigation**: $100 / 5 = 20\times$.

**Systems insight**: Limiting initial exposure to 5 percent reduces affected traffic by 20× under the shared observation and rollback assumptions. This limits harm while the platform collects live evidence. It does not guarantee detection of rare failures or delayed quality effects, so the release policy must choose its observation window and containment triggers alongside the traffic share.

#### Blue-Green Deployment

^sec-ml-operations-scale-bluegreen-deployment-894e

Blue-green deployment keeps the current version (blue) serving while the new version (green) is readied in a parallel environment, then shifts traffic through the routing layer once readiness checks pass. Switching time depends on routing propagation and treatment of in-flight requests. For a large model, keeping both releases ready can reserve substantial accelerator memory. Separate full-capacity fleets duplicate the weights and serving resources during the transition, while a smaller candidate fleet reduces that initial reservation. Fast rollback requires enough ready capacity for the previous version; otherwise model loading and replica startup become part of recovery time. Capacity planning must therefore account for the overlap between releases as well as the steady-state serving allocation.

The environment layout and the traffic policy are separate decisions. A blue-green deployment can switch all traffic at once (the policy notebook [12.5](https://mlsysbook.ai/vol2/12_ops_scale/12_ops_scale.html#nbk-ops-scale-safety-staged-rollouts) assumed) or expose the green environment through canary stages. An all-at-once switch forgoes the evidence from limited live exposure, while staged routing retains parallel-environment costs for longer. The release contract determines whether that additional observation and rollback capacity justify their resource cost.

#### Canary Deployment

^sec-ml-operations-scale-canary-deployment-3d8b

Canary deployment[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.17 Footnotes#^fn9|⁹]] routes a small percentage of traffic to the new version while monitoring for regressions. If metrics remain acceptable, traffic percentage increases until the new version serves all traffic.

![[90 Assets/Volume II/12 Ops Scale/Ops Scale Canary Exposure Ladder 82548831e2.svg]]

*Five gray vertical bars rising left to right on a linear scale, labeled 1%, 5%, 25%, 50%, and 100%; the first bar is a thin sliver and the last is full height.*

*Each canary stage earns a larger share of live traffic.*

A typical progression moves from 1 percent to 5 percent to 25 percent to 50 percent to 100 percent as evidence accumulates. The 5 percent canary in notebook [12.5](https://mlsysbook.ai/vol2/12_ops_scale/12_ops_scale.html#nbk-ops-scale-safety-staged-rollouts) is the second of these stages; opening at 1 percent bounds initial exposure further. The duration of each stage matters. [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^eq-canary-duration|Equation 7]] relates stage duration to sample requirements, request rate, and traffic percentage, giving a lower bound on the time needed to collect the planned sample:

$$
{T_{\text{stage}}}= \frac{{n}}{{\lambda_{\text{arr}}} \times {p_{\text{stage}}}} \tag{7}
$$

^eq-canary-duration

where ${T_{\text{stage}}}$ is the time needed to collect the planned observations, ${n}$ is the sample requirement from the experiment design, ${\lambda_{\text{arr}}}$ is the request rate, and ${p_{\text{stage}}}$ is the traffic share expressed as a fraction. This is a collection-time bound, not a complete stopping rule; delayed labels, correlated requests, and the required observation window can extend the stage.

#### Canary Duration Calculation

^sec-ml-operations-scale-worked-example-canary-duration-calculation-9448

A model serves 1 million requests per hour. Suppose its canary plan specifies approximately 10,000 samples per variant. That is a guardrail sample, sized to catch a large regression quickly before exposure widens, not the sample needed to confirm a small improvement. The sample-size derivation of [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ml-operations-scale-ab-testing-statistical-foundations-b9bd|section 12.5.3.5]] takes the baseline rate, effect size, confidence, and power as inputs. Its worked example needs about 30,000 samples per variant to detect a 10 percent relative change at a 5 percent baseline click-through rate. Smaller effects need far more, so promotion evidence comes from the full experiment, while the canary stages below take their guardrail sample as an input.

At 1 percent canary traffic: ${T_{\text{stage}}} = \frac{10,000}{1,000,000 \times 0.01} = 1\text{ hour}$. At 5 percent canary traffic: ${T_{\text{stage}}} = \frac{10,000}{1,000,000 \times 0.05} = 0.2\text{ hours} = 12\text{ minutes}$.

The organization might configure five rollout stages:

- 1 percent for 2 hours (2$\times$ minimum for buffer)
- 5 percent for 30 minutes
- 25 percent for 30 minutes
- 50 percent for 1 hour
- 100 percent deployment

The schedule totals approximately 4 hours. Promotion still requires the planned statistical test and guardrail windows to pass; elapsed time alone does not establish confidence.

Four hours is far shorter than the ensemble soak of [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.04 Governance of State and Change#^tbl-ops-scale-ensemble-deploy|table 7]] or the multi-region waves that [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ml-operations-scale-deployment-strategies-fc90|section 12.5.7.2]] develops later in this chapter, because each schedule answers a different question. A guardrail sample of fast outcomes, such as errors and clicks, fills in hours. An ensemble change whose effects surface through delayed outcomes needs days of soak. A multi-region rollout repeats evidence collection region by region. The slowest outcome the release must observe, not the traffic share, sets the length of the schedule.

### Rollout Risk Management

^sec-ml-operations-scale-rollout-risk-management-a3d0

Observation windows set how long each rollout stage must run, but a minor bug fix and a core architecture replacement should not share the same exposure schedule or rely on manual intervention when metrics degrade: on a high-throughput ranking service, even a fraction-of-a-point click-through regression compounds into substantial revenue loss during the hours a team spends debating whether an alert is real. Because deployments differ in risk, effective CI/CD systems estimate each change’s risk before deciding how quickly to expose it. [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^eq-rollout-risk|Equation 8]] formalizes deployment risk as the product of regression probability, impact severity, and exposure level, providing a quantitative foundation for risk-based rollout decisions:

$$
\text{Risk}_{\text{rollout}} = \Pr(\text{regression}) \times \text{Impact}_{\text{regression}} \times {E_{\text{exposure}}} \tag{8}
$$

^eq-rollout-risk

where $\Pr(\text{regression})$ is the probability that the change causes a regression, $\text{Impact}_{\text{regression}}$ is the conditional harm per exposure unit, and ${E_{\text{exposure}}}$ is the number of those units exposed during the rollout period. For example, harm per affected request multiplied by exposed requests gives a total harm estimate. If impact already denotes total loss over the rollout, multiplying by exposure again would double-count it.

The rollout risk framework distinguishes three operational levers. Pre-release evaluation screens out known defects and provides evidence about regression probability ($\Pr(\text{regression})$). Validated fallbacks can reduce conditional harm ($\text{Impact}_{\text{regression}}$) when a defect occurs. Traffic limits, regional isolation, and prompt containment bound exposure (${E_{\text{exposure}}}$). Longer observation at a small traffic share can reveal delayed failures, but also exposes that cohort for longer. The release policy must balance evidence collection against accumulated harm rather than assuming that every longer hold reduces risk. Exposure accumulates in time as well as in traffic share. A regression that no alarm catches keeps charging its harm for every hour it stays live, and notebook [12.6](https://mlsysbook.ai/vol2/12_ops_scale/12_ops_scale.html#nbk-ops-scale-cost-delayed-alert) prices one such day.

**Napkin Math 12.6: The cost of a delayed alert**

**Problem**: A team deploys a recommendation model that has a silent bug: it reduces click-through rate (CTR) by 0.5 percentage points (10 percent relative), from 5 percent to 4.5 percent. If the service handles 5,000 requests/s and each click is worth \$0.50/click, how much revenue is lost if detection and remediation take 24 hours?

**Math**:

1.  **Total Requests**: 5,000 requests/s $\times$ 86,400 s/day = 432,000,000 requests.
2.  **Lost Clicks**: 432,000,000 requests $\times$ 0.005 = 2,160,000 lost clicks.
3.  **Total Financial Loss**: 2,160,000 lost clicks $\times$ \$0.50/click = \$1,080,000.

**Systems insight**: At the assumed traffic and value per click, a 0.5 percentage-point regression costs \$1,080,000 per day. Earlier detection creates value when it enables effective containment sooner. Monitoring and rollback therefore share one operating objective: reducing the time users remain exposed to a harmful release. A drift alarm alone neither establishes the revenue loss nor stops it.

#### Automated Rollback Triggers

^sec-ml-operations-scale-automated-rollback-triggers-ffa3

Risk categories decide how cautiously traffic should expand, but rollback triggers decide when expansion must stop. The trigger configuration in [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^lst-rollback-triggers|listing 5]] makes that stop condition executable by binding each monitored metric to a threshold, observation window, and minimum sample count.

``` python
rollback_config = {
    "metrics": {
        "engagement_rate": {
            "threshold": -0.02,  # 2% relative decline triggers rollback
            "window_minutes": 15,
            "min_samples": 1000,
        },
        "error_rate": {
            "threshold": 0.01,  # 1% absolute increase triggers rollback
            "window_minutes": 5,
            "min_samples": 500,
        },
        "latency_p99": {
            "threshold": 1.5,  # 50% relative increase triggers rollback
            "window_minutes": 5,
            "min_samples": 100,
        },
    },
    "rollback_action": "immediate",  # or 'gradual' for less severe issues
    "notification": ["oncall", "model-owner"],
}
```

Listing 5: **Automated Rollback Configuration**: Metric-specific thresholds, observation windows, and minimum sample sizes that balance sensitivity against false triggers.

^lst-rollback-triggers

Automated rollback must balance sensitivity against false triggers. Minimum sample counts and window durations limit unstable decisions, but they do not define a statistical test. The release contract must also specify the comparison, uncertainty rule, and repeated-monitoring policy. Immediate safety guardrails may require containment before statistical significance is available. These triggers assume a single serving domain. A fleet that spans regions must also keep its version boundary coherent while traffic expands or retracts, which turns rollout and rollback into a coordination protocol.

### Multi-Region Deployment Coordination

^sec-ml-operations-scale-multiregion-deployment-coordination-ab6a

When Region B switches traffic to a new ranking model before its updated embedding tables finish replicating, or when a regional rollback leaves mobile users bouncing between incompatible model versions across regions, a rollout that passed every single-region check fails globally. A regional rollout must move each model version together with the embedding tables and feature versions it depends on. Where replicas live and how global traffic reaches them is the serving design of **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^sec-inference-scale-global-inference-infrastructure-df52|Global Inference Infrastructure]]**; operations inherits that placement and must change versions across it safely. Geographic distribution therefore adds artifact propagation, routing, and regional recovery decisions to the release protocol. Multiple versions may coexist during a staged rollout, but their compatibility, traffic assignment, and rollback behavior must remain within the release contract.

↩︎ Geographic replication of serving replicas, with the spare regional capacity and gradual traffic return it requires, is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^sec-fault-tolerance-reliability-reliability-replication-strategies-aaa2|Replication strategies]]**.

#### Coordination Challenges

^sec-ml-operations-scale-coordination-challenges-085c

Multi-region ML deployment couples artifact readiness with input readiness. Large model artifacts consume transfer and loading capacity before a region can serve the new version. For models that retrieve features, receiving the binary is not enough: the region must also provide the feature versions and freshness that the candidate validated. If Region B loads a new model before its required embeddings arrive, requests may fail or use incompatible inputs. The readiness check must therefore cover the model, its feature dependencies, and serving health as one versioned state.

Uncontrolled version mixing is the failure mode that binds multi-region deployment. Staged releases intentionally serve multiple versions, but the protocol must preserve compatibility and experiment assignment even when clocks, traffic volume, routing, and rollback behavior differ by region.

Clock skew and asynchronous progress make timestamps insufficient to establish rollout state. At a planned 2:00 PM UTC start, Region A may begin its 1 percent canary while Region B is still loading the candidate. The coordinator needs explicit readiness and phase acknowledgments to distinguish a permitted staggered release from a failed transition. Regional version differences are acceptable only when routing preserves the declared compatibility and assignment rules.

Regional traffic variation turns the same percentage into different amounts of evidence. A larger canary share in a low-volume region can still collect fewer eligible observations than a smaller share in a high-volume region. The platform must evaluate per-region sample counts, assignment units, and outcome delays against the experiment plan; traffic percentages alone do not establish statistical power.

Cross-region routing can expose version skew when requests move for latency, load balancing, or failover. If an experiment assigns treatment by user, routing must preserve that assignment across regions or record and handle any deviation according to the experiment plan. Mixed versions alone do not invalidate an experiment; unplanned changes in exposure violate the assumptions on which its interpretation depends.

Rollback is the final consistency test. Reverting one region changes the available version set and can violate assignment or dependency assumptions elsewhere. A regional rollback is valid when the release contract permits that state; otherwise the coordinator must contain exposure across the affected regions. Rollback therefore belongs in the rollout protocol rather than an ad hoc emergency procedure.

#### Deployment Strategies

^sec-ml-operations-scale-deployment-strategies-fc90

Multi-region coordination trades deployment duration against permitted regional skew. In a sequential regional rollout, each region completes its canary progression before the next begins, limiting early exposure while extending the schedule. A globally coordinated rollout instead requires regions to satisfy shared readiness and activation conditions. Logical ordering does not make network delivery simultaneous; routing must enforce the version boundary while activation propagates. A hybrid rollout permits regional progress within declared phase or version bounds, pausing regions when local evidence is insufficient or further progress would exceed the allowed skew. The appropriate policy follows the service’s compatibility, assignment, and availability requirements.

An illustrative rollout across 5 regions uses three waves followed by final validation:

1.  Canary region (lowest traffic): Full canary cycle, 24 to 48 hours
2.  Early adopter regions (2 regions, 20 percent global traffic): Parallel deployment, 24 to 48 hours
3.  Majority regions (2 regions, 70 percent global traffic): Parallel deployment, 24 to 48 hours
4.  Final validation: Cross-region consistency check, 12 to 24 hours

The assumed windows total 3.5 to 7 days. Actual promotion still depends on regional evidence and guardrails, so low traffic, delayed outcomes, or a failed check can extend the schedule.

#### Traffic Management During Transitions

^sec-ml-operations-scale-traffic-management-during-transitions-731d

Routing controls enforce different parts of the release contract. Region affinity keeps a user’s requests in one region, but does not by itself prevent version changes within that region. Version pinning directs requests to replicas serving the assigned release, including during permitted failover. Restricting cross-region fallback can simplify an experiment’s exposure boundary, but sacrifices availability when the selected region fails. The platform chooses and tests these controls together so assignment remains interpretable under both normal routing and recovery.

#### Consistency Models for Deployment

^sec-ml-operations-scale-consistency-models-deployment-4995

The choice of activation contract affects both coordination cost and the interpretation of deployment metrics. Multi-region systems choose among three consistency models, each trading coordination cost against permitted divergence ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^tbl-multi-region-consistency|table 14]]). Globally ordered activation establishes a shared transition order, eventual convergence permits temporary regional divergence, and bounded staleness limits that divergence. The application must specify which guarantee its decisions require; a financial use case alone does not prohibit controlled experiments or staged versions.

| **Model**             | **Guarantee**                                             |          **Use case**          | **Coordination overhead**     |
|:----------------------|:----------------------------------------------------------|:------------------------------:|:------------------------------|
| **Strong**            | Globally ordered version activation                       | One shared activation contract | High (global synchronization) |
| **Eventual**          | Regions converge to same version                          |    Content recommendations     | Low (independent progression) |
| **Bounded staleness** | Regions within ${k_{\text{skew}}}$ versions of each other |       Real-time ranking        | Medium (version monitoring)   |

Table 14: **Consistency Models for Multi-Region Deployment**: Version activation contracts trade coordination cost against permitted divergence. Financial or safety-related use does not by itself require identical versions everywhere: assignment consistency, compatible schemas, auditability, and explicitly authorized experiments may permit staged versions. The decision being served sets the required guarantee.

^tbl-multi-region-consistency

For A/B testing, the serving system must implement the declared assignment and record actual exposure. A user assigned to the candidate should receive that candidate across permitted regional routes unless the experiment explicitly models another exposure policy. Unrecorded fallback to the old version changes the intervention being measured and can bias the comparison. Different versions across control and treatment groups are intentional; they are not a relaxation of the assignment contract.

#### Rollback Coordination

^sec-ml-operations-scale-rollback-coordination-b751

Rolling back a multi-region deployment requires careful coordination to prevent oscillation and mixed-version serving. The rollback protocol executes across two ordered phases separated by an acknowledgment barrier ([[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^fig-ops-scale-rollback-protocol|figure 10]]). First, the coordinator halts traffic to the new version globally by broadcasting rollback intent, waiting for every region to acknowledge that it has stopped routing new requests to the rejected version, and allowing in-flight requests to drain. Any region failing to acknowledge before the timeout expires is marked unhealthy. Next, the coordinator restores the old version globally once it confirms that all healthy regions serve only the previous release, re-enabling normal traffic routing, clearing transient deployment state, and resetting the system for a future attempt.

![[90 Assets/Volume II/12 Ops Scale/Ops Scale Rollback Protocol d0e72651ed.svg]]

Figure 10: **Two-Phase Multi-Region Rollback**: Time runs left to right on one lane per participant. In phase 1 the coordinator broadcasts rollback intent; regions A and B stop routing new requests to the rejected version (v2), drain in-flight work, and acknowledge. Region C never answers, so when the acknowledgment timeout expires the coordinator marks it unhealthy and fences it. Only after the barrier, when no healthy region still routes to v2, does phase 2 restore the previous version (v1) on the healthy regions; the fenced region stays out of routing until it rejoins under the restored version.

^fig-ops-scale-rollback-protocol

The acknowledgment barrier prevents restoration from completing while reachable regions still route new requests to the rejected version. A timeout alone cannot stop an isolated region from serving; the serving path must enforce a lease, routing exclusion, or equivalent fencing rule. The release contract must specify what happens to in-flight requests and to availability during that interval.

Partial rollback allows rolling back individual regions while others continue. This is appropriate when issues are region-specific (infrastructure problems, regional traffic patterns) rather than model-inherent. The deployment coordinator tracks per-region state and prevents inconsistent global decisions based on partial information.

#### Multi-Region Coordination Overhead

^sec-ml-operations-scale-worked-example-multiregion-coordination-overhead-a78b

In an illustrative five-region deployment with an assumed 80 ms one-way delay per coordination leg, each phase transition needs four synchronous legs (announce intent, collect acknowledgments, confirm completion, collect confirmations), about 320 ms. A canary progression through five traffic stages (1, 5, 25, 50, and 100 percent) adds under two seconds to a rollout measured in hours. Latency is therefore not where coordination costs the release.

The coordination service nevertheless becomes a critical dependency. Its failure policy must specify whether regions may continue serving their last authorized state and whether any further promotion is permitted. A shared activation barrier can halt progress while existing traffic continues; a policy allowing regional independence can permit local progress within its compatibility limits. A bounded-skew contract must stop progress before the bound is exceeded, rather than merely alert afterward. Replicating coordinator state through a consensus protocol, which commits a decision only after a majority of replicas (a quorum) has recorded it, can preserve decisions across replica failures while a quorum remains available. Routing enforcement and regional readiness still determine whether those decisions hold in the serving path.

### The End-To-End Evaluation Contract

^sec-ops-scale-end-to-end-evaluation-contract

Shadow runs, experiments, canary stages, and regional waves each produce release evidence, yet a candidate that passes offline accuracy on one dataset, passes latency benchmarks on a lighter synthetic load profile, and enters an online A/B test without a tested rollback target remains unverified as a whole. Those checks never evaluated the same release state. Evidence from different stages is useful only when it refers to the same candidate and decision. An **evaluation contract** is the versioned release record that binds a model and its dependencies to the workload, metrics, statistical design, acceptance thresholds, rollback conditions, and accountable owners. This record is the subject of the evaluation contract principle ([[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-evaluation-contract|21]]), one of the fleet-in-production principles listed in the opener to this part of the book. It holds that a fleet release decision is valid only when all of its evidence refers to one versioned contract. The record therefore becomes the unit of validity for everything this chapter has built, from registry versions and feature contracts to rollout stages and experiment statistics. [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^tbl-ops-scale-evaluation-contract|Table 15]] assembles that record across five evidence planes.

| Evidence plane            | Contract must pin                                                                                                                                                                                                                                                                        | Acceptance or invalidation rule                                                                                                                               | Accountable owner                                  |
|:--------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------|
| Offline behavior          | Evaluation-set version, primary metric, consequential slices, baseline, uncertainty evidence, and robustness tests (developed later, in **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.04 A Unified Framework for Robust AI#^sec-robust-ai-common-robustness-principles-cb22\|Common robustness principles]]**)    | Promote only if prespecified aggregate and slice bounds hold; invalidate when the population, label definition, or intended use leaves the validated envelope | Model owner and domain reviewer                    |
| System performance        | Hardware and software envelope, open- or closed-loop workload model, concurrency, request mix, warm-up, p50 and tail latency, throughput, errors, and resource cost                                                                                                                      | Promote only under the production-equivalent load contract; invalidate when capacity headroom or an SLO budget is exhausted                                   | Serving and site-reliability owners                |
| Responsibility and safety | Fairness slices, privacy and safety evidence, affected-party requirements, and assurance claims (developed later, in **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/16 Responsible AI/V2-16.03 The Governance and Assurance Lifecycle#^sec-responsible-ai-governance-assurance-lifecycle\|The Governance and Assurance Lifecycle]]**) | Promote only when the named claims have sufficient evidence and review; invalidate on a material change, control failure, or unbounded harm signal            | Risk owner and governance authority                |
| Online experiment         | Assignment unit, holdout, minimum detectable effect, power, sample size, confidence interval, multiple-testing correction, stopping rule, and guardrail metrics                                                                                                                          | Promote only after the planned decision rule passes; stop and roll back when any guardrail crosses its prespecified threshold                                 | Experiment owner and product decision owner        |
| Recovery and audit        | Rollback artifact and dependencies, trigger windows, evidence-retention period, data and code versions, environment, seeds, raw aggregate counts, and approvals                                                                                                                          | Reject exposure without a tested rollback; reopen the decision when evidence cannot be reproduced or retained for the required review period                  | Release owner, platform owner, and audit custodian |

Table 15: **End-to-End Evaluation Contract**: A model release is accepted against one versioned record spanning offline behavior, production-equivalent performance, specialist assurance, online experimentation, and recovery. Each plane has both an evidence owner and a condition that expires its claim.

^tbl-ops-scale-evaluation-contract

Acceptance is deliberately distributed, but promotion authority is not ambiguous. The model and domain owners accept predictive utility; the serving owner accepts capacity and reliability; specialist risk owners accept bounded robustness, fairness, privacy, and safety claims. A named release authority promotes only when all required sign-offs refer to the same artifact. The platform automates gates and preserves evidence, but it cannot choose the product objective or waive a failed assurance claim.

Invalidation is the return path through the contract. Drift beyond the evaluated population, a feature or label-definition change, exhausted latency headroom, a statistically supported guardrail regression, or a material governance change sends the candidate back to the owning gate. Thresholds and rollback targets are fixed before exposure so an apparent primary-metric gain cannot redefine success after the result is known. Reproducibility requires retaining the inputs to that decision, not merely its verdict: the dataset and traffic snapshot, model and code versions, environment and hardware envelope, random seeds, assignment and sampling rules, sufficient statistics or permitted logs, approvals, and the exact rollback artifact.

The fraud shadow workflow of [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ml-operations-scale-worked-example-shadow-deployment-workflow-216d|section 12.5.3.2]] shows how one stage’s evidence maps onto these planes. Its labeled precision and recall, with the paired outcomes, label maturity, intervals, and recall tolerance its gate required, are paired live-traffic quality evidence that the contract records. They do not discharge the online-experiment plane, because a shadow run has no randomized assignment and exposes no user to the candidate’s outputs. The workflow’s p99 latency is system-performance evidence, but the sampled phase saw only 10 percent of traffic; the full-shadow phase would supply the production-load measurement if its latency were recorded. The clipping change then triggered an invalidation rule. Because it changed the model’s inputs, it voided that evidence and sent the revised candidate back through its gates. The workflow as described names no tested rollback artifact, raw aggregate counts, evidence-retention period, or approvals, so its recovery-and-audit plane would still be empty before canary exposure.

### CI/CD Patterns by Model Type

^sec-ml-operations-scale-cicd-patterns-model-type-b412

Every workload family shares the five evidence planes of [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^tbl-ops-scale-evaluation-contract|table 15]], yet the intended use determines which plane gates promotion. Releasing a general-purpose LLM with a two-hour automated check misses subtle safety regressions, whereas holding an emergency fraud-model patch in a two-week human review window lets an active attack drain funds. [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^tbl-ops-scale-cicd-patterns|Table 16]] returns to the workload families of [[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.03 The N-Models Problem#^tbl-ops-scale-model-types|table 2]], whose cadence and rollback targets still apply, and adds the column that table lacked, what each family must validate before promotion. The listed durations are operating assumptions, not consequences of architecture; label maturity, traffic, and potential harm determine the actual validation and rollback policy.

| **Pattern**          | **Model type** |  **Validation focus**  | **Rollout speed** |    **Rollback speed**     |
|:---------------------|:--------------:|:----------------------:|:-----------------:|:-------------------------:|
| **Quality-gated**    |      LLM       |   Human eval, safety   |   Days to weeks   | Minutes with warm standby |
| **Metric-driven**    | Recommendation |   Engagement metrics   |   Hours to days   |          Minutes          |
| **Threshold-gated**  |     Fraud      |    Precision/recall    |       Hours       |          Seconds          |
| **Accuracy-focused** |     Vision     | Classification metrics |       Days        |          Minutes          |

Table 16: **CI/CD Patterns by Model Type**: The rows illustrate validation and response policies for different workloads. Their durations are planning assumptions; promotion depends on the required evidence, including outcome-label delay, and rollback depends on a ready compatible target.

^tbl-ops-scale-cicd-patterns

For a broadly capable LLM, evaluation must cover consequential uses that aggregate benchmarks can miss. Automated tasks such as MMLU and HumanEval screen selected capabilities; human review and adversarial probes examine additional failure modes; shadow traffic tests operational behavior on live inputs. A planning window of 2–4 weeks may accommodate these activities and staged observation, but elapsed time is not the acceptance criterion. The required evidence depends on the changed capabilities and the service’s exposure policy.

Recommendation pipelines balance freshness with statistically defensible comparison. Offline NDCG and recall can screen candidates, interleaving can compare ranker preference, and A/B tests measure the selected product outcomes. A 24–48-hour rollout is feasible only when traffic and outcome timing supply the required evidence within that interval. Promotion and rollback follow the prespecified rules rather than a fixed refresh deadline.

Fraud models add adversarial urgency, but confirmed outcomes can arrive after the decision window. Historical labeled cases and shadow scoring provide evidence before exposure; neither makes fresh precision and recall immediately observable. The release policy must state what evidence supports an urgent change, what uncertainty remains, and who accepts its bounded exposure. Rapid routing to a validated fallback can contain harm while additional labels accumulate, provided that fallback remains suitable for the current threat.

Edge fleets, absent from the table, apply the same contract to weeks-long rollouts that leave many model versions active at once, to devices whose memory and thermal limits require hardware-in-the-loop validation, and to telemetry that privacy rules limit to federated aggregates. **[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.11 Production Integration#^sec-edge-intelligence-fleet-release-controls-5e1a|Fleet release controls]]** develops these release controls, including why the devices that report health do not represent the deployed fleet.

Whether a model runs in a data center or on a phone, a CI/CD pipeline promotes candidates supported by evidence within a specified operating envelope. Production can move outside that envelope as data, traffic, and dependencies change. Monitoring must therefore preserve the release contract after promotion, detect when its evidence no longer applies, and return the affected model to evaluation or recovery.
