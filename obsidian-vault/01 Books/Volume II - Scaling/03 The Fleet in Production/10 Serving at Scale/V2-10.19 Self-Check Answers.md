**Self-Check: Answer**

1.  **True or False: A service that meets its latency SLO on every admitted request is serving all of its offered load.**

    *Answer*: False. Offered load counts all arriving work, including requests the service rejects or sheds, while admitted load counts only the work it accepts. A service can meet its latency target on admitted requests by refusing others, so capacity must be judged by how much offered work completes within the targets.

    *Learning Objective*: Distinguish offered load from admitted load when judging whether a service meets its contract.

2.  **Configuration X reports 900 requests per second on a benchmark of short prompts, and configuration Y reports 700 requests per second on the production prompt and output mix, both at the same TTFT and TPOT targets. Which conclusion is justified?**

    1.  X has more capacity, because request rate is the capacity metric for a serving system.
    2.  Neither can be ranked yet, because prompt and output lengths change the work per request, so capacity must be compared at the same request mix and SLO by counting offered work that completes within the targets.
    3.  Y has more capacity, because production traffic always contains longer requests than a benchmark.
    4.  The two are equivalent, because both meet the same latency targets.

    *Answer*: The correct answer is B. For language models, request rate alone is insufficient because prompt and output lengths determine how much work each request carries, so a benchmark of short prompts inflates the rate. Ranking by raw rate repeats that error, and assuming production traffic is always longer replaces measurement with a guess. Meeting the same targets on different mixes does not make the configurations equivalent.

    *Learning Objective*: Justify why serving capacity must be compared at a fixed request mix and SLO rather than by raw request rate.

3.  **In a streaming language-model service, explain which latency budget is consumed by waiting before prefill and which by contention during decode, and why a faster decode kernel alone cannot settle either problem.**

    *Answer*: Everything up to the end of prefill, including routing, admission, tokenization, queueing, and the prefill pass, counts against time to first token, while contention among sequences sharing decode steps stretches the gaps between streamed tokens and so consumes the TPOT budget. A faster decode step raises the service rate, but it does not decide how long a request waits to join a batch, which replica receives it, which requests get scarce KV-cache space, or when the fleet adds a replica. A request queued 400 ms behind a burst misses a 300 ms TTFT target however fast decode runs, so the scheduler must budget waiting and contention alongside execution time.

    *Learning Objective*: Analyze how queueing before prefill and contention during decode consume the TTFT and TPOT budgets independently of kernel speed.

1.  **A recommendation service must answer 100,000 queries per second within 10 ms. Its model fits comfortably on one machine, which peaks at 10,000 queries per second with optimal batching. Which strategy addresses the binding constraint?**

    1.  Shard the model with tensor parallelism across machines, because sharding is the general remedy whenever one machine is insufficient.
    2.  Quantize the weights so a single machine runs ten times faster.
    3.  Replicate the full model across at least ten machines and route requests among them, because the binding constraint is throughput rather than memory or per-request latency.
    4.  Raise the batch size on one machine until it reaches 100,000 queries per second.

    *Answer*: The correct answer is C. The model fits and a single request meets its budget, so the shortfall is aggregate throughput, which horizontal replication solves by multiplying independent replicas. Sharding addresses memory or per-request latency and adds communication without multiplying throughput. Larger batches cannot help because the 10,000-query peak already assumes optimal batching, and quantization does not reliably deliver a tenfold gain.

    *Learning Objective*: Classify a serving shortfall as a memory, throughput, or latency trigger and select replication or sharding accordingly.

2.  **A 70B-parameter model needs roughly 140 GB of FP16 weights, more than one 80 GB accelerator holds, and quantization can make it fit on one device. Explain why the team might still shard it, and how they should decide.**

    *Answer*: Fitting in memory removes the memory trigger, but the single-device execution time may still exceed the request latency budget. Sharding across several GPUs divides computation and weight traffic, yet it adds communication and synchronization, and it shortens compute-bound prefill and bandwidth-bound decode by different amounts. The team should measure the sharded configuration’s prefill latency against the TTFT target and its decode latency against the TPOT target separately, and shard only if both phases gain more than the added communication costs.

    *Learning Objective*: Evaluate when a latency target justifies sharding a model that already fits on one device, measuring each phase against its own target.

3.  **True or False: A stream that meets its TPOT target cannot stall the reader, because TPOT bounds the gap between successive tokens.**

    *Answer*: False. TPOT is the average of the gaps between tokens, so one long gap can stall the reader while the average still meets its target. Per-gap tail targets are stated as time between tokens (TBT), which must be monitored separately from average cadence.

    *Learning Objective*: Distinguish average token cadence (TPOT) from per-gap time between tokens (TBT) when setting streaming latency targets.

1.  **Two configurations serve the same request mix under the same TTFT and TPOT targets. Configuration X completes 1,200 requests per second, of which 70 percent meet both targets; configuration Y completes 1,000 requests per second, of which 95 percent meet both. Which has more serving capacity?**

    1.  X, because it completes more requests per second and keeps its accelerators busier.
    2.  The two are equal, because both process the same request mix.
    3.  X, because requests that miss their targets still return results to users.
    4.  Y, because SLO goodput counts only requests that meet their targets, about 950 per second against about 840 for X.

    *Answer*: The correct answer is D. SLO goodput is the rate of completed requests that meet the stated TTFT and TPOT targets for a fixed request mix, so X delivers about 840 useful requests per second and Y about 950. A request that misses its contract counts for nothing however busy the accelerators were, so higher raw throughput or a returned result does not add useful capacity.

    *Learning Objective*: Calculate SLO goodput from completion rate and target attainment, and use it to compare serving configurations.

2.  **Explain the composition of the distributed ‘serving tax’ (${L_{\text{lat,total}}} = {L_{\text{lat,infer}}} + {L_{\text{lat,network}}} + {L_{\text{lat,serialization}}} + {L_{\text{lat,coordination}}} + {L_{\text{lat,queue}}}$) and describe how zero-copy serialization formats mitigate serialization overhead.**

    *Answer*: The serving tax comprises exposed network, serialization, coordination, and queueing delays beyond model execution. Zero-copy formats can expose compatible wire-format data without a separate parse-and-copy pass. They do not remove network transmission, all validation, or every memory copy: layout, ownership, device placement, and transport determine what can be avoided. Measure each contribution on the request critical path rather than adding overlapping intervals.

    *Learning Objective*: Analyze the components of the distributed serving tax and the mechanism by which zero-copy serialization reduces latency.

3.  **True or False: Interactive inference recovery is judged against request latency and availability objectives, whereas long-running training recovery is usually judged against lost progress and time to completion.**

    *Answer*: True. Interactive serving may need rerouting, bounded retries, or a fallback before a request deadline. Training often restores a checkpoint and repeats lost work. Neither mode guarantees invisible recovery; the acceptable interruption follows the workload contract.

    *Learning Objective*: Compare operational fault tolerance and state management requirements between distributed training and distributed inference.

1.  **A production recommendation model costs \$50,000 to train (a one-time expense) and serves 10,000 QPS continuously for 2 years (730 days) at an operational cost of \$10 per million queries. What is the ratio of lifetime serving cost to training cost?**

    1.  Approximately $1.3\times$
    2.  Approximately $126.1\times$
    3.  Approximately $12.6\times$
    4.  Approximately $630.7\times$

    *Answer*: The correct answer is B. The model serves $10{,}000 \times 86{,}400 \times 730 = 6.3072 \times 10^{11}$ queries. At $10^{-5}$ dollars per query, serving costs 6,307,200 dollars, or approximately 126.1 times the 50,000-dollar training cost. The other ratios miscount accumulated queries or unit cost. This result depends on the specified sustained traffic, lifetime, and price rather than a universal cost ratio.

    *Learning Objective*: Calculate the lifetime economic leverage of recurring inference expense relative to one-time training expense.

2.  **True or False: Serving cost always exceeds training cost once a model is large enough, because larger models cost more per query.**

    *Answer*: False. Whether serving dominates depends on traffic, unit serving cost, deployment duration, and the training expense, not on model size alone. A low-traffic deployment or a short lifetime can leave training as the larger cost over the whole deployment.

    *Learning Objective*: Identify the inputs that decide whether serving or training dominates a model’s lifetime cost.

3.  **A team estimates its cost per query from GPU time on fully loaded replicas, but its fleet also bills for reserved replicas that sit idle overnight to absorb the daytime peak. What does the lifetime cost model require?**

    1.  Nothing more, because idle replicas do no work and therefore add no cost per query.
    2.  Doubling the query rate to account for the peak, because peaks set the cost.
    3.  Replacing cost per query with training cost, because idle capacity is a one-time expense.
    4.  Charging the billed idle and reserved capacity inside the unit cost, and counting the same served queries in the rate that was used to estimate that cost.

    *Answer*: The correct answer is D. Unit serving cost must include the chosen serving boundary, including idle or reserved capacity whenever it is billed, and the query rate must count the same served queries. Treating idle replicas as free understates the bill, and inflating the query rate double-counts traffic rather than fixing the cost boundary. Reserved capacity recurs with every billing period, so it is not a one-time expense.

    *Learning Objective*: Apply a consistent accounting boundary when estimating unit serving cost for the lifetime cost model.

4.  **A model costs \$2M to train, and its first year of serving costs about \$18M. Explain why a 10 percent reduction in cost per request can be worth nearly as much as the original training run, and state the conditions under which that saving is real.**

    *Answer*: Serving expense recurs with traffic, so a 10 percent reduction in cost per request saves about \$1.8M in the first year alone and keeps saving every year after, while training was paid once. The saving is real only if request volume and service quality stay fixed, because the reduction must lower billed capacity for the same useful work. A change that only lowers latency does not reduce billed capacity, so engineering effort on a deployed model should target cost per completed request at the SLO.

    *Learning Objective*: Justify why recurring serving savings can rival training cost, and identify the conditions under which a unit-cost reduction yields real savings.

1.  **A vision model has fixed latency overhead ${T_{\text{fixed}}} = 2\text{ ms}$ and variable compute time ${t_{\text{req}}} = 1\text{ ms/item}$. An LLM decode step has ${T_{\text{fixed}}} = 40\text{ ms}$ (loading 140 GB weights from HBM) and ${t_{\text{req}}} = 0.5\text{ ms/token}$. At what approximate batch size ${B}$ does each workload reach the ‘knee’ of its batching efficiency curve (${B} \approx {T_{\text{fixed}}} / {t_{\text{req}}}$)?**

    1.  Vision knee at ${B} \approx 10$; LLM decode knee at ${B} \approx 20$
    2.  Vision knee at ${B} \approx 80$; LLM decode knee at ${B} \approx 2$
    3.  Vision knee at ${B} \approx 4$; LLM decode knee at ${B} \approx 40$
    4.  Vision knee at ${B} \approx 2$; LLM decode knee at ${B} \approx 80$

    *Answer*: The correct answer is D. The knee of the batching efficiency curve occurs where the variable compute cost (${B} \times {t_{\text{req}}}$) begins to exceed fixed overhead (${T_{\text{fixed}}}$). For the vision model, ${B} \approx 2\text{ ms} / 1\text{ ms} = 2$. For LLM decode, ${B} \approx 40\text{ ms} / 0.5\text{ ms} = 80$. The larger LLM knee illustrates a stronger incentive to amortize weight reads across concurrent requests. The chosen batch can remain below that knee when arrivals, KV-cache capacity, or the latency budget limit useful concurrency; the knee is not a universal batch requirement. The inverted result swaps the two workloads; the intermediate configurations miscalculate the quotient of fixed and variable parameters.

    *Learning Objective*: Calculate the knee point on the batching efficiency curve for compute-bound versus memory-bandwidth-bound inference workloads.

2.  **For a static LLM batch that retains all slots and pads completed sequences until the longest sequence finishes, define the waste ratio $W=1-\bar{S}/S_{\max}$. How can continuous batching reduce this waste?**

    *Answer*: The stated implementation allocates $B S_{\max}$ token-step slots but performs only $B\bar{S}$ useful token steps, leaving a waste fraction $1-\bar{S}/S_{\max}$. Continuous batching can replace completed sequences with waiting requests at each iteration. This reduces padded-slot waste when enough admissible work is queued; it does not guarantee a full batch under light arrivals or memory pressure. Holding responses until the batch finishes is a separate response-barrier policy, not an inherent consequence of fixed membership.

    *Learning Objective*: Analyze the mathematical formulation of batching waste in static LLM execution and the mechanism of continuous batching.

3.  **For a recommendation pipeline that first retrieves sparse features and then processes dense features before combining them, order: (1) Feature Interaction, (2) Dense Feature Processing, (3) Sparse Feature Lookup, (4) Ranking Head.**

    *Answer*: The correct sequence is (3) Sparse Feature Lookup -\> (2) Dense Feature Processing -\> (1) Feature Interaction -\> (4) Ranking Head for the stated pipeline. Interaction consumes both sparse and dense representations; ranking consumes their combined features. Sparse lookup and dense processing can run concurrently in other implementations when neither depends on the other, so their serial order is an explicit scenario assumption.

    *Learning Objective*: Structure the sequential execution stages of a feature-parallel recommendation model pipeline.

4.  **A stable inference service completes 1,000 requests/sec with an assumed mean end-to-end latency of 100 ms. Each replica executes full batches of eight in 80 ms, giving 100 requests/sec of service capacity. With a separate target of at most 80% mean service utilization, what mean in-flight work and candidate fleet size follow, without claiming a P99 guarantee?**

    1.  Mean in-flight work is 100 requests; sizing service capacity at the 80% utilization target gives 13 replicas
    2.  Required concurrency $Q_{\text{req}} = 1{,}000$; minimum SLO-sized fleet $= 125$ replicas
    3.  Required concurrency $Q_{\text{req}} = 80$; minimum SLO-sized fleet $= 10$ replicas
    4.  Required concurrency $Q_{\text{req}} = 100$; minimum SLO-sized fleet $= 10$ replicas

    *Answer*: The correct answer is A. Little’s law gives 1,000 × 0.1 = 100 requests in flight on average, including waiting work. Fleet sizing instead uses the separate utilization target: ceil(1,000/(0.8 × 100)) = 13 replicas, running at about 76.9% utilization. Their 104 executing positions exclude queues. Under the idealized assumption that all other latency is waiting or batch formation, the fixed 80 ms service time gives 80 requests executing on average and leaves 20 waiting or accumulating. Ten replicas are the throughput-only saturation boundary. The assumed mean and tail SLO both require validation; dividing in-flight work by batch slots does not establish the fleet size.

    *Learning Objective*: Separate mean in-flight occupancy from executing capacity and size a candidate fleet with an explicit service-utilization target.

5.  **What is a per-request compute budget for test-time compute, and how does additional reasoning change the serving cost of a request?**

    *Answer*: A per-request compute budget limits the generated tokens, candidate evaluations, or search steps a request may consume, stated in both latency and capacity. It binds when serial reasoning tokens exhaust a request’s latency budget or its share of fleet capacity before further reasoning stops improving the answer. Additional generated tokens, candidate evaluations, or search steps increase work per request and can extend KV-cache residency without changing the bottleneck of each decode step. A serving policy sets that budget from measured quality gains, request deadlines, and fleet load. Parallel candidate evaluations consume capacity without necessarily adding the same serial latency.

    *Learning Objective*: Explain the serving cost of test-time compute and why a per-request compute budget is stated in both latency and capacity.

6.  **True or False: Increasing the batching timeout window during a high-traffic spike is always the optimal policy for reducing tail latency.**

    *Answer*: False. In the chapter’s traffic-adaptive rule, a fixed target batch fills sooner as arrival rate rises, permitting a shorter formation window. This reduces intentional formation delay, not the separate wait for a busy replica. Shrinking the maximum batch can also reduce service capacity and worsen queueing. The policy must be evaluated against arrival patterns, measured service rates, tail latency, and overload handling; neither a longer nor a shorter window is universally optimal.

    *Learning Objective*: Evaluate adaptive batching control policies under varying traffic arrival intensities.

1.  **How does PagedAttention reduce memory waste in LLM KV cache management, and what system-level benefit can follow?**

    1.  It compresses KV cache tensors using lossless entropy coding to reduce arithmetic intensity in attention kernels.
    2.  It replaces standard multi-head attention with grouped query attention by dynamically merging key-value heads.
    3.  It maps logical tokens to non-contiguous fixed-size physical blocks, reclaiming unused reservations so that more requests may fit
    4.  It offloads 100% of KV cache data to host CPU DRAM, eliminating GPU HBM usage entirely for active sequences.

    *Answer*: The correct answer is C. Any free block can extend a sequence, removing external fragmentation within the fixed-block pool. Only the final partly filled block retains internal waste. Reclaimed capacity can support larger batches, but the gain depends on request lengths, available memory, and the latency contract. Paging changes allocation; it neither compresses tensor values nor changes the number of KV heads.

    *Learning Objective*: Analyze the virtual memory mapping mechanism of PagedAttention and its impact on KV cache fragmentation and serving throughput.

2.  **What cost does a colocated draft model impose on a speculative decoding replica, and how does it influence whether speculative decoding should be enabled for a specific serving endpoint?**

    1.  The latency penalty paid when draft models fail to generate valid UTF-8 token encodings.
    2.  The GPU memory allocated to draft model weights and draft KV cache, which reduces available HBM for batch concurrency.
    3.  The serialization overhead incurred when transmitting draft tokens across InfiniBand interconnects.
    4.  The loss in model generation accuracy caused by greedy sampling during draft token verification.

    *Answer*: The correct answer is B. Draft weights and draft KV cache consume memory that could otherwise support target-model concurrency. Speculation is useful when lower latency or more accepted output per target pass outweighs that capacity cost and draft execution. The result depends on load, acceptance, and both models; a latency-oriented endpoint does not automatically benefit, nor is every throughput-oriented endpoint harmed.

    *Learning Objective*: Evaluate the memory and throughput trade-offs of speculative decoding as an admission and scheduling policy under service-level agreements.

3.  **Why does speculative decoding accelerate autoregressive generation on modern GPUs without altering the target model’s output probability distribution?**

    1.  It lets the draft model’s tokens through whenever the draft model’s own confidence exceeds a fixed threshold, so the target pass can be skipped for confident tokens
    2.  It runs the target model at lower precision during verification, so each verification pass streams fewer weight bytes than an ordinary decode step
    3.  It accepts each draft token with probability equal to the smaller of one and the ratio of the target model’s probability to the draft model’s probability, resamples a rejected position from the normalized positive difference between the two distributions, and verifies all drafts in one target pass for roughly the weight traffic of one token
    4.  It verifies only the first draft token and emits the remaining drafts unchecked, relying on the draft model’s training to match the target

    *Answer*: The correct answer is C. The acceptance-and-resampling rule makes the emitted sequence follow the target model’s distribution exactly, and verifying every drafted position in one target pass streams the target’s weights once, the same reuse batching buys but drawn from one request’s future tokens. Confidence thresholds or partial verification are approximate rules that do not inherit the guarantee, and verification runs at the target’s own precision.

    *Learning Objective*: Analyze how speculative decoding achieves latency speedups while preserving exact target model output distributions

4.  **A chatbot has 1,000 concurrent users sharing a 2,000-token prefix and retaining 500 private response tokens each. For a hypothetical MHA model with 80 layers, 64 KV heads, head width 128, and FP16 cache, explain the reduction from about 6.6 TB to 1.3 TB with prefix sharing.**

    *Answer*: Each cached token uses 2 × 80 × 64 × 128 × 2 = 2,621,440 bytes. Without sharing, 2,500,000 token positions consume 6.5536 TB; storing the shared prefix once leaves 2,000 + 1,000 × 500 = 502,000 positions, or 1.316 TB. The reduction is 79.92%. This is an MHA scenario, not the smaller eight-KV-head GQA cache of Llama-2-70B; saved memory alone does not prove a fivefold throughput gain.

    *Learning Objective*: Calculate KV cache memory savings achieved through prefix caching in shared-context multi-tenant workloads.

5.  **True or False: When measured acceptance falls and the scheduler stops running the draft model, the memory that speculative decoding consumed returns immediately to the target model’s KV-cache admission budget.**

    *Answer*: False. Disabling draft execution stops the drafting and verification work, but the resident draft weights and any draft KV pages remain allocated. Recovering that memory for target requests requires unloading the draft weights and ending or migrating the speculative state, so the speculation policy and the admission controller must be evaluated together.

    *Learning Objective*: Evaluate speculative decoding as a serving policy whose memory cost persists until the draft state is released.

6.  **In the precision dividend for the reference 70B replica, FP16 weights use 17.5 GB per GPU on eight 80 GB GPUs. Ignoring runtime reserves and quantization metadata, INT4 weights use about 4.4 GB per GPU and INT8 KV cache halves the per-request cache footprint. Why is the gain in maximum batch about 2.4 times rather than the fourfold weight reduction?**

    1.  Because INT4 weights must be dequantized into a resident FP16 copy, so only part of the weight saving survives in HBM
    2.  Because the gain applies only to the eight-head GQA cache; the 64-head MHA baseline gains nothing from INT8 KV storage
    3.  Because the freed weight memory raises the KV budget from 62.5 GB to about 75.6 GB per GPU, a factor of about 1.21, and halving bytes per cached request doubles the count again, so the two effects multiply to about 2.4
    4.  Because quantizing the KV cache lengthens each decode step enough to cancel most of the extra capacity

    *Answer*: The correct answer is C. Maximum batch is free memory divided by per-request cache. INT4 weights raise free memory by 75.6/62.5 ≈ 1.21, and INT8 cache halves per-request state, a factor of two, giving about 2.4 for either attention layout. The weight reduction is fourfold, but weights are only part of each GPU’s budget. Runtime reserves, metadata, and the latency target lower the deployable batch below this bound.

    *Learning Objective*: Synthesize how weight and KV-cache quantization interact multiplicatively to expand serving batch capacity

1.  **Why do the prompt prefill phase and the token decode phase of LLM serving exhibit different performance bottlenecks on the same accelerator?**

    1.  Prefill generates tokens sequentially one by one, making it memory-bound by weight reads, whereas decode processes all prompt tokens in parallel, making it compute-bound by Tensor Cores
    2.  Prefill relies exclusively on integer arithmetic units, whereas decode requires floating-point matrix multiplication units
    3.  Long-prompt prefill GEMMs reuse weights across prompt tokens and can have a compute ceiling, whereas weight-dominated single-request decode has low intensity and a bandwidth ceiling
    4.  Prefill requires continuous network AllToAll collective exchanges between GPUs, whereas decode requires no inter-GPU communication

    *Answer*: The correct answer is C. Long-prompt prefill GEMMs can reuse weights across many prompt tokens, while single-request decode streams weights for one token. The simplified FP16 estimates place those components above and below the ridge, respectively. Neither estimate proves saturation or classifies every operator: actual traffic, kernel shapes, cache reads, dispatch, and communication require profiling. The phases use compatible arithmetic rather than exclusively different number types.

    *Learning Objective*: Compare the computational characteristics and primary hardware bottlenecks of the prefill and decode serving phases

2.  **How can an un-chunked long prompt prefill delay active decode streams on the same worker, and what trade-off does chunked prefill introduce?**

    *Answer*: A policy that schedules a full long-prompt prefill before returning to decode can create a conspicuous gap in active streams’ time between tokens (TBT). An isolated stall can be diluted in a long response’s average time per output token (TPOT). Chunked prefill interleaves bounded prompt-token chunks with decode work, controlling how much prefill work enters each iteration. Smaller chunks can reduce interference while adding overhead and extending the incoming prompt’s TTFT. A token budget alone does not guarantee a time bound; both TTFT and TBT tails require measurement.

    *Learning Objective*: Explain the operational mechanism of chunked prefill in preventing decode stalls and mitigating tail latency.

3.  **The architectural pattern that decouples LLM inference by executing the compute-bound prompt prefill phase and the bandwidth-bound autoregressive token decode phase on separate, specialized hardware pools is known as \_\_\_\_ serving.**

    *Answer*: disaggregated. Separate pools specialize for prompt processing and token generation; transferring the KV cache between them adds a communication cost that the specialization must repay.

    *Learning Objective*: Identify the architectural term for separating prefill and decode workloads across specialized hardware pools

4.  **True or False: Because disaggregation removes prefill-decode interference, moving a deployment to separate prefill and decode pools lowers time to first token most for the longest prompts.**

    *Answer*: False. The prefill pool must hand each request’s KV cache to the decode pool, and that handoff costs at least a startup term plus KV bytes divided by link bandwidth. KV bytes grow linearly with prompt length, so the longest prompts pay the largest transfer, and it lands on time to first token. Disaggregation earns its transfer cost only when removing interference and balancing the two pools raises measured SLO goodput.

    *Learning Objective*: Evaluate the KV-cache handoff cost that disaggregated serving adds to time to first token

1.  **How does SmoothQuant enable efficient 8-bit weight and 8-bit activation (W8A8) inference, and why is its speedup significantly higher during prefill than during decode?**

    1.  Autoregressive decode is strictly compute-bound; increasing memory without adding Tensor Cores leaves execution time unchanged.
    2.  Autoregressive decode is memory-bandwidth bound ($D_{\text{vol}} / \text{BW}$); once model weights fit resident in memory, token generation speed is constrained by memory bandwidth, not total memory capacity.
    3.  140 GB GPUs automatically disable CUDA graph compilation, adding driver launch latency to every iteration.
    4.  The larger memory capacity forces PagedAttention block sizes to shrink from 16 tokens to 2 tokens.

    *Answer*: The correct answer is B. At the same small batch and context length, when weight reads dominate decode and the resident model already fits, extra memory capacity does not increase the bandwidth ceiling. A larger admitted batch can nevertheless raise aggregate token throughput by sharing weight reads across more sequences while execution remains bandwidth-bound. The gain stops when KV traffic, compute, or the latency budget binds; crossing into a compute-bound regime is not required for batching to help.

    *Learning Objective*: Analyze why memory bandwidth, rather than memory capacity, bounds autoregressive decode throughput.

2.  **A capacity planner provisions an inference serving fleet for 80% average utilization based on mean daily traffic. Why can traffic spikes exhaust headroom before reactive scaling helps, and what determines whether the P99 SLO is missed?**

    *Answer*: Waiting grows sharply as utilization approaches one. At an 80% baseline, a 25% traffic increase reaches exactly 100% utilization, leaving no spare capacity to absorb arrival or service-time variation; a larger sustained increase exceeds capacity. Cold starts can take minutes, so reactive scaling may arrive after latency failures begin. Whether a spike misses the P99 SLO depends on its duration, the arrival and service-time distributions, the waiting budget, and admission policy. Capacity planning therefore needs measured peak behavior and ready headroom alongside average traffic.

    *Learning Objective*: Explain the queuing theory and autoscaling risks of provisioning inference fleets based on average rather than peak-plus-headroom demand.

3.  **True or False: Deploying continuous batching alone completely solves all throughput and latency bottlenecks in LLM serving.**

    *Answer*: False. Continuous batching reuses slots at iteration boundaries. It does not remove the quadratic attention work of long full-attention prefills, shrink the KV tensors needed by admitted requests, or eliminate communication within sharded replicas. Additional mechanisms are selected for the binding constraint: chunking can limit prefill interference, paging can recover allocation waste, compatible prefix reuse can avoid repeated work, and sharding or replication can supply needed capacity. No fixed combination establishes the service contract without workload measurements.

    *Learning Objective*: Evaluate the scope and limitations of continuous batching within the end-to-end LLM serving pipeline.

4.  **True or False: Because each token activates only a small fixed number of experts, raising an MoE model’s expert count from 8 to 256 adds serving capacity at essentially no cost.**

    *Answer*: False. Every expert occupies memory whether or not a token selects it, so more experts mean more devices or less KV headroom, and a distributed placement adds dispatch, combine, and imbalance costs. The design is justified only when a matched-quality comparison shows active-compute savings exceeding routing, imbalance, memory, and communication costs.

    *Learning Objective*: Analyze the system-level memory, communication, and load balancing costs of scaling expert counts in MoE models

5.  **A team moves its endpoint from INT8 to INT4 weights and INT4 KV cache, doubling tokens per second while held-out perplexity changes by less than 1 percent. What should it conclude before rollout?**

    1.  The change doubles useful capacity, because perplexity confirms quality is unchanged
    2.  The change is safe only if the KV cache returns to FP16, because weight precision never affects quality
    3.  Useful capacity has not been established: low-bit formats can degrade rare languages, edge cases, or reasoning while perplexity barely moves, so quality must be evaluated per layer and per task and reported beside throughput
    4.  The change should be rejected, because INT4 always reduces quality below an acceptable level

    *Answer*: The correct answer is C. Throughput and quality form a frontier, and a precision choice is a point on it. Perplexity can stay nearly flat while users see worse answers on hard or rare inputs, so targeted quantization measures per-layer sensitivity, keeps sensitive tensors at higher precision, and evaluates diverse quality benchmarks alongside latency and throughput. Neither blanket acceptance nor blanket rejection follows from bit width alone.

    *Learning Objective*: Evaluate quantized serving changes on the throughput-quality frontier rather than throughput alone
