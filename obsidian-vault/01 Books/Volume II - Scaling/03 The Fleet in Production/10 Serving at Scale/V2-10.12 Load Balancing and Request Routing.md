# V2-10.12 Load Balancing and Request Routing

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-load-balancing-request-routing-4997

Suppose ten model replicas are serving traffic when a request for a 5,000-word document summary arrives. Assigning it to an overloaded replica adds waiting and can increase interference for work already admitted there. The effect depends on admission, batching, and priority policies. Round-robin assignment does not inspect those differences in remaining work. A state-aware router uses memory and queue information to choose a feasible destination, while limiting the cost and staleness of its observations.

**Lighthouse 10.2: Archetype B (DLRM at Scale): The tail at scale**

Archetype B (DLRM at Scale) uses $\text{p99} \le 100\text{ ms}$ as its illustrative latency target. At $10^{7}$ QPS, an event probability of $10^{-4}$ implies an expected 1,000 such events per second. This count motivates examining the tail, but does not identify its cause. Two-choice routing can reduce imbalanced queuing delay ${L_{\text{lat,queue}}}$; traces must establish whether queueing, inference time ${L_{\text{lat,infer}}}$, or another component drives the misses.

Load balancing serves two goals that can conflict: sending each request to the replica that can serve it fastest, and spreading load so that no replica idles or saturates. Latency-optimal routing can concentrate load on fast replicas until they slow down. Evaluation therefore needs signals for both goals, queue length and estimated remaining work per replica for latency and utilization spread for balance. It also needs the decision overhead of the routing choice. All signals are judged against completed-request tail latency and admission outcomes rather than balanced request counts.

### Tail Latency Under Fan-Out

^sec-inference-scale-fanout-tail

When a serving request fans out to 100 backend shards that each meet their own p99 latency target independently, the assembled response misses that threshold about 63 percent of the time. Many serving requests are not one call but a set of parallel sub-requests whose results must all return before the response can be assembled. Examples are a ranking query that scores candidates on many shards, a recommendation that looks up embeddings across tables, and a sharded model whose replicas must all finish a step. Because the request completes only when its slowest leaf returns, it inherits the tail of every leaf it touches, the way a series system fails when any one component fails. If each of ${N_{\text{series}}}$ leaves independently exceeds its own latency threshold with probability ${p}$, the request exceeds it with probability $1 - (1 - {p})^{{N_{\text{series}}}}$.

Reading the same expression backward turns it into a budgeting rule. To keep the whole request within its p99 target, each of the 100 leaves may be slow only about 0.01 percent of the time, so the leaf target moves from p99 to roughly p99.99. Fan-out width is therefore a tail-latency cost that the service pays per request, and the levers act on different terms. Fewer, larger shards lower ${N_{\text{series}}}$. Queue-aware routing and isolation lower ${p}$ by keeping leaves out of their own queueing tails. A deadline with a partial or default result, as in the search cascade of [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.16 Case Studies#^sec-inference-scale-google-search-ranking-aab2|section 10.15.4]], caps the damage when a leaf still misses. Hedged requests lower ${p}$ further at the price of duplicated work. The independence assumption is optimistic, because a shared switch, host, or hot key slows many leaves together, so the measured composed tail is the quantity to budget, not the formula alone.

↩︎ The same independence model applied to storage reads, and hedged reads with their failure-domain placement, are established in **[[01 Books/Volume II - Scaling/01 The Fleet/04 Data Storage/V2-04.04 The ML Storage Hierarchy#^sec-storage-tier3-pfs|Tier 3 parallel file systems]]**.

### Round-Robin and Random Assignment

^sec-inference-scale-roundrobin-random-assignment-f374

Routing requests in a fixed cycle or at random works when every call costs the same, but in an inference fleet where one request generates 10 tokens and the next generates 2,000, stateless assignment piles long queues onto unlucky replicas while others sit idle. Round-robin cycles through the servers in order, which distributes work evenly only when servers are homogeneous and processing times identical, while random assignment picks a server uniformly, converging to an even mean with higher variance. Both are reasonable baselines for identical servers, but heterogeneous GPU generations, variable request sizes, warmup behavior, and replicas nearing memory limits make the state of the server fleet matter in production.

A static placement model isolates the imbalance caused by random choice: place ${R}$ equal-size jobs sequentially into ${R}$ initially empty bins, without departures. With uniform independent choices, the expected maximum bin occupancy follows the classical balls-into-bins result ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-mitzenmacher2001|Mitzenmacher 2001]]) in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^eq-random-max-queue|equation 14]]:

![[90 Assets/Volume II/10 Inference/Vol2 Inference Margin 003 add17bc002.svg]]

*Two slowly rising curves of maximum load as the fleet grows: a gray random-assignment curve keeps climbing, while a blue two-choice curve stays lower and flattens.*

*Two-choice routing flattens the tail imbalance of random placement.*

$$
\mathbb{E}[\text{max bin occupancy}] ={\Theta}\left(\frac{\log {R}}{\log \log {R}}\right) \tag{14}
$$

^eq-random-max-queue

Here ${R}$ counts both jobs and bins. The asymptotic expression does not predict a finite serving queue at a given fleet size, because arrivals, departures, job sizes, and service rates are absent from this model. The power of two choices (principle [[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-power-two-choices|19]]) changes the occupancy tail using one additional probe.

### The Power of Two Choices

^sec-inference-scale-power-two-choices-ffdd

Polling every replica in a large fleet on every arrival turns the load balancer into a coordination bottleneck, yet picking one replica blindly leaves hot queues unchecked. A foundational result in load-balancing theory ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-mitzenmacher2001|Mitzenmacher 2001]]) shows that querying only two random servers before making a routing decision provides exponentially better load distribution than random assignment in the static balls-into-bins model. The procedure is deliberately small, but the load signal must match the serving workload. The destination must atomically admit or reject the request because probe results can become stale; a rejection requires bounded retry or overload handling. For a homogeneous vision fleet, current queue length may be enough. For an LLM fleet, active tokens, estimated remaining decode work, and KV-cache pressure better approximate the work a replica has already accepted. [Algorithm 4](https://mlsysbook.ai/vol2/10_inference/10_inference.html#algo-power-two-choices-routing) states a representative routing loop: probe two replicas, compare normalized work, and route without polling the whole fleet.

$\mathcal{S}$

Two probes avoid an all-replica scan. The practical algorithm uses predicted work and capacity weights; it is a serving heuristic, not the uniform static placement process. For the latter process, choosing the less occupied of two independently sampled bins gives [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^eq-two-choices-max-queue|equation 15]]:

$$
\mathbb{E}[\text{max bin occupancy}]_{\text{two choices}} = {\Theta}(\log \log {R}) \tag{15}
$$

^eq-two-choices-max-queue

**Theorem 10.2: Power-of-two choices load-balancing bound**

For ${R}$ equal-size jobs placed sequentially into ${R}$ initially empty bins, without departures, uniform random placement has maximum occupancy $\mathcal{O}(\log {R}/ \log \log {R})$ with high probability. Choosing the less occupied of two independent uniform candidates reduces this to $\mathcal{O}(\log \log {R})$.

The bound shows that limited probing substantially improves maximum occupancy in this static model. Two probes avoid the ${R}$-probe cost of examining every bin. Applying the idea to serving requires a load signal that reflects remaining work and available capacity; the theorem does not establish near-optimal latency for changing queues, heterogeneous replicas, or stale measurements.

The mechanism is the suppression of repeated unlucky placement. If ${m}$ of ${R}$ bins have occupancy at least ${k}$, one uniform probe hits that set with probability ${m}/{R}$, whereas two independent probes both hit it with probability $({m}/{R})^2$.

### Weighted and Adaptive Load Balancing

^sec-inference-scale-weighted-adaptive-load-balancing-1c03

Sending equal request rates to replicas with different hardware capacities saturates the slower tier while leaving the faster tier underutilized. In a mixed A100 and T4 fleet, the lower-capacity replicas reach saturation first as demand increases; equal routing does not imply overload at every arrival rate. Weighted assignment accounts for measured capacity by allocating the following long-run request share to each server:

$$
\Pr(\text{route to server } {i}) = \frac{{w}_i}{\sum_j {w}_j}
$$

where ${w}_i$ is the weight, or capacity, of server ${i}$. Weighted two-choices applies the same idea to tail control: sample two servers with probability proportional to their weights, compare current load relative to capacity, and route to the lower relative load. The weighted-routing example makes this policy concrete for mixed GPU hardware.

**Example 10.8: Heterogeneous GPU cluster**

**Scenario**: A serving cluster mixes 10 H100 GPUs (1000 QPS each) and 20 A100 GPUs (600 QPS each), processing 15,000 QPS target traffic.

**Diagnosis**: Unweighted round-robin routes equal request counts (500 QPS) to all nodes, leaving H100s underutilized (50 percent) while leaving less latency headroom on A100s (83.3 percent). Weighted routing assigns H100s a weight of 4.5 percent and A100s a weight of 2.7 percent, balancing utilization across tiers (68.2 percent vs. 68.2 percent).

**Systems lesson**: Heterogeneous inference clusters require capacity-weighted routing. Equal request volumes produce unbalanced load when hardware tiers have different service rates.

^exmp-inference-heterogeneous-gpu-cluster

Static weights handle known capacity differences, but production replicas also change over time. Adaptive load balancing adjusts weights dynamically based on observed performance:

    For each server i:
        latency[i] = exponential_moving_average(observed_latency)
        weight[i] = 1 / latency[i]  # Inverse latency weighting

Inverse latency weighting reduces traffic to replicas whose observed latency rises. That observation mixes server condition with request cost: a replica receiving longer generations can appear slow even when its hardware is healthy. Delayed measurements can also make weights oscillate as traffic shifts. The heuristic therefore needs evaluation against comparable request classes, measurement lag, and overload behavior before its weights can be treated as capacity estimates.

### Least-Connections Load Balancing

^sec-inference-scale-leastconnections-load-balancing-3f21

Even capacity-weighted routing can overload a replica that draws several long-running generations in a row while neighboring servers finish short replies. Least-connections routes to the server with the fewest active requests, incrementing a counter on dispatch and decrementing it on completion. This accounts for unfinished requests that round-robin does not inspect, though a connection carrying multiple requests needs different bookkeeping. The policy improves routing only to the extent that the count represents the work and capacity competing at each replica. Connection counts are themselves a proxy. Two in-flight LLM requests can differ fiftyfold in remaining decode work, from a 10-token reply to a 500-token essay, so active tokens or estimated remaining work track load more faithfully than the count of open requests.

The challenge is maintaining accurate connection counts in a distributed system. A centralized counter gives a single source of truth but can become a bottleneck. Distributed counters with gossip scale better but may route using stale information. Sampled least-connections combines the idea with two choices by probing only a subset of servers and choosing the minimum.

No routing policy wins on every axis. Random and round-robin assignment have low decision overhead but ignore work in progress. Two-choice routing samples load state, while least-connections tracks outstanding requests at the cost of maintaining current counts. Neither counts nor limited probes fully describe remaining work when request costs vary widely. Which policy meets a tail target is an empirical question, evaluated with the same arrival trace, request-length mix, and replica capacities.

### Consistent Hashing for Stateful Routing

^sec-inference-scale-consistent-hashing-stateful-routing-ae5b

Routing each turn of a multi-turn conversation to a different replica forces the receiving server to recompute or fetch the entire conversation’s KV cache before generating a single new token. How much state a serving system retains across requests determines what must be preserved when traffic moves between replicas. Vision inference and individual embedding lookups can expose stateless interfaces because they need no session history from an earlier request. A ready replica with the required model and data can then accept a rerouted request. Adding replicas still requires loading that state, distributing traffic, and checking downstream capacity; failure recovery also requires spare capacity and a policy for retrying interrupted work. Statelessness removes session-state migration from these operations, but does not remove their resource costs.

↩︎ Stateless and stateful failure recovery mechanics are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^sec-fault-tolerance-reliability-reliability-stateless-vs-stateful-serving-0a60|Stateless vs. stateful serving]]**.

An autoregressive request is stateful while it is generating because its KV cache belongs to that in-flight sequence. Cross-request statefulness is optional. An API may send the full conversation history with every turn and rebuild KV state during prefill, making any replica eligible for the next request. A serving platform may instead retain a completed turn’s KV state as a session cache, reducing repeated prefill at the cost of replica affinity, cache lifetime management, and recovery complexity. Sticky routing is an optimization for that retained cache, not a correctness requirement of autoregressive models.

The scaling divide is therefore an interface and cache-policy decision. Every live generation needs request-scoped state, but the service decides whether state survives the request boundary. Session-cached service saves prefill work but must drain, migrate, or rebuild cached state during scaling and failure, so affinity earns its place only when measured cache-reuse value exceeds the resulting imbalance and recovery costs. Recommendation sessions that carry user context and streaming inference that depends on state from earlier frames benefit from the same routing affinity, while a stateless LLM API may still use prefix-aware routing when a reusable prefix happens to be cached.

Consistent hashing[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.21 Footnotes#^fn6|⁶]] ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-karger1997|Karger et al. 1997]]) maps requests to servers based on a hash of the routing key (user ID, session ID). Servers and keys are hashed onto the same circular space, called the ring, and each key belongs to the first server reached by moving clockwise from the key’s position:

$$
\text{server}(\text{request}) = \operatorname{arg\,min}_{{s}\in {\mathcal{S}_{\text{srv}}}} \text{distance}(\text{hash}(\text{key}), \text{hash}({s}))
$$

where ${\mathcal{S}_{\text{srv}}}$ is the set of servers mapped onto the ring and distance is measured clockwise from the key’s hash.

For fixed ring membership, consistent hashing sends the same key to the same server. Membership changes affect only part of the ring, because a server that joins or leaves changes the owner of only the arc of keys next to it. With balanced equal-capacity assignments and uniformly distributed keys, adding a server moves an expected $1/({N}+1)$ fraction of keys, those in the arc it takes over, while removing one affects its expected $1/{N}$ share. Virtual nodes help smooth uneven ranges, but popular keys can still concentrate traffic even when key counts are balanced. For session-cached LLM serving, affinity increases the chance of reaching reusable state. That benefit must outweigh additional waiting; overload routing, failure, eviction, and remapping can still require repeated prefill. The same stateful routing machinery becomes a correctness boundary when cached state is user-specific.

**War Story 10.1: When cache state crossed users (2023)**

**Context**: ChatGPT used Redis Cluster through the redis-py client to cache user information and conversation titles in a high-volume serving system ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-openai2023chatgptoutage|OpenAI 2023]]).

**Mechanism**: Under an Asyncio connection-pooling race condition, canceled requests left unread responses in recycled connection buffers, causing subsequent requests to receive cache data belonging to previous users.

**Impact**: On March 20, 2023, OpenAI took ChatGPT offline after a bug allowed some users to see another active user’s conversation titles. Further investigation found possible exposure of payment-related information for a subset of active Plus subscribers during a nine-hour window; full credit card numbers were not exposed.

**Fix**: OpenAI sent the Redis maintainers a patch for the redis-py cancellation path and added redundant checks that the data returned from the cache belongs to the requesting user.

**Systems lesson**: Stateful inference infrastructure needs isolation guarantees around caches, connection pools, and routing keys. A cache is part of the serving correctness boundary, not merely an optimization.

↪ Shared prefix caches as a cross-tenant leakage channel, and the tenant-scoped caches that close it, are developed in **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.07 Fleet-Internal Trust Boundaries#^sec-security-privacy-shared-accelerators|Shared accelerators and caches]]**.

### Request Routing for Sharded Models

^sec-inference-scale-request-routing-sharded-models-6432

Treating individual GPUs inside a sharded model as independent routing targets breaks execution: a tensor-parallel group must run every layer in lockstep across all its ranks, and a pipeline group can admit new requests only at its first stage. A sharded replica is therefore one routing destination even though several devices execute the request. A tensor-parallel group presents one destination whose latency already includes its per-layer collectives ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.11 Model Sharding for Inference#^fig-tensor-parallel-flow|figure 16]]). A pipeline group admits requests at its first stage ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.11 Model Sharding for Inference#^fig-pipeline-bubbles|figure 17]]), so the router must account for the group’s service capacity rather than treat each stage as a replica. In expert-parallel architectures, the gating network ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.11 Model Sharding for Inference#^sec-inference-scale-moe-parallelism|section 10.10.4.2]]) routes tokens across internal expert destinations after the external router has chosen the replica, so expert imbalance and replica imbalance require different controls. The result is a two-tier topology ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^fig-shard-group-scaling|figure 18]]) in which the external load balancer sees each shard group as one destination and the group’s NVLink collectives stay inside it.

![[90 Assets/Volume II/10 Inference/Shard Group Scaling 044e892dbd.svg]]

Figure 18: **Horizontal Scaling with Shard Groups**: The load balancer treats each shard group as a single logical inference server and chooses among groups by round-robin, two-choice, or session-affinity routing. Within a group, eight GPUs hold the tensor-parallel weight shards and join partial results with an NVLink AllReduce inside every layer, which the router never sees. Adding ready groups raises aggregate capacity; the group’s internal parallelism affects per-request latency.

### KV Cache Migration Between Replicas

^sec-inference-scale-kv-cache-distributed-settings-712e

When a replica fails or consistent hashing remaps a session to a new shard group, the new group cannot generate the next token until it either receives the conversation’s gigabyte-scale KV cache over the network or reruns prefill across the entire history. Routing a request to a shard group fixes where its KV state lives ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.11 Model Sharding for Inference#^sec-inference-scale-tensor-parallelism-b29f|section 10.10.2]]), so moving an active session between groups forces a choice between network transfer and recomputation ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^sec-inference-scale-consistent-hashing-stateful-routing-ae5b|section 10.11.6]]). Transfer requires a reachable source or a saved copy; after an unrecoverable replica failure, the service rebuilds from authoritative conversation history:

    Migration options:
    1. Rebuild: Re-run prefill on new replica (cost grows with context length)
    2. Transfer: Send KV cache over network (cache bytes / link bandwidth)
    3. Hybrid: Apply the threshold below when the source is reachable;
       otherwise rebuild

    Decision threshold:
    if cache_size_bytes/network_bandwidth < prefill_time:
        transfer()
    else:
        rebuild()

For Llama 3 70B with GQA and a 4,096-token context, KV cache is about 1.3 GB total per sequence, or about 168 MB per device under 8-way tensor parallelism. At 100 Gb/s (12.5 GB/s), the bandwidth-only estimate for one shard is roughly 13 ms, while sending the full cache over one such link takes about 107 ms. The prefill approximation counts $5.8 \times 10^{14}$ FLOPs ($2 \times 7.1 \times 10^{10}$ parameters $\times$ 4,096 tokens), giving roughly 180 ms on the tensor-parallel group at the assumed 40 percent utilization. Transfer is faster in this comparison, but achieving the per-shard time for the whole group requires concurrent links with sufficient aggregate bandwidth. Shared network bottlenecks, source availability, cache conversion, and destination queueing can change the decision. Long-context attention adds rebuild work omitted from this approximation, so measured transfer and prefill times should determine the policy.

The shard group boundary also defines readiness. A group can accept work only when the devices, model state, and cache capacity required for its execution plan are available, so the load balancer needs a health signal for the serving replica as a whole.

### Health Checking and Failover

^sec-inference-scale-health-checking-failover-070e

An inference worker whose HTTP server responds `200 OK` to a shallow ping can still time out every real query if its weights are still loading, its KV pool is exhausted, or its CUDA context is wedged. Load balancers can route around failure only if the health signal matches the failure mode across three probe tiers (liveness, readiness, and inference correctness) that escalate from cheapest to most realistic. On an accelerator replica, each tier must test a different part of the serving state: readiness includes admission capacity as well as loaded weights and completed warmup, while an inference probe compares a fixed prompt’s output or logits against expected bounds. Passing that probe does not establish correctness or capacity for every request shape, so production errors and latency remain necessary health signals. Failover then depends on the detected failure, available replacement capacity, and whether affected KV state can be transferred or must be reconstructed.

↩︎ Liveness, readiness, and inference-correctness probes, the failover time their settings bound, and stateful failover are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^sec-fault-tolerance-reliability-reliability-failover-mechanisms-5ddd|Failover mechanisms]]**.

### Circuit Breakers and Backpressure

^sec-inference-scale-circuit-breakers-backpressure-e61c

When a GPU inference server slows down, routing more requests to it can turn a local problem into a fleet-wide failure. Consider an illustrative rise in service time from 50 ms to 500 ms. Queues accumulate, client timeouts generate retries, and rerouted work consumes neighboring replicas’ headroom. The cause might be a stalled dependency, device degradation, or resource contention. The load balancer needs a policy for withdrawing an unhealthy replica while controlling the displaced load.

The circuit breaker pattern ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-nygard2007releaseit|Nygard 2007]]) limits repeated work sent to an unhealthy destination. In the closed state, the server receives normal traffic. When the configured error, timeout, or latency threshold is exceeded, the breaker opens and requests fail fast or become candidates for rerouting. After a recovery interval, a half-open state admits limited probes, closing on recovery or reopening on failure ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^fig-circuit-breaker|figure 19]]). Opening a breaker does not create replacement capacity, so rerouting must respect admission limits and retry budgets or it can overload the surviving replicas.

![[90 Assets/Volume II/10 Inference/Circuit Breaker 8251bf00d4.svg]]

Figure 19: **Circuit Breaker States**: The circuit breaker protects the system from cascading failure. Closed: normal operation. Open: error threshold exceeded; all requests fail fast to prevent resource exhaustion. Half-open: after a timeout, a limited number of requests are allowed through to probe the dependency’s health. Success resets to closed; failure returns to open.

^fig-circuit-breaker

Backpressure propagation complements the breaker by making overload visible upstream. When queue depth crosses a threshold, the server returns a signal such as `503 Service Unavailable`; the load balancer marks the replica as degraded and routes fewer requests to it. If all replicas become degraded, the system shifts from routing control to admission control, rejecting some requests at the edge rather than accepting work it cannot serve within the latency SLO. Load-shedding policies decide which requests to reject first. Circuit breakers isolate unhealthy replicas; backpressure tells the rest of the system to slow down before retries amplify the failure.

↩︎ Load shedding, model fallback, and the other strategies that trade quality for availability are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.13 Graceful Degradation#^sec-fault-tolerance-reliability-reliability-graceful-degradation-strategies-e85e|Graceful degradation strategies]]**.

Backpressure works only when the request contract propagates through the whole serving graph. The gateway converts the client timeout into an absolute deadline and every downstream stage subtracts elapsed time before admitting more work. If the client disconnects or the deadline expires, cancellation must reach queued CPU work, accelerator batches, retrieval calls, and streamed output. A canceled request that remains in a continuous batch is zombie work: it consumes KV pages and decode bandwidth while producing no useful response. Some kernels cannot be interrupted mid-launch, so cancellation commonly takes effect at the next batch or token boundary; the scheduler must measure that cancellation lag rather than promise instantaneous preemption.

The same request identifier must connect routing, queueing, prefill, decode, cache allocation, and response streaming. A useful serving trace records admitted and rejected requests, queue delay, TTFT, TPOT, input and output tokens, cache pages, batch membership, preemptions, cancellations, and fallback decisions. Aggregate accelerator utilization cannot distinguish useful work from late or canceled work. SLO goodput and the wasted-token rate close that gap. SLO goodput reports how much completed work met its contract. The **wasted-token rate** is the fraction of generated tokens spent on requests that were canceled, timed out, or delivered after their deadline, the execution the system performed after the result had lost value.

A saturated LLM fleet operating under severe KV cache pressure has three workload-specific relief options. Engines can apply context eviction through an explicitly supported sliding-window or approximate policy with a quality check, or truncate retained history and recompute its state. Silently dropping old KV entries is not equivalent to recomputing a shorter conversation, because later cached states already depend on the earlier context. Disabling speculative execution reduces draft work, but reclaiming its memory also requires unloading draft weights and releasing the associated cache state. Finally, fallback routing can send eligible requests to a smaller model with available capacity, provided that model meets the application’s fallback quality contract.

These options change latency, resource use, or model behavior in different ways. The application must specify which changes are acceptable at each pressure tier. Context truncation can remove information essential to an answer, and a smaller model can fail the task’s quality requirement. In those cases, an explicit rejection can be preferable to an apparently successful but unacceptable response.

Routing relies on estimates of replica capacity, but shared hardware can make that capacity change when another workload becomes active. Critical production models may share a cluster or device with experimental models and developer endpoints. Protecting the serving contract under that interference requires multi-tenant isolation in addition to routing.
