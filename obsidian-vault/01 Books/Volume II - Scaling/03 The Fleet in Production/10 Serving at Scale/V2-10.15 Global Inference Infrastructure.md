# V2-10.15 Global Inference Infrastructure

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-global-inference-infrastructure-df52

A fleet confined to one region can batch, shard, route, isolate, and autoscale well, yet a user in Sydney still pays roughly a 200 ms round trip to a US-East deployment before any of that machinery acts. A regional outage also removes every replica at once. Extending resource isolation and failure boundaries beyond one data center introduces placement decisions at geographic scale. Distance, regional failures, and data-placement requirements can motivate regional replicas, caches, or a centralized service with an explicit network budget. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^fig-serving-deployment-stack|Figure 23]] illustrates three tiers: edge points of presence for reusable responses, regional gateways for authentication and routing, and GPU clusters for model execution. Its 10 ms, 50 ms, and 2 s budgets are scenario targets, not measured performance or universal deadlines. The application must define whether its execution budget governs first response, individual tokens, or completion of the entire request.

![[90 Assets/Volume II/10 Inference/Serving Hierarchy 8959a9f87b.svg]]

Figure 23: **Serving Deployment Stack**: A cache miss crosses three tiers before reaching a model replica. Tier 1 edge points of presence (PoPs) enforce authorization and reuse eligibility before answering repeated requests from cache; a miss passes to Tier 2, where the gateway applies rate limits and authentication and the router picks a destination; Tier 3 GPU workers run prefill and decode while an autoscaler sizes the fleet from queue depth and KV cache use. Tokens stream back up through the tiers to the client. The per-tier latency budgets on the right, drawn on a log scale, are illustrative.

^fig-serving-deployment-stack

### Drivers for Multi-Region Deployment

^sec-inference-scale-multiregion-matters-d7d3

Serving all global traffic from a single US-East cluster forces European, Asian, and Australian users to pay a 75 to 200 ms wide-area network round trip on every request and leaves the entire service vulnerable to a single regional outage. Network round-trip time (RTT) adds a latency floor for distant users, and illustrative regional timings show that floor rising with distance from the serving region ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^tbl-rtt-by-user-location|table 23]]). Actual paths, access networks, and congestion require measurement.

| **User location** | **RTT to US-East** | **RTT to local region** |
|:------------------|:------------------:|:-----------------------:|
| **New York**      |       10 ms        |          10 ms          |
| **London**        |       75 ms        |          10 ms          |
| **Tokyo**         |       150 ms       |          10 ms          |
| **Sydney**        |       200 ms       |          10 ms          |

Table 23: **Network RTT by User Location**: A single US-East deployment imposes a 75 to 200 ms RTT on European, Asian, and Australian users, an order of magnitude above the local-region floor. Sequential calls that cross this boundary can add repeated wide-area delay. Regional replicas can reduce that exposed delay when placement policy, workload volume, and available capacity justify them.

^tbl-rtt-by-user-location

Network delays compound when a request makes sequential calls across the distant boundary; multiple model calls inside one backend region do not each pay another client-to-region RTT. Regional replication can shorten that path and separate failure domains. Data-placement policies also constrain eligible destinations. The General Data Protection Regulation permits international transfers under specified conditions rather than requiring blanket EU-only processing; applicable law and contractual commitments must be translated into explicit placement rules. Regional replicas, edge caches, and cross-region sharding then trade capacity, communication, and coordination within those rules.

### Global Load Balancing with Regional Replicas

^sec-inference-scale-pattern-1-global-load-balancing-regional-replicas-b7ac

Deploying replicas in multiple regions cuts wide-area latency only if the global router avoids sending users to a nearby region whose GPU queues are already saturated or whose data-residency rules forbid the request. In [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^fig-global-inference-multiregion|figure 24]], a global load balancer selects among regions that satisfy placement policy, serve a compatible artifact version, and meet readiness and capacity requirements. Measured network latency helps choose among those eligible destinations, because geographic proximity alone does not determine completion time, while a shared registry supplies versioned artifacts to the independent regional replicas.

![[90 Assets/Volume II/10 Inference/Global Inference Multiregion 6db60ec584.svg]]

Figure 24: **Global Load Balancing across Inference Regions**: A global load balancer routes each user to an eligible region with suitable latency and ready capacity ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^tbl-rtt-by-user-location|table 23]] gives the round-trip times this avoids). Each region (US-East, EU-West, Asia-Pacific) runs independent replicas of the same model, and EU requests can stay in the EU to meet data-residency rules. A shared model registry supplies versioned weights to every region. If a region fails, the load balancer reroutes its users only to destinations that still satisfy placement, readiness, and capacity requirements.

^fig-global-inference-multiregion

Replication also creates a version-management obligation. Push-based synchronization sends artifacts to each region, while pull-based synchronization lets regions fetch them after notification or polling. Neither mechanism alone guarantees consistent serving versions. Artifact verification, readiness gates, and coordinated activation determine when a region may serve the new version; hybrid synchronization combines push notification with pull verification.

During a rollout, regions may serve different versions. The application must decide whether that is acceptable and whether a request or session needs version pinning. A region-by-region canary deployment exposes the new version to one region’s traffic share at a time, and each expansion passes its own error-rate, latency, and quality gate with compatible prior artifacts retained for rollback.

↪ Staged rollout and the canary observation window, sized from the required sample count and the canary’s traffic share, are developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^sec-ml-operations-scale-canary-deployment-3d8b|Canary deployment]]** (**[[01 Books/Volume II - Scaling/03 The Fleet in Production/12 ML Operations at Scale/V2-12.06 CI CD for ML at Scale#^eq-canary-duration|equation 12.7]]**).

### Edge Caching with Central Inference

^sec-inference-scale-pattern-2-edge-caching-central-inference-f08e

Standing up a full GPU cluster in every continent is an expensive way to reduce round-trip latency when a large fraction of distant requests ask repeated FAQ or autocomplete questions. Caching responses at the edge avoids both the wide-area round trip and repeated central inference whenever a stored response remains valid for the incoming request. Before returning a hit, the edge must enforce authorization and match the relevant model version, conversation or retrieval context, generation policy, and freshness requirements. Identical visible queries do not necessarily permit the same answer, and fresh-sample semantics may prohibit reuse. A hit returns within an illustrative 10 ms budget, while a miss reaches the central cluster ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^fig-edge-cache-routing|figure 25]]); only responses eligible for reuse should enter the edge store.

![[90 Assets/Volume II/10 Inference/Edge Cache Routing a1e6752503.svg]]

Figure 25: **Cache Hit and Cache Miss Paths at the Edge**: A query first reaches the nearest edge point of presence (PoP). After enforcing authorization and reuse eligibility, the edge targets a cache-hit response in under 10 ms without touching a GPU. On a miss, the request passes through the regional gateway to the central GPU cluster, which runs prefill and decode. Generated tokens stream back to the user, and a response eligible for reuse can be stored at the edge for later queries. The saving depends on the rate of requests eligible for reuse; open-ended generation may offer few such requests.

^fig-edge-cache-routing

On the two paths of [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^fig-edge-cache-routing|figure 25]], cache hits avoid the backend round trip, while misses incur it. Effectiveness depends on request repeatability across workloads such as autocomplete, FAQ chatbots, open-ended chat, and code generation. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^tbl-edge-cache-hit-rates|Table 24]] supplies illustrative hit-rate envelopes for sensitivity analysis; an actual design must derive hit rate and correctness from production traces.

| **Workload**        | **Cache hit rate** | **Suitability** |
|:--------------------|:------------------:|:---------------:|
| **Autocomplete**    |       60–80%       |    Excellent    |
| **FAQ chatbot**     |       40–60%       |      Good       |
| **Open-ended chat** |       5–15%        |      Poor       |
| **Code generation** |       20–40%       |    Moderate     |

Table 24: **Illustrative Edge-Cache Hit-Rate Envelopes**: Assumed cache-hit ranges for four workload shapes. These values are scenario inputs, not universal workload statistics. Trace-derived repeatability, response validity, and latency saved determine whether caching is worthwhile.

^tbl-edge-cache-hit-rates

Semantic caching[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.21 Footnotes#^fn8|⁸]] (caching based on embedding similarity rather than exact match) can improve hit rates for open-ended workloads. Any cache miss still requires full model execution, raising the question of whether a large model can be split across regions or must run inside a single data center.

### Cross-Region Model Sharding

^sec-inference-scale-pattern-3-cross-region-model-sharding-7a2f

Splitting a single model replica across data centers puts wide-area network latency directly on the request’s execution path: when pipeline stages reside in separate regions, every stage crossing pays a 75–150 ms inter-region transfer against only 1–5 ms of local stage computation. That illustrative gap can slow inference by 10–100$\times$, though the exact penalty depends on the model’s stage layout. Such placement needs a reason strong enough to justify that cost, such as unavailable colocated capacity, and must be evaluated against the actual stage layout and deadline. Because cross-region sharding is so costly on the steady-state path, most production designs keep inference co-located and use other regions for resilience. The cross-region question therefore shifts from splitting one request across regions to deciding how quickly traffic can move when a region fails.

### Cross-Region Failover

^sec-inference-scale-crossregion-failover-0d67

When a region becomes unavailable, failover must choose a healthy destination permitted to process the request and able to absorb its work. A simplified fallback tries the nearest eligible region first and, on timeout or rejection, the next one ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^lst-active-failover|listing 3]]). A production policy must also preserve the request’s remaining deadline, version requirements, and data-placement constraints when selecting the secondary region.

``` python
# Eligibility includes placement, version, readiness, and capacity.
def route_request(user_region, request):
    attempted = set()
    for attempt_budget in (2.0, 5.0):
        remaining = request.deadline - monotonic_time()
        regions = eligible_regions(request, excluding=attempted)
        if remaining <= 0 or not regions:
            break
        region = nearest_region(user_region, regions)
        attempted.add(region)
        try:
            # The endpoint atomically admits work and enforces the deadline.
            return call_region(region, request,
                               timeout=min(attempt_budget, remaining))
        except (Timeout, RegionUnavailable, AdmissionRejected):
            # Cancel abandoned work; retries require replay-safe semantics.
            cancel_attempt(region, request)
    return unavailable_or_deadline_exceeded(request)
```

Listing 3: **Active-Active Failover**: A bounded retry policy selects eligible regions and limits each attempt to the remaining request deadline.

^lst-active-failover

Rerouting is only part of regional failover. The destination needs accessible, authoritative conversation history to reconstruct lost KV state and enough headroom for both reconstruction and continuing traffic. If the required history is unavailable or cannot be processed there under the placement policy, a healthy replica alone cannot restore the session.

↩︎ Regional headroom, session rebuilding, and the gradual return of traffic to a recovered region are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.12 Serving Fault Tolerance#^sec-fault-tolerance-reliability-reliability-replication-strategies-aaa2|Replication strategies]]**.

### Cost Optimization Across Regions

^sec-inference-scale-cost-optimization-across-regions-c1c2

Running every batch job and latency-tolerant query in the primary interactive region overpays whenever another compliant region has cheaper spot or off-peak GPU capacity. Because GPU pricing varies by provider, contract, region, and time, [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^tbl-gpu-region-pricing|table 25]] uses a hypothetical price snapshot to show how placement can balance cost against latency requirements; it must not be used for procurement.

| **Region**  | **H100 spot price** | **On-demand** | **Latency to US users** |
|:------------|:-------------------:|:-------------:|:-----------------------:|
| **US-East** |      \$2.50/hr      |   \$4.00/hr   |        10–50 ms         |
| **US-West** |      \$2.30/hr      |   \$3.80/hr   |        30–70 ms         |
| **EU-West** |      \$2.80/hr      |   \$4.20/hr   |        75–100 ms        |

Table 25: **Hypothetical Regional Price and Latency Snapshot**: Scenario prices and RTTs illustrate a placement calculation. Both inputs are time- and provider-specific; a deployment must refresh them from its contract and measured network paths before making a routing decision.

^tbl-gpu-region-pricing

Cost-aware routing compares eligible regions for latency-tolerant work ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.15 Global Inference Infrastructure#^lst-cost-aware-routing|listing 4]]). GPU price alone is insufficient: transfer charges, startup and idle capacity, retries, and achieved useful throughput determine the cost of completing the workload. Deadline and data-placement constraints must filter destinations before that comparison.

``` python
def route_batch_request(request):
    # Filter by placement, version, readiness, capacity, and deadline.
    regions = eligible_regions(request)
    if not regions:
        return no_feasible_destination(request)
    if request.priority == "low":
        return lowest_completion_cost_region(request, regions)
    return nearest_region(request.user_location, regions)
```

Listing 4: **Cost-Aware Routing**: The router filters eligible destinations before comparing completion cost for low-priority work or proximity for interactive work.

^lst-cost-aware-routing

Time-of-day routing can reduce batch cost when regional price differences exceed data-transfer and coordination costs. Savings require a workload-specific calculation, and interactive traffic must retain its own latency budget. Regional placement completes the serving hierarchy, from one request’s batch slot to a fleet that spans continents. The design cases that follow show how these techniques combine when a service must meet specific cost and latency targets.
