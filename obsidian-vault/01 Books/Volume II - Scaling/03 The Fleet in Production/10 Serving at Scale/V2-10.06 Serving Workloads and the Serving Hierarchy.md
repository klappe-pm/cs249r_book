# V2-10.06 Serving Workloads and the Serving Hierarchy

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-serving-hierarchy-fe8c

An optimization tuned for one model family or one layer of the stack can miss the active bottleneck when applied to another. Paging a key-value cache does nothing for an embedding-heavy recommendation model, and fusing a GPU kernel cannot rescue a service whose requests stall in a load balancer. Controlling serving cost therefore requires separating the workload mix from the system layer that owns each bottleneck.

### Inference Beyond LLMs

^sec-inference-scale-inference-landscape-beyond-llms-9560

Designing a serving platform around autoregressive token generation alone leaves a fleet unprepared for the workloads that dominate consumer request volume. In large consumer platforms, recommendation and ranking workloads can consume the majority of AI inference cycles and capacity ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-gupta2020architectural|Gupta et al. 2020]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-hazelwood2018|Hazelwood et al. 2018]]), stalling on terabyte-scale sparse embedding lookups under sub-10 ms deadlines rather than sequential weight reads. Vision and image processing, NLP and LLM workloads, fraud detection, ads, and other classification tasks create additional serving demands. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.06 Serving Workloads and the Serving Hierarchy#^tbl-inference-landscape|Table 4]] compares representative pressures: sparse lookup for recommendation, batch efficiency for fixed-shape vision, weight and cache traffic for LLM decode, and incremental deadlines for speech. These are starting points for diagnosis; the active bottleneck still depends on the model, input shape, and deployment.

Request volume must be derived from application behavior. In a recommendation service, a page load, scroll, or click can trigger ranking or retrieval, so one browsing session can produce many inference requests. A language-model application may likewise issue several model calls for one user action or run background tasks without an explicit query. Capacity planning therefore counts the model work triggered by each interaction rather than treating user count as request rate.

Workload structure also determines which techniques can help. Embedding sharding and lookup locality address large recommendation models ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-naumov2019deep|Naumov et al. 2019]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-gupta2020architectural|Gupta et al. 2020]]), and feature store architectures must deliver the inputs a model expects within its latency budget, while continuous batching and KV cache management address variable-length autoregressive work. Text-to-image systems such as DALL-E add multimodal serving demands ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-ramesh2021zero|Ramesh et al. 2021]]) whose volume and latency targets remain product-specific.

| **Model type**               |       **Serving pressure**        | **Latency target**  |    **Key challenge**     |
|:-----------------------------|:---------------------------------:|:-------------------:|:------------------------:|
| **Recommendation/ranking**   | High volume in consumer platforms | $<10\text{ ms}$ p99 |     Embedding lookup     |
| **Vision (CNN)**             |        Workload-dependent         |      20–100 ms      |     Batch efficiency     |
| **LLM**                      |       High cost per request       |     100 ms–10s      |     Memory bandwidth     |
| **Speech/Audio**             |           Stream-driven           |      Real-time      |    Sequential decode     |
| **Multimodal/text-to-image** |   Emerging and product-specific   |       Varies        | Cross-modal coordination |

Table 4: **Production Inference Landscape**: Different model types create different serving pressure, latency requirements, and optimization challenges. The table is a qualitative workload map rather than a universal traffic-share distribution. Technique selection must match the specific workload.

### The Serving Hierarchy

^sec-inference-scale-serving-hierarchy-levels

Tuning a replica’s kernels or cache allocator cannot fix tail latency when requests are waiting inside a router or starving behind a noisy neighbor on a shared cluster. To locate the right control, serving optimizations organize into a four-level serving hierarchy ordered by scope, where each level owns a distinct bottleneck and measurement boundary. The request level follows one request through preprocessing, batch-formation waiting, response caching, and model execution, where the target is the latency a user sees. The replica level looks inside one model instance, where utilization, KV-cache memory management, and kernel efficiency set the throughput it can deliver before it saturates. The service level turns many replicas of the same model into aggregate capacity through load balancing, request routing, and autoscaling. The platform level decides, across services and tenants, whether a shared serving fleet stays efficient without allowing one workload to degrade another.

Each level supplies a different measurement boundary. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.06 Serving Workloads and the Serving Hierarchy#^tbl-serving-hierarchy|Table 5]] associates request latency, replica throughput, aggregate service capacity, and cross-tenant efficiency with the controls most directly responsible for them. Their effects still cross boundaries: batching can increase replica throughput while adding request delay, and replica placement can change both communication cost and service capacity. The hierarchy helps locate the decision without treating its metric in isolation. In C³ terms, batching and cache management improve compute reuse, sharding introduces communication, and routing, isolation, and autoscaling coordinate the resources that make those gains usable.

| **Level**    | **Optimization target** | **Key techniques**                   |
|:-------------|:-----------------------:|:-------------------------------------|
| **Request**  |   Per-request latency   | Dynamic batching, response caching   |
| **Replica**  | Throughput, utilization | KV-cache paging, kernel fusion       |
| **Service**  |   Aggregate capacity    | Load balancing, routing, autoscaling |
| **Platform** |   Resource efficiency   | Multi-tenancy, scheduling, placement |

Table 5: **Serving Hierarchy Optimization Targets**: Each level of the serving hierarchy targets distinct performance metrics, from per-request latency at the request tier to aggregate resource efficiency at the platform tier.

^tbl-serving-hierarchy

**Checkpoint 10.2: The serving hierarchy**

Verify your understanding of where specific optimizations sit within the serving hierarchy:

**Replica level**: identify the hierarchy level at which KV-cache paging reduces GPU memory waste, and explain why that raises concurrent request capacity rather than single-request latency.

**Caching level**: distinguish response caching, which shortens one request’s path, from KV-cache paging, which raises a replica’s capacity, and place each in the hierarchy.

**Load balancing**: identify why load balancing belongs at the service level and explain how its choice of replica can affect both aggregate goodput and a request’s queueing delay.

**Isolation level**: evaluate the claim that multi-tenancy and resource isolation are primarily request-level concerns.

The serving decisions that follow climb the hierarchy from the request level to the platform level. Batching sets how long each request waits to share execution. KV-cache layout, decode-time policies, and adapter state decide how many requests a replica can hold. The split between prefill and decode decides whether a new prompt and the streams already decoding share a worker or separate pools. Weight quantization and model sharding change the replica’s memory and compute budget. Routing, isolation, autoscaling, and global placement then turn replicas into a service and a platform. Precision enters every capacity calculation that follows through two separate budgets: reducing weight precision frees resident memory, whereas reducing KV precision lowers the memory required per active sequence. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.10 Weight Quantization for Serving#^sec-inference-scale-weight-quantization-serving-097b|Section 10.9]] compares the serving trade-offs of these representation choices before sharding divides a replica across devices.

    3.  Service level: Managing aggregate capacity across multiple replicas via load balancing and autoscaling
    4.  Replica level: Reducing client-side network RTT via edge caching and CDN routing
