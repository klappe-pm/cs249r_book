# V2-10.02 Inference Cost and Serving Architecture

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-scaling-inference-beyond-single-machines-54e6

A language model that costs millions of dollars to train over two months can, once deployed to a global user base at thousands of queries per second, consume a comparable sum in inference compute within weeks. Inference is then no longer a temporary batch job. It is a continuous, latency-sensitive service.

Running that continuous service takes more than an efficient steady-state replica. Fleet efficiency characterizes a replica by three quantities, each averaged over windows of hours to weeks. The first is model bandwidth utilization (MBU), which measures how close the replica’s decode steps come to the bandwidth floor, the time needed to stream each step’s weight and KV-cache bytes at peak memory bandwidth. The second is how long the replica takes to become ready. The third is the fraction of the time the replica holds its accelerators that it spends doing useful work at the ideal rate the bandwidth floor sets, which combines the runtime and program factors of ML goodput. Serving policy determines how that capacity is shared when requests arrive unevenly and each carries a latency target. A faster decode step supplies a better service rate, but it does not determine how long requests wait to join a batch, which replica receives them, which requests receive scarce cache space, or when the fleet needs another replica. These decisions connect the local execution toolkit to user-visible performance under load.

↩︎ The serving replica’s program and runtime goodput, its bandwidth floor, and the fusion, graph replay, and compilation levers that shape it are established in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09 Fleet Efficiency#^sec-performance-engineering|Fleet Efficiency]]**.

The service contract makes that distinction measurable. Offered load is the work arriving at the endpoint, including requests the service may reject; admitted load is the work it accepts. A service-level objective (SLO) specifies the required outcome over a measurement window, such as a latency percentile or successful-request fraction. For language models, request rate alone is insufficient because prompt and output lengths determine different amounts of work. Capacity comparisons must therefore hold the request mix and SLO fixed while measuring how much offered work completes successfully within the targets.

An admitted request passes through routing, preprocessing, queueing, batch formation, model execution, and response delivery, crossing between the host CPU and the accelerator twice on the way ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.02 Inference Cost and Serving Architecture#^fig-inference-lifecycle|figure 1]]). The host manages admission, tokenization, and detokenization, while the GPU executes the prompt prefill pass and iterative KV-cache decode loop. The figure maps noncompute serving overhead against the time-to-first-token (TTFT) and time-per-output-token (TPOT, the average gap between streamed tokens) latency budgets. For an autoregressive model, prefill processes the prompt and builds cached attention keys and values; decode extends that KV cache as it generates subsequent tokens. Waiting before prefill delays the first token, while competition during decode delays the stream. The scheduler must budget both delays alongside execution time. Batching and cache management govern work within a replica, sharding changes the replica’s capacity, and routing and autoscaling distribute demand across replicas.

↩︎ Prefill’s arithmetic-bound regime and decode’s bandwidth floor, measured as MBU, are established in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.03 ML Goodput#^sec-performance-engineering-fleet-efficiency-metric-dff4|Program goodput and its measure]]**.

Figure 1: **End-to-End Inference Pipeline**: One language-model request crosses between CPU and GPU twice. The load balancer routes and admits it and the CPU tokenizes it; prefill then processes the whole prompt in one pass and writes its keys and values to the KV cache, and decode reads and appends that cache one token per step before the CPU detokenizes the stream. The strip orders one request’s latency, with illustrative segment widths. Everything up to the end of prefill counts against time to first token, and the routing and CPU segments are serving-tax work that spends latency budget outside GPU compute.

^fig-inference-lifecycle

Distribution adds placement and coordination decisions to the local serving problem. Load balancing[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.21 Footnotes#^fn1|¹]] must distribute requests across replicas with different amounts of unfinished work and available memory. Request routing must also account for model-specific characteristics: recommendation systems with large sharded embedding tables require different placement strategies than language models that generate responses token by token. When demand changes faster than new replicas can become ready, routing alone cannot restore capacity. Autoscaling, spare capacity, and admission limits must work together to protect the service’s latency targets.

Training and serving place costs on different timelines. A model version’s training expense can be amortized over its deployment, while serving capacity must follow recurring demand. An e-commerce recommendation service, for example, must accommodate peak shopping traffic without paying for an unnecessarily large idle fleet during quiet periods. Both training efficiency and serving efficiency matter, but the serving decision must also account for when requests arrive and how long they can wait. Building such a service requires three linked decisions: when distribution becomes necessary, how the architecture meets latency targets under varying load, and how resource utilization stays high enough that serving cost does not erode the value the model creates. The worked scenarios that follow size these decisions using registry values for real hardware and models alongside labeled scenario assumptions for traffic, prices, and latency budgets, starting with the physical limits that force a service beyond a single machine.

**Self-Check: Question**

1.  True or False: A service that meets its latency SLO on every admitted request is serving all of its offered load.

2.  Configuration X reports 900 requests per second on a benchmark of short prompts, and configuration Y reports 700 requests per second on the production prompt and output mix, both at the same TTFT and TPOT targets. Which conclusion is justified?

    1.  X has more capacity, because request rate is the capacity metric for a serving system.
    2.  Neither can be ranked yet, because prompt and output lengths change the work per request, so capacity must be compared at the same request mix and SLO by counting offered work that completes within the targets.
    3.  Y has more capacity, because production traffic always contains longer requests than a benchmark.
    4.  The two are equivalent, because both meet the same latency targets.

3.  In a streaming language-model service, explain which latency budget is consumed by waiting before prefill and which by contention during decode, and why a faster decode kernel alone cannot settle either problem.
