# V2-10.21 Footnotes

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^footnotes

<sup>1</sup> **Load balancing for inference**: Request service times can span milliseconds to tens of seconds as models, prompt lengths, and generated outputs vary. Queue-aware routing exposes that remaining work more directly than assignment counts alone.

^fn1

<sup>2</sup> **HBM3 capacity and bandwidth**: The H100 combines 80 GB of 3D-stacked DRAM with 3.35 TB/s of bandwidth, compared with 2.04 TB/s for HBM2e on the A100. Capacity determines whether model and cache state fit; bandwidth bounds memory-bound decode throughput.

^fn2

<sup>3</sup> **DLRM (Deep Learning Recommendation Model)**: Meta’s 2019 reference architecture combines dense features processed by multilayer perceptrons (MLPs) with sparse features represented by embedding lookups ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-naumov2019deep|Naumov et al. 2019]]). This separation permits different placement strategies; it does not require embeddings on CPUs and MLPs on GPUs. Production recommendation characterizations show why this structure matters for serving: embedding-heavy recommendation models create memory-access and capacity constraints that differ from dense convolutional neural network (CNN), recurrent neural network (RNN), or large language model (LLM) inference ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-gupta2020architectural|Gupta et al. 2020]]).

^fn3

<sup>4</sup> **Little’s law**: The identity holds for any stable system regardless of the arrival or service distribution, which is why it survives the bursty, variable-length traffic of inference. Because it relates averages, it bounds neither maximum service capacity nor tail latency.

^fn4

<sup>5</sup> **MoE (mixture-of-experts) serving trade-off**: Only a subset of experts activates per token (2 of 8 in Mixtral, 8 of 256 routed experts in DeepSeek-V3). Keeping all weights accelerator-resident gives a total-to-active weight ratio of roughly 3.6× (Mixtral) to 18× (DeepSeek-V3). Expert parallelism distributes that storage while adding token-routing communication; offloading is an alternative that trades resident capacity for weight transfers.

^fn5

<sup>6</sup> **Consistent hashing**: The ring-based algorithm was introduced for distributed caching ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-karger1997|Karger et al. 1997]]) and then used in large-scale content delivery. Its limited-remapping property made it useful wherever membership changes should preserve cache locality.

^fn6

<sup>7</sup> **Bulkhead limits**: A divider isolates failure only if it closes the relevant boundary. The Titanic’s incomplete bulkheads allowed water to cascade between compartments; similarly, a soft quota cannot isolate shared memory or bandwidth that remains globally exhaustible.

^fn7

<sup>8</sup> **Semantic caching**: A similarity lookup can reuse responses beyond exact string matches, but it adds retrieval work and can return an invalid answer when superficially similar queries require different responses. The similarity threshold therefore trades cache coverage against correctness.

^fn8

<sup>9</sup> **Two-tower architecture**: Encodes user features and item features through separate neural networks (“towers”) into embeddings, then scores via dot product. Its serving advantage is that item embeddings can be precomputed offline and cached, reducing online candidate generation to the user tower forward pass and vector similarity search. Search latency depends on index size, placement, and the required recall. The trade-off is reduced model expressiveness from late interaction, since the towers cannot attend to each other’s features during encoding.

^fn9
