# V2-10.03 Limits of Single-Machine Serving

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-singlemachine-serving-insufficient-3f13

A single accelerator fails a production endpoint in three ways: its memory fills before the model weights or caches fit, its throughput saturates below the arriving query rate, or its forward pass runs longer than a request’s latency budget. Overcoming those limits requires distributing work across several devices within one machine or across machines over the network. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.03 Limits of Single-Machine Serving#^tbl-distribution-triggers|Table 1]] categorizes these three triggers and their matching distribution strategies, whose necessity depends on the permitted precision, placement, and service contract.

The first signal is memory exhaustion, which occurs when model parameters, key-value caches, or embedding tables exceed single-device capacity. A single NVIDIA H100 GPU provides 80 GB of HBM3[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.21 Footnotes#^fn2|²]] memory, whereas an illustrative mixture-of-experts model with ~1.8T parameters requires ~3.5 TB for FP16 weights alone. Keeping all those weights resident on accelerators requires multiple devices regardless of request volume; quantization and offloading change that placement constraint. Recommendation systems with trillion-parameter embedding tables face similar constraints. Meta’s DLRM architecture[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.21 Footnotes#^fn3|³]] stores embedding tables that require multiple terabytes of memory (**[[05 Reference/Volume II - Scaling/V2 System Assumptions#^sec-appdx-fleet-assumption-provenance|Assumption Provenance]]** records the provenance of the hardware and model constants used throughout this chapter).

Beyond memory constraints, throughput limitations emerge when request volume exceeds single-machine capacity even with optimal batching. Consider a recommendation system serving 100,000 queries per second with a 10 ms latency budget. If single-machine throughput peaks at 10,000 QPS, no amount of optimization on that machine can satisfy demand. Horizontal scaling across multiple replicas becomes mandatory.

Finally, latency requirements can motivate distribution even when memory is sufficient. The FP16 weights of a 70-billion parameter model, approximately 140 GB, exceed a single 80 GB H100-class GPU before KV cache is considered, but quantizing the weights to fewer bits or choosing larger-memory hardware can fit the model on one device. Even when the model fits, that device’s execution time may still exceed the request budget. Sharding the model across multiple GPUs can divide computation and weight traffic, but it adds communication and synchronization. Because sharding shortens compute-bound prefill and bandwidth-bound decode by different amounts, the latency benefit must be measured for each phase against its own target.

| **Constraint** |  **Single-machine limit**   |      **Example workload**       |  **Distribution strategy**  |
|:---------------|:---------------------------:|:-------------------------------:|:---------------------------:|
| **Memory**     |        80 GB (H100)         | Illustrative MoE (~3.5 TB FP16) | Tensor/pipeline parallelism |
| **Throughput** |      ~10K QPS (vision)      |         100K QPS RecSys         |   Horizontal replication    |
| **Latency**    | Forward pass $> \text{SLO}$ |         500 ms LLM TTFT         |       Model sharding        |

Table 1: **Triggers for Distributed Inference**: Each constraint type indicates different distribution strategies. Memory constraints require model sharding; throughput constraints require replication; latency constraints may require either depending on whether the bottleneck is compute or memory bandwidth.

^tbl-distribution-triggers

Memory, throughput, and latency triggers all become user-visible once an interactive endpoint starts streaming. TTFT determines when the user sees a response begin, while TPOT determines whether the rest of the response arrives at a readable pace. TPOT is the average of the time between tokens (TBT), the gap between successive streamed tokens, which many serving systems report as inter-token latency (ITL). A stream can meet its TPOT target while a single long TBT gap still stalls the reader, so average cadence is stated here as TPOT and per-gap tail targets as TBT. Protecting both first-token delay and stream cadence is why inference reverses many of the optimization priorities from training.

**Checkpoint 10.1: Distribution strategy selection**

Verify your understanding of when to move from single-machine to distributed inference:

**Shard vs. replicate**: for a 13B model (26 GB weights) that fits on a single A100, select model sharding or horizontal replication when throughput requirements double.

**Latency floor**: for a real-time speech-to-text service where TBT is the primary bottleneck, determine whether data-parallel replication reduces this latency.

**Mandatory sharding**: explain why a 175B model requires multiple 80 GB GPUs when all FP16 weights must remain accelerator-resident, regardless of request volume.

**Latency trigger**: identify when a latency target forces distribution and when added network, serialization, coordination, or queuing overhead can erase the benefit.

**Self-Check: Question**

1.  A recommendation service must answer 100,000 queries per second within 10 ms. Its model fits comfortably on one machine, which peaks at 10,000 queries per second with optimal batching. Which strategy addresses the binding constraint?

    1.  Shard the model with tensor parallelism across machines, because sharding is the general remedy whenever one machine is insufficient.
    2.  Quantize the weights so a single machine runs ten times faster.
    3.  Replicate the full model across at least ten machines and route requests among them, because the binding constraint is throughput rather than memory or per-request latency.
    4.  Raise the batch size on one machine until it reaches 100,000 queries per second.

2.  A 70B-parameter model needs roughly 140 GB of FP16 weights, more than one 80 GB accelerator holds, and quantization can make it fit on one device. Explain why the team might still shard it, and how they should decide.

3.  True or False: A stream that meets its TPOT target cannot stall the reader, because TPOT bounds the gap between successive tokens.
