# V2-10.07 Batching Strategies at Scale

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-batching-strategies-scale-6733

A stream of hundreds of disparate chat requests arrives at an inference server every second. Processing them one by one leaves much of the GPU idle, starved for work between small decode steps. Waiting to gather a large static batch forces the first request in line to endure unacceptable latency. Batching at scale therefore needs policies that group requests as they arrive without violating tail-latency deadlines.

Processing multiple requests together shares weight reads and kernel launch overhead across more useful work. The resulting service-rate gain can reduce queueing, but waiting to form a batch adds delay; the net effect on request latency depends on load. Single-machine serving applies this insight through dynamic batching, which collects requests within a time window before processing them together.

At scale, batching must also account for workload structure. A policy suited to uniform vision inputs can leave slots unused during variable-length generation, while grouping sparse embedding lookups solves a different problem from batching dense execution. The unit of reusable work determines which policy is worth evaluating. The strategies below proceed in order of mechanism rather than traffic share: vision (request batching), LLMs (iteration-level batching with KV state), and recommendation (feature-parallel batching over distributed embeddings), even though recommendation often dominates consumer inference volume ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.06 Serving Workloads and the Serving Hierarchy#^sec-inference-scale-inference-landscape-beyond-llms-9560|section 10.5.1]]).

### Batching Across Model Architectures

^sec-inference-scale-batching-differs-across-model-types-2026

Holding arriving requests until a fixed batch fills forces early arrivals to wait and pads shorter inputs with wasted work, whereas running every request immediately leaves later arrivals queued behind one-request passes that underuse the GPU. Batching efficiency depends on how computation scales with batch size relative to memory and communication constraints, and the execution timeline in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^fig-batching-strategies|figure 4]] separates waiting to form a batch from waiting for the accelerator to become available. Unbatched serving adds no batch-formation delay, but later requests can still queue behind earlier forward passes. Static batching consolidates all four illustrated requests into one pass, adding formation delay and padding to accommodate different input lengths. Dynamic batching closes formation windows at fixed time intervals (${\Delta} {t}$), producing two passes with two requests each in this example. The window limits intentional formation delay; it does not bound total queueing when ready batches arrive faster than the server can execute them.

![[90 Assets/Volume II/10 Inference/Batching Strategies 32ff00a1f3.svg]]

Figure 4: **Batching Strategies Compared**: Four requests of different lengths arrive one time unit apart under three policies; the timings are illustrative. (a) Without batching, each request receives its own forward pass, so later arrivals queue behind earlier ones and the GPU runs four passes. (b) Static batching holds every request until the batch of four is full, then runs one pass padded to the longest request; early arrivals pay the longest wait. (c) Dynamic batching dispatches whatever has arrived when a short window closes, limiting intentional formation delay in this timeline while sharing each pass between two requests. Waiting for an occupied worker remains a separate source of delay.

^fig-batching-strategies

In vision models processing fixed-size images, arithmetic work grows roughly in proportion to batch size while requests share the weights, so larger batches improve weight reuse until compute, memory, or the latency budget binds. The largest feasible batch is not necessarily the best interactive operating point. By contrast, in LLMs during the decode phase, small batches perform little computation per byte of active weights loaded, so memory bandwidth binds. Larger batches raise arithmetic intensity until compute, KV-cache traffic, or the latency budget limits further gains. Small-batch decode therefore does not inherit a new accelerator generation’s headline compute improvement. From Volta to Blackwell, peak compute climbs 18× while memory bandwidth expands by only 8.9×, and [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^fig-gpu-memory-wall|figure 5]] shows generation throughput tracking the slower curve whenever weight streaming dominates at small batch sizes.

↩︎ The accelerator trajectory behind this divergence, with compute outpacing memory bandwidth from one generation to the next, is established in **[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.03 The Accelerator#^sec-compute-infrastructure-evolution-gpu-architectures-566b|Evolution of GPU architectures]]**.

Recommendation systems shift the bottleneck again: sparse embedding lookup can limit throughput before dense computation does. Grouping sparse accesses improves locality and distributes lookup work across shards, while batching the dense stages improves matrix multiplication throughput. The serving policy must therefore account for both stages and the communication between them rather than infer the bottleneck from the model category alone.

Figure 5: **Decode Inherits the Bandwidth Deficit**: Peak compute and memory bandwidth for four accelerator generations, normalized to the V100. Compute rises 18× against bandwidth’s 8.9×. In weight-bandwidth-bound decode, each iteration loads the active weights and reuses them across its output tokens; at fixed batch size, bandwidth growth constrains the gain. ### Batching Physics and Efficiency Curves

^sec-inference-scale-physics-batching-efficiency-curve-021c

Raising batch size to maximize a replica’s throughput stretches each batch’s execution time and holds arriving requests in a formation queue until the service violates its latency SLO. Batch size is the single-replica control knob that moves a workload along the roofline by reusing each weight read across more requests, which raises arithmetic intensity. At fleet scale, the same knob also sets how long arriving work waits and how much request state the replica must hold. A model relating batch size $({B})$, batch service time $({T_{\text{svc}}}({B}))$, and batched service rate $({\mu_{\text{eff}}}({B}))$ exposes that trade-off; selecting an operating point also requires the arrival pattern, memory budget, and latency target.

↪ The roofline bound, and why batch-one decode sits far below the ridge point, are collected for reference in **[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^sec-appdx-dam-taxonomy-roofline|The roofline bound]]**.

The first model isolates batch execution. Here ${T_{\text{svc}}}({B})$ is the service time once a batch begins execution; it excludes queueing and batch formation. Keeping the measurement boundary explicit prevents an execution-time improvement from being mistaken for an end-to-end SLO guarantee.

The service-time equation decomposes batch execution time into fixed overheads (kernel launch, memory loading) and variable costs (compute per sample):

$$
{T_{\text{svc}}}({B}) = {T_{\text{fixed}}}+ {B}\times {t_{\text{req}}}
$$

In this formulation, ${T_{\text{fixed}}}$ captures costs paid once per batch, such as loading weights from high-bandwidth memory (HBM) and kernel launch latency, while ${t_{\text{req}}}$ denotes the marginal cost of adding one request, such as the compute time for that sample. Treating these terms as constants is a local approximation for a fixed workload and execution regime. Kernel changes, cache traffic, and resource saturation can alter the measured curve as batch size grows.

The throughput equation describes the system’s capacity:

$$
{\mu_{\text{eff}}}({B}) = \frac{{B}}{{T_{\text{svc}}}({B})} = \frac{{B}}{{T_{\text{fixed}}}+ {B}\times {t_{\text{req}}}}
$$

The resulting batching efficiency curve shows diminishing returns from amortizing overhead. For small batch sizes (${B}$), ${T_{\text{fixed}}}$ dominates service time, so increasing ${B}$ shares that cost and raises throughput substantially. As ${B}$ grows, the relative contribution of ${T_{\text{fixed}}}$ shrinks and the model approaches its asymptotic rate $1/{t_{\text{req}}}$. This limit alone does not identify whether compute or bandwidth binds on the actual device. The knee of the curve, where fixed and variable costs become comparable, is a useful candidate operating point. It is not an optimum independent of the service contract; a tight latency budget may require a smaller batch, while a throughput-oriented workload may benefit from a larger one.

![[90 Assets/Volume II/10 Inference/Inference Batching Knee ae7aa4e514.svg]]

*Throughput on the vertical axis against batch size on the horizontal axis. The curve rises steeply and then keeps climbing ever more slowly toward a dashed asymptote labeled 1 over t sub req. A ring marks the knee, where throughput reaches half the asymptote.*

*Throughput saturates toward $1/{t_{\text{req}}}$; past the knee, each larger batch buys less.*

The execution-only feasibility condition is ${T_{\text{svc}}}({B}) \le \text{SLO}$. In a live service, execution receives only the budget remaining after routing, queueing, batch formation, and response delivery. The batch-size decision must therefore use that remaining budget rather than consume the full SLO. Comparing a vision workload with a relatively high ${t_{\text{req}}}$ against an LLM decode workload with a high ${T_{\text{fixed}}}$ from weight loading shows how those measured costs shift the efficiency knee (notebook [10.2](https://mlsysbook.ai/vol2/10_inference/10_inference.html#nbk-inference-batching-efficiency-curve)).

**Napkin Math 10.2: The batching efficiency curve**

**Problem**: An engineer optimizes two services: a vision model (ResNet) and an LLM (70B). At what batch size does each hit the “knee” of its efficiency curve?

**Math**: The knee occurs where the variable compute cost $({B}\times {t_{\text{req}}})$ starts to exceed the fixed overhead $({T_{\text{fixed}}})$.

1.  **Vision Model** $({T_{\text{fixed}}}= 2\text{ ms}, {t_{\text{req}}}= 1\text{ ms})$:
    - Knee: ${B}\approx 2\text{ ms}/1\text{ ms} =$ 2.
    - **Result**: This simplified latency model reaches its first overhead-amortization knee at a small batch. It does not locate hardware saturation; measuring throughput at larger batches tests whether additional concurrency still helps.
2.  **LLM Decode** $({T_{\text{fixed}}}= 40\text{ ms}, {t_{\text{req}}}= 0.5\text{ ms})$:
    - Knee: ${B}\approx 40\text{ ms}/0.5\text{ ms} =$ 80.
    - **Result**: The larger fixed cost in this decode example moves the overhead-amortization knee to a larger batch.
    - **Where 0.5 ms comes from**: It is an assumed marginal cost per added sequence, dominated by reading that sequence’s own KV state at a moderate context length. Unlike the weight stream, that read is private to each sequence, so it grows with batch size instead of being shared.
    - **Where 40 ms comes from**: It is roughly the time to stream the model’s 140 GB of FP16 weights through one H100’s 3.35 TB/s of HBM bandwidth, the aggregate weight traffic of one decode step expressed in single-device time. No single H100 holds those weights. The reference replica of **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.02 Where Fleet Capacity Goes#^sec-performance-engineering-memory-wall|Where Fleet Capacity Goes]]** spreads them over eight GPUs, which divides both ${T_{\text{fixed}}}$ and ${t_{\text{req}}}$ by the tensor-parallel degree and leaves their ratio, and therefore the knee, unchanged.

**Systems insight**: Because streaming the weights is the dominant per-step cost of decode, the system has not reached the efficiency knee until batch size 80. The knee depends on the ratio of fixed to per-request cost, not on how many devices share them, which is why sharing weight reads across concurrent requests matters at every replica size. The batch a service actually runs also depends on context length, cache capacity, kernel efficiency, and the latency target; continuous batching and paged allocation are the mechanisms that let a replica reach it.

While the analytical batching model locates the knee from each model class’s ratio of fixed to per-request cost ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^tbl-batching-by-model|table 9]]), production serving stacks measure the resulting throughput-latency frontier directly. The open InferenceX benchmark serves DeepSeek-R1, a mixture-of-experts reasoning model, with 1,024-token prompts and 1,024-token responses on each accelerator across many combinations of serving framework, parallelism, and concurrency ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-semianalysis2026inferencex|SemiAnalysis 2026]]). For every configuration it records the output tokens per second each user receives, called interactivity (the reciprocal of TPOT), and the output tokens per second each GPU delivers across all users. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^fig-throughput-interactivity|Figure 6]] plots 325 such configurations at FP8 precision and traces, for each accelerator, the frontier of configurations that no other configuration beats on both rates. Every frontier falls as interactivity rises, because a faster stream per user permits fewer concurrent sequences per decode step. The best B200 configuration delivers about 6,300 output tokens per second per GPU when each user receives about 13 tokens per second. It delivers about 210 when each user must receive at least 100, a 30× difference in per-GPU output paid for faster streams. The interactivity target alone moves per-GPU output by that much, so it must be fixed before any two throughput figures can be compared.

The same frontiers separate hardware generations by more than their datasheets do. At 50 tokens per second per user, the best measured H100 configuration delivers about 80 output tokens per second per GPU and the best GB200 NVL72 configuration about 3,650, a 44× difference. Yet the peak dense FP8 rate of a GB200 GPU is only about 2.3× that of an H100. The benchmark does not apportion the gap, but the candidates lie mostly beyond peak arithmetic, in memory bandwidth and capacity per GPU, a 72-GPU NVLink domain that keeps experts and KV state off slower networks, and platform-tuned serving software. A throughput figure quoted without its latency target therefore says little about either system.

Translating the batch-level equations into system-wide capacity planning requires Little’s law,[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.21 Footnotes#^fn4|⁴]] a classical result from queuing theory that relates concurrency, throughput, and latency in any stable system. Whereas ${T_{\text{svc}}}({B})$ prices one replica’s execution batch, Little’s law connects the external arrival rate and mean request time in system to the total number of requests concurrently in flight across the fleet.

↩︎ The M/G/1 waiting-time model, in which utilization and service-time variability multiply queueing delay, is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.04 Scheduling Objectives and Their Conflicts#^sec-fleet-orchestration-objectives|Scheduling Objectives and Their Conflicts]]**.

**Theorem 10.1: Little's law for inference**

**Concept**: In any stable queuing system, the average number of requests in the system $({Q_{\text{req}}})$ equals the arrival rate $({\lambda_{\text{arr}}})$ multiplied by the average time a request spends in the system $({T_{\text{lat}}})$.

$$
{Q_{\text{req}}} = {\lambda_{\text{arr}}} \cdot {T_{\text{lat}}}
$$

**Application**: Concurrency planning. This idealized service counts only batch formation, queueing, and execution in its end-to-end latency; routing and response delivery add no delay. Assume the mean latency given below and full execution batches of the stated size. A percentile SLO cannot generally be substituted for the mean in Little’s law.

- **Target Throughput** $({\lambda_{\text{arr}}})$: 1,000 requests/sec
- **Assumed mean latency** $({T_{\text{lat}}})$: 100 ms (0.1 s)

**Mean in-flight work** $({Q_{\text{req}}})$: $1000 \times 0.1 =$ 100 concurrent requests

**Capacity planning**: If a single GPU replica executes batches of 8 in 80 ms, and the fleet targets at most 80 percent mean service utilization:

1.  Replica throughput $=$ $8/0.08 =$ 100 req/s
2.  Throughput-only lower bound $=$ $\lceil 1000/100\rceil =$ 10 replicas
3.  Illustrative headroom-sized replica count $=$ $\lceil 1000/(0.8 \times 100)\rceil =$ 13 replicas

**Verification**: Maximum executing positions $=$ $13\text{ replicas} \times 8\text{ batch positions} =$ 104. These positions do not include requests waiting for execution or batch formation. Under the assumed fixed batch service time, Little’s law on the execution boundary gives 80 requests executing on average; the remaining 20 of the assumed mean in-flight population are waiting or accumulating. The throughput-only lower bound would run at the stability boundary; the utilization-sized candidate runs at about 76.9 percent service utilization. The assumed mean latency still needs validation, and this arithmetic does not prove a percentile latency SLO; that requires an arrival/service model or a measured load test.

A load test can locate the stability boundary, where arrivals equal service capacity, only when its load generator keeps offering work at the stated arrival rate. The measurement contract of **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.04 Measuring Goodput#^sec-performance-engineering-measurement-contract|The measurement contract]]** guards against load that eases off while the replica stalls. A serving measurement therefore holds a fixed external arrival process rather than a fixed concurrency, because response-paced generation can reduce arrivals during a stall and make the system appear to have more headroom than it does.

↪ The mean queuing delay under a batched M/G/1 surrogate, and how utilization headroom and batch size trade against latency, is developed in **[[05 Reference/Volume II - Scaling/V2 Inference Foundations#^sec-appdx-inference-scale-queuing-theory-batched-inference-bbf0|Queuing theory for batched inference]]**.

### Static and Dynamic Batching for Vision Models

^sec-inference-scale-static-dynamic-batching-vision-models-4623

Static batching, which waits until exactly ${B}$ requests arrive before launching a forward pass, leaves early requests stranded during traffic lulls until their latency budgets expire. Vision models otherwise present the simplest batching case: preprocessed inputs share a fixed tensor shape and execute in a predictable time, so single-machine batching applies directly and fleet scale adds only the question of where batches form.

Dynamic batching collects requests for a maximum time window ${T_{\text{window}}}$ or until reaching maximum batch size ${B_{\text{max}}}$, whichever occurs first. For Poisson arrivals with rate ${\lambda_{\text{arr}}}$ (requests arriving independently of one another at that constant average rate), [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^eq-dynamic-batch-latency|equation 3]] organizes expected request latency into queueing, formation, and execution contributions:

$$
\mathbb{E}[{T_{\text{lat}}}] = \mathbb{E}[{L_{\text{lat,queue}}}] + {L_{\text{lat,form}}} + {T_{\text{svc}}}({B}) \tag{3}
$$

^eq-dynamic-batch-latency

where $\mathbb{E}[{L_{\text{lat,queue}}}]$ is the expected queuing delay, ${L_{\text{lat,form}}}$ represents mean batch formation delay (up to ${T_{\text{window}}}$), and ${T_{\text{svc}}}({B})$ represents mean inference time over the realized batch sizes ${B}$. Queueing here excludes time already counted as batch formation. The two waiting terms respond differently to load. Under Poisson arrivals the mean inter-arrival gap is $1/{\lambda_{\text{arr}}}$, so a higher arrival rate fills a batch faster and reduces formation delay. Queueing for a busy replica can nevertheless grow as arrival rate approaches service capacity; the batching timeout does not cap that queueing delay. Spending a small slice of the latency budget on batch formation can multiply per-GPU capacity while keeping end-to-end latency within target (example [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^exmp-dynamic-batching-resnet50|10.1]]).

**Example 10.1: Dynamic batching for ResNet-50**

**Scenario**: A vision classification service receives requests at 5,000 QPS with a 50 ms p99 latency SLO across 10 replicas, so each replica sees 500 QPS. One image served alone takes 5 ms. The scenario assumes that a batch of about 5 images executes in 8 ms and a batch of about 10 in 12 ms, because a batch shares weight reads and kernel launches across its images.

**Diagnosis**: Each utilization below is the per-replica arrival rate multiplied by the service time one request consumes. Option A serves every image alone, which overloads the replica (${\rho_{\text{serv}}} = {\lambda_{\text{arr}}} \times {T_{\text{svc}}} = 500 \times 0.005 = 2.5$ utilization). Option B holds a 10 ms batching window, which collects about 5 requests (arrival rate $\times$ window). Their batch runs in 8 ms, so each request consumes 1.6 ms of execution, and utilization falls to ${\rho_{\text{serv}}} = 500 \times 0.0016 = 0.8$. The wider 20 ms window of Option C collects about 10 requests whose batch runs in 12 ms, or 1.2 ms each, reaching ${\rho_{\text{serv}}} = 500 \times 0.0012 = 0.6$ and a further 33 percent of per-replica capacity. Both options leave service headroom. Whether they also meet the p99 SLO depends on the window plus the queueing delay each utilization implies under the service’s real arrival pattern, which utilization alone does not determine.

**Systems lesson**: Dynamic batching is effective when the latency budget has unused slack. The serving policy converts latency headroom into throughput, but requires careful tuning to prevent SLO violations.

^exmp-dynamic-batching-resnet50

↪ A procedure for this tuning, from fitting the service-time model to checking the p99 target, is developed in **[[05 Reference/Volume II - Scaling/V2 Inference Foundations#^sec-appdx-inference-scale-decision-framework-batch-size-selection-given-sla-8e4e|Batch size selection framework given an SLO]]**.

At scale with multiple replicas, batch formation can occur either at individual replicas or at a centralized batching layer. Replica-local batching has each replica independently form batches from its assigned traffic. This avoids a shared batching stage, but splitting a light arrival stream among many replicas can leave each waiting to fill its batch. Centralized batching pools arrivals before dispatching formed batches, potentially shortening formation waits, at the cost of an additional network hop and a shared scheduling bottleneck. Load balancing helps local batching, but equal request counts do not guarantee equal work or reproduce the formation benefit of pooling arrivals. The choice depends on arrival density, request compatibility, and replica service times.

### Continuous Batching for LLM Inference

^sec-inference-scale-continuous-batching-llm-inference-f8e6

When a request-level batch locks its membership until the longest sequence finishes, a short reply that ends after 10 tokens leaves its slot stranded for the remaining 90 steps of a 100-token neighbor. Queued requests starve while the GPU still streams the full model weights on every step. The autoregressive bottleneck (principle [[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-autoregressive-bottleneck|18]]) makes that wasted slot expensive: at small batch sizes, decode is typically bandwidth-bound because each iteration streams active model weights while generating only one token per sequence. Batching shares those weight reads across concurrent requests, and as the batch grows, compute or KV-cache traffic can become the binding constraint, so bandwidth-bound decode is an operating regime rather than a property of every serving configuration.

**Definition 10.1: Continuous batching**

***Continuous batching*** is a serving strategy that updates batch membership at iteration boundaries, allowing new requests to enter without waiting for every request in the original batch to finish.

1.  **Significance**: It reduces padding waste by refilling completed slots at iteration boundaries. Throughput gains require waiting requests, available KV-cache capacity, and scheduling overhead small enough to preserve the benefit.
2.  **Distinction**: Unlike static or dynamic batching (which group requests at the request level), continuous batching operates at the iteration level, reshaping the active batch between decode iterations.
3.  **Common pitfall**: Continuous admission must coordinate scheduling with KV-state ownership and lifetime. A paged KV-cache allocator such as PagedAttention ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-pagedattention-3c94|section 10.7.3]]) improves space utilization, but paging is not required: an implementation can recycle fixed-capacity request slots, at the cost of unused reserved space.

The Orca system ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-yu2022orca|Yu et al. 2022]]) removed the request-level barrier by updating membership at iteration boundaries to enable slot reuse. Once a request completes, another can enter if its prompt has been processed and sufficient cache capacity is available. The scheduler must account for that preparation rather than treat every replacement as a decode-only operation.

Consider a fixed-width batch of 8 sequences. If one sequence completes after 10 tokens while others require 100 tokens, its slot contributes no useful output for 90 iterations. If the kernel continues executing padded work for that slot, the fraction of wasted compute attributable to it is:

$$
\text{Wasted compute} = \frac{(100 - 10) \times 1}{100 \times 8} = 11.25\%
$$

The waste grows with the spread of output lengths, a dependence that [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^sec-inference-scale-continuous-batching-throughput-analysis-ecd2|section 10.6.5]] turns into a formula. A kernel that skips completed sequences avoids their padded arithmetic, but a fixed-membership policy still prevents waiting requests from using the vacated capacity. [Algorithm 1](https://mlsysbook.ai/vol2/10_inference/10_inference.html#algo-continuous-batching-decode-scheduler) states the continuous-batching scheduler as a decode loop with a prefilled waiting queue. In this simplified policy, completed requests release their KV-cache pages (the fixed-size blocks in which cache memory is allocated), eligible waiting requests enter freed slots, and the next kernel runs over the updated active set. For Archetype A workloads (GPT-4/Llama-3), refilling slots lets more useful tokens share each weight read. The gain comes from reusing transferred weights, not merely from saturating bandwidth, which a smaller batch may already do.

↩︎ Archetype A (GPT-4/Llama-3), the autoregressive transformer whose serving must stream billions of weights for every generated token, is established in **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.07 The Fleet Stack and the Lighthouse Archetypes#^sec-introduction-archetype-gpt4llama3-b02f|Archetype A (GPT-4/Llama-3)]]**.

$Q$

Admitting, completing, and refilling slots on every iteration lets waiting work use capacity released before the longest sequence finishes. The illustrated preemption path adds HBM-to-CPU-DRAM transfers under memory pressure, so recovered capacity must repay both scheduling and state-movement costs. Counted in slot-iterations ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^fig-continuous-batching-comparison|figure 7]]), fixed membership leaves only 20 of 32 productive, while continuous admission fills all 32 under the illustrated arrival and capacity assumptions. Prefill and decode cells do not necessarily take equal time. Slot occupancy therefore measures the opportunity; the realized throughput gain depends on how much longer the inserted prefill cells take than the decode steps they share an iteration with.

### Quantifying Continuous Batching

^sec-inference-scale-continuous-batching-throughput-analysis-ecd2

In a static batch whose output lengths vary widely, a single long response holds every completed slot idle until its final token, wasting a growing share of the batch’s sequence-iterations as length variance rises. Continuous batching recovers that stranded capacity by refilling vacated slots at iteration boundaries ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^fig-continuous-batching-comparison|figure 7]]). Counting useful and unused sequence-iterations in a fixed batch bounds the recoverable opportunity; arrivals, KV-cache admission, prefill scheduling, and scheduler overhead determine how much of that ceiling a live replica actually captures.

#### The Waste Function for Traditional Batching

^sec-inference-scale-waste-function-traditional-batching-1fb8

The 11.25 percent example of one early-finishing sequence generalizes to any mix of output lengths. For this waste model, traditional batching (also called static batching) retains a fixed batch width through all decode iterations until the longest sequence completes. How a batch forms (by count or by time window) and how its membership changes (fixed, or updated at iteration boundaries) are separate choices, so this waste model applies to any fixed-membership batch, including one formed by a dynamic batching window. Assume equal compute cost per sequence-iteration, including padded work for completed requests. For batch size ${B}$ with output lengths $\{{S}_1, {S}_2, ..., {S}_{{B}}\}$, the total compute performed under those assumptions is:

$$
{O_{\text{traditional}}}= {B}\times {S_{\text{max}}}\times {c_{\text{decode}}}
$$

where ${S_{\text{max}}}= \max_i({S}_i)$ and ${c_{\text{decode}}}$ is the compute cost per decode iteration per sequence. However, the useful compute is only:

$$
{O_{\text{useful}}} = \sum_{i=1}^{{B}} {S}_i \times {c_{\text{decode}}}
$$

[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^eq-waste-ratio|Equation 4]] defines the waste ratio that quantifies the inefficiency:

$$
{W}= 1 - \frac{{O_{\text{useful}}}}{{O_{\text{traditional}}}} = 1 - \frac{\sum_{i=1}^{{B}} {S}_i}{{B}\times {S_{\text{max}}}} = 1 - \frac{{\bar{S}}}{{S_{\text{max}}}} \tag{4}
$$

^eq-waste-ratio

where ${\bar{S}}$ is the mean output sequence length. Waste therefore depends entirely on the ratio of mean to maximum output length within the batch. For uniform output lengths $({\bar{S}}= {S_{\text{max}}})$, waste is zero. For highly variable lengths, waste can exceed 50 percent.

#### Serving Variable-Length Outputs in LLMs

^sec-inference-scale-worked-example-llm-serving-variablelength-outputs-5e38

Consider a GPT-class model serving four concurrent requests whose prompt and output lengths vary fourfold across the batch. | **Request** | **Prompt length** | **Output length** | **Total tokens** |
|:------------|:-----------------:|:-----------------:|:----------------:|
| **R1**      |        100        |        50         |       150        |
| **R2**      |        80         |        200        |       280        |
| **R3**      |        120        |        100        |       220        |
| **R4**      |        90         |        150        |       240        |

The 4$\times$ spread in output length (50 to 200 tokens) drives batching waste, because a static batch of four pads every request to the longest, wasting compute on the three shorter requests until the longest finishes generating. **Napkin Math 10.3: Continuous batching waste calculation**

**Problem**: Four LLM requests with unequal output lengths share a four-slot batch. Assume fixed decode-iteration time and no queueing. How much of the batch’s slot time does fixed membership leave unused, how much of it can continuous admission hand to new requests, and what happens to the original requests’ latencies?

**Variables**:

- Decode time per iteration (batch of 4): 20 ms
- Maximum output length in batch: 200 tokens (R2)
- Mean output length: $(50 + 200 + 100 + 150) / 4 =$ 125 tokens

**Slot accounting under fixed membership**: The batch keeps all four slots until R2, the longest request, finishes.

- Total decode iterations: 200
- Total batch time: $200 \times 20\text{ ms} =$ 4,000 ms

The waste ratio in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^eq-waste-ratio|equation 4]], one minus the ratio of mean to maximum output length, measures the slot time that finished requests leave idle:

${W} = 1 - \frac{125}{200} = 1 - 0.625 = 37.5\%$

The fixed-width schedule contains $4 \times 200 =$ 800 “sequence-iterations” but only 500 are useful. These counts measure executed work only if the kernel continues processing completed slots; otherwise they measure useful work relative to the schedule’s available slots.

**Continuous admission**: Sequences depart at the iteration where they complete, and eligible new requests take their slots without delaying the original requests under the fixed-iteration-time assumption.

- Iteration 50: R1 completes → slot freed, new request R5 can join
- Iteration 100: R3 completes → slot freed, new request R6 can join
- Iteration 150: R4 completes → slot freed, new request R7 can join
- Iteration 200: R2 completes

**Response latency, a separate effect**: The fixed-membership schedule in this comparison deliberately withholds all four responses until R2 completes its 200 tokens. Static batch membership alone does not require that barrier.

- Completion times with the barrier:
  - R1 completes useful work at iteration 50, but waits until iteration 200 → latency = 4,000 ms
  - R2 completes at iteration 200 → latency = 4,000 ms
  - R3 completes useful work at iteration 100, but waits until iteration 200 → latency = 4,000 ms
  - R4 completes useful work at iteration 150, but waits until iteration 200 → latency = 4,000 ms

Latencies with immediate release under continuous admission (assuming no queuing delay):

- R1: $50 \times 20\text{ ms} =$ 1,000 ms (4× improvement over traditional)
- R3: $100 \times 20\text{ ms} =$ 2,000 (2× improvement)
- R4: $150 \times 20\text{ ms} =$ 3,000 (1.33× improvement)
- R2: $200 \times 20\text{ ms} =$ 4,000 (no improvement for longest request)

Average latency comparison

- Traditional: 4,000 ms (all requests)
- Continuous: (1,000 ms + 2,000 + 3,000 + 4,000) / 4 = 2,500

**Result**: Under fixed membership, only 500 of the 800 sequence-iterations do useful work. Continuous admission hands the rest to R5, R6, and R7, which start generating at iterations 50, 100, and 150 instead of waiting for a new batch, so the same 200 iterations now advance seven requests rather than four. Releasing each response on completion separately reduces the original requests’ average latency by 37.5 percent, numerically matching the unused-slot ratio, and static batching that released responses on completion would obtain the same original-request latencies.

**Systems insight**: Response release and slot reuse are separate decisions. Removing a response barrier helps the requests already in the batch; only continuous admission recovers the stranded iteration capacity shown in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^fig-continuous-batching-comparison|figure 7]], and that recovered capacity is what raises a replica’s throughput.

#### Efficiency Regimes for Continuous Batching

^sec-inference-scale-continuous-batching-provides-maximum-benefit-a406

The continuous-batching analysis relates recoverable slot capacity to the gap between a batch’s longest and average output lengths. Let $\text{CV} = {\sigma}/ {\mu}$ be the coefficient of variation of output lengths. For the idealized fixed-width schedule, suppose the longest request in a batch is roughly ${k}$ standard deviations above the mean. The factor ${k}$ is an assumption about the batch rather than a property of the workload, because a larger batch draws more samples and pushes its maximum further into the tail. With immediate refill and unchanged iteration time, the corresponding capacity ratio is:

$$
\text{Improvement} \approx \frac{{S_{\text{max}}}}{{\bar{S}}} = \frac{{\mu}+ {k}{\sigma}}{{\mu}} = 1 + {k}\cdot \text{CV}
$$

where ${k}$ specifies how far the batch maximum lies above the mean, so the expression is a scenario ceiling on the opportunity from filling otherwise unused slots; scheduler overhead, KV-cache pressure, and refill gaps reduce the recovered fraction.

[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^tbl-continuous-batching-benefit|Table 7]] applies this ceiling across workload types, including retrieval-augmented generation (RAG) ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-lewis2020retrieval|Lewis et al. 2020]]). Its CV and ${k}$ columns are inputs. Its speedup column is an assumed realized fraction held below the $1 + {k}\cdot \text{CV}$ ceiling. Its waste column is the effective waste that each assumed speedup implies through $\text{speedup} \approx 1/(1 - {W_{\text{effective}}})$. That waste is smaller than the slot waste of [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^eq-waste-ratio|equation 4]], because each speedup sits below its ceiling. Neither the speedup nor the waste column is a measurement. Together they show how much of the ceiling a scheduler must recover to reach a given gain, which is the quantity a load test should measure.

| **Workload type**           | **CV** | **k** | **Waste (trad.)** | **Speedup (continuous)** |
|:----------------------------|:------:|:-----:|:-----------------:|:------------------------:|
| **Code completion**         |  0.3   |  2.5  |       16.7%       |           1.2×           |
| **Chat (short responses)**  |  0.6   |   2   |       33.3%       |           1.5×           |
| **General text generation** |   1    |  2.5  |        50%        |            2×            |
| **Creative writing**        |  1.5   |   3   |       64.3%       |           2.8×           |
| **RAG with variable docs**  |   2    |  2.5  |       71.4%       |           3.5×           |

Table 7: **Continuous Batching Benefit by Workload Type**: Higher output-length variance (CV) raises the ceiling on improvement from continuous batching. The ${k}$ values are assumed, so each $1 + {k}\cdot \text{CV}$ ceiling is a scenario value, and the speedups are assumed values held below it rather than measurements; the waste column is the effective waste those speedups imply. Workloads with predictable output lengths (code completion) have little to recover, while highly variable workloads (RAG with documents of varying length) have the most.

^tbl-continuous-batching-benefit

Continuous batching is most valuable when output lengths are unpredictable, mixed workload types share the same cluster, request volume is high enough to refill vacated slots, and latency SLOs make early completion valuable. It provides minimal benefit when output lengths are uniform, as in classification or embedding generation, when batch sizes are too small for slot reuse to matter, or when request volume is too low to refill vacated slots.

Because arrivals, KV-cache admission, prefill scheduling, and scheduler overhead decide how much vacated capacity is actually recovered, serving teams must compare policies under the same arrival trace, latency objective, and memory budget. The published vLLM system, which pairs iteration-level admission with paged KV allocation, reports 2–4$\times$ higher throughput at comparable latency than FasterTransformer and Orca on its evaluated workloads ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-kwon2023|Kwon et al. 2023]]). That figure compares whole systems rather than isolating slot reuse, because paged allocation also permits larger active batches.

#### Implementation Complexity Trade-Offs

^sec-inference-scale-implementation-complexity-tradeoffs-e055

The same variability that makes continuous batching valuable also makes it harder to operate. Memory management must support overlapping request lifetimes. Fixed-membership batching can reserve cache regions when a batch forms and release them together, whereas continuous admission must track which request owns each region and when it becomes reusable, either through fixed-capacity slots that retain unused reservations or through paging with its block tables. Kernels must also handle variable-length sequences and changing batch membership, often by packing short sequences under shared attention masks.

Scheduler work moves into the decode loop as well. A fixed-membership policy checks once per batch whether it is full or its timeout has expired, while continuous admission tracks completions, free cache capacity, and eligible waiting requests at every iteration boundary. That work must stay small relative to a decode step or it erodes the throughput that slot reuse recovers, so engines keep the per-iteration path short and prepare the next iteration’s batch on the host while the accelerator executes the current one. Continuous batching therefore buys its throughput gain with implementation and operating cost, weighed dimension by dimension in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^tbl-batching-tradeoffs|table 8]].

| **Dimension**             | **Traditional batching**  | **Continuous batching**          |
|:--------------------------|:-------------------------:|:---------------------------------|
| **Implementation effort** | Low (standard frameworks) | High (custom scheduler, kernels) |
| **Memory overhead**       |     Fixed allocation      | Dynamic + fragmentation mgmt     |
| **Scheduler work**        |      Once per batch       | Every decode iteration           |
| **Debugging complexity**  |  Deterministic behavior   | State-dependent, harder to trace |
| **Throughput (variable)** |         Baseline          | Up to $1 + {k}\cdot \text{CV}$   |
| **Throughput (uniform)**  |         Baseline          | ~1.0$\times$ (no improvement)    |

Table 8: **Traditional vs. Continuous Batching Trade-Offs**: Continuous batching provides significant throughput gains for variable-length workloads at the cost of implementation complexity. For uniform-length workloads, the complexity overhead may not justify adoption.

^tbl-batching-tradeoffs

Because continuous batching carries this implementation cost, some services still run request-level batching, and its barrier can surface as a tail-latency regression whose cause is not obvious. A constructed p99 regression shows how to investigate infrastructure, execution, and serving layers to find that cause. Its latency observations and mitigation outcome are scenario assumptions; only the transfer-time estimates are computed from payload and bandwidth.

**Example 10.2: Debugging high p99 latency**

**Scenario**: An LLM serving system shows high tail latency: p50 = 100 ms and p95 = 180 ms maintain SLO, but p99 spikes to ${T_{\text{lat},\text{p99}}} =$ 500 ms against a 200 ms target despite a monitored GPU utilization of 85 percent.

**Diagnosis**: The system runs across 4 A100 GPUs linked via PCIe Gen4 (32 GB/s per GPU) rather than NVLink. For a 100 MB payload, the bandwidth-only transfer estimate is ${T_{\text{comm}}}({N}) \approx$ 3.1 ms over PCIe versus 0.17 ms over NVLink. Collective startup, topology, and contention can add time. The service still runs an older request-level batching server rather than an iteration-level engine, with max batch size 32 and timeout 50 ms, so a batch holds its members until its longest generation finishes. The scenario assumes that 5 percent of batches experience head-of-line queuing delay ${L_{\text{lat,queue}}}$ as short requests wait behind long generations.

**Systems lesson**: The latency distribution motivates tracing both candidates, because a transfer paid by every request also amplifies tail queueing near saturation. In this scenario, traces showing stable transfer times too small to explain the additional delay, together with short requests waiting behind long generations, identify the fixed-membership barrier as the immediate cause. Continuous admission removes that barrier; prefill scheduling, cache capacity, and other waits still require measurement. Until the server can be replaced, the following policy reduces output-length variation within request-level batches:

1.  **Request classification**: Classify requests by expected output length (short: under 50 tokens, medium: 50 to 200 tokens, long: over 200 tokens)
2.  **Differentiated batching**: Limit short batches to 8, medium to 16, long to 32

Grouping requests by expected length shrinks the spread of output lengths inside each batch, which is the quantity [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^eq-waste-ratio|equation 4]] says drives both waste and waiting. The scenario assumes a post-mitigation p99 latency of ${T_{\text{lat},\text{p99}}} =$ 185 ms; a real service confirms it by replaying the same arrival workload and measuring the tail.

### Feature-Parallel Batching for Recommendation Systems

^sec-inference-scale-featureparallel-batching-recommendation-systems-2a3f

A single recommendation request may issue thousands of sparse lookups across embedding tables holding billions of entries before the dense ranking head can score a candidate. Grouping requests solely at the dense MLP therefore leaves the service bottlenecked on scattered memory reads and cross-server transfers. While fixed-shape vision inputs allow simple request grouping and autoregressive generation pairs iteration-level admission with KV-cache management (and with prefill-decode scheduling in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.09 Prefill and Decode#^sec-inference-scale-prefill-decode|section 10.8]]), recommendation systems must also batch around the placement of sparse state. *Sparse embedding lookups* can dominate memory access and communication in an embedding-heavy workload even when *dense matrix multiplications* account for much of the arithmetic. Feature-parallel batching groups those accesses by feature type and destination, which improves lookup locality at each shard and complements request batching in the dense stages.

Recommendation batching starts by grouping work around embedding locality rather than request shape. An incoming request splits across user, item, and context feature types to query sharded embedding tables concurrently, after which a gather barrier concatenates the retrieved representations for the dense MLP ranking head ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^fig-feature-parallel-pipeline|figure 8]]).

![[90 Assets/Volume II/10 Inference/Feature Parallel Pipeline 3011eb3e59.svg]]

Figure 8: **Feature-Parallel Batching Pipeline**: Requests are batched by feature type (Users, Items, Context) and dispatched to specialized embedding servers in parallel. The retrieved embeddings are then concatenated and processed by the dense ranking head. This architecture enables scaling to trillions of parameters by decoupling embedding storage from dense compute.

^fig-feature-parallel-pipeline

The sparse lookup path and the dense feature path can execute concurrently before feature interaction combines their representations and a ranking head produces final scores. The interaction stage must wait for its required inputs, which puts the slowest embedding shard on the request’s critical path.

When sparse embedding access dominates latency, feature-parallel batching groups lookups by feature type and destination across requests. Each embedding server then handles the lookups for its shard across the whole batch. This turns feature sharding into a serving strategy rather than a storage detail, while preserving the association needed to reconstruct each request for ranking:

    Request 1: [user_id_1, item_ids_1, context_1]
    Request 2: [user_id_2, item_ids_2, context_2]
    Request 3: [user_id_3, item_ids_3, context_3]

    Feature-parallel view:
    User embeddings:  [lookup(user_1), lookup(user_2), lookup(user_3)]  → parallel
    Item embeddings:  [lookup(items_1), lookup(items_2), lookup(items_3)]  → parallel
    Context features: [process(ctx_1), process(ctx_2), process(ctx_3)]  → parallel

    Then: Combine features per request for ranking

**Example 10.3: RecSys batching at hyperscale**

**Scenario**: A hyperscale recommendation service handles 10 million QPS, querying 5,000 embedding lookups per request across 1,000 shards.

**Diagnosis**: The assumed distribution of requests requires 50 million lookups/sec per shard. That rate is the capacity target each shard’s lookup service must sustain. Accumulating requests over a 1 ms window forms batches of 50K lookups per shard, creating an opportunity to deduplicate, reorder, or coalesce lookups. Batching alone does not make random addresses sequential.

**Systems lesson**: Shard-level batching exploits sparse feature locality, but its benefit depends on cache hits, access distribution, and the amount of work each shard receives. The formation window spends part of the 5.2 ms end-to-end latency budget; measured lookup and communication times must fit in what remains alongside the dense stages.

### Streaming Inference for Real-Time Applications

^sec-inference-scale-streaming-inference-realtime-applications-906c

Holding a live audio chunk or robot control frame in a batching queue until a large batch fills stalls transcription and breaks closed-loop control. Speech recognition, video analysis, and robotics process an ongoing sequence of observations under tight per-frame deadlines, so batching across ready streams helps only while the added waiting time fits each frame’s slack.

Streaming inference processes inputs incrementally rather than waiting for the complete recording or interaction. Illustrative input cadences include 10–20 ms audio chunks for speech recognition, 30–60 FPS video, and 100–1000 Hz sensor or control updates in robotics. These rates specify how often work arrives, not a universal inference deadline. Buffering, frame selection, and batching must follow the application’s latency and freshness requirements.

A streaming service must sustain the arrival rate while meeting the latency budget for each accepted input. The end-to-end processing path includes:

$$
{T_{\text{streaming}}}= {T_{\text{capture}}}+ {T_{\text{transfer}}}+ {L_{\text{lat,infer}}} + {T_{\text{action}}}
$$

where the sum must fit the end-to-end latency budget. A pipelined implementation must also sustain the input arrival rate; its slowest stage must process frames at least as quickly as they arrive. The end-to-end budget may span several frame intervals. A speech pipeline with 20 ms frames and a 100 ms budget can hold at most five frames of delay, so batching ready frames from independent streams helps only while the added waiting and service time fit that slack.

### Adaptive Batching Strategies

^sec-inference-scale-adaptive-batching-strategies-4fc1

A batching window and maximum batch size tuned for daytime peak traffic either hold requests waiting too long when traffic drops at night or cap throughput too early when a flash crowd arrives. Because fixed batching parameters break as arrival rates and request mixes shift, production systems adapt their batching windows and size limits to live conditions.

Traffic-adaptive batching adjusts the batch window based on arrival rate:

$$
{T_{\text{window}}}= \min\left({T_{\text{max}}}, \frac{{B_{\text{target}}}}{{\lambda_{\text{arr}}}}\right)
$$

When traffic is high, the window shrinks because the target batch size fills quickly. When traffic is low, the window extends but is capped to bound batch-formation delay. This cap does not bound the separate wait for a busy replica.

SLO-adaptive batching takes a complementary approach, monitoring latency percentiles and adjusting parameters aggressively:

    if P99_latency > 0.9 * SLO:
        reduce B_max by 20%
        reduce T_window by 20%
    elif P99_latency < 0.5 * SLO:
        increase B_max by 10%
        increase T_window by 10%

The feedback loop is a tuning heuristic, not a guarantee of latency headroom. Reducing batch size can shorten execution while also reducing service capacity and increasing queueing under heavy load. Feedback delay and noisy percentile estimates can cause oscillation, so the controller must be evaluated with the intended arrival trace and overload policy.

Request-aware batching adds another dimension by considering request characteristics. For LLMs, prompt length can guide padding and prefill budgets, while estimated output length can guide grouping. Prediction errors and priority choices must be included when evaluating tail latency.

Production runtimes expose these controls directly. NVIDIA Triton Inference Server, for example, caps batches with `max_batch_size`, bounds formation waiting with `max_queue_delay_microseconds`, and accepts `preferred_batch_size` values for particularly efficient execution profiles; priority queues and overload policy remain separate controls. Under a load test, larger batches absorb rising traffic until offered load approaches execution capacity, after which completions fall below arrivals and the growing queue needs an admission or scaling response rather than a larger batch.

The batching strategies to this point take each request’s work as given, apart from a cap on generation length. Reasoning-heavy inference makes that budget an explicit quality-cost decision. The service may allocate additional tokens or candidate evaluations when the expected benefit justifies their latency and capacity costs.

### Test-Time Compute and the Per-Request Budget

^sec-inference-logic-wall

![[90 Assets/Volume II/10 Inference/Inference Logic Wall Ladder f70d462d46.svg]]

*A two-rung latency ladder on a log scale in slate gray. The reasoning response rung is 12.8 seconds; the standard response rung is 100 milliseconds. A bracket between their ends marks the 128 times gap.*

*Reasoning through 128 serial tokens turns a 100 ms answer into 12.8 s.*

Letting a model emit hundreds of serial chain-of-thought (CoT) tokens or sample dozens of candidate solutions per query can turn a 100 ms interactive reply into a multi-second job that pins KV-cache memory and drains replica capacity. Test-time scaling buys answer quality by spending more compute on each query at inference time, which moves the scaling curve out of the training cluster and into the request path. Every increment of quality bought this way is paid on every request for the lifetime of the deployment, the recurring cost that the serving cost dominance principle ([[01 Books/Volume II - Scaling/03 The Fleet in Production/V2 Fleet-In-Production Principles#^pri-serving-cost-dominance|17]]) already prices. Whether extra generated tokens, internal CoT steps, or search branches actually improve quality on a given task is an empirical question. Capability studies describe abilities that appear abruptly with scale ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-wei2022emergent|Wei et al. 2022]]), while later analysis finds some apparent jumps to be artifacts of the metric chosen ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-schaeffer2023mirage|Schaeffer et al. 2023]]). A serving budget should therefore rest on measured quality gains for the workload.

From a serving-systems perspective, the relevant shift is the work issued per request. Additional reasoning consumes accelerator time and can extend both latency and KV-cache residency. Increasing test-time work does not necessarily change the bottleneck of each decode step. It instead requires a **per-request compute budget**, a limit on the generated tokens, candidate solutions, or search steps a request may consume, stated in both latency and capacity. The budget binds when serial reasoning tokens exhaust a request’s latency target, or its share of fleet capacity, before additional reasoning stops improving the answer. A harder task may justify more work, but additional work does not guarantee a correct answer. Adaptive batching decides when requests run together; test-time compute allocation decides how much work each request is allowed to issue.

↩︎ Test-time scaling, the lifecycle regime that spends compute per request rather than per training run, is established alongside the empirical scaling laws in **[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.04 AI Scaling Laws#^sec-vol2-intro-resourceconstrained-scaling-regimes-062d|Resource-constrained scaling regimes]]**.

**Napkin Math 10.4: Scaling reasoning depth**

**Problem**: Calculate the latency impact of a model that uses 128 “Thinking Tokens” to solve a complex math proof vs. a standard answer.

1.  **Standard response**: 1 token answer = 100 ms.
2.  **Reasoning response**: 128 tokens of internal search/CoT before the answer.
3.  **The latency**: 128 $\times$ 100 ms = 12.8 seconds.

**Systems insight**: The per-token time is a round figure chosen for easy arithmetic, more than ten times the batch-one decode step of the reference 70B replica in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.07 Program Goodput#^sec-performance-engineering-roofline|Drilling into the step]]**. What the calculation teaches does not depend on it. Serial reasoning tokens multiply latency by the ratio of reasoning tokens to answer tokens, whatever each token costs, so a faster replica shortens both responses in proportion and leaves the 128-fold expansion intact. Against a direct answer of many tokens rather than one, the ratio shrinks accordingly; against a one-token answer it is largest. A search step that evaluates several candidates in parallel adds compute and KV residency without adding the same serial latency, which is why reasoning budgets must be stated in both time and capacity. At fleet scale, compute allocation weighs the measured quality gain against both the request deadline and the capacity the additional work consumes.

Variable work per request closes the batching story: continuous and adaptive batching handle variation the system observes, while test-time compute is variation the system chooses. A serving policy therefore sets each request’s budget from task difficulty, latency tolerance, and fleet load rather than applying a fixed decode budget to every prompt. With the batching mechanism and the per-request compute budget both defined, the remaining decision is which combination a given workload should run.

### Selecting a Batching Strategy

^sec-inference-scale-quantitative-summary-batching-strategy-selection-d5af

Each batching mechanism trades scheduler overhead against slot utilization, so a fixed-shape vision classifier needs a different policy than an autoregressive chat endpoint or a sparse recommendation ranker. Selecting a batching strategy starts by matching the mechanism to the model’s work shape, traffic variance, and where the request path spends its latency budget.

                    |- Yes → Feature-parallel batching (RecSys)
                    `- No → Dynamic batching with adaptive parameters

Each resulting strategy has a typical batch range, a constraint that binds it, and a parameter it tunes ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.07 Batching Strategies at Scale#^tbl-batching-by-model|table 9]]). Vision and long-prompt prefill can emphasize compute utilization, small-batch decode can emphasize weight bandwidth, and sharded recommendation can emphasize embedding access, while speech introduces deadlines tied to the input stream. Each row is a starting point for measurement against both useful throughput and the latency budget, not a fixed bottleneck or batch-size requirement for every model in a category.

| **Model type**    | **Strategy**     |   **Typical batch size**   | **Key constraint** | **Key parameters**               | **Tuning goal**                  |
|:------------------|:-----------------|:--------------------------:|:-------------------|:---------------------------------|:---------------------------------|
| **Vision (CNN)**  | Static/Dynamic   |           32–256           | GPU compute        | Batch size; window and max batch | Balance latency vs. throughput   |
| **LLM (prefill)** | Dynamic          |            1–64            | GPU compute        | Window, max batch                | Balance latency vs. throughput   |
| **LLM (decode)**  | Continuous       | Tens–hundreds (KV-limited) | Memory bandwidth   | Chunk size, max batch            | Minimize decode latency variance |
| **RecSys**        | Feature-parallel |        1000–10000s         | Embedding lookup   | Accumulation window              | Match embedding shard capacity   |
| **Speech**        | Streaming        |             1              | Real-time          | Pipeline depth                   | Meet real-time deadline          |

Table 9: **Batching Strategy by Model Type**: Each model class pairs a batching policy (from static or dynamic batching in vision to continuous batching in LLM decode and feature-parallel batching in recommendation) with its dominant constraint and the parameter that tunes it. Typical batch sizes are operating ranges set by latency budgets and KV-cache capacity; they may fall below or above the overhead-amortization knees of notebook [10.2](https://mlsysbook.ai/vol2/10_inference/10_inference.html#nbk-inference-batching-efficiency-curve), which mark where fixed costs stop dominating rather than where batching stops paying.

^tbl-batching-by-model

Batching policy and memory admission are coupled. In a full-attention deployment that retains active KV state on the GPU, every admitted sequence consumes cache capacity as its context grows. A schedule with room for more decode work can therefore run out of memory before it reaches its execution limit. Managing that state is the next step in determining useful concurrency.
