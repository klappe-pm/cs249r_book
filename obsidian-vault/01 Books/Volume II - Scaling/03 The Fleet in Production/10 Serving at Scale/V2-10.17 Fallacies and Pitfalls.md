# V2-10.17 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-fallacies-pitfalls-55f9

A DevOps team that applies its standard web-server load-balancing rules to a new fleet of GPU inference nodes can see tail latency climb sharply, because those rules ignore the extreme variance of autoregressive token generation. Web services also face variable work and queueing, but an inference fleet adds model residency, accelerator scheduling, and per-sequence state to those familiar concerns. The fallacies below arise when a serving design ignores these constraints or treats one optimization as a complete solution.

**Fallacy**: *Serving at scale is synonymous with LLM serving.*

The misconception leads to over-focus on LLM-specific techniques. As [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.06 Serving Workloads and the Serving Hierarchy#^sec-inference-scale-inference-landscape-beyond-llms-9560|section 10.5.1]] showed, recommendation and ranking models can consume most AI inference cycles on large consumer platforms ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-gupta2020architectural|Gupta et al. 2020]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-hazelwood2018|Hazelwood et al. 2018]]). A practitioner who knows only continuous batching and KV cache management is unprepared for the feature-parallel batching and embedding sharding that dominate that traffic. Technique selection must match the actual workload.

**Pitfall**: *Using training infrastructure for production serving.*

Training and serving have different requirements, as [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.04 SLO Goodput and the Serving Tax#^tbl-training-inference-inversion|table 2]] summarized. Interactive serving must satisfy per-request latency targets under external arrivals, so its batch size depends on the workload and waiting budget, and its recovery policy must account for in-flight requests, retries, and the availability target rather than a checkpoint. Hardware can be shared or repurposed, but a training configuration does not establish serving readiness.

**Fallacy**: *Continuous batching solves the whole LLM serving problem.*

Continuous batching reuses slots released by completed requests, but it addresses only one dimension of the problem. Prefill can remain a bottleneck for long contexts because scheduling subsequent decode iterations does not remove the quadratic attention work of full-attention prefill. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-kv-cache-management-04ed|Section 10.7]] demonstrates that KV cache memory, not compute, often limits batch size. Network bandwidth between sharded model components can dominate latency for large models. The value of continuous batching depends on the workload; slot reuse alone does not resolve these other constraints.

**Pitfall**: *Sizing the fleet by average throughput.*

Average throughput alone does not establish capacity for bursts. With unchanged work per request and service capacity, a 25 percent traffic increase from 80 percent utilization reaches 100 percent utilization, leaving no spare capacity to absorb variance. Whether the resulting queue violates an SLO depends on burst duration, the waiting budget, and admission policy. Cluster-level cold starts can delay relief for multiple minutes. Capacity planning must therefore account for peak load, burst duration, ready headroom, and the work the service can defer or reject.

**Fallacy**: *Load balancing does not matter much for inference.*

Simple load balancing strategies like round-robin can distribute request counts while leaving work uneven. The static placement analysis in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^sec-inference-scale-load-balancing-request-routing-4997|section 10.11]] motivates two probes, but its occupancy bounds do not predict production queue lengths. Serving comparisons must preserve arrivals, request lengths, cache affinity, and replica capacity. Work-aware routing earns its place when it improves measured tail latency without excessive coordination cost.

**Pitfall**: *Ignoring the serving tax.*

Distributed inference adds network round-trips and shard coordination to the serialization, routing, and queueing costs that can already surround a single-machine model. This serving tax depends on deployment topology and load. In the illustrative budget of [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.04 SLO Goodput and the Serving Tax#^sec-inference-scale-serving-tax-overhead-distribution-5ef3|section 10.3]], 70 ms of model execution leaves only 30 ms for every other stage of a 100 ms request target, and queueing alone can consume that remainder as load rises. A kernel benchmark measures only the first term of [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.04 SLO Goodput and the Serving Tax#^eq-serving-tax|equation 1]]; the serving latency is the measured sum along the complete request path.

**Fallacy**: *More GPU memory always means larger batch size and higher throughput.*

Larger GPU memory raises throughput only when the extra capacity supports useful work within the latency budget. Even when memory bandwidth is saturated, a larger decode batch can increase tokens per second by sharing weight reads across more sequences. That gain stops when compute, per-sequence KV-cache traffic, or the SLO becomes binding. The bottleneck hierarchy distinguishes these limits.

For an H100 with 80 GB memory and 3.35 TB/s HBM3 bandwidth, capacity and transfer rate are separate limits. More capacity may admit additional sequences, but the resulting batch must still meet compute, bandwidth, and latency budgets. Once extra sequences no longer improve useful throughput within those budgets, adding memory alone cannot help. Capacity planning therefore measures the bottleneck at the intended batch size and context length rather than assigning one permanent bottleneck to the model.

**Pitfall**: *Neglecting multi-tenancy isolation until production.*

In development and staging, single-tenant deployments work well. In production, noisy neighbors cause sudden, unpredictable performance degradation that is difficult to diagnose and resolve. A tenant bursting to 5$\times$ normal traffic can degrade latency for all other tenants on shared infrastructure. As emphasized in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.13 Multi-Tenancy and Isolation#^sec-inference-scale-multitenancy-isolation-688c|section 10.12]], resource quotas, priority scheduling, and bulkhead isolation must be designed into the system from the start, not retrofitted after production incidents.

**Fallacy**: *The lowest supported precision is always the best precision.*

Aggressive quantization (INT4 weights, INT4 KV cache, FP8 activations) can degrade model quality in ways that standard benchmarks miss but users see. Perplexity on a held-out dataset may change by less than 1 percent while responses degrade for edge cases, rare languages, or complex reasoning. A serving system that doubles its tokens per second with a format that lowers answer quality has not doubled its useful capacity, because throughput and quality form a frontier and a precision choice is a point on it. The disciplined approach is targeted quantization: measure per-layer sensitivity under representative workloads, restrict lower bit widths to the tensors that tolerate them, and evaluate KV caches, endpoint layers, and attention logits empirically rather than by a presumed sensitivity ranking. Calibration on representative data, followed by evaluation on diverse quality benchmarks reported beside the latency and throughput results, comes before any quantized model reaches production ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.10 Weight Quantization for Serving#^sec-inference-scale-weight-quantization-serving-097b|section 10.9]]).

**Pitfall**: *Treating MoE expert count as a free scaling knob.*

Adding experts to an MoE model raises total parameters without proportionally raising active per-token arithmetic, which makes expert count look free. Every expert still occupies memory whether or not a token selects it, as [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.11 Model Sharding for Inference#^sec-inference-scale-moe-economics|section 10.10.4.1]] prices for resident versus active parameters, so more experts mean more devices or less KV headroom. A distributed placement also adds dispatch and combine communication to every layer. The realized cost depends on experts selected per token, token-to-expert skew, expert capacity, topology, and batching, and no universal expert count marks where the design starts to lose. The change is justified only when a matched-quality comparison shows that active-compute savings exceed routing, imbalance, memory, and communication costs over the intended workload envelope.

These fallacies and pitfalls identify what a serving evaluation must test: traffic variance, cost per completed request within the SLO, output quality beside throughput, and interference across tenants. Correct technique selection must be followed by measurement under the intended load and failure conditions.

**Self-Check: Question**

1.  A team upgrades a cluster serving a 13B LLM from 80 GB GPUs to 140 GB GPUs with identical HBM3 memory bandwidth (3.35 TB/s). At an unchanged small batch and context length, with resident weights and weight-read-dominated decode, why does extra capacity alone not raise the bandwidth-limited throughput ceiling?

    1.  Autoregressive decode is strictly compute-bound; increasing memory without adding Tensor Cores leaves execution time unchanged.
    2.  Autoregressive decode is memory-bandwidth bound ($D_{\text{vol}} / \text{BW}$); once model weights fit resident in memory, token generation speed is constrained by memory bandwidth, not total memory capacity.
    3.  140 GB GPUs automatically disable CUDA graph compilation, adding driver launch latency to every iteration.
    4.  The larger memory capacity forces PagedAttention block sizes to shrink from 16 tokens to 2 tokens.

2.  A capacity planner provisions an inference serving fleet for 80% average utilization based on mean daily traffic. Why can traffic spikes exhaust headroom before reactive scaling helps, and what determines whether the P99 SLO is missed?

3.  True or False: Deploying continuous batching alone completely solves all throughput and latency bottlenecks in LLM serving.

4.  True or False: Because each token activates only a small fixed number of experts, raising an MoE model’s expert count from 8 to 256 adds serving capacity at essentially no cost.

5.  A team moves its endpoint from INT8 to INT4 weights and INT4 KV cache, doubling tokens per second while held-out perplexity changes by less than 1 percent. What should it conclude before rollout?

    1.  The change doubles useful capacity, because perplexity confirms quality is unchanged
    2.  The change is safe only if the KV cache returns to FP16, because weight precision never affects quality
    3.  Useful capacity has not been established: low-bit formats can degrade rare languages, edge cases, or reasoning while perplexity barely moves, so quality must be evaluated per layer and per task and reported beside throughput
    4.  The change should be rejected, because INT4 always reduces quality below an acceptable level
