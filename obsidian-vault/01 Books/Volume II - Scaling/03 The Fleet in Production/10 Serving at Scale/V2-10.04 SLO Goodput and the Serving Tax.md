# V2-10.04 SLO Goodput and the Serving Tax

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-serving-tax-overhead-distribution-5ef3

A replica that runs near its hardware limit still wastes its capacity if requests wait so long in queues, network hops, and host processing that responses arrive after the user’s deadline. Because a served request counts as useful work only when it meets its latency and quality targets, every stage it crosses spends part of that contract’s budget.

### The Inversion from Training to Inference

^sec-inference-scale-fundamental-inversion-training-vs-inference-8834

A training iteration that takes 2 seconds instead of the usual 1 second slows a run slightly, and faster steps later can still keep the job on schedule. An interactive request that takes 2 seconds against a 100 ms target fails its contract immediately, even if every subsequent request finishes on time. This contrast between training and inference centers on the unit of useful progress. Training evaluates throughput together with convergence over a run; interactive serving evaluates completed requests against quality and latency targets. Offline inference can also prioritize throughput, and training still loses progress to stragglers and stalls, so the distinction is which delays violate the workload’s contract, not whether one activity cares about time and the other does not. That difference reorders priorities across six system aspects, from the primary metric onward ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.04 SLO Goodput and the Serving Tax#^tbl-training-inference-inversion|table 2]]).

| **Aspect**              |   **Distributed training**    |      **Distributed inference**       |
|:------------------------|:-----------------------------:|:------------------------------------:|
| **Primary metric**      |   Throughput (samples/hour)   |           Latency (p99 ms)           |
| **Acceptable variance** |             Hours             |             Milliseconds             |
| **State management**    |    Checkpoints (periodic)     |      Session state (continuous)      |
| **Batch formation**     |       Large, controlled       |       Request-driven, variable       |
| **Failure tolerance**   |    Restart from checkpoint    | Redirect if capacity and state allow |
| **Cost structure**      | Fixed duration, variable rate |     Variable duration, fixed SLO     |

Table 2: **Training vs. Inference System Requirements**: The fundamental inversion from throughput to latency optimization ripples through system design, state management, batch formation, and failure recovery.

^tbl-training-inference-inversion

Failure handling follows those different contracts. Training restores a checkpoint and repeats lost work, charging recovery time to the run. Interactive serving has far less time per request, so redirecting work needs spare capacity and recoverable request state, and substituting a smaller model needs an acceptable quality fallback. SLOs define which failures and delays the service may tolerate, and a recovery mechanism helps only when its added work fits within that contract.

The same targets also define the serving system’s capacity metric. **SLO goodput** is the rate of completed requests that meet the stated TTFT and TPOT targets for a fixed request mix. It is the serving counterpart of the useful-progress goodput that coordination protects in training (**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^sec-vol2-introduction-dim-coord|Orchestration coordination layer]]**). ML goodput measures how much of the fleet’s capacity becomes useful work at the ideal rate; SLO goodput counts only the part of that capacity that completes requests within their targets. A request that misses its contract counts for nothing, however busy the accelerators were while serving it, so increasing arrivals without completing more requests within those targets does not increase useful capacity.

↩︎ ML goodput, the fraction of fleet capacity that becomes useful work at the ideal rate, and its three factors are established in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.03 ML Goodput#^sec-performance-engineering-measurement-scale|ML Goodput]]**.

### The Serving Tax

^sec-inference-scale-serving-tax-budget

If an interactive request carries a 100 ms latency target and model execution takes 70 ms on an idle replica, routing, network transfers, serialization, coordination, and queueing must all fit inside the remaining 30 ms. Distributing inference adds transfers and coordination to a request that already spends time in host processing and queues. This “serving tax” is the exposed work outside model execution that consumes the request’s latency budget, and its size depends on which components the request crosses and which costs can overlap.

Network communication contributes setup and transfer time at each cross-machine dependency. Synchronization between GPUs can expose that cost when the next operation needs a remote result. For an illustrative path with four sequential exchanges taking 50–500 microseconds each, the exposed contribution is 200 microseconds to 2 milliseconds. Actual collective time also depends on payload, topology, contention, and the number of communication rounds; a generic network round-trip time cannot be charged once per collective without checking its implementation.

↩︎ The ${\alpha}$-${\beta}$ model, which splits each transfer into a fixed startup latency plus a bandwidth-dependent term, is established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-performance-model|The α-β performance model]]**.

Before and after those network hops, serialization adds host work whenever a service converts structured data into a wire representation and reconstructs it at the receiver. Protocol Buffers, JSON, and Python’s `pickle` provide different representations and implementation paths, so their cost must be measured for the actual payload and runtime. Tensor transfers within a sharded model need not pass through the same object-serialization path as a service request. Formats such as FlatBuffers and Cap’n Proto permit access to wire-format data in place, avoiding a separate unpacking step when the consumer supports that representation, though they do not eliminate network transfer or every downstream copy.

Once the payload is on the wire, load balancing adds a routing decision and sometimes another forwarding hop: examining request metadata, consulting replica state, and forwarding to the selected backend all consume time before execution begins. The measurement must separate decision time from waiting and transport so that a slow routing path is not mistaken for a slow model.

When a request fans out to several backend services such as feature stores, retrieval indexes, and ranking models, coordination overhead emerges as the gateway joins their results. Independent feature or model calls can run concurrently, but a dependent ranking stage must wait for the inputs it needs, so the critical path includes exposed coordination and the slowest required branch rather than the sum of every branch’s runtime. Finally, queuing delay (${L_{\text{lat,queue}}}$) adds waiting time whenever work arrives while the required resources are busy, even when the average arrival rate remains below average service capacity.

The serving tax must be measured on the same request boundary as model execution. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.04 SLO Goodput and the Serving Tax#^eq-serving-tax|Equation 1]] decomposes that latency, with each term counting an exposed contribution so concurrent work is not counted twice:

$$
{L_{\text{lat,total}}}= {L_{\text{lat,infer}}}+ {L_{\text{lat,network}}}+ {L_{\text{lat,serialization}}}+ {L_{\text{lat,coordination}}}+ {L_{\text{lat,queue}}} \tag{1}
$$

^eq-serving-tax

In the 100 ms request budget above, the four sequential exchanges alone can claim up to 2 ms of the 30 ms non-compute slack before any request waits for a busy replica. The measured contribution determines the intervention: co-location removes a network hop, fewer dependent exchanges reduce startup costs, and a faster link shortens large transfers, whereas queueing requires controlling admitted work or increasing usable capacity. Each choice spends resources to recover latency budget, connecting the request-level diagnosis to lifetime serving cost.

    1.  X, because it completes more requests per second and keeps its accelerators busier.
    2.  The two are equal, because both process the same request mix.
    3.  X, because requests that miss their targets still return results to users.
    4.  Y, because SLO goodput counts only requests that meet their targets, about 950 per second against about 840 for X.
