# V2-10.13 Multi-Tenancy and Isolation

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-multitenancy-isolation-688c

Consider a critical customer-support chatbot running on the same GPU server as an experimental computer vision script. If the experimental workload monopolizes the PCIe bus or memory bandwidth, the chatbot can miss its latency target. Sharing saves capacity only when the resulting interference remains within each service’s contract. Fleet quotas, fair-share hierarchies, and priority preemption decide how much of the cluster a serving system receives; the problem here is controlling contention among the tenants who share that allocation, request by request.

↩︎ Fleet quotas, hierarchical fair-share, and the priority classes that govern preemption are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.12 Multi-Tenancy and Quotas#^sec-fleet-orchestration-multi-tenancy|Multi-Tenancy and Quotas]]**.

Sharing a serving pool can raise utilization and reduce separately provisioned capacity when tenant demand peaks occur at different times. This statistical-multiplexing gain weakens when bursts are correlated, and shared resources introduce interference even when aggregate demand fits. Pooling therefore needs both a demand model and enforceable isolation.

![[90 Assets/Volume II/10 Inference/Vol2 Inference Margin 004 3cedd55614.svg]]

*A red tenant workload fans gray arrows to five blue peer workloads, showing one source degrading many shared dependents.*

*One tenant’s burst can degrade every workload sharing the pool.*

A burst from one tenant can delay others through shared KV-cache capacity, network bandwidth, and accelerator time. The pool must preserve each tenant’s data boundary and service contract; different SLOs can require different admission limits, reservations, or placements. Noisy-neighbor interference comes first because it connects shared-resource contention directly to those latency contracts.

### Noisy Neighbor Problems

^sec-inference-scale-noisy-neighbor-problems-1b87

A noisy neighbor, the tenant whose consumption of a shared resource slows the others on the same hardware, interferes inside a serving pool through three resources at once, and each is denominated in units a request-level scheduler can meter. Unchecked demand for KV-cache capacity, network egress bandwidth, or accelerator execution time lets one bursty workload erode the headroom of every co-located tenant.

GPU memory contention can limit admission before compute capacity is exhausted. Consider three tenants sharing a 60 GB KV pool with nominal 20 GB shares. Without enforced limits, one tenant’s long-context requests can raise its allocation to 45 GB. In the scenario, the others lose capacity from 200 concurrent sequences each to 75, a 62.5 percent reduction. That is a concurrency loss, not a proportional throughput prediction; the effect depends on their execution regime and preemption costs. Egress bandwidth and accelerator time are additional shared resources whose contention must be measured alongside memory occupancy.

↩︎ Noisy-neighbor contention and the device-level interference channels of shared accelerators (memory bandwidth, cache hierarchy, host-device interconnect, and thermal dissipation) are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.11 Serving Capacity in the Shared Fleet#^sec-fleet-orchestration-resource-isolation|Resource isolation]]**.

**Example 10.9: Quantifying noisy neighbor impact**

**Scenario**: An inference platform serves 10 tenants on shared H100 GPUs at 100 QPS each under a 50 ms p99 SLO. Tenant 3 bursts to 500 QPS, 5× its baseline.

**Diagnosis**: Without quotas, contention raises pool-wide p99 into the 22 ms to 45 ms range in this scenario, eroding every tenant’s headroom while remaining within the stated target. With quotas, Tenant 3 is limited to 120 QPS and the other tenants retain 15 ms p99. Throttling turns Tenant 3’s excess into rejected or delayed requests, which are judged against Tenant 3’s own contract rather than spread across the pool.

**Systems lesson**: Shared capacity raises utilization only when it is coupled with isolation. Quotas turn pool-wide erosion of latency headroom into an admission decision confined to the tenant that caused it; without them, a larger burst or a tighter SLO turns the same erosion into violations across the pool.

### Resource Quotas and Fair Sharing

^sec-inference-scale-resource-quotas-fair-sharing-006c

Limiting tenants by request count alone fails when one request carries a 20-token query and the next submits a 100,000-token document that monopolizes KV-cache pages and prefill compute. Resource quotas limit what each tenant can consume across every scarce resource, preventing any single tenant from monopolizing shared hardware. Hard quotas turn shared serving into admission control: request rate and concurrency bound arrival pressure, while input tokens, output tokens, KV-cache pages, accelerator time, and egress bytes bound the work performed after admission. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.13 Multi-Tenancy and Isolation#^lst-resource-quotas|Listing 1]] shows representative gates so a tenant can be throttled at the scarce resource boundary instead of degrading the whole batch.

``` python
class TenantQuota:
    max_concurrent_requests: int  # e.g., 100
    max_kv_cache_mb: int  # e.g., 20,000
    max_qps: int  # e.g., 1,000
    max_input_tokens_per_minute: int
    max_output_tokens_per_minute: int
    max_batch_tokens: int  # e.g., 50,000

def check_quota_snapshot(tenant_id, request):
    quota = get_quota(tenant_id)
    usage = get_usage(tenant_id)

    if usage.concurrent + 1 > quota.max_concurrent_requests:
        return RateLimitError("concurrent request limit")
    if usage.kv_cache_mb + request.reserved_kv_mb > quota.max_kv_cache_mb:
        return RateLimitError("memory limit")
    if usage.requests_last_second + 1 > quota.max_qps:
        return RateLimitError("rate limit")
    if usage.input_tokens + request.input_tokens > quota.max_input_tokens_per_minute:
        return RateLimitError("input-token limit")
    if usage.output_tokens + request.max_output_tokens > quota.max_output_tokens_per_minute:
        return RateLimitError("output-token limit")

    if request.prefill_chunk_tokens > quota.max_batch_tokens:
        return RateLimitError("prefill chunk exceeds batch-token limit")

    return None  # Snapshot is eligible; no resources have been reserved.
```

Listing 1: **Multidimensional Resource Quotas**: A snapshot check compares prospective resource use with tenant limits. Atomic reservation and scheduler enforcement are separate requirements.

^lst-resource-quotas

This listing assumes that `reserved_kv_mb` includes the requested prompt and output-token budget, and that usage counters include outstanding reservations in their stated time windows. A passing snapshot is not an admission guarantee: simultaneous callers can observe the same free capacity. Production admission must check and reserve resources atomically, roll back failed admissions, and release reservations on completion or cancellation. The batch scheduler separately enforces the aggregate batch-token limit. Quotas protect the resources they account for; shared compute, networking, and control-plane contention still require isolation and measurement.

Soft quotas permit borrowing unused capacity while preserving an enforceable share when demand rises. The unit of account matters: equal request counts can hide large differences in prefill work, output length, and retained state. Input and output tokens therefore need separate accounting, with memory and concurrency limits alongside them. The progressive-filling approach in **[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.05 Core Allocation Constraints#^sec-fleet-orchestration-drf-worked-allocation|Dominant-resource fairness allocation]]** reduces to max-min fairness when only one divisible resource constrains the allocation. For three tenants demanding 30,000, 20,000, and 80,000 output tokens/sec from an idealized 100,000-token/sec pool with equal token costs, the allocation is 30,000, 20,000, and 50,000. Coupled prefill, decode, and memory constraints require joint feasibility checks; independent fair allocations do not automatically compose into a feasible service.

### Priority Scheduling

^sec-inference-scale-priority-scheduling-3e37

First-come, first-served scheduling treats a paid interactive query and a background batch job identically, letting a surge of free-tier or offline traffic delay revenue-critical requests past their SLO. Priority-aware scheduling gives eligible high-priority requests precedence at scheduling boundaries: a production API might classify revenue-generating customer requests as critical, internal batch processing as standard, and free-tier traffic as best-effort. Already-running kernels and shared resources can still delay critical work, so admission limits and reserved capacity must complement priority ordering. Priority becomes an isolation tool once its classes map to tenants and service tiers. Fleet priority classes govern preemption across allocations; request priority applies inside a serving allocation. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.13 Multi-Tenancy and Isolation#^tbl-priority-scheduling-classes|Table 19]] illustrates a policy that combines precedence with reservations. Those reservations must be provisioned and enforced separately: priority alone cannot create capacity, interrupt every running kernel, or guarantee a deadline under unbounded critical traffic.

| **Class**       |    **Use case**    |     **Preemption**      | **Resource guarantee** |
|:----------------|:------------------:|:-----------------------:|:----------------------:|
| **Critical**    | Revenue-generating |    Can preempt lower    |     100% reserved      |
| **Standard**    |  General traffic   | Can preempt best-effort |     Weighted share     |
| **Best-effort** | Background, batch  |     Cannot preempt      |      No guarantee      |

Table 19: **Priority Scheduling Classes**: Three-tier priority hierarchy for multi-tenant inference. Critical traffic gets 100 percent reserved capacity and can preempt any lower class; standard traffic shares capacity proportionally and can preempt best-effort; best-effort runs on leftover capacity with no guarantees.

^tbl-priority-scheduling-classes

Preemption extends priority to requests already in flight, but priority does not make state movement free. The retain, swap, recompute, or reject choice of [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-vllm-architecture-9b84|section 10.7.7]] still decides how a displaced request’s KV state is handled; priority adds an input to that choice rather than replacing it. A priority class determines who may be displaced, while remaining service time, state size, and deadline slack determine which victim is cheapest. Ignoring those costs lets aggressive preemption consume more capacity than it releases.

### Bulkhead Pattern

^sec-inference-scale-bulkhead-pattern-1c3a

Quotas and priority queues inside a single shared serving process cannot stop a malformed request or out-of-memory fault from crashing the worker and dropping every tenant’s in-flight generations at once. The bulkhead pattern[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.21 Footnotes#^fn7|⁷]] ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-nygard2007releaseit|Nygard 2007]]), named after ship compartments intended to contain flooding, partitions resources across separate concurrency pools, processes, or dedicated hardware so exhaustion or failure in one allocation stays contained.

Dedicated replicas separate more resources than request limits inside one process. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.13 Multi-Tenancy and Isolation#^fig-bulkhead-patterns|Figure 20]] assigns distinct compute and memory pools to tenant groups, so an engine crash or exhausted local allocation in the standard tier need not stop the gold-tier engines. Shared networking, storage, and control-plane services can still carry interference across that boundary.

![[90 Assets/Volume II/10 Inference/Bulkhead Patterns 06c280f0fd.svg]]

Figure 20: **Bulkhead Isolation Patterns**: To prevent cascading failures in multi-tenant systems, bulkheads isolate resources. Deployment-level bulkheads (shown) assign dedicated physical replicas to high-priority tenants, separating their compute and memory pools. Request-level bulkheads enforce strict concurrency limits within shared processes. Shared networking, storage, and control-plane dependencies remain possible paths for interference.

^fig-bulkhead-patterns

Deployment-level bulkheads cost pooling efficiency and the operational overhead of dedicated infrastructure. Request-level bulkheads are cheaper but weaker. Caps such as 8,000 input tokens, 2,000 output tokens, and 30 seconds of execution bound request size and duration when the scheduler enforces them, but they still need concurrency limits, reservations, and cancellation handling, and they cannot contain a crash. A malformed request that crashes a shared worker interrupts every tenant on that worker, so service tiers that require stronger fault isolation need placement boundaries to match.

**Example 10.10: Bulkhead configuration for API tiers**

**Scenario**: An LLM API platform serves Enterprise, Professional, and Free service tiers across shared and dedicated hardware.

**Diagnosis**: Unpartitioned pools allow Free-tier bursts or shared-worker failures to affect Enterprise requests. The example assigns Enterprise to dedicated GPU pools with a 99.9 percent availability target, allocates 70 percent of the remaining shared capacity to Professional, and caps Free at 30 percent best-effort capacity. Meeting that target still requires reliability evidence for the dedicated pools themselves.

**Systems lesson**: Bulkheads concentrate isolation overhead where business requirements dictate. Hardware partitioning reduces cross-tenant compute and memory contention. SLO compliance still depends on sufficient capacity, admission policy, shared dependencies, and failure handling.

^exmp-inference-bulkhead-configuration-api-tiers

Multi-tenant isolation limits the blast radius of excess demand, but it does not create capacity. Once protected queues approach their latency budgets, the service needs a control loop that can add replicas before admission begins to fail.
