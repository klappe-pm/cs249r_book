# V2-10.08 Memory and Decode-Time Management

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10 Serving at Scale|V2-10 Serving at Scale]]

^sec-inference-scale-kv-cache-management-04ed

As a full-attention LLM generates a 2,000-word essay, each new token attends to representations of earlier tokens. The KV cache retains the keys and values needed for that attention, with a per-request footprint that grows as generation proceeds. Large contiguous reservations can leave HBM reserved but unused or create gaps too small for another reservation. Admission can then fail even though the stored attention state occupies less than the available capacity.

**Definition 10.2: KV cache**

***KV cache*** is a per-request LLM inference memory buffer that stores key and value attention tensors for processed prompt and generated tokens. It avoids recomputing those tensors for the prefix; each new query still performs attention against the cached state.

1.  **Significance**: Compared with recomputing full-prefix attention for each new token, caching changes the attention work from $\mathcal{O}({S}^2)$ to $\mathcal{O}({S})$ in sequence length for full attention with fixed model dimensions. Retaining that state costs memory proportional to context length and the number of active sequences, potentially exceeding the weight footprint. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-kv-cache-wall|Section 10.7.1]] sizes it per token and per replica.
2.  **Distinction**: Model weights are shared across requests using the same model, while each sequence has its own logical KV state. Physical storage can still be shared for compatible common prefixes. The scheduler must budget for distinct retained state and its growth, rather than assume every request needs a wholly separate copy or that sharing removes the capacity limit.
3.  **Common pitfall**: A frequent misconception is that reducing model size proportionally reduces serving memory. In practice, the KV cache dominates HBM at long contexts, so a quantized 70B model can still be capacity-bound at batch sizes the weights alone would easily admit.

Two classes of techniques meet at this boundary. KV-state capacity techniques, such as PagedAttention and prefix caching, decide where attention state lives and how much fragmentation the memory manager tolerates. Decode-time latency techniques, such as speculative decoding, change how much target-model work is needed per emitted token. Speculative decoding is not KV-cache compression; it trades extra draft-model state, target-model verification, and scheduler complexity for lower TPOT under the same memory budget. Capacity accounting and adapter locality then determine how retained KV state and task-specific weights share the remaining memory budget.

Most of the calculations that follow share one reference replica, the 70B model on one eight-GPU H100 node that fleet efficiency measured as its serving replica, with FP16 weights split eight ways; the few that leave it say so. The attention layout matters even more, because it sets the bytes cached per token. Grouped-query attention (GQA) with eight KV heads, the layout of the Llama-family 70B models, caches one eighth the state of a 64-head multi-head attention baseline, because groups of query heads share each cached key and value head ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-gqa|section 10.7.5.2]]). Each calculation therefore names its hardware and attention layout, and numbers from different calculations compare only after conversion to the same configuration.

↩︎ The reference serving replica, a 70B model on one eight-GPU H100 node, is established in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/09 Fleet Efficiency/V2-09.02 Where Fleet Capacity Goes#^sec-performance-engineering-memory-wall|Where Fleet Capacity Goes]]**.

### The KV Cache Wall and Memory Capacity

^sec-inference-scale-kv-cache-wall

Even when a 4-bit quantized 70B model occupies only 35 GB of an 80 GB H100, admitting a second 128K-token request pushes the combined weight and KV-cache footprint past 80 GB and exhausts HBM before execution resources saturate. Increasing batch size in LLM serving therefore hits the KV cache wall long before compute binds. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^fig-kv-cache-wall|Figure 9]] leaves the reference replica to show the wall on a single H100. It combines an idealized 35 GB weight payload for a quantized 70B model with its full-attention, eight-KV-head GQA state. The budget reads the nameplate label in decimal gigabytes, slightly less than the device’s registered byte capacity, which keeps the plotted wall conservative; the node estimator below uses the registered byte capacity. A batch of 8 reaches the memory boundary at roughly 17K tokens per sequence; quantization metadata, runtime buffers, and other allocations make the plotted boundary an optimistic sizing limit.

![[90 Assets/Volume II/10 Inference/Cell 24 Output 1 69fb9c0821.png]]

Figure 9: **The KV Cache Wall**: Total GPU memory usage for a 4-bit quantized 70B model (35 GB weights) on an 80 GB H100. While the model fits easily at small context lengths, the KV cache (sloped lines) eventually consumes all remaining HBM. At 128K context, a batch size of 2 is physically impossible on a single GPU (35 GB + 84 GB exceeds 80 GB), forcing the system to either reduce batch size, change the state representation, or distribute the state across devices.

^fig-kv-cache-wall

The visualization explains why weight fit alone does not establish serving capacity. A long-context request can consume nearly all remaining memory in the illustrated configuration, leaving little space for other active sequences. Sharding can add headroom, but its communication cost must be weighed against alternatives such as lower concurrency or a smaller cache representation. The effect of a 128K context depends on the model’s cache dimensions and precision, not on context length alone.

The capacity model behind the figure starts from the cost of one cached token. Every layer stores a key vector and a value vector for each KV head, so with ${N_L}$ layers, ${H_{\text{KV}}}$ KV heads, head dimension ${d_{\text{head}}}$, and ${s_{\text{elem}}}$ bytes per element, [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^eq-kv-bytes-per-token|equation 5]] gives the bytes cached per token:

$$
{m_{\text{token}}} = 2 \times {N_L} \times {H_{\text{KV}}} \times {d_{\text{head}}} \times {s_{\text{elem}}} \tag{5}
$$

^eq-kv-bytes-per-token

A replica’s KV footprint is that cost multiplied by every token it holds, ${M_{\text{KV}}} = {B} \times {S} \times {m_{\text{token}}}$, so the largest admissible batch at context ${S}$ is the HBM left after weights and runtime allocations divided by ${S} \times {m_{\text{token}}}$. Each serving lever acts on a different factor. Grouped-query attention lowers ${H_{\text{KV}}}$, KV quantization lowers ${s_{\text{elem}}}$, a shorter admitted context lowers ${S}$, and paging returns HBM lost to fragmentation without changing the per-token cost. The notebook below turns this budget into an explicit batch-size limit for a production node.

**Napkin Math 10.5: KV-cache capacity estimator**

Unlike the conservative decimal budgets used in the illustrative comparisons, this estimator retains the registered byte capacity when summing the node’s HBM. Converting its display units does not change that byte count.

**Problem**: A deployment serves an illustrative 70B-class GQA model with 128K context support (FP16 weights $\approx$ 141.2 GB) on an 8$\times$ H100 node (640 GB total HBM). The goal is to determine the maximum batch size for a context length of 128K tokens.

**Formula**: Bytes per token come from [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^eq-kv-bytes-per-token|equation 5]], and

$$
{M_{\text{total}}} = {M_{\text{weights}}} + {M_{\text{KV}}}, \qquad {M_{\text{KV}}} = {B}\times {S}\times {m_{\text{token}}}
$$

**Parameters**:

- ${N_L} = 80$, ${H_{\text{KV}}} = 8$ for the assumed GQA architecture, ${d_{\text{head}}} = 128$.
- ${s_{\text{elem}}} = 2$ bytes (FP16).
- Context $= 131{,}072$ tokens.

**Step 1**: Calculate memory per token.

$$
m_{\text{token}} = 2 \times 80 \times 8 \times 128 \times 2 = 327,680 \text{ bytes} \approx 0.33 \text{ MB/token}
$$

**Step 2**: Calculate cache per request.

$$
131,072 \text{ tokens} \times 0.33 \text{ MB/token} \approx 42.9 \text{ GB/request}
$$

**Step 3**: Determine max batch size. Available Memory for KV = 687.2 GB (Total) - 141.2 GB (Weights) - 20 GB (System) = 526.0 GB.

$$
\text{Max Batch} = \left\lfloor \frac{526.0}{42.9} \right\rfloor = 12
$$

**Systems insight**: Even with GQA, whose shared key-value heads the 8-head count in this calculation already reflects, each 128K-context request consumes tens of gigabytes of KV state. This configuration therefore admits only a limited number of concurrent long-context requests. PagedAttention can recover allocation waste, but cannot shrink the attention tensors counted here. Increasing concurrency beyond that limit requires changing the memory budget, cache representation, or placement of state.

### The Fragmentation Problem

^sec-inference-scale-fragmentation-problem-28be

An allocator that reserves a contiguous HBM slab for every sequence’s maximum permitted length strands KV-cache memory in unused reservations and noncontiguous gaps ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-kwon2023|Kwon et al. 2023]]). Traditional contiguous allocation creates two distinct forms of this waste.

Internal fragmentation wastes memory within each allocation. Preallocated memory management reserves room at admission for the prompt plus the permitted output, so a request allowed 4,096 output tokens holds that room even if generation stops after 50. The unused reservation cannot serve another request until it is released. If the output reservation holds 4,096 tokens but the average output uses 100 tokens, 97.6 percent of that output reservation goes unused. Prompt state consumes additional space; this calculation does not give the unused fraction of the combined prompt-and-output allocation.

External fragmentation compounds this problem across allocations. As sequences complete and new ones start, memory becomes fragmented into noncontiguous free blocks. Even with sufficient total free memory, no single block may be large enough for a new maximum-length allocation.

Consider a simplified example with 8 memory slots and maximum sequence length of 4. Fixed-size reservations first create internal fragmentation:

    Time 0: Allocate Seq A (slots 0-3), Seq B (slots 4-7)
            [A][A][a][a][B][B][B][b]
            lowercase = reserved but unused

External fragmentation can arise when the allocator also permits smaller contiguous reservations. In a later state, A and B have finished and released their slots, and two shorter sequences, C and D, hold two-slot reservations, leaving separated gaps:

    Time 1: Active Seq C and Seq D leave two 2-slot gaps
            [ ][ ][C][C][ ][ ][D][D]

    Time 2: Try to allocate Seq E (needs 4 contiguous slots)
            [ ][ ][C][C][ ][ ][D][D]  <- Total free slots = 4, largest block = 2

    Result: enough total free capacity exists, but no contiguous block is large enough.

Under variable sequence lengths, the two effects compound. The vLLM authors measured roughly 60 to 80 percent of reserved KV-cache memory going unused in the prior serving systems they studied, capacity that could otherwise have admitted more sequences ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-kwon2023|Kwon et al. 2023]]).

### PagedAttention

^sec-inference-scale-pagedattention-3c94

The fragmentation example exposes the allocator failure: enough KV-cache capacity can exist in aggregate while no contiguous block is available for the next sequence. PagedAttention fixes that serving problem by treating KV-cache storage like virtual memory rather than a single preallocated slab (perspective [10.1](https://mlsysbook.ai/vol2/10_inference/10_inference.html#psp-inference-analogy-inefficient-hotel) and definition [10.3](https://mlsysbook.ai/vol2/10_inference/10_inference.html#dfn-inference-pagedattention)).

**Systems Perspective 10.1: Analogy: The inefficient hotel**

Consider a hotel storage room with 100 lockers. Each guest may bring up to 10 suitcases, but currently every guest has only one suitcase.

Under maximum-size reservation, the manager reserves 10 lockers for each guest. Ten guests exhaust the 100-locker budget while occupying only 10 lockers; the other 90 remain reserved but unused.

With on-demand allocation, each suitcase receives any free locker, and a directory records which lockers belong to each guest. At the current one-suitcase occupancy, the room can accommodate 100 guests. Additional suitcases still consume real capacity; allocation does not remove the storage limit.

**Definition 10.3: PagedAttention**

***PagedAttention*** is an LLM serving memory management technique that applies virtual memory principles to KV cache allocation, storing attention states in noncontiguous, fixed-size physical blocks.

1.  **Significance**: It eliminates external fragmentation within the fixed-block pool and bounds internal waste to the unused portion of each sequence’s final block. Recovering capacity from contiguous preallocation permits larger concurrent batches; the throughput gain depends on sequence lengths, demand, and the serving bottleneck.
2.  **Distinction**: A contiguous allocation must find a sufficiently large free region; supporting later growth may require reserving extra space or relocating the allocation. PagedAttention uses a block table to map logical sequence indices to physical memory pages, allocating blocks as the sequence grows without requiring adjacent free space.
3.  **Common pitfall**: A frequent misconception is that PagedAttention speeds up *individual token math*. In reality, it is a capacity optimization: it improves *system-level efficiency* by allowing larger batch sizes, though it adds a small indirection overhead for the block-table lookups.

In vLLM ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-kwon2023|Kwon et al. 2023]]), this paged memory layout divides the KV cache into fixed-size pages, using 16-token blocks in the original paper’s default configuration, and allocates them on demand. Whereas contiguous reservation strands non-adjacent free slots when earlier sequences finish, each sequence’s block table maps logical token pages to scattered physical HBM slots as generation proceeds ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^fig-paged-attention|figure 10]]). The block size fixes how many tokens each page holds, so a sequence’s pages need not form one contiguous allocation run.

![[90 Assets/Volume II/10 Inference/KV Cache Fragmentation 518f86418c.svg]]

Figure 10: **KV Cache Fragmentation and the PagedAttention Solution**: The panels replay the eight-slot example from the text. (a) Contiguous reservation holds the maximum length of four slots per sequence, so the slots Seq A and Seq B never fill sit idle (internal fragmentation). (b) After sequences finish, four slots are free but the largest contiguous gap is two, so Seq E, which needs four contiguous slots, cannot be admitted (external fragmentation). (c) PagedAttention maps Seq E’s logical pages through a block table onto any free physical blocks, so the same memory now holds it; only the unfilled tail of its final block remains unused.

^fig-paged-attention

Beyond the fragmentation bounds in the definition, paging gives two further capacity advantages. Sequences grow page by page without worst-case preallocation, and common prefixes across requests can share physical pages directly in memory. Together, these properties turn KV cache capacity into a schedulable resource rather than a fixed per-request reservation. The price is indirection, because custom attention kernels must gather keys and values from noncontiguous blocks through each sequence’s block table. Recovered capacity also raises throughput only when demand fills it. Allocator occupancy is not a throughput measurement, since throughput still depends on decode work, prefill interference, and the latency budget.

### Prefix Caching

^sec-inference-scale-prefix-caching-8e8b

Recomputing the same 2,000-token system prompt, few-shot example block, or shared document on every arriving request burns prefill compute and fills HBM with identical copies of the same key-value tensors. Because many LLM workloads prepend those shared prefixes across thousands of concurrent queries, prefix caching stores the prefix’s KV-cache blocks once and shares them across compatible requests. Reuse requires the same token prefix and the same model computation, including any task-specific weight adapter and other inputs that affect the cached state. The cache key must distinguish those conditions, and the service must restrict sharing to the permitted users or tenants; matching visible text alone is insufficient. In valid block-level sharing ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^fig-prefix-caching|figure 11]]), logical tables for independent requests map common prefix tokens to physical blocks B0–B5, skipping their repeated prefill work while storing request-specific suffix state separately.

![[90 Assets/Volume II/10 Inference/Prefix Caching af66ec319c.svg]]

Figure 11: **Prefix Caching via Block Sharing**: PagedAttention enables efficient prefix caching by allowing multiple sequences’ block tables to point to the same physical blocks for shared content. In this example, the system prompt is stored in blocks 0–5. Request A and Request B map their first six logical pages to these same physical blocks, storing only their unique suffixes in new blocks. Sharing reduces KV memory and repeated prefill computation for workloads with a common context.

^fig-prefix-caching

With PagedAttention, prefix caching uses copy-on-write semantics, in which shared blocks stay shared until a request must write into one, and that request then receives a private copy. Three requests that share a system prompt map their first six logical pages to the same physical blocks:

    System prompt → Physical blocks [0, 1, 2, 3, 4, 5]

    Request A page table: [0, 1, 2, 3, 4, 5, 10, 11]  <- shares prefix blocks
    Request B page table: [0, 1, 2, 3, 4, 5, 12, 13, 14]  <- shares prefix blocks
    Request C page table: [0, 1, 2, 3, 4, 5, 15]  <- shares prefix blocks

All three requests reference the same physical blocks for the system prompt, and their distinct suffixes occupy new blocks. If a shared prefix ends partway through a block, appending a different suffix writes into a shared block, which is the copy-on-write case. In a chatbot deployment where thousands of concurrent users share a long system prompt, sharing those prefix blocks cuts total KV-cache memory by roughly four-fifths (notebook [10.6](https://mlsysbook.ai/vol2/10_inference/10_inference.html#nbk-inference-prefix-caching-at-scale)).

**Napkin Math 10.6: Prefix caching at scale**

**Scenario**: A chatbot service uses a 2,000-token system prompt and serves 1,000 concurrent users. The illustrative model uses multi-head attention with 80 layers, 64 KV heads of dimension 128, and FP16 state. These full-width KV assumptions differ from the grouped-query attention of Llama-70B.

**Without prefix caching**:

- KV cache per user: $2000 + 500\text{ (avg response)} =$ 2,500 tokens
- Total KV cache: 2,500 tokens $\times 1000 \times 2 \times 80 \times 8192 \times 2 =$ 6.6 TB

**With prefix caching**:

- Shared prefix: 2,000 tokens (once)
- Unique per user: 500 tokens
- Total: $(2000 \times 1) + (500 \times 1000) =$ 502,000
- Memory: 502,000 $\times 2 \times 80 \times 8192 \times 2 =$ 1.3 TB

**Result**: Prefix caching yields a 79.9 percent memory reduction in KV cache, a roughly 5× capacity ratio for this fixed request population. Actual admitted concurrency also depends on other memory use, generation lengths, and latency limits.

**Systems insight**: Prefix caching pays off when the prefix hit rate is high because many requests share a long prefix. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^tbl-inference-prefix-caching-workloads|Table 10]] uses illustrative hit-rate envelopes to show where the technique changes serving capacity and where it does not; production sizing must derive the distribution from a request trace.

| **Workload**                     | **Prefix hit rate** | **Memory savings** |
|:---------------------------------|:-------------------:|:------------------:|
| **Chatbot (same system prompt)** |        95%+         |       70–80%       |
| **Document QA (same doc)**       |       80–90%        |       50–70%       |
| **General API (diverse)**        |       20–40%        |       10–30%       |

Table 10: **Illustrative Prefix-Caching Sensitivity**: Assumed prefix hit rates and resulting KV-cache memory savings for three workload shapes. ### KV Cache Compression and Attention Layout

^sec-inference-scale-kv-cache-compression-943a

Even after paged allocation ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-pagedattention-3c94|section 10.7.3]]) eliminates unused reservations and prefix sharing ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-prefix-caching-8e8b|section 10.7.4]]) deduplicates shared prompts, unique active tokens still consume enough HBM per token to cap concurrency at small batch sizes. Shrinking that per-token footprint requires reducing either the bytes stored per element or the number of key-value heads cached per layer. The calculation here starts from a 64-KV-head multi-head attention (MHA) baseline so the grouped query attention subsection can isolate the head-count reduction as a separate architectural lever. For a 70B parameter model with 80 layers, 64 heads, head dimension 128, and sequence length 4096 in FP16, the KV cache requires:

$$
\text{KV cache} = 2 \times 80 \times 64 \times 128 \times 4096 \times 2 \approx 10.7\text{ GB (FP16)}
$$

A single request’s KV cache alone consumes a substantial fraction of the H100’s 80 GB of HBM. For a batch of 8 concurrent requests, the KV cache would require 85.9 GB, leaving no room for model weights or runtime state. Quantization reduces bytes per cached element, while architectural optimization can reduce the number of cached elements. These complementary levers change different factors in the capacity calculation.

#### KV Cache Quantization

^sec-inference-scale-kv-quantization

Weight-only quantization leaves the KV cache untouched. KV cache quantization instead stores cached keys and values in INT8, FP8, or even INT4. Storing the cache payload in INT4 reduces it to approximately 2.7 GB per request, a 4× reduction before quantization metadata and any higher-precision residual state. Recovered memory can admit more sequences, but throughput depends on kernel support, conversion costs, and the latency target. Quality must also be evaluated for the intended contexts.

Cached keys and values also have different distributions from the model weights and from each other. Keys tend to carry outlier magnitudes, entries far larger than the rest, that persist in the same few hidden channels across tokens. Quantizing keys per token would force every channel in a token’s key vector to share one wide scale determined by those hot channels, compressing the remaining channels into only a few quantization levels. Grouping key elements along the token axis within each channel isolates each outlier channel under its own scale. Values lack that fixed channel pattern and can be quantized per token across channels, which lets each new token’s value vector be quantized immediately upon generation without rescaling earlier tokens.

#### Grouped-Query Attention

^sec-inference-scale-gqa

Grouped query attention ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-ainslie2023|Ainslie et al. 2023]]) changes the number of key-value heads cached per layer, while quantization changes bytes per cached element. GQA is a model architecture choice established through training or checkpoint adaptation, not a serving switch that discards heads from an unchanged model. Holding the other cache dimensions fixed, the representative comparison of 64 KV heads under MHA with 8 under GQA gives an 8$\times$ reduction:

$$
\text{KV cache (GQA)} = 2 \times 80 \times 8 \times 128 \times 4096 \times 2 \approx 1.3\text{ GB (FP16)}
$$

At 1.3 GB, the GQA cache occupies less memory than the 10.7 GB required by MHA in this comparison. Combining GQA with INT8 KV cache quantization reduces the payload further, but per-request size still grows with context length. The architectural and numerical changes each require quality evaluation; recovered capacity permits additional sequences only while their execution remains within the service budget.

**Napkin Math 10.7: The precision dividend**

The precision dividend is the gain in maximum batch when lower precision frees memory for KV cache. Computing it first with the 64-head MHA baseline, whose requests carry eight times more KV state than the reference replica’s eight-head GQA cache, and then with the replica’s own GQA cache separates what the attention layout changes from what precision changes.

This comparison uses a conservative decimal HBM budget of 80 GB per GPU, matching the nameplate label rather than the registered byte capacity used by the node estimator.

**Problem**: A team serves a 70B model on 8$\times$ H100 GPUs. Weights in FP16 consume 140 GB (17.5 GB/GPU). KV cache at FP16 consumes 10.7 GB per request. How does quantizing weights to INT4 and KV cache to INT8 change the maximum batch size?

**Before optimization** (all FP16):

- Weights: 17.5 GB/GPU
- Available for KV cache: 80 GB $-$ 17.5 GB = 62.5 GB/GPU
- KV cache per request: 10.7 GB $\div$ 8 $\approx$ 1.34 GB/GPU
- Maximum batch size: $\lfloor$ 62.5 GB divided by 1.34 GB $\rfloor$ $\approx$ 46 requests

**After optimization** (INT4 weights, INT8 KV cache):

- Weights: 17.5 GB $\times (4/16) =$ 4.38 GB/GPU (INT4)
- Available for KV cache: 80 GB $-$ 4.38 GB = 75.62 GB/GPU
- KV cache per request (INT8): 5.4 GB $\div$ 8 $\approx$ 0.67 GB/GPU
- Maximum batch size: $\lfloor$ 75.62 GB divided by 0.67 GB $\rfloor$ $\approx$ 112 requests

**The reference replica’s GQA cache** (same budgets, eight KV heads):

- KV cache per request at FP16: 1.34 GB, or 0.17 GB/GPU, giving a maximum batch of about 372 requests with FP16 weights
- KV cache per request at INT8: 0.08 GB/GPU, giving about 901 requests with INT4 weights, a dividend of 2.4×

**Systems insight**: The two layouts yield the same multiplicative dividend, because each maximum batch is free memory divided by per-request cache, and precision changes both quantities by the same factors whatever the head count. The layout sets the absolute count, and at either precision the MHA replica admits roughly an eighth as many requests. In both layouts, compressing the cache does more for admission than compressing the weights, since halving per-request state doubles the count while INT4 weights free only the weight share of each GPU. At serving scale the recovered headroom is an admission budget, not yet throughput. The scheduler converts it into completed requests only while the larger batch still meets TPOT, and the counts here omit runtime allocations and headroom, so they are optimistic upper bounds on what admission control should allow.

### Speculative Decoding

^sec-inference-scale-speculative-decoding-c438

When a lightly loaded replica serves one or a few interactive streams, batching has no other requests to share each weight read with, so every generated token pays the full latency of streaming the target model’s weights from HBM. While KV compression and GQA shrink the state each decode step reads, speculative decoding raises the useful work each step performs within a single request. A small draft model proposes ${K}$ tokens, and the target model verifies all of them in one parallel forward pass ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-leviathan2023speculative|Leviathan et al. 2023]]; [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-chen2023accelerating|Chen et al. 2023]]). That pass streams the target’s weights once, as a single decode step does, so it processes ${K}$ candidate positions for roughly the weight traffic of one token. This is the reuse that batching buys, drawn from one request’s future tokens instead of from other requests, and it moves the decode operating point up the bandwidth slope toward the ridge.

On a shared time axis ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^fig-speculative-decoding|figure 12]]), standard decoding uses four target passes to emit four tokens. In the speculative round, the draft model proposes ${T}_1$ through ${T}_4$ sequentially and the target evaluates those positions in one pass; three drafts are accepted, and the first rejected token, ${T}_4$, is replaced by ${T_4'}$ sampled from the target. The shorter timeline holds only when drafting, verification, and correction together cost less than the target passes they replace. If too many drafts are rejected, the target streams its weights and keeps little of the work; if the draft model is too expensive, its own sequential passes consume the time that one-pass verification saved.

![[90 Assets/Volume II/10 Inference/Speculative Decoding 8a58e759b4.svg]]

Figure 12: **Speculative Decoding Process**: Instead of generating tokens sequentially with the large target model, a small draft model proposes a sequence of ${K}$ tokens. The target model verifies all ${K}$ tokens in a single parallel forward pass. Drafted tokens that pass the acceptance test are emitted together; the first rejected token triggers a corrected sample and discards the remaining draft.

^fig-speculative-decoding

[Algorithm 2](https://mlsysbook.ai/vol2/10_inference/10_inference.html#algo-speculative-decoding) makes the acceptance test precise. After the single target pass, each drafted token is accepted with probability $\min(1, {p_{\theta}}/{q_{\phi}})$, and a rejection resamples from the normalized positive residual $({p_{\theta}}- {q_{\phi}})_+$, so the emitted sequence is distributed exactly as the target model would have produced it unaided. That exactness is what lets a serving system trade draft-model compute for latency without changing the output distribution. Approximate verification rules, which accept drafts the target merely ranks highly, do not inherit the guarantee.

$p_\theta(\cdot \mid \cdot)$

The draft acceptance rate ${\alpha_{\text{acc}}}$ determines how much proposed work survives. Under a simplified model in which each drafted position is accepted independently with that probability, a round emits its accepted prefix plus one target-sampled token, either the correction at the first rejection or the extra token after full acceptance. Each draft position contributes a token only if every earlier draft was accepted, so each successive position adds one more factor of ${\alpha_{\text{acc}}}$ and the expectation is a geometric series over the ${K}+1$ possible emissions. [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^eq-speculative-expected-tokens|Equation 6]] gives its closed form, the expected output of one verification round with ${K}$ drafted tokens:

$$
\mathbb{E}[{N_{\text{emit}}}] = \frac{1-{\alpha_{\text{acc}}}^{{K}+1}}{1-{\alpha_{\text{acc}}}} \tag{6}
$$

^eq-speculative-expected-tokens

The target streams its weights once per round whatever the acceptance, so the weight traffic amortized per emitted token falls in proportion to [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^eq-speculative-expected-tokens|equation 6]]. Low acceptance can make generation slower than ordinary decoding, because rejected drafts still cost drafting and verification time. That mechanism belongs to one replica. A serving fleet must decide when to enable speculation, how its memory cost interacts with admission, and whether it improves the endpoint’s SLO-compliant capacity.

Those decisions start from how steeply the benefit falls with acceptance. The following calculation assumes ${K}= 5$ draft tokens, a draft step 20$\times$ faster than a target decode step, and a verification pass costing one target decode step, which isolates sensitivity to acceptance. A round then costs ${K}$ draft steps plus one verification step, and the speedup divides the expected tokens emitted per round by that round cost, with the round cost measured in target decode steps:

High acceptance (${\alpha_{\text{acc}}}= 0.9$) yields an expected 4.69 tokens per verification round for a 3.7× speedup. Medium acceptance (${\alpha_{\text{acc}}}= 0.7$) delivers 2.94 tokens per round for a 2.4× speedup. Low acceptance (${\alpha_{\text{acc}}}= 0.5$) drops progress to 1.97 tokens per round, yielding a modest speedup of 1.6×.

![[90 Assets/Volume II/10 Inference/Vol2 Inference Margin 001 cd3421a6eb.svg]]

*Three slate-gray horizontal bars on a linear scale: 90 percent acceptance gives 3.7 times faster decoding, 70 percent gives 2.4 times, and 50 percent gives 1.6 times. A dashed vertical line at 1 times marks no gain.*

*Speedup shrinks quickly as draft acceptance falls.*

Acceptance depends on the draft-target pair, sampling policy, and request distribution. The preceding calculations are sensitivity cases, not fixed acceptance rates for chat, reasoning, or code generation. A serving fleet must measure acceptance and useful token throughput for its actual traffic before selecting a speculation policy, and that policy must answer three serving concerns: memory, the SLO, and change over time.

The first concern is memory. The draft model is not free state. It requires memory for weights, and each in-flight request that uses it reserves additional draft KV state. Pairing a 7B draft model with a 70B target adds roughly 14 GB of FP16 weights per replica plus per-request draft cache. When colocated with the target, this memory overhead competes directly with the KV-cache admission budget developed in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-kv-cache-wall|section 10.7.1]]; every gigabyte reserved for the draft is unavailable to target requests. Under a binding memory limit, that reservation lowers maximum concurrency. Placing the draft on separate devices preserves target memory at the cost of additional hardware and communication. The admission controller and the speculation policy therefore require a joint capacity and latency evaluation.

The second concern is which service-level objective the endpoint must meet. At sufficient acceptance, speculation can reduce TPOT, while draft execution and cache residency reduce admission capacity, so the scheduler should compare SLO-compliant goodput with and without speculation under the intended load. TTFT needs separate measurement because draft setup and prefill can add work before the first response token.

The third concern is that acceptance and load change over time. Batch size moves the payoff as well as acceptance does. Verification is cheap only while decode leaves compute idle, and a larger batch consumes that headroom, so the same draft configuration can cross from a gain to a loss as concurrency rises. Variable accepted lengths also add scheduler work. The crossover batch must be measured for each draft-target pair and machine rather than inferred from a batch-one result. A scheduler can enable speculation when measured TPOT or goodput improves and disable it when verification cost outweighs accepted progress. Disabling draft execution, however, frees neither the resident draft weights nor the draft KV pages. Recovering that capacity requires unloading the weights and ending or migrating the speculative state. Self-speculative decoding, Medusa prediction heads ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-cai2024medusa|Cai et al. 2024]]), and lookahead decoding change this budget, and each needs its own quality, acceptance, and resource evaluation.

### Preemption and the Victim Policy

^sec-inference-scale-vllm-architecture-9b84

When active sequences grow their contexts until every free KV-cache page is claimed, the replica can neither advance those sequences nor admit a higher-priority arrival without evicting a sequence that is already running. Iteration-level admission removes the batch-barrier form of head-of-line blocking, because finished sequences leave and waiting ones join at every iteration boundary. Memory pressure can still produce head-of-line blocking under strict first-come-first-served (FCFS) order, because a waiting request too large for the free KV pages holds back smaller requests that would fit. Once the KV pool fills, admitting a waiting request or extending an active one means taking capacity from a running sequence.

Preemptive scheduling allows the system to stop allocating decode iterations to one request so that another can run. Preemption is practical at token boundaries, but it is not free. The scheduler must retain the request’s KV pages in HBM, swap them to host memory, or discard them and repeat prefill when the request resumes. A useful victim policy compares those three costs with the waiting request’s remaining deadline rather than preempting at a fixed generation length. Retaining state consumes scarce capacity, swapping consumes interconnect bandwidth, and recomputation consumes prefill compute; under heavy load, rejecting low-priority work can cost less than repeatedly moving or rebuilding its state.

### KV-Cache Budgeting and Eviction

^sec-inference-scale-memory-management-best-practices-67e2

Admitting sequences up to a naive average-length estimate without reserving headroom for context growth forces the replica into constant mid-generation preemptions or out-of-memory crashes. Effective KV-cache management therefore begins with capacity accounting rather than an eviction policy. The serving process first reserves memory for weights, activations, runtime overhead, and safety headroom, then treats the remaining HBM as a managed pool for active sequences:

    Available GPU memory = Total - Weights - Activations - Overhead
    KV pool size = 0.9 * Available  # Leave 10% headroom

    Max concurrent sequences = KV pool size / (avg_seq_length * KV bytes per token)

That budget estimates how many sequences can coexist, but an average length does not reserve space for future growth. Admission must account for the admitted requests’ remaining budgets. LRU eviction can reclaim retained prefix blocks that no active request references. Reclaiming an active sequence’s state instead requires a preemption decision, made with the victim policy of [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^sec-inference-scale-vllm-architecture-9b84|section 10.7.7]]. What capacity accounting adds is the observation that freeing the most bytes is not necessarily the cheapest recovery, because the largest sequence is also the most expensive to swap or rebuild.

**Example 10.4: KV cache memory hierarchy**

**Scenario**: A multi-tenant LLM serving system experiences KV-cache HBM exhaustion (80 GB limit) during peak concurrency.

**Diagnosis**: Pure HBM allocation limits node concurrency to 50 active sequences in this scenario. Implementing a 3-tier memory hierarchy (HBM $\to$ CPU DRAM $\to$ Non-Volatile Memory Express (NVMe) SSD) allows swapping inactive sequence pages to CPU DRAM or NVMe. The illustrative swap budgets of 1–5 ms and 10–50 ms, respectively, require validation for the bytes transferred, effective bandwidth, and contention; they are not fixed properties of the storage tiers.

**Systems lesson**: In this scenario, multi-tier paging raises retained sequence capacity from 50 to 500, while the active HBM-resident set remains limited to 50. Suspended sequences must be restored before execution resumes under this policy. The extra retention does not establish a throughput gain; restoration costs must fit the affected requests’ deadlines. Streaming active state from another tier would be a different execution policy with transfer costs on the decode path.

### Adapter State and Locality

^sec-inference-scale-lora-multi-tenancy

Deploying a separate copy of a 140 GB base model for each of 10,000 fine-tuned tenants is prohibitive in HBM, yet fetching a tenant’s weight delta from host memory on the critical path stalls every decode step. Alongside the KV-cache attention state of concurrent sequences, adapter serving therefore adds a second claim on the replica’s memory and bandwidth budget. A low-rank adaptation (LoRA) adapter is a user- or task-specific weight delta that must be available when its request executes. It stores that delta as the product of two thin matrices, so it holds far fewer values than the weight matrix it modifies. LoRA modifies a shared base model without copying all of its weights: the serving process keeps the 140 GB base resident once while loading the adapters needed by active requests. Whether adapter storage or transfer becomes limiting depends on the active adapter mix, ranks, and reuse.

**Systems Perspective 10.2: The context switch of machine learning**

Adapter locality becomes a performance constraint when a scheduled request needs weights that are not resident. Loading those weights from host memory resembles part of an operating-system context switch, because execution must wait for the required state unless transfer overlaps other useful work. An adapter already in HBM need not be transferred from the host on every generation step. Coordinating admission with adapter placement can reduce these stalls, while grouping requests by adapter can improve reuse at the cost of waiting for compatible work. The policy must balance locality against the latency and fairness of less frequent adapters.

#### Multi-LoRA Serving and Batched Adapter Execution

^sec-inference-multi-lora-serving

In multi-tenant environments, thousands of fine-tuned adapters share a single base foundation model. For a linear projection layer with base weights ${\mathbf{W}}_0 \in \mathbb{R}^{{d_{\text{out}}} \times {d_{\text{in}}}}$, an adapter ${k}$ parameterizes the forward transformation using low-rank decomposition matrices ${\mathbf{A}}_k \in \mathbb{R}^{{r}_k \times {d_{\text{in}}}}$ and ${\mathbf{B}}_k \in \mathbb{R}^{{d_{\text{out}}} \times {r}_k}$ with rank ${r}_k \ll \min({d_{\text{in}}}, {d_{\text{out}}})$ (typically ${r}\in \{8, 16, 64\}$), as formulated in [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^eq-lora-forward|equation 7]]:

$$
{\mathbf{y}}= {\mathbf{x}}{\mathbf{W}}_0^T + \frac{{\gamma}_k}{{r}_k} {\mathbf{x}}{\mathbf{A}}_k^T {\mathbf{B}}_k^T \tag{7}
$$

^eq-lora-forward

where ${\mathbf{x}}\in \mathbb{R}^{1 \times {d_{\text{in}}}}$ is a row vector, ${\mathbf{y}}\in \mathbb{R}^{1 \times {d_{\text{out}}}}$, and ${\gamma}_k$ is a fixed scaling factor, the hyperparameter usually written ${\alpha}$ in LoRA papers and renamed here because ${\alpha}$ already denotes startup latency and draft acceptance in this chapter. Each adapted projection adds ${r}_k({d_{\text{in}}} + {d_{\text{out}}})$ parameters instead of a full ${d_{\text{in}}}{d_{\text{out}}}$ weight matrix. The resident adapter budget therefore depends on which layers are adapted, their dimensions and ranks, precision, and the number of simultaneously loaded tenants.

↪ How low-rank adapters are trained, and how their rank is chosen under a device’s memory and energy budget, is developed in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.05 Model Adaptation#^sec-edge-intelligence-lowrank-techniques-4570|Low-rank techniques]]**.

Packing requests with different adapters into one batch lets the base projection ${\mathbf{X}}{\mathbf{W}}_0^T$ execute as one shared dense general matrix multiply (GEMM), but a naive implementation then launches a separate small kernel for each request’s adapter $({\mathbf{A}}, {\mathbf{B}})$. Hundreds of such launches per layer make host dispatch and launch latency significant even when each adapter performs little arithmetic, and the small kernels leave GPU streaming multiprocessors (SMs) underused. The following batched operation removes the need for one launch per request.

**Definition 10.4: Batched gather-matrix-vector multiplication (BGMV)**

***Batched gather-matrix-vector multiplication (BGMV)*** is a GPU kernel operation that batches matrix-vector products across distinct adapters, dynamically gathering adapter weights from a memory pool according to a per-token adapter index vector.

1.  **Significance**: It reduces per-request kernel launch overhead in multi-adapter serving, allowing different adapters to share kernel launches. The remaining overhead depends on adapter ranks, batch composition, and memory locality.
2.  **Distinction**: A single dense GEMM applies one weight matrix across its input rows. BGMV gathers the adapter-specific weight slice for each element, combining distinct matrix-vector products in one kernel operation.
3.  **Common pitfall**: Batched execution does not itself solve allocation waste. Loading and unloading differently sized adapters can fragment a contiguous allocator. Paged adapter storage addresses that separate problem, provided the execution kernels support its layout.

Systems such as Punica ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-chen2023punica|Chen et al. 2024]]) and S-LoRA ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-lin2023slora|Sheng et al. 2024]]) address launch overhead and adapter memory through two architectural mechanisms (definition [10.4](https://mlsysbook.ai/vol2/10_inference/10_inference.html#dfn-inference-multi-lora-bgmv)):

##### Batched Gather-Matrix-Vector (BGMV) Kernels

^sec-inference-bgmv-kernel

Instead of launching separate kernels for every request, batched or segmented gather-matrix-vector operations group different adapters within each projection. Down-projection and up-projection can use separate kernels; Punica distinguishes shrink and expand operators ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-chen2023punica|Chen et al. 2024]]). The scheduler builds a per-request adapter index, and each kernel uses it to gather a request’s activation row and its adapter’s matrices, apply the rank-${r}$ down- and up-projections of [[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.08 Memory and Decode-Time Management#^eq-lora-forward|equation 7]], and add the resulting delta to the shared base projection’s output. The gain must be measured against the actual adapter mix; irregular access and small ranks can still limit achieved bandwidth.

##### Unified Paged Adapter Memory Management

^sec-inference-paged-adapter-memory

S-LoRA ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-lin2023slora|Sheng et al. 2024]]) jointly manages adapter weights and KV state in a unified GPU memory pool. Its page holds a vector along the shared hidden dimension, rather than a fixed operating-system-sized byte allocation. Adapter matrices ${\mathbf{A}}_k$ and ${\mathbf{B}}_k$ occupy noncontiguous pages, allowing adapters of varying ranks (${r}\in \{8, 16, 32, 64\}$) to share capacity with growing KV caches. Paging reduces fragmentation; both kinds of state still consume the same finite pool.

The published design keeps adapters in host memory and uses the waiting queue to predict which weights the next batch will need. Prefetching overlaps adapter transfers with current execution when sufficient time and free GPU memory are available. A cache miss whose transfer cannot be hidden still delays the affected request.

Across a tensor-parallel group, S-LoRA aligns each adapter with the base layer’s column- or row-parallel split (**[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.06 Model Parallelism#^sec-distributed-training-systems-systems-tensor-parallelism-d76e|Tensor parallelism]]**) and communicates only the ${r}_k$-dimensional intermediates rather than full ${d_{\text{out}}}$-dimensional activations. The layout avoids replicating adapter weights across GPUs at the price of one extra collective on the small rank-${r}_k$ intermediate.

Which collective that is depends on the base layer’s split. When the base layer is column-parallel, the input ${\mathbf{x}}$ is already replicated across GPUs, so S-LoRA partitions ${\mathbf{A}}_k$ across the rank dimension, uses an AllGather to assemble the full ${r}_k$-dimensional intermediate on every GPU, and partitions ${\mathbf{B}}_k$ across the output columns to match the base weights. When the base layer is row-parallel, the input ${\mathbf{x}}$ arrives partitioned across the input dimension, so S-LoRA splits ${\mathbf{A}}_k$ along that same input dimension, uses an AllReduce to sum the partial ${r}_k$-dimensional vectors ([[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.20 Source References#^ref-lin2023slora|Sheng et al. 2024]]), and applies ${\mathbf{B}}_k$ before the final output assembly shares the base layer’s own collective.

KV pages and adapter deltas share HBM with the base weights, so every byte freed in one allocation can admit work in another. When a request claims that memory, and how fast it then uses it, depends on the phase it is in: prefill builds a request’s cache in one pass, while decode extends it one token at a time.
