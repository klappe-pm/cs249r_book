# V2-01.03 From Single Node to Fleet

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01 Introduction|V2-01 Introduction]]

^sec-vol2-introduction-engineering-crux

Inside one H100 server, NVLink moves tensors between accelerators at 450 GB/s in each direction per accelerator. Once a training job spans racks, the same tensors leave through an InfiniBand NDR port at 400 Gb/s (50 GB/s) in each direction, a bandwidth step down of roughly 9× for an accelerator served by one such port. That step illustrates a general pattern. The layered structure of an ML system persists across scale, while the physics at each layer changes.

The **fleet stack** names the fleet’s layers by grouping them into four bands, Infrastructure at the bottom, then Distribution, Serving, and Governance at the top, with two rows in each ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^fig-fleet-stack|figure 4]]). At the bottom, the hardware substrate of one node grows into the Infrastructure band, whose Facility and Accelerators row houses many nodes and whose Fabric and Storage row joins them with an RDMA fabric spanning racks. There the binding constraint can shift from the memory wall to the network wall as network congestion and message-passing latency consume a growing share of step time. Efficient data movement inside each node remains a prerequisite, because a fleet of underutilized nodes only multiplies the waste. One layer up, system software (a single CUDA runtime managing PCIe direct memory access (DMA)) becomes the Distribution band. This band holds the NVIDIA Collective Communications Library (NCCL) and RDMA libraries that coordinate thousands of processes across the fabric, together with the schedulers that place distributed jobs and the recovery machinery that restarts them.

![[90 Assets/Volume II/Shared Figures/Fleet Stack dfae3bfd77.svg]]

Figure 4: **The Fleet Stack**: The organizing framework for this book, eight rows grouped into four bands, one band per part. Each band is labeled with its part number and a short functional name for that part, and each row lists what it holds beside the icon that marks it in the chapter margin stacks; the Reliability & Control row, for example, is where orchestration, scheduling, and recovery live. Capabilities decided in a lower band constrain the choices available in the bands above it. The same stack, shaded to show each chapter’s focus, appears beside the Purpose of every chapter.

^fig-fleet-stack

The upper bands add responsibilities rather than replace the familiar software layers. The ML framework (PyTorch or JAX executing a training loop on one node) remains part of model execution. The Serving band adds request handling and deployment pipelines that manage rolling releases across the fleet. Applications also remain, while the Governance band sets security, robustness, sustainability, and responsible AI requirements for their operation. The full stack and its eight rows, the map that organizes the rest of this book, return in [[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.07 The Fleet Stack and the Lighthouse Archetypes#^sec-vol2-introduction-foundational-concepts|section 1.6]]. The stack identifies where a design decision belongs; C$^3$ identifies how that decision affects execution time.

A map of layers does not by itself explain why the same decision behaves differently once it spans a fleet. Four changes separate a fleet from a larger server: synchronous coupling turns independent tasks into a shared step, the facility itself becomes the computer, communication can dominate the step, and failure becomes routine. The scale moment quantified that last change, and its availability model follows with the other constraints of scale in [[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.05 Constraints of Scale#^sec-vol2-introduction-reliability-gap|section 1.4.1]]. Archetype A (GPT-4/Llama-3), the large-language-model workload of the book’s canonical roster ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.07 The Fleet Stack and the Lighthouse Archetypes#^sec-vol2-introduction-archetypes|section 1.6.1]]), runs on a reference cluster of NVIDIA H100 accelerators and makes each change concrete where a chapter needs it.

### Independent Tasks Vs. Synchronous Training Steps

^sec-introduction-traditional-vs-ml-fleet-dynamics-c43e

When one worker in a MapReduce batch job fails or slows down, the scheduler can retry its task alone while the rest of the cluster keeps making progress. When one worker in a synchronous training job slows by 10 percent on the critical path (the chain of dependent work that sets the step’s length), every other accelerator waits at the step barrier and the whole job slows by nearly 10 percent. Many distributed systems isolate work into tasks or requests so that one failure need not stop unrelated work: **MapReduce** ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.12 Source References#^ref-dean2004mapreduce|Dean and Ghemawat 2004]]) partitions an input into map tasks and combines their outputs in reduce tasks, both of which can be retried; Apache Spark ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.12 Source References#^ref-zaharia2016|Zaharia et al. 2016]]) processes data in parallel stages that exchange results at explicit shuffle boundaries; and a web microservice handles requests whose failures can be isolated. Search engines and banking databases use other forms of replication, partitioning, and coordination; they are not uniformly independent or asynchronous. The useful contrast is therefore between failure domains (what a single fault can stop) and coupling patterns, not between “traditional” and ML systems.

Large synchronous training jobs operate under **synchronous tight coupling**, in which all required workers must finish one shared step before any of them can begin the next. Parameter-server architectures ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.12 Source References#^ref-li2014|Li et al. 2014]]), which keep the model on dedicated servers, and collective runtimes manage distributed state, but synchronous optimization updates a large shared model state across thousands of accelerators at every step rather than completing independent one-shot tasks. At each synchronization point, progress can depend on the slowest participating worker, and communication-heavy partitions can also become bisection-bandwidth bound because large gradient or activation tensors cross the network every step. These properties do not invalidate established recovery techniques; they increase recovery cost and restrict which replication, re-execution, and consistency strategies preserve useful training progress.

↪ The barrier that makes every update wait for every required contribution, and the failure modes it creates, are developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06.04 Data Parallelism#^sec-distributed-training-systems-systems-barrier-semantics-failure-modes-5c94|Barrier semantics and failure modes]]**.

The two execution pathways differ at the point of failure ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^fig-traditional-vs-ml-fleet|figure 5]]). In MapReduce, a failed map task is retried on its own while its peers complete. In synchronous data-parallel training, every worker holds a full copy of the model, spread over as many accelerators as its training state needs, and processes a different slice of each batch. Before the shared parameter update can occur, every worker must contribute its gradient to an AllReduce, a collective operation that combines the gradients of all workers and returns the result to each of them. A slow map task can delay downstream reduction and job completion, but other map tasks finish without waiting; in synchronous training, by contrast, healthy workers sit idle whenever a straggler delays the collective.

![[90 Assets/Volume II/01 Introduction/Traditional Vs ML Fleet 59a8f05678.svg]]

Figure 5: **Retryable Tasks vs. Shared Training Steps**: Map tasks (left) deliver their outputs independently, so a failed task is re-run on its own while the others finish; its missing output delays only the reducers that need it. In synchronous data-parallel training (right), the AllReduce needs every worker’s gradient before the shared update can proceed, so a slow worker on the critical path holds the whole step and the healthy workers wait. How much the step stretches depends on overlap and the other costs of the step.

^fig-traditional-vs-ml-fleet

The collective barrier in [[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^fig-traditional-vs-ml-fleet|figure 5]] is why MapReduce-style localized task re-execution cannot be transferred directly to tightly coupled training. When all workers advance a single shared parameter step, recovery must restore mutually consistent model, optimizer, and input state across every participating node before coordinated execution can resume.

↪ Coordinated checkpointing, which captures that mutually consistent state so that recovery need not search for it, is developed in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-reliability-checkpoint-coordination-patterns-f670|Checkpoint coordination patterns]]**.

### The Shift to the Warehouse-Scale Computer

^sec-introduction-shift-warehousescale-computer-2ccd

Once a single training job spans thousands of accelerators across dozens of racks, a facility’s cooling loops, power distribution, and bisection bandwidth can cap step throughput long before any individual chip reaches its arithmetic limit. A tightly coupled data-center fleet therefore demands the **warehouse-scale computer (WSC)**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.13 Footnotes#^fn4|⁴]] perspective. Where a machine-centric view treats the data center as a building that houses many separate servers, the warehouse-scale view treats the data center itself as one computer. Single-node abstractions then map directly onto distributed infrastructure: the network fabric functions as the system bus, distributed storage serves as the local disk, and the fleet orchestrator acts as the operating system.

For this data-center regime, the engineering boundary extends from local execution to the shared power, network, and recovery systems that sustain the entire facility. The warehouse-scale computer, the standard design for large models, moves data between chips over a network. Wafer-scale engines, single processors built from an entire silicon wafer, aim to keep that movement on the wafer instead, trading a cluster’s modularity for on-chip bandwidth (**[[01 Books/Volume II - Scaling/01 The Fleet/02 Compute Infrastructure/V2-02.03 The Accelerator#^sec-compute-wafer-scale|Wafer-scale engines]]**). Both designs answer the same constraint, the cost of moving data between chips, from opposite directions.

### Communication Dominance and the Network Wall

^sec-introduction-communication-becomes-dominant-e1b6

On a single GPU, a dense training step keeps its gradients in local memory, so matrix multiplications dominate step time and inter-node communication is zero. Once that workload spans racks in a warehouse-scale computer, every step must exchange gradients or activations across inter-server links before parameters can update, which can make communication the dominant cost and expose the network wall of the scale moment.

![[90 Assets/Volume II/01 Introduction/Vol2 Introduction Margin 001 8abf2e5038.svg]]

*Three horizontal bars on one linear scale: a blue bar for the 700 GB FP32 gradient, a violet ring-traffic bar for FP32 twice as long and marked about 2×, with a white dashed tick at one gradient length, and a violet ring-traffic bar for FP16 the same length as the gradient, marked about 1×.*

*Ring AllReduce moves about twice the gradient per step; 16-bit gradients halve it.*

Distributed data-parallel training synchronizes gradients across workers after each batch. For a model with 175B parameters, FP32 gradients occupy about 700 GB before any collective algorithm is applied. Ring AllReduce arranges the AllReduce exchange among neighbors in a logical ring. With ${N}$ workers, each worker sends roughly $2({N}-1)/{N}$ times the gradient tensor size and receives the same amount across the reduction and distribution phases (**[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-collective-operations-collective-operations-ring-allreduce-ffce|Ring AllReduce]]** derives this factor). For large ${N}$ the factor approaches two, so each worker moves about twice the FP32 gradient per step, and half that, about 700 GB, when mixed-precision training exchanges 16-bit gradients. Network traffic therefore depends on precision, worker count, collective implementation, and partitioning. On slower interconnects or partitions with little computation per communicated byte, it can consume a large fraction of each iteration rather than a negligible one. Notebook [1.1](https://mlsysbook.ai/vol2/01_introduction/01_introduction.html#nbk-introduction-coordination-energy-tax) later prices the gradient exchange of the 175B reference job in seconds per step.

↪ The ${\alpha}$-${\beta}$ communication model, with the per-interconnect latency and bandwidth parameters that turn a link’s specifications into a predicted transfer cost, is developed in **[[05 Reference/Volume II - Scaling/V2 Communication Foundations#^sec-appdx-comm-foundations-alpha-beta|The α-β Communication Model]]**.

Communication’s share of the step grows as a fixed workload spreads across more devices, because each worker’s local computation shrinks while its gradient exchange does not. Across illustrative tiers from 8 to 4,096 GPUs, compute can fall from 75 percent of the step to 20 percent as communication widens ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^fig-compute-comm-timeline|figure 6]]). The fractions are assumed regimes rather than measurements. Gradient size, local batch size, partition topology, and overlap determine where the critical path actually lies, so it must be measured at each scale.

![[90 Assets/Volume II/01 Introduction/Cell 19 Output 1 ab9111515c.png]]

Figure 6: **The Compute-Communication Timeline**: Illustrative fractions show how exposed communication and synchronization can take a growing share of a training step as a fixed workload spreads across more devices. The fractions are assumed scenarios, not measurements or predictions for a particular model or cluster; they motivate measuring the critical path at each scale.

^fig-compute-comm-timeline

This exposed transfer cost explains why distributed training systems optimize communication so aggressively. Distributing work also distributes state that must move or be kept consistent. Horovod, for example, runs Ring AllReduce and fuses many small gradient tensors into fewer large transfers, so that the fixed cost of starting each exchange is paid fewer times ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.12 Source References#^ref-sergeev2018horovod|Sergeev and Balso 2018]]). Splitting each layer across devices, as Megatron-LM does with tensor parallelism ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.12 Source References#^ref-shoeybi2019megatron|Shoeybi et al. 2019]]), and sharding optimizer state across workers, as ZeRO does ([[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.12 Source References#^ref-rajbhandari2020|Rajbhandari et al. 2020]]), trade per-device memory for different traffic patterns. Gradient sparsification (sending fewer gradient bytes) and 3D parallelism (partitioning data, tensor, and pipeline dimensions across different fabric tiers) change how much data moves and where it moves. **[[01 Books/Volume II - Scaling/02 Distributed ML/06 Distributed Training/V2-06 Distributed Training#^sec-distributed-training-systems|Distributed Training]]** develops these partitioning methods. Overlapping a transfer with independent computation instead reduces exposed waiting time without changing how many bytes move. The design decision at this stage is which cost prevents progress; selecting a particular mechanism requires the workload and fabric models developed later.

### Communication Intensity (The CI Ratio)

^sec-vol2-introduction-ci-ratio

If arithmetic intensity governs where a single accelerator stalls, **communication intensity (CI)** governs where a fleet stalls. On a single accelerator, the Roofline Model determines whether a kernel is compute-bound or memory-bound. At fleet scale, the same analysis extends to the network.

[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.03 From Single Node to Fleet#^eq-ci-ratio|Equation 1]] defines communication intensity as the ratio of data moved across the network to the operations performed locally. The numerator counts bytes and the denominator counts operations for the same worker and interval, such as one training step; the ratio therefore has units of bytes per operation.

$$
{\text{CI}} = \frac{{M}}{{O}} \tag{1}
$$

^eq-ci-ratio

where ${M}$ is the number of bytes the worker moves across the network and ${O}$ is the number of operations it performs locally in the same interval. A comparison must also state whether it counts sent bytes, received bytes, or both.

![[90 Assets/Volume II/01 Introduction/Vol2 Introduction Ci Knee e515522fed.svg]]

*Step time on the vertical axis against communication intensity in bytes per operation on the horizontal axis. The line stays flat, meets a red dot on a dashed red vertical line labeled fabric balance, then rises in a straight line.*

*Past the fabric balance point, step time grows with communication intensity.*

Low communication intensity describes compute-heavy workloads whose accelerators spend most of their time doing math, so scaling is comparatively easy. High communication intensity describes workloads whose bytes per operation approach or exceed the hardware’s fabric balance, the ratio of per-worker network bandwidth to peak arithmetic throughput. Past that balance point, network transfers take longer than the local computation they accompany. Fabric balance plays the role of the ridge point with the ratio flipped, so a workload approaches the network limit as its communication intensity rises, whereas a kernel approaches the memory limit as its arithmetic intensity falls.

Splitting a fixed batch across still more accelerators shrinks the local operations ${O}$ per worker while leaving gradient traffic ${M}$ in place or adding collective overhead, which raises ${\text{CI}}$ further and can make the step slower rather than faster. The balance point is configuration-specific because it depends on both local compute throughput and effective network bandwidth. When the workers’ traffic must cross the fabric’s narrowest cut, that effective bandwidth is each worker’s share of the bisection bandwidth, so past the balance point the cut, rather than the accelerator, is the limit.

The 175B reference job gives the ratio a concrete value. [[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.07 The Fleet Stack and the Lighthouse Archetypes#^sec-introduction-archetype-gpt4llama3-b02f|Section 1.6.1.1]] fixes that job as Archetype A’s running instance, with 1,024 H100 GPUs, each data-parallel worker a replica of the model spread over 64 GPUs, and a global batch of 1,536 sequences per step. Each of the 16 replicas therefore processes 96 sequences, or 196,608 tokens, per step. Dividing both the replica’s traffic and its work among its GPUs leaves the ratio unchanged, so it can be computed per GPU. Each GPU’s share of the work is about six FLOPs per parameter per token, two in the forward pass and four in the backward pass (**[[05 Reference/Volume II - Scaling/V2 Single-Machine Foundations#^eq-appdx-dam-training-flops|equation 4]]**), or $3.2 \times 10^{15}$ FLOPs, while its 16-bit ring AllReduce of its gradient slice across the replicas moves about 10.3 GB. The communication intensity is therefore about $3.2 \times 10^{-6}$ bytes per FLOP. An H100 on one 400 Gb/s InfiniBand link has a fabric balance of $5.1 \times 10^{-5}$ bytes per FLOP, its link bandwidth divided by its peak arithmetic rate, so the job sits at about 6 percent of balance. At line rate and peak throughput, the gradient exchange takes only that fraction of the time the computation takes, which leaves the job far from the network wall and dominated by computation.

Spreading the same job over 8,192 GPUs moves it toward the wall. With the global batch fixed, each of the 128 replicas processes only 12 sequences per step, so each GPU’s local work shrinks by the same 8× as the cluster grows, to $4.0 \times 10^{14}$ FLOPs. Its ring traffic barely changes, rising to 10.9 GB as the ring factor approaches two. Communication intensity climbs 8.5× to $2.7 \times 10^{-5}$ bytes per FLOP, about 53 percent of the same balance, so the exchange now takes about half as long as the computation at peak and must be hidden by overlap or appear in every step. The cost of keeping replicas in step grows with the fleet because each accelerator has less local work to set against an exchange of nearly fixed size. These values are modeled rather than measured, and they count only the data-parallel exchange that crosses the fabric; tensor-parallel traffic stays on each node’s NVLink. The ratio describes workload demand; the fabric and execution schedule determine how much of that demand delays progress. Methods that send fewer bytes, such as gradient sparsification, lower the ratio itself, whereas overlap leaves the ratio unchanged and only hides exposed time.

↪ The communication-computation ratio, and the threshold beyond which communication can no longer hide behind computation, are developed in **[[05 Reference/Volume II - Scaling/V2 Fleet Foundations#^sec-appdx-fleet-foundations-comm-compute-ratio|The communication-computation ratio]]**.

Communication costs, together with the recovery costs quantified at the scale moment, describe how a fleet executes work. Neither explains what drives the relentless growth in fleet size, or how much work a model should receive. Both answers lie in empirical relationships between model quality and resource investment, relationships that have made warehouse-scale infrastructure an economic necessity rather than an engineering luxury.

    1.  Accelerators in large clusters automatically switch to lower-clock power states that disable floating-point exception traps.
    2.  Operating systems disable host-to-device PCIe DMA on multi-node clusters, forcing all memory through unbuffered network sockets.

    4.  Distributed coupling introduces network partitions that cause state divergence, stragglers that stall global synchronization barriers, and collective communication deadlocks.
