# V2-13.06 Model-Specific Attack Vectors

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13 Security & Privacy|V2-13 Security & Privacy]]

^sec-security-privacy-modelspecific-attack-vectors-0575

A stop sign with strategically placed black and white stickers can remain recognizable to a human while an evaluated image classifier labels it as a speed limit sign. The attacker changes the observed input rather than the classifier’s code or stored weights. This adversarial example illustrates why the lifecycle entry point matters. Training data, model artifacts, and runtime inputs give an attacker different ways to influence the system and require controls at different boundaries.

The lifecycle entry point separates five objectives. Model theft targets confidentiality by obtaining artifacts or reproducing behavior from queries. Output leakage targets the training data, which the same queries can expose through the predictions the service is authorized to return. Poisoning targets training integrity by changing what the model learns. Adversarial examples target deployed behavior by changing the inputs a model receives. Availability abuse uses the same serving interface to exhaust the service’s compute and cost budget rather than to change any prediction. Data poisoning therefore requires an intervention in the learning pipeline, whereas adversarial inputs and availability abuse call for controls on the deployed service.

Written as the four-field threat model of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.05 Systematic Threat Analysis and Risk Assessment#^sec-security-privacy-systematic-threat-analysis-risk-assessment-3ef1|section 13.4]], the objectives differ mainly in asset and adversary capability. Theft targets weights or behavior and needs either artifact access or query access, and output leakage targets the training data with nothing more than query access. Poisoning targets training integrity and needs write access to something the model learns from. Adversarial inputs target deployed decisions and need control over an input, while availability abuse targets the serving budget and needs nothing beyond an account. These objectives connect the attack surface analysis in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.05 Systematic Threat Analysis and Risk Assessment#^sec-security-privacy-security-threat-modeling-ml-systems-f60d|section 13.4.1]] to the controls available before training, during artifact handling, and at inference, while [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^sec-security-privacy-llmspecific-threat-vectors-65f2|section 13.5.5]] examines how token-stream architectures fuse instructions, untrusted content, and retrieved data across those objectives.

These entry points sit at different stages of the ML lifecycle ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-ml-lifecycle-threats|figure 4]]). Upstream, an attacker may inject samples or alter labels in a data source the pipeline accepts. A backdoor can then remain inactive on ordinary evaluation inputs and activate on a chosen trigger. Downstream, deployed files expose an artifact-access boundary, while prediction APIs expose a query boundary. An adversarial input crosses the latter without requiring the attacker to alter the training pipeline.

Controls must act at the relevant entry point and preserve their assumptions through later stages. Data validation limits what enters training, artifact controls authenticate what deployment loads, and serving controls constrain requests and returned information. None establishes behavioral correctness by itself; the threat model determines which attack each control must withstand.

### Model Theft

^sec-security-privacy-model-theft-1879

A competitor spending a few thousand dollars on public API queries to train a surrogate model, or an insider copying unencrypted weights from a bucket, can replicate a model that cost millions of dollars to train ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-oliynyk2023|Oliynyk et al. 2023]]). Model theft, the first of those five objectives, targets confidentiality by recovering a trained model’s parameters, architecture, or output behavior, undermining its economic value or exposing private information encoded in its weights.

Such threats arise across a range of deployment settings, including public APIs, cloud-hosted services, on-device inference engines, and shared model repositories. Prediction interfaces can leak enough signal to recover model functionality ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-tramer2016stealing|Tramèr et al. 2016]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-oliynyk2023|Oliynyk et al. 2023]]), while classifier outputs can reveal meaningful information about training sets or learned structure ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-ateniese2015|Ateniese et al. 2015]]). Artifact handling introduces separate risks. Unsafe deserialization[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn3|³]] can execute attacker-supplied code, while insufficient access controls can expose model files or deployment packages directly.

Model theft pursues two distinct objectives, and each requires different controls ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-model-theft-types|figure 5]]). **Exact artifact theft** obtains the model file or deployment artifact through storage, registry, or device access. The attacker can reuse the recovered weights without repeating their training. **Approximate behavioral theft** uses API responses, such as labels, logits, embeddings, or confidence scores, to train a surrogate. It can exploit permitted queries without breaking authentication. The literature names this query-based branch in several ways. *Model extraction* and *model stealing* are synonyms for the attack, while *model distillation* names its usual training step, in which a surrogate learns from the victim’s outputs. Its usual product is a behavioral surrogate, but the same query access can also recover selected internal parameters, a third outcome that the OpenAI results below demonstrate. Encryption, access control, and protected deployment paths restrict artifact access; signatures separately authenticate artifact integrity. Output limits, query budgets, auditing, and pricing constrain behavioral extraction, while watermarking can support attribution after copying.

Approximate behavioral theft (right) uses black-box API queries, output signals, and surrogate training or distillation to clone the model’s behavior without direct access to weights.

**Definition 13.3: Model extraction**

***Model extraction*** is the class of attacks in which an adversary, with only black-box query access to a deployed model’s prediction interface, recovers the model’s parameters, decision boundaries, or behavior by analyzing observable outputs.

1.  **Significance**: Successful extraction often costs orders of magnitude less than the original training. Published demonstrations have recovered logistic regression, neural-network, and decision-tree models from public machine-learning APIs with high fidelity and modest query cost ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-tramer2016stealing|Tramèr et al. 2016]]). Later work has reconstructed components of large language models, including OpenAI deployments studied by Carlini et al. ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-carlini2024stealing|2024]]), using only public query access. The BERT extraction example below illustrates the same dynamic on a transformer model, using only synthetic queries to train the copy.
2.  **Distinction**: Extraction differs from direct theft of model files (which requires intrusion into the storage layer) and from model inversion (which uses model outputs to infer training-data properties or reconstruct representative inputs rather than the model itself). Its attack surface is the model’s query interface, so every deployed ML service faces it by construction whenever the model is reachable.
3.  **Common pitfall**: A frequent misconception is that rate limiting alone is a sufficient defense. An attacker willing to issue queries slowly, distribute requests across accounts, or accept a multi-month attack window may still extract useful behavior. Reducing output information, detecting systematic probing, and pricing queries can raise the cost or expose the attempt, but their combination does not guarantee prevention.

Model theft can also enable attacks on information encoded by the model. Extraction studies demonstrate recovery of useful behavior or selected internal parameters, although those outcomes do not imply complete replication of a large model or its training pipeline ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-tramer2016stealing|Tramèr et al. 2016]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-carlini2024stealing|Carlini et al. 2024]]). A competitor holding a stolen Archetype B (DLRM at Scale) recommendation model obtains its embedding tables, which store a learned vector for each value of each categorical feature. In a recommender those features commonly include user and item IDs, so the stolen tables hand the competitor a per-user vector shaped by that user’s history, a natural starting point for inferring the user’s attributes. Whether this exposes particular customer attributes depends on the model, accessible features, and auxiliary information. Model inversion attacks investigate that boundary by attempting to infer sensitive input properties from the learned model ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^sec-security-privacy-model-inversion|section 13.5.2.2]]).

**Example 13.1: The BERT model extraction**

**Scenario**: Proprietary language models deployed behind public inference APIs return full probability vectors and confidence scores to client queries ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-krishna2020thieves|Krishna et al. 2020]]).

**Diagnosis**: The attacker needed no real training data. Because both the victim and the copy were fine-tuned from the same publicly released pretrained BERT, queries made of random word sequences shaped by simple task-specific heuristics supplied enough labeled outputs to train a student. That student recovered much of the victim’s task performance on tasks including natural language inference and question answering ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-krishna2020thieves|Krishna et al. 2020]]). With a shared public starting point, the API responses had to supply only the task-specific fine-tuning signal. Retaining task accuracy is distinct from agreeing with the target on each input; neither implies recovery of its exact parameters.

**Systems lesson**: API endpoints expose intellectual property when outputs carry raw decision-boundary logits. Serving platforms combine rate-limiting, query auditing, and confidence-score truncation to make model extraction more costly and detectable.

#### Exact Artifact Theft

^sec-security-privacy-exact-model-theft-b738

Exact artifact theft targets the model’s stored structure and learned parameters. The exposed path may be an artifact-download API, an on-device inference package, or a model repository. This differs from querying a prediction API: the attacker obtains the artifact itself. Weak access control or unprotected packaging can expose that artifact without requiring full control of the underlying infrastructure.

The value of a stolen artifact depends on what it contains and what the attacker wants to reproduce. Learned parameters and architecture details can support inference when the necessary preprocessing and runtime are available. Training hyperparameters, including learning rate schedules, batch sizes, and regularization settings, help reproduce or extend training, but are not required merely to execute an existing checkpoint. Side-channel attacks,[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn4|⁴]] reverse engineering, or analysis of observable outputs may reveal additional structure when the artifact is incomplete. The threat model should therefore distinguish running a copied model from rebuilding the pipeline that produced it.

System designers must account for these risks by separating artifact security from interface security. Artifact controls secure model files, registry entries, and deployment packages; interface controls restrict APIs, reduce output precision, audit query patterns, and price or rate-limit access so behavioral extraction becomes harder to perform economically ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-tramer2016stealing|Tramèr et al. 2016]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-oliynyk2023|Oliynyk et al. 2023]]).

#### Insider Theft of Engineering Assets

^sec-security-privacy-case-study-tesla-ip-theft-9d78

Insider access is often the shortest path to artifact theft, because an insider needs no exploit to reach files that the development environment already grants. The two cases below involve documents and source code rather than model weights, and that difference is their lesson. The protected asset extends beyond the serialized model to the code and data that produced it. Former Google engineer Anthony Levandowski was accused of taking proprietary Waymo materials before founding a competing startup ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-nytimes2017levandowski|The New York Times 2017]]), a case about engineering intellectual property rather than demonstrated extraction of model weights. In March 2019, Tesla filed two trade-secret lawsuits involving former employees who left for autonomous-vehicle competitors ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-korosec2019tesla|Korosec 2019]]). One complaint alleged that employees who joined Zoox copied proprietary warehousing, logistics, and inventory-control documents. A separate complaint alleged that former Autopilot engineer Guangzhi Cao copied Tesla Autopilot source-code repositories before joining XPeng/XMotors.

These allegations matter for ML systems because training code, feature pipelines, labeling workflows, deployment scripts, simulation assets, and operational playbooks can reveal enough about a system to accelerate a competitor’s replication effort or expose downstream security weaknesses. API-level extraction defenses do not reach this boundary. Restricting prediction queries cannot prevent a developer from copying repositories that the developer can already access. Development access, artifact handling, and release provenance therefore belong in the same threat model as inference interfaces, with controls matched to the sensitivity of each asset.

#### Query-Based Extraction

^sec-security-privacy-approximate-model-theft-1155

Approximate behavioral theft uses observed input-output pairs to train a substitute without copying the target’s parameters. This application of model distillation, or knockoff modeling, can reproduce useful functionality from public API responses ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-orekondy2019|Orekondy et al. 2019]]).

Evaluation must distinguish task performance from agreement with the victim. A substitute can achieve similar benchmark accuracy while making different predictions; reproducing the victim’s correct answers and mistakes measures behavioral fidelity. The service therefore has to limit accumulated observations while preserving the outputs legitimate users need.

Query access can also expose internal parameters rather than only supply examples for a surrogate. In their paper, Carlini et al. ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-carlini2024stealing|2024]]) show how to reconstruct the final embedding projection matrix of OpenAI’s `ada` and `babbage` models, and to recover the hidden dimensionality (and estimate the cost of full matrix recovery) for `gpt-3.5-turbo`, using only public API access. That final projection maps a hidden state vector to a much larger token vocabulary, so every output logit vector lies in a linear subspace whose rank equals the model’s hidden dimension. Collecting logit vectors across enough varied prompts until new responses become linearly dependent on earlier ones reveals where the rank saturates and recovers the hidden dimensionality. For the smaller models, solving for a basis of that subspace replicates the weight matrix up to affine transformations, because the logits alone cannot distinguish the true hidden basis from any invertible transformation of it. This partial parameter extraction is distinct from both copying a complete artifact and training a behavioral substitute. It stops short of recovering the full model, yet it shows that an API’s exposed scores and query controls can reveal internal structure that its operator intended to keep private.

The empirical results in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^tbl-openai-theft|table 4]] demonstrate extraction of smaller models’ output-projection parameters with root mean square errors on the order of $10^{-4}$, while the larger GPT-3.5 rows show dimension recovery and estimated recovery costs rather than implemented weight-matrix extraction. The production-interface attack used features such as top-${k}$ token log-probabilities together with logit-bias controls. The logit-bias control adds a caller-chosen offset to the logits of named tokens. Because a production API returns only the top-${k}$ log-probabilities rather than the full vocabulary vector, the caller can use that control to push selected tokens into the top-${k}$ set and read their relative logit values across prompts. The interaction between returned information and permitted query modifications therefore belongs in the threat model, even when neither feature exposes weights directly.

#### Defenses Against Model Extraction

^sec-security-privacy-model-extraction-defenses-8f3b

Unlike data poisoning and adversarial perturbations, whose algorithmic defenses are developed in **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14 Robust AI#^sec-robust-ai|Robust AI]]**, and training-data leakage, whose formal privacy bounds are developed in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.10 Differential Privacy#^sec-security-privacy-differential-privacy-8c2b|section 13.9]], model extraction is countered directly at the serving API boundary. Its quantitative defenses therefore belong beside the attack, while [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.09 Comprehensive Defense Architectures#^sec-security-privacy-secure-model-deployment-e08c|section 13.8.2]] covers artifact custody, cryptographic packaging, and endpoint authentication infrastructure.

Model extraction defenses must account for what an adversary can accumulate through the API across four operational levers. Reducing output precision or returning fewer classes restricts the observations supplied by each response. Query quotas constrain collection per credential, and pricing increases its cost. Behavioral monitoring supplies evidence of systematic probing that can trigger investigation or enforcement. A daily rate limit only slows collection without bounding its lifetime total, and an attacker can combine observations from several accounts. The defense must therefore connect output design to cumulative budgets and the identities over which those budgets can actually be enforced.

Monitoring supplies evidence for adjusting those controls. High query volume is one possible signal, although legitimate batch jobs can produce it and an extractor can deliberately slow collection. A high-traffic, general-purpose prediction API might begin with an illustrative volume rule:

$$
\text{alert}(\text{user}) = \begin{cases} 1 & \text{if } {q_{\text{daily}}}> 10{,}000 \text{ or } {q_{\text{hourly}}}> 2{,}000 \\ 0 & \text{otherwise} \end{cases}
$$

where ${q_{\text{daily}}}$ and ${q_{\text{hourly}}}$ represent query counts. Such thresholds are only the first signal. They must be calibrated by service tier and by the shape of normal use, because batch customers and attackers can both generate high volume.

The next signal compares the inputs with expected use. Synthetic or systematically varied queries may reveal probing, but an extractor can also submit ordinary examples. A detector can compare the user’s query distribution with a baseline chosen for the service and customer workload:

$$
{\mathcal{D}_{\text{KL}}}({p_{\text{user}}}\lVert {p_{\text{expected}}}) > {\tau}
$$

where ${\mathcal{D}_{\text{KL}}}$ is Kullback-Leibler (KL) divergence, a measure of how far one probability distribution departs from another, and ${\tau}$ is an alert threshold. A practical detector needs a tractable representation of inputs and enough observations to estimate those distributions. For a language model API, unusual token distributions or repetitive prompt templates may provide useful features. Regular inter-query intervals can add evidence of automation, but legitimate applications also automate requests and attackers can vary their timing.

An anomaly detector combines these signals into a score that can drive enforcement:

$$
\text{score}_{\text{anomaly}}({u}) = {f_{\theta}}(\text{qps}({u}), {\mathcal{D}_{\text{KL}}}({u}), {\sigma_{\text{inter-query}}}({u}), \ldots)
$$

where ${f_{\theta}}$ is a trained classifier and the features capture query volume, distribution, and temporal regularity. The score supports a response policy rather than establishing that theft occurred. A service can tighten quotas, request additional verification, or refer activity for review, with thresholds calibrated against legitimate workload variation. Free, paid, and enterprise tiers can carry different limits, but account-level enforcement constrains an adversary only to the extent that collection across credentials is also controlled.

A concrete quota ladder for the same general-purpose API makes that information cap visible. A free tier might allow 1,000 queries/day with a 10 queries/s burst, a basic paid tier might allow 100,000 queries/day with 100 queries/s, and an enterprise tier might allow 10M queries/day with custom burst limits and contractual monitoring. The exact numbers depend on product needs, but the ladder matters because extraction cost scales with accumulated responses.

An illustrative adaptive policy connects the anomaly score to a request limit. Higher scores reduce the quota, so false positives translate directly into lost capacity for legitimate workloads:

$$
\text{limit}_{\text{effective}}({u}) = \text{limit}_{\text{base}} \times \exp(-{\gamma_{\text{rate}}}\cdot \text{score}_{\text{anomaly}}({u}))
$$

where ${\gamma_{\text{rate}}}$ controls sensitivity. With ${\gamma_{\text{rate}}}=1$, a user with anomaly score 0.8 keeps about 45 percent of the base quota, a 55 percent rate reduction. The calculation specifies enforcement strength, not detection accuracy. Its security effect also depends on the response: full logits, hidden states, or detailed confidence scores can make each permitted query more useful to an extractor. Quota design therefore needs an explicit output contract.

Output shaping reduces the leakage per response while preserving the part of the answer legitimate users usually need. **Confidence rounding** returns coarser probabilities instead of full-precision logits or probabilities:

$$
{p^{\text{rnd}}}_i = \text{round}({p}_i, {d_{\text{dec}}})
$$

where ${d_{\text{dec}}}$ is the number of decimal places. For a 1000-class ImageNet classifier, rounding from 6 decimals to 2 decimals removes 4 decimal digits, about 13.3 bits per class. The count uses a decimal-bin model, which treats each decimal digit as selecting one of ten equally likely levels, so every dropped digit removes $\log_2 10 \approx 3.3$ bits. This counts representational precision, not measured information about the model. Rounding can also create score ties, so the service must evaluate the effect on ranking and downstream decisions.

The **top-${k}$ truncation** defense returns only the top-${k}$ predicted classes rather than the full probability distribution:

$$
\text{output} = \{({c}_i, {p}_i) : {i}\in \text{top-}{k}\}
$$

For ${k}=$ 5 on a 1000-class problem, the API returns only those top scores instead of the full softmax vector, eliminating 99.5 percent of the distribution entries an extractor could otherwise observe per query. Legitimate users often need only the top few predictions, while an extractor benefits from the full distribution.

![[90 Assets/Volume II/13 Security Privacy/Security Privacy Output Leakage Ladder fb3e684517.svg]]

*Two-rung ladder comparing a full 1000-score output distribution with top-5 returned scores, annotated as a 200 times reduction in exposed scores.*

*Top-${k}$ truncation exposes far fewer scores per query than the full distribution.*

When rounded or truncated outputs still leak too much, calibrated noise can make repeated measurements less useful. Adding Gaussian noise to the score vector ${\hat{\mathbf{y}}}$ of a ${K}$-class model (uppercase ${K}$ for the class count, distinct from the ${k}$ of top-${k}$) can push some scores below zero, so the noisy vector is projected back onto a valid probability distribution:

$$
{\tilde{\mathbf{p}}}={\Pi_{\Delta^{K-1}}}\!\left({\hat{\mathbf{y}}}+{\mathbf{z}}\right), \qquad {\mathbf{z}}\sim{\mathcal{N}}({\mathbf{0}},{\sigma}^2 {\mathbf{I}})
$$

where ${\Pi_{\Delta^{K-1}}}$ returns the closest valid distribution to the noisy vector, one whose scores are all nonnegative and sum to one $({\tilde{p}}_i\geq 0,\ \sum_i{\tilde{p}}_i=1)$. The set of such vectors is the probability simplex ${\Delta}^{{K}-1}$. The noise scale ${\sigma}$ must balance extraction defense with utility preservation. Too little noise leaves the confidence surface measurable; too much noise changes decisions for legitimate users. This randomized response shaping is not, by itself, a differential privacy guarantee: such a claim also requires an adjacency relation, a sensitivity bound (the most one protected contribution can change the result), calibrated noise, and composition accounting.

Differential privacy addresses a different objective when a response is computed from sensitive records. It bounds the change in the released distribution under a specified change to the protected data. [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.10 Differential Privacy#^sec-security-privacy-differential-privacy-8c2b|Section 13.9]] develops the full $({\epsilon}, {\delta})$ definition and the adjacent-dataset notation. Repeated interactive DP releases compose, but queries to a fixed DP-trained model are post-processing, computation on the released model that never reads the protected data again, and do not consume additional training privacy budget. Such queries may still enable model extraction, so output shaping and rate limits remain security controls.

The final lever is economics. Consider a simplified comparison in which extraction and independent training produce equally useful substitutes and query charges represent the extraction cost. If training from scratch costs ${C_{\text{train}}}$ and extraction requires ${n_{\text{queries}}}$ queries at price ${p_{\text{query}}}$ per query, extraction is the cheaper option when:

$$
{n_{\text{queries}}}\cdot {p_{\text{query}}}< {C_{\text{train}}}
$$

Setting ${p_{\text{query}}}$ so that ${n_{\text{queries}}}\cdot {p_{\text{query}}}> {C_{\text{train}}}$ makes extraction costlier than independent training in this simplified equal-quality comparison. It does not remove incentives based on unavailable training data, competitive value, or objectives other than acquiring a substitute cheaply. For example, if training a competitive large model costs \$5M and extraction requires 100M queries, the break-even price is \$0.05/query; pricing above that makes extraction more expensive than retraining under those assumptions. The comparison must include the attacker’s alternative costs of compute, data, and engineering. In practice, pricing, monitoring, quotas, and output shaping work together. Restricted outputs and coarse confidence bins reduce exposed detail, while quotas constrain access through the identities they cover. Neither control alone bounds all information an actor can accumulate across accounts, alternate endpoints, or other sources.

**Napkin Math 13.1: Protecting a production API**

**Problem**: For a production ResNet-50 image-classification API serving 1M daily queries from 10,000 users, how can the operator make model extraction economically unattractive without degrading normal service?

**Scenario**: The model costs about \$5K to train in this scenario. An extractor needs about 5M queries for 90 percent fidelity, or 5,000 queries/class for a 1,000-class classifier. Without defenses, an attacker abusing a free tier can send 25K queries/day for 200 days and pay nothing, making extraction economically favorable. The service is far smaller than the general-purpose API above, so its tiers and alert thresholds are scaled to its own traffic, and its training cost sits three orders of magnitude below the large model of the break-even example.

**Mechanism**: The defense stack works as a sequence:

1.  **Cap collection**: The free tier allows 100 queries/day, the paid tier costs \$50/month for 10K queries/day, and enterprise access requires authentication plus monitoring.
2.  **Monitor probing**: The monitoring path watches for systematic measurement behavior, including more than 5K queries/day from one user or median inter-query gaps below 100 ms; the lightweight detector adds 2 ms per query.
3.  **Shape outputs**: Output shaping rounds confidences to 2 decimal places, retaining about 6.7 bits from each rounded scalar probability, and returns only the top-5 classes, eliminating 99.5 percent of distribution entries.
4.  **Price extraction**: At pay-as-you-go \$0.001/query (above tier caps), 5M extraction queries cost \$5K, matching the training cost in this scenario. An attacker limited to the \$50/month tier (10K queries/day) would need 500 days and about \$833 total, which is cheaper under these assumptions. A daily quota slows collection but does not cap its lifetime total.
5.  **Cap cumulative collection**: A per-principal lifetime budget closes that route. If each principal’s queries beyond an allowance well below 5M are billed at the pay-as-you-go \$0.001/query, assembling the full extraction set costs close to \$5K on any tier, the same as training the model.

**Outcomes to measure**: Whether the design works is decided by four measurements, namely the surrogate’s accuracy, the accuracy legitimate users still receive, the latency the controls add, and the share of users flagged by mistake. The values below are constructed inputs that show the shape of that measurement, not results derived from the controls above. Suppose the surrogate’s accuracy drops from 90 percent without defenses to 72 percent with defenses, an 18 percentage-point reduction, while legitimate top-5 accuracy remains 99.2 percent, close to the 99.3 percent baseline. Monitoring and output shaping add 2.5 ms on top of 100 ms inference, or 2.5 percent overhead, while flagging 0.3 percent of users for manual review.

**Systems insight**: Tier caps, monitoring, and output shaping slow an extractor; only the cumulative budget makes the full extraction set cost as much as retraining. Break-even is the design target rather than a weakness. At that price the query bill alone equals the cost of training an equivalent model. The extractor still pays for the surrogate’s own training run and engineering on top of it while receiving a copy that the shaped outputs leave less faithful. Under the assumed equal-quality comparison, a lifetime price at or above break-even therefore removes the cost advantage of extraction over training an equivalent model independently. The residual route is to spread queries across many accounts, which account issuance controls and cross-account detection must bound, because a per-principal budget constrains an adversary only as far as principals map to real actors. The accuracy, latency, and false-positive figures are assumptions that the operator must measure before the design ships.

Pay-as-you-go pricing alone would charge the full training cost, but an extractor can stay inside the flat-fee tier, and tracking the cumulative bill against the queries collected shows what that choice is worth ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-extraction-cost-regimes|figure 6]]). A daily quota stretches collection over 500 days but leaves the total near \$833. A lifetime budget that bills every query beyond an allowance of 100K queries at the pay-as-you-go price instead makes the bill climb with the extraction set itself, reaching about \$4,917 when the set is complete, close to the cost of training the model.

### Leakage Through Authorized Outputs

^sec-security-privacy-leakage-authorized-outputs

Whereas model theft copies the model, a second confidentiality failure needs no copy at all, because a model that executes correctly can disclose its training data through the outputs it is authorized to return. Persistent learning ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.02 The Expanded Attack Surface#^sec-security-privacy-security-privacy-ml-systems-0b1e|section 13.1]]) carries sensitive information past the original processing, and the attacker reads nothing but permitted predictions, so storage encryption and caller authentication offer no protection. Three attacks exploit that leakage at increasing levels of detail. Membership inference learns a single bit indicating whether a given record was in the training set. Model inversion reconstructs properties of the training data, such as a representative input for a class or an identity. Training-data extraction recovers memorized records verbatim. All three need only query access or released weights, and all three grow more effective as the model fits its training data more closely than the population that data came from.

#### Membership Inference

^sec-security-privacy-membership-inference

**Membership inference** tests whether a particular record was part of a model’s training set ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-shokri2017membership|Shokri et al. 2017]]). The attack exploits a gap that training creates. The model has fitted its training members, so it usually assigns them lower loss and higher confidence than records it has never seen. The simplest test thresholds that signal and declares a record a member when the model’s confidence on its true label exceeds a calibrated cutoff. A stronger test trains *shadow models* on data drawn from the same distribution with known membership. It learns from their outputs how member and nonmember responses differ, and it applies that classifier to the target model’s outputs ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-shokri2017membership|Shokri et al. 2017]]). Both tests succeed in proportion to the gap between training and held-out behavior, so the risk grows with overfitting and tends to concentrate on small datasets and on rare records that the model had to fit individually. A control added for another threat can widen that gap,[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn5|⁵]] so each one is rechecked against membership inference.

For threat modeling, the relevant variable is what the adversary observes: confidence scores, labels only, or individual client updates. Attack success depends on the target model, data, outputs, and adversary knowledge. Confirming that an individual’s data was in a training set can still create privacy and compliance risk. In healthcare or legal prediction, membership itself can disclose sensitive information about a person, such as a diagnosis or a case. Whether that disclosure violates GDPR, HIPAA, or another rule depends on the data, parties, and deployment context ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-gdpr2016|European Parliament and Council of the European Union 2016]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-hhs2003hipaaprivacy|U.S. Department of Health and Human Services 2003]]).

Membership inference is also the standard privacy audit, and the audit and differential privacy bound the same leakage from opposite sides. An audit runs the strongest available attack against the trained model and reports its success. It must state which attacker access it assumes, because some threat models permit only model queries while others grant parameters or auxiliary information. A successful attack proves leakage. A failed attack shows only that this attack, under these assumptions, found none, so an empirical audit is a lower bound on what the model reveals.

Differential privacy ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.10 Differential Privacy#^sec-security-privacy-differential-privacy-8c2b|section 13.9]]) supplies the upper bound. A membership test is itself a computation on the released model, so the guarantee applies to its verdict directly and limits how much more often any test can flag a protected record when that record was in training than when it was absent. Under a guarantee with budget ${\epsilon}$ and no additive slack, the rate at which a test flags true members can exceed the rate at which it falsely flags nonmembers by at most a factor of $e^{{\epsilon}}$, which places a ceiling over every possible attack. The distance between the measured lower bound and the accounted upper bound is the uncertainty that a privacy claim carries, the band between the audit curve and the ceiling in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-mia-audit-dp-bound|figure 7]].

![[90 Assets/Volume II/13 Security Privacy/Cell 9 Output 1 ae85b4bded.png]]

Figure 7: **Membership Audit and the Privacy Ceiling**: Each point on the plane is a membership test, read by how often it flags true members against how often it falsely flags nonmembers. A differential privacy guarantee with no additive slack at the illustrative budget ${\epsilon} = 1$ confines every possible test below the dark ceiling, an upper bound on leakage. #### Model Inversion

^sec-security-privacy-model-inversion

Model inversion infers sensitive properties of the training data, or a representative input for a class or identity, from the learned model ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-fredrikson2015|Fredrikson et al. 2015]]). It can use either query access or exposed model internals. Confidence scores, for example, can guide a search for inputs that the model associates with a target identity or attribute. A reconstructed face may reveal recognizable features without reproducing an exact training photograph; the privacy claim must distinguish those outcomes. Gradient inversion applies the same idea to the updates that a federated client sends ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.09 Comprehensive Defense Architectures#^sec-security-privacy-gradient-inversion-risks-d2c1|section 13.8.5.2]]).

#### Memorization and Training-Data Extraction

^sec-security-privacy-memorization-extraction

**Memorization** is the strongest form of the leak, in which a model retains enough of a specific training record to reproduce it. It is not confined to language models. Under one published extraction protocol, a diffusion model reproduced a training-set photograph almost exactly ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-carlini2023diffusion|Carlini et al. 2023]]); [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-diffusion-model-example|figure 8]] pairs the original with the reconstruction. Evidence of extraction concerns that specific training instance; a similar-looking output of the same subject would not establish memorization. The exposure matters most for assistants trained or adapted on user logs, where the memorized strings are the users’ own messages.

#### GPT-2 Data Extraction Case Study

^sec-security-privacy-case-study-gpt2-data-extraction-attack-5126

The GPT-2 extraction case shows why storage access control is insufficient once a model has learned sensitive content. In 2020, researchers demonstrated that query access to OpenAI’s GPT-2 model could reveal verbatim training examples ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-carlini2021extracting|Carlini et al. 2021]]). The attack targeted information exposed through generation rather than direct access to the stored training dataset. The researchers generated hundreds of thousands of samples, some unconditioned and some seeded with short snippets of internet text. They then ranked the samples by how much more likely GPT-2 found them than a reference model or compression baseline did. This allowed them to extract personal information such as names, phone numbers, and email addresses, along with source code, unique identifiers, and other verbatim snippets that the model had memorized from its training data.

The technical approach exploited GPT-2’s memorization of rare or repeated text sequences through three stages. Sampling came first. The researchers generated 600,000 samples using top-${k}$ sampling, sampling with a temperature that decays over the first generated tokens, and sampling conditioned on short prefixes drawn from internet text. Ranking then applied membership-inference metrics that compare GPT-2’s perplexity on a sample (a measure of how unlikely the model finds the text) against a reference, namely the sample’s zlib compression entropy, the perplexity a smaller GPT-2 model assigns it, and GPT-2’s perplexity on the lowercased text. A sample that GPT-2 finds far more likely than the reference suggests memorization rather than fluent generalization. Manual verification closed the pipeline. The researchers inspected 1,800 top-ranked candidates, checking them first by internet search and then against the training data with OpenAI’s cooperation, and confirmed 604 of them as unique memorized training examples.

The attack challenged the assumption that training data would be “forgotten” after optimization. Some training examples remained recoverable even though the model was designed to generate text rather than retrieve records. Across the GPT-2 family studied (124M to 1.5B parameters), larger models exposed more memorized training data under the evaluation. This comparison motivates testing memorization as models scale; it does not establish a universal relationship between parameter count and privacy loss across different datasets and training procedures. For Archetype A (GPT-4/Llama-3), the deployment must therefore assess its actual corpus, training procedure, and exposed outputs rather than infer leakage from parameter count alone.

Filtering, deduplication, and manual review can reduce exposure, and output filters can screen known sensitive patterns, but empirical screening does not prove that no sensitive string remains recoverable. Differential privacy addresses a different requirement by bounding how much a protected contribution changes the distribution of released results. It does not prohibit every reproduction of text that appears in training, especially information shared across many records. Its contribution bound and the utility effects of filtering or private training must therefore be evaluated separately.

The result demonstrates why training-data controls need layered mitigations rather than storage access control alone ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-carlini2021extracting|Carlini et al. 2021]]). Those layers can include filtering of personally identifiable information (PII), deduplication, extraction-style memorization audits, membership-inference testing, and differential privacy when a formal bound is required. Machine unlearning and policy controls address related lifecycle questions, but their guarantees require separate evidence and validation.

### Data Poisoning

^sec-security-privacy-data-poisoning-351f

While model theft and output leakage compromise confidentiality through read access to a finished model, data poisoning compromises training integrity through write access to something the model will learn from, arriving earlier in the lifecycle than any serving control can act. Injecting a few hundred mislabeled or trigger-stamped examples into a web-scraped corpus or user-feedback stream can plant a targeted backdoor while overall validation accuracy looks completely normal ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-biggio2012poisoning|Biggio et al. 2012]]).

**Definition 13.4: Data poisoning**

***Data poisoning*** is the corruption of training data to compromise model behavior at inference time, either by injecting malicious samples or modifying existing labels.

1.  **Significance**: It undermines the foundational assumption of data integrity. Even a small fraction of poisoned samples can create backdoors or systematic biases that remain latent until triggered by specific inputs during serving.
2.  **Distinction**: Unlike inference-time evasion attacks against a fixed model, data poisoning operates through data collection or training, contaminating the model’s learned mapping from the source.
3.  **Common pitfall**: A frequent misconception is that poisoning can be “fixed” by more data. In reality, poisoning often exploits the aggregation property of training: adding more clean data may not “wash out” a carefully targeted backdoor that uses a unique trigger.

Poisoned data may cause a model to make incorrect predictions, degrade its generalization ability, or embed failure modes that remain dormant until triggered after deployment. The exposure is greatest in applications that retrain on data collected from external sources, including user interactions, crowdsourced annotations, and online scraping, because an attacker can then contribute training data without any access to the training pipeline itself.

The access axes of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.05 Systematic Threat Analysis and Risk Assessment#^sec-security-privacy-threat-vector-classification-3042|section 13.4.1.2]] apply with one change of emphasis. Model visibility still determines how precisely a poison can be crafted. A white-box attacker can optimize examples against the actual architecture and training procedure, while a black-box attacker relies on surrogates and open submission channels. What makes poisoning possible at all, however, is the write capability that the threat-vector scenarios separated from visibility. That capability can sit at collection, preprocessing, labeling, or storage, so the poisoning surface spans the whole data path. Its priority relative to other threats follows the deployment context analyzed in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.05 Systematic Threat Analysis and Risk Assessment#^sec-security-privacy-threat-prioritization-framework-f2d5|section 13.4.2]].

A poisoning attempt spans admission, learning, and exploitation. The attacker first places manipulated examples where the training pipeline may accept them. Training then determines whether those examples induce the intended behavior; merely inserting a record does not guarantee success. If the altered behavior survives evaluation and deployment, the adversary may exploit it to cause selected errors or degrade service. The attack must therefore be evaluated through the actual learning procedure and release gates.

Data poisoning can be viewed as a bilevel optimization problem, because the attacker’s choice affects a model through the defender’s training procedure. In the outer problem, the attacker selects poisoning data ${\mathcal{S}_{\text{poison}}}$ to increase loss on a validation or target dataset ${\mathcal{S}_{\text{test}}}$. The inner problem trains the model on the resulting data. Let ${\mathcal{S}}$ represent the original training data. Subject to the attacker’s permitted modifications and poisoning budget, an untargeted objective is:

$$
\max_{{\mathcal{S}_{\text{poison}}}} \ {\mathcal{L}}({f_{\mathcal{S} \cup \mathcal{S}_{\text{poison}}}}, {\mathcal{S}_{\text{test}}}) \tag{1}
$$

^eq-untargeted-poisoning

where ${f_{\mathcal{S} \cup \mathcal{S}_{\text{poison}}}}$ represents the model trained on the combined dataset of original and poisoned data. For targeted attacks, this objective can be refined to focus on specific inputs ${x}_t$ and target labels ${y}_t$:

$$
\min_{{\mathcal{S}_{\text{poison}}}} \ {\mathcal{L}}({f_{\mathcal{S} \cup \mathcal{S}_{\text{poison}}}}, {x}_t, {y}_t) \tag{2}
$$

^eq-targeted-poisoning

In the training system, the nested objectives become two coupled loops ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-data-poisoning-loop|figure 9]]). The outer loop is the attacker’s proposal step, which optimizes the attack objective, either raising loss on the test set ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^eq-untargeted-poisoning|equation 1]]) or, for a targeted attack, lowering loss on the chosen label ${y}_t$ ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^eq-targeted-poisoning|equation 2]]). The inner loop is the defender’s training process, which minimizes loss on the combined data. The attacker evaluates or approximates this inner effect on training, and uses the resulting target loss to refine the proposal. An attacker without access to the defender’s training process must instead rely on a surrogate or other available feedback.

![[90 Assets/Volume II/13 Security Privacy/Data Poisoning Loop bac56c03ed.svg]]

Figure 9: **Data Poisoning as Bilevel Optimization**: The attacker (outer loop) chooses poisoning data ${\mathcal{S}_{\text{poison}}}$ to raise the trained model’s loss on a test set, the untargeted form drawn here, or, for a targeted attack, to lower its loss on the attacker’s chosen label. The system (inner loop) attempts to minimize its training loss on the combined dataset ${\mathcal{S}} \cup {\mathcal{S}_{\text{poison}}}$. The nested attack objective can require repeated training evaluations or approximations. It does not imply that every poisoning defense must simulate full training.

^fig-data-poisoning-loop

This formulation captures the adversary’s goal of introducing carefully crafted data points to manipulate the model’s decision boundaries. Consider an email spam filter that retrains on messages users report as legitimate. An attacker who controls a set of accounts can report a batch of messages written in the style of an upcoming campaign as “not spam.” The goal is to shift the filter’s decision boundary so that the campaign’s future messages reach inboxes. In this case, the poisoning data ${\mathcal{S}_{\text{poison}}}$ consists of mislabeled campaign-style messages, and the attacker’s objective is to have the campaign messages ${x}_t$ classified as legitimate mail ${y}_t$, following the targeted attack formulation in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^eq-targeted-poisoning|equation 2]]. If the mislabeled messages influence training enough to induce that behavior, aggregate performance on other traffic may still appear normal. The contrast with the stop-sign stickers that opened the discussion of model-specific attacks is the lifecycle stage. Poisoning changes the model before deployment, whereas the stickers change only the input that an unmodified deployed model receives.

Data poisoning attacks differ in their objective and scope ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-biggio2012poisoning|Biggio et al. 2012]]). Availability attacks seek broad degradation of useful performance. Targeted attacks seek errors on selected inputs or classes and may leave aggregate accuracy largely unchanged ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-shafahi2018poison|Shafahi et al. 2018]]). The targeted objective of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^eq-targeted-poisoning|equation 2]] rewards errors only on the attacker’s chosen inputs, while the inner training loop still fits the combined data, which remain mostly clean, so the objective itself does not push aggregate accuracy down. Backdoor attacks associate an attacker-chosen trigger with unwanted behavior; the trigger can be visible, as in a sticker, even when its significance is hidden ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-gu2017badnets|Gu et al. 2017]]). Subpopulation attacks instead target a group defined by shared features ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-jagielski2021subpopulation|Jagielski et al. 2021]]). These categories can overlap. Their objectives guide which evaluations are needed beyond aggregate accuracy, including targeted, trigger-specific, and subgroup tests.

The objective classes say what an attacker wants; the attack *mechanism* depends on the attacker’s access to the system and knowledge of the data pipeline. Every mechanism shares the shape traced in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-poisoning-impact|figure 10]], in which a poisoned record enters the training pipeline alongside clean data and attempts to alter the resulting model’s behavior. The most direct mechanism is label modification, where an attacker selects a subset of training samples and alters their labels, flipping ${y}= 1$ to ${y}= 0$ or reassigning categories in multi-class settings. Even small-scale label corruption can shift decision boundaries. At web scale the same mechanism mislabels multimodal pretraining pairs, as in the dirty-label sample of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-dirty-label-example|figure 11]], which pairs cat images with misleading “dog” captions to induce false associations.

In the illustrated successful attack, a poisoned record admitted at ingestion contaminates the training corpus, pulls the optimizer’s gradients toward the attacker’s trigger, and yields a backdoored model whose clean accuracy can remain intact, so aggregate validation alone can miss it.

Beyond label modification, the attacker can keep the label intact and corrupt the features instead, the strategy known as **clean-label poisoning**. In the bilevel formulation, only the attacker’s permitted modifications change, from labels to features. Because every label is correct, label audits cannot flag these records. Imperceptible image perturbations, subtle shifts in structured fields, and fixed trigger patterns aim for the same outcome. In each case the training example still appears legitimate, but it bends the learned decision boundary toward a future failure. Generative methods and data-synthesis tools raise the same risk at larger scale because they can create natural-looking examples whose only purpose is to distort what the model learns.

Clean-label poisoning is not always malicious in intent; researchers have begun exploring it as a defensive tool, particularly for protecting creative work from unauthorized use by generative AI models. Nightshade, developed by researchers at the University of Chicago, aims to deter unauthorized training by poisoning images that a scraper may collect ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-shan2024|Shan et al. 2023]]). It does not block scraping itself. Its perturbations preserve the apparent image content while changing how a model learns from it; the reported experiments show targeted concept corruption when the modified images enter the tested training pipelines.

The dose-response matrix in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-poisoning|figure 12]] charts this progressive corruption across four poison doses (0 to 300 samples) and eight prompt concepts. As the dose increases, Stable Diffusion XL outputs morph away from source concepts (generating cows for “car” or cats for “dog”) under the tested training conditions. These outputs demonstrate changed behavior without, by themselves, identifying the internal representation that caused it. The experiment demonstrates concept poisoning, in which poisoned samples distort a model’s semantic associations.

The Nightshade experiments also report effects on concepts related to the poisoned target. This spillover extends the observed attack beyond the exact target prompt, but its reach depends on the model, poison construction, and training procedure. The same technique used to protect artistic content could also be repurposed to sabotage legitimate training pipelines, highlighting the dual-use dilemma[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn6|⁶]] at the heart of machine learning security.

Whether crafted examples become poisoning depends on the data boundary. Web scraping, social media feeds, crowdsourced annotation, and untrusted user submissions all allow poisoned records to enter upstream and pass through weak cleaning checks in a “trusted” form. Physical systems add a second path. A sticker on a road sign attacks a car at inference time, but photographs of that sign harvested into a training corpus poison the model only when they are crafted or labeled to serve the attacker. Correctly labeled examples can instead help the model resist the sticker. Online learning systems tighten the feedback loop further, allowing an attacker to introduce small increments of malicious data until model behavior drifts without a single obvious anomaly. In collaborative training the same boundary sits at aggregation, where one malicious client’s update reaches every participant ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-poisoning-attack-example|figure 13]]). [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.07 Fleet-Internal Trust Boundaries#^sec-security-privacy-gradient-sync-integrity|Section 13.6.1]] examines the same exposure among the workers of a synchronous data-parallel job.

![[90 Assets/Volume II/13 Security Privacy/Poisoning Attack 1479796252.svg]]

Figure 13: **Collaborative Poisoning via Aggregation**: In a collaborative learning setting, multiple clients each train on local data and contribute model updates to a central server that aggregates them into a shared global model. A single malicious participant can inject poisoned updates that the server folds into the aggregated model, so the corruption spreads to every client without any one obvious anomaly. This attack surface differs from adversarial examples because it targets the model during *training* rather than at *inference*.

^fig-poisoning-attack-example

Mitigating poisoning requires controls from data admission through model evaluation, and **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.08 Data Poisoning Defenses#^sec-robust-ai-data-poisoning-defenses-d070|Data Poisoning Defenses]]** develops those defenses and the evidence for them. Because targeted and backdoor attacks can preserve aggregate validation accuracy, clean evaluation cannot certify integrity. The provenance bound on trust (principle [[01 Books/Volume II - Scaling/04 The Responsible Fleet/V2 Responsible Fleet Principles#^pri-provenance-bounds-trust|22]]) makes source verification and lineage necessary evidence about what entered training, but a verified source can still supply harmful records. Validation and anomaly detection examine those records, while robust training can limit their influence under a specified contamination model. Release evaluation must then test the targeted behaviors that ordinary accuracy metrics can miss.

### Adversarial Attacks

^sec-security-privacy-adversarial-attacks-9f84

An attacker who can modify a sensor input or submit an API request can target the deployed model without changing its training data. The security question is which inputs the actor can control and which service decisions those inputs can influence. Behavioral robustness asks how much the model’s predictions degrade under that specified manipulation. Here the threat model establishes the allowed attack; **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.07 Adversarial Defenses#^sec-robust-ai-input-attack-detection-defense-19d3|Adversarial Defenses]]** develops the evaluation and training methods needed to measure and improve resistance.

Adversarial inputs exploit the deployed model’s decision behavior under attacker-chosen modifications. Some attacks use small, hard-to-perceive perturbations; others use visible patches or changes allowed by a physical or semantic constraint. The threat model must state those constraints before attack success or defense quality can be measured. This shifts attention from the integrity of upstream training data to the inputs and decisions exposed during inference.

These attacks create real-world risks in domains such as autonomous driving, biometric authentication, and content moderation. Small, visually hard-to-distinguish perturbations can cause image classifiers to make high-confidence errors ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-szegedy2013intriguing|Szegedy et al. 2013]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-goodfellow2015explaining|Goodfellow et al. 2015]]). Physical-world work showed that printed adversarial images can survive camera capture and remain misclassified by an ImageNet classifier ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-kurakin2018|Kurakin et al. 2017]]). Road-sign attacks then showed that small stickers or perturbations can cause signs to be misclassified under realistic viewing conditions ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-eykholt2018|Eykholt et al. 2018]]). A deployed defense must be evaluated against attacks adapted to its mechanisms. Changing the attacker model or the deployment can invalidate earlier evidence, so each change requires renewed testing.

The Perspective API case makes the inference-time distinction concrete. Researchers studying Google’s toxicity detection API in 2017[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn7|⁷]] showed that subtle misspellings, character substitutions, and added punctuation could cause explicitly toxic phrases to receive low toxicity scores ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-hosseini2017deceiving|Hosseini et al. 2017]]). The training pipeline had not been poisoned; the deployed decision surface was fragile to small input perturbations.

The shared abstraction is a search over permitted input changes for an outcome the attacker wants. A norm bound constrains numerical distance, while a physical constraint may limit sticker placement or camera conditions. Neither automatically establishes that a modification is imperceptible or harmless to a human observer.

The access types of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.05 Systematic Threat Analysis and Risk Assessment#^sec-security-privacy-threat-vector-classification-3042|section 13.4.1.2]] determine how that search proceeds. White-box access lets the attacker compute input gradients directly, while black-box and gray-box attackers must estimate them from queries, partial architecture knowledge, or a surrogate model. Common attack strategies include surrogate model construction, transfer attacks exploiting adversarial transferability[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn8|⁸]] ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-papernot2016transferability|Papernot et al. 2016]]), and generative adversarial network (GAN)-based perturbation generation. The evaluation must also state the query budget and which inputs the actor can modify.

↪ Gradient-based perturbation attacks and their white-box, black-box, and transfer variants are developed in **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.06 Adversarial Attacks#^sec-robust-ai-inputlevel-attacks-model-robustness-d6ea|Adversarial Attacks]]**.

The threat model usually bounds the attacker’s change to a ball around the clean input, $\|{\boldsymbol{\delta}_{\text{adv}}}\| \leq {\epsilon_{\text{adv}}}$. A perturbation inside that radius succeeds when it carries the input across a decision boundary. The radius ${\epsilon_{\text{adv}}}$ lives in input space and is unrelated to the privacy budget ${\epsilon}$ of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.10 Differential Privacy#^sec-security-privacy-differential-privacy-8c2b|section 13.9]]. The stop-sign stickers that opened the discussion of model-specific attacks are the physical form of such a boundary crossing. **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.06 Adversarial Attacks#^sec-robust-ai-physical-world-attacks|Physical-world attacks]]** treats the case as a robustness problem and examines what its separate laboratory and field-test success rates imply for evaluation.

Because these attacks succeed against models with high clean accuracy, defenses must act on the attack itself. They divide between runtime controls, such as input validation and anomaly monitoring during inference ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.09 Comprehensive Defense Architectures#^sec-security-privacy-runtime-system-monitoring-a71c|section 13.8.3]]), and training-time methods such as adversarial training on deliberately perturbed examples ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-madry2018towards|Madry et al. 2018]]). **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.07 Adversarial Defenses#^sec-robust-ai-input-attack-detection-defense-19d3|Adversarial Defenses]]** evaluates both against stated threat models.

### LLM-Specific Attack Vectors

^sec-security-privacy-llmspecific-threat-vectors-65f2

The same inference-time framing extends to large language models (LLMs), where security surveys catalog prompt injection, jailbreaking, data leakage, and malicious reuse as cybersecurity and privacy risks ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-gupta2023|Gupta et al. 2023]]). The systems mechanism is that the interface often mixes instructions, user content, retrieved context, and policy controls in one token stream, making the trust boundary between control and data fragile ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-perez2022ignore|Perez and Ribeiro 2022]]). The boundary is weakest where retrieved or external content enters that stream, because text the system fetched can be reinterpreted as instructions ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-greshake2023not|Greshake et al. 2023]]). A secure LLM system therefore separates four objects that the model tends to collapse. Instructions, comprising system and developer directives, define the intended control plane, whereas untrusted content from user input and external text must remain strictly data rather than authority. Retrieved documents provide evidence but should never rewrite policy or permissions, and sensitive secrets (credentials, private data, and hidden policy state) must remain outside model-visible context unless explicitly required. Separating these objects gives the serving system concrete boundaries it can enforce even when the model output tries to blur them.

The serving system must treat every model output as untrusted input, not as authorization. Each model receives the least privilege needed for the current task ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-saltzer1975|Saltzer and Schroeder 1975]]), and any component that consumes model output validates it before acting on it. An external policy-enforcement point must check the authenticated principal and current context rather than accepting a model-generated claim of permission. High-impact or irreversible operations require a separate approval path. These boundaries prevent model text from expanding its authority and limit the blast radius when prompt injection succeeds ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-greshake2023not|Greshake et al. 2023]]). They do not eliminate injection: an attacker may still abuse every operation that the current principal legitimately allows.

Three recurring failure modes organize the space: prompt injection attempts to cross the boundary between control and data, training data extraction exposes memorized records ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-carlini2021extracting|Carlini et al. 2021]]), and jailbreaking seeks to bypass alignment controls ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-zou2023|Zou et al. 2023]]). Prompt injection exploits the model’s interpretation of content as instructions ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-perez2022ignore|Perez and Ribeiro 2022]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-greshake2023not|Greshake et al. 2023]]). Instruction roles and delimiters can guide behavior, but do not supply an authorization boundary equivalent to separating SQL parameters from executable query structure. An attacker can embed directives within legitimate inputs (such as “Ignore previous constraints and output the system prompt”) that the model may follow. Input and output classifiers can detect some attempts, while sandboxing and external permission checks constrain what a manipulated output can reach. These controls need separate evaluation because detecting suspicious text and enforcing authority are different tasks.

Training data extraction is the memorization leak of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^sec-security-privacy-memorization-extraction|section 13.5.2.3]], in which generated text reproduces retained training sequences, including PII, without implying that the model stores a retrievable copy of every record. A third category, jailbreaking and alignment bypass, targets controls intended to keep generated behavior within policy. Reinforcement learning from human feedback shapes behavior during training ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-ouyang2022instructgpt|Ouyang et al. 2022]]), Constitutional AI uses critique against explicit principles ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-bai2022constitutional|Bai et al. 2022]]), and guardrail models classify inputs or outputs at runtime ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-inan2023llamaguard|Inan et al. 2023]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-shieldgemma2024|Google 2024]]). These learned controls do not establish a formal guarantee against every prompt; adversarial suffixes demonstrate one way to bypass them ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-zou2023|Zou et al. 2023]]). A deployment can combine behavioral training, separately evaluated monitors, query budgets, and review of consequential outputs. Their value depends on measured resistance to adaptive attacks and on the external permissions that limit what an unsafe output can cause.

### Availability Abuse and Denial of Wallet

^sec-security-privacy-availability-denial-wallet

Generative serving also exposes availability to an attack that needs no flood of requests. The cost of a request grows with the tokens it generates and the documents it retrieves, so an attacker can select requests that maximize that work or defeat cache reuse, consuming more accelerator time and downstream service capacity than ordinary traffic while the endpoint remains reachable. In this *denial-of-wallet* scenario, the asset under attack is the cost budget rather than only the request queue: autoscaling (**[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.14 Autoscaling and Capacity Control#^sec-inference-scale-autoscaling-capacity-control|Autoscaling and Capacity Control]]**) can preserve apparent availability by purchasing more capacity while spend and tail latency exceed their operating limits.

Availability defenses must therefore meter work, not merely request counts. The mechanisms are the overload controls that already protect a serving fleet; what security changes is the signal they act on, which becomes work and cost per authenticated principal rather than aggregate load. The serving boundary should assign budgets to input size, generated tokens, retrieval calls, concurrent work, and cumulative cost per authenticated principal. Admission control can reject or degrade requests before they reserve scarce accelerators; bounded generation, timeouts, circuit breakers, and per-request retrieval quotas limit the work admitted by any one request. Operators should monitor cost per successful result alongside latency and error rate because an attacker can preserve HTTP success while exhausting the service’s economic budget. These controls also constrain model extraction, but their availability objective is distinct. They keep adversarially induced work from displacing legitimate service or producing unbounded spend.

↩︎ Circuit breakers and backpressure, the serving fleet’s overload controls, are established in **[[01 Books/Volume II - Scaling/03 The Fleet in Production/10 Serving at Scale/V2-10.12 Load Balancing and Request Routing#^sec-inference-scale-circuit-breakers-backpressure-e61c|Circuit breakers and backpressure]]**.

While LLM control-data entanglement cuts across multiple objectives inside a single token stream, the five primary lifecycle objectives span distinct stages of the ML pipeline and demand targeted defensive strategies. Grouping those five objectives by lifecycle stage and attack vector ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^tbl-threats-models-summary|table 5]]) shows where each vulnerability appears and which mitigation it calls for.

| **Threat type**           | **Lifecycle stage** |     **Attack vector**     | **Example impact**                            |
|:--------------------------|:-------------------:|:-------------------------:|:----------------------------------------------|
| **Model Theft**           |     Deployment      | API access, insider leaks | Stolen IP, behavioral clone                   |
| **Training-Data Leakage** |      Inference      |    Authorized queries     | Memorized PII, membership disclosure          |
| **Data Poisoning**        |      Training       | Label flipping, backdoors | Targeted misclassification, degraded accuracy |

The appropriate defense depends on the attack vector, lifecycle stage, and available evidence. For each threat, assessment evidence and candidate controls play different roles ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^fig-threat-mitigation-flow|figure 14]]). Monitoring can reveal suspicious querying, while watermarking can support attribution after extraction; neither establishes that theft was prevented. Privacy audits measure attack success under tested conditions, whereas an accounted DP mechanism provides a formal bound under its stated assumptions. Each row identifies a design starting point, not a guaranteed detection-to-defense pipeline.

**Checkpoint 13.2: Knowledge check: Model attacks**

An autonomous vehicle’s vision system misclassifies a stop sign as a speed limit sign because of a specially crafted sticker placed on the sign. This attack happens at inference time without access to the training data.

**Attack timing**: distinguish this inference-time failure from a training-time compromise.

**Input mechanism**: explain how the attacker changed the model’s observed input without changing the model itself.

**Defense choice**: select the detection or robustness control that belongs closest to the serving path.

Model theft, output leakage, poisoning, and adversarial inputs all reach the model through an interface the fleet exposes on purpose: a query endpoint, a data feed, or a sensor. A fleet also has interfaces it never exposes to users, between its own workers, tenants, and nodes, and those interfaces carry the next set of threats.

**Self-Check: Question**

1.  A security architect must deploy defenses against two distinct model theft vectors: (1) an unauthorized party copying serialized model checkpoints from a cloud bucket, and (2) a competitor sending millions of synthetic queries to a public REST endpoint to distill a student model. Which combination of defenses correctly targets each vector?

    1.  Vector (1) requires output rounding and top-$k$ truncation; Vector (2) requires hardware security modules for model weights at rest.
    2.  Vector (1) requires differential privacy during training; Vector (2) requires air-gapping the inference server from the internet.
    3.  Vector (1) requires encrypted storage, signed model artifacts, and strict IAM/RBAC permissions; Vector (2) requires rate limiting, query anomaly monitoring, and confidence-score truncation.
    4.  Both vectors are mitigated exclusively by converting model checkpoints to Python pickle files.

2.  Data poisoning is formalized as a bilevel optimization problem. State the attacker’s untargeted outer objective and the defender’s inner training objective, and explain why evaluating a poison’s learning effect can be computationally demanding.

3.  Research on language model APIs (e.g., Carlini et al., 2024) demonstrated that output-projection matrices of models like OpenAI `ada` and `babbage` could be extracted with root-mean-square errors around $10^{-4}$ using fewer than $4 \times 10^6$ queries at a cost of under \$15. In an image API serving a 1,000-class classifier, what is the systems effect of replacing full softmax probability distributions with top-5 class predictions and rounding confidences to 2 decimal places?

    1.  It completely eliminates all adversarial perturbation vectors while increasing inference latency by 100x.
    2.  It introduces a formal $(\epsilon, \delta)$ differential privacy guarantee across all subsequent user queries.
    3.  It reduces model parameter size in GPU VRAM by 99.5% during the forward pass.
    4.  It returns 99.5% fewer distribution entries and coarser confidences; extraction resistance and legitimate-client utility require separate measurement.

4.  In the road-sign study, stickers on a stop sign changed only the input a deployed classifier received. Explain why a numerical perturbation norm alone does not establish physical feasibility or human recognizability, and what a physical threat model must state in addition.

5.  True or False: A model compromised by a backdoor attack (such as BadNets) will exhibit a noticeable drop in validation accuracy on standard, clean test datasets, allowing automated validation pipelines to flag the compromise before deployment.

6.  A team runs a shadow-model membership-inference audit against its model and finds attack accuracy barely above chance. Explain what this result establishes, what it does not, and what would supply a bound that holds against any membership test.
