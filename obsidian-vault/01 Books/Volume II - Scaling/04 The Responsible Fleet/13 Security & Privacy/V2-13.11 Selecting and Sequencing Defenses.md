# V2-13.11 Selecting and Sequencing Defenses

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13 Security & Privacy|V2-13 Security & Privacy]]

^sec-security-privacy-practical-roadmap-8f3a

Moving from mathematical guarantees to production controls requires more than setting an epsilon value. A common mistake is attempting to deploy every defense at once, including differential privacy, trusted execution environments, adversarial training, model watermarking, and red-team automation, while basic controls such as access boundaries and encrypted transport remain weak. Two decisions prevent that mistake. The first selects the defenses a deployment context requires; the second sequences them so that each control rests on the ones beneath it.

### Defense Selection by Deployment Context

^sec-security-privacy-defense-selection

A hospital training a federated diagnostic model on patient records and a public-facing customer chatbot face completely different attackers, latency budgets, and legal mandates. The hardware mechanisms of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.09 Comprehensive Defense Architectures#^tbl-hw-security-comparison|table 7]], the deployment and runtime controls, and the cryptographic and statistical privacy techniques of the data layer therefore form a menu rather than a fixed recipe. The appropriate defense for any given deployment depends on three interacting factors: the threat model (who attacks and with what capabilities), the deployment context (what computational and latency budgets exist), and the regulatory environment (what legal mandates constrain design). A defense selection framework maps seven common deployment contexts to their primary threats, recommended defense combinations, and the trade-offs each combination requires evaluating ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.11 Selecting and Sequencing Defenses#^tbl-defense-selection-framework|table 9]]). The rows that include differential privacy require an accounted mechanism, built from the sensitivity and composition machinery of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.10 Differential Privacy#^sec-security-privacy-differential-privacy-8c2b|section 13.9]], rather than a universal privacy-budget value.

| **Deployment context**                                         | **Primary threats**                                                              | **Recommended defenses**                                                                                                                                                                                                     | **Key trade-offs**                                                                                                                                                       |
|:---------------------------------------------------------------|:---------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Healthcare ML** (federated diagnostic models)                | Data leakage (HIPAA violation); membership inference; unauthorized access        | Accounted differential privacy for training when the threat model requires it; federated learning across hospitals; TEE for inference on sensitive data; audit logging and RBAC                                              | Privacy and TEE parameters require task-specific utility and latency measurement                                                                                         |
| **Financial ML** (fraud detection API)                         | Model theft (IP loss); adversarial evasion; data poisoning                       | Model encryption (AES-256) at rest; HSM for cryptographic key management; adversarial training on perturbed transactions; input validation and per-principal rate limiting; output confidence monitoring                     | HSM units cost roughly \$20,000–\$100,000 each before integration and certification; rate limiting may impact legitimate high-frequency users                            |
| **Edge ML** (mobile/IoT devices)                               | Physical access; side-channel attacks; model extraction                          | Secure boot; a suitable TEE; authenticated encrypted model storage; PUF-backed device identity                                                                                                                               | Protected working set, paging support, power cost, and physical-attack resistance depend on the platform                                                                 |
| **Cloud ML Training** (multi-tenant platform)                  | Data poisoning; backdoor injection; gradient leakage                             | Secure data pipelines with provenance; accounted DP-SGD when participation leakage is in scope; gradient verification and anomaly detection; secure aggregation for federated training; model watermarking for IP protection | DP and verification overhead depend on implementation and workload; federated aggregation requires authenticated, confidential communication                             |
| **Public-Facing LLM** (chatbot/API)                            | Prompt injection; data extraction (training leakage); abuse/overuse              | Instruction-data separation; input/output policy checks; isolated execution; authentication and rate budgets                                                                                                                 | Measure latency and false-positive cost; filtering and confidence scores do not guarantee resistance to injection                                                        |
| **Multi-Party ML** (cross-organizational training)             | Data sharing restrictions; curious or malicious participants; regulatory duties  | Federated learning (no raw data sharing); SMPC for secure aggregation; accounted differential privacy when participation leakage is in scope; homomorphic encryption for selected operations                                 | Communication and cryptographic overhead depend on topology and protocol; utility must be measured for the selected privacy mechanism; requires agreements for liability |
| **Critical Infrastructure** (autonomous vehicles, power grids) | Supply chain compromise; real-time adversarial attacks; safety-critical failures | Hardware attestation (trusted platform module, or TPM, and PUF); Secure Boot and runtime integrity checks; redundant model validation; fault injection detection; fail-safe fallback mechanisms                              | Validate physical threat coverage, latency, fail-safe behavior, and the required assurance process                                                                       |

Table 9: **Defense Selection Framework**: Maps deployment contexts to threat-specific defensive strategies and deployment trade-offs. The framework provides starting points for security architecture design, highlighting primary threats, recommended defense combinations, and key implementation trade-offs across seven common ML system deployment scenarios.

**Checkpoint 13.5: Mapping hardware and deployment threats to defenses**

The chapter introduced six hardware-level attack categories, four hardware-security primitives ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.09 Comprehensive Defense Architectures#^tbl-hw-security-comparison|table 7]]), and a framework mapping seven deployment contexts to full-stack defenses ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.11 Selecting and Sequencing Defenses#^tbl-defense-selection-framework|table 9]]). Apply that combined mapping to the scenarios below.

**Primitive matching**: match fault injection on model weights and side-channel extraction from the inference pipeline to the most relevant hardware-security primitives and runtime controls across the critical-infrastructure and edge rows of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.11 Selecting and Sequencing Defenses#^tbl-defense-selection-framework|table 9]].

**Edge defense stack**: select a combination of hardware and deployment controls for an edge inference deployment facing physical access, side-channel attacks, and model extraction.

**Supply-chain gap**: identify which supply-chain compromises remain outside the four hardware primitives’ guarantees in the selected edge or cloud-training deployment, and specify the provenance or inspection evidence needed to assess those risks.

**TEE vs. attestation**: distinguish runtime isolation from cryptographic evidence about an execution environment, and identify which fault-injection, counterfeit-hardware, and output-leakage risks remain outside those guarantees.

A recurring theme across [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.11 Selecting and Sequencing Defenses#^tbl-defense-selection-framework|table 9]] is the cost of privacy. Differential privacy appears in three of seven deployment contexts, and each such row exposes an accuracy or systems cost that must be weighed against regulatory mandates and risk tolerance. The table is therefore a deployment triage tool rather than a universal recipe, because serialization, artifact integrity, access control, runtime isolation, and privacy budgets each defend a different boundary. Selecting the right defenses for a context settles what to build; the maturity model settles the order in which to build it.

### Security and Privacy Maturity Model

^sec-security-privacy-maturity-model

Deploying homomorphic encryption or a red-team harness while model checkpoints sit in an unauthenticated bucket and API keys lack per-principal budgets leaves the easiest attack paths wide open. A maturity model asks which system property is currently unprotected: access boundary, data privacy, model integrity, adversarial robustness, or governance evidence. The dependency structure in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.11 Selecting and Sequencing Defenses#^tbl-security-privacy-maturity-model|table 10]] keeps that choice tied to the boundary being defended.

| **Maturity layer**                | **Primary question**                                       | **Control family**                                                                  |
|:----------------------------------|:-----------------------------------------------------------|:------------------------------------------------------------------------------------|
| Access and configuration boundary | Who can touch data, weights, deployments, and logs?        | Least privilege, service identity, encrypted transport, audit logging               |
| Data and privacy boundary         | What can be learned from training, fine-tuning, or output? | Privacy accounting, output limiting, secure aggregation, sensitive-data isolation   |
| Model integrity boundary          | How is the validated model and data path authenticated?    | Signed artifacts, registry controls, hash checks, release gates, rollback paths     |
| Adversarial and abuse boundary    | What can an adaptive attacker extract, infer, or induce?   | Query monitoring, rate limiting, robustness evaluation, red-team exercises          |
| Governance and evidence boundary  | Which obligations must be proven after deployment?         | Compliance mapping, incident records, retention policy, reproducible control checks |

Table 10: **ML Security and Privacy Maturity Model**: Security controls should be added according to the threat model and deployment context. The order is not a calendar; it is a dependency structure from basic access boundaries to stronger privacy, integrity, adversarial, and governance controls.

^tbl-security-privacy-maturity-model

The maturity layers are cumulative. Access controls and encrypted channels close paths that model-interface defenses do not cover, such as an exposed registry. Privacy analysis begins with the original training data and continues through fine-tuning, personalization, and telemetry feedback loops. When DP is required, the release budget becomes a system resource covering the relevant training, selection, and evaluation mechanisms that access protected data. Model-integrity controls protect the artifact path: signed manifests, key management, hash checks, and release gates connect the loaded model to the approved version, subject to the enforcement boundary remaining intact.

Adversarial evaluation tests deliberate, adaptive behavior in addition to accidental failures. Query monitoring and output limiting constrain extraction attempts, while robustness evaluation and red-team exercises test whether an attacker can induce unsafe behavior. Trusted execution environments and certified robustness defenses protect different boundaries, so each needs a threat model that justifies its costs and assumptions. Governance defines obligations and evidence requirements from the start, rather than entering only after technical controls. Audit logs, compliance mappings, incident records, and reproducible checks then help assess whether those obligations remain satisfied as the model, data, and traffic change.

Different domains traverse the model differently. A healthcare deployment prioritizes privacy accounting and governance evidence before broad patient-facing use. A financial fraud system emphasizes access control, model integrity, and abuse monitoring because extraction and evasion directly change loss exposure. An autonomous system emphasizes adversarial robustness and incident evidence because safety depends on behavior under distribution shift and physical-world perturbations. The point is not to follow a universal implementation calendar; it is to make the threat model determine which control boundary must mature next.

The evidence produced by these controls supports a separate governance decision: which uses are permitted, who accepts residual risk, and who can require remediation. **[[01 Books/Volume II - Scaling/04 The Responsible Fleet/16 Responsible AI/V2-16.03 The Governance and Assurance Lifecycle#^sec-responsible-ai-governance-assurance-lifecycle|The Governance and Assurance Lifecycle]]** develops those institutional responsibilities. Here the engineering obligation is to make access decisions, release budgets, and incident histories verifiable. By sequencing controls around those boundaries, the maturity model moves security from reactive patching toward proactive threat control, though even well-designed systems can still fail when teams mistake a local mechanism for a complete guarantee.

**Self-Check: Question**

1.  An ML team wants to deploy automated red-teaming adversarial evaluations and differential privacy accounting on their newly deployed recommender service. However, their model registry permits unauthenticated write access and internal API calls lack TLS encryption. According to the ML Security and Privacy Maturity Model, why is this defensive plan structurally flawed?

    1.  The open registry permits artifact substitution and cleartext channels can expose payloads; those paths need controls even when a correctly released DP artifact retains its release-level guarantee.
    2.  Differential privacy cannot be mathematically calculated unless the model registry uses hardware security modules.
    3.  Adversarial red teaming is strictly illegal under GDPR without prior completion of ISO 27001 certification.
    4.  Red-teaming algorithms require unencrypted network channels to simulate black-box query traffic.

2.  Compare how a healthcare diagnostic ML system and an autonomous vehicle perception system should prioritize their progression through the ML Security and Privacy Maturity Model based on their distinct threat models.

3.  To enforce the Model Integrity Boundary in a continuous deployment ML pipeline, which set of controls connects the served checkpoint to the approved artifact, assuming the verification and enforcement boundary remains trusted?

    1.  Applying randomized output perturbation at the web proxy layer without checking checkpoint signatures.
    2.  Cryptographic signing of model packages, SHA-256 checksum verification against an authenticated registry manifest, and automated release gates with rollback paths.
    3.  Adding Laplace differential privacy noise to the model weights prior to saving checkpoints.
    4.  Storing model checkpoints in Python pickle format on public, unauthenticated object buckets.

4.  At the foundational Access and Configuration layer of the maturity model, enforcing the principle of \_\_\_\_ ensures that data engineers, ML researchers, and inference services possess only the minimum permissions required for their specific lifecycle tasks.
