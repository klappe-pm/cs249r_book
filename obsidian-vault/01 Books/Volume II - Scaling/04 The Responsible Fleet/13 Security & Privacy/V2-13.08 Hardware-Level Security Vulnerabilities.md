# V2-13.08 Hardware-Level Security Vulnerabilities

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13 Security & Privacy|V2-13 Security & Privacy]]

^sec-security-privacy-hardwarelevel-security-vulnerabilities-1ab4

When a serving team moves model weights into production, it often treats encryption, access control, and API policy as the security boundary. Hardware attacks break that assumption. A processor can leak across isolation domains, a field device can be opened, a bus or power rail can expose signals, and a counterfeit component can enter the system before deployment begins. Hardware therefore belongs inside the threat model, as the substrate that can invalidate software controls after those controls appear to pass.

The practical deployment question is which substrate layer can still violate trust. A cloud LLM endpoint is mostly an isolation problem, because one tenant’s process, memory, and accelerator context must not reveal another tenant’s prompts or weights. An embedded vision sensor is mostly a physical-access problem, because the attacker may probe power, attach to a debug port, or replace a module. A regulated procurement pipeline is mostly a provenance problem, because the organization must know which components were built, handled, patched, and retired. These cases use different defenses, but they share the same reasoning pattern.

Hardware security planning therefore begins with four fundamental checks. Processor isolation must separate tenants, cryptographic keys, model weights, and intermediate activations from untrusted code and co-tenants. Physical-access controls must protect devices, sensors, memory, and debug interfaces when attackers can physically touch the hardware. Side-channel evaluation tests whether observable power, timing, electromagnetic, bus, or thermal signals expose sensitive computation despite those boundaries. Finally, supply-chain validation checks evidence that the deployed component matches the component the system was designed and certified to use. Each check needs an explicit attacker model; passing it does not establish protection against access or measurements outside that model.

Grouping the hardware threat landscape by these four checks rather than by attack family ties each vulnerability to the deployment decision that controls it ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.08 Hardware-Level Security Vulnerabilities#^tbl-threat-types-07efa48b|table 6]]). The defensive strategies in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.09 Comprehensive Defense Architectures#^sec-security-privacy-comprehensive-defense-architectures-48ab|section 13.8]] return to the same decisions from the perspective of trusted execution, attestation, and hardware roots of trust.

| **Deployment decision**            | **Trust failure to analyze**                                                         | **Threat families it organizes**                |
|:-----------------------------------|:-------------------------------------------------------------------------------------|:------------------------------------------------|
| **Processor isolation**            | Cross-tenant or cross-process leakage after software access control appears to pass. | Hardware bugs, speculative execution flaws.     |
| **Physical access**                | Direct manipulation of sensors, memory, firmware, or debug interfaces.               | Physical attacks, fault injection, leaky ports. |
| **Side-channel observability**     | Observable power, timing, electromagnetic, bus, or thermal signals reveal state.     | Side-channel attacks, leaky interconnects.      |
| **Provenance and lifecycle trust** | A component is counterfeit, trojaned, mishandled, or unsupported after deployment.   | Counterfeit hardware, supply chain risks.       |

Table 6: **Hardware Threat Landscape**: Hardware security decisions group diverse vulnerability families into isolation, physical-access, side-channel, and provenance questions that determine whether software protections remain meaningful in deployment.

^tbl-threat-types-07efa48b

Each threat family tests one of those decisions. Hardware bugs test processor isolation. Physical attacks, fault injection, and leaky interfaces test whether direct access can change the system after software controls pass. Side-channel attacks test whether computation leaks through observable signals. Supply chain risks, from a single counterfeit part to a compromised part number, test whether the deployed component is the one the architecture assumes. Because a fleet deploys many identical copies of a few parts, a weakness that fails one of these checks on one machine can fail it on every copy at once.

### Hardware Bugs

^sec-security-privacy-hardware-bugs-9efc

When tenants share a cloud host, a transient-execution flaw such as Spectre or Meltdown in the CPU can leak decrypted keys, prompts, or feature batches across process boundaries after software access checks have already passed ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-lipp2018meltdown|Lipp et al. 2018]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-kocher2019|Kocher et al. 2019]]). Hardware bugs therefore test the first deployment decision: whether processor isolation can be trusted as an empirical boundary rather than a default guarantee. Attackers can exploit these microarchitectural design flaws to bypass memory isolation and read the data of co-tenant applications and the operating system.

Spectre exploits speculative execution, a performance optimization in which a CPU executes instructions along a predicted path before it knows whether that path is correct. An attacker influences the prediction so that a victim transiently accesses sensitive data. Meltdown instead exploits affected processors that transiently make data available before enforcing the access restriction. In both cases, discarding the unauthorized or mispredicted computation can leave observable traces in microarchitectural state, such as CPU caches. Software-visible execution can therefore respect a boundary while the traces of transient execution leak across it.

Further research identified related transient-execution attacks, including Foreshadow, ZombieLoad, and RIDL, against different microarchitectural structures in affected processors. Their existence motivates examining each component’s isolation assumptions without assuming that every processor shares the same vulnerability. ML systems pair CPUs with GPUs, Tensor Processing Units (TPUs), field-programmable gate arrays (FPGAs), or custom accelerators. A compromise can propagate across this heterogeneous stack when components share sensitive data, keys, or privileged access; the threat model must trace those relationships.

For a fleet, the consequence can be cross-tenant exposure. Host processors stage data for accelerators, run tokenizers and preprocessing, and hold decrypted keys. When tenants share a vulnerable host and the required attack conditions hold, a transient-execution flaw can expose sensitive state before any accelerator is involved. Mitigations depend on the vulnerability and deployment: restricting simultaneous multithreading, in which two threads share one core’s execution resources, or clearing affected microarchitectural state at isolation boundaries can reduce throughput on the data-loading and serving paths that keep accelerators fed. The fleet must remeasure those paths after applying the relevant protections rather than assume a fixed overhead.

Hardware security therefore extends beyond physical tamper prevention to architectural isolation: preventing processors, accelerators, and memory systems from leaking across boundaries the software assumes are sealed. Mitigations often carry performance costs, especially for data-bound ML workloads, so confidential computing ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.07 Fleet-Internal Trust Boundaries#^sec-security-privacy-fleet-attestation|section 13.6.4]]) and trusted execution environments (TEEs) must be evaluated as capacity and latency decisions as well as security decisions.

### Physical Attacks

^sec-security-privacy-physical-attacks-095a

An attacker who can physically touch an edge drone or biometric kiosk can swap a camera module, probe a memory bus, or attach to an unlocked debug port, bypassing every network firewall and API policy. Physical attacks test the second deployment decision: what an adversary can observe or modify by touching the device, sensor, memory, firmware, or debug interface. An exposed debug port may permit memory reads, a replacement sensor may supply false inputs, and a writable firmware interface may change execution. Encryption and authentication remain useful when their keys and enforcement mechanisms stay protected; the threat model must identify which physical paths bypass those protections.

The failure mode depends on what the attacker can touch. Replacing a drone’s navigation module, swapping the sensor of a biometric access system, or misaligning a vehicle’s cameras changes system behavior without changing a single model weight. In edge fleets such as the phone-class devices of Archetype C (Federated MobileNet), the coordinator does not control clients’ physical environments. Device ownership does not automatically defeat protected storage or execution, but the coordinator cannot infer the integrity of a client’s data or updates from ownership or enrollment alone.

Internal components create the same risk at a lower layer. A hardware trojan inserted during chip fabrication can remain dormant until a specific input or state triggers it, then leak outputs, corrupt computation, or degrade performance in ways that are difficult to diagnose after deployment. Memory chips and accelerator buses can expose model parameters or training data when an attacker has physical access. Data centers are not exempt. An implant installed by someone with sufficient facility access can monitor administrative credentials or data streams and provide a persistent path into training and inference pipelines.

The defensive implication is that physical-access analysis belongs in the system architecture rather than solely in device packaging. Disabling production debug interfaces closes one access path; signed firmware and secure boot constrain which code can execute. Tamper detection can signal interference, while attestation and supply chain checks provide evidence about measured state and component provenance. These controls address different parts of the trust boundary, so none alone establishes that sensor inputs or runtime computations remain correct after deployment.

### Fault Injection Attacks

^sec-security-privacy-fault-injection-attacks-8c52

A timed voltage glitch or laser pulse on a microcontroller can skip a single assembly jump instruction in a ReLU layer, zeroing out an activation and forcing a safety-critical misclassification without altering a single stored weight ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-breier2018|Breier et al. 2018]]). Fault injection is the active version of the physical-access decision: the attacker does not replace the model artifact but changes the computation while it runs. A precisely timed voltage drop, power spike, clock glitch, temperature shift, electromagnetic pulse, or laser strike can induce bit flips, skipped instructions, or corrupted memory states ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-joye2012|Joye and Tunstall 2012]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-barenghi2010|Barenghi et al. 2010]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-hutter2009|Hutter et al. 2009]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-amiel2006|Amiel et al. 2006]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-skorobogatov2009|Skorobogatov 2009]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-skorobogatov2002|Skorobogatov and Anderson 2003]]). For ML systems, those faults can force incorrect outputs, bypass security checks, degrade reliability, or expose internal state for later reverse engineering.

The ML-specific risk is that a small computation fault can become a semantic failure. An embedded classifier running on a microcontroller may misclassify a safety-important input, while a fault in memory or control logic may expose proprietary weights or architecture details. Unlike ordinary random faults, adversarially timed faults are chosen to land on computations the model or security protocol depends on.

The experiments of Breier et al. ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-breier2018|2018]]) targeted activation-function implementations on a microcontroller with timed laser faults. [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.08 Hardware-Level Security Vulnerabilities#^fig-injection|Figure 16]] identifies the vulnerable instruction in the observed ReLU implementation. For a positive accumulator, the copy instructions assign the activation to the output, and the following `jmp end` normally skips the zeroing block. A laser pulse timed to suppress that jump makes execution fall through into the clear instructions, overwriting the positive output with zero and forcing the neuron inactive. The fault changes executed control flow rather than any stored model weight.

![[90 Assets/Volume II/13 Security Privacy/Fault Injection Assembly e036aa4668.svg]]

Figure 16: **Fault Injection Attack**: A timed laser pulse that skips the unconditional jump at line 6 forces a positive ReLU activation through the zeroing block at lines 7–10. The fault changes executed control flow without changing the stored model parameters.

^fig-injection

Fault injection attacks can also be combined with side-channel analysis, where attackers first observe power or timing characteristics to infer model structure or data flow. This reconnaissance helps them time faults against specific layers or operations, such as activation functions or final decision layers. The resulting effect still depends on the implementation, the induced fault, and any checks that detect or contain it.

Embedded and edge ML systems can be vulnerable when exposed hardware combines with resource constraints that limit runtime defenses. Access to system buses, memory, or power supplies can give attackers opportunities to induce faults, even when software access controls remain intact. The relevant protection comes from the device and execution stack: a lightweight model does not itself establish whether memory has error correction, computations have redundant checks, or packaging resists probing.

The defense must combine physical hardening with runtime evidence. Tamper-resistant packaging restricts access, while design obfuscation makes targets harder to locate without itself preventing interference. Error-correcting memory and redundant checks can detect or correct some induced errors; secure firmware constrains code changes but does not prevent a fault during execution. Model-output and sensor-consistency monitors can catch some fault-induced behavior that escapes lower layers; MAVFI demonstrates this pattern for micro-aerial-vehicle workloads with anomaly detection and recovery ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-hsiao2023|Hsiao et al. 2023]]). These protections are hardest in cost- and power-constrained edge systems, where extra cryptographic hardware or redundancy may be unaffordable, so resilience has to be designed across the electrical, firmware, software, and system layers.

A data center fleet rarely faces a laser, but it faces the same class of failure in two other forms. Without any attacker, marginal processors corrupt computation silently at fleet scale. With an attacker, shared electrical resources can provide a path for interference. Co-tenants on a shared FPGA have induced timing faults remotely by drawing enough current to drop the supply voltage ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-gnad2017|Gnad et al. 2017]]). The check-and-verify defenses of **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.06 Check-And-Verify Defenses Against Silent Data Corruption#^sec-ft-sdc-verification|Check-and-Verify Defenses Against Silent Data Corruption]]** can therefore serve security as well as reliability. Their security coverage requires separate evaluation, however, because an attacker may target both the computation and its check rather than induce the independent errors a reliability analysis assumes.

↩︎ Silent data corruption from probabilistic hardware faults at fleet scale is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.06 Check-And-Verify Defenses Against Silent Data Corruption#^sec-fault-tolerance-reliability-physics-silent-corruption-5d5d|The physics of silent corruption]]**.

### Side-Channel Attacks

^sec-security-privacy-sidechannel-attacks-cdfd

Even when every network port and debug interface is locked down, variations in power draw, electromagnetic emissions, or cache timing during a forward pass can reveal secret keys, layer topologies, or user inputs ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-kocher1999|Kocher et al. 1999]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-gandolfi2001|Gandolfi et al. 2001]]). Side-channel attacks test the third deployment decision: whether computation is observable through physical or shared-resource signals when explicit interfaces are sealed. Measuring and analyzing power, electromagnetic, timing, or acoustic signals lets an attacker infer internal state or recover secret data without exploiting any software or network vulnerability.

ML accelerators executing inference are exposed to physical leakage as other computing devices are. A matrix multiplication on an edge accelerator can draw current in a pattern correlated with the weight values and input activations being processed. An attacker who can measure that signal may infer properties of the computation, but recovery depends on measurement quality, implementation details, and knowledge or control of inputs. Additional samples help only if the observable signal carries the relevant information. The side-channel surface for a deployed model therefore encompasses both the cryptographic operations protecting its keys and the inference computation itself.

Studies of Advanced Encryption Standard (AES) implementations showed that an implementation can leak information about a key without an attacker breaking the cipher’s mathematical construction. The same distinction between an algorithm and its implementation applies to the ReLU activations, softmax normalizations, and weight-load sequences that constitute a forward pass.

Power analysis of a password check shows the mechanism in its simplest form ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-kocher2011|Kocher et al. 2011]]). A device that compares a 5-byte password one byte at a time draws a stable power profile while the bytes match, and [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.08 Hardware-Level Security Vulnerabilities#^fig-encryption2|figure 17]] shows the trace jump at the first wrong byte, where the device halts the comparison.

![[90 Assets/Volume II/13 Security Privacy/Power Analysis Of An Encryption Device With A Partially Wrong Password 836eaf66ff.png]]

Figure 17: **Side-Channel Attack Vulnerability**: Power consumption patterns reveal information about a password comparison; consistent power usage indicates correct password bytes, while abrupt changes signal incorrect input and halted processing. Even without knowing the password, an attacker can infer it by analyzing the device’s power usage during authentication attempts. Source: Colin O’Flynn.

^fig-encryption2

The position of the jump reveals how many leading bytes are correct, so repeated guesses collapse a search over all $256^5$ strings into five searches of 256 values each. ML inference can expose analogous data-dependent behavior when a microcontroller branches on a ReLU input’s sign or hardware skips zero values, producing signals correlated with activation sparsity. Recovering layer topology or parameters from such a signal requires a further inference step supported by the implementation and the available measurements.

The underlying lesson is physical. Computation emits signals, whether as the sound of a cipher machine ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-wright1987spycatcher|Wright and Greengrass 1987]]) or of a laptop running a cipher ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-genkin2017acoustic|Genkin et al. 2017]]), the clicks of a keyboard ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-asonov2004|Asonov and Agrawal 2004]]), or the current drawn by a processor. For a fleet, the important variant needs no probe at all. On shared hardware, the shared resource itself becomes the measurement instrument. Researchers built a power monitor from logic in their own region of an FPGA shared among users and used it to recover a cryptographic key computed in another user’s region ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-zhao2018|Zhao and Suh 2018]]). The sharing that makes multi-tenancy economical turns caches, memory bandwidth, and power delivery into channels between tenants.

Machine learning systems inherit this risk when accelerators or edge devices process sensitive data near an observable signal. A local speech-recognition device may leak timing or power patterns correlated with commands. An accelerator may reveal layer structure, parameter access patterns, or batch shape through timing, power, or electromagnetic traces. Side-channel defense therefore asks which signals are observable in the deployment environment and whether shielding, constant-time execution, noise, monitoring, or physical access controls can reduce the signal enough to preserve the trust boundary.

#### Learned Side-Channel Analysis

^sec-security-privacy-case-study-deep-learning-sca-b0b3

Machine learning also changes the attacker’s side of this analysis. Extracting a key from noisy power traces requires finding signal patterns associated with secret-dependent computations, and a convolutional neural network can learn those patterns from labeled traces, turning part of the analysis into a learned classification task. The attacker still needs suitable measurements and training data, but can reuse the trained model across repeated attempts under compatible conditions. The SCAAML framework (Side-Channel Attacks Assisted with Machine Learning), developed by researchers at Google, is a widely studied and reproducible demonstration of this learned pipeline ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-bursztein2024|Bursztein et al. 2024]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-burszteindc27|Bursztein and Picod 2019]]).

Power drawn during an AES S-box substitution depends on the data being processed ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.08 Hardware-Level Security Vulnerabilities#^fig-side-channel-curves|figure 18]]). The left panel places a possible leakage interval within a longer trace; the right panel magnifies a schematic difference between processed values. Hamming weight counts the ones in a binary value: 1111 has weight 4, 0101 has weight 2, and 0000 has weight 0. The drawing orders amplitudes by that weight to illustrate a leakage model, not a measured law of CMOS switching. Actual leakage depends on circuit structure, state transitions, noise, and countermeasures. A classifier must learn a reproducible relationship in measured traces before these differences can support key recovery.

![[90 Assets/Volume II/13 Security Privacy/Cell 12 Output 1 26b275ecdb.png]]

Figure 18: **Power Traces**: Cryptographic computations reveal subtle, data-dependent variations in power consumption that reflect internal states during specific operations. The traces are schematic: amplitudes are illustrative and follow the Hamming-weight ordering rather than a measured capture.

^fig-side-channel-curves

Statistical methods use an explicit leakage model. A neural network instead learns features from labeled traces, and its predictions of an intermediate value are combined across traces to score candidate key bytes. This works only if the learned relationship generalizes to traces not used in training.

In a SCAAML guide, Bursztein and Picod ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-burszteindc27|2019]]) used convolutional neural networks (CNNs) to recover AES keys from power traces collected on an STM32F415 microcontroller running the open-source TinyAES implementation. The models predicted intermediate values of the AES algorithm, such as the output of the S-box[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn9|⁹]] in the first round, from power traces. The demonstration recovered a full 128-bit key by combining byte-level predictions. Its target was an unprotected implementation, so the number of traces it needed sets no expectation for devices with masking, shuffling, or other countermeasures.

Learned side-channel models can reduce the analysis effort or trace count of an attack when suitable training data and measurable leakage are available. In a fleet built from a few part numbers, reusable attack models create correlated risk. Transfer still requires evaluation across devices, firmware, measurement conditions, and countermeasures; matching part numbers alone do not guarantee it. The defensive response must therefore address both the attacker’s access to measurements and the leakage of the computation itself.

### Leaky Interfaces

^sec-security-privacy-leaky-interfaces-9206

Whereas side-channel attacks leak through unintended physical signals, leaky interfaces expose information or accept unverified inputs through diagnostic, update, and communication channels the system already provides. An exposed baseboard management controller in a data center rack or an active JTAG debug port on a field camera allows an attacker to read memory or rewrite firmware while bypassing every OS and model-layer defense, placing leaky interfaces directly between physical access and lifecycle trust.

A leaky interface is any access point that reveals more information than intended or accepts commands from the wrong actor. The common causes are weak authentication, missing encryption, inadequate isolation, and development interfaces left exposed in production. Consumer, medical, and industrial systems have repeatedly shown the pattern: Wi-Fi-enabled baby monitors have exposed unsecured remote access ports,[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn10|¹⁰]] and pacemaker vulnerabilities[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn11|¹¹]] have shown how wireless interfaces can become safety-critical control channels. Debug ports[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn12|¹²]] left enabled on production devices are the canonical hardware case: a consumer smart lightbulb, for example, exposed unencrypted Wi-Fi credentials through such a port, giving attackers a path into the home network without defeating any network defense.

The data center has its own privileged maintenance interfaces. A server’s baseboard management controller commonly supports power control, console access, and firmware management over an out-of-band network, independently of the host operating system. Compromising its credentials or firmware can therefore expose control paths that host access policies do not govern. The resulting reach depends on network segmentation, controller privileges, and firmware-update protections. The attestation checks of [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.07 Fleet-Internal Trust Boundaries#^sec-security-privacy-fleet-attestation|section 13.6.4]] help only when trusted measurements cover the affected components and the attacker cannot forge the evidence or alter the verifier’s approved state. The same reasoning applies at the edge, where a maintenance interface that lacks authentication can expose user data, alter model weights, or disable security features.

Securing interfaces is therefore inventory work as much as cryptography. Strong authentication, encrypted communication, anomaly detection, access-control policy, periodic audit, and zero-trust defaults all serve the same principle: every interface must justify what it exposes and who can use it.

### Supply Chain Risks

^sec-security-privacy-supply-chain-risks-c99c

Supply chain risks extend the provenance decision from exposed maintenance interfaces to every hardware and software component across every stage of its life. A counterfeit memory module, modified network interface card (NIC) firmware, or compromised open-source dependency replicated across 128 cluster nodes introduces a backdoor before the first training job even starts. The smallest unit of this risk is the counterfeit part. A counterfeit processor, memory module, sensor, or network device may look and function like a genuine one while degrading faster, failing under load, or containing hidden circuitry, so procurement becomes part of the security boundary. Organizations that unknowingly deploy such parts may also violate safety, privacy, or cybersecurity obligations, which makes component provenance evidence that the deployed system matches the certified one.

A component’s life runs through design, fabrication, assembly, distribution, and deployment ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.08 Hardware-Level Security Vulnerabilities#^fig-hw-supply-chain|figure 19]]), and each stage presents opportunities for tampering or substitution. Recycled electronic waste can be relabeled as new, distributors can mix cloned parts into legitimate shipments, and insiders at manufacturing facilities can embed hardware trojans that routine functional tests may miss. Micrography, X-ray screening, and functional testing provide different evidence, with coverage and cost determined by the suspected modification. Procurement therefore needs risk-based provenance controls as well as inspection; passing a functional test does not establish a component’s origin or exclude dormant malicious behavior.

Fleet procurement changes the shape of this risk. A training cluster is bought in bulk from a small number of part numbers, so each of the 128 nodes of the reference cluster carries the same accelerators, network adapters, management controller, and firmware images as every other. A compromised shared design, firmware release, or production batch can therefore affect many nodes at once. Replication does not remove a vulnerability shared by the replicas, although one compromised unit is evidence about its part number, not proof that every unit carrying it is affected. The provenance bound on trust (principle [[01 Books/Volume II - Scaling/04 The Responsible Fleet/V2 Responsible Fleet Principles#^pri-provenance-bounds-trust|22]]) applies to silicon and firmware as much as to data. Supplier, batch, and firmware records help identify the affected population; supplier concentration increases common dependencies even when those records are complete.

![[90 Assets/Volume II/13 Security Privacy/Hw Supply Chain 1b23a58f1f.svg]]

Figure 19: **Hardware Supply Chain Attack Surface**: Each lifecycle stage admits its own compromise (red arrows) and needs its own assurance evidence (green gates); no single check covers the chain, and dashed lines carry each missed compromise forward to deployment. Unlike software, which can be patched remotely, a compromise that survives to deployment often requires physical replacement.

^fig-hw-supply-chain

Hardware compromise also changes the economics of response. Software vulnerabilities can often be patched remotely, but a hardware compromise that slips past every check to deployment ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.08 Hardware-Level Security Vulnerabilities#^fig-hw-supply-chain|figure 19]]) may require physical replacement. That possibility adds replacement cost, service interruption, and revalidation to the expected loss and strengthens the case for preventive checks before deployment.

A disputed 2018 report of surveillance chips implanted on server motherboards, which the named companies publicly denied ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-TheBigHa77|Robertson and Riley 2018]]), shows why allegations must be separated from verified compromise. A claim about deployed components needs evidence from the relevant fabrication, assembly, distribution, and integration stages, and component validation, runtime monitoring, attestation, and hardware roots of trust each supply part of that evidence.

The engineering takeaway is that hardware trust must be evidenced continuously across design, fabrication, procurement, deployment, and retirement. A trusted execution environment (TEE) isolates selected code and data from parts of the surrounding host. Attestation supplies cryptographic evidence about that protected environment before another component entrusts it with secrets. Neither mechanism establishes that a model is behaviorally correct, and both depend on an explicit set of trusted hardware and software components.

**Checkpoint 13.3: Knowledge check: Hardware security**

Before moving from hardware threats to the defenses anchored in hardware, check that each vulnerability family is attached to the deployment decision it tests.

**Processor isolation**: explain how a transient-execution flaw can expose a co-tenant’s prompts or keys even after software access control passes.

**Physical access**: distinguish what fault injection changes in a running computation from what a side-channel attack observes about it.

**Interfaces**: identify a maintenance or debug interface in a training node or edge device that host access policies do not govern.

**Correlated risk**: explain why a compromised part number threatens a fleet differently from a compromised individual device.

These hardware threats endanger the model, its data, and the execution environment that protects them. They also set the limit of every software control examined so far, because each of those controls assumes that some layer beneath it remains trustworthy. A defense architecture must therefore state which components it trusts and what each layer adds when another fails.

**Self-Check: Question**

    1.  Transient instructions can encode protected data in cache state that remains measurable after the processor discards their architectural effects.
    2.  Speculative execution permanently overwrites physical DRAM cells with ciphertext keys without notifying the OS kernel.
    3.  The CPU floating-point unit truncates FP32 tensor activations to INT8 during branch prediction.
    4.  Speculative branch predictors disable hardware-level AES encryption engines on PCIe accelerator interconnects.

    1.  By sending malformed TCP packets that trigger core dumps over the microcontroller’s UART interface.
    2.  By measuring instruction-dependent power consumption waveforms where current draw varies with weight values, multiplication operand hamming weights, and ReLU pre-activation signs.
    3.  By overwriting the microcontroller’s secure boot ROM keys using over-the-air firmware updates.
    4.  By inducing thermal shutdown to force the microcontroller to reboot into an unauthenticated recovery bootloader.
