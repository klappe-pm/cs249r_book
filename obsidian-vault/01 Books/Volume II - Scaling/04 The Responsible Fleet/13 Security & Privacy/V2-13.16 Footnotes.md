# V2-13.16 Footnotes

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13 Security & Privacy|V2-13 Security & Privacy]]

^footnotes

<sup>1</sup> **Air-gapped**: Physical network separation does not eliminate transfer paths through removable media or authorized personnel. An isolated ML training cluster still needs a controlled process for admitting frameworks, datasets, and pretrained weights; each transfer must preserve the intended trust boundary.

^fn1

<sup>2</sup> **GDPR (General Data Protection Regulation)**: Article 17 establishes a right to erasure under specified grounds and exceptions. For an ML pipeline, responding to an applicable request requires tracing personal data through source records, derived datasets, logs, and deployed artifacts. Whether a trained model requires remediation depends on the data it retains and the applicable obligation; deleting a source row does not establish that every derived copy or learned disclosure has been removed. Retraining and machine unlearning are possible technical responses whose effectiveness requires separate validation.

^fn2

<sup>3</sup> **Model serialization**: Python’s pickle format, common in PyTorch checkpoint workflows, can execute arbitrary code during deserialization, so loading an untrusted checkpoint is equivalent to running untrusted code. Formats such as SafeTensors store only tensor data and remove that execution path ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-huggingface-safetensors-51152970|Hugging Face 2026]]).

^fn3

<sup>4</sup> **ML side-channel attacks**: Timing or power observations can reveal properties of inference even when model files and query outputs are restricted. Recovering useful structure depends on the implementation, measurement access, and signal quality; physical proximity is a precondition for some channels, not a guarantee of success.

^fn4

<sup>5</sup> **Robustness-privacy trade-off**: Adversarial training can increase susceptibility to membership inference in the settings studied by Song et al. ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-song2019privacy|2019]]). The result means that a robustness intervention must be reevaluated against privacy invariants rather than assumed to improve every security property at once.

^fn5

<sup>6</sup> **Dual-use dilemma**: The structural tension that defensive ML capabilities (adversarial training, data poisoning tools, red-teaming frameworks) are simultaneously offensive capabilities. This creates an arms race where defensive research publications become attack playbooks. For ML systems engineering, the consequence is architectural: robustness mechanisms must assume attacker knowledge of the defense, ruling out security-through-obscurity and motivating formal guarantees where feasible and adaptive empirical evaluation within the remaining threat model.

^fn6

<sup>7</sup> **Perspective API**: Google’s toxicity model has been reported in use across many platforms, including *The New York Times* and Wikipedia. A shared classifier can create correlated exposure to an evasion technique, but success at each site also depends on its model version, preprocessing, thresholds, and additional moderation controls.

^fn7

<sup>8</sup> **Adversarial transferability**: Adversarial inputs crafted on one model can also fool another ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-szegedy2013intriguing|Szegedy et al. 2013]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-papernot2016transferability|Papernot et al. 2016]]). A surrogate can therefore support an attack without target-model parameters, but transfer success depends on the models, data, and allowed perturbations; it is not uniformly comparable to white-box access.

^fn8

<sup>9</sup> **S-box (substitution box)**: The nonlinear byte-substitution table in AES. In the first round, its input combines a plaintext byte with a key byte. Predicting its output is a 256-way classification problem; with the corresponding plaintext byte known, the attacker can map predictions back to candidate key bytes and combine evidence across traces.

^fn9

<sup>10</sup> **IoT device vulnerabilities**: Default credentials, unencrypted communications, and outdated firmware create access paths into connected devices. A compromised smart camera can supply manipulated inputs or participate in distributed attacks; if it also contributes training data or federated updates, that path can carry poisoning attempts. The consequences depend on the device’s role and permissions.

^fn10

<sup>11</sup> **Medical device security**: Connected medical devices require secure maintenance over long operating lifetimes. In a device that uses ML, compromised inputs, weights, or preprocessing can alter clinical behavior without stopping the device. Traditional device software can also fail silently, so the additional ML requirement is to evaluate learned behavior alongside firmware integrity and physical safety controls.

^fn11

<sup>12</sup> **Debug port vulnerabilities**: JTAG and Serial Wire Debug can expose memory and execution control when debug access remains enabled and authorized checks are absent or bypassed. An attacker may then recover weights accessible in plaintext, but an exposed connector alone does not defeat correctly enforced debug locks or encryption whose keys remain unavailable.

^fn12

<sup>13</sup> **ARM TrustZone**: Introduced in 2004, TrustZone partitions an ARM processor into secure and normal “worlds” with hardware-enforced isolation. Its presence on a device does not by itself protect an ML deployment: the model, keys, and data path must actually be placed inside the secure world, which depends on whether the device vendor exposes secure-world applications beyond key storage.

^fn13

<sup>14</sup> **PUF (physical unclonable function)**: Manufacturing variation can support device-specific key derivation without storing a persistent copy of the key. Separate device keys limit the reach of a storage-key compromise, but they do not prevent extraction of plaintext model weights during execution or attacks that predict a vulnerable PUF’s responses.

^fn14

<sup>15</sup> **Container vs. VM isolation**: Containers share the host kernel, which keeps overhead low and model scale-out fast but leaves a kernel attack surface shared with co-tenants. VMs separate guest kernels and memory at additional resource cost, yet hypervisor flaws and shared-hardware side channels can still enable cross-tenant attacks on a multi-tenant serving fleet.

^fn15

<sup>16</sup> **HIPAA ML requirements**: For electronic protected health information, the HIPAA Security Rule treats encryption at rest and in transit as addressable specifications, which an organization implements when reasonable and appropriate or replaces with a documented equivalent ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-hhs2005hipaasecurity|U.S. Department of Health and Human Services 2005]]). Its audit-control standard requires mechanisms that record and examine activity in systems holding that information, scoped by risk analysis rather than a mandate to log every read. Cloud services handling it generally require Business Associate Agreements. In an ML pipeline, these duties become risk-based audit coverage, protected checkpoints, controlled access, and evidence that the safeguards are operating.

^fn16

<sup>17</sup> **Model watermarking**: In trigger-set watermarking, the owner’s secret inputs reliably identify the model while normal test accuracy is preserved ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-adi2018turning|Adi et al. 2018]]). The systems challenge is robustness, because a watermark must survive fine-tuning, pruning, and distillation, the same operations an attacker uses to strip ownership marks from a stolen model.

^fn17

<sup>18</sup> **Homomorphic encryption**: Operations on ciphertexts correspond to operations on the underlying plaintexts. Gentry’s 2009 work supplied the first fully homomorphic construction; it did not make arbitrary ML workloads immediately practical. Inference cost depends on circuit depth, packing, rotations, numerical representation, and the chosen security parameters.

^fn18

<sup>19</sup> **SMPC performance overhead**: Cryptographic computation adds protocol-specific communication and local work. The bottleneck depends on round count, network latency, arithmetic representation, and the adversary model; a single slowdown factor does not characterize all deployments. Moving some layers outside protection changes the information exposed and therefore requires a new privacy analysis.

^fn19

<sup>20</sup> **Netflix deanonymization**: As few as 8 movie ratings with approximate dates uniquely identified 99 percent of records in the anonymized Netflix Prize dataset, and correlation with public IMDb ratings re-identified users ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-narayanan2008|Narayanan and Shmatikov 2008]]). For ML training data, removing direct identifiers does not establish privacy when retained records can be linked to auxiliary information.

^fn20

<sup>21</sup> **${k}$-anonymity**: A property of a released dataset ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-sweeney2002|Sweeney 2002]]). Generalization, such as coarsening dates or postal codes, and suppression of rare rows can achieve the property at the cost of information loss. It does not bound inference from homogeneous sensitive attributes or auxiliary knowledge and is not a per-request privacy guarantee.

^fn21

<sup>22</sup> **DP-SGD (differentially private stochastic gradient descent)**: Introduced by Abadi et al. ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-abadi2016deep|2016]]), DP-SGD clips each per-sample gradient and adds calibrated Gaussian noise. Per-example clipping adds memory, recomputation, and reduction work that ordinary minibatch training avoids; vectorized clipping implementations recover much of the parallelism, so the throughput cost must be measured for the chosen model and implementation.

^fn22
