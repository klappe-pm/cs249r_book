# V2-13.07 Fleet-Internal Trust Boundaries

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13 Security & Privacy|V2-13 Security & Privacy]]

^sec-security-privacy-fleet-trust-boundaries

A training job on the reference cluster of 1,024 GPUs (128 nodes with 8 GPUs each) depends on contributions from many participants. Each optimizer step of the Archetype A (GPT-4/Llama-3) reference model reduces 350 GB of FP16 gradients across the job, and each checkpoint interval produces a 2.45 TB artifact containing valuable learned state. Public inference controls do not govern these internal exchanges. Four boundaries determine how a node compromise can propagate: the gradient each worker contributes, the fabric that carries it, the accelerators and caches tenants share, and the evidence used to admit nodes into the job.

### Gradient Synchronization Integrity

^sec-security-privacy-gradient-sync-integrity

Because standard ring AllReduce averages worker contributions, a single compromised node submitting an arbitrarily large gradient vector can corrupt the global step for all 1,024 GPUs. The **breakdown point** of an aggregation rule measures this weakness as the smallest fraction of corrupted inputs that can drive the aggregate arbitrarily far from the honest value. Weighting each of the ${N_{\text{DP}}}$ contributions (one per model replica) by $1/{N_{\text{DP}}}$ does not bound the corruption when the contribution’s magnitude is unconstrained, so one input out of ${N_{\text{DP}}}$ suffices, and the mean’s breakdown point falls to zero as the job grows. **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.04 Failure Taxonomy#^sec-fault-tolerance-reliability-reliability-byzantine-failures-8a24|Byzantine failures]]** introduces aggregation rules such as Krum and coordinate-wise trimmed mean, whose guarantees require assumptions about the number of faulty workers and the honest updates ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-blanchard2017machine|Blanchard et al. 2017]]; [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-yin2018byzantine|Yin et al. 2018]]). Under those assumptions they keep a positive breakdown point, so a bounded number of corrupted workers cannot drive the step arbitrarily far. An intentional adversary can adapt its update to the deployed norm or distance checks and repeat the attempt across steps. Evaluation must therefore test attacks against the active control rather than rely only on evidence from random faults.

Robust aggregation also changes the collective’s information requirements. Ring AllReduce computes a sum with about $2({N_{\text{DP}}}-1)/{N_{\text{DP}}}$ times the gradient size ${M}$ in per-worker communication as ${N_{\text{DP}}}$ grows; its result does not provide a separate gradient for every worker. A direct implementation of a median, trimmed mean, or distance-based rule can instead gather all individual gradients. Gathering them at every worker receives $({N_{\text{DP}}}-1){M}$ bytes per worker, a factor of ${N_{\text{DP}}}/2$ relative to the ring traffic expression. Unlike the device count ${N}$ of the Fleet Law, the data-parallel degree ${N_{\text{DP}}}$ counts replicas rather than accelerators. The comparison assumes a data-parallel degree of 64 on the reference cluster, which leaves each replica two full nodes of 8 GPUs (for example, tensor parallelism inside each node). At that degree ${N_{\text{DP}}}/2$ gives 32× the ring traffic. Because the gradient synchronization is bandwidth-dominated, its share of ${T_{\text{comm}}}({N})$ grows by roughly that factor unless the extra traffic can be overlapped with backward computation. That ratio is the cost of the gather-based implementation, not a lower bound for every robust protocol.

Worker admission through attestation ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.07 Fleet-Internal Trust Boundaries#^sec-security-privacy-fleet-attestation|section 13.6.4]]) restricts which environments join the job, but does not prove their gradients are benign; update checks or redundant computation address different evidence. Federated deployments face heterogeneous attestation support and independently controlled clients. **[[01 Books/Volume II - Scaling/03 The Fleet in Production/11 Edge Intelligence/V2-11.08 Federated Learning Systems at Scale#^sec-edge-intelligence-federated-privacy-a1ed|Federated privacy]]** examines the additional conflict between inspecting individual updates and hiding them through secure aggregation.

↩︎ Ring AllReduce and its $2({N_{\text{DP}}}-1)/{N_{\text{DP}}}$ per-worker traffic bound are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/05 Collective Communication/V2-05.07 AllReduce Algorithms and Topologies#^sec-communication-collective-operations-collective-operations-ring-allreduce-ffce|Ring AllReduce]]**.

### Collective Traffic Confidentiality

^sec-security-privacy-collective-traffic

Moving 350 GB of plaintext FP16 gradients per step over remote direct memory access (RDMA) bypasses host CPUs for speed, but exposes sensitive training updates to any adversary who can tap the fabric links, switches, or management plane. Gradient inversion, examined for federated clients in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.09 Comprehensive Defense Architectures#^sec-security-privacy-gradient-inversion-risks-d2c1|section 13.8.5.2]], demonstrates that exposed gradients can reconstruct training examples under particular observation and training conditions. The exposure of a gradient shard, aggregate, or activation therefore needs its own analysis of what an observer on the fabric can recover. A dedicated facility can restrict physical access to links and switches without eliminating the fabric trust boundary.

↩︎ RDMA and GPUDirect transports, which move payloads directly between accelerator memories, are established in **[[01 Books/Volume II - Scaling/01 The Fleet/03 Network Fabrics/V2-03.05 Level 2 Transport and the Performance Model#^sec-network-fabrics-rdma|RDMA and GPUDirect]]**.

Encrypting collective traffic can add to the communication term of the Fleet Law (**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^eq-fleet-law|equation 1.3]]**). The size of that addition follows from the ring traffic just derived. For the large gradient buckets that dominate a step, the bandwidth term of the AllReduce, about $2({N_{\text{DP}}}-1){M}/({N_{\text{DP}}}{\beta})$ for link bandwidth ${\beta}$, outweighs the per-message latency. A cipher that sustains only half the link rate therefore halves the effective ${\beta}$ and roughly doubles that part of ${T_{\text{comm}}}({N})$. A cipher that keeps pace with the link adds latency but little transfer time, while a host-based path that stages accelerator data adds copies that GPUDirect RDMA avoids. Adapter or link-layer encryption can protect traffic without that staging path, subject to the endpoints and keys included in its trust boundary. The added latency and any lost overlap must be measured on the actual collective schedule, because an increase in ${T_{\text{comm}}}({N})$ recurs at every step and can raise the accelerator time the run requires.

### Shared Accelerators and Caches

^sec-security-privacy-shared-accelerators

Sharing a GPU across tenants without hardware memory partitioning or prefix-cache scoping lets one tenant infer another’s prompt prefix from response-timing hits or read residual high-bandwidth memory (HBM) state. When a serving engine shares its key-value prefix cache across tenants, a request whose opening tokens match a cached prefix skips prefill computation and returns its first token noticeably faster, letting a co-tenant probe whether a target system prompt or document was recently processed. At the processor layer, Volta-era and later implementations of Multi-Process Service, which lets several processes run kernels on one GPU at once, provide separate client GPU address spaces, but processes still share compute units, caches, and memory controllers without hardware fault isolation, so address separation alone does not establish a boundary between mutually distrustful users. Multi-Instance GPU (MIG) partitions memory, cache, and compute resources in hardware ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-nvidiaMigUserGuide|NVIDIA 2026]]), while sequential reuse introduces a separate requirement to scrub accessible residual memory before reassignment. Tenant-scoped prefix caches remove cross-tenant timing leakage at a potential hit-rate cost, leaving other timing channels and within-tenant access boundaries to be assessed.

↩︎ The accelerator sharing options and the isolation strength each provides are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/08 Fleet Orchestration/V2-08.11 Serving Capacity in the Shared Fleet#^sec-fleet-orchestration-resource-isolation|Resource isolation]]**.

Each of these controls spends capacity, through reserved partitions, fragmentation, scrubbing time, or lost cache reuse. Measuring that capacity effect requires a matched workload and resource budget; a smaller partition cannot be compared with a whole accelerator and labeled pure security overhead.

**Systems Perspective 13.2: The cost of secure multi-tenancy**

Consider a hypothetical comparison of two serving configurations with the same allocated accelerator capacity, models, request mix, and latency target. Assume the baseline sustains 1,000 tokens per second and the configuration with additional security controls sustains 850 tokens per second. These are scenario inputs for a capacity calculation, not measured overheads for MIG or another isolation mechanism.

For this matched comparison, the throughput loss is 1,000 tokens - 850 tokens = 150 tokens per second, or (150 tokens/1,000 tokens) = 15 percent. Spatial partitioning does not inherently require tenant context switches. Its capacity cost may instead arise from fragmentation or idle reserved resources, which should be recorded separately from execution overhead.

**Systems insight**: The assumed controls reduce useful throughput by 15 percent under the stated comparison. In a measured deployment that loss would split among the mechanisms of this section. Hardware partitions strand capacity whenever a tenant’s load falls below its slice, memory scrubbing between tenants takes time out of every reassignment, and tenant-scoped prefix caches give up the hits that cross-tenant reuse would have supplied. Each source has a different remedy. Right-sizing partitions recovers stranded capacity, while cache scoping is the price of closing a timing channel and cannot be tuned away without reopening it. Fleet planning must therefore record each source separately; none can be inferred from comparing a whole accelerator with a smaller partition.

### Attestation and Key Custody at Fleet Scale

^sec-security-privacy-fleet-attestation

When 128 cluster nodes restart and update independently, releasing the decryption key for a 2.45 TB checkpoint to a node whose boot firmware was silently modified exposes the entire model. Remote attestation lets a verifier appraise authenticated hardware claims about each node against an admission policy before delivering keys or data. The central claim is a set of measurements, cryptographic hashes of the firmware and software the node loaded, recorded and signed by the node’s hardware so that compromised software cannot rewrite them. Before releasing the key for the 2.45 TB checkpoint, the service can require fresh evidence covering the relevant firmware and workload measurements. Coverage depends on the platform; a valid measurement does not prove that approved code is free of vulnerabilities or that every runtime update is correct. The provenance bound on trust (principle [[01 Books/Volume II - Scaling/04 The Responsible Fleet/V2 Responsible Fleet Principles#^pri-provenance-bounds-trust|22]]) links this evidence to the release path. Confidential computing adds runtime protection for code and data placed inside a hardware-enforced boundary, under the platform’s stated adversary model. [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.09 Comprehensive Defense Architectures#^sec-security-privacy-hardware-security-foundations-f5e8|Section 13.8.1]] develops those mechanisms and their limits.

The recovery sequence in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.07 Fleet-Internal Trust Boundaries#^fig-attestation-key-release|figure 15]] places key delivery between fresh appraisal and checkpoint restoration.

![[90 Assets/Volume II/13 Security Privacy/Attestation Key Release 0bfbd687f2.svg]]

Figure 15: **Attestation Before Recovery Admission**: A restarted node answers a fresh verifier challenge with authenticated measurements. Under the illustrated admission policy, the verifier authorizes the key service only after appraisal succeeds. Protected key delivery permits checkpoint restoration; the node rejoins the collective afterward. Stale or rejected evidence stops this sequence before authorization. The diagram shows ordering rather than elapsed time and assumes the platform protects key delivery and custody.

^fig-attestation-key-release

Attestation and key management add coordination work when admission or recovery requires renewed evidence and key delivery. The policy must specify when evidence expires and which changes require another check. Key rotation also needs a transition plan, while revocation after a suspected compromise may require interrupting work that no longer has valid authority. Hardware security modules can protect the keys used to authorize or wrap secrets (wrapping encrypts one key under another), with node-level custody governed separately. When these operations delay participants or restart, their cost enters ${T_{\text{sync}}}({N})$ and the recovery path. A node that restarts after a failure must present fresh evidence and receive the checkpoint key again before it rejoins, so every failure costs that re-admission delay on top of the restart time and lost work that the checkpoint-interval calculation already charges.

↩︎ The Young-Daly checkpoint interval, which balances checkpoint write cost against expected lost work, is established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.09 Checkpointing and Progress Preservation#^sec-fault-tolerance-young-daly|The Young-Daly checkpoint interval]]**.

The four boundaries draw on all three C³ axes. Redundant computation and memory scrubbing add compute work, while tenant-scoped caches can reduce reuse. Robust aggregation and encrypted collectives can add communication cost; attestation and key rotation add coordination. These controls also depend on components beneath the job. A driver with access to plaintext state, a compromised memory path, or an observable power signal can undermine a protection enforced higher in the stack. The hardware threat model must identify which of those components remain trusted and which observations the attacker can obtain.

**Self-Check: Question**

1.  A 64-worker data-parallel job replaces ring AllReduce with a gather-based coordinate-wise median implementation: every worker gathers every individual gradient before computing the median. Approximately how does per-worker gradient traffic change under this schedule?

    1.  It rises by about 32 times, because this implementation gathers the 63 peer gradients instead of moving about twice the gradient size in the ring.
    2.  It is unchanged, because this median implementation uses only the sum returned by ring AllReduce.
    3.  It roughly doubles, because gathering all individual gradients costs one extra ring pass.
    4.  It falls, because the implementation discards outlier gradients before receiving them.

2.  Two hypothetical serving configurations use the same allocated accelerator capacity, models, request mix, and latency target. The baseline sustains 1,000 tokens/s and the configuration with additional security controls sustains 850 tokens/s. Explain what this 15% capacity loss establishes and why comparing a whole GPU against a smaller MIG partition would not isolate security overhead.

3.  True or False: RDMA movement between accelerator memories establishes gradient confidentiality even when the fabric payloads are plaintext.

4.  A multi-tenant LLM service shares one prefix cache across all tenants, and cache hits are distinguishable in time-to-first-token measurements. What can a probing tenant infer, and which control removes this cross-tenant cache-reuse path?

    1.  Evidence that a probed prefix was recently processed outside the probing tenant; per-tenant cache scoping removes this shared-reuse path at the cost of a lower hit rate.
    2.  The model weights of the serving replica; encrypting the weights at rest closes the channel.
    3.  Another tenant’s API key; mutual TLS between client and gateway closes the channel.
    4.  The exact output tokens of other tenants; rounding output probabilities closes the channel.

5.  When a 128-node training job waits for fresh remote attestation and key delivery before admission or recovery, explain why that delay enters the coordination term and recovery path of the Fleet Law. Distinguish it from steady-state protected-execution costs.
