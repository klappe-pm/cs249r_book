# V2-13.05 Systematic Threat Analysis and Risk Assessment

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13 Security & Privacy|V2-13 Security & Privacy]]

^sec-security-privacy-systematic-threat-analysis-risk-assessment-3ef1

An authenticated request can still probe a model for memorized data, and an accepted training sample can still carry a backdoor. Network security and user authentication therefore need a threat model that includes learned behavior. Training data can be manipulated to embed backdoors, input perturbations can exploit learned decision boundaries, and systematic API queries can expose enough behavior to train a substitute. Each attack uses an interface the system needs for ordinary work.

Each of these vectors requires a formal **threat model**, written down as four fields: asset, boundary, adversary, and control. The asset defines what must remain confidential, intact, or available. The boundary defines where trust changes, such as between training data and model registry, user prompt and system instruction, or tenant workload and shared accelerator. The adversary field records the actor’s capability (what it can access, observe, or modify) and its goal (what it seeks to compromise). The control identifies a permission, isolation mechanism, or observable signal that constrains the attack or supports a response. Without those fields, a risk matrix cannot explain why a particular defense deserves resources. Attack cost and expected benefit help assess feasibility, but the model must also cover actors whose objective is disruption rather than financial return.

For a federated training round, suppose the coordinator may inspect messages but follows the aggregation protocol, while a compromised enrolled client may submit an arbitrary update. The same update crosses two boundaries. Hiding individual contributions from the coordinator addresses confidentiality; checking or limiting a client contribution addresses integrity. Authenticating the client establishes who sent an update, not whether the update is benign. A defense comparison is meaningful only after stating which of these actors, capabilities, and possible collusions it covers.

### Security Threat Modeling for ML Systems

^sec-security-privacy-security-threat-modeling-ml-systems-f60d

Systematic threat modeling identifies what must be protected and from whom. It is a structured approach to security analysis that characterizes the attack surface and guides defensive investments. For machine learning systems, threat modeling must account for dependence on training data, statistical decision boundaries, and distributed deployment patterns.

#### Attack Surface Analysis

^sec-security-privacy-attack-surface-analysis-b10b

The attack surface of an ML system encompasses all points where an adversary can interact with or observe the system. It includes the lifecycle risks of ordinary software, such as compromised dependencies, as well as the data and learned state that determine model behavior. Decomposing this surface into data, model, interface, and infrastructure layers identifies where a control can constrain the attacker and what remains exposed beyond that control.

The training data pipeline lets an adversary influence behavior before the model exists. At collection endpoints, raw data enters through application logs, sensors, forms, APIs, or uploads. Training corpora then reside in object stores, warehouses, feature stores, or dataset registries. Preprocessing pipelines normalize, filter, augment, and join these inputs, while human annotation, weak-labeling rules, or model-assisted labeling supply the targets used for learning. Dataset manifests and lineage systems identify which snapshot enters a release. A compromised source can affect successive model versions if the pipeline continues to ingest its records, and a backdoor may persist when training reuses an affected checkpoint. Retraining alone therefore does not establish that the compromised contribution has been removed.

The model itself presents multiple attack surfaces spanning training infrastructure, model storage and versioning systems, model serialization and deserialization code, hyperparameter configuration management, and gradient computation and aggregation processes. Attacks at the model layer can compromise integrity by embedding trojans during training, extract intellectual property through parameter theft, or manipulate behavior through weight poisoning.

Deployed models expose additional attack surfaces through inference API endpoints and load balancers, authentication and authorization systems, input validation and preprocessing logic, output formatting and response generation, and monitoring and logging infrastructure. At this interface layer, input checks enforce the accepted request contract, query limits constrain collection, and output controls restrict the information returned. An adversarial input can satisfy the request contract, and a permitted response can still reveal useful model behavior, so these controls need evaluation against the specified attack.

The underlying computational infrastructure presents traditional attack surfaces amplified by ML-specific concerns, including accelerator firmware and drivers, container orchestration and scheduling systems, network communication between distributed training nodes, key management and secrets infrastructure, and supply chain for ML frameworks and dependencies. Infrastructure compromises can affect all systems running on shared resources, making this layer critical for multi-tenant ML platforms.

#### Threat Vector Classification

^sec-security-privacy-threat-vector-classification-3042

Threat-vector classification matters because the same model failure demands different defenses when the attacker has only API access, partial design knowledge, or full insider access. The three axes are access type, auxiliary knowledge, and attack timing.

Access type specifies how the adversary can inspect or interact with the model. Under black-box access, the available interface returns outputs for submitted inputs. It can support model extraction ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-tramer2016stealing|Tramèr et al. 2016]]) and query- or transfer-based adversarial attacks ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-papernot2016transferability|Papernot et al. 2016]]) without exposing the target’s parameters. Gray-box access adds partial internal information, such as the architecture or training procedure. White-box access supplies the model’s parameters and architecture, enabling direct gradient-based attacks (which follow the model’s gradient with respect to its input to find a small change that alters the output) ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-goodfellow2015explaining|Goodfellow et al. 2015]]) and parameter copying when the files are accessible. These labels describe model visibility; they do not grant permission to alter training data, replace weights, or modify the runtime. Those write capabilities must be stated separately. Each access level, which the literature also calls a knowledge level, has a typical attack it enables and a typical deployment where it arises ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.05 Systematic Threat Analysis and Risk Assessment#^tbl-adversary-knowledge-spectrum|table 2]]).

| **Adversary knowledge level** | **Model access**                             | **Training data access** | **Attack example**                                        | **Common scenario**                         |
|:------------------------------|:---------------------------------------------|:------------------------:|:----------------------------------------------------------|:--------------------------------------------|
| **White-box**                 | Full access to architecture and parameters   |   Specified separately   | Crafting adversarial examples using gradients             | Insider threats, open-source model reuse    |
| **Gray-box**                  | Partial access (e.g., architecture only)     |   Specified separately   | Attacks based on surrogate model approximation            | Known model family, unknown fine-tuning     |
| **Black-box**                 | No internal access; only query-response view |   Specified separately   | Query-based surrogate model training and transfer attacks | Public APIs, model-as-a-service deployments |

Table 2: **Adversarial Knowledge Spectrum**: Model access defines the white-box, gray-box, and black-box distinction used here; training-data access is specified independently. An open-weight model can expose its parameters while keeping its training records private. The table categorizes these models by access level, typical attack methods, and common deployment scenarios, clarifying the practical challenges of securing machine learning systems.

^tbl-adversary-knowledge-spectrum

Auxiliary knowledge adds the background information available beyond the exposed interface. A black-box client may know the application domain, public architecture documentation, or examples resembling the training distribution. An insider may know the deployment configuration without being able to read every training record. Model visibility and auxiliary knowledge therefore overlap, but neither replaces an explicit inventory of what the adversary knows. Claims of full knowledge must identify whether they include training records, preprocessing, and defense settings as well as model parameters.

Attack timing determines where the defense can still intervene across the system lifecycle. Training-time attacks, such as data poisoning or backdoor injection, manipulate the learning process before the model artifact is produced. Deployment-time attacks compromise model distribution, serialization, or container installation before serving begins. Once in production, inference-time attacks exploit the deployed model through adversarial inputs or extraction queries. Finally, postdeployment attacks target online model updates, monitoring telemetry, or operational feedback loops after the model is already in service. The defense surface therefore moves in lockstep with the model lifecycle, from data controls to artifact integrity to serving-time containment.

Combining these dimensions defines a testable threat scenario. A public API adversary might query a deployed classifier, know its task and output format, and lack access to its parameters or training records. A training insider might inspect the model and alter a specified subset of examples before fitting begins. The second scenario permits poisoning because it grants a write capability, not merely because the attacker knows more about the model.

#### Defense Strategy Framework

^sec-security-privacy-defense-strategy-framework-7654

Effective defense against the threat vectors identified by the threat model requires a layered strategy that addresses each attack surface while accounting for adversary capabilities. The defense framework operates on three principles: defense in depth, minimal attack surface, and fail-safe defaults.

No single defensive mechanism provides complete protection. The principle of **defense in depth** requires multiple independent layers such that compromising one layer does not grant full system access. For ML systems, this means combining data validation with model robustness techniques, access controls with output perturbation, and software defenses with hardware security mechanisms.

The principle of **minimal attack surface** treats every exposed interface, stored artifact, and network endpoint as a potential entry or observation point. An API should expose only the functionality and output precision its users need, because detailed scores provide additional observations of model behavior. Encryption at rest protects stored models and training corpora when the attacker cannot also obtain their keys. Separating training clusters from inference endpoints constrains lateral movement, while protected access logs support investigation of sensitive operations. Each control reduces a particular exposure; none removes the need to examine the paths that remain.

The principle of **fail-safe defaults** makes access depend on established permission rather than the absence of a detected threat. A request that cannot be authorized must not acquire privileges because a service failed. Behavioral anomalies require a separate response policy because they can also arise from legitimate traffic or distribution shift. Depending on the application, the system may reject a request, defer to a verified fallback, suspend a release, or isolate an affected component while preserving essential service. The safe response follows from the consequences of both continued operation and interruption; it cannot be inferred from an anomaly score alone.

Each layer of the attack surface calls for its own defensive mechanisms and detection methods ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.05 Systematic Threat Analysis and Risk Assessment#^tbl-defense-mapping|table 3]]). Data defenses validate provenance, model defenses protect learned behavior and weights, API defenses govern query exposure, and infrastructure defenses anchor runtime trust.

| **Attack surface**       | **Primary threats**                                             | **Defensive mechanisms**                                                                      | **Detection methods**                                      |
|:-------------------------|:----------------------------------------------------------------|:----------------------------------------------------------------------------------------------|:-----------------------------------------------------------|
| **Data Layer**           | Poisoning, label manipulation, supply chain compromise          | Input validation, provenance tracking, secure data pipelines                                  | Statistical anomaly detection, data quality monitoring     |
| **Model Layer**          | Backdoor injection, parameter theft, trojan insertion           | Secure training environments, encrypted model storage, access controls                        | Model behavior analysis, weight distribution monitoring    |
| **API/Interface Layer**  | Adversarial examples, model extraction, membership inference    | Input sanitization, rate limiting, output perturbation, differential privacy                  | Query pattern analysis, confidence distribution monitoring |
| **Infrastructure Layer** | Side-channel attacks, firmware compromise, supply chain attacks | Trusted execution environments (TEEs), secure boot, network segmentation, dependency scanning | Hardware performance monitoring, integrity verification    |

Table 3: **Defense Mapping by Attack Surface**: Each layer of the ML system attack surface requires specific defensive mechanisms and detection methods. Effective security integrates protections across all layers while maintaining detection capabilities that can identify attacks that bypass preventive controls.

^tbl-defense-mapping

Attack surfaces, threat vectors, and the defense mapping together enumerate what could go wrong and which control addresses each failure. They do not say which failure to address first, and no deployment can fund every control at once.

### Threat Prioritization Framework

^sec-security-privacy-threat-prioritization-framework-f2d5

A team that spends months hardening against physical laser fault injection while leaving a public inference API without query budgets or loading untrusted pickle checkpoints (a Python file format that can run arbitrary code when loaded) from a public hub leaves its highest-probability attack paths wide open. Prioritization ranks the enumerated threats by how likely each is in the deployment and how much damage it would cause. Impact is not purely technical. Regulatory obligations raise the cost of some failures, as when an erasure request under the European Union’s General Data Protection Regulation (GDPR)[[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.16 Footnotes#^fn2|²]] obliges the operator to trace personal data through derived datasets, logs, and deployed artifacts. A prioritization matrix based on likelihood and impact turns the threat model into an allocation decision. Teams automate defenses for threats that are both likely and damaging, prepare for rare but severe failures, and avoid spending scarce engineering time on low-value controls.

Penalties make the regulatory part of impact concrete. In healthcare, where ML systems routinely handle patient data, a breach can violate the Health Insurance Portability and Accountability Act (HIPAA), with significant legal and ethical consequences. Similar regulatory risks apply globally. For personal data within its territorial and material scope, GDPR authorizes fines up to 2 percent of total worldwide annual turnover when an organization fails to implement appropriate security measures, and up to 4 percent for violations of its core processing principles or data-subject rights ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.15 Source References#^ref-gdpr2016|European Parliament and Council of the European Union 2016]]).

The following placements illustrate a threat model rather than universal attack frequencies. Poisoning can fall in the high-likelihood/high-impact quadrant in a federated deployment that admits untrusted contributors and suffers severe consequences from manipulated predictions. Such a deployment needs controls on update integrity and a response path for suspected compromise. High-likelihood/low-impact extraction describes a different scenario in which public queries are accessible but behavioral copying creates limited competitive loss. Output restrictions and query budgets may then be proportionate controls, although their effectiveness still requires evaluation.

The lower-likelihood quadrants receive different treatment. Low-likelihood/high-impact hardware side-channel attacks describe a deployment in which obtaining the necessary observations is difficult but a successful attack could reveal valuable secrets. The required access depends on the channel; some attacks use a physical probe, while others exploit shared resources or remotely observable timing. In the public API scenario used for this matrix, membership inference attacks, which test whether a particular record was part of the training set ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.06 Model-Specific Attack Vectors#^sec-security-privacy-membership-inference|section 13.5.2.1]]), may sit in a lower-likelihood/lower-impact quadrant than direct integrity failures. That placement must be reassessed when the training data is sensitive or the exposed outputs make membership easier to infer. The matrix records those deployment assumptions rather than assigning a permanent rank to each attack family.

The framework guides resource allocation, as [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13.05 Systematic Threat Analysis and Risk Assessment#^fig-threat-matrix|figure 3]] summarizes. The example prioritizes accessible model and data threats before more specialized hardware attacks. A deployment with sensitive co-tenants or exposed edge hardware may require a different order. The allocation decision depends on the expected harm, the control’s effectiveness, and its engineering cost, not on the attack category alone.

**Checkpoint 13.1: Knowledge check: Threat modeling**

A team detects a high volume of API queries from a single IP address that are systematically exploring the decision boundary of a fraud detection model.

**Lifecycle stage**: identify whether the suspicious activity occurs during training, serving, or infrastructure operation.

**Attack surface**: identify the interface the attacker is exercising and infer what the query pattern reveals.

**Defense mapping**: select the rate-limiting, monitoring, or output-control mechanisms that should activate first.

An unusual query pattern is evidence to investigate, not proof of extraction. The threat model connects that observation to an actor’s capabilities and the asset at risk. Specific attack mechanisms then explain how access to data, artifacts, or predictions can compromise the model.

    3.  Model extraction is Low-Likelihood / High-Impact requiring full homomorphic encryption; data poisoning is High-Likelihood / Low-Impact requiring only API key rotation.
