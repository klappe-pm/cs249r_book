# V2-13.13 Summary

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/04 The Responsible Fleet/13 Security & Privacy/V2-13 Security & Privacy|V2-13 Security & Privacy]]

^sec-security-privacy-summary-831c

Privacy and security protect the machine learning fleet’s models, data, hardware, and service boundaries from extraction, poisoning, manipulation, and unauthorized access. The breach cases establish the boundaries a fleet must defend: Strava shows that an aggregate release can disclose behavior without leaking a single record, Stuxnet exposes supply-chain trust, the Jeep Cherokee hack exposes insufficient isolation, and Mirai exposes weak endpoint identity. Learned behavior adds further boundaries because poisoned data, extraction queries, and prompt injection can compromise a system through otherwise legitimate interfaces. The fleet adds boundaries of its own that no API gateway sees: the gradient each worker contributes, the fabric that carries it, the accelerators tenants share, and the evidence that each node runs approved code. Hardware trust anchors protect execution, provenance connects artifacts to release decisions, runtime controls contain abuse, and differential privacy bounds participation leakage. These mechanisms compose only when each is tied to the actor and exposure it addresses.

Their costs span all three C$^3$ axes and can enter different terms of the Fleet Law (**[[01 Books/Volume II - Scaling/00 Introduction/01 Introduction/V2-01.06 The C³ Taxonomy and Foundations of Scale#^eq-fleet-law|equation 1.3]]**). Output shaping, input validation, redundant gradient checks, DP-SGD clipping and noise, and protected execution can add work to ${T_{\text{compute}}}$. Fabric encryption, gathering individual updates for some robust aggregation methods, and masked federated uploads can increase ${T_{\text{comm}}}({N})$; offload and overlap determine how much reaches the critical path. Admission checks, key rotation, privacy-budget checks, and aggregation thresholds can add to ${T_{\text{sync}}}({N})$ when the workflow waits for them. Federated protocols also need deadlines and dropout handling rather than an assumption that every client responds. Capacity planning must measure these costs in the deployed path so that operating targets do not depend on bypassing a control under load.

**Key Takeaways: Defend the model, not just the server**

- **The model is the attack surface**: ML systems inherit ordinary server threats but add attacks against the learned boundary itself. Poisoned data, model extraction, adversarial inputs, and prompt injection can compromise behavior without exploiting a traditional software vulnerability.
- **Extraction is bounded by cumulative budgets**: A daily rate limit slows a query-based extractor without capping what it collects. A lifetime per-principal budget priced at break-even with retraining, paired with an output contract that limits what each response reveals, removes the cost advantage of copying, but only as far as principals map to real actors.
- **Privacy is an accounted budget**: Because models can encode information about sensitive data, a correctly executing model can disclose training data through memorization and membership inference, so privacy cannot be treated as anonymization at the perimeter. Differential privacy (principle [[01 Books/Volume II - Scaling/04 The Responsible Fleet/V2 Responsible Fleet Principles#^pri-information-leakage|23]]) offers bounded $({\epsilon}, {\delta})$ claims only when all data-dependent DP mechanisms are composed correctly; querying a fixed DP-trained model is post-processing and does not add training privacy loss.
- **Generative systems need enforceable control boundaries**: Prompt injection, jailbreaks, and PII leakage pass through normal text channels. Treat model output as untrusted, keep instructions separate from untrusted content, and keep authorization in an external policy layer.
- **The fleet’s own interfaces are trust boundaries**: An unbounded malicious update can dominate a mean; the examined gather-based implementation of robust aggregation adds about ${N_{\text{DP}}}/2$ times the traffic, an implementation cost rather than a universal lower bound. Worker admission, collective traffic, and shared accelerators need separate controls, and admission does not replace update checks, because an admitted worker can still submit a malicious update.
- **Provenance bounds trust and enables recovery**: A model can be trusted only as far as its record of data, code, weights, and hardware reaches (principle [[01 Books/Volume II - Scaling/04 The Responsible Fleet/V2 Responsible Fleet Principles#^pri-provenance-bounds-trust|22]]). Signed datasets, locked dependencies, registry permissions, and deployment attestations let operators answer which data, code, principal, node, and checkpoint produced a suspect model. Without that chain, rollback and forensics become guesswork at fleet speed.
- **Hardware trust has explicit boundaries**: TEEs isolate execution, secure boot verifies an authorized boot chain, and HSMs protect keys and cryptographic operations. These mechanisms address different trust boundaries; they do not establish that model behavior is correct or that an authorized output preserves privacy.

^callout-takeaways--13-12-a5b9c631

A fleet can execute every authorized operation correctly and still disclose sensitive information through an approved release. The information leakage invariant (principle [[01 Books/Volume II - Scaling/04 The Responsible Fleet/V2 Responsible Fleet Principles#^pri-information-leakage|23]]) therefore makes the release boundary as important as the execution boundary. A deployment decision must establish both who can access the computation and what its outputs allow an observer to learn.

**What’s Next: From security to resilience**

Security and privacy controls address adversarial intent and control, establishing who can infer, manipulate, disable, or authorize what across data, model, interface, and infrastructure boundaries. Those controls decide who may reach the model and what its releases may disclose. They cannot show that its answers stay valid once inputs, data distributions, or hardware depart from the conditions under which it was validated. A fleet can pass every access check and every health signal while its predictions degrade without raising an error, whether from road conditions its training data never covered, from a crafted input that satisfies the interface contract, or from a faulty accelerator that keeps returning plausible numbers. Detecting and bounding that silent failure requires behavioral evidence about accuracy, calibration, and fallback under environmental shift, input-level attack, and system faults, which is the robustness problem the next chapter takes up.
