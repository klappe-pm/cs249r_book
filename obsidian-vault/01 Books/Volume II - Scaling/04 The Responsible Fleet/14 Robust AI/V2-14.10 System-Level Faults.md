# V2-14.10 System-Level Faults

[[Home|Home]] · [[01 Books/Volume II - Scaling/Volume 2 Overview|Volume Overview]] · [[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14 Robust AI|V2-14 Robust AI]]

^sec-robust-ai-diagnosing-the-masquerade-9f21

A preprocessing bug that silently rescales an input feature or an accelerator bit flip that corrupts a stored weight can make a healthy replica emit wrong predictions while triggering the exact same alarms as distribution drift or an adversarial attack. Every defense in the two preceding pillars reads evidence produced by the system it protects: drift monitors read preprocessed features, adversarial detectors read model scores, and poisoning filters read learned representations. The third pillar asks what happens when that machinery is itself wrong. Execution-level detection and recovery belong to fault tolerance. Robustness adds two obligations on top of them: behavioral checks that run on the model’s own values and outputs, and a diagnosis that decides whether a behavioral alarm came from a fault at all.

### Behavioral Checks for Silent Faults

^sec-robust-ai-behavioral-fault-checks

The exponent bit flip introduced in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.04 A Unified Framework for Robust AI#^sec-robust-ai-unified-framework-robust-ai-b25d|section 14.3]] shows how a single physical upset cascades through neural inference ([[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.10 System-Level Faults#^fig-weight-corruption|figure 14]]). In panel (b), flipping bit 30 of an FP32 weight scales its magnitude by $2^{128}$, transforming a modest weight ${w}$ of 0.042 into an extreme outlier ${w'}$ of about $1.4 \times 10^{37}$. Panel (a) traces the affected path through hidden unit ${h}_2$ to output logits (${y}_1, {y}_2$). The corrupted weight is finite and can evade NaN or infinity checks; whether it dominates those outputs depends on the input, activation function, and downstream weights. Targeted bit-flip attacks deliberately select vulnerable weight bits, so their results should not be interpreted as the effect of one random hardware upset. Memory subsystem failures during training can likewise corrupt gradient updates and prevent model convergence. Scale turns one corrupted value into a persistent exposure. Every forward pass of a dense GPT-3-class model reads all 175B of its parameters, so a corrupted weight resident in memory participates in every request that replica serves until something detects it.

![[90 Assets/Volume II/14 Robust AI/Weight Corruption fbc9065404.svg]]

Figure 14: **Weight Corruption via Bit Flip**: (a) One corrupted weight ${w'}$ drives hidden unit ${h}_2$, whose output feeds every downstream logit. (b) For an illustrative trained weight ${w} = 0.042 \approx 1.34 \times 2^{-5}$, flipping bit 30, the most significant exponent bit of the FP32 word, raises the stored exponent from $2^{-5}$ to $2^{123}$. In general, flipping an exponent bit with place value $2^{{k}}$ scales the value by $2^{\pm 2^{{k}}}$; here the factor is $2^{128}$, giving ${w'} \approx 1.4 \times 10^{37}$. The result is still finite, so NaN and infinity checks never fire, yet it can produce extreme downstream activations, depending on the input, activation function, and downstream weights. A range check $|{w}| \le {W_{\text{max}}}$ against the trained weight distribution catches it cheaply.

^fig-weight-corruption

The cheapest behavioral checks test invariants that a correctly executing model satisfies. A range check $|{w}| \le {W_{\text{max}}}$ against the trained weight distribution catches the exponent flip above at the cost of one comparison per stored value, and the same idea bounds each layer’s activations at serving time against the range observed on validation traffic. Where range checks catch extreme values, golden-input canaries replay a fixed set of requests through each replica on a schedule and compare the outputs with stored references, catching a corrupted replica whose liveness and readiness probes still pass. For corruption that stays inside normal ranges and appears only on live inputs, cross-replica comparison runs the same request on two replicas. Because that doubles the work for every request it covers, fleets apply it to sampled traffic, following the check-and-verify pattern used against silent data corruption elsewhere in the fleet. Each check spends along a different C$^3$ axis: invariant checks add compute on the serving path, canaries and cross-replica comparison add compute and communication, and deciding which replicas and checkpoints remain trustworthy after a check fails is coordination.

↩︎ Check-and-verify defenses against silent data corruption, and their cost relative to full redundancy, are established in **[[01 Books/Volume II - Scaling/02 Distributed ML/07 Fault Tolerance/V2-07.06 Check-And-Verify Defenses Against Silent Data Corruption#^sec-ft-sdc-verification|Check-and-Verify Defenses Against Silent Data Corruption]]**.

### Distinguishing Faults from Shift and Attack

^sec-robust-ai-fault-shift-diagnosis

These checks cover faults that leave a numerical signature. The harder case is a fault whose symptom looks like one of the other pillars. Consider an operator who sees the same surface symptom from all three pillars, falling model accuracy while latency and uptime hold steady. A preprocessing bug that silently rescales a feature can look like covariate shift to a drift monitor, because the feature statistics have genuinely moved. A numerical overflow that corrupts a layer’s activations can produce confident misclassifications that look like an adversarial example, because the decision flipped without a visible input cause. The difficulty lies in the disguise, because the cheap pillar-specific detectors fire on the symptom rather than the cause. Three complementary signals guide this investigation: the timing boundary of the change, reproducibility under fixed inputs, and cross-layer correlation with infrastructure telemetry.

The boundary and timing of a change often provide the first diagnostic clue. While environmental shift can evolve gradually or appear abruptly with real-world events, a shift synchronized with a deployment, dependency bump, or schema migration raises the pipeline-fault hypothesis. This suspicion strengthens when multiple features shift simultaneously in directions that the underlying physical process cannot explain. Timing alone narrows the search space without proving causation.

Reproducibility under fixed inputs helps locate the failure boundary. Replaying golden inputs through version-pinned preprocessing pipelines and model artifacts can expose the stage where outputs begin to differ. A deterministic software defect fails at the same stage on every replay. A transient upset in the computation usually vanishes on replay, whereas a corrupted value resident in memory, such as a flipped weight, reproduces on the same replica and disappears only on a second device or after the weights are reloaded. Race conditions and marginal hardware fail intermittently, so isolating them takes repeated runs or a second device. Stochastic execution also requires controlling random state or comparing repeated runs. Because shifted or adversarial inputs can reproduce the same error under fixed execution conditions, replay alone cannot settle the diagnosis; operators must compare raw and preprocessed tensors, artifact versions, and population-level statistics alongside the replay output.

Finally, cross-layer correlation links model behavior to surrounding infrastructure telemetry. Query-rate spikes or unusual input patterns can support an attack hypothesis, while deployment releases, ECC memory counters, SDC checkers, or memory-pressure alarms can support a system-fault hypothesis. Neither pattern is necessary or sufficient. An attack can remain within normal traffic patterns, and silent corruption can escape the available counters. Correlation guides the next diagnostic test rather than establishing the cause.

**Example 14.2: A drift alert that was a pipeline fault**

**Scenario**: A credit-risk service raises drift alerts on three income-related features on the morning after a routine dependency update, and the approval rate for applicants in the affected income bands shifts sharply. Latency, error rates, and uptime are unchanged, and every request that the on-call engineer retries returns a score without error.

**Diagnosis**: The three signals point the same way. The alerts begin at the release boundary, and the three features moved together in a direction that no change in applicant behavior explains. Replaying a stored set of golden requests through the previous and current pipeline versions produces identical raw inputs but preprocessed tensors that differ by a constant factor on exactly those features, because the updated library changed a default normalization. Deployment telemetry correlates with the change; query-rate and hardware counters do not. The failure is a software fault disguised as covariate shift. Retraining on the corrupted features would have taught the model the bug, and the successful retries proved only that the service answered, not that its answers passed acceptance.

**Systems lesson**: A replay harness that pins artifact versions and compares tensors at each pipeline stage turns an ambiguous drift alert into an attributable fault. Recovery is complete only when the replayed outputs satisfy the model’s acceptance tests again, which is a behavioral check that a successful retry or a green health dashboard cannot supply.

^exmp-robust-ai-masquerade-replay

The paired replay in [[01 Books/Volume II - Scaling/04 The Responsible Fleet/14 Robust AI/V2-14.10 System-Level Faults#^fig-paired-pipeline-replay|figure 15]] isolates the first changed stage in this example by holding the raw requests and model artifact fixed.

![[90 Assets/Volume II/14 Robust AI/Paired Pipeline Replay 262e0f96ec.svg]]

Figure 15: **Locating a Pipeline Fault by Replay**: Previous and current pipelines receive identical stored request bytes and use the same model artifact. Their preprocessing libraries differ, and the first differing tensor appears immediately after preprocessing. The changed decision is downstream evidence, while the earlier tensor difference identifies the boundary to investigate. This controlled example supports a pipeline-fault diagnosis; replay alone does not distinguish every fault, attack, or population shift.

^fig-paired-pipeline-replay

Comparing only the final scores would expose a behavioral change without locating it. Comparing intermediate tensors directs the acceptance test and rollback toward preprocessing before a retraining decision.

The diagnostic discipline is therefore to read the system-level evidence before accepting the drift or attack hypothesis the surface symptom suggests, because each pillar suggests a different intervention and more than one cause can be active at once. Skipping that diagnosis, or mistaking a passed clean-data or single-norm test for comprehensive protection, produces the recurring engineering pitfalls examined next.

**Self-Check: Question**

1.  A serving replica’s liveness and readiness probes pass and its latency is normal, but one of its weights has suffered an exponent bit flip that left the value finite and very large. Which check is designed to catch this replica?

    1.  A range check of stored weights or layer activations against the distribution observed on trusted data, or a scheduled golden-input canary compared with stored reference outputs.
    2.  A NaN and infinity check on the replica’s outputs, because a corrupted weight always produces a non-finite value.
    3.  A population stability index alarm on the replica’s input features.
    4.  A retry of failed requests, because a successful retry shows that the replica’s answers are valid.

2.  A preprocessing library update introduces a feature scaling bug that shifts input distributions, causing a drift detector to alarm and trigger an automated model retraining pipeline. Explain why this response fails, and describe how cross-layer correlation separates software faults from true environmental shifts.

3.  True or False: If replaying a fixed set of golden inputs through the current pipeline reproduces the same wrong outputs every time, the failure must be a software or hardware fault rather than distribution shift or an adversarial input.
