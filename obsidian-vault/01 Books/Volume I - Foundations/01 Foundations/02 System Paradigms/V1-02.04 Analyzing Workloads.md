# V1-02.04 Analyzing Workloads

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02 System Paradigms|V1-02 System Paradigms]]

^sec-ml-systems-analyzing-workloads-cbb8

Which of the three physical walls a system hits first is not a fixed property of a model family. A vision network that saturates accelerator compute units during batched training can stall on memory bandwidth when serving one image at a time, and a model that runs effortlessly in a data center can overheat a phone in under a minute. Turning those physical limits into a quantitative diagnosis for any pairing of workload and target hardware requires the iron law of ML systems from **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**, restated here in the same notation because every tier in this chapter is analyzed through it. For a serialized execution path, [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-iron-law|equation 4]] adds three costs:

$$
{T}= \frac{{D_{\text{vol}}}}{{\text{BW}}} + \frac{{O}}{{R_{\text{peak}}} \cdot {\eta_{\text{hw}}}} + {L_{\text{lat}}} \tag{4}
$$

^eq-iron-law

[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-iron-law|Equation 4]] decomposes total latency into three terms: data movement $({D_{\text{vol}}}/{\text{BW}})$, compute $({O}/({R_{\text{peak}}} \cdot {\eta_{\text{hw}}}))$, where ${\eta_{\text{hw}}}$ is the fraction of the peak rate the hardware actually achieves, and fixed overhead $({L_{\text{lat}}})$. A workload is **compute bound** when its compute term ${O}/({R_{\text{peak}}} \cdot {\eta_{\text{hw}}})$ exceeds its data term ${D_{\text{vol}}}/{\text{BW}}$, and bandwidth-bound in the reverse case, an outcome that depends on the workload, its execution conditions, and the deployment hardware. For an inference path that executes these stages sequentially, their times add. When one request overlaps its own work, for example by loading the next layer’s weights while computing the current layer, its time follows the actual dependencies rather than the plain sum. In production systems, however, tasks are processed continuously as a stream, and the analysis shifts from single-task latency to identifying which stage limits steady-state throughput.

### The Bottleneck Principle

^sec-ml-systems-bottleneck-principle-3514

Adding a twice-as-fast accelerator to a pipelined server, where loading and computing overlap, does nothing for steady-state throughput if the processor spends half of every step waiting for the memory bus to deliver the next batch of weights. Where the iron law quantifies the cost of each stage, the **bottleneck principle** identifies which stage governs continuous throughput. **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]** gave the overlapped form of the iron law for **pipelined execution**, in which the memory system prefetches batch ${k}+1$ while the accelerator computes on batch ${k}$. The slowest stage then hides the others and sets the interval between completions, so speeding a nonlimiting stage does not raise ideal steady-state throughput while the system bottleneck remains unchanged, just as widening a highway cannot help traffic constrained by a narrow bridge.

Deployment adds one more overlapped stage, ${T_{\text{IO}}}$, the time to transfer data over a storage or network link, including offloading a request to a remote server. [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-bottleneck|Equation 5]] extends the pipelined form with that stage. Its left-hand side is the steady-state time per completed task. The fixed overhead sits outside the maximum because it does not overlap with the other stages, and the bound becomes an equality only when the other stages overlap perfectly:

$$
{T_{\text{pipelined}}}\ge \max\left(\frac{{D_{\text{vol}}}}{{\text{BW}}}, \frac{{O}}{{R_{\text{peak}}} \cdot {\eta_{\text{hw}}}}, {T_{\text{IO}}}\right) + {L_{\text{lat}}} \tag{5}
$$

^eq-bottleneck

When a system is bandwidth-bound $({D_{\text{vol}}}/{\text{BW}} > {O}/({R_{\text{peak}}} \cdot {\eta_{\text{hw}}}))$, faster processors $({R_{\text{peak}}})$ do not raise ideal pipeline throughput while memory remains the slowest stage. Shortening that compute stage still reduces an individual request’s start-to-finish latency. One request pays for loading its inputs and then for its arithmetic, whereas the overlapped stream pays per task only for the slower of the two. Engineers must therefore identify both the metric that matters and the dominant term before optimizing. The *additive form* in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-iron-law|equation 4]] governs a single task’s serialized path, whereas the *max form* in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-bottleneck|equation 5]] governs the completion interval of an ideally overlapped continuous stream, and the actual data dependencies determine which stages can overlap.

### Workload Archetypes

^sec-ml-systems-workload-archetypes-fd10

The bottleneck principle reduces optimization to identifying the dominant constraint for a given workload. The answer depends on all three D·A·M axes at once: the data a request carries, the algorithm’s arithmetic and memory demands, and the machine that executes it. Different deployment environments create different bottlenecks along these axes, so the same model family can require different engineering when it moves from a cloud server with terabytes of memory to a microcontroller with kilobytes.

Classifying workloads by what limits them first yields four **workload archetypes**.[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn6|⁶]] Each archetype is a recurring physical bottleneck that determines which engineering moves can help. Two of them correspond to terms of the iron law. The other two are limited by preconditions the time equation assumes are already met, namely that the working set fits in memory and that the energy budget can pay for the run. A capacity or energy limit can therefore decide feasibility before any term of [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-iron-law|equation 4]] is evaluated.

The first split, between the two iron-law terms, separates arithmetic-bound systems from data-movement-bound systems. A **compute-bound** workload performs many calculations per byte loaded, so progress comes from higher arithmetic throughput, better utilization, and more parallel execution; large neural-network training is the canonical case. A **bandwidth-bound** workload, by contrast, waits on dense weight or activation movement, so wider memory buses and better data reuse matter more than additional peak FLOP/s; autoregressive text generation illustrates this regime. The roofline literature calls this regime *memory-bound*; this book says bandwidth-bound to keep it distinct from running out of memory capacity, which is the next archetype.

The second split covers workloads where the limiting constraint is not a term of the time equation at all. **Capacity-bound** workloads need more memory than the device holds. In recommendation systems with large embedding tables, irregular table lookups and poor cache locality add to that pressure, so memory capacity, access latency, and communication shape performance. **Power-bound** workloads are limited by an energy budget instead. Energy per inference, not raw speed, determines whether always-on sensing can run at all, because every inference is paid for out of a small battery or harvested supply. A capacity-bound workload fails because its data do not fit; a power-bound workload fits but cannot afford to run as often as the application needs.

**Lighthouse 2.1: Five reference workloads**

The introduction (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-lighthouse-models-9b1c|Lighthouse models put the iron law into practice]]**) introduced five lighthouse models by the system bottleneck each isolates (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^tbl-lighthouse-examples|Lighthouse Models as Reference Workloads]]**); [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^tbl-ml-systems-lighthouse-archetypes|table 2]] pairs each with a representative workload archetype and deployment paradigm. The classifications describe operating regimes: batched image processing can emphasize arithmetic, single-request text generation can emphasize weight transfers, and a large recommendation table can exceed local memory capacity. Changing batch size, model size, or hardware can change the limiting constraint. The table records each model’s home regime: ResNet-50 is compute-bound when it processes images in batches, yet serving one image at a time can leave it bandwidth-bound, as the roofline analysis in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^sec-ml-systems-system-balance-hardware-96ab|section 2.4]] shows. [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^tbl-ml-systems-lighthouse-archetypes|Table 2]] files MobileNetV2 as compute-bound in an “efficient regime,” meaning far less arithmetic per image than ResNet-50, yet some of its layers perform few operations per byte and can be bandwidth-bound on mobile accelerators. Which resource limits it on a specific device depends on target hardware balance, precision, and batching, the same factors that shift ResNet-50 between regimes. **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures#^sec-network-architectures|Network Architectures]]** opens up the architecture behind each lighthouse.

| **Lighthouse**             | **Archetype**                    | **Deployment Paradigm**        |
|:---------------------------|:---------------------------------|:-------------------------------|
| **ResNet-50**              | Compute-bound                    | Cloud training, edge inference |
| **GPT-2/Llama**            | Bandwidth-bound (decode)         | Cloud inference                |
| **DLRM**                   | Capacity-bound                   | Cloud for large tables         |
| **MobileNetV2**            | Compute-bound (efficient regime) | Mobile, edge                   |
| **Keyword Spotting (KWS)** | Power-bound                      | TinyML, always-on              |

Table 2: **Five Lighthouse Models**: Five recurring workloads ground the iron law in concrete practice throughout the book. Each lighthouse pairs a home regime (compute-bound, bandwidth-bound, capacity-bound, power-bound) with the deployment paradigm where it predominantly runs, illustrating a distinct resource constraint under representative execution conditions.

^tbl-ml-systems-lighthouse-archetypes

Each archetype gravitates toward the tier that relieves its primary bottleneck, starting in the cloud where compute-bound training, bandwidth-bound decoding of large models, and capacity-bound tables pool data-center resources. The image classifier **ResNet-50** anchors the compute-bound regime, spending approximately 8.2 GFLOP per image on 25.6 million parameters that occupy 102.2 MB at FP32, the 32-bit floating-point format that stores each weight in four bytes ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-he2016|He et al. 2016]]). That regular, compute-dense structure makes it the canonical benchmark for hardware accelerator performance.

Where ResNet-50 reuses weights across spatial positions and batches, the language models **GPT-2/Llama** shift the cloud bottleneck from arithmetic to memory bandwidth during autoregressive text generation ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-radford2019language|Radford et al. 2019]]; [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-touvron2023llama|Touvron, Lavril, et al. 2023]]; [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-touvron2023llama2|Touvron, Martin, et al. 2023]]). Because multi-billion parameter models exceed on-chip cache, weights reside in external memory, and generating text one token at a time for a single request forces the processor to stream those weights across the memory bus on every token with little reuse (1.5 billion parameters for GPT-2, 7 billion–70 billion parameters for Llama). This sequential access pattern creates an autoregressive bottleneck that shapes serving cost ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-pope2023efficiently|Pope et al. 2023]]), keeping large-model decoding in the cloud unless a smaller variant fits locally.

↪ Continuous batching and KV-cache paging, the runtime mechanisms that serve token-by-token generation, are developed in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^sec-model-serving-continuous-batching-8bb6|Continuous batching]]**.

A third cloud workload hits the memory precondition before bandwidth or arithmetic can become the limit. The recommendation lighthouse, **DLRM**[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn7|⁷]], is the embedding-heavy recommendation workload behind large-scale “You might also like” systems ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-naumov2019deep|Naumov et al. 2019]]). It represents each user and each item by an embedding, a learned vector of numbers that the model looks up by ID. With one vector for every user and item, these lookup tables can exceed 100 GB of embeddings, making memory capacity rather than computation the limiting constraint.

Moving from data centers to edge and mobile devices requires shrinking those resource demands by orders of magnitude. The mobile lighthouse, **MobileNetV2**, performs the same image classification task as ResNet-50 while cutting its computation by 13.7× ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-sandler2018|Sandler et al. 2018]]). It gets there by restructuring the image-filtering layers, splitting each expensive filtering step into two much cheaper ones (depthwise separable convolutions). That reduction makes it a candidate for real-time inference within a smartphone’s 3–5 W envelope; the implementation and workload determine whether it meets the deadline.

↪ How depthwise separable convolutions factor one filtering step into two cheaper ones is developed in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.04 CNNs Spatial Pattern Processing#^sec-network-architectures-efficient-architectures-keyword-spotting-0625|Depthwise separable convolutions]]**.

Stepping down once more to microcontrollers puts power and kilobyte memory first. The TinyML lighthouse, **keyword spotting (KWS)**, represents the always-on sensing archetype, detecting short trigger phrases with compact models built for resource-constrained microcontrollers ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-zhang2017hello|Zhang et al. 2017]]). The lighthouse workload has approximately 200K parameters, about 200 KB at INT8, 8-bit integers that store each weight in one byte (kept in flash), placing it in the kilobyte-memory, milliwatt-budget TinyML regime. Its weights must first fit in kilobytes of memory; once they do, the energy each inference costs decides how long the device can keep listening, which is why [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^tbl-ml-systems-lighthouse-archetypes|table 2]] files it as power-bound.

Checking whether such a constrained workload can run at all requires testing the capacity precondition before evaluating the iron law’s time terms. A smart doorbell, a TinyML scenario that recurs through later chapters alongside the five lighthouses, applies the always-on pattern to vision and illustrates this two-level screen, checking storage first and latency second. A visual wake-word model ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-chowdhery2019vww|Chowdhery et al. 2019]]), a small classifier that answers only whether a person is in view, runs on an ESP32-S3, an inexpensive microcontroller with megabytes of flash for weights and a few hundred kilobytes of on-chip SRAM for working data; [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^tbl-representative-systems|table 4]] later uses the same chip as its TinyML platform. At level 1, the 0.5 MB of 16-bit weights occupy 11.9 percent of the 4.2 MB flash. Passing this storage check does not establish complete memory fit, because intermediate results and runtime state must also fit in SRAM, the two-tier split that [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.09 TinyML Ubiquitous Sensing#^sec-ml-systems-tinyml-advantages-operational-tradeoffs-2d40|section 2.8.1]] develops.

Level 2 of the doorbell screen applies the iron law. The model needs 25 MFLOP per frame, and the microcontroller sustains about 0.25 GFLOP/s at this precision, so compute takes 100 ms; about 1 ms of fixed overhead brings the total to 101 ms. That estimate clears the scenario’s canonical 200 ms budget; sensor acquisition and any data movement omitted by the estimate must still be checked. A more responsive chime with a 50 ms budget changes the verdict without changing the model, and [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^fig-doorbell-scorecard|figure 3]] plots that tightened case. In the plot, flash stays far below the saturation line while latency reaches 202 percent of its budget. Flash storage was not the limiting constraint; latency is, and on-chip SRAM still has to be checked separately.

![[90 Assets/Volume I/02 System Paradigms/Doorbell Scorecard Output 1 a39d442dbc.png]]

Figure 3: **Smart Doorbell Constraint Scorecard**: Each bar is demand over supply, so the dashed line marks the point where a level is exactly saturated. The model occupies a small fraction of the ESP32-S3’s 4 MB flash budget (Level 1: PASS), but its 101 ms latency (25 MFLOP of compute plus fixed overhead) is twice a tightened 50 ms budget for a responsive chime (Level 2: FAIL), even though it clears the scenario’s canonical 200 ms budget.

^fig-doorbell-scorecard

Even on one microcontroller, tightening the deadline turns latency from a passing check into the limiting constraint, and across the full lighthouse set the resource demands diverge far more sharply. A keyword spotter operates with roughly 20 MFLOP per inference and about 200 KB of INT8 weights, whereas ResNet-50 requires about 8.2 GFLOP per image and roughly 102.2 MB of FP32 weights. The reference DLRM example already reaches 100 GB, and Meta has demonstrated scaling recommendation models to 100 TB using embedding offloading ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-park2024offloading|Park et al. 2024]]), while language models stream billions of parameters repeatedly from memory during autoregressive inference. Whether each of these demands passes its capacity and timing checks depends on the compute, bandwidth, and memory a given platform supplies.
