# V1-02.07 Edge ML Latency and Privacy

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02 System Paradigms|V1-02 System Paradigms]]

^sec-ml-systems-edge-ml-reducing-latency-privacy-risk-2625

The robotic-arm safety monitor in napkin math [2.2](https://mlsysbook.ai/vol1/02_system_paradigms/02_system_paradigms.html#nbk-ml-systems-distance-penalty), an industrial IoT (IIoT) control loop,[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn13|¹³]] left one option open: running the model beside the arm it protects. Edge ML is built on that move, trading elastic cloud capacity for shorter request paths and local data retention.

In terms of the pipelined iron law ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-bottleneck|equation 5]]), placing computation adjacent to the sensor removes the wide-area offload term ${T_{\text{IO}}}$ and the remote propagation floor from the request path, leaving execution time bounded by local compute and memory transfer. Proximity alone does not guarantee that a deadline such as the arm’s is met, however, because the local hardware has fixed capacity and the complete sensing-to-actuation path must still fit within the deadline.

**Definition 2.2: Edge ML**

***Edge machine learning*** is the deployment paradigm optimized for local response and data locality by locating computation physically adjacent to data sources.

1.  **Significance**: It circumvents the distance penalty $({L_{\text{lat}}})$ of the cloud, trading elastic scale for a fixed local compute capacity $({R_{\text{peak}}})$.
2.  **Distinction**: Unlike cloud ML, which prioritizes throughput, edge ML prioritizes response deadlines and local data control. Unlike TinyML, edge ML may still use workstation-class accelerators such as general-purpose GPUs (GPGPUs).
3.  **Common pitfall**: A frequent misconception is that edge ML refers to a specific hardware class. In reality, it is a location paradigm: it spans from IoT gateways to on-premises servers, unified by physical proximity to the data source.

Real-time deadlines are not the only driver. Data sovereignty and privacy rules can restrict transmitting raw sensor streams across external networks, which places computation on local gateways, industrial PCs, and on-premises servers. Placing compute near sensors and filtering data locally helps meet sub-100 ms response budgets, while introducing failure boundaries in fixed node capacity and remote fleet management ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.07 Edge ML Latency and Privacy#^fig-edge-ml|figure 6]]).

Even when latency budgets are relaxed, the second limiting constraint in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.07 Edge ML Latency and Privacy#^fig-edge-ml|figure 6]], where raw sensor data is wider than the network pipe, can rule out cloud ingestion on bandwidth alone. When continuous IoT sensor ingestion rates[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn14|¹⁴]] exceed uplink capacity, local filtering or inference must shrink the transmitted stream before it reaches the wide-area link, and the complete local and remote paths then determine where inference can meet the application’s requirements.

**Napkin Math 2.4: The bandwidth bottleneck**

**Problem**: Consider a quality control system for a factory floor with 100 cameras running at 30 FPS with 1080p resolution. Does video streaming become the bandwidth bottleneck, and does edge ML reduce the bandwidth enough to process locally?

**Physics**:

1.  **Raw data rate per camera**: 1920 $\times$ 1080 $\times$ 3 bytes $\times$ 30 FPS ≈ 186.6 MB/s.
2.  **Total data rate**: 100 cameras $\times$ 186.6 MB/s = 18.7 GB/s.
3.  **Network reality**: Even a dedicated 10 Gbps line (1.25 GB/s) cannot carry the load, because the workload demands 14.9× more bandwidth than exists.
4.  **Retrieval cost**: Uploading the raw feeds is a bandwidth problem first. If the raw stream were stored in the cloud anyway, pulling it back out would also cost money. Retrieving it, for example to relabel footage for retraining, at \$0.09/GB data-transfer-out pricing would cost \$4.4M/month.

**Systems insight**: Streaming these raw feeds over the stated link is *impossible*. Local processing or a smaller transmitted representation is required; compression changes the bandwidth calculation but must preserve the information and timing needed for defect detection. If an edge server transmits only defect metadata (1 KB per detection at roughly 20 events/s across the floor), bandwidth falls by about 933,120×.

Uncompressed sensor streams can saturate an uplink, which is the bandwidth barrier to centralized ingestion. For battery-powered edge devices (wireless cameras, drones, wearables), the energy cost of wireless communication introduces an even stricter physical ceiling. The battery and thermal limits behind that ceiling are developed with mobile devices in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.08 Mobile ML Offline Intelligence#^sec-ml-systems-mobile-ml-personal-offline-intelligence-0983|section 2.7]]; the question here is only whether transmitting data costs more energy than processing it locally. Offloading adds energy to the time-based analysis of [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-bottleneck|equation 5]], so the local-versus-offload decision must weigh joules as well as milliseconds.

**Napkin Math 2.5: The energy of transmission**

**Problem**: Should a battery-powered device such as a phone process one inference’s raw input locally (on its NPU) or send it to the cloud when the energy of transmission must come out of a fixed battery budget?

**Given**:

- **Data $({D_{\text{vol}}})$**: 1 MB (the raw input for one inference, an illustrative volume).
- **Transmission energy $({E_{\text{tx}}})$**: 100 mJ/MB (Wi-Fi/LTE; an energy per byte, quoted here per megabyte).
- **Compute energy $({E_{\text{local}}})$**: 0.1 mJ/inference (illustrative MobileNetV2 anchor for the neural processing unit alone, excluding the rest of the phone).

**Math**:

1.  **Cloud approach**: ${E_{\text{transmit}}}\approx {D_{\text{vol}}} \times {E_{\text{tx}}}$ = 1 MB $\times$ 100 mJ/MB = 100 mJ.
2.  **Local approach**: ${E_{\text{local}}}\approx$ Inference = 0.1 mJ.

**Systems insight**: Transmitting raw data is 1,000× more expensive than processing it locally. Charging local inference with the whole phone’s energy over the inference window (2.6 mJ, the MobileNetV2 bar charted in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.07 Edge ML Latency and Privacy#^fig-energy-per-inference|figure 7]]) still leaves transmission 39× more expensive. Even if the cloud had infinite speed $({T}\approx 0)$, the stated battery budget favors local inference over raw-data transmission. The machine constraint (battery) shapes the deployment choice.

[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.07 Edge ML Latency and Privacy#^fig-energy-per-inference|Figure 7]] steps back from that matched comparison. It supplies energy scale anchors for different tasks and accounting boundaries on a logarithmic scale spanning eight orders of magnitude. The figure isolates the 100,000,000× gap between an always-on TinyML keyword spotting inference (about 10 µJ) and a cloud foundation-model query (about 1 kJ, an order-of-magnitude scenario anchor that includes data-center overhead rather than a measured value).

**Systems Perspective 2.2: Reading the energy-per-inference numbers**

The logarithmic comparisons plotted in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.07 Edge ML Latency and Privacy#^fig-energy-per-inference|figure 7]] combine solver-derived device-energy estimates with separate scale anchors; they are not controlled full-system measurements. Each vision bar counts one device over its batch-1 inference window. The cloud ResNet-50 bar, for example, charges an A100 averaging about ~130 W for 0.57 ms. It excludes the host CPUs, memory, networking, and cooling that bring an entire server to about ~1 kW, so a whole-server accounting of the same request would be several times larger.

The span becomes tangible when measured in a familiar unit of energy, one smartphone battery. The nominal energy stored in a 3.7 V, 3000 mAh battery covers about 4 billion inferences on the keyword spotter but only about 40 queries on a cloud LLM. The battery serves only as a familiar yardstick for an amount of energy: a cloud query’s energy is spent in the data center, not drawn from the phone. Nor are the keyword-spotting counts elapsed battery life: actual runtime still depends on inference cadence, sleep power, sensing, communication, and the rest of the device.

### The Data Locality Invariant: When the Network Is Too Slow

^sec-ml-systems-data-locality-invariant

Even if a battery-powered drone or camera could afford the radio energy to stream raw video, the wireless link would still fail a more immediate test: time. When a delivery drone captures 4K video at 60 frames per second to dodge obstacles, shipping even one uncompressed frame over a cellular link takes longer than the 16.7 ms interval before the next frame arrives. That per-request bandwidth-latency trade-off governs the choice between local edge processing and remote cloud offload. The data locality invariant below is the per-request, deadline-bound form of the data-gravity principle from the cloud section. Where data gravity weighs moving a whole dataset against moving the computation, the invariant weighs moving one input against one deadline. A remote path is rejected when its complete time exceeds the service deadline, and among the paths that remain, the faster one wins.

**Definition 2.3: The data locality invariant**

***The data locality invariant*** states that no remote hardware can shorten the time to send an input across the network and back, so a remote path is ruled out when even its lower bound, that network time plus the fastest possible remote computation, exceeds the service deadline. The expression below gives a lower bound on complete remote-path time ${T_{\text{remote}}}$; let ${T_{\text{deadline}}}$ denote the deadline, ${\text{BW}_{\text{network}}}$ offload bandwidth, ${L_{\text{lat,network}}}$ network latency, and ${R_{\text{peak,remote}}}$ and ${\eta_{\text{hw,remote}}}$ the remote compute rate and efficiency:

$$
{T_{\text{remote}}} \ge \frac{{D_{\text{vol}}}}{{\text{BW}_{\text{network}}}} + {L_{\text{lat,network}}} + \frac{{O}}{{R_{\text{peak,remote}}} \cdot {\eta_{\text{hw,remote}}}}
$$

The bound omits remote memory movement, queueing, preprocessing, runtime overhead, and response serialization, so a bound above the deadline rejects the remote path, whereas a bound below it only makes the path a candidate for complete-path measurement. Here, ${L_{\text{lat,network}}}$ covers propagation, routing, and protocol handshakes.

1.  **Significance**: What stays invariant is the transmission and propagation time, which no amount of remote compute $({R_{\text{peak,remote}}})$ reduces. The invariant therefore marks a crossover, the input size at which transmission alone uses up the deadline; beyond it, faster remote hardware cannot rescue the remote path, as the drone frame in napkin math [2.6](https://mlsysbook.ai/vol1/02_system_paradigms/02_system_paradigms.html#nbk-ml-systems-napkin-math-locality-crossover) shows. The local path is preferred only after its own complete execution time and resource limits are checked.
2.  **Distinction**: Unlike the iron law, which decomposes one execution path, the locality invariant uses a deadline to reject an idealized remote path, then requires complete-path evidence to choose between the remaining alternatives.
3.  **Common pitfall**: A frequent misconception is that 5G/6G “solves” locality. While these technologies improve ${\text{BW}_{\text{network}}}$, they do not remove propagation and protocol latency, so a remote path can still miss a tight service deadline.

The locality formulation also explains what every local tier gains, edge, mobile, and TinyML alike. Local execution removes network transit time (${D_{\text{vol}}}/{\text{BW}_{\text{network}}} + {L_{\text{lat,network}}}$) from the request path, eliminating wide-area network variability. A closed-loop latency guarantee requires validating a bound on the complete local path under its operating conditions, ${T_{\text{local}}}\le {T_{\text{deadline}}}$. Uplink traffic drops from raw sensor bitrates to lightweight event telemetry, relieving congestion and recurring transit charges. Keeping raw sensor data where it is captured shrinks the transmission attack surface, although local processing alone does not guarantee privacy: data at rest still needs access control, and retention and secondary use still need governance. Local inference also continues through wide-area outages whenever local power and sensor links remain functional. Mobile and TinyML inherit all four gains; what distinguishes them is what each gives up to obtain them.

The drone that opened this section shows where the crossover falls in practice.

**Napkin Math 2.6: The locality crossover**

**Problem**: Should a drone’s object avoidance system (4K, 60 FPS) offload to the cloud, or does this become a locality crossover?

**Given**:

- **Data $({D_{\text{vol}}})$**: 4K frame ≈ 24.9 MB.
- **Bandwidth $({\text{BW}_{\text{network}}})$**: 100 Mb/s cellular uplink.
- **Remote network and compute response**: 110 ms (round-trip + remote compute).
- **Per-frame completion deadline**: 16.7 ms, equal to the frame interval in this illustrative scenario; each avoidance result must be ready before the next frame arrives.

**Math**:

1.  **Transmission time**: 24.9 MB $\times$ 8 bits/100 Mb/s = 1,990.7 ms.
2.  **Remote-path lower bound**: Transmission + 110 ms remote response = 2100.7 ms, vs. the stated 16.7 ms per-frame deadline.

**Systems insight**: The remote path misses the stated per-frame deadline, and faster remote compute cannot remove the transmission time. Cloud offload is therefore infeasible under these assumptions; the local path must still be measured to confirm that it meets the deadline.

### Edge ML Deployment Challenges

^sec-ml-systems-edge-ml-benefits-deployment-challenges-b2d0

Keeping inference on the factory floor or inside a retail store eliminates the wide-area network delay, but now the model must fit inside whatever compute box is bolted to the wall. If a firmware update fails across a thousand stores, no data-center operations team can walk down the aisle to swap the board. Edge deployment trades network transit for fixed local capacity.

Edge hardware spans a wide power envelope, from 5–50 W embedded modules to site-powered servers drawing hundreds of watts, and its limit is the fixed capacity of a site rather than the elastic capacity of a cloud region. Many smaller embedded modules operate within 1–8 GB of memory,[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn15|¹⁵]] and their power and board budgets cannot support the wide, high-power interfaces of HBM. They rely on LPDDR or shared system DRAM instead, so memory capacity limits parameter scale and memory bandwidth limits throughput. Fitting modern machine learning models into these bounds requires efficiency techniques that store weights in fewer bits (quantization), remove weights that contribute little (pruning), or train a smaller model to imitate a larger one (distillation). Model footprint, activation buffers, runtime state, and thermal duty cycles all become limiting constraints.

Operating these devices is as hard as fitting models onto them. Coordinating software updates and model versions across thousands of heterogeneous, physically exposed devices requires specialized deployment pipelines,[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn16|¹⁶]] where intermittent links and physical access complicate rollback and failure diagnosis.

↪ Over-the-air updates, dual-bank rollback, and lightweight fleet telemetry for edge devices are developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-edge-ai-deployment-patterns-dc1d|Edge AI deployment]]**.

A realistic retail deployment shows how those constraints turn into throughput, hardware, and fleet-cost requirements. Consider a smart retail chain that deploys person detection across 500 stores, each with 20 cameras/store running at 15 FPS. [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.07 Edge ML Latency and Privacy#^tbl-ml-systems-edge-sizing-requirements|Table 7]] cascades the per-store inference rate through the per-frame FLOP count of YOLOv8-nano, a compact object-detection model, to yield the throughput each store must sustain. The 2$\times$ headroom keeps the device out of saturation when traffic bursts above the average rate. Edge accelerators run such a model in 8-bit integer arithmetic and count one integer operation for each floating-point one, so the floating-point rate converts directly into an INT8 TOPS requirement.

**Napkin Math 2.7: Edge inference sizing**

**Problem**: Given the throughput target in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.07 Edge ML Latency and Privacy#^tbl-ml-systems-edge-sizing-requirements|table 7]] and the candidates in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.07 Edge ML Latency and Privacy#^tbl-ml-systems-edge-hardware-options|table 8]], which edge accelerator (Google Coral Dev Board with an Edge TPU, workstation-class embedded GPU, or general-purpose mini-PC) delivers the required throughput at the lowest estimated three-year hardware-and-power budget?

**Math**: The capacity screen uses an assumed sustained rate rather than the datasheet peak. The scenario’s 50 percent derating plays the role of the efficiency ${\eta_{\text{hw}}}$ in the iron law. One Jetson derates from 100 TOPS to 50 TOPS, far above the 5.22 TOPS requirement. One NUC derates to 0.5 TOPS and falls short; meeting the target would take 11 per store, about \$2,200,000 of hardware across the fleet. A Coral Dev Board is rated at 4 TOPS peak. The same derating gives 2 TOPS, so the count per store is 5.22 TOPS required ÷ 2 TOPS per board = 2.6 boards, which rounds up to 3 boards/store. This estimate assumes the model’s operations and numerical format are supported and that work can be divided across the boards at the assumed rate.

Over 3 years across 500 stores, the hardware-and-power estimate for that configuration is Hardware \$225,000 + Power (0.006 kW $\times$ 500 $\times$ 8760 h/year $\times$ 3 years $\times$ \$0.12/kWh = \$9,461) = \$234,461 total. For comparison, a baseline of one dedicated cloud GPU per store, at the same \$0.75/hr instance rate as the cloud-versus-edge comparison, costs ~\$9,855,000. Within this accounting boundary, the other two candidates need no power arithmetic to rank, because the Coral configuration’s hardware-and-power estimate is already below the Jetson fleet’s \$300,000 hardware cost and far below a feasible NUC fleet’s. Integration, maintenance, redundancy, and matched cloud operating costs remain outside this comparison.

**Result**: One Coral alone is undersized under these assumptions, but the sharded configuration with 3 boards/store is a low-cost edge candidate within the hardware-and-power boundary, with an estimated 6 TOPS and about 1.3× lower per-store hardware CapEx than Jetson. Jetson remains the simpler single-device candidate when integration complexity matters more than hardware cost.

**Systems insight**: Edge sizing is a capacity-and-cost problem, not a device-name problem. The cheapest feasible design may be several small accelerators per site rather than one larger board, but that hardware saving must be weighed against the coordination and maintenance burden of a sharded edge fleet. The estimate narrows the candidates; measurements of the actual model and runtime must establish task quality, throughput, and end-to-end latency before deployment.

Edge hardware is also physically exposed. Unlike servers housed in access-controlled data centers, edge hardware deployed across retail floors or public infrastructure is physically accessible to adversaries. This exposure calls for hardware protections that keep an attacker from altering the device’s software or reading the model it stores.

Capital expenditures also scale linearly with deployment footprint, so equipping 1,000 sites with \$500–2,000 of edge hardware per site requires \$500,000–2,000,000 in upfront CapEx before installation, cabling, and fleet operations. Whether that upfront investment yields a lower total cost of ownership than recurring cloud inference depends on utilization duty cycles, local energy rates, and site maintenance overhead.

### Real-Time Industrial and IoT Systems

^sec-ml-systems-realtime-industrial-iot-systems-373a

Organizations accept that upfront capital cost and fleet-management burden most readily when physical locality makes remote execution impossible. Autonomous vehicles show the strictest latency case: safety-critical perception and control decisions must fit millisecond-scale budgets as the vehicle moves. Onboard systems process streams from multiple cameras and other sensors through local hardware because a remote cloud path cannot satisfy the control loop when network delay alone exceeds the deadline.

In smart retail, the per-store camera sizing in napkin math [2.7](https://mlsysbook.ai/vol1/02_system_paradigms/02_system_paradigms.html#nbk-ml-systems-edge-inference-sizing) extends from person detection to full store state, where uplink bandwidth and privacy become the limits before compute does. A checkout-free store[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn17|¹⁷]] processes feeds from many cameras on local edge servers, tracking customer movements and item selections without continuously transmitting raw video over a wide-area link. This architecture reduces bandwidth demand and transmission exposure, but it does not by itself ensure privacy: retention, access, secondary use, and governance controls still determine the system’s compliance and risk.

On the factory floor, the industrial IoT (often called Industry 4.0 when ML closes the factory control loop[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn18|¹⁸]]) combines the latency constraint of the robotic-arm monitor (napkin math [2.2](https://mlsysbook.ai/vol1/02_system_paradigms/02_system_paradigms.html#nbk-ml-systems-distance-penalty)) with the uplink wall of multi-camera inspection (napkin math [2.4](https://mlsysbook.ai/vol1/02_system_paradigms/02_system_paradigms.html#nbk-ml-systems-bandwidth-bottleneck)). Manufacturing facilities deploy these local loops where millisecond-level responsiveness governs real-time quality control and where continuous vibration and thermal sensing drive predictive maintenance.[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn19|¹⁹]]

Many industrial and retail edge systems are stationary and connected to site power, where a factory edge server drawing hundreds of watts around the clock remains viable. Mobile devices, by contrast, travel with untethered users on strictly bounded battery reserves. When computation moves from stationary infrastructure to an untethered mobile device, battery energy becomes a central constraint alongside latency, and the dominant optimization target shifts from raw execution time to energy per inference.

**Self-Check: Question**

1.  A manufacturing facility deploys 100 cameras recording uncompressed 1080p video ($1920 \times 1080 \times 3\text{ bytes/pixel}$) at 30 FPS. The factory has a dedicated 10 Gbps (~1.25 GB/s) fiber uplink. Why is streaming all raw video to a cloud ML server physically impossible?

    1.  The total is only about $186.6\text{ MB/s}$ because that is the per-camera rate, so the 10 Gbps uplink has ample headroom.
    2.  The aggregate is about $18.7\text{ Gb/s}$ because the camera output should be compared numerically to 10 Gbps without converting bytes to bits, so the link is close enough to be practical.
    3.  The aggregate raw video data rate is approximately $18.7\text{ GB/s}$, which exceeds the $1.25\text{ GB/s}$ uplink capacity by roughly $15\times$.
    4.  The aggregate raw stream is large, but normal compression assumptions would make it fit within the 10 Gbps uplink in practice.

2.  An autonomous drone navigates at 60 FPS (16.7 ms per-frame budget) capturing uncompressed 4K frames (~24.9 MB per frame). The drone connects via a 100 Mbps uplink to a cloud server whose round-trip latency plus inference time is 110 ms. Applying the data locality invariant, what is the feasibility of offloading this obstacle avoidance system to the cloud?

    1.  Feasible, because the cloud GPU computes inference in under 10 ms.
    2.  Feasible, provided 5G network slicing is enabled on the drone modem.
    3.  Infeasible, solely because cloud servers do not support drone telemetry protocols.
    4.  Infeasible, because transmitting a 24.9 MB frame over a 100 Mbps link requires ~2,000 ms, causing even the remote-path lower-bound estimate (~2,100 ms) to violate the 16.7 ms frame deadline by over two orders of magnitude.

3.  Why cannot high-bandwidth wireless networking technologies (such as 5G or 6G) eliminate the need for edge ML in tight real-time control loops ($<10\text{ ms}$)?

4.  A retail store needs about 5.2 TOPS of sustained throughput. Why does the chapter’s estimate call for three 4 TOPS boards rather than two, even though two boards’ combined 8 TOPS peak exceeds the target?

5.  An illustrative 60 Hz industrial control scenario assumes each sensing-to-actuation response must finish before the next sample. Its complete ML control loop latency ($L_{\text{lat}}$) must therefore fit within one \_\_\_\_ (about 16.7 ms).
