# V1-02.11 Hybrid Architectures

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02 System Paradigms|V1-02 System Paradigms]]

^sec-ml-systems-hybrid-architectures-combining-paradigms-7cdd

A voice interface can use a microcontroller to listen continuously for a wake word, a phone to transcribe speech, and cloud servers to interpret requests that need a larger model. Each stage has a different task and resource budget. Sending every audio sample to the cloud would add communication and radio costs; asking the microcontroller to perform every stage would exceed its compute and memory capacity. *Hybrid architectures* divide the pipeline across tiers so that each stage meets its requirements ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-kang2017neurosurgeon|Kang et al. 2017]]). Economics drive this division as much as latency: processing voice interactions for billions of devices entirely in the cloud runs into both an economic and an infrastructure ceiling, and the voice assistant wall puts a number on each.

**Napkin Math 2.10: The voice assistant wall**

**Problem**: In this illustrative capacity scenario, 1B voice assistant devices (smartphones, smart speakers, earbuds) each issue 20 queries/day after the wake word. Detecting the wake word itself in the cloud would require every microphone to stream audio continuously. What load would cloud-side detection impose, and what load remains in the cloud once detection moves on device?

**Cloud-side detection**: The always-listening path that local detection removes.

- **Audio streaming**: Every device streams audio continuously (16 kHz, 16-bit), about 32 KB/s each. Across 1 billion devices the aggregate is 32 TB/s, and each stream would also need its own continuously running detector.
- **Cloud cost**: ~\$0.50/device/year $\times$ 1B devices = \$500,000,000/year. Economically prohibitive under these assumptions for a free feature.
- **TinyML alternative**: 0.1–1 mW local wake-word detection, \<\$0.01/device/year. If each post-wake query uploads about 5 s of audio, local detection cuts the audio leaving each device by about 860×.

**Residual cloud load**: The post-wake queries the hybrid design still serves in the cloud. Even with local wake-word filtering, the residual query volume (1 billion devices generating 20B queries/day at ~200 ms per query) still requires substantial centralized accelerator capacity (~1.1 million GPU-hours per day).

Five parameters determine the required cluster capacity:

1.  **Query volume**: 1 billion devices $\times$ 20 queries/day = 20B queries/day.
2.  **GPU demand**: Each query requires ~200 ms of GPU time. Total: 1.1 million GPU-hours/day.
3.  **Scenario capacity**: A data-center equivalent provisioned with 10,000 GPUs provides 240,000 GPU-hours/day.
4.  **Average requirement**: ~4.6 dedicated data centers just for voice inference.
5.  **Peak reality**: Queries cluster in waking hours (~4.5× peak-to-average), requiring ~20.8 data centers at peak.

**Systems insight**: Local detection reduces each device’s upload to its post-wake queries, 20 queries/day of a few seconds each. The residual post-wake load is still large, tens of data centers at peak, but it is bounded by what users actually ask. It is the load the hybrid design deliberately keeps in the cloud, to use a larger language model than the local device can support.

Partitioning the voice pipeline into an on-device wake-word filter and a cloud-based language model relieves both the client’s energy limit and the data center’s capacity limit. The division also creates engineering work: deciding what data crosses each boundary and keeping the participating stages consistent. Three integration patterns organize these choices.

### Splitting Work Across Tiers: Three Integration Patterns

^sec-ml-systems-integration-patterns-5935

When a single tier cannot satisfy every stage of an ML pipeline, engineers split the pipeline along one of three physical boundaries: train-serve split, hierarchical processing, or progressive deployment. Selecting a pattern is an iron-law decision, because each stage of computation must execute where its limiting term (throughput capacity ${R_{\text{peak}}}$, local latency floor ${L_{\text{lat}}}$, or the memory-capacity precondition) incurs the lowest system penalty.

Under a **train-serve split**, training executes in centralized data centers while inference runs locally on edge, mobile, or embedded devices. Training must retain intermediate results and information used to calculate and apply parameter updates, in addition to the model weights. Under a common 16-bit training setup, the weights and the extra values training keeps for each weight to compute its updates together occupy about 16 bytes per parameter ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-rajbhandari2020|Rajbhandari et al. 2020]]). That is roughly 8× the 2 bytes per parameter that 16-bit inference weights need, before any batch activations are counted (**[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^sec-model-training-memory-management-c1ec|Memory management]]** develops this accounting). Inference uses the trained weights to compute predictions, sometimes through repeated passes as in token-by-token generation, and must satisfy local latency and privacy constraints. Amortization underpins the economics of this split: the high fixed cost of training is distributed across millions of forward-pass queries served locally without recurring network transmission costs.[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn33|³³]]

**Definition 2.6: Hybrid ML**

***Hybrid machine learning*** is the deployment strategy that distributes an ML pipeline across two or more deployment tiers, assigning each stage according to its latency, compute, data, and operational constraints.

1.  **Significance**: Hybrid architectures exploit the iron law’s additive structure: the edge tier can reduce ${L_{\text{lat}}}$ for time-sensitive preprocessing and inference, while the cloud tier can provide the ${R_{\text{peak}}}$ needed for training, retraining, and heavy batch inference. The split follows the data locality invariant: compare each stage’s complete local and remote paths, reject paths that miss the service deadline, and then choose among the feasible alternatives.
2.  **Distinction**: Unlike cloud-only deployment (which accepts the distance penalty for all stages) or edge-only deployment (which accepts limited ${R_{\text{peak}}}$ for all stages), hybrid ML assigns each pipeline stage to the tier where its limiting iron law term is minimized.
3.  **Common pitfall**: A frequent misconception is that hybrid ML is just “running two models.” In reality, the participating tiers must share synchronized state (feature definitions, model versions, and preprocessing logic) so that their paths produce consistent results. Without this synchronization, training-serving skew emerges at tier boundaries, in which a model receives inputs prepared differently from those it was trained on (**[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-ensuring-trainingserving-consistency-c683|Training-serving consistency]]**).

Under **hierarchical processing**, computation cascades across tiers to filter and summarize data step by step, matching communication volume to available link bandwidth. Raw sensor streams from cameras or microphones at the edge of the network often exceed wide-area network (WAN) uplink capacity; continuously streaming uncompressed telemetry to a data center saturates network links and wastes radio power. To prevent network saturation, early tiers filter data locally. TinyML microcontrollers run low-power anomaly detectors, edge gateways aggregate and correlate temporal features across multiple sensors, and cloud clusters ingest only anomalous events or aggregated summaries for global analytics. A voice interface that divides wake-word detection, acoustic processing, and language understanding among tiers applies the same cascade across different tasks.

During inference serving, hierarchical processing frequently takes the form of a confidence cascade ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-teerapittayanon2017distributed|Teerapittayanon et al. 2017]]). A compact, low-latency model on the local device evaluates the input first. If its prediction confidence exceeds a calibrated confidence threshold, the device returns the result immediately, bypassing the network entirely. Only ambiguous or low-confidence inputs trigger a WAN payload transfer to a larger cloud model. The cascade seeks lower median latency at the required task quality, but confident local errors can bypass escalation. Representative evaluation must establish the routed system’s accuracy, error costs, and escalation frequency before accepting that trade-off.

Under **progressive deployment**, an engineering team derives a family of specialized model variants from a unified architecture or training corpus, tailoring each variant to the memory capacity, compute-to-bandwidth balance, and thermal limits of a specific tier. Rather than forcing a single model onto every device, developers produce tier-specific artifacts and evaluate the quality lost or retained as resource demands fall. The compression mechanisms are developed later; the placement decision here depends on whether each artifact meets its task and hardware constraints. For a shared image-classification task, an edge server and a phone can use different members of a model family, each evaluated against the same task requirements and its own resource budget.

With three integration patterns available, selection becomes a constraint-matching problem: choose the pattern whose trade-off profile matches the system’s dominant bottleneck, weighing the conditions that favor each pattern against those that disqualify it ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.11 Hybrid Architectures#^tbl-ml-systems-hybrid-pattern-selection|table 10]]).

| **Pattern**                 | **Trade-off**                          | **Choose when**                                                                             | **Avoid when**                                                      |
|:----------------------------|:---------------------------------------|:--------------------------------------------------------------------------------------------|:--------------------------------------------------------------------|
| **Train-Serve Split**       | Training cost vs. inference latency    | Training requires more resources than inference; training data may leave the serving device | Local adaptation cannot wait for remote training and model delivery |
| **Hierarchical Processing** | Local autonomy vs. global optimization | Data volume exceeds transmission capacity; decisions needed at multiple timescales          | All processing can occur at one tier; network is reliable and fast  |
| **Progressive Deployment**  | Model quality vs. deployment reach     | Same model needed at multiple capability levels; graceful degradation required              | Model cannot be meaningfully compressed; single deployment target   |

Table 10: **Hybrid Pattern Selection Guide**: Each of the three hybrid integration patterns has a characteristic trade-off, favoring conditions, and disqualifying conditions. Selection matches the pattern’s trade-off profile to the system’s dominant bottleneck.

^tbl-ml-systems-hybrid-pattern-selection

Production deployments rarely implement these patterns in isolation; complex systems compose them across different phases of the pipeline. An autonomous vehicle, for example, combines progressive deployment to fit specialized vision backbones into its on-board compute envelope. It uses hierarchical processing to arbitrate between immediate millisecond-scale emergency braking on local hardware and multi-second trajectory planning. It also applies a train-serve split that uploads anomalous driving slices to cloud clusters for fleet-level retraining. Privacy-preserving distributed training approaches extend this composition further when raw training data cannot leave client devices for regulatory or privacy reasons. In federated learning ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-mcmahan2017communication|McMahan et al. 2017]]), for example, each device trains on its own data and sends only model updates to the cloud for aggregation.

### How Hybrid Tiers Communicate in Production

^sec-ml-systems-production-system-integration-3bb3

If a phone’s audio preprocessor updates its normalization constants while the cloud transcription model expects the old scaling, or if a smartwatch and phone disagree on which activity labels are active, the hybrid pipeline fails silently across the tier boundary. Keeping multiple execution tiers working as one system requires five explicit communication channels ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.11 Hybrid Architectures#^fig-hybrid|figure 12]]). Compiled model artifacts deploy downward from cloud training clusters to edge, mobile, and TinyML inference engines, while raw sensor streams and filtered telemetry propagate upward toward cloud analytics. Between adjacent local tiers, devices forward intermediate inference results and offload heavier queries through assist handoffs, while continuous state synchronization keeps feature definitions, preprocessing constants, and model versions aligned across every boundary.

Five connection types (deploy, data, results, assist, and sync) establish a distributed architecture where each paradigm contributes unique capabilities.

In the factory, agricultural, and wearable domains introduced earlier in the chapter, production systems place each tier boundary where a single-tier deployment hits its physical limit:

1.  **Industrial defect detection**: Assembly lines running at high cycle rates require sub-10 ms deterministic visual inspection. Streaming high-resolution camera frames over WAN to a data center violates inspection deadlines and exhausts factory uplink bandwidth. The system deploys a train-serve split: centralized cloud infrastructure trains high-capacity vision models on historical defect databases, then compiles and quantizes runtime weights for factory-floor edge servers and embedded smart cameras, which run inference locally without external network dependencies. The complete local pipeline, including frame acquisition, preprocessing, and inference, must still be validated under the expected load.
2.  **Agricultural monitoring**: Deployed across hundreds of hectares, remote soil probes run on coin-cell batteries or small solar harvesters and communicate over low-power wide-area radios such as LoRa, which carry little data and spend much energy per bit. Streaming continuous moisture and temperature telemetry would exhaust battery reserves within days. Hierarchical processing therefore keeps high-frequency sampling and basic anomaly detection on TinyML microcontrollers in sub-milliwatt power budgets. Local edge gateways aggregate measurements across clusters of probes and send only compressed, field-level summaries over cellular backhaul to cloud servers that schedule irrigation farm-wide.
3.  **Wearable fitness tracking**: A battery-powered smartwatch must keep its always-on sensing path averaging under $1\text{ mW}$ to preserve battery life. The system employs hierarchical processing. Lightweight integer kernels run on an embedded microcontroller to track real-time motion and detect heart-rate thresholds. Intermediate biometric data synchronizes over Bluetooth Low Energy (BLE) to a paired smartphone, which uses mobile neural engines and gigabytes of DRAM to classify complex activity patterns. Finally, the smartphone transmits periodic compressed summaries over Wi-Fi or cellular networks to cloud infrastructure for longitudinal health modeling.

**Checkpoint 2.3: Hybrid ML patterns**

Hybrid architectures work when partitioning work across tiers, not when copying the same pipeline everywhere.

**Integration patterns**

**Train-serve split**: Can you explain why training in the cloud and serving on edge/mobile is often economically optimal, even when the model runs locally?

**Hierarchical processing**: Can you describe what each tier does in a sensor → edge → cloud pipeline, and why pushing some decisions down reduces both latency and bandwidth?

**Progressive deployment**: Can you explain why a shared task may require different model artifacts on different tiers, and which quality and resource measurements would establish their suitability?

**Design sanity checks**

**Boundary choice**: Given a concrete application, can you justify where the tier boundary should fall (latency, privacy, bandwidth, power), not just what model to use?

**State synchronization**: Can you identify which feature definitions, model versions, and preprocessing logic must remain synchronized across tiers?

Partitioning a workload across tiers works because each stage still answers to the same physical laws and software abstractions. Whether a stage executes on a coin-cell microcontroller or a megawatt cloud pod, it is governed by the same iron-law terms and maintained through the same engineering foundations.

**Self-Check: Question**

1.  Why does serving always-on voice assistant traffic entirely in the cloud create an infrastructure and economic wall, and what does on-device wake-word detection actually remove?

    1.  On-device wake-word detection removes the need to stream every microphone continuously to the cloud, so the data-center-count estimate applies to the remaining post-wake queries rather than to constant listening traffic.
    2.  Once wake-word detection moves on device, all cloud serving disappears because speech recognition and language understanding no longer need remote models.
    3.  The main problem is only that encrypted audio cannot be processed efficiently in cloud accelerators, so local wake detection solves a hardware compatibility issue rather than a traffic-scaling issue.
    4.  Wake-word detection on device matters only for privacy; it does not materially change network load because continuous listening traffic and post-wake query traffic are the same scale.
