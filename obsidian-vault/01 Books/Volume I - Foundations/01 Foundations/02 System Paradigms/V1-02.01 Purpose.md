*Why does deploying the same model to a phone vs. a data center demand fundamentally different engineering?*

The defining insight of ML systems engineering is that constraints drive architecture. The speed of light sets an absolute floor on how quickly distant servers can respond, thermodynamics limits how much computation can occur in a given volume before heat becomes unmanageable, and memory physics makes moving data more expensive than processing it. Because these physical limits persist as technology improves, deployment categories name recurring constraint regimes rather than fixed, mutually exclusive classes of hardware, and one device can sit in more than one regime. A data center can train billion-parameter models yet cannot guarantee low-latency responses to users thousands of miles away. A smartphone can respond immediately yet holds a fraction of the memory budget and must share a small battery with the rest of the phone. A microcontroller can run on a coin-cell battery for years while offering barely enough compute for a simple keyword detector. Across these regimes, power budgets span roughly nine orders of magnitude, from megawatts in a data center to milliwatts on a microcontroller, while memory capacity spans from terabytes to kilobytes. The same model applied to the same data therefore demands radically different engineering in each regime, not because the physics changes, but because different constraints dominate. The engineering task is not to identify a universally best deployment, but to locate the limiting constraint in the intended operating regime. In D·A·M terms, understanding these regimes turns deployment from an operational afterthought into a co-design problem in which data locality, algorithm structure, and machine constraints jointly determine what is possible.

**Learning Objectives**

- Explain how physical constraints shape deployment paradigms from cloud to TinyML
- Diagnose which term of a tier’s silicon contract limits a workload, separating iron-law limits from memory and energy feasibility
- Match workload demands to deployment budgets using lighthouse model examples
- Compare cloud, edge, mobile, and TinyML by operational constraints and quantitative trade-offs
- Apply the decision framework to select paradigms by privacy, latency, resource, and cost constraints
- Analyze hybrid patterns that combine paradigms to satisfy system constraints
- Evaluate deployment placements against data-locality deadlines, energy per inference, and lifecycle cost
