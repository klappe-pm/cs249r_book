# V1-02.14 Summary

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02 System Paradigms|V1-02 System Paradigms]]

^sec-ml-systems-summary-d75c

The same model demands different engineering on a phone and in a data center because each deployment target offers the model different hardware terms. The iron law of ML systems (${T}= \frac{{D_{\text{vol}}}}{{\text{BW}}} + \frac{{O}}{{R_{\text{peak}}} \cdot {\eta_{\text{hw}}}} + {L_{\text{lat}}}$) unifies these physical limits into a single execution model. Propagation delay contributes fixed latency (${L_{\text{lat}}}$), the memory wall bounds data movement (${D_{\text{vol}}}/{\text{BW}}$), and thermal power budgets cap sustained compute.

By applying the bottleneck principle to workload archetypes, engineers determine whether a model’s latency is dominated by compute efficiency, memory bandwidth, or network transit before committing to single-node or hybrid architectures. The quantitative trade-offs summarized in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.10 Choosing a Deployment Paradigm#^tbl-big-vs-tiny-d3f9a072|table 9]] and the tiered screening sequence formalized in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.10 Choosing a Deployment Paradigm#^fig-mlsys-playbook-flowchart|figure 11]] establish the physical baselines for later decisions in model compression, data pipeline design, and high-performance serving.

**Key Takeaways: Same model, different engineering**

- **Physical constraints define feasibility**: Propagation delay sets a lower bound on remote response time (about 36 ms for a cross-country round trip). Power and memory budgets limit what a platform can sustain, so a feasible deployment must meet the task’s deadline within the target platform’s resource limits.
- **Identify bottlenecks before optimizing**: The same model can be compute bound in batched training yet bandwidth-bound at batch-1 inference. The iron law and bottleneck principle pinpoint which constraint dominates; shortening a nonlimiting stage may reduce request latency without increasing steady-state throughput.
- **Match workload demands to deployment budgets**: A compute-bound workload such as large-scale image-model training often needs cloud-scale resources; a power-bound workload such as keyword spotting benefits from microcontroller efficiency. Engineers must identify the limiting constraint under the intended execution conditions rather than choose a deployment from the model name alone.
- **Screen feasibility before comparing cost**: Privacy, latency, and resource checks remove infeasible tiers before cost is compared. Among the survivors, utilization, provisioning, and fleet maintenance, not resource savings alone, decide which architecture is cheaper.
- **Hybrid architectures divide work by constraint**: The voice-assistant example assigns wake-word detection to TinyML, speech-to-text to mobile, and language understanding to cloud. Train-serve split, hierarchical processing, and progressive deployment provide three patterns for combining tiers; the choice depends on each stage’s requirements.
- **Deployment begins a feedback loop**: Live data can diverge from training conditions while code and weights stay fixed, so monitoring and bounded operational exposure are part of the system architecture.

^callout-takeaways--2-14-49ac251e

Deployment paradigms are not product categories. They are operating regimes shaped by physical and operational constraints, and selecting one changes which constraint is most likely to limit the system. Data-center training can push against peak compute (${O}/{R_{\text{peak}}}$). Mobile inference is bounded by energy, with the battery setting the budget and the chassis capping the rate at which it can be spent. Remote real-time inference can be constrained by propagation delay (${L_{\text{lat}}}$). Systems engineering begins by measuring that limiting constraint, and the measurement is worth most when it comes early. Optimizing model architecture or software runtimes without first identifying the limiting constraint produces systems that fail when they meet real operating conditions.

**What’s Next: From theory to process**

The decision framework in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.10 Choosing a Deployment Paradigm#^sec-ml-systems-decision-framework-241f|section 2.9.2]] identifies where an ML system can execute, but the team must use those constraints throughout development. Knowing where a model can run helps little if the team learns it too late, because constraints discovered at launch invalidate months of earlier decisions. **[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle#^sec-ml-workflow|ML Lifecycle]]** traces exactly that failure, a deployment memory budget discovered only after five months of work, and shows how such constraints must travel backward to the first design meeting. It introduces the machine learning lifecycle, the iterative engineering process that carries a system from problem definition through deployment, monitoring, and maintenance, and the workflow that carries constraints around it.
