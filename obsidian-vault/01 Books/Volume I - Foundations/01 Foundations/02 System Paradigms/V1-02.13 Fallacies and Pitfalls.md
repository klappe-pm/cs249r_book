# V1-02.13 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02 System Paradigms|V1-02 System Paradigms]]

^sec-ml-systems-fallacies-pitfalls-3dfe

Most deployment misconceptions share one root. Each treats a physical envelope as a software detail that a later optimization can fix. Data movement, thermal dissipation, and hardware balance can invalidate otherwise reasonable optimization choices, and each fallacy and pitfall below records a system mismatched to its operating envelope.

**Fallacy**: *One deployment paradigm solves all ML problems.*

No single paradigm satisfies every physical constraint. A real-time robotics system requiring sub-10 ms response cannot use a remote cloud path whose end-to-end network round-trip exceeds that budget. A billion-parameter language model cannot reside within the few hundred kilobytes of SRAM on a microcontroller regardless of compression. Robust architectures frequently combine paradigms, using cloud resources for distributed training and burst capacity while executing localized inference or sensor preprocessing on client devices.

A related misconception assumes that moving computation closer to the user always reduces latency. It overlooks the execution delay introduced by thermally constrained or lower-bandwidth edge processors, a trade-off exposed when end-to-end latency is separated from model execution time, as in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.04 Benchmarking Granularity#^sec-benchmarking-endtoend-vs-component-latency-9952|End-to-end vs. component latency]]**.

**Pitfall**: *Relying on model optimization to overcome mobile power and thermal limits.*

Compression techniques reduce power but cannot remove the thermal ceiling. Consider a smartphone equipped with a 15 Wh battery. A light inference workload drawing 1 W runs for $\frac{15\text{ Wh}}{1\text{ W}}$ = 15 h, but an intensive workload drawing 5 W in this illustrative heavy-load scenario depletes that same battery in $\frac{15\text{ Wh}}{5\text{ W}}$ = 3 h.

Sustained execution at 5 W also exceeds the approximately 3 W that a smartphone chassis can dissipate passively, so the device throttles as in napkin math [2.9](https://mlsysbook.ai/vol1/02_system_paradigms/02_system_paradigms.html#nbk-ml-systems-thermal-wall). Quantizing FP32 parameters to INT8 shrinks the memory footprint by an illustrative 4×, but switching energy and static leakage (the power a chip draws even while idle) do not fall in proportion. A continuous pipeline above the thermal envelope therefore still requires a lower duty cycle, a restructured architecture, or dedicated accelerator silicon.

**Fallacy**: *TinyML represents scaled-down mobile ML.*

The boundary between TinyML and mobile deployment changes the execution environment: much smaller working-memory and energy budgets require different scheduling and runtime choices. As [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.09 TinyML Ubiquitous Sensing#^sec-ml-systems-tinyml-advantages-operational-tradeoffs-2d40|section 2.8.1]] establishes, microcontrollers provide $10^5$ to $10^6$ bytes of on-chip RAM compared to mobile platforms with 8–16 GB of LPDDR DRAM, a 10,000× capacity disparity that dictates memory residency. Where mobile systems execute models with tens of millions of parameters, many TinyML architectures use tens or hundreds of thousands of parameters, with low-precision arithmetic and layer scheduling that holds fewer intermediate results at once. Operating power budgets show an even sharper discontinuity: mobile inference draws 3–5 W, whereas TinyML targets an average power of \< 1 mW to operate within energy-harvesting envelopes. Teams that apply mobile optimization techniques directly to TinyML environments discover that quantizing a trained model from FP32 to INT8 is insufficient on the smallest microcontrollers. There, total working memory must fit inside as little as 64 KB of SRAM, which forces complete algorithmic redesign.

**Pitfall**: *Minimizing computational resources minimizes total cost.*

Shaving dollars off per-inference compute in isolation often drives up operating bills and slows down shipping. As the decision framework in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.10 Choosing a Deployment Paradigm#^sec-ml-systems-decision-framework-241f|section 2.9.2]] emphasizes, architectural selection requires evaluating TCO across the entire system lifecycle rather than raw server costs. In this scenario, a cloud inference service costing \$2,000/month in compute appears expensive compared to \$500/month in amortized edge hardware. However, a distributed edge fleet introduces recurring operational expenses: network engineering (\$3,000/month), field hardware maintenance (\$500/month), and fleet reliability engineering (\$2,000/month). Together with hardware amortization, these bring the listed edge budget to \$6,000/month, erasing the apparent hardware-only saving. Unlike the single-server comparison in napkin math [2.3](https://mlsysbook.ai/vol1/02_system_paradigms/02_system_paradigms.html#nbk-ml-systems-cloud-vs-edge-tco), this scenario operates a distributed fleet, where network, maintenance, and reliability labor scale with the number of sites. Operating labor, not hardware, dominates the edge budget. The cloud figure counts compute alone, so the comparison shows where edge money goes rather than which tier costs less in total. If a cloud-managed service reaches production in two months while custom edge infrastructure requires six, the four-month delay also carries an opportunity cost. Sound systems engineering balances compute efficiency against developer velocity, fleet manageability, and operational maintenance.

**Fallacy**: *Model optimization translates linearly to system speedup.*

Amdahl’s law[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn34|³⁴]] caps end-to-end speedup by the share of time an optimization leaves untouched, the limit that the introduction’s fallacies already showed for preprocessing (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.12 Fallacies and Pitfalls#^sec-introduction-fallacies-pitfalls-230d|Fallacies and Pitfalls]]**); **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** states the general bound as **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^eq-amdahl|equation 11.1]]**. Pipelining can overlap stages to raise steady-state throughput ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^sec-ml-systems-bottleneck-principle-3514|section 2.3.1]]), but the stages of an interactive capture path run in strict serial order, so the cap applies in full. A smartphone camera spends 60 ms of its 200 ms capture path on ML scene classification, which runs between 100 ms of image signal processing and 40 ms of tone mapping and HDR merge. A 10× faster model (6 ms of classification) shortens the path only to 146 ms, an end-to-end gain of 1.37×. Even an infinitely fast model cannot exceed 1.43× while the other 70 percent of the path is unchanged. Optimizing an ML system requires profiling the full execution graph; accelerating an isolated stage yields diminishing returns once that stage ceases to be the critical-path bottleneck.

**Pitfall**: *Assuming more training data always improves deployed model performance.*

Three constraints bound the returns of data scaling. First, algorithmic capacity ($\text{A}$) saturates: when a model’s parameter budget is fixed, additional training data cannot squeeze more patterns into a model whose layers are too small to represent them. Second, data quality ($\text{D}$) matters more than raw volume: mislabeled examples, uncalibrated sensors, and spurious shortcuts teach the model wrong patterns, so scaling up a noisy dataset only teaches the model its errors with higher confidence. Third, the deployment tier decides which data counts as in-domain. A microcontroller’s microphone, a phone camera, and a data-center log stream capture inputs with different noise, resolution, and sampling, so a large corpus gathered under one tier’s conditions can match another tier’s inputs poorly. High-fidelity data collected under the target tier’s own sensing conditions often yields higher serving accuracy than a much larger out-of-domain corpus.

**Fallacy**: *One model binary can serve every edge hardware target efficiently.*

Teams frequently compile a single model artifact and deploy it uniformly across diverse devices, treating deployment as a packaging step rather than a hardware co-design problem. In practice, hardware-specific compilation and kernel lowering (translating each operation into code tuned for the target’s instruction set and memory layout) capture critical efficiencies that generic binaries forfeit. For example, quantized INT8 operations on a dedicated neural processing unit (NPU) achieve substantially higher throughput per watt than the identical model on a general-purpose CPU. Kernel fusion also keeps intermediate activation tensors in on-chip SRAM rather than evicting them to energy-expensive off-chip DRAM. Hardware targets differ in kind, as the data-center accelerator and mobile NPU of [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^sec-ml-systems-system-balance-hardware-96ab|section 2.4]] already showed, and a binary compiled for a general-purpose mobile CPU does not use the specialized matrix engines of an embedded NPU. A portable model artifact can run through multiple backends, but portability alone does not establish efficiency. Production deployment requires profiling the target runtime and hardware, then selecting compilation, kernels, and memory layouts that meet its resource and thermal limits.

**Self-Check: Question**

1.  A smartphone camera pipeline takes 200 ms total: 100 ms for the image signal processor (ISP), 60 ms for ML scene classification, and 40 ms for postprocessing. If an engineering team optimizes the ML model to run $10\times$ faster (reducing ML time from 60 ms to 6 ms), what is the overall system-level speedup?

    1.  $10.00\times$ speedup
    2.  $1.37\times$ speedup
    3.  $5.50\times$ speedup
    4.  $0.73\times$ speedup (system becomes slower)

2.  Why does deploying a single generic FP32 model binary across diverse edge devices (e.g., Arm CPU, Apple Neural Engine, and Google Coral Edge TPU) result in suboptimal efficiency compared to per-target compilation?

    1.  Generic model binaries violate cryptographic signatures required by PCI Express buses.
    2.  Floating-point operations are mathematically undefined on mobile CPUs.
    3.  Generic binaries cannot exploit hardware-specific kernel fusion, dedicated fixed-point INT8 matrix datapaths, or accelerator-specific on-chip SRAM memory tiling.
    4.  The operating system automatically deletes untuned model weights to prevent memory fragmentation.

3.  Why does choosing an on-premises edge deployment solely because its hardware amortizes to a lower monthly compute cost than a cloud VM often result in a higher Total Cost of Ownership (TCO)?

4.  Increasing the quantity of training data is guaranteed to continuously improve deployed model performance regardless of model capacity, label noise, or domain distribution shift.
