# V1-02.05 System Balance and Hardware

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02 System Paradigms|V1-02 System Paradigms]]

^sec-ml-systems-system-balance-hardware-96ab

A model that clears its latency budget on paper can still stall on a real host if transfers over PCIe, the expansion bus that connects the CPU to the GPU, choke the pipeline or if single-sample inference leaves the accelerator’s matrix units starved for bytes. Checking the iron law and workload archetypes against real hardware means tracing a request through every layer of one host, from the application’s latency or throughput target down to the silicon that must meet it.

### Inside One Machine: the Single-Node Stack

^sec-ml-systems-architectural-anchor

When an application issues an inference request or a training step on a single machine, that work travels down a four-layer **single-node stack**, which refines the machine side of the D·A·M taxonomy for one host. At the top of the stack, the application brings the data and algorithmic requirements into a training-throughput or inference-latency target, and the ML framework below it translates model code into executable operations that aim to meet that target. Those operations then pass through the operating system, drivers, and runtime, which coordinate resources and move tensors (multidimensional arrays of numbers) between host memory and accelerator memory. At the bottom is the hardware itself, where memory capacity, memory bandwidth, the links between processors, and compute throughput set the physical limits, with the memory wall as a recurring constraint.

↪ How an ML framework turns model code into executed operations, eagerly or through a captured graph, is developed in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-problem-e1e1|Execution: From Graphs to Kernels]]**.

The hardware layer fixes the terms on offer to any model: a memory bandwidth $({\text{BW}})$, a peak compute rate $({R_{\text{peak}}})$, and an execution overhead $({L_{\text{lat}}})$. These are the three terms of the silicon contract that opened this chapter. The hardware sets these terms, and the model decides how much work it does per byte it moves, which in turn decides which of these limits it reaches first. Deployment analysis asks which term a given platform makes scarce; how a model architecture chooses which resource to saturate belongs to **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures#^sec-network-architectures|Network Architectures]]**.

↩︎ The iron law of ML systems and its decomposition of end-to-end latency are established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**.

### Matching Workloads to Hardware

^sec-ml-systems-matching-workloads-hardware-bf91

Testing whether a host’s silicon contract can satisfy a workload proceeds in two steps, from coarse to fine, before any kernel-level profiling begins. The coarse test asks whether an operation can fit inside the latency budget at all. The fine test asks which hardware resource limits the operations that do fit, and its answer depends on system balance, the ratio of a platform’s peak compute rate to its memory bandwidth.

Operation latencies supply the coarse test, and they turn latency-vs-throughput trade-offs into decisions through concrete numbers. They span roughly eight orders of magnitude, from about a nanosecond for an on-chip cache hit or a single accelerator multiply, through milliseconds for one mobile vision inference, to tens or hundreds of milliseconds for a cross-region network call. **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-numbers-know-b531|Numbers to Know]]** collects the memory-hierarchy and network round-trip anchors along with illustrative application latency budgets. The span matters because of one strict rule: an operation with latency $> {T_{\text{deadline}}}$ *cannot* appear on the critical path of a system whose latency budget is ${T_{\text{deadline}}}$ ms.[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn8|⁸]]

![[90 Assets/Volume I/Shared Figures/Vol1 Benchmarking Margin 002 14cb326b13.svg]]

*A roofline silhouette: a blue memory-bound slope rising to a dashed ridge line, then a flat orange compute-bound ceiling, with a batch-1 workload dot on the memory-bound slope, left of the ridge, and a gray arrow to a B=32 dot on the compute-bound ceiling, right of the ridge.*

*In this example, batching moves the workload from the memory-bound side toward the compute ceiling.*

For the operations that pass the latency test, system balance decides which resource limits them. Roofline analysis classifies bottlenecks by comparing a workload’s arithmetic intensity, the operations it performs per byte moved (FLOP/byte), against the platform’s system balance $({R_{\text{peak}}} / {\text{BW}})$, which the roofline literature calls the ridge point ([[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.16 Source References#^ref-williams2009|Williams et al. 2009]]) and whose comparison the introduction made in words with the iron law (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**). The same ResNet-50 model can shift from compute-bound training behavior at high batch sizes to more memory-sensitive single-image inference at batch=1, and deployment paradigm selection must account for this shift. The framing is informal here; **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]** develops the model and the ridge point that separates the bandwidth-bound regime from the compute-bound one, with a worked derivation collected for reference in **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-roofline-model-2529|The Roofline model]]**.

ResNet-50 inference on a high-end data center accelerator and on a mobile neural processing unit (NPU)[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn9|⁹]] puts numbers on this analysis. The hardware figures are point-in-time anchors; the reasoning rests on compute rate, memory bandwidth, and batch size, which outlast any one product.

**Napkin Math 2.1: ResNet-50 on cloud vs. mobile**

**Problem**: Is ResNet-50 inference compute-bound or bandwidth-bound on (a) a high-end data center accelerator (an NVIDIA A100) and (b) a flagship mobile NPU?

**Given** (from lighthouse models):

- ResNet-50: 8.2 GFLOP per inference, 25.6 million parameters (102.2 MB FP32, 51.1 MB FP16)

**Analysis**:

**(a) Cloud data-center accelerator (batch=1, FP16)**

The analytical model assumes 56.2 MB moved per inference, including weights and activation traffic. This is a modeled transfer volume, not the stored parameter footprint; reuse and runtime choices can change it.

- Peak compute: 312 TFLOP/s (FP16)
- Memory bandwidth: 2.04 TB/s
- Compute time: ${T_{\text{compute}}}$ = $\frac{8.20 \times 10^{9}}{3.12 \times 10^{14}}$ = 0.026 ms
- Memory time (weights plus activations): ${T_{\text{memory}}}$ = $\frac{5.62 \times 10^{7}}{2.04 \times 10^{12}}$ = 0.028 ms
- **Result**: Bottleneck = Memory bandwidth, so the workload is bandwidth-bound (memory transfer is 1.0× slower than compute)
- **Ridge point**: ${R_{\text{peak}}}/{\text{BW}}$ = 312 TFLOP/s ÷ 2.04 TB/s ≈ 153 FLOP/byte.
- **Analysis**: Arithmetic intensity = $\frac{8.20 \times 10^{9}}{5.62 \times 10^{7}}$ = 146 FLOP/byte, just below the ridge point, so the workload is bandwidth-bound; above the ridge it would be compute bound. For single-image inference, the low batch size yields limited reuse, explaining why even high-throughput accelerators can be bandwidth-bound at batch = 1. Both times use peak rates (efficiency ${\eta_{\text{hw}}} = 1$ and full bandwidth), so they are lower bounds. Because this workload sits close to the ridge, the efficiencies a real kernel achieves decide which term dominates in practice.

**(b) Mobile: Flagship NPU (batch=1, INT8)**

At INT8, the analytical model assumes 28.1 MB moved per inference, including weights and activation traffic. The INT8 weight footprint below is only one component of that transfer volume.

- Peak compute: ~35 TOPS (INT8; TOPS counts trillions of operations per second), representative of modern mobile NPUs
- Memory bandwidth: ~51.2 GB/s (LPDDR5)
- Model size: 25.6 MB (INT8 quantized)
- Compute time: ${T_{\text{compute}}}$ = $\frac{8.20 \times 10^{9} \text{ INT8 ops}}{3.50 \times 10^{13} \text{ INT8 ops/s}}$ = 0.23 ms
- Memory time (weights plus activations): ${T_{\text{memory}}}$ = $\frac{2.81 \times 10^{7}}{5.12 \times 10^{10}}$ = 0.55 ms
- **Result**: Bottleneck = Memory bandwidth, so the workload is bandwidth-bound (memory transfer is 2.3× slower than compute)

**Systems insight**: Under these peak-rate assumptions, both platforms are bandwidth-bound for single-image inference. The A100’s faster memory bandwidth (2.04 TB/s vs. 51.2 GB/s = 39.8×) gives roughly 19.9× lower modeled memory-transfer time under the stated FP16 and INT8 traffic assumptions; this ratio is not a measured end-to-end inference speedup. Byte-reduction and lower-precision techniques can therefore beat buying more peak FLOP/s for deployment.

ResNet-50 becomes compute bound when batching and data reuse raise computation per byte moved above the system balance (the ridge point), ${I} > {R_{\text{peak}}}/{\text{BW}}$, where ${I} = {O}/{D_{\text{vol}}}$: a batch reuses each loaded weight for all ${B}$ of its inputs, so computation time eventually overtakes memory-transfer time. The crossover is architecture- and implementation-dependent because activation traffic, input/output movement, cache reuse, and runtime execution details all change the effective bytes moved per inference.

The batch-size gap between batched training and single-image inference is one instance of a broader change between execution phases, in which physical constraints reconfigure all three D·A·M axes at once. Training updates model weights from batches of examples, so the weights are mutable; serving applies fixed, immutable weights to new inputs. [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^tbl-dam-phase|Table 3]] contrasts typical training and latency-sensitive serving demands; cloud serving can also batch requests for throughput.

| **Component** | **Training (Mutable)**                                      | **Inference (Immutable)**                               |
|:--------------|:------------------------------------------------------------|:--------------------------------------------------------|
| **Data**      | Massive throughput: large batches, shuffling, augmentation  | Low latency: single samples, freshness, speed           |
| **Algorithm** | Learning phase: update model parameters from examples       | Prediction phase: apply fixed weights to new inputs     |
| **Machine**   | Throughput-optimized: high-bandwidth clusters, large memory | Latency-optimized: edge devices, inference accelerators |

Table 3: **D·A·M $\times$ Phase**: The same model imposes starkly different demands on Data, Algorithm, and Machine depending on whether the system is training or serving. When bottlenecks shift unexpectedly, check which phase is currently being optimized.

^tbl-dam-phase

Extending the cloud-versus-mobile comparison of napkin math [2.1](https://mlsysbook.ai/vol1/02_system_paradigms/02_system_paradigms.html#nbk-ml-systems-resnet-50-cloud-vs-mobile) across all four deployment tiers grounds the conceptual regimes of [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.02 Four Deployment Regimes Across Nine Orders of Magnitude#^tbl-deployment-paradigms-overview|table 1]] in concrete hardware. [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^tbl-representative-systems|Table 4]] places one real platform in each paradigm and pairs it with the per-device envelope that marks the tier.[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn10|¹⁰]] The example-platform and power columns describe complete systems, including a cloud pod.

The tier compute and tier memory bandwidth columns describe a single device instead. Each of their cells gives a tier threshold, the peak rate that characterizes one device of that tier, and each compute threshold is quoted at the numerical precision that tier’s chips target. Because those precisions differ, the compute column does not rank the tiers. The cloud entry counts 16-bit operations on one data-center accelerator, whereas the edge entry counts far lower-precision operations, which a high-end workstation chip executes much faster. Compared on the same 16-bit operations, one TPU v4 chip delivers 2.2× the dense 16-bit throughput and 4.4× the memory bandwidth of the DGX Spark. The marking on each cell says which kind of threshold it is: a floor (≥), a ceiling (≤), an approximate value (~), or a range across representative devices.

Compared as complete systems rather than as equivalent individual chips, the four platforms span enormous ranges. Memory drops from 128 TB (cloud) to 512 KB (TinyML), a 268 million-fold reduction. Power runs from about 3 MW for the cloud pod to the TinyML tier’s average-power target of \< 1 mW. Hardware cost spans six orders of magnitude, from multimillion-dollar clusters to \$10 microcontrollers. Together with facility overheads such as power usage effectiveness (PUE),[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.17 Footnotes#^fn11|¹¹]] these spreads decide which paradigm can serve a workload economically, and they explain why model compression becomes essential as the budget tightens.

The hardware spectrum turns the bottleneck diagnosis into a fit test, in which each workload must be matched to the tier whose compute, bandwidth, power, and cost envelope it can satisfy.

**Systems Perspective 2.1: System balance across paradigms**

The last column of [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^tbl-representative-systems|table 4]] reads each tier through the pipelined bound in [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^eq-bottleneck|equation 5]]. For cloud and edge the limiting constraint is a term of that bound, whereas for mobile and TinyML it is a limit the time equation leaves out, and in every tier the dominant constraint sets the optimization strategy. Compute-bound cloud training rewards higher accelerator utilization and larger batches. Bandwidth-bound large language model (LLM) decode (token-by-token generation) and bandwidth-bound edge inference reward moving fewer bytes (through smaller models, lower precision, and more reuse per loaded weight), so a faster accelerator helps them little.

Moving to battery-powered devices adds an implicit energy term, whose battery and thermal limits [[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.08 Mobile ML Offline Intelligence#^sec-ml-systems-mobile-ml-personal-offline-intelligence-0983|section 2.7]] develops. Mobile systems integrate power over time under a tight thermal cap, which makes lower precision and duty cycling (running the model only part of the time) pay off in both battery life and sustained speed. TinyML faces a strict memory precondition before any time or energy term applies, because weights and code must fit in flash and activations and runtime state must fit in SRAM through compact models and low-precision arithmetic. **[[05 Reference/Volume I - Foundations/V1 The D·A·M Taxonomy#^sec-appdx-dam-taxonomy-bottleneck-diagnostic-3fc9|Acting on the limiting term]]** maps each dominant term to the optimizations that work and the ones that are wasted, turning this diagnosis into an action plan.

Each paradigm is therefore an operating envelope with different resource budgets, and moving from warehouse data centers down to microcontrollers traces a physical gradient that trades raw compute throughput for energy and memory efficiency. The four sections that follow walk that gradient one tier at a time. Each asks the same four questions, which the constraint map in each section draws as four branches: which constraint limits the tier, how the system responds, where the paradigm fails, and which workloads fit. Because that structure is shared, each section concentrates on what is distinctive about its tier and on the one or two calculations that decide whether a workload belongs there.

**Self-Check: Question**

1.  Why is single-image (batch=1) ResNet-50 inference memory-bound on both a high-end cloud accelerator (NVIDIA A100) and a mobile NPU (iPhone 15 Pro)?

    1.  ResNet-50 contains dynamic control flow that causes branching stalls on SIMD execution units.
    2.  Both platforms lack matrix multiplication coprocessors, forcing scalar CPU execution.
    3.  At batch=1, model weights must be loaded from memory once per single image without weight reuse across batch items, keeping arithmetic intensity below each platform’s hardware balance point ($R_{\text{peak}}/\text{BW}$).
    4.  The activations at batch=1 exceed the total high-bandwidth memory (HBM) and SRAM capacities of both devices.

2.  Why does a convolutional neural network (e.g., ResNet-50) shift from a compute-bound regime during cloud training to a memory-bound regime during single-sample ($\text{batch}=1$) edge inference?

3.  An ML service SLA guarantees a total end-to-end response time of 100 ms. The pipeline involves client preprocessing, a cross-region network RPC, model inference, and postprocessing. According to critical path latency principles, why will this system fail if a cross-region network call taking 120 ms is placed on the synchronous critical path?

    1.  The ML framework compiler will refuse to lower the graph if network RPC operations are detected.
    2.  Cross-region RPCs corrupt the numerical precision of FP16 tensors during serialization.
    3.  A cross-region network call reduces the accelerator compute throughput ($R_{\text{peak}}$) by half.
    4.  The critical path is the longest sequential chain of dependent operations; any single stage exceeding 100 ms guarantees the end-to-end SLA will be breached regardless of how fast all other stages execute.

4.  What is the hardware balance point (or roofline ridge point) of an accelerator, and what does it tell an ML systems engineer about whether a workload will be compute-bound or memory-bound?

5.  For batch-1 LLM decode in the cloud and for most edge inference, the iron-law term that dominates is memory \_\_\_\_ rather than peak compute, so a faster accelerator alone yields little speedup.

6.  Order the four architectural layers of the single-node stack from the top-level mission goal down to the physical execution engine:

<!-- -->

1.  Operating system (resource orchestration and host-accelerator memory transfers)
2.  ML framework (operator graph lowering and execution planning)
3.  Hardware and silicon contract (peak compute throughput, memory bandwidth, HBM/SRAM)
4.  Application layer (training throughput target or inference latency SLA)
