# V1-03.13 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle|V1-03 ML Lifecycle]]

^sec-ml-workflow-fallacies-pitfalls-4d91

Treating ML as ordinary software produces predictable failures, each of which traces back to a section of this chapter. The misconceptions below recur when teams manage statistical models with assumptions inherited from deterministic application code.

**Fallacy**: *ML development can follow traditional software workflows without modification.*

Software practices such as version control, unit testing, and iterative delivery remain necessary. Machine learning systems also derive behavior from data, so those practices must cover datasets, learned artifacts, and statistical performance evidence ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^tbl-sw-ml-cycles|table 1]]). In an ML workflow, problem definitions evolve as exploratory training reveals distribution gaps, class imbalances, or infeasible accuracy-latency trade-offs, and practitioners name data preparation as a major time sink ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.04 Where the Hours Go Quantifying the ML Lifecycle#^sec-ml-workflow-quantifying-ml-lifecycle-bd69|section 3.3]]).

**Pitfall**: *Treating data preparation as a one-time preprocessing step.*

Teams often treat data cleaning and feature engineering as a static milestone to clear before training begins. In production, incoming data distributions evolve continuously as user behavior shifts, sensors degrade, and upstream schemas change. The dual-pipeline lifecycle of [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^fig-ml-lifecycle|figure 2]] reflects this operational reality, with an upper data pipeline and a lower model pipeline that execute concurrently and feed back into each other. Early data preparation decisions cascade directly through training and deployment ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.07 Stage 2 Data Collection and Preparation#^sec-ml-workflow-data-collection-preparation-stage-ae99|section 3.6]]). When data preparation is static, silent distribution shifts and training-serving feature skew bypass code-level tests, degrading inference accuracy long before raising an operational alert. Continuous data validation pipelines with automated schema checking and distribution monitoring are necessary to catch data drift at ingestion rather than after silent model failure in production.

**Fallacy**: *Passing model evaluation means the system is ready for deployment.*

Model-only offline evaluation measures statistical loss on curated validation sets and leaves operational serving dynamics untested. Across the dual pipelines mapped in [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^fig-ml-lifecycle|figure 2]], an accuracy-only evaluation tests the candidate model without establishing serving integration, real-time input delivery, or operational monitoring. The diabetic retinopathy case ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^sec-ml-workflow-case-study-diabetic-retinopathy-screening-7d71|section 3.1.2]]) shows the disconnect, since a model with specialist-level accuracy on curated images rejected 21 percent of clinic images as ungradable and struggled with variable camera lighting, technician workflow interruptions, and intermittent network connectivity. Production readiness demands system-level verification, including tail-latency budgets under concurrency, feature pipeline consistency, and graceful degradation under hardware faults.

**Pitfall**: *Scaling data collection before checking marginal model value.*

Expanding dataset size is often assumed to be a universally profitable investment for boosting accuracy. Additional examples incur storage, ingestion, and labeling costs, but their learning value depends on which gaps they fill. Once a region of the input distribution is well covered, returns there diminish, and more examples of already well-covered cases may contribute little, while targeted collection can expose a failure that aggregate accuracy conceals. The upstream feedback loops in [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^fig-ml-lifecycle|figure 2]] route data fixes from curation back to collection before samples enter training, allowing observed errors and coverage gaps to guide acquisition. Because data quality decisions cascade through all downstream pipeline stages ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.07 Stage 2 Data Collection and Preparation#^sec-ml-workflow-data-collection-preparation-stage-ae99|section 3.6]]), teams must measure the marginal gain in the required task and subgroup metrics against the cost of collecting and processing additional data.

**Fallacy**: *Skipping validation stages accelerates delivery.*

Compressing or bypassing justified validation stages transfers unresolved risk to production traffic. Multi-stage validation ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.09 Stage 4 Evaluation and Validation#^sec-ml-workflow-evaluation-validation-stage-b47d|section 3.8]]) supplies complementary evidence across increasingly realistic execution environments, and no stage substitutes for another or for independent offline evaluation. A release plan should state the evidence required, the exposure permitted, and the conditions for stopping or reversing a rollout. A validation stage may be removed only when its evidence obligation is met another way.

**Pitfall**: *Deferring deployment paradigm selection until after model development.*

Teams often assume deployment targets can be selected after optimizing model accuracy. In practice, the deployment paradigm (Cloud, Edge, Mobile, or TinyML) is a primary constraint that shapes every preceding lifecycle stage ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.05 Stage Ownership and Hand-Offs#^tbl-stage-interface|table 2]]). The day-153 failure is the canonical case, in which a model needing 4 GB reached deployment (stage 5) before anyone checked that the clinic device reserves about 500 MB for it. Deployment hardware dictates which models are physically realizable, not merely where they execute.
