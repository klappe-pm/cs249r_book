# V1-03.08 Stage 3 Model Development and Training

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle|V1-03 ML Lifecycle]]

^sec-ml-workflow-model-development-training-stage-d901

The DR team has on the order of $10^5$ labeled retinal images, the scale of the 128,000-image dataset in Google’s study, along with a validated preprocessing pipeline and a target: more than 90 percent sensitivity on edge hardware, returned within seconds of capture. The question is no longer *what data* to collect but *what model* to build, and that question has no answer independent of the deployment constraints already established.

In iron law terms, this stage defines the operations $({O})$ term, because architectural choices set the computational floor that hardware must sustain. Training is where that cost is first paid. The model learns by making repeated passes over the labeled images, adjusting its parameters slightly after each group of examples, and a single training run can occupy an accelerator for hours or weeks. Every idea the team wants to test costs at least one such run, so training systems must coordinate data ingestion, accelerator execution, and the search over training settings[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn12|¹²]] without stalling execution pipelines or exhausting the compute budget before reaching clinical accuracy.

Training a vision backbone from random weights on finite medical data rarely reaches specialist-level accuracy within a practical compute budget. **Transfer learning**[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn13|¹³]] addresses this constraint by starting from a backbone pretrained on a large general vision corpus, such as the ImageNet Large Scale Visual Recognition Challenge (ILSVRC) 2012 training subset of 1.3 million labeled images ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-russakovsky2015|Russakovsky et al. 2015]]), and adapting it to the retinal task. Starting from those learned visual features can make training on the retinal images reach good accuracy in fewer training steps and generalize better than starting from random weights. The size of the benefit depends on how closely the source images resemble the target images, on which layers are reused, and on how optimization proceeds after the transfer ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-yosinski2014transferable|Yosinski et al. 2014]]).

In Google’s controlled validation study ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-gulshan2016|Gulshan et al. 2016]]), transfer learning and a labeled dataset of 128,000 images produced an AUC[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn14|¹⁴]] of 0.99, with sensitivity of 97.5 percent and specificity of 93.4 percent at one operating point. The result demonstrates the potential of pretraining on general images followed by further training on retinal images under the study conditions; it does not by itself establish deployment performance. Reaching a result of this kind takes repeated training runs over the full labeled dataset, and the arithmetic cost of each run on the available hardware sets how many runs a team can afford, which is the iteration tax again in another form.

Achieving high statistical accuracy on benchmark data is only the first hurdle, because edge deployment requires models to fit within strict memory allocations, execute within tight latency envelopes, and stay within thermal limits. **Ensemble learning** sets maximum accuracy against fit to the deployment target most sharply. Combining predictions from multiple models routinely delivers top benchmark accuracy, yet inference compute, parameter storage, and memory traffic scale directly with ensemble size. Serial execution increases latency, while parallel execution demands additional hardware concurrency, so no fixed latency multiplier follows from ensemble size alone.

The historic Netflix Prize demonstrated how ensemble complexity can block deployment. The winning solution delivered the highest predictive accuracy, yet Netflix never deployed it because the operational costs of maintaining and serving the ensemble exceeded the marginal business value ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-johnston2012netflixprize|Johnston 2012]]). Even an ensemble of lightweight models multiplies orchestration complexity, working memory, and operational monitoring, so every architectural decision creates downstream systems ripples that accumulate at the physical deployment boundary.

### Accuracy Vs. Efficiency

^sec-ml-workflow-balancing-performance-deployment-constraints-1e8e

Fitting that deployment boundary without sacrificing clinical safety is the core trade-off of model development. Because missing an active DR case risks permanent vision loss whereas misclassifying a healthy eye generates an unnecessary referral, training must optimize specialized clinical objectives[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn15|¹⁵]] rather than generic average error, maintaining $>90$ percent sensitivity and $>80$ percent specificity across patient demographics, illumination conditions, and fundus camera models.

↪ The probability outputs and cross-entropy losses that standard classifiers optimize are developed in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-crossentropy-classification-loss-functions-7def|Cross-entropy and classification loss functions]]**.

At the same time, the architecture that clears those clinical thresholds must execute within the physical deployment envelope. In this scenario, running the model must remain strictly within the 500 MB memory reservation on the clinic’s shared 4–8 GB edge device. That budget must accommodate the static weight parameters alongside input buffers, activations, and runtime execution overhead. Simultaneously, the accelerator must operate within the Orin Nano-class power envelope of 7–15 W and return each prediction within seconds.

Balancing those memory, power, and latency pressures requires navigating the trade-offs of the iron law. For one inference, the team must shrink the bytes moved $({D_{\text{vol}}})$, which include the model’s weights as well as the input image, and the arithmetic operations $({O})$. Two common levers are storing each weight in fewer bits and removing parts of the model that contribute little, and after each change the team must revalidate that the smaller model preserves clinical sensitivity.[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn16|¹⁶]] The accuracy in the cited study came from a larger Inception-family network (an image-classification design with far more computation per image than MobileNetV2), so whether a mobile backbone such as MobileNetV2 keeps that sensitivity is exactly what compression and validation must show. The capture resolution needed to see small hemorrhages also raises the backbone’s operation count above its figure at the default input size, so the 500 MB budget and the latency target must be checked at that resolution.

↪ Renegotiating accuracy against memory and latency envelopes through systematic pruning, quantization, and distillation is developed in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.02 Fitting the Deployment Budget#^sec-model-compression-optimization-framework-9e21|Fitting the Deployment Budget]]**.

The model that training produces is therefore a candidate, not yet the model that ships. Making it fit the clinic device is engineering work in its own right, and it acts on all three parts of the system. On the data side, training compute goes to the examples that teach the model the most (**[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09 Data Selection#^sec-data-selection|Data Selection]]**). On the algorithm side, the trained model is made smaller and cheaper to run (**[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression#^sec-model-compression|Model Compression]]**). On the machine side, its operations are mapped onto the accelerator so that the hardware’s peak rate is approached in practice (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]**). Each change is then measured against the budgets that problem definition fixed (**[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12 Benchmarking#^sec-benchmarking|Benchmarking]]**). None of these steps can be skipped by training a more accurate model, because accuracy and fit are separate properties that the workflow must establish separately.

### Constraint-Driven Development

^sec-ml-workflow-constraintdriven-development-process-cc90

An ML engineer who downsamples retinal images to standard $224 \times 224$ ImageNet resolution to save compute will erase tiny microaneurysms before the network ever sees them. Avoiding that kind of blind spot requires domain experts (ophthalmologists in the DR case) at the table from initial exploration through final optimization to identify which lesions and image-quality details matter clinically. Without that domain knowledge, a model architect can easily choose an input resolution that discards the diagnostic signal before training even begins. Working together keeps model architectures focused on clinically relevant evidence while respecting the compute limits identified during data collection.

Even after domain knowledge narrows the candidate space, each remaining model variant, training setting, and preprocessing choice adds training runs, so exhaustive experimentation quickly becomes expensive. This economic reality drives investments in scheduling runs so accelerators do not sit idle, reusing intermediate results instead of recomputing them, and stopping runs that are clearly not improving. Searching training settings systematically, with disciplined experiment design, reduces computation relative to exhaustive search.

That experimental discipline is essential because ML training is stochastic, and without controlled comparisons a team can spend its iteration budget chasing run-to-run noise. Teams therefore control variables through fixed random seeds and environment versions. They run systematic **ablation studies**[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn17|¹⁷]] to isolate component contributions, and they control for confounding factors to separate architecture effects from optimization effects, such as making sure a new backbone does not appear better only because its learning rate was tuned more carefully than the baseline’s.

Teams also test statistical significance across multiple training runs, using paired offline tests, which compare two models on the same held-out images, rather than the A/B testing[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn18|¹⁸]] reserved for comparing models on live production traffic. Without this rigor, teams cannot distinguish genuine performance improvements from statistical noise, a distinction that becomes critical when a model sits near the clinical sensitivity threshold. Because sensitivity is computed only over patients who actually have the disease, a screening test set dominated by healthy eyes can still contain too few confirmed positive cases to pin that fraction down tightly. The test set must therefore hold enough of those cases that a sensitivity above the floor stays above it after allowing for sampling uncertainty.

↪ How many test examples a measured difference needs before it can be trusted is developed in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.09 Benchmarking Best Practices#^sec-benchmarking-statistical-methodological-issues-7aa5|Statistical and methodological issues]]**.

Checking both statistical significance and edge-device fit at every milestone keeps exploration aligned with deployment goals rather than laboratory conditions, but sustaining that rigor across a growing team quickly outgrows individual scripts and notebooks.

### Prototype to Production

^sec-ml-workflow-prototype-productionscale-development-168a

A small team of data scientists can often coordinate early exploratory runs using ad hoc scripts, spreadsheets, and shared notebooks. As projects evolve from prototype to production, however, complexity grows on several fronts at once. Datasets grow, models require distributed training across accelerator clusters, and multiple engineers launch concurrent runs. Under these conditions, informal coordination rapidly becomes a development bottleneck. Without shared infrastructure, team members inadvertently train on conflicting data splits, duplicate expensive preprocessing passes across separate machines, overwrite shared model checkpoints, and struggle to reconcile divergent notebook versions. On the DR team, two engineers who split the graded images differently would each report a sensitivity the other could not reproduce. The time required to untangle conflicting artifacts and unrecorded configurations begins to dominate development.

Shared workflow platforms resolve this coordination friction by standardizing stage interfaces and centralizing resource management. Rather than relying on manual handoffs and uncoordinated scripts, a shared platform gives the whole team the same data splits and the same preprocessed data, schedules accelerators across jobs, and records which code and configuration produced each result. Operating at scale therefore requires teams to systematically preserve each experiment’s inputs, software dependencies, and execution configuration, establishing the baseline needed to verify genuine improvements.

### Reproducibility and System Artifacts

^sec-ml-workflow-reproducibility-technical-debt-4c78

Shared infrastructure accelerates experimentation only if its results can be trusted. If a candidate model beats the validation baseline by a full percentage point on Tuesday, but rerunning the same training script on Thursday falls short, the team cannot tell whether the gain was real or a fluke of thread scheduling and unrecorded library versions. **Reproducibility**, the ability to rebuild a result and bound how much it varies from run to run, is what lets a team distinguish a genuine improvement from noise. Its absence is an economic cost as well as a scientific one, because a team that cannot reproduce a result reruns experiments that may not converge to the same outcome, and each unreproducible result adds to the system’s technical debt.[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn19|¹⁹]]

↪ The technical debt that accumulates when experiments and artifacts go untracked, and the practices that contain it, are developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.03 Technical Debt#^sec-ml-operations-technical-debt-system-complexity-2762|Technical Debt]]**.

Reproducing ML results requires tracking data versions, random seeds, hardware configurations, and library versions alongside program logic, because the hardware itself introduces run-to-run variation. When parallel accelerator threads add up partial results during training, the order in which partial sums arrive can differ from run to run, and floating-point addition is non-associative ($({a}+ {b}) + {c}\neq {a}+ ({b}+ {c})$), so identical code can produce slightly different weights.

Recording a random seed alone therefore does not establish reproducibility; the execution configuration and the measured variation across repeated runs matter as well, a requirement that **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.09 Benchmarking Best Practices#^sec-benchmarking-reproducibility-standardization-7ecf|Reproducibility]]** extends to benchmark reports. Systematic **experiment tracking** records unique run identifiers and links data versions, code commits, hyperparameters, and resulting models, so a team can reconstruct what changed between two runs.

Experiment tracking needs a well-defined unit to version, and that unit is the stage’s actual deliverable. A common failure mode is treating the trained model weights as the sole output of model development. In a mature ML workflow, the deliverable is a **reproducible system artifact** whose inference package has four components:

- **Model weights**: The learned parameters.
- **Inference code**: The exact code used to run the model, including preprocessing logic.
- **Environment specification**: The complete dependency graph (for example, a container image, `requirements.txt`, and accelerator drivers) required to execute the code.
- **Configuration**: Hyperparameters and runtime settings.

Reproducing inference and rebuilding a trained candidate require different evidence. Alongside the inference package, the artifact must link to the dataset version, training-code version, preprocessing recipe, training configuration, and execution environment that produced the weights. Under the data-as-code principle ([[01 Books/Volume I - Foundations/01 Foundations/V1 Foundation Principles#^pri-data-as-code|1]]), which treats training data as the system’s source code, a changed training set changes learned behavior as surely as changed inference code does. This provenance makes the training procedure repeatable; the nondeterminism described earlier still requires checking variation across runs rather than promising identical weights.

The environment belongs in the bundle because dependency mismatches do not always fail loudly. An unsupported driver or a missing library stops the serving process at once, whereas a different linear algebra library or image-resizing routine can alter floating-point results or pixel interpolation without any crash, shifting model outputs and accuracy. A model that meets its sensitivity target in development must therefore be reevaluated if its production environment changes, even when inference completes without an exception. Packaging a reproducible artifact still establishes only that the candidate runs consistently as built; the next stage tests whether it holds up under the clinical conditions it will actually encounter.
