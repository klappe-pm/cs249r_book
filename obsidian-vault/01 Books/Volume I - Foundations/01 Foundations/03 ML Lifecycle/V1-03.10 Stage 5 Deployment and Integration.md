# V1-03.10 Stage 5 Deployment and Integration

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle|V1-03 ML Lifecycle]]

^sec-ml-workflow-deployment-integration-stage-d549

An approved release manifest certifies that a model configuration passed validation, but a manifest is not yet a running clinical service. In the DR scenario, deployment must install the compiled model on Orin Nano-class edge devices across rural clinics with intermittent connectivity, wire the runtime into hospital information systems with distinct schema requirements, and return predictions clinicians can act on before the patient leaves. On the clinic device, the serving path must first fit the 500 MB memory reservation, the precondition every candidate must meet. Latency is then not the binding limit, because the scenario assumes that on-device inference takes well under a second per image (napkin math [3.3](https://mlsysbook.ai/vol1/03_ml_lifecycle/03_ml_lifecycle.html#nbk-ml-workflow-cloud-vs-edge-deployment-economics)), comfortably inside the seconds-scale budget. Dedicated serving infrastructure manages these trade-offs under live traffic, and **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving#^sec-model-serving|Model Serving]]** develops it in depth.

### Deployment Requirements

^sec-ml-workflow-technical-operational-requirements-36ab

Committing that serving path across a 500-clinic network turns per-device memory, latency, thermal, and bandwidth budgets into a fleet-wide infrastructure decision. In the clinical screening scenario, feasibility settles the choice between centralized cloud serving and local edge execution before cost is weighed, because the in-visit latency target and offline operation fixed during problem definition already rule out a cloud round trip. Cost serves only as a check. Napkin math [3.3](https://mlsysbook.ai/vol1/03_ml_lifecycle/03_ml_lifecycle.html#nbk-ml-workflow-cloud-vs-edge-deployment-economics) applies the comparison of capital expense against recurring operating expense from **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.06 Cloud ML Computational Power#^sec-ml-systems-cloud-ml-tradeoffs-constraints-96ed|Cloud ML trade-offs and constraints]]** at network scale to confirm that the feasible option also pays back.

**Napkin Math 3.3: Cloud vs. edge deployment economics**

**Problem**: The cloud option fails the clinic’s stated latency and connectivity requirements, so treat it as a cost benchmark only. Compare the total cost of ownership and operational trade-offs between a cloud inference endpoint and clinic edge devices for processing 760,000 billable screening images monthly across 500 clinics. Where the bandwidth calculation in napkin math [3.2](https://mlsysbook.ai/vol1/03_ml_lifecycle/03_ml_lifecycle.html#nbk-ml-workflow-bandwidth-vs-compute) sized one busy clinic uploading every photograph, this network-wide estimate assumes an average clinic at 50 patients/day and bills one graded image per patient rather than every capture, so its image volume is lower by design.

**Option A: Cloud inference.**

- Model runs on centralized GPU servers
- Inference cost: ~\$0.01/image (cloud GPU time + API overhead)
- Annual inference cost across 500 clinics, 50 patients/day, 1 billable image per patient, 365 days/year, and \$0.01/image is \$91,250/year
- Plus: An assumed connectivity and network-operations allocation for uploading 5 MB per billable image = ~\$45,000/year
- **Total**: ~\$136,250/year operational cost
- Risk: uploading one 5 MB image over the clinic’s 2 Mb/s uplink alone takes about 20 s, before 200 ms+ of remote processing, far beyond the scenario latency target; connectivity outages halt screening

**Option B: Edge deployment on a clinic device.**

- One-time hardware: one \$500/device per clinic across 500 clinics requires \$250,000 capital expense
- Inference cost: ~\$0.001/image (assumed all-in variable operating allocation)
- Annual cost: approximately \$25,000/year maintenance plus approximately \$9,125/year variable inference cost, for about \$34,125/year
- **Total**: \$250,000 upfront + ~\$34,125/year
- Benefit: latency below 50 ms; works offline; much lower per-inference cost

**Math**:

- Annual savings: \$136,250/year (cloud) − \$34,125/year (edge) = \$102,125/year
- Payback: \$250,000 (hardware) ÷ \$102,125/year = ~2.4 years

**Systems insight**: Under these scenario assumptions, edge deployment pays back in ~2.4 years and allows inference during connectivity outages, yet it requires tighter model optimization (must fit in edge memory) and more complex update pipelines. The deployment paradigm selected during Problem Definition determines whether the edge option is even viable.

Once edge hardware is provisioned inside the clinic, host integration extends these physical budgets to the software interfaces of existing clinical infrastructure, where the inference runtime exchanges data with hospital information systems (HIS) to ingest patient records and record diagnostic output. Because prediction scores do not automatically provide reliable uncertainty estimates, their interpretation must be evaluated on representative data before an interface contract uses them to route decisions. This contract specifies which classifications trigger automated referrals and which demand physician review, including how rejected or low-quality inputs are handled, so a confidence threshold cannot be evaluated in isolation from the downstream workflow it triggers.

Privacy rules also shape what happens to data after deployment. Data protection laws can restrict whether production inputs may be stored, linked to patient identifiers, or used for retraining. When a clinic may not retain raw inputs, continuous improvement cannot rely on logging them, so privacy rules limit how the model can be maintained (**[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14 ML Operations#^sec-ml-operations|ML Operations]]**).

### Pilot to Full Deployment

^sec-ml-workflow-scaling-deployment-pilot-production-b3b2

Even after each clinic’s hardware, HIS contract, and privacy rules are satisfied, shipping a new screening model to 500 clinics at once would turn any undiscovered camera mismatch or schema bug into a network-wide outage. Production rollout therefore proceeds in stages to contain failures as the environment widens. Offline replay and synthetic test harnesses first verify schema contracts and concurrency limits without risking patient safety. Pilot deployments in a handful of clinics then expose the serving stack to real-world conditions absent from laboratory benchmarks: optical distortion across camera models, sensor noise under uneven clinic lighting, and differences in how staff position patients. Full-scale rollout broadens exposure to rare anatomical variations and uncommon pathologies. Catching those shifts requires continuous runtime monitoring rather than assuming validation distributions hold forever.

Scaling across hundreds of remote clinics brings hardware diversity and tight network limits across the fleet. Differences in local camera optics shift pixel distributions before inference even begins, requiring on-device input checks that reject out-of-spec captures on the spot. At the same time, narrow wide-area bandwidth rules out continuous weight updates or streaming high-resolution telemetry back to a central cluster. Clinic edge devices must instead run on their own, logging metrics locally and syncing state during scheduled maintenance windows.

Keeping the screener clinically safe requires calibrated uncertainty estimates rather than high average accuracy alone. When the model encounters a borderline retina, returning an uncalibrated score risks a missed diagnosis. Instead, the serving path uses **human-in-the-loop routing**, applying calibrated confidence cutoffs to send borderline cases to specialist ophthalmologists. This routing protects patients in real time and also creates a steady stream of high-value training examples. Specialist-graded borderline cases provide verified labels that feed back into later training runs, targeting the model’s hardest cases.

Keeping hundreds of clinic devices consistent requires versioned, immutable model packages that each clinic installs whole or not at all, a release practice developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-edge-ai-deployment-patterns-dc1d|Edge AI deployment]]**. Deployment marks the shift from static offline evaluation to continuous operations, where telemetry checks whether real-world latency and predictions stay within their approved bounds.

1.  A deployment model processes ~760,000 screening images per month across 500 rural clinics. Cloud inference costs \$0.01/image plus \$45,000/year for connectivity/network operations (\$136,200/year total). Edge deployment requires a \$500 device per clinic (\$250,000 CapEx), \$25,000/year maintenance, and \$0.001/image (\$34,120/year total OpEx). Treat cloud as a counterfactual cost benchmark because it fails the stated connectivity and latency requirements. Using these rounded annual-cost givens, what is the annual operating savings of edge deployment and its payback period?

    1.  A. Approximately \$102,080 annual savings with a payback period of approximately 2.4 to 2.5 years, while enabling offline operation during connectivity outages.
    2.  B. The same annual savings with a payback period of ten years, making cloud deployment far more economical.
    3.  C. The same annual savings with an immediate three-month payback period.
    4.  D. Zero annual savings, because edge hardware maintenance costs exactly equal cloud inference fees at 500 clinics.

2.  Explain what integration requirements an ML screening score adds to a Hospital Information System (HIS) interface beyond recording a measurement with units, and why neither a sensor reading nor a model score establishes its own reliability.

3.  An edge-deployed vision device has a 100 ms total latency budget. Profiling reveals the following execution breakdown: on-device model inference = 15 ms, remote cloud lookup for patient metadata = 60 ms, and local serialization/HIS formatting = 40 ms (total = 115 ms). Assume a local cache contains valid, sufficiently fresh patient metadata and a lookup takes less than 1 ms without changing the other costs. Which engineering modification directly reduces the Iron Law fixed overhead ($L_{\text{lat}}$) term to meet the 100 ms budget?

    1.  A. Prune the neural network weights to reduce on-device model inference time from 15 ms to 5 ms.
    2.  B. Cache patient metadata locally on the device to eliminate the 60 ms remote network round-trip.
    3.  C. Quantize the model from FP32 to INT8 to increase arithmetic intensity (operations per byte).
    4.  D. Increase the GPU clock frequency on the edge device to accelerate tensor core processing.

4.  True or False: Phased deployment progressing from simulation to pilot clinics to full production rollout is recommended because each phase is designed to expose a distinct, non-overlapping class of system failures: simulation catches software integration and schema bugs; pilots catch real-world camera and workflow heterogeneity; and full production catches distributed concurrency contention and rare clinical tail cases.
