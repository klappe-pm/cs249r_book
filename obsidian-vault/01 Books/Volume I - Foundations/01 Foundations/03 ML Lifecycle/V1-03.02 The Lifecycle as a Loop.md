# V1-03.02 The Lifecycle as a Loop

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle|V1-03 ML Lifecycle]]

^sec-ml-workflow-understanding-ml-lifecycle-ca87

A model that runs comfortably on a cloud accelerator can be unusable on the low-power device in a rural clinic, and **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02 System Paradigms#^sec-ml-systems|System Paradigms]]** showed that such a change of deployment target can alter the engineering of the same model by orders of magnitude. The deployment target is only one decision in a longer chain. A team must also decide what the system has to do, gather and prepare the data it learns from, train and test the model, install it where it will run, and keep checking that it still works as the world around it changes. The rest of this book takes that work apart piece by piece along the data, algorithm, and machine axes, from data pipelines and model architectures through training, optimization, and serving. Those pieces are not independent. Each hands its results to the next, and a mistake made in one tends to surface in another. Understanding any single piece therefore requires first understanding how they connect: the sequence of stages every ML system moves through, what each stage hands to the next, and how a constraint discovered in one place reaches the others.

That sequence is the **machine learning lifecycle**, a structured, iterative process[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn1|¹]] that guides the development, evaluation, and improvement of ML systems ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-amershi2019|Amershi et al. 2019]]). Numbered in the order a project first meets them, its six stages form a chain in which each stage produces the artifact the next one needs. Problem definition (1) turns a request into measurable targets and deployment constraints. These guide data collection and preparation (2), which turns raw observations into a versioned, validated dataset. Model development and training (3) then fits trained weights to that dataset, and evaluation and validation (4) tests those weights against the original targets and records the release evidence in a release manifest, the fixed record of what was tested and approved. Once that evidence supports a release, deployment and integration (5) installs the approved model where it must run, while monitoring and maintenance (6) watches the live system and sends what it learns back to earlier stages, closing the loop drawn in [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^fig-lifecycle-overview|figure 1]].

![[90 Assets/Volume I/03 ML Lifecycle/Generated Figure 4602c3e387.svg]]

Figure 1: **Simplified Lifecycle with Feedback**: The six core stages of ML engineering form a closed loop rather than a linear handoff. A primary feedback path from monitoring back to data collection supports investigation and adaptation as production distributions shift, model accuracy degrades, and operational constraints evolve.

^fig-lifecycle-overview

The return arrow from monitoring is what makes the lifecycle a loop rather than a checklist. Evidence flows back from later stages to earlier ones, and constraints should flow back with it. A memory limit set by the deployment device belongs in problem definition, where it can shape the dataset, the model, and the evaluation, not in deployment, where it can only reject them.

**Definition 3.1: Machine learning lifecycle**

***Machine learning lifecycle*** is the iterative engineering process of building, deploying, monitoring, and updating ML systems, where evidence from later stages can feed back to earlier stages because model performance may change after deployment.

1.  **Significance**: The lifecycle is a closed loop, not a linear pipeline. Each stage hands the next an artifact it depends on (targets, a dataset, trained weights, release evidence, a running service, monitoring evidence). A decision at one stage therefore constrains every stage after it, and evidence from a later stage can force an earlier one to be revisited. How often the loop must turn is itself a recurring budget, set by how quickly the deployment environment changes and how long verified labels, the confirmed outcomes that show whether each prediction was right, take to arrive after the prediction.
2.  **Distinction**: Unlike traditional software, whose behavior changes when code, configuration, dependencies, or environment changes, ML behavior can also change as the world changes. A deployed model’s accuracy may change through distribution shift even when the code, infrastructure, and configuration remain untouched.
3.  **Common pitfall**: Treating deployment as the end of the lifecycle. Retraining decisions depend on outcome evidence that exists only after deployment.

Carrying constraints around that loop is the job of the **ML workflow**, the engineering framework that makes constraints explicit at each stage and traces how deployment constraints propagate across Data, Algorithm, and Machine. The two terms divide the job. The lifecycle is *what gets traversed*, the stages themselves; the workflow is *how the traversal is managed*, the engineering discipline of orchestrating them. A team that writes the deployment device’s memory limit into the problem definition is practicing the workflow; a team that discovers that limit only when the finished model fails to fit is working without one. That discipline separates a systems engineer from a model researcher. A researcher optimizes individual elements: a better architecture, a cleaner dataset, a faster accelerator. A systems engineer orchestrates those elements into production systems that reliably deliver value.

↩︎ The deployment paradigms whose memory, latency, and power constraints the workflow propagates are established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.02 Four Deployment Regimes Across Nine Orders of Magnitude#^sec-ml-systems-deployment-paradigm-framework-0d25|Four Deployment Regimes Across Nine Orders of Magnitude]]**.

In practice, the stages between problem definition and deployment run as two pipelines on different clocks. The model pipeline repeats once per training-and-evaluation cycle, which takes hours to a week, whereas the data pipeline and the production feedback that reshapes it turn over in weeks to months. [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^fig-ml-lifecycle|Figure 2]] zooms into that work as ten finer-grained blocks. It covers data collection through deployment and splits stage 4 into a model-evaluation block and a system-validation block; its feedback arrows stand in for the monitoring stage.

The upper data pipeline, the substance of stage 2, continuously transforms raw operational streams through ingestion, curation, annotation, and validation into versioned, ML-ready datasets. The lower model pipeline runs the inner loop of stages 3 and 4, the fast cycle that trains architectures, computes evaluation metrics, validates system constraints, and packages approved artifacts for deployment; the figure draws stage 4’s release manifest as an ML certificate. The feedback arrows form the slower outer loop that monitoring drives. They carry production telemetry (logs of what the system does in service) and data-validation findings (checks on incoming data, distinct from stage 4’s model validation) back to the upstream data stages.

![[90 Assets/Volume I/03 ML Lifecycle/Generated Figure 88873e3f79.svg]]

Figure 2: **Dual-Pipeline ML Development**: Machine learning engineering decouples into parallel data and model pipelines operating on different timescales. While the model pipeline executes rapid inner-loop training and evaluation, outer-loop feedback from production deployment and data validation continuously reshapes upstream collection and curation.

^fig-ml-lifecycle

### ML Vs. Traditional Software

^sec-ml-workflow-ml-vs-traditional-software-development-c5f5

The loop and its two pipelines exist because of one difference between ML systems and traditional software. Both iterate.[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn2|²]] The difference that forces new workflow controls is where behavior comes from. Rule-based software changes behavior when someone changes the code, configuration, or dependencies. An ML system learns its behavior from data, so that behavior can also change when the data changes while the code stays fixed, and only fresh labeled outcomes can show whether today’s model still meets today’s requirement. Every workflow addition this chapter introduces (versioned datasets,[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn3|³]] statistical evaluation checks, drift monitoring) exists to manage that second path.

↩︎ Data-defined behavior, and the silent degradation it makes possible, are established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.07 When ML Systems Fail Silently#^sec-introduction-ml-vs-traditional-software-e19a|When ML Systems Fail Silently]]**.

That difference alters how lifecycle stages interact. While conventional software engineering relies on production feedback to refine code and requirements, ML systems introduce feedback loops where operational data reshapes training distributions, detected drift prompts investigation, and runtime errors expose dataset blind spots. [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^tbl-sw-ml-cycles|Table 1]] contrasts traditional software and ML engineering across six core lifecycle dimensions. In each, data evolution redefines testing, deployment, or ongoing maintenance.

| **Aspect**                 | **Traditional Software Lifecycles**                                                                 | **Machine Learning Lifecycles**                                                                            |
|:---------------------------|:----------------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------|
| **Problem Definition**     | Functional requirements specify behavior; tests check the code against them.                        | Objectives are statistical targets whose feasibility is known only after experiments on data.              |
| **Development Process**    | Engineers write and revise the logic directly in code and configuration.                            | Engineers shape behavior indirectly through data, features, architecture, and training runs.               |
| **Testing and Validation** | Many functional tests have exact expected results; performance and reliability remain quantitative. | Metrics over held-out data, reported with uncertainty and across subgroups.                                |
| **Deployment**             | Logic stays fixed until code, configuration, or dependencies change.                                | Accuracy can degrade when input distributions shift, with code unchanged.                                  |
| **Maintenance**            | Maintenance involves modifying code to address bugs or add features.                                | Continuous monitoring, updating data pipelines, retraining models, and adapting to new data distributions. |
| **Feedback Loops**         | Production feedback changes code, configuration, and requirements.                                  | Production data can become future training data, so feedback also reshapes data collection and the model.  |

Table 1: **Traditional Software vs. ML Development Lifecycles**: Six dimensions where ML development diverges from traditional software engineering. Both use production feedback, while ML systems add loops in which deployment insights reshape data collection, monitoring drives model updates, and production experience informs model design.

^tbl-sw-ml-cycles

**Checkpoint 3.1: ML vs. traditional software**

ML systems are not traditional software with a model attached. Check the differences that force a separate workflow:

**Failure modes**: Can you explain how a shift in input data can degrade an ML system silently, with no code change and no error raised?

**Logic source**: Can you explain why changing training data can change model behavior even when the code remains fixed?

**Iteration**: Can you explain why ML requires monitoring and, when evidence warrants it, model or data updates?

Each difference in the comparison traces back to behavior learned from data, which ties every stage to the stages around it. A diagram shows where the stages sit, but seeing how tightly data-learned behavior ties them together requires tracing one production system across the full loop.

### The Running Case: Diabetic Retinopathy Screening

^sec-ml-workflow-case-study-diabetic-retinopathy-screening-7d71

Automated screening for diabetic retinopathy (DR), a major cause of preventable vision loss,[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn4|⁴]] exposes that stage-to-stage coupling in practice. While early detection prevents severe vision loss, limited access to specialist ophthalmologists in rural regions motivates automated screening programs. Detecting the pathology, however, requires identifying subtle microvascular features under variable capture conditions. [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^fig-eye-dr|Figure 3]] contrasts a normal retina (Panel A) with one showing diabetic retinopathy (Panel B).

![[90 Assets/Volume I/03 ML Lifecycle/Eye Dr 03682f55c2.png]]

Figure 3: **Retinal Hemorrhages in DR Screening**: Side-by-side fundus images illustrate the subtle visual features an ML screening system must detect. Identifying localized microvascular lesions (such as the indicated hemorrhage) requires preserving fine spatial resolution through the vision pipeline and establishing strict input-quality validation to handle lighting and camera variations in clinical field deployments. Source: ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-peng2016deep|Peng and Gulshan 2016]]).

^fig-eye-dr

Google built one of the best documented of these programs, a deep-learning model that performed at the level of ophthalmologists on curated retinal images ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-gulshan2016|Gulshan et al. 2016]]) and that Google Health then deployed in clinics in Thailand ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-beede2020human|Beede et al. 2020]]). This screening program therefore spans both sides of the lab-to-field gap, the difference between the curated images a model is developed on and the images clinics actually capture, making it a revealing system to trace across the full lifecycle. Its deployment in Thai clinics exposed operational friction that the controlled validation never saw: images rejected as ungradable, retakes that added work for nurses, and screening delayed when slow clinic internet connections held up uploads to the remote grading service.[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn5|⁵]]

To put concrete numbers on each stage, our running scenario adapts that case study into a composite clinic architecture. Because the remote grading path depended on each clinic’s internet connection, the scenario moves inference into the clinic. It describes a network of rural clinics, each executing local inference on an Orin Nano-class edge device, a low-power accelerator board, with 4 to 8 GB of shared memory, of which the clinic’s IT plan reserves about 500 MB for the model. Each clinic connects over an intermittent wide-area uplink of roughly 2 Mbps. The clinical mandate requires more than 90 percent sensitivity and a result the nurse can act on before the patient leaves, which means within seconds of capture and even when the uplink is down.

Sensitivity, the mandate’s headline metric, measures the fraction of true disease cases correctly flagged. Its denominator includes only patients with the condition, so high aggregate accuracy on an imbalanced, mostly healthy population provides no assurance that sick patients will be detected. Specificity measures the fraction of healthy patients correctly left unflagged, bounding unnecessary referrals that would overwhelm regional specialists.

A team that runs these stages as a line rather than a loop fails in a predictable way. Day one: “Build a diabetic retinopathy screening model for rural clinics.” Day 90: 92 percent sensitivity on the validation set used to guide development. Day 120: 94 percent sensitivity after a month of architecture tuning. Day 150: the model is handed to deployment engineers. Day 151: deployment engineers report that the model needs 4 GB of memory to run. Day 152: someone checks the deployment target, a low-power edge device in each clinic whose 4–8 GB of memory is shared with the operating system, the camera pipeline, and the clinic software; the clinic’s IT plan reserves about 500 MB of it for the model. Day 153: five months of work is discarded.

The model’s accuracy was excellent. The team’s machine learning skills were excellent. *The failure was a workflow failure.* A deployment constraint that should have shaped every decision from day one was discovered only after the work was done. That 500 MB budget should have propagated backward to the first architecture meeting, constraining which models were even worth considering. Instead, the team optimized each component in isolation (data collection, architecture selection, training), and the integration failure appeared only when the pieces were assembled. The day-153 failure is one instance of a general principle about how constraints travel through the lifecycle.

**Self-Check: Question**

1.  Team A ships a diabetic retinopathy (DR) screening model and freezes all development once the model clears validation in the lab, treating subsequent tasks as standard server operations. Team B treats the launch as the beginning of an ongoing feedback loop, monitoring operational telemetry and data distributions to guide investigation and evidence-based model updates. Which team’s posture aligns with the ML lifecycle as defined in this chapter, and why?

    1.  A. Team B, because the ML lifecycle is a closed loop where operational feedback, distribution drift, and real-world performance continuously reshape upstream data and model decisions.
    2.  B. Team A, because once a model meets its offline validation thresholds, its statistical properties remain fixed and require only standard infrastructure maintenance.
    3.  C. Team A, because changing a validated model in production introduces regulatory risk that outweighs the benefits of adapting to data drift.
    4.  D. Team B, because the ML lifecycle mandates automatic daily retraining of production models regardless of whether input distributions have drifted.
