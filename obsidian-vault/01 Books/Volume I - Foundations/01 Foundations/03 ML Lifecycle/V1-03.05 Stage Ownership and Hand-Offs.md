# V1-03.05 Stage Ownership and Hand-Offs

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle|V1-03 ML Lifecycle]]

^sec-ml-workflow-six-core-lifecycle-stages-00b0

The rural-clinic failure paid that rework penalty in full because no stage owned the 500 MB memory constraint. The deployment limit surfaced only after data curation, model training, and evaluation decisions had hardened around an infeasible target, and preventing such misalignments requires clear ownership across the system stack. The six stages of [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^fig-lifecycle-overview|figure 1]] divide project responsibilities along the D·A·M axes. Problem definition sets the governing requirements for all three. Data collection and preparation owns the Data axis, model development and training governs the Algorithm axis, and deployment and integration commits both to a physical Machine. Evaluation and monitoring own no single axis of their own; their role is verification, testing whether the three axes work together before release and continuously in production.

A single model choice in the DR project touches every stage. Problem definition fixed the clinic device’s 500 MB model budget, so model development starts from architectures designed for budgets of that kind. MobileNetV2, the book’s mobile lighthouse workload (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-lighthouse-models-9b1c|Lighthouse models put the iron law into practice]]**), is a natural candidate backbone (the network that extracts visual features from each image), at about 14 MB of FP32 weights and about 600 MFLOP per inference. It reaches that operation count by replacing standard image-processing layers with a cheaper variant[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn8|⁸]] rather than by pruning a larger model.

Choosing MobileNetV2 immediately constrains the other stages. Data preparation must produce images at the capture resolution that keeps small hemorrhages visible, since that resolution rather than the backbone’s default sets the input size. Evaluation must measure latency on the clinic device as well as sensitivity. Deployment must confirm that weights, activations (the intermediate values each layer produces while processing an image), and runtime together fit the budget. If on-device evaluation then misses the latency target, the fix loops back to architecture or input resolution, so the stage sequence in the diagram is traversed as a cycle rather than once.

**Checkpoint 3.2: The workflow cycle**

Verify that each stage enforces contracts that tie upstream choices to physical deployment constraints.

**Problem definition**: Can you identify which stage records latency, memory, and accuracy targets, and explain why later stages need those targets?

**Data preparation**: Can you identify which downstream artifacts must use the same image-resolution and preprocessing choices as the training data?

**Model development**: Can you explain why model development needs a deployment memory budget before committing to a candidate?

**Feedback**: Can you explain why a failed on-device latency test sends work back to architecture or input resolution rather than ending at deployment?

Each of those stage decisions also lands on a term of the iron law, which times one task, a training run when the team trains and a single screening when the model serves. Its D·A·M form multiplies samples per task, operations per sample, and seconds per operation, and its additive form sums data movement, compute, and fixed overhead, ${T} = \frac{{D_{\text{vol}}}}{{\text{BW}}} + \frac{{O}}{{R_{\text{peak}}} \cdot {\eta_{\text{hw}}}} + {L_{\text{lat}}}$. In the retinal screening pipeline, the capture resolution chosen during data preparation sets how many bytes each input image adds to the bytes moved (${D_{\text{vol}}}$), both for a training run and for one screening. The MobileNetV2 backbone selected during model development fixes the operations per frame ($\text{FLOPs/Sample}$). The clinic hardware together with its serving runtime determines the realized execution speed ($\text{Seconds/FLOP}$) and dispatch overhead (${L_{\text{lat}}}$).

↩︎ The iron law of ML systems and its governing terms are established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**.

**Systems Perspective 3.1: Lifecycle stages and the iron law**

The six lifecycle stages alter distinct factors in both forms of the iron law of ML systems, the multiplicative D·A·M form (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|equation 1.2]]**) and the additive form above. Rather than rigid one-to-one assignments, the mappings serve as diagnostic starting points:

- Problem definition: Sets target constraints for accuracy, latency, cost, privacy, and deployment paradigm (screened against privacy, latency, compute, and cost criteria using the decision framework in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.10 Choosing a Deployment Paradigm#^fig-mlsys-playbook-flowchart|Deployment Decision Screening]]**). These targets determine which terms of the equation are permitted to grow and which must be bounded from the outset.
- Data collection and preparation: Shapes dataset composition, the sample budget ($\text{Samples/Task}$), and the byte volume (${D_{\text{vol}}}$) presented to downstream pipelines. Curation can also change the training work required to reach a quality target.
- Model development and training: Dictates per-sample algorithmic work ($\text{FLOPs/Sample}$) and total operations (${O}$), along with data reuse patterns, parameter movement, and achievable hardware efficiency (${\eta_{\text{hw}}}$).
- Evaluation and validation: Tests whether model quality and end-to-end execution meet deployment requirements on the target system.
- Deployment and integration: Determines the serving path and realized machine speed ($\text{Seconds/FLOP}$), including runtime data movement, execution efficiency, and fixed overhead (${L_{\text{lat}}}$).
- Monitoring and maintenance: Observes distribution drift, latency, throughput, and operational cost after launch, feeding violations back into earlier stages for re-optimization.

Viewing the lifecycle through the iron law grounds latency and cost in hardware physics. Production workflows must simultaneously satisfy accuracy, safety, privacy, and organizational constraints that sit outside the equation.

### Stage Interface Contracts

^sec-ml-workflow-stage-interface-specification-ae3c

Assigning stage ownership across the iron law works only if each hand-off is checked before the next team builds on it. If the data team hands over $512 \times 512$ retinal crops while the training script expects $1024 \times 1024$ images, or if problem definition hands off to data collection without recording the clinic device’s 500 MB memory limit, the defect travels silently and surfaces only when a downstream stage crashes or rejects the finished model. Just as microservice architectures rely on API specifications to govern service boundaries, ML pipelines use explicit **stage interface contracts** that define the required inputs, output deliverables, and quality invariants for every stage ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.05 Stage Ownership and Hand-Offs#^tbl-stage-interface|table 2]]). A quality invariant is a condition the output must meet before the next stage may build on it, such as a dataset whose images match the resolution the training script expects.

Several cells in the table name evidence, such as subgroups and rollback procedures, that later stages take up. In production, pipeline orchestrators, the tools that run each stage’s jobs in order, enforce these contracts by halting a run the moment a boundary check fails (**[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-development-infrastructure-automation-de41|Development Infrastructure]]**).

| **Stage**                         | **Input Contract**                                                                  | **Output Contract**                                                           | **Quality Invariant**                                                                                                                 |
|:----------------------------------|:------------------------------------------------------------------------------------|:------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------------|
| **Problem Definition**            | Business requirements; operational context                                          | Measurable objectives; deployment paradigm selection; resource constraints    | All success criteria are quantifiable; target deployment paradigm is explicit                                                         |
| **Data Collection & Preparation** | Objectives; deployment target; quality requirements                                 | Versioned dataset with schema; preprocessing pipeline; data validation rules  | Distribution approximates anticipated production environment; labeling meets accuracy requirements                                    |
| **Model Development & Training**  | Dataset; accuracy targets; resource constraints                                     | Trained model weights; training configuration; experiment logs                | Meets accuracy thresholds within computational budget; architecture compatible with deployment target                                 |
| **Evaluation & Validation**       | Trained model; held-out test data; evaluation criteria                              | Performance metrics across subgroups; failure mode analysis; release manifest | No critical subgroup falls below minimum thresholds; predicted confidence matches observed accuracy as closely as the domain requires |
| **Deployment & Integration**      | Validated model; infrastructure requirements; service-level agreement (SLA) targets | Serving endpoint; monitoring instrumentation; rollback procedures             | Latency and throughput meet paradigm requirements; integration tests pass                                                             |
| **Monitoring & Maintenance**      | Live system; performance baselines; alert threshold                                 | Drift detection alerts; update-review criteria; incident reports              | Alert coverage and detection windows are defined; detected degradation triggers review                                                |

Table 2: **Stage Interface Specification**: Each lifecycle stage has explicit input requirements, output deliverables, and quality invariants that must hold for the stage to be considered complete. Violations of these contracts create technical debt that compounds through subsequent stages. The deployment paradigm selection in Problem Definition (Cloud, Edge, Mobile, or TinyML) constrains all downstream stages, as a TinyML target imposes different data, model, and monitoring requirements than a Cloud target.

^tbl-stage-interface

Enforcing explicit contracts turns the conceptual feedback loop in [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.02 The Lifecycle as a Loop#^fig-lifecycle-overview|figure 1]] into an operational audit trail. When validation or monitoring surfaces a defect, the contract boundary identifies which upstream stage owns the fix. Each hand-off recorded what the artifact was checked against, so the team can walk back to the earliest boundary whose contract the artifact broke, or whose contract never stated the condition. On the day-153 model, deployment found the defect, but no earlier hand-off had checked memory. Evaluation measured sensitivity, model development received no memory budget, and problem definition handed off without recording the 500 MB limit. Problem definition is therefore the earliest boundary whose contract never stated the condition, so the fix starts there rather than at deployment. Other defects walk back to other owners. Images from one clinic’s camera that differ from the training set call for targeted data collection, whereas images resized differently in serving than in training point to a bug in the serving pipeline. Catching these violations at stage boundaries stops bad assumptions before they harden into late-stage rework.

**Example 3.1: Auditing stage transitions**

**Scenario**: An engineering team claims to have completed Problem Definition for the DR screening classifier, attempting to transition to Data Collection without establishing deployment target constraints.

**Diagnosis**: The output contract lacks deployment paradigm selection and resource constraints (latency and memory targets). If the violation surfaces only at deployment as a trained model larger than the edge device’s 500 MB model budget, the audit must trace what relied on the missing limit. A smaller candidate may require revised input-resolution or preprocessing choices, new weights, repeated sensitivity and on-device memory tests, and a replacement deployment package. Existing raw images may remain usable; changing the candidate does not imply recollecting every image.

**Repair schedule**: Suppose the repair plan preserves the raw images and labels but changes input preparation and the candidate architecture. Assume 1 day to revise preparation, 2 days to train new weights, 2 days to repeat validation, and 1 day to package the approved result. If each task waits for the preceding artifact and the required staff and compute are available, the repair takes 6 days. A late constraint has two costs, and this schedule prices only one. Repair time is the days just estimated, short only because the raw images and labels survive and a smaller candidate is assumed to be at hand. Wasted work is the part of those five months spent tuning a model too large for the device, and no repair recovers it.

**Systems lesson**: Stage transitions act as quality checks in the ML lifecycle. Enforcing strict output contract validation before proceeding downstream prevents expensive upstream rework and ensures data collection aligns with target deployment hardware.

^exmp-ml-workflow-auditing-stage-transitions

Without explicit contract checks at each hand-off, unstated assumptions propagate downstream. The earliest opportunity to bound them is Problem Definition, which records the operational constraints that subsequent stages must satisfy.

    1.  A. Approved, because decoupling model development from hardware targets allows researchers to maximize accuracy before applying post-hoc pruning.
    2.  B. Approved with warning, provided the team commits to using cloud inference if the model exceeds edge memory budgets.
    3.  C. Blocked, because Problem Definition’s output contract explicitly requires deployment paradigm and resource constraints to be established before data collection and modeling begin.
    4.  D. Blocked only if the model architecture requires distributed multi-GPU training, since single-device models can adapt to any deployment target.

Explain how choosing a model to fit that budget propagates across Data Collection, Model Development, and Evaluation.

4.  Which mapping between lifecycle stages and the terms in the Iron Law of ML Systems ($T = \frac{D_{\text{vol}}}{\text{BW}} + \frac{O}{R_{\text{peak}} \cdot \eta_{\text{hw}}} + L_{\text{lat}}$) is conceptually consistent with the chapter?

    1.  A. Problem Definition exclusively determines $R_{\text{peak}}$, and later lifecycle stages cannot materially affect hardware throughput or efficiency once the use case is chosen.
    2.  B. Model Development and Training exclusively determines $O$, while Data Collection and Preparation cannot affect bytes moved and Deployment and Integration cannot affect latency overhead.
    3.  C. Deployment and Integration exclusively determines $L_{\text{lat}}$, while earlier stages cannot materially affect operation count, data volume, or serving-path overhead once deployment begins.
