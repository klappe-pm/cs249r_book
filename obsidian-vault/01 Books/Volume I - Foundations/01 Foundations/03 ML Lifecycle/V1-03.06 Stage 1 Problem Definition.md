# V1-03.06 Stage 1 Problem Definition

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle|V1-03 ML Lifecycle]]

^sec-ml-workflow-problem-definition-stage-5974

Problem definition in ML begins with sentences that look deceptively simple. A product manager writes: “Build a model that detects diabetic retinopathy.” That single sentence conceals a dozen engineering decisions: sensitivity thresholds for patient safety, hardware capabilities in rural clinics, latency budgets that keep clinicians engaged, and regulatory frameworks governing approval. Software requirements still govern control flow, interfaces, and data storage. ML adds an empirical obligation. Defining *what* the system should do is inseparable from defining *how* it will learn from data and what physical constraints its execution must survive.

The request for a model must first become a requirement for a measurable improvement over a named baseline, the way the work is done today. In the clinic case, the baseline is the existing screening and referral workflow, evaluated on the outcomes and resource limits the proposed system must improve. Stated against that baseline, the request becomes a testable requirement, for example to find more referable disease than the current referral path finds, at a referral volume regional specialists can absorb, measured on the clinics’ own patients. The scenario sets floors of more than 90 percent sensitivity and more than 80 percent specificity. Those floors carry that comparison into numbers only if the team derives them from it. The sensitivity floor must sit above the share of disease the current path finds, and the specificity floor must hold referrals to a volume specialists can absorb, or clearing them shows nothing about whether the clinics gain. “Build a model” names no such comparison, so it offers no test of success.

A simpler rule or an existing model can provide an additional comparison where appropriate. The comparison must include the complexity tax established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.10 Choosing a Deployment Paradigm#^sec-ml-systems-decision-framework-241f|Four screening checks for choosing a tier]]**, the infrastructure, monitoring, and maintenance cost that a learned system adds, so a learned system earns its place only when the value of the errors it avoids exceeds that cost. If available data cannot support the required evaluation, or the expected benefit does not justify the added cost, the team should revise the problem or retain the baseline rather than proceed automatically to training.

Balancing the clinical, hardware, and regulatory demands hidden in that one-sentence request requires reasoning across the full system stack. An engineering team cannot optimize accuracy in isolation, because pursuing marginal sensitivity gains by scaling model depth or adopting a larger model family inflates parameter count and computational demands (FLOPs per inference), directly challenging the memory capacity and thermal limits of low-cost clinic hardware. Conversely, pruning a model (removing the weights that contribute least) to fit an embedded accelerator’s DRAM budget risks dropping sensitivity below clinical safety thresholds. Every technical decision in problem definition therefore operates as a multi-constraint optimization problem in which accuracy targets and deployment limits restrict each other from day one.

### Constraint Layers

^sec-ml-workflow-balancing-competing-constraints-b92a

A screening model that reaches 95 percent sensitivity in a cloud notebook still fails that optimization if it needs 4 GB of RAM on a clinic device with 500 MB to spare, or if clinic staff cannot audit why it flagged a patient. To make all of those limits explicit before data collection begins, problem definition decomposes requirements into three interacting **constraint layers**: statistical, physical, and operational. Rather than isolated checklists, these layers form a coupled stack where a limit in one tier narrows the choices available in the others.

At the top of the stack, the statistical layer specifies target behavior over data distributions, such as achieving $>90$ percent sensitivity and $>80$ percent specificity across diverse patient demographics and camera models rather than an unweighted aggregate accuracy that conceals failure modes on minority subpopulations. Meeting that target in the field depends on the physical layer, which bounds execution within hardware limits. For rural clinics, that means running inference on local edge accelerators under tight thermal budgets and bounded memory capacity (such as 4 to 8 GB of shared DRAM) and returning a result during the visit without depending on intermittent network uplinks. Surrounding both is the operational layer, which governs clinical auditability, regulatory clearance, and the maintenance rules that keep the deployed system safe over time.

The operational layer carries physical consequences that traditional software engineering rarely encounters. In a traditional database, deleting a patient’s record is a `DELETE` statement. In an ML system, model weights may encode statistical patterns learned from that record. Where law or a regulator requires removing that influence, compliance may require machine unlearning ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-cao2015|Cao and Yang 2015]]; [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-bourtoule2021|Bourtoule et al. 2021]]), methods that remove a record’s influence from trained weights with incomplete guarantees, or else retraining on the remaining data. The team must therefore budget compute for retraining runs and record which patient records trained each released model.

↪ Why removing a record’s influence from trained weights remains a compliance obligation is developed in **[[01 Books/Volume I - Foundations/04 Deployment/15 Responsible Engineering/V1-15 Responsible Engineering#^sec-responsible-engineering|Responsible Engineering]]**.

The constraint propagation principle ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.03 How Decisions Cascade the Constraint Propagation Principle#^sec-ml-workflow-decisions-cascade-system-98f4|section 3.2]]) explains why all three layers must be bound before development begins. A constraint that exists in the physical or operational environment but remains unstated in the problem definition does not vanish. It re-emerges later as an architectural violation after dependent decisions have hardened. For example, if an engineering team defines the objective solely as aggregate classification accuracy on retinal images, standard optimization will minimize the average training loss (the error score that training drives down), which the majority class dominates. In an imbalanced screening population where 90 percent of patients are healthy, a model predicting “no disease” achieves 90 percent aggregate accuracy while failing every patient who needs urgent care. Because training pursues only the metric it is given, a metric that diverges from the goal defeats the system before the first training run. Preventing this requires translating a domain invariant (a missed diagnosis costs far more than a false referral) into an explicit statistical contract: a training loss that weighs each missed case more heavily than a false referral, a sensitivity floor, and subgroup targets.

**War Story 3.1: When the label was the bias (2018)**

**Context**: In 2014, Amazon assembled an engineering team at its Edinburgh hub to build an internal machine-learning system for ranking technical job applicants, training it on ten years of resumes submitted to Amazon ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-dastin2018|Dastin 2018]]).

**Mechanism**: Because prior hiring was male-dominated, the model learned that male-coded language correlated with hiring success, systematically penalizing terms like “women’s” and downgrading graduates of two all-women’s colleges.

**Impact**: The model reproduced historical hiring bias, rendering automated resume screening unsuitable for production recruitment.

**Fix**: Amazon abandoned the experimental tool after attempts to remove explicit gender signals could not guarantee that it would not learn other discriminatory proxies.

**Systems lesson**: Problem definition must specify fairness, auditability, and rejection criteria before data collection and training. A workflow trained on biased labels does not learn the operational goal; it learns to reproduce the labels.

### Problem Definitions Evolve

^sec-ml-workflow-adapting-definitions-scale-40ed

When a DR screening program expands from one pilot clinic with a calibrated fundus camera to dozens of regional health centers with different camera brands and patient populations,[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn9|⁹]] its initial assumptions break. Sensor noise profiles diverge, optical resolutions shift, and demographic changes alter subgroup error rates. A problem definition is therefore not a static specification frozen at the start of a project; it must evolve as deployment expands, adding subgroup accuracy targets and broader hardware compatibility checks. How such subgroup and governance requirements are specified, tested, and maintained is developed in **[[01 Books/Volume I - Foundations/04 Deployment/15 Responsible Engineering/V1-15 Responsible Engineering#^sec-responsible-engineering|Responsible Engineering]]**.

This evolution follows directly from how ML systems learn. Scaling exposes rare inputs absent from pilot evaluations, while production environments shift the input distribution in ways no static offline dataset fully captures. A sound problem definition anticipates this drift by setting governance rules upfront. Those rules define which monitoring signals trigger formal re-evaluation and bound how threshold updates propagate through later pipeline stages. Once these operational constraints and performance boundaries are defined on paper, the workflow must ground them in physical artifacts, beginning with the data collection pipelines that gather the training distribution.

    1.  A. It specifies only a high-level task while omitting the statistical constraint layers (sensitivity/specificity floors across subgroups), physical constraints (edge device memory/latency budgets), and operational constraints (regulatory compliance, clinical workflow integration).
    2.  B. It fails to specify which exact deep neural network backbone and learning rate schedule must be used during training.
    3.  C. It defines an image classification problem when medical AI systems must always be framed as unsupervised anomaly detection tasks.
    4.  D. It defines quantifiable objectives before data collection has occurred, which violates standard ML agile practices.

2.  Explain why ophthalmologists and clinic administrators must participate directly in Problem Definition for a DR screening system, rather than being consulted only during clinical evaluation.

    2.  B. Offline evaluation metrics are inherently incapable of measuring demographic disparities in supervised learning models.
    3.  C. A model trained on historical data learns to reproduce historical label biases rather than the intended operational goal; fairness criteria and auditability must be explicitly defined at Problem Definition.
    4.  D. Multi-class classification algorithms should not be applied to human evaluation tasks where ground truth is subjective.

True or False: When a diabetic retinopathy screening deployment scales from a 3-clinic pilot to 200 clinics across diverse regions, the high-level clinical intent (detect referable retinopathy early) remains stable, but the specific engineering targets (subgroup sensitivity thresholds, device latency budgets, and camera-specific preprocessing rules) must evolve.
