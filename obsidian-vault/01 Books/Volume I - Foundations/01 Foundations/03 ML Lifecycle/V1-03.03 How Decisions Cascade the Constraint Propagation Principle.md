# V1-03.03 How Decisions Cascade the Constraint Propagation Principle

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle|V1-03 ML Lifecycle]]

^sec-ml-workflow-decisions-cascade-system-98f4

In the DR scenario, the in-visit requirement already ruled out cloud inference and so required edge deployment. The edge target’s memory and power budgets then constrain model architecture, favoring compact MobileNet-class models (a family of small image models designed for phones and edge devices) over large ensembles (several models whose predictions are combined) and requiring automated image-quality checks at capture time. Each downstream constraint narrows the design space for upstream stages, coupling hardware limits directly to data collection and model design.

**Definition 3.2: Constraint propagation principle**

***The constraint propagation principle*** states that a constraint discovered late in the ML lifecycle can force rework across affected upstream stages. Datasets, trained weights, validation evidence, and deployment packages record decisions that later work depends on. Correcting a missing constraint requires tracing those dependencies to determine which artifacts must change and which remain valid. Estimating actual rework requires the effort to revise each affected artifact, repeat its dependent work, and validate the resulting system.

1.  **Significance**: A latency target discovered at deployment (stage 5), such as 100 ms in a web service, may propagate backward. It can constrain model size (stage 3: operation count ${O}$), dataset requirements (stage 2: dataset size ${D}$, the number of training examples), and problem definition (stage 1: what accuracy is achievable). Rework depends on which earlier decisions relied on the missing constraint. The iron law (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**) writes a task’s total time ${T}$ as the time to move data, plus the time to compute, plus fixed overhead. A latency budget bounds that total, and therefore every term that sums to it. It thus limits ${O}$, the bytes moved ${D_{\text{vol}}}$ (distinct from the example count ${D}$), and the hardware efficiency ${\eta_{\text{hw}}}$ the model needs.
2.  **Distinction**: Unlike modular decomposition (which encourages independent optimization of each component), this principle mandates end-to-end reasoning, because an accuracy optimum reached in isolation can be an infeasible system.
3.  **Common pitfall**: Treating deployment as “the last step” and so deferring its latency, memory, and power limits until they can only reject finished work.

For the day-153 model, that trace starts at the 500 MB limit and runs back through the artifacts built without it. The input preparation and architecture must be revised, new weights trained, and the system validated again before it is repackaged. The worked repair schedule in example [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.05 Stage Ownership and Hand-Offs#^exmp-ml-workflow-auditing-stage-transitions|3.1]] estimates that chain, and it keeps the repair separate from the work lost over the five months, which went into a model that did not fit.

Propagation runs in both directions, so the stages form a network of constraints rather than a chain. Backward propagation carries a deployment limit upstream. When rural clinic deployment reveals tight bandwidth, the team can compress images before sending them over the uplink. Lossy compression degrades input quality, however, so the training dataset must then include matching compression artifacts, or the model will meet inputs in service that differ from those it trained on, a mismatch called training-serving skew. Shifting inference entirely to the edge and transmitting only the diagnostic result relieves the uplink instead, but tightens the edge device’s memory capacity and power budget. Forward propagation carries an early data decision downstream. Capturing fundus images at the resolution needed to see small hemorrhages fixes the model’s input size, and with it the operation count every inference must pay on the clinic device, since a larger input image takes more operations to process. Upstream data choices and downstream machine boundaries remain physically coupled.

Decisions made without accounting for downstream execution boundaries accumulate technical debt.[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.17 Footnotes#^fn6|⁶]] Stage interface contracts, the checked hand-offs listed in [[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.05 Stage Ownership and Hand-Offs#^tbl-stage-interface|table 2]], put this principle to work by making constraints explicit at each stage boundary, so the team catches violations before handing an artifact downstream. When propagation occurs specifically through data quality failures, the resulting pattern is known as a data cascade, a chain of downstream failures triggered by bad data ([[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.16 Source References#^ref-sambasivan2021|Sambasivan et al. 2021]]) that **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.03 How Data Fails#^sec-data-engineering-data-cascades-systematic-foundations-matter-2efe|Data cascades]]** examines. Propagation explains why a late constraint is expensive; how much time each loop costs, and where that time goes, is the next question.
