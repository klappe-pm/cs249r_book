# V1-04.14 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering|V1-04 Data Engineering]]

^sec-data-engineering-fallacies-pitfalls-886b

Data engineering pipelines rarely fail with immediate runtime crashes; instead, they silently distort feature distributions, corrupt training state, or starve expensive accelerator clusters. The nine fallacies and pitfalls that follow collect the recurring assumptions behind those failures, pairing each with the pipeline measurement or contract that prevents it.

**Fallacy**: *More data always improves model performance.*

The bitter lesson says that general methods fed with more data and compute keep winning, but it does not say each new sample is worth as much as the last. Beyond a threshold, additional data yields diminishing returns described by empirical scaling laws, fitted curves relating model error to dataset size. Studies across computer vision, translation, and language modeling find that test loss falls as a power law in dataset size, so each successive error reduction demands a multiplicatively larger volume of samples ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-hestness2017deep|Hestness et al. 2017]]). In the illustrative KWS design space, a tenfold larger training set buys 5–8 percent more detection rate at 10× the labeling cost. In systems terms, repeated examples consume disk I/O, host-to-device bus bandwidth, and accelerator FLOPs without adding distinct observations. Repeated passes can still shift the model slightly, so redundancy must be judged by its measured effect on evaluation rather than assumed to contribute nothing. The task-relevant signal heuristic from [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-physics-data-cdcb|section 4.9]] captures this trade-off: scaling raw byte volume without preserving information density inflates infrastructure cost while yielding negligible improvements in evaluation loss.

↪ Scaling laws, and the selection methods that decide which samples are worth their training compute, are developed in **[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.02 The Data Wall#^sec-data-selection-data-selection-fundamentals-e839|The Data Wall]]**.

**Pitfall**: *Planning petabyte migration as a bandwidth-only transfer.*

Dividing data volume by network link bandwidth gives the theoretical wire time, about 22 h for the chapter’s 1 PB example at 100 Gb/s, but wire transfer is rarely the critical path. Data gravity ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-physics-data-cdcb|section 4.9]]) ties large datasets to a web of surrounding infrastructure: ingestion transformation pipelines, schema validation checks, access-control policies, and downstream consumers. Moving a petabyte-scale corpus between clouds or data centers requires refactoring pipelines, revalidating data integrity, re-warming caches, and rebuilding metadata indexes. In practice, the engineering time spent adapting dependent systems dwarfs the raw network transit time.

**Fallacy**: *Data preprocessing can be finished once and left alone.*

Preprocessing pipelines turn raw observations into model inputs using parameters fitted on historical data: vocabularies that map words or categories to integer codes, mean and variance scaling vectors, category frequency tables, and numerical clipping bounds. When production distributions drift, these fixed transformations go stale. Fixed vocabularies meet a rising share of values they never saw, fixed normalization constants push scaled features outside the range the model trained on, and static clipping bounds cut off valid signal. Keeping the pipeline accurate requires monitoring input tensors and outcomes, then validating any change to preprocessing together with the model that consumes its features. Recomputing statistics independently at serving time can itself introduce skew.

**Pitfall**: *Ignoring data serialization cost.*

Profiling often focuses exclusively on accelerator execution while data loaders quietly parse raw JSON or CSV files. Parsing text-based records requires host CPU cores to spend hundreds of cycles per sample on string decoding, tokenization, ASCII-to-float conversions, and heap allocations. This host-side parsing starves the accelerator just as the dataloader choke point does ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-data-ingestion-8efc|section 4.10.4]]). In the chapter’s ResNet-50 scenario, JPEG decoding already occupies 9 workers per accelerator, each preparing 375 img/s. A tabular or log-feature pipeline that parses text records pays the string-decoding cost described here on top of any such preparation. Binary serialization formats, such as Apache Arrow or memory-mapped arrays, eliminate parsing overhead by storing numbers directly in machine-native binary layouts that the loader can hand to the accelerator without conversion. For tabular schemas, columnar formats such as Parquet cut disk I/O by reading only the required columns. Benchmarking data ingestion against accelerator consumption rates shows whether host CPU deserialization is throttling training throughput.

**Fallacy**: *High training accuracy indicates production readiness.*

Training accuracy and held-out validation accuracy both describe the historical distribution the data was drawn from. Production adds edge cases, sensor noise, and live drift, and a model with high validation accuracy still fails if upstream feature pipelines change or inference timeouts trigger fallback defaults. Diagnosing post-deployment regressions requires the symptom checks across temporal drift, label artifacts, and training-serving skew ordered in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.13 Operational Data Health#^fig-debug-flowchart|figure 20]], rather than reliance on a single offline score.

**Pitfall**: *Ignoring training-serving skew until deployment.*

Training-serving skew occurs when feature generation logic diverges between the offline training pipeline and the online inference runtime, for example through differences in floating-point precision, time-window aggregation, library versions, or temporal leakage from data timestamped after the prediction point. Because the model still receives valid floating-point vectors, inference raises no runtime exceptions while prediction quality degrades. Avoiding this pitfall requires shared transformation logic, reproducible feature stores, and automated predeployment parity tests that check feature equivalence across offline and online paths.

**Fallacy**: *Synthetic data can fully replace real-world data collection.*

Synthetic data enriches training sets by generating rare edge cases, controlled physical variations, or privacy-safe samples, but a generator can only sample within the assumptions built into it. When trained exclusively on synthetic data, models learn generator-specific artifacts and fail on real-world variation the generator never modeled. In a KWS system, for example, a detector trained entirely on synthesized speech loses accuracy when it meets real room reverberation, unfamiliar accents, microphone distortion, and shifting background noise. Synthetic generation supplements real collection, but representative real-world recordings remain essential for testing whether the system is ready to deploy.

**Pitfall**: *Neglecting data versioning until model debugging requires it.*

Treating training datasets as mutable object-storage directories destroys experiment reproducibility. When a retrained model loses accuracy, an unversioned pipeline cannot show whether the cause is a modified labeling rubric, a silent schema change, or genuine distribution shift, and once tables are overwritten or raw logs deleted, the historical training inputs cannot be rebuilt. As established in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^sec-data-engineering-tracking-data-transformation-lineage-3b09|section 4.8.1]], every model checkpoint must link immutably to a specific dataset snapshot, transformation code hash, and configuration file.

**Fallacy**: *Production logs show where the model fails.*

A deployed system decides much of what data comes back from it. The keyword spotter uploads audio only when it wakes, so its logs fill with correct detections and false wakes, while a wake word it misses leaves no recording at all ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.13 Operational Data Health#^sec-data-engineering-detecting-responding-data-drift-509a|section 4.12.1]]). A team that measures quality from those logs alone sees a false-rejection rate lower than the real one, and retraining on the same logs over-represents the cases the model already handles. Measuring failures requires collection designed for that purpose: consented recording studies, reports of failed activations, and evaluation streams kept independent of the deployed model’s choices.
