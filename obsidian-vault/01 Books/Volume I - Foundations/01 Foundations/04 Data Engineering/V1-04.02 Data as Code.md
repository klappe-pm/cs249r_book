# V1-04.02 Data as Code

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering|V1-04 Data Engineering]]

^sec-data-engineering-data-engineering-dataset-compilation-0496

A missing accent in a speech corpus, a mislabeled class, or a feature computed one way in training and another in serving becomes a defect in system behavior with no line of code to point to. Because a machine learning system learns its behavior from data, the trained model is a compressed summary of its training set. It can represent only the evidence that data contains, and it treats the data’s labels as the definition of a correct answer. In the lifecycle that **[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle#^sec-ml-workflow|ML Lifecycle]]** lays out, the work of building that training set is Stage 2, which ends by handing a versioned dataset to model development; every later stage inherits what that dataset contains and what it lacks.

The bitter lesson (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.05 The Bitter Lesson#^sec-introduction-bitter-lesson-79c7|The Bitter Lesson]]**) explains why this dependence on data has grown rather than shrunk. Methods that learn from data at scale have repeatedly overtaken methods built on hand-encoded knowledge, so the knowledge that engineers once wrote into programs must now arrive through data. The 8 selected models in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.02 Data as Code#^fig-dataset-size-growth|figure 1]] illustrate the resulting range of training-data scales. The image corpora extend from handwritten digits to billions of images, while the language models process hundreds of billions to trillions of tokens. These counts describe different units and counting conventions, so they cannot establish a common doubling time or a common storage requirement.

^fig-dataset-size-growth

At that scale, data constrains the machine as well as the model. Every training step reads its examples from storage, decodes them, and moves them to the accelerator, and an accelerator waiting on input computes nothing however fast it is. Datasets measured in terabytes also have physical mass. They are slow and expensive to move, and they spend energy at every level of the memory hierarchy they cross. Data therefore occupies two of the pairwise overlaps of the D·A·M taxonomy at once, the ones labeled *what to learn from* and *how to move information* in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.06 Defining ML Systems#^fig-ai-triad|The D·A·M Intersection Landscape]]**. Toward the algorithm, it bounds what the model can learn; toward the machine, it bounds how fast learning can proceed.

Both bounds are expensive to meet. Cleaning and organizing data was the most common answer to where data scientists spend their time in the practitioner survey that **[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle#^sec-ml-workflow|ML Lifecycle]]** presents ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-crowdflower2016data|CrowdFlower 2016]]). In the image-classification cost comparison later in this chapter, labeling a dataset costs roughly 2,500× to 5,000× as much as one training run on it. Each stage between raw input and an ML-ready dataset (acquisition, ingestion and validation, labeling, and processing) can also introduce a defect that no later stage detects. Data bounds both capability and throughput and often dominates cost, so it requires the same engineering discipline as the model and the machine: acquisition systems, validation checks, labeling workflows, storage layouts, and governance.

**Definition 4.1: Data engineering**

***Data engineering*** is the infrastructure layer that manages the lifecycle of data from source to model, encompassing acquisition, transformation, storage, and governance.

1.  **Significance**: It sets both bounds that data places on an ML system. Dataset composition, coverage, and labels determine whether the logical dataset, the examples a training task processes (${D}$, the $\text{Samples/Task}$ factor of the iron law), represents the target distribution, and therefore what the model can learn. In the form of the iron law that unpacks the Machine factor (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 1.3]]**), the pipeline governs the data-movement term, the physical bytes moved divided by bandwidth $({D_{\text{vol}}}/{\text{BW}})$, and therefore how fast learning can proceed.
2.  **Distinction**: Unlike data science, which focuses on inference and insight, data engineering addresses the scalability and reliability of the data pipeline.
3.  **Common pitfall**: A frequent misconception reduces data engineering to mere “data cleaning.” In systems terms, it is a build pipeline that turns raw, noisy observations into the validated, versioned tensors that accelerator runtimes consume.

↩︎ The iron law of ML systems, whose data-movement term this chapter governs, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**.

Two of the book’s recurring lighthouse workloads (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-lighthouse-models-9b1c|Lighthouse models put the iron law into practice]]**) carry the chapter, one for each bound. Keyword spotting (KWS), the always-on wake-word detector behind phrases such as “Alexa” and “OK Google,” carries the question of what the data must contain. It takes over from the diabetic retinopathy screening case of **[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03 ML Lifecycle#^sec-ml-workflow|ML Lifecycle]]** because its data problems span both a cloud training pipeline and a microcontroller-class device. The model must recognize a few words across accents, microphones, and rooms, stay silent through months of ordinary speech, and fit in tens of kilobytes on a TinyML-class device. Its reference corpus, the Multilingual Spoken Words Corpus ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-mazumder2021multilingual|Mazumder et al. 2021]]), is real; the smart-speaker requirements and data budget that this chapter sets for it are an illustrative scenario. ResNet-50 image classification on one accelerator carries the question of how fast data must arrive, because image examples are large enough to stress storage, decoding, and transfer in ways that one-second audio clips do not.

The data-as-code principle ([[01 Books/Volume I - Foundations/01 Foundations/V1 Foundation Principles#^pri-data-as-code|1]]) turns the model’s dependence on its data into an engineering rule. Changing a dataset changes the trained model just as changing source code changes a program, even when no line of algorithmic code is touched. The pipeline that produces a dataset is therefore the system’s build, and every retraining is a rebuild.

A dataset then needs the disciplines code already has. Its lineage, the record of what produced each version, must be immutable. Its checks must run as executable validation suites, its versions must ship as named releases, and a regression must be debugged by comparing one version against another. Code also keeps its tests apart from what they test, and a dataset needs the same trust boundary between its splits. The training set is allowed to shape parameters; the validation set is allowed to shape modeling and pipeline choices; the test set is reserved for estimating generalization after those choices have been made.

**Data leakage** occurs when information crosses the boundaries between splits, so that an evaluation score rewards what the model or its designers already saw instead of measuring generalization to unseen data. Leakage enters through duplicate examples appearing in multiple splits, modified copies of the same source record landing on both sides of the split, user records from the same household appearing in both training and test, or time-derived features computed using future observations ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-kaufman2012leakage|Kaufman et al. 2012]]). Preprocessing can leak too, a case [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-ensuring-trainingserving-consistency-c683|section 4.7.1]] takes up once normalization and encoding have been introduced.

The keyword spotter shows the split boundary at work before any model exists. Assigning each speaker’s utterances to a single split keeps the acoustic model from memorizing speaker-specific vocal-tract resonances, so evaluation measures generalization to speakers the model has never heard. The general rule is to assign whole groups to a split rather than individual examples, keyed by whatever unit could carry information across the boundary: a speaker, a household, or the source record behind several modified copies of it.

Like a build, the pipeline that produces a dataset runs in stages, and the chapter follows them in the order of the two bounds. The capability half, which works the Data–Algorithm overlap, comes first. After the ways data fails and the requirements of the keyword spotter, acquisition, ingestion and validation, labeling, and processing build the dataset and settle what the model can learn, and a release step records exactly what was built. The throughput half works the Data–Machine overlap. The physics of moving datasets sets the cost of every byte, and storage and delivery must move those bytes fast enough to keep the accelerator fed. An acceptance test then checks both halves against the targets they started with, and operation keeps both bounds true after deployment.

**Self-Check: Question**

1.  A team is building a training dataset from distributed sensor logs. They discover that the same event can appear in multiple log partitions. They add a pipeline step that identifies duplicate records and keeps one canonical copy. Where must this step run, and why?

    1.  After splitting, because each split should be cleaned independently so that evaluation data is never touched by training-side processing.
    2.  Only on the training split, because duplicates in validation and test data do not affect the trained model.
    3.  Before splitting, because a duplicated record that lands on both sides of the split leaks the same evidence into evaluation and inflates the measured quality.
    4.  Anywhere in the pipeline, because duplicates only waste storage and compute and do not change what the model learns.

2.  Explain why treating training data as the ‘source code’ of a machine learning system necessitates software-engineering practices such as immutable snapshot versioning, automated regression testing, and explicit split boundaries.

3.  True or False: In a keyword-spotting dataset, randomly partitioning audio recordings into an 80/20 train/test split at the individual audio file level maintains a valid trust boundary for estimating real-world generalization.
