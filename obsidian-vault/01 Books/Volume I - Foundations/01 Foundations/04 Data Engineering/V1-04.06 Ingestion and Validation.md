# V1-04.06 Ingestion and Validation

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering|V1-04 Data Engineering]]

^sec-data-engineering-data-pipeline-architecture-b527

A crowdsourced wake-word recording arrives as a stereo MP3, a synthetic one as a mono WAV file at a different sampling rate, and a clip from a consenting user’s device as a compressed fragment stamped in the wrong time zone. The ingestion boundary turns this mix into one consistent record format and decides which records may enter at all. It is the front end of the **data pipeline** in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^fig-pipeline-flow|figure 9]], where records pass through ingestion and central storage before the transformation loops that feed training, inside a governance perimeter that controls what may be kept and who may read it. For keyword spotting, the boundary handles the recorded examples used to build and update the model; the detector’s live audio on the device never passes through it.

![[90 Assets/Volume I/04 Data Engineering/Generated Figure 5d9d5864e3.svg]]

Figure 9: **End-to-End Data Pipeline**: Heterogeneous raw sources (batch and streaming) normalize into unified storage before feeding downstream training and feature processing. The architecture decouples ingestion throughput from iterative transformation and labeling loops, all bounded by an overarching data-governance layer.

^fig-pipeline-flow

The tiers in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^fig-pipeline-flow|figure 9]] keep raw ingestion separate from the validation, transformation, and feature-engineering loops that feed training, so a slow transformation never stops records from arriving, and a check added at ingestion protects every stage after it. Two decisions shape that boundary before any record is checked: when records are taken in, and where they are transformed relative to storage.

### Batch Vs. Streaming Ingestion Patterns

^sec-data-engineering-batch-vs-streaming-ingestion-patterns-e1b2

The first decision, when records are taken in, depends on how quickly data loses value and how much infrastructure cost that freshness justifies. A fraud detector that flags a stolen card hours after the purchase arrives after the money has moved, whereas a week’s worth of crowdsourced wake-word recordings loses nothing by waiting for the next scheduled training run. Batch systems gain efficiency by tolerating that staleness, while streaming systems gain freshness by taking on continuous operational complexity.

**Batch ingestion** collects records over a period and processes them together on a schedule. It amortizes startup cost across large volumes, runs when compute is cheapest, and releases its resources between runs, which suits data whose value decays slowly ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-akidau2015|Akidau et al. 2015]]), such as the new crowdsourced recordings and opt-in diagnostic clips that the keyword spotter folds into its next training run. Batch processing also simplifies recovery and reproducibility: a failed batch can be rerun from its inputs, inspected, and reprocessed after a fix, and the result is repeatable when inputs, code, configuration, and randomness are controlled.

**Stream ingestion** processes each record as it arrives, which is necessary whenever data loses value within seconds, as in real-time fraud scoring. However, stream processing introduces complexity that batch processing avoids. The system must handle **backpressure**, the condition where downstream systems cannot keep pace with incoming data rates. During traffic spikes, when a sudden surge produces data faster than processing capacity, the system must either buffer data (requiring memory and introducing latency), sample (losing some data), or push back to producers (potentially causing their failures). Late or out-of-order events further complicate windowed aggregations, such as a count of clicks per five-minute window, because the system must hold each window’s state open for a set grace period so late events can still be counted, which costs memory.

Buffering, backpressure handling, and per-window state raise compute and memory overhead, so freshness guarantees trade directly against infrastructure cost and operational burden. Data freshness service level agreements (SLAs) specify maximum acceptable delays between data generation and processing. Meeting a 100-millisecond SLA requires different infrastructure than meeting a one-hour SLA, affecting networking, storage, and processing architectures.

Many production ML systems combine the two. A recommendation system might use streaming ingestion for real-time user interactions to update session-based recommendations immediately, while using batch ingestion for overnight processing of user profiles and item features; Notebook [4.3](https://mlsysbook.ai/vol1/04_data_engineering/04_data_engineering.html#nbk-data-engineering-cost-real-time) quantifies the financial trade-off between these two operational regimes.

**Napkin Math 4.3: The cost of real-time**

**Problem**: A pipeline ingests 1M events/s. Which is cheaper, Batch (hourly) or Stream (sub-second) ingestion?

**Physics**:

1.  **Throughput**: At 1M events/s and 1 KB per event, the pipeline carries 1 GB/s.
2.  **Stream requirements**: To sustain 1 GB/s with less than 100 ms latency, the design assumes each core can parse, validate, and update features for about 20 MB/s of events, which takes 50 primary cores. A standby core for each provisions recovery capacity, for 100 always-on cores in total, although latency under failure and recovery must still be measured. Running those cores for 24 hours/day at \$0.05/hr costs \$120/day.
3.  **Batch requirements**: Process 3.6 TB (1-hour window) in 10 minutes. That is 6 GB/s in aggregate. Sequential reads over large files let each core sustain about 30 MB/s, more than a streaming core handling events one at a time. The batch design therefore needs 200 cores for 10 minutes per clock hour, accumulating 800 core-hours per day. At \$0.05/hr, that costs \$40/day.

**Systems insight**: Under these provisioning and per-core throughput assumptions, streaming compute costs approximately 3× as much as batch compute for the same data volume. This premium is justified when the value of subsecond latency exceeds the added cost.

The premium comes from this scenario’s provisioning assumptions and leaves out storage, buffering, and failover, so the choice still rests on the feature freshness that inference actually needs.

The ingestion paradigm also shapes how the downstream model trains. Batch ingestion naturally pairs with periodic retraining: data accumulates in storage, an automated job retrains the model on the updated corpus, and a verified checkpoint deploys to serving. Stream ingestion makes that batch boundary less natural, raising the possibility of continuous online learning, in which model weights update directly as events arrive. Continuous updates, however, introduce operational risks that batch checkpoints avoid. Sudden distribution shifts, corrupted records, or adversarial payloads from any public-facing input path can reach the model before any validation check catches them. Most production systems therefore decouple ingestion from training: they stream data into a durable buffer while training on validated batches, reserving continuous online updates for tightly bounded, low-risk domains.

**War Story 4.1: When users became the training set (2016)**

**Context**: In March 2016, Microsoft launched Tay, a Twitter chatbot designed to engage with users online and adapt its responses from public interactions ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-microsoft2016tay|Lee 2016]]).

**Mechanism**: Adversarial users coordinated toxic prompts and exploited a public interaction surface, including behavior that repeated user-supplied text.

**Impact**: Tay began tweeting abusive, racist, and misogynistic statements within 16 hours of deployment.

**Fix**: Microsoft suspended the chatbot 16 hours after launch, apologized publicly, and stated that a relaunch would require stronger safeguards against misuse.

**Systems lesson**: Public ingestion paths require adversarial-input controls. Otherwise, a feature that accepts user-generated content also becomes a security surface, and harmful inputs can propagate through the system within hours.

### ETL and ELT Comparison

^sec-data-engineering-etl-elt-comparison-2e2b

Batch or streaming decides when records arrive; the next decision is where they are transformed relative to persistent storage. If a pipeline strips out unparsed fields before writing to storage and a later model needs one of those fields, the team must replay months of upstream source logs; if it stores every raw payload first, the storage bill multiplies. Traditional extract, transform, load (ETL)[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn5|⁵]] ($\text{E} \to \text{T} \to \text{L}$) transforms records in an external engine before loading them into a data warehouse, a database built for analytical queries over large tables ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-ml-storage-systems-architecture-options-67fa|section 4.10.1]]). Extract, load, transform (ELT)[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn6|⁶]] ($\text{E} \to \text{L} \to \text{T}$) lands raw records in staging tables and transforms them inside the warehouse ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^fig-etl-vs-elt|figure 10]]). Where that boundary sits determines what each later schema change costs and how much raw data must be retained.

![[90 Assets/Volume I/04 Data Engineering/Generated Figure 3d57af61f6.svg]]

Figure 10: **ETL vs. ELT Architectural Paradigms**: The two paradigms differ in where the transformation boundary sits relative to storage. ETL enforces schema validation and cleaning before loading to protect warehouse quality, whereas ELT loads raw data directly into scalable storage, trading warehouse compute and footprint for flexible, repeatable re-transformations.

^fig-etl-vs-elt

In machine learning systems, the ELT pattern separates ingestion throughput from downstream feature engineering by writing raw, immutable events directly into scalable storage. Keeping those raw events preserves unparsed fields that may later prove useful, so teams can compute new features over historical data without re-ingesting external source streams. When transformation logic changes or a bug surfaces, engineers recompute features by querying the stored raw events rather than replaying upstream logs. The price is physical and operational: raw events take more storage, shared transforms repeat their work unless their outputs are materialized, and keeping unscrubbed raw payloads makes privacy and retention rules harder to enforce. Notebook [4.4](https://mlsysbook.ai/vol1/04_data_engineering/04_data_engineering.html#nbk-data-engineering-cost-transformation-placement) prices these trade-offs on a daily clickstream workload and finds that the answer turns on one accounting choice, whether ELT must keep its own raw copy in the warehouse.

**Napkin Math 4.4: The cost of transformation placement**

**Problem**: A team processes 10 TB of raw clickstream data daily and must compute user session features for 3 ML models, each requiring different aggregation windows (1-hour, 24-hour, 7-day). Which is cheaper, ETL or ELT?

**Accounting boundary**: Both designs serve the same aggregation windows and keep the same replayable upstream raw logs for 30 days, so that shared retention and its ingestion costs drop out of the comparison. ETL stores only the derived features in the warehouse, about 2 TB per model; ELT also keeps its own raw copy there, as when the warehouse cannot query the upstream log store in place, and computes features on demand.

**Math**:

1.  **ETL approach**: Transform before loading. Compute all three aggregation windows in a Spark cluster (a group of machines running a distributed data-processing engine) before loading into the warehouse.
    - Spark compute: 10 TB at \$5/TB = \$50/day
    - Storage: 3 transformed datasets, ~2 TB each = 6 TB at \$23/TB/month = \$138/month
    - Feature-definition change: Replay the retained source logs and rerun the pipeline, an assumed ~4 hours of machine time after the edit. The two designs state this change cost in different units (machine hours here, editing minutes below), so the comparison leaves it unquantified
2.  **ELT approach**: Load raw data first, transform in warehouse.
    - Storage: 10 TB raw/day, 30 days retention = 300 TB at \$23/TB/month = \$6,900/month
    - Query compute: 3 models, each with \$5/query of daily query cost over 30 days, totals \$450/month
    - Feature-definition change: Rewrite the SQL query (~30 minutes of editing time), then execute and validate it against the retained raw copy; execution time is not supplied

**Systems insight**: ETL saves \$6,762/month in storage. After normalizing Spark compute to a monthly cost, ETL totals \$1,638/month (\$1,500/month compute + \$138/month storage), while ELT totals \$7,350/month (\$6,900/month storage + \$450/month query compute), for a cloud-cost advantage of \$5,712/month before engineering labor. The other cost is feature-definition change, which a fair comparison measures as elapsed time from the start of an edit to validated, feature-ready output in each design, with engineer time for editing, supervising, and validating counted separately. Stable definitions favor this scenario’s lower ETL cloud bill; frequent changes favor ELT only if measured labor and reprocessing savings repay its additional raw copy.

Because raw retention rather than compute dominates ELT’s bill here, a lakehouse, which runs warehouse queries directly over the stored files, can reverse the comparison by querying the retained logs in place instead of keeping a second copy.

Production ML systems rarely use one pattern exclusively. Structured tables often flow through ETL for efficiency and compliance, while unstructured data pushes the ELT preference further. For deep learning workloads processing images, audio, or text, the “Transform” step often executes inside the ML framework’s data loader rather than in the warehouse at all, applying random crops, spectrogram generation, or text tokenization on-the-fly during each training epoch (one full pass over the training data). Materializing ten augmented variants upstream would increase a 50,000-image dataset to 500,000 stored copies, so ELT’s “load raw, transform late” principle extends naturally to the training loop itself.

Whichever pattern lands the records, integrating diverse sources remains the core ingestion challenge. Data may originate from databases, APIs, file systems, and IoT devices, each with its own format (relational rows, JavaScript Object Notation (JSON)[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn7|⁷]] documents, binary streams), access protocol, and update frequency. The systems principle is to standardize at the ingestion boundary: normalize formats, validate schemas, and present a consistent interface to downstream processing regardless of source. This boundary standardization separates the complexity of source diversity from the complexity of feature engineering, allowing each to evolve independently.

In the keyword spotter’s pipeline, backend ingestion takes in activated requests (the audio a device sends after it wakes), consented diagnostic clips, crowdsourced recordings, synthetic data, and logged device interactions that pass validation, for serving and training; always-on audio that never triggers the wake word stays on the device. Format normalization and segmentation into consistent durations run as an ETL stage before storage in training-optimized formats, while augmentation stays late-bound in the loader, where ELT’s flexibility pays off, and unparsable captures route to the error-handling path of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^sec-data-engineering-reliability-graceful-degradation-f83d|section 4.5.5]].

A record that arrives on time and parses cleanly is well-formed, but well-formed is not the same as trustworthy. A field can parse correctly and still carry a wrong value, a source can drift away from the distribution the model learned, and a label can be wrong while every type check passes. Deciding which records may proceed is the boundary’s next job.

### Quality Through Validation and Monitoring

^sec-data-engineering-quality-validation-monitoring-498f

Validation makes that boundary decision, enforcing the quality pillar where a defect is cheapest to stop before it cascades into features, models, and predictions ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-sculley2015hidden|Sculley et al. 2015]]). Stopping structural defects is not enough on its own: in a batch of crowdsourced wake-word recordings where a phone app update has silently halved the microphone gain on 15 percent of the clips, every file is still a valid audio file of the right length and sampling rate, so schema checks pass even though the clips are far quieter than anything the detector will hear in deployment. Catching such silent shifts requires pairing schema checks with statistical monitoring across the batch.

Checks at this boundary work at two speeds. A hard failure, such as a source that stops delivering or a batch that fails its schema, must halt the affected path at once. A gradual degradation, such as a feature’s null rate creeping from 1 to 5 percent, a rising duplicate rate, or delivery delays that exceed their service level, is flagged for investigation. The gradual kind is often the more dangerous, because it persists for days before anyone looks. Routing and escalating such alerts in production is an operational practice developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.06 Production Monitoring#^sec-ml-operations-production-monitoring-5e1b|Production Monitoring]]**.

Schema and latency alerts expose structural and timing failures, but a shift in a continuous quantity needs a statistical comparison with the training baseline. Tracking statistical properties captures whether serving data continues to reflect the training distribution. Rather than merely checking that individual values fall within predefined ranges, production systems maintain rolling statistics across operational windows. For continuous quantities such as a clip’s loudness or signal-to-noise ratio, the monitoring harness computes rolling empirical distribution functions, using nonparametric evaluations like the Kolmogorov-Smirnov test[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn8|⁸]] to detect when serving inputs diverge from the training baseline. Notebook [4.5](https://mlsysbook.ai/vol1/04_data_engineering/04_data_engineering.html#nbk-data-engineering-detecting-drift-with-k-s-test) works one example.

**Napkin Math 4.5: Detecting drift with the K-S test**

**Scenario**: Monitoring whether the loudness of incoming wake-word clips still matches the training baseline $({P_0})$, using a sample of recent clips $({P_t})$.

**Analysis**: Apply the Kolmogorov-Smirnov test to compare the empirical cumulative distribution functions:

1.  **Compute CDFs**: Calculate cumulative distribution functions for both datasets. At a given loudness, an empirical CDF gives the fraction of sampled clips that are at most that loud. Comparing those fractions at the same loudness shows how the two distributions differ.

2.  **Calculate statistic** $({\mathcal{D}_{\text{KS}}})$: Find the maximum absolute difference between the CDFs. Let ${F_{P_0}}({x_{\text{feat}}})$ and ${F_{P_t}}({x_{\text{feat}}})$ denote the empirical cumulative distribution functions of the training baseline $({P_0})$ and current serving $({P_t})$ datasets, evaluated at value ${x_{\text{feat}}}$.

$$
{\mathcal{D}_{\text{KS}}}= \max_{{x_{\text{feat}}}}|{F_{P_0}}({x_{\text{feat}}}) - {F_{P_t}}({x_{\text{feat}}})|
$$

3.  **Determine significance**: For two independent samples, compare ${\mathcal{D}_{\text{KS}}}$ to the critical value ${c_{\text{crit}}}$ based on training-baseline sample size ${n}_0$ and serving sample size ${n}_t$. The coefficient 1.36 is the large-sample approximation for significance level ${\alpha} = 0.05$, which means that if both samples came from the same distribution, a maximum difference above the critical value would arise by chance about 5 percent of the time.

$$
{c_{\text{crit}}}\approx 1.36\sqrt{\frac{{n}_0 + {n}_t}{{n}_0 {n}_t}}
$$

 **Result**: With sample sizes ${n}_0 = {n}_t = 1000$, the critical value is approximately 0.061:

$$
{c_{\text{crit}}}\approx 1.36\sqrt{(1000 + 1000)/(1000 \cdot 1000)}.
$$

 An observed maximum difference of ${\mathcal{D}_{\text{KS}}}= 0.08$ exceeds the critical value, so a gap this large is unlikely to be sampling noise and the test flags drift.

**Systems insight**: A drift test is useful only if crossing the threshold starts an investigation or retraining workflow rather than becoming another dashboard number.

The K-S test compares one continuous feature in one batch against the baseline, and it is one of several drift statistics. Operational monitoring repeats such comparisons over months, adds statistics that work on binned distributions, and separates the kinds of shift they reveal ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.13 Operational Data Health#^sec-data-engineering-detecting-responding-data-drift-509a|section 4.12.1]]).

Categorical features require different statistical approaches. Instead of comparing continuous distributions, monitoring systems track category frequency distributions. When new categories appear that never existed in training data, or when existing categories shift substantially in relative frequency, the system flags potential data quality issues or genuine distribution shifts. For example, the share of recordings from one phone model might jump after its launch. Statistical monitoring of this kind catches problems that schema validation misses entirely, although only outcome checks establish whether quality changed.

Running both record-level schema rules and distribution-level statistical checks without stalling ingestion requires splitting validation into synchronous and asynchronous paths. Schema validation executes synchronously as data enters the pipeline, rejecting malformed records immediately before they can propagate downstream. Modern tools like TensorFlow Data Validation (TFDV) ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-breck2019data|Breck et al. 2019]]) automatically infer these baseline schemas from training data, capturing expected data types, value ranges, and presence requirements.

This synchronous validation remains simple and fast, checking properties that can be evaluated on individual records in microseconds. More sophisticated validation that requires comparing serving data against training data distributions or aggregating statistics across many records must run asynchronously to avoid blocking the ingestion pipeline. Statistical validation systems typically sample 1–10 percent of serving traffic, enough to detect meaningful shifts while avoiding the computational cost of analyzing every record. These samples accumulate in rolling windows, commonly one hour, 24 hours, and seven days, with different windows revealing different patterns. Hourly windows detect sudden shifts like a data source failing over to a backup with different characteristics, while weekly windows reveal gradual drift in user populations or behavior.

Asynchronous comparisons also catch training-serving skew, in which training and serving compute the same feature differently and the model receives inputs unlike those it learned from. Detecting it means passing a sample of raw serving data through both pipelines and comparing the results ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-ensuring-trainingserving-consistency-c683|section 4.7.1]]). None of these schema, distribution, or parity checks protects the system if it lives only in an exploratory notebook; to guard the boundary continuously, the checks must be versioned and executed as code.

↩︎ Training-serving skew, as one of the ways ML systems fail without raising errors, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.07 When ML Systems Fail Silently#^sec-introduction-ml-vs-traditional-software-e19a|When ML Systems Fail Silently]]**.

↪ Deployment checks that compare training and serving feature distributions and block a release when they diverge are developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-skew-detection-cicd-e361|Skew detection in CI/CD]]**.

### Data Quality as Code

^sec-data-engineering-data-quality-code-1cca

A statistical check like the one that catches the halved microphone gain protects the pipeline only if it runs on every batch, so production teams write such checks down as code. Data expectation tests are the data counterpart of unit tests. In **data quality as code**, engineers use declarative libraries like Great Expectations or Pandera to express data contracts as executable test suites that run across pipeline stages. Deequ, built at Amazon, framed the same idea as unit tests for data and showed that it scales to very large datasets ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-schelter2018automating|Schelter et al. 2018]]).

Running these expectation suites inside the continuous integration and deployment (CI/CD) pipeline checks every ingested batch automatically and halts downstream training when a contract fails. A pipeline structured as data ingestion followed by data validation followed by training blocks deployment when validation catches an anomaly, such as a batch of wake-word clips recorded at 8 kHz in a 16 kHz pipeline, and raises an alert for investigation. Executable expectations catch properties a suite can encode; the remaining question is what valid-looking data can still get wrong.

**Systems Perspective 4.1: Mechanical vs. semantic quality**

In traditional software, many checks are *mechanical*. A type checker rejects a string passed where an integer is expected, without anyone having to say what the value means.

In ML systems, data quality also has a *semantic* dimension.

- **Mechanical check**: Validates schema and type constraints, such as verifying that `age` is a non-null integer.
- **Semantic check**: Validates distribution drift and statistical invariants, such as testing whether the mean or variance of `age` shifts unexpectedly.

A dataset can be mechanically perfect (no nulls, correct types) but semantically broken (for example, all users are suddenly 25 years old due to a default value change). Robust ML systems must validate both the container (mechanical) and the content (semantic).

Once validation becomes code, expectation suites become versioned artifacts alongside training code. When training code changes, expectation updates keep data contracts evolving with it. This coupling reduces the risk of silent divergence where code assumes data properties that the upstream pipeline no longer provides; [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^lst-data-expectations|listing 1]] demonstrates this pattern by defining explicit constraints on column ranges, nullability, uniqueness, and categorical sets.

``` python
import great_expectations as gx

# Create a data context
context = gx.get_context()

# Define an expectation suite as executable quality contract
suite = gx.ExpectationSuite(name="user_data_quality")
suite = context.suites.add(suite)

# Range validation: prevents physiologically impossible values
suite.add_expectation(
    gx.expectations.ExpectColumnValuesToBeBetween(
        column="age", min_value=0, max_value=120
    )
)

# Null detection: ensures primary key integrity for joins
suite.add_expectation(
    gx.expectations.ExpectColumnValuesToNotBeNull(column="user_id")
)

# Uniqueness: prevents duplicate training examples
suite.add_expectation(
    gx.expectations.ExpectColumnValuesToBeUnique(column="user_id")
)

# Categorical validation: detects unexpected values from upstream changes
suite.add_expectation(
    gx.expectations.ExpectColumnDistinctValuesToBeInSet(
        column="country_code",
        value_set=["US", "CA", "UK", "DE", "FR"],
    )
)

# Link the suite to a preconfigured Batch Definition and run validation
# (the Batch Definition connects GX to the training_users data asset)
validation_definition = gx.ValidationDefinition(
    name="training_users_validation",
    data=batch_definition,
    suite=suite,
)
validation_definition = context.validation_definitions.add(
    validation_definition
)
results = validation_definition.run()
if not results.success:
    raise ValueError(f"Data quality check failed: {results}")
```

Listing 1: **Data Quality Assertions**: A Great Expectations suite checks age range, identifier presence and uniqueness, and allowed country codes, then raises an error when validation fails.

^lst-data-expectations

These checks catch many schema-level production data issues before they reach training, including missing values, invalid ranges, type errors, and contract violations. Rejecting bad records, however, is only half of the boundary’s job; the pipeline itself must also stay up when upstream dependencies fail or formats shift mid-run.

### Reliability Through Graceful Degradation

^sec-data-engineering-reliability-graceful-degradation-f83d

While validation enforces the quality pillar on individual records, the reliability pillar governs what happens when an upstream service goes down in the middle of an ingestion run. It also governs what happens when a date field switches from `"YYYY-MM-DD"` to `"MM/DD/YYYY"` without tripping a basic string check, or when a traffic spike exhausts worker memory at peak load. **Graceful degradation** means planning for these faults in advance and handling them automatically so that the system keeps running under degraded conditions rather than crashing or silently corrupting model inputs.

Three kinds of fault recur in ingestion pipelines. Format and encoding drift, such as that re-formatted date string, slips past type checks while breaking date-based feature logic. Schema evolution[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn9|⁹]] occurs when upstream producers add fields, rename columns, or re-type values without coordinating with downstream consumers. Resource exhaustion builds more slowly as data volume outgrows provisioned capacity and then causes jobs to fail during peak traffic. The defenses follow how a fault shows up rather than what caused it. A brief upstream outage, or a peak that exhausts capacity for a moment, shows up as transient errors. Format drift and unannounced schema changes show up, when something catches them, as individual records that fail processing. An upstream service that stays down shows up as every call to it failing.

Transient errors are retried with exponential backoff (waiting one second, then two, then four) so that retries do not flood a service that is trying to recover. Records that still fail after their retries go to a **dead-letter queue (DLQ)**, a side store that holds records that fail processing so they neither block the main pipeline nor disappear ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-kleppmann2017designing|Kleppmann 2016]]). Reviewing the queue regularly turns it from passive error storage into a source of diagnoses, because its contents reveal schema violations that indicate upstream changes, edge cases the model should handle, and data quality issues that need source system fixes. In the KWS pipeline, routing failed or unparsable audio captures to an analysis queue rather than discarding them exposes new hardware revisions whose audio arrives in an unexpected encoding or underrepresented acoustic conditions that need targeted collection in future model iterations.

When a whole dependency fails rather than individual records, a circuit breaker ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-nygard2007releaseit|Nygard 2007]]) stops calling it after repeated consecutive failures and fails fast or takes a fallback path until a trial request succeeds. One failed feature service therefore does not stall every caller waiting on its timeouts. The ML-specific part of recovery is that fallback.

Even a pipeline on a single machine needs an explicit policy for an unavailable source, choosing among waiting for fresh data, serving a validated stale-feature fallback, and rejecting the request. Multi-tier fallback systems implement the middle option, providing degraded service when primary data sources fail by using cached or approximate features only when their age and quality satisfy a validated fallback contract. A recommendation system unable to compute user preferences from the past 30 days might fall back to preferences from the past 90 days if evaluation establishes acceptable recommendation quality with that representation. The allowable feature age and the model-quality contract determine which response is safe, and durable buffering alone does not make old inputs suitable for inference. If no fallback meets the contract, the system waits for fresh data or rejects the request.

With ingestion, validation, and these error handlers in place, the boundary admits records that are well-formed and checked. They still say nothing about what they mean. A wake-word recording that passes every check does not yet state which word was spoken, or where in the clip it begins and ends.
