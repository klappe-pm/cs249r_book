# V1-04.10 Physics of Data

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering|V1-04 Data Engineering]]

^sec-data-engineering-physics-data-cdcb

The throughput bound lives in the Data–Machine overlap, and it is physical. Moving a petabyte of training data across cloud regions incurs tens of thousands of dollars in egress fees and hours of network serialization delays. Source code is small enough to move freely, so the data-as-code principle explains what data does without explaining why moving it costs so much. The physics of data supplies that explanation by giving data measurable properties. **Data gravity** ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-mccrory2010datagravity|McCrory 2010]]) is the bandwidth, I/O, and latency cost of moving a large byte volume, the cost behind the principle ([[01 Books/Volume I - Foundations/01 Foundations/V1 Foundation Principles#^pri-data-gravity|2]]) that already decided where computation should run. **Task-relevant signal** is the learning value those bytes carry for the task. A third property, flow rate, decides whether those bytes reach the accelerator as fast as it consumes them, and the ResNet-50 scenario measures it.

![[90 Assets/Volume I/04 Data Engineering/Data Engineering Data Gravity Entropy 2f9e33b33c.svg]]

*Two-by-two quadrant with a data gravity axis increasing to the right and a task-signal axis increasing upward; the top-left cell is filled green and labeled high gain, while the other three cells are gray.*

*Returns peak where task signal is high and movement cost (gravity) is low.*

Engineering effort pays off most when early filtering and selection separate high-signal records from the rest before data gravity makes them expensive to move. Low-signal data (repetitive audio frames or duplicate samples) consumes host-to-accelerator bandwidth and memory capacity while teaching the model little. An efficient pipeline resolves this physical bottleneck by maximizing the task-relevant signal delivered per byte moved across the storage and interconnect hierarchy, an optimization that begins with the physical properties of the data itself.

### Data Gravity

^sec-data-engineering-data-gravity-adcb

Transferring a petabyte dataset across a 10 Gb/s link requires days of continuous transmission (${T} = {D_{\text{vol}}}/{\text{BW}} \approx 9.3 \text{ days}$), and even across a dedicated 100 Gb/s link, transfer latency and egress tariffs remain substantial enough to govern system design. That physical and economic cost is the data-gravity principle ([[01 Books/Volume I - Foundations/01 Foundations/V1 Foundation Principles#^pri-data-gravity|2]]) at work. Data gravity scales directly with data volume $({D_{\text{vol}}})$ and inversely with network bandwidth $({\text{BW}})$, so teams move compute to the data when suitable compute is available there. The same constraint underlies lakehouse storage architectures[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn20|²⁰]] ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-zaharia2021lakehouse|Zaharia et al. 2021]]), where query and preprocessing engines execute directly against shared object storage rather than repeatedly copying raw data across network fabrics.

↩︎ The data-gravity principle, which weighs shipping a dataset against shipping the computation to it, is established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.06 Cloud ML Computational Power#^sec-ml-systems-cloud-infrastructure-scale-f0b1|Cloud infrastructure and scale]]**.

**Napkin Math 4.7: The physics of data gravity**

**Problem**: A 1 PB training dataset resides in a US East data center, while a remote accelerator pod is available in US West. What transfer time and egress cost does remote training add, and when would suitable compute near the data avoid that overhead?

**Math**:

1.  **Network bandwidth**: 100 Gb/s $\div 8 =$ 12.5 GB/s.
2.  **Transfer time**: 1,000,000 GB $\div$ 12.5 GB/s = 80,000 seconds, approximately 22 h.
3.  **Cost**: 1,000,000 GB $\times$ \$0.02/GB = \$20,000. (Baseline: AWS data transfer out pricing, 2024.)

**Systems insight**: If training takes less than 22 h, data transfer takes longer than training. If training costs less than \$20,000 (approximately 5,000 TPUv4-hours), bandwidth costs more than compute. When suitable compute is available near the data, these transfer costs favor moving code to data. Smaller datasets make moving data to code more practical, but placement still depends on compute availability and comparative training time.

### Task-Relevant Signal

^sec-data-engineering-information-entropy-5622

A dataset containing one million identical images carries heavy data gravity yet adds no new observations beyond the first sample; repeated passes over that single image can nudge model weights slightly, but they supply no fresh evidence. Conversely, a curated collection of 10,000 diverse edge cases is small enough to move cheaply yet contributes rich supervisory signal. Physical storage measures raw bytes, whereas machine learning extracts **task-relevant signal**: evidence that helps the model learn the target task, rather than raw Shannon entropy, the number of bits needed to describe the bytes themselves. Comparing task-relevant signal with data gravity motivates a selection heuristic:

$$
\text{Data Selection Gain} \propto \frac{\text{Task-Relevant Signal}}{\text{Data Gravity}} \tag{3}
$$

 Task-relevant signal has no universal unit, so the ratio ranks candidate selections rather than producing a number. A team estimates a selection’s learning value by comparing held-out model quality with and without it, and keeps the selection only when that benefit justifies the cost of moving its bytes, with scoring, labeling, and training costs counted separately. Deduplication and the active learning of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.07 Data Labeling#^sec-data-engineering-scaling-aiassisted-labeling-9360|section 4.6.5]] can improve the ratio by removing redundant bytes and proposing informative examples for labeling, although an example that looks informative can also be ambiguous or corrupted, so the selection still requires validation.

^eq-data-selection-gain

↪ The information-compute ratio, which measures the learning signal each sample returns per unit of training compute, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.03 Measuring Data Value#^sec-data-selection-informationcompute-ratio-8c0b|The information-compute ratio]]**.

### The Feeding Problem

^sec-data-engineering-feeding-problem

Data gravity dictates the cost of moving data in bulk; **the feeding problem** dictates the cost of delivering it to execution units in real time. It is an input/output **flow rate** bottleneck: storage bandwidth fails to keep pace with compute throughput. The bottleneck is measured, not hypothetical. Profiling nine widely used vision and audio models found their training time often dominated by data stalls, time spent waiting for data to be fetched and preprocessed ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-mohan2021|Mohan et al. 2021]]). In production recommendation training, the data storage and ingestion pipeline has become a dominant constraint on training performance and capacity ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-zhao2022dsi|Zhao et al. 2022]]).

When data delivery and computation overlap, the bottleneck principle holds that a system runs only as fast as its slowest stage. Consider the chapter’s throughput workload, one A100-class accelerator training ResNet-50 on images. The accelerator’s peak arithmetic rate is 312 TFLOP/s, and one training step on one image costs about 24.6 GFLOP, roughly three times the cost of a single prediction because training must also work out how to adjust every parameter. Dividing the first by the second gives an arithmetic ceiling of about 12,682 img/s. In practice a well-tuned pipeline sustains about 3,200 img/s, roughly 25 percent of that ceiling, once layers that wait on memory and the synchronization between steps take their share.

Each image sits on disk as a 150 KB JPEG, so sustaining that rate requires storage to deliver 480 MB/s. When the attached volume supplies only 250 MB/s, compute units stall on I/O. The calculation assumes that every epoch reads its images from storage, as it does when the dataset is larger than host memory; [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-storage-bandwidth-budget-5d2a|section 4.10.3]] returns to datasets that fit in memory. The gap between required and supplied bandwidth defines **the feeding loss**, the throughput penalty from insufficient input supply, which directly degrades system efficiency $({\eta_{\text{hw}}})$. Storage supplies 250 MB/s of the 480 MB/s the sustained rate requires, so the pipeline can run at only their ratio of the sustained rate, and the share it loses is a modeled feeding loss of about 48 percent. The model assumes steady-state overlap, in which the loader fetches the next batch while the accelerator computes on the current one. It compares throughput with the sustained rate rather than the advertised peak, and it does not count all accelerator idle time.

↩︎ The bottleneck principle is established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^sec-ml-systems-bottleneck-principle-3514|The bottleneck principle]]**.

Which bytes are counted matters as much as how many. After decoding and conversion to an FP32 tensor, the same image occupies 602 KB, about 4 times its compressed size, so a loader that converts on the host moves 1.9 GB/s through host memory and across the host-to-accelerator link. Many loaders ship 8-bit pixels instead and convert on the accelerator to avoid that cost. Compression thus trades storage bandwidth for CPU decode work. A pipeline that caches pre-decoded tensors on disk to skip that work pays the full 1.9 GB/s at the storage tier instead, and it freezes the random crops that augmentation would otherwise vary from epoch to epoch. Applying the same supply-to-demand calculation gives a modeled throughput loss of 87 percent relative to the sustained baseline. Storage and delivery apply this slowest-stage bound to the storage tiers ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-storage-bandwidth-budget-5d2a|section 4.10.3]]) and then to the CPU decode workers ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-data-ingestion-8efc|section 4.10.4]]) without re-deriving it.

Distance costs energy as well as time. The farther data travels to reach the processor, the more energy moving it costs relative to computing on it.

**Systems Perspective 4.2: The energy cost of data movement**

The memory-wall analysis in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.03 Physical Constraints on Deployment#^sec-ml-systems-deployment-spectrum-71be|Physical Constraints on Deployment]]** implies a data-engineering principle: *moving one 32-bit value costs roughly 173× to 10,811× as much energy as the table’s FP32 multiply*, with the multiplier rising as the data leaves the chip. Later optimization chapters exploit the same cost gradient inside model and hardware design. Here, the question is how much energy the information flow from the external world already consumes before the model computes, at each level of the memory hierarchy ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^tbl-energy-movement-cost|table 6]]).

| **Operation**                   | **Energy (pJ)** | **Relative Cost** |
|:--------------------------------|:---------------:|:-----------------:|
| **32-bit FP Multiply**          |   3.7 pJ/FLOP   |     1$\times$     |
| **DRAM Memory Access (32-bit)** |     640 pJ      |       173×        |
| **Local SSD Access (32-bit)**   |    4,000 pJ     |      1,081×       |
| **Network Transfer (32-bit)**   |    40,000 pJ    |      10,811×      |

Table 6: **Energy Cost of Moving vs. Computing on a 32-Bit Value**: Each row gives the approximate energy per event at one stage of the data-movement hierarchy, with multipliers normalized to one 32-bit FP32 multiply. All rows use the same 32-bit width, so the ratios compare like-sized events. They do not by themselves prove which term dominates a complete workload; total energy also depends on the number of arithmetic operations and transfers. Arithmetic and DRAM rows follow Horowitz ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-horowitz2014|2014]]).

^tbl-energy-movement-cost

That gradient is why data locality dominates systems optimization. Each avoided transfer eliminates its corresponding movement energy, compounding across training epochs.

Because data movement incurs physical energy costs, data volume acts like physical mass. Removing 50 percent of training data through deduplication saves more than persistent storage capacity. It also eliminates energy expenditure across network, memory, and preprocessing stages. Filtering uninformative samples early is among the most effective architectural levers when I/O and communication dominate workload runtime.

**Checkpoint 4.3: The physics of data**

Data engineering is governed by physical costs. Check your intuition:

**Data gravity**: Why does a petabyte-scale dataset pull compute toward the data, and which assumption in the petabyte example (link speed, egress price, training duration) would have to change to reverse that conclusion?

**Energy cost of data movement**: Why does fetching a 32-bit value from DRAM, an SSD, or the network cost more energy than one 32-bit multiply, and what else (how many operations, how many transfers) must you know before saying which dominates a workload’s total energy?

**Task-relevant signal**: Why can a smaller, diverse dataset be more valuable than a large, redundant one?

The energy hierarchy and the signal-density heuristic converge on the same optimization lever, the Data Selection Gain of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^eq-data-selection-gain|equation 3]]. Every redundant or uninformative record removed early saves movement energy and interconnect bandwidth at each later stage without costing task-relevant signal. For the released dataset, these costs come due in delivery. Every training epoch moves it from storage, through the host, to the accelerator, and the feeding problem decides whether that movement keeps pace.

**Self-Check: Question**

1.  A machine learning team maintains a $1\text{ PB}$ raw training corpus in a US East cloud storage bucket and provisions a dedicated compute cluster in US West. The regions are connected by a dedicated $100\text{ Gbps}$ network fabric. Cloud egress pricing is \$0.02/GB, and the model training run takes $20\text{ hours}$. Under the chapter’s data-gravity reasoning, which conclusion is best supported by these numbers?

    1.  The team should stream the dataset remotely during training, because a $100\text{ Gbps}$ link guarantees that data movement cannot become the bottleneck.
    2.  The team should split the dataset evenly across regions, because cross-region placement automatically removes the need to evaluate transfer cost or placement constraints.
    3.  The team should first apply compression, because any realistic compression plan will make the transfer clearly cheaper and faster than colocating compute.
    4.  The ideal one-time transfer is about $22.2\text{ hours}$ and costs about \$20,000, so colocating or relocating compute near the data is worth evaluating, but the final decision still depends on compute availability, cost, and other deployment constraints.

2.  Assume decoded tensors must be read from storage at a sustained demand of $1.9\text{ GB/s}$, while the attached baseline block-storage path can supply only $250\text{ MB/s}$. Assume no compression or cache alternative changes this bound. Under this simplified feeding-loss model, what follows?

    1.  The storage bound reduces the sustained baseline throughput by about $87\%$ relative to its supplied demand, because the supply-to-demand ratio is $0.25/1.9 \approx 0.132$ and the feeding loss is about $1-0.132 \approx 0.87$.
    2.  The accelerator remains compute-bound, because storage throughput and tensor execution are independent once batches have been scheduled.
    3.  Increasing batch size alone removes the bottleneck, because larger steps always improve the ratio between storage supply and decoded-tensor demand.
    4.  The storage path is only modestly underprovisioned, so the waiting fraction must stay below $20\%$.

3.  Using the data selection gain relationship $\text{Gain} \propto \frac{\text{Task-Relevant Signal}}{\text{Data Gravity}}$, explain why removing $50\%$ redundant samples can have large systems value when the retained dataset still covers the task-relevant cases and the training schedule is held fixed in passes over the data. Why is quality validation still necessary?
