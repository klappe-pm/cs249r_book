# V1-04.08 Data Processing

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering|V1-04 Data Engineering]]

^sec-data-engineering-systematic-data-processing-aebc

The keyword spotter learns from audio features computed by a library on a training server, and it runs on a device whose feature code is written separately for a microcontroller. If the two compute the same features even slightly differently, the deployed model receives inputs unlike any it learned from, and nothing raises an error. Processing cannot add capability the data lacks, but it can silently remove capability the data has.

Processing turns labeled records into the features the model consumes, and consistency governs it. Transformations shared between training and serving must keep identical semantics, repeated operations must give the same result when retried, and the work must scale without losing track of what was done. Unlike a code refactoring, which must preserve a program’s behavior exactly, filtering or augmenting observations can change the learning problem itself, so each transformation needs an explicit contract stating what it may change and what it must hold fixed.

Training-serving inconsistency is one concrete form of the hidden technical debt that Sculley et al. ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-sculley2015hidden|2015]]) identify in production ML systems. In the KWS pipeline, transformations must standardize recordings across microphones, noise levels, and sampling rates while preserving the acoustic cues that distinguish wake words from ambient speech. The shared feature extraction must also keep the same semantics and fitted state on the server and on the device, with numerical differences held within a validated tolerance.

### Training-Serving Consistency

^sec-data-engineering-ensuring-trainingserving-consistency-c683

If a training script standardizes features using the training set’s mean and variance while the serving service recomputes those statistics on each incoming batch, both paths run the same code yet feed the model different numbers. Sharing feature code between training and serving is therefore not enough: parameters learned from the training data (normalization constants, encoding dictionaries, vocabulary mappings) must also be stored and reused during serving. This requirement is the **consistency imperative**.

**Definition 4.3: Consistency imperative**

***Consistency imperative*** requires equivalent transformation behavior and state across training and serving environments.

1.  **Significance**: An unvalidated discrepancy between training and serving features can change the model’s effective input and degrade prediction quality without a runtime error. Equivalent semantics, shared fitted state, and tested numerical tolerances therefore make preprocessing a stateful component of the model artifact itself.
2.  **Distinction**: Unlike data quality, which focuses on the cleanliness of a single record, the consistency imperative focuses on the alignment of the entire transformation pipeline.
3.  **Common pitfall**: A frequent misconception is that sharing code makes the two paths consistent. Identical code still diverges when each environment recomputes its own statistics, so consistency is a state synchronization problem.

Violating the imperative produces training-serving skew silently, because the model still accepts a numerically valid vector computed under different rules, so neither exception tracking nor latency monitoring registers the failure ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-sculley2015hidden|Sculley et al. 2015]]; [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-baylor2017|Baylor et al. 2017]]).

**Definition 4.4: Training-serving skew**

***Training-serving skew*** is the distributional divergence between the training and inference environments caused by inconsistent logic or state.

1.  **Significance**: It violates the consistency imperative and can cause silent accuracy degradation when the training and serving transformations compute different features from the same raw input.
2.  **Distinction**: Unlike data drift (which is an external shift in the environment), training-serving skew is an internal failure of the engineering stack.
3.  **Common pitfall**: A frequent misconception is that skew is “found” by looking for errors. In reality, it raises no exceptions; the system runs and the latency stays low, but the predictions are statistically wrong.

Pipeline parity tests detect the discrepancy between the two paths; outcome evaluation establishes its effect on predictions. Designing from serving constraints backward allows the team to test equivalent preprocessing on the target device and bound numerical differences before deployment.

**Checkpoint 4.2: Defensive processing**

Training-serving skew is a common cause of silent production degradation.

**Definition**: Can you define training-serving skew in terms of the training and live-request processing paths?

**Mechanism**: Can you explain why recomputing normalization means independently in training and serving can make live data look unfamiliar to the model?

**Invariant**: Can you explain how shared transformation logic and synchronized feature state reduce skew?

Data cleaning is the first stage where training and serving can diverge. Raw data frequently contains missing values, duplicates, or outliers that degrade model performance. Cleaning operations must be deterministic and reproducible: given the same input, they must produce the same output regardless of environment. This requirement shapes which cleaning techniques are safe to use in production.

Data cleaning encompasses **deduplication**, which merges repeated records so they neither overweight what the model learns nor leak across splits ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-lee2022|Lee et al. 2022]]), along with missing-value handling and normalization. In the KWS corpus, deduplication must catch more than identical files. One speaker’s repeated takes of a wake word are near-duplicates, and they must stay within a single split, or evaluation measures memorization of that voice rather than generalization. The matching rule and its threshold must be captured in code that runs the same way every time the dataset is rebuilt.

Outlier handling exposes a sharp operational split between batch training and online serving. During training, the pipeline can drop corrupted records or extreme sensor glitches so that a few bad values do not dominate parameter updates. At serving time, the response contract determines whether an invalid request may be rejected, routed to review, or answered with an abstention or request for another sample. Clamping features to bounded intervals (such as $[{\mu}- 3{\sigma}, {\mu}+ 3{\sigma}]$) is safe only when that transformation has been validated for the task and uses the fitted training parameters. A serving-time filter must judge each request against the fitted training statistics alone, never against other requests that happen to arrive at the same moment, or one user’s result would depend on another user’s input.

The validation monitors in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^sec-data-engineering-quality-validation-monitoring-498f|section 4.5.3]] also check transformed outputs. A rise in nulls after a join, unexpected duplicate records, or a shifted feature distribution can expose a transformation defect even when the raw inputs passed their checks.[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn15|¹⁵]] Comparing raw and transformed records across the same pipeline version helps localize the fault before changing the model.

Quality validation must enforce identical schemas and validation predicates across training and serving pipelines. While training environments can afford compute-intensive profiling passes over entire datasets, serving paths must execute lightweight assertion checks (such as type validation, range bounding, and required-field existence) within the request’s latency budget. Mismatches between training-time validation and serving-time assertions allow corrupted inputs to reach the model undetected.

↪ The cost of training-serving skew and the shared feature libraries and schema validation tests that enforce training-serving parity are developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^sec-ml-operations-principle-3-consistency-imperative-a292|Consistency imperative]]**.

Transformation techniques convert data from its raw form into a model-ready representation, but the systems risk lies in the parameters those transformations learn. Common transformation tasks include normalization and standardization, which scale numerical features to a common range or distribution. For example, square footage and room count may differ greatly in scale; normalization places them on comparable numerical ranges, though their influence still depends on the model and learned parameters ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-bishop2006pattern|Bishop 2006]]). Maintaining training-serving consistency requires that normalization parameters computed on training data be stored and applied identically during serving. Operationally, these parameters must be persisted alongside the model itself and loaded during serving initialization.

Preprocessing parameters fall under the same split-boundary rule as the data itself ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.02 Data as Code#^sec-data-engineering-data-engineering-dataset-compilation-0496|section 4.1]]). If the mean and variance, or a category vocabulary, are fitted on the entire dataset before it is split, statistics of the test examples flow into the transformation the model trains through, and the test score no longer measures generalization to unseen data. The pipeline therefore fits every transformation parameter on the training split alone and applies the frozen result to validation, test, and serving inputs.

The fit and apply paths in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^fig-preprocessing-fitted-state|figure 16]] separate learning a transformation from using it. This distinction keeps held-out data outside the fitting boundary while making the serving path reproducible.

For deterministic preprocessing shared by training and serving, parity tests compare transformed features for the same raw record under the released code and state. The tests declare a numerical tolerance where execution backends differ.

Beyond numerical scaling, transformations convert discrete inputs through categorical encoding, extract cyclical representations from timestamps, and construct derived spatial features. Categorical encodings must handle both the categories present during training and unseen categories encountered during serving. A reliable pipeline builds the vocabulary index exclusively from the training split, serializes this dictionary with the model artifact, and maps unknown runtime tokens to an explicit out-of-vocabulary (`<UNK>`) index. Omitting this mapping causes runtime dimension mismatches or silent index collisions during online inference.

Domain-specific feature engineering turns raw inputs into representations that expose informative signals directly to the learning algorithm ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-kuhn2013|Kuhn and Johnson 2013]]). Instead of requiring the model to discover non-linear combinations from scratch, engineered features encode domain structure directly. The audio features the keyword spotter uses, described later, are themselves engineered: they encode what is known about human hearing, so a small model does not have to learn it from data.

Feature engineering can be a high-leverage activity because it changes what signal the model can see. In some workloads, well-designed features improve performance more than another round of algorithm selection or hyperparameter tuning. That leverage must be balanced against the consistency requirements of production systems. Every engineered feature shared by training and serving must have equivalent behavior in both environments. Production systems therefore implement feature engineering logic in shared libraries or coordinated pipelines rather than reimplementing it independently. Many organizations centralize those shared definitions in a feature store, the storage layer that [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-feature-stores-bridging-training-serving-55c8|section 4.7.5]] defines, to reduce inconsistency across environments.

In the KWS pipeline, audio recordings collected across crowdsourced contributors, synthetic speech generators, and field captures arrive with wide acoustic variation. The raw audio contains the imperfections anticipated during problem formulation: environmental noise spanning quiet bedrooms to noisy kitchens, amplitude clipping from saturated analog-to-digital converters, gain differences across microphone hardware, and inconsistent sampling rates. Reaching the 98 percent detection target requires standardizing these inputs while preserving the short speech transients that distinguish wake words from ambient noise. Gain normalization is a specific trap. Normalizing each stored clip against its own peak uses information a streaming device never has, because the device hears continuous audio rather than finished clips. The training pipeline therefore applies only gain handling the device can reproduce as audio arrives, such as a reference level fitted once on the training split and persisted with the model like any other fitted state.

That boundary between batch training and live streaming also governs KWS audio quality screens. Unlike gain normalization, which alters the signal and must match what the device runs, admission checks on background noise (signal-to-noise ratio above 20 dB), audio clarity (frequency spectrum analysis), and speaking rate (wake-word duration within 500 ms to 800 ms) filter which recordings enter each training slice without changing the serving path. The pipeline flags recordings whose noise, duration, clipping, or distortion falls outside the scenario’s acceptance rules for review. These thresholds screen the clean baseline slice, while valid noisy or unusually timed speech remains in a separately labeled robustness slice consistent with the noisy data budgeted in the KWS design. Review distinguishes these coverage examples from corrupted recordings before rejecting a sample, stopping defects from spreading along the arcs traced in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.03 How Data Fails#^fig-cascades|figure 2]].

For every recording that passes those screens, feature extraction must convert raw waveforms into model-ready inputs while maintaining training-serving consistency. Raw audio waveforms (sequences of amplitude values sampled thousands of times per second) are high-dimensional, so KWS pipelines transform them into compact representations that emphasize the frequencies and temporal patterns most relevant to speech. [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^fig-spectrogram-example|Figure 17]] aligns three views of an audio sample across a two-second window: the raw amplitude waveform, the corresponding time-frequency spectrogram isolating high-power acoustic energy around 500 Hz, and a compact 13-coefficient MFCC approximation. These standardized feature representations, typically MFCCs or spectrograms,[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn16|¹⁶]] emphasize speech-relevant characteristics while reducing noise and variability across different recording conditions.

MFCCs reach that compactness in two steps, after a short-time Fourier transform (STFT) measures how much energy each short window of audio carries at each frequency. Mel-frequency analysis pools those measurements into a few dozen bands spaced the way human hearing resolves pitch, and a final transform compresses the band energies into 13 to 40 coefficients. Each step has parameters, such as the window length, the number of bands, and the number of coefficients, that the device must reproduce exactly. For edge devices, this pipeline collapses data volume by over an order of magnitude, allowing audio feature frames to fit inside the tight tens-of-kilobytes SRAM budgets of embedded coprocessors.

### Feature Computation Placement

^sec-data-engineering-feature-computation-placement-a998

Precomputing those MFCC frames once during ingestion lets training iterate at disk speed, but it freezes any random noise or pitch augmentation applied to the raw waveform. Computing them on the fly in the data loader keeps every epoch fresh at the cost of repeating the work and risking accelerator stalls. **Feature computation placement** decides which resource pays for a feature: storage pays when features are materialized on disk, while compute and latency pay when features are generated on demand.

When features are precomputed during ETL and stored on disk, training epochs read ready-made tensors without paying the transformation cost on every pass, and every run consumes the exact same values. That speed and reproducibility come at the price of storage footprint and rigidity: derived features must be stored alongside the raw data, and any change to feature logic requires recomputing the entire corpus before the next experiment can run. Computing features on the fly inside the data loader reverses the trade-off. Because only raw data is stored and transformations execute as batches are read, logic changes take effect immediately and random augmentations vary from epoch to epoch. The host CPU, however, repeats the work on every pass and can stall the accelerator if preparation falls behind.

In practice, production systems combine both approaches. Expensive, slowly changing representations, such as high-dimensional user embeddings (learned vectors that summarize each user) or multi-month historical aggregations, are precomputed offline and materialized in storage. Volatile, lightweight signals, such as session recency, interaction timestamps, or client-side telemetry, are computed dynamically in the data loader. The keyword spotter shows why placement is not a free choice. The clean features of each recording can be computed once and stored, but noise augmentation must be applied to the raw audio before feature extraction, so the features of augmented clips have to be computed in the loader on every pass. This split matches each feature’s placement to its rate of change, trading storage capacity against execution latency.

### Idempotent Transformations

^sec-data-engineering-building-idempotent-data-transformations-7961

Consistency and placement settle what a transformation produces and where it runs, which serves the quality pillar; the reliability pillar asks whether that transformation can safely run again after a crash. If a processing stage appends transformed records to a target table and a worker fails after writing its output but before acknowledging completion, the automatic retry runs the job a second time and writes duplicate records into the training set. **Idempotency**[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn17|¹⁷]] prevents that corruption by ensuring that applying an operation repeatedly has the same effect as applying it once. This property matters whenever jobs retry after node failures, engineers reprocess historical data to fix a bug, or the same records flow through multiple paths. Determinism is a related but distinct requirement: identical inputs and captured state should produce identical outputs.

In state-machine terms, an operation ${f}$ is idempotent if ${f}({f}({s})) = {f}({s})$. In storage systems, setting a register to an absolute value (${s}\leftarrow 1$) is idempotent, whereas incrementing a counter (${s}\leftarrow {s}+ 1$) or appending a row to an unkeyed log is not: each re-execution mutates system state. Distributed data pipelines execute across preemptible workers and unreliable networks where timeouts and node crashes trigger automatic retries. Rather than appending blindly, an idempotent pipeline enforces write semantics such as deterministic keyed upserts (insert if absent, overwrite if present) or atomic directory swaps, ensuring that repeated job attempts converge to the identical final dataset.

Managing partial pipeline failures requires clear state boundaries between stages. Decoupling stages with persistent intermediate checkpoints ensures that each phase can be retried independently without re-executing upstream work. For long-running jobs processing terabyte-scale corpora, checkpointing progress (such as completed file shards or the position reached in an input stream) bounds retry latency: a task failure after five hours of execution requires replaying only the unfinished shard rather than restarting the entire five-hour job. Each checkpoint must record an output and its completion marker together, so a retry never finds one without the other and neither drops nor repeats records.

Deterministic transformations are those that always produce the same output for the same input, without dependence on external factors like time, random numbers, or mutable global state. Transformations that depend on current time (for example, computing “days since event” based on current date) break determinism because reprocessing historical data would produce different results. The solution is to capture temporal reference points explicitly: instead of “days since event,” compute “days from event to reference date” where reference date is fixed and persisted. Random operations should use seeded random number generators where the seed is derived deterministically from input data, ensuring reproducibility.

Reliability in the KWS pipeline requires reproducible feature extraction. Audio preprocessing must be deterministic: given the same raw audio file, the same MFCC features are always computed regardless of when processing occurs or which server executes it. That determinism serves three needs. Debugging can always recreate the exact features of a problematic example, reprocessing after a bug fix produces consistent results, and different workers in a distributed job produce identical features from the same input. The processing code captures all parameters, such as the fast Fourier transform (FFT) window size, the hop length (how far each window advances), and the number of MFCC coefficients, in configuration versioned alongside the code, ensuring reproducibility across time and execution environments.

### Distributed Processing

^sec-data-engineering-scaling-distributed-processing-cb9b

A single server with 256 GB of RAM can process datasets of several terabytes when transformations stream data out-of-core from disk rather than loading the entire corpus into memory at once, yet a naive script that materializes intermediate copies in RAM will crash on a fraction of that volume. Scaling data processing therefore begins by exhausting single-machine efficiency before taking on the coordination costs of a cluster, while keeping transformation semantics unchanged. Libraries that stream data from disk and parallelize across cores extend familiar dataframe interfaces to multi-terabyte workloads. Before investing in distributed processing infrastructure, teams should use efficient data formats (Parquet[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn18|¹⁸]] instead of CSV), minimize memory allocations, apply vectorized operations, and exploit multi-core parallelism. The operational simplicity of single-machine processing (no network coordination, no partial failures, simple debugging) makes it preferable whenever one node can meet the deadline.

Within a single machine, parallelizing data ingestion across host CPU workers yields diminishing throughput returns whenever unpartitionable stages, such as sequential decompression or central database lock acquisition, limit concurrency. Amdahl’s law caps how much speeding up one part of a pipeline can improve the whole. Applied to host worker count, it means that even when 90 percent of a feature extraction pipeline parallelizes across workers, the speedup cannot exceed 10×. The serial stages keep their full duration however many workers share the rest, so eliminating serial I/O and single-threaded stages takes precedence over launching more worker processes.

↪ Amdahl’s law, the ceiling that untouched work places on any speedup, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^sec-hardware-acceleration-ai-hardware-acceleration-fundamentals-9b28|Anatomy of an Accelerator]]**.

#### Coordination Across Machines

^sec-data-engineering-distributed-cluster-extension

When a corpus or the number of concurrent feature rebuilds outgrows one server, processing crosses the single-machine boundary into a cluster, and three things change. Data locality becomes a design constraint, because a network link moves bytes far more slowly than a node reads the shard it already holds, so cluster frameworks send the computation to the data instead of the data to the computation. Network transfer becomes the dominant cost of any operation that exchanges whole records between machines rather than small summaries such as partial sums. Coordination becomes part of the work, because the machines wait on the slowest worker and must recover when one fails partway through a job. In that case the idempotent, deterministic transformations described earlier become essential rather than merely convenient.

The KWS pipeline crosses that cluster boundary only when many experiments rebuild features at the same time: the reference corpus fits on the local storage of one well-provisioned server, and routine development uses single-machine processing on sample subsets to iterate rapidly. Even when feature extraction fans out across workers, per-file extraction is embarrassingly parallel while end-to-end speedup remains bounded by shared storage bandwidth, metadata operations, scheduling, and output contention. At the opposite end of the scale spectrum, production deployment adds a strict 16 KB preprocessing-state budget alongside the 256 KB model-size limit, requiring careful footprint optimization so feature extraction fits on the device.

### Feature Stores

^sec-data-engineering-feature-stores-bridging-training-serving-55c8

The keyword spotter needs no feature store, because its features are computed on the device from audio alone. A fraud or recommendation model whose features come from user history, by contrast, faces two failure modes at once. In the first, data scientists compute features like `user_purchase_count_30d` with batch SQL queries in a warehouse during model development. During serving, an online microservice computes the same metric incrementally from an in-memory cache. Minor differences in timezone arithmetic, missing-value handling, or floating-point rounding cause offline and online features to drift apart. Worse, if the training query joins a historical transaction against the user’s current profile rather than the profile as it stood when the transaction happened, future information leaks into the training set.

Keeping the two paths consistent means serving historical feature values for training and current feature values for inference from a single shared definition. **Point-in-time correctness** and shared feature logic are the primary operational requirements that drive teams to adopt **feature stores**, which Uber’s Michelangelo platform popularized to eliminate this class of training-serving skew ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-hermann2017michelangelo|Hermann and Del Balso 2017]]).

**Definition 4.5: Feature store**

***Feature store*** is the architectural layer that centralizes the management of machine learning features, decoupling feature computation from consumption.

1.  **Significance**: It supports point-in-time-correct historical retrieval for training, which returns each feature as it stood at a past observation $({x_{t-\Delta}})$, and coordinated feature definitions for real-time inference on current features $({x}_t)$, reducing training-serving skew when timestamps, backfills, freshness, and synchronization are handled correctly.
2.  **Distinction**: Unlike a general-purpose database, a feature store is designed for dual storage modes: an *offline store* (columnar/batch) for training and an *online store* (key-value/low-latency) for serving.
3.  **Common pitfall**: A frequent misconception is that a feature store is only “a place to store data.” In reality, it manages feature definitions, values, and retrieval; transformation may run in the feature store, an offline store, or a separate batch or stream-compute engine.

Feature stores establish a single source of truth for feature definitions across the ML lifecycle. By registering a feature definition as a unified computation graph, the feature store evaluates the identical transformation across both historical batch data and live inference streams. This shared definition reduces one source of training-serving skew, but equivalent execution still requires synchronized fitted state, correct timestamps, and appropriate freshness. Those conditions must be tested across both retrieval paths. Centralization also enables organizational feature reuse: expensive representations, such as multi-dimensional user embeddings derived from months of interaction logs, are computed once and served to multiple downstream modeling teams.

↪ How feature stores are operated in production, including point-in-time retrieval and training-serving skew prevention at scale, is developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-feature-stores-c01c|Feature stores]]**.

To serve both access patterns, feature stores pair two storage engines. The offline store keeps columnar formats (such as Parquet) on object storage, a high-capacity networked service that holds whole files under keys, and it is tuned for multi-gigabyte sequential scans during batch training. The online store uses low-latency key-value databases (such as Redis), tuned for sub-10-millisecond point lookups during real-time inference. Automated pipelines synchronize the two engines by pushing batch-computed feature snapshots to the online store while streaming ingestion updates both stores continuously as new user events arrive.

Time-travel queries separate a true feature store from a simple cache. Training requires evaluating features as they existed at the exact moment of an event, rather than their current values. In a customer churn model, for example, training on a customer who churned on January 15 must use features computed on January 14, not current post-churn profile state.

Feature stores enforce point-in-time correctness using an **as-of join** (temporal join): for every observation at timestamp ${t_{\text{obs}}}$, the retrieval engine joins the most recent feature record whose update timestamp satisfies ${t_{\text{feat}}}\le {t_{\text{obs}}}$. Here ${t_{\text{feat}}}$ must record when the feature value became available in the store rather than merely when the underlying real-world event occurred. If a user action occurred before ${t_{\text{obs}}}$ but arrived late over the network or entered through a later backfill, the live serving path at ${t_{\text{obs}}}$ could not see it. Excluding records that were not yet ingested at ${t_{\text{obs}}}$ ensures that timestamp ordering prevents both training-serving skew and future-information leakage across the upstream feature tables.

Every processing choice in this section, from cleaning and scaling to placement, idempotency, and feature retrieval, leaves derived state that downstream training depends on. Whether features are computed in a loader, materialized in storage, or served from a feature store, the team must eventually be able to say exactly which recordings, labels, and transformation versions produced the dataset a model learned from. Recording that answer is the last step of building the dataset.

**Self-Check: Question**

1.  An engineer normalizes a numerical feature by computing standard $z$-scores: $x' = (x - \mu)/\sigma$. During production serving, how must the parameters $\mu$ and $\sigma$ be handled to satisfy the consistency imperative and prevent training-serving skew?

    1.  Persist the exact $\mu$ and $\sigma$ computed on the training dataset alongside the model artifact, loading and applying those fixed constants to live serving inputs.
    2.  Recompute $\mu$ and $\sigma$ dynamically over each incoming serving batch to ensure the live data is always centered at zero.
    3.  Discard $\mu$ and $\sigma$ entirely at inference time and rely on batch normalization layers inside the neural network.
    4.  Compute $\mu$ and $\sigma$ independently over a rolling 1-hour window of serving traffic to track seasonal shifts.

2.  A feature pipeline outgrows one server and its data is split into partitions across several machines. Which operation adds the least network transfer in the cluster compared with running it on one machine?

    1.  A join between two tables partitioned on different keys, because the database engine performs the join automatically.
    2.  A global shuffle that regroups every record by speaker identifier, because each record moves only once.
    3.  Computing a global mean, because each machine can reduce its own partition to a partial sum and count and send only that summary.
    4.  Gathering all partitions onto one coordinator machine before any processing, because a single machine avoids coordination entirely.

3.  Define idempotency in the context of data transformation pipelines and explain why idempotent operations (such as upserts) are essential for fault recovery in distributed ML pipelines.

4.  True or False: Using the identical Python preprocessing function in both training and serving code repositories is sufficient to eliminate training-serving skew.

5.  Order the following steps for keeping an audio feature transformation consistent between training and serving: (1) split the data into the appropriate training and evaluation partitions, (2) version the transformation code together with the fitted transformation state, (3) fit any transformation state, such as normalization or vocabulary parameters, using only the training partition, (4) reuse the same transformation or a validated equivalent during serving and check that outputs stay within an accepted tolerance.

6.  How does a feature store’s point-in-time correctness (time-travel join) prevent data leakage during offline training dataset generation?

    1.  It encrypts historical feature values so that model weights cannot memorize training labels.
    2.  It forces all features to be computed strictly in real time on the client device during model inference.
    3.  It converts all timestamps into UTC strings to prevent database indexing errors.
    4.  It reconstructs feature values exactly as they existed at the observation timestamp of each training event, preventing future feature values from leaking into historical training records.
