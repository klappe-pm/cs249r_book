# V1-04.11 Storage and Delivery

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering|V1-04 Data Engineering]]

Delivery is where the throughput bound is met or missed. On baseline cloud block storage, the ResNet-50 scenario of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|section 4.9.3]] already loses about 48 percent of its sustained training rate. Following that scenario to its end means choosing a storage tier that can sustain the accelerator’s rate, keeping the host processor between storage and accelerator from becoming the next bottleneck, and cutting the bytes each sample costs to move. The KWS data poses the same questions at smaller scale, for the multilingual reference corpus (23.4 million samples spanning 50 languages) and for the much smaller product-specific subset.

### Storage System Options

^sec-data-engineering-ml-storage-systems-architecture-options-67fa

The ResNet-50 job reads its images in long sequential scans, while a serving system fetches one feature vector per request. These opposing access patterns pull storage in two directions, and selecting a system means minimizing the data term $\left(\frac{{D_{\text{vol}}}}{{\text{BW}}}\right)$ of the iron law of ML systems for whichever pattern dominates. Every storage medium imposes physical constraints on bandwidth that determine the maximum speed of the training and serving pipelines.

Two storage performance metrics govern this optimization. **IOPS (input/output operations per second)** counts the distinct read or write requests a device can handle per second, bounding *random access* workloads such as fetching small batches of images or individual user profiles. **Throughput (bandwidth)** measures the volume of data transferred per second, typically $\text{IOPS} \times \text{Block Size}$, bounding *sequential access* workloads such as scanning a Parquet file for training.

Three architectures cover these patterns, and the ResNet-50 scan and the feature-serving lookup sit at opposite ends of the range. Conventional databases (online transaction processing (OLTP)) optimize for high IOPS with small, row-oriented blocks, strict ACID guarantees, and sub-millisecond point lookups. That profile fits online feature serving, such as a recommendation system fetching one user profile or an anti-fraud service querying historical transaction counts, but it wastes bandwidth on a training scan. The storage engine fetches entire rows even when the model consumes only 20 of 100 features.

Data warehouses (online analytical processing (OLAP)) organize tables by column rather than by row ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-stonebraker2018|Stonebraker et al. 2018]]), so a sequential scan reads only the required features, transferring one fifth of the uncompressed row payload when selecting 20 out of 100 columns. The format-efficiency calculation in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-formats-compression-partitioning-8b17|section 4.10.5]] quantifies this gain with a worked fraud-detection scenario. Warehouses suit feature engineering, batch aggregation, and tabular training, but they require structured schemas, handle raw audio, imagery, and free-form text poorly, and make schema changes during experimentation costly `ALTER TABLE` operations across billion-row tables.

Data lakes store structured, semi-structured, and unstructured data in native formats on high-capacity object storage and defer structure to query time, an architectural pattern known as schema-on-read.[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn21|²¹]] A ResNet-50 job can read raw JPEG files from a lake at sequential rates, while independent jobs impose their own schemas without coordinating migrations. The cost is that governance shifts from ingestion to retrieval. Without a metadata catalog recording lineage, update cadence, schema versions, and access policies, a lake degrades into a “data swamp,” a set of orphaned directories such as `userdata_v2_final` and `userdata_v2_ACTUALLY_FINAL` whose lineage and quality are unrecorded. Each storage architecture therefore optimizes for a distinct access pattern and lifecycle phase, as [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^tbl-storage|table 7]] summarizes.

| **Attribute**                | **Conventional Database**                  | **Data Warehouse**                      | **Data Lake**                                          |
|:-----------------------------|:-------------------------------------------|:----------------------------------------|:-------------------------------------------------------|
| **Purpose**                  | Operational and transactional              | Analytical and reporting                | Storage for raw and diverse data for future processing |
| **Data type**                | Structured                                 | Structured                              | Structured, semi-structured, and unstructured          |
| **Scale**                    | Small to medium volumes                    | Medium to large volumes                 | Large volumes of diverse data                          |
| **Performance Optimization** | Optimized for transactional queries (OLTP) | Optimized for analytical queries (OLAP) | Optimized for scalable storage and retrieval           |

Databases support the high-IOPS random access needed for real-time feature serving; data warehouses provide sequential throughput for batch training and feature engineering; and data lakes provide schema flexibility and cost efficiency for large-scale raw data retention. A poor match between system and workload can impose substantial performance penalties.

^tbl-storage

Each lifecycle stage also reads the same data in its own way: exploratory analysis samples it at random, training streams it sequentially at high throughput, and production serving issues low-latency point lookups. During initial development, iteration velocity and schema flexibility dominate raw throughput. The primary systems challenge is managing experiment revisions without exploding storage capacity: ten exploratory runs on a 100 GB dataset naively generate 1 TB of redundant copies. The metadata-pointer approach of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^sec-data-engineering-data-versioning-ml-reproducibility-16d0|section 4.8.2]] avoids this by decoupling version tracking from file storage. Governance policies reinforce this tiering by granting broad access to anonymized development datasets while restricting sensitive production data to encrypted, auditable access tiers.

During training, the access profile shifts toward sustained sequential throughput. Modern deep neural networks process large datasets across dozens or hundreds of epochs, making storage bandwidth the determinant of hardware utilization. Scaling the chapter’s ResNet-50 scenario to eight accelerators, each sustaining its per-device rate, gives 25,600 img/s and a sustained storage demand of 3.8 GB/s of 150 KB compressed images; staging decoded FP32 tensors instead would raise it to 15.4 GB/s. Storage tiers unable to sustain this rate idle the accelerators, inflating cluster operating costs.

End-to-end ResNet-50 training cannot shrink that demand by precomputing features, because its features change at every step. A model trained on the outputs of a frozen upstream encoder (a pretrained model whose outputs are reused as input features) can, and there the feature placement trade-off ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-feature-computation-placement-a998|section 4.7.2]]) becomes critical. Precomputing those representations delivers a 30× storage reduction (150 KB raw inputs reduced to 5 KB embedding vectors) but introduces staleness when the encoder updates.

Production inference reverses the optimization target from sequential bandwidth to low-latency random access. A recommendation service handling 10,000 req/s with a 10 ms SLA and 10 feature reads/request demands 100,000 IOPS. Local Non-Volatile Memory Express (NVMe)[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn22|²²]] storage can sustain this random-access rate within the latency budget; in-memory key-value stores such as Redis, distributed caches, and purpose-built feature stores buy headroom for tail latency, the delay of the slowest few requests.

Edge deployment imposes further physical boundaries: constrained flash storage, intermittent network connectivity, and non-disruptive model updates dictate tiered caching, where core models reside in local flash while reference data synchronizes asynchronously with cloud endpoints. In production, reverting a deployed model or comparing two models on live traffic depends on tracing each model to the exact dataset release from which it was trained.

Across exploration, training, serving, and the edge, no single storage technology fits every access pattern, so production ML architectures rarely select just one; mature systems combine all three, with databases serving point lookups, warehouses running feature extraction, and lakes holding raw captures and intermediate checkpoints.

### Storage Tiers and Cost

^sec-data-engineering-ml-storage-requirements-performance-1b0d

Beneath each of these systems sits a physical storage medium, and media span about three orders of magnitude in cost and nearly four in bandwidth. Mismatching the storage tier to the access pattern either inflates infrastructure costs with underutilized capacity or starves training accelerators during I/O stalls.

That spread survived a long collapse in absolute price. [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^fig-storage-price-trend|Figure 18]] traces the lowest recorded price per terabyte of each medium in constant 2020 dollars. Hard disk storage fell from about \$88B per terabyte in 1956 to \$10.6 in 2023, roughly 10 orders of magnitude, yet in 2023 DRAM still cost 42× as much as solid-state storage per terabyte, and solid-state storage cost 2.4× as much as hard disk. Capacity became cheap, but since the 1980s the gaps between tiers have not closed, so the choice of tier, rather than raw capacity, sets the cost of keeping a training job fed.

ML systems use tiered storage because no single tier is both cheap and fast ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^tbl-storage-performance|table 8]]). Under these 2024 assumptions, storing the KWS reference corpus (748.8 GB) in object storage costs \$17.2/month, enabling affordable raw-audio retention, while working datasets on NVMe cost \$74.9/month–\$224.6/month for active training but load 50× faster.

In wall-clock terms, that 50× bandwidth gap changes the input-loading component of engineering iteration time on the same KWS corpus: loading at 5 GB/s on local NVMe completes in 149.8 s, compared to 7,488 s over a single object-storage stream. That loading speedup translates into shorter experiments only to the extent that exposed I/O contributes to their duration, since transformation and model execution still consume time.

Beyond input datasets, storage must hold what training produces: the model’s learned parameters, the extra bookkeeping values training keeps for each one, and periodic checkpoints (saved snapshots) of both. Modern neural networks contain millions to hundreds of billions of parameters, imposing storage and retrieval patterns distinct from tabular data. GPT-3 ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-brown2020language|Brown et al. 2020]]) requires approximately 700 GB for model weights when stored in FP32 format (175B parameters times 4 bytes), though practical deployments often use smaller numeric formats such as FP16 (350 GB) to halve memory pressure. Reading and writing those weights in parallel during startup and checkpointing demands aggregate storage bandwidth approaching network fabric limits (25 to 100 Gbps) to keep compute units active.

↪ Quantization, which shrinks these weight footprints by storing parameters at lower precision, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-quantization-precision-cd46|Numerical Precision: Changing How Values Are Stored]]**.

Tracking these artifacts introduces versioning challenges. Git’s incremental text diffs fail on multi-gigabyte binaries, where a single weight update produces an entirely new file and ten historical checkpoints of a 10 GB model occupy 100 GB. Production workflows therefore keep lightweight content hashes in Git and the binaries in content-addressed object storage, the same decoupling that [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^sec-data-engineering-data-versioning-ml-reproducibility-16d0|section 4.8.2]] applies to datasets.

Multi-accelerator training compounds storage pressure through concurrent I/O. When a training job spans multiple accelerators, every training process (one per accelerator) reads training batches concurrently, and the job periodically writes checkpoints of the parameters and bookkeeping values, often from a single process, in bursts that compete with those reads. Storage must absorb reads that scale with the worker count and checkpoint bursts on top of them, preventing I/O serialization that leaves expensive accelerators idle.

↪ The data- and model-parallel strategies that coordinate these workers within one node are developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-singlenode-multigpu-training-c87f|Single-node multi-GPU training]]**.

### The Storage Bandwidth Budget

^sec-data-engineering-storage-bandwidth-budget-5d2a

Each storage tier sets its own ceiling on the feeding problem of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|section 4.9.3]]. Host RAM delivers 50 to 200 GB/s on modern server nodes, local NVMe SSDs deliver 5–7 GB/s, and network-attached storage provides 1 to 10 GB/s. Whichever tier serves the training reads caps the data supply rate, so the design question is which tier can sustain the chapter’s ResNet-50 scenario, and at which of its two rates.

**Napkin Math 4.8: Storage bandwidth budget**

**Problem**: What storage configuration keeps an A100-class accelerator from being data-starved while training ResNet-50? **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]** explains why delivered throughput falls short of an accelerator’s advertised peak; here, the point is how a compute ceiling becomes a data-path budget.

Start with the compute ceiling derived in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|section 4.9.3]]. The A100’s 312 TFLOP/s divided by about 24.6 GFLOP per training image gives 12,682 img/s.

That compute ceiling becomes a storage requirement once each image must arrive from disk or object storage. Storage reads compressed bytes, so the budget uses the 150 KB JPEG rather than the decoded tensor: feeding the ceiling takes approximately 1.9 GB/s, while the 3,200 img/s that the accelerator actually sustains takes 480 MB/s.

Three storage options can now be compared against these two targets:

- S3 Standard delivers about 100 MB/s per connection when it streams large objects such as sharded archives, so feeding the ceiling needs 19 concurrent worker threads before software overhead. Fetching each 150 KB image as its own object is latency-bound and delivers far less.
- SATA SSDs deliver about 500 MB/s sequentially, enough for the sustained rate but a bottleneck at the ceiling.
- NVMe SSDs deliver approximately 5–7 GB/s, which covers the ceiling with headroom.

**Systems insight**: A SATA SSD caps the pipeline at 500 MB/s divided across 150 KB images, or approximately 3,333 img/s. That clears the sustained 3,200 img/s, so a faster drive buys nothing at today’s rate. Once faster kernels or a faster accelerator push the rate toward the ceiling, the same drive holds an A100-class accelerator to 26 percent of it. Each fix to the slowest stage exposes the next, so the storage tier must be sized for the rate the pipeline is heading toward, not the rate it runs at today.

The notebook’s 500 MB/s figure is effective SATA III sequential read throughput (the interface ceiling is 550 MB/s), and real-world random read performance with small files can be significantly lower. Designing for high-throughput training starts by matching storage throughput to accelerator demand, the storage-tier form of the slowest-stage bound that [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|section 4.9.3]] measured as lost training rate.

All of these comparisons apply one general bound. Let ${R_{\text{train}}}$, ${R_{\text{compute}}}$, and ${R_{\text{data}}}$ be rates in samples per second, ${\text{BW}_{\text{storage}}}$ storage bandwidth in bytes per second, ${f_{\text{overhead}}}$ the dimensionless fraction lost to overhead, and ${s_{\text{sample}}}$ the bytes per sample. [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^eq-training-throughput|Equation 4]] then limits training throughput by compute capacity and by the data supply rate defined in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^eq-data-supply|equation 5]].

$$
{R_{\text{train}}}\leq \min({R_{\text{compute}}}, {R_{\text{data}}}) \tag{4}
$$

$$
{R_{\text{data}}}= \frac{{\text{BW}_{\text{storage}}}(1-{f_{\text{overhead}}})}{{s_{\text{sample}}}} \tag{5}
$$

^eq-data-supply

^eq-training-throughput

Under full overlap, the min-of-rates form is the slowest-stage bound of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|section 4.9.3]] written as rates. Written as times, it becomes the step-time lower bound ${T_{\text{step}}}= \max({T_{\text{compute}}}, {T_{\text{IO}}})$ that [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-data-ingestion-8efc|section 4.10.4]] applies to host workers; with incomplete overlap, actual step time is higher.

Once ${R_{\text{data}}}$ is the smaller rate, additional accelerator compute cannot raise training throughput; the remedy must increase usable storage bandwidth or reduce bytes per sample. Like the feeding-problem calculation, the budget assumes every epoch reads from storage. A dataset that fits in host memory, as an ImageNet-sized dataset does on many eight-accelerator servers, is read from storage once and then served from the operating system’s page cache, so storage limits throughput only on the first epoch. The budget governs the cases that remain: datasets larger than memory, nodes whose memory several jobs share, and data streamed from remote storage.

When storage bandwidth becomes the limiting factor, teams must either improve storage performance through faster media, parallelization, or caching, or reduce the amount of data that must move. Large language model training may require processing hundreds of gigabytes of text per hour, while computer vision models processing high-resolution imagery can demand sustained data rates exceeding 50 gigabytes per second across distributed clusters. Prefetching hides the time to fetch the next batch behind the computation on the current one, but only when the loader sustains the required supply rate; it cannot create bandwidth that storage lacks. Provisioning a fast drive, however, solves only the first half of delivery, because compressed bytes from storage must still be decoded and transformed by the host processor before the accelerator can use them.

### The Dataloader

^sec-data-engineering-data-ingestion-8efc

Between storage and the accelerator sits the host processor, which reads each stored example, decodes it, augments it, and stages it for transfer. The barrier at this stage is the **input/output (I/O) bottleneck**: the accelerator idles whenever the host cannot stage examples as fast as the accelerator consumes them. The slowest-stage bound of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|section 4.9.3]] applies unchanged: in an idealized two-stage model, step time ranges from $\max({T_{\text{compute}}}, {T_{\text{IO}}})$ with full overlap to ${T_{\text{compute}}} + {T_{\text{IO}}}$ with no overlap. What changes is the limiting resource: while the initial feeding scenario was starved by baseline storage bandwidth, data loading on provisioned storage is more commonly starved by CPU-side decompression and decode ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-mohan2021|Mohan et al. 2021]]).

In computer vision, JPEG decode and augmentation on host CPUs are typically the limiting stage; in keyword spotting, MFCC extraction and audio augmentation load the same host threads. This host-side preparation executes within the framework’s data loader (such as the `DataLoader` of PyTorch, a widely used ML framework), which decodes and transforms raw records across parallel worker processes before staging batches for device transfer. Input-pipeline frameworks such as tf.data treat this stage as a system in its own right, with operators for parallel transformation, prefetching, and caching ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-murray2021|Murray et al. 2021]]).

To isolate CPU worker scaling, assume storage and bus transfers are provisioned to satisfy the 480 MB/s compressed input requirement, which a SATA solid-state drive does ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-storage-bandwidth-budget-5d2a|section 4.10.3]]). When storage and interconnect keep pace, the training pipeline depends entirely on whether CPU workers can match the accelerator’s sustained rate of 3,200 img/s. If each worker process transforms 375 img/s, 9 workers are required to reach the capacity crossing. Below this threshold the CPU input pipeline sets the rate, and adding accelerators yields no speedup, which surprises teams that expect compute investments to scale linearly. Above the crossing, launching additional workers produces no gain because the accelerator sets the rate. The worker count represents a capacity match rather than a hardware constant: actual ResNet-50 requirements on a given accelerator shift with image transformations, host processor architecture, batch size, and runtime configuration. [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^fig-dataloader-choke-point|Figure 19]] plots this capacity crossing, where the starved regime gives way to a compute-saturated plateau.

![[90 Assets/Volume I/04 Data Engineering/Cell 45 Output 1 dc372252c1.png]]

Figure 19: **The Dataloader Choke Point**: Training throughput (img/s) is plotted against DataLoader worker count, with storage and transfer provisioned above the required 480 MB/s rate. The blue CPU-supply curve rises with worker count until it reaches the illustrative input-pipeline cap; the red dashed line marks accelerator consumption capacity. The lower curve is the bottleneck: the accelerator starves to the left of the crossing, while extra workers beyond the crossing do not increase accelerator throughput.

^fig-dataloader-choke-point

At eight accelerators the worker count grows eightfold, more decode cores than many hosts can spare. Relieving the choke point takes three mechanisms. Multi-process worker pools scale decoding across host cores. Asynchronous prefetching copies the next batch to the accelerator while it computes on the current one. Hardware decode engines move image decompression off the host processor entirely. Hardware decode removes the host bound and hands the constraint back to storage bandwidth, where the remaining lever is the number of bytes each sample costs to move.

↪ How asynchronous prefetching and overlapping pipeline stages hide host preparation latency behind accelerator compute is developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-data-prefetching-pipeline-overlapping-e984|Data prefetching and overlapping]]**.

### Formats, Compression, and Partitioning

^sec-data-engineering-formats-compression-partitioning-8b17

Scanning a 100-column CSV file when the model uses only 20 columns wastes four-fifths of disk bandwidth on unused text, and opening millions of individual 150 KB JPEG files spends more time on filesystem seeks than on transferring bytes. File format sets the byte count and access pattern, so format selection directly scales the data term $\left(\frac{{D_{\text{vol}}}}{{\text{BW}}}\right)$ of the iron law. Columnar formats like Parquet excel for tabular features by allowing column projection and pushdown filtering, whereas shard-based sequential formats like WebDataset or TFRecord pack millions of small binary objects (such as images or audio) into contiguous sequential streams. This sharding eliminates random disk seek overhead (${L_{\text{lat}}}$), turning slow random I/O into sustained sequential storage throughput (${\text{BW}_{\text{storage}}}$).

The price is shuffling. Records within a shard arrive in order, so loaders approximate a random order by shuffling the shard list and mixing records in a buffer, and too small a buffer feeds the model correlated batches. Redesigning the format and the loader together pays off at the scale of this chapter’s lighthouse. One such system trains ResNet-50 on ImageNet to 75 percent accuracy in about 20 minutes on a single machine ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-leclerc2023ffcv|Leclerc et al. 2023]]). Quantifying the effect of format choice as *format efficiency* $({\eta_{\text{format}}})$ provides a multiplier on effective bandwidth.

**Napkin Math 4.9: Format efficiency**

Storage formats determine how much “waste” data must move to retrieve the signal needed for training. Let ${\eta_{\text{format}}}$ be the dimensionless fraction of bytes read that carry selected features, from 0 to 1. [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^eq-effective-bandwidth|Equation 6]] shows how that fraction scales physical bandwidth into usable pipeline bandwidth:

$$
\text{Effective Bandwidth} = \text{Physical Bandwidth} \times {\eta_{\text{format}}} \tag{6}
$$

 Values below 1 mean the format spends part of the physical data path on irrelevant bytes. Improving storage layout can therefore raise usable throughput without changing the underlying storage device.

^eq-effective-bandwidth

**Scenario**: Training a fraud model using 20 features from a 100-column table, assuming equal uncompressed byte size per column.

Row-oriented formats (such as CSV) must read all 100 columns to retrieve the 20 required features, giving a useful-byte fraction of 0.2 and wasting 80 percent of disk bandwidth. Conversely, column-oriented formats (such as Parquet) read only the selected columns, achieving ${\eta_{\text{format}}}\approx$ 1 (ignoring metadata overhead) and delivering 5× higher effective throughput.

**Systems insight**: In this projection-only scenario, switching from CSV to Parquet provides the same effective read-throughput gain as a 5× faster data path.

Columnar storage formats such as Parquet or Optimized Row Columnar (ORC) cut I/O for typical ML workloads by 5$\times$ to 10$\times$ through two complementary mechanisms: column projection, and column-level compression that exploits repeated values within a column. Compression is particularly effective for categorical features with few distinct values. A country code column with 200 unique values across 100 million records compresses 20$\times$ to 50$\times$ by storing each distinct code once and replacing every occurrence with a short reference to it. Measured against an uncompressed row format, projection and compression together cut I/O by 20$\times$ to 100$\times$, which shortens training epochs and shrinks storage footprints.

↪ How row and columnar layouts arrange records on disk, and how projection pushdown reads only the selected column chunks, are collected for reference in **[[05 Reference/Volume I - Foundations/V1 Data Foundations#^sec-appdx-data-foundations-row-vs-columnar-formats-bca2|Row and columnar formats]]**.

Compression algorithms trade storage density against CPU decompression bandwidth. While gzip achieves higher compression ratios of 6$\times$ to 8$\times$, Snappy achieves 2$\times$ to 3$\times$ compression but decompresses at 500 MB/s, roughly 4.2× faster than gzip’s 120 MB/s. Reading a 100 GB dataset compressed with gzip costs 13.9 minutes of CPU decompression per epoch, while Snappy costs only 3.3 minutes. Over 50 epochs, this 10.6 minutes difference per epoch compounds to 9 hours of host CPU time. That CPU time lengthens training only when decompression sits on the critical path, as it does when host-side decode is the limiting stage of the dataloader choke point. With spare host cores and prefetching, it hides behind accelerator compute. The trade reverses when storage bandwidth is the limit instead. Gzip’s higher compression ratio means fewer bytes per sample cross the storage path, which raises ${R_{\text{data}}}$ in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^eq-data-supply|equation 5]], so the right codec depends on which stage limits throughput. Snappy suits a CPU-bound loader, and a denser codec suits a storage-bound one.

Parquet defines the columnar layout on disk, and the Apache Arrow standard plays the same role in memory. It defines one columnar layout that ingestion engines, dataframes, and ML frameworks all read directly, so data passes between them without being converted to a new format at each handoff.

↪ Illustrative CPU decoding throughput and deserialization cost across storage formats are collected for reference in **[[05 Reference/Volume I - Foundations/V1 Data Foundations#^sec-appdx-data-foundations-cost-serialization-b921|Serialization cost]]**.

Beyond format and compression, data partitioning governs retrieval efficiency by aligning storage layout with common access patterns. The KWS corpus can be partitioned by speaker and recording date, so a training run can select a slice without scanning the whole corpus, and the speaker key that assigns splits also governs the storage layout.

Partitioning strategies interact directly with distributed training. Range partitioning by user ID routes each user’s records to one training worker (one of several that each process a different slice of every batch), which feeds each worker a skewed stream rather than a representative sample. Random partitioning mixes records from the source pool across workers under the sampling policy. It does not remove correlations already present in that pool or prevent leakage between evaluation splits; speaker grouping and other independence constraints must be enforced separately. Granularity matters: too few coarse partitions limit parallel worker concurrency, while millions of tiny shards add heavy metadata overhead and break sequential disk prefetching.

In multi-accelerator training, partition skew creates stragglers. If seven workers in an eight-accelerator job finish loading their batch in 12 ms but one worker reads from an oversized partition and takes 180 ms, that single slow worker, a straggler, holds up the whole job, because every worker must finish its batch before the next training step begins. Balanced partitioning that matches worker read budgets therefore keeps accelerator efficiency high.

Format, compression, and partitioning complete the delivery path by cutting the bytes each sample costs to move and keeping worker shards balanced. With a storage tier sized for the accelerator, the host matched to its rate, and bytes per sample reduced, both scenarios now have every stage of the pipeline in place, and each can be checked against the targets it started with.
