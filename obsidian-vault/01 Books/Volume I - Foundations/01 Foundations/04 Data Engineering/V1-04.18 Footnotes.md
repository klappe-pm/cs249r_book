# V1-04.18 Footnotes

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering|V1-04 Data Engineering]]

^footnotes

<sup>1</sup> **SoC always-on island**: Modern system-on-chip designs partition power domains so a low-power “always-on” island (typically achieving sub-milliwatt draw) monitors for wake triggers while the main processor sleeps. The critical constraint is that this island must hold both the model weights *and* the audio preprocessing code within its dedicated SRAM, a split budget that forces KWS architectures to optimize for total footprint, not just parameter count.

^fn1

<sup>2</sup> **MFCC (mel-frequency cepstral coefficients)**: Mel-scale filtering gives this representation its compactness and noise resistance by emphasizing the frequencies humans use to distinguish speech. MFCC extraction reduces the hundreds of raw samples in a short window (400 samples in 25 ms at 16 kHz) to 13–40 coefficients, so each frame fits inside an always-on, kilobyte-scale memory budget. A parameter mismatch between training and serving gives the model inputs unlike those it learned from, which can degrade accuracy.

^fn2

<sup>3</sup> **ImageNet**: The 2009 paper reported 3.2 million images across 5,247 synsets; the full database later reached about 14.2 million images across 21,841 synsets, whereas the challenge used a 1,000-class subset ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-deng2009|Deng et al. 2009]], [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-imagenet-website-32504219|2024]]; [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-russakovsky2015|Russakovsky et al. 2015]]). Its value as a benchmark is inseparable from its data engineering: Fei-Fei Li’s team built labeling infrastructure that later teams could reuse. The catch is sensitivity to annotation procedures and modest distribution shifts: models tuned to ImageNet’s distribution can underperform on related but shifted test sets ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-recht2019imagenet|Recht et al. 2019]]; [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-beyer2020we|Beyer et al. 2020]]).

^fn3

<sup>4</sup> **Amazon Mechanical Turk (MTurk)**: A crowdsourcing platform that routes small tasks to distributed workers and can scale annotation beyond expert-only workflows. Snow et al. ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-snow2008|2008]]) evaluate this pattern for natural-language annotation tasks, showing that non-expert annotations can be useful when task design and quality control are handled carefully. For wake-word audio collection, the same systems trade-off appears in domain-specific form: scale is attractive, but submissions still need acoustic checks such as signal-to-noise ratio, duration, and recording validity before they can safely enter the training set.

^fn4

<sup>5</sup> **Extract, transform, load (ETL)**: Conventional ETL validates deterministic schema constraints, whereas ML ETL must additionally monitor distributional properties using the statistical drift tests developed in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^sec-data-engineering-quality-validation-monitoring-498f|section 4.5.3]]. A detected shift prompts investigation and validation against labeled outcomes before concluding that model quality has degraded. When feature computation logic changes, reprocessing costs depend on replay scope, windowing, and execution plans rather than requiring an unconditional full-dataset pass.

^fn5

<sup>6</sup> **Extract, load, transform (ELT)**: This approach stores raw data before transformation, allowing teams to revise a transformation query and rerun it over the stored input without re-ingesting from source systems. The iteration time still depends on data volume, query complexity, warehouse capacity, and materialization strategy.

^fn6

<sup>7</sup> **JSON (JavaScript Object Notation)**: The schema flexibility that makes JSON a common format for APIs creates a validation bottleneck at the ingestion boundary. Unlike binary formats with predefined schemas, every JSON document requires parsing and schema validation before it can be standardized for downstream use. This per-record overhead can make ingestion slower than with binary formats such as Protobuf; the difference depends on the schema, parser, payload, and workload.

^fn7

<sup>8</sup> **Kolmogorov-Smirnov (K-S) test**: A nonparametric test that measures the maximum distance between two empirical cumulative distribution functions without assuming a parametric distribution family ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-berger2014kolmogorov|Berger and Zhou 2014]]). In ML pipelines, the K-S test is commonly used as a univariate continuous-feature drift detector, with thresholds such as ${p_{\text{val}}}< 0.05$ serving as investigation triggers rather than universal failure rules. Discrete and categorical variables require tests and calibrations appropriate to their distributions.

^fn8

<sup>9</sup> **Schema evolution**: This failure mode arises from a lack of contract testing between upstream data producers and downstream ML consumers. While “loud” failures like a renamed column break explicit assumptions and cause immediate pipeline crashes, “silent” failures are more dangerous. A field changing type from integer to string can pass validation but corrupt feature logic without immediate detection.

^fn9

<sup>10</sup> **Ground truth**: From remote sensing, where orbital measurements are verified by sending a team to the physical location (the “ground”) to establish the “truth.” The etymology carries a systems warning: ML labels are proxies for reality, not reality itself. When a crowdsourced annotator labels an image as “cat,” that label reflects the annotator’s judgment, not an objective fact. Every downstream metric, including accuracy, is measured against this proxy, meaning label quality errors propagate silently into every evaluation of the model.

^fn10

<sup>11</sup> **Pricing ratios**: Cloud and labeling prices reflect provider policy and labor markets, not physical invariants, so the ratio between labeling and compute moves whenever either side reprices. Storage adds its own policy multipliers: archive tiers such as the Glacier row in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.07 Data Labeling#^tbl-data-engineering-cost-constants|table 3]] charge more for faster retrieval. Verify current prices before using these ratios in a deployment decision.

^fn11

<sup>12</sup> **Cohen’s kappa**: Introduced by Cohen ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-cohen1960|1960]]) to measure inter-rater agreement while correcting for agreement expected from the raters’ class marginals, which raw percentage agreement ignores. If two independent annotators each label 90 percent of messages as “not spam” in a binary task, they agree by chance on “not spam” 81 percent of the time ($0.90^2$) and on “spam” 1 percent of the time ($0.10^2$). Their total expected chance agreement is 82 percent, making raw agreement potentially misleading. The statistic is denoted ${\kappa}$, and interpretive bands such as the Landis-Koch categories are descriptive heuristics rather than universal data-quality thresholds ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-landis1977measurement|Landis and Koch 1977]]).

^fn12

<sup>13</sup> **Weak supervision**: A “data programming” paradigm that exchanges some manual annotation labor for the upfront effort of writing and validating programmatic labeling functions. Once written, a function can be applied cheaply at scale, but execution, conflict resolution, quality monitoring, and maintenance still incur cost; the useful comparison is workload-specific rather than literally zero marginal cost.

^fn13

<sup>14</sup> **Forced alignment**: Given a known transcription, an aligner estimates where its words occur in the audio, often using frame-level acoustic scores and sequence decoding. Timing resolution and accuracy depend on the model, features, language, and recording quality, so boundary estimates still need quality checks. The known transcript makes word-level segmentation far cheaper than labeling every clip manually, though computation, review, and error correction remain.

^fn14

<sup>15</sup> **Statistical drift detection**: The means, variances, and quantiles tracked in quality monitoring are early-warning signals for the distance between the production and training distributions, the divergence term ${\mathcal{D}(P_t \| P_0)}$ of the degradation equation (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.07 When ML Systems Fail Silently#^eq-degradation|equation 1.1]]**). A mean session length shifting from eight to 12 minutes over six months may indicate drift; a sudden drop to three minutes may indicate a collection fault. Outcome checks and source investigation are needed before choosing retraining or a source-system fix.

^fn15

<sup>16</sup> **Spectrogram**: The short-time Fourier transform (STFT) computes this 2D representation by converting the one-dimensional waveform into a time-frequency image. This representation lets image-style ML models process audio, but it also creates a rigid dependency: a mismatch in STFT parameters (for example, a 25 ms vs. 30 ms window) changes the feature representation between training and serving and can degrade performance.

^fn16

<sup>17</sup> **Idempotency**: From Latin *idem* (“the same”) + *potens* (“having power”), literally “having the same power when applied again.” In ML pipelines, idempotency enables safe retries after partial failures: a nonidempotent operation (for example, appending to a log) creates duplicates on retry. An idempotent operation leaves the same resulting state after one application or repeated applications.

^fn17

<sup>18</sup> **Parquet**: A columnar storage format that organizes data by column, not by row. Where a CSV reader must parse every row in full to reach a few columns, a Parquet reader loads only the columns a computation needs. The resulting I/O reduction depends on the selected columns, encoding, compression, and workload.

^fn18

<sup>19</sup> **Data lineage**: When a model produces an erroneous or discriminatory prediction, lineage helps engineers determine whether the contributing problem originated in raw data, feature computation, training, or serving. The resulting trace can support incident investigation and jurisdiction-specific documentation duties, but its usefulness depends on complete instrumentation and retained history; it does not guarantee an explanation of model behavior.

^fn19

<sup>20</sup> **Data lakehouse**: Combines data lake storage (cheap, schema-less) with warehouse query semantics (atomic, consistent, isolated, and durable (ACID) transactions, schema enforcement) using transactional table layers such as Delta Lake. For ML workloads, the lakehouse reduces the ETL copy between lake and warehouse, enabling direct feature computation on the storage layer where data already resides. This is a direct response to data gravity, since repeated petabyte-scale copies increase the ${D_{\text{vol}}}/{\text{BW}}$ cost ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-armbrust2020|Armbrust et al. 2020]]; [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-zaharia2021lakehouse|Zaharia et al. 2021]]).

^fn20

<sup>21</sup> **Schema-on-read**: Applies data structure definitions at query time rather than during ingestion, contrasting with schema-on-write (traditional databases) where data must conform to a predefined structure before storage. For ML pipelines in early development, schema-on-read enables rapid experimentation, because teams can store raw sensor data, images, and logs without committing to a feature schema upfront.

^fn21

<sup>22</sup> **NVMe (Non-Volatile Memory Express)**: A storage protocol designed for solid-state drives, delivering 5–7 GB/s sequential throughput and microsecond-scale latency. The contrast with SATA SSD (500 MB/s) is a 10× bandwidth gap that can bottleneck a training pipeline when storage service time exceeds compute time.

^fn22

<sup>23</sup> **ML failure distribution**: Treat the data-dominance pattern as a practical triage rule rather than a universal law. Data and pipeline checks are good first hypotheses, but they do not rule out code defects, hardware communication bottlenecks, or numerical instability.

^fn23
