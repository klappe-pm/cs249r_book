# V1-04.09 Dataset Release

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering|V1-04 Data Engineering]]

^sec-data-engineering-dataset-release-7c4e

Months after launch, the keyword spotter’s detection rate drops on a new hardware revision. The first question the team must answer is what the shipped model learned from, down to the recordings, the labels and the guideline they followed, the splits, and the feature code. A **dataset release** answers that question in advance. It is an immutable, versioned record of everything that produced a training set: the source records, how they were split and labeled, and the code and parameters that turned them into features. It is the versioned dataset that Stage 2 of the lifecycle hands to model development, and it turns the pipeline built so far into something that can be reproduced, compared, and audited.

The release is built from what each record carries. [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^tbl-data-engineering-kws-record|Table 5]] lists the fields of one KWS training clip and the question each field answers later. Two of them do most of the work. The split is assigned by hashing the speaker key, so every clip from a speaker lands in the same split in every release and a later relabeling pass cannot leak a test speaker into training. The label carries the version of the guideline it was made under, so a change in labeling rules can be told apart from a change in the data.

| **Field**                    | **Recorded value**                                         | **Question it answers later**                           |
|:-----------------------------|:-----------------------------------------------------------|:--------------------------------------------------------|
| **Recording ID**             | Content hash of the audio file                             | Is this clip a duplicate, and what was derived from it? |
| **Speaker key**              | Pseudonymous speaker identifier                            | Are all of this speaker’s clips in one split?           |
| **Consent record**           | Reference to the terms the clip was collected under        | May it be retained, and must it be deleted on request?  |
| **Split**                    | Train, validation, or test, from a hash of the speaker key | Is the split stable across releases?                    |
| **Label and rubric version** | Wake word or none, with the labeling guideline version     | Did the data change, or only the labeling rules?        |
| **Alignment version**        | Aligner version and word-boundary confidence               | Where could a segmentation error have come from?        |
| **Feature configuration**    | Window, hop, coefficient count, and processing code commit | Can the features be recomputed exactly?                 |

Table 5: **Anatomy of a KWS Training Record**: Each row names a field that one keyword-spotting training clip carries into a dataset release and the later question it answers. Speaker-keyed splits prevent leakage across releases, and rubric versions separate label changes from data changes.

^tbl-data-engineering-kws-record

Each record’s fields capture local provenance, while the release manifest ties the whole collection together. The rest of a release records how those fields were produced and pins the resulting dataset in storage so that any historical build can be recovered verbatim.

### Transformation Lineage

^sec-data-engineering-tracking-data-transformation-lineage-3b09

The last row of [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^tbl-data-engineering-kws-record|table 5]], the feature configuration, exists because recording the raw audio file and label is not enough if a later change to the MFCC window function leaves the team guessing which window the shipped model trained on. Governance, the fourth pillar, closes that gap by tracking what transformations were applied, when they ran, which version of processing code executed, and what parameters were used. This **transformation lineage** is the processing part of **data lineage**, the recorded trail that links each dataset, feature, and model to the sources, code, and parameters that produced it.[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.18 Footnotes#^fn19|¹⁹]] Transformation lineage supports reproducibility, debugging, auditability, and iterative improvement when transformation bugs surface. It can supply evidence for documentation or compliance workflows, but lineage alone does not explain a model’s decision or establish regulatory compliance.

That trail starts with transformation versioning, which records which version of the processing code produced each dataset. Whenever engineers change the transformation logic to fix a bug, add features, or improve quality, the version number increments, and tagging datasets with that version identifies every table or shard that must be reprocessed after a fix. Because identical source code can still produce slightly different floating-point outputs across different NumPy releases, runtime environment variables, or CPU instruction sets, each dataset also records the Git commit hash of the code that created it. A container image stored alongside it freezes the code, dependencies, and system libraries in one immutable environment.

Code and environment versions still leave out the data-dependent state that transformations learn. Parameter tracking therefore records the fitted values applied during transformation: the mean and standard deviation computed on training data for normalization, the vocabulary (set of all observed categories) for categorical encoding, and any constants or thresholds used in feature engineering ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-ensuring-trainingserving-consistency-c683|section 4.7.1]]). Serializing these parameters alongside the model artifact ensures that serving applies the exact same values as training.

Processing lineage then joins code, environment, and fitted parameters into a complete execution history from raw data to final features: which raw files were read, what transformations ran in what order, what parameters were applied, and when the job executed. Lineage systems instrument the pipeline so that each job records these links as it runs, because a history reconstructed after an incident is rarely complete. When model predictions go wrong, engineers can trace back through the lineage graph to find the training data that contributed to the behavior, the quality scores attached to that data, and the transformations applied, then recreate the exact scenario for investigation.

In the KWS pipeline, governance applies to the audio processing parameters that affect model behavior. The reference volume level used for normalization is persisted. The Fourier transform and MFCC settings versioned with the processing code ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-building-idempotent-data-transformations-7961|section 4.7.3]]) are joined by the shape of each audio window, the frequency range, and the spacing of the mel bands. Recording them makes it possible to reproduce training data exactly when debugging model failures, to validate that serving uses preprocessing identical to training, and to study how preprocessing choices affect accuracy. Without this record, teams fall back on manual documentation that becomes outdated, which allows subtle training-serving skew.

### Data Versioning for ML Reproducibility

^sec-data-engineering-data-versioning-ml-reproducibility-16d0

Lineage records how a dataset was built, but reproducing or comparing two runs also requires recovering the exact bytes of each release. Without immutable snapshots, diagnosing why a keyword spotter’s measured detection rate fell takes days of guesswork across new recordings, changed labels, and upstream batches. With data versioning, engineers compare two dataset releases directly and can rule each candidate cause in or out. A comparison of the two releases shows, for instance, whether the labeling guideline version in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^tbl-data-engineering-kws-record|table 5]] changed between them, so that the same clips now carry different labels.

File-level versioning engines like DVC (Data Version Control) provide this link by pairing Git with content-addressed remote storage ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-dvc|Iterative 2024]]). Git tracks small text pointer files (`.dvc`) containing cryptographic hashes, while DVC synchronizes the underlying binary dataset to object storage ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^lst-dvc-workflow|listing 2]]). Checking out an earlier Git commit restores the historical pointers; the paired DVC retrieval step shown in the listing restores the dataset contents matched to that code state.

``` bash
# Add data to version control
dvc add data/training.csv
git add data/training.csv.dvc
git commit -m "Add training data v1"
dvc push  # Upload to remote storage

# Later: retrieve exact data for any historical commit
git checkout abc123
dvc checkout  # Restores exact data from that commit
```

Listing 2: **DVC Workflow**: DVC brings Git-like semantics to data versioning. DVC tracks large data files alongside code commits, enabling exact reproduction of any historical training dataset through paired `git checkout` and `dvc checkout` commands.

^lst-dvc-workflow

While file-level versioning suits bulk artifacts like images and audio, tabular datasets require versioning over tables that change row by row. Open table formats such as Delta Lake solve this by keeping an append-only transaction log of all row insertions, deletions, and schema changes ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.17 Source References#^ref-armbrust2020|Armbrust et al. 2020]]). This log supports time-travel queries that pin a dataset state by timestamp or version ID ([[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^lst-delta-time-travel|listing 3]]).

``` sql
-- Query data as it existed on a specific date
SELECT * FROM training_data TIMESTAMP AS OF '2024-01-15'

-- Or by version number for programmatic access
SELECT * FROM training_data VERSION AS OF 47
```

Listing 3: **Delta Lake Time Travel**: SQL queries identify a historical table state by timestamp or transaction-log version.

^lst-delta-time-travel

Two production components work with these versioning engines to complete end-to-end reproducibility. Feature store point-in-time retrieval evaluates features as they existed at the observation timestamp, preventing the leakage from future observations described in [[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.02 Data as Code#^sec-data-engineering-data-engineering-dataset-compilation-0496|section 4.1]]. A model registry records the lineage manifest for each deployed model: Git commit SHA, data version ID, training configuration, and evaluation metrics. In the keyword spotter’s regression, this audit trail turns an open-ended debugging investigation into a set of controlled snapshot comparisons.

↪ How the model registry promotes, holds, or rolls back the exact artifact that was evaluated is developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-versioning-lineage-b1cf|Versioning and lineage]]**.

Long-term retention balances auditability against storage cost and privacy rules. High-volume production pipelines use tiered retention: hot SSD tiers for active training and debugging, warm object storage for periodic evaluation snapshots, and cold archive storage for compliance records. Because keeping petabyte-scale data forever is too expensive and often violates privacy statutes, data lifecycle policies must set explicit retention windows and deletion schedules.

A release fixes what the dataset is, yet it says nothing about how fast that dataset can reach the accelerator during training. That is the second bound from the opening of this chapter, the one the remaining stages of the pipeline must meet.

**Self-Check: Question**

1.  In the chapter’s KWS dataset release, each clip’s split is assigned by hashing its speaker key rather than by drawing splits at random each time a release is built. What failure does this prevent?

    1.  A later release or relabeling pass could move some of a test speaker’s clips into training, so evaluation would reward memorization of that voice instead of generalization to new speakers.
    2.  Hashing compresses the audio so that each split fits in less storage.
    3.  Hashing guarantees equal numbers of keyword and non-keyword clips in every split.
    4.  Hashing removes the need to record a consent reference for each clip.

2.  A keyword spotter’s detection rate drops after a scheduled retraining even though no code changed. Explain how a dataset release that records label rubric versions, alignment versions, and feature configuration lets the team locate the cause.
