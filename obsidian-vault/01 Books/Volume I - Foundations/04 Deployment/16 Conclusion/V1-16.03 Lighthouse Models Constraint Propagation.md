# V1-16.03 Lighthouse Models Constraint Propagation

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/16 Conclusion/V1-16 Conclusion|V1-16 Conclusion]]

^sec-conclusion-lighthouse-constraint-propagation

Predicting how an engineering change propagates across layers starts with identifying which physical resource limits the workload. Each of the book’s five lighthouse models has a home regime defined by the resource it saturates first under typical operating conditions: ResNet-50 is compute-bound, decode for GPT-2 and Llama is bandwidth-bound, DLRM is capacity-bound, MobileNetV2 is compute-bound in its efficient regime, and keyword spotting (KWS) is power-bound. MobileNetV2’s efficient regime is the whole network running on the phone’s neural processing unit (NPU) it was built for, where a few watts buy little arithmetic.

Each regime names the lever that pays. Adding peak arithmetic throughput to a batch-one large language model (LLM) decoder leaves token latency untouched because every token waits on high-bandwidth memory (HBM) weight reads. Adding memory bandwidth to a batched ResNet-50 convolution instead buys nothing once its arithmetic intensity, the operations it performs per byte moved, sits right of the ridge point, the intensity at which the bandwidth ceiling meets the compute ceiling. Roofline modeling (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-3e1a|The roofline model]]**) turns that comparison into a quantitative upper bound on attainable speed ([[01 Books/Volume I - Foundations/04 Deployment/16 Conclusion/V1-16.11 Source References#^ref-williams2009|Williams et al. 2009]]). Across the book, each lighthouse rewarded the lever aimed at its limiting term and wasted the effort aimed anywhere else ([[01 Books/Volume I - Foundations/04 Deployment/16 Conclusion/V1-16.03 Lighthouse Models Constraint Propagation#^tbl-lighthouse-trace|table 1]]).

↩︎ The five lighthouse models and their diagnostic execution regimes are established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-lighthouse-models-9b1c|Lighthouse models put the iron law into practice]]**.

| **Lighthouse**             | **Home Regime**                       | **Limiting Term**                                                                  | **Lever That Paid**                                                                         | **Lever Wasted**                                                                              |
|:---------------------------|:--------------------------------------|:-----------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------|
| **ResNet-50**              | Compute-bound                         | Compute, ${O}/({R_{\text{peak}}} \cdot {\eta_{\text{hw}}})$                        | Batching that reuses filter weights across inputs; reduced-precision tensor arithmetic      | More memory bandwidth once batched convolutions sit right of the ridge point                  |
| **GPT-2/Llama decode**     | Bandwidth-bound                       | Data movement, ${D_{\text{vol}}}/{\text{BW}}$                                      | Batching across requests; fewer bytes per weight; managing the per-request key-value cache  | More peak arithmetic throughput, or compute-only kernel tuning at batch one                   |
| **DLRM**                   | Capacity-bound                        | Memory capacity, a precondition before any term applies                            | Placing and sharding embedding tables across memory tiers; caching frequently accessed rows | Faster dense arithmetic for the small fully connected layers                                  |
| **MobileNetV2**            | Compute-bound in its efficient regime | Compute within a phone’s power envelope; depthwise layers cross to bandwidth-bound | Depthwise separable convolutions, then INT8 once depthwise layers became bandwidth-bound    | Further operation cuts on layers already bound by bandwidth                                   |
| **Keyword spotting (KWS)** | Power-bound                           | Energy per inference within a milliwatt budget                                     | A sub-megabyte INT8 model with a tensor arena planned at build time                         | Streaming audio to the cloud, whose radio transmission costs more energy than local inference |

Table 1: **Lighthouse Constraint Traces**: Each lighthouse probes one home regime, and the lever that paid off was the one aimed at that regime’s limiting term. A regime describes a workload on a machine rather than a model name, so a lighthouse crosses regimes when batch size, phase, or precision changes.

^tbl-lighthouse-trace

The regime belongs to the workload on a machine, so the same model can change regime, and the regime has to be checked before an optimization is chosen. GPT-2 training is compute-bound even though its decode is bandwidth-bound, because a training step reuses each weight across every token in the batch. ResNet-50 became input-bound in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training#^sec-model-training|Model Training]]**, starved by a data pipeline that could not keep the accelerator fed.

Precision and the machine move the regime as well. INT8 arithmetic doubles the H100’s peak rate without raising its memory bandwidth, so it doubles the ridge point. A ResNet-50 layer whose activations still move at 16 bits does not halve its bytes, so its intensity rises less than the ridge does, and the layer can fall below the doubled ridge and become bandwidth-bound (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-calculating-memory-bandwidth-bounds-7fc0|Memory bandwidth bounds]]**). MobileNetV2 changes regime with the machine. The network that is compute-bound on the phone NPU falls below the far higher ridge of an H100, where its depthwise layers wait on memory bandwidth (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.11 Heterogeneous SoC Design#^sec-hardware-acceleration-heterogeneous-soc-ai-acceleration-b1bb|Heterogeneous SoC Design]]**). A recommendation model larger than DLRM, a larger decoder, a faster vision network, or a smaller keyword spotter differs from its lighthouse in scale, not in which term dominates, so the diagnosis carries forward to models that do not yet exist.

A regime diagnosis guides one decision, but a deployed model is the product of many decisions, and each one constrains the next. [[01 Books/Volume I - Foundations/04 Deployment/16 Conclusion/V1-16.03 Lighthouse Models Constraint Propagation#^tbl-lighthouse-journey-mobilenet|Table 2]] follows MobileNetV2 through nine phases of the book, from the deployment tier’s envelope through architecture, training, data selection, compression, acceleration, benchmarking, serving, and runtime operations, and every engineering decision along the way narrows the options available downstream.

|:-------------------------------------------------------------------------------------------------------------------------------------------------|:-------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Foundations (**[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02 System Paradigms#^sec-ml-systems\|System Paradigms]]**)**                  | Deployment Tier Constraints    | Mobile tier sets a watt-scale power, thermal, and battery envelope that every later phase must respect                                                                                                             |

Table 2: **The Lighthouse Journey (MobileNetV2)**: Applying the book’s nine phases to one model shows how decisions in one domain (for example, architecture) propagate constraints and opportunities into downstream domains (for example, hardware acceleration and monitoring).

^tbl-lighthouse-journey-mobilenet

Decisions in one row constrain options in the next. Depthwise separable convolutions cut the operation count, but depthwise filtering reduces cross-channel reuse and often leaves these layers bandwidth-bound on mobile hardware. When profiling confirms that regime, a further cut in operations buys little, and the compression row’s reduction in bytes per value becomes the next lever. That lever pays only if the acceleration row confirms that the mobile NPU executes those INT8 operators, and only if the benchmarking row shows the gain surviving preprocessing and transfer. The same propagation runs through every lighthouse, and reasoning about it before profiling requires the quantitative principles the book accumulated part by part.

**Self-Check: Question**

1.  A production recommender workload is dominated by embedding tables larger than one accelerator’s memory where engineers spend significant effort deciding where data physically resides across storage tiers rather than optimizing dense matrix math. Which lighthouse model embodies this constraint regime, and how does its primary bottleneck differ from low-batch GPT-2/Llama decoding?

    1.  MobileNetV2; it is capacity-bound on microcontrollers, whereas autoregressive decoding is bound by network packet round-trip times.
    2.  ResNet-50; it is capacity-bound by image batch activation footprints in host DRAM, whereas LLM decode is compute-bound.
    3.  Keyword Spotting (KWS); it is capacity-bound by microcontroller flash storage, whereas LLM decode is strictly compute-bound by tensor core peak FLOP/s.
    4.  DLRM; it is capacity-bound by embedding tables larger than one accelerator’s memory requiring physical data placement design, whereas low-batch LLM decode is memory-bandwidth-bound due to streaming weights with minimal arithmetic reuse per token.

2.  A team serving GPT-2 at batch size one on an H100 proposes two investments: hand-tuning the matrix-multiply kernels to raise achieved FLOP/s, or batching concurrent requests and storing weights in fewer bytes. Using the chapter’s lighthouse trace, which investment pays off, and why?

    1.  Kernel tuning, because GPT-2 is compute-bound at every batch size and phase.
    2.  Batching and fewer bytes per weight, because batch-one decode is bandwidth-bound: its data-movement term exceeds its compute term, so only levers that reuse each weight across more tokens or move fewer bytes per token shorten the step.
    3.  Neither, because GPT-2 decode is capacity-bound like DLRM and must first be sharded across several devices.
    4.  Kernel tuning, because a high ridge point means every workload gains more from compute than from bandwidth.

3.  Order the following phases of the MobileNetV2 lighthouse journey in their chronological lifecycle order as constraints propagate from initial requirements through deployment operations:

<!-- -->

1.  Compression (INT8 quantization navigating the Pareto frontier)
2.  Acceleration (Mapping operators to mobile NPUs under the silicon contract)
3.  Foundations (Establishing battery, thermal, and machine constraints)
4.  Architecture (Depthwise separable convolutions reducing FLOPs)
5.  Operations (Cohort-level drift monitoring across heterogeneous devices)
6.  Serving (Enforcing P99 latency budgets under 50 ms)
