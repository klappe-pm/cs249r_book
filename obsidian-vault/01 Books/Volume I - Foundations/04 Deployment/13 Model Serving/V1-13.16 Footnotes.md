# V1-13.16 Footnotes

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^footnotes

<sup>1</sup> **SLOs in ML serving**: An SLO is the internal target, as distinct from the contractual SLA. For ML serving, task quality and inference latency can both contribute to SLOs, creating multidimensional targets where improving one dimension (for example, deploying a larger model for accuracy) can violate another (latency).

^fn1

<sup>2</sup> **TensorRT**: TensorRT builds its engine ahead of time for one microarchitecture (such as Hopper or Blackwell) ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidia2024tensorrt|NVIDIA 2024a]]). That target-specific build phase allows the compiler to generate fused kernels, select microarchitecture-specific Tensor Core execution paths, and optimize memory layouts (such as NC/32HW32). The resulting nonportable engine reduces per-request execution latency and minimizes the accelerator count needed to satisfy a target throughput.

^fn2

<sup>3</sup> **Inference server**: Google’s TensorFlow Serving ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-olston2017tensorflow|Olston et al. 2017]]) helped establish the separation of model logic from serving infrastructure; NVIDIA’s Triton ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidia-triton-c2de726e|NVIDIA 2024b]]) extends this pattern across multiple model frameworks and backends. In both, a scheduler and dynamic batcher turn irregular single-request traffic into accelerator-friendly execution, improving utilization when latency budgets allow batching. Exact utilization gains depend on model, hardware, arrival rate, and the configured batching window.

^fn3

<sup>4</sup> **NCHW and NHWC (tensor memory layouts)**: These acronyms encode the dimension order of 4D image tensors: N (batch), C (channels), H (height), and W (width). In a contiguous NCHW tensor, each channel plane is contiguous; in NHWC, channels for one spatial position are adjacent. Optimized kernels may favor either layout, and a semantic mismatch can scramble values even when the element count is correct. Serving code should therefore make both dimension meaning and any physical-layout conversion explicit.

^fn4

<sup>5</sup> **Protocol Buffers (Protobuf)**: Protobuf uses a predefined schema (from a `.proto` file) to encode structured data into a compact binary format ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-protobufDocs|Protocol Buffers Authors 2026]]). Because the schema carries field names and types, the wire payload need not repeat them as JSON does. Its wire format is still not identical to a C++ object’s in-memory layout, so it requires a parsing step and does not provide the same direct zero-copy access pattern that FlatBuffers targets.

^fn5

<sup>6</sup> **FlatBuffers**: The “flat” in the name describes the design: the binary buffer can serve as the serialized representation and the data structure being read, avoiding a separate parsing or unpacking phase for supported access patterns ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-flatbuffersDocs|FlatBuffers Authors 2026]]). For ML inference, this can enable zero-copy access to tensor metadata, because the serving system reads tensor shapes and offsets directly from the buffer rather than allocating a second object representation.

^fn6

<sup>7</sup> **gRPC (gRPC remote procedure call)**: The gRPC framework pairs HTTP/2 transport with an interface definition language and message format, most commonly Protocol Buffers ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-grpcDocs|gRPC Authors 2026]]). The size and latency benefit over REST/JSON depends on payload shape, client/server implementation, and whether serialization is a meaningful share of the end-to-end latency budget.

^fn7

<sup>8</sup> **Tail latency**: Unlike averages, percentile latencies reveal the performance impact of system outliers common in ML serving, such as model cache misses or garbage collection pauses. These rare, high-latency requests can disproportionately harm user satisfaction and business outcomes. Because the magnitude is workload-specific, services validate percentile targets (p95, p99) against their own users and SLOs.

^fn8

<sup>9</sup> **M/M/1 queue**: Queuing theory originated with Agner Krarup Erlang’s 1909 analysis of the Copenhagen Telephone Exchange, where call arrivals were modeled as memoryless (Poisson).

^fn9

<sup>10</sup> **Poisson process**: Named after French mathematician Simeon Denis Poisson (1781–1840), this stochastic model describes events occurring continuously and independently at a constant average rate, so counts in disjoint intervals are independent.

^fn10

<sup>11</sup> **Kendall notation**: Kendall’s A/S/c (arrival/service/servers) shorthand ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kendall1953stochastic|Kendall 1953]]) is the one already used for ${M}/{M}/1$, where “M” signifies a Markovian (memoryless) process; the “D” in M/D/1 denotes deterministic service. Neither model replaces measurement of a production workload’s arrival process, service-time variance, or tail behavior.

^fn11

<sup>12</sup> **Hedging**: The term is borrowed from finance, where an offsetting position reduces risk; here, the redundant request insures against a slow server. The insurance is not free. For ML systems, the losing hedged request may still occupy accelerator time if inference has already launched, because ordinary GPU kernels are not cheaply canceled mid-execution. Thus, a hedging policy must budget duplicate work as well as the latency benefit.

^fn12

<sup>13</sup> **Batch**: From Old French *bache* (a quantity baked at one time), entering computing in the 1950s for jobs processed together without human interaction. The ML serving usage preserves the original trade-off: grouping requests amortizes fixed costs (kernel launch, weight movement) across multiple inputs, but an online request may wait for a batch to form.

^fn13

<sup>14</sup> **ONNX Runtime**: Microsoft’s inference engine applies graph optimizations such as constant folding, redundant-node elimination, and kernel fusion before handing subgraphs to execution providers. Performance relative to a tuned target-specific engine such as TensorRT depends on the workload, execution provider, and hardware.

^fn14

<sup>15</sup> **OpenVINO (open visual inference and neural network optimization)**: An Intel-oriented inference toolkit that converts, optimizes, and runs models across Intel CPU, GPU, and NPU targets ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-openvinoDocs|Intel Corporation 2026]]). Specializing for direct hardware execution departs from the portable execution guarantees of general-purpose frameworks, enabling the compiler to emit architecture-tuned vector instructions (such as AVX-512 or AMX) and exploit low-precision integer execution units. While speedups depend on the specific operator mix and target processor, this specialization can make CPU or edge serving economically viable for latency-sensitive models.

^fn15

<sup>16</sup> **Layer fusion**: The term parallels loop fusion in compiler optimization, where adjacent loops over the same array are combined into one pass to reduce memory traffic.

^fn16

<sup>17</sup> **SIMD**: From Michael Flynn’s 1966 taxonomy of computer architectures, SIMD enables one instruction to operate on multiple data elements simultaneously. Intel’s AVX-512 can process sixteen FP32 values in a 512-bit vector, while AMX adds matrix tile operations. The attainable fraction of peak depends on data type, matrix shape, memory behavior, and implementation, but optimized vector kernels provide multiple-fold speedups over scalar execution.

^fn17

<sup>18</sup> **Warmup**: Borrowed from just-in-time (JIT) compilation, where initial executions compile hot paths into optimized machine code; for ML serving, warmup inferences trigger CUDA kernel compilation, cuDNN algorithm auto-tuning, and memory pool allocation that frameworks defer until first use.

^fn18

<sup>19</sup> **Safetensors**: The name emphasizes safety: unlike unrestricted pickle deserialization, the format does not encode executable Python objects ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-huggingface-safetensors-51152970|Hugging Face 2026]]). It stores tensors as contiguous raw bytes with a small header and supports memory-mapped loading. In the local benchmark example, that path is 10× faster than the compared PyTorch checkpoint path; the result is workload- and storage-specific and does not include transfer to a discrete accelerator.

^fn19

<sup>20</sup> **MIG (multi-instance GPU)**: Introduced with NVIDIA’s A100 ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020]]) and documented across supported data-center GPUs ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidiaMigUserGuide|NVIDIA 2026e]]), MIG partitions a single physical GPU into independent instances, each with dedicated compute and memory resources; unlike software sharing (MPS or time-slicing), MIG provides hardware-level isolation between partitions. The trade-off is granularity, because partitions must follow fixed profiles, so resources cannot be divided arbitrarily. For multi-model serving, MIG reduces noisy-neighbor risk on shared hardware, while per-model SLO guarantees still depend on scheduler policy, load, and the selected partition profile.

^fn20

<sup>21</sup> **Autoregressive**: From Greek *auto-* (self) and Latin *regressus* (a going back), since the output “regresses” on itself; George Udny Yule introduced autoregressive models in 1927 for analyzing sunspot cycles. In language modeling, each output token conditions on all previously generated tokens, creating a serial dependency that prevents the parallelism exploited during training. Decode is often weight-bandwidth-bound at small batches; larger batches amortize the weight stream and can shift the bottleneck toward compute or KV-cache traffic ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-pope2023efficiently|Pope et al. 2023]]).

^fn21

<sup>22</sup> **Continuous batching**: NVIDIA TensorRT-LLM calls the same technique “in-flight batching” ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidiaTensorRtLlm|NVIDIA 2026f]]). Request-level batching commits to a fixed batch for an entire generation sequence (potentially hundreds of iterations), while continuous batching reschedules at every token-generation step, a contrast that parallels preemptive OS process scheduling versus run-to-completion.

^fn22

<sup>23</sup> **vLLM (virtual large language model (LLM))**: An open-source serving system that enables continuous batching with PagedAttention, a paged allocator for the KV cache that [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^sec-model-serving-pagedattention-b8d4|section 13.9.4.2]] develops ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kwon2023|Kwon et al. 2023]]). Keeping KV-cache waste low lets it serve larger effective batches on the same hardware.

^fn23

<sup>24</sup> **Speculative decoding**: Parallel verification is possible because the draft has already committed to all ${\gamma}$ candidate tokens, so the target can score the whole block in one causal-attention forward pass, as it scores a prompt during prefill, rather than in ${\gamma}$ sequential steps ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-leviathan2023speculative|Leviathan et al. 2023]]). The technique removes serial steps at the runtime layer without changing the model architecture.

^fn24

<sup>25</sup> **PagedAttention**: The name directly references OS virtual memory paging, first implemented on the Atlas computer at Manchester (1962) to solve the same class of allocation problem, in which programs needed more memory than physically available, and contiguous allocation wasted space ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kilburn1962onelevel|Kilburn et al. 1962]]). Introduced at SOSP 2023, PagedAttention applies this six-decade-old abstraction to GPU KV-cache memory; in its evaluation, the recovered memory enabled 2–4$\times$ higher throughput on the same hardware ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kwon2023|Kwon et al. 2023]]).

^fn25

<sup>26</sup> **Jevons paradox**: William Stanley Jevons observed in 1865 that efficiency improvements in coal-powered steam engines increased total coal consumption by making steam power economically viable for applications previously too costly ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-jevons1865coal|Jevons 1865]]); the same dynamic can apply to AI inference, where each 10$\times$ cost reduction opens application classes that were economically infeasible at the previous price point, expanding aggregate demand by more than the efficiency gain.

^fn26
