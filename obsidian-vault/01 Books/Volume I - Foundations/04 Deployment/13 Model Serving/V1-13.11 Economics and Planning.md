# V1-13.11 Economics and Planning

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-economics-capacity-planning-3e7e

A team that has raised an H100’s ResNet-50 throughput several-fold through batching still faces a fleet-level question, namely whether serving a 5,000 QPS target within the same p99 latency SLO costs less on a few H100s or on several times as many lower-cost T4s. Batching, precision tuning, kernel fusion, graph compilation, and the LLM levers that share each weight stream across sequences all improve single-node performance, but production deployment requires choosing how many machines to rent, of what type, and at what total bill. Serving infrastructure cost grows continuously with request volume ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-zhang2019mark|Zhang et al. 2019]]), while training cost follows a one-time dataset, model, and optimization budget. The bitter lesson sharpens this asymmetry. The methods that win are the ones that scale, so successive models grow larger, and while training pays for that scale once, serving pays for it on every request.

↩︎ The bitter lesson, that general methods which scale with computation keep outperforming hand-engineered ones, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.05 The Bitter Lesson#^sec-introduction-bitter-lesson-79c7|The Bitter Lesson]]**.

Tail latency dictates the technical design of a serving system, but economics dictates its operational scale. As specialized accelerators and runtime optimizations reduce the compute cycles required per forward pass, the marginal cost per inference declines.[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn26|²⁶]] Counterintuitively, reduced unit cost need not shrink aggregate serving expenditures. When Jevons paradox applies, lower marginal costs can stimulate disproportionately higher query volumes, integrating model evaluation deeper into user-facing product loops. At hyperscale, recurring operational inference costs quickly eclipse one-time offline training investments, shifting the primary systems bottleneck toward sustained per-query efficiency.

**Example 13.12: Inference cost at Facebook**

**Scenario**: Production ML serving systems at Meta execute tens of trillions of inferences daily across global user-facing services ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-hazelwood2018|Hazelwood et al. 2018]]).

**Diagnosis**: Recurring inference serving compute and energy costs dwarf initial offline model training expenses. Live request arrival patterns and strict latency bounds constrain GPU batching.

**Systems lesson**: Model architectures cheap to train can prove unviable to serve at fleet scale. Production serving infrastructure requires hardware-software co-design to balance tail latency, batch size, and recurring operational total cost of ownership.

^exmp-model-serving-facebook-inference-tax

The same serving-economics pressure appears in public API prices. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.11 Economics and Planning#^fig-intelligence-deflation|Figure 11]] tracks this cost collapse across representative public API list-price snapshots from late 2022 to early 2025 on a logarithmic scale. The steep downward trend line isolates how prompt token pricing fell by multiple orders of magnitude, from thirty dollars per million tokens for original GPT-4 down to several cents for Gemini 1.5 Flash and DeepSeek-V3. Vendor prices change frequently, so these points should be read as historical provenance for the trend rather than as current purchasing guidance ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-openai2023chatgptwhisper|OpenAI 2023b]], [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-openai2023gpt4web|2023a]], [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-openai2024gpt4oMini|2024]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-openaiCommunity2024gpt4oApi|OpenAI Developer Community 2024]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-anthropic2024claude3family|Anthropic 2024]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-google2024gemini15flashPricing|Google Developers Blog 2024]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-deepseek2024v3|DeepSeek 2024]]). Each order-of-magnitude drop changes which applications are economically viable, and a provider can sustain such prices only if its serving stack extracts more completed requests from each accelerator-hour. Converting engineering efficiency into unit cost draws on the latency, batching, and memory mechanisms of the preceding sections.

### Cost per Inference Across Hardware

^sec-model-serving-cost-per-inference-27fc

Choosing serving instances by hourly rental price alone, or by peak throughput alone, misleads whenever traffic fluctuates. An H100 that costs several times as much per hour as a T4 delivers the lowest cost per million images when traffic keeps it full, but becomes the more expensive option when overnight traffic drops and the GPU sits mostly idle. The **cost per inference** divides the allocated serving cost by the number of completed inferences that satisfy the service objective. The numerator can include provisioned CPU or accelerator time, memory capacity, data transfer, storage, and orchestration. At high utilization, useful throughput spreads that provisioned cost across many requests. At low utilization, paid capacity sits idle, so the same hourly cost is divided among fewer successful inferences.

Hardware selection for model serving trades hourly rental price against parallel throughput. Although GPU instances cost several times as much per hour as commodity CPU instances, their matrix units can process enough requests per second to cut the cost per completed query by an order of magnitude. Whether CPUs or dedicated accelerators win economically depends on arithmetic intensity, batchability, and the latency deadline.

Host CPU execution is cheaper for small models, services with relaxed latency deadlines (hundreds of milliseconds), and sparse or unpredictable traffic that leaves dedicated accelerators idle. Conversely, GPU acceleration wins when models perform dense matrix operations, when service-level objectives require response times of tens of milliseconds or less, and when sustained traffic lets dynamic batching amortize kernel launch and memory transfer costs.

Beyond steady-state costs, startup time affects scaling economics. Instance launch, image pull, driver initialization, model loading, compilation, and warmup can make accelerator replicas slower to become ready than CPU replicas, although exact times depend on the platform and deployment artifact. If traffic rises faster than useful capacity can come online, latency SLOs can fail despite sufficient eventual capacity.

When accelerator replicas have a long readiness delay, predictive scaling or a warm pool may be more reliable than purely reactive scaling. For a model that runs acceptably on both device types, a hybrid design can use always-on accelerator capacity for baseline load and CPU overflow for spikes, trading a different unit cost and latency profile for faster reserve capacity. Whether this GPU+CPU hybrid works depends on model compatibility and identical output semantics across runtimes.

### Capacity Planning

^sec-model-serving-capacity-planning-96a3

The unit-cost comparison in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.11 Economics and Planning#^tbl-model-serving-resnet-cloud-cost|table 18]] evaluates each instance at its saturated throughput, but a live fleet cannot run at 100 percent utilization without pushing every arrival burst past the knee of the latency curve ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^fig-tail-latency-explosion|figure 5]]). Determining how many replicas to provision therefore combines those per-device service rates with the queueing bounds from [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^sec-model-serving-queuing-theory-tail-latency-29a6|section 13.4]]. **Capacity planning** translates three inputs into replica counts: traffic patterns (peak request rate, daily and weekly cycles, growth projections), latency SLOs (p50, p95, p99 targets), and model service times across batch sizes ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-harchol-balter2013|Harchol-Balter 2013]]).

The ResNet-50 capacity notebook in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^sec-model-serving-tail-latency-5376|section 13.4.3]] ran this workflow for batch-one service, deriving an M/M/1 utilization threshold of 68 percent from [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^eq-p99-latency|equation 5]] and arriving at 36 H100s with headroom for a 5,000 QPS target. The plan extends to batched service by the same arithmetic. Applying the same utilization factor to the saturated batched rate of 7,040 img/s in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.11 Economics and Planning#^tbl-model-serving-resnet-cloud-cost|table 18]] gives 2 H100 before headroom and 3 after; the batch-1 plan needed 27 and 36.

This arithmetic compares assumed capacities under different service models; it does not establish equal p99 latency. Batching changes service times, realized batch sizes, and waiting distributions, so the factor derived for unbatched M/M/1 service cannot by itself certify the batched plan. The throughput opportunity is the batching gain of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-throughput-optimization-18d1|section 13.5]]; its usable capacity requires a load test including formation delay and worker backlog. This scenario provisions peak load plus 30 percent headroom; production margins depend on the workload and policy. Autoscaling can reduce costs during low-traffic periods while meeting latency objectives during peaks; **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-infrastructure-management-bf8f|Infrastructure as code]]** develops the operational policy layer around these serving calculations. Capacity must be sized for requests that meet the SLO rather than for raw request volume, and that sizing becomes multi-dimensional when each request is an autoregressive token stream constrained by TTFT, TPOT, and KV-cache capacity at once.

### Production Case Study: Serving 8-Billion-Parameter Llama 3

^sec-model-serving-production-case-study-serving-llama38b-0499

A team that deploys an 8-billion-parameter Llama 3 chat service on a single H100 under a 200 ms TTFT and 20 ms TPOT budget must determine whether GPU memory capacity, prefill compute, or decode bandwidth caps the number of requests per hour. It must also determine what each million tokens cost. The serving bounds of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^sec-model-serving-llm-serving-b8bf|section 13.9]] become a dollar figure only when they meet a concrete workload, an SLO, and an hourly rental rate. This case study costs out that single-H100 deployment, reusing the decode floor and the cache budget derived earlier rather than re-deriving them. Unlike the 70-billion-parameter scale-up in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^fig-kv-cache-growth|figure 10]], the 8-billion-parameter model fits on one GPU with substantial memory headroom, so batching, prompt prefill, and autoregressive decoding can be balanced on a single device without multi-node sharding.

#### Workload Profile

^sec-model-serving-workload-profile-a380

Four fixed parameters anchor the latency, memory, and cost calculations for this single-GPU deployment:

- **Model**: 8-billion-parameter Llama 3 (quantized to 4-bit using activation-aware weight quantization (AWQ); see **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-quantization-precision-cd46|Numerical Precision: Changing How Values Are Stored]]** for quantization techniques) ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-dubey2024llama|Dubey et al. 2024]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-lin2023awq|Lin et al. 2024]]).
- **Hardware**: 1$\times$ NVIDIA H100 SXM5 GPU (80 GB HBM3 device capacity, equivalent to 85.9 GB on the decimal basis used for tensor footprints, 3.35 TB/s bandwidth) ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-choquette2023|Choquette 2023]]).
- **Request characteristics**: 1,000-token input prompt (Prefill), 256-token generated response (Decode).
- **Target SLOs**: TTFT $<$ 200 ms, TPOT $<$ 20 ms.

#### Latency Deconstruction

^sec-model-serving-latency-deconstruction-217e

The end-to-end request latency is governed by the two-phase execution model of autoregressive transformers, applying the TTFT and TPOT metrics defined in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^sec-model-serving-performance-metrics-ttft-tpot-b009|section 13.9.1]]. Prefill determines whether the user sees a prompt response quickly; decode determines whether the generated stream keeps moving after it starts.

##### Prefill Phase (Time to First Token)

^prefill-phase-time-to-first-token

The model processes the 1,000-token prompt in parallel. Assuming 40 percent of peak compute efficiency during prefill, the model-side TTFT estimate is 41.9 ms, comfortably within the 200 ms SLO and leaving the remaining budget for network ingress, tokenization, and queueing.

##### Decode Phase (Time per Output Token)

^decode-phase-time-per-output-token

The model generates 256 tokens sequentially. At batch one, this phase is memory-bandwidth bound: each step streams the 4 GB weight tensor from VRAM. A batched step amortizes that stream across its active sequences.

Dividing the 4 GB weight tensor by the 3.35 TB/s bandwidth yields the theoretical floor: ${T_{\text{token}}}\approx$ 1.2 ms. The modeled TPOT of 1.57 ms assumes that the serving engine captures the decode step into a single CUDA Graph, so it adds only a small assumed residual per-layer dispatch cost to that floor. Without graph capture, each token would launch 8–10 discrete GPU kernels (normalization, positional encoding, projections, attention, multilayer perceptron (MLP)) in each of the model’s 32 layers. At batch size one, those roughly 250–320 small kernels would add several milliseconds of CPU-GPU submission and driver overhead on top of the modeled TPOT. Generating all 256 tokens therefore takes 256 tokens $\times$ 1.57 ms = 0.40 s.

#### Memory and Throughput

^sec-model-serving-memory-throughput-63dd

With 4-bit weights occupying 4 GB, the remaining ~81.9 GB is available for the KV cache and runtime workspace, and the case study sets aside the cache reserve below while leaving the rest as workspace headroom. AWQ compresses the weights to 4 bits but leaves the KV cache in 16-bit precision, so each token still costs the approximately 0.131 MB of FP16 cache derived for this model in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^sec-model-serving-kv-budget-e81c|section 13.9.5.1]]. Dividing the 77.3 GB reserve by that per-token cost yields capacity for ≈ 0.6 million tokens, so at 1,256 tokens the GPU can hold a concurrent batch size of ~469 requests.

#### Unit Economics

^sec-model-serving-unit-economics-b685

Consider a representative H100 SXM5 rental cost of approximately \$3/hour and an assumed isolated prefill rate of 10,000 prompt tokens/s, deliberately below the rate implied by the model-side TTFT estimate above to allow for scheduling and kernel inefficiency. Steady-state request throughput cannot exceed either the rate at which the GPU prefills incoming prompts or the rate at which resident KV-cache slots turn over completed responses. Dividing the 10,000 prompt tokens/s prefill rate by the 1,000-token prompt bounds admissions to 10 requests/s. For this calculation, each completed request counts both its prompt and its generated output tokens, 1,256 tokens in total. The result is therefore a blended cost over every token the request processes, not a price for input or output tokens alone. Multiplying a 10 requests/s limiting rate by this token count and the 3,600 seconds in an hour gives 45.2 million tokens/hour, and dividing the hourly rental cost by that throughput gives \$0.066/million tokens.

KV-cache capacity sets a second ceiling on request throughput. Little’s Law converts the ~469 requests that the KV cache can hold at once into a maximum turnover rate by dividing that resident count by the modeled time each request needs to finish prefill and decode. That rate assumes every resident request advances at the modeled batch-one pace, which a real decode batch does not achieve, so it is an optimistic ceiling. Even so, it comes out more than ten times higher than the 10 requests/s prefill bound. The smaller of the two ceilings sets the cost floor, so isolated prefill, not KV residency, prices this service. Neither ceiling is a measured throughput. Prefill and decode contend for the same accelerator, so the request rate the service sustains while meeting its SLO must come from a load test, and the checkpoint that follows lays out that experiment. Until that measurement exists, the cost computed here is a floor on what serving this workload costs, not the price of a deployment.

**Checkpoint 13.6: Complete the LLM capacity decision**

**Define acceptance**: For the case study’s 200 ms TTFT and 20 ms TPOT targets, state the required completion quantiles, availability requirement, and memory reserve before evaluating a configuration. Why do latency thresholds alone leave the SLO incomplete?

**Measure the missing capacity**: Hold runtime, precision, hardware, and prompt/output lengths fixed. Increase offered request rate across several concurrency limits below the residency ceiling. For each warmed configuration, record TTFT and TPOT distributions, completed request rate, rejection rate, and peak allocated memory. Identify the configurations that satisfy all acceptance conditions.

**Close the economic decision**: Recompute cost using each qualifying configuration’s completed request rate and the case study’s prompt-plus-output token convention. Select the lowest-cost qualifying setting for the required load. If none qualifies, identify whether lower offered load, a different batching/runtime policy, or different hardware is the next experiment. Explain why the KV-residency ceiling cannot supply the missing throughput observation.

For large language models, memory capacity (the size of the unallocated VRAM dedicated to the KV cache) determines maximum concurrent residency, while prefill compute and decode bandwidth determine realized token throughput and cost under a specific traffic mix. Memory bandwidth bounds low-batch decode latency; larger batches amortize parameter movement and shift the limit toward compute or KV-cache traffic. Physical constraints govern serving economics across the entire stack. Latency budgets partition into prefill and decode phases, queueing theory dictates batch sizing and capacity headroom, and memory bandwidth bounds decode throughput. Misinterpreting these interactions leads directly to the operational fallacies and pitfalls that follow.

**Self-Check: Question**

1.  A team evaluates deploying a small classification model with an average arrival rate of 5 QPS and a 200 ms latency SLA. Measurements at 5 QPS show that both a single CPU server instance and a single GPU server instance meet the matched quality target and the p99 latency target of 200 ms. The CPU instance costs \$0.20/hour and sustains up to 20 QPS under the target latency; the GPU instance costs \$2.00/hour and sustains up to 200 QPS under the target latency. Which deployment option is more cost-effective for this specific workload, and why?

    1.  The GPU server is more cost-effective because its 10x greater SLO-qualified peak throughput more than offsets its 10x higher hourly cost, making it the lower-cost choice even at 5 QPS.
    2.  The GPU server is more cost-effective because GPUs always have lower total cost of ownership regardless of arrival traffic.
    3.  The CPU server is more cost-effective because at 5 QPS, it already meets the SLA with adequate headroom at \$0.20/hour, whereas the GPU server would use only 2.5% of its SLO-qualified capacity and cost about $10\times$ more per served query at that traffic level.
    4.  Neither option is viable because 5 QPS requires at least a 10-node cluster for high availability.

2.  In capacity planning for a mission-critical model serving cluster with a peak expected traffic of $\lambda_{\text{peak}} = 1\text{,}000\text{ QPS}$ and an individual replica capacity of $R = 100\text{ QPS}$ at its target latency SLO, why would a capacity engineer provision 16 to 20 replicas ($1.6\times\text{--}2.0\times$ headroom multiplier) rather than exactly 10 replicas?

3. 4.  An engineer serves an 8-billion parameter LLM on a GPU with 2 TB/s of High-Bandwidth Memory (HBM) bandwidth. Assume the model weights are 16 GB in FP16, the decode step effectively streams those 16 GB of weights from HBM each token at batch size $B = 1$, and ignore KV-cache traffic and compute time.
