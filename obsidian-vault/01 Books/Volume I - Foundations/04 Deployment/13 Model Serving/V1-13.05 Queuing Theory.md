# V1-13.05 Queuing Theory

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-queuing-theory-tail-latency-29a6

An inference service that responds in a few milliseconds at moderate load can suffer sudden, tenfold latency spikes when traffic climbs toward capacity, even though no hardware has failed and the model’s execution time has not changed. Because requests arrive in irregular bursts and contend for shared accelerator queues, host-to-device PCIe links, and memory buses, queuing theory governs how waiting times grow and why latency explodes nonlinearly as utilization approaches capacity.

### Little’s Law

^sec-model-serving-littles-law-9352

Before deciding how many accelerators to provision, an engineer must know how many requests will sit inside the server at the same time. Underestimating that in-flight population exhausts host request buffers, worker threads, and device activation memory under load. Given an expected arrival rate and mean response time, Little’s Law determines this average concurrency directly from throughput, while queuing models predict how response times climb as utilization nears saturation.

↪ The derivation of Little’s Law from conservation of requests is collected for reference in **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-littles-law-21a3|Little's Law]]**.

Formulated by John D. C. Little ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-little1961|Little 1961]]), **Little’s law** establishes an exact relationship among three macroscopic metrics in any stable queuing system:

$$
{Q_{\text{req}}} = {\lambda_{\text{arr}}} \cdot {T_{\text{lat}}} \tag{3}
$$

 where ${Q_{\text{req}}}$ is the average number of requests residing in the system, ${\lambda_{\text{arr}}}$ is the arrival rate (requests per second), and ${T_{\text{lat}}}$ is the average time each request spends from arrival to completion.

^eq-littles-law

**Systems Perspective 13.3: Notation alert: L vs. latency**

Classical queueing texts write Little’s law with the single letter L for the in-system count and W for the time in system. This book writes ${Q_{\text{req}}}$ for the count and ${T_{\text{lat}}}$ for the time, because a bare L would collide with the loss ${\mathcal{L}}$ and with the iron law’s fixed-latency term ${L_{\text{lat}}}$. In queuing theory, ${T_{\text{lat}}}$ denotes the *response time* or *time in system per request*; queue-only waiting time is ${W_{q}}$. Here, ${Q_{\text{req}}}$ denotes the average in-system request count, ${\lambda_{\text{arr}}}$ the arrival rate, ${\mu}$ the service rate of a server that handles one request at a time, and ${\rho_{\text{serv}}}={\lambda_{\text{arr}}}/{\mu}$ the serving utilization. The subscripts keep serving utilization from occupying bare ${\rho}$, which stays free for other ratio models. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-batching-tax|Section 13.5.2]] adds the few symbols that batching needs.

Little’s law holds regardless of the arrival distribution, service-time distribution, or scheduling discipline; it requires only that the system is stable and that requests are neither created nor destroyed internally. For an inference service targeting 1000 QPS with a mean response time of 50 ms, Little’s law dictates the average in-flight request population that host memory buffers and worker threads must sustain.

**Napkin Math 13.2: Little's Law capacity sizing**

**Problem**: How many requests are in the system on average at 1,000 QPS?

**Math**: Little’s Law gives ${Q_{\text{req}}} = {\lambda_{\text{arr}}} {T_{\text{lat}}}$, so average population equals throughput multiplied by mean time in system.

**Given**:

- **Arrival rate $({\lambda_{\text{arr}}})$**, equal to throughput in a stable system: 1,000 QPS.
- **Mean time in system $({T_{\text{lat}}})$**: 50 ms (0.05 s).

**Math**: ${Q_{\text{req}}}$ = 1,000 QPS $\times$ 0.05 s = 50 concurrent requests on average

**Systems insight**: The system holds 50 requests on average across batch and queue state. That population is a memory and concurrency requirement, not a limit on the accelerator. A server whose GPU executes at most 32 requests per batch can still sustain this load, because the requests not currently executing wait in host memory. Service rate, queueing behavior, and the tail distribution, not the population itself, determine whether the load is feasible.

Because [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^eq-littles-law|equation 3]] ties these three variables together, constraining any two dictates the third. If an inference service averages 10 ms per request $({T_{\text{lat}}} = 0.01 \text{ s})$ and holds 50 concurrent requests on average $({Q_{\text{req}}} = 50)$, the sustainable arrival rate must be ${\lambda_{\text{arr}}} = {Q_{\text{req}}} / {T_{\text{lat}}} = 5000$ requests per second. Conversely, if host memory limits concurrency to an average of 10 requests while average time in system remains 10 ms, the system cannot exceed a throughput of 1,000 requests per second without dropping traffic.

### The Utilization-Latency Relationship

^sec-model-serving-utilizationlatency-relationship-a2f0

Little’s Law describes average system inventory under steady-state conditions, but it does not reveal how latency behaves as traffic approaches system capacity. The M/M/1 queuing model (in Kendall’s notation: Markovian, that is Poisson, arrivals; Markovian, that is exponential, service times; and one server) quantifies the headroom required to prevent latency collapse ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-harchol-balter2013|Harchol-Balter 2013]]).[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn9|⁹]] For a system with Poisson arrivals[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn10|¹⁰]] and exponential service times, [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^eq-mm1-wait|equation 4]] gives the average time in system:

$$
{T_{\text{lat}}} = \frac{1}{{\mu}- {\lambda_{\text{arr}}}} = \frac{\text{service time}}{1 - {\rho_{\text{serv}}}} \tag{4}
$$

 where ${\lambda_{\text{arr}}}$ is the arrival rate, ${\mu}$ is the service rate (requests per second the server can handle), and ${\rho_{\text{serv}}} = {\lambda_{\text{arr}}}/{\mu}$ is the utilization (the fraction of time the server is busy).

^eq-mm1-wait

Because the denominator contains $1 - {\rho_{\text{serv}}}$, latency grows nonlinearly as utilization approaches unity, and small incremental increases in traffic near saturation trigger severe backpressure and queuing delays. The standard M/M/1 formulation assumes exponentially distributed service times. For compiled neural networks processing fixed-size batches and static tensor dimensions, execution times are nearly constant, making an M/D/1 queue a tighter model of mean queuing delay. The analysis here retains the M/M/1 model because it yields closed-form solutions and predicts greater mean queueing delay than M/D/1 under matched arrival rate and mean service time. In production environments, variable input lengths, dynamic batch formation, CPU preprocessing, and key-value cache lookups introduce runtime variance that quickly breaks deterministic assumptions.[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn11|¹¹]] Under this model, average time in system multiplies rapidly as utilization approaches 100 percent ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^tbl-utilization-latency|table 7]]).

| **Utilization $({\rho_{\text{serv}}})$** | **Latency Multiple** | **Example (3.5 ms service)** |
|:-----------------------------------------|:--------------------:|:----------------------------:|
| **50%**                                  |          2×          |            7.1 ms            |
| **70%**                                  |         3.3×         |           11.8 ms            |
| **80%**                                  |          5×          |           17.6 ms            |
| **90%**                                  |         10×          |           35.3 ms            |
| **95%**                                  |         20×          |           70.6 ms            |

Table 7: **Utilization-Latency Relationship**: Average time in system (wait + service) as a multiple of service time for an M/M/1 queue. At 50 percent utilization, time in system is 2× service time; at 90 percent, it reaches 10×. This nonlinear growth explains why systems that perform well at moderate load suddenly violate SLOs when traffic increases: moving from 80 percent to 90 percent utilization doubles latency.

^tbl-utilization-latency

Plotted against the serving utilization ${\rho_{\text{serv}}}$, the fraction of time the server is busy, the same ${M}/{M}/1$ model shows why the knee matters ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^fig-tail-latency-explosion|figure 5]]). Latency stays nearly flat at low utilization and then climbs without bound as the server approaches 100 percent busy, because each new arrival is increasingly likely to find work already waiting. The 99th percentile curve rises even faster in absolute terms, staying a fixed multiple above the mean that [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^sec-model-serving-tail-latency-5376|section 13.4.3]] derives next. The green zone below 50 percent utilization and the red zone above 70 percent illustrate a planning policy, not universal operating limits. This rapid compounding near saturation is why latency-sensitive systems reserve headroom rather than planning for permanently high accelerator occupancy.

### Tail Latency

^sec-model-serving-tail-latency-5376

A serving cluster running at 70 percent utilization can report a comfortable mean latency while its slowest 1 percent of requests take more than four times the mean to complete. Because averages hide this tail contention, production SLOs specify percentile targets (p95, p99) that bound experience for the slowest requests ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-dean2013|Dean and Barroso 2013]]).

The M/M/1 model that produced the mean in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^eq-mm1-wait|equation 4]] also yields the full latency distribution, and the tail follows from it. Total request latency (queue wait plus service) is exponentially distributed with cumulative distribution function ${F}({t}) = 1 - e^{-{t}/ {T_{\text{lat}}}}$, where ${T_{\text{lat}}} = \frac{\text{service time}}{1 - {\rho_{\text{serv}}}}$ is that mean response time. To derive the 99th percentile latency (p99), we solve for the time ${t}_{99}$ where 99 percent of requests have completed (${F}({t}_{99}) = 0.99$):

$$
1 - e^{-{t}_{99}/{T_{\text{lat}}}} = 0.99 \implies e^{-{t}_{99}/{T_{\text{lat}}}} = 0.01 \implies -\frac{{t}_{99}}{{T_{\text{lat}}}} = \ln(0.01) = -\ln(100) \approx -4.605
$$

 Solving for ${t}_{99}$ and substituting the mean latency ${T_{\text{lat}}}$ yields the governing expression for tail latency:

$$
{T_{\text{lat},\text{p99}}}\approx \frac{\text{service time}}{1 - {\rho_{\text{serv}}}} \cdot \ln\left(\frac{1}{1 - 0.99}\right) \approx \frac{4.6 \cdot \text{service time}}{1 - {\rho_{\text{serv}}}} \tag{5}
$$

^eq-p99-latency

At 70 percent utilization, average latency is only 3.3× service time, while p99 latency reaches 15.3× service time $(4.6/0.3 \approx 15.3)$. Evaluating a serving cluster by average latency therefore conceals severe tail degradation. Before exploring software mitigations like hedging, systems engineers must first provision sufficient accelerator capacity to satisfy tail-latency SLOs under peak load. For a ResNet-50 deployment, the M/M/1 tail-response-time model turns provisioning into a short sequence of steps.

**Napkin Math 13.3: ResNet-50 capacity planning**

Consider designing a ResNet-50 serving system with these requirements:

- **Queue-plus-GPU p99 subbudget**: 50 ms
- **Peak expected traffic**: 5,000 QPS
- **GPU service time** (batch one, the chapter’s reference ResNet-50 profile): 3.5 ms

**Step 0**: Define the modeled request boundary. The worker model covers waiting for the GPU and the GPU forward pass only. This scenario gives the worker a p99 subbudget of 50 ms. All stages outside the worker (network transit, serialization, preprocessing, transfer, and postprocessing) get a separate combined upper bound of 18 ms. The end-to-end deadline is therefore the worker’s 50 ms plus those 18 ms.

**Step 1**: Find safe utilization. From [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^eq-p99-latency|equation 5]], ${T_{\text{lat},\text{p99}}}\approx$ 4.6 $\times$ service time / $(1 - {\rho_{\text{serv}}})$. Setting ${T_{\text{lat},\text{p99}}}\leq$ 50 ms with 3.5 ms service time gives ${\rho_{\text{serv}}} \leq 1 - (4.6 \times 3.5\,\mathrm{ms})/50\,\mathrm{ms} = 0.68$ (68 percent maximum utilization). This is an M/M/1 p99 estimate under the stated arrival and service assumptions; a load test must validate the tail.

**Step 2**: Calculate required service rate. ${\mu_{\text{required}}} = 5,000\,\mathrm{QPS} / 0.68 = 7402.9\,\mathrm{req}/\mathrm{s}$

**Step 3**: Determine GPU count. In this M/M/1 model, the single-GPU rate is 283 req/s.

GPUs needed = 7402.9 req/s / 283 req/s = 26.1 → 27 GPUs

This single-GPU rate is the batch-1 service rate. Each request holds the GPU for the full service time, which keeps the M/M/1 model closed-form. Dynamic batching ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-throughput-optimization-18d1|section 13.5]]) amortizes fixed overhead across requests and raises the per-GPU rate several-fold, so a batched deployment may need fewer GPUs after its own latency distribution is validated. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.11 Economics and Planning#^sec-model-serving-capacity-planning-96a3|Section 13.10.2]] compares the two regimes.

**Step 4**: Add headroom for variance. This scenario adds 30 percent headroom for traffic spikes and variance: final count = 27 $\times$ 1.3 = 35.1, rounded up to 36.

**Step 5**: Verify fault tolerance. The 30 percent headroom addresses traffic variance, but production systems also need fault tolerance. With 36 GPUs, losing one leaves 35 GPUs handling 5,000 QPS. The postfailure utilization is 5,000 QPS / (283 req/s $\times$ 35) = $50.4\%$.

This remains well below the 68 percent safe utilization threshold, confirming N+1 redundancy, enough capacity to lose any one GPU and still meet the target. For stricter fault tolerance requirements, N+2 redundancy (tolerating two simultaneous failures) would require 29 GPUs under the same safe-utilization threshold, or about 38 GPUs if the 30 percent headroom must remain after two simultaneous failures.

**Result**: Under the batch-1 M/M/1 assumptions, 36 H100 GPUs supply the modeled queue-plus-GPU capacity for 5,000 QPS within the 50 ms p99 subbudget, including one failed replica. End-to-end acceptance still requires validating the tail under load and the separately reserved outside-worker allowance.

The queuing analysis explains the capacity planning approach detailed in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.11 Economics and Planning#^sec-model-serving-capacity-planning-96a3|section 13.10.2]] and connects directly to the MLPerf Server scenario. The Server scenario (**[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.05 Benchmark Suites#^sec-benchmarking-server-e69f|Server]]**) is defined as Poisson arrivals scored by throughput against a tail-latency target. A Server result is therefore valid only when the run satisfies its percentile-latency constraint; otherwise, the target QPS must be reduced and the run repeated.

### Tail-Tolerant Techniques

^sec-model-serving-tailtolerant-techniques-066e

A capacity plan built on stationary Poisson arrivals holds only while traffic stays near the planned rate. Production traffic instead arrives in bursty, uncoordinated surges driven by user behavior, scheduled jobs, and daily cycles. When a surge pushes arrivals past the reserved headroom, accelerator service times cannot shrink to absorb the excess, so queries pile up in host and device queues and clients begin timing out.

**Example 13.3: The 'Black Friday' traffic spike**

**Scenario**: An e-commerce recommendation serving system experiences a 10× traffic surge (10,000 QPS) during Black Friday sales events.

**Diagnosis**: A fleet sized for normal traffic now receives more requests per second than it can complete. Utilization pins at 100 percent, and every second of the surge adds the excess arrivals to a queue that the servers cannot drain, so waiting time grows for as long as the surge lasts. In this scenario, latency reaches 10 s and clients time out. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^sec-model-serving-utilizationlatency-relationship-a2f0|Section 13.4.2]] showed why the queue starts growing sharply well before utilization reaches 100 percent.

**Systems lesson**: High average throughput does not prevent queueing collapse under traffic surges. Depending on the service, preserving a tail-latency objective may require load shedding, graceful degradation, or autoscaling, which adds replicas automatically as load rises, before utilization reaches the workload’s queueing knee.

^exmp-model-serving-black-friday-traffic-spike

Eliminating all sources of latency variability is often impractical. Production systems instead use techniques that tolerate variability while still meeting SLOs ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-dean2013|Dean and Barroso 2013]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-dean2012rapid|Dean 2012]]). For one serving node, the first distinction is between an isolated straggler and overload. Racing an isolated slow request, by sending a duplicate to another worker and keeping whichever answer returns first (the hedging of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^sec-model-serving-tail-scale-problem-958d|section 13.4.5.1]]), can reduce its latency when spare capacity exists. When the node is overloaded, however, racing requests injects duplicate work and deepens the queue, so the system must instead protect the latency of admitted requests through graceful degradation or admission control.

Graceful degradation returns lower-fidelity results to preserve throughput: classification pipelines fall back to cached approximations, generative models truncate decoding lengths, and model ensembles evaluate only a subset of members. Dynamically reducing active ensemble members shortens the service time ${T_{\text{svc}}}({B})$ of each batch of ${B}$ requests ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-throughput-optimization-18d1|section 13.5]] develops batching; without it, ${B} = 1$). The shorter service time increases the effective service rate ${\mu_{\text{eff}}}({B}) = {B}/{T_{\text{svc}}}({B})$ and lowers utilization ${\rho_{\text{serv}}} = {\lambda_{\text{arr}}} / {\mu_{\text{eff}}}({B})$ toward a workload-appropriate operating point with more headroom, as illustrated by [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^fig-tail-latency-explosion|figure 5]]. The system trades a controlled accuracy reduction for SLO survival instead of an uncontrolled latency collapse.

**Admission control** (also called load shedding) enforces a stricter boundary than degradation. When the ingress queue exceeds a designated threshold, the server immediately rejects excess queries with HTTP 503 status codes rather than admitting work doomed to violate its latency deadline. Rejection sheds load only if clients wait before retrying, with the exponential backoff of **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^sec-data-engineering-reliability-graceful-degradation-f83d|Reliability through graceful degradation]]**; clients that retry immediately return that load to a server already past capacity.

Setting this rejection threshold requires comparing how long the arriving request can afford to wait against how long the work already ahead of it will take to drain. Consider a warmed, isolated worker that serves requests one at a time in first-in-first-out (FIFO) order, and assume known upper bounds on each request’s service time and on every stage outside the worker, including the response path.

An arriving request has already spent part of its end-to-end allowance on network ingress and preprocessing, and it must still reserve time for its own execution and for the stages that follow. Subtracting the time already spent, the remaining outside-worker bound, and the request’s own service bound from the deadline leaves its **waiting allowance**, the longest it can sit in the queue and still finish on time. The work it would wait behind is the worker’s **outstanding-work bound**, the remaining service bound of the request now executing plus the service bounds of all requests already queued. Comparing the two gives the **deadline screen**, and the request passes only when the outstanding-work bound fits within the waiting allowance. A negative allowance means the request would miss its deadline even on an idle worker.

A simple limit on queue length approximates the deadline screen only when service costs are nearly uniform across requests. When they are, a practical starting point bounds the ingress queue at two or three requests per worker, the backlog a worker clears within two or three further service times, and the deadline screen and measured tails then tighten or relax that bound.

When the backlog exceeds the full model’s waiting allowance, a smaller fallback model that is already resident and warmed may still fit. The fallback does not shorten the backlog ahead of the request, but it reserves less service time for the request’s own execution, which enlarges the waiting allowance. If neither model fits and meets the application’s minimum quality, rejection avoids spending accelerator time on a result that would arrive too late.

Rejection reduces availability, and fallback can reduce prediction quality, so reported tails must count both. Otherwise, shedding difficult requests makes the service appear successful merely by shrinking its measurement population.

The deadline screen is a deterministic bound only under its stated assumptions. Mean service time or a per-stage p99 cannot replace its upper bounds, and variable input lengths, batch formation, and shared memory-bus contention require calibration against measured request latency. Production frameworks may also use shortest-job-first or deadline-aware scheduling rather than FIFO, which changes what lies ahead of an arrival and requires a corresponding admission analysis ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-harchol-balter2013|Harchol-Balter 2013]]). Neither a fixed queue count nor the simplified screen certifies a production p99 target.

### Scaling Across Multiple Replicas

^sec-model-serving-multiserver-considerations-00fc

Once traffic outgrows a single node’s safe utilization knee, no single-machine tuning can prevent queue build-up. Higher aggregate volume requires **horizontal replication**, placing identical model replicas behind a load balancer so that each holds a complete model copy and serves disjoint queries without inter-node synchronization. (Model parallelism, which shards one large model across accelerators linked by a fabric such as NVLink, solves a different problem: fitting a model that exceeds one device’s memory or latency budget.) The ${M}/{M}/{c}$ queuing model extends the single-server analysis to ${c}$ parallel workers. Provided dispatch is balanced (least-loaded routing, for example) and each replica keeps its own headroom, pooling requests in one shared queue absorbs arrival bursts better than isolated single-server queues. Pooling helps because no worker sits idle while requests still wait for another worker.

#### The Tail at Scale Problem

^sec-model-serving-tail-scale-problem-958d

Dean and Barroso’s analysis shows why tail latency matters more as systems scale beyond single machines ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-dean2013|Dean and Barroso 2013]]). When requests fan out to ${m}$ parallel backends (querying an ensemble of models, searching sharded embedding indices, or parallelizing pipeline stages), the overall user request completes only when the slowest sub-task finishes. If sub-task completion events are independent and each has a 99 percent probability of finishing within latency threshold ${L_{\text{lat,SLO}}}$, the probability that all ${m}$ backends finish within ${L_{\text{lat,SLO}}}$ is $(0.99)^{m}$. For a fan-out of ${m}= 10$, only $0.99^{10} \approx 90.4\%$ of requests meet the target; at ${m}= 100$, that probability drops to $0.99^{100} \approx 36.6\%$, meaning nearly two-thirds of user requests experience a tail delay. This “tail at scale” effect means that overall system performance depends on controlling single-node tail variance.

Hedging and tied requests limit the damage from a straggler replica. Under hedging, a request that has not completed within the expected time is duplicated to another server, and the client keeps whichever response arrives first.[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn12|¹²]] With a stable latency distribution, a threshold at the historical 95th percentile duplicates about 5 percent of requests; correlated slowdowns raise that fraction and can make hedging amplify overload instead of reducing the tail. Tied requests instead enter several server queues at once and cancel the other copies when one server begins processing, which avoids waiting to detect a slow response. Both techniques create duplicate work. Cancellation before dispatch prevents a losing copy from consuming accelerator time, whereas cancellation after dispatch only discards its result, so either needs spare capacity and an explicit duplicate-work budget. Canary requests, a different use of the word from the canary rollouts that shift traffic between model versions, apply the same idea to fan-out, sending the request first to one or two servers and committing to the full fan-out only if they answer within the expected time. Replicas or streams on one machine can also race requests, but sharing an accelerator or memory bus can correlate their slowdowns and exhaust the same headroom.

**Checkpoint 13.2: Queuing and SLO headroom**

Latency SLOs are not enforced by *fast inference* alone; they are enforced by *headroom*.

**Little’s Law**: at a fixed stable throughput, can you use ${Q_{\text{req}}} = {\lambda_{\text{arr}}} {T_{\text{lat}}}$ to explain why a higher average in-system population implies a higher mean response time, even if per-request compute time is unchanged?

**Utilization cliff**: can you explain why latency grows nonlinearly as utilization ${\rho_{\text{serv}}}$ approaches one, and why production systems target a conservative ${\rho_{\text{serv}}}$ rather than “100 percent busy”?

**Queue behavior**: use the mean and p99 curves in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^fig-tail-latency-explosion|figure 5]] to explain nonlinear latency growth near saturation. Why is the marked 70 percent knee an illustrative planning choice rather than a model-derived breakpoint?

**Capacity planning**: can you explain why a throughput number is only “real” if requests still meet the percentile latency SLO under load?

**Admission decision**: for the isolated FIFO worker, how does increasing the arriving request’s service bound change its waiting allowance? If a faster fallback fits behind the outstanding work, what quality and availability conditions distinguish admitting it from rejecting the request? Why would substituting measured mean times invalidate the deterministic bound?

**Headroom estimate**: a stable service handles 2,000 requests per second and measures a 10 ms mean response time. Use ${Q_{\text{req}}} = {\lambda_{\text{arr}}} {T_{\text{lat}}}$ to estimate its average in-flight population. Why does this result alone not establish compliance with a 50 ms p99 SLO?

Headroom keeps the queue stable by leaving capacity idle, and adding replicas creates headroom by adding accelerators. The other way to keep utilization below the knee is to raise each replica’s service rate, and for an accelerator that executes one request at a time the largest lever is to execute several at once.
