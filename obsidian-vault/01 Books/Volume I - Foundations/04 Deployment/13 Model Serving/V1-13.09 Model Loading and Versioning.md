# V1-13.09 Model Loading and Versioning

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-model-lifecycle-management-ff2e

Every optimization so far assumed a replica that is already warmed up in device memory and a host pipeline that reproduces the exact transformations used during training. Both assumptions fail at the edges of a replica’s lifecycle. Provisioning a new container or swapping an active model stalls traffic until weights and compiled engines are resident on the device, and any drift between training and serving preprocessing silently corrupts accuracy even when every latency target is met.

### Cold Start and Initialization Dynamics

^sec-model-serving-model-loading-initialization-cc5a

When an autoscaler spins up a new serving container during a traffic surge, that replica can sit dark for 35 seconds before answering its first request, most of them spent compiling an execution engine after fetching weights from remote storage ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-romero2021infaas|Romero et al. 2021]]). That initialization delay, known as cold start, governs how quickly a service recovers from node failures or scales out into a spike.

**Definition 13.4: Cold start**

***Cold start*** is the initialization latency incurred when starting a new model replica.

1.  **Significance**: It represents the fixed startup cost of loading weights, compiling graphs, and allocating buffers, which can take seconds or minutes and block elastic scaling during traffic bursts.
2.  **Distinction**: Unlike inference latency $({L_{\text{lat,infer}}})$, which is a per-request cost, cold start is an initialization cost paid when a replica or model instance is created, including deployment, scale-out, recovery, and on-demand model loading.
3.  **Common pitfall**: A frequent misconception is that cold start is “just loading weights.” In reality, it includes graph compilation and memory allocation, which can often take longer than the bandwidth-limited data transfer itself $({D_{\text{vol}}}/{\text{BW}})$.

Total cold-start latency compounds across four physical operations along the initialization path. Weight loading streams serialized parameters from persistent storage across the network or host I/O subsystem into host memory and then across the PCIe bus into GPU HBM. Graph compilation then lowers the framework computational graph into device-specific machine code by fusing operators and auto-tuning matrix multiplication kernels for the target accelerator. Once the compiled graph is ready, memory allocation reserves device arenas for activation scratchpads and intermediate buffers. Warmup[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn18|¹⁸]] execution then runs synthetic inferences to populate kernel caches, prime framework memory allocators, and complete any remaining lazy initialization before live traffic arrives.

Establishing a CUDA context is the first fixed cost on the device initialization timeline. Before launching any GPU kernel or allocating device memory, the runtime must instantiate a driver-level context: an internal control structure that manages virtual address spaces, loaded kernel binaries, and hardware event queues. Creating this context requires synchronous communication with the kernel-mode driver and allocates tens to hundreds of megabytes of device memory for bookkeeping. The 0.3–0.5 s range in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.09 Model Loading and Versioning#^tbl-model-serving-resnet-coldstart|table 17]] reflects a typical data center environment. While CUDA lazy loading defers kernel module loading to shorten this initial pause, it merely defers that latency penalty to the first executed inference ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidiaCudaLazyLoading|NVIDIA 2026a]]).

In multi-process serving deployments where multiple worker processes share a single accelerator, replicating individual CUDA contexts wastes both memory capacity and initialization time. CUDA Multi-Process Service (MPS) coordinates concurrent work from multiple client processes, reducing scheduling overhead when individual processes underuse the device ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidiaCudaMps|NVIDIA 2026d]]). From the Volta generation (2017) onward, clients keep separate GPU address spaces and contexts while their kernels can execute concurrently, but separate address spaces do not provide hard fault containment. A fatal GPU fault can affect other clients sharing the affected GPU, so the serving design must budget for correlated replica failures.

**Example 13.9: ResNet-50: Cold start timeline**

[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.09 Model Loading and Versioning#^tbl-model-serving-resnet-coldstart|Table 17]] traces the per-phase duration of a ResNet-50 cold start:

| **Phase**                       | **Duration** | **Notes**                                           |
|:--------------------------------|:------------:|:----------------------------------------------------|
| **Weight loading (SSD)**        |    0.5 s     | 102.2 MB FP32 weights from local storage            |
| **Weight loading (S3)**         |    3–5 s     | Network latency dominates for cloud storage         |
| **CUDA context**                |  0.3–0.5 s   | GPU driver initialization and memory setup          |
| **TensorRT compilation**        |   15–30 s    | Converts PyTorch model to optimized engine          |
| **Warmup (10 inferences)**      |    0.2 s     | Triggers remaining lazy initialization              |
| **Runtime overhead**            |    0.4 s     | Process startup, framework hooks, and runtime setup |
| **Total (local, optimized)**    |  **~1.5 s**  | With precompiled TensorRT engine, warm container    |
| **Total (cloud, first deploy)** |  **~35 s**   | Including compilation from cold state               |

^tbl-model-serving-resnet-coldstart

**Systems insight**: Precompiling models and storing the optimized engine eliminates the 30 s compilation phase on subsequent deployments.

^exmp-model-serving-resnet-50-cold-start-timeline

Without warmup, the first live request absorbs deferred JIT compilation, driver memory allocation, and kernel launch overhead. A request whose steady-state forward pass takes 3.5 ms can stall for hundreds of milliseconds during an unmitigated cold start, violating strict SLOs. Cold start also delays capacity. An autoscaler that adds replicas when a surge begins gains no useful throughput until each new replica has finished the whole timeline above, so the existing replicas absorb the surge alone for that long. A warm pool keeps a few spare replicas already loaded and warmed but receiving no traffic, so a scale-out event can route requests to them at once and pays the cold start only when the pool is refilled. Shortening the timeline itself requires systematic selection among storage, memory, and runtime loading strategies.

### Loading Strategies and Serialization Formats

^sec-model-serving-loading-strategies-eb38

Once precompilation removes the 30 s compiler step from [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.09 Model Loading and Versioning#^tbl-model-serving-resnet-coldstart|table 17]], weight loading becomes the largest remaining term in the startup budget, and how the server schedules that read trades cold-start duration against first-request latency and memory footprint. The simplest approach, full loading, reads the entire model into memory before the server marks itself ready. This maximizes steady-state inference speed because all weights are resident in memory, but it stretches cold-start time and restricts model size to available memory. A second strategy, lazy initialization, defers compilation and allocation until first use. This minimizes startup time but shifts latency to the first request, so production systems often combine lazy initialization with synthetic warmup requests to trigger initialization before real traffic arrives.

Under either loading schedule, reading a multi-gigabyte checkpoint from persistent storage into host memory dominates the remaining initialization time once compilation is moved offline. Whether that read runs at NVMe bandwidth or stalls on single-threaded CPU parsing depends on the checkpoint’s serialization format.

Legacy PyTorch checkpoints loaded via `torch.load()` package weights within a zip archive containing pickle-encoded object metadata. Deserializing a pickle file forces the CPU to interpret a stream of serialization opcodes sequentially, allocating individual Python objects (dictionaries, metadata wrappers, and tensor headers) and potentially copying tensor bytes into newly allocated memory. Restricted loading modes reduce arbitrary code execution risks, while memory-mapped options can avoid some eager copies. Whether parsing or storage dominates depends on the checkpoint, loading path, and hardware.

A tensor-oriented format[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn19|¹⁹]] bypasses interpreter-driven object construction. Safetensors organizes checkpoints with a lightweight header containing tensor metadata followed by contiguous, uncompressed tensor byte buffers aligned to memory boundaries. Because the on-disk binary layout mirrors the in-memory array layout, the runtime can use memory mapping (`mmap(2)`), which maps file blocks directly into the process’s virtual address space. Virtual memory pages fault into host RAM on access or are prefetched sequentially by the operating system, reducing Python object reconstruction and avoiding eager user-space tensor copies on the mapped path.

Mapping shortens apparent startup, but a dense model eventually touches nearly all of its weights, so deferred page faults can move loading latency into early requests. The benefit is greater for sparsely accessed components or model repositories that load subsets on demand; latency-sensitive services still prefault or warm the pages needed on the request path. On systems with discrete accelerators, transferring these tensors across PCIe or NVLink is still required before computation begins, so memory-mapped host loading reduces CPU reconstruction costs without eliminating page faults, storage reads, or device initialization.

**Example 13.10: Loading speed: Safetensors vs. Pickle**

**Scenario**: A serverless inference replica loads a 5 GB model checkpoint during cold-start scaling events.

**Diagnosis**: PyTorch `torch.load()` (Pickle) requires CPU object reconstruction, taking 15 s to initialize. Safetensors memory-mapping bypasses CPU parsing, loading weights in 1.5 s (10× faster).

**Systems lesson**: Tensor-oriented, memory-mapped formats can reduce CPU reconstruction and eager-copy overhead during cold start. Storage throughput, page faults, runtime initialization, and accelerator transfer still remain in the scale-out budget.

### Model Caching Infrastructure

^sec-model-serving-model-caching-infrastructure-4f1a

A zero-copy format like Safetensors can only load as fast as the underlying storage tier delivers bytes, so production systems pair fast checkpoint formats with infrastructure-level weight caching matched to how often the model changes. Embedding the weights in the container image yields a single deployment artifact with no network fetch at startup, but images of 10–50 GB slow every container pull, so the approach suits models that rarely update. A shared filesystem of versioned weights lets many replicas read one copy without rebuilding images, at the price of network latency in every cold start and a new availability dependency. It still requires an explicit, atomic version switch so that files never change underneath a live replica.

Node-local SSD caching prepopulates Non-Volatile Memory Express (NVMe) drives on inference nodes with frequently used models and loads at several GB/s without the network, but it needs its own refresh policy as models update. Which versions those caches hold, and how a new version replaces an old one in production, belongs to the release process of **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-model-deployment-b9b9|Model deployment]]**; once those cached weights reach a node, the next question is how multiple models or versions share its GPU memory.

### Multi-Model Serving

^sec-model-serving-multimodel-serving-a9c1

Dedicating an entire GPU to each regional model, A/B candidate, or ensemble stage leaves most of the fleet idle whenever traffic to individual models is uneven, yet packing several models onto one GPU without coordination risks out-of-memory crashes and noisy-neighbor latency spikes. Production systems therefore share a single machine across multiple models, making GPU memory capacity and bandwidth isolation the primary constraints.

How a server manages that shared memory depends on whether models fit in VRAM simultaneously. When the combined footprint exceeds device capacity, time-multiplexing loads one model at a time and swaps weights on demand as routing changes, keeping implementation simple at the cost of swap latency. When several models fit together, memory sharing partitions GPU memory among them so that more models remain resident without swapping, even though each model receives a smaller concurrency budget. Across both regimes, model virtualization, as implemented by frameworks like Triton, decouples model lifecycle from application code by exposing repository and control APIs that load, unload, and version models dynamically ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidia-triton-c2de726e|NVIDIA 2024b]], [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidiaTritonModelRepository|2026c]], [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidiaTritonModelManagement|2026b]]). Which policy wins depends on the arrival mix. Steady traffic across models favors keeping them concurrently resident, whereas bursty, model-specific traffic favors time-multiplexing with explicit preloading to balance average latency against GPU utilization.

#### Partitioning One GPU Across Models

^sec-model-serving-multistream-execution-1b1f

When multiple models or multiple instances of the same model must run concurrently on a single GPU, the hardware must partition resources between them. NVIDIA’s Multi-Instance GPU[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn20|²⁰]] technology enables hardware-level isolation, dividing a data-center GPU such as the H100 into up to seven independent GPU instances, each with dedicated memory and compute resources ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidiaMigUserGuide|NVIDIA 2026e]]). On GPUs without MIG, CUDA stream scheduling permits overlapping or time-multiplexed work without hardware partitioning. The choice depends on whether consistent latency with MIG or maximum utilization with shared streams is the priority.

#### Model Swapping and Host Memory

^sec-model-serving-model-swapping-host-memory-c54f

When the aggregate size of all models exceeds GPU memory capacity, the serving system must swap models between host dynamic random-access memory (DRAM) and device memory (VRAM) on demand. This introduces a new latency component determined by the PCIe bus bandwidth. For a 10 GB model on PCIe Gen4 x16 (32 GB/s theoretical bandwidth), loading takes at least 312.5 ms before deserialization, graph setup, or warmup. This raw transfer latency dwarfs a tight service-level objective such as a 50 ms deadline by more than 6×, rendering on-demand model swapping unviable on the interactive request path.

![[90 Assets/Volume I/13 Model Serving/Vol1 Model Serving Margin 001 29f0301ce9.svg]]

*Horizontal millisecond scale with a dashed red 50 ms SLO marker far left of a red model-load dot labeled 312.5 ms, with the region past the SLO shaded light red.*

*Model loading lands far outside a tight serving SLO.*

To accelerate this transfer path, systems keep the weights in pinned memory (page-locked host RAM), because the CPU must first copy a pageable buffer into a pinned staging buffer before DMA can move it across PCIe. Allocating model weights with `cudaHostAlloc` removes that CPU staging copy; achieved bandwidth still depends on transfer size, memory locality, and contention.

For serving, pinning adds a capacity trade-off. Pinned memory cannot be paged out or reclaimed by the OS under memory pressure, so every pinned model holds its share of physical host RAM until it is released. High-throughput serving systems therefore pin active model weights and I/O ring buffers while leaving standby model checkpoints in pageable memory.

↩︎ Pinned memory and the DMA staging copy it avoids are established in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.06 Abstraction Tensors, Devices, and Operations#^sec-ml-frameworks-os-interface|Frameworks as the operating system interface]]**.

### Training-Serving Skew

^sec-model-serving-trainingserving-skew-7b99

↩︎ Training-serving skew and the consistency imperative it violates are established in **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-ensuring-trainingserving-consistency-c683|Training-serving consistency]]**.

Loading the exact checkpoint that training produced still does not guarantee that the server computes the same function if the host pipeline transforms raw inputs differently before those weights ever run. A model that performed well during validation degrades silently in production whenever training-serving skew causes the two paths to compute different features from the same raw input while every latency and error-rate dashboard stays green. The consistency requirement belongs to the data pipeline; serving is where a violation surfaces, and because the divergence is measurable on identical inputs without labels (principle [[01 Books/Volume I - Foundations/04 Deployment/V1 Deployment Principles#^pri-training-serving-skew|11]]), it is also one of the most preventable failures. **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-trainingserving-skew-diagnosis-prevention-9dc1|Training-serving skew: Diagnosis and prevention]]** catalogs the skew categories and the method that detects each.

The serving-specific manifestation of skew is **preprocessing divergence**: the real-time inference pipeline processes raw data differently than the batch training pipeline, a common failure mode when training uses Python/Pandas while serving uses C++/Java or optimized inference servers.

**Example 13.11: ResNet-50: Image preprocessing skew**

**Scenario**: ResNet-50 vision serving models experience silent prediction accuracy degradation between offline training and online serving pipelines.

**Diagnosis**: The serving pipeline implemented C++/OpenCV preprocessing (`cv2.INTER_LINEAR`, BGR order) while training used Python/PIL (`PIL.BILINEAR`, RGB order, different normalization constants).

**Systems lesson**: Preprocessing divergence causes silent training-serving skew without raising runtime exceptions. Standardizing data transformation pipelines across training and serving environments prevents input distribution corruption.

^exmp-model-serving-resnet-50-image-preprocessing-skew

A replica that loads quickly, runs predictably, and computes what training computed completes fixed-output serving. Every workload so far, however, has treated a request as one completed prediction. The fastest-growing category of serving workloads violates this assumption entirely. Large language models generate outputs token by token, with each token depending on every previous one. A single request may produce hundreds or thousands of tokens over seconds of elapsed time, yet must feel responsive from the first token onward. The shift from *fixed-output* to *variable-length, streaming-output* serving reopens each tool developed so far, from the latency budget to the runtime.

**Self-Check: Question**

1.  A computer vision team trains a ResNet-50 model in PyTorch using torchvision’s PIL-based bilinear image resizing. In production, high-throughput C++ inference servers use OpenCV’s `cv::resize` with default bilinear interpolation. On matched input images, the team observes different preprocessed tensors; when they rerun evaluation with the training preprocessing path, the original accuracy returns. What phenomenon is causing this degradation, and what is the proper engineering solution?

    1.  Training-serving skew caused by subtle implementation differences in resize anti-aliasing and pixel coordinate rounding between PIL and OpenCV; the solution is using shared or parity-verified preprocessing across training and serving, such as a common library or exportable graph when supported.
    2.  Accelerator thermal throttling caused by high frame rates; the solution is downclocking the GPU Tensor Cores.
    3.  Floating-point precision drift between Python and C++; the solution is switching all production inference to 64-bit double precision.
    4.  Catastrophic forgetting in the weights caused by static batching; the solution is retraining the model with dynamic dropout.

2.  Why does simply copying model weights into GPU HBM upon container startup fail to prevent latency spikes on the very first incoming user requests, and how does executing a ‘warmup pass’ resolve this issue?

3.  Sequence the stages of an illustrative serial cold-start initialization workflow when autoscaling an inference server pod from an idle state to serving live production traffic:

<!-- -->

1.  Initialize device context or runtime state needed before host-to-device copies, then transfer model weights from host staging memory to GPU High-Bandwidth Memory (HBM) over PCIe
2.  Fetch model checkpoint artifacts and configuration from remote object storage (e.g., S3) to local NVMe SSD cache
3.  Initialize remaining execution-engine state, allocate memory pools, and run synthetic dummy warmup passes
4.  Container initialization, environment bootstrap, and runtime dependency loading
5.  Register pod as healthy with load balancer gateway to begin receiving live traffic
6.  Memory-map (`mmap`) or deserialize model weights from local SSD into host memory, with explicit pinned staging buffers if the transfer path uses them

4.  True or False: In multi-model serving on a shared GPU, Volta-era NVIDIA Multi-Process Service (MPS) provides hard physical hardware partitioning of high-bandwidth memory (HBM) channels and compute cores, completely preventing memory out-of-memory (OOM) faults caused by co-located tenant models.

5.  A multi-model serving platform hosts 50 distinct fine-tuned vision models on a single GPU node with 24 GB of VRAM. Each model requires 2 GB of memory, exceeding total VRAM capacity. Traffic to individual models is sporadic. What loading and memory management architecture enables serving all 50 models while minimizing request latency?

    1.  Redeploy the cluster on 50 dedicated GPU nodes running continuous batching 24/7.
    2.  Quantize all models to 1-bit weights to fit all 50 models into GPU L2 cache simultaneously.
    3.  Maintain a tiered memory cache (storing active models in GPU VRAM and inactive models in host pinned DRAM), using asynchronous PCIe DMA transfers to swap weights into VRAM on demand with an LRU eviction policy.
    4.  Compress all models into a single shared zip archive on remote S3 and download the entire archive over HTTP on each incoming request.

6.  Why can loading model weights from modern `safetensors` format provide faster startup times than some legacy PyTorch checkpoint paths?

    1.  `safetensors` files compress weights using gzip, reducing disk storage by $10\times$.
    2.  `safetensors` files store raw tensor buffers in a simple deterministic layout that supports memory mapping (`mmap`) without Python object deserialization or arbitrary code execution.
    3.  `safetensors` files compile PyTorch code directly into binary x86 machine instructions on disk.
    4.  `safetensors` files automatically quantize FP32 weights into 4-bit integers during read operations.
