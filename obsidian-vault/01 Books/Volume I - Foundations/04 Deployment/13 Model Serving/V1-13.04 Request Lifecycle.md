# V1-13.04 Request Lifecycle

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-request-lifecycle-d9c6

When a single HTTP request carrying a $224{\times}224$ JPEG image arrives at an inference server, the clock starts on the client’s deadline as soon as the first byte enters the network stack and stops only when the classification payload departs. Between those two boundaries, the request must be decoded on the host, copied across the interconnect, evaluated on the accelerator, and formatted into a response, with every stage drawing from the same millisecond allowance.

### The Latency Budget

^sec-model-serving-latency-budget-ef40

A vision service that completes thousands of classifications per second still fails its users if individual requests take two seconds to return and miss their interactive deadlines. For dynamic inference systems, the serving inversion established in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.02 The Serving Inversion#^sec-model-serving-serving-paradigm-9634|section 13.1]] therefore imposes a strict latency budget across the entire request path ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-gujarati2020|Gujarati et al. 2020]]).

Under that budget, the metrics that matter expand from aggregate throughput and mean latency to the latency distribution. Mean and p50 describe the center, while p95 and p99 expose the slow tail. If mean latency is 50 ms but p99 is 2 s, the p99 threshold is 40× the mean, so about 1 percent of requests are at or beyond 2 s. Whether that tail matters depends on the service and its users, which is why percentile targets should come from the SLO rather than convention.[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn8|⁸]] Managing these percentile constraints requires decomposing the total allowed response time into a **latency budget** that allocates time across each processing phase, the serial accounting that the latency budget principle ([[01 Books/Volume I - Foundations/04 Deployment/V1 Deployment Principles#^pri-latency-budget|12]]) states formally.

**Definition 13.2: Latency budget**

***Latency budget*** is the time allocated to request stages under an end-to-end deadline; the SLO also specifies the required completion quantile.

1.  **Significance**: It acts as a zero-sum constraint system where any milliseconds consumed by serialization or network overhead directly reduce the share of the end-to-end budget (${L_{\text{lat,total}}}$) left for model inference.
2.  **Distinction**: The budget allocates time across stages, while the latency SLO of **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.07 Inference Benchmarks#^sec-benchmarking-latency-tail-latency-5cde|Latency and tail latency]]** couples the deadline (for example, $<50\text{ ms}$) with a completion quantile ($\text{p99}$ or $\text{p99.9}$). A service-level indicator (**SLI**) is the measured quantity used to evaluate that objective.
3.  **Common pitfall**: A frequent misconception is that the “model” has the entire budget. In the illustrative breakdown in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^tbl-model-serving-resnet50-latency-budget|table 3]], the remainder is consumed by host preprocessing and data movement (JPEG decode, resize, normalization, and PCIe transfer), while upstream network and serialization overheads ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^tbl-serving-tax|table 5]]) consume further margin.

![[90 Assets/Volume I/13 Model Serving/Model Serving Latency Budget Bar 2b3599d3ab.svg]]

*Horizontal stacked bar of the request latency budget: a gray preprocessing segment on the left, an orange inference segment of about the same width in the middle, and a thin gray trailing segment on the right. Inference is one slice among equals rather than the whole budget.*

*Inference is one slice of the latency budget; preprocessing rivals it.*

Every serving request traverses three sequential phases that share this latency budget. Preprocessing converts raw input such as image bytes or text strings into model-ready tensors, inference executes the model computation over those tensors, and postprocessing turns the resulting device outputs into user-facing responses. Counting the network and the queue as well, the full budget is spent serially on network ingress, deserialization, preprocessing, queueing, transfer to the accelerator, inference, postprocessing, and egress of the response back to the client. Accelerating model execution alone yields diminishing returns when host-side preprocessing and response formatting consume the majority of the latency budget, an immediate manifestation of Amdahl’s law. As hardware compilers compress accelerator kernel runtimes into sub-millisecond durations, host-device coordination and memory transfers emerge as the primary latency bottlenecks.

### Stage-By-Stage Latency Breakdown

^sec-model-serving-latency-distribution-analysis-b0f8

An engineer who measures only total request duration in a vision service sees a single millisecond number that lumps together CPU-bound JPEG decompression, host-to-device PCIe transfers, accelerator kernel execution, and response formatting. It is then easy to spend weeks optimizing GPU kernels that account for less than half of total response time. Timing each pipeline boundary independently isolates the actual bottleneck before optimization begins.

The forward pass in the breakdown below comes from the chapter’s reference profile for ResNet-50, and that profile is modeled from the iron law’s terms rather than measured. It assumes an eager framework running FP16 on the reference H100, which gives a 3.5 ms batch-one forward pass, and every later ResNet-50 example derives from it. The framework issues 174 kernels, one per operation, and each pays 10 μs of Python dispatch and 5 μs of driver launch, the per-operation costs of **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-dispatch-tax|Dispatch overhead in eager execution]]**. Each kernel also occupies the accelerator for at least an assumed 5 μs, and the arithmetic itself, at the 25 percent of peak that ResNet-50 sustains in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^sec-model-training-data-pipeline-8e71|Data pipeline]]**, takes about 33 μs per image. For comparison, MLPerf Inference measured 89,500 images/s for a compiled INT8 engine on one H100 at large batch ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-reddi2020|Reddi et al. 2019]]).

In the ResNet-50 scenario, dense convolutional arithmetic dominates the model stage’s work. That does not make the stage compute bound at every batch size. At batch size one on the reference H100, issuing the kernels takes 2.6 ms, 74 percent of the forward pass, so the stage is overhead-bound and runs far below peak arithmetic throughput. Reading the weights, the other fixed cost named in the chapter’s opening, costs far less in this eager profile than issuing the kernels. Batching amortizes both fixed costs and fills the machine ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-batching-helps-f1dc|section 13.5.1]]). Changing the model architecture can move the dominant cost out of dense arithmetic entirely, and recommendation systems make this shift concrete.

Optimization effort goes where ML expertise applies (model quantization, pruning) while the limiting constraint sits elsewhere (image decoding on CPU for ResNet-50, embedding-table memory bandwidth for DLRM). For an isolated serial request with other stage times held fixed, model-only optimization is bounded by the time spent outside the model, the Amdahl ceiling that **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.04 Benchmarking Granularity#^sec-benchmarking-endtoend-vs-component-latency-9952|End-to-end vs. component latency]]** derives for a request path. Serving modifies that familiar result in two ways. Accelerator progress tightens the ceiling, because each hardware generation shrinks the model term while the host stages stay where they were; the perspective below quantifies this for the reference request. Under load, a faster model also shortens the queue, an effect the fixed-fraction calculation cannot see and the first fallacy in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.12 Fallacies and Pitfalls#^sec-model-serving-fallacies-pitfalls-336b|section 13.11]] develops.

**Systems Perspective 13.2: The quantitative approach to serving**

**Analysis**: Amdahl’s law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-amdahl|8]]) sets this ceiling (**[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-strong-scaling-amdahls-law-c6c2|Strong scaling (Amdahl's Law)]]** provides the formal derivation). Preprocessing (4.5 ms) and data transfer (0.5 ms) consume 58 percent of total latency. Optimizing the model 10× faster (3.5 ms → 0.35 ms) yields only a 1.6× end-to-end speedup (reducing latency from 8.6 ms to 5.5 ms). Focusing exclusively on model optimizations like quantization or pruning yields diminishing returns when non-model stages dominate execution time.

**Mechanism**: Each generation of domain-specific accelerators shrinks the model term. The host-side stages stay on general-purpose CPUs and I/O buses, so the faster the accelerator, the larger their share of end-to-end latency.

**Systems insight**: Profile before optimizing. If preprocessing dominates, GPU-accelerated pipelines (NVIDIA DALI) that move preprocessing next to the accelerator may outperform model quantization, although the end-to-end gain is pipeline-specific.

#### Per-Request Overheads Outside the Model

^sec-model-serving-serving-tax-bill-dc6c

Beyond model forward-pass execution, every request pays fixed overheads to the host system and network stack. When an inference query arrives, it traverses the network interface, moves across kernel and user space, deserializes from wire protocols into memory buffers, queues for batch assembly, and copies across the PCIe interconnect to accelerator device memory. The response later crosses the same network stack on its way out, so egress pays these network costs a second time. These host-side operations run on general-purpose CPUs and I/O buses, which is why their share grows as the model term shrinks. Each overhead has a representative cost, a scaling behavior, and a design choice that reduces it ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^tbl-serving-tax|table 5]]).

| **Overhead**      |       **Typical Cost**       | **Scaling Behavior**   | **Reduction Strategy**          |
|:------------------|:----------------------------:|:-----------------------|:--------------------------------|
| **Network I/O**   |            1–5 ms            | Linear with payload    | Compression, Region Colocation  |
| **Serialization** | 50–500 ${\text{µ}}\text{s}$  | Linear with payload    | gRPC/Protobuf (vs. JSON)        |
| **Queuing**       |          0.1–10 ms           | Diverges near capacity | Dynamic Batching, Autoscaling   |
| **Dispatch**      |  10–50 ${\text{µ}}\text{s}$  | Constant per batch     | Kernel Fusion (reduce launches) |
| **Data Copy**     | 100–500 ${\text{µ}}\text{s}$ | Linear with tensor     | Zero-Copy/Shared Memory         |

Table 5: **Per-Request Overheads Outside the Model**: A representative breakdown of noninference latency sources. While individual components like serialization can be below 1 ms, they compound. Under the upper ends of the displayed ranges, these overheads together can rival the reference ResNet-50 forward pass. The engineering goal is to measure the actual request path and reduce the dominant costs through choices such as binary payloads, persistent connections, and fewer copies.

^tbl-serving-tax

#### The Killer Microseconds Problem

^sec-model-serving-killer-microseconds-problem-bc00

Barroso, Patterson, and colleagues identified a gap in how computer systems handle latency across time scales ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-barroso2017|Barroso et al. 2017]]). Nanosecond-scale stalls (such as cache misses) are hidden by the processor, which keeps executing other instructions, while millisecond-scale delays (such as disk I/O or network RPCs) are hidden by operating system thread context switching. Operations in the microsecond range (1–100 ${\text{µ}}\text{s}$) fall into the gap between these two mechanisms. They are too long to spin-wait on a CPU core without wasting compute cycles and power, yet too short for the operating system to context-switch to another thread without paying scheduling overheads that exceed the wait time itself.

Serving infrastructure operates directly in this killer microseconds regime. Using the representative ranges in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^tbl-serving-tax|table 5]], serialization at 50–500 ${\text{µ}}\text{s}$, dispatch at 10–50 ${\text{µ}}\text{s}$, and data copy at 100–500 ${\text{µ}}\text{s}$ are each individually small. For the 3.5 ms reference forward pass, however, these named microsecond-scale overheads collectively add about 5 percent to 30 percent of the latency budget before network and queuing delays are counted. No single overhead justifies optimization in isolation, yet together they determine whether the system meets its SLO.

Reducing this compound overhead requires changing the architecture across the software-hardware interface. When microsecond delays accumulate across serialization, kernel dispatch, and memory copies, isolated optimizations to individual functions yield negligible improvements. Instead, high-performance serving runtimes remove the boundaries themselves. They use zero-copy memory buffers between networking and execution runtimes, maintain persistent CUDA streams to bypass driver dispatch latencies, and migrate preprocessing kernels directly onto the accelerator to avoid intermediate host-device transfers. Eliminating those fixed boundary costs leaves the portion of preprocessing and execution that scales with the dimensions of the input payload itself.

### Resolution and Input Size Trade-Offs

^sec-model-serving-resolution-input-size-tradeoffs-155d

Doubling an image’s side length from $224{\times}224$ to $448{\times}448$ quadruples the pixel count that the host must decode and that the convolutional layers must process, making input resolution a primary serving control as well as a model property. Model architectures are often evaluated at fixed resolutions, but the serving runtime must ingest variable client inputs and rescale them before kernel execution. In convolution-dominated vision networks, floating-point operations scale quadratically with spatial dimensions ($\mathcal{O}({H} \cdot {W})$), whereas static costs (such as weight streaming from accelerator memory and kernel launch overheads) remain invariant. Varying input resolution therefore shifts the arithmetic intensity across the roofline boundary. A compute-bound stage slows in proportion to its arithmetic, which grows with pixel count and therefore with the square of the side length. A memory-bound stage slows in proportion to the bytes it moves, and only the activation part of those bytes grows with pixel count, because the weight bytes stay fixed.

↩︎ The roofline boundary and arithmetic intensity ridge points that separate compute-bound from memory-bound stages are established in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]**.

For convolution-dominated, compute-bound models, [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^eq-resolution-throughput|equation 1]] gives a first-order approximation in which throughput scales inversely with resolution squared, comparing two input resolutions ${r}_1$ and ${r}_2$ (image side lengths in pixels):

$$
\frac{\text{Throughput}({r}_2)}{\text{Throughput}({r}_1)} = \left(\frac{{r}_1}{{r}_2}\right)^2 \tag{1}
$$

^eq-resolution-throughput

Doubling resolution from 224 to 448 gives a 4× compute-scaling estimate, whereas an illustrative slowdown of 3.6× for the same model includes fixed overhead. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^tbl-resolution-bottleneck|Table 6]] shows the mechanism behind that gap. Each step up in resolution reuses the same weights across more pixels, so the modeled arithmetic intensity rises and the fixed weight traffic becomes a smaller share of the work. That amortization is why the illustrative slowdown falls short of the pure compute estimate. The model counts only weights plus one write and one read of a scaled activation term. That term is an assumed 12.5 MB activation footprint at $224{\times}224$, scaled up in proportion to pixel count at each larger resolution. This simplified count shows only the direction of the effect. A profiler decides whether the executed kernels are compute or memory bound.

| **Resolution**       | **Assumed Activation Term** | **Modeled Arith. Intensity** |
|:---------------------|:---------------------------:|:----------------------------:|
| **$224{\times}224$** |           12.5 MB           |        64.5 FLOP/byte        |
| **$384{\times}384$** |           36.7 MB           |       137.2 FLOP/byte        |
| **$512{\times}512$** |           65.3 MB           |        184 FLOP/byte         |
| **$640{\times}640$** |          102.0 MB           |       218.5 FLOP/byte        |

Table 6: **Resolution and Modeled Arithmetic Intensity**: This estimate divides FLOPs by weight bytes plus one assumed read/write of a scaled activation term. It omits aggregate intermediate-tensor, cache, and workspace traffic, so crossing a ridge point does not establish the executed-kernel bottleneck.

#### Resolution Strategies in Production

^sec-model-serving-deploymentspecific-resolution-decisions-1d76

Different deployment contexts choose resolution according to which constraint dominates. A mobile application may accept $224{\times}224$ inputs because latency and battery life outweigh marginal accuracy gains, whereas medical-imaging workloads often step up to $512{\times}512$ or higher because diagnostic detail justifies the extra compute. Between those fixed choices, a perception pipeline may run a wide field at low resolution and reserve high-resolution crops for fine-grained recognition. A public API that receives arbitrary user uploads can either normalize every image to a single input size or route each request to one of several validated resolution profiles.

#### Adaptive Resolution

^sec-model-serving-adaptive-resolution-cb4e

Adaptive resolution lets production systems select resolution dynamically based on content. One approach runs a lightweight classifier at $128{\times}128$ to categorize content type, then selects task-appropriate resolution with documents at $512{\times}512$, landscapes at $224{\times}224$, and faces at $384{\times}384$. In this illustrative scenario, the policy provides 1.4× throughput improvement with 99.2 percent accuracy retention vs. fixed high resolution. This pattern trades preprocessing cost from running the lightweight classifier for inference savings on the main model. The stage after the model, postprocessing, usually costs far less, but it still crosses the device boundary and spends host CPU time.

### Postprocessing

^sec-model-serving-postprocessing-3b24

When a model finishes a forward pass, its raw output logits sit in accelerator memory that client applications cannot read directly; copying thousands of unreduced floats across the PCIe bus and formatting strings on the CPU can stall the worker thread between batches. Postprocessing turns those device tensors into structured application responses across the physical boundary between the accelerator and the host CPU. How the serving engine splits computation across that boundary determines whether the final stage finishes in microseconds or blocks the pipeline.

#### From Logits to Predictions

^sec-model-serving-logits-predictions-09df

Classification models emit unnormalized logits across the label space, and turning those raw scores into application-ready predictions requires a chain of reduction, filtering, and calibration steps. When only the single most likely label matters, argmax selection extracts the index of the highest logit, whereas applications that present ranked alternatives use top-${k}$ extraction to keep the ${k}$ largest scores alongside their class indices. Before returning those candidates, probability calibration (**[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.10 Model and Data Evaluation#^sec-benchmarking-calibration-confidence-scores-matter-3669|Confidence calibration]]**), such as temperature scaling, rescales raw logits so that output confidences reflect empirical accuracy, allowing thresholding to discard predictions that fall below a required certainty cutoff. Fitting the calibration mapping is an offline task. Applying a simple fitted mapping online is usually inexpensive, but it is valuable only when downstream decisions require confidence scores whose empirical meaning has been validated.

Executing reduction operations on the accelerator can reduce host-device transfer volume when the saved transfer cost outweighs the device execution and launch overhead. Performing softmax, argmax, or top-${k}$ selection in device memory prunes the payload before it crosses the PCIe bus. In ResNet-50 classification, for example, running top-${k}$ on the GPU reduces the transfer payload from 1,000 float32 logits (4,000 bytes) to five values and five integer indices. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^lst-resnet-postprocessing|Listing 1]] traces this execution path from GPU tensor operations to host CPU label lookup and response formatting.

``` python
# Normalize raw logits into probabilities
# Input: logits tensor of shape (1, 1000), one score per ImageNet
# class
probs = torch.softmax(logits, dim=-1)  # Normalize to sum=1 on GPU

# Extract top-5 predictions for multi-class response
# topk returns (values, indices) sorted by probability
top5_probs, top5_indices = probs.topk(5)  # GPU operation
top5_probs = top5_probs.squeeze(0).tolist()
top5_indices = top5_indices.squeeze(0).tolist()

# Map class indices to human-readable labels
# imagenet_labels: list of 1000 class names from synset mapping
labels = [imagenet_labels[i] for i in top5_indices]  # CPU lookup

# Format response with predictions and metadata for API contract
response = {
    "predictions": [
        {"label": label, "confidence": float(prob)}
        for label, prob in zip(labels, top5_probs)
    ],
    "model_version": "resnet50-v2.1",  # Client-side version tracking
    "inference_time_ms": 5.2,  # Observability for latency monitoring
}
```

Listing 1: **ResNet-50 Postprocessing**: Normalizes raw logits into probabilities, extracts top-${k}$ predictions, and formats the API response.

^lst-resnet-postprocessing

In [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^lst-resnet-postprocessing|listing 1]], total postprocessing time is approximately 0.1 ms, negligible compared with preprocessing and inference. The GPU handles the normalization and top-5 reduction, so the subsequent `.tolist()` call transfers only tens of bytes across PCIe. However, `.tolist()` forces a synchronous device-to-host copy, blocking the host thread until the GPU stream finishes. In high-throughput pipelined servers, such synchronization barriers must be scheduled carefully to avoid stalling the CPU thread while it feeds subsequent requests.

#### Output Formatting

^sec-model-serving-output-formatting-753f

Production systems package predictions to satisfy application-level API contracts. These contracts govern JSON serialization schemas, floating-point formatting, error codes, and fallback defaults when thresholding rejects all candidates. In Python-based runtimes, repetitive JSON serialization and string allocation can consume unexpected host CPU cycles under heavy concurrency, turning a microsecond-scale formatting step into a CPU bottleneck. High-throughput servers address this by delegating serialization to native C++ runtimes or binary protocols like Protocol Buffers. Response metadata, including model version and inference execution time, completes the payload to enable downstream observability. Postprocessing completes the single request’s latency budget. That accounting has so far assumed that each request finishes before the next one begins.

### Hardware Utilization and Request Pipelining

^sec-model-serving-utilization-request-pipelining-c61c

Executing each request in lockstep isolation leaves specialized accelerators heavily underutilized. Because network termination, payload preprocessing, neural network evaluation, and response serialization run on distinct physical subsystems (host network interfaces, CPU cores, PCIe interconnects, and accelerator matrix units), strict serial processing forces the accelerator into idle bubbles while the host prepares incoming tensors. The central systems objective is to maximize the accelerator’s **duty cycle**, the proportion of wall-clock time spent actively executing arithmetic kernels, without violating request tail-latency deadlines. Serving runtimes achieve this through **request pipelining**, overlapping asynchronous host preprocessing of forthcoming queries with concurrent accelerator execution on previously staged batches.

↩︎ Asynchronous host-accelerator transfer and double buffering mechanisms are established in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^sec-hardware-acceleration-transfer-optimization-85a8|Transfer optimization]]**.

#### Overlapping I/O and Compute

^sec-model-serving-overlapping-io-compute-966c

[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^fig-serving-pipeline-timing|Figure 4]] sequences execution across CPU preprocessing and GPU inference to demonstrate how request pipelining recovers lost compute capacity. In serial execution (A), each request must complete its entire lifecycle (Network $\rightarrow$ CPU Preprocessing $\rightarrow$ GPU Inference $\rightarrow$ Postprocessing) before the next request begins, leaving the GPU idle for more than 50 percent of wall-clock time. Pipelining concurrent requests (B) overlaps CPU preprocessing of upcoming requests with active GPU inference on earlier inputs, eliminating the idle bubbles and maximizing accelerator duty cycle.

![[90 Assets/Volume I/13 Model Serving/Generated Figure 18376be809.svg]]

Figure 4: **Request Pipelining**: Pipelining hides latency by overlapping independent operations across different hardware resources. In pipelined execution (B), the CPU processes the next request’s data while the GPU executes the current request’s inference. This can increase accelerator duty cycle and throughput without changing the model.

^fig-serving-pipeline-timing

Pipelining relies on non-blocking hardware queues and asynchronous execution streams. Instead of blocking until a GPU kernel completes, the host CPU thread enqueues memory transfers and kernel launches into an accelerator stream and immediately begins preprocessing the next incoming request. The accelerator’s DMA engine and compute cores execute those queued operations independently, overlapping host preprocessing with device execution.

#### The Systems Metric: Hardware Duty Cycle

^sec-model-serving-systems-metric-hardware-duty-cycle-7530

System efficiency here measures accelerator duty cycle rather than the fraction of peak arithmetic throughput or bandwidth achieved. It is therefore a different quantity from the iron law’s hardware efficiency ${\eta_{\text{hw}}}$, which asks how close the running kernels come to peak; system efficiency asks only whether any kernel is running at all. A resource is one device that executes kernels, so the ResNet-50 node counts its single GPU and the resource count is one. In [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^eq-system-efficiency|equation 2]], compute time is the union of useful kernel-active intervals on each resource, summed across resources; overlapping kernels on one GPU are not counted twice.

$$
\text{System Efficiency} = \frac{\sum {T_{\text{compute}}}}{\text{Wall Clock Time} \times \text{Resource Count}} \tag{2}
$$

^eq-system-efficiency

The reference ResNet-50 request spends 4.5 ms preprocessing on a host CPU core and 3.5 ms in the accelerator stage, so in a serial system the accelerator stage occupies only 41 percent of each request. That share is an upper bound on duty cycle, because host dispatch and kernel launch fill most of the stage and its kernels run for only part of it. With at least two requests in flight in a sustained stream, the accelerator stage works on one request while the host prepares the next, and its occupancy rises to 78 percent after pipeline fill. Occupancy cannot reach 100 percent with one preprocessing worker, because the host stage is the slower of the two; a second worker removes that cap. A finite pair still pays pipeline fill and drain time, and stochastic service must retain enough capacity headroom to meet its tail-latency objective.

If the CPU is too slow to feed the GPU, the system becomes CPU-bound, and further model optimization provides zero throughput gain. This is the Amdahl ceiling of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^sec-model-serving-latency-distribution-analysis-b0f8|section 13.3.2]] seen from the throughput side. Hardware upgrades tighten it, because accelerator compute throughput has grown far faster than CPU single-thread performance across successive generations. A system that was compute-bound on an older accelerator may become CPU-bound after a hardware upgrade, not because preprocessing got slower but because the model got dramatically faster while the CPU did not.

**Checkpoint 13.1: The latency budget**

A request’s latency is spent across every stage of its path, not only in the model. Use this checkpoint to locate where the budget goes before choosing an optimization.

**Amdahl ceiling**: in the reference ResNet-50 request, why does a 10$\times$ faster model yield far less than a 10$\times$ faster response, and why does a faster accelerator make the ceiling tighter rather than looser?

**Tail vs. mean**: can you explain why mean latency cannot demonstrate compliance with a p99 SLO?

**Latency budget**: given a 50 ms request deadline and a combined upper bound of 18 ms for all other stages, including network transit, preprocessing, transfer, and postprocessing, how much remains for inference and queueing? Why would a measured 18 ms mean for those stages be insufficient to certify a p99 SLO?

**Pipelining**: explain how overlapping CPU preprocessing with GPU inference raises accelerator duty cycle without changing the model, and what happens to throughput when the CPU stage is slower than the GPU stage.

Tracing an isolated request reveals the intrinsic execution time of each pipeline phase. In production, however, multiple requests arrive concurrently and contend for shared accelerators, CPU cores, and memory buses, introducing queuing delays that dwarf raw computation time.
