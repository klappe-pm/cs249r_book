# V1-13.03 Serving System Architecture

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-serving-system-architecture-4879

Inside each replica, user requests arrive in irregular bursts (milliseconds apart one moment and silent for seconds the next), whereas accelerator compute engines demand steady streams of uniform, dense batches to saturate memory bandwidth and arithmetic units. Reconciling these two incompatible rhythms at the system boundary requires a serving architecture that decouples network ingress from execution scheduling, absorbing arrival bursts and packing irregular inputs into dense batches without violating latency SLOs.

### Internal Architecture and Request Flow

^sec-model-serving-anatomy-inference-server-f12e

If a web server invoked the accelerator synchronously every time a socket read completed, slow client uploads would stall the GPU and concurrent connections would contend for device memory. An inference server[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn3|³]] (such as NVIDIA Triton or TensorFlow Serving) avoids this by acting as a specialized runtime scheduler that manages concurrency, device memory, and data movement between host CPUs and accelerator devices. Rather than running the model directly on the network thread, the server pipelines incoming requests through dedicated subsystems that isolate client network handling from accelerator compute. Every request traverses a six-stage runtime pipeline ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.03 Serving System Architecture#^fig-server-anatomy|figure 2]]) from network ingress and request-buffering queues through the dynamic batcher to the inference runner and hardware accelerator.

![[90 Assets/Volume I/13 Model Serving/Generated Figure 5d374ddfa7.svg]]

Figure 2: **Inference Server Anatomy**: A modern inference server decouples network handling from accelerator execution through a staged pipeline. Each stage isolates a concern, from absorbing bursty traffic to forming efficient batches, so the hardware accelerator stays busy despite irregular arrival patterns.

^fig-server-anatomy

Across the stages in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.03 Serving System Architecture#^fig-server-anatomy|figure 2]], the server handles concurrency management, request transformation, model lifecycle management, and execution scheduling. At network ingress, the server manages concurrency through asynchronous event loops (such as `epoll` or `kqueue`) and worker thread pools that handle thousands of concurrent client TCP connections without stalling accelerator execution pipelines. Decoupling network I/O from compute ensures that slow client transfers or network stalls do not starve the accelerator of ready work.

Once a payload arrives, the server transforms requests into tensors, decoding serialized network bytes into contiguous, aligned memory buffers that match the tensor layout required by the underlying execution engine. For example, four-dimensional vision tensors typically adopt NCHW[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn4|⁴]] or NHWC formats. Accelerator matrix multiplication units (such as Tensor Cores) often favor the channels-last (NHWC) layout.

When the incoming layout differs from the one the execution kernel requires, the server must materialize the required layout, and that conversion has a cost of its own. A view that relabels the dimensions moves no bytes, so an explicit memory copy or transpose kernel must physically reorder the data in memory. Because such materialization performs zero arithmetic (${I}\approx 0$ FLOP/byte), memory traffic and launch overhead dominate its cost. A device-local conversion consumes device memory bandwidth, whereas conversions across the host-device boundary consume PCIe bandwidth.

For those tensors to execute without startup stalls, the server also manages the model’s local lifecycle. The runtime establishes the CUDA context before allocating device memory (VRAM) and streaming weights onto the accelerator. It also pins host memory buffers for direct memory access (DMA) transfers and executes representative warmup passes to trigger deferred compilation and memory allocation before admitting live client traffic. While enterprise model registries (versioned catalogs of approved models), canary rollouts, and rollback policies belong to cluster-level operations (**[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14 ML Operations#^sec-ml-operations|ML Operations]]**), the serving engine governs local state, validating that active model instances are warmed, resident in accelerator memory, and ready for dispatch.

Between request buffering and the warmed model sits the execution **scheduler**, which coordinates accelerator dispatch by implementing dynamic batching ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-throughput-optimization-18d1|section 13.5]]). For weight-dominated inference at batch size ${B}=1$, streaming parameters from HBM can limit execution before the arithmetic units reach peak throughput. Grouping ${B}$ requests into a concurrent batch amortizes the byte transfers of reading model weights across all ${B}$ inputs, increasing the arithmetic intensity (${I}= {O}/{D_{\text{vol}}}$).

To balance individual request latency against batch compute efficiency, the scheduler tunes queue residency using a **batching window** (or timeout threshold). Setting the batching window to zero removes deliberate batch formation delay, but requests can still wait for an available worker. An immediately dispatched small batch may also expose too little work to use the accelerator efficiently. Conversely, setting a bounded window (such as 2 to 5 ms) allows the scheduler to buffer arriving requests until either the queue reaches a target batch size or the timeout expires. The window bounds deliberate formation delay; waiting for a busy worker is a separate resource-queue delay. Batching trades that formation time for greater weight reuse and potentially higher service capacity, while total latency includes both waits and execution. Before a request ever reaches those internal queues, however, it must cross the network boundary at the server’s network ingress.

### Interface Protocols and Serialization

^sec-model-serving-interface-protocols-serialization-5510

At that network boundary, a request’s wire representation can cost more CPU time than the model itself spends on the accelerator. As device kernels undergo aggressive compilation (via TensorRT, TorchDynamo, or custom kernels), forward-pass execution often drops below a single millisecond, leaving payload ingestion, transport, and deserialization as a major share of end-to-end latency (quantified stage by stage in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^sec-model-serving-serving-tax-bill-dc6c|section 13.3.2.1]]). Two interface choices, the wire serialization format and the network transport protocol, determine whether that host ingress path stays in microseconds or consumes the latency budget before inference begins.

#### The Serialization Bottleneck

^sec-model-serving-serialization-bottleneck-aaa0

Machine learning payloads differ from conventional web API payloads. They consist of multi-dimensional arrays of floating-point numbers (such as image tensors, dense embedding vectors, or token sequence logits). While text-based JSON is ubiquitous in web services, serializing dense numerical arrays into text incurs severe CPU and memory penalties. Serialization overhead manifests because JSON parsers must scan every byte sequentially, validate syntax, allocate heap nodes, and invoke string-to-float conversion routines (such as `strtod`). Each 32-bit float expands from 4 raw bytes into 7 to 15 ASCII characters including punctuation. Furthermore, raw binary data (such as compressed JPEG or raw image bytes) requires Base64 encoding to travel within JSON strings, imposing a 33 percent size inflation before parsing begins.

↩︎ Clipper’s decomposition of serving latency, in which serialization rivals model execution, is established in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.04 Benchmarking Granularity#^sec-benchmarking-endtoend-vs-component-latency-9952|End-to-end vs. component latency]]**.

Binary serialization formats, such as Protocol Buffers[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn5|⁵]] and FlatBuffers,[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn6|⁶]] bypass this text conversion cost. Float arrays transmit directly as packed IEEE 754 byte streams with zero ASCII conversion and zero Base64 framing. Furthermore, FlatBuffers organizes serialized records with internal relative offsets, enabling zero-copy deserialization. The serving application reads tensor dimensions, data types, and byte offsets directly out of the network receive buffer without allocating an intermediate object graph on the heap.

#### REST Vs. gRPC

^sec-model-serving-rest-vs-grpc-c7b7

Transport protocol selection governs connection life cycles and socket multiplexing. Conventional REST APIs typically deploy HTTP/1.1 with JSON payloads. HTTP/1.1 clients commonly use multiple persistent TCP connections for concurrency. Establishing each connection incurs handshake and, for HTTPS, TLS costs, but keep-alive reuse amortizes setup across requests. HTTP/1.1 also returns the responses on a connection in request order, so one slow response delays every response behind it. While REST APIs can adopt HTTP/2 or binary encodings, the combination of HTTP/1.1 and JSON creates significant socket overhead and CPU parsing contention when serving high-throughput tensor workloads.

In contrast, gRPC (gRPC Remote Procedure Call)[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn7|⁷]] pairs HTTP/2 transport with Protocol Buffers serialization. HTTP/2 establishes a single long-lived TCP connection and multiplexes hundreds of concurrent request and response streams simultaneously using binary framing. Because responses no longer share one ordered channel, a slow response no longer delays the others at the HTTP level. Protobuf, meanwhile, enforces strongly typed contracts and serializes binary tensor payloads efficiently. Consequently, gRPC is the standard protocol for internal microservice communication in model serving clusters, where low latency, compact wire payloads, and bidirectional token streaming are primary design criteria. Even a modest embedding payload shows the gap in wire footprint and host parsing time.

**Napkin Math 13.1: JSON vs. Protobuf serialization**

Consider a request payload containing 1,000 floating point numbers (for example, an embedding vector).

- **JSON**: Uses ~9 KB on the wire. Requires ~50 μs to parse.
- **Protobuf**: Uses ~4 KB on the wire. Requires ~5 μs to parse.

**Math**: Switching one request to the binary payload saves 50 μs − 5 μs = 45 μs of parse time. For this illustrative system processing 10,000 requests per second, the savings compound to 10,000 $\times$ 45 μs = 0.45 s of CPU time reclaimed every wall-clock second, which is 45 percent of one core freed from serialization overhead alone.

**Systems insight**: This 10× scenario gain makes gRPC/Protobuf, FlatBuffers, or another binary protocol a strong candidate for high-throughput internal microservices when serialization is a visible part of the latency budget.

Which protocol to choose therefore depends on where the interface sits. REST over HTTP/1.1 remains practical for public-facing edge gateways where broad client compatibility and human-readable debugging take precedence over raw wire efficiency. Within cluster boundaries, gRPC over HTTP/2 with binary serialization can reduce overhead when high query volume or tensor serialization consumes a significant share of the host CPU budget; its streaming support also suits incremental token responses.

### The Load Balancer Layer

^sec-model-serving-load-balancer-layer-9c4d

When traffic exceeds what a single machine can handle, adding model replicas does not prevent tail-latency spikes if requests still land on a replica that is mid-batch or still loading weights into GPU memory. Cloud and data center deployments therefore place a **load balancer** between clients and model servers to route around busy or unready replicas. A serving load balancer protects the fleet by coupling request distribution with readiness checks and traffic shifting. It routes incoming requests across replicas using policies such as round-robin or least-connections, so that traffic steers around slow or saturated workers before queues build. It also backs that routing with health monitoring that inspects both process liveness and model initialization state, confirming that weights are loaded and warmup passes are complete before a replica receives live queries. The same routing control also supports progressive rollouts, shifting traffic gradually between model versions rather than cutting over abruptly.

↪ Shadow, canary, and blue-green release strategies that build on this traffic shifting are developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-model-deployment-b9b9|Model deployment]]**.

On a single machine running several model instances, such as several Open Neural Network Exchange (ONNX) Runtime sessions, the serving framework and the operating system queue requests without a separate balancer. A dedicated balancer becomes necessary once replicas span machines, and its distribution algorithms belong to that distributed setting. This chapter therefore plans capacity one node at a time. The unit of capacity is the sustained model throughput of one node. The queueing analysis in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^sec-model-serving-queuing-theory-tail-latency-29a6|section 13.4]] determines the utilization at which that node can no longer meet its latency target and a second replica must be added behind the balancer. Protocol selection, process architecture, and the balancer in front of the replicas establish the structural skeleton of a serving deployment. Evaluating actual operational performance requires tracing how latency accumulates as one request traverses each stage of a replica’s runtime pipeline.
