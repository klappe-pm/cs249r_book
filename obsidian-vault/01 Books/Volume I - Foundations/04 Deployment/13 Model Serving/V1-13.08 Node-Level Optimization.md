# V1-13.08 Node-Level Optimization

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-nodelevel-optimization-3d9d

Runtime selection and precision tuning operate at the model level, determining what computation runs and what numerical format it uses. In the reference ResNet-50 service, however, the forward pass accounts for 3.5 ms out of 8.6 ms end to end, and once a compiled engine shrinks that forward pass to 0.33 ms, host preprocessing alone consumes 83 percent of the remaining time. An isolated model benchmark hides those host-side costs: JPEG decoding on CPU cores, copies across the PCIe bus, and the driver work that launches each kernel.

A request and its model cross four physical boundaries. The storage boundary governs how a new replica loads its weights, and [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.09 Model Loading and Versioning#^sec-model-serving-model-lifecycle-management-ff2e|section 13.8]] and [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.09 Model Loading and Versioning#^sec-model-serving-loading-strategies-eb38|section 13.8.2]] develop it. The other three lie on the active request path of a warmed node, and node-level optimization targets them:

- **Graph-to-kernel boundary**: Translating computation graphs into numerous fine-grained kernel launches incurs driver serialization overhead and forces intermediate tensors through device HBM. Graph compilers fuse adjacent operations into composite kernels that preserve intermediate activations in on-chip SRAM or register files.
- **Host-accelerator boundary**: Accelerators sit idle when the host processor fails to enqueue work ahead of execution. Unpipelined copies across host-device interconnects (such as PCIe) and blocking synchronization calls stall accelerator compute pipelines.
- **CPU execution boundary**: Host preprocessing pipelines and CPU-based inference degrade when executed through interpreted scalar code rather than vectorized single instruction, multiple data (SIMD) instruction units and NUMA-local memory allocations, and when operating-system noise preempts the threads that feed the accelerator.

Each boundary represents a distinct physical constraint where a live request stalls on memory bandwidth, bus transit, or OS scheduling noise rather than peak arithmetic throughput. Crossing them from the accelerator outward moves from runtime graph capture and host resource isolation to CPU-native execution and end-to-end timeline profiling.

### Runtime Graph Compilation

^sec-model-serving-runtime-graph-compilation-7a7e

Crossing the first of those boundaries, the graph-to-kernel interface, without compilation leaves the host CPU submitting tiny kernels one operator at a time across a 32-layer transformer or 50-layer convnet, often spending more time in the driver than the GPU spends on the math. Because serving workloads run fixed operator graphs over bounded input shapes ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-inference-runtime-selection-5eef|section 13.6]]), the specialized engines of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-specialized-inference-engines-475f|section 13.6.2.2]] apply kernel fusion and compile-time constant folding (such as folding batch normalization into preceding convolution weights) ahead of deployment, while static memory planning (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.09 Compilers and Runtimes#^sec-hardware-acceleration-memory-planning-fb9f|Memory planning]]**) preallocates a single arena for non-overlapping tensor lifetimes so allocator calls stay off the request path.

Beyond memory planning and kernel fusion, static execution paths can use CUDA Graphs, the replay of a captured sequence of kernel launches that **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-hybrid-approaches-jit-compilation-8954|Graph capture and JIT compilation]]** developed. Each eager submission pays the 5–20 ${\text{µ}}\text{s}$ of host launch work quantified in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-batching-helps-f1dc|section 13.5.1]], and total submission cost depends on the executed kernel count, not the number of layers. A decode step launching 8 to 10 sub-kernels across each of 32 transformer layers can accumulate several milliseconds of host submission work, longer than the accelerator needs for the tensor math at small batch sizes. Serving systems therefore capture the graph during warmup, once per supported batch size because replay requires static shapes and fixed buffer addresses. They dispatch it during live inference with a single driver invocation (illustratively $\sim 5\,{\text{µ}}\text{s}$, depending on the graph, driver, and hardware). Replay removes repeated host submission work without eliminating device execution costs.

**Systems Perspective 13.4: Compilation timing trade-off**

Just-in-time compilation defers graph optimization until the runtime engine observes concrete input shapes and execution paths. This runtime visibility enables aggressive kernel specialization for dynamic control flow and variable sequence lengths, but it injects compilation overhead directly into the serving path, generating multi-second latency spikes on early requests.

Ahead-of-time compilation executes graph analysis, kernel fusion, and hardware-specific auto-tuning prior to deployment. Pre-building removes the covered compilation work from the request path, but weights, device contexts, allocations, and representative execution paths still require loading and warmup. The compiled engine remains constrained to its supported shape profiles and may require padding or multi-profile compilation to accommodate dynamic input sizes.

### Deterministic Latency and Resource Isolation

^sec-model-serving-deterministic-latency-resource-isolation-4d1c

![[90 Assets/Volume I/13 Model Serving/Model Serving Blast Radius 8592826baf.svg]]

*Three horizontal rows, each holding the same total length of blue work, under the label same pass. The top row is unbroken. The second row is split by one red gap and the third by two red gaps, so each row ends further right. A dashed gray line marks where the unbroken row ends, and a red bracket labeled jitter spans from that line to the end of the longest row.*

*Noisy neighbors stretch identical forward passes unevenly, widening the tail.*

Compilation fixes what the accelerator executes; it does not control how steadily the host feeds it. The server shares its host with other work. On a single host, the operating system multiplexes hardware across background telemetry daemons, logging agents, and kernel worker threads. When these unisolated processes contend for execution resources, they intermittently preempt the inference pipeline. These noisy neighbors are a primary source of **latency jitter**, where the physical time required to execute identical forward passes fluctuates unpredictably. This contention inflates 99th percentile (p99) tail latency even when average hardware utilization remains low. Resource contention thus widens tail latency through service-time variance, a physical degradation distinct from the queuing-delay accumulation along the saturation knee plotted in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^fig-tail-latency-explosion|figure 5]].

Keeping latency predictable requires isolating the serving process from the operating system’s default time-sharing scheduler. Serving systems such as Clockwork demonstrate that deep neural network (DNN) inference execution times can be predictable down to sub-millisecond tolerances under their controlled workload and hardware conditions ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-gujarati2020|Gujarati et al. 2020]]). CPU affinity (thread pinning) establishes the baseline compute boundary by binding inference worker threads to designated physical cores. Without pinning, the OS scheduler periodically migrates threads between cores, so a migrated thread loses its warm cache contents and must refetch them. On multi-socket machines the penalty is larger, because memory left on the previous socket must then be reached across the link between sockets, adding tens of nanoseconds of latency per transaction. Pinning threads to specific cores and binding their memory allocations to local NUMA nodes reduces migration-related cache misses and remote-socket memory traffic.

Even with pinned CPU cores, memory access latency remains vulnerable to the virtual memory subsystem. Under host memory pressure, the kernel can page inactive address ranges out to disk. When the CPU touches a paged-out address, execution can stall for milliseconds while the page returns to DRAM. Host buffers used for PCIe DMA also need resident, registered backing pages during the transfer. Memory locking (`mlock`) instructs the kernel to pin specified virtual address ranges into physical host RAM, preventing page eviction for host-resident weights, input staging buffers, and offloaded key-value (KV) cache blocks. This removes eviction-related page faults at the cost of host memory flexibility; locked pages remain resident until unlocked, while cache misses and memory contention can still delay access. Because `mlock` operates strictly on host page tables, it does not apply to accelerator HBM, which is allocated directly by the accelerator driver.

Beyond scheduled processes, asynchronous hardware interrupts introduce another source of sub-millisecond preemption. When a network interface card (NIC) receives packet bursts, it triggers hardware interrupt requests (IRQs) that force the handling CPU core to immediately suspend user-space execution and process kernel interrupt handlers. If the OS routes these interrupts to cores running the inference engine’s submission loop, the CPU pauses command dispatch to the accelerator. Because GPUs process short inference layers in microseconds, even brief CPU submission stalls empty the accelerator’s queue of submitted work, leaving compute units idle until the next kernel arrives. Interrupt shielding restricts IRQ affinities to dedicated housekeeping cores, reducing preemption of the GPU dispatch thread by those device interrupts.

Isolating physical cores, locking host memory, and shielding interrupt lines reduce specific sources of operating system noise, though the resulting service-time distribution still needs measurement under the intended load. Thus far, isolation has treated the host as a predictable partner that feeds a discrete accelerator; when deployment constraints or workload profiles dispense with the accelerator altogether, the host CPU becomes the executor itself.

### CPU Inference Optimization

^sec-model-serving-cpu-inference-optimization-ae86

For a small fraud-detection or ranking model evaluated at batch size one, copying a single request across PCIe and launching GPU kernels through the driver can take longer than running the forward pass directly on the host processor. Deploying inference on CPUs therefore remains practical for lightweight models, sparse or bursty request streams that cannot saturate an accelerator, and services where host-to-device transfer time exceeds the math time. Yet an untuned Python CPU path leaves most of the processor’s silicon idle. Modern server CPUs[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn17|¹⁷]] (such as Intel Xeon and AMD EPYC) include wide SIMD vector registers and matrix units (AVX-512 and AMX), which specialized runtimes such as OpenVINO target by tiling matrix operations across L1/L2 caches and emitting packed fused multiply-add (FMA) instructions ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-openvinoDocs|Intel Corporation 2026]]).

The NUMA boundaries that thread pinning respects matter more when the CPU itself runs the model. Memory controllers are physically distributed across CPU sockets, so accessing memory attached to a remote socket incurs substantially higher latency and lower bandwidth than local channel access. A NUMA-aware inference server therefore pins worker threads to dedicated physical cores and keeps the weight tensors and request buffers those threads touch in memory local to that socket. Because model weights, at hundreds of megabytes to tens of gigabytes, routinely exceed per-socket L3 cache capacities, every forward pass streams weights from main RAM. Mismatched socket allocations force continuous weight streaming across the slower inter-socket interconnect, creating severe tail-latency degradation.

For lightweight models evaluated at batch size one, a CPU frequently outperforms a discrete GPU. When an accelerator processes an isolated request, the fixed overhead of transferring inputs across the host PCIe bus (several microseconds), driver queue serialization, and kernel launch overhead (5–20 ${\text{µ}}\text{s}$ per kernel) can easily surpass the arithmetic execution time. The CPU processes the request directly in local cache without bus transfers or driver queue delays. Determining the operational crossover requires empirical measurement across model architecture, arithmetic intensity, batch size, and latency constraints.

### Profiling the Serving Node

^sec-model-serving-profiling-serving-node-1e99

Finding that crossover, or diagnosing why an accelerator-backed node misses its p99 target while average GPU utilization sits below 30 percent, requires inspecting where each request actually waits across the host and device. The top-down profiling method of **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.06 Identifying Bottlenecks#^sec-model-training-identifying-bottlenecks-f57f|Identifying Bottlenecks]]** applies unchanged to a serving node, where the objective is useful throughput that meets the latency SLO. The duty-cycle metric defined in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.04 Request Lifecycle#^eq-system-efficiency|equation 2]] helps locate idle intervals, but active time alone does not measure arithmetic efficiency or prove adequate queueing headroom. Timeline profilers, such as PyTorch Profiler and NVIDIA Nsight Systems (`nsys`), record concurrent CPU threads, OS runtime calls, memory transfers, and GPU hardware queues along a synchronized timeline.

Serving traces show three recurring signatures:

- **Idle compute bubbles**: White space on the GPU execution track indicates hardware starvation. Compute warps idle while waiting for the host CPU to complete request preprocessing (e.g., tokenization or image decoding), page faults during on-demand weight paging, or blocking inter-thread synchronization. A gap that lines up with preemption of the dispatch thread points instead to the operating-system noise of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.08 Node-Level Optimization#^sec-model-serving-deterministic-latency-resource-isolation-4d1c|section 13.7.2]].
- **Kernel launch fragmentation**: A sequence of micro-kernels, each executing in under 5–10 ${\text{µ}}\text{s}$, suggests launch overhead as a candidate. Host launch timing and gaps between device kernels reveal whether submission starves the GPU; if so, graph capture or legal fusion may help.
- **Interconnect transfer stalls**: Synchronous `MemcpyHtoD` blocks on the primary CUDA stream indicate unpipelined host-to-device data movement. Overcoming this stall requires allocating page-locked (pinned) host memory and executing asynchronous transfers on dedicated copy streams to overlap bus transit with concurrent accelerator execution on preceding requests.

**Example 13.8: The profiling loop**

**Scenario**: An inference serving node reports high p99 tail latency despite low average GPU compute utilization.

**Diagnosis**: Timeline profiling (Nsight Systems/PyTorch Profiler) reveals large idle gaps between tiny GPU kernels caused by CPU host-side preprocessing bottlenecks and kernel launch overhead.

**Systems lesson**: Serving node optimization requires empirical timeline profiling. Iteratively identifying trace bottlenecks (kernel launch overhead, host-device copy stalls) guides targeted optimizations like kernel fusion and pinned memory.

This diagnostic hierarchy ensures engineering resources address structural bottlenecks along the entire request path rather than applying isolated micro-optimizations. A four-level audit checkpoint structures this prioritization from external service boundaries down to device kernels.

**Checkpoint 13.4: The optimization hierarchy**

Optimizing inference follows the request path from the outside in across four structural levels:

**System budget**: Partition the end-to-end latency budget between network transit, host application processing, queueing delay, and kernel execution, and verify compliance with per-stage timing measurements.

**Application level**: Determine whether the arrival stream and latency budget permit batching, and test whether the gain in service capacity outweighs formation and resource-queue waiting.

**Model level**: If dispatch or operator placement limits the request path, evaluate a compatible compiled engine or graph configuration and recheck quality across supported input shapes.

**Kernel level**: Where intermediate traffic or launch overhead is measured, assess legal fusion candidates and verify their numerical behavior and end-to-end benefit.

A node tuned this way runs each request near its physical limit, but only once it is running. The compiled engine that makes the steady state fast took tens of seconds to build, its weights must cross storage, host memory, and the PCIe bus before the first request arrives, and its preprocessing must match what training used. How a replica reaches that steady state, and whether it computes what training computed once there, decides whether the fast node is also a correct and available one.
