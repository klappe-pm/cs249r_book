# V1-13.06 Throughput Optimization

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-throughput-optimization-18d1

Consider the reference ResNet-50 classifier on an H100 GPU operating at batch size one. Each forward pass reads the model’s weights from high-bandwidth memory to serve a single image and issues a long sequence of small kernels whose fixed launch cost is paid once per image, leaving neither weight traffic nor launch overhead shared across inputs. Processing requests continuously at 280 images/s, each pass spends 99 percent of its time on those fixed costs. Processing 32 images at once delivers 7,000 images/s, a 25× throughput improvement on identical hardware, because one kernel sequence and one weight read now serve thirty-two inputs.

**Batching**[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn13|¹³]] is the primary lever for improving serving economics, but its operational constraints differ sharply between training and serving ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-crankshaw2017clipper|Crankshaw et al. 2017]]). *Training* batches maximize throughput by grouping hundreds or thousands of samples together with no constraint on individual sample latency. *Serving* batches must balance accelerator saturation against individual request deadlines, ensuring that no early-arriving input waits excessively for a batch to form. An inference server resolves this tension through **dynamic batching**, adjusting batch size at runtime to match incoming request arrivals.

**Definition 13.3: Dynamic batching**

***Dynamic batching*** is the ML serving optimization that trades latency for throughput under stochastic arrival patterns.

1.  **Significance**: By buffering requests into a batching window, the scheduler amortizes fixed per-batch costs, the launch overhead $({L_{\text{lat}}})$ and the weight read from memory, across multiple inputs, pushing the system away from the overhead-bound regime and the bandwidth-bound regime $({\text{BW}})$ toward the compute-bound regime $({R_{\text{peak}}})$.
2.  **Distinction**: Unlike fixed-size serving batches, dynamic batching adjusts the realized batch size at inference time according to arriving traffic, a timeout, and a maximum-batch limit.
3.  **Common pitfall**: A frequent misconception is that batching “always helps.” In reality, batching moves along a latency-throughput Pareto frontier. If the batching window is too large, the increased queuing delay may violate the system’s SLO before the throughput gains are realized.

### Why Batching Helps

^sec-model-serving-batching-helps-f1dc

A single request often leaves an accelerator’s compute units idle because its operations expose too little parallel work to hide kernel launch overhead or reuse weights streamed from memory (though large spatial inputs or smaller edge accelerators may already saturate at batch one). For workloads that underuse the device at small batches, increasing the batch size improves hardware efficiency ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-shen2019|Shen et al. 2019]]) by amortizing fixed costs across multiple requests and running inputs in parallel across the batch dimension.

Two fixed costs dominate at small batch sizes. Kernel launch overhead is the time for the CPU to prepare and submit work to the GPU. The number of launches depends on graph lowering and fusion rather than the layer count. For each launch, the CPU must assemble kernel parameters, copy them to GPU-accessible memory, and signal the GPU to begin execution. The cost per kernel does not depend on batch size. The reference ResNet-50 profile issues 174 kernels at 15 μs of host time each, 2.6 ms per forward pass. At batch size 1, this overhead far exceeds the actual compute time; at batch size 32, the same overhead is amortized across thirty-two images.

The second fixed cost, weight loading, reads model parameters from GPU memory (VRAM) to the compute units. In a weight-streaming approximation, batch size 1 reads the weights for one image; batch size 32 reuses that weight stream across thirty-two images, increasing weight-only arithmetic intensity by 32$\times$. Activation traffic, caches, and workspace determine the executed operation’s full intensity.

↩︎ Per-kernel launch overhead, and why fusion and graph execution attack it, are established in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-dispatch-overhead-law-9e0a|The dispatch overhead law]]**.

Larger batches improve hardware efficiency but inflate per-request latency. The engineering objective is to identify the operating point that maximizes sustainable throughput while satisfying the request deadline. For the reference ResNet-50 profile quantified in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^tbl-model-serving-batching-throughput-tradeoff|table 8]] below, serving batch size 8 with a 10 ms batching window requires a mean formation-plus-inference budget of approximately 8.8 ms. An arriving request waits on average half the window (5 ms, as derived in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-queue-waiting-time-analysis-8d5c|section 13.5.4.1]]) and requires 3.8 ms of inference. If the service must meet a 20 ms SLO, the remaining 11.2 ms provides headroom for worker backlog and auxiliary pipeline stages, while delivering 7.5× higher service throughput than batch 1 on identical hardware. On this accelerator the batching window, not the computation, is most of the batch-8 budget.

Batch size cannot grow indefinitely, and [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^fig-throughput-latency-knee|figure 6]] shows why by modeling this relationship across batch sizes on a logarithmic axis. To isolate the planning knee under worst-case scheduling conditions, the figure assumes a strictly serialized single worker that waits out the full batching window before executing each batch, without pipelined overlap ($\text{Latency} = {T_{\text{window}}} + {T_{\text{svc}}}({B})$). Under this unpipelined assumption, batch-1 throughput is 74 requests/s rather than the 280 images/s sustained when inference runs back to back.

Throughput rises almost in proportion to batch size while the fixed overhead dominates each batch, because each added image costs only 33 μs of device time. The planning knee sits where the batch’s total per-image work equals the fixed part of its latency, the window plus the fixed cost, near batch 410. There latency is approximately twice that of batch one and throughput is half its ceiling. Beyond it, each doubling of the batch roughly doubles latency while throughput gains less and less. In this model throughput never declines; it saturates, so the throughput curve alone never says when to stop. A separate limit sets the largest useful batch, whichever of latency, memory, or the engine’s maximum batch binds first, and in this model that limit is latency.

### Formation Delay and the Latency-Throughput Frontier

^sec-model-serving-batching-tax

The throughput gains demonstrated in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^tbl-model-serving-batching-throughput-tradeoff|table 8]] incur a deliberate systems cost. Every request in a batch pays a latency penalty, an engineered queueing delay introduced to elevate hardware utilization. The performance gain arises from parameter reuse across inputs. Evaluating ${B}$ independent queries simultaneously converts memory-bound matrix-vector products into compute-dense general matrix multiplications (GEMM), raising arithmetic intensity toward the hardware roofline ceiling (Principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-arithmetic-intensity|6]]). Conversely, the latency penalty accumulates in the queue, because assembling ${B}$ distinct queries forces earlier arrivals to sit idle while waiting for subsequent requests to appear.

How long that wait lasts depends on what triggers dispatch, so the same batch size carries different latencies under different batcher models. Production servers run the dual-trigger batcher, and the analysis also uses three simpler models, each the easiest way to answer one question:

- **Dual-trigger batcher**: The batch launches when it reaches a maximum size or when its oldest request has waited ${T_{\text{window}}}$, whichever comes first. The dispatch example that closes the configuration guidelines (example [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^exmp-model-serving-batch-dispatch-decision|13.4]]) traces it.
- **Full-window worst case**: Every request waits out the whole batching window ${T_{\text{window}}}$ before its batch runs. The batching sweep ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^tbl-model-serving-batching-throughput-tradeoff|table 8]]) and [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^fig-throughput-latency-knee|figure 6]] use it to bound latency for a single worker.
- **Count-triggered batcher**: The batch launches once ${B}$ requests have arrived. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batching-tax|Equation 6]] uses it to show how formation delay depends on the arrival rate, so a large batch at modest traffic waits far longer than one window.
- **Calendar-window batcher**: Batches launch on a fixed clock, one every ${T_{\text{window}}}$. It gives the average wait, the distribution of batch sizes, and the tail envelope used to choose a window ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-queue-waiting-time-analysis-8d5c|section 13.5.4.1]] through [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-practical-configuration-guidelines-9791|section 13.5.4.7]]).

All four are planning models. Each screens candidate configurations under its stated assumptions, and none certifies a percentile SLO; only a load test of the deployed policy under the intended traffic, with worker backlog and the other request stages included, establishes that.

Formalizing the latency penalty of batch formation requires extending the single-server queuing notation. Let ${T_{\text{svc}}}({B})$ denote the execution duration for a batch of size ${B}$. The unbatched service rate is ${\mu}= {\mu_{\text{eff}}}(1) = 1/{T_{\text{svc}}}(1)$, while batching ${B}$ inputs yields an effective aggregate throughput of ${\mu_{\text{eff}}}({B}) = {B}/{T_{\text{svc}}}({B})$. In a count-triggered batcher, end-to-end response time decomposes into two distinct penalties. **Batch formation delay** $({L_{\text{lat,form}}})$ is the time earlier requests wait while the batch accumulates to capacity. **Inference inflation** is the modest increase in kernel execution duration ${T_{\text{svc}}}({B})$ as batch size expands from 1 to ${B}$. Under stationary Poisson arrivals at rate ${\lambda_{\text{arr}}}$, the first request in a batch waits an average of $({B}-1)/{\lambda_{\text{arr}}}$ seconds while the final arrival waits zero, yielding an average formation delay of $({B}-1)/(2{\lambda_{\text{arr}}})$. Assuming an execution worker is immediately available upon batch assembly, [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batching-tax|equation 6]] models the resulting latency-throughput Pareto frontier:

$$
{L_{\text{lat,batch}}}\approx \underbrace{ \frac{{B}-1}{2{\lambda_{\text{arr}}}} }_{\text{Formation delay}} + \underbrace{ {T_{\text{svc}}}({B}) }_{\text{Inference time}} \tag{6}
$$

^eq-batching-tax

[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batching-tax|Equation 6]] formalizes the component trade-off between accelerator throughput and individual request latency, assuming an idle worker is immediately available upon batch assembly. Increasing ${B}$ raises arithmetic intensity and amortizes memory bandwidth across inputs. Its price is a modest inference inflation in ${T_{\text{svc}}}({B})$ and a formation delay for early arrivals. Evaluated as a formation-plus-service component comparison using the service times from [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^tbl-model-serving-batching-throughput-tradeoff|table 8]] at 500 QPS, moving from batch 1 to batch 32 increases formation wait from 0 ms to 31 ms. That is a 10× increase in isolated stage latency (3.5 ms to 36 ms).

Batch-one service, however, cannot sustain 500 QPS on a single worker whose peak service rate is only 280 requests/s. Without batching, worker backlog diverges toward infinity, so 3.5 ms does not represent a viable steady-state response time at this arrival rate. Batching is what makes 500 QPS feasible on that hardware in the first place, demonstrating that grouping requests can lower loaded end-to-end response time even while adding formation delay. Sizing ${B}$ is therefore an operational stability screen before it is an economic optimization. Operators first enforce queue stability (${\lambda_{\text{arr}}} < {\mu_{\text{eff}}}({B})$) and then select the batch size that maximizes throughput within the memory ceiling and latency SLO $({L_{\text{lat,SLO}}})$. Because [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batching-tax|equation 6]] assumes the batcher waits for a full count of ${B}$ requests before launching, the two batching policies below differ in how they relax that count-only assumption when traffic fluctuates.

### Static Vs. Dynamic Batching

^sec-model-serving-static-vs-dynamic-batching-fd0a

If an inference server holds execution until its queue accumulates a fixed batch of ${B}$ requests, a lull in traffic can leave early arrivals waiting indefinitely until enough subsequent queries arrive to fill the batch. **Static batching** (where *static* describes the batch dimension rather than the precomputed predictions of static inference) fixes the batch size at compile time so compilers can allocate static memory buffers and emit specialized compute kernels. That is a natural fit for offline processing and model training, where inputs are already staged, but a liability when interactive requests arrive stochastically. Conversely, setting a small fixed batch size to cap waiting time leaves accelerator compute units underutilized and fails to amortize weight transfers from high-bandwidth memory when traffic spikes.

Dynamic batching decouples batch formation from arrival determinism by buffering incoming requests behind a dual-trigger scheduler ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-olston2017tensorflow|Olston et al. 2017]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidia-triton-c2de726e|NVIDIA 2024b]]). Rather than waiting indefinitely for a fixed tensor shape, the serving runtime makes a batch eligible for dispatch when either of two thresholds is satisfied. Either the queue accumulates a maximum batch size ${B_{\text{max}}}$, or a timeout window ${T_{\text{window}}}$ expires relative to the oldest buffered request. When traffic bursts, the queue fills to ${B_{\text{max}}}$ almost instantaneously, achieving high arithmetic intensity with minimal queuing delay. When arrival rates drop, the timeout window forces the dispatch of an undersized batch (${B}< {B_{\text{max}}}$), bounding formation time at the expense of per-request compute efficiency. If the accelerator is busy, the ready batch can still wait for service.

The timeout window ${T_{\text{window}}}$ and maximum batch size ${B_{\text{max}}}$ form the primary operational levers. Shorter windows limit formation delay, whereas longer windows allow larger batches when enough requests arrive. A longer window is useful only when the resulting throughput gain remains within the latency and memory constraints.

### Dynamic Batching Latency-Throughput Trade-Offs

^sec-model-serving-dynamic-batching-latencythroughput-tradeoffs-986d

Setting those two levers (${T_{\text{window}}}$ and ${B_{\text{max}}}$) requires accounting for what happens to the latency budget while the batcher waits. A wide window can spend a large share of the SLO accumulating requests before a single kernel launches. Because latency under load grows in the queue before it grows on the accelerator ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.05 Queuing Theory#^sec-model-serving-tailtolerant-techniques-066e|section 13.4.4]]), configuring a dynamic batcher starts by separating time spent waiting from time spent in service.

[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batching-latency|Equation 7]] decomposes the modeled batching-and-service portion of request latency into two components. Its total excludes network transit and any host stages outside the service interval:

$$
{L_{\text{lat,batch}}}= {L_{\text{lat,wait}}}+ {T_{\text{svc}}}({B}) \tag{7}
$$

 where ${L_{\text{lat,wait}}}$ is the time spent waiting in the batching queue (corresponding to ${L_{\text{lat,queue}}}$ in the latency budget of principle [[01 Books/Volume I - Foundations/04 Deployment/V1 Deployment Principles#^pri-latency-budget|12]]) and ${T_{\text{svc}}}({B})$ is the service time for a batch of size ${B}$ (encompassing ${L_{\text{lat,infer}}}$ plus portions of ${L_{\text{lat,pre}}}$ and ${L_{\text{lat,post}}}$). This wait includes formation and any subsequent wait for a worker. The batching window ${T_{\text{window}}}$ bounds formation time alone; ${L_{\text{lat,wait}}}\leq {T_{\text{window}}}$ holds only when no additional resource backlog delays dispatch. Batch size affects service time through weight reuse, parallel work, and execution overhead.

^eq-batching-latency

#### Quantitative Analysis of Batching

^sec-model-serving-queue-waiting-time-analysis-8d5c

Configuring a dynamic batching policy requires balancing batch formation delay against accelerator execution time and pending queue backlog. In a pure count-triggered batcher ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batching-tax|equation 6]]), average formation delay $({B}-1)/(2{\lambda_{\text{arr}}})$ contracts as arrival rate ${\lambda_{\text{arr}}}$ grows, but diverges under light traffic. Conversely, a pure timer-triggered batcher dispatches on a periodic schedule of length ${T_{\text{window}}}$, decoupling formation delay from instantaneous arrival fluctuations.

To evaluate how time-based batching impacts latency budgets, consider a baseline fixed calendar window where batches dispatch periodically every ${T_{\text{window}}}$ seconds and an idle execution worker is available at the boundary. Under stationary Poisson arrivals, query arrival times distribute uniformly across the interval $[0, {T_{\text{window}}}]$. A request arriving at offset ${t}$ within the window experiences a formation wait of ${T_{\text{window}}} - {t}$. Integrating across the uniform distribution yields an expected waiting time equal to exactly half the batching window ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-avg-wait|equation 8]]):

$$
\mathbb{E}[{L_{\text{lat,wait}}}] = \frac{{T_{\text{window}}}}{2} \tag{8}
$$

^eq-avg-wait

A 20 ms batching window adds 10 ms average wait (up to 20 ms for the first arrival in a window; later arrivals wait less) regardless of batch size achieved. For a 50 ms mean latency SLO with 3.5 ms inference, the average wait consumes 20 percent of the latency budget before any computation begins, about 3× the forward pass itself; tail SLOs must budget the full window.

#### Batch Size Distribution

^sec-model-serving-batch-size-distribution-b3d3

For fixed calendar windows, the number of requests collected during ${T_{\text{window}}}$ follows a Poisson distribution with mean ${\lambda_{\text{arr}}} {T_{\text{window}}}$. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batch-distribution|Equation 9]] formalizes this relationship:

$$
\Pr(\text{batch size} = {k}) = \frac{({\lambda_{\text{arr}}} {T_{\text{window}}})^{k} e^{-{\lambda_{\text{arr}}} {T_{\text{window}}}}}{{k}!} \tag{9}
$$

 where ${k}$ is a nonnegative integer count of arrivals in the window.

^eq-batch-distribution

With a fixed 10 ms window, the count a window collects fluctuates most at low traffic. At 50 QPS the mean batch is 0.5 with a standard deviation of 0.7, and 61 percent of windows contain no request at all, so no GPU batch launches. At 200 QPS the mean is 2 and the standard deviation 1.4, so realized batches still swing widely around the mean. At 1000 QPS the mean reaches 10 and the spread narrows relative to it. The probability that a window collects at least twice the mean falls from 39 percent at the lowest traffic level to 0.3 percent at the highest, the law of large numbers at work.

#### Throughput Maximization Strategy

^sec-model-serving-throughput-maximization-strategy-27f5

Throughput optimization requires separating per-request latency from saturated service capacity. A request waits for batch formation, then pays the service time of the formed batch. Under sustained load, however, batch formation can overlap with the previous batch’s execution, so capacity is governed by the ready-batch service time:

$$
{\mu_{\text{eff}}}({B}) \approx \frac{{B}}{{T_{\text{svc}}}({B})}, \qquad \text{throughput} = \min({\lambda_{\text{arr}}}, {\mu_{\text{eff}}}({B})) \tag{10}
$$

^eq-batch-throughput

In [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batch-throughput|equation 10]], ${\lambda_{\text{arr}}}$ is the offered arrival rate and ${\mu_{\text{eff}}}({B})$ is the saturated service capacity for batch size ${B}$. The numerator increases linearly with batch size while service time often increases sublinearly over a useful range, because larger batches amortize fixed kernel-launch overheads and DRAM weight transfers. This shifts execution from memory-bandwidth-bound matrix-vector operations toward compute-bound matrix-matrix multiplication. The batching window still appears in request latency and in low-traffic regimes, where the expected batch size is limited by arrivals during the window, roughly ${\lambda_{\text{arr}}} {T_{\text{window}}}$.

The reference ResNet-50 profile is affine in batch size, ${T_{\text{svc}}}({B}) = 3.50\text{ ms} + (0.033\text{ ms})\,{B}$, so batching strategies can be evaluated across arbitrary batch sizes without interpolating discrete benchmark tables. The model has 3.50 ms of fixed kernel issue, per-kernel device floor, and weight read, plus 0.033 ms of device work per image. It is the same model that produced the batching sweep ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^tbl-model-serving-batching-throughput-tradeoff|table 8]]), so the sweep and the model describe one service. This analytical service model unifies the queueing, window screening, and dispatch calculations throughout the remainder of this section. The sweep’s window-plus-inference column already evaluates it for a 10 ms batching window ${T_{\text{window}}}$, pairing formation-plus-service latency with saturated pipelined capacity. The sweep’s throughput gains trace back to two fixed costs in the iron law (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-iron-law|3]]), kernel issue and the per-kernel floor in the latency term ${L_{\text{lat}}}$ and the weight read in the bandwidth term ${D_{\text{vol}}}/{\text{BW}}$, and batching amortizes both across requests.

The sweep’s service times, the formation wait, and the arrival statistics compose a calendar-window planning model. Average formation wait is half the window, Poisson arrivals make the window count fluctuate around ${\lambda_{\text{arr}}} {T_{\text{window}}}$, and saturated service capacity ${\mu_{\text{eff}}}({B})$ grows as batching amortizes fixed costs. An oldest-request timer, a maximum-batch trigger, or a busy worker changes the observed wait and batch distributions.

#### Latency-Constrained Optimization

^sec-model-serving-latencyconstrained-optimization-8f66

When latency is the limiting constraint, a mean-latency approximation provides an initial screen of candidate batch sizes. For the portion of a mean latency SLO allocated to batching and service, ${L_{\text{lat,budget}}}$, and average wait time ${T_{\text{window}}}/2$, [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-latency-constrained-batch|equation 11]] defines the maximum allowable batch size ${B_{\text{SLO}}}$ using a first-order average latency approximation. Other request stages require separate budget allocations. This is a feasibility bound on mean latency, not a throughput optimum:

$$
{B_{\text{SLO}}}= \max\left\{{B} : \frac{{T_{\text{window}}}}{2} + {T_{\text{svc}}}({B}) \leq {L_{\text{lat,budget}}}\right\} \tag{11}
$$

^eq-latency-constrained-batch

Applying [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-latency-constrained-batch|equation 11]] to the affine service model for a 50 ms mean budget shows how the choice of batching window shapes the feasible configuration space. A conservative 5 ms window adds 2.5 ms of average formation wait (up to the full 5 ms for the first request in a window) and leaves 47.5 ms for inference, enough by [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-latency-constrained-batch|equation 11]] for a batch of about 1,340 images. The configured engine maximum batch of 128, an assumed setting, is reached first, so the batch is capped at 128 images and the worker sustains about 16,600 img/s when saturated. An aggressive 25 ms window adds 12.5 ms of average wait and leaves 37.5 ms, still enough for about 1,030 images, so the same engine cap limits the batch and saturated capacity does not change. A tail SLO, unlike this mean-latency plan, must budget the full window rather than its average.

This comparison quantifies the diminishing returns of expanding the batching window. Widening the window by 20 ms buys no saturated capacity while increasing average formation wait by 10 ms. On an accelerator this fast relative to its fixed cost, the latency budget no longer binds first. The engine’s maximum batch does. The capped batch forms only when traffic delivers that many requests within one window, so the saturated rate above is a ceiling the worker reaches under heavy load, and at lighter traffic the arrival rate sets the batch size instead. However, this initial screen relies on mean formation wait and deterministic batch sizing. In production, stochastic arrivals introduce batch-size variance that can breach tail deadlines even when the mean latency appears well within the budget, requiring the percentile envelope analysis developed next.

#### SLO Violation Analysis

^sec-model-serving-slo-violation-analysis-6ebf

Batch size variability can cause SLO violations even when mean latency appears safe. Earlier, [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-batch-distribution|equation 9]] counted arrivals across all calendar windows, including empty windows in which no request arrived and no batch launched. Latency, however, is measured only over requests that actually arrive. Under a Poisson process, an arriving request lands in a window alongside a number of *other* arrivals that is itself distributed as $\operatorname{Poisson}({\lambda_{\text{arr}}} {T_{\text{window}}})$. Including the arriving request itself gives the **request-seen batch size** ${B_{\text{req}}}=1+\operatorname{Poisson}({\lambda_{\text{arr}}} {T_{\text{window}}})$, whose mean is $1 + {\lambda_{\text{arr}}} {T_{\text{window}}}$ rather than ${\lambda_{\text{arr}}} {T_{\text{window}}}$. With an available worker at dispatch, combining the worst-case formation wait of a full window ${T_{\text{window}}}$ with the service time of the 99th-percentile request-seen batch size ${B_{\text{req,p99}}}$ gives the conservative formation-plus-service envelope in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-p99-batch-latency|equation 12]]:

$$
{L_{\text{lat,envelope}}}= {T_{\text{window}}}+ {T_{\text{svc}}}({B_{\text{req,p99}}}) \tag{12}
$$

 For ${\lambda_{\text{arr}}}$ = 500 QPS and ${T_{\text{window}}}$ = 10 ms, an average window sees five other arrivals plus the request itself, so the mean request-seen batch size is 6 and its p99 is 12. The mean latency is 8.7 ms, whereas the conservative envelope reaches 13.9 ms.

^eq-p99-batch-latency

The envelope is 1.6× the mean, showing why a configuration whose mean sits comfortably inside the SLO can still breach it when a long formation wait coincides with an unusually large batch. Under the available-worker calendar-window assumptions, [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^eq-p99-batch-latency|equation 12]] is a conservative upper envelope rather than the exact p99 latency because it assumes the same request suffers both extremes at once: arriving at the very start of the window (waiting the full ${T_{\text{window}}}$) and landing in a 99th-percentile batch (${B_{\text{req,p99}}}$). A configuration that fails the envelope can be rejected conservatively or examined with a more faithful model, and one that passes has cleared only the formation-plus-service part of the request.

#### Adaptive Batching Windows

^sec-model-serving-adaptive-batching-windows-c404

Static batching windows impose a rigid trade-off that penalizes both traffic extremes. Under heavy traffic surges, a static timeout window holds early arrivals unnecessarily long after sufficient queries have already accumulated, consuming latency budget without enlarging the batch. Conversely, during off-peak periods, a fixed window frequently dispatches tiny, inefficient batches, failing to exploit accelerator arithmetic intensity. To navigate this tension, serving runtimes use **adaptive batching** policies that dynamically adjust the window duration based on instantaneous queue backlog, observed arrival rates, and the residual latency margin before the service-level objective expires. An adaptive window contracts during surges and expands during lulls, so it can lower average latency and raise realized batch size at the same time, within the remaining latency budget. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^lst-adaptive-batching|Listing 2]] implements one such heuristic.

``` python
def adaptive_batching_window(
    queue_depth, arrival_rate, slo_ms, service_ms, fixed_overhead_ms
):
    """Compute a heuristic batching window.

    Based on current system state.
    """
    target_batch_size = 16  # Deployment-tuned target batch

    # Fast path: batch ready, close immediately to minimize latency
    if queue_depth >= target_batch_size:
        return 0

    # Compute maximum allowable wait from the remaining p99 budget.
    max_wait_ms = max(0, slo_ms - service_ms - fixed_overhead_ms)

    # Estimate time to accumulate target batch at current arrival
    # rate.
    # arrival_rate is requests/second, so convert seconds to
    # milliseconds.
    if arrival_rate > 0:
        requests_needed = target_batch_size - queue_depth
        estimated_wait_ms = requests_needed / arrival_rate * 1000.0
        # Return minimum of estimated wait and SLO-constrained maximum
        return min(estimated_wait_ms, max_wait_ms)

    return max_wait_ms  # Low traffic: use remaining budget to accumulate batch
```

Listing 2: **Adaptive Batching Window**: Heuristically adjusts batch timeout based on queue depth, arrival rate, and the remaining latency budget.

^lst-adaptive-batching

The heuristic returns only a formation timer. Its inputs omit the time the oldest request has already spent and the work queued ahead of the batch, so deadline-aware dispatch must add both before it trusts the returned window.

The nondominated batching configurations form a Pareto frontier where improving throughput requires accepting higher latency. Across five window and batch-cap configurations on the reference profile, from a 2 ms window capped at batch 8 to a 50 ms window capped at batch 128, modeled throughput rises from 2,100 img/s to 16,600 img/s, a gain of 680 percent. The modeled p99 envelope rises from 5.8 ms to 57.7 ms, 10× its initial value. Average latency over the same range grows from 4.8 ms to 32.7 ms.

#### Practical Configuration Guidelines

^sec-model-serving-practical-configuration-guidelines-9791

The frontier, like the knee of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^fig-throughput-latency-knee|figure 6]], shows why configuration must work backward from the latency budget. Past the knee, widening the window buys diminishing throughput for sharply rising tail latency. In the scenario below, reserving 30 percent of the SLO for batching wait gives ${T_{\text{window}}}\leq 0.3 \times {L_{\text{lat,SLO}}}$; another workload may allocate a different fraction after accounting for network, preprocessing, inference, and postprocessing. The traffic estimate should include peaks and burst duration rather than rely only on the mean. GPU memory supplies a separate ceiling on batch size through activations and runtime workspace. Finally, monitoring the realized batch-size and wait-time distributions reveals whether the assumed arrival model holds and whether a fixed or adaptive window is appropriate.

For an illustrative ResNet-50 serving system with a 50 ms SLO and 500 QPS traffic, the calculation provides starting estimates for two configuration knobs: the batching window and maximum batch size. **Example 13.4: From a batching window to a dispatch decision**

**Problem**: In a hypothetical trace of the selected dual-trigger configuration, four requests arrive at 0, 2, 5, and 9 ms. No further requests arrive before dispatch. The worker becomes available at 18 ms, and the remaining response path takes 4 ms. Does the oldest request meet the 50 ms deadline under the planning service-time model?

**Analysis**: The batch remains below the maximum count, so the oldest-request timer makes it eligible after 12 ms. The worker is still busy, adding 6 ms of resource-queue wait. The four-request batch then takes 3.6 ms under the same linear service model used for the window analysis. Adding the remaining response path gives 25.6 ms from the oldest arrival to completion.

**Result**: Dispatching the four-request batch meets the oldest request’s deadline with 24.4 ms of slack; the later arrivals finish with more slack. Waiting for the maximum batch would leave these requests stalled because the trace supplies no further arrivals. The timeout therefore determines eligibility, while worker availability determines actual dispatch.

**Systems insight**: The selected window passes this complete trace, including backlog and the response path. A single trace is not a percentile, so the SLO still rests on the load test described with the batcher models.

^exmp-model-serving-batch-dispatch-decision

Working backward from the budget can also conclude that the right window is zero, because schedulers and dynamic memory allocators add coordination and synchronization overhead that hurts latency-critical or resource-constrained deployments. Under an ultra-low p99 target, even a brief formation delay consumes an unacceptable fraction of the latency budget. In runtimes without ragged (variable-length) tensor support, batching variable-length inputs pads every sequence to the longest item in the batch, which wastes work that single-request execution avoids completely. Memory capacity can rule out batching as well. When model weights already occupy most of the accelerator’s physical memory, concurrent batch activations and dynamic KV-cache allocations risk out-of-memory aborts, forcing the runtime to serve one request at a time.

### Traffic Patterns and Batching Strategy

^sec-model-serving-traffic-patterns-batching-strategy-2e6b

A timeout window tuned for independent web API calls will stall a multi-camera robotics rig whose frames arrive in synchronized bursts, and it is useless on a smartphone that processes one user photo at a time. Because the right batching policy depends on how requests arrive, the MLPerf inference benchmark supplies four standardized scenarios that approximate common production arrival patterns.

#### Server Traffic (Poisson Arrivals)

^sec-model-serving-server-traffic-poisson-arrivals-5d26

The MLPerf Server scenario models cloud/API-like inference traffic with Poisson arrivals ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-reddi2020|Reddi et al. 2019]]), the arrival model behind the window statistics of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-batch-size-distribution-b3d3|section 13.5.4.2]]. A fixed calendar window collects ${\lambda_{\text{arr}}} {T_{\text{window}}}$ requests on average, and that count fluctuates most, relative to its mean, at low traffic. Higher traffic can fill a desired batch sooner, permitting a shorter formation window, and an oldest-request timer counts the request that starts the window as well. Increasing the arrival rate therefore allows the same expected batch count with less deliberate waiting. The scheduler may instead target a larger batch if the latency and memory budgets permit it. Neither choice creates service capacity. The formed batches must complete fast enough to keep up with sustained arrivals, or resource backlog grows despite the shorter window. Window tuning must jointly check the arrival count, the service rate at the realized batch sizes, and the full request-latency distribution.

#### Streaming Traffic (Correlated Arrivals)

^sec-model-serving-streaming-traffic-correlated-arrivals-32b6

Video analytics, robotics, and other multi-sensor systems receive inputs from several synchronized sensors, so arrivals are correlated rather than independent. The batch size equals the number of sensors and the deadline equals the frame period, both fixed outside the server, and the limiting quantity becomes arrival jitter. Inference cannot start until the last frame of a set lands, so jitter consumes the frame budget before any computation runs. Such pipelines bound latency with an explicit synchronization deadline, the latest batch start that still meets the frame deadline, and a fallback, such as reusing a sensor’s previous frame, when a frame misses it. The MultiStream scenario (**[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.05 Benchmark Suites#^sec-benchmarking-multistream-38d1|MultiStream]]**) approximates this shape for benchmarking.

#### Single-User Traffic (Sequential Arrivals)

^sec-model-serving-singleuser-traffic-sequential-arrivals-78da

Synchronized sensors fix batch size and deadline outside the server. At the opposite end of the spectrum, interactive mobile and edge applications process one request stream at a time, leaving no opportunity to batch independent queries. The MLPerf SingleStream scenario captures this sequential-serving shape. Here, the optimization target shifts from a synchronization budget under a frame deadline to per-request latency and energy consumption under a rigid thermal envelope. For the smartphone vision pipeline modeled below, the primary engineering objective is not batch formation, but minimizing per-phase latency and energy dissipation.

#### Mobile Serving Constraints

^sec-model-serving-mobile-serving-constraints-eb68

Cloud services often emphasize fleet cost and latency; mobile serving adds the energy, thermal, and memory limits of **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.08 Mobile ML Offline Intelligence#^sec-ml-systems-mobile-ml-benefits-resource-constraints-c568|Mobile ML benefits and resource constraints]]**. Throughput alone does not capture the energy budget, because each inference consumes battery. In the modeled pipeline, 2.98 mJ at 22 FPS draws about 66 mW for the inference path alone, before camera, display, ISP, and OS overhead add to that total in a full photo app. Thermal throttling can compound this limit when sustained system power reaches a device-specific thermal boundary. Memory constraints close the set because the model shares RAM with the application and operating system. Reload time depends on device storage, runtime, and model state; quantization and memory-mapped loading ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.09 Model Loading and Versioning#^sec-model-serving-loading-strategies-eb38|section 13.8.2]]) can reduce footprint and startup work but do not eliminate those dependencies.

**Example 13.5: ResNet-50: Mobile serving**

[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^tbl-model-serving-mobile-pipeline-breakdown|Table 11]] decomposes per-phase latency and energy for a single-user mobile vision inference:

| **Phase**              | **Duration** | **Energy**  | **Notes**         |
|:-----------------------|:------------:|:-----------:|:------------------|
| **Camera buffer read** |     8 ms     |   0.08 mJ   | System API        |
| **JPEG decode (CPU)**  |    15 ms     |   1.5 mJ    | Single-threaded   |
| **Resize + Normalize** |     5 ms     |   0.4 mJ    | CPU preprocessing |
| **NPU inference**      |    12 ms     |   0.8 mJ    | 82% utilization   |
| **Postprocess + UI**   |     5 ms     |   0.2 mJ    | Result rendering  |
| **Total**              |  **45 ms**   | **2.98 mJ** | 22 FPS sustained  |

Table 11: **Mobile ResNet-50 pipeline**: Illustrative per-phase latency and energy for a single-user mobile vision inference, showing that JPEG decode on the CPU dominates the energy budget even though the NPU inference stage carries the model’s compute. Optimization targets shift from throughput to energy-per-inference at the edge.

^tbl-model-serving-mobile-pipeline-breakdown

The mobile serving node is governed by four metrics:

- **Energy per inference**: 2.98 mJ enables ~12.1M inferences per 10 Wh battery (typical smartphone)
- **Modeled inference power**: 2.98 mJ / 45 ms = 66 mW, excluding the rest of the device and therefore not a guarantee of indefinite operation
- **NPU vs. CPU trade-off**: CPU fallback replaces the 12 ms, 0.8 mJ NPU inference stage with a 45 ms, 4.2 mJ CPU stage; the full pipeline would rise from 45 ms and 2.98 mJ to about 78 ms and 6.4 mJ before additional system overhead.
- **Memory footprint**: 150 MB peak (model + activations), competing with app memory

**Systems insight**: In this illustrative pipeline, the mobile NPU is assumed to run at 82 percent utilization at batch size one. The chapter’s eager H100 forward pass faces a different limit at batch one, spending 99 percent of its time on fixed costs (kernel issue, each kernel’s minimum run time, and the weight read) that only a larger batch would share. The contrast is workload- and hardware-specific, but it shows why a mobile accelerator designed for single-stream execution can operate efficiently without the batches used to amortize a large server GPU.

^exmp-model-serving-resnet-50-mobile-serving

These physical constraints make edge serving optimization different from data-center optimization. Rather than maximizing aggregate batch throughput, the objective is to sustain real-time execution within a tight thermal and battery envelope without triggering hardware throttling or starving foreground applications of system memory.

#### Traffic Pattern Summary

^sec-model-serving-traffic-pattern-summary

Traffic-adaptive batching adjusts the batching window as queue depth and request rate change. The four MLPerf inference scenarios that **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.05 Benchmark Suites#^sec-benchmarking-mlperf-execution-scenarios-89f0|MLPerf execution scenarios]]** defines map onto these traffic shapes and the batching strategy each favors ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^tbl-traffic-patterns-summary|table 12]]). These scenarios are benchmark abstractions rather than deployment prescriptions, so the operative batching policy must still follow the service’s current concurrency, deadline, and power constraints.

| **Scenario**     | **Context**                      | **Strategy**                  | **Focus**                                |
|:-----------------|:---------------------------------|:------------------------------|:-----------------------------------------|
| **Server**       | Cloud APIs, web services         | Dynamic batching with timeout | Window tuning, utilization-latency curve |
| **MultiStream**  | Grouped sensor-like inputs       | Joint query processing        | Group latency under benchmark rules      |
| **SingleStream** | Mobile apps, embedded devices    | No batching (${B}= 1$)        | Preprocessing, power efficiency          |
| **Offline**      | Batch processing, data pipelines | Maximum batch size            | Throughput, hardware utilization         |

Table 12: **Traffic Patterns and Batching Strategies**: The four MLPerf inference scenarios approximate distinct deployment contexts. Server traffic (cloud APIs) uses dynamic batching with a timeout; MultiStream evaluates grouped queries under its version-specific latency rules, while a production sensor deadline requires separate validation; SingleStream processes requests individually; Offline uses large batches subject to memory capacity to maximize throughput.

^tbl-traffic-patterns-summary

The examples developed here (cloud API traffic under the Server scenario, grouped sensor inputs motivated by MultiStream, and throughput-dominated pipelines under Offline inference) all decide how requests share the accelerator. Together with the latency budget and the queueing model, they decide how one replica of the ResNet-50 service schedules its requests. None of them decides how efficiently the accelerator executes each batch once it forms. The same batch of the same model can run several times faster or slower depending on the engine that compiles and schedules its kernels and on the number format it computes in, and those choices are the next lever.
