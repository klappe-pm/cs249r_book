# V1-13.10 LLM Serving

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-llm-serving-b8bf

An image classifier returns a single class vector in a few milliseconds and immediately frees its activation buffers, whereas a conversational LLM streams hundreds of tokens over several seconds while holding a growing key-value cache in GPU memory. LLMs make three properties far more prominent than in fixed-output serving. *Autoregressive generation*[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn21|²¹]] means that each token depends on all previous tokens, which makes output inherently sequential. *Variable-length output* means that response length is unknown at request time, which complicates fixed-batch assumptions. *Stateful memory* means that the key-value cache grows with each generated token, which creates dynamic memory pressure.

Each property strains a different tool from the preceding sections. Sequential generation splits the latency budget into phases, unknown output length breaks fixed-batch scheduling, and the growing cache makes memory capacity, not arithmetic, the limit on concurrency. The p50, p95, and p99 metrics used for classification serving still matter, but they apply separately to the initial prompt processing and to the subsequent token generation. The same principles of queuing theory, batching trade-offs, and latency budgets remain applicable; LLM serving adds domain-specific techniques atop them.

↩︎ Prefill, small-batch autoregressive decode, and the KV cache that every decode step reads are established in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^sec-network-architectures-inference-memory-bandwidth-wall-98d1|Autoregressive decoding]]**.

The chapter’s second service carries the section. GPT-2 XL, the bandwidth-bound lighthouse, anchors the metrics, the decode floor, speculative decoding, and the energy per generated token, because its weight stream sets each of them. Llama 3 8B, introduced with the running cases, carries the cache budget, paging, and prefix reuse, because its longer contexts make memory capacity rather than bandwidth the first constraint to run out.

### Performance Metrics: TTFT and TPOT

^sec-model-serving-performance-metrics-ttft-tpot-b009

![[90 Assets/Volume I/13 Model Serving/Vol1 Model Serving Margin 004 d892e0c6cb.svg]]

*A roofline silhouette: a blue memory-bound slope rising to a dashed ridge, then a flat orange compute-bound ceiling. A prefill dot sits on the orange ceiling; a low-batch decode dot sits on the blue slope.*

*Prefill and low-batch decode often face different resource limits.*

A single end-to-end latency number cannot distinguish a chat response that begins streaming in 100 ms and flows at reading speed from one that leaves the user staring at a blank screen for two and a half seconds before dumping the entire paragraph at once. Because generative models emit a stream of tokens rather than a single output tensor, serving systems split latency into time to first token (TTFT) and time per output token (TPOT). TPOT is the average of a request’s inter-token latencies (ITL), as defined in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.07 Inference Benchmarks#^sec-benchmarking-token-latency-ttft-tpot-4e1a|Token latency: TTFT and TPOT]]**. In serving, each metric belongs to one phase. *Prefill* (processing the prompt and populating its KV cache) sets TTFT and is often compute-bound, while *decode* (generating output) sets TPOT and is often bandwidth-bound at small batches.

A low TTFT therefore does not mean a fast model. A model can have a fast TTFT but a sluggish TPOT (if the memory wall $({\text{BW}})$ is the bottleneck), leading to a frustrating user experience where the answer starts quickly but “stutters” thereafter. Because these metrics capture distinct aspects of the user experience, interactive services set separate targets for TTFT, TPOT or ITL, and aggregate throughput.

**Systems Perspective 13.5: LLM serving latency targets**

Interactive LLM services usually need separate SLOs for responsiveness, generation fluidity, and fleet throughput. The following values are illustrative targets rather than universal requirements:

- **TTFT**: $<$ 500 ms (for a 1000-token prompt)
- **TPOT**: $<$ 50 ms (equivalent to ~20 tokens/s, faster than human reading speed)
- **Throughput**: $>$ 1000 tokens/s aggregate across active serving replicas

A single “latency” number therefore hides the prefill/decode split. TTFT is the blank-screen budget, TPOT is the reading-flow budget, and aggregate service throughput, measured as tokens/s summed across active serving replicas, determines whether those targets hold under shared load.

### The Decode Floor

^sec-model-serving-decode-floor-7d3a

The chapter’s bandwidth-bound lighthouse puts numbers on both phases. A GPT-2 XL chat request with a 512-token prompt performs about 1.5 TFLOP of prefill arithmetic, which an H100 sustaining 40 percent of its FP16 peak completes in about 3.9 ms, the model’s share of TTFT. Each decode step then reads all 3 GB of FP16 weights to produce one token per active sequence. At batch one that read takes 0.9 ms, so the model-side TPOT can be no shorter, however many arithmetic units the accelerator adds. The floor assumes the step is launched as one captured graph. Issued operation by operation from an eager framework, the same step spends about 8.6 ms on the host submitting 576 kernels, roughly 10× the weight read, which is why every decode floor in this chapter assumes the CUDA Graph capture that **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-hybrid-approaches-jit-compilation-8954|Graph capture and JIT compilation]]** developed.

Batch-one decode with FP16 weights runs at the weight-only arithmetic intensity of about 1 FLOP/byte that **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^sec-network-architectures-inference-memory-bandwidth-wall-98d1|Autoregressive decoding]]** derived. The H100’s ridge point sits near 295 FLOP/byte, so the step is memory-bandwidth bound by more than two orders of magnitude ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-pope2023efficiently|Pope et al. 2023]]). [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^eq-token-generation-time|Equation 14]] gives its floor per token, where ${D_{\text{vol}}}$ is the bytes the step reads and ${\text{BW}_{\text{accelerator}}}$ is the accelerator’s memory bandwidth:

$$
{T_{\text{token}}}\approx \frac{{D_{\text{vol}}}}{{\text{BW}_{\text{accelerator}}}} \tag{14}
$$

 While decode remains bandwidth bound, every step pays to move every weight, in energy as well as in time, and adding compute cores yields little latency improvement. Faster memory (Machine), fewer bytes per parameter or a smaller model (Algorithm), or better batching and cache management change the bound.

^eq-token-generation-time

Batching changes which bytes dominate. Each sequence also reads its own KV cache on every step. GPT-2 XL’s attention heads each keep their own keys and values, so its cache holds 307.2 KB per token of context, or 314.6 MB for a full 1,024-token context. Batching shares the weight read across sequences but not the cache reads. At batch one with a full context, a step moves 3.3 GB and takes 1.0 ms. At batch 32 it moves 13.1 GB, 77 percent of it cache, and takes 3.9 ms. Aggregate throughput rises from about 1,010 tokens/s to 8,200 tokens/s, while each sequence’s TPOT stretches by 3.9×. The same trade between per-sequence cadence and aggregate throughput governs every scheduling technique that follows.

### Decoding Strategies

^sec-model-serving-decoding-strategies-afe8

Switching a chat endpoint from greedy decoding to four-way beam search quadruples both the arithmetic per step and the KV-cache memory each active user holds. The sampling algorithm executed at each step therefore shapes serving cost directly. Greedy decoding takes the highest-scoring token and needs one forward pass per token, though it can fall into repetitive output because it never revisits an early choice. Beam search keeps several candidate sequences and multiplies both computational work and KV-cache footprint by the beam width. Stochastic sampling instead draws each token at random from the model’s output, after scaling the logits by a temperature and restricting the draw to the most likely tokens with top-${k}$ or top-${p}$ nucleus sampling ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-holtzman2020curious|Holtzman et al. 2020]]). For the serving system, beam width multiplies the state each request holds, while the sampling variants add only a small per-step reduction whose cost depends on its kernel implementation.

Interactive LLM services commonly return tokens as they are produced rather than waiting for complete generation. This streaming response transforms the user experience. A two-second total generation feels responsive when tokens stream continuously, but feels broken when users stare at a blank screen for two seconds. Streaming requires infrastructure support for incremental responses and client-side rendering. Once generation streams token by token, the serving unit changes from one fixed-output prediction to a stateful sequence whose length is unknown when it is admitted and whose memory footprint grows on every step. The unknown length breaks the fixed-batch scheduling developed for fixed-output models, and the growing state turns accelerator memory into the next constraint.

### Continuous Batching

^sec-model-serving-continuous-batching-8bb6

An autoregressive request finishes only when it emits an end-of-sequence token, so its length is revealed one step at a time. Extending the request-level dynamic batching of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-throughput-optimization-18d1|section 13.5]] to an entire generation cycle keeps batch membership fixed until every sequence finishes. When sequence lengths vary, this static commitment degrades accelerator efficiency. If one sequence in a batch of eight finishes after ten tokens while others require 100 tokens, 90 percent of the compute and memory bandwidth allocated to that sequence slot is wasted on padding tokens or masked dummy operations while awaiting the slowest sequence ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-yu2022orca|Yu et al. 2022]]).

**Continuous batching**[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn22|²²]] (also called iteration-level batching) eliminates this idle-slot waste by rescheduling batch composition at each decoding iteration ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-yu2022orca|Yu et al. 2022]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kwon2023|Kwon et al. 2023]]). Rather than committing to a static batch that persists across hundreds of forward passes, the serving engine re-evaluates batch membership at every token-generation step. When a sequence emits its end-of-sequence token, the scheduler immediately reclaims that execution slot, admitting an arriving request into the batch for the subsequent forward pass. Active sequences continue decoding without interruption, maintaining high accelerator utilization across variable-length workloads.

Serving runtimes such as vLLM[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn23|²³]] and TensorRT-LLM improve throughput via two mechanisms: reclaiming wasted compute from completed sequences and shortening queue wait times for new arrivals ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kwon2023|Kwon et al. 2023]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidiaTensorRtLlm|NVIDIA 2026f]]). However, admitting new requests dynamically creates a systems collision between prompt prefill and token decoding. Long-prompt prefill often exposes high arithmetic intensity and can occupy the GPU for tens of milliseconds. Low-batch decoding often has less weight reuse and is memory-bandwidth bound, advancing one token per active sequence at a time. When an engine admits an entire long prompt before advancing active decodes, those streams wait for that prefill, stretching their inter-token gaps.

Sarathi-Serve resolves this prefill-decode interference through chunked prefill and stall-free batching, which admits new prompts without pausing the decodes already running ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-agrawal2024sarathi|Agrawal et al. 2024]]). By splitting long prompts into fixed-size chunks (e.g., 512 tokens) and co-scheduling a single chunk alongside active decode requests per step, the scheduler limits the prefill work admitted per iteration, reducing interference with active decodes. Measured iteration times determine the resulting token cadence.

The scheduling boundary determines when an existing stream can emit its next token. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^fig-serving-chunked-prefill|Figure 8]] compares admission of one complete prompt with admission of the same prompt in chunks, while keeping the active stream visible in both schedules.

![[90 Assets/Volume I/13 Model Serving/Generated Figure ceb078301c.svg]]

Figure 8: **Prefill Admission and Decode Cadence**: A new prompt P shares one worker with an active decode stream. Admitting P whole leaves a long interval between that stream’s tokens. Admitting P in chunks inserts a decode step at each iteration boundary; P finishes later in the schedule shown. Both paths process the same prompt. Bar widths and token spacing are schematic, not measured durations or a throughput prediction.

^fig-serving-chunked-prefill

Chunking creates more opportunities to advance the active streams, but each chunk still consumes accelerator time. The scheduler must choose a chunk budget from measured iteration latency; an iteration boundary alone does not guarantee a token deadline.

#### Speculative Decoding

^sec-model-serving-speculative-decoding-b52e

Continuous batching and chunked prefill keep decode batches full and their cadence steady, but at small batch each generated token still pays for one full weight stream. Speculative decoding[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn24|²⁴]] attacks that bound directly by exploiting the arithmetic units that sit idle during bandwidth-bound batch-one decode. A small, fast **draft model** runs ${\gamma}$ sequential decode steps to propose a block of ${\gamma}$ candidate tokens, and the large **target model** then evaluates all ${\gamma}$ candidates at once in a single forward pass, much like a short prefill step.

Because the target model computes next-token probability distributions at the last confirmed position and after each of the ${\gamma}$ draft tokens simultaneously, it can check each draft choice in order. At the first position where a draft token is rejected, the target model substitutes a token sampled from its own distribution at that position and discards the remaining draft tokens. If all ${\gamma}$ draft tokens are accepted, the target model’s distribution at the final position yields one additional $({\gamma}+1)$-th token at no extra cost. A single target weight stream therefore always produces at least one valid token and up to ${\gamma}+1$ tokens, while preserving the exact output distribution of the target model alone. Evaluated T5-XXL workloads achieved roughly 2–3$\times$ speedups ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-leviathan2023speculative|Leviathan et al. 2023]]), though the gain depends on how often the target model accepts the draft.

If the draft proposes ${\gamma}$ tokens and the target accepts each with probability ${\alpha}$, independently of the others ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-leviathan2023speculative|Leviathan et al. 2023]]), the number of tokens emitted in one verification round is the accepted prefix of length $0$ to ${\gamma}$ plus the one guaranteed token from the target model’s own distribution. Summing that geometric series gives the expected tokens per target pass in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^eq-speculative-tokens|equation 15]]:

$$
\mathbb{E}[\text{tokens per target pass}] = \frac{1-{\alpha}^{{\gamma}+1}}{1-{\alpha}} \tag{15}
$$

^eq-speculative-tokens

Verifying ${\gamma}+1$ positions in parallel multiplies the target pass’s arithmetic by ${\gamma}+1$, but at batch one its arithmetic intensity starts two orders of magnitude below the H100’s ridge point, so the verification pass remains memory-bandwidth bound and still costs about one weight stream. For the GPT-2 XL service, a GPT-2 Small draft with 248 MB of FP16 weights proposes 4 tokens per round, spending 0.30 ms on draft reads against 0.90 ms for the target’s verification pass. At an assumed acceptance rate of 70 percent, a round yields 2.8 tokens on average, so the time per generated token falls from 0.90 ms to 0.43 ms, a 2.1× speedup. The gain shrinks as acceptance falls or as the batch grows. A full batch already shares each weight stream across many sequences, and verifying several positions per sequence then consumes arithmetic that a batch-one step left idle but a full batch does not.

#### PagedAttention

^sec-model-serving-pagedattention-b8d4

Keeping decode batches full, however, shifts the primary serving bottleneck to memory management. Because transformer generation appends attention states at every step, the KV cache for each active request grows dynamically in accelerator HBM. When sequences of varying lengths share memory, contiguous allocation produces severe external fragmentation. If a completed 100-token sequence releases its cache, an arriving 150-token request cannot occupy that freed memory because it requires a larger contiguous address range. Over time, physical memory fractures into small, noncontiguous gaps, preventing new sequences from launching even when total unallocated capacity appears sufficient. Contiguous allocators also reserve memory for the maximum sequence length up front, so much of each reservation sits unused while the sequence is short. Together with that over-reservation, this memory fragmentation can waste 60 to 80 percent of KV-cache memory in naive implementations ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kwon2023|Kwon et al. 2023]]), severely limiting the concurrent batch size that determines serving throughput. Paging recovers that waste, and [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^sec-model-serving-kv-budget-e81c|section 13.9.5.1]] then computes how many conversations the recovered memory can hold.

![[90 Assets/Volume I/13 Model Serving/Vol1 Model Serving Margin 002 8f1f33918c.svg]]

*Two horizontal bars: the contiguous-allocation bar carries a wide red wasted segment; the paged-allocation bar below shows only a thin red sliver, the rest used.*

*PagedAttention recovers the KV-cache waste of contiguous allocation.*

**PagedAttention**,[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn25|²⁵]] introduced in vLLM, resolves this fragmentation by applying operating system virtual memory paging to accelerator memory ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kwon2023|Kwon et al. 2023]]). In static contiguous allocation, reserving maximum sequence length memory up front causes internal waste, while freed regions may be too small or poorly placed to satisfy a new contiguous reservation. Instead of allocating one contiguous region per sequence, PagedAttention divides the KV cache into fixed-size blocks mapped through a block table. A sequence’s cache can therefore occupy noncontiguous physical blocks. When a sequence completes, its blocks return to a free pool for reuse. Rather than copying noncontiguous blocks into a temporary contiguous buffer before computing attention, a specialized PagedAttention CUDA kernel traverses the block table directly, staging noncontiguous blocks into on-chip SRAM during query-key multiplication.

By eliminating external fragmentation and bounding internal waste to each sequence’s last, partially filled block, PagedAttention reduced KV-cache waste below 4 percent in the reported evaluation and enabled substantially higher batch concurrency on the same accelerator hardware ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-kwon2023|Kwon et al. 2023]]). Paging decides where cache blocks live, however. It does not reduce the KV bytes stored per token; a sequence needs another block only when its current allocation fills.

A block table separates a sequence’s token order from its physical placement. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^fig-serving-paged-kv-mapping|Figure 9]] uses an eight-block pool: requests C and D occupy the middle pairs, leaving four free blocks in two separated runs. A request E that needs four blocks can use those scattered blocks without moving C or D.

![[90 Assets/Volume I/13 Model Serving/Generated Figure 7612892bf0.svg]]

Figure 9: **Logical Pages and Physical KV Blocks**: Request E’s logical pages remain ordered even though its physical blocks are separated by other requests. Each table entry names one physical block; the partially filled last block remains allocated to E. After E completes and its pending accesses finish, its unshared blocks return to the free pool. C and D retain their blocks. The diagram assumes no prefix sharing and uses equal block sizes; paging changes placement, not the KV bytes per token.

^fig-serving-paged-kv-mapping

The free capacity becomes usable without compacting the pool into one contiguous region. The table lookup adds indirection, and the last block can still contain unused token slots; allocation efficiency does not eliminate either cost.

### Memory and KV Cache

^sec-model-serving-memory-kv-cache-d1ea

Even after PagedAttention eliminates fragmentation waste, thirty-two long-context conversations can exhaust an 80 GB GPU’s memory when the quantized model weights themselves occupy less than half the device. The KV cache, the per-sequence store of attention keys and values defined in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^sec-network-architectures-inference-memory-bandwidth-wall-98d1|Autoregressive decoding]]**, grows linearly with sequence length. Prefill creates cache entries for every prompt token, and each decoded token appends another entry, so a request’s footprint is set by its prompt length plus the tokens it has generated so far. Summed across concurrent variable-length sequences, this dynamic state can exceed the model weights and dominate available accelerator memory, which is why the remaining memory levers either reuse cache state across requests or move it off the accelerator.

#### KV Budget

^sec-model-serving-kv-budget-e81c

Once contexts grow, the cache rather than the weights sets how many conversations one accelerator can hold, and Llama 3 8B makes the budget concrete. Each token stores a key vector and a value vector in every layer for every key-value head. Grouped-query attention (GQA) ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-dubey2024llama|Dubey et al. 2024]]) lets the model’s 32 query heads share a smaller set of key-value heads, which cuts the cache by 4× relative to full multi-head attention. Storing 16-bit Key and Value tensors across ${N_L}=32$ layers with ${H_{\text{KV}}}=8$ such key-value heads of dimension ${d_{\text{head}}}=128$ requires $2 \times 32 \times 8 \times 128 \times 2\text{ bytes} = 131{,}072\text{ bytes} \approx 131\text{ KB}$ per token per sequence. An 8,192-token conversation therefore holds 1.07 GB.

With 16.1 GB of FP16 weights resident on an H100 whose 80 GB datasheet capacity is 85.9 GB in the decimal units used for tensor footprints, about 69.8 GB remains for caches before runtime workspace, room for about 65 such conversations at once. The weights are a fixed cost; every additional conversation, and every additional thousand tokens of context, draws on the same remainder.

Larger models make the cache the limiting constraint sooner. For a 70-billion-parameter-class model with grouped-query attention, 4-bit weights consume 35.3 GB of the same H100, leaving 50.6 GB for FP16 cache before runtime workspace. A batch of 32 conversations exhausts that budget at roughly 4,800 tokens of context, so serving engines trade concurrent batch size against context length to avoid out-of-memory failures ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.10 LLM Serving#^fig-kv-cache-growth|figure 10]]).

![[90 Assets/Volume I/13 Model Serving/Cell 53 Output 1 a1ffe70f01.png]]

Figure 10: **The KV-Cache Explosion**: FP16 KV-cache usage vs. context length for a 70-billion-parameter-class model with GQA. On the modeled H100’s 80 GB of HBM (85.9 GB decimal), 35.3 GB of INT4 weights leave 50.6 GB for KV cache before runtime overhead. Batch size 32 reaches that cache budget at roughly 4.8k tokens, forcing a trade-off between batch size and context length.

^fig-kv-cache-growth

The 70-billion-parameter-class model fits one H100 only because its weights were cut to 4 bits. A model whose weights and cache do not fit one accelerator, even at reduced precision, can still be served from one machine by splitting it across the node’s accelerators with the model parallelism of **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-model-parallelism-c97e|Model parallelism]]**. Serving usually favors tensor parallelism, because every accelerator then works on every token at once, reading only its slice of the weights and of the KV cache, so the node’s combined memory bandwidth serves each token. A pipeline split also fits the model, but a token still passes through its stages in turn, so the step is no shorter.

Tensor parallelism pays for its split with a collective operation after each layer’s matrix multiplications. On NVLink that exchange is small next to the layer’s compute; over PCIe or a network it would dominate each decode step. A serving engine therefore keeps one model’s tensor-parallel group inside a single node and meets higher volume by replicating whole groups across machines rather than stretching one group across them.

#### Prefix Caching and Memory Offloading

^sec-model-serving-prefix-caching-offloading

Many requests carry identical prefixes, and recomputing their cache entries wastes both prefill compute and memory. **Prefix caching** stores the KV states of common instruction prefixes (such as a 2,000-token system prompt or a shared retrieval-augmented generation (RAG) context), allowing independent requests to reuse the prefill result for an identical prefix. For ${n_{\text{req}}}$ requests sharing a prefix of ${S_{\text{prefix}}}$ tokens, the avoided prefill work is roughly $({n_{\text{req}}}-1){S_{\text{prefix}}}$ token steps, subject to cache hits, eviction, and implementation overhead. Prefix caching saves memory as well, because requests that share a prefix can map to the same stored cache blocks rather than each holding a copy. The shared tokens then count once against the cache budget, which leaves room for more resident conversations. For multi-turn conversations, the same principle lets a subsequent turn process only the new suffix after reusing compatible prior state.

When the aggregate KV cache exceeds GPU VRAM, systems can use **KV cache offloading**. This strategy spills inactive or low-priority context windows to host CPU RAM or NVMe SSD, freeing VRAM for active generation. The reload cost is bounded below by bytes moved divided by PCIe or NVMe bandwidth, before software overhead and queueing are added. Offloading therefore prevents OOM failures and enables larger context windows, but it also creates affinity, invalidation, and hot-decode latency risks that must be budgeted explicitly.

### Session Affinity Constraints

^sec-model-serving-session-affinity-constraints-8b1f

Prefix reuse and offloading both assume that the next turn of a conversation reaches the replica that holds its cache. Session affinity, routing successive requests from a client to the same physical replica, arises whenever serving state resides in local accelerator memory rather than being reconstructed on every invocation. In conversational models, this resident state is dominated by the KV cache. When turn ${i}$ executes on a replica, that replica’s HBM retains the projected keys and values across all prior prompt and generation tokens. Routing turn ${i}+1$ to a different replica discards that local memory footprint, forcing the new node to recompute the entire prefix sequence from scratch. This redundant prefill consumes memory bandwidth and tensor-core cycles that would otherwise advance active decode iterations, directly inflating time-to-first-token.

A parallel physical constraint governs personalized serving using fine-tuned Low-Rank Adaptation (LoRA) modules: small per-user adapters, each a pair of low-rank matrices whose product is added to a frozen base weight matrix. While base-model weights remain pinned in device HBM, individual user adapters must be dynamically staged into memory. If incoming requests for a user scatter across multiple replicas, each node must repeatedly transfer adapter tensors over the host-to-device PCIe bus or fetch them across the network, displacing other active working sets in memory. Stateful preprocessing pipelines, such as tokenizer vocabularies and per-session normalization state, impose the same penalty, requiring redundant CPU-side allocations and cache rebuilds whenever execution moves across node boundaries.

↩︎ Products of two low-rank matrices, and the storage and memory traffic they save relative to a full matrix, are established in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-lowrank-factorization-955e|Matrix factorization]]**.

Strict affinity creates a direct conflict with dynamic batching. Continuous batch schedulers maximize accelerator throughput by packing concurrent requests into unified matrix multiplications, raising arithmetic intensity in proportion to batch size (${I}\propto {B}$). When requests are pinned to designated replicas, the scheduler’s pool of batchable candidates fragments across the cluster. A replica assigned to an idle or low-concurrency user session must either process underfilled batches, collapsing arithmetic intensity back into the memory-bandwidth-bound regime, or stall waiting for affinity-matched tokens. To prevent this collapse in utilization, production routers use soft affinity. Under soft affinity, the ingress gateway prioritizes the cache-holding replica when capacity allows, but sheds requests to alternate nodes when local queue delays exceed the physical latency required to transfer adapter weights or recompute prefix tokens.

**Systems Perspective 13.6: LLM serving: Beyond the fundamentals**

Each LLM serving technique answers one of two physical limits. The first is the decode bound, in which every generated token pays for a full weight stream at small batch. Continuous batching keeps decode batches full so each stream serves many sequences, chunked prefill keeps prompt processing from stalling that stream, and speculative decoding extracts more than one accepted token per stream. The second is the KV cache, which grows with sequence length and batch size and often exceeds the weights themselves; PagedAttention, prefix caching, offloading, and session affinity decide where it lives and how much of it can be reused. Weight-only quantization (such as INT4 weights with FP16 activations), the precision lever of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-precision-selection-serving-55ba|section 13.6.3]] applied to the weight stream, addresses both at once, because it shrinks the bytes streamed per token and frees capacity for cache ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-lin2023awq|Lin et al. 2024]]).

These LLM-specific optimizations build directly on core serving mechanics. Queueing models govern scheduling timeouts, batching dynamics determine throughput-latency curves, and reduced precision bounds memory traffic. Advanced treatments extend these mechanics to multi-tenant prefix sharing across fleets and multi-node tensor-parallel execution.

Every technique above changes how many sequences share each weight stream and how long each one holds its cache. Because an accelerator draws power whether a decode pass serves one sequence or a full batch, that same sharing directly governs the energy each generated token costs. Dividing node power by aggregate token throughput converts batching and prefix-caching gains into joules per token.

**Napkin Math 13.5: The energy cost of a chat**

**Problem**: How much energy does an H100-backed chat service spend per generated token and for a response with 500 tokens?

As LLMs scale, joules per token becomes a first-class operational metric alongside latency. Assuming the H100 draws its 700 W thermal design power (TDP), this scenario estimate follows from throughput and power ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-choquette2023|Choquette 2023]]):

1.  **Throughput**: 114 concurrent requests $\times$ 8 tokens/s per request ≈ 912 tokens/s.
2.  **Power**: 700 W (GPU) + 300 W (Host/Overhead) = 1000 W.
3.  **Energy per token**: 1000 W / 912 tokens/s ≈ 1.0965 J/token

**Systems insight**: Under these assumptions, a response of 500 tokens consumes ≈ 548.2 J. A measured production figure is of the same order. Google reports ≈ 864 J (0.24 Wh) for the median Gemini text prompt, counting host, idle-reserve, and facility energy, although the study does not state how long that prompt was ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-elsworth2025measuring|Elsworth et al. 2025]]).

- For comparison, charging a smartphone consumes ≈ 40000 J.
- Boiling a cup of water consumes ≈ 100000 J.

The primary way to reduce J/token is to increase hardware utilization and eliminate redundant compute. If the GPU sits at 10 percent utilization due to poor batching, it still draws ~300 W and the host adds 300 W, causing energy per token to rise to 6.6 J/token (approximately 6× the baseline). Architectural optimizations like prefix caching also skip the energy-intensive prefill phase for shared context, directly reducing the energy footprint of retrieval-augmented generation (RAG) and chat applications. The serving lesson is that efficiency is not only a latency or cost metric; it also determines how much energy each useful token consumes.

**Systems Perspective 13.7: Looking ahead: Spending more compute per query**

Every lever so far takes the number of tokens a request generates as given, and fixed-output serving minimizes latency (${L_{\text{lat,total}}} \to 0$) for a fixed amount of work per request. Reasoning models and other inference-time-compute systems make that token count a choice. They deliberately spend more computation per query to improve answer quality, generating intermediate reasoning or search tokens before the visible answer. The optimization target then expands to include answer quality, and every extra reasoning token pays the decode costs this section derived. It adds one more step of decode work at the batch’s cadence, holds one more KV-cache entry until the response ends, and takes its share of the joules per token. Answer quality now trades directly against TPOT, cache capacity, and energy per query.

**Checkpoint 13.5: LLM serving fundamentals**

LLM serving introduces constraints absent from traditional model serving.

**TTFT vs. TPOT**: Contrast the distinct user experiences captured by TTFT and TPOT, explain why long-prompt prefill often exposes more arithmetic intensity than low-batch decode, and convert a 50 ms TPOT target into its tokens-per-second equivalent.

**Continuous batching and PagedAttention**: Contrast static batching waste under variable sequence lengths against iteration-level scheduling, and explain how PagedAttention eliminates external fragmentation in the KV cache and bounds internal waste to a single partially filled block per sequence.

**Memory wall**: Explain why adding compute units yields negligible latency improvement when token generation is bandwidth-bound, and identify how higher-bandwidth memory, model quantization, or batching alters the operating regime.

**Prefix caching and offloading**: Explain how caching key-value activations for shared prompt prefixes eliminates redundant prefill compute, and evaluate the latency trade-offs that govern offloading KV caches to host system memory.

**Joules per token**: Explain why energy consumption scales with generated sequence length, and how low hardware utilization inflates the energy cost per useful token.

Every LLM serving optimization ultimately decides how many sequences share each weight stream and how much accelerator memory each sequence holds. The chat-energy calculation showed that the same sharing sets the joules spent per useful token, because each decode step streams the weights once for the whole active batch, so a well-filled batch divides that energy across sequences. Unlike fixed-output inference, LLM energy also grows with response length. These per-token bounds, however, describe one accelerator. Deciding how many accelerators a service needs, and what each generated token costs, requires carrying them, together with the fixed-output results of the earlier sections, into capacity planning and unit economics.
