# V1-13.07 Inference Runtime Selection

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving|V1-13 Model Serving]]

^sec-model-serving-inference-runtime-selection-5eef

Running an unchanged ResNet-50 model through a compiled C++ engine rather than an eager Python interpreter cuts batch-one latency on the reference H100 by more than 5×, without altering a single weight. Dynamic batching and request scheduling govern how requests are grouped and queued, but an execution engine still has to map the resulting tensor operations onto physical execution units and memory hierarchies. The **inference runtime**, the software layer that schedules tensor operations and manages device resources, therefore changes both latency and throughput for a fixed model architecture. Runtime engineering proceeds in two steps. Selection chooses the execution engine that fits the deployment target, and configuration tunes that engine for the model, hardware, input shapes, and latency budget.

### Runtime Constraint Map

^sec-ml-frameworks-quantitative-framework-efficiency-comparison-3b77

Attempting to deploy a Python-based server runtime onto a 256 KB microcontroller fails before the first request arrives, and exporting a model with custom operators to a mobile neural processing unit (NPU) delegate can silently push unsupported layers back onto the CPU. The deployment target narrows the viable runtime family before any speed comparison matters, and each tier in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.02 The Serving Inversion#^tbl-resnet-serving-spectrum|table 2]] rules out entire classes of software. The keyword-spotting microcontroller in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-tinyml-micro-runtimes-2a1b|Static runtimes for microcontrollers]]** requires a fixed memory arena and a compact C/C++ runtime. A smartphone, by contrast, can host an application runtime that routes supported operators to accelerator delegates and falls back to another path when an operator is missing. Within each target envelope, [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^tbl-framework-efficiency-matrix|table 13]] lists the candidate runtime families and the conversion or execution condition each candidate must pass before latency or memory numbers can be compared.

| **Runtime family**              | **Where it fits**              | **Constraint anchor**                                             | **Optimization path**                         | **Constraint to test**                     |
|:--------------------------------|:-------------------------------|:------------------------------------------------------------------|:----------------------------------------------|:-------------------------------------------|
| **PyTorch eager**               | Research and iteration         | Baseline latency; full Python/runtime footprint                   | Dynamic graphs, eager debugging               | Dispatch overhead and missing graph view   |
| **Compiled PyTorch/TensorFlow** | Server training and serving    | Workload-dependent gains when graph capture is clean              | Graph capture, fusion, layout planning        | Operator coverage and graph breaks         |
| **TensorFlow Lite/Core ML**     | Mobile and edge inference      | Target-specific mobile latency and package-size budgets           | Quantization, static graphs, NPU delegates    | Target-specific conversion constraints     |
| **TF Lite Micro/microTVM**      | Microcontroller inference      | Target-specific microcontroller RAM and flash budgets             | Static allocation, INT8 kernels               | Selected operators and constrained memory  |
| **ONNX Runtime**                | Cross-framework serving        | Backend-dependent; can match native runtimes for supported graphs | Standard graph format, execution providers    | Export gaps and custom-operator fallbacks  |
| **TensorRT/TVM**                | Hardware-specialized inference | Target-dependent gains over untuned eager baselines               | Kernel fusion, precision lowering, autotuning | Narrower target and conversion assumptions |

Table 13: **Runtime Constraint Map**: Read each row left to right as one trade, in which a family gives up flexibility, gains an optimization path, and acquires a new way to fail. The middle column records where a family sits relative to an untuned eager baseline rather than a measured result, so latency, memory use, energy, and utilization still have to be measured for the specific model, hardware, precision, batch size, and compiler configuration.

^tbl-framework-efficiency-matrix

A runtime can fit the device and still fail to execute the exported model. Specialized inference runtimes such as TensorRT and Apache TVM require compatible operators and conversion paths; a mobile delegate may support only part of a graph. Unsupported regions can introduce fallback execution and extra transfers. Portability therefore requires an agreement about the graph and operator semantics on both sides of the export boundary.

### Runtime Ecosystem and Configuration

^sec-model-serving-frameworknative-serving-da62

Serving a model directly from the Python interpreter used to train it is the fastest path to a working endpoint, but under production load the interpreter itself becomes the bottleneck. Threads contend for the Global Interpreter Lock (GIL), operators launch one by one without whole-graph fusion, and dynamic allocations fragment memory. Engine selection therefore starts with the limiting system constraint rather than the training framework. When rapid iteration and full support for dynamic Python control flow or custom operators matter most, PyTorch and TensorFlow models can serve directly through their native runtimes. When interpreter overhead limits throughput, serialized graph formats such as `torch.export` and TensorFlow SavedModel (with TorchScript supporting legacy deployments) capture a static operator graph for ahead-of-time optimization and multi-threaded C++ execution. Framework-native runtimes prioritize developer flexibility and broad operator coverage, whereas specialized inference engines trade that generality for whole-graph rewrites and lower launch overhead.

#### General-Purpose Optimization

^sec-model-serving-generalpurpose-optimization-9ec2

The development framework and deployment runtime need not be the same system, but they must exchange a representation both can interpret. The **ONNX** format addresses this fragmentation by standardizing model exchange across runtimes ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-bai2019onnx|ONNX Contributors 2019]]). A pipeline can train an architecture in PyTorch, export the computation graph to an ONNX intermediate representation, and execute the serialized graph in ONNX Runtime or compile it for a target accelerator. In contrast, TensorFlow Lite relies on its own conversion path, translating TensorFlow SavedModels into FlatBuffers rather than routing through ONNX. Although standard interchange formats reduce manual model conversion between development and production environments, they do not eliminate compatibility testing, operator coverage gaps, or custom-kernel fallback overhead.

The exchange is hub-and-spoke around the common ONNX intermediate representation ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^fig-onnx|figure 7]]). Training frameworks export inward to the shared representation, and ONNX Runtime and other target frameworks load the serialized computation graph outward without reimplementing model code.

![[90 Assets/Volume I/13 Model Serving/Onnx New b5026c866c.jpg]]

Figure 7: **Framework Interoperability**: The inward spokes represent exports into the shared ONNX format, while the outward spokes represent loads into compatible tools and runtimes; portability requires support on both sides of that boundary.

^fig-onnx

Interchange formats mitigate framework fragmentation, but an export boundary cannot salvage an architecture that violates the target’s physical limits. Converting a graph to ONNX or an embedded runtime after development completes cannot resolve an excessive memory footprint, missing hardware operators, or unsupported dynamic control flow. Treating deployment as an afterthought guarantees costly rewrites, which is why hardware and runtime trade-offs need evaluating before the first line of model code is written.

When cross-hardware portability is the limiting constraint, ONNX Runtime[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn14|¹⁴]] provides an intermediate, hardware-agnostic execution layer ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-onnxruntime2024|Microsoft 2024]]). Models export to the ONNX format, after which ONNX Runtime applies target-independent graph optimizations and delegates subgraphs to hardware-specific execution providers. This architecture enables single-format deployment across CPUs, GPUs, and custom accelerator application-specific integrated circuits (ASICs).

Portability still demands profiling operator placement across execution boundaries. If an operation is unsupported by the preferred execution provider, placement depends on the configured provider order and available implementations. A CPU fallback can introduce host-accelerator transfers and synchronization that erode the expected latency advantage; if no provider supports the operation, execution may fail. Profiling must therefore verify provider assignment and operator coverage across the entire graph, not merely confirm that the exported artifact executes without errors.

#### Specialized Inference Engines

^sec-model-serving-specialized-inference-engines-475f

When latency budgets or serving costs matter more than portability, specialized engines such as TensorRT for NVIDIA GPUs and OpenVINO[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn15|¹⁵]] for Intel hardware optimize graphs specifically for target microarchitectures ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidia2024tensorrt|NVIDIA 2024a]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-openvinoDocs|Intel Corporation 2026]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-chen2018tvm|Chen et al. 2018]]). Rather than maintaining portable abstractions, these compilers specialize kernels directly to the hardware’s register files, cache hierarchies, and matrix execution units. A specialized engine such as TensorRT or TVM offers no advantage unless its backend supports the target and its conversion path supports the model ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-nvidia2024tensorrt|NVIDIA 2024a]]; [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-chen2018tvm|Chen et al. 2018]]), and ONNX reduces the exchange burden without proving either condition ([[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.15 Source References#^ref-bai2019onnx|ONNX Contributors 2019]]).

Layer fusion[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.16 Footnotes#^fn16|¹⁶]] is kernel fusion (also called operator fusion) applied when the engine is built. For the convolution $\to$ batch normalization $\to$ ReLU block, whose folding **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^sec-model-compression-operator-fusion-ac1d|Compression-specific fusion]]** derives, the serving compiler performs the fold once, at engine build time, because batch normalization is a fixed affine transform once training ends, and the fused kernel reads its input feature map from HBM once.

↩︎ Kernel fusion, which merges adjacent operations so intermediates stay in registers and on-chip memory instead of round-tripping through HBM, is established in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8|The memory wall and kernel fusion]]**.

Kernel auto-tuning benchmarks and selects the optimal algorithm for each operation on the target microarchitecture. A single 2D convolution can run directly, as a general matrix multiplication, or through specialized algorithms for small $3 \times 3$ filters or large spatial filters, alongside dozens of tile-size variations. Because the winning strategy depends on filter dimensions, batch size, and the accelerator’s register and shared memory capacity, the compiler benchmarks candidate implementations against target hardware and caches the lowest-latency kernel, trading ahead-of-time compilation time for predictable serving latency. Together with operator fusion, these optimizations produce substantial speedups over an untuned framework-native baseline, though they require explicit graph compilation and may restrict dynamic tensor dimensions.

**Example 13.6: ResNet-50: Runtime comparison**

[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^tbl-model-serving-runtime-comparison|Table 14]] applies the chapter’s profile to each engine at batch one on the reference H100, changing one term at a time. The eager row is the reference profile. TorchScript runs the same kernels from a graph executor, removing the per-operation Python dispatch. ONNX Runtime also fuses each convolution with its normalization, activation, and residual add, cutting 174 kernels to 56. TensorRT replays the whole fused pass as one captured graph and then varies only the number format. Its FP32 engine computes the matrix products in TF32, the reduced-mantissa Tensor Core format of **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-mixedprecision-computing-656f|Mixed-precision computing]]**, so even the FP32 rows run on Tensor Cores.

| **Runtime**         | **Latency** | **Speedup** | **Notes**                 |
|:--------------------|:-----------:|:-----------:|:--------------------------|
| **PyTorch (eager)** |   3.53 ms   |     1×      | Reference profile         |
| **TorchScript**     |   1.79 ms   |     2×      | No per-op Python dispatch |
| **ONNX Runtime**    |   0.61 ms   |    5.8×     | Fused kernels             |
| **TensorRT FP32**   |   0.38 ms   |    9.3×     | One graph launch; TF32    |
| **TensorRT FP16**   |   0.33 ms   |    10.6×    | FP16 Tensor Cores         |
| **TensorRT INT8**   |   0.30 ms   |    11.6×    | Requires calibration      |

Table 14: **Inference runtime comparison**: Modeled batch-one latency and speedup for ResNet-50 on the reference H100 across PyTorch eager, TorchScript, ONNX Runtime, and TensorRT, from the chapter’s serving profile.

^tbl-model-serving-runtime-comparison

**Systems insight**: Removing per-operation overhead, not lowering precision, produces most of the batch-one speedup. TensorRT FP32 is already 9.3× faster than eager execution, and INT8 adds only 1.3× over FP32, because once host overhead is gone the per-kernel floor dominates a single image. Precision pays at large batch, where per-image work dominates; INT8 also requires calibration data and NVIDIA-specific deployment.

^exmp-model-serving-resnet-50-runtime-comparison

This optimization-compatibility trade-off governs engine selection. Higher specialization can improve hardware efficiency for supported operations and shapes but increases deployment complexity, restricts dynamic control flow, and may introduce numerical deviations from the training baseline. The engineering choice depends on latency budgets, operational constraints, and how frequently model architectures evolve.

Once an execution engine is selected, configuration tunes its resource allocation to the hardware envelope. For CPU inference, thread pool sizes must match physical core counts, because too few threads leave execution units idle, while too many cause CPU cache thrashing, OS scheduling delays, and lock contention across non-uniform memory access (NUMA) domains. For accelerators, static memory preallocation reserves fixed-size activation workspaces during initialization, removing runtime memory allocations (`cudaMalloc`) and page-table faults from the latency-critical request path. Execution provider priority determines which hardware backend handles each operator subgraph, while graph optimization levels balance build times against constant folding and algebraic simplification. Production deployments must benchmark these configurations across full latency distributions (p50, p99) rather than relying on framework defaults.

### Precision Selection for Serving

^sec-model-serving-precision-selection-serving-55ba

On the reference H100, Tensor Cores execute FP16, FP8, and INT8 matrix operations, and each halving of the bytes per value doubles the dense peak rate. For ResNet-50, moving from FP32 to INT8 multiplies large-batch throughput several times over while sacrificing less than 0.4 percentage points of top-1 accuracy. Numerical precision is therefore coupled directly to infrastructure economics. At the serving layer, precision engineering introduces operational constraints: calibration data fidelity, layer sensitivity under live inputs, and dynamic precision dispatch.

↩︎ The quantization techniques this selection draws on, from numerical formats through calibration and quantization-aware training, are established in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-quantization-precision-cd46|Numerical Precision: Changing How Values Are Stored]]**.

#### Precision-Throughput Relationship

^sec-model-serving-precisionthroughput-relationship-b503

For memory-bandwidth-bound operations, reducing precision raises throughput by cutting the byte volume transferred across the memory bus. [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^eq-precision-throughput|Equation 13]] gives the largest gain that fewer bytes alone can buy, a limit that applies only to memory-bound kernels:

$$
\frac{\text{Throughput}_{\text{INT8}}}{\text{Throughput}_{\text{FP32}}} = \frac{32}{8} = 4\times \text{ (theoretical maximum)} \tag{13}
$$

^eq-precision-throughput

Actual speedup depends on the compute-to-memory ratio, operator mix, hardware instruction throughput, and matrix alignment. For memory-bound operations, operator mix and alignment keep the speedup below this bound. At large batch the kernels are compute bound, and the gain follows the ratio of the formats’ peak arithmetic rates and of the fraction of peak each engine sustains. A measured large-batch gain, such as the INT8 row of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^tbl-model-serving-precision-tradeoffs|table 15]], can therefore exceed [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^eq-precision-throughput|equation 13]] without contradicting it, because that bound counts only memory traffic. Low-precision kernels achieve peak arithmetic efficiency only when matrix dimensions align with the accelerator’s warp-level execution tiles (for example, multiples of 8 or 16 elements). When dimensions do not align with hardware tiles, libraries such as cuBLAS and cuDNN pad tensors or fall back to slower execution paths.

↩︎ Tensor Core tile architectures and their matrix-dimension alignment constraints are established in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-tensor-cores-771f|Tensor Cores]]**.

**Example 13.7: ResNet-50: Precision trade-offs on the H100**

| **Precision**  | **Batch-1 Latency** | **Large-Batch Throughput** | **Weights** | **Accuracy** | **Calibration**     |
|:---------------|:-------------------:|:--------------------------:|:-----------:|:------------:|:--------------------|
| **FP32**       |       0.38 ms       |        15,200 img/s        |  102.2 MB   |    76.13%    | None                |
| **FP16**       |       0.33 ms       |        30,400 img/s        |   51.1 MB   |    76.13%    | None                |
| **INT8 (PTQ)** |       0.30 ms       |        89,500 img/s        |   25.6 MB   |    75.80%    | 1,000 samples       |
| **INT8 (QAT)** |       0.30 ms       |        89,500 img/s        |   25.6 MB   |    76.05%    | Additional training |

Table 15: **Precision trade-offs on the H100**: Modeled batch-one latency for each TensorRT engine of the chapter’s profile; large-batch throughput modeled at the sustained fraction for FP32 (on TF32 Tensor Cores) and FP16, and measured by MLPerf Inference for INT8; weight bytes from the registry; assumed top-1 accuracy.

^tbl-model-serving-precision-tradeoffs

**Systems insight**: At batch one, INT8 is only 1.3× faster than FP32, because the fixed per-kernel cost dominates a single image. At large batch it sustains about 6× FP32’s throughput and loses 0.33 percentage points of accuracy with PTQ. QAT recovers most of that loss but requires retraining.

^exmp-model-serving-resnet-50-precision-trade-offs-v100

Integer formats are not the only 8-bit option. On the reference H100, an 8-bit floating-point format (FP8, whose E4M3 layout for weights and activations **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-quantization-precision-cd46|Numerical Precision: Changing How Values Are Stored]]** introduced) is the natural serving default for transformer workloads. The H100’s dense FP8 peak of 1,979 TFLOP/s is 2× its FP16 peak of 989 TFLOP/s, and each value occupies one byte instead of two. For the chapter’s GPT-2 XL service, FP8 weights shrink from 3 GB to 1.5 GB, which lowers the bandwidth floor on a batch-one decode step from 0.9 ms to 0.45 ms. Because the format keeps a floating-point exponent, it tolerates the wide activation ranges of transformers better than INT8, though it still needs per-tensor scale factors and an accuracy check before deployment.

#### Precision Selection Constraints

^sec-model-serving-layer-sensitivity-6a31

Quantizing every layer of a network to INT8 indiscriminately, or calibrating scale factors on daytime studio photos before serving nighttime camera feeds, can cost several percentage points of accuracy. Precision selection is constrained by layer sensitivity, calibration data, and runtime policy.

Not all layers tolerate reduced precision equally. The error bound of the uniform quantizer, half a quantization step inside the calibrated clipping range plus saturation error outside it (**[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-quantization-precision-cd46|Numerical Precision: Changing How Values Are Stored]]**, with the step from **[equation 10.1](https://mlsysbook.ai/vol1/10_model_compression/10_model_compression.html#eq-quant-scale)**), limits what each layer must absorb. Layer-level output or task error depends on activation distributions and downstream sensitivity, so it must be measured layer by layer rather than predicted from a general rule. Comparing each layer’s quantization error with what that layer can absorb explains the common pattern in which first convolutional and final classification layers are retained at FP16 while intermediate layers tolerate INT8. Initial layers receive only a few raw input channels (such as 3 RGB channels), so they have little redundancy with which to absorb quantization noise. Final classification layers, by contrast, produce raw logits where small numerical perturbations directly shift decision boundaries and alter top-$1$ predictions.

Post-training quantization adds a data dependency. The calibration dataset determines the clipping thresholds $[{\alpha}, {\beta}]$ and scale factors ${s}$ used for INT8 conversion, requiring it to match the statistical profile of live serving traffic rather than arbitrary training or validation splits. A calibration-serving distribution mismatch causes excessive clipping or underflow, degrading end-to-end task accuracy, an operational pitfall analyzed in [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.12 Fallacies and Pitfalls#^sec-model-serving-fallacies-pitfalls-336b|section 13.11]].

Production serving architectures can also turn precision from a static compilation setting into a dynamic runtime policy. When request queues are shallow and the system operates with ample latency headroom against its service level objective (SLO), the engine can dispatch requests at FP16 to maximize task accuracy. During traffic spikes that threaten queue saturation, a server that keeps an INT8 engine resident beside the FP16 engine can route requests to it to preserve latency bounds. Similarly, requests that yield low classification confidence under INT8 can be selectively re-evaluated at FP16, so the system pays the extra FP16 latency only on the uncertain requests. Either policy holds two engines in memory, and the INT8 engine must be calibrated and validated for accuracy before it takes live traffic.

Precision selection carries direct infrastructure sizing consequences. Under the large-batch throughput gain of [[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^tbl-model-serving-precision-tradeoffs|table 15]], 10 GPUs at INT8 offer the same aggregate saturated capacity as about 59 GPUs at FP32. Equal capacity does not establish equal queueing latency; service-time distributions, batching policy, and failure reserve must still satisfy the same SLO. Precision engineering is therefore an infrastructure sizing discipline, directly coupling numerical representation to cluster capital expense and energy consumption. Yet configuring the runtime and numerical bit width addresses only the model level; achieving low-latency serving in production requires optimizing the host-to-device boundaries within the physical server node itself.
