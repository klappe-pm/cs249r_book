# V1-14.05 Releasing Models

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14 ML Operations|V1-14 ML Operations]]

^sec-ml-operations-production-operations-b76d

A model that passes every offline check has still not made a single production decision. Between the validated checkpoint and the first user-facing prediction lie packaging, conversion to a serving runtime, staged exposure to live traffic, and a path back if the new version misbehaves. At each step, the artifact users see can drift from the artifact that was evaluated. Deployment transforms a static checkpoint into a versioned, reproducible execution artifact. Serving then allocates accelerator memory, stages input batches, and schedules compute kernels to satisfy latency SLOs under dynamic request loads. The release and recover steps of the operations loop own the seams between the two: proving that what ships is what was validated, limiting how much traffic a bad version can reach, and keeping rollback fast enough to use. On the ranking service each of those seams also costs memory, because any control that keeps two versions alive must hold two copies of the embedding tables.

### Infrastructure as Code

^sec-ml-operations-infrastructure-management-bf8f

Holding two copies of the ranking tables across a staged release only works if staging and production provision the same accelerator hardware, memory limits, and scaling quotas. When teams manage clusters through manual commands or tickets instead of code, environments drift apart. A model that passed staging fails in production because an operator provisioned a different GPU type. A training job crashes because a colleague’s experiment exhausted shared memory. An inference service fails to scale because its resource quotas were set in an informal message six months earlier.

**Infrastructure as code (IaC)** treats infrastructure configuration as software (version-controlled, reviewed, tested, and automatically executed) rather than something configured through graphical interfaces or command-line tools. Changes are tracked, configurations can be tested before deployment, and environments can be reliably reproduced.

The specific tool matters less than the property it enforces. Infrastructure-as-code tools such as Terraform ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-terraform|HashiCorp 2014]]) version infrastructure definitions alongside application code. A team can then reproduce the accelerator type, network policy, storage permissions, and scaling limits of a training or serving environment on any cloud provider or on-premises hardware, and can audit and test those definitions in the same CI/CD pipelines as the model. Containerization provides the same reproducibility boundary for runtime dependencies. Docker ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-docker|Merkel 2014]]) packages the model, libraries, and serving code into an isolated unit, and orchestration systems such as Kubernetes ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-kubernetes-orchestration-fec67438|Cloud Native Computing Foundation 2024a]]) deploy that unit repeatedly while keeping resource allocation, scaling, and health management explicit.

To absorb spikes during hyperparameter tuning and surges in prediction traffic, teams use autoscaling[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn11|¹¹]] ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-aws-autoscaling-eacffe63|Amazon Web Services 2024]]), which adjusts compute capacity from usage metrics to balance performance and cost. The same infrastructure definitions must also cover on-premises and edge targets when latency, privacy, or regulation keeps part of a deployment off the cloud.

Infrastructure as code addresses how to provision resources reproducibly, but operators must still decide when and how much capacity to allocate. ML workloads break the assumptions of conventional web provisioning. Training jobs demand high-concurrency bursts across distributed accelerator topologies, creating friction between cluster utilization efficiency and time-to-solution. Inference services require sustained baseline allocations with rapid elastic scale-out to absorb request spikes under strict tail-latency SLOs, a balance that the utilization targets of [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.06 Production Monitoring#^sec-ml-operations-hardware-utilization-patterns-5c10|section 14.5.1.1]] quantify. Reproducible cluster and container provisioning fixes the environment around the model, yet the model binary loaded into that container is itself transformed before serving.

### Validating the Serving Artifact

^sec-ml-operations-model-format-optimization-c9d6

Matching the cluster and container across staging and production still does not guarantee that the model inside the container computes the same predictions it produced in evaluation, because the artifact that reaches the serving fleet is rarely the raw training checkpoint. Before deployment, the model is usually compiled from eager framework code into a static graph for a specific runtime and often lowered in precision. Each conversion trades portability for speed, and each can change what the model computes, so the operational obligation is to prove that the converted artifact still behaves like the model that was validated.

↩︎ Inference runtimes and the precision choices they support for serving are established in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-inference-runtime-selection-5eef|Inference Runtime Selection]]**.

That proof must target the failure modes that conversion introduces silently. Consider a team that deploys an INT8-quantized model after verifying only throughput improvement. Classification accuracy drops on rare but high-value edge cases, and the degradation goes undetected for weeks because aggregate metrics remain within SLO bounds. The first validation layer is numerical equivalence, comparing optimized outputs against the original model on a representative test set with application-specific divergence thresholds. That check is necessary but insufficient, because a static calibration slice (the fixed sample of inputs used to set the quantization scales) is not live traffic. Rare inputs, out-of-distribution examples, and subgroup-specific cases can expose quantization artifacts that aggregate test metrics hide, so the comparison must be disaggregated by the same cohorts that production monitoring tracks ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.06 Production Monitoring#^sec-ml-operations-production-monitoring-5e1b|section 14.5]]).

↩︎ Range calibration, which sets quantization scales from a sample of inputs, is established in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-calibration-c650|Range calibration]]**.

The second layer is operational validation. Memory footprint must be measured at peak runtime utilization, including dynamic allocations during inference, since some optimizations trade increased runtime memory for computational speed. Warm-up behavior varies by runtime: Accelerated Linear Algebra (XLA) may just-in-time (JIT) compile kernels during initial execution, whereas TensorRT builds its compiled engine before deployment. Loading that engine can still add startup latency. Runtime version compatibility then closes the loop. Deployment configurations need explicit version pinning, because even a minor runtime upgrade can change kernel selection, and with it both latency and numerical results, in an artifact whose weights never changed. An unpinned runtime is an untracked input to [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^eq-model-reproducibility|equation 1]].

### Model Deployment

^sec-ml-operations-model-deployment-b9b9

Even a verified, runtime-pinned model engine can fail on its first live request if an engineer copies the weights onto a production server whose feature-extraction library differs from the one used in evaluation, causing the ranking model to score nearly every item the same. Model deployment is therefore a systems release problem rather than a file transfer, because the validated model weights, pinned serving runtime, and preprocessing configuration must ship as a single deployable unit. Packaging that bundle into the immutable container image of [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-infrastructure-management-bf8f|section 14.4.1]][[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn12|¹²]] enforces environment parity between development and cluster nodes.

When the model registry promotes that containerized candidate ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-chen2020|Chen et al. 2020]]), the release pipeline first deploys it to a staging or QA environment[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn13|¹³]] to verify functional and statistical invariants before any user traffic reaches it.

A **staged rollout** carries that staging validation into live traffic in steps, widening a candidate’s exposure only after the previous step shows no regression. Three release strategies put it into practice. **Shadow deployments**[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn14|¹⁴]] duplicate live production traffic asynchronously to a candidate model without returning its inferences to users, enabling latency and output comparison without direct user exposure; accuracy still requires labels or another ground-truth reference. **Canary deployments**[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn15|¹⁵]] route a small share of user traffic to the candidate and keep ramping that share toward full traffic as long as no regression appears under live load. **Blue-green deployments**[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn16|¹⁶]] maintain parallel environments for router-level cutover and rapid rollback. Each strategy reduces a different release risk, but none removes the need for tested rollback procedures and production monitoring.

↩︎ Staged rollout as the lifecycle’s last validation step, extending offline evaluation to live traffic, is established in **[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.09 Stage 4 Evaluation and Validation#^sec-ml-workflow-offline-online-evaluation-3a6b|Offline and online evaluation]]**.

In a canary release, the router exposes the candidate to an initial slice of live traffic ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-martin-fowler-canary-26cb78d7|Fowler 2014]]) while telemetry pipelines monitor inference latency, system stability, and prediction distributions. On the ranking service, a candidate receives 5 percent of live queries while the team compares click-through rate, p99 latency, and prediction drift against the baseline model. Only after the candidate demonstrates statistical stability without latency regressions is it promoted to serve full production traffic.

**War Story 14.2: The Knight Capital error (2012)**

**Context**: Knight Capital Group was a major market maker in US equities whose trading accounted for about 10 percent of all trading in listed US stocks. In August 2012, an operational deployment updated SMARS, the firm’s automated order-routing software, on seven of eight production servers but omitted the eighth ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-sec2013knight|U.S. Securities and Exchange Commission 2013]]).

**Mechanism**: The deployment repurposed a binary feature flag that, on the un-updated eighth server, activated Power Peg, an obsolete order-handling routine that had been left in the code. On the stale server, Power Peg no longer counted how many shares of each incoming parent order had already been filled, so it kept sending smaller child orders to trading venues without stopping.

**Impact**: In about 45 minutes, 212 parent orders produced millions of child orders and more than 4 million executions in 154 stocks, covering more than 397 million shares, and Knight lost more than \$460 million. Less than a year later, Knight’s parent company combined with GETCO Holding Company to form KCG Holdings.

**Response**: The incident motivates verifying that every production node runs the intended version before it receives traffic, explicit feature-flag lifecycle controls, and circuit breakers that limit the damage a faulty release can cause.

**Systems lesson**: One server running the wrong version was enough to cause a \$460 million loss. ML deployments share this vulnerability: a model registry version mismatch, un-synchronized feature schemas, or partial canary routing can flood production with corrupted inference requests before telemetry alerts fire.

Knight Capital shows why every node must be verified to run the intended version before traffic reaches it. Each serving node therefore reports the content hash of the bundle it loaded, and the release pipeline compares that hash with the version the model registry promoted and keeps any node that disagrees out of rotation. Staged rollouts add a complementary protection by limiting how much traffic a bad version sees, but they can also expose load-dependent behavior.

When canary deployments reveal anomalies at elevated traffic shares (such as memory exhaustion, queue spillover, or p99 tail latency inflation appearing at 30 percent traffic that remained undetectable at 5 percent), isolation requires systematic debugging across the stack. Effective diagnosis requires correlating multiple signals: performance benchmarking metrics, data distribution analysis to detect drift, and feature importance shifts that might explain degradation. Teams maintain debug toolkits for this work, including A/B test analysis ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-ab-testing-model-validation-e480|section 14.4.3.2]]), feature attribution ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.08 Incident Response and Governance#^sec-ml-operations-feature-attribution-debugging-f4ab|section 14.7.1.2.3]]), and slice analyzers that identify which subpopulations are experiencing degraded performance ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.08 Incident Response and Governance#^sec-ml-operations-slice-analysis-9fe6|section 14.7.1.2.2]]). That diagnosis loop must connect directly to the release pipeline, because CI/CD integration automates deployment and rollback only when rollback is designed as part of the rollout mechanism rather than treated as an emergency script.

#### Rollback Strategies and Safety Mechanisms

^sec-ml-operations-rollback-strategies-safety-mechanisms-7707

Without reliable rollback[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn17|¹⁷]] capability, teams become deployment-averse and slow their iteration velocity, so an effective rollback design plans for three distinct scenarios. The fastest tier, **immediate rollback**, addresses critical failures detected right after deployment, such as serving errors, latency spikes, or obvious prediction failures, keeping the previous model version loaded and warm to switch traffic without cold-start delay. **Rapid rollback** handles performance degradation detected through canary metrics soon after deployment and relies on model registry integration to redeploy previous versions with minimal configuration changes. Once a release has ramped to full traffic, **delayed rollback** addresses subtler regressions that surface later in business metrics or user feedback. Reverting there must also handle model-dependent data such as personalization state or cached embeddings accumulated under the new version. [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^tbl-rollback-patterns|Table 9]] summarizes implementation patterns for each rollback type:

| **Rollback Type** | **Trigger**               | **Implementation**                   | **State Handling**              |
|:------------------|:--------------------------|:-------------------------------------|:--------------------------------|
| **Immediate**     | Serving errors, crashes   | Hot standby with fast routing switch | Verify state compatibility      |
| **Rapid**         | Canary metric degradation | Registry-based redeployment          | Clear caches, restart sessions  |
| **Delayed**       | Business metric decline   | Full redeployment with migration     | Migrate state, replay if needed |

Table 9: **Rollback Patterns by Scenario**: Each rollback type requires different infrastructure support and state handling strategies. Immediate rollback demands always-warm standbys; delayed rollback may require data migration procedures.

^tbl-rollback-patterns

##### Rollback Testing

^rollback-testing

Rollback procedures that have never been exercised often fail during an active incident, when cognitive load and time pressure are highest, because configuration dependencies, incompatible state, or unclear ownership only surface when a revert is actually attempted. Periodic rollback drills expose those gaps beforehand, while step-by-step runbooks ensure that the on-call responder can execute the revert without having designed the deployment. Automated rollback triggers shorten reaction time further, provided their thresholds are calibrated to the service with safeguards against flapping (a metric hovering near its threshold that rolls the service back and forward repeatedly) and the restored model is checked against live caches rather than serving predictions corrupted by incompatible feature state.

##### Stateful Vs. Stateless Rollback

^stateful-vs--stateless-rollback-1366c06a

ML systems vary in statefulness, which directly governs rollback complexity. For stateless workloads like tabular classification and static regression, rollback requires only swapping model weights or routing traffic back to the prior container, because individual inferences share no execution context. In contrast, stateful models (including sequential recommenders, session-based search rankers, and conversational systems) accumulate transient user state. Reverting such workloads can demand session resets, schema shims for cached context vectors, or explicit state migration. Capturing versioned checkpoints at deployment boundaries mitigates this friction, but clean restoration remains an architectural property that requires empirical validation rather than assumption.

The ranking service is the stateful case. It precalculates dense user and item embeddings and holds them in low-latency caches, so if version 2 rotates the latent vector space or changes the embedding dimension, the cached vectors become meaningless to a rolled-back version 1. A stateful rollback must therefore redeploy the weights together with either an atomic cache invalidation or a namespace switch, in which each version’s cached vectors live under their own versioned key prefix (a namespace) and the rollback points lookups back to version 1’s prefix, so that no query is scored against an incompatible vector space. In systems with feedback loops, the most complex failure mode arises when bad predictions pollute downstream feature logs or clickstream training sets during the degraded window. Reverting the serving binary then leaves contaminated data in the retraining corpus, and that data must be expunged or quarantined before previous behavior is restored.

The compatible unit of rollback is larger than the weights. [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^fig-rollback-compatible-bundles|Figure 7]] separates the bundle selected for a new request from the bundle retained by a request already in flight.

![[90 Assets/Volume I/14 ML Ops/Generated Figure a57437e33d.svg]]

Figure 7: **Rollback Preserves a Compatible Version Bundle**: New requests switch to the previous model together with its feature schema and embedding namespace. Requests already admitted to the candidate retain their pinned bundle until completion or confirmed cancellation. Pairing old weights with the new namespace is invalid; reverting routing does not repair logs collected during the degraded interval.

^fig-rollback-compatible-bundles

The router must select the compatible model, schema, and namespace as one decision at request admission. A cutover changes that decision for later requests; it does not migrate earlier requests into a different vector space. A single ranking request finishes in milliseconds, so for it the overlap is brief, but a session in a session-based ranker or a conversational system can stay pinned to one bundle for minutes. Keeping the candidate bundle available until those requests finish or their cancellation is confirmed preserves the contract during coexistence, while log quarantine addresses a separate repair obligation.

#### A/B Testing for Model Validation

^sec-ml-operations-ab-testing-model-validation-e480

Rollback contains a release that degrades service health, and canary routing verifies that a candidate runs without errors or latency spikes, but neither check proves that the candidate improves user outcomes over the incumbent. A/B testing provides the statistical foundation for that promotion decision by comparing model versions on live traffic under controlled conditions, measuring whether the new model improves business metrics with statistical confidence.

##### Experiment Setup and Decision Rules

^experiment-setup-and-decision-rules

A valid A/B test establishes four controls to ensure deployment decisions remain statistically sound. First, the **randomization unit** specifies whether traffic is split by user ID or individual request. User-level hashing preserves consistency across sessions at the expense of larger sample requirements, whereas request-level splitting maximizes sample throughput but risks exposing a single user to alternating model variants. Second, the required traffic volume follows from two probabilities that the team fixes in advance. Confidence is the probability that the test does not report a difference when none exists, and statistical power is the probability that it detects a real difference of the chosen size. Under a common-variance Normal approximation, which treats each variant’s average outcome as normally distributed with the same spread, let ${n}$ be the required users per variant and ${\delta_{\text{MDE}}}$ the minimum detectable effect. Let ${\sigma}$ be the outcome standard deviation (for a conversion metric, each user’s outcome is a yes-or-no event, so ${\sigma}^2$ is the baseline conversion rate times one minus that rate). Let ${z_{\alpha/2}}$ and ${z_{\beta}}$ be the positive standard-Normal critical values for the chosen two-sided confidence and power. The worked scenario uses 95 percent confidence and 80 percent power. [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^eq-ab-sample-size|Equation 4]] translates those design targets into required traffic before launch.

$$
{n}= \frac{2({z_{\alpha/2}}+ {z_{\beta}})^2 {\sigma}^2}{{\delta_{\text{MDE}}}^2} \tag{4}
$$

 The equation’s form follows from sampling noise. The uncertainty of an average shrinks only with the square root of its sample size, so halving the minimum detectable effect quadruples the required traffic, and doubling the outcome standard deviation quadruples it too.

^eq-ab-sample-size

For a 2 percent relative lift on a 5 percent baseline conversion rate (5 percent to 5.1 percent) and 80 percent power, the experiment requires roughly 745,644 users per variant. If traffic limits the test to 25,000 users per variant instead, solving [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^eq-ab-sample-size|equation 4]] for ${\delta_{\text{MDE}}}$ shows that the test can detect only a much larger lift, about 0.5 percentage points absolute.

Third, **guardrail metrics** define operational and behavioral boundaries that must not degrade even if the primary metric improves. A recommendation model improving click-through rate by 10 percent while increasing p99 response latency by 500 ms violates system guardrails and risks cascading timeouts across downstream services. Fourth, a fixed evaluation horizon runs the test until the preregistered sample size and a minimum duration covering weekly seasonality are reached. Stopping the moment significance first appears inflates false positive rates through repeated peeking; sequential designs permit early stopping but need specialized analysis.

Those controls establish the statistical envelope, yet ML systems add failure modes that ordinary web experiments can hide. Conversion events may arrive days after prediction, creating delayed feedback: a recommendation shown Monday can drive a purchase Friday, so the attribution window must be part of the test design. Novelty effects can also inflate early performance as users engage with fresh recommendations, which is why mature experiments include a burn-in period before measurement. Ranking systems add interference effects, because showing an item to one user can change what remains available to another, violating the independence assumption behind standard A/B analysis. Segment heterogeneity creates a further problem when an overall neutral result hides opposite effects in different cohorts. Guardrails, segment analysis, and preregistered decisions therefore belong to the experiment design, and [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^tbl-ab-test-decisions|table 10]] turns those constraints into a deployment decision:

| **Primary Metric**          | **Guardrails** | **Decision**                                                                                                             |
|:----------------------------|:---------------|:-------------------------------------------------------------------------------------------------------------------------|
| **Significant improvement** | All pass       | Ship new model                                                                                                           |
| **Significant improvement** | Some fail      | Investigate trade-offs, may need model iteration                                                                         |
| **No significant change**   | All pass       | Evidence inconclusive; retain current model unless a prespecified equivalence or noninferiority test supports the change |
| **Significant degradation** | N/A            | Do not ship; investigate root cause                                                                                      |

Table 10: **A/B Test Decision Matrix**: Deployment decisions should consider both primary metrics and guardrails. Improvements that come at the cost of guardrail violations require careful trade-off analysis rather than automatic deployment.

^tbl-ab-test-decisions

The “no significant change” row needs care, because failing to detect a difference does not show that none exists. Two tests address that gap directly, each against a margin fixed in advance. A noninferiority test asks whether the candidate is worse than the incumbent by no more than that margin, and an equivalence test asks whether the difference in either direction stays inside it.

↩︎ The rule that nonsignificance never shows equivalence is established in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.09 Benchmarking Best Practices#^sec-benchmarking-statistical-methodological-issues-7aa5|Statistical and methodological issues]]**.

The decision matrix is reliable only when the evaluation methodology is preregistered before launch, establishing expected effect sizes, the randomization unit, attribution windows, guardrail thresholds, and minimum runtimes prior to observing production traffic. Variance-reduction techniques ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-deng2013improving|Deng et al. 2013]]) can shorten an experiment without sacrificing power. Automated analysis pipelines protect the decision boundary from manual calculation errors, and archiving negative results discourages repeating unproductive architectures. An A/B deployment decision is actionable only when the release machinery can promote, hold, or roll back the exact artifact that was evaluated, which is the guarantee the model registry of [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-versioning-lineage-b1cf|section 14.3.1.2]] provides.

### Edge AI Deployment

^sec-ml-operations-edge-ai-deployment-patterns-dc1d

The keyword spotter needs the same two operational guarantees, controlled rollout and fast rollback, on devices with limited power, memory, and connectivity. Consider it after its detection drop. When its model degrades, an engineer cannot SSH into the device, roll back to a previous version, and restart. The device sits in someone’s home on intermittent Wi-Fi, and its 200 KB model shares 4 MB of flash with the firmware that runs it. Every operational assumption from cloud MLOps (instant rollback, centralized logging, real-time monitoring) must be reimagined.

Edge AI runs machine learning inference at or near the data source rather than in centralized cloud infrastructure ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-reddi2020|Reddi et al. 2019]]), and its operations inherit the memory and power envelopes that separate the deployment tiers (**[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.09 TinyML Ubiquitous Sensing#^sec-ml-systems-tinyml-ubiquitous-sensing-scale-a67b|TinyML: Ubiquitous Sensing]]**). A model reaches an edge device already quantized, pruned, or distilled to fit those envelopes ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-warden2020tinyml|Warden and Situnayake 2020]]; [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-david2021tensorflow|David et al. 2021]]), and on microcontrollers (TinyML) it runs on specialized engines such as TensorFlow Lite Micro and CMSIS-NN ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-lai2018cmsis|Lai et al. 2018]]). Power budgets across edge devices span about four orders of magnitude, from milliwatts for sensors through watts for gateways to tens of watts in automotive systems. A deployment splits work across three tiers of its own, from the device up to the cloud: sensor-level microcontrollers at 1–100 mW filter and detect, gateways at 1–10 W run heavier inference, and the cloud distributes models and retrains. Latency-critical decisions stay local while expensive work moves upward.

Every operational control must fit inside the tier that runs it. An update shares flash with the running model, telemetry competes with the radio’s energy budget, and a failed release must recover without a technician. Safety-critical real-time targets also add worst-case execution time (WCET) analysis, which bounds the longest a single inference can take, to the release criteria, because thermal throttling and memory contention can push inference past a deadline that average latency never reveals.

↩︎ The quantization, pruning, and knowledge-distillation techniques that edge deployment relies on are established in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression#^sec-model-compression|Model Compression]]**.

![[90 Assets/Volume I/14 ML Ops/Vol1 ML Ops Margin 003 82505082dd.svg]]

*Vertical log-scale ladder of three orange bars, smallest at bottom: sensor at 1 mW, gateway at 1 W, automotive at tens of watts.*

*Power budgets across the three edge tiers span about four orders of magnitude.*

OTA model updates are how operations reaches physically inaccessible devices. OTA pipelines need secure model distribution, artifact verification, and rollback mechanisms; delta or differential updates can reduce transfer volume when devices need not receive a complete model artifact. The keyword spotter’s fail-safe OTA design uses dual-bank flash memory, a pattern common on microcontroller and embedded targets. The device keeps running from Bank A while it writes the candidate model and runtime to Bank B. After switching to Bank B, a hardware watchdog timer and a post-update self-test supervise the first inferences. If the new model triggers memory faults, hangs, or violates latency budgets, the bootloader automatically reverts execution to Bank A, preventing physically inaccessible devices from being bricked. Update scheduling must account for device connectivity patterns, power availability, and operational criticality.

Monitoring and tier coordination must fit inside the same power and bandwidth budgets. Because continuous streaming would drain the battery, lightweight telemetry reports compact operational counters (inference latency, power draw, and accuracy indicators) alongside device-level health signals (thermal status, battery levels, and connectivity quality) that predict maintenance needs before a node fails. When local load or link quality shifts, edge-cloud coordination can offload heavier inference to a gateway where feature caching avoids redundant computation. Federated learning lets edge devices contribute model updates rather than raw training records, and **[[01 Books/Volume I - Foundations/04 Deployment/15 Responsible Engineering/V1-15.06 Data Governance and Compliance#^sec-responsible-engineering-technical-privacy-protection-methods-4a74|Technical privacy protection methods]]** develops the privacy protections those updates still need.

Graceful degradation is a core operational pattern for edge AI. When thermal limits or battery depletion constrain hardware capacity, edge runtimes must dynamically shed load (downsampling input sample rates, skipping optional processing stages, or falling back to shallow heuristic models) within a fallback policy validated for the application’s safety and quality requirements. Each of these controls, on the device and in the cloud, reserves resources for a version that serves little or no traffic, and the size of that reservation depends on the workload’s regime.

### Memory and Compute of Release Controls

^sec-ml-operations-release-control-footprint-c3e8

Every control in this section keeps a second version of the model alive, and for a capacity-bound model that second version, not the extra arithmetic, is the dominant cost ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^tbl-ml-ops-release-control-footprint|table 11]]). A shadow deployment scores every request twice. A canary, an A/B test, and a blue-green switch divert traffic rather than adding work, yet each must hold the candidate’s full embedding tables in accelerator memory whatever share of traffic it serves, because any request in that share can look up any row of those tables. A hot standby for immediate rollback holds the previous version for the same reason. The ranking service’s 5 percent canary therefore doubles the accelerators that hold tables, from 2 to 4, while it carries a twentieth of the requests. A compute-bound ResNet-50 service pays the opposite way. Its 51.1 MB of FP16 weights fit beside the serving copy on one accelerator, so its canary costs almost no memory and only its share of compute. The keyword spotter’s dual-bank update costs flash instead of accelerator memory, a second 200 KB bank that brings the model’s share of the device’s 4 MB to 400 KB.

| **Release control**        | **Extra resident memory**                                   | **Extra inference work**                         | **What it buys**                                    |
|:---------------------------|:------------------------------------------------------------|:-------------------------------------------------|:----------------------------------------------------|
| **Shadow deployment**      | Second copy of the tables (100 GB); 2 $\rightarrow$ 4 H100s | Every request scored twice                       | Output and latency comparison with no user exposure |
| **Canary (5% of traffic)** | Second copy; 2 $\rightarrow$ 4 H100s                        | None; a share of requests is diverted            | Live quality evidence on a bounded share of users   |
| **A/B test**               | Second copy; 2 $\rightarrow$ 4 H100s                        | None; traffic is split between variants          | A statistically valid outcome comparison            |
| **Blue-green switch**      | Full second environment; 2 $\rightarrow$ 4 H100s            | Duplicate provisioned capacity during the switch | Rollback by a single routing change                 |
| **Hot standby**            | Previous version resident; 2 $\rightarrow$ 4 H100s          | None until rollback                              | Immediate rollback without a cold start             |
| **KWS dual-bank update**   | Second flash bank (200 KB in 4 MB of flash)                 | None                                             | Automatic revert after a failed update              |

Table 11: **Release Controls on a Capacity-Bound Model**: Extra resident memory and inference work that each release control adds to the DLRM ranking service on H100 accelerators, and to the keyword spotter’s flash. Every server-side control holds a second full copy of the embedding tables regardless of the traffic share it serves, so release safety for this model is paid in memory rather than arithmetic.

**Checkpoint 14.2: Evidence for a release**

**Promotion evidence**: A shadow model has acceptable latency and similar output distributions, but outcome labels have not arrived. What has been established, and what quality evidence is still missing?

**Recovery state**: A canary changes an embedding dimension. Which artifacts and cached state must a tested rollback restore together?

**Converted artifact**: Explain why passing aggregate accuracy before quantization does not replace numerical, slice-level, and runtime checks after conversion.

Getting a model into production, and back out again, is only half the operational challenge. A successfully released model can still degrade through distribution shift or corrupted upstream features without raising runtime errors, and none of the controls above will notice. Production monitoring supplies the evidence that tells the team a release, a rollback, or a retraining run is needed at all.
