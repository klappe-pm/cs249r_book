# V1-14.15 Footnotes

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14 ML Operations|V1-14 ML Operations]]

^footnotes

<sup>1</sup> **Telemetry**: The feedback path that can make model degradation visible before it becomes a business failure; crashes and error codes expose some software failures, but semantic errors can remain silent in any application. ML systems add distribution shift, which can go undetected without statistical telemetry such as feature distributions, prediction confidence, and drift indicators.

^fn1

<sup>2</sup> **Artifact**: Model weights are realized training outputs; the inputs and randomness that produced them cannot generally be inferred from the parameters. Versioning only code is therefore insufficient, and even versioning code, data, configuration, and environment may not guarantee exact replay when kernels or training are nondeterministic.

^fn2

<sup>3</sup> **Concept drift**: Concept-drift and data-stream research formalized the problem that a model’s target relationship can change after deployment ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-widmer1996|Widmer and Kubat 1996]]; [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-gama2014|Gama et al. 2014]]). In adversarial domains such as spam, fraud, and abuse detection, the distribution can actively adapt in response to the model, making continuous monitoring and retraining a structural requirement rather than an operational luxury.

^fn3

<sup>4</sup> **DVC (Data Version Control)**: DVC brings Git-like versioning to datasets and model artifacts ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-dvc|Iterative 2024]]), closing the artifact gap that [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^eq-model-reproducibility|equation 1]] formalizes. Without data versioning, the $\text{Data}_{v}$ term is unrecoverable, and no combination of code commits can reconstruct the model that was deployed.

^fn4

<sup>5</sup> **Technical debt**: Ward Cunningham’s 1992 WyCash experience report introduced the debt metaphor for expedient code and delayed consolidation ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-cunningham1992wycash|Cunningham 1992]]).

^fn5

<sup>6</sup> **Feature store**: Uber’s Michelangelo platform described a centralized feature store for sharing and serving features across production models ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-hermann2017michelangelo|Hermann and Del Balso 2017]]). At that scale, the consistency guarantee must hold under an online latency budget. A feature store differs from a shared library of feature code because its shared feature path must also serve fresh features fast enough for real-time inference.

^fn6

<sup>7</sup> **Model registry**: Prevents “registry bypass,” the failure mode where the undocumented production model diverges from the trained artifact through different preprocessing, stale serialization formats, or manual hotfixes applied directly to the serving endpoint. Without a registry enforcing versioned, immutable artifacts with queryable metadata and state, rollbacks require locating the correct weights from an ad hoc artifact store under incident pressure.

^fn7

<sup>8</sup> **MLflow**: An open-source MLOps framework that records hyperparameter runs, model binary hashes, and deployment stage transitions. The systems trade-off is centralizing lineage tracking vs. bottlenecking its metadata store during massive parallel hyperparameter sweeps.

^fn8

<sup>9</sup> **Ray**: A distributed computing framework ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-moritz2018ray|Moritz et al. 2018]]) with a unified task and actor interface. The broader MLOps lesson is that fragmented infrastructure creates translation points where preprocessing logic, normalization constants, tokenizer versions, or artifact formats can diverge silently. Shared execution abstractions can reduce that fragmentation, but training-serving skew still requires explicit consistency checks across data, features, and serving code.

^fn9

<sup>10</sup> **Idempotency**: This property ensures that retrying a pipeline stage does not create duplicate externally visible effects, conflicting registrations, or repeated deployment actions. Producing identical models from identical inputs is a separate property (determinism and reproducibility), and the `training` stage may violate it due to randomness such as weight initialization. Production systems therefore combine stable run identifiers and atomic publication for idempotency with fixed random seeds, deterministic kernels, fixed library versions, and controlled data ordering for reproducibility.

^fn10

<sup>11</sup> **ML autoscaling**: Autoscaling adjusts capacity based on demand signals ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-aws-autoscaling-eacffe63|Amazon Web Services 2024]]), but ML serving adds constraints absent from stateless web services. Autoscaling decisions must account for model loading time (cold-start overhead), GPU memory fragmentation, and batching behavior in addition to CPU utilization. Scaling up too slowly violates latency SLOs; scaling down too aggressively forces repeated cold starts that degrade p99 latency.

^fn11

<sup>12</sup> **Containerization for ML deployment**: Docker ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-docker|Merkel 2014]]) packages code with dependencies into portable units; Kubernetes ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-burns2016|Burns et al. 2016]]) orchestrates those units across clusters. Containerization addresses the $\text{Environment}_{v}$ term in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^eq-model-reproducibility|equation 1]] partially by capturing user-space dependencies as a versioned artifact; host kernels, drivers, and hardware remain external dependencies.

^fn12

<sup>13</sup> **Staging validation**: ML staging adds statistical quality checks to conventional functional and operational validation. A model can pass unit tests and still fail in production because the test data does not reflect the deployment distribution, so rollout checks must compare prediction statistics, evaluation slices, and business guardrails against calibrated thresholds rather than rely on unit tests alone.

^fn13

<sup>14</sup> **Shadow deployment**: Economically justified when its expected reduction in rollout loss exceeds the cost of shadow infrastructure for duplicated inference without serving results.

^fn14

<sup>15</sup> **Canary deployment**: The ML-specific challenge is that a “failure” is statistical degradation, not a deterministic crash: detecting a small accuracy difference with high confidence can require thousands of inferences, creating a tension between decision speed and statistical power that determines minimum canary duration.

^fn15

<sup>16</sup> **Blue-green deployment**: Maintains two comparable production environments, “blue” (serving current traffic) and “green” (running the candidate), then switches traffic in a routing change once the green environment passes validation. Because rollback is a traffic flip rather than a staged drain, recovery can be faster than a gradual canary for stateless services. The trade-off is extra infrastructure during the switch, so blue-green wins over canary when brief duplicate capacity is acceptable and per-segment statistical validation is expensive.

^fn16

<sup>17</sup> **Rollback (from database transaction management)**: This “undo” action for deployments is complicated in ML by model-dependent state (for example, cached embeddings), which may be incompatible between model versions. This mismatch can prolong recovery and contribute to deployment aversion and slower iteration.

^fn17

<sup>18</sup> **Prometheus**: Prometheus periodically scrapes targets and stores time series for aggregation. Scrape and rule-evaluation intervals jointly affect alert latency and may miss short excursions. Monitoring per-accelerator thermals allows precise workload routing at higher data cost, while server-level aggregates can mask component-level throttling.

^fn18

<sup>19</sup> **Label-free vs. label-dependent detection**: A change in ${p(x)}$, or in the model’s prediction distribution, can be estimated from sufficient samples without labels, although detection is not immediate. Concept drift generally requires labeled outcomes, which in high-stakes domains (medical diagnosis, fraud detection, legal decisions) can take days, weeks, or months. Proxy metrics such as prediction-confidence distributions and output entropy can provide imperfect early warnings that trade false-alarm rate for detection speed.

^fn19

<sup>20</sup> **Covariate shift**: Reweighting training examples to correct for covariate shift assumes that every deployment input could have appeared in training, just with different probability. When deployment contains genuinely out-of-distribution inputs (new product categories, new demographics, adversarial inputs), the correction can fail and the model can produce confidently wrong outputs with no warning signal. That coverage is the hidden assumption that determines whether drift correction or full retraining may be required.

^fn20

<sup>21</sup> **Schema validation**: The rules in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.06 Production Monitoring#^lst-ops-schema-validation|listing 3]] prevent silent data contract violations, such as a feature column changing from an integer to a float. Without this input-level guardrail, downstream model monitoring cannot distinguish a data quality error from a true performance regression, masking the root cause. A schema mismatch in a critical feature can invalidate an otherwise well-formed prediction batch.

^fn21

<sup>22</sup> **PSI**: PSI is widely used in credit-risk scorecard monitoring to compare expected and observed binned populations; Yurdakul and Naranjo analyze its statistical properties ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-yurdakul2020|Yurdakul and Naranjo 2020]]). The common 0.1 and 0.25 bands are useful operational conventions, not universal statistical laws. ML operations adopted PSI because it works on binned categorical or continuous features and provides an interpretable drift score that non-specialists can review.

^fn22

<sup>23</sup> **System entropy**: A name for the silent degradation of **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.07 When ML Systems Fail Silently#^sec-introduction-ml-vs-traditional-software-e19a|When ML Systems Fail Silently]]**, in which quality decays while code and weights stay unchanged. The fitted decay rate ${\gamma}$ measures how fast it proceeds. That rate can differ substantially across deployments and must be estimated from outcome data. A shorter decay timescale demands more responsive monitoring, but it does not by itself require continuous training; label delay, validation risk, retraining cost, and rollback capacity determine the operational cadence.

^fn23

<sup>24</sup> **Half-life** (from nuclear physics, where it measures the time for half of a radioactive sample to decay): In ML operations, the metaphor is a convenient approximation, not a universal law. For the exponential fit in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.07 Retraining Decisions#^eq-accuracy-decay|equation 8]], derived below, the half-life is $\ln(2)/{\gamma}$. Retraining cadence also depends on traffic, value, retraining cost, and risk; seasonal, abrupt, or adversarial change requires a richer drift process.

^fn24

<sup>25</sup> **Bulkhead pattern**: This pattern partitions system resources to contain failures within isolated zones. In ML serving, a bulkhead allocates fixed accelerator memory, host RAM, and worker thread pools to experimental model versions, so a canary’s resource exhaustion is less likely to terminate the primary serving path; the protection depends on the process and hardware isolation actually enforced.

^fn25

<sup>26</sup> **Photoplethysmography (PPG)**: Optical technique that infers blood-volume changes from variations in detected light after illuminating tissue. For ML operations, PPG introduces a data quality challenge absent in controlled environments. Motion artifacts from wrist movement corrupt the signal, creating a data drift pattern where the same physiological state produces different input distributions depending on user activity. Models must either filter corrupted windows before inference or learn to be robust to motion noise, and monitoring must distinguish genuine physiological changes from artifact-induced distribution shift.

^fn26

<sup>27</sup> **Polysomnography (PSG)**: A multi-parameter sleep study that provides the clinical ground truth data for this classification task. This “truth” is inherently noisy; expert human scorers interpreting the same PSG recordings agree with each other at about 82 percent–83 percent reliability ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-altini2021promise|Altini and Kinnunen 2021]]). Inter-scorer agreement indicates label uncertainty but does not impose an accuracy ceiling against a fixed or adjudicated reference.

^fn27

<sup>28</sup> **Continuous therapeutic monitoring (CTM)**: Healthcare approach using wearable sensors for real-time physiological data collection and personalized treatment adjustments. CTM forces MLOps to confront constraints absent in typical deployments: feedback loops require oversight appropriate to the intended use, training labels need clinical validation, and model changes must follow applicable authorization and change-control requirements. These constraints reshape every MLOps principle, making CTM a stress test for operational maturity.

^fn28
