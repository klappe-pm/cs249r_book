# V1-14.11 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14 ML Operations|V1-14 ML Operations]]

^sec-ml-operations-fallacies-pitfalls-e4e0

Operating production machine learning systems under conventional software assumptions creates distinct failure modes, each a place where a standard software engineering intuition breaks down against the statistical behavior of deployed models.

**Fallacy**: *MLOps is just applying traditional DevOps practices to machine learning models.*

Engineers often assume that standard CI/CD pipelines transfer directly to machine learning. Traditional DevOps automates code builds, testing, and artifact deployment with controls for dependencies and execution environments. In an ML system, code represents only one axis of the D·A·M triad. Model execution depends jointly on code, large evolving datasets, and accelerator compute budgets. As detailed in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-cicd-pipelines-a9de|section 14.3.2.1]], ML pipelines introduce stateful retraining, multi-metric validation checks, and immutable artifact registration. Standard CI/CD engines cannot natively track data lineage, orchestrate feature stores, or detect distribution drift. When teams apply DevOps without ML-specific adaptations, they maximize the computational availability of their serving cluster while leaving statistical behavior unmonitored. The system achieves high uptime and low latency, yet silently serves degraded predictions due to unvalidated data shifts and training-serving skew. The cost is concrete. A 1 percent skew rate on 1,000,000 queries/day costs \$365,000 a year ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^eq-skew-cost|equation 2]]) while every DevOps health check stays green.

**Pitfall**: *Treating model deployment as a one-time event rather than an ongoing process.*

Treating deployment as a terminal milestone assumes that deployed weights remain permanently aligned with the production input distribution. Unlike compiled binaries whose execution semantics remain fixed, model quality can change as real-world distributions shift. Monitoring statistical indicators such as PSI ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.06 Production Monitoring#^sec-ml-operations-data-quality-monitoring-c6b6|section 14.5.2.1]]) provides an early signal of feature drift, distinguishing benign variance from actionable distribution change. Crossing a warning threshold requires operational diagnosis rather than unvalidated retraining. As established in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.07 Retraining Decisions#^sec-ml-operations-quantitative-retraining-economics-1579|section 14.6.2]], scheduling updates is an economic balancing problem. The optimal retraining interval ${T}^* \approx \sqrt{\frac{2{C}}{{Q_{\text{day}}}\cdot {V}\cdot {\text{Accuracy}_0} \cdot {\gamma}}}$ weighs the fixed compute and engineering cost ${C}$ against the business losses accumulated from daily query volume ${Q_{\text{day}}}$, unit accuracy value ${V}$, and staleness decay rate ${\gamma}$. For the ranking service, a 0.24 percent daily decay on 1,000,000 requests a day puts that optimum near 3 days (notebook [14.6](https://mlsysbook.ai/vol1/14_ml_ops/14_ml_ops.html#nbk-ml-ops-half-life-model)), a cadence no one-time deployment can meet. Operating a production model demands treating deployment as a continuous control loop that balances monitoring signals against retraining economics.

**Fallacy**: *Automated retraining ensures optimal model performance without human oversight.*

Automating pipeline execution does not eliminate the need for operational governance. Closed-loop retraining pipelines operate without semantic awareness; if upstream data ingestion suffers schema anomalies, corrupted labels, or sudden sensor drift, automated retraining bakes those errors directly into updated model weights. Furthermore, automated validation checks typically evaluate aggregate loss across a held-out test split, which easily conceals severe performance regressions on critical slices or low-frequency edge cases. For instance, retraining a ranking model on weekend traffic can degrade performance on weekday traffic, where user query distributions diverge. An aggregate check would pass it, just as the 91 percent overall accuracy in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.08 Incident Response and Governance#^tbl-slice-analysis-example|table 20]] conceals a tablet slice at 62 percent. Resilient MLOps architectures decouple automated pipeline execution from automated production promotion, enforcing canary deployments, slice-level regression tests, and human sign-off when validation metrics deviate from expected historical envelopes.

**Pitfall**: *Focusing on technical infrastructure while neglecting organizational and process alignment.*

Investing in MLOps tooling without defining organizational interfaces leads to fragmented operational ownership. Machine learning systems bridge two distinct engineering cultures: model developers optimizing offline accuracy metrics and platform engineers managing host-level latency, memory capacity, and throughput budgets. When organizations treat deployment as a handoff between isolated teams, root-cause triage stalls during production incidents. Infrastructure engineers inspect container health and GPU utilization without insight into model prediction distributions, while model authors inspect offline training curves without understanding runtime serving constraints. The ML Test Score ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.09 Operational Maturity#^sec-ml-operations-assessing-technical-debt-ml-test-score-0099|section 14.8.1]]) makes the gap measurable, because a deployment with a perfect model suite and no production monitoring scores 0 under its minimum-category rule. Tools such as feature stores and registries provide technical scaffolding, but reliability requires institutional alignment: unified SLOs spanning statistical accuracy and serving latency, joint on-call runbooks, and shared accountability for production regressions.

**Fallacy**: *Training and serving environments automatically remain consistent once pipelines are established.*

Establishing an initial end-to-end pipeline does not guarantee permanent parity between training and serving. Training-serving skew arises from fundamental architectural divergences between offline and online execution paths. Training typically runs as an offline batch workflow (such as distributed SQL queries or Spark pipelines) optimized for high-throughput scans over historical logs, whereas online serving runs in low-latency microservices under millisecond latency constraints. Maintaining dual implementations of feature transformations across these environments risks numerical disparities, differing missing-value semantics, or lookahead bias in historical joins. On the ranking service, the two paths computed `user_session_length` with means of 45 and 12 minutes and cost 8 percent of accuracy with no change to model code ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-trainingserving-skew-case-study-4d24|section 14.3.1.1.2]]). As demonstrated in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-feature-stores-c01c|section 14.3.1.1]], feature stores alleviate this divergence by unifying transformation logic and synchronizing batch and point-lookup stores. However, software pipelines alone cannot guarantee consistency. Operational verification requires request-keyed value comparisons and schema assertions between offline replays and online inference inputs, alongside separate distribution monitoring to catch divergence before it degrades downstream decisions.

**Pitfall**: *Assuming comprehensive monitoring prevents all production incidents.*

Dashboards and alert thresholds cannot prevent production outages caused by silent data failures. Monitoring supplies evidence; reducing harm also requires a response. Input-boundary checks can catch some defects before inference, while statistical quality estimates may arrive after affected predictions have been served. Furthermore, tracking output metrics alone leaves critical blind spots along the data pipeline. As shown in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.06 Production Monitoring#^sec-ml-operations-data-quality-monitoring-c6b6|section 14.5.2.1]], measuring service latency and prediction distributions fails to detect input anomalies such as feature staleness. An inference service can maintain nominal p99 response times and normal prediction ranges while consuming stale user embeddings caused by upstream database replication lag or cache eviction failures. By the time downstream business metrics degrade, corrupted predictions have already impacted users; an input-boundary check acts on the first malformed request, without waiting for labeled outcomes to accumulate. Production reliability requires defensive boundary controls alongside passive observability: strict input schema enforcement, feature freshness assertions, and circuit breakers that fall back to deterministic heuristics when input quality slips below operational tolerances.

**Fallacy**: *Accuracy is the first production signal to monitor, so leading indicators can wait on a dashboard.*

Teams often configure accuracy dashboards as their primary operational tripwire, assuming degradation will register there first. When outcome labels arrive late, ground-truth accuracy is a lagging indicator. In production environments such as fraud detection, ad conversion, or credit underwriting, ground-truth labels arrive with substantial latency, often requiring weeks or months to accumulate through chargebacks or repayment histories. Relying solely on accuracy dashboards leaves the system operating blind throughout this label-delay window. Furthermore, aggregate accuracy can remain deceptively stable even as input distributions diverge across critical sub-populations. As detailed in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.06 Production Monitoring#^sec-ml-operations-data-quality-monitoring-c6b6|section 14.5.2.1]], monitoring input feature distributions with metrics like PSI or Kullback-Leibler (KL) divergence supplies indicators that can be estimated from sufficient input samples without labels. These statistical signals detect distribution shifts without waiting for labels, often enabling investigation before delayed outcome metrics are available, without guaranteeing that prediction errors have not already occurred.

Waiting for labels is slow, and the delay has a price. The same evidence budget that one labeled outcome per second fills in about 16.7 minutes takes 10 days at 100 outcomes a day. In the silent-failure scenario, each incident detected at monthly rather than daily review costs \$184,932 more (notebook [14.3](https://mlsysbook.ai/vol1/14_ml_ops/14_ml_ops.html#nbk-ml-ops-cost-silent-failures)). A leading indicator recovers that time only when it is routed to an owner with a response deadline, an escalation rule, and a diagnostic runbook; drift and freshness warnings parked on an informational dashboard accumulate unnoticed until an emergency forces a response.

Observability in production machine learning extends far beyond passive dashboard telemetry. It requires closed operational loops across the entire D·A·M architecture: enforcing input data integrity and feature stability, bounding model behavior through automated validation checks, and routing leading indicators directly to engineers empowered with diagnostic runbooks to investigate changes and limit harm.
