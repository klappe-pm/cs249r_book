# V1-14.04 Development Infrastructure

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14 ML Operations|V1-14 ML Operations]]

^sec-ml-operations-development-infrastructure-automation-de41

When a production model fails an accuracy check, an engineer who cannot recover the exact training dataset, feature transformation code, and container image that produced it can only guess which input changed. Development infrastructure turns the debt patterns diagnosed in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.03 Technical Debt#^sec-ml-operations-technical-debt-system-complexity-2762|section 14.2]] into concrete enforcement points. A feature schema that drifts upstream cannot be repaired by a dashboard alone; it needs a shared contract, a versioned artifact, and a deployment path that rejects incompatible changes before they reach production. [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^tbl-mlops-infrastructure-debt|Table 7]] maps each component directly to a foundational principle ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^sec-ml-operations-mlops-3ea3|section 14.1.1]]) and a specific failure mode. CI/CD pipelines also carry versioned artifacts, but the table assigns them cost-aware automation because the pipeline is where the retraining and promotion criteria of [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^eq-retrain-decision|equation 3]] are actually checked, automating only the changes that meet them.

| **Infrastructure Component** | **Principle Implemented** | **Debt Pattern Addressed**                  |
|:-----------------------------|:--------------------------|:--------------------------------------------|
| **Feature stores**           | Consistency               | Data dependency debt, training-serving skew |
| **Versioning systems**       | Reproducibility           | Configuration debt, correction cascades     |
| **CI/CD pipelines**          | Cost-aware automation     | Pipeline debt, boundary erosion             |
| **Monitoring systems**       | Observable degradation    | Feedback loops, silent failures             |

Table 7: **MLOps Infrastructure as Debt Remediation**: Each infrastructure component responds to a class of technical debt observed in production ML systems. Feature stores can reduce training-serving skew by reusing feature definitions and values; versioning systems support reproducibility; CI/CD pipelines automate rollout controls; monitoring systems can surface silent degradation before users do.

^tbl-mlops-infrastructure-debt

These operational components sit between the framework and the hardware and track what neither of them tracks, the data lineage and the cluster state. MLOps occupies the middle tiers of the implementation stack in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^fig-ops-layers|figure 5]], between the models and frameworks on one side and the hardware on the other. Model orchestration, which runs from data management to serving, and operational infrastructure, which runs from job scheduling to monitoring, together bridge mathematical frameworks and physical accelerator clusters and enforce the remediations of [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^tbl-mlops-infrastructure-debt|table 7]]. The tiers say *where* a component sits in the implementation stack, while the four layers of [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^tbl-mlops-layers|table 3]] say *who* owns an operational responsibility; the rest of the chapter reasons with the layers and the three interfaces.

Inside the orchestration and infrastructure tiers, four architectural mechanisms execute these operational responsibilities. At the data boundary, a feature storage and retrieval layer serves a unified schema across two disparate access patterns. Offline training uses high-throughput analytical scans over immutable columnar files, and online serving uses low-latency point lookups against key-value stores ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-feature-stores-c01c|section 14.3.1.1]]). To keep every transformation and checkpoint traceable, an artifact and lineage store records content-addressed hashes for dataset snapshots, code commits, container images, and model weights. Any live prediction can then be audited back to its exact training inputs ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-versioning-lineage-b1cf|section 14.3.1.2]]). Workflow orchestration then sequences the pipeline stages, from ingestion and validation through training and evaluation, as declared dependency graphs with retry semantics and automated triggers ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-cicd-pipelines-a9de|section 14.3.2.1]]). A compute runtime underneath schedules accelerator hardware, host memory, and processor cores across training jobs and serving endpoints under strict resource isolation ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-training-pipelines-2dcf|section 14.3.2.2]]). Specific frameworks implement pieces of this decomposition, but the underlying mechanisms and interface boundaries outlast any particular tool.

### Data Infrastructure and Preparation

^sec-ml-operations-data-infrastructure-preparation-284a

Because unversioned datasets erode system boundaries, inconsistent feature computation triggers correction cascades, and undocumented data dependencies create hidden downstream consumers, paying down machine learning technical debt begins at the data boundary. If an offline training pipeline reads a backfilled warehouse table while the online serving path reads a live event stream with different null defaults, the deployed model evaluates inputs it never learned to score. Data engineering built the collection, preprocessing, and feature-transformation pipelines, together with the validation and dataset versioning that make one pipeline correct and reproducible. Operations turns those pipelines into versioned interfaces that it enforces across every pipeline touching a model. Where data engineering optimizes single-pipeline correctness and ingestion throughput, MLOps data management governs cross-pipeline consistency, ensuring that offline training and online serving compute identical features.

↩︎ The collection, preprocessing, and feature-transformation pipelines that MLOps formalizes are established in **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering#^sec-data-engineering|Data Engineering]]**.

Operations holds those interfaces to three properties: consistency, freshness, and quality. Consistency requires every artifact that influences model behavior, from raw records to engineered feature tables, to remain addressable by version, so that a checkpoint can be traced to the dataset snapshot that produced it ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-versioning-lineage-b1cf|section 14.3.1.2]]). It also requires training and serving to share one feature definition ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^sec-ml-operations-feature-stores-c01c|section 14.3.1.1]]). Content-addressed dataset versioning tools such as DVC ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-dvc|Iterative 2024]]) supply the first half of this requirement. Because consistent definitions still degrade if inputs arrive late, freshness requires scheduled pipelines, declared in workflow orchestrators such as Apache Airflow ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-apache-airflow-e1a7c02d|Apache Software Foundation 2024]]), to deliver current data on a known cadence. A late run then becomes a visible failure rather than a stale feature. Even timely, versioned pipelines can ingest corrupted values, so quality requires the validation checks of **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^sec-data-engineering-quality-validation-monitoring-498f|Quality through validation and monitoring]]** to run as automatic checks that reject a corrupted batch before it reaches training or serving. Annotation platforms such as Label Studio ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-label-studio-56e65787|HumanSignal 2024]]) keep label corrections under version history.

On the ranking service, the three properties operate in concert. Click and session events are ingested and joined with the item catalog through a scheduled pipeline (freshness). The resulting features, such as session length and rolling click rates, are stored in a feature store for both offline retraining and low-latency online lookup (consistency). Schema validation, range checks, missingness tests, and label audits reject corrupted event records before they enter the training set (quality), while dataset versioning and model-registry integration maintain traceability from raw event logs to deployed predictions.

#### Feature Stores

^sec-ml-operations-feature-stores-c01c

Keeping those ranking features consistent across offline training and online serving fails whenever the two paths maintain separate feature code, the root cause of the data-dependency debt in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.03 Technical Debt#^sec-ml-operations-technical-debt-system-complexity-2762|section 14.2]]. Without a unified feature layer, feature definitions are typically implemented twice. On the ranking service, a data scientist writes `user_session_length` in Python over historical batch logs, while a systems engineer reimplements the calculation in Java or C++ to meet millisecond serving latencies. Any discrepancy in how the two implementations bound a session or handle missing events trains the model on one feature and serves it with another, degrading accuracy silently in production. Feature stores[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn6|⁶]] address this divergence by providing an abstraction layer between data engineering and machine learning, implementing the consistency imperative through a single source of truth for feature transformations. In pipelines lacking this abstraction, duplicated feature logic across environments introduces training-serving skew, temporal data leakage, and distribution drift.

↩︎ Training-serving skew, a violation of the consistency imperative, is established in **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-ensuring-trainingserving-consistency-c683|Training-serving consistency]]**.

Feature stores resolve the tension between batch throughput and online latency by keeping two synchronized storage tiers behind one API, an offline store for high-throughput training scans and an online store for point lookups under a tail-latency service-level objective (SLO). Their as-of join also gives each training example only the feature values that existed at its observation time (**[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.08 Data Processing#^sec-data-engineering-feature-stores-bridging-training-serving-55c8|Feature stores]]**). Operations depends on that guarantee because a ranking model trained on leaked features looks excellent offline and fails on live traffic.

Beyond consistency, feature stores support versioning, metadata management, and feature reuse across models. A ranking model and a fraud model built on the same user activity frequently depend on overlapping features that can be centrally maintained, validated, and shared. Integration with data pipelines and model registries preserves lineage. When an upstream feature definition is updated or deprecated, downstream models can be automatically identified and scheduled for retraining.

##### Training-Serving Skew: Diagnosis and Prevention

^sec-ml-operations-trainingserving-skew-diagnosis-prevention-9dc1

Training-serving skew manifests operationally through feature store inconsistencies and pipeline divergence. [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^tbl-training-serving-skew|Table 8]] summarizes common causes and their detection methods:

| **Skew Type**               | **Example**                                   | **Detection Method**                          |
|:----------------------------|:----------------------------------------------|:----------------------------------------------|
| **Feature preprocessing**   | Normalization uses different statistics       | Same-input replay and value comparison        |
| **Missing data handling**   | Training fills NaN with mean; serving uses 0  | Schema validation with explicit null handling |
| **Time-dependent features** | Features computed with different time cutoffs | Timestamp validation in feature pipelines     |
| **Library version drift**   | NumPy or Pandas version differences           | Environment hash comparison                   |

Table 8: **Training-Serving Skew Categories**: Each category requires different detection and prevention strategies. Preprocessing and missing-data skew emerge from divergent transformation code and require parity validation, which shared feature logic, including a feature store where appropriate, can reduce. Time-dependent features need timestamp checks that both paths apply the same cutoff, and library version drift needs environment comparison because identical code can compute different values under different library versions.

^tbl-training-serving-skew

##### Training-Serving Skew Case Study

^sec-ml-operations-trainingserving-skew-case-study-4d24

Two implementations of `user_session_length` are enough to break a model that no one has touched. After a later release of the ranking service’s serving path, the model loses 8 percent of its accuracy despite zero alterations to model code or weights. Comparing feature distributions reveals that `user_session_length` has an empirical mean of 45 minutes in the training set but only 12 minutes in online inference. That difference starts the investigation; different user populations could produce it even with identical feature logic. Replaying the same recorded sessions through the versioned training and serving transformations, with the same available events and cutoff, reveals different durations for the same requests. Inspection of those artifacts then identifies feature-definition skew. The offline training pipeline calculated wall-clock duration from the initial event to the final event in a session, whereas the online serving path counted only foreground-active time after filtering idle periods. The model learned decision boundaries against a feature distribution that the serving infrastructure never delivers.

Feature stores resolve this discrepancy by centralizing feature logic into a single versioned definition, extending upstream data pipelines. In [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^lst-feature-store-consistency|listing 1]], training materializes historical features with point-in-time correctness, serving performs real-time point lookups, and both pipelines reference the identical versioned definition hash rather than independent code paths.

``` python
feature_definitions = registry.load(version="2026-06-01")

training_features = feature_definitions.materialize_historical(
    entities=training_entities,
    at_event_time=True,
    names=["user.session_length", "user.purchase_history"],
)

serving_features = feature_definitions.lookup_online(
    entities=[{"user_id": 12345}],
    names=["user.session_length", "user.purchase_history"],
)

assert training_features.schema == serving_features.schema
assert (
    training_features.definition_hash
    == serving_features.definition_hash
)
```

Listing 1: **Feature Store Consistency**: Unified retrieval reduces training-serving skew by sharing versioned feature definitions across both pipelines.

^lst-feature-store-consistency

By centralizing the definition of `session_length`, both offline and online pipelines execute identical transformation logic, though automated integration tests must still verify value parity. Centralized registries also record metadata and lineage, enabling rapid diagnosis when feature definitions evolve ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-hermann2017michelangelo|Hermann and Del Balso 2017]]; [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-feast2019|Gojek and Google 2019]]).

The consistency imperative ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^sec-ml-operations-principle-3-consistency-imperative-a292|section 14.1.1.3]]) priced this failure per query, and the `user_session_length` divergence above shows how a single feature computed two ways produces such errors, at a cost of 8 percent of the model’s accuracy. Centralized feature stores amortize the engineering cost of this infrastructure across multiple models and services, translating architectural consistency into measurable operational savings.

##### Skew Detection in CI/CD

^sec-ml-operations-skew-detection-cicd-e361

Continuous integration pipelines must validate feature consistency before deployment. A parity test replays recorded inputs through the versioned training and serving transformations, aligns results by request identifier, and compares each feature using its declared semantics and numerical tolerance. Both paths must receive the exact event snapshot available at the prediction cutoff. Otherwise an offline path reading a backfilled warehouse table will include events that arrived after the request, confounding code differences with differences in available information. For a duration feature, the contract specifies the time unit and whether idle periods count. Categorical values and missingness must agree exactly, whereas floating-point values may use a feature-specific tolerance.

A small counterexample shows why distributions cannot replace this check. Suppose the training transformation returns session durations of 12 and 45 minutes for requests A and B, respectively, while serving returns 45 and 12 minutes for those same requests. The marginal distributions, the feature’s values taken on their own without regard to which request produced each one, are identical, so a Kolmogorov-Smirnov (KS) comparison, which sees only the two sets of values, finds no difference, but request-keyed comparison detects both mismatches. Conversely, a new population of shorter sessions can shift the marginal distribution while both paths still agree for every replayed request. Point-in-time correctness remains a separate requirement, because two replay paths fed the same unwindowed log will agree with each other while both leak future events that did not exist at prediction time.

[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^lst-ops-validate-skew|Listing 2]] supplies a complementary distribution screen using the two-sample KS test that the data pipeline already uses to watch for drift (**[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.06 Ingestion and Validation#^sec-data-engineering-quality-validation-monitoring-498f|Quality through validation and monitoring]]**). The KS statistic is the largest vertical gap between the empirical cumulative distribution functions (eCDFs) of the training and serving samples. Setting the threshold to $0.1$ asserts that cumulative probabilities do not diverge by more than 10 percentage points at any value across the feature’s support. In this illustrative release policy, exceeding the threshold pauses promotion for review rather than diagnosing skew. The threshold must be calibrated against sample size and feature sensitivity. Passing the screen establishes only limited marginal divergence at that threshold; it does not establish per-request parity.

``` python
def screen_feature_distributions(
    training_features, serving_features, threshold=0.1
):
    """Pause promotion for review if distributions diverge."""
    for feature in training_features.columns:
        ks_stat = ks_2samp(
            training_features[feature], serving_features[feature]
        )
        if ks_stat.statistic > threshold:
            raise DistributionReviewRequired(
                f"{feature}: KS={ks_stat.statistic:.3f}"
            )
```

Listing 2: **Feature Distribution Screen**: This function compares training and serving feature distributions using the Kolmogorov-Smirnov test, pausing promotion for review under an illustrative threshold policy.

^lst-ops-validate-skew

#### Versioning and Lineage

^sec-ml-operations-versioning-lineage-b1cf

Replaying recorded requests to isolate skew or pausing promotion on a distribution screen works only when the team can recover the exact feature definitions, dataset snapshot, and model checkpoint that ran. Lineage tracking and versioning provide that record, implementing the reproducibility principle formalized in [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.02 Silent Failure in Production#^sec-ml-operations-mlops-3ea3|section 14.1.1]]. Software artifact provenance already depends on source code, build tools, dependencies, and configuration. In machine learning systems, model behavior is the joint product of code, hyperparameter configuration, and the training dataset snapshot. Changing any single dependency produces an entirely distinct model artifact. Each artifact gets a content hash, so any model can be traced to its inputs.

↩︎ Content-addressed dataset versioning, which records each dataset release by its hash, is established in **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.09 Dataset Release#^sec-data-engineering-data-versioning-ml-reproducibility-16d0|Data versioning for ML reproducibility]]**.

Data versioning addresses dataset mutability by retaining raw data snapshots and intermediate feature tables under content-addressable hashes, so the recorded inputs to historical runs remain retrievable. Hashes identify artifacts but cannot reconstruct missing content or remove execution nondeterminism. Model versioning registers trained weights as immutable artifacts alongside training hyperparameters, evaluation metrics, and environment dependency manifests. A **model registry**[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn7|⁷]] is the store that holds these immutable artifacts under lifecycle states (such as staging, production, or retired) and exposes lineage graphs tracing the complete dependency chain from raw ingested records to deployed prediction endpoints ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-mlflowModelRegistryDocs|MLflow Project 2026]]; [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-vertex-ai-model-registry-52be556d|Google Cloud 2024]]).

The registry is also what lets the release machinery promote, hold, or roll back the exact artifact that was evaluated. It stores immutable version tags, links evaluation metrics to artifact hashes, and governs which checkpoint each serving tier runs ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-vertex-ai-model-registry-52be556d|Google Cloud 2024]]). This distinguishes a registry from an exploratory model catalog, which indexes candidate architectures for experimentation; a model enters the registry only when it becomes a versioned candidate for deployment. Experiment tracking frameworks such as MLflow[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn8|⁸]] ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-mlflow-website-13eae327|Databricks 2024]]) and unified distributed runtimes such as Ray[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn9|⁹]] record the surrounding execution state, training parameters, and lineage. Together, registry governance and lineage tracking turn experimental validation into controlled release, so a tested candidate can be promoted to production, monitored under live traffic, and reversed without losing provenance.

These mechanisms construct the lineage graph of the machine learning system. This graph establishes the audit trail required to diagnose production failures: determining whether an incoming request distribution diverged from training baselines, whether upstream feature calculations changed, or whether the serving environment loaded an unvalidated weight checkpoint. By recording provenance as a required, queryable artifact, systems engineering gives incident triage a verifiable record against which to test root-cause hypotheses.

### Continuous Pipelines and Automation

^sec-ml-operations-continuous-pipelines-automation-27a4

Feature stores and versioning systems lock down data and artifact consistency at a single point in time. Production models, however, must repeat preprocessing, training, evaluation, and release without an engineer running scripts by hand and risking a skipped validation check or a mismatched dataset path. Continuous automation joins those static controls into integrated workflows that respond to new data, shifting objectives, and operational constraints ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-orr2021|Orr et al. 2021]]; [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-googleCloudMlopsPipelines|Google Cloud 2026]]).

#### CI/CD Pipelines

^sec-ml-operations-cicd-pipelines-a9de

CI/CD pipelines carry that consistency from the *data* side to the *process* side, ensuring that changes flow through validated stages rather than ad hoc deployments. ML CI/CD pipelines must handle complexity absent from traditional software: data dependencies, model training workflows, and artifact versioning that couple code changes to statistical behavior changes.

A typical ML CI/CD pipeline consists of coordinated stages: checking out updated code, preprocessing input data, training a candidate model, validating performance, packaging the model, and deploying to a serving environment. In some cases, pipelines also include triggers for automatic retraining based on data drift or performance degradation. By codifying these steps, CI/CD pipelines[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.15 Footnotes#^fn10|¹⁰]] reduce manual intervention, enforce quality checks, and support continuous improvement of deployed systems.

ML CI/CD adds a second tier of tooling because a general-purpose orchestrator handles code but not data or models. A general-purpose CI/CD orchestrator (GitHub Actions ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-github-actions-11e45e24|GitHub, Inc. 2024b]]), for example) manages version-control events and execution logic, but the ML layer must additionally version data, block promotion on model metrics, and trigger retraining. Teams therefore add an ML platform or workflow orchestrator (Kubeflow ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-kubeflow|Authors 2024]]), for example) that supplies higher-level abstractions for those tasks.

Without this automation, model deployment degrades into a manual, error-prone process in which an engineer retrains locally, copies artifacts to a staging server, and promotes to production with no guarantee that the data, code, or hyperparameters match what was validated. The cost of such ad hoc workflows compounds with team size and deployment frequency, producing configuration drift and silent regressions that surface only after the model has served incorrect predictions.

A continuous training pipeline runs seven sequential stages, from dataset ingestion, data validation, and data transformation through training, evaluation, validation, and registry promotion ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.04 Development Infrastructure#^fig-ops-cicd|figure 6]]). Driven by dedicated processing, training, and evaluation engines beneath the pipeline, the workflow coordinates with surrounding dataset, model, and metadata repositories whenever an external trigger initiates retraining.

![[90 Assets/Volume I/14 ML Ops/Generated Figure 4a0181a9b7.svg]]

Figure 6: **ML CI/CD Pipeline**: Read the enclosed stages in execution order; the retraining trigger starts a new run, while connected repositories preserve the dataset, model, metadata, and artifacts needed to reproduce and govern it. Adapted from Google Cloud’s MLOps continuous delivery and automation pipeline guidance ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-googleCloudMlopsPipelines|Google Cloud 2026]]).

^fig-ops-cicd

Consider the ranking model under active development. When a developer commits code changes, the CI pipeline pulls the specified dataset version, performs feature preprocessing, and initiates model training. Experiments are tracked with an experiment tracker such as MLflow ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-mlflow-website-13eae327|Databricks 2024]]), which logs loss curves and also registers model artifacts. After passing automated offline validation, the model is containerized and deployed to a staging cluster. If the candidate satisfies staging validation, the pipeline executes a canary rollout ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-model-deployment-b9b9|section 14.4.3]]), gradually shifting production query traffic to the new model while monitoring inference latency and error rates. If a performance regression emerges, traffic automatically rolls back to the previous model checkpoint.

CI/CD becomes foundational when systems release models repeatedly or carry meaningful production risk, turning ad hoc experimentation into structured, repeatable deployment. Scaling beyond one pipeline requires reusable components and explicitly specified artifact schemas.

**Example 14.1: Google TFX production ML pipelines**

**Scenario**: Google’s production experience motivated TensorFlow Extended (TFX), a set of reusable components for production ML pipelines ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-baylor2017|Baylor et al. 2017]]). As pipelines multiply, ad hoc handoffs make validation, lineage, and reproducibility difficult.

**Diagnosis**: Each stage needs explicit validation and metadata so a deployed model can be traced to the data, transformations, code, and evaluation that produced it.

**Systems lesson**: Directed acyclic graph orchestration alone does not establish reproducibility. Standardized components and ML Metadata (MLMD), a store that records the inputs and outputs of every pipeline component run, preserve lineage through recorded inputs and transformations.

#### Training Pipelines

^sec-ml-operations-training-pipelines-2dcf

CI/CD pipelines orchestrate the overall workflow, but training itself requires specialized compute infrastructure. Model training builds on the single-node parallel execution primitives that training systems already provide. Within MLOps, training activities become components of a reproducible pipeline supporting continual experimentation and production deployment.

↩︎ The single-node data- and model-parallel execution that training pipelines schedule is established in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-singlenode-multigpu-training-c87f|Single-node multi-GPU training]]**.

Frameworks such as TensorFlow ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-abadi2016tensorflow|Abadi et al. 2016]]), PyTorch ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-paszke2019pytorch|Paszke et al. 2019]]), and Keras ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-keras|Chollet et al. 2024]]) supply modular components for model architectures and optimization routines. Operational discipline determines which exploratory training routines graduate into versioned, tested retraining jobs, and under what execution triggers.

↩︎ The criteria for selecting a framework are established in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.10 Choosing a Framework#^sec-ml-frameworks-model-requirements-2e01|Framework selection criteria]]**.

Training scripts and environment configurations are version-controlled with Git ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-git|Torvalds and Hamano 2024]]) and hosted on GitHub ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-github|GitHub, Inc. 2024a]]). Interactive Jupyter ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-jupyter|Project Jupyter 2024]]) notebooks accelerate prototyping by coupling code, inline visualizations, and execution state, but running them unaltered in production pipelines introduces severe operational liabilities.

##### Notebooks in Production

^sec-ml-operations-notebooks-production-7016

Automated CI/CD pipelines assume deterministic and reproducible code execution, but Jupyter notebooks violate this assumption through persistent kernel state. In an interactive session, cells can be executed out of linear order, creating hidden memory dependencies that cannot be reproduced from a clean interpreter restart. A common production failure occurs when development relies on cells executed in sequence 1-3-2; a scheduled batch runner executing top-to-bottom (1-2-3) fails due to undefined variables or altered intermediate tensors.

Testing difficulties compound this state vulnerability. Standard unit-testing harnesses and mocking frameworks do not interface cleanly with interactive notebook documents. Cell-level assertions are rarely parameterized or wired into test runners, leaving notebooks significantly less tested than modular Python code.

Both liabilities shrink once a notebook runs like a script. Headless execution with injected parameters (Papermill ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-papermillDocs|Papermill Project 2026]])) runs cells top-to-bottom as discrete pipeline stages, and export to a plain script (nbconvert ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-nbconvertDocs|Project Jupyter 2026]])) exposes the code to linters and CI test runners. Teams must still select or refactor exploratory cells and verify clean, ordered execution.

Extracting code from notebooks into tested modules introduces refactoring overhead, but it prevents hidden state assumptions from causing training-serving skew in production. Such skew is a silent failure whose cost grows with every day it goes undetected, as the silent-failure calculation in the monitoring discussion shows (notebook [14.3](https://mlsysbook.ai/vol1/14_ml_ops/14_ml_ops.html#nbk-ml-ops-cost-silent-failures)).

Modular training logic also allows a pipeline to schedule repeatable experiments within the node’s resource budget. Concurrent runs compete for accelerator memory, host preprocessing capacity, and storage bandwidth; enforcing resource limits recorded alongside each run’s configuration keeps experiments within the capacity reserved for them. If execution can be interrupted, checkpoint-and-resume (**[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^sec-model-training-training-state-checkpoints-5b3e|Training state and checkpoints]]**) preserves completed training work without requiring the entire run to restart.

How often to run this pipeline depends on evidence that only production monitoring supplies, so [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.07 Retraining Decisions#^sec-ml-operations-retraining-decisions-7d3a|section 14.6]] takes up the decision after monitoring. A pipeline that can run on demand still produces only candidates, and validation decides which of them may ship.

#### Model Validation

^sec-ml-operations-model-validation-a891

Training pipelines produce model candidates; model validation determines which candidates merit production deployment. Unlike research evaluation, where a model that beats a benchmark on a static test set may be considered successful, production validation must assess operational readiness under representative conditions and establish the monitoring and rollback controls needed after the distribution changes. This is where MLOps manages the verification gap (principle [[01 Books/Volume I - Foundations/04 Deployment/V1 Deployment Principles#^pri-verification-gap|9]]), the distance between what a finite test set can verify and what the model meets in deployment, rather than closing it. No test suite covers the deployment population, so validation keeps re-estimating performance as that population changes.

↩︎ Model validation as the evidence-based check that decides whether a model ships is established in **[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.09 Stage 4 Evaluation and Validation#^sec-ml-workflow-evaluation-validation-stage-b47d|Stage 4: Evaluation and Validation]]**.

The evaluation process begins with performance testing against a holdout test set sampled to represent the current production population and refreshed as that population changes. Core metrics such as accuracy, AUC, precision, recall, and F1 score ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-rainio2024|Rainio et al. 2024]]) are computed and tracked longitudinally to detect degradation from data drift ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-ibm-data-drift-b3579f63|IBM 2024]]). [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.06 Production Monitoring#^sec-ml-operations-model-infrastructure-monitoring-3988|Section 14.5.2]] shows how such drift appears in live telemetry.

Beyond static evaluation, production pipelines expose candidate weights to live traffic in controlled stages (shadow, canary, and blue-green deployment) while bounding the blast radius, and [[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.05 Releasing Models#^sec-ml-operations-model-deployment-b9b9|section 14.4.3]] develops each. Validation defines the evidence every stage must produce before a candidate advances. Evaluating candidates under identical operational conditions is the prerequisite for a sound promotion decision. A candidate that shows apparent metric gains only because it was evaluated against a differing traffic slice or temporal window confounds model quality with data variance. Cloud ML platforms support controlled evaluation through request replay, shadow serving, and synthetic load testing. The comparison must also be recorded. Experiment trackers such as Weights & Biases ([[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.14 Source References#^ref-weights-biases-platform-ac4ffad7|Weights & Biases, Inc. 2024]]) log the data slice, time window, configuration, and metrics used for each candidate, so a promotion decision can be audited and repeated under the same conditions.

While automated validation checks protect against regressions on primary aggregate metrics, production validation also requires auditing slices and long-tail behavior. Automated test suites often mask severe performance drops on underrepresented subpopulations or safety-critical edge cases. Production architectures combine automated checks with policy reviews, particularly for models deployed in regulated domains. This multi-stage validation discipline bridges offline evaluation with live production monitoring, ensuring that candidate models satisfy accuracy, latency, and safety invariants before receiving unconstrained serving traffic.

### Infrastructure Integration

^sec-ml-operations-infrastructure-integration-summary-cb2f

A versioned model checkpoint is still unsafe to deploy if the serving cluster runs a different feature definition or lacks a tested path back to the previous weights. Development infrastructure locks these pieces together across two of the three system interfaces. Feature stores and data versioning reduce inconsistency at the data-model interface by centralizing and tracking feature access across training and serving. CI/CD pipelines, model registries, and validation checks stabilize the model-infrastructure interface by automating the transition from trained weights to containerized services with rollback capability. Together, these controls prepare an artifact for release. The third interface, production monitoring, closes the operations loop by tracking whether predictive quality holds as inputs and operating conditions change, though the release must come first.
