# V1-11.09 Compilers and Runtimes

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration|V1-11 Hardware Acceleration]]

^sec-hardware-acceleration-compiler-support-172e

The roofline gives each ResNet-50 layer a ceiling, and hardware mapping showed which schedules can approach it, but neither reaches the silicon by itself. Every layer needs a tiling, a stationary operand, a tensor layout, a precision for the activations it reads and writes, and a fusion boundary. The resulting plan must then run on a device whose input shapes, free memory, and clock rate change while it serves. Across a whole model these choices number in the thousands, which is why compilers and runtimes, not engineers, make them. Graph capture and dispatch overhead, which decide how a model reaches a compiler, belong to **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks#^sec-ml-frameworks|ML Frameworks]]**, and the choice of a deployment runtime for a service belongs to **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-inference-runtime-selection-5eef|Inference Runtime Selection]]**. What remains here is lowering, the path from a captured graph to the accelerator’s units, and the runtime that executes the result.

A single convolution can be implemented with dozens of valid tiling strategies, kernel variants, and memory layouts, most of which perform poorly on a given target. **Machine learning compilers** navigate this space by translating high-level dataflow representations into target-specific executable code, making the mapping and dataflow decisions of the preceding sections automatically. Compiling ResNet-50 for GPU inference passes through four core stages:

1.  **Graph optimization** fuses repeated Conv2D-BatchNorm-ReLU patterns into single compound kernels, eliminating intermediate round-trips to HBM.
2.  **Kernel selection** chooses specialized Tensor Core implementations for compatible matrix multiplications, exploiting the high arithmetic intensity of dense convolutions.
3.  **Memory planning** determines activation lifetimes to safely overlap and reuse intermediate buffer allocations.
4.  **Computation scheduling** pipelines memory copies with execution across independent hardware queues to hide data transfer latencies.

↩︎ Graph compilation, kernel fusion, and framework dispatch overhead are established in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-problem-e1e1|Execution: From Graphs to Kernels]]**.

On the reference H100, the modeled batch-one forward pass falls from 3.53 ms in an eager framework to 0.33 ms as a compiled FP16 engine, a 10.6× improvement without altering the model’s mathematical output. The arithmetic per image is unchanged. The gain comes from fusing the network’s 174 framework kernels into 56 and launching them as one graph instead of one Python dispatch at a time, which shrinks the fixed per-launch cost that dominates a single image.

The same fixed cost explains why INT8 barely moved ResNet-50’s batch-one latency in the profile the chapter opened with. The INT8 arithmetic for one image takes about 4 μs on the H100 (8 μs at FP16). Compilation shrinks the launch overhead but does not remove it, and what remains still dwarfs those microseconds of arithmetic, so even the compiled pass spends almost all of its time on launch and overhead. Batch-one latency sits on the overhead floor rather than on either roofline ceiling, which is why halving the arithmetic barely moves it. The latencies are modeled rather than measured, and **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-inference-runtime-selection-5eef|Inference Runtime Selection]]** separates the same gap into the contribution of each runtime, but the mechanism is general. Graph rewrites, kernel selection, memory planning, and scheduling systematically apply kernel fusion ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-kernel-fusion-7faf|section 11.7.7]]) and memory-efficient tiling ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-memoryefficient-tiling-strategies-9fce|section 11.7.5.1]]) to convert theoretical hardware FLOP/s into delivered throughput ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2018tvm|Chen et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2024tensorrt|NVIDIA 2024b]]).

### ML Compiler Design

^sec-hardware-acceleration-compiler-design-differences-ml-workloads-0698

A conventional C++ compiler such as `gcc` or `clang` cannot collapse ResNet-50’s 174 framework dispatches into 56 fused kernels on its own, because by the time operators lower to scalar loops and pointer arithmetic, the high-level tensor algebra is gone. Machine learning compilers preserve that domain structure by operating on tensor graphs and operator libraries before lowering to machine code. Whereas general-purpose compilers optimize scalar control flow, vector instructions, register allocation, and cache locality, ML compiler stacks optimize graph topology, tensor memory layouts, shape specialization, accelerator kernel dispatch, and inter-device execution planning ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-li2021|Li et al. 2021]]). [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.09 Compilers and Runtimes#^tbl-ml-vs-traditional-compilers|Table 15]] contrasts the emphasis of these two compiler layers. The boundary is complementary rather than disjoint: an ML compiler stack lowers high-level tensor operations into intermediate representations that feed into an LLVM, GPU, or vendor-specific backend.

| Aspect                      | **Traditional compiler**                                         | **Machine learning compiler**                                         |
|:----------------------------|:-----------------------------------------------------------------|:----------------------------------------------------------------------|
| **Input representation**    | Source or intermediate-representation program                    | Tensor graph or tensor-level intermediate representation              |
| Execution Model             | Control flow, loops, threads, vectors, and tasks                 | Tensor operators, kernels, graphs, and accelerator streams            |
| **Optimization priorities** | Instruction selection, loop transforms, vectorization, registers | Graph rewrites, fusion, layouts, shapes, and kernel selection         |
| **Memory management**       | Objects, stack/heap, caches, locality, and prefetching           | Tensor lifetimes, buffer reuse, layouts, tiling, and device transfers |
| Target Hardware             | CPUs, GPUs, and other programmable targets                       | CPUs, GPUs, TPUs, and custom accelerators                             |
| **Compilation output**      | Machine code or lower-level intermediate representation          | Kernels plus a hardware-specific graph or execution plan              |

Table 15: **Compiler Optimization Priorities**: ML compiler stacks add tensor- and graph-level decisions to conventional instruction- and loop-level compilation. In a production toolchain, the two layers commonly cooperate rather than replace one another.

^tbl-ml-vs-traditional-compilers

The distinction in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.09 Compilers and Runtimes#^tbl-ml-vs-traditional-compilers|table 15]] explains why compiler configuration dictates delivered performance even when the underlying neural network code remains unmodified. ML compilers manage the translation layer between high-level tensor operations and hardware execution units; when this mapping fails to expose reuse or efficient access, execution can be limited by memory traffic, latency, or insufficient parallel work.

### ML Compilation Pipeline

^sec-hardware-acceleration-ml-compilation-pipeline-7676

Bridging those two compiler layers requires a staged **ML compilation pipeline** that progressively lowers a framework’s dataflow graph into executable code for CPUs, GPUs, TPUs, or custom ASICs ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2018tvm|Chen et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-GoogleXLA|Google 2025]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-lattner2021|Lattner et al. 2020]]). A full production pipeline adds a fifth stage, code generation, to the four stages previewed on ResNet-50 (graph optimization, kernel selection, memory planning, and computation scheduling), emitting target-specific machine instructions, assembly, or interpreted bytecode. Across these five stages, the compiler applies the dataflow strategies developed in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-dataflow-optimization-strategies-ce52|section 11.7.3]]: kernel fusion, memory tiling, and compute placement. Hardware acceleration delivers its theoretical throughput only when these compiler-driven transformations expose sufficient arithmetic intensity and align memory access with the hardware hierarchy.

#### Graph Optimization

^sec-hardware-acceleration-graph-optimization-f888

Machine learning frameworks represent models as the computation graphs of **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-computational-graph-00f7|Computational graphs]]**, operators joined by the tensors that flow between them. Executing each operator as a separate kernel can incur intermediate-buffer traffic and repeated launches. When intermediate materialization and dispatch dominate execution, graph transformations can remove substantial overhead.

Graph optimization transforms this computation graph into an efficient execution plan before hardware code generation ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2018tvm|Chen et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-Jia2019|Jia et al. 2019]]). Working primarily at a target-independent intermediate representation (IR) level before lowering ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.09 Compilers and Runtimes#^sec-hardware-acceleration-code-generation-85c8|section 11.8.2.5]]), graph passes apply four core transformations. Kernel fusion merges adjacent operations into a single compound kernel to eliminate off-chip memory round-trips and launch overheads. In convolutional networks, fusing Conv2D, batch normalization with frozen inference statistics, and ReLU keeps activations in local registers or shared SRAM throughout the sequence ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-kernel-fusion-7faf|section 11.7.7]]). In transformers, pattern matchers replace the multi-operator self-attention subgraph with IO-aware attention kernels that keep active tiles and running reduction statistics in fast on-chip memory ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-dao2022|Dao et al. 2022]]).

Redundant computation elimination and constant folding remove work that need not happen at runtime at all. A typical case is folding frozen normalization parameters into the weights and biases of the preceding linear or convolutional layer (**[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^sec-model-compression-operator-fusion-ac1d|Compression-specific fusion]]**). These passes also prune dead subgraphs and merge identical parallel paths through common subexpression elimination.

The remaining two passes reduce data movement and live memory footprint without changing the operator set. Algebraic simplification and layout adjustments reorder mathematically equivalent operations to avoid runtime reshape traffic, for example by pushing transpositions through elementwise ops or canceling them against inverse permutations. Memory-aware node reordering evaluates topological sorts of the dependency graph. It schedules independent operations so intermediate activations are consumed and deallocated promptly before memory pressure forces spills to host DRAM. Production compilers execute these rewrites through pattern-matching rules, producing a coarse-grained execution graph aligned with the accelerator’s bandwidth constraints before assigning each node to a concrete hardware routine.

#### Kernel Selection

^sec-hardware-acceleration-kernel-selection-df01

Kernel selection assigns each node in the optimized graph to a concrete hardware implementation. Accelerators provide dozens of valid kernel implementations for a single tensor operation, each parameterized by tile dimensions, thread block configurations, memory staging patterns, and target precision. Choosing the optimal kernel determines whether the execution engine achieves high compute utilization or stalls on uncoalesced memory accesses and pipeline bubbles ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2018tvm|Chen et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-zheng2020ansor|Zheng et al. 2020]]).

In most production pipelines, compilers draw from vendor-optimized kernel libraries (NVIDIA’s cuDNN and cuBLAS for GPUs, Intel’s oneDNN for x86) rather than synthesizing kernels from scratch. These libraries encode microarchitectural details such as register file capacity, cache latency, and vector lane width, so the compiler can invoke pre-tuned implementations.

AI compilers trade compilation time against execution speed across three strategies when choosing among candidate kernels, with numerical precision constraining all three. Rule-based selection is the fastest at compile time. It relies on static heuristics over tensor shapes, alignment, data types, and target support to pick implementations such as a Tensor Core GEMM without benchmarking a large candidate set, at the risk of missing faster configurations on irregular shapes. Cost-model selection refines that choice without running hardware benchmarks by estimating kernel latency, register pressure, cache hit rates, and arithmetic intensity with analytical models that prune unpromising candidates ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-lattner2021|Lattner et al. 2020]]).

When compilation budgets allow hardware measurement, profile-guided selection benchmarks candidates directly on the target device. Autotuners such as TVM’s AutoTVM and Ansor search over tile sizes, unrolling factors, and thread configurations to converge on the fastest implementation ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2018tvm|Chen et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-zheng2020ansor|Zheng et al. 2020]]), and TensorRT similarly times candidate tactics against the target batch sizes. Across all three strategies, precision-aware constraints govern which candidates are legal: inference can use lower-precision paths after quality validation, but selecting INT8 without appropriate range handling degrades accuracy, whereas selecting a wider path unnecessarily forgoes available throughput.

For INT8 ResNet-50, the precision choice that matters most concerns the activations passed between layers, the condition that decided the crossing in notebook [11.6](https://mlsysbook.ai/vol1/11_hw_acceleration/11_hw_acceleration.html#nbk-hw-acceleration-int8-ridge-crossing). When neighboring layers both run at INT8, the compiler can select a kernel whose epilogue performs the requantization of **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-weights-vs-activations-5efb|Weights vs. activations]]**, so each activation leaves the kernel at 8 bits. Where a calibrated scale, an INT8 kernel for the shape, or INT8 support in a neighboring operator is missing, or where timing favors the FP16 kernel, the compiler keeps that edge at FP16 and inserts conversions, returning the layer to the mixed case that the notebook places below the INT8 ridge.

#### Memory Planning

^sec-hardware-acceleration-memory-planning-fb9f

Memory planning assigns physical storage locations, buffer offsets, and tensor lifetimes across the accelerator’s memory hierarchy ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-roesch2018|Roesch et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2018tvm|Chen et al. 2018]]). High-performance execution plans fail if memory management introduces uncoalesced memory transactions, bank conflicts, or unnecessary memory allocations that exhaust accelerator memory, so the compiler coordinates three core memory management mechanisms.

Tensor layout optimization chooses the physical arrangement of tensor dimensions that each kernel needs for coalesced access and vectorization, such as channels-last `NHWC` for Tensor Core convolutions ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-memoryefficient-tensor-layouts-e250|section 11.7.6]]) ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2021cudnn|NVIDIA Corporation 2021]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-GoogleXLA|Google 2025]]). Compilers perform layout assignment globally across the graph to prevent back-to-back layout transformation kernels that consume memory bandwidth.

Liveness analysis and buffer reuse prevent out-of-memory errors by sharing physical memory across non-overlapping tensors. Deep neural networks generate dozens of intermediate activation tensors during forward propagation. Allocating a unique memory buffer for every tensor would quickly exceed the capacity of device memory (such as 16 to 80 GB on typical accelerator GPUs). The compiler analyzes the graph to compute the liveness interval of each tensor, from its generation to the completion of its last consumer. Tensors whose intervals do not overlap can then share the same physical memory offsets, and the compiler packs them accordingly ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-roesch2018|Roesch et al. 2018]]). This static reuse reduces peak device memory requirements to the working set size of concurrently active tensors, avoiding runtime allocation overhead and fragmentation.

Memory hierarchy placement optimizes the staging of data between external memory (HBM or GDDR) and on-chip scratchpad memories (SRAM or shared memory). External memory bandwidth is a scarce resource; moving intermediate tiles back and forth across the memory bus creates memory-bound stalls. Compilers synthesize tiling parameters that guarantee intermediate blocks remain resident in on-chip SRAM until all local compute operations complete, minimizing round-trip traffic across the memory bus. With memory layouts fixed and buffer addresses assigned, the compiler schedules operation execution across hardware compute resources.

#### Computation Scheduling

^sec-hardware-acceleration-computation-scheduling-7ccd

Computation scheduling determines the execution timeline and hardware resource assignment for operations in the compiled graph ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-zheng2020ansor|Zheng et al. 2020]]). Modern accelerators feature deep hardware pipelines, multiple independent compute engines, and dedicated DMA copy engines. Effective scheduling coordinates these resources across three distinct architectural dimensions to maximize hardware occupancy, preserve data dependencies, and prevent pipeline stalls ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2018tvm|Chen et al. 2018]]).

Task partitioning maps computational subgraphs onto the target’s physical execution units. On GPUs, computations are partitioned into grids of thread blocks dispatched across streaming multiprocessors (SMs). On TPUs, matrix multiplications are partitioned into tile sequences matched to the physical dimensions of systolic arrays (e.g., $128 \times 128$ or $256 \times 256$ processing elements) ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-norrie2021|Norrie et al. 2021]]). On CPUs, tasks are split into thread pools matching physical cores and vectorized to fill SIMD registers.

Execution ordering resolves dependencies while minimizing live memory pressure. Operations that depend on prior results must wait for producer kernels to complete, but independent branches (such as multi-head attention projections or parallel residual paths) can execute concurrently or interleave to maintain uniform compute utilization. Compilers analyze the dependency graph to schedule operations in an order that keeps compute pipelines full while keeping activation lifetimes short, preventing buffer bloat.

Asynchronous overlap hides memory latency by executing data transfers concurrently with compute kernels. Accelerators feature dedicated DMA engines that operate independently of arithmetic pipelines. Compilers exploit this architectural separation by scheduling memory transfers (such as host-to-device weights or inter-accelerator halo exchanges) in separate hardware queues or CUDA streams, overlapping transfer latency behind long-running compute operations ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2018tvm|Chen et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2024tensorrt|NVIDIA 2024b]]). When compute and transfer overlap completely, data movement costs are hidden behind arithmetic execution. Poor scheduling instead introduces execution bubbles where arithmetic units sit idle waiting for kernel dispatches or serialized data copies, so synchronizing kernels via explicit compiler-generated events and stream schedules ensures the hardware sustains continuous execution without CPU driver intervention ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2024tensorrt|NVIDIA 2024b]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-zheng2020ansor|Zheng et al. 2020]]).

#### Code Generation

^sec-hardware-acceleration-code-generation-85c8

With scheduling complete, the final compilation stage translates the scheduled execution plan into target-specific machine instructions. Code generation applies traditional backend compiler passes (instruction selection, register allocation, instruction scheduling, and peephole optimization) tailored to accelerator architectures.

Instruction selection for ML targets must emit instructions that directly engage specialized matrix ISA extensions. On NVIDIA GPUs, code generators emit PTX instructions such as `mma.sync.aligned` to invoke Tensor Cores directly, as shown in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^lst-tensor-core-op-aeb713a1|listing 13]]. CPU matrix extensions such as Intel’s AMX have their own tile instructions that the backend must target in the same way. A backend that emits generic floating-point vector instructions instead of these matrix extensions leaves the primary compute engines idle, reducing effective throughput by an order of magnitude. For CPUs and GPUs, compilers emit machine code or optimized assembly; for TPUs, field-programmable gate arrays (FPGAs),[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn27|²⁷]] and proprietary NPUs, the output is often an optimized bytecode or binary execution package executed by a specialized hardware runtime.

### Runtime Support

^sec-hardware-acceleration-runtime-support-f94f

A compiler transforms a high-level model into an execution plan tailored to target hardware, but that plan embeds static assumptions about runtime conditions: tensor shapes, workspace allocation limits, device capabilities, and execution concurrency. Ahead-of-time (AOT) compilation optimizes graph structures, fusion boundaries, and memory layouts for fixed shapes and known hardware configurations. While just-in-time (JIT) compilation can compile specialized variants dynamically as new shapes arrive, each compiled kernel still executes a fixed execution plan. Production serving breaks those assumptions: request arrival rates fluctuate, batch sizes vary, several inference workloads compete for shared accelerator memory, and thermal throttling can pull clock frequencies below their rated values. Request batching and admission control belong to the serving layer (**[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving#^sec-model-serving|Model Serving]]**); the concern here is how the accelerator runtime dispatches compiled execution plans once a batch reaches the hardware.

An AI runtime bridges static graph compilation and the dynamic realities of accelerator execution. Compilers optimize and lower computational graphs under fixed structural assumptions, but production systems encounter variable batch sizes, fluctuating sequence lengths, and constrained memory budgets. The runtime executes compiled engines while managing input-dependent tensor shapes, device-memory buffers and workspace, asynchronous hardware streams, and precompiled execution profiles. In production inference stacks such as NVIDIA TensorRT, the offline builder optimizes the network and benchmarks candidate tactics to construct an execution engine, while the runtime engine attaches input buffers, selects valid optimization profiles, and dispatches kernels to the accelerator ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2026tensorrtarchitecture|NVIDIA Corporation 2026a]], [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2026tensorrtdynamicshapes|2026b]]).

This execution lifecycle spans three core responsibilities. First, the runtime selects and dispatches precompiled kernel variants matched to runtime tensor dimensions and hardware capabilities. Second, it manages device memory through arena allocators and static buffer reuse, reducing repeated allocation and associated host-device synchronization overhead. Third, when a model spans several accelerators, the runtime coordinates the boundaries between them, as in pipeline-parallel frameworks such as GPipe ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-huang2019gpipe|Huang et al. 2019]]) and automated device-placement systems ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-mirhoseini-device-placement-2017-b3c4cbc8|Mirhoseini et al. 2017]]). While serving schedulers oversee request batching and admission control across clusters, the accelerator runtime governs local execution on the device.

#### ML Runtime Architecture

^sec-hardware-acceleration-runtime-architecture-differences-ml-systems-932e

General-purpose runtimes manage threads, preemptive tasks, heap allocations, and asynchronous I/O across arbitrary control-flow paths. In contrast, an AI runtime operates over dataflow graphs composed of multidimensional tensors, pre-scheduled kernel grids, device memory arenas, and hardware command queues, as contrasted in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.09 Compilers and Runtimes#^tbl-runtime-comparison|table 16]].

| Aspect                  | **Traditional runtime**                                    | **AI runtime**                                                |
|:------------------------|:-----------------------------------------------------------|:--------------------------------------------------------------|
| Execution Model         | Functions, threads, tasks, events, and asynchronous I/O    | Tensor graphs, kernels, streams, and device events            |
| **Task scheduling**     | Threads and tasks across processor resources               | Dependency-aware kernel and transfer dispatch                 |
| Memory Management       | Objects, stacks, heaps, pools, and virtual memory          | Tensor buffers, workspaces, device memory, and buffer reuse   |
| Optimization Priorities | Responsiveness, throughput, locality, and resource sharing | Shape compatibility, transfer overlap, reuse, and utilization |
| **Adaptability**        | Dynamic scheduling and allocation within program semantics | Runtime choices within compiled graphs and available kernels  |
| Target Hardware         | CPUs and heterogeneous devices                             | CPUs, GPUs, TPUs, and custom accelerators                     |

Table 16: **Runtime Execution Models**: AI runtimes add tensor-, graph-, and accelerator-aware resource management to conventional runtime services. The exact boundary among framework, compiler runtime, device library, and serving scheduler varies by stack.

^tbl-runtime-comparison

Tensor memory management represents a primary architectural divergence. In traditional systems, general-purpose allocators manage variable-sized heap objects using runtime metadata. Traditional device allocation calls such as `cudaMalloc` can introduce costly driver work and synchronization. AI runtimes reduce repeated allocation overhead by combining lifetime analysis with pooled or arena allocation. For fixed-shape graphs, the compiler computes static memory offsets, mapping non-overlapping intermediate tensors to shared physical buffers. For variable-shape tensors, the runtime can carve device-memory buffers from preallocated pools, avoiding repeated driver allocation calls within the reserved capacity.

Power and thermal limits add a further divergence, because production environments impose physical constraints that differ from offline benchmarks. For example, an NVIDIA A100 SXM accelerator operates with a maximum thermal design power (TDP), the sustained power its cooling is designed to remove, of 400 W, whereas the A100 PCIe variant is constrained to a 300 W TDP envelope. Because sustained clock frequencies scale with available power and thermal dissipation, a compiled kernel tuned for an SXM module may experience thermal throttling or fail to meet latency bounds on a PCIe card. The runtime cannot re-synthesize loop structures or change thread-block dimensions dynamically in response to thermal constraints; it must execute within precompiled profiles while the serving system handles request batching and admission control.

#### Dynamic Kernel Execution

^sec-hardware-acceleration-dynamic-kernel-execution-33fc

While static compilation generates high-performance machine code for fixed shapes, production inference requires executing requests with dynamic dimensions. In language models, input sequence length ${S}$ and batch size ${B}$ vary across requests. Recompiling an execution plan for each unexpected shape can violate a request deadline: exploring loop unrolling, shared-memory tiling, and register allocation requires seconds or minutes, while serving deadlines operate on millisecond timescales.

↪ How serving runtimes form batches of varying size under latency deadlines is developed in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-static-vs-dynamic-batching-fd0a|Static vs. dynamic batching]]**.

Profile-based inference stacks address this mismatch with precompiled shape ranges. The engine is built for a declared range of each dynamic dimension (the minimum, typical, and maximum shapes), with device-memory workspace reserved for that range. A request inside the range places its tensors in preallocated buffers and launches precompiled kernels without compilation overhead. A request outside it must be padded, split, or routed to a slower general-purpose kernel, because the runtime cannot synthesize new tiling strategies on the fly. TensorRT’s optimization profiles are the common example, and choosing and configuring such a runtime for a service is developed in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-inference-runtime-selection-5eef|Inference Runtime Selection]]**.

Variable requests also keep the host link busy, and the runtime hides those transfers with the asynchronous streams and double buffering of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^sec-hardware-acceleration-transfer-optimization-85a8|section 11.5.4.2]], copying batch ${k}{+}1$ while batch ${k}$ executes. The overlap holds only while compute duration exceeds transfer duration.

#### Runtime Kernel Selection

^sec-hardware-acceleration-runtime-kernel-selection-1ffe

An operation may have multiple kernel implementations, termed tactics in TensorRT. The builder selects tactics while constructing an engine; other stacks may retain variants for runtime dispatch. The available choice depends on tensor dimensions, the compiled plan, and permitted device-memory workspace.

Operational batch size changes the available reuse and parallelism. At ${B}=1$ in weight-streaming autoregressive decoding, GEMV kernels often target memory throughput. Larger prompt-processing batches can favor GEMM kernels using Tensor Core paths, register tiles, and shared memory. The transition depends on dimensions, precision, traffic, and hardware balance; no fixed batch threshold establishes compute-bound execution.

Device-memory workspace availability further constrains tactic selection. In a standard output-tiled GEMM, each thread block computes one $({M}, {N})$ output tile and loops sequentially over the entire inner reduction dimension ${K}$, accumulating partial sums in on-chip registers before writing the final output tile once. When the output matrix is small but the reduction dimension ${K}$ is long, the output grid spawns too few thread blocks to occupy every streaming multiprocessor. A split-${K}$ tactic exposes extra parallelism by partitioning the ${K}$ reduction loop across multiple thread blocks running on different multiprocessors. Because separate multiprocessors do not share registers or local scratchpad memory, each split-${K}$ block must write its partial tile sum to a temporary buffer in global device memory so a subsequent reduction step can sum the slices into the final result. A runtime execution plan built under a tight workspace memory limit may therefore disallow split-${K}$ tactics and accept lower multiprocessor occupancy instead.

Runtime selection remains strictly bounded by the numerical formats established during compilation. In mixed-precision training and inference systems such as Megatron-LM, executing matrix multiplications in FP16 or BF16 on Tensor Cores with FP32 accumulation is a numerical requirement of the chosen recipe, validated prior to deployment ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-shoeybi2019megatron|Shoeybi et al. 2019]]). The runtime does not monitor loss values or dynamically alter precision; it only chooses among the validated tactics that implement the specified numerical precision.

#### Kernel Scheduling and Utilization

^sec-hardware-acceleration-kernel-scheduling-utilization-99d6

Kernel dispatch represents the final stage of runtime execution, coordinating host-side task queues with device-side execution. The software runtime manages host-side command queues (such as CUDA streams or TPU command rings) and records hardware events or semaphores to enforce dataflow dependencies asynchronously. When independent operations (such as parallel multi-head attention projections) have no mutual data dependencies, the runtime dispatches them onto separate streams to enable concurrent execution on the accelerator. Once submitted to the device queue, however, execution control transfers entirely to hardware schedulers. On a GPU, the hardware warp scheduler and work distribution engine assign thread blocks to SMs based on register file availability, shared memory capacity, and maximum warp occupancy. The software runtime cannot schedule individual threads or dictate L1/L2 cache replacement policies. Similarly, TPU runtimes submit macro-instructions to on-chip command queues, while hardware sequencers feed systolic matrix units and vector units ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-jouppi2017|Jouppi et al. 2017]]).

A low achieved rate alone cannot distinguish runtime gaps from a memory bottleneck. Consider three hypothetical profiles of low-intensity kernels, constructed to separate the cases rather than measured on a particular device. In the first, the timeline shows continuous kernel execution and HBM traffic close to the sustainable bandwidth ceiling. Reducing transferred bytes or increasing reuse addresses that observed limit. In the second, kernels remain active but dependent loads produce long stalls while HBM traffic stays well below its ceiling. More bandwidth alone need not help: independent requests or a different access schedule must expose enough concurrency to hide the latency. In the third, short kernels alternate with device-idle gaps while the host submits work. Reducing dispatch and synchronization overhead addresses those gaps; changing the arithmetic instruction rate does not.

The discriminating evidence is the timeline together with traffic and stall observations. If added independent requests raise bandwidth and shorten load stalls, they support the latency hypothesis; if bandwidth is already sustained near its ceiling, traffic reduction is the more direct lever. The roofline bounds the resource opportunity, while the profile identifies which mechanism leaves the kernel below it. Even with aggressive kernel fusion, optimal tactic selection, and zero-allocation memory reuse, the execution capacity of a single accelerator is physically bounded by its silicon area, thermal dissipation limit, and high-bandwidth memory capacity. Scaling beyond these physical boundaries therefore requires distributing computation across multiple accelerators.
