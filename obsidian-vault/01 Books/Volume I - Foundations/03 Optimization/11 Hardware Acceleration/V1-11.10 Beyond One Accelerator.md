# V1-11.10 Beyond One Accelerator

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration|V1-11 Hardware Acceleration]]

^sec-hardware-acceleration-multichip-scaling-c649

A single accelerator holds the chapter’s ResNet-50 workload and GPT-2 XL decoding comfortably in on-package memory, but larger workloads outgrow one device either because their arithmetic would take too long on it or because their weights and runtime state do not fit in its HBM. Multi-chip scaling still depends on an efficient per-device dataflow, since each accelerator must feed its own execution units, but communication adds further boundaries to the memory hierarchy. Moving data through on-chip storage, HBM, an intra-node link, and a network fabric generally lowers bandwidth and raises latency and energy at each step, so scaling is not merely a question of adding chips.

Each step outward moves the communication boundary and changes the dominant trade-off. Inside the package, chiplet-based architectures partition a large design into smaller dies joined at relatively low latency, bypassing the manufacturing limits of a monolithic chip. Wafer-scale integration takes the opposite approach and keeps more computation on one device.

At the node, a multi-accelerator server joins several chips, each with its own memory, through board- or server-level interconnects such as NVLink. A workload then splits through data parallelism (each accelerator processes different batches) or model parallelism (different accelerators hold different layers, or individual matrix multiplications are sliced across devices). When a model’s weights and runtime state exceed one device’s HBM, that split becomes a placement requirement rather than a speed choice. How training uses the accelerators of one machine, including how they synchronize gradients, is developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-singlenode-multigpu-training-c87f|Single-node multi-GPU training]]**. Within a server, the engineering test compares the computation or device-memory capacity that partitioning saves with the communication it exposes, accounting for overlap and the actual directional link bandwidth. Splitting a layer’s matrix multiplication across two accelerators, for example, halves each device’s arithmetic but pays off only if exchanging the partial results over the link takes less time than the arithmetic it removed.

Beyond the node, the network interface card links each machine to the others over Ethernet or InfiniBand. It is the narrowest, highest-latency step of the bandwidth taper measured in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^sec-hardware-acceleration-nodelevel-interconnect-topology-b45b|section 11.5.4.1]], and traffic that must cross it leaves single-node reasoning behind. Work that spans several machines lies beyond this book’s one-machine scope. Scaling out across identical data-center accelerators is one way a system combines multiple engines; at the opposite end of the power spectrum, mobile and embedded systems integrate several *different* engines onto a single silicon die.

**Self-Check: Question**

1.  Why have accelerator architectures increasingly shifted from monolithic single-die designs toward Multi-Chip Module (MCM) and chiplet architectures?

    1.  Chiplets eliminate all need for semiconductor fabrication foundries
    2.  Monolithic dies are constrained by the physical lithography reticle limit ($\approx 858\text{ mm}^2$) and suffer exponential yield loss as die size increases
    3.  Monolithic dies cannot support high-bandwidth memory (HBM) interfaces
    4.  Chiplets allow electrical signals to travel faster than the speed of light

2.  Explain how communication boundaries change performance as a neural network workload scales from chiplets within a package to multiple accelerators within a node and then across nodes.

3.  Describe the architectural rationale behind a wafer-scale accelerator and explain which multi-chip bottlenecks it reduces and which constraints remain.

4.  What is the primary bottleneck introduced when scaling out from accelerators within one server to accelerators across separate servers?

    1.  Inter-node network adapters cannot transmit FP16 or BF16 floating-point values
    2.  Inter-node communication requires GPUs to switch to single-threaded CPU emulation mode
    3.  The communication boundary moves onto a much narrower and higher-latency network path, making collective communication more expensive
    4.  Inter-node scaling eliminates the need for gradient synchronization in distributed training
