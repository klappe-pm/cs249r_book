# V1-11.06 Memory Systems

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration|V1-11 Hardware Acceleration]]

^sec-hardware-acceleration-ai-memory-systems-0057

That gap between a 4 μs arithmetic floor and real inference latency opens whenever the memory subsystem cannot deliver weights and activations fast enough to keep the compute units busy. Modern accelerators provide hundreds of teraflops (or even petaflops) on low-precision tensor datapaths ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020a]], [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2024blackwell|2024]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-choquette2023|Choquette 2023]]), yet their arithmetic pipelines idle as soon as memory traffic saturates the bus. This is the memory wall, the growing divergence between arithmetic capability and memory bandwidth, seen from inside the accelerator.

↩︎ The memory wall, the widening gap between compute growth and memory bandwidth growth, is established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.03 Physical Constraints on Deployment#^sec-ml-systems-deployment-spectrum-71be|Physical Constraints on Deployment]]**.

Because deep neural networks manipulate millions or billions of parameters across high-dimensional activation tensors, performance is frequently dictated by data movement rather than raw arithmetic capacity. Accelerators combat this memory wall through tiered storage hierarchies, software-managed scratchpads, high-bandwidth 3D stacked memory, and architectural dataflow strategies designed to maximize spatial and temporal reuse. For the chapter’s ResNet-50 workload the question becomes where each activation tile lives between the moment one convolution writes it and the moment the next consumes it, and what each tier on that path costs in time and energy.

### The AI Memory Wall

^sec-hardware-acceleration-understanding-ai-memory-wall-3ea9

Upgrading to an accelerator with twice the peak FLOP/s yields zero speedup when a workload’s weights and activations already saturate memory bandwidth, pinning execution time at $\frac{{D_{\text{vol}}}}{{\text{BW}}}$. On an accelerator the **AI memory wall** is chiefly this bandwidth ceiling, set by the parameter volumes and activation tensors of deep learning rather than by the single-access latency gap of the classic CPU formulation. Adding more memory capacity does not remove it either, because a model that fits comfortably in device memory still waits on the rate at which its bytes reach the compute units of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-compute-units-execution-models-f406|section 11.4]]. The energy side of the wall was set out with the energy ladder in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.03 Hardware Specialization#^sec-hardware-acceleration-machine-learning-hardware-specialization-09c5|section 11.2.3]]: an off-chip DRAM access costs about 173× the energy of the FP32 multiply that consumes its operand ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.03 Hardware Specialization#^fig-energy-hierarchy|figure 4]]). The memory wall adds the time side of the same imbalance, which grows with every hardware generation.

#### Quantifying the Compute-Memory Performance Gap

^sec-hardware-acceleration-quantifying-computememory-performance-gap-1526

Over the past two decades, peak computational capabilities have grown substantially faster than DRAM bandwidth ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-gholami2024|Gholami et al. 2024]]). This divergence stems from physical scaling constraints: while transistor scaling and dense systolic arrays multiply arithmetic throughput, memory bandwidth remains bounded by pin counts, package-substrate routing density, and interface signaling power. Representative high-end accelerators can deliver on the order of $10^3$ TFLOP/s of peak tensor throughput (for example, NVIDIA H100 delivering 989 TFLOP/s in FP16 or 1,979 TFLOP/s in dense FP8) while providing approximately 3.35 TB/s of memory bandwidth ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-choquette2023|Choquette 2023]]). This implies that on the order of $10^2$ FLOP of work per byte moved is required to fully use the compute, a threshold [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-hardware-balance|section 11.6.2]] calls the ridge point and that exceeds the arithmetic intensity of many practical neural network workloads.

When a workload’s arithmetic intensity falls below this threshold, data transfer ($\frac{{D_{\text{vol}}}}{{\text{BW}}}$) sets the larger of the two modeled time bounds. Accelerators attempt to tolerate memory latency (typically hundreds of clock cycles for off-chip DRAM) by maintaining thousands of concurrent execution threads and switching between active warps while memory requests remain in flight. However, when memory bandwidth saturates or when register pressure limits occupancy (the number of warps resident on a streaming multiprocessor at once, which falls as each thread claims more registers), the scheduler runs out of independent instructions to issue. Compute pipelines then stall, leaving high-throughput tensor cores idle while waiting for operands. Moving those bytes also costs power, because driving a wide off-chip memory interface consumes a substantial fraction of the chip’s power budget and leaves less for arithmetic ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-horowitz2014|Horowitz 2014]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-sze2017|Sze et al. 2017]]).

The time gap and the energy ladder describe the same pressure from two sides: each byte fetched from DRAM costs more time relative to the arithmetic it feeds with every generation, on top of its energy cost. The TPU v1’s performance-per-watt advantage (example [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.03 Hardware Specialization#^exmp-hw-acceleration-tpuv1-vs-k80-efficiency-shock|11.1]]) came largely from minimizing that off-chip movement through systolic arrays and large on-chip SRAM ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-jouppi2017|Jouppi et al. 2017]]).

The hardware’s ratio of arithmetic to bandwidth is the supply side of the memory wall; model size is the demand side. Parameter count is a capacity quantity, but it becomes a bandwidth demand during low-batch dense decoding. In that regime, every generated token streams the weights from device memory, so weight traffic per token grows with the parameter count. For such workloads, the structural widening between model footprints and available memory bandwidth is therefore what turns the iron law’s memory term into the limiting constraint across generations. Sparse expert models read selected experts rather than every stored parameter, so their total parameter counts do not directly specify per-token traffic.

[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^fig-memory-wall|Figure 7]] plots the logarithmic divergence between model size and bandwidth relative to 2014. It contrasts the roughly 3,900× increase in dense model parameters (filled red points) against the 33× increase in per-device accelerator memory bandwidth (blue points). The contrast isolates the widening shaded memory-wall gap ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-krizhevsky2012imagenet|Krizhevsky et al. 2012]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-simonyan2014very|Simonyan and Zisserman 2015]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-brown2020language|Brown et al. 2020]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chowdhery2022palm|Chowdhery et al. 2022]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-dubey2024llama|Dubey et al. 2024]]). DeepSeek-V3 appears as an open marker at its total parameter count and is left out of the trend for exactly that reason ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-deepseek2025v3|DeepSeek-AI 2025]]). Even high-bandwidth accelerators such as NVIDIA B200 and AMD MI300X/MI325X cannot close this growth-rate gap through bandwidth scaling alone ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2024blackwell|NVIDIA Corporation 2024]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-amd2023mi300x|AMD 2023]]). Because bandwidth scaling alone cannot close this gap, whether a model can exploit an accelerator’s design depends on the pattern of its memory accesses, which differs sharply among parameters, activations, and optimizer state.

### Memory Access Patterns in ML Workloads

^sec-hardware-acceleration-memory-access-patterns-ml-workloads-a960

In dense FP16 autoregressive generation at batch size 1, streaming a model’s weights from device memory for each generated token yields roughly 1 FLOP/byte on the matrix-vector work, starving compute units before activations or gradients ever enter the picture. Across training and inference, parameters, activations, and optimizer states compete for that same memory bandwidth in distinct ways. Model parameters (weights and biases) can span hundreds of billions of values ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-brown2020language|Brown et al. 2020]]) that must stream from memory whenever batch reuse is low. Intermediate activations produced at each layer must also be buffered for subsequent operations, and during training those forward activations must either stay in memory until backpropagation consumes them or be recomputed on the backward pass. Training then compounds the traffic with gradients and optimizer state. Backpropagation writes a gradient for every parameter, and adaptive optimizers such as Adaptive Moment Estimation (Adam) read and write multi-word momentum states on every step, multiplying the bytes moved per parameter update ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-narayanan2021|Narayanan et al. 2021]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-kwon2019|Kwon and Rhu 2018]]).

The physical cost of this data movement depends on where each tensor resides in the memory hierarchy. While an on-chip register access completes in a single clock cycle at sub-picojoule energy, a dependent off-chip DRAM fetch can expose hundreds of cycles of latency and expends orders of magnitude more energy. Independent requests can overlap that latency, subject to available concurrency and bandwidth. Tracing a single tensor of the chapter’s ResNet-50 workload through the memory tiers during an inference pass makes this disparity concrete (lighthouse [11.2](https://mlsysbook.ai/vol1/11_hw_acceleration/11_hw_acceleration.html#lhs-hw-acceleration-life-tensor-resnet50)).

**Lighthouse 11.2: Life of a tensor: A ResNet-50 activation map**

Follow one activation map of the chapter’s ResNet-50 workload, the output of a stage-2 convolution ($56{\times}56$ positions by 64 channels), on its way to the next convolution’s Tensor Cores on an H100:

1.  **HBM**: The previous kernel wrote the map here.
    - **Size**: 201 KB per image at INT8 and 401 KB at FP16; a batch of 32 holds 6.4 MB at INT8.
    - **Latency**: A dependent off-chip request takes about 273 ns, while streaming one image’s map at full bandwidth would take only about 60 ns, so the kernel must keep many requests in flight to approach the bandwidth ceiling.
    - **Energy**: About 160 pJ per byte in the 45 nm estimates used throughout the chapter, or about 32.1 µJ to read one image’s map once.
2.  **L2 cache**: The H100 shares 50 MB of L2 across its streaming multiprocessors (SMs), enough to hold the whole batch’s map at INT8 if the next kernel consumes it soon after the previous one wrote it.
    - **Latency**: About 150 ns on Hopper.
3.  **Shared memory**: One SM stages a tile of the map in its 228 KB of software-managed shared memory. A whole image’s map fits at INT8 but not at FP16, so the INT8 format changes which tier can hold it.
    - **Latency**: About 17 ns on Hopper.
4.  **Registers**: The Tensor Core reads its operands here.
    - **Latency**: A small number of cycles, depending on the instruction.
    - **Energy**: About 0.1 pJ per access, more than three orders of magnitude below an off-chip access.
    - **Device arithmetic peak**: 1,979 TOPS on the H100 INT8 tensor path. This is a rate of operations, which the operands in these registers must sustain, not a rate of bytes moved.

**Systems insight**: Latency and energy per access rise from registers to HBM. The working set’s location, access count, reuse, and dependencies determine the memory contribution to time and energy; arithmetic adds its own cost. The bandwidth term of the roofline is whichever link of this hierarchy the working set must cross; HBM-to-L2 is one possible limiting link, not the only one.

The boundary between bandwidth-bound and compute-bound execution emerges directly from the balance between data transfer time and arithmetic execution time. Consider a workload that requires data volume ${D_{\text{vol}}}$ (bytes) across available memory bandwidth ${\text{BW}}$ (bytes/s). It executes ${O}$ floating-point operations on hardware with peak throughput ${R_{\text{peak}}}$ (FLOP/s) at realized hardware utilization ${\eta_{\text{hw}}}$. The respective execution times are the iron law’s data and compute terms:

$$
\begin{gather*} {T_{\text{memory}}} = \frac{{D_{\text{vol}}}}{{\text{BW}}} \\ {T_{\text{compute}}} = \frac{O}{{R_{\text{peak}}} \cdot {\eta_{\text{hw}}}} \end{gather*}
$$

Whichever term is larger identifies the regime, and ${T_{\text{memory}}} > {T_{\text{compute}}}$ identifies bandwidth-bound execution. Overlap changes the total time, not that classification. Without overlap the two terms add, and when hardware overlaps memory transfers with computation, the larger term alone sets the theoretical lower bound on execution time. In practice, however, data dependencies, memory controller queueing, and partial pipeline overlap dictate how much arithmetic hardware remains idle while waiting for operands.

#### Irregular Memory Access

^sec-hardware-acceleration-irregular-memory-access-c6ec

Production machine learning workloads combine regular dense matrix kernels with irregular memory access patterns that defeat conventional caching and prefetching hardware. While dense operations like general matrix multiply (GEMM) and convolution stream contiguous blocks that map cleanly onto hardware caches and systolic arrays, irregular operations rely on indirect, sparse, or input-dependent memory addresses. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^tbl-traditional-vs-ml-mem|Table 5]] contrasts these two memory regimes across access geometry, cache locality, and hardware pressure.

| Feature                | **Regular dense kernels**                               | **Irregular ML components**                          |
|:-----------------------|:--------------------------------------------------------|:-----------------------------------------------------|
| **Access pattern**     | Contiguous or tiled                                     | Indirect, scattered, or input-dependent              |
| **Cache locality**     | Often high after tiling                                 | Often lower and workload-dependent                   |
| **Data reuse**         | Structured across tiles or batches                      | Sparse or dynamic, depending on the operator         |
| Dependencies           | Static loop nests                                       | Input-dependent routing or variable shapes           |
| Examples               | GEMM, convolution, dense attention                      | Embedding lookup, unstructured sparsity, MoE routing |
| **Primary pressure**   | Compute or bandwidth, depending on arithmetic intensity | Latency, bandwidth, metadata, and load imbalance     |
| **Energy consequence** | Depends on reuse and memory tier                        | Extra movement and metadata can increase energy      |

Table 5: **Regular and Irregular Memory Access**: Regular dense kernels expose tileable reuse and predictable addresses, whereas irregular ML components rely more on indirect or input-dependent access, weakening caching and prefetching and adding metadata or load-balance overhead. A single model may contain both regimes.

^tbl-traditional-vs-ml-mem

Within a single neural network, memory access behavior varies sharply across layer types. Convolutional layers have high spatial locality and register reuse as small weight kernels slide across input feature maps. Fully connected layers and dense attention, by contrast, execute regular matrix multiplications whose large parameter matrices or key-value caches can exceed on-chip SRAM capacity and become bandwidth bound when operational reuse is low. Variable sequence lengths complicate memory buffer allocation, yet the attention operations within each sequence remain regular, contiguous matrix multiplies.

True memory irregularity arises instead from unstructured sparsity,[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn19|¹⁹]] embedding lookups, and dynamic token routing. Unstructured sparsity stores nonzero weights or activations in compressed formats such as CSR and coordinate list (COO), which require pointer indirection to decode operand coordinates. Embedding tables break sequential transfers in a different way: sparse categorical IDs select arbitrary rows from tables spanning tens of gigabytes in DRAM, turning reads into uncoalesced, scattered fetches. DLRM, the book’s capacity-bound lighthouse, is the extreme case. Its embedding tables exceed one accelerator’s memory, and each lookup fetches a short row from an address known only when the input arrives, which defeats both caches and prefetchers. Mixture-of-Experts (MoE) models introduce a third irregularity at the routing layer, where gates direct tokens to different expert networks based on input context. Although deterministic for a given input, token assignments vary across batches, disrupting prefetch pipelines and unbalancing execution queues across parallel cores.

Irregularity degrades performance through distinct mechanisms, and treating them as one memory problem can point to the wrong optimization. Scattered addresses may turn one logical access into several memory transactions, so each fetched cache line carries few useful payload bytes. Indirection can also serialize address generation: the system must fetch an index or pointer before it knows which payload to request, limiting how many requests can be in flight at once even when aggregate bandwidth remains available. Input-dependent routing creates a third failure mode when some processing elements receive longer queues than others; completion time follows the slowest queue while neighboring units idle. A sequential stream can saturate bandwidth without being irregular, whereas a dependent lookup chain can stall far below peak bandwidth.

The paired address strips in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^fig-irregular-address-transactions|figure 8]] isolate spatial utilization from address dependence. The example counts traffic in sectors, the aligned fixed-size blocks that the memory interface fetches as a unit, so it does not infer physical DRAM traffic from logical addresses alone.

![[90 Assets/Volume I/11 Hw Acceleration/Generated Figure 4ad0964be1.svg]]

Figure 8: **Spatial Utilization and Address Dependencies**: Each cell is a four-byte word; heavy outlines mark aligned 16-byte sectors fetched at an illustrative interface. With a cold cache, no reuse, and requests merged within each sector, adjacent requests fetch one sector while scattered requests fetch four for the same useful payload. The separate dependency chain shows why a payload read may have to wait even when bandwidth is available.

^fig-irregular-address-transactions

Packing requests into fewer sectors reduces surplus bytes at that interface. It does not remove the dependency in the lower panel: the payload request still waits until the index or pointer returns its address. Increasing bandwidth and exposing independent requests therefore address different limits.

Diagnosis should begin with the mechanism limiting the kernel. A low ratio of useful payload bytes to transferred bytes indicates poor spatial utilization. Long memory stalls alongside unused bandwidth indicate dependent misses or too few concurrent requests to hide latency. Uneven queue depths or per-route work reveal load imbalance rather than a cache-capacity problem. Cache hit rate alone cannot separate the first two cases, because a miss can waste bandwidth, expose latency, or both, and it says nothing about imbalance.

Each mechanism calls for a different remedy. Packing or blocking raises the useful bytes per transaction, reordering and prefetching keep more independent requests in flight, structured sparse formats remove indirection, and routing or partitioning balances work. Where the format is under system control, changing it comes first, because that removes the indirection before a kernel executes. Additional cache capacity or bandwidth helps only when measurement shows that the reorganized requests still exhaust that resource. More bandwidth cannot resolve a serial pointer dependency, and more capacity cannot rebalance skewed work.

Software can mitigate irregular access by regularizing tensor layouts, enforcing structured sparsity, and sorting dynamic routes into uniform batches. Yet software restructuring cannot eliminate the physical penalty of data movement: whether a memory request is contiguous or scattered, every transferred byte must cross physical wires governed by finite bandwidth, propagation latency, and energy dissipation. Bounding these physical costs requires organizing storage into cascading hardware tiers.

### Memory Hierarchy

^sec-hardware-acceleration-memory-hierarchy-1839

No single storage technology can simultaneously satisfy the multi-terabyte-per-second bandwidth required by dense execution units and the tens of gigabytes of capacity required to hold modern model parameters. Accelerators resolve this tension through multilevel memory hierarchies. Rather than treating memory as a monolithic address space, the machine organizes storage into distinct physical tiers, each optimized for a specific balance of capacity, access latency, bandwidth, and energy dissipation.

At the apex of the hierarchy, register files and on-chip SRAM caches supply operands to arithmetic units with sub-nanosecond latency and single-digit picojoule energy costs, but their capacity is strictly limited by silicon die area. At the base, nonvolatile flash storage holds hundreds of gigabytes of model checkpoints and training datasets, but requires milliseconds or microseconds to access. Between these boundaries, software-managed scratchpads stage active tensor tiles, while device-local DRAM (such as HBM or GDDR) provides the primary working memory for parameters and activations.

This organization establishes an inverse relationship across tiers: as storage capacity expands and physical distance from arithmetic units grows, bandwidth falls, latency lengthens by orders of magnitude, and energy consumption per bit escalates. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^tbl-memory-hierarchy|Table 6]] compares these tiers across latency, bandwidth, capacity, and functional roles in deep learning workloads.

| Memory Level                          | **Relative latency**                |     Bandwidth      | **Relative capacity** | **Example Use in Deep Learning**                                 |
|:--------------------------------------|:------------------------------------|:------------------:|:----------------------|:-----------------------------------------------------------------|
| Registers                             | Lowest                              |      Highest       | Tiny                  | Storing operands for immediate computation                       |
| **L1/L2 Cache (SRAM)**                | Very low                            |        High        | Small                 | Caching frequently accessed activations and small weight blocks  |
| **Scratchpad memory**                 | Very low                            |        High        | Small to medium       | Software-managed storage for intermediate computations           |
| **Device DRAM (HBM, GDDR, or LPDDR)** | High                                | Moderate–Very High | Large                 | Storing model parameters and activations that do not fit on-chip |
| **Host DRAM (typically DDR)**         | High locally; transfer adds latency |      Moderate      | Large to very large   | Staging or offloading data outside accelerator memory            |
| **Flash Storage (SSD/NVMe)**          | Very high                           |        Low         | Very large            | Storing pretrained models and checkpoints for later loading      |

Table 6: **Memory Hierarchy Trade-Offs**: AI accelerators use a multilevel memory hierarchy to balance performance and capacity. Each level provides distinct latency, bandwidth, and capacity characteristics that dictate how neural network components (weights, activations, and intermediate results) should be allocated to minimize bottlenecks and maximize throughput. Relative labels describe the typical ordering; exact values depend on architecture. **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-latencies-every-programmer-know-e89f|The latency hierarchy]]** supplies registry-backed reference latencies.

^tbl-memory-hierarchy

A recurring systems question is why accelerators cannot bypass on-chip SRAM entirely and stream all operands directly from high-capacity off-chip DRAM. A dependent DRAM request exposes the full access latency. Many independent requests can hide that latency, but their sustained operand supply remains limited by off-chip bandwidth; on-chip staging also enables reuse.

**Napkin Math 11.2: Why HBM cannot feed the array directly**

**Problem**: HBM sits only millimeters from the die. Why is on-chip SRAM still necessary instead of fetching all data from HBM?

**Math**:

1.  **Clock cycle**: At 2 GHz, $1/(2\text{ GHz}) = 500\text{ ps}$.
2.  **DRAM access**: Off-chip HBM sits millimeters away on the package, but row activation, DRAM-array latency, serialization, protocol traversal, and queuing add up to 100+ cycles per access.
3.  **Distance, for comparison**: On an H100-class 814 mm² die, signals travel ~20 mm; at $\approx 0.5{c}$, $20\text{ mm}/(0.5{c}) \approx 130\text{ ps}$, less than one cycle, so wire distance is not what makes an HBM access slow.

**Systems insight**: The access path, not the distance, sets the DRAM access cost; the propagation estimate also omits real interconnect delay from wiring and routing. Independent requests can overlap the 100-plus-cycle access path; a dependent request cannot. Registers and SRAM supply operands at the rate the array needs while reusing values that would otherwise cross HBM repeatedly.

#### On-Chip Memory

^sec-hardware-acceleration-onchip-memory-72d1

The **on-chip memory** subsystem integrates registers, Static Random-Access Memory (SRAM) caches, and software-managed scratchpads directly on the accelerator die. Register files provide the immediate operand and accumulator storage needed by execution pipelines. Modern accelerators provision substantial register capacity in aggregate across the chip but divide it among concurrent threads, so a thread that keeps a larger tile in registers leaves room for fewer resident warps to hide memory latency.

Hardware-managed L1 and L2 caches provide fast buffering for frequently referenced data using automatic tag checking and hardware eviction policies. However, automatic caches are poorly suited for streaming multi-gigabyte tensor operations: scanning through large activation tensors can evict reusable weight tiles before arithmetic units can reuse them. Furthermore, specialized execution pipelines impose strict layout and data-type constraints that general caches cannot satisfy automatically. As illustrated in example [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^exmp-hw-acceleration-tensor-core-contract|11.3]], hardware matrix engines require specific alignments and memory layouts; a mismatch may require padding, conversion, or a different kernel whose efficiency must be checked.

**Example 11.3: Tensor Cores that never engage**

**Scenario**: An engineering team migrates a transformer workload to NVIDIA A100 GPUs expecting automatic Tensor Core acceleration, but profiling reveals Tensor Cores remain idle ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020a]]).

**Diagnosis**: The workload used shapes and data types that selected less efficient kernels rather than the intended Tensor Core path.

**Systems lesson**: Specialized paths have operator, precision, layout, and shape requirements. Libraries can often handle nonaligned dimensions through padding or alternative kernels, but reaching high utilization requires verifying which path was actually selected.

^exmp-hw-acceleration-tensor-core-contract

To avoid the eviction overhead and unpredictability of automatic caches, AI accelerators incorporate scratchpad memory. Unlike hardware caches, scratchpads are software-managed SRAM structures mapped directly into the core’s address space without tag directories or hardware replacement logic. The compiler or programmer explicitly controls when tensor tiles are loaded from external DRAM, how long they reside on-chip, and when updated values are written back. In convolutional models, scratchpads retain input feature maps and weight kernels across sliding receptive windows, eliminating redundant DRAM reads ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2017|Chen et al. 2017]]).

On NVIDIA GPUs, scratchpad memory is exposed as *shared memory*: a fast, programmer-controlled SRAM bank shared across all threads within a thread block. Custom kernels written in CUDA or Triton manage shared memory explicitly. FlashAttention, the IO-aware attention kernel, keeps its active tiles in shared memory rather than materializing the full ${S}{\times}{S}$ attention score matrix in off-chip HBM ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-dao2022|Dao et al. 2022]]). Its speedup comes from the HBM round trips it removes, not from fewer arithmetic operations.

↩︎ FlashAttention as an IO-aware attention kernel for training is established in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-flash-attention-ioaware-attention-optimization-3da0|FlashAttention: IO-aware attention optimization]]**.

#### Off-Chip Memory

^sec-hardware-acceleration-offchip-memory-ecdb

When tensor working sets exceed on-chip SRAM capacity, operands and parameters reside in device-local DRAM. Rather than sequential hierarchy levels, HBM, Graphics DDR (GDDR), and Low-Power DDR (LPDDR) represent alternative memory architectures engineered for distinct cost, bandwidth, and power envelopes. High-performance accelerators use HBM, which stacks DRAM dies inside the accelerator’s package and connects them to the accelerator die through a very wide bus (e.g., 1,024 to 8,192 bits). This wide bus delivers multi-terabyte-per-second bandwidth at lower clock frequencies and lower energy per bit than conventional DRAM, but requires complex packaging. Where that packaging is too costly, accelerators adopt GDDR, which uses narrower buses (e.g., 256 to 384 bits) driven at high pin speeds across standard circuit boards. Mobile and embedded accelerators use LPDDR, trading raw bandwidth for low operating voltage and reduced standby power.

When parameter and activation footprints exceed device-local DRAM capacity, the system must offload state to host DRAM (typically standard DDR). Accessing host memory requires crossing an I/O interconnect such as PCIe or another host link such as NVLink or Compute Express Link (CXL). Because PCIe bandwidth (tens of gigabytes per second) is one to two orders of magnitude lower than accelerator DRAM bandwidth, unmanaged offloading stalls arithmetic execution. Efficient runtimes mitigate this penalty by overlapping asynchronous direct memory access (DMA) copies with kernel execution, prefetching upcoming layer parameters while current layers compute.

At the base of the hierarchy, nonvolatile flash storage and solid-state drives (SSDs) provide persistent, multi-terabyte capacity for datasets and training checkpoints ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-narayanan2021|Narayanan et al. 2021]]). With read latencies measured in tens of microseconds and bus bandwidths capped at single-digit gigabytes per second, flash devices cannot participate directly in kernel execution. Checkpointing and data-loading pipelines treat flash storage as an asynchronous streaming source, staging batches through host DRAM into accelerator memory before computation begins.

The physical tiers of the memory hierarchy establish the latency floors and capacity ceilings of the accelerator, but advertised memory bandwidth is only a ceiling within them. Achievable bandwidth depends on access pattern, batching, locality, and the host interface that feeds the accelerator. Peak figures assume continuous, stride-1 coalesced access across all memory channels. Real neural network workloads deviate substantially from this ideal: transformer attention, convolution, and fully connected layers realize distinct fractions of peak bandwidth because their memory access strides, tiling dimensions, and operational reuse differ. A sufficiently large, coalesced weight stream can approach peak bandwidth even at small batch size. Batching instead reuses each loaded weight across more samples, raising arithmetic intensity as analyzed under the roofline model in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|section 11.6]]. Small or irregular kernels may lack enough concurrent accesses to approach the bandwidth ceiling, making memory latency and available parallelism part of the diagnosis.

### Host-Accelerator Communication

^sec-hardware-acceleration-hostaccelerator-communication-bb7a

An accelerator rated for hundreds of teraflops sits idle if its input tensors are still crawling across a host PCIe bus an order of magnitude slower than its on-package HBM. In discrete accelerator systems, the host CPU and the accelerator operate as separate computational domains joined by a peripheral bus. The host manages storage I/O, network streams, and runtime orchestration in system DRAM, while the accelerator executes dense mathematical kernels over device memory (HBM or GDDR). Because those two memories occupy separate physical address spaces, computation cannot begin until tensors cross the host-accelerator interconnect, making peripheral bus bandwidth and launch latency a hard limit on end-to-end speedup.

[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^fig-host-accelerator-data-movement|Figure 9]] sequences the four-stage execution trace across host and device lifelines. Step 1 copies input data across PCIe to device memory via DMA. Step 2 dispatches kernel instructions from the CPU. Step 3 executes parallel core compute with local writeback. Step 4 copies results back to host memory. In a naive synchronous execution model, every transfer step sits directly on the critical path, stalling either the host or the accelerator until each memory transaction finishes.

![[90 Assets/Volume I/11 Hw Acceleration/Generated Figure c028b0ced7.svg]]

Figure 9: **Host-Accelerator Data Transfer Sequence**: Four-step execution flow between CPU host and GPU device: (1) copying input data over PCIe, (2) issuing kernel instructions, (3) GPU compute, and (4) transferring results back to host memory. Low PCIe bandwidth and host dispatch latencies can easily dominate runtime unless kernel compute time exceeds data transfer overhead.

^fig-host-accelerator-data-movement

The end-to-end latency of a kernel launch decomposes into transfer time, queue dispatch overhead, and arithmetic execution time. When tensor transfers are small or frequent, the fixed overhead of driver submission and bus round trips dominates runtime. When transfers are large, the low bandwidth of PCIe relative to on-package HBM creates a sustained I/O bottleneck. In D·A·M terms, the Machine boundary between host and accelerator forces the Algorithm to maximize arithmetic reuse on the device once tensors arrive.

#### Node-Level Interconnect Topology

^sec-hardware-acceleration-nodelevel-interconnect-topology-b45b

Within a single machine, how bits move between GPUs and the CPU sets the next ceiling. In the 1–8 GPU regime, two kinds of link carry that traffic. High-speed intra-node interconnects such as NVLink carry GPU-to-GPU traffic, and PCIe links carry data between the CPU and each GPU. These links form a **bandwidth taper**: data-movement speed falls at each step away from the compute units, from on-package HBM through the GPU-to-GPU NVLink bridge down to the host PCIe link. The PCIe step is much slower than the accelerator-local memory and inter-GPU fabric, so any data path that touches the CPU can become a performance hazard. Keeping accelerator-to-accelerator traffic off that link is the reason NVLink exists ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020nvlink|NVIDIA Corporation 2020b]]). A typical AI server is therefore not a flat mesh of connected devices, and optimizing data movement starts from its physical topology.

![[90 Assets/Volume I/11 Hw Acceleration/Vol1 Hw Acceleration Margin 002 d22114ccc7.svg]]

*Vertical log-scale ladder of violet bandwidth bars, widest at top: HBM, then NVLink, then PCIe, down to a narrow network bar at the bottom.*

*Bandwidth tapers steeply as data moves farther from the accelerator.*

Within a multi-accelerator server node, two interconnect tiers define this bandwidth taper below device memory:

1.  **Device-device interconnect (NVLink/Infinity Fabric)**: Modern multi-GPU nodes use specialized high-speed bridges like NVLink[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn20|²⁰]] to connect accelerators directly, bypassing the host CPU. Bandwidth ranges from 600 GB/s to 900 GB/s per GPU ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020nvlink|NVIDIA Corporation 2020b]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-choquette2023|Choquette 2023]]). This link matters whenever tensors must move between accelerators within one server, including model partitioning, activation exchange, and gradient synchronization during training. The architectural principle is the boundary: traffic that stays on the accelerator fabric is far cheaper than traffic that falls back through the host.
2.  **Host-device interconnect (PCIe)**: The link between the CPU and the accelerator. Bandwidth ranges from 32 to 64 GB/s (PCIe Gen4/Gen5). Host-staged training data can bottleneck here, although resident data, direct storage or network I/O, and coherent accelerator links can use other paths. Multi-GPU servers may also provide multiple PCIe links rather than a single shared 64 GB/s path.

A third tier, the network link from one server to others, continues the taper beyond the node ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.10 Beyond One Accelerator#^sec-hardware-acceleration-multichip-scaling-c649|section 11.9]]). Together the levels produce a characteristic bandwidth taper:

$$
\begin{aligned} \text{HBM (3350 GB/s)} &\gg \text{NVLink (900 GB/s)} \\ &\gg \text{PCIe (64 GB/s)} > \text{Network (50 GB/s)} \end{aligned}
$$

The taper extends the memory hierarchy’s ordering across the whole machine, and the result is the operand-supply hierarchy that sets a kernel’s delivered throughput. Registers keep pace with the array because each operand they hold is reused many times. On-chip SRAM refills them at tens of terabytes per second, HBM at terabytes per second, host memory over PCIe at tens of gigabytes per second, and flash storage at single-digit gigabytes per second. System efficiency depends on keeping tensors on the highest-bandwidth links available, so the measure that matters for a kernel is the traffic it sends across each boundary, not merely whether its data fits in a tier. Because PCIe and network links offer orders of magnitude less bandwidth and higher latency than on-package memory, placement and scheduling must minimize crossings across these boundaries.

#### Transfer Optimization

^sec-hardware-acceleration-transfer-optimization-85a8

The standard remedy for transfer overhead is the asynchronous pipeline of **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.06 Abstraction Tensors, Devices, and Operations#^sec-ml-frameworks-device-memory-management-9404|Devices and memory]]**. Batches staged in pinned (page-locked) host memory are copied by dedicated DMA engines while the accelerator computes on the previous batch. This double buffering conceals transfer latency behind arithmetic runtime whenever computation time exceeds transfer time (${T_{\text{compute}}} \ge {T_{\text{transfer}}}$). When compute duration is too short to amortize the transfer, execution remains bus bound and the compute units stall.

↩︎ The feeding problem, in which data delivery fails to keep pace with compute throughput, is established in **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|The feeding problem]]**.

Unified Memory takes the opposite approach, presenting a single virtual address space that spans host DRAM and device HBM while the driver migrates pages on demand whenever either processor touches an address. On-demand migration removes staging code at the cost of predictability, because each page fault stalls execution and scattered accesses can thrash pages across the PCIe bus. High-throughput production workloads therefore rely on explicit, pipelined DMA transfers and reserve Unified Memory for prototyping or for applications where programmer productivity outweighs sustained hardware utilization. Once tensors reside on the accelerator, the model’s own architecture determines whether weights, activations, or lookup tables dominate the device memory hierarchy.

### Model Memory Pressure

^sec-hardware-acceleration-model-memory-pressure-f95e

An optimization that relieves memory pressure for one model family can leave another untouched: caching weights helps nothing when ResNet-50’s early convolutions spill large activation maps to DRAM, and spatial activation tiling helps nothing when GPT-2 decode streams gigabytes of weights for a single token. Model architecture determines which memory term dominates. The architectural reasons each family stresses memory as it does were traced in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^sec-network-architectures-understanding-arithmetic-intensity-ade5|Arithmetic intensity across workloads]]**; the hardware consequence differs by family, and the lighthouse models of **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^tbl-lighthouse-examples|Lighthouse Models as Reference Workloads]]** cover the cases.

Dense layers, the multilayer perceptron (MLP) blocks that every family contains, are bound by weight traffic at small batch. At batch size ${B}= 1$, each parameter loaded from off-chip memory serves a single multiply-accumulate operation (often $\le 1\text{ FLOP/byte}$), so execution sits on the bandwidth slope; batching reuses each loaded weight across ${B}$ inputs and moves the layer toward the compute ceiling. Dense weight matrices regularly exceed the tens of megabytes of on-chip SRAM, so parameters reside in HBM and stream through tiles that the accelerator double-buffers into SRAM ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2017|Chen et al. 2017]]). The host link enters the critical path only when inputs stream from the host or when the model exceeds device memory.

Convolutional layers, the core of ResNet-50, place their memory pressure on activations rather than weights, because each small filter is reused at every spatial position while the feature maps it reads stay large. Early layers therefore carry compact parameter tensors but large activation maps that exceed on-chip SRAM, and unoptimized layer-by-layer execution spills those maps to device DRAM. Spatial tiling keeps activation tiles, with their overlapping boundary pixels, in on-chip buffers so adjacent convolutions consume them without refetching ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-chen2017|Chen et al. 2017]]).

Transformers such as GPT-2 stress both capacity and bandwidth, differently in each phase. During training and prefill, standard attention materializes an ${S}{\times}{S}$ score matrix for sequence length ${S}$ and moves $\mathcal{O}({S}^2)$ bytes through HBM; IO-aware kernels such as FlashAttention ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-dao2022|Dao et al. 2022]]) keep those tiles in on-chip SRAM instead (**[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-flash-attention-ioaware-attention-optimization-3da0|FlashAttention: IO-aware attention optimization]]**). During autoregressive decode, each generated token reads the weights and the accumulated key-value (KV) cache from HBM for a vector-matrix product, which ties generation speed to memory bandwidth.

↩︎ How much memory one request’s KV cache claims as its sequence grows is established in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^sec-network-architectures-inference-memory-bandwidth-wall-98d1|Autoregressive decoding]]**.

Two other lighthouses stress memory in other ways. DLRM’s sparse embedding lookups stress random-access bandwidth rather than dense compute, and MobileNetV2’s depthwise convolutions trade arithmetic intensity for a smaller parameter footprint, so on an H100 both reappear as memory-bound rows in the roofline operations table ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^tbl-roofline-operations|table 7]]); on the phone NPU it was built for, MobileNetV2 is compute bound ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.11 Heterogeneous SoC Design#^sec-hardware-acceleration-heterogeneous-soc-ai-acceleration-b1bb|section 11.10]]). Accelerators answer these divergent demands with the tiered hierarchy. On-chip SRAM captures high-reuse activations and tiled matrix blocks at tens of terabytes per second, HBM stages large weight tensors and sequence state, and NVLink-class links carry tensors between accelerators when a model exceeds one device, avoiding the narrower host PCIe bus. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^tbl-mapping-strategies|Table 14]] later pairs each family’s memory profile with the mapping that answers it.

A reference off-chip DRAM access costs far more energy per event than arithmetic ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.03 Hardware Specialization#^fig-energy-hierarchy|figure 4]]), so reducing repeated external accesses improves efficiency. Deciding whether a given kernel is limited by compute throughput or by memory bandwidth, however, requires an analytical boundary. The roofline model supplies that boundary by comparing operational intensity against hardware performance limits, so that optimization effort targets the resource that actually limits performance.
