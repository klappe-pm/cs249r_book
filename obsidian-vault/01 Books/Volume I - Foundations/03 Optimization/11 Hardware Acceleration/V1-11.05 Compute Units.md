# V1-11.05 Compute Units

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration|V1-11 Hardware Acceleration]]

^sec-hardware-acceleration-compute-units-execution-models-f406

Applying ReLU to a 512-element vector shows why execution models matter. The operation is simple, but throughput depends on whether the hardware treats those 512 comparisons as scalar instructions, as lanes of a single instruction, multiple data (SIMD) unit, as GPU threads, or as elements of a tile that one tile-level program processes together. Modern AI processors package the three compute primitives into distinct execution units: vector units for vector work, matrix units such as Tensor Cores and systolic arrays for matrix work, and special function units for nonlinear functions. They then group those units into processing elements. That organization defines how computations are structured and exposed to programmers, and it explains why theoretical capability and delivered throughput diverge.

The packaging follows reuse per operand. For the reference low-precision operations, reading an operand from a register file and moving it across on-chip wires can cost more energy than the arithmetic itself, so each primitive goes to the unit whose dataflow supplies the reuse it offers. In D·A·M terms, this partition maps algorithmic primitives onto machine execution paths. Routing dense matrix multiplications through vector pipelines saturates register-file read ports, because every multiply-accumulate on a vector lane reads fresh operands from the register file ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-tensor-cores-771f|section 11.4.2]]), and collapses throughput to a small fraction of peak. Routing low-intensity elementwise work through matrix arrays fails the other way, leaving their lanes idle.

### From SIMD Lanes to SIMT Threads

^sec-hardware-acceleration-evolution-simd-simt-architectures-e1fd

Even a wide CPU vector unit stalls when streaming through gigabytes of tensor data: cache misses freeze the pipeline for hundreds of cycles waiting on main memory, the instruction reorder buffer fills, and the SIMD lanes sit empty. The vector path of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^sec-hardware-acceleration-vector-operations-19bf|section 11.3.1]] follows Flynn’s SIMD execution model, which amortizes instruction fetch and decode by issuing a single decoded instruction across multiple data elements packed into wide vector registers ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-flynn1966|Flynn 1966]]). A 512-bit SIMD register processes sixteen 32-bit floating-point values per instruction. The same idea appears in fixed-width CPU vector extensions, Arm’s length-agnostic Scalable Vector Extension (SVE) ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-stephens2017|Stephens et al. 2017]]), and two-dimensional tile extensions such as Intel’s Advanced Matrix Extensions (AMX) ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-intel2021amx|Intel Corporation 2021a]]). Even so, those wide registers still live inside a CPU core built around branch predictors, out-of-order execution logic, and deep cache hierarchies for a few sequential threads. Conditional branching within a vector also requires evaluating divergent paths under bitmasks, further cutting useful lane utilization.

Architectures built on **single instruction, multiple threads (SIMT)** execution resolve these bottlenecks by decoupling the logical programming abstraction from physical hardware execution ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-lindholm2008|Lindholm et al. 2008]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nickolls2008|Nickolls et al. 2008]]). Instead of requiring the programmer to pack data into explicit vector registers, SIMT exposes an execution model of independent scalar threads. In GPU architectures, each streaming multiprocessor (SM)[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn11|¹¹]] coordinates thousands of concurrent threads. Hardware warp schedulers group these threads into warps, the 32-thread scheduling groups (wavefronts in AMD architectures). Every thread in a warp executes a common instruction in lockstep across parallel ALUs.

This lockstep execution introduces a constraint known as **warp divergence**. When threads within a single warp take different paths through a conditional branch, the hardware must execute both required paths sequentially, masking off the inactive lanes during each path. This serialization reduces useful lane utilization and increases execution time, which is why performance-critical ML kernels avoid divergent branching in favor of uniform or predicated control flow.

↩︎ Warps as the 32-thread unit in which GPUs schedule tensor kernels are established in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^sec-model-training-compute-operations-83ee|Compute operations]]**.

Rather than relying on large caches to reduce memory latency, GPUs hide latency through extensive thread-level concurrency. An SM statically partitions an on-chip register file across all active threads, eliminating context-saving overhead. When one warp stalls waiting hundreds of cycles for an off-chip memory fetch, the warp scheduler selects and issues instructions from another ready warp on the very next cycle.

In the baseline matrix multiplication kernel of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^lst-cuda-simt-920cd6d8|listing 12]], each scalar thread computes one output element. CUDA organizes the threads into a grid of thread blocks, each block being the group of threads launched together on one streaming multiprocessor. A thread derives its row and column from its block’s position in the grid and its own position within the block (`blockIdx`, `blockDim`, and `threadIdx`).

``` c
__global__ void matrix_multiply(float* C, float* A, float*
                                B, int N) {  // CUDA kernel
    // Each thread processes one output element
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    float sum = 0.0f;
    for (int k = 0; k < N; k++) {
        // Threads in a warp execute in parallel
        sum += A[row * N + k] * B[k * N + col];
    }
    C[row * N + col] = sum;
}
```

Listing 12: **SIMT Execution**: Each thread processes a unique output element in parallel, demonstrating how SIMT enables efficient matrix multiplication on GPUs.

^lst-cuda-simt-920cd6d8

In [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^lst-cuda-simt-920cd6d8|listing 12]], the CUDA[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn12|¹²]] kernel assigns one output element `C[row * N + col]` to each thread. Neighboring threads in a warp compute neighboring columns, so their loads of `B` fall on consecutive addresses that the hardware combines into a few wide memory transactions, and the element of `A` they all need is fetched once and shared.

However, this naive kernel runs into the arithmetic intensity law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-arithmetic-intensity|6]]). Because each inner-loop iteration performs only two floating-point operations while reloading operands from global memory without on-chip SRAM staging, the kernel remains severely memory bound. Furthermore, executing dense matrix multiplication on scalar SIMT ALUs requires one instruction fetch, decode, and issue cycle for every multiply-accumulate, saturating register file read ports. Overcoming this machine bottleneck requires moving beyond vector-of-scalars execution to specialized two-dimensional matrix units.

### Tensor Cores

^sec-hardware-acceleration-tensor-cores-771f

For a single transformer attention head over a 2,048-token sequence with 64-dimensional embeddings, the ${\mathbf{Q}}\times {\mathbf{K}}^T$ product multiplies a $2048{\times}64$ matrix by a $64{\times}2048$ matrix. That is roughly 268.4M MACs, or 536.9 MFLOP when the multiply and add are counted separately. On a scalar processor executing one FLOP per cycle at 2 GHz, that single attention head would take 268.4 ms. Even on GPU SIMT lanes, issuing a separate scalar fused multiply-add for every element pair saturates instruction-issue bandwidth and register-file read ports. Dedicated matrix engines remove both bottlenecks by organizing work around multidimensional tiles and reusing fetched operands across many multiply-accumulate operations on chip. NVIDIA GPUs expose Tensor Cores, the reduced-precision matrix units,[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn13|¹³]] whereas Google TPUs use matrix units built around systolic arrays. Both execute tiled matrix multiplication and accumulation.[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn14|¹⁴]]

Assume, for illustration, that the Tensor Cores of a single streaming multiprocessor complete that 2,048-token attention head in 0.5 ms, an implied rate of about 1.1 TFLOP/s and a small slice of a full GPU’s tensor peak. The tiled path is then roughly 536.9× faster than the scalar baseline, and that speedup comes not from a higher clock frequency but from hardwiring tile-level data reuse into the execution datapath. Whether a workload reaches that rate depends on tile reuse, matrix shape, numeric precision, and memory delivery.

In NVIDIA Parallel Thread Execution (PTX), Tensor Core operations are invoked through warp-synchronous matrix instructions (`mma.sync`).[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn15|¹⁵]] The mnemonic encodes the tile geometry and data types: `.m16n8k16` gives the tile dimensions (${M}=16, {N}=8, {K}=16$), and the trailing types (`.f32.f16.f16.f32`) declare FP16 inputs accumulated into an FP32 destination. In [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^lst-tensor-core-op-aeb713a1|listing 13]], all 32 threads in a warp execute this single instruction collectively to compute the tile product ${\mathbf{D}}= {\mathbf{A}}{\mathbf{B}}+ {\mathbf{C}}$.

``` c
Tensor Core Operation (example GPU PTX):
mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32
  {d0,d1,d2,d3},     // Destination registers
  {a0,a1,a2,a3},     // Source matrix A
  {b0,b1},           // Source matrix B
  {c0,c1,c2,c3};     // Accumulator
```

Listing 13: **Tensor Core Operation**: Matrix multiplications are performed in parallel across entire matrix blocks, optimizing computational efficiency for neural network training.

^lst-tensor-core-op-aeb713a1

Here inputs ${\mathbf{A}}$ ($16{\times}16$) and ${\mathbf{B}}$ ($16{\times}8$) are FP16, while accumulator ${\mathbf{C}}$ and destination ${\mathbf{D}}$ ($16{\times}8$) are FP32. The register operands in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^lst-tensor-core-op-aeb713a1|listing 13]] represent the per-thread fragment held by each of the 32 threads in the warp rather than the entire matrix tile. Because each 32-bit GPU register packs two 16-bit FP16 values, a single thread’s four source registers `{a0,a1,a2,a3}` hold 8 FP16 elements of ${\mathbf{A}}$, so all 32 threads together supply the $32 \times 8 = 256$ elements of the $16{\times}16$ tile. Similarly, `{b0,b1}` holds 4 FP16 elements per thread ($32 \times 4 = 128$ elements for the $16{\times}8$ tile ${\mathbf{B}}$), and `{c0,c1,c2,c3}` holds four 32-bit FP32 accumulator elements per thread ($32 \times 4 = 128$ elements for the $16{\times}8$ tile ${\mathbf{C}}$).

A single warp instruction evaluates all $16 \times 8 \times 16 = 2{,}048$ multiply-accumulate operations that would otherwise require 64 separate scalar fused multiply-add (`fma`) instructions per thread. This tile-level execution relieves two bottlenecks of conventional SIMT pipelines: instruction-issue bandwidth and register-file read-port contention. In scalar SIMT execution, every `fma` reads its source operands fresh from the register file, whereas the Tensor Core reads each thread’s register fragment once and reuses every fetched element across multiple inner-product steps inside the matrix datapath.

Design priorities determine how matrix engines appear in different processor families. GPU Tensor Cores preserve programmability while accelerating general-purpose deep learning kernels. TPU-style designs use large-scale matrix units arranged in systolic arrays to maximize sustained training throughput on dense tensor kernels. Mobile NPUs[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn16|¹⁶]] shrink the same idea into low-power inference blocks, while server CPUs add matrix instruction extensions (AMX-class tiles) for inference and mixed workloads. Each version keeps a different amount of flexibility in exchange for removing a different amount of data movement.

Tensor Cores also changed how each accelerator generation states its peak. Successive generations combined more matrix units with narrower formats (FP16, then INT8, FP8, and FP4) and, from Ampere onward, a structured-sparsity path. As a result, the headline rating rose by more than three orders of magnitude between 2012 and 2024 while measuring a different precision at almost every step ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2017gpu|NVIDIA Corporation 2017]], [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|2020a]], [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2024blackwell|2024]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-choquette2023|Choquette 2023]]). A peak quoted without its precision and sparsity assumption therefore says little about a given workload. The generation-by-generation ratings, with their precision-specific peaks, bandwidths, and power limits, are collected with the other dated specifications in **[[05 Reference/Volume I - Foundations/V1 System Assumptions#^sec-appdx-assumptions-accelerator-matrix-c4d0|Master accelerator matrix]]**. Whatever the format, a Tensor Core retires a tile per instruction only when its operands are already nearby, so accelerators never deploy matrix units on their own. The next level of the execution hierarchy exists to supply that proximity.

### Processing Elements

^sec-hardware-acceleration-processing-elements-daa1

High-throughput matrix units cannot be fed directly from global memory: off-chip DRAM and even on-package HBM lack the bandwidth and low latency required to stream fresh operands into dense arithmetic arrays on every cycle. Accelerators resolve this bandwidth deficit by grouping Tensor Cores, vector units, and special function units alongside high-bandwidth register files and scratchpad SRAM inside modular processing elements (PEs). Staging operands inside the PE keeps data adjacent to the functional units, amortizing the latency and energy cost of external memory accesses across repeated arithmetic reuse. The term is used at two scales in this chapter. Here a PE is a tile or core that bundles several units with local memory, the role a streaming multiprocessor plays in a GPU and a core plays in a TPU. Inside a systolic array ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-systolic-arrays-6fa8|section 11.4.4]]), a PE is a single multiply-accumulate cell in the grid.

Processing element design varies because each architecture chooses a different balance between compute density, local memory capacity, and interconnect distance. Graphcore’s Intelligence Processing Unit (IPU), for example, distributes computation across tiles backed by dedicated local SRAM ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-Graphcore2020|Graphcore 2020]]). Retaining an operand in one tile saves external traffic, but a consumer on another tile still requires an interconnect transfer. Local storage therefore shifts the mapping problem toward keeping repeated consumers close to their operands.

Across these designs, the limiting physical constraint is compute density versus data locality: silicon area dedicated to arithmetic units cannot simultaneously house SRAM storage or routing wires. Packing more execution units raises peak theoretical FLOP/s, but those units idle if memory bandwidth and routing channels cannot deliver operands. A processing element’s delivered efficiency therefore depends as much on its local memory hierarchy and interconnect strategy as on its raw arithmetic capability. Systolic arrays push this locality principle to its limit: rather than staging operands in a processing element’s local memory and fetching them again for each operation, they pass operands directly from one processing element to its neighbor.

### Systolic Arrays

^sec-hardware-acceleration-systolic-arrays-6fa8

Even when operands sit in local SRAM or registers, reading two inputs and writing a partial sum back to a central register file on every multiply-accumulate burns wire energy and port bandwidth that limit how many arithmetic cells a chip can pack. While Tensor Cores amortize register access across instruction-driven micro-tiles, systolic arrays remove intermediate register-file round-trips altogether by wiring hundreds or thousands of processing elements into two-dimensional spatial grids. In a classic 2D systolic array, data streams rhythmically through adjacent cells on regular clock cycles: inputs march horizontally, partial sums accumulate vertically, and stationary weights remain anchored in place. Because every value passed from one processing element to its immediate neighbor participates in an arithmetic operation without returning to a register file or SRAM buffer, nearest-neighbor wires replace memory reads. An operand loaded once at the array edge contributes to ${N}$ sequential multiply-accumulate steps across an ${N} \times {N}$ grid. Each memory fetch therefore serves as many operations as the array is wide, which cuts memory traffic by roughly that factor. Counting DRAM accesses per multiply-accumulate with and without neighbor-to-neighbor passing makes the saving concrete.

**Napkin Math 11.1: The energy advantage of pulsing data**

**Scenario**: The systolic architecture improves energy efficiency by keeping operands local as work pulses through the array; the “Systolic” (heartbeat) metaphor reflects this benefit of reusing operands locally. This worked model compares systolic dataflow with a naive implementation that streams every operand through DRAM:

1.  **DRAM-streaming baseline**: Loads ${\mathbf{A}}$, ${\mathbf{B}}$, and the running ${\mathbf{C}}$, computes ${\mathbf{A}}\times {\mathbf{B}}+ {\mathbf{C}}$, and writes ${\mathbf{C}}$ back without cache or register reuse.
    - **Data movement**: 3 loads + 1 write = 4 DRAM accesses (per operation).
    - **Energy**: ≈ 4 $\times$ 640 pJ + 1 pJ (compute) = 2561 pJ/op.
2.  **Systolic array** (128 $\times$ 128): Loads ${\mathbf{A}}$ and ${\mathbf{B}}$ once at the edges. Data “pulses” through 128 processing elements.
    - **Data movement**: 2 loads per 128 operations = 0.016 DRAM accesses (per operation).
    - **Energy**: ≈ 0.016 $\times$ 640 pJ + 1 pJ (compute) ≈ 11 pJ/op.

**Systems insight**: Under this deliberately naive DRAM-streaming baseline, the worked model gives the systolic array a 232.8× energy advantage. The ratio measures locality, not an inherent gap between vector and systolic arithmetic.

- Concretely, a $128{\times}128$ array can sustain 16,384 MACs/cycle with a large energy saving by pulsing data through processing elements instead of repeatedly loading it from DRAM ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-horowitz2014|Horowitz 2014]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-jouppi2023|Jouppi et al. 2023]]).
- This locality lets dense arrays sustain many simultaneous MAC operations without paying a DRAM access for every operation.
- **Limitation**: The comparison assumes no effective reuse in the baseline and full reuse across the array. Caches, register blocking, array underutilization, and other dataflows change the ratio substantially.

Kung and Leiserson[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn17|¹⁷]] ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-kung1979systolic|Kung and Leiserson 1979]]) first introduced systolic arrays, formalizing their use in parallel computing architectures for efficient matrix operations ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-kung1982|Kung 1982]]). Unlike general-purpose execution units, systolic arrays exploit spatial and temporal locality by reusing operands as they propagate through the grid. Google’s TPU exemplifies this architectural approach: in the TPU v4, a $128{\times}128$ systolic array of multiply-accumulate units processes matrix operations by streaming data through the array in a pipelined manner ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-jouppi2023|Jouppi et al. 2023]]).

[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^fig-systolic-array|Figure 5]] traces the 2D pipelined dataflow of such an array: a control unit stages operands into input FIFO buffers that stream activation data horizontally across the processing grid, while partial sums accumulate vertically down columns into the bottom adder-accumulator chain. Each processing element performs one multiply-accumulate per cycle and passes its operands to its neighbors, so a value loaded once is reused across an entire row or column rather than refetched from memory.

![[90 Assets/Volume I/11 Hw Acceleration/Generated Figure e22fc11152.svg]]

Figure 5: **Systolic Array Dataflow Architecture**: A pipelined grid of processing elements (PEs) passes operands and partial results between neighbors. The illustrated movement is one possible matrix-multiplication dataflow; designs choose which operand or partial sum remains stationary to match reuse, buffers, and tensor shape. Utilization depends on mapping and dimensions.

^fig-systolic-array

A 128 $\times$ 128 systolic array capable of 16,384 operations per cycle requires a continuous operand stream to maintain utilization. On-chip buffers feed activations and weights to the array edges and are replenished from off-chip memory as needed; reuse within the array avoids fetching every operand from HBM each cycle. The TPU v4’s 1,200 GB/s HBM2 bandwidth helps sustain this stream, but off-chip bandwidth can still limit models whose working sets and reuse patterns exceed on-chip capacity.

**Systems Perspective 11.1: Matching architecture to workload**

**Challenge**: Systolic arrays must choose which operand to keep stationary in processing-element registers (weights, inputs, or partial sums), and that choice hard-codes the hardware’s preference for certain model types. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-dataflow-optimization-strategies-ce52|Section 11.7.3]] develops the three options as a general mapping decision.

No single accelerator architecture suits every workload. A chip that keeps weights stationary in its processing elements (like early TPUs) excels at convolutional neural networks (CNNs), where filter weights are small and reused across many image patches. That same architecture stalls on large language model (LLM) autoregressive inference at batch size 1, where the entire weight matrix must be read from off-chip memory once per generated token with zero batch reuse. No choice of stationary operand recovers reuse that does not exist; the levers are batching, lower-precision weights, and memory bandwidth.

### Numerics and Sparsity on the Datapath

^sec-hardware-acceleration-numerics-ai-acceleration-f7be

Storing weights in INT8 or pruning half of them to zero shrinks a checkpoint on disk. If the accelerator lacks a datapath that multiplies narrow integers or skips zero weights in silicon, however, the runtime must unpack those weights back to dense floating point, and the layer executes no faster than the baseline. Number formats and structured sparsity patterns were defined in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression#^sec-model-compression|Model Compression]]**. The hardware datapath that executes them is what turns them into wall-clock speedups, including the speedup in the ResNet-50 INT8 profile. Systolic arrays and Tensor Cores often provision higher multiply-accumulate capacity for narrower formats such as FP16, BF16, INT8, and FP8, while halving or quartering the bytes moved per value relative to FP32. That speedup is not automatic: it requires a supported kernel, matching input and accumulation formats, and enough parallel work to keep the narrower datapath full without hitting another bottleneck.

#### Precision Trade-Offs

^sec-hardware-acceleration-precision-tradeoffs-8fa8

Lower precision is not free, for the range-and-precision reasons that forced loss scaling in mixed-precision training and that **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-numerical-format-comparison-8fa2|Numerical formats]]** compared format by format. FP16 trades dynamic range for significand bits, BF16 keeps FP32’s exponent range at the cost of precision, and INT8 has no exponent at all, so its usable range depends on scale, zero-point, and clipping choices. For the hardware designer, those numerical properties set the silicon cost of each datapath. A narrower format needs a smaller multiplier and moves fewer bytes, but accumulation usually stays wider, as the FP32 accumulator of the Tensor Core instruction in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^lst-tensor-core-op-aeb713a1|listing 13]] shows, so part of the area saved in the multipliers is spent keeping sums accurate.

↩︎ The software side of mixed-precision training, including loss scaling, is established in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-mixedprecision-training-9218|Mixed-precision training]]**.

Precision support is integrated into execution units and memory paths. SIMD and SIMT lanes may support several scalar formats, while Tensor Cores ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-tensor-cores-771f|section 11.4.2]]) and systolic units ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-systolic-arrays-6fa8|section 11.4.4]]) expose architecture-specific input and accumulation combinations. Changing storage alone may reduce bytes without producing the advertised arithmetic speedup, because the model must select a kernel that uses the efficient path. Converting FP32 weights to INT8 cuts weight traffic by 4$\times$. Whether that moves a kernel from bandwidth bound to compute bound depends on the operation’s original arithmetic intensity, the ridge point of the accelerator’s INT8 path, and the overhead of quantization and dequantization (**[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^eq-dequantize|equation 10.4]]**). Tiling and dataflow, not precision itself, determine reuse, while conversion, scaling, or fallback overhead can offset part of the gain. A format is useful only when the kernel and numerical policy can employ it safely.

#### Mixed-Precision Computing

^sec-hardware-acceleration-mixedprecision-computing-656f

Modern AI accelerators support mixed-precision execution, in which different stages of one computation use different numerical formats. The training recipe (FP16 or BF16 multiplications with FP32 accumulation) ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-micikevicius2017mixed|Micikevicius et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-mellempudi2019mixed|Mellempudi et al. 2019]]) is developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-mixedprecision-training-9218|Mixed-precision training]]**, and the inference recipe (INT8 or INT4 weights with selected activations kept wider) in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-quantization-precision-cd46|Numerical Precision: Changing How Values Are Stored]]**. The hardware’s part is to execute several formats side by side, with an accumulator wide enough for each.

The shift toward precision diversity is evident in the evolution of AI hardware. Early architectures such as NVIDIA Volta provided Tensor Core support only for FP16, whereas later architectures, including Turing and Ampere, added integer formats and then TF32, which keeps FP32’s exponent range but carries an FP16-length mantissa, alongside BF16 ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia-tf32-2b878de3|NVIDIA 2020b]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2017gpu|NVIDIA Corporation 2017]], [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2018t4|2018]], [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|2020a]]). The generation-by-generation list of supported formats belongs with the other dated specifications in **[[05 Reference/Volume I - Foundations/V1 System Assumptions#^sec-appdx-system-assumptions|System Assumptions]]**; the durable observation is the direction of the trend, toward more formats, each narrower than the last.

The precision format used in hardware design has cascading implications across the entire system. Reducing an operand from FP32 to FP16 halves its value bytes. When those values dominate traffic, the reduction can substantially lower movement energy; the full energy budget still includes access counts, arithmetic, and other device activity ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-horowitz2014|Horowitz 2014]]). Simultaneously, Tensor Cores and systolic arrays can pack more lower-precision multiply-accumulate units into the same silicon area, raising peak throughput ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-dally2021|Dally et al. 2021]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-dally2023|Dally 2023]]). Lower-precision integer arithmetic also consumes less energy than FP32 in representative technology studies ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-horowitz2014|Horowitz 2014]]), and the inference-focused TPU v1 was built around 8-bit multiply units ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-jouppi2017|Jouppi et al. 2017]]). Reduced precision can therefore cut value traffic *and* raise the supported compute ceiling at the same time.

Each narrower format raises the arithmetic ceiling again. The H100 advertises 989 TFLOP/s on its dense FP16 tensor path and 1,979 TFLOP/s on its FP8 path, an 8-bit floating-point format introduced for training and inference ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-choquette2023|Choquette 2023]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-blankevoort2022|Kuzmin et al. 2022]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-micikevicius2022fp8|Micikevicius et al. 2022]]). NVIDIA’s Blackwell (B200) architecture extends this trajectory with an FP4 tensor datapath (a 4-bit floating-point format that, unlike INT4, spends some of its four bits on an exponent and so trades uniform spacing for range). The datapath is rated at up to 9 PFLOP/s dense or 18 PFLOP/s sparse peak throughput per chip ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia2024blackwell|NVIDIA Corporation 2024]]). Reaching those theoretical ceilings requires numerical representations, kernel implementations, and sparsity patterns that align exactly with the specialized hardware paths. Narrower numerical formats expand the available design space, but numerical stability and dynamic range requirements dictate whether a workload can safely use FP4.

#### N:M Structured Sparsity Mechanics

^sec-hardware-acceleration-nm-structured-sparsity-mechanics-9a71

The sparse rating in that comparison depends on one more datapath feature, one that skips zeros only when they follow a fixed pattern. While unstructured pruning reduces model parameter counts, it rarely translates to hardware speedup because arbitrary nonzero placements destroy memory locality. Hardware accelerators resolve this with N:M structured sparsity,[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn18|¹⁸]] the pruning constraint from model compression that keeps exactly ${n_{\text{keep}}}$ of every ${m_{\text{group}}}$ contiguous values along the reduction dimension nonzero, so memory access stays uniform and indexing predictable across parallel execution units.

↩︎ The N:M and 2:4 structured sparsity patterns and their compressed storage are established in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-structured-pruning-9692|Structured pruning]]**.

Parallel hardware needs this regularity because of how sparse matrices are encoded. Indexed formats such as compressed sparse row (CSR) locate each nonzero through an index array, so the matching activations sit at scattered addresses and rows with different nonzero counts leave parallel lanes unevenly loaded. Whether such a format saves bytes or time at a given sparsity, its break-even point, is derived with the formats themselves in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^sec-model-compression-sparse-break-even-7e4a|Storage and execution break-even]]**. The datapath question here is how regular the retained values must be for parallel hardware to use them.

↪ The CSR storage format is collected for reference in **[[05 Reference/Volume I - Foundations/V1 Algorithm Foundations#^sec-appdx-algorithm-foundations-sparse-matrix-formats-0bd0|Sparse matrix formats]]**.

NVIDIA’s Sparse Tensor Cores implement the 2:4 instance of the N:M pattern ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020a]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia-cusparse-block-9fdec588|NVIDIA 2020a]]). Their input is the compressed 2:4 encoding, the two retained values of each group plus a 4-bit metadata tag (2 bits per value) recording their original positions. During execution, the memory hierarchy transfers only the compressed weights and their metadata, halving the weight-value payload while adding metadata traffic; total transferred bytes therefore fall by less than half before other overheads. Inside the Sparse Tensor Core, the metadata selects the two activations that match the retained weights in each group of four, so only half the multiplications are performed. Because the hardware computes only on the nonzeros while streaming compressed weights, this design doubles the peak arithmetic instruction throughput. The result is an advertised 2$\times$ tensor-math speedup over dense operations when weights are fine-tuned to satisfy the pattern ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^fig-2-4-gemm|figure 6]]).

![[90 Assets/Volume I/11 Hw Acceleration/Generated Figure 1c09e50aed.svg]]

Figure 6: **2:4 Structured Sparsity GEMM**: Left: standard dense matrix multiplication on Tensor Cores using full 8-element rows. Right: 2:4 sparse multiplication retains two nonzeros in every group of four and uses compact indices to select matching elements from the dense right-hand matrix. A supported sparse inner loop can halve the multiplied values, although metadata handling and the rest of the execution path determine end-to-end speedup. ^fig-2-4-gemm

The 2:4 pattern saves about half of the weight bytes and half of the multiplies, minus the metadata, so the reduced weight payload can lower traffic across HBM and on-chip SRAM. Any roofline comparison ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|section 11.6]]) of a dense layer with its 2:4 pruned counterpart must count operations the same way for both, either as the dense-equivalent work of the unpruned layer or as the multiplies the sparse hardware executes, with metadata and activation bytes counted under either convention. Narrower values and skipped zeros therefore help when they reduce the bytes moved and keep the matrix engines fed. The ResNet-50 INT8 profile collects that benefit only on an execution path that supports both its format and its shapes, and how fast such a path can possibly run follows from one division.

Dividing a model’s total operation count by peak arithmetic throughput produces an idealized lower bound on execution time, not a realistic inference latency. On the H100’s INT8 tensor path, dividing ResNet-50’s 8.2 GFLOP per inference by the 1,979 TOPS peak yields a floor of about 4 μs, against 8 μs at the FP16 peak. Real single-image ResNet-50 inference takes far longer than either floor. Part of that gap is kernel launch, synchronization, and host overhead that no roofline captures; part is memory traffic in low-intensity layers, because bandwidth has improved more slowly than tensor arithmetic throughput. That imbalance decides whether the advertised INT8 peak delivers high sustained utilization or sits largely idle on a given workload ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-horowitz2014|Horowitz 2014]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-gholami2024|Gholami et al. 2024]]). Closing the gap requires the other half of the anatomy, the memory hierarchy that supplies the compute units.
