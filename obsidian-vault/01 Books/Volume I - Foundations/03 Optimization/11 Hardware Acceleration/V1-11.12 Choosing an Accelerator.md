# V1-11.12 Choosing an Accelerator

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration|V1-11 Hardware Acceleration]]

^sec-hardware-acceleration-choosing-accelerator-6b2d

Every section of this chapter ends in the same question asked at a different level: which machine should run a given workload. The question cannot be answered from a datasheet, because the limiting resource belongs to the workload on a particular machine rather than to the machine alone. The book’s five lighthouses make the point on a single reference machine. Their bytes and operations differ by orders of magnitude, and each one exhausts a different resource of an H100 first ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.12 Choosing an Accelerator#^tbl-hw-acceleration-lighthouse-memory-compute|table 17]]).

| **Lighthouse**             | **Home regime** | **Model bytes (FP16)** | **Model bytes (INT8)**     | **Operations per inference** | **Limiting resource on one H100**                                    |
|:---------------------------|:----------------|:-----------------------|:---------------------------|:-----------------------------|:---------------------------------------------------------------------|
| **ResNet-50**              | Compute bound   | 51.1 MB                | 25.6 MB                    | 8.2 GFLOP                    | Arithmetic, once batching amortizes the weights                      |
| **MobileNetV2**            | Compute bound   | 7.0 MB                 | 3.5 MB                     | 0.6 GFLOP                    | Launch overhead and depthwise-layer bandwidth; built for a phone NPU |
| **GPT-2 XL (decode)**      | Bandwidth bound | 3 GB                   | 1.5 GB                     | 3 GFLOP per token            | HBM bandwidth: every token rereads every weight                      |
| **DLRM**                   | Capacity bound  | 100 GB of tables       | Tables dominate either way | Few per lookup               | Memory capacity: tables exceed one device’s 80 GB                    |
| **Keyword spotting (KWS)** | Power bound     | 400 KB                 | 200 KB                     | 20 MFLOP                     | None on an H100; built for a microcontroller’s milliwatt budget      |

Table 17: **Lighthouse Memory and Compute**: Model bytes and operations for the book’s five lighthouses from the model registry, with the resource each exhausts first on one H100. The operation counts are per inference, and per generated token for GPT-2 XL decode; DLRM’s bytes are dominated by its embedding tables, whose lookups perform little arithmetic.

^tbl-hw-acceleration-lighthouse-memory-compute

The table turns the chapter’s diagnosis into a selection rule. Its home-regime column names what limits each model on the machine it was built for, and its last column names what limits that model on one H100, which is why the two disagree for MobileNetV2 and KWS. ResNet-50 rewards arithmetic throughput on a supported INT8 path, GPT-2 XL decode rewards memory bandwidth, DLRM rewards memory capacity, and MobileNetV2 and KWS reward energy per inference on chips that never see a data center. The rest of the section applies that rule at three levels: the configurations accelerator families adopt for their target deployments, the cost of delivered throughput, and the energy each request consumes.

### Processor Configurations Across Deployment Targets

^sec-hardware-acceleration-interconnects

Across data-center, server-CPU, and mobile targets, architects assemble SIMD lanes, Tensor Cores, and systolic arrays into markedly different full-chip organizations depending on which resource runs out first. Training-optimized accelerators such as the NVIDIA A100 pack 108 streaming multiprocessors with wide SIMD units and FP16 Tensor Cores because training throughput scales with aggregate multiply-accumulate capacity across general kernels ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020a]]). Google’s TPU v4, by contrast, concentrates each chip into two cores built around large $128{\times}128$ BF16 systolic arrays, trading per-thread flexibility for area and energy efficiency on dense matrix multiplications ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-jouppi2023|Jouppi et al. 2023]]). Inference and edge targets shift the balance again. Intel’s Sapphire Rapids dedicates Advanced Matrix Extensions (AMX) tile engines to INT8 and BF16 because server inference models tolerate reduced precision ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-intel2021amx|Intel Corporation 2021a]]), while mobile neural engines shrink those matrix datapaths into low-power SoC blocks that prioritize energy per operation over peak throughput. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.12 Choosing an Accelerator#^tbl-execution-units|Table 18]] compares these architectural configurations.

| Processor          | **Vector execution** |             **Matrix engine**              |  Processing Elements  | **Primary workloads** |
|:-------------------|:--------------------:|:------------------------------------------:|:---------------------:|:----------------------|
| **NVIDIA A100**    |  CUDA FP/INT lanes   |       Tensor Core instruction tiles        |        108 SMs        | Training, HPC         |
| **Google TPU v4**  |     Vector unit      |   $128{\times}128$ BF16 systolic arrays    |     2 cores/chip      | Training              |
| **Intel Sapphire** |   512-bit AVX-512    | AMX tiles (up to 16 rows by 64 bytes each) |    Up to 60 cores     | Inference             |
| Mobile NPU         | CPU/GPU/DSP vectors  |            Small matrix engines            | Integrated NPU blocks | Mobile inference      |

Table 18: **AI Processor Configurations**: Modern AI processors prioritize different execution unit characteristics for specific workloads: NVIDIA A100 uses wide SIMD and Tensor Cores for training, Google TPU v4 emphasizes high-throughput BF16 matrix multiplication, Intel Sapphire Rapids focuses on INT8-optimized inference, and mobile NPUs prioritize low-power execution. These variations in SIMD width, Tensor Core size, and processing element count reflect the growing diversity in AI hardware architectures.

^tbl-execution-units

The pattern across these configurations reveals a consistent engineering principle: each design sacrifices generality to optimize for its target workload’s dominant operation and precision. Training chips invest silicon in wide floating-point datapaths; inference chips trade precision for throughput; mobile chips trade throughput for energy efficiency. No single design dominates across all workloads, which is precisely why hardware selection depends on workload analysis rather than headline specifications.

### Cost-Performance Analysis

^sec-hardware-acceleration-costperformance-analysis-e925

Consider an engineering team choosing between deploying a larger cluster of older accelerators or a smaller cluster of newer units. Architectural specifications define computational potential, but procurement decisions require **cost-performance analysis** grounded in delivered throughput rather than datasheet peaks. Because memory access costs dominate computation ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.03 Hardware Specialization#^sec-hardware-acceleration-machine-learning-hardware-specialization-09c5|section 11.2.3]]), accelerators achieve only a fraction of their advertised FLOP/s on memory-bound kernels while sustaining high utilization on dense matrix multiplications that amortize each fetch across many operations.

Peak FLOP/s figures therefore mislead whenever dominant kernels are memory-bandwidth or communication bound. In a large model pipeline, dense feed-forward and attention projection layers may remain compute bound, whereas embedding lookups, layer normalization, residual additions, and small-batch autoregressive decoding often have low arithmetic intensity. Their measured bottlenecks can include memory bandwidth, dependent access latency, reductions, and launch overhead; the operator name alone does not identify the limiting resource. The decisive metric is delivered workload throughput per dollar under realistic cluster utilization, memory capacity constraints, available memory bandwidth, and scale-out interconnect efficiency.

These architectural and economic constraints explain the rapid industry adoption of newer accelerators despite substantial increases in nominal unit price. A newer chip whose delivered throughput on the limiting resource rises faster than its price lowers the cost of each delivered result, even though each unit costs more. For bandwidth-bound workloads, generational improvements in memory bandwidth and compiler code generation dominate end-to-end execution time. Cloud deployments introduce additional trade-offs: hourly rental rates, dynamic instance utilization, and infrastructure overhead continuously shift the economic break-even point between purchasing on-premises hardware and leasing cloud capacity.

Price-per-peak worksheets for named products age quickly. List prices vary with vendor, region, contract terms, and procurement volume, and each product’s headline peak uses a different precision, so the ratio of price to peak is meaningful for one device but not as a comparison across devices. A dated worksheet for several accelerator generations is kept with the other specifications in **[[05 Reference/Volume I - Foundations/V1 System Assumptions#^sec-appdx-system-assumptions|System Assumptions]]**. The durable rule is the one the lighthouse table states: divide cost by the throughput the workload delivers on its limiting resource, not by the advertised peak.

No worksheet reduces accelerator selection to a single headline specification. A bandwidth-bound kernel benefits more from the H100’s 3,350 GB/s memory subsystem than from an incremental gain in peak arithmetic, whereas a compute-bound GEMM shows the opposite sensitivity. Device memory capacity dictates whether working sets fit on-chip without spilling or partitioning, while compiler and driver maturity determines whether the application can actually reach the advertised datapath.

### Energy per Request

^sec-hardware-acceleration-hardware-sustainability-e902

At fleet scale, energy per useful inference becomes an important hardware-selection criterion. Operational emissions depend on workload throughput, measured system power, utilization, cooling overhead, and the electricity mix; embodied emissions add another lifecycle cost. Peak performance per watt is therefore a screening metric, not a substitute for end-to-end energy per request. The following scenario shows how useful throughput and a common power boundary determine the fleet needed for the same inference service.

**Napkin Math 11.11: An illustrative operational-energy comparison**

**Problem**: An inference service must complete 1 billion requests per day. Which of two hypothetical server platforms uses less operational energy for that service?

**Supplied observations**: For the same model, input distribution, accuracy, and latency target, a CPU server sustains 100 requests/s, and an NPU-equipped server sustains 1,000 requests/s. Their whole-server wall powers are 100 W and 200 W, respectively, including hosts and attached accelerators. These are hypothetical observations for this exercise, not product benchmarks. Assume requests arrive steadily through the day. Both fleets operate at no more than 80 percent of the supplied throughput to reserve capacity for arrival-rate variation. Assume the listed wall power throughout the 24 h day, including spare capacity. Facility cooling and embodied emissions are outside this operational boundary.

**Calculation**:

1.  **Size the fleets from useful work.** Multiplying useful throughput by the operating fraction and the day length gives 6,912,000 requests per CPU server per day and 69,120,000 per NPU-equipped server. Divide the daily target by each capacity and round up to whole servers. The service requires 145 CPU servers or 15 NPU-equipped servers.
2.  **Account for the provisioned fleet.** Server count multiplied by wall power and day length yields 348 kWh per day for CPUs and 72 kWh for NPUs. Dividing each fleet’s energy by the same completed-request target gives 1.2528 J per request and 0.2592 J per request. These values include capacity headroom and integer fleet rounding.
3.  **Translate the energy difference.** At a common grid factor of 0.429 kg/kWh, the NPU-equipped fleet avoids approximately 43.2 t of operational CO<sub>2</sub> emissions per year at the stated system boundary.

**Decision**: Choose the NPU-equipped fleet if the objective is to minimize operational energy under these supplied conditions. Each server draws more power, but its greater useful throughput reduces the required fleet enough to lower joules per completed request. This conclusion depends on meeting the same quality and latency targets; a faster peak arithmetic rate alone would not establish the advantage. A procurement decision must additionally compare acquisition costs, software support, and embodied emissions.

Energy per request completes the selection rule that the lighthouse table began. Hardware selection is not determined by peak speed alone. Energy per useful result and total cost of ownership belong beside latency, throughput, and memory capacity, and each is measured against the resource the workload actually exhausts. The misconceptions that follow are the ways teams skip that measurement and choose the wrong hardware path.
