*D·A·M taxonomy triangle with three vertices labeled D, A, and M connected by edges. The M (Machine) vertex is filled in solid color; the D and A vertices are gray, marking the Machine axis.*

*Hardware acceleration turns on the machine axis.*

The same INT8 weights can run far faster on one execution path than on another, because the hardware that executes a model, not the model itself, determines how much of every compression saving survives execution. **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression#^sec-model-compression|Model Compression]]** closed on a deployment profile for ResNet-50 quantized to INT8 (**[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.07 Measuring Compression Gains#^tbl-resnet50-int8-profile|ResNet-50 INT8 Deployment Profile on the Reference H100]]**): a model four times smaller whose large-batch throughput rises severalfold on the reference H100 while its batch-one latency barely moves. That batch-one result comes from a fixed cost paid each time the host launches a kernel on the device ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.09 Compilers and Runtimes#^sec-hardware-acceleration-compiler-support-172e|section 11.8]]). Data selection reduced the iron law’s Data factor ($\text{Samples/Task}$) and compression reduced the Algorithm factor ($\text{FLOPs/Sample}$) and byte traffic (${D_{\text{vol}}}$), but whether either saving reaches the wall clock is decided by the Machine factor ($\text{Seconds/FLOP}$). This chapter supplies the machine side of that profile.

The explanation starts with the memory wall: arithmetic is cheap relative to data movement, so specialized hardware matters less because it raises compute throughput than because it organizes memory, dataflow, and parallelism so that its arithmetic units stay fed.

One workload runs through the chapter. ResNet-50 quantized to INT8 carries the book’s compute-bound regime (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^tbl-lighthouse-examples|Lighthouse Models as Reference Workloads]]**): its convolutions reuse each weight across many image positions, so on a data-center accelerator most of its time can go to arithmetic rather than to moving bytes. It reappears at every level of the machine, from the matrix units that execute its convolutions to the compiler that lowers its graph, and each time the question is what the INT8 path changes.

GPT-2 XL decoding one token at a time supplies the single contrast. It carries the bandwidth-bound regime: every generated token streams all of the model’s weights from memory for about two operations per parameter, so the machine that keeps ResNet-50 busy spends most of a decode step waiting for bytes. MobileNetV2, whose depthwise layers trade arithmetic for a small parameter footprint, and keyword spotting (KWS), the power-bound lighthouse, return where the chapter reaches phone-class and embedded chips. DLRM appears where its embedding lookups, the capacity-bound regime, break the regular access patterns that accelerators assume. The reference machine is the NVIDIA H100, the data-center accelerator this book uses for training and serving examples; its numbers are one generation’s instance of limits that every generation obeys.

**Definition 11.1: Hardware acceleration**

***Hardware acceleration*** is the practice of mapping work from general-purpose execution onto specialized processors or functional units optimized for a narrower operation class. For ML workloads, that specialization commonly trades some programmability for the compute density $({R_{\text{peak}}})$ and performance-per-watt gains that regular tensor operations can exploit.

1.  **Significance**: An H100 GPU delivers 989 TFLOP/s for dense FP16/BF16 matrix multiplication; against this chapter’s illustrative 1–2 TFLOP/s reference-CPU baseline, this is a 490–990× gap. Its 80 billion transistors devote far more silicon to parallel arithmetic than to branch prediction, out-of-order scheduling, and large caches ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-choquette2023|Choquette 2023]]).
2.  **Distinction**: A general-purpose CPU is designed for flexible execution, low-latency control, and varied workloads. An accelerator instead concentrates resources on a narrower operation class, so it achieves its gains only when the workload exposes the supported operations and enough parallel work to keep its arithmetic units busy.
3.  **Common pitfall**: A frequent misconception is that an accelerator’s advertised peak throughput is the throughput a workload receives. Delivered performance is bounded above by the lower of the compute ceiling and what memory bandwidth can feed (the roofline constraint, developed later in this chapter). A low-arithmetic-intensity kernel can therefore sit at a small fraction of peak FLOP/s no matter how fast the silicon is rated, because it starves for data rather than for arithmetic.

The anatomy of an accelerator is the arrangement of parts that every machine learning accelerator shares: arithmetic units built for tensor operations, on-chip memory that holds operands next to those units, a wide path to off-chip memory, and a host interface through which work arrives. Every inference and every training step on such a machine is a stream of operand movements that ends in multiply-accumulate operations, and the anatomy decides how far each operand travels before it is used. A matrix unit that can retire thousands of multiply-accumulates per cycle sits idle whenever its next operands are still in flight, and an off-chip access can take many processor cycles and cost orders of magnitude more energy than the low-precision operation it feeds. The arithmetic units are the easy part of the design; the rest of the anatomy exists to keep them fed.

The definition becomes concrete in the generic chip of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^fig-accelerator-anatomy|figure 1]], which serves as this chapter’s map. External high-bandwidth memory (HBM) feeds shared on-chip storage (an L2 cache), which distributes operands into rows of processing elements, each equipped with a private scratchpad or cache, a matrix unit, a vector unit, and a special function unit. A host interface connects the chip to the CPU that issues its work.

![[90 Assets/Volume I/11 Hw Acceleration/Generated Figure ed69b8d311.svg]]

Figure 1: **Anatomy of a Modern AI Accelerator**: This generic schematic combines common components rather than depicting one product. A host interface connects the accelerator to a CPU, a high-bandwidth device-memory interface feeds shared on-chip storage, and processing elements contain matrix, vector, and special-function units with local memory. Real accelerators differ in which units they provide and whether storage is hardware-managed cache or software-managed scratchpad.

^fig-accelerator-anatomy

Within each processing element, specialized units partition execution across distinct mathematical primitives: dedicated matrix units (Tensor Cores) execute dense matrix multiplication, vector units evaluate element-wise arithmetic, and special function units (SFUs) approximate transcendental operations such as activations and exponentials. Their number, grouping, and names vary by vendor; some designs arrange them into an explicit 2D systolic grid, in which each unit passes its operands directly to its neighbor every cycle ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-systolic-arrays-6fa8|section 11.4.4]]), and others distribute matrix engines among wide parallel cores.

The memory hierarchy amortizes the cost of data transport across tiers. High-bandwidth memory provides off-chip capacity and throughput, while shared on-chip storage and per-element caches or scratchpads cut off-chip traffic. Because moving a tensor tile across the package boundary costs orders of magnitude more energy than keeping it on chip, compilers and kernels must coordinate tile capacity, reuse, and prefetching to keep operands staged locally. More HBM bandwidth raises the off-chip ceiling, but without local reuse the execution units still stall. The system assumptions appendix (**[[05 Reference/Volume I - Foundations/V1 System Assumptions#^sec-appdx-system-assumptions|System Assumptions]]**) collects reference specifications for the accelerators this book uses, including the H100.

The host interface links the accelerator to the host CPU, which coordinates execution graphs, asynchronous I/O, and fallback operations while the accelerator executes dispatched kernels. Direct-memory-access engines can overlap host-device transfers with execution, so a well-scheduled transfer need not stall the accelerator.

Work that leaves the matrix units, or the device, can also cap the speedup. An operator unsupported by the accelerator backend may require a CPU round-trip across the host link, whereas an operator merely outside the matrix-unit instruction set can still run on the device as a vector or other device kernel. Every fallback adds launch and synchronization time, a CPU round-trip adds transfer time as well, and kernel execution time matters little if those costs dominate end-to-end latency. The three parts of the figure (the processing elements, the memory tiers, and the host link) are the parts this chapter takes apart in turn.

The anatomy embodies the chapter’s central engineering trade-off. General-purpose processors allocate silicon area to complex control logic, speculative execution, branch prediction, and multi-level cache hierarchies to handle arbitrary control flow. An accelerator redirects that transistor budget toward dense arithmetic arrays, dedicated register files, and high-bandwidth memory paths tailored to a narrower workload class. When the software path exposes sufficient tensor parallelism, this specialization yields order-of-magnitude improvements in energy efficiency and throughput per watt. Silicon built for a narrow class of dense tensor operations pays off only because, as the bitter lesson predicts, the general methods that win by exploiting computation keep reducing to those same operations at ever larger scale. The dependence also runs the other way, because scale keeps winning only while accelerators keep lowering the time and energy of each additional operation, so the hardware this chapter studies is part of what sustains the bitter lesson itself.

↩︎ The bitter lesson, the observation that general methods exploiting computation win as computation grows, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.05 The Bitter Lesson#^sec-introduction-bitter-lesson-79c7|The Bitter Lesson]]**.

Hardware alone cannot achieve these gains. Algorithms must structure operations to expose data reuse and regular memory access, while silicon architectures must allocate physical units to the mathematical primitives and numeric precisions that algorithms actually execute. That mutual dependence motivates a complementary principle: hardware-software co-design.

**Definition 11.2: Hardware-software co-design**

***Hardware-Software Co-design*** is an ML accelerator development method that crosses conventional abstraction boundaries, allowing algorithm constraints to inform silicon design and hardware capabilities to shape algorithm formulation.

1.  **Significance**: On a supported tensor-core path, 8-bit integer (INT8) quantization can deliver multi-fold throughput gains because hardware executes lower-precision operations more densely and moves fewer bytes than an FP32 path; the exact gain depends on the architecture and workload ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020a]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-dally2021|Dally et al. 2021]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-dally2023|Dally 2023]]).
2.  **Distinction**: Unlike layered abstraction (where software calls a hardware API without knowing the silicon details), co-design exposes hardware constraints directly to algorithm and compiler authors: data alignment requirements, precision formats, and memory access patterns all become visible inputs to global cross-layer optimization.
3.  **Common pitfall**: A frequent misconception is that co-design is a one-time hardware design choice. In practice, the supported features continue to evolve: NVIDIA Tensor Cores began with FP16 matrix multiplication, later generations added TF32 and broader integer support, and Ampere added acceleration for 2:4 structured sparsity ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia-tensors-fp16-2017-23d257af|NVIDIA 2017]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020a]]).

Co-design explains why model compression techniques deliver real speedups. Quantization shows why converting FP32 to INT8 accelerates execution on supported hardware: reduced precision cuts memory traffic, while specialized arithmetic units execute more low-precision operations per cycle than FP32 equivalents ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020a]]). Structured pruning improves performance when it produces smaller dense shapes or a sparsity pattern recognized by silicon, whereas arbitrary unstructured sparsity incurs metadata handling and non-coalesced memory accesses (scattered addresses that the memory system cannot combine into a few wide transfers) that often erase theoretical gains.

Evaluating accelerator performance requires tracing the path from workload to silicon: compute primitives, memory hierarchies, roofline diagnosis, mapping and dataflow, and compiler scheduling. The recurring question is why algorithmic improvements frequently fail to deliver proportional end-to-end speedups. Amdahl’s law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-amdahl|8]]) already answered it for model-side optimizations, since whatever an optimization leaves untouched caps the overall gain. The same bound governs hardware. The theorem below applies the principle to an accelerator, and the only new quantity is the gain, which becomes the accelerator’s path gain ${G_{\text{accel}}}$.

↩︎ Quantization and its effect on weight payload, memory traffic, and compute cost are established in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-quantization-precision-cd46|Numerical Precision: Changing How Values Are Stored]]**.

**Theorem 11.1: The fundamental limit of acceleration (Amdahl's law)**

Hardware acceleration *does not speed up the entire system*; it speeds only the baseline-time fraction using the accelerated path. For that fraction ${f_{\text{parallel}}}$ and path gain ${G_{\text{accel}}}$, **Amdahl’s law** ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-amdahl1967|Amdahl 1967]]) gives the bound in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^eq-amdahl|equation 1]].

$$
\text{Speedup} = \frac{1}{(1 - {f_{\text{parallel}}}) + \frac{{f_{\text{parallel}}}}{{G_{\text{accel}}}}} \tag{1}
$$

^eq-amdahl

- **Accelerated fraction** (${f_{\text{parallel}}}$): Share of baseline time receiving the stated gain, often in matrix multiplication or another supported kernel.
- **Accelerator gain** (${G_{\text{accel}}}$): The raw speed advantage of the GPU or Tensor Processing Unit (TPU) over the CPU for the accelerated portion of the workload.
- **Unaccelerated fraction** ($1-{f_{\text{parallel}}}$): Work outside the chosen path, such as data loading, host overhead, unsupported operators, and kernel launch latency.

**Pitfall**: *Unaccelerated work caps total speedup.* If 10 percent of baseline time is unaffected (${f_{\text{parallel}}}=0.9$), even infinite path gain (${G_{\text{accel}}}=\infty$) yields at most 10$\times$ overall. Once the accelerated component is fast enough, unaffected work dominates.

Hardware acceleration targets specific terms in the iron law of ML systems. The product form used at the start of this chapter multiplies the Data, Algorithm, and Machine factors. The additive form of **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 1.3]]** splits the same end-to-end time into data movement $({D_{\text{vol}}}/{\text{BW}})$, computation $({O}/({R_{\text{peak}}} \cdot {\eta_{\text{hw}}}))$, and fixed latency $({L_{\text{lat}}})$, which exposes the machine’s own terms. Data selection and compression shrank ${O}$ and ${D_{\text{vol}}}$; hardware acceleration instead reduces the realized time per operation ($\text{Seconds/FLOP}$) by improving ${R_{\text{peak}}}$, ${\eta_{\text{hw}}}$, and ${\text{BW}}$. Which of these physical terms an upgrade actually improves determines its accelerated fraction under Amdahl’s law.[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn1|¹]]

↩︎ The decomposition of execution time into data, compute, and latency terms is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**.

This dynamic explains why hardware upgrades frequently fail to produce proportional end-to-end speedups. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^fig-iron-law-heatmap|Figure 2]] maps system speedup across accelerator gain (${G_{\text{accel}}}$) and accelerated fraction (${f_{\text{parallel}}}$), charting where those returns diminish. Where the unaccelerated fraction $1-{f_{\text{parallel}}}$ remains substantial, the white contour curves flatten horizontally into the unaccelerated-bound regime, bounding total speedup at the $1/(1-{f_{\text{parallel}}})$ asymptote regardless of how far ${G_{\text{accel}}}$ scales along the horizontal axis. Because ${f_{\text{parallel}}}$ differs substantially across workload archetypes running on identical hardware, a workload’s vertical position on this map determines whether an accelerator investment pays off or stalls on non-matrix operations.

**Checkpoint 11.1: The parallelism check**

These checks turn Amdahl’s bound into a hardware-selection test.

**Amdahl’s reality**

**Serial bottlenecks**: use Amdahl’s bound to explain why a 1,000$\times$ faster GPU may only speed up training by 5$\times$ when data loading is slow.

**Speedup ceiling**: for ${f_{\text{parallel}}}=0.95$ and ${G_{\text{accel}}}=100$, estimate total speedup and compare it with the infinite-accelerator ceiling.

**Workload variation**: what baseline profiling would establish the ResNet-50 and MobileNet accelerated fractions for a proposed hardware change? Explain how those fractions would determine which benefits more.

The serial bottleneck becomes concrete on real hardware, where the same accelerator that nears its parallel ceiling on one workload can stall on another. The comparison below uses the INT8 (8-bit integer) path, whose advantage over FP32 or FP16 has two sources. Each operand occupies a half or a quarter of the bytes, and an 8-bit multiplier occupies far less silicon area than a floating-point one, so the same die holds more multiply-accumulate (MAC) units. Two workloads on an NVIDIA H100 with different unaccelerated fractions show how that fraction governs whether this peak INT8 advantage becomes realized speedup. A second look at the decode case then separates that limit from a different one, bandwidth-boundedness.

↪ Order-of-magnitude throughput, bandwidth, and capacity for each accelerator class are collected for reference in **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-ai-hardware-cheat-sheet-modern-reference-4dc1|Accelerator classes]]**.

**Lighthouse 11.1: An illustrative Amdahl budget on H100**

**Illustrative ResNet-50 inference on NVIDIA H100**:

- Assume H100 provides ${G_{\text{accel}}}$ = 247× on matrix multiplication relative to a server CPU without matrix extensions (1979 TOPS INT8 vs. ~8 TOPS) ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-choquette2023|Choquette 2023]]). The CPU’s INT8 rate is a scenario assumption for this budget, not the FP32 peak of the reference CPU used elsewhere in the chapter.
- Assume ${f_{\text{parallel}}}$ = 0.95: 95 percent of baseline time receives that gain, while 5 percent remains in data loading, preprocessing, postprocessing, and other work.

$$
\text{$\text{Speedup} = \frac{1}{(1-0.95) + \frac{0.95}{247}} = \frac{1}{0.05 + 0.0038} \approx 18.6\times$}
$$

 The 247× path gain produces only 18.6× end-to-end speedup because the 5 percent unaffected fraction sets the ceiling.

**Contrast with GPT-2 (autoregressive)**:

- For GPT-2 token generation, assume ${f_{\text{parallel}}}$ = 0.80; the remaining 20 percent includes host overhead, sampling, and decoding work outside the accelerated matrix path.

$$
\text{$\text{Speedup} = \frac{1}{(1-0.80) + \frac{0.80}{247}} = \frac{1}{0.20 + 0.0032} \approx 4.9\times$}
$$

 Less token-generation time receives the assumed gain, so even an infinite path gain yields at most $1/(1-{f_{\text{parallel}}})$ = 5×.

This calculation still overstates the decode path gain. Decode is bandwidth bound, limited by how fast memory delivers weights rather than by how fast the chip multiplies, so its accelerated path runs at memory’s rate, not the INT8 TOPS rate. The relevant ratio is the H100’s memory bandwidth over the reference CPU socket’s, 67× (each chip’s path to its own local memory, the H100’s HBM against the CPU socket’s DRAM, not the PCIe link between host and accelerator). INT8 helps decode on either machine by halving the bytes each weight occupies relative to FP16, not by multiplying faster. With that gain the bound falls from 4.9× to 4.7×, barely moving, because the unaccelerated fraction already dominates. Two distinct limits are at work. Bandwidth-boundedness shrinks ${G_{\text{accel}}}$, whereas the unaccelerated fraction caps what any ${G_{\text{accel}}}$ can deliver. Serving optimizations attack both. Batching raises ${G_{\text{accel}}}$, because each weight byte fetched now serves many requests. Speculative decoding, developed in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving#^sec-model-serving|Model Serving]]**, changes the execution schedule by having a smaller model propose tokens for the full model to verify together. Its speedup requires a new timing breakdown that includes drafting, verification, and rejected proposals.

Whether an operation is limited by compute rate or by data movement dictates both hardware selection and software optimization. Under the arithmetic intensity law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-arithmetic-intensity|6]]), upgrading to an accelerator with $10\times$ higher peak compute yields negligible speedup if data delivery is the bottleneck. The roofline model, previewed in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^sec-ml-systems-matching-workloads-hardware-bf91|Matching workloads to hardware]]**, makes this diagnosis ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-williams2009|Williams et al. 2009]]). It compares an operation’s arithmetic intensity, the ratio of operations to bytes of memory traffic (FLOP/byte), with the hardware’s ridge point, the peak compute rate divided by memory bandwidth, which is the intensity at which the compute limit and the bandwidth limit meet. An operation below the ridge is bandwidth bound, the regime the roofline literature calls *memory bound*; an operation above it is compute bound. GPT-2 decode and ResNet-50 sit on opposite sides of that line, a difference the Amdahl budget above already registered in the decode path gain. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Section 11.6]] turns the classification into numbers once the compute units and memory systems that set the two ceilings have been examined.

↩︎ The arithmetic-intensity spectrum that separates the workload signatures of the major architectures is established in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^sec-network-architectures-understanding-arithmetic-intensity-ade5|Arithmetic intensity across workloads]]**.

The chapter builds the machine from the bottom up ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^tbl-hw-acceleration-chapter-spine|table 1]]). Compute primitives and compute units supply the arithmetic side of the anatomy, ending with the INT8 and sparse paths that ResNet-50’s profile depends on, and memory systems supply the other side, from registers to host memory. Performance bounds then combine the two into the roofline’s ceilings, show which ResNet-50 layers clear the H100’s ridge point, and explain why faster INT8 arithmetic can leave a layer below it; this is the chapter’s midpoint, marked by a checkpoint. The second half asks how software reaches those ceilings, through hardware mapping and then the compilers and runtimes that make its choices automatically. Three shorter sections widen the view to work beyond one accelerator, heterogeneous systems-on-chip, and the choice of an accelerator for a workload and a budget.
