# V1-11.13 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration|V1-11 Hardware Acceleration]]

^sec-hardware-acceleration-fallacies-pitfalls-dc1f

Hardware acceleration often defies intuition because headline specifications mask workload-specific bottlenecks. The fallacies and pitfalls here capture selection, scaling, and optimization errors that leave expensive compute resources underused. Sound system evaluation follows one diagnostic habit instead: characterize the workload arithmetic intensity, identify the physical bottleneck metric, match execution to the appropriate datapath, and account for interconnect, scaling, and portability costs.

**Fallacy**: *More specialized hardware always provides better performance than general-purpose alternatives.*

Specialized accelerators achieve high efficiency only when workload access patterns match their execution datapaths. On the roofline ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|section 11.6]]), the A100 reference tensor path has a ridge point of 153 FLOP/byte; below that ridge, increasing its 312 TFLOP/s arithmetic peak does not raise the modeled bandwidth ceiling. A transformer attention softmax with ${I}$ = 2 FLOP/byte–5 FLOP/byte is capped at 4.1 TFLOP/s–10.2 TFLOP/s (3.3 percent of tensor peak) on an A100. On a CPU, whose ridge point sits around 10 FLOP/byte–20 FLOP/byte, the same traffic model places the kernel below the reference ridge, and its bandwidth ceiling represents 10 percent–50 percent of the CPU’s compute capacity. These modeled bandwidth bounds, not measured utilization, show that the specialized chip leaves most of its arithmetic idle on this kernel, even though its absolute bandwidth ceiling still exceeds the CPU’s. A CPU often wins on irregular memory access, tiny batches, and dynamic control flow, where highly parallel pipelines stall on memory latency and thread divergence. Its large caches, out-of-order execution, and branch predictors deliver lower latency and better resource efficiency on that work. Hardware selection requires matching workload arithmetic intensity and dataflow regularity to architectural ridge points rather than assuming specialization guarantees speed.

**Pitfall**: *Ignoring memory bandwidth limitations when selecting acceleration strategies.*

Procurement decisions frequently target peak arithmetic throughput while overlooking memory interface constraints. Off-chip data movement imposes severe performance and energy penalties: fetching an operand from DRAM consumes roughly 640 pJ compared to 0.5 pJ for a small, register-adjacent L1 SRAM access, the cheapest tier noted in the caption of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.03 Hardware Specialization#^fig-energy-hierarchy|figure 4]]. Consider an accelerator providing 300 TFLOP/s of compute alongside 2 TB/s of memory bandwidth, setting a ridge point of 150 FLOP/byte. A normalization kernel such as LayerNorm with an arithmetic intensity of 1.5 FLOP/byte has a bandwidth ceiling of 3 TFLOP/s (1 percent of compute peak). Under the stated HBM streaming assumption, memory bandwidth supplies this upper bound, and adding compute units alone does not raise it.

**Fallacy**: *Hardware acceleration benefits scale linearly with additional accelerators.*

Distributed training need not deliver $8\times$ throughput on eight accelerators because exposed inter-chip communication can reduce parallel efficiency. Synchronizing gradients across ranks via ring AllReduce makes each rank send and receive about twice the gradient payload (**[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^eq-training-ring-allreduce|equation 8.12]]**), or 1.75× payloads across eight devices. With an interconnect such as NVLink providing 600 GB/s bidirectional bandwidth (half that per direction), transmitting a 1 GB gradient payload consumes 5.83 ms. For a model with a 50 ms compute step, this data exchange adds 11.7 percent communication overhead before counting software collective latency. Without compute-communication pipelining, an eight-accelerator node reaches only 7.2× speedup (89.6 percent parallel efficiency). Stragglers, barrier synchronizations, and collective protocol overhead widen the gap between linear expectations and physical cluster scaling.

**Pitfall**: *Planning accelerator capacity from peak FLOP/s specifications.*

Peak FLOP/s measures arithmetic unit capacity under ideal instruction mixes and continuous operand availability, not delivered application throughput. Realized performance depends on kernel arithmetic intensity, matrix dimensions, memory coalescing, and runtime launch overhead. The roofline model ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|section 11.6]]) bounds the gap between peak compute and bandwidth-limited execution. On an A100 GPU with a 312 TFLOP/s peak, an illustrative dense-transformer scenario supplies a sustained range of 120 TFLOP/s–180 TFLOP/s (40 percent–60 percent model FLOPs utilization). This supplied range is illustrative, not a measurement or a prediction for every model. Sizing cluster capacity from peak FLOP/s creates severe under-provisioning; capacity planning must rely on measured sustained throughput or roofline-bounded kernel projections.

**Fallacy**: *One peak FLOP/s rating describes a workload at every precision.*

Accelerators have separate datapaths for different precisions, and the peak throughput varies dramatically across them. An H100 delivers roughly 989 TFLOP/s in FP16 tensor operations but only about 67 TFLOP/s in FP32 CUDA-core operations: a roughly 15× gap within the same chip ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-choquette2023|Choquette 2023]]). Dividing achieved BF16 model FLOP/s by the smaller FP32 peak inflates the reported utilization, while using that FP32 peak to estimate ideal training time overestimates the time. Matching against the wrong roofline misclassifies kernels as compute-bound when they are memory-bound (or vice versa). Useful model FLOP utilization divides the model’s useful operations per elapsed second by the matching supported precision and execution-path peak. Hardware busy time is a different metric: an active device can spend time on transfers, redundant work, or fallback execution. Quote the denominator and precision explicitly.

**Pitfall**: *Deploying small-batch inference workloads on high-compute accelerators.*

Small-batch dense inference can use only a small fraction of arithmetic peak because single-sample execution lacks cross-sample parameter reuse. For a dense linear projection with widths ${d_{\text{in}}}={d_{\text{out}}}=2048$, a single request (${B}=1$) is modeled as streaming the entire weight tensor from device memory to execute a matrix-vector product, yielding an arithmetic intensity of only 1 FLOP/byte. At batch size ${B}=256$, weight reuse amortizes memory transfers across tokens, elevating arithmetic intensity to 204.8 FLOP/byte. At ${B}=1$, memory bandwidth bounds performance at 2.04 TFLOP/s on an A100 and 0.32 TFLOP/s on a T4. Although the T4 provides a lower peak of 65 TFLOP/s with a ridge point of 203.1 FLOP/byte, the two batch-1 ceilings differ by 6.4×, which is exactly their memory-bandwidth ratio. The A100’s 4.8× advantage in peak compute contributes nothing. The A100 costs 6× as much as the T4, so their modeled batch-1 throughput ceilings per dollar are nearly the same. Actual procurement requires measured latency, throughput, memory fit, and the intended request mix.

**Fallacy**: *Vendor-specific optimizations have no long-term portability cost.*

Optimizing exclusively for a single vendor runtime captures immediate kernel efficiency but introduces severe architectural lock-in ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.09 Compilers and Runtimes#^sec-hardware-acceleration-compiler-support-172e|section 11.8]]). Codebases saturated with proprietary device intrinsics, vendor-specific assembly, and non-standard memory layouts require months of engineering labor to port when newer, more cost-effective accelerators emerge. This technical debt delays hardware transitions and prevents multi-vendor procurement. To preserve flexibility, systems must isolate vendor-tuned micro-kernels behind hardware abstraction layers or target intermediate compiler representations (such as Triton or MLIR).

**Checkpoint 11.5: Feasibility assessment: Can you run it?**

Before procuring hardware, validate each physical constraint. These failure modes translate into a concrete feasibility test:

**Memory capacity**: use ${M_{\text{total}}} = {M_{\text{weights}}} + {M_{\text{KV}}} + {M_{\text{activations}}}$ (weights, KV cache, and activation buffers) to list the inputs needed to test ${M_{\text{total}}} < {M_{\text{device}}}$ for a 7-billion-parameter Llama model with 14 GB FP16 weights on a 16 GB GPU. What sequence length, concurrency, model dimensions, and runtime workspace information is missing before a complete fit decision?

**Bandwidth**: compute the weight-streaming lower bound ${T_{\text{token}}}= {D_{\text{vol}}} / {\text{BW}}$ for a 70-billion-parameter model (140 GB) on 1 TB/s memory bandwidth, then compare the result with a 50 ms latency target. Assume one dense FP16 weight read per generated token; what additional traffic and overhead would a measured latency include?

**Compute**: identify the operation count, numerical path, and measured efficiency needed to use ${T_{\text{compute}}} = {O} / ({R_{\text{peak}}} \cdot {\eta_{\text{hw}}})$. With serialized frame processing, 30 FPS leaves 33.3 ms per frame for the whole pipeline. How does overlapped processing change the distinction between frame latency and sustained throughput?

**Roofline placement**: for an accelerator at roughly 2 TFLOP/s peak and 200 GB/s bandwidth, estimate the ridge-point arithmetic intensity, then place a 10 FLOP/byte kernel against it: how do the two ceilings compare, and would increasing only the compute clock raise the overall bound? What measurements would test the actual bottleneck?
