# V1-11.14 Summary

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration|V1-11 Hardware Acceleration]]

^sec-hardware-acceleration-summary-a5f8

Hardware acceleration co-designs compute engines, memory hierarchies, numerical formats, and dataflows. For a chosen memory interface, the iron law compares compute time ${O}/({R_{\text{peak}}}{\eta_{\text{hw}}})$ with movement time ${D_{\text{vol}}}/{\text{BW}}$; the roofline restates that competition as $\min({R_{\text{peak}}}, {\text{BW}} \times {I})$. End-to-end latency also includes launch, synchronization, communication, and fixed overheads. Accelerators improve efficiency only when supported paths capture reuse locally. Hardware selection therefore begins with the workload’s measured or modeled bottleneck, not a vendor peak. For ResNet-50, INT8 multiplies large-batch throughput because at large batch its heavy convolutions sit near the ridge, where a faster arithmetic path pays off if activations also move at INT8. Batch-one latency instead sits on the overhead floor and moves only as far as compilation shrinks launch cost.

The chapter map ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^tbl-hw-acceleration-chapter-spine|table 1]]) can now be read row by row for the INT8 ResNet-50 workload that opened the chapter. Its convolutions lower onto matrix units. Its INT8 path doubles the H100’s arithmetic ceiling without moving the bandwidth ceiling. Its activation tiles stay on chip only when the mapping and the tile sizes allow it. Whether a given layer gains from INT8 depends on whether its activations travel at INT8, a choice the compiler and runtime make. GPT-2 XL decode, the single contrast, gains from none of the arithmetic and from every byte saved.

The bounds developed across the chapter fit in one table ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.14 Summary#^tbl-hw-acceleration-key-equations|table 19]]). Together they let an engineer estimate, before profiling, whether a kernel on a given accelerator is limited by arithmetic, by memory bandwidth, by on-chip capacity, or by work the accelerator never touches.

**Key Takeaways: Moving data costs more than computing it**

- **The roofline model bounds attainable performance**: Compare a kernel’s arithmetic intensity with the ridge for its memory interface and supported execution path (295.2 FLOP/byte for the H100’s dense FP16 tensor path and 590.7 FLOP/byte for its INT8 path). Below it, bandwidth supplies the tighter modeled ceiling; above it, compute does. Profiling establishes whether the kernel approaches that ceiling or is limited by dependencies, dispatch, or another execution resource.
- **Memory bandwidth constrains performance**: GPU compute capacity has grown faster than memory bandwidth. Many inference phases are memory bound, especially low-batch decoding and embedding lookup, while large-batch GEMMs can remain compute bound.
- **Hardware-software co-design compounds performance**: Matching algorithm patterns to architectural capabilities, such as dense GEMM on systolic or tensor units and supported sparsity on sparse paths, can produce large improvements.
- **Tensor Cores require a compatible path**: Precision, dimensions, layouts, and library support must match the architecture. Batch and shape affect reuse and utilization, but no single batch threshold guarantees peak performance.
- **End-to-end speedup stops at the next bottleneck**: Accelerating one kernel leaves launch, transfer, synchronization, communication, and unsupported work unchanged. Use Amdahl’s law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-amdahl|8]]) and profiling to decide whether further silicon, better mapping, or less movement will improve the complete workload.

^callout-takeaways--11-14-483fb3f6

An accelerator is not a uniformly faster computer. It provides efficient paths for particular operations and dataflows, and each of those paths is a way of moving fewer bytes per useful operation. Tiling, fusion, stationary dataflows, and systolic execution pay off only when the workload, numerical format, and software path can use them. The diagnostic habit the chapter leaves is therefore an ordering. Place the kernel on the relevant roofline to bound its performance, bound the end-to-end gain with Amdahl’s law, and only then choose among more silicon, a better mapping, or less movement. Each step is a prediction that measurement must confirm. The same habit is what keeps the bitter lesson affordable. Scale keeps winning only while each additional operation gets cheaper in time and energy, and on modern accelerators the operation is rarely the expensive part. The bytes that feed it are.

**What’s Next: From optimization to validation**

Data selection, model compression, and hardware acceleration each end with a favorable local number, a prediction made for one stage in isolation. **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12 Benchmarking#^sec-benchmarking|Benchmarking]]** tests those predictions on a real device under real load, beginning with this chapter’s ResNet-50 workload, whose predicted roofline position becomes the first claim a measurement must confirm. It asks which local gains survive deployment-representative conditions, and it supplies the measurement scope, standardized suites, and statistical protocols that let different systems be compared on the same terms.
