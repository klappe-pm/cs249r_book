# V1-11.04 Compute Primitives

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration|V1-11 Hardware Acceleration]]

^sec-hardware-acceleration-ai-compute-primitives-2c99

A single forward pass through a neural network layer can issue millions or billions of MAC operations, and executing them one scalar instruction at a time would swamp the processor in instruction-fetch and register-access overhead. Across fully connected, convolutional, and attention layers, learned linear transformations reduce to these repeated MACs, whose regular tensor structure exposes the parallel work and operand reuse that hardware specialization requires. MACs do not dominate every model or phase (normalization, routing, indexing, communication, and element-wise operations can become limiting), but much of a modern ML accelerator’s peak arithmetic capacity is built to execute them. Whether they dominate elapsed time still depends on tensor shape, data movement, and the surrounding operators.

The hardware units that exploit these patterns are **AI compute primitives**: specialized functional blocks, each optimized for a particular class of operation. Three primitives are especially common in accelerators, each targeting a distinct pattern in neural networks: vector operations over elementwise data, matrix operations for dense products, and special functions such as exponentials and square roots. At the framework level, a single declarative statement encapsulates thousands of these operations ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-dense-layer-def-c3d09dfa|listing 1]]).

``` python
# Framework abstracts compute-intensive operations
dense = Dense(512)(input_tensor)  # 256x512 MACs per sample
```

Listing 1: **Dense Layer Abstraction**: High-level framework APIs encapsulate 131,072 MACs (256 inputs times 512 outputs) in a single function call, hiding the computational complexity from developers while enabling automatic hardware optimization.

^lst-dense-layer-def-c3d09dfa

Beneath this API call, an autograd or compilation engine lowers the layer into a computational graph. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-dense-expansion-d13fcb4d|Listing 2]] exposes a bulk matrix multiplication and bias broadcast, followed by an optional element-wise activation; the activation is a separate stage rather than an implicit part of the shown `Dense` call.

``` python
# Linear transformation work scales with input_dim x output_dim x
# batch.
output = (
    matmul(input, weights) + bias
)  # Matrix multiply dominates cost
output = activation(
    output
)  # Element-wise: proportional to output_dim x batch
```

Listing 2: **Matrix Operation Expansion**: Each dense layer decomposes into matrix multiplication and element-wise operations, exposing the dominant compute pattern that many neural-network kernels are built around.

^lst-dense-expansion-d13fcb4d

While graph representations group these steps into coarse tensor operators, execution on physical hardware requires scheduling individual scalar operations. Lowering the matrix multiplication to loop nests ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-loop-level-dense-bf7934ca|listing 3]]) makes the execution structure explicit: three nested iterations traverse the batch, output feature, and reduction dimensions, establishing $\mathcal{O}({B}\times {d_{\text{in}}} \times {d_{\text{out}}})$ arithmetic complexity.

``` python
# Total operations: batch_size × output_size × input_size MACs
for n in range(batch_size):  # Batch dimension: parallelizable
    for m in range(output_size):  # Output neurons: parallelizable
        sum = bias[m]  # Initialize accumulator
        for k in range(input_size):  # Reduction dimension: sequential
            sum += input[n, k] * weights[k, m]  # MAC operation
        output[n, m] = activation(sum)  # Nonlinear transformation
# Example work scales as batch_size × output_size ×
# input_size multiply-accumulate operations
```

Listing 3: **Processor-Level Execution**: Nested loops reveal the $\mathcal{O}({B} \times {d_{\text{in}}} \times {d_{\text{out}}})$ multiply-accumulate operations that accelerators must execute, with 4.2M MACs for ${B}$=32, ${d_{\text{in}}}$=256, ${d_{\text{out}}}$=512 configurations.

^lst-loop-level-dense-bf7934ca

These nested loops expose three recurring computational patterns: element-wise operations along vectors, matrix-level multiply-accumulate reductions, and nonlinear transformations. Their ubiquity justifies dedicated hardware execution paths: vector pipelines stream independent elements and reductions, matrix engines organize multiply-accumulate grids across spatial tiles, and special-function units approximate nonlinear math. The boundaries between these units are architectural rather than mathematical; an optimizing compiler frequently fuses operations across all three paths within a single kernel invocation to eliminate intermediate memory traffic.

### Vector Operations

^sec-hardware-acceleration-vector-operations-19bf

In the scalar loop nest of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-loop-level-dense-bf7934ca|listing 3]], evaluating a batch of 32 samples through a 256-to-512 dense layer requires 4.2M MACs. A scalar processor must fetch and decode separate instructions to load each input-weight pair, multiply-accumulate them, and advance the loop counters. Vector architectures eliminate this per-element control overhead by packing multiple data elements into wide register files (typically 128 to 512 bits) and applying a single decoded instruction across parallel execution lanes simultaneously.

RISC-V,[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn8|⁸]] an open instruction-set architecture (ISA) with a standardized vector extension ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-waterman2013|Waterman et al. 2013]]), provides a concrete vehicle for this execution model. In RISC-V vector assembly, code does not depend on a fixed hardware width. The instruction `vsetvli` queries the hardware to determine how many elements fit into available registers, the code processes that chunk, and the loop repeats until all features are exhausted.

``` c
fmv.w.x fa0, zero          # Scalar dot-product accumulator
fmv.w.x ft1, zero          # Zero seed for vector reduction
loop_feature:
    vsetvli t0, feature_cnt, e32, m1, ta, ma
    vle32.v v1, (in_ptr)
    vle32.v v2, (wt_ptr)
    vfmul.vv v3, v1, v2
    vfmv.v.f v0, ft1
    vfredusum.vs v4, v3, v0
    vfmv.f.s ft0, v4
    fadd.s fa0, fa0, ft0
    slli t1, t0, 2         # Four bytes per FP32 element
    add in_ptr, in_ptr, t1
    add wt_ptr, wt_ptr, t1
    sub feature_cnt, feature_cnt, t0
    bnez feature_cnt, loop_feature
```

Listing 4: **Vectorized Dot-Product Loop**: This illustrative loop processes several element pairs per iteration and reduces them into one scalar dot product.

^lst-riscv-vector-mac-943b13b6

Each pass of the loop in [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-riscv-vector-mac-943b13b6|listing 4]] loads as many input and weight elements as fit in the vector registers with two wide loads, multiplies them lane by lane, and reduces the products into a partial sum. One decoded instruction thus does the work of a whole chunk of scalar instructions. The two wide loads assume that the weights one dot product needs sit next to each other in memory.

Across iterations, the vector multiply instruction processes multiple data elements concurrently while wide loads amortize instruction decode and memory-request overhead. Because the runtime vector length dynamically adapts to the implementation’s hardware width, the identical binary executes correctly on both narrow embedded vector units and wide data-center pipelines. For this 256-feature workload, an 8-lane implementation splits each dot product into eight-element chunks. Across all 512 outputs and all 32 samples, that comes to 524,288 vector chunks.

Beyond dense inner products, deep learning workloads rely on a broader set of vector instructions. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^tbl-vector|Table 2]] maps these primitive vector operations to the specific neural network layers that depend on them.

| **Vector operation**        | Description                                               | **Neural network application**              |
|:----------------------------|:----------------------------------------------------------|:--------------------------------------------|
| **Reduction**               | Combines elements across a vector (for example, sum, max) | Pooling layers, attention score computation |
| **Gather**                  | Loads multiple nonconsecutive memory elements             | Embedding lookups, sparse operations        |
| **Scatter**                 | Writes to multiple nonconsecutive memory locations        | Gradient updates for embeddings             |
| **Masked operations**       | Selectively operates on vector elements                   | Attention masks, padding handling           |
| **Vector-scalar broadcast** | Applies scalar to all vector elements                     | Bias addition, scaling operations           |

Table 2: **Vector Operations**: Core vector operations map directly to deep learning primitives: reductions implement pooling layers, gathers enable embedding lookups, scatters update embedding gradients, and masked operations handle attention masks. These mappings show how vector hardware supports common ML primitives.

^tbl-vector

The benefit extends beyond instruction count. Contiguous vector loads can use memory interfaces efficiently, and control overhead is amortized across several data elements. Gather, scatter, masking, and short tails may use fewer lanes or require extra memory transactions, so vector width alone does not guarantee proportional speedup. The architectural pattern is not new. The Cray-1[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn9|⁹]] used vector registers and pipelined functional units for scientific computing in the 1970s ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-jordan1982|Jordan 1982]]); modern ML processors apply related principles at much larger commercial scale. In ResNet-50 the vector path carries the ReLU after every convolution and the residual addition that closes every bottleneck block. Each touches every activation element once and performs about one operation per element, so on its own it is limited by how fast the activations stream past, not by lane count.

Vector operations excel at element-wise transformations such as activation functions, where each output depends only on *its corresponding input*. Neural networks, however, also require structured computations where each output depends on *all inputs*, the weighted sums that define layer transformations. These many-to-many operations naturally express themselves as matrix multiplications, the second compute primitive.

### Matrix Operations

^sec-hardware-acceleration-matrix-operations-508d

Evaluating a dense layer one vector dot product at a time wastes reuse: each weight row is loaded for one sample and discarded before the next sample in the batch arrives, and each input vector is re-read for every output neuron. Matrix multiplication eliminates this redundant traffic by organizing work across two-dimensional tiles of weights, activations, and gradients, accounting for much of the arithmetic in dense neural networks ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-goodfellow2016deep|Goodfellow et al. 2016]]). Hardware and libraries tile those dimensions, splitting them into blocks small enough to stay in fast memory ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-tiling-principle|section 11.7.5]]), so the weights and activations in each block are reused across the whole tile while partial sums accumulate locally, though small or irregular matrices can still leave tile capacity unused.

#### Matrix Operations in Neural Networks

^sec-hardware-acceleration-matrix-operations-neural-networks-527a

Neural network computations decompose into hierarchical matrix operations. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-linear-matrix-hierarchy-c36ffdf5|Listing 5]] captures this hierarchy through a linear layer that transforms input features into output neurons over a batch. This listing and [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-matrix-patterns-77c333fd|listing 6]] store each sample as a column (the column-batch convention named in the code), so the weight matrix sits on the left of the product; the arithmetic is the same as in the row-per-sample loops of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-loop-level-dense-bf7934ca|listing 3]]. The expansion also adds an optional ReLU; it illustrates the arithmetic rather than the framework API’s internal tensor layout or an activation implicit in `nn.Linear`.

``` python
layer = nn.Linear(256, 512)  # Layer transforms 256 inputs to 512 outputs
output = layer(input_batch)  # Process a batch of 32 samples

# Framework Internal: Core operations (column-batch convention)
Z = matmul(weights, input)  # Matrix: transforms [256×32]
# input to [512×32] output
Z = Z + bias  # Vector: adds bias to each
# output independently
output = relu(Z)  # Vector: applies activation to
# each element independently
```

Listing 5: **Linear-Layer Operation Hierarchy**: The example expands a linear layer into a matrix multiply and bias broadcast, then applies element-wise ReLU, separating the matrix and vector work that hardware must execute.

^lst-linear-matrix-hierarchy-c36ffdf5

The scale of this matrix work follows from the layer dimensions. Each output neuron (512 total) must process all input features (256 total) for every sample in the batch (32 samples). The weight matrix alone contains 256 $\times$ 512 = 131,072 parameters that define these transformations, illustrating why efficient matrix multiplication dominates performance considerations.

Neural networks employ matrix operations across architectural patterns beyond simple linear layers. Convolution operations transform into matrix multiplications through the im2col technique,[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.17 Footnotes#^fn10|¹⁰]] enabling efficient execution on matrix-optimized hardware. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-matrix-patterns-77c333fd|Listing 6]] writes a linear layer, attention’s query-key scores, and an im2col convolution each as a matrix multiplication.

``` python
hidden = matmul(weights, inputs)
# weights: [out_dim x in_dim], inputs: [in_dim x tokens]
# Result combines all inputs for each output

# Attention Mechanisms - Multiple matrix operations
Q = matmul(Wq, inputs)
# Project inputs to query space [query_dim x tokens]
K = matmul(Wk, inputs)
# Project inputs to key space [key_dim x tokens]
attention = matmul(Q.T, K)
# Compare all query tokens with all key tokens [tokens x tokens]

# Convolutions - Matrix multiply after reshaping
patches = im2col(input)
# Convert [H x W x C] image to matrix of patches
output = matmul(kernel, patches)
# Apply kernels to all patches simultaneously
```

Listing 6: **Matrix Patterns Across Architectures**: Linear layers, attention mechanisms, and convolutions all reduce key work to matrix multiplications, making matrix hardware the shared primitive across modern neural architectures.

^lst-matrix-patterns-77c333fd

These examples differ in tensor shape and reuse pattern, which determines how efficiently each multiplication occupies a matrix unit. Linear layers reuse one weight matrix across a batch; attention forms projections and then a token-to-token score matrix; convolution reuses each kernel across many image patches. Expressing all three as matrix multiplication exposes a common interface to hardware, but it does not make their execution costs identical. Batch size, sequence length, channel count, and tiling determine whether operands are reused locally or repeatedly fetched from memory. For ResNet-50 the lowering is nearly total: every convolution and the final fully connected layer become matrix multiplications, so almost all of its operations run on whatever matrix hardware the accelerator provides. The INT8 profile of **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression#^sec-model-compression|Model Compression]]** is in effect a statement about that hardware.

#### Matrix Operations Hardware Acceleration

^sec-hardware-acceleration-matrix-operations-hardware-acceleration-514a

Accelerators therefore need units that handle whole tiles. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-matrix-unit-4966c580|Listing 7]] demonstrates a representative dedicated matrix unit that processes an entire $16{\times}16$ block at once, illustrating why matrix instructions and Tensor Cores can deliver much higher throughput than scalar or vector-only execution paths ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-nvidia-tensors-fp16-2017-23d257af|NVIDIA 2017]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-intel2021amx|Intel Corporation 2021a]]).

``` c
mload mr1, (weight_ptr)     # Load e.g., 16x16 block of
                            # weight matrix
mload mr2, (input_ptr)      # Load corresponding input block
matmul.mm mr3, mr1, mr2     # Multiply and accumulate entire
                            # blocks at once
mstore (output_ptr), mr3    # Store computed output block
```

Listing 7: **Illustrative Matrix-Unit Operation**: Representative load, matrix-multiply-accumulate, and store instructions operate on matrix blocks rather than individual scalar elements.

^lst-matrix-unit-4966c580

The illustrative unit operates on matrix tiles rather than individual elements. A full $16{\times}16{\times}16$ tile product contains $16^3=4{,}096$ multiply-accumulate operations, but the cycles required depend on the actual instruction and architecture. Sustained throughput also depends on the number of matrix units, operand precision, issue rate, pipeline behavior, and whether memory can keep the units fed. Matrix units complement vector execution by accelerating structured many-to-many transformations.

Much like vector processing, matrix acceleration has deep historical roots; digital signal processors (DSPs) and graphics processors optimized matrix computations in the 1980s–1990s for image processing, scientific computing, and 3D rendering ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-owens2008|Owens et al. 2008]]; [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-hwu2011|Hwu 2011]]). Neural networks have made matrix multiplication commercially dominant, driving the integration of two-dimensional systolic arrays and matrix execution engines (such as NVIDIA Tensor Cores and Google TPUs) directly into processor datapaths.

Linear algebra constitutes only part of the neural network execution pipeline. Between linear transformations, neural networks introduce nonlinear activation functions and normalization layers. While piecewise-linear functions such as ReLU map to simple vector comparison instructions, transcendental computations (such as exponentials in softmax and GELU, or reciprocal square roots in normalization) cannot be computed directly on multiply-accumulate datapaths without incurring severe cycle penalties. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^tbl-matrix|Table 3]] summarizes the execution characteristics of the three primary compute primitives and their mapping to neural network operations.

| **Operation type**         | Best For                  | Examples                                                          | **Key characteristic**                                      |
|:---------------------------|:--------------------------|:------------------------------------------------------------------|:------------------------------------------------------------|
| **Matrix Operations**      | Many-to-many transforms   | Layer transformations, attention, convolutions                    | Each output depends on multiple inputs                      |
| **Vector Operations**      | Vector and reduction work | Activation functions, layer normalization, element-wise gradients | Uses element-wise operations and vector reductions          |
| **Special-Function Paths** | Transcendental arithmetic | Exponential, logarithm, reciprocal square root                    | Uses architecture-specific approximation or dedicated logic |

Table 3: **Operation Characteristics**: Matrix operations excel at many-to-many transformations, while vector units handle element-wise operations and reductions such as activation and normalization. Special-function paths handle transcendental arithmetic through architecture-specific approximation or dedicated logic. The operation structure determines which hardware primitive is appropriate.

^tbl-matrix

### Special Function Units

^sec-hardware-acceleration-special-function-units-ed00

Standard multiply-accumulate hardware evaluates an exponential in softmax, a hyperbolic tangent in GELU, or a reciprocal square root in layer normalization only through a multi-instruction polynomial approximation, which can stall the pipeline between fast matrix kernels. Special Function Units (SFUs) and specialized instruction paths remove this bottleneck, completing the chapter’s trio of processing primitives. The need is not new: floating-point coprocessors addressed scalar arithmetic bottlenecks ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-palmer1980intel8087|Palmer 1980]]), and digital signal processors added specialized arithmetic for signal-processing workloads ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-broesch1997|Smith 1997]]). An implementation may use a standalone unit, vector approximation instructions, or a library sequence, trading accuracy, latency, and throughput. In neural networks, activation, normalization, and softmax operations can become the limiting stage between matrix kernels when repeated memory passes or transcendental functions cap throughput.

#### Nonlinear Functions

^sec-hardware-acceleration-nonlinear-functions-cc93

Non-matrix operators enter the execution pipeline even in a common layer sequence ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-goodfellow2016deep|Goodfellow et al. 2016]]). [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-nonlinear-layer-c18b010e|Listing 8]] chains a linear transformation with ReLU activation and batch normalization, operations that appear trivial in Python framework code but impose distinct arithmetic and memory constraints on hardware.

``` python
layer = nn.Sequential(
    nn.Linear(256, 512), nn.ReLU(), nn.BatchNorm1d(512)
)
output = layer(input_tensor)
```

Listing 8: **Linear–Nonlinear Layer Sequence**: A linear layer, ReLU, and BatchNorm combine matrix, element-wise, and normalization work in one common layer sequence.

^lst-nonlinear-layer-c18b010e

[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-nonlinear-math-a9e30648|Listing 9]] expands this sequence into its arithmetic primitives, isolating the element-wise thresholding of ReLU from the cross-batch reductions and reciprocal square root required by batch normalization. Here rows are samples and columns are features; `weights` has input features by output features, while `bias`, `gamma`, and `beta` contain one value per output feature. Keeping the reduced batch dimension permits those per-feature statistics to broadcast across samples.

``` python
Z = matmul(input, weights) + bias  # Linear transformation
H = max(0, Z)  # ReLU activation
mean = reduce_mean(H, axis=0, keepdims=True)  # BatchNorm statistics
var = reduce_mean((H - mean) ** 2, axis=0, keepdims=True)  # Variance computation
output = gamma * (H - mean) / sqrt(var + eps) + beta  # Normalization
```

Listing 9: **Nonlinear Operation Expansion**: Expanding the layer sequence exposes ReLU comparison, BatchNorm reductions, variance computation, and square-root normalization around the matrix multiply.

^lst-nonlinear-math-a9e30648

#### Hardware Implementation of Nonlinear Functions

^sec-hardware-acceleration-hardware-implementation-nonlinear-functions-1e39

The label *nonlinear* hides three different execution patterns. Pointwise functions such as ReLU leave elements independent and therefore map naturally to vector lanes or parallel threads. Reductions such as the mean and variance in batch normalization introduce cross-element dependencies: partial results must be combined before later stages can proceed. Transcendental functions such as exponential, logarithm, and reciprocal square root add a numerical trade-off because their implementations balance latency, precision, and valid input range. The dependency pattern, not the mathematical label alone, determines whether vector arithmetic, a reduction tree, or a specialized approximation path is appropriate. A faster special-function path accelerates only the operation it implements; it does not remove surrounding tensor traffic or synchronization.

Translating these mathematical functions to silicon exposes sharp differences in memory traffic, instruction count, and pipeline utilization. For instance, batch normalization ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.16 Source References#^ref-ioffe2015batch|Ioffe and Szegedy 2015]]) demands multi-pass statistics gathering across memory, variance accumulation, and a reciprocal square root, while softmax requires computing exponentials across an entire normalization dimension. While a rectified linear unit (ReLU) is mathematically simple, a naive scalar implementation incurs branch overhead or redundant memory round-trips unless fused into adjacent kernels. [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-traditional-overhead-9411d54e|Listing 10]] contrasts the memory and dependency overheads of pointwise activation against multi-pass normalization in an unfused loop model.

``` python
for batch in range(32):
    for feature in range(512):
        # ReLU: Naive scalar compare/select; optimized kernels
        # usually implement this branchlessly.
        z = matmul_output[batch, feature]
        h = max(0.0, z)  # Conditional operation

        # BatchNorm: Multiple passes over data
        mean_sum[feature] += h  # Sum for the mean
        var_sum[feature] += h * h  # Sum of squares for variance

        temp[batch, feature] = h  # Extra memory storage needed

# Normalization requires complex arithmetic
for feature in range(512):
    mean = mean_sum[feature] / batch_size
    var = (var_sum[feature] / batch_size) - mean * mean

    # Square root computation: Multiple iterations
    scale = gamma[feature] / sqrt(var + eps)  # Iterative
    # approximation
    shift = beta[feature] - mean * scale

    # Second pass over data for final computation
    for batch in range(32):
        output[batch, feature] = temp[batch, feature] * scale + shift
```

Listing 10: **ReLU and BatchNorm Operations**: Neural networks process input data through element-wise selections and multiple normalization passes, highlighting efficiency challenges in naive implementations.

^lst-traditional-overhead-9411d54e

[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-traditional-overhead-9411d54e|Listing 10]] is intentionally dependency-explicit rather than a model of an optimized kernel. Normalization cannot begin until the batch statistics are complete, so an implementation must either store each activation, as `temp` does here, or recompute it. Training derives those statistics from the current batch, whereas inference uses stored statistics and reduces normalization to an element-wise affine transform that a compiler can fuse into neighboring kernels.

Naive execution of this dependency graph pays two costs. The pointwise ReLU and normalization scale-and-shift perform little arithmetic per accessed byte, so materializing each pass can place a low bandwidth ceiling on throughput. In this unfused loop model, `temp` is stored and reread after batch statistics are finalized; its physical traffic depends on cache residency and the chosen memory interface. Computing $1/\sqrt{\text{var} + {\epsilon}}$ also adds a dependent arithmetic path. The listing illustrates an iterative approximation, but actual kernels may use a reciprocal-square-root instruction and refinement, with device- and accuracy-dependent latency. Specialized function paths address this arithmetic cost, while legal fusion and local buffering reduce intermediate traffic. Neither removes the need to complete the reductions before normalization.

#### SFU Hardware Implementation

^sec-hardware-acceleration-sfu-hardware-implementation-90ff

SFUs address arithmetic bottlenecks by implementing nonlinear and transcendental operations in specialized functional units rather than multi-instruction software routines. Accelerators deploy dedicated datapath circuits, such as quadratic polynomial interpolators and small lookup tables (LUTs), that evaluate functions like exponential, reciprocal square root, and logarithm within a few pipeline stages. An instruction set exposes these operations alongside vector memory accesses, as the pseudocode of [[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^lst-sfu-vector-ops-fae16786|listing 11]] shows.

``` c
vld.v v1, (input_ptr)    # Load vector of values (pseudocode)
vrelu.v v2, v1           # Vector ReLU path
vsigm.v v3, v1           # Vector sigmoid path
vtanh.v v4, v1           # Vector tanh path
vrsqrt.v v5, v1          # Vector reciprocal-square-root path
```

Listing 11: **Illustrative SFU Operations**: Pseudocode shows vector nonlinear operations that may map to specialized execution paths; instruction names and latency are implementation dependent.

^lst-sfu-vector-ops-fae16786

Specialized function paths balance circuit area against mathematical precision. While piecewise linear activations such as ReLU require only single-cycle compare-and-select (maximum) datapath logic, transcendental functions trade off lookup table size and polynomial interpolation degrees against approximation error. Representative mechanisms and their qualitative latencies differ by function ([[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^tbl-sfu|table 4]]).

| **Function unit**    | Operation               | **Implementation strategy**                    | **Illustrative latency**    |
|:---------------------|:------------------------|:-----------------------------------------------|:----------------------------|
| **Activation unit**  | ReLU                    | Compare-and-select or maximum                  | Low; architecture-dependent |
| **Statistics unit**  | Mean, variance          | Parallel reduction trees                       | Grows with reduction depth  |
| **Exponential unit** | exp, log, sigmoid, tanh | Approximation, table lookup, and interpolation | Architecture-dependent      |
| **Root/power unit**  | sqrt, rsqrt             | Iterative or approximation hardware            | Architecture-dependent      |

Table 4: **Special Function Units**: Dedicated paths reduce instruction overhead for nonlinear and reduction primitives. Implementations and latency are architecture-dependent; the table describes mechanisms rather than universal cycle counts.

^tbl-sfu

The two lighthouses use this path differently. ResNet-50 barely touches it. Its only activation is ReLU, a comparison. At inference its BatchNorm layers use frozen statistics, so a compiler can fold them into the weights of the preceding convolution (**[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^sec-model-compression-operator-fusion-ac1d|Compression-specific fusion]]**), leaving no reciprocal square root to run per image. The only exponentials are the thousand in the final softmax, one per ImageNet class. GPT-2 XL leans on it at every step, because each attention head applies softmax across the whole context and each feed-forward block applies GELU, so its special-function work grows with sequence length while ResNet-50’s stays fixed.

Vector operations, matrix operations, and special-function paths establish the foundational arithmetic primitives of ML accelerators, but functional units alone do not dictate sustained throughput. These primitives govern *what* the silicon computes; the execution model and memory hierarchy govern *how* data feeds the datapath. A matrix unit rated for hundreds of teraFLOP/s will idle if memory bandwidth cannot sustain operand delivery, if tile dimensions mismatch register blocking, or if thread synchronization serializes execution. Peak assumes operands are always ready; the execution model decides how much of it a real workload achieves.
