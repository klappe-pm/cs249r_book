# V1-12.03 Benchmark Carpentry

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12 Benchmarking|V1-12 Benchmarking]]

^sec-benchmarking-benchmark-components-97cc

A claim that ResNet-50 runs faster at INT8 than at FP32 can reverse depending on whether timing starts at a JPEG on storage or at a preprocessed tensor in accelerator memory, or whether the quantized weights drop accuracy below the target floor. **Benchmark carpentry** is the craft of building a benchmark that measures what its claim says. It fixes the task, data, model, metrics, harness, system specification, and run rules so that the number the benchmark produces answers the engineering question and no other. Together these fixed choices are the benchmark’s specification. A synthetic matrix-multiplication loop, a ResNet-50 training run over ImageNet, and a full serving pipeline all need these specifications, and changing one component changes what the next can measure. The components follow the D·A·M taxonomy. The problem definition fixes the input representation (Data). The dataset and task objective bound the feasible models (Algorithm), because a candidate model must reach the quality target on that data before its speed matters. The target hardware’s memory, energy envelope, and deadlines bound how the model may execute (Machine).

Evaluating an ML system requires coupling statistical task metrics with physical efficiency metrics. Quantization and pruning reduce parameter footprint and memory bus traffic, but they alter numerical representations and risk degrading task accuracy. A benchmark that records execution latency without statistical accuracy (such as classification error) rewards aggressive approximations that produce invalid outputs. Conversely, reporting accuracy without latency or memory consumption conceals whether the model satisfies the target system’s physical constraints.

The measurement harness and run rules provide the experimental controls that make these evaluations reproducible. The protocol follows the question being tested. A controlled steady-state experiment can use warm-up iterations, fixed processor clocks, and pinned (page-locked) host memory, which the accelerator can copy from directly, to isolate execution differences. A deployment benchmark instead retains the relevant dynamic voltage and frequency scaling (DVFS) policy, cold starts, and competing workloads, documenting their effects. Recording tail latency distributions (p95, p99) alongside the mean exposes delays hidden by averages. Each component is built here on the claim the chapter inherited, that ResNet-50 runs faster at INT8 than at FP32, and MLPerf Tiny’s anomaly-detection benchmark at the end shows every component fixed at once on a small embedded model.

### Turning a Claim into a Test

^sec-benchmarking-problem-definition-79e4

Every benchmark begins as a claim. The claim from the preceding chapters, that ResNet-50 at INT8 runs faster than at FP32 without unacceptable accuracy loss, is not yet testable, because it names neither the inputs, the output, nor the conditions under which faster must hold. Fixing those boundaries is the first act of carpentry. This chapter designs the test that would settle the claim; it does not report a result, which depends on the accelerator a team runs it on. Without an explicit task specification, hardware and software optimizations cannot be evaluated on equivalent terms: altering an input resolution, a numerical datatype, or a latency deadline changes how much work the machine does. For ResNet-50 the input is a decoded $224{\times}224$ RGB image and the output is one of a thousand ImageNet class labels. Whether the task is natural language processing ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-hirschberg2015|Hirschberg and Manning 2015]]) or computer vision ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-everingham2009|Everingham et al. 2009]]; [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-lin2014microsoft|Lin et al. 2014]]), a complete problem definition establishes three specifications: an input specification, an output specification, and a performance specification.

The input and output specifications fix the data each run must move and define the exact scope of timed execution. The input specification fixes tensor dimensions, batching behavior, numerical representations (such as FP16 or INT8), and ingestion rates. For the ResNet-50 claim, it decides whether timing starts at a JPEG on storage or at a preprocessed tensor already in accelerator memory, a choice that can change the measured time more than the precision change being tested. Conversely, the output specification defines the termination boundary of the computation. Benchmarks frequently introduce measurement bias by timing only accelerator forward passes while ignoring the CPU post-processing required to turn raw tensor outputs into usable decisions. A robust output specification defines whether the system emits raw logits, intermediate embeddings, or final class labels, accounting for any downstream thresholding or reduction kernels that consume host memory bandwidth.

The performance specification defines the operational envelope that governs whether an optimization is viable. Unconstrained throughput numbers are meaningless if statistical accuracy degrades below acceptable thresholds, and high average throughput cannot rescue a system that violates a latency SLO. For the ResNet-50 claim, the performance specification couples a quality floor (MLPerf Training requires 75.9 percent top-1, and an INT8 deployment might permit at most one percentage point of loss against FP32) with hardware execution limits. These are a tail-latency ceiling, sustained throughput matching the arrival rate of images, and a resident memory footprint that leaves room for activations at the chosen batch size. By defining these three boundaries up front, the benchmark ensures that the later stages, from dataset construction to measurement harness configuration, evaluate system optimizations against the true operational constraints of deployment.

### Task and Dataset

^sec-benchmarking-standardized-datasets-123f

Fixing ResNet-50’s quality floor at 75.9 percent top-1 accuracy means nothing until the evaluation dataset itself is fixed, because a team that tests its INT8 model on a private slice of easy daytime photographs can claim no accuracy loss while a team testing on all 50,000 ImageNet validation images sees a regression. Standardized datasets enforce identical evaluation conditions across competing approaches, preventing teams from cherry-picking private slices that obscure comparative weaknesses. In computer vision, ImageNet ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-imagenet-website-32504219|Deng et al. 2024]], [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-deng2009|2009]]), COCO ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-lin2014microsoft|Lin et al. 2014]]), and CIFAR-10 ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-cifar10-website-87d86101|Krizhevsky 2009]]) establish reference tasks across classification and detection. In natural language processing, SQuAD[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn3|³]] ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-rajpurkar2016|Rajpurkar et al. 2016]]), GLUE[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn4|⁴]] ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-wang2018|Wang et al. 2018]]), and WikiText ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-wikitext-website-337c6b77|Merity 2016]]; [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-merity2016pointer|Merity et al. 2016]]) fulfill equivalent roles by standardizing comprehension, classification, and language modeling across diverse textual domains.

Even a standardized dataset is the first place a benchmark can lose contact with deployment reality. ImageNet’s validation set fixes ResNet-50’s quality target, but its curated, centered photographs are not the frames a camera trap returns at dusk, a gap that [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.10 Model and Data Evaluation#^sec-benchmarking-data-benchmarking-22f9|section 12.9.2]] returns to. A benchmark dataset must be representative enough to expose deployment failures and hard enough to separate models, so that the model architecture and metrics chosen next are tested against meaningful inputs.

### Model and Metrics

^sec-benchmarking-evaluation-metrics-6bac

Even on the same ImageNet validation split, two ResNet-50 benchmarks cannot be compared if one team alters layer widths or swaps the runtime while the other changes the accelerator. In systems benchmarking, the model defines the execution workload because its computational graph sets arithmetic intensity, memory footprint, and communication topology. Selecting and fixing the benchmark model determines whether measured performance variations reflect architectural efficiency, software runtime optimizations, or raw accelerator capacity. Evaluating an architectural modification requires holding the runtime and hardware target constant. Conversely, evaluating hardware platforms or software execution engines requires standardizing on a fixed, representative model graph so that throughput differences isolate execution efficiency rather than mathematical changes to the workload.

Baseline models establish the empirical reference point for a target domain. Rather than toy algorithms, systems benchmarks rely on canonical workloads whose computational profiles and memory access patterns are well-characterized. In vision, ResNet-50 plays this role, which is why the chapter’s claim is stated on it. In language processing, BERT[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn5|⁵]] serves as a standard baseline because its multi-head self-attention and dense feed-forward blocks exercise both compute-bound matrix multiplications and memory-bandwidth-bound reduction operations.

A baseline specification, however, cannot stop at the mathematical graph. Two implementations of the identical architecture across different frameworks or runtimes often behave differently at runtime. Differences in kernel fusion (such as applying normalization and activation inside the matrix-multiplication kernel, so its output is not written to high-bandwidth memory (HBM) and read back), kernel launch overhead, and memory allocator behavior can exceed the performance impact of minor architectural variations. A comparison that isolates hardware must control the runtime implementation alongside the mathematical model. A runtime comparison instead names that implementation as the intervention and documents both stacks.

A benchmark must select the operational regime relevant to its engineering question. In training, memory capacity and interconnect bandwidth can be limiting constraints, because storing forward activations, backward gradients, and optimizer states across multiple accelerators limits batch size and demands high-bandwidth collective communication. Training benchmarks therefore measure time-to-accuracy under fixed convergence criteria rather than raw iteration speed alone. In inference, backward passes and optimizer states disappear. Evaluation instead emphasizes the serving objective, such as a tail-latency SLO.

Transitioning a model to production frequently requires precision reduction, quantizing FP32 or BF16 weights and activations to INT8 or FP8. Moving eligible tensors from a 16-bit to an 8-bit format halves their raw storage and can reduce traffic or raise supported arithmetic throughput. Whole-model gains depend on the execution path, and validation must establish whether numerical error stays within the quality target. Because efficient training does not establish serving feasibility, a claim that spans development and deployment needs training and inference measured separately. A deployment decision for a fixed pretrained model can measure inference alone.

Fixing the model and its regime settles what runs; the remaining choice is which numbers the run reports. Evaluation metrics[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn6|⁶]] translate raw model behavior into numbers that can be compared, ranked, and used to make engineering decisions. The difficulty lies in choosing the right numbers. A metric that captures accuracy but ignores latency may declare the winner to be a model too slow for production; one that rewards throughput but ignores energy may optimize for a deployment budget that does not exist. [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^tbl-metric-taxonomy|Table 3]] categorizes evaluation measures by the failure mode each exposes and the deployment context it serves.

^tbl-metric-taxonomy

The metrics in [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^tbl-metric-taxonomy|table 3]] expose physical trade-offs governed by the accelerator architecture. Throughput measures aggregate processing capacity, whereas latency measures individual request completion time. These two objectives conflict directly at the hardware boundary. Maximizing throughput requires grouping requests into larger batches, and each request then waits while its batch forms and while the larger operation runs.

Even at a fixed batch size, the arithmetic mean of latency masks tail behavior. Queuing jitter, memory allocation stalls, and accelerator thermal throttling cause execution times to diverge; a system with a 10 ms mean latency can still suffer a 500 ms p99 latency that violates its latency SLO. Benchmarks must therefore report distribution percentiles (p50, p95, p99) rather than averages.

Compound metrics such as samples/second/watt compress multiple dimensions into a single scalar, simplifying high-level comparisons but obscuring where bottlenecks reside. Reporting atomic metrics (latency distributions, throughput, and power draw) alongside compound figures isolates which physical constraint limits the system.

↪ The batch size at which waiting for a batch to form pushes latency past its budget is measured with a batch-size sweep in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-batching-tax|Formation delay and the latency-throughput frontier]]**.

Task-specific metrics evaluate the algorithmic dimension, quantifying whether the model solves the statistical problem. Classification workloads evaluate accuracy (the fraction of correct predictions), precision (the fraction of predicted positives that are correct), recall (the fraction of actual positives the model finds), and the F1 score (their harmonic mean) ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-sokolova2009|Sokolova and Lapalme 2009]]). Precision and recall isolate true positive rates from false alarms, which is essential when class distributions are imbalanced. Continuous estimation tasks rely on Mean Squared Error (MSE) or Mean Absolute Error (MAE), while sequence generation uses specialized scoring rules such as BLEU[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn7|⁷]] to measure modified n-gram precision against human reference translations ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-papineni2001|Papineni et al. 2002]]).

Task metrics evaluate algorithmic quality in isolation, but deployment viability depends on physical machine constraints. Model capacity, measured in parameter count and memory footprint, determines whether weights fit into on-chip SRAM or accelerator memory, or whether they spill across high-latency interconnects. Per-inference execution latency dictates whether a system meets real-time deadlines, while energy consumption per inference (measured in joules or millijoules) bounds thermal dissipation and battery life.

Benchmarks must also account for measurement sensitivity across software runtimes. Frameworks differ in how they fuse kernels (**[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8|The memory wall and kernel fusion]]**), and training code differs in how it computes the loss and accumulates gradients (**[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training#^sec-model-training|Model Training]]**), so the same model can report different numbers on different software stacks. Subtle implementation differences shift measured accuracy and latency enough to invert benchmark rankings when candidate models differ by narrow margins. Examples include whether batch normalization is configured to use stored running statistics or current mini-batch statistics during evaluation, and how reduction kernels reorder non-associative floating-point additions. Controlling how the runtime is driven and how those metrics are timed is the job of the benchmark harness.

### Benchmark Harness

^sec-benchmarking-benchmark-harness-09ea

When host software initiates an inference or training step on an accelerator, the framework runtime enqueues commands onto a work queue (such as a CUDA stream or hardware command buffer) and returns control to the CPU in microseconds. A naive timer wrapping that host-level call measures queue dispatch rather than device execution. Avoiding such measurement traps is the job of the benchmark harness, the software and instrumentation scaffold that feeds inputs to the system under test, coordinates execution across the asynchronous host-accelerator boundary, collects timing and power traces, and enforces reproducibility. A rigorous harness inserts explicit device synchronization barriers (such as `torch.cuda.synchronize()`) or queries on-device timestamp events (such as `torch.cuda.Event`), ensuring that recorded timings cover the declared device-work interval rather than host enqueue overhead.

The timer endpoints determine which work enters the result. [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^fig-benchmark-async-timing|Figure 1]] separates the host call, the synchronized host interval, and the device-event interval for one inference.

![[90 Assets/Volume I/12 Benchmarking/Generated Figure 623bc3169c.svg]]

Figure 1: **Timing Across an Asynchronous Boundary**: The host call returns after enqueueing work, before the accelerator completes it. A synchronized host timer spans enqueueing through completion; device events measure elapsed time between their positions on the stream. The timing boundaries determine whether transfers and other queued work are included.

^fig-benchmark-async-timing

These intervals answer different questions. Earlier device work must finish before the host timer starts, or work still queued from previous calls is counted in the interval. A synchronized host interval then measures elapsed completion time under the stated synchronization boundary, whereas events measure the interval between their positions in the accelerator stream. A report must state those boundaries before comparing two implementations; neither method includes work that falls outside them.

Harness architecture must align with the operational regime of the deployment target. In server environments, the harness generates concurrent request traffic using an open-loop load generator, often parameterizing inter-arrival times with a Poisson distribution.[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn8|⁸]] An open-loop harness issues requests according to an independent arrival schedule regardless of server responsiveness. This decoupling exposes queuing delays and tail latency (such as p99 response times) when arrival bursts saturate available compute.

In contrast, a naive benchmarking client often employs a closed-loop pattern: sending a request, blocking until the response arrives, and only then issuing the next request. This design introduces the severe measurement distortion known as **coordinated omission**. Consider a server that experiences a transient 500 ms garbage collection pause or memory reallocation stall. In an open-loop production environment, independent users continue submitting queries, causing dozens of requests to accumulate in the server’s ingress queue; once the pause ends, every queued query suffers inflated tail latency. In a closed-loop benchmark, however, the client blocks idly during the entire 500 ms pause, sending zero traffic while the server is struggling. The benchmark records a single slow query and zero queue backlog. By coordinating request generation with server responsiveness, the closed-loop harness artificially paces traffic, systematically erasing the very queue collapse and p99 latency spikes it was constructed to measure.

The missing requests are the source of the distortion. [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^fig-benchmark-coordinated-omission|Figure 2]] aligns the two arrival policies against one server pause so that the change in offered work remains visible.

![[90 Assets/Volume I/12 Benchmarking/Generated Figure c22d239f32.svg]]

Figure 2: **A Pause Under Two Arrival Policies**: Each green interval runs from a request arrival to its response. Independent arrivals continue through the same server pause, while one closed-loop client waits for a response before sending again. The resulting workloads differ, so the closed-loop sample omits delays that the independent stream would experience. The timeline is schematic.

^fig-benchmark-coordinated-omission

A closed-loop result is valid for a population whose clients wait in this way. It does not by itself estimate latency for an independent arrival stream, because it reduces the offered load, the rate at which clients submit requests, precisely when the server slows. The harness must therefore reproduce the deployment arrival policy or report why a different policy answers the intended question. Server clients arrive independently of one another, so a serving benchmark defaults to an open-loop harness with synchronized device timing.

A third arrival policy, offline batch processing, eliminates arrival scheduling entirely. The harness pre-stages large input batches in memory to saturate accelerator execution units, maximize memory bandwidth utilization, and measure peak sustained throughput.

In embedded and edge deployments, workloads are neither stochastic network streams nor unconstrained batch queues. Instead, inputs arrive sequentially from physical sensors (such as an audio analog-to-digital converter or an image sensor) governed by fixed hardware sampling clocks. The harness must feed these sensor streams into limited on-chip SRAM buffers at their sampling rate and verify that each inference completes before the next sample arrives, because a late inference overflows the buffer. Edge harnesses must also measure voltage and current directly across active execution cycles and low-power sleep states to capture the true energy consumed per inference.

Reproducibility requires specifying which runtime and environmental conditions are controlled and which are part of the workload. Warm-up matters at every scale, from a single kernel to a whole run, because modern accelerators and runtime frameworks have substantial cold-start transients. Initial inference passes trigger on-demand memory allocations, dynamic just-in-time (JIT) compilation, driver initialization, and weight transfers from secondary storage into accelerator memory. For steady-state measurements, the harness executes unmeasured warm-up iterations until caches populate, memory allocators stabilize, and the intended thermal operating state is reached. Controlled experiments may fix clocks and remove competing processes; deployment tests retain and report the relevant DVFS policy and contention. Cold-start measurements time initialization separately instead of discarding it. Finally, telemetry logging must minimize the probe effect by recording execution timestamps and performance counters into non-blocking, pre-allocated memory buffers. The remaining instrumentation overhead should be checked against a minimally instrumented run.

### Specifications and Run Rules

^sec-benchmarking-run-rules-c33f

Even a well-instrumented harness produces an uninterpretable number if the report omits the machine and the rules under which the harness ran. A throughput figure reported without accelerator model, memory bandwidth, or operating clocks conceals whether an observed speedup stems from algorithmic efficiency or upgraded silicon, and a result reported without its seed policy conceals whether it is reproducible at all, because the stochastic processes examined in [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.05 Benchmark Suites#^sec-benchmarking-ml-measurement-challenges-60ea|section 12.4.2]] mean that two runs on identical hardware can produce different numbers.

System specifications record the computational environment, the physical hardware and software stack that establishes the Machine ($\text{M}$) boundaries of the system, while run rules govern how the benchmark executes on it. The hardware must be recorded because every execution metric reflects the interaction between an algorithm’s arithmetic intensity and a machine’s peak arithmetic throughput, memory bandwidth, and interconnect latency. The run rules must address randomness because training is stochastic, so a protocol either fixes seeds and data order when isolating system effects or requires repeated runs and quality thresholds when stochastic variation is part of the workload. [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^tbl-benchmarking-spec-run-rules|Table 4]] lists what a reproducible report records.

| **Item**                       | **What the report records**                                                                | **Why the result depends on it**                                          |
|:-------------------------------|:-------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------|
| **Accelerator**                | Microarchitecture, active core count, base and boost clocks, power limit (TDP)             | Sets the peak arithmetic rate and how long boost clocks persist           |
| **Device memory**              | Capacity, bus width, peak bandwidth                                                        | Sets the bandwidth ceiling and the largest batch that fits                |
| **Multi-accelerator topology** | Host interface (PCIe lanes) and accelerator links (NVLink or shared PCIe switches)         | All-reduce time is bounded by link bandwidth and topology                 |
| **Software stack**             | Operating system, driver, compute runtime (CUDA or ROCm), math libraries (cuBLAS, CUTLASS) | Kernel selection, tiling, and reduction order change with library version |
| **Framework layer**            | Framework version, eager or compiled execution (`torch.compile`), fusion settings          | Separates framework overhead from model cost                              |
| **Power and thermal**          | Sustained board power, throttling events, energy per sample or token                       | A speedup from transient clock boosting does not persist                  |
| **Randomness**                 | Seed policy, data order, known nondeterministic kernels                                    | Two runs on identical hardware can produce different numbers              |
| **Configuration**              | Every hyperparameter, including the learning-rate schedule                                 | A learning-rate change shifts convergence and final accuracy              |
| **Data**                       | Dataset version, splits, preprocessing; any privacy or licensing limit on sharing          | Different splits or preprocessing define a different workload             |
| **Code**                       | Version of model, preprocessing, training, and evaluation code; container image            | Lets another team inspect and, where access permits, reproduce the run    |

Table 4: **Benchmark Specification and Run Rules**: What a reproducible benchmark report records about the machine, the software, and the run, and why each item changes the measured result.

^tbl-benchmarking-spec-run-rules

Reference suites may distribute containerized environments that encapsulate dependencies and configurations, while experimental logs retain training metrics, checkpoints, and any mid-run adjustments. Together, these records turn a one-time measurement into evidence another team can inspect and, when access permits, reproduce.

### Interpreting Results

^sec-benchmarking-result-interpretation-cd29

Once the harness and run rules produce a number, such as a 2 ms inference latency or a 10,000 images/s throughput figure, a single metric still rarely reveals whether an optimization will succeed in deployment. Turning raw benchmark numbers into an engineering decision requires checking both the experimental intervention and the execution state. Checking the intervention means stating what changes and what remains comparable. ResNet-50 versus MobileNet can be a valid architecture comparison at matched task and quality requirements; FP32 versus INT8 can be a valid precision comparison on a supported execution path. Either comparison holds the other relevant conditions fixed or reports their changes, including batch size, hardware, runtime, input distribution, and service targets.

Checking the execution state means separating steady-state execution from initialization, using the harness’s warm-up protocol ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^sec-benchmarking-benchmark-harness-09ea|section 12.2.4]]). A single run conflates cold-start overhead (kernel compilation, page faults, and cache warming) with sustained throughput, while a prolonged stress test may instead capture the thermal throttling examined for edge devices in [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.07 Inference Benchmarks#^sec-benchmarking-mobile-edge-benchmarks-fd4f|section 12.6.4]]. The report gives cold-start or steady-state results as the deployment question requires and records variation across repeated trials. Whether a measured difference exceeds that variation is a statistical question, answered with the interval and paired-test rules of [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.09 Benchmarking Best Practices#^sec-benchmarking-statistical-methodological-issues-7aa5|section 12.8.1]].

**Systems Perspective 12.3: Interpreting a benchmark claim**

A vendor claims “Our system achieves 10,000 inferences/second on ResNet-50.” Taken alone, the number cannot support deployment planning because the conditions that determine its meaning are unstated.

Four unstated conditions determine what the claim means:

1.  **Batch size**: Large batches can raise compute utilization but inflate queuing delay; batch 1 minimizes latency but leaves execution units underutilized.
2.  **Precision**: INT8 execution exploits higher-throughput integer pipelines and cuts memory traffic, but requires quantization-range calibration that can compromise numerical fidelity.
3.  **Measurement boundary**: The measurement window must state whether it isolates pure accelerator kernel execution or includes host-to-device transfers, JPEG decoding, and tensor format conversions.
4.  **Accuracy**: The claim must state whether the optimized model retains baseline validation accuracy (such as the 76.1 percent top-1 a standard FP32 ResNet-50 reaches on ImageNet, above MLPerf Training’s 75.9 percent target) or trades task quality for raw execution speed.

**Example**: “10,000 inferences/second on ResNet-50 at batch size 32, INT8 precision, 76 percent Top-1 accuracy, including JPEG decoding, on NVIDIA H100 at 700 W thermal design power (TDP).”

A claim whose workload boundary, precision, and excluded costs cannot be reconstructed should be rejected. Marketing phrases compress such omissions into a few words, usually reporting the most favorable operating point without saying so. [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^tbl-benchmarking-vendor-claims|Table 5]] translates common ones into the technical caveats behind each.

| **Vendor Claim**               | **What It Often Means**                                            |
|:-------------------------------|:-------------------------------------------------------------------|
| **“Up to 10,000 images/sec”**  | Peak throughput at maximum batch size, INT8, without preprocessing |
| **“Sub-millisecond latency”**  | Accelerator compute only, excluding data transfer                  |
| **“5$\times$ more efficient”** | Per-operation efficiency, not total system efficiency              |
| **“Optimized for AI”**         | May only accelerate specific operations or precisions              |

Table 5: **Decoding Vendor Benchmark Claims**: Four common marketing phrases and the technical caveats that determine whether a claim describes end-to-end performance, a narrow accelerator measurement, or an unsupported efficiency comparison.

^tbl-benchmarking-vendor-claims

Which metric governs viability depends on the deployment. In safety-critical applications such as medical imaging or autonomous driving, a 1 percent accuracy gain justifies substantial computational cost. In interactive search or speech transcription, tail latency within a tight latency SLO dominates, so a minor accuracy gain is irrelevant if it breaches the latency budget.

Systems evaluation must also guard against *benchmark overfitting*, in which an optimization targets the idiosyncratic computational patterns of a standardized suite at the expense of production workloads. For example, aggressive kernel fusion or operator tiling tuned exclusively for fixed sequence lengths in a benchmark harness can degrade throughput when deployed against dynamic, variable-length user requests. Robust interpretation requires validating performance across diverse input distributions, perturbed batch sizes, and representative operational duty cycles.

**Checkpoint 12.1: Decoding vendor benchmark claims**

When evaluating hardware or software based on vendor-reported benchmarks, check whether the claim identifies the workload, measurement boundary, and operating conditions.

Measured quantity: Does the latency number include preprocessing and postprocessing, not just model execution?

Precision boundary: Can the precision behind a throughput claim, such as INT4 versus INT8 or FP16, be identified?

Workload boundary: Are the model, batch size, and input distribution used to produce the comparison explicitly named?

Excluded costs: Are memory transfers, model loading, initialization, sustained thermal behavior, and power accounted for at the claimed performance level?

Claimed vs. achieved: Given a 1,000 TFLOP/s peak claim and a benchmark that sustains 350 TFLOP/s, estimate the MFU and state whether that utilization ratio alone identifies the bottleneck.

### A Complete Reference Benchmark

^sec-benchmarking-example-benchmark-229f

MLPerf Tiny’s anomaly-detection benchmark shows every component fixed at once on one small embedded model. The multi-stage pipeline in [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^fig-benchmark-components|figure 3]] traces this industrial audio benchmark across nine sequential phases. It carries the task from problem definition in the top chevrons through spectrogram extraction, autoencoder training, and INT8 quantization down to embedded deployment on an ARM mbed OS microcontroller. Each stage fixes boundary conditions for the next, from the input representation (Data) through the feasible models (Algorithm) to the device limits (Machine). On the microcontroller the Machine constraints are unusually tight. SRAM capacity, the energy envelope, and real-time deadlines dictate INT8 quantization and memory-efficient kernel compilation. Because every choice constrains the next, a benchmark that measures only classification accuracy or only raw inference latency misses cross-stage interactions, where an engineering decision at any stage narrows the feasible design space downstream.

Its problem definition fixes the same three specifications that the ResNet-50 claim needed. The input is single-channel audio streamed at 16 kHz in fixed one-second windows, which sets a rigid ingestion rate and memory buffer requirement before feature extraction begins. The model is an autoencoder, a network trained to reproduce normal machine sounds at its output, so a sound it reconstructs poorly (a large reconstruction error) signals an anomaly. The output is a binary “Normal” or “Anomaly” flag, including any thresholding that turns a reconstruction error into that decision. The performance specification couples a quality metric with execution limits. The quality metric is the area under the ROC curve (AUC), which scores the detector across every setting of that threshold rather than at one. The execution limits are a per-inference latency that keeps pace with the one-second input windows, sustained throughput matching the arrival rate, and a resident footprint that avoids out-of-memory faults on the microcontroller.

At the dataset selection stage (the second chevron), the benchmark pipeline ingests representative audio waveform samples of normal machine operation alongside anomalous conditions before spectrogram feature extraction. Domain-specific collections cover different audio tasks: ToyADMOS[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn9|⁹]] ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-koizumi2019|Koizumi et al. 2019]]) supports controlled anomaly-detection research, while Google Speech Commands ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-warden2018speech|Warden 2018]]) supports keyword recognition. Simplified datasets like ToyADMOS are valuable for methodological development but may not capture the full complexity of production environments.

The dataset also decides which quality metric the benchmark can trust. In industrial monitoring, extreme class imbalance renders raw accuracy deceptive. If anomalies constitute only 0.1 percent of operating samples, a trivial model that constantly predicts normal operation achieves 99.9 percent accuracy while failing to detect any faults. The benchmark must instead report AUC, which scores how well the model ranks anomalous samples above normal ones across every decision threshold, alongside physical resource metrics.

This multi-metric evaluation approach governs the anomaly detection pipeline, which balances four simultaneous constraints. The model has 270K parameters, and its stored representation and runtime buffers must fit the embedded SRAM budget. Processing takes 10.4 ms per inference, which maintains real-time sampling. Detection accuracy is 0.86 AUC. Energy consumption is 516 µJ per inference, within the target battery budget. Evaluating across all four axes prevents declaring a model superior when its accuracy gain stems from an architecture too large to fit in memory or too power-hungry to survive sustained deployment.

The deployed anomaly detection workflow in [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^fig-benchmark-components|figure 3]] records the four measurements from [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^sec-benchmarking-evaluation-metrics-6bac|section 12.2.3]] in its terminal reporting table (lower right). For the fully connected autoencoder (FC-AE) on the ARM mbed OS target, each certifies something different. Parameter count and per-inference latency certify computational resources, the AUC certifies task effectiveness, and energy per inference certifies operational efficiency.

On a microcontroller, each metric governs a different failure: energy per inference sets battery life on untethered devices, model size decides whether weights fit in fast on-chip SRAM or spill into off-chip DRAM, and latency determines whether streaming audio is processed without dropped frames. The metrics trade against one another. Reducing model size below 270K parameters can reduce memory traffic and execution time on a supported path, but risks degrading the 0.86 AUC detection accuracy. Whether these measurements constitute a passing benchmark depends on the operational envelope; the benchmark specification standardizes the evaluation protocol, but application requirements dictate the acceptance thresholds.

The reference flow fixes the task, data, model, and measurement boundary, but it measures one model on one device at one scope. Before choosing that scope, a benchmark should pass three methodological checks.

**Checkpoint 12.2: Benchmarking methodology**

Three practices distinguish rigorous benchmarks from misleading ones:

Representative data: Compare the benchmark input distribution against the production distribution.

Warm-up: State whether the goal is steady-state or cold-start performance, and which initialization work is timed or discarded.

Isolation: Document the machine, runtime, and competing workloads; explain which controls isolate the intervention and which conditions represent deployment.

A benchmark that passes those checks has still made a second choice, often implicitly. It decides how much of the system it measures. A single kernel, the whole model, and the request path around the model each answer a different question, and each fails in a different way.
