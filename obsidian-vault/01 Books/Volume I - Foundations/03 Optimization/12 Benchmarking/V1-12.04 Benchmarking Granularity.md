# V1-12.04 Benchmarking Granularity

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12 Benchmarking|V1-12 Benchmarking]]

^sec-benchmarking-benchmarking-granularity-3855

A kernel that runs 3× faster in isolation may deliver no end-to-end speedup if the data pipeline cannot keep the accelerator fed. In an illustrative request, a 3× inference speedup applied to a 10 ms model stage inside a 50 ms request yields only about a 1.2× end-to-end improvement, or less if the optimization increases memory pressure. The dilution makes the measurement boundary a design choice. Carpentry specifies *how* a measurement is built, while **benchmarking granularity** specifies *what* physical boundary it measures. System validation spans multiple architectural scales, from individual tensor operations to complete production pipelines, with each granularity diagnosing distinct bottlenecks:

- Micro benchmarks isolate individual components: kernel execution time, memory bandwidth utilization, and single-layer numerical behavior. These diagnose *where* low-level hardware inefficiencies occur.
- Macro benchmarks evaluate composed model subsystems: full model training convergence, inference pipeline throughput, and dataset accuracy metrics. These reveal *what* architectural trade-offs exist across layer compositions.
- End-to-end benchmarks measure complete operational pipelines: client request-to-response latency including preprocessing, training time-to-accuracy including storage I/O, and model robustness on production data distributions. These show whether the combined system satisfies real-world service-level objectives.

![[90 Assets/Volume I/Shared Figures/Vol1 Benchmarking Margin 001 ca3d30ea35.svg]]

*Two stacked latency bars compare before and after a 3 times model-stage speedup: the model segment shrinks, but the other pipeline work remains, so 50 milliseconds only falls to about 43 milliseconds.*

*Component speedup rarely survives as end-to-end benchmark speedup.*

Optimization techniques operate across distinct granularities: kernel fusion targets micro-level execution, structured pruning alters macro-level parameter structures, and data curation determines end-to-end generalization. System validation must align with these respective boundaries. An isolated micro-benchmark may show substantial kernel speedup, yet a macro-benchmark can reveal that increased activation memory footprints force smaller batch sizes that degrade overall throughput. Similarly, an end-to-end benchmark exposes storage or host deserialization stalls that remain invisible at the accelerator kernel level.

Measurement perimeters widen from left to right in [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.04 Benchmarking Granularity#^fig-granularity|figure 4]], and the figure inserts one tier between macro and end-to-end. Micro-benchmarks isolate kernel layers (ML Layers) and macro-benchmarks evaluate composed models (ML Model). An application benchmark then adds the supporting host compute around the model (AI Task), and the end-to-end benchmark adds the non-AI compute nodes the request also traverses. The three granularities in this section fold the application tier into end-to-end, but the four-tier view shows where bottlenecks migrate as the boundary widens: out of the accelerator and into the host systems around it.

### Micro Benchmarks

^sec-benchmarking-micro-benchmarks-7f5a

While end-to-end metrics decide whether a service meets its SLO, optimizing an accelerator pipeline requires isolating the specific mathematical operations that consume execution time and energy. Micro-benchmarks serve this diagnostic role by evaluating individual tensor operations in isolation, measuring the accelerator’s hardware primitives directly. When profiling a slow inference service, macro-benchmarks report aggregate latency violations, but only micro-benchmarks reveal whether execution time is dominated by matrix multiplications, self-attention projections, memory copies across the host-accelerator interconnect, or elementwise activation kernels.

↩︎ The compute primitives that micro-benchmarks isolate, vector and matrix operations and special function units, are established in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^sec-hardware-acceleration-ai-compute-primitives-2c99|Compute Primitives]]**.

Tensor operations constitute the primary target of micro-benchmarking because matrix multiplications and convolutions dominate the arithmetic budget of deep neural networks. Highly optimized runtime libraries such as cuDNN[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn10|¹⁰]] ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-chetlur2014cudnn|Chetlur et al. 2014]]) provide hand-tuned kernel implementations tailored to specific microarchitectures. Micro-benchmarks also evaluate standalone activation functions (such as ReLU, Sigmoid, and GELU) and structural submodules (such as multi-head attention projections or transformer feed-forward blocks) across standardized input shapes. Benchmark suites such as Baidu’s DeepBench ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-deepbench-github-5141a735|Baidu Research 2016]]) formalized this methodology by evaluating raw general matrix multiply (GEMM), convolution, and collective communication primitives across diverse hardware platforms, isolating silicon-level execution efficiency from higher-level framework dispatch overhead.

Measuring isolated kernels requires rigorous experimental control. Without disciplined measurement protocols, dynamic hardware frequency scaling, asynchronous execution queues, and cache state introduce transient artifacts that distort kernel runtime.

**Systems Perspective 12.4: Micro-benchmarking rules**

Five rules keep a micro-benchmark measuring the kernel rather than a hardware artifact:

1.  **The warm-up rule**: Do not measure cold-start iterations as steady-state performance. Modern hardware uses DVFS and dynamic frequency boosting; caches, kernels, and clocks need warm-up before the measured loop represents sustained behavior.
2.  **The variance rule**: Report the coefficient of variation (CV) $(\text{CV} = {\sigma_{\text{run}}}/ {\mu_{\text{run}}})$, where ${\sigma_{\text{run}}}$ and ${\mu_{\text{run}}}$ are the standard deviation and mean across repeated runs. Investigate values above the protocol’s workload-specific tolerance; common causes include background OS jitter, thermal throttling, and memory contention, and 5 percent is not a universal cutoff.
3.  **The “speed of light” (SOL) check**: Compare the achieved throughput against the roofline. If a kernel achieves 10 TFLOP/s on an H100 (peak ~989 TFLOP/s FP16, or ~1,979 TFLOP/s FP8 dense), the diagnostic step is to identify the cause of low utilization before optimizing the code itself. Within one kernel, common causes are too little parallel work to occupy the execution units or a memory-access pattern that holds the kernel below the roofline; across a sequence of small kernels, the cause is often the launch latency between them, which the per-kernel check misses and a profiler timeline exposes.
4.  **The cache-state rule**: Set cache state to match the claim. Flush or exceed the L2 cache when measuring cold dynamic random-access memory (DRAM) bandwidth; preserve a warmed cache when measuring steady-state reuse. Otherwise a nominal DRAM result may instead reflect cache bandwidth (~5 TB/s–10 TB/s) rather than DRAM bandwidth (~1 TB/s–2 TB/s).
5.  **The synchronization barrier rule**: Place the device barrier of [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.03 Benchmark Carpentry#^sec-benchmarking-benchmark-harness-09ea|section 12.2.4]] immediately before and after the timed region, or use device timestamp events, so that the timer measures kernel execution rather than host enqueue latency.

The speed-of-light check in those rules compares a kernel against the roofline model[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn11|¹¹]] of **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]**, which plots the bound of the arithmetic intensity law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-arithmetic-intensity|6]]). That ceiling is a prediction, and a benchmark is the measurement that tests it. The roofline bounds where a kernel can sit; a benchmark determines where it does sit, and the gap between the two is the diagnostic. A kernel far below its predicted ceiling is losing time to something the model omits (launch overhead, synchronization, or poor memory coalescing; see **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]**), which is exactly what profiling looks for.

Making the prediction requires the workload’s arithmetic intensity at a named memory interface and the target’s matching compute and bandwidth limits. For an NVIDIA H100 with 989 TFLOP/s of dense FP16 Tensor Core performance (FP32 is 67 TFLOP/s)[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.15 Footnotes#^fn12|¹²]] and 3.35 TB/s of memory bandwidth, the ridge point (peak compute divided by peak bandwidth, the intensity at which the two ceilings meet) falls at 295 FLOP/byte. Below it, bandwidth sets the lower ceiling; above it, compute does (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-hardware-balance|Hardware ridge points]]** derives the threshold).

↪ The H100 ridge point, with a compute-bound matrix multiplication and a memory-bound element-wise kernel placed on either side of it, is collected for reference in **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-concrete-example-a100-analysis-5b30|A concrete example: The H100 analysis]]**.

A profiler translates these measurement rules into physical diagnostics by decomposing kernel execution time into the three governing terms of the iron law: data movement, compute throughput, and latency overhead. Comparing the measured utilization of each resource against hardware limits reveals which term dominates the trace.

**Systems Perspective 12.5: Measuring the iron law terms**

Moving from theory to trace means mapping the iron law equation onto a profiler timeline (like Nsight Systems or PyTorch Profiler).

**Measuring the data term** $\left(\frac{{D_{\text{vol}}}}{{\text{BW}}}\right)$

- **Signal**: Look for the “Memory Throughput” or “DRAM Bandwidth” line.
- **Formula**: ${\text{BW}_{\text{effective}}} = \frac{{D_{\text{vol}}}}{{T_{\text{kernel}}}}$.
- **Diagnosis**: If ${\text{BW}_{\text{effective}}} \approx {\text{BW}_{\text{peak}}}$ (for example, close to the H100’s 3.35 TB/s peak), bandwidth pressure is a strong candidate bottleneck. Test whether reducing traffic or increasing bandwidth improves time; a high bandwidth reading alone does not establish that changing compute (${O}$) has no effect.

**Measuring achieved compute throughput $({R_{\text{peak}}} \cdot {\eta_{\text{hw}}})$**

- **Signal**: Distinguish “SM Active,” the fraction of time the GPU’s Streaming Multiprocessors (SMs), its parallel execution cores, have work resident, from executed-operation throughput. A busy multiprocessor does not imply high useful-model FLOP/s.
- **Formula**: ${R_{\text{peak}}} \cdot {\eta_{\text{hw}}} = \frac{{O}}{{T_{\text{kernel}}}}$, reported in TFLOP/s.
- **Diagnosis**: If ${\eta_{\text{hw}}} \ll 1$ AND ${\text{BW}_{\text{effective}}} \ll {\text{BW}_{\text{peak}}}$, neither quoted peak is being approached, and these two rates alone cannot say why. Kernels too small to amortize launch latency, dependency stalls, and an inefficient memory-access path are all candidate causes, and profilers separate them.

**Measuring the latency term $({L_{\text{lat}}})$**

- **Signal**: Look for gaps (empty space) between colored kernel bars on the timeline.
- **Formula**: $\text{Kernel gap fraction} = \frac{{T_{\text{gap}}}}{{T_{\text{kernel}}}+ {T_{\text{gap}}}}$.
- **Diagnosis**: A “Sawtooth” pattern (Compute, Gap, Compute, Gap) suggests exposed waiting; correlate CPU dispatch, dependencies, and transfers before attributing it to software overhead. If dispatch dominates, candidates include kernel fusion, covered in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-kernel-fusion-7faf|Kernel fusion on the accelerator]]**, or the CUDA Graphs of **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-hybrid-approaches-jit-compilation-8954|Graph capture and JIT compilation]]**.

Profilers supply the measurements this mapping needs. A framework profiler such as the PyTorch Profiler isolates the dominant layer on the step timeline. A kernel profiler such as NVIDIA Nsight Compute explains it from on-chip performance counters, the top-down method developed on a training step in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.06 Identifying Bottlenecks#^sec-model-training-identifying-bottlenecks-f57f|Identifying Bottlenecks]]**. Counter collection and kernel replay perturb timing, so diagnostic traces are compared against a minimally instrumented run. The benchmarking use is narrower, confirming or refuting a prediction.

These granular measurements enable precise kernel optimization, but they cannot reveal how components interact when assembled into complete models. Macro-benchmarks address this gap.

### Macro Benchmarks

^sec-benchmarking-macro-benchmarks-4283

A convolution kernel that hits 80 percent of the roofline in a micro-benchmark can still stall when chained into a 50-layer network. Macro-benchmarks determine whether operator-level gains persist when layers are composed into a complete model. Composing layers introduces physical interactions that isolated benchmarks cannot observe, because intermediate activation tensors expand peak memory footprint, sequential kernel launches expose CPU driver dispatch overhead, and memory access streams from preceding operations evict shared cache lines before downstream kernels can reuse them.

Evaluating composed model architectures and runtime configurations under standardized workloads exposes trade-offs across those interactions, including generalization accuracy on unseen validation data, dynamic memory allocation across batch sizes and context lengths, and aggregate throughput across varied request arrival patterns. An architecture that achieves higher accuracy may require an activation footprint that forces a smaller batch size under device memory constraints, collapsing the computational throughput that justified its adoption. ResNet-50’s training step tests the roofline’s prediction at exactly this granularity, because the prediction is made layer by layer and the measurement is made on the composed model.

**Napkin Math 12.1: ResNet-50 on the roofline: Predicted versus measured**

**Problem**: The roofline predicts the fastest an H100 can train ResNet-50, and MLPerf measures how fast it does. How large is the gap, and what does it say about where the time goes?

**Prediction**: One training image costs about 24.6 GFLOP, three times the 8.2 GFLOP forward pass, because the backward pass computes gradients with respect to both activations and weights. At training batch sizes, the convolution layers reuse each weight across hundreds of images and sit above the 295 FLOP/byte ridge, so the roofline places the step on the compute roof. Dividing the 989 TFLOP/s peak by the work per image gives a ceiling of about 40,200 images/s.

**Measurement**: In MLPerf Training v3.1, NVIDIA’s 64-accelerator H100 system trained ResNet-50 at about 5,000 images/s per accelerator, which delivers about 123 TFLOP/s of model arithmetic, 12.4 percent of peak.

**Diagnosis**: The measurement sits 8.0× below the prediction. The roofline did not err; it bounded the convolutions and omitted the rest of the step. Normalization and elementwise layers have intensities far below the ridge and run on the bandwidth slope, the host must decode and augment thousands of JPEG images every second, and every step pays launch and synchronization overhead. The prediction cannot say which of these dominates. A profiler attributes the gap among them (perspective [12.5](https://mlsysbook.ai/vol1/12_benchmarking/12_benchmarking.html#psp-benchmarking-measuring-iron-law-terms)), and **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.06 Identifying Bottlenecks#^sec-model-training-identifying-bottlenecks-f57f|Identifying Bottlenecks]]** works that attribution for a training step.

**Systems insight**: A prediction and a measurement together locate a bottleneck; either alone does not. The roofline says ResNet-50 could train 8.0× faster on this accelerator, and the measurement says something other than arithmetic is setting its pace.

The claim the chapter inherited, that ResNet-50 runs faster at INT8 than at FP32, needs a different macro-benchmark from this training one. An inference run under MLPerf Inference rules settles it directly. The benchmark’s ResNet-50 Offline scenario on ImageNet ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-imagenet-website-32504219|Deng et al. 2024]]), which hands the system every input at once and measures bulk throughput ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.05 Benchmark Suites#^sec-benchmarking-offline-6ece|section 12.4.4.1.4]]), can be run at INT8 and at the higher-precision baseline on the same accelerator across fixed batch sizes. Each run must hold the reference top-1 accuracy within the benchmark’s quality target, so the two throughputs and latencies are reported under one set of rules. Natural language macro-benchmarks apply the same model-level discipline to sequence-to-sequence translation and autoregressive generation, pairing output quality with token generation rate across defined context lengths.

Industry-standard suites make these model-level comparisons reproducible across platforms. The MLPerf suite spans data centers, edge appliances, mobile devices, and microcontrollers ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.07 Inference Benchmarks#^sec-benchmarking-mlperf-inference-benchmarks-e878|section 12.6.3]]), while EEMBC’s MLMark quantifies inference throughput and energy under strict embedded memory budgets and AI-Benchmark ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-ai-benchmark-website-7b4974ed|Ignatov and Timofte 2024]]) evaluates mobile systems-on-chip across heterogeneous compute units. The chapter’s own deployment measurement moves to MobileNetV2 on the camera-trap board, where even a composed-model benchmark is not yet enough because timing only the model omits the host preprocessing, storage, and transfer stages that surround it in an end-to-end pipeline.

### End-To-End Benchmarks

^sec-benchmarking-endtoend-benchmarks-51bb

In a computer vision service, decoding a compressed JPEG image, resizing, cropping, and normalizing colors on the host CPU can take several times longer than running the model itself on a modern accelerator, leaving high-throughput tensor cores idle while they wait for host memory transfers. Macro-benchmarks that start at a pre-staged tensor never see that stall. End-to-end benchmarks encompass the entire production pipeline, capturing every stage required to ingest raw data, generate model predictions, and deliver results to downstream clients. Across workloads, the primary bottleneck frequently sits in these surrounding stages, where natural language pipelines can be paced by host-CPU subword tokenization and dynamic sequence padding, while object detection pipelines can stall on sequential postprocessing such as non-maximum suppression (NMS) and bounding-box coordinate transformations when those steps remain outside the accelerated graph.

↩︎ The feeding problem, the wall-clock time an accelerator loses waiting on input I/O, is established in **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|The feeding problem]]**.

Distributed infrastructure components introduce further performance constraints beyond the compute fabric. Remote storage systems bound training throughput when reading large multimodal datasets, and a saturated network link between machines slows the gradient exchange that multi-machine training performs every step. End-to-end benchmarks must measure pipeline throughput under realistic network latencies, concurrent query arrival patterns, and actual storage I/O constraints to ensure reproducible evaluation of the deployment as an integrated system.

Public benchmark suites rarely measure storage, networking, and compute within a single unified protocol. While MLPerf Training and Inference evaluate end-to-end scenarios more closely than isolated operator tests, their closed divisions (the categories in which every submitter runs the same reference model under the same rules, [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.05 Benchmark Suites#^sec-benchmarking-communitydriven-standardization-5c56|section 12.4.4]]) deliberately standardize input data loading to isolate accelerator performance from storage and network variability. Consequently, production end-to-end benchmarking remains primarily an internal engineering practice, evaluated through distributed tracing and production telemetry on live query distributions, where the first diagnostic step is separating model execution time from the rest of the request.

### End-To-End Vs. Component Latency

^sec-benchmarking-endtoend-vs-component-latency-9952

When the designers of the Clipper serving system profiled pipelines for lightweight models, CPU-side JSON deserialization and interprocess data copying took more wall-clock time than the accelerator’s model execution ([[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.14 Source References#^ref-crankshaw2017clipper|Crankshaw et al. 2017]]). Reporting model latency alone would have hidden the largest cost in the request path, a serialization bottleneck that **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.03 Serving System Architecture#^sec-model-serving-serialization-bottleneck-aaa0|The serialization bottleneck]]** develops for serving systems. Measured at the request, the critical distinction is therefore between component latency (time spent in model computation) and end-to-end latency (total time from request arrival to response delivery). Because serialization, network hops, and queue wait time can dominate total request time, benchmarks that report only model inference time obscure what the user experiences and overstate the return on model-only optimizations.

[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.04 Benchmarking Granularity#^tbl-latency-breakdown|Table 6]] gives an illustrative latency breakdown for an inference request. The model inference stage that vendors report as their “benchmark” number spans 5 to 100 ms, yet the queue wait time it sits behind ranges from 0 to over 1,000 ms. Under load, the single component a benchmark measures is dwarfed by one it never sees, so the reported number can be a small slice of what the user actually experiences.

| **Component**              | **Example Range** | **Notes**                  |
|:---------------------------|:-----------------:|:---------------------------|
| **Network round-trip**     |     10–100 ms     | Varies by region           |
| **Request parsing**        |     0.1–1 ms      | JSON/protobuf              |
| **Input preprocessing**    |      1–50 ms      | Tokenization, image resize |
| **Queue wait time**        |    0–1000+ ms     | Load-dependent             |
| **Model inference**        |     5–100 ms      | The “benchmark”            |
| **Output postprocessing**  |     0.5–10 ms     | Decoding, format           |
| **Response serialization** |     0.1–1 ms      | JSON/protobuf              |

Table 6: **Inference Latency Breakdown**: Different pipeline components contribute to end-to-end latency, and model inference (the number vendors typically report) can be only one part of total request time. Queue wait time can dominate under load, making end-to-end measurement essential for realistic performance assessment. Ranges are illustrative rather than universal.

These component-level contributions explain why optimizing any single stage yields diminishing returns on end-to-end performance, an *optimization ceiling* formalized by Amdahl’s Law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-amdahl|8]]). The bound itself appears as **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^eq-amdahl|equation 11.1]]**, derived in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** for an accelerated path; the notebook below applies it to a measured pipeline.

**Napkin Math 12.2: Amdahl's Law: Optimization ceiling**

**Problem**: A vision pipeline spends 8 ms on preprocessing (JPEG decode, resize, normalize) and 10 ms on inference. If inference alone is optimized by 5×, how much does end-to-end latency actually improve?

**Math**: Assume fixed work, sequential stages, and unchanged preprocessing, with no queueing feedback. Optimizing inference from 10 ms to 2 ms reduces total latency from 18 ms to only 10 ms, a 1.8× improvement rather than 5×. Amdahl’s Law formalizes this ceiling: if inference, the part being accelerated, is fraction ${f_{\text{parallel}}}$ of total latency, then even infinitely fast inference yields at most $1/(1-{f_{\text{parallel}}})$ speedup, because the preprocessing fraction $1-{f_{\text{parallel}}}$ remains. With preprocessing at 44.4 percent of total latency, the remaining fraction $1-{f_{\text{parallel}}}$ is 0.444, which yields a maximum achievable speedup $1/(1-{f_{\text{parallel}}})$ of 2.25×, regardless of model optimization.

**Systems insight**: Aggressive model optimization yields disappointing end-to-end results whenever the nonmodel fraction dominates. Any component speedup quoted in isolation shrinks once the untouched stages are measured alongside it, and the shortfall grows as those stages take a larger share of the pipeline. Comprehensive benchmarks must either include preprocessing in measurements or state explicitly that reported speedups apply only to the inference component.

A latency report that supports a deployment decision therefore states which components it includes, the load it was measured under, and whether each figure is a component or an end-to-end number. Choosing that boundary is the trade-off between isolating a component bottleneck and measuring what the user experiences.

### Granularity Trade-Offs and Selection Criteria

^sec-benchmarking-granularity-tradeoffs-selection-criteria-b7d9

Choosing a measurement boundary means deciding which question the benchmark must answer, because an engineer tuning a convolution kernel needs micro-level isolation free of network jitter, an architect comparing ResNet-50 and MobileNetV2 needs macro-level model composition, and a release engineer certifying an SLO needs the full end-to-end request path. [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.04 Benchmarking Granularity#^tbl-benchmark-comparison|Table 7]] contrasts the diagnostic focus, scope, and trade-offs across the three granularities.

| **Component**   | **Micro Benchmarks**                                      | **Macro Benchmarks**                                   | **End-to-End Benchmarks**                              |
|:----------------|:----------------------------------------------------------|:-------------------------------------------------------|:-------------------------------------------------------|
| **Focus**       | Individual operations                                     | Complete models                                        | Full system pipeline                                   |
| **Scope**       | Tensor ops, layers, activations                           | Model architecture, training, inference                | Extract, transform, load; model; infrastructure        |
| **Example**     | Conv layer performance on cuDNN                           | ResNet-50 on ImageNet                                  | Production recommendation system                       |
| **Advantages**  | Precise bottleneck identification, Component optimization | Model architecture comparison, Standardized evaluation | Realistic performance assessment, System-wide insights |
| **Challenges**  | May miss interaction effects                              | Limited infrastructure insights                        | Complex to standardize, Often proprietary              |
| **Typical Use** | Hardware selection, Operation optimization                | Model selection, Research comparison                   | Production system evaluation                           |

Table 7: **Benchmarking Granularity Levels**: Different benchmark scopes target distinct stages of ML system development. Micro-benchmarks isolate individual operations for low-level optimization, macro-benchmarks evaluate complete models to guide architectural choices, and end-to-end benchmarks assess full system performance in production environments.

^tbl-benchmark-comparison

Selecting a single granularity level is rarely sufficient because benchmarking presents an inherent trade-off between diagnostic isolation and production fidelity. Along the descending diagonal in [[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.04 Benchmarking Granularity#^fig-benchmark-tradeoffs|figure 5]], evaluation regimes trade diagnostic power for operational realism. Micro-benchmarks (the red point at the top left) isolate kernel-level behavior such as achieved memory bandwidth, at the expense of end-to-end context. Macro-benchmarks (the blue center point) capture composed model topologies. End-to-end benchmarks (the green point at the bottom right) encompass live production traffic but obscure the root causes of latency spikes. Effective evaluation requires strategically combining all three tiers to verify that kernel speedups survive full-system deployment.

![[90 Assets/Volume I/12 Benchmarking/Generated Figure 2a9deb4108.svg]]

Figure 5: **Isolation vs. Representativeness**: The core trade-off in benchmarking granularity. Micro-benchmarks provide high diagnostic precision but limited real-world relevance, while end-to-end benchmarks capture realistic system behavior but offer less precise component-level insights. Effective ML system evaluation requires strategic combination of all three levels.

^fig-benchmark-tradeoffs

This trade-off maps directly onto the D·A·M taxonomy. Micro-benchmarks assess the physical capability of the Machine ($\text{M}$) executing a primitive Algorithm ($\text{A}$). Macro-benchmarks evaluate how the Algorithm ($\text{A}$) orchestrates tensor data flow across composed layers on the Machine ($\text{M}$). End-to-end benchmarks evaluate how raw Data ($\text{D}$) ingestion from external storage and network infrastructure interacts with both Algorithm and Machine under production load.

Carpentry and granularity let one team build a trustworthy measurement. Comparing that measurement with another team’s, or with a vendor’s, requires that both were built the same way, and that agreement is what standardized benchmark suites provide.

**Self-Check: Question**

1.  An e-commerce search service reports that production query latency has increased by $40\%$, violating its SLA. Which benchmarking workflow represents the most effective top-down diagnostic strategy?

    1.  Immediately rewrite all GEMM kernels in CUDA assembly without measuring the higher layers
    2.  Run isolated microbenchmarks on the GPU memory bus to determine peak DRAM bandwidth
    3.  Start with an end-to-end pipeline benchmark to isolate latency contributions across database lookup, tokenization, model inference, and reranking; next run macrobenchmarks on the slowest stage; then use microbenchmarks and kernel profilers to optimize the specific bottleneck operator
    4.  Benchmark only the isolated tokenization library on CPU and assume the rest of the pipeline is unaffected

2.  Consider the following three benchmarking tasks:

<!-- -->
