# V1-10.08 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression|V1-10 Model Compression]]

^sec-model-compression-fallacies-pitfalls-1b5e

A team deploying GPT-2 XL on a phone might find that an uncalibrated 4-bit quantization cuts weight memory by 4$\times$ while generation quality collapses. Conversely, a vision team might achieve 70 percent weight sparsity through unstructured pruning only to find inference latency increases because commodity GPU kernels cannot execute irregular sparse indexing. Model compression presents numerous counterintuitive traps where theoretical parameter or FLOP reductions fail to produce wall-clock speedups. The following fallacies and pitfalls examine where standard engineering assumptions break down across the model-runtime interface.

**Fallacy**: *Optimization techniques can be applied independently without considering their interactions.*

Engineers assume optimization strategies compose additively: 50 percent pruning plus 4× quantization yields combined benefits. In reality, techniques interact nonlinearly and compound losses. In a representative BERT-style compression scenario, pruning to 70 percent sparsity may preserve most task performance, but applying INT8 post-training quantization afterward can lose more accuracy than quantization-aware training on the pruned model, because the pruned weights never adapt to rounding error. As [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.06 Choosing and Combining Techniques#^sec-model-compression-optimization-strategies-f2f6|section 10.5.3]] demonstrates, successful optimization requires coordinated application where techniques are sequenced together.

**Pitfall**: *Assuming theoretical metrics or compression ratios translate directly into proportional deployment speedup.*

Teams frequently reduce FLOPs or parameter counts substantially without realizing proportional latency gains on physical hardware. In one representative trace, a pruned model with 40 percent fewer parameters achieves only a 12 percent latency reduction because irregular sparsity prevents efficient execution. Similarly, reducing a transformer from 440 MB to 110 MB through INT8 quantization yields a 4× raw weight-payload reduction, yet format conversion and scalar fallback on hardware without a native low-precision datapath erode the latency gain. In the chapter’s illustrative composed pipeline combining 50 percent structured pruning and INT8 quantization, the realized speedup reaches only 1.5× against an 8× paper target. Measure wall-clock latency on the target execution units rather than extrapolating from nominal compression ratios.

**Fallacy**: *Aggressive quantization maintains model performance with minimal accuracy loss.*

Engineers assume quantization error scales uniformly with bit width. In practice, precision reduction can show threshold effects, and the threshold depends on the model, layer, quantizer, calibration, and training method. The ResNet and BERT values in this chapter are illustrative rather than universal degradation bands. The same risk applies to operators such as LayerNorm and Softmax. Integer versions exist, but whether one preserves task quality must be measured, not assumed. As [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-precision-reduction-strategies-db83|section 10.3.3]] demonstrates, mixed-precision approaches can retain higher precision where uniform quantization fails.

**Pitfall**: *Defaulting to FP32 everywhere to avoid quantization risk.*

FP32 uses twice the raw storage and bandwidth of BF16, a cost the default pays on every inference whether or not the model needs the extra precision. Lower precision still has to be validated, because it does not automatically preserve convergence or accuracy. Mixed-precision training often retains FP32 accumulators or master weights and may require loss scaling, while inference precision must be validated per model and operator. The right question is what lowest precision preserves quality on the evaluation distribution and maps efficiently to the target hardware.

**Fallacy**: *Post-training optimization is always enough.*

Teams often begin with post-training quantization (PTQ) because it avoids retraining, and move to quantization-aware training (QAT) only when the PTQ artifact misses its thresholds. That move is sometimes unavoidable. At INT4, or on sensitive models even at INT8, PTQ can lose accuracy that calibration and finer scaling granularity do not restore, because no training step ever compensates its rounding error, whereas QAT lets the weights adapt to the integer grid. Post-training pruning and post-hoc distillation can likewise underperform training-aware schedules at aggressive sparsity or bit width. As detailed in [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-precision-reduction-strategies-db83|section 10.3.3]], the production threshold, not a presumption that either path is universally superior, governs the decision.

**Fallacy**: *Sparse matrix representations always save memory and accelerate inference.*

Sparse formats introduce coordinate metadata that erodes storage savings at moderate densities, as the 16-bit case of [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^sec-model-compression-sparse-break-even-7e4a|section 10.4.2.2]] showed; 32-bit indices make the penalty larger. To represent ${n_{\text{nz}}}$ nonzero values across ${n_{\text{rows}}}$ rows, a coordinate list (COO) stores explicit coordinate tuples `(row_idx, col_idx, value)`. For 32-bit floats and 32-bit integer indices, each nonzero element consumes 12 bytes (3× a dense 4-byte FP32 entry), requiring greater than 66.7 percent sparsity just to break even on memory footprint. Compressed sparse row (CSR) eliminates redundant row coordinates by storing three arrays: `values` (${n_{\text{nz}}} \times 4\text{ B}$), `col_indices` (${n_{\text{nz}}} \times 4\text{ B}$), and `row_pointers` ($({n_{\text{rows}}}+1) \times 4\text{ B}$). Each nonzero entry costs 8 bytes (2× a dense FP32 entry), requiring over 50 percent sparsity before the sparse structure consumes less memory than the original dense tensor; below 50 percent sparsity, CSR metadata expands the model’s memory footprint.

Execution faces similar break-even constraints. Converting tensors to sparse storage as soon as pruning creates zeros degrades latency if metadata decoding, irregular gather operations, and poor cache locality outweigh the saved arithmetic. No universal sparsity threshold exists, because tensor dimensions, sparse format, runtime kernel, batch size, and hardware architecture jointly govern whether sparse execution outperforms dense execution. Specialized formats such as 2:4 structured sparsity eliminate index arrays in favor of fixed 2-bit position metadata, providing an accelerator datapath that nearly halves weight traffic with minimal indexing overhead ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-structured-pruning-9692|section 10.2.1.3]]). Production workflows must therefore measure realized density and commit to a sparse representation only after verifying that the operational break-even threshold has been crossed on target hardware.
