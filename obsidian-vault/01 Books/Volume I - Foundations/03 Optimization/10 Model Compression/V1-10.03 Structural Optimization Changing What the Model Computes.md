# V1-10.03 Structural Optimization Changing What the Model Computes

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression|V1-10 Model Compression]]

^sec-model-compression-structural-optimization-ee93

At the top of the optimization stack, **efficient model representation** modifies *what* the model computes because trained networks routinely carry far more parameters than inference requires.[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn1|¹]] A standard ResNet-50 trained on ImageNet, for example, contains over 25 million parameters, yet careful magnitude pruning and retraining can remove about 80 percent of its weights for roughly a one-point loss in top-1 accuracy ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-gale2019state|Gale et al. 2019]]). Although that extra capacity aids gradient optimization during training, parameters that do not improve the deployed predictions still consume memory capacity, bandwidth, arithmetic, and energy on every query. The structural design task is to strip away capacity the task does not need while preserving what it does. Each structural method moves the model along the Pareto frontier,[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn2|²]] the set of designs that cannot be made cheaper without losing accuracy. A design off the frontier is *dominated*, because some other design is at least as accurate and cheaper. As conservation of complexity predicts, each sends part of the cost somewhere else, whether into training-time discovery, runtime sparse indexing, or student-model capacity.

The structural techniques strip that surplus through complementary mechanisms. Pruning eliminates redundant parameters from an existing network, and low-rank factorization stores an existing weight matrix as a product of two thin ones. Knowledge distillation transfers learned behavior into an independently designed compact network, efficient architecture design and neural architecture search build a network that is efficient on the target by construction ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-hutter2019automl|Hutter et al. 2019]]), and adaptive computation decides for each input how much of the network runs. In production pipelines, these techniques frequently compose, as when a NAS-discovered architecture, supervised by a distilled teacher, is pruned before final quantization.

The camera pipeline gives every structural technique the same test. MobileNetV2 must finish a frame within 33 ms on the phone, and its weights are not what fills that budget, so a structural change pays off only if it removes multiply-accumulates or activation traffic that the phone actually executes. The analysis below evaluates what structural artifact each method produces, what fine-tuning or recovery step it requires, and which hardware execution conditions allow it to deliver physical speedups. Pruning comes first because it exposes the systems constraint most directly. Eliminating mathematical parameters translates to physical hardware acceleration only when the resulting sparsity pattern aligns with the memory hierarchy and compute units of the target processor.

### Pruning

^sec-model-compression-pruning-d1cb

For the camera pipeline, pruning[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn3|³]] is the first lever to try because it starts from the trained MobileNetV2 rather than from a new design. Removing whole channels from its convolutions shrinks every layer that consumes them and cuts the multiply-accumulates that fill the 33 ms frame budget. Removing scattered individual weights, by contrast, leaves the same layers in place and saves bytes or time only if the runtime stores the zeros compactly and skips them. The safe removable fraction depends on the architecture, task, pruning pattern, and recovery procedure. Every pruning design also turns on three choices: *what* to prune (individual weights vs. entire structures), *how* to score what is expendable (magnitude, gradients, or activations), and *when* to prune (after training, during training, or at initialization).

**Definition 10.2: Pruning**

***Pruning*** is a model-compression technique that sparsifies the parameter space by removing the weights or structures whose removal increases the training loss least.

1.  **Significance**: It can convert dense matrices into sparse structures, reducing memory footprint and total data volume $({D_{\text{vol}}})$ when the sparse representation, metadata, and recovery procedure preserve acceptable quality.
2.  **Distinction**: Unlike quantization, which reduces the precision of every weight, pruning reduces the count of weights by identifying and eliminating redundancy.
3.  **Common pitfall**: A frequent misconception is that pruning “automatically” speeds up execution. In reality, without specialized sparse execution support, the resulting sparse matrices may actually run slower than dense ones due to irregular memory access patterns. A speedup requires a storage format and a kernel that skip the zeros, not merely a faster processor.

The formal pruning objective seeks a sparse parameter tensor ${\hat{\mathbf{W}}}$ that minimizes empirical loss subject to a parameter budget ${k_{\text{nz}}}$:

$$
\min_{{\hat{\mathbf{W}}}} {\mathcal{L}}({\hat{\mathbf{W}}}) \quad \text{subject to} \quad \|{\hat{\mathbf{W}}}\|_0 \leq {k_{\text{nz}}}
$$

 where $\|{\hat{\mathbf{W}}}\|_0$ is the **$\ell_0$ norm** (the count of nonzero parameters). Solving this cardinality-constrained optimization is combinatorial, so practical methods use heuristics[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn4|⁴]] such as **magnitude-based pruning**. The thresholding heuristic keeps the largest weights and zeroes the rest ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^lst-pruning-example-daad0b7c|listing 1]]). Applied to an $11\times 11$ weight tensor, it collapses sub-threshold entries to zero while irregular, high-magnitude weights persist across the grid ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-sparse-matrix|figure 3]]).

``` python
import torch

# Original dense weight matrix
weights = torch.tensor(
    [[0.8, 0.1, -0.7], [0.05, -0.9, 0.03], [-0.6, 0.02, 0.4]]
)

# Simple magnitude-based pruning: keep only the 4 largest weights
threshold = 0.5
mask = torch.abs(weights) >= threshold
pruned_weights = weights * mask

print("Original:", weights)
print("Pruned (4 nonzeros):", pruned_weights)
```

Listing 1: **Magnitude-Based Pruning**: Removes weights below a threshold to create sparse matrices, reducing the number of nonzero parameters from 9 to 4 $({k_{\text{nz}}}=4)$.

^fig-sparse-matrix

The resulting sparse matrix retains only the high-magnitude values (colored cells) while near-zero weights become exact zeros. In models amenable to pruning, much of the representational capacity remains intact after removing low-magnitude weights, establishing magnitude thresholding as an effective baseline heuristic.

To make pruning computationally tractable during gradient-based training, practical methods often relax the combinatorial $\ell_0$ constraint with continuous penalties such as $\ell_1$-regularization $({\lambda_{\text{L1}}}\| {\mathbf{W}}\|_1)$, where ${\lambda_{\text{L1}}}$ scales the sparsity penalty applied to weight tensor ${\mathbf{W}}$. Penalizing weight magnitudes drives non-essential parameters toward zero, making downstream thresholding easier. Practitioners typically couple this with **iterative pruning**, removing parameters in successive increments interleaved with fine-tuning cycles to recover lost accuracy ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-gale2019state|Gale et al. 2019]]; [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-blalock2020state|Blalock et al. 2020]]). Before choosing a penalty or a schedule, however, an engineer must decide *what* structural unit the mask removes.

#### Target Structures

^sec-model-compression-target-structures-1230

Zeroing individual weights in [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-sparse-matrix|figure 3]] leaves the matrix dimensions unchanged, whereas removing whole neurons, channels, or layers shrinks the tensors themselves. Which unit to prune depends on the deployment target’s hardware constraints and which resource is the bottleneck. When memory capacity is primary, **neuron pruning** can provide direct relief in models whose fully connected layers dominate parameter storage. Removing entire neurons and their associated weights and biases reduces layer width and parameter count. Profiling must first establish that these layers, rather than embeddings, activations, or another component, are the actual bottleneck.

When convolutional inference latency on commodity accelerators is the bottleneck, **channel pruning** (also called filter pruning) is a strong candidate. Eliminating entire channels or filters reduces feature-map depth and the multiply-accumulate count in subsequent layers. The resulting subnetwork remains dense and regular, so it can map to conventional GPU and Tensor Processing Unit (TPU) kernels without an unstructured sparse format. Realized latency still depends on the resulting dimensions, kernels, and memory traffic.

When a model contains removable stages, **layer pruning** removes entire layers from the network. Each removal eliminates all computation in that stage, but it also reduces representational depth and may change tensor shapes, residual paths, or downstream interfaces. The remaining layers must absorb the lost function, typically through fine-tuning or retraining. The nominal operation saving therefore does not guarantee proportional latency, because graph rewrites, kernel shapes, and memory traffic still govern execution. Layer pruning demands careful task validation and end-to-end profiling. Side by side, the two granularities differ in what they remove. An individual filter slice contracts intermediate feature depth, while an excised layer collapses a full computational stage ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-channel-layer-pruning|figure 4]]).

![[90 Assets/Volume I/10 Model Compression/Generated Figure 1644089d38.svg]]

Figure 4: **Channel vs. Layer Pruning**: Structural pruning operates at different architectural granularities. Channel pruning (left) removes feature map slices within convolutional layers while preserving overall network topology and dense execution, whereas layer pruning (right) eliminates entire computational stages, requiring graph rewiring and risking greater capacity loss to achieve larger per-operation savings.

^fig-channel-layer-pruning

Channel and layer pruning place different demands on accelerator hardware. Channel pruning contracts the inner dimensions of dense general matrix multiply (GEMM) operations, because eliminating output channels in layer $\ell$ reduces the input channel dimension in layer $\ell+1$. The tensors remain dense and avoid sparse pointer lookups, but their dimensions still decide how well single instruction, multiple data (SIMD) lanes and Tensor Core tiles fill. A tile is the fixed-size block of a matrix that a matrix unit processes in one step.

Pruning a 256-channel layer to 250 channels, for example, removes about 2 percent of the work yet can leave a matrix unit that processes channels in groups of 8 running a partly empty final tile, so the layer may run no faster. Pruning to 248 keeps every tile full. The camera pipeline’s MobileNetV2 shows the same rule in its design, since its reference implementation rounds every channel count to a multiple of 8, and a pruning policy for the phone keeps the pruned counts on that grid. The preferred multiple depends on the kernel and numerical format, and because it counts elements rather than bytes, it is a different constraint from cache-line or memory-transaction alignment.

Layer pruning removes full computational stages and their associated launches and intermediates, but the rewritten graph must still satisfy shape, residual-connection, and kernel-layout requirements. Both approaches require quality validation, and both trade away the per-weight freedom of masking individual connections.

#### Unstructured Pruning

^sec-model-compression-unstructured-pruning-1c47

When preserving task accuracy at high sparsity matters more than keeping tensors dense, **unstructured pruning** removes individual weights while preserving the overall network architecture. Because individual connections can be zeroed without sacrificing an entire filter or neuron, unstructured masks retain more representational capacity at a given sparsity ratio than coarse structural cuts.

To formalize the element-wise thresholding illustrated in [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-sparse-matrix|figure 3]], let ${\mathbf{W}}\in \mathbb{R}^{{m}\times {n}}$ represent a weight matrix in a given layer. Pruning applies a binary mask ${\mathbf{M}}\in \{0,1\}^{{m}\times {n}}$, yielding a pruned weight matrix:

$$
{\hat{\mathbf{W}}}= {\mathbf{M}}\odot {\mathbf{W}}
$$

 where $\odot$ represents the element-wise Hadamard product. Magnitude-based pruning removes a fraction ${\rho_{\text{sparse}}}$ of the lowest-magnitude weights by choosing a threshold ${\delta_{\text{prune}}}$ such that:

$$
{M_{i,j}} = \begin{cases} 1, & \text{if } |{W}_{i,j}| > {\delta_{\text{prune}}}\\ 0, & \text{otherwise} \end{cases}
$$

 where ${\delta_{\text{prune}}}$ is chosen to ensure that only the largest $(1 - {\rho_{\text{sparse}}})$ fraction of weights remain. This method assumes that larger-magnitude weights contribute more to the network’s function, making them preferable for retention.

Unstructured pruning reduces the count of nonzero parameters, but translating that reduction into physical storage savings requires an indexed sparse encoding such as Compressed Sparse Row (CSR) or coordinate list (COO), which stores each surviving value beside a record of its position. That positional metadata can cancel the saving at low sparsity. Storing a dense tensor with zeroed entries saves no memory at all. Where the indexed formats break even in bytes and in time is a question about execution rather than about which weights to remove, and [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^sec-model-compression-sparse-break-even-7e4a|section 10.4.2.2]] answers it.

#### Structured Pruning

^sec-model-compression-structured-pruning-9692

Where unstructured pruning removes individual weights across arbitrary tensor coordinates, **structured pruning** ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-li2017pruning|Li et al. 2017]]) eliminates regular groups of parameters, such as the neurons, channels, filters, and layers that [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-target-structures-1230|section 10.2.1.1]] matched to deployment bottlenecks, along with attention heads. Because removing whole structural units contracts weight arrays into smaller, contiguous dense tensors, the remaining computation executes directly on standard Basic Linear Algebra Subprograms (BLAS) and convolution engines without specialized sparse libraries or metadata indexing overhead.

Between unconstrained irregular masks and coarse-grained channel excision lies hardware-aligned fine-grained regularity. Hardware-aware pruning strategies, such as *N:M structured sparsity*,[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn5|⁵]] enforce fine-grained patterns that map directly onto accelerator execution datapaths. Under a *2:4 structured sparsity* constraint, every contiguous block of four weights must contain exactly two zeros and two nonzero values:

$$
\text{Original block (4 values):}\quad [0.0,\; 1.4,\; 0.0,\; -2.1] \;\longrightarrow\; \text{Compressed storage:}\quad [1.4,\; -2.1] \quad \text{with 2-bit indices:}\; [01_2,\; 11_2]
$$

 Because every group of four weights compresses to exactly two surviving values, the weight payload halves, and each kept weight needs only a 2-bit index ($00_2$ through $11_2$) to record which of the four positions it occupied. A matrix unit with a sparse path uses those indices ($01_2$ and $11_2$ in the example) to multiply only the matching activations. Because every block has the same layout, every block performs the same two multiply-accumulates, avoiding the variable-length loops that stall irregular CSR or COO formats. Unlike channel pruning, 2:4 sparsity leaves the matrix’s shape unchanged. The runtime receives half the values plus their indices rather than a smaller dense tensor. The pattern counts as structured because it is fixed in advance, and it runs faster only on hardware with a sparse path that reads it; elsewhere the matrix executes as an ordinary dense one that happens to contain zeros. This chapter uses the 2:4 pattern as the canonical compression example, and [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^sec-model-compression-sparsity-exploitation-48a6|section 10.4.2]] returns to what a sparse matrix unit does with it.

↪ How sparse Tensor Cores use the 2-bit metadata to select matching activations and skip the zeroed multiplies is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-nm-structured-sparsity-mechanics-9a71|N:M structured sparsity mechanics]]**.

The regularity-compression trade-off spans three architectural granularities, from irregular connection masking to coarse-grained neuron dropping and full convolutional channel excision ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-structured-unstructured|figure 5]]). Moving from left to right trades per-weight freedom for dense tensor structure that standard hardware kernels can execute directly.

![[90 Assets/Volume I/10 Model Compression/Generated Figure fd2fd7e949.svg]]

Figure 5: **Unstructured vs. Structured Pruning**: The regularity-compression trade-off across pruning granularities. Unstructured pruning (left) removes arbitrary individual connections and requires a sparse representation and matching kernel to change execution. Structured pruning of neurons (middle) or convolutional channels (right) can produce smaller dense tensors that remain compatible with standard kernels, although realized latency depends on the resulting shapes and runtime. ^fig-structured-unstructured

In fully connected layers (center of [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-structured-unstructured|figure 5]]), pruning neurons eliminates the corresponding rows and columns in adjacent weight matrices. In convolutional layers (right), pruning channels removes complete 3D filter slices. Either way the subnetwork stays dense, so the remaining systems requirement is matching the resulting tensor shapes and layouts to efficient kernels, the tile-filling condition of [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-target-structures-1230|section 10.2.1.1]].

Once the structural unit is fixed, an importance score decides which units to remove. The three criteria that follow (magnitude, activation, and gradient scores) are described here for neurons and filters. Magnitude and gradient scores also rank individual weights for unstructured pruning. A common approach to structured pruning ranks entire neurons or filters by the magnitude of their associated weights. A low group norm is an inexpensive proxy for low importance, not proof that the unit is dispensable. The score can use an $\ell_1$-norm or $\ell_2$-norm over the weights associated with each unit; groups below a selected threshold become pruning candidates. Layer-wise ranking matters because raw scales can differ across layers. The method needs no representative data pass, but computing scores, choosing a threshold, materializing the smaller graph, and validating or fine-tuning the result still incur engineering and compute cost.

Another strategy is **activation-based pruning**, which evaluates neuron or filter activations over a dataset. Units that remain weak across representative inputs become candidates for removal, subject to ablation or fine-tuning checks. This method captures input-dependent behavior rather than relying only on static weights. Its ranking can still miss rare but important inputs, depend on activation scaling, or change after upstream units are removed. Activation-based pruning therefore requires representative profiling data and validation after the selected structures are removed.

**Gradient-based pruning** uses loss derivatives to estimate how removing a neuron or filter would change the objective. A small first-order score suggests a candidate at the current checkpoint and on the sampled data; it does not establish permanent irrelevance or capture every interaction among units. Gradient-based criteria can combine a unit’s value with its gradient to rank the expected local loss change. Mathematically, this criterion approximates the change in loss ${\Delta}{\mathcal{L}}$ when zeroing parameter ${w}_i$ via a first-order Taylor expansion: ${\Delta}{\mathcal{L}} \approx |{w}_i \cdot \frac{\partial {\mathcal{L}}}{\partial {w}_i}|$. Weights that are either near zero or have negligible gradients exert minimal influence on the objective, making them prime candidates for excision. Unlike weight-only magnitude criteria, they require backward computation and are usually integrated into training or fine-tuning. The pruned result still needs task-level validation because the score is a local approximation.

These criteria trade measurement cost against fidelity to model behavior. Magnitude scores are inexpensive and provide a useful baseline, but they ignore the input distribution. Activation scores incorporate representative inputs and expose units that are quiet on that workload, while gradient-based scores also incorporate the local loss surface at additional training cost. None dominates across models, and none establishes that removal is harmless. A sound comparison prunes to the same structural target, applies the same recovery budget, and measures task quality after removal. It then profiles the exported graph, because a better importance score can preserve quality without producing shapes that the target runtime executes efficiently. The choice therefore depends on available data and compute, the structure being removed, and the deployment’s quality margin.

#### Pruning Trade-Offs

^sec-model-compression-pruning-tradeoffs-fada

Unstructured and structured pruning occupy opposite ends of the regularity-versus-granularity trade-off. Unstructured pruning can remove individual weights and therefore express fine-grained sparsity, but accelerators need matching sparse formats and kernels to skip those zeros. Structured pruning removes channels, filters, or layers and can produce smaller dense operations that conventional hardware already supports. Dynamic pruning, a third approach that [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-adaptive-computation-methods-d164|section 10.2.6]] develops with the other input-dependent methods, makes the executed structure depend on each input, adding control and batching overhead in exchange for conditional allocation. The three differ in what they remove, what the runtime must support, and what recovery they need ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^tbl-pruning|table 3]]).

These categories describe deployed execution rather than mutually exclusive training algorithms. A structured subnetwork may be learned with a mask that changes during training and then frozen for serving; classify the artifact by what its runtime actually executes. Once the structural granularity is chosen, the next decision is whether to remove that capacity in a single cut or across gradual prune-and-retrain cycles.

| **Aspect**                  | **Unstructured Pruning**                                                                  | **Structured Pruning**                                                         | **Dynamic Pruning**                                           |
|:----------------------------|:------------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------|:--------------------------------------------------------------|
| **Removed unit**            | Individual weights in the model                                                           | Entire neurons, channels, filters, or layers                                   | Adjusts pruning based on runtime conditions                   |
| **Model structure**         | Sparse weight matrices; original architecture remains unchanged                           | Model architecture is modified; pruned layers are fully removed                | Structure adapts dynamically                                  |
| **Impact on memory**        | Reduces the nonzero count; storage falls only with an appropriate sparse representation   | Reduces model storage by removing entire components                            | Varies based on real-time pruning                             |
| **Impact on computation**   | Dense work remains unless a supported sparse path skips zeros                             | Reduces nominal FLOPs; latency depends on resulting shapes and kernels         | Varies with routing policy and controller overhead            |
| **Hardware compatibility**  | Requires sparse formats and matching execution support                                    | Produces dense subnetworks, but awkward shapes can still underutilize hardware | Requires adaptive inference engines                           |
| **Fine-tuning requirement** | Often used to recover accuracy after pruning                                              | Often used after structural modification                                       | Depends on how the routing policy and subnetworks are trained |
| **Use cases**               | Targets whose runtime provides sparse formats and kernels, or storage-bound high sparsity | Real-time inference optimization, mobile/edge AI, and efficient training       | Adaptive AI applications, real-time systems                   |

#### Pruning Schedules

^sec-model-compression-pruning-strategies-03f7

Removing a large share of a layer’s weights in a single step can collapse accuracy before fine-tuning has a chance to route signals around the missing connections. The pruning schedule controls how much recovery training the network receives between cuts, trading training compute against final accuracy through either gradual iterative cycles or a single one-shot cut.

##### Iterative Pruning

^sec-model-compression-iterative-pruning-ee12

Iterative pruning removes capacity gradually, alternating each structural cut with fine-tuning so that the network recovers before the next cut. Across three successive prune-and-retrain cycles, accuracy drops after each cut and recovers during the fine-tuning that follows ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-iterative-pruning|figure 6]]).

![[90 Assets/Volume I/10 Model Compression/Generated Figure a42ac3d9f5.svg]]

Figure 6: **Illustrative Iterative Pruning Performance**: Three rows depict successive prune-then-fine-tune cycles, each removing two of the original twenty-two channels. Accuracy drops from 0.995 to 0.971 after the first prune, recovers to 0.992 after fine-tuning, and settles at 0.991 after all three cycles, a 0.4 percent loss with 27 percent fewer channels.

^fig-iterative-pruning

In the illustrative workflow, a convolutional network loses six channels with recovery between successive cuts. Rather than removing all six channels in a single pass, the pipeline removes two channels per cycle across three iterations, fine-tuning the remaining parameters after each cut. The initial cut drops accuracy from 0.995 to 0.971, but brief fine-tuning restores performance to 0.992. Two subsequent prune-and-tune cycles produce a final model at 0.991 accuracy, a 0.4 percent degradation despite a 27 percent reduction in channel count. Staging structural surgery across multiple retraining intervals allows surviving weights to adjust their representations along the loss landscape.

##### One-Shot Pruning

^sec-model-compression-oneshot-pruning-12a1

**One-shot pruning** removes multiple architectural components in a single step, followed by an extensive fine-tuning phase to recover model accuracy. This aggressive approach compresses the model quickly but risks greater accuracy degradation, as the network must adapt to significant structural changes simultaneously.

Applying one-shot pruning to the same network illustrates the hazard of aggressive structural truncation. Removing all six highlighted channels at once ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-oneshot-pruning|figure 7]]) causes a sharp accuracy drop from 0.995 to 0.914, from which fine-tuning recovers only partially to 0.943, leaving about a 5 percent quality penalty under the recovery procedure shown. The two figures illustrate a mechanism, not a controlled result. Both runs end with the same tensor geometry, but the iterative run also received three rounds of fine-tuning, so its better final accuracy mixes the benefit of smaller cuts with the benefit of more recovery training. A fair comparison holds the final structure and the total recovery budget fixed.

![[90 Assets/Volume I/10 Model Compression/Generated Figure 18ba16e390.svg]]

Figure 7: **Illustrative One-Shot Pruning Impact**: All six channels (27 percent) are removed simultaneously, causing accuracy to drop from 0.995 to 0.914. Fine-tuning recovers only to 0.943, a 5 percent degradation from the original accuracy.

^fig-oneshot-pruning

The working rule follows from that mechanism. Start with one-shot pruning plus recovery, because it is cheapest, and accept it if the recovered model meets the quality target. Move to an iterative schedule when it does not, which is most likely at high sparsity, where a single large cut removes capacity the network cannot rebuild in one recovery phase. Compare the two at a matched recovery budget. The iterative schedule’s advantage is reaching a smaller model at acceptable accuracy, so spend the extra cycles only when that smaller model runs faster on the target. For structured cuts such as these channels, it usually does, because the survivors form smaller dense tensors that standard kernels run, provided their shapes still fill the hardware’s tiles. For unstructured or N:M sparsity, the extra sparsity saves time only if the accelerator can skip the zeros.

#### Lottery Ticket Hypothesis (Optional Depth)

^sec-model-compression-lottery-ticket-hypothesis-1b3d

Standard pruning workflows remove weights from a fully trained dense model. The Lottery Ticket Hypothesis[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn6|⁶]] (LTH) asks whether pruning can instead find a small trainable network inside the untrained one, proposing that within large neural networks, there exist small, well-initialized subnetworks (“winning tickets”) that can achieve comparable accuracy to the full model when trained in isolation. Rather than viewing pruning as a post-training compression step, LTH suggests it can serve as a discovery mechanism to identify these efficient subnetworks early in training ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-rachwan2022winning|Rachwan et al. 2022]]).

The discovery procedure is an iterative pruning-and-rewinding loop. After training to convergence and pruning low-magnitude connections, the surviving weights reset to their initialization state ${\theta}_0$, which isolates a sparse subnetwork ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-winning-ticket|figure 8]]). Repeating the cycle can isolate a sparse subnetwork that, in the reported settings, trains to accuracy comparable with the original network ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-frankle2019lottery|Frankle and Carbin 2019]]). Whether the same procedure succeeds depends on architecture, scale, optimizer, and training budget.

Figure 8: **Lottery Ticket Iteration Cycle**: The original procedure repeatedly trains, prunes low-magnitude weights, and resets surviving weights to their initial state ${\theta}_0$. The cycle tests whether the resulting sparse subnetwork can match the dense baseline when trained in isolation; the outcome is empirical rather than guaranteed.

The Lottery Ticket Hypothesis suggests that compact, trainable subnetworks may exist inside an overparameterized initialization, which motivates direct sparse-training research. The standard discovery procedure, however, does not eliminate dense training cost. It first pays for one or more dense or partially dense runs, plus a rewind and a recovery phase per pruning cycle, to find the ticket. A winning ticket is therefore a training result. It becomes a systems win only when that total accelerator time, the final artifact size, target latency, and task quality beat the simpler alternatives: training a smaller dense model from the start, one-shot pruning with recovery, and direct sparse training.

#### Pruning in Practice

^sec-model-compression-pruning-practice-8059

While the Lottery Ticket Hypothesis illuminates the optimization landscape, practical serving systems care only about executable artifacts. Framework-level pruning is useful only when it materializes concrete hardware savings: a smaller dense tensor, a hardware-aligned structured sparse matrix, or an indexed sparse layout paired with matching runtime kernels. Training-time pruning often begins as mask application. The original tensor remains resident in memory, while a binary mask zeros selected weights during forward propagation. That mechanism guides gradient flow during recovery, but it delivers zero memory reduction or latency improvement on its own. Measurable efficiency gains emerge only after the masked structure is exported into the physical artifact loaded by the inference engine.

This artifact boundary is where the unstructured and structured strategies part ways. An exported unstructured mask still needs a sparse storage format and a matching kernel, whereas exported structured pruning is already a smaller dense graph. The systems audit therefore has three concrete steps. Identify what was pruned, identify the format the runtime receives, and verify that the target hardware has kernels that make the sparsity useful.

↪ Benchmark protocols that separate structured from unstructured pruning and specify the hardware and sparse-kernel support behind any measured speedup are developed in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.10 Model and Data Evaluation#^sec-benchmarking-compression-benchmarks-9cf0|Compression benchmarks]]**.

In practice, BERT-style transformers[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn7|⁷]] have been pruned by removing redundant attention heads or intermediate dimensions, while DistilBERT and TinyBERT reach smaller dense models that retain much of BERT’s performance by a different route, the distillation of [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-knowledge-distillation-1842|section 10.2.3]]. Pruning decides which weights exist, and every weight it keeps is still stored and multiplied at full size. A second way to shrink an existing layer keeps every weight position but stores the matrix as a product of two thin matrices, which suits layers whose weights carry less information than their dimensions suggest.

### Low-Rank Factorization

^sec-model-compression-structured-approximations-4798

When a layer’s weights concentrate their variation along a small number of directions, replacing the full matrix with a product of two thin factors removes parameters without introducing irregular sparse indices. Consider a $4096 \times 4096$ weight block whose outputs vary along only about 128 independent directions, so that a rank-128 matrix, one built from that many directions, reproduces nearly all of the layer’s output. Two thin rank-128 factors can then stand in for the block, so about 93.75 percent of the bytes fetched from DRAM and the multiply-accumulates spent on the full dense block are avoidable. Low-rank factorization exploits this algebraic redundancy by decomposing a dense ${m} \times {n}$ weight matrix into thin factors that store only a fraction of the original parameters (6.25 percent in the rank-128 case).

Tensor decomposition extends low-rank factorization to weights with more than two axes, and the two together are called **structured approximation**. Despite the shared word, structured approximation differs from structured pruning, because it replaces a dense matrix with smaller dense factors instead of removing whole units. In the camera pipeline, the natural candidates are MobileNetV2’s pointwise $1{\times}1$ convolutions, which act as dense matrix multiplications across channels; factoring one trades fewer multiply-accumulates against an extra kernel launch and an intermediate activation tensor.

#### Matrix Factorization

^sec-model-compression-lowrank-factorization-955e

**Low-rank matrix factorization (LRMF)** approximates weight matrices with lower-rank representations. Given a weight matrix ${\mathbf{W}}\in \mathbb{R}^{{m}\times {n}}$, LRMF identifies factor matrices ${\mathbf{U}}\in \mathbb{R}^{{m}\times {k}}$ and ${\mathbf{V}}\in \mathbb{R}^{{n}\times {k}}$ such that:

$$
{\mathbf{W}}\approx {\mathbf{U}}{\mathbf{V}}^T
$$

 where the approximation rank ${k}\ll \min({m}, {n})$. This decomposition is typically computed via singular value decomposition (SVD),[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn8|⁸]] retaining only the ${k}$ largest singular values. Each singular value measures how much one of the matrix’s independent directions contributes to its outputs, so keeping the largest ones keeps the directions that matter most. Writing the truncated decomposition as ${\mathbf{W}}\approx {\mathbf{P}}_k {\boldsymbol{\Sigma}}_k {\mathbf{Q}}_k^T$ and splitting the singular values evenly between the two factors gives ${\mathbf{U}}= {\mathbf{P}}_k {\boldsymbol{\Sigma}}_k^{1/2}$ and ${\mathbf{V}}= {\mathbf{Q}}_k {\boldsymbol{\Sigma}}_k^{1/2}$. During inference, computing the layer output as ${\mathbf{h}}= {\mathbf{U}}({\mathbf{V}}^T {\mathbf{x}})$ replaces a single large matrix-vector product with two sequential, smaller multiplications. The primary systems question is whether the reduction in parameter footprint and arithmetic operations compensates for the overhead of staging an intermediate activation and dispatching an additional kernel.

**Systems Perspective 10.1: The bandwidth-compute trade-off**

Low-rank factorization can reduce both arithmetic and bandwidth demand when the retained rank is small, though it adds a second factor operation and possible kernel-launch overhead. Storing a 4096 by 4096 matrix requires 67.1 MB (at FP32). Fetching this matrix for a single inference imposes substantial memory traffic, especially when execution is limited by physical memory bandwidth.

Factoring the matrix at rank ${k}=$ 128 requires storing two smaller matrices (4096 by 128 and 128 by 4096), totaling only 4.2 MB, a 16× reduction in stored values. When inference uses the two factors directly, matrix-vector arithmetic also falls from $\mathcal{O}({m} {n})$ to $\mathcal{O}({k}({m}+{n}))$ for small ${k}$. The deployment speeds up only if the two factor operations and their intermediate traffic cost less than the original dense kernel. Explicitly materializing ${\mathbf{U}}{\mathbf{V}}^T$ would add $\mathcal{O}({m} {k} {n})$ work and defeat the purpose.

This bandwidth-compute trade-off is the memory wall at the operator level. When batch sizes are small, execution is bottlenecked by the time required to fetch weight bytes from DRAM rather than the time required to perform multiply-accumulate operations. To keep those weight fetches small, a serving engine that evaluates the factored form never materializes the full-rank matrix. The original ${m}\times {n}$ weight matrix ${\mathbf{W}}$ is held only as the product of a tall factor ${\mathbf{U}}$ (${m}\times {k}$) and a wide factor ${\mathbf{V}}^T$ (${k}\times {n}$) ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-matrix-factorization|figure 9]]).

↪ The AI memory wall, the regime in which arithmetic throughput outpaces the memory bandwidth that feeds it, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^sec-hardware-acceleration-understanding-ai-memory-wall-3ea9|The AI memory wall]]**.

![[90 Assets/Volume I/10 Model Compression/Generated Figure 3ce4d4f289.svg]]

Figure 9: **Low-Rank Factorization**: A weight matrix ${\mathbf{W}}$ of size ${m}{\times}{n}$ is approximated by two smaller factors, ${\mathbf{U}}$ $({m}{\times}{k})$ and ${\mathbf{V}}^T$ $({k}{\times}{n})$. Storage falls from ${m} \times {n}$ to ${m} \times {k} + {k} \times {n}$ parameters, while one dense operation becomes two factor operations.

^fig-matrix-factorization

LRMF applies directly to fully connected projection layers and to flattened convolutional weight tensors. The storage and arithmetic savings derived above are only half of the accounting on a real accelerator. The intermediate activation vector ${\mathbf{z}}= {\mathbf{V}}^T {\mathbf{x}}$ must be staged in on-chip SRAM or round-tripped through memory, and dispatching two separate kernels incurs launch latency unless the operations are fused. Furthermore, if the approximation rank ${k}$ is small or unaligned with hardware tile dimensions (such as the $16{\times}16$ tile of a systolic array), the hardware compute units operate well below peak throughput. Selecting rank ${k}$ therefore balances memory footprint and bandwidth reduction against approximation error, kernel dispatch overhead, and hardware tile utilization.

↪ How a matrix is tiled onto a fixed-size systolic array, and why a dimension just past the tile width drops utilization sharply, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-tiling-principle|Tiling]]**.

Storage and accuracy bound that choice. The factors save storage at all only while they hold fewer values than the original matrix, which requires the rank to stay below the product of the two dimensions divided by their sum; for a square matrix, that is half its width. Within that limit, the rank is chosen layer by layer from the singular values. Truncation stops where the discarded values are small relative to the kept ones, and the layer’s measured accuracy confirms the cut. Truncation, like pruning, removes information the network was trained to use, so the factored model is usually fine-tuned briefly afterward to recover the accuracy the approximation lost.

#### Tensor Decomposition (Optional Depth)

^sec-model-compression-tensor-decomposition-5e9e

**Tensor decomposition** extends low-rank approximation to multidimensional arrays, such as four-dimensional convolutional kernels (${d_{\text{out}}} \times {d_{\text{in}}} \times {K_h} \times {K_w}$) and multi-head attention weights. Matrix factorization could compress such a tensor only after unfolding it into a matrix, which discards which axis was which. Tensor decompositions instead keep each axis separate by representing the tensor through smaller factors, one for each axis. A three-dimensional tensor ${\mathcal{Y}}\in \mathbb{R}^{{I}\times {J}\times {T}}$, for example, decomposes into three rank-${k}$ factor matrices (${\mathbf{A}}$, ${\mathbf{B}}$, and ${\mathbf{C}}$), and outer products of the slice vectors ${\mathbf{a}}_i$, ${\mathbf{b}}_j$, and ${\mathbf{c}}_t$ reconstruct entry ${y_{ijt}}$ ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-tensor-decomposition|figure 10]]).

![[90 Assets/Volume I/10 Model Compression/Generated Figure 35e03a2cdb.svg]]

Figure 10: **Tensor Decomposition**: A three-dimensional tensor ${\mathcal{Y}}\in\mathbb{R}^{{I}{\times}{J}{\times}{T}}$ is approximated by factor matrices ${\mathbf{A}}$, ${\mathbf{B}}$, and ${\mathbf{C}}$. The highlighted factor vectors ${\mathbf{a}}_i$, ${\mathbf{b}}_j$, and ${\mathbf{c}}_t$ combine across rank ${k}$ to reconstruct the entry ${y_{ijt}}$. Extending low-rank approximation from two dimensions to three carries the storage and computation argument into convolutional layers. Source: ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-gholami2022|Gholami et al. 2022]]).

^fig-tensor-decomposition

Formats trade parameter reduction against contraction complexity. **CP decomposition** (canonical polyadic decomposition) is the form drawn in [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-tensor-decomposition|figure 10]]. It expresses the tensor as a sum of ${k}$ rank-one outer products, ${\mathcal{Y}}\approx \sum_{{s}=1}^{{k}} {\mathbf{a}_s} \otimes {\mathbf{b}_s} \otimes {\mathbf{c}_s}$, where ${\mathbf{a}_s}$, ${\mathbf{b}_s}$, and ${\mathbf{c}_s}$ are column ${s}$ of the factor matrices ${\mathbf{A}}$, ${\mathbf{B}}$, and ${\mathbf{C}}$ ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-lebedev2015speeding|Lebedev et al. 2015]]). Because component ${s}$ along one axis interacts only with the matching component ${s}$ along the other axes, CP replaces a multidimensional convolution with a chain of one-dimensional projections and achieves maximal parameter reduction, though fitting a high-rank CP decomposition directly can be numerically unstable.

**Tucker decomposition** relaxes CP’s one-to-one coupling by keeping a small dense core tensor multiplied along each mode by a factor matrix, ${\mathcal{Y}}\approx {\mathcal{G}}\times _1 {\mathbf{A}}\times _2 {\mathbf{B}}\times _3 {\mathbf{C}}$, where $\times_{{n_{\text{mode}}}}$ multiplies along axis ${n_{\text{mode}}}$ of the tensor. In a convolutional layer, the factor matrices project the input and output channels into a narrow bottleneck, the dense core ${\mathcal{G}}$ captures every cross-channel and spatial interaction within that subspace, and the final factor restores the output channels. For tensors with many axes, the Tucker core itself becomes large, and **tensor-train (TT)** decomposition replaces it with a chain of small cores so that storage grows linearly rather than exponentially with the number of axes.

Tensor decomposition applies to convolutional filters, attention projections, and embedding tables. Its barrier is execution cost, because accelerators are specialized for dense matrix multiplication (GEMM). Contracting decomposed tensors needs transposition kernels or many small contractions, and without fused contraction kernels the data movement and launch latency can erase the arithmetic savings. LRMF and tensor decomposition differ in the data structures they apply to, the compression they achieve, and what they ask of the execution engine ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^tbl-lrmf-tensor|table 4]]).

| **Feature**                   | **Low-Rank Matrix Factorization (LRMF)**                                       | **Tensor Decomposition**                                                                                     |
|:------------------------------|:-------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------|
| **Applicable Data Structure** | Two-dimensional matrices                                                       | Multi-dimensional tensors                                                                                    |
| **Compression Mechanism**     | Factorizes a matrix into two or more lower-rank matrices                       | Decomposes a tensor into multiple lower-rank components                                                      |
| **Common Methods**            | SVD; Alternating Least Squares (ALS), which fits one factor at a time          | CP Decomposition, Tucker Decomposition, Tensor-Train (TT)                                                    |
| **Compute cost**              | Depends on the factorization method, selected rank, and kernels                | Depends on the decomposition, selected ranks, optimization procedure, and tensor-contraction kernels         |
| **Storage Reduction**         | Reduces storage from $\mathcal{O}({m} {n})$ to $\mathcal{O}({m} {k}+ {k} {n})$ | Depends on the decomposition and selected ranks; stores factor matrices and, for some methods, a core tensor |
| **Inference execution**       | Replaces one dense operation with two factor operations                        | Introduces tensor contractions whose latency depends on available kernels                                    |
| **Primary Use Cases**         | Fully connected layers, embeddings, recommendation systems                     | Convolutional filters, attention mechanisms, multi-modal learning                                            |

^tbl-lrmf-tensor

In production pipelines, practitioners frequently combine these structured approximations, applying LRMF to large linear projections and embedding tables while targeting multi-dimensional convolutional layers with tensor decompositions. Under the D·A·M taxonomy, structured approximation alters the Algorithm to relieve Machine memory-capacity and bandwidth bottlenecks. When fetched weights dominate serving latency, reducing weight bytes can reduce that component of execution time. Added factor operations, intermediate tensors, and launch overhead must still be counted; they can offset the saving in either a memory-bound or compute-bound workload.

Pruning and factorization both modify the parameterization of an existing model, and neither can replace an operator that suits the target poorly. If the original operator choices, kernel dimensions, or memory access patterns are ill-suited to the target accelerator, removing or factoring weights cannot substitute more efficient primitives. When deployment limits demand a different topology altogether, the compression objective shifts from subtracting weights to training a compact model to behave like the original.

### Knowledge Distillation

^sec-model-compression-knowledge-distillation-1842

The camera pipeline’s MobileNetV2 does not have to learn its task from labels alone. A ResNet-50 trained for the same task needs 102.2 MB of FP32 weights and 8.2 GFLOP per image against MobileNetV2’s 14 MB and 600 MFLOP ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.02 Fitting the Deployment Budget#^tbl-model-vs-device|table 1]]). That is far too much arithmetic for the phone’s frame budget, yet its output distribution carries information that labels do not. Knowledge distillation trains a compact *student* network, here MobileNetV2, to reproduce the output behavior and representations of an overparameterized *teacher*, here ResNet-50 ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-hinton2015distilling|Hinton et al. 2015]]; [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-sanh2019distilbert|Sanh et al. 2019]]). While the term borrows from chemical purification,[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn9|⁹]] the systems mechanism is algorithmic. Distillation transfers the information in the teacher’s outputs across architectures, amortizing a one-time training phase across millions of lower-latency inference queries.

**Definition 10.3: Knowledge distillation**

***Knowledge distillation*** is a model-compression technique that trains a smaller *student* model to match the behavior of a larger, pretrained *teacher* model.

1.  **Significance**: Distillation moves cost from repeated inference to an additional training phase. A student can be substantially smaller than its teacher while retaining useful task performance; DistilBERT, for example, reports 40 percent fewer parameters, 60 percent faster inference, and 97 percent of BERT’s language-understanding performance ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-sanh2019distilbert|Sanh et al. 2019]]). This trade-off is valuable when the student-training cost is amortized across many deployed queries.
2.  **Distinction**: Unlike pruning, which removes parameters from an existing architecture, and quantization, which lowers numerical precision, distillation trains a new dense architecture. The student inherits behavior from the teacher’s output distribution or intermediate representations rather than inheriting the teacher’s full parameter count or layer structure.
3.  **Common pitfall**: A frequent misconception is that distillation is lossless compression. In reality, the student is bounded by its own capacity, the quality of the teacher, and the match between the distillation data and deployment distribution; a student can faithfully reproduce teacher errors as well as teacher knowledge.

Data selection used the teacher’s soft targets as training data (**[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.06 Synthetic Data Generation#^sec-data-selection-knowledge-distillation-compressing-information-ce68|Knowledge distillation]]**); here they become a compression mechanism. Teacher models transfer semantic knowledge through nonzero probabilities assigned across non-target classes. Whereas a one-hot ground-truth label assigns a probability of one exclusively to the correct class, a teacher’s distribution keeps the inter-class correlations known as **dark knowledge**. These correlations reveal that an input classified as a cat (85 percent) shares subtle semantic features with a dog (10 percent) and a fox (5 percent) ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-kd-targets|figure 11]]). The camera pipeline’s segmentation task applies the same idea pixel by pixel. The teacher assigns each pixel a probability of belonging to the foreground, and a pixel on a hair or shoulder boundary that the teacher scores at an intermediate value tells the student more than a hard foreground-or-background label.

![[90 Assets/Volume I/10 Model Compression/Generated Figure fa9e3e5cd2.svg]]

Figure 11: **Soft Target Distribution**: The teacher’s relative confidence levels indicate which classes are semantically similar (for example, cat vs. dog), providing a much richer supervision signal than a binary “correct” label.

^fig-kd-targets

Training a student model requires balancing teacher imitation against ground-truth task supervision. Operationally, the workflow requires four decisions before training begins: selecting a teacher with the desired behavior, designing a student whose dense architecture satisfies the target accelerator’s memory and compute budget, generating soft targets over the training corpus, and choosing the temperature (a divisor applied to the logits that softens the output probabilities, developed below) and the loss weights that govern optimization. In the resulting dual-path pipeline, an input sample ${x}$ passes through both the teacher and the student, temperature-scaled soft predictions (${T_{\text{distill}}} > 1$) feed the distillation loss, and unscaled student predictions (${T_{\text{distill}}} = 1$) are scored against ground-truth hard labels ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-kd-overview|figure 12]]).

![[90 Assets/Volume I/10 Model Compression/Generated Figure f6b80f1aef.svg]]

Figure 12: **Knowledge Distillation Workflow**: An input sample passes through both the teacher and the student network. The teacher produces soft labels via temperature-scaled softmax, while the student output is compared against both the soft labels (distillation loss) and the hard labels (student loss).

^fig-kd-overview

Deploying the distilled student requires verifying more than top-1 accuracy. Because a student can inherit the teacher’s systematic biases and miscalibrations as readily as its useful representations, verification must measure confidence calibration (whether predicted probabilities match observed accuracy), subgroup behavior, and executed latency on the target hardware.

#### Distillation Mathematics

^sec-model-compression-distillation-mathematics-4af6

Standard softmax normalization converts raw model logits ${z}_i$ into probabilities. Introducing a **temperature parameter**[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn10|¹⁰]] ${T_{\text{distill}}}$ softens the resulting probability distribution across output classes:

$$
{p^{(T_{\text{distill}})}}_i = \frac{\exp({z}_i/{T_{\text{distill}}})}{\sum_j \exp({z}_j/{T_{\text{distill}}})}
$$

A higher ${T_{\text{distill}}}$ flattens the softmax distribution and exposes more of the dark knowledge carried in relative class probabilities, such as a teacher assigning a small but nonzero probability to dog and near-zero probability to truck when classifying an image of a cat. Raising ${T_{\text{distill}}}$ above one brings the dog and fox probabilities of [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-kd-targets|figure 11]] closer to the cat probability, so the student’s loss weighs how the teacher ranks the wrong classes and not only which class wins. Raising it too far flattens every class toward the same probability and erases that ranking, which is why the useful temperature is found by experiment. The total distillation loss ${\mathcal{L}_{\text{distill}}}$ balances standard cross-entropy with the Kullback-Leibler (KL) divergence against the teacher’s softened distribution:[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn11|¹¹]]

$$
{\mathcal{L}_{\text{distill}}} = (1 - {\gamma_{\text{KD}}}) {\mathcal{L}_{\text{CE}}}({\mathbf{p}_{\text{student}}}, {\mathbf{y}}) + {\gamma_{\text{KD}}}{T_{\text{distill}}}^2 {\mathcal{D}_{\text{KL}}}({\mathbf{p}_{\text{teacher}}^{(T_{\text{distill}})}} \lVert {\mathbf{p}_{\text{student}}^{(T_{\text{distill}})}})
$$

Here ${\mathbf{p}_{\text{teacher}}^{(T_{\text{distill}})}}$ and ${\mathbf{p}_{\text{student}}^{(T_{\text{distill}})}}$ are the probability vectors computed at temperature ${T_{\text{distill}}}$, ${\mathbf{y}}$ is the one-hot ground-truth label vector, and ${\gamma_{\text{KD}}}\in [0,1]$ balances the hard-label and soft-target objectives. The scaling factor ${T_{\text{distill}}}^2$ keeps the two terms in balance. Softening both distributions shrinks the gradient of the KL term by roughly $1/{T_{\text{distill}}}^2$, so multiplying by ${T_{\text{distill}}}^2$ prevents the teacher’s signal from vanishing relative to the hard-label loss as ${T_{\text{distill}}}$ increases. This loss defines response-based distillation, which matches final output distributions; feature-based distillation instead trains intermediate student layers to match the teacher’s hidden representations.

##### Efficiency Gains and Trade-Offs

^sec-model-compression-efficiency-gains-tradeoffs-fb5b

Distillation’s primary deployment advantage over unstructured pruning is that it produces a smaller dense model. Standard accelerators achieve peak throughput on contiguous matrix multiplications; unstructured sparse models incur irregular memory access and index decoding overheads that often negate theoretical FLOP reductions unless sparsity is extreme. A compact dense student reads its weights in contiguous blocks and executes vendor-optimized dense GEMM kernels. However, parameter reduction alone does not guarantee lower latency, because arithmetic intensity, layer depth, attention sequence length, and memory bandwidth limits still govern runtime. DistilBERT, for example, is about 60 percent faster (roughly 1.6$\times$) primarily because it removes half of BERT’s transformer layers ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-sanh2019distilbert|Sanh et al. 2019]]). The gap from the ideal 2$\times$ reflects work that halving the layers does not remove, such as the embedding layer, the task head, and fixed per-request overheads.

Distillation composes with pruning and quantization in multi-stage compression pipelines, and the order matters. Quantization usually comes last, because its calibration must see the weight and activation distributions of the final structure. The student need not be a freshly designed network. Structured pruning already leaves a compact dense network, so pruning first and then distilling makes the pruned network itself the student, and distillation doubles as the recovery training after the cut. [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.06 Choosing and Combining Techniques#^sec-model-compression-optimization-strategies-f2f6|Section 10.5.3]] applies this order to the camera pipeline and to a modeled BERT pipeline. Structural compression can also happen earlier than fine-tuning. Gordon et al. ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-gordon2020|2020]]) show that BERT pruned during pretraining transfers to downstream tasks, so the structural step need not wait for a task-specific model.

These operational gains trade inference efficiency for substantial training overhead. Distillation requires running inference across the teacher model to generate soft targets and backpropagating loss through the student across millions of tokens. For large models, this auxiliary training phase consumes significant accelerator FLOPs and memory bandwidth, whereas post-training quantization, introduced later in this chapter, needs only a pass over a small calibration set. Compression effectiveness is also bounded by student capacity and teacher fidelity. An undersized student lacks the capacity to absorb the teacher’s distribution, while an inaccurate or uncalibrated teacher imparts its own systematic errors to the student. Selecting an optimization strategy therefore requires evaluating task accuracy, parameter footprint, serving latency, and total training cost together, the comparison that [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.06 Choosing and Combining Techniques#^tbl-optimization-tradeoffs|table 11]] in [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.06 Choosing and Combining Techniques#^sec-model-compression-technique-selection-ba16|section 10.5]] makes for distillation, pruning, and quantization.

Distillation still needs a student architecture, and the student’s own design decides how much of the frame budget remains for everything else. Efficient architecture design and neural architecture search build that student to be efficient on the target by construction.

### Efficient Architecture Design

^sec-model-compression-hardwareaware-design-c561

Hardware-aware design begins before compression. If the target device cannot keep convolution kernels fed, cannot store activations without spilling, or cannot meet the power budget at the chosen input resolution, pruning and quantization only treat symptoms. The architecture itself must expose the kind of work the hardware can execute efficiently. That means choosing layer shapes, scaling rules, and operator patterns with memory bandwidth, parallelism, and energy as first-class constraints rather than post-hoc deployment checks. The efficient families of **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures#^sec-network-architectures|Network Architectures]]**, among them MobileNetV2’s depthwise separable factorization, are best read here as responses to a measured deployment bottleneck rather than as a catalog of architectures.

#### Efficient Design Principles

^sec-model-compression-efficient-design-principles-b015

A camera pipeline that misses its 33 ms frame budget because $3{\times}3$ convolutions saturate the mobile NPU needs a different architectural rewrite from a keyword spotter whose weights must fit inside 512 KB of microcontroller SRAM. Identifying the limiting resource in the profiling trace is therefore the first design step. A model can miss its target because every stage is scaled too large, because one convolution family dominates arithmetic, because activations or parameters overflow the memory hierarchy, or because the candidate graph uses operators the platform executes poorly. These responses interact. Reducing convolutional FLOPs with depthwise separable convolutions helps only if the target runtime has efficient kernels for the resulting operators. Shrinking a model with parameter-reduction layers helps only if activation storage or memory traffic was part of the measured problem. Hardware-aware design therefore does not replace profiling; it moves profiling information earlier, into the architecture itself.

#### Scaling Optimization

^sec-model-compression-scaling-optimization-6ad9

The first architectural response is global. When every stage of the profile is over budget, the problem is not one bad layer; the model is scaled incorrectly for the deployment envelope. The design task is then to distribute capacity across depth, width, and input resolution rather than choose a single parameter count. Depth adds sequential stages and activation storage. Width exposes more parallel work within each stage at the cost of larger weight and activation tensors. Higher input resolution sharpens spatial detail by multiplying the positions every convolution must visit. Which dimension to grow therefore depends on the machine, since a wide parallel accelerator can absorb extra channels while a small edge device is limited first by memory capacity and energy per access.

Mathematically, the total FLOPs for a convolutional model can be approximated as:

$$
{O}\propto {N_L} \cdot {w_{\text{mult}}}^2 \cdot {r}^2,
$$

 where ${N_L}$ is depth (number of layers), ${w_{\text{mult}}}$ is the width multiplier (channel count relative to a base model), and ${r}$ is the input resolution. This expression shows why naive scaling fails. Increasing width and resolution together multiplies work quickly, and the resulting model may exceed the memory bandwidth or power budget even when the parameter count appears reasonable.

The camera pipeline’s own architecture exposes one of these knobs directly. MobileNetV2’s width multiplier scales every layer’s channel count, and at a width of 0.75 the network shrinks from 3.5M to 2.6M parameters and from 600 MFLOP to 418 MFLOP per frame, keeping about 70 percent of the arithmetic. The width-squared term of the FLOP formula predicts a larger cut than this. The real cut is smaller because depthwise layers cost in proportion to the width rather than its square, and the network’s final convolution keeps its full width at reduced multipliers. A width setting is therefore a trade the phone can measure directly, in milliseconds per frame, against the accuracy the narrower network loses.

Compound scaling turns this balancing act into a controlled design rule. Instead of adjusting depth, width, and resolution independently, compound scaling grows all three dimensions by fixed ratios $({\alpha}, {\beta}, {\gamma})$ relative to a base model:

$$
{N_L} = {\alpha}^{\phi} {N_{L,0}}, \quad {w_{\text{mult}}}= {\beta}^{\phi} {w_{\text{mult},0}}, \quad {r}= {\gamma}^{\phi} {r}_0
$$

 Here, ${\phi}$ is a scaling coefficient, and ${\alpha}$, ${\beta}$, and ${\gamma}$ (as in the original EfficientNet paper) are scaling factors determined from empirical accuracy and efficiency measurements. The rule matters because it prevents one dimension from consuming the budget before the others can contribute useful accuracy.

EfficientNet ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-neural-architecture-search-cf12|section 10.2.5]]) validated this principle by using search to find a baseline architecture and then scaling it with balanced depth, width, and resolution coefficients ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-tan2019efficientnet|Tan and Le 2019]]). The lesson is not that every deployment should use EfficientNet. The systems lesson is that scaling is a resource-allocation decision, because the same accuracy target can imply different depth-width-resolution trade-offs depending on which resource the target platform makes scarce. **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12 Benchmarking#^sec-benchmarking|Benchmarking]]** formalizes how to measure those trade-offs; the design principle here is to scale the dimensions against the limiting resource.

The same logic extends beyond convolutional models. Transformer layers, attention heads, sequence length, and embedding width play roles analogous to depth, width, and resolution. Each increases capacity, but each stresses compute, memory bandwidth, or activation storage differently. Hardware-aware scaling keeps those dimensions tied to the measured bottleneck instead of treating model size as a single scalar.

#### Computation Reduction

^sec-model-compression-computation-reduction-13de

If the profile shows that a small set of convolutional operators dominates arithmetic, reducing the whole model uniformly is wasteful. The better response is to change the expensive operator. Modern efficient architectures do this by factorizing dense computations into cheaper pieces that preserve the representation needed for accuracy.

Depthwise separable convolutions, the factorization behind the MobileNetV2 and KWS lighthouses ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-howard2017mobilenets|Howard et al. 2017]]; [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-sandler2018|Sandler et al. 2018]]), are the standard example. They split a standard convolution into a depthwise stage that filters each input channel separately and a pointwise $1{\times}1$ stage that mixes channels. This cuts the arithmetic to about $1/{d_{\text{out}}} + 1/{K}^2$ of a standard layer with ${d_{\text{out}}}$ output channels and kernel width ${K}$, roughly one-ninth for $3{\times}3$ kernels and many output channels. What this chapter adds to that result is the deployment condition. The wall-clock benefit depends on kernel support and memory behavior. A mobile runtime with optimized depthwise kernels can convert much of this arithmetic reduction into latency savings, while a poorly supported backend may expose the factorized operations as many small, memory-bound kernels.

↩︎ Depthwise separable convolution and its cost reduction relative to a standard convolution are established in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.04 CNNs Spatial Pattern Processing#^sec-network-architectures-efficient-architectures-keyword-spotting-0625|Depthwise separable convolutions]]**.

Other factorization patterns follow the same logic. ResNeXt’s grouped convolutions split feature maps into independent channel groups before merging them, and ResNet’s bottleneck blocks use $1{\times}1$ projections to narrow the channel dimension before an expensive $3{\times}3$ spatial convolution and restore it afterward. Because all of these rewrites help only when the spatial convolution they shrink actually dominates the trace, they yield much smaller gains once memory traffic, launch overhead, or unsupported kernels become the dominant cost.

Arithmetic reduction is only one possible response. When profiling instead identifies memory capacity or data movement as the limiting resource on the target device, the architecture must address that memory bottleneck directly.

#### Memory Optimization

^sec-model-compression-memory-optimization-8c43

When the profile points to memory rather than arithmetic, the architecture must reduce the working set or the number of expensive memory accesses. Activations, feature maps, and parameters can exceed cache, SRAM, accelerator memory, or edge-device storage even when the FLOP count is acceptable. Memory-efficient architectures therefore try to preserve useful information while storing or moving less data.

DenseNet ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-huang2017|Huang et al. 2017]]) responds to memory pressure by reusing features, which saves parameters at the cost of keeping activations resident longer. Instead of letting each layer relearn representations similar to those of earlier layers, DenseNet connects layers so later computations reuse the earlier feature maps directly. In DenseNet with ${N_L}$ layers and growth rate ${g}$, each layer generates ${g}$ new feature maps concatenated with prior layers, causing the total number of feature maps to grow linearly:

$$
\mathcal{O}({N_L} {g})
$$

DenseNet reduces parameter redundancy through feature reuse, but concatenating retained features can increase activation storage and memory traffic. The resulting working set and runtime must be measured on the target hardware.

Parameter reduction applies the channel-narrowing idea of a $1{\times}1$ projection directly to weight storage. SqueezeNet’s *fire modules* replace $3{\times}3$ filters with a $1{\times}1$ “squeeze” layer that contracts the input channel count ${d_{\text{in}}}$ before feeding a mixed $1{\times}1$ and $3{\times}3$ “expand” layer ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-iandola2016squeezenet|Iandola et al. 2016]]). Because the parameter count of a standard convolutional layer scales with the product of both channel dimensions and the spatial kernel area,

$$
\mathcal{O}({d_{\text{in}}} {d_{\text{out}}} {K}^2)
$$

 shrinking ${d_{\text{in}}}$ before the $3{\times}3$ filters cuts stored weights sharply, achieving the paper’s AlexNet-level accuracy target with far fewer parameters than AlexNet. That trade is attractive when the deployment constraint is flash storage, model download size, or parameter bandwidth; it is less decisive when activation memory or operator overhead dominates.

Feature reuse and parameter reduction are therefore not interchangeable recipes. Reused features cut redundant representations, whereas $1{\times}1$ bottlenecks cut parameter movement at deployment, so the profile’s dominant memory term decides between them. Each of these manual motifs fixes one operator pattern at a time, leaving open how to choose kernel sizes, expansion ratios, and channel widths jointly across an entire network.

### Neural Architecture Search

^sec-model-compression-neural-architecture-search-cf12

Hand-tuning kernel sizes, expansion ratios, and channel widths across twenty or more layers can explore only a handful of the billions of valid configurations that fit a phone’s latency budget, leaving significant accuracy or speed on the table. **Neural architecture search (NAS)** automates this structural design by systematically traversing a bounded space of operations, topologies, and compound scaling rules prior to training ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-elsken2019|Elsken et al. 2019]]). Early reinforcement-learning formulations maximized task accuracy without hardware constraints ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-zoph2017neural|Zoph and Le 2016]]); subsequent weight-sharing methods amortized evaluation overhead ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-pham2018efficient|Pham et al. 2018]]); and hardware-aware NAS explicitly incorporated measured device latency and energy into the multi-objective search ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-tan2019|Tan et al. 2019]]). For the camera pipeline, architecture search is already part of the model’s lineage, since MnasNet and MobileNetV3, MobileNetV2’s successors, came from searches that measured candidate latency on phones ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-tan2019|Tan et al. 2019]]; [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-howard2019|Howard et al. 2019]]).

Discovery runs as a closed loop. The search strategy samples candidate architectures ${a}\in {\mathcal{A}}$ from the defined search space, and the performance estimation engine evaluates their latency or accuracy and feeds the result back to refine subsequent proposals ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-nas-flow|figure 13]]). NAS[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn12|¹²]] returns graphs that sit on the Pareto frontier under explicit resource bounds.

#### The NAS Optimization Problem (Optional Depth)

^sec-model-compression-nas-optimization-problem-7f8e

NAS rests on three design choices: the search space, the search strategy, and how each candidate is evaluated. All three serve one nested problem. An architecture’s quality cannot be known until it is trained, and training is expensive, so every search couples an outer problem, which operations to include (the architecture), with an inner one, which parameters work best for them (the weights).

NAS is therefore a **bi-level optimization problem**.[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn13|¹³]] The outer loop searches the architecture space ${\mathcal{A}}$, while the inner loop trains candidate architectures to evaluate performance. Formally, the objective seeks the optimal architecture ${a}^*$ that minimizes validation loss ${\mathcal{L}_{\text{val}}}$ under constraints ${C}$ (latency, memory):

$$
{a}^* = \operatorname{arg\,min}_{{a}\in {\mathcal{A}}} {\mathcal{L}_{\text{val}}}({\theta}^*({a}), {a}) \quad \text{subject to} \quad {C}({a}) \leq {C_{\text{max}}}
$$

 where ${\theta}^*({a})$ represents the optimal model parameters for architecture ${a}$, obtained by minimizing training loss:

$$
{\theta}^*({a}) = \operatorname{arg\,min}_{{\theta}} {\mathcal{L}_{\text{train}}}({\theta}, {a})
$$

The computational bottleneck lies in this inner loop. If evaluating every candidate requires independent training from scratch, a modest search space of 10 operation choices across 20 layers yields $10^{20}$ possible architectures, making exhaustive enumeration impossible. Practical NAS methods overcome this combinatorial explosion through three mechanisms: restricting the search space to reusable cells, amortizing evaluation through weight sharing, or relaxing discrete choices into continuous, differentiable formulations.

#### Search Space Design (Optional Depth)

^sec-model-compression-search-space-design-62db

Many NAS systems search for reusable *cells*, small directed acyclic graphs of operations that are stacked to form complete networks, rather than searching every layer of a deep backbone independently. Within a cell, each node represents an intermediate feature map and each directed edge applies a candidate primitive chosen from $3{\times}3$ convolution, $5{\times}5$ convolution, depthwise separable convolution, max pooling, or an identity skip connection. Because the search algorithm only has to wire up this local graph, a simplified cell with four intermediate nodes, each fed by the cell’s two inputs and by every earlier node, has fourteen edges, and two candidate operations per edge yield $2^{14}$, more than ten thousand, possible cell designs, decoupling the size of the search space from the final depth of the network.

Search spaces also encode hardware constraints by restricting candidate operations to primitives with efficient kernels on the target platform. Mobile search spaces, for example, prioritize depthwise separable convolutions with bounded kernel sizes and channel counts ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-zhang2020fast|Zhang et al. 2020]]). MobileNetV3 paired this structured block-level search space with NetAdapt to prune layer channels against measured mobile CPU latency ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-howard2019|Howard et al. 2019]]).

#### Search Strategies (Optional Depth)

^sec-model-compression-search-strategies-84ad

Search strategies trade search cost against architectural diversity ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^tbl-nas-strategies|table 6]]). Reinforcement learning treats search as a sequential decision in which a controller proposes architectures and receives an accuracy reward. It discovered NASNet, but every reward requires training a candidate. The search of Zoph and Le ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-zoph2017neural|2016]]) evaluated roughly 12,800 architectures on 800 GPUs for 28 days, a total of 22,400 GPU-days, a cost that pushed practical NAS toward weight sharing and cheaper performance predictors. Evolutionary algorithms instead mutate and recombine a population of candidates and keep the fittest. AmoebaNet reached ImageNet accuracy competitive with top human-designed models after 3,150 GPU-days ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-real2019|Real et al. 2019]]), a cost that needs proxy tasks, weight sharing, or extensive parallelism to control. Gradient-based methods such as DARTS (Differentiable Architecture Search) ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-liu2019darts|Liu et al. 2019]]) relax the search space into weighted combinations of all operations. They optimize architecture weights and model weights jointly by gradient descent, which reduces search cost from hundreds of GPU-days to one to four, though the relaxation may miss discrete patterns that discrete search finds.

Hardware-aware NAS optimizes execution metrics on target silicon rather than FLOP counts, which correlate poorly with latency when memory bandwidth or launch overheads dominate. Under the arithmetic intensity law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-arithmetic-intensity|6]]), an operation with few FLOPs but low arithmetic intensity (few operations per byte moved) can run slower than a higher-FLOP operation that saturates compute. MnasNet addresses this divergence by measuring each candidate’s latency directly on a mobile phone and folding it into the reward, which combines accuracy and latency through a weighted product:

$$
\text{Reward}({a}) = \text{Accuracy}({a}) \times \left(\frac{{L_{\text{lat,target}}}}{{L_{\text{lat,infer}}}({a})}\right)^{{\beta_{\text{lat}}}}
$$

 where ${L_{\text{lat,infer}}}({a})$ is the measured on-device inference latency of architecture ${a}$, ${L_{\text{lat,target}}}$ is the latency constraint, and the exponent ${\beta_{\text{lat}}}$ controls the accuracy-latency trade-off. Architectures that exceed the latency target are penalized. Searching under this reward, MnasNet found that varying the inverted-residual expansion ratio (how much each MobileNetV2-style block widens its channels before the depthwise convolution) from block to block gave a stronger accuracy-latency trade-off than using one ratio everywhere.

#### When to Use NAS

^sec-model-compression-use-nas-2b47

Neural architecture search can discover architectures that outperform hand-designed alternatives, but its cost demands a check on whether the investment is justified. NAS can be worthwhile for novel hardware platforms with unusual constraints, such as new accelerator architectures or highly constrained edge devices, where existing architectures are poorly optimized. It can also make sense at deployment scales where small efficiency improvements justify the upfront search cost, or when architecture families for cloud, edge, and mobile deployments can amortize one search across many variants.

Conversely, custom NAS is difficult to justify when standard deployment constraints already have well-optimized architecture families. If the compute budget is only a few GPU-days, large reinforcement-learning or evolutionary searches are impractical; differentiable or weight-sharing methods such as DARTS may remain feasible, but still require deployment-scale and validation-cost justification. Rapidly changing requirements also weaken the case because the target can move before search and validation finish.

For most practitioners, existing NAS-discovered or NAS-assisted architectures provide strong baselines before funding a search from scratch. EfficientNet jointly scales depth, width, and resolution with compound coefficients ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-tan2019efficientnet|Tan and Le 2019]]), MobileNetV3 combines hardware-aware search with NetAdapt for phone latency targets ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-howard2019|Howard et al. 2019]]), MnasNet folds measured phone latency into its reward ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-tan2019|Tan et al. 2019]]), and FBNet puts device-specific latency into a mobile-CPU search objective ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-wu2019|Wu et al. 2019]]). NAS has also been applied to compact transformer models under compute or memory constraints.

The published NAS results show what search found under particular spaces, objectives, and measurements, not that search universally beats careful manual design. When latency, memory, or energy enters the objective and is measured on the target platform, the search evaluates candidates against the resource deployment actually constrains, yet the transfer quality of the resulting architectures still depends on task and hardware. Reserve custom NAS for unusual constraints or deployment scales that can amortize the search and validation investment. Even a searched architecture, however, still executes the same fixed graph on every input, spending as much compute on a blank background frame as on a crowded street scene.

### Adaptive Computation Methods

^sec-model-compression-adaptive-computation-methods-d164

In the phone’s camera pipeline, a static backbone runs the same multiply-accumulate (MAC) operations on a blank background frame as on a crowded street scene, just as a static 24-layer transformer streams its entire parameter footprint from HBM for an obvious token as for an ambiguous one. Because pruning, distillation, factorization, and architecture search all produce a fixed execution graph, every input follows the same scheduled path regardless of difficulty.

**Adaptive inference** replaces this open-loop pipeline with an input-dependent control loop in which intermediate representations or runtime budgets decide whether to terminate execution early or which specialized subnetwork receives the activations. While dynamic paths can reduce average arithmetic operations and memory traffic, they introduce runtime overheads in routing logic, batch management, confidence calibration, and latency variance. Single-stream edge workloads such as the camera pipeline are natural candidates because many frames are easy and the phone processes one frame at a time. Dynamic pruning applies conditional execution at the fine granularity of individual channels and filters; coarser dynamic schemes skip whole layers, exit early, or route tokens across expert subnetworks.

#### Dynamic Pruning

^sec-model-compression-dynamic-pruning-b794

Traditional pruning methods, whether unstructured or structured, produce a **static pruning** mask or subnetwork that remains fixed during deployment, even if the mask was learned gradually during training. **Dynamic pruning** instead decides at inference time, from each input, which computation is active, so the executed subnetwork changes from one input to the next.

Dynamic pruning can therefore allocate different amounts of work to different inputs and can use, for a hard input, capacity that a static deployment mask would remove permanently. Activation-conditioned pruning, for example, deactivates neurons or channels for particular inputs ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-hu2023|Hu et al. 2023]]). On a simple image with mostly uniform regions, some convolutional filters produce negligible activations, and a dynamic policy can exclude them for that frame.

Excluding filters per input reduces nominal work, but the controller sits on the critical path, input-dependent routing breaks the uniform batched execution that parallel hardware relies on, and any quality change remains part of the result. Training may also need routing losses or regularization so that the policy actually uses its cheaper paths. Dynamic pruning is therefore a candidate when input complexity varies enough to repay the controller and batching overhead, not a default substitute for static pruning, and its gain must be measured as latency and accuracy together across the full input distribution.

↪ Joint evaluation of compressed models on accuracy and target efficiency metrics such as latency, plotted as an efficiency-quality frontier, is measured in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.10 Model and Data Evaluation#^sec-benchmarking-compression-validation-efficiencyquality-frontier-e9c4|Compression validation: The efficiency-quality frontier]]**.

Methods that change the mask during training are sometimes also called dynamic, but they solve a different problem. Gradual magnitude pruning progressively increases the fraction of pruned parameters while fine-tuning the survivors, which is the iterative schedule of [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-pruning-strategies-03f7|section 10.2.1.5]] run inside training, and dynamic sparse training additionally regrows connections that prove important later. Both end in a static mask for deployment, so this chapter reserves *dynamic pruning* for input-dependent execution. Skipping individual channels within a layer still executes every stage of the backbone; larger per-decision savings come from modulating the macro-graph itself.

#### Dynamic Schemes

^sec-model-compression-dynamic-schemes-e9ff

Coarser dynamic schemes route each input through only as much of the backbone as its difficulty warrants, preserving the full network for worst-case inputs while cutting whole stages or subnetworks on simple ones. Depending on whether the controller varies network depth (early exit), stage execution (conditional layer skipping), specialist capacity (mixture-of-experts), or a continuous runtime budget, each mechanism trades a larger compute saving against a coarser routing decision.

To control execution depth, **early exit** architectures attach auxiliary classification heads to intermediate layers, terminating execution when intermediate representations yield sufficient prediction confidence ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-teerapittayanon2016|Teerapittayanon et al. 2017]]). BranchyNet implements this mechanism across convolutional backbones using shallow exit branches, whereas multi-exit vision transformers attach linear probes and entropy estimators between transformer blocks ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-xin2021|Xin et al. 2021]]). When an input satisfies an exit criterion, such as softmax prediction entropy dropping below a pre-tuned threshold, the runtime halts evaluation and returns the intermediate prediction. The net operational benefit requires that the arithmetic operations and memory transfers avoided in subsequent layers exceed the computational overhead of evaluating the intermediate classifiers and gating thresholds.

The systems trade-off diverges sharply across hardware deployment targets. On single-sample edge processors (batch size ${B}=1$, typical of microcontrollers and mobile NPUs), early exit immediately terminates the execution thread ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-hu2020triple|Hu et al. 2020]]). Skipping remaining layers eliminates both the arithmetic operations and the off-chip DRAM transactions required to load subsequent layer weights into on-chip SRAM cache.

Conversely, on parallel throughput accelerators (GPUs and TPUs) processing batched workloads (${B}> 1$), early exit introduces severe batch fragmentation ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-chen2024eellm|Chen et al. 2024]]). If only a subset of samples in a batch reaches the exit threshold, the remaining samples must still traverse deeper layers. Unless the runtime regroups the unfinished samples into a smaller batch, which costs memory copies and synchronization, the finished samples keep occupying memory and parallel hardware lanes that do no useful work. Consequently, tail latency for the batch remains dictated by the deepest traversing sample.

Transformer backbones apply the same exit mechanism block by block. Each block taps its intermediate representation into an auxiliary classifier and a learned confidence estimator (learning to exit, LTE) that can trigger an early exit, while unresolved inputs continue to deeper layers ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-early-exit-transformers|figure 14]]).

^fig-early-exit-transformers

Where early exit truncates depth along a single linear pipeline, **conditional computation** dynamically modulates the topological routing of activations through the network graph ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-bengio2015conditional|Bengio et al. 2015]]). Instead of executing every block in a predefined sequence, gating functions evaluate activation tensors to bypass residual layers, alter operator kernels, or select specialized functional blocks. This converts a static directed acyclic graph (DAG) into an input-dependent dynamic graph.

SkipNet illustrates the pattern at the granularity of whole blocks. It uses lightweight recurrent or feedforward gating controllers to conditionally bypass residual blocks in convolutional networks, preserving full network depth only for computationally difficult inputs ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-wang2018skipnet|Wang et al. 2018]]). From a hardware systems perspective, conditional routing achieves wall-clock speedups only when the cycles saved by bypassing operators surpass the latency of evaluating the gating network, executing host-device control synchronization, and managing irregular memory accesses.

In a dense transformer, every token computes against every weight matrix, so parameter capacity and per-token compute grow together. The **mixture-of-experts (MoE)** architecture decouples them by replacing dense feedforward network (FFN) layers with a bank of parallel expert subnetworks coordinated by a parameterized router ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-shazeer2017outrageously|Shazeer et al. 2017]]). Google’s Switch Transformer[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn14|¹⁴]] steers each token to a single expert (${k_{\text{experts}}}=1$), which reduces communication overhead relative to routing to ${k_{\text{experts}}}> 1$ experts ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-fedus2022switch|Fedus et al. 2022]]).

Sparse activation trades compute for memory. A token routed to one of ${N_{\text{experts}}}$ experts executes arithmetic against only $1/{N_{\text{experts}}}$ of the expert parameters, yet an all-resident deployment keeps all ${N_{\text{experts}}}$ expert matrices in device memory. In a Switch Transformer block, a Switching FFN layer sits inside the standard transformer stack, and its gating router dispatches individual tokens (“More” with ${p_{\text{gate}}}=0.65$, “Parameters” with ${p_{\text{gate}}}=0.8$) to distinct expert sub-blocks (FFN 2 and FFN 1) while unselected experts stay idle ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^fig-switch-transformer|figure 15]]). Because the router chooses per token, the runtime must group the tokens sent to each expert into batches of their own ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-lepikhin2021gshard|Lepikhin et al. 2021]]). At low batch sizes or under a skewed routing distribution, divergent routing leaves some experts with too few tokens to keep matrix units busy and overloads others. The runtime must then either truncate tokens or launch kernels that leave lanes idle.

Early exit and MoE routing make discrete branch selections, but adaptive inference can also modulate depth or iteration counts continuously according to task difficulty ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-yang2020|Yang et al. 2020]]). BlockDrop adjusts the number of active layers with a runtime policy network ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-wu2018blockdrop|Wu et al. 2018]]), and dynamic layer scaling adds computation until output uncertainty drops below a calibrated threshold. In an embedded vision system, high-contrast frames with clear road geometry resolve through a minimal prefix of layers, whereas degraded frames with occluded obstacles trigger deeper processing. The gain materializes only if the control evaluation remains computationally lightweight and the runtime schedules frames with matched execution depths concurrently to maintain high hardware utilization.

#### Implementation Challenges

^sec-model-compression-implementation-challenges-1184

Realizing the efficiency gains of adaptive computation requires overcoming challenges across optimization, runtime orchestration, and hardware execution. During training, discrete routing decisions (such as non-differentiable $\mathrm{argmax}$ branch selections) break standard gradient-based backpropagation, because a hard choice of branch has no gradient. Training therefore substitutes smooth approximations of the choice and adds auxiliary losses that keep routers from collapsing onto a single favored expert ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-shazeer2017outrageously|Shazeer et al. 2017]]).

At runtime, input-dependent branching conflicts with the batched execution of modern accelerators, which apply the same instruction across many samples at once. Samples that take different paths leave hardware idle, which erodes the theoretical FLOP savings. Gating can also block fusion and add host-device synchronization. If these overheads exceed the compute time saved by skipping layers, the dynamic model has higher end-to-end latency than a dense baseline.

Dynamic control also adds a quality failure mode. Poorly calibrated gates underallocate computation to rare inputs, which degrades accuracy on safety-critical edge cases. Evaluating adaptive models therefore cannot rely on average FLOP counts alone. Rigorous system profiling must report path distribution histograms, tail latency (p99, the time that 99 percent of requests finish within), accuracy stratified by input difficulty, and throughput stability under dynamic batching (grouping requests that arrive close together), and a production deployment keeps monitoring route frequency and quality by route after launch.

**Checkpoint 10.1: Choosing a structural method**

Structural methods relocate deployment cost in different ways.

**Structured vs. unstructured pruning**: compare how each pattern interacts with GPU and TPU execution.

**Distillation vs. pruning**: explain why a dense student may preserve accuracy better than aggressive pruning while requiring additional training.

**NAS selection**: identify when hardware-specific constraints and deployment scale justify architecture search rather than manual design.

**Factorization cost**: explain why fewer stored parameters and MACs may not reduce latency when two factor operations add launches and an intermediate tensor.

**Adaptive computation**: explain why early exit can cut latency at batch size one yet fragment batched execution on a GPU.

The structural techniques covered so far (pruning, low-rank factorization, distillation, efficient architecture design, NAS, and adaptive computation) all optimize *what* computations the model performs: which parameters exist, how layers are wired, and which paths a given input executes. Once those structural cuts have carved away redundant parameters and stages, every surviving weight and activation must still cross the memory hierarchy and execute at some numerical bit width. Optimizing that representation forms the second tier of the compression stack, and its clearest case is a workload whose time is set by bytes rather than by arithmetic.
