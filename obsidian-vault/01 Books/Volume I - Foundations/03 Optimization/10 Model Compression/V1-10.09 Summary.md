# V1-10.09 Summary

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression|V1-10 Model Compression]]

^sec-model-compression-summary-8229

Model compression fits a trained model inside a deployment budget by working three tiers of one stack, the descent the chapter map laid out at the start ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.02 Fitting the Deployment Budget#^tbl-model-compression-chapter-spine|table 2]]). Structural optimization changes what the model computes, precision changes how each value is stored, and hardware implementation decides how efficiently the remaining operations execute. The running cases showed each tier where it matters most. The camera pipeline’s MobileNetV2 spends its frame budget on arithmetic, so channel pruning, distillation from a ResNet-50 teacher, and an INT8 path onto the phone’s integer accelerator are its levers. GPT-2 XL decoding spends its per-token time on bytes, so INT4 weights raise its token rate by 3.1× on the same phone, and only when dequantization is fused into the matrix multiplication.

The tiers can compound, but their gains do not multiply automatically. Pruning, distillation, and quantization together produce the illustrative pipeline’s 16× footprint reduction from 440 MB to 28 MB; metadata, unsupported operators, and hardware mapping determine the realized deployment gain. A parameter reduction approaches the same latency reduction only when the affected work is on the critical path and the runtime can exploit the new representation. Profile on target hardware, not paper metrics.

Data selection and model compression divide the efficiency work along the D·A·M axes. Data selection acts on the Data axis and lowers the cost of producing a model by spending compute only on examples that carry signal. Compression acts where Algorithm meets Machine and lowers the cost of running the model by reshaping its structure and numerics for the target. Whether those deployment savings become real speedups still depends on the hardware and runtime that execute the compressed model. The need for them does not fade, because the bitter lesson keeps growing the models that win benchmarks while the envelopes of phones and microcontrollers stay fixed.

The counting rules developed across the chapter fit on one page ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.09 Summary#^tbl-model-compression-key-equations|table 14]]). Together they let an engineer bound what a compression plan can save before a model is profiled on its target.

**Key Takeaways: From benchmark winner to production model**

- **Compression spends surplus capacity**: Production models trade unused parameters, precision, and capacity for latency, memory, power, or cost limits the deployment cannot violate. The target is an artifact that meets the deployment objective and all required quality and resource constraints.
- **Bytes multiply; speed does not**: Structural pruning, distillation, quantization, and architecture changes multiply raw footprint reductions, as the modeled BERT mobile pipeline’s 16× ratio illustrates. Speed compounds far less, because each step changes what the next one sees, and it becomes real only when task quality holds and the resulting operators match the target runtime and accelerator.
- **Precision is a deployment decision**: Where the target runtime supports it, INT8 post-training quantization is a useful first experiment because it reduces raw FP32 weight payload by 4$\times$ without retraining. QAT, distillation, or mixed precision become candidates when range calibration or layer sensitivity exposes unacceptable error.
- **Hardware decides what a saving is worth**: Unstructured sparsity and theoretical FLOP cuts do not imply latency gains unless kernels and memory layouts can exploit them. The gap between the chapter’s hypothetical 8× paper target and its 1.5× realized outcome is why target-hardware profiling is mandatory.
- **End-to-end latency caps model wins**: Compression reduces end-to-end latency only when it accelerates the critical path; capacity or energy savings can remain valuable elsewhere. When inference is 20 percent of total request latency, Amdahl’s law (principle [[01 Books/Volume I - Foundations/03 Optimization/V1 Optimization Principles#^pri-amdahl|8]]) caps even perfect model acceleration at 1.25×, so preprocessing, dispatch, and data movement may be the true optimization target.

^callout-takeaways--10-9-37f89920

The techniques in this chapter differ in almost every detail, yet one rule runs beneath all of them. Each obtains a smaller, faster, or cooler model by giving up something else. Pruning gives up capacity, quantization gives up numerical precision, and distillation consumes training compute. Where the model holds no surplus to give up, task quality degrades instead. Apart from removing genuinely avoidable work, such as an unfused intermediate round-trip, compression does not make the work disappear; it moves cost or risk from one part of the system to another, and the hardware decides how much each move saves. A technique that helps on a phone can therefore be worthless on a data-center GPU. This is the conservation-of-complexity heuristic at the level of a single model. A production artifact is a model whose structure, representation, and execution path have been engineered together until they fit the silicon and application constraints that govern deployment.

**What’s Next: From math to physics**

These optimization techniques compress the model’s logic, reducing the work the algorithm asks the machine to perform. Whether less work becomes less time depends on the silicon that executes it, and this chapter repeatedly ran into the memory wall, the regime where fetching a weight costs more than computing with it. **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** starts from that wall and from the ResNet-50 INT8 profile that closed this chapter. It explains how GPUs, TPUs, and NPUs organize tensor units, systolic arrays, and tiered SRAM/HBM hierarchies to keep arithmetic fed, which is what decides whether a quantized or sparse representation actually runs faster.
