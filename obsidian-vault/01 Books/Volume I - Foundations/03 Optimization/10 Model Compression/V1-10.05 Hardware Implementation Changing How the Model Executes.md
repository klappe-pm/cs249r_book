# V1-10.05 Hardware Implementation Changing How the Model Executes

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression|V1-10 Model Compression]]

^sec-model-compression-architectural-efficiency-8dd3

Pruning a model structurally to half its weights and quantizing the survivors from FP32 to INT8 cuts stored weight bytes by 2× and 4×, or 8× in all, which would be the speedup if run time scaled with weight bytes. The byte reduction is real, because the stored artifact does shrink by that product; it is the speed that fails to multiply. In production such a model can easily run only 1.5× faster, roughly 18.8 percent of that paper projection. Profiling shows where the missing speedup goes. The structurally pruned layers are smaller dense tensors, but their new shapes can leave tiles partly empty. Reduced-precision operators trigger unfused type conversions that flood the memory bus, and small layers spend more time launching kernels and moving intermediates than doing arithmetic. Paper metrics (parameter counts, theoretical FLOPs, and nominal bit depths) establish upper bounds that hold only when a workload is limited purely by weight traffic and every kernel exploits the new representation. Bridging the divide between paper reduction and measured hardware speedup is the job of the third tier of the stack, efficient **hardware implementation**.

The measured bottleneck selects the implementation technique. Kernel fusion consolidates memory-bound operator chains, custom dequantization loops keep packed low-precision weights inside cache, and hardware sparsity engines align with tensor layouts to bypass zeroed arithmetic.

### Compression-Specific Fusion

^sec-model-compression-operator-fusion-ac1d

In the camera pipeline’s MobileNetV2, every inverted residual block chains a convolution, a batch normalization, and a rectified linear unit (ReLU). Executed as separate kernels, each operator writes its output to accelerator global memory and the next reads that output back, paying three memory round-trips for work that could stay in on-chip registers. Kernel fusion (or operator fusion) eliminates those redundant memory transactions by combining adjacent operators into a single kernel ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-chen2018tvm|Chen et al. 2018]]; [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-nvidia2024tensorrt|NVIDIA 2024]]). Model compression introduces fusion requirements of its own. Folding batch normalization into a pruned convolution, keeping a dequantize step inside the matrix-multiplication kernel that consumes it, and choosing which adjacent operators of a rewritten graph can share one kernel are all fusion decisions that arise once the graph has been compressed.

The read-compute-write cycle of unfused kernels creates memory bandwidth bottlenecks for operations with low arithmetic intensity (FLOP/byte). The traffic rule for a fused chain, established in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8|The memory wall and kernel fusion]]**, bounds what fusion can recover. Fusing a chain of ${n_{\text{ops}}}$ operations over an intermediate tensor of ${M_{\text{tensor}}}$ bytes cuts idealized read-and-write traffic from $2\,{n_{\text{ops}}} {M_{\text{tensor}}}$ to $2{M_{\text{tensor}}}$ bytes, because the fused kernel reads its input once and writes its final output once. Weights, auxiliary inputs, cache effects, and register spills are outside this simple bound, and data dependencies, tensor shapes, and register pressure limit how much can legally be fused. Several inference patterns nevertheless approximate the bound closely enough for fusion to matter.

#### Convolution-BatchNorm-ReLU Fusion

^convolution-batchnorm-relu-fusion

The common Conv-BN-ReLU pattern can replace three launches and intermediate round-trips with one fused path when the compiler can legally fold batch normalization and combine the activation ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^lst-conv-bn-relu-fusion|listing 4]]). Folding itself is a standard inference step for any network with batch normalization. Compression makes its timing matter, because folding writes batch normalization’s per-channel constants into the convolution weights, so it must happen after pruning has fixed which channels survive, and the quantizer must then calibrate the folded weights rather than the unfolded ones.

During training, batch normalization recomputes channel means and variances across every mini-batch, but at inference time those statistics freeze into fixed per-channel constants: the running mean ${\boldsymbol{\mu}_{\mathcal{B}}}$ and the stabilized running standard deviation ${\boldsymbol{\sigma}_{\mathcal{B}}}$ (the square root of the sum of running variance and the numerical stabilizer). Once frozen, batch normalization is a fixed per-channel affine rescaling that subtracts ${\boldsymbol{\mu}_{\mathcal{B}}}$, divides by ${\boldsymbol{\sigma}_{\mathcal{B}}}$, multiplies by the learned scale ${\boldsymbol{\gamma}}$, and adds the learned shift ${\boldsymbol{\beta}}$ directly to the linear output of the convolution. Because composing two linear transformations yields a single linear transformation, distributing $\frac{{\boldsymbol{\gamma}}}{{\boldsymbol{\sigma}_{\mathcal{B}}}}$ across the convolution output folds batch normalization into the preceding convolution weights (${\mathbf{W}_{\text{fused}}}= \frac{{\boldsymbol{\gamma}}}{{\boldsymbol{\sigma}_{\mathcal{B}}}} {\mathbf{W}}$) and adjusts the convolution bias to ${\mathbf{b}_{\text{fused}}} = \frac{{\boldsymbol{\gamma}}}{{\boldsymbol{\sigma}_{\mathcal{B}}}}({\mathbf{b}}- {\boldsymbol{\mu}_{\mathcal{B}}}) + {\boldsymbol{\beta}}$. Batch normalization’s per-channel scale thus multiplies into the surviving filters, and its shift becomes the convolution’s bias, so a pruned network is folded once its structure stops changing, before its ranges are calibrated.

``` python
# Pseudocode: runtime APIs and fusion legality are
# implementation-dependent.
# === UNFUSED: 3 kernel launches, 6 memory transfers ===
conv_out = conv2d(input, weight)
bn_out = batch_norm(conv_out, ...)
relu_out = relu(bn_out)

# === FUSED: 1 kernel launch, 2 memory transfers ===
def conv_bn_relu_fused(input, weight, gamma, beta, mean, var):
    # Read input and weight once
    conv = conv2d(input, weight)

    # Apply batch norm in registers (no memory write)
    bn = gamma * (conv - mean) / sqrt(var + eps) + beta

    # Apply ReLU in registers (no memory write)
    output = relu(bn)

    # Write final result once
    return output
```

Listing 4: **Conv-BN-ReLU Fusion**: Combining three operations into a single kernel reduces the idealized intermediate-tensor stream from 6 transfers to 2; weights, auxiliary inputs, and spills are outside this count.

Fusion preserves the intended function, although batch-normalization folding changes the order of the arithmetic. The intermediate traffic falls by 3×. Generic bias-activation and attention fusion, by contrast, do not depend on compression and belong to the general fusion toolkit of **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks#^sec-ml-frameworks|ML Frameworks]]**.

↩︎ IO-aware attention tiling and its HBM-traffic accounting are established in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-flash-attention-ioaware-attention-optimization-3da0|FlashAttention: IO-aware attention optimization]]**.

A ResNet-50 layer with 256 channels and a $28{\times}28$ spatial size puts numbers on this. Its feature map occupies 802.8 KB, so the four intermediate transfers that fusion removes amount to $4 \times 256 \times 28 \times 28 \times 4 \text{ bytes} \approx \text{3.2 MB}$ per layer. The full accounting also counts weights and parameters. Without fusion, each operation performs its own memory round-trip: Conv reads input (802.8 KB) plus weights (2.4 MB) and writes output (802.8 KB), totaling 4 MB. BN then reads that output, adds its parameters (2 KB), and writes again, for 1.6 MB. ReLU repeats the pattern for another 1.6 MB. The total unfused memory traffic is 7.2 MB. With fusion, the entire sequence reads input and weights once and writes the final output once, requiring only 4 MB, a 44.8 percent bandwidth reduction.

At the reference H100’s 3,350 GB/s HBM bandwidth, these traffic volumes imply ideal lower bounds of 2 microseconds before fusion and 1.2 microseconds after fusion, a 1.81× ratio for the traffic component alone. These are not full layer latencies because convolution compute, cache effects, and launch overhead must also be included. Furthermore, fusion needs the computation captured as a graph, and dynamic control flow, in-place mutation, or unsupported operations can block the rewrite, so the exported plan must be inspected rather than assumed (graph capture is developed in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-hybrid-approaches-jit-compilation-8954|Graph capture and JIT compilation]]**).

↪ The register pressure and accelerator-specific constraints that bound how far kernels can be fused on GPUs and TPUs are developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-performance-benefits-constraints-1b74|Performance benefits and constraints]]**.

Quantization adds a fusion of its own. A weight-only INT8 or INT4 kernel must turn each packed integer code ${x_q}$ back into a real value ${x}$ before multiplying it, using the scale ${s}$ and zero-point ${z}$ of [equation 1](https://mlsysbook.ai/vol1/10_model_compression/10_model_compression.html#eq-quant-scale) and [equation 2](https://mlsysbook.ai/vol1/10_model_compression/10_model_compression.html#eq-quant-zero-point):

$$
{x}= {s}({x_q} - {z}) \tag{4}
$$

 Executed as a separate kernel, dequantization writes the full-precision weights back to memory and reads them again, restoring the traffic that quantization removed. Fused into the matrix-multiplication kernel, the dequantize step runs in registers on each tile as it arrives, so only the packed bytes cross the memory bus. That fusion is what lets GPT-2 XL’s INT4 weights deliver the decode speedup computed in [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-performance-gains-0656|section 10.3.5]]. When a runtime cannot fuse it, the quantized model can run slower than its FP16 baseline, a failure [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.06 Choosing and Combining Techniques#^sec-model-compression-hardwarespecific-optimization-libraries-3ab1|section 10.5.4.2]] examines. Fusion removes intermediate traffic between operations that must all run, leaving the complementary hardware question of how to skip operands that pruning has already set to zero.

### Sparsity Exploitation

^sec-model-compression-sparsity-exploitation-48a6

Replacing pruned weights with zeros inside a standard dense matrix still fetches every zero from memory and multiplies it in the ALU, yielding no wall-clock speedup. Sparsity exploitation designs the storage layouts and kernels that translate **sparsity**,[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.12 Footnotes#^fn19|¹⁹]] where a substantial fraction of tensor entries are zero, into reduced memory traffic and execution time.

Recall from [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-unstructured-pruning-1c47|section 10.2.1.2]] that pruning a weight matrix ${\mathbf{W}_{\text{sparse}}}\in \mathbb{R}^{{m}\times {n}}$ removes a fraction ${\rho_{\text{sparse}}}$ of its entries. From the hardware’s perspective, that nominal sparsity ratio counts the exact zeros in the stored tensor:

$$
{\rho_{\text{sparse}}}= \frac{\Vert {\mathbf{1}_{\{(\mathbf{W}_{\text{sparse}})_{ij} = 0\}}}\Vert_0}{{m}\times {n}}
$$

 where ${\mathbf{1}_{\{(\mathbf{W}_{\text{sparse}})_{ij} = 0\}}}$ holds a 1 at each entry $({i},{j})$ where the weight matrix is exactly zero, and $\Vert \cdot \Vert_0$, which counts nonzero entries, counts those 1s. Read plainly, ${\rho_{\text{sparse}}}$ is the fraction of entries that are exactly zero. Magnitude thresholding at ${\delta_{\text{prune}}}$ sets its zeros by rule, so its sparsity ratio applies the same count to an indicator ${\mathbf{1}_{\{|(\mathbf{W}_{\text{sparse}})_{ij}| \leq \delta_{\text{prune}}\}}}$ that marks every entry whose magnitude falls below ${\delta_{\text{prune}}}$:

$$
{\rho_{\text{sparse},\delta}}= \frac{\Vert {\mathbf{1}_{\{|(\mathbf{W}_{\text{sparse}})_{ij}| \leq \delta_{\text{prune}}\}}} \Vert_0}{{m}\times {n}}
$$

 Whether those zeros come from exact masking or thresholding at ${\delta_{\text{prune}}}$, they yield wall-clock acceleration only when the execution pipeline skips both the arithmetic and the associated memory traffic.

From an execution standpoint, the spatial pattern of zeros determines memory transaction efficiency. Unstructured masks zero arbitrary scalar coordinates, so the kernel needs pointer arrays and must gather values from scattered addresses, which wastes the memory bandwidth that SIMD and systolic units depend on. Conversely, structured patterns, such as channel pruning or the 2:4 N:M constraint of [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-structured-pruning-9692|section 10.2.1.3]], preserve predictable memory layouts that align with standard dense kernels or dedicated sparse datapaths.

#### Sparsity Utilization Methods

^sec-model-compression-sparsity-utilization-methods-04c3

Translating zeros into runtime speedup requires a representation that encodes nonzero positions and a kernel that decodes those coordinates to bypass unneeded computation ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-hoefler2021sparsity|Hoefler et al. 2021]]). In a matrix-vector product, a dense $4{\times}4$ operator executes 16 multiply-accumulate operations, whereas a sparse execution path computes only the six nonzero products alongside the necessary metadata lookups:

$$
\begin{bmatrix} 2 & 0 & 0 & 1 \\ 0 & 3 & 0 & 0 \\ 4 & 0 & 5 & 0 \\ 0 & 0 & 0 & 6 \end{bmatrix} \begin{bmatrix} {v}_1 \\ {v}_2 \\ {v}_3 \\ {v}_4 \end{bmatrix} = \begin{bmatrix} 2{v}_1 + {v}_4 \\ 3{v}_2 \\ 4{v}_1 + 5{v}_3 \\ 6{v}_4 \end{bmatrix}
$$

The runtime benefit depends entirely on whether the latency eliminated by skipping 10 multiply-accumulate operations exceeds the latency added by coordinate decoding and non-contiguous activation loads. For unstructured sparsity, that trade has a computable answer in bytes and a measurable one in time.

#### Storage and Execution Break-Even

^sec-model-compression-sparse-break-even-7e4a

A variant of the running case makes the byte side concrete. Suppose the camera team must also ship its MobileNetV2 to a wearable companion device whose microcontroller offers only 2 MB of flash memory, against the model’s 14 MB of FP32 weights. Retraining a smaller architecture from scratch would require weeks of data collection and validation that the product schedule does not allow. Suppose profiling shows that about 85.7 percent of the model’s weights are near zero and contribute little on the validation set. Removing those weights and fine-tuning the remainder for a few epochs leaves surviving weight values that total 2 MB with an acceptable accuracy loss. Whether the stored artifact also fits in 2 MB depends on how the surviving weights are stored. The numbers are a labeled scenario that anchors the engineering trade-off, not a universal MobileNet benchmark.

Storing only the surviving values requires an indexed sparse encoding such as **Compressed Sparse Row (CSR)** or coordinate list (COO). Because these formats must store positional metadata (such as column indices and row pointers) alongside the nonzero values, metadata overhead offsets savings at low sparsity. COO records a row index and a column index beside every value. CSR keeps only the column index per value and replaces the repeated row indices with one pointer per row. For example, storing a 16-bit floating-point weight with a 16-bit column index doubles the per-element byte footprint, requiring over 50 percent sparsity just to break even on artifact size (${D_{\text{vol}}}$). The general rule follows from the same count. Each kept value costs its own bytes plus its index bytes, so an indexed format saves space only when the sparsity exceeds the index’s share of that total.

The wearable variant shows the consequence of that metadata. Its surviving weights total 2 MB only if they cost nothing to locate. A 16-bit index beside each value adds half again to 32-bit values and doubles 16-bit ones, so the stored artifact misses the 2 MB flash budget. A denser position encoding, such as a bitmap, reduces the metadata overhead but cannot close the gap, because the surviving values alone already fill the entire flash budget and leave no room for any metadata. Fitting requires further pruning or lower-precision values with room reserved for metadata, or structured removal of whole channels so that the remaining tensors can be stored without per-value indices.

↪ The memory footprint and index-pointer layouts for compressed sparse row (CSR) representations are collected for reference in **[[05 Reference/Volume I - Foundations/V1 Algorithm Foundations#^sec-appdx-algorithm-foundations-sparse-matrix-formats-0bd0|Sparse matrix formats]]**.

Fitting the bytes, moreover, does not make unstructured sparsity run faster on modern hardware. Accelerators reach their peak rate (${R_{\text{peak}}}$) by reading neighboring values together in wide, aligned memory transactions and feeding them to dense matrix and vector units. A dense masked tensor still moves its zero entries. An indexed sparse encoding instead packs nonzero values, but Sparse Matrix-Dense Matrix Multiplication (SpMM) kernels must decode metadata and gather the matching activations from scattered addresses. Irregular activation accesses, load imbalance, and kernel overhead can offset the skipped arithmetic even when stored weight values are contiguous. The performance break-even point depends on shape, format, batch size, and the available sparse kernel, so artifact reduction alone does not establish a speedup.

#### Structured Patterns

^sec-model-compression-structured-patterns-c3f4

Structured patterns resolve the break-even problem by constraining where zeros occur, and achieving actual speedups from them requires hardware that can efficiently skip zero-valued computations. Processor architectures differ in which patterns they exploit. Ampere-generation and later Sparse Tensor Cores exploit fine-grained 2:4 structured patterns, while systolic arrays require dense block structures. Software can also recast sparse work into such patterns, as MegaBlocks ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-gale2022megablocksefficientsparsetraining|Gale et al. 2022]]) does for mixture-of-experts training.

A sparse pattern earns hardware speedup only when it is regular enough for kernels to predict. Two formats make that regularity explicit: block sparse matrices and N:M sparsity patterns. Block sparse matrices group nonzeros into dense submatrices, so operations on the large sparse matrix become a smaller number of dense operations on submatrices. In the illustrated representation, $3\times 3$ dense sub-blocks are indexed by an auxiliary coordinate array, so sub-block kernels can bypass the empty tiles ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.05 Hardware Implementation Changing How the Model Executes#^fig-block-sparse-gemm|figure 28]]) ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-nvidia-cusparse-block-9fdec588|NVIDIA 2020]]). The block size is a teaching choice. Actual speedup requires a block shape, layout, datatype, and kernel supported by the target library and hardware; regular blocks alone do not guarantee aligned memory transactions or Tensor Core execution.

^fig-block-sparse-gemm

Similarly, N:M sparsity retains at most ${n_{\text{keep}}}$ nonzeros in each group of ${m_{\text{group}}}$ consecutive elements; hardware-oriented pruning often enforces exactly ${n_{\text{keep}}}$ retained values so every group has the same representation ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-zhou2021learningnmfinegrainedstructured|Zhou et al. 2021]]). The deterministic format lets a supported kernel predict the value and metadata layout while retaining more capacity than removing whole channels or blocks. That regularity creates an executable compromise between arbitrary masks and dense computation, but only for targets with the matching path.

On hardware with a sparse matrix path, the 2:4 pattern of [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-structured-pruning-9692|section 10.2.1.3]] turns into execution savings, since its 2-bit position indices cost far less than the pointer arrays of general CSR or COO formats ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020]]). The sparse datapath that consumes those indices and skips the zeroed multiplies is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-nm-structured-sparsity-mechanics-9a71|N:M structured sparsity mechanics]]**. Learned masks need not stop at 2:4; STEP, for example, learns more general N:M masks for inference ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-lu2023steplearningnmstructured|Lu et al. 2023]]).

Unstructured pruning offers none of this regularity, because it zeroes arbitrary individual weights. Those irregular locations can break up wide memory transactions and leave vector lanes idle, while Compressed Sparse Row (CSR) or Coordinate (COO) metadata adds storage and scattered reads. An unstructured sparse model can therefore run slower than its dense counterpart when metadata and underutilization outweigh skipped arithmetic. TPUs show the contrast, because their systolic arrays are built for dense matrix arithmetic ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-jouppi2021|Jouppi et al. 2021]]), so sparse acceleration on them still depends on a specific hardware and software path rather than accepting arbitrary masks. Field-programmable gate arrays can implement application-specific sparse formats, yet their efficiency depends on the chosen dataflow and resource budget; programmability is not a universal sparse-speedup guarantee.

Across all platforms, sparse operations can reduce memory bandwidth requirements and energy consumption when the sparse representation and kernels actually skip data movement rather than only arithmetic. This benefit compounds with quantization, since a sparse INT8 model can require less memory traffic than either technique alone when the format overhead is small enough ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-hoefler2021sparsity|Hoefler et al. 2021]]; [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-gale2020|Gale et al. 2020]]).

#### Challenges and Limitations

^sec-model-compression-challenges-limitations-975f

![[90 Assets/Volume I/10 Model Compression/Vol1 Model Compression Margin 003 9b4b448f0f.svg]]

*A blue speedup curve starts just below a dashed horizontal line labeled Dense 1×, crosses that line inside a gray shaded band labeled Break-even varies, then climbs to the right. The horizontal axis is labeled Sparsity. No sparsity percentage is marked.*

*Unstructured sparsity pays off only after crossing a hardware- and kernel-specific break-even point.*

The dependence of every sparse speedup on a matching format and kernel explains why nominal sparsity often fails to deliver speedups in practice. The performance break-even point varies with tensor dimensions, sparse format, kernel implementation, and hardware architecture. When coordinate metadata and irregular activation gathers waste most of each memory transaction, an unstructured sparse kernel can run slower than an optimized dense baseline until sparsity exceeds 80 to 90 percent. Accuracy compounds the problem, because it falls nonlinearly. Models often tolerate moderate pruning before task quality degrades abruptly past a critical density threshold, so the sparsity a kernel needs to break even can lie beyond what the model tolerates. Even when both conditions hold, energy savings do not scale linearly with skipped operations, because irregular memory access and index decoding can consume more power on edge devices than the arithmetic they eliminate. Fusion and sparse kernels thus decide whether each technique’s paper savings survive contact with the hardware. Most deployments apply several techniques at once, and choosing and ordering them is the next decision.
