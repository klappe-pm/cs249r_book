# V1-10.02 Fitting the Deployment Budget

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10 Model Compression|V1-10 Model Compression]]

^sec-model-compression-optimization-framework-9e21

A trained model arrives with demands on memory capacity, latency, and energy that were set by the server accelerators it trained on, not by the device it must run on. The target device instead enforces a strict **deployment budget**: the memory, time, and energy it grants to each result the model produces. Memory capacity bounds the bytes of weights and activations that can stay resident, a frame rate or token rate bounds the milliseconds available for each result, and a battery or thermal envelope bounds the joules that each result may consume. Bringing a model’s demands inside that budget, by changing what the model computes, how its values are stored, and how its operations execute, is the work of model compression.

**[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09 Data Selection#^sec-data-selection|Data Selection]]** lowered the cost of producing a trained model by spending training compute only on examples that carry signal, but its savings end where the trained model begins. A model trained on a curated subset has the same parameter count, numerical precision, and memory footprint as one trained on the full corpus, so it can still overflow a phone’s memory or leave inference bound by memory bandwidth. **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** then examines the silicon that executes a model. Compression sits between them because it decides what that silicon is asked to run: how many operations, how many bytes per value, and which kernels.

![[90 Assets/Volume I/10 Model Compression/Vol1 Model Compression Margin 001 13fd2e0674.svg]]

*Vertical log-scale ladder of blue bars: a 175B FP16 weight footprint at top towers over a phone RAM bar, which towers over a tiny microcontroller RAM bar at the bottom.*

*Frontier weights dwarf phone and microcontroller memory; compression bridges the gap.*

The gap between a model’s demands and a device’s budget is easiest to see at its extreme. A 7-billion-parameter language model requires 14 GB merely to store its weights in FP16. A smartphone offers 8 GB of RAM shared across the operating system, background applications, and the user interface, so even if the operating system surrendered its entire memory pool to one process, the weights would not fit.

Fitting in memory would only expose a second limit, the token rate. At batch size one, dense autoregressive decoding is memory-bandwidth bound because generating each token reads every weight from DRAM, and no other request shares those bytes (**[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^sec-network-architectures-inference-memory-bandwidth-wall-98d1|Autoregressive decoding]]**). Over a flagship phone’s 51.2 GB/s low-power DDR (LPDDR) bus, streaming 14 GB takes about 270 ms per token and about 2 J of DRAM access energy. The memory traffic alone would therefore draw about 8 W, above the phone’s sustained thermal envelope of 3–5 W. A model of this size is the extreme case; the rest of the chapter works with models that come closer to fitting, where the engineering choices are less obvious.

Capacity and bandwidth are two of the four quantities in the silicon contract (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-silicon-contract|4]]), under which compute throughput, memory bandwidth, memory capacity, and fixed launch overhead determine which physical resource runs out first for a given model on a given machine. Training sets those quantities generously, because it must hold gradients, optimizer state, and saved activations alongside the weights.

Inference needs less. Execution is forward-only, so optimizer state disappears and most activation buffers can be reused, although autoregressive decoding still keeps the keys and values of earlier tokens, the KV cache, across tokens. Deployment can also lower precision past the FP16 or BF16 of mixed-precision training, to INT8, INT4, or specialized microformats, when the target’s execution units support them. Informally, model compression is the work of meeting the silicon contract of a constrained execution context by reducing parameter footprint, memory traffic, or arithmetic operations while preserving task accuracy.

↩︎ Mixed-precision training with FP16 and BF16, including loss scaling and FP32 accumulation, is established in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-mixedprecision-training-9218|Mixed-precision training]]**.

Across deployment targets, the disparity in weight memory spans about six orders of magnitude, from the 350 GB of FP16 weights in a 175-billion-parameter frontier model to the 512 KB of on-chip SRAM in an embedded microcontroller. The bitter lesson explains why this gap persists. General methods that scale with compute keep winning benchmarks, so the winning models grow with available training compute while a phone’s or microcontroller’s memory and power envelope stays fixed for the life of the device. Compression is the deployment-side counterweight to scale.

↩︎ The bitter lesson, that general methods which scale with compute keep displacing hand-engineered ones, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.05 The Bitter Lesson#^sec-introduction-bitter-lesson-79c7|The Bitter Lesson]]**.

The record of language models shows how much ground that counterweight can recover. [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.02 Fitting the Deployment Budget#^fig-smallest-capable-model|Figure 1]] follows the smallest dense model reported to score at least 60 percent on the Massive Multitask Language Understanding (MMLU) benchmark ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-hendrycks2021mmlu|Hendrycks et al. 2020]]) at each point in time. That size fell from 280 billion parameters for Gopher at the end of 2021 to 3 billion for Qwen2.5-Coder-3B, a code-specialized model, in 2024, about 93× smaller in under three years ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-epochai2026benchmarks|Epoch AI 2026]]). Better training data, longer training, and distillation from larger models all contributed, so the decline is not compression alone, but it shows that a capability first reached at frontier scale can later fit a far smaller deployment budget.

Bridging the gap between frontier models and fixed deployment targets requires an engineering framework with predictable physical trade-offs. Every compression technique removes specific structure from the model, whether unnecessary weights, surplus numerical bits, or redundant operator subgraphs. Designing a production deployment requires identifying which resource runs out first on the target platform and analyzing how successive approximations compound across the memory hierarchy. The framework this chapter builds works on three tiers: what the model computes (its structure), how many bits represent each value (its precision), and how the result executes on the target processor (its implementation). Benefits compound only when transformations relieve distinct bottlenecks and the runtime supports the resulting graph.

**Definition 10.1: Model compression**

***Model compression*** is a family of techniques that reduce a trained model’s computational cost and memory footprint by eliminating redundant parameters (pruning), reducing numerical precision (quantization), or transferring learned behavior into a smaller architecture (distillation), while preserving as much predictive accuracy as possible.

1.  **Significance**: In the iron law (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-iron-law|3]]), compression targets both the Algorithm factor ($\text{FLOPs/Sample}$, and therefore total operations ${O}$) and the Machine factor ($\text{Seconds/FLOP}$, through its physical data-movement and compute terms). INT8 quantization of a 175-billion-parameter LLM leaves $\text{FLOPs/Sample}$ unchanged but cuts weight memory from 350 GB (FP16) to 175 GB, a 2× reduction in the bytes moved (${D_{\text{vol}}}$), while dedicated low-precision matrix units can raise the peak compute rate (${R_{\text{peak}}}$) when kernels and layouts use the supported INT8 path. Unstructured pruning to 50 percent sparsity halves the nonzero parameter count, but executed operations fall only when the runtime can skip those zeros through a supported sparse format or kernel without inflating $\text{Seconds/FLOP}$ via index-traffic stalls.
2.  **Distinction**: Neural architecture search differs from compressing a trained model by pruning or quantization because it changes the representation before training, discovering an efficient architecture rather than compressing a finished model.
3.  **Common pitfall**: Compression techniques do not compose without interference. Pruning changes weight distributions and operation patterns; quantization adds calibration and kernel constraints. Their combination can lose accuracy or fail to accelerate without joint validation.

↩︎ The iron law of ML systems, which splits execution time into data-movement, compute, and fixed-overhead terms, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**.

The three tiers form a stack that descends from algorithmic software toward physical silicon, the same direction in which **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks#^sec-ml-frameworks|ML Frameworks]]** lowered a computational graph to kernels. At the top sits what operations the model executes, in the middle how many bits encode each operand, and at the bottom how kernels map onto the processor’s compute and memory structures ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.02 Fitting the Deployment Budget#^fig-3-sections|figure 2]]).

![[90 Assets/Volume I/10 Model Compression/Generated Figure 21c9ce2c41.svg]]

Figure 2: **Three Tiers of Compression**: Model optimization progresses from software-level representation (pruning, distillation, NAS) down through numerical precision (quantization) to hardware execution (kernel fusion, sparsity engines). Lowering abstraction moves optimizations closer to physical silicon, where representation decisions dictate achievable execution efficiency.

^fig-3-sections

Each tier removes a different kind of surplus across the two levels of the iron law. The Algorithm factor ($\text{FLOPs/Sample}$) counts the operations each result needs, and the Machine factor ($\text{Seconds/FLOP}$) is the time each operation takes once the data-movement, compute, and fixed-overhead terms are added up. The top tier, efficient model representation, removes structure and lowers the Algorithm factor. Pruning drops weights or whole channels that contribute little to accuracy, knowledge distillation trains a compact student to match a larger teacher, and neural architecture search (NAS) looks for layer shapes that meet an explicit latency or memory bound.

The middle and bottom tiers leave $\text{FLOPs/Sample}$ unchanged and instead lower the Machine factor ($\text{Seconds/FLOP}$). In the middle tier, efficient numerics representation removes bits. Quantization maps floating-point values to 8-bit or 4-bit integers, which shrinks weight memory and bus traffic (${D_{\text{vol}}}$) by two to four times and lets integer units execute each operation at higher peak rate (${R_{\text{peak}}}$) and lower energy. In the bottom tier, efficient hardware implementation removes wasted execution. Kernel fusion keeps intermediate activations in on-chip memory instead of sending them back to DRAM (shrinking ${D_{\text{vol}}}$) and reduces launch overhead (${L_{\text{lat}}}$). Sparsity pays off only when its zeros follow a pattern the hardware can skip, such as two zeros in every group of four weights, so that the FLOP cut made by pruning does not inflate $\text{Seconds/FLOP}$.

These three tiers are tightly coupled across the compilation and execution boundary. Pruning changes the values that flow through the network, so the numeric ranges a later quantization step must cover change too. Quantization reduces the bytes that cross the memory bus, which can shift a memory-bound workload toward compute-bound execution, where how kernels are fused and scheduled matters more. Achieving compounding performance gains requires co-designing transformations across all three tiers rather than applying them in isolation, a composition strategy that [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.06 Choosing and Combining Techniques#^sec-model-compression-optimization-strategies-f2f6|section 10.5.3]] develops through a staged pipeline.

Every technique in this chapter answers to the conservation-of-complexity heuristic that opened Part I. Complexity tends to move among the Data, Algorithm, and Machine axes of the D·A·M taxonomy (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.06 Defining ML Systems#^sec-introduction-defining-ml-systems-d4af|Defining ML Systems]]**) rather than disappear, so engineers must account for where each technique sends cost and risk. It is a heuristic, not a literal conservation law, and removing genuinely avoidable work can reduce total cost. Pruning may reduce parameters while asking the runtime to exploit sparse structure; distillation may reduce inference cost while adding a teacher-student training phase; quantization may reduce data movement while spending numerical precision. The engineer’s task is to move complexity to where the cost is lowest given deployment constraints.

Which tier of the optimization stack yields the highest return depends entirely on the physical machine hosting the workload. A data-center server equipped with several high-bandwidth memory (HBM) accelerators tolerates multi-gigabyte models but demands high token throughput under concurrency. A smartphone or an embedded microcontroller operates under severe physical ceilings on memory capacity, bus bandwidth, and thermal dissipation.

### Deployment Budgets and the Running Cases

^sec-model-compression-deployment-scenarios-70c9

Cloud serving, a phone camera, and an embedded microcontroller each break down on a different term of the deployment budget, so compression begins by asking which term a given model violates and what it costs to stop violating it. Cloud inference centers on throughput (requests per second per dollar), where supported integer quantization paths increase serving density and kernel fusion reduces per-request kernel launch overhead ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-choudhary2020|Choudhary et al. 2020]]; [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-dean2018|Dean et al. 2018]]). Mobile and edge deployments must fit within tight physical memory bounds while meeting deterministic real-time deadlines. A serialized camera pipeline that must finish each frame before the next arrives at 30 frames per second has about 33 ms per frame. A pipelined design that overlaps capture, inference, and display can sustain 30 frames per second even when each frame takes longer than 33 ms end to end, so it must check frame rate and per-frame latency as two separate budgets.

TinyML makes physical fit a deployment requirement. A microcontroller with only a few hundred kilobytes of SRAM and limited model storage *cannot* accommodate a 100 MB model, regardless of predictive accuracy ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-banbury2020benchmarking|Banbury et al. 2020]]). Persistent weights may reside in flash or other supported storage, while runtime buffers occupy working memory. Without paging, the peak SRAM working set must fit the available SRAM; the model artifact must separately fit its storage budget. Capacity is also a hard bound on mobile and cloud devices, though their placement options differ.

↩︎ The latency, memory, and power envelopes defining cloud, edge, mobile, and TinyML tiers are established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.02 Four Deployment Regimes Across Nine Orders of Magnitude#^sec-ml-systems-deployment-paradigm-framework-0d25|Four Deployment Regimes Across Nine Orders of Magnitude]]**.

Meeting real-time deadlines on commodity mobile hardware depends as much on the hardware-supported precision path as on absolute memory capacity. When execution units provide hardware acceleration exclusively for fixed-point arithmetic, precision selection dictates whether a workload executes on energy-efficient neural processing units or falls back to power-hungry general-purpose cores. That choice decides the chapter’s running case, a camera pipeline that must meet an interactive frame rate within a phone’s thermal budget (Example [[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.02 Fitting the Deployment Budget#^exmp-model-compression-mobilenet-win|10.1]]).

**Example 10.1: The running case: Real-time blur on a phone**

**Scenario**: An illustrative composite rather than one measured product. A camera application deploys a MobileNetV2-based segmentation model for real-time background blur on mid-tier smartphones at 30 FPS.

**Diagnosis**: An uncompressed FP32 MobileNetV2 model runs on the phone’s CPU at only 8 FPS, about 125 ms per frame against a 33 ms budget, while holding the CPU at a power level the thermal envelope cannot sustain. The phone’s NPU or DSP accelerates integer matrix arithmetic, not FP32, so the uncompressed model cannot use it.

**Systems lesson**: INT8 quantization cuts raw parameter payload by 4$\times$, but most of the gain from 8 FPS to 35 FPS comes from what INT8 unlocks, a move from the CPU onto the integer accelerator. The precision change is the enabler; the change of processor supplies most of the speed. The frame rates are illustrative, so speed and power still require device measurement.

^exmp-model-compression-mobilenet-win

The chapter follows that camera pipeline through the structural and hardware tiers of the stack. Its model is one of the book’s lighthouses (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-lighthouse-models-9b1c|Lighthouse models put the iron law into practice]]**), the recurring reference workloads that are each chosen because one physical resource limits them. MobileNetV2 is the compute-bound lighthouse in its efficient form. Depthwise separable convolutions keep its arithmetic small, and at batch one on a phone its frame time goes to arithmetic and activation traffic rather than to reading weights. The precision tier needs a workload whose time is set by bytes, so it follows GPT-2 XL decoding on the same phone. GPT-2 XL is the bandwidth-bound lighthouse, and every token it generates streams every weight.

Two more lighthouses mark the ends of the memory constraint within the precision tier. DLRM ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-naumov2019deep|Naumov et al. 2019]]), the capacity-bound lighthouse, shows precision deciding whether embedding tables fit, and keyword spotting (KWS) ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.11 Source References#^ref-zhang2017hello|Y. Zhang et al. 2017]]), the power-bound lighthouse, shows precision deciding whether a model fits a microcontroller’s SRAM and energy budget. The fifth, ResNet-50, is the compute-bound lighthouse at full size, and it has two roles. In the structural tier it is the teacher that distills into MobileNetV2, and at the chapter’s close it is the subject of an INT8 deployment profile on the H100, the book’s reference data center accelerator, because a full-size model is served there rather than on a phone. Rather than running every technique on all five, the chapter returns to each workload where it exposes the limiting resource most clearly.

[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.02 Fitting the Deployment Budget#^tbl-model-vs-device|Table 1]] places the cases’ weight bytes and work beside the deployment budget, and two of its rows explain how the chapter divides the work. MobileNetV2’s FP32 weights stream across the phone’s 51.2 GB/s memory bus in about 0.27 ms, roughly 1 percent of the 33 ms frame budget. The frame is therefore spent on its 600 MFLOP of arithmetic and on activation traffic, so the structural and execution tiers are the levers that matter. GPT-2 XL’s FP16 weights fit in the phone’s memory but take about 59 ms to stream for every generated token, so precision, which shrinks the bytes behind each weight, is the lever that matters. Even MobileNetV2 at INT8 exceeds the TinyML envelope by about 6.7×, while the purpose-built depthwise separable convolutional network (DS-CNN) keyword spotter fits it after INT8 quantization.

The chapter descends the optimization stack one tier at a time ([[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.02 Fitting the Deployment Budget#^tbl-model-compression-chapter-spine|table 2]]). Structural optimization changes what the model computes and carries the camera pipeline through pruning, low-rank factorization, distillation from a ResNet-50 teacher, efficient architecture design, architecture search, and input-dependent computation. Numerical precision changes how each surviving value is stored and carries GPT-2 XL decoding from numerical formats and their energy, through the quantization methods, to the conditions under which fewer bits run faster. Hardware implementation changes how the remaining operations execute, through the fusions and sparse kernels that compression makes possible and the gap between paper savings and measured ones. That tier also sets the hardware efficiency ${\eta_{\text{hw}}}$, the fraction of the peak compute rate a kernel actually sustains. Choosing and combining techniques maps a limiting constraint to the levers that relieve it, sequences them on the camera pipeline, and turns to the toolchains that apply them. Measuring compression gains closes the chapter on a ResNet-50 INT8 deployment profile, which **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** takes up. The descent begins at the top of the stack, with the structure of the model itself.
