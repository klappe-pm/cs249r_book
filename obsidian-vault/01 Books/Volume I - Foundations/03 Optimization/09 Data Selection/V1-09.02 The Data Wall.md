# V1-09.02 The Data Wall

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09 Data Selection|V1-09 Data Selection]]

^sec-data-selection-data-selection-fundamentals-e839

Every example a training run processes costs the same forward pass, backward pass, and optimizer update, whether it teaches the model something new or repeats what the model already knows. A duplicated image, a mislabeled record, and a rare boundary case cost the same arithmetic while contributing very different learning signals. **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training#^sec-model-training|Model Training]]** made each of those steps as cheap as one machine allows and accounted for a whole run as roughly $6{P}{D}$ floating-point operations for ${P}$ parameters and ${D}$ tokens. Once each step is cheap, the next saving lies upstream, in choosing which examples deserve a step at all. This waste becomes acute at the **data wall**, the point at which the compute available for training grows faster than the supply of novel, high-quality examples to spend it on.[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.15 Footnotes#^fn1|¹]]

![[90 Assets/Volume I/09 Data Selection/Data Selection Scaling Saturation 5dd1042d2b.svg]]

*Two trend lines labeled compute and data diverge, opening a red-shaded gap labeled wall.*

*Compute outruns high-quality data supply; the widening gap is the data wall.*

Scaling laws[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.15 Footnotes#^fn2|²]] ([[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.14 Source References#^ref-kaplan2020scaling|Kaplan et al. 2020]]; [[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.14 Source References#^ref-hoffmann2022chinchilla|Hoffmann et al. 2022]]) quantify how model performance improves with dataset size, and teams have responded by collecting ever larger corpora, yet accelerator capacity expands faster than human-generated text and expert annotations. Much of the accessible public web has already been incorporated into large training sets, and specialist labeling grows slowly. **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering#^sec-data-engineering|Data Engineering]]** compared reported training-data scales, and **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.05 Data Acquisition#^fig-running-out-of-human-data|Training Data Approaching the Stock of Public Text]]** places selected language-model token totals against a fixed 2024 estimate of the effective stock of public text. Their fitted intersection is a constraint scenario, not a forecast of when unique text will run out. That is the wall at frontier scale, on fleets far larger than one machine, and it shifts engineering effort from collecting everything available to extracting more learning signal from each stored and processed sample.

↩︎ GPT-2, the bandwidth-bound lighthouse for decoder-only language models, is established in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^sec-network-architectures-inference-memory-bandwidth-wall-98d1|Autoregressive decoding]]**.

The full GPT-2 XL run that **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training#^sec-model-training|Model Training]]** costed shows the same wall on a single machine. WebText, GPT-2’s training corpus ([[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.14 Source References#^ref-radford2019language|Radford et al. 2019]]), holds 40 GB of text, about 10 billion tokens at roughly 4 bytes per token. The compute-optimal balance fitted by the Chinchilla study, about 20 training tokens per parameter (developed in [[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.03 Measuring Data Value#^sec-data-selection-computeoptimal-frontier-24ba|section 9.2.3]]), asks for 30 billion unique tokens for GPT-2’s 1.5 billion parameters, 3× what WebText holds.

The original run spent about 1.5 × 10²¹ FLOPs, which at six FLOPs per parameter per token processed about 167 billion tokens, so the model saw its corpus roughly 17 times. This chapter places the same run on one machine with 8 H100 accelerators running at 50 percent model FLOPs utilization (MFU), the fraction of peak arithmetic a training run actually delivers (definition [8.3](https://mlsysbook.ai/vol1/08_training/08_training.html#dfn-training-model-flops-utilization-mfu)), where it completes that budget in about 4.4 days and 590 kWh of accelerator energy.

Less than a week of one machine’s compute therefore passes over the whole corpus many times. An engineering team in that position can repeat epochs over the same text, where gradient updates on familiar tokens yield diminishing loss reductions, or it can lower quality thresholds to admit uncurated web text, where noisy and misaligned tokens degrade downstream evaluation. Instead of accepting either penalty, the team can invest in data selection (refining quality filters, constructing difficulty curricula, and synthesizing missing edge cases) to raise the learning return per FLOP.

When *compute* is abundant and *quality data* is scarce, the optimization priority inverts. Selection, not faster kernels, then extracts more learning per dollar, and for teams whose accelerator budget exceeds their curated corpus, the bottleneck shifts from accelerator access to the quality, legality, and diversity of the training data.

The bitter lesson applies here in data terms. A filter written from human intuition about which examples matter is the hand-built expertise the lesson warns against, whereas selection that uses the model’s own signals, such as loss, gradient norms, or embedding similarity, scales with compute. Either way, improved rankings must be established against downstream quality and coverage.

↩︎ The bitter lesson, that general methods using more computation outperform encoded human expertise, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.05 The Bitter Lesson#^sec-introduction-bitter-lesson-79c7|The Bitter Lesson]]**.

Data engineering makes data correct; data selection asks which correct examples are worth training on. When selection removes processing at matched quality, it shrinks the Data factor ($\text{Samples/Task}$) and therefore the total operations $({O})$ term in the iron law (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-iron-law|3]]). Selection therefore needs sample value stated relative to compute cost, and the information-compute ratio of [[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.03 Measuring Data Value#^sec-data-selection-informationcompute-ratio-8c0b|section 9.2.1]] measures that value as learning signal gained per unit of training compute.

**Definition 9.1: Data selection**

***Data selection*** is the process of retaining, prioritizing, or generating training examples to minimize the end-to-end cost of reaching target quality while preserving required coverage.

1.  **Significance**: Each excluded example removes a forward pass, a backward pass, and an optimizer update, so selection reduces $\text{Samples/Task}$ and therefore total operations $({O})$ directly.
2.  **Distinction**: A dataset can pass every data engineering check and still contain many examples that teach the model nothing new; selection judges informativeness and diversity, not correctness.
3.  **Common pitfall**: Minimizing dataset size instead of end-to-end cost. Scoring, labeling, and lost coverage can erase the savings of a smaller set.

Holding epoch count, batch size, and per-sample work fixed, a 50 percent reduction in dataset size directly halves the required forward passes, backward passes, and gradient updates. For the GPT-2 run above, it would halve both the 4.4 days on one eight-H100 machine and the 590 kWh of accelerator energy, provided the training schedule does not compensate by adding optimization steps. When data selection is combined with model compression and hardware acceleration, those reductions compound across all three axes of the iron law.

**Systems Perspective 9.1: Data selection and the iron law**

In the multiplicative D·A·M form of the iron law of ML systems (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|equation 1.2]]**, where ${T} = (\text{Samples/Task}) \times (\text{FLOPs/Sample}) \times (\text{Seconds/FLOP})$), data selection reduces the first factor ($\text{Samples/Task}$). Model-level optimizations reduce the second ($\text{FLOPs/Sample}$). Machine-level optimizations reduce the third ($\text{Seconds/FLOP}$, by increasing ${R_{\text{peak}}} \cdot {\eta_{\text{hw}}}$ and cutting memory and latency stalls). Selection removes work before those downstream optimizations execute it.

Because the three D·A·M factors multiply, their speedups compound. A 2× reduction in dataset size with 2× fewer operations per sample and 2× higher effective machine throughput yields an 8× reduction in run time because each axis divides the work or time the next axis sees. The machine factor unpacks into the three physical terms of **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 1.3]]** (${T} = \frac{{D_{\text{vol}}}}{{\text{BW}}} + \frac{{O}}{{R_{\text{peak}}} \cdot {\eta_{\text{hw}}}} + {L_{\text{lat}}}$), which state the condition for realizing that full product. Selection scales all three together when the loader stops reading the discarded records, because each step removed takes its bytes, its arithmetic, and its fixed overhead with it. The algorithmic and hardware speedups, however, make each remaining step faster, so they achieve their full multiplier only when they shrink the term that dominates the step, whether that term is compute, data movement $({D_{\text{vol}}}/{\text{BW}})$, or fixed overhead $({L_{\text{lat}}})$.

These compute savings propagate throughout the hardware hierarchy. By decreasing total data volume (${D_{\text{vol}}}$), deduplication and coreset selection (keeping a small subset that stands in for the full dataset) alleviate storage bandwidth demands, network fabric ingress, and host-to-accelerator PCIe transfers that otherwise leave the accelerator’s arithmetic units waiting on input. Upstream, active learning curbs annotation budgets by directing human labeling to samples chosen for uncertainty, diversity, or other task-relevant query criteria.

Yet selection is not free. Every selection strategy incurs its own runtime overhead to score, filter, shuffle, or coordinate samples. An online selection algorithm that executes additional forward passes to rank sample difficulty can consume more accelerator cycles than it saves if its selection overhead exceeds the subsequent reduction in training time. A pipeline claiming a training-time saving must make filtering plus subset training faster than full-data training at the same target quality, the selection inequality of [[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.03 Measuring Data Value#^sec-data-selection-selection-inequality-3b7e|section 9.2.6]]. Labeling savings and reusable representations require the broader cost accounting of [[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.09 Choosing a Selection Strategy#^sec-data-selection-decision-framework-0261|section 9.8]].

A learning-theory view of this problem counts the samples needed to reach a test error and treats each sample as free. The systems view counts the FLOPs, bytes, labels, seconds, and joules needed to reach the same quality, including the cost of choosing the samples. In the D·A·M taxonomy, data selection works on the data axis, deciding whether an example warrants processing at all before the algorithm fixes the operations each example costs and the machine fixes how fast those operations run. Removing an example therefore helps at both boundaries of the data axis. At the boundary with the machine, fewer bytes need to be stored, read, and moved to the accelerator. At the boundary with the algorithm, the operations that remain go to examples that still teach the model something, so each one returns more learning.

↩︎ The D·A·M taxonomy and its three diagnostic axes are established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.06 Defining ML Systems#^sec-introduction-defining-ml-systems-d4af|Defining ML Systems]]**.

The engineering toolkit for intelligent data selection follows a deliberate optimization ordering, first asking whether a sample is worth processing and only then how to process the remaining workload efficiently. Static pruning acts first by fixing the retained subset before target-model training begins, even when its scoring step uses a smaller proxy model, a cheap stand-in for the model being trained. Because a sample’s usefulness changes as the model learns, dynamic selection then adapts the training stream (curriculum learning) and the choice of examples for human labels (active learning) as training proceeds. Where real data still falls short after pruning and reordering, synthetic generation creates missing high-value samples on demand through augmentation, simulation, or distillation, in which a larger trained model (a *teacher*) labels the examples.

Learning from unlabeled data complements these three levers by redefining what counts as a supervision signal. Rather than selecting among labeled examples, semi-supervised and self-supervised methods derive learning targets from the structure of unannotated data. Which levers to use, and in what order, depends on the workload ([[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.02 The Data Wall#^fig-data-selection-pipeline|figure 1]]).

Two lighthouses carry the chapter, each in its own role. GPT-2 XL illustrates the data wall, the compute-optimal diagnosis of whether a run is data-starved, and token-level deduplication. Although GPT-2 XL is bandwidth-bound when it decodes one token at a time, it is compute-bound when it trains on long batches (**[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training#^sec-model-training|Model Training]]**), and training is the regime this chapter studies. ResNet-50 on ImageNet, the book’s compute-bound lighthouse, carries coresets, labels, augmentation, the input pipeline that must feed it, and the decision of which lever to fund.

Both lighthouses run on the book’s reference machine, the H100, so every saving can be stated in accelerator seconds and joules, and the measures of value in the next section use both lighthouses. Those seconds are compute-bound figures, which assume the host keeps the accelerator fed. ResNet-50 training crosses into an input-bound regime whenever the host cannot decode images as fast as the accelerator consumes them (**[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^sec-model-training-staged-pipeline|Pipeline stages and accelerator bubbles]]**), and [[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.08 Selection Engineering#^sec-data-selection-selection-engineering-a4eb|section 9.7]] shows what a pruned epoch saves in that regime. The recommendation lighthouse (DLRM), MobileNetV2, and keyword spotting return only in the closing comparison of [[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.09 Choosing a Selection Strategy#^sec-data-selection-decision-framework-0261|section 9.8]], where each turns out to be bound by a different resource.

Every lever in the chapter removes work at one stage of the machine and adds work of its own, so each must pass a test before it is accepted ([[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.02 The Data Wall#^tbl-data-selection-chapter-spine|table 1]]). Each test in the right-hand column depends on measuring what an example is worth, which is the subject of the next section.
