# V1-07.09 Major Frameworks TensorFlow, PyTorch, and JAX

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-major-framework-platform-analysis-fe96

A team that prototypes quickly but cannot deploy the resulting model, or deploys reliably but cannot debug training failures, has run into a framework design trade-off rather than a missing API call. Each major framework solves all three core problems but emphasizes a different path through them. TensorFlow couples eager development to graph capture and a broad deployment ecosystem. PyTorch begins with eager execution and adds capture, compilation, and export paths. JAX organizes differentiation, vectorization, and compilation as composable function transformations. These are architectural emphases, not exclusive capabilities, and their value depends on the workload and deployment target.

### TensorFlow

^sec-ml-frameworks-tensorflow-ecosystem-063c

TensorFlow’s architecture spans eager development and graph-based optimization across hardware from cloud TPUs to microcontrollers. TensorFlow 2 executes eagerly by default. Performance-sensitive functions can be captured with `tf.function`, and deployment formats route captured computation to server, mobile, and browser runtimes. This dual path preserves the production graph capabilities inherited from TensorFlow 1.x without requiring every TensorFlow 2 program to build a complete graph before it runs.

Within a captured `tf.function`, TensorFlow can apply graph optimizations such as constant folding, kernel fusion, and layout planning. The SavedModel serialization format is the boundary that separates training from deployment ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.09 Major Frameworks TensorFlow, PyTorch, and JAX#^fig-tensorflow-architecture|figure 14]]). Training workflows on the left, including `tf.data` preprocessing, the Keras modeling API, and distribution strategies across CPUs, GPUs, and TPUs, serialize into one SavedModel artifact. From this central interface, graph definitions pass through supported serving or target-specific conversion paths into deployment runtimes on the right (TensorFlow Serving, TensorFlow Lite, TensorFlow.js, and native language bindings) without retaining Python runtime dependencies.

![[90 Assets/Volume I/07 Frameworks/Generated Figure 7673229e5b.svg]]

Figure 14: **TensorFlow Training-to-Deployment Pipeline**: The SavedModel format provides a boundary between training and deployment by capturing graph structure, weights, and signatures. The right-hand paths include direct serving and target-specific conversion for Lite and JavaScript runtimes. Supported operators and conversion determine whether each path can run without Python in production.

^fig-tensorflow-architecture

TensorFlow’s answer to the execution problem is therefore two-sided: eager by default for development, with `tf.function` as the graph-conversion path for performance-sensitive code ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-tensorflowFunctionGuide|TensorFlow Developers 2024]]). Its strength is the compiled path from a captured graph to many deployment runtimes.

### PyTorch

^sec-ml-frameworks-pytorch-85cd

Where TensorFlow’s design centers the path from captured graph to deployment runtime, PyTorch centers *developer experience*. PyTorch was built from the start on dynamic graphs (or define-by-run). Instead of building a graph before execution, PyTorch builds the computational graph as the code runs, because researchers need immediate feedback when experimenting with novel architectures and a define-then-run cycle slows that loop. Python loops, conditionals, and debuggers work directly inside a model’s forward pass, with no special syntax and no separate compilation step, which matters most while architectures and training objectives are still changing.

PyTorch’s answer to the differentiation problem is tape-based autograd ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-pytorch-autograd-internals-4fa0|section 7.4.3.1]]): flexible and debuggable, but harder to optimize globally because the tape is rebuilt each iteration. Its answer to the abstraction problem is more pragmatic than comprehensive: strong GPU support through cuBLAS and cuDNN, with deployment paths including `torch.export`, edge-targeted ExecuTorch, ONNX, and specialized runtimes.

The cost of that flexibility is a more fragmented deployment path. Because the graph is dynamic, the framework cannot easily perform global optimizations before execution. A model that works perfectly in development may hit performance walls in production when dispatch overhead dominates small operations. To bridge this research-to-production gap, PyTorch added graph-capture and compilation paths (`torch.compile` and export workflows) that capture a dynamic model and turn it into an optimized representation for deployment. This evolution shows how an eager framework can move toward the production end of the compilation continuum while preserving the interactive experience that motivated the design.

### JAX

^sec-ml-frameworks-jax-functional-transformation-engine-242e

PyTorch’s eager execution and TensorFlow’s graph compilation represent two points on a spectrum, yet both share an imperative programming heritage where computation proceeds as a sequence of stateful operations. JAX takes a different user-facing approach, built on functional programming principles and composable program transformations rather than object-level tapes or user-authored graph APIs ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-bradbury2018jax|Bradbury et al. 2018]]). Developed at Google, JAX is especially useful for work requiring custom differentiation, advanced optimization research, and large-scale distributed training.

Where PyTorch and TensorFlow track state through objects and expose autograd through dynamic tapes or graph-capture paths, JAX asks users to write pure Python functions and treats differentiation, vectorization, and compilation as composable *program transformations* ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.09 Major Frameworks TensorFlow, PyTorch, and JAX#^lst-jax-transformations|listing 21]]). The `jax.grad` function returns a new function that computes gradients, which can then be transformed again when the interfaces are compatible: `vmap(grad(f))` computes per-example gradients, and `jit(vmap(grad(f)))` compiles that batched computation. Transformation order is semantically meaningful rather than arbitrary.

``` python
import jax
import jax.numpy as jnp

def loss_fn(params, x, y):
    pred = jnp.dot(x, params["w"]) + params["b"]
    return jnp.mean((pred - y) ** 2)

# Transform: compute gradients
grad_fn = jax.grad(loss_fn)

# Transform: vectorize over batch dimension
batched_grad = jax.vmap(grad_fn, in_axes=(None, 0, 0))

# Transform: compile to XLA
fast_batched_grad = jax.jit(batched_grad)

# Compose all three: fast, batched gradient computation
```

Listing 21: **JAX Function Transformations**: Wrapping an ordinary loss function in `grad`, then `vmap`, then `jit` yields per-example gradients compiled through XLA.

^lst-jax-transformations

This functional approach requires **pure functions** (no side effects) and **immutable data** (arrays cannot be modified in place). These constraints are stricter than PyTorch’s mutable object model, and they are what make the transformations safe. Because function outputs depend only on inputs, the compiler can reorder, fuse, and parallelize operations without changing results, and one transformation can be applied to the output of another.

Each transformation does one job. `jax.grad` returns a gradient function; `jax.vmap` can vectorize a compatible function over mapped axes; and `jax.jit` can trace and compile a stable transformed function for a particular argument signature. Unlike an iterative Python loop that issues individual operations sequentially with repeated dispatch overhead, `jax.vmap` pushes the batch dimension directly into the underlying primitives, allowing compatible per-sample matrix-vector operations to become batched matrix-matrix multiplications (GEMM). The compiled program can contain multiple kernels and library calls. The same transformation style extends across devices, where `jax.shard_map` (the successor to the older `jax.pmap`) maps a function over a group of accelerators. These transformations compose according to their types and semantics, and different orders can compute different quantities.

The same minimalist core delegates neural network abstractions to companion libraries (Flax and Equinox) and optimization to Optax. This separation reflects the functional philosophy: the core provides transformations, while libraries build conventional abstractions on top. The trade-off is that production readiness depends on both the transformation model and the maturity of the surrounding libraries, export paths, and operational tooling for the target environment.

The functional constraints pay off where gradient computation is itself the object of study. Custom differentiation, including higher-order gradients and custom vector-Jacobian product (VJP) and Jacobian-vector product (JVP) rules, composes cleanly because pure functions make differentiation rules predictable, which serves optimization research and scientific computing with AD. Compilation-heavy accelerator workloads gain utilization from XLA when the program fits the functional style. In exchange, JAX demands more upfront investment than PyTorch, with explicit state management, a learning curve for the functional paradigm, and compiled code that is harder to debug than eager execution. It fits teams whose requirements match these strengths rather than serving as a default.

### Design Trade-Offs Compared

^sec-ml-frameworks-quantitative-platform-performance-analysis-816d

Comparing TensorFlow, PyTorch, and JAX by asking which framework is fastest in the abstract asks the wrong question, because raw speed changes with model shape, batch size, hardware backend, and compiler configuration. The durable difference among the three designs (graph-first vs. eager-first, stateful vs. functional) is what each one lets the system see and optimize. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.09 Major Frameworks TensorFlow, PyTorch, and JAX#^tbl-mlfm-comparison|Table 11]] therefore maps TensorFlow, PyTorch, and JAX back to the three framework problems: execution visibility, differentiation model, and hardware abstraction path.

| **Aspect**                    | TensorFlow                               | PyTorch                                      | JAX                                  |
|:------------------------------|:-----------------------------------------|:---------------------------------------------|:-------------------------------------|
| **Graph Type**                | Static roots, dynamic front end in 2.x   | Dynamic                                      | Functional transformations           |
| **Programming Model**         | Imperative front end, graph capture path | Imperative                                   | Functional                           |
| **Core Data Structure**       | Tensor with framework-managed state      | Tensor with framework-managed state          | Immutable array                      |
| **Execution Mode**            | Eager by default, graph for optimization | Eager by default                             | Trace and just-in-time compilation   |
| **Automatic Differentiation** | Reverse mode over captured computation   | Reverse mode over an eager tape              | Forward and reverse transformations  |
| **Hardware Abstraction**      | Broad deployment runtimes and XLA paths  | Native GPU path plus export/compile runtimes | XLA-centered accelerator compilation |
| **Optimization Risk**         | Graph capture and operator coverage      | Graph breaks after eager development         | Purity, shape stability, and tracing |

Table 11: **Framework Design Trade-Offs**: Each column reflects a distinct answer to the three core problems. TensorFlow makes deployment and graph capture central, PyTorch makes eager execution and debugging central, and JAX makes functional transformation and compiler visibility central. The table is a diagnostic map, not a benchmark ranking.

^tbl-mlfm-comparison

The comparison therefore tells an engineer which constraint to profile first. In PyTorch the first question is whether eager dispatch or graph breaks dominate. In TensorFlow it is whether the captured graph covers the operators and deployment target, and in JAX whether shapes and purity let XLA compile the program actually executed. A framework-level comparison or leaderboard can orient a decision, but it cannot replace profiling the specific workload on the target hardware.

The same simple network exposes how each design philosophy shapes the code. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.09 Major Frameworks TensorFlow, PyTorch, and JAX#^lst-framework-hello-world|Listing 22]] implements one neural network, a single linear layer mapping ten inputs to one output, across all three frameworks.

``` python
# PyTorch - Dynamic, Pythonic
import torch.nn as nn

class SimpleNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(10, 1)

    def forward(self, x):
        return self.fc(x)

# TensorFlow/Keras - High-level API
import tensorflow as tf

model = tf.keras.Sequential(
    [tf.keras.layers.Dense(1, input_shape=(10,))]
)

# JAX - Functional approach
import jax.numpy as jnp
from jax import random

def simple_net(params, x):
    return jnp.dot(x, params["w"]) + params["b"]

key = random.PRNGKey(0)
key_w, key_b = random.split(key)
params = {
    "w": random.normal(key_w, (10, 1)),
    "b": random.normal(key_b, (1,)),
}
```

Listing 22: **Hello World in Three Frameworks**: One single-layer network is written three ways, in PyTorch (object-oriented), TensorFlow/Keras (declarative), and JAX (functional).

^lst-framework-hello-world

These three implementations solve the same mathematical problem, yet each reveals where its framework keeps state and when its computation graph comes into existence. PyTorch couples state and computation through class inheritance (`nn.Module`) and evaluates eagerly, building the graph as Python runs. Standard debuggers and control flow therefore work naturally, at the cost of hiding the full computation from an optimizer unless a graph-capture pass is invoked. TensorFlow and Keras also execute eagerly by default in TensorFlow 2, whereas structured models can be captured with `tf.function` and exported to supported deployment runtimes whenever operator coverage and target conversion allow. By contrast, JAX treats the model as a pure function[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn25|²⁵]] over immutable arrays with no internal object state. It turns `grad`, `vmap` (automatic vectorization), and `jit` (just-in-time compilation[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn26|²⁶]]) into composable transformations on stateless functions, in exchange for explicit parameter passing.

No single design serves every goal at once, and the ten-line program makes the trade visible in source code rather than buried in compiler internals: where state lives, when the graph exists, and what the compiler is allowed to see. Each design trades what the compiler can see against how quickly a person can iterate. Graph capture and ahead-of-time compilation can reduce runtime overhead and intermediate data movement. Eager evaluation shortens the human iteration loop, outside the iron-law runtime equation, at the cost of compiler visibility until a graph-capture path is used. Functional purity gives XLA more freedom to transform a stable traced program. Each philosophy also shapes code syntax, team workflows, debugging practices, and deployment pipelines, so migration costs grow with project-specific integrations and assumptions.
