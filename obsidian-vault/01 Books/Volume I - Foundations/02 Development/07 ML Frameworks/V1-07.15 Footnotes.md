# V1-07.15 Footnotes

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^footnotes

<sup>1</sup> **Kernel (GPU)**: In GPU programming, a kernel is the function dispatched to execute in parallel across thousands of threads. Each kernel launch costs about 5 ${\text{µ}}$s of CPU-side overhead for parameter assembly and GPU signaling, and an eager framework’s Python dispatch adds about 10 ${\text{µ}}$s more before the launch, the split this chapter’s overhead model uses. Small, unfused operations therefore spend more time on launch overhead $({L_{\text{lat}}})$ than on useful arithmetic. Kernel fusion, which merges several operations into one kernel ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8|section 7.3.2]]), reduces the kernel count and is therefore a direct attack on the overhead term of the iron law.

^fn1

<sup>2</sup> **Eager execution**: This mode executes each operation immediately, which enables direct debugging with standard tools but sacrifices the global view needed for graph-level optimizations. Without capturing a larger region of computation, an eager runtime cannot fuse across that region or preplan its memory, leaving workload-dependent optimization opportunities for compilers such as `torch.compile`.

^fn2

<sup>3</sup> **Computational graph**: Optimizing before executing is the design choice that separates graph execution from eager execution. Capturing the program as a data structure lets a framework fuse compatible operations into fewer GPU kernels before execution, reducing launch overhead and intermediate memory traffic. The engineering cost of this visibility is that the executed program differs from the source code, making debugging harder, a trade-off every graph-based framework must justify against the performance gain.

^fn3

<sup>4</sup> **BLAS (basic linear algebra subprograms)**: The 1979 API specification at the bottom layer of the stack; it fixed a set of Fortran-callable vector operations and separated the public routine names from the machine-specific implementation beneath them. Every framework above it inherits the same division: call a standard linear-algebra routine from any language and let a tuned vendor library target the processor. On NVIDIA GPUs, the tuned path for general matrix multiply (GEMM), a Level 3 routine added in 1990, is cuBLAS ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-nvidia-cublas-10898670|NVIDIA 2024]]).

^fn4

<sup>5</sup> **GEMM**: The matrix-matrix primitive behind `C = A @ B`. Hardware vendors hand-tune GEMM for their specific chips because dense layers, attention projections, and convolution lowering all rely on matrix multiplication, making this one routine a performance floor for many frameworks above it in the stack. Its high arithmetic intensity makes GEMM the operation most able to approach peak compute throughput, while small or misaligned shapes often fall back to much lower utilization.

^fn5

<sup>6</sup> **NumPy (numerical Python)**: In 2005, Travis Oliphant unified two competing Python array libraries (Numeric and Numarray) into a single BLAS-backed package. Its pattern of writing logic in Python and executing loops in compiled code became the design template for ML frameworks: PyTorch tensors and TensorFlow arrays extend the same ${n}$-dimensional array abstraction to GPUs.

^fn6

<sup>7</sup> **Theano**: Developed at the Montreal Institute for Learning Algorithms (MILA) under Yoshua Bengio starting in 2007, Theano was an early and influential Python framework that compiled symbolic mathematical expressions into optimized CPU and GPU code via computational graphs ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-bergstra2010|Bergstra et al. 2010]]; [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-al2016theano|Team et al. 2016]]). It demonstrated that a Python-defined computation graph could be compiled for GPU execution without requiring the researcher to write CUDA code. Mila ended active development of Theano in 2017 ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-milaTheanoDevelopment|Mila 2026]]).

^fn7

<sup>8</sup> **Fused attention kernel**: A fused attention kernel combines the ${\mathbf{Q}}{\mathbf{K}}^T$ product, softmax, and value-weighted output into one kernel. FlashAttention, introduced in **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.07 Attention Dynamic Processing#^sec-network-architectures-memory-requirements-72c3|Memory requirements]]**, is the canonical named example. The framework lesson is broader than the specific algorithm: fusion can shift an operation’s position on the roofline model from bandwidth-limited toward throughput-limited execution by reducing round-trips through external memory.

^fn8

<sup>9</sup> **Autograd tape**: The tape’s own nodes are small; its memory cost comes from the tensors they reference. That footprint grows with model depth and sequence length as saved activations accumulate until backpropagation releases them, a cost that [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-memory-management-strategies-b008|section 7.4.2]] quantifies.

^fn9

<sup>10</sup> **Dead code elimination (DCE)**: Removes graph nodes whose results do not affect observable outputs or side effects. In ML graphs, dead code arises from unused branches or post-transform artifacts; side-effect analysis ensures safe removal to prevent execution of dead operations and reduce kernel launch overhead.

^fn10

<sup>11</sup> **XLA (accelerated linear algebra)**: XLA fuses subgraphs, specializes layouts, and lowers high-level operations into backend-specific code, so its fusion attacks both launch overhead $({L_{\text{lat}}})$ and intermediate memory writes $({D_{\text{vol}}})$. Its speedup is therefore not a fixed multiplier. Large GEMM-heavy regions may already be compute bound, while chains of small elementwise operations benefit more because fusion removes repeated trips through external memory, so gains depend on graph structure, backend support, and input-shape stability.

^fn11

<sup>12</sup> **Intermediate representation (IR)**: The “intermediate” captures this format’s architectural role: a language-independent layer that decouples the frontend (Python capture) from the backend (hardware code generation), exactly as LLVM IR decouples C/Rust/Swift frontends from x86/ARM backends. ML frameworks adopted this compiler pattern because it reduces the $\mathcal{O}({M}\times {N_{\text{backend}}})$ cost of supporting ${M}$ frontends and ${N_{\text{backend}}}$ backends to $\mathcal{O}({M}+ {N_{\text{backend}}})$: a single graph capture mechanism (PyTorch’s TorchDynamo, or TensorFlow’s bridge into XLA) can target multiple hardware backends without rewriting the capture logic.

^fn12

<sup>13</sup> **`torch.compile`**: PyTorch’s capture front end analyzes Python bytecode as each frame runs, rather than recording tensor operations alone. That vantage lets it keep capturing across Python control flow it can resolve from guarded values and insert a graph break where it cannot, which is why graph breaks rather than tracing errors are its characteristic failure mode.

^fn13

<sup>14</sup> **CUDA (compute unified device architecture)**: NVIDIA’s parallel computing platform, released in 2007, serving as the foundational layer between high-level Python operations and GPU silicon; when PyTorch executes `torch.matmul(A, W)`, the call traverses the framework’s dispatcher, selects a cuBLAS kernel, and launches it on the GPU. Each launch adds the 5 μs kernel-launch share of the per-operation overhead on top of the framework’s Python dispatch. For small operations, this dispatch overhead $({L_{\text{lat}}})$ can exceed useful compute time. Fusing compatible groups of operations then reduces launch count as well as intermediate memory traffic; capturing the graph alone does not imply a single kernel.

^fn14

<sup>15</sup> **TinyML**: Systems designed for MCUs cannot afford a Python interpreter. Micro-runtimes instead use small C/C++ runtimes, fixed memory planning, and model-specific operators. TensorFlow Lite Micro remains interpreter-based: the application supplies a tensor arena whose buffers are planned and reused without heap allocation after setup. Predictable memory is mandatory because exceeding a 256 KB device budget can prevent initialization or inference.

^fn15

<sup>16</sup> **Gradients**: A gradient holds one value for every parameter it differentiates, so each weight tensor acquires a gradient tensor of the same shape. Computing gradients automatically therefore doubles the parameter-sized state before any optimizer runs, which is why training-memory accounts, such as the one in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-memory-training-vs-inference|Worked example: Training vs. inference memory]]**, list gradients as a full copy of the weights.

^fn16

<sup>17</sup> **Reverse-mode AD**: Reverse mode’s single backward pass has a concrete memory cost, because the operation-dependent values that derivative rules read must be retained until the backward traversal reaches them.

^fn17

<sup>18</sup> **Gradient accumulation**: The framework processes a large logical batch as smaller micro-batches, freeing each micro-batch’s saved activations after backward while accumulating parameter-sized gradients. Processing 4,096 samples in 64-sample micro-batches can reduce the batch-dependent activation peak by up to 64× when activation memory scales linearly with batch size; weights, gradients, optimizer state, and other fixed costs do not shrink. The trade-off is more sequential work before each optimizer update.

^fn18

<sup>19</sup> **Fusion and saved state**: Fusion removes the forward round-trip of an intermediate through HBM, but it does not remove the backward pass’s need for that value. If a derivative rule reads a fused intermediate, such as the pre-activation whose sign forms the ReLU mask, the fused kernel must still write that value (or a compact mask) to memory, or the backward pass must recompute it. Fusion and checkpointing therefore interact, because the compiler decides which intermediates to materialize from what the backward graph will read.

^fn19

<sup>20</sup> **JAX**: JAX exposes `grad`, `jit`, and `vmap` as transformations on functions; they can be composed when one transformation’s outputs match what the next expects as inputs, but order matters: vectorizing gradients is not generally the same operation as differentiating a vector-valued result. Compilation can produce fused regions, library calls, and multiple kernels rather than one universal kernel. Transformed functions should be pure; Python side effects may occur during tracing but are not represented in the compiled program, while supported callbacks express intentional runtime effects.

^fn20

<sup>21</sup> **Tensor**: In mathematics, tensors obey coordinate-transformation laws; ML frameworks use the term more broadly for multidimensional arrays carrying shape, dtype, strides, device placement, and often automatic-differentiation metadata. A transpose commonly creates a strided view, while reshape may return either a view or a copy depending on the layout. These storage semantics make layout relevant to kernel selection and data movement.

^fn21

<sup>22</sup> **NVLink**: NVIDIA’s high-bandwidth GPU-to-GPU interconnect, providing 900 GB/s bidirectional bandwidth (NVLink 4.0 on the H100) compared to 128 GB/s for its PCIe Gen5 x16 host link. This 7.0× bandwidth advantage determines whether splitting one large tensor computation across multiple GPUs is practical for a given model size: GPUs connected only by PCIe can make the ${D_{\text{vol}}}/{\text{BW}}$ communication term dominate total training time, erasing the benefit of additional compute.

^fn22

<sup>23</sup> **nn.Module**: The pattern recurs across frameworks because the organizational problem is universal. `nn.Module` automatically registers any assigned submodule or parameter into a hierarchical tree, enabling a single `.to('cuda')` call to recursively place millions of parameters onto a GPU. Keras layers, JAX Flax modules, and TensorFlow’s `tf.Module` all implement the same tree-walking pattern. Without it, managing model state would require manual bookkeeping that scales linearly with architectural depth, a cost that grows prohibitive for models with hundreds of layers.

^fn23

<sup>24</sup> **HBM (high bandwidth memory)**: Provides 3.35 TB/s on the H100, making it the memory tier that most directly feeds accelerator arithmetic; HBM bandwidth determines whether operations are memory bound or compute bound, and its 80 GB capacity sets the hard ceiling on total live training state. Weights, activations, gradients, optimizer state, and temporary workspace must fit during execution. When they do not, the framework must resort to offloading, selective recomputation, or placement across devices, each adding complexity to what the programmer perceives as a single `loss.backward()` call.

^fn24

<sup>25</sup> **Pure function**: Returns outputs determined by its inputs without relying on untracked side effects; JAX transformations are designed for pure functions. Ordinary Python effects may run during tracing but are not represented in the compiled computation, and impure code can fail or behave unexpectedly. Runtime printing or external effects require supported mechanisms such as `jax.debug.print` or callbacks; random draws require explicitly managed keys.

^fn25

<sup>26</sup> **Just-in-time (JIT) compilation**: Traces a function for an argument signature and lowers it to backend-specific executable code; the first call pays tracing and compilation costs; compatible later calls can reuse the cached executable. New shapes, dtypes, devices, or static arguments may trigger another compilation. Both compilation time and cached-call overhead depend on the program, backend, and hardware.

^fn26
