# V1-07.04 Execution from Graphs to Kernels

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-execution-problem-e1e1

Consider two engineers writing the same neural network. The first debugs interactively, printing tensor shapes after each operation, inspecting intermediate values, and stepping through code with `pdb`. The second waits through a compilation step, then watches a model built from many small operations run faster while losing that direct, line-by-line view of intermediate state. Both are correct; they have made different choices about the **execution problem**, the question of whether operations should execute immediately as written or be recorded for later execution. It sets debugging workflow, deployment options, and peak hardware utilization. The GPT-2 XL decoding step that opened this chapter is the case in point: issued one operation at a time, it keeps the accelerator waiting on the host for most of the step.

### Computational Graphs

^sec-ml-frameworks-computational-graph-00f7

If a runtime sees only one Python operation at a time and forgets it as soon as the kernel returns, it cannot know which intermediate tensors later gradient rules will need or which adjacent operations could share registers on the accelerator. To plan across operations, a framework represents the program the same way **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures#^sec-network-architectures|Network Architectures]]** represented model architectures, as a computational graph: a directed acyclic graph (DAG) where nodes represent operations and edges represent data dependencies. The rest of this chapter follows that graph down toward the hardware. It is the same structure that backpropagation traverses in reverse, here serving as the framework’s internal model of the computation for scheduling and optimization as well.

A graph decouples the mathematical operations from the order in which hardware evaluates them. In the minimal case ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^fig-comp-graph|figure 2]]), directed edges route input variables ${x}$ and ${y}$ into the central transformation operator ${f}({x}, {y})$, which emits the output variable ${z}$.

![[90 Assets/Volume I/07 Frameworks/Generated Figure 4f76f06c96.svg]]

Figure 2: **Simple Computational Graph**: Representing ${z} = {f}({x}, {y})$ as a directed acyclic graph decouples mathematical dependencies from physical execution order, providing the structural blueprint frameworks require to track gradients and schedule operations across devices.

^fig-comp-graph

Real machine learning models require much more complex graph structures. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^fig-mlfm-comp-graph|Figure 3]] partitions a larger graph and the runtime that executes it into two coupled domains: the left container isolates a six-node neural network DAG with explicit dataflow edges, while the right container houses the runtime components (memory management and device placement) that interface with it.

![[90 Assets/Volume I/07 Frameworks/Generated Figure 0970a7fcc1.svg]]

Figure 3: **Computation Graph with System Interactions**: A neural network DAG (left) interfaces with framework runtime components (right). By maintaining an explicit graph representation independent of execution, the framework can analyze tensor lifetimes for memory reuse and assign operations to target accelerators before issuing arithmetic.

^fig-mlfm-comp-graph

This graph representation is more than a visualization; it is the data structure that enables both efficient execution and automatic differentiation. Without a graph that spans multiple operations, a runtime must launch each operator in isolation and materialize every intermediate tensor in off-chip memory before the next kernel can read it.

### The Memory Wall and Kernel Fusion

^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8

That isolation is costly whenever an unoptimized runtime evaluates a sequence of memory-bound operations such as $\text{LayerNorm} \to \text{Dropout} \to \text{ReLU}$ as three separate GPU kernels. Dropout and ReLU are purely element-wise; LayerNorm also computes a mean and variance across each row, but in the idealized count, like the other two, it reads each element once and writes each result once. The first kernel reads inputs from off-chip high-bandwidth memory (HBM) and writes intermediate results back to HBM, the second reads those results and writes back again, and the third reads them a final time. Shuttling intermediate tensors across the external memory bus three times dwarfs the arithmetic time and leaves compute units idle.

This bottleneck stems from the memory wall, the widening gap between compute growth and memory-bandwidth growth that **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.03 Physical Constraints on Deployment#^eq-memory-wall|equation 2.3]]** quantifies. An accelerator performs arithmetic far faster than it fetches operands from off-chip memory. Most individual operation types in a neural network (activations, normalizations, and other element-wise operations) are therefore memory bound, limited by data movement. The large matrix multiplications that dominate total arithmetic can be compute bound, limited by arithmetic throughput. **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]** formalizes the boundary between the two regimes. Both regimes trace back to the memory hierarchy, in which on-chip storage (registers and SRAM scratchpads) is fast but small while off-chip HBM is large but far slower to reach.

↩︎ The memory wall and the growth-rate ratio behind it are established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.03 Physical Constraints on Deployment#^sec-ml-systems-deployment-spectrum-71be|Physical Constraints on Deployment]]**.

Kernel fusion (also called operator fusion) fixes memory-bound chains by combining them into a single kernel that avoids intermediate HBM traffic. Instead of three round-trips to HBM, a fused kernel loads inputs from HBM once, evaluates normalization, dropout, and ReLU entirely within on-chip registers and SRAM, and writes only the final output tensor back to HBM, cutting memory traffic by roughly 3×. In general, for ${N}$ elements of ${s_{\text{elem}}}$ bytes each, fusing a chain of ${n_{\text{ops}}}$ elementwise operations into one kernel reduces idealized read-and-write traffic from $2{n_{\text{ops}}} {N}{s_{\text{elem}}}$ to $2{N}{s_{\text{elem}}}$ bytes, a derivation worked in **[[05 Reference/Volume I - Foundations/V1 Algorithm Foundations#^sec-appdx-algorithm-foundations-operator-fusion-5d73|Operator fusion]]**. Fusion also removes all but one of the chain’s kernel launches. During training, fusion has a limit. It removes an intermediate’s round-trip through HBM, but if the backward pass must later read that intermediate, the fused kernel still has to write it to memory and keep it ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-memory-management-strategies-b008|section 7.4.2]]).

Attention kernels[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn8|⁸]] use the same principle at larger scale. The full attention matrix holds one score for every pair of positions, so it grows with the square of the sequence length. Instead of materializing that matrix in HBM, a fused implementation can work through it in tiles, blocks small enough to stay in on-chip memory close to the compute units, cutting HBM accesses by up to 9$\times$ and producing workload-specific speedups from 15 percent to 3$\times$ ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-dao2022|Dao et al. 2022]]).

↪ The on-chip limits that decide which intermediates a fused kernel can keep on a specific accelerator are developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-kernel-fusion-7faf|Kernel fusion on the accelerator]]**.

Framework compilers can fuse only operations that are visible to them simultaneously. When an eager runtime dispatches operations individually, each kernel launch executes in isolation, concealing cross-operation fusion and buffer-reuse opportunities. Capturing a broader region of computation into a deferred graph removes that isolation: the compiler can examine an entire sequence of dependencies, establish intermediate tensor lifetimes, and fuse compatible operations before dispatching work to the accelerator.

The computational graph enables global optimization, but the timing of its construction forces a four-way trade-off across debugging, optimization, deployment, and flexibility. Consider an elementary expression such as `y = x * 2`. Evaluating the multiplication immediately yields a concrete tensor in `y` so developers can inspect intermediate values and branch on computed tensor values with standard Python control flow, but the runtime sees only one operation at a time. Deferring execution records the operation symbolically into a dependency graph that can be fused, memory-planned, and exported to run without the host interpreter. Because no single execution model serves all four demands at once, modern frameworks span three strategies: eager execution with dynamic graphs, static computation graphs, and hybrid approaches that combine just-in-time (JIT) compilation with eager development.

### Eager Execution with Dynamic Graphs

^sec-ml-frameworks-eager-execution-dynamic-graphs-29c2

When a tensor shape mismatches or an activation turns to `NaN` mid-layer, a deferred graph fails far from the Python line that created the operation, hiding the intermediate values that caused the fault. Eager execution, also called define-by-run, avoids that disconnect by evaluating each operation as soon as the program calls it and building the computation graph dynamically at runtime.

**Example 7.1: Eager vs. graph execution code comparison**

**PyTorch (eager execution)**:

``` python
import torch

x = torch.tensor([1.0, 2.0])
y = x * 2
print(f"Intermediate value: {y}")  # Works immediately
z = y.sum()
```

**TensorFlow 1.x (static graph)**:

``` python
import tensorflow as tf

x = tf.placeholder(tf.float32)
y = x * 2
# print(y) -> Prints Tensor("mul:0"...), not value!
z = tf.reduce_sum(y)

with tf.Session() as sess:
    result = sess.run(z, feed_dict={x: [1.0, 2.0]})
```

**Systems insight**: Eager execution exposes intermediate values as ordinary runtime state, which makes debugging direct. Static graphs stage computation before execution, which enables whole-graph optimization but changes the debugging model.

^exmp-frameworks-eager-vs-graph-execution-code-comparison

In this define-by-run model, when host code evaluates `y = x * 2`, the runtime places the multiplication kernel in the device’s command queue and immediately returns a tensor handle, a reference to a result the device may not have computed yet. Python moves on to the next line while the device works through its queue asynchronously, and later operations that use `y` queue up behind the multiplication. The host waits only when it needs the actual number, for example to print `y` or to branch on its value; that wait is called synchronization.

Immediate evaluation gives eager code the flexibility of ordinary programming: developers can print intermediate values, use conditionals based on computed results, and debug with standard tools. The framework records operations as they happen, constructing a dynamic graph that reflects the actual execution path taken.

For gradient computation, the framework records a history of operations in what is called an autograd tape,[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn9|⁹]] a transient data structure built during execution. Each tensor operation creates a node that records: the operation performed, references to input tensors, and how to compute gradients. These nodes form a DAG that records the actual path taken during forward-pass execution rather than a graph fixed in advance. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^lst-autograd-tape-example|Listing 1]] shows how PyTorch records operations as they execute in its default eager mode.

``` python
import torch

x = torch.tensor([1.0], requires_grad=True)
y = x * 2  # Executes immediately; records MulBackward node
z = y + 1  # Executes immediately; records AddBackward node
# The autograd tape exists NOW, built during execution
```

Listing 1: **Autograd Tape Construction**: Each operation executes immediately while recording a backward node to the autograd tape for later gradient computation.

^lst-autograd-tape-example

After these two operations, the framework has constructed an autograd tape with two nodes: one for the multiplication and one for the addition. The tape records that `z` depends on `y`, and `y` depends on `x`. PyTorch names each node after its operation with a numeric suffix, so the two nodes in the listing’s comments appear at runtime as `MulBackward0` and `AddBackward0`.

Calling `z.backward()` traverses this tape in reverse topological order, applying the chain rule at each node:

1.  Compute $\frac{\partial {z}}{\partial {z}} = 1$ (seed gradient)
2.  Call `AddBackward0.backward()` $\rightarrow \frac{\partial {z}}{\partial {y_{\text{tape}}}} = 1$
3.  Call `MulBackward0.backward()` $\rightarrow \frac{\partial {z}}{\partial {x}} = 2$
4.  Accumulate gradient in `x.grad`

Backward rules read values saved during the forward pass, so those values stay in memory until backward consumes them. After `backward()` completes, autograd normally releases that saved state, and the next forward pass builds a new graph. Why the traversal works, and what keeping those values costs, is the subject of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-differentiation-problem-8b8a|section 7.4]].

**Example 7.2: In-place operations can break gradients**

**Scenario**: An engineer applies an in-place mutation (`x += 1`) within a custom PyTorch activation function to reduce memory allocations.

**Diagnosis**: In-place operations overwrite tensor memory containing forward-pass activations required by the autograd tape for backward-pass gradient computation, triggering a runtime version-counter error ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-pytorchAutogradDocs|PyTorch Contributors 2026a]]). PyTorch enforces this safety invariant by maintaining an integer version counter on each tensor that increments on every in-place write. If a saved tensor’s version at backward execution differs from its version recorded during the forward pass, autograd throws an error, because the activation required by the derivative rule was modified in place.

**Systems lesson**: Framework automatic differentiation depends on immutable forward-pass activation records. In-place writes to a saved tensor invalidate the autograd record, so PyTorch stops with an error rather than compute a wrong gradient.

^exmp-frameworks-in-place-autograd-failure

Recording that tape and launching device work happen inside the same one-operation-at-a-time loop ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^fig-mlfm-dynamic-graph-flow|figure 4]]). Python defines an operation, the runtime records its backward node and enqueues its device work, and control returns to Python for the next call while the device may execute asynchronously. When the runtime decides what to launch, it sees only the current operation rather than a whole region of future calls.

![[90 Assets/Volume I/07 Frameworks/Generated Figure 28293cabb9.svg]]

Figure 4: **Dynamic Graph Execution Flow**: In eager execution, each operation is issued as the program encounters it. Accelerator work may execute asynchronously after dispatch. This define-by-run model enables natural debugging and data-dependent control flow while limiting optimization across Python calls.

^fig-mlfm-dynamic-graph-flow

The dynamic autograd tape expresses data-dependent behavior directly in the host language. Conditionals and loops can depend on tensor values computed during execution, enabling algorithms such as beam search, dynamic-length recurrent models, or adaptive compute paths that adjust their execution based on intermediate activations. Static graphs can also represent data-dependent control flow and dynamic dimensions through graph operations, but eager execution makes these patterns natural to write and debug in Python. Because operations are issued immediately, developers can print tensors, inspect values, and use standard debuggers (`pdb`, breakpoints) to diagnose errors much as they would in another Python program.

This flexibility imposes latency costs that map directly to the iron law. Each training step constructs an autograd tape dynamically, adding host-side Python dispatch latency and tape allocation to ${L_{\text{lat}}}$. Because every operation traverses the framework dispatcher before a device kernel launches, host overhead quickly dominates when individual kernels execute in single-digit microseconds. Eager execution also lacks a whole-graph view, preventing the framework from fusing element-wise chains into single GPU launches (which would cut ${D_{\text{vol}}}$) or pre-allocating a static memory arena, one block reserved in advance from which every intermediate buffer is carved (which would cut allocation overhead in ${L_{\text{lat}}}$). The autograd tape must retain every tensor requested by registered backward rules, holding memory until backpropagation consumes it. Together, these costs impose a throughput ceiling on fine-grained workloads where dispatch latency overshadows device arithmetic.

### Dispatch Overhead in Eager Execution

^sec-ml-frameworks-dispatch-tax

That throughput ceiling appears whenever a kernel finishes in a few microseconds while the host-side interpreter and driver need tens of microseconds to issue it. The **dispatch overhead ratio**, host software time ${T_{\text{sw}}}$ divided by device hardware time ${T_{\text{hw}}}$, quantifies this mismatch in an additive model without host-device overlap. Asynchronous enqueue hides host cost only while the host stays ahead of the device and keeps its queue full. If each kernel finishes faster than the host can issue the next one, the queue drains and the device waits, so host time adds to the step as the model assumes. When the ratio exceeds 1, host dispatch takes more than half of each step; the dispatch overhead law of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-dispatch-overhead-law-9e0a|section 7.3.7.2]] writes this same ratio in terms of operation count and per-operation cost.

![[90 Assets/Volume I/07 Frameworks/Frameworks Dispatch Tax Divergence be0b7ebcea.svg]]

*Two stacked bars, each normalized to its own step time. For a small operation, a gray dispatch segment labeled 94 percent fills nearly the whole bar beside a sliver of orange compute; for a large operation, an orange compute segment fills most of the bar and the gray dispatch segment is labeled 13 percent.*

*Fixed dispatch dominates small ops and fades behind large ones.*

In the illustrative eager-execution model used here, every operation pays a fixed cost of approximately 15 μs for Python-side dispatch and driver launch combined, the same per-operation cost as the decoding step that opened the chapter. Actual overhead varies by framework, backend, and hardware, but its relative weight still depends on operation size. For a small operation such as a ReLU on a small vector, the kernel might execute in only 1 μs. Dispatch then takes 94 percent of the modeled step time, the dispatch overhead ratio sits far above 1, and the GPU spends most of its time waiting for the next command. For a large operation such as a large matrix multiply, the kernel executes for 100 μs, dispatch drops to 13 percent of the modeled step time, and the dispatch overhead ratio falls well below 1. The operation is device-work dominated; distinguishing compute from memory limits still requires comparing its work and traffic.

Dispatch overhead explains why models with many small layers run significantly slower than their raw FLOP count predicts. **[[05 Reference/Volume I - Foundations/V1 The D·A·M Taxonomy#^sec-appdx-dam-taxonomy-bottleneck-diagnostic-3fc9|Acting on the limiting term]]** places this symptom in the bottleneck taxonomy, classifying a dispatch-dominated workload as overhead-bound rather than compute-bound and showing which optimizations actually move it. Removing that per-operation interpreter work requires moving from *kernel-by-kernel dispatch* to *graph-level execution*, either by defining a static computation graph ahead of time or by capturing and compiling regions just in time ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-hybrid-approaches-jit-compilation-8954|section 7.3.6]]). A captured graph can still launch multiple kernels, so how much launch overhead remains depends on fusion and on whether a runtime resubmits the captured launch sequence as one unit.

↩︎ The MNIST epoch estimate, in which this fixed per-operation cost decides training time on a CPU and an accelerator alike, is established in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-iterative-learning-process-10b9|Iterative learning process]]**.

### Static Computation Graphs

^sec-ml-frameworks-static-computation-graphs-e100

The overhead costs of eager execution motivate the opposite design: capturing the entire computation before executing any of it. Because an eager runtime sees only one operation at a time, it cannot fuse a chain of small kernels or plan buffer reuse across a whole layer before launching work on the accelerator. Static graph execution solves this visibility problem by defining the complete computational graph as a symbolic representation first and executing it in a separate phase. This “define-then-run” execution model means the graph exists before any computation occurs, enabling ahead-of-time analysis, transformation, and global optimization that separate eager calls cannot support unless a compiler captures them.

Static graphs implement a clear separation between graph construction and execution. TensorFlow 1.x, which exemplified this approach, makes the two phases explicit in code ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^lst-tf-static-graph|listing 2]]). It deliberately runs the same `x * 2` then `+ 1` computation shown under eager execution in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^lst-autograd-tape-example|listing 1]], holding the arithmetic fixed so that the only thing that changes is *when* it executes. Symbolic definition creates placeholders and operations without computation, while explicit execution triggers actual arithmetic.

``` python
# Phase 1: Graph Construction (symbolic, no computation)
import tensorflow.compat.v1 as tf

tf.disable_v2_behavior()

# Define graph symbolically
x = tf.placeholder(tf.float32, shape=[1])  # Just a placeholder
y = x * 2  # Not executed, just recorded
z = y + 1  # Still no execution
# At this point, nothing has been computed

# Phase 2: Graph Execution (actual computation)
with tf.Session() as sess:
    result = sess.run(z, feed_dict={x: [1.0]})
    # Now computation happens: result = [3.0]
```

Listing 2: **Static Graph Two-Phase Execution**: Graph construction (symbolic definition) is separated from execution (actual computation), enabling ahead-of-time optimization.

^lst-tf-static-graph

In the definition phase, the program declares operations and variables and builds the symbolic DAG without allocating any tensor memory. Only in the execution phase do data load, concrete buffers materialize on the accelerator, and the captured graph run ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^fig-mlfm-static-graph|figure 5]]).

![[90 Assets/Volume I/07 Frameworks/Generated Figure e33d910813.svg]]

Figure 5: **Static Graph Execution Lifecycle**: Separating symbolic graph definition (left) from concrete execution (right) provides global visibility over the computation, allowing compilers to apply ahead-of-time optimizations (such as kernel fusion, buffer reuse, and layout transforms) before any tensors are materialized.

^fig-mlfm-static-graph

The key difference from eager execution is that during construction, `x`, `y`, and `z` are not tensors containing values but rather symbolic nodes in a graph. Operators such as `*` and `+` append transformation nodes to the graph definition without issuing arithmetic. Calling `print(y)` makes this distinction visible: it prints symbolic tensor metadata rather than numerical values. Only when the host invokes `sess.run()` does the runtime analyze, optimize, and execute the captured graph on device buffers.

Because the framework has the complete graph before execution, it can perform ahead-of-time optimization unavailable across uncaptured eager calls. The kernel fusion opportunity introduced in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8|section 7.3.2]] becomes actionable here. Because the framework sees `y = x * 2` and `z = y + 1` together in the graph, it can fuse them into `z = x * 2 + 1`, eliminating the intermediate `y` and halving idealized memory traffic. When tensor shapes and lifetimes are known, the compiler can plan memory before execution and reuse buffers whose lifetimes do not overlap; dynamic dimensions may require bounds or runtime allocation. Tensor layouts can also be transformed globally (for example, NCHW to NHWC) to match hardware preferences, though physical layout conversions may still require copies. Dead-code elimination (DCE)[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn10|¹⁰]] removes operations whose results are unused, and constant folding precomputes operations on constant values when their inputs are known.

These optimizations map directly to iron law terms: kernel fusion can reduce ${D_{\text{vol}}}$ by avoiding intermediate memory writes, constant folding reduces repeated work, planned allocation can reduce runtime overhead, and dead code elimination removes work and associated data movement when unused computations are present. Compilers such as **XLA**[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn11|¹¹]] ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-GoogleXLA|Google 2025]]) extend this approach, compiling captured subgraphs into fused machine code specialized for target hardware.

Static graphs can therefore approach high utilization when shapes, operators, and layouts match efficient backend paths. The cost of this performance is reduced flexibility. Standard Python control flow (`if`, `for`) cannot depend on computed tensor values in static graphs. TensorFlow provides graph-level control flow primitives (`tf.cond` and `tf.while_loop`) that support data-dependent conditions, but these require special syntax that diverges from standard Python, making code harder to write and reason about. Debugging suffers as well, because stack traces point to graph construction code, not execution code, and error messages often reference symbolic node names rather than the actual operations that failed.

### Graph Capture and JIT Compilation

^sec-ml-frameworks-hybrid-approaches-jit-compilation-8954

Staying in eager mode leaves small-operation workloads bound by host dispatch and unfused HBM traffic, while rewriting a research model into a static graph gives up interactive Python debugging and standard control flow. **JIT compilation** bridges that gap by letting developers write and debug ordinary eager code while capturing regions of the program at runtime for graph-level optimization. The core trade-off in graph capture is *fidelity vs. generality*. Tracing, one of the two classic capture modes, is faithful to the one path an observed run takes; scripting, the other, generalizes across inputs by preserving control flow that applies to every input. Both approaches produce an intermediate representation (IR)[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn12|¹²]] that enables graph optimizations such as kernel fusion, constant folding, dead code elimination, and buffer reuse.

The eager-vs.-compiled trade-off has a direct iron law consequence: JIT compilation amortizes ${L_{\text{lat}}}$ (dispatch overhead) and fuses memory traffic across each captured region, so compilation pays only when captured regions are long enough and stable enough to amortize capture, lowering, code generation, and cache-management costs.

Graph-capture JIT systems follow a common architectural pattern across frameworks. The first execution observes tensor operations, records a graph region guarded by assumptions about shapes, dtypes, layouts, and control flow, lowers that region into an intermediate representation, applies fusion and layout optimizations, and caches executable code for later calls that satisfy the same guards. The compiled artifact remains valid only while those guards hold; a failed guard forces the runtime to recompile or fall back to eager execution.

PyTorch’s TorchScript, now deprecated in favor of capture and export paths such as `torch.export` ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-pytorchTorchScriptDocs|PyTorch Contributors 2026c]], [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-pytorchExportDocs|2026b]]), offered both capture modes. Tracing executed a function with example inputs and recorded the tensor operations observed on that path. Scripting instead compiled a restricted, type-annotated subset of Python source, preserving supported branches in the graph at the cost of rejecting unsupported Python objects, library calls, and metaprogramming. In either mode, TorchScript’s IR used static types in static single-assignment (SSA) form, where each variable is assigned exactly once, so fusion, constant folding, and dead code elimination could run without the Python interpreter.

The main limitation of tracing is that a trace records operations from an observed path rather than preserving arbitrary Python control flow. A data-dependent branch can therefore freeze into whichever side the example input took ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^lst-tracing-silent-failure|listing 3]]).

``` python
import torch

def conditional_forward(x):
    if x.sum() > 0:  # Data-dependent condition
        return x * 2
    else:
        return x * 3

traced = torch.jit.trace(conditional_forward, torch.tensor([1.0]))
# Tracing captures ONLY the x.sum() > 0 branch
# If input later has sum <= 0, traced version
# still executes x * 2 branch
```

Listing 3: **Tracing a Data-Dependent Branch**: Tracing records the path taken by the example input. PyTorch commonly emits a `TracerWarning` when a tensor value is converted to a Python condition because the resulting trace may not generalize.

^lst-tracing-silent-failure

In this example, converting the tensor condition to a Python Boolean commonly produces a `TracerWarning`; the resulting trace nonetheless runs without error and silently executes the captured branch for later inputs that require the other branch. Trace warnings should therefore be treated as correctness failures when data-dependent Python control flow is present. Guarded capture prevents this silent failure only for the assumptions it checks. An input that breaks a guard forces a recompile, a fallback to eager execution, or an error, whereas an unchecked assumption fails as silently as this trace.

A captured region still has to be lowered into the compiler’s intermediate representation, and lowering is far easier when the target vocabulary is small. The eager frameworks a compiler starts from are not small. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^fig-operator-surface|Figure 6]] counts the operators that each framework defines at successive releases. PyTorch’s native-function table grew from 1,064 schemas, overloads included, at version 1.0 in 2018 to 2,658 by version 2.9 in 2025 ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-pytorch2025nativefunctions|PyTorch Contributors 2025]]). TensorFlow’s operator registry grew from 594 at version 1.0 in 2017 to 1,563 by version 2.20 in 2025 ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-tensorflow2025opsregistry|TensorFlow Developers 2025]]). Every one of those entries is something a backend must either implement directly or, before compilation, rewrite into combinations of a much smaller set of primitive operations, a lowering pass called decomposition.

Compiler-facing representations work from far smaller sets, which grew by tens of operators while the eager surfaces grew by thousands. The Core ATen IR, the operator set that PyTorch’s compiler and export paths lower to, holds 192 operators ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-pytorch2025nativefunctions|PyTorch Contributors 2025]]). The XLA compiler that TensorFlow and JAX both target defines 123 high-level optimizer (HLO) operations ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-openxla2025hloopcodes|OpenXLA Project 2025]]). The Open Neural Network Exchange (ONNX) standard, which carries models between frameworks and runtimes, defines 203 ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-onnx2026operators|ONNX Project 2026]]). JAX starts on the compiler’s side of this divide. Its user-facing operations reduce to about 135 `lax` primitives ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-jax2025laxprimitives|JAX Developers 2025]]), a set the size of the compiler cores, so a JAX program reaches XLA with little decomposition left to do.

Decomposition closes this gap, a reduction of 13–14× in vocabulary (PyTorch’s full operator table against Core ATen, and TensorFlow’s registry against XLA’s HLO operations). A new accelerator backend that implements a small core set can run models written against the full eager surface, which is why operator coverage, not peak throughput, often decides whether a model runs on a new device at all.

Once a region is captured and lowered, compilation attacks the dispatch overhead of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-dispatch-tax|section 7.3.4]] directly, and fusion adds a second saving in memory traffic. Notebook [7.1](https://mlsysbook.ai/vol1/07_frameworks/07_frameworks.html#nbk-frameworks-physics-software-overhead) quantifies both for a two-operation activation block.

**Napkin Math 7.1: The physics of software overhead**

**Iron law connection**: For small operations, the latency term $({L_{\text{lat}}})$ in the iron law is dominated by software overhead: dispatching instructions from Python to the GPU. Each operation pays a Python dispatch cost of ~10 μs plus a kernel launch cost of ~5 μs, which together set the per-operation overhead applied in the two scenarios below. Python dispatch covers the framework call; driver launch covers submission to the device.

**Scenario one: Eager mode (the tiny-op trap)** Consider a simple activation block, `y = relu(x + bias)`, in which the input and output each contain ${N}$ elements of ${s_{\text{elem}}}$ bytes each. Assume a scalar or broadcast bias remains in fast memory, so the traffic model counts the full input, intermediate, and output tensors.

- **Operations**: Two (Add, ReLU).
- Execution:
  1.  Dispatch and launch `Add` kernel: 15 μs overhead.
  2.  Read/Write Memory: $2{N}{s_{\text{elem}}}$ bytes.
  3.  Dispatch and launch `ReLU` kernel: 15 μs overhead.
  4.  Read/Write Memory: $2{N}{s_{\text{elem}}}$ bytes.
- **Total overhead**: 30 μs.
- **Total memory traffic**: $4{N}{s_{\text{elem}}}$ bytes.

**Scenario two: Compiled mode (fusion)** The compiler fuses this into one kernel: `FusedAddRelu`. This scenario retains one ordinary Python entry and one driver launch, applying the same combined cost as eager mode to isolate the effect of reducing two calls to one.

- Execution:
  1.  Dispatch and launch `Fused` kernel: 15 μs overhead.
  2.  Read/Write Memory: $2{N}{s_{\text{elem}}}$ bytes (the intermediate result stays on chip).
- **Total overhead**: 15 μs (2× less launch overhead).
- **Total memory traffic**: $2{N}{s_{\text{elem}}}$ bytes (2× bandwidth efficiency).

**Systems insight**: Fusion saves on both terms at once: half the launches and, by the fused-chain traffic rule of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8|section 7.3.2]] with ${n_{\text{ops}}} = 2$, half the idealized traffic.

Scaling this arithmetic to a sequence of 5 small operations exposes the idle gaps on the accelerator timeline ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^fig-python-tax|figure 7]]). In eager execution, each 1 μs kernel waits on 10 μs of Python dispatch, leaving the accelerator idle for about 91 percent of the sequence, and that count includes only the Python share; each kernel’s launch cost would widen every gap further. Compiling the sequence removes both costs that eager execution pays per operation, the dispatch gaps and the intermediate memory traffic. The framework submits the work in a single launch of 5 μs, which eliminates the intermediate host dispatch gaps. Operator fusion keeps intermediate activations in registers or cache, so the entire sequence completes in 4 μs instead of the uncompiled 5 μs. A compiled region entered from Python, as in the notebook above, still pays one Python dispatch per call, once for the whole sequence rather than once per operation, a single entry cost the figure omits.

Eager execution incurs per-operation host overhead for each kernel, whereas compilation and fusion collapse the sequence into a single launch (drawn in the overhead color as one direct device submission), eliminating intermediate dispatch gaps and intermediate global memory round-trips.

Graph-capture compilers such as PyTorch 2.0’s `torch.compile`[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn13|¹³]] ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-ansel2024|Ansel et al. 2024]]) realize the compiled timeline of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^fig-python-tax|figure 7]] over captured regions without requiring engineers to write custom CUDA kernels.[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn14|¹⁴]] However, compilation cannot span arbitrary Python code: graph breaks mark the boundary where compilation ceases to apply (a configuration requiring full-graph capture can instead report an error). Data-dependent Python control flow, unsupported library calls, I/O, custom Python objects, and highly variable shapes can shorten compiled regions. With eager fallback enabled, each break separates compiled subgraphs with standard Python execution, reintroducing interpreter dispatch, resetting ${L_{\text{lat}}}$ amortization, and preventing fusion across the boundary. Tensor handles can pass between these regions while their storage remains on the device; host reads of device values can additionally require synchronization. This is why graph-break analysis belongs in performance engineering: the relevant metric is not whether compilation is enabled, but how much of the hot path remains inside long, stable compiled regions.

The backends that compile those captured regions occupy different points on the flexibility-performance spectrum. A JIT compiler compiles captured regions at runtime and pays warmup latency on the first pass. An **ahead-of-time (AOT)** compiler instead compiles captured computation before deployment, shifting compilation out of the hot path and enabling a standalone runtime when the export target supports one. A general JIT backend, such as TorchInductor behind `torch.compile` or XLA, optimizes ordinary training and serving workloads with moderate compilation cost. A specialized ahead-of-time inference compiler, such as NVIDIA’s TensorRT, can apply deeper fusion, precision lowering, and autotuning when the deployment target is fixed. An ahead-of-time mobile or embedded runtime, such as ExecuTorch or TensorFlow Lite, removes even more flexibility to gain footprint and predictability. The same rule governs all of them: the narrower the target and the more stable the graph, the more optimization the compiler can safely perform.

Compilation shortens the list of kernels; a second mechanism removes the per-launch cost of whatever list remains. CUDA Graphs record a fixed sequence of kernel launches, with their arguments and memory addresses, once, and then replay the whole sequence with a single submission from the host ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-nvidia2026cudaGraphs|NVIDIA Corporation 2026]]). The price is rigidity, because replay requires static shapes and fixed buffer addresses. For the GPT-2 XL decoding step that opened the chapter, replay turns 576 separate launches into one submission, so the host’s launch rate no longer sets the step time. What remains is the weight read of about 0.9 ms plus the device-side cost of running those kernels back to back, which fusion attacks.

The resulting workflow is a systems decision. Rapid prototyping favors eager execution because architecture changes and guard failures make recompilation cost visible. Long training runs and high-volume inference amortize compilation cost over many executions, provided the model has stable shapes and limited graph breaks. Debugging usually starts in eager mode because errors map directly to source code and standard debuggers such as `pdb` work mid-execution; compilation is reintroduced after the model behavior is correct and the performance bottleneck is measurable.

These trade-offs are not binary choices. Modern frameworks offer a spectrum of execution options, which raises the quantitative question of where on this spectrum a given project should operate.

### Compilation and Dispatch Costs

^sec-ml-frameworks-compilation-continuum-principle-c106

Two quantitative principles make the choice of execution model measurable. The compilation continuum principle asks when compilation gains justify development cost by comparing production executions with development iterations. The dispatch overhead law writes the dispatch overhead ratio in terms of operation count and per-operation cost, giving a threshold that says when a whole workload is overhead-bound.

#### The Compilation Continuum Principle

^sec-ml-frameworks-compilation-continuum-principle-7122

[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-execution-continuum|Equation 1]] orders the execution path from maximum flexibility to maximum optimization in four positions, and each labeled arrow names the mechanism that carries a project one step rightward toward hardware:

$$
\text{Eager} \xrightarrow{\text{capture}} \text{Graph JIT} \xrightarrow{\text{export}} \text{AOT Runtime} \xrightarrow{\text{specialize}} \text{Hardware} \tag{1}
$$

 The first three positions are execution models. The last, Hardware, stands for code specialized to a single accelerator and fixed shapes, such as an engine that a vendor inference compiler builds for one chip, where the model can no longer change without a rebuild. Each step rightward sacrifices flexibility for performance. The practical question is *where* a given project should be placed on this continuum. The optimal compilation strategy depends on production executions, development recompilations, and their respective time costs, combined in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-compilation-benefit|equation 2]]:

^eq-execution-continuum

$$
\text{Compilation Benefit} = \frac{{N_{\text{prod}}}\cdot ({T_{\text{eager}}}- {T_{\text{compiled}}})}{{T_{\text{compile}}}+ {N_{\text{dev}}}\cdot {T_{\text{compile}}}} \tag{2}
$$

^eq-compilation-benefit

where:

- ${N_{\text{prod}}}$ = number of production executions (dimensionless count: inference requests, training steps)
- ${N_{\text{dev}}}$ = number of development iterations requiring recompilation (dimensionless count)
- ${T_{\text{eager}}}$ = time per execution in eager mode (seconds)
- ${T_{\text{compiled}}}$ = time per execution in compiled mode (seconds)
- ${T_{\text{compile}}}$ = time per compilation or recompilation (seconds; assumed constant)

This model assumes that the compiled artifact remains valid between development changes and that the initial compilation and each recompilation have the same cost; under these assumptions, the decision rule is to compile when $\text{Compilation Benefit} > 1$. The ratio is dimensionless.

How often compiled code is reused decides the compilation question, and three common cases land in different places. In research prototyping (${N_{\text{dev}}}\gg {N_{\text{prod}}}$), teams should stay eager. If the architecture changes every few minutes, compilation overhead can dominate. Under the scenario’s 30 s compilation assumption, 10 compilations per hour consume 5 min.

For repeated execution (${N_{\text{prod}}}\gg {N_{\text{dev}}}$), compilation can pay off because its one-time cost is amortized across many calls. In the hypothetical ResNet-50 inference scenario in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^tbl-training-benchmark|table 4]], torch.compile provides 48.3 percent higher throughput (2,150 img/s vs. 1,450 img/s). Using the scenario’s 30 s compile cost, this pays off after the breakeven point in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-compile-breakeven|equation 3]]:

$$
{N_{\text{breakeven}}}= \frac{{T_{\text{compile}}}}{{T_{\text{eager}}}- {T_{\text{compiled}}}} \tag{3}
$$

^eq-compile-breakeven

This breakeven count is the production-only case of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-compilation-benefit|equation 2]]. With a single compilation and no development recompilations, the compilation benefit reaches 1 exactly when the number of production executions equals the breakeven count, so every execution beyond it is a net gain. Evaluating [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-compile-breakeven|equation 3]] with the hypothetical ResNet-50 values gives approximately 134,000 images. The same amortization principle applies to long training runs, using training throughput and compilation costs measured for that workload.

Long-lived production inference (${N_{\text{dev}}}\approx 0$, ${N_{\text{prod}}}\rightarrow \infty$) extends this reuse further, providing more opportunity to amortize compilation. Aggressive autotuning can be worthwhile even when setup takes much longer, provided the model converts correctly, meets numerical requirements, and improves measured performance over the deployment lifetime.

The cases form a continuum of increasing reuse ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^fig-compilation-continuum|figure 8]]). Each strategy’s total time starts at its one-time compilation cost and grows at its per-execution cost. Eager therefore wins at low execution counts, JIT wins once its compilation is amortized, and AOT wins only at the largest counts, where its higher upfront cost is fully repaid. The figure’s crossovers (near $2 \times 10^{6}$ and $6.7 \times 10^{6}$ executions) come from an illustrative cost model in arbitrary units, not from the ResNet-50 scenario, whose eager-to-compiled breakeven sits near 134,000 images. What carries over is the order of the regions, not their positions.

#### The Dispatch Overhead Law

^sec-ml-frameworks-dispatch-overhead-law-9e0a

Whereas the compilation continuum asks whether enough executions will run to repay compilation setup, the **dispatch overhead law** asks whether a single execution is stalled on the host in the first place. Let ${N_{\text{ops}}}$ be the number of operations (count), ${t_{\text{dispatch}}}$ the per-operation dispatch overhead (seconds), and ${T_{\text{compute}}}$ and ${T_{\text{memory}}}$ the total compute and memory times (seconds). Under the additive, no-overlap approximation ${T_{\text{hw}}}\approx {T_{\text{compute}}} + {T_{\text{memory}}}$ (when execution overlaps those costs, measured hardware time should replace their sum), [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-dispatch-overhead|equation 4]] identifies when framework overhead dominates compute and memory:

$$
\text{Overhead Ratio} = \frac{{N_{\text{ops}}}\cdot {t_{\text{dispatch}}}}{{T_{\text{compute}}} + {T_{\text{memory}}}} \tag{4}
$$

^eq-dispatch-overhead

When Overhead Ratio $> 1$, the model is overhead-bound. This is the dispatch overhead ratio ${T_{\text{sw}}}/{T_{\text{hw}}}$ of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-dispatch-tax|section 7.3.4]], written with ${T_{\text{sw}}}= {N_{\text{ops}}}\cdot {t_{\text{dispatch}}}$ so that operation count and per-operation cost appear explicitly. The fraction of step time spent in dispatch is $\text{Overhead Ratio}/(1+\text{Overhead Ratio})$, so a ratio above 1 means dispatch takes more than half of the step. Compilation can provide its largest gains for overhead-bound workloads because fusion reduces the number of dispatches. The same equation names every lever on the ratio. Fusion and compilation shrink the numerator by cutting the operation count ${N_{\text{ops}}}$, and graph replay shrinks it by lowering the host cost ${t_{\text{dispatch}}}$ that each launch pays. A larger batch works on the denominator instead, giving each kernel more device work while its dispatch cost stays fixed. The training-step trace in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.08 Anatomy of a Training Step#^sec-ml-frameworks-putting-together-anatomy-training-step-c7f1|section 7.7]] works these levers through end to end, previewed by the numbers that follow.

Applying [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-dispatch-overhead|equation 4]] means comparing the software overhead ${T_{\text{sw}}}= {N_{\text{ops}}}\cdot {t_{\text{dispatch}}}$ with the hardware execution time ${T_{\text{hw}}}$ (both in seconds). The regime depends on the size of individual operations rather than on the model’s parameter count. Notebook [7.2](https://mlsysbook.ai/vol1/07_frameworks/07_frameworks.html#nbk-frameworks-dispatch-tax) contrasts a small multilayer perceptron with a large transformer layer to quantify when host overhead or device arithmetic bounds the system.

**Napkin Math 7.2: Dispatch overhead at two scales**

**Problem**: Determine the threshold where host-side Python interpreter dispatch overhead bounds end-to-end execution time relative to accelerator hardware execution.

**Scenario one: Small multilayer perceptron (overhead bound)**

- **Compute**: 6 ops across small matrix/element-wise operations.
- **Hardware time**: ${T_{\text{hw}}}\approx$ 2.6 μs (mostly memory latency).
- **Software overhead**: ${T_{\text{sw}}}\approx$ 6 ops $\times$ 15 μs/op = 90 μs.
- **Ratio**: 90 μs/2.6 μs ≈ 34.6.
- **Small-model outcome**: The system spends 97 percent of time in host-side dispatch and kernel-launch overhead. Eliminating all modeled dispatch overhead would give an upper-bound speedup of 35.6×.

**Scenario two: GPT-3 layer (device bound)**

- **Compute**: Huge matrix multiplications.
- **Assumptions**: Both times below are illustrative round values for one GPT-3-scale layer over a large batch, not derived from a specific accelerator. The conclusion does not hinge on them, because at the chapter’s 15 μs/op the ratio would reach 1 only if the layer issued thousands of separately dispatched kernels.
- **Hardware time**: ${T_{\text{hw}}}\approx$ 100 ms = 100000 μs.
- **Software overhead**: ${T_{\text{sw}}} \approx 180 \, {\text{µ}}\text{s}$, one transformer block’s 12 eager kernels at 15 μs/op. The kernel count is the GPT-2 XL count from the chapter opening, a fair proxy because GPT-3 builds each block from the same attention and feed-forward operations, only wider.
- **Ratio**: 180 μs/100000 μs ≈ 0.0018.
- **Large-model outcome**: Modeled Python overhead is negligible. Compilation may still improve fusion, layout, or backend specialization; dispatch elimination contributes little.

**Systems insight**: Dispatch overhead is regime-dependent. Compilation can reduce host-side overhead for small-operation workloads by fusing operations into fewer launches, while large models benefit mainly from fused kernels and memory movement reductions.

### Static Runtimes for Microcontrollers

^sec-ml-frameworks-tinyml-micro-runtimes-2a1b

The compilation continuum ends at the far edge, where the limiting cost on a microcontroller is not each dispatch but the runtime itself, whose memory and latency footprint exceeds the device. While cloud frameworks such as PyTorch and TensorFlow 2.x prioritize flexibility through eager execution, TinyML[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn15|¹⁵]] systems operating on microcontrollers (MCUs) with kilobytes of memory cannot afford the overhead of a Python interpreter or a fully dynamic runtime. A micro-runtime may still step through the model one operator at a time, yet it sits at the specialized end of the continuum because the operator list, the kernels linked into the binary, and the memory plan are all fixed before the device ships, leaving almost nothing to decide at run time.

**Lighthouse 7.2: Lighthouse example: KWS on TinyML**

**Scenario**: Deploying the keyword spotting (KWS) lighthouse, a DS-CNN and the book’s power-bound workload, to an Nordic nRF52840 (Cortex-M4F) microcontroller with 256 KB RAM and 1 MB Flash. This is a smaller target than the ESP32-S3 of the smart-doorbell scenario (**[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^sec-ml-systems-workload-archetypes-fd10|Workload archetypes]]**), chosen to show the runtime at its tightest.

**Constraint**: A full PyTorch and Python runtime exceeds the device’s memory budget by orders of magnitude.

**Framework solution**: Micro-frameworks such as **TensorFlow Lite Micro (TFLM)** ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-david2021tensorflow|David et al. 2021]]) solve this through a tiny interpreter-based runtime with a fixed memory discipline:

1.  **Fixed memory arena**: The application supplies a contiguous tensor arena, and the framework plans and reuses buffers from that arena rather than relying on dynamic allocation during inference.
2.  **Kernel selection**: Only the specific kernels used by the model (for example, Conv2D, DepthwiseConv) need to be linked or registered with the runtime.
3.  **Compact interpreter execution**: The MCU runs a small C/C++ interpreter over a flat model representation, with the model and arena bound at initialization rather than assembled dynamically at runtime.

**Limiting constraint**: The power budget makes keyword spotting a power-bound workload, but the first test the framework must pass is memory capacity, not bandwidth or dispatch overhead, which is why [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^tbl-framework-archetype-strategy|table 5]] treats it as a feasibility threshold. The framework’s primary job is to ensure the model’s intermediate activations (the “working set”) fit within the MCU’s tiny SRAM.

These micro-runtimes sacrifice dynamic flexibility to reduce footprint and make memory predictable. With compact models, low-power hardware, and duty cycling, that discipline enables milliwatt-scale inference with mostly on-chip data movement. Across the full spectrum from dynamic eager execution to static graph compilation and specialized micro-runtimes, developers must therefore match the execution strategy to the limiting constraint of the target.
