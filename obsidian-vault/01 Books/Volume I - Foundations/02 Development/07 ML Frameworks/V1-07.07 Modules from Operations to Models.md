# V1-07.07 Modules from Operations to Models

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-nnmodule-abstraction-2622

Coordinating those same 25.6M ResNet-50 parameters across fifty layers requires registering weights with optimizers, moving buffers across devices, toggling training and evaluation modes, and serializing checkpoints, the saved copies of training state from which a run can resume. Managing that state tensor by tensor would drown model development in error-prone bookkeeping. Frameworks resolve this through hierarchical composition, packaging layers into modules that compose into full models.

Every major framework implements this through a module abstraction that packages parameter tensors, forward computation, and lifecycle hooks into a unified interface. PyTorch’s `nn.Module`[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn23|²³]] provides an instructive case study because its design patterns recur across frameworks. Keras uses similar layer abstractions ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-chollet2018keras|Chollet 2018]]), JAX’s Flax employs analogous module structures, and TensorFlow’s functional API shares conceptual parallels. Three enduring design principles recur regardless of syntax or programming paradigm: automatic parameter discovery, mode-dependent behavior, and hierarchical composition with serialization.

### Automatic Parameter Discovery

^sec-ml-frameworks-nn-module-parameter-discovery-4a91

Passing each of ResNet-50’s weight and bias tensors to an optimizer by hand would break the moment a layer is added or renamed. Frameworks eliminate that manual wiring through **automatic parameter discovery**: the system walks the module tree, collecting every parameter tensor so the optimizer can update them in a single call.

This is a tree traversal problem at its core. PyTorch’s `Module.__setattr__` registers an assigned `nn.Parameter` or child `nn.Module` in the module’s internal mappings. A call to `.parameters()` recursively traverses registered submodules and yields registered parameters. Other frameworks expose analogous parameter trees or collections, though their mechanisms differ.

Automatic parameter discovery gives the optimizer a complete parameter set or parameter groups, enabling grouped or fused multi-tensor update kernels when the framework and backend support them. The immediate win is correctness and composability: newly attached submodules participate in device moves, serialization, and optimizer construction without a separate manual registry. In [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.07 Modules from Operations to Models#^lst-parameter-registration-94fc82d2|listing 16]], attribute assignment triggers registration, and `.parameters()` returns all discovered tensors.

Discovery also separates *parameters* from *buffers*. Registered parameters appear in `.parameters()` whether trainable or frozen; `requires_grad` separately controls whether autograd accumulates a gradient for them. Registered buffers move with the module and can appear in its state dictionary but are excluded from `.parameters()` and ordinary optimizer discovery. Batch-normalization running statistics are a common buffer use case. A device move carries both kinds of state, because calling `nn.Module.to()` moves every registered parameter and buffer in place and returns the module itself, whereas a tensor’s `.to()` returns a converted copy.

``` python
import torch
import torch.nn as nn

class CustomLayer(nn.Module):
    def __init__(self, input_size, output_size):
        super().__init__()
        self.weight = nn.Parameter(
            torch.randn(output_size, input_size)
        )
        self.bias = nn.Parameter(torch.randn(output_size))
        self.register_buffer("running_mean", torch.zeros(output_size))

    def forward(self, x):
        return torch.matmul(x, self.weight.t()) + self.bias

layer = CustomLayer(10, 20)
# Framework discovers both parameters automatically:
for name, param in layer.named_parameters():
    print(f"{name}: shape {param.shape}")
```

Listing 16: **Parameter Registration**: Automatic parameter tracking through attribute assignment enables optimizer access to all trainable weights without manual enumeration.

^lst-parameter-registration-94fc82d2

The other major frameworks draw the same line between trainable parameters and nontrainable state through different accessors ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.07 Modules from Operations to Models#^tbl-frameworks-parameter-discovery-apis|table 8]]). Regardless of syntax, each API separates tensors that the optimizer should update from persistent buffers that merely ride along in checkpoints and device transfers.

| **Framework** | **Parameter Access**                                         | **Nontrainable State**                                     |
|:--------------|:-------------------------------------------------------------|:-----------------------------------------------------------|
| PyTorch       | `model.parameters()`                                         | `register_buffer()`                                        |
| **Keras**     | `layer.trainable_weights`                                    | `layer.non_trainable_weights`                              |
| **JAX/Flax**  | `variables["params"]` after `variables = model.init(key, x)` | Separate variable collections (for example, `batch_stats`) |
| TensorFlow    | `module.trainable_variables`                                 | `module.non_trainable_variables`                           |

Table 8: **Parameter Discovery APIs Across Frameworks**: Each framework exposes a different surface for distinguishing trainable parameters from nontrainable buffers, but all four solve the same underlying problem of letting optimizers find weights to update while preserving state (running statistics, frozen tensors) across forward passes. The shared pattern is structured access to parameters and persistent state. Accessor semantics differ: PyTorch also yields frozen registered parameters, so trainability remains a separate property.

### Mode-Dependent Behavior

^sec-ml-frameworks-nn-module-mode-dependent-behavior

The same module tree that distinguishes trainable parameters from running-statistic buffers also governs layers whose forward computation changes between training and inference. During training, dropout layers randomly zero elements with probability ${p_{\text{drop}}}= \Pr(\text{drop})$ to regularize the network, while during inference those same layers must perform identity mapping to produce deterministic outputs. Batch normalization uses per-batch statistics during training but switches to accumulated running statistics during inference. If these behavioral changes are left to the programmer, forgetting a single mode switch produces silently incorrect predictions in production.

Frameworks solve this with a *state flag* that propagates through the module hierarchy. A single call to `.eval()` on the root module recursively sets `self.training = False` on every descendant, and each layer queries this flag to select its behavior. This is an instance of a broader systems principle: the same computation graph must produce different execution behavior depending on context. Compilers face the same challenge when the same source code must produce debug builds (with bounds checking and symbol tables) vs. release builds (with aggressive optimization). The flag-propagation pattern ensures correctness by centralizing the mode decision at the root rather than requiring per-layer coordination.

Evaluation mode and gradient recording are separate controls. Calling `.eval()` changes mode-dependent layer behavior but leaves autograd recording enabled. Inference that needs no gradients therefore also runs inside the `torch.no_grad()` region of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-principle-2-memorycompute-tradeoff-19f2|section 7.4.3.2]].

Parameter freezing is the per-parameter counterpart of that region. Setting `requires_grad=False` on a submodule’s parameters prevents autograd from accumulating gradients in those parameters and removes their gradient storage, although gradients may still need to pass through the layer’s operations to reach trainable inputs or earlier parameters. Because both mode propagation and subtree freezing operate on nested modules, they rely on how the framework composes layers into a hierarchy and serializes that hierarchy’s state.

### Hierarchical Composition and Serialization

^sec-ml-frameworks-nn-module-hierarchical-composition-6c13

Complex models compose from reusable submodules, creating a tree structure. A ResNet is not implemented as a monolithic block of operations but as a hierarchy: the root module contains a sequence of residual blocks, each block contains convolution layers and normalization layers, and each layer contains parameter tensors. This hierarchical composition must support two operations, made concrete in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.07 Modules from Operations to Models#^lst-nested-modules-97f7dfe7|listing 17]]: recursive parameter collection for training and **state serialization** for checkpointing and deployment.

``` python
import torch
import torch.nn as nn

class ResidualBlock(nn.Module):
    def __init__(self, channels):
        super().__init__()
        self.conv1 = nn.Conv2d(channels, channels, 3, padding=1)
        self.bn1 = nn.BatchNorm2d(channels)
        self.conv2 = nn.Conv2d(channels, channels, 3, padding=1)
        self.bn2 = nn.BatchNorm2d(channels)

    def forward(self, x):
        residual = x
        x = torch.relu(self.bn1(self.conv1(x)))
        x = self.bn2(self.conv2(x))
        return torch.relu(x + residual)

class ResNet(nn.Module):
    def __init__(self, num_blocks, channels=64):
        super().__init__()
        self.conv_in = nn.Conv2d(3, channels, 7, padding=3)
        self.blocks = nn.ModuleList(
            [ResidualBlock(channels) for _ in range(num_blocks)]
        )
        self.fc = nn.Linear(channels, 10)

    def forward(self, x):
        x = self.conv_in(x)
        for block in self.blocks:
            x = block(x)
        x = x.mean(dim=[2, 3])  # Global average pooling
        return self.fc(x)

model = ResNet(num_blocks=4)
total = sum(p.numel() for p in model.parameters())
print(f"Total parameters: {total}")
# state_dict() flattens the tree: 'blocks.0.conv1.weight', etc.
print(list(model.state_dict().keys())[:4])
```

Listing 17: **Nested Module Composition**: Hierarchical module composition enables recursive parameter collection and a flat state mapping across the module tree.

^lst-nested-modules-97f7dfe7

Hierarchical composition also gives the framework natural units for placement. Each submodule’s parameters can be loaded independently, so when a model is too large for a single GPU, the framework can assign different subtrees of the module hierarchy to different devices, with the tree structure providing the partition boundaries.

The `state_dict()` method produces an ordered mapping whose dotted keys (for example, `blocks.0.conv1.weight`) encode locations in the module hierarchy. A checkpoint for 7 billion FP16 parameters contains approximately 14 GB of weight payload before metadata or additional state, but the file format and storage path determine how those bytes are serialized. Resuming training needs more than the model’s state: optimizers expose their moment buffers and step counts through their own `state_dict()`, and a training checkpoint saves both so that the run continues with the same optimizer state. `load_state_dict()` copies matching parameter and buffer values into an already-constructed module and reports missing or unexpected keys according to its strictness setting; it does not reconstruct the module hierarchy. Cross-framework exchange requires a compatible graph and operator representation in addition to weights.

The hierarchical structure also enables module-level traversal for systematic operations. Methods such as `.named_modules()` iterate the entire tree, supporting bulk transformations such as replacing all BatchNorm layers with GroupNorm or applying Xavier initialization to every Linear layer. These traversal operations depend on the same tree structure that enables parameter discovery, so a single design decision pays off in several unrelated uses.

None of these three principles is specific to PyTorch. Keras layers, Flax modules, and functional approaches address the same problems of parameter management, state tracking, and composition, and differ in how they prioritize among competing solutions rather than in which problems they solve. Two practical patterns show how the principles become system controls: selective parameter freezing reduces unnecessary gradient work for transfer learning ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.07 Modules from Operations to Models#^lst-parameter-freezing-65c4b009|listing 18]]), and module hooks provide noninvasive inspection ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.07 Modules from Operations to Models#^lst-module-hooks-6b6c6421|listing 19]]).

``` python
import torch
import torch.nn as nn
from torchvision.models import ResNet18_Weights, resnet18

# Freeze all parameters in a pretrained
# model
pretrained_model = resnet18(weights=ResNet18_Weights.DEFAULT)

for param in pretrained_model.parameters():
    param.requires_grad = False

# Replace final layer with trainable parameters
pretrained_model.fc = nn.Linear(512, 10)  # New layer is trainable

# Only fc.parameters() will receive
# gradients during training
optimizer = torch.optim.Adam(
    filter(lambda p: p.requires_grad, pretrained_model.parameters()),
    lr=0.001,
)
```

Listing 18: **Parameter Freezing**: Setting `requires_grad=False` on a pretrained backbone keeps it fixed while a newly attached head trains, and the optimizer receives only the trainable parameters.

^lst-parameter-freezing-65c4b009

Module hooks are the inspection counterpart to parameter freezing. They intercept intermediate computations without modifying model code, enabling gradient flow diagnosis and activation monitoring ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.07 Modules from Operations to Models#^lst-module-hooks-6b6c6421|listing 19]]).

``` python
import torch
import torch.nn as nn

model = nn.Sequential(nn.Linear(10, 20), nn.ReLU(), nn.Linear(20, 5))

# Forward hook to inspect activations
def forward_hook(module, input, output):
    print(
        f"Layer: {module.__class__.__name__}, "
        f"Output shape: {output.shape}, "
        f"mean={output.mean():.3f}, "
        f"std={output.std():.3f}"
    )

# Backward hook to inspect gradients
def backward_hook(module, grad_input, grad_output):
    print(f"Gradient norm: {grad_output[0].norm():.3f}")

# Register hooks on specific layer
handle_fwd = model[0].register_forward_hook(forward_hook)
handle_bwd = model[0].register_full_backward_hook(backward_hook)

# Execute forward and backward pass
x = torch.randn(32, 10)
y = model(x)
loss = y.sum()
loss.backward()

# Remove hooks when done
handle_fwd.remove()
handle_bwd.remove()
```

Listing 19: **Module Hooks**: Forward hooks capture activations and backward hooks capture gradients during training without modifying the model’s code.

^lst-module-hooks-6b6c6421

Parameter discovery, freezing, and hooks are how the module abstraction turns thousands of tensors, each with its own shape, dtype, device, and lifetime, into one object that an optimizer can update, a serializer can save, and a profiler can inspect. With execution, differentiation, and abstraction each examined on its own, the remaining step is to watch them operate together: a single training step exercises every mechanism of this chapter at once.
