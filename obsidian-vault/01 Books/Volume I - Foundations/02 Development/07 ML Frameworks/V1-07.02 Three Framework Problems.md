# V1-07.02 Three Framework Problems

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-three-problems-every-framework-must-solve-317d

A few lines of Python can express one decoding step of a language model: embed the newest token, pass it through every transformer block, and project the result onto the vocabulary. The accelerator never sees those lines. It sees a stream of kernels,[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn1|¹]] the compiled routines it executes one launch at a time, together with memory allocations and copies, and the machine learning framework is the software that turns the first into the second. **[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures#^sec-network-architectures|Network Architectures]]** fixed *what* work each architecture performs. It left open *when* each operation runs, *how* its gradients are computed, and *which* kernel on which device executes it.

GPT-2 XL, the book’s bandwidth-bound lighthouse (one of the recurring reference workloads of **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.04 Analyzing Workloads#^sec-ml-systems-workload-archetypes-fd10|Workload archetypes]]**), shows what those open questions cost. One batch-one decoding step reads 3 GB of FP16 weights, which takes about 0.9 ms at the 3.35 TB/s memory bandwidth of an H100, the book’s reference accelerator. Executed one operation at a time, the same step issues about 12 kernels in each of its 48 transformer blocks, 576 launches in all. At 5 μs of driver overhead per launch, launching alone takes 2.9 ms, about 3× the weight read. An eager Python framework adds 10 μs of dispatch to every operation, which raises the host’s time to issue the step to 8.6 ms, about 10× the time the accelerator needs to read its weights. The accelerator spends most of the step waiting for its next instruction. Whether the step costs one millisecond or ten depends on what the framework does with those few lines of Python: run each operation as it is called, or capture the sequence, fuse it into fewer kernels, and launch it as a unit.

Every ML framework, regardless of API or design philosophy, must solve three core problems. The first is the *execution problem*: deciding when and how computation runs. A framework can execute operations immediately as written (eager execution[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn2|²]]) or first construct a computational graph[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn3|³]] (a record of operations and their data dependencies, developed in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-computational-graph-00f7|section 7.3.1]]) to optimize before launching device kernels (graph execution). The decoding step above is an execution problem, and this choice sets the trade-off between interactive debugging and whole-program compiler optimization.

With an execution strategy in place, the framework must solve the *differentiation problem*: computing gradients automatically. Because gradient-based training requires derivatives of a scalar loss with respect to millions or billions of parameters, manual calculus is impossible at scale. Frameworks implement automatic differentiation by registering a derivative rule for every supported operator and chaining those rules backward from the loss. Each step of that chain multiplies the gradient arriving from later operations by one operation’s local derivatives, a step that [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-reverse-mode-d328|section 7.4.1.2]] names a vector-Jacobian product. Along the way the framework must manage numerical precision and the memory overhead of intermediate activations retained for backward passes.

↩︎ Backpropagation over saved activations, which reverse-mode automatic differentiation mechanizes here, is established in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-gradient-computation-backpropagation-dacf|Gradient computation and backpropagation]]**.

The third problem is *hardware abstraction*: targeting diverse hardware from a single interface. The same model definition should be expressible across CPUs, GPUs, Tensor Processing Units (TPUs), and mobile accelerators, even though each target presents distinct memory hierarchies, instruction sets, and interconnect bandwidths. For every operation the framework must choose which kernel runs on which device, with which memory layout and precision. Within the GPU domain, framework ecosystems increasingly expose custom-kernel languages such as Triton ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-tillet2019|Tillet et al. 2019]]), allowing developers to write high-performance, block-level kernels without hand-crafting low-level CUDA (NVIDIA’s GPU programming platform ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-nickolls2008|Nickolls et al. 2008]])) or device assembly.

These three problems are tightly coupled: the execution model dictates when differentiation data structures are recorded, while the hardware abstraction layer determines which graph transformations can be lowered to the target, that is, translated into a representation closer to the target’s hardware instructions. In the terms of the iron law of ML systems (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-iron-law|3]]), the model architecture fixes the forward operation count ${O}$, and the framework shapes the remaining terms. Execution strategy bears most directly on the fixed overhead ${L_{\text{lat}}}$, because it sets how many launches the host must issue. Differentiation bears on the bytes moved ${D_{\text{vol}}}$, because every activation saved for backward is written to memory during the forward pass and read back during the backward pass, and on ${O}$, since the backward pass adds work. Abstraction bears on the hardware efficiency ${\eta_{\text{hw}}}$, because the kernel, layout, and precision it selects decide how fully an operation uses the device’s arithmetic units. These are emphases rather than exclusive assignments, since fusion, for example, cuts both launches and traffic, and the chapter uses this one mapping throughout.

The framework plays the role for a model that a compiler plays for a C program. The correspondence is literal: modern frameworks include optimizing compilers, such as Accelerated Linear Algebra (XLA) ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-GoogleXLA|Google 2025]]) and TorchInductor ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-ansel2024|Ansel et al. 2024]]), that lower a captured graph to machine code for the target accelerator. That compiler role is also what separates a framework from a numerical library such as NumPy.

**Definition 7.1: Machine learning frameworks**

***Machine learning frameworks*** are software systems that translate high-level mathematical model definitions into hardware-optimized execution plans by managing the computational graph, automatic differentiation, kernel dispatch, and memory allocation across the hardware hierarchy.

1.  **Significance**: Frameworks shape every iron law term that the model itself does not fix: the bytes moved $({D_{\text{vol}}})$, the hardware efficiency achieved $({\eta_{\text{hw}}})$, and the fixed overhead paid $({L_{\text{lat}}})$. Compiler-backed kernel fusion, for example, can eliminate writes and subsequent reads of intermediate values between compatible operations. Fusing a matrix multiplication, bias add, and rectified linear unit (ReLU) changes how the same mathematics reaches hardware without changing the model.
2.  **Distinction**: Unlike a numerical library such as NumPy, which normally evaluates each operation as it is called, an ML framework can capture or defer execution to analyze a larger computational graph and apply cross-operation optimizations: kernel fusion, memory layout transformations, and parallel scheduling. Those optimizations require visibility beyond separately dispatched operations.
3.  **Common pitfall**: A frequent misconception is that frameworks are interchangeable API wrappers. Framework choice determines which compiler paths are available. PyTorch can recover graph-level optimization from eager code through `torch.compile()`, while TensorFlow and JAX commonly rely on XLA-backed compilation paths that lower operations to target hardware. Moving from eager execution to a compiler path can change throughput materially, but the gain depends on model structure, shapes, operator support, and hardware.

Within the iron law, a framework works on whichever term dominates (data movement ${D_{\text{vol}}}$, arithmetic computation, or launch latency ${L_{\text{lat}}}$), partitioning computation across memory hierarchies, trading numerical precision for throughput, and scheduling operations to shrink that term. The framework is where the governing physics developed throughout this book becomes executable code.

This chapter follows a model’s graph downward, one level at a time ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.02 Three Framework Problems#^tbl-frameworks-chapter-spine|table 1]]): the decoding step above carries the execution level, and a two-layer MNIST training step, traced at the end, gathers every level. After a brief look at how the layers of the stack came to exist, the execution section takes the graph to kernels and decides when each operation runs. The differentiation section builds the backward graph that training adds and accounts for the values it must keep. The abstraction section reaches the bottom of the descent, where tensors occupy device memory and kernels operate on them. Modules then assemble those pieces back into a model, and the anatomy of one training step traces a single step through every level. The chapter closes with the major frameworks and how to choose among them.

Automating this machinery (recording operation graphs, allocating gradient buffers, traversing dependencies in reverse, and dispatching hardware kernels) did not happen all at once. Execution, differentiation, and abstraction emerged sequentially as responses to scaling bottlenecks in earlier numerical tools, a four-decade progression from hand-tuned assembly routines to compiled graph runtimes.

**Self-Check: Question**

1.  A team reports that their model executes correctly on CPU but produces mismatched tensor shapes and silent numerical corruption when switched to a GPU backend because some operators silently default to a different memory layout (such as NCHW versus NHWC). Which of the three fundamental framework problems does this failure most directly expose?

    1.  The hardware abstraction problem, because one unified model interface must preserve consistent semantic behavior, memory layouts, and numerical behavior across diverse hardware backends
    2.  The execution problem, because the operators were evaluated eagerly instead of being captured into a static graph
    3.  The differentiation problem, because the backward pass failed to propagate gradients through non-contiguous strides
    4.  A data engineering pipeline defect unrelated to framework runtime responsibilities

2.  Explain how viewing an ML framework as a compiler that lowers a model graph to hardware, rather than merely a numerical library like NumPy, changes an engineer’s expectations regarding framework selection and optimization under the systems iron law.

3.  True or False: Two frameworks that expose nearly identical user-facing Python tensor APIs and target the same GPU hardware will necessarily provide equivalent graph-level operator fusion and ahead-of-time compilation capabilities.

4.  An engineering organization chose a specialized research framework for rapid prototyping, only to discover later that the framework lacks export paths to their production edge accelerators, requiring months of manual re-implementation. Applying the chapter’s infrastructure-commitment principle, what is the key systems insight?

    1.  Framework choice is easily reversible because weight arrays can be loaded into any runtime with zero engineering overhead
    2.  Framework selection functions as a durable infrastructure commitment whose reversal cost compounds across model checkpoints, serving runtimes, CI/CD pipelines, and hardware access
    3.  The primary failure was selecting an overly compact model architecture that failed to saturate edge accelerator memory
    4.  Hardware abstraction layers eliminate all differences between training frameworks and production inference engines
