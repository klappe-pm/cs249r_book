# V1-07.12 Summary

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-summary-07f0

Machine learning frameworks solve three core systems challenges that make deep learning tractable on modern hardware. The first is execution: deciding when and how operations run. Frameworks balance the trade-off between eager evaluation for interactive debugging and graph execution for whole-program compilation, while modern hybrid approaches such as `torch.compile` capture graphs dynamically without sacrificing the Python control loop. The second is differentiation: computing gradients automatically. Frameworks implement reverse-mode automatic differentiation that applies the chain rule across compositions of operations, constructing an autograd tape or backward graph of vector-Jacobian products while making the required forward values available through retention or recomputation. This primitive makes training large models feasible through a single `loss.backward()` call. The third is abstraction: targeting heterogeneous hardware from a unified interface. Frameworks provide multi-dimensional tensor abstractions, intermediate representations, and runtime dispatch systems that bridge high-level model definitions to optimized device kernels across CPUs, GPUs, TPUs, and custom accelerators.

These challenges are linked through the iron law of ML systems (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**): execution strategy affects dispatch latency $({L_{\text{lat}}})$, differentiation adds arithmetic and memory traffic $({D_{\text{vol}}})$, and abstraction influences hardware utilization efficiency $({\eta_{\text{hw}}})$. These are diagnostic emphases, not exclusive assignments, since fusion changes both launches and traffic while differentiation changes both work and live storage. Workloads with little reuse are frequently memory-bandwidth bound (${D_{\text{vol}}}/{\text{BW}}$). Frameworks mitigate this memory wall through kernel fusion, which merges compatible element-wise operations to keep intermediates in registers or on-chip SRAM instead of round-tripping through global memory. The separate capacity limit yields to selective recomputation, which trades additional floating-point operations $({O})$ for lower peak activation memory.

The counting rules developed across the chapter fit on one page ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.12 Summary#^tbl-framework-cost-formulas|table 13]]). Together they let an engineer estimate, before profiling, whether a step is bound by dispatch, by memory traffic, or by arithmetic.

**Key Takeaways: The layer between math and hardware**

- **Every framework solves three problems**: Execution dictates runtime dispatch, differentiation computes gradients, and abstraction targets heterogeneous hardware. TensorFlow, PyTorch, and JAX give different answers on each axis, from graph capture to eager tapes to functional transformations, and those answers fix what a team can debug, compile, and deploy long after the API syntax has changed.
- **The memory wall drives optimization**: Accelerator compute capacity has outpaced memory bandwidth, making off-chip data movement a recurring bottleneck. Kernel fusion and lower-precision formats can reduce the memory traffic term (${D_{\text{vol}}}/{\text{BW}}$), while selective recomputation primarily reduces peak activation storage by adding work.
- **Compilation must amortize setup cost**: The compilation continuum principle in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-compilation-benefit|equation 2]] quantifies when runtime speedup offsets compilation overhead. While dynamic workloads favor eager execution, repeatedly executed graphs benefit from JIT or ahead-of-time compilation, where the dispatch overhead law ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-dispatch-overhead|equation 4]]) demonstrates that small operations gain disproportionately when host launch overhead (${L_{\text{lat}}}$) is reduced.
- **Gradients cost memory as well as arithmetic**: Reverse-mode differentiation keeps the forward values that backward rules read, so saved activations grow with batch size and depth and often dominate training memory; activation checkpointing trades recomputation for that storage.
- **Where a tensor lives sets what it costs**: A host-to-device copy runs at a small fraction of on-device bandwidth, so placement, pinned memory, and stream overlap decide whether transfers hide behind computation, while layout and data type decide which kernel runs.
- **Module abstractions automate state management**: Automatic parameter registration, mode flags that propagate from the root, hierarchical serialization, and hooks let one object be updated, saved, switched between training and evaluation, and inspected without per-tensor bookkeeping.
- **A step can be estimated before it is profiled**: The chapter’s cost formulas (dispatch overhead ratio, fused traffic, compilation breakeven, saved activations, transfer time) show that a small MLP training step is overhead-bound on a data-center accelerator before any profiler runs.
- **Deployment targets filter the development framework**: A framework is viable only if it can export every required operator to a runtime that fits the target device; among the viable paths, team expertise and migration cost decide.

A framework presents itself as an ergonomic programming interface, yet its true role is translating mathematical graphs into physical hardware operations. That translation determines the work, traffic, and overhead paid under the iron law of ML systems (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-iron-law|3]]). Eager execution prioritizes developer iteration at the cost of host dispatch latency (${L_{\text{lat}}}$), while graph compilation trades upfront optimization time to reduce avoidable global memory traffic (${D_{\text{vol}}}/{\text{BW}}$) through fused kernels. Automatic differentiation adds backward work and traffic (${D_{\text{vol}}}$), with checkpointing trading retained activation storage against recomputed arithmetic (${O}$). What appears to be an API convenience therefore decides, for as long as a project uses it, how much avoidable work and data movement the implementation performs within physical limits that no framework can remove.

**What’s Next: From one training step to a training run**

Frameworks translate architectures into executable kernels, and their computational graphs, autograd tapes, and dispatch pipelines are what let engineers see and control each step of training. This chapter traced a single training step through that machinery. A training run repeats that step many thousands or millions of times. Every budget decision the machinery exposes is still unmade, including which activations to checkpoint when memory runs short, how large a batch the hardware allows, and at what point a single device stops being enough. **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training#^sec-model-training|Model Training]]** makes those decisions. It opens with why training costs orders of magnitude more than inference, then budgets memory, time, and cost for real training runs and shows how far one machine can go before scaling out.
