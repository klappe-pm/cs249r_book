# V1-07.05 Differentiation Automatic Gradient Computation

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-differentiation-problem-8b8a

A framework that executes graphs efficiently but cannot compute gradients[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn16|¹⁶]] can run inference, yet it cannot learn. Training requires the derivative of a scalar loss ${\mathcal{L}}$ with respect to every parameter: doing this manually for even a three-layer network demands dozens of hand-derived partial derivatives, and for a billion-parameter transformer it is intractable. The **differentiation problem** is the task of mechanizing that derivative computation automatically. During the forward pass, the runtime records an execution tape and saves intermediate activation buffers for subsequent derivative evaluations. As backpropagation already showed, reverse-mode automatic differentiation (AD)[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn17|¹⁷]] matches this regime because a single reverse traversal from a scalar loss yields every parameter gradient ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-baydin2018|Baydin et al. 2018]]).

The systems engineering of differentiation extends the backpropagation algorithm. It addresses how frameworks represent computation graphs, manage memory for intermediate values, and orchestrate the backward pass efficiently across accelerators. The framework mechanizes the chain rule as large-scale systems bookkeeping: tracking operator dependencies, staging activation buffers, and dispatching backward kernels. The function in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-auto-diff-intro-b6f9f598|listing 4]] reduces the core idea to three elementary operations.

↪ The optimization algorithms that consume these gradients are developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-optimization-algorithms-c6a9|Optimizers and their memory]]**.

``` python
def f(x):
    a = x * x  # Square
    b = sin(x)  # Sine
    c = a * b  # Product
    return c
```

Listing 4: **Automatic Differentiation**: The function ${f}({x}) = {x}^2 \sin({x})$ breaks into a square, a sine, and a product, each with a known local derivative.

^lst-auto-diff-intro-b6f9f598

Frameworks decompose this function into elementary operations, each with a known local derivative, and then combine these local derivatives via the chain rule to compute gradients through supported compositions. The systems challenge is executing this transformation under physical hardware constraints: the framework must represent the computation graph, make necessary forward values available, and schedule backward kernels without exhausting accelerator HBM. Production runtimes address these challenges through structured graph recording, caching allocators, and reverse-mode traversal.

### Forward and Reverse Mode

^sec-ml-frameworks-forward-reverse-mode-differentiation-f70a

Computing the gradient of a scalar loss across millions of model weights one weight at a time would require millions of separate passes through the network, whereas sweeping backward from the single scalar loss recovers every weight gradient in one reverse pass. Automatic differentiation operates in these two traversal directions: forward mode, whose cost scales with the number of inputs, and reverse mode, whose cost scales with the number of outputs. Because deep learning objectives reduce a large parameter set to a single scalar loss, this asymmetry dictates both the memory footprint and the execution schedule of the underlying framework.

#### Forward Mode

^sec-ml-frameworks-forward-mode-c3ff

Forward mode automatic differentiation computes directional derivatives alongside the forward calculation itself. For each intermediate variable ${v}_i$, the runtime evaluates both the value ${v}_i$ and its directional derivative (tangent) ${\dot{v}}_i = \sum_j \frac{\partial {v}_i}{\partial {x}_j} {\dot{x}}_j$, where the seed ${\dot{x}}_j$ is the input direction, chosen by the caller, along which the derivative is taken. Because tangents flow forward alongside the values, forward mode requires no execution tape and never retains forward activations for a later backward pass.

To see the mechanism concretely, consider computing both the value and derivative of ${f}({x}) = {x}^2 \sin({x})$. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-forward-mode-ad-141f361d|Listing 5]] shows how forward mode evaluates local derivative rules alongside each elementary operation, applying the chain and product rules at every step:

``` python
def f(x):  # Computing both value and derivative
    # Step 1: x -> x²
    a = x * x  # Value: x²
    da = 2 * x  # Derivative: 2x

    # Step 2: x -> sin(x)
    b = sin(x)  # Value: sin(x)
    db = cos(x)  # Derivative: cos(x)

    # Step 3: Combine using product rule
    result = a * b  # Value: x² * sin(x)
    dresult = a * db + b * da  # Derivative: x²*cos(x) + sin(x)*2x

    return result, dresult
```

Listing 5: **Forward Mode AD**: Forward mode propagates derivatives forward through the computation graph, computing one directional derivative per seeded forward pass.

^lst-forward-mode-ad-141f361d

Forward mode mechanizes this paired tracking through dual numbers, values of the form ${v}+ {\dot{v}}{\epsilon}$ where ${\epsilon}^2 = 0$, so each operator updates the value and its tangent together without retaining a graph. Seeding ${\dot{x}}= 1.0$ carries the derivative through the trace ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-forward-mode-dual-a06e3960|listing 6]]).

``` python
x, dx = 2.0, 1.0  # seed: track the derivative with respect to x

a = x * x  # value:      4.0
da = 2 * x  # derivative: 4.0
b = sin(x)  # value:      0.9093
db = cos(x)  # derivative: -0.4161
c = a * b  # value:      3.637
dc = a * db + b * da  # derivative: 1.973
```

Listing 6: **Dual-Number Trace**: Evaluating the forward-mode function of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-forward-mode-ad-141f361d|listing 5]] at ${x} = 2.0$ keeps a value and its derivative on every line, so one pass yields both ${f}(2.0)\approx 3.637$ and ${f}'(2.0)\approx 1.973$.

^lst-forward-mode-dual-a06e3960

A single forward pass with a seeded tangent vector ${\dot{\mathbf{x}}}$ evaluates a Jacobian-vector product (JVP), ${\mathbf{J}}{\dot{\mathbf{x}}}$, where ${\mathbf{J}}\in \mathbb{R}^{{M}\times {P}}$ is the Jacobian, the matrix of slopes of every output with respect to every input. When an objective maps ${P}$ parameter inputs to a single scalar loss (${M}= 1$), recovering the full gradient $\nabla_{{\theta}}{\mathcal{L}} \in \mathbb{R}^{{P}}$ requires setting ${\dot{\mathbf{x}}}$ to each of the ${P}$ standard basis vectors in turn. Recovering gradients with forward mode therefore requires ${P}$ distinct forward evaluations (or propagating ${P}$-wide tangent bundles), scaling compute and memory traffic as $\mathcal{O}({P})$ with parameter count. For networks with millions or billions of parameters, this scaling makes forward-mode gradient calculation intractable, although forward mode remains efficient for functions with few inputs.

#### Reverse Mode

^sec-ml-frameworks-reverse-mode-d328

An intermediate layer that maps an input vector ${\mathbf{x}}\in \mathbb{R}^{N}$ to an output ${\mathbf{y}}\in \mathbb{R}^{M}$ of width ${N}= {M}= 100{,}000$ has a full Jacobian ${\mathbf{J}}\in \mathbb{R}^{{M}\times {N}}$ of $10^{10}$ elements, which would require 40 GB of memory in FP32 to store one layer’s derivatives. Neither mode of automatic differentiation materializes this matrix. Forward mode would need one pass per input direction, while reverse-mode automatic differentiation needs one pass per output, a single pass for a scalar loss, which matches the many-parameters-to-one-loss shape of neural network training. Instead of propagating tangents forward from inputs, reverse mode propagates adjoints ${\bar{v}}_i = \partial {\mathcal{L}} / \partial {v}_i$ backward from the single scalar loss ${\mathcal{L}}$ to all parameters.

While forward mode computes Jacobian-vector products (${\mathbf{J}}{\dot{\mathbf{x}}}$), reverse mode evaluates vector-Jacobian products (VJPs), ${\mathbf{v}}^T {\mathbf{J}}= \sum_{j=1}^{M} {\bar{y}}_j \, \partial {y}_j / \partial {\mathbf{x}}$, where ${\bar{y}}_j = \partial {\mathcal{L}} / \partial {y}_j$ is one element of the upstream gradient vector ${\mathbf{v}}= \frac{\partial {\mathcal{L}}}{\partial {\mathbf{y}}} \in \mathbb{R}^{{M}}$. Because training optimizes a single scalar loss ${\mathcal{L}}$, the backward pass only ever needs to multiply this upstream gradient vector by each local operation’s derivative rule, never the 40 GB full Jacobian matrix.

To see how VJPs sidestep the full matrix, consider a simple element-wise operation such as ${\mathbf{y}}= \text{ReLU}({\mathbf{x}})$ with an input vector ${\mathbf{x}}= [-1.0, 2.0, 3.0]$ and an upstream gradient ${\mathbf{v}}= [0.5, 0.5, 0.5]$ flowing backward from the loss. Because the derivative of ReLU is $1$ when ${x}> 0$ and $0$ otherwise, the local gradient vector is $\frac{\partial {\mathbf{y}}}{\partial {\mathbf{x}}} = [0, 1, 1]$. Instead of building a $3{\times}3$ diagonal matrix and executing a matrix multiplication, the VJP computes the element-wise product ${\mathbf{v}}\odot \frac{\partial {\mathbf{y}}}{\partial {\mathbf{x}}} = [0.0, 0.5, 0.5]$ directly. It streams vectors without ever materializing the full ${M}\times {N}$ matrix in memory. Seeding the reverse sweep with ${\bar{\mathcal{L}}} = 1$ yields the complete parameter gradient vector $\nabla_{{\theta}}{\mathcal{L}}$ in a single backward pass, regardless of whether the model contains ten parameters or ten billion.

Reverse mode operates on the same three-operation function ${f}({x}) = {x}^2\sin({x})$ from [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-auto-diff-intro-b6f9f598|listing 4]], where ${x}$ reaches the output through two distinct computational paths: the square and the sine. [Algorithm 1](https://mlsysbook.ai/vol1/07_frameworks/07_frameworks.html#algo-reverse-mode-ad-trace) defines the reverse-mode traversal algorithm over a directed acyclic graph before tracing this concrete evaluation.

$y$

The algorithmic structure of [algorithm 1](https://mlsysbook.ai/vol1/07_frameworks/07_frameworks.html#algo-reverse-mode-ad-trace) reveals its systems cost. The forward pass records operator dependencies and buffers intermediate values required by backward derivative rules until the reverse sweep consumes them. Reverse mode trades activation storage and graph bookkeeping for a single backward pass. That pass runs one derivative rule per recorded operation, and each rule costs about as much as the operation it differentiates, so the whole sweep costs a small constant multiple of the forward pass regardless of parameter count ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-baur1983complexity|Baur and Strassen 1983]]; [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-griewank2008evaluating|Griewank and Walther 2008]]).

For the concrete function in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-auto-diff-intro-b6f9f598|listing 4]] evaluated at ${x}=2.0$, the forward pass records ${a}={x}^2=4.0$, ${b}=\sin({x})\approx0.9093$, and ${c}={a} {b}\approx3.637$. Seeding ${\bar{c}}=1.0$, the product rule yields adjoints ${\bar{a}}=0.9093$ and ${\bar{b}}=4.0$. The square branch contributes $0.9093\cdot4.0\approx3.6372$ to ${\bar{x}}$, its adjoint times the square’s local derivative $2{x} = 4.0$, while the sine branch contributes $4.0\cos(2.0)\approx-1.6646$, its adjoint times the sine’s local derivative $\cos({x})$. Accumulating both paths gives the exact derivative $\partial {c}/\partial {x}= {\bar{x}}\approx 1.973$.

This single backward traversal computes $\partial {c}/\partial {x}$ regardless of how many fan-out paths connect ${x}$ to ${c}$. In a deep neural network, every weight tensor influences the scalar loss through thousands of divergent paths across successive layers; reverse mode aggregates all incoming adjoints in one reverse sweep. That one sweep, rather than one pass per parameter, is what keeps training a 175B-parameter model such as GPT-3 computationally tractable.

Executing this traversal in hardware exposes a physical constraint: evaluating local derivatives during the backward pass requires the operating point established during forward execution. The framework must therefore determine which forward tensors to persist in device memory, when to allocate them, and when to free them. The recorded graph answers the “when to free” question, because each saved tensor can be released as soon as the last backward rule that reads it has run.

A two-layer network makes these requirements concrete ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-reverse-simple-nn-c46a2869|listing 7]]). Tracing both passes explicitly shows which forward activations must survive until the reverse sweep consumes them.

``` python
def simple_network(x, w1, w2):
    hidden = x * w1  # First layer
    activated = max(0, hidden)  # ReLU activation
    output = activated * w2  # Second layer
    return output

# --- Forward pass stores intermediates ---
x, w1, w2 = 1.0, 2.0, 3.0
hidden = x * w1
activated = max(0, hidden)
output = activated * w2

# --- Backward pass consumes them ---
d_output = 1.0  # Seed gradient
d_w2 = activated  # = 2.0
d_activated = w2  # = 3.0
d_hidden = d_activated * (1 if hidden > 0 else 0)  # ReLU gate: 3.0
d_w1 = x * d_hidden  # = 3.0
d_x = w1 * d_hidden  # = 6.0
```

Listing 7: **Reverse Mode in a Neural Network**: The forward pass computes and stores intermediate values; the backward pass walks the computation in reverse to produce gradients for every parameter.

^lst-reverse-simple-nn-c46a2869

Three implementation requirements emerge from this example. First, the framework must track dependencies between operations to determine the correct reverse traversal order. Second, the information needed by each backward rule must be available, either saved during the forward pass or regenerated. The chain rule evaluates local derivatives at the forward operating point. For example, evaluating $\frac{\partial}{\partial {z}}\text{ReLU}({z}) = {\mathbb{I}}({z}> 0)$ requires the sign of the pre-activation ${z}$, which can be recovered from a saved value or mask. Computing a dense layer’s weight gradient $\frac{\partial {\mathcal{L}}}{\partial {\mathbf{W}}} = {\mathbf{X}}^T \frac{\partial {\mathcal{L}}}{\partial {\mathbf{Z}}}$, where ${\mathbf{Z}}$ is the layer’s pre-activation output, requires the forward input activation tensor ${\mathbf{X}}$. Third, every differentiated operation needs both a forward implementation and a corresponding backward rule. These requirements define the engineering surface of automatic differentiation, where retaining forward values can consume much of the training memory budget.

### Activation Memory

^sec-ml-frameworks-memory-management-strategies-b008

Retaining those forward values turns device memory capacity, rather than raw floating-point throughput, into the feasibility boundary of training. A 175B-parameter model in FP16 already requires 350 GB for weights alone, exceeding the physical memory of any single accelerator before a single forward activation is saved, and reverse-mode AD compounds that pressure by retaining operation-dependent activations for backward derivative rules. Saved activations weigh just as heavily on models whose weights fit easily: in a batch-64 ResNet-50 (worked in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-principle-2-memorycompute-tradeoff-19f2|section 7.4.3.2]]), saved activations exceed the FP32 weights by roughly two orders of magnitude, on top of weights, gradients, and optimizer states.

This saved-activation footprint accumulates across successive layers, because each forward layer adds tensors that must persist until the backward sweep unwinds to that layer ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-reverse-memory-00e5e911|listing 8]]). For a batch of ${B}$ sequences of length ${S}$ passing through ${N_L}$ layers of width ${d}$, each saving ${n_{\text{saved}}}$ tensors of ${s_{\text{elem}}}$ bytes per element, the saved state is approximately

$$
{M_{\text{activations}}} \approx {B} \times {N_L} \times {S} \times {d} \times {n_{\text{saved}}}\times {s_{\text{elem}}}
$$

 A model without sequences, such as a multilayer perceptron, drops the sequence length from this formula, and a convolutional network such as ResNet-50 replaces sequence length and width with the height, width, and channel count of each feature map. In every case the total grows linearly in both batch size and network depth. Consequently, the batch size that fits on an accelerator during training is far smaller than the batch size that fits during inference, where intermediate activations can be discarded as soon as the next layer consumes them.

The saved footprint peaks at the onset of the backward pass, when every saved tensor is still live, and recedes as backward rules consume those tensors. Total training memory can peak later, as gradients and temporary workspaces become live. Linear growth also lets a framework lower the saved peak by splitting a large batch into smaller micro-batches (gradient accumulation).[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn18|¹⁸]]

``` python
def deep_network(x, w1, w2, w3):
    # Forward pass - must store intermediates
    hidden1 = x * w1
    activated1 = max(0, hidden1)  # Store for backward
    hidden2 = activated1 * w2
    activated2 = max(0, hidden2)  # Store for backward
    output = activated2 * w3
    return output
```

Listing 8: **Activation Persistence Across Layers**: The marked intermediates represent values retained for backward; peak saved-activation memory depends on their number and sizes.

^lst-reverse-memory-00e5e911

The saved peak is a capacity limit rather than the bandwidth gap of the memory wall, and beyond shrinking the batch per pass, frameworks relieve it through two architectural strategies. The first is activation checkpointing (or gradient checkpointing), a reverse-mode technique ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-griewank2000revolve|Griewank and Walther 2000]]) that deep learning frameworks adopted to train deep networks in sublinear memory ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-chen2016training|Chen et al. 2016]]). Rather than buffering every intermediate activation, the runtime stores only selected segment boundary tensors and recomputes dropped intermediates on demand during the backward pass. In [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-checkpoint-recompute|listing 9]], the backward pass re-executes each forward segment to regenerate its activations rather than loading them from global memory.

↪ Activation checkpointing schedules and their recomputation cost are developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-optimal-checkpoint-placement-strategy-4a0d|Optimal checkpoint placement strategy]]**.

``` python
# Standard backward: every forward activation stays resident
h1 = layer1(x)  # kept for backward
h2 = layer2(h1)  # kept for backward
out = layer3(h2)  # kept for backward

# Checkpointed: keep only the boundary h1 and drop h2. The
# backward pass re-runs the wrapped segment to regenerate
# h2 on demand instead of holding it in memory.
h1 = layer1(x)  # boundary: kept
out = checkpoint(
    lambda a: layer3(layer2(a)), h1
)  # h2 recomputed in backward
```

Listing 9: **Activation Checkpointing**: The forward pass stores only segment boundaries; the backward pass re-runs each segment to regenerate the dropped activations, trading recomputation for memory.

^lst-checkpoint-recompute

The second strategy is the kernel fusion that the memory wall motivated in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8|section 7.3.2]], applied here to the body of a layer. Rather than executing matrix multiplication, bias addition, and activation functions as separate kernels that serialize intermediate tensors to accelerator global memory (HBM), compilers fuse compatible operators into a single kernel that passes intermediate values through registers or on-chip shared memory. Fusion’s capacity benefit is narrower than its traffic benefit. Temporaries that pass only between the fused operators are never allocated in HBM, so they add nothing to peak memory, while any value a backward rule reads must still be stored.[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn19|¹⁹]]

The backward pass itself relies on specialized hardware-optimized kernels. Rather than synthesizing backward passes from naive elementary operations, frameworks invoke tuned backward kernels (such as those of cuDNN, NVIDIA’s library of neural network primitives) that optimize memory access strides and register usage on accelerator hardware ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-chetlur2014cudnn|Chetlur et al. 2014]]). Checkpointing and kernel fusion are what let large architectures train within physical accelerator memory limits without out-of-memory faults; the specialized backward kernels make the backward pass faster without reducing what it must store.

### Autograd Internals

^sec-ml-frameworks-framework-implementation-automatic-differentiation-1407

Checkpointing, fusion, and specialized kernels address the physical bottlenecks of automatic differentiation, but production frameworks hide these mechanisms beneath a training loop of four calls. These calls clear the gradients, run the forward pass, call backward on the loss, and step the optimizer. Behind those calls, the runtime builds and traverses a dynamic computation graph, allocates and frees intermediate buffers, schedules backward kernels on device streams, and applies a numerical-precision policy.

#### Recording the Backward Graph

^sec-ml-frameworks-pytorch-autograd-internals-4fa0

If a forward operation discards its inputs and leaves no record of what function produced its output, calling `loss.backward()` has no path back to the model weights and no saved activations to plug into the chain rule. To make reverse traversal possible without ahead-of-time graph compilation, the autograd system dynamically constructs a directed acyclic graph of `Node` (or `Function`) objects during the forward pass. Each node stores an operator’s backward differentiation rule and holds references to the tensors needed to evaluate its vector-Jacobian products. Because edges point backward from outputs toward inputs, the engine can walk the graph in reverse topological order as soon as it receives the initial gradient from the scalar loss. The memory that those node references keep alive is examined in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-principle-2-memorycompute-tradeoff-19f2|section 7.4.3.2]].

When gradient recording is enabled and an operation has inputs requiring gradients, its output carries a `grad_fn` referencing the backward `Function`. Each `Function` links to antecedent nodes through its `next_functions` list, forming a chain from the scalar loss back to leaf parameter tensors. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-grad-fn-chain|Listing 10]] inspects this pointer chain for a simple composite computation:

``` python
import torch

x = torch.tensor([2.0], requires_grad=True)
y = x * 3
z = y.pow(2)

# Traverse the reverse-linked graph
print(z.grad_fn)  # PowBackward0
print(z.grad_fn.next_functions)  # -> MulBackward0
print(
    z.grad_fn.next_functions[0][0].next_functions
)  # -> AccumulateGrad (leaf)
```

Listing 10: **Reverse-Linked Graph Structure**: Recorded outputs link through `grad_fn` to backward functions, forming a reverse chain from output to leaf parameters. One backward traversal computes the scalar loss gradient; its work grows with the graph.

^lst-grad-fn-chain

The inspection exposes the traversal path: `PowBackward0` (from `z = y.pow(2)`) links to `MulBackward0` (from `y = x * 3`), which terminates at `AccumulateGrad` on the leaf parameter tensor `x`. Leaf tensors are graph sinks where accumulated gradients write directly into the `.grad` buffer rather than propagating further. The tuple format `(Function, index)` tracks the specific output index for multi-output operations.

This reverse-linked graph imposes a lifetime constraint: the topology and the forward information required by each backward rule must remain available until that rule executes. Host-side graph metadata (pointers and node descriptors) is distinct from the device tensor buffers it references. Retaining those buffers can consume gigabytes of accelerator capacity as model depth and batch size grow; recomputation or offloading changes where and how the required values are made available.

Production training also needs control over gradient propagation beyond a standard backward sweep. Selective gradient computation freezes layers during transfer learning via `requires_grad=False` or `.detach()`. Gradient inspection and modification supports clipping, debugging, or logging intermediate adjoints via runtime hooks. Custom differentiation rules cover non-standard operations such as specialized CUDA kernels or novel activation functions. In PyTorch, these needs map onto the runtime mechanisms of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^tbl-autograd-control|table 6]]. The `.detach()` call serves selective computation, gradient hooks serve inspection, and a custom `autograd.Function` serves custom rules. Two further mechanisms span backward passes. The `retain_graph=True` flag reuses one graph, and gradient accumulation, the micro-batch technique of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-memory-management-strategies-b008|section 7.4.2]], reuses one gradient buffer by summing successive passes into it. Each mechanism carries its own memory or correctness hazard.

| **Mechanism**                  | **What it controls**                                                                                          | **Cost or hazard**                                                                                             |
|:-------------------------------|:--------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------|
| **`retain_graph=True`**        | Keeps saved graph state available for another backward traversal                                              | Retains memory that would otherwise be released; the amount depends on the graph and saved values              |
| **Gradient accumulation**      | Successive backward passes sum into `.grad` until `zero_grad()` resets them, enabling large effective batches | Forgetting the reset silently mixes gradients across optimization steps                                        |
| **Custom `autograd.Function`** | User-defined forward and backward rules for operations outside the built-in library                           | Makes the implementer decide what to save and how to differentiate                                             |
| **Gradient hooks**             | Inspecting or modifying gradients mid-traversal (clipping, logging, debugging)                                | Runs arbitrary Python per registered tensor on every backward pass                                             |
| **`.detach()`**                | Cuts gradient flow at a chosen boundary (frozen layers, inference outputs)                                    | The legacy `.data` attribute bypasses autograd and silently corrupts gradients; clone before in-place mutation |

Table 6: **Autograd Control Mechanisms**: Each extension point that the autograd engine exposes during graph traversal trades a specific control for a memory or correctness cost.

^tbl-autograd-control

Custom autograd functions move two decisions from the engine to the programmer, what to save and how to differentiate. The implementation explicitly defines which forward tensors to preserve in `ctx.save_for_backward()` and evaluates the corresponding vector-Jacobian products in `backward()`. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-custom-autograd-function|Listing 11]] applies this interface to a custom multiply-add operation.

``` python
import torch

class MultiplyAdd(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, y, z):
        # Save tensors needed for backward
        ctx.save_for_backward(x, y)
        return x * y + z

    @staticmethod
    def backward(ctx, grad_output):
        # Retrieve saved tensors
        x, y = ctx.saved_tensors

        # Compute gradients using chain rule
        grad_x = grad_output * y  # dL/dx = dL/dout * dout/dx
        grad_y = grad_output * x  # dL/dy = dL/dout * dout/dy
        grad_z = grad_output  # dL/dz = dL/dout * 1

        return grad_x, grad_y, grad_z

# Usage
x = torch.tensor([2.0], requires_grad=True)
y = torch.tensor([3.0], requires_grad=True)
z = torch.tensor([1.0], requires_grad=True)

output = MultiplyAdd.apply(x, y, z)
output.backward()

print(
    x.grad, y.grad, z.grad
)  # tensor([3.]), tensor([2.]), tensor([1.])
```

#### Saved Tensors and the Memory-Compute Trade-Off

^sec-ml-frameworks-principle-2-memorycompute-tradeoff-19f2

Every call to `save_for_backward` in the backward graph keeps a device tensor live from the forward pass until its backward consumer finishes. Because different operations require different forward information (a matrix multiplication weight gradient requires the full input activation tensor, whereas elementwise ReLU needs only the pre-activation sign), the resulting memory profile depends on each operator’s backward rule and dwarfs the model weights even on modest architectures.

![[90 Assets/Volume I/07 Frameworks/Vol1 Frameworks Margin 001 c8f52d4cc2.svg]]

*Two-bar log-scale ladder: an illustrative ResNet-50 training memory sum of about 8.4 to 12.4 GB far above 102.2 MB of FP32 weights, with a bracket marking a gap of 82.3 to 121.4 times.*

*The training memory sum dwarfs FP32 weight storage alone.*

Consider an illustrative ResNet-50 training scenario with 25.6M parameters (~102.2 MB of FP32 weights), batch size 64, and $224{\times}224$ images. With 8 GB–12 GB of saved activations, gradients add ~102.2 MB, and two Adaptive Moment Estimation (Adam) FP32 moment buffers add ~204.5 MB. Summing those four kinds of training state (**[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-memory-training-vs-inference|Worked example: Training vs. inference memory]]**) gives an 8.4 GB–12.4 GB training scenario, roughly 82.3–121.4× the FP32 weight storage alone. This is a capacity-planning sum; actual peak memory depends on which components are live together. Inference requires no optimizer states, gradients, or saved backward buffers, but still has live activations and runtime workspace.

Parameter count alone therefore does not tell an engineer whether training fits. Total training memory obeys the four-component formulation (${M_{\text{total}}} = {M_{\text{weights}}} + {M_{\text{gradients}}} + {M_{\text{optimizer}}} + {M_{\text{activations}}}$) plus allocator overhead, as stated in **[[05 Reference/Volume I - Foundations/V1 Algorithm Foundations#^sec-appdx-algorithm-foundations-true-cost-training-memory-e54e|Training memory]]**.

Frameworks provide three graph-level controls to manage this trade-off. Activation checkpointing, whose mechanism [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-checkpoint-recompute|listing 9]] showed, alters what the graph retains. In iron law terms, checkpointing increases the arithmetic operation count (${O}$) to reduce peak activation storage; its effect on transfer volume (${D_{\text{vol}}}$) depends on the recomputation path.

Tensor detachment, the second control, sets a gradient boundary: calling `.detach()` makes subsequent operations treat that tensor as independent of its prior computation, so no gradient flows back through it. Detachment changes what is kept from that point on, not what was already saved. Operations after the cut record nothing that points back through it, so the upstream graph and its saved activations can be released once nothing else references them, but detaching does not free them by itself. A detached tensor also shares storage with the original, so an in-place write to it changes the original too, which is why the hazard column of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^tbl-autograd-control|table 6]] advises cloning before in-place mutation.

Preventing the saving in the first place takes a third control. Inside a `torch.no_grad()` region, autograd records no operations and saves no activations. In transfer learning, where a pretrained feature extractor stays frozen while a new head trains, running the extractor inside `torch.no_grad()` means only the head pays the activation-storage cost, and the extractor’s output enters the head as a constant. The last two controls divide the work: `.detach()` cuts the gradient path at one tensor, `torch.no_grad()` stops recording for a whole region, and neither releases state that something still references.

The recorded graph fixes which backward kernels the device must execute (the ${O}$ term), and the saved-tensor policy fixes how many bytes stay resident and move through the memory hierarchy (the ${D_{\text{vol}}}$ term). Mixed precision, a lever that changes the number format rather than the graph, acts on the second directly, because it shrinks every saved value and every operand a kernel reads.

↪ The decision of when these single-machine levers stop being enough and training must scale beyond one machine is developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-scale-physical-ceiling-e06c|When to scale: The physical ceiling]]**.

#### Mixed-Precision Training Support

^sec-ml-frameworks-mixedprecision-training-support-d31d

Mixed precision ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-micikevicius2017mixed|Micikevicius et al. 2018]]) improves two iron law terms at once. Tensor Cores, the dedicated matrix-multiply units of NVIDIA GPUs, run 16-bit matrix multiplications faster than FP32 units, raising ${R_{\text{peak}}}$, and eligible 16-bit activations halve the bytes stored and moved, reducing ${D_{\text{vol}}}$.

Automatic mixed-precision APIs deliver both gains through a dispatch policy rather than a change to model code. Inside an `autocast` region, the dispatcher consults a per-operator precision list before selecting a kernel. Compute-intensive operations such as convolutions and linear projections run in FP16 or BF16, while numerically sensitive operations such as softmax, reductions, and loss calculations run in FP32.

Alongside `autocast`, a second framework component, `GradScaler`, compensates for FP16’s narrow exponent range (5 bits, with normal values bounded below by $\approx 6.10 \times 10^{-5}$). Gradients smaller than that bound lose precision or round to zero, the numeric form of vanishing gradients from **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-parameter-initialization-5d1a|Initialization and numerical range]]**. The scaler multiplies the scalar loss by a loss-scale factor ${s_{\text{loss}}}$ before backward traversal so that small gradients remain representable, divides the parameter gradients by ${s_{\text{loss}}}$ before the optimizer update, and skips any step whose gradients overflow. BF16 keeps FP32’s 8-bit exponent, so BF16 recipes usually run under `autocast` with the scaler disabled. The framework therefore supplies the dispatch and scaling machinery. The choice of number format and the way the loss scale adapts during training are policy decisions that **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-mixedprecision-training-9218|Mixed-precision training]]** develops. The scaling mechanism itself appears in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-loss-scaling-f9f5|Loss scaling]]**. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-autocast-usage|Listing 12]] shows the two framework components working together in the FP16 path.

``` python
import torch
from torch.amp import autocast, GradScaler

model = MyModel().cuda()
optimizer = torch.optim.Adam(model.parameters())
scaler = GradScaler("cuda")

for inputs, targets in dataloader:
    inputs, targets = inputs.cuda(), targets.cuda()
    optimizer.zero_grad()

    # Framework automatically selects precision per operation
    with autocast(device_type="cuda", dtype=torch.float16):
        outputs = model(inputs)
        loss = criterion(outputs, targets)

    # GradScaler handles gradient scaling for numerical stability
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()
```

Listing 12: **Mixed-Precision API**: Modern frameworks provide automatic mixed-precision support through context managers that handle precision selection and numerical stability.

^lst-autocast-usage

Operation precision and weight storage are separate choices. Under autocast the parameters stay in FP32 for the optimizer update and are cast to 16 bits on the fly for eligible operations; why training keeps this full-precision copy is part of the mixed-precision policy that **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-mixedprecision-training-9218|Mixed-precision training]]** develops.

Beyond the FP32 weights, the optimizer keeps FP32 moment buffers that sit on top of gradients and saved activations. The per-parameter accounting, and the gap it opens between a model’s weight file and its training footprint, is worked in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-memory-training-vs-inference|Worked example: Training vs. inference memory]]**, and **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-optimizer-memory-training-loop-4383|Reducing optimizer memory]]** develops how to budget and reduce that optimizer memory.

#### Tensor Lifetimes and the Caching Allocator

^sec-ml-frameworks-memory-management-gradient-computation-bb77

Checkpointing, fusion ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-memory-management-strategies-b008|section 7.4.2]]), and mixed precision decide which tensors exist during a training step and how many bytes each one occupies. The runtime still has to decide when each tensor’s memory is reclaimed and how fresh device memory is obtained. Where tensors live and how they move between host and device are the subject of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.06 Abstraction Tensors, Devices, and Operations#^sec-ml-frameworks-device-memory-management-9404|section 7.5.2]]; the question here is narrower, namely when a value saved for the backward pass can be freed. In the retained-activation scheme of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^lst-reverse-memory-00e5e911|listing 8]], forward layers add saved tensors that remain live until backward traversal consumes them, and modern runtimes reclaim each one once its backward consumers and other references no longer need it.

Allocation itself is also slow. Invoking device memory allocation and release (`cudaMalloc` and `cudaFree`) incurs substantial driver overhead, and `cudaFree` can block the host until all previously queued device work completes, draining accelerator command queues ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-paszke2019pytorch|Paszke et al. 2019]]). To eliminate this latency, modern frameworks intercept allocations with **caching allocators** that maintain pools of pre-reserved device memory blocks across training iterations. Suballocating from these pools amortizes device allocation costs and avoids the synchronizations that these calls can force, though varying tensor lifetimes can still induce memory fragmentation.

The snapshots in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^fig-allocator-live-cached-blocks|figure 9]] distinguish tensor lifetime from allocator reservation. They assume a fixed pool with no additional segment growth, compaction, or virtual-address remapping, so the free-block geometry determines whether a request fits.

![[90 Assets/Volume I/07 Frameworks/Generated Figure 80b32b6be2.svg]]

Figure 9: **Live and Cached Allocator Blocks**: Equal widths represent equal amounts of a fixed virtual-address pool. Releasing a tensor makes its block reusable without reducing the reserved pool. After splitting a cached block and releasing another tensor, the remaining free regions cannot satisfy the larger contiguous request. The example permits no pool growth, compaction, or remapping.

The request fails although enough memory is free in total, because no single free block is large enough to hold it.

**Systems Perspective 7.1: Caching allocator and utilization**

Caching allocators reduce allocation overhead and improve block reuse, but they cannot rule out the failure above. An out-of-memory error can therefore reflect live allocations, allocator-reserved blocks, fragmentation, or another process, and telling them apart requires the allocator’s own memory statistics.

### Tape-Based and Transform-Based Differentiation

^sec-ml-frameworks-different-frameworks-implement-ad-2f8e

Frameworks record computation for differentiation in one of two ways. A tape-based system records each operation as the forward pass runs, while a transform-based system turns a captured function into its derivative function before anything executes. The choice shows up in per-step bookkeeping and memory planning. A framework that builds a dynamic trace at runtime pays per-operation bookkeeping on every forward pass, and its caching allocator must accommodate allocation patterns that can vary with execution. A framework that captures a stable computation, by contrast, may pre-plan buffers and reuse storage across the forward and backward graphs because it can reason about lifetimes before execution. The gain depends on capture coverage, tensor lifetimes, shapes, and backend support.

The execution models of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-problem-e1e1|section 7.3]] dictate these designs. PyTorch ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-paszke2019pytorch|Paszke et al. 2019]]) builds its tape during forward execution, which grants unconstrained Python control flow and direct debugging but retains tape metadata and saved tensors until backward traversal completes. Early TensorFlow ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-abadi2016tensorflow|Abadi et al. 2016]]) differentiated symbolically during graph construction, producing a fixed backward graph amenable to whole-graph dead-code elimination and memory reuse before execution. TensorFlow 2.x executes eagerly by default and compiles differentiation graphs through `tf.function` when throughput requires it ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-tensorflowFunctionGuide|TensorFlow Developers 2024]]). JAX[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn20|²⁰]] ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-frostig2018compiling|Frostig et al. 2018]]) treats differentiation as a transformation that turns one function into its derivative function, which composes with vectorization (`jax.vmap()`) and compilation (`jax.jit()`) at the cost of requiring pure functions.

These implementation differences determine how much debugging visibility, compiler optimization, and deployment portability a team can expect from each framework. Each design also resolves a tension common to all of them. Backward rules need forward information, while device memory limits how much of it can be kept, so every framework must choose which activations to save, which operations to fuse, and how much recomputation to accept. Those choices decide which models can train on a given accelerator.
