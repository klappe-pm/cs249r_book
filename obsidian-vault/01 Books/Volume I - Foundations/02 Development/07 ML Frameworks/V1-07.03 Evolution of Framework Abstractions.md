# V1-07.03 Evolution of Framework Abstractions

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-frameworks-evolved-ac68

In 1979, writing a matrix multiplication in Fortran that used the hardware efficiently required deep knowledge of cache lines, register scheduling, and vector units. By the late 2010s, a single line of Python (`torch.matmul(A, W)`) could dispatch to a tuned implementation without the programmer knowing the details of the hardware. Four decades of abstraction closed that gap, each layer removing a bottleneck that made the previous generation impractical at scale. History built a ladder of abstraction from the bottom up in four layers (tuned kernels, array libraries, automatic differentiation, and graph compilers), and each layer automates what the one below left to the programmer. The rest of this chapter walks the ladder from the top down, starting from the graph a model defines.

The first layer established reusable hardware primitives. The Basic Linear Algebra Subprograms (BLAS)[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn4|⁴]] standardized low-level linear-algebra operations ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-lawson1979|Lawson et al. 1979]]), and LAPACK ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-anderson1999lapack|Anderson et al. 1999]]) built factorizations and eigensolvers on top of them. A standard interface mattered because naive nested loops saturate memory bandwidth long before the arithmetic units reach peak throughput. BLAS let numerical software delegate these operations to vendor libraries tuned for each processor’s cache sizes, vector widths, and register files. Its Level 3 extension added the matrix-matrix routines, such as matrix multiplication (`C = A @ B`),[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn5|⁵]] that dominate ML workloads ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-dongarra1990level3|Dongarra et al. 1990]]).

The second layer, NumPy[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn6|⁶]] ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-harris2020|Harris et al. 2020]]), wrapped those libraries in Python: the interpreter manages control flow and array metadata (shape, strides, and data type), while compiled code runs the inner loops over contiguous buffers. That division of labor, high-level intent in an interpreted language and inner loops in native code, became the template for every framework that followed.

The third layer automated gradient computation. NumPy users still derived and coded backpropagation by hand, an error-prone process that does not scale to deep networks. Deep learning frameworks such as Theano,[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn7|⁷]] TensorFlow ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-abadi2016tensorflow|Abadi et al. 2016]]), and PyTorch ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-paszke2019pytorch|Paszke et al. 2019]]) made automatic differentiation a runtime primitive: by recording the forward computation as a graph, they construct the backward computation automatically. That automation let the bitter lesson operate at the pace of research. Once a new architecture no longer needed a hand-derived backward pass, general methods that scale with computation could be tried as quickly as their forward functions could be written.

↩︎ The bitter lesson, that general methods which exploit growing computation outlast hand-engineered approaches, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.05 The Bitter Lesson#^sec-introduction-bitter-lesson-79c7|The Bitter Lesson]]**.

The fourth layer automated kernel construction. With one tuned kernel per operation, speeding up a chain of small operations still meant writing a combined kernel by hand. Graph compilers such as XLA and TorchInductor take over that work by capturing a region of the program and generating kernels fused for the target device.

Across that history ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.03 Evolution of Framework Abstractions#^fig-mlfm-timeline|figure 1]]), the milestones run from BLAS and LAPACK routines through NumPy vectorization to symbolic graph capture in Theano and TensorFlow, dynamic graphs in PyTorch, and functional transformations in JAX. Each generation preserved the vendor-tuned kernel layer beneath it while raising the level of abstraction at which engineers express and differentiate models.

Each generation hid details that consumed engineering effort in the previous one, and each introduced new trade-offs. BLAS hid assembly-level optimization but fixed the interface. NumPy hid memory management but left differentiation manual. Modern frameworks hide gradient computation but force a choice among execution models. Every layer also hides assumptions about the data it passes along: each operation expects its inputs to have a particular shape, data type, device, and, for physical quantities, unit. When nothing checks those expectations at the boundary, correct components can compose into a wrong system.

**War Story 7.1: The interface that forgot its units (1999)**

**Context**: NASA’s Mars Climate Orbiter depended on ground software, spacecraft software, navigation teams, and contractor interfaces all agreeing on the physical meaning of exchanged values ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-nasa1999marsclimateorbiter|Mars Climate Orbiter Mishap Investigation Board 1999]]).

**Mechanism**: Ground software supplied by Lockheed Martin computed thruster impulse in English units (pound-force seconds), while JPL navigation software consumed the values assuming SI units (newton-seconds), a 4.45$\times$ implicit unit mismatch.

**Impact**: On September 23, 1999, the spacecraft was lost after passing behind Mars (occultation). Its corrected 57 km periapsis, rather than the planned 226 km, was judged too low for survival.

**Response**: The board recommended unit-consistency checks, specification audits of transferred data, and stronger end-to-end verification of ground software.

**Systems lesson**: Two pieces of correct code can compose into a wrong system when the meaning of the values they exchange is implicit. ML frameworks meet the same failure whenever tensor memory layouts (such as channels-first NCHW \[$\text{Batch} \times \text{Channels} \times \text{Height} \times \text{Width}$\] vs. channels-last NHWC \[$\text{Batch} \times \text{Height} \times \text{Width} \times \text{Channels}$\]), quantization scale factors, or physical feature units differ across pipeline stages. The outputs look plausible but quietly corrupt downstream inference. Frameworks guard against the tensor cases by checking, at every operation, that its inputs have the expected shape, data type, and device.

A framework can run those checks as each operation executes, when the failing line and its intermediate values are directly visible, or before execution, when a captured graph can be validated and optimized as a whole. When checks and optimizations happen is the execution problem. It is the first framework design choice because runtime dispatch and graph capture determine both the debugging experience and what optimizations automatic differentiation and hardware mapping can later exploit.
