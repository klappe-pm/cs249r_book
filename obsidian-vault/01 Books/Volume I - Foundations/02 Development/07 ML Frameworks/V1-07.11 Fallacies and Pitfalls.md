# V1-07.11 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-fallacies-pitfalls-61ef

Framework selection involves subtle trade-offs where intuitions from conventional software engineering fail. The memory wall, kernel fusion constraints, and deployment target diversity create pitfalls that waste engineering effort and cause production systems to miss latency targets.

**Fallacy**: *All frameworks provide equivalent performance for the same model architecture.*

Engineers assume that a model performs the same in every framework because the mathematics is the same. The GPT-2 XL decoding step that opened this chapter refutes this. The identical step spends about 8.6 ms on the host when an eager framework issues its 576 kernels one at a time, against a weight read of about 0.9 ms once the launches are captured and replayed. In the hypothetical ResNet-50 scenario of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^tbl-training-benchmark|table 4]], compilation raises throughput by 48.3 percent and a specialized inference engine by 2.6× over eager mode. Fusion depth, graph capture, and backend libraries differ between frameworks, so organizations that assume equivalence can miss latency targets and face late framework migrations.

**Pitfall**: *Choosing frameworks based on popularity rather than project requirements.*

Engineers assume the most popular framework works for any project. In reality, deployment constraints dominate. A mobile runtime such as ExecuTorch or TensorFlow Lite and a microcontroller runtime such as TensorFlow Lite Micro make different assumptions about memory allocation, operator coverage, and hardware delegates. The former targets phones with GB-scale memory, while the latter often targets devices with hundreds of KB of RAM, commonly below 256 KB for small TinyML deployments. Teams that prototype edge applications without checking the final runtime can face memory bloat that exceeds device capacity or a late framework migration after development completes. The deployment runtime (**[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-inference-runtime-selection-5eef|Inference Runtime Selection]]**) therefore belongs among the first checks, made before the training framework is chosen.

**Fallacy**: *Framework abstractions eliminate the need for systems knowledge.*

Engineers assume high-level APIs handle all optimization automatically. The training step of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.08 Anatomy of a Training Step#^sec-ml-frameworks-putting-together-anatomy-training-step-c7f1|section 7.7]] shows otherwise. Its ReLU has an arithmetic intensity (FLOPs performed per byte moved) of 0.125 FLOP/byte, about 160× below the H100’s FP32 ridge of roughly 20 FLOP/byte (the arithmetic intensity below which an operation is memory bound), and the whole step spends about 95 μs in host dispatch against well under a microsecond of ideal device time. No API call reveals either fact. Engineers must identify the limiting resource before choosing fusion, batching, layout, or precision optimizations.

**Pitfall**: *Ignoring vendor lock-in from framework-specific formats.*

Engineers assume framework migration is straightforward since models are “just math.” Converting TensorFlow SavedModel to PyTorch can require rewriting custom operations, validating numerical equivalence across large test suites, and retraining when operations lack exact equivalents. The ONNX interchange format (**[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-inference-runtime-selection-5eef|Inference Runtime Selection]]**) improves portability, but custom operators, dynamic shapes, and backend-specific optimizations can still require manual work. Organizations that ignore this during initial framework selection face costly migrations when deployment requirements change or better frameworks emerge.

**Pitfall**: *Increasing batch size without modeling activation memory.*

Engineers assume that if memory is available, larger batches always improve throughput. Larger mini-batches amortize fixed dispatch overhead, but they also scale the activation memory that must stay live until the backward pass consumes it. In the illustrative ResNet-50 scenario of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-principle-2-memorycompute-tradeoff-19f2|section 7.4.3.2]], batch 64 already holds 8 GB–12 GB of saved activations. Batch 256 holds 32 GB–48 GB, and batch 512 holds 64 GB–96 GB, which on an 80 GB H100 forces activation checkpointing. Recomputation then adds roughly one extra forward pass per step, which can cost more throughput than the larger batch gained, and materialized attention scores make the effect sharper for transformers because they grow with the square of sequence length. Teams that blindly maximize batch size can achieve lower throughput than smaller batches that avoid recomputation.

↪ How activation memory grows linearly with batch size and caps the batch that fits in accelerator memory is developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-minibatch-processing-4eb0|Mini-batch processing]]**.

**Fallacy**: *Compilation overhead is negligible.*

Engineers assume compilation overhead is a one-time cost that pays off quickly. The hypothetical values in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^tbl-training-benchmark|table 4]] assign ResNet-50 higher compiled throughput and a compile window of 15 s to 30 s per graph change. Under those assumptions, and timed with the table’s inference throughputs, a 10,000-image experiment with 10 code changes completes in 6.9 s in eager mode and 304.7 s in compiled mode, including recompilation overhead. The compiled workflow is therefore about 44.2× slower in this illustrative rapid-prototyping scenario; a training loop would add backward work to every pass but pay the same recompilation cost. Teams that enable compilation during rapid prototyping can waste time waiting for recompilations that negate throughput gains.

**Pitfall**: *Using one execution policy for exploration and production.*

The right framework mode depends on the loop. During exploration, eager execution and small tests shorten feedback by avoiding repeated graph captures and recompilations. During production serving or long training runs, compilation can amortize setup across many requests or samples. The deciding factors are workload duration and stability: compilation pays when graph structure and shapes recur, whereas changing control flow or input shapes can invalidate cached artifacts and restart the amortization. In the hypothetical ResNet-50 scenario, one 30 s compilation pays for itself only after about 134,000 images. A prototyping loop that recompiles every few minutes never reaches that point, while a serving system passes it within minutes of steady traffic. One policy for both phases either slows research iteration or leaves production throughput unused.

1.  A research team exploring architecture modifications runs experiments where model code changes every 10 training steps. When they enable JIT graph compilation (`torch.compile`), total training time increases by 5$\times$ compared to standard eager mode. What systems principle explains this performance degradation?

    1.  Compilation incurs a large upfront compilation latency ($T_{\text{compile}}$); if graph structures or tensor shapes change frequently, the compilation cost cannot be amortized across executions ($N_{\text{steps}} \times (T_{\text{eager}} - T_{\text{compiled}}) < T_{\text{compile}}$), making repeated recompilation slower than eager execution
    2.  Compiled kernels run at half the floating-point clock frequency of eager kernels on NVIDIA GPUs
    3.  JIT compilers disable GPU hardware acceleration when running short training scripts
    4.  Dynamic graph compilation automatically converts all FP32 operations to 64-bit double precision

2.  Explain why choosing a framework based on community popularity or GitHub stars rather than the deployment constraints that limit the design is a severe engineering pitfall for edge and embedded ML projects.
