# V1-07.08 Anatomy of a Training Step

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-putting-together-anatomy-training-step-c7f1

In every iteration of a training loop, millions of floating-point operations, dynamic memory allocations, and hardware kernel launches must complete within a step that lasts anywhere from microseconds to seconds. Execution, differentiation, and hardware abstraction operate simultaneously during model training. Even a minimal two-layer multilayer perceptron, written as eight executable statements in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.08 Anatomy of a Training Step#^lst-training-step-anatomy|listing 20]], exercises all three. For a network this small, host dispatch takes most of the step. Tracing each statement through the runtime stack connects the quantitative principles developed in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-compilation-continuum-principle-c106|section 7.3.7]] to physical execution.

The network is a two-layer version of the MNIST digit classifier from **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation#^sec-neural-computation|Neural Computation]]**, with 784 inputs, 128 hidden units, and 10 outputs, trained at batch size 32. The example assumes trainable CUDA tensors `W1` and `W2` with shapes `(784, 128)` and `(128, 10)`, matching bias vectors `b1` and `b2`, and an optimizer already constructed over these parameters. The listing shows one iteration after that setup.

``` python
# Single training step for a 2-layer MLP
x = torch.randn(32, 784, device="cuda")  # Input batch
y = torch.randint(0, 10, (32,), device="cuda")  # Labels

# Forward pass
optimizer.zero_grad()
h = torch.relu(x @ W1 + b1)  # Hidden layer
logits = h @ W2 + b2  # Output layer
loss = F.cross_entropy(logits, y)

# Backward pass
loss.backward()

# Parameter update
optimizer.step()
```

Listing 20: **Training Step Anatomy**: One minimal training iteration of a two-layer MLP exercises tensor allocation, kernel dispatch, autograd recording, gradient computation, and parameter updates.

### Forward Pass

^sec-ml-frameworks-anatomy-forward-pass-7a1c

During the forward pass, executing `h = torch.relu(x @ W1 + b1)` triggers an eager execution sequence:

1.  Python dispatch: The Python interpreter invokes `torch.matmul`, which routes through PyTorch’s C++ dispatcher to select the CUDA backend, incurring the Python-dispatch share of the per-operation overhead (about 10 μs in this chapter’s model) before issuing work to the device.
2.  Kernel selection: cuBLAS selects a GEMM kernel configured for dimensions 32 $\times$ 784 $\times$ 128, one that splits the matrix product into blocks sized to fit the accelerator’s on-chip memory.
3.  Kernel launch: The host thread enqueues the launch descriptor into the GPU command stream, consuming driver launch latency while asynchronous execution allows host execution to proceed without blocking on completion.
4.  GPU execution: The streaming multiprocessors stream `W1` from HBM[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.15 Footnotes#^fn24|²⁴]] through L2 cache into registers and the FP32 arithmetic units (Tensor Cores engage only when a reduced-precision matrix format, either TF32 or a 16-bit data type, is enabled), evaluate the matrix product, and write the output activations back to HBM.
5.  Autograd recording: Concurrently on the host, PyTorch’s autograd engine instantiates an `MmBackward` node on the dynamic tape, saving references to the device tensors needed for the requested gradients. Here the weight gradient requires `x`; no input gradient is requested.

The subsequent bias addition (`+ b1`) and activation (`torch.relu`) follow an identical eager path, with each operation dispatching a separate kernel, executing round-trips to HBM, and appending a node to the tape. By the time the forward pass reaches the loss function, the autograd graph holds a complete chain of backward functions and saved activation pointers ready for reverse traversal.

### Backward Pass

^sec-ml-frameworks-anatomy-backward-pass-3e9d

Calling `loss.backward()` executes reverse-mode automatic differentiation in four stages:

1.  Tape traversal: The autograd engine traverses the recorded computational graph in reverse topological order, starting from the scalar loss node.
2.  Gradient computation: The engine executes the backward kernel registered to each node. Traversing backward, `CrossEntropyBackward` evaluates $\frac{\partial {\mathcal{L}}}{\partial \text{logits}}$ using the combined softmax-cross-entropy derivative. The `MmBackward` node for ${\mathbf{W}}_2$ computes $\frac{\partial {\mathcal{L}}}{\partial {\mathbf{W}}_2} = {\mathbf{H}}^T \cdot \frac{\partial {\mathcal{L}}}{\partial \text{logits}}$ and $\frac{\partial {\mathcal{L}}}{\partial {\mathbf{H}}}$, where ${\mathbf{H}}$ is the batch of hidden activations (`h`). The `ReluBackward` node evaluates the activation mask, zeroing gradients where forward activations satisfy ${\mathbf{H}} \leq 0$. The `MmBackward` node for ${\mathbf{W}}_1$ computes $\frac{\partial {\mathcal{L}}}{\partial {\mathbf{W}}_1} = {\mathbf{X}}^T \cdot \frac{\partial {\mathcal{L}}}{\partial {\mathbf{Z}}_1}$, where ${\mathbf{Z}}_1 = {\mathbf{X}}{\mathbf{W}}_1 + {\mathbf{b}}_1$ is the pre-activation. Because the input batch ${\mathbf{X}}$ (`x`) does not set `requires_grad=True`, traversal terminates without evaluating $\frac{\partial {\mathcal{L}}}{\partial {\mathbf{X}}}$.
3.  Gradient write-back: Computed parameter gradients are added in place into the `.grad` fields of leaf tensors (${\mathbf{W}}_1$, ${\mathbf{b}}_1$, ${\mathbf{W}}_2$, ${\mathbf{b}}_2$).
4.  Saved-state release: As each backward node completes, the framework releases the saved tensor references that it no longer needs. Storage becomes reusable only when no other live reference retains it; in this listing, Python variables such as `h` can keep tensors alive after backward. The caching allocator can reuse released regions for subsequent operations without returning them immediately to the device.

After backward fills the parameter `.grad` buffers, `optimizer.step()` reads those gradients, updates the parameters, and advances any optimizer state. Backward itself computes gradients without applying that update, and the optimizer state the update reads is part of training memory, not of the backward pass.

### Memory Traffic

^sec-ml-frameworks-anatomy-memory-traffic-c42b

Knowing which forward and backward kernels run lets us count the arithmetic work and memory traffic of the step to test whether it is bound by compute, HBM bandwidth, or host dispatch. To isolate the core forward and backward operators from [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.08 Anatomy of a Training Step#^sec-ml-frameworks-anatomy-forward-pass-7a1c|section 7.7.1]] and [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.08 Anatomy of a Training Step#^sec-ml-frameworks-anatomy-backward-pass-3e9d|section 7.7.2]], the count excludes input generation, bias additions and reductions, optimizer updates, and allocator bookkeeping. Within that boundary, each matrix multiplication reads two operands and writes one result, while loss and activation kernels follow the simplified operation-equivalent models stated next.

The traffic model assumes FP32 values occupying 4 bytes each. For `x @ W1`, it counts one read of the input matrix with shape `(32, 784)`, one read of the weight matrix with shape `(784, 128)`, and one write of the result with shape `(32, 128)`. Multiplying each shape’s dimensions, summing the three element counts, and multiplying by the element width gives the table’s 0.52 MB. The second matrix multiplication uses the same operand rule with its own shapes.

ReLU instead reads and writes each element of its `(32, 128)` tensor once, so its modeled traffic is twice that tensor’s element count times 4 bytes, yielding 32.8 KB. These counts describe the modeled operator-buffer boundary. They assume full operand reuse within each matrix multiplication and exclude extra layout copies, workspace, and repeated tile loads; cached operands can also reduce actual HBM reads. Saving a reference for backward does not itself copy a tensor. A physical layout conversion, when required, adds its own read and write traffic to these counts.

The backward products use the same read/read/write rule. The weight gradient `h.T @ dlogits` multiplies `(128, 32)` by `(32, 10)`; the hidden gradient `dlogits @ W2.T` multiplies `(32, 10)` by `(10, 128)`; and `x.T @ dz1` multiplies `(784, 32)` by `(32, 128)`. The first two each cost as much arithmetic as the second forward GEMM, while the third matches the first forward GEMM. No `(32, 128)` by `(128, 784)` product is needed because the raw input requests no gradient. The total dense matrix work is therefore 2.013× the forward dense work. This applies the input-gradient exception derived in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-derivative-calculation-process-edaa|Derivative calculation process]]** to this two-layer network.

The forward cross-entropy model assigns one operation-equivalent each to exponentiation, accumulation, and normalization per logit, and counts the logit read and saved-score write. For the nonlinear backward work, the ReLU model reads the saved activation and upstream gradient and writes a masked gradient. The simplified combined cross-entropy model reads saved probabilities and integer labels, then subtracts the target and scales by the batch mean to write the logit gradient. Actual loss implementations may split these operations across kernels. The resulting estimates, collected in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.08 Anatomy of a Training Step#^tbl-training-step-roofline|table 9]], make the arithmetic-intensity comparison reproducible without substituting for a measured memory-traffic profile.

| **Component**                       |                 **Modeled Work**                 | **Memory Traffic** | **Arithmetic Intensity** |
|:------------------------------------|:------------------------------------------------:|:------------------:|:------------------------:|
| **MatMul (x @ W1)**                 | $2 \times 32 \times 784 \times 128$ = 6.42 MFLOP |      0.52 MB       |      12.4 FLOP/byte      |
| **ReLU**                            |           $32{\times}128$ = 4.1 KFLOP            |      32.8 KB       |     0.125 FLOP/byte      |
| **MatMul (h @ W2)**                 | $2 \times 32 \times 128 \times 10$ = 81.9 KFLOP  |      22.8 KB       |      3.6 FLOP/byte       |
| **Cross-entropy (simplified)**      |                   ~0.96 KFLOP                    |       2.6 KB       |     0.375 FLOP/byte      |
| **Backward `dW2`**                  |                    81.9 KFLOP                    |      22.8 KB       |      3.6 FLOP/byte       |
| **Backward `dh`**                   |                    81.9 KFLOP                    |      22.8 KB       |      3.6 FLOP/byte       |
| **Backward `dW1`**                  |                    6.42 MFLOP                    |      0.52 MB       |      12.4 FLOP/byte      |
| **Backward nonlinear (simplified)** |                    4.7 KFLOP                     |      52.0 KB       |     0.091 FLOP/byte      |

Table 9: **Per-Operation Roofline Analysis**: Analytical work and buffer-traffic estimates separate the two-layer MLP’s matrix multiplications from its low-intensity elementwise and loss operations. Each GEMM counts two operand reads and one result write; backward includes only the requested gradients. Cross-entropy and pointwise derivative work use the simplified models stated in the text. These are operator-level estimates rather than measured device instruction or HBM-transaction counts.

^tbl-training-step-roofline

The arithmetic-intensity column helps predict each layer’s regime when compared with the target machine’s compute-to-bandwidth ratio. Matrix multiplications reuse operands far more than element-wise operations, but their shapes still determine whether they reach the compute roofline. Conversely, the forward ReLU and cross-entropy estimates perform negligible compute per byte transferred (0.125 FLOP/byte and 0.375 FLOP/byte), making them sensitive to memory bandwidth and, at small sizes, launch latency. In un-fused eager execution, each element-wise operation incurs a separate kernel dispatch and writes intermediate tensors to global-memory buffers between kernels; actual HBM traffic depends on caching.

The analytical model yields ~13.1 MFLOP of arithmetic work and ~1.2 MB of memory traffic for the operations included in the table. Dividing these quantities by peak H100 hardware rates determines the idealized lower bounds:

- ${T_{\text{compute}}} \approx$ 13.1 MFLOP/67 TFLOP/s FP32 ≈ 0.2 μs
- ${T_{\text{memory}}} \approx$ 1.2 MB/3.35 TB/s ≈ 0.4 μs
- Under a one-kernel-per-modeled-operator assumption, the 4 selected forward operators and 5 backward operators require 9 driver launches. Python dispatches each of the 4 forward operations individually, whereas `backward()` enters the C++ autograd engine once and launches all 5 backward kernels without returning to the Python interpreter between them, giving 5 Python entries in total. The illustrative host cost is therefore 5 $\times$ 10 μs plus 9 $\times$ 5 μs, or 95 μs.

This dispatch model excludes autograd traversal overhead, allocation, and the operations omitted from the table, and it also excludes the optimizer step, which is not small. An FP32 Adam update reads each parameter, its gradient, and the two moments Adam keeps for every parameter (running averages of the gradient and of its square), and writes three of them, 28 bytes per parameter, so the 101,770 parameters of this network move about 2.85 MB, more than the whole modeled forward and backward traffic. Counting its launches and the omitted Python calls only raises the host cost above this lower bound.

Host costs are added without overlap here, and a profile must still establish the actual launch count, particularly for loss kernels. Even so, in this model ${T_{\text{sw}}}$ exceeds the ideal lower bounds ${T_{\text{compute}}}$ and ${T_{\text{memory}}}$ by more than an order of magnitude, so the overhead ratio of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^eq-dispatch-overhead|equation 4]] sits far above 1 and the step is overhead-bound under these assumptions. This is the small multilayer perceptron (MLP) regime of notebook [7.2](https://mlsysbook.ai/vol1/07_frameworks/07_frameworks.html#nbk-frameworks-dispatch-tax), now reached from a real training loop. Profiling has a specific job here, which is to confirm that measured kernel times, achieved bandwidth, and host-device overlap match the model before acting on it.

When dispatch dominates, three mechanisms attack the launch overhead from different angles. Kernel fusion via `torch.compile` merges consecutive memory-bound operations into a single kernel, which avoids intermediate round-trips to HBM and collapses launch boundaries. Batch size scaling grows the arithmetic payload linearly while keeping dispatch overhead constant, which amortizes fixed launch latency across more compute work. Graph capture removes repeated Python work in captured regions and allows CUDA Graph replay to submit a captured launch sequence with less host overhead, without requiring the entire step to become one fused kernel.

### Dispatch to Hardware

^sec-ml-frameworks-anatomy-dispatch-hardware-5f60

The timing analysis in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.08 Anatomy of a Training Step#^sec-ml-frameworks-anatomy-memory-traffic-c42b|section 7.7.3]] followed the script’s `device="cuda"` placement on an H100, but the same eight lines of Python can target a CPU, a TPU, or Apple Silicon by changing the device placement to a supported backend ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.08 Anatomy of a Training Step#^tbl-framework-backends|table 10]]). Each backend maps common tensor semantics to silicon-specific primitives, so a single `loss.backward()` invocation routes to different execution pipelines depending on where its tensors live. Because differences in floating-point summation order, reduction trees, and non-deterministic atomic operations introduce numerical variation across backends, equivalence must be validated against explicit numerical tolerances rather than bitwise identity.

| **Hardware**      | **Backend library**                                                                                                                                                                                                                   | **Execution mechanism**                           |
|:------------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------|
| **CUDA GPU**      | cuBLAS ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-nvidia-cublas-10898670\|NVIDIA 2024]]; [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-choquette2021\|Choquette et al. 2021]])                           | GEMM kernels and CUDA streams for async execution |
| **CPU**           | Intel oneMKL or OpenBLAS ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-intelOneMKL\|Intel Corporation 2026]]; [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-openblasDocs\|OpenBLAS Project 2026]]) | Thread-level parallelism around optimized kernels |
| **TPU**           | XLA ([[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.14 Source References#^ref-GoogleXLA\|Google 2025]])                                                                                                                                         | Compilation to TPU-specific HLO operations        |
| **Apple Silicon** | Metal Performance Shaders                                                                                                                                                                                                             | MPS backend                                       |

^tbl-framework-backends

Implementation decisions such as device placement, batch size, and compilation mode cascade through execution, differentiation, and abstraction layers simultaneously. Treating the framework as an opaque mathematical interpreter rather than a hardware-aware scheduler hides these interactions until they surface as an idle accelerator or an out-of-memory failure.

**Systems Perspective 7.2: The three problems in action**

In D·A·M terms, the single training step exposes how the framework balances algorithm and machine:

- Execution: Eager mode preserves imperative line-by-line debugging at the cost of per-kernel launch and dispatch latency.
- Differentiation: Reverse-mode automatic differentiation retains intermediate forward activations in HBM to compute exact vector-Jacobian products in reverse topological order.
- Abstraction: Unified tensor APIs decouple model code from heterogeneous silicon, dispatching identical operations to cuBLAS, oneMKL, or XLA-compiled HLO programs.

Resolving the friction among these dimensions requires matching operator granularity to hardware rooflines: fusing operations to eliminate memory round-trips, scaling batches to amortize launch latency, and structuring tensors to saturate accelerator execution pipelines.

The step’s costs reduce to a handful of counting rules derived earlier in the chapter and collected in the chapter summary. These rules let a training or inference step be estimated on paper before it is profiled, by counting dispatched operations and comparing their overhead with device time, counting the passes an unfused elementwise chain makes over memory, checking whether a compiled artifact will run often enough to repay its compilation, sizing the activations that backward must keep, and timing every host-to-device copy.

Applied to the two-layer MLP, the dispatch rule gives the overhead-bound verdict reached above. The elementwise-traffic rule explains why fusing its bias and ReLU kernels removes a round trip. The saved-activation rule bounds what activation checkpointing could save. Every one of these costs exists whichever framework runs the step; frameworks differ in which of them they make easy to see and to reduce. TensorFlow, PyTorch, and JAX each answer the three framework problems in a different way.
