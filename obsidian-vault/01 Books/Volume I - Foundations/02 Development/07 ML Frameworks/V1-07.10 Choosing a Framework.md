# V1-07.10 Choosing a Framework

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks|V1-07 ML Frameworks]]

^sec-ml-frameworks-selecting-framework-2949

Those differences in where state lives and what the compiler sees become concrete obligations once a team commits to one framework for a project that must ship to a particular device. Framework selection decides which framework a team develops in, given the model it must express, the team that must maintain it, and the targets it must eventually run on. Development framework and deployment runtime need not be the same system: a model can be developed in PyTorch or TensorFlow and exported to a compact runtime for the device. The choice of that inference runtime is a serving decision, developed in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-inference-runtime-selection-5eef|Inference Runtime Selection]]**. The development framework still has to reach it, so the deployment target acts as a filter on which frameworks are viable.

Suppose a team deploys a fixed-shape vision model to a CPU-only embedded Linux device, with a 20 ms p99 (99th-percentile, **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.07 Inference Benchmarks#^sec-benchmarking-latency-tail-latency-5cde|Latency and tail latency]]**) inference-latency target under a specified load and a 256 MB model-and-runtime memory budget. Assume target-device trials with matching inputs, batch size, precision, and numerical tolerances establish two viable paths. PyTorch development with ONNX Runtime has 18 ms p99 latency and 140 MB peak memory use, while TensorFlow development with TensorFlow Lite has 15 ms p99 latency and 90 MB peak memory use. A path that depends on a GPU-only runtime fails the hardware filter even if its latency elsewhere is lower. These are hypothetical project measurements, not general performance rankings. The selection must now distinguish a feasible path from a worthwhile migration.

The embedded project has already fixed the deployment target, but it leaves two choices open: which development environment the team can maintain and which compatible export path meets its budget. Eager development and compiled deployment can coexist along either path, so the team need not trade away its debugging workflow to obtain a compact inference runtime.

**Systems Perspective 7.3: Framework selection constraints**

Rather than seeking the “best” framework, effective selection first eliminates candidates that cannot satisfy hard constraints: deployment target, required operations, and compiler path. Only then should soft preferences such as team pipeline, migration cost, development speed, ecosystem, and performance beyond the target rank the survivors.

### Framework Selection Criteria

^sec-ml-frameworks-model-requirements-2e01

The two hypothetical measurements establish latency and memory feasibility only for the tested model and inputs. A defensible choice also checks operator semantics, software dependencies, and hardware coverage for each candidate path, PyTorch exported through ONNX to ONNX Runtime and TensorFlow converted to TensorFlow Lite. [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.10 Choosing a Framework#^tbl-tf-comparison|Table 12]] shows what those filters examine, using TensorFlow, whose three variants span all three deployment tiers, from full TensorFlow through TensorFlow Lite to TensorFlow Lite Micro. Both of the project’s candidates target the middle, mobile-and-embedded tier, so each subsection below applies its filter to the two candidates directly. The table’s delegates are TensorFlow Lite plug-ins that hand supported operators to an accelerator such as an NPU.

|                                    | TensorFlow                                | **TensorFlow Lite**                        | **TensorFlow Lite for Microcontrollers**     |
|:-----------------------------------|:------------------------------------------|:-------------------------------------------|:---------------------------------------------|
| **Training**                       | Yes                                       | Limited                                    | No                                           |
| **Inference**                      | Yes                                       | Yes                                        | Yes                                          |
| **Operator Coverage**              | Broad                                     | Inference-focused                          | Model-selected subset                        |
| **Native Lower-Precision Tooling** | Yes                                       | Yes                                        | Yes                                          |
| **Needs an OS**                    | Yes                                       | Yes                                        | No                                           |
| **Model Access**                   | Filesystem or service                     | Platform-specific storage mapping          | Platform-specific compiled or mapped storage |
| **Accelerator Support**            | Yes                                       | Delegates                                  | Optimized kernels and integrations           |
| **Base Binary Size**               | Build- and package-dependent              | Build- and delegate-dependent              | Model- and operator-selection-dependent      |
| **Base Memory Footprint**          | Model-, runtime-, and allocator-dependent | Model-, delegate-, and allocator-dependent | Fixed arena plus runtime state               |
| **Optimized Architectures**        | x86, TPUs, GPUs                           | Arm Cortex-A, x86                          | Arm Cortex-M, DSPs, MCUs                     |

Table 12: **TensorFlow Variants Across Deployment Tiers**: The rows group what each variant can express (first four), what it requires of the platform (middle three), and what hardware and footprint it targets (last three). Training capability disappears across the tiers while inference and lower-precision tooling survive, which leaves operator coverage as the discriminating capability: broad in TensorFlow, inference-focused in TensorFlow Lite, and reduced to the operators one model selects in TensorFlow Lite Micro. Binary size and memory footprint depend on the build, selected operators, delegates, model, and runtime configuration rather than on the variant alone.

#### Model Requirements

^sec-ml-frameworks-model-requirements-ca8b

For the fixed-shape vision model, the first filter is successful conversion of every required operation with acceptable numerical results. On the PyTorch path, every operator in the exported graph needs an ONNX operator and an ONNX Runtime CPU kernel; on the TensorFlow path, every operator must convert to one that TensorFlow Lite supports. Training support is needed in the development framework but not in the deployed runtime. TensorFlow, TensorFlow Lite, and TensorFlow Lite Micro expose different operator and training capabilities. A missing inference operator, by contrast, can invalidate the deployment path even when the rest of the graph fits, which is why operator coverage is the discriminating row among the capabilities in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.10 Choosing a Framework#^tbl-tf-comparison|table 12]].

**Systems Perspective 7.4: Dynamic vs. static computational graphs**

The static-vs.-dynamic graph distinction (examined in [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-problem-e1e1|section 7.3]]) has direct implications for model requirements analysis. Static graphs require control flow and dynamic behavior to be represented in forms understood by the graph runtime, which enables ahead-of-time optimization for deployment. Eager execution follows ordinary Python control flow directly, while graph-capture paths such as `torch.compile` and `tf.function` recover optimization opportunities when they can represent the executed program.

#### Software Dependencies

^sec-ml-frameworks-software-dependencies-5245

Embedded Linux supplies operating-system services, so an OS dependency does not eliminate either candidate in this project. A bare-metal microcontroller would impose a different filter, which the TensorFlow Lite for Microcontrollers column of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.10 Choosing a Framework#^tbl-tf-comparison|table 12]] describes. TensorFlow Lite Micro links a selected operator set into a small C/C++ application and can read a model FlatBuffer compiled into flash, which removes the need for a POSIX filesystem or heap allocation during inference, savings that matter on bare metal but give a Linux device no reason to choose it. The platform rows of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.10 Choosing a Framework#^tbl-tf-comparison|table 12]] separate that requirement from model access and accelerator integration; availability of a runtime on one tier does not imply availability on another.

The CPU-only project needs a supported CPU implementation of every required operator in both ONNX Runtime and TensorFlow Lite; it cannot count on a mobile NPU delegate or a server GPU backend.

#### Hardware Constraints

^sec-ml-frameworks-hardware-constraints-e449

A runtime that supports the operating system still has to fit alongside the model, working buffers, and application. The hardware rows of [[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.10 Choosing a Framework#^tbl-tf-comparison|table 12]] separate supported processor families from footprint, which depends on the actual build. The project must compare peak memory for the deployed configuration, not the size of its weight file or an empty runtime package.

The supplied trials already include model-and-runtime peak memory, so both candidates pass the project’s capacity filter. That conclusion must be revisited when input shapes, selected operators, delegates, or runtime versions change. On a fixed-arena target, the analogous check is whether the planned tensor and scratch buffers fit with the rest of the application.

#### Production-Ready Evaluation Factors

^sec-ml-frameworks-productionready-evaluation-factors-e088

Satisfying model requirements, software dependencies, and hardware constraints establishes technical feasibility; production viability also depends on what the development framework’s toolchain supports. If the deployment uses reduced precision, the framework must support the chosen path. The options are post-training quantization (PTQ), which converts an already-trained model using a small representative calibration dataset to set value ranges, or quantization-aware training (QAT), which simulates low-precision arithmetic during training to recover accuracy before deployment. Toolchain stability matters as much: whether saved models remain loadable across framework and runtime updates, and whether the framework exposes the profiling hooks needed to confirm that the deployed model still meets its latency target.

↪ Post-training quantization, its calibration, and quantization-aware training are developed in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-precision-reduction-strategies-db83|Quantization methods]]**.

### Development Support and Long-Term Viability Assessment

^sec-ml-frameworks-development-support-longterm-viability-assessment-d1d7

Once both paths pass the technical filters, the remaining decision concerns the team’s ability to maintain them. The project already has PyTorch models and an ONNX export pipeline. Adopting another development stack would add conversion validation, new debugging practices, and another set of runtime dependencies even though both candidates meet the deployment limits.

Custom C++ or CUDA operators, specialized serialization, and vendor compiler passes increase the cost of later migration. Preserving an exit path means isolating framework-specific ingestion and operator code and testing the intended export format throughout development. These commitments belong in the selection decision because the shortest inference time does not account for the work needed to keep the model deployable.

Because both surviving paths meet the stated runtime limits, the team selects PyTorch with ONNX Runtime, the stack it already maintains. The measured path satisfies deployment requirements without introducing a second development stack. The faster TensorFlow Lite path remains viable, but its unused latency and memory advantage does not by itself justify migration. The decision depends on retaining that headroom as the model changes. Before committing, the team must check export coverage and numerical tolerances across representative inputs and repeat the latency check under expected contention; a later operator change or tighter latency target can invalidate the choice. The choice follows the project’s constraints and maintenance costs; a different team or deployment envelope can favor the other viable path.

The worked selection turned on constraints that no benchmark table records: export coverage, numerical tolerance, the team’s existing pipeline, and the cost of a second stack. Engineers who reason from benchmark headlines or general-purpose programming habits fall into predictable traps.
