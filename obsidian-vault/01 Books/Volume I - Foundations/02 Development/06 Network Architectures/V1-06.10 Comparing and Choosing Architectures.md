# V1-06.10 Comparing and Choosing Architectures

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures|V1-06 Network Architectures]]

^sec-network-architectures-architecture-selection-framework-a442

The three requests that opened this chapter can now be costed in numbers. A single ResNet-50 frame performs about 8.2 GFLOP of arithmetic against 102.2 MB of FP32 weights, and each convolutional filter is reused across its feature map, creating opportunities to keep arithmetic units busy. A single GPT-2 token at batch size one performs about 3 GFLOP/token against 3 GB of FP16 weights. Streaming those weights once gives a weight-only arithmetic intensity of roughly 1 FLOP/byte, making bandwidth a likely limit. A DLRM request gathers a handful of embedding rows from tables totaling 100 GB, more than the accelerator’s 80 GB of memory, so before any question of speed arises the system must decide where those tables live.

The silicon is identical in all three cases, but the demands differ. Convolutional reuse favors arithmetic throughput, streamed token projections stress bandwidth, and oversized embedding tables impose a capacity constraint that decides which bandwidth their lookups pay. The iron law (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|Iron Law of ML Systems]]**) then predicts which term dominates, given the execution conditions and machine balance.

Each of those costs is part of a family’s cost signature, and each comes from a counting rule derived in that family’s section. [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-nn-architectures-cost-formulas|Table 7]] collects the rules in exact form, so that a new model can be estimated on paper in the same order: count the weights, count the multiply-accumulates, count the bytes that must move or stay resident, then compare those counts with the machine.

| **Building block**                  | **Weights**                                                | **Multiply-accumulates per example**                                                           | **Bytes that move or stay resident**                                                        |
|:------------------------------------|:-----------------------------------------------------------|:-----------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------|
| **Dense layer**                     | ${d_{\text{in}}} {d_{\text{out}}}$                         | ${d_{\text{in}}} {d_{\text{out}}}$                                                             | Every weight read once per batch, so weight-only intensity grows with batch size            |
| **Convolution layer**               | ${K}^2 {C_{\text{in}}} {C_{\text{out}}}$                   | ${H_{\text{img}}} {W_{\text{img}}} {K}^2 {C_{\text{in}}} {C_{\text{out}}}$                     | Output activations, ${H_{\text{img}}} {W_{\text{img}}} {C_{\text{out}}}$ values per example |
| **Depthwise separable convolution** | ${K}^2 {C_{\text{in}}} + {C_{\text{in}}} {C_{\text{out}}}$ | ${H_{\text{img}}} {W_{\text{img}}} ({K}^2 {C_{\text{in}}} + {C_{\text{in}}} {C_{\text{out}}})$ | Same activations as a standard layer for far fewer operations                               |
| **Recurrent step**                  | ${d}^2 + {d} {d_{\text{in}}}$                              | ${d}^2 + {d} {d_{\text{in}}}$ per step, ${S}$ steps in order (four times for an LSTM)          | State of ${d}$ values at inference; ${S} {d}$ kept for training                             |
| **Transformer block**               | $4{d}^2 + 2{d} {d_{\text{ff}}}$                            | $4{S}{d}^2 + 2{S}^2{d} + 2{S}{d}{d_{\text{ff}}}$ for ${S}$ tokens                              | ${S}^2$ scores per head if materialized                                                     |
| **Decoding one token**              | All of the model’s weights                                 | About one per weight                                                                           | Every weight read per step, plus a KV cache of $2{N_L}{d}$ values per token                 |
| **Embedding lookup**                | Rows $\times$ vector width                                 | Almost none (rows are copied)                                                                  | Whole table resident: rows $\times$ width $\times$ bytes per value                          |

Table 7: **Cost Formulas by Building Block**: Counting rules for inference, one per building block, in the notation of the family sections. A FLOP count is twice the multiply-accumulate count; arithmetic intensity divides FLOPs by bytes moved; and a step can finish no faster than the larger of its FLOPs divided by the peak rate and its bytes divided by the bandwidth. For GPT-2 XL, the KV-cache rule gives 307.2 KB per token in FP16, the figure quoted in the transformer section.

### Arithmetic Intensity Across Workloads

^sec-network-architectures-understanding-arithmetic-intensity-ade5

Each family section measured reuse in its own terms: filters reused across a feature map, weights streamed once per decoded token, rows gathered from a table. Arithmetic intensity, the FLOP/byte ratio set against a machine’s balance, puts them on one scale and shows whether each workload is likely to be compute or memory bound.

↩︎ Arithmetic intensity and the system balance it is compared against are established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^sec-ml-systems-system-balance-hardware-96ab|System Balance and Hardware]]**.

The intensities in [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-lighthouse-comparison|table 8]] are a weight-only proxy rather than a complete measurement of main-memory traffic. Each divides floating-point work by FP32 model-weight bytes, omitting activation, intermediate, and KV-cache traffic. Batching can amortize weight traffic across examples or tokens, while additional state movement can lower realized intensity. **[[05 Reference/Volume I - Foundations/V1 Algorithm Foundations#^sec-appdx-algorithm-foundations-computational-complexity-cheat-sheet-0c6c|Operation cost reference]]** gives the per-operation FLOP and parameter formulas used in the proxy. Under these assumptions ResNet-50’s proxy exceeds GPT-2 XL’s by roughly 160×, the widest gap among the lighthouses.

The intensity proxy is one input to architecture selection. Deployment constraints extend beyond the FLOP-to-byte ratio, and batch size, precision, sequence length, and target hardware decide whether the proxy predicts the deployed bottleneck. [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-lighthouse-comparison|Table 8]] sets the proxy beside parameter footprint, inference cost, and the governing hardware constraint for all five canonical workloads: compute throughput, memory bandwidth, memory capacity, latency, and power. For compute- and bandwidth-bound workloads, the iron law directly maps the primary bottleneck to operations (${O}$) or data movement (${D_{\text{vol}}}$). For capacity-, latency-, and power-constrained workloads, physical boundaries dictate where and within what budget those operations must execute, determining which optimization strategies prove effective.

| **Model**        | **Domain**  | **Params** | **FLOPs/Inf** | **Memory** | **Intensity (weight-only)** | **Bottleneck** | **Role in Textbook**                   |
|:-----------------|:------------|:----------:|:-------------:|:----------:|:---------------------------:|:---------------|:---------------------------------------|
| **ResNet-50**    | Vision      |   25.6M    |   8.2 GFLOP   |  102.2 MB  |       80.2 FLOP/byte        | Compute        | Dense vision throughput                |
| **GPT-2 XL**     | Language    |    1.5B    | 3 GFLOP/token |    6 GB    |       0.50 FLOP/byte        | Mem. Bandwidth | Token-by-token serving                 |
| **DLRM**         | Recommender |    25B     |      Low      |   100 GB   |             n/a             | Mem. Capacity  | Embedding tables and capacity planning |
| **MobileNetV2**  | Edge Vision |    3.5M    |   600 MFLOP   |   14 MB    |       42.8 FLOP/byte        | Compute        | Depthwise convolutions and efficiency  |
| **KWS (DS-CNN)** | Audio       |    200K    |   20 MFLOP    |   800 KB   |        25 FLOP/byte         | Power          | Always-on power budget                 |

Table 8: **Lighthouse Model Comparison**: Quantitative characteristics and analytical roles of the five canonical workloads. Memory is FP32 weight storage, and FLOPs are per inference except for GPT-2 XL, which is quoted per generated token; the DLRM row reports embedding-table entries rather than dense parameters. Intensity is the weight-only FP32 proxy (FLOPs per weight byte), which omits activation and KV-cache traffic; it is not defined for DLRM’s embedding lookups. The bottleneck column indicates the primary system constraint each model reveals: compute-bound models like ResNet stress arithmetic throughput, while bandwidth-bound models like GPT-2 stress memory transfer rates.

^tbl-lighthouse-comparison

Architecture selection is ultimately an engineering trade-off between math $({O})$ and memory movement $({D_{\text{vol}}})$. The mechanisms behind the intensities in [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-lighthouse-comparison|table 8]] explain why each lighthouse sits where it does on the intensity spectrum. ResNet-50 earns its high intensity because convolutional layers reuse each weight many times across the spatial dimensions of an image (individual deeper ResNet layers reach 100–200+ FLOP/byte). Arithmetic throughput becomes the limit when effective intensity exceeds the target machine’s compute-to-bandwidth balance. GPT-2 sits at the opposite extreme during batch-one decoding with streamed weights, because each projection loads weights for one token’s matrix-vector product, making bandwidth a likely limit. MobileNet lands between the two at the whole-model level, with individual depthwise layers falling lower once activation traffic is included. The comparison table’s compute entry describes that whole-model average; MobileNetV2’s own profile ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.04 CNNs Spatial Pattern Processing#^tbl-nn-architectures-mobilenet-profile|table 3]]) names memory access and dispatch overhead instead, because single-image latency is paid layer by layer and its depthwise layers sit below the machine’s balance. Depthwise separable convolutions reduce total ${O}$ but move more data relative to that work, which fits mobile hardware well yet often leaves the matrix units of high-end GPUs idle.

**Checkpoint 6.7: Arithmetic intensity and architecture**

Match the architectural choice to its systems implication:

**One accelerator, three requests**: can you say which iron-law term limits a batched ResNet-50 frame, a batch-one GPT-2 token, and a DLRM lookup, and name one change that would move each?

**Batching**: why does batching move the dense-layer and decode workloads toward the machine’s balance point while leaving the embedding gather’s bottleneck in place?

Comparing this spectrum with the target machine’s balance helps determine whether faster arithmetic or faster memory would improve performance. The roofline model ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-williams2009|Williams et al. 2009]]) plots achievable throughput against arithmetic intensity to show where a workload turns from memory bound to compute bound. This chapter needs only the comparison introduced with system balance, a workload’s intensity set against the machine’s ratio of peak compute to memory bandwidth. The full construction, including the ridge point of an H100 and how the same operation falls on either side of it, is collected for reference in **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-concrete-example-a100-analysis-5b30|A concrete example: The H100 analysis]]**.

↪ The roofline model’s analytical treatment, from the memory-bound slope to the ridge point, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]**.

Intensity is one column of a fuller profile. Persistent state, per-request state, the axis along which the work parallelizes, and the iron-law term that dominates complete the comparison.

The parameter and activation columns of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-nn-architectures-machine-demands|table 9]] decide how data reaches the arithmetic units, and the pattern of access matters as much as the volume. Three patterns cover the table. Sequential access, the streaming of contiguous weight rows in an MLP layer or a transformer projection, lets memory deliver long uninterrupted runs of bytes, so it approaches the memory’s peak bandwidth. Strided access, which a convolution produces when its window steps across a layout that does not keep the window contiguous, fetches whole blocks of memory to use only a fraction of each. The im2col lowering ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.04 CNNs Spatial Pattern Processing#^sec-network-architectures-computational-mapping-824c|section 6.3.3]]) moves that gather into a separate copy pass so the matrix multiply itself reads sequentially, at the cost of up to ${K}^2$-fold duplication (because overlapping sliding windows copy the same input pixels into multiple rows).

Random access, the third pattern, characterizes the DLRM row. Sparse IDs index arbitrary rows across multi-gigabyte tables, so the next row cannot be predicted from the last, the memory system cannot fetch it early, and each lookup waits out the full memory latency unless many concurrent requests are in flight. Caching the popular rows is what reduces those off-chip waits. Attention is not random access despite its content-dependent weights, because its queries, keys, and values sit in contiguous tensors that tiled kernels stream through on-chip SRAM.

Whether an access incurs DRAM traffic at all depends on the working set, the data the execution units need at once. Small layers, such as the $784{\times}128$ reference layer at 401.4 KB in FP32, fit in on-chip SRAM. Production-width layers of tens of megabytes do not, which is why unbatched MLP inference and transformer decode stream their weights from off-chip memory on every request. Accelerators answer both ends of the table with memory hierarchy rather than arithmetic. HBM, DRAM stacked beside the processor, supplies the streaming rows more than an order of magnitude faster than ordinary DRAM. Multi-megabyte on-chip SRAM, often a scratchpad that software fills explicitly, lets compilers stage blocks of data so that reuse happens on chip (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** develops this hierarchy). The intensity column measures how much a family can profit from that staging, and it doubles as an energy column.

**Systems Perspective 6.2: Reuse sets each family's energy cost**

Moving a 32-bit value from DRAM costs far more energy than one arithmetic operation on it (**[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^tbl-energy-movement-cost|Energy Cost of Moving vs. Computing on a 32-Bit Value]]** in **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|The feeding problem]]**). Against the full multiply-accumulate that a dense layer performs, the gap is about 139×, the basis used for the MLP above. How much of that cost each family pays depends on reuse, so low-intensity rows are energy-dominated by DRAM traffic. An unbatched MLP or a decode step loads each weight once per request and spends most of its energy moving it. A CNN amortizes each filter load over ${H_{\text{img}}}\times {W_{\text{img}}}$ applications, so the locality that makes it compute bound also makes it energy efficient, unless a fully materialized im2col buffer inflates temporary traffic by up to ${K}^2$. An RNN keeps its compact state in SRAM but idles execution units across serial steps, which raises energy per token. Tiled attention keeps score blocks on chip, so its energy tracks matrix multiplication rather than DRAM round-trips.

The parallel-axis column determines how data must move among processing elements once the work is spread out. Four data movement patterns (broadcast, scatter, gather, and reduction; [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^fig-collective-comm|figure 16]]) govern how tensors travel among processing elements, whether those are units on one chip or several accelerators in one server. Batch parallelism in MLPs, CNNs, and prefill broadcasts stationary weight tiles to many units, each working on a different example or position, and compilers tile loops to reuse each broadcast value as often as possible. Spatial and model partitioning scatter a tensor across tiles or devices.

Gathers and reductions collect what broadcast and scatter spread out. DLRM gathers embedding rows from wherever the sharded tables live, and each attention query gathers keys and values from every position in its sequence. Reductions combine values through sums or maxima (softmax denominators, normalization statistics, and the summing of gradients across accelerators that each trained on a different slice of the batch). Tree-structured reduction hardware finishes a reduction over ${n}$ values in $\mathcal{O}(\log {n})$ stages rather than $\mathcal{O}({n})$. The rows with a serial axis, RNNs and decode, are the rows these collectives cannot rescue, because no amount of broadcast or reduction bandwidth shortens a dependency chain.

![[90 Assets/Volume I/06 Nn Architectures/Generated Figure 33675d0436.svg]]

Figure 16: **Data Movement Primitives**: Four fundamental patterns govern information flow in neural network computation. Broadcast (top-left) replicates a single value to all destinations, used when sharing weights across batch elements. Scatter (top-right) distributes distinct elements to different destinations, enabling work partitioning. Gather (bottom-left) collects distributed values to a single location, as in attention pooling. Reduction (bottom-right) combines multiple values through aggregation (sum, max), appearing in gradient synchronization and attention scoring. Because moving data costs more than computing on it, these patterns are primary optimization targets.

^fig-collective-comm

The last column applies the iron law under each row’s execution assumptions. When effective intensity exceeds the machine’s balance and parallel work is sufficient (batched CNNs, prefill), the compute term ${O}/({R_{\text{peak}}}\,{\eta_{\text{hw}}})$ dominates. Below that balance (streamed small-batch MLPs, decode), the data term ${D_{\text{vol}}}/{\text{BW}}$ dominates, favoring fewer transferred bytes, more reuse, or higher bandwidth. RNNs add a serial chain of state updates. Faster arithmetic, faster memory, and reduced launch overhead $({L_{\text{lat}}})$ can shorten each step but cannot remove the dependency. DLRM adds a constraint that sits in front of the equation. Capacity decides where the tables live and thus which bandwidth the data term pays.

ResNet-50, GPT-2, and DLRM isolate the compute, data, and capacity regimes. MobileNetV2 and KWS share the CNN row, with depthwise layers pulling their intensity down. MobileNetV2 stands for a single-image latency budget and KWS for a power budget, deployment budgets that bound the whole execution rather than one term. No lighthouse occupies the RNN row, whose serial chain the recurrent family section analyzes directly.

### Shared Building Blocks

#### Dense Projections

^sec-network-architectures-evolution-perceptron-multilayer-networks-d06e

General matrix multiplication is the one primitive every row of the profile shares. Inside every transformer block it is the fused query, key, and value projection, the score and context products of attention, and the feedforward layer. It is also the $1{\times}1$ pointwise convolution in MobileNets, the input and recurrent projections inside every RNN cell (fused into one wider product in an LSTM), and the bottom and top MLPs of DLRM. Convolution reaches the same path through the im2col patch unfolding of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.04 CNNs Spatial Pattern Processing#^fig-im2col-diagram|figure 5]] or through implicit GEMM, and dedicated matrix engines, such as GPU Tensor Cores and the systolic arrays of TPUs, exist because this one primitive dominates the operation count of nearly every workload. What does not lower onto GEMM is the memory-bound remainder. Embedding gathers copy rows without arithmetic, and elementwise steps such as residual additions, normalization, and softmax do little work for each byte they move. Depthwise filters also fall outside the GEMM path, because each works on one channel alone and cannot fill a matrix engine.

The hardware cost of matrix multiplication depends on shape rather than on the family that invokes it. Batching therefore acts on every family that reaches this path as it acts on the dense layer measured in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-implementation-optimization-considerations-f2ca|Implementation and optimization considerations]]**, converting a matrix-vector product into a matrix-matrix product with greater reuse. The higher intensity can cross the target machine’s balance point, which is why batch size changes the modeled regime of three rows of the table. An embedding gather gets no such reuse from batching, because each sample reads its own rows and two samples share a fetch only when they hit the same hot row.

Dense connectivity supplies a common cost baseline, but each family changes a different part of the workload. Convolution shares filters across spatial positions; attention combines dense projections with pairwise interactions; and embedding lookup replaces an arithmetic transformation with an indexed read. Their parameter storage, operation counts, and transferred bytes must therefore be compared separately, as in [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-nn-architectures-machine-demands|table 9]]. Dense projections remain inside all these architectures, so improvements to their execution can transfer between families.

#### Gating, Routing, and the Transformer Block

^sec-network-architectures-routing-transformer-block

Gating generalizes beyond recurrence as the basic mechanism for data-dependent routing. Highway Networks ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-srivastava2015highway|Srivastava et al. 2015]]) used gates to choose how much of each input passes through a transformation and how much bypasses it, an early form of the residual shortcut. Encoder-decoder attention ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-bahdanau2015neural|Bahdanau et al. 2015]]) computes a dynamic routing distribution over input representations, and in transformers the softmax attention weights act as data-dependent routing coefficients that decide how features aggregate across tokens. Mixture-of-experts architectures extend the idea by sending each token to a few of many feedforward subnetworks, called experts ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-jacobs1991adaptive|Jacobs et al. 1991]]; [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-shazeer2017outrageously|Shazeer et al. 2017]]). The hardware cost of gating is irregularity. Dense attention keeps static tensor shapes even though its weights vary per token, but sparse attention, expert routing, and dynamic graph execution introduce data-dependent control flow and runtime tensor sizes that defeat static memory allocation and balanced work dispatch.

↪ The irregular memory access that unstructured sparsity, embedding lookups, and dynamic routing impose on hardware is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^sec-hardware-acceleration-irregular-memory-access-c6ec|Irregular memory access]]**.

A transformer block combines four of these building blocks. In the encoder tower of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^fig-transformer|figure 12]], residual paths bypass each multi-head attention and feed-forward sub-layer to preserve gradient flow through deep stacks, dense GEMM projections carry the attention and feedforward transformations, LayerNorm or RMSNorm stabilizes activations around each sub-layer, and softmax attention weights gate information across positions. What the transformer changed was the dependency structure. Replacing recurrence with all-to-all attention cut the sequential depth for tokens to interact from $\mathcal{O}({S})$ steps to $\mathcal{O}(1)$, which let the other three blocks run at full width on parallel hardware. Vision Transformers[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn28|²⁸]] carry the same block set to images ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-dosovitskiy2021image|Dosovitskiy et al. 2021]]).

This portability separates optimizations that transfer from those that do not. GEMM tiling and mixed-precision arithmetic help every row of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-nn-architectures-machine-demands|table 9]], residual memory management helps every deep network, and normalization kernel fusion helps CNNs and transformers alike. Attention-specific kernels remain tied to attention’s memory pattern, but even they are built from the same GEMM and memory-access primitives. The profile and the building blocks describe what each family costs; choosing among families for a particular deployment requires turning those costs into a procedure.

### Architecture Selection Framework

^sec-network-architectures-decision-framework-a889

Turning those family profiles into a selection procedure starts from deployment constraints, which eliminate architectures that look competitive on unconstrained accuracy benchmarks. A structural mismatch chosen here cannot be rescued later by compiler optimization or kernel tuning. A battery-powered edge sensor bounded by milliwatts of thermal envelope and a data-center ranking service bounded by tens of milliseconds of tail latency rule out opposite rows of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-nn-architectures-machine-demands|table 9]] before training ever begins. Engineering teams nonetheless often default to architectures by popularity, deploying over-parameterized transformers where a compact convolutional network would suffice or selecting models whose state exceeds on-device memory. In D·A·M terms, architecture selection chooses the algorithm ($\text{A}$) that bridges the structure of the data ($\text{D}$) to the budgets of the machine ($\text{M}$): memory capacity, memory bandwidth, compute throughput, and thermal envelope.

![[90 Assets/Volume I/06 Nn Architectures/Nn Architectures Algorithm Axis d0b8247fab.svg]]

*D·A·M locator triangle with three nodes connected by violet edges: D (Data) at top and M (Machine) at lower right shown gray, A (Algorithm) at lower left filled solid orange. The Algorithm node is highlighted.*

*Architecture selection turns on the algorithm axis, bridging data to machine.*

Selection begins with data-to-architecture mapping, matching the symmetries of the input to an operator family. The useful strength of an inductive bias depends on the task ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.02 Architectural Principles#^sec-network-architectures-architectural-principles-engineering-tradeoffs-362e|section 6.1]]). CNNs impose local connectivity, weight sharing, and translation equivariance, reducing parameter volume and exposing reuse for grid-like data. RNNs impose temporal recurrence, bounding inference state across sequence lengths at the cost of serialization. Transformers use content-based attention, gaining flexible interactions while paying for dense quadratic score computation. MLPs impose no specific spatial or temporal connectivity pattern, leaving those relationships to be learned.

Ordered by the strength of their assumptions, the families therefore run from CNNs through RNNs and transformers to MLPs. RNNs, absent from the margin sketch beside the inductive-bias definition, sit between CNNs and transformers, because recurrence fixes the order in which information flows but not which earlier positions matter. The stronger the prior, the fewer samples and the less computation a matching task needs, and the more a mismatched task loses, because a strong prior can exclude useful solutions as easily as it excludes useless ones. Model selection must test both predictive fit and what the chosen model costs to run in production, and the Netflix Prize shows what happens when only the first test is run.

**War Story 6.1: The ensemble Netflix did not ship (2009)**

**Context**: Netflix awarded its \$1M Grand Prize in 2009 for a 10 percent improvement in recommendation accuracy ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-johnston2012netflixprize|Johnston 2012]]).

**Mechanism**: Bringing the winning improvement, an ensemble that blended the predictions of many separately trained models, into production required substantial engineering effort just as Netflix’s business was shifting from mailed DVDs to streaming. That shift also produced richer viewing signals and changed what personalization needed to optimize.

**Impact**: The additional accuracy did not justify the production effort, so Netflix did not deploy the Grand Prize code.

**Fix**: Netflix retained two algorithms from the earlier Progress Prize and redirected its recommendation work toward streaming-era personalization.

**Systems lesson**: An offline metric gain is only valuable when its integration cost and objective still match the production system.

[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^fig-dnn-fm-framework|Figure 17]] formalizes this selection pipeline as a multi-stage triage tree. Candidate architectures route first by input data structure (text, sequences, spatial grids, or tabular features) and then pass through a sequence of checks for memory capacity, compute budget, inference latency, accuracy targets, and hardware deployment readiness. High-cardinality recommendation workloads sit outside this dense flowchart and route to the sparse embedding family ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.09 Sparse Architectures Recommendation Systems#^sec-network-architectures-sparse-architectures-recommendation-systems-5d19|section 6.8]]) before applying the same memory, compute, speed, accuracy, and deployment checks. If any constraint fails, the decision loop routes execution back to scale the model down, increase its capacity when accuracy falls short, or substitute an alternative architecture family.

![[90 Assets/Volume I/06 Nn Architectures/Generated Figure 79abc595ed.svg]]

Figure 17: **Architecture Selection Decision Framework**: A systematic flowchart for choosing dense neural network architectures based on data characteristics and deployment constraints. The process begins by identifying the data type (text, sequences, images, or tabular features) to select initial candidates (transformers, RNNs, CNNs, or MLPs), then iteratively evaluates memory budget, computational cost, inference speed, accuracy targets, and hardware compatibility. High-cardinality recommendation workloads are handled separately by the sparse-embedding family, DLRM ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.09 Sparse Architectures Recommendation Systems#^sec-network-architectures-sparse-architectures-recommendation-systems-5d19|section 6.8]]), then re-enter the same constraint checks.

^fig-dnn-fm-framework

The framework executes in three ordered phases, with model compression as the systematic way to scale a candidate down when it fails a budget:

1.  **Data symmetry identification ($\text{D}$)**: Identify structural symmetries and invariances in the input data. Spatial locality routes candidates to CNNs; temporal sequence structure to RNNs; unconstrained cross-token dependency to transformers; tabular features without spatial geometry to MLPs; and high-cardinality categorical IDs to sparse embedding tables.
2.  **Progressive physical constraint filtering ($\text{A} \times \text{M}$)**: Filter candidate models against hardware budgets: static parameter storage in flash/DRAM, peak dynamic activation footprint in SRAM/HBM, arithmetic intensity against the hardware roofline, tail latency deadlines, and the device’s power envelope. A violation requires scaling down model width or depth, applying quantization and compression, or switching to a lower-overhead architecture family.
3.  **Empirical capacity and deployment validation**: Verify that candidate capacity meets target accuracy on representative evaluation distributions. If predictive accuracy falls short, scale model capacity and re-evaluate physical hardware constraints. If target accelerator hardware cannot sustain the required arithmetic throughput or memory bandwidth, select an alternative architecture rather than relying on marginal hyperparameter adjustments.

Kernel-level choices refine this decision. Im2col or direct convolution, fused normalization, and IO-aware tiled attention (**[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-flash-attention-ioaware-attention-optimization-3da0|FlashAttention: IO-aware attention optimization]]**) change realized traffic and utilization, and can shift which iron-law term dominates; **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks#^sec-ml-frameworks|ML Frameworks]]** and **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** develop them. Architectural dependencies still matter. Batching independent recurrent sequences or fusing their operations reduces per-step cost, while the ordered state transitions remain. Candidate selection and kernel measurements therefore inform each other.

### Architecture Selection in Practice

^sec-network-architectures-putting-together-architecture-selection-practice-052f

Every selection must first pass a feasibility check: whether the target hardware can sustain the required frame rate at all. A server-class vision pipeline on a mid-range GPU shows the throughput ceiling calculation in its simplest form. The wildlife monitoring deployment that follows applies the same checks under a watt-scale budget where GPUs are ruled out, which is where data structure, model capacity, and hardware budgets interact.

**Napkin Math 6.3: The throughput ceiling**

**Problem**: A real-time application must process 30 FPS of video with ResNet-50. What sustained compute throughput is required?

**Math**:

1.  **Model cost**: ResNet-50 requires ~8.2 GFLOP per $224{\times}224$ image.
2.  **Frame rate**: 30 FPS required.
3.  **Sustained throughput**: 30 FPS $\times$ 8.2 GFLOP = 246 GFLOP/s.
4.  **Effective throughput**: 10 TFLOP/s peak $\times$ 50–60 percent utilization = 5 TFLOP/s–6 TFLOP/s.
5.  **ResNet-50 headroom**: 5 TFLOP/s $\div$ 246 GFLOP/s = 20.3×.
6.  **Detection-model check**: 30 FPS $\times$ 100 GFLOP = 3 TFLOP/s, leaving 1.7× headroom at the lower effective-throughput estimate.

**Systems insight**: A mid-range GPU delivering 10 TFLOP/s theoretical peak achieves 50–60 percent utilization in this planning scenario, yielding 5 TFLOP/s–6 TFLOP/s effective. For ResNet-50 at 30 FPS, the system has 20.3× headroom. Switching to an object detection model at 100 GFLOP per frame, however, requires 3 TFLOP/s sustained, leaving only 1.7× headroom. Batch size constraints or multi-stream processing quickly push the system toward the compute ceiling. The headroom assumes the GPU stays busy; a single 30 FPS stream runs at batch one, where kernel launches and small matrices usually hold utilization well below this planning figure.

The throughput ceiling converts an abstract compute requirement into a concrete hardware utilization percentage. A real-world deployment adds physical constraints the ceiling alone does not capture.

#### Worked Example: Real-Time Wildlife Monitoring

^sec-network-architectures-worked-wildlife-monitoring

The design task is an embedded ML system that classifies wildlife species from camera trap images in an isolated national park. The deployment must execute inference entirely on-device with zero network connectivity, operate on solar-recharged battery power for six months, and achieve 90 percent accuracy across 50 target animal species. The walk-through applies the three-phase framework in five steps. Data characterization is the symmetry phase. Deployment constraint profiling, candidate architecture evaluation, and hardware budget checks carry out the constraint-filtering phase. Operational risk assessment sets up the validation phase that only target-device measurement can complete.

The first step characterizes the data. The input consists of camera trap image frames ($1920{\times}1080$ raw sensor resolution, downsampled to $224{\times}224$ for inference). Three properties favor a CNN candidate: spatial locality (fur textures or ear shapes occupy bounded neighborhoods), label invariance to translation (moving an animal within the frame should preserve its species label), and hierarchical composition (edges combine into textures, anatomical parts, and organisms). Convolution provides equivariant intermediate features that follow the animal’s location; pooling can then support an invariant classification. Local weight sharing supplies a compact feature detector for these images.

The second step, constraint profiling, translates the deployment environment into hard hardware boundaries. [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-nn-architectures-wildlife-constraints|Table 12]] catalogs these physical constraints alongside the architectural requirements each imposes:

| **Constraint**   | **Requirement**                | **Implication**                                          |
|:-----------------|:-------------------------------|:---------------------------------------------------------|
| **Connectivity** | None (offline)                 | All inference must run on-device                         |
| **Power**        | ~2 W average (solar + battery) | Rules out GPUs; needs a low-power SoC or edge NPU        |
| **Latency**      | \<500 ms per detection         | Allows batch size 1, no real-time streaming              |
| **Memory**       | 512 MB RAM, 2 GB storage       | Model, activations, and runtime buffers must fit locally |
| **Accuracy**     | 90%+ on 50 species             | Requires sufficient model capacity                       |

Table 12: **Wildlife Monitoring Constraints**: Five deployment constraints and their implications for the camera-trap scenario. No connectivity rules out cloud-only inference, while the power, latency, memory, and accuracy requirements must be validated on the target device.

^tbl-nn-architectures-wildlife-constraints

With physical constraints established, the third step evaluates candidate architectures against reference model baselines. The planning scenario reserves 100 MB of the available RAM for model weights, leaving the rest for activations, system software, and runtime buffers:

- **ResNet-50** (25.6M parameters, 8.2 GFLOP): A costly starting point for the 2 W envelope. Its weights fit once quantized (25.6 MB in INT8 against 102.2 MB in FP32), but its arithmetic does not: at the platform’s 2 GOPS of sustained INT8 throughput assumed below, one frame takes about 4.1 seconds against a 500 ms target.
- **MobileNetV1** (4.2M parameters, 1138 MFLOP): The original MobileNet, built from depthwise separable layers, with a viable footprint and operation count. Its low arithmetic intensity, which can leave a data center GPU’s matrix units idle, costs far less on a batch-one edge CPU whose much smaller compute peak is easier to keep busy. Storing weights in INT8 reduces model footprint to 4.2 MB (16.8 MB in FP32), and factorized depthwise separable convolutions reduce arithmetic operations.
- **KWS DS-CNN** (200K parameters, 20 MFLOP): An unmatched baseline. This model targets audio keyword spotting, so its reported size and task results do not establish accuracy on visual species classification. An adapted compact vision model would require training and evaluation on the camera-trap task.

While MobileNetV1 demonstrates the viability of depthwise separable convolutions, MobileNetV2 offers another compact candidate, built from the inverted residual blocks of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.04 CNNs Spatial Pattern Processing#^sec-network-architectures-efficient-architectures-keyword-spotting-0625|section 6.3.5]]. Sizing the model with width multiplier 0.75× yields ~2.6M parameters (10.4 MB FP32, 2.6 MB with INT8 weights) and costs ~418 MFLOP at $224{\times}224$ input resolution. Its weight footprint fits the allocation; task evaluation must establish whether its capacity meets the accuracy target for the 50 species.

The fourth step, hardware sizing, checks the candidate against physical platform budgets. INT8 weights occupy 2.6 MB, the network’s largest activation tensor, a $112{\times}112{\times}72$ expansion inside its second bottleneck block, occupies 0.9 MB in INT8, and the scenario reserves 50 MB for OS and runtime buffers. Their 53.5 MB subtotal is only a single-tensor screen. Peak memory must instead include the weights, the maximum sum of simultaneously live tensor bytes, kernel workspace, and OS and runtime buffers. Inputs and outputs can coexist, and a residual path retains its input while the branch executes. The scenario has not yet established that live-tensor peak or the required workspace, so the small subtotal supports candidacy without confirming a fit in 512 MB of RAM.

For the candidate system-on-chip (SoC), an ARM Cortex-A53 at 1.2 GHz with NEON SIMD, this planning calculation assumes sustained throughput of ~2 GOPS INT8: $\frac{418 \times 10^6 \text{ INT8 ops}}{0.002 \times 10^{12} \text{ INT8 ops/s}} = 209 ms \text{ latency} \ll 500 ms \text{ target}~\checkmark$

Active power is the last physical budget to check. At an estimated active inference draw of ~200 mW over 209 ms, each classification consumes 41.8 mJ. For a trigger-based rate of 100 inferences/day, model execution consumes 4.2 J/day. Full-system energy must also include image capture, sleep current, storage, and peripherals. Battery capacity, conversion losses, trigger frequency, and seasonal solar yield determine whether that daily budget supports six months of operation.

The fifth step assesses operational risks in the field. [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.10 Comparing and Choosing Architectures#^tbl-nn-architectures-wildlife-risks|Table 13]] pairs the primary accuracy, thermal, and coverage failure modes with corresponding systems engineering mitigations:

| **Risk**                             | **Mitigation**                                                                        |
|:-------------------------------------|:--------------------------------------------------------------------------------------|
| **90% accuracy not achieved**        | Train on augmented dataset; consider EfficientNet-Lite if MobileNet insufficient      |
| **Thermal throttling in enclosure**  | Add passive heatsink; reduce inference frequency in high-temperature conditions       |
| **New species added postdeployment** | Expand or retrain the output head; install the update during a physical service visit |

Table 13: **Wildlife Camera Deployment Risks**: Top accuracy, thermal, and species-coverage risks for the MobileNetV2 deployment, paired with the engineering mitigation chosen for each.

^tbl-nn-architectures-wildlife-risks

The sizing exercise selects MobileNetV2 (0.75× width multiplier) quantized to INT8 as a candidate for an ARM Cortex-A53 SoC with 512 MB RAM. Under the assumed sustained throughput, the arithmetic estimate is approximately 209 ms per frame. Qualification now requires target-device measurements of end-to-end latency, peak memory, thermal behavior, and full-system energy, together with classification accuracy on representative camera distributions and seasonal battery tests. In production, this qualification phase regularly exposes counterintuitive trade-offs: models with fewer FLOPs can stall on bandwidth-limited hardware, expressive architectures can degrade on datasets lacking matched structure, and lab prototypes can fail against deployment memory hierarchies.
