# V1-06.12 Summary

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures|V1-06 Network Architectures]]

^sec-network-architectures-summary-e642

*Architecture is infrastructure.* Choosing among MLPs, CNNs, RNNs, transformers, and recommendation models (DLRM) shapes the physical terms in the serialized form of the iron law of ML systems (${T}= {D_{\text{vol}}}/{\text{BW}} + {O} / ({R_{\text{peak}}} \cdot {\eta_{\text{hw}}}) + {L_{\text{lat}}}$). Examining each architecture through the four-part lens (pattern processing needs, algorithmic structure, computational mapping, and system implications) connects mathematical inductive bias to work, state, and dependencies. Execution conditions and the target machine then determine which term limits hardware performance.

The durable tool is arithmetic intensity read against the machine’s balance. Reuse raises ${I} = {O}/{D_{\text{vol}}}$ and pushes a workload toward the compute term, as ResNet-50 does when batched; streamed weights lower it and expose the data term, as GPT-2 decoding does at small batch. Two families escape that single axis. A recurrent dependency chain sets a floor of ${S}$ ordered updates that neither term removes, and an oversized embedding table imposes a capacity decision that fixes which bandwidth the data term pays before any arithmetic begins. Low FLOP counts, as MobileNetV2 and KWS show, help only when the resulting operation shapes still keep the hardware’s functional units busy.

**Key Takeaways: Architecture is infrastructure**

- **Inductive bias is the unifying concept**: Every architecture encodes structural assumptions, such as locality for CNNs, sequence for RNNs, and global context for transformers. These biases trade generality for sample efficiency and determine which problems an architecture can solve efficiently.
- **Intensity against balance names the bottleneck**: A workload’s arithmetic intensity, set against the machine’s balance, predicts whether compute or bandwidth sets the limit. One transformer sits on both sides: prefill reuses every weight across the prompt, while batch-one decode re-reads every weight and a growing KV cache for each token.
- **Quadratic costs are permanent constraints**: Dense transformer attention computes $\mathcal{O}({S}^2)$ score interactions. Naive implementations also use quadratic score storage; tiled exact attention removes that storage cost but not the dense computation.
- **Lighthouse models isolate distinct bottlenecks**: ResNet-50 (compute), GPT-2 (bandwidth), DLRM (capacity), MobileNetV2 (compute-bound in its efficient regime, under an edge latency budget), KWS (power-bound). Each isolates one regime, and together they diagnose which physical constraint dominates a given system.
- **Depth benefits from architectural support**: Skip connections and normalization make deep networks trainable by keeping gradients and activations in range; no single depth makes them mandatory. These building blocks, illustrated here through CNNs, transfer to many deep architectures, including transformers.
- **FLOPs do not equal speed**: MobileNetV2 uses 13.7× fewer FLOPs than ResNet-50 but can gain far less than that on data center GPUs when its operation shapes and arithmetic intensity use the available compute units poorly. Architecture-hardware alignment, not operation count alone, determines throughput.
- **Architecture selection is deployment selection**: Choosing a transformer over a CNN determines memory requirements, latency floors, hardware utilization, and infrastructure costs. The architecture is the system constraint.

Architecture selection signs the silicon contract (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-silicon-contract|4]]) with hardware. A CNN commits to spatial locality and weight reuse; dense attention commits to $\mathcal{O}({S}^2)$ score computation; and an RNN commits to serial time-step dependencies. These topological choices constrain operations ${O}$, opportunities for reducing transferred data ${D_{\text{vol}}}$, and dependency order. Realized memory footprint, bandwidth demand, and parallel efficiency also depend on the implementation. Systems engineers can therefore anticipate likely bottleneck shifts before implementation by matching model inductive bias and data geometry to silicon physics.

**What’s Next: From blueprints to construction**

Raw computational primitives (**[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation#^sec-neural-computation|Neural Computation]]**) became concrete architectures in this chapter. Each architecture fixes *what* work must be performed, yet nothing in an architecture says when its operations run, how their gradients are computed, or which device executes them. A machine learning framework answers those three questions, acting as a compiler that lowers the architectural graph to the silicon. **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07 ML Frameworks#^sec-ml-frameworks|ML Frameworks]]** examines how PyTorch, TensorFlow, and JAX solve these execution, differentiation, and hardware-abstraction problems, turning architectural graphs into computational graphs, autograd records, and optimized device kernels.
