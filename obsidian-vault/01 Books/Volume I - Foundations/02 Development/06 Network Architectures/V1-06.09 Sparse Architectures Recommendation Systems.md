# V1-06.09 Sparse Architectures Recommendation Systems

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures|V1-06 Network Architectures]]

^sec-network-architectures-sparse-architectures-recommendation-systems-5d19

Coupling sparse lookups with dense interaction layers is the defining pattern of industrial recommendation engines. When a user opens a streaming service or e-commerce platform, the system must select a handful of recommendations from a catalog of millions within an end-to-end budget of tens of milliseconds. Meeting that target requires mapping both users and items to dense vectors in a shared embedding space and scoring their interactions at scale, which exposes a regime governed first by memory capacity. A data-center accelerator engineered for dense matrix multiplication, providing hundreds of teraflops of arithmetic throughput alongside 80 GB of HBM, cannot hold terabytes of user and item embeddings locally. Its sparse stage gathers rows from those tables, placing different demands on the machine than the batched convolutions of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.04 CNNs Spatial Pattern Processing#^sec-network-architectures-cnns-spatial-pattern-processing-5b8d|section 6.3]] or the streamed-weight decoding of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^sec-network-architectures-transformers-attentiononly-architecture-1b56|section 6.7]].

### Pattern Processing Needs

^sec-network-architectures-pattern-processing-needs-3c57

A recommendation model must process user IDs across billions of accounts and item IDs across millions of products, yet raw integer IDs carry no inherent distance. User 1042 is no closer to user 1043 than to user 9,000,000, so a dense network cannot infer relationships from the numbers themselves. A single request also carries many such categorical features at once (the items a user recently viewed, the categories they follow), so one prediction can require dozens of separate ID lookups.

Recommendation models solve the representation problem by mapping each discrete ID to a dense vector called an **embedding**[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn27|²⁷]] ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-mikolov2013efficient|Mikolov et al. 2013]]). The vectors are ordinary learned parameters. Each row of an embedding table is a weight vector that gradient descent updates whenever its ID appears in a training example, so users and items with similar behavior end up near one another. The dot product of a user vector with an item vector becomes a learned score for how well they match. The system cost is that every lookup becomes an irregular read into a table spanning tens or hundreds of gigabytes. Recommendation models therefore encounter a capacity wall and a memory-bandwidth bottleneck before the first dense feedforward layer executes.

### Algorithmic Structure

^sec-network-architectures-algorithmic-structure-732e

The DLRM architecture ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-naumov2019deep|Naumov et al. 2019]]) organizes this computation into a four-stage pipeline split between dense and sparse paths. Continuous features such as user age or time of day first flow through a bottom MLP, a compute-intensive but memory-light stage dominated by dense matrix multiplications. The bottom MLP projects the raw continuous inputs into a single dense vector with the same dimension as each embedding table row (such as 128 elements), placing continuous and categorical features in a common vector space. In parallel, categorical IDs index into dedicated embedding tables, which is where the memory capacity wall appears. A feature that carries several IDs, such as a user’s recently viewed items, gathers one row per ID and sums or averages them into a single vector, a step called pooling (a different operation from CNN pooling) that leaves each feature with one vector of the shared length.

For example, an embedding table for one billion users with 128-dimensional vectors requires $10^{9} \times 128 \times 4$ bytes $\approx$ 512 GB of memory. This stage is memory-intensive but compute-light because each lookup is a memory copy with zero arithmetic reuse. Because the bottom MLP output and every gathered embedding row now share the same vector length, the interaction layer can combine the dense activations from the bottom MLP with the gathered sparse embedding vectors through pairwise dot products that capture user-item correlations. Finally, a top MLP processes the concatenated interaction representations through feedforward layers to predict a target probability such as click-through rate. Each of the four stages stresses a different part of the machine ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.09 Sparse Architectures Recommendation Systems#^fig-dlrm-pipeline|figure 15]]), and [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.09 Sparse Architectures Recommendation Systems#^sec-network-architectures-computational-mapping-b346|section 6.8.3]] quantifies the capacity-bound profile that results.

### Computational Mapping and System Implications

^sec-network-architectures-computational-mapping-b346

DLRM’s computational mapping splits into two regimes that stress different hardware subsystems. The dense MLPs execute standard GEMM operations, identical to the MLP computational mapping discussed in [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.03 MLPs Dense Pattern Processing#^sec-network-architectures-computational-mapping-cf30|section 6.2.4]] and handled efficiently by Tensor Cores. The sparse embedding lookups, however, are qualitatively different. They are index-based memory gathers that copy parameter data with zero arithmetic reuse. An isolated lookup is bound by memory access latency. When a batch executes hundreds of lookups across features and samples, however, aggregate throughput becomes memory-bandwidth bound as concurrent requests saturate the memory bus. This operational throughput limit is distinct from the capacity constraint. Total table size dictates whether parameters fit in accelerator memory or must spill across PCIe, the general-purpose link between host and accelerator, to host DRAM, whereas available bandwidth governs how fast gathered rows arrive.

Within each selected row, an embedding vector is contiguous (for instance, 128 FP32 elements spanning 512 bytes), allowing the downstream pooling loop to consume every transferred byte. Across rows, however, data-dependent categorical IDs lack predictable spatial locality, so hardware prefetchers, which fetch the next memory blocks before the processor asks for them, cannot anticipate the next row. Access popularity remains heavily skewed. A small set of hot rows (popular items, frequent users) shows strong temporal locality in on-chip caches, while the long tail of rarely touched rows misses to main memory. [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.09 Sparse Architectures Recommendation Systems#^lst-embedding-bag-compute-ec895926|Listing 9]] writes this sparse stage as a loop nest parallel to those of the other families.

``` python
def embedding_bag_compute(sparse_ids, tables):
    # Loop 1: Process each sample in the batch (parallelizable)
    for b in range(batch_size):
        # Loop 2: Each categorical feature has its own table
        for f in range(num_features):
            pooled[b, f, :] = 0
            # Loop 3: Multi-hot feature, one gather per active ID
            for idx in sparse_ids[b][f]:  # data-dependent address
                row = tables[f][idx]  # irregular read, little reuse
                # Loop 4: Pool (sum) the gathered rows
                for d in range(embed_dim):
                    pooled[b, f, d] += row[d]
    return pooled  # feeds the interaction layer
```

Listing 9: **Embedding-Bag Gather**: Four nested loops expose DLRM’s sparse stage. Loops 1 and 2 parallelize across samples and features, but Loop 3 takes its addresses from the input IDs, so hardware cannot predict them, and Loop 4 performs one addition per 4-byte FP32 value loaded. Batching raises that intensity only when samples share hot rows.

^lst-embedding-bag-compute-ec895926

DLRM ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-naumov2019deep|Naumov et al. 2019]]), which Meta open-sourced as a reference for this hybrid architecture, anchors the chapter’s recommendation lighthouse. Its combination of gigabyte-scale embedding tables and small multilayer perceptrons serves as the standard benchmark for memory capacity and irregular sparse access in the data center.

**Lighthouse 6.5: DLRM (recommendation lighthouse)**

**Why it matters**: DLRM exemplifies **memory-capacity-bound** workloads. Its large embedding tables often exceed the memory of a single accelerator or server, so the system must decide where those tables live before it can optimize arithmetic throughput. The interaction layer then gathers selected embedding vectors and combines them with dense features, making capacity and irregular data movement the dominant constraints. This capacity-first decision differs from the batched convolution and streamed-weight decoding regimes examined here, requiring different hardware and deployment choices. [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.09 Sparse Architectures Recommendation Systems#^tbl-nn-architectures-dlrm-profile|Table 6]] summarizes the recommendation lighthouse’s quantitative properties.

| **Property**             | **Value**               | **System Implication**                                   |
|:-------------------------|:------------------------|:---------------------------------------------------------|
| **Embedding Parameters** | 25B                     | Parameters $\times$ 4 bytes; dominates total model size. |
| **Model Size**           | 100 GB (FP32)           | May exceed one device’s fast memory.                     |
| **Constraint**           | Memory Capacity         | Model size $> \text{Single GPU Memory}$.                 |
| **Bottleneck**           | Irregular Data Movement | Gather operations dominate sparse feature processing.    |
| **Profile**              | Mixed (Sparse/Dense)    | Combines memory-heavy lookups with compute-heavy MLPs.   |

Table 6: **DLRM Systems Profile**: Quantitative properties of the recommendation lighthouse and their system consequences. Embedding tables holding billions of values push the model past single-device memory, creating a capacity-bound regime that decides which bandwidth the iron law’s data term must pay.

^tbl-nn-architectures-dlrm-profile

DLRM’s cost signature is a table of weights that must stay resident and almost no multiply-accumulates per lookup, because each lookup is a copy. Once embedding tables exceed one device, capacity, not arithmetic, becomes the primary systems constraint. While a ResNet-50 (102.2 MB) fits on a single accelerator and a dense language model like GPT-3 ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-brown2020language|Brown et al. 2020]]) (350 GB) fits within a single multi-GPU node, production recommendation models reach terabytes of embedding parameters. In iron law terms, capacity acts as a feasibility constraint that comes before either execution term. It decides where the tables live, and therefore which bandwidth the data term ${D_{\text{vol}}}/{\text{BW}}$ must use: HBM when the tables fit, and otherwise host DRAM over PCIe or a peer accelerator over NVLink, a direct accelerator-to-accelerator link, both far slower than HBM.

The architecture therefore breaks the single-device assumption that holds for smaller dense models. Systems designers have three ways to resolve the capacity wall. They can **shrink the tables** through compression, hashing, or pruning, at the risk of losing information on long-tail users and items. They can **move the tables** to host DRAM or external key-value stores, at the cost of slower remote lookups over PCIe or Ethernet. They can **partition the tables** across multiple accelerators so that no single device stores the full model, trading local memory pressure for cross-device communication. Architecturally, DLRM turns recommendation into a capacity-management challenge before it becomes a compute-optimization task. Training-time model partitioning and hardware-accelerated interconnects address these distributed layouts, and the baseline sizing calculation begins with a single table.

**Napkin Math 6.2: The capacity wall**

**Problem**: Consider a recommendation system for a store with 100M items using an embedding size of 128. How much memory does the item table alone require?

**Math**:

1.  **Table entries**: 100M items.
2.  **Vector size**: 128 elements.
3.  **Precision**: FP32 (4 bytes per element).
4.  **Table size**: 100M items $\times$ 128 $\times$ 4 bytes ≈ 51.2 GB.
5.  **Capacity share**: 51.2 GB $\div$ 80 GB = 64 percent of device capacity.
6.  **Two-table check**: Two tables at 64 percent each exceed 100 percent of device capacity.

**Systems insight**: A single embedding table for one feature (items) already consumes 64 percent of an 80 GB A100 GPU. Adding a user table of the same size means the embedding tables no longer fit on a single 80 GB accelerator, motivating table compression, off-device memory, or partitioning across devices. DLRM is capacity bound: the primary systems question is not how many FLOP/s the accelerator can deliver, but where the embedding state can physically reside.

Once the tables no longer fit on one device, sparse lookups cross memory and interconnect boundaries. A request may need rows owned by several accelerators, forcing the device executing the downstream MLP to wait while the system gathers them across PCIe or NVLink. Within a multi-accelerator server, gathering rows distributed across multiple GPUs turns memory routing into an interconnect bandwidth bottleneck, because every accelerator may need rows held by every other, an all-to-all exchange. The architectural consequence is that a recommendation model’s memory layout directly determines its cross-accelerator data-transfer traffic, creating coordination overhead for both training and serving.

**Checkpoint 6.6: DLRM and capacity-bound lookups**

Recommendation systems stress a different part of the machine than CNNs or transformers.

**Capacity-bound**: Can you explain why embedding tables push DLRM into a memory capacity regime where “FLOPs” is not the limiting constraint?

**Sparse access**: Can you explain why embedding lookups defeat prefetching, and why popularity skew still lets a cache capture the hot rows?

**Placement logic**: If a single embedding table does not fit in fast device memory, can you describe which state must move, shrink, or be partitioned?

**Data-movement bottleneck**: Can you explain why sparse embedding lookups can dominate even when the dense MLP has modest FLOP cost?

With DLRM, the roster of five families is complete, and each has been analyzed on its own terms: the pattern it targets, the computation it performs, the mapping it induces, and the bottleneck it exposes. A deployment rarely gets to examine one family in isolation. The same accelerator that serves a vision model today may serve a language model or a recommender tomorrow, and the architecture decides which of its resources gives out first.
