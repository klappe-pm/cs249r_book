# V1-06.03 MLPs Dense Pattern Processing

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06 Network Architectures|V1-06 Network Architectures]]

^sec-network-architectures-multilayer-perceptrons-dense-pattern-processing-bc11

Assuming the least about the input means letting every feature interact directly with every hidden unit. The MNIST digit classifier of **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation#^sec-neural-computation|Neural Computation]]** is the purest example of that dense processing. Each of its 784 pixel inputs connects to every hidden unit, and each hidden unit connects to every unit in the next layer. The same all-to-all pattern suits tabular inputs, such as the sender reputation, link count, and keyword features a spam filter scores, where no feature has a fixed neighbor.

**MLPs**[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn3|³]] turn this minimal prior into an architectural rule: *they impose no specific spatial or temporal connectivity pattern, allowing any input to relate to any output*. That generality makes MLPs versatile across arbitrary feature combinations, though costly whenever the input carries geometric structure that a specialized operator could exploit. Their representational capacity is guaranteed by the universal approximation theorem (UAT)[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn4|⁴]] ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-cybenko1989|Cybenko 1989]]; [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-hornik1989|Hornik et al. 1989]]), introduced in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation#^sec-neural-computation|Neural Computation]]**, which proves that a sufficiently wide MLP with nonlinear activations can approximate any continuous function on a compact domain.

**Definition 6.2: Multilayer perceptrons**

***Multilayer perceptrons*** are feed-forward neural network architectures that apply fully connected layers in sequence, where every neuron in one layer connects to every neuron in the next, without imposing a specific spatial or temporal connectivity pattern.

1.  **Significance**: The lack of structural prior gives dense layers quadratic parameter scaling in layer width: a single layer mapping 1,024 inputs to 1,024 outputs requires 1,048,576 parameters and about 2.1 MB of weight memory in FP16. Every input gets its own weight to every output, which makes MLPs inefficient for high-dimensional structured inputs like images.
2.  **Distinction**: Unlike convolutional neural networks, which exploit spatial locality to reduce parameter count, MLPs treat all input elements symmetrically, making them the architecture of choice for tabular data where no spatial or sequential structure is present.
3.  **Common pitfall**: A frequent misconception is that MLPs are too simple to matter for complex tasks. Dense layers carry much of the arithmetic inside the most complex models: every transformer block contains a position-wise feed-forward MLP, and recommendation models such as DLRM run dense MLP towers on their features. The other families add structure around dense layers (weight sharing, recurrence, attention) rather than replacing them.

Universal expressive power, however, does not explain why deeper, more constrained architectures outperform dense layers on structured inputs.

### Representation Vs. Learnability

^sec-network-architectures-learnability-gap-universal-approximation-enough-0624

Although the UAT guarantees that a wide enough MLP can represent any continuous function on a bounded domain, it gives no guarantee that gradient descent can find those weights from a finite dataset or fit the required width in memory. *Representation capacity* refers to the functions an architecture can express given unlimited resources, whereas *learnability* refers to whether gradient descent can find good weights given finite training samples and compute budgets. A function may be representable in theory yet unlearnable in practice; the *manifold hypothesis*,[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn5|⁵]] which holds that high-dimensional data lies near a much simpler low-dimensional surface, explains why real-world functions have structure that a well-matched architecture can exploit.

This distinction resolves the apparent paradox between universal approximation and architectural progress. Specialized architectures such as CNNs and their deep ResNet descendants improve learnability by embedding inductive biases that match the structure of the data, even when doing so restricts representational capacity. Two factors create this *learnability gap*:

1.  **Sample complexity**: The UAT bounds neither the training examples nor the width needed, and some function classes require widths that grow rapidly with input dimension. For $28{\times}28$ images, an MLP receives 784 pixel values without built-in local connectivity or spatial weight sharing. It can learn spatial correlations, as the digit classifier of **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation#^sec-neural-computation|Neural Computation]]** shows, but must learn relationships that a CNN encodes structurally. When those priors match the task, a CNN can reach a target accuracy with fewer examples and represent the function more compactly. The sample requirement depends on the target function, data distribution, and learning procedure.
2.  **Optimization difficulty**: Even when optimal weights exist, gradient descent may not find them. Without architectural constraints to narrow the search, gradient descent must discover structure that a matching architecture supplies from the start, so training an MLP on images or sequences is typically slower and less reliable. Specialized architectures narrow the search space and introduce symmetries that gradient descent can exploit.

On the classic MNIST handwritten digit benchmark, the first of these factors shows up concretely as far fewer weights per feature detector.

**Example 6.1: MNIST: Representation vs. learnability**

**Scenario**: Classifying $28{\times}28$ MNIST digits with a fully connected MLP vs. a CNN.

**Diagnosis**: The locality saving appears per feature detector. A dense unit learns one weight for every pixel, so 32 features cost 25,088 weights; a convolutional layer learns one $3{\times}3$ filter per feature, 288 weights in total, and reuses each filter at all 784 positions. At equal feature count, the convolutional layer needs 87× fewer weights. Whole-network parameter counts, by contrast, depend mostly on width choices. The 784-128-64-10 MLP has 109,184 weights, fewer than the 421,408 of a small two-convolution CNN, but only because that CNN’s dense classifier head holds 96 percent of them. The saving that convolution buys is the per-detector one.

**Systems lesson**: Inductive bias buys parameter efficiency per feature and reuse per weight. Fewer weights per detector reduce the data needed to learn spatial structure, and each weight fetched from memory feeds hundreds of multiply-accumulates, which raises arithmetic intensity.

^exmp-nn-architectures-mnist-representation-vs-learnability

The learnability gap motivates the core design principle of this chapter: embed inductive biases that match data structure. Each architecture sacrifices theoretical generality for practical learnability. The No Free Lunch theorem[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn6|⁶]] ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-wolpert1997|Wolpert and Macready 1997]]) formalizes this trade-off; the bias that helps one task may hurt another. A bias that ignores where a pattern appears in an image aids image classification but impairs tasks where absolute position matters, such as locating an object. Choosing an architecture means choosing a bias that fits the data.

Appropriate inductive biases reduce parameter counts (enabling edge deployment), accelerate convergence (reducing training costs), and produce structured computation patterns that map efficiently to specialized hardware. The MNIST comparison earned its per-detector saving by matching architecture to data structure, not by shrinking the network. Understanding where dense connectivity remains necessary requires identifying the data patterns that lack structural shortcuts.

### Pattern Processing Needs

^sec-network-architectures-pattern-processing-needs-3c2a

In a tabular dataset such as customer records or a credit risk model, any input column (income, account age, or recent transaction count) can interact with any other, and the columns have no spatial neighbors or time order. Because the data carries no grid or sequence structure, the network cannot restrict computation to local windows or sequential steps. Every output neuron must be free to combine every input feature, leaving gradient descent to learn which connections matter.

Applying that same unstructured treatment to images explains why the MNIST MLP in example [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.03 MLPs Dense Pattern Processing#^exmp-nn-architectures-mnist-representation-vs-learnability|6.1]] needed so many weights per detector. Flattening each $28{\times}28$ image into a 784-element vector discards the two-dimensional grid, so the layer treats adjacent pixels and pixels on opposite corners identically. While this lets every hidden unit relate any pixel to any class, the network must rediscover spatial adjacency from scratch during training. That all-to-all requirement leads directly to the matrix operations that define the MLP.

### Algorithmic Structure

^sec-network-architectures-algorithmic-structure-99f2

Letting every input feature interact with every output unit requires complete connectivity between adjacent layers. In an MLP, this takes the form of a sequence of fully connected layers where every neuron connects to every neuron in the preceding layer. Dense connectivity translates directly into matrix multiplication, the formulation that makes dense layers executable on parallel hardware. The fully connected graph on the left of [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.03 MLPs Dense Pattern Processing#^fig-mlp|figure 2]] becomes the matrix-vector product on its right, in which each hidden neuron’s activation is the dot product of the input with one entire column of the weight matrix.

↩︎ The matrix multiplication formulation of a dense layer’s forward pass is established in **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-matrix-multiplication-formulation-417c|Matrix multiplication formulation]]**.

Figure 2: **Multilayer Perceptron Architecture**: A three-layer network in which every neuron connects to all neurons in adjacent layers. The highlighted neuron receives weighted contributions from all inputs, illustrating the dense $\mathcal{O}({d_{\text{in}}} \times {d_{\text{out}}})$ connectivity pattern implemented through matrix multiplications. For MNIST classification, a 784-dimensional input (${d_{\text{in}}} = 784$) connects to 128 hidden neurons (${d_{\text{out}}} = 128$) through a $784{\times}128$ weight matrix, requiring 100,352 multiply-accumulate operations per sample. Adapted from Reagen et al. ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-reagen2017|2017]]).

^fig-mlp

[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.03 MLPs Dense Pattern Processing#^eq-dense-layer|Equation 1]] restates the dense layer that **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation#^sec-neural-computation|Neural Computation]]** built, an affine transformation followed by its activation.

$$
{\mathbf{h}}^{({\ell})} = {f}\big({\mathbf{h}}^{({\ell}-1)}{\mathbf{W}}^{({\ell})} + {\mathbf{b}}^{({\ell})}\big) \tag{1}
$$

^eq-dense-layer

${\mathbf{h}}^{({\ell})}$ represents the layer ${\ell}$ output, ${\mathbf{h}}^{({\ell}-1)}$ represents the input from the previous layer, ${\mathbf{W}}^{({\ell})}$ denotes the weight matrix for layer ${\ell}$, ${\mathbf{b}}^{({\ell})}$ denotes the bias vector, and ${f}(\cdot)$ denotes the activation function. The dimensions of these operations reveal the computational scale of dense pattern processing. The input vector ${\mathbf{h}}^{(0)} \in \mathbb{R}^{{d_{\text{in}}}}$ (treated as a row vector in this formulation) represents all potential input features. Weight matrices ${\mathbf{W}}^{({\ell})} \in \mathbb{R}^{{d_{\text{in}}} \times {d_{\text{out}}}}$ capture all possible input-output relationships. The output vector ${\mathbf{h}}^{({\ell})} \in \mathbb{R}^{{d_{\text{out}}}}$ produces transformed representations. A four-pixel example recalls that arithmetic in miniature before this section turns to what full connectivity costs.

**Example 6.2: Concrete computation example**

Consider a simplified 4-pixel image processed by a 3-neuron hidden layer:

**Input**: ${\mathbf{h}}^{(0)} = [0.8, 0.2, 0.9, 0.1]$ (4 pixel intensities)

**Weight matrix**:

$$
{\mathbf{W}}^{(1)} = \begin{bmatrix} 0.5 & 0.1 & -0.2 \\ -0.3 & 0.8 & 0.4 \\ 0.2 & -0.4 & 0.6 \\ 0.7 & 0.3 & -0.1 \end{bmatrix}\quad (4{\times}3 \text{ matrix})
$$

**Preactivation** ${\mathbf{z}}^{(1)}$ (the weighted sums before the activation function is applied):

$$
\begin{gather*} \mathbf{z}^{(1)T} = (\mathbf{h}^{(0)}\mathbf{W}^{(1)})^T = \begin{bmatrix} 0.5{\times}0.8 + (-0.3)\times 0.2 + 0.2{\times}0.9 + 0.7{\times}0.1 \\ 0.1{\times}0.8 + 0.8{\times}0.2 + (-0.4)\times 0.9 + 0.3{\times}0.1 \\ (-0.2)\times 0.8 + 0.4{\times}0.2 + 0.6{\times}0.9 + (-0.1)\times 0.1 \end{bmatrix} = \begin{bmatrix} 0.59 \\ -0.09 \\ 0.45 \end{bmatrix} \end{gather*}
$$

 **After ReLU**: ${\mathbf{h}}^{(1)} = [0.59, 0, 0.45]$ (negative values zeroed)

**Systems insight**: Each hidden neuron combines all input pixels with different weights, demonstrating unrestricted feature interaction. Dense layers buy generality by paying the maximum connectivity cost.

^exmp-nn-architectures-concrete-computation-example

The MNIST example makes this scale concrete. The 784-dimensional input connects to every one of the 128 neurons in the first hidden layer of the 784-128-64-10 network from **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation#^sec-neural-computation|Neural Computation]]**. That layer is a $784{\times}128$ weight matrix of 100,352 parameters, and each weight represents a learnable relationship between an input pixel and a hidden feature. This layer is the reference MNIST layer for the computational analysis in the rest of this chapter.

The matrix form specifies every input-output interaction, but it leaves the execution schedule open. Evaluating one sample at a time streams weights with little reuse; grouping samples lets several outputs share each fetched weight.

### Computational Mapping

^sec-network-architectures-computational-mapping-cf30

The layer equation fixes what a dense layer computes, not the order in which a processor computes it. At the framework level the whole layer is a single call to general matrix multiply (GEMM), the dense matrix routine that **[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation#^sec-neural-computation|Neural Computation]]** introduced and that every family in this chapter reaches ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.03 MLPs Dense Pattern Processing#^lst-mlp-layer-matrix-aa3f4636|listing 1]]).

``` python
def mlp_layer_matrix(X, W, b):
    """MLP forward pass using framework-level matrix operations."""
    # X: input matrix (batch_size by num_inputs)
    # W: weight matrix (num_inputs by num_outputs)
    # b: bias vector (num_outputs)

    # Single GEMM call: frameworks dispatch to optimized BLAS/cuBLAS
    # For MNIST: 784 * 128 = 100,352 MACs per sample
    H = activation(matmul(X, W) + b)
    return H
```

Listing 1: **MLP Layer in Matrix Form**: Framework-level matrix operations hide $\mathcal{O}({B} \times {d_{\text{in}}} \times {d_{\text{out}}})$ multiply-accumulate complexity behind a single function call, enabling hardware-optimized BLAS libraries to use dense matrix hardware efficiently.

^lst-mlp-layer-matrix-aa3f4636

The function `mlp_layer_matrix` mirrors [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.03 MLPs Dense Pattern Processing#^eq-dense-layer|equation 1]] directly, using high-level matrix primitives to express the forward transformation while delegating tile scheduling and execution to framework backends. Beneath this software interface, dense matrix multiplication lowers to a canonical three-deep loop nest that determines memory access locality, parallelization boundaries, and register allocation ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.03 MLPs Dense Pattern Processing#^lst-mlp-layer-compute-4e9e288d|listing 2]]). The outermost loop iterates across batch samples, the middle loop iterates over output neurons, and the innermost loop executes repeated multiply-accumulate (MAC) operations[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn7|⁷]] that pair each input feature with its weight.

``` python
def mlp_layer_compute(X, W, b):
    """Explicit loop structure exposing MLP computational patterns."""
    # Loop 1: Process each sample independently (parallelizable)
    for batch in range(batch_size):
        # Loop 2: Compute each output neuron
        for out in range(num_outputs):
            Z[batch, out] = b[out]  # Initialize with bias

            # Loop 3: Accumulate weighted inputs (innermost loop)
            # This is the MAC operation: result += input * weight
            for in_ in range(num_inputs):
                Z[batch, out] += X[batch, in_] * W[in_, out]
            # Total per output: num_inputs MACs +
            # num_inputs memory reads

    H = activation(Z)  # Element-wise nonlinearity
    return H
```

Listing 2: **Dense Layer Computation**: Nested loops reveal $\mathcal{O}({B} \times {d_{\text{out}}} \times {d_{\text{in}}})$ complexity where each output neuron requires num_inputs multiply-accumulate operations, so the reference MNIST input layer requires 100,352 MACs per sample.

^lst-mlp-layer-compute-4e9e288d

In the reference MNIST layer, computing 128 hidden neurons requires 100,352 MACs in total. Each individual output neuron requires 784 multiply-accumulate operations and 1,568 logical operand reads (784 for inputs, 784 for weights). Registers and caches can serve repeated reads, so this count is not a DRAM-traffic estimate. Production implementations call optimized matrix libraries such as Basic Linear Algebra Subprograms (BLAS),[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn8|⁸]] but the same nested-loop pattern still determines the system design problem. The hardware architectures that accelerate these matrix operations, including GPU Tensor Cores[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn9|⁹]] and specialized AI accelerators, are covered in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.04 Compute Primitives#^sec-hardware-acceleration-matrix-operations-hardware-acceleration-514a|Matrix operations hardware acceleration]]**.

### System Implications

^sec-network-architectures-system-implications-0550

While the reference MNIST layer $(784{\times}128)$ needs only 100,352 parameters, a single dense layer connecting 2048 inputs to 2048 outputs requires 4,194,304 parameters (16.8 MB at FP32), and evaluating one sample uses each weight only once. Because every input connects to every output, $\mathcal{O}({d_{\text{in}}} \times {d_{\text{out}}})$ weight storage dominates the memory footprint, and when those weights exceed on-chip cache and stream from DRAM on every request, memory bandwidth becomes the bottleneck. Dense layers therefore concentrate hardware pressure across three dimensions: memory capacity for weight storage, compute throughput on matrix engines, and memory bandwidth for weight movement.

The core computation is a dense matrix-vector product (GEMV), or a matrix-matrix product (GEMM) when batched. This computation is regular and parallelizable, so modern processors optimize dense layers in hardware. CPUs use single instruction, multiple data (SIMD) units, which apply one instruction to many values at once. GPUs use dense matrix engines such as Tensor Cores, and Tensor Processing Units (TPUs) use systolic arrays[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.15 Footnotes#^fn10|¹⁰]] ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-jouppi2017|Jouppi et al. 2017]]). Regular structure does not guarantee reuse, however. The arithmetic intensity (FLOP/byte) of a dense layer is low for small batches, and a larger batch size amortizes weight-loading cost over more computations.

**[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-implementation-optimization-considerations-f2ca|Implementation and optimization considerations]]** measured this weight-loading cost on the running network, where at batch one each weight read serves a single multiply-accumulate. For the reference layer, which reads $784{\times}128$ weights to compute 128 hidden values, a weight-only model that counts one FP32 read per weight and omits input, output, bias, and cache traffic gives roughly 0.5 FLOP/byte at batch one. [[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.03 MLPs Dense Pattern Processing#^eq-dense-intensity|Equation 2]] restates that ratio, where ${d_{\text{in}}}$ and ${d_{\text{out}}}$ are the input and output widths. The memory tier serving those reads determines the relevant bandwidth.

$$
{I}\approx \frac{2 \cdot {d_{\text{in}}} \cdot {d_{\text{out}}} \text{ FLOPs}}{4 \cdot {d_{\text{in}}} \cdot {d_{\text{out}}} \text{ bytes}} = 0.5 \text{ FLOP/byte} \tag{2}
$$

^eq-dense-intensity

If these weights stream from off-chip memory, a machine whose off-chip ridge point, the intensity at which its compute and bandwidth limits meet, lies in the hundreds of FLOP/byte cannot supply them fast enough to reach peak arithmetic throughput. The small MNIST layer may instead remain cached across requests; its traffic must then be compared with the bandwidth of that cache, and dispatch overhead may matter more than off-chip bandwidth. Batching raises the weight-bound intensity in proportion to the batch size until input and activation traffic begin to dominate, but where it crosses the machine’s balance depends on matrix shape, precision, implementation, and hardware. This is why a fully connected layer can become an inference bottleneck even when it performs fewer total FLOPs than the convolutional layers introduced next.

The same intensity sets the energy per inference. With the energy constants introduced alongside the iron law ([[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.14 Source References#^ref-horowitz2014|Horowitz 2014]]), about 160 pJ per byte read from DRAM and 4.6 pJ per FP32 multiply-accumulate, a batch-one dense layer that streams its weights spends about 139× more energy moving each weight than computing with it. Batching divides that ratio by the batch size until activation traffic takes over, so the knob that raises throughput also cuts energy per inference.

![[90 Assets/Volume I/06 Nn Architectures/Nn Architectures Arithmetic Intensity 6a62de04cb.svg]]

*Two orange lollipops on a log FLOP-per-byte axis: ResNet 80 reaches far to the right, Dense 0.5 sits near the left edge.*

*A batch-one dense layer sits far below convolution’s weight reuse.*

A dense layer’s cost signature is therefore one weight for every input-output pair, one multiply-accumulate per weight per example, and every weight read once per batch. Because dense connectivity offers little weight reuse within a single-example forward pass, applying MLPs to high-dimensional structured signals forces an undesirable trade-off between parameter explosion and low arithmetic intensity. When data possesses inherent physical organization (spatial coordinates in images, sequential order in time series), specialized architectures replace all-to-all connectivity with structural priors that simultaneously raise accuracy and computational efficiency. The most established of these spatial architectures is the convolutional neural network.
