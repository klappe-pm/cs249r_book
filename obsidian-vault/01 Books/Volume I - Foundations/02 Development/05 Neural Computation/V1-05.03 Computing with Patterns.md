# V1-05.03 Computing with Patterns

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation|V1-05 Neural Computation]]

^sec-neural-computation-evolution-ml-paradigms-ec9c

Before a learned network spent 109,184 MACs on that $28{\times}28$ digit, earlier generations of computing attacked the same classification problem with two simpler representation strategies. An illustrative rule tree tests roughly one hundred pixel comparisons per digit; an engineered feature pipeline performs several thousand arithmetic operations; the three-layer neural network performs more than one hundred thousand multiply-accumulates. Each strategy replaced a predecessor whose representations ran out of expressive reach on unconstrained handwriting, and each step up in representation capacity shifted which hardware resource bound execution.

↩︎ The succession of logic, knowledge, feature-engineering, and infrastructure bottlenecks that these paradigms answered is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.04 The Evolution of AI Bottlenecks#^sec-introduction-ai-paradigm-evolution-ae2b|The Evolution of AI Bottlenecks]]**.

### From Rules to Engineered Features

^sec-neural-computation-feature-engineering-bottleneck-6172

Writing explicit `if-else` rules to recognize a handwritten digit breaks as soon as a writer tilts a stroke, thickens a line, or leaves a loop open. Rule-based programming requires developers to specify every procedure that maps inputs to outputs: in the classical flow of [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.03 Computing with Patterns#^fig-traditional|figure 1]], human-authored rules and input data enter the program together, and the program deterministically computes the answers.

![[90 Assets/Volume I/05 Nn Computation/Generated Figure d50e1af8e6.svg]]

Figure 1: **Traditional Programming Flow**: Answers are the program’s output, never its input. This input-output pattern formed the basis for early AI systems but lacks the adaptability needed for complex pattern recognition tasks.

^fig-traditional

An illustrative rule-based classifier for the digit compares pixel intensities against fixed thresholds, checks stroke patterns in localized regions, and branches on the results. Under this toy implementation, the computation requires roughly 100 comparisons over 784 bytes of pixel data, a workload that is small, predictable, and easily held in an ordinary CPU cache. The comparison establishes a workload baseline, not the accuracy of a production rule system. Rules fail on coverage rather than cost. Every new writing style demands new branches, the same coverage problem that stalled the expert systems of **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.04 The Evolution of AI Bottlenecks#^sec-introduction-expert-systems-era-knowledge-bottleneck-f928|The expert systems era and the knowledge bottleneck]]**.

Classical machine learning replaced the rule for every situation with patterns found in examples, yet its success still depended on human insight to define which patterns to look for, a process known as feature engineering (**[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.04 The Evolution of AI Bottlenecks#^sec-introduction-statistical-learning-era-feature-engineering-bottleneck-8cf5|The statistical learning era and the feature engineering bottleneck]]**).

Feature engineering transformed raw data into representations that expose patterns to learning algorithms. The histogram of oriented gradients (HOG)[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.13 Footnotes#^fn2|²]] ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-dalal2005hog|Dalal and Triggs 2005]]) exemplifies this approach. In [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.03 Computing with Patterns#^fig-hog|figure 2]], the feature-extraction pipeline divides an image into spatial cells and bins local pixel gradient directions (the direction in which brightness changes fastest, a different quantity from the training gradients of this chapter) into an eight-bin orientation histogram for each cell, turning raw pixels into shape descriptors that tolerate lighting changes and small shifts in position.

![[90 Assets/Volume I/05 Nn Computation/Hog 4344e7787e.png]]

Figure 2: **HOG Method**: A local image patch is divided into cells, gradient orientations are accumulated into a histogram, and the resulting descriptor summarizes local shape while reducing sensitivity to illumination. Source: Figure 5 of Bakheet and Al-Hamadi ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-bakheet2021hog|2021]]), licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).

^fig-hog

Feature engineering raises the digit’s cost while keeping it CPU friendly. For the same $28{\times}28$ digit, an illustrative HOG implementation divides the image into a 7 by 7 grid of 4 by 4 cells and computes gradient magnitudes and orientations. It bins them into one 9-bin orientation histogram per cell (the figure draws an eight-bin variant) and produces a 441-element feature vector. A linear support vector machine (SVM) classifier then performs ten dot products over that vector. The result is roughly 8,000 operations and about 2 KB of working memory, about 80× the work of the toy rule-based baseline. The work is still structured and well served by CPU vector units, which apply one instruction to several values at once, a style called **single instruction, multiple data (SIMD)**. Descriptor size, class count, and implementation all change this cost.

Every new problem still needed an expert to design a new extractor, so human expertise, not computation, set the ceiling on how much real-world visual variation a system could absorb.

### Automatic Pattern Discovery

^sec-neural-computation-deep-learning-automatic-pattern-discovery-214d

Neural networks remove that ceiling by discovering their own features, learning representations directly from raw data instead of following explicit rules or human-designed extractors. Supervised learning inverts the traditional programming relationship. Engineers provide examples and target answers, and optimization produces the decision rules as output rather than taking them as input ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.03 Computing with Patterns#^fig-deeplearning|figure 3]]). Humans still shape the task through data, objectives, architectures, and evaluation.

![[90 Assets/Volume I/05 Nn Computation/Generated Figure 5a920546a2.svg]]

Figure 3: **Data-Driven Rule Discovery**: The flow diagram inverts the traditional programming pattern: data and answers serve as inputs to the machine learning process, which produces a learned decision function as output. This shift replaces a hand-coded decision policy while leaving engineers responsible for the data, objective, architecture, and evaluation.

^fig-deeplearning

The same digit, processed by the chapter’s three-layer network (784 → 128 → 64 → 10), costs 109,184 MACs, 1,100× the work of the toy rule-based baseline. The 109,386 parameters occupy 438 KB in FP32, more than most L1 caches, a processor’s smallest and fastest level of memory, can hold, so even inference creates traffic between cache levels. Training multiplies the cost further. Each image is processed forward and backward before an update, which costs two to three times the dense-layer arithmetic of the forward pass alone, and that work repeats over 60,000 images for multiple epochs (full passes over the training set). Dense matrix multiplications now dominate the arithmetic and favor parallel hardware, shifting the engineering challenge from control-flow branching to memory bandwidth, data reuse, and hardware parallelism.

![[90 Assets/Volume I/05 Nn Computation/Vol1 Nn Computation Margin 001 fd08dd5561.svg]]

*Vertical log-scale ladder of orange bars, smallest at bottom: rule-based comparisons, then HOG operations, then neural-network matrix MACs at the top, spanning several orders of magnitude.*

*In this MNIST comparison, learned features spend far more arithmetic.*

This trade is the bitter lesson at the scale of a single layer. HOG encodes an expert’s knowledge of edges and orientations in 8,000 operations that never change; the learned first layer spends far more arithmetic and lets the data decide which pixel combinations matter. As computation became cheap enough, the general method that converts arithmetic into accuracy overtook the hand-built one. That victory demands the arithmetic, memory traffic, and training infrastructure that the rest of this chapter quantifies.

↩︎ Why general methods that scale with computation keep overtaking methods built on human knowledge, the bitter lesson, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.05 The Bitter Lesson#^sec-introduction-bitter-lesson-79c7|The Bitter Lesson]]**.

The escalation matters less for its 1,100× operation count than for what each step does to the limiting resource, which moves from branch-heavy CPU control, to batch-oriented feature pipelines, to memory-fed matrix parallelism ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.03 Computing with Patterns#^tbl-evolution|table 2]]). Dense matrix work meets the memory wall, the widening gap between compute throughput and off-chip memory bandwidth, whenever an operation performs too little arithmetic per byte it moves. That ratio is the arithmetic intensity introduced alongside the iron law; the forward-pass analysis later in this chapter measures it for the running network, and **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]** develops it into a full performance bound.

↩︎ The memory wall and the physical reasons that off-chip bandwidth lags arithmetic are established in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.03 Physical Constraints on Deployment#^sec-ml-systems-deployment-spectrum-71be|Physical Constraints on Deployment]]**.

↪ The AI memory wall, the point at which added FLOP/s stops reducing runtime because data movement dominates, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.06 Memory Systems#^sec-hardware-acceleration-understanding-ai-memory-wall-3ea9|The AI memory wall]]**.

| **System Aspect**    | **Traditional Programming** | **ML with Features**        | **Deep Learning**                        |
|:---------------------|:----------------------------|:----------------------------|:-----------------------------------------|
| **Computation**      | Often control-flow oriented | Structured parallel ops     | Often matrix-parallel                    |
| **Memory Access**    | Workload dependent          | Commonly batch-oriented     | Large tensor working sets                |
| **Data Movement**    | Program and input dependent | Feature-pipeline movement   | Parameter and activation movement        |
| **Hardware Needs**   | Commonly CPU-centric        | Often CPU with vector units | Frequently accelerator-friendly          |
| **Resource Scaling** | Input and program dependent | Descriptor and data driven  | Driven by width, batch, state, and reuse |

Table 2: **System Resource Tendencies**: The illustrated implementations shift from control-oriented rules to structured feature pipelines and then to matrix-heavy neural computation. These are workload tendencies rather than requirements of every program in each paradigm.

^tbl-evolution

Each step up in representation moved the bottleneck from control flow toward data movement and parallel hardware, and further scale keeps loading those same resources. Larger models and training budgets turn arithmetic throughput, memory bandwidth, storage capacity, and communication into potential bottlenecks, and model size is not a decision rule. Choosing a model requires comparing candidates on representative deployment data and on the complete cost of training, serving, monitoring, and maintenance, with the uncertainty in both gains and costs included. The useful question is whether the measured gain from additional scale earns those system costs.

↪ How model size, training data, and compute trade off along a compute-optimal frontier is developed in **[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09.03 Measuring Data Value#^sec-data-selection-computeoptimal-frontier-24ba|The compute-optimal frontier]]**.

**Systems Perspective 5.1: When to use neural networks**

Not every problem benefits from deep learning. **[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.06 Stage 1 Problem Definition#^sec-ml-workflow-problem-definition-stage-5974|Stage 1: Problem Definition]]** established that a problem definition must require a learned system to improve on an existing baseline by more than its added cost. [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.03 Computing with Patterns#^tbl-nn-when-to-use|Table 3]] lists the conditions under which a neural network tends to win that comparison, and [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.03 Computing with Patterns#^tbl-nn-when-not-to-use|table 4]] the conditions under which a classical method tends to match it with less training, serving, and maintenance effort. Among those classical baselines, linear models learn one weight per input feature and additive models one simple curve per feature, while decision trees learn nested if-then splits on the features and ensembles such as gradient boosting combine many trees.

| **Condition**             | **Evidence to seek**                                  | **Rationale**                            |
|:--------------------------|:------------------------------------------------------|:-----------------------------------------|
| **Representative data**   | Training and validation cover deployment conditions   | Capacity cannot replace missing coverage |
| **Exploitable structure** | Spatial, sequential, or hierarchical patterns         | Architecture can encode a useful prior   |
| **Baseline gap**          | Simpler methods miss the required task-quality target | Complexity buys a measured gain          |
| **Operational fit**       | Gain survives latency, memory, and cost limits        | Offline accuracy alone is insufficient   |
| **Maintenance advantage** | Learned features reduce recurring manual updates      | Full-system maintenance becomes simpler  |

Table 3: **Neural-Network Candidates**: Conditions under which deep learning is likely to outperform classical methods.

^tbl-nn-when-to-use

| **Condition**                   | **Baseline to test**              | **Reason to prefer it**                            |
|:--------------------------------|:----------------------------------|:---------------------------------------------------|
| **Limited labeled data**        | Linear model or tree ensemble     | Lower variance and easier validation               |
| **Structured tabular inputs**   | Gradient boosting or linear model | Strong accuracy without learned features           |
| **Approximately linear signal** | Linear or additive model          | Transparent and inexpensive execution              |
| **Hard resource bound**         | Rules or compact classical model  | Predictable latency, memory use, and energy demand |
| **Direct auditability needed**  | Constrained tree or linear model  | Decisions are easier to inspect                    |

Table 4: **Classical-Method Candidates**: Conditions under which simpler models are likely to match or beat a neural network.

^tbl-nn-when-not-to-use

**Systems insight**: Establish a simple baseline before building a neural network, and retain the neural approach only when its measured benefit justifies the added system. The document-recognition history in [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.07 Handwritten Digit Recognition#^sec-neural-computation-case-study-usps-digit-recognition-97be|section 5.6]] shows why the comparison must include preprocessing, rejection policy, and the cost of human review rather than model accuracy alone.

### Why Backpropagation Waited for Systems

^sec-neural-computation-evolution-neural-network-computing-8754

Every increase in a neural network’s size multiplies its forward operations, saved activations, gradient computations, and parameter updates, which is why backpropagation waited decades for hardware and data to catch up with the algorithm. Paul Werbos applied backpropagation[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.13 Footnotes#^fn3|³]] to neural networks in 1974 ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-werbos1974beyond|Werbos 1974]]), building on Seppo Linnainmaa’s 1970 work on automatic differentiation ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-linnainmaa1970representation|Linnainmaa 1970]]), and Rumelhart, Hinton, and Williams showed in 1986 that hidden units, the computing elements in the layers between a network’s input and its output, could learn useful internal features ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-rumelhart1986|Rumelhart et al. 1986]]). That demonstration did not remove the systems cost that grows with network size. The decades between early backpropagation work and widespread adoption required the maturation of parallel hardware, large datasets, better weight initialization ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-parameter-initialization-5d1a|section 5.4.5.3]]), non-saturating nonlinearities ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.04 Neural Network Fundamentals#^sec-neural-computation-relu-7184|section 5.3.2.2.3]]), and software frameworks. An algorithm can be viable in principle long before its surrounding system makes it useful in practice. The lesson does not run in reverse: a computationally expensive idea is not vindicated by expense alone, and it must be evaluated together with the data, software, hardware, and task regime that would make it useful.

↩︎ How AlexNet, GPUs, and ImageNet ended the feature-engineering era, and why infrastructure became the next bottleneck, is established in **[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.04 The Evolution of AI Bottlenecks#^sec-introduction-deep-learning-era-infrastructure-bottleneck-2f02|The deep learning era and the infrastructure bottleneck]]**.

**Checkpoint 5.1: Understanding deep learning's emergence**

Before turning to the primitives that set these costs, verify your understanding of why deep learning emerged when it did:

**Adoption lag**: can you explain why backpropagation existed for more than a decade before it was widely used, naming the systems costs that grow with model size?

**The cost of feature learning**: can you explain, using the digit-classification operation counts, why replacing hand-engineered features with learned ones raises the arithmetic and memory demand?

**Bottleneck shift**: can you use [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.03 Computing with Patterns#^tbl-evolution|table 2]] to explain how the limiting resource moves from control flow toward data movement as representation moves from rules to learned features?

**Baseline first**: can you name two conditions under which a classical baseline should be tried before a neural network, and the evidence that would justify switching?

If any of these concepts remain unclear, review the relevant sections before continuing.

The digit classifier’s cost and the adoption lag lead to the same conclusion. What a network costs the machine is fixed by the primitives it is built from, and those primitives are the subject of the rest of this chapter.

**Self-Check: Question**

1.  A team replaces a hand-coded digit recognition system ($\approx 100$ conditional comparisons, $784\text{ bytes}$ of working state) with a $784 \to 128 \to 64 \to 10$ MLP ($\approx 109{,}184\text{ MACs}$, $\approx 438\text{ KB}$ of weights) on the same MNIST input. Which systems consequence should they expect when deploying this new model on a commodity CPU?

    1.  The workload becomes dominated by branch mispredictions because artificial neurons execute frequent if-then branching decisions.
    2.  The workload transitions from branch-heavy scalar code to dense matrix arithmetic whose weight footprint exceeds L1 cache capacity, generating cache-level memory traffic absent in the rule-based system.
    3.  Execution memory traffic drops to zero because the $438\text{ KB}$ weight footprint fits entirely within standard CPU register files.
    4.  The model executes without using arithmetic logic units (ALUs) because learned representations bypass hardware compute pipelines.

2.  A hardware vendor claims that increasing single-threaded CPU clock frequencies by $5\times$ will eliminate the necessity of specialized accelerators (such as GPUs or TPUs) for deep neural networks. Based on the computational profile of neural networks, what is the strongest technical refutation of this claim?

    1.  Deep learning is dominated by massive parallel matrix multiplications bounded by arithmetic throughput and memory bandwidth, which benefit from thousands of parallel SIMD/tensor units rather than higher scalar clock speeds.
    2.  Higher CPU clock frequencies force the loss function to become non-convex, destabilizing gradient descent.
    3.  Modern neural networks require asynchronous analog circuits that cannot be simulated on digital CPU cores.
    4.  Increasing CPU clock frequencies reduces the numerical precision of floating-point registers to 4-bit integers.

3.  A computer vision team evaluates two approaches for a multi-class recognition task: (a) a handcrafted feature pipeline (e.g. HOG + SVM) and (b) an end-to-end convolutional neural network. Compare the systems engineering trade-offs between these two approaches when the product must scale from 2 initial categories to 50 diverse object categories.

4.  Explain the systems-level concept of the ‘algorithm-hardware adoption lag’ using the historical trajectory of backpropagation (Werbos 1974 / Rumelhart et al. 1986) and modern deep learning. Which surrounding factors had to mature before the algorithm achieved widespread practical viability?

5.  True or False: For a tabular dataset with 500 records and linear relationships between features and targets, deploying a deep neural network is generally superior to a linear regression model because deep networks inherently generalize better across all problem scales.

6.  Order the pattern-computing paradigms as the chapter presents their progression, from explicit logic to learned representations: (1) Deep learning with automatic hierarchical feature discovery on parallel accelerators, (2) Rule-based programming with explicit hand-authored logical branches, (3) Classical machine learning pairing hand-engineered feature extractors (e.g. HOG) with statistical classifiers.
