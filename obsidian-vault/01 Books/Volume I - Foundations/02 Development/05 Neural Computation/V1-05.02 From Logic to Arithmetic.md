# V1-05.02 From Logic to Arithmetic

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation|V1-05 Neural Computation]]

^sec-neural-computation-deep-learning-systems-engineering-foundation-597f

Recognizing one handwritten digit costs the small network at the center of this chapter 109,184 MACs. A multiply-accumulate (MAC) multiplies one weight by one input value and adds the product to a running sum (${\text{acc}}\leftarrow {\text{acc}}+ {w}\cdot {x}$), and the usual convention counts it as two floating-point operations ($1\text{ MAC} = 2\text{ FLOPs}$), so the digit costs 218,368 FLOPs. None of that work is a logical branch. A program that once tested pixel thresholds and stroke patterns with if-then-else rules has become a fixed sequence of arithmetic. How fast it runs now depends on how quickly the machine can supply operands to that arithmetic, and so on whether memory bandwidth or arithmetic capacity runs out first. Such a program also fails differently. It rarely fails logically; it fails numerically, as values grow or shrink until they stop carrying information.

The data pipeline of **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering#^sec-data-engineering|Data Engineering]]** ends by delivering a clean, versioned training example, and that example by itself teaches the model nothing. Learning begins when the digit crosses from the pipeline into the model, the algorithm axis of D·A·M, where mathematical operators fix the work to be done and the state to be held. Under the silicon contract (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-silicon-contract|4]]), those operators supply the model’s side of the contract, while precision, data layout, implementation, and hardware fix how many bytes actually move and which machine resource saturates first.

↩︎ The hardware’s side of the silicon contract, the terms that memory bandwidth, peak compute rate, and fixed overhead set for any model, is established on the single-node stack in **[[01 Books/Volume I - Foundations/01 Foundations/02 System Paradigms/V1-02.05 System Balance and Hardware#^sec-ml-systems-architectural-anchor|Inside one machine: The single-node stack]]**.

The digit passes through five stages in the life of a model. The *forward pass* carries the image through three weight matrices to ten class scores. The *loss* reduces those scores to one number that says how wrong they are. The *backward pass* carries that signal back through the layers with the chain rule, and the *update* adjusts every parameter. *Serving* runs the forward pass alone with frozen weights.

Two of those stages leave per-parameter values behind. The backward pass produces one *gradient* per parameter, a number that says how much the loss would change if that parameter changed slightly, and the update moves each parameter a small step in the direction that lowers the loss. Many update rules also keep extra running values for each parameter, such as an average of its recent gradients, and those values are the *optimizer state*.

The iron law of ML systems (principle [[01 Books/Volume I - Foundations/02 Development/V1 Development Principles#^pri-iron-law|3]]) charges each stage for the bytes it moves, the operations it performs, and its fixed overhead, and [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.02 From Logic to Arithmetic#^tbl-nn-computation-stage-costs|table 1]] shows how differently the five stages spend those terms. The loss costs almost nothing, yet it is the only signal training receives; the update does little arithmetic but touches every parameter; the backward pass cannot run without the activations (the intermediate values each layer produces) that the forward pass left behind. Training repeats the first four stages millions of times and serving repeats only the first, and that asymmetry produces the chapter’s central result, the gap between what training and inference must hold in memory.

| **Stage**         | **Work**                                                | **Data moved**                                               | **State left behind**                     | **Usually dominant cost**                   |
|:------------------|:--------------------------------------------------------|:-------------------------------------------------------------|:------------------------------------------|:--------------------------------------------|
| **Forward pass**  | One MAC per weight per example (109,184 MACs per digit) | Every weight read; each layer’s activations written and read | Activations, kept until the backward pass | Bytes at small batch, operations at large   |
| **Loss**          | A few operations per class                              | Ten scores per example                                       | One number per batch                      | Negligible                                  |
| **Backward pass** | Up to twice the forward pass                            | Weights and saved activations read; gradients written        | Gradients                                 | Operations or bytes, as in the forward pass |
| **Update**        | A few operations per parameter                          | Every weight, gradient, and optimizer value read and written | Optimizer state                           | Bytes                                       |
| **Serving**       | The forward pass alone                                  | Weights plus two short-lived activation buffers              | Nothing beyond the weights                | Bytes and fixed overhead at small batch     |

Table 1: **Where Each Stage Spends Its Budget**: Work, data movement, and retained state for the five stages in the life of a model, for the running 784-128-64-10 network. Training repeats the first four stages for every batch, while serving runs only the forward pass. Later sections derive each row, and the summary returns to the table.

**Example 5.1: Running example: MNIST digit recognition**

**Scenario**: A handwritten-digit classifier receives $28{\times}28$ grayscale images from the Modified National Institute of Standards and Technology (MNIST) dataset ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-lecun1998|LeCun et al. 1998]]), flattens each into 784 pixel values, and maps them through hidden layers of 128 and 64 units to 10 class scores, one per digit (784 → 128 → 64 → 10).

**Diagnosis**: The network holds 109,386 parameters, which occupy 438 KB in 32-bit floating point (FP32), and it spends 109,184 MACs (218,368 FLOPs) to classify one digit. Those three numbers summarize what one classification costs.

**Systems lesson**: The task is small enough to compute by hand yet exercises every mechanism that larger networks scale up. Each later section either derives one of these numbers or asks what happens to it when the network trains, grows, or ships.

^exmp-nn-computation-running-example-mnist-digit-recognition

Even this small network counts as deep in the sense the field uses, because it stacks more than one layer of learned features between input and output. Each of its layers computes new features from the layer before, and training learns those features from examples instead of receiving them from a designer.

**Definition 5.1: Deep learning**

***Deep learning*** is the computational paradigm that learns layered feature representations from data by composing nonlinear transformations. For suitable tasks, those learned representations can reduce manual feature engineering while increasing the operation count $({O})$ and the state a model must hold.

1.  **Significance**: For suitable compositional function classes, depth can represent a hierarchy much more parameter-efficiently than a shallow network. Each layer adds work and state, and the resulting limiting constraint may lie on the data, algorithm, or machine axis depending on the workload.
2.  **Distinction**: Shallow methods such as logistic regression and support vector machines learn a single stage on top of features a designer builds, and they can work well when those features are good. Deep learning instead uses multiple nonlinear stages to learn representations jointly with the prediction task, which can reduce manual feature design and sometimes support transfer across tasks.
3.  **Common pitfall**: A frequent misconception is that parameter count alone explains deep learning. Two networks with the same parameter count can differ sharply in what they learn, because architecture, data, optimization, and scale together determine the practical result.

Learning representations end to end also introduces engineering failure modes that conventional software debugging cannot isolate. Deep learning failures produce subtle symptoms: gradient instabilities[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.13 Footnotes#^fn1|¹]] that stop training from making progress, numerical precision errors that corrupt parameter state across millions of updates, or inefficient memory access patterns in tensor operations (operations on multidimensional arrays of numbers) that leave accelerator compute units underutilized. Resolving these failures requires reasoning about the physical execution of tensor algebra on hardware rather than stepping through procedural control flow. Those hardware demands depend first on representation, that is, on whether patterns are expressed through hand-authored rules, engineered statistical features, or learned parameters.

**Self-Check: Question**

1.  An engineer deploys the same neural network model on an accelerator with high GPU memory and on an older accelerator with smaller memory capacity. The model executes cleanly on the larger card but crashes mid-batch on the smaller card with a CUDA out-of-memory error on an intermediate activation tensor, without generating a Python traceback. Per the Silicon Contract perspective of neural computation, which diagnostic approach addresses the root cause of this failure?

    1.  Audit the Python application code and framework version to identify an unhandled control-flow software exception.
    2.  Increase logging verbosity to capture a Python traceback, assuming the crash stems from glue-code syntax errors.
    3.  Downgrade the GPU driver and CUDA toolkit under the assumption that the newer driver introduced backward-incompatibility bugs.
    4.  Calculate the intermediate activation and parameter memory requirements directly from layer tensor dimensions, because the mathematical operators—not the application code—determine the physical memory demands.

2.  Recognizing one MNIST digit requires approximately $109{,}000$ multiply-accumulate operations. Explain why a traditional control-flow debugger is insufficient when such a network fails, and describe how its failures differ from those of a rule-based program.

3.  True or False: In the iron law of ML systems ($T = \frac{D_{\text{vol}}}{\text{BW}} + \frac{O}{R_{\text{peak}} \cdot \eta_{\text{hw}}} + L_{\text{lat}}$), the shift from rule-based logic to dense neural computation primarily increases the network latency term $L_{\text{lat}}$ because matrix multiplications introduce distributed network round-trips.
