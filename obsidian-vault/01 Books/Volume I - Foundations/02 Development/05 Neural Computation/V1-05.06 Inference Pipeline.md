# V1-05.06 Inference Pipeline

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation|V1-05 Neural Computation]]

^sec-neural-computation-inference-pipeline-5372

Training transforms randomly initialized weights into parameters that encode useful patterns, but deployment executes those parameters under a different resource profile. During inference,[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.13 Footnotes#^fn23|²³]] the same mathematical operators face a different operating regime. Online latency deadlines or offline throughput targets replace the training objective, gradients and optimizer state disappear from memory, and target execution environments range from milliwatt edge processors to multi-accelerator cloud servers. This transition reshapes how memory bandwidth, compute capacity, and pipeline stages govern system performance. Because ordinary inference never updates the weights, a deployed model adapts to a changing world only through monitored data collection, validation, and retraining, a loop that **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14 ML Operations#^sec-ml-operations|ML Operations]]** develops.

The training memory estimate of [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^sec-neural-computation-memory-training-vs-inference|section 5.4.5.5]] counted four kinds of state. Inference keeps exactly one of them, the weights, and replaces the saved activations with a pair of short-lived buffers. Persistent weights plus rolling activations are the whole of inference memory for a feed-forward network. Batching then trades latency for reuse, and once the network itself is fast, the stages around it can dominate.

↪ When monitored drift should trigger retraining, and what each retraining cadence costs, is developed in **[[01 Books/Volume I - Foundations/04 Deployment/14 ML Operations/V1-14.07 Retraining Decisions#^sec-ml-operations-retraining-decision-framework-e33d|Retraining decision framework]]**.

### Operational Phase Differences

^sec-neural-computation-operational-phase-differences-3f95

A training job chooses a fixed batch of 32 or 1,024 images to keep an accelerator full and runs both passes of the graph, whereas an online digit-recognition service must run the forward pass alone on whatever requests arrive within its latency window. In [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.06 Inference Pipeline#^fig-training-vs-inference|figure 20]], training couples large, uniform batches with a bidirectional loop in which output errors trigger a reverse gradient pass and update; inference executes a strictly unidirectional forward pass over smaller, variable batches without backward state retention. Even though the underlying network weights are identical, the execution graph changes: training-only regularizers such as dropout are stripped away, and adjacent matrix operations and activations can be fused or quantized (stored in fewer bits) into specialized serving kernels.

![[90 Assets/Volume I/05 Nn Computation/Generated Figure d8297f1d9e.svg]]

Figure 20: **Inference vs. Training Flow**: Both flows run the same fully connected network; the batch outlines (dashed and varied for inference, solid and uniform for training) mark the two operating regimes.

^fig-training-vs-inference

These differences determine which hardware each phase runs on and how it is deployed. Training clusters rely on high-bandwidth, high-memory accelerators backed by hundreds of watts per socket and dedicated data-center cooling.[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.13 Footnotes#^fn24|²⁴]] Inference deployments on constrained hardware prioritize bounded tail latency (the latency of the slowest few percent of requests) and energy efficiency across diverse platforms. Mobile devices execute on low-power neural processing units (typically 2–4 W), edge servers employ dedicated inference accelerators,[[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.13 Footnotes#^fn25|²⁵]] and cloud instances use reduced numerical precision to saturate dedicated matrix-multiply units (NVIDIA’s versions are called Tensor Cores). At scale, production serving introduces operational requirements that do not arise in isolated training runs, including dynamic request batching, load balancing, and failure isolation. [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.06 Inference Pipeline#^tbl-forward-pass-comparison|Table 10]] contrasts how the two phases execute the same forward equations under different state rules.

↪ Tensor Cores, which execute a small matrix multiply-accumulate per instruction and set the reduced-precision peak rates quoted for data center GPUs, are developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-tensor-cores-771f|Tensor Cores]]**.

| **Characteristic**     | **Training Forward Pass**                         | **Inference Forward Pass**                       |
|:-----------------------|:--------------------------------------------------|:-------------------------------------------------|
| **Activation Storage** | Retains values required by the backward pass      | Retains the current input and output buffers     |
| **Memory Pattern**     | Saves or recomputes selected intermediate states  | Reuses buffers as successive layers complete     |
| **Computational Flow** | Same matrix products; each layer input is kept    | Same matrix products; each input freed after use |
| **Resource Profile**   | Weights, gradients, optimizer state, saved inputs | Weights plus the largest adjacent buffer pair    |

Table 10: **Training vs. Inference Forward Pass**: Both phases execute the same forward equations, but they manage state differently. Training must retain or recompute the values required by the backward pass and also carries gradients and optimizer state. Inference can reuse a rolling pair of layer buffers.

### Memory and Computational Resources

^sec-neural-computation-memory-computational-resources-d02b

Pricing the inference column of [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.06 Inference Pipeline#^tbl-forward-pass-comparison|table 10]] separates persistent parameter storage from transient buffer reuse. For the canonical MNIST network (784 → 128 → 64 → 10), the persistent parameter block holds 109,386 parameters, or about 438 KB at 32-bit floating point precision, which must remain available for every request. The layer-level counts in [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.04 Neural Network Fundamentals#^tbl-nn-computation-mnist-params|table 5]] show why this persistent block is straightforward to plan: each fully connected layer performs one multiply-add per weight, so parameter memory and per-sample arithmetic scale together.

Transient activation storage is where buffer reuse cuts the footprint. Whereas retained-activation training holds all layer outputs simultaneously across the network depth ($\sum_{\ell} {M_{\text{activations}}}^{({\ell})}$, where ${M_{\text{activations}}}^{({\ell})}$ is the byte size of layer ${\ell}$’s activations), a sequential feed-forward inference pass needs layer ${\ell}$’s buffer only until layer ${\ell}+1$ has produced its output. Once layer ${\ell}+1$ finishes, the buffer for layer ${\ell}$ is dead and its storage can be overwritten, reducing peak transient activation memory from the cumulative sum to the largest adjacent pair, $\max_{\ell} \big({M_{\text{activations}}}^{({\ell})} + {M_{\text{activations}}}^{({\ell}+1)}\big)$. A skip connection or any other later consumer extends a buffer’s lifetime and must enter that plan. The static memory planners that serving runtimes build on this property are developed in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.07 Inference Runtime Selection#^sec-model-serving-specialized-inference-engines-475f|Specialized inference engines]]**.

For the running network at batch size 32, that rule produces the inference column of [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^tbl-nn-computation-mnist-memory-budget|table 9]]. Inference holds the 438 KB parameter block plus a rolling activation pair of about 117 KB, roughly 554 KB in all. The training step of [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^tbl-nn-computation-mnist-memory-budget|table 9]] holds about 1.9 MB, 3.4× as much, for the same weights and the same forward arithmetic. The entire difference is state that training keeps and inference does not: saved activations, gradients, and optimizer buffers. Fixed parameters and short buffer lifetimes also make inference easier to optimize, and batching is the first lever.

### Optimizing Inference Throughput and Latency

^sec-neural-computation-performance-enhancement-techniques-692f

Serving one request at a time (${B}=1$) turns every fully connected layer into a matrix-vector product. That product reads each weight from memory only to use it in a single multiply-accumulate (${z}_j \leftarrow {z}_j + {x}_i {W_{ij}}$), leaving arithmetic intensity at about 0.5 FLOP/byte (notebook [5.1](https://mlsysbook.ai/vol1/05_nn_computation/05_nn_computation.html#nbk-nn-computation-counting-ops-forward-pass)). Because inference freezes parameters and eliminates backward state, runtime engines can plan batching, memory layout, operator scheduling, and numerical precision against the physical limits of the target processor.

Input batching trades per-request latency against hardware efficiency. Aggregating requests into a batch turns that matrix-vector product into a matrix-matrix product that reuses each loaded weight across all ${B}$ inputs, raising the MNIST network’s intensity to about 11.9 FLOP/byte at batch 32. Weight reuse matters most when parameters stream from off-chip memory and the workload sits below the machine’s ridge point; a model as small as MNIST can instead keep its weights in cache from one request to the next.

Batching also increases the activation values produced: the MNIST network produces 202 layer-output values per image (986 values including the input), or 6,464 layer-output values for a batch of 32. Because inference keeps only the largest adjacent pair of activation buffers live at once ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.06 Inference Pipeline#^sec-neural-computation-memory-computational-resources-d02b|section 5.5.2]]), batching multiplies that rolling pair, and with it peak activation memory, by the batch size. Production systems serving interactive traffic must also limit the wait to accumulate inputs according to their service-level latency budget.

↪ How serving systems batch incoming requests dynamically to amortize parameter transfers is developed in **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13.06 Throughput Optimization#^sec-model-serving-static-vs-dynamic-batching-fd0a|Static vs. dynamic batching]]**.

The stages around the network have a different computational profile from the forward pass. While neural network execution exploits massively parallel matrix units on accelerators, preprocessing (such as image decoding and normalization) and postprocessing (such as argmax reduction, threshold checking, and message serialization) often execute on the host CPU, although implementations can parallelize or accelerate them. Amdahl’s law, met in the introduction and developed for accelerated systems in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^sec-hardware-acceleration-ai-hardware-acceleration-fundamentals-9b28|Anatomy of an Accelerator]]**, caps end-to-end speedup at one divided by the fraction of time that is not accelerated, however fast the accelerated part becomes. As accelerator kernels drive forward-pass execution times toward zero, these unaccelerated CPU stages and their associated Peripheral Component Interconnect Express (PCIe) data transfers can come to dominate end-to-end request latency.

Three further mechanics complete the inference design space. Kernel fusion keeps a layer’s intermediate results in on-chip storage instead of writing them to off-chip memory between the matrix multiply, the bias addition, and the activation (**[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.04 Execution from Graphs to Kernels#^sec-ml-frameworks-execution-strategy-matters-memory-wall-1ce8|The memory wall and kernel fusion]]**). Quantization stores frozen weights in fewer bits, which inference tolerates better than training because no small gradient updates must survive (**[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-posttraining-quantization-bb5b|Post-training quantization]]**). Autoregressive transformers, language models that generate their output one token at a time, add a key-value cache of intermediate results from earlier tokens that grows with every token generated (**[[01 Books/Volume I - Foundations/02 Development/06 Network Architectures/V1-06.08 Transformers Parallel Sequence Processing#^sec-network-architectures-inference-memory-bandwidth-wall-98d1|Autoregressive decoding]]**).

The complete lifecycle of the running network, from architecture through training to inference, is now a set of operations with quantifiable costs. Those estimates were made in a controlled setting, with clean data, no deadline, and an unchallenged machine. A production deployment, where none of those conditions holds, is the real test of whether they are complete.

**Batching trade**: can you explain why batching raises arithmetic intensity at batch size ${B} > 1$, what it costs in activation memory and per-request latency, and why serving systems cap the wait to fill a batch?

Recognizing a digit was not always a benchmark. Decades before large datasets and specialized accelerators, the same task ran in production, in the mail-sorting and check-reading systems where neural inference first met a physical deadline.

**Self-Check: Question**

1.  A real-time voice transcription service has a strict $\text{p99}$ end-to-end latency budget of $50\text{ ms}$. In configuring the serving infrastructure for the acoustic model, which batching strategy best aligns with this requirement?

    1.  Choose the policy only from peak accelerator utilization: the largest stable batch is always best for a tight latency SLO.
    2.  Fix batch size at $64$ and avoid any explicit waiting bound, because a consistent large batch is the most reliable way to manage tail latency.
    3.  Use measured arrival patterns, queueing behavior, batch-execution times, and other pipeline-stage latencies to choose a maximum batch size and an explicit waiting bound that fit within the end-to-end deadline, then validate the policy under representative traffic.
    4.  Minimize average latency on an unloaded test host, then keep that batch size in production even if arrival patterns and queueing behavior change.

2.  Why can an inference serving runtime for a sequential feed-forward network achieve a significantly smaller memory footprint than a training runtime for the exact same model architecture, beyond the omission of optimizer states and gradients?

    1.  Inference converts all parameter tensors into single-bit binary hash tables.
    2.  Inference requires no backward pass, allowing intermediate activation buffers to be immediately recycled or overwritten once their single downstream consumer layer finishes execution.
    3.  Inference executes all network layers simultaneously in parallel, eliminating the need for intermediate buffers.
    4.  Inference executes exclusively within on-chip CPU registers, bypassing main memory completely.

3.  Why is reduced numerical precision (such as 8-bit integer quantization, INT8) generally much more practical to deploy during inference than during model training?

    1.  Inference has no small iterative parameter updates or gradient accumulation to preserve, so reduced precision is often practical to test, but rounding can still propagate through forward layers and any INT8 speedup requires supported kernels or hardware plus calibration and quality validation.
    2.  If the quantized weights fit in memory, that alone guarantees inference quality and latency comparable to higher precision.
    3.  A single calibration set is sufficient to guarantee correct INT8 behavior for every slice of future production traffic.
    4.  INT8 is universally faster whenever it reduces bytes moved, so if a model can run in INT8 it should replace FP32 or BF16 without further checks.

4.  A computer vision inference service has a target $\text{p99}$ latency SLO of $100\text{ ms}$. For one measured representative request, the non-overlapping stages are: image JPEG decoding $45\text{ ms}$, resizing and normalization $30\text{ ms}$, neural network inference $15\text{ ms}$, and JSON response serialization $25\text{ ms}$. If inference alone becomes $2\times$ faster, what is the new computed request latency, and why does that result alone still not establish whether the service meets the $\text{p99}$ SLO? What should be profiled next?
