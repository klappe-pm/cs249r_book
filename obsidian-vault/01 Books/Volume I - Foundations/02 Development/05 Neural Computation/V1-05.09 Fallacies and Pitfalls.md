# V1-05.09 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05 Neural Computation|V1-05 Neural Computation]]

^sec-neural-computation-fallacies-pitfalls-3422

Statistical learning adds failure modes that line-by-line code inspection alone cannot reveal. Each of the recurring mistakes below treats a property of the data, the optimization, or the machine as if the model’s source code alone decided it.

**Fallacy**: *Neural networks are entirely opaque and cannot be debugged.*

Neural networks do not offer the line-by-line causal trace of traditional code, but they are not beyond diagnosis. Activation visualization can reveal learned patterns, gradient analysis measures local input sensitivity, and ablation studies estimate component contributions. These tools provide partial evidence rather than a complete explanation: gradient-based saliency maps (per-input sensitivity heat maps) can be unstable, correlated features complicate attribution, and an ablation may change the behavior it is meant to probe. For the MNIST classifier in [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.04 Neural Network Fundamentals#^sec-neural-computation-network-architecture-fundamentals-1f58|section 5.3.2]], first-layer weights can still provide a useful check on what patterns the model has learned. Debugging a statistical system therefore combines model-level probes with data slices, controlled interventions, and end-to-end evaluation.

**Pitfall**: *Discarding domain expertise because a deep model is available.*

Teams assume automatic feature learning removes the need for domain knowledge. Successful systems require domain expertise at every stage: architecture selection, training objective design, dataset curation, and output interpretation. The document-recognition history in [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.07 Handwritten Digit Recognition#^sec-neural-computation-case-study-usps-digit-recognition-97be|section 5.6]] shows why confidence thresholds must reflect operating economics and route uncertain cases to human operators. Without domain knowledge, teams can deploy networks that look strong on a test set but fail in production because their thresholds, fallback paths, or error costs are wrong.

**Fallacy**: *Deeper networks are always more accurate than wider ones.*

Engineers assume that stacking more layers is the primary path to higher accuracy, since depth enables hierarchical feature extraction. In practice, depth alone encounters diminishing returns. ResNet showed that very deep residual networks can train effectively, yet its 1,202-layer CIFAR-10 network tested worse than its 110-layer counterpart ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-he2016|He et al. 2016]]). EfficientNet later showed that compound scaling, which grows width, depth, and input resolution together, can outperform depth-only scaling at a given resource budget ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-tan2019efficientnet|Tan and Le 2019]]). Depth itself is not the problem; scaling it alone is. Teams should profile capacity utilization and scale the dimension that gives the best accuracy per FLOP, since depth adds sequential steps and saved activations while width adds arithmetic inside each step ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.04 Neural Network Fundamentals#^eq-depth-width-cost|equation 10]]).

**Fallacy**: *Training data distribution issues can be fixed after model design.*

Teams treat training as mechanically feeding data through architectures. Networks on imbalanced datasets often perform poorly on the minority class: a fraud detector with 99:1 imbalance achieves 99 percent accuracy by always predicting “not fraud” while catching zero fraud cases. The unweighted batch average of [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^eq-batch-loss|equation 16]] can underweight rare but critical classes unless sampling, weighting, loss design, and evaluation address the imbalance. Teams that skip exploratory data analysis may deploy models with strong aggregate metrics but unacceptable minority-class performance.

**Pitfall**: *Deploying research models to production without addressing system constraints.*

Production adds constraints absent from research: latency budgets (50–100 ms end-to-end), memory limits (2–4 GB for edge devices), and concurrent loads (100–1,000 requests per second). The complete pipeline includes preprocessing, inference, and postprocessing ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.06 Inference Pipeline#^sec-neural-computation-inference-pipeline-5372|section 5.5]]). A model achieving 20 ms inference fails its 50 ms budget when preprocessing adds 25 ms and postprocessing adds 10 ms (55 ms total). Separating model development from system design therefore wastes effort on accuracy while ignoring deployment feasibility.

**Fallacy**: *More compute automatically means faster training.*

Teams purchase expensive GPUs expecting proportional speedups, but memory traffic or launch overhead may limit performance instead. Arithmetic intensity tests that hypothesis ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^fig-mnist-roofline|figure 14]]). The MNIST forward pass in [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.05 Learning Process#^tbl-nn-computation-mnist-flops|table 7]] reaches only about 11.9 FLOP/byte at batch 32 (notebook [5.1](https://mlsysbook.ai/vol1/05_nn_computation/05_nn_computation.html#nbk-nn-computation-counting-ops-forward-pass)) and less at batch 1. The ridge point ${R_{\text{peak}}}/{\text{BW}}$, the intensity a workload needs before peak compute becomes the limit, sits above it on both machines at FP32 and far higher at the reduced-precision peak rates of data-center accelerators. A faster chip therefore leaves this workload waiting on memory, or on kernels too small to fill the machine. The roofline model in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]** makes the condition precise, and measured speedup remains the final test.

**Pitfall**: *Extrapolating accuracy improvements without considering diminishing returns.*

Teams may extrapolate a 5-point gain from scaling 10K parameters to 100K into another 5-point gain at 1M. Empirical improvement instead diminishes with scale according to the task, metric, data quality, model family, and scaling regime. Published benchmark histories cannot settle the question either. ImageNet top-5 error fell from AlexNet’s 15.3 percent to 3.6 percent for a ResNet ensemble ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-krizhevsky2012imagenet|Krizhevsky et al. 2012]]; [[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-he2016|He et al. 2016]]) while training compute rose by more than an order of magnitude ([[01 Books/Volume I - Foundations/02 Development/05 Neural Computation/V1-05.12 Source References#^ref-amodei2018ai|Amodei and Hernandez 2018]]). Those systems, however, mix new architectures with more compute, so they do not isolate the return on scale alone. Teams must therefore measure marginal return within one model family in their own regime rather than extrapolate linearly.

These fallacies and pitfalls share a common root: treating statistical behavior as if code behavior alone determined it. Recognizing them early directs attention toward the appropriate measurements and diagnostics.

**Self-Check: Question**

1.  An engineering team migrates a small multilayer perceptron inference workload with low arithmetic intensity from a CPU to a high-end GPU featuring $10\times$ higher peak TFLOP/s, but observes less than a $1.2\times$ end-to-end speedup. Which systems explanation correctly diagnoses this outcome?

    1.  The workload may be limited by memory traffic, launch overhead, or underutilization rather than peak arithmetic throughput, so the next step is to measure bandwidth use, kernel timelines, achieved utilization, and end-to-end stage breakdowns.
    2.  The model should be tuned only for the highest achieved TFLOP/s metric, because low arithmetic intensity means memory behavior is no longer informative.
    3.  The small speedup proves the CPU implementation is already optimal, so further measurement of competing bottlenecks is unnecessary.
    4.  Because GPU utilization is lower than peak TFLOP/s, the only meaningful next step is to increase parameter count until the accelerator saturates.

2.  On a fraud detection dataset where $99.5\%$ of transactions are legitimate and $0.5\%$ are fraudulent, a newly trained classifier achieves $99.4\%$ aggregate accuracy on held-out test data. Why is this aggregate metric deceptive from an ML systems engineering standpoint?

    1.  Cross-entropy loss is undefined when class proportions differ by more than $10\times$.
    2.  An accuracy of $99.4\%$ exceeds the theoretical mathematical limit of floating-point representation.
    3.  A naive baseline that blindly predicts ‘legitimate’ for every transaction achieves $99.5\%$ accuracy; an aggregate $99.4\%$ accuracy can conceal a near-$100\%$ failure rate on detecting actual fraud cases.
    4.  High accuracy on an imbalanced dataset causes immediate GPU out-of-memory errors during inference.

3.  A development team attempts to improve model accuracy by repeatedly stacking additional layers to a neural network (scaling depth alone) without modifying layer widths or input resolution. Why does this depth-only scaling strategy typically suffer from diminishing returns and training instability?

    1.  Adding layers automatically reduces total parameter count by compressing intermediate representations.
    2.  Increasing depth alone elongates the backpropagation chain-rule path, amplifying vanishing and exploding gradient risks while increasing sequential execution latency, without providing the balanced capacity gains of compound scaling across width, depth, and resolution.
    3.  Modern GPU hardware architectures cannot allocate computational graphs with more than 10 layers.
    4.  Deeper networks are legally restricted from using nonlinear activation functions.

4.  A colleague argues that ‘because neural networks contain millions of weights functioning as an uninterpretable black box, they cannot be systematically debugged when prediction errors occur.’ Refute this claim by describing three concrete systems diagnostic techniques used to debug neural models.

5.  During a model training run, an engineer observes that training loss continuously decreases across 50 epochs, but validation loss reaches a minimum at epoch 20 and increases steadily thereafter. Diagnose the model’s operational regime and describe a sensible next workflow.
