# V1-08.09 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training|V1-08 Model Training]]

^sec-model-training-fallacies-pitfalls-cf7d

The approach developed throughout this chapter quantifies costs through the iron law, diagnoses bottlenecks through profiling, applies targeted optimizations, and scales only when necessary. The following fallacies and pitfalls are the errors that most often waste training compute.

**Fallacy**: *Larger models always yield better performance.*

Teams sometimes treat scale as a monotonic lever: if a 7B-parameter model works well, a 20B-parameter model must work better. A 20B model requires approximately 320 GB of nonactivation training state in the stated mixed-precision Adam recipe (40 GB FP16 parameters + 40 GB FP16 gradients + 80 GB FP32 master weights + 160 GB Adam states). Whether it outperforms a 7B model depends on data quantity and quality, training compute, optimization, and evaluation, not on parameter count alone.

**Pitfall**: *Assuming distributed training automatically accelerates development.*

More accelerators do not guarantee faster training because communication, smaller local batches, input limits, and imbalance can consume the gain. The chapter’s own derivation shows the mechanism: splitting GPT-2 XL’s batch of 32 across eight H100s shrinks each replica’s compute while the gradient bytes stay fixed, so unoverlapped synchronization grows to about 14 percent of the step. In a hypothetical 8 GPUs scenario, the same effect lets synchronization occupy 30–50 percent of step time, so speedup reaches only 4–6× rather than the ideal 8×. The decision requires measured end-to-end time and scaling efficiency.

**Fallacy**: *Hyperparameters transfer directly from small-scale experiments to large-scale training.*

A learning rate that works at batch size 512 may not transfer to batch size 4,096. The linear scaling rule ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-goyal2017accurate|Goyal et al. 2017]]) would increase the rate from 0.1 to 0.8 for this eightfold change, often with warmup, but it is an empirical recipe rather than a requirement or convergence guarantee. Large-scale runs must validate the learning rate, schedule, optimizer state, and effective batch together.

**Pitfall**: *Treating mixed precision training as a simple toggle without validation.*

The H100’s peak ratios bound the gain at 2× over the TF32 Tensor Core path and 15× over FP32 scalar units, but elementwise kernels, optimizer updates, and input waits do not speed up with the matrix units, so the measured gain is smaller. FP16 commonly requires loss scaling ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-micikevicius2017mixed|Micikevicius et al. 2018]]), while BF16 usually does not ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-google-bfloat16-3450e2b6|Wang and Kanwar 2019]]; [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-kalamkar2019|Kalamkar et al. 2019]]) ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-mixedprecision-training-9218|section 8.6.3]] compares the two formats). Either recipe can change numerical behavior, so throughput and convergence must be validated on the target workload.

**Fallacy**: *Memory and computation can be optimized independently.*

Memory *and* compute are coupled. In an illustrative profile of one model trained at different physical batch sizes, accelerator utilization drops from 90 percent at batch 256 to 60–70 percent at batch 16, because each kernel receives less work. Gradient accumulation that builds an effective batch of 512 from physical batches of 64 cuts activation memory by 8× but runs 5 percentage points below the utilization of the same batch trained without accumulation. Tuning these parameters independently can therefore extend training time materially, because the utilization lost at the smaller physical batch applies to every step of the run ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-gradient-accumulation-checkpointing-0c47|section 8.6.5]] develops this trade-off).

**Pitfall**: *Budgeting training memory as if it only contains model weights.*

Sizing training memory from weights alone omits gradients, optimizer state, master weights when used, activations, temporary workspaces, and allocator overhead. In the chapter’s mixed-precision Adam recipe, the static state alone is 16 bytes per parameter before activations. Other optimizers and sharding strategies change this budget. Activation memory then depends on batch size, sequence length, architecture, kernels, and checkpointing; no universal multiple of the weight footprint applies.

**Fallacy**: *The accelerator is always the training bottleneck.*

Data loading often creates idle time, yet teams optimize computation first. On the reference H100, ResNet-50’s demand outruns the host cores available to it and leaves the accelerator busy only about 52 percent of the time, and GPT-2 XL with single-core tokenization is busy only about 48 percent. A faster accelerator fixes neither, while parallel preparation and overlap ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-data-prefetching-pipeline-overlapping-e984|section 8.6.2]]) address both. Profile before assuming the GPU is the bottleneck.

**Pitfall**: *Optimizing kernels before profiling the input pipeline.*

Kernel-level tuning is attractive because accelerator utilization is easy to inspect, but a starved accelerator can look like an inefficient one. Before changing precision, rewriting kernels, or adding accelerators, measure dataloader throughput, host preprocessing time, and storage wait. If the accelerator is waiting for batches, feeding it reliably beats faster kernels.

**Self-Check: Question**

1.  A team scales a dense model from 7 billion to 20 billion parameters while keeping the same training-token budget, precision recipe, and optimizer structure. Under the chapter’s fallacies discussion, what is the most defensible conclusion?

    1.  Validation accuracy must improve in proportion to parameter count because the larger model can represent more functions.
    2.  The run will necessarily move to CPU execution because 20B parameters cannot be trained on accelerators.
    3.  The larger model guarantees worse accuracy because fixed-token training always causes catastrophic interference at higher parameter counts.
    4.  The training-state and compute budgets rise substantially under the same dense-model accounting, but model quality is not guaranteed to improve because it still depends on data, optimization, and evaluation.

2.  Explain why directly transferring hyperparameters such as learning rate and weight decay from a batch-size 512 baseline to a batch-size 4,096 distributed run can cause training to underperform, even when raw GPU busy time stays above 90 percent.

3.  Which engineering mistake exemplifies the input-pipeline pitfall described in the chapter’s fallacies and pitfalls?

    1.  Using BF16 mixed precision instead of FP16 on NVIDIA Ampere GPUs.
    2.  Spending weeks hand-tuning custom CUDA attention kernels to achieve 95% peak arithmetic throughput, only to discover in production that the GPU sits idle 50% of the time waiting for single-threaded Python CPU tokenization.
    3.  Setting `pin_memory=True` and `num_workers=8` in a PyTorch DataLoader.
    4.  Checkpointing activations every $\sqrt{N_L}$ layers to reduce peak memory.

4.  A team proposes moving a single-GPU training job to a 16-GPU cluster to achieve a $16\times$ reduction in development cycle time. Explain two reasons why distributed training rarely delivers a linear $16\times$ improvement in developer velocity.
