# V1-08.10 Summary

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training|V1-08 Model Training]]

^sec-model-training-summary-2d06

Training cost is governed by three quantities that this chapter first kept separate and then joined. The training-time law, ${T_{\text{train}}}= {O}/({R_{\text{peak}}} \times {\eta_{\text{hw}}})$, sets the time a run takes, and device power multiplied by that time sets its energy. The four-term memory budget decides what fits, and in a standard mixed-precision Adam recipe the static state alone reaches 8× the FP16 weights before a single activation is stored. The min-of-three pipeline model decides whether the accelerator is fed at all. GPT-2 XL tied the three together. Its $6{P}{D}$ operation count set a run of about 35 days on one H100, its weights, optimizer state, and activations overflowed that accelerator at batch 32 before any arithmetic began, and its single-threaded data loader could starve the device once the step fit.

Every intervention in the chapter relieves one term and burdens another, which is the conservation of complexity at work. Mixed precision raises ${R_{\text{peak}}}$ and shrinks activation memory and traffic, but it leaves the static state unchanged and requires loss scaling or a wider-exponent format. Checkpointing trades extra forward arithmetic for activation memory, accumulation trades update frequency for batch size, prefetching hides input time at the cost of host memory, and FlashAttention removes quadratic HBM traffic by recomputing tiles. Scaling to more devices adds aggregate memory and compute but turns gradient synchronization into a new term on the critical path. The profile, not the menu of techniques, decides which trade is worth making.

The same pressures shaped the hardware. Dense matrix patterns drove Tensor Cores, frameworks exposed them through mixed-precision APIs, and reduced-precision training pushed later accelerators toward BF16 and FP8. The bitter lesson explains why this matters. If capability grows with the computation a general method can absorb, every point of utilization lost to stalls is capability forgone at a fixed budget.

The counting rules developed across the chapter fit on one page ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.10 Summary#^tbl-training-key-equations|table 17]]). Together they estimate, before any profiler runs, how long a run takes, what it costs in energy, whether its step fits in memory, and which stage of its pipeline is the bottleneck.

**Key Takeaways: Why training costs millions**

- **Training cost is an iron-law budget**: ${T_{\text{train}}}= \frac{{O}}{{R_{\text{peak}}} \times {\eta_{\text{hw}}}}$ makes every optimization accountable: reduce work, raise effective throughput, or improve utilization. A change that misses the dominant term only moves cost around the training loop.
- **Memory determines whether a step fits**: Standard mixed-precision Adam holds 16 bytes per parameter, 8× the FP16 inference weights, before activations. Optimizer state and batch-dependent activations, not weights alone, determine whether training fits.
- **Training scope decides which memory terms exist**: Full fine-tuning of Llama 3 8B needs 128 GB of static state, whereas low-rank adapters shrink gradients and optimizer state to 0.11 GB. The frozen weights stay resident, and activations still follow the backward path through every frozen layer.
- **Profiles choose the remedy**: Profile, diagnose, fix, and re-profile, judging utilization by MFU because device busy time is only an upper bound. Compute-bound jobs need better arithmetic or algorithms; memory-bound jobs need less state or traffic; data- and communication-bound jobs need pipeline or parallelism changes.
- **Precision and IO-aware kernels shift bottlenecks**: FP16 with FP32 accumulation can improve throughput and shrink activation memory (the static state is unchanged), while FlashAttention avoids materializing the full ${S}{\times}{S}$ matrix in HBM; realized gains depend on workload and hardware.
- **Checkpointing trades recomputation for memory**: The segment schedule counts retained boundaries and one live reconstructed segment, reducing GPT-2 XL’s batch-32 activations from 85.6 GB to 11.5 GB for about one-third more arithmetic. Use it when memory, not compute, is the limit.
- **Composed optimizations can postpone scale-out**: Mixed precision, FlashAttention, and gradient accumulation turn GPT-2 XL’s 598 GB batch-32 step into a modeled 66.8 GB that fits one H100, for a run of about 35 days. Use relevant local levers before accepting distributed communication and operational overhead.

^callout-takeaways--8-10-7fc4de3e

Training is where the iron law becomes a daily instrument. A profile read against the law names the dominant term, and the engineering task is to apply the least costly intervention that changes it before reaching for more hardware. The analysis took the model and training corpus as given, while changing how the system executed their work, including the extra arithmetic needed for recomputation. A further lever is which examples enter that workload in the first place.

**What’s Next: From training to data selection**

Training produces learned parameters by spending compute on every example. Once the training loop is efficient, the next question is whether every example earns that cost.

**[[01 Books/Volume I - Foundations/03 Optimization/09 Data Selection/V1-09 Data Selection#^sec-data-selection|Data Selection]]** therefore turns upstream from execution to workload composition, and in doing so opens the book’s optimization sequence, which asks whether work is necessary before asking how to simplify or accelerate it. It starts from a supply imbalance. Accelerator fleets can grow usable compute faster than the stock of high-quality data, so extracting more learning from each example begins to matter more than collecting more examples. Its measure is the information-compute ratio, the learning an example returns per unit of training compute, and redundancy, representativeness, uncertainty, and class coverage all enter through it.

A useful subset must reduce work without erasing rare cases or shifting the effective training distribution. When that balance holds, a carefully selected subset can approach full-dataset accuracy while lowering the cost of every epoch and making additional experiments affordable. The optimization target is no longer only how efficiently the system processes an example, but which examples the system should process at all.
