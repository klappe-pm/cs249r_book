# V1-08.05 Pipeline Architecture

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training|V1-08 Model Training]]

^sec-model-training-pipeline-architecture-81c9

A training step is not a single operation but a sequence of dependent stages: data must be loaded before computation can begin, forward passes must complete before backward passes start, and gradients must be computed before parameters can update. The speed of the slowest stage determines the speed of the entire system. Without pipelining, these stages serialize, idling the accelerator while the host prepares data or transfers batches across the bus.

While model execution graphs govern arithmetic on the accelerator, sustained training requires feeding those kernels across physical machine boundaries. Host CPUs ingest raw records from storage and apply preprocessing in host DRAM, while accelerators execute matrix multiplications on data held in HBM. Data must cross the interconnect, typically a PCIe link whose bandwidth is an order of magnitude lower than device memory bandwidth. When upstream data preparation or bus transfer exceeds the duration of the forward and backward passes, the accelerator compute engines starve, reducing the hardware utilization factor ${\eta_{\text{hw}}}$ in the training-time law.

The training system divides into three subsystems. The data pipeline handles ingestion, transformation, and batching on the host; the training loop coordinates forward passes, backward passes, and parameter updates on the accelerator; and the evaluation pipeline periodically assesses model quality on held-out data. The three subsystems decouple across the training lifecycle ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^fig-training-pipeline|figure 2]]): processed batches flow into the core forward/backward training loop, while the evaluation pipeline runs on its own schedule and shares the accelerator with training whenever it scores the model. The interfaces between them form critical synchronization boundaries where I/O latency, interconnect transfers, or synchronous validation pauses can throttle accelerator utilization. The data pipeline supplies two of the three terms of the pipeline bottleneck model defined later ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-training-bottleneck|equation 6]]), host preprocessing and host-to-accelerator transfer. The accelerator training loop supplies the third through matrix compute.

The interfaces between these three pipelines represent critical synchronization boundaries where I/O delays or evaluation pauses can throttle accelerator utilization.

### Pipeline Stages and Accelerator Bubbles

^sec-model-training-staged-pipeline

A training step passes through four stages, a **staged system pipeline** rather than a monolithic loop. If one stage is slower than the rest, the others wait:

1.  **Data Loading & Preprocessing** (CPU/Storage): Fetching raw bytes from Non-Volatile Memory Express (NVMe) storage, decoding samples, and executing transformations on CPU cores.
2.  **Host-to-Device Transfer** (PCIe): Moving the preprocessed batch across the PCIe bus into GPU memory via direct memory access (DMA).
3.  **Forward/Backward Pass** (Accelerator): Propagating activations forward and gradients backward through layer kernels on the GPU.
4.  **Parameter Synchronization** (Interconnect, present only when multiple accelerators train the model): Exchanging gradients between accelerators across the available interconnect fabric. NVLink, NVIDIA’s direct accelerator-to-accelerator link, provides up to 900 GB/s in the H100 configuration examined later, while alternative architectures rely on PCIe switches or scale-out network fabrics.

Any throughput mismatch among these stages creates **accelerator bubbles**, idle windows during which compute units stall while waiting for upstream dependencies. These bubbles stem from imbalances within the per-step pipeline. A systems engineer eliminates them through asynchronous prefetching and pipeline overlapping, staging the next batch into high-bandwidth memory before the active step completes. The first three stages form the analytical basis for the pipeline execution model in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-training-bottleneck|equation 6]], where the slowest stage dictates end-to-end iteration throughput, and [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.06 Identifying Bottlenecks#^sec-model-training-identifying-bottlenecks-f57f|section 8.5]] provides the profiling methods required to isolate that bottleneck.

Those per-step stages map directly onto the subsystem boundaries of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^fig-training-pipeline|figure 2]]. At the ingestion boundary, host workers decode, normalize, and augment raw records ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-lecun2012|LeCun et al. 2012]]) before packing dense batches for PCIe transfer, while at the validation boundary, periodic evaluation on held-out data competes for the same accelerator cores and trades monitoring resolution against training throughput. Within the accelerator itself, the training iteration forms a closed feedback loop governed by strict data and memory dependencies. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^fig-training-loop|Figure 3]] traces this cyclic sequence across three stages (predict, gradients, and update), showing how predictions, the loss, and parameter gradients feed the optimizer before returning updated weights to the next iteration.

![[90 Assets/Volume I/08 Training/Generated Figure b84e51cb2e.svg]]

Figure 3: **The Iterative Training Loop**: Each iteration sequences forward prediction, gradient computation by backpropagation, and an optimizer update. Updated parameters return to the next forward pass while the next batch remains a separate input. Data dependencies and memory residency set the step’s minimum execution time and memory floor.

^fig-training-loop

While [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-mathematical-foundations-d894|section 8.3]] counted the FLOPs and bytes of each operator in this cycle, memory residency and data dependencies govern how the hardware executes them. During the forward pass, intermediate activation tensors must remain resident in accelerator HBM because the backward pass requires them to evaluate chain-rule derivatives. Once gradients are computed, the optimizer reads both the parameters and accumulated gradients to apply the update rule, producing new weights for the subsequent iteration. The memory capacity required to hold activations, weights, and optimizer states establishes the memory floor for the entire training step.

This execution loop repeats across batches and epochs until the optimization converges. Maximizing accelerator arithmetic efficiency requires overlapping these pipeline stages across the system hierarchy. Host CPU threads prefetch and stage batch ${k}+1$ into page-locked (*pinned*) host memory while the accelerator executes batch ${k}$, so the DMA engine can stream it across PCIe asynchronously (**[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.06 Abstraction Tensors, Devices, and Operations#^sec-ml-frameworks-device-memory-management-9404|Devices and memory]]** explains why pinning is required). This concurrent staging hides storage latency and bus transfer time behind matrix-multiplication compute kernels. When this concurrency breaks down, because an I/O-bound data pipeline starves the device of input tensors or frequent evaluation stalls the update loop, the accelerator idles, degrading effective throughput.

### Data Pipeline

^sec-model-training-data-pipeline-8e71

Keeping an accelerator’s arithmetic units saturated requires streaming training examples from persistent storage into device memory at or above the model’s consumption rate. Data engineering posed this as the feeding problem (**[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|The feeding problem]]**) and measured the throughput lost when a slow storage path cannot keep up; training is where that loss is paid on every step. Upstream data engineering prepares and partitions datasets on storage media, while the runtime data pipeline executes concurrently with model computation on the host CPU. ResNet-50 is the chapter’s input-pipeline case, because its images are far heavier for the host to prepare than GPT-2’s token IDs. The stage trace below starts with GPT-2 XL under a scenario assumption, on-the-fly single-core tokenization (production runs usually pre-tokenize), and the system implications then turn to ResNet-50.

The data pipeline bridges raw storage and accelerator execution across the machine boundary. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^fig-data-pipeline|Figure 4]] partitions this data movement across three physical zones: staging raw files from persistent storage into host memory, formatting and augmenting tensors across CPU worker threads, and streaming batched inputs over the interconnect to parallel GPU accelerators.

![[90 Assets/Volume I/08 Training/Generated Figure cc85b50f7c.svg]]

Figure 4: **CPU-to-GPU Data Flow**: Training data transitions through storage, CPU preprocessing, and GPU execution zones. Each stage represents a potential throughput bottleneck; disk read bandwidth, transformation latency, and PCIe host-to-device transfers must collectively sustain the GPU consumption rate to keep accelerators at peak utilization.

^fig-data-pipeline

In the storage zone, raw records reside on local NVMe drives or networked storage systems. In the CPU preprocessing zone, host worker threads decode raw bytes, apply transformations such as tokenization or data augmentation, and collate individual records into dense mini-batch tensors. In the GPU training zone, accelerators transfer those tensors across the PCIe bus and execute forward and backward passes. Because these three zones form a strict pipeline, the slowest stage dictates end-to-end training throughput. In the pipeline model developed below, the storage and CPU zones together set the preprocessing term, the PCIe crossing sets the transfer term, and the GPU zone sets the compute term.

#### Core Components

^sec-model-training-core-components-d28d

Data pipeline throughput originates at the storage subsystem. Upstream layout decisions, such as sequential chunking in columnar or container formats (Parquet, TFRecord, Arrow), dictate the physical I/O patterns presented to the operating system.

↩︎ How file format and storage layout set the data term of the iron law is established in **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.11 Storage and Delivery#^sec-data-engineering-ml-storage-requirements-performance-1b0d|Storage tiers and cost]]**.

Storage throughput is bounded by the slower of two hardware constraints,

$$
{R_{\text{storage}}}= \min({\text{BW}_{\text{disk}}}, {\text{BW}_{\text{network}}}),
$$

where ${\text{BW}_{\text{disk}}}$ is the physical disk bandwidth and ${\text{BW}_{\text{network}}}$ represents the network bandwidth for distributed storage systems. In practice, training workloads rarely achieve this theoretical maximum because data shuffling can turn large sequential reads into smaller, less efficient accesses. Effective storage throughput can be modeled as ${R_{\text{storage,eff}}}= {R_{\text{storage}}}\times {F_{\text{access}}}$, where ${F_{\text{access}}}$ depends on record size, file layout, caching, and storage hardware. When unbuffered random reads degrade ${F_{\text{access}}}$, storage bandwidth drops by an order of magnitude, transforming an I/O system that appears sufficient on paper into a primary training bottleneck.

GPT-2’s 40 GB WebText corpus fits in the host memory of a single training server, so once cached it can be served from system RAM without repeated storage reads, although preprocessing and transfer costs remain. A corpus that exceeds local memory must instead be streamed, and the system must orchestrate storage reads, preprocessing, caching, and delivery throughout training. Whether multiple workers, prefetching, local caches, or distributed storage pay off then depends on which of those stages limits throughput.

#### Preprocessing

^sec-model-training-preprocessing-523c

Once retrieved from storage, raw bytes require CPU transformation into model-ready tensors. While static feature extraction can run offline, dynamic transformations such as on-the-fly tokenization and image augmentation execute during training. Under ideal independent-worker scaling, the CPU worker pool delivers transformation capacity according to [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-preprocess-throughput|equation 5]]:

$$
{R_{\text{preprocessing}}}= \frac{{N_{\text{workers}}}}{{T_{\text{transform}}}} \tag{5}
$$

 where ${N_{\text{workers}}}$ parallel processing threads each perform transformations requiring ${T_{\text{transform}}}$ seconds per batch. Training architectures employ multiple workers to ensure transformation keeps pace with accelerator consumption rates.

^eq-preprocess-throughput

However, transforming records assumes that storage delivers raw bytes fast enough to keep worker queues filled. Under overlapped host staging, the achieved host preparation rate cannot exceed the slower of storage retrieval and CPU transformation. Dividing effective storage throughput ${R_{\text{storage,eff}}}$ by the raw bytes retrieved per batch yields the storage delivery rate in batches per second. When storage delivery lags behind worker demand, additional CPU threads sit idle waiting on disk I/O, capping host throughput regardless of ${N_{\text{workers}}}$. The complete host preparation rate is therefore bounded by the lesser of the storage delivery rate and the worker transformation capacity ${N_{\text{workers}}} / {T_{\text{transform}}}$.

Preprocessed data must then transfer across the host-accelerator interconnect before computation can begin. End-to-end training throughput is consequently constrained by the slowest of three sequential stages, as formalized in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-training-bottleneck|equation 6]]. In this three-stage pipeline model, the host preparation rate ${R_{\text{preprocessing}}}$ captures the joint bound of storage delivery and CPU worker transformation, while the remaining terms capture host-to-device bus transfer and device execution:

$$
{R_{\text{training}}}=\min\left({R_{\text{preprocessing}}}, \frac{{\text{BW}_{\text{host}}}}{{D_{\text{vol}}^{(\text{batch})}}}, \frac{{R_{\text{sustained}}}}{{O_{\text{batch}}}}\right) \tag{6}
$$

 where ${\text{BW}_{\text{host}}}$ is the host-to-accelerator transfer bandwidth, ${D_{\text{vol}}^{(\text{batch})}}$ is the input bytes per batch transferred to the device, ${R_{\text{sustained}}}$ is the accelerator’s sustained compute rate in FLOP/s, and ${O_{\text{batch}}}$ is the forward-backward work per batch in FLOPs. Every term is therefore expressed in batches per second before the minimum is taken.

^eq-training-bottleneck

**Example 8.1: GPT-2 language model data pipeline**

**Scenario**: Quantifying storage access, CPU tokenization, and PCIe host-to-device transfers supplying one H100 training GPT-2 XL at batch 32. The device service interval is the step time the training-time law gives at the chapter’s utilization, about 596 ms per batch; fitting that batch in memory requires the techniques of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-pipeline-optimizations-cd9d|section 8.6]], but the input path does not depend on which ones are used.

**Stage trace**:

1.  **Raw text storage**: The WebText corpus contributes about 40 GB of raw text. Sequential reads from NVMe SSD storage reach 7 GB/s. Under document sampling with access factor 0.1, random-access storage bandwidth drops to 0.70 GB/s, giving ${T_{\text{read}}}= {D_{\text{vol}}} / {R_{\text{storage,eff}}}\approx 0.1\text{ ms}$.
2.  **Tokenization**: A byte-pair encoding (BPE) tokenizer (50,257 vocabulary) converts text into token IDs. For batch size ${B}=32$ and sequence length ${S}=1024$ (32.8K tokens total), a single CPU core processing 50K tokens/s takes ${T_{\text{tokenize}}}\approx$ 655.4 ms per batch.
3.  **Batching and padding**: Padding and packing generate an int64 tensor of shape 32 sequences $\times$ 1,024 tokens, producing 262.1 KB per batch.
4.  **PCIe transfer**: Transferring the tensor across the H100’s PCIe Gen5 x16 link (64 GB/s bandwidth) takes ${T_{\text{transfer}}}=$ 0.004 ms, making bus transfer negligible.

**Systems insight**: Single-core CPU preparation (${T_{\text{prep}}} \approx$ 655.4 ms) exceeds the accelerator service interval (${T_{\text{GPU}}} \approx$ 596 ms), so a serial pipeline pays both costs on every step and the device service stage occupies only about 48 percent of the serial step. Slower preparation increases the exposed input wait. Scaling to 8 parallel worker processes reduces the ideal average interval between prepared batches to ${T_{\text{tokenize}}} / {N_{\text{workers}}} \approx$ 81.9 ms. Prefetching also overlaps ${T_{\text{prep}}}$ with ${T_{\text{GPU}}}$ to keep the device stage supplied throughout ideal steady-state execution, delivering 54 sequences per second on one H100. Parallel workers shorten the interval between batches, not the latency of any one batch, and contention or imperfect overlap can reduce this modeled throughput.

^exmp-training-gpt-2-language-model-data-pipeline

This min-of-three relationship governs training pipeline design because system throughput equals bottleneck throughput. An accelerator with 989 TFLOP/s of compute capacity delivers zero useful work while waiting for data. Conversely, a perfectly optimized data pipeline provides no benefit if the accelerator is already compute-saturated. Balanced pipeline design aligns preprocessing capacity, transfer bandwidth, and compute throughput so that no single stage dominates iteration time. For GPT-2, CPU tokenization, not storage or bus transfer, limits throughput unless parallel workers and prefetching hide host preparation latency.

Data pipeline throughput is not the only flow that can starve the accelerator. Multi-GPU training adds a second stream of traffic: the gradient synchronization required after every step. Once synchronization time exceeds compute time, communication becomes the limiting factor. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-scaling-beyond-single-node-a671|Section 8.7.2]] quantifies that network wall at the point where training crosses the node boundary.

#### System Implications

^sec-model-training-system-implications-2539

Comparing supply with demand requires both in the same unit. Grouping the two host-side terms of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-training-bottleneck|equation 6]] into a single pipeline rate ${R_{\text{pipeline}}}$, in batches per second, and writing the accelerator’s consumption rate as ${R_{\text{accel}}}= {R_{\text{sustained}}}/{O_{\text{batch}}}$, also in batches per second (where ${R_{\text{sustained}}}$ stays in FLOP/s), leaves a coupled system whose throughput is $\min({R_{\text{pipeline}}}, {R_{\text{accel}}})$. When ${R_{\text{pipeline}}}< {R_{\text{accel}}}$, the accelerator sits idle waiting for data, and its busy-time fraction drops proportionally in this ideal supply model, as [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-gpu-utilization|equation 7]] shows. Busy time counts every moment the accelerator is executing, so it is an upper bound on, and distinct from, the model-FLOP utilization defined later in the chapter:

$$
\text{Accelerator Utilization} = \min\left(1, \frac{{R_{\text{pipeline}}}}{{R_{\text{accel}}}}\right) \times 100\% \tag{7}
$$

^eq-gpu-utilization

ResNet-50 shows how quickly that drop arrives on current hardware. One training image costs about 24.6 GFLOP, so the H100’s dense 16-bit peak could consume about 40,200 images/s. A well-tuned training step sustains only part of that ceiling; at the 25 percent fraction implied by the 3,200 images/s that **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04.10 Physics of Data#^sec-data-engineering-feeding-problem|The feeding problem]]** assumed for the previous-generation A100, the H100 consumes about 10,100 images/s. A host worker that decodes and augments 375 images/s would need 28 workers per accelerator to keep up, but an eight-accelerator H100 server provides 112 host cores, 14 per accelerator. Those workers supply about 5,250 images/s, so by [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-gpu-utilization|equation 7]] the accelerator is busy only about 52 percent of the time.

The same host fed an A100 with 9 workers and cores to spare. Upgrading the accelerator raised its appetite 3× without changing the host, which moves ResNet-50 from its home compute-bound regime into an input-bound one. Faster arithmetic adds nothing until the input pipeline is rebalanced, with more host cores per accelerator, decoding on the accelerator, or cached decoded data, and [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-data-prefetching-pipeline-overlapping-e984|section 8.6.2]] takes up the overlap that hides what remains.

#### Data Flows

^sec-model-training-data-flows-0b2e

Training data traverses three memory tiers on its way from disk to accelerator, and the bandwidth gap between these tiers, spanning roughly two orders of magnitude, is the central challenge of data pipeline design. For equal byte volumes at each tier, the effective transfer rate is bounded by $\min({\text{BW}_{\text{storage}}}, {\text{BW}_{\text{system}}}, {\text{BW}_{\text{accelerator}}})$, the same minimum as [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-training-bottleneck|equation 6]] applied to bandwidth tiers. When decoding, tokenization, or reuse changes the bytes handled per batch, each bandwidth must first be divided by its own per-batch byte volume so that the rates are comparable.

![[90 Assets/Volume I/08 Training/Vol1 Training Margin 002 0e857f4d24.svg]]

*Three-rung bandwidth ladder for the training data path on a log scale: NVMe storage around 7 GB/s, system DRAM around 50 GB/s, and H100 HBM around 3,350 GB/s.*

*Bandwidth steps up the storage to DRAM to HBM hierarchy.*

Local NVMe storage provides 7 GB/s, system memory delivers 50 GB/s, and the H100’s HBM delivers 3350 GB/s. Each tier is roughly an order of magnitude or more faster than the one below it, which means data that flows freely within accelerator memory creates a bottleneck when it must be fetched from disk.

Stated in time rather than rate, the pipeline model covers the case where stages overlap correctly, fetching the next batch from storage while preprocessing the current one and transferring the previous one to the accelerator. In that case the steady-state input service interval, the time between successive batches the input path delivers, is governed by the *maximum* of the stage times, ${T_{\text{iteration}}}= \max({T_{\text{fetch}}}, {T_{\text{process}}}, {T_{\text{transfer}}})$, rather than their *sum*. This overlap is what prefetching seeks to achieve, with each tier operating concurrently on different batches. End-to-end training must also include accelerator compute and any exposed synchronization or evaluation time.

#### Practical Architectures

^sec-model-training-practical-architectures-d54d

Sustaining that stage overlap across the storage-to-HBM gap is harder in practice because an NVMe drive rated at 7 GB/s delivers only 3.50 GB/s if, as assumed here, it sustains about half of its rated peak, and small random reads during dataset shuffling degrade throughput further depending on access size, queue depth, file layout, and caching. To keep accelerators fed despite this bandwidth reduction, pipeline architectures maintain multiple data buffers simultaneously: prefetch buffers loading future batches, processing buffers holding data under transformation, and transfer buffers staging data for accelerator consumption. The total host memory required scales with the per-batch memory footprint ${M_{\text{batch}}}$ according to [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-buffer-memory|equation 8]]:

$$
{M_{\text{required}}}= ({N_{\text{prefetch}}}+ {N_{\text{processing}}}+ {N_{\text{transfer}}}) \times {M_{\text{batch}}} \tag{8}
$$

^eq-buffer-memory

To avoid starving the accelerator, the average preprocessing service time per batch across all workers must not exceed the compute time per batch (${T_{\text{preprocessing}}}\leq {T_{\text{compute}}}$), which restates the preprocessing term of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-training-bottleneck|equation 6]] in time. If preprocessing takes 40 ms per batch on one worker while the accelerator consumes a batch every 10 ms, ideal scaling requires at least four workers. Actual worker requirements depend on storage throughput, CPU contention, and transformation cost, which [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-data-prefetching-pipeline-overlapping-e984|section 8.6.2]] examines through prefetching and parallel workers.

### Forward and Backward Pass

^sec-model-training-forward-pass-9695

The operation counts in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-matrix-operations-1f21|section 8.3.1.1]] become a scheduling problem once a prepared batch reaches the forward pass: the runtime must launch kernels with enough parallel work, stage their operands, and keep the values required by backward execution.

#### Compute Operations

^sec-model-training-compute-operations-83ee

A dense layer’s FLOP count is already fixed by its input width, output width, and batch size. Its execution time also depends on how that work fills the accelerator. A layer with dimensions of $512 \times 1024$ at batch 64 supplies 33.6 million MACs, or 67.1 MFLOP; the kernel must divide this work among execution units without leaving a mostly empty final wave, a last round of work that occupies only a few of the execution units while the rest sit idle.

Accelerators execute these parallel workloads by grouping execution threads into fixed-size units: warps[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.13 Footnotes#^fn14|¹⁴]] of 32 threads on NVIDIA architectures, or wavefronts of 64 threads on AMD architectures. Warps run on streaming multiprocessors (SMs), the many identical compute cores replicated across a GPU (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-evolution-simd-simt-architectures-e1fd|From SIMD lanes to SIMT threads]]**). Execution efficiency therefore depends on choosing tensor dimensions that divide evenly into warps and into the operand shapes that specialized units like Tensor Cores require.

**Systems Perspective 8.3: Wave quantization and tail effects**

A common mistake in ML systems is ignoring the fixed execution granularity of GPU kernels. GPU execution is quantized into waves of work, but the relevant unit is the kernel’s thread or tile mapping, not necessarily one sample per thread.

Warps make the granularity concrete. In the illustrative special case where one independent work item maps to one thread, 32 items fill one warp while 33 items require a second, mostly empty warp. Neural-network kernels usually map each sample to many threads, so batch size alone does not determine this utilization.

On a large GPU such as the NVIDIA H100 with 132 SMs, where each SM schedules groups of warps, the hardware processes thousands of threads in a single wave. If the total workload slightly exceeds a wave boundary (for example, 1.01 waves), the hardware must execute a second, nearly empty wave to completion before the next task begins.

[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^tbl-training-wave-quantization|Table 6]] quantifies that one-item-per-thread illustration. It is not a general batch-size performance model.

| **Independent Work Items** | **Warps Needed** | **Lane Utilization** | **Relative Time** |
|:---------------------------|:----------------:|:--------------------:|:-----------------:|
| 32                         |        1         |         100%         |     1$\times$     |
| 33                         |        2         |        51.6%         |        ~2×        |
| 64                         |        2         |         100%         |     1$\times$     |
| 65                         |        3         |        67.7%         |       ~1.5×       |

Table 6: **Illustrative Warp-Tail Arithmetic**: Under a one-work-item-per-thread mapping, counts just above a 32-thread boundary launch a partially filled warp, so 33 items use two warps while 64 fill the same two warps. Actual training kernels map tensors to threads and tiles in implementation-specific ways, often assigning many threads to each sample, so these values cannot be inferred from batch size alone. Profiling must identify the kernel’s real mapping and wave boundaries.

^tbl-training-wave-quantization

**Systems insight**: The table teaches the shape of the penalty, not its size for any real kernel. The actionable rule is to choose batch, sequence, and hidden dimensions that are multiples of the kernel’s tile size and that divide into whole waves across the SMs, then benchmark the neighboring candidates. Profiling reveals partially filled warps or waves; batch size alone cannot.

Beyond dense matrix multiplication, distinct neural architectures introduce specialized computational patterns. Convolutional networks, for instance, slide spatial filters across multichannel input tensors. Consider an input tensor of dimensions $64 \times 224 \times 224 \times 3$ (batch size $\times$ height $\times$ width $\times$ channels) processed by $7 \times 7$ kernels. Each position requires 147 multiply-accumulate operations, and with 64 filters operating across the $218 \times 218$ output positions of a convolution with stride 1 and no padding, the arithmetic work reaches hundreds of millions of multiply-accumulate operations per image. ResNet-50’s own first layer uses a stride of 2, which shrinks its output to 112 by 112, the size the memory analysis below uses. Accelerators usually execute these convolutions on the same matrix-multiply units as dense layers, after rearranging the input so that each filter application becomes part of one large matrix product.

The other operator families impose different scheduling constraints. Attention alternates batched matrix products with row-wise reductions, while normalization requires statistics before normalized outputs can be produced. The arithmetic-intensity analysis in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-arithmetic-intensity-training-bottlenecks-4446|section 8.3.4]] explains their traffic cost; the runtime must additionally respect these reduction dependencies and choose which intermediates can remain inside a fused kernel.

Optimized operator libraries such as cuDNN ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-chetlur2014cudnn|Chetlur et al. 2014]]) implement multiple computational algorithms for each layer type, dynamically selecting among them based on tensor dimensions, scratchpad memory limits, and hardware capabilities. For convolution, cuDNN weighs the extra workspace memory each algorithm needs against the arithmetic it saves ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-nvidia2023cudnn896|NVIDIA Corporation 2023a]]). These hardware utilization patterns reinforce the coupling between batch size and hardware efficiency established in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-gradientbased-optimization-methods-9798|section 8.3.2.1]]: larger batch sizes saturate accelerator compute units and amortize memory transfers, but increase intermediate activation storage.

#### Memory Management

^sec-model-training-memory-management-c1ec

Memory management becomes the central concern during the forward pass, when intermediate activations must be retained in high-bandwidth memory for gradient computation during backpropagation. How quickly that retained state grows depends on the architecture, as a convolutional network shows.

Consider ResNet-50 processing images at 224 $\times$ 224 resolution with a batch size of 32. The initial convolutional layer produces activation maps of dimension 112 $\times$ 112 $\times$ 64; per image at single-precision (4 bytes), this requires approximately 3.2 MB. For an illustrative capacity budget, assume retained forward activations total 8 GB, the backward pass adds another 4 GB of working set for activation gradients, and model parameters consume 102.2 MB. Activation gradients are the gradients with respect to each layer’s outputs that the backward pass computes on its way upstream; they are distinct from the stored parameter gradients, and their size here is a supplied scenario assumption. This 12.1 GB subtotal excludes parameter gradients, optimizer state, and additional runtime workspace; those terms must be added before deciding whether training fits.

Under the same linear-scaling assumption, doubling the batch size to 64 doubles activation storage: forward activations reach 16 GB and the activation-gradient working set reaches 8 GB, raising this subtotal to 24.1 GB. In vision models with large spatial resolutions, activations dominate the memory footprint while parameter storage (102.2 MB) is negligible. For large language models, the balance inverts: GPT-3 (175B parameters) requires approximately 700 GB for parameters alone in FP32 (350 GB in FP16), exceeding single-accelerator capacity before allocating any activation memory or optimizer state.

During backpropagation ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-backpropagation-mechanics-0b64|section 8.3.3]]), the backward pass traverses that network in reverse order, consuming retained forward activations to compute parameter and activation gradients at roughly twice the arithmetic cost of the forward pass. Memory requirements shift dynamically across layers as activations are freed and gradient buffers are populated. In ResNet-50, mid-network layers expand to 256 filters from the initial 64, where reduced spatial map dimensions partly compensate for higher channel depth, so the peak memory footprint reflects retained forward activations, active gradient buffers, temporary workspaces, and the runtime allocation schedule rather than the width of a single layer alone.

Because accelerator memory (80 GB on the reference H100) must hold those peak activations, parameters, gradients, and optimizer states simultaneously, memory capacity rather than compute throughput frequently caps the feasible batch size. Two system-level techniques analyzed in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-pipeline-optimizations-cd9d|section 8.6]] relieve this capacity bottleneck. Activation checkpointing discards intermediate activations during the forward pass and recomputes them during the backward pass, trading redundant arithmetic for reduced storage, while mixed-precision training halves storage per value for tensors represented in 16-bit formats instead of FP32 (leaving FP32 master weights and optimizer state accounted for separately in the memory budget). Once the backward sweep finishes releasing activations and populating the parameter gradients, execution reaches the parameter update boundary.

### Parameter Updates

^sec-model-training-parameter-updates-optimizers-b1a4

Once backward execution populates the gradient buffers, the optimizer consumes them and updates the persistent state defined in [algorithm 1](https://mlsysbook.ai/vol1/08_training/08_training.html#algo-adam-update). The important pipeline boundary is the weight mutation: the next forward pass must observe the completed update. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^lst-param-update-34a879b8|Listing 2]] shows that boundary at the framework interface.

``` python
loss.backward()  # Compute gradients
optimizer.step()  # Update parameters
```

Listing 2: **Parameter Update**: Computes gradients and applies an optimizer step to model parameters. Repeating this cycle seeks to minimize the training objective, although improvement is not guaranteed on every step or epoch.

^lst-param-update-34a879b8

The optimizer’s memory traffic is exposed on this dependency path. The FP32 Adam update, which moves 28 bytes per parameter in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-framework-optimizer-interface-82ff|section 8.3.2.4]], must finish before the next forward pass reads those weights. Fusing moment updates and weight writes can shorten this interval by reducing passes over HBM, even when the forward and backward matrix products already use the arithmetic units efficiently.

#### Batch Size and Parameter Updates

^sec-model-training-batch-size-parameter-updates-4d0b

Increasing batch size improves accelerator utilization by raising the arithmetic intensity of matrix multiplications and reducing synchronization frequency, but it also alters optimization dynamics. Scaling batch size without retuning the learning-rate schedule can degrade convergence, creating an optimization gap where hardware efficiency comes at the expense of model quality. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^fig-linear-scaling-failure|Figure 5]] isolates this dynamic across synthetic loss trajectories: holding the learning rate fixed while expanding from batch 32 to batch 256 leaves an acute optimization gap (dashed silver curve), whereas linearly scaling the learning rate brings convergence close to the baseline path (green curve).

![[90 Assets/Volume I/08 Training/Cell 34 Output 1 fd4a3f5ac6.png]]

Figure 5: **Illustrative Linear-Scaling Scenario**: Synthetic training-loss curves (arbitrary units) compare a batch-32 baseline with batch 256 under a fixed or linearly scaled learning rate. The curves illustrate why increasing batch size may require retuning; they are not measured traces or a guarantee that linear scaling preserves convergence.

^fig-linear-scaling-failure

For a fixed token budget, doubling the global batch size halves the number of parameter updates per epoch. To traverse a comparable distance in parameter space with fewer updates, the linear scaling rule of the large-batch ResNet-50 recipe in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-minibatch-processing-4eb0|section 8.3.2.1.2]] scales the learning rate proportionally with batch size (${\eta_{\text{new}}} = {\eta_{\text{base}}} \times {B_{\text{new}}}/{B_{\text{base}}}$), although the rule does not guarantee equivalent convergence or generalization. Beyond the critical batch size defined in the same section, further batch expansion yields diminishing returns per training sample while escalating memory pressure.

Beyond convergence dynamics, batch size dictates communication frequency in distributed systems. A larger global batch reduces the number of optimizer steps and gradient synchronizations per epoch. Because the communication payload of dense AllReduce synchronizations, the collective step that sums gradients across accelerators so every copy of the model applies the same update ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-data-parallelism-ad1c|section 8.7.1.1]]), depends on parameter count rather than batch size, larger batches amortize interconnect latency over more compute FLOPs. In distributed settings, local micro-batch size and global batch size jointly determine the maximum degree of data parallelism. When memory capacity constrains the local micro-batch, gradient accumulation ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-gradient-accumulation-checkpointing-0c47|section 8.6.5]]) decouples the effective batch size from per-device activation memory, accumulating gradients across multiple forward-backward passes before triggering an optimizer step.

### Training State and Checkpoints

^sec-model-training-training-state-checkpoints-5b3e

A run that takes 35 days on one accelerator does not run uninterrupted. Hardware fails, jobs are preempted, and numerical instabilities corrupt weights, so a training system must save the run’s state to storage at intervals and restore it exactly. That saved state is a different mechanism from the activation checkpointing of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-activation-checkpointing-2ee1|section 8.6.5.2]], which recomputes values inside one step; a training checkpoint is a file that carries the run across steps.

Resuming requires restoring model weights and optimizer state in lockstep: first-moment vectors, second-moment variance estimates, and step counters. In the mixed-precision Adam recipe of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-optimization-algorithm-system-implications-f9f2|section 8.3.2.3]], a checkpoint holds the FP16 working weights (2 bytes per parameter), the FP32 master weights (4 bytes), and the two FP32 moments (8 bytes), 14 bytes per parameter. The FP16 gradients, 2 of the 16 bytes per parameter that training holds in device memory, are recomputed every step and so are left out of the checkpoint. For GPT-2 XL the checkpoint payload is therefore about 21 GB (3 GB + 6 GB + 12 GB), 7× the FP16 weights alone, and writing it to a local NVMe drive at 7 GB/s takes about 3 s. Checkpoint volume governs how long a save stalls the run and how long recovery takes, because every save adds its bytes to the data movement that the iron law’s ${D_{\text{vol}}}$ term counts.

At the framework level, optimizers expose internal state dictionaries via `state_dict()` for serialization ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^lst-state-dict-interface|listing 3]]), and the same interface saves and restores model parameters and optimizer states ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^lst-checkpoint-save-load|listing 4]]). Reproducing the training trajectory also requires the relevant random-number state, data position, learning-rate scheduler, and gradient-scaler state. Without them, a resumed run would draw different random numbers, repeat or skip examples, and fall back to the wrong learning rate and loss scale.

``` python
import torch
import torch.nn as nn
import torch.optim as optim

model = nn.Linear(10, 5)
optimizer = optim.Adam(model.parameters(), lr=0.001)

# After training steps, optimizer accumulates state
loss = model(torch.randn(3, 10)).sum()
loss.backward()
optimizer.step()

# Access state for checkpointing
state = optimizer.state_dict()
# Contains: {'state': {...}, 'param_groups': [{'lr': 0.001, ...}]}
```

Listing 3: **State Dictionary Interface**: Optimizers expose internal state through state_dict(), enabling serialization of momentum buffers and adaptive learning rate estimates for checkpointing.

^lst-state-dict-interface

``` python
# Saving checkpoint
checkpoint = {
    "epoch": epoch,
    "model_state_dict": model.state_dict(),
    "optimizer_state_dict": optimizer.state_dict(),
}
torch.save(checkpoint, "checkpoint.pt")

# Resuming training
checkpoint = torch.load("checkpoint.pt")
model.load_state_dict(checkpoint["model_state_dict"])
optimizer.load_state_dict(checkpoint["optimizer_state_dict"])
```

Listing 4: **Checkpoint Save and Load**: Save both model parameters and optimizer state to properly resume training with correct momentum and adaptive learning rate values.

^lst-checkpoint-save-load

A checkpoint holds only persistent state. During a training step, the FP16 gradients rejoin that state in device memory and the saved activations from reverse-mode automatic differentiation sit on top of it, so device memory must hold more than the checkpoint file suggests. Notebook [8.5](https://mlsysbook.ai/vol1/08_training/08_training.html#nbk-training-billion-parameter-memory) works through the full comparison for a billion-parameter model.

**Napkin Math 8.5: Training memory beyond the checkpoint**

The ResNet-50 breakdown in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-pytorch-autograd-internals-4fa0|Recording the backward graph]]** already showed training memory several times the size of the stored weights. The following scenario extends the comparison to gradients, optimizer state, and saved activations at billion-parameter scale.

**Problem**: Calculate the memory that gradients, optimizer states, and forward activations add beyond raw model weights in this billion-parameter training scenario.

**Math**:

1.  Model weights (FP16): 2 GB.
2.  Gradients (FP16): 2 GB (same size as weights).
3.  Master weights (FP32): 4 GB, the full-precision copy that mixed-precision training updates.
4.  Optimizer states (Adam): 8 GB (momentum and variance in FP32, 4$\times$ the FP16 weight memory).
5.  Activations: For a batch size of 32 and a 100-layer network, reverse-mode automatic differentiation retains the operation-dependent values required by derivative rules; activation checkpointing can omit selected values and recompute them during the backward pass.

$$
{M_{\text{activations}}} \approx {B} \times {N_L} \times {S} \times {d} \times {n_{\text{saved}}}\times {s_{\text{elem}}}
$$

 For a 1024-token sequence, 1024-wide hidden state, 1 saved tensor per layer, and ${s_{\text{elem}}} = 2$ bytes for FP16: $32 \times 100 \times 1024 \times 1024 \times 1 \times 2 \approx \text{\textbf{6.7}}\,\text{GB}$. Materialized attention terms can add a separate ${B} \times {N_{\text{heads}}} \times {S}^2$ component, which is why memory-efficient attention kernels matter.

**Systems insight**: A 2 GB model carries 16 GB of steady-state training state once gradients and optimizer buffers have been allocated, 8× its FP16 weights (16 bytes per parameter in the mixed-precision Adam recipe), while its checkpoint file holds 14 bytes per parameter. During a training step, batch-dependent activations add another 6.7 GB, raising the peak to about 20.7 GB beyond the weights.

Checkpoint cadence decides how much work a failure discards. Because every update depends on the one before it, a single unmitigated numerical explosion does not cost one step; it can invalidate every step taken since the last good checkpoint, which at frontier scale means thousands of accelerator-hours.

**War Story 8.1: The PaLM loss spikes (2022)**

**Context**: PaLM’s 540-billion-parameter run used 6,144 TPU v4 chips and suffered severe training-instability spikes absent from smaller runs ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-chowdhery2022palm|Chowdhery et al. 2022]]).

**Failure mode**: The training loss spiked roughly 20 times despite gradient clipping, the safeguard that keeps one bad batch from throwing the weights far off course. The spikes occurred at highly irregular intervals, sometimes late in training, never appeared in smaller models, and had no identified principled mitigation.

**Impact**: Each recovery discarded recent progress on an expensive 6,144-chip run, so reproducible checkpoints and repeatable data order were prerequisites for replay.

**Response**: Engineers restarted training from an uncorrupted checkpoint roughly 100 steps prior to each spike and skipped approximately 200–500 data batches around the failure window.

**Systems lesson**: Every step discarded in a recovery is paid for again in cluster time, so operational fault tolerance decides how much of the hardware’s time turns into lasting progress. Automated loss-spike detection, checkpoint cadence, and batch skipping are core system mechanisms for keeping that lost fraction small.

PaLM’s recoveries kept 6,144 chips busy on steps that were later thrown away, so the cluster’s time was spent without the run advancing. In the training-time law that discarded work appears as a lower utilization factor ${\eta_{\text{hw}}}$, which makes checkpoint cadence a throughput decision as well as a reliability one. Frequent saves stall the run for the write time above, while sparse saves lengthen the replay after each failure.

Decomposing the training pipeline exposes the mechanics of data loading, forward and backward execution, parameter updates, and saved training state, while the computation and memory costs in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-mathematical-foundations-d894|section 8.3]] quantify the FLOPs, memory footprint, and bandwidth each phase demands, but knowing how stages execute does not reveal where a specific training workload stalls. A pipeline is only as fast as its slowest stage. In an overlapped pipeline where data loading takes 120 ms and computation takes 100 ms, a 20 percent faster kernel saves nothing, because the step still takes 120 ms. Before applying optimization techniques, systems engineers must profile the execution timeline to determine whether compute, memory bandwidth, storage I/O, or network synchronization limits performance.
