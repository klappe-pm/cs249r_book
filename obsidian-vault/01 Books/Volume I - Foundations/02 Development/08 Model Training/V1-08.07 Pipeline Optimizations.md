# V1-08.07 Pipeline Optimizations

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training|V1-08 Model Training]]

^sec-model-training-pipeline-optimizations-cd9d

Even well-designed training pipelines rarely approach hardware peak throughput without targeted optimization: at a typical model-FLOP utilization of 30 percent to 50 percent, an H100 rated at 989 TFLOP/s delivers only 296.7 TFLOP/s–494.5 TFLOP/s of useful model arithmetic. These derived scenario values reflect the gaps between peak and realized throughput reported across published large-model systems ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-narayanan2021|Narayanan et al. 2021]]; [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-chowdhery2022palm|Chowdhery et al. 2022]]). Systems such as SuperNeurons show one version of this problem, in which memory-management bottlenecks prevent larger networks from training efficiently unless the runtime actively optimizes activation storage and transfer ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-wang2019superneurons|Wang et al. 2018]]).

Closing that utilization gap requires matching a targeted systems intervention to the specific resource that profiling shows is saturated: data movement, arithmetic throughput, or memory capacity. Because training throughput is governed by whichever resource currently limits the step, applying a remedy from [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^tbl-optimization|table 8]] to any other subsystem yields no end-to-end speedup, while relieving the active bottleneck immediately shifts pressure to the next stage in the Data, Algorithm, and Machine triad. The conservation-of-complexity heuristic from the opening of Part I names this pattern, in which complexity moves among the three axes rather than disappearing. Even as the governing constraint shifts with the workload, from host-ingestion stalls on ResNet-50 to HBM capacity and attention bandwidth on GPT-2 XL, every optimization pass follows the same diagnostic loop.

### Systematic Optimization Framework

^sec-model-training-systematic-optimization-framework-83b0

Tuning a training pipeline without a profile wastes work on resources that are not limiting step time or shifts the bottleneck to a neighbor. A disciplined optimization pass therefore proceeds in three steps: profile the step to locate the limiting constraint, pick an intervention that relieves that specific limit, and check how combined interventions compete for shared memory and bandwidth.

First, profiling tools such as PyTorch Profiler, TensorFlow Profiler, or NVIDIA Nsight Systems record timestamps and hardware counters across each iteration. Traces capture kernel execution times on accelerator execution units, DMA transfers across PCIe or NVLink buses, and host CPU thread scheduling. Comparing elapsed time across these lanes isolates which subsystem sets the critical path. When data-loading intervals lie on the critical path and coincide with accelerator input waits, as in the modeled GPT-2 XL timeline above, the run is data-starved; speeding up matrix multiply kernels yields almost no wall-clock gain until input delivery keeps up.

Second, each diagnosed bottleneck points to a specific remedy. When the accelerator idles waiting for batches, asynchronous prefetching and double-buffering over PCIe (keeping one batch in use while the next waits ready) overlap host data preparation with device compute. When kernel runtimes are bound by HBM bandwidth rather than arithmetic, kernel fusion and tiled algorithms such as FlashAttention keep intermediate activations in on-chip SRAM. When HBM capacity runs out, activation checkpointing discards and recomputes activations during the backward pass, or gradient accumulation splits each batch across sequential micro-batches to cap peak allocation. When streaming multiprocessors saturate with dense matrix math, 16-bit formats (FP16 or BF16) move eligible operations onto Tensor Cores, multiplying peak matrix throughput several-fold over FP32 CUDA cores ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^tbl-precision-comparison|table 9]]) while halving the bytes moved per operand.

Third, combining interventions requires checking their side effects on shared hardware resources. Asynchronous prefetching hides data movement latency behind computation, but double-buffered batch queues consume pinned host memory and device HBM. Other pairs reinforce one another: combining 16-bit mixed precision with activation checkpointing cuts activation memory enough to admit a larger per-device batch size, raising the arithmetic intensity of matrix multiplications on underfed Tensor Cores. After each change, a fresh profile verifies that the secondary resource cost has not created a new bottleneck.

[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-optimization-flowchart|Figure 7]] formalizes this diagnostic playbook into a triage flowchart, using low accelerator activity and high memory allocation as signals for further investigation. Idle gaps require tracing input preparation, host work, and synchronization; capacity pressure motivates memory-saving techniques. When neither signal explains a missed target, kernel profiling distinguishes bandwidth, arithmetic, and launch limits.

^fig-optimization-flowchart

Each fix moves the bottleneck, so optimization is iterative and governed by Amdahl’s law. A speedup applied to one stage is capped by the share of step time that stage occupies, because even an infinitely fast stage leaves the rest of the step untouched (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^eq-amdahl|equation 11.1]]** formalizes this bound). Resolving input starvation through asynchronous prefetching, for instance, drives accelerator utilization upward until memory bandwidth or compute saturation limits step time. Each intervention requires re-profiling to identify the newly emerged critical path, continuing the cycle until accelerator execution units operate near peak theoretical throughput or application performance targets are achieved.

### Data Prefetching and Overlapping

^sec-model-training-data-prefetching-pipeline-overlapping-e984

Prefetching and overlapping put the systematic framework to work on the bottleneck the data pipeline left open. ResNet-50’s host workers prepare images more slowly than the H100 consumes them, so the accelerator is busy only about 52 percent of the time ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^sec-model-training-data-pipeline-8e71|section 8.4.2]]). That figure already assumes the host prepares the next batch while the accelerator computes the current one. Run serially, preparation and computation add, and the accelerator would be busy only about 34 percent. Overlap recovers the difference by hiding host work behind computation, but it cannot raise the supply rate itself, so closing the rest of the gap for ResNet-50 requires more host workers or decoding on the accelerator. The techniques below are most effective when profiling shows computational units idle while waiting for data.

In ML training, a “Read” stage is rarely a simple disk fetch. For image workloads it encompasses JPEG decoding, random crops, and color jitter applied on CPU cores before the tensor is ready to transfer; for language workloads it encompasses tokenization, subword encoding, and sequence padding. The Gantt schedule in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-fetching-naive|figure 8]] isolates the serial bottleneck of unbuffered ingestion. The GPU Train row remains completely idle during file-open intervals (Open 1, Open 2) and read stages (Read 1, Read 2), stretching the two-epoch schedule out to about 95 min because compute steps cannot begin until host-side decoding and transfer finish.

Framework data loaders such as PyTorch `DataLoader` and `tf.data` ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-murray2021|Murray et al. 2021]]) eliminate those synchronous gaps by staging the next batch into host memory while the accelerator is still executing the current batch.

Overlapping extends prefetching by coordinating multiple pipeline stages to execute concurrently. As the system processes the current batch on the accelerator, background host threads load and preprocess subsequent batches. Set against the serial schedule of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-fetching-naive|figure 8]], the overlapped timeline in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-fetching-optimized|figure 9]] hides host latency behind computation. Concurrent staging of Open 2 and Read 3 behind active execution eliminates idle bubbles between training blocks (Train 1 through Train 3). It compresses total wall-clock duration from approximately 95 min down to 65 min (a 31.6 percent reduction). Actual gains depend on stage balance and available concurrency.

#### Prefetching Mechanics

^sec-model-training-prefetching-mechanics-2ba2

The overlapped schedule requires enough host workers and buffering to make the next batch ready before the device requests it. Worker count controls preparation capacity; queue depth absorbs variation in preparation time. Neither changes the slowest-stage bound established by [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-training-bottleneck|equation 6]].

Machine learning frameworks expose the control variables for this trade-off. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^lst-dataloader-usage-2d012bb4|Listing 5]] demonstrates PyTorch’s DataLoader configuration, where num_workers = 4 sets preprocessing parallelism and prefetch_factor = 2 maintains a buffer of 8 batches ready for accelerator consumption.

``` python
loader = DataLoader(
    dataset, batch_size=32, num_workers=4, prefetch_factor=2
)
```

Listing 5: **DataLoader Prefetch Configuration**: Four workers with a prefetch factor of two maintain up to eight batches in the host-side prefetch window.

^lst-dataloader-usage-2d012bb4

The parameters `num_workers` and `prefetch_factor` are not generic performance toggles. They determine CPU parallelism and buffer depth, which means they shift pressure from accelerator idle time to host memory and CPU scheduling. A third setting, `pin_memory=True`, lets host-to-device copies overlap accelerator execution through DMA; its cost is page-locked host memory that the rest of the system can no longer page.

↩︎ The DataLoader’s three knobs, worker count, prefetch depth, and pinned memory for DMA transfers, are established in **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.06 Abstraction Tensors, Devices, and Operations#^sec-ml-frameworks-domainspecific-data-organizations-48d9|Data loading]]**.

Buffer management is the main trade-off. A buffer that is too small causes the GPU to wait for data preparation, reintroducing the idle time prefetching was meant to remove. An overly large host-side buffer consumes memory that could otherwise support input processing and other host work. The right configuration coordinates CPU preparation, storage I/O, and GPU computation so each resource has work ready at the moment it can use it. These techniques yield the greatest benefit when storage access is slow, preprocessing is complex, or datasets are large.

#### Practical Considerations

^sec-model-training-pipeline-practical-considerations-4ba0

Prefetch buffers and overlap depth are tunable, so the same machinery adapts to whichever stage is the bottleneck, whether slow storage, limited network bandwidth, or computational throughput. Prefetching and overlapping deliver the greatest gains when preprocessing lies on the critical path but can run concurrently with model computation. In an illustrative image pipeline, random cropping (10 ms), color jittering (15 ms), and normalization (5 ms) total 30 ms per batch. Overlap can hide up to the concurrent accelerator-computation time; any excess remains on the critical path. NLP workloads similarly benefit when tokenization and subword processing would otherwise block the training loop.

The primary trade-off is memory: prefetch buffers consume host memory, or device memory when a separate device-side queue is used, in proportion to buffer depth and batch size. With batch size 256 high-resolution images ($1024\times 1024$ pixels), one buffered batch requires approximately 3.2 GB. With num_workers = 4 and prefetch_factor = 2, the 8-batch prefetch window can hold about 25.8 GB. Tuning these parameters requires empirical testing because excessive workers contend for CPU, storage, and memory resources, while insufficient buffering reintroduces data stalls. Start with a modest worker count, increase it while measuring throughput and memory, and stop when additional workers no longer reduce accelerator idle time. When the input pipeline already exceeds compute demand, deeper prefetching adds complexity without improving throughput.

### Mixed-Precision Training

^sec-model-training-mixedprecision-training-9218

Running a modern training job entirely in 32-bit floating point (FP32) leaves the accelerator’s 16-bit Tensor Cores idle and doubles the byte footprint of every forward activation kept in HBM. Mixed-precision training removes both bottlenecks by executing matrix multiplications and storing activations in a 16-bit format while retaining 32-bit precision for sensitive accumulations and parameter updates. **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-floatingpoint-format-comparison-1836|Floating-point formats]]** compares FP32, FP16, BF16, FP8, and INT8 precision-range trade-offs. A training recipe commonly combines FP32 with either FP16 or BF16; it does not ordinarily use FP16 and BF16 interchangeably in the same path. The resulting speed, memory, and accuracy effects depend on the workload and hardware ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-micikevicius2017mixed|Micikevicius et al. 2018]]; [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-google-bfloat16-3450e2b6|Wang and Kanwar 2019]]; [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-kalamkar2019|Kalamkar et al. 2019]]).

A neural network’s stored FP32 weights require 4 bytes per parameter, while FP16 and BF16 weights use 2 bytes. For a model with $10^9$ parameters, the working copy of the weights shrinks from 4 GB to 2 GB. That saving does not carry over to the static training state. The common FP16 recipe keeps FP32 master weights and FP32 Adam moments. Per parameter, it spends 2 + 2 + 4 + 8 = 16 bytes on weights, gradients, master copy, and moments, exactly what FP32 Adam spends on its 4 + 4 + 8. Mixed precision’s memory benefit therefore comes from the tensors stored in 16 bits, above all the activations, together with the halved bytes moved for every 16-bit read, write, and gradient exchange.

Mixed precision’s throughput benefit is larger than its memory benefit. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-precision-ladder|Figure 10]] plots peak dense throughput by number format across four generations of data center accelerators. From V100 to B200 the FP32 rate grew 4.8×, the FP16/BF16 tensor rate grew 18×, and the lowest supported format, 4-bit floating point (FP4) on B200, delivers 72× the V100’s FP16 tensor rate. Hardware gains now arrive almost entirely through tensor units built for lower precision. On B200 the FP16/BF16 tensor path is 30× faster than FP32, so a training job that stays in FP32 leaves nearly all of the chip’s arithmetic idle.

The numerical differences between these formats shape their use cases. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^tbl-precision-comparison|Table 9]] shows that BF16’s 8-bit exponent gives it approximately the same normal exponent range as FP32, while FP16’s 5-bit exponent gives a minimum positive normal value of about $6.1 \times 10^{-5}$ and a maximum finite value of $65{,}504$. FP16 subnormals extend toward $6 \times 10^{-8}$, although their treatment depends on the operation and hardware mode. FP32 provides about seven decimal digits of precision, FP16 about three, and BF16 about two to three. BF16 therefore trades mantissa precision for the exponent range that often simplifies deep-learning training.

The choice between formats depends on model characteristics and hardware support. BF16’s wider exponent range reduces overflow and underflow concerns, while FP16 provides more mantissa bits but often requires loss scaling. Framework autocast policies and fused kernels choose higher-precision accumulation for numerically sensitive operations when needed; loss reduction, softmax, normalization, and optimizer updates are common candidates, but their exact execution dtype is implementation-dependent.

[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-mixed-precision|Figure 11]] traces this conventional FP16 execution cycle across six numbered stages. FP32 master weights are downcast to FP16 for the forward pass. Loss scaling shifts small gradient values into representable range before backpropagation, and the resulting scaled gradients are unscaled and cast back to FP32 prior to the parameter update. Modern framework implementations may store or accumulate particular tensors differently, and BF16 recipes commonly omit loss scaling because of their wider exponent range.

![[90 Assets/Volume I/08 Training/Generated Figure 66c6eabb27.svg]]

Figure 11: **Conventional FP16 Mixed-Precision Training**: A schematic six-step recipe casts FP32 master weights for lower-precision computation, scales the loss, computes scaled gradients, then unscales them for an FP32 update. Framework implementations may vary, and BF16 usually does not require this loss-scaling path.

^fig-mixed-precision

The cycle pays off because modern accelerator architectures pair dense matrix execution units with reduced-precision numerical formats to maximize arithmetic throughput. NVIDIA introduced Tensor Cores for FP16 operations in the Volta architecture ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-nvidia-tensors-fp16-2017-23d257af|NVIDIA 2017]]) and added native BF16 execution in Ampere ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-NVIDIA2020|NVIDIA Corporation 2020a]]), matching the native BF16 support Google developed for Tensor Processing Units ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-google-bfloat16-3450e2b6|Wang and Kanwar 2019]]). These specialized functional units execute low-precision matrix multiply-accumulate operations at roughly one order of magnitude or more above the rate of standard 32-bit floating-point ALUs ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-precision-ladder|figure 10]]).

Mixed-precision training turns those hardware capabilities into a split numerical policy. Eligible matrix multiplications and convolutions execute in FP16 or BF16 on tensor units, while reductions, accumulations, and parameter updates retain higher precision. The performance gain comes from both arithmetic throughput and data movement: lower-precision units pack more multiply-accumulates into each cycle and each unit of silicon area, while narrower tensors halve data transfer volumes across caches and high-bandwidth memory. Higher precision remains necessary where wide reductions, small parameter updates, or sensitive normalizations can accumulate rounding error. Framework autocast policies enforce this split dynamically, selecting lower-precision execution for compute-intensive matrix multiplications while preserving FP32 for numerically fragile operations.

#### Loss Scaling

^sec-model-training-loss-scaling-f9f5

FP16’s 5-bit exponent limits its representable dynamic range, creating underflow hazards during backpropagation. When computing gradients across deep networks, successive chain-rule multiplications frequently produce gradient magnitudes smaller than FP16’s minimum positive normal value ($2^{-14} \approx 6.1 \times 10^{-5}$). While IEEE 754 FP16 defines subnormal numbers down to $\approx 6 \times 10^{-8}$, hardware accelerators often flush subnormal inputs and outputs to zero to prevent pipeline stalls. When gradients underflow to zero, weight updates stall and training fails to converge.

Loss scaling counters underflow by exploiting the linearity of differentiation: $\nabla_{{\theta}} ({s_{\text{loss}}} \cdot {\mathcal{L}}) = {s_{\text{loss}}} \cdot \nabla_{{\theta}} {\mathcal{L}}$. Multiplying the scalar loss ${\mathcal{L}}$ by a large scaling factor ${s_{\text{loss}}}$ (such as $2^{10}$ or $2^{15}$) prior to backpropagation shifts the gradient distribution rightward into FP16’s normal representable range. Once backpropagation completes, the accumulated gradients are divided by ${s_{\text{loss}}}$ (unscaled) before applying the optimizer update.

Deep learning frameworks automate this process through dynamic loss scaling; **[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-mixedprecision-training-support-d31d|Mixed-precision training support]]** describes the `GradScaler` machinery that scales the loss, unscales the gradients, and skips any step whose gradients overflow. The training decision is how the scale factor adapts. Because gradient norms fluctuate during training, a static scale factor risks either underflow (if ${s_{\text{loss}}}$ is too small) or numerical overflow past FP16’s maximum finite value of $65{,}504$ (if ${s_{\text{loss}}}$ is too large). A dynamic scaler therefore skips each overflowing step so that nonfinite gradients never reach the FP32 master weights, halves ${s_{\text{loss}}}$ at each skip, and doubles ${s_{\text{loss}}}$ after a configurable growth window without overflow (such as 2,000 consecutive steps). Together these adjustments keep gradients near the upper end of the dynamic range without saturating.

#### Mixed-Precision Benefits

^sec-model-training-mixedprecision-benefits-d57b

Once dynamic loss scaling or BF16 preserves gradient fidelity, mixed-precision training compounds gains across memory footprint, arithmetic throughput, and communication volume. Although the 50 percent reduction in working weight storage (from 4 GB to 2 GB on a one-billion-parameter model) is absorbed by the 16-bytes-per-parameter static master weights and Adam moments derived above, forward activations shrink by the full 50 percent. Computationally, reduced precision routes dense matrix multiplication kernels to high-throughput Tensor Core pipelines ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-mixedprecision-hardware-support-d7c1|section 8.6.3.3]]), while in distributed topologies, transferring 16-bit rather than 32-bit gradients halves collective AllReduce traffic across the interconnect. Because reclaimed activation memory permits larger micro-batches, Tensor Cores run at higher arithmetic intensity while narrower tensors reduce gradient exchange latency. The following case study evaluates these memory effects on GPT-2 XL at batch 32, the configuration the activation notebook left far over the H100’s capacity.

**Napkin Math 8.6: GPT-2 mixed precision memory savings**

**Problem**: What does mixed precision save when GPT-2 XL (1.5B parameters) trains at batch 32 and sequence length 1,024 on one H100, and what does it leave unchanged?

**FP32 baseline**:

- Parameters and gradients (FP32): 12 GB (6 GB parameters + 6 GB gradients)
- Activations: ~574 GB
- Optimizer states (Adam first and second moments in FP32): 12 GB
- Total: ~598 GB

**FP16 mixed precision**:

- Parameters (FP16): 1.5B parameters at 2 bytes each = 3 GB
- Activations (FP16): ~287 GB
- Gradients (FP16): 3 GB
- FP32 master weights: 6 GB (for precise optimizer updates)
- Optimizer states (Adam first and second moments in FP32): 12 GB
- Total: ~311 GB, about 3.6× the H100’s 80 GB

**Systems insight**: Mixed precision halves the activations and leaves the static state unchanged at 24 GB. At batch 32 the remaining activations still dominate, and most of them are the quadratic attention-score matrices, which FlashAttention ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-flash-attention-ioaware-attention-optimization-3da0|section 8.6.4]]) removes next.

Memory savings alone do not guarantee stable training. In the FP16 training recipe used here, maintaining FP32 master weights is necessary because parameter updates ${\Delta} {w}= -{\eta} \cdot {g}$ (learning rate times gradient) are typically orders of magnitude smaller than the weight values ${w}$. In FP16, where the 10-bit mantissa provides roughly three decimal digits of precision, adding an update that is more than $2^{11} \approx 2048$ times smaller than the weight magnitude results in arithmetic swamping: the updated weight rounds back to its original value. This loss of an increment through rounding is distinct from the update value itself underflowing. Retaining master weights in FP32 preserves these incremental updates across thousands of optimizer steps, casting to 16 bits only when staging weights for the forward pass. Autocast policies similarly isolate wide reductions, layer normalizations, and softmax layers in FP32 to prevent catastrophic cancellation, the loss of significant digits when nearly equal numbers are subtracted.

Once numerical stability is established, reduced-precision arithmetic and reduced memory traffic can shorten execution when they reduce work on the critical path. Comparing complete training recipes does not isolate the contribution of precision alone; model quality, batch size, optimizer representation, and activation policy must be accounted for. The following scenario models these compound throughput, schedule, and infrastructure cost gains for a GPT-2 XL training run.

**Napkin Math 8.7: GPT-2 mixed precision throughput and cost**

**Problem**: Holding utilization fixed, how much faster and cheaper is GPT-2 XL’s run on one H100 when its matrix products run in BF16 instead of in 32-bit formats?

**Peak rates by path**: FP32 on scalar units 67 TFLOP/s; TF32 (TensorFloat-32, which lets Tensor Cores run FP32 matrix products by rounding their inputs to a shorter mantissa) on Tensor Cores 494.5 TFLOP/s; BF16 on Tensor Cores 989 TFLOP/s.

**Run time and cost** at 50 percent utilization and \$4/hour per accelerator:

- FP32: about 518 days, \$49,751
- TF32: about 70 days, \$6,741
- BF16: about 35 days, \$3,370

**Systems insight**: The peak ratios, 2× over TF32 and 15× over FP32, bound the gain rather than predict it. Holding utilization fixed assumes that every part of the step speeds up with the matrix units, but elementwise kernels, optimizer updates, and input waits do not run on Tensor Cores, so by Amdahl’s law the measured speedup is smaller. A real decision requires measured throughput, billing, and quality validation for the target workload.

Realizing these speedups requires empirical profiling rather than assuming automatic acceleration. For small models or memory-bound workloads not dominated by large matrix multiplications, data type casting and kernel launch overheads can offset the arithmetic throughput advantage. Whether an accelerator supports native BF16 or requires FP16 loss scaling also depends on the underlying microarchitecture.

#### Mixed-Precision Hardware Support

^sec-model-training-mixedprecision-hardware-support-d7c1

Specialized matrix execution units deliver the wall-clock speedup of mixed precision by spending fewer bits per operand. Accelerators pair these low-precision multiply units with higher-precision accumulation registers to maintain numerical stability during dense matrix reductions.

The Volta-generation Tensor Cores introduced earlier in this section perform $4{\times}4$ matrix multiply-accumulate operations in a single clock cycle, a datapath that **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.05 Compute Units#^sec-hardware-acceleration-tensor-cores-771f|Tensor Cores]]** examines in detail. For FP16 inputs, a single Tensor Core executes:

$$
{\mathbf{D}_{\text{tc}}}= {\mathbf{A}_{\text{tc}}}\times {\mathbf{B}_{\text{tc}}}+ {\mathbf{C}_{\text{acc}}}
$$

 where ${\mathbf{A}_{\text{tc}}}$ and ${\mathbf{B}_{\text{tc}}}$ are FP16 inputs and ${\mathbf{C}_{\text{acc}}}$ and ${\mathbf{D}_{\text{tc}}}$ may use FP32 accumulation. Higher-precision accumulation reduces rounding error, although it does not eliminate numerical error or cancellation.

Hardware peak specifications define the theoretical ceiling on this acceleration. The reference H100 exposes 67 TFLOP/s of FP32 throughput on standard CUDA cores and 989 TFLOP/s of dense FP16 or BF16 Tensor Core throughput, a 15× peak ratio. These figures represent hardware ceilings rather than end-to-end training guarantees: matrix multiplications map directly to Tensor Cores, but data movement, non-Tensor-Core kernels, communication, loss scaling, and optimizer updates remain. While the batched matrix multiplication ${\mathbf{Q}}{\mathbf{K}}^T$ in transformer self-attention ($2 \times {B}\times {N_{\text{heads}}} \times {S}^2 \times {d_{\text{head}}}$ FLOPs) maps directly to these tensor units, Amdahl’s law dictates that the remaining memory-bound elementwise operations, communication collectives, and optimizer updates bound the realized end-to-end speedup.

Microarchitecture generation also determines whether a pipeline must run the dynamic loss-scaling loop of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-loss-scaling-f9f5|section 8.6.3.1]]. Volta and Turing Tensor Cores support only FP16, where gradients below $6.1 \times 10^{-5}$ risk subnormal flushing to zero unless scaled. On Google TPUs and on NVIDIA GPUs from Ampere (A100) onward, native Brain Float 16 (BF16) Tensor Core paths preserve FP32’s 8-bit exponent range (down to $\approx 10^{-38}$ at 7 mantissa bits), avoiding loss scaling while still relying on FP32 accumulation registers to limit rounding error.

NVIDIA’s Hopper architecture (H100) adds FP8 Tensor Core paths for 8-bit floating-point values at about 2× the FP16/BF16 rate (1.98 PFLOP/s on H100 dense vs. 0.99 PFLOP/s for FP16 dense, without sparsity); FP8’s two bit layouts and the per-tensor scaling they require are developed in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.04 Numerical Precision Changing How Values Are Stored#^sec-model-compression-numerical-format-comparison-8fa2|Numerical formats]]**. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^tbl-precision-decision-tree|Table 10]] summarizes when each precision is appropriate:

| **Precision** | **When to Use**                                      |   **Hardware Requirement** |
|:--------------|:-----------------------------------------------------|---------------------------:|
| **FP8**       | Throughput-oriented training with validated scaling  |     Supported FP8 hardware |
| **BF16**      | Wide exponent range without FP16 loss scaling        | Supported BF16 accelerator |
| **FP16**      | Higher mantissa precision with managed loss scaling  | Supported FP16 accelerator |
| **FP32**      | Higher precision or unsupported lower-precision path |                        GPU |

Table 10: **Precision Selection Guide**: Format choice depends on hardware support, kernel coverage, numerical behavior, and validation results. FP8 requires an explicit scaling strategy; BF16 provides a wider exponent range than FP16; FP16 often uses loss scaling; and FP32 remains available for sensitive operations or unsupported lower-precision paths.

^tbl-precision-decision-tree

In addition to accelerating compute-bound matrix operations, reduced precision relieves memory bandwidth bottlenecks by altering operational arithmetic intensity. On modern accelerators, large matrix multiplications reside in the compute-bound regime of the roofline model, whereas elementwise operations (such as bias additions, layer normalization, and residual connections) reside firmly in the memory-bound regime. On the H100, arithmetic capability far outruns memory bandwidth. Its HBM3 bus supplies 3,350 GB/s, whereas sustaining its 67 TFLOP/s of FP32 throughput without operand reuse would demand 268 TB/s if every FLOP required fresh data from memory. Although operand reuse reduces actual traffic for dense matrix multiplications, operations with low arithmetic intensity remain strictly bandwidth-limited.

For memory-bound kernels, execution time is determined by bytes transferred across the memory bus rather than arithmetic clock cycles. Converting 32-bit operands to 16-bit FP16 or BF16 halves the byte volume transferred across the HBM bus, doubling the theoretical throughput of memory-bound operations even without engaging Tensor Cores. Realized bandwidth gains depend on cache hit rates, kernel fusion, and format conversion costs.

**[[01 Books/Volume I - Foundations/02 Development/07 ML Frameworks/V1-07.05 Differentiation Automatic Gradient Computation#^sec-ml-frameworks-mixedprecision-training-support-d31d|Mixed-precision training support]]** describes how `autocast` and `GradScaler` implement the split between 16-bit and FP32 operations inside the framework. The policy decision that remains for the training recipe is which format to run, and [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^lst-mixed-precision|listing 6]] makes it a single switch: the FP16 path enables gradient scaling, and the BF16 path disables it.

``` python
import torch

model = TransformerModel().cuda()
optimizer = torch.optim.Adam(model.parameters(), lr=1e-4)
amp_dtype = (
    torch.float16
)  # torch.bfloat16 usually does not need loss scaling
scaler = torch.amp.GradScaler(
    "cuda", enabled=(amp_dtype == torch.float16)
)

for inputs, targets in dataloader:
    optimizer.zero_grad()

    # Automatic precision selection per operation
    with torch.amp.autocast("cuda", dtype=amp_dtype):
        output = model(inputs)
        loss = criterion(output, targets)

    # Scale loss to prevent gradient underflow
    scaler.scale(loss).backward()

    # Unscale gradients before optimizer step
    scaler.step(optimizer)
    scaler.update()  # Adjust scaling factor dynamically
```

### FlashAttention: IO-Aware Attention Optimization

^sec-model-training-flash-attention-ioaware-attention-optimization-3da0

Mixed-precision training addresses two bottlenecks, compute throughput because Tensor Cores run faster on 16-bit operands, and memory capacity because each value uses fewer bytes. For transformer models, a third bottleneck often dominates, and the roofline analysis has already located it. Counting only its score-matrix traffic, materialized attention in GPT-2 Small reaches about 32 FLOP/byte, well left of the H100 ridge point in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^fig-training-roofline|figure 1]], because its quadratic intermediate matrices are written to HBM during the forward pass and read back during backpropagation. Halving the bytes per value does not change that quadratic traffic, so even with reduced precision the compute units can sit idle while the processor waits for data.

The same quadratic term dominates GPT-2 XL’s memory. At batch 32 and 1,024 tokens, the stored score, probability, and dropout matrices account for about 201 GB of the 287 GB of mixed-precision activations, about 70 percent. An attention kernel that never stores them leaves 85.6 GB of activations; with the static state the step needs 109.6 GB, still about 24 GB more than the H100’s 80 GB (85.9 GB in decimal units). Removing attention’s traffic is therefore necessary but not sufficient.

FlashAttention ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-dao2022|Dao et al. 2022]]) addresses this bandwidth bottleneck by treating attention as an IO problem. Processing attention in SRAM-sized tiles avoids materializing the full ${S}{\times}{S}$ matrix in HBM and reduces traffic without changing the mathematical output, which is how the roofline preview moved attention rightward toward, and for favorable shapes past, the ridge.

#### The Standard Attention Memory Bottleneck

^sec-model-training-standard-attention-memory-bottleneck-6f39

Standard self-attention materializes an ${S}{\times}{S}$ score matrix and an ${S}{\times}{S}$ probability matrix in off-chip HBM for every attention head, turning long-sequence training into a memory-bandwidth and capacity bottleneck:

$$
\text{Attention}({\mathbf{Q}}, {\mathbf{K}}, {\mathbf{V}}) = \text{softmax}\left(\frac{{\mathbf{Q}}{\mathbf{K}}^T}{\sqrt{{d_{\text{head}}}}}\right){\mathbf{V}} \tag{9}
$$

^eq-attention

Here, ${\mathbf{Q}}$, ${\mathbf{K}}$, and ${\mathbf{V}}$ are the query, key, and value matrices for a sequence of length ${S}$, and ${d_{\text{head}}}$ is the key-vector dimension used to scale the dot products before softmax. Because the intermediate product ${\mathbf{Q}}{\mathbf{K}}^T$ is written out to HBM before softmax and read back immediately afterward, attention becomes an I/O problem even when the matrix products themselves map cleanly onto Tensor Cores.

The memory bottleneck emerges from materializing the ${S}{\times}{S}$ intermediate matrices for scores and probabilities. For a sequence length of 4,096 with head dimension ${d_{\text{head}}} =$ 64 (typical for a single attention head), the attention score matrix alone requires $4{,}096^2 \times 4$ bytes = 67.1 MB in FP32. This section counts FP32 scores throughout, since autocast policies commonly keep softmax in FP32; at FP16 every figure halves, as in the roofline estimate and the earlier activation notebook, which counted FP16 probabilities, while the quadratic growth stays the same. With 16 heads, this grows to 1.1 GB for the intermediate attention matrices alone, not including the keys, queries, values, or output tensors.

GPU memory hierarchy creates the opportunity for I/O-aware attention. HBM offers large off-chip capacity, while much smaller on-chip SRAM has substantially higher bandwidth and lower latency. Attention implementations that materialize the quadratic intermediates in HBM must write and later read them during backpropagation. Because that traffic grows with the square of sequence length, it takes a growing share of step time as sequences lengthen.

The backward pass requires the information represented by the attention probabilities, but an implementation may either save those intermediates or recompute them. For ${\mathbf{A}} = \text{softmax}({\mathbf{S}})$ and ${\mathbf{S}} = {\mathbf{Q}}{\mathbf{K}}^T/\sqrt{{d_{\text{head}}}}$, one gradient expression is:

$$
\frac{\partial {\mathcal{L}}}{\partial {\mathbf{Q}}} = \frac{1}{\sqrt{{d_{\text{head}}}}} \cdot \text{dsoftmax}\!\left(\frac{\partial {\mathcal{L}}}{\partial {\mathbf{A}}},\, {\mathbf{A}}\right) \cdot {\mathbf{K}}
$$

 where $\text{dsoftmax}$ denotes softmax’s backward rule, which turns the gradient with respect to the probabilities into the gradient with respect to the scores and needs the probabilities themselves to do so. A conventional implementation saves the probability matrix for this computation. FlashAttention instead saves compact normalization statistics and recomputes tiled score and probability blocks during backward propagation, avoiding full quadratic intermediates in HBM.

#### IO-Aware Attention Through Tiling

^sec-model-training-ioaware-attention-tiling-f02f

FlashAttention eliminates the need to materialize full ${S}{\times}{S}$ attention matrices in HBM by computing attention incrementally through tiling. Instead of computing the entire attention matrix at once, the algorithm partitions ${\mathbf{Q}}$, ${\mathbf{K}}$, and ${\mathbf{V}}$ into tiles small enough to fit in fast SRAM, computes attention scores for these tiles, and incrementally accumulates results.

The key algorithmic insight relies on the structure of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^eq-attention|equation 9]]. Softmax normalizes each row of scores by a sum over the entire row, which seems to require the whole row before any output can be formed, yet the online softmax algorithm removes that requirement. Ordinary softmax, $\text{softmax}({\mathbf{x}})_i = e^{{\mathbf{x}}_i} / \sum_j e^{{\mathbf{x}}_j}$, is computed stably by first subtracting the row maximum. The online form instead keeps two running statistics per row as blocks of scores arrive: the largest score seen so far, ${m}$, and the sum of exponentials taken relative to that maximum, ${z}$. When a new block raises the maximum from ${m}$ to ${m'}$, everything accumulated so far was exponentiated relative to the old maximum, and multiplying it by $e^{{m}-{m'}}$ re-expresses it relative to the new one. The same factor rescales the partially accumulated output. After the last block, dividing the output by ${z}$ gives exactly the softmax-weighted result, as if the whole row had been seen at once.

[Algorithm 2](https://mlsysbook.ai/vol1/08_training/08_training.html#algo-streaming-attention) decomposes this computation by partitioning the queries and the keys/values into tiles small enough to fit in SRAM, then streaming over the key/value tiles while maintaining the running softmax statistics needed to assemble each output tile, without ever forming the full score matrix.

Other inputs, outputs, and running statistics remain, so the tile is not necessarily the largest tensor in the entire kernel.

The storage boundary distinguishes the tiled algorithm from the materialized implementation. #### Memory and IO Complexity Analysis

^sec-model-training-memory-io-complexity-analysis-5da5

FlashAttention improves both activation memory and memory IO, which are the limiting costs in bandwidth-bound attention. Standard attention requires $\mathcal{O}({S}^2)$ memory to store score matrices ${\mathbf{S}}$ and attention-probability matrices ${\mathbf{A}}$ across all sequence positions. FlashAttention reduces the stored activation footprint to $\mathcal{O}({S})$ by keeping only input and output tensors $({\mathbf{Q}}, {\mathbf{K}}, {\mathbf{V}}, {\mathbf{O}})$ plus a small SRAM buffer for the current tile.

The comparison that decides memory is the whole per-head footprint each algorithm keeps for the backward pass. For ${S} = 4096$ and ${d_{\text{head}}} = 64$, the conventional baseline assumed here stores the inputs, the output, and both the score and probability matrices, about 138.4 MB. FlashAttention stores the inputs, the output, and two numbers per row (the running maximum and sum), about 4.2 MB, roughly 32.7× smaller. The quadratic intermediates account for the difference. One materialized FP32 score matrix alone occupies $4096^2 \times 4$ bytes = 67.1 MB per head, 21.3× the $(3 \times 4096{\times}64) \times 4$ bytes ≈ 3.1 MB that the three FP32 input tensors occupy together. Only the standard footprint is quadratic in ${S}$, so the gap widens as sequences grow.

These stored-tensor totals exclude gradient buffers, temporary workspace, and the live SRAM tile, so they are not estimates of peak training memory. Implementations may also retain fewer quadratic intermediates than the conventional baseline assumed here.

The IO pattern changes for the same reason. Standard attention reads ${\mathbf{Q}}$, ${\mathbf{K}}$, and ${\mathbf{V}}$ from HBM, writes score, probability, and output matrices during the forward pass, then rereads those stored matrices during the backward pass before writing the gradients $d{\mathbf{Q}}$, $d{\mathbf{K}}$, and $d{\mathbf{V}}$ (shorthand for $\partial {\mathcal{L}}/\partial {\mathbf{Q}}$ and its counterparts). The resulting HBM traffic includes the same $\mathcal{O}({S}^2)$ term that made the activation footprint large.

FlashAttention forms score and probability blocks in SRAM and never writes the full ${S} \times {S}$ tensors to HBM. In the backward pass, it recomputes the needed blocks rather than reading stored full matrices. Because each outer-loop pass holds a query tile in on-chip SRAM while streaming the key and value tiles past it from HBM, an entire row of score blocks is computed on chip for one HBM read of the keys and values. Larger SRAM holds larger tiles and requires fewer streaming passes over HBM, so HBM traffic falls in inverse proportion to SRAM capacity. It still grows with the square of sequence length, however, rather than dropping to the $\mathcal{O}({S} \cdot {d})$ bytes needed simply to read the inputs and write the output once.

Both approaches require $\mathcal{O}({S}^2 {d})$ asymptotic FLOPs for dense attention, so FlashAttention’s gain comes from traffic, not arithmetic. The resulting reduction in HBM traffic can shift the kernel toward compute-bound execution and produce a net speedup, but the final bottleneck remains shape- and hardware-dependent.

#### When to Use FlashAttention

^sec-model-training-use-flash-attention-375d

For transformer training with long sequences, FlashAttention is usually the first attention implementation to test. It often becomes essential once sequence length pushes standard attention into an HBM-capacity or HBM-bandwidth bottleneck, especially around the multi-thousand-token regime where the ${S}{\times}{S}$ attention matrices dominate memory. A100- and H100-class GPUs with fast on-chip SRAM benefit most. The returns diminish for short sequences where tiling overhead is not worthwhile, on older GPU architectures without comparable SRAM bandwidth, and for nonattention architectures such as convolutional neural networks and multilayer perceptrons.

In practice, deep learning frameworks handle much of FlashAttention’s integration, but the decision still depends on layout, precision, and memory budget. PyTorch’s `scaled_dot_product_attention` can dispatch to FlashAttention when hardware, inputs, and backend constraints permit; hand-written attention must use an eligible primitive. Three practical checks determine whether the fast path actually runs and pays off. Tensor layouts must match library expectations (contiguous memory and the expected dimension ordering). Execution must use FP16 or BF16, because FlashAttention kernels target mixed precision. Gradient checkpointing should be combined with FlashAttention whenever additional activation-memory savings are needed beyond the attention scores.

The integration is often a single-line change, swapping a manual attention call for `F.scaled_dot_product_attention`, as [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^lst-flash-attention-comparison|listing 7]] shows. The engineering decision is still the same one established by the roofline analysis: use the optimized primitive when the bottleneck is HBM traffic, and let the library manage the tiling and SRAM scheduling needed to remove it.

#### IO-Aware Design Beyond Attention

^sec-model-training-systems-implications-broader-principles-c4f0

FlashAttention is an instance of **IO-aware algorithm design**: because modern accelerators are compute-abundant relative to memory bandwidth, traffic governs runtime for a bandwidth-bound kernel even when FLOPs do not change. This principle extends beyond attention. In IO-aware matrix multiplication, tiling algorithms like those in CUTLASS minimize DRAM traffic by maximizing data reuse in fast caches. A naive ${N}{\times}{N}$ matrix multiply performs $\mathcal{O}({N}^3)$ FLOPs and, without reuse, $\mathcal{O}({N}^3)$ memory traffic; blocking keeps tiles in fast memory (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.08 Hardware Mapping#^sec-hardware-acceleration-tiling-principle|Tiling]]**) and moves traffic toward the $\mathcal{O}({N}^2)$ lower bound.

The same byte-movement principle reappears in communication-efficient distributed training, where gradient compression trades extra computation (compression/decompression) for reduced network bandwidth consumption.

Eliminating off-chip materialization of the $\mathcal{O}({S}^2)$ attention matrices reclaims accelerator memory across three architectural trade-offs. First, it enables longer sequence contexts on fixed hardware, with the workable context boundary determined by the complete training recipe. Second, freeing activation memory allows larger micro-batch sizes that improve hardware arithmetic saturation, provided gradient dynamics remain stable. Third, the contracted activation footprint permits deeper transformer stacks within a given memory budget, although end-to-end multi-billion-parameter feasibility continues to depend on parameter sharding, optimizer states, and remaining layer activations.

FlashAttention performs the same arithmetic but moves fewer bytes, which is why counting bytes before FLOPs is the first step on any bandwidth-bound kernel. Bandwidth is not the only memory limit, however. The capacity required to hold activations and optimizer states at the same time can still exceed the accelerator, and when models or batch sizes outgrow device memory, two complementary techniques trade computation for memory.

### Gradient Accumulation and Checkpointing

^sec-model-training-gradient-accumulation-checkpointing-0c47

FlashAttention left GPT-2 XL’s batch-32 step about 24 GB over the H100’s capacity, and the excess now consists of ordinary activations, the layer inputs, projections, and feed-forward intermediates that backpropagation must read. Two techniques remove it without adding hardware. Gradient accumulation builds the batch from smaller micro-batches that each fit, and activation checkpointing keeps fewer activations and recomputes the rest during the backward pass. Both were named earlier, accumulation with mini-batch processing ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-minibatch-processing-4eb0|section 8.3.2.1.2]]) and recomputation with activation memory ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-memorycomputation-tradeoffs-411e|section 8.3.3.2]]). Using them correctly requires knowing when accumulated gradients equal the large-batch gradient, what each technique costs in time, how checkpoints are placed (the $\sqrt{{N_L}}$ schedule), and which loss-normalization errors most often break accumulation.

#### Gradient Accumulation

^sec-model-training-gradient-accumulation-308f

To execute large batch training on memory-constrained accelerators, systems split an effective logical batch across smaller sequential micro-batches. Three consecutive micro-batches evaluate independent losses (${\mathcal{L}}_1, {\mathcal{L}}_2, {\mathcal{L}}_3$) and gradients (${\mathbf{g}}_1, {\mathbf{g}}_2, {\mathbf{g}}_3$, where ${\mathbf{g}}_j = \nabla_{{\theta}}{\mathcal{L}}_j$), accumulating into a single unified tensor (${\mathbf{g}}_1 + {\mathbf{g}}_2 + {\mathbf{g}}_3$) before triggering the optimizer step ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-grad-accumulation|figure 13]]).

![[90 Assets/Volume I/08 Training/Generated Figure 5bb3da8ca8.svg]]

Figure 13: **Gradient Accumulation**: Three micro-batches each compute independent losses and gradients, which sum into a single combined gradient for one parameter update. This simulates training with a batch three times larger without requiring the memory to hold all samples simultaneously.

^fig-grad-accumulation

In PyTorch, gradient accumulation is usually implemented by dividing each micro-batch loss by the number of accumulation steps and calling `optimizer.step()` only after processing the entire effective batch. Under that averaging convention, no learning-rate adjustment is needed solely because of accumulation. The implementation follows five steps:

1.  Perform the forward pass for a micro-batch.
2.  Compute the gradients during the backward pass.
3.  Accumulate the gradients into a buffer without updating the model parameters.
4.  Repeat steps 1–3 for all micro-batches in the effective batch.
5.  Update the model parameters using the accumulated gradients after all micro-batches are processed.

Gradient accumulation can reproduce the gradient of a larger batch under controlled assumptions. For an effective batch size ${B}= {k}\times {B_{\text{micro}}}$ where ${k}$ is the number of accumulation steps and ${B_{\text{micro}}}$ is the micro-batch size, [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^eq-gradient-accumulation-equivalence|equation 10]] confirms that the accumulated gradient equals the true batch gradient:

$$
\nabla {\mathcal{L}_B} = \frac{1}{{B}}\sum_{i=1}^{{B}} \nabla {\mathcal{L}}_i = \frac{1}{{k}}\sum_{j=1}^{{k}}\left(\frac{1}{{B_{\text{micro}}}}\sum_{i \in {\mathcal{B}}_j} \nabla {\mathcal{L}}_i\right) \tag{10}
$$

^eq-gradient-accumulation-equivalence

This equivalence holds when each example’s computation is identical and the loss is averaged consistently. The right-hand side shows that averaging ${k}$ micro-batch gradients (each computed over ${B_{\text{micro}}}$ examples) produces the same result as computing the gradient over all ${B}= {k} {B_{\text{micro}}}$ examples at once. Stateful layers such as BatchNorm, stochastic operations such as dropout and data augmentation, finite-precision accumulation order, and step-indexed schedules can break exact equivalence, so large-batch accumulation still requires validation.

Gradient accumulation exchanges memory capacity for computation time. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^tbl-gradient-accumulation-tradeoffs|Table 12]] separates the memory benefit from the compute and scheduling costs that remain.

| **Dimension**   | **Effect**                                                                                                                                      |
|:----------------|:------------------------------------------------------------------------------------------------------------------------------------------------|
| **Memory**      | $\mathcal{O}({B_{\text{micro}}})$ instead of $\mathcal{O}({B})$, yielding a ${k}\times$ reduction in activation memory                          |
| **Computation** | Unchanged total FLOPs, as all ${B}$ examples are still processed                                                                                |
| **Time**        | ${k}$ micro-batch forward and backward passes precede each optimizer step; smaller micro-batches can reduce utilization and add launch overhead |

Table 12: **Gradient Accumulation Trade-Offs**: Accumulation reduces resident activation memory and preserves total example-level arithmetic. Wall-clock cost depends on micro-batch efficiency, kernel-launch overhead, and whether distributed synchronization is deferred until the accumulated update.

^tbl-gradient-accumulation-tradeoffs

Accumulation preserves the total example-level arithmetic but can change efficiency because smaller micro-batches use the accelerator differently and launch kernels more often. The model in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^eq-gradient-accumulation-overhead|equation 11]] gives the per-update time:

$$
{T_{\text{effective}}}= \sum_{j=1}^{{k}} {T_{\text{micro},j}}+ {T_{\text{sync}}}+ {T_{\text{update}}} \tag{11}
$$

^eq-gradient-accumulation-overhead

Here ${T_{\text{micro},j}}$ is the measured forward/backward time for micro-batch ${j}$, ${T_{\text{sync}}}$ is the synchronization time paid for the accumulated update, and ${T_{\text{update}}}$ is the optimizer-step time. On one accelerator the synchronization term is zero. It appears when several accelerators each hold a copy of the model and must combine their gradients before the update, the data parallelism of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-data-parallelism-ad1c|section 8.7.1.1]]. Accumulation then lets them combine gradients once per update rather than once per micro-batch, so the term is paid once.

The wall-clock penalty relative to processing the effective batch at once is workload-dependent and must be measured rather than inferred from the memory-reduction factor.

#### Activation Checkpointing

^sec-model-training-activation-checkpointing-2ee1

Activation checkpointing reduces activation memory by trading additional FLOPs for lower HBM occupancy during backpropagation. Only selected boundary tensors are retained in device memory; intermediate activations are dropped during the forward pass and recomputed on demand as the backward pass traverses in reverse ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^fig-activation-checkpointing|figure 14]], where retained tensors are solid green, dropped ones dashed gray, and recomputed ones orange). [Algorithm 3](https://mlsysbook.ai/vol1/08_training/08_training.html#algo-gradient-checkpointing) states the schedule layer by layer.

${N_L}$

In this segment schedule, recomputed intermediate values remain available until their backward consumers finish; recomputing a segment afresh for each layer would add more work. For layers with comparable activation sizes and forward costs, spacing checkpoints uniformly every $\sqrt{{N_L}}$ layers reduces peak activation memory from $\mathcal{O}({N_L})$ to $\mathcal{O}(\sqrt{{N_L}})$ at the cost of one additional forward pass of arithmetic per training step ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-chen2016training|Chen et al. 2016]]). This increases executed step computation from roughly $3\times$ to $4\times$ the forward-pass FLOPs, trading extra arithmetic operations for a substantially reduced activation footprint. The useful model FLOP count ${O}$ is unchanged, so the additional work enters the training-time law through effective utilization ${\eta_{\text{hw}}}$. Actual fit and wall-clock overhead still depend on the full memory budget and execution profile. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-optimal-checkpoint-placement-strategy-4a0d|Section 8.6.5.3]] derives why $\sqrt{{N_L}}$ spacing minimizes this footprint and works out its cost for GPT-2’s 48 layers.

![[90 Assets/Volume I/08 Training/Generated Figure 730cd3ca03.svg]]

Figure 14: **Activation Checkpointing**: Trading memory usage for recomputation during backpropagation enables training deeper neural networks. By storing only a subset of activations from the forward pass and recomputing others on demand, this technique reduces peak memory requirements at the cost of increased training time.

^fig-activation-checkpointing

Frameworks like PyTorch provide tools such as `torch.utils.checkpoint` that split a model into segments and manage the recomputation, but the recompute cost remains. Checkpointing is most effective for deep architectures with dozens or hundreds of layers, such as transformers or large convolutional networks, where activation storage exceeds the GPU’s capacity before arithmetic throughput is exhausted.

The two techniques address different terms. Gradient accumulation bounds the activation memory tied to batch size, while checkpointing bounds the memory held by each layer’s intermediate activations, so together they widen the range of models that fit on available hardware.

#### Optimal Checkpoint Placement Strategy

^sec-model-training-optimal-checkpoint-placement-strategy-4a0d

[Algorithm 3](https://mlsysbook.ai/vol1/08_training/08_training.html#algo-gradient-checkpointing) stated the $\sqrt{{N_L}}$ schedule without justifying it. For a network with ${N_L}$ layers of comparable activation size and recomputation cost, each storing ${M_{\text{activations}}}^{({\ell})}$ bytes of activations per example (the per-layer share inside [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^eq-activation-memory-per-batch|equation 3]], not the batch total ${M_{\text{activations}}}$), [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^tbl-checkpoint-tradeoffs|table 13]] quantifies how the number and placement of checkpoints determines the memory-compute trade-off. Sub-linear checkpointing strategies can reduce memory consumption from $\mathcal{O}({N_L})$ to $\mathcal{O}(\sqrt{{N_L}})$ with additional forward arithmetic; the resulting wall-clock overhead depends on execution, while the reduced footprint can enable deeper models on existing hardware.

| **Strategy**                               |                                                         **Memory Cost**                                                         | **Recompute Cost**                      |
|:-------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------:|:----------------------------------------|
| **No checkpointing**                       |                                        ${N_L} \times {M_{\text{activations}}}^{(\ell)}$                                         | 0 forward ops                           |
| **One checkpoint (${n_{\text{ckpt}}}=1$)** |                      ${M_{\text{activations}}}^{(\ell)} + {N_L} \times {M_{\text{activations}}}^{(\ell)}$                       | $({N_L}-1)$ forward ops                 |
| **${n_{\text{ckpt}}}$ checkpoints**        | ${n_{\text{ckpt}}}\times {M_{\text{activations}}}^{(\ell)} + ({N_L}/{n_{\text{ckpt}}})\times {M_{\text{activations}}}^{(\ell)}$ | $({N_L}-{n_{\text{ckpt}}})$ forward ops |

Table 13: **Checkpointing Memory-Compute Trade-Offs**: Different checkpoint strategies trade memory savings against recomputation overhead. The optimal number of checkpoints balances these factors.

^tbl-checkpoint-tradeoffs

The memory column counts two things, the stored checkpoints and the one segment that must be rematerialized at a time during backward, which holds ${N_L}/{n_{\text{ckpt}}}$ layers of activations. The one-checkpoint row shows why both terms matter. With a single checkpoint the only segment spans the whole network, so backward rebuilds all ${N_L}$ layers of activations at once and the peak is no lower than storing everything. Checkpoints pay off only when they are spread out so that each recomputed segment is short. The recompute column counts layer forwards. Every layer that is not itself a checkpoint is run forward once more, $({N_L} - {n_{\text{ckpt}}})$ layer forwards in all, which is nearly one full forward pass when ${n_{\text{ckpt}}}$ is much smaller than ${N_L}$.

Setting the derivative of total memory cost $({n_{\text{ckpt}}}\times {M_{\text{activations}}}^{(\ell)} + ({N_L}/{n_{\text{ckpt}}}) \times {M_{\text{activations}}}^{(\ell)})$ with respect to the checkpoint count ${n_{\text{ckpt}}}$ to zero yields the analytical optimum at ${n_{\text{ckpt}}}= \sqrt{{N_L}}$. In the standard $\sqrt{{N_L}}$ checkpointing scheme, this costs roughly one extra forward pass, about one-third more total step compute, in exchange for minimizing activation footprint under this analytical model. For GPT-2 with forty-eight transformer layers, the operational difference is substantial. Uncheckpointed training requires $48 \times {M_{\text{activations}}}^{(\ell)}$ in full activation storage. Uniform checkpointing ($\sqrt{48} \approx 7$ checkpoints) requires $7 \times {M_{\text{activations}}}^{(\ell)} + (48/7) \times {M_{\text{activations}}}^{(\ell)} \approx 14 \times {M_{\text{activations}}}^{(\ell)}$, which saves 71 percent of activation memory for approximately 33 percent additional total step computation (by recomputing one forward pass over the uncheckpointed layers during backpropagation).

A practical schedule treats $\sqrt{{N_L}}$ as a starting point rather than the answer, because the derivation above priced a stored segment input and one layer of the live segment as equal amounts of memory. In GPT-2 they differ greatly. Each segment input is only the hidden tensor, whereas each layer of the live segment being recomputed also holds its attention and feed-forward intermediates. When stored inputs are this cheap, adding segments shrinks the large live segment at little cost in stored inputs, so the best count lies above $\sqrt{{N_L}}$, while the recomputation stays at about one extra forward pass for any count. The GPT-2 notebook below therefore counts the small segment inputs and the large live segment separately, and it uses eight equal segments of six layers, an even division of the forty-eight layers just above that starting point.

**Napkin Math 8.8: GPT-2 segment checkpointing**

**Problem**: With mixed precision and FlashAttention-style attention, can a segment schedule fit GPT-2 XL’s batch-32 step on one H100, and what does it cost in arithmetic?

**Schedule**: Partition the 48 transformer layers into 8 contiguous segments of 6 layers. During forward execution, retain each segment’s input and discard its internal backward state. During backward execution, reconstruct one segment, retain its internal state while differentiating that segment, then free it before reconstructing the preceding segment. Each layer therefore executes one additional forward pass; against a forward-plus-backward step costing about three forward passes, the extra arithmetic is about one-third. This is work accounting, not a wall-clock penalty.

**Math**: Each retained segment input has shape batch $\times$ sequence length $\times$ hidden width, 32 $\times$ 1,024 $\times$ 1600 $\times$ 2 bytes. Keep all 8 inputs resident while adding the complete saved-state estimate for the 6 layers of one reconstructed segment. This deliberately counts the active segment’s input in both terms, making the estimate conservative rather than omitting a live boundary.

- Retained segment inputs: 0.84 GB
- Live reconstructed segment: 10.7 GB
- Activation allowance: 11.5 GB, against 85.6 GB without checkpointing (7.4× smaller)
- Static state plus activations: 35.5 GB, leaving about 50 GB of the H100’s capacity

**Systems insight**: Checkpointing admits the batch-32 step by replacing retained layer interiors with small boundary tensors and one live reconstructed segment. The remaining capacity must still hold output and loss buffers, temporary backward workspaces, and allocator overhead, which a runtime peak-memory measurement confirms. Gradient accumulation offers the alternative trade, keeping every activation of a smaller micro-batch and paying in update frequency instead of recomputation.

Not all operations are equally expensive to recompute, which motivates selective checkpointing: the practical rule is to spend recomputation on high-memory layers rather than on operations whose activations are already cheap to retain. |:------------------------|:------------------------------------------------------------------------|:-----------------------------------|:---------------------------------------------------------------------|
| **Attention blocks**    | Shape-dependent; materialized attention can add quadratic intermediates | High and sequence-length-dependent | Checkpoint block boundaries when saved state justifies recomputation |
| **Feed-forward blocks** | Often dominated by expanded hidden activations                          | High and width-dependent           | Checkpoint when expanded activations dominate memory                 |
| **Normalization**       | Small standalone outputs                                                | Low                                | Usually handled within a larger checkpointed block                   |

#### Memory and Computational Benefits

^sec-model-training-memory-computational-benefits-9372

Both techniques reduce activation-memory requirements without adding hardware, though each targets a different dimension of the activation footprint. Gradient accumulation produces an effective batch larger than the resident micro-batch without storing all of its activations simultaneously. A larger effective batch reduces sampling variance, but it does not by itself guarantee faster convergence or better generalization. Activation checkpointing instead reduces the per-layer memory footprint of intermediate activations by discarding and recomputing them as needed, freeing capacity for deeper models, additional layers, or higher-resolution inputs. For lighthouse [8.1](https://mlsysbook.ai/vol1/08_training/08_training.html#lhs-training-lighthouse-example-training-gpt-2), accumulation provides a direct way to reach a chosen effective batch size while keeping the resident micro-batch within one H100’s memory.

**Napkin Math 8.9: GPT-2 gradient accumulation strategy**

The chapter’s run estimates plan GPT-2 XL at batch 32 on one H100. GPT-2’s published recipe used a much larger batch of 512 sequences ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-radford2019language|Radford et al. 2019]]), and this scenario shows how gradient accumulation reaches that batch on a small server. It uses the lighthouse’s one-accelerator run time and a representative rental price; it does not reconstruct GPT-2’s historical training bill. It looks ahead to data parallelism, developed in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-data-parallelism-ad1c|section 8.7.1.1]], in which each accelerator holds a full copy of the model, works on its own share of the batch, and averages gradients with the others before every update. The scenario compares two ways of building the same effective batch: enough accelerators to hold the whole batch at once, or fewer accelerators that each accumulate several micro-batches before those gradients are averaged.

**Memory Constraints**

- With FlashAttention-style attention and no checkpointing, a micro-batch of ${B_{\text{micro}}}=$ 16 needs about 67 GB, within one H100’s 80 GB.
- A resident effective batch of ${B}=$ 512 would therefore require 512 ÷ 16 = 32 accelerators.

**Accumulation Configuration**

- Use 8 accelerators and accumulate 4 micro-batches of 16 sequences each.
- Each accelerator processes 16 $\times$ 4 = 64 sequences per update, giving a global effective batch of 8 accelerators $\times$ 64 = 512.

Each accelerator defers AllReduce, the gradient sum across accelerators, until its final micro-batch.

**Trade-off Analysis**

- Idealized wall-clock time: 4× longer (105 hours against 26 hours) because fewer accelerators perform the same arithmetic work
- Memory overhead: accumulation normally reuses parameter-gradient buffers, although bookkeeping and temporary storage remain
- Communication: both configurations synchronize once per 512-sequence update, but participant count and topology differ
- Equal-work cost: \$3,370 either way at \$4/hour per accelerator, before utilization and communication effects

**Why this works**: Under the equivalence conditions stated above, averaged per-example gradients are additive. Each accelerator first accumulates a local gradient over its 64 examples:

$$
\frac{1}{4}\sum_{j=1}^{4} \left[\frac{1}{16}\sum_{i=1}^{16} \nabla \mathcal{L}(x_{ji})\right]
$$

AllReduce then averages those local gradients across 8 accelerators, producing the global effective batch:

$$
\frac{1}{8}\sum_{r=1}^{8} \nabla \mathcal{L}_{\text{local}}^{(r)}, \qquad B = 8 \times 64 = 512
$$

**Operational comparison**

Resident configuration:

- 32 accelerators $\times$ 16 sequences = 512 resident sequences per update
- Gradient synchronization spans 32 accelerators
- Hourly cost: \$128/hour

Accumulated configuration:

- 8 accelerators $\times$ (16 sequences $\times$ 4 micro-batches) = 512 sequences per update
- Gradient synchronization occurs once per update across 8 accelerators, all within one server
- Hourly cost: \$32/hour
- Hourly reduction: \$96/hour, or 75 percent

**Quality check**

- Match the examples and their order, loss normalization, optimizer state and step schedule, and stochastic-layer behavior.
- Compare held-out loss or perplexity and the optimization trajectory across repeated runs rather than assuming that the effective batch alone guarantees equivalent quality.
- Expect small round-off differences from the changed summation order; require convergence within a declared tolerance rather than bitwise identity. No perplexity result is assumed here.

**Systems insight**: Accumulation lowers accelerator count and hourly burn, but ideal scaling preserves accelerator-hours; actual cost depends on utilization and communication.

[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^lst-gradient-accumulation-loop|Listing 8]] places one AllReduce after 4 local micro-batches, making the synchronization boundary explicit.

``` python
optimizer.zero_grad()
for step in range(4):  # Accumulation steps
    micro_batch = next(dataloader)  # 16 sequences
    loss = model(micro_batch) / 4  # Average effective-batch loss
    loss.backward()  # Accumulate gradients
# Now gradients represent 64 local sequences
all_reduce(gradients, op=SUM)  # Sum across 8 accelerators
gradients /= 8  # Convert the sum to the global mean
optimizer.step()  # Update with effective batch=512
```

#### Practical Considerations

^sec-model-training-gradient-accumulation-practical-considerations-a5a4

Gradient accumulation is most valuable when optimal batch sizes exceed GPU memory capacity. Transformer language models often use effective batches of hundreds of thousands to millions of tokens; if memory only permits a smaller number of sequences per device, accumulation bridges the gap without requiring additional hardware. Activation checkpointing complements this by enabling deeper architectures and is commonly used in transformer-scale training.

Both techniques introduce explicit trade-offs. Activation checkpointing recomputes discarded activations during backward propagation; with ordinary segment checkpointing, each discarded activation is typically reconstructed once, while recursive schedules may behave differently. Gradient accumulation reduces parameter-update frequency because each update follows ${k}$ micro-batches. When each micro-batch loss is divided by ${k}$, the accumulated gradient follows the effective-batch mean convention. If losses are summed instead, the gradients must be rescaled before the optimizer step or the learning-rate convention changed accordingly. Framework and codebase conventions differ, making normalization a common source of subtle bugs.

### GPT-2 Optimization Walkthrough

^sec-model-training-putting-together-gpt2-optimization-walkthrough-def7

Training GPT-2 XL at batch 32 on a single H100 exposes the physical boundaries that govern large-model optimization. The tensor allocation first exceeds accelerator memory, and once it fits, a naive input pipeline starves the execution engines. Each step below fixes whatever blocks the next, memory feasibility first and execution evidence second, before any accelerator is added.

**Napkin Math 8.10: GPT-2 optimization on one H100**

**Step 1**: Establish the baseline memory footprint.

The trace starts with GPT-2 XL at batch 32 and sequence length 1,024, FP32 tensors throughout, standard attention, and a single-threaded synchronous data loader. Weights, gradients, and Adam moments take 24 GB, and FP32 activations take 574 GB, so the step needs 598 GB, about 7× the H100’s 80 GB (85.9 GB in decimal units). The run fails the machine constraint before throughput matters.

**Step 2**: Apply mixed precision.

The first intervention targets memory feasibility rather than speed. Mixed precision (notebook [8.6](https://mlsysbook.ai/vol1/08_training/08_training.html#nbk-training-gpt-2-mixed-precision-memory)) halves the activations and leaves the static state unchanged, reducing the step to 311 GB. The allocation still exceeds the accelerator.

**Step 3**: Replace standard attention with FlashAttention.

Never storing the quadratic score matrices removes most of the remaining activations and brings the step to 109.6 GB, still above capacity. With this kernel, the largest batch that stays resident is about 23 sequences, so the configuration overflows somewhere between batch 16 and batch 32.

**Step 4**: Fit the batch.

Two techniques close the gap. Accumulating two micro-batches of 16 keeps the same arithmetic per update and needs 66.8 GB. Segment checkpointing (notebook [8.8](https://mlsysbook.ai/vol1/08_training/08_training.html#nbk-training-gpt-2-segment-checkpointing)) keeps all 32 sequences resident in 35.5 GB but adds about 33 percent more arithmetic per step. The walkthrough takes accumulation, because the batch it needs fits without recomputation; checkpointing is the choice when a larger resident micro-batch matters more than arithmetic. Runtime measurement must still verify that backward workspaces, output and loss buffers, and allocator overhead fit in the remaining capacity.

**Step 5**: Read the modeled timeline.

Fitting the model resolves capacity but does not guarantee efficient execution. With single-core tokenization, host preparation takes longer than the device’s step (example [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^exmp-training-gpt-2-language-model-data-pipeline|8.1]]), so a serial pipeline keeps the accelerator busy only about 48 percent of the time ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-gpu-utilization|equation 7]]). The diagnostic focus shifts from machine memory capacity (M) to the data pipeline (D) in D·A·M terms: reducing accelerator memory further would not touch the dominant exposed delay.

**Step 6**: Apply prefetching and parallel preparation.

Eight worker processes, page-locked (pinned) host memory for asynchronous DMA transfers, and a prefetch queue overlap host preparation with accelerator computation, and the parallel preparation interval falls well inside the device’s step. In the ideal overlapped model the accelerator is then busy for the whole step. A busy accelerator is not yet an efficient one; MFU measures how much of that busy time does useful model arithmetic, and re-profiling must establish whether memory bandwidth, arithmetic throughput, or another stage now limits execution.

**Result**: At the assumed 50 percent utilization, one step takes 0.60 s, the accelerator processes about 55,000 tokens/s, and the run takes about 35 days on one accelerator (about 47 days with segment checkpointing at the same executed rate). **Systems insight**: The order of interventions follows a dependency, not a preference. Memory feasibility comes first because a configuration that does not fit produces no profile at all.     2.  $50\text{ ms}$, because in ideal steady state the interval is bounded by the slowest overlapped stage rather than the serial sum.
    3.  $10\text{ ms}$, because all stages run concurrently and the fastest one sets the pace.
    4.  $90\text{ ms}$, because DMA transfers cannot overlap useful GPU computation.

3.  Why does the chapter’s conventional FP16 mixed-precision recipe keep FP32 master weights and perform selected reductions in FP32 instead of forcing every part of training into 16-bit precision?

    1.  Tensor Cores cannot execute backpropagation unless gradients are stored in FP64.
    2.  FP16 allocations can lock the accelerator memory bus unless the master weights are moved to host RAM.

    4.  Very small parameter updates can be rounded away when applied directly to FP16 weights, and selected reductions benefit from the wider range or precision of FP32 accumulation.
