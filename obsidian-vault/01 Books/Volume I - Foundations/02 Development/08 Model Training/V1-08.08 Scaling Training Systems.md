# V1-08.08 Scaling Training Systems

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training|V1-08 Model Training]]

^sec-model-training-scaling-training-systems-adfd

The GPT-2 walkthrough fits the batch-32 step on one H100 and finishes the run in about 35 days. One accelerator cannot finish sooner, and some models cannot fit at all. Spread across the 8 accelerators of one server with perfect scaling, the same run would take about 4.4 days. A 70-billion-parameter model needs about 140 GB for its FP16 weights alone and far more for full training state, which no single accelerator holds, motivating sharding, offload, or multiple devices.

![[90 Assets/Volume I/08 Training/Vol1 Training Margin 004 d84bceae90.svg]]

*Memory bars on a decimal-gigabyte scale: GPT-2 XL with two micro-batches of 16 (66.8 GB), the H100's capacity (85.9 GB), GPT-2 XL at batch 32 (109.6 GB), and 70B FP16 weights (140 GB); only the micro-batched step fits.*

*Two micro-batches of 16 fit one H100; batch 32 without checkpointing and a 70B model do not.*

When a chosen workload still exceeds one device’s memory or schedule, spreading it across devices provides aggregate memory and compute. Other responses include reducing the model, batch, sequence length, or training scope; offloading state; and parameter-efficient adaptation, which trains only a small set of added parameters on top of a frozen model. Scaling beyond one device begins with multi-GPU configurations inside one machine and may extend across nodes. The major parallelism strategies make different communication trade-offs; a full treatment of distributed-training implementation lies beyond this chapter.

These strategies are older than deep learning. Training platforms inherit dense matrix multiplication kernels and tightly synchronized parallel execution from high-performance computing (HPC). From warehouse-scale computing they inherit cluster orchestration and automated fault recovery for multi-day jobs, the lineage that matters once a run spans many machines.

Inside a single server, adding accelerators forces a choice between replicating weights across devices and partitioning the model, and it introduces synchronization overhead that can dominate training time. The stage interfaces formalized in **[[01 Books/Volume I - Foundations/01 Foundations/03 ML Lifecycle/V1-03.05 Stage Ownership and Hand-Offs#^sec-ml-workflow-stage-interface-specification-ae3c|Stage interface contracts]]** still govern what each part of the system may assume of the others.

Not all workloads benefit equally from adding GPUs. Adding accelerators helps only until communication and synchronization consume the time saved. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^fig-communication-tax|Figure 15]] charts this scaling decay on a log-log speedup plot up to 256 GPUs, contrasting ideal linear scaling against compute-bound (ResNet), balanced (a large language model (LLM) over NVLink), and communication-bound regimes. In this fixed-fraction model, even unlimited parallel compute leaves the non-scaling fraction of the original runtime, so the limiting speedup is its reciprocal, the Amdahl bound of **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^eq-amdahl|equation 11.1]]**.

![[90 Assets/Volume I/08 Training/Cell 62 Output 1 03cad2a38c.png]]

Figure 15: **Communication Overhead**: An Amdahl-style model compares ideal linear scaling against workloads with varying non-scaling communication and synchronization fractions. Real communication overhead scales dynamically with device count, network topology, message size, and overlap efficiency.

^fig-communication-tax

The red curve, labeled bandwidth bound in the legend, is the communication-bound workload synchronizing over a slow network. It falls furthest below the dashed ideal. Its widening gap is communication overhead made visible, and shrinking that gap is what the distributed strategies in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^sec-model-training-singlenode-multigpu-training-c87f|section 8.7.1]] exist to do.

### Single-Node Multi-GPU Training

^sec-model-training-singlenode-multigpu-training-c87f

Multi-GPU training within a single node introduces the core parallelism strategies. AlexNet[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.13 Footnotes#^fn16|¹⁶]] ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-krizhevsky2012imagenet|Krizhevsky et al. 2012]]) split its convolutional layers across two GTX 580 GPUs because the 3 GB device memory limit prevented single-chip execution, making cross-GPU connectivity an immediate architectural constraint. This section stays inside one node, where accelerators communicate over PCIe or NVLink.

The two foundational strategies partition different things. Data parallelism replicates the model and partitions the data, while model parallelism partitions model state or computation. This distinction determines memory requirements, communication patterns, and scaling behavior.

#### Data Parallelism

^sec-model-training-data-parallelism-ad1c

Data parallelism replicates the entire model on each GPU, with each processing different batches. After computing gradients locally, GPUs synchronize via gradient averaging. Input batches split across parallel GPU workers for independent forward and backward passes, then converge into an AllReduce collective, which sums the gradients from every worker and returns the result to each of them. Each replica divides that sum by the worker count to get the average, so every replica applies the identical parameter update ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^fig-train-data-parallelism|figure 16]]).

![[90 Assets/Volume I/08 Training/Generated Figure 8f54f2a99e.svg]]

Figure 16: **Data Parallelism**: Each GPU holds a complete model copy, processes a different data shard, and synchronizes gradients. Throughput can approach linear scaling only while computation dominates synchronization, input, and imbalance costs.

^fig-train-data-parallelism

When a model and its optimizer state fit comfortably within single-device memory, data parallelism serves as the primary scaling baseline because local forward and backward kernels run at native memory bandwidth without inter-device synchronization. Gradient aggregation is the principal recurring communication cost; some implementations also synchronize buffers or other state.

Implementations commonly run one process per accelerator, as PyTorch’s `DistributedDataParallel` (DDP) does, because a single coordinating process would have to scatter every batch and gather every output itself while serializing Python work under the global interpreter lock (GIL). Each process maintains its own model replica and local optimizer and exchanges gradients through collective AllReduce operations that overlap with backward-pass computation.

Synchronizing gradients is the step that data parallelism adds, and for GPT-2 XL inside one server its cost can be derived directly. Each replica holds FP16 gradients of 3 GB, and every replica must end the step with their sum. Ring AllReduce ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-patarasuk2009bandwidth|Patarasuk and Yuan 2009]]) arranges the ${N_{\text{GPU}}}$ accelerators in a logical ring and splits the gradient into ${N_{\text{GPU}}}$ chunks. In a reduce-scatter phase, each accelerator passes a chunk to its neighbor ${N_{\text{GPU}}} - 1$ times, adding the chunk it receives to its own, until each holds one fully summed chunk. In an all-gather phase, the summed chunks circulate ${N_{\text{GPU}}} - 1$ more times until every accelerator holds all of them. Each accelerator therefore sends $2({N_{\text{GPU}}}-1)/{N_{\text{GPU}}}$ of the gradient bytes ${D_{\text{vol}}}$, nearly twice the gradient however large the ring, and over a link of bandwidth ${\text{BW}}$ the bandwidth term of the synchronization time is

$$
{T_{\text{comm}}} \approx \frac{2({N_{\text{GPU}}}-1)}{{N_{\text{GPU}}}} \cdot \frac{{D_{\text{vol}}}}{{\text{BW}}} \tag{12}
$$

^eq-training-ring-allreduce

For 8 H100s the factor is 1.75, so each accelerator sends 5.25 GB per step, which takes about 12 ms at 450 GB/s per direction over NVLink. Against a 596 ms step when each replica processes the full batch of 32 sequences, synchronization is about 2 percent of the step even without overlap. Splitting a fixed batch of 32 eight ways shrinks each replica’s compute to 75 ms while the gradient bytes stay the same, raising the unhidden share to about 14 percent. Data parallelism inside one server is cheap for GPT-2 XL as long as each replica keeps enough work to amortize a synchronization whose size depends only on the parameter count. Frameworks hide most of what remains by launching AllReduce calls for groups of gradients, called buckets, while the backward pass is still computing earlier layers’ gradients.

Unsharded data parallelism has a hard constraint. Every accelerator holds a complete model replica and its full training state, 16 bytes per parameter in the mixed-precision Adam recipe, or 24 GB for GPT-2 XL on each of the 8 accelerators. The Zero Redundancy Optimizer (ZeRO) ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-rajbhandari2020|Rajbhandari et al. 2020]]) removes that redundancy by sharding training state across the data-parallel replicas in three stages. ZeRO-1 shards the 12 bytes of FP32 master weights and Adam moments, leaving 8.2 GB per accelerator for GPT-2 XL. ZeRO-2 also shards the gradients, leaving 5.6 GB. ZeRO-3, which fully sharded data parallelism (FSDP) ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-zhao2023|Zhao et al. 2023]]) implements, also shards the FP16 parameters, leaving 3 GB. The same arithmetic brings the Llama 3 8B full fine-tune that overflowed one accelerator in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-finetuning-memory-one-accelerator-7c2e|section 8.3.3.3]] down to about 16 GB of static state per accelerator.

That memory saving rearranges how replicas communicate. One Ring AllReduce consists of a reduce-scatter phase followed by an all-gather phase, moving two parameter-sized tensors per replica in total. ZeRO-1 and ZeRO-2 keep that total volume, because each accelerator needs only the summed gradients for its own shard, updates that shard between the two phases, and broadcasts the new weights in the all-gather. ZeRO-3 keeps no full copy of the weights, so it must all-gather each layer’s weights once for the forward pass and again for the backward pass before reduce-scattering the layer’s gradients. That schedule takes three parameter-sized collective passes instead of two, or about 1.5 times the data-parallel communication volume ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-rajbhandari2020|Rajbhandari et al. 2020]]).

Sharding within one node takes two forms. ZeRO splits training state while every accelerator still runs every layer, and it pays in communication. Model parallelism splits the layers themselves and pays in idle stages or in communication inside each layer, and a model that still exceeds local memory after ZeRO sharding needs this second form.

#### Model Parallelism

^sec-model-training-model-parallelism-c97e

Model parallelism partitions the model itself across GPUs, which becomes necessary when the model exceeds single-GPU memory. AlexNet adopted an early form of this strategy: selected convolutional layers split their kernels and channels across two GPUs, with communication at selected connections. A layerwise partition applies the same model-parallel idea differently ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^fig-model-parallelism|figure 17]]). Device 1 through Device 3 sequentially process layers 1–16, 17–32, and 33–48, streaming boundary activations forward during the forward pass and propagating loss gradients in reverse during backpropagation.

![[90 Assets/Volume I/08 Training/Generated Figure 5105188ee0.svg]]

Figure 17: **Model Parallelism**: The model is partitioned across devices, with intermediate activations passing between them. This enables training models larger than single-GPU memory at the cost of sequential dependencies.

^fig-model-parallelism

**Systems Perspective 8.4: Data vs. model parallelism**

When a selected workload is partitioned across ${N_{\text{GPU}}}$ devices, the split may divide examples, model state, layers, or tensor operations. For a model with parameters ${P}$ and batch size ${B}$, data and model parallelism provide two starting points.

**Data parallelism (split the batch)**: For a fixed global batch, each of ${N_{\text{GPU}}}$ workers processes about $1/{N_{\text{GPU}}}$ of the examples, but every worker holds a model replica and ordinarily its associated training state. Dense gradient communication is proportional to ${P}$ per update. Scaling departs from the ideal as local batches shrink or synchronization and input costs grow.

**Model parallelism (split model computation)**: Each accelerator stores and computes a portion of the model. An even partition may approach ${P}/{N_{\text{GPU}}}$ parameters per worker, but embeddings, buffers, imbalance, and replicated state alter that estimate. Communication depends on the partition: layerwise pipeline parallelism exchanges activations at stage boundaries, while tensor parallelism performs collectives within partitioned layers.

**Systems insight**: Data parallelism is the simplest candidate when the complete training state fits per worker and more throughput is needed. Model-state, pipeline, or tensor partitioning becomes necessary when it does not, often in combination with data parallelism.

When a model exceeds the memory capacity of a single accelerator, its depth can be partitioned across sequential devices. [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^fig-layers-blocks|Figure 18]] stages this pipeline allocation across a four-accelerator execution chain, grouping 24 transformer blocks into contiguous six-block partitions (Blocks 1–6 through 19–24) that exchange boundary activations over the interconnect. This chain is a separate illustration, smaller than the 48-layer, three-device split of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^fig-model-parallelism|figure 17]]; both follow the same rule of giving each device one contiguous group of layers.

![[90 Assets/Volume I/08 Training/Generated Figure eb45796620.svg]]

Figure 18: **Layer-Wise Model Partitioning**: Distributing consecutive transformer layers across sequential devices bounds network communication to intermediate activations (forward) and boundary gradients (backward). However, sequential layer dependencies leave downstream devices idle during forward passes unless micro-batches are pipelined.

^fig-layers-blocks

The main bottleneck in naive layer-wise partitioning is device serialization. Because layer evaluation is strictly sequential, Device 1 computes layers 1–6 while Devices 2–4 sit idle waiting for forward activations. During the backward pass, the dependency reverses: Device 4 computes first while upstream devices wait for returning gradients. This idle duration constitutes the *pipeline bubble*, which caps theoretical hardware utilization at $1/{N_{\text{GPU}}}$ under naive sequential execution. It differs from the accelerator bubbles of the staged training pipeline, which arise when one device’s data-loading, transfer, and compute stages run at mismatched rates. A pipeline bubble arises even with perfectly fed devices, because each device must wait for another device’s layers. Mitigating this idle time requires either pipelining micro-batches across stages or partitioning tensor dimensions within layers so that all devices compute simultaneously.

Both remedies fit inside one node. Pipeline parallelism splits each batch into micro-batches and streams them through the stages, so Device 2 works on the first micro-batch while Device 1 starts the second. The bubble then shrinks to the time spent filling and draining the pipeline at the start and end of each batch ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-huang2019gpipe|Huang et al. 2019]]; [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-narayanan2019|Narayanan et al. 2019]]), a share of the step that shrinks as the number of micro-batches grows relative to the number of stages. Tensor parallelism instead splits the matrix operations of each layer across devices, so every device works on every layer at once ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-shoeybi2019megatron|Shoeybi et al. 2019]]). The price is communication inside every layer, because the partial results must be combined before the next layer can begin. That frequency is why tensor parallelism is normally kept within one node, on its fastest links.

Within a node, GPUs may communicate through high-bandwidth links such as NVLink (up to 900 GB/s aggregate bidirectional bandwidth for the represented H100 configuration). Effective collective bandwidth depends on topology and contention and is lower than a raw aggregate link specification. Data parallelism communicates gradients via collective AllReduce operations, while layerwise model parallelism communicates activations point-to-point at partition boundaries. Data parallelism suits models that fit on one accelerator, whereas larger models require sharded training state or a split model.

### Scaling Beyond a Single Node

^sec-model-training-scaling-beyond-single-node-a671

One machine is this book’s scope, but its boundary is worth knowing. When a model’s parameter footprint, optimizer state, or training duration exceeds the capacity of an 8-accelerator node, distributed training extends across machines. The strategies of this section still apply, but three things change once training leaves the node. First, bandwidth drops sharply because machines are joined by a network such as Ethernet or InfiniBand rather than NVLink. Link throughput falls by one to two orders of magnitude, so gradient synchronization that overlapped with the backward pass inside a node can come to dominate each step. Second, placement must match each strategy to a tier of the network: the frequent intra-layer communication of tensor parallelism stays inside the node, whereas the once-per-step gradient exchange of data parallelism can cross slower inter-node links.

The third change is failure. Across thousands of accelerators during a multi-day run, hardware failure becomes a routine operational event, which makes automated checkpointing and restart an essential part of the training design. Each of the three changes is a subject of its own in large-scale distributed training; within one machine the same principles appear in their simplest form, which is why the single-node case comes first.

↪ Empirical protocols for quantifying multi-accelerator scaling efficiency and communication loss are developed in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.06 Training Benchmarks#^sec-benchmarking-scalability-parallelism-1124|Scalability and parallelism]]**.

### When to Scale: the Physical Ceiling

^sec-model-training-scale-physical-ceiling-e06c

Because crossing device and node boundaries adds communication traffic, synchronization barriers, and new failure modes that can slow a job that would have fit locally, a disciplined engineering workflow exhausts single-accelerator optimizations before adding hardware. Lower-precision execution ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-mixedprecision-training-9218|section 8.6.3]]) applies when numerical stability permits, gradient accumulation ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-gradient-accumulation-checkpointing-0c47|section 8.6.5]]) reaches target batch sizes without activation blowup, activation checkpointing ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-gradient-accumulation-checkpointing-0c47|section 8.6.5]]) trades redundant forward compute for memory headroom, and overlapped data prefetching ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.07 Pipeline Optimizations#^sec-model-training-data-prefetching-pipeline-overlapping-e984|section 8.6.2]]) hides host ingestion when it limits the critical path.

[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.08 Scaling Training Systems#^tbl-scaling-decision|Table 16]] structures this progression as a resource lookup keyed to measured hardware bottlenecks rather than arbitrary parameter thresholds.

| **Observed constraint**                                  | **Candidate approach**                 | **Rationale**                                             |
|:---------------------------------------------------------|:---------------------------------------|:----------------------------------------------------------|
| Training state fits one device and time is acceptable    | Single GPU                             | Minimizes communication and operational complexity        |
| State or throughput exceeds one device but fits one node | Single multi-GPU node                  | Uses fast local interconnects before crossing the network |
| Required state or schedule exceeds one node              | Multi-node cluster                     | Adds aggregate memory or compute at a communication cost  |
| Input service rate is below accelerator demand           | Parallel or distributed input pipeline | Adds input throughput where profiling shows it is needed  |

Table 16: **Scaling Decision Guidelines**: Choose the least distributed configuration that satisfies measured memory, throughput, and schedule requirements. Model architecture, training state, input pipeline, hardware, and topology all affect the boundary.

^tbl-scaling-decision

A measured single-device baseline guides scaling decisions, while a decisive capacity or compute-time lower bound can establish the need for additional resources before every local optimization is attempted. Once local tuning is exhausted or ruled out by lower bounds, resource expansion must match the specific physical limit that has been reached.

Memory capacity is the first such limit, reached when model weights, gradients, optimizer states, and activations exceed the memory of a single accelerator. A 70-billion-parameter model requires about 140 GB in FP16 for weights alone, exceeding the reference H100’s capacity and leaving little or no headroom on higher-capacity variants once training state is included. Training wall-clock time becomes the limit when the estimated duration on one device exceeds the project’s deadline, as in a $10^{24}$-FLOP workload that would take roughly 32 years at $10^{15}$ FLOP/s sustained. Input throughput limits the run when the host pipeline cannot sustain the aggregate accelerator consumption rate, which calls for more input-service capacity rather than more training accelerators. Dataset size alone does not determine this limit, because reuse, compression, locality, transformation cost, and storage bandwidth govern delivery rate.

Data parallelism also meets a statistical ceiling. Each added replica enlarges the global batch, and beyond the critical batch size defined in the discussion of mini-batch processing ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.04 Computation and Memory Costs of Training#^sec-model-training-minibatch-processing-4eb0|section 8.3.2.1.2]]), larger batches stop reducing the number of updates needed to reach a target loss ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.12 Source References#^ref-mccandlish2018empirical|McCandlish et al. 2018]]). Past that point, more replicas raise throughput in samples per second without shortening the time to target quality, so a scaling decision needs both the hardware ceiling and the batch at which the recipe’s convergence flattens.

These limits are technical, but scaling carries a cost beyond complexity and capacity. The training-time law already ties energy to run time. With ideal scaling, adding devices multiplies the power drawn and divides the run time by the same factor, so energy stays flat. Every loss in scaling efficiency raises the energy of the run, because each device keeps drawing power through the communication and idle time that the loss adds. **[[01 Books/Volume I - Foundations/04 Deployment/15 Responsible Engineering/V1-15.05 Environmental and Cost Awareness#^sec-responsible-engineering-tco-calculation-methodology-7cb0|Accounting for cost and carbon]]** converts that energy into carbon emissions.

**Napkin Math 8.11: The carbon footprint of training**

**Context**: Training large models requires substantial energy and compute. The physical ceiling appears once training time is converted to energy, cluster power multiplied by training time (${E_{\text{total}}} = {P_{\text{cluster}}}\cdot {T_{\text{train}}}$), quantifying environmental scale:

1.  Workload: Training a 7 billion-parameter model for 1 trillion tokens.
2.  Compute: ${O}\approx$ $4.2 \times 10^{22}$.
3.  Efficiency: 494 TFLOP/s sustained on the H100 (700 W thermal design power).
4.  **Execution time**: ${T_{\text{train}}}\approx$ 0.96 days on 1,024 GPUs.
5.  **Energy footprint**: ${E_{\text{total}}} = {P_{\text{cluster}}}\cdot {T_{\text{train}}}= ({N_{\text{GPU}}} \cdot {P_{\text{device}}} + {N_{\text{nodes}}} \cdot {P_{\text{host}}}) \cdot {T_{\text{train}}}$ evaluates to (1,024 GPUs $\times$ 700 W + 128 hosts $\times$ 200 W) $\times$ 23 hours $\approx$ 17,104.8 kWh.

**Impact**: Under the assumed constant GPU and host-CPU power, this modeled subtotal equals 19.0 months of average household electricity use. GPU thermal design power is a scenario input rather than measured draw; memory, storage, network equipment, and facility overhead are not separately included, so the subtotal is not total facility energy.

**Systems lesson**: Doubling hardware utilization ${\eta_{\text{hw}}}$ at constant cluster power ${P_{\text{cluster}}}$ halves execution time ${T_{\text{train}}}$ and total energy ${E_{\text{total}}}$. Under average grid carbon intensity (emissions per unit of electricity), doubling efficiency saves ~8,552.4 kWh of electricity and avoids 3.7 t of emissions. Environmental audits must measure ${E_{\text{total}}} = \int {P_{\text{cluster}}}({t})\,d{t}$ rather than relying on GPU utilization metrics alone.

Scaling changes the limiting constraint rather than removing it. Data parallelism adds throughput, sharded and model parallelism add memory capacity, pipeline parallelism recovers utilization lost to idle stages, and tensor parallelism makes layers larger than one device feasible, but each adds communication and coordination cost. The implementation details of multi-node distributed training, including collective communication primitives, fault tolerance mechanisms, and elastic scheduling, build directly on the single-machine principles covered throughout this chapter and are treated in depth in advanced distributed systems texts.

**Checkpoint 8.4: Scaling decisions**

Scaling trades compute bottlenecks for communication bottlenecks.

**Hard limits**: Identify which resource limits a given training run: memory capacity, compute throughput, or input-service rate.

**Single-node first**: Explain how a single-node baseline and relevant local optimizations inform scaling, and when a physical lower bound can justify scaling before all tuning is exhausted.

**Data vs. model parallelism**: Justify why unsharded data parallelism fails when model states exceed single-accelerator memory, and identify what model parallelism must partition.

**Communication overhead**: Explain why scaling efficiency degrades with accelerator count, and identify the communication metrics that dictate this ceiling.

**Scaling ceiling**: Estimate the theoretical speedup ceiling via Amdahl’s law when unparallelized synchronization accounts for 10 percent of step time, and determine where adding accelerators yields diminishing returns.

**Self-Check: Question**

1.  A team trains a 1.5-billion-parameter model that already fits on one 80 GB GPU with batch size 16 and its Adam training state, but one epoch still takes 12 days. The team has an 8-GPU node available. Which strategy is the best first baseline, and why?

    1.  Tensor parallelism, because splitting every weight matrix across the 8 GPUs is always the fastest way to improve training throughput.
    2.  Pipeline parallelism, because dividing layers across devices is the default first step whenever a model is a transformer.
    3.  Data parallelism such as DDP, because the model already fits per device and replication avoids unnecessary pipeline bubbles or intra-layer communication as the initial throughput baseline.
    4.  Full parameter sharding first, because any multi-GPU run should avoid keeping complete replicas even when memory is sufficient.

2.  In distributed data parallel training with $N$ GPUs and a model with $P$ parameters whose gradients use $B_{\text{bytes}}$ bytes each, what is the number of bytes sent by each GPU during a Ring AllReduce?

    1.  $2 \times \frac{N-1}{N} \times P \times B_{\text{bytes}}$, which approaches $2 P B_{\text{bytes}}$ as $N$ grows.
    2.  $N \times P \times B_{\text{bytes}}$, because each GPU must broadcast the full gradient to every other GPU.
    3.  $\frac{P \times B_{\text{bytes}}}{N^2}$, because the ring divides both the model and the communication quadratically.
    4.  Zero, because GPU replicas synchronize through shared CPU memory rather than explicit data movement.

3.  Explain what communication overhead is in distributed training, and analyze why adding more GPUs can lead to diminishing throughput returns.

4.  In pipeline model parallelism, partitioning a network linearly across $K$ stages without micro-batching (naive pipeline parallelism) achieves 100 percent GPU utilization because downstream devices can compute backward gradients while upstream devices run forward passes.

5.  Arrange the following engineering steps in the chapter’s preferred order for deciding whether to scale beyond one device, assuming the initial bounds do not already prove that single-device training is infeasible: (1) Re-evaluate whether memory or time limits still justify scaling. (2) Add distributed parallelism or sharding if the remaining limit still requires it. (3) Establish a single-device baseline and quantify the current bottleneck. (4) Apply relevant local optimizations such as mixed precision, prefetching, checkpointing, or accumulation.
