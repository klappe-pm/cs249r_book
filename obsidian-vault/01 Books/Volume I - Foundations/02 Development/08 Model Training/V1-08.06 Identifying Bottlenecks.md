# V1-08.06 Identifying Bottlenecks

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training|V1-08 Model Training]]

^sec-model-training-identifying-bottlenecks-f57f

An accelerator can report near-100 percent activity in `nvidia-smi` while spending half its cycles stalled on memory traffic, padding, or recomputing discarded activations. Knowing what each operation costs on paper does not show which resource actually saturates during a run, and raw device busy-time percentages cannot separate useful training arithmetic from overhead. Model FLOPs utilization (MFU)[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.13 Footnotes#^fn15|¹⁵]] supplies that comparison by measuring achieved model arithmetic against the hardware’s peak rate.

**Definition 8.3: Model FLOPs utilization (MFU)**

***Model FLOPs utilization (MFU)*** is the efficiency metric ${\text{MFU}} = {O_{\text{model}}}/ ({R_{\text{peak}}} \cdot {T_{\text{step}}})$, where ${O_{\text{model}}}$ is the useful per-step model FLOP count (forward plus backward, excluding rematerialization) and ${T_{\text{step}}}$ is the measured wall-clock time per training step. It expresses what fraction of peak hardware throughput is doing useful model computation.

1.  **Significance**: MFU makes the effective-throughput term in the iron law concrete. For GPT-2 XL (1.5B parameters) processing 32,768 tokens per step on an H100 (989 TFLOP/s dense FP16/BF16 Tensor Core peak), a 0.60 s step gives model FLOPs divided by the available peak-rate FLOP budget of approximately 0.50 (50 percent). The remaining 50 percent is not credited as model FLOPs and can reflect memory traffic, communication, bubbles, non-model operations, or idle time. Diagnosing that gap requires a profile rather than a universal threshold.
2.  **Distinction**: Hardware utilization reports whether device engines are active, whereas MFU credits the analytical model-FLOP estimate used in its numerator. It can therefore exclude recomputation and padding even when those operations keep the device busy. Comparisons across accelerators remain sensitive to the selected peak-throughput specification and FLOP-counting convention.
3.  **Common pitfall**: A frequent misconception is that 100 percent MFU is a realistic sustained target. Memory traffic, communication, and non-matrix work keep end-to-end runs below peak. Reported values depend on the model, precision, batch shape, hardware, and MFU definition, and can improve with FlashAttention and careful tuning.

Three distinct metrics are commonly referred to as “utilization” in training systems, and each addresses a different operational question. The hardware efficiency factor ${\eta_{\text{hw}}}$ in the training-time law ([[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.03 Training-Time Law#^eq-training-iron-law|equation 1]]) represents the end-to-end fraction of theoretical peak compute converted into useful model arithmetic across an entire run. MFU measures this same ratio over an individual training step, as the direct empirical estimator for ${\eta_{\text{hw}}}$. In contrast, the accelerator busy-time fraction of [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^eq-gpu-utilization|equation 7]], the metric reported by standard operating-system and vendor monitoring utilities such as `nvidia-smi`, indicates only whether execution cores are active, without distinguishing useful matrix products from memory-stall cycles, padding overhead, or rematerialization. Consequently, busy-time utilization serves only as an upper bound on MFU: a data-starved pipeline has a low busy-time fraction, whereas a well-fed but memory-stalled workload shows near-100 percent busy-time utilization alongside low MFU.

Training bottlenecks can be investigated through three categories aligned with the D·A·M taxonomy (Data, Algorithm, Machine). [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.06 Identifying Bottlenecks#^tbl-dam-training-bottlenecks|Table 7]] sorts each common bottleneck by the axis where its first remedy is usually found, and lists the symptoms and techniques for each. A compute-bound kernel is first relieved by asking for less or cheaper arithmetic, an Algorithm change. A memory-bound kernel is first relieved by changing how the machine stages and moves bytes, a Machine change. An input stall is relieved by repairing the data path, a Data change. The axis therefore tells an engineer where to look first, not the only place a fix can come from. Several remedies in the table act on more than one axis. Reduced precision appears in both the compute-bound and memory-bound rows because it raises the arithmetic peak and also halves the bytes each value moves. Faster compute hardware, listed in the compute-bound row, relieves the same bottleneck from the Machine side.

↪ The full D·A·M diagnostic framework, with its troubleshooting matrix and scorecard, is collected for reference in **[[05 Reference/Volume I - Foundations/V1 The D·A·M Taxonomy#^sec-appdx-dam-taxonomy|The D·A·M Taxonomy]]**.

| **D·A·M Axis** | **Bottleneck** | **Symptoms**                                                                                                          | **Primary Solutions**                                                 |
|:---------------|:---------------|:----------------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------|
| **Algorithm**  | Compute-bound  | High arithmetic-unit activity; additional bandwidth does not improve throughput; arithmetic throughput is limiting    | Reduced precision, more efficient algorithms, faster compute hardware |
| **Machine**    | Memory-bound   | High memory-bandwidth use relative to arithmetic throughput; kernels stall on data movement                           | Kernel fusion, memory-efficient attention, reduced precision formats  |
| **Data**       | Data-bound     | Periodic accelerator utilization drops to near-zero; CPU fully busy during gaps; pipeline cannot feed GPU fast enough | Prefetching, pipeline overlap, faster storage, DataLoader parallelism |

Table 7: **D·A·M Taxonomy Applied to Training Bottlenecks**: Each row associates a D·A·M axis with one common bottleneck and its characteristic symptoms. Profiling reveals the workload’s limiting constraint and guides practitioners to an appropriate optimization technique.

^tbl-dam-training-bottlenecks

Among these three regimes, data-bound stalls are the most frequently misdiagnosed because they manifest on the accelerator as idle gaps rather than saturated execution units. When host-side ingestion, decoding, or preprocessing cannot sustain the throughput demanded by the accelerator, the accelerator starves.

**Example 8.2: The GIL-locked GPU**

**Scenario**: An engineering team builds a PyTorch data-loading pipeline using standard Python `threading` for CPU-bound image preprocessing that holds the global interpreter lock (GIL), the lock that lets only one thread at a time run Python code in a process.

**Diagnosis**: The GIL serializes these Python-level preprocessing threads, making host preparation time (${T_{\text{prep}}}\approx 250 \text{ ms}$) far exceed GPU execution time (${T_{\text{GPU}}}\approx 12 \text{ ms}$), reducing the accelerator busy-time fraction to about 4.6 percent in this serial preparation-and-compute model. Here the fraction measures time spent computing, not arithmetic efficiency relative to peak throughput.

**Systems lesson**: Python CPU work that holds the GIL can serialize threads and starve GPUs; native operations may release it. Process workers (`num_workers > 0`) avoid interpreter serialization, while the NVIDIA Data Loading Library (DALI) can move eligible work off the host.

These idle gaps mark periods where accelerator streams stall waiting for CPU-side batch preparation and host-to-device transfers, providing a characteristic signature of an input-bound pipeline.

Two classes of tools expose these signatures. Framework-level profilers record a timeline of operations, memory allocations, and input-pipeline stalls, which locates idle gaps and attributes them to host work. System- and kernel-level GPU profilers record kernel execution, memory transfers, synchronization points, and per-kernel counters such as achieved memory throughput and arithmetic-unit occupancy, which explains why a kernel that runs is slow. The method below uses the first class to find where time goes and the second to explain it.

↪ How profilers and benchmark harnesses turn these measurements into reproducible results is developed in **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12.06 Training Benchmarks#^sec-benchmarking-training-benchmarks-96da|Training Benchmarks]]**.

A disciplined profiling workflow proceeds top-down from system timelines to kernel-level performance counters, mapping observable profiler traces to the D·A·M taxonomy in [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.06 Identifying Bottlenecks#^tbl-dam-training-bottlenecks|table 7]]. First, timeline visualization locates idle intervals between kernel invocations. Correlating these gaps with batch preparation, transfers, host dispatch, and synchronization establishes what prevents the next kernel from running. When input starvation is confirmed, remedies include asynchronous prefetching, multi-process workers, or offloading preprocessing to the accelerator to overlap data movement with compute. Second, when kernels execute contiguously without host-induced gaps, memory throughput relative to peak bandwidth distinguishes memory-bound from compute-bound execution. If HBM traffic saturates while arithmetic units idle, the workload is memory-bound; kernel fusion and memory-efficient attention relieve this constraint by retaining intermediate tensors in on-chip SRAM rather than writing them back to global memory. Finally, if tensor cores operate near theoretical capacity and memory buses have spare bandwidth, the workload is compute-bound, where throughput gains require lower numerical precision, such as BF16 or FP8, to increase peak arithmetic throughput.

Applied to the chapter’s two running cases, the method gives two different first moves. Before profiling anything, the FP32 GPT-2 XL step at batch 32 does not fit in an H100’s memory. Feasibility comes before speed, because a configuration that does not fit produces no profile to read, so the memory techniques below must address this capacity limit first. Once it fits, the timeline shows the input gaps. With single-core tokenization, host preparation takes about 655.4 ms per batch against a device step of about 596 ms (example [[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.05 Pipeline Architecture#^exmp-training-gpt-2-language-model-data-pipeline|8.1]]). A serial pipeline therefore keeps the device stage busy only about 48 percent of each step, a Data-axis diagnosis that no kernel optimization can fix. ResNet-50 on the H100 reaches the same axis by a different route: the host cores available per accelerator supply too few decoded images, leaving the accelerator busy only about 52 percent of the time. A diagnosis names the limiting resource; it does not remove it. These two profiles, read against the training-time law and the memory constraint, determine which intervention to apply first and which ones would change nothing.

1.  Why is Model FLOPs Utilization (MFU) a more reliable metric than raw GPU busy percentage (reported by tools like `nvidia-smi`) when evaluating training systems efficiency?

    1.  MFU is measured directly from host CPU clock cycles, eliminating GPU driver instrumentation overhead.
    2.  MFU is mathematically fixed to 100% on any healthy accelerator cluster regardless of software overhead.
    3.  MFU counts only the theoretical forward and backward FLOPs required by the model architecture divided by the product of peak hardware throughput and measured step time, whereas raw GPU busy percentage also counts time spent on recomputation, padding, and memory stalls outside that model-FLOP numerator.
    4.  MFU measures training loss convergence speed per dollar rather than floating-point operations.
