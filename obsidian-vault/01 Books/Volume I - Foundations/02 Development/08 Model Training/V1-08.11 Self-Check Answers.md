1.  **A 7-billion-parameter model uses 14 GB of FP16 weights for inference and fits comfortably on a single 40 GB accelerator. Switching the same model to standard mixed-precision Adam training causes immediate out-of-memory failures even before activations are accounted for. Using the mixed-precision Adam accounting that the section previews, which factor is most directly responsible?**

    1.  Adam internally re-runs the forward and backward passes, so the same weights must be stored several extra times during each step.
    2.  Adam adds 14 GB of FP16 gradients, 28 GB of FP32 master weights, and 56 GB of FP32 first- and second-moment state, pushing the static training state to about 112 GB before activations.
    3.  Adam requires the full training corpus to be cached in accelerator memory so batches can be reused across optimizer steps.
    4.  Adam forces all model tensors into FP64 during backpropagation, which multiplies the weight footprint beyond device capacity.

    *Answer*: The correct answer is B. In the section’s standard mixed-precision Adam recipe, training state includes 14 GB of FP16 weights, 14 GB of FP16 gradients, 28 GB of FP32 master weights, and 56 GB of FP32 moment state, for about 112 GB before activations. The idea that Adam re-runs model passes confuses optimizer state with the forward/backward computation, and dataset caching is part of the input pipeline rather than resident model-training state on the accelerator.

    *Learning Objective*: Calculate the static mixed-precision Adam training-state footprint from weights, gradients, master weights, and optimizer state.

2.  **True or False: Sudden NaN loss spikes during mixed-precision training are usually the same failure mode as an out-of-memory error, because both come from the GPU running out of memory during backpropagation.**

    *Answer*: False. An out-of-memory failure is a capacity problem that triggers an allocation error, while NaNs indicate numerical instability somewhere in the training computation. Mixed precision can contribute to numerical issues, but a NaN spike is not the same diagnosis as memory exhaustion.

    *Learning Objective*: Distinguish memory-capacity failures from numerical-instability failures in mixed-precision training.

3.  **In machine learning frameworks, the technique of discarding selected intermediate forward activations and recomputing them on demand during the backward pass to reduce peak memory is known as activation \_\_\_\_.**

    *Answer*: The correct answer is checkpointing (also called gradient checkpointing or activation recomputation). Activation checkpointing allows training systems to trade additional computation for a substantially reduced activation memory footprint.

    *Learning Objective*: Identify the systems term for trading backward recomputation against forward activation storage.

Under the training-time law $T_{\text{train}} = \frac{O}{R_{\text{peak}} \times \eta_{\text{hw}}}$, which lever is the most direct target for the next round of profiling?**

    1.  Hardware utilization $\eta_{\text{hw}}$, because with $O$ and the relevant $R_{\text{peak}}$ convention fixed, the remaining gap points to how efficiently kernels are being executed end to end.
    2.  Peak throughput $R_{\text{peak}}$, because low effective end-to-end utilization relative to the stated peak automatically means the hardware peak specification is too small for the workload.
    3.  Total operations $O$, because once data and communication are hidden, utilization is no longer relevant to training time.
    4.  Dataset size, because shrinking the number of tokens directly raises effective end-to-end utilization relative to the stated peak even when execution efficiency is unchanged.

    *Answer*: The correct answer is A. That does not prove one unique cause, but it does justify profiling device execution for stalls, inefficient kernels, launch overhead, or other losses inside the end-to-end throughput term. Reducing $O$ may shorten total training time, but it answers a different question than why this execution reaches only 38 percent of the chosen peak.

2.  **When a team transitions a model from FP32 training to mixed-precision (FP16/BF16) on Tensor Core accelerators without changing the model architecture, batch size, or dataset, which term of the training-time law ($T_{\text{train}} = \frac{O}{R_{\text{peak}} \times \eta_{\text{hw}}}$) is most directly improved?**

    1.  Total operations $O$, because lower numerical precision halves the number of multiplications required in each matrix multiplication.
    2.  Hardware utilization $\eta_{\text{hw}}$, because mixed precision automatically eliminates all GPU pipeline bubbles and CPU data stalls.
    3.  Peak throughput $R_{\text{peak}}$, because Tensor Cores provide a substantially higher theoretical FLOP/s ceiling for reduced-precision matrix operations compared to standard FP32 execution units.
    4.  Data volume $D_{\text{tokens}}$, because lower precision requires fewer training tokens for the loss to converge.

    *Answer*: The correct answer is C. The chapter’s optimization matching table assigns mixed precision (FP16/BF16) to peak throughput ($R_{\text{peak}}$). Tensor Cores execute reduced-precision matrix multiplications at several times the theoretical FLOP/s ceiling of FP32 ALUs. The claim regarding total operations $O$ is incorrect because the algorithmic graph and number of multiply-accumulate operations remain identical. The utilization claim is incorrect because $\eta_{\text{hw}}$ measures efficiency relative to the available peak, and precision changes do not inherently eliminate data loader bubbles. The data volume claim is false because precision does not reduce sample requirements.

    *Learning Objective*: Classify mixed-precision training by its direct target term ($R_{\text{peak}}$) in the training-time law.

3.  **Explain the scope conditions under which the simplified training-time law $T_{\text{train}} = \frac{O}{R_{\text{peak}} \times \eta_{\text{hw}}}$ is useful, and identify why the formula alone cannot diagnose a slow small-batch debugging run.**

    *Answer*: The equation is useful as an accounting identity: it relates total work, a chosen peak-throughput reference, and effective achieved throughput into one training-time estimate. But because the end-to-end utilization term can already include stalls from launches, transfers, synchronization, and underfilled kernels, the formula alone does not reveal which mechanism caused a slow run. In a small-batch debug session, the problem is not that the law becomes invalid; it is that a low measured utilization could come from many overheads, so diagnosis still requires profiling rather than reading the formula by itself.

    *Learning Objective*: Explain what the simplified training-time law captures and why it does not by itself localize the cause of low-throughput execution.

4.  **True or False: All large deep learning models are primarily compute-bound, so training speed is always governed mainly by Tensor Core TFLOP/s.**

    *Answer*: False. Dense transformer training often spends much of its work in matrix multiplications, but other workloads can be limited by memory capacity or bandwidth instead. The section’s DLRM example is dominated by large embedding tables, where fitting and moving the state can matter more than raw dense-math throughput.

    *Learning Objective*: Distinguish compute-bound dense training from regimes where memory capacity or bandwidth is the limiting constraint.

    *Answer*: The correct order is: (2) Backpropagation is popularized for multilayer neural networks, (4) AlexNet demonstrates that deep neural network training maps effectively to GPUs, (1) Transformers shift sequence modeling toward high-throughput dense matrix multiplication and large activation footprints, (3) Large-scale foundation models such as GPT-3 make utilization and multi-accelerator scaling central engineering concerns, (5) IO-aware FlashAttention appears as a response to attention memory-bandwidth limits. 1.  **Why do batched matrix-matrix multiplications (GEMM, BLAS Level 3) usually achieve much higher accelerator utilization in neural network training than matrix-vector operations (GEMV, BLAS Level 2)?**

    1.  Matrix-matrix operations avoid gradient computation during backpropagation, so they save both memory traffic and arithmetic work.
    2.  Under the ideal traffic model in the section, GEMM reuses loaded operands across many outputs, so arithmetic intensity can grow with matrix size, whereas GEMV offers much less reuse and tends to stay near constant arithmetic intensity.
    3.  Matrix-vector operations cannot run efficiently on GPUs because every layer result must be synchronized back to the CPU before the next layer starts.
    4.  Batched matrix-matrix operations reduce the model’s parameter count, which is why they keep more of the network in HBM.

    *Answer*: The correct answer is B. Under the section’s idealized traffic analysis, GEMM performs many more FLOPs per byte moved because tiles of weights and activations are reused across multiple outputs, so its arithmetic intensity can scale upward with problem size. GEMV offers far less reuse, so moving bytes can dominate execution. The claim that GEMM avoids gradients is wrong because training uses matrix multiplies heavily in backward as well as forward, and the CPU-synchronization explanation confuses low arithmetic intensity with an unsupported execution model.

    *Learning Objective*: Compare GEMM and GEMV using arithmetic intensity and operand reuse in the accelerator memory hierarchy.

2.  **A team trains a 7-billion-parameter model on accelerators with 80 GB of HBM each. Weights, gradients, activations, and common workspaces already occupy 64 GB per accelerator, and this total already includes any FP32 master weights if the recipe uses them. The model is unsharded per device. Using the section’s optimizer-memory accounting, explain the systems trade-off between choosing plain SGD and Adam for this run.**

    *Answer*: Adam adds two FP32 moment tensors, or 8 bytes per parameter, so a 7B-parameter model needs about 56 GB more optimizer state. That pushes the per-device total from 64 GB to about 120 GB, which exceeds an 80 GB accelerator before any sharding decision is considered, whereas plain SGD adds no auxiliary optimizer state and still fits at 64 GB. The practical consequence is that this choice is first a capacity question; once a feasible optimizer is chosen, the team should then measure time to target quality rather than assume one optimizer will always converge faster.

    *Learning Objective*: Calculate whether SGD or Adam fits within a fixed HBM budget when common training state is already accounted for.

    *Answer*: The correct answer is ridge (or roofline ridge). The ridge point represents the minimum arithmetic intensity required for an operation to reach the accelerator’s maximum computational throughput.

Host-to-device PCIe transfer sustains $32\text{ GB/s}$, and GPU compute consumes data at an equivalent rate of $12\text{ GB/s}$. Under the section’s ideal-overlap pipeline model, what determines end-to-end throughput, and what is the best first engineering action?**

    1.  The average of the three rates, so the effective throughput is $16\text{ GB/s}$ and all stages should be tuned evenly.
    2.  The PCIe transfer rate, because every batch must cross the bus before any compute can happen.
    3.  The minimum rate, $4\text{ GB/s}$ from preprocessing, so the first action is to reduce the input-side bottleneck before tuning faster stages.
    4.  The GPU compute rate, because training pipelines are ultimately limited by accelerator execution speed rather than host stages.

3.  **Explain why CPU-side tokenization and data augmentation can severely bottleneck GPU training even when the resulting tensor transfer across PCIe takes less than one millisecond.**

    *Answer*: A fast PCIe copy only shows that the transfer stage is short once a batch already exists; it says nothing about how long the CPU needed to create that batch. If CPU preprocessing takes 65 ms and GPU compute takes 80 ms, then with proper overlap the next batch can still be ready in time, but without overlap or with an unstable host service interval the GPU can see bubbles despite the sub-millisecond transfer. The practical consequence is that busy-time fractions alone are not peak arithmetic efficiency and do not prove a specific worker count; what matters is whether preprocessing can consistently supply the next batch before compute needs it.

    *Learning Objective*: Analyze why preprocessing latency can dominate input delivery even when the PCIe transfer itself is short.

4.  **True or False: Scaling the training batch size by $8\times$ while keeping the learning rate and schedule unchanged guarantees the same model quality in less wall-clock time.**

    *Answer*: False. A larger batch changes both the number of updates per epoch and the gradient statistics seen by the optimizer, so the old learning-rate schedule may no longer be appropriate. The section says validation is needed after a large batch-size change, and retuning may be needed rather than guaranteed.

    *Learning Objective*: Evaluate why changing batch size can alter optimization behavior even when hardware throughput improves.

5.  **To enable fast, asynchronous Direct Memory Access (DMA) transfers from host RAM to GPU memory without intermediate CPU staging copies, host memory buffers must be allocated as page-locked or \_\_\_\_ memory.**

    *Answer*: The correct answer is pinned (or page-locked). Pinned memory prevents the operating system from paging memory to disk, enabling the GPU DMA controller to read tensors asynchronously concurrently with compute.

    *Learning Objective*: Identify the systems mechanism (pinned memory) used for asynchronous host-to-device transfers.

6.  **In the chapter’s staged system pipeline framework, what constitutes an “accelerator bubble” and what is the primary diagnostic step to resolve it?**

An accelerator bubble is defined as idle or underutilized accelerator time resulting from a throughput mismatch across the four pipeline stages (Data Loading & Preprocessing, Host-to-Device Transfer, Forward/Backward Compute, and Parameter Synchronization). Resolving bubbles requires profiling each stage to locate the limiting constraint and applying overlapping techniques such as asynchronous prefetching. The assertion of intentional synchronization misinterprets a performance inefficiency as a design feature. The SRAM cache eviction option confuses low-level cache misses with macro pipeline stalls. The ridge-point loss option misapplies roofline terminology to pipeline-level time allocation.

1.  **Why is Model FLOPs Utilization (MFU) a more reliable metric than raw GPU busy percentage (reported by tools like `nvidia-smi`) when evaluating training systems efficiency?**

    1.  MFU is measured directly from host CPU clock cycles, eliminating GPU driver instrumentation overhead.
    2.  MFU is mathematically fixed to 100% on any healthy accelerator cluster regardless of software overhead.
    3.  MFU counts only the theoretical forward and backward FLOPs required by the model architecture divided by the product of peak hardware throughput and measured step time, whereas raw GPU busy percentage also counts time spent on recomputation, padding, and memory stalls outside that model-FLOP numerator.
    4.  MFU measures training loss convergence speed per dollar rather than floating-point operations.

    *Answer*: The correct answer is C. Raw GPU utilization measures the percentage of time GPU execution units or kernels are active. A GPU can show 95% utilization while spending half its time stalling on memory bandwidth or recomputing activations during gradient checkpointing. In contrast, MFU ($\text{MFU} = \frac{O_{\text{model}}}{R_{\text{peak}} \times T_{\text{step}}}$) includes only the useful forward and backward model FLOPs in the numerator, explicitly penalizing recomputation, padding FLOPs, memory stalls, and pipeline bubbles. MFU is an accelerator metric, not a CPU metric. MFU is not fixed to 100%; reported values depend on workload, hardware, precision, and the FLOP-counting convention. MFU measures hardware efficiency, not loss convergence per dollar.

    *Learning Objective*: Differentiate Model FLOPs Utilization (MFU) from raw GPU busy utilization and explain which overheads MFU exposes.

1.  **For each batch, a training step has three dependent stages in a serial baseline: data preprocessing ($T_{\text{prep}} = 30\text{ ms}$), host-to-device transfer ($T_{\text{xfer}} = 10\text{ ms}$), and GPU compute ($T_{\text{comp}} = 50\text{ ms}$). 2.  **Explain how FlashAttention computes exact self-attention with substantially lower memory footprint than standard attention, and describe what its backward pass does instead of reading a full stored score matrix from HBM.**

    *Answer*: FlashAttention keeps the same attention mathematics, with possible floating-point rounding differences, but changes where intermediate work lives: it processes query, key, and value tiles in on-chip SRAM and maintains the softmax statistics online instead of materializing the full $S \times S$ score matrix in HBM. That cuts saved activation storage and reduces off-chip traffic tied to those score blocks rather than implying a linear law for all HBM IO. In backward, it recomputes the needed tiled score and probability blocks from saved inputs and normalization statistics rather than loading a full stored score matrix, so the systems gain comes from less HBM traffic, not from changing the attention mathematics.

    *Learning Objective*: Explain how IO-aware tiling and backward recomputation reduce attention memory traffic without changing attention mathematics.

3.  **Why does the chapter’s conventional FP16 mixed-precision recipe keep FP32 master weights and perform selected reductions in FP32 instead of forcing every part of training into 16-bit precision?**

    1.  Tensor Cores cannot execute backpropagation unless gradients are stored in FP64.
    2.  FP16 allocations can lock the accelerator memory bus unless the master weights are moved to host RAM.
    3.  Automatic differentiation requires symbolic derivatives to be represented only in FP32.
    4.  Very small parameter updates can be rounded away when applied directly to FP16 weights, and selected reductions benefit from the wider range or precision of FP32 accumulation.

    *Answer*: The correct answer is D. The section’s FP16 recipe keeps FP32 master weights because an update can be too small to change a stored FP16 weight after rounding even when the update itself is representable; preserving the update in FP32 avoids losing it across many steps. The same section also notes that selected reductions are often kept in FP32 because wider accumulation improves numerical behavior, though it does not guarantee stability everywhere. The FP64 and host-RAM claims invent hardware requirements the chapter does not make, and autodiff does not require a purely FP32 graph representation.

    *Learning Objective*: Justify FP32 master weights and selected FP32 reductions in the conventional FP16 mixed-precision training recipe.

4.  **Gradient accumulation increases the memory footprint on the accelerator linearly with the accumulation factor $K$ because all $K$ micro-batches’ intermediate activations must remain in GPU memory simultaneously until the optimizer step.**

    *Answer*: False. Gradient accumulation executes forward and backward passes sequentially across $K$ micro-batches, accumulating (summing) only the parameter gradients in a single fixed-size gradient buffer. Saved backward tensors for each micro-batch can be released after its backward pass when the graph is not retained; other references or cached tensors may extend storage lifetime. Consequently, activation memory is bounded by the size of a single micro-batch ($B_{\text{micro}}$), allowing systems to emulate an effective batch size of $K \times B_{\text{micro}}$ without increasing activation memory.

    *Learning Objective*: Analyze the memory behavior of gradient accumulation across multiple micro-batches.

5.  **In FP16 mixed-precision training, the loss is multiplied before backpropagation so the resulting gradients are shifted into a safer numeric range, then divided back down before the optimizer update. This technique is known as loss \_\_\_\_.**

    *Answer*: scaling. Loss scaling multiplies the loss before backward so the resulting gradients are less likely to underflow in FP16, then unscales them before the optimizer step.

    *Learning Objective*: Identify loss scaling as the technique used to reduce FP16 gradient underflow risk.

6.  **A team enables mixed precision on a transformer model and observes compute time drop by 45 percent, but total step time decreases by only 10 percent because the GPU now shows large idle gaps. Explain what likely happened in the system pipeline and what the team should do next.**

    *Answer*: The compute optimization removed part of the old critical path, but the new timeline shows that another stage is now exposed because the GPU is spending meaningful time idle. Those gaps are not proof of a data-loader problem by themselves: they could come from input waits, dispatch overhead, synchronization, or another serial stage. The right next step is to re-profile and correlate the gaps with pipeline stages so the next optimization targets the new bottleneck rather than assuming mixed precision failed.

    *Learning Objective*: Explain why speeding up compute can expose a different bottleneck and why re-profiling is required before choosing the next optimization.

**Self-Check: Answer**

1.  **A team trains a 1.5-billion-parameter model that already fits on one 80 GB GPU with batch size 16 and its Adam training state, but one epoch still takes 12 days. The team has an 8-GPU node available. Which strategy is the best first baseline, and why?**

    1.  Tensor parallelism, because splitting every weight matrix across the 8 GPUs is always the fastest way to improve training throughput.
    2.  Pipeline parallelism, because dividing layers across devices is the default first step whenever a model is a transformer.
    3.  Data parallelism such as DDP, because the model already fits per device and replication avoids unnecessary pipeline bubbles or intra-layer communication as the initial throughput baseline.
    4.  Full parameter sharding first, because any multi-GPU run should avoid keeping complete replicas even when memory is sufficient.

    *Answer*: The correct answer is C. When the full model and training state already fit on one device, data parallelism is the natural first baseline because each GPU can run the local forward and backward pass without introducing the extra sequential dependencies of pipeline parallelism or the frequent collectives of tensor partitioning. An answer based on splitting layers or tensors solves a memory problem the scenario does not currently have. Sharding may still become useful later, but it is not the first throughput baseline when replication already fits.

    *Learning Objective*: Select data parallelism as the first multi-GPU baseline when memory already fits on each device and the main goal is throughput.

2.  **In distributed data parallel training with $N$ GPUs and a model with $P$ parameters whose gradients use $B_{\text{bytes}}$ bytes each, what is the number of bytes sent by each GPU during a Ring AllReduce?**

    1.  $2 \times \frac{N-1}{N} \times P \times B_{\text{bytes}}$, which approaches $2 P B_{\text{bytes}}$ as $N$ grows.
    2.  $N \times P \times B_{\text{bytes}}$, because each GPU must broadcast the full gradient to every other GPU.
    3.  $\frac{P \times B_{\text{bytes}}}{N^2}$, because the ring divides both the model and the communication quadratically.
    4.  Zero, because GPU replicas synchronize through shared CPU memory rather than explicit data movement.

    *Answer*: The correct answer is A. In a ring AllReduce, each GPU participates in a scatter-reduce phase and an all-gather phase, and the bytes sent per GPU total $2 \times \frac{N-1}{N} \times P \times B_{\text{bytes}}$. That expression tends toward $2 P B_{\text{bytes}}$ as $N$ becomes large, so the per-GPU sent volume stays bounded rather than growing linearly with the cluster size. The broadcast-style answer describes a different and less efficient mental model of synchronization.

    *Learning Objective*: Calculate the per-GPU bytes sent in Ring AllReduce and interpret its scaling with device count.

3.  **Explain what communication overhead is in distributed training, and analyze why adding more GPUs can lead to diminishing throughput returns.**

    *Answer*: Communication overhead is the time spent synchronizing gradients or exchanging partitioned activations and tensors instead of doing local model computation. As more GPUs are added, ideal compute work per device can fall, but communication latency, transfer volume, and incomplete overlap do not disappear, so synchronization becomes a larger fraction of each step. The practical consequence is that scaling efficiency drops once communication and coordination consume enough of the step that extra devices save less compute time than they add in communication cost.

    *Learning Objective*: Analyze how communication overhead limits scaling efficiency as distributed training spans more accelerators.

4.  **In pipeline model parallelism, partitioning a network linearly across $K$ stages without micro-batching (naive pipeline parallelism) achieves 100 percent GPU utilization because downstream devices can compute backward gradients while upstream devices run forward passes.**

    *Answer*: False. In naive pipeline parallelism without micro-batching, downstream devices must wait idle until upstream devices complete their forward passes, and upstream devices must wait idle until downstream devices compute backward loss gradients. This introduces massive idle pipeline bubbles where device utilization collapses to $\approx 1/K$. Practical pipeline parallelism systems (like GPipe and 1F1B in PipeDream) mitigate this by splitting batches into multiple small micro-batches and interleaving forward and backward passes to fill the pipeline.

    *Learning Objective*: Identify the pipeline bubble pathology of naive pipeline parallelism and explain how micro-batch schedules mitigate it.

5.  **Arrange the following engineering steps in the chapter’s preferred order for deciding whether to scale beyond one device, assuming the initial bounds do not already prove that single-device training is infeasible: (1) Re-evaluate whether memory or time limits still justify scaling. (2) Add distributed parallelism or sharding if the remaining limit still requires it. (3) Establish a single-device baseline and quantify the current bottleneck. (4) Apply relevant local optimizations such as mixed precision, prefetching, checkpointing, or accumulation.**

    *Answer*: The correct order is: (3) Establish a single-device baseline and quantify the current bottleneck, (4) Apply relevant local optimizations such as mixed precision, prefetching, checkpointing, or accumulation, (1) Re-evaluate whether memory or time limits still justify scaling, (2) Add distributed parallelism or sharding if the remaining limit still requires it. This order matters because the chapter’s scaling discipline uses baseline measurement first, then local fixes targeted to the observed constraint, then a new decision about whether a hard limit remains. Jumping straight to distributed scaling can add communication and operational complexity before the single-device bottleneck is even understood.

    *Learning Objective*: Sequence the chapter’s single-machine-first process for deciding when distributed scaling is actually justified.

1.  **A team scales a dense model from 7 billion to 20 billion parameters while keeping the same training-token budget, precision recipe, and optimizer structure. Under the chapter’s fallacies discussion, what is the most defensible conclusion?**

    1.  Validation accuracy must improve in proportion to parameter count because the larger model can represent more functions.
    2.  The run will necessarily move to CPU execution because 20B parameters cannot be trained on accelerators.
    3.  The larger model guarantees worse accuracy because fixed-token training always causes catastrophic interference at higher parameter counts.
    4.  The training-state and compute budgets rise substantially under the same dense-model accounting, but model quality is not guaranteed to improve because it still depends on data, optimization, and evaluation.

    *Answer*: The correct answer is D. Under the chapter’s dense-model accounting with fixed precision and optimizer assumptions, a larger parameter count clearly raises memory and leading FLOP requirements, so systems cost goes up in a predictable direction. But the scientific outcome is not guaranteed: keeping the same token budget does not prove either improvement or collapse in validation quality. The “must improve” answer mistakes model size for a universal quality guarantee, while the CPU answer invents a hardware consequence the chapter does not state.

    *Learning Objective*: Distinguish the predictable systems costs of scaling parameter count from the uncertain effect on final model quality.

2.  **Explain why directly transferring hyperparameters such as learning rate and weight decay from a batch-size 512 baseline to a batch-size 4,096 distributed run can cause training to underperform, even when raw GPU busy time stays above 90 percent.**

    *Answer*: An eightfold batch increase means eight times fewer parameter updates per fixed epoch, and it also changes the gradient statistics seen by the optimizer, so the old hyperparameters no longer operate in the same regime. High GPU busy time only shows that hardware is active; it does not prove that the optimizer is making equally effective progress per unit data. The practical response is to validate the learning-rate schedule, warmup, and target quality metric on the larger-batch run instead of assuming the small-batch recipe transfers unchanged.

    *Learning Objective*: Explain why batch-size scaling can invalidate a previously successful optimization recipe even when hardware utilization looks strong.

3.  **Which engineering mistake exemplifies the input-pipeline pitfall described in the chapter’s fallacies and pitfalls?**

    1.  Using BF16 mixed precision instead of FP16 on NVIDIA Ampere GPUs.
    2.  Spending weeks hand-tuning custom CUDA attention kernels to achieve 95% peak arithmetic throughput, only to discover in production that the GPU sits idle 50% of the time waiting for single-threaded Python CPU tokenization.
    3.  Setting `pin_memory=True` and `num_workers=8` in a PyTorch DataLoader.
    4.  Checkpointing activations every $\sqrt{N_L}$ layers to reduce peak memory.

    *Answer*: The correct answer is B. The chapter’s pitfall of optimizing kernels before profiling the input pipeline occurs when engineers focus exclusively on accelerator-side compute optimizations (such as custom CUDA kernels, mixed precision, or Tensor Core utilization) while neglecting end-to-end profiling. If the upstream data pipeline (CPU tokenization, disk I/O, or augmentation) is bottlenecked, the GPU will starve, rendering kernel-level speedups useless at the system level. BF16, DataLoader worker and pinned-memory settings, and checkpointing are candidate interventions whose value depends on the diagnosed constraint and validation results.

    *Learning Objective*: Recognize optimizing kernels before profiling the input pipeline as a major operational pitfall in training optimization.

4.  **A team proposes moving a single-GPU training job to a 16-GPU cluster to achieve a $16\times$ reduction in development cycle time. Explain two reasons why distributed training rarely delivers a linear $16\times$ improvement in developer velocity.**

    *Answer*: First, distributed execution adds communication and synchronization overhead, so throughput rarely scales linearly with GPU count even when the code is correct. Second, developer velocity depends on more than throughput: distributed jobs bring extra debugging, launch, checkpointing, and failure-handling overhead that can delay iteration even if step time improves. The practical consequence is that cluster scaling should be justified by measured end-to-end iteration gains, not by hardware count alone.

    *Learning Objective*: Evaluate why communication overhead and operational complexity both limit the developer-velocity gains of distributed training.
