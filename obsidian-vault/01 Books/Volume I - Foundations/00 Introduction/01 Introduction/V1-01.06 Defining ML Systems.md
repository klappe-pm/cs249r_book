# V1-01.06 Defining ML Systems

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01 Introduction|V1-01 Introduction]]

^sec-introduction-defining-ml-systems-d4af

Absorbing computational growth takes a working system, not only a trained model. Return to the email spam filter introduced in [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.03 From Code-Defined Logic to Data-Defined Behavior#^sec-introduction-datacentric-paradigm-shift-4eca|section 1.2]]: in a notebook, it is a classifier that maps message text to a spam probability, but in production it must process global email traffic measured in hundreds of billions of messages per day ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-statista2024email|Statista Research Department 2024]]). At that scale, the classifier is only one component inside an end-to-end operational pipeline that must continuously ingest new examples, retrain as attack tactics evolve, and classify incoming mail within strict delivery latency budgets.

The challenge begins with data. The filter is trained on labeled examples and needs updated training data and periodic retraining as spam tactics change. It is also an algorithmic problem, because the model must generalize from those examples to messages it has never seen before. Two measures judge that generalization. Precision measures the fraction of flagged messages that are actually spam; recall measures the fraction of all spam messages that the filter catches. Flagging more messages may catch more spam while also hiding legitimate mail, so the system must evaluate both consequences. Finally, it is an infrastructure problem. Providers must handle incoming traffic, store and update models, and return predictions within their delivery latency budget. The classifier is therefore only one component of an evolving data, software, and hardware system.

When a new phishing template appears, the data layer must capture representative messages, the algorithm must learn to separate attacks from legitimate mail, and the infrastructure must deploy and serve the updated model. Any layer can fail while the others continue working. The full chain from measurement through learning to execution is therefore the right unit of analysis.

**Definition 1.1: Machine learning systems**

***Machine learning systems*** combine models that learn from data with the software and hardware needed to train, deploy, and maintain them. Their performance depends jointly on data quality, algorithm choice, and machine capacity.

1.  **Significance**: Requirements are end to end, so a failure in any layer changes the user-visible result even while the other layers operate correctly.
2.  **Distinction**: The system includes every path an input travels, not only the model. A feature computed one way in training and another in serving changes what the system predicts even when the model and its weights are identical.
3.  **Common pitfall**: The model is not the system, as the small share of model code in Sculley’s account of production systems already showed. Data pipelines, feature transformations, serving infrastructure, monitoring, and feedback loops surround the learned parameters and often dominate the engineering burden, and the costliest failures tend to arise there too, at interfaces that no single component’s tests exercise ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-sculley2015hidden|Sculley et al. 2015]]).

The definition exposes three diagnostic axes: the data that describes the task, the algorithm that turns examples into behavior, and the machine, the infrastructure that executes that behavior within the operating budget. The same user-visible symptom can originate in any of the three. Treating every miss as a model problem risks improving the wrong component. The D·A·M taxonomy separates these causes for diagnosis.

**Definition 1.2: D·A·M taxonomy**

***D·A·M taxonomy*** is a diagnostic framework for examining machine learning system bottlenecks along three axes. Data determines what examples and bytes the system must process, Algorithm determines the model structure and work required to learn or predict, and Machine determines the hardware capacity available to execute that work. The goal is to identify which axis is the limiting constraint.

1.  **Significance**: The diagnostic power is concrete even before detailed hardware arithmetic enters the story. If the spam filter misses a new phishing campaign because the training set never contained that tactic, the limiting axis is Data. If the training examples are adequate but the model cannot express the pattern, the limiting axis is Algorithm. If both are adequate but the service cannot classify messages quickly enough during a traffic spike, the limiting axis is Machine. Quantitative diagnosis begins by asking which axis is limiting the system.
2.  **Distinction**: The D·A·M taxonomy connects predictive quality to physical execution. Algorithm choice shapes both the data needed to learn useful behavior and the machine resources needed to run it. Those requirements depend on the task and training procedure, so model size alone does not determine either generalization or runtime.
3.  **Common pitfall**: A frequent misconception is that the three axes are independent. Changing from a simple classifier to a larger model can require more memory, different serving infrastructure, and a broader data distribution. Because changing one of Data, Algorithm, and Machine can change the requirements imposed on the other two, every edge of the triangle in [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.06 Defining ML Systems#^fig-dam-axis-triad-intro|figure 3]] points both ways.

Each of the three explanations calls for different evidence. The data hypothesis sends the engineer to coverage, labels, and distribution shift. The algorithm hypothesis sends the engineer to error slices (errors grouped by input type), model capacity (how complex a pattern the model can represent), and the learning objective. The machine hypothesis sends the engineer to latency, throughput, memory, and utilization. These investigations are not interchangeable. Faster hardware cannot supply examples that were never collected, while a larger dataset cannot repair a serving path that misses its deadline because memory is saturated.

The relevant constraint is the one whose relaxation improves the end-to-end result. This idea of a **limiting constraint**, used informally in the history of [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.04 The Evolution of AI Bottlenecks#^sec-introduction-ai-paradigm-evolution-ae2b|section 1.3]], prevents teams from optimizing the most visible component instead of the component that governs the outcome. The purpose of D·A·M is therefore operational: it identifies the next hypothesis to test and the class of intervention capable of changing system behavior. The diagnosis is provisional. Once an intervention relaxes one limit, the system must be measured again because a different axis may now set the limit, the same bottleneck migration the history traced across eras. D·A·M is a loop, not a one-time label.

Figure 3: **The D·A·M Axis Triad**: Each vertex is one diagnostic axis, and each double-headed edge is a path along which a relaxed bottleneck can reappear on the neighboring axis.

^fig-dam-axis-triad-intro

An operational diagnosis earns confidence only when an intervention validates it, that is, when relaxing the identified constraint improves full-system behavior. Resolving one bottleneck frequently migrates the limiting constraint across an adjacent edge of [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.06 Defining ML Systems#^fig-dam-axis-triad-intro|figure 3]], so interventions rarely end the optimization process. Upgrading to faster accelerators (Machine) leaves execution units idling if storage I/O cannot stream input batches quickly enough (Data). Conversely, expanding dataset volume (Data) exposes model architectures that lack the expressive capacity to absorb new patterns (Algorithm). Scaling model capacity to close that gap (Algorithm) soon exceeds accelerator memory, triggering out-of-memory faults or expensive paging across the PCIe bus (Machine). Engineering an ML system therefore requires identifying the current limiting constraint while anticipating where the bottleneck will migrate once that constraint is relaxed.

While the triad separates the three axes to simplify initial diagnosis, practical systems operate at their boundaries. Data formats govern memory traffic, model architectures dictate hardware functional unit utilization, and deployment budgets reshape both data representation and algorithmic design. [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.06 Defining ML Systems#^fig-ai-triad|Figure 4]] partitions these interfaces into a three-set Venn diagram whose pairwise overlaps each pose one question: what the system can learn from ($\text{D} \cap \text{A}$), how information moves ($\text{D} \cap \text{M}$), and how computation executes efficiently ($\text{A} \cap \text{M}$). Each overlap also lists, in smaller type, techniques such as mixed precision and active learning together with the later chapters that develop them, while this chapter uses only the three questions.

![[90 Assets/Volume I/01 Introduction/Generated Figure 46944d28c6.svg]]

Figure 4: **The D·A·M Intersection Landscape**: Each circle lists the concerns that belong to one axis, and each pairwise overlap is titled with the question that axis pair must answer jointly. The central region, where all three circles overlap, is labeled ML systems engineering.

^fig-ai-triad

At the center, all three questions must be answered together. Data selection and training determine which examples help the model learn useful behavior. Data engineering and hardware acceleration deliver that information to the machine at speed. Frameworks and execution techniques turn the model’s computations into efficient work on that silicon. Pruning a model (Algorithm), which removes parameters that contribute little to its predictions, alters its memory footprint and how much of it stays in fast on-chip memory (Machine). Compressing input features can likewise reduce transfers while adding preparation work (Data). These changes must be evaluated across the interfaces, because a local improvement may leave the end-to-end result unchanged.

↪ How pruning shrinks a model’s memory footprint, and why its effect on speed depends on the sparsity pattern the hardware can exploit, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/10 Model Compression/V1-10.03 Structural Optimization Changing What the Model Computes#^sec-model-compression-pruning-d1cb|Pruning]]**.

**Self-Check: Question**

1.  An ML engineering team trains a 70-billion-parameter language model. When profiling the distributed cluster, they notice that accelerator compute engines remain idle for 45% of execution time waiting for batch tensors to be loaded from remote object storage over the network. Along which D·A·M axis does the primary limiting constraint lie, and which intersection represents the appropriate optimization space?

    1.  Machine axis; $\text{Algorithm} \cap \text{Machine}$ (mixed precision quantization and kernel fusion)
    2.  Algorithm axis; $\text{Data} \cap \text{Algorithm}$ (curriculum learning and active data selection)
    3.  Data axis; $\text{Data} \cap \text{Machine}$ (I/O pipelining, prefetching, and storage memory hierarchy)
    4.  Workload axis; $\text{Data} \cap \text{Algorithm} \cap \text{Machine}$ (reinforcement learning from human feedback)

2.  Explain what the concept of a ‘limiting constraint’ means in the D·A·M framework, and describe the risk of optimizing an axis that is not limiting.

3.  In the D·A·M intersection landscape, the intersection between Algorithm and Machine ($\text{A} \cap \text{M}$) addresses the core question of ‘How to \_\_\_\_’, focusing on how the model’s mathematical work is mapped onto hardware execution and data movement efficiently.
