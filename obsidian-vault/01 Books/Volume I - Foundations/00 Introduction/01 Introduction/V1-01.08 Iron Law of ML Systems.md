# V1-01.08 Iron Law of ML Systems

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01 Introduction|V1-01 Introduction]]

^sec-introduction-iron-law-ml-systems-c32a

Computational scale has a physical cost, and it shows up as two familiar failures. A training job stalls when storage cannot feed an accelerator; an inference path misses its deadline when model state moves too slowly through memory or across the network. Their symptoms differ, but both are governed by how the three D·A·M axes combine to consume wall-clock time. Across Data (D), Algorithm (A), and Machine (M), every ML task completes by processing a set of samples (examples in vision or tabular workloads, tokens in language models) through an algorithm’s operations on hardware. By dimensional cancellation, total execution time ${T}$ (seconds) is the product of these three factors ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|equation 2]]):

$$
{T} = \underbrace{\left(\frac{\text{Samples}}{\text{Task}}\right)}_{\text{Data}} \times \underbrace{\left(\frac{\text{FLOPs}}{\text{Sample}}\right)}_{\text{Algorithm}} \times \underbrace{\left(\frac{\text{Seconds}}{\text{FLOP}}\right)}_{\text{Machine}} \tag{2}
$$

^eq-intro-dam-iron-law

The same equation governs both training and inference because only the definition of the task and the scale of each factor change. The product of the first two factors sets the total arithmetic work ${O}$ (FLOPs), while the third factor ($\text{Seconds/FLOP}$) is the realized time the machine takes per operation:

- **Training**: A task is a training run (or an optimization step). Here $\text{Samples/Task}$ is the corpus token budget ${D}$ (billions to trillions of tokens), and $\text{FLOPs/Sample}$ spans the forward and backward passes ($\approx 6{P}$ FLOPs per token for a dense language model, giving ${O} \approx 6{P}{D}$). Because large training batches (groups of examples processed together) reuse model weights across thousands of tokens per step, the machine amortizes memory transfers and dispatch overhead, keeping realized $\text{Seconds/FLOP}$ low and close to the best the hardware can deliver.
- **Inference**: A task is serving a request or generating a response. Here $\text{Samples/Task}$ shrinks to a small request batch (${B}$) or a stream of generated tokens, and $\text{FLOPs/Sample}$ covers only the forward pass ($\approx 2{P}$ FLOPs per token). With far fewer samples per invocation to amortize weight reads and orchestration, realized $\text{Seconds/FLOP}$ rises sharply as memory bandwidth and fixed latency overtake arithmetic.

A real machine does not achieve the datasheet minimum of $1/{R_{\text{peak}}}$ seconds per FLOP because physical execution requires moving data across memory and interconnect buses, driving arithmetic units at some realized utilization, and paying fixed control overheads. Assuming these three physical costs occur sequentially, the **iron law of ML systems** unpacks total execution time ${T}$ (seconds) into their sum ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 3]]):

$$
{T} = \underbrace{\frac{{D_{\text{vol}}}}{{\text{BW}}}}_{\text{Memory Time}} + \underbrace{\frac{{O}}{{R_{\text{peak}}} \cdot {\eta_{\text{hw}}}}}_{\text{Compute Time}} + \underbrace{{L_{\text{lat}}}}_{\text{Latency Overhead}} \tag{3}
$$

^eq-intro-iron-law

Dividing that sum by the operations performed, ${O}$, gives the realized $\text{Seconds/FLOP}$ of the Machine factor in [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|equation 2]], so all three terms set its value. The product and the sum are therefore two forms of the same iron law, one factoring the work and the other unpacking the Machine factor. A workload whose memory term is large relative to its operation count has a large realized $\text{Seconds/FLOP}$, however fast its arithmetic units are.

Together, [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|equation 2]] and [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 3]] account for the physical-execution half of the dual mandate introduced in [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.02 The AI Systems Moment#^sec-introduction-ai-moment-37f1|section 1.1]]:

1.  **The memory term** $({D_{\text{vol}}}/{\text{BW}})$ represents the physical cost of moving bits. ${D_{\text{vol}}}$ is the volume of data moved (bytes), and ${\text{BW}}$ is the memory or network bandwidth (bytes/s). Whether loading terabytes from cloud storage or fetching weights from high-bandwidth memory (HBM), the stacked dynamic random-access memory (DRAM) packaged beside an accelerator, performance is often limited by I/O physics. **[[01 Books/Volume I - Foundations/01 Foundations/04 Data Engineering/V1-04 Data Engineering#^sec-data-engineering|Data Engineering]]** develops the storage side of this term, and **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** the memory hierarchy.
2.  **The compute term** $({O}/({R_{\text{peak}}} \cdot {\eta_{\text{hw}}}))$ represents the cost of arithmetic. ${O}$ is the number of floating-point operations (FLOPs) set by the product of $\text{Samples/Task}$ and $\text{FLOPs/Sample}$. ${R_{\text{peak}}}$ is the hardware’s theoretical peak throughput (FLOP/s). ${\eta_{\text{hw}}}$ is dimensionless realized compute utilization $(0 \le {\eta_{\text{hw}}} \le 1)$. **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08 Model Training#^sec-model-training|Model Training]]** and **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** develop this term.
3.  **The latency term** $({L_{\text{lat}}})$ represents orchestration, networking, and serialization overhead (seconds), treated as fixed for the modeled execution. Engineering changes can reduce this overhead, which can dominate small, latency-critical requests where little data moves and little arithmetic runs. **[[01 Books/Volume I - Foundations/04 Deployment/13 Model Serving/V1-13 Model Serving#^sec-model-serving|Model Serving]]** develops this term.

Consider a hypothetical task that spends 2 seconds moving data, 8 seconds computing, and 1 second on overhead. Its total is 11 seconds. Doubling the arithmetic rate reduces computation to 4 seconds, but leaves movement and overhead unchanged. The task now takes 7 seconds, rather than half its original time. A faster component helps only through the portion of the time budget it changes.

Data enters [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|equation 2]] and [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 3]] in two distinct ways: logical samples versus physical bytes. In [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|equation 2]], the Data factor counts how many examples or tokens the task processes (such as the dataset size ${D}$ in the $6 \cdot {P} \cdot {D}$ training estimate), which multiplies $\text{FLOPs/Sample}$ to fix total arithmetic work ${O}$. In [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 3]], by contrast, ${D_{\text{vol}}}$ counts the physical bytes moved across a memory or interconnect bus, including model weights (${P}$) and intermediate results alongside the raw inputs. A language model answering a single request illustrates the difference. It produces its reply one token at a time, so each step processes one token ($\text{Samples/Task} = 1$), yet each step must read every model weight from memory, so ${D_{\text{vol}}}$ spans gigabytes.

**Systems Perspective 1.1: The iron law analogy**

The name “iron law” follows the processor performance equation of Patterson and Hennessy ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-patterson2017hardware|2017]]), $\text{Time/Program} = (\text{Instructions/Program}) \times (\text{Cycles/Instruction}) \times (\text{Seconds/Cycle})$. [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|Equation 2]] is the direct ML counterpart: the Data ($\text{Samples/Task}$) and Algorithm ($\text{FLOPs/Sample}$) factors multiply to set total operations ${O}$ just as program path length and instruction set determine instruction count. The Machine factor ($\text{Seconds/FLOP}$) mirrors cycles per instruction times clock period. Reducing $\text{FLOPs/Sample}$ (for example, by removing individual weights scattered across the model) can still slow down execution if the resulting irregular memory accesses inflate $\text{Seconds/FLOP}$, just as complex CPU instructions that cut instruction count can lose performance by inflating cycles per instruction. [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|Equation 3]] then takes the same second step that computer architects take when decomposing processor time into compute cycles, memory-stall cycles, and pipeline overhead.

The additive form assumes sequential execution. When movement and computation overlap, the critical-path lower bound replaces the sum in [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law-pipelined|equation 4]]:

$$
{T_{\text{pipelined}}}\ge \max\left(\frac{{D_{\text{vol}}}}{{\text{BW}}}, \frac{{O}}{{R_{\text{peak}}} \cdot {\eta_{\text{hw}}}}\right) + {L_{\text{lat}}} \tag{4}
$$

 This max-based formulation reflects hardware that transfers the next block of data while computing on the current one, so the slower of the two stages hides the faster. Equality requires ideal overlap and assumes that ${L_{\text{lat}}}$ remains outside the overlapped phases.

^eq-intro-iron-law-pipelined

Even as a sum, the iron law identifies which physical constraint dominates before any optimization begins. Amdahl’s law ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-amdahl1967|Amdahl 1967]]) plays the same role for speedups. Accelerating only part of a task leaves the untouched remainder in place, and that remainder caps the whole task’s speedup however fast the accelerated part becomes. **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11 Hardware Acceleration#^sec-hardware-acceleration|Hardware Acceleration]]** states that cap as a bound on overall speedup (**[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^eq-amdahl|equation 11.1]]**). **[[05 Reference/Volume I - Foundations/V1 The D·A·M Taxonomy#^sec-appdx-dam-taxonomy-dam-coordination-sum-max-92bb|From sum to max]]** presents the refined treatment, including pipelining and overlap techniques that transform the additive model into the max-based formulation used in practice.

Whether the memory term or the compute term dominates depends on the workload’s arithmetic intensity $({I} = {O}/{D_{\text{vol}}})$, the operations it performs per byte it moves. A workload that performs few operations per byte, relative to what the machine’s arithmetic units could process in the time each byte takes to arrive, waits on memory; one that performs many waits on computation. Improving the smaller of the two terms yields a limited end-to-end gain, while overhead $({L_{\text{lat}}})$ sits outside this comparison and can dominate small requests. The single-accelerator estimate below describes a workload that waits on memory, whose movement term outweighs its compute term.

↪ The roofline model, which bounds attainable throughput by arithmetic intensity and locates the ridge point, is developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.07 Performance Bounds#^sec-hardware-acceleration-roofline-model-42ff|Performance Bounds]]**.

**Napkin Math 1.1: Estimating one local execution**

**Problem**: A hypothetical workload on one accelerator moves 2 GB at 100 GB/s, performs 1 GFLOP at an effective arithmetic rate of 100 GFLOP/s, and incurs 5 ms of fixed overhead. Movement precedes computation. What execution time does the iron law predict, and which rate should be improved first?

**Math**: Dividing bytes by bytes/s gives a movement time of 20 ms. Dividing FLOPs by FLOP/s gives a compute time of 10 ms; the supplied effective rate already includes ${\eta_{\text{hw}}}$, so it must not be multiplied by efficiency again. Adding these durations and overhead gives 35 ms. Movement is the largest term.

**Result**: Raising bandwidth to 200 GB/s reduces movement to 10 ms and total sequential time to 25 ms. Arithmetic and overhead remain unchanged, so doubling bandwidth does not halve the total.

**Systems insight**: If movement and computation could instead overlap ideally, with overhead still outside both phases, the lower bound would be 25 ms before the upgrade and 15 ms afterward. The upgrade balances the two stages; further bandwidth increases alone would leave that ideal bound unchanged. Whether the sum or the bound describes a measured run depends on its execution schedule.

A larger training estimate, for GPT-3, returns to the product form of [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-dam-iron-law|equation 2]] and uses the symbol ${\eta_{\text{hw}}}$ in a wider sense. In [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 3]], ${\eta_{\text{hw}}}$ measures only how busy the arithmetic units are, and memory stalls and overhead have their own terms. The GPT-3 estimate has no separate memory or overhead term, so its ${\eta_{\text{hw}}}$ is an end-to-end factor that absorbs memory stalls, communication among accelerators, and every other non-arithmetic delay. With that wider factor, the realized machine factor across ${N_{\text{GPU}}}$ parallel accelerators is $({N_{\text{GPU}}} \cdot {R_{\text{peak}}} \cdot {\eta_{\text{hw}}})^{-1}$ seconds per FLOP. A multi-machine cluster of that kind lies outside this book’s single-machine scope; the estimate appears here only to show the scale the compute term can reach.

↪ The training-time form of the iron law, which converts an operation count into days of training at a realized utilization, is developed in **[[01 Books/Volume I - Foundations/02 Development/08 Model Training/V1-08.03 Training-Time Law#^sec-model-training-iron-law-training-performance-a53f|Training-Time Law]]**.

**Napkin Math 1.2: Training GPT-3**

**Problem**: How long would a GPT-3-class model take to train on a hypothetical modern cluster of 1,024 accelerators? This reference cluster uses A100-class accelerators, a generation newer than the V100 GPUs of the original run estimated earlier at roughly 405 V100 GPU-years. The result therefore shows what the same work could cost on newer hardware at the utilization assumed below. The original run achieved lower utilization, so part of the speedup comes from that assumption rather than from the hardware.

**Given**:

- **Operations $({O})$**: $\approx 3.14 \times 10^{23}\ \text{FLOPs}$ (the product of the Data factor, 300 billion tokens, and the Algorithm factor, $6{P}$ FLOPs/token for 175 billion parameters)
- **Peak Rate $({R_{\text{peak}}})$**: 312 TFLOP/s
- **Efficiency $({\eta_{\text{hw}}})$**: ≈ 45 percent (an end-to-end factor that absorbs communication and memory stalls, not the compute-only utilization of [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-intro-iron-law|equation 3]]; an assumed planning value for large-scale distributed training, where those delays keep realized throughput well below peak)
- **Accelerator Count $({N_{\text{GPU}}})$**: 1,024 accelerators

**Math**:

Assume that the training workload reuses data sufficiently to make arithmetic dominant and overlaps data loading with computation. Under this compute-dominated approximation, the remaining communication and memory stalls are included in the effective end-to-end utilization ${\eta_{\text{hw}}}$ across ${N_{\text{GPU}}}$ parallel accelerators, and the training time ${T_{\text{train}}}$ follows:

- ${T_{\text{train}}} \approx \frac{{O}}{{N_{\text{GPU}}} \cdot {R_{\text{peak}}} \cdot {\eta_{\text{hw}}}}$ $\approx \frac{3.14 \times 10^{23}}{1024 \times 312 \times 10^{12} \times 0.45}$ $\approx 25\ \text{days}$

**Result**: 25 days.

**Systems insight**: If hardware utilization $({\eta_{\text{hw}}})$ improves from 45 percent to 60 percent through better scheduling and more efficient execution, training time drops to 19 days, saving 6 days of expensive compute time.

Every term of the iron law is measured in seconds, but time is not the only physical constraint. For battery-powered edge devices and warehouse-scale accelerator clusters alike, energy dissipation and thermal limits often cap the system before throughput limits are reached. Moving bits across the memory hierarchy also costs **data-movement energy**, which parallels the delay of the memory term.

↪ The term-by-term unit check showing that every iron-law term is measured in seconds, and its use as a test for any performance equation, are collected for reference in **[[05 Reference/Volume I - Foundations/V1 Machine Foundations#^sec-appdx-machine-foundations-dimensional-analysis-76b3|Dimensional analysis]]**.

Let ${D_{\text{vol}}}$ be the total data volume moved (bytes), ${E_{\text{move}}}$ the energy per byte moved, ${O}$ the total operation count, and ${E_{\text{compute}}}$ the energy per operation. [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^eq-energy-cost|Equation 5]] formalizes this relationship, following the hardware-energy observation that data movement can dominate arithmetic energy ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-horowitz2014|Horowitz 2014]]):

$$
{E_{\text{total}}} \approx \underbrace{ {D_{\text{vol}}} \times {E_{\text{move}}} }_{\text{Movement Term}} + \underbrace{ {O} \times {E_{\text{compute}}} }_{\text{Compute Term}} \tag{5}
$$

^eq-energy-cost

![[90 Assets/Volume I/01 Introduction/Introduction Energy Hierarchy c5c1ab252d.svg]]

*Vertical ladder of three orange bars on a log scale, longest at top: DRAM (Dynamic Random-Access Memory) 160 pJ towers far above FP16 1.1 pJ and INT8 (8-bit integer) 0.2 pJ, showing data movement costs orders of magnitude more energy than arithmetic.*

*Moving a byte from DRAM costs about 145 times the energy of a 16-bit floating-point multiply, so data movement, not arithmetic, dominates the energy cost.*

The energy comparison depends on the transfer size and arithmetic operation being counted. Under the energy constants used in this text, moving one byte from off-chip DRAM consumes roughly 145× the energy of a 16-bit floating-point (FP16) multiply and 800× that of an INT8 (8-bit integer) multiply ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-horowitz2014|Horowitz 2014]]). Whether movement dominates a complete workload also depends on the number and width of transfers relative to its operation count. The physical reason for the per-access gap is that data movement requires charging and discharging wires over longer distances, while arithmetic occurs locally within a processing unit’s circuits. Minimizing avoidable data movement $({D_{\text{vol}}})$ can therefore improve both speed and energy efficiency.

↪ The energy ladder from on-chip arithmetic to off-chip memory, and why its gap makes data movement a primary target for accelerator design, are developed in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.03 Hardware Specialization#^sec-hardware-acceleration-machine-learning-hardware-specialization-09c5|Machine learning hardware specialization]]**.

### Lighthouse Models Put the Iron Law into Practice

^sec-introduction-lighthouse-models-9b1c

Each term of the iron law suggests an engineering intervention. The memory term can be reduced by moving fewer bytes or increasing effective bandwidth. The compute term can be reduced by performing fewer operations or using arithmetic units more effectively. The latency term calls for reducing orchestration and communication overhead. The equation alone does not say which intervention a system needs; that depends on its measured workload and whether the required data fits in memory.

Concrete workloads answer that question. Five recurring **lighthouse models** serve as diagnostic probes for the iron law throughout this book; later chapters explain the model structures and execution mechanisms behind their constraints. Each is a distinct stress case under the workload conditions stated for it:

- **Image classification (ResNet-50)** ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-he2016|He et al. 2016]]) probes compute throughput. With sufficient reuse of learned filters across image positions and batched inputs, the arithmetic term (${O}/({R_{\text{peak}}} \cdot {\eta_{\text{hw}}})$) can dominate execution time.
- **Text generation (GPT-2/Llama)** probes memory bandwidth, with GPT-2 ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-radford2019language|Radford et al. 2019]]) anchoring the lighthouse and Llama ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-touvron2023llama|Touvron et al. 2023]]) representing its larger successors. Generating text one token at a time for a single request offers little weight reuse per token, so fetching weights from memory (${D_{\text{vol}}}/{\text{BW}}$) can become the limiting constraint.
- **Recommendation (DLRM)**, the Deep Learning Recommendation Model ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-naumov2019deep|Naumov et al. 2019]]), probes memory capacity, which determines whether the model can run at all. Embedding tables store numerical vectors for user and item IDs. Large tables can reach about a hundred gigabytes in reference models ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-naumov2019deep|Naumov et al. 2019]]), and terabytes in production ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-mudigere2022software|Mudigere et al. 2022]]), exceeding single-accelerator device memory.
- **Mobile vision (MobileNetV2)** ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-sandler2018|Sandler et al. 2018]]) probes compute throughput within a power envelope. Its efficient operators cut arithmetic far enough that a phone-class processor can classify frames in real time while sharing a battery and thermal budget with other applications.
- **Keyword spotting (KWS)** probes the power envelope, because an always-on microcontroller[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.16 Footnotes#^fn21|²¹]] must listen continuously for a wake word within a milliwatt budget and kilobytes of memory ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-zhang2017hello|Zhang et al. 2017]]).

These five are deliberately not the newest models. Each marks a point where the field turned and isolates one limiting constraint in its cleanest form. ResNet-50 made deep convolutional training on accelerators routine and became a reference workload of the MLPerf training benchmark ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-mattson2020mlperf|Mattson et al. 2020]]). GPT-2 showed that scaling a decoder-only language model changes what it can do. DLRM represents the recommendation models that accounted for most AI inference cycles in Facebook’s data centers when it was introduced ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-gupta2020architectural|Gupta et al. 2020]]). MobileNetV2 showed that careful operator design could bring accurate vision to phone-class processors ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-sandler2018|Sandler et al. 2018]]), and keyword spotting showed that useful inference could run continuously on a microcontroller ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-zhang2017hello|Zhang et al. 2017]]). Later models grow in scale, but the same terms of the iron law govern them, so the analysis in this book should transfer to models that do not yet exist.

The iron law makes these differences actionable under the stated workload conditions. Raising peak compute ${R_{\text{peak}}}$ helps convolutions when arithmetic dominates, while increasing memory bandwidth ${\text{BW}}$ helps generation when weight transfers dominate. Batch size, reuse, and serving patterns can change that diagnosis, so the bottleneck belongs to the workload on a particular machine rather than to the model name alone. For that reason, [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^tbl-lighthouse-examples|table 4]] identifies each lighthouse by the regime it probes.

The lighthouse models supply the book’s recurring workloads; the deployment paradigms described later in this chapter supply the operating envelopes those workloads must fit. The iron law estimates the execution time of one run on one machine, but over the past decade the training runs themselves grew faster than hardware improvements alone could accommodate, which made efficiency a central concern.

**Self-Check: Question**

1.  In the Iron Law of ML Systems, $T = \frac{D_{\text{vol}}}{\text{BW}} + \frac{O}{R_{\text{peak}} \cdot \eta_{\text{hw}}} + L_{\text{lat}}$, how do the terms differ when analyzing small-batch autoregressive LLM token decode versus large-batch ResNet-50 image inference?

    1.  LLM decode is dominated by the latency term $L_{\text{lat}}$, while ResNet-50 is dominated by the data movement term $D_{\text{vol}}/\text{BW}$.
    2.  Both workloads are dominated strictly by the compute term $\frac{O}{R_{\text{peak}} \cdot \eta_{\text{hw}}}$, making memory bandwidth irrelevant.
    3.  ResNet-50 is memory-capacity bound by embedding tables, while LLM decode is bound by network serialization overhead.
    4.  Small-batch LLM decode is bound by the data movement term ($D_{\text{vol}}/\text{BW}$) because billions of weights and cached context must be fetched from memory for every single token generated, whereas batched ResNet-50 reuses weight parameters across many inputs and spatial locations, making the compute term ($\frac{O}{R_{\text{peak}} \cdot \eta_{\text{hw}}}$) dominant.
