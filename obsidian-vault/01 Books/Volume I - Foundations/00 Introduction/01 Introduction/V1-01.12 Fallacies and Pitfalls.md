# V1-01.12 Fallacies and Pitfalls

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01 Introduction|V1-01 Introduction]]

^sec-introduction-fallacies-pitfalls-230d

Every chapter in this book closes with a section like this one. A **fallacy** is a belief that sounds right but is false, a **pitfall** is a practice that is easy to fall into and costly to recover from, and each entry corrects the mistake with evidence from the chapter.

A passing code test, a high held-out score, and a faster inference stage each provide useful evidence, but none alone establishes that an ML system meets its requirements. Mistaking code-level checks for validation of learned behavior overlooks the verification gap and silent degradation. Treating a held-out score as proof of deployment readiness ignores distribution shift and execution budgets. Extrapolating a component speedup to the whole system overlooks the untouched costs captured by Amdahl’s law. Each of these errors applies evidence beyond the conditions that support it.

**Fallacy**: *Better algorithms automatically produce better systems.*

A more accurate spam classifier can still be a worse production choice if it needs too much memory or cannot classify incoming messages within the delivery budget. The iron law ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.08 Iron Law of ML Systems#^sec-introduction-iron-law-ml-systems-c32a|section 1.7]]) explains why algorithmic quality alone does not settle that decision. Model selection must maximize task quality subject to latency, memory, energy, cost, and reliability requirements. A simpler model supported by representative data and reliable infrastructure can meet those requirements more effectively than a sophisticated model whose surrounding system is inadequate.

**Pitfall**: *Treating ML systems as traditional software that happens to include a model.*

Established testing and deployment practices remain necessary for ML systems, but code-level checks alone cannot validate learned behavior ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.07 When ML Systems Fail Silently#^sec-introduction-ml-vs-traditional-software-e19a|section 1.6]]). In the driver-assistance example, pedestrian recall can fall from 95 to 85 percent while the accelerator keeps its full frame rate and raises no fault. ML systems additionally require outcome monitoring to detect declining predictive quality, with enough labeled samples from each user group to reveal a drop in that group. Teams deploying ML with only continuous integration and continuous deployment (CI/CD) pipelines risk silent failures, in which test suites and health checks report green while user-facing prediction quality degrades.

**Fallacy**: *High accuracy on benchmark datasets indicates production readiness.*

A benchmark score describes performance on a stated dataset under an evaluation protocol; it does not establish deployment readiness ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.10 AI Engineering as a Discipline#^sec-introduction-deployment-spectrum-a38c|section 1.9.2]]). The ILSVRC validation set holds 50,000 images, while the number of possible inputs has 362,508 digits ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.03 From Code-Defined Logic to Data-Defined Behavior#^sec-introduction-datacentric-paradigm-shift-4eca|section 1.2]]), so even a perfect score is evidence about a sample, not proof about the population. A sentiment model may lose accuracy when users employ slang or context absent from the test set. Deployment also introduces resource requirements: mobile memory and latency limits may make running several models together (an ensemble) impractical, while network round trips can consume the response budget. Production validation must cover the intended operating conditions, relevant subgroups, resource use, and monitoring needed to detect change.

**Pitfall**: *Optimizing individual components without considering system interactions.*

Amdahl’s law, which holds that the untouched share of a task caps the speedup of the whole, explains why improving inference alone may produce a small end-to-end gain. Consider a team that reduces model inference from 45 ms to 15 ms, expecting proportional improvement. Preprocessing still consumes 60 ms and postprocessing adds 25 ms, so total latency drops only from 130 ms to 100 ms. That is a 23 percent improvement in total latency rather than the 67 percent improvement of the inference stage alone. Most of the request path was untouched. Measuring the whole request prevents a component speedup from being mistaken for a system speedup. The bound in **[[01 Books/Volume I - Foundations/03 Optimization/11 Hardware Acceleration/V1-11.02 Anatomy of an Accelerator#^eq-amdahl|equation 11.1]]** computes the overall speedup from the share of time a component occupies and its local gain.

**Fallacy**: *ML systems can be deployed once and left to run indefinitely.*

Deployed ML systems cannot assume static performance over time: environmental distribution shifts can degrade a frozen model even when underlying execution code remains untouched. In this illustrative scenario, a recommendation system deployed at 85 percent accuracy drops to 80.2 percent within 6 months as purchasing patterns shift, losing 4.8 percentage points without any code changes. The ML lifecycle ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.10 AI Engineering as a Discipline#^sec-introduction-ml-system-lifecycle-849f|section 1.9.1]]) therefore treats outcome monitoring and evidence-based retraining as operational requirements. Without continuous monitoring, systems can appear healthy while prediction quality silently erodes.

**Pitfall**: *Assuming that ML expertise alone is sufficient for ML systems engineering.*

Production ML ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.10 AI Engineering as a Discipline#^sec-introduction-deployment-spectrum-a38c|section 1.9.2]]) requires expertise across algorithms, software, systems, and operations. A team with strong ML skills can still miss throughput targets if storage layout or serving infrastructure is inadequate. Conversely, infrastructure built without attention to model inputs can introduce preprocessing defects that degrade predictions. Deployment case studies show the need for coordinated attention to data, models, infrastructure, and organizational workflow ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-paleyes2022|Paleyes et al. 2022]]). Failures can arise at the boundaries, where one team’s assumptions become another team’s inputs.

**Self-Check: Question**

1.  An inference pipeline consists of three sequential stages: data preprocessing taking 60 ms, model inference taking 45 ms, and output postprocessing taking 25 ms (total latency = 130 ms). An engineering team applies kernel fusion and quantization to achieve a $3\times$ speedup on the model inference stage alone (reducing it from 45 ms to 15 ms). What is the resulting end-to-end pipeline latency and approximate overall system speedup, and what principle does this demonstrate?

    1.  New latency is 100 ms (an overall speedup of $\approx 1.30\times$, or a 23% reduction in execution time), illustrating Amdahl’s Law that component-level speedups yield only marginal end-to-end gains when non-optimized stages dominate.
    2.  New latency is 43.3 ms (a $3.0\times$ overall speedup, or 67% reduction), illustrating linear speedup scaling across modular microservices.
    3.  New latency is 15 ms, illustrating that hardware acceleration bypasses pre- and post-processing stages.
    4.  New latency is 115 ms, illustrating that quantization overhead cancels out inference gains.

2.  Why does high accuracy on curated benchmark datasets (such as ImageNet or GLUE) frequently fail to guarantee production readiness in real-world deployments?

    1.  Benchmarks are evaluated on GPUs, whereas all production models run on CPUs.
    2.  Benchmark datasets contain only synthetic, computer-generated data that lacks realistic labels.
    3.  Neural networks automatically lose their learned weights when exported to production formats.
    4.  Benchmarks evaluate models on static, clean distributions without operational constraints (e.g., sub-100 ms latency budgets, memory limits, noise, and ongoing distribution shift), whereas production systems face uncurated edge cases, shifting user behavior, and hardware precision limits.

3.  Why can code and infrastructure checks in a standard CI/CD pipeline fail to detect a loss of predictive quality, and how should drift and outcome monitoring guide the response?

4.  True or False: In production ML systems engineering, selecting a model that provides a 1% higher benchmark accuracy is always preferable, even if it requires doubling inference latency and memory footprint beyond the client application’s SLA.
