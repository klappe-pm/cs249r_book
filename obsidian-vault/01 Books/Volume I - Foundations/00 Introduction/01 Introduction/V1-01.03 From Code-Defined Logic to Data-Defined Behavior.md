# V1-01.03 From Code-Defined Logic to Data-Defined Behavior

[[Home|Home]] · [[01 Books/Volume I - Foundations/Volume 1 Overview|Volume Overview]] · [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01 Introduction|V1-01 Introduction]]

^sec-introduction-datacentric-paradigm-shift-4eca

In traditional software engineering, a programmer encodes domain logic directly into source code: a tax calculator applies statutory brackets line by line, and an early email filter blocks messages that match a list of forbidden keywords. That rule-based approach works when the specification is closed, but it breaks as soon as attackers rephrase their messages or disguise trigger words faster than engineers can patch the rules. Rather than encoding those decision rules by hand, an ML team pairs historical emails with binary spam labels and runs an optimization procedure that adjusts millions of numerical weights[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.16 Footnotes#^fn2|²]] until the model’s predictions align with the labels.

Andrej Karpathy[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.16 Footnotes#^fn3|³]] framed this transition from code-defined logic to data-defined behavior as the shift from **Software 1.0** to **Software 2.0** ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-karpathy2017software|Karpathy 2017]]). In Software 1.0, people write the instructions; in Software 2.0, a training procedure adjusts the model’s weights until its outputs match the examples ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.03 From Code-Defined Logic to Data-Defined Behavior#^tbl-software-1-vs-2|table 1]]). That procedure is usually stochastic gradient descent, which nudges the weights a small step at a time toward predictions that match the labels. Inference[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.16 Footnotes#^fn4|⁴]] then applies the trained weights to new messages whose labels are unknown, and a separate test set, held back from training, checks whether the model also works on examples it has never seen.

Software 2.0 does not eliminate traditional software engineering. Engineers still write the code that collects and prepares data, the program that runs training, and the services that deliver predictions to users. The decisions themselves, however, no longer live in human-readable control flow. They live in millions of numerical weights shaped by data, so static analysis and manual code review cannot reveal what the system will decide for a new input. Learned systems add a distinct failure mode in which predictive accuracy falls silently even when source code, compiler binaries, and execution environments remain unchanged.

| **Feature**      | **Software 1.0 (Traditional)** | **Software 2.0 (Machine Learning)**         |
|:-----------------|:-------------------------------|:--------------------------------------------|
| **Source Code**  | C++, Python, Java              | Learned weights, shaped by training data    |
| **Compiler**     | GCC, LLVM                      | Training loop (stochastic gradient descent) |
| **Logic**        | Explicit (Hand-coded)          | Implicit (Learned)                          |
| **Failure Mode** | Crashes or silent logic errors | Also statistical quality loss               |
| **Debugging**    | Trace execution and inputs     | Also inspect data and learned behavior      |

Table 1: **The Paradigm Shift from Software 1.0 to Software 2.0**: In Software 2.0, the “programmer” curates the dataset and designs the training process that shapes learned behavior. Debugging expands to include the data. The “compiler” analogy is approximate: unlike a deterministic compiler, the training process is stochastic and may produce different learned weights from the same training data.

^tbl-software-1-vs-2

The data-centered workflow changes what engineers must build and maintain. Sculley and colleagues described how model code occupies only a small fraction of a production ML system ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-sculley2015hidden|Sculley et al. 2015]]). The surrounding system includes data collection, verification, feature extraction, resource management, serving, and monitoring, each with its own maintenance obligations.

*A small orange box labeled ML code nested inside a much larger surrounding frame labeled System; the inner box occupies a tiny fraction of the outer area.*

*Production ML work is mostly the surrounding system, not the model code alone.*

That imbalance creates hidden technical debt, the accumulating cost of maintaining undocumented dependencies and brittle infrastructure around the model. Each surrounding component encodes assumptions about how an example is sampled, what a label means, when a feature is computed, which version reaches serving, and how degradation is detected. None of those assumptions appears in the matrix multiplication that produces a prediction, yet any of them can change the result. Improving the model alone cannot repair a measurement that no longer tracks its target, a broken feature pipeline, or a missing feedback signal.

Production data is therefore not a passive input. It is a measurement of the world, collected through a particular product and transformed by a changing pipeline. If that measurement stops representing the intended target, the model can remain numerically healthy while the system becomes wrong. Google Flu Trends had an enormous, timely stream of search data, but the meaning of that data changed beneath the model.

**War Story 1.1: When search logs mistook attention for illness (2013)**

**Context**: Google Flu Trends (GFT) estimated influenza activity from patterns in aggregated search queries ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-ginsberg2009detecting|Ginsberg et al. 2009]]; [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-lazer2014|Lazer et al. 2014]]). Its attraction came from the speed and scale at which searches arrived relative to clinical reports. If people searched for flu symptoms when they became ill, query volume appeared to offer a timely proxy, or indirect measurement, for infection.

**Failure mode**: The proxy was not stable. News coverage could change what people searched for, and autocomplete could change how they expressed those searches. Query volume could therefore reflect public attention and product behavior as well as illness. During the 2012–2013 season, GFT estimated roughly twice the CDC-reported proportion of doctor visits for influenza-like illness, and from August 2011 onward it overestimated in 100 of 108 weeks.

**Systems lesson**: The remedy was not a larger search dataset or a better-tuned model. Researchers combined search signals with U.S. Centers for Disease Control and Prevention (CDC) sentinel clinical data and recalibrated the relationship over time. Data volume is not ground truth. A behavioral proxy needs a feedback loop to a trusted measurement and continual evidence that the proxy still represents the quantity the system claims to estimate.

In Google Flu Trends, predictive quality deteriorated while the software kept operating, because both the input distribution (the kinds of inputs and how often each occurs) and the relationship between the proxy and its target had changed. The code stayed the same, so the change in behavior came from the data. The **data-as-code principle** names this property. Training data does not merely enter a fixed program; it helps determine the operational logic that the model implements. Engineers still write the optimization procedure, but the examples shape the model weights through stochastic gradient descent[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.16 Footnotes#^fn5|⁵]] and related methods. Changing the dataset can therefore change system behavior as surely as changing source code.

If data defines behavior, improving the data is a direct way to improve the system. Data-defined behavior is a property of machine learning; *data-centric* AI is a development strategy that treats improving the data as an explicit route to better predictions ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-ng2021datacentric|Ng 2021]]).

Data-defined behavior adds a testing obligation: assessing predictive quality over the population of inputs the system will encounter. Conventional software can also have input spaces too large to enumerate, so exhaustive testing is not a realistic expectation for either kind of system. The difference lies in what a passing test establishes. A unit assertion checks a specified condition for the tested input and state, while a predictive-quality claim describes aggregate performance over a population that can change over time.

In the 2012 ImageNet challenge, AlexNet’s decisive win[[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.16 Footnotes#^fn6|⁶]] helped set the deep learning era in motion, yet the benchmark could evaluate only a vanishing fraction of the inputs the model might encounter. Each input is a $224{\times}224$ RGB image with $256^{150{,}528}$ possible pixel configurations, a number with 362,508 digits. The base of that power is the number of intensity levels each color value can take, and the exponent is the number of color values in the image, three per pixel. Real photographs occupy only a tiny region of that space, but even that region is far too large to enumerate. The ImageNet Large Scale Visual Recognition Challenge (ILSVRC) validation set contains only 50,000 images ([[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-krizhevsky2012imagenet|Krizhevsky et al. 2012]]; [[01 Books/Volume I - Foundations/00 Introduction/01 Introduction/V1-01.15 Source References#^ref-russakovsky2015|Russakovsky et al. 2015]]). The ratio of evaluated inputs to possible configurations ($\text{Test Set Coverage} / \text{Total Input Space}$) is effectively zero. That disparity between what any test set can cover and what a deployed system will meet is the **verification gap**.

This disparity does not make evaluation futile; it changes what testing can establish. Predeployment evaluation provides statistical evidence over sampled inputs, while continuous production monitoring verifies whether the operating population and observed outcomes continue to support that empirical baseline. Statistical confidence replaces any expectation of exhaustive proof. **[[01 Books/Volume I - Foundations/03 Optimization/12 Benchmarking/V1-12 Benchmarking#^sec-benchmarking|Benchmarking]]** and the deployment chapters return to this gap and bound it statistically over a specified operating population.

*A large shaded field labeled Input space containing a single tiny dot labeled Test set.*

*Test coverage is a vanishing fraction of the input space.*

Because a machine learning claim is statistical and its population keeps moving, robustness cannot mean immunity to change. It means instrumenting the system to detect when production evidence no longer supports the model, and acting on that evidence.

Debugging an ML system therefore starts with inspecting datasets and pipeline transformations rather than tracing Python call stacks alone. Version control must record dataset snapshots and feature configurations alongside source-code commits, and evaluation harnesses must measure statistical distribution shifts and subpopulation outcomes rather than branch coverage. These practices establish reproducibility and provenance, even though they cannot transform empirical sampling into formal verification.

**Checkpoint 1.1: The paradigm shift**

Before tracing the history of AI, verify your understanding of the paradigm shift in how software is built:

**Software 1.0 vs. 2.0**: can you distinguish Software 1.0 (explicit instructions) from Software 2.0 (behavior learned from data)?

**Debugging shift**: can you identify which dataset evidence to inspect when accuracy falls without a code change?

**Verification gap**: can you explain why finite test coverage can provide statistical evidence but never exhaustive proof, and why production monitoring must continue gathering that evidence?

Learning behavior from data can seem inevitable in hindsight, but its adoption also reflects the scaling limits of earlier approaches. Many AI systems attempted to program intelligence directly through hand-crafted symbols and rules. Reading that history through a systems lens reveals recurring limiting constraints, the limits whose relaxation would most improve the whole system: logic, knowledge acquisition, feature design, and the physical infrastructure that the rest of this book studies.

**Self-Check: Question**

1.  In Andrej Karpathy’s Software 1.0 vs. Software 2.0 framing, how do the roles of source code, the compiler, and debugging map to machine learning workflows?

    1.  Learned weights shaped by training data act as source code, the training loop (stochastic gradient descent) acts as the compiler, and debugging expands from execution traces to the data and learned behavior.
    2.  Python scripts act as source code, the deep learning framework acts as the compiler, and debugging focuses on stepping through tensor operations in an interactive debugger.
    3.  Training datasets act as source code, GPU hardware acts as the compiler, and debugging focuses on profiling memory bandwidth utilization.
    4.  Pretrained model weights act as source code, inference serving runtimes act as the compiler, and debugging focuses on network packet inspection.

2.  A computer vision test suite evaluates a $224{\times}224$ RGB image classifier on 50,000 validation images. Why does passing 100% of these test cases still leave a substantial ‘verification gap’ in production?

    1.  Validation sets evaluate floating-point weights, whereas production inference engines always run in integer precision.
    2.  The total input space of possible pixel configurations ($256^{150{,}528}$, spanning over 300,000 decimal digits) vastly exceeds the sample coverage of any finite test set, making exhaustive testing mathematically impossible.
    3.  Convolutional neural networks cannot generalize beyond the exact batch size used during validation testing.
    4.  Test suites only evaluate forward inference passes, whereas production systems must continuously execute backward gradient updates.

3.  How did Google Flu Trends fail despite having access to hundreds of billions of real-time search queries, and what systems engineering lesson does this failure provide regarding behavioral proxies?

4.  The development paradigm where engineering teams hold model architecture code relatively fixed and systematically improve dataset quality, labels, and coverage to program model behavior is known as \_\_\_\_ AI.
