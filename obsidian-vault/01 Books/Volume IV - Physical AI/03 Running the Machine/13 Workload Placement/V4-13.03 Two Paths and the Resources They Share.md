# V4-13.03 Two Paths and the Resources They Share

[[Home|Home]] · [[01 Books/Volume IV - Physical AI/Volume 4 Overview|Volume Overview]] · [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13 Workload Placement|V4-13 Workload Placement]]

^sec-placement-two-paths-one-die

The third law, proposal is not permission, separates the machine’s two paths in authority; placement decides whether the hardware keeps them separate in time when the proposer is working hardest. Whether a candidate placement preserves that separation depends on the execution profile of each path, the physical resources that could couple them beneath software access controls, and which of those resources remain shared across the compute board.

If a 40 ms neural proposer and a 400 μs-deadline safety loop share the same operating-system scheduler or memory controller, a single kernel preemption tail or memory-bus burst can stall the 1 kHz permission tick past its deadline. To prevent that stall, the mobile manipulator splits control across two execution paths with different systems requirements. The proposal path runs the chunk policy on the application processor at 20 Hz, ingesting synchronized navigation and wrist camera streams to emit coordinated base velocity and arm joint targets. Its 99th-percentile (p99) inference latency, vision processing included, consumes 40 ms (an illustrative benchmark; see the Reader Guide) of each 50 ms chunk period. Running in unprivileged user space, the proposal path holds no direct hardware authority over the motor drives. In the reference design from Part I, the permission path executes on a discrete safety microcontroller (MCU) at 1 kHz. On every tick, it checks the active trajectory and any candidate replacement against the stopping envelope from **[[01 Books/Volume IV - Physical AI/03 Running the Machine/12 Safety Enforcement/V4-12.04 Stopping Envelopes#^sec-enforcement-stopping-envelopes|Stopping Envelopes]]**, staging admitted setpoints into the outbound EtherCAT frame destined for the drives. This routine must finish within a chosen 400 μs deadline inside its 1 ms tick. It runs in a privileged real-time domain on a dual-core lockstep controller,[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn1|¹]] whose cycle-by-cycle comparator flags divergent execution. That hardware guard is needed because a software envelope check cannot diagnose a silent fault in the CPU core executing it. Only the permission path holds memory-mapped input-output (MMIO) access to the fieldbus master carrying drive commands.

**Definition 13.2: Heterogeneous silicon partitioning**

***Heterogeneous silicon partitioning*** is the architectural allocation of stochastic, high-capacity cognitive workloads (perception, learned policy evaluation) and deterministic safety loops (safety invariant checks, admission and fallback) across specialized execution domains isolated in hardware.

1.  **Significance**: Placing high-capacity neural deliberation and real-time safety enforcement on the same general-purpose operating system or compute engine creates common-mode failures. Kernel thread preemption, dynamic memory allocation, and time-slicing between accelerator contexts add tail delay that no measured average bounds, and a permission path exposed to that tail can miss its physical control deadline.
2.  **Distinction**: Unlike logical software process isolation (such as Linux containers or POSIX process priorities), silicon partitioning enforces isolation across independent hardware registers, tightly coupled memories (TCM), and dedicated peripheral buses.
3.  **Common pitfall**: Treating multicore CPU affinity as failure-domain separation. Cores on one die still share caches, memory controllers, clock trees, and power rails, the resources that operational independence (definition [13.1](https://mlsysbook.ai/vol4/13_placement/13_placement.html#dfn-placement-operational-independence)) must bound one by one.

These two processors run separate software stacks. Proposal inference, global scene-map updates, telemetry streaming, and fleet networking run on the application processor under Linux. While a real-time kernel patch shortens scheduler dispatch latency, it cannot bound latency tails added by unvetted device drivers, bus arbitration, or shared memory controllers.[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn2|²]] Similarly, zero-copy buffers reduce internal memory-bus traffic, but they do not remove contention at the physical memory controller.

By contrast, enforcement and sensor validation run on the discrete safety microcontroller as bare-metal firmware governed by a hardware memory protection unit (MPU).[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn3|³]] Quadrature encoder counters, the inertial measurement unit (IMU) on its Serial Peripheral Interface (SPI) bus, and hardware timer capture channels are mapped directly to dedicated physical pins. Each candidate proposal arrives from the application processor across a board-level serial link and is published into local memory via the seqlock mailbox of **[[01 Books/Volume IV - Physical AI/01 Machine Anatomy/04 The Nervous System/V4-04.04 Multi-Rate Cadences#^sec-nervous-mailbox-exchanges|Lock-free and wait-free mailbox exchanges]]**. No dynamic random-access memory (DRAM) is shared between the two paths. The memory protection unit isolates local state, while the dedicated peripheral bus insulates the enforcer’s execution path from the host’s memory traffic.

Admitting an entire plan is a different computation from running the cyclic permission tick. For example, the whole-plan validation routine of **[[01 Books/Volume IV - Physical AI/03 Running the Machine/11 Trajectory Planning/V4-11.04 Replacement Timing and the Planning Horizon#^sec-planning-horizon-tradeoff|Action chunk horizons and reaction lag]]** cannot run uninterrupted inside a 1 ms control loop without breaking timing guarantees. Instead, the runtime scheduler must preserve the real-time tick either by running admission as bounded, interruptible work or by moving it to a separate processor whose own timing is verified. In either case, admission ends with an atomic check of current state and sensor evidence right before activation. The running machine splits admission across these domains. The host performs the global geometry checks of **[[01 Books/Volume IV - Physical AI/03 Running the Machine/12 Safety Enforcement/V4-12.09 Admission, Cyclic Checking, and Monitor Independence#^sec-enforcement-where-enforcer-sits|Admission, Cyclic Checking, and Monitor Independence]]**. The microcontroller checks the resulting record against bounded local evidence as background work below the tick’s priority, so the tick preempts it. [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.07 Silicon Isolation Decisions#^sec-placement-dispatch-admission|Section 13.6.2]] lists the bounds that keep this background work from delaying the tick through the microcontroller’s own buses and memory. The resource budget must cover the active trajectory buffer, the resident fallback plan, the temporary admission workspace, and worst-case interruption overheads. The proposal generation rate also does not set the interval between successful admissions. Qualification must show that the end-to-end pipeline (transfer, admission, and activation) preserves the lease renewal bound, a guarantee the tick deadline alone cannot provide.

Similarly, the full volumetric scene map stays on the application processor. The permission path receives only a compact, bounded local evidence snapshot whose spatial coverage, state uncertainty, observation timestamp, expiration horizon, and transport integrity have been pre-validated for the proposed motion and its fallback maneuver. Updating the host map, serializing the snapshot, transporting it across the bus, validating admission, storing it locally, and running per-tick spatial queries are separate computational costs that need their own entries in the timing budget. A synchronous query to the host processor must never stall the permission tick. If a proposed trajectory strays outside the validated bounds or lifetime of the local snapshot, the MCU rejects it immediately. The microcontroller’s static memory budget must therefore show that the local snapshot buffer and resident fallback trajectories fit alongside the compiled enforcement binary.

Electrically, the power delivery network isolates the microcontroller, low-voltage drive logic, and electromechanical spring-brake coils onto a dedicated safety rail. This rail carries a local capacitive hold-up of 2 s and draws zero load from the proposal subsystem. Hardware qualification must verify that voltage transients from motor acceleration or neural accelerator bursts on the shared battery pack cannot trigger an undervoltage reset on this isolated rail. This local energy reserve keeps the logic alive and holds the mechanical brakes released throughout a controlled stop without supplying traction power. Achieving the powered deceleration profiles of **[[01 Books/Volume IV - Physical AI/03 Running the Machine/12 Safety Enforcement/V4-12.10 The Fallback Ladder#^sec-enforcement-four-rungs|The four rungs of the fallback ladder]]** requires both an intact high-voltage drive path and a sink for regenerative braking energy. If either fails, the system must trigger a certified fail-safe fault response rather than relying on powered stopping-distance assumptions.

↩︎ The isolated permission rail and its hold-up sizing are established in **[[01 Books/Volume IV - Physical AI/01 Machine Anatomy/02 The Physical Body/V4-02.09 Which Physical Budget Binds First#^sec-body-permission-rail-isolation|Cross-budget coupling and permission rail isolation]]**.

On an unloaded machine, the initial compute budgets look generous. Representative baseline costs on the safety microcontroller allocate 40 μs to sample motor encoders, read the IMU over SPI, and check the proposal’s evidence epoch. They allocate 80 μs to check kinematic and dynamic envelope constraints and 15 μs to stage admitted setpoints into the outbound drive frame. That gives an unloaded enforcer execution time of 135 μs, or 54,000 cycles at the microcontroller’s 400 MHz clock. Measured against the 400 μs hard deadline, this baseline path leaves 265 μs of slack. Even the declared worst-case execution time (WCET) of 250 μs, the design envelope from **[[01 Books/Volume IV - Physical AI/03 Running the Machine/12 Safety Enforcement/V4-12.08 The Minimal Intervention Principle and Optimization Filters#^sec-enforcement-loop-budget|Execution timing in the sub-millisecond loop]]**, leaves 150 μs of headroom.

This timing margin cannot be spent entirely on shared-hardware contention. The response bound of **[[01 Books/Volume IV - Physical AI/01 Machine Anatomy/04 The Nervous System/V4-04.06 Real-Time Command Transport and Bus Determinism#^eq-nervous-response-budget|equation 4.3]]** already charges the tick for blocking ${B}_i$ by lower-priority tasks (50 μs) and interference ${I}_i$ from higher-priority tasks and interrupts (40 μs), both from the microcontroller’s own workload (**[[01 Books/Volume IV - Physical AI/01 Machine Anatomy/04 The Nervous System/V4-04.06 Real-Time Command Transport and Bus Determinism#^sec-nervous-rta-variance|Response time analysis and execution variance]]**). Delay from hardware shared with the proposer is a separate cost because it lengthens the execution term ${C}_i$ itself. A loaded tick meets its deadline only if its execution time, including all shared-hardware interference, stays below the deadline minus those internal overheads (90 μs), leaving an execution ceiling of 310 μs. Under the declared WCET bound, shared-hardware contention can add at most 60 μs of delay before the tick misses its deadline, and every placement analysis must account for this full budget.

The declared bound, not the deadline, is what a placement must defend. It bounds the tick’s execution in isolation, and the chosen placement claims that proposal-side load adds nothing to it. A loaded tick that runs longer than 250 μs therefore refutes that claim even when it finishes before the 400 μs deadline, because every margin downstream of the bound was computed on the premise it just broke. Each coupling in this chapter is priced against that *falsification threshold*, which [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.08 Empirical Verification of Silicon Isolation#^sec-placement-testing-separation|section 13.7]] formalizes and turns into a test campaign.

On the application processor, meanwhile, the neural policy’s 40 ms inference latency leaves 10 ms of margin within its 50 ms period. The enforcer’s sub-costs above are a baseline model rather than an integrated measurement, and local spatial-query overheads must also fit inside the cyclic budget. Full qualification requires measuring the loaded control cycle on the target to establish which spatial queries fall inside constraint evaluation and to account for any separate overheads. Neither an unloaded benchmark nor an isolated query model can verify the declared WCET bound.

↩︎ The spatial-query workload the safety microcontroller must answer each tick is established in **[[01 Books/Volume IV - Physical AI/03 Running the Machine/09 Spatial Memory/V4-09.07 Certified Spatial Assertions in Scene Memory#^sec-memory-volumetric-metric-maps|Volumetric metric maps and distance fields]]**.

### Shared Failure Domains and Attack Surfaces

^shared-failure-domains-and-attack-surfaces

A single stalls-per-tick coupling across shared silicon can consume the entire 60 μs shared-hardware allowance even when the proposal and permission paths run on separate processor cores.[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn4|⁴]] Beneath software access controls, four physical channels can bind the two paths without appearing on a software architecture diagram: memory subsystems, power rails, thermal paths, and clock distribution networks. The physical architecture from Part I is designed to sever each of them at the board level.

Memory contention is the first and often most severe coupling. On cores sharing an address space, operating-system page-table updates trigger inter-processor interrupts for Translation Lookaside Buffer (TLB) shootdowns,[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn5|⁵]] while coherent direct memory access (DMA) from high-throughput camera pipelines incurs cache-invalidation stalls.[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn6|⁶]] More fundamentally, a time-critical control loop cannot read its sensor buffers if an asynchronous accelerator monopolizes the physical interconnect. In a Unified Memory Architecture (UMA), neural accelerators, application cores, and real-time cores arbitrate for a single pool of DRAM across a shared crossbar. A high-resolution vision pipeline or an aggressive DMA engine can then saturate the bus and starve the permission routine of encoder and IMU feedback, whatever its software thread priority. This mismatch between software priority and unmanaged interconnect contention is the **UMA crossbar trap**, and [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.04 Contention for Shared Resources#^sec-placement-resource-contention|section 13.3]] prices the queueing delays and bank conflicts behind it. The chosen design avoids the trap by giving the safety controller exclusive ownership of its memory. Candidate proposals cross an isolated board-level serial bus into dedicated local SRAM, so no DRAM is shared between the two domains.

Power delivery represents the second coupling vector. Although the host processor and the safety controller draw from a common battery, they do not share a power rail. The host application processor draws from the nominal 47.7 V motor drive bus through a dedicated DC-DC step-down converter that triggers an undervoltage lockout (UVLO) if the supply sags to 33 V. The steady-state margin analysis in **[[01 Books/Volume IV - Physical AI/01 Machine Anatomy/02 The Physical Body/V4-02.07 Electrical Power Integrity#^sec-body-power-integrity|Electrical Power Integrity]]** ensures that even a depleted battery pack remains above this threshold during simultaneous drive acceleration and peak neural inference. Unmodeled transients or supply faults (a blown fuse, or a battery management system (BMS) contactor trip), however, can depress the bus and crash the application processor. Had the safety microcontroller shared this unisolated supply, that same brownout would reset the safety monitor simultaneously. Motor gate drivers incorporate internal hardware protections for such events: integrated undervoltage lockouts disable power MOSFET outputs when gate-drive rails collapse, and pull-down resistors prevent floating logic pins from triggering destructive shoot-through currents. Those protections mitigate electrical switching faults; they do not establish a harmless coast or a controlled stop. A shared brownout would also extinguish the permission path, leaving no MCU-controlled response to manage the robot’s kinetic energy. The dedicated, held-up rail preserves supervision while the host browns out and reboots. The safety microcontroller detects the bus undervoltage interrupt and commands the fault response whose resources survive. Powered deceleration requires an intact drive-energy path and regenerative sink; if the supply fault removes either, the separately qualified mechanical or passive response governs.

Thermal dissipation and clock distribution introduce the third and fourth coupling channels. When co-located on a shared silicon die or bonded to a common heat spreader, heavy sustained compute workloads on the application processor raise junction temperatures toward thermal trip points. Dynamic voltage and frequency scaling (DVFS) governors configured to protect the silicon package can throttle clock frequencies in shared clock domains, slowing real-time safety cores that share no code with the proposal pipeline. As demonstrated in [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.05 Thermal and Timing Coupling#^sec-placement-thermal-timing-coupling|section 13.4]], thermal throttling introduces hysteresis that outlasts the transient compute burst that triggered it. Similarly, relying on a shared external crystal oscillator creates a single point of failure, because thermal drift, mechanical shock, or a fractured crystal desynchronizes both execution domains at once. A discrete microcontroller removes the shared die and oscillator dependencies by providing a physically separated package, dedicated heat dissipation, and an independent quartz crystal oscillator. Its own clock, supply, and thermal operating limits, including exposure to the common chassis environment, still require qualification.

Any safety-critical design must still evaluate the alternative it rejects, a single shared die carrying both paths. On one die the four couplings collapse into one semiconductor package, so real-time cores that execute their instructions independently of the application cores remain coupled through each resource. Bursts of camera DMA, neural accelerator memory access, and high-volume diagnostic logging can stall the real-time cores’ cache fills and delay their interrupt handling unless hardware arbiters enforce deterministic bandwidth caps. At the same time, high-slew current transients can droop a shared core rail and a software-initiated host reset can take down a common reset chain unless power and supervisor domains are strictly isolated. Even when memory and power are partitioned, heat from the neural processing units raises the substrate temperature under the real-time cores, which share the package’s only route to the chassis. A unified on-die governor throttles the real-time cores’ clock together with the accelerator’s when that substrate temperature reaches its trip point. A shared PLL or crystal also carries any clock fault to both.

Beyond accidental contention, these shared silicon pathways expose a **cyber-physical attack vector**. An adversary who compromises the unprivileged proposal stack can generate malicious memory traffic or toggle accelerator power states rapidly. The traffic starves the permission routine of memory service, and coordinated current surges pull the shared supply down ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.04 Contention for Shared Resources#^sec-placement-resource-contention|section 13.3]] prices both). An isolation claim must therefore hold against the worst contention the proposal domain can generate within its authorized hardware limits, and benchmarks of benign workloads cannot establish that bound.

Functional-safety engineering provides formal tools to analyze this shared inventory. On the mobile manipulator, the intended certified safety scope is deliberately narrow; this illustrative platform has not established certification. The trajectory admission algorithms that validate learned proposals carry no formal safety integrity rating; the intended integrity claims belong to the scoped protective stop functions implemented in the motor drives and safety laser scanner. The function selected for a safety rating on the microcontroller is the watchdog that revokes authority when the chunk lease expires or the host heartbeat falls silent. It then commands a certified drive-level stop, safe stop 1 (SS1, a controlled deceleration followed by torque removal) or safe torque off (STO), whichever the risk assessment assigns to the machine’s state. Keeping that intended rated function apart from unrated software components (the trajectory admission checks and the neural proposer) is a formal *safety decomposition*. The decomposition requires evidence that faults and interference from the unrated elements cannot defeat the claimed protective functions under the declared fault model. Workload placement determines which shared dependencies that evidence must address. A **dependent failure analysis** identifies the shared hardware resources whose failure or overload could compromise both paths at once. ISO 26262 Part 9 ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-iso26262|International Organization for Standardization 2018]]) requires it, and IEC 61508 ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-iec61508|International Electrotechnical Commission 2010]]) treats it as common-cause failure analysis. The warehouse machine answers to industrial and mobile-robot safety standards rather than automotive ones (ISO 10218-2:2025, for instance, incorporates the collaborative-robot protections first defined in ISO/TS 15066 ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-iso10218part2|International Organization for Standardization 2025]], [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-isots15066|2016]])), but the requirement of freedom from interference is the same in every domain. The resource audit of this chapter is that dependent-failure analysis carried out on physical silicon, with every coupling priced in the tick’s timing budget.

↩︎ The certified drive functions beneath the permission path, and the stop each failure triggers, are established in **[[01 Books/Volume IV - Physical AI/03 Running the Machine/12 Safety Enforcement/V4-12.10 The Fallback Ladder#^sec-enforcement-certified-functions|Certified safety functions beneath the permission path]]**.

↪ The industrial and mobile-robot standards that govern this machine, and where each one’s evidence is generated, are developed in **[[01 Books/Volume IV - Physical AI/04 Governing the Machine/16 Deployment Release/V4-16.04 Safety Cases and Claims#^sec-release-standards-map|The standards map for the running machine]]**.

Because each shared dependency names a physical or adversarial mechanism that could defeat the decomposition, qualification must test the isolation by injecting faults rather than by reviewing schematics. The timing stress campaign designed in [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.08 Empirical Verification of Silicon Isolation#^sec-placement-testing-separation|section 13.7]] validates these boundaries against the declared WCET threshold across four stress regimes, three aimed at the supply, clock, and link and one at the proposals themselves:

1.  *Power-rail droop testing*: Injecting maximum-slew current transients into the drive bus to verify that the noise coupled onto the safety rail stays inside the microcontroller’s specified supply tolerance, the limit the placement record’s droop field carries.
2.  *Clock glitching and frequency margining*: Verifying that the real-time core maintains deterministic instruction cycle counts under clock jitter and voltage fluctuation.
3.  *Communication link flooding*: Saturating shared interconnects to confirm that safety-critical heartbeat frames and trajectory proposals retain their deterministic transmission windows.[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn7|⁷]]
4.  *Numerical and semantic fault injection*: Streaming synthetic proposals populated with out-of-range floats, subnormal numbers, and IEEE 754 NaNs to verify single-cycle rejection without pipeline stalls or exception traps.

↪ The physical injection apparatus for supply, clock, and bus disturbances is developed in **[[01 Books/Volume IV - Physical AI/04 Governing the Machine/15 Adversarial Verification/V4-15.09 Fault Injection on Hardware#^sec-verification-hardware-fault-injection|Fault Injection on Hardware]]**.

### Four Candidate Placements Against One Shared-Resource Inventory

^four-candidate-placements-against-one-shared-resource-inventory

On the mobile manipulator’s compute board, four candidate placements for the permission loop span the options from sharing every silicon resource to sharing only the battery ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.03 Two Paths and the Resources They Share#^tbl-13-placement-candidates|table 1]]). Scoring each candidate row by row exposes the common-cause faults that a high-level chip block diagram hides, including whether a commercial module actually routes an on-die safety island’s pins and rails to the integrator. At the least isolated extreme, *shared application cores* (a) expose the permission loop to operating-system scheduling jitter, driver interrupt stalls, and kernel preemption tails, delays that can push execution past the 400 μs deadline and even the 1 ms control period. Moving to *a real-time cluster in the host clock and power domain* (b) dedicates execution cores to safety enforcement, yet it still shares the die’s cache hierarchy, memory controller, core supply rail, clock governor, and thermal path. [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.04 Contention for Shared Resources#^sec-placement-resource-contention|Section 13.3]] prices its memory exposure, and [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.05 Thermal and Timing Coupling#^sec-placement-thermal-timing-coupling|section 13.4]] shows the clock throttling that rules this candidate out.

To sever those host-domain couplings without leaving the package, modern automotive and industrial SoCs provide *an on-die safety island* (c). For instance, the Functional Safety Island of NVIDIA’s Orin-class SoCs integrates four dual-core lockstep Cortex-R52 processors, each with private tightly coupled memory, around 3 MB of on-island SRAM ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-nvidia2023drivefsi|NVIDIA 2023b]]). The island runs from an independent crystal oscillator and a dedicated voltage rail behind hardware firewalls that block unauthorized access from the rest of the die. The application governor therefore cannot throttle its clock, and an enforcement routine whose code and data stay in island memory never waits on host DRAM arbitration. Even so, several couplings remain inside the package: shared substrate temperature, common reset and power sequencing logic, arbitration across the on-chip fabric carrying proposals or island DMA, and the common board-level power supply. Adopting an on-die island therefore requires reading back the configured firewall registers, tracing the power-sequencing logic, and running the loaded stress campaign of [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.08 Empirical Verification of Silicon Isolation#^sec-placement-testing-separation|section 13.7]] while the safety loop executes. Where those remaining die-level couplings cannot be bounded or the module does not expose the island, *a discrete safety microcontroller* (d) removes every on-die coupling altogether, trading silicon integration for an explicit board-level link from the application processor that [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.07 Silicon Isolation Decisions#^sec-placement-isolation-decisions|section 13.6]] budgets and characterizes.

Laid out on the machine’s compute board, the four candidates differ in how many shared blocks stand between the permission tick and the proposer ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.03 Two Paths and the Resources They Share#^fig-13-placement-resource-map|figure 1]]). Candidates (a) and (b) sit behind the application die’s last-level cache, DRAM controller, clock governor, core rail, and fabric. The island (c) moves cores, crystal, and SRAM behind a firewall but stays in the same package and heat path. Only (d), a separate package clocked at 400 MHz with local TCM and a 2 s rail hold-up, leaves the die entirely and reaches it through a checked board link.

^tbl-13-placement-candidates

On the inventory alone, candidate (c) is a strong contender. It separates the cache and miss handling, DRAM, core rail, and governed clock, the rows behind the strongest mechanisms the next two sections price. It leaves shared the die temperature, the fabric its proposals cross, the board supply, and a reset chain whose independence still needs evidence, each of which a qualification would have to cover. This verdict is provisional, since nothing has yet been priced, but the machine does not wait on it, because it adopts candidate (d) for a reason outside silicon capability. While the safety island exists on the physical SoC die, commercial edge modules packaging the application processor do not expose it to system integrators, reserving access for dedicated industrial platforms ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.03 Two Paths and the Resources They Share#^tbl-13-island-exposure|table 2]]). Because an unexposed, unprogrammable safety island cannot serve as a valid deployment target, safety enforcement must move off the primary module.

Commercial platform exposure is therefore itself an architectural constraint. A vendor block diagram illustrating isolated silicon domains establishes what the hardware could theoretically execute, but system developers can use only the execution resources unlocked by board support packages and platform firmware. While specific commercial product tiers change over time, the engineering requirement to audit software accessibility before committing to a workload placement remains permanent.

The third law (principle [[01 Books/Volume IV - Physical AI/03 Running the Machine/V4 Running the Machine#^pri-vol4-proposal-permission|3]]) says a proposal is not permission, and that separation is empty if the proposal can delay the permission decision through hardware the two share. The four candidates differ in which resources they force the paths to share, and even for the discrete microcontroller the separation remains a hypothesis about timing under load that only a measurement of the loaded tick can support.

Choosing candidate (d) before pricing the shared die does not make the quantitative analysis of shared resources superfluous, for three reasons. First, each mechanism priced in [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.04 Contention for Shared Resources#^sec-placement-resource-contention|section 13.3]] and [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.05 Thermal and Timing Coupling#^sec-placement-thermal-timing-coupling|section 13.4]] turns the rejection of candidates (a) and (b) from an architectural assumption into empirical evidence. Second, each mechanism names an obligation that the discrete design carries in miniature, because the microcontroller has its own DMA engines, interrupt controller, internal buses, and power supply, as detailed in [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.07 Silicon Isolation Decisions#^sec-placement-dispatch-admission|section 13.6.2]] and [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.08 Empirical Verification of Silicon Isolation#^sec-placement-testing-separation|section 13.7]]. Finally, the same analysis provides the qualification blueprint for an integrator whose platform firmware exposes an on-die safety island. Unless a passage says otherwise, the calculations in [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.04 Contention for Shared Resources#^sec-placement-resource-contention|section 13.3]] and [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.05 Thermal and Timing Coupling#^sec-placement-thermal-timing-coupling|section 13.4]] evaluate the permission tick placed hypothetically on the application die, using the sub-costs and timing budget assigned to the microcontroller. On a shared die, the first place proposal-side load encounters that tick is the memory system.
