# V4-13.08 Empirical Verification of Silicon Isolation

[[Home|Home]] · [[01 Books/Volume IV - Physical AI/Volume 4 Overview|Volume Overview]] · [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13 Workload Placement|V4-13 Workload Placement]]

^sec-placement-testing-separation

The thermal hangover refuted candidate (b) from a model, but a placement that survives every model still has to face a measurement that could refute it. A claim of silicon isolation between an unverified learned workload and a safety enforcer must therefore reduce to a testable bound on enforcement latency and refusal availability. This bound must hold across all declared proposal workloads, junction temperatures, and operational modes. If shared-resource contention delays an enforcer refusal past its physical deadline, the claimed operational separation has failed, whatever architectural isolation was promised on paper.

### The Worst-Case Execution Time Falsification Threshold

^the-worst-case-execution-time-falsification-threshold

When a loaded permission tick runs for 260 µs against a declared isolated worst-case execution time of 250 μs, it finishes well inside the 400 μs deadline yet still refutes the claim that shared hardware added zero interference. The budget section of [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.03 Two Paths and the Resources They Share#^sec-placement-two-paths-one-die|section 13.2]] introduced the permission tick’s declared worst-case execution time (${T_{\text{wcet}}}$) as this falsification threshold, and a test designed to refute a placement must name the exact measured quantity it compares against that bound. In this example, the declared worst-case execution time bounds the task in isolation, whereas a qualified execution model can instead include bounded resource interference. Here, microarchitectural interference from hardware shared with co-running workloads lengthens the execution term rather than appearing as a separate term of the response-time bound (**[[01 Books/Volume IV - Physical AI/01 Machine Anatomy/04 The Nervous System/V4-04.06 Real-Time Command Transport and Bus Determinism#^eq-nervous-response-budget|equation 4.3]]**). The loaded ${C}_i$ includes that penalty, beside the blocking ${B}_i$ and interference ${I}_i$ that the microcontroller’s own tasks contribute.

The pass-fail threshold for silicon isolation derives directly from the system specification. The machine’s permission path specifies a declared worst-case execution time ${T_{\text{wcet}}} =$ 250 μs, representing the isolated execution parameter ${C}_i$ in **[[01 Books/Volume IV - Physical AI/01 Machine Anatomy/04 The Nervous System/V4-04.06 Real-Time Command Transport and Bus Determinism#^eq-nervous-response-budget|equation 4.3]]**. It must complete each permission evaluation within a chosen enforcer deadline ${T_{\text{deadline,enf}}} =$ 400 μs, which is nested inside the overall permission period ${T_{\text{tick}}} =$ 1 ms. When measured under operational load, total enforcer execution time is the sum of isolated execution latency and cross-workload hardware interference, as formalized in [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.08 Empirical Verification of Silicon Isolation#^eq-placement-falsification-threshold|equation 7]]:

$$
{t_{\text{enf}}} = {t_{\text{iso}}} + {T_{\text{interf,shared}}}, \qquad {t_{\text{iso}}} \le {T_{\text{wcet}}} < {T_{\text{deadline,enf}}} < {T_{\text{tick}}} \tag{7}
$$

 where ${t_{\text{iso}}}$ represents the execution time of the permission path running with zero contention, and ${T_{\text{interf,shared}}}$ captures the cumulative delay inflicted by proposal-side activity competing for shared DRAM channels, caches, interconnects, clock trees, power distribution networks, and thermal budgets.

^eq-placement-falsification-threshold

An ideal isolated placement claims that proposal-side execution introduces zero cross-workload interference (${T_{\text{interf,shared}}} = 0$), making the declared bound ${T_{\text{wcet}}}$ the **falsification threshold**. Because isolated execution cannot exceed ${T_{\text{wcet}}}$ by definition, any measured cycle under load that exceeds ${T_{\text{wcet}}}$ demonstrates that either the declared baseline WCET was underestimated or the shared hardware introduced an interference penalty that the architecture failed to eliminate. Either outcome refutes the timing contract of the placement, even if the cycle completes before ${T_{\text{deadline,enf}}}$, because every downstream margin, from the deadline itself to the stopping distance budgeted for each tick, depends on that premise. Conversely, observing a loaded execution cycle below ${T_{\text{wcet}}}$ does not establish that ${T_{\text{interf,shared}}}$ is zero. Empirical testing can decisively falsify a declared bound, but measurements alone cannot prove its universal validity. Any test campaign samples only the microarchitectural states it reaches, and microarchitectural timing anomalies can push the true worst-case latency beyond every observed cycle.[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn13|¹³]]

Even a small overrun invalidates the declared premise. It need not cause a collision on that tick, but it removes the guarantee beneath every downstream stopping and lease-renewal margin. Response-time verification charges the full bound from **[[01 Books/Volume IV - Physical AI/01 Machine Anatomy/04 The Nervous System/V4-04.06 Real-Time Command Transport and Bus Determinism#^eq-nervous-response-budget|equation 4.3]]**, ${t_{\text{enf}}} + {B}_i + {I}_i \le {T_{\text{deadline,enf}}}$, in which ${T_{\text{interf,shared}}}$ inflates the execution term ${t_{\text{enf}}}$, while ${B}_i$ and ${I}_i$ remain the blocking and interference from the safety microcontroller’s own workload. Under the declared bound, shared platform hardware can introduce at most 60 μs of cross-workload delay before the enforcer violates its deadline, and every candidate in this chapter, chosen or rejected, is judged against that allowance.

Because a single permission tick at 1.3 m/s corresponds to only ${v}\,{T_{\text{tick}}} =$ 1.3 mm of vehicle displacement, engineers often underestimate the severity of a missed deadline. The stopping budget, however, leaves little margin for error. Under the baseline assumptions compiled in **[[01 Books/Volume IV - Physical AI/03 Running the Machine/12 Safety Enforcement/V4-12.04 Stopping Envelopes#^tbl-enforcement-stopping-budget|The warehouse mobile manipulator's stopping budget]]**, bringing the vehicle to a controlled stop from 1.3 m/s requires 969.0 mm, which leaves 131.0 mm of clearance within the 1.10 m clear distance. That subtotal accounts only for the onboard stopping maneuver; it excludes the dispatch-to-admission latency ${\Delta_{\text{da}}}$, which is an allocated system budget rather than a measured property. Deducting the 63.3 ms allocated to ${\Delta_{\text{da}}}$ in notebook [13.3](https://mlsysbook.ai/vol4/13_placement/13_placement.html#nbk-placement-transport-budget) shrinks the stopping reserve to 48.7 mm. While the stopping budget can absorb the loss of an isolated ${T_{\text{tick}}}$, unmitigated microarchitectural contention does not produce predictable single-tick delays; it produces open-ended stalls that exhaust the stopping margin entirely. That asymmetry is why the thermal case of [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.05 Thermal and Timing Coupling#^sec-placement-thermal-timing-coupling|section 13.4]] disqualifies candidate (b) even though each of its late refusals slips only about one tick. The distance lost is small, but the placement has broken the bound on which every distance was computed, and a broken bound no longer limits how far the next stall can run.

Guaranteeing that the enforcer finishes before ${T_{\text{deadline,enf}}}$ also stabilizes the downstream feedback loop. When the system dispatches motor-drive command frames at a deterministic phase offset scheduled no earlier than ${T_{\text{deadline,enf}}}$, execution jitter never propagates to the actuators. Instead, the feedback controller encounters a constant computation delay equal to 0.4 of the tick period. Control engineers model this fixed latency directly as phase lag at the loop crossover frequency, mirroring the phase delay introduced by a zero-order hold.

↪ The zero-order hold’s phase lag, about half a sample period of delay, is developed in **[[05 Reference/Volume IV - Physical AI/V4 Control and Dynamics#^sec-appendix-control-zoh|Discrete-time sampling and zero-order hold phase lag]]**.

### Worst-Case Execution Time Analysis Methods

^worst-case-execution-time-analysis-methods

Measuring ten thousand clean cycles on a quiet laboratory bench cannot reveal the worst-case stall that occurs when an out-of-order core suffers a cache-eviction cascade at the exact instant a DMA controller locks the memory bus. A declared worst-case execution time is a formal timing commitment, and systems engineers establish it through one of four methods, each resting on distinct premises ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-puschner1989calculating|Puschner and Koza 1989]]; [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-wilhelm2008worst|Wilhelm et al. 2008]]).

*Static analysis* operates entirely without executing the binary on hardware. The analyzer reconstructs the control-flow graph directly from machine instructions, bounds every loop iteration, and applies abstract interpretation ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-cousot1977abstract|Cousot and Cousot 1977]]) to model the processor pipeline and cache states so that memory references are classified as definite hits, definite misses, or unresolvable states. The tool then solves an integer linear program ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-li1995performance|Li and Malik 1995]]) to identify the longest feasible execution path. It uses basic-block execution frequencies as decision variables constrained by structural flow conservation and loop bounds, while the objective function maximizes total cycle count based on block-level worst-case latencies. Static analysis yields a sound upper bound only with valid loop and path bounds and a model of the actual binary, memory and peripheral accesses, and relevant processor and resource states. The reference microcontroller’s in-order execution and private tightly coupled memory make these obligations more tractable, though they do not establish model fidelity by themselves. On application multicores, out-of-order execution, undocumented interconnect arbitration, and shared non-blocking caches make a static bound difficult to justify when relevant resource states and co-running demand remain uncontrolled or unmodeled.

Where an exhaustive microarchitectural model is unavailable, *measurement-based analysis* executes the binary directly on target hardware under the most demanding synthetic test harnesses the engineer can construct, appending an empirical safety margin to the observed maximum latency (the high-water mark). That directness explains its ubiquity in complex systems, yet it provides no mathematical guarantee against unobserved execution paths or rare microarchitectural collisions. The adversarial stress testing suite developed below targets contention states that ordinary workloads may leave unexercised, and its coverage limits remain part of the qualification record. *Hybrid analysis* bridges those two regimes. It measures the execution latency of isolated code snippets or basic blocks directly on physical silicon, then composes those empirical timings across the program’s control-flow graph using static path-analysis techniques. It thus relies on target measurements at the sub-routine scale while adopting the structural path bounds of static modeling. Alternatively, *probabilistic analysis* models execution times as random variables, fitting extreme value distributions to empirical latency traces to project the probability that an execution exceeds a given threshold ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-cucugrosjean2012measurement|Cucu-Grosjean et al. 2012]]). Because this methodology assumes that experimental measurement runs faithfully sample the operational probability distribution, unmodeled dependencies on platforms with complex hidden microarchitectural state can invalidate the projection. **[[05 Reference/Volume IV - Physical AI/V4 Systems and Hardware#^sec-appendix-systems-timers|Real-Time Timers, Watchdogs, and Schedulability]]** analyzes these statistical models and their operational limits.

When migrating from an isolated processor to a shared multicore system-on-chip, isolated execution analysis becomes insufficient. Isolated worst-case latency must be augmented with explicit interference penalties for every contended shared resource. Modern multicore response-time frameworks construct these bounds by combining the formal service guarantees of shared arbiters with the maximum request demand generated by co-running cores ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-davis2018extensible|Davis et al. 2018]]). Such composition yields finite, provable bounds only when hardware mechanisms or operating system regulators enforce resource budgets, which is why [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.07 Silicon Isolation Decisions#^sec-placement-isolation-decisions|section 13.6]] relies on memory-bandwidth regulation (such as MemGuard) to render shared silicon analyzable. FAA AC 20-193 provides an acceptable means of compliance for airborne multicore systems. Where time interference is not mitigated, it calls for WCET analysis confirmed by testing on the target processor with all software executing in the intended final configuration. It also permits separate determination when time interference is shown to be mitigated ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.13 Source References#^ref-faa2024ac20193|Federal Aviation Administration 2024]]).

On the running machine, the available execution models and enforced resource bounds determine the verification method. A discrete microcontroller reduces the shared-resource model, but analysis and testing must still cover local DMA, interrupts, internal buses, background admission, and the board-level supply, clock, and link faults inventoried here. On a shared application SoC, this example’s declared 250 μs remains the isolated baseline, not a loaded execution bound. To validate such a shared placement, the engineering team must formally bound ${T_{\text{interf,shared}}}$ across every shared architectural row identified in [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.03 Two Paths and the Resources They Share#^tbl-13-placement-candidates|table 1]]. It must also verify that the resulting response bound remains safely within ${T_{\text{deadline,enf}}}$, and it must execute an adversarial campaign capable of refuting both the analytical bounds and the isolation claims.

### Adversarial Stress Testing and End-To-End Brake Onset Timing

^adversarial-stress-testing-and-end-to-end-brake-onset-timing

Refuting an independence claim requires synthetic workloads engineered to induce correlated worst-case microarchitectural contention rather than standard benchmarks (such as MLPerf) that report average throughput. Standard ML inference pipelines schedule memory transactions to maximize pipeline overlap and average data bus utilization, which conceals transient contention peaks. On physical silicon, maximum interference occurs during synchronized bursts when multiple subsystems demand the exact same physical resources at the exact same clock edge. An adversarial stress suite must synthesize these collision patterns deliberately. The five generators below target the shared die first, because that is where the strongest mechanisms of this chapter live, and they serve two campaigns: refuting a shared-die candidate, or qualifying an island an integrator can use.

1.  **Targeted DRAM bank conflict generators**: The stress suite issues unaligned DMA transfers with access strides calibrated to target the exact DRAM bank and bank group assigned to the enforcer’s memory buffers. By continuously alternating access across conflicting row addresses, the generator repeatedly evicts open row buffers, incurring the full precharge and activation latency (37.5 ns at the application SoC’s memory clock rate) on every subsequent read.
2.  **Shared-cache miss-handling engines**: Streaming memory threads cycle through footprints substantially larger than the shared last-level cache. These routines exhaust its MSHRs and saturate writeback buffers with dirty cache lines, triggering the structural interconnect stalls identified in [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.04 Contention for Shared Resources#^sec-placement-interference-mechanisms|section 13.3.2]] as the primary threat to bounded enforcer latency.
3.  **Resonant PDN current-step generators**: Microbenchmarks execute rapid, high-amplitude current transients across neural accelerator arrays while sweeping the transient’s phase relative to the permission tick. High-bandwidth oscilloscope probes on the PDN capture package-level ${L_{\text{pkg}}} \cdot d{i}/d{t}$ voltage droop and ringing, directly testing whether supply collapse induces clock throttling or logic faults on co-located cores.
4.  **Correlated peripheral interrupt storms and storage saturation**: High-bandwidth camera deserializers and NVMe storage controllers stream raw telemetry at line rate while asserting uncoalesced hardware interrupts. This flood stresses the interrupt controller, consumes shared crossbar bandwidth, and saturates system write buffers.
5.  **Chassis electromechanical transient coupling**: Test benches inject realistic traction-motor current transients and regenerative braking pulses into the shared DC bus. These tests verify whether DC-DC converter dropout, ground bounce, or electromagnetic interference couples into the enforcer’s power rails or clock distribution networks under worst-case operating envelope conditions.

The campaign on the chosen discrete microcontroller keeps only the generators that can reach it, and it maps onto the four fault-injection regimes of [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.03 Two Paths and the Resources They Share#^sec-placement-two-paths-one-die|section 13.2]], now applied together rather than one at a time. Supply transients on the shared battery bus (generator 5) are regime 1, power-rail droop testing. Clock margining under those transients is regime 2. Saturating the board link while the microcontroller’s own receive DMA, fieldbus interrupts, and background plan validation contend for its internal buses ([[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.07 Silicon Isolation Decisions#^sec-placement-dispatch-admission|section 13.6.2]]) is regime 3, link flooding. Streaming malformed and NaN-laden proposals during all of it is regime 4. The host-side targets of generators 1 to 4 do not reside on the microcontroller, which shares no DRAM, cache, or package with the proposer. Analogous contention from its own DMA and interrupts remains in regime 3. They drop out because (d) removes those rows, a claim the register readback and the inventory must support, not because the campaign overlooked them.

Hardware instrumentation must trace the complete perception-action timeline: sensor observation capture, coherent ingestion across the interconnect, permission decision completion, drive-frame dispatch over the real-time fieldbus, and physical frame arrival at the motor inverters. While digital bus logs reveal software delays, issuing a bus frame does not equal physical braking. For a controlled powered stop, synchronized motor-phase current probes and external optical tracking must measure the actual onset and dynamic trajectory of vehicle deceleration. The nominal renewal-to-onset budget is 82 ms, combining the software lease duration, one permission tick, fieldbus transit, and motor-drive torque development. Spring-applied mechanical brakes engage only when the vehicle has already decelerated to near-standstill, so mechanical brake contact cannot serve as a proxy for powered deceleration onset. In fault-injection scenarios involving total MCU failure or bus power loss, testing must independently verify the physical stopping distance delivered by the fail-safe emergency circuits. All timing intervals must be reported alongside verified clock synchronization bounds and instrument measurement uncertainties.

Because interference compounds across physical, thermal, and architectural domains, stress testing requires a full factorial experimental matrix to uncover paired-stress vulnerabilities. The evaluation sweeps across four orthogonal axes. The first axis is a cold condition (an illustrative junction temperature of $35\,^{\circ}\text{C}$) vs. a hot one, which on a shared die means junctions held at or above the throttling threshold ${T_{\text{trip}}}$ of [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.05 Thermal and Timing Coupling#^sec-placement-thermal-timing-coupling|section 13.4]] and on the discrete microcontroller means the bay at its highest qualified ambient. The second is an idle proposal path vs. a saturated proposal engine executing maximum-batch inference. The next is diagnostic circular logging disabled vs. streaming at full non-volatile memory bandwidth. The last is nominal tracking commands vs. boundary-violating commands that trigger refusal routines. Testing refusal paths under full stress is mandatory because executing a safe clamping trajectory or entering emergency shutdown involves cold branch paths, non-cached error-handling code, and secondary bus transactions that never execute during steady-state aisle driving.

The factorial matrix exists to uncover co-runner collisions that escape isolated unit testing. Consider what happens on the rejected shared-die placement when an unexpected obstacle steps into the warehouse aisle. Detecting the obstacle forces the enforcer to execute its cold refusal branch to initiate an emergency stop. Simultaneously, the application processor flags the anomalous visual scene and triggers a high-priority diagnostic core dump over the shared DMA interconnect. If tested in isolation, the refusal branch executes within its latency budget, and diagnostic dumping runs without error. When triggered concurrently, however, the diagnostic DMA burst floods the shared memory controller precisely when the enforcer must fetch its cold refusal instructions from DRAM. The resulting contention spike stalls the enforcer at the exact moment safe physical actuation is most urgent.

To see how empirical traces refute invalid isolation claims, evaluate an illustrative $10^7$-tick stress test conducted on the rejected shared-die configuration (where the enforcer executes on a real-time core cluster within the application SoC). Operating at one tick per 1 ms, this campaign runs for 10,000 s, or 2 h 46 min 40 s of continuous physical execution, excluding platform setup and reset overheads. Under cold, unloaded conditions, enforcer latency remains well within limits: the trace shows a median $\text{p50} =$ 95 μs, a 99th percentile $\text{p99} =$ 128 μs, and a maximum recorded latency of 152 μs. Under warm, heavily contended conditions, however, resource conflicts degrade the tail latency: $\text{p50}$ rises to 210 μs, $\text{p99}$ climbs to 330 μs, $\text{p99.9}$ reaches 395 μs, and the observed maximum spikes to 468 μs.

Because the loaded $\text{p99}$ alone exceeds the declared isolated bound ${T_{\text{wcet}}} =$ 250 μs, the trace invalidates the joint claim that the isolated baseline is bounded and proposal-side interference is zero. The overrun alone does not distinguish an underestimated baseline from interference; attributing it to interference requires independently justifying the baseline. Once the 90 μs of local blocking and RTOS task interference is charged, the loaded 99th percentile also pushes the response beyond the enforcer deadline ${T_{\text{deadline,enf}}} =$ 400 μs. A loaded trace of this shape would reach the verdict that the thermal analysis of [[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.05 Thermal and Timing Coupling#^sec-placement-thermal-timing-coupling|section 13.4]] reached from a model, without relying on that model, and the verdict would stand even if the model were wrong. The percentiles here are illustrative; the point is that a real trace on the target, not an argument, is what can refute a placement.

Even if a 10-million-tick stress trace records zero deadline violations, that outcome demonstrates only that interference remained bounded across the specific microarchitectural states generated during the test. A qualification report must document the full latency distribution, observed maximums, total sample counts, and test durations, while explicitly listing all unexercised physical conditions, such as long-term power delivery degradation, transient electromagnetic interference, and silicon aging.[[01 Books/Volume IV - Physical AI/03 Running the Machine/13 Workload Placement/V4-13.14 Footnotes#^fn14|¹⁴]] When an empirical contention test fails, the engineering team must re-evaluate its architecture: partition memory channels, implement strict arbiter bandwidth caps, restrict proposal workload concurrency, or relocate the enforcer to physically isolated silicon. Conversely, when a campaign passes, it provides empirical evidence that supports the analytical model within the tested parameters, without mistaking a finite empirical sample for an absolute mathematical proof.

**Checkpoint 13.3: Refuting a placement**

A placement claim is only as strong as the test that could have refuted it. Verify the core empirical criteria that defend this boundary:

**Threshold arithmetic**: A loaded campaign on a shared-die candidate records one cycle of 300 μs. By how much does it exceed the declared 250 μs, how much of the 400 μs deadline does it leave once blocking and interference are charged, and which claim does it refute?

**Isolation and interference**: Can you explain why a loaded cycle below the declared worst-case execution time does not prove that the shared hardware added zero interference?

**Model and resource premises**: Can you explain which binary, path, memory, peripheral, and resource-control assumptions permit a sound execution bound on the discrete microcontroller or a shared multicore SoC?

**Paired loads**: Can you explain why the enforcer’s cold refusal routine must be evaluated concurrently with the application processor’s diagnostic memory dump, rather than measured in isolation?
